《System Design Interview 深度指南：從 Senior Engineer 到 Staff-Level Thinking》

用常考題目學會 scalable, reliable, maintainable distributed systems

Part 0：System Design 面試心法

Chapter 1：System Design Interview 到底在考什麼？

1. 這是什麼？

System Design Interview 是大廠（Google、Meta、Amazon、Microsoft、Apple）用來評估 Senior+ 工程師的核心面試環節。面試官會給你一個開放式問題（例如 "Design Twitter"、"Design Uber"），你需要在 35-45 分鐘內設計出一個可擴展的分散式系統。

關鍵認知：這不是考試，是模擬工作場景。

面試官想看的是：如果明天你加入團隊，面對一個新系統需求，你會怎麼思考、怎麼溝通、怎麼做決策？

2. 為什麼需要？

因為 Senior Engineer 的核心價值不是寫 code，而是： - 做正確的技術決策（選 SQL 還是 NoSQL？用 push 還是 pull？） - 預見問題（這個設計在 10x traffic 時會怎樣？） - 溝通複雜概念（讓 PM、其他工程師、VP 都能理解你的方案）

Coding interview 測試你能不能寫出正確的程式。 System Design interview 測試你能不能設計出正確的系統。

3. 不用會怎樣？

  • L4 以下可能不考或只考簡單版本
  • L5+ 幾乎必考，而且權重通常佔 30-50%
  • 如果 System Design 表現差，即使 Coding 全過也可能拿不到 offer
  • 更重要的是：這些能力在實際工作中每天都在用

4. 面試官真正在評估的 6 個維度

維度 1：Requirement Clarification（需求釐清）

Junior 做法： 聽到題目就開始畫圖。

Senior 做法： 花 3-5 分鐘問問題，把模糊的需求變成具體的設計約束。

面試官：Design a chat system.

Senior 會問：
- 1v1 chat 還是 group chat？group 最大多少人？
- 需要支援 offline message 嗎？
- 需要 read receipts 嗎？
- 預期 DAU 多少？peak QPS？
- 需要 end-to-end encryption 嗎？
- 需要支援 file/image sharing 嗎？
- message retention policy？永久保存還是有期限？

為什麼這很重要？

因為 "Design a chat system" 可以是 WhatsApp（10 億用戶、E2E encryption、multimedia）也可以是公司內部的簡單 messaging tool。不問清楚就設計，等於在解錯的問題。

維度 2：Tradeoff Judgment（權衡判斷）

每個設計決策都有 tradeoff。面試官想看你能不能： 1. 識別出有哪些選項 2. 分析每個選項的 pros/cons 3. 根據需求做出合理選擇 4. 清楚解釋為什麼

例子：News Feed 的 fanout 策略

Option A: Fanout on Write (Push model)
- 用戶發文時，立刻推送到所有 follower 的 feed cache
- Pros: 讀取超快（O(1) 從 cache 拿）
- Cons: celebrity user 發文要推送給百萬人，寫入延遲高

Option B: Fanout on Read (Pull model)
- 用戶打開 feed 時，即時去拉所有 following 的最新貼文
- Pros: 寫入簡單
- Cons: 讀取慢，每次都要 merge sort 多個 source

Senior answer:
"Given that most users have < 1000 followers, I'd use fanout-on-write 
as the default. For celebrity users (> 100K followers), I'd switch to 
fanout-on-read to avoid write amplification. This hybrid approach gives 
us O(1) read for 99% of users while handling the celebrity edge case."

維度 3：Scale Estimation（規模估算）

Back-of-the-envelope estimation 不是要你算出精確數字，而是要展示你有「規模感」。

例子：Design URL Shortener

假設：
- 100M DAU
- 每人每天產生 0.1 個短網址 = 10M writes/day
- 讀寫比 100:1 → 1B reads/day
- Write QPS: 10M / 86400 ≈ 115 QPS
- Read QPS: 1B / 86400 ≈ 11,500 QPS
- Peak (2-3x): ~35,000 read QPS

Storage (5 年):
- 每條記錄: short_url(7B) + long_url(100B) + metadata(50B) ≈ 200B
- 5 年: 10M/day × 365 × 5 = 18.25B records
- 總儲存: 18.25B × 200B ≈ 3.65 TB

結論：
- 讀 QPS 不算高，單台 Redis 就能扛
- 儲存量中等，需要 sharding 但不需要太多 shard
- 這是一個 read-heavy, latency-sensitive 的系統

維度 4：Bottleneck Detection（瓶頸識別）

設計完 happy path 後，Senior 會主動指出：「這個設計在哪裡會先爆？」

常見瓶頸：
- Single point of failure（只有一台 DB）
- Hot partition（某個 shard 流量特別大）
- Thundering herd（cache 過期時大量請求同時打 DB）
- Write amplification（一次寫入觸發多次 downstream write）
- Network bandwidth（大量 media file transfer）

維度 5：Communication（溝通能力）

System Design 面試是一場 對話，不是獨白。

好的溝通模式： - "Let me start with the requirements to make sure we're aligned..." - "I see two options here. Option A is... Option B is... Given our requirement for low latency, I'd go with A because..." - "Before I dive deeper, does this high-level architecture make sense? Any area you'd like me to focus on?" - "One concern I have with this design is... Let me address that..."

壞的溝通模式： - 沉默 5 分鐘然後突然畫一大堆東西 - 只講結論不講原因 - 面試官問問題時防禦性回答 - 用太多 buzzword 但解釋不清楚

維度 6：Failure Handling（故障處理）

這是區分 L5 和 L6 最明顯的維度。

L5 會說：
"We use Redis for caching to improve read performance."

L6 會說：
"We use Redis for caching. But I want to address a few failure scenarios:
1. Cache miss storm: If Redis goes down, all traffic hits DB. 
   Mitigation: Circuit breaker + local cache fallback.
2. Hot key: Celebrity user's profile gets millions of reads.
   Mitigation: Replicate hot keys across multiple Redis nodes.
3. Cache inconsistency: After DB write, cache might serve stale data.
   Mitigation: Write-through for critical data, TTL-based for others.
4. Memory pressure: If cache is full, eviction might remove important keys.
   Mitigation: LRU eviction + separate cache tier for hot data."

5. Tradeoffs

面試策略 Pros Cons
花很多時間問需求 設計方向正確 可能沒時間做 deep dive
快速進入設計 有更多時間展示技術深度 可能設計方向錯誤
廣度優先（畫完整架構） 展示全局觀 每個部分都淺
深度優先（挑重點深入） 展示專業度 可能漏掉重要組件

最佳策略：3-5 分鐘需求 → 5 分鐘 high-level → 20-25 分鐘 deep dive（挑 2-3 個重點）→ 5 分鐘 wrap up

6. Failure Modes（面試中常見失敗模式）

失敗模式 症狀 修正方法
Over-engineering 設計了用不到的功能 回到需求，問 "Do we need this?"
Under-designing 只畫了 client → server → DB 加入 cache、queue、CDN 等必要組件
不問需求 假設太多，方向錯誤 養成習慣：前 3 分鐘只問問題
只講 happy path 沒有 failure handling 每個組件都問 "What if this fails?"
數字亂猜 estimation 差 10 倍以上 記住常見數字（見下方）
不互動 獨白 30 分鐘 每 5 分鐘 check in 一次

7. 面試怎麼講？

開場白模板：

"Before I start designing, I'd like to clarify a few requirements 
to make sure we're solving the right problem.

First, let me understand the scale:
- How many DAU are we targeting?
- What's the read/write ratio?
- What's our latency requirement?

Then, functional requirements:
- [specific to the problem]

And non-functional requirements:
- Availability target? (99.9%? 99.99%?)
- Consistency requirement? (strong? eventual?)
- Any geographic distribution needs?"

轉場話術：

需求 → 設計：
"Great, based on these requirements, let me sketch out a high-level architecture..."

High-level → Deep dive：
"Now that we have the overall picture, I'd like to dive deeper into 
[the most interesting/challenging component]. Would that be a good area to focus on?"

遇到不確定的：
"I'm not 100% sure about the exact number here, but my intuition says 
it's in the range of X to Y. Let me reason through it..."

被問到不會的：
"That's a great question. I haven't worked with that specific technology, 
but based on my understanding of similar systems, I'd approach it by..."

8. 具體例子：同一題的 Junior vs Senior 回答

題目：Design a URL Shortener

Junior (L4) 回答：

"OK so we have a service that takes a long URL and returns a short one.
API: POST /shorten {url} → {short_url}
     GET /{short_code} → 301 redirect

Database: MySQL table with (id, short_code, long_url, created_at)
Generate short_code using base62 encoding of auto-increment ID.
Done."

Senior (L5) 回答：

"Let me first clarify requirements...
[asks about scale, read/write ratio, custom aliases, analytics, expiration]

Estimation: 100M DAU, 10M writes/day, 1B reads/day → read-heavy system.
Storage: 3.65 TB over 5 years.

Key generation: I'll use a pre-generated key service (KGS) instead of 
base62(auto_increment) because:
1. No single point of failure on ID generation
2. No collision risk
3. Can pre-validate uniqueness

Architecture:
- Write path: Client → API → KGS → DB (write-through cache)
- Read path: Client → API → Cache (Redis) → DB (fallback)
- Cache hit rate should be > 95% given Zipf distribution of URL access

Deep dive on caching:
- Use Redis cluster, 3.65TB won't fit in memory but top 20% URLs 
  handle 80% traffic → cache ~700GB
- TTL: 24h for regular, longer for popular URLs
- Cache-aside pattern with async refresh for hot keys"

Staff (L6) 回答會額外加：

"A few additional considerations:

1. Abuse prevention: Rate limiting per IP/user, URL blacklist checking,
   phishing detection before creating short URLs.

2. Analytics pipeline: Async event stream (Kafka) for click tracking,
   geo distribution, referrer analysis. Separate from serving path.

3. Multi-region: DNS-based routing to nearest region. Each region has 
   full read replica. Writes go to primary region, async replicate.
   Tradeoff: eventual consistency on new URLs (acceptable, < 1s lag).

4. Failure modes:
   - KGS down: Pre-fetch batch of keys, local buffer survives 
     KGS outage for ~1 hour
   - Redis down: Circuit breaker, fallback to DB with connection pooling
   - DB down: Read from replica, queue writes for retry

5. Observability: Track p99 redirect latency, cache hit rate, 
   KGS key pool size (alert when < 10% remaining)"

9. 常見追問

追問 考察點
"How would you handle 10x traffic spike?" Scalability thinking
"What if your database goes down?" Fault tolerance
"How do you ensure no duplicate short URLs?" Consistency
"How would you add analytics?" System extensibility
"What metrics would you monitor?" Operational maturity
"How would you migrate from monolith to this?" Practical experience
"What would you do differently with unlimited budget?" Vision vs pragmatism

10. Senior-Level Summary

✅ System Design Interview 的本質：
   - 不是背答案，是展示思考過程
   - 不是畫完美架構，是做合理 tradeoff
   - 不是獨白，是協作式設計對話

✅ 6 個評估維度：
   1. Requirement Clarification
   2. Tradeoff Judgment
   3. Scale Estimation
   4. Bottleneck Detection
   5. Communication
   6. Failure Handling

✅ 時間分配（45 分鐘）：
   - 0-5 min: Requirements
   - 5-10 min: High-level design
   - 10-35 min: Deep dive (2-3 areas)
   - 35-40 min: Bottlenecks + failure modes
   - 40-45 min: Wrap up + questions

✅ 最重要的心態轉換：
   從 "我要設計一個完美系統" 
   變成 "我要展示我如何思考和做決策"

Part 1：一套萬用答題框架

Chapter 2：7-Step System Design Interview Framework

1. 這是什麼？

一套結構化的答題框架，讓你在 35-45 分鐘的面試中有條理地展開設計。這不是死板的公式，而是一個思考的骨架 — 你可以根據題目調整每步的時間和深度。

7 個步驟：

Step 1: Requirement Clarification (3-5 min)
Step 2: API Design (3-5 min)
Step 3: Back-of-the-envelope Estimation (3-5 min)
Step 4: Data Model (3-5 min)
Step 5: High-Level Architecture (5-8 min)
Step 6: Deep Dive (10-15 min)
Step 7: Bottlenecks + Failure Modes (5-8 min)

2. 為什麼需要？

  • 避免漫無目的：沒有框架的人容易東講一點西講一點，面試官跟不上
  • 確保覆蓋面：不會漏掉重要面向（很多人忘記 estimation 或 failure mode）
  • 控制時間：知道什麼時候該往下走，不會卡在某一步太久
  • 展示結構化思維：Senior engineer 的標誌就是能把複雜問題拆解成可管理的步驟

3. 不用會怎樣？

  • 面試時腦袋一片空白，不知道從哪開始
  • 花 20 分鐘在不重要的細節上，重要的部分沒時間講
  • 面試官覺得你思路混亂，給 "not structured" 的 feedback
  • 漏掉 failure mode 和 scalability，被評為 "junior-level thinking"

4. 七步詳解

Step 1: Requirement Clarification

目標： 把開放式問題變成有明確邊界的設計問題。

必問清單：

Functional Requirements（功能需求）:
- 核心功能是什麼？（MVP scope）
- 用戶可以做什麼操作？
- 有哪些 edge case 需要處理？

Non-Functional Requirements（非功能需求）:
- Scale: DAU? Peak QPS?
- Latency: p99 要求？
- Availability: 99.9%? 99.99%?
- Consistency: Strong? Eventual?
- Durability: 資料可以丟嗎？

Constraints（限制）:
- 地理分佈？Multi-region?
- 預算限制？
- 現有系統整合？

面試話術：

"Before I jump into the design, I'd like to spend a couple of minutes 
understanding the scope. Let me ask a few clarifying questions..."

"For the MVP, I'll focus on [core features] and mention [nice-to-haves] 
as extensions if we have time."

"Based on your answers, let me summarize the requirements:
- Functional: [list]
- Non-functional: [list]
- Out of scope: [list]
Does this align with what you had in mind?"

Anti-pattern： - ❌ 不問任何問題就開始設計 - ❌ 問太多問題（超過 5 分鐘） - ❌ 問面試官 "What should I design?"（你應該提出方案讓他確認） - ❌ 假設所有功能都要做（要主動 scope down）

具體例子 — Design Instagram：

好的問法：
Q: "Are we focusing on the photo sharing and feed, or also stories, 
    reels, DMs, and explore?"
A: "Let's focus on photo upload and news feed."

Q: "What's our target scale? Instagram-level (~2B MAU) or smaller?"
A: "Let's design for Instagram scale."

Q: "For the feed, should it be chronological or ranked?"
A: "Ranked, like the real Instagram."

Q: "Do we need real-time updates or is pull-to-refresh acceptable?"
A: "Pull-to-refresh is fine for MVP."

整理後：
Functional: Upload photo, view feed (ranked), follow/unfollow, like
Non-functional: 2B MAU, 500M DAU, p99 feed load < 500ms, 
               99.99% availability, eventual consistency OK for feed
Out of scope: Stories, Reels, DMs, Explore, Ads

Step 2: API Design

目標： 定義系統的外部介面，讓面試官知道你的系統「長什麼樣」。

格式：

REST API 風格（最常用）：

POST /v1/photos
  Request: { user_id, image_data, caption, location }
  Response: { photo_id, url, created_at }

GET /v1/feed?user_id={id}&page_size=20&cursor={cursor}
  Response: { photos: [...], next_cursor }

POST /v1/follow
  Request: { follower_id, followee_id }
  Response: { success: true }

POST /v1/like
  Request: { user_id, photo_id }
  Response: { success: true, like_count }

Senior-level 加分點：

  1. Pagination：用 cursor-based 而非 offset-based 為什麼？Offset-based 在資料變動時會重複或漏掉項目。 Cursor-based 用 last_seen_id 或 timestamp 作為錨點，更穩定。

  2. Idempotency：寫入 API 加 idempotency key POST /v1/photos Header: Idempotency-Key: uuid-xxx → 重試不會產生重複照片

  3. Rate Limiting：在 API 層面提及 Response Header: X-RateLimit-Remaining: 95 429 Too Many Requests when exceeded

  4. Versioning：URL path versioning (/v1/) 或 header versioning

Anti-pattern： - ❌ 花太多時間在 API 細節上（這不是 API design 面試） - ❌ 忘記 pagination - ❌ 用 GET 做有 side effect 的操作 - ❌ 不考慮 error response

Step 3: Back-of-the-envelope Estimation

目標： 用粗略計算確定系統的規模，指導後續的技術選型。

計算模板：

1. Traffic estimation:
   - DAU = X
   - Actions per user per day = Y
   - Total requests/day = X × Y
   - QPS = Total / 86400
   - Peak QPS = QPS × 3

2. Storage estimation:
   - Size per record = Z bytes
   - Records per day = X × Y
   - Storage per year = Records/day × 365 × Z
   - 5-year storage = above × 5

3. Bandwidth estimation:
   - Incoming: Write QPS × avg request size
   - Outgoing: Read QPS × avg response size

4. Memory estimation (for cache):
   - Follow 80/20 rule: cache top 20% of data
   - Cache size = Total daily data × 20%

具體例子 — Design Twitter：

Assumptions:
- 300M MAU, 150M DAU
- Each user: 2 tweets/day (write), 100 feed views/day (read)
- Average tweet: 280 chars + metadata ≈ 500 bytes
- 10% tweets have media (average 500KB)

Traffic:
- Write: 150M × 2 = 300M tweets/day
- Write QPS: 300M / 86400 ≈ 3,500 QPS
- Peak write QPS: ~10,000 QPS
- Read: 150M × 100 = 15B feed requests/day
- Read QPS: 15B / 86400 ≈ 175,000 QPS
- Peak read QPS: ~500,000 QPS
→ 結論：極度 read-heavy (50:1 ratio)，需要大量 cache

Storage (text only):
- 300M tweets/day × 500B = 150GB/day
- Per year: ~55TB
- 5 years: ~275TB (text only)
- With media: 300M × 10% × 500KB = 15TB/day → 需要 object storage

Memory (cache):
- Cache 20% of daily tweets: 150GB × 20% = 30GB
- 一台 Redis 128GB 就夠放一天的 hot data
- Feed cache: 150M users × 20 tweets × 8B (tweet_id) = 24GB
→ 結論：Cache 需求合理，Redis cluster 可以搞定

Bandwidth:
- Incoming: 10K QPS × 500B ≈ 5MB/s (text) + media upload
- Outgoing: 500K QPS × 5KB (rendered tweet) ≈ 2.5GB/s
→ 結論：需要 CDN 來分擔 outgoing bandwidth

面試話術：

"Let me do a quick estimation to understand the scale we're dealing with.
I'll make some assumptions — please correct me if they seem off.

[do the math]

So we're looking at roughly 500K read QPS at peak. This tells me:
1. We definitely need a caching layer
2. A single database won't cut it — we need sharding
3. The read/write ratio of 50:1 suggests we should optimize for reads"

Anti-pattern： - ❌ 花超過 5 分鐘在計算上 - ❌ 追求精確數字（差 2-3 倍都可以接受） - ❌ 算完不做結論（數字本身不重要，重要的是它告訴你什麼） - ❌ 完全跳過 estimation（面試官會覺得你沒有規模感）

Step 4: Data Model

目標： 定義核心資料結構和儲存選型。

思考順序：

1. 識別核心 entities（User, Tweet, Follow, Like...）
2. 定義 relationships（1:1, 1:N, N:N）
3. 選擇儲存類型（SQL? NoSQL? Cache? Object Store?）
4. 設計 schema 或 key structure
5. 考慮 access patterns（怎麼查？怎麼寫？）

具體例子 — Twitter Data Model：

Core Entities:

User:
  user_id (PK, bigint)
  username (unique, varchar)
  email (varchar)
  profile_pic_url (varchar)
  created_at (timestamp)
  → Storage: SQL (strong consistency for user data)

Tweet:
  tweet_id (PK, bigint, snowflake ID)
  user_id (FK)
  content (text, max 280 chars)
  media_urls (json array)
  created_at (timestamp)
  like_count (int)
  retweet_count (int)
  → Storage: SQL for metadata, Object Store for media

Follow:
  follower_id (PK1)
  followee_id (PK2)
  created_at (timestamp)
  → Storage: SQL or Graph DB
  → Access pattern: "Who does user X follow?" and "Who follows user X?"

Feed (precomputed):
  user_id (PK)
  tweet_ids (sorted list, most recent first)
  → Storage: Redis sorted set
  → Key: feed:{user_id}, Score: timestamp, Value: tweet_id

Timeline Cache:
  → Redis: tweet:{tweet_id} → serialized tweet object
  → TTL: 24-48 hours

選型決策框架：

需求 選擇 原因
User profile (strong consistency) PostgreSQL ACID, complex queries
Tweet storage (high write throughput) Cassandra or PostgreSQL + sharding Append-heavy, time-series-like
Feed cache (fast read) Redis Sorted Set O(1) read, sorted by time
Media files S3 + CDN Large binary, immutable
Search Elasticsearch Full-text search, ranking
Analytics Kafka → Data Warehouse Async, batch processing

Anti-pattern： - ❌ 所有東西都用 SQL - ❌ 所有東西都用 NoSQL - ❌ 不考慮 access pattern 就選 DB - ❌ 忘記 index 設計

Step 5: High-Level Architecture

目標： 畫出系統的主要組件和它們之間的關係。

標準組件清單（按需選用）：

Client Layer:
  - Web client
  - Mobile client
  - CDN (static assets)

API Layer:
  - Load Balancer

  3. 你最擅長的：如果你對 caching 很熟，可以主動提議 "I'd like to dive deeper into our caching strategy"

Deep dive 的深度標準：

淺（不夠）：
"We use Redis for caching."

中（L5 水準）：
"We use Redis cluster with cache-aside pattern. 
Key format: feed:{user_id}, value: sorted list of tweet_ids.
TTL: 24 hours. On cache miss, we query DB and backfill."

深（L6 水準）：
"Let me walk through the caching strategy in detail:

1. Cache topology: Redis Cluster, 6 nodes (3 primary + 3 replica)
   - Sharded by user_id hash
   - Each node handles ~50K QPS

2. Cache pattern: Cache-aside with async refresh
   - On read: check cache → if miss, query DB, write to cache
   - On write: invalidate cache, let next read backfill
   - Why not write-through? Because feed is computed (not raw data)

3. Hot key handling:
   - Celebrity users (>1M followers) get replicated to all nodes
   - Local in-memory cache (Guava, 30s TTL) as L1 before Redis

4. Cache stampede prevention:
   - Probabilistic early expiration (jitter on TTL)
   - Mutex lock on cache miss (only one thread rebuilds)

5. Failure mode:
   - Redis node down → replica promotes in <5s
   - Entire Redis down → circuit breaker, serve from DB with 
     degraded latency (p99: 50ms → 500ms)
   - Monitor: cache hit rate (alert if < 90%), eviction rate"

目標： 主動指出設計的弱點，並提出解決方案。

Bottleneck 分析模板：

For each component, ask:
1. What's the throughput limit?
2. What happens when it's exceeded?
3. How do we scale it?
4. What's the single point of failure?
5. What's the blast radius if it fails?

具體例子：

Bottleneck 1: Database write throughput
- Problem: 10K write QPS, single PostgreSQL handles ~5K
- Solution: Shard by user_id, 4 shards → each handles 2.5K QPS
- Tradeoff: Cross-shard queries become expensive
- Mitigation: Design access patterns to be shard-local

Bottleneck 2: Fanout for celebrity users
- Problem: User with 10M followers → 10M cache writes per tweet
- Solution: Hybrid fanout — celebrities use pull model
- Tradeoff: Celebrity followers have slightly higher read latency
- Mitigation: Pre-fetch celebrity tweets on feed load

Bottleneck 3: Hot partition in cache
- Problem: Trending topic → millions of reads on same cache key
- Solution: Replicate hot keys, add local cache layer
- Tradeoff: Slightly stale data (30s)
- Mitigation: Acceptable for non-critical data like like_count

Failure Mode 1: Cache cluster failure
- Impact: All reads hit DB, DB overloaded
- Detection: Cache hit rate drops below 50%
- Mitigation: Circuit breaker, serve degraded feed (fewer items)
- Recovery: Redis auto-failover, warm up cache gradually

Failure Mode 2: Kafka consumer lag
- Impact: Feed updates delayed, users see stale feed
- Detection: Consumer lag metric > 1 minute
- Mitigation: Auto-scale consumers, alert on-call
- Recovery: Consumers catch up, feed eventually consistent

Failure Mode 3: Database failover
- Impact: Writes fail for 10-30 seconds during failover
- Detection: Connection errors spike
- Mitigation: Retry with exponential backoff, queue writes
- Recovery: New primary elected, connections re-established

Part 2：核心分散式系統觀念

Chapter 3：Scalability 可擴展性

1. 這是什麼？

Scalability（可擴展性）是指系統在負載增加時，能夠通過增加資源來維持或提升效能的能力。

一個 scalable 的系統不是「現在很快」，而是「當用戶從 1 萬變成 1 億時，我知道怎麼讓它繼續快」。

核心問題： 當 traffic 增加 10x，你的系統需要做什麼改變？

  • 如果答案是「什麼都不用改」→ 完美（但幾乎不可能）
  • 如果答案是「加機器就好」→ 很好（horizontally scalable）
  • 如果答案是「要重新設計」→ 有問題（scalability bottleneck）

2. 為什麼需要？

因為成功的產品一定會成長。今天 1000 QPS 的系統，明年可能要扛 100,000 QPS。

真實案例： - Twitter 2007 年用 Ruby on Rails monolith，到 2012 年因為 scale 問題重寫了整個 backend - Instagram 2012 年被 Facebook 收購時只有 13 個工程師，但已經有 3000 萬用戶 — 因為架構設計得好 - Pokémon GO 2016 年上線第一天就超過預期 50 倍流量，Google Cloud 團隊緊急擴容

3. 不用會怎樣？

  • 系統在流量高峰時崩潰（Black Friday、新年倒數、病毒式傳播）
  • 加機器也沒用（因為有 stateful bottleneck）
  • 資料庫成為瓶頸，整個系統卡住
  • 用戶體驗變差，p99 latency 從 100ms 變成 10s
  • 最終：用戶流失、營收損失、工程師 on-call 地獄

4. 常見 Implementation

4.1 Vertical Scaling vs Horizontal Scaling

Vertical Scaling (Scale Up):
- 換更大的機器（更多 CPU、RAM、SSD）
- 例：從 8 core / 32GB 升級到 64 core / 256GB
- 優點：簡單，不需要改 code
- 缺點：有上限（最大的機器也就那樣）、單點故障、成本指數增長

Horizontal Scaling (Scale Out):
- 加更多機器
- 例：從 1 台 server 變成 10 台 server + load balancer
- 優點：理論上無上限、容錯性好
- 缺點：需要 stateless 設計、分散式系統複雜度

面試中怎麼講：

"For this system, I'd design for horizontal scaling from the start. 
The application servers will be stateless — all session state stored 
in Redis, all persistent data in the database. This way, we can add 
more servers behind the load balancer as traffic grows."

什麼時候用 vertical scaling？ - 資料庫（在 sharding 之前，先 scale up 是最簡單的） - 單機計算密集型任務（ML training、video transcoding） - 早期 startup（用戶少，不值得投入分散式架構的複雜度）

4.2 Stateless vs Stateful Service

Stateless Service:
- 每個 request 獨立，server 不保存任何 client state
- 任何 server 都能處理任何 request
- 例：REST API server、Lambda function

Stateful Service:
- Server 保存了 client 的狀態
- 特定 client 必須路由到特定 server
- 例：WebSocket connection、game server、database

為什麼 stateless 更好 scale？

Stateless:
Client A ──→ Server 1 ✓
Client A ──→ Server 2 ✓  (任何 server 都行)
Client A ──→ Server 3 ✓

→ 加 server 就能 scale，load balancer 隨便分配

Stateful:
Client A ──→ Server 1 ✓  (只能去 Server 1，因為 state 在那)
Client A ──→ Server 2 ✗
Client A ──→ Server 3 ✗

→ Server 1 掛了，Client A 的 state 就丟了
→ Server 1 過載了，不能簡單地把 Client A 移走

如何把 stateful 變 stateless：

Before (stateful):
  Server memory: { session_id: "abc", user: "john", cart: [...] }

After (stateless):
  Server: no local state
  Redis: { "session:abc": { user: "john", cart: [...] } }

  → 任何 server 都能讀 Redis 拿到 session
  → Server 掛了不影響 session
  → 可以自由 scale server 數量

4.3 Partitioning（分區）

當單一節點無法處理所有資料或流量時，把資料分散到多個節點。

Horizontal Partitioning (Sharding):
- 把同一張 table 的 rows 分散到不同 DB
- 例：user_id % 4 → 分到 4 個 shard

Vertical Partitioning:
- 把不同的 columns 或 tables 分到不同 DB
- 例：User profile → DB1, User posts → DB2, User messages → DB3

Functional Partitioning:
- 按功能拆分成不同的 service + DB
- 例：Auth Service + Auth DB, Order Service + Order DB
- 這就是 microservice 的核心思想

4.4 Replication（複製）

把資料複製到多個節點，目的是： 1. 提高讀取吞吐量（多個 replica 分擔讀取） 2. 提高可用性（一個節點掛了，其他還能服務） 3. 降低延遲（把 replica 放在離用戶近的地方）

Leader-Follower Replication:
- 1 個 Leader 處理所有寫入
- N 個 Follower 複製 Leader 的資料，處理讀取
- 例：MySQL primary + 3 read replicas

寫入：Client → Leader → replicate to Followers
讀取：Client → any Follower (or Leader)

Tradeoff: 
- Follower 可能有 replication lag（幾毫秒到幾秒）
- 讀取可能拿到 stale data
- 如果需要 read-after-write consistency，要讀 Leader

4.5 Fanout

Fanout 是指一個事件觸發多個下游操作的模式。

Fanout on Write (Push):
- 事件發生時，立刻推送給所有相關方
- 例：用戶發 tweet → 立刻寫入所有 follower 的 feed cache
- Pros: 讀取快（已經預計算好了）
- Cons: 寫入放大（1 次寫入 → N 次 downstream write）

Fanout on Read (Pull):
- 讀取時才去收集相關資料
- 例：用戶打開 feed → 即時查詢所有 following 的最新 tweet
- Pros: 寫入簡單
- Cons: 讀取慢（要 merge 多個 source）

Hybrid Fanout:
- 普通用戶：fanout on write（follower 少，寫入成本低）
- Celebrity 用戶：fanout on read（follower 太多，寫入成本太高）
- 這是 Twitter/Instagram 實際使用的策略

具體數字：

普通用戶（500 followers）發一條 tweet：
- Fanout on write: 500 次 cache write ≈ 5ms（可接受）

Celebrity（10M followers）發一條 tweet：
- Fanout on write: 10,000,000 次 cache write ≈ 幾分鐘（不可接受）
- Fanout on read: 讀取時多查一個 source ≈ 增加 10ms（可接受）

4.6 Read Scaling vs Write Scaling

Read-Heavy System (read:write > 10:1):
- 例：Instagram feed, Wikipedia, 商品頁
- 策略：Cache + Read Replicas + CDN
- 相對容易 scale

Write-Heavy System (write:read ≈ 1:1 or write > read):
- 例：Logging system, IoT sensor data, Chat messages
- 策略：Sharding + Async write + Append-only storage
- 比較難 scale

Mixed System:
- 例：E-commerce（瀏覽多、下單少，但下單要 strong consistency）
- 策略：CQRS (Command Query Responsibility Segregation)
  - 讀和寫用不同的 model/store
  - 寫入到 primary DB
  - 讀取從 optimized read store (denormalized, cached)

   5. Shard when you must, not before

✅ Scaling 的優先順序（從簡單到複雜）：
   1. Optimize code (fix N+1 queries, add indexes)
   2. Add caching (Redis, CDN)
   3. Add read replicas
   4. Vertical scaling (bigger machine)
   5. Horizontal scaling (more machines)
   6. Sharding (last resort for DB)

✅ Staff-level insight：
   "The best scaling strategy is the one you don't need yet. 
   Design for it, but don't implement it until the metrics 
   tell you it's necessary. Premature optimization of 
   scalability adds complexity without value."

✅ 面試中的 signal：
   - Junior: "We can just add more servers"
   - Senior: "Given the read-heavy pattern, I'd add caching first, 
     then read replicas. Sharding is plan C if we hit write limits."
   - Staff: "I'd instrument the system to measure actual bottlenecks 
     before deciding. My hypothesis is [X] will be the first limit, 
     and here's my plan for when we hit it."

Chapter 4：Availability / Reliability / Fault Tolerance

1. 這是什麼？

三個相關但不同的概念：

Availability（可用性）:
- 系統在任意時刻能正常服務的機率
- 通常用 "幾個 9" 表示
- 99.9% = 每年 8.76 小時 downtime
- 99.99% = 每年 52.6 分鐘 downtime
- 99.999% = 每年 5.26 分鐘 downtime

Reliability（可靠性）:
- 系統在一段時間內持續正確運作的機率
- 強調「正確」— 不只是活著，還要給出正確結果
- MTBF (Mean Time Between Failures): 平均多久壞一次
- MTTR (Mean Time To Recovery): 壞了多久能修好

Fault Tolerance（容錯性）:
- 系統在部分組件故障時仍能繼續運作的能力
- 不是「不會壞」，而是「壞了也能撐住」
- 核心思想：Failure is inevitable, design for it

關鍵公式：

Availability = MTBF / (MTBF + MTTR)

提高 availability 的兩種方式：
1. 增加 MTBF（讓系統更少壞）→ 更好的硬體、更少的 bug
2. 減少 MTTR（壞了更快修好）→ 自動 failover、快速 deploy

2. 為什麼需要？

商業影響：

Amazon: 每 100ms 延遲 = 1% 營收損失
Google: 每 500ms 延遲 = 20% 搜尋量下降
Facebook: 2021 年 6 小時 outage = 估計損失 $60M+ 廣告收入

99.9% vs 99.99% 的差異：
- 99.9% = 每月 43 分鐘 downtime
- 99.99% = 每月 4.3 分鐘 downtime
- 對於支付系統，43 分鐘 downtime 可能 = 數百萬美元損失

SLA 的商業意義：

如果你的 SLA 是 99.99%，但實際只做到 99.9%：
- 客戶可以要求賠償（通常是 service credit）
- AWS S3 SLA: 99.9% → 低於此賠 10% credit
- 低於 99.0% → 賠 25% credit

3. 不用會怎樣？

  • 系統一個組件掛了，整個系統跟著掛（cascading failure）
  • 半夜被 page，花 2 小時手動修復
  • 用戶看到 500 error，轉去用競爭對手的產品
  • 面試時只講 happy path，被評為 "doesn't think about production"

4. 常見 Implementation

4.1 Redundancy（冗餘）

Server Redundancy:
- 至少 2 台 server 做同一件事
- Active-Active: 兩台都在服務（load balance between them）
- Active-Passive: 一台服務，一台待命（failover when active dies）

Database Redundancy:
- Primary + Replica(s)
- Multi-AZ deployment（AWS RDS 自動做）
- Cross-region replication（for disaster recovery）

Network Redundancy:
- Multiple network paths
- Multiple ISPs
- DNS failover

Data Center Redundancy:
- Multi-AZ (同 region 不同機房)
- Multi-Region (不同地理位置)

面試中怎麼講：

"For high availability, I'll deploy across 3 availability zones. 
Each AZ has its own set of application servers, cache, and a 
database replica. If one AZ goes down, the load balancer routes 
traffic to the remaining two. The database uses synchronous 
replication within the region to ensure zero data loss on failover."

4.2 Failover（故障轉移）

Database Failover:
- Primary dies → Replica promoted to Primary
- Automatic (managed services like RDS) or manual
- Failover time: 10-60 seconds (automatic), minutes-hours (manual)

DNS Failover:
- Health check detects server/region down
- DNS record updated to point to healthy endpoint
- Propagation delay: 30s - 5min (depending on TTL)

Application Failover:
- Load balancer health check fails
- Traffic routed to healthy instances
- Failover time: < 10 seconds

Failover 的陷阱：

Split Brain Problem:
- Primary 沒真的死，只是 network partition
- Replica 被 promote 成新 Primary
- 現在有兩個 Primary 同時接受寫入
- 資料不一致！

Solution:
- Fencing token: 舊 Primary 的 token 失效，無法寫入
- Quorum: 需要多數節點同意才能成為 Primary
- STONITH (Shoot The Other Node In The Head): 強制關閉舊 Primary

4.3 Retry（重試）

Simple Retry:
- 失敗了就重試
- 問題：如果 server 過載，重試會讓情況更糟

Exponential Backoff:
- 第 1 次重試：等 1s
- 第 2 次重試：等 2s
- 第 3 次重試：等 4s
- 第 4 次重試：等 8s
- 加上 jitter（隨機偏移）避免 thundering herd

Retry with Jitter:
wait_time = min(cap, base * 2^attempt) + random(0, base)

例：base=1s, cap=30s
- Attempt 1: 1-2s
- Attempt 2: 2-3s  
- Attempt 3: 4-5s
- Attempt 4: 8-9s

什麼時候該重試，什麼時候不該：

✅ 該重試：
- Network timeout (可能是暫時的)
- 503 Service Unavailable
- Connection refused (server 可能在重啟)
- Database deadlock

❌ 不該重試：
- 400 Bad Request (你的 request 有問題，重試也一樣)
- 401 Unauthorized (token 過期，要 refresh 不是 retry)
- 404 Not Found (資源不存在)
- 409 Conflict (需要 resolve conflict，不是 retry)

⚠️ 要小心重試：
- 非 idempotent 操作 (POST /payment → 可能重複扣款！)
- Solution: Idempotency key

4.4 Timeout（超時）

為什麼需要 timeout：
- 沒有 timeout → 一個慢的 downstream 會拖垮整個系統
- Thread/connection 被佔住 → 資源耗盡 → 所有 request 都失敗

Timeout 設定原則：
- Connect timeout: 1-5s (建立連線)
- Read timeout: 5-30s (等待回應)
- 總 timeout < 用戶能接受的等待時間

例子：
- API Gateway → Service A: timeout 5s
- Service A → Database: timeout 3s
- Service A → External API: timeout 10s (外部不可控)

Cascading timeout 問題：
- Gateway timeout: 30s
- Service A timeout to B: 30s
- Service B timeout to C: 30s
- 如果 C 慢了，A 和 Gateway 都在等
- Solution: 每層 timeout 要比下層短
  Gateway: 10s > Service A: 5s > Service B: 3s

4.5 Circuit Breaker（斷路器）

靈感來自電路的保險絲：電流過大時自動斷開，保護電路。

三個狀態：
┌─────────┐    failure threshold    ┌──────┐
│  CLOSED  │ ─────────────────────→ │ OPEN │
│(正常通過) │                         │(直接失敗)│
└─────────┘                         └──┬───┘
     ↑                                 │
     │         timeout expires         │
     │                                 ▼
     │                          ┌───────────┐
     └──────── success ─────────│ HALF-OPEN │
                                │(試探性通過) │
                                └───────────┘

CLOSED: 正常狀態，所有 request 通過
  → 如果連續 N 次失敗（或失敗率 > X%），切換到 OPEN

OPEN: 斷路狀態，所有 request 直接返回 error（不打 downstream）
  → 等待 timeout（例如 30s）後，切換到 HALF-OPEN

HALF-OPEN: 試探狀態，允許少量 request 通過
  → 如果成功，切換回 CLOSED
  → 如果失敗，切換回 OPEN

為什麼需要 Circuit Breaker？

Without Circuit Breaker:
- Service B 掛了
- Service A 每個 request 都等 B timeout (5s)
- A 的 thread pool 被佔滿
- A 也開始 timeout
- A 的上游也開始 timeout
- 整個系統 cascading failure

With Circuit Breaker:
- Service B 掛了
- A 偵測到 B 連續失敗 5 次
- Circuit breaker OPEN
- A 直接返回 fallback response（不等 B）
- A 的 thread pool 正常
- 30s 後 half-open，試探 B 是否恢復

實際 implementation：

// Netflix Hystrix (deprecated but concept lives on)
// Resilience4j (modern Java)
CircuitBreaker cb = CircuitBreaker.ofDefaults("serviceB");

Supplier<String> decorated = CircuitBreaker
    .decorateSupplier(cb, () -> serviceB.call());

Try<String> result = Try.ofSupplier(decorated)
    .recover(throwable -> "fallback response");

4.6 Bulkhead（隔艙）

靈感來自船的隔艙設計：一個艙進水不會沉整艘船。

應用在系統中：
- 把資源（thread pool、connection pool）隔離
- 一個 downstream 出問題不會影響其他

例子：
Without Bulkhead:
- 共用 thread pool: 100 threads
- Service B 慢了 → 100 threads 都在等 B
- Service C 的 request 也拿不到 thread → 全部失敗

With Bulkhead:
- Service B thread pool: 30 threads
- Service C thread pool: 30 threads  
- Service D thread pool: 40 threads
- Service B 慢了 → 只有 30 threads 被佔
- Service C 和 D 不受影響

4.7 Fallback（降級）

當主要功能不可用時，提供替代方案：

例子 1: 推薦系統
- 正常：個人化推薦（ML model）
- Fallback: 熱門內容（pre-computed, cached）
- 用戶體驗稍差，但不是空白頁

例子 2: 搜尋
- 正常：Elasticsearch full-text search
- Fallback: 簡單的 DB LIKE query（慢但能用）
- 或者：顯示 "Search is temporarily unavailable, 
         here are trending topics"

例子 3: 用戶頭像
- 正常：從 CDN 載入用戶上傳的頭像
- Fallback: 顯示 default avatar
- 不影響核心功能

Fallback 的層次：
Level 1: 用 cache 的舊資料（stale but available）
Level 2: 用簡化版功能（degraded but functional）
Level 3: 顯示友善的 error message（graceful failure）
Level 4: 完全不可用（worst case）

4.8 Graceful Degradation（優雅降級）

系統在壓力下主動放棄非核心功能，保護核心功能：

例子：電商網站在 Black Friday

正常模式（所有功能開啟）：
✓ 商品瀏覽
✓ 個人化推薦
✓ 商品評論
✓ 即時庫存
✓ 購物車
✓ 結帳

壓力模式（流量超過 80% capacity）：
✓ 商品瀏覽
✗ 個人化推薦 → 改用靜態推薦
✗ 商品評論 → 隱藏評論區
✓ 即時庫存
✓ 購物車
✓ 結帳

極端模式（流量超過 95% capacity）：
✓ 商品瀏覽（簡化版，無圖片）
✗ 推薦
✗ 評論
✗ 即時庫存 → 改用 "可能有貨"
✓ 購物車
✓ 結帳

核心原則：寧可讓非核心功能掛掉，也不能讓結帳掛掉。

4.9 Disaster Recovery（災難恢復）

RPO (Recovery Point Objective):
- 可以接受丟失多少資料？
- RPO = 0: 不能丟任何資料（synchronous replication）
- RPO = 1 hour: 最多丟 1 小時的資料（hourly backup）
- RPO = 24 hours: 最多丟 1 天的資料（daily backup）

RTO (Recovery Time Objective):
- 系統需要多快恢復？
- RTO = 0: 不能有任何 downtime（active-active multi-region）
- RTO = 1 hour: 1 小時內恢復（warm standby）
- RTO = 24 hours: 1 天內恢復（cold backup）

DR 策略（從便宜到貴）：

1. Backup & Restore (RTO: hours, RPO: hours)
   - 定期備份到 S3
   - 災難時從備份恢復
   - 最便宜，但恢復最慢

2. Pilot Light (RTO: 10-30 min, RPO: minutes)
   - 核心系統在 DR region 保持最小運行
   - 災難時 scale up DR region

3. Warm Standby (RTO: minutes, RPO: seconds)
   - DR region 運行完整系統但 scaled down
   - 災難時 scale up + DNS failover

4. Active-Active (RTO: ~0, RPO: ~0)
   - 兩個 region 同時服務流量
   - 災難時只是一個 region 的流量轉到另一個
   - 最貴，但最快恢復

5. Tradeoffs

策略 Availability 提升 成本 複雜度 適用場景
Single server 99% $ Low Dev/test
Multi-AZ 99.9% $$ Medium Production
Multi-Region active-passive 99.95% $$$ High Critical services
Multi-Region active-active 99.99% $$$$ Very High Payment, auth

8. 具體例子

例子 1：Netflix 的 Chaos Engineering

Netflix 的哲學：
"The best way to avoid failure is to fail constantly."

Chaos Monkey: 隨機殺掉 production server
- 確保系統能自動恢復
- 工程師被迫設計 fault-tolerant 系統

Chaos Kong: 模擬整個 region 掛掉
- 確保 multi-region failover 正常運作
- 每季度演練一次

結果：
- Netflix 在 AWS us-east-1 大規模故障時幾乎不受影響
- 因為他們每天都在練習 failure recovery

例子 2：Payment System 的 Availability 設計

需求：99.99% availability, 0 data loss

Architecture:
1. Multi-region active-active
   - US-East + US-West 同時服務
   - 用戶路由到最近的 region

2. Synchronous replication for payment records
   - 寫入必須在兩個 region 都確認才算成功
   - Tradeoff: 增加 ~50ms latency
   - 但保證 RPO = 0

3. Idempotency everywhere
   - 每個 payment request 有 unique idempotency key
   - 重試不會重複扣款
   - 即使 failover 過程中有 duplicate request

4. Circuit breaker to payment providers
   - Visa API 掛了 → 切換到 Mastercard
   - 所有 provider 都掛了 → queue payment, process later
   - 用戶看到 "Payment processing, you'll receive confirmation shortly"

5. Reconciliation job
   - 每小時比對兩個 region 的資料
   - 發現不一致 → alert + auto-fix or manual review

追問 Senior 回答

10. Senior-Level Summary

✅ 核心原則：
   1. Everything fails, all the time (Werner Vogels, AWS CTO)
   2. Design for failure, not for perfection
   3. Detect fast, recover fast, degrade gracefully
   4. The more 9s you need, the more it costs (exponentially)

✅ Availability 計算：
   - 串聯系統：A × B × C (每個都要活)
   - 並聯系統：1 - (1-A) × (1-B) (任一個活就行)
   - 例：兩台 99% 的 server 並聯 = 1 - 0.01² = 99.99%

     analysis, not arbitrary 9s."

✅ 記住：
   Availability is not a feature you add later.
   It's a property that emerges from good design decisions 
   made throughout the system.

Chapter 5：Latency / Throughput / QPS / p99

1. 這是什麼？

Latency（延遲）:
- 一個 request 從發出到收到 response 的時間
- 包含：network time + processing time + queueing time
- 單位：ms (milliseconds)
- 例：用戶點擊 → 頁面載入完成 = 200ms latency

Throughput（吞吐量）:
- 系統在單位時間內能處理的 request 數量
- 單位：requests/second (RPS) 或 transactions/second (TPS)
- 例：這台 server 每秒能處理 10,000 個 request

QPS (Queries Per Second):
- 特指查詢類的 throughput
- 常用於 database 或 read-heavy 系統
- 例：MySQL 單機 QPS ~5,000-10,000（simple queries）

Percentile（百分位數）:
- p50 (median): 50% 的 request 在這個時間內完成
- p95: 95% 的 request 在這個時間內完成
- p99: 99% 的 request 在這個時間內完成
- p99.9: 99.9% 的 request 在這個時間內完成

為什麼用 percentile 而不是 average？

假設 100 個 request：
- 99 個花了 10ms
- 1 個花了 10,000ms (10 seconds)

Average = (99×10 + 1×10000) / 100 = 109ms
→ 看起來還好？

但 p99 = 10,000ms
→ 每 100 個用戶就有 1 個等了 10 秒！

如果你有 1M DAU，p99 = 10s 意味著每天有 10,000 個用戶體驗極差。
這些往往是你最重要的用戶（heavy users 做更多操作，更容易碰到 tail latency）。

2. 為什麼需要？

Latency 對商業的影響：

Google: +500ms latency → -20% searches
Amazon: +100ms latency → -1% sales ($1.6B/year at their scale)
Walmart: -1s page load → +2% conversion rate
Pinterest: -40% perceived wait time → +15% sign-ups

結論：Latency 直接影響營收。

Throughput 決定了你需要多少機器：

需求：100,000 QPS at peak
單機能力：10,000 QPS
需要機器數：100,000 / 10,000 = 10 台（最少）
加上 redundancy (N+2): 12 台
加上 headroom (30%): 15 台

3. 不用會怎樣？

  • 不理解 p99 → 只看 average，忽略了 1% 用戶的糟糕體驗
  • 不理解 throughput → 機器數估算錯誤，要嘛浪費錢要嘛扛不住
  • 不理解 latency breakdown → 不知道瓶頸在哪，優化了錯的地方
  • 面試中被問 "What's your latency target?" 答不出來

4. 常見 Implementation

4.1 Latency Breakdown

一個典型的 API request 的 latency 組成：

Client → CDN → Load Balancer → App Server → Cache/DB → Response

Breakdown:
┌─────────────────────────────────────────────────────┐
│ DNS lookup:           1-50ms (cached: <1ms)         │
│ TCP handshake:        1-100ms (depends on distance) │
│ TLS handshake:        10-100ms (first time)         │
│ Network (client→LB):  1-200ms (depends on region)   │
│ LB → App Server:      <1ms (same AZ)               │
│ App processing:       1-50ms                        │
│ Cache lookup:         0.1-1ms (Redis)               │
│ DB query:             1-100ms                       │
│ Network (response):   1-200ms                       │
│ Rendering (client):   10-500ms                      │
└─────────────────────────────────────────────────────┘

Total: 50-1000ms (typical web request)

優化優先順序（impact 最大的先做）：
1. Cache hit → 省掉 DB query (最大的 win)
2. CDN → 省掉 network latency for static content
3. Connection pooling → 省掉 TCP/TLS handshake
4. Query optimization → 減少 DB query time
5. Async processing → 把非必要工作移出 critical path

4.2 p50 / p95 / p99 的意義

一個健康的系統：
- p50: 20ms (大部分 request 很快)
- p95: 100ms (少數 request 稍慢)
- p99: 500ms (極少數 request 慢)
- p99.9: 2000ms (千分之一很慢)

一個有問題的系統：
- p50: 20ms (看起來正常)
- p95: 200ms (開始有問題)
- p99: 5000ms (嚴重問題！)
- p99.9: 30000ms (timeout!)

p99 vs p50 差距大 → 說明有 tail latency 問題

SLO 通常怎麼定：

Tier 1 (核心 API, e.g., 搜尋、結帳):
- p50 < 100ms
- p99 < 500ms
- Availability: 99.99%

Tier 2 (重要但非核心, e.g., 推薦、通知):
- p50 < 200ms
- p99 < 1000ms
- Availability: 99.9%

Tier 3 (背景任務, e.g., analytics、報表):
- p50 < 5s
- p99 < 30s
- Availability: 99%

4.3 Tail Latency 的常見原因

1. Garbage Collection (GC):
   - Java/Go 的 GC pause 可能造成 10-100ms 的 stop-the-world
   - 影響：p99 spike
   - Mitigation: Tune GC, use low-latency GC (ZGC, Shenandoah)

2. Hot Shard / Hot Key:
   - 某個 shard 或 cache key 流量特別大
   - 影響：該 shard 的所有 request 都慢
   - Mitigation: Shard splitting, key replication

3. Noisy Neighbor:
   - 共享資源（CPU, network, disk）被其他 tenant 佔用
   - 影響：不可預測的 latency spike
   - Mitigation: Resource isolation, dedicated instances

4. Database Lock Contention:
   - 多個 transaction 競爭同一行的 lock
   - 影響：等待 lock 的 request 延遲增加
   - Mitigation: Optimistic locking, reduce transaction scope

5. Cache Miss Storm:
   - 大量 cache 同時過期
   - 影響：所有 request 都打 DB
   - Mitigation: Jittered TTL, probabilistic early refresh

6. Network Congestion:
   - Cross-AZ or cross-region traffic spike
   - 影響：network latency 增加
   - Mitigation: Data locality, reduce cross-AZ calls

7. Cold Start:
   - 新 instance 啟動，cache 是空的
   - 影響：前幾分鐘 latency 很高
   - Mitigation: Cache warming, gradual traffic ramp-up

4.4 Queueing Delay

Little's Law:
L = λ × W
- L: 系統中的平均 request 數
- λ: 到達率 (requests/second)
- W: 平均等待時間

例子：
- Server 處理能力: 1000 QPS
- 實際流量: 800 QPS (80% utilization)
- 平均 queueing delay: 很小

- 實際流量: 950 QPS (95% utilization)
- 平均 queueing delay: 顯著增加！

- 實際流量: 999 QPS (99.9% utilization)
- 平均 queueing delay: 爆炸性增長！

關鍵 insight：
Queueing delay 在 utilization > 70% 時開始顯著增加。
這就是為什麼我們通常把 capacity planning 設在 70% utilization。

│ Latency                                │
│    │                              ╱    │
│    │                           ╱       │
│    │                        ╱          │
│    │                     ╱             │
│    │                 ╱                 │
│    │            ╱                      │
│    │      ╱                            │
│    │ ╱                                 │
│    └──────────────────────────── Util  │
│    0%   20%   40%   60%   80%  100%   │
└────────────────────────────────────────┘
→ 超過 70% 後 latency 急劇上升

4.5 Batching Tradeoff

Batching: 把多個小 request 合併成一個大 request

例子：寫入 database
- Without batching: 1000 個 INSERT，每個 5ms = 5000ms total
- With batching: 1 個 batch INSERT (1000 rows) = 50ms total
- 100x throughput improvement!

但 batching 增加了 latency：
- 要等 batch 湊滿（或 timeout）才發送
- 單個 request 的 latency = wait_time + processing_time

Tradeoff:
- Batch size 大 → throughput 高，但 latency 高
- Batch size 小 → latency 低，但 throughput 低

常見策略：
- Size-based: batch 滿 100 條就發送
- Time-based: 每 50ms 發送一次（不管幾條）
- Hybrid: 滿 100 條 OR 50ms，先到先發

適用場景：
✅ Logging (latency 不重要)
✅ Analytics events (可以延遲幾秒)
✅ Bulk data import
❌ Real-time chat messages (latency 很重要)
❌ Payment processing (每筆都要即時確認)

4.6 Backpressure（背壓）

當 producer 產生資料的速度 > consumer 處理的速度時：

Without backpressure:
- Queue 無限增長 → OOM
- 或者 drop messages → data loss

With backpressure:
- Consumer 告訴 producer "我處理不過來了，慢一點"
- Producer 降速或暫停

Implementation 方式：

1. Bounded Queue:
   - Queue 滿了 → producer 被 block 或收到 error
   - 例：Kafka partition 有 size limit

2. Rate Limiting:
   - 限制 producer 的發送速率
   - 例：API rate limit 1000 req/s

3. Credit-based Flow Control:
   - Consumer 發 credit 給 producer
   - Producer 只能發送 credit 數量的 message
   - 例：TCP flow control (window size)

4. Reactive Streams:
   - Consumer 主動 request N 條
   - Producer 只發 N 條
   - 例：Project Reactor, RxJava

面試中的應用：
"If our message queue starts backing up, I'd implement backpressure 
at the API layer. When queue depth exceeds threshold, we return 
429 Too Many Requests to clients, signaling them to slow down. 
This prevents the queue from growing unbounded and protects 
downstream consumers from being overwhelmed."

2. Connection server 和 message server 分離

4. Presence service 用 heartbeat (every 30s) 而非 real-time

Part 3：Data Layer 核心知識

Chapter 6：SQL vs NoSQL 選型

1. 這是什麼？

資料庫選型是 System Design 中最關鍵的決策之一。選錯資料庫，後期要遷移的成本極高。

SQL (Relational Database):
- 結構化資料，固定 schema
- ACID transactions
- 強大的 JOIN 能力
- 例：PostgreSQL, MySQL, Oracle, SQL Server

NoSQL (Non-Relational Database):
- 靈活 schema（或 schema-less）
- 通常犧牲部分 ACID 換取 scalability
- 多種類型：Document, Key-Value, Column-family, Graph
- 例：MongoDB, DynamoDB, Cassandra, Redis, Neo4j

2. 為什麼需要？

因為沒有一種資料庫適合所有場景。選型取決於： - 資料結構（structured? nested? graph?） - 存取模式（read-heavy? write-heavy? scan?） - 一致性需求（strong? eventual?） - 規模（GB? TB? PB?） - 延遲需求（ms? seconds?）

3. 不用會怎樣？

  • 用 SQL 存 time-series data → 效能極差
  • 用 NoSQL 做複雜 JOIN → 要在 application layer 做，又慢又容易出 bug
  • 用 Redis 存大量持久化資料 → 記憶體爆掉
  • 面試中被問 "Why did you choose X?" 答不出來

4. 常見 Implementation

4.1 RDBMS (PostgreSQL / MySQL)

特點：
- ACID: Atomicity, Consistency, Isolation, Durability
- Schema enforcement
- Powerful SQL queries (JOIN, GROUP BY, subquery)
- Mature ecosystem (ORM, migration tools, monitoring)

適用場景：
- 需要 transaction 的場景（金融、訂單、庫存）
- 資料之間有複雜關係（user → orders → items → reviews）
- 需要 ad-hoc query（analytics, reporting）
- 資料量 < 幾 TB（超過就要 shard）

Scaling 方式：
1. Read replicas（讀寫分離）
2. Vertical scaling（換更大的機器）
3. Connection pooling（PgBouncer, ProxySQL）
4. Sharding（最後手段，複雜度高）

限制：
- 單機 QPS: ~5,000-10,000（complex queries）
- 單機 storage: ~幾 TB（practical limit）
- Horizontal scaling 困難（JOIN across shards 很痛）
- Schema migration 在大表上很慢

面試中的選型理由：

"I'll use PostgreSQL for user profiles and order data because:
1. We need ACID transactions for payment processing
2. The data has clear relationships (user → orders → items)
3. We need complex queries for the admin dashboard
4. Our data size (~500GB) fits comfortably in a single instance 
   with read replicas for scaling reads"

4.2 DynamoDB / Cassandra (Wide-Column / Key-Value)

DynamoDB:
- AWS managed, serverless
- Single-digit ms latency at any scale
- Partition key + sort key
- Auto-scaling, pay-per-request
- 限制：item size 400KB, no JOIN, limited query flexibility

Cassandra:
- Open-source, self-managed (or DataStax managed)
- Linear scalability (add nodes = more capacity)
- Tunable consistency (ONE, QUORUM, ALL)
- Wide-column model (partition key + clustering columns)
- 適合 write-heavy, time-series data

適用場景：
- 超高 QPS (100K+ writes/sec)
- 已知的 access pattern（不需要 ad-hoc query）
- Time-series data（IoT, logs, metrics）
- 需要 linear scalability

Access Pattern 設計（DynamoDB 例子）：
Table: Messages
  Partition Key: conversation_id
  Sort Key: timestamp

Query: "Get last 50 messages in conversation X"
→ Query(PK=X, SortKey DESC, Limit=50)
→ 超快，single partition read

Anti-pattern:
→ "Get all messages from user Y across all conversations"
→ 需要 scan 或 GSI，效能差
→ 如果這是常見 query，需要另一個 table/GSI

DynamoDB 的 Single Table Design：

把多個 entity 放在同一張 table，用 PK/SK 的命名規則區分：

PK              | SK              | Data
USER#123        | PROFILE         | {name, email, ...}
USER#123        | ORDER#456       | {total, status, ...}
USER#123        | ORDER#456#ITEM1 | {product, qty, ...}
ORDER#456       | METADATA        | {user_id, date, ...}

好處：Single request 拿到所有相關資料（no JOIN needed）
壞處：設計複雜，需要提前知道所有 access patterns

4.3 MongoDB (Document Store)

特點：
- JSON-like documents (BSON)
- Flexible schema（同 collection 的 documents 可以有不同 fields）
- Rich query language（比 DynamoDB 靈活很多）
- 支援 secondary indexes, aggregation pipeline
- Horizontal scaling via sharding

適用場景：
- Schema 經常變動（early-stage product, A/B testing）
- Nested/hierarchical data（product catalog with variants）
- 需要比 DynamoDB 更靈活的 query
- Content management systems

例子 — Product Catalog：
{
  "_id": "prod_123",
  "name": "iPhone 15",
  "category": "electronics",
  "price": 999,
  "variants": [
    { "color": "black", "storage": "128GB", "sku": "IP15-BK-128" },
    { "color": "white", "storage": "256GB", "sku": "IP15-WH-256" }
  ],
  "specs": {
    "screen": "6.1 inch",
    "chip": "A16",
    "battery": "3349 mAh"
  },

    "count": 12345
  }
}

→ 一個 document 包含所有商品資訊
→ 不需要 JOIN 5 張 table
→ Schema 可以隨時加新 field

4.4 Redis (In-Memory Key-Value)

特點：
- In-memory, 超快（< 1ms）
- 豐富的資料結構（String, Hash, List, Set, Sorted Set, Stream）
- 支援 TTL（自動過期）
- Pub/Sub
- Lua scripting（atomic operations）
- Cluster mode（horizontal scaling）

適用場景：
- Cache（最常見用途）
- Session store
- Rate limiter（sliding window counter）
- Leaderboard（Sorted Set）
- Real-time analytics（HyperLogLog for unique counts）
- Distributed lock
- Message queue（Stream or List）

限制：
- 資料必須 fit in memory（貴！）
- 持久化有限（RDB snapshot + AOF，但不如 disk-based DB 可靠）
- 不適合作為 primary data store（除非可以接受 data loss）

常見 Redis 資料結構在面試中的應用：

| 場景 | 資料結構 | 例子 |
|------|----------|------|
| Cache | String | SET user:123 "{json}" EX 3600 |
| Session | Hash | HSET session:abc user_id 123 |
| Feed | Sorted Set | ZADD feed:123 timestamp tweet_id |
| Rate limit | String + INCR | INCR rate:user:123:minute |
| Leaderboard | Sorted Set | ZADD leaderboard score user_id |
| Unique visitors | HyperLogLog | PFADD visitors:today user_id |
| Distributed lock | String + NX | SET lock:resource uuid NX EX 30 |

4.5 Elasticsearch (Search Engine)

特點：
- Full-text search（inverted index）
- Near real-time indexing（~1s delay）
- Distributed, horizontally scalable
- Rich query DSL（fuzzy, wildcard, range, geo, aggregation）
- 不是 primary data store（通常從 DB sync 過來）

適用場景：
- 搜尋功能（product search, log search）
- Autocomplete / typeahead
- Log aggregation（ELK stack）
- Analytics（aggregation queries）
- Geo-spatial queries

Architecture pattern：
DB (source of truth) → Change Data Capture → Elasticsearch (search index)

例子 — E-commerce Search：
POST /products/_search
{

    "bool": {
      "must": [

    }

    { "sales_count": "desc" }

4.6 Object Storage (S3 / GCS)

特點：
- 無限 storage（practically）
- 極低成本（$0.023/GB/month for S3 Standard）
- 高 durability（99.999999999% = 11 nines）
- HTTP-based access
- 不適合頻繁小檔案讀寫

適用場景：
- 圖片、影片、音檔
- 備份
- Static website hosting
- Data lake（raw data for analytics）
- ML training data

Access pattern：
- Upload: PUT object (multipart for large files)
- Download: GET object (or via CDN)
- 不支援 partial update（要整個 object 重寫）
- 不支援 append（除了 S3 的 multipart upload trick）

4.7 Data Warehouse (BigQuery / Redshift / Snowflake)

特點：
- Columnar storage（適合 analytics query）
- 處理 PB 級資料
- SQL interface
- 不適合 OLTP（high-latency, batch-oriented）
- 通常從 OLTP DB 或 event stream ETL 過來

適用場景：
- Business analytics / reporting
- Data science / ML feature engineering
- Historical data analysis
- Dashboard (Tableau, Looker, etc.)

Architecture：
OLTP DB → ETL/ELT → Data Warehouse → BI Tools
         (Kafka/Airflow)              (Tableau/Looker)

Chapter 7：Index

1. 這是什麼？

Index（索引）是資料庫用來加速查詢的資料結構。就像書的目錄 — 不用翻遍整本書就能找到你要的章節。

Without index:
SELECT * FROM users WHERE email = 'john@example.com'
→ Full table scan: 檢查每一行 → O(N)
→ 1 億行 = 掃描 1 億行 = 幾十秒

With index on email:
→ B-tree lookup → O(log N)
→ 1 億行 = ~27 次比較 = 幾毫秒

2. 為什麼需要？

  • 沒有 index 的 query 在資料量大時會極慢
  • 正確的 index 可以把 query 從秒級降到毫秒級
  • 面試中設計 data model 時，index 設計是 Senior 的加分項
  • 理解 index 的 tradeoff 能幫你做更好的 schema 設計

3. 不用會怎樣？

  • Query 隨著資料增長越來越慢
  • 加了太多 index → 寫入變慢、storage 膨脹
  • 加了錯誤的 index → 沒有效果，浪費空間
  • 面試中被問 "How would you optimize this query?" 答不出來

4. 常見 Implementation

4.1 B-tree Index

最常見的 index 類型（PostgreSQL, MySQL 預設）。

結構：平衡多叉樹
- 每個 node 包含多個 key（通常幾百個）
- Leaf nodes 包含指向實際 data row 的 pointer
- 樹高通常 3-4 層（即使 billions of rows）

特點：
- 查詢：O(log N) — 非常快
- 範圍查詢：excellent（leaf nodes 是 linked list）
- 插入/刪除：O(log N) — 需要維護平衡
- 適合：等值查詢、範圍查詢、排序

例子：
CREATE INDEX idx_users_email ON users(email);

Query: WHERE email = 'john@example.com'
→ 從 root 開始，每層比較，3-4 次 disk read 就找到

Query: WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'
→ 找到起點，然後沿 leaf nodes 順序掃描
→ 非常高效（sequential read）

4.2 LSM Tree (Log-Structured Merge Tree)

用於 write-optimized 資料庫（Cassandra, RocksDB, LevelDB, HBase）。

原理：
1. 寫入先到 memory (memtable) — 超快
2. Memtable 滿了 → flush 到 disk 成為 SSTable (sorted)
3. 背景 compaction: 合併多個 SSTable

Write path:
Write → Memtable (memory) → [flush] → SSTable L0 → [compact] → L1 → L2...

Read path:
Read → Memtable → L0 SSTables → L1 → L2... (merge results)
→ 可能需要查多個 file → 用 Bloom filter 加速

Tradeoff vs B-tree：
| | B-tree | LSM tree |
|---|--------|----------|
| Write | O(log N) + random I/O | O(1) sequential write |
| Read | O(log N) 1 次 disk seek | 可能查多個 SSTable |
| Space | 較大（page 可能半滿）| 較小（compaction 後緊湊）|
| Write amplification | 低 | 高（compaction 重寫）|
| 適合 | Read-heavy, OLTP | Write-heavy, time-series |

4.3 Inverted Index

用於全文搜尋（Elasticsearch, Lucene, Solr）。

原理：從 "document → words" 反轉為 "word → documents"

Documents:
Doc1: "Redis is a fast in-memory database"
Doc2: "PostgreSQL is a reliable relational database"
Doc3: "Redis supports many data structures"

Inverted Index:
redis      → [Doc1, Doc3]
fast       → [Doc1]
memory     → [Doc1]
database   → [Doc1, Doc2]
postgresql → [Doc2]
reliable   → [Doc2]
relational → [Doc2]
supports   → [Doc3]
structures → [Doc3]

Query: "redis database"
→ redis: [Doc1, Doc3]
→ database: [Doc1, Doc2]
→ Intersection: [Doc1] (contains both words)

加上 TF-IDF / BM25 scoring → 排名結果

4.4 Secondary Index

Primary index: 通常是 primary key（自動建立）
Secondary index: 在非 primary key 的 column 上建立

例子：
Table: orders (id PK, user_id, status, created_at, total)

Primary index: id (自動)
Secondary indexes:
- idx_user_id: 查某用戶的所有訂單
- idx_status: 查所有 pending 訂單
- idx_created_at: 按時間範圍查詢

在 NoSQL 中的 secondary index：
- DynamoDB: Global Secondary Index (GSI) / Local Secondary Index (LSI)
- Cassandra: Secondary index（效能差，通常用 materialized view 代替）
- MongoDB: 支援任意 field 的 secondary index

Tradeoff：
- 每個 secondary index = 額外的寫入成本
- DynamoDB GSI = 額外的 table（要付額外的 RCU/WCU）
- 太多 index → 寫入變慢

4.5 Covering Index

一個 index 包含了 query 需要的所有 columns，不需要回表查 data row。

例子：
Query: SELECT email, name FROM users WHERE email = 'john@example.com'

Normal index on (email):
1. 查 index 找到 row pointer
2. 用 pointer 去 data page 讀取 email + name
→ 2 次 I/O

Covering index on (email, name):
1. 查 index，index 本身就包含 email 和 name
→ 1 次 I/O（不需要回表）

CREATE INDEX idx_covering ON users(email) INCLUDE (name);

什麼時候用：
- 高頻 query 且只需要少數 columns
- 想避免 random I/O（回表是 random read）
- 注意：index 越大，維護成本越高

4.6 Composite Index (複合索引)

在多個 columns 上建立的 index。

CREATE INDEX idx_composite ON orders(user_id, created_at, status);

Leftmost prefix rule（最左前綴原則）：
這個 index 可以加速：
✅ WHERE user_id = 123
✅ WHERE user_id = 123 AND created_at > '2024-01-01'
✅ WHERE user_id = 123 AND created_at > '2024-01-01' AND status = 'pending'

但不能加速：
❌ WHERE created_at > '2024-01-01' (沒有 user_id)
❌ WHERE status = 'pending' (沒有 user_id 和 created_at)
❌ WHERE user_id = 123 AND status = 'pending' (跳過了 created_at)

設計原則：
1. 等值條件的 column 放前面
2. 範圍條件的 column 放後面
3. 高 cardinality 的 column 放前面

例子：
Query: WHERE user_id = ? AND status = ? AND created_at > ?
Best index: (user_id, status, created_at)
→ user_id 等值 → status 等值 → created_at 範圍

4.7 Write Amplification

每次寫入 data，需要額外寫入多少 index？

例子：
Table: users
Indexes: 
1. Primary key (id)
2. idx_email (email)
3. idx_username (username)
4. idx_created_at (created_at)
5. idx_status_city (status, city)

INSERT 一行 → 寫入 1 次 data + 5 次 index update = 6x write amplification

UPDATE email → 更新 data + 更新 idx_email = 2x write

影響：
- 更多 index = 更慢的寫入
- 更多 disk I/O
- 更多 storage space（index 也佔空間）

經驗法則：
- OLTP table: 3-5 個 index 是合理的
- 超過 10 個 index → 寫入效能會明顯下降
- Write-heavy table → 盡量少 index
- Read-heavy table → 可以多加 index

5. Tradeoffs

Index 策略 Read 效能 Write 效能 Storage 適用場景
No index O(N) scan O(1) append Minimal Write-only logs
B-tree O(log N) O(log N) Medium General OLTP
LSM tree O(log N) × levels O(1) amortized Compact Write-heavy
Hash index O(1) exact match O(1) Medium Key-value lookup
Covering index Fastest (no table lookup) Slower (bigger index) Large High-freq queries
Composite index Fast for multi-column Slower writes Large Multi-condition queries

6. Failure Modes

Failure 原因 影響 Mitigation
Index bloat 大量 delete 後 index 沒 reclaim space 查詢變慢 REINDEX / VACUUM
Index corruption Disk failure, crash during write Query 結果錯誤 Checksum + rebuild
Wrong index chosen Query planner 選了次優 index 查詢慢 ANALYZE + hint
Index not used Query 不符合 index 條件 Full scan EXPLAIN + redesign
Lock contention Index update 需要 lock Write 排隊 Reduce index count

7. 面試怎麼講？

"For the orders table, I'll design indexes based on our access patterns:

1. Primary key: order_id (auto-generated, UUID or snowflake)
2. Composite index: (user_id, created_at DESC) 
   — for 'show my recent orders'
3. Index: (status) with partial index WHERE status = 'pending'
   — for 'process pending orders' background job
4. Covering index: (user_id, status) INCLUDE (total, created_at)
   — for the order summary page (avoids table lookup)

I'm intentionally NOT indexing every column because this is a 
write-heavy table (new orders constantly). Each additional index 
adds ~20% write overhead. I'll monitor slow query logs and add 
indexes only when needed."

8. 具體例子

例子：Twitter 的 Timeline Query 優化

需求：SELECT * FROM tweets WHERE user_id IN (following_list) 
      ORDER BY created_at DESC LIMIT 20

Approach 1: Index on (user_id, created_at)
- 問題：如果 follow 1000 人，要 merge sort 1000 個 index range
- 延遲：~100ms（太慢）

Approach 2: Precomputed feed (Redis Sorted Set)
- 寫入時 fanout 到 follower 的 feed
- 讀取：ZREVRANGE feed:user_id 0 19
- 延遲：< 5ms

Approach 3: Hybrid
- 普通用戶：precomputed feed (fanout on write)
- Celebrity：on-the-fly merge (fanout on read)
- Index 只用於 fallback 和 backfill

教訓：有時候最好的 "index" 不是 DB index，
而是 precomputed data structure (cache)。

9. 常見追問

追問 Senior 回答
"Why does index slow down writes?" Each write must update data + all relevant indexes. More indexes = more disk I/O per write.
"How do you decide which indexes to create?" Start with access patterns (queries), use EXPLAIN to verify, monitor slow query log
"B-tree vs LSM tree?" B-tree for read-heavy OLTP; LSM for write-heavy (logs, time-series). LSM trades read performance for write performance.
"What's index selectivity?" Ratio of distinct values to total rows. High selectivity (e.g., email) = good index candidate. Low selectivity (e.g., boolean) = poor candidate.
"How do you handle index on a 1B row table?" Online index creation (CREATE INDEX CONCURRENTLY in PostgreSQL), or build on replica then promote

10. Senior-Level Summary

✅ Index 的核心原則：
   1. Index 是 read-write tradeoff 的具體體現
   2. 設計 index 要從 access pattern 出發，不是從 schema 出發
   3. 每個 index 都有維護成本，不要盲目加
   4. Composite index 的 column 順序很重要

✅ 面試中的 signal：
   - Junior: "I'll add an index on every column we query"
   - Senior: "Based on our top 3 access patterns, I'll create 
     these specific indexes, and here's the write amplification 
     tradeoff I'm accepting"
   - Staff: "I'd implement a query analysis pipeline that 
     identifies slow queries in production and suggests index 
     changes. Index strategy should evolve with actual usage 
     patterns, not just initial design assumptions."

Chapter 8：Sharding / Partitioning

1. 這是什麼？

Sharding（分片）是把一個大的資料集分散到多個資料庫節點上。每個節點只存一部分資料，但合起來是完整的資料集。

Before sharding:
┌─────────────────────────┐
│     Single Database      │
│   100M users, 10TB      │
│   QPS: 50,000 (at limit)│
└─────────────────────────┘

After sharding (4 shards):
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ Shard 0  │ │ Shard 1  │ │ Shard 2  │ │ Shard 3  │
│ 25M users│ │ 25M users│ │ 25M users│ │ 25M users│
│ 2.5TB    │ │ 2.5TB    │ │ 2.5TB    │ │ 2.5TB    │
│ 12.5K QPS│ │ 12.5K QPS│ │ 12.5K QPS│ │ 12.5K QPS│
└──────────┘ └──────────┘ └──────────┘ └──────────┘

2. 為什麼需要？

  • 單機 DB 有容量上限（storage, QPS, connections）
  • Vertical scaling 有天花板且成本指數增長
  • 需要地理分佈（不同 region 的資料放在不同 shard）
  • 需要隔離（不同 tenant 的資料互不影響）

3. 不用會怎樣？

  • 資料量超過單機容量 → 無法存更多資料
  • QPS 超過單機能力 → 所有 query 都慢
  • 一台 DB 掛了 → 所有用戶都受影響
  • 無法做地理分佈 → 遠端用戶延遲高

4. 常見 Implementation

4.1 Hash Partitioning

原理：shard_id = hash(partition_key) % num_shards

例子：
partition_key = user_id
num_shards = 4

user_id = 123 → hash(123) % 4 = 3 → Shard 3
user_id = 456 → hash(456) % 4 = 0 → Shard 0
user_id = 789 → hash(789) % 4 = 1 → Shard 1

優點：
- 資料分佈均勻（好的 hash function）
- 簡單易實現

缺點：
- 不支援範圍查詢（WHERE user_id BETWEEN 100 AND 200 要查所有 shard）
- 增加/減少 shard 時需要 rehash（大量資料搬移）

4.2 Range Partitioning

原理：按 key 的範圍分配到不同 shard

例子：
user_id 1-25M      → Shard 0
user_id 25M-50M    → Shard 1
user_id 50M-75M    → Shard 2
user_id 75M-100M   → Shard 3

或按時間：
2024-Q1 data → Shard 0
2024-Q2 data → Shard 1
2024-Q3 data → Shard 2
2024-Q4 data → Shard 3

優點：
- 支援範圍查詢（只需查相關 shard）
- 容易理解和管理

缺點：
- 容易產生 hot shard（新用戶都在最後一個 shard）
- 資料分佈可能不均勻
- 時間分區：最新的 shard 永遠最忙

4.3 Consistent Hashing

解決的問題：普通 hash partitioning 在增減 shard 時要 rehash 所有資料。

原理：
1. 把 hash space 想像成一個環（0 到 2^32-1）
2. 每個 shard 在環上佔一個位置
3. 每個 key hash 後，順時針找到最近的 shard

      Shard A
        │
   ─────●─────
  │           │
  ●           ●  Shard B
  │           │
   ─────●─────
        │
      Shard C

key1 hash 到 Shard A 和 B 之間 → 順時針 → 去 Shard B
key2 hash 到 Shard C 和 A 之間 → 順時針 → 去 Shard A

增加 Shard D：
- 只有 D 和它前一個 shard 之間的 key 需要搬移
- 其他 key 不受影響
- 搬移量：~1/N（N = shard 數量）

Virtual Nodes（虛擬節點）：
- 每個實體 shard 在環上放多個點（例如 150 個）
- 解決資料分佈不均的問題
- 也方便處理不同 shard 的容量差異

4.4 Hot Shard Problem

問題：某些 shard 的流量遠大於其他 shard

原因：
1. Celebrity user（百萬 follower 的用戶在某個 shard）
2. Viral content（某個熱門帖子的所有互動都在同一 shard）
3. Temporal hotspot（新資料都寫入最新的 time-based shard）

解決方案：

1. Shard splitting:
   - 把 hot shard 再分成 2 個
   - 需要 rebalancing

2. Key salting:
   - 在 hot key 後面加 random suffix
   - user_id:celebrity_123 → celebrity_123_0, celebrity_123_1, ..._9
   - 分散到 10 個 shard
   - 讀取時要 scatter-gather（查 10 個 shard 再合併）

3. Dedicated shard:
   - 把 celebrity user 放到專用 shard
   - 該 shard 有更多資源

4. Caching layer:
   - Hot data 放 cache，不直接打 DB shard
   - 大部分 read 被 cache 擋住

4.5 Rebalancing

什麼時候需要 rebalancing：
- 加新 shard（scale out）
- 移除 shard（scale in）
- 某個 shard 資料量不均

Rebalancing 策略：

1. Fixed number of partitions:
   - 預先分好 N 個 partition（N >> shard 數）
   - 例：1000 個 partition 分配到 10 個 shard
   - 加新 shard → 從其他 shard 搬一些 partition 過來
   - 不需要 rehash，只是搬移 partition
   - 例：Cassandra, Elasticsearch

2. Dynamic partitioning:
   - Partition 太大 → split
   - Partition 太小 → merge
   - 例：HBase, MongoDB

3. Proportional to nodes:
   - 每個 node 固定數量的 partition
   - 加 node → 從其他 node 偷一些 partition
   - 例：Cassandra (virtual nodes)

Rebalancing 的風險：
- 搬移資料時增加 network traffic
- 搬移過程中可能影響 query latency
- 如果搬移失敗，可能造成資料不一致
- 建議：限制搬移速度，在低峰期執行

4.6 Celebrity Problem (Hot Partition)

場景：Design Twitter
- Taylor Swift 有 9000 萬 follower
- 她發一條 tweet → fanout 到 9000 萬人的 feed
- 如果按 user_id shard，她的 tweet 都在同一個 shard
- 該 shard 的寫入量是其他 shard 的 1000 倍

解決方案：

Approach 1: Hybrid fanout
- 普通用戶（< 10K followers）: fanout on write
- Celebrity（> 10K followers）: fanout on read
- 讀取 feed 時：precomputed feed + merge celebrity tweets

Approach 2: Shard by tweet_id (not user_id)
- 每條 tweet 獨立 shard
- Celebrity 的 tweets 分散在不同 shard
- 但 "get all tweets by user X" 需要 scatter-gather

Approach 3: Dedicated celebrity infrastructure
- Celebrity users 有專用的 write pipeline
- 更多 buffer, 更多 worker
- 普通用戶走正常 pipeline

面試中怎麼講：
"For the celebrity problem, I'd use a hybrid approach. 
Users with > 10K followers are flagged as celebrities. 
Their tweets are NOT fanned out on write. Instead, when 
a follower loads their feed, we merge the precomputed 
feed (from normal users) with a real-time fetch of 
celebrity tweets. This bounds our write amplification 
while keeping read latency acceptable (extra ~10ms for 
the celebrity merge)."

5. Tradeoffs

Sharding 策略 資料分佈 範圍查詢 Rebalancing 適用場景
Hash 均勻 差 需要 rehash General purpose
Range 可能不均 好 容易 Time-series, ordered data
Consistent hash 均勻 差 只搬 1/N Dynamic scaling
Directory-based 可控 取決於設計 靈活 Complex routing rules

More shards 每個 shard 負載低 更多 operational overhead
Fewer shards 管理簡單 每個 shard 負載高

6. Failure Modes

Failure 原因 影響 Mitigation
Hot shard 不均勻的 access pattern 一個 shard 過載 Monitoring + auto-split
Cross-shard query 需要 JOIN 不同 shard 的資料 延遲高、複雜 Denormalization, avoid cross-shard
Shard failure Hardware/software failure 部分資料不可用 Replication within each shard
Rebalancing storm 同時搬太多資料 Network 飽和 Rate limiting on rebalancing
Incorrect routing Routing table stale 查到錯的 shard Consistent hashing + gossip protocol

7. 面試怎麼講？

"For sharding strategy, I'll use consistent hashing with virtual nodes:

1. Partition key: user_id
   - All of a user's data on the same shard (data locality)
   - Queries like 'get user's orders' are shard-local

2. Why consistent hashing:
   - We can add/remove shards with minimal data movement
   - Virtual nodes ensure even distribution

3. Shard count: Start with 16 shards
   - Each shard: ~6M users, ~600GB, ~3K QPS
   - Well within single-node capacity
   - Room to grow to 64 shards without redesign

4. Cross-shard queries:
   - Avoided by design (denormalize where needed)
   - For analytics: async ETL to data warehouse
   - For search: Elasticsearch (separate from sharded DB)

5. Replication: Each shard has 2 replicas
   - 1 sync replica (same AZ, for failover)
   - 1 async replica (different AZ, for DR)"

8. 具體例子

例子：Instagram 的 Sharding 策略

Instagram 用 PostgreSQL + 自建 sharding layer：

Shard key: user_id
Shard count: 數千個 logical shard → 映射到數百個 physical DB

ID generation (Snowflake-like):
- 41 bits: timestamp (ms since custom epoch)
- 13 bits: logical shard ID
- 10 bits: auto-increment sequence

好處：
- ID 本身包含 shard 資訊 → 不需要額外 lookup
- 時間排序 → 可以按 ID 排序得到時間順序
- 全局唯一 → 不需要 centralized ID generator

Routing:
- 從 ID 提取 shard bits → 知道在哪個 logical shard
- Logical shard → physical DB 的 mapping 存在 config
- 可以把多個 logical shard 合併到一個 physical DB
- Scale out: 把 logical shard 搬到新的 physical DB

9. 常見追問

追問 Senior 回答
"How do you handle cross-shard transactions?" Avoid them by design. If unavoidable, use saga pattern or 2PC (with performance cost).
"How do you choose the shard key?" Based on most common query pattern. The key should ensure data locality for frequent queries.
"What if you need to re-shard?" Use logical shards (many more than physical). Re-sharding = moving logical shards between physical nodes.
"How do you handle auto-increment IDs across shards?" Snowflake ID (timestamp + shard + sequence) or UUID. Never use DB auto-increment across shards.
"When should you NOT shard?" When data fits on one machine, when you need complex JOINs, when operational complexity isn't justified.

10. Senior-Level Summary

✅ Sharding 的核心原則：
   1. Shard key 決定一切 — 選錯了後期改不了
   2. 設計時就要避免 cross-shard queries
   3. Consistent hashing 是最靈活的方案
   4. 先用 read replicas + caching，sharding 是最後手段

✅ Shard key 選擇原則：
   - 高 cardinality（避免 hot shard）
   - 符合最常見的 query pattern
   - 讓相關資料在同一 shard（data locality）

Chapter 9：Replication / Consistency

1. 這是什麼？

Replication（複製）是把資料複製到多個節點。Consistency（一致性）是指這些副本之間資料的同步程度。

核心矛盾：
- 複製越多 → 可用性越高、讀取越快
- 但副本之間的同步需要時間
- 同步越嚴格 → 延遲越高、可用性越低
- 同步越寬鬆 → 可能讀到 stale data

這就是 CAP theorem 的本質。

2. 為什麼需要？

Replication 的三個目的： 1. High Availability: 一個節點掛了，其他節點繼續服務 2. Read Scalability: 多個 replica 分擔讀取流量 3. Low Latency: 把 replica 放在離用戶近的地方

Consistency 的重要性： - 用戶改了密碼，下一秒登入用舊密碼能進去嗎？（不行！需要 strong consistency） - 用戶發了一條 tweet，follower 晚 2 秒看到可以嗎？（可以！eventual consistency OK）

3. 不用會怎樣？

  • 沒有 replication → 單點故障，DB 掛了全部掛
  • Consistency 太強 → 延遲高，可用性差
  • Consistency 太弱 → 用戶看到矛盾的資料，體驗差
  • 不理解 tradeoff → 面試中無法解釋為什麼選 eventual consistency

4. 常見 Implementation

4.1 Leader-Follower (Primary-Replica)

架構：
┌────────┐     sync/async      ┌──────────┐
│ Leader │ ──────────────────→ │ Follower1│
│(writes)│ ──────────────────→ │ Follower2│
└────────┘                     │ Follower3│
     ↑                         └──────────┘
     │                              ↑
  Writes                         Reads
     │                              │
  Clients                        Clients

特點：
- 所有寫入都到 Leader
- Follower 複製 Leader 的 write-ahead log (WAL)
- 讀取可以從任何 Follower（或 Leader）

Sync vs Async replication：

Synchronous:
- Leader 等 Follower 確認才回覆 client
- 保證：Follower 的資料和 Leader 一致
- 代價：每次寫入多等一個 network round trip (~1-5ms same AZ)
- 風險：Follower 掛了 → 寫入被 block

Asynchronous:
- Leader 寫完就回覆 client，不等 Follower
- 好處：寫入延遲低
- 風險：Leader 掛了 → 還沒複製的資料丟失
- Replication lag: 通常 < 1s，但壓力大時可能幾秒甚至幾分鐘

Semi-synchronous (常見折衷):
- 至少 1 個 Follower 是 sync（保證至少一個副本是最新的）
- 其他 Follower 是 async
- 例：PostgreSQL synchronous_standby_names

4.2 Multi-Leader (Multi-Primary)

架構：
┌────────┐         ┌────────┐
│Leader A│ ←─────→ │Leader B│
│(Region1)│        │(Region2)│
└────────┘         └────────┘
     ↑                  ↑
  Writes             Writes
  (US users)         (EU users)

特點：
- 多個節點都能接受寫入
- 節點之間互相複製
- 適合 multi-region deployment

問題：Write Conflict!
- User 在 Region A 改名為 "John"
- 同時在 Region B 改名為 "Johnny"
- 兩個 Leader 都接受了 → 衝突！

Conflict Resolution 策略：
1. Last-write-wins (LWW): 用 timestamp，最新的贏
   - 簡單但可能丟資料

2. Custom resolution: Application 定義 merge 邏輯
   - 例：Google Docs 的 OT (Operational Transform)

3. Conflict-free Replicated Data Types (CRDTs):
   - 資料結構本身保證 merge 不衝突
   - 例：Counter, Set, Register

適用場景：
- Multi-region deployment（每個 region 一個 leader）
- Collaborative editing（Google Docs）
- Offline-first apps（手機離線時本地寫入，上線後 sync）

4.3 Leaderless (Dynamo-style)

架構：
┌──────┐ ┌──────┐ ┌──────┐
│Node A│ │Node B│ │Node C│
└──────┘ └──────┘ └──────┘
   ↑↓       ↑↓       ↑↓
      Client writes to multiple nodes
      Client reads from multiple nodes

特點：
- 沒有 leader，任何節點都能接受讀寫
- 用 quorum 保證一致性
- 例：Cassandra, DynamoDB, Riak

Quorum:
- N = 總 replica 數
- W = 寫入需要確認的 replica 數
- R = 讀取需要查詢的 replica 數
- 只要 W + R > N → 保證讀到最新資料

常見配置：
N=3, W=2, R=2 (standard quorum)
- 寫入：2/3 節點確認 → 成功
- 讀取：查 2/3 節點 → 取最新版本
- 容忍 1 個節點故障

N=3, W=1, R=3 (write-optimized)
- 寫入超快（只要 1 個確認）
- 讀取要查所有節點
- 適合 write-heavy workload

N=3, W=3, R=1 (read-optimized)
- 寫入要所有節點確認（慢）
- 讀取只要查 1 個節點（快）
- 適合 read-heavy workload

4.4 Consistency Models

Strong Consistency (Linearizability):
- 寫入完成後，所有後續讀取都能看到新值
- 就像只有一個副本一樣
- 實現：同步複製、consensus (Raft/Paxos)
- 代價：高延遲、低可用性
- 適用：金融交易、庫存扣減、密碼修改

Eventual Consistency:
- 寫入後，副本最終會一致（但不保證什麼時候）
- 中間可能讀到 stale data
- 實現：異步複製
- 好處：低延遲、高可用性
- 適用：Social feed、推薦、analytics

Read-after-write Consistency (Read-your-writes):
- 用戶自己寫的東西，自己一定能馬上讀到
- 其他用戶可能晚一點才看到
- 實現：寫入後從 leader 讀（或等 replication 完成）
- 適用：用戶 profile 更新、發文後看自己的 timeline

Monotonic Read Consistency:
- 用戶不會看到時間倒退（先看到新資料，再看到舊資料）
- 實現：同一用戶的讀取固定到同一 replica
- 適用：聊天記錄、timeline

Causal Consistency:
- 有因果關係的操作保證順序
- 例：先發問題，再發回答 → 所有人都先看到問題再看到回答
- 實現：vector clock, causal ordering
- 適用：討論串、comment thread

4.5 CAP Theorem

CAP: 在 network partition 發生時，你只能選 Consistency 或 Availability。

C (Consistency): 所有節點看到相同的資料
A (Availability): 每個 request 都能得到 response
P (Partition tolerance): 網路分區時系統繼續運作

重要澄清：
- CAP 不是「三選二」— Partition 一定會發生
- 真正的選擇是：Partition 發生時，選 C 還是 A？
- 正常情況下（沒有 partition），C 和 A 都可以有

CP System (選 Consistency):
- Partition 時，寧可不服務也不給錯誤資料
- 例：ZooKeeper, HBase, MongoDB (default)
- 適用：金融系統、配置管理

AP System (選 Availability):
- Partition 時，繼續服務但可能給 stale data
- 例：Cassandra, DynamoDB, CouchDB
- 適用：Social media, 推薦系統

實際上的 spectrum：
- 不是非黑即白，而是一個 spectrum
- 可以對不同的資料用不同的策略
- 例：同一個系統中
  - 用戶餘額：strong consistency (CP)
  - 用戶 feed：eventual consistency (AP)
  - 用戶 profile：read-after-write consistency

4.6 PACELC Theorem (CAP 的延伸)

PACELC: 即使沒有 Partition，也有 Latency vs Consistency 的 tradeoff。

If Partition:
  Choose Availability or Consistency (same as CAP)
Else (normal operation):
  Choose Latency or Consistency

例子：
- DynamoDB: PA/EL (Partition → Available, Else → Low Latency)
- PostgreSQL sync replication: PC/EC (Partition → Consistent, Else → Consistent)
- Cassandra (QUORUM): PA/EC (Partition → Available, Else → Consistent)
- Cassandra (ONE): PA/EL (Partition → Available, Else → Low Latency)

面試中的應用：
"Even without network partitions, there's a fundamental tradeoff 
between latency and consistency. Synchronous replication gives us 
consistency but adds latency. For our feed service, I choose low 
latency (async replication) because stale feed data for 1-2 seconds 
is acceptable. For the payment service, I choose consistency 
(sync replication) because incorrect balance is unacceptable."

7. 面試怎麼講？

"For consistency, I'll use different levels for different data:

1. User balance / Payment: Strong consistency
   - Synchronous replication to at least 1 replica
   - Read from leader for balance queries
   - Accept higher latency (~5ms extra) for correctness

2. User profile: Read-after-write consistency
   - After user updates profile, route their reads to leader for 5s
   - Other users can read from any replica (eventual, ~1s lag)

3. News feed: Eventual consistency
   - Async replication, ~1-2s lag acceptable
   - Users won't notice if a new post appears 2s late
   - Massive read scalability (all replicas serve reads)

This tiered approach gives us the best of both worlds:
correctness where it matters, performance where it doesn't."

8. 具體例子

例子 1：Facebook 的 Read-after-write

問題：
- 用戶在 US-East 更新大頭照
- 資料寫入 US-East primary
- 用戶刷新頁面，request 被路由到 US-West replica
- Replica 還沒收到更新 → 用戶看到舊照片 → 困惑

解決方案：
1. 寫入後，在 client 記錄 "last_write_timestamp"
2. 讀取時帶上這個 timestamp
3. 如果 replica 的資料比 timestamp 舊 → 改讀 leader
4. 或者：寫入後 5 秒內，強制讀 leader

實現：
// Client-side
const lastWrite = localStorage.get('last_write_ts');
fetch('/api/profile', {
  headers: { 'X-Min-Freshness': lastWrite }
});

// Server-side
if (request.minFreshness > replica.lastSyncTime) {
  return readFromLeader();
} else {
  return readFromReplica();
}

例子 2：Cassandra 的 Tunable Consistency

Cassandra 讓你每個 query 都能選 consistency level：

// 寫入 — 至少 2 個節點確認
INSERT INTO users (id, name) VALUES (123, 'John')
USING CONSISTENCY QUORUM;

// 讀取 — 只要 1 個節點回覆（最快）
SELECT * FROM users WHERE id = 123
USING CONSISTENCY ONE;

// 讀取 — 要所有節點回覆（最一致）
SELECT * FROM users WHERE id = 123
USING CONSISTENCY ALL;

實際應用：
- 寫入用戶 profile: QUORUM (重要資料)
- 讀取 feed: ONE (速度優先)
- 讀取用戶餘額: QUORUM (一致性優先)
- 寫入 analytics event: ONE (速度優先，丟一個不要緊)

9. 常見追問

追問 Senior 回答
"How do you handle replication lag?" Monitor lag metric, route critical reads to leader, use read-after-write for user's own data
"What happens during a network partition?" Depends on consistency choice. CP: reject writes. AP: accept writes, resolve conflicts later.
"How does consensus work?" Raft/Paxos: leader election + log replication. Majority must agree. Guarantees consistency at cost of latency.
"Strong consistency vs linearizability?" Linearizability = real-time ordering guarantee. Strongest form of consistency. Implemented via consensus protocols.
"How do you test consistency?" Jepsen testing framework, chaos engineering (kill nodes during writes), verify with linearizability checker

10. Senior-Level Summary

✅ 核心原則：
   1. There is no free lunch: consistency, availability, latency — pick two
   2. Use the weakest consistency level that your use case can tolerate
   3. Different data in the same system can have different consistency levels
   4. Replication lag is not a bug, it's a feature (enables scalability)

✅ 決策框架：
   問自己：如果用戶讀到 1 秒前的舊資料，會怎樣？
   - 會造成金錢損失 → Strong consistency
   - 會造成用戶困惑 → Read-after-write
   - 用戶不會注意到 → Eventual consistency

✅ 面試中的 signal：
   - Junior: "We'll use replication for high availability"
   - Senior: "I'll use async replication for the feed (eventual 
     consistency acceptable) but sync replication for payments 
     (strong consistency required). Here's the latency tradeoff."
   - Staff: "I'd implement a consistency framework that lets each 
     service declare its consistency requirements. The platform 
     handles routing reads to the appropriate replica based on 
     freshness requirements. This decouples consistency policy 
     from application code."

✅ 記住：
   "Consistency is not a property of the database.
   It's a property of each individual operation.
   The same database can serve both strongly consistent 
   and eventually consistent reads."

Part 4：Performance Building Blocks

Chapter 10：Cache

1. 這是什麼？

Cache 是一個高速的臨時儲存層，存放經常被存取的資料副本，避免每次都去慢速的 data source（如 DB）取資料。

Without cache:
Client → App Server → Database (5-50ms per query)
每次都打 DB → DB 成為瓶頸

With cache:
Client → App Server → Cache (0.1-1ms) → Database (only on cache miss)
95% 的 request 從 cache 拿 → DB 壓力降 95%

2. 為什麼需要？

  • DB 的 QPS 有上限（MySQL ~5-10K QPS），但 Redis 可以 100-300K QPS
  • 減少 latency：Redis < 1ms vs DB 5-50ms
  • 減少 DB 負載：cache hit rate 95% = DB 只需處理 5% 的流量
  • 省錢：1 台 Redis 能擋住 10 台 DB 的讀取量

數字感：

假設 100K read QPS:
- Without cache: 需要 10-20 台 DB replica
- With cache (95% hit rate): 5K QPS 打 DB → 1-2 台 DB 就夠
- 成本差異：10x+

3. 不用會怎樣？

  • DB 被讀取流量打爆
  • p99 latency 很高（每次都要查 DB）
  • 無法應對流量高峰（DB 是 bottleneck）
  • 面試中不提 cache → 被認為不理解 performance optimization

4. 常見 Implementation

4.1 Cache-Aside (Lazy Loading)

最常見的 pattern。Application 自己管理 cache。

Read:
1. 查 cache
2. Cache hit → 返回
3. Cache miss → 查 DB → 寫入 cache → 返回

Write:
1. 寫入 DB
2. 刪除 cache（invalidate）
3. 下次讀取時會 miss → 從 DB 重新載入

def get_user(user_id):
    # 1. Check cache
    cached = redis.get(f"user:{user_id}")
    if cached:
        return deserialize(cached)

    # 2. Cache miss → query DB
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)

    # 3. Write to cache
    redis.setex(f"user:{user_id}", 3600, serialize(user))
    return user

優點：
- 只 cache 被請求的資料（不浪費記憶體）
- Cache 掛了不影響正確性（只是變慢）
- 簡單易實現

缺點：
- 第一次請求一定是 cache miss（cold start）
- Cache miss 時有額外延遲（查 DB + 寫 cache）
- 可能有短暫的 stale data（DB 更新後到 cache 失效之間）

4.2 Read-Through

Cache 自己負責從 DB 載入資料。Application 只跟 cache 互動。

Read:
1. Application 查 cache
2. Cache miss → Cache 自己去查 DB → 存入 cache → 返回

跟 cache-aside 的差別：
- Cache-aside: Application 負責 DB 查詢和 cache 寫入
- Read-through: Cache library/proxy 負責（對 application 透明）

例子：Hibernate L2 cache, AWS DAX (DynamoDB Accelerator)

優點：
- Application code 更簡單（不需要管 cache miss 邏輯）
- 統一的 cache 行為

缺點：
- Cache library 需要知道怎麼查 DB
- 靈活性較低

4.3 Write-Through

寫入時同時更新 DB 和 cache。

Write:
1. Application 寫入 cache
2. Cache 同步寫入 DB
3. 兩者都成功才回覆 client

優點：
- Cache 永遠是最新的（no stale data）
- 讀取永遠 cache hit（如果之前寫過）

缺點：
- 寫入延遲增加（要等 cache + DB 都完成）
- 可能 cache 了不常讀取的資料（浪費記憶體）
- 通常搭配 TTL 使用（避免 cache 無限增長）

4.4 Write-Back (Write-Behind)

寫入只更新 cache，異步批量寫入 DB。

Write:
1. Application 寫入 cache → 立刻回覆 client
2. 背景 worker 定期把 cache 的 dirty data flush 到 DB

優點：
- 寫入延遲極低（只寫 cache）
- 可以合併多次寫入（batch write to DB）
- 適合 write-heavy workload

缺點：
- 資料可能丟失（cache 掛了但還沒 flush 到 DB）
- 複雜度高（需要 dirty tracking, flush 邏輯）
- 不適合需要 durability 的場景

適用場景：
- 計數器（like count, view count）— 丟幾個不要緊
- Gaming leaderboard — 定期 sync 就好
- IoT sensor data — 批量寫入更高效

4.5 Cache Invalidation

"There are only two hard things in Computer Science: 
cache invalidation and naming things." — Phil Karlton

策略 1: TTL (Time-To-Live)
- 設定過期時間，到期自動刪除
- 簡單但可能有 stale window
- redis.setex("user:123", 3600, data)  # 1 hour TTL

策略 2: Event-driven invalidation
- DB 更新時主動刪除 cache
- 更即時但需要額外機制
- 用 CDC (Change Data Capture) 或 application-level event

策略 3: Version-based
- Cache key 包含版本號
- 更新時 bump version → 舊 cache 自然失效
- "user:123:v5" → update → "user:123:v6"

為什麼用「刪除」而不是「更新」cache？
- 刪除：簡單，下次讀取時重新載入最新值
- 更新：可能有 race condition
  Thread A: read DB (old value)
  Thread B: write DB (new value)
  Thread B: update cache (new value)
  Thread A: update cache (old value) ← 覆蓋了新值！
- 刪除不會有這個問題（最多多一次 cache miss）

4.6 Cache Stampede (Thundering Herd)

問題：
- 熱門 key 的 TTL 到期
- 同時 1000 個 request 發現 cache miss
- 1000 個 request 同時打 DB
- DB 被打爆

解決方案：

1. Mutex Lock:
   def get_with_lock(key):
       value = cache.get(key)
       if value: return value

       if cache.set(f"lock:{key}", 1, nx=True, ex=5):  # 拿到鎖
           value = db.query(key)
           cache.set(key, value, ex=3600)
           cache.delete(f"lock:{key}")
           return value
       else:  # 沒拿到鎖，等一下再試
           sleep(0.05)
           return get_with_lock(key)

2. Probabilistic Early Expiration:
   - 在 TTL 到期前，有一定機率提前 refresh
   - 避免所有 request 同時 miss
   def should_refresh(ttl_remaining, total_ttl):
       # 剩餘 TTL 越少，refresh 機率越高
       return random() < (1 - ttl_remaining / total_ttl) * 0.1

3. Background Refresh:
   - 背景 worker 在 TTL 到期前主動 refresh
   - 用戶永遠不會碰到 cache miss
   - 適合 hot key（值得額外的 refresh 成本）

4.7 Hot Key Problem

問題：
- 某個 key 被極大量讀取（例如 celebrity user profile）
- 單個 Redis node 扛不住（100K+ QPS on one key）

解決方案：

1. Local Cache (L1 Cache):
   - Application server 本地 in-memory cache
   - 例：Guava Cache, Caffeine (Java), lru-cache (Node.js)
   - TTL 很短（10-30s）避免 stale
   - 每台 server 獨立 cache → 分散壓力

2. Key Replication:
   - 把 hot key 複製到多個 Redis node
   - 讀取時 random 選一個 node
   - key: "user:celebrity:123" → "user:celebrity:123:r0", "r1", "r2"

3. Redis Cluster with Read Replicas:
   - 每個 master 有多個 read replica
   - Hot key 的讀取分散到 replicas

Cache 層次：
┌─────────────────────────────────┐
│ L1: Local Memory (10-30s TTL)   │ ← 0.01ms, per-server
├─────────────────────────────────┤
│ L2: Redis Cluster (1-24h TTL)   │ ← 0.5ms, shared
├─────────────────────────────────┤
│ L3: Database                    │ ← 5-50ms, source of truth
└─────────────────────────────────┘

4.8 CDN (Content Delivery Network)

CDN 是 cache 的一種特殊形式 — 把靜態內容 cache 在離用戶最近的 edge server。

適合 CDN 的內容：
- 圖片、影片、CSS、JS（靜態檔案）
- API response（如果可以 cache）
- HTML pages（如果不是 personalized）

CDN 的工作方式：
1. 用戶請求 image.jpg
2. DNS 解析到最近的 CDN edge server
3. Edge server 有 cache → 直接返回（cache hit）
4. Edge server 沒有 → 去 origin server 拿 → cache → 返回

效果：
- Latency: 200ms (cross-region) → 20ms (edge server)
- Bandwidth: Origin server 只需處理 cache miss
- Availability: CDN 有多個 edge，一個掛了自動切換

CDN Invalidation:
- TTL-based: 設定 Cache-Control header
- Purge: 主動清除 CDN cache（API call）
- Versioned URLs: image_v2.jpg（新版本 = 新 URL = 不需要 invalidate）

短 TTL 更新鮮的資料 更多 cache miss
大 cache 更多資料 cached 更貴（memory）
小 cache 便宜 更多 eviction, 低 hit rate

2. Lease mechanism (防止 thundering herd + stale set)
3. Cold cluster warmup (新 cluster 從舊 cluster 拿資料)
4. Gutter pool (backup pool，主 pool 掛了自動切換)

Lease 機制：
- Client A cache miss → 拿到 lease token
- Client A 去查 DB
- 同時 Client B 也 cache miss → 被告知 "wait, someone is loading"
- Client A 查完 DB → 用 lease token 寫入 cache
- Client B retry → cache hit

效果：
- 避免 thundering herd
- 避免 stale data (lease 過期 = 重新載入)

Chapter 11：Load Balancer

1. 這是什麼？

Load Balancer（負載均衡器）把流量分配到多台 server，確保沒有單一 server 過載。

Without LB:
Client → Single Server (overloaded, SPOF)

With LB:
Client → Load Balancer → Server 1 (33% traffic)
                       → Server 2 (33% traffic)
                       → Server 3 (33% traffic)

2. 為什麼需要？

  • 分散流量，避免單台 server 過載
  • 提供 high availability（server 掛了自動移除）
  • 支援 horizontal scaling（加 server 就能扛更多流量）
  • SSL termination（集中處理加密，減輕 backend 負擔）

3. 不用會怎樣？

  • 單台 server 成為瓶頸和 SPOF
  • 無法 horizontal scale
  • Server 掛了用戶直接看到 error
  • 無法做 rolling deployment（沒辦法逐台更新）

4. 常見 Implementation

4.1 L4 vs L7 Load Balancer

L4 (Transport Layer):
- 基於 IP + Port 做路由
- 不看 HTTP content（不知道 URL、header、cookie）
- 速度快（不需要解析 HTTP）
- 例：AWS NLB, HAProxy (TCP mode), Linux IPVS

L7 (Application Layer):
- 基於 HTTP content 做路由（URL path, header, cookie）
- 可以做 content-based routing
- 可以做 SSL termination
- 例：AWS ALB, Nginx, HAProxy (HTTP mode), Envoy

什麼時候用 L4：
- 需要極高 throughput（millions of connections）
- 不需要 content-based routing
- Non-HTTP protocols (gRPC, WebSocket, custom TCP)
- 例：Database connection load balancing

什麼時候用 L7：
- 需要 URL-based routing (/api → service A, /web → service B)
- 需要 header-based routing (A/B testing, canary)
- 需要 SSL termination
- 需要 request/response modification
- 例：API Gateway, microservice routing

4.2 Load Balancing Algorithms

1. Round Robin:
   - 依序分配：1→2→3→1→2→3...
   - 簡單，適合 server 能力相同的情況
   - 問題：不考慮 server 當前負載

2. Weighted Round Robin:
   - 能力強的 server 分配更多流量
   - Server A (weight 3): 拿 3/6 的流量
   - Server B (weight 2): 拿 2/6 的流量
   - Server C (weight 1): 拿 1/6 的流量

3. Least Connections:
   - 把 request 送到當前連線數最少的 server
   - 適合 request 處理時間差異大的場景
   - 自動適應 server 能力差異

4. Least Response Time:
   - 把 request 送到回應最快的 server
   - 結合了 connection count 和 latency
   - 最智能但 overhead 較高

5. IP Hash:
   - hash(client_ip) % num_servers
   - 同一 client 永遠去同一 server
   - 適合需要 session affinity 的場景
   - 問題：server 增減時會 rehash

6. Consistent Hashing:
   - 類似 IP Hash 但增減 server 影響小
   - 適合 WebSocket、stateful 連線
   - 例：WebSocket connection routing

4.3 Health Check

LB 需要知道哪些 server 是健康的：

Active Health Check:
- LB 定期發 request 到每台 server
- 例：每 10 秒 GET /health
- 連續 3 次失敗 → 標記為 unhealthy → 停止發流量
- 恢復後連續 2 次成功 → 標記為 healthy

Passive Health Check:
- 觀察實際 request 的結果
- 如果某台 server 連續返回 5xx → 標記為 unhealthy
- 不需要額外的 health check request

Health Check Endpoint 設計：
GET /health
Response:
{
  "status": "healthy",
  "checks": {
    "database": "ok",
    "redis": "ok",
    "disk_space": "ok"
  },
  "version": "1.2.3",
  "uptime": "3d 5h"
}

Shallow vs Deep health check:
- Shallow: 只檢查 server 本身是否活著（快，但可能 DB 掛了不知道）
- Deep: 檢查所有 dependency（慢，但更準確）
- 建議：LB 用 shallow（快速判斷），monitoring 用 deep（全面檢查）

4.4 Active-Active vs Active-Passive

Active-Active:
- 多台 LB 同時服務流量
- DNS round robin 或 anycast 分配到不同 LB
- 任一台 LB 掛了，其他繼續服務
- 資源利用率高

Active-Passive:
- 一台 LB 服務所有流量（active）
- 另一台待命（passive/standby）
- Active 掛了 → passive 接管（failover）
- 資源利用率低（passive 平時閒置）
- 但 failover 更簡單可靠

雲端通常是 Active-Active：
- AWS ALB/NLB: 自動 multi-AZ, active-active
- 不需要自己管 LB 的 HA

4.5 TLS Termination

TLS termination at LB:
Client ──HTTPS──→ LB ──HTTP──→ Backend Servers

好處：
- Backend 不需要處理 TLS（省 CPU）
- 證書管理集中在 LB
- LB 可以看到 HTTP content（做 L7 routing）

壞處：
- LB 到 Backend 之間是明文（如果在同一 VPC 通常可接受）
- 如果需要 end-to-end encryption → TLS passthrough 或 re-encryption

TLS Passthrough (L4):
Client ──HTTPS──→ LB ──HTTPS──→ Backend
- LB 不解密，直接轉發
- Backend 自己處理 TLS
- LB 無法做 L7 routing

5. Tradeoffs

方案 Throughput 靈活性 複雜度 適用場景
L4 LB Very High Low Low TCP/UDP, high throughput
L7 LB High High Medium HTTP, content routing
DNS LB Medium Low Low Multi-region, simple
Client-side LB High High High Microservices (gRPC)

6. Failure Modes

Failure 原因 影響 Mitigation
LB itself fails Hardware, software bug All traffic drops Active-active LB, DNS failover
Health check false positive Network glitch Healthy server removed Require multiple failures before removal
Health check false negative Shallow check misses DB issue Traffic sent to broken server Deep health check for critical deps

Chapter 12：Queue / Stream

1. 這是什麼？

Message Queue 和 Event Stream 是異步通訊的基礎設施。Producer 發送 message，Consumer 處理 message，兩者不需要同時在線。

Synchronous (without queue):
Service A ──request──→ Service B ──response──→ Service A
- A 必須等 B 回覆
- B 掛了 → A 也失敗

Asynchronous (with queue):
Service A ──publish──→ Queue ──consume──→ Service B
- A 發完就走，不等 B
- B 掛了 → message 留在 queue，B 恢復後繼續處理
- A 和 B 完全解耦

2. 為什麼需要？

  • 解耦：Producer 和 Consumer 獨立開發、部署、擴展
  • 削峰：流量高峰時 queue 當 buffer，Consumer 按自己的速度處理
  • 可靠性：message 持久化在 queue，不怕 Consumer 暫時掛掉
  • 擴展性：加更多 Consumer 就能提高處理速度

具體場景：

1. 用戶下單後：
   - 同步：扣庫存 + 發通知 + 更新推薦 + 記 analytics = 2s
   - 異步：扣庫存（同步）→ 發 event → 通知/推薦/analytics 異步處理 = 200ms

2. 流量高峰（Black Friday）：
   - Without queue: 10x traffic → backend 崩潰
   - With queue: 10x traffic → queue 暫存 → backend 按能力處理

3. 不用會怎樣？

  • 服務之間強耦合（一個掛全部掛）
  • 無法應對流量高峰（沒有 buffer）
  • 失敗的操作無法重試（message 丟了）
  • 系統延遲高（所有操作都同步等待）

4. 常見 Implementation

4.1 Kafka

特點：
- Distributed event streaming platform
- 超高吞吐量（1M+ messages/sec per broker）
- 持久化（message 存在 disk，可以 replay）
- Consumer group（多個 consumer 分擔 partition）
- Ordering guarantee（within partition）
- Retention（可以保留 7 天、30 天甚至永久）

架構：
Producer → Topic (partitioned) → Consumer Group
                                    ├── Consumer 1 (partition 0, 1)
                                    ├── Consumer 2 (partition 2, 3)
                                    └── Consumer 3 (partition 4, 5)

適用場景：
- Event sourcing
- Log aggregation
- Stream processing (with Kafka Streams / Flink)
- CDC (Change Data Capture)
- Analytics pipeline
- 需要 replay 的場景

不適合：
- 需要 message-level acknowledgment（用 RabbitMQ/SQS）
- 需要 complex routing（用 RabbitMQ exchange）
- 低延遲 request-reply pattern

4.2 RabbitMQ

特點：
- Traditional message broker
- 支援多種 protocol (AMQP, MQTT, STOMP)
- 靈活的 routing (direct, topic, fanout, headers exchange)
- Message-level acknowledgment
- Priority queue
- Dead letter queue (DLQ)

架構：
Producer → Exchange → Binding → Queue → Consumer

Exchange types:
- Direct: routing key 完全匹配
- Topic: routing key pattern 匹配 (*.error, order.#)
- Fanout: 廣播到所有 bound queue
- Headers: 基於 message header 路由

適用場景：
- Task queue (background jobs)
- RPC over message queue
- Complex routing requirements
- 需要 message priority
- 需要 per-message acknowledgment

vs Kafka：
| | Kafka | RabbitMQ |
|---|-------|----------|
| Throughput | Very High (1M+/s) | High (50K/s) |
| Ordering | Per partition | Per queue |
| Retention | Configurable (days/forever) | Until consumed |
| Replay | Yes | No (once consumed, gone) |
| Routing | Simple (topic/partition) | Complex (exchange types) |
| Use case | Event streaming, logs | Task queue, RPC |

4.3 SQS (AWS Simple Queue Service)

特點：
- Fully managed (no infrastructure to manage)
- Two types: Standard (at-least-once, best-effort ordering)
             FIFO (exactly-once, strict ordering)
- Visibility timeout (message invisible while being processed)
- Dead letter queue
- Auto-scaling (unlimited throughput for Standard)
- Pay per message

Standard Queue:
- Nearly unlimited throughput
- At-least-once delivery (may get duplicates)
- Best-effort ordering (may be out of order)

FIFO Queue:
- 300 messages/sec (3000 with batching)
- Exactly-once processing
- Strict ordering within message group
- Message deduplication

適用場景：
- Simple task queue (don't want to manage infrastructure)
- Decoupling microservices on AWS
- 不需要 replay 或 complex routing

4.4 Delivery Semantics

At-most-once:
- Message 可能丟失，但不會重複
- 實現：發送後不確認，不重試
- 適用：metrics, logs（丟幾個不要緊）

At-least-once:
- Message 不會丟失，但可能重複
- 實現：Consumer ack 後才刪除 message；失敗則重試
- 適用：大部分場景（配合 idempotency）
- 這是最常見的選擇

Exactly-once:
- Message 不丟失也不重複
- 實現：非常困難！通常是 at-least-once + idempotent consumer
- 或者：Kafka transactions (within Kafka ecosystem)
- 適用：金融交易（但通常用 idempotency 實現）

面試中怎麼講：
"I'll use at-least-once delivery with idempotent consumers. 
This is the pragmatic choice because:
1. At-most-once risks data loss (unacceptable for orders)
2. True exactly-once is extremely complex and expensive
3. At-least-once + idempotency key gives us effective exactly-once 
   with much simpler implementation"

4.5 Idempotency

問題：At-least-once delivery 意味著 consumer 可能收到重複 message。
解決：讓 consumer 的處理是 idempotent 的（處理多次結果一樣）。

Implementation:

1. Idempotency Key:
   - 每個 message 帶一個 unique key
   - Consumer 處理前檢查 key 是否已處理過
   - 已處理 → skip
   - 未處理 → 處理 + 記錄 key

   def process_payment(message):
       idempotency_key = message['idempotency_key']

       # Check if already processed
       if redis.exists(f"processed:{idempotency_key}"):
           return  # Skip duplicate

       # Process
       execute_payment(message)

       # Mark as processed (with TTL for cleanup)
       redis.setex(f"processed:{idempotency_key}", 86400, "1")

2. Database unique constraint:
   - INSERT ... ON CONFLICT DO NOTHING
   - 重複 insert 自動被忽略

3. Conditional update:
   - UPDATE orders SET status = 'paid' WHERE id = ? AND status = 'pending'
   - 第二次 update 不會匹配（status 已經不是 pending）

4.6 Ordering

為什麼 ordering 很難：
- 多個 partition/queue → 不同 partition 之間無法保證順序
- 多個 consumer → 並行處理可能亂序
- Retry → 失敗的 message 重試時可能插隊

Kafka 的 ordering guarantee:
- 同一 partition 內保證順序
- 不同 partition 之間不保證
- 策略：把需要有序的 message 發到同一 partition
  - 例：同一 user 的 message → partition key = user_id
  - 同一 order 的事件 → partition key = order_id

SQS FIFO 的 ordering:
- Message Group ID: 同一 group 內保證順序
- 不同 group 之間可以並行

什麼時候需要 ordering：
✅ 同一用戶的操作（create → update → delete 必須有序）
✅ 同一訂單的狀態變更（pending → paid → shipped）
❌ 不同用戶之間（User A 和 User B 的操作不需要有序）
❌ 獨立事件（notification, analytics event）

4.7 Dead Letter Queue (DLQ)

問題：某些 message 永遠處理失敗（bad data, bug, dependency down）
如果一直 retry → 阻塞其他 message

解決：DLQ — 失敗超過 N 次的 message 移到 DLQ

Flow:
Main Queue → Consumer → 失敗 → retry (3 times) → 還是失敗 → DLQ

DLQ 的處理：
1. Alert on-call（DLQ 有 message = 有問題）
2. 人工檢查（是 bug? bad data? dependency issue?）
3. 修復後 replay DLQ message 回 main queue
4. 或者 discard（如果是 invalid data）

DLQ 設計：
- 保留原始 message + error info + retry count
- 設定 retention（例如 14 天）
- Monitor DLQ depth（alert if > 0）

4.8 Backpressure

問題：Producer 速度 > Consumer 速度 → queue 無限增長

解決方案：

1. Bounded Queue:
   - Queue 有 size limit
   - 滿了 → producer 被 block 或收到 error
   - 例：Kafka (disk limit), RabbitMQ (memory limit)

2. Rate Limiting at Producer:
   - 限制 producer 的發送速率
   - 例：API rate limit → 間接限制 message 產生速度

3. Consumer Auto-scaling:
   - Queue depth 增加 → 自動加 consumer
   - Queue depth 減少 → 自動減 consumer
   - 例：AWS Lambda + SQS (自動 scale)

4. Drop Policy:
   - Queue 滿了 → drop oldest / drop newest
   - 適合 metrics, real-time data（舊資料沒價值）

Monitoring:
- Queue depth (越來越大 = consumer 跟不上)
- Consumer lag (Kafka: offset difference)
- Processing rate (messages/sec)
- Error rate (failed messages/sec)

RabbitMQ High Per queue No Medium Task queue, RPC

1. Trip lifecycle events:
   Trip Requested → Driver Matched → Trip Started → Trip Completed
   - Kafka topic: 'trips'
   - Partition key: trip_id (保證同一 trip 的事件有序)
   - Consumers: billing, analytics, driver stats, ETA model

2. Driver location updates:
   - 每秒數百萬次 GPS update
   - Kafka topic: 'driver-locations'
   - Partition key: driver_id
   - Consumer: matching service, ETA service, map service
   - Retention: 1 hour (舊位置沒用)

3. Payment events:
   - Kafka topic: 'payments'
   - Exactly-once semantics (Kafka transactions)
   - Consumer: ledger service, receipt service, fraud detection
   - DLQ: payment failures → manual review

Key design decisions:
- Kafka for high-throughput event streaming
- SQS for simple task queues (email sending, push notification)
- 不同 topic 不同 retention (locations: 1h, trips: 30d, payments: forever)

追問 Senior 回答
"How do you ensure exactly-once processing?" At-least-once delivery + idempotent consumer (idempotency key in Redis/DB). True exactly-once only within Kafka transactions.
"Kafka vs SQS?" Kafka for event streaming (replay, high throughput, ordering). SQS for simple task queue (managed, no infra, per-message ack).
"How do you handle message ordering across services?" Design for eventual consistency. If strict ordering needed, use same partition key. Cross-service ordering usually not required.
"What if consumer is much slower than producer?" Auto-scale consumers, backpressure at API layer, or accept processing delay (queue as buffer).
"How do you replay events?" Kafka: reset consumer offset to earlier timestamp. SQS: not possible (messages deleted after consumption).

Chapter 13：Rate Limiter

1. 這是什麼？

Rate Limiter 限制用戶或系統在一段時間內能發送的 request 數量。超過限制的 request 會被拒絕（通常返回 HTTP 429 Too Many Requests）。

例子：
- Twitter API: 300 requests / 15 minutes per user
- GitHub API: 5000 requests / hour per token
- Stripe: 100 requests / second per account

2. 為什麼需要？

  • 防止濫用：惡意用戶或 bot 不能打爆你的系統
  • 保護資源：確保所有用戶公平共享系統資源
  • 成本控制：防止意外的流量暴增導致帳單爆炸
  • 穩定性：在高峰期保護 downstream services

3. 不用會怎樣？

  • DDoS 攻擊直接打穿系統
  • 一個 bug 的 client 無限重試，拖垮整個服務
  • 爬蟲大量抓取，影響正常用戶
  • 下游服務被上游的流量打爆

4. 常見 Implementation

4.1 Fixed Window Counter

原理：把時間分成固定窗口（例如每分鐘），計算窗口內的 request 數。

例子：限制 100 requests/minute
- 12:00:00 - 12:00:59 → counter = 0...100 (允許)
- 12:00:xx 第 101 個 request → 拒絕
- 12:01:00 → counter reset to 0

Implementation (Redis):
def is_allowed(user_id, limit=100, window=60):
    key = f"rate:{user_id}:{int(time.time()) // window}"
    count = redis.incr(key)
    if count == 1:
        redis.expire(key, window)
    return count <= limit

優點：簡單、記憶體少
缺點：邊界問題 — 在窗口交界處可能允許 2x 的流量
  例：12:00:59 發 100 個 + 12:01:00 發 100 個 = 1 秒內 200 個

4.2 Sliding Window Log

原理：記錄每個 request 的 timestamp，計算最近 N 秒內的 request 數。

Implementation:
def is_allowed(user_id, limit=100, window=60):
    now = time.time()
    key = f"rate:{user_id}"

    # Remove old entries
    redis.zremrangebyscore(key, 0, now - window)

    # Count current window
    count = redis.zcard(key)

    if count < limit:
        redis.zadd(key, {str(now): now})
        redis.expire(key, window)
        return True
    return False

優點：精確，沒有邊界問題
缺點：記憶體大（要存每個 request 的 timestamp）
  100 requests × 8 bytes × 1M users = 800MB

4.3 Sliding Window Counter

原理：結合 fixed window 和 sliding window 的優點。
用前一個窗口的 count 按比例計算。

例子：限制 100 requests/minute, 當前時間 12:01:20
- 前一個窗口 (12:00:00-12:00:59): count = 80
- 當前窗口 (12:01:00-12:01:59): count = 30
- 當前位置在窗口的 20/60 = 33% 處
- 估算值 = 80 × (1 - 33%) + 30 = 53.6 + 30 = 83.6
- 83.6 < 100 → 允許

優點：記憶體小（只存 2 個 counter），精確度高
缺點：是近似值（但誤差很小，< 1%）

4.4 Token Bucket

原理：
- 桶裡有 tokens（初始滿的）
- 每個 request 消耗 1 個 token
- 桶以固定速率補充 tokens
- 桶滿了就不再補充
- 沒有 token → 拒絕 request

參數：
- Bucket size (capacity): 最大 burst 量
- Refill rate: 每秒補充幾個 token

例子：capacity=10, refill_rate=2/sec
- 初始：10 tokens
- 瞬間 burst 10 個 request → 全部允許（10 tokens 用完）
- 之後每秒只能 2 個 request（等 refill）
- 5 秒後桶又滿了（10 tokens）

Implementation:
def is_allowed(user_id, capacity=10, refill_rate=2):
    key = f"bucket:{user_id}"
    now = time.time()

    bucket = redis.hgetall(key)
    tokens = float(bucket.get('tokens', capacity))
    last_refill = float(bucket.get('last_refill', now))

    # Refill tokens
    elapsed = now - last_refill
    tokens = min(capacity, tokens + elapsed * refill_rate)

    if tokens >= 1:
        tokens -= 1
        redis.hset(key, mapping={'tokens': tokens, 'last_refill': now})
        redis.expire(key, capacity // refill_rate + 1)
        return True
    return False

優點：
- 允許 burst（桶滿時可以瞬間發很多）
- 平均速率受控
- Amazon 和 Stripe 都用這個

缺點：
- 實現稍複雜
- 需要存 2 個值（tokens + last_refill）

4.5 Leaky Bucket

原理：
- Request 進入桶（queue）
- 桶以固定速率漏出（處理）
- 桶滿了 → 新 request 被丟棄

跟 Token Bucket 的差別：
- Token Bucket: 允許 burst（桶滿時可以瞬間消耗所有 token）
- Leaky Bucket: 不允許 burst（永遠以固定速率處理）

適用場景：
- 需要平滑流量（不允許 burst）
- 例：向第三方 API 發送 request（他們有嚴格的 rate limit）

4.6 Distributed Rate Limiter

問題：多台 server 各自做 rate limiting → 實際允許 N × limit

例子：limit = 100/min, 10 台 server
- 每台 server 各自計數 → 用戶實際可以發 1000/min

解決方案：

1. Centralized (Redis):
   - 所有 server 共用一個 Redis counter
   - 優點：精確
   - 缺點：每個 request 都要查 Redis（增加 latency）

2. Local + Sync:
   - 每台 server 本地計數
   - 定期 sync 到 central store
   - 優點：低 latency
   - 缺點：不精確（sync 之間可能超限）

3. Token bucket per server:
   - 把 total limit 平分給每台 server
   - 100/min ÷ 10 servers = 10/min per server
   - 優點：不需要 central store
   - 缺點：如果流量不均勻，某些 server 的 quota 浪費

推薦：用 Redis（方案 1）。
Redis 延遲 < 1ms，對大部分系統來說可以接受。
用 Lua script 保證 atomic operation。

4.7 Rate Limit 的維度

Per-User: 每個用戶 100 req/min
Per-IP: 每個 IP 1000 req/min（防 DDoS）
Per-API-Key: 每個 API key 5000 req/hour
Per-Endpoint: POST /api/orders 限制更嚴格
Per-Tenant: 企業客戶有更高的 limit

多層 rate limiting:
Layer 1: Per-IP (防 DDoS) — 在 LB/CDN 層
Layer 2: Per-User (防濫用) — 在 API Gateway 層
Layer 3: Per-Service (保護 downstream) — 在 service 層

Failure 影響 Mitigation

- 適用：安全相關（login attempt limiting, payment）

Chapter 14：Authentication / Authorization / Security

1. 這是什麼？

Authentication (AuthN): 你是誰？
- 驗證用戶身份
- 例：登入（username + password → 確認是本人）

Authorization (AuthZ): 你能做什麼？
- 驗證用戶權限
- 例：普通用戶不能刪除其他人的帖子

Security: 保護系統和資料不被未授權存取或攻擊

2. 為什麼需要？

  • 沒有 AuthN → 任何人都能冒充其他用戶
  • 沒有 AuthZ → 任何用戶都能做任何操作（包括刪除資料庫）
  • 沒有 Security → 資料洩露、系統被攻擊、法律問題

3. 不用會怎樣？

  • 資料洩露（用戶個資、信用卡）
  • 系統被入侵
  • 法律責任（GDPR, CCPA 罰款）
  • 面試中不提 security → 被認為缺乏 production 經驗

4. 常見 Implementation

4.1 Session-based Authentication

Flow:
1. User 登入 (username + password)
2. Server 驗證 → 建立 session → 存在 server (or Redis)
3. 返回 session_id (通常放在 cookie)
4. 後續 request 帶 session_id → server 查 session store → 確認身份

優點：
- Server 完全控制 session（可以隨時 invalidate）
- 簡單直觀

缺點：
- Server 需要存 session state（stateful）
- Horizontal scaling 需要 shared session store (Redis)
- 不適合 mobile app 和 third-party API

4.2 JWT (JSON Web Token)

Flow:
1. User 登入 → Server 驗證 → 產生 JWT (signed with secret)
2. 返回 JWT 給 client
3. Client 每次 request 帶 JWT (Authorization: Bearer <token>)
4. Server 驗證 JWT signature → 確認身份（不需要查 DB）

JWT 結構：
Header.Payload.Signature

Header: { "alg": "HS256", "typ": "JWT" }
Payload: { "user_id": 123, "role": "admin", "exp": 1700000000 }
Signature: HMAC-SHA256(header + payload, secret)

優點：
- Stateless（server 不需要存 session）
- 適合 microservices（每個 service 都能驗證）
- 適合 mobile 和 SPA

缺點：
- 無法即時 revoke（除非加 blacklist）
- Token 洩露 → 在過期前都能被使用
- Payload 不加密（只是 base64，別放敏感資料）

Best practices：
- 短 expiration (15 min access token + refresh token)
- 用 HTTPS only
- 存在 httpOnly cookie（防 XSS）或 memory（不存 localStorage）
- Refresh token rotation（每次 refresh 都換新的）

4.3 OAuth 2.0

用途：讓第三方應用存取用戶資源，不需要用戶給出密碼。

例子：用 Google 帳號登入第三方 app

Flow (Authorization Code Grant):
1. User 點 "Login with Google"
2. Redirect 到 Google 授權頁面
3. User 同意授權
4. Google redirect 回 app，帶 authorization code
5. App 用 code 向 Google 換 access token (server-to-server)
6. App 用 access token 存取 Google API (get user info)

Roles:
- Resource Owner: 用戶
- Client: 第三方 app
- Authorization Server: Google (發 token)
- Resource Server: Google API (驗證 token, 返回資料)

面試中的應用：
"For third-party integrations, I'll use OAuth 2.0 with 
authorization code flow. This ensures we never see the user's 
Google password, and the user can revoke access at any time."

4.4 RBAC / ABAC

RBAC (Role-Based Access Control):
- 用戶 → 角色 → 權限
- 例：admin 角色有 delete 權限，viewer 角色只有 read 權限
- 簡單，適合大部分場景

User: John → Role: editor → Permissions: [read, write, publish]
User: Jane → Role: admin  → Permissions: [read, write, publish, delete]

ABAC (Attribute-Based Access Control):
- 基於屬性做決策（用戶屬性、資源屬性、環境屬性）
- 更靈活但更複雜
- 例：只有 department=engineering AND level>=5 的人能存取 production DB

Policy: 
  IF user.department == "engineering" 
  AND user.level >= 5 
  AND resource.environment == "production"
  AND time.hour BETWEEN 9 AND 18
  THEN ALLOW

什麼時候用 RBAC vs ABAC：
- RBAC: 權限模型簡單，角色數量有限（< 20 種角色）
- ABAC: 需要細粒度控制，條件複雜（multi-tenant, compliance）

4.5 API Security

1. API Key:
   - 簡單的 authentication（識別 caller）
   - 不適合 user-level auth（key 洩露 = 全部權限）
   - 適合 service-to-service, third-party API access

2. mTLS (Mutual TLS):
   - Client 和 Server 互相驗證證書
   - 適合 service-to-service（microservices 內部通訊）
   - 例：Istio service mesh 自動管理 mTLS

3. Rate Limiting + Abuse Detection:
   - 限制 request 頻率
   - 偵測異常模式（大量 failed login, unusual access pattern）
   - 自動 block suspicious IP/user

4. Input Validation:
   - 永遠不信任 client input
   - SQL injection prevention (parameterized queries)
   - XSS prevention (escape output)
   - CSRF prevention (token)

4.6 Encryption

Encryption at Rest:
- 資料存在 disk 時加密
- 例：AWS RDS encryption, S3 server-side encryption
- 保護：disk 被偷或 unauthorized access to storage

Encryption in Transit:
- 資料在網路傳輸時加密
- 例：HTTPS (TLS), gRPC with TLS
- 保護：man-in-the-middle attack, network sniffing

End-to-End Encryption (E2EE):
- 只有 sender 和 receiver 能解密
- Server 也看不到明文
- 例：WhatsApp, Signal
- 實現：Public key exchange (Diffie-Hellman)

Chapter 15：Observability

1. 這是什麼？

Observability 是指你能從系統的外部輸出（logs, metrics, traces）來理解系統內部狀態的能力。

Three Pillars of Observability:

1. Logs: 離散事件的記錄
   "2024-01-15 10:23:45 ERROR PaymentService: Payment failed for order_123, reason: timeout"

2. Metrics: 數值型的時間序列資料
   payment_success_rate = 99.2%
   api_latency_p99 = 450ms
   active_connections = 12,345

3. Traces: 一個 request 跨多個 service 的完整路徑
   Request abc123: Client → Gateway (2ms) → OrderService (15ms) → PaymentService (200ms) → DB (5ms)

2. 為什麼需要？

  • 沒有 observability → 系統出問題時你是瞎的
  • 不知道哪個 service 慢、哪個 query 有問題、哪個 server 快掛了
  • 無法做 capacity planning（不知道現在用了多少資源）
  • 面試中提到 observability 是 Senior 的加分項（很多人只畫 happy path）

3. 不用會怎樣？

  • 系統掛了不知道為什麼
  • 用戶抱怨慢但你找不到瓶頸
  • 問題要幾小時才能定位（MTTR 很長）
  • 無法預防問題（只能事後救火）

4. 常見 Implementation

4.1 Logging

Log Levels:
- DEBUG: 開發時的詳細資訊
- INFO: 正常操作的記錄
- WARN: 潛在問題但系統仍正常
- ERROR: 操作失敗但系統仍運行
- FATAL: 系統即將崩潰

Structured Logging (推薦):
{
  "timestamp": "2024-01-15T10:23:45Z",
  "level": "ERROR",
  "service": "payment-service",
  "trace_id": "abc123",
  "user_id": "user_456",
  "message": "Payment failed",
  "error": "timeout after 5000ms",
  "order_id": "order_789",
  "amount": 99.99
}

→ 可以用 Elasticsearch 搜尋、過濾、聚合

Log Pipeline:
Application → Log Agent (Fluentd/Filebeat) → Kafka → Elasticsearch → Kibana

Best Practices:
- 用 structured logging (JSON)
- 包含 trace_id（跨 service 關聯）
- 不要 log 敏感資料（password, credit card）
- 設定 retention（30 天 hot, 90 天 warm, 1 年 cold）

4.2 Metrics

Types of Metrics:
- Counter: 只增不減（total_requests, error_count）
- Gauge: 可增可減（active_connections, memory_usage）
- Histogram: 分佈（request_latency_bucket）
- Summary: 百分位數（p50, p95, p99）

Key Metrics to Monitor:

RED Method (for services):
- Rate: requests/second
- Errors: error rate (%)
- Duration: latency (p50, p95, p99)

USE Method (for resources):
- Utilization: CPU %, memory %, disk %
- Saturation: queue depth, thread pool usage
- Errors: hardware errors, OOM kills

Golden Signals (Google SRE):
- Latency
- Traffic
- Errors
- Saturation

Tools: Prometheus + Grafana, Datadog, CloudWatch

4.3 Distributed Tracing

問題：一個 request 經過 10 個 service，哪個慢了？

解決：Distributed tracing — 追蹤一個 request 的完整路徑

Trace 結構：
Trace ID: abc123
├── Span: API Gateway (2ms)
├── Span: Auth Service (5ms)
├── Span: Order Service (150ms)
│   ├── Span: DB Query (10ms)
│   ├── Span: Payment Service (120ms)  ← 瓶頸！
│   │   ├── Span: Stripe API (100ms)
│   │   └── Span: DB Write (15ms)
│   └── Span: Cache Write (2ms)
└── Span: Notification Service (async, 50ms)

Implementation:
- 每個 request 產生 unique trace_id
- 每個 service 產生 span (start_time, end_time, metadata)
- Trace_id 在 service 之間傳遞 (HTTP header: X-Trace-Id)
- 所有 span 送到 tracing backend (Jaeger, Zipkin, X-Ray)

Tools: Jaeger, Zipkin, AWS X-Ray, Datadog APM

4.4 SLI / SLO / SLA

SLI (Service Level Indicator):
- 衡量服務品質的具體指標
- 例：p99 latency, error rate, availability

SLO (Service Level Objective):
- 對 SLI 設定的目標值
- 例：p99 latency < 200ms, availability > 99.9%
- 內部目標，用來指導工程決策

SLA (Service Level Agreement):
- 對外的承諾（合約）
- 通常比 SLO 寬鬆（留 buffer）
- 違反 SLA → 賠償
- 例：SLO = 99.95%, SLA = 99.9%

Error Budget:
- 允許的 "不可用" 時間
- 99.9% SLO → 每月 43 分鐘 error budget
- Error budget 用完 → 凍結 feature release，專注 reliability
- Error budget 充足 → 可以承擔更多風險（faster releases）

面試中怎麼講：
"I'd define SLOs based on user-facing journeys:
- Feed loading: p99 < 500ms, availability 99.9%
- Payment: p99 < 2s, availability 99.99%, error rate < 0.01%
- Search: p99 < 200ms, availability 99.9%

Each SLO has an error budget. If we burn through 50% of monthly 
budget in one week, we trigger a reliability sprint."

4.5 Alerting

Alert 設計原則：
1. Alert on symptoms, not causes
   ✅ "Error rate > 1% for 5 minutes"
   ❌ "CPU > 80%" (可能不影響用戶)

2. Actionable alerts only
   ✅ Alert → on-call 知道要做什麼
   ❌ Alert → "hmm, not sure what to do" → alert fatigue

3. Severity levels:
   - P1 (Critical): 用戶受影響，立刻處理
   - P2 (High): 可能很快影響用戶，1 小時內處理
   - P3 (Medium): 需要關注，工作時間處理
   - P4 (Low): 記錄，下次 sprint 處理

Alert 設定例子：
- p99 latency > 500ms for 5 min → P2 (page on-call)
- Error rate > 5% for 2 min → P1 (page on-call + manager)
- Disk usage > 80% → P3 (ticket)
- Cache hit rate < 90% → P3 (investigate)
- Queue depth growing for 10 min → P2 (consumer issue)

5. Tradeoffs

方面 多 observability 少 observability
問題定位 快（分鐘級） 慢（小時級）
成本 高（storage, compute） 低
Performance overhead 有（logging, tracing） 無
資料量 大（需要管理 retention） 小

6. Failure Modes

Failure 影響 Mitigation
Monitoring system down 看不到問題 Redundant monitoring, external health check
Alert fatigue 真正的 alert 被忽略 Reduce noise, only alert on actionable items
Log pipeline lag 看到的是幾分鐘前的狀態 Monitor pipeline lag itself
Sampling too aggressive Miss rare but important events Adaptive sampling (always sample errors)
Cardinality explosion Metrics storage OOM Limit label values, use exemplars

"For observability, I'll implement all three pillars:

8. 具體例子

例子：Debugging a Latency Spike

Scenario: p99 latency jumped from 200ms to 2000ms

Investigation flow:
1. Dashboard: Which service's latency increased?
   → Order Service p99: 200ms → 1800ms

2. Traces: Sample slow requests
   → Order Service → Payment Service (1500ms!) → Stripe API
   → Stripe API is responding slowly

3. Metrics: Payment Service error rate?
   → Error rate normal, but latency increased
   → Stripe API latency: p99 went from 100ms to 1500ms

4. Logs: Any errors from Stripe?
   → "Stripe API: rate limit exceeded, retrying..."
   → We're hitting Stripe's rate limit!

5. Root cause: Marketing campaign caused 3x order volume
   → Exceeded Stripe rate limit → retries → latency spike

6. Fix: 
   - Short term: Increase Stripe rate limit (contact Stripe)
   - Long term: Queue payment requests, process at controlled rate

Time to resolution: 15 minutes (with good observability)
Without observability: Could take hours of guessing

Chapter 16：Design URL Shortener

Problem Statement

設計一個像 bit.ly 的短網址服務。用戶輸入長 URL，系統返回短 URL；訪問短 URL 時 redirect 到原始 URL。

Clarifying Questions

  • 短網址長度？（7 characters）
  • 需要自訂 alias 嗎？（Yes, optional）
  • 短網址會過期嗎？（Optional, default 5 years）
  • 需要 analytics 嗎？（Click count, geo, referrer）
  • Scale？（100M DAU, read-heavy）

Requirements

Functional: Create short URL, redirect, custom alias, expiration, analytics Non-functional: p99 redirect < 50ms, 99.99% availability, no collision

Estimation

Write: 100M DAU × 0.1 URL/user/day = 10M URLs/day
Read: 100:1 ratio → 1B redirects/day
Write QPS: 10M / 86400 ≈ 115 QPS (peak: ~350)
Read QPS: 1B / 86400 ≈ 11,500 QPS (peak: ~35,000)
Storage (5yr): 10M/day × 365 × 5 × 200B ≈ 3.65 TB
Cache: Top 20% = ~730 GB (fits in Redis cluster)

API

POST /api/v1/shorten
  Body: { long_url, custom_alias?, expiration? }
  Response: { short_url, created_at }

GET /{short_code}
  Response: 301/302 Redirect to long_url

GET /api/v1/stats/{short_code}
  Response: { clicks, created_at, geo_distribution }

Data Model

Table: urls
  short_code (PK, varchar(7))
  long_url (text)
  user_id (bigint, nullable)
  created_at (timestamp)
  expires_at (timestamp, nullable)
  click_count (int)

Storage: PostgreSQL (strong consistency for writes)
Cache: Redis (short_code → long_url, TTL 24h)
Analytics: Kafka → ClickHouse (async, high-volume)

High-Level Design

Write Path:
Client → API Server → Key Generation Service → DB → Cache (warm)

Read Path (redirect):
Client → CDN/Cache → API Server → Redis Cache → DB (fallback)
                                       ↓
                              Kafka (click event, async)

Deep Dives

Key Generation:

Option A: Hash (MD5/SHA256) + truncate to 7 chars
- Pros: Simple, deterministic
- Cons: Collision possible, need collision check

Option B: Pre-generated Key Service (KGS)
- Pre-generate all possible 7-char keys (62^7 = 3.5 trillion)
- Store unused keys in DB, mark as used when assigned
- Pros: No collision, O(1) generation
- Cons: Need to manage key pool

Option C: Snowflake ID → Base62
- Unique ID generator → encode to base62
- Pros: No collision, distributed
- Cons: IDs are sequential (predictable)

My choice: KGS
- Pre-generate batch of keys, cache in memory
- Each server holds 1000 keys locally
- When local pool < 100, fetch more from KGS DB
- If server crashes, those keys are "lost" (acceptable, tiny fraction)

Caching Strategy:

- Cache-aside with Redis
- Key: short_code, Value: long_url
- TTL: 24h (popular URLs stay cached)
- Expected hit rate: 95%+ (Zipf distribution)
- Hot URLs (viral): replicate across Redis nodes

Bottlenecks & Failure Modes

1. KGS single point of failure
   → Run multiple KGS instances, each manages different key ranges

2. Cache stampede on popular URL expiry
   → Probabilistic early refresh for hot keys

3. Abuse (spam URLs, phishing)
   → URL blacklist check before creation, rate limit per user/IP

4. Analytics pipeline lag
   → Kafka buffer, async processing, doesn't affect redirect latency

Senior-Level Tradeoffs

301 vs 302 redirect:
- 301 (Permanent): Browser caches → fewer requests to our server
  But: Can't track clicks accurately (browser skips us)
- 302 (Temporary): Every click hits our server
  But: More load, more accurate analytics

Decision: 302 for analytics-enabled URLs, 301 for others

Chapter 17：Design News Feed / Twitter

Problem Statement

設計 Twitter/Facebook 的 News Feed 系統。用戶可以發文、follow 其他人、看到 following 的最新動態。

Clarifying Questions

  • Feed 是 chronological 還是 ranked？（Ranked）
  • 支援 media 嗎？（Yes, images/videos）
  • Celebrity users（millions of followers）？（Yes, need to handle）
  • Real-time updates 還是 pull-to-refresh？（Pull-to-refresh for MVP）
  • Scale？（300M MAU, 150M DAU）

Requirements

Functional: Post tweet, follow/unfollow, view feed (ranked), like/retweet Non-functional: Feed load p99 < 500ms, 99.99% availability, eventual consistency OK

Estimation

Write: 150M DAU × 2 tweets/day = 300M tweets/day → 3,500 QPS (peak 10K)
Read: 150M DAU × 10 feed loads/day = 1.5B reads/day → 17,000 QPS (peak 50K)
Storage: 300M × 500B/tweet = 150GB/day text, + media
Fanout: Average user has 200 followers → 300M × 200 = 60B fanout ops/day

API

POST /api/v1/tweets { content, media_ids[] }
GET /api/v1/feed?cursor={cursor}&page_size=20
POST /api/v1/follow { followee_id }
POST /api/v1/like { tweet_id }

Data Model

Tweet: { tweet_id (snowflake), user_id, content, media_urls, created_at, like_count }
User: { user_id, username, follower_count, following_count }
Follow: { follower_id, followee_id, created_at }
Feed Cache: Redis Sorted Set — key: feed:{user_id}, score: timestamp, value: tweet_id

Storage:
- Tweet metadata: Cassandra (write-optimized, time-series)
- User/Follow: PostgreSQL (relational, ACID)
- Feed: Redis (precomputed, fast read)
- Media: S3 + CDN
- Search: Elasticsearch

High-Level Design

Write Path:
User posts tweet → Tweet Service → DB + Kafka
                                        ↓
                              Fanout Service → update followers' feed cache (Redis)

Read Path:
User opens feed → Feed Service → Redis (precomputed feed)
                                    ↓ (cache miss)
                              Compute feed from DB + merge celebrity tweets

Deep Dives

Hybrid Fanout (核心設計):

普通用戶 (< 10K followers): Fanout on Write
- 發文時推送到所有 follower 的 feed cache
- 200 followers × 1 cache write = 200 ops (fast)
- Feed 讀取: O(1) from Redis

Celebrity (> 10K followers): Fanout on Read
- 發文時只存到自己的 timeline
- Follower 讀 feed 時: precomputed feed + merge celebrity tweets
- 避免 10M cache writes per celebrity tweet

Implementation:
def get_feed(user_id):
    # Get precomputed feed (from normal users)
    feed = redis.zrevrange(f"feed:{user_id}", 0, 19)

    # Get celebrity tweets (fanout on read)
    celebrities = get_followed_celebrities(user_id)
    for celeb in celebrities:
        celeb_tweets = get_recent_tweets(celeb.id, limit=5)
        feed.extend(celeb_tweets)

    # Merge and rank
    feed = rank(feed)
    return feed[:20]

Feed Ranking:

Simple ranking: chronological (sort by timestamp)
Advanced ranking (ML-based):
  score = f(relevance, recency, engagement, user_affinity)

Features:
- Recency: newer = higher score
- Engagement: likes + retweets + comments
- User affinity: how often you interact with this person
- Content type: video > image > text (for engagement)
- Diversity: don't show 10 tweets from same person

Implementation: Pre-compute scores in Fanout Service,
store in Redis Sorted Set with score = ranking_score

Bottlenecks & Failure Modes

1. Celebrity fanout storm
   → Hybrid model (fanout on read for celebrities)

2. Feed cache cold start (new user)
   → Compute feed on first load, cache for subsequent

3. Redis cluster failure
   → Circuit breaker, compute feed from DB (slower but works)

4. Kafka consumer lag (fanout delayed)
   → Auto-scale consumers, monitor lag, acceptable delay (< 30s)

5. Viral tweet (millions of likes in minutes)
   → Like count in Redis (atomic INCR), async persist to DB
   → Don't update every follower's feed for like count change

Common Follow-ups

  • "How would you add real-time updates?" → WebSocket for online users, push notification for offline
  • "How would you handle tweet deletion?" → Soft delete in DB, async remove from all feed caches
  • "How would you add search?" → Elasticsearch, index tweets on write (async via Kafka)

Chapter 18：Design Chat / Messenger

Problem Statement

設計一個即時通訊系統（WhatsApp/Messenger），支援 1v1 和 group chat。

Clarifying Questions

  • 1v1 only 還是 group chat？（Both, group max 500 people）
  • 需要 read receipts 嗎？（Yes）
  • 需要 file/image sharing？（Yes）
  • Online/offline status？（Yes）
  • Message history 保留多久？（Forever）
  • Scale？（500M DAU, 50M concurrent connections）

Requirements

Functional: Send/receive messages, group chat, read receipts, online status, media sharing Non-functional: Message delivery < 100ms, at-least-once delivery, message ordering per conversation

Estimation

Messages: 500M DAU × 40 messages/day = 20B messages/day
QPS: 20B / 86400 ≈ 230K messages/sec
Concurrent connections: 50M WebSocket connections
Storage: 20B × 200B/msg = 4TB/day → 1.5PB/year

High-Level Design

┌────────┐     WebSocket      ┌──────────────┐
│ Client │ ←───────────────→  │ Connection   │
└────────┘                    │ Service      │
                              └──────┬───────┘
                                     │
                              ┌──────▼───────┐
                              │ Message      │
                              │ Service      │
                              └──────┬───────┘
                                     │
                    ┌────────────────┼────────────────┐
                    │                │                │
             ┌──────▼──┐     ┌──────▼──┐     ┌──────▼──────┐
             │ Message │     │ Presence │     │ Notification│
             │ Store   │     │ Service  │     │ Service     │
             │(Cassandra)│    │ (Redis)  │     │ (Push/SMS)  │
             └─────────┘     └─────────┘     └─────────────┘

Deep Dives

WebSocket Connection Management:

Challenge: 50M concurrent connections

Design:
- Connection Service: stateful, holds WebSocket connections
- Each server: ~100K connections (500 servers needed)
- User → server mapping: stored in Redis
  Key: "conn:{user_id}" → Value: "server_id:ws_connection_id"

Message routing:
1. User A sends message to User B
2. Message Service looks up User B's connection server
3. Routes message to that server
4. Server pushes to User B via WebSocket

If User B is offline:
- Store message in DB (undelivered)
- Send push notification
- When B comes online → deliver pending messages

Message Ordering:

Challenge: Messages must appear in order within a conversation

Solution: 
- Message ID = Snowflake (timestamp-based, monotonically increasing)
- Within same conversation, messages are ordered by ID
- Client displays messages sorted by message_id
- If messages arrive out of order (network), client reorders locally

Edge case: Two users send at "same time"
- Server assigns message_id based on arrival order
- Both users see same final order (server is source of truth)

Group Chat:

Small group (< 500):
- Fanout on write: message sent to all members' queues
- Each member's Connection Service delivers via WebSocket
- 500 members × 1 delivery = 500 ops per message (acceptable)

Message storage:
- Partition key: conversation_id
- Sort key: message_id (timestamp-based)
- One write to DB, fanout only for delivery (not storage)

At-Least-Once Delivery:

1. Client sends message → Server acks with message_id
2. Server stores message → delivers to recipient
3. Recipient acks delivery → Server marks as delivered
4. If no ack within timeout → Server retries delivery

Client-side deduplication:
- Each message has unique client_message_id
- If client receives duplicate → ignore (already displayed)
- Server also deduplicates on client_message_id

Bottlenecks & Failure Modes

1. Connection server crash → 100K users disconnected
   → Clients auto-reconnect, routed to new server
   → Pending messages delivered from DB

2. Message ordering across servers
   → Use centralized ID generator (Snowflake) for global ordering

3. Hot group (10K+ members)
   → Limit group size, or use pub/sub model for large groups

4. Presence service accuracy
   → Heartbeat every 30s, mark offline after 2 missed heartbeats
   → Accept ~1 min staleness for online status

Chapter 19：Design Notification System

Problem Statement

設計一個通知系統，支援 push notification、SMS、email，服務 100M+ 用戶。

Clarifying Questions

  • 哪些 channel？（Push, SMS, Email）
  • Real-time 還是可以延遲？（Urgent < 5s, normal < 1 min）
  • 用戶可以設定偏好嗎？（Yes, opt-in/out per channel）
  • 需要 template 嗎？（Yes）
  • Delivery guarantee？（At-least-once, no duplicates）

Requirements

Functional: Send notifications (push/SMS/email), user preferences, templates, priority, history Non-functional: Urgent delivery < 5s, 99.9% delivery rate, no duplicate sends

Estimation

Volume: 100M DAU × 10 notifications/day = 1B notifications/day
QPS: 1B / 86400 ≈ 11,500 QPS (peak: 35K)

High-Level Design

Caller Service → Notification API → Validation + Preference Check
                                          ↓
                                    Priority Router
                                    ↓           ↓
                              Urgent Queue   Normal Queue
                                    ↓           ↓
                              Workers (auto-scaled)
                                    ↓
                    ┌───────────────┼───────────────┐
                    ↓               ↓               ↓
              Push Provider    SMS Provider    Email Provider
              (APNs/FCM)      (Twilio)        (SES/SendGrid)

Deep Dives

Deduplication:

Problem: At-least-once delivery may cause duplicate sends

Solution: Idempotency key per notification
- Key: hash(user_id + event_type + event_id + timestamp_bucket)
- Check Redis before sending: if key exists → skip
- Set key with TTL (24h) after successful send

Example:
event: "order_shipped", order_id: "123", user: "456"
idempotency_key = hash("456:order_shipped:123") 
→ Even if event is published twice, notification sent only once

Rate Limiting per Provider:

APNs: No hard limit but recommends batching
FCM: 600K messages/min per project
Twilio SMS: Varies by number type (1 msg/sec per number)
SES: 50K emails/day (default, can increase)

Implementation:
- Token bucket per provider
- If rate exceeded → queue and retry with backoff
- Monitor provider-specific error codes (429, throttling)

Retry + DLQ:

Retry policy:
- Attempt 1: immediate
- Attempt 2: after 1 min
- Attempt 3: after 5 min
- Attempt 4: after 30 min
- After 4 failures → move to DLQ

DLQ handling:
- Alert on-call if DLQ depth > threshold
- Manual review: is it a bug? provider outage? invalid token?
- Replay after fix

Bottlenecks & Failure Modes

1. Provider outage (APNs down)
   → Queue messages, retry when provider recovers
   → Alert if queue depth grows beyond threshold

2. Duplicate notifications
   → Idempotency key check before every send

3. User preference not loaded (cache miss)
   → Fail-safe: DON'T send (respect user privacy)
   → Better to miss a notification than spam someone who opted out

4. Burst traffic (flash sale announcement to 10M users)
   → Pre-schedule, gradual rollout (10% → 50% → 100%)
   → Prevents provider rate limit and system overload

Chapter 20：Design Search / Typeahead

Problem Statement

設計一個搜尋系統，包含 typeahead（自動完成）功能。

Clarifying Questions

  • 搜尋什麼？（Products for e-commerce）
  • Typeahead 需要多快？（< 100ms）
  • 需要 typo tolerance？（Yes）
  • 需要 personalization？（Nice to have）
  • Scale？（1B products, 10K search QPS）

Requirements

Functional: Full-text search, typeahead suggestions, filters, ranking, typo tolerance Non-functional: Typeahead p99 < 100ms, search p99 < 200ms, fresh index (< 1 min lag)

High-Level Design

Typeahead Path (< 100ms):
Client (keystroke) → API → Trie Service (Redis/in-memory) → Top suggestions

Search Path (< 200ms):
Client (submit) → API → Elasticsearch Cluster → Ranked results
                                ↑
                    Indexing Pipeline (Kafka → Indexer → ES)

Deep Dives

Typeahead with Trie:

Data structure: Trie (prefix tree) with top-K results at each node

Example:
Root
├── "i"
│   ├── "ip" → [iPhone 15, iPad Pro, iPod]
│   │   ├── "iph" → [iPhone 15, iPhone 14, iPhone case]
│   │   └── "ipa" → [iPad Pro, iPad Air, iPad mini]
│   └── "in" → [Intel, Instagram, insurance]
└── "s"
    └── "sa" → [Samsung, Salesforce, sandals]

Each node stores top 10-15 suggestions (pre-computed).
Query "iph" → traverse trie → return pre-stored results → O(length of prefix)

Storage: Redis or in-memory (entire trie fits in ~10GB for 1B products)
Update: Rebuild trie periodically (every hour) or incremental update

Elasticsearch for Full Search:

Index design:
{
  "mappings": {
    "properties": {
      "name": { "type": "text", "analyzer": "standard" },
      "description": { "type": "text" },
      "category": { "type": "keyword" },
      "price": { "type": "float" },
      "brand": { "type": "keyword" },
      "rating": { "type": "float" },
      "sales_count": { "type": "integer" }
    }
  }
}

Ranking formula:
score = text_relevance × 0.4 + popularity × 0.3 + recency × 0.2 + personalization × 0.1

Typo tolerance: Elasticsearch fuzzy query (edit distance 1-2)

Indexing Pipeline:

Product DB → CDC (Debezium) → Kafka → Indexer Service → Elasticsearch

Lag: ~1-5 seconds (near real-time)
Bulk indexing: For initial load or reindex, use Elasticsearch bulk API
Partial update: Only update changed fields (not full document)

Bottlenecks & Failure Modes

1. Typeahead latency spike
   → Local in-memory trie (no network hop), replicated to all servers

2. Elasticsearch cluster overload
   → Read replicas, query caching, limit result window

3. Index corruption
   → Blue-green indexing: build new index, swap alias when ready

4. Hot queries (trending search terms)
   → Query result cache (Redis), TTL 5 min for popular queries

Chapter 21：Design File Storage / Dropbox

Problem Statement

設計一個雲端檔案儲存系統，支援上傳、下載、同步、分享。

Clarifying Questions

  • 最大檔案大小？（10GB）
  • 需要 real-time sync？（Yes, across devices）
  • 需要 version history？（Yes, last 30 versions）
  • 需要 sharing/collaboration？（Yes）
  • Scale？（500M users, 100M DAU）

Requirements

Functional: Upload/download files, sync across devices, sharing, version history, conflict resolution Non-functional: Upload resumable, sync < 30s for small files, 99.99% durability

Estimation

Storage: 500M users × 5GB avg = 2.5 EB (exabytes) — need object storage
Files: 500M users × 200 files avg = 100B file metadata records
Sync events: 100M DAU × 10 file changes/day = 1B sync events/day
Upload bandwidth: Peak 100K concurrent uploads × 1MB/s = 100GB/s

High-Level Design

Client (Desktop/Mobile)
    ↓ (chunked upload)
API Gateway → Upload Service → Object Storage (S3)
                    ↓
            Metadata Service → Metadata DB (PostgreSQL)
                    ↓
            Sync Service → Notification (WebSocket/Long-poll)
                    ↓
            Other devices download changes

Deep Dives

Chunking:

Why chunk large files:
- Resumable upload (only re-upload failed chunks)
- Deduplication (same chunk across files = store once)
- Parallel upload (multiple chunks simultaneously)
- Delta sync (only upload changed chunks)

Chunk size: 4MB (balance between overhead and granularity)
10GB file = 2,500 chunks

Upload flow:
1. Client splits file into 4MB chunks
2. Compute hash (SHA-256) for each chunk
3. Send chunk hashes to server → server returns which chunks already exist
4. Upload only new/changed chunks (deduplication!)
5. Server assembles file metadata (ordered list of chunk hashes)

Deduplication savings:
- Same file uploaded by 100 users → stored only once
- File with 1 line changed → only 1 chunk re-uploaded (not entire file)
- Typical dedup ratio: 30-50% storage savings

Sync Conflict Resolution:

Scenario: User edits file on laptop (offline), also edits on phone
Both devices come online → conflict!

Resolution strategies:
1. Last-write-wins (simple but may lose data)
2. Keep both versions (let user choose) ← Dropbox approach
3. Auto-merge (for text files, like Git)

Dropbox approach:
- Detect conflict (same file, different content, same base version)
- Keep both: "report.docx" + "report (conflicted copy - John's laptop).docx"
- User manually resolves

Implementation:
- Each file has version number
- Edit: version N → version N+1
- If two edits both based on version N → conflict
- Server accepts first, marks second as conflict

Notification Service (Sync):

How does Device B know Device A uploaded a new file?

Option A: Polling (every 30s check for changes)
- Simple but wasteful (most polls return "no changes")
- Acceptable for mobile (battery-friendly intervals)

Option B: Long polling
- Client sends request, server holds until there's a change (or timeout 60s)
- More efficient than polling
- Dropbox uses this

Option C: WebSocket
- Persistent connection, server pushes immediately
- Best latency but more resource-intensive
- Good for desktop client

Hybrid: WebSocket for desktop, long-poll for web, push notification for mobile

Bottlenecks & Failure Modes

1. Large file upload failure midway
   → Chunked upload with resume (only re-upload failed chunks)

2. Storage cost explosion
   → Deduplication, compression, tiered storage (hot/warm/cold)

3. Sync storm (user copies 10,000 files)
   → Rate limit sync events, batch notifications

4. Metadata DB overload
   → Shard by user_id, cache hot metadata in Redis

Chapter 22：Design Video Streaming / YouTube

Problem Statement

設計一個影片串流平台，支援上傳、轉碼、串流播放。

Clarifying Questions

  • 需要 live streaming 嗎？（No, VOD only for MVP）
  • 支援哪些解析度？（360p, 720p, 1080p, 4K）
  • 需要推薦系統嗎？（Basic, not ML-heavy）
  • Scale？（1B MAU, 500M DAU, 500 hours video uploaded/min）

Requirements

Functional: Upload video, transcode, stream (adaptive bitrate), search, recommendations Non-functional: Start playback < 2s, no buffering at stable connection, 99.9% availability

Estimation

Upload: 500 hours/min = 30,000 hours/day
Storage per hour (raw): ~5GB → 150TB raw/day
After transcoding (multiple resolutions): ~3x → 450TB/day
Viewing: 500M DAU × 5 videos/day × 10 min avg = 25B minutes/day
Bandwidth: 25B min × 5Mbps avg = ~1 Pbps peak (CDN handles this)

High-Level Design

Upload Path:
Client → Upload Service → Object Storage (raw)
                              ↓
                    Transcoding Pipeline (async)
                    ↓           ↓           ↓
                  360p        720p        1080p
                    ↓           ↓           ↓
                         CDN (serve to viewers)

View Path:
Client → CDN (edge cache) → Origin Storage
Client uses adaptive bitrate (HLS/DASH) to switch quality

Deep Dives

Transcoding Pipeline:

Steps:
1. Upload raw video to S3
2. Trigger transcoding job (SQS/Step Functions)
3. Split video into segments (10s each)
4. Transcode each segment to multiple resolutions (parallel)
5. Generate manifest file (HLS .m3u8 / DASH .mpd)
6. Upload transcoded segments to CDN origin
7. Update metadata DB: video status = "ready"

Parallel processing:
- 1 hour video = 360 segments (10s each)
- Each segment transcoded independently
- 360 segments × 4 resolutions = 1,440 jobs
- With 100 workers: ~15 minutes total

Tools: FFmpeg, AWS Elastic Transcoder, or custom on GPU instances

Adaptive Bitrate Streaming (ABR):

How it works:
1. Video split into 10s segments, each in multiple qualities
2. Client downloads manifest file (list of segments + qualities)
3. Client measures bandwidth
4. Picks appropriate quality for next segment
5. If bandwidth drops → switch to lower quality (no buffering)
6. If bandwidth improves → switch to higher quality

HLS manifest example:
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p/playlist.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=2400000,RESOLUTION=1280x720
720p/playlist.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
1080p/playlist.m3u8

CDN Strategy:

Hot videos (top 1%): Cached at edge (closest to user)
Warm videos (top 20%): Cached at regional PoPs
Cold videos (long tail): Served from origin

Cache hit rate target: 95%+ for edge
- Top 1% of videos = 80% of views (Zipf distribution)
- These fit easily in CDN edge cache

Pre-warming: When a video goes viral, proactively push to all edges

Bottlenecks & Failure Modes

1. Transcoding backlog (upload spike)
   → Auto-scale transcoding workers, priority queue (paid users first)

2. CDN cache miss for viral video
   → Pre-warm CDN when video trending, origin can handle burst

3. Storage cost
   → Delete low-quality versions of unpopular videos after 90 days
   → Compress with newer codecs (AV1 vs H.264)

4. Video processing failure
   → Retry failed segments, DLQ for persistent failures, notify uploader

Chapter 23：Design Booking System / Ticketmaster

Problem Statement

設計一個訂票/預約系統，處理高並發搶票場景。

Clarifying Questions

  • 什麼類型的 booking？（Concert tickets, like Ticketmaster）
  • 需要選座位嗎？（Yes）
  • 預期並發？（Hot event: 100K+ users competing for 50K tickets）
  • Payment flow？（Reserve → Pay → Confirm）
  • 超賣可以嗎？（Absolutely not）

Requirements

Functional: Browse events, select seats, reserve, pay, confirm booking Non-functional: No overselling, handle 100K concurrent users, reservation timeout (10 min)

Estimation

Hot event: 100K users in first minute
Seat selection QPS: 100K / 60 ≈ 1,700 QPS (peak: 5K)
Payment QPS: Much lower (only successful reservations)
Total events: 100K events/year, 50K seats avg = 5B total seats

High-Level Design

Client → API Gateway (rate limit) → Booking Service
                                         ↓
                                    Inventory Service (seat availability)
                                         ↓
                                    Payment Service
                                         ↓
                                    Confirmation + Notification

Deep Dives

Preventing Overselling (核心挑戰):

Problem: 100 users simultaneously try to book the same seat

Option A: Pessimistic Locking (SELECT FOR UPDATE)
- Lock the seat row when user selects it
- Other users get "seat unavailable"
- Pros: Simple, guaranteed no oversell
- Cons: Lock contention, reduced throughput

Option B: Optimistic Locking (version number)
- Read seat with version number
- UPDATE seats SET status='reserved', version=version+1 
  WHERE id=? AND version=? AND status='available'
- If 0 rows affected → someone else got it → retry with different seat
- Pros: Better throughput (no blocking)
- Cons: More retries under high contention

Option C: Redis atomic operation
- SETNX (set if not exists) on seat key
- First one wins, others get rejection
- Pros: Extremely fast, no DB lock
- Cons: Need to sync with DB

My choice: Option C (Redis) + Option A (DB) as two-phase:
1. Redis SETNX for instant feedback (< 5ms)
2. Async confirm in DB with pessimistic lock
3. If DB fails → release Redis key

Reservation Timeout:

Problem: User reserves seat but never pays → seat locked forever

Solution: Reservation expires after 10 minutes
- Reserve: set seat status = 'reserved', set TTL in Redis
- After 10 min: Redis key expires → seat becomes available again
- If payment completes before timeout → mark as 'sold' (permanent)

Implementation:
1. SETNX seat:event123:A15 user_456 EX 600  (10 min TTL)
2. User has 10 min to complete payment
3. Payment success → UPDATE DB, DELETE Redis key (or let it expire)
4. Payment timeout → Redis key expires → seat available again

Edge case: Payment completes at exactly timeout moment
→ Use distributed lock with fencing token
→ Payment service checks if reservation still valid before charging

Handling Flash Sales (搶票):

100K users, 50K tickets, first minute:

1. Virtual waiting room:
   - Users enter queue, assigned random position
   - Release users in batches (1000 at a time)
   - Prevents thundering herd on booking service

2. Rate limiting:
   - Per-user: 1 booking attempt per 5 seconds
   - Global: 5000 concurrent booking processes

3. Pre-computed inventory:
   - Load all seat availability into Redis before event opens
   - All checks against Redis (not DB)
   - DB is updated async (source of truth, but not in hot path)

4. Graceful degradation:
   - If system overloaded → show "high demand, please wait"
   - Don't crash, don't oversell

Bottlenecks & Failure Modes

1. Overselling (worst case)
   → Redis atomic ops + DB constraint (belt and suspenders)
   → Reconciliation job every minute

2. Payment service timeout
   → Reservation timeout releases seat
   → User can retry (new reservation)

3. Hot event DB contention
   → Shard by event_id (each event on different shard)
   → Redis handles hot path, DB is async

4. Abandoned reservations filling up inventory
   → 10 min TTL, aggressive cleanup
   → Show "X seats being held" to manage user expectations

Chapter 24：Design Uber / Location System

Problem Statement

設計 Uber 的核心系統：rider 叫車、driver 接單、即時位置追蹤。

Clarifying Questions

  • 只做 ride-matching 還是整個 Uber？（Core: matching + location）
  • 需要 ETA 嗎？（Yes, basic）
  • Scale？（10M concurrent drivers, 1M rides/hour）
  • Location update 頻率？（Driver: every 3s, Rider: on demand）

Requirements

Functional: Request ride, match driver, real-time location tracking, ETA Non-functional: Match < 30s, location update < 1s delivery, 99.9% availability

Estimation

Driver location updates: 10M drivers × 1 update/3s = 3.3M updates/sec
Ride requests: 1M rides/hour = 280 rides/sec
Nearby driver queries: 280/sec (one per ride request)

High-Level Design

Rider App → Ride Service → Matching Service → Driver App
                               ↓
                    Location Service (driver positions)
                               ↓
                    Geospatial Index (find nearby drivers)

Deep Dives

Geospatial Indexing:

How to efficiently find "drivers within 3km of rider"?

Option A: Geohash
- Divide world into grid cells, each with a hash string
- Nearby locations share common prefix
- "9q8yyk" and "9q8yym" are adjacent cells
- Query: find all drivers in same cell + adjacent cells
- Store in Redis: GEOADD drivers longitude latitude driver_id
- Query: GEORADIUS drivers lng lat 3 km

Option B: QuadTree
- Recursively divide space into 4 quadrants
- Subdivide until each cell has < N drivers
- Dense areas (Manhattan) → more subdivisions
- Sparse areas (rural) → fewer subdivisions

Option C: H3 (Uber's actual choice)
- Hexagonal grid system
- Better than square grids (uniform distance to neighbors)
- Multiple resolution levels

My choice: Geohash with Redis GEORADIUS
- Simple, Redis handles it natively
- Performance: O(N) where N = drivers in radius (typically < 100)
- Update: GEOADD on every location update (3.3M/sec → Redis handles this)

Driver Matching:

Algorithm:
1. Rider requests ride → get rider location
2. Query nearby available drivers (radius 3km, expand if none)
3. Rank drivers by: distance, ETA, rating, acceptance rate
4. Send request to top driver
5. Driver has 15s to accept
6. If declined/timeout → send to next driver
7. If accepted → create trip, notify rider

Optimization:
- Don't query all drivers in 3km (could be 1000+)
- Use geohash precision to limit initial set
- Pre-filter: only "available" drivers (not on trip, not offline)
- Supply-demand balancing: in high-demand areas, expand radius

Real-time Location Tracking:

During trip, rider sees driver's live location:

Flow:
1. Driver app sends GPS every 3 seconds
2. Location Service updates Redis GEOADD
3. Location Service publishes to rider's WebSocket channel
4. Rider app renders updated position on map

Optimization:
- Don't send every update to rider (3s might be too frequent for rendering)
- Client-side interpolation: smooth movement between updates
- Batch updates: send every 5s to reduce WebSocket messages

ETA calculation:
- Simple: distance / average_speed
- Better: Use road network graph + current traffic
- Uber uses: ML model trained on historical trip data

Bottlenecks & Failure Modes

1. Location update storm (3.3M/sec)
   → Redis Cluster (sharded by geohash region)
   → Each shard handles one geographic area

2. No drivers available
   → Expand search radius, surge pricing to attract drivers
   → Show "no drivers available, try again in X minutes"

3. Driver app loses connection
   → Mark as unavailable after 30s no heartbeat
   → Don't assign new rides to disconnected drivers

4. Hot city (Manhattan at rush hour)
   → Dedicated shard for hot areas
   → Pre-computed supply/demand heatmap for matching optimization

1. 這是什麼？

3. 常見 Tradeoff 決策

SQL vs NoSQL

Decision: Primary data store for user orders

Option A: PostgreSQL
  Pros: ACID, complex queries, mature tooling
  Cons: Harder to scale writes, schema migration pain
  Failure mode: Single primary bottleneck at high write QPS
  When to use: < 10K write QPS, need transactions, complex queries

Option B: DynamoDB
  Pros: Unlimited write scale, single-digit ms, managed
  Cons: No JOIN, limited query patterns, vendor lock-in
  Failure mode: Hot partition if bad key design
  When to use: > 10K write QPS, known access patterns, AWS ecosystem

My decision: PostgreSQL. Our write QPS is ~2K (well within limits),
we need transactions for payment, and we need flexible queries for
the admin dashboard. We'll revisit if writes exceed 10K QPS.

Push vs Pull

Decision: How to deliver feed updates to users

Option A: Push (Fanout on Write)
  Pros: Read is O(1), instant feed load
  Cons: Write amplification, celebrity problem
  When to use: Most users have < 1K followers

Option B: Pull (Fanout on Read)
  Pros: Simple write, no amplification
  Cons: Slow read (merge N sources), high read latency
  When to use: Users follow few accounts, or all are celebrities

Option C: Hybrid
  Pros: Best of both worlds
  Cons: More complex, two code paths
  When to use: Mix of normal and celebrity users (most real systems)

My decision: Hybrid. Push for users with < 10K followers (99% of users),
pull for celebrities. This bounds write amplification while keeping
read latency low for the vast majority.

Consistency vs Availability

Decision: What happens during a network partition?

Option A: Choose Consistency (CP)
  Pros: No stale/incorrect data
  Cons: Some requests fail during partition
  When to use: Financial data, inventory, authentication

Option B: Choose Availability (AP)
  Pros: System always responds
  Cons: May serve stale data
  When to use: Social feed, recommendations, analytics

My decision: Different for different data:
- Payment balance: CP (incorrect balance = money loss)
- News feed: AP (stale feed for 2s = acceptable)
- User profile: Read-after-write (user sees own changes immediately)

Sync vs Async

Decision: How to process post-order actions (notification, analytics, recommendation update)

Option A: Synchronous (in same request)
  Pros: Simple, immediate consistency
  Cons: Slow response (user waits for all actions), coupling
  Failure mode: One slow service blocks entire request

Option B: Asynchronous (via message queue)
  Pros: Fast response, decoupled, resilient
  Cons: Eventual consistency, harder to debug
  Failure mode: Message lost or delayed

My decision: Async for non-critical actions. The order confirmation
response should return in < 200ms. Notification, analytics, and
recommendation updates happen async via Kafka. The user doesn't
need to wait for these.

4. 面試中的 Tradeoff 話術

"I see two main approaches here. Let me walk through the tradeoffs:

[Describe Option A and B]

Given our requirement for [specific constraint], I'd go with [choice].
The main tradeoff I'm accepting is [downside], which is acceptable 
because [reasoning].

If our requirements change — specifically if [condition] — I'd

5. Staff-Level Insight

Staff engineers don't just pick the "better" option.
They:
1. Identify that a decision point exists (many people don't even notice)
2. Enumerate options (including "do nothing" and "defer decision")
3. Evaluate against CURRENT requirements (not hypothetical future)
4. Make the decision explicit and documented
5. Define criteria for revisiting the decision
6. Communicate the tradeoff to stakeholders

The worst decision is an implicit one — where the team drifts into
a choice without realizing they made one.

Chapter 26：Failure Mode Playbook

常見問題與 Staff-Level 解法

1. Hot Shard 怎辦？

Detection: One shard's CPU/latency significantly higher than others
Root cause: Uneven data distribution or access pattern

Immediate mitigation:
- Add read replicas for the hot shard
- Cache hot keys aggressively
- Rate limit requests to hot shard

Long-term fix:
- Re-shard with better partition key
- Split hot shard into 2
- Use consistent hashing with virtual nodes
- For celebrity problem: dedicated shard or hybrid fanout

Prevention:
- Monitor per-shard metrics (not just aggregate)
- Alert when any shard > 2x average load
- Design partition key for uniform distribution

2. One Region Down 怎辦？

Detection: Health check from other regions fails, or AWS status page
Impact: All users in that region lose service

Immediate response:
- DNS failover to healthy region (Route 53 health check)
- Failover time: 30s-5min (depending on DNS TTL)

Data handling:
- If active-active: Other region already has data, minimal impact
- If active-passive: Promote standby, accept RPO data loss
- If no DR: Extended outage until region recovers

Recovery:
- Region comes back → don't immediately shift traffic back
- Verify data consistency first
- Gradual traffic shift (10% → 50% → 100%)

Prevention:
- Multi-region active-active for critical services
- Regular DR drills (quarterly)
- Chaos engineering (simulate region failure)

3. Cache Avalanche 怎辦？

Detection: Cache hit rate drops to 0%, DB CPU spikes to 100%
Root cause: Cache cluster failure or mass TTL expiration

Immediate mitigation:
- Circuit breaker: limit DB connections
- Serve stale data if available (extend TTL on read)
- Graceful degradation: disable non-critical features

Recovery:
- Bring cache back online
- Warm cache gradually (don't let all traffic hit DB)
- Use cache warming script for hot data

Prevention:
- Jittered TTL (random offset prevents mass expiration)
- Redis Cluster with replicas (survive node failure)
- Local cache as L1 (survives Redis outage for hot data)
- Never let cache be the only copy of computed data

4. Queue Backlog 怎辦？

Detection: Consumer lag growing, queue depth increasing
Root cause: Consumer too slow, or sudden traffic spike

Immediate mitigation:
- Auto-scale consumers (if possible)
- Increase consumer parallelism (more threads/instances)
- If non-critical: temporarily drop low-priority messages

Investigation:
- Is consumer slow? (check processing time per message)
- Is producer too fast? (check incoming rate)
- Is there a poison message? (one message causing crash/retry loop)

Recovery:
- Fix consumer bottleneck (DB query? external API? bug?)
- Process backlog (may take hours for large backlogs)
- Consider: is old data still relevant? (maybe skip messages > 1h old)

Prevention:
- Auto-scaling based on queue depth
- DLQ for poison messages (don't let them block the queue)
- Backpressure at producer (rate limit if queue too deep)
- Monitor consumer lag with alerting

5. DB Migration 怎辦？

Challenge: Change schema on a table with 1B rows without downtime

Strategy: Expand-Contract pattern

Phase 1 - Expand:
- Add new column (nullable, no default)
- Deploy code that writes to BOTH old and new column
- Backfill new column for existing rows (batch job)

Phase 2 - Migrate:
- Deploy code that reads from new column
- Verify correctness (compare old vs new)

Phase 3 - Contract:
- Deploy code that only writes to new column
- Drop old column (after verification period)

Timeline: Days to weeks (not minutes)

Tools:
- PostgreSQL: pg_repack (online table rewrite)
- MySQL: pt-online-schema-change, gh-ost
- DynamoDB: No schema migration needed (schemaless)

Risk mitigation:
- Feature flag: can switch between old/new at any time
- Rollback plan at each phase
- Monitor error rates during migration

6. p99 Latency Spike 怎辦？

Detection: p99 > SLO threshold for > 5 minutes
Impact: 1% of users experiencing very slow responses

Investigation playbook:
1. Which service? (distributed tracing)
2. Which endpoint? (per-endpoint metrics)
3. When did it start? (correlate with deployments, traffic changes)
4. What's different about slow requests? (specific user? specific data?)

Common causes and fixes:
- GC pause → Tune GC, use low-latency GC (ZGC)
- Hot key → Replicate key, add local cache
- DB lock contention → Optimize transaction scope, read replica
- Noisy neighbor → Resource isolation, dedicated instances
- Cache miss storm → Fix TTL, add stampede prevention
- Slow dependency → Circuit breaker, timeout, fallback

Prevention:
- Latency-based alerting (not just average, but p99)
- Load testing with realistic traffic patterns
- Canary deployments (catch regressions early)
- Hedged requests for critical paths

7. Data Corruption 怎辦？

Detection: Data validation checks fail, user reports incorrect data
Impact: Potentially catastrophic (wrong balances, lost orders)

Immediate response:
- STOP the source of corruption (disable the buggy service/job)
- Assess blast radius (how many records affected?)
- Communicate to stakeholders

Recovery:
- Point-in-time recovery (restore DB to before corruption)
- Selective fix (if blast radius is small, fix individual records)
- Replay events (if event-sourced, replay from last good state)

Prevention:
- Immutable audit log (append-only, never delete)
- Data validation at write time (constraints, triggers)
- Reconciliation jobs (compare data across systems)
- Checksums on critical data
- Backup verification (regularly test restore)

8. Duplicate Messages 怎辦？

Detection: Users report duplicate notifications, double charges
Root cause: At-least-once delivery + consumer crash before ack

Immediate fix:
- Deduplicate at consumer level (idempotency key)
- For already-sent duplicates: apologize, reverse if needed

Implementation:
- Every message has unique message_id
- Consumer checks: "Have I processed this message_id before?"
- If yes → skip
- If no → process + record message_id (with TTL)

Storage for dedup:
- Redis SET with TTL (fast, but limited retention)
- DB unique constraint (durable, but slower)
- Bloom filter (probabilistic, space-efficient, may have false positives)

Prevention:
- Idempotent consumers (design operations to be safe to repeat)
- Exactly-once semantics where possible (Kafka transactions)
- Deduplication window (24h is usually sufficient)

Chapter 27：面試回答範本

同一題目的 L4 / L5 / L6 回答對比

題目：Design a Rate Limiter

L4 (Junior) Answer:

"We can use a token bucket algorithm. Each user has a bucket with 
tokens. Each request consumes a token. Tokens refill at a fixed rate.
If no tokens left, reject the request with 429.

We'll store the token count in Redis. The API server checks Redis 
before processing each request."

評價：正確但淺。只講了 algorithm，沒有 distributed 考量、
failure handling、或 production concerns。

L5 (Senior) Answer:

"Let me first clarify requirements: What's our scale? What dimensions 
do we rate limit on? What's the latency budget?

[After clarification]

I'll use a token bucket algorithm implemented with Redis + Lua script 
for atomicity. Here's why:

1. Algorithm choice: Token bucket over sliding window because it 
   allows controlled burst (better UX for legitimate users).

2. Implementation: Redis Lua script ensures check-and-update is atomic.
   No race condition even with multiple API servers.

3. Multi-dimensional: 
   - Per-user: 100 req/min (prevent abuse)
   - Per-IP: 1000 req/min (prevent DDoS)
   - Per-endpoint: Sensitive endpoints have stricter limits

4. Response: 429 with headers (X-RateLimit-Remaining, Retry-After)
   so clients can back off gracefully.

5. Failure mode: If Redis is down, fail-open for general API 
   (allow all) but fail-close for auth endpoints (deny all).

6. Monitoring: Track rate limit hits per user, alert on anomalies 
   that might indicate an attack or a buggy client."

評價：Good depth. Covers distributed concerns, failure handling, 
and operational aspects. Clear tradeoff reasoning.

L6 (Staff) Answer:

"Before diving into implementation, let me think about this at a 
system level.

[Requirements + Estimation as above]

Architecture decision: Where does rate limiting live?

Option A: At API Gateway (centralized)
- Pros: Single enforcement point, consistent across all services
- Cons: Gateway becomes bottleneck, can't do service-specific limits

Option B: At each service (distributed)
- Pros: Service-specific logic, no single bottleneck
- Cons: Inconsistent implementation, harder to manage

Option C: Sidecar/Service Mesh (Envoy)
- Pros: Transparent to services, consistent, no code changes
- Cons: Operational complexity of service mesh

My choice: Layered approach.
- Layer 1: CDN/WAF for IP-based DDoS protection (Cloudflare/AWS Shield)
- Layer 2: API Gateway for per-user/per-key limits (centralized Redis)
- Layer 3: Service-level for resource-specific limits (local + sync)

Advanced considerations:

1. Multi-region consistency:
   - Global rate limit across regions? Or per-region?
   - If global: need cross-region Redis sync (adds latency)
   - My choice: Per-region with slightly higher total limit
     (accept 2x burst during region failover)

2. Tenant isolation:
   - In multi-tenant system, one tenant shouldn't affect others
   - Separate rate limit pools per tenant
   - "Noisy neighbor" detection and automatic throttling

3. Adaptive rate limiting:
   - When system is healthy: generous limits
   - When system is degraded: automatically tighten limits
   - Based on: error rate, latency, queue depth
   - This protects the system during partial outages

4. Abuse modeling:
   - Rate limiting alone doesn't stop sophisticated abuse
   - Combine with: behavioral analysis, CAPTCHA, account reputation
   - ML model for anomaly detection (unusual patterns)

5. Observability:
   - Dashboard: rate limit hits by user, endpoint, time
   - Alert: sudden spike in 429s (might be a bug, not abuse)
   - Audit: who changed rate limit configs and when

6. Graceful degradation:
   - Instead of hard reject at limit: queue with lower priority
   - Or: serve cached/degraded response instead of 429
   - Better UX than a wall of errors

Failure modes:
- Redis cluster failure: Fail-open with local in-memory fallback
  (each server allows burst, sync when Redis recovers)
- Config propagation delay: Use eventual consistency for config
  changes (new limits take effect within 30s across all servers)
- Clock skew: Use Redis server time (EVAL), not local time

Revisit criteria:
- If we move to service mesh → migrate to Envoy rate limiting
- If we need global consistency → evaluate Redis Global Datastore
- If abuse patterns change → add ML-based adaptive limits"

評價：This is Staff-level. Thinks about the problem at system level,
considers organizational impact, multi-region, tenant isolation,
adaptive behavior, and defines criteria for revisiting decisions.

從 L5 升級到 L6 的關鍵思維

1. 從 "How to build it" → "How to evolve it"
   L5: 設計一個能工作的系統
   L6: 設計一個能隨需求變化而演進的系統

2. 從 "Technical solution" → "System-level thinking"
   L5: 選 Redis 因為它快
   L6: 選 Redis 但考慮 failure mode、multi-region、operational cost

3. 從 "Single service" → "Platform thinking"
   L5: 為這個 service 實現 rate limiting
   L6: 建立 rate limiting 作為 platform capability，所有 service 受益

4. 從 "Happy path" → "Failure-first design"
   L5: 系統正常時怎麼工作
   L6: 系統部分故障時怎麼 degrade gracefully

5. 從 "Current requirements" → "Future-proofing with boundaries"
   L5: 滿足當前需求
   L6: 滿足當前需求 + 定義清楚的擴展點 + 知道什麼時候該重新設計

結語

System Design Interview 的本質不是考你記住了多少架構圖，
而是考你能不能像一個 Senior/Staff Engineer 一樣思考：

1. 面對模糊的問題，能問出正確的問題
2. 面對多個選項，能做出合理的 tradeoff
3. 面對規模挑戰，能設計可擴展的方案
4. 面對故障場景，能設計容錯的系統
5. 面對面試官，能清楚地溝通你的思考過程

記住：沒有完美的設計，只有適合當前 context 的設計。
你的工作不是畫出最複雜的架構圖，
而是展示你如何在 constraints 下做出最好的決策。
