# 第 1 章　怎麼讀這本書：SAA／SAP 考什麼、怎麼解題

> [!abstract] 本章地圖
> **你會學到**：
> - 說出 SAA-C03 與 SAP-C02 的題數、時間、計分方式與及格分數，知道考場上會遇到哪些題型
> - 看懂兩張證照的四個 domain 與 task 清單，知道本書每一章對應到哪些考點
> - 分辨「單一 workload 的架構題」（SAA）與「組織層級的架構題」（SAP）有什麼不同
> - 用固定的四步驟讀題：先圈限制與最佳化目標，再刪去不符合的選項，最後比較剩下的選項
> - 依自己的背景挑一份讀書計畫（30 天 SAA、45 天 SAP、12 週零背景）
>
> **前置知識**：無
> **考試比重**：本章不對應單一考點，但所有題目都會用到這裡的讀題方法

## 1.1 故事：一位工程師與一家旅遊新創

阿哲是一位寫了三年後端程式的工程師。他熟悉 Python 與 SQL，會用 Git，部署則一直是「把程式丟給維運同事」。某天他加入一家剛起步的線上旅遊訂房新創 **Wanderly**，公司只有十幾個人，沒有專職維運，執行長的要求很直接：「下個月網站要上線，所有東西都放 AWS，你負責。」

阿哲打開 AWS Console，看到兩百多個服務名稱，第一個問題就卡住了：資料庫要用 RDS、Aurora 還是 DynamoDB？機器要開在哪個 Region？網站要不要放 CloudFront？每個選擇背後都有成本、安全與可用性的取捨，而他連那些名詞是什麼都不太確定。

技術顧問建議他準備 **AWS Certified Solutions Architect – Associate（SAA-C03）**：這張證照的考試範圍幾乎就是「在 AWS 上設計一個安全、可靠、效能好又省錢的系統」需要的知識地圖。準備考試的過程，會逼他把每個服務「為什麼存在、什麼時候用、什麼時候不用」想清楚。等 Wanderly 長大成多帳號、要併購另一家公司時，再挑戰 **Professional（SAP-C02）**。

這本書就是為阿哲這樣的人寫的：會寫程式，但沒有雲端或網路維運背景。本章先回答三個問題：考試長什麼樣子？題目要怎麼讀？這本書要怎麼讀？

## 1.2 兩張證照的考試形式

先把考試的硬規格講清楚，因為它會直接影響你的作答策略。

| 項目 | SAA-C03（Associate） | SAP-C02（Professional） |
|---|---|---|
| 題數 | 65 題 | 75 題 |
| 其中計分題 | 50 題 | 65 題 |
| 其中不計分題 | 15 題 | 10 題 |
| 時間 | 130 分鐘 | 180 分鐘 |
| 分數量表 | 100–1000 | 100–1000 |
| 及格分數 | 720 | 750 |
| 題型 | 單選、多選 | 單選、多選 |
| 答錯是否倒扣 | 否 | 否 |
| 先決條件 | 無 | 無（不必先考 SAA） |

以上數字取自 AWS 官方 exam guide 與證照頁面：官方 exam guide 寫明 SAA-C03 有 50 題計分、15 題不計分，SAP-C02 有 65 題計分、10 題不計分；考試時間則列在各證照的官方頁面。

> [!warning] SAP 改版提醒（截至 2026 年 10 月）
> AWS 已公告 SAP-C02 將由 **SAP-C03** 取代：SAP-C03 自 2026 年 10 月 27 日開放報名，SAP-C02 的最後應考日是 2026 年 11 月 17 日。截至本書撰寫時，AWS 尚未公布 SAP-C03 的 exam guide，因此本書的 SAP 題數、domain 與 task 都以 SAP-C02 為準。若你在 SAP-C02 停考後才應考，請先到官方證照頁面確認 SAP-C03 的題數、時間與 domain 比重；本書的架構知識仍然適用，但比重與 task 編號可能不同。

幾個新手常誤解的地方：

**不計分題（unscored questions）** 是 AWS 用來試驗新題目的題目，混在正式題目中，**你無法分辨哪一題不計分**。所以不要因為某題特別怪而放棄它，每一題都要當成計分題作答。SAP-C02 的 exam guide 另外說明，生成式 AI 的安全與治理等「新興主題」可能以不計分的試驗題出現，遇到時一樣正常作答即可。

**分數量表（scaled score）** 不是「答對百分比」。AWS 會依題目難度把原始成績換算成 100–1000 分，所以 720 分不等於答對 72%。AWS 用換算分數，是為了讓難度略有不同的多套試卷可以公平比較。考試採用**補償式計分（compensatory scoring）**：只看總分是否達標，不要求每個 domain 都及格。成績單可能附上各 domain 的表現等級，方便你知道哪裡需要加強；官方也提醒這只是大致參考，不要過度解讀。

**題型只有兩種**。**單選題（multiple choice）** 有一個正確答案和三個干擾選項；**多選題（multiple response）** 會在題目中明確寫出要選幾個（例如「Choose two」），官方定義是「五個或更多選項中有兩個或以上正確」，必須全部選對才得分，沒有部分給分。

**沒有倒扣**：官方規定未作答的題目一律算錯，猜錯也不會扣分，所以每題都一定要作答。時間快到時，沒把握的題目也要至少選一個答案。

> [!note] 報名與應考的實務細節
> 兩張考試都可以選擇 Pearson VUE 考場或線上監考。英文不是母語的考生，若以英文應考，可以申請「ESL +30」延長 30 分鐘。這項申請要在 AWS Certification 帳號中、在**報名考試之前**提出；只要申請一次，之後所有考試報名都適用。官方說明這項延長是針對「以英文應考」的情況，選擇中文等其他語言應考時不要預期有額外時間。證照效期為三年，到期前可以通過最新版考試來重新認證。報名費、可選語言與政策會調整，報名前請以 AWS Certification 官方頁面為準：[SAA-C03 考試指南](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-associate-03/solutions-architect-associate-03.html)、[SAP-C02 考試指南](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-professional-02/solutions-architect-professional-02.html)。

### 時間預算

把總時間除以題數，就得到每題的平均預算：

- SAA：130 分鐘 ÷ 65 題 ≈ **每題 2 分鐘**。
- SAP：180 分鐘 ÷ 75 題 ≈ **每題 2.4 分鐘**，但 SAP 的題幹常常長達一整段，加上四個選項都是兩三行的完整方案，實際閱讀量是 SAA 的兩到三倍。

SAA 的時間通常夠用，難點在知識是否精確；SAP 的難點常常是**時間**，讀題速度和刪去法的熟練度會直接決定成績。1.6 節會講時間管理的具體做法。

## 1.4 兩張證照差在哪裡

很多人以為 SAP 只是「更多服務、更難的細節」。實際上兩者問的是不同層級的問題。

先把前言出現過的那個詞說清楚，因為後面每一章都會用到：**workload（工作負載）** 指為了完成某項業務而一起運作的一組資源與程式，例如「訂房網站加上它的資料庫」就是一個 workload。一個 AWS 帳號裡可以有很多個 workload，它們各自有自己的可用性、安全與成本要求。

**SAA 的題目通常圍繞一個 workload**：一個網站、一條資料管線、一個 API。情境三到五句，限制一兩個，例如「要撐過 AZ 故障」「要最省錢」。考的是你是否知道正確的服務與設定，例如 RDS Multi-AZ 和 read replica 的差別、S3 哪個儲存類別適合每季讀一次的資料。

**SAP 的題目圍繞一個組織**：五十個帳號、兩個資料中心、一家剛併購的公司、一個已經上線三年但問題不斷的系統。情境常常有五到八個限制同時存在，例如「既有的 Active Directory 不能更換」「遷移必須在六個月內完成」「法規要求日誌不可竄改」「營運團隊只有三個人」。四個選項往往**都能用**，差別在於哪一個同時滿足所有限制，而且營運負擔最低。

| 面向 | SAA-C03 | SAP-C02 |
|---|---|---|
| 範圍 | 單一 workload、單一或少數帳號 | 整個組織、多帳號、多 Region、hybrid |
| 情境長度 | 3–5 句 | 一整段，常含現況描述與多個限制 |
| 選項 | 常有一兩個明顯錯誤 | 四個都技術可行，差在細節與取捨 |
| 核心能力 | 知道「什麼服務做什麼」 | 知道「在這些限制下哪個組合最好」 |
| 典型主題 | Multi-AZ、Auto Scaling、S3 storage class、IAM role | Organizations／SCP、Transit Gateway、遷移策略、DR 演進、成本治理 |
| 時間壓力 | 中等 | 高 |

所以本書每一章的結構都是先打 SAA 的基礎，再用「SAP 加深」一節延伸到組織層級。先讀懂 SAA 的部分，SAP 的部分才有地基。

## 1.5 怎麼讀題：四步驟解題法

AWS 的情境題有固定的結構。學會拆解這個結構，比多背十個服務限制更能提高分數。

### 一道題目的解剖

```text
┌──────────────────────────────────────────────────────────────┐
│ ① 背景：一家公司在做什麼、現在的架構長什麼樣子               │
│ ② 問題或新需求：發生了什麼事、要新增什麼功能                 │
│ ③ 限制（硬條件）：必須／不得／不能修改程式／30 天內……        │
│ ④ 最佳化目標：MOST cost-effective / LEAST operational        │
│              overhead / MOST secure / highest availability   │
├──────────────────────────────────────────────────────────────┤
│ ⑤ 問句：Which solution will meet these requirements …？      │
├──────────────────────────────────────────────────────────────┤
│ ⑥ 四個（或更多）選項                                         │
└──────────────────────────────────────────────────────────────┘
```

① 背景告訴你現況，例如「應用程式跑在一台 EC2 上」。② 是題目真正要解的問題。③ 是**一票否決**的條件：違反任何一個，選項直接出局。④ 是**決勝**的條件：所有符合硬條件的選項，用它來比較誰最好。⑤ 問句常常重複④，或加上「選兩項」。⑥ 選項裡有正解，也有刻意設計的干擾項。

### 四步驟

**步驟 1：先讀問句與最後一句。** 問句通常在最後，裡面會有最佳化目標。先知道「要比什麼」，再讀前面的情境，讀的時候才知道該注意哪些細節。

**步驟 2：圈出硬條件與最佳化目標。** 在腦中（或考場提供的白板）列出：必須滿足的條件有哪些？要最佳化的是哪一個？例如「不能修改應用程式」「資料必須加密」「最少營運負擔」。

**步驟 3：刪去違反硬條件的選項。** 一個一個檢查，只要違反任何一個硬條件就刪掉。這一步通常能刪掉一到兩個。常見的刪除理由有：功能做不到（例如用 SNS 保存訊息等消費者稍後處理）、違反限制（例如題目說不能改程式，選項卻要改寫成 Lambda）、引入單點故障、把資料暴露在 Internet。

**步驟 4：用最佳化目標比較剩下的選項。** 剩下的選項都「能用」，這時只看最佳化目標。要求最少營運負擔，就選受管服務多、自己寫的程式少的那個；要求成本最低，就選付費元件最少、計價模型最適合的那個。

> [!tip] 考試提示：「能用」不等於「正確」
> AWS 的題目幾乎不會出現「只有一個選項技術上可行」的情況。錯誤選項通常也能運作，只是比正解多花錢、多維運、少一點可用性，或違反某一個你沒注意到的限制。所以讀選項時要問的是「它違反了哪個條件？」，而不是「它能不能動？」。

### 最佳化目標的關鍵字

下表是最常出現的關鍵字，以及它們通常代表的方向。後面每一章的「考試這樣考」都會再針對該章主題補充。

| 題目關鍵字 | 代表的意思 | 常見的正解方向 |
|---|---|---|
| LEAST operational overhead／least management effort | 自己要管的東西越少越好 | 受管服務、serverless、AWS 原生功能，而不是自建 EC2 加腳本 |
| MOST cost-effective／lowest cost | 滿足需求的前提下最便宜 | 合適的儲存類別、Spot／Savings Plans、關掉不需要的資源、避免 NAT 或跨 Region 傳輸 |
| highly available | 單一元件或 AZ 故障時服務不中斷 | 跨至少兩個 AZ、Load Balancer + Auto Scaling、Multi-AZ 資料庫 |
| fault tolerant | 故障時完全不中斷、不掉資料 | 比 highly available 更嚴格：多副本同時運作、資料同步複寫 |
| durable／must not lose data | 資料不能遺失 | S3、佇列先保存再處理、同步複寫、備份 |
| decouple／loosely coupled | 元件之間不要互相等待 | SQS、SNS、EventBridge |
| real-time／near real-time | 秒級或更短的處理延遲 | Kinesis、串流處理；near real-time 常指 Data Firehose 的緩衝延遲 |
| without changing application code | 不能改程式 | 基礎設施層的做法：DNS、Load Balancer、儲存掛載、受管服務的設定 |
| securely／least privilege | 權限最小化、不暴露 | IAM role（而非存取金鑰）、private subnet、VPC endpoint、加密 |
| global users／low latency worldwide | 使用者分布全球 | CloudFront、Global Accelerator、多 Region |
| as soon as possible／in the shortest time | 時程優先 | 不需要重新設計的做法，例如 rehost 而非 refactor |
| unpredictable／spiky traffic | 流量難以預測 | Auto Scaling、serverless、on-demand 計價模式 |

### 刪去法的四個常見訊號

讀多了題目，你會發現錯誤選項有幾種固定的「味道」：

1. **自己造輪子**：「在 EC2 上安裝開源軟體並用 cron 腳本……」。當題目要求最少營運負擔，而 AWS 有現成的受管服務時，這種選項通常是錯的。
2. **過度設計**：題目只要求跨 AZ 高可用，選項卻搬出多 Region active-active。它能用，但更貴、更複雜，不是「最」適合的方案。
3. **用錯工具**：用 CloudFront 解決資料庫寫入瓶頸、用 SNS 當持久佇列。這類選項聽起來相關，但機制根本對不上需求。
4. **安全捷徑**：把存取金鑰寫進程式、把 bucket 設為公開、把 security group 開成 `0.0.0.0/0`。即使題目沒有明說安全需求，這類選項幾乎一定是錯的。

> [!warning] 常見誤解
> 「選項越長、用的服務越多，越可能是正解。」剛好相反：在符合所有條件的前提下，**最簡單**的方案通常就是正解。SAP 的正解選項可能很長，但那是因為題目的限制很多，不是因為長本身是優點。

## 1.6 時間管理與考場策略

### 兩輪作答

考試介面允許你把題目標記為「稍後檢查（flag for review）」，最後還有一個總覽頁可以跳回任何題目。建議用兩輪的方式作答：

- **第一輪**：每題都要作答。有把握的直接作答；猶豫超過兩分鐘的，先選一個最可能的答案並標記，然後繼續下一題。不要卡在任何一題上，後面的題目可能更簡單。
- **第二輪**：回頭只看標記的題目。這時你已經沒有「後面還有很多題」的壓力，而且後面的題目有時會提醒你某個服務的特性。

### 檢查時間點

| 考試 | 第一輪目標 | 檢查點 |
|---|---|---|
| SAA（130 分鐘） | 約 100 分鐘內完成 65 題（每題約 1.5 分鐘） | 第 60 分鐘時應在第 38–40 題左右 |
| SAP（180 分鐘） | 約 150 分鐘內完成 75 題（每題約 2 分鐘） | 第 60 分鐘時應在第 30 題左右 |

第一輪刻意比平均預算快一點，是為了留下 30 分鐘給第二輪檢查標記的題目。如果檢查點落後超過 5 題，就要更積極地「先選一個答案、標記、往下走」。

SAP 的題幹很長，讀題技巧更重要：**先讀問句與四個選項的差異**。SAP 的四個選項常常前半段相同、只有一兩個元件不同，例如三個選項都用 Transit Gateway，只差在 route table 怎麼設。先找出差異，再回頭讀情境中跟這個差異有關的句子，就不必把每一句都記住。

### 多選題的作答方式

多選題沒有部分給分，所以要把每個選項當成獨立的是非題判斷：這個選項本身是否正確、是否滿足需求？先挑出最有把握的那一個，再從剩下的選項中找出第二個。如果兩個選項互相衝突（例如一個說用 Multi-AZ、一個說用 read replica 達成同一個目的），通常只有一個是正解。

**新創期**：Wanderly 從一台 EC2 跑網站加資料庫開始，很快遇到資料庫暴露在 Internet、單台機器故障就整站停擺、流量高峰撐不住等問題。這些故事對應網路（Part 1）、安全（Part 2）與運算（Part 3），也是 SAA 最核心的範圍。

**營運期**：系統穩定之後，問題變成「怎麼知道哪裡壞了」「怎麼安全地部署」「Region 掛掉怎麼辦」「帳單為什麼這麼高」（Part 7）。

**企業期**：Wanderly 併購一家傳統旅行社，對方有一個舊資料中心，裡面有 300 台虛擬機、Oracle 資料庫與 Windows 檔案伺服器。突然之間，問題變成多帳號治理、資料中心與 AWS 之間的網路、遷移計畫與法規遵循（Part 8），這是 SAP 的主戰場。

**全球化與 AI**：最後，Wanderly 要服務亞洲以外的使用者，並推出一個 AI 旅遊助理（Part 9、10）。

阿哲會在不同章節以不同角色出現，有時是解決問題的工程師，有時是犯錯的人。跟著他的錯誤走，往往比直接看正確答案更容易記住。

## 1.10 比較與選型：考試中「最佳化目標」怎麼互相取捨

本章沒有要比較的 AWS 服務，但有一組考試中最常互相衝突的目標，值得先建立直覺：

| 目標 | 通常會讓你選 | 通常會讓你放棄 |
|---|---|---|
| 最少營運負擔 | 受管服務、serverless、AWS 原生整合 | 自建軟體、需要 patch 的 EC2、自寫腳本 |
| 最低成本 | 合適的計價模式、儲存分層、只在需要時運行 | 過度備援、一直開著的閒置容量 |
| 最高可用性 | 多 AZ、多副本、自動 failover | 單一 instance、單一 AZ |
| 最快上線／不改程式 | 基礎設施層設定、rehost | 重新架構成微服務或 serverless |
| 最安全 | IAM role、private 網路、加密、最小權限 | 長期存取金鑰、公開存取、寬鬆規則 |

當題目同時列出兩個目標（例如「highly available and cost-effective」），先滿足硬性的那個（可用性要求通常是硬條件），再在符合的選項中挑便宜的那個。

## 1.11 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| Choose two／Choose three | 每個選項獨立判斷；全部選對才得分 |
| LEAST operational overhead | 受管服務或 serverless，排除自建 EC2 與自寫腳本 |
| MOST cost-effective | 在滿足所有硬條件的選項中挑最便宜的，不是全場最便宜的 |
| highly available | 跨至少兩個 AZ，不要有單點 |
| without modifying the application | 刪掉所有需要改寫程式的選項 |
| decouple components | SQS、SNS、EventBridge |
| securely access AWS services from EC2 | IAM role（instance profile），不是存取金鑰 |
| minimize latency for global users | CloudFront（可快取內容）或 Global Accelerator（非 HTTP 或需要固定 IP） |
| as quickly as possible | 不需要重新設計的方案 |
| must not lose any orders／messages | 先持久保存（佇列、資料庫），再處理 |

**常見陷阱**：

1. 只讀情境不讀問句，結果用錯的最佳化目標比較選項。
2. 選了「技術上可行但違反一個小限制」的選項，例如題目寫「不能修改程式」，選項卻需要改用 SDK 呼叫新服務。
3. 把多區域或多帳號的選項當成「比較安全、比較穩」而選它，實際上題目只要求單一 Region 高可用。
4. 多選題選了兩個互相重複、解決同一件事的選項，漏掉處理另一個需求的選項。
5. 看到熟悉的服務名稱就選，沒有確認它的機制是否真的對應需求。

## 1.12 SAP 加深：讀長題目的方法

SAP 的題目常在情境中藏了大量資訊，但大部分句子只是背景。有效率的讀法是把每一句歸類：

- **現況（As-is）**：「公司目前在兩個資料中心運行……」。用來判斷遷移方式與相容性限制。
- **限制（Constraints）**：「必須使用既有的 Active Directory」「預算不能增加」「六個月內完成」。這些是一票否決條件，要逐條核對選項。
- **痛點（Pain points）**：「部署常常失敗」「帳單不透明」。告訴你題目屬於 SAP Domain 3（持續改善）的哪一個面向。
- **目標（Goal）**：「最少營運負擔」「最快遷移」。決勝條件。

SAP 選項的典型差異有三種：**順序**（先建 landing zone 再遷移，還是反過來）、**範圍**（用 SCP 套在 OU 上，還是在每個帳號各設 IAM policy）、**機制**（Transit Gateway 還是 VPC peering、DMS 還是原生備份還原）。看到四個選項長得很像，先把它們的差異寫在白板上，再回情境找能判斷差異的那一句。

## 本章重點整理

- SAA-C03 有 65 題（50 題計分、15 題不計分）、130 分鐘，720 分及格；SAP-C02 有 75 題（65 題計分、10 題不計分）、180 分鐘，750 分及格。
- 分數量表是 100–1000 的換算分數，不是答對百分比；採補償式計分，只看總分。
- AWS 已公告 SAP-C02 的最後應考日為 2026 年 11 月 17 日，之後改考 SAP-C03；應考前要到官方頁面確認當時的考試版本與 exam guide。
- 不計分題無法辨識、答錯不倒扣，所以每一題都要認真作答，時間不夠也要選一個答案。
- 多選題會寫明要選幾個，必須全部選對才得分，沒有部分給分。
- SAA 四個 domain 是安全 30%、韌性 26%、效能 24%、成本 20%；安全是最大的一塊。
- SAP 四個 domain 是組織複雜度 26%、新方案 29%、持續改善 25%、遷移與現代化 20%。
- SAA 圍繞單一 workload，SAP 圍繞整個組織；SAP 的四個選項通常都可行，差在是否同時滿足所有限制。
- 讀題順序：先讀問句找出最佳化目標，再圈出硬條件，接著刪去違反硬條件的選項，最後用最佳化目標比較剩下的選項。
- 「能用」不等於「正確」：錯誤選項通常也能運作，只是更貴、更難維運或違反某個限制。
- 錯誤選項常見的四種訊號是自己造輪子、過度設計、用錯工具與安全捷徑。
- 在符合所有條件的前提下，最簡單、受管程度最高的方案通常就是正解。
- 用兩輪作答：第一輪每題都答、猶豫就標記，第二輪只回頭看標記的題目。
- 本書以 Wanderly 從新創成長為企業的故事串連全書，Part 0–7 是 SAA 主體，Part 8 是 SAP 主戰場。
- 讀完每章就做練習題並記錄錯題，錯題本要寫下「判斷依據是哪一句話」。

## 本章練習題

以下 6 題是「示範解題」。題目本身都是正式考試風格的 SAA 題，涉及的服務會在後面章節詳細介紹；現在請把重點放在解析裡的**思考步驟**：先圈關鍵字，再排除，最後比較。讀完全書後再回來做一次，你會發現自己能直接看出答案。

做完這六題，你應該會明顯感覺到卡住的地方不是解題方法，而是服務本身：Multi-AZ、儲存類別、IAM role 都還只是名詞。第 2 章就從最底層的那個問題開始補：雲端到底是什麼，AWS 的機器放在哪裡。

### 練習 1-1｜SAA｜單選｜最少營運負擔的關鍵字

Wanderly 讓旅館業者上傳照片到一個 S3 bucket。每張照片上傳後，系統都要產生三種尺寸的縮圖並存回另一個 bucket，每張照片的處理時間約 3 秒。上傳量很不穩定：平日每小時幾十張，促銷活動時每小時上萬張。團隊只有兩位工程師，希望營運負擔最少。

哪個方案最符合需求？

- A. 在一台 EC2 上執行排程腳本，每 5 分鐘列出 bucket 中的新照片並產生縮圖
- B. 設定 S3 event notification，在物件建立時觸發 AWS Lambda 函式產生縮圖
- C. 建立 Auto Scaling group，讓多台 EC2 依 CPU 使用率擴縮，並在每台機器上執行縮圖程式輪詢 bucket
- D. 在 Amazon ECS 上執行一個常駐的縮圖 container，並以 cron 排程每小時批次處理

> [!answer]- 答案：B
> **思考步驟 1｜圈關鍵字**：「每張照片上傳後」（事件驅動）、「處理約 3 秒」（短任務）、「上傳量很不穩定」（要能自動擴縮）、「只有兩位工程師、營運負擔最少」（最佳化目標）。
>
> **思考步驟 2｜排除**：A 是單台 EC2，有單點故障、促銷時處理不完，也要自己 patch 機器，先刪。D 每小時批次一次，縮圖延遲最長一小時，而且常駐 container 也要管理，與「上傳後就處理」不符，刪除。
>
> **思考步驟 3｜比較剩下的 B 與 C**：兩者都能擴縮。C 要管理 launch template、作業系統、擴縮政策與輪詢邏輯；B 由 S3 直接觸發 Lambda，沒有伺服器要管，流量突增時 Lambda 自動擴展、閒置時不收費。最佳化目標是營運負擔最少，所以選 B。
>
> **A ✗** 排程輪詢加單台 EC2，有單點故障與容量上限，作業系統也要自己維護；這種「自己造輪子」的選項在要求最少營運負擔時幾乎不會是正解。
>
> **B ✓** S3 event notification 搭配 Lambda 是事件驅動的 serverless 模式：每上傳一張照片就觸發一次函式，3 秒的任務遠低於 Lambda 15 分鐘的上限，流量高低都由 AWS 自動處理（第 19 章）。
>
> **C ✗** 技術上可行，也能應付尖峰，但要維護 EC2、AMI、擴縮政策與輪詢程式，營運負擔明顯高於 B。如果每張照片要處理數十分鐘、超過 Lambda 的限制，這類以 EC2 或 container 為主的方案才會變成合理選擇。
>
> **D ✗** 批次排程讓縮圖延遲最長一小時，而且常駐 container 在平日大多閒置，既不即時也不省事。
>
> **考點**：SAA-3.2、SAA-2.1｜事件驅動與 serverless 降低營運負擔

### 練習 1-2｜SAA｜單選｜最划算的關鍵字

Wanderly 的會計系統每月產生約 500 GB 的報表檔案存放在 S3。報表在產生後的 30 天內常被查閱；之後只有在每季稽核時才會被讀取一次，但稽核人員要求打開檔案時能立即看到內容（毫秒級取回）。檔案必須保存 5 年。公司希望以最划算的方式滿足這些需求。

哪個方案最符合需求？

- A. 所有報表一直保存在 S3 Standard，並啟用 versioning
- B. 設定 lifecycle rule，30 天後把報表轉到 S3 Glacier Deep Archive
- C. 設定 lifecycle rule，30 天後把報表轉到 S3 Glacier Instant Retrieval，並在 5 年後刪除
- D. 每月把報表複製到 EBS volume，並建立 EBS snapshot 保存

> [!answer]- 答案：C
> **思考步驟 1｜圈關鍵字**：「30 天內常被查閱」、「之後每季讀一次」（存取頻率低）、「毫秒級取回」（硬條件）、「保存 5 年」、「最划算」（最佳化目標）。
>
> **思考步驟 2｜排除**：B 的 Deep Archive 取回需要數小時，違反毫秒級取回的硬條件，刪除。D 把檔案搬到 EBS，EBS 按配置容量計費且綁在單一 AZ，用它長期存放檔案既貴又不方便讀取，刪除。
>
> **思考步驟 3｜比較 A 與 C**：兩者都能毫秒級取回。A 讓 30 天後幾乎不被讀取的資料仍付 Standard 的儲存費；C 在 30 天後轉到為「很少讀、讀時要立即拿到」設計的儲存類別，儲存費低很多，並在 5 年後自動刪除。最划算是 C。
>
> **A ✗** 可以滿足取回速度，但 30 天後的資料仍用最貴的儲存類別存放 5 年，不划算；額外啟用 versioning 還可能保留更多舊版本而增加費用。
>
> **B ✗** Deep Archive 是最便宜的儲存類別，但取回時間以小時計，不符合「打開時立即看到內容」。如果題目改成「稽核可以提前一天申請」，它才會是更好的答案。
>
> **C ✓** Lifecycle rule 自動在 30 天後轉換儲存類別、5 年後刪除，不需要人工操作。Glacier Instant Retrieval 適合每季存取一次左右、但要求毫秒級取回的資料（第 23 章）。
>
> **D ✗** EBS 是掛在 EC2 上的區塊儲存，不適合當長期檔案封存；snapshot 也不能讓稽核人員直接打開單一檔案。
>
> **考點**：SAA-4.1｜依存取模式選擇 S3 儲存類別與 lifecycle

### 練習 1-3｜SAA｜單選｜高可用的關鍵字

Wanderly 的訂房網站目前跑在一台 EC2 上，同一台機器還安裝了 MySQL 資料庫。上個月這台機器所在的 AZ 發生故障，網站停擺了兩小時。執行長要求：任何一個 AZ 故障時，網站都要能繼續服務，且不能遺失已確認的訂單。團隊希望盡量使用受管服務。

哪個方案最符合需求？

- A. 把 EC2 換成更大的 instance type，並每小時建立一次 EBS snapshot
- B. 在同一個 AZ 再啟動一台 EC2，兩台都安裝 MySQL 並設定互相複寫
- C. 把資料庫搬到 Amazon RDS for MySQL 並建立一個同 AZ 的 read replica，網站仍維持一台 EC2
- D. 把網站放到跨兩個 AZ 的 Auto Scaling group 並以 Application Load Balancer 分流，資料庫搬到 Amazon RDS for MySQL Multi-AZ 部署

> [!answer]- 答案：D
> **思考步驟 1｜圈關鍵字**：「任何一個 AZ 故障時都要繼續服務」（跨 AZ，硬條件）、「不能遺失已確認的訂單」（資料要同步複寫）、「盡量使用受管服務」（最佳化目標）。
>
> **思考步驟 2｜排除**：A 和 B 的所有資源仍在同一個 AZ，AZ 故障時一樣全部停擺，違反第一個硬條件，刪除。C 的網站仍只有一台 EC2，而且 read replica 和 primary 在同一個 AZ，網站層與資料層都還有單點，刪除。
>
> **思考步驟 3｜確認剩下的 D**：網站層跨兩個 AZ、由 Load Balancer 分流，資料庫用 Multi-AZ（同步複寫到另一個 AZ 的 standby，故障時自動 failover），兩層都不再有單點，而且都是受管服務。
>
> **A ✗** 更大的機器不會讓它跨 AZ；snapshot 每小時一次，最壞情況會遺失將近一小時的訂單，也需要人工從 snapshot 重建。
>
> **B ✗** 兩台機器在同一個 AZ，AZ 故障時同時失效；自己維護 MySQL 複寫也違反「盡量使用受管服務」。
>
> **C ✗** Read replica 是非同步複寫，主要用途是分散讀取，不是自動 failover；而且放在同 AZ 也擋不住 AZ 故障。網站層仍只有一台 EC2。
>
> **D ✓** 這是 AWS 上高可用 web 應用的標準架構：ALB 與 Auto Scaling group 跨 AZ，RDS Multi-AZ 以同步複寫保護已提交的交易，故障時自動切換（第 18、26 章）。
>
> **考點**：SAA-2.2｜跨 AZ 的 web tier 與 RDS Multi-AZ

### 練習 1-4｜SAA｜選兩項｜安全存取的關鍵字

Wanderly 的一支應用程式跑在 EC2 上，需要讀取 S3 bucket `wanderly-hotel-photos` 中的照片。目前做法是把一組 IAM user 的存取金鑰寫在程式設定檔中，而這個設定檔被誤推到公開的程式碼儲存庫。安全團隊要求：程式中不能再有長期憑證，應用程式只能讀取這一個 bucket，而且 bucket 絕不能被公開存取。

哪兩個做法能滿足需求？（選兩項）

- A. 把存取金鑰改存在 EC2 的環境變數中，並每 90 天手動輪替一次
- B. 建立一個只允許對 `wanderly-hotel-photos` 執行 `s3:GetObject` 的 IAM role，透過 instance profile 附加到 EC2，並刪除舊的存取金鑰
- C. 把 bucket policy 改成允許所有人讀取，再用 CloudFront 隱藏 bucket 名稱
- D. 為 IAM user 附加 `AmazonS3FullAccess` managed policy，確保程式一定能讀到照片
- E. 確認 bucket 維持啟用 S3 Block Public Access，不使用任何公開的 bucket policy 或 ACL

> [!answer]- 答案：B、E
> **思考步驟 1｜圈關鍵字**：這是選兩項題，題目有三個硬條件：「程式中不能有長期憑證」、「只能讀取這一個 bucket」（最小權限）、「bucket 絕不能被公開存取」。兩個正解加起來要覆蓋這三個條件。
>
> **思考步驟 2｜逐項排除**：A 仍然使用長期存取金鑰，只是換了位置，違反第一個條件。C 把 bucket 設為公開，直接違反第三個條件。D 給了全部 S3 權限，違反最小權限，而且仍在用 IAM user 的金鑰。三個都刪除。
>
> **思考步驟 3｜確認剩下的 B 與 E**：B 用 IAM role 取代存取金鑰（EC2 會自動取得會過期的臨時憑證），並把權限限制在單一 bucket 的讀取，滿足前兩個條件；E 守住第三個條件。兩者各自負責不同的需求，合起來剛好完整。
>
> **A ✗** 環境變數裡的存取金鑰仍是長期憑證，外洩風險沒有消除，手動輪替也增加營運負擔。
>
> **B ✓** EC2 透過 instance profile 取得 IAM role 的臨時憑證，AWS SDK 會自動取得與更新，程式裡完全不需要金鑰；policy 只允許讀取指定 bucket，符合最小權限（第 12 章）。
>
> **C ✗** 公開的 bucket policy 讓任何知道物件網址的人都能讀取；CloudFront 不會讓公開的 bucket 變成私有。正確的 CloudFront 做法是搭配 Origin Access Control，讓 bucket 保持私有（第 11 章）。
>
> **D ✗** `AmazonS3FullAccess` 允許對帳號內所有 bucket 讀寫刪除，與「只能讀取這一個 bucket」相反，而且沒有解決長期憑證的問題。
>
> **E ✓** S3 Block Public Access 是帳號或 bucket 層級的安全開關，可以阻擋任何讓 bucket 變成公開的 policy 或 ACL。新建的 bucket 預設就是啟用的，保持啟用即可防止誤設定（第 22 章）。
>
> **考點**：SAA-1.1、SAA-1.3｜IAM role 取代存取金鑰與 S3 Block Public Access

### 練習 1-5｜SAA｜單選｜鬆耦合的關鍵字

Wanderly 的網站收到訂單後，會直接以同步 HTTP 呼叫後端的訂單處理服務。促銷期間訂單量暴增，訂單處理服務來不及處理而逾時，網站因此回傳錯誤給使用者，部分訂單就這樣遺失了。團隊希望網站在後端忙碌或短暫故障時仍能接受訂單，且不能遺失任何訂單，同時盡量不增加營運負擔。

哪個方案最符合需求？

- A. 網站把訂單寫入 Amazon SQS queue 後立即回應使用者，訂單處理服務從 queue 取出訂單處理，並依 queue 深度擴展處理端
- B. 網站把訂單發布到 Amazon SNS topic，訂單處理服務稍後有空時再到 topic 讀取訂單
- C. 把訂單處理服務的 EC2 換成更大的 instance type，並把網站的 HTTP 逾時時間延長到 5 分鐘
- D. 在網站與訂單處理服務之間加入 Application Load Balancer，並在處理服務前放 Amazon ElastiCache 暫存訂單

> [!answer]- 答案：A
> **思考步驟 1｜圈關鍵字**：「後端忙碌或短暫故障時仍能接受訂單」（網站與後端解耦）、「不能遺失任何訂單」（訊息要持久保存）、「盡量不增加營運負擔」（最佳化目標）。
>
> **思考步驟 2｜排除**：C 仍是同步呼叫，後端故障時網站一樣失敗，延長逾時只會讓使用者等更久，刪除。D 加了 Load Balancer 但仍是同步呼叫；ElastiCache 是快取，不保證資料不遺失，也不是佇列，刪除。
>
> **思考步驟 3｜比較 A 與 B**：兩者都是非同步訊息服務。B 的 SNS 是推播模型：發布時立即推給訂閱者，不會把訊息存著等消費者「稍後來讀」，訂閱者不可用時無法像佇列一樣讓它之後再取。A 的 SQS 會持久保存訊息，直到消費者處理完並刪除，正好滿足「不遺失」與「後端稍後處理」。選 A。
>
> **A ✓** SQS 讓網站和後端之間有一個緩衝區：網站寫入 queue 就能回應使用者，後端依自己的速度處理；後端暫時故障時訊息留在 queue 中（預設保存 4 天，最長 14 天）。以 queue 深度驅動 Auto Scaling 是標準做法（第 32 章）。
>
> **B ✗** SNS 是發布／訂閱的推播服務，不提供「訊息先存著、消費者之後再來拉取」的能力。常見做法是 SNS 搭配多個 SQS queue（fan-out），但單獨用 SNS 無法滿足需求。
>
> **C ✗** 垂直擴展只能提高上限，下一次尖峰仍可能超過；而且同步架構下後端一故障，網站就無法接受訂單。
>
> **D ✗** ALB 可以把流量分給多台後端，但呼叫仍是同步的；ElastiCache 是記憶體快取，不是可靠的訊息佇列，不能保證每筆訂單都被處理一次。
>
> **考點**：SAA-2.1｜以 SQS 解耦並吸收尖峰

### 練習 1-6｜SAA｜單選｜不改程式與全球低延遲

Wanderly 的旅遊攻略網站是一個靜態網站（HTML、CSS、圖片），存放在東京 Region 的 S3 bucket。歐洲與美國使用者抱怨頁面載入很慢。團隊要求降低全球使用者的載入延遲、減少直接存取 S3 的流量，且不能修改網站內容或建置流程；bucket 也必須保持私有。

哪個方案最符合需求？

- A. 在歐洲與美國各建立一個 bucket，設定 S3 Cross-Region Replication，並修改網站讓使用者依所在地區連到不同 bucket
- B. 在 bucket 前面建立 AWS Global Accelerator，讓使用者經由 anycast IP 連到 S3
- C. 建立 Amazon CloudFront distribution，以 S3 bucket 作為 origin 並使用 Origin Access Control，讓 bucket 只允許 CloudFront 存取
- D. 把網站搬到東京 Region 中更大的 EC2 instance，並啟用 enhanced networking

> [!answer]- 答案：C
> **思考步驟 1｜圈關鍵字**：「靜態網站」（可快取）、「歐洲與美國使用者」（全球低延遲）、「減少直接存取 S3 的流量」、「不能修改網站內容或建置流程」與「bucket 必須保持私有」（兩個硬條件）。
>
> **思考步驟 2｜排除**：A 要修改網站讓使用者連到不同 bucket，違反「不能修改」，刪除。D 把內容留在東京，只換更大的機器，距離造成的延遲完全沒解決，也要開始管理 EC2，刪除。
>
> **思考步驟 3｜比較 B 與 C**：兩者都是 AWS 的全球邊緣網路服務。Global Accelerator 透過 AWS 骨幹網路加速 TCP／UDP 連線，但**不快取內容**，每個請求仍回到原始端點，也無法減少 S3 流量；CloudFront 是 CDN，會把靜態檔案快取在全球的 edge location，第二位使用者就直接從附近的 edge 拿到內容。題目要「快取靜態內容並減少回源」，選 C。
>
> **A ✗** 多 Region 複寫可以讓內容更靠近使用者，但要修改網站的導向邏輯，還要付三份儲存與複寫費用，是過度設計。
>
> **B ✗** Global Accelerator 適合非 HTTP 協定、需要固定 IP 或快速跨 Region failover 的情境；它不快取內容，對靜態網站的幫助不如 CDN，也不是放在 S3 bucket 前面的標準做法。
>
> **C ✓** CloudFront 把內容快取在靠近使用者的 edge location，大幅降低延遲並減少回源流量；Origin Access Control 讓 bucket 保持私有、只允許這個 distribution 讀取。網站內容和建置流程都不需要修改，只要把網域指向 CloudFront（第 11 章）。
>
> **D ✗** 延遲主要來自地理距離，不是伺服器規格；把靜態網站從 S3 搬到 EC2 還會增加營運負擔。
>
> **考點**：SAA-3.4｜CloudFront 加速全球靜態內容、OAC 保持 bucket 私有
