# 第 4 章　儲存、資料庫與可靠性基礎

## 4.1 故事：一台機器扛下所有事

第 3 章處理的是「封包怎麼送到」。但系統會出問題的地方不只網路：資料存在哪裡、一台機器壞掉會怎樣、資料能不能補回來，都還沒有答案。這是 Part 0 的最後一章，要補上的就是這些詞彙，它們在後面談每一個 AWS 服務時都會用到。

Wanderly 的第一版系統非常簡單：一台 EC2 上同時跑網站程式、MySQL 資料庫，使用者上傳的旅館照片直接存在這台機器的磁碟裡。開發快、成本低，三個人的團隊完全夠用。

半年後，三件事在同一個月發生。第一，旅館照片塞滿了磁碟，網站寫不進新訂單，工程師小林半夜爬起來擴充磁碟。第二，一場促銷讓流量變成平常的十倍，CPU 衝到 100%，網站整整慢了兩小時。第三，那台機器所在的硬體出問題，EC2 被迫重啟，小林發現前一天的備份根本沒有成功，最後幾個小時的訂單只能靠客服一筆一筆跟旅館核對。

事後檢討會上，技術主管在白板寫下幾個問題：照片應該放在哪裡？資料庫要怎樣才不怕一台機器壞掉？流量暴增時能不能自動多開幾台？最多可以接受丟失多久的資料、停機多久？訂房成功後寄確認信，要不要讓使用者等信寄出去？

這些問題的答案，就是本章要建立的語彙：運算與儲存的形態、資料庫的種類、一致性與複寫、可用性與耐久性、RTO 與 RPO、擴展與解耦。後面 Part 3 到 Part 7 的每個 AWS 服務，都是在回答這幾個問題中的某一個。

## 4.2 運算的三種形態：VM、container、serverless

程式總要在某個地方執行。雲端上有三種主要的「執行環境」，差別在於你要管理多少東西。

**VM（Virtual Machine，虛擬機器）** 是用軟體模擬出來的一台完整電腦。實體伺服器上跑著一層 **hypervisor（虛擬化管理程式）**，它把 CPU、記憶體、磁碟切給多台 VM，每台 VM 有自己的作業系統。你可以安裝任何軟體、調整任何設定，但作業系統的更新、修補、監控都是你的責任。AWS 的 VM 服務是 **EC2**（第 17 章）。

**Container（容器）** 把應用程式和它需要的函式庫打包成一個 **image（映像檔）**，在同一個作業系統核心上隔離執行。它不帶完整作業系統，所以啟動只要幾秒、體積小，同一個 image 在筆電和正式環境的行為一致。但你需要一個平台來決定 container 跑在哪台機器、掛了要重啟、流量變大要多開幾個，這就是 **orchestration（編排）**。AWS 提供 ECS、EKS，以及不用管底層機器的 Fargate（第 21 章）。

**Serverless（無伺服器）** 不是真的沒有伺服器，而是「伺服器完全由雲端管理，你看不到也不用管」。以 **Lambda** 為例，你只上傳一段函式，有事件發生（例如 HTTP 請求、檔案上傳）時 AWS 才執行它，按執行次數與時間計費，沒有請求就幾乎不花錢（第 19 章）。代價是限制較多：Lambda 單次最長執行 15 分鐘，也不適合需要長時間保持連線或狀態的程式。

| 比較 | VM（EC2） | Container（ECS／EKS／Fargate） | Serverless（Lambda） |
|---|---|---|---|
| 你管理什麼 | 作業系統以上全部 | Image 與執行設定（用 EC2 承載時還要管機器） | 只有程式碼與設定 |
| 啟動速度 | 數十秒到數分鐘 | 數秒 | 毫秒到數秒 |
| 計費 | 依開機時間 | 依 task 資源與時間，或底層 EC2 | 依請求數與執行時間 |
| 適合 | 需要完整控制、傳統軟體、特殊授權 | 微服務、長時間執行的服務、批次工作 | 事件驅動、流量起伏大、短時間工作 |
| 主要限制 | 營運負擔最高 | 要學編排平台 | 執行時間、記憶體與冷啟動 |

> [!tip] 考試提示
> 題目出現 **LEAST operational overhead（最低營運負擔）** 時，通常往右邊選：能用 serverless 就不要自己管 VM。但如果工作要跑超過 15 分鐘，Lambda 就被排除，改看 Fargate 或 AWS Batch。

## 4.3 儲存的三種形態：block、file、object

小林的第一個問題是照片塞爆了磁碟。要回答「照片應該放哪裡」，得先知道儲存有三種形態，它們不是「快慢之分」，而是「存取方式」根本不同。

```text
Block storage                File storage                 Object storage
┌──────────────┐            ┌──────────────┐             ┌────────────────────────┐
│ 一台機器      │            │ 多台機器      │             │ 任何地方的程式          │
│ 看到一顆「磁碟」│            │ 掛載同一個目錄 │             │ 用 HTTP API 存取        │
│ /dev/xvda     │            │ /mnt/shared   │             │ PUT / GET  key=…       │
└──────┬───────┘            └──┬────┬────┬─┘             └───────────┬────────────┘
       │ 讀寫第 N 個區塊        │ NFS／SMB 協定             │ 整個物件上傳／下載
       ▼                       ▼                           ▼
 [Volume：一格格固定大小的區塊]  [共享檔案系統：資料夾與檔案]   [Bucket：key → 物件 + metadata]
  例：EBS、instance store       例：EFS、FSx                  例：S3
```

### Block storage：一顆裸磁碟

**Block storage（區塊儲存）** 提供一顆「磁碟」，資料被切成固定大小的區塊，作業系統可以直接讀寫任意區塊。你要先在上面建立檔案系統（例如 ext4、NTFS）才能放檔案。它延遲最低、可以改寫檔案中任何一小段，所以適合作業系統開機磁碟和資料庫的資料檔。

限制是：一顆 block volume 通常只掛在一台機器上。AWS 的 **EBS（Elastic Block Store）** 是透過網路連到 EC2 的 block volume，資料在**同一個 AZ 內**自動複寫，但 volume 綁定在單一 AZ；另一種 **instance store** 是 EC2 實體主機上的本機磁碟，速度很快，但 instance 停止或終止時資料就消失，只能放暫存資料（第 17、24 章）。

### File storage：大家共用的資料夾

**File storage（檔案儲存）** 提供一個有資料夾階層的共享檔案系統，多台機器透過網路協定同時掛載同一個目錄，例如 Linux 常用 **NFS**、Windows 常用 **SMB**。應用程式用一般的檔案路徑讀寫，不需要改程式。適合多台伺服器要共用同一批檔案的情境，例如共用的內容管理目錄、機器學習訓練資料、使用者家目錄。

AWS 的 **EFS** 提供 Linux 用的 NFS 檔案系統，標準類型的資料跨多個 AZ 儲存、容量自動增減；**FSx** 系列則提供 Windows File Server、Lustre（高效能運算）等特定檔案系統（第 24 章）。

### Object storage：用 key 存取的無限倉庫

**Object storage（物件儲存）** 不是磁碟也不是資料夾，而是一個透過 HTTP API 存取的倉庫。每個 **object（物件）** 由資料本身、一組 **metadata（描述資料的資料）** 和一個唯一的 **key（鍵）** 組成，例如 `hotels/1234/lobby.jpg`。你只能整個上傳、整個下載（或讀取其中一段範圍），不能像磁碟那樣「改寫第 100 個 byte」，要修改就得上傳一個新版本。

換來的好處是：容量實際上沒有上限、按用量計費、資料自動跨多個設施複寫，而且任何地方的程式（甚至使用者的瀏覽器）都能透過 HTTPS 直接存取。AWS 的 **S3** 是最具代表性的 object storage（第 22、23 章）。Wanderly 的旅館照片正是 S3 的典型用途。

> [!warning] 常見誤解
> 「S3 的 key 有斜線，所以 S3 是檔案系統。」不是。`hotels/1234/lobby.jpg` 整串是一個 key，「資料夾」只是 console 為了好看而顯示的前綴。S3 沒有真正的目錄，也不能被傳統應用程式當作本機磁碟直接改寫。需要共享檔案系統時，選 EFS 或 FSx。

### 衡量儲存效能的三個數字

- **IOPS（I/O operations per second）**：每秒能完成幾次讀寫操作。資料庫大量的小筆隨機讀寫最在意它。
- **Throughput（吞吐量）**：每秒能傳輸多少資料量（MB/s）。大檔案的循序讀寫（例如影片處理、log 分析）最在意它。
- **Latency（延遲）**：單次操作要等多久。本機 block storage 最低，透過網路的 file 與 object storage 較高。

第 24 章選 EBS volume type 時，就是在 IOPS、throughput 與價格之間取捨。

## 4.4 資料庫的四種角色

照片有了去處，接著是訂單、會員、旅館房況這些「結構化資料」。資料庫不只一種，選錯種類比選錯規格的代價更大。

### Relational database：表格與關聯

**Relational database（關聯式資料庫）** 把資料存成有固定欄位的 **table（資料表）**，例如 `orders` 表有訂單編號、會員編號、旅館編號、金額。表與表之間用欄位建立關聯，用 **SQL** 查詢，可以 **JOIN（合併）** 多張表回答複雜問題：「上個月在東京訂房超過三次的會員有哪些？」它事先定義 **schema（資料結構）**，並支援交易（下一節），適合訂單、帳務這類要求正確性的資料。

AWS 上的受管關聯式資料庫是 **RDS**（MySQL、PostgreSQL、Oracle、SQL Server 等）與 **Aurora**（第 26 章）。

### NoSQL：為特定存取模式而生

**NoSQL** 泛指不以關聯表格為主的資料庫，常見類型有：

- **Key-value（鍵值）**：用一個 key 直接取回一筆資料，例如「用 session ID 取回登入資訊」。
- **Document（文件）**：每筆資料是一份 JSON 文件，欄位可以不固定。
- **Graph（圖）**：專門處理「誰認識誰」這種關係網路。

NoSQL 通常放棄複雜的 JOIN 與彈性查詢，換取「已知存取模式下」幾乎不受規模影響的效能與水平擴展能力。AWS 的 **DynamoDB** 是 key-value／document 資料庫，無論資料多大，用 key 查詢都能維持穩定的低延遲（第 27 章）；其他類型見第 29 章。

### Cache：放在記憶體裡的捷徑

**Cache（快取）** 把常被讀取的資料放在記憶體中，讀取延遲可以從毫秒級降到微秒級，也大幅減輕資料庫的負擔。例如熱門城市的旅館列表，每分鐘被查幾萬次，但內容幾分鐘才變一次，就很適合快取。

最重要的觀念是：**cache 不是 source of truth（資料的正本）**。記憶體中的資料可能過期、可能因為節點重啟而消失，正確的資料永遠要存在資料庫裡。AWS 的快取服務是 **ElastiCache**（第 28 章）。

### Data warehouse：為分析而生

訂房系統每秒處理大量「小而快」的讀寫，例如建立一筆訂單、查一位會員，這種工作叫 **OLTP（Online Transaction Processing，線上交易處理）**。而老闆想知道「過去三年各城市各月份的營收趨勢」，需要掃描數億筆資料做加總，這種工作叫 **OLAP（Online Analytical Processing，線上分析處理）**。

把 OLAP 查詢丟給 OLTP 資料庫，會拖慢正在處理訂單的系統。**Data warehouse（資料倉儲）** 專為分析設計：資料以 **columnar（欄式）** 格式儲存，查「營收」只需要讀營收那一欄，不必讀整筆訂單，掃描量大幅減少。AWS 的 data warehouse 是 **Redshift**，也可以把資料放在 S3 用 Athena 直接查詢（第 30 章）。

| 類型 | 擅長 | 不擅長 | AWS |
|---|---|---|---|
| Relational | 交易、JOIN、彈性查詢 | 超大規模水平擴展寫入 | RDS、Aurora |
| NoSQL（key-value／document） | 已知存取模式、極大規模、穩定低延遲 | 臨時起意的複雜查詢、JOIN | DynamoDB |
| Cache | 微秒級讀取、減輕資料庫負擔 | 作為唯一的資料正本 | ElastiCache |
| Data warehouse | 大量資料的彙總分析 | 高頻率的小筆交易 | Redshift、Athena |

## 4.5 ACID：交易要嘛全做、要嘛全不做

訂一間房，系統至少要做兩件事：把旅館的可售房數減 1，並新增一筆訂單。如果第一步做完、第二步之前機器當機，就會出現「房間少了一間，卻沒有人訂到」的錯誤。**Transaction（交易）** 把多個操作包成一個不可分割的單位，關聯式資料庫用 **ACID** 四個性質保證它的正確性：

- **Atomicity（原子性）**：交易中的操作要嘛全部成功，要嘛全部取消（rollback），不會只做一半。
- **Consistency（一致性）**：交易前後，資料都符合規則，例如可售房數不能小於 0。
- **Isolation（隔離性）**：多筆交易同時進行時，彼此不會看到對方做到一半的狀態。兩個人同時搶最後一間房，只有一人會成功。
- **Durability（持久性）**：交易一旦回報成功，即使下一秒斷電，結果也不會遺失。

> [!note] 兩個不同的「一致性」
> ACID 的 C 指「資料符合業務規則」；下一節的 strong／eventual consistency 指「不同副本之間讀到的資料是否相同」。名字一樣，意思不同，讀題時要分清楚。

NoSQL 資料庫傳統上只保證單筆資料的原子性，但現代服務也提供交易功能，例如 DynamoDB transactions 可以讓多筆 item 的寫入一起成功或一起失敗（第 27 章）。

## 4.6 一致性：剛寫進去，馬上讀得到嗎？

為了不怕機器壞掉，資料通常會存多份 **replica（副本）**。這帶來一個新問題：寫入一份副本之後，其他副本要過多久才會更新？

**Strong consistency（強一致性）** 保證寫入成功之後，任何人從任何地方讀，都一定讀到最新的值。**Eventual consistency（最終一致性）** 則只保證「如果沒有新的寫入，所有副本最終會變成一樣」，在那之前，讀者可能讀到舊值。

為什麼不全部都用強一致？因為強一致要等所有（或多數）副本確認，寫入或讀取的延遲較高、可用性也可能受影響；最終一致讓讀取可以從最近的副本立即回答，速度快、成本低。這是分散式系統永恆的取捨。

AWS 上幾個必須記住的行為：

- **S3** 自 2020 年 12 月起提供 **strong read-after-write consistency**：PUT 或 DELETE 成功後，接下來的 GET 與 LIST 都會看到最新結果（第 22 章）。
- **DynamoDB** 讀取預設是 eventually consistent，可以在請求中指定 strongly consistent read，代價是消耗較多讀取容量（第 27 章）。
- **RDS read replica** 透過非同步複寫更新，從 replica 讀到的資料可能落後主資料庫一小段時間（第 26 章）。

> [!example] 例子
> 使用者剛付款完成，頁面跳轉到「我的訂單」，卻看不到剛剛那筆訂單。原因很可能是寫入走主資料庫、讀取走了還沒同步的 read replica。解法是讓「剛寫完就要讀」的關鍵流程讀主資料庫，其他不敏感的查詢再交給 replica。這種需求稱為 **read-your-writes（讀到自己的寫入）**。

## 4.7 Replication：同步還是非同步

**Replication（複寫）** 是把資料持續複製到另一份副本的機制。它同時服務好幾個目的：機器壞掉時資料不會只剩一份（耐久性）、主機故障時可以切到副本繼續服務（可用性）、把讀取分散到副本（效能）、把資料放到離使用者更近的地方（延遲）。

複寫的關鍵問題是：主資料庫要不要「等副本確認」才回報寫入成功？

```text
同步複寫（synchronous）                     非同步複寫（asynchronous）

App ──① 寫入──► Primary                     App ──① 寫入──► Primary
                  │ ② 送到副本                                 │ ② 立即回報成功 ──► App
                  ▼                                            │
               Standby                                         │ ③ 稍後送到副本
                  │ ③ 副本確認                                 ▼
                  ▼                                         Replica（可能落後幾毫秒到數秒）
Primary ──④ 回報成功──► App
```

**同步複寫**：主資料庫等副本確認寫入後，才回報成功（左圖 ①→②→③→④）。優點是主資料庫故障時副本一定有最新資料，不會遺失已確認的交易；缺點是每次寫入都要多等一段網路來回，副本距離越遠越慢。所以同步複寫通常只用在距離很近的地方，例如同一個 Region 的不同 AZ。

**非同步複寫**：主資料庫寫完就回報成功，再另外把變更送到副本（右圖）。寫入速度不受副本影響，副本可以放在很遠的地方（另一個 Region）；代價是副本會有 **replication lag（複寫延遲）**，主資料庫突然故障時，最後一小段還沒送過去的資料可能遺失。

| | 同步 | 非同步 |
|---|---|---|
| 寫入延遲 | 較高（要等副本） | 低 |
| 主機故障時資料遺失 | 不會遺失已確認的寫入 | 可能遺失 lag 期間的寫入 |
| 副本距離 | 近（同 Region 跨 AZ） | 可以很遠（跨 Region） |
| 典型用途 | 高可用 failover | 讀取擴展、跨 Region 災難復原 |
| AWS 例子 | RDS Multi-AZ（standby） | RDS read replica、跨 Region 複寫 |

把這張表對應到 AWS（細節在第 26、34 章）：

- **RDS Multi-AZ** 在另一個 AZ 維護一份同步的 standby。主資料庫故障時，AWS 自動 **failover（容錯移轉）** 到 standby，並把資料庫的 DNS 名稱指向新主機；AWS 文件說明 failover 通常需要 60–120 秒，大型交易或較長的復原過程會讓時間變長。最常見的 **Multi-AZ instance 部署**（一個 primary 加一個 standby）中，standby 不能拿來讀取，它的任務只有接手。RDS 另有一種 **Multi-AZ DB cluster** 部署，有兩個可以承接讀取的 standby，第 26 章再比較；本書說「Multi-AZ standby 不能讀」時，指的都是前者。
- **RDS read replica** 用非同步複寫，可以承接讀取流量，也可以建在其他 Region；必要時可以手動 **promote（提升）** 成獨立的主資料庫。
- **Aurora** 把儲存層設計成 6 份副本分散在 3 個 AZ，寫入只需要其中 4 份確認（多數決），即使整個 AZ 損失也不影響資料，兼顧耐久性與速度（第 26 章）。

### Replication 不是備份

這是本章最重要的警告之一：**複寫會忠實地複製錯誤**。工程師誤下 `DELETE FROM orders`，這個刪除會在幾毫秒內同步到所有副本。複寫保護你不怕「機器壞掉」，但不保護你不怕「資料被改壞」。要能回到過去某個時間點，需要 **backup（備份）**：定期的 snapshot，加上 RDS 的 **point-in-time recovery（PITR，還原到某個時間點）**、S3 的 versioning、AWS Backup 等機制（第 23、26、34 章）。

## 4.8 Availability 與 durability：幾個 9 的意義

可靠性有兩個常被混用的指標。

**Availability（可用性）** 是「系統能正常提供服務的時間比例」，問的是「現在用得到嗎？」。**Durability（耐久性）** 是「資料不會遺失的機率」，問的是「存進去的東西還在嗎？」。一個系統可以暫時連不上（可用性下降），但資料完好無缺（耐久性不受影響）；反過來，資料一旦遺失就無法挽回，所以耐久性的要求通常比可用性高得多。

可用性常用「幾個 9」表示：

| 可用性 | 每年最多停機 | 每月最多停機（約） |
|---|---|---|
| 99%（兩個 9） | 約 3.65 天 | 約 7.3 小時 |
| 99.9%（三個 9） | 約 8.76 小時 | 約 43.8 分鐘 |
| 99.95% | 約 4.38 小時 | 約 21.9 分鐘 |
| 99.99%（四個 9） | 約 52.6 分鐘 | 約 4.4 分鐘 |
| 99.999%（五個 9） | 約 5.26 分鐘 | 約 26 秒 |

每多一個 9，允許的停機時間就縮小十倍，需要的架構投入也大幅增加。四個 9 一年只能停機不到一小時，這已經不允許「出事後由人工慢慢修復」，必須自動偵測並切換。

### 串聯與並聯

一個請求要經過多個元件時，可用性會**相乘**。網站 99.9%、資料庫 99.9%，兩者都要正常才能訂房，整體只有 99.9% × 99.9% ≈ 99.8%。元件串得越多，整體越低。

反過來，同一個功能準備多份**互相獨立**的備援（並聯），只要有一份活著就能服務，整體可用性 = 1 − （每份都故障的機率）。兩台各 99% 的伺服器，假設故障互不相關，整體約為 1 − 0.01 × 0.01 = 99.99%。關鍵字是「互相獨立」：兩台機器放在同一個機架、同一個 AZ，很可能一起壞，就享受不到這個效果。這就是為什麼 AWS 一再強調**跨 AZ 部署**（第 2 章）。

### S3 的數字

S3 Standard 設計上提供 **99.999999999%（11 個 9）的耐久性**，資料存放在至少 3 個 AZ；可用性設計為 99.99%。另一個常考的對比是 **S3 One Zone-IA**：資料只存在單一 AZ，便宜，但該 AZ 損毀時資料可能遺失，只適合「遺失了可以重新產生」的資料，例如由原圖產生的縮圖（第 23 章）。

## 4.9 SLA、SLO 與 RTO、RPO：把可靠性寫成數字

「系統要很可靠」不是需求，「每月可用性 99.9%、最多遺失 5 分鐘資料、1 小時內恢復」才是。這一節介紹把可靠性變成數字的幾個名詞。

### SLA、SLO、SLI

- **SLI（Service Level Indicator）**：實際量測的指標，例如「成功回應的請求比例」「p99 延遲」（把所有請求的延遲由快到慢排列，第 99 百分位的值；代表 99% 的請求都比它快）。
- **SLO（Service Level Objective）**：團隊給自己訂的目標，例如「每月 99.9% 的請求在 300 毫秒內成功」。
- **SLA（Service Level Agreement）**：和客戶簽的正式承諾，沒達到要賠償。

AWS 各服務公布的 SLA，沒達到時提供的是**服務抵用金**，不是保證不會故障。你的系統的可靠性，仍然要靠你的架構設計來達成。

### RTO 與 RPO

災難發生時，最重要的兩個數字是：

- **RPO（Recovery Point Objective，復原點目標）**：最多可以接受**遺失多久的資料**。RPO 1 小時，代表恢復後的資料最舊可以停在故障前 1 小時。
- **RTO（Recovery Time Objective，復原時間目標）**：最多可以接受**停機多久**。RTO 4 小時，代表故障後 4 小時內必須恢復服務。

```text
   最後一次可用的資料點          故障發生                     服務恢復
           │                         │                            │
───────────●─────────────────────────✕────────────────────────────●──────► 時間
           │◄──────── RPO ──────────►│◄────────── RTO ───────────►│
             這段時間的資料會遺失        這段時間服務無法使用
```

左段是 RPO：從最後一個能恢復的資料點到故障發生，這段時間寫入的資料會遺失。右段是 RTO：從故障到恢復服務的時間。

RPO 由「資料多久被複製或備份一次」決定：每天備份一次，RPO 最壞就是 24 小時；同步複寫，RPO 接近 0。RTO 由「恢復要做多少事」決定：從備份重建整個環境可能要好幾小時；已經有一套隨時待命的副本，切換只要幾分鐘。

**RPO 和 RTO 越小，成本越高。** 第 34 章會介紹四種 DR 策略（backup & restore、pilot light、warm standby、multi-site active-active），它們就是在 RTO／RPO 與成本之間的四個取捨點。考題常給你一組 RTO／RPO 和預算，要你選出「剛好滿足」的那一個。

## 4.10 Single point of failure：找出那個一壞全壞的元件

**SPOF（Single Point of Failure，單點故障）** 是指「只要它壞掉，整個系統就停擺」的元件。Wanderly 的第一版架構處處是 SPOF：唯一的 EC2、唯一的資料庫、唯一的磁碟。

消除 SPOF 的原則是「重要元件至少兩份，而且放在不同的 **fault domain（故障範圍）**」。AWS 上由小到大的故障範圍是：

1. **單一 instance 或硬體**：用多台 instance 分擔，壞一台自動替換（Auto Scaling，第 18 章）。
2. **單一 AZ**：資源分散到至少兩個 AZ，例如 Multi-AZ 資料庫、跨 AZ 的 Load Balancer。
3. **單一 Region**：極端情況下的整個 Region 問題，需要跨 Region 的 DR 架構（第 34、42 章）。

有些 SPOF 很隱蔽，常出現在考題裡：

- 兩個 AZ 的應用程式都依賴**同一個 AZ 的 NAT Gateway**（第 5 章）。
- DNS 記錄只指向**一台機器的 IP**，那台機器換掉就全斷。
- 所有伺服器都把 session 存在**某一台**機器的記憶體裡。
- 一個需要**人工**執行的恢復步驟，而會做的人正在休假。

> [!warning] 常見誤解
> 「我開了兩台 EC2，所以高可用。」如果兩台都在同一個 AZ，AZ 故障時會一起停擺；如果前面沒有 Load Balancer 做健康檢查與分流，一台壞了，送到它的請求仍然會失敗。高可用要同時具備「多份」「分散在不同故障範圍」「自動偵測並繞過故障」三個條件。

## 4.11 擴展：scale up、scale out 與 stateless 設計

促銷時 CPU 衝到 100%，有兩種擴展方向。

**Scale up（垂直擴展）** 是把機器換大：更多 CPU、更多記憶體。它簡單、不需要改程式，但有上限（最大的機型就那麼大），換機型通常需要重啟，而且仍然只有一台，SPOF 沒有消失。關聯式資料庫的寫入端常常只能 scale up。

**Scale out（水平擴展）** 是增加機器數量，把流量分給多台。它理論上沒有上限，也同時解決了 SPOF，是雲端架構的主流做法。搭配 Load Balancer 與 Auto Scaling，可以依流量自動增減機器數量（第 10、18 章）。

**Scalability（可擴展性）** 指「系統能透過增加資源來承接更多負載」；**elasticity（彈性）** 更進一步，指「依需求自動增加，需求下降時也自動減少」，只為實際用量付費。促銷結束後把多開的 20 台關掉，就是 elasticity 帶來的成本優勢。

### Scale out 的前提：stateless

要讓任何一台機器都能處理任何一個請求，機器本身不能保存「只有它知道」的資料，這種設計叫 **stateless（無狀態）**。**State（狀態）** 是指跨請求需要記住的資料，例如登入 session、購物車、上傳到一半的檔案。

如果 session 存在 A 機器的記憶體裡，下一個請求被分到 B 機器，使用者就被登出了；Auto Scaling 在離峰關掉 A 機器時，A 上的所有 session 也一起消失。解法是把狀態搬出去：

| 狀態 | 搬到哪裡 | 章節 |
|---|---|---|
| 登入 session、購物車 | ElastiCache 或 DynamoDB | 第 18、27、28 章 |
| 使用者上傳的檔案 | S3 | 第 22 章 |
| 多台機器共用的檔案 | EFS | 第 24 章 |
| 交易資料 | RDS／Aurora／DynamoDB | 第 26、27 章 |

Load Balancer 也提供 **sticky sessions（黏著連線）**，把同一位使用者固定送到同一台機器。它可以作為過渡手段，但機器被終止時 session 仍會遺失，而且會讓負載不平均，不能取代真正的 stateless 設計。

### 資料庫怎麼擴展

應用程式容易 scale out，資料庫比較難，常見手段依序是：先用 cache 擋掉重複的讀取；再用 read replica 分擔讀取；寫入真的撐不住時，才考慮把資料依某個 key 切到多個資料庫（**sharding，分片**），或改用天生水平擴展的 DynamoDB。第 35 章會完整討論這些手段。

## 4.12 Loose coupling：別讓一個慢元件拖垮整個系統

訂房成功後，Wanderly 要寄確認信、通知旅館、更新推薦系統。第一版的寫法是：訂房 API 依序呼叫這三個服務，全部完成才回應使用者。某天寄信服務變慢，每封信要 10 秒，訂房 API 就跟著卡住，最後整個網站的連線被佔滿，連搜尋都打不開。

這就是 **tight coupling（緊密耦合）**：元件之間直接、同步地依賴，一個慢了或壞了，故障會一路傳染上去。**Loose coupling（鬆散耦合）** 則讓元件透過中間層溝通，彼此不需要知道對方是否存在、是否正常、處理得多快。

### 同步 vs 非同步通訊

**同步通訊**：呼叫方送出請求後，等待對方回應才繼續，例如一般的 HTTP API 呼叫。簡單直覺，適合「需要立刻知道結果」的情境（查房價、驗證付款）。

**非同步通訊**：呼叫方把訊息交給一個中介（例如 **queue，佇列**），立刻繼續做自己的事；另一端的 **consumer（消費者）** 依自己的速度把訊息取出處理。

```text
同步（緊密耦合）
使用者 ─► 訂房 API ─► 寄信服務（慢 10 秒）─► 回應 ─► 使用者等 10 秒以上

非同步（鬆散耦合）
使用者 ─► 訂房 API ──① 寫入訂單──► 資料庫
               │
               ├──② 放一則「訂單已成立」訊息──► [Queue]
               │                                  │ ④ 依自己的速度取出
               ▼                                  ▼
       ③ 立即回應「訂房成功」               寄信 worker、旅館通知 worker
```

① 訂房 API 只做必須同步完成的事：把訂單寫進資料庫。② 把後續工作包成訊息放進 queue。③ 立刻回應使用者。④ 寄信 **worker**（在背景專門處理某類工作的程式）依自己的速度處理；即使它暫時掛掉，訊息也會留在 queue 裡等它恢復，不會遺失，也不會拖累訂房。

非同步帶來三個好處：**削峰**（促銷時訊息先堆在 queue，worker 慢慢消化）、**故障隔離**（下游壞了不影響上游）、**獨立擴展**（queue 很長時就多開 worker）。代價是：結果不是立刻完成（使用者要晚幾秒收到信）、要處理重複訊息（多數 queue 保證「至少送達一次」，所以 consumer 要設計成重複處理也不會出錯，稱為 **idempotent，冪等**），以及除錯時要追蹤跨元件的流程。

AWS 上的非同步元件（第 31、32、33 章）：

- **SQS**：queue，一則訊息由一個 consumer 處理，最典型的削峰與解耦工具。
- **SNS**：publish／subscribe（發布／訂閱），一則訊息同時推送給多個訂閱者。
- **EventBridge**：事件匯流排，依規則把事件送往不同目標。
- **Kinesis**：大量、需保持順序的資料串流。
- **Step Functions**：把多個步驟組成有重試與錯誤處理的工作流程。

## 4.13 組起來：Wanderly 的下一版架構

把本章的觀念套回故事開頭的三個事故，Wanderly 的架構演進成這樣：

```text
                   使用者
                     │
             [Load Balancer]（跨兩個 AZ）
              │                │
   AZ-a ┌─────▼─────┐   ┌──────▼────┐ AZ-c
        │ Web/App ① │   │ Web/App ① │   ← stateless，Auto Scaling 依流量增減
        └──┬───┬──┬─┘   └──┬───┬──┬─┘
           │   │  │ ⑤      │   │  │
           │   │  └────────┼───┼──┴──► [Queue] ──► 寄信／通知 worker
           │   │ ③         │   │
           │   └──► [Cache：session、熱門查詢]
           │ ②             │
        ┌──▼────────┐ 同步  ┌▼──────────┐
        │ DB primary│─────►│ DB standby│   ← Multi-AZ，自動 failover
        └───────────┘      └───────────┘
                     ④ 照片 ──► [Object storage（S3）]
```

① 應用程式 stateless、跨兩個 AZ、由 Load Balancer 分流並自動擴展，消除了「一台機器」的 SPOF，也解決促銷時的 CPU 瓶頸。② 資料庫用同步複寫的 standby 放在另一個 AZ，主機故障時自動切換，RPO 接近 0、RTO 只有幾分鐘；另外每天備份並啟用 PITR，防止「資料被改壞」。③ Session 與熱門查詢放在 cache，讓應用程式可以任意增減。④ 照片改存 object storage，容量不再是問題。⑤ 寄信等後續工作透過 queue 非同步處理，下游變慢不再拖垮訂房。

這張圖裡的每個方框，Part 1 到 Part 7 都會用一到兩章把它講透。

## 4.14 比較與選型

### 我的資料該放哪裡？

```text
這份資料是什麼？
├─ 檔案（照片、影片、文件、備份、log）
│    ├─ 要讓多台伺服器用一般檔案路徑同時讀寫？ → File storage（EFS／FSx）
│    └─ 其他情況，尤其要大量、便宜、可用 HTTP 存取 → Object storage（S3）
├─ 作業系統或資料庫底下的磁碟 → Block storage（EBS；暫存資料可用 instance store）
└─ 結構化的業務資料
     ├─ 需要交易、JOIN、彈性 SQL 查詢 → Relational（RDS／Aurora）
     ├─ 存取模式固定、規模極大、要穩定低延遲 → NoSQL（DynamoDB）
     ├─ 只是想讓讀取更快，正本另有存放 → Cache（ElastiCache）
     └─ 大量歷史資料做彙總分析 → Data warehouse（Redshift／Athena）
```

### 易混淆觀念對照

| 一組觀念 | 差別 | 一句話 |
|---|---|---|
| Availability vs durability | 現在能不能用 vs 資料會不會遺失 | 連不上不代表資料丟了 |
| 同步 vs 非同步複寫 | 等不等副本確認 | 同步換零遺失，非同步換速度與距離 |
| Replication vs backup | 複製現在 vs 保存過去 | 複寫會同步錯誤，備份才能回到過去 |
| RPO vs RTO | 遺失多少資料 vs 停機多久 | P 是資料點（Point），T 是時間（Time） |
| Scale up vs scale out | 換大機器 vs 加機器 | Scale out 同時解決容量與 SPOF |
| Scalability vs elasticity | 能擴展 vs 自動伸縮 | Elasticity 也包含「縮」 |
| Strong vs eventual consistency | 一定讀到最新 vs 最終會一致 | 剛寫完要讀，就要強一致或讀主庫 |
| 同步 vs 非同步通訊 | 等結果 vs 交給 queue | 不需要立即結果的工作就非同步 |

## 4.15 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 多台 Linux 伺服器共用檔案、用檔案路徑存取 | File storage → EFS |
| 大量圖片／影片、容量無上限、用 HTTP 存取 | Object storage → S3 |
| 資料庫或開機磁碟、低延遲 | Block storage → EBS |
| 暫存、重開機可遺失、最高 IOPS | Instance store |
| 主資料庫故障自動切換、同 Region、不能遺失資料 | 同步複寫 → RDS Multi-AZ |
| 讀取量大、主資料庫 CPU 高 | Read replica、cache |
| 剛寫入就要讀到最新資料 | Strong consistency 或讀主資料庫 |
| 誤刪資料要恢復到某個時間 | 備份／PITR，不是 replication |
| 可重新產生的資料、要省錢 | 單 AZ 儲存（S3 One Zone-IA） |
| Auto Scaling 縮減後使用者被登出 | Session 外部化（ElastiCache／DynamoDB），stateless |
| 下游變慢拖垮整個系統、流量尖峰 | 用 queue 解耦（SQS） |
| 一則事件要通知多個系統 | Pub/sub（SNS、EventBridge） |
| 工作超過 15 分鐘、不想管伺服器 | 不是 Lambda；考慮 Fargate、AWS Batch |
| RPO／RTO 數字 + 最低成本 | 選「剛好滿足」的 DR 策略（第 34 章） |

**常見陷阱**：

1. 把 Multi-AZ 當成讀取擴展：傳統 Multi-AZ instance 部署的 standby 不能承接讀取，擴展讀取要用 read replica。
2. 以為 replication 可以取代備份：誤刪、程式錯誤會被同步到所有副本。
3. 把 availability 和 durability 混為一談：S3 的 11 個 9 是耐久性，不是可用性。
4. 用 sticky sessions 解決 session 遺失：instance 被終止時 session 仍然消失。
5. 把 cache 當成資料正本：cache 的資料可能過期或被清除。
6. 以為兩台 instance 就是高可用：還要分散在不同 AZ，並有自動偵測與繞過故障的機制。

## 4.16 SAP 預告：從單一 workload 到整個組織

SAA 問的是「這個應用程式怎麼做到高可用」，SAP 會把同樣的觀念放大：跨 Region 的非同步複寫要怎麼處理寫入衝突（第 42 章）、整個組織的備份政策怎麼統一並防止被刪（第 43 章）、遷移一個 Oracle 資料庫時要怎麼在最小停機下切換（第 45 章）。RTO／RPO 不再只是一個應用程式的數字，而是數百個系統要分級管理。本章的語彙是這些題目的共同基礎。

## 本章重點整理

- VM 給你完整控制但營運負擔最高；container 打包一致、啟動快但需要編排；serverless 只管程式碼，但有執行時間等限制（Lambda 最長 15 分鐘）。
- Block storage 是單機使用的低延遲磁碟（EBS、instance store），file storage 是多台機器共用的檔案系統（EFS、FSx），object storage 是以 key 透過 HTTP 存取、容量幾乎無上限的倉庫（S3）。
- Relational database 擅長交易與 JOIN，NoSQL 擅長已知存取模式下的大規模低延遲，cache 加速讀取但不是資料正本，data warehouse 專為大量資料分析。
- ACID 保證交易全做或全不做、符合規則、彼此隔離、成功後不遺失；它的 C 和副本一致性的「一致」意義不同。
- Strong consistency 保證讀到最新寫入，eventual consistency 允許短暫讀到舊值；S3 提供 strong read-after-write consistency，DynamoDB 讀取預設最終一致。
- 同步複寫不遺失已確認的寫入但較慢，用於同 Region 跨 AZ 的 failover（RDS Multi-AZ）；非同步複寫快且能跨 Region，但有 lag 與資料遺失風險（read replica）。
- Replication 會同步錯誤與刪除，不能取代備份；回到過去某個時間點要靠 snapshot、PITR、versioning。
- Availability 是能不能用，durability 是資料會不會遺失；每多一個 9，允許的停機時間縮小十倍。
- 串聯元件的可用性相乘而下降，互相獨立的備援並聯可大幅提高可用性，所以要跨 AZ 部署。
- SLA 是對客戶的承諾、SLO 是內部目標、SLI 是實際量測；AWS SLA 未達成時提供服務抵用金，不是不會故障的保證。
- RPO 是可接受遺失多少資料，RTO 是可接受停機多久；兩者越小成本越高。
- 消除 SPOF 要「多份、分散在不同 fault domain、自動偵測並繞過故障」，並留意隱藏的 SPOF。
- Scale out 同時解決容量與 SPOF，前提是 stateless；session、檔案等狀態要搬到 cache、資料庫或 S3。
- Loose coupling 用 queue 等中介把同步呼叫改成非同步，帶來削峰、故障隔離與獨立擴展，代價是延後完成與需要冪等處理。

## 本章練習題

### 練習 4-1｜SAA｜單選｜使用者上傳照片的儲存選擇

Wanderly 的旅館照片目前存在單一 EC2 的 EBS volume 上，磁碟空間經常不足。照片總量預計每年成長數十 TB，使用者的瀏覽器需要透過 HTTPS 直接下載照片，未來網站伺服器也會增加到多台。團隊希望容量不需要預先規劃，並以最低成本達成。

照片應該存放在哪裡？

- A. 為 EC2 掛載更大的 EBS volume，並設定每月擴充一次
- B. Amazon S3，以物件形式儲存照片，並由應用程式產生網址提供下載
- C. 每台 EC2 的 instance store，以取得最高的讀取效能
- D. 在 EC2 上自行架設 NFS 伺服器，讓所有網站伺服器掛載同一個目錄

> [!answer]- 答案：B
> **A ✗** EBS 是 block storage，容量需要事先配置並為整個配置大小付費，仍然只掛在單一 AZ 的機器上，無法解決「不想預先規劃容量」與多台伺服器共用的問題。
>
> **B ✓** 照片是「整個上傳、整個下載」的檔案，正是 object storage 的典型用途。S3 容量實際上沒有上限、按實際用量計費、資料跨多個 AZ 儲存，並能透過 HTTPS 直接提供下載，網站伺服器也因此保持 stateless。
>
> **C ✗** Instance store 的資料在 instance 停止或終止時會消失，不能存放唯一的一份使用者照片。
>
> **D ✗** 自建 NFS 伺服器本身就是一個新的 SPOF，還要自己管理容量與備份，營運負擔和成本都高於 S3。
>
> **考點**：SAA-3.1、SAA-4.1｜block、file、object storage 的選擇

### 練習 4-2｜SAA｜單選｜多台伺服器共用檔案系統

Wanderly 有一套舊的旅館合約管理系統，程式以一般的 Linux 檔案路徑讀寫 `/data/contracts` 目錄下的檔案，會頻繁修改既有檔案。系統要擴充為分布在兩個 AZ 的 4 台 EC2，所有機器必須同時讀寫同一批檔案，團隊不希望修改程式。

最合適的儲存方案是什麼？

- A. 把檔案搬到 S3，並把程式中的檔案路徑直接改成 S3 key
- B. 為每台 EC2 各掛載一個 EBS volume，並每小時用 snapshot 互相同步
- C. 使用 instance store 並在 4 台 EC2 之間設定 rsync 同步
- D. 建立 Amazon EFS 檔案系統，在每個 AZ 建立 mount target，讓 4 台 EC2 都以 NFS 掛載到 `/data/contracts`

> [!answer]- 答案：D
> **A ✗** S3 是透過 API 存取的 object storage，不是檔案系統；程式必須改寫成呼叫 S3 API，而且無法原地修改檔案的一部分，違反「不修改程式」。
>
> **B ✗** EBS volume 一般只掛在一台 instance，各自的 volume 是不同的資料；用 snapshot 同步會有延遲與衝突，而且 volume 綁定單一 AZ。
>
> **C ✗** Instance store 的資料在 instance 停止或終止時消失，rsync 同步也無法正確處理多台同時寫入同一檔案的衝突。
>
> **D ✓** 需求是「多台機器、跨 AZ、用一般檔案路徑同時讀寫」，正是 file storage 的用途。EFS 提供 NFS 共享檔案系統，資料跨多個 AZ 儲存，應用程式不需修改即可掛載使用。
>
> **考點**：SAA-3.1｜file storage 與共享存取

### 練習 4-3｜SAA｜單選｜AZ 故障時不遺失訂單

Wanderly 的訂單資料庫是單一 AZ 的 RDS for MySQL，每天凌晨做一次自動備份。管理層新訂的要求是：資料庫所在 AZ 發生故障時，已經回報成功的訂單不能遺失，並且要在幾分鐘內自動恢復寫入，不需要人工介入。

哪個做法最能滿足需求？

- A. 啟用 RDS Multi-AZ，讓 AWS 在另一個 AZ 維護同步複寫的 standby，並在主資料庫故障時自動 failover
- B. 把自動備份改為每小時一次，故障時從最新備份還原
- C. 在另一個 Region 建立 read replica，故障時手動 promote
- D. 把 RDS instance 換成更大的機型，以降低故障機率

> [!answer]- 答案：A
> **A ✓** Multi-AZ 用同步複寫，主資料庫要等 standby 確認才回報寫入成功，所以故障時已確認的訂單不會遺失（RPO 接近 0）；AWS 會自動 failover 並把資料庫 DNS 名稱指向新主機，通常在 1–2 分鐘內恢復，符合 RTO 與「不需人工」的要求。
>
> **B ✗** 每小時備份最壞仍會遺失近一小時的資料，從備份還原也需要人工操作且耗時，RPO 與 RTO 都不符合。
>
> **C ✗** 跨 Region read replica 是非同步複寫，故障時可能遺失 lag 期間的資料；而且需要手動 promote 並修改應用程式連線，不符合「不遺失」與「自動恢復」。它適合跨 Region DR，不是同 Region 的 AZ 故障。
>
> **D ✗** 換大機型只是 scale up，依然是單一 AZ 的單一資料庫，AZ 故障時照樣停擺，SPOF 沒有消除。
>
> **考點**：SAA-2.2｜同步複寫、RPO／RTO 與 Multi-AZ

### 練習 4-4｜SAA｜單選｜付款後看不到剛建立的訂單

Wanderly 為了分散讀取壓力，建立了 RDS read replica，並把所有 `SELECT` 查詢改成送到 replica。之後客服接到大量反映：使用者付款完成跳轉到「我的訂單」頁面時，有時看不到剛剛那筆訂單，重新整理幾秒後才出現。

最合適的修正方式是什麼？

- A. 把 read replica 換成更大的機型，讓它處理得更快
- B. 刪除 read replica，所有讀寫都回到主資料庫
- C. 讓付款完成後的「我的訂單」查詢讀取主資料庫，其他對即時性不敏感的查詢繼續使用 read replica
- D. 把 read replica 改為 Multi-AZ standby，並讓查詢讀取 standby

> [!answer]- 答案：C
> **A ✗** Read replica 使用非同步複寫，lag 的根本原因是「寫入後才複製」，加大機型可能稍微縮短 lag，但無法保證剛寫入的資料立刻可讀。
>
> **B ✗** 能解決問題，但完全放棄了讀取擴展，主資料庫的壓力回到原點，過度修正。
>
> **C ✓** 這是 read-your-writes 需求：剛寫入就要讀到。只把這類關鍵流程導向主資料庫（強一致），其他可以容忍幾秒延遲的查詢（例如旅館列表）繼續由 replica 分擔，同時兼顧正確性與效能。
>
> **D ✗** 傳統 RDS Multi-AZ instance 部署的 standby 不能承接讀取，它只負責 failover。
>
> **考點**：SAA-3.3｜非同步複寫的 replication lag 與 read-your-writes

### 練習 4-5｜SAA｜單選｜串聯元件的整體可用性

Wanderly 的訂房流程必須依序經過三個元件才能完成：前端服務、訂房服務、付款服務，任何一個無法使用，訂房就會失敗。三個元件的可用性各為 99.9%，故障彼此獨立。產品經理認為「每個元件都是三個 9，所以整個訂房流程也是三個 9」。

關於整體可用性，哪個敘述最正確？

- A. 整體約為 99.7%，因為串聯元件的可用性要相乘；要提高整體可用性，應為各元件建立分散在不同 AZ 的獨立備援
- B. 整體仍為 99.9%，因為可用性取決於最弱的元件
- C. 整體約為 99.97%，因為三個元件互相備援
- D. 整體約為 99.99%，因為三個元件分散了風險

> [!answer]- 答案：A
> **A ✓** 三個元件都要正常才能完成訂房，屬於串聯，整體可用性 = 0.999 × 0.999 × 0.999 ≈ 99.7%，每年可能停機約一天。改善方式是讓每個元件都有互相獨立、分散在不同 AZ 的多份備援（並聯），提高單一元件的可用性。
>
> **B ✗** 「取決於最弱元件」低估了風險；即使三個一樣可靠，每個元件的故障都會讓流程失敗，故障機率會累加。
>
> **C ✗** 三個元件做的是不同的事，不能互相替代，因此不是備援（並聯）關係。
>
> **D ✗** 串聯只會讓整體可用性低於任一元件，不可能更高。
>
> **考點**：SAA-2.2｜可用性的串聯與並聯

### 練習 4-6｜SAA｜單選｜Auto Scaling 縮減後使用者被登出

Wanderly 的網站在 Application Load Balancer 後面使用 Auto Scaling group，登入 session 存在各台 EC2 的記憶體中，並啟用了 sticky sessions。每天深夜 Auto Scaling 縮減 instance 數量時，總有一批使用者被強制登出，購物車也被清空。

哪個做法能根本解決問題，並讓網站可以自由擴展？

- A. 延長 sticky sessions 的 cookie 有效時間
- B. 把 session 資料存放到 Amazon ElastiCache 等外部共享儲存，讓每台 EC2 都成為 stateless
- C. 關閉 Auto Scaling 的縮減，讓 instance 數量只增不減
- D. 把每台 EC2 的 session 定期寫到自己的 EBS volume

> [!answer]- 答案：B
> **A ✗** Sticky sessions 只是把使用者固定送到同一台機器；那台機器被終止時，記憶體中的 session 依然消失，延長 cookie 時間無濟於事。
>
> **B ✓** 把狀態搬出應用伺服器，任何一台 EC2 都能處理任何請求，Auto Scaling 增減機器不再影響使用者。ElastiCache 提供低延遲的共享 session 儲存（DynamoDB 也是常見選擇）。
>
> **C ✗** 不縮減可以避免登出，但失去 elasticity，離峰時為閒置機器付費，而且 instance 因故障被替換時問題仍會發生。
>
> **D ✗** EBS volume 綁在各自的 instance 上，其他機器讀不到；instance 被終止時預設也會刪除根 volume，問題沒有解決。
>
> **考點**：SAA-2.1、SAA-3.2｜stateless 設計與 session 外部化

### 練習 4-7｜SAA｜單選｜下游變慢拖垮訂房

Wanderly 的訂房 API 在寫入訂單後，會同步呼叫寄信服務寄出確認信，等寄信完成才回應使用者。促銷期間寄信服務變慢，每次呼叫要 8 秒，訂房 API 的連線因此被佔滿，連帶造成網站其他功能逾時。業務上，確認信晚幾分鐘寄出可以接受。

哪個做法最能解決問題，且營運負擔最低？

- A. 把寄信服務的 EC2 換成更大的機型
- B. 把訂房 API 呼叫寄信服務的逾時時間從 10 秒延長到 60 秒
- C. 在訂房 API 中加入重試，寄信失敗時自動重送三次再回應使用者
- D. 訂房 API 寫入訂單後，把寄信工作送入 Amazon SQS queue 並立即回應使用者，由寄信 worker 依自己的速度從 queue 取出處理

> [!answer]- 答案：D
> **A ✗** Scale up 可能暫時改善，但兩者仍是同步、緊密耦合的關係；下次寄信服務因其他原因變慢，訂房還是會被拖垮。
>
> **B ✗** 延長逾時只會讓連線佔用更久，更快耗盡訂房 API 的資源，讓問題更嚴重。
>
> **C ✗** 在同步路徑上重試會讓使用者等更久，並對已經過載的寄信服務施加更多壓力。
>
> **D ✓** 寄信不需要立即結果，適合非同步處理。SQS 是受管的 queue，可以吸收尖峰、隔離下游故障；寄信 worker 依 queue 長度獨立擴展。由於 queue 可能重複送出訊息，worker 應設計成冪等，避免重複寄信。
>
> **考點**：SAA-2.1｜loose coupling 與非同步通訊

### 練習 4-8｜SAA｜選兩項｜依耐久性需求選擇儲存

Wanderly 每天收到數萬張旅館原始照片，並由程式自動產生多種尺寸的縮圖。原始照片是唯一的一份，遺失就無法取得；縮圖隨時可以從原始照片重新產生。團隊想在符合耐久性需求的前提下降低儲存成本。

哪兩個做法最合適？（選兩項）

- A. 原始照片存放在 S3 Standard，資料跨多個 AZ 儲存，提供 11 個 9 的設計耐久性
- B. 原始照片存放在 S3 One Zone-IA，以取得最低的單價
- C. 原始照片與縮圖都存放在 EC2 的 instance store，以取得最高效能
- D. 縮圖存放在 S3 One Zone-IA，即使單一 AZ 損毀導致縮圖遺失，也能從原始照片重新產生
- E. 縮圖存放在 io2 EBS volume，並啟用 Multi-Attach 讓所有伺服器讀取

> [!answer]- 答案：A、D
> **A ✓** 原始照片不可重新取得，需要最高的耐久性。S3 Standard 把資料存放在多個 AZ，單一 AZ 損毀不會造成資料遺失。
>
> **B ✗** One Zone-IA 只把資料存放在單一 AZ，該 AZ 損毀時資料可能遺失，不適合唯一一份、不可重建的資料。
>
> **C ✗** Instance store 在 instance 停止或終止時資料就消失，完全不適合長期保存。
>
> **D ✓** 縮圖可以重新產生，能接受較低的耐久性與可用性，One Zone-IA 的較低價格正好符合「可重建資料」的情境。
>
> **E ✗** EBS 是 block storage，以配置容量計費且成本遠高於 S3；Multi-Attach 也限制在同一個 AZ 與特定 volume 類型，不是提供大量圖片給網站讀取的方式。
>
> **考點**：SAA-4.1｜durability 需求與儲存成本

### 練習 4-9｜SAA｜選兩項｜讀取量大的資料庫擴展

Wanderly 的 RDS for PostgreSQL 主資料庫 CPU 長期超過 85%。分析顯示 90% 的查詢是讀取，其中大部分是「熱門城市的旅館列表」，內容每幾分鐘才變動一次；寫入量不高。資料庫已經以 Multi-AZ instance 部署（一個 primary 加一個 standby）運作。團隊希望降低主資料庫負載，並盡量不要更換資料庫引擎。

哪兩個做法最合適？（選兩項）

- A. 讓應用程式把讀取查詢送到 Multi-AZ 的 standby
- B. 建立一或多個 RDS read replica，把可以容忍些微延遲的讀取查詢導向 replica
- C. 把資料庫遷移到 Amazon Redshift，以取得更好的查詢效能
- D. 把主資料庫的備份頻率提高到每小時一次
- E. 使用 Amazon ElastiCache 快取熱門城市的旅館列表，並設定適當的 TTL

> [!answer]- 答案：B、E
> **A ✗** 傳統 RDS Multi-AZ instance 部署的 standby 只用於 failover，不能承接讀取查詢。這是最常見的考試陷阱。
>
> **B ✓** Read replica 透過非同步複寫取得資料，可以分擔讀取流量；旅館列表能容忍幾秒的 lag，很適合交給 replica。
>
> **C ✗** Redshift 是為大量資料分析設計的 data warehouse，不適合訂房系統高頻率的小筆查詢，也等於更換資料庫。
>
> **D ✗** 備份頻率影響 RPO，與降低讀取負載無關，反而可能增加負擔。
>
> **E ✓** 內容幾分鐘才變一次的熱門查詢非常適合快取。ElastiCache 從記憶體回應，大幅減少打到資料庫的查詢；TTL 讓快取定期更新，資料正本仍在資料庫中。
>
> **考點**：SAA-3.3｜read replica、cache 與 Multi-AZ 的用途差異

### 練習 4-10｜SAA｜單選｜長時間批次工作的運算選擇

Wanderly 每天凌晨要執行一個對帳程式，讀取前一天的所有訂單並與金流商的報表比對，執行時間約 40 分鐘，已經打包成 container image。其他時間不需要任何運算資源。團隊希望營運負擔最低，並且只為實際執行的時間付費。

最合適的做法是什麼？

- A. 改寫成 AWS Lambda 函式，由排程每天觸發一次
- B. 準備一台 24 小時運作的 EC2，用 cron 每天凌晨執行對帳程式
- C. 以 Amazon EventBridge Scheduler 每天觸發一個 Amazon ECS task，使用 AWS Fargate 執行該 container image
- D. 建立一個 EKS cluster 與一組常駐的 EC2 worker node，用 Kubernetes CronJob 執行

> [!answer]- 答案：C
> **A ✗** Lambda 單次執行最長 15 分鐘，40 分鐘的工作會被中斷；若要改寫成多段函式，還要額外處理拆分與狀態。
>
> **B ✗** EC2 全天運作，但一天只用 40 分鐘，絕大部分時間在為閒置付費，還要自己管理作業系統修補。
>
> **C ✓** 工作已經是 container image，Fargate 不需要管理伺服器，只在 task 執行期間依資源計費；排程觸發 ECS task 是執行定時批次工作的標準做法，沒有 15 分鐘限制。
>
> **D ✗** EKS 可以執行 CronJob，但要維護 cluster 與常駐的 worker node，營運負擔與成本都比 Fargate 高，對單一個每日工作過度設計。
>
> **考點**：SAA-3.2、SAA-4.2｜VM、container、serverless 的選擇
