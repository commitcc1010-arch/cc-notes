# 第 48 章　案例：全球電商平台

> [!abstract] 本章地圖
> **你會學到**：
> - 把一份「促銷 30 倍尖峰、不可超賣、不可重複扣款、全球低延遲」的需求，拆成每一層各自要解決的問題
> - 先畫出 SAA 等級的單 Region 解法，再說明它在哪些地方撐不住，以及怎麼演進到 SAP 等級的多 Region 架構
> - 為限量庫存、訂單非同步處理、圖片與影片處理管線選擇正確的 AWS 元件，並說明「為什麼不選另一個」
> - 用故障演練檢查架構：AZ 故障、快取節點故障、資料庫 failover、毒訊息、整個 Region 不可用
> - 用「每筆成功訂單的成本」而不是「每月帳單總額」思考電商架構的成本
>
> **前置知識**：第 10 章（ALB）、第 11 章（CloudFront）、第 18 章（Auto Scaling）、第 21 章（ECS）、第 26 章（Aurora）、第 28 章（ElastiCache）、第 32 章（SQS）、第 34 章（DR 策略）、第 42 章（多 Region 架構）
> **考試比重**：SAA ★★★（Domain 2、3）｜SAP ★★★（Domain 2 新解決方案設計、Domain 3 改善既有架構）

## 48.1 故事：一元房的那一夜

Wanderly 在台灣站穩腳步後，推出了新業務「Wanderly Deals」：和旅館合作的限時搶購。第一場活動的主打是「東京新宿一元房」，限量 500 間，晚上八點整開賣。行銷團隊在社群上預告了一週，結果開賣前五分鐘，網站流量從平常的每秒 3,000 個請求衝到每秒 9 萬個。

那一晚發生了三件事。第一，商品頁在八點前就開始逾時，因為每個使用者都在狂按重新整理，而每一次重新整理都打到資料庫。第二，資料庫上那一列「剩餘房數」被幾萬個交易同時搶著鎖定，等待時間一路拉長，最後應用程式的連線池耗盡。第三，好不容易撐到活動結束，客服發現賣出了 517 間房，有 17 位客人付了錢卻沒有房間；還有 40 多位客人因為按了兩次「付款」，被扣了兩次款。

技術主管小林在事後檢討會上把問題寫在白板上：讀取流量沒有被擋在前面、庫存扣減設計錯誤、付款沒有冪等性。同時，公司已經決定明年進軍日本、東南亞與美國，要求商品頁在這些市場都要快，而且東京 Region 出事時，訂單服務要能在 15 分鐘內在另一個 Region 恢復。

這一章不重新教 CloudFront、Aurora 或 SQS 的基礎，那些分別在第 11、26、32 章。我們要做的是把它們組起來：先列需求與限制，再畫 SAA 等級的解法，接著演進到 SAP 等級的全球架構，並用設計決策紀錄、故障演練與成本分析檢查每一個選擇。

## 48.2 需求與限制

設計之前，先把需求寫成可以驗證的數字。模糊的「要很快、要穩」沒辦法拿來做選型；「商品頁 p95 小於 300 毫秒」才可以。

| 類別 | 需求 | 這條需求會逼出什麼設計 |
|---|---|---|
| 流量 | 平日 3,000 RPS，開賣前後 10 分鐘內到 9 萬 RPS，其中 95% 是瀏覽 | 讀取必須在 edge 與快取吸收，不能讓尖峰直接打到資料庫 |
| 延遲 | 台灣、日本、東南亞、美國的商品頁 p95 < 300 ms | 全球 CDN；之後要有第二個 Region 服務美國 |
| 正確性 | 限量庫存不可超賣；同一筆付款不可重複扣款 | 庫存需要原子扣減；付款需要冪等性設計 |
| 可用性 | 單一 AZ 故障不影響下單；Region 故障時訂單服務 RTO 15 分鐘、RPO 1 分鐘 | SAA 階段 Multi-AZ；SAP 階段 warm standby |
| 媒體 | 旅館上傳最大 2 GB 的宣傳影片與大量照片，10 分鐘內要轉成多種解析度 | 直傳 S3、事件驅動、受管轉碼 |
| 合規 | 信用卡號不得經過或儲存在 Wanderly 系統 | 使用金流商的 tokenization，詳見第 50 章與第 43 章 |
| 團隊 | 12 位工程師，沒有專職 DBA 或維運 | 優先選受管服務，降低營運負擔 |

這張表有一個重要的觀察：**不同的流量有完全不同的性質**。瀏覽是讀多、可快取、可以容忍幾秒鐘的舊資料；扣庫存是寫入、不可快取、必須強一致；付款是呼叫外部系統、可能逾時、必須可安全重試；媒體處理是長時間的批次工作、可以排隊。把這四種流量混在同一條路徑上，正是那一夜失敗的根本原因。好的電商架構會**讓每一種流量走自己的路**。

## 48.3 SAA 等級解法：單 Region 的穩固基礎

第一階段，Wanderly 只在東京（`ap-northeast-1`）一個 Region，目標是撐住尖峰、不超賣、不重複扣款，並且撐過單一 AZ 故障。

```text
使用者（瀏覽器／App）
   │ ① HTTPS
   ▼
[CloudFront + AWS WAF]──────────────► [S3：商品圖片、前端靜態檔]（OAC）
   │ ② 動態請求：/api/*
   ▼
[ALB]（public subnet，跨 3 AZ）
   │ ③
   ▼
[ECS on Fargate：catalog / cart / checkout 服務]（private subnet，跨 3 AZ）
   │ ④ 讀取              │ ⑤ 扣庫存            │ ⑥ 送出訂單
   ▼                     ▼                     ▼
[ElastiCache Valkey]  [DynamoDB：庫存計數]  [SQS：orders queue] ──► DLQ
   │ cache miss                                 │ ⑦
   ▼                                            ▼
[Aurora MySQL：writer + 2 readers]◄──── [訂單 worker（ECS）] ──⑧──► 外部金流 API
```

① 所有使用者流量先進 CloudFront。圖片、JavaScript、CSS 由 S3 提供，CloudFront 透過 **OAC（Origin Access Control）** 存取私有 bucket（第 11、22 章），WAF 掛在 CloudFront 上擋常見攻擊與機器人（第 16 章）。

② 動態 API 也走 CloudFront，但使用不同的 cache behavior：`/api/catalog/*` 可以快取數秒，`/api/cart/*` 與 `/api/checkout/*` 完全不快取。這一點下一節會細講。

③ ALB 跨三個 AZ，把請求依路徑轉給不同的 ECS service（第 10、21 章）。選 Fargate 是因為團隊沒有人想管 EC2 叢集的 patch 與容量。

④ 商品資料採 **cache-aside**：先讀 ElastiCache，沒有才讀 Aurora reader 並寫回快取（第 28 章）。ElastiCache 使用 cluster mode 並開啟 Multi-AZ 自動 failover。

⑤ 限量商品的庫存不放在 Aurora，而是放在 DynamoDB，用條件式寫入原子扣減（48.5 節說明原因）。

⑥⑦ 扣庫存成功後，checkout 服務只做一件事：把訂單放進 SQS，立刻回應使用者「訂單處理中」。真正的寫 Aurora、呼叫金流，由 worker 依自己的速度消化（第 32 章）。

⑧ Worker 呼叫外部金流 API 時帶上 idempotency key，重試不會造成重複扣款（48.6 節）。

Aurora 使用一個 writer 加兩個 Aurora Replica，分散在不同 AZ；writer 故障時，Aurora 會把其中一個 replica 提升為新 writer，cluster endpoint 會指向它（第 26 章）。Fargate 任務也平均分布在三個 AZ。這樣一來，任何一個 AZ 故障，剩下兩個 AZ 都還有完整的每一層。

> [!note] 為什麼是三個 AZ 而不是兩個？
> 第 34 章介紹過 static stability：失去一個 AZ 後，剩下的容量要能撐住負載，而不是等 Auto Scaling 慢慢補。兩個 AZ 時，每個 AZ 平時要預留 100% 的容量（失去一半就剩一半）；三個 AZ 時，每個 AZ 預留 50% 即可（失去三分之一還有三分之二，每個 AZ 承擔 1.5 倍）。三個 AZ 總共只需要 150% 的容量，比兩個 AZ 的 200% 省。

## 48.4 促銷尖峰：讓瀏覽流量停在最前面

那一夜的第一個問題是讀取流量直達資料庫。解決方法是一層一層地吸收讀取，讓越後面的元件看到越少的流量。

**第一層：CloudFront 快取商品頁 API。** 商品名稱、照片、價格在活動期間幾乎不變，即使「剩餘房數」顯示晚個兩三秒也沒關係，因為真正的檢查發生在扣庫存那一步。所以 `/api/catalog/*` 可以設定很短的 TTL（例如 2–5 秒）。這個數字看起來很小，但在每秒 9 萬個請求的情況下，同一個商品頁在每個 edge location 每 5 秒只需要回源一次，origin 看到的流量會降低好幾個數量級。關鍵是 cache key 只包含真正會改變回應的東西（商品 ID、語系），不要包含 cookie 或 Authorization header，否則每個使用者都是不同的 cache key，命中率會歸零（第 11 章）。

> [!warning] 常見誤解
> 「所有 API 都放到 CloudFront 後面快取就能抗尖峰。」個人化的回應（購物車、訂單、會員資料）絕對不能用共用的 cache key 快取，否則 A 使用者會看到 B 使用者的購物車。正確做法是依路徑拆 behavior：可共享的內容積極快取，個人化與交易路徑使用 `CachingDisabled` 這類不快取的 policy。

**第二層：ElastiCache。** 穿過 CloudFront 的請求進到 catalog 服務，先查 ElastiCache。活動商品在開賣前就先寫進快取（cache warming），避免開賣瞬間大量 cache miss 同時打到 Aurora，也就是第 28 章的 cache stampede。熱門商品的 key 會成為 **hot key**：所有請求都落在同一個 shard。對策是在應用程式內再加一層極短 TTL 的本機快取，或把同一份資料複製成多個 key 分散到不同 shard。

**第三層：預先擴展，不要等自動擴展。** Target tracking 擴展需要先看到指標上升、再啟動新任務，從看到尖峰到新容量上線需要數分鐘，而促銷尖峰在幾十秒內就到頂。因為活動時間是事先知道的，Wanderly 使用 **scheduled scaling**：開賣前 30 分鐘把 ECS service 的最小任務數拉高、加開 Aurora Replica、確認 ElastiCache 容量（第 18、35 章）。同時要檢查 service quotas，例如帳號的 Fargate vCPU 配額，這些是預設值可以申請提高，但必須提前申請。

**第四層：入場控制（admission control）。** 即使瀏覽撐住了，500 間房不可能讓 9 萬人同時去搶。Wanderly 在開賣時啟用**虛擬等候室（virtual waiting room）**：使用者先拿到一個排隊號碼，系統依後端能承受的速度（例如每秒放行 2,000 人）發出有時效的入場 token，只有帶著有效 token 的請求才能呼叫 checkout API。AWS 有提供這個模式的參考解決方案，也可以用 API Gateway、Lambda 與 DynamoDB 自己實作。它的本質是第 35 章的 load shedding：與其讓所有人都慢，不如讓一部分人先等。

## 48.5 限量庫存：為什麼不在 Aurora 扣

那一夜的第二個問題是超賣與鎖競爭。原本的寫法是：

```sql
SELECT stock FROM inventory WHERE sku = 'TYO-1YEN';
-- 應用程式判斷 stock > 0
UPDATE inventory SET stock = stock - 1 WHERE sku = 'TYO-1YEN';
```

這段程式有兩個問題。第一，讀和寫是兩個獨立步驟，兩個交易可能同時讀到 `stock = 1`，然後都扣成功，這就是超賣的來源（race condition，競爭條件）。第二，就算改成單一的 `UPDATE ... WHERE stock > 0`，幾萬個交易仍然在搶**同一列的鎖**，每個交易都要排隊，延遲和連線數一起爆炸。

Wanderly 改成用 DynamoDB 的**條件式寫入（conditional write）**：

```bash
aws dynamodb update-item \
  --table-name FlashInventory \
  --key '{"pk": {"S": "TYO-1YEN#bucket-07"}}' \
  --update-expression "SET stock = stock - :one" \
  --condition-expression "stock >= :one" \
  --expression-attribute-values '{":one": {"N": "1"}}'
```

DynamoDB 在單一 item 上執行「檢查條件 + 更新」是原子的：條件不成立就回傳 `ConditionalCheckFailedException`，絕對不會扣成負數。但還有一個陷阱：第 27 章提過，DynamoDB 單一 partition 的寫入吞吐有上限（每秒約 1,000 WCU）。如果所有人都扣同一個 item，這個 item 會變成熱分割。所以 Wanderly 把 500 間房拆成 20 個 bucket（`bucket-00` 到 `bucket-19`），每個 bucket 25 間，使用者隨機挑一個 bucket 扣，扣不到（條件失敗）再換一個。這叫 **sharded counter（分片計數器）**。加上前一節的等候室把 checkout 速度限制在每秒 2,000 次，熱分割的壓力就被控制住了。

扣庫存成功不代表訂單成立，使用者還沒付款。所以實際寫入的不是「扣掉」，而是「保留」：用 DynamoDB 的 `TransactWriteItems` 把「條件式扣減 bucket」與「建立一筆 reservation item（記錄 `orderId`、`expiresAt` 為 10 分鐘後）」放在同一個交易裡，兩者要嘛一起成功、要嘛一起失敗，不會出現扣了庫存卻沒有保留紀錄的情況。付款成功就把 reservation 標記為確認；付款失敗或逾時，由一個排程的 Lambda 掃描過期 reservation，把庫存加回對應 bucket。這是第 33 章 saga 模式的**補償交易（compensating transaction）**。

> [!tip] 考試提示
> 題目出現「限量、不可超賣、高併發」時，看選項有沒有**原子的條件式更新**（DynamoDB condition expression、資料庫的單一條件 UPDATE）。「先讀 replica 判斷有沒有庫存再寫入」是典型錯誤，因為 replica 有複寫延遲，而且讀與寫之間沒有原子性。

## 48.6 訂單非同步處理與付款冪等

扣庫存成功後，checkout 服務把訂單訊息送進 SQS standard queue 並立刻回應。為什麼要排隊而不是同步寫 Aurora 再呼叫金流？因為金流 API 經壓測只能承受每秒約 500 筆，而且偶爾要好幾秒才回應。如果同步呼叫，金流一慢，所有 checkout 請求都卡住，連帶 ALB 與 ECS 的連線都被占滿。SQS 把「接單速度」和「處理速度」拆開：尖峰時訊息在 queue 裡累積，worker 以固定的併發數消化，金流商看到的是平穩的流量。這就是第 32 章的 **queue-based load leveling**。

但 SQS standard queue 是 **at-least-once delivery**（至少送達一次）：同一則訊息有可能被送達兩次。加上 worker 呼叫金流後若在寫回結果前當機，visibility timeout 到期後訊息會被另一個 worker 再處理一次。如果沒有防護，這就是重複扣款的來源。Wanderly 的設計是：

1. **Idempotency key（冪等鍵）** 在使用者按下「付款」時由前端產生（例如 UUID），跟著訂單一路傳下去。使用者按兩次，送出的是同一個 key。
2. Worker 處理前先在 Aurora 的 `payments` 表以這個 key 插入一筆 `PROCESSING` 紀錄，key 有 unique constraint。插入失敗代表已經有人處理過，直接讀出既有結果，不再呼叫金流。
3. 呼叫金流時把同一個 key 放在金流商的 idempotency header 裡（主流金流 API 都支援），即使 worker 在中途當機、訊息被重送，金流商也只會扣一次款。
4. Queue 的 visibility timeout 設定要大於 worker 處理一則訊息的最長時間；若 consumer 是 Lambda，AWS 建議 visibility timeout 至少是函數 timeout 的六倍。`maxReceiveCount` 設為 5，超過就進 **DLQ（dead-letter queue）**，並設 CloudWatch alarm（第 36 章）。

> [!warning] 常見誤解
> 「改用 SQS FIFO queue 就不會重複了。」FIFO 的 deduplication 只在 5 分鐘的去重視窗內有效，而且它防的是「重複送進 queue」，不是「worker 處理到一半當機後重新處理」。付款這種有外部副作用的操作，最終一定要靠持久化的冪等紀錄。FIFO 還有吞吐限制，在這個場景沒有必要。

還有一個細節：checkout 服務「扣庫存」和「送 SQS」是兩個不同系統的寫入，不可能放在同一個交易裡。如果扣完庫存、送 SQS 前服務當機，就會有一筆被保留卻永遠不會處理的庫存。前一節的 reservation 過期機制剛好處理了這種情況：10 分鐘後庫存自動歸還。設計分散式系統時，要問的不是「會不會失敗」，而是「在每兩個步驟之間失敗，系統會停在什麼狀態，誰負責收拾」。

## 48.7 圖片與影片處理管線

Wanderly Deals 讓旅館自己上傳照片與宣傳影片。舊做法是檔案經過 ECS 服務再存到 S3，一支 2 GB 的影片會占住一個任務好幾分鐘，也讓 ALB 的連線一直掛著。新設計讓檔案**不經過應用程式**：

```text
旅館後台
   │ ① 向 API 要上傳授權
   ▼
[API（ECS）] ── ② 回傳 presigned URL（multipart，15 分鐘有效）
   │
旅館後台 ── ③ 直接上傳 ──► [S3：media-raw bucket]
                               │ ④ ObjectCreated 事件
                               ▼
                         [EventBridge] ──► [Step Functions：媒體處理流程]
                                              │ ⑤ 惡意程式掃描、內容審核
                                              │ ⑥ 圖片：Lambda 產生多種尺寸
                                              │ ⑦ 影片：MediaConvert 轉 HLS 多種解析度
                                              ▼
                                      [S3：media-public bucket] ──► CloudFront（OAC）
```

① ② API 驗證旅館身份後，用 S3 **presigned URL**（預先簽章的網址）授權「在 15 分鐘內，把一個檔案上傳到這個指定的 key」。大檔使用 multipart upload，每個 part 各自簽章，中斷後只需要重傳失敗的 part（第 22 章）。

③ 檔案直接從旅館的瀏覽器傳到 S3，應用程式完全不碰檔案內容。

④ Bucket 開啟「把事件送到 EventBridge」的設定後，S3 會把 `Object Created` 事件送到 EventBridge，再由 EventBridge rule 觸發 Step Functions 工作流程（第 32、33 章）。S3 事件通知也是 at-least-once，所以處理流程要能承受同一個檔案被觸發兩次：輸出檔名用來源物件的 key 與 version 決定，重做一次也只是覆寫同一份結果。

⑤ 使用 GuardDuty 的 S3 惡意程式防護掃描上傳檔，Rekognition 檢查不當內容（第 16、47 章）。未通過的檔案移到隔離 prefix，不會被發布。

⑥ 圖片縮圖是幾秒內完成的小工作，適合 Lambda。

⑦ 影片轉碼交給 **AWS Elemental MediaConvert**：受管的檔案型影片轉碼服務，輸出 HLS 等串流格式與多種解析度。它以 job 為單位執行，可以設定 on-demand queue 或預留容量的 reserved queue。舊題目可能出現 Elastic Transcoder，但 AWS 已終止這項服務，新設計請使用 MediaConvert。

處理完成的檔案寫到另一個 bucket，再經 CloudFront 發布。原始檔與成品分開放有兩個好處：權限可以分開（CloudFront 只讀得到成品），生命週期也可以分開。原始影片在 30 天後轉到 S3 Standard-IA，180 天後轉到 Glacier Flexible Retrieval；成品依存取頻率交給 Intelligent-Tiering（第 23 章）。若某些付費內容只給已購買的使用者看，再加上 CloudFront signed URL 或 signed cookie（第 11 章）。

## 48.8 演進到 SAP 等級：全球化與 Region 級韌性

第一階段的架構撐過了第二場促銷：零超賣、零重複扣款。接下來的需求是 SAP 等級的：美國使用者覺得結帳慢、董事會要求 Region 故障時 15 分鐘內恢復下單、而且團隊從 12 人成長到 40 人，開始需要多帳號與獨立部署。

**1. 讀取全球化：靜態與可快取內容在 edge，動態讀取靠近使用者。** CloudFront 已經讓全球的靜態內容夠快。美國使用者慢在動態 API：每次從美國回到東京要 150 毫秒以上的往返。Wanderly 在美國西部（`us-west-2`）部署第二套應用程式層，由 Route 53 的 latency-based routing 依使用者位置把 `api.wanderly.com` 導向最近的 Region（第 9 章）。

**2. 資料層：依資料性質選擇複寫模型。** 這是全章最關鍵的 SAP 決策，因為不同資料對一致性的要求不同：

| 資料 | 選擇 | 理由 |
|---|---|---|
| 商品目錄、會員、訂單 | Aurora Global Database，東京為 primary，奧勒岡為 secondary | 跨 Region 儲存層複寫，延遲通常在一秒內；secondary 可提供本地讀取，故障時可提升為 primary（第 26、42 章） |
| 購物車、session | DynamoDB global tables | 兩個 Region 都能寫；衝突時以 last writer wins 處理，對購物車可以接受 |
| 限量庫存 | DynamoDB 單一 Region（東京）作為唯一 writer | 兩邊同時扣減，衝突時 last writer wins 會吃掉扣減紀錄，等於超賣 |
| 媒體檔 | S3 Cross-Region Replication 到奧勒岡 | 成品在兩個 Region 都有，CloudFront 用 origin group 做 failover |

庫存那一列值得多想一下。為什麼美國使用者不能在美國扣庫存？因為 global tables 的預設多 Region 寫入是非同步複寫，兩個 Region 可能在同一秒各自把最後一間房扣掉，兩邊都回應「成功」，事後複寫時才發現衝突，此時兩位客人都已經付款了。所以**有唯一性限制的資料必須有唯一的 writer**。美國使用者扣庫存時要跨太平洋到東京，多 150 毫秒；但限量商品一年只有幾場活動，這個代價可以接受。DynamoDB global tables 近年也推出了多 Region 強一致（MRSC）模式，但它必須剛好部署在三個 Region（或兩個 replica 加一個 witness）、寫入延遲較高，也不支援 transactions（第 27 章），而本章的庫存保留正好用到交易；考試與多數既有架構仍以「唯一 writer」作為不可超賣資料的標準答案。

**3. DR 策略：warm standby。** RTO 15 分鐘、RPO 1 分鐘，對照第 34 章的四種策略：backup & restore 要從備份還原，RTO 以小時計；pilot light 的資料層雖然持續複寫，但應用程式運算層平時是關閉的，災難時才啟動、擴展、驗證整個應用層，15 分鐘非常緊（第 34 章的範例中，pilot light 對應的 RTO 是 1 小時）；multi-site active-active 對訂單資料又太複雜。Wanderly 選擇 **warm standby**：奧勒岡平時就在服務美國的讀取流量，應用層一直在執行，只是規模較小；Aurora secondary cluster 持續複寫。東京故障時，流程是：

1. 確認東京確實不可用（不是監控誤報），由值班主管決定切換。
2. 對 Aurora Global Database 執行 failover，把奧勒岡的 secondary 提升為 primary。
3. 把庫存服務的 writer 改到奧勒岡（從最新的 DynamoDB 備份或預先複製的資料重建限量庫存；若活動進行中，可直接暫停該場活動）。
4. 透過 **Amazon Application Recovery Controller（ARC，舊名 Route 53 Application Recovery Controller）** 的 routing control 把所有寫入流量切到奧勒岡，並把奧勒岡的 ECS service 擴展到全量（第 34、53 章）。第 2 到第 4 步也可以預先寫成 ARC 的 Region switch 計畫，出事時依序執行，減少手動操作的失誤。

為什麼要用 ARC 而不是只靠 Route 53 health check 自動切換？因為資料庫 failover 是有代價的決定（可能遺失最後幾秒的寫入），不應該因為一次健康檢查的誤判就自動發生。ARC 的 routing control 由人或自動化流程明確地「撥開關」，而且它的 data plane 由跨 5 個 Region 的叢集提供，東京出事時仍能從其他 Region 的 endpoint 操作，也不需要依賴 Route 53 的 control plane 修改 DNS 記錄（第 34 章）。

**4. 多帳號與部署。** 團隊變大後，catalog、checkout、media 各自擁有獨立的 production 帳號，網路由網路帳號用 Transit Gateway 集中管理（第 40、41 章）。每個服務以 CodeDeploy 做 ECS blue/green 部署，並設定 CloudWatch alarm 自動回滾（第 37 章）。促銷開關、等候室放行速率這類「活動當天才會調整」的參數放在 AWS AppConfig，改設定不必重新部署。

               ▼                        ▼

  │   │            │              │               │   │   │            │                         │
  │ Valkey      DynamoDB        SQS → worker → 金流 │   │ Valkey      DynamoDB（cart global table）  │
  │   │        （庫存唯一 writer）                  │   │   │                                      │
  │ Aurora Global primary ════ 儲存層複寫 ════════════════► Aurora Global secondary（唯讀）          │
  │ DynamoDB cart ◄═══════════ global tables ═════════════► DynamoDB cart                           │
  │ S3 media ═════════════════ CRR ═══════════════════════► S3 media（CloudFront origin group 備援）  │

讀這張圖時，請沿三條路徑走一次。**瀏覽路徑**：使用者 → CloudFront（大部分在這裡結束）→ 最近 Region 的 ALB → ECS → Valkey → 本地 Aurora（primary 或 secondary 皆可讀）。**下單路徑**：一律到東京，因為庫存與訂單的 writer 在東京；奧勒岡的 checkout 服務收到寫入請求時，轉送到東京的 checkout API。**媒體路徑**：旅館上傳到東京 bucket，管線處理後由 CRR 複製到奧勒岡，CloudFront 的 origin group 以東京為主、奧勒岡為備。注意 CloudFront origin failover 只對 GET、HEAD、OPTIONS 請求生效，所以它適合媒體與靜態內容，不能拿來替寫入 API 做 failover。

最底下的觀測層有一個容易被忽略的元素：**業務指標**。CPU 與延遲都正常，但「每分鐘成功訂單數」突然掉到零，往往是金流商或某個設定出問題的第一個訊號。Wanderly 把這個指標做成 CloudWatch alarm，比任何技術指標都早發現問題。

## 48.10 設計決策紀錄：為何選 A 不選 B

**設計決策紀錄（ADR，Architecture Decision Record）** 是把「當時為什麼這樣選」寫下來的文件。一年後有人問「為什麼不用 Kinesis」，答案就在這裡，不必靠某位資深工程師的記憶。考試的選項其實也是同一件事：每個錯誤選項都是一個「B」，你要知道它在這個情境下輸在哪裡。

| 決策 | 選擇 A | 不選 B | 理由 |
|---|---|---|---|
| 應用程式運算 | ECS on Fargate | EC2 Auto Scaling group | 團隊沒有維運人力；Fargate 免管 OS 與叢集容量。若有大量穩定 baseline，EC2 加 Savings Plans 會更便宜，這是成本上的取捨 |
| 限量庫存 | DynamoDB 條件式寫入 + sharded counter | Aurora 單列 `UPDATE` | 單列鎖競爭會拖垮整個資料庫，而 Aurora 同時服務其他所有功能，故障半徑太大 |
| 限量庫存 | DynamoDB | ElastiCache `DECR` | Valkey／Redis OSS 的複寫是非同步的，primary failover 時可能遺失最近的扣減，庫存數字不可靠；它適合當「入場閘門」，不適合當庫存帳本 |
| 訂單佇列 | SQS standard | SQS FIFO | 訂單之間沒有順序需求；重複由冪等設計處理；standard 沒有 FIFO 的吞吐上限 |
| 訂單佇列 | SQS | Kinesis Data Streams | 每筆訂單是獨立工作，需要個別重試與 DLQ；Kinesis 適合多個 consumer 重播同一串事件，shard 內一筆失敗會卡住後面（第 31 章） |
| 全球加速 | CloudFront | Global Accelerator | 內容大多可快取、協定是 HTTP；Global Accelerator 適合非 HTTP 或需要固定 anycast IP 的情境（第 11 章） |
| 跨 Region 資料庫 | Aurora Global Database | 跨 Region read replica | Global Database 的儲存層複寫延遲低、支援受管的 switchover／failover 流程，較能達成 RPO 1 分鐘 |
| DR 策略 | Warm standby | Multi-site active-active | 訂單與庫存需要唯一 writer，真正的雙寫要重新設計資料模型；warm standby 已滿足 RTO 15 分鐘 |
| 影片轉碼 | MediaConvert | EC2 上自建 FFmpeg | 不必管轉碼叢集、容量與編碼器版本；只有在需要極度客製的處理流程時才值得自建 |
| 上傳路徑 | Presigned URL 直傳 S3 | 經過 ECS 服務轉存 | 大檔不占用應用程式資源與 ALB 連線，S3 自動擴展 |

## 48.11 故障演練

架構畫完不算完成，要能回答「這一塊壞了會怎樣」。Wanderly 每季用 **AWS Fault Injection Service（FIS）** 在 staging 環境做一次 game day（第 34 章），下表是演練腳本與預期結果：

| 故障 | 預期行為 | 怎麼發現 | 要確認的事 |
|---|---|---|---|
| 一個 AZ 不可用 | ALB 停止把流量送到該 AZ；Aurora 若 writer 在該 AZ 則自動 failover；ECS 在其他 AZ 補任務 | ALB healthy host 數、Aurora failover 事件 | 剩下兩個 AZ 的既有容量能撐住（不依賴擴展）；應用程式會重連 cluster endpoint |
| ElastiCache primary 節點故障 | Replica 自動提升，數十秒內恢復寫入 | ElastiCache 事件、cache miss 率上升 | Aurora 能承受短暫的 cache miss 尖峰；用戶端有重試與 timeout |
| Aurora writer 故障 | 某個 replica 被提升，通常在一分鐘內完成 | Aurora 事件、應用程式連線錯誤 | 應用程式的 DNS 快取時間夠短，會重新解析 cluster endpoint；交易失敗可安全重試 |
| 金流 API 變慢或逾時 | Worker 逾時、訊息回到 queue 稍後重試；queue 深度上升 | `ApproximateAgeOfOldestMessage` alarm | 冪等鍵防止重試造成重複扣款；使用者看到「處理中」而不是錯誤 |
| 毒訊息（格式錯誤的訂單） | 重試 5 次後進 DLQ，不阻塞其他訊息 | DLQ 訊息數 alarm | 修正後用 redrive 把 DLQ 訊息送回原 queue |
| 開賣瞬間 cache stampede | 預熱的快取與等候室讓 Aurora 不受衝擊 | Aurora CPU、連線數 | 預熱腳本在開賣前確實執行 |
| 東京 Region 不可用 | 依 runbook 執行 Aurora Global failover 與 ARC 切換，15 分鐘內恢復下單 | 跨 Region 的 Synthetics canary、業務指標 | Runbook 在演練中實際跑過；奧勒岡的 quota 已預先提高到全量所需 |

最後一列的「quota 已預先提高」是很多 DR 計畫失敗的原因：warm standby 平時規模小，帳號的 Fargate vCPU 配額可能只夠平時用量，真正要擴展到全量時被 quota 擋住。DR Region 的 quota 必須按「全量」申請（第 35 章）。

## 48.12 成本思路

電商的成本不能只看月帳單，因為流量本來就會隨業務成長。Wanderly 財務長要的指標是**每筆成功訂單的基礎設施成本**：如果月帳單漲了 30%、訂單漲了 60%，那其實是變便宜了。用這個角度看，主要的成本來源和對策如下：

- **Data transfer out 與 origin 負載**：CloudFront 快取命中率每提高一點，就少一份 origin 運算與一份跨 Internet 的傳輸。從 AWS 到 CloudFront 的 origin fetch 不收 data transfer out 費用，CloudFront 對使用者的傳輸費率通常也低於直接從 Region 送出（第 39 章）。
- **運算**：平日穩定的 baseline 用 Compute Savings Plans 涵蓋（同時適用 Fargate 與 Lambda）；促銷尖峰的超出部分用 on-demand。媒體轉碼前處理、縮圖重建這類可中斷的批次工作，可以用 Fargate Spot。使用 Graviton（ARM）架構的任務通常有更好的價格效能比。
- **資料庫**：Aurora 的 I/O 費用若占 Aurora 總費用的比例很高（AWS 的參考門檻是超過約 25%），改用 Aurora I/O-Optimized 計價較划算。促銷前加開的 Aurora Replica 活動後要記得移除，或使用 Aurora Auto Scaling 管理 replica 數量。
- **快取**：ElastiCache 讓 Aurora 不必為尖峰配置大規格；用快取節點的錢換資料庫的錢，通常是划算的交換。
- **NAT Gateway**：ECS 任務從 ECR 拉 image、存取 S3 與 DynamoDB 都會經過 NAT 產生處理費。為 S3、DynamoDB 建立 gateway endpoint，為 ECR 建立 interface endpoint（`ecr.api` 與 `ecr.dkr`；image layer 實際從 S3 下載，所以 S3 gateway endpoint 也是必要的），可以省下大量 NAT 費用（第 6 章）。
- **儲存**：原始媒體檔用 lifecycle 轉到較便宜的儲存類別；未完成的 multipart upload 用 lifecycle 規則自動清除，否則殘留的 part 會一直收費。
- **DR**：warm standby 的奧勒岡環境同時服務美國讀取，所以它不是純粹的「保險費」，而是有業務價值的容量。這也是向財務說明多 Region 成本時的重點。

> [!tip] 考試提示
> SAP 成本題常給一個「看起來省很多」的選項，例如「拿掉 DR Region、災難時再用 IaC 重建」。先檢查它有沒有違反題目的 RTO／RPO：違反的話，再省也是錯的。

## 48.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 促銷、已知時間的流量尖峰 | Scheduled scaling 預先擴展；預熱快取；提前提高 quota |
| 商品頁大量重複讀取、資料庫 CPU 高 | CloudFront 短 TTL 快取 + ElastiCache cache-aside + Aurora Replica |
| 部分使用者看到別人的購物車 | CloudFront cache behavior 拆分，個人化路徑不快取 |
| 限量、不可超賣 | 原子的條件式更新（DynamoDB condition expression）；單一 writer |
| 下游（金流、ERP）處理能力有限、尖峰會壓垮它 | SQS 緩衝 + 限制 consumer 併發 |
| 重試造成重複扣款 | Idempotency key + 持久化紀錄；SQS standard 是 at-least-once |
| 大檔案上傳、不想經過應用程式伺服器 | S3 presigned URL + multipart upload |
| 上傳後自動轉成多種解析度影片 | S3 事件 → EventBridge／Step Functions → MediaConvert |
| 全球使用者靜態內容慢 | CloudFront；私有 S3 origin 用 OAC |
| 跨 Region、RPO 秒級的關聯式資料庫 | Aurora Global Database |
| 跨 Region、兩邊都要寫的購物車／session | DynamoDB global tables |
| Region 切換不要因為誤判自動發生 | Route 53 ARC routing control，人為或流程控制 |
| 處理失敗的訊息不能卡住整個 queue | DLQ + `maxReceiveCount` + redrive |

**常見陷阱**：

1. 以為 target tracking 能及時接住秒級尖峰：已知時間的尖峰要用 scheduled scaling 預先擴展。
2. 以為 SQS FIFO 的去重能保證付款只扣一次：去重視窗只有 5 分鐘，也防不了處理中途當機後的重新處理。
3. 用 DynamoDB global tables 或多 Region 雙寫處理限量庫存：非同步複寫加 last writer wins 會造成超賣。
4. 以為 CloudFront origin group 能替 POST 寫入 API 做 failover：origin failover 只適用 GET、HEAD、OPTIONS。
5. 用 ElastiCache 當唯一的庫存或訂單帳本：快取的複寫是非同步的，failover 可能遺失寫入。
6. 只靠 Route 53 health check 自動觸發資料庫的跨 Region failover：可能因誤判而不必要地遺失資料，SAP 題通常要求受控切換。

## 本章重點整理

- 電商流量要依性質分流：瀏覽在 edge 與快取吸收、扣庫存要強一致、付款要可安全重試、媒體處理要排隊。
- 促銷尖峰是事先知道的，用 scheduled scaling、快取預熱與提前提高 quota 準備，不要等 target tracking 反應。
- CloudFront 依路徑拆分 cache behavior：可共享內容積極快取，個人化與交易路徑不快取，cache key 只放真正改變回應的值。
- 虛擬等候室把進入 checkout 的速度限制在後端能承受的範圍，是 load shedding 的應用。
- 限量庫存用原子的條件式寫入；單一 item 太熱時拆成 sharded counter，並以 reservation 加過期補償處理未付款的保留。
- SQS 把接單速度與處理速度拆開，保護處理能力有限的下游；standard queue 是 at-least-once，consumer 必須冪等。
- 付款冪等靠前端產生的 idempotency key、資料庫 unique constraint 與金流商的冪等 header，不是靠 FIFO queue。
- 大檔上傳用 presigned URL 與 multipart 直傳 S3；媒體處理以事件觸發 Step Functions，影片轉碼用 MediaConvert（Elastic Transcoder 已終止）。
- 多 Region 時依資料性質選複寫：訂單用 Aurora Global Database，購物車用 DynamoDB global tables，不可超賣的庫存維持唯一 writer。
- RTO 15 分鐘、RPO 1 分鐘的需求適合 warm standby；Region 切換用 ARC routing control 受控執行，不要只靠健康檢查自動觸發。
- CloudFront origin failover 只對 GET、HEAD、OPTIONS 生效，適合媒體與靜態內容，不適合寫入 API。
- 故障演練要涵蓋 AZ、快取、資料庫、下游逾時、毒訊息與 Region 故障，並確認 DR Region 的 quota 按全量申請。
- 成本以「每筆成功訂單的成本」衡量；主要槓桿是快取命中率、Savings Plans、gateway endpoint、Aurora I/O-Optimized 與儲存生命週期。

### 練習 48-1｜SAA｜單選｜個人化內容的快取隔離

一家電商把整個網站放在 CloudFront 後面，所有路徑共用一個 cache behavior，TTL 為 60 秒，cache key 只包含 URL 路徑。上線後，部分登入使用者在 `/api/cart` 看到別人的購物車內容。團隊希望維持商品頁 `/api/catalog/*` 的高快取命中率。

最合適的修正是什麼？

- A. 為 `/api/cart/*` 與 `/api/checkout/*` 建立獨立的 cache behavior 並使用不快取的 cache policy，`/api/catalog/*` 維持只以商品 ID 與語系作為 cache key
- B. 把所有 cookie 與 header 加入整個 distribution 唯一的 cache key，讓每個使用者都有自己的快取
- C. 每次有使用者修改購物車時，對整個 distribution 執行 invalidation
- D. 把 TTL 從 60 秒縮短為 1 秒，降低看到別人資料的機率

> [!answer]- 答案：A
> **A ✓** 個人化回應不能以共用 cache key 快取。依路徑拆分 behavior，讓交易與購物車路徑不快取，而可共享的商品頁仍以最少的 cache key 元素積極快取，同時滿足安全與命中率。
>
> **B ✗** 把所有 cookie 與 header 放進 cache key 雖然能避免互相看到，但每個請求幾乎都是不同的 key，連商品頁的命中率也會歸零，違反「維持商品頁高命中率」的需求。
>
> **C ✗** Invalidation 是讓快取失效的工具，不是使用者隔離機制；在下一次 invalidation 前，其他使用者仍會拿到被快取的個人化內容，而且頻繁 invalidation 會產生費用。
>
> **D ✗** 縮短 TTL 只是縮小出錯的時間窗，1 秒內仍會把 A 的購物車交給 B，問題沒有解決。
>
> **考點**：SAA-1.2、SAA-3.4｜CloudFront cache behavior 與 cache key 設計

### 練習 48-2｜SAA｜單選｜已知時間的促銷尖峰

Wanderly 每個月的第一個星期五晚上八點舉辦限時搶購，流量會在兩分鐘內從平日的 3,000 RPS 升到 9 萬 RPS。應用程式執行在 ECS on Fargate，使用以 CPU 為目標的 target tracking 擴展。過去兩次活動，開賣後前五分鐘都出現大量 5xx 錯誤，之後才恢復正常。

哪個做法最能解決這個問題？

- A. 把 target tracking 的目標 CPU 從 60% 降到 30%
- B. 改用 step scaling，並把每一級的擴展幅度加大
- C. 使用 scheduled scaling 在開賣前 30 分鐘提高 ECS service 的最小任務數，並事先確認 Fargate 相關 quota 足夠
- D. 把 ECS 任務改成更大的 CPU 與記憶體規格，並維持原本的擴展設定

> [!answer]- 答案：C
> **A ✗** 降低目標值會讓平時多開一些容量，但 target tracking 仍然要先看到指標上升才擴展，面對兩分鐘內 30 倍的尖峰仍然來不及；而且平日成本會上升。
>
> **B ✗** Step scaling 同樣是看到 alarm 後才反應，新任務啟動與通過健康檢查都需要時間，無法消除尖峰開始時的空窗。
>
> **C ✓** 活動時間事先知道，最可靠的做法是 scheduled scaling 在尖峰前把容量準備好。預先擴展時還要確認帳號的 Fargate vCPU 等 quota 足夠，這些是預設值，可申請提高，但必須提前處理。
>
> **D ✗** 加大單一任務規格能提高每個任務的處理量，但無法讓總容量提高 30 倍，擴展反應慢的問題依然存在。
>
> **考點**：SAA-3.2、SAA-2.1｜scheduled scaling 與已知尖峰

### 練習 48-3｜SAA｜單選｜限量庫存不可超賣

一個限量 500 份的商品在開賣時會有數萬人同時下單。目前的程式先從 Aurora Replica 讀取剩餘數量，如果大於 0，再對 writer 執行 `UPDATE inventory SET stock = stock - 1`。活動後發現賣出的數量超過 500 份。

哪個修改能保證不超賣，並且能承受高併發？

- A. 改從 Aurora writer 讀取剩餘數量，其他邏輯不變
- B. 把庫存放在 DynamoDB，以 condition expression `stock >= :qty` 的 UpdateItem 原子扣減，並把庫存拆成多個 item 分散寫入
- C. 把庫存放在 ElastiCache，並把讀取 TTL 縮短為 1 秒
- D. 把扣庫存的請求送進 SQS standard queue，由多個 consumer 並行處理

> [!answer]- 答案：B
> **A ✗** 改讀 writer 消除了複寫延遲，但「讀」與「寫」仍是兩個獨立步驟，兩個交易仍可能同時讀到剩 1 份而都扣成功；在高併發下，同一列的鎖競爭也會拖垮資料庫。
>
> **B ✓** DynamoDB 的條件式寫入在單一 item 上原子地「檢查並更新」，條件不成立就失敗，不可能扣成負數。把庫存拆成多個 item（sharded counter）可以避免所有寫入集中在一個熱分割上。
>
> **C ✗** 縮短快取 TTL 只是讓讀到的數字比較新，判斷與扣減之間仍然沒有原子性；快取也不是可靠的庫存帳本。
>
> **D ✗** 多個 consumer 並行處理仍然各自執行「讀後寫」，競爭條件沒有消失；standard queue 還可能重複送達訊息。
>
> **考點**：SAA-3.3、SAA-2.1｜原子條件式寫入與熱分割

### 練習 48-4｜SAA｜單選｜保護處理能力有限的下游

Checkout 服務在使用者下單時同步呼叫外部金流 API。金流 API 經壓測只能穩定處理每秒約 500 筆，促銷時下單請求會達到每秒 2,000 筆，金流 API 開始逾時，checkout 服務的連線也被占滿，連帶影響瀏覽功能。業務可以接受付款結果在一分鐘內以通知告知使用者。

哪個設計最合適？

- A. 在 checkout 與金流之間加上 Network Load Balancer，分散對金流 API 的連線
- B. 把 checkout 服務的任務數增加 4 倍，讓更多請求可以同時呼叫金流
- C. 在 checkout 服務中對金流 API 加上無限次重試，直到成功為止
- D. Checkout 服務把訂單寫入 SQS 後立即回應使用者，由 worker 以限制的併發數消化 queue 並呼叫金流 API

> [!answer]- 答案：D
> **A ✗** NLB 是用來分散流量到自己的後端，無法提升外部金流 API 的處理能力，也無法吸收尖峰。
>
> **B ✗** 更多任務代表更多同時打到金流的請求，只會讓下游更快過載，逾時與重試會進一步放大問題。
>
> **C ✗** 無限重試會在下游過載時製造 retry storm，持續占用連線，讓故障擴散得更嚴重。
>
> **D ✓** SQS 把接單速度與處理速度拆開，尖峰期間訊息在 queue 中累積，worker 以固定併發數平穩地呼叫金流，下游看到的是它能承受的流量。業務接受一分鐘內通知，正好允許非同步處理。
>
> **考點**：SAA-2.1｜queue-based load leveling

### 練習 48-5｜SAA｜選兩項｜避免重複扣款

一家電商的訂單 worker 從 SQS standard queue 取得訂單後呼叫金流 API 扣款。偶爾 worker 在扣款成功後、刪除訊息前當機，訊息在 visibility timeout 到期後被另一個 worker 再處理一次，造成重複扣款。使用者在網路不穩時也常按兩次「付款」。

哪兩個做法能一起解決這個問題？（選兩項）

- A. 由前端在使用者按下付款時產生 idempotency key，worker 處理前以這個 key 在資料庫插入有 unique constraint 的付款紀錄，已存在就直接回傳既有結果
- B. 把 visibility timeout 設為 12 小時，讓訊息不會被重新處理
- C. 呼叫金流 API 時把同一個 idempotency key 放入金流商支援的冪等 header
- D. 改用 SQS FIFO queue，依靠 content-based deduplication 防止重複扣款
- E. 把 worker 的記憶體加大，降低當機機率

> [!answer]- 答案：A、C
> **A ✓** 持久化的冪等紀錄讓「同一筆付款」不論被觸發幾次、由哪個 worker 處理，都只會執行一次；使用者按兩次也會帶著同一個 key。
>
> **B ✗** 過長的 visibility timeout 只是讓重新處理延後到 12 小時後，worker 真的當機時訂單會卡住半天，重複仍然可能發生。
>
> **C ✓** 若 worker 在呼叫金流後、寫回結果前當機，下一次重試會再呼叫金流一次。把同一個 key 交給金流商，由金流商在它的系統中去重，才能覆蓋這個時間窗。
>
> **D ✗** FIFO 的去重只在 5 分鐘視窗內防止重複送進 queue，無法防止處理到一半當機後的重新處理；也有吞吐上限。
>
> **E ✗** 降低當機機率不等於消除；at-least-once 的系統必須在設計上容忍重複。
>
> **考點**：SAA-2.1、SAA-2.2｜冪等性與 at-least-once delivery

### 練習 48-6｜SAA｜單選｜大型影片上傳與轉碼

旅館會上傳最大 2 GB 的宣傳影片，目前檔案先傳到 ECS 上的 API 服務，再由服務轉存 S3，再由同一個服務呼叫 FFmpeg 轉碼。上傳經常中斷，轉碼也讓 API 服務的 CPU 飆高。團隊希望以最少的營運負擔，讓影片自動轉成多種解析度的串流格式。

最合適的設計是什麼？

- A. 把 ECS 任務改成更大規格，並把 ALB idle timeout 調長到 1 小時
- B. 用 S3 Transfer Acceleration 上傳到 API 服務，再由 API 服務呼叫 Elastic Transcoder
- C. API 發出 multipart 上傳用的 presigned URL 讓旅館直傳 S3，S3 事件經 EventBridge 觸發 Step Functions，由 MediaConvert 轉碼
- D. 讓旅館把影片上傳到 EFS，再由一組 EC2 Auto Scaling group 輪詢 EFS 目錄執行 FFmpeg

> [!answer]- 答案：C
> **A ✗** 大檔仍然經過應用程式，占用任務與連線，上傳中斷也必須整個重傳；轉碼仍在 API 服務上與正常請求搶 CPU。
>
> **B ✗** Transfer Acceleration 是 S3 的功能，不是用來上傳到應用程式伺服器的；Elastic Transcoder 已終止服務，新設計不應使用。
>
> **C ✓** Presigned URL 讓檔案直接進 S3，multipart 可以只重傳失敗的 part；事件驅動的工作流程把轉碼交給受管的 MediaConvert，營運負擔最低。
>
> **D ✗** 自建轉碼叢集與輪詢機制需要自己管理容量、FFmpeg 版本與失敗重試，營運負擔遠高於受管服務。
>
> **考點**：SAA-3.1、SAA-2.1｜presigned URL 直傳與事件驅動媒體管線

### 練習 48-7｜SAA｜單選｜Multi-AZ 容量規劃

一個電商應用程式在平時尖峰需要 60 個 ECS 任務。公司要求任何一個 AZ 故障時，不需要等待擴展，剩下的容量就能撐住平時尖峰。團隊在比較使用 2 個 AZ 或 3 個 AZ。

哪個配置能以最少的總任務數滿足需求？

- A. 3 個 AZ，每個 AZ 30 個任務，共 90 個
- B. 2 個 AZ，每個 AZ 30 個任務，共 60 個，故障時依賴 Auto Scaling 補足
- C. 2 個 AZ，每個 AZ 60 個任務，共 120 個
- D. 3 個 AZ，每個 AZ 20 個任務，共 60 個

> [!answer]- 答案：A
> **A ✓** 失去一個 AZ 後剩下 2 × 30 = 60 個任務，正好撐住尖峰，總共 90 個任務，是滿足 static stability 的最少配置。
>
> **B ✗** 失去一個 AZ 後只剩 30 個任務，必須等 Auto Scaling 補足，違反「不需要等待擴展」的要求；故障時其他客戶也可能在搶同一批容量。
>
> **C ✗** 兩個 AZ 時每個 AZ 都要能獨自撐住 60 個任務，總共 120 個雖然可行，但比三個 AZ 的 90 個多。
>
> **D ✗** 失去一個 AZ 後只剩 40 個任務，不足以撐住 60 個任務的尖峰。
>
> **考點**：SAA-2.2、SAA-4.2｜static stability 與多 AZ 容量

### 練習 48-8｜SAP｜單選｜多 Region 的資料複寫選擇

Wanderly 要在東京與奧勒岡兩個 Region 服務使用者。購物車兩邊都要能低延遲寫入；限量商品的庫存絕對不可超賣；訂單資料需要 RPO 1 分鐘以內的跨 Region 保護。團隊希望營運負擔低。

哪個資料架構最合適？

- A. 購物車、庫存、訂單全部放在 DynamoDB global tables，兩個 Region 都可寫入
- B. 購物車使用 DynamoDB global tables；庫存只在東京有唯一 writer；訂單使用 Aurora Global Database
- C. 購物車與訂單使用 Aurora Global Database 並在兩個 Region 都啟用寫入；庫存使用 ElastiCache Global Datastore
- D. 所有資料都放在東京的 Aurora，奧勒岡只部署應用程式層，每天把 snapshot 複製到奧勒岡

> [!answer]- 答案：B
> **A ✗** Global tables 預設的多 Region 寫入是非同步複寫，衝突以 last writer wins 解決。兩個 Region 同時扣最後一份庫存時，兩邊都會回應成功，造成超賣。
>
> **B ✓** 依資料性質選擇：購物車可以接受 last writer wins，適合 global tables；不可超賣的庫存必須有唯一 writer；訂單用 Aurora Global Database 的儲存層複寫，延遲通常在一秒內，滿足 RPO 1 分鐘。
>
> **C ✗** Aurora Global Database 只有 primary Region 可寫入（secondary 可用 write forwarding 轉送到 primary，但不是兩個獨立的寫入點）；ElastiCache 的複寫是非同步的，不能當作不可超賣的庫存帳本。
>
> **D ✗** 每天一次的 snapshot 只能提供約 24 小時的 RPO，遠超過 1 分鐘的要求；購物車在奧勒岡的寫入也要跨太平洋，延遲不符。
>
> **考點**：SAP-2.4、SAP-1.3｜依資料一致性需求選擇跨 Region 複寫

### 練習 48-9｜SAP｜單選｜受控的 Region 切換

Wanderly 採用 warm standby：東京為 primary，奧勒岡持續執行縮小規模的應用程式層，Aurora Global Database 的 secondary 位於奧勒岡。目前 Route 53 failover record 的 health check 失敗時會自動觸發一支 Lambda，對 Aurora Global Database 執行 failover。上個月一次健康檢查端點的設定錯誤，導致資料庫在東京完全正常的情況下被切到奧勒岡，遺失了數秒的訂單。公司要求 Region 切換必須由值班主管明確決定，且在東京 Region 故障時仍能可靠操作切換。

哪個改善最合適？

- A. 把 health check 的失敗門檻從 3 次提高到 10 次，降低誤判機率
- B. 改用 Route 53 latency-based routing，讓流量自然流向健康的 Region
- C. 在東京部署一個管理後台，由值班主管登入後執行 failover 腳本
- D. 改用 Amazon Application Recovery Controller（ARC）的 routing control 控制流量切換，搭配經過演練的 runbook 由值班主管執行 Aurora Global failover 與擴展奧勒岡

> [!answer]- 答案：D
> **A ✗** 提高門檻只能降低誤判機率，切換仍然是自動觸發，沒有滿足「由主管明確決定」；真正故障時也會拖慢偵測。
>
> **B ✗** Latency-based routing 只依延遲選擇端點，無法處理資料庫角色切換，也沒有人為控制。
>
> **C ✗** 管理後台放在東京，正是東京故障時最可能無法使用的地方，違反「Region 故障時仍能操作」的要求。
>
> **D ✓** ARC 的 routing control 是由人或自動化流程明確設定的開關，它的 data plane 由跨 5 個 Region 的叢集提供，東京出事時仍可從其他 Region 的 endpoint 操作。資料庫 failover 這種可能遺失資料的決定，搭配 runbook 由人決定，符合需求。
>
> **考點**：SAP-2.2、SAP-3.4｜ARC routing control 與受控 failover

### 練習 48-10｜SAP｜選兩項｜DR Region 的隱藏風險

一家電商以 warm standby 準備 DR：備援 Region 平時以全量 15% 的規模執行 ECS on Fargate 與較小的 Aurora secondary。年度演練中，切換後 ECS service 擴展到全量時，大量任務啟動失敗，RTO 超過目標兩倍。事後發現團隊從未在備援 Region 實際擴展到全量過。

哪兩個做法最能防止這種情況再次發生？（選兩項）

- A. 依全量需求預先提高備援 Region 的 Fargate、ALB 等 service quotas，並把這項檢查列入 runbook
- B. 把備援 Region 改成 backup & restore 策略，降低平時成本
- C. 定期在備援 Region 執行包含擴展到全量的演練，例如使用 AWS FIS 與 game day 驗證 RTO
- D. 在主要 Region 增加更多 AZ，降低需要切換 Region 的機率
- E. 把所有任務改成更大的規格，讓需要啟動的任務數變少

> [!answer]- 答案：A、C
> **A ✓** Service quotas 以帳號與 Region 為單位計算，備援 Region 平時用量小，quota 常只夠平時規模。這些預設值可申請提高，但必須在災難前就申請好。
>
> **B ✗** Backup & restore 的 RTO 通常以小時計，只會讓 RTO 更長，與問題方向相反。
>
> **C ✓** 只有實際擴展到全量的演練，才能發現 quota、容量、相依服務與 runbook 的缺口。沒有演練過的 DR 計畫，在真正出事時常常無法如期完成。
>
> **D ✗** 更多 AZ 能提高 Region 內的可用性，但無法解決 Region 級故障，也沒有修正備援 Region 擴展失敗的問題。
>
> **E ✗** 更大的任務規格不會繞過 vCPU 類的 quota，反而每個任務消耗更多配額；也沒有驗證整體流程。
>
> **考點**：SAP-2.2、SAP-3.4｜DR 演練與 service quotas

### 練習 48-11｜SAP｜單選｜媒體內容的跨 Region 備援

Wanderly 的旅館照片與影片成品存放在東京的 S3 bucket，經 CloudFront 發布。公司要求東京 Region 發生問題時，全球使用者仍能看到這些媒體內容，且不需要人為介入。媒體上傳 API 可以暫時停止服務。

最合適的設計是什麼？

- A. 啟用 S3 Cross-Region Replication 把成品複製到奧勒岡的 bucket，在 CloudFront 建立以東京為主、奧勒岡為備的 origin group
- B. 把 CloudFront 的 TTL 設為一年，讓所有內容都留在 edge location
- C. 用 Route 53 failover record 把 CloudFront distribution 的網域切換到奧勒岡 bucket 的 S3 website endpoint
- D. 在奧勒岡建立第二個 CloudFront distribution，並在東京故障時更新應用程式中的媒體網址

> [!answer]- 答案：A
> **A ✓** CRR 讓成品在奧勒岡有副本；CloudFront origin group 在主要 origin 回傳錯誤或逾時時，自動對次要 origin 重試。媒體讀取是 GET 請求，正好在 origin failover 支援的範圍內，不需要人為介入。
>
> **B ✗** 長 TTL 不保證物件一直留在 edge，冷門內容可能已被淘汰，仍需要回源；而且內容更新後也無法及時反映。
>
> **C ✗** S3 website endpoint 不支援 OAC 也不支援 HTTPS，bucket 必須公開，降低安全性；DNS 切換也還需要處理 CloudFront 的網域設定，並不是自然的自動化方案。
>
> **D ✗** 需要人為更新網址，違反「不需要人為介入」，使用者端快取的舊網址也會繼續失敗。
>
> **考點**：SAP-2.2、SAP-2.4｜S3 CRR 與 CloudFront origin failover

### 練習 48-12｜SAP｜單選｜以單位成本最佳化

財務團隊要求降低每筆成功訂單的基礎設施成本 20%，但不得違反 Region 故障時 RTO 15 分鐘的要求。分析帳單發現：NAT Gateway 處理費很高，主要來自 ECS 任務存取 S3、DynamoDB 與 ECR；Aurora 的 I/O 費用約占 Aurora 總費用的 40%；CloudFront 快取命中率只有 55%，因為商品頁的 cache key 包含所有 cookie。

哪個方案組合最合適？

- A. 移除奧勒岡的 warm standby，改用 IaC 在災難時重建；其他維持不變
- B. 把所有 ECS 任務改成 Fargate Spot，並把 Aurora 改成單一 AZ
- C. 建立 S3 與 DynamoDB gateway endpoint、ECR interface endpoint；把 Aurora 改為 I/O-Optimized；移除商品頁 cache key 中不影響回應的 cookie
- D. 購買三年期 Reserved Instances 涵蓋促銷尖峰所需的最大容量

> [!answer]- 答案：C
> **A ✗** 災難時才重建整個環境（含資料庫還原與擴展）很難在 15 分鐘內完成，違反 RTO。不能用違反限制的方式省錢。
>
> **B ✗** Fargate Spot 可能被中斷，不適合處理付款的關鍵路徑；Aurora 單一 AZ 也犧牲了 AZ 級的可用性。
>
> **C ✓** 三個措施都直接針對帳單中的問題且不影響可靠性：endpoint 讓 AWS 服務流量不經過 NAT；I/O 費用占比高時 I/O-Optimized 計價較划算；修正 cache key 提高命中率，同時減少 origin 運算與傳輸。
>
> **D ✗** 以尖峰容量購買承諾，一個月只有一晚用得到，大部分時間是浪費；而且 ECS on Fargate 應該用 Compute Savings Plans 涵蓋穩定的 baseline，而不是 EC2 Reserved Instances。
>
> **考點**：SAP-3.5、SAP-2.6｜依帳單分析選擇成本最佳化措施
