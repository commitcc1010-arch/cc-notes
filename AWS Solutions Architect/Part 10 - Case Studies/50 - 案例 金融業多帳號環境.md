# 第 50 章　案例：金融業多帳號與合規環境

> [!abstract] 本章地圖
> **你會學到**：
> - 把金融監理與 PCI DSS 的要求翻譯成具體的帳號、網路、金鑰、日誌與存取設計
> - 為受監理的 workload 設計 landing zone：OU、帳號、guardrail，以及把高風險範圍縮到最小的切法
> - 用 Transit Gateway 與 Network Firewall 做集中 inspection，並避開非對稱路由的陷阱
> - 在 KMS、KMS custom key store 與 CloudHSM 之間依需求做選擇，並在 key policy 中落實職責分離
> - 設計「連 root user 都改不了」的日誌、可證明的資料主權、可演練的 break-glass，以及能持續產生的稽核證據
>
> **前置知識**：第 8 章（Direct Connect）、第 14 章（Organizations、SCP、Control Tower）、第 15 章（KMS、CloudHSM）、第 16 章（GuardDuty、Security Hub）、第 40 章（landing zone）、第 41 章（集中 inspection）、第 43 章（合規與稽核）
> **考試比重**：SAA ★★☆（Domain 1）｜SAP ★★★（Domain 1 安全控制與多帳號、Domain 3 改善安全）

## 50.1 故事：監理機關的第一封信

Wanderly 的旅客常常問：「可以分期付款嗎？」於是 Wanderly 在日本成立了子公司 **Wanderly Pay**，提供旅遊分期與電子錢包服務。這是一門受監理的生意：Wanderly Pay 要向日本的金融監理機關登記，要通過支付卡產業資料安全標準 **PCI DSS（Payment Card Industry Data Security Standard）** 的評估，而且合作銀行在簽約前會派人做資安查核。

專案啟動第二週，法遵主管轉來監理機關與合作銀行的要求清單。工程師阿哲讀完，發現沒有一條是「用某個服務」，全都是「要能證明」：證明客戶資料沒有離開日本、證明日誌沒有被任何人修改過、證明管理金鑰的人不能使用金鑰、證明工程師不能隨便進入正式環境、證明系統對外只連到核准的對象、證明每一項控制在過去一整年都持續有效。

阿哲在第 40 章幫 Wanderly 集團建好了 landing zone，但那是為一般 workload 設計的。Wanderly Pay 的要求更嚴：它需要在集團的 Organization 裡切出一塊「更高圍牆」的區域，讓稽核人員可以清楚地畫出邊界，說「邊界以內的每一個控制，我們都看得到證據」。

這一章不重新介紹 SCP、KMS 或 Network Firewall 的基礎，它們分別在第 14、15、41 章。我們把需求逐條對應到設計，然後問兩個問題：「這樣做在 SAA 的範圍內夠不夠？」以及「到了 SAP 的規模與監理要求，要怎麼演進？」

## 50.2 需求與限制

| 編號 | 要求（翻譯成工程語言） | 對應設計 |
|---|---|---|
| R1 | 客戶資料只能存放與處理在日本境內 | 只允許東京（`ap-northeast-1`）與大阪（`ap-northeast-3`）；以 SCP 預防，以 Config 偵測 |
| R2 | 持卡人資料環境（CDE）與其他系統分離，縮小 PCI 稽核範圍 | CDE 放在專屬 OU 與帳號，網路上分段 |
| R3 | 所有跨網段與對外流量都要經過檢查，對外只能連到核准的網域 | 集中 inspection VPC + Network Firewall |
| R4 | 金鑰管理與金鑰使用職責分離；特定金鑰必須在單一租戶的 HSM 中 | KMS key policy 職責分離；CloudHSM 與 custom key store |
| R5 | 稽核日誌保存 7 年，任何人（含系統管理者）都不能修改或刪除 | Organization trail → Log Archive 帳號，S3 Object Lock compliance mode |
| R6 | 平時沒有人有正式環境的常駐管理權限；緊急時可以進入，且全程留下紀錄 | IAM Identity Center 臨時權限；break-glass 流程 |
| R7 | 持續、可重現地提供控制有效的證據 | Config（conformance pack、aggregator）、Security Hub CSPM |
| R8 | 東京 Region 故障時，核心服務 4 小時內在大阪恢復 | 跨 Region 複寫只到大阪；AWS Backup 跨 Region copy |
| R9 | 與合作銀行的連線不經 Internet | Direct Connect + private VIF／transit VIF |

這張表的第三欄是設計，但對稽核人員來說，更重要的是每一列背後的**證據**：R1 的證據是 SCP 的內容與 Config 的合規報告；R5 的證據是 bucket 的 Object Lock 設定與 CloudTrail 的完整性驗證結果。設計時就要同時想好「怎麼證明」，否則系統做對了也過不了稽核。

## 50.3 SAA 等級解法：在一個 workload 裡把基本功做對

如果只考慮單一 workload，SAA 等級的設計已經能涵蓋許多要求：

- **網路**：應用程式與資料庫放在 private subnet，存取 S3、KMS、Secrets Manager 走 VPC endpoint，不經 Internet（第 5、6 章）。
- **加密**：RDS、EBS、S3 都使用 customer managed KMS key 加密；資料庫密碼放在 Secrets Manager 並自動輪換；傳輸一律 TLS（第 15 章）。
- **身份**：人員用 IAM Identity Center 登入並啟用 MFA；應用程式用 IAM role，不使用長期 access key（第 12、13 章）。
- **偵測**：啟用 CloudTrail、Config、GuardDuty，敏感資料所在的 bucket 用 Macie 掃描個資（第 16 章）。
- **日誌保存**：CloudTrail 寫到啟用 Object Lock 的 S3 bucket。

這些都是必要的，但對 Wanderly Pay 來說不夠，原因有三個。第一，**所有控制都在同一個帳號裡**：帳號管理員可以關掉 CloudTrail、修改 bucket policy、刪除 Config rule，「防止管理員竄改」的要求無法成立。第二，**沒有邊界**：如果 CDE 與一般系統在同一個帳號或同一個平坦的網路中，PCI 稽核範圍會擴大到整個環境。第三，**證據是零散的**：每個帳號各自的設定，無法讓稽核人員一次看到整個組織的控制狀態。解決這三個問題，就是 SAP 等級的工作。

## 50.4 演進到 SAP 等級（一）：landing zone 與帳號切分

Wanderly Pay 在集團的 Organization 中擁有自己的 OU 子樹。設計原則是**依控制要求切 OU，依爆炸半徑切帳號**（第 40 章）：

```text
Root（集團 Organization，management account 不放任何 workload）
├── Security OU
│   ├── Log Archive 帳號 ......... 全組織日誌，Object Lock
│   └── Security Tooling 帳號 .... GuardDuty／Security Hub／Config／Macie 的 delegated admin
├── Infrastructure OU
│   ├── Network 帳號 ............. Transit Gateway、inspection VPC、egress VPC、DX
│   └── Shared Services 帳號 ..... CI/CD、共用 AMI pipeline
├── Wanderly（集團一般 workload，略）
└── WanderlyPay OU ............... SCP：Region 限制、禁止公開資源
    ├── PCI-CDE OU ............... 額外 SCP：禁止建立 IGW、只允許核准的服務
    │   ├── pay-cde-prod 帳號 ..... 卡片 token 化、授權交易
    │   └── pay-cde-dr 帳號（大阪）
    ├── Prod OU
    │   └── pay-wallet-prod、pay-lending-prod 帳號
    ├── NonProd OU
    │   └── pay-dev、pay-staging 帳號（只用合成資料）
    └── BreakGlass OU
        └── pay-breakglass 帳號 ..... 緊急存取用，平時無人使用
```

為什麼 CDE 要有自己的 OU 和帳號？PCI DSS 的稽核範圍是「儲存、處理或傳輸持卡人資料的系統，以及能連到它們的系統」。如果 CDE 和電子錢包服務在同一個帳號、同一個 VPC，錢包服務也會被納入稽核範圍。把 CDE 隔到獨立帳號，加上網路分段（下一節），稽核範圍就能縮小到少數幾個帳號，其他服務的開發節奏也不會被 PCI 的變更流程綁住。

更進一步，CDE 本身的範圍也可以縮小：卡號一進入系統就交給 **tokenization（代碼化）** 服務換成無意義的 token，其他服務只拿 token 處理；只有 tokenization 服務需要接觸真正的卡號。需要 PIN 處理、卡片資料加密這類支付專用密碼學功能時，AWS 也有 **AWS Payment Cryptography** 這個受管服務可以評估。

**Guardrail 的三種類型**都要用上（第 14、40 章）：

| 類型 | 作用時間 | Wanderly Pay 的例子 |
|---|---|---|
| 預防式（preventive） | 動作發生前就拒絕 | SCP 禁止日本以外的 Region、禁止停用 CloudTrail、CDE 帳號禁止建立 Internet Gateway；RCP 讓 S3 與 KMS 資源只接受組織內的 principal |
| 偵測式（detective） | 事後發現不合規 | Config rule 偵測未加密的 EBS、公開的 S3；Security Hub 的 PCI DSS 標準檢查 |
| 主動式（proactive） | 部署前檢查 IaC | CloudFormation Hooks 在建立資源前檢查 template，例如拒絕沒有加密設定的 RDS |

資料主權（R1）的預防式控制是一條 Region 限制的 SCP。Control Tower 本身提供 Region deny control，可以直接啟用；若要自己撰寫，形式如下（節錄，豁免清單要依實際使用的 global 服務調整）：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideJapanRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "organizations:*",
        "sts:*",
        "support:*",
        "cloudfront:*",
        "route53:*",
        "budgets:*",
        "health:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["ap-northeast-1", "ap-northeast-3"]
        },
        "ArnNotLike": {
          "aws:PrincipalARN": "arn:aws:iam::*:role/AWSControlTowerExecution"
        }
      }
    }
  ]
}
```

`NotAction` 列出的是 IAM、Organizations、Route 53 這類 global 服務：它們的 API 端點在 `us-east-1` 等特定 Region，不豁免的話會連帶無法使用。`ArnNotLike` 讓 Control Tower 的管理角色不受限制，否則 landing zone 本身的維護會失敗。

Region 限制只是 R1 的一半。另一半是**資料的複寫目的地**：S3 Cross-Region Replication、AWS Backup 的跨 Region copy、KMS multi-Region key 的 replica、Aurora 的跨 Region 複寫，目的地都只能是大阪。這些設定由 Config rule 持續檢查。另外，CloudFront 這類 global 服務會在全球的 edge 快取內容，所以含個資的 API 回應必須設定為不快取。

## 50.5 演進到 SAP 等級（二）：集中 inspection 與網路分段

R3 要求所有跨網段與對外流量都要被檢查。Wanderly Pay 採用第 41 章的集中 inspection 架構：所有 VPC 都接到 Network 帳號的 Transit Gateway，流量先送到 inspection VPC 的 **AWS Network Firewall**，檢查通過才轉往目的地。

```text
 pay-cde-prod VPC        pay-wallet-prod VPC        合作銀行（地端）
       │ ①                      │                        │ DX（transit VIF）
       ▼                        ▼                        ▼
 ┌─────────────────── Transit Gateway（Network 帳號）──────────────────┐
 │  rt-cde：0.0.0.0/0 → inspection     rt-workload：0.0.0.0/0 → inspection │
 │  rt-inspection：各 VPC CIDR → 對應 VPC；0.0.0.0/0 → egress VPC      │
 └──────────────┬─────────────────────────────────────────────────────┘
                │ ② appliance mode 開啟
                ▼
       [Inspection VPC：Network Firewall endpoint（每 AZ 一個）]
                │ ③ stateful 規則：CDE ↔ wallet 只允許 443 到 token API
                │                    對外只允許核准網域（TLS SNI 比對）
                ▼
       [Egress VPC：NAT Gateway（每 AZ）] ──► Internet（只到核准網域）
```

① 每個 VPC 的 TGW attachment 關聯到依安全等級區分的 TGW route table：CDE 一張、一般 workload 一張。這兩張 route table 的 default route 都指向 inspection VPC，所以 CDE 與錢包服務之間沒有直接的路由，彼此要通訊一定要經過防火牆。這就是 TGW 的**網路分段（segmentation）**（第 7 章）。

② Inspection VPC 的 TGW attachment 必須開啟 **appliance mode**。原因是 Network Firewall 是 stateful（有狀態）的：它要看到同一條連線的去程和回程，才能判斷這是合法連線的回應。沒有 appliance mode 時，TGW 可能把去程送到 AZ-a 的防火牆端點、回程送到 AZ-c 的端點，AZ-c 的防火牆沒看過這條連線的開頭，就會把回程丟掉。Appliance mode 讓 TGW 對同一條連線固定選擇同一個 AZ 的 attachment，維持**對稱路由（symmetric routing）**。

③ Network Firewall 的 stateful 規則做兩件事：東西向（east-west，內部服務之間）只允許 CDE 與錢包之間的特定 port 與方向；南北向（north-south，對外）用網域清單比對 HTTP Host 或 TLS SNI，只允許連到金流網路、合作銀行與作業系統更新來源。再加上 **Route 53 Resolver DNS Firewall**，讓 VPC 內的機器連不認識的網域都解析不到，兩層一起擋住資料外洩與惡意程式回連（第 16、41 章）。

與合作銀行的連線（R9）使用 Direct Connect 的 transit VIF 接到 Direct Connect gateway，再連到同一個 Transit Gateway，所以銀行的流量也經過 inspection（第 8 章）。為了高可用，兩條 DX 連線分別接在不同的 DX location，並以 Site-to-Site VPN 作為備援路徑。

> [!warning] 常見誤解
> 「Security group 已經很嚴格了，不需要集中 inspection。」Security group 控制的是「哪個 IP 和 port 可以連」，看不到網域名稱、TLS SNI 或應用層內容，也分散在每個帳號由各團隊管理。集中 inspection 提供的是**一個由安全團隊掌控、所有流量必經的檢查點**，稽核人員只要檢查一套規則與一份日誌。兩者是互補的。

## 50.6 演進到 SAP 等級（三）：KMS、CloudHSM 與職責分離

R4 有兩個部分：「職責分離」與「特定金鑰在單一租戶 HSM」。

**職責分離寫在 key policy 裡。** KMS 的 key policy 是金鑰的主要存取控制（第 15 章）。Wanderly Pay 把權限分成三種角色：

- **金鑰管理員**（安全團隊）：可以建立、停用、排程刪除金鑰、修改 key policy，但**不能**用金鑰加解密。
- **金鑰使用者**（應用程式角色）：只能 `kms:Encrypt`、`kms:Decrypt`、`kms:GenerateDataKey`，不能修改金鑰。
- **稽核人員**：只能 `kms:DescribeKey`、`kms:GetKeyPolicy`、`kms:ListGrants` 等唯讀動作。

另外，SCP 禁止安全團隊以外的任何人呼叫 `kms:ScheduleKeyDeletion` 與 `kms:PutKeyPolicy`。即使金鑰被誤排刪除，KMS 也有 7 到 30 天（預設 30 天）的等待期可以取消；Wanderly Pay 對排程刪除事件設了 EventBridge 告警，一發生就通知安全團隊。

**KMS 還是 CloudHSM？** 這是金融案例最常見的選型題：

| 需求 | 選擇 | 理由 |
|---|---|---|
| 一般資料的靜態加密，要和 S3、EBS、RDS 原生整合 | KMS customer managed key | 全受管、高可用，與 AWS 服務整合最完整 |
| 金鑰必須在由本公司獨占控制的單一租戶 HSM，但仍要用 S3、RDS 的原生加密 | KMS custom key store（CloudHSM key store） | KMS 的 API 與整合不變，金鑰材料產生並存放在自己的 CloudHSM 叢集 |
| 應用程式需要直接呼叫 HSM（PKCS#11、JCE），例如自訂的簽章或 SSL offload | CloudHSM | 單一租戶 HSM，由客戶管理 HSM 使用者與金鑰 |
| 金鑰必須放在 AWS 以外、由公司自己的 HSM 保管 | KMS external key store（XKS） | 金鑰留在外部，KMS 每次加解密都要呼叫外部 key manager，可用性與延遲取決於外部系統 |

Wanderly Pay 的選擇是：一般資料用 KMS customer managed key；CDE 中 tokenization 服務的主金鑰使用 CloudHSM key store，因為合作銀行要求這把金鑰存放在只有 Wanderly Pay 能控制的 HSM。CloudHSM 叢集必須至少有兩台 HSM 分布在不同 AZ，才能被 KMS 作為 custom key store 使用，也才有高可用。

> [!warning] 常見誤解
> 「CloudHSM 比 KMS 安全，因為它有 FIPS 驗證。」KMS 使用的 HSM 本身也通過 FIPS 140 Level 3 等級的驗證。兩者的差別不在驗證等級，而在**控制權與租戶模型**：CloudHSM 是單一租戶、由客戶自己管理 HSM 使用者與金鑰，AWS 無法存取金鑰；代價是客戶要自己負責叢集的高可用、備份與使用者管理。題目沒有要求「單一租戶」或「客戶獨占控制」時，KMS 通常是營運負擔最低的答案。

## 50.7 演進到 SAP 等級（四）：不可竄改的日誌

R5 要求日誌保存 7 年、任何人都不能修改或刪除。「任何人」包含 Wanderly Pay 自己的帳號管理員、甚至集團的雲端團隊。設計分四層：

1. **集中收集。** 在 management account（或 delegated administrator）建立 **organization trail**，自動涵蓋所有成員帳號與所有 Region，成員帳號無法修改或刪除這個 trail（第 16 章）。Config、VPC Flow Logs、Network Firewall 日誌也都送到 Log Archive 帳號。
2. **WORM 儲存。** Log Archive 的 bucket 啟用 **S3 Object Lock** 的 **compliance mode**，保留期 7 年。Compliance mode 下，在保留期內**沒有任何人能刪除或覆寫物件、也不能縮短保留期，包含 root user**。另一種 governance mode 允許有特殊權限的人繞過，不符合這裡的要求。Object Lock 需要 bucket 啟用 versioning（第 23 章）。
3. **完整性可驗證。** 開啟 CloudTrail 的 **log file integrity validation**：CloudTrail 每小時產生一份 digest 檔，包含該小時每個日誌檔的 SHA-256 雜湊值並以數位簽章簽署。稽核人員可以用 `aws cloudtrail validate-logs` 驗證任何日誌檔沒有被修改、刪除或偽造。Object Lock 證明「改不了」，digest 證明「沒被改過」，兩者互補。
4. **權限隔離。** Log Archive 帳號只有安全團隊能以唯讀方式存取；bucket 使用 Log Archive 帳號中的 KMS key 加密。SCP 禁止成員帳號呼叫 `cloudtrail:StopLogging`、`cloudtrail:DeleteTrail` 與 `config:StopConfigurationRecorder`。

日誌放 7 年的成本不低。Object Lock 的保留設定在物件透過 lifecycle 轉換到 Glacier 類儲存類別後仍然有效，所以 Wanderly Pay 讓日誌在 90 天後轉到 Glacier Flexible Retrieval、一年後轉到 Glacier Deep Archive。

備份也需要同樣的保護。勒索軟體或惡意的內部人員可能刪除備份，再破壞正式資料。Wanderly Pay 的 AWS Backup vault 啟用 **Vault Lock 的 compliance mode**：在設定後的寬限期（至少 3 天）結束後，任何人都無法刪除 vault 中的 recovery point 或修改保留設定。備份同時複製到大阪的另一個帳號的 vault（第 34、43 章）。

## 50.8 演進到 SAP 等級（五）：存取管理與 break-glass

R6 要求「平時沒有人有正式環境的常駐管理權限」。Wanderly Pay 的日常存取全部透過 IAM Identity Center（第 13 章）：

- 工程師在 production 帳號只有唯讀的 permission set。
- 需要變更時，透過核准流程取得有時效的提升權限（例如 2 小時），所有操作由 CloudTrail 記錄，並關聯到具名的員工身份。
- 正式環境的變更原則上只透過 pipeline 以 IaC 執行，人員不直接在 console 修改。

但 Identity Center 依賴公司的外部 IdP。如果 IdP 本身故障，或者事故正好是 IdP 被入侵，所有人都進不了 AWS。這時需要 **break-glass（打破玻璃）** 存取：

1. 在 `pay-breakglass` 帳號建立少數幾個 IAM user，各自綁定**硬體 MFA**。密碼與 MFA 裝置分開保管，啟用時需要兩個人在場（雙人控制）。
2. 這些 user 唯一的權限是 assume 各 production 帳號中的 `BreakGlassRole`；各帳號的 `BreakGlassRole` trust policy 只信任這個帳號。
3. EventBridge 規則監聽這些 user 的 `ConsoleLogin` 事件與 `BreakGlassRole` 的 AssumeRole 事件，一發生就通知資安主管與法遵。
4. 使用後立即更換密碼並寫事後報告；每季演練一次，確認流程與憑證都還有效。

成員帳號的 root user 則透過 Organizations 的**集中 root 存取管理**移除長期憑證，需要執行只有 root 能做的動作時，由 management account 或 delegated administrator 發起短時效的 root 工作階段（第 40 章）。

> [!tip] 考試提示
> Break-glass 題的正確選項通常同時具備四個特徵：**獨立於日常 IdP**、**強 MFA**、**使用時立即告警**、**定期演練**。只做到「建一個管理員帳號把密碼鎖在保險箱」而沒有告警與演練的選項，通常不是最佳答案。

## 50.9 演進到 SAP 等級（六）：持續產生的稽核證據

R7 要求的不是「某一天合規」，而是「過去一整年都合規，並能拿出證據」。人工截圖無法滿足這個要求，Wanderly Pay 讓證據自動產生：

- **AWS Config** 在所有帳號與 Region 記錄資源設定的變更歷史，並以 **conformance pack**（一組 Config rule 的集合）持續評估。**Aggregator** 把所有帳號的結果彙整到 Security Tooling 帳號（第 43 章）。
- **AWS Security Hub** 以 delegated administrator 集中在 Security Tooling 帳號，啟用 PCI DSS 與 AWS Foundational Security Best Practices 標準，持續產生控制檢查結果。新版文件中，這部分的標準與控制檢查功能稱為 Security Hub CSPM。
- **Organization conformance pack**：從 Config 的 delegated administrator 把 AWS 提供的「Operational Best Practices for PCI DSS」範本部署到 WanderlyPay OU 的所有帳號。這個範本把 PCI DSS 的各項技術要求對應到一組 Config rule，Config 會持續評估並保留每個資源的合規歷史；稽核時用 Config 的 advanced query 匯出指定期間的結果作為證據。政策文件、人員訓練這類非技術控制不在 Config 的範圍內，需要另外以 GRC（治理、風險與合規）工具或文件流程管理。
- **AWS Artifact** 提供 **AWS 自己**的合規報告（例如 AWS 的 PCI DSS 評估結果與 SOC 報告）。它證明的是「AWS 負責的那一半」，Wanderly Pay 負責的那一半仍然要靠上面這些機制產生的證據，這正是第 2 章的責任分擔模型（shared responsibility model）。
- **Amazon Macie** 定期掃描 S3，證明卡號或個資沒有出現在不該出現的 bucket。
- **AWS Backup restore testing** 定期自動還原並驗證備份，證明 R8 的復原能力不只是紙上計畫。

> [!note] 為什麼不是 Audit Manager？
> 第 16 章介紹過 **AWS Audit Manager**：選一個 PCI DSS 等預建框架，它會自動從 Config、Security Hub、CloudTrail 收集證據並產生評估報告。但 Audit Manager 已進入維護模式，自 2026 年 4 月 30 日起新帳號無法再設定這個服務，既有客戶才能繼續使用。Wanderly Pay 是新建立的帳號，所以照 AWS 的建議改用 Config conformance pack。考試題庫早於這次變更，題目若問「自動收集稽核證據並對應到合規框架」，答案仍是 Audit Manager。

## 50.10 完整架構圖

```text
                         ┌──────────── 集團 Organization ────────────┐
                         │ management account：SCP／RCP、org trail     │
                         └───────────────┬────────────────────────────┘
        ┌───────────────────────┬────────┴─────────────┬───────────────────────────┐
        ▼                       ▼                      ▼                           ▼
 [Log Archive]          [Security Tooling]        [Network]                  [WanderlyPay OU]
 S3 Object Lock         GuardDuty／Security Hub   TGW + 分段 route tables     PCI-CDE OU
 （compliance 7 年）    Config aggregator         Inspection VPC：            ├ pay-cde-prod（東京）
 CloudTrail digest      Conformance packs         Network Firewall            │  tokenization
 Backup Vault Lock      Macie                     （appliance mode）          │  CloudHSM key store
 複本 → 大阪            EventBridge 告警          Egress VPC：NAT + 網域清單   └ pay-cde-dr（大阪）
                                                  DNS Firewall                Prod OU：wallet、lending
                                                  DX ×2 + VPN 備援 → 合作銀行  BreakGlass OU
        ▲                       ▲                      ▲                           │
        └──── 日誌、設定紀錄 ───┴──── findings ────────┴──── 所有流量 ─────────────┘
```

沿三條線讀這張圖。**流量線**：任何 workload VPC 之間、往 Internet、往合作銀行的流量，都經 TGW 進入 inspection VPC，由 Network Firewall 依規則放行。**日誌線**：所有帳號的 CloudTrail、Config、Flow Logs、防火牆日誌都流向 Log Archive，在那裡被 Object Lock 鎖住 7 年。**證據線**：Security Tooling 帳號彙整 GuardDuty、Security Hub、Config 的結果，conformance pack 把 Config rule 對應到 PCI DSS 的控制要求。三條線的終點都不在 workload 帳號裡，這就是「workload 帳號的管理員無法竄改證據」的結構性保證。

## 50.11 設計決策紀錄：為何選 A 不選 B

| 決策 | 選擇 A | 不選 B | 理由 |
|---|---|---|---|
| CDE 邊界 | 獨立 OU 與帳號 | 與其他服務同帳號、以 tag 區分 | 帳號是最強的隔離邊界；PCI 稽核範圍縮到少數帳號 |
| 資料主權 | SCP（或 Control Tower Region deny）預防 + Config 偵測 | 只用 Config 偵測 | 偵測只能事後發現，資料可能已經離開日本 |
| 流量檢查 | 集中 inspection VPC + Network Firewall | 每個 VPC 各自部署防火牆 | 一套規則、一個日誌來源，營運與稽核都較簡單；分散部署成本與管理負擔都高 |
| 對外過濾 | Network Firewall 網域清單 + DNS Firewall | 只用 security group 限制 IP | 外部服務的 IP 會變動，網域層級的規則較能精確表達「只連核准對象」 |
| Tokenization 主金鑰 | KMS custom key store（CloudHSM） | 直接使用 CloudHSM API | 合作銀行要求單一租戶 HSM，但仍希望使用 KMS 的整合與稽核紀錄 |
| 一般資料加密 | KMS customer managed key | CloudHSM | 不需要單一租戶，KMS 營運負擔最低 |
| 日誌不可竄改 | Object Lock compliance mode | Governance mode | Governance mode 可被有權限者繞過，不符合「任何人都不能改」 |
| 日常管理存取 | Identity Center 臨時提升權限 | 常駐的管理員 role | 常駐權限違反最小權限，事故時爆炸半徑大 |
| 稽核證據 | Config conformance pack + aggregator + Security Hub 自動收集 | 每季人工截圖 | 人工證據不連續、不可重現，也無法證明期間內持續合規 |
| DR 目的地 | 大阪 | 新加坡（延遲較低的其他市場） | R1 不允許資料離開日本 |

## 50.12 故障演練

金融環境的演練除了基礎設施故障，更重要的是**安全事件**與**治理被破壞**的情境：

| 情境 | 預期行為 | 要確認的事 |
|---|---|---|
| 工程師嘗試在新加坡 Region 建立 S3 bucket | SCP 拒絕，CloudTrail 留下 `AccessDenied` 紀錄 | Global 服務豁免清單正確，正常操作不受影響 |
| 有人嘗試停用 organization trail 或刪除 Log Archive 中的物件 | SCP 與 Object Lock 拒絕；EventBridge 告警 | 告警確實送到資安值班 |
| CDE 中的 instance 嘗試連到未核准的網域 | DNS Firewall 不回應解析，Network Firewall 丟棄連線並記錄 | GuardDuty 是否同時產生 finding；事件回應 runbook 是否啟動 |
| Inspection VPC 的一個 AZ 故障 | TGW 把新連線送往其他 AZ 的防火牆端點 | 每個 AZ 都有防火牆端點與 NAT；既有連線會中斷重建，應用程式要能重試 |
| 公司的 IdP 無法使用 | 依 break-glass 流程，雙人取得憑證登入，資安主管立即收到通知 | 憑證與 MFA 裝置有效；流程在演練中實際走過 |
| KMS key 被誤排程刪除 | EventBridge 告警，安全團隊在等待期內取消刪除 | 等待期設為最長 30 天；告警規則涵蓋所有帳號 |
| CloudHSM 叢集中一台 HSM 故障 | 另一個 AZ 的 HSM 繼續服務，叢集自動補上新 HSM | 叢集至少兩台 HSM 分布在不同 AZ |
| 東京 Region 不可用 | 依 runbook 在大阪的 DR 帳號以備份與複寫資料恢復核心服務 | Backup restore testing 的結果證明 4 小時內可以完成 |

## 50.13 成本思路

金融等級的控制有實際的成本，設計時要知道錢花在哪裡，才能在不降低控制的前提下最佳化：

- **集中 inspection**：Network Firewall 依端點小時數與處理的資料量收費，Transit Gateway 依 attachment 小時數與處理量收費。集中部署比每個 VPC 各放一套防火牆便宜得多；而大量流向 S3、DynamoDB 的流量應走各 VPC 的 gateway endpoint，不必經過 TGW 與防火牆（endpoint policy 本身也是控制點）。
- **CloudHSM**：依 HSM 數量按小時收費，而且至少要兩台才有高可用，是固定成本中的大項。只把真正需要單一租戶 HSM 的金鑰放進 custom key store，其餘使用 KMS。
- **KMS 請求費**：大量 S3 物件使用 SSE-KMS 時，開啟 **S3 Bucket Keys** 可以大幅減少對 KMS 的請求次數與費用（第 22 章）。
- **日誌**：CloudTrail 的管理事件第一份複本免費，但 data events（例如 S3 物件層級操作）依事件數收費，只對 CDE 與敏感 bucket 開啟。7 年的日誌用 lifecycle 轉到 Glacier 類儲存，Object Lock 仍然有效。
- **合規服務**：Config 依記錄的設定項目與規則評估次數收費，Security Hub 依檢查次數收費。排除不需要的資源類型記錄、避免重複啟用相同控制，可以降低成本而不降低涵蓋範圍。
- **縮小範圍本身就是最大的成本槓桿**：CDE 越小，需要最嚴格控制、最頻繁稽核的系統就越少。Tokenization 讓大部分服務完全不接觸卡號，是金融架構中投資報酬率最高的設計之一。

## 50.14 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 日誌任何人（含 root）都不能刪除或修改、保存 N 年 | S3 Object Lock compliance mode（需 versioning） |
| 證明 CloudTrail 日誌沒有被竄改 | Log file integrity validation（digest 檔 + `validate-logs`） |
| 所有帳號的 API 紀錄集中、成員帳號無法關閉 | Organization trail + Log Archive 帳號 + SCP |
| 資料不得離開特定國家／Region | SCP `aws:RequestedRegion`（豁免 global 服務）或 Control Tower Region deny |
| 單一租戶 HSM、客戶獨占控制金鑰 | CloudHSM；要保留 AWS 服務整合時用 KMS custom key store |
| 金鑰必須放在 AWS 以外 | KMS external key store |
| 金鑰管理者不能使用金鑰 | Key policy 職責分離 |
| 集中 inspection、stateful 防火牆、回程被丟棄 | TGW inspection VPC attachment 開啟 appliance mode |
| 對外只允許連到核准網域 | Network Firewall 網域清單（SNI／Host）+ Route 53 Resolver DNS Firewall |
| 縮小 PCI DSS 稽核範圍 | CDE 獨立帳號／OU、網路分段、tokenization |
| IdP 故障時仍要能進入 AWS | Break-glass：獨立 IAM user + 硬體 MFA + 告警 + 演練 |
| 持續收集合規證據、產生稽核報告 | 考試答案：Audit Manager；實務上新帳號已無法啟用，改用 Config conformance pack + aggregator |
| 取得 AWS 自己的 PCI／SOC 報告 | AWS Artifact |
| 找出 S3 中的卡號或個資 | Amazon Macie |
| 備份不能被任何人刪除 | AWS Backup Vault Lock compliance mode |

**常見陷阱**：

1. 以為 SCP 能授予權限：SCP 只設定上限，帳號內仍需要 IAM policy 授權；SCP 也不影響 management account，所以 management account 不應放 workload。
2. 用 governance mode 實現「任何人都不能刪除」：governance mode 可以被有 `s3:BypassGovernanceRetention` 權限的人繞過。
3. 以為 AWS Artifact 能證明自己的系統合規：它只提供 AWS 負責範圍的報告。
4. Region 限制 SCP 忘了豁免 global 服務：IAM、Organizations 等操作會跟著被拒絕。
5. 集中 inspection 沒開 appliance mode：跨 AZ 的回程流量被 stateful 防火牆丟棄，症狀是間歇性連線失敗。
6. 以為 CloudHSM 的優勢是「FIPS 等級比 KMS 高」：真正的差異是單一租戶與客戶獨占控制，代價是營運負擔。

## 本章重點整理

- 金融與 PCI 需求的核心是「能證明」，設計每一個控制時都要同時設計它的證據來源。
- SAA 等級的基本功（private subnet、VPC endpoint、KMS 加密、Secrets Manager、CloudTrail）是必要條件，但單一帳號無法防止管理員竄改控制與證據。
- 依控制要求切 OU、依爆炸半徑切帳號；CDE 放在獨立 OU 與帳號，加上 tokenization，可以把 PCI 稽核範圍縮到最小。
- Guardrail 要同時有預防式（SCP、RCP）、偵測式（Config、Security Hub）與主動式（CloudFormation Hooks）三種。
- 資料主權用 Region 限制 SCP 或 Control Tower Region deny 預防，並記得豁免 global 服務；複寫、備份、multi-Region key 的目的地也要受限。
- 集中 inspection 以 TGW route table 做分段、流量必經 Network Firewall，inspection VPC attachment 必須開啟 appliance mode 維持對稱路由。
- 對外過濾使用 Network Firewall 的網域清單與 DNS Firewall，比只限制 IP 更精確。
- Key policy 落實職責分離：管理員不能使用金鑰、使用者不能管理金鑰；誤排刪除有 7 到 30 天的等待期可取消。
- 需要單一租戶、客戶獨占控制的金鑰時用 CloudHSM；要保留 AWS 服務原生整合時用 KMS custom key store，叢集至少兩台 HSM 分在不同 AZ。
- 不可竄改的日誌由 organization trail、Log Archive 帳號、Object Lock compliance mode、log file integrity validation 與 SCP 共同構成。
- 備份以 AWS Backup Vault Lock compliance mode 保護，並跨帳號、跨 Region（在允許範圍內）複製。
- 日常存取用 Identity Center 臨時權限；break-glass 要獨立於 IdP、使用硬體 MFA、使用即告警、定期演練。
- 稽核證據由 Config conformance pack、aggregator 與 Security Hub 持續自動產生（考試題的答案常是 Audit Manager，但它已進入維護模式，自 2026-04-30 起新帳號無法再設定）；AWS Artifact 只提供 AWS 自己的合規報告。

## 本章練習題

### 練習 50-1｜SAA｜單選｜日誌保存的不可竄改性

一家金融公司要把 CloudTrail 日誌保存 7 年。法規要求在保存期間內，任何人（包括擁有 root 權限的管理員）都不能刪除或覆寫日誌，也不能縮短保存期限。

哪個做法能滿足需求？

- A. 在 S3 bucket 啟用 versioning 與 MFA Delete，並以 bucket policy 拒絕所有刪除動作
- B. 啟用 S3 Object Lock 的 governance mode，保留期 7 年，並只授予安全團隊 `s3:BypassGovernanceRetention` 權限
- C. 啟用 S3 Object Lock 的 compliance mode，設定 7 年的保留期
- D. 把日誌送到 CloudWatch Logs，並把 log group 的保存期限設為 7 年

> [!answer]- 答案：C
> **A ✗** MFA Delete 增加了刪除的門檻，bucket policy 也能拒絕刪除，但有權限的管理員可以修改 bucket policy，root user 也可以停用 MFA Delete，無法保證「任何人都不能刪除」。
>
> **B ✗** Governance mode 允許擁有 `s3:BypassGovernanceRetention` 權限的人繞過保留設定，只要有人有這個權限，就不符合「任何人都不能刪除」的要求。
>
> **C ✓** Compliance mode 下，保留期內任何人（包含 root user）都不能刪除或覆寫物件，也不能縮短保留期，正是法規要求的 WORM（寫入一次、多次讀取）保護。
>
> **D ✗** 有權限的人可以修改 CloudWatch Logs 的保存期限，甚至直接刪除整個 log group，它不提供 WORM 保護。
>
> **考點**：SAA-1.3｜S3 Object Lock compliance mode

### 練習 50-2｜SAA｜單選｜單一租戶 HSM 與服務整合

一家銀行的合作夥伴要求：用來加密 S3 與 RDS 資料的金鑰，必須產生並存放在由本公司獨占控制的單一租戶 HSM 中。開發團隊希望繼續使用 S3 與 RDS 原生的 SSE-KMS 加密整合，不想修改應用程式，並希望營運負擔最低。

最合適的做法是什麼？

- A. 使用 KMS customer managed key，並啟用自動金鑰輪換
- B. 建立至少兩台 HSM 分布在不同 AZ 的 CloudHSM 叢集，並以它建立 KMS custom key store，在其中建立 KMS key 供 S3 與 RDS 使用
- C. 建立 CloudHSM 叢集，修改應用程式在寫入 S3 與 RDS 前以 PKCS#11 API 自行加密資料
- D. 使用 KMS external key store，把金鑰放在公司資料中心的 HSM

> [!answer]- 答案：B
> **A ✗** KMS customer managed key 的金鑰材料存放在 KMS 的多租戶 HSM 中，不符合「單一租戶、本公司獨占控制」的要求。
>
