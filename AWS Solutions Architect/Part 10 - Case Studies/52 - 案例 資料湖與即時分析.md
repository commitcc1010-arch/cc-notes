# 第 52 章　案例：資料湖與即時分析平台：從一個分析帳號到集團資料平台

> [!abstract] 本章地圖
> **你會學到**：
> - 把串流擷取、S3 分層、Glue、Lake Formation、Athena、Redshift 與 QuickSight 組成一個完整的分析平台，並說明每個元件的責任邊界
> - 分辨 SAA 等級（單一帳號、單一團隊）與 SAP 等級（多帳號、多資料擁有者、集中治理）的資料平台設計差異
> - 為「一分鐘內看到」與「每天看一次」兩種時效需求，選擇不同的資料路徑
> - 處理資料平台最棘手的治理問題：欄位與資料列權限、個資刪除、支付卡資料不得入湖
> - 從儲存、掃描、運算三個方向拆解分析平台的帳單，並預先演練五種常見故障
>
> **前置知識**：第 23 章（S3 儲存類別與 lifecycle）、第 30 章（資料湖與分析）、第 31 章（Streaming）、第 40 章（多帳號）
> **考試比重**：SAA ★★☆（Domain 3 資料擷取與轉換、Domain 4 成本）｜SAP ★★☆（Domain 2、3 的效能與成本、多帳號治理）

## 52.1 故事：兩套報表，兩個數字

第 30 章的分析平台上線一年多，Wanderly 的資料分析師小周已經升任資料平台負責人。平台本身運作良好：點擊事件經第 31 章的 Kinesis 管線流進 S3，訂單資料透過 zero-ETL 進入 Redshift，行銷與財務每天看 QuickSight 儀表板。

麻煩來自併購。第 51 章把旅行社的系統搬上 AWS 之後，集團第一次召開合併營收會議，Wanderly 的儀表板說上季團體旅遊營收是 4.2 億，旅行社自己的 Oracle 報表說是 3.7 億。兩邊都沒錯：一邊用訂單成立日，一邊用出發日；一邊含稅，一邊不含。CFO 的結論是：「我要一個大家都相信的數字，而且我要知道它是從哪裡來的。」

同一週，營收管理團隊提出另一個需求：促銷活動期間，某些熱門旅館的點擊量會在幾分鐘內暴增。他們希望**一分鐘內**在儀表板上看到「點擊多、但房價沒調」的旅館，而不是隔天才從報表發現錯過了機會。再加上法務提醒：會員可以依個資法要求刪除自己的資料，而目前沒有人說得清楚，一位會員的資料散落在湖裡的哪些檔案。

小周把這些問題帶到架構會議。這一章不再重新介紹 Glue 或 Athena 怎麼運作（那是第 30、31 章的工作），而是把它們放進一個要同時滿足時效、治理、多團隊與成本的真實案例裡，看每個決策是怎麼做出來的。

## 52.2 需求與限制

| 類型 | 項目 | 內容 |
|---|---|---|
| 硬限制 | 單一事實來源 | 集團營收指標只能有一套定義與一個計算位置，所有報表都從這裡讀 |
| 硬限制 | 時效 | 營收管理的「熱門旅館」儀表板延遲 ≤ 1 分鐘；財務報表 T+1 即可 |
| 硬限制 | 個資 | 分析師預設看不到 email、電話、身分證號；行銷只能看到自己負責市場的會員資料；會員刪除請求 30 天內完成 |
| 硬限制 | 支付卡 | 卡號等持卡人資料不得進入資料湖（否則整個資料平台都落入 PCI DSS 範圍，第 51 章） |
| 硬限制 | 資料擁有權 | 訂單資料由訂房團隊擁有，旅行社資料由旅行社團隊擁有；平台團隊不擁有業務資料，只負責基礎與治理 |
| 現況 | 資料量 | 點擊事件尖峰每秒約 3 萬筆；S3 上已累積約 600 TB，其中 70% 是一年以上沒人讀的原始 JSON |
| 現況 | 帳單 | Athena 費用半年內成長三倍；有分析師每天跑掃描整個 raw 層的查詢 |
| 希望 | 自助 | 新的分析團隊（例如客服品質團隊）能在一週內自助取得需要的資料 |

最後一列「希望」看起來不起眼，卻是 SAA 與 SAP 設計的分水嶺：如果每個新需求都要平台團隊幫忙開權限、複製資料、建 pipeline，平台團隊就會成為整個公司的瓶頸。

## 52.3 SAA 等級解法：一個帳號裡的標準資料湖

先看單一團隊、單一帳號時的「教科書解法」，這也是 SAA 題目最常出現的組合。

```text
 App / Web ──① 點擊事件──► [Kinesis Data Streams] ──② ──► [Data Firehose]
                                                          │ Lambda 遮罩 + 轉 Parquet + 動態分區
                                                          ▼
                      ┌──────────── S3 data lake ────────────────┐
 Aurora / RDS ──③──►  │ raw/ → curated/（Parquet）→ analytics/    │
                      └──────────────────┬───────────────────────┘
                                ④ Glue Data Catalog（crawler / ETL job）
                                         │
                              ⑤ Athena ──┴── QuickSight（SPICE）⑥
```

① 應用程式把事件寫進 Kinesis Data Streams（KDS），保留多個 consumer 與重播的能力（第 31 章）。② Firehose 讀取 KDS，用 Lambda 遮罩 IP，把 JSON 轉成 Parquet 並依日期動態分區寫入 S3，不需要自己寫 consumer。③ 交易資料庫的資料用 export 或 DMS 匯入 raw 層。④ Glue crawler 或 ETL job 維護 Data Catalog 的表格定義，並把 raw 整理成 curated。⑤ Athena 直接對 S3 下 SQL，按掃描量計費。⑥ QuickSight 用 SPICE（記憶體內快取引擎）畫儀表板，避免每次開圖都重新掃描。

這個設計對一個團隊、一份資料完全夠用，而且每一個元件都是 serverless 或受管服務，營運負擔很低。但套到 52.2 的需求，會在四個地方卡住：

1. **時效**：Firehose 會先累積一段時間或一定大小再寫入（buffer），加上 Athena 查詢與 SPICE 刷新，從點擊到儀表板通常是數分鐘等級，達不到「一分鐘內」。
2. **治理**：只用 IAM 與 bucket policy，權限的最小單位是「S3 prefix」，做不到「這張表的 email 欄位不給看」或「只能看日本市場的資料列」。
3. **擁有權**：所有資料都複製到平台團隊的帳號，訂房團隊和旅行社團隊不再擁有自己的資料，出錯時責任不清；每多一個團隊，就多一份複製。
4. **刪除**：Parquet 檔案不能原地修改。要刪掉一位會員的資料，就要找出所有包含他的檔案、整個重寫，在 600 TB 的湖裡幾乎不可行。

## 52.4 演進到 SAP 等級：集團資料平台

小周的新設計有一句話的核心：**資料由擁有者產出、由中央治理、由使用者自助取用**。這種把資料視為各團隊「產品」、再以中央治理串起來的模式，常被稱為 **data mesh（資料網格）**（第 30 章的 SAP 加深介紹過集中式與分散式的取捨）。

### 帳號分工：producer、治理中心與 consumer

- **Producer 帳號**：`booking-data`（訂房團隊）、`agency-data`（旅行社團隊）、`clickstream-data`（平台團隊代管）。每個帳號擁有自己的 S3 bucket 與 ETL，負責把資料整理成有品質保證的 curated 表格，也就是自己的「資料產品」。
- **治理帳號** `data-governance`：放置中央的 Glue Data Catalog 與 Lake Formation 設定。Producer 把 curated 表格登錄到這裡，治理團隊用標籤決定誰能看什麼。
- **Consumer 帳號**：`analytics-finance`、`analytics-marketing`、`analytics-revenue`。各團隊在自己的帳號裡用 Athena 或 Redshift 查詢，**運算費用算在自己帳號**，不必複製資料。

這個分工直接對應第 40 章的觀念：帳號是權限、帳單與故障的邊界。財務團隊跑了一個昂貴查詢，帳單出現在 `analytics-finance`，而不是平台團隊。

### 權限：Lake Formation 與 LF-Tags

第 30 章說過，**Lake Formation** 讓你用「資料庫、表格、欄位、資料列」的語言授權，取代 S3 prefix 的語言。在多帳號下，小周用的是 **LF-Tags（以標籤為基礎的存取控制）**：

| LF-Tag | 值 | 用途 |
|---|---|---|
| `domain` | `booking`、`agency`、`clickstream` | 資料屬於哪個業務領域 |
| `sensitivity` | `public`、`internal`、`pii` | 欄位層級標記，email、電話等欄位標為 `pii` |
| `market` | `tw`、`jp`、`global` | 搭配 data filter 做資料列層級限制 |

授權規則因此寫成「行銷團隊可以讀 `domain=booking` 且 `sensitivity` 屬於 `public` 或 `internal` 的欄位」，而不是逐張表、逐個欄位授權。新表格只要在登錄時貼對標籤，就自動適用既有規則，這正是「新團隊一週內自助取得資料」的基礎。

「行銷只能看自己市場的會員」用 **data filter（資料篩選器）** 做資料列層級的限制，例如 `market = 'jp'`。跨帳號共享時，Lake Formation 透過 AWS RAM 把授權分享給 consumer 帳號，consumer 帳號再建立指向共享表格的 **resource link**，就能在自己的 Athena 裡查詢。整個過程沒有任何資料被複製。

> [!warning] 常見誤解
> 「Lake Formation 啟用後，IAM 權限就不重要了。」Lake Formation 管的是 Data Catalog 與經它授權的資料存取，查詢者仍需要 IAM 權限去呼叫 Athena、Glue 等 API。另外，若 S3 位置沒有登錄到 Lake Formation，或表格仍保留預設的 `IAMAllowedPrincipals` 權限，存取控制仍由 IAM 與 bucket policy 決定，Lake Formation 的欄位限制不會生效。導入時要逐步把位置登錄、移除預設權限（或使用第 30 章的 hybrid access mode 過渡），並同時移除分析師以 IAM 直接讀取 S3 物件的權限，否則他們可以繞過 Athena 直接下載整個 Parquet 檔。

### 資料格式：用 Apache Iceberg 處理更新與刪除

為了解決「刪除一位會員」與「訂單會被修改」的問題，curated 層的會員與訂單表改用 **Apache Iceberg** 這種 open table format（第 30 章）。Iceberg 在 Parquet 檔案之上加了一層中繼資料，記錄「這張表目前由哪些檔案組成、哪些資料列已被刪除」，因此支援：

- **資料列層級的 `DELETE` 與 `MERGE`**：Athena 與 Glue 都能對 Iceberg 表執行 `DELETE FROM members WHERE member_id = ...`，不必手動找檔案重寫。
- **Time travel**：可以查詢某個時間點的表格版本，方便稽核「上季報表當時用的是哪些資料」。
- **Schema evolution**：新增欄位不會破壞既有查詢。

Iceberg 會隨著更新產生大量小檔案與舊版本，需要定期 compaction（合併小檔案）與清除過期 snapshot。Glue Data Catalog 對 Iceberg 表提供自動最佳化功能（table optimizers：compaction、snapshot 保留期與孤兒檔案清除）；另一個選擇是 **S3 Tables**，以專用的 table bucket 儲存 Iceberg 表並由 S3 自動維護。兩者都能減少自己排程維護 job 的負擔。點擊事件的冷路徑也一併改寫成 Iceberg 表：Data Firehose 支援以 Apache Iceberg 表作為目的地，Lambda 遮罩之後直接寫入，不必再另外跑一個轉換 job。

刪除請求的完整流程是：客服系統收到請求 → 寫入一張「待刪除清單」表 → 每日的 Glue job 對所有含 `member_id` 的 Iceberg 表執行 `DELETE`，再執行 snapshot 過期，確保舊版本檔案也被實際移除 → 結果寫回稽核紀錄。raw 層的原始 JSON 則在擷取時就把 `member_id` 以外的個資欄位去識別化（例如以加鹽的雜湊值取代，無法反推原值），並用 lifecycle 在 90 天後轉入封存、一年後刪除，讓 raw 層不再保存可直接識別的個資。

### 支付卡資料：在入口擋下來

PCI DSS 的考量最簡單也最重要：卡號從來不進資料湖。支付系統（第 51 章的 `payments-prod`）送出的付款事件只包含付款服務商回傳的 token、卡別與末四碼。為了防止有人不小心把完整卡號寫進日誌或事件，小周再加兩道保險：Firehose 的 Lambda 轉換函式以正則表示式檢查疑似卡號的字串，一旦命中就把該字串遮罩後才放行，並發出告警通知支付團隊追查來源（不要把原始內容寫到錯誤 prefix，否則錯誤 prefix 本身就存了卡號）；**Amazon Macie**（第 16 章）定期掃描資料湖的 bucket，偵測到信用卡號等敏感資料時發出 finding。

### 即時路徑：一分鐘內的熱門旅館

「一分鐘內」的需求不能靠 Firehose → S3 → Athena 這條批次路徑達成，所以小周加了一條獨立的熱路徑（hot path）：

1. **Managed Service for Apache Flink** 以 enhanced fan-out 讀取 clickstream，對每家旅館計算一分鐘滑動視窗的點擊數與轉換率，並和 DynamoDB 中的目前房價比對（第 31 章）。
2. 結果寫入另一條 KDS，再由 **Redshift streaming ingestion** 以 materialized view 直接從 stream 讀入 Redshift，延遲為秒級，不必先落地 S3。
3. QuickSight 以 **direct query** 模式（每次開圖直接查詢資料來源，不經 SPICE）連 Redshift 的這張 materialized view，並設定儀表板定期自動重新整理。

同一份 clickstream 因此有兩條路：冷路徑（Firehose → S3 Iceberg）負責完整、可重算的歷史；熱路徑（Flink → Redshift）負責即時、可以容忍近似值的營運畫面。這種「冷熱分流」設計常被稱為 **Lambda architecture**（與 AWS Lambda 無關），它的代價是兩條路的邏輯要一致，否則儀表板和隔天的報表又會出現「兩個數字」。小周的做法是讓熱路徑只負責「趨勢與警示」，正式營收數字一律以冷路徑為準。

### 單一事實來源：指標定義集中在 Redshift

回到 CFO 的「一個大家都相信的數字」。小周在 `analytics-finance` 帳號建立 **Redshift Serverless**，作為集團指標的唯一計算位置：

- 訂房團隊的 Aurora 透過 zero-ETL 進入 Redshift（第 30 章）。
- 旅行社的訂單在 RDS for Oracle（第 51 章），由 DMS 以 CDC 寫到 `agency-data` 帳號的 S3，再由 Glue job 以 `MERGE` 合併進 Iceberg 表；Redshift 透過 Lake Formation 的共享直接查詢。
- 「營收」的定義（以出發日認列、未稅、扣除取消）寫成一組由財務與兩邊資料團隊共同審核的 SQL view，並放在版本控制裡。
- 其他需要營收數字的團隊不重算，而是透過 **Redshift data sharing** 直接讀取這組 view，資料不複製，consumer 端用自己的運算資源查詢、自己付費。

## 52.5 完整架構圖

```text
   ┌────────────── Producer 帳號 ──────────────┐     ┌──── data-governance 帳號 ────┐
   │ clickstream-data                          │     │ Glue Data Catalog（中央）     │
   │  App ─① KDS(on-demand) ─┬─② Firehose ─────┼──►S3│ Lake Formation               │
   │                         │   Lambda：遮罩、 │ Iceberg │  LF-Tags：domain /        │
   │                         │   擋卡號、寫 Iceberg │  │    sensitivity / market ⑥ │
   │                         └─③ Flink(EFO) ───┼─┐   │  data filters（資料列）    │
   │ booking-data                              │ │   └───────┬───────────▲──────────┘
   │  Aurora ─④ zero-ETL ──────────────────────┼─┼──┐   RAM 共享│           │ 登錄表格
   │ agency-data                               │ │  │          │           │
   │  RDS for Oracle ─⑤ DMS CDC ─► S3 raw ─Glue MERGE─► Iceberg curated ────┘
   └───────────────────────────────────────────┘ │  │          │
                                                  │  │          ▼
   ┌────────────── Consumer 帳號 ─────────────────┼──┼──────────────────────────────┐
   │ analytics-revenue：⑦ KDS → Redshift streaming ingestion（MV）→ QuickSight 直接查詢│
   │ analytics-finance：⑧ Redshift Serverless（營收指標 view）◄─ zero-ETL / LF 共享    │
   │                        └─ data sharing ─► 其他團隊的 Redshift                     │
   │ analytics-marketing：⑨ Athena workgroup（掃描上限）→ resource link → 共享表格     │
   │ 全部：QuickSight（SPICE、row-level security）⑩      Macie 掃描所有 lake bucket ⑪  │
   └────────────────────────────────────────────────────────────────────────────────┘
```

① 點擊事件進入 on-demand 模式的 KDS，承受促銷尖峰。② Firehose 以 Lambda 做遮罩、擋卡號，直接寫入 S3 上的 Iceberg 表（冷路徑）。③ Flink 以 enhanced fan-out 計算一分鐘視窗（熱路徑）。④ 訂房 Aurora 以 zero-ETL 進入財務的 Redshift。⑤ 旅行社 Oracle 以 DMS CDC 落地 S3，Glue 以 `MERGE` 合併進 Iceberg。⑥ 所有 curated 表登錄到中央 Catalog，以 LF-Tags 與 data filter 授權，經 RAM 共享到 consumer 帳號。⑦ 營收管理以 streaming ingestion 拿到秒級資料。⑧ 財務的 Redshift Serverless 是集團指標的唯一計算位置，再以 data sharing 分享。⑨ 行銷用 Athena，透過 resource link 查詢共享表格，workgroup 限制掃描量。⑩ QuickSight 以 row-level security 讓每個市場只看到自己的資料。⑪ Macie 持續掃描，確認敏感資料沒有漏進湖裡。

## 52.6 設計決策紀錄

| # | 決策 | 選 A | 不選 B | 理由 | 何時 B 會變成正確答案 |
|---|---|---|---|---|---|
| 1 | 擷取 | KDS + Firehose | 應用程式直接寫 Firehose | 需要 Flink 等多個 consumer 與重播能力 | 只有「送進 S3」一個目的地、不需要重播 |
| 2 | KDS 容量模式 | On-demand | Provisioned | 促銷尖峰難以預測，避免 throttling | 流量穩定可預測，provisioned 通常較便宜 |
| 3 | 串流平台 | Kinesis | Amazon MSK | 團隊沒有 Kafka 經驗，Kinesis 與 Firehose、Redshift 整合簡單 | 既有 Kafka 生態、需要 Kafka API 相容（第 31 章） |
| 4 | Curated 表格式 | Apache Iceberg | 一般 Parquet 分區 | 需要資料列刪除、`MERGE` 與 time travel | 只追加（append-only）且從不更新的事件資料 |
| 5 | 權限 | Lake Formation LF-Tags + data filter | IAM + bucket policy | 需要欄位與資料列層級權限、跨帳號共享 | 只有少數團隊、以整個 prefix 授權就足夠 |
| 6 | 帳號結構 | Producer／治理／consumer 分帳號 | 全部集中到一個分析帳號 | 資料擁有權清楚、運算費用歸屬到使用者 | 小公司、單一資料團隊，集中最簡單 |
| 7 | 即時儀表板 | Flink + Redshift streaming ingestion | Firehose → S3 → Athena | Firehose buffer 與查詢延遲達不到一分鐘 | 「幾分鐘到一小時」的近即時即可 |
| 8 | 指標計算位置 | Redshift Serverless + data sharing | 各團隊各自用 Athena 計算 | 單一事實來源，避免各自重算出不同數字 | 探索型、一次性的臨時分析 |
| 9 | 卡號防護 | 入口不收 + Lambda 檢查 + Macie | 進湖後再用 Lake Formation 遮蔽 | 卡號一旦進湖，整個平台落入 PCI 範圍 | 無（持卡人資料不應進入分析平台） |
| 10 | Raw 層 | 去識別化 + lifecycle 封存與刪除 | 永久保留原始 JSON 在 Standard | 降低個資風險與儲存費 | 法規要求保存原始紀錄時，改用 Object Lock 與封存類別 |

## 52.7 故障演練

小周的團隊每季做一次資料平台的 game day。資料平台的故障和線上服務不太一樣：最常見的不是「整個掛掉」，而是**資料悄悄變錯、變慢或變貴**。

### 演練一：促銷開跑，KDS 出現 throttling

**情境**：以前的 provisioned stream 在一次限時促銷時出現 `ProvisionedThroughputExceededException`。**根因**：partition key 用的是 `hotel_id`，一家爆紅旅館的事件全部擠進同一個 shard，成為 hot shard（第 31 章）。**處理**：partition key 改為 `session_id`，負載平均分散；stream 改用 on-demand。Producer 端對部分失敗的紀錄做指數退避重試。

### 演練二：Firehose 的 Lambda 轉換失敗

**情境**：一次部署讓 Lambda 轉換函式對新格式的事件拋出例外。**觀察**：Firehose 把失敗的紀錄寫到 S3 的錯誤 prefix，而不是丟掉；CloudWatch 的 Firehose 指標顯示轉換失敗數上升，觸發告警。**處理**：回滾 Lambda 版本，再把錯誤 prefix 的紀錄重新處理補回 curated 表。因為 KDS 的 retention 設為 7 天（預設只有 24 小時，延長要另外付費），最壞情況也能從 stream 重播。

### 演練三：上游改了欄位，儀表板全部壞掉

**情境**：訂房團隊把 `amount` 欄位改名為 `total_amount`，curated 表的 crawler 自動更新了 schema，下游的財務 view 全部查詢失敗。**處理**：curated 層的表改由 ETL job 明確管理 schema，crawler 只用在 raw 層探索，並把 crawler 的 schema change policy 設為「只新增欄位、不更新或刪除既有欄位」。串流事件則用 **Glue Schema Registry** 設定相容性規則（例如 backward compatible），不相容的 schema 在 producer 端就被擋下。更根本的是，每個資料產品要有 owner 與變更通知流程，這是 data mesh 的「產品」精神。

### 演練四：分析師看到了不該看的欄位

**情境**：稽核發現某個新表格的 email 欄位，行銷分析師查得到。**根因**：該表登錄時漏貼 `sensitivity=pii` 標籤，而且 S3 位置沒有登錄到 Lake Formation，存取權限仍由 IAM 決定。**處理**：從 CloudTrail 找出誰在何時查過該表，評估影響；補上標籤並登錄位置。預防措施是在表格登錄流程中加一道自動檢查：欄位名稱或 Macie 的分類結果疑似個資卻沒有 `pii` 標籤時，拒絕登錄。

### 演練五：一個查詢燒掉一個月預算

**情境**：分析師對 raw 層的 JSON 跑了一個沒有分區條件的查詢，一次掃描數百 TB。**處理**：每個 consumer 帳號的 Athena workgroup 設定每次查詢的掃描量上限，以及整個 workgroup 的每日掃描上限與告警；raw 層不授權給一般分析師，只開放 curated 與 analytics 層。

## 52.8 成本思路

分析平台的錢花在三個地方：**存（儲存）、讀（掃描）、算（運算）**。第 30 章列過各元件的最佳化手段，這裡從帳單的角度看小周怎麼排優先順序。

**存：600 TB 中 70% 沒人讀。** 這是最大、也最容易的節省：

| 層 | 儲存類別策略 | 理由 |
|---|---|---|
| Raw（原始 JSON） | 30 天後轉 Glacier Flexible Retrieval 或 Deep Archive，一年後刪除 | 只在重算時才讀，可以接受取回時間；注意 Athena 無法直接查詢這兩種封存類別的物件，要先還原 |
| Curated（Iceberg／Parquet） | S3 Intelligent-Tiering | 存取模式隨專案變動、難以預測，讓 S3 自動依存取頻率移動 |
| Analytics（彙總表） | S3 Standard | 每天被大量讀取 |
| 舊版 Iceberg snapshot | 定期過期清除 | 不清除的話，刪除與更新只會讓儲存量不斷變大 |

把 raw JSON 轉成壓縮的 Parquet 本身也能把儲存量降到原本的一小部分，這同時降低了「存」與「讀」的費用。

**讀：Athena 費用三倍。** 根因是掃描整個 raw 層的查詢。對策依序是：只開放 curated 層、分區與 Parquet、合併小檔案、workgroup 掃描上限、常用結果用 CTAS 預先彙總。QuickSight 儀表板用 SPICE，避免每次開圖都打一次 Athena。

**算：熱路徑最貴。** Flink 依 KPU（運算單位）按小時計費、KDS on-demand 依資料量計費、enhanced fan-out 依 consumer 與 shard 額外計費、Redshift Serverless 依 RPU 小時計費。小周的做法：

- Redshift Serverless 設定 base capacity 與每月 RPU 小時上限，避免意外的長時間查詢。
- 熱路徑只處理「需要一分鐘內看到」的指標，其他全部走冷路徑。
- Firehose 的動態分區與格式轉換會另外計費，但比自己維護一套 consumer 與 Spark job 便宜得多。

**歸屬：誰用誰付。** Consumer 帳號架構讓 Athena 與 Redshift 的運算費自動落在使用者的帳號；Redshift data sharing 由 consumer 自己的運算資源執行查詢。再搭配第 43 章的 cost allocation tags 與成本類別（cost categories），財務能看到每個資料產品的「生產成本」與「使用成本」。

## 52.9 考試這樣考

| 題目關鍵字 | 優先想到 |
|---|---|
| 串流資料要給多個 consumer、可重播 | Kinesis Data Streams |
| 把串流送進 S3／Redshift，不想寫 consumer、near real-time | Data Firehose |
| 串流 JSON 轉 Parquet、依欄位分區寫入 S3 | Firehose 格式轉換（Glue schema）+ 動態分區 |
| 串流上做時間視窗、狀態運算 | Managed Service for Apache Flink |
| 秒級把串流資料放進 data warehouse | Redshift streaming ingestion（materialized view） |
| 欄位層級、資料列層級權限；跨帳號共享資料湖 | Lake Formation（LF-Tags、data filters、RAM） |
| 資料湖要支援 update／delete、time travel | Apache Iceberg（Athena、Glue、S3 Tables） |
| 不複製資料，讓其他帳號的 Redshift 查詢 | Redshift data sharing |
| Athena 費用高 | 分區 + Parquet + 壓縮、workgroup 掃描上限 |
| 儀表板太多人看，資料來源負載高 | QuickSight SPICE |
| 存取模式不可預測的資料湖物件 | S3 Intelligent-Tiering |
| 偵測 S3 裡的信用卡號、個資 | Amazon Macie |
| 上游 schema 改變導致下游失敗 | Glue Schema Registry、crawler schema change policy |

**常見陷阱**：

1. 以為 Firehose 是即時的：它是 near real-time，有 buffer 時間；「一分鐘內、可重播、多個 consumer」要看 KDS 與 Flink。
2. 以為 Lake Formation 能取代所有 IAM 權限：查詢者仍需 IAM 權限呼叫服務，未登錄的 S3 位置仍由 IAM 控制。
3. 用 SQS 承載點擊流：SQS 訊息被處理後就刪除，不支援多 consumer 重播。
4. 把 raw 層丟進 Glacier Deep Archive 後還想用 Athena 直接查：要先還原，或改用 Glacier Instant Retrieval。
5. 為了跨團隊共享而複製資料：Lake Formation 共享與 Redshift data sharing 都能不複製資料。
6. 以為在一般 Parquet 上刪除一筆資料很容易：Parquet 不能原地修改，需要 Iceberg 這類 table format。

> 延伸閱讀：[Lake Formation 細粒度存取控制](https://docs.aws.amazon.com/lake-formation/latest/dg/access-control-fine-grained.html)、[Lake Formation hybrid access mode](https://docs.aws.amazon.com/lake-formation/latest/dg/hybrid-access-mode.html)、[Kinesis Data Streams 延長保存](https://docs.aws.amazon.com/streams/latest/dev/kinesis-extended-retention.html)、[Athena 資料最佳化技巧](https://docs.aws.amazon.com/athena/latest/ug/performance-tuning-data-optimization-techniques.html)、[Glue crawler 的 schema 變更設定](https://docs.aws.amazon.com/glue/latest/dg/crawler-schema-changes-prevent.html)。

## 本章重點整理

- SAA 等級的資料湖是「KDS／Firehose → S3（Parquet、分區）→ Glue Catalog → Athena → QuickSight」，全部受管、營運負擔低。
- SAP 等級的資料平台要處理多個資料擁有者、集中治理與自助取用，常見做法是 producer、治理、consumer 分帳號的 data mesh。
- Lake Formation 以 LF-Tags 做標籤式授權、以 data filter 做資料列與欄位限制，並透過 RAM 跨帳號共享，資料不需要複製。
- Lake Formation 要生效，S3 位置必須登錄且移除預設的 IAMAllowedPrincipals 權限；查詢者仍需要 IAM 權限。
- 需要更新、刪除、time travel 的表格用 Apache Iceberg；要定期 compaction 與清除過期 snapshot，刪除才會真正移除舊檔案。
- 「一分鐘內」的需求要走獨立的熱路徑（Flink、Redshift streaming ingestion），正式數字仍以可重算的冷路徑為準。
- 單一事實來源的做法是把指標定義集中在一個位置（例如 Redshift），其他團隊透過 data sharing 讀取，而不是各自重算。
- 支付卡資料要在入口就擋下，不讓它進入資料湖；Macie 持續掃描作為偵測控制。
- Raw 層在擷取時就把個資欄位去識別化，並以 lifecycle 封存與刪除；curated 層用 Intelligent-Tiering，熱資料留在 Standard。
- Athena 費用靠分區、Parquet、權限分層與 workgroup 掃描上限控制；儀表板用 SPICE 減少重複查詢。
- 資料平台的故障常是「悄悄變錯、變慢、變貴」，要監控 schema 變更、轉換失敗、consumer 延遲與掃描量。
- 多帳號架構讓運算費用自動歸屬到使用者帳號，搭配 cost allocation tags 做 showback 或 chargeback。

## 本章練習題

### 練習 52-1｜SAA｜單選｜多 consumer 的串流擷取

Wanderly 的 App 每秒產生數萬筆點擊事件。三個團隊都要讀取完整的事件：資料團隊要寫入 S3、推薦團隊要即時更新特徵、營收團隊要計算一分鐘視窗的熱門旅館。若某個 consumer 的程式有錯，必須能在修正後從三天前開始重新處理。

應使用哪個服務接收這些事件？

- A. Amazon Kinesis Data Streams，設定足夠的 retention，讓各 consumer 獨立讀取並可重播
- B. Amazon Data Firehose，直接把事件寫入 S3，再讓另外兩個團隊從 S3 讀取
- C. Amazon SQS standard queue，三個團隊共用一個 queue
- D. Amazon SNS topic，三個團隊各自訂閱 Lambda

> [!answer]- 答案：A
> **A ✓** KDS 會依 retention 保留資料（預設 24 小時，可延長），每個 consumer 依自己的位置獨立讀取，不互相影響，也能從過去的時間點重播。
>
> **B ✗** Firehose 是單一目的地的投遞服務，不提供多個 consumer 或重播；而且它有 buffer，從 S3 讀取無法滿足一分鐘視窗的即時運算。
>
> **C ✗** SQS 的訊息被某個 consumer 處理並刪除後，其他 consumer 就讀不到；也無法重播已刪除的訊息。
>
> **D ✗** SNS 可以扇出給多個訂閱者，但不保存訊息，consumer 出錯後無法從三天前重新處理。
>
> **考點**：SAA-3.5、SAA-2.1｜KDS 的多 consumer 與重播

### 練習 52-2｜SAA｜單選｜串流資料轉 Parquet 寫入 S3

資料團隊目前用一個自寫的 consumer 程式讀取 KDS，把 JSON 事件累積後轉成 Parquet，依 `event_date` 與 `country` 分區寫入 S3。這個程式經常因為記憶體不足而當機，需要專人維護。團隊希望以最少的營運負擔取代它，資料延遲數分鐘可以接受。

最合適的做法是什麼？

- A. 改用 EMR 叢集持續執行 Spark Streaming 作業
- B. 改用 Lambda 讀取 KDS，每一筆事件各寫成一個 Parquet 檔案到 S3
- C. 建立以 KDS 為來源的 Data Firehose，使用 Glue Data Catalog 的表格定義啟用格式轉換為 Parquet，並啟用動態分區
- D. 改由應用程式直接把事件寫成 CSV 檔上傳到 S3，再每天執行 Glue crawler

> [!answer]- 答案：C
> **A ✗** EMR 能做到，但要管理叢集與 Spark 作業，營運負擔比 Firehose 高得多。
>
> **B ✗** 每筆事件一個檔案會產生大量小檔案，讓 Athena 查詢又慢又貴，也沒有解決分區與批次的問題。
>
> **C ✓** Firehose 是受管服務，可以以 KDS 為來源，依 Glue 表格的 schema 把 JSON 轉成 Parquet，並依記錄中的欄位動態分區寫入 S3，完全不需要維護 consumer 程式；buffer 帶來的數分鐘延遲符合需求。
>
> **D ✗** 改變應用程式的寫法並不能減少營運負擔，CSV 也比 Parquet 查詢成本高，crawler 只負責探索 schema，不做格式轉換。
>
> **考點**：SAA-3.5｜Firehose 格式轉換與動態分區

### 練習 52-3｜SAA｜單選｜降低 Athena 查詢費用

行銷團隊每天在 Athena 上執行數十次查詢，分析最近 7 天各國的訂房轉換率。資料以 gzip 壓縮的 JSON 存在 S3，依「年/月」分資料夾，每次查詢都掃描整個月的資料，且只用到 30 個欄位中的 4 個。Athena 費用持續上升。

哪個做法最能降低費用？

- A. 把 S3 物件改存到 S3 Standard-IA，降低儲存單價
- B. 用 Glue ETL job 把資料轉成 Parquet，並依日期與國家分區，讓查詢只掃描需要的分區與欄位
- C. 把 Athena 查詢改到 Redshift Spectrum 執行，因為 Spectrum 不按掃描量計費
- D. 每次查詢前先用 S3 Select 把資料下載到分析師的電腦

> [!answer]- 答案：B
> **A ✗** Athena 按掃描量計費，改變儲存類別不會減少掃描量；Standard-IA 還有取回費，頻繁查詢反而更貴。
>
> **B ✓** 依日期分區後，查詢 7 天只掃描 7 個分區；Parquet 是 columnar 格式，只讀需要的 4 個欄位，且壓縮率高。兩者合起來通常能把掃描量降低一到兩個數量級。
>
> **C ✗** Redshift Spectrum 同樣依掃描的 S3 資料量計費，資料格式不變時掃描量一樣大。
>
> **D ✗** 把資料搬到個人電腦違反治理，無法擴展，也沒有處理資料格式這個根本問題；S3 Select 也自 2024 年 7 月起不再開放新客戶（第 22 章）。
>
> **考點**：SAA-4.1、SAA-3.5｜分區與 columnar 格式降低掃描量

### 練習 52-4｜SAA｜單選｜資料湖原始層的儲存類別

Wanderly 的資料湖 raw 層存放原始 JSON 事件，已轉換成 Parquet 的 curated 層才是日常查詢對象。Raw 層在寫入 30 天後幾乎不會被讀取，只有在 ETL 邏輯出錯、需要重算時才會讀取某幾天的資料，這時可以接受等待數小時。法規要求 raw 資料保存一年後刪除。

最具成本效益的 lifecycle 設定是什麼？

- A. 全部保留在 S3 Standard，一年後刪除
- B. 30 天後轉到 S3 One Zone-IA，一年後刪除
- C. 寫入後立即轉到 S3 Intelligent-Tiering，永久保存
- D. 30 天後轉到 S3 Glacier Flexible Retrieval 或 Deep Archive，一年後以 expiration 規則刪除

> [!answer]- 答案：D
> **A ✗** Standard 是最貴的儲存類別，對幾乎不讀的資料不划算。
>
> **B ✗** One Zone-IA 比 Standard 便宜，但仍比封存類別貴，資料也只存在單一 AZ；既然可以接受數小時取回，封存類別更省。
>
> **C ✗** Intelligent-Tiering 適合存取模式不可預測的資料，且每個物件有監控費；這裡模式明確。「永久保存」也違反一年後刪除的要求。
>
> **D ✓** 存取模式明確（30 天後幾乎不讀）、可以接受數小時的取回時間，是封存類別的典型場景，儲存單價遠低於 Standard；一年後用 expiration 規則自動刪除，同時滿足法規。需要重算時先還原物件再處理。
>
> **考點**：SAA-4.1｜依存取模式設定 S3 lifecycle

### 練習 52-5｜SAA｜選兩項｜欄位與資料列權限

Wanderly 的會員表存在 S3 並登錄在 Glue Data Catalog。行銷分析師要以 Athena 查詢會員的消費行為，但不能看到 email 與電話欄位；日本行銷團隊只能看到 `market = 'jp'` 的會員。公司希望以集中、可擴展的方式管理這些權限，且不複製資料。

哪兩個做法能滿足需求？（選兩項）

- A. 在 Lake Formation 為 email、電話欄位貼上表示個資的 LF-Tag，只授權分析師角色存取非個資標籤的欄位
- B. 為每個團隊建立一份去除敏感欄位的資料複本，存在不同的 S3 prefix
- C. 在 Lake Formation 建立 `market = 'jp'` 的 data filter，並把它授權給日本行銷團隊
- D. 在 S3 bucket policy 中以 `s3:prefix` 條件限制分析師只能讀取部分欄位
- E. 用 IAM policy 的 `Condition` 限制 Athena 查詢語句不得包含 email 欄位名稱

> [!answer]- 答案：A、C
> **A ✓** Lake Formation 支援欄位層級授權；以 LF-Tag 標記敏感欄位，再依標籤授權，新增的表與欄位只要貼對標籤就自動適用，集中且可擴展。
>
> **B ✗** 複製資料能隔離欄位，但違反「不複製資料」，每多一個團隊就多一份資料與 pipeline，難以維護與保持一致。
>
> **C ✓** Data filter 可以定義資料列層級（以及欄位層級）的篩選條件，授權給特定 principal 後，該團隊的查詢只會看到符合條件的資料列。
>
> **D ✗** Bucket policy 以物件或 prefix 為單位，無法限制 Parquet 檔案內的欄位。
>
> **E ✗** IAM 無法以查詢語句的內容作為條件；這種做法既不可行，也容易被繞過。
>
> **考點**：SAA-1.3、SAA-1.1｜Lake Formation 欄位與資料列權限

營收管理團隊要在 Redshift 中以 SQL 分析最近幾分鐘的旅館點擊與訂房速率，並與 Redshift 既有的旅館主檔 join。事件目前已在 Kinesis Data Streams 中。團隊要求資料延遲在數秒到一分鐘內，且不想維護額外的中介儲存或排程作業。

- B. 用 Firehose 把事件寫入 S3，再每 15 分鐘以 COPY 載入 Redshift

### 練習 52-8｜SAP｜單選｜多帳號資料共享

Wanderly 集團有三個 producer 帳號各自擁有 S3 上的 curated 表格，並有五個分析團隊各自擁有 consumer 帳號。公司要求：資料不得複製到 consumer 帳號、欄位權限要集中管理、各分析團隊的查詢費用要算在自己的帳號、新團隊加入時不必修改 producer 的 bucket policy。

哪個架構最合適？

- A. 把所有 producer 的資料複製到一個中央分析帳號，所有分析團隊都在中央帳號裡以 IAM role 查詢
- B. 每個 producer 在 bucket policy 中逐一授權各 consumer 帳號的 IAM role，consumer 自行建立 Glue crawler 掃描
- C. 建立中央治理帳號，以 Lake Formation 管理中央 Data Catalog 與 LF-Tags，透過 AWS RAM 把授權共享給 consumer 帳號；consumer 建立 resource link，以自己帳號的 Athena 查詢
- D. 每個 producer 每天把表格匯出成 CSV，透過 S3 Cross-Region Replication 複製到各 consumer 帳號的 bucket

> **C ✓** 中央 Catalog 與 LF-Tags 讓權限集中管理到欄位層級，經 RAM 共享後 consumer 用 resource link 在自己帳號查詢，資料留在原處不複製，查詢費用落在 consumer 帳號；新團隊只需要在 Lake Formation 授權，不必改 bucket policy。
>
> **D ✗** 複製資料違反要求，CSV 也增加掃描成本，還會產生多份不一致的資料。
>
> **考點**：SAP-1.4、SAP-2.3｜Lake Formation 跨帳號共享與 data mesh

### 練習 52-9｜SAP｜單選｜資料湖中的個資刪除

Wanderly 的資料湖有約 200 TB 的會員與訂單歷史資料，以一般 Parquet 檔案依日期分區存放。依個資法，會員提出刪除請求後必須在 30 天內移除其可識別資料。目前每次刪除都要找出所有包含該會員的檔案並重寫整個分區，一次要跑好幾天。公司希望讓刪除可以規模化執行，並保留稽核能力。

哪個方案最合適？

- A. 改用 S3 Object Lock 的 compliance mode 保護資料，避免被誤刪
- B. 對整個 bucket 啟用 versioning，刪除請求時直接刪除整個分區的檔案
- C. 用 Lake Formation 的欄位權限對所有人隱藏該會員的資料列，資料本身不刪除
- D. 把會員與訂單表轉換成 Apache Iceberg 表，以 Athena 或 Glue 執行資料列層級的 `DELETE`，再定期過期舊 snapshot 並清除不再被引用的檔案

> [!answer]- 答案：D
> **A ✗** Object Lock compliance mode 讓物件在保存期間無法被刪除或覆寫，與「必須刪除」的需求正好相反。
>
> **B ✗** 刪除整個分區會一併刪掉其他會員的資料；啟用 versioning 後被刪的物件仍以舊版本存在，個資並沒有真正消失。
>
> **C ✗** 隱藏不等於刪除，資料仍存在於檔案中，不符合刪除請求的要求。
>
> **D ✓** Iceberg 支援資料列層級的 `DELETE`，引擎會只重寫受影響的檔案並更新中繼資料，不必手動找檔案。之後過期舊 snapshot 並清除檔案，舊版本中的個資才會真正被移除；在 snapshot 保留期內也能以 time travel 支援稽核。
>
> **考點**：SAP-2.3、SAP-3.2｜Open table format 支援資料刪除

### 練習 52-10｜SAP｜選兩項｜把遷移後的 Oracle 資料納入資料湖

旅行社的訂單資料庫已遷移到 Amazon RDS for Oracle，每天有大量新增與修改。資料平台團隊要把這些訂單納入資料湖，讓 Athena 查詢到的資料與來源的延遲在一小時內，並且能正確反映訂單的修改與取消。團隊希望盡量使用受管服務，且不影響來源資料庫的效能。

哪兩個步驟最合適？（選兩項）

- A. 每小時對 RDS for Oracle 執行 `SELECT *` 全表匯出成 CSV 到 S3
- B. 使用 AWS DMS 建立以 RDS for Oracle 為來源、S3 為目標的 full load + CDC task，把變更以 Parquet 格式寫入 S3
- C. 使用 MGN 複寫 RDS for Oracle 的磁碟到 S3
- D. 以排程的 Glue job 讀取 DMS 寫出的變更檔，用 `MERGE` 把新增、修改與刪除合併到 Iceberg 格式的訂單表
- E. 在 Athena 中直接把每個 CDC 變更檔都當成一個獨立的表格查詢

> [!answer]- 答案：B、D
> **A ✗** 每小時全表匯出會對來源資料庫造成大量讀取負載，也無法表達刪除，資料量變大後更不可行。
>
> **B ✓** DMS 的 CDC 從資料庫的交易日誌讀取變更，對來源的影響小；以 S3 為目標時可以輸出 Parquet，並在每筆紀錄標示是新增、修改或刪除。
>
> **C ✗** MGN 搬遷的是伺服器，不能用於 RDS 這種受管資料庫，也不會產生可查詢的資料格式。
>
> **D ✓** CDC 檔案是一連串的變更紀錄，要合併成「目前狀態」的表才方便查詢。Iceberg 的 `MERGE` 能依主鍵套用新增、修改與刪除，排程每小時執行即可滿足延遲要求。
>
> **E ✗** 直接查詢變更檔只會看到一連串事件，使用者每次都要自己處理同一筆訂單的多次修改，容易得到錯誤的結果。
>
> **考點**：SAP-4.3、SAP-2.5｜DMS CDC 到 S3 與 Iceberg MERGE

### 練習 52-11｜SAP｜單選｜集團指標的單一事實來源

Wanderly 集團的財務帳號以 Redshift Serverless 計算營收指標。行銷、營收管理與投資人關係三個團隊各自有自己的 AWS 帳號與 Redshift，都需要使用這些營收指標。過去各團隊自己複製資料並重算，導致數字不一致。公司要求只有一套計算邏輯、資料不複製，且各團隊的查詢不會影響財務帳號的運算資源。

最合適的做法是什麼？

- A. 每天把財務帳號的指標表 UNLOAD 到 S3，讓各團隊 COPY 回自己的 Redshift
- B. 在財務帳號建立包含營收 view 的 datashare，以 Redshift data sharing 跨帳號分享給三個團隊，各團隊以自己的 Redshift 運算資源查詢
- C. 讓三個團隊直接連線到財務帳號的 Redshift Serverless 執行查詢
- D. 把營收計算邏輯的 SQL 寄給三個團隊，請他們在各自的 Redshift 中執行

>
> **B ✓** Redshift data sharing 讓 consumer 直接讀取 producer 的即時資料，不需要複製；查詢在 consumer 自己的運算資源上執行，不會搶財務帳號的資源。計算邏輯只存在財務帳號的 view 中，確保單一事實來源。
>
> **C ✗** 直接連線財務帳號會使用財務帳號的運算資源，月初尖峰時互相影響，也讓財務帳號需要管理其他團隊的使用者。
>
> **D ✗** 各自執行同一份 SQL 仍會因為資料版本與修改時間不同而出現不一致，正是過去的問題。
>
> **考點**：SAP-2.5、SAP-1.5｜Redshift data sharing 與成本歸屬

### 練習 52-12｜SAP｜單選｜上游 schema 變更造成下游失敗

資料平台在 curated 層對每個資料產品排程執行 Glue crawler，crawler 設定為發現變更時自動更新表格定義。某天訂房團隊把一個欄位改名，crawler 更新 schema 後，下游十幾個財務 view 和儀表板全部失敗。公司希望避免同樣的事件，同時保留資料產品團隊的自主性。

哪個方案最合適？

- A. 停用所有 crawler，改由平台團隊人工維護所有表格定義
- B. 把所有資料改用 CSV 格式，避免 schema 問題
- C. Curated 層由 ETL job 明確管理 schema，crawler 的 schema change policy 設為只新增欄位、不更新或刪除既有欄位；串流事件以 Glue Schema Registry 設定相容性規則，並建立資料產品的變更通知流程
- D. 在每個下游 view 中加入 `TRY` 函式，讓欄位不存在時回傳空值

> [!answer]- 答案：C
> **A ✗** 平台團隊人工維護所有表格會成為瓶頸，違反資料產品團隊自主的原則。
>
> **B ✗** CSV 一樣有 schema，只是更不明確，問題不會消失，查詢成本還會上升。
>
> **C ✓** Curated 層是對下游的承諾，應由擁有者以 ETL 明確管理 schema；crawler 設定為只新增欄位，避免自動刪改既有欄位。Glue Schema Registry 能在 producer 寫入時檢查相容性，不相容的變更在源頭就被擋下；變更通知流程則保留資料產品團隊的自主性。
>
> **D ✗** 讓錯誤靜默變成空值，報表會在沒有人察覺的情況下算錯，比直接失敗更危險。
>
> **考點**：SAP-3.1、SAP-3.4｜Schema 治理與資料產品契約
