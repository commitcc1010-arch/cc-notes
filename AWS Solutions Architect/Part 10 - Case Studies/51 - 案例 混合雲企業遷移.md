# 第 51 章　案例：企業資料中心遷移：300 台 VM 在十八個月內搬上 AWS

> [!abstract] 本章地圖
> **你會學到**：
> - 把一個 300 台 VM、含 Oracle 與 Windows 檔案伺服器的資料中心，拆解成可以執行的遷移計畫：評估、7Rs 分類、wave 與 cutover
> - 比較「SAA 等級」與「SAP 等級」的遷移解法差在哪裡，知道考題在哪個環節加入限制
> - 為遷移期間的 hybrid 網路做決策：先 VPN 還是先 Direct Connect、DX 要幾條線、流量要不要加密
> - 用 MGN 搬伺服器、用 DMS 搬資料庫、用 DataSync 搬檔案，並寫出可以回退（rollback）的 cutover runbook
> - 預先演練遷移最常出事的五種故障，並說明遷移前、中、後的成本從哪裡來、怎麼壓下來
>
> **前置知識**：第 8 章（VPN、Direct Connect、Hybrid DNS）、第 40 章（Landing Zone）、第 44 章（7Rs 與 wave planning）、第 45 章（MGN、DMS、SCT）
> **考試比重**：SAA ★★☆（Domain 2、3、4）｜SAP ★★★（Domain 4 遷移、Domain 1 網路與多帳號）

## 51.1 故事：機房租約只剩十八個月

第 40 章開頭，Wanderly 完成了併購：對方是一家經營二十年的旅行社，有一座自己的資料中心、300 台 VM、Oracle 資料庫和一排 Windows 檔案伺服器。當時平台負責人阿哲先處理了「帳號」這件事，把 landing zone 蓋好。現在，真正困難的部分開始了：資料中心所在大樓的租約在十八個月後到期，房東已經確定不續約。

旅行社的 IT 主管吳經理帶著 CMDB（設定管理資料庫）的匯出檔來開會。上面列著 300 台 VM 的名稱、作業系統與「負責人」，但第 44 章的專案經理美玲早已發現它不可信：41 台標示「已下線」的 VM 其實還開著，23 台的負責人是已離職的員工。吳經理坦白說：「我知道哪些系統最重要：訂房系統、Oracle 核心庫、會計、還有大家每天在用的檔案伺服器。但這些系統之間誰呼叫誰，我只知道一半。」

Wanderly 的工程師小林從新創時期就在 AWS 上工作（第 5 章那個 VPC 就是他建的），這次被指派為遷移專案的技術負責人，和負責盤點、排程與溝通的美玲搭檔。他很快發現，這個專案不是「把 VM 複製到 EC2」那麼簡單：要先知道有什麼、決定每個系統的命運、把網路接通、一批一批搬，而且每一批都要能在出事時退回去。

第 44、45 章從美玲的角度，依序走過評估、規劃與遷移工具；本章換成技術負責人的角度，把全書前面學過的工具串成一個完整的遷移專案。我們不重新教每個服務的細節，而是在每個決策點指出「這裡用的是第 N 章的哪個觀念」，並且誠實記錄為什麼選 A 不選 B。

## 51.2 需求與限制

小林把會議結論整理成一張需求表。案例題（不論是考試還是實務）最重要的第一步，就是把「硬限制」和「希望」分開：硬限制違反了方案就不成立，希望則可以拿來排序方案。

| 類型 | 項目 | 內容 |
|---|---|---|
| 硬限制 | 時程 | 18 個月內關閉資料中心，第 16 個月要完成最後一批，留 2 個月緩衝 |
| 硬限制 | 停機 | 訂房系統與核心 Oracle 庫的切換停機不得超過 4 小時，且只能在週六 22:00 到隔天 02:00（第 45 章） |
| 硬限制 | 合規 | 處理信用卡資料的支付系統要通過 PCI DSS；會員個資不得離開台灣與日本兩地的處理範圍（第 43 章的資料主權） |
| 硬限制 | 網路 | 遷移期間 AWS 與資料中心要長期共存，至少一年；地端與 AWS 間的資料傳輸要加密 |
| 現況 | 伺服器 | 300 台 VM（VMware vSphere），約 60% Linux、40% Windows；另有幾台不在 vCenter 管理下的實體機跑 Oracle |
| 現況 | 資料庫 | 3 套 Oracle：核心訂房庫（Enterprise Edition，3 TB，含大量 PL/SQL）、會計庫（Standard Edition 2，800 GB）、報表庫（2 TB） |
| 現況 | 檔案 | 6 台 Windows 檔案伺服器，共約 38 TB，用 Active Directory 群組控制權限 |
| 現況 | 身份 | 地端 Active Directory 是員工登入與許多應用程式服務帳號的來源 |
| 希望 | 成本 | 遷移完成後一年內，IT 總成本比現在低 |
| 希望 | 現代化 | 核心訂房系統 TourBook 未來要拆成服務（第 46 章），但不必在這 18 個月內完成 |

這張表已經排除掉一些看似漂亮的方案。例如「全部 refactor 成 serverless」違反時程；「一次 big-bang 週末全部切換」違反停機限制；「先把資料庫搬走、應用程式留在地端」則會讓每一筆查詢都跨越 Direct Connect，延遲和停機風險都變大。

> [!tip] 考試提示
> SAP 案例題常常一口氣給五、六個條件。先圈出「不能違反」的硬限制（時程、停機時間、合規、既有系統不能改），再用最佳化目標（MOST cost-effective、LEAST operational overhead）在剩下的選項裡挑。這一步就能刪掉一半選項。

## 51.3 SAA 等級解法：先讓一個系統搬得動

如果這是一題 SAA 等級的題目，範圍通常只有一兩個系統，問題也比較單純：「把一台跑在 VMware 上的應用程式和它的 Oracle 資料庫搬到 AWS，停機時間最短」。小林先用這個角度設計一個「最小可行」的解法，當作後面演進的起點。

### 網路：先用 Site-to-Site VPN 接通

搬東西之前要先有路。第 8 章說過，**Site-to-Site VPN** 可以在幾天內透過 Internet 建立兩條 IPsec tunnel，而 **Direct Connect（DX）** 需要和電信商、DX location 協調實體線路，常常要幾週到幾個月。SAA 解法的直覺是：先用 VPN 接通，開始做小規模的測試遷移。

VPN 的限制也要說清楚：標準 tunnel 每條的頻寬上限約 1.25 Gbps（考試常用數字；AWS 近年對部分架構推出更高頻寬的 tunnel 選項，實際上限以官方文件為準），而且走 Internet，延遲不穩定。對數百台 VM、數十 TB 的資料量來說，它適合起步，不適合當主幹。

### 伺服器：MGN 做 rehost

第 45 章介紹的 **AWS Application Migration Service（MGN）** 是 rehost（原封不動搬遷）的標準工具。它的運作方式是：在來源伺服器安裝 replication agent，agent 把磁碟以區塊（block）層級持續複寫到 AWS 一個 **staging area subnet** 裡的輕量 replication server 與 EBS volume；要測試或切換時，MGN 依照 launch template 把複寫好的磁碟轉換成可開機的 EC2。

因為是持續複寫，切換當下只需要等最後一點差異同步完成，停機時間可以壓到分鐘級。

### 資料庫：DMS full load + CDC

Oracle 資料庫不適合用 MGN 搬：區塊複寫無法保證資料庫在切換瞬間是交易一致的，也無法順便換到受管的 RDS。SAA 標準答案是 **AWS DMS（Database Migration Service）**：

1. 在 AWS 建立目標資料庫（例如 RDS for Oracle，同引擎搬遷）。
2. DMS task 選 **full load + CDC**：先把整份資料複製過去，同時記錄來源端新的變更（Change Data Capture，從 Oracle 的 redo log 讀取），full load 結束後持續套用變更，讓兩邊保持同步。
3. 切換時停止應用程式寫入，等 CDC 延遲歸零，把應用程式的連線字串指向新資料庫。

### 檔案：DataSync 到 FSx for Windows File Server

Windows 檔案伺服器使用 SMB 協定與 AD 群組權限，對應的 AWS 服務是第 24 章的 **FSx for Windows File Server**：完全支援 SMB、NTFS 權限，並能加入 Active Directory。搬遷工具是第 25 章的 **DataSync**：在地端部署 agent，定期做增量同步，會保留檔案的時間戳記與 NTFS 權限，並在傳輸後做完整性驗證。

### SAA 解法的全貌與不足

```text
 資料中心                                     AWS（單一帳號、單一 VPC）
 ┌──────────────────────────┐   ① VPN    ┌────────────────────────────────┐
 │ App VM（VMware）          │══════════►│ staging subnet：replication server│
 │  └ MGN replication agent  │  ② block  │   → 切換時 launch EC2             │
 │ Oracle DB                 │──③ DMS ──►│ RDS for Oracle（Multi-AZ）        │
 │ Windows 檔案伺服器         │──④ DataSync►│ FSx for Windows File Server     │
 └──────────────────────────┘            └────────────────────────────────┘
```

① VPN 提供加密通道。② MGN 持續複寫伺服器磁碟。③ DMS 先全量再持續同步資料庫。④ DataSync 增量同步檔案。

這套做法對單一系統完全正確，也是 SAA 題目的典型答案。但把它直接套到 300 台 VM，會立刻撞牆：VPN 頻寬不夠、沒有人知道該先搬哪一台、所有東西擠在一個帳號裡違反 PCI 範圍隔離、沒有統一的進度追蹤，而且「每台都 rehost」會把 36 台根本沒人用的 VM 也一起搬上雲、繼續付錢。下一節把它演進成 SAP 等級的設計。

## 51.4 演進到 SAP 等級：從搬一台到搬一座機房

SAP 等級的差別不在於用了更多服務，而在於**處理組織規模的問題**：資訊不完整、多個團隊並行、合規邊界、長期共存，以及每一批都要能回退。小林把專案拆成五條工作線。

### 工作線一：評估，先知道自己有什麼

Excel 清單不可信，所以第一步是自動化盤點（第 44 章）。小林用了兩種 **AWS Application Discovery Service** 收集方式：

- **Agentless Collector**：部署在 VMware vCenter 旁，從 vCenter 讀出所有 VM 的規格與 CPU、記憶體、磁碟使用率。不用碰每一台 VM，兩週內就拿到 300 台的完整清單。
- **Discovery Agent**：安裝在核心的 80 台伺服器（訂房、付款、Oracle、檔案伺服器與周邊系統，包括不在 vCenter 裡的實體 Oracle 主機）上，額外收集**執行中的 process 與網路連線**。這是畫出「誰呼叫誰」的關鍵：agentless 只看得到 VM 規格，看不到連線關係。

收集兩個月後，資料在 Migration Hub 彙整，並匯出到 S3 用 Athena 分析。結果有幾個意外：36 台 VM 過去 60 天的 CPU 幾乎是零、也沒有任何網路連線；一台叫 `rpt-legacy-02` 的「報表機」其實每晚 2 點會被會計系統呼叫；訂房系統寫死了一個 Oracle 的 IP 位址，而不是用 DNS 名稱。

> [!warning] 常見誤解
> 「收集一週的網路連線就能畫出完整依賴圖。」月結、季結、年度稽核這類低頻工作一週內根本不會出現。Discovery 至少要涵蓋一個完整的業務週期，並且和系統負責人訪談交叉確認；工具資料是證據，不是全部真相。

成本面，小林用 **Migration Evaluator** 根據實際使用率估算 TCO（總持有成本）。地端 VM 普遍配置過大：平均 CPU 使用率不到 15%，所以 AWS 上的 instance 規格要依實際用量重新選擇，而不是照抄 VM 的 vCPU 數。

> [!note] 工具現況
> 依 AWS 文件，Migration Hub 與 Application Discovery Service 自 2025 年 11 月 7 日起不再對新客戶開放：既有客戶可以繼續使用，從未用過的帳號則無法啟用。新的探索、依賴分析與 wave 規劃由以生成式 AI 輔助的 **AWS Transform** 提供；Migration Evaluator 仍持續提供。如第 44 章所述，旅行社在這個日期之前就已啟用這兩個服務，屬於既有客戶，所以本案例照常使用。考試中，「集中追蹤多個遷移工具的進度」仍以 Migration Hub 為標準答案，「探索伺服器與依賴關係」以 Application Discovery Service 為標準答案。

### 工作線二：7Rs 分類，替每個系統決定命運

有了資料，小林和吳經理逐一替系統套上第 44 章的 7Rs。重點是：**分類的單位是「應用程式」而不是「VM」**，同一個應用程式的 web、app、batch 機器必須一起決定。

| 策略 | 數量（VM） | 代表系統 | 判斷理由 |
|---|---|---|---|
| Retire（退役） | 36 | 舊報表、重複的測試環境、舊官網 | 60 天無使用、負責人確認可關閉；有保存義務的資料先封存到 S3 |
| Retain（保留） | 14 | 需要插 USB 硬體金鑰的機票開票系統、即將被 SaaS 取代的人資系統 | 依賴實體硬體或即將被取代，現在搬不划算；開票系統經 Direct Connect 與 AWS 溝通，資料中心關閉前改放到合作夥伴的託管機房 |
| Repurchase（改買 SaaS） | 20 | Exchange 郵件、自建 CRM | 已有成熟 SaaS（例如 Microsoft 365、SaaS CRM），搬遷不如換掉 |
| Rehost（直接搬） | 192 | 大部分 Linux／Windows 應用伺服器、中介軟體、訂房系統 TourBook | 時程優先，商用軟體不能改；AD domain controller 也列在這裡，但做法是在 AWS 新建 DC 加入網域，而不是用 MGN 複製 |
| Replatform（小幅調整） | 14 | 8 台 Oracle 主機與 VM → RDS（報表庫轉 Aurora PostgreSQL）、6 台檔案伺服器 → FSx | 換成受管服務能明顯降低營運負擔，改動有限 |
| Refactor（重構） | 24 | 團體行程報價引擎 | 必須與 Wanderly 的訂房平台整合，無論如何都要大改；依第 46 章以 strangler fig 逐步進行 |
| Relocate（整體平移） | 0 | — | 評估過把整個 VMware 環境平移到 AWS 上的 VMware 方案（第 44 章），但團隊希望藉遷移擺脫 hypervisor 授權與維運，因此不採用 |

這張表最常被問的是：「為什麼核心訂房系統 TourBook 不直接 refactor？」答案寫在需求表裡：時程是硬限制，refactor 是希望。先 rehost 讓它離開即將關閉的機房，再到第 46 章的現代化階段用 strangler fig 逐步拆分。報價引擎之所以列為 refactor，是因為整合需求讓它「不改就不能用」，而不是因為重構比較漂亮。這種「先搬再改（migrate first, then modernize）」是大型遷移最常見的節奏。

### 工作線三：基礎先行，landing zone 與網路

SAP 等級的遷移一定是 **landing zone 先行**（第 40 章）：在第一台 VM 上雲之前，帳號結構、日誌、guardrail、網路都要先就位。小林的帳號規劃依照第 40 章的原則：旅行社的系統依環境與敏感度放進 `agency-apps-prod`、`agency-apps-nonprod`，支付系統獨立放進 `payments-prod`，讓 PCI DSS 的稽核範圍只涵蓋這一個帳號。MGN 與 DMS 的 staging 資源放在各自的目標帳號，避免跨帳號複寫的權限問題。

網路採用第 41 章的 hub-and-spoke：網路帳號擁有 Transit Gateway 與 Direct Connect，各 workload VPC 以 TGW attachment 接入，prod 與 nonprod 使用不同的 TGW route table 互相隔離，地端流量進入 AWS 後先經過 inspection VPC。

Direct Connect 的設計是本章最重要的網路決策：

1. **先 VPN 後 DX**：專案第 1 個月就建好 Site-to-Site VPN（接在 TGW 上，可用 ECMP 聚合多條 tunnel 的頻寬），讓 discovery 資料上傳與 pilot wave 可以開始；DX 同時下單。
2. **兩個 DX location 各一條 10 Gbps dedicated connection**：對應第 8 章的 high resiliency 模型。遷移期間這條路就是「生產線」，任何一個 location 故障都不能讓整個專案停擺。
3. **Transit VIF 接 DX Gateway，再接 TGW**：新 VPC 加入時不必新增 VIF。
4. **加密**：DX 本身不加密（第 8 章）。合規要求傳輸加密，所以在支援的 location 啟用 **MACsec**（dedicated 10 Gbps 以上的 connection 才支援），做為鏈路層加密；尚未就緒前，先在 DX 上跑 IPsec VPN（private IP VPN），而應用層原本就使用 TLS 的流量則保持 TLS。
5. **VPN 保留為第三條路**：DX 正常時 BGP 自動偏好 DX，VPN 只在兩條 DX 都失效時接手。

### 工作線四：身份與 DNS，看不見但最容易卡住

有一半的應用程式會向地端 AD 驗證服務帳號。如果搬到 AWS 的伺服器每次登入都要跨 DX 回地端找 domain controller，延遲會讓某些老應用程式逾時，而 DX 中斷時更會全面無法登入。

小林的做法是在 AWS 的 shared services VPC 部署屬於同一個 AD 網域的 domain controller（EC2 上的自管 DC，設定成 AD 的另一個 site），讓雲上的伺服器就近驗證；這樣搬遷後的伺服器不用改任何網域設定。另一個常見選項是 **AWS Managed Microsoft AD** 搭配與地端網域的信任關係（trust），適合「新建的 AWS 資源想用受管 AD」；但對「要原封不動搬遷、已經加入舊網域的伺服器」，延伸既有網域的摩擦最小（第 13 章）。

DNS 沿用第 8 章的 Route 53 Resolver 架構：outbound endpoint 加上 forwarding rule，把 `agency.local` 這類地端網域轉給地端 DNS；inbound endpoint 讓地端解析 AWS 的 private hosted zone。Resolver rule 透過 AWS RAM 共享給所有 workload 帳號。

### 工作線五：wave、cutover 與回退

最後是執行。小林和美玲把 192 台 rehost 與 14 台 replatform 的系統，依照依賴關係分成 **move group（必須一起搬的一組系統）**，再把 move group 排進第 44 章的 wave 計畫：

| Wave | 時間 | 內容 | 目的 |
|---|---|---|---|
| W0 | 第 1–3 個月 | Landing zone、TGW、VPN、DX、AWS 上的 AD DC、Resolver、監控 | 基礎，沒有任何業務系統 |
| W1（pilot） | 第 4 個月 | 12 台內部工具（低風險、依賴少） | 驗證工具鏈與 runbook，量測實際複寫速度 |
| W2 | 第 5 個月 | 30 台低風險應用 | 開始建立節奏 |
| W3 | 第 6 個月 | 6 台檔案伺服器 → FSx | 被很多系統依賴的共用資源提前搬 |
| W4 | 第 7–8 個月 | 45 台中風險應用 | 放大規模，像工廠一樣量產 |
| 凍結 | 第 9 個月 | 暑假旺季，不做任何 cutover | 避開業務高峰 |
| W5 | 第 10–11 個月 | 客服、行銷等 50 台 | 依序搬遷其餘業務系統 |
| W6 | 第 12–13 個月 | 訂房系統 TourBook + 核心 Oracle（move group A） | 最關鍵的系統，前面每一波都是它的彩排 |
| W7 | 第 14 個月 | 其餘 40 台應用 | 收尾 |
| 凍結、緩衝、退場 | 第 15–18 個月 | 春節凍結；失敗重試與遺漏項目；關閉來源、清空機房 | 保留重來的時間 |

會計系統與會計庫、支付系統（進 `payments-prod`）分別排在 W5 與 W7 中各自的 move group，細節不在這裡展開。

最關鍵的系統排在後段，是因為前面的 wave 會把 runbook、監控、權限、DNS 切換這些「肌肉」練熟；也因為最關鍵的系統依賴最多，等它的依賴大多已經在 AWS 上，它搬過去後才不會每次呼叫都跨 DX。但它**不能放在最後一波**：W6 之後還留了好幾個月，萬一切換失敗，還有機會修正後重來。

每個 wave 都有一份 cutover runbook。以 W6 的訂房系統為例（第 45 章有逐步說明）：

```text
T-14 天  MGN 完成初始複寫；核心 Oracle 以 Data Pump 完成初始載入，DMS 從匯出時的 SCN
         以 CDC 持續同步（第 45 章）；做一次 test launch 驗收
T-7 天   把相關 DNS 記錄的 TTL 從 3600 降到 60 秒
T-1 天   變更凍結；確認 DMS CDC 延遲 < 5 秒、資料驗證無差異；go/no-go 會議
T-0 22:00 停止地端應用程式寫入（維護頁面），確認批次作業也已停止
T-0 22:15 等 CDC 延遲歸零；DMS validation 確認；停止 DMS task；依來源重設 sequence
T-0 22:30 啟動反向 DMS CDC task（RDS → 地端 Oracle），準備好回退路徑
T-0 22:40 MGN launch cutover instances；post-launch actions 安裝 CloudWatch agent、設定連線字串
T-0 23:20 Route 53 記錄改指向 AWS 的 ALB；開始 smoke test（訂房、付款、查詢）
T-0 00:30 go/no-go：成功 → 開放流量；失敗 → 執行回退（保留到 02:00 的時間給回退）
T+7 天   回退期限結束：停止反向 CDC、MGN finalize cutover；地端 VM 關機（不刪除）
T+30 天  確認無回退需求，地端 VM 刪除、授權歸還
```

回退（rollback）計畫是這份 runbook 的核心：在開放新寫入之前，小林就先建立一個**反向的 DMS CDC task**，把 AWS 上新寫入的資料同步回地端 Oracle，讓地端在 7 天的回退期限內始終「可以接手」。如果 T+3 天才發現嚴重問題，回退時不會遺失這三天的訂單。

## 51.6 設計決策紀錄

**設計決策紀錄（Architecture Decision Record，ADR）** 是把「當時為什麼這樣選」寫下來的文件。它對考試的價值是：每一列都是一個潛在考點，「為何不選 B」往往就是題目裡的錯誤選項。

| # | 決策 | 選 A | 不選 B | 理由 | 何時 B 會變成正確答案 |
|---|---|---|---|---|---|
| 1 | 第一條連線 | Site-to-Site VPN 先行 | 等 DX 完成才開始 | DX 交付需數週到數月，時程不能等 | 時程寬鬆、資料量小到 VPN 就夠時，甚至可以只用 VPN |
| 2 | 主幹連線 | 兩個 location 各一條 DX | 同一 location 兩條 DX | 同一 location 會共同故障（電力、機房） | 非關鍵 workload，可接受 location 故障時降級到 VPN |
| 3 | DX 加密 | MACsec，過渡期 IPsec over DX | 「DX 是專線所以不用加密」 | DX 預設不加密，合規要求傳輸加密 | 合規沒有要求、且應用層已全面 TLS |
| 4 | 伺服器搬遷 | MGN 持續區塊複寫 | 匯出 VM 映像檔再匯入（VM Import） | MGN 持續同步，停機分鐘級，可大量平行 | 少量、可長時間停機、只是一次性複製的 VM |
| 5 | 核心 Oracle | RDS for Oracle（同引擎，BYOL） | 立即轉 Aurora PostgreSQL | 3 TB、大量 PL/SQL，轉換風險不符時程 | 程式邏輯簡單、授權即將到期、時程寬裕（見第 45 章 SCT） |
| 6 | 資料庫搬遷 | 停機前完成初始載入（Data Pump），再以 DMS CDC 持續同步 | 停機窗內一次匯出、傳輸、匯入 | 3 TB 的匯出、傳輸、匯入加驗證遠超過 4 小時停機窗 | 小型資料庫，停機時間足以完成一次全量匯出匯入 |
| 7 | 檔案伺服器 | FSx for Windows + DataSync | EFS | 需要 SMB 與 AD 群組權限；EFS 是 NFS，給 Linux 用 | Linux 應用程式之間共用檔案 |
| 8 | AD | 延伸既有網域，在 AWS 部署 DC | 遷移期間只靠地端 DC | 減少跨 DX 驗證延遲，DX 中斷時仍可登入 | 只有少量 AWS 資源需要 AD 且能接受依賴地端 |
| 9 | 搬遷順序 | 低風險 pilot 先、核心系統排在後段（但保留重來的時間） | 最重要的先搬 | 前面的 wave 是核心系統的彩排，依賴也先就位 | 核心系統所在硬體即將故障等急迫情況 |
| 10 | 訂房系統 TourBook | 先 rehost，遷移後再現代化（第 46 章） | 遷移時直接 refactor | 時程是硬限制，refactor 是希望 | 原平台已無法運作或授權無法延續 |

## 51.7 故障演練

小林在 pilot wave 結束後開始定期辦 game day（第 34 章），刻意製造遷移期間最常見的故障，確認團隊知道「看什麼訊號、做什麼動作」。以下五個情境中，大多是演練，演練四則是專案中真的發生過、事後被寫進演練劇本的事件。

### 演練一：一條 DX 中斷

**情境**：DX location A 的連線被拔掉。**預期**：BGP 在數秒內（有啟用 BFD 時，第 8 章）把流量移到 location B 的連線，MGN 與 DMS 只會出現短暫延遲。**實際觀察**：location B 的 10 Gbps 足以承受全部流量，但 MGN 複寫流量與正式業務流量擠在同一條線上，業務延遲上升。**改善**：在 MGN 的 replication settings 設定頻寬限制（throttling），並在 DX 容量規劃時用「剩一條線也能撐住業務 + 複寫」的 N+1 算法。

### 演練二：test launch 時才發現寫死的 IP

**情境**：訂房系統的 test instance 開機後，無法連到資料庫。**原因**：程式設定檔寫死了地端 Oracle 的 IP；W0 時已把找得到的寫死 IP 改成 DNS 名稱（第 44 章），但這個設定檔藏在一個很少用的批次模組裡，清查時漏掉了。**處理**：在 MGN 的 post-launch actions 加入一個 Systems Manager 文件，在 instance 啟動後改寫設定檔，指向新的 DNS 名稱。這正是**為什麼每台伺服器都要先 test launch**：問題在不影響正式環境的測試階段被抓出來，而不是在凌晨兩點的停機窗裡。

### 演練三：CDC 延遲在切換窗口內降不下來

**情境**：T-0 停止寫入後，DMS 的 CDC 延遲仍有 20 分鐘。**原因**：前一晚的批次作業產生大量 redo log，replication instance 的 CPU 打滿。**處理**：runbook 的 go/no-go 條件寫著「23:00 前 CDC 延遲未歸零即中止切換」，團隊依規則中止，地端繼續服務，沒有任何資料損失。事後把 replication instance 放大，並把批次作業移到切換前一晚以外的時段。

> [!warning] 常見誤解
> 「DMS task 狀態是 running，就代表資料一致。」Running 只表示 task 在跑。要看 CDC latency 指標（來源端與目標端延遲），並啟用 DMS 的 data validation 比對兩邊的資料列。LOB 欄位在 limited LOB mode 下超過上限會被截斷，也要事先檢查。

### 演練四：切換後三天才發現報表錯誤

**情境**：會計系統切換後第三天，月中報表金額對不上。**處理**：觀察期內地端 Oracle 透過反向 CDC 持續接收 AWS 的新資料，因此可以在一小時內回退到地端，且沒有遺失這三天的交易。根因是一個時區設定：RDS 的參數群組（parameter group）時區與地端不同。修正後重新排程切換。

### 演練五：DX 全斷、只剩 VPN

**情境**：同時中斷兩條 DX。**觀察**：VPN 接手，但頻寬只有 DX 的一小部分；MGN 複寫大幅落後，部分跨 DX 的同步呼叫逾時。**結論**：VPN 是「維持基本營運」的路，不是「維持遷移速度」的路。這被寫進風險登錄表：若兩條 DX 同時中斷超過一天，暫停當週的 cutover。

## 51.8 成本思路

遷移專案的成本有三段，每一段的槓桿不同。

**遷移期間：雙軌成本。** 在資料中心關閉前，地端和 AWS 兩邊都在花錢，這被稱為 **double bubble**。最大的槓桿是速度與退役：早一個月關掉一批地端硬體，就少付一個月的雙軌費用；36 台 retire 的 VM 不搬，就永遠不用為它們付錢。

**遷移工具與連線。** 逐項看：

| 項目 | 收費方式 | 思路 |
|---|---|---|
| Direct Connect | port 小時費 + 從 AWS 流出的資料傳輸費 | 遷移流量大多是「進 AWS」，資料流入 AWS 不收傳輸費；出站費率也比 Internet 低 |
| Site-to-Site VPN | 每條連線每小時 + 出站傳輸 | 保留做第三路徑的成本不高 |
| MGN | 每台來源伺服器有 2,160 小時（約 90 天連續複寫）的免費額度，之後按伺服器時數收費；staging area 的 EC2、EBS 與快照一開始就照常計費 | 讓每台伺服器在免費期內完成 cutover 並 finalize，不要讓複寫掛著好幾個月 |
| DMS | replication instance 按小時（或 DMS Serverless 按容量單位） | 切換完成、觀察期結束就刪除 task 與 instance |
| DataSync | 按傳輸的資料量 | 先清掉不需要的舊檔案再搬 |

**遷移完成後：最佳化。** 這是「一年內 IT 成本低於現在」能否達成的關鍵（第 39 章）：

1. **Rightsizing**：rehost 時已依實際使用率選規格，上線一個月後再用 Compute Optimizer 調整一次。
2. **儲存**：EBS 一律 gp3；FSx for Windows 對冷資料多的檔案共享評估 HDD 儲存類型與資料去重（data deduplication）。
3. **購買方式**：用量穩定兩、三個月後再買 Compute Savings Plans；太早買會把錯誤的規格鎖住。
4. **授權**：Windows 大多數走 license included；RDS for Oracle 的 license included 只支援 Standard Edition 2，所以會計庫（SE2）可以選 license included，核心庫（Enterprise Edition）必須 BYOL，並盤點 vCPU 數確保授權足夠（Multi-AZ 的 standby 也要授權）。長期而言，把 Oracle 轉到 Aurora PostgreSQL 是最大的授權節省來源：報表庫已依 DMS Schema Conversion 的評估結果排進第 46 章的現代化計畫（第 45 章），會計庫這類邏輯簡單的資料庫是下一個候選。
5. **關機排程**：nonprod 環境用 Instance Scheduler 或 Systems Manager 在下班時間停機。

> [!note] 遷移資金支援
> AWS 與合作夥伴有針對大型遷移的資金與顧問支援計畫（例如 Migration Acceleration Program），內容與資格會變動，專案初期就應該洽詢，而不是等帳單出來才想到。

## 51.9 考試這樣考

| 題目關鍵字 | 優先想到 |
|---|---|
| 探索地端伺服器、規格與使用率，不想在每台 VM 安裝軟體 | Application Discovery Service Agentless Collector（vCenter）；新客戶改用 AWS Transform |
| 需要 process 與網路連線來畫依賴圖 | Application Discovery Service Discovery Agent |
| 建立遷移的商業論證、TCO | Migration Evaluator |
| 集中追蹤多個工具的遷移進度 | Migration Hub（2025-11-07 起不再開放新客戶，考試仍以它為答案） |
| 大量 VM rehost、停機最短、可先測試 | MGN（test launch → cutover → finalize） |
| 資料庫遷移且要求最少停機 | DMS full load + CDC |
| Oracle／SQL Server 轉到 Aurora PostgreSQL | SCT 或 DMS Schema Conversion 轉 schema，DMS 搬資料 |
| Windows 檔案伺服器、SMB、AD 權限 | FSx for Windows File Server + DataSync |
| DX 還沒好但要立即開始 | 先 Site-to-Site VPN，DX 完成後 VPN 當備援 |
| 關鍵連線要能承受一個 DX location 故障 | 兩個 DX location（high／maximum resiliency） |
| DX 上的資料必須加密 | MACsec（支援的 dedicated connection）或 IPsec VPN over DX |
| 遷移後的伺服器要就近做 AD 驗證 | 在 AWS 部署 DC 或使用 AWS Managed Microsoft AD + trust |
| 地端與 AWS 互相解析名稱 | Route 53 Resolver inbound／outbound endpoint + forwarding rule |
| 遷移後最快的省錢手段 | Rightsizing 後再買 Savings Plans；退役閒置資源 |

**常見陷阱**：

1. 以為 DX 是加密的：DX 只是專用線路，加密要另外用 MACsec、IPsec 或應用層 TLS。
2. 用 MGN 搬資料庫並期待交易一致與受管化：資料庫要 replatform 到 RDS 時用 DMS；MGN 是整台伺服器原樣搬。
3. 只做 DMS full load 就切換：忽略 full load 期間來源仍在寫入，必須搭配 CDC。
4. 把 7Rs 套在單台 VM 而不是應用程式上：同一應用的機器要一起決定、一起搬。
5. 遷移完立刻買三年 Reserved Instances：規格還沒穩定，應先 rightsizing。
6. 跳過 test launch 直接 cutover：MGN 的測試階段就是用來在不影響正式環境下抓出設定問題。

## 本章重點整理

- 大型遷移的第一步是把需求分成硬限制（時程、停機窗、合規、不能改的系統）與希望（成本、現代化），硬限制直接淘汰方案。
- SAA 等級的遷移解法是「VPN 接通 + MGN rehost 伺服器 + DMS full load + CDC 搬資料庫 + DataSync 搬檔案到 FSx」；SAP 等級在此之上處理評估、分類、多帳號、網路韌性與可回退的 wave。
- Application Discovery Service 的 agentless 方式快速取得 VM 規格與使用率，agent 方式才能取得 process 與網路連線依賴；discovery 期間要涵蓋完整業務週期。ADS 與 Migration Hub 自 2025-11-07 起不再開放新客戶，新專案改用 AWS Transform。
- 7Rs 以應用程式為單位決定，退役與改買 SaaS 往往是最省錢的遷移；時程緊時採「先搬再改」。
- Landing zone 與網路要在第一個 wave 之前完成；支付系統放進獨立帳號以縮小 PCI DSS 範圍。
- DX 交付需要時間，所以先 VPN 後 DX；關鍵連線用兩個 DX location，VPN 保留為第三路徑。
- DX 預設不加密，合規要求時使用 MACsec 或 IPsec over DX。
- 遷移後的伺服器需要就近的 AD 驗證與 hybrid DNS，否則會在切換後出現逾時與名稱解析錯誤。
- MGN 的流程是持續複寫 → test launch 驗收 → cutover → 觀察期 → finalize，post-launch actions 可以自動修正設定。
- DMS 切換要看 CDC 延遲與 data validation，並準備反向 CDC 作為回退路徑。
- 每個 cutover 都要有 go/no-go 條件與回退計畫；最關鍵的系統排在後段、讓前面的 wave 成為彩排，但要留下失敗後重來的時間。
- 遷移期間的雙軌成本靠速度與退役壓低；遷移後的成本靠 rightsizing、gp3、穩定後才買 Savings Plans，以及授權最佳化。

### 練習 51-1｜SAA｜單選｜DX 交付前的連線

一家公司要在六個月內把資料中心的 40 台伺服器搬到 AWS。網路團隊已經向電信商申請 Direct Connect，但預估要八週以上才能交付。專案經理希望下週就開始做 pilot 遷移與連線測試，資料必須加密傳輸，且不想為過渡期另外購買硬體設備。

最合適的做法是什麼？

- A. 暫停所有遷移工作，等 Direct Connect 交付後再開始，以避免流量經過 Internet

- C. 改申請 hosted Direct Connect connection，因為 hosted connection 不需要實體線路，可在一天內啟用
- D. 讓來源伺服器直接透過 Internet 以 HTTPS 呼叫 MGN 公開 endpoint，不建立任何私有連線，DX 交付後也不再使用

>
> **D ✗** MGN 雖然可以經 Internet 複寫並加密傳輸，但完全不建立私有連線，遷移後的應用程式與地端系統之間就沒有私有路徑可共存；放棄已申請的 DX 也與長期 hybrid 需求不符。
>

### 練習 51-2｜SAA｜單選｜Windows 檔案伺服器遷移

一家旅行社有 12 台 Windows 檔案伺服器，共約 80 TB，員工透過 SMB 存取，權限以 Active Directory 群組控制。公司要把這些檔案搬到 AWS 的受管服務，保留既有的 NTFS 權限，搬遷期間檔案仍會持續被修改，並希望營運負擔最低。

哪個方案最合適？

- A. 建立 Amazon EFS，用 rsync 每晚同步，再讓 Windows 用戶端掛載 EFS
- B. 在 EC2 上自建 Windows 檔案伺服器，使用 MGN 複寫原本的伺服器
- C. 建立 S3 bucket，使用 S3 File Gateway 讓員工以 SMB 存取，並用 S3 Batch Operations 搬移檔案
- D. 建立加入 AD 的 FSx for Windows File Server，使用 DataSync 做多次增量同步，切換前做最後一次同步

>
> **D ✓** FSx for Windows File Server 原生支援 SMB 並能加入 AD，保留 NTFS 權限。DataSync 會保留檔案中繼資料與權限、只傳變更的部分並驗證完整性，可以在切換前反覆做增量同步，最後一次同步的時間很短。
>
> **考點**：SAA-3.1、SAA-2.1｜FSx for Windows File Server 與 DataSync

> **D ✗** 6 小時停機直接違反 30 分鐘的限制。這種做法只在停機時間足夠時才合適。

### 練習 51-4｜SAA｜選兩項｜遷移期間 DX 的韌性

一家公司在遷移期間要以 Direct Connect 作為地端與 AWS 間的主要連線，承載持續的伺服器複寫與正式業務流量。需求是：任何單一 DX location 故障時業務都不中斷，並且在兩條 DX 都故障的極端情況下仍保有基本連線。

哪兩個做法能滿足需求？（選兩項）

- A. 在兩個不同的 DX location 各建立一條 dedicated connection，地端使用不同的路由器連接
- B. 在同一個 DX location 建立 LAG，把兩條 connection 綁在一起
- C. 在同一條 connection 上建立兩個 transit VIF，分別接到不同的 DX Gateway
- D. 建立一條 Site-to-Site VPN 作為備援路徑，平時由 BGP 優先選擇 DX
- E. 把所有流量改走 S3 Transfer Acceleration，以避開 DX location 故障

> [!answer]- 答案：A、D
> **A ✓** 兩個不同 location 的連線不會因單一機房的電力或設備問題同時中斷，地端也用不同路由器避免單點，對應 high resiliency 模型。
>
> **B ✗** LAG 把多條 connection 聚合以增加頻寬與連線層級的備援，但它們都在同一個 location，location 故障時會一起中斷。
>
> **C ✗** VIF 是在同一條實體 connection 上的邏輯介面，connection 或 location 故障時所有 VIF 一起失效。
>
> **D ✓** VPN 經由 Internet，與 DX 是完全不同的故障域。當 DX 相同 prefix 也在宣告時，AWS 會優先選擇 DX，VPN 只在 DX 全部失效時接手，頻寬雖低但能維持基本連線。
>
> **E ✗** Transfer Acceleration 只用於加速對 S3 的上傳與下載，無法承載伺服器複寫以外的私有業務流量，也不是私有網路連線。
>
> **考點**：SAA-2.2、SAA-3.4｜DX 多 location 與 VPN 備援

### 練習 51-5｜SAA｜單選｜遷移後的名稱解析

Wanderly 已把一批應用程式伺服器搬到 AWS 的 VPC。這些伺服器仍需要以 `erp.agency.local` 這類名稱呼叫留在地端的系統，地端 DNS 伺服器負責 `agency.local` 網域。VPC 已透過 Direct Connect 與地端連通，VPC 使用 Amazon-provided DNS。

- D. 依依賴關係把必須一起搬的系統組成 move group，再把 move group 排入 wave，並在 Migration Hub 集中追蹤各伺服器的遷移狀態
- E. 所有 300 台在同一個週末一起切換，就不會有跨環境依賴的問題

> [!answer]- 答案：B、D
> **A ✗** 作業系統類型與應用程式之間的呼叫關係無關，正是上次事故的成因；vCenter 清單也看不到網路連線。
>
> **B ✓** Discovery Agent 收集執行中的 process 與網路連線，是建立依賴圖的依據。收集期間要涵蓋月結等低頻工作，並以訪談補足工具看不到的人工流程，才能找出「每晚才呼叫一次」的依賴。
>
> **C ✗** 字母順序與依賴無關，仍會把互相呼叫的系統拆到不同 wave。
>
> **D ✓** Move group 確保強依賴的系統一起搬，wave 再依風險與資源排程。Migration Hub 提供跨工具的集中進度視圖，取代分散的試算表。
>
> **E ✗** Big-bang 把 300 台的所有未知風險集中在一個週末，任何一個問題都可能讓全部回退，違反分批降低風險的原則。
>
> **考點**：SAP-4.1、SAP-4.2｜依賴探索、move group 與 Migration Hub

### 練習 51-11｜SAP｜單選｜Oracle 遷移的引擎選擇

一家公司有兩套 Oracle：核心訂票庫是 Enterprise Edition、6 TB，含大量 PL/SQL 預存程序與觸發器，必須在 4 個月內離開資料中心；會計庫是 800 GB 的小型資料庫，PL/SQL 很少，Oracle 授權將在一年後到期且公司不打算續約。公司希望兩者都改用受管服務，並在不影響時程的前提下長期降低授權成本。

哪個方案最合適？

- A. 兩套都在 4 個月內用 SCT 轉成 Aurora PostgreSQL，再用 DMS 搬遷
- B. 兩套都搬到 RDS for Oracle 並選擇 license included，以免除授權問題
- C. 兩套都用 MGN 搬到 EC2，保留現有授權與設定
- D. 核心訂票庫先以 DMS full load + CDC 搬到 RDS for Oracle（BYOL）；會計庫以 SCT 或 DMS Schema Conversion 轉換 schema，再用 DMS 搬到 Aurora PostgreSQL

> [!answer]- 答案：D
> **A ✗** 6 TB 且含大量 PL/SQL 的核心庫要轉換引擎，需要改寫與大量測試，4 個月內完成風險極高，可能違反時程這個硬限制。
>
> **B ✗** RDS for Oracle 的 license included 只適用於 Standard Edition 2（SE2），Enterprise Edition 必須 BYOL；而且會計庫若繼續用 Oracle，就錯過了授權到期這個轉換引擎的時機。
>
> **C ✗** 搬到 EC2 仍要自己管理資料庫的備份、patch 與高可用，不符合「改用受管服務」的需求。
>
> **D ✓** 核心庫以同引擎搬遷到 RDS for Oracle，轉換風險最低，能守住時程；Enterprise Edition 在 RDS 上以 BYOL 方式使用。會計庫小而邏輯簡單，又遇上授權到期，是轉到 Aurora PostgreSQL 的最佳時機：用 SCT 或 DMS Schema Conversion 轉 schema、DMS 搬資料，長期免去 Oracle 授權費。
>
> **考點**：SAP-4.2、SAP-4.3、SAP-1.5｜同質與異質資料庫遷移、Oracle 授權

### 練習 51-12｜SAP｜單選｜PCI 範圍與遷移的網路加密

Wanderly 要把旅行社的支付系統搬到 AWS。這個系統處理信用卡資料，必須通過 PCI DSS 稽核。公司已用 Control Tower 建立 landing zone，地端與 AWS 之間以兩條 10 Gbps dedicated Direct Connect 連接，DX location 支援 MACsec。稽核要求是：盡量縮小需要接受 PCI DSS 稽核的 AWS 範圍，且地端到 AWS 之間的所有流量都要加密。

哪個方案最合適？

- A. 為支付系統建立獨立的 `payments-prod` 帳號並放在專屬的 OU，套用更嚴格的 SCP 與 Config 規則；在兩條 DX connection 上啟用 MACsec，加密地端到 AWS 的鏈路
- B. 把支付系統放進既有的 `agency-apps-prod` 帳號，以 security group 隔離；DX 是專用線路，不需額外加密
- C. 把支付系統放進獨立帳號，但所有地端流量改走 Internet 上的 HTTPS，停用 Direct Connect
- D. 把支付系統與其他系統放在同一個帳號，並在每台 EC2 上安裝主機防火牆；DX 上啟用 BGP MD5 驗證以加密流量

> [!answer]- 答案：A
> **A ✓** 帳號是最強的隔離邊界（第 40 章），把持卡人資料環境獨立成一個帳號，可以讓 PCI DSS 範圍只涵蓋這個帳號，並以 OU 層級的 SCP 與 Config 規則強化控制。DX 預設不加密；在支援的 dedicated connection 上啟用 MACsec，提供鏈路層加密，不影響 DX 的頻寬優勢。
>
> **B ✗** 和其他系統共用帳號會讓整個帳號都落入稽核範圍；DX 是專用線路但預設不加密，不符合加密要求。
>
> **C ✗** 獨立帳號是對的，但放棄 DX 改走 Internet 會失去穩定頻寬與延遲，對遷移與長期共存不利；DX 加上 MACsec 或 IPsec 就能滿足加密需求。
>
> **D ✗** 共用帳號擴大稽核範圍；BGP MD5 只驗證路由協定的 session，不會加密業務資料。
>
> **考點**：SAP-1.4、SAP-1.2、SAP-1.1｜以帳號縮小合規範圍、DX 上的 MACsec 加密
