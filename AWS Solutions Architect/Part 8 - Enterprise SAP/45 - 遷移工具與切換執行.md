# 第 45 章　遷移工具與切換執行：MGN、DMS、SCT 與資料搬遷

> [!abstract] 本章地圖
> **你會學到**：
> - 說明 AWS Application Migration Service（MGN）如何以區塊層級持續複寫，把伺服器搬到 EC2，並走完測試、cutover、finalize 的生命週期
> - 設定 MGN 的 replication settings、launch settings 與 post-launch actions，讓複寫走私有網路、搬上去的 instance 自動符合規範
> - 用 AWS DMS 的 full load 與 CDC 搬資料庫，選擇 replication instance 或 DMS Serverless，並以 validation 證明資料一致
> - 分辨同質（homogeneous）與異質（heterogeneous）資料庫遷移，知道 SCT 與 DMS Schema Conversion 負責什麼、DMS 不會幫你搬什麼
> - 依資料量與頻寬，在 DataSync、Direct Connect 與離線傳輸之間做選擇
> - 寫出一份有 go／no-go 檢查點與 rollback 路徑的 cutover runbook，把停機時間壓到最短
>
> **前置知識**：第 8 章（Direct Connect）、第 24 章（FSx）、第 25 章（DataSync 與資料移轉）、第 26 章（RDS）、第 44 章（7Rs 與 wave planning）
> **考試比重**：SAA ★★☆（Domain 3 資料庫與資料傳輸）｜SAP ★★★（Domain 4 遷移執行、Domain 2 業務持續）

## 45.1 故事：一個只有四小時的週六夜晚

第 44 章的 wave 計畫走到了 W6：訂房系統與它的 Oracle 資料庫。這是旅行社最關鍵的 move group：6 台應用伺服器、2 台帳務批次伺服器，以及一套 3 TB 的 Oracle Enterprise Edition 資料庫。業務部門只同意一個停機窗口：某個週六晚上 22:00 到隔天 02:00，四個小時。超過這個時間，週日早上的團體旅遊報到就會受影響。

四個小時聽起來不少，但美玲算了一下：如果用「關機、備份、複製、還原、開機」的傳統方式，就算旅行社已經有兩條 10 Gbps 的 Direct Connect（第 41 章），單一備份檔的複製也很難跑滿專線（單一 TCP 連線的吞吐量受往返延遲與視窗大小限制），加上專線同時承載正式流量與其他 wave 的複寫，實測只能用到約 2 Gbps。光是把 3 TB 的備份檔傳過去就要三個多小時（3 × 10¹² × 8 ÷ (2 × 10⁹) ＝ 12,000 秒），還沒算備份本身、還原與驗證。8 台伺服器的磁碟加起來還有 4 TB。

答案是：**不要在停機窗口內搬資料**。資料要在停機前好幾週就開始持續複寫到 AWS，讓 AWS 那一端一直保持「只落後幾秒」的狀態。停機窗口內只做三件事：停止來源的寫入、等最後幾秒的差異同步完成、把流量切過去。這就是本章所有工具的共同設計思想：**持續複寫，最後才切換**。

本章依照這個週六夜晚需要的工具，依序介紹：搬伺服器的 MGN、搬資料庫的 DMS、轉換資料庫結構的 SCT 與 DMS Schema Conversion、搬檔案與大量資料的 DataSync 與其他選項，最後把它們組成一份 cutover runbook，並準備好萬一失敗時的退路。

## 45.2 工具地圖：誰負責搬什麼

在進入細節之前，先建立全貌。遷移時要搬的東西可以分成四類，每一類有對應的工具：

| 要搬的東西 | 主要工具 | 搬的單位 | 停機前持續同步？ |
|---|---|---|---|
| 整台伺服器（作業系統、應用程式、設定） | AWS Application Migration Service（MGN） | 磁碟區塊 | 是 |
| 資料庫的資料 | AWS Database Migration Service（DMS） | 資料表的列（row） | 是（CDC） |
| 資料庫的結構與程式碼（異質遷移） | AWS SCT、DMS Schema Conversion | 資料表定義、預存程序、函式 | 否（遷移前一次性轉換） |
| 檔案（NFS、SMB 共用資料夾） | AWS DataSync | 檔案與 metadata | 可排程增量同步 |
| 極大量資料且網路不足 | 離線實體傳輸（見 45.9 節） | 裝置 | 否 |

```text
 旅行社資料中心                          Direct Connect                 AWS（東京）
 ┌──────────────────────────┐          ┌──────────┐      ┌─────────────────────────────────┐
 │ App／批次伺服器 ×8        │ ① 區塊    │          │      │ MGN staging subnet               │
 │  (MGN replication agent) │ ─────────┼──────────┼────▶ │  replication servers + EBS       │
 │                          │          │          │      │        │ ② test／cutover launch  │
 │                          │          │          │      │        ▼                        │
 │                          │          │          │      │ App subnet：EC2 instances        │
 │ Oracle 3 TB              │ ③ 初始載入 │          │      │                                 │
 │  (redo / archived logs)  │ ─────────┼──────────┼────▶ │ DMS replication instance        │
 │                          │  + CDC   │          │      │        │                        │
 │                          │          │          │      │        ▼                        │
 │                          │          │          │      │ Data subnet：RDS for Oracle      │
 │ Windows 檔案伺服器 ×6     │ ④ 檔案    │          │      │                                 │
 │  (DataSync agent VM)     │ ─────────┼──────────┼────▶ │ FSx for Windows File Server      │
 └──────────────────────────┘          └──────────┘      └─────────────────────────────────┘
```

① MGN 的 agent 持續把每台伺服器的磁碟變更送到 AWS 的 staging area（暫存區）。② 要測試或正式切換時，MGN 從暫存的資料啟動真正的 EC2 instance。③ DMS 先把 Oracle 的既有資料載入 RDS，之後持續讀取 Oracle 的交易日誌，把每一筆變更套用到 RDS。④ DataSync 透過部署在機房的 agent 把檔案伺服器的資料同步到 FSx（檔案伺服器在 W3 就已經搬完，這裡畫出來是為了完整）。所有流量都走 Direct Connect，不經過 Internet。

> [!note] 已經退場的舊工具
> 你可能在舊文章看到 AWS Server Migration Service（SMS）或 CloudEndure Migration。這兩者都已停止服務，功能由 MGN 取代。考試若出現「把伺服器 rehost 到 EC2」，現行答案是 MGN。

## 45.3 MGN 的原理：區塊層級的持續複寫

### 為什麼是「區塊」而不是「檔案」

**AWS Application Migration Service（MGN）** 是把實體機、VM 或其他雲端上的伺服器 rehost 到 EC2 的主要工具。它的核心技術是**區塊層級複寫（block-level replication）**：不管磁碟上是什麼作業系統、什麼檔案系統、什麼應用程式，agent 只看磁碟的區塊（block，磁碟讀寫的最小單位），哪個區塊被寫了，就把那個區塊送到 AWS。

這個設計帶來兩個重要特性。第一，**應用程式無關**：Oracle、SQL Server、自寫的 C++ 程式、甚至沒有人知道是什麼的老軟體，只要它們的資料在磁碟上，就能被完整複製。第二，**持續且近乎即時**：初始同步完成後，agent 只送變更的區塊，AWS 端的副本通常只落後幾秒到幾分鐘。

### 架構與流程

```text
 來源伺服器（Linux／Windows）
 ┌───────────────────────────┐
 │ 應用程式寫入磁碟            │
 │ AWS Replication Agent      │── ① TCP 443 ──▶ MGN 服務 endpoint（控制、註冊、指令）
 │  攔截區塊變更、壓縮、加密    │
 └─────────────┬─────────────┘
               │ ② TCP 1500（資料）
               ▼
 AWS 目標帳號 ── staging subnet ───────────────────────────────────────
 │ ┌──────────────────────────┐                                         │
 │ │ Replication server（EC2） │── ③ 寫入 ──▶ Staging EBS volumes        │
 │ │  輕量 instance，多台來源共用│             （每個來源磁碟一個）         │
 │ └──────────────────────────┘                     │                   │
 │                                                  │ ④ 建立 snapshot     │
 │                                                  ▼                   │
 │                            ┌──────────────────────────────┐          │
 │                            │ Conversion server             │          │
 │                            │  修改開機設定、安裝 EC2 驅動程式│          │
 │                            └───────────────┬──────────────┘          │
 └────────────────────────────────────────────┼─────────────────────────┘
                                              │ ⑤ 依 launch template 啟動
                                              ▼
                               目標 subnet：test／cutover EC2 instance
```

① **AWS Replication Agent** 安裝在來源伺服器的作業系統裡，透過 TCP 443 向 MGN 服務註冊並接收指令。② 磁碟資料經 TCP 1500 送到 AWS 端的 replication server，傳輸時加密並壓縮。③ **Replication server** 是 MGN 在你帳號的 **staging subnet** 中自動建立的輕量 EC2 instance，把收到的區塊寫入 **staging EBS volume**；一台 replication server 可以服務多台來源伺服器，這讓暫存區的成本很低。④ 要啟動 instance 時，MGN 從 staging volume 建立快照。⑤ MGN 啟動一台 **conversion server**，把來源磁碟「改裝」成能在 EC2 上開機的狀態，例如安裝 EC2 需要的網路與儲存驅動程式、調整開機設定，再依照 launch template 啟動目標 instance。

這裡要記住一個重點：**staging area 與最終的 instance 是分開的**。複寫期間只有便宜的 replication server 與 EBS 在運作，真正的應用程式 instance 只在測試或 cutover 時才啟動。MGN 服務本身對每台來源伺服器提供 2,160 小時（約 90 天的連續複寫）的免費使用額度，超過後按伺服器時數計費；staging area 的 EC2、EBS 與快照則一開始就照常計費。

### 網路需求

MGN 的連線需求是考試常考的設定題：

| 來源 → 目的 | Port | 用途 |
|---|---|---|
| 來源伺服器 → MGN 服務 endpoint | TCP 443 | 註冊、控制、指令 |
| 來源伺服器 → replication server | TCP 1500 | 磁碟資料複寫 |
| Replication server → MGN 服務 endpoint、S3 | TCP 443 | 回報狀態、下載軟體 |

旅行社的資安規定，複寫流量不得經過 Internet。MGN 的 replication settings 有一個選項是**使用 private IP 傳送資料**：replication server 不配 public IP，來源伺服器透過 Direct Connect 或 VPN 直接連到 replication server 的 private IP。控制流量則可以透過 MGN 的 interface VPC endpoint（PrivateLink，第 6 章）走私有路徑。

> [!warning] 常見誤解
> 「MGN 是 agent 對 agent 的複製，AWS 這邊不需要網路設計。」AWS 端需要一個專門的 staging subnet，而且它的路由、security group 與 NACL 必須允許來源伺服器連入 TCP 1500、允許 replication server 對外連到 MGN 與 S3 的 endpoint。最常見的「複寫卡在初始同步」原因，就是機房防火牆或 staging subnet 擋了 1500 port。

### Agentless 選項

MGN 也支援 VMware vCenter 環境的 **agentless replication**：在機房部署一個連接 vCenter 的元件，以快照方式複寫 VM，不用在每台 VM 內安裝 agent。代價是複寫以快照週期進行，不像 agent 那樣近乎連續，cutover 時的資料差異窗口較大。有 agent 可用時，MGN 的標準做法仍是 agent-based。

## 45.4 MGN 的設定：複寫怎麼走、instance 長什麼樣

MGN 的設定分成兩大類：決定「資料怎麼複寫」的 replication settings，與決定「目標 instance 長什麼樣」的 launch settings。

### Replication settings template

**Replication settings template** 是套用到所有新加入來源伺服器的預設複寫設定，也可以對個別伺服器覆寫。主要欄位：

| 設定 | 作用 | 旅行社的選擇 |
|---|---|---|
| Staging area subnet | Replication server 放在哪個 subnet | 遷移帳號中專用的 staging subnet |
| Replication server instance type | Replication server 的規格 | 預設；高寫入的資料庫主機改用專屬 replication server |
| Staging disk type | Staging EBS 的類型 | 預設自動選擇；高變更量的磁碟用 SSD 類型 |
| EBS encryption | Staging volume 加密 | 使用遷移帳號的 KMS customer managed key |
| Data routing | 是否用 private IP 傳資料 | 使用 private IP（經 Direct Connect） |
| Bandwidth throttling | 限制複寫頻寬 | 白天限速，避免擠壓機房的正式流量 |
| Security group | Replication server 的 security group | 由 MGN 自動建立並維護 |

頻寬限速很重要。旅行社的兩條 Direct Connect 各 10 Gbps，但白天還要承載與 AWS 上已遷移系統之間的正式流量，而且網路團隊以「只剩一條線也要撐得住業務加複寫」做容量規劃（第 51 章）。如果十幾台伺服器同時做初始同步，仍可能擠壓正式流量。美玲的做法是錯開各 wave 的初始同步時間，並在白天對每台伺服器限速。

### Launch settings 與 EC2 launch template

每台來源伺服器都有自己的 **launch settings** 與一份 **EC2 launch template**，決定測試與 cutover 時啟動的 instance：

- **Instance type right-sizing**：依來源伺服器的 CPU 與記憶體自動挑選相近的 instance type，或關閉此功能、在 launch template 中手動指定（例如依第 44 章的使用率資料選擇較小的規格）。
- **Subnet、security group、private IP**：test 與 cutover 可以使用不同的 subnet，例如測試放在隔離的 test subnet，cutover 放在正式的 app subnet。也可以選擇沿用來源伺服器的 private IP（前提是目標 subnet 涵蓋該位址）。
- **作業系統授權**：Windows 伺服器可以選擇 License Included 或 BYOL（BYOL 時搭配第 44 章的 Dedicated Hosts）。
- **Tags 與 IAM instance profile**：把來源伺服器的 tag 轉移到 instance，並指定 instance profile 讓 Systems Manager 能管理它。

### Post-launch actions

只把 instance 開起來還不夠：它還需要安裝 CloudWatch agent、加入監控、移除只在機房用得到的軟體（例如舊的備份 agent、VMware Tools），也許還要驗證應用程式的 HTTP 回應。**Post-launch actions** 讓 MGN 在 instance 啟動後，自動透過 **Systems Manager（SSM）** 執行一系列動作。MGN 提供一組預先定義的動作（例如安裝 SSM agent、驗證磁碟空間、驗證 HTTP 回應），你也可以指定自己撰寫的 SSM document。

這個功能是 migration factory 的關鍵：200 台伺服器的「搬上去之後要做的事」被寫成程式碼，每台都一樣執行，不會因為某位工程師某天太累而漏掉一步。旅行社的 post-launch actions 包括：安裝 SSM agent 與 CloudWatch agent、移除舊的防毒與備份 agent、加入 AWS Backup 的 tag、執行應用程式健康檢查。

> [!tip] 考試提示
> 題目若要求「遷移後的每台 instance 自動安裝監控 agent、執行設定腳本，而且要最少人工操作」，答案是 MGN 的 post-launch actions（透過 Systems Manager 執行）。若要求「調整遷移後 instance 的規格、subnet 或 security group」，答案是 launch settings／EC2 launch template。

## 45.5 MGN 的生命週期：測試、cutover 與 finalize

設定完成、資料持續複寫之後，每台來源伺服器會走過一個固定的生命週期。理解每個狀態代表什麼、能不能回頭，是設計 cutover 計畫的基礎。

```text
 Not ready ──▶ Ready for testing ──▶ Test in progress ──▶ Ready for cutover
 （初始同步中）  （同步完成，可測試）     │ 驗收不通過              │
                     ▲                │ 修正後重新測試           │
                     └────────────────┘                        ▼
                                              Cutover in progress ──▶ Cutover complete
                                                   │（可 revert，回到 Ready for cutover）
                                                   ▼
                                        Finalize cutover：停止複寫、清除 staging 資源
                                                   ▼
                                           Disconnected ──▶ Archived
```

**1. Not ready → Ready for testing**：agent 安裝後開始初始同步，把整顆磁碟複製一次。完成後進入持續複寫，狀態變成 Ready for testing。

**2. Test launch**：從最新的複寫資料啟動 test instance。重點是：**測試期間複寫不會停止**，來源伺服器照常服務使用者，test instance 在隔離的 test subnet 中執行，不影響正式環境。這讓你可以在 cutover 之前，對真正的資料與真正的作業系統做完整測試。

測試要測什麼？開得了機只是第一步。美玲的測試清單包括：應用程式服務能否啟動、能否連到 AD 與 DNS、能否連到相依的系統（在測試環境中可能要連到測試用的資料庫副本）、完整跑一次核心業務流程（查詢、訂房、取消）、批次作業能否執行。第 44 章那個每天 06:00 才出現的列印伺服器相依，就是在 test launch 期間被發現的。

**3. Mark as ready for cutover**：測試通過、應用程式負責人驗收後，終止 test instance 並把伺服器標記為 Ready for cutover。若測試發現問題，修正 launch settings 或來源設定後可以重新測試，次數不限。

**4. Cutover launch**：在停機窗口內，先在來源伺服器停止應用程式（讓磁碟不再變更），確認 MGN 顯示的複寫延遲（lag）為零、沒有待傳的資料（backlog），再啟動 cutover instance。cutover instance 會使用正式的 subnet 與設定。

**5. Revert 或 finalize**：cutover instance 啟動後，如果驗收失敗，在 **finalize 之前可以 revert cutover**，伺服器回到 Ready for cutover 狀態，複寫可以繼續，日後再試。驗收成功後執行 **finalize cutover**：MGN 停止這台伺服器的複寫並清除 staging area 的資源（replication server 的關聯、staging volume）。Finalize 之後就無法再從 MGN 回頭，所以它應該在 rollback 期限過後才執行（45.11 節）。

**6. Disconnect 與 archive**：最後把來源伺服器從 MGN 斷開並封存，讓清單只顯示還在進行中的伺服器。

```bash
# 在 Linux 來源伺服器上執行安裝程式（需提供有權限的 credentials，指定目標 Region）
sudo ./aws-replication-installer-init --region ap-northeast-1

# 以 CLI 啟動測試、cutover 與 finalize（也可以在 console 依 wave 批次操作）
aws mgn start-test --source-server-ids s-1234567890abcdef0
aws mgn start-cutover --source-server-ids s-1234567890abcdef0
aws mgn finalize-cutover --source-server-id s-1234567890abcdef0
```

MGN 也支援在服務內把伺服器分組成 **application** 與 **wave**，對整個 wave 一次執行測試或 cutover，與第 44 章的 wave 計畫對應。

> [!warning] 常見誤解
> 「Cutover instance 開起來就代表遷移完成，馬上 finalize 省錢。」Finalize 會移除 MGN 的回頭路。在業務驗收、監控穩定、rollback 期限都過了之前，不要 finalize，也不要刪除或重新利用來源伺服器。

> [!note] MGN 與 Elastic Disaster Recovery
> AWS Elastic Disaster Recovery（DRS，第 34 章）使用相同的區塊層級複寫技術，但目的是災難備援：持續複寫、平時不啟動、災難時快速在 AWS 上 recovery，之後還能 failback 回原處。MGN 的目的是一次性遷移。題目說「遷移」選 MGN，說「持續的 DR、RPO 秒級、可 failback」選 DRS。

## 45.6 DMS：一邊服務一邊搬資料庫

伺服器的問題解決了，接下來是更棘手的資料庫。你可能會問：既然 MGN 能複製整台伺服器，為什麼不直接用 MGN 搬 Oracle 主機？

答案取決於目標。如果目標是「Oracle 繼續跑在 EC2 上的自管 Oracle」（rehost），用 MGN 複製整台主機是可行的。但旅行社的目標是 **RDS for Oracle**（第 44 章的 replatform）：RDS 是受管服務，你不能把一顆磁碟映像檔直接塞進去。要把資料搬進受管資料庫，就需要在「資料」這一層運作的工具。

### DMS 的組成

**AWS Database Migration Service（DMS）** 在資料庫的邏輯層搬資料：它以 SQL 或資料庫的原生介面從來源讀出資料列，再寫入目標。它有四個組成：

- **Source endpoint／target endpoint**：來源與目標資料庫的連線資訊（主機、port、帳號、加密設定），帳密可以存在 Secrets Manager。支援的來源與目標很多：Oracle、SQL Server、MySQL、PostgreSQL、MongoDB、Db2 等；目標除了 RDS 與 Aurora，也可以是 S3、DynamoDB、Redshift、Kinesis Data Streams 等。
- **Replication instance**：實際執行搬遷工作的運算資源，是 DMS 在你 VPC 內建立的受管 EC2 instance。它必須能同時連到來源與目標，所以通常放在可經 Direct Connect 連回機房的 subnet。它可以啟用 **Multi-AZ**，在另一個 AZ 有備援，避免單一 AZ 故障中斷長時間的複寫。
- **DMS Serverless**：不用自己挑 replication instance 的規格，而是設定容量範圍（以 DCU，DMS capacity unit 為單位的最小值與最大值），由 DMS 依負載自動配置與擴縮。適合負載難以預估、或不想管理 instance 規格的情境；支援的來源與目標引擎組合以官方清單為準。
- **Task（任務）**：定義「從哪個 endpoint 搬到哪個 endpoint、搬哪些資料表、用什麼方式搬」。

### 三種遷移類型

每個 task 要選擇一種 **migration type**：

| 類型 | 做什麼 | 適用 |
|---|---|---|
| Full load | 把選定資料表的現有資料一次複製到目標 | 可以接受停機、資料量小，或一次性的資料搬遷 |
| Full load + CDC | 先做 full load，接著持續套用來源的變更 | **最小停機遷移的標準做法** |
| CDC only | 只從某個時間點開始套用變更 | 初始資料已用其他方式（例如原生備份工具）載入後，接續同步 |

**CDC（Change Data Capture，變更資料擷取）** 是 DMS 能做到最小停機的關鍵。DMS 不是定期掃描整張表找差異，而是讀取資料庫自己的**交易日誌**：每個資料庫都會把每一筆 INSERT、UPDATE、DELETE 記錄在日誌中（Oracle 的 redo log 與 archived redo log、SQL Server 的 transaction log、MySQL 的 binary log、PostgreSQL 的 WAL），DMS 從日誌讀出變更，依序套用到目標。

### Full load + CDC 的時間線

```text
 時間 ─────────────────────────────────────────────────────────────────────▶
 T0：task 開始          T1：full load 完成            T2：停止來源寫入   T3：切換
  │                       │                             │                │
  ├─ ① 開始擷取變更並暫存（cached changes）              │                │
  ├─ ② 逐表 full load ────┤                             │                │
  │                       ├─ ③ 套用暫存的變更             │                │
  │                       ├─ ④ 持續 CDC：落後數秒 ───────┤                │
  │                       │                             ├─ ⑤ 等 CDC 延遲歸零
  │                       │                             │    驗證、切換連線 ┤
```

① Task 一開始，DMS 就記下交易日誌的位置並開始擷取變更，因為 full load 期間來源仍在接受寫入。② 依資料表逐一 full load；3 TB 的資料可能要跑上好幾天，期間應用程式照常運作。③ Full load 完成後，DMS 把載入期間累積的變更（cached changes）套用到目標。④ 進入持續 CDC，目標通常只落後來源數秒。這個狀態可以維持數週，讓團隊從容地測試與驗證。⑤ 停機窗口內停止來源寫入，等 CDC 延遲歸零後切換。停機時間只剩 T2 到 T3，通常是分鐘級。

### CDC 的前提條件

CDC 讀的是交易日誌，所以來源資料庫必須保留足夠完整的日誌，而且要提前設定好，這常常需要 DBA 協助並可能需要重新啟動資料庫：

- **Oracle**：資料庫要在 **ARCHIVELOG 模式**，並啟用 **supplemental logging**（補充日誌，讓日誌記錄足夠的欄位資訊以識別被修改的資料列）。DMS 可以用 Oracle LogMiner 或 Binary Reader 讀取日誌。
- **SQL Server**：使用 full recovery model，並啟用 MS-Replication 或 MS-CDC。
- **MySQL**：啟用 binary log，`binlog_format` 設為 `ROW`。
- **PostgreSQL**：`wal_level` 設為 `logical`，使用 logical replication slot。

另外，archived log 的保留時間要夠長：如果 DMS task 因故暫停了一天，而來源只保留 12 小時的 archived log，DMS 回來時就找不到中間的變更，只能重新 full load。

> [!tip] 考試提示
> 「資料庫遷移、停機時間最短」→ DMS full load + CDC。「CDC task 建立成功但沒有擷取到任何變更」或「Oracle 來源的變更沒有同步」→ 檢查 ARCHIVELOG 與 supplemental logging（MySQL 則是 binlog 格式）。

## 45.7 Schema conversion：同質與異質遷移

DMS 搬的是**資料**。資料表的結構、索引、預存程序、觸發程序這些「資料庫物件」，DMS 只處理一小部分。這一節釐清哪些工作需要另外的工具。

### 同質 vs 異質

- **同質遷移（homogeneous）**：來源與目標是同一種資料庫引擎，例如 Oracle → RDS for Oracle、MySQL → Aurora MySQL。資料表定義、資料型別、PL/SQL 程式碼都能原樣使用，不需要轉換。
- **異質遷移（heterogeneous）**：引擎不同，例如 Oracle → Aurora PostgreSQL、SQL Server → Aurora MySQL。資料型別要對應（Oracle 的 `NUMBER` 對應到 PostgreSQL 的 `NUMERIC` 或整數型別）、SQL 語法要改寫、預存程序要從 PL/SQL 轉成 PL/pgSQL，這些工作在搬資料之前必須先完成。

### DMS 不會幫你搬的東西

DMS 在目標上建立資料表時，只會建立**資料表與主鍵**（某些情況下包含唯一索引），不會建立：

- Secondary index（次要索引）
- 外鍵等非主鍵限制條件
- 欄位預設值
- Sequence（序號產生器）的目前值
- 預存程序、函式、觸發程序、view

這是遷移後最常見的兩個事故來源：**忘了建 secondary index**，切換後查詢從毫秒變成數十秒；**忘了重設 sequence**，切換後應用程式新增資料時，sequence 從 1 開始產生編號，和已搬過來的資料主鍵衝突。

因此標準做法是：**先用其他方式在目標建立完整的 schema，再讓 DMS 只搬資料**。同質遷移可以用資料庫原生工具匯出匯入 schema（例如 Oracle Data Pump 只匯出 metadata）；異質遷移則用下面的轉換工具。

### AWS SCT 與 DMS Schema Conversion

**AWS Schema Conversion Tool（SCT）** 是一個安裝在你電腦上的桌面應用程式。它連到來源資料庫讀取所有物件的定義，自動轉換成目標引擎的語法，並產生 **assessment report（評估報告）**：列出多少比例的物件可以自動轉換、哪些需要人工處理（**action items**），以及每一項的轉換難度。這份報告是第 44 章「要 replatform 還是要 refactor」的重要依據：如果 95% 的物件能自動轉換，異質遷移可行；如果有數萬行 PL/SQL 無法自動轉換，可能先同質遷移、之後再現代化比較實際。SCT 也支援資料倉儲的轉換（例如 Teradata 或 Oracle 資料倉儲 → Redshift），並能掃描應用程式原始碼中內嵌的 SQL。

**DMS Schema Conversion** 是整合在 DMS console 裡的受管版本：不需要安裝軟體，在 DMS 中建立 **migration project**，指定來源與目標的 **data provider**（資料庫連線資訊）與 **instance profile**（執行轉換的網路與儲存設定），即可產生評估報告並轉換 schema。它支援的來源與目標組合比 SCT 少，但對新專案來說是 AWS 目前主推的方式，營運負擔也較低。

| 比較 | AWS SCT | DMS Schema Conversion |
|---|---|---|
| 形式 | 桌面應用程式，自行安裝 | DMS console 中的受管功能 |
| 評估報告與 action items | 有 | 有 |
| 資料倉儲轉換（→ Redshift） | 支援 | 支援範圍較有限 |
| 應用程式內嵌 SQL 掃描 | 支援 | 以官方文件為準 |
| 營運負擔 | 要自己維護執行環境 | 低 |

不論哪一個工具，**轉換 schema 是一次性的前置工作，不負責搬資料**；資料的 full load 與 CDC 仍由 DMS 執行。

### 不同情境的組合

| 情境 | Schema | 初始資料 | 持續同步 |
|---|---|---|---|
| Oracle → RDS for Oracle（3 TB，同質） | Data Pump 匯出 metadata | Data Pump 匯出匯入（快、保留原生物件） | DMS CDC only，從匯出時的 SCN 開始 |
| MySQL → Aurora MySQL（同質，中小型） | 原生工具或讓 DMS 建表後補索引 | DMS full load | DMS CDC |
| MySQL 5.7／8.0 → Aurora MySQL（同質，數 TB 以上） | 隨實體備份一起還原；使用者帳號、function、stored procedure 另外匯出重建 | Percona XtraBackup 實體備份上傳 S3，再「Restore from S3」建立新 cluster | MySQL binlog replication（或 DMS CDC） |
| Oracle → Aurora PostgreSQL（異質） | SCT 或 DMS Schema Conversion | DMS full load | DMS CDC |
| SQL Server → Aurora PostgreSQL，盡量不改應用程式 | SCT 或 DMS Schema Conversion，評估 Babelfish | DMS full load | DMS CDC |

第一列是旅行社實際採用的方案。對大型同質資料庫，原生工具通常比 DMS full load 更快、更能保留所有原生物件；DMS 的角色是在原生匯出的時間點之後接手 CDC。**SCN（System Change Number）** 是 Oracle 交易日誌中的位置編號，DMS 的 CDC-only task 可以指定從某個 SCN 開始，確保匯出與 CDC 之間不漏也不重複。DMS 對部分同質組合（例如 MySQL、PostgreSQL）也提供以原生工具為基礎的 **homogeneous data migrations** 功能，以 serverless 方式執行。

大型 MySQL 的第二列做法有幾個容易漏掉的限制：Aurora 從 S3 的 XtraBackup 備份還原時**不會帶入使用者帳號、function、stored procedure 與時區資訊**（時區改用 Aurora cluster 本身的設定），這些要事先從來源匯出定義（例如 `mysqldump --no-data --routines` 加上帳號與權限的匯出），在新 cluster 上重建；此外只能還原成新的 cluster、S3 bucket 必須和 cluster 在同一個 Region、來源不能是加密的資料庫，未壓縮備份目前上限 64 TiB。漏掉這一步的典型症狀是：資料都在，但應用程式一連線就因為帳號不存在或呼叫不到 stored procedure 而失敗。

旅行社另一套只用基本功能的 Oracle 報表資料庫，美玲先跑了 DMS Schema Conversion 的評估報告：92% 的物件可以自動轉換，剩下的 action items 多是日期函式與分頁語法。這份報告讓它被排進第 46 章的現代化計畫，轉到 Aurora PostgreSQL。

## 45.8 DMS 的細節：mapping、LOB、validation 與效能

### Table mapping

**Table mapping** 是一份 JSON 規則，告訴 DMS 要搬哪些 schema 與資料表（selection rule），以及搬的時候要不要改名稱或欄位（transformation rule）。

```json
{
  "rules": [
    {
      "rule-type": "selection",
      "rule-id": "1",
      "rule-name": "include-booking",
      "object-locator": { "schema-name": "BOOKING", "table-name": "%" },
      "rule-action": "include"
    },
    {
      "rule-type": "selection",
      "rule-id": "2",
      "rule-name": "exclude-temp-tables",
      "object-locator": { "schema-name": "BOOKING", "table-name": "TMP_%" },
      "rule-action": "exclude"
    },
    {
      "rule-type": "transformation",
      "rule-id": "3",
      "rule-name": "lowercase-schema",
      "rule-target": "schema",
      "object-locator": { "schema-name": "BOOKING" },
      "rule-action": "convert-lowercase"
    }
  ]
}
```

規則 1 選取 `BOOKING` schema 下所有資料表，規則 2 排除以 `TMP_` 開頭的暫存表，規則 3 把 schema 名稱轉成小寫（從 Oracle 搬到 PostgreSQL 時常用，因為 PostgreSQL 對未加引號的名稱預設使用小寫）。

### LOB 的處理

**LOB（Large Object，大型物件）** 是存放大量資料的欄位型別，例如 Oracle 的 `CLOB`、`BLOB`，旅行社用它存行程 PDF 與護照影像。LOB 很大且大小不一，DMS 提供幾種處理模式：

- **Limited LOB mode**：預先設定 LOB 的最大大小，DMS 以固定大小的緩衝區批次處理，速度快；**超過上限的部分會被截斷**。
- **Full LOB mode**：完整搬移任何大小的 LOB，但要逐筆查詢，速度明顯較慢。
- **Inline LOB mode**：小於門檻的 LOB 直接隨資料列處理，大於門檻的才用 full LOB 方式，兼顧兩者。

選 limited LOB mode 之前，一定要先在來源查詢 LOB 欄位的最大實際大小，否則可能在不知不覺中截斷資料。

### Validation：證明資料一致

稽核顧問問美玲：「你怎麼證明 RDS 上的資料和 Oracle 上的一模一樣？」答案是 **DMS data validation**。啟用後，DMS 在 full load 完成後逐列比較來源與目標的資料，並在 CDC 期間持續比較新變更的資料列，結果記錄在 task 的統計與一張控制表中，標示每張表的驗證狀態與不一致的資料列。也可以建立**只做驗證（validation-only）**的 task，對已經搬好的資料進行比對而不重新搬移。

Validation 會額外讀取來源與目標，增加負載與時間，所以要在規劃效能時納入考量。它證明的是「資料列一致」；應用程式行為是否正確，仍然要靠業務驗收測試。

```json
{
  "FullLoadSettings": {
    "TargetTablePrepMode": "DO_NOTHING",
    "StopTaskCachedChangesNotApplied": true
  },
  "TargetMetadata": {
    "LimitedSizeLobMode": true,
    "LobMaxSize": 32768
  },
  "ValidationSettings": {
    "EnableValidation": true,
    "ThreadCount": 5
  }
}
```

這份 task settings 的意思是：① `TargetTablePrepMode: DO_NOTHING` 表示目標的資料表已經預先建好（schema 由原生工具或轉換工具建立），DMS 不要刪除或重建它們。② `StopTaskCachedChangesNotApplied` 讓 task 在 full load 完成、套用暫存變更之前先停下來，團隊可以趁這時在目標建立 secondary index，再繼續 task；full load 期間沒有索引，寫入較快，CDC 階段有了索引，套用 UPDATE 與 DELETE 時才找得到資料列。③ Limited LOB mode 上限 32,768 KB（32 MB），前提是已確認沒有更大的 LOB。④ 啟用 validation。

### 效能與監控

- 大型資料表可以在 table mapping 中設定**平行載入**（依分割區或欄位範圍切段同時載入）。
- Full load 期間，目標的外鍵與觸發程序應暫時停用：DMS 以資料表為單位載入，順序不一定符合外鍵關係；觸發程序則可能在目標重複執行來源已經執行過的邏輯。
- 以 CloudWatch 監控 **`CDCLatencySource`**（DMS 從來源讀取變更的落後時間）與 **`CDCLatencyTarget`**（變更套用到目標的落後時間）。Cutover 的關鍵條件就是這兩個值接近零。
- 開始前執行 **premigration assessment**，DMS 會檢查不支援的資料型別、缺少主鍵的資料表、LOB 設定等常見問題。

## 45.9 搬檔案與大量資料：DataSync、Direct Connect 與離線傳輸

資料庫之外，旅行社還有 6 台 Windows 檔案伺服器，共 38 TB 的行程文件與掃描檔。這些在 W3 已經搬到 FSx for Windows File Server，這裡回頭說明當時的工具選擇。第 25 章已詳細介紹各種資料傳輸服務，本節只聚焦在遷移情境的判斷。

### DataSync：線上搬檔案的主力

**AWS DataSync** 是線上搬移檔案的受管服務。在機房部署一台 **DataSync agent**（以 VM 形式執行），agent 讀取 NFS、SMB 等來源，透過加密連線傳到 AWS 的目的地：S3、EFS 或各種 FSx 檔案系統。它的特點正好符合遷移的需求：

- **增量同步**：第一次完整傳輸後，之後的執行只傳有變更的檔案，可以排程每天執行，讓 AWS 端持續追上來源。
- **保留 metadata**：SMB 來源到 FSx for Windows File Server 時，可以保留 NTFS 權限（ACL）、時間戳記等 metadata，使用者搬過去後權限不變。
- **傳輸驗證**：可以在傳輸後檢查來源與目的地的資料是否一致。
- **頻寬限制**：設定上限，避免擠壓正式流量。
- **私有路徑**：agent 可以透過 VPC endpoint 經 Direct Connect 連到 DataSync 服務。

旅行社的做法：先用 DataSync 做完整傳輸，之後每晚增量同步；cutover 當天把來源共用資料夾設為唯讀、執行最後一次增量同步，再把使用者的網路磁碟機改指向 FSx。因為旅行社原本就使用 **DFS Namespaces**（Windows 的分散式檔案系統命名空間，讓使用者用一個邏輯路徑存取實際位於不同伺服器的共用資料夾），只要把命名空間的目標從舊伺服器改到 FSx，使用者看到的路徑完全不變。

> [!tip] 考試提示
> 「把地端 SMB 檔案伺服器遷移到 FSx for Windows File Server、保留 NTFS 權限、可增量同步」→ DataSync。「長期讓地端應用程式以 SMB 或 NFS 存取雲端儲存，並在本地快取」→ Storage Gateway（第 25 章），那是 hybrid 架構，不是一次性遷移。

### 先算頻寬：線上還是離線

選擇線上或離線傳輸，第一步永遠是計算。公式很簡單：

> 傳輸時間（秒）＝ 資料量（bit）÷ 實際可用頻寬（bit／秒）

以旅行社的檔案伺服器為例：38 TB ＝ 38 × 10¹² × 8 ＝ 3.04 × 10¹⁴ bit。旅行社的兩條 10 Gbps Direct Connect 同時承載正式流量與 MGN、DMS 的複寫，網路團隊依「剩一條線也撐得住」的原則分配頻寬後，給 DataSync task 的頻寬上限是 600 Mbps：

> 3.04 × 10¹⁴ ÷ (6 × 10⁸) ≈ 506,667 秒 ≈ 5.9 天

六天的線上傳輸完全可以接受，而且之後的增量同步只傳變更。這就是為什麼大多數企業遷移都以線上傳輸為主。實際規劃時還要再保留餘裕：網路不可能 100% 達到理論值，小檔案很多時每個檔案的處理開銷也會降低吞吐量。

但如果資料量是 2 PB、頻寬只有 500 Mbps，同樣的公式算出來超過一年，線上傳輸就不可行，這時才考慮離線傳輸或先加大頻寬。

### Direct Connect 在遷移中的角色

**Direct Connect**（第 8 章）在遷移中同時扮演兩個角色：MGN、DMS、DataSync 的複寫通道，以及遷移期間地端與 AWS 系統共存時的連線。它的頻寬穩定、延遲可預測，而且資料不經過 Internet。要注意的是，專線從申請到可用通常需要數週以上，所以它屬於 Wave 0 的工作；在專線就緒前，可以先用 Site-to-Site VPN 開始 pilot 與初始同步。遷移期間若需要更大頻寬，可以暫時增加連線或提高 hosted connection 的頻寬。

### 離線傳輸與 Snow 系列的現況

當網路怎樣都不夠時，就要把資料裝進實體裝置寄送。過去的標準答案是 **AWS Snow 系列**：Snowball Edge（數十 TB 等級的堅固裝置，AWS 寄到你的機房，裝滿資料後寄回，由 AWS 匯入 S3）、Snowcone（小型裝置）、Snowmobile（貨櫃車等級，用於 EB 級資料）。

這個系列的現況必須特別說明：**Snowmobile 已經退役，Snowcone 已經停產，Snowball Edge 也已不再對新客戶開放**（既有客戶仍可繼續使用），也就是說，新客戶已經無法訂購任何 Snow 系列裝置。AWS 對新客戶建議的替代方案是：線上傳輸用 DataSync（頻寬不足時，可以在遷移期間向 Direct Connect 合作夥伴租用臨時的 hosted connection 加大頻寬）；離線傳輸用 **AWS Data Transfer Terminal**：在特定城市設置的實體設施，你可以預約時段，把自己的儲存裝置帶到現場，透過高速網路直接上傳到 AWS；或者使用 AWS Marketplace 上合作夥伴提供的離線傳輸服務。

對考試而言，SAA／SAP 的題庫仍可能出現「頻寬不足、數百 TB、要在幾週內搬完 → Snowball Edge」這類題目，遇到時依題目的條件作答即可。實務上，新專案要先確認可用的離線選項，並優先考慮加大頻寬或延長線上傳輸時程。

延伸閱讀：[Snowball Edge availability change](https://docs.aws.amazon.com/snowball/latest/developer-guide/snowball-edge-availability-change.html)、[AWS Data Transfer Terminal](https://docs.aws.amazon.com/datatransferterminal/latest/userguide/what-is-dtt.html)。

## 45.10 資料庫切換：一步一步把連線換過去

工具都就位了，回到那個週六晚上。資料庫切換是整個 cutover 中最敏感的部分，因為它是唯一「兩邊都可能被寫入」的地方。下面是美玲團隊的資料庫切換步驟，以及每一步的用意。

### 切換前（T-14 天到 T-1 天）

1. **降低 DNS TTL**：應用程式透過 `orders-db.travel.internal` 這個名稱連資料庫。兩週前把這筆記錄的 TTL（快取時間，第 3 章）從 1 小時降到 60 秒，切換時用戶端才會很快拿到新位址。TTL 要提前降，因為舊的 TTL 值已經被快取在各處，要等舊 TTL 過期，新的 TTL 才會生效。
2. **確認 CDC 穩定**：`CDCLatencySource` 與 `CDCLatencyTarget` 持續維持在數秒內，validation 沒有不一致的資料列。
3. **效能測試**：在目標資料庫上以正式等級的負載測試查詢效能，確認 secondary index、統計資訊都到位。
4. **彩排**：用 MGN 的 test launch 加上一個資料庫測試副本，完整演練一次切換流程並計時。

### 切換當晚（T-0）

```text
 22:00  ① 公告維護、應用程式切到維護頁面，停止批次排程
 22:10  ② 確認來源資料庫沒有應用程式連線（session），必要時鎖定應用帳號
 22:15  ③ 等待 CDCLatencySource／Target 歸零，確認 validation 無不一致
 22:30  ④ 停止 DMS task
 22:35  ⑤ 目標資料庫收尾：依來源目前值重設 sequence、啟用觸發程序與外鍵
 22:50  ⑥ 啟動反向複寫 task（RDS → 地端 Oracle），作為 rollback 路徑
 23:00  ⑦ MGN cutover：確認 8 台伺服器 lag 為零後啟動 cutover instance
 23:40  ⑧ 更新 DNS：orders-db 指向 RDS endpoint；應用設定指向新的伺服器
 00:00  ⑨ 技術驗收：smoke test、核心交易、批次試跑
 01:00  ⑩ Go／no-go 決策：業務代表確認，通過則開放流量；不通過則執行 rollback
 02:00  窗口結束
```

① 和 ② 確保來源不再被寫入，這是避免資料分歧的前提。如果應用程式停了但還有排程作業或其他系統在寫，切換後那些寫入就會遺失。③ 是整個流程的關鍵條件：只有延遲歸零，才代表目標已經擁有來源的所有資料。⑤ 是 45.7 節提到的 DMS 不會處理的部分：sequence 要依來源的目前值重設（通常再加上一段安全間隔），否則新增資料時會主鍵衝突。⑥ 在開放新寫入之前就把反向複寫準備好，下一節說明為什麼。⑦ 到 ⑨ 切換應用伺服器並驗收。⑩ 的 go／no-go 是預先定義好的決策點：誰有權決定、依據什麼標準、最晚何時決定。這張時程表在 01:00 留了一個小時給 rollback，因為 rollback 也需要時間。

> [!warning] 常見誤解
> 「DMS validation 通過就代表可以切換。」Validation 證明的是資料列一致，不包含 sequence 的值、索引是否齊全、應用程式的 SQL 在新環境中的效能。切換前的檢查清單一定要包含 schema 物件的比對與實際的業務交易測試。

## 45.11 Cutover 與 rollback 計畫

### 為什麼 rollback 計畫比 cutover 計畫更重要

每一次 cutover 都可能失敗：應用程式在新環境出現未預期的錯誤、效能不如預期、某個相依系統連不上。如果沒有 rollback 計畫，失敗時團隊只能在凌晨兩點硬著頭皮修，這是遷移事故最常見的劇本。好的 rollback 計畫要事先回答三個問題：

1. **回到哪裡**：來源系統必須保持完整、可以重新啟動。MGN 的來源伺服器在 finalize 之前都不要關閉刪除，只是停止應用程式。
2. **資料怎麼辦**：切換後新系統可能已經接受了新的訂單。退回舊系統時，這些新資料要嘛同步回去，要嘛確認可以放棄（通常不行）。
3. **何時不能再回頭**：定義 **point of no return（不可回頭點）**，超過之後只能往前修。

### 反向複寫：讓 rollback 不遺失資料

這就是 45.10 節步驟 ⑥ 的用意。切換完成、新系統開始接受寫入之前，先建立一個方向相反的 DMS CDC task：**以 RDS 為來源、地端 Oracle 為目標**。之後新系統上的每一筆訂單都會持續同步回地端。萬一兩天後發現嚴重問題，只要停止新系統的寫入、等反向 CDC 延遲歸零，就能把應用程式切回地端，而且不遺失這兩天的訂單。

反向複寫有前提：目標（現在的 RDS）也要能提供 CDC 所需的日誌，地端 Oracle 要保持可寫入且結構不變。一旦在新系統上做了舊系統不支援的變更（例如修改 schema、啟用新功能），反向複寫就無法繼續，這就是自然形成的 point of no return。

### Rollback 計畫範例

| 時間點 | 失敗情境 | Rollback 方式 | 資料處理 |
|---|---|---|---|
| ⑧ 之前 | MGN instance 開不起來、DMS 延遲無法歸零 | 取消切換，重新啟動來源應用程式；MGN 執行 revert cutover | 來源從未停止作為權威，無資料遺失 |
| ⑩ go／no-go 不通過 | 驗收測試失敗 | DNS 改回地端、重新啟動來源應用程式 | 新系統尚未開放使用者寫入，無資料遺失 |
| 切換後 1–7 天 | 效能問題、隱藏的相依問題 | 停止新系統寫入，等反向 CDC 歸零，DNS 改回地端 | 反向複寫已把新資料同步回地端 |
| 第 7 天後 | — | 不再回退，往前修復 | 停止反向複寫，finalize MGN |

旅行社把 rollback 期限定為 7 天，涵蓋一次週末尖峰與一次每日帳務批次。7 天後，美玲才執行 MGN finalize cutover、停止反向複寫，並把地端伺服器排入關機清單。

### 減少停機時間的技巧整理

把本章的技巧整理在一起，就是最小停機遷移的完整方法：

- **持續複寫**：伺服器用 MGN、資料庫用 DMS full load + CDC、檔案用 DataSync 增量同步，讓停機窗口只需要處理最後的差異。
- **提前降低 DNS TTL**，切換時用戶端很快拿到新位址。
- **事先完成 schema 與索引**，切換當晚不做耗時的 DDL。
- **彩排並計時**，知道每一步實際要多久。
- **以 test launch 驗證**，讓 cutover 當晚不是第一次在 AWS 上啟動這些伺服器。
- **讓 go／no-go 的標準與決策者事先定案**，避免凌晨的臨時爭論。

## 45.12 Mainframe：最後一塊拼圖

旅行社沒有大型主機，但 Wanderly 打算收購的下一家航空票務公司有。SAP 考試偶爾會出現大型主機遷移的題目，這裡簡述 AWS 的選項。

**Mainframe（大型主機）** 是 IBM z 系列等專用硬體，上面常跑著以 COBOL 撰寫、使用 CICS（交易處理）、JCL（批次作業控制）、DB2 或 VSAM（資料儲存）的系統，很多已經運作數十年。它們無法用 MGN rehost，因為 MGN 只支援 x86 上的 Windows 與 Linux。

**AWS Mainframe Modernization** 把大型主機遷移整理成兩種模式（pattern）：

- **Replatform（重新平台化）**：保留 COBOL 原始碼，只做少量修改並重新編譯，在 AWS 上的相容執行環境（例如 Rocket Software，前身為 Micro Focus 的 Enterprise 方案）中執行。程式邏輯與語言不變，團隊既有的 COBOL 知識可以沿用，風險較低。
- **Automated refactor（自動重構）**：用工具把 COBOL 程式與資料層自動轉換成 Java 應用程式，資料轉到關聯式資料庫，之後可以用一般的 Java 技能維護與現代化。這個工具原名 **AWS Blu Age**，現在以 **AWS Transform for mainframe** 的名稱提供（並加入生成式 AI 協助分析與轉換程式碼）。

這個領域的提供方式近年變動很大，寫法要保守：依 AWS 文件，AWS Mainframe Modernization 的**受管執行環境（Managed Runtime Environment）**與 **self-managed experience**（包含以 Rocket 做 replatform 等方案）都已不再對新客戶開放，既有客戶可以繼續使用；新客戶的建議路徑是 AWS Transform 與軟體廠商直接提供的方案。考試的重點是判斷方向，而不是產品名稱：題目說「保留 COBOL、最少程式變更」→ replatform；說「轉成 Java、擺脫 COBOL 技能依賴、自動轉換」→ automated refactor（AWS Transform for mainframe／舊稱 Blu Age）。

## 45.13 比較與選型

### 工具選型

| 需求 | 選擇 | 不要選 |
|---|---|---|
| 伺服器 rehost 到 EC2，最小停機 | MGN | SMS（已停止）、手動匯出 VM 映像檔 |
| VMware 環境、不能在 VM 內裝 agent | MGN agentless replication（快照式） | — |
| 持續 DR、可 failback | Elastic Disaster Recovery | MGN |
| 資料庫搬到 RDS／Aurora，最小停機 | DMS full load + CDC | MGN（目標是受管服務時無法使用） |
| 大型同質資料庫的初始載入 | 原生工具（Data Pump 等）+ DMS CDC only | 只用 DMS full load（可能較慢） |
| 異質遷移的 schema 與程式碼 | DMS Schema Conversion 或 SCT | 只用 DMS（只建資料表與主鍵） |
| 容量難以預估、不想管 instance | DMS Serverless | 過大的 replication instance |
| 證明資料一致 | DMS data validation（或 validation-only task） | 只比較資料筆數 |
| SMB 檔案伺服器 → FSx for Windows | DataSync | 手動複製且不保留 ACL |
| 長期 hybrid 檔案存取 | Storage Gateway | DataSync |
| 資料量極大、頻寬不足 | 加大頻寬，或依現況評估離線傳輸 | 未經計算就假設線上傳得完 |
| COBOL 大型主機 | replatform（保留 COBOL）或 automated refactor（AWS Transform for mainframe 轉 Java） | MGN |

### 決策流程

```text
要搬的是什麼？
├─ 整台伺服器（Windows／Linux on x86）
│    └─ 目的是遷移 → MGN；目的是持續 DR → Elastic Disaster Recovery
├─ 資料庫
│    ├─ 目標是 EC2 上的自管同一引擎 → MGN 或原生工具
│    └─ 目標是 RDS／Aurora 等受管服務
│         ├─ 同質 → 原生工具或 DMS 建 schema → DMS full load + CDC
│         └─ 異質 → DMS Schema Conversion／SCT 轉 schema → DMS full load + CDC
├─ 檔案（NFS／SMB）
│    ├─ 一次性遷移 → DataSync（S3、EFS、FSx）
│    └─ 長期 hybrid → Storage Gateway
└─ 極大量資料
     └─ 先算：資料量 ÷ 可用頻寬 → 可接受就線上傳輸；不行再考慮加頻寬或離線傳輸
```

## 45.14 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 把大量實體或虛擬伺服器 rehost 到 EC2、最小停機 | AWS Application Migration Service（MGN） |
| 複寫流量不得經過 Internet | MGN replication settings 使用 private IP，經 Direct Connect／VPN |
| MGN 初始同步卡住 | 檢查 TCP 1500（來源 → replication server）與 TCP 443 |
| 遷移前在 AWS 上測試，不影響來源 | MGN test launch（複寫持續進行） |
| 遷移後自動安裝 agent、執行腳本 | MGN post-launch actions（Systems Manager） |
| 調整遷移後的 instance type、subnet | MGN launch settings／EC2 launch template |
| 資料庫遷移、停機時間最短 | DMS full load + CDC |
| Oracle 來源的 CDC 沒有變更 | ARCHIVELOG 模式與 supplemental logging |
| Oracle → PostgreSQL、轉換 PL/SQL | DMS Schema Conversion 或 SCT + DMS 搬資料 |
| 遷移後查詢很慢／新增資料主鍵衝突 | DMS 不建 secondary index、不搬 sequence 目前值 |
| 證明來源與目標資料一致 | DMS data validation |
| DMS 容量難以預估、不想管理 instance | DMS Serverless |
| SMB 檔案伺服器 → FSx、保留 NTFS 權限 | DataSync |
| 切換後幾天內仍要能退回、不遺失資料 | 反向 DMS CDC（新目標 → 舊來源） |
| 切換時用戶端快速改連新位址 | 提前降低 DNS TTL |
| COBOL 轉 Java | Automated refactor（AWS Transform for mainframe，舊稱 Blu Age） |

**常見陷阱**：

1. 以為 MGN 可以把資料庫搬進 RDS：MGN 複製的是整台伺服器，目標只能是 EC2；要進 RDS／Aurora 用 DMS。
2. 以為 DMS 會搬完整的 schema：它只建資料表與主鍵，secondary index、外鍵、sequence、預存程序要另外處理。
3. 以為 SCT 或 DMS Schema Conversion 會搬資料：它們只轉換 schema 與程式碼，資料仍由 DMS 搬。
4. Cutover 後立刻 finalize MGN 或刪除來源伺服器，失去 rollback 能力。
5. 選 limited LOB mode 卻沒有確認 LOB 最大大小，導致資料被截斷。
6. 沒有計算頻寬就選擇線上或離線傳輸；或把 Snowball Edge 當成新客戶一定可用的現行方案。
7. 把 Storage Gateway 當成一次性遷移工具：它是長期 hybrid 存取，遷移選 DataSync。

## 本章重點整理

- 最小停機遷移的核心是「持續複寫，最後才切換」：停機窗口內只停止寫入、同步最後差異並切換流量。
- MGN 以區塊層級持續複寫伺服器到 staging area（輕量 replication server 與 staging EBS），只有 test 或 cutover 時才啟動真正的 EC2 instance。
- MGN 的來源需要能連到服務 endpoint 的 TCP 443 與 replication server 的 TCP 1500；可設定以 private IP 經 Direct Connect 傳輸並限制頻寬。
- Launch settings 與 EC2 launch template 決定目標 instance 的規格、subnet 與授權；post-launch actions 透過 Systems Manager 自動執行遷移後的設定。
- MGN 生命週期為初始同步 → test launch（複寫持續）→ ready for cutover → cutover → finalize；finalize 之前可以 revert，finalize 後停止複寫並清除 staging 資源。
- DMS 由 endpoint、replication instance（可 Multi-AZ）或 DMS Serverless、task 組成；full load + CDC 是最小停機的標準做法。
- CDC 讀取交易日誌，來源要預先設定：Oracle 需要 ARCHIVELOG 與 supplemental logging，MySQL 需要 ROW 格式的 binlog，且日誌保留時間要足夠。
- DMS 只建立資料表與主鍵；secondary index、外鍵、預設值、sequence、預存程序要用原生工具或 schema 轉換工具處理，切換時要重設 sequence。
- 異質遷移先用 DMS Schema Conversion 或 SCT 轉換 schema 並產生評估報告，再用 DMS 搬資料；大型同質遷移可用原生工具做初始載入，再以 DMS CDC only 從 SCN 接續。
- DMS data validation 逐列比對來源與目標；LOB 欄位要依實際大小選擇 limited、full 或 inline LOB mode，以免截斷。
- DataSync 以 agent 增量同步 NFS／SMB 檔案到 S3、EFS、FSx，可保留 NTFS ACL；長期 hybrid 存取才用 Storage Gateway。
- 選擇傳輸方式前先計算「資料量 ÷ 可用頻寬」；Snowmobile 已退役、Snowcone 已停產、Snowball Edge 不再對新客戶開放，實務上要確認現況。
- Cutover runbook 要有提前降低 DNS TTL、停止寫入、等待 CDC 延遲歸零、資料庫收尾、預先定義的 go／no-go 決策點與 rollback 時間。
- 以反向 DMS CDC 讓切換後一段期間仍能退回而不遺失資料，並明確定義 point of no return 與 rollback 期限。
- 大型主機遷移分兩個方向：保留 COBOL 選 replatform，轉成 Java 選 automated refactor（AWS Transform for mainframe，舊稱 Blu Age）；AWS Mainframe Modernization 的受管執行環境已不再對新客戶開放。

### 練習 45-1｜SAA｜單選｜伺服器 rehost 工具

一家公司要把資料中心裡 150 台 Windows 與 Linux 伺服器搬到 Amazon EC2，其中包含實體機與 Hyper-V VM。每台伺服器的停機時間不能超過一小時，而且公司希望在正式切換前先在 AWS 上測試每台伺服器，測試期間來源伺服器必須持續服務使用者。

最合適的工具是什麼？

- A. AWS Application Migration Service，安裝 replication agent 持續複寫，先執行 test launch，再於停機窗口執行 cutover

- D. AWS Database Migration Service，以 full load + CDC 複製每台伺服器的資料

> **A ✓** MGN 以區塊層級持續複寫實體機、VM 與其他雲端上的伺服器，test launch 期間複寫不中斷、來源照常服務；cutover 時只需同步最後的差異，停機時間短。

> **C ✗** DataSync 搬的是檔案，不是可開機的作業系統；EC2 也無法從 EFS 上的檔案啟動成原本的伺服器。
>
> **D ✗** DMS 搬的是資料庫的資料，不處理作業系統、應用程式與設定。
>
> **考點**：SAA-3.2、SAA-2.2｜MGN 的持續複寫與測試

### 練習 45-2｜SAP｜單選｜複寫流量走私有網路

旅行社以 MGN 遷移 80 台伺服器。資安政策規定，所有遷移資料都不得經過 Internet，資料中心與 AWS 之間已有 Direct Connect，並以 Transit Gateway 連到遷移帳號的 VPC。安裝 agent 後，伺服器一直停在初始同步階段，複寫進度為零。網路團隊確認機房防火牆只開放了往 AWS 的 TCP 443。

應如何修正？

- A. 為 replication server 配置 Elastic IP，並在機房防火牆開放到這些 EIP 的 TCP 443
- B. 把 staging subnet 改為 public subnet，讓 replication server 透過 Internet Gateway 接收資料
- C. 在 replication settings 中選擇以 private IP 傳輸資料，並在機房防火牆與 staging subnet 的 security group、NACL 開放來源伺服器到 replication server 的 TCP 1500
- D. 把每台伺服器的 replication agent 改用 TCP 443 傳送資料，以符合現有的防火牆規則

> [!answer]- 答案：C
> **A ✗** 使用 EIP 代表資料走 public 位址，違反不經 Internet 的規定；而且資料複寫使用的是 TCP 1500，不是 443，開放 443 解決不了問題。
>
> **B ✗** 把 staging subnet 改成 public subnet 會讓複寫走 Internet，違反資安政策，也沒有處理 TCP 1500 被擋的問題。
>

>
> **D ✗** 資料複寫的 port 是固定的設計，不能改用 443 繞過防火牆規則；正確做法是依需求開放 1500。
>
> **考點**：SAP-1.1、SAP-4.2｜MGN 網路需求與 private IP 複寫

### 練習 45-3｜SAP｜單選｜Cutover 前的測試

最合適的做法是什麼？

- A. 對 30 台伺服器直接執行 cutover，若驗收失敗再 revert cutover

> **C ✗** 手動建立 AMI 繞過了 MGN 的轉換與 launch 設定，暫停複寫也會讓資料落後；在正式 subnet 測試還可能與正式系統衝突。
>
> **D ✗** 停止來源應用程式違反「來源必須繼續服務使用者」的要求；test launch 不需要停止來源。
>
> **考點**：SAP-4.2、SAP-2.1｜MGN test launch

> **E ✓** Launch settings 的 right-sizing 預設依來源規格挑選 instance type；關閉後在 EC2 launch template 指定較小的規格，test 與 cutover instance 就會依使用率資料啟動。
>
> **考點**：SAP-4.2、SAP-3.1｜MGN launch settings 與 post-launch actions

### 練習 45-6｜SAP｜單選｜異質資料庫遷移的分工

- A. 以 DMS Schema Conversion（或 AWS SCT）產生評估報告並轉換 schema 與 PL/SQL，在 Aurora 建立轉換後的物件，再以 DMS full load + CDC 搬資料

- C. 以 AWS Application Migration Service 複製 Oracle 主機到 EC2，再在 EC2 上安裝 PostgreSQL 並匯入資料

> **D ✗** Data Pump 是 Oracle 專用格式，PostgreSQL 的 `pg_restore` 無法讀取；而且這種一次性匯出匯入無法做到短停機。

### 練習 45-7｜SAP｜單選｜CDC 沒有擷取到變更

DMS task 以 full load + CDC 模式從地端 Oracle 遷移到 RDS for Oracle。Full load 順利完成，但進入 CDC 階段後，來源上新增與修改的訂單都沒有出現在目標，task 日誌顯示無法從交易日誌取得足夠的資訊來識別被修改的資料列。來源資料庫是 DBA 很久以前建立的。

最可能需要的修正是什麼？

- A. 把 replication instance 升級為更大的 instance class，提高 CDC 的處理能力
- B. 在目標 RDS 上啟用 Multi-AZ，確保 CDC 寫入有足夠的可用性
- C. 確認來源 Oracle 在 ARCHIVELOG 模式並啟用 supplemental logging，保留足夠的 archived log 後重新啟動 task
- D. 改用 limited LOB mode，減少 CDC 需要處理的資料量

> [!answer]- 答案：C
> **A ✗** 錯誤訊息指出的是交易日誌資訊不足，而不是效能不足；更大的 instance 無法讀到日誌中不存在的資訊。

>
> **C ✓** DMS 的 Oracle CDC 讀取 redo 與 archived redo log，前提是資料庫在 ARCHIVELOG 模式，且啟用 supplemental logging，讓日誌記錄足夠的欄位以識別被修改的資料列。老舊資料庫常未啟用這些設定。
>
> **D ✗** LOB mode 影響大型欄位的搬移方式，與 CDC 能否識別變更無關；任意改為 limited LOB mode 還可能截斷資料。
>
> **考點**：SAP-4.2｜DMS CDC 的來源前提

### 練習 45-8｜SAP｜選兩項｜遷移後的資料庫問題

團隊用 DMS 讓 DMS 自動建立目標資料表，把一套 PostgreSQL 資料庫從地端遷移到 Amazon RDS for PostgreSQL，validation 結果顯示所有資料列一致。切換後立刻出現兩個問題：應用程式新增訂單時出現主鍵重複的錯誤；以客戶編號查詢訂單的 API 從 50 毫秒變成 20 秒。

哪兩個步驟能解決這兩個問題？（選兩項）

- A. 依來源的目前值（加上安全間隔）重設目標資料庫中的 sequence
- B. 把 replication instance 改為 Multi-AZ，並重新執行 full load
- C. 在目標啟用 DMS data validation 並重新比對所有資料表
- D. 在目標建立來源上原有的 secondary index（例如客戶編號欄位的索引）
- E. 把 DMS task 的 LOB 設定改為 full LOB mode

> [!answer]- 答案：A、D
> **A ✓** DMS 搬的是資料列，不會同步 sequence 的目前值。目標的 sequence 從初始值開始產生編號，就會與已搬過來的主鍵衝突。切換時要依來源目前值重設。
>
> **B ✗** Multi-AZ 提供 replication instance 的可用性，與 sequence 及索引都無關；重新 full load 也不會建立 sequence 值或索引。
>
> **C ✗** Validation 已經證明資料列一致，問題不在資料本身，而在 DMS 不處理的 schema 物件。
>
> **D ✓** DMS 自動建表時只建立資料表與主鍵，不建 secondary index。沒有客戶編號的索引，查詢就變成全表掃描。應在目標補建原有索引（最好在 full load 後、CDC 前建立）。
>
> **E ✗** LOB mode 決定大型欄位的搬移方式，與主鍵衝突和查詢效能無關。
>
> **考點**：SAP-4.2、SAP-3.3｜DMS 不搬 sequence 與 secondary index

### 練習 45-9｜SAP｜單選｜向稽核證明資料一致

支付相關的帳務資料庫已用 DMS 從地端 SQL Server 遷移到 Amazon RDS for SQL Server，目前處於 CDC 持續同步狀態。PCI DSS 稽核要求在切換前提出證據，證明目標的每一筆資料都與來源一致，並在 CDC 期間持續確認新變更也一致。團隊希望用最少的自訂開發完成。

最合適的做法是什麼？

- A. 撰寫腳本每天比較兩邊每張資料表的資料筆數，並把結果存到 S3
- B. 啟用 DMS data validation，讓 DMS 逐列比較來源與目標並在 CDC 期間持續驗證，以 task 的驗證統計與控制表作為證據
- C. 在目標建立 read replica，讓稽核人員直接查詢比對
- D. 在切換當晚停止寫入，匯出兩邊所有資料表成 CSV 後以檔案雜湊值比對

>
> **B ✓** DMS data validation 會在 full load 後逐列比較資料，並在 CDC 期間持續驗證新變更，驗證結果與不一致的資料列都會被記錄，可直接作為稽核證據，不需要自訂開發。若資料已搬好，也可以建立 validation-only task。
>
> **C ✗** Read replica 只是目標的副本，讓人工查詢比對既不完整也無法規模化，不能證明「每一筆」資料一致。
>
> **D ✗** 在停機窗口內匯出並比對全部資料會大幅拉長停機時間；兩個不同系統匯出的 CSV 格式細節也可能不同，雜湊值比對不可靠。
>
> **考點**：SAP-4.2、SAP-2.3｜DMS data validation

### 練習 45-10｜SAP｜單選｜難以預估的 DMS 容量

一家公司要在三個月內把 40 個大小不一的 MySQL 與 PostgreSQL 資料庫遷移到 Aurora，每個資料庫的寫入量變化很大，月底結帳時可能是平時的十倍。遷移團隊只有兩位工程師，沒有經驗估算 replication instance 的規格，也不希望持續監控並手動調整 instance 大小。

- B. 所有資料庫共用一台 replication instance，並設定 CloudWatch 告警，在 CPU 過高時手動升級規格
- C. 改用 AWS Application Migration Service 複製所有資料庫主機，避免估算 DMS 容量
- D. 使用 DMS Serverless，為每個遷移設定最小與最大容量範圍，由 DMS 依負載自動配置與擴縮

> **B ✗** 共用一台 instance 會讓多個 task 互相搶資源，手動升級也需要持續監控與介入，正是團隊想避免的負擔。
>
> **C ✗** MGN 只能把資料庫主機複製到 EC2，無法把資料搬進 Aurora 受管服務。
>
> **D ✓** DMS Serverless 不需要挑選 instance 規格，只設定容量範圍，DMS 會依實際負載自動配置與擴縮，最適合負載變化大且團隊不想管理容量的情境。
>
> **考點**：SAP-4.2、SAP-3.1｜DMS Serverless

### 練習 45-11｜SAA｜單選｜檔案伺服器遷移到 FSx

一家公司要把三台地端 Windows 檔案伺服器（共 25 TB）遷移到 Amazon FSx for Windows File Server。使用者在遷移期間仍會持續修改檔案，切換後所有資料夾的 NTFS 權限都必須維持不變。公司希望先完成大部分資料的傳輸，切換當天只同步最後的變更，並且盡量減少自行開發的腳本。

最合適的做法是什麼？

- A. 在地端部署 AWS DataSync agent，建立從 SMB 共用資料夾到 FSx for Windows File Server 的 task 並保留 metadata，先完整傳輸再排程增量同步，切換當天執行最後一次同步
- B. 部署 Amazon S3 File Gateway，把檔案伺服器的資料複製到 gateway，再從 S3 匯入 FSx
- C. 以 AWS Application Migration Service 複製檔案伺服器到 EC2，再在 EC2 上設定 Windows 檔案共用
- D. 用 AWS DMS 把檔案伺服器的資料夾以 full load + CDC 同步到 FSx

> [!answer]- 答案：A
> **A ✓** DataSync 支援 SMB 來源到 FSx for Windows File Server，可保留 NTFS 權限與時間戳記等 metadata；首次完整傳輸後只傳有變更的檔案，切換當天執行最後一次增量同步即可，不需要自行開發腳本。
>
> **B ✗** S3 File Gateway 提供以檔案介面存取 S3 的 hybrid 存取方式，並不是把資料搬到 FSx 的工具；多繞一次 S3 也無法保留 NTFS 權限到 FSx。
>
> **C ✗** 這是 rehost 到 EC2 上的自管檔案伺服器，不是遷移到 FSx 受管服務；仍要自己管理 Windows Server 與磁碟。
>
> **D ✗** DMS 搬的是資料庫的資料表，不支援檔案共用資料夾。
>
> **考點**：SAA-3.1、SAA-3.5｜DataSync 遷移到 FSx for Windows File Server

### 練習 45-12｜SAA｜單選｜線上或離線傳輸

一家公司要把 120 TB 的影像封存資料從地端 NAS 搬到 Amazon S3，期限是 45 天。公司已有一條 1 Gbps 的 Direct Connect，扣除正式業務流量後，晚上與週末平均可以提供約 500 Mbps 給遷移使用。資料在遷移期間幾乎不會變更。

最合適的判斷與做法是什麼？

- A. 120 TB 一定要使用離線實體裝置寄送，線上傳輸不可能在 45 天內完成
- B. 先申請把 Direct Connect 升級到 10 Gbps，升級完成後再開始傳輸
- C. 以 500 Mbps 計算約需 22 天，在 45 天期限內且保有餘裕，使用 DataSync 經 Direct Connect 傳輸並設定頻寬限制
- D. 使用 S3 Transfer Acceleration 從 NAS 直接上傳，以加快傳輸速度

> [!answer]- 答案：C
> **A ✗** 沒有經過計算就假設要用離線傳輸。以可用頻寬計算，線上傳輸在期限內完成，不需要寄送裝置。
>
> **B ✗** 專線升級通常需要數週以上，而且現有頻寬已經足夠，升級只會增加成本與等待時間。
>
> **C ✓** 120 TB ＝ 9.6 × 10¹⁴ bit，除以 5 × 10⁸ bit／秒約 1,920,000 秒，約 22 天，即使實際吞吐量打折仍在 45 天內。DataSync 經 Direct Connect 傳輸，可以設定頻寬上限避免影響正式流量，並驗證傳輸結果。
>
> **D ✗** Transfer Acceleration 透過 edge location 改善遠距離的 Internet 上傳，對已有 Direct Connect 的情境沒有幫助，還會增加費用，也不會突破可用頻寬的限制。
>
> **考點**：SAA-3.5、SAA-4.4｜依頻寬計算選擇傳輸方式

### 練習 45-13｜SAP｜單選｜切換後仍能安全退回

Wanderly 將在週六晚上把訂房資料庫從地端 Oracle 切換到 Amazon RDS for Oracle。業務要求：切換後 5 天內若發現嚴重問題，必須能退回地端系統，而且不能遺失這 5 天內在新系統上產生的訂單。地端 Oracle 在這段期間會保持運作但不接受應用程式寫入。

最合適的做法是什麼？

- A. 切換前在 RDS 建立手動 snapshot，若需要退回就把 snapshot 還原到地端
- B. 切換完成、開放新寫入之前，建立以 RDS 為來源、地端 Oracle 為目標的反向 DMS CDC task，持續把新變更同步回地端
- C. 切換後立即 finalize 所有 MGN 來源伺服器，降低雙軌運行成本，若需退回再重新安裝地端系統
- D. 啟用 RDS 的 Multi-AZ 與自動備份，若發生問題就在 AWS 上 point-in-time restore

> [!answer]- 答案：B
> **A ✗** RDS snapshot 無法直接還原到地端 Oracle；而且切換前的 snapshot 不包含切換後 5 天的新訂單。
>
> **B ✓** 反向 CDC 讓新系統上的每一筆變更持續同步回地端。要退回時，只要停止新系統寫入、等反向 CDC 延遲歸零，再把應用程式切回地端即可，不遺失資料。必須在開放新寫入前建立，才能從第一筆新訂單開始同步。
>
> **C ✗** 立即 finalize 會讓 MGN 停止複寫並清除 staging 資源，失去伺服器層級的回頭路；重新安裝地端系統也無法帶回新訂單。
>
> **D ✗** Multi-AZ 與 point-in-time restore 保護的是 AWS 上的資料庫可用性與資料，並不能讓系統退回地端。
>
> **考點**：SAP-2.2、SAP-4.2｜反向複寫與 rollback 計畫

### 練習 45-14｜SAP｜單選｜縮短切換停機

旅行社的上一個 wave 在切換時出了問題：DMS 延遲早已歸零，資料庫也切換成功，但切換後兩個小時內，有一半的應用伺服器仍連到地端的舊資料庫。調查發現，應用程式以 DNS 名稱連資料庫，該 DNS 記錄的 TTL 是 4 小時，切換當晚才改成 60 秒並更新記錄。下一個 wave 要避免同樣的問題。

最合適的改善是什麼？

- A. 切換當晚更新 DNS 記錄後，重新啟動所有 DNS resolver
- B. 把應用程式改成直接使用資料庫的 IP 位址，跳過 DNS
- C. 切換當晚把 TTL 設為 0，強制所有用戶端立即重新查詢
- D. 在切換前至少一個舊 TTL 週期（例如提前數天）先把 TTL 降到 60 秒，切換時只需更新記錄，用戶端在一分鐘內就會取得新位址

> [!answer]- 答案：D
> **A ✗** 重新啟動 resolver 無法清除每台應用伺服器作業系統或執行環境的本地快取，而且影響範圍大，不是可靠的做法。
>
> **B ✗** 寫死 IP 正是第 44 章指出的隱藏相依問題：每次切換或 failover 都要修改應用程式，而且 RDS endpoint 的 IP 可能改變。
>
> **C ✗** 當晚才改 TTL 和上一次的錯誤相同：已經被快取的記錄仍會使用舊的 4 小時 TTL，直到過期才會重新查詢。
>
> **D ✓** 用戶端依照取得記錄時的 TTL 決定快取多久。提前把 TTL 降到 60 秒並等待舊 TTL 過期，切換當晚更新記錄後，用戶端在一分鐘內就會改連新位址。
>
> **考點**：SAP-4.2、SAP-2.1｜Cutover 前降低 DNS TTL

### 練習 45-15｜SAP｜選三項｜切換流量前的必要步驟

在週六的停機窗口中，團隊已把應用程式切到維護頁面，準備把訂房系統的資料庫連線從地端 Oracle 改到 RDS for Oracle。DMS task 是 full load + CDC，目標的 schema 由 Data Pump 預先建立，觸發程序在載入期間被停用。

在更新連線並開放使用者流量之前，哪三個步驟是必要的？（選三項）

- A. 確認來源已無應用程式與排程作業的寫入，並等待 `CDCLatencySource` 與 `CDCLatencyTarget` 歸零後停止 DMS task
- B. 在目標刪除所有資料表並重新執行 full load，確保資料是最新的
- C. 依來源目前值重設目標的 sequence，並重新啟用觸發程序與外鍵限制
- D. 對所有 MGN 來源伺服器執行 finalize cutover，以免來源與目標同時運作
- E. 把 DMS replication instance 改為 Multi-AZ，以提高切換當晚的可用性
- F. 建立以 RDS 為來源、地端 Oracle 為目標的反向 CDC task，作為 rollback 路徑

> [!answer]- 答案：A、C、F
> **A ✓** 只有在來源停止寫入、CDC 延遲歸零後，目標才擁有來源的全部資料。若有排程作業仍在寫入來源，切換後那些資料就會遺失。
>
> **B ✗** 重新 full load 會讓停機時間從分鐘變成數小時甚至數天，而且 CDC 已經讓目標保持最新，完全沒有必要。
>
> **C ✓** DMS 不同步 sequence 的目前值；載入期間停用的觸發程序與外鍵也必須在開放流量前恢復，否則新增資料會主鍵衝突、業務邏輯不會執行。
>
> **D ✗** Finalize 會移除 MGN 的回頭路，應該在 rollback 期限過後才執行，而不是切換當晚。
>
> **E ✗** 切換當晚 DMS task 即將停止，此時調整 replication instance 沒有意義；Multi-AZ 應在長時間複寫開始前就決定。
>
> **F ✓** 在開放新寫入之前建立反向 CDC，才能從第一筆新資料開始同步回地端，讓切換後的 rollback 不遺失資料。
>
> **考點**：SAP-4.2、SAP-2.2｜資料庫 cutover runbook

### 練習 45-16｜SAP｜單選｜大型主機現代化

Wanderly 計畫收購一家航空票務公司，對方的核心系統是在 IBM 大型主機上執行的 COBOL 與 CICS 應用程式，資料存在 DB2。熟悉 COBOL 的員工即將退休，公司希望遷移到 AWS 後，由現有的 Java 團隊接手維護，並盡量以自動化方式轉換程式碼，而不是人工重寫。

最合適的方向是什麼？

- A. 以 AWS Application Migration Service 把大型主機 rehost 到 EC2
- B. 採用 replatform 方式，保留 COBOL 原始碼並在 AWS 上相容的 COBOL 執行環境中執行
- C. 採用 automated refactor 路徑（例如 AWS Transform for mainframe，舊稱 AWS Blu Age），把 COBOL 程式自動轉換成 Java 應用程式，資料遷移到關聯式資料庫
- D. 由 Java 團隊依照現有系統的畫面與報表，從零開始人工重寫整個系統

> [!answer]- 答案：C

>
> **B ✗** Replatform 可以最少變更地離開大型主機，但保留的是 COBOL 原始碼，仍然需要 COBOL 技能維護，無法解決員工退休的問題。若題目重點是最少變更，這才是答案。
>
> **C ✓** 自動 refactor 把 COBOL 轉換成 Java，資料轉到關聯式資料庫，讓 Java 團隊可以接手維護，同時以自動化取代人工重寫，最符合題目的兩個要求。
>
> **D ✗** 從零人工重寫風險與成本最高、時間最長，也違反「盡量以自動化方式轉換」的要求。
>
> **考點**：SAP-4.2、SAP-4.4｜Mainframe 的 replatform 與 automated refactor
