## 41.1 故事：60 個帳號、兩個 Region、兩座資料中心

第 40 章的 landing zone 上線三個月後，Wanderly 已經有 60 個帳號，並且在東京之外開始使用新加坡 Region。網路團隊的白板上畫滿了線：早期的幾個 VPC 用 VPC peering 互連，旅行社的資料中心用兩條 Site-to-Site VPN 連到其中一個 VPC，每個 VPC 都有自己的 NAT Gateway，有些 VPC 還各自建了十幾個 interface endpoint。

網路負責人小魏列出了他必須解決的問題。第一，**安全**：PCI 稽核要求所有往 Internet 的流量與跨環境的流量都要經過可記錄、可阻擋的防火牆，但現在每個 VPC 都直接出去。第二，**隔離**：開發環境理論上不該能連到 production，但 peering 一層一層接下來，已經沒人能保證這件事。第三，**規模**：新帳號每週都在增加，每次都要手動建 peering、改 route table、建 NAT 和 endpoint。第四，**hybrid**：旅行社的 300 台 VM 要遷移，需要從 VPN 升級到 Direct Connect，而且兩個 Region 都要能連回地端；地端的 DNS 也要能解析 AWS 內部的名稱。

這些問題有一個共同的答案方向：**把共用的網路功能集中到 Network 帳號，由少數幾個中央 VPC 提供給所有 workload VPC 使用**。但「集中」不是免費的，每多一跳就多一次處理費、多一個可能故障的地方。這一章會一步步建出 Wanderly 的企業網路，並在每一步說清楚代價。

第 7 章介紹了 Transit Gateway 的基本元件，第 8 章介紹了 VPN、Direct Connect 與 Resolver endpoints。這一章不重講這些元件本身，而是把它們組合成企業級架構。

## 41.2 Hub-and-spoke：Transit Gateway 作為網路的中心

### 為什麼不再用 peering

VPC peering 不支援遞移路由，要讓 N 個 VPC 全部互通需要 N×(N−1)/2 條連線：60 個 VPC 就是 1,770 條。更大的問題是**管理與稽核**：每條 peering 兩端的 route table 都要手動維護，任何一個人加錯一條 route，prod 和 dev 就通了，而且很難從整體看出來。

**Hub-and-spoke（中心輻射）** 架構讓每個 workload VPC（spoke，輻條）只連到一個中心（hub）。在 AWS 上，這個中心就是 **Transit Gateway（TGW）**。所有路由決策集中在 TGW 的 route table 中，網路團隊只要看 TGW route table，就知道誰能連到誰。

### Wanderly 的 TGW 設計原則

1. **TGW 放在 Network 帳號，透過 AWS RAM 共享給整個 Organization。** Workload 帳號可以把自己的 VPC attach 到共享的 TGW，但無法修改 TGW 的 route table。路由權集中在網路團隊。
2. **關閉 default route table association 與 default route table propagation。** TGW 預設會把每個新 attachment 自動關聯並傳播到同一張預設 route table，等於「所有人都能互通」。企業環境要關掉這兩個選項，讓每個 attachment 由自動化流程明確決定它屬於哪個 segment。
3. **每個 spoke VPC 在每個 AZ 建立一個專用的小 subnet（例如 /28）放 TGW attachment。** TGW 會在這些 subnet 中建立 ENI。只有在 attachment 有 subnet 的 AZ，該 AZ 的資源才能經由 TGW 送出流量，所以每個有 workload 的 AZ 都要選。專用 subnet 讓它可以有自己的 route table 與寬鬆的 NACL，不和應用程式的規則互相干擾。
4. **新 attachment 需要接受（acceptance）。** 共享 TGW 時可以要求 Network 帳號接受 attachment 請求，搭配第 40 章的帳號 baseline 自動化，由流程依帳號所在 OU 自動接受並關聯到正確的 route table。

### 用 IPAM 讓路由可以彙總

第 5 章介紹過 IPAM 的 pool 階層。在企業網路中，IPAM 的規劃方式會直接影響 route table 的複雜度。Wanderly 讓位址階層和網路 segment 對齊：

| 範圍 | CIDR | 說明 |
|---|---|---|
| 東京 production | `10.16.0.0/13` | 所有東京 prod VPC 從這裡取得 CIDR（含 shared services `10.16.0.0/16`、production `10.20.0.0/16`、data `10.21.0.0/16`） |
| 東京 non-production | `10.24.0.0/13` | 東京 staging、dev VPC（例如 staging `10.24.0.0/16`、dev `10.25.0.0/16`） |
| 新加坡 production | `10.32.0.0/13` | |
| 新加坡 non-production | `10.40.0.0/13` | |
| 地端（台北辦公室、旅行社資料中心） | `10.0.0.0/16`、`172.16.0.0/16` | 既有，不能動 |

這樣規劃的好處是：TGW route table 中「往東京所有 dev VPC」只需要一條 `10.24.0.0/13`，地端的路由器也只需要接收幾條彙總路由。如果每個 VPC 的 CIDR 是隨機挑的，route table 就要一條一條列，還會碰到第 8 章提過的 Direct Connect 路由數量上限。這份表就是第 5 章位址規劃的延伸：東京整個 Region 是 `10.16.0.0/12`、新加坡是 `10.32.0.0/12`，再各自切成 production 與 non-production 兩個 /13。早期建立的 production、shared services、data VPC 原本就從東京 production 區塊取得位址，正好落在新的 pool 內，不需要重新編址，只要讓 IPAM 把它們的 CIDR 納入對應 pool 的已分配範圍即可。

## 41.3 Segmentation：用 TGW route table 切出路由網域

小魏的第二個問題是隔離。在 TGW 上，隔離靠的是 **route table 分開**。先複習第 7 章的兩個動作：

- **Association（關聯）**：決定「從這個 attachment 進來的流量查哪一張 TGW route table」。每個 attachment 只能關聯一張。
- **Propagation（傳播）**：決定「這個 attachment 的 CIDR 會被自動寫進哪幾張 route table」。可以傳播到多張。

一張 TGW route table 就是一個 **route domain（路由網域）**：關聯到同一張表的 attachment，看到的是同一份「世界地圖」。

### Wanderly 的 segment 設計

需求是：prod 與 dev 互不可達；兩者都能存取 shared services（AD、CI、監控）；兩者都能連回地端；所有往 Internet 的流量都要經過 inspection（41.5 節）。下表是第一階段的設計：東西向流量（VPC 之間、VPC 與地端之間）直接由 TGW 轉送，只有往 Internet 的流量經過 inspection。41.5 節會說明當東西向流量也要檢查時，這幾張表要怎麼改。

| TGW route table | 關聯的 attachment | 表中的 route | 結果 |
|---|---|---|---|
| `rt-prod` | 所有 prod VPC | shared VPC（propagation）、地端 DX（propagation）、`0.0.0.0/0 → inspection` | prod 看得到 shared、地端；看不到 dev |
| `rt-nonprod` | 所有 dev／staging VPC | shared VPC、地端 DX、`0.0.0.0/0 → inspection` | dev 看得到 shared、地端；看不到 prod |
| `rt-shared` | shared services VPC | prod VPC、nonprod VPC、地端（propagation） | shared 能回應所有人 |
| `rt-onprem` | DX Gateway attachment | prod、nonprod、shared（propagation） | 地端能連到所有 VPC |
| `rt-inspection` | inspection VPC | 所有 VPC 與地端（propagation） | 檢查完的流量能送回任何目的地 |

讀這張表時要抓住一個重點：**「A 能不能連到 B」要同時看兩個方向。** A 的 route table 要有 B 的 route，B 的 route table 也要有 A 的 route，回程才回得來。prod 和 dev 都能存取 shared，是因為 `rt-shared` 同時有 prod 與 nonprod 的 route；但 prod 的表沒有 dev 的 route，dev 的表也沒有 prod 的 route，兩者就互不可達，即使它們都能連到同一個 shared VPC。TGW 不會因為「A 能到 shared、shared 能到 B」就把 A 的流量轉給 B，每一跳都只依當下 attachment 關聯的那張表決定。

> [!warning] 常見誤解
> 「prod 與 dev 共用一張 TGW route table，再用 NACL 或 security group 擋住彼此。」這樣在路由層面兩者仍然互通，只是靠逐一設定的過濾規則維持隔離，任何一個 VPC 漏設就破功，稽核也很難證明。Segmentation 應該在**路由層**做：不同 route table、不互相 propagation。NACL 和 security group 是第二層防護，而不是第一層。

### 用 CloudFormation 描述 attachment 與關聯（節錄）

```yaml
Resources:
  BookingProdAttachment:
    Type: AWS::EC2::TransitGatewayVpcAttachment
    Properties:
      TransitGatewayId: tgw-0abc1234def567890
      VpcId: !Ref BookingProdVpc
      SubnetIds:
        - !Ref TgwSubnetA        # 每個 AZ 一個 /28 專用 subnet
        - !Ref TgwSubnetC
      Tags:
        - Key: segment
          Value: prod

  BookingProdAssociation:
    Type: AWS::EC2::TransitGatewayRouteTableAssociation
    Properties:
      TransitGatewayAttachmentId: !Ref BookingProdAttachment
      TransitGatewayRouteTableId: tgw-rtb-prod0000000000

  BookingProdToShared:
    Type: AWS::EC2::TransitGatewayRouteTablePropagation
    Properties:
      TransitGatewayAttachmentId: !Ref BookingProdAttachment
      TransitGatewayRouteTableId: tgw-rtb-shared000000000

  BookingProdToInspection:
    Type: AWS::EC2::TransitGatewayRouteTablePropagation
    Properties:
      TransitGatewayAttachmentId: !Ref BookingProdAttachment
      TransitGatewayRouteTableId: tgw-rtb-inspect00000000
```

注意 prod attachment **關聯**到 `rt-prod`，但**傳播**到 `rt-shared` 與 `rt-inspection`，而不傳播到 `rt-nonprod`。實務上，association 與 propagation 屬於 Network 帳號的 TGW，這段 template 由 Network 帳號的自動化部署，而 VPC attachment 本身可以由 workload 帳號建立。

## 41.4 集中 egress：一個出口，而不是六十個

### 為什麼要集中

每個 VPC 各自建 NAT Gateway（每 AZ 一台，第 5 章）有兩個問題。一是**成本**：60 個 VPC × 2 AZ = 120 台 NAT Gateway 的小時費，很多 VPC 的對外流量其實很少。二是**控制**：120 個出口代表 120 個需要監控與過濾的地方，PCI 要求的「往 Internet 的流量都要能記錄與阻擋」幾乎做不到。

**集中 egress（centralized egress）** 的做法是在 Network 帳號建立一個 **egress VPC**，裡面放 NAT Gateway（每 AZ 一台）和 Internet Gateway；所有 spoke VPC 不再有自己的 NAT 與 IGW，default route 都指向 TGW，由 TGW 送到 egress VPC 出去。

### 封包怎麼走

```text
 Spoke VPC（booking-dev 10.26.8.0/21）
┌─────────────────────────────┐
│ app 10.26.8.25              │
│  │ ① subnet RT: 0.0.0.0/0 → TGW
└──┼──────────────────────────┘
   ▼
[Transit Gateway]
   │ ② rt-nonprod: 0.0.0.0/0 → egress VPC attachment
   │    （另加 blackhole route 擋住其他 segment 的範圍，見下文）
   ▼
 Egress VPC（Network 帳號）
┌──────────────────────────────────────────────────────┐
│ TGW subnet（每 AZ）                                   │
│   ③ RT: 0.0.0.0/0 → 同 AZ 的 NAT Gateway               │
│        ▼                                              │
│ Public subnet（每 AZ）：NAT Gateway（EIP）               │
│   ④ RT: 0.0.0.0/0 → IGW；10.0.0.0/8 → TGW（回程）        │
│        ▼                                              │
│ [Internet Gateway] ──► Internet                       │
└──────────────────────────────────────────────────────┘
```

逐步解說：

1. Spoke VPC 的所有 subnet 只有 local route 與 `0.0.0.0/0 → TGW`。它沒有 IGW，也沒有 NAT。
2. TGW 依 spoke attachment 關聯的 route table，把 default route 指向 egress VPC 的 attachment。這條 `0.0.0.0/0` 是**static route**，因為 egress VPC 的 CIDR 傳播進來只會是它自己的範圍，不會產生 default route。
3. 流量進入 egress VPC 的 TGW subnet 後，依該 subnet 的 route table 送往**同一個 AZ 的 NAT Gateway**。
4. NAT Gateway 轉換位址後經 IGW 出去；回程封包回到 NAT Gateway 後，public subnet 的 route table 用 `10.0.0.0/8 → TGW` 把它送回 TGW，再由 TGW 依 egress VPC attachment 關聯的表送回原本的 spoke。

### 一個容易漏掉的洞：經由 egress VPC 的 spoke 互通

假設 egress VPC 的 public subnet 有 `10.0.0.0/8 → TGW`，而 egress VPC attachment 關聯的 TGW route table 有所有 spoke 的 route（回程需要）。這時如果 dev VPC 送一個目的地是 prod VPC（`10.16.x.x`）的封包會怎麼樣？`rt-nonprod` 裡沒有 prod 的 route，只有 `0.0.0.0/0 → egress`，於是封包被送進 egress VPC；egress VPC 的 route table 又把 `10.0.0.0/8` 送回 TGW；TGW 再依 egress attachment 的表把它送到 prod。**Default route 繞了一圈，把 segmentation 打穿了。**

修正方式是在 spoke 的 TGW route table 加上 **blackhole route（黑洞路由）**：例如在 `rt-nonprod` 加入 `10.16.0.0/13 → blackhole`、`10.32.0.0/13 → blackhole`。依 longest prefix match，往 prod 範圍的封包會命中更精確的 blackhole route 被丟棄，而不是落到 `0.0.0.0/0`。Shared services VPC（`10.16.0.0/16`）雖然位在東京 production 區塊內，但 `rt-nonprod` 裡指向它的 `/16` route 比 `/13` 的 blackhole 更精確，所以 dev 仍然到得了 shared services。這也是 41.2 節要求 IPAM 位址可彙總的原因之一：彙總後只需要少數幾條 blackhole route。

### 集中 egress 的成本取捨

集中 egress 減少了 NAT Gateway 的數量與小時費，但**每 GB 流量多了一次 TGW 資料處理費**，NAT Gateway 的處理費仍然存在。對大多數「很多 VPC、每個 VPC 對外流量不大」的企業環境，集中的總成本較低、控制也更好；但對單一個每天往 Internet 傳數 TB 的 VPC，多出來的 TGW 處理費可能高於省下的 NAT 小時費，讓這個 VPC 保留自己的 NAT Gateway 反而划算。另外別忘了第 6 章的原則：往 S3 與 DynamoDB 的大量流量應該在 spoke VPC 內走 gateway endpoint，根本不必經過 TGW 和 NAT。

## 41.5 集中 inspection：讓流量先經過防火牆

集中 egress 解決了「出口太多」，但還沒解決「出口沒有檢查」。PCI 要求阻擋到未核准網域的連線、記錄所有對外連線，還要檢查 prod 與地端之間的流量。這需要 **inspection（流量檢查）**：讓流量先經過有狀態的防火牆再往目的地。

### 兩種防火牆選擇

**AWS Network Firewall** 是受管的 stateful 防火牆（第 16 章），支援 stateless 與 stateful rule groups、Suricata 相容規則、依 TLS SNI 或 HTTP Host 的網域允許清單，以及 TLS inspection。部署時在每個 AZ 的專用 subnet 建立一個 **firewall endpoint**，route table 以這個 endpoint（`vpce-` 開頭）作為 target。

**Gateway Load Balancer（GWLB）** 則讓你使用第三方防火牆 appliance（第 10 章）。GWLB 用 GENEVE 協定（UDP 6081）把原始封包封裝後送到後端 appliance fleet，appliance 檢查完再送回；在 route table 中以 **GWLB endpoint** 作為 target。當公司已有特定廠商防火牆的規則、授權與維運團隊，或需要該廠商特有的功能時選它。

### Inspection VPC 的封包路徑

Wanderly 選擇 Network Firewall，並把 inspection 與 egress 放在同一個 VPC（Network 帳號），讓東西向（VPC 之間、VPC 與地端之間）與南北向（往 Internet）流量都經過檢查。

```text
 Spoke A（prod，AZ-a）                          Spoke B（shared，AZ-c）
      │ ①                                              ▲
      ▼                                                │ ⑥
 [Transit Gateway] ── rt-prod：0.0.0.0/0 → inspection ──┘（rt-inspection：propagation）
      │ ②                                              ▲
      ▼                                                │ ⑤
 Inspection VPC（appliance mode 已啟用）                 │
┌─────────────────────────────────────────────────────┴───────┐
│ AZ-a                                  AZ-c                   │
│ TGW subnet-a                          TGW subnet-c           │
│  RT: 0.0.0.0/0 → fw-endpoint-a         RT: 0.0.0.0/0 → fw-endpoint-c
│        │ ③                                                   │
│        ▼                                                     │
│ Firewall subnet-a：[Network Firewall endpoint-a]               │
│  RT: 10.0.0.0/8 → TGW  ④（東西向回 TGW）                         │
│      0.0.0.0/0 → NAT-a ⑦（南北向）                               │
│        ▼                                                     │
│ Public subnet-a：[NAT-a] → [IGW]                               │
│  RT: 10.0.0.0/8 → fw-endpoint-a（回程先過防火牆）                  │
└──────────────────────────────────────────────────────────────┘
```

逐步解說東西向流量（Spoke A → Spoke B）：

1. Spoke A 的封包經 subnet route table 送到 TGW。
2. `rt-prod` 沒有 Spoke B 的明確 route，命中 `0.0.0.0/0 → inspection VPC attachment`。（這和 41.3 節第一階段的表不同：Wanderly 的 PCI 範圍要求東西向也要檢查，所以拿掉了 `rt-prod` 中 shared 的 route，下文說明完整的改法。）
3. 封包從 inspection VPC 的 TGW subnet 進來，依該 subnet 的 route table 送往**同 AZ** 的 firewall endpoint。
4. 防火牆放行後，firewall subnet 的 route table 用 `10.0.0.0/8 → TGW` 把封包送回 TGW。（旅行社資料中心使用 `172.16.0.0/16`，所以 firewall subnet 與 public subnet 的 route table 也要各加一條 `172.16.0.0/16`，目標與 `10.0.0.0/8` 相同；否則往這個地端範圍的封包會落到 `0.0.0.0/0`，被送往 NAT。）
5. 這次封包是從 inspection attachment 進入 TGW，查的是 `rt-inspection`，裡面有所有 spoke 的 route。
6. 封包抵達 Spoke B。回程時 Spoke B 的封包同樣先經過 inspection VPC，再回到 Spoke A。

南北向流量（往 Internet）在第 4 步之後改走 ⑦：firewall subnet 的 `0.0.0.0/0 → NAT`，再經 IGW 出去；回程封包到 NAT 所在的 public subnet 後，`10.0.0.0/8 → fw-endpoint` 讓它**先回到防火牆**，再送回 TGW。

### 東西向也要檢查時，TGW route table 要跟著改

41.3 節的第一階段設計中，`rt-prod` 直接有 shared 與地端的 route，`rt-shared` 也直接有 prod 的 route。如果只拿掉 `rt-prod` 的 shared route、卻保留 `rt-shared` 的 prod route，就會變成「去程經過防火牆、回程直接走 TGW」：防火牆只看到一半的連線，stateful 規則會把後續封包當成不明流量丟棄。**要檢查的路徑，去回兩個方向都必須導向 inspection。**做法是讓 spoke 的 CIDR 只傳播到 `rt-inspection`：

| TGW route table | 東西向也檢查時的內容 |
|---|---|
| `rt-prod` | `0.0.0.0/0 → inspection`，加上往 nonprod 範圍的 blackhole（41.4 節） |
| `rt-nonprod` | `0.0.0.0/0 → inspection`，加上往 prod 範圍的 blackhole |
| `rt-shared` | `0.0.0.0/0 → inspection`；不再接收 prod、nonprod 的 propagation |
| `rt-onprem` | 往各 AWS 彙總範圍（例如 `10.16.0.0/12`）的 static route 指向 inspection attachment；不再接收 VPC 的 propagation |
| `rt-inspection` | 接收所有 VPC 與地端的 propagation，檢查完的流量從這裡送往真正的目的地 |

prod 與 dev 的隔離仍然在路由層完成：blackhole route 讓 dev 往 prod 的封包在 TGW 就被丟棄，不會進到防火牆再靠規則擋。若某條高流量路徑確定不需要檢查，可以讓它保留直接 propagation，但同樣要兩個方向一起保留。

### Appliance mode：為什麼回程一定要走同一個 AZ

上圖有一個關鍵細節：Spoke A 在 AZ-a，Spoke B 在 AZ-c。TGW 預設會讓流量盡量**留在來源的 AZ**：從 AZ-a 進入 TGW 的封包，會從 inspection VPC 在 AZ-a 的 attachment ENI 送出。所以去程進入 AZ-a 的防火牆；但 Spoke B 的回程封包是從 AZ-c 進入 TGW，預設會被送到 AZ-c 的防火牆。

Stateful 防火牆依賴「看過去程才會放行回程」。AZ-c 的防火牆沒看過這條連線的去程，就會把回程當成不明流量丟棄，結果是連線時好時壞、跨 AZ 的流量全部失敗，這是 inspection 架構最經典的故障。

**Appliance mode** 是 TGW VPC attachment 的一個選項，在 **inspection VPC 的 attachment** 上啟用後，TGW 會依連線的來源與目的位址等資訊雜湊選擇一個 AZ，讓**同一條連線的去程與回程都經過同一個 AZ 的 appliance**，維持流量對稱。在 CloudFormation 中，它是 `AWS::EC2::TransitGatewayVpcAttachment` 的 `Options: ApplianceModeSupport: enable`。

> [!tip] 考試提示
> 題目描述「集中防火牆後，同 AZ 的流量正常、跨 AZ 的流量間歇失敗或被重設」→ 在 **inspection VPC 的 TGW attachment 啟用 appliance mode**。只在 spoke attachment 上啟用沒有用；同時要確認 inspection VPC 內每個 AZ 的 TGW subnet 都指向同 AZ 的 firewall endpoint。

### Inspection 的其他部署選擇

- **Network Firewall 與 TGW 的原生整合**：Network Firewall 現在可以直接以 **transit gateway-attached firewall**（一種 TGW attachment）掛上 Transit Gateway，Network Firewall 會替你處理底層的 endpoint 與網路設定，省去自己建立與維護 inspection VPC 和其中的 route table；TGW route table 只要把要檢查的流量指向這個 firewall attachment。多數既有架構與考題仍以「inspection VPC + appliance mode」為標準答案，看到時知道兩者都能達成集中檢查即可。
- **分散式 inspection（distributed）**：在每個需要檢查的 VPC 內各自部署 firewall endpoint。適合入站流量的檢查：Internet → IGW → firewall endpoint → ALB，搭配 IGW 的 **ingress routing**（把 route table 關聯到 IGW，讓進入 VPC 的流量先導向防火牆）。成本較高，但不經過 TGW、延遲最低，故障也只影響單一 VPC。
- **DNS 層過濾**：**Route 53 Resolver DNS Firewall** 可以在名稱解析階段阻擋惡意或未核准的網域，成本低、部署簡單，可以和 Network Firewall 疊加使用。但它只看 DNS 查詢，攻擊者直接連 IP 就繞過了，不能取代網路層的檢查。

### 入站流量為什麼通常不集中

集中 egress 與 inspection 很常見，但**集中 ingress（所有 Internet 入站都經由一個中央 VPC）** 在 AWS 上較少採用。入站流量通常由各 workload 帳號自己的 CloudFront、ALB 與 WAF 處理（第 10、11、16 章），每個應用團隊管理自己的入口，故障與變更不互相影響。只有在法規明確要求「所有入站都要經過同一套第三方防火牆」時，才會建立 ingress VPC 搭配 GWLB。

## 41.6 集中 VPC endpoints 與 private hosted zone 共享

第 6 章說過，interface VPC endpoint 每個 AZ 都要收小時費。Wanderly 的 60 個 VPC 平均各需要 SSM、Secrets Manager、KMS、ECR、CloudWatch Logs 等 10 個 endpoint、2 個 AZ，就是 1,200 個 endpoint ENI 的小時費。對流量不大的 VPC，這是一筆可觀而浪費的支出。

### 集中 endpoint 的架構

在 Network 帳號建立一個 **shared endpoints VPC**，只在這裡建立 interface endpoints；spoke VPC 經由 TGW 連到這些 endpoint。問題在 DNS：interface endpoint 的 private DNS 只會在**它所在的 VPC** 生效，spoke VPC 解析 `secretsmanager.ap-northeast-1.amazonaws.com` 時仍會得到 public IP。

解決步驟：

1. 在 shared endpoints VPC 建立 endpoint 時**關閉 private DNS**。
2. 為每個服務建立一個 **private hosted zone（PHZ）**，名稱就是服務的完整網域，例如 `secretsmanager.ap-northeast-1.amazonaws.com`，在 zone apex 建立 alias record 指向 endpoint 的 Regional DNS 名稱。
3. 把這些 PHZ **關聯到所有 spoke VPC**。PHZ 與 spoke VPC 在不同帳號時，需要 PHZ owner 先建立授權，再由 VPC 所在帳號完成關聯：

```bash
# 在 Network 帳號（PHZ owner）執行：授權 booking-prod 帳號的 VPC 關聯
aws route53 create-vpc-association-authorization \
  --hosted-zone-id Z0123456789ABCDEFGHIJ \
  --vpc VPCRegion=ap-northeast-1,VPCId=vpc-0bookingprod0001

# 在 booking-prod 帳號執行：完成關聯
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id Z0123456789ABCDEFGHIJ \
  --vpc VPCRegion=ap-northeast-1,VPCId=vpc-0bookingprod0001
```

逐一授權在帳號很多時很繁瑣。**Route 53 Profiles** 提供更好的做法：在 Network 帳號建立一個 profile，把 PHZ、Resolver forwarding rules、DNS Firewall rule groups 等 DNS 設定放進去，透過 AWS RAM 共享，各帳號只要把 profile 關聯到自己的 VPC，就一次取得全部 DNS 設定，之後中央新增的 PHZ 也會自動生效。

### 集中 endpoint 的限制與取捨

- **Gateway endpoint 不能集中。** S3 與 DynamoDB 的 gateway endpoint 是 route table 中的 prefix list route，只對它所在的 VPC 有效，**無法經由 TGW、peering 或 VPN 從其他網路使用**。每個 spoke VPC 應各自建立 gateway endpoint，它本身免費。若地端需要私有存取 S3，則要使用 S3 的 interface endpoint。
- **每 GB 多了 TGW 處理費。** 集中後省下 endpoint 小時費，但流量要經過 TGW。對資料量極大的服務（例如大量拉取映像檔的 ECR），在該 VPC 保留本地 endpoint 可能更划算。
- **Endpoint policy 變成共用的。** 集中的 endpoint policy 會套用到所有使用它的 VPC；需要「只有 prod 能存取 prod 的 bucket」這類差異化控制時，要在 policy 中使用 `aws:PrincipalOrgPaths` 等條件，或為不同 segment 建立不同的 endpoint VPC。
- **Security group 要允許所有 spoke CIDR。** 集中 endpoint 的 security group 要允許來自各 spoke 範圍的 443，這也是 41.2 節彙總位址的另一個好處。

## 41.7 Shared VPC：另一種「少一點 VPC」的思路

前幾節的集中化，都是「每個帳號有自己的 VPC，再把共用功能集中到中央 VPC」。**VPC sharing（共享 VPC）** 走的是另一條路：讓多個帳號直接**共用同一個 VPC**。第 5 章介紹過它的基本概念：Network 帳號（owner）建立 VPC 與 subnet，透過 AWS RAM 把 subnet 共享給同一 Organization 的其他帳號（participant），participant 在共享 subnet 中建立自己的 EC2、RDS、Lambda 等資源，但不能修改 owner 的 VPC、subnet、route table 與 NACL。

### 什麼時候選 shared VPC

Wanderly 有 30 個小型內部工具帳號，都屬於 NonProd、資料分類相同、流量很小。如果每個帳號一個 VPC，就有 30 個 TGW attachment 的小時費、30 組 TGW subnet、30 次 IPAM 配置。改成一個 `nonprod-shared` VPC 共享給這 30 個帳號：

- **TGW attachment 從 30 個降到 1 個**，attachment 小時費與 route table 規模同時下降。
- **同一 VPC 內的流量走 local route**，不經過 TGW，沒有 TGW 處理費（跨 AZ 仍有一般資料傳輸費）。
- 網路團隊集中管理路由與出口，應用團隊只管自己的資源。

### Shared VPC 的界線

- **只在同一個信任等級內共享。** Prod 與 NonProd 不應共用同一個 VPC，因為同一 VPC 內的資源在路由上互通（local route），隔離只剩 security group。Wanderly 的做法是每個 segment 一個 shared VPC：`prod-shared`、`nonprod-shared`，PCI 帳號則完全不使用 shared VPC。
- **帳號邊界仍然存在。** Participant 看不到也改不了其他 participant 的資源；每個帳號的 IAM、配額、帳單仍然獨立。
- **共享範圍限於同一個 Organization。** Subnet 只能共享給同一 Organization 內的帳號或 OU。
- **費用歸屬要另外處理。** 共用網路元件（例如 NAT Gateway、TGW attachment）的費用主要落在 owner 帳號，需要用第 43 章的成本分攤機制分配回各團隊。
- **Subnet 的 IP 是共用資源。** 一個 participant 大量建立 ENI，可能吃光其他 participant 也在使用的 subnet 位址，規劃 subnet 大小時要預留空間。

### Shared VPC 與 TGW-per-VPC 怎麼選

| 比較 | 每帳號一個 VPC + TGW | Shared VPC |
|---|---|---|
| 隔離 | 路由層隔離，可放不同 segment | 同 VPC 內路由互通，只靠 SG 隔離 |
| 成本 | 每個 VPC 一個 attachment，VPC 間流量有 TGW 處理費 | Attachment 少，VPC 內流量無 TGW 費 |
| 自主性 | 應用團隊可管理自己的路由（若授權） | 路由完全由網路團隊管理 |
| 適合 | 不同信任等級、需要獨立網路設定、受管制 workload | 同信任等級、大量小型帳號、團隊不需管網路 |

實務上兩者常常併用：一部分帳號使用 segment 層級的 shared VPC，另一部分（例如 PCI、需要特殊網路設定的系統）擁有自己的 VPC，而所有 VPC 都接到同一個 TGW。

## 41.8 大規模 hybrid：Direct Connect Gateway 與 Transit Gateway

旅行社的遷移需要穩定、高頻寬的地端連線。第 8 章介紹了 Direct Connect 的基本元件與高可用建議；這裡要回答的是企業級問題：**一組 DX 連線，怎麼同時服務兩個 Region、60 個帳號的 VPC？**

### 架構

```text
 台北資料中心（10.0.0.0/16）    旅行社資料中心（172.16.0.0/16）
        │ 客戶路由器                    │
        └──────────┬───────────────────┘
                   │ ① 兩個 DX location、各一條 dedicated connection（第 8 章）
                   ▼
           [Transit VIF] × 2
                   │
                   ▼
     [Direct Connect Gateway]（global 資源，Network 帳號）
          │ ② association + allowed prefixes
   ┌──────┴─────────────────────────┐
   ▼                                ▼
 [TGW 東京]  ◄── ④ TGW peering ──►  [TGW 新加坡]
   │ ③ rt-onprem 等 route table        │
   ▼                                ▼
 東京各 VPC                         新加坡各 VPC
```

逐步解說：

1. 地端透過兩個 Direct Connect location 的連線建立 **transit VIF（transit virtual interface）**。只有 transit VIF 能連到 Transit Gateway；private VIF 只能連到 virtual private gateway 或 DX Gateway 後的 VGW。
2. Transit VIF 連到 **Direct Connect Gateway（DXGW）**。DXGW 是 global 資源，可以和**多個 Region 的 TGW** 建立 association。每個 association 都有一份 **allowed prefixes** 清單，決定 DXGW 會把哪些 AWS 端的 CIDR 透過 BGP 宣告給地端。這裡正好用上 IPAM 彙總：東京只宣告 `10.16.0.0/12`，新加坡只宣告 `10.32.0.0/12`。
3. DXGW 的 attachment 關聯到 TGW 的 `rt-onprem`，地端學到的路由則依 41.3 節的設計傳播到 `rt-prod`、`rt-nonprod` 與 `rt-shared`。
4. 東京與新加坡的 TGW 之間用 **TGW peering** 互通（41.10 節）。

> [!warning] 常見誤解
> 「兩個 TGW 都接到同一個 DXGW，所以東京和新加坡的 VPC 可以經由 DXGW 互通。」不行。DXGW 不會在它所關聯的兩個 TGW（或 VGW）之間轉送流量，它只負責地端與 AWS 之間。Region 之間的互通要用 TGW peering 或 Cloud WAN。

### 加密與 SD-WAN

Direct Connect 本身不加密。PCI 要求傳輸中的持卡人資料必須加密時，有兩個選擇：在支援的 dedicated connection 上啟用 **MACsec**（第 8 章，L2 加密），或在 DX 之上建立 **private IP VPN**：Site-to-Site VPN 直接以 TGW 為終點，tunnel 走在 DX 的 transit VIF 上，不經過 Internet。

若公司已導入 SD-WAN 設備，可以使用 **TGW Connect attachment**：SD-WAN appliance 以 GRE tunnel 加上 BGP 和 TGW 交換路由，tunnel 跑在既有的 VPC 或 DX attachment 之上，讓 SD-WAN 的動態路由直接延伸到 AWS。

### 高可用的提醒

DXGW 與 TGW 都是 AWS 管理的高可用元件，真正的單點通常在**實體連線與客戶路由器**。第 8 章的 resiliency 建議在這裡同樣適用：關鍵 workload 至少兩個 DX location；成本受限時用 Site-to-Site VPN 作為 DX 的備援路徑，並以 BGP 屬性讓 DX 優先。遷移期間，旅行社資料中心原有的 VPN 不要急著拆，正好可以成為備援。

## 41.9 大規模 hybrid DNS

網路通了，名稱解析也要通。第 8 章介紹了 Route 53 Resolver 的 inbound endpoint（地端查 AWS）、outbound endpoint 與 forwarding rule（AWS 查地端）。在 60 個帳號的規模下，關鍵是**不要每個 VPC 各建一組 endpoint**，而是集中在一個 DNS VPC。

### 集中 DNS 架構

```text
                地端 DNS（AD DNS：corp.wanderly.local）
                 │ ▲
   ① conditional │ │ ④ 查詢 corp.wanderly.local
     forwarder： │ │
 aws.wanderly.internal
                 ▼ │
 DNS VPC（Network 帳號，經 TGW 與 DX 連回地端）
┌──────────────────────────────────────────────────┐
│ [Inbound endpoint]（2 AZ）                        │
│    ② 以 Route 53 Resolver 回答：已關聯到此 VPC 的 PHZ │
│ [Outbound endpoint]（2 AZ）                       │
│    ③ Forwarding rule：corp.wanderly.local → 地端 DNS │
└──────────────────────────────────────────────────┘
        │ RAM 共享 rule（或 Route 53 Profile）
        ▼
 各 spoke VPC：關聯共享的 rule；
              自己的 PHZ（如 booking.aws.wanderly.internal）也關聯到 DNS VPC
```

逐步解說：

1. 地端 DNS 伺服器為 AWS 使用的網域（`aws.wanderly.internal`）設定 conditional forwarder，指向 DNS VPC 中 inbound endpoint 的 IP。
2. Inbound endpoint 收到查詢後，由 DNS VPC 的 Resolver 回答。Resolver 只能回答**已關聯到 DNS VPC** 的 PHZ，所以每個帳號的 PHZ 除了關聯到自己的 VPC，**也要關聯到 DNS VPC**，否則地端查不到。這一步最常被漏掉。
3. AWS 端要查地端網域時，由 outbound endpoint 依 forwarding rule 把查詢送到地端 DNS。這條 rule 建立在 Network 帳號，**透過 AWS RAM 共享給整個 Organization**，各帳號把 rule 關聯到自己的 VPC 即可。Spoke VPC 不需要自己的 outbound endpoint：查詢由 Resolver 經 Network 帳號的 outbound endpoint 送出。Rule 與 outbound endpoint 必須在同一個 Region，所以東京與新加坡各有一個 DNS VPC。
4. 地端 DNS 回答 `corp.wanderly.local` 的查詢。

### 規模化的細節

- **Route 53 Profiles** 把 PHZ、forwarding rules 與 DNS Firewall 設定打包共享，對新帳號特別方便：baseline 自動化只要把 profile 關聯到新 VPC（第 40 章）。
- **避免轉送迴圈（forwarding loop）。** 如果 AWS 端有一條 rule 把 `aws.wanderly.internal` 轉到地端，而地端又把它轉回 inbound endpoint，查詢會在兩邊來回直到逾時。AWS 擁有的網域不應出現在 AWS 端的 forwarding rule 中。
- **Resolver endpoint 也有容量。** 每個 endpoint ENI 有每秒查詢數上限，大量查詢時要在多個 AZ 增加 ENI，並監控 CloudWatch 指標。
- **記錄查詢。** Resolver query logging 可以記錄 VPC 內的 DNS 查詢，送到第 40 章的 Log Archive，對事件調查很有價值。

## 41.10 多 Region：TGW peering 或 Cloud WAN

### TGW peering

Transit Gateway 是 Regional 資源。東京與新加坡各有一個 TGW，兩者以 **TGW peering attachment** 連接（同一 Region 內的兩個 TGW 也可以 peering）。流量走 AWS 骨幹網路並加密。

TGW peering 有一個考試很愛考的限制：**peering attachment 不支援 route propagation**。東京的 TGW route table 要能到新加坡的 VPC，必須手動加 **static route**，例如在東京的 `rt-prod` 加入 `10.32.0.0/13 → peering attachment`，新加坡那邊也要加回程。Segment 越多、Region 越多，要維護的 static route 就越多，這正是 IPAM 彙總再一次發揮作用的地方。兩個 TGW 建議使用不同的 BGP ASN。

### AWS Cloud WAN

當 Region 數量增加到 4、5 個以上，每個 Region 一個 TGW、兩兩 peering、每張表手動維護 static route 的方式會越來越難管理。**AWS Cloud WAN** 是 AWS 管理的全球廣域網路服務：

- 你用一份 JSON 格式的 **core network policy** 描述整個全球網路：在哪些 Region 有 **core network edge（CNE）**、有哪些 **segment**（例如 prod、nonprod、shared），以及 segment 之間怎麼共享路由。
- VPC、VPN、Connect（SD-WAN）與 TGW route table 都可以 attach 到 Cloud WAN；**attachment policy** 可以依 attachment 的 tag 自動把它放進正確的 segment。
- 同一個 segment 內，各 Region 的 edge 之間**自動交換路由**，不需要手動維護跨 Region 的 static route。
- 可以用 segment actions 讓特定流量先送到 inspection VPC 再到目的地。

```json
{
  "version": "2021.12",
  "core-network-configuration": {
    "asn-ranges": ["64512-64555"],
    "edge-locations": [
      { "location": "ap-northeast-1" },
      { "location": "ap-southeast-1" }
    ]
  },
  "segments": [
    { "name": "prod", "require-attachment-acceptance": true },
    { "name": "nonprod", "require-attachment-acceptance": false },
    { "name": "shared", "require-attachment-acceptance": true }
  ],
  "segment-actions": [
    {
      "action": "share",
      "mode": "attachment-route",
      "segment": "shared",
      "share-with": ["prod", "nonprod"]
    }
  ],
  "attachment-policies": [
    {
      "rule-number": 100,
      "conditions": [
        { "type": "tag-value", "operator": "equals", "key": "segment", "value": "prod" }
      ],
      "action": { "association-method": "constant", "segment": "prod" }
    },
    {
      "rule-number": 200,
      "conditions": [
        { "type": "tag-value", "operator": "equals", "key": "segment", "value": "nonprod" }
      ],
      "action": { "association-method": "constant", "segment": "nonprod" }
    }
  ]
}
```

讀這份 policy：網路在東京與新加坡各有一個 edge；有三個 segment；shared 的路由共享給 prod 與 nonprod（但 prod 與 nonprod 彼此不共享，所以互不可達）；帶 `segment=prod` tag 的 attachment 自動進入 prod segment，並需要網路團隊接受。和 41.3 節的五張 TGW route table 比較，同樣的意圖在 Cloud WAN 裡是**宣告式**的，而且自動跨 Region 生效。

| 比較 | TGW + peering | Cloud WAN |
|---|---|---|
| 範圍 | Regional，Region 間手動 peering | 全球，單一 policy |
| 跨 Region 路由 | Static route，手動維護 | Segment 內自動交換 |
| Segmentation | 每個 TGW 各自的 route table | Policy 中的 segment，全球一致 |
| 適合 | 1–3 個 Region、已有 TGW 投資 | 多 Region、多分支據點、希望集中宣告式管理 |
| 遷移 | — | 可與既有 TGW peering，逐步遷入 |

Wanderly 目前只有兩個 Region，TGW peering 足夠；但第 42 章規劃的全球化會加入更多 Region，屆時 Cloud WAN 會是合理的下一步。

## 41.11 成本與效能取捨

集中化的每一個設計都在用「多一跳的處理費與延遲」換「更少的元件與更好的控制」。把本章的取捨整理成一張表：

| 設計 | 省下什麼 | 多付什麼 | 什麼時候不划算 |
|---|---|---|---|
| 集中 egress | NAT Gateway 數量與小時費、管理負擔 | 每 GB 的 TGW 處理費 | 單一 VPC 對外流量極大 |
| 集中 inspection | 防火牆數量、規則一致 | Network Firewall endpoint 小時費與每 GB 處理費、TGW 處理費、多一跳延遲 | 不需要檢查的高流量路徑（可設計直接 route 繞過） |
| 集中 interface endpoints | Endpoint 的 AZ 小時費 | TGW 處理費；endpoint policy 較難差異化 | 單一服務流量很大（例如 ECR 大量 pull） |
| Shared VPC | TGW attachment 數量、VPC 內流量無 TGW 費 | 隔離降到 security group 層級 | 不同信任等級的 workload |
| Gateway endpoint（每個 VPC） | NAT 與 TGW 處理費 | 無（免費） | 幾乎沒有不划算的情況 |
| Cloud WAN | 多 Region 的人工路由維護 | Core network edge 與 attachment 費用 | 只有 1–2 個 Region |

效能方面要注意三點：

1. **AZ 對齊。** 每一段 route 都要指向同 AZ 的 NAT、firewall endpoint 或 interface endpoint，否則除了跨 AZ 傳輸費，一個 AZ 故障也會擴散。Appliance mode 會讓部分流量為了對稱而跨 AZ，這是為正確性付出的代價。
2. **MTU。** TGW 在 VPC、Direct Connect 與 peering 之間支援最大 8,500 bytes 的 MTU，但經過 Site-to-Site VPN 時是 1,500 bytes 以下。混合路徑中遇到大封包傳輸異常時，要檢查 MTU 與 path MTU discovery。
3. **頻寬與封包率上限。** TGW attachment、Network Firewall endpoint、NAT Gateway 都有各自的頻寬與連線數上限（部分為預設 quota，可申請提高）。集中化把流量匯集到少數元件，設計時要依尖峰流量估算，必要時把高流量 workload 拆到不同的 egress 或 inspection VPC。

### 企業網路設計流程

```text
① 位址：IPAM pool 依 Region × 環境彙總（41.2）
② 骨幹：Network 帳號建立 TGW，RAM 共享，關閉預設 association／propagation（41.2）

```

## 41.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 數十個 VPC、多帳號、要互連並連地端，營運負擔低 | Transit Gateway（Network 帳號擁有、RAM 共享） |
| prod 與 dev 不可互通，但都要存取 shared services | 不同 TGW route table；shared 的表包含兩邊，prod／dev 不互相 propagation |
| 減少每個 VPC 的 NAT Gateway、集中控制對外流量 | 集中 egress VPC + TGW default route |
| 經由 egress VPC 意外出現 spoke 互通 | Spoke 的 TGW route table 加 blackhole route |
| 所有 VPC 間與往 Internet 的流量都要經 stateful 檢查 | Inspection VPC + Network Firewall（或 GWLB）+ TGW |
| 集中防火牆後跨 AZ 流量間歇失敗 | Inspection VPC attachment 啟用 appliance mode |
| 使用既有第三方防火牆、要能水平擴展 | Gateway Load Balancer + GWLB endpoint |
| 只允許連到核准的外部網域 | Network Firewall stateful domain list（SNI／Host）；DNS Firewall 作輔助 |
| 減少每個 VPC 的 interface endpoint 費用 | 集中 endpoint VPC + 關閉 private DNS + PHZ 關聯到 spoke（或 Route 53 Profiles） |
| 其他 VPC 經 TGW 使用 S3 gateway endpoint | 不可行；每個 VPC 各建 gateway endpoint，或用 S3 interface endpoint |
| 多帳號共用網路、應用團隊不能改路由、降低 attachment 數 | Shared VPC（RAM 共享 subnet） |
| 一組 DX 連到多個 Region 的 TGW | Transit VIF → Direct Connect Gateway → 多個 TGW association（allowed prefixes） |
| Region 間 VPC 互通 | TGW peering（static route）或 Cloud WAN；不是經由 DXGW |
| DX 上的流量需要加密 | MACsec 或 private IP VPN（TGW 為終點） |
| 地端要解析 60 個帳號的 PHZ | 集中 inbound endpoint；所有 PHZ 關聯到 DNS VPC |
| 所有帳號都要能解析地端網域，不要每個 VPC 建 outbound endpoint | 集中 outbound endpoint + RAM 共享 forwarding rule |
| 多 Region、宣告式、依 tag 自動分段 | AWS Cloud WAN core network policy |

**常見陷阱**：

1. 以為 TGW peering 會自動傳播路由：peering attachment 只支援 static route。
2. 以為兩個 TGW 接到同一個 DXGW 就能互通：DXGW 不在 TGW 之間轉送流量。
3. 把 appliance mode 啟用在 spoke attachment：要啟用在 appliance（inspection）VPC 的 attachment。
4. 用 NACL 或 security group 取代 TGW route table 做 segmentation：路由層仍互通。
5. 以為 gateway endpoint 能集中共用：它只對所在 VPC 有效。
6. 忘了把 spoke 的 PHZ 關聯到 DNS VPC，導致地端透過 inbound endpoint 查不到名稱。

## 本章重點整理

- 企業網路以 Transit Gateway 為 hub：放在 Network 帳號、透過 RAM 共享、關閉預設 association 與 propagation，每個 spoke 在每個 AZ 用專用小 subnet 建 attachment。
- IPAM 依 Region × 環境配置可彙總的位址，讓 TGW route table、blackhole route、DX allowed prefixes 與跨 Region static route 都能用少數幾條彙總路由表示。
- TGW 的 segmentation 靠 route table：association 決定查哪張表、propagation 決定出現在哪些表；可達性必須去回兩個方向都成立。
- 集中 egress 讓 spoke 的 default route 指向 TGW、再到有 NAT 與 IGW 的 egress VPC；要用 blackhole route 防止 spoke 經 egress VPC 互通。
- 集中 inspection 以 Network Firewall 或 GWLB 放在 inspection VPC，每個 AZ 的 TGW subnet 指向同 AZ 的 endpoint，並在 inspection VPC 的 attachment 啟用 appliance mode 維持流量對稱。
- Network Firewall 是受管 stateful 防火牆，GWLB 用於第三方 appliance；DNS Firewall 只能作為 DNS 層的補充。
- 集中 interface endpoints 要關閉 private DNS，建立服務名稱的 PHZ 並關聯到所有 spoke（或用 Route 53 Profiles）；gateway endpoint 無法跨 VPC 使用，每個 VPC 各自建立。
- Shared VPC 適合同信任等級的大量小帳號，能減少 attachment 與 TGW 處理費，但 VPC 內隔離只剩 security group，不應混放 prod 與 dev。
- Direct Connect 以 transit VIF 連到 DXGW，再與多個 Region 的 TGW association；DXGW 不在 TGW 之間轉送，Region 互通要用 TGW peering 或 Cloud WAN。
- DX 本身不加密，需要時用 MACsec 或以 TGW 為終點的 private IP VPN；SD-WAN 用 TGW Connect。
- 大規模 hybrid DNS 集中在一個 DNS VPC：inbound endpoint 回答已關聯到該 VPC 的 PHZ，outbound endpoint 的 forwarding rule 以 RAM 共享給全組織。
- TGW peering 只支援 static route；多 Region、多據點時，Cloud WAN 以宣告式 policy、segment 與 tag 型 attachment policy 管理全球網路。
- 集中化用 TGW、firewall 與 endpoint 的處理費換取更少元件與更好控制；高流量路徑、AZ 對齊、MTU 與元件頻寬上限都要納入評估。

## 本章練習題

### 練習 41-1｜SAA｜單選｜大量 VPC 互連

Wanderly 有 25 個 VPC 分布在多個帳號，目前用 VPC peering 互連，另有一條 Site-to-Site VPN 連到台北辦公室。每新增一個 VPC，網路團隊就要建立十幾條 peering 並修改大量 route table，而且辦公室無法經由 peering 連到其他 VPC。公司希望以最少的營運負擔讓所有 VPC 與辦公室互通。

最合適的做法是什麼？

- A. 繼續使用 VPC peering，並撰寫腳本自動建立所有 peering 與 route
- B. 為每個 VPC 各自建立一條到辦公室的 Site-to-Site VPN
- C. 建立 Transit Gateway，把所有 VPC 與辦公室的 VPN 都 attach 到它，由 TGW route table 集中管理路由
- D. 為每個 VPC 建立 PrivateLink endpoint service，讓其他 VPC 以 interface endpoint 連線

> [!answer]- 答案：C
> **A ✗** 自動化可以減少手動工作，但 peering 數量仍以 N² 成長，而且 peering 不支援遞移路由，辦公室的 VPN 仍無法經由一個 VPC 到達其他 VPC。
>
> **B ✗** 25 條 VPN 要在辦公室路由器各自維護，VPC 之間的互通也沒有解決，營運負擔更高。
>
> **C ✓** Transit Gateway 是 hub-and-spoke 架構的中心，支援遞移路由；VPC 與 VPN 都是它的 attachment，新增 VPC 只需一個 attachment 與 route table 設定。
>
> **D ✗** PrivateLink 適合暴露單一服務，不提供 VPC 之間的完整網路互通，也不處理辦公室連線。
>
> **考點**：SAA-3.4、SAA-2.1｜Transit Gateway hub-and-spoke

### 練習 41-2｜SAP｜單選｜TGW segmentation 設計

Wanderly 的 Transit Gateway 連接 20 個 prod VPC、30 個 dev VPC、1 個 shared services VPC，以及經 Direct Connect 連回的地端。要求：prod 與 dev 不可互相路由；prod、dev 都能存取 shared services 與地端；新 VPC 加入時不能自動與其他 VPC 互通。

最合適的 TGW 設定是什麼？

- A. 關閉 TGW 的 default route table association 與 propagation；prod attachment 關聯到 `rt-prod`、dev 關聯到 `rt-dev`；shared 與地端的 CIDR 傳播到這兩張表；prod 與 dev 的 CIDR 都傳播到 shared 與地端關聯的表，但 prod 與 dev 不互相傳播
- B. 保留 default route table，讓所有 attachment 關聯並傳播到同一張表，再在每個 dev VPC 的 NACL 拒絕 prod CIDR
- C. 為 prod 與 dev 各建一張表，但把所有 attachment 的 CIDR 都傳播到兩張表，以便 shared services 能回應
- D. 只建立一張 route table，用 static route 把 dev 的 CIDR 指向 shared services attachment

> [!answer]- 答案：A
> **A ✓** 關閉預設行為讓每個新 attachment 都必須被明確放進某個 segment。prod 與 dev 各自關聯不同的表，表中只有 shared 與地端的 route；shared 與地端的表則同時有 prod 與 dev，讓回程可達。prod 與 dev 沒有彼此的 route，在路由層就互不可達。
>
> **B ✗** 同一張表中 prod 與 dev 在路由上互通，只靠 NACL 逐一阻擋，任何遺漏都會打破隔離；新 VPC 也會自動與所有人互通。
>
> **C ✗** 分開關聯是正確的起點，但把 prod 與 dev 的 CIDR 都傳播到兩張表，又重新建立了雙向可達。
>
> **D ✗** 單一路由表無法讓不同 attachment 看到不同的路由，也無法讓 prod 與 dev 隔離。
>
> **考點**：SAP-1.1、SAP-1.2｜TGW association 與 propagation 分段

### 練習 41-3｜SAP｜單選｜集中 egress 造成的意外互通

Wanderly 建立了集中 egress VPC。所有 spoke 的 TGW route table 只有 `0.0.0.0/0 → egress VPC attachment` 與 shared services 的 route；egress VPC 的 public subnet route table 有 `10.0.0.0/8 → TGW` 以便回程；egress VPC attachment 關聯的 TGW route table 有所有 spoke 的 route。安全掃描發現 dev VPC 竟然可以連到 prod VPC。prod 位址範圍是 `10.16.0.0/13`，dev 是 `10.24.0.0/13`。

最合適的修正是什麼？

- A. 移除 egress VPC public subnet 的 `10.0.0.0/8 → TGW` route
- B. 在每個 prod VPC 的 security group 拒絕來自 dev CIDR 的流量
- C. 把 egress VPC 的 NAT Gateway 換成 NAT instance 並設定防火牆規則
- D. 在 dev 的 TGW route table 加入 `10.16.0.0/13 → blackhole`，在 prod 的 TGW route table 加入 `10.24.0.0/13 → blackhole`

> [!answer]- 答案：D
> **A ✗** 這條 route 是 NAT 回程封包回到 spoke 的必要路徑，移除後所有 spoke 的對外連線都會失敗。
>
> **B ✗** Security group 只有 allow 規則，無法寫「拒絕」；而且這只是在第二層補洞，路由層仍然互通。
>
> **C ✗** 改用 NAT instance 增加營運負擔，問題根源在路由：dev 往 prod 的封包落到 default route、被 egress VPC 送回 TGW。
>
> **D ✓** Blackhole route 比 `0.0.0.0/0` 更精確，依 longest prefix match，往對方環境的封包會被直接丟棄，不再經 default route 繞進 egress VPC。IPAM 的彙總位址讓每個方向只需要一條 blackhole route。
>
> **考點**：SAP-1.1、SAP-1.2｜集中 egress 與 blackhole route

### 練習 41-4｜SAP｜選兩項｜Inspection 的非對稱流量

Wanderly 在 inspection VPC 部署了 AWS Network Firewall，每個 AZ 一個 firewall endpoint，所有 spoke 之間的流量都經 TGW 導向 inspection VPC。測試發現：兩個 VPC 的 instance 在同一個 AZ 時連線正常，在不同 AZ 時連線經常被重設。Firewall 日誌顯示部分回程封包被判定為不屬於任何已知連線。另外，檢查設定時發現 inspection VPC 在 AZ-c 的 TGW subnet route table 把流量送往 AZ-a 的 firewall endpoint，上次 AZ-a 維護時，從 AZ-c 進入的流量也全部中斷。團隊要修正連線重設問題，並確保單一 AZ 的故障不會波及其他 AZ 的流量。

哪兩個做法最能修正？（選兩項）

- A. 在 inspection VPC 的 Transit Gateway attachment 啟用 appliance mode
- B. 在所有 spoke VPC 的 Transit Gateway attachment 啟用 appliance mode，inspection VPC 保持不變
- C. 確認 inspection VPC 中每個 AZ 的 TGW subnet route table 都把流量導向同一 AZ 的 firewall endpoint
- D. 把 Network Firewall 的 stateful rule group 全部改成 stateless 規則
- E. 把所有 spoke 的 instance 集中到單一 AZ

> [!answer]- 答案：A、C
> **A ✓** TGW 預設讓流量從來源 AZ 進入 inspection VPC，去程與回程可能進入不同 AZ 的防火牆。Appliance mode 啟用在 appliance 所在 VPC 的 attachment 上，讓同一條連線的雙向流量都經過同一個 AZ 的防火牆。
>
> **B ✗** Appliance mode 要在 inspection（appliance）VPC 的 attachment 啟用才有效；只改 spoke 無法讓 TGW 對送往 inspection VPC 的流量維持對稱。
>
> **C ✓** 流量進入 inspection VPC 後，必須在同一 AZ 內送到防火牆。AZ-c 的 TGW subnet 指向 AZ-a 的 endpoint，會讓 AZ-c 的流量依賴 AZ-a，正是 AZ-a 維護時 AZ-c 也中斷的原因；改成各 AZ 指向自己的 endpoint，才能滿足「單一 AZ 故障不波及其他 AZ」，也避免多餘的跨 AZ 傳輸費。
>
> **D ✗** 改成 stateless 會失去依連線狀態放行回程的能力，規則也更難寫，等於為了避開問題放棄 PCI 需要的 stateful 檢查。
>
> **E ✗** 集中到單一 AZ 能讓症狀消失，卻犧牲了高可用，違反基本架構原則。
>
> **考點**：SAP-1.1、SAP-1.3｜appliance mode 與 AZ 對齊

### 練習 41-5｜SAP｜單選｜第三方防火牆的集中部署

旅行社的資安團隊多年來使用某廠商的次世代防火牆，有大量既有規則與授權，PCI 稽核程序也依該廠商的報表設計。Wanderly 要在 AWS 上集中檢查所有 VPC 之間與往 Internet 的流量，使用同一廠商的 virtual appliance，並要求 appliance 可以水平擴展、單台故障時流量自動轉移。

最合適的架構是什麼？

- A. 在 inspection VPC 部署兩台 appliance EC2，route table 指向其中一台的 ENI，另一台作為手動切換的備援
- B. 在 inspection VPC 建立 Gateway Load Balancer，後端以 Auto Scaling group 管理 appliance，各 AZ 建立 GWLB endpoint 作為 route target，並在 inspection VPC 的 TGW attachment 啟用 appliance mode
- C. 以 Network Load Balancer 放在 appliance 前面，route table 的 target 指向 NLB
- D. 改用 AWS Network Firewall，並把廠商規則手動轉換成 Suricata 規則

> [!answer]- 答案：B
> **A ✗** 單台 active appliance 是單點與頻寬瓶頸，手動切換無法滿足自動轉移的要求。
>
> **B ✓** GWLB 專為透明插入第三方 appliance 設計：以 GENEVE 把原始封包送到 appliance、對 appliance 做 health check 並分散流量，搭配 Auto Scaling 水平擴展；GWLB endpoint 可作為 route table target。加上 appliance mode 維持跨 AZ 流量對稱。
>
> **C ✗** NLB 不能作為 route table 的 target，也不會保留原始封包讓 appliance 透明檢查。
>
> **D ✗** Network Firewall 是很好的受管選擇，但題目要求延續既有廠商的規則、授權與稽核流程，手動轉換規則耗時且有遺漏風險。
>
> **考點**：SAP-1.2、SAP-2.3｜Gateway Load Balancer 與第三方 appliance

### 練習 41-6｜SAP｜單選｜集中 interface endpoints 的 DNS

Wanderly 在 Network 帳號的 shared endpoints VPC 建立了 Secrets Manager、SSM、KMS 的 interface endpoints，spoke VPC 經 TGW 可以連到這些 endpoint 的 IP。但 spoke 中的應用程式解析 `kms.ap-northeast-1.amazonaws.com` 時仍得到 public IP，流量因此走 NAT。團隊希望所有 spoke 自動使用集中 endpoint，不想在每個 VPC 建立 endpoint。

應如何設定？

- A. 在每個 spoke VPC 開啟 `enableDnsSupport` 與 `enableDnsHostnames`，集中 endpoint 的 private DNS 就會自動在 spoke 生效
- B. 修改每個 spoke 的 DHCP option set，把 DNS server 改成 shared endpoints VPC 的 CIDR +2 位址
- C. 在集中 endpoint 上關閉 private DNS，為每個服務建立名稱與服務網域相同的 private hosted zone，以 alias record 指向 endpoint，並把 PHZ 關聯到所有 spoke VPC（或透過 Route 53 Profiles 共享）
- D. 在 spoke VPC 建立 Resolver outbound endpoint，把 `amazonaws.com` 轉送到 shared endpoints VPC

> [!answer]- 答案：C
> **A ✗** 這兩個屬性是 private DNS 的前提，但 endpoint 的 private DNS 只在 endpoint 所在的 VPC 生效，不會延伸到其他 VPC。
>
> **B ✗** 其他 VPC 的 Amazon-provided DNS 位址只服務該 VPC 內部，從外部 VPC 無法這樣使用；改 DHCP option set 還會影響所有其他名稱解析。
>
> **C ✓** 關閉 private DNS 後，自建與服務網域同名的 PHZ 並關聯到 spoke，spoke 的 Resolver 就會把服務名稱解析到集中 endpoint 的 private IP。帳號很多時，Route 53 Profiles 可以一次共享所有 PHZ。
>
> **D ✗** Outbound endpoint 用來把查詢轉送到 Resolver 以外的 DNS 伺服器（例如地端），把 `amazonaws.com` 整個轉出去會破壞其他 AWS 名稱解析，也沒有解決誰來回答這些名稱。
>
> **考點**：SAP-1.1、SAP-3.5｜集中 interface endpoint 與 PHZ

### 練習 41-7｜SAP｜單選｜S3 私有存取與集中架構

Wanderly 的 spoke VPC 都沒有 NAT，對外流量經 TGW 走集中 egress VPC。網路團隊在 egress VPC 建立了 S3 gateway endpoint，希望所有 spoke 往 S3 的流量都經由它，以避免 NAT 處理費。但帳單顯示 S3 流量仍然產生大量 NAT 與 TGW 處理費。資料分析 VPC 每天從 S3 讀取數 TB。

最具成本效益的修正是什麼？

- A. 在每個 spoke VPC 各自建立 S3 gateway endpoint，並加入該 VPC 的 route table
- B. 在 egress VPC 的 TGW subnet route table 加入 S3 prefix list 指向 gateway endpoint
- C. 在 egress VPC 建立 S3 interface endpoint，讓所有 spoke 經 TGW 存取
- D. 為 S3 bucket 啟用 Transfer Acceleration

> [!answer]- 答案：A
> **A ✓** Gateway endpoint 只對所在 VPC 的 route table 有效，無法經由 TGW 從其他 VPC 使用。在每個 spoke 各自建立 gateway endpoint 是免費的，S3 流量直接在 VPC 內走 endpoint，不經 TGW 與 NAT。
>
> **B ✗** 從其他 VPC 經 TGW 進來的流量無法使用 egress VPC 的 gateway endpoint，這是 gateway endpoint 的設計限制。
>
> **C ✗** S3 interface endpoint 可以從其他 VPC 或地端經 TGW 使用，在地端需要私有存取 S3 時是正確選擇；但它有小時費與每 GB 處理費，再加上 TGW 處理費，對每天數 TB 的流量遠比 gateway endpoint 昂貴。
>
> **D ✗** Transfer Acceleration 透過 edge location 加速遠距離傳輸並額外收費，與 NAT、TGW 處理費無關。
>

>
> **C ✗** DXGW 不會在它關聯的 TGW 之間轉送流量，無法作為 Region 間的骨幹。
>
> **D ✗** VPC peering 不支援遞移路由，大量 VPC 跨 Region 互連的管理負擔更高，也無法處理分公司接入。
>
> **考點**：SAP-1.1、SAP-3.1｜AWS Cloud WAN 與 segment policy

### 練習 41-14｜SAA｜單選｜多 VPC 的 NAT 成本

Wanderly 有 40 個 VPC，每個都在兩個 AZ 各部署一台 NAT Gateway，但大多數 VPC 每天只有少量對外流量（下載 patch、呼叫少數 API）。所有 VPC 已經透過 Transit Gateway 互連。財務要求降低 NAT 相關費用，安全團隊也希望對外流量集中在少數出口以便監控。

最合適的做法是什麼？

- A. 把所有 NAT Gateway 換成 NAT instance，以降低每小時費用
- B. 建立集中 egress VPC，在其中每個 AZ 部署 NAT Gateway；移除各 VPC 的 NAT Gateway，讓各 VPC 的 default route 經 Transit Gateway 送到 egress VPC
- C. 為每個 VPC 增加 Internet Gateway，並讓 private subnet 的 default route 改指向 IGW
- D. 在每個 VPC 只保留一台 NAT Gateway，兩個 AZ 共用

> [!answer]- 答案：B
> **A ✗** NAT instance 雖然沒有 NAT Gateway 的小時費，但 80 台 EC2 的維護、修補與高可用負擔很重，也沒有集中出口。

>
> **C ✗** 讓 private subnet 直接指向 IGW 等於變成 public subnet，資源若有 public IP 就可被 Internet 主動連入，違反安全需求。
>
> **D ✗** 每個 VPC 仍有 40 台 NAT Gateway，而且一個 AZ 故障會讓另一個 AZ 失去對外連線，犧牲高可用。
>
> **考點**：SAA-4.4、SAA-3.4｜集中 egress 降低 NAT 成本

### 練習 41-15｜SAP｜選兩項｜位址規劃與路由彙總

Wanderly 的網路團隊發現 TGW route table、Direct Connect 對地端宣告的路由、跨 Region TGW peering 的 static route 數量都快速增加，因為 landing zone 上線後新增的帳號各自從 `10.0.0.0/8` 中挑選 VPC CIDR，沒有沿用早期依 Region 與環境劃分的位址區塊。地端路由器接收的路由數已接近 DX 的上限。團隊要在不影響既有服務的前提下，讓未來的路由保持精簡。

哪兩個做法最合適？（選兩項）

- A. 在 IPAM 中依 Region × 環境建立連續的 pool（例如東京 prod `10.16.0.0/13`、東京 nonprod `10.24.0.0/13`），透過 RAM 共享給對應 OU，新 VPC 一律從 pool 取得 CIDR
- B. 把所有既有 VPC 的 CIDR 立即修改為新 pool 中的範圍
- C. 在 DXGW 的 allowed prefixes、TGW 的 blackhole 與跨 Region static route 中使用 pool 層級的彙總 CIDR，而不是逐一列出每個 VPC
- D. 為每個 VPC 建立獨立的 Direct Connect VIF，分散路由數量
- E. 在 TGW 上啟用 ECMP，讓重複的路由自動合併

> [!answer]- 答案：A、C
> **A ✓** 讓位址階層與網路 segment 對齊，未來同一 Region、同一環境的 VPC 都落在一個連續範圍內，從源頭讓路由可彙總。
>
> **B ✗** VPC 的主要 CIDR 無法修改，既有服務也不能中斷；既有 VPC 只能保留並逐步遷移到新 VPC。
>
> **C ✓** 有了連續的 pool，宣告給地端與跨 Region 的路由、blackhole route 都可以用少數彙總 CIDR 表示，大幅降低路由數量。
>
> **D ✗** 大量 VIF 增加 BGP session 與管理成本，也受 VIF 數量配額限制，並沒有減少路由的本質數量。
>
> **E ✗** ECMP 是在多條等價路徑上分散流量（例如多條 VPN tunnel），不會合併或減少路由條目。
>
> **考點**：SAP-1.1、SAP-3.4｜IPAM 與路由彙總

> **C ✗** DNS Firewall 能阻擋未核准網域的名稱解析，是很好的補充層；但程式若直接連 IP，就完全繞過 DNS 層，無法滿足「所有其他連線都被阻擋」。
>
> **D ✓** Network Firewall 的 stateful domain list 能依 TLS SNI 與 HTTP Host 標頭允許特定網域，搭配預設拒絕與流量日誌，同時滿足阻擋與記錄的要求；放在集中 inspection VPC 中，規則也只需維護一份。
>
> **考點**：SAA-1.2、SAA-3.4｜Network Firewall 網域過濾
