## 43.1 故事：稽核前六週，和財務長的一張表

第 40 章建好 landing zone 一年後，Wanderly 集團已經有 130 個 AWS 帳號，分布在東京、新加坡，以及第 42 章為歐洲合作案新增的法蘭克福與愛爾蘭。PCI DSS 的年度稽核還有六週，合規負責人小芸把稽核員寄來的清單貼在牆上，其中有三條讓她特別頭痛：

1. 「請證明所有處理持卡人資料的系統都有備份、備份保存一年，且任何人都無法提前刪除。」
2. 「請提供過去十二個月，所有帳號的安全設定基準符合程度，以及不符合項目的處理紀錄。」
3. 「請說明歐洲客戶的個人資料如何確保不離開歐盟。」

同一週，財務長也找上門。他手上有一張 Excel：AWS 帳單每月 48 萬美元，但他無法回答「訂房事業部花了多少」「共用的網路帳號那 6 萬美元該算誰的」「集中買的 Savings Plans 省下的錢，該讓哪些團隊享受」。更麻煩的是，集團旗下即將分拆獨立的旅行社子公司要求：「我們自己買的 Reserved Instances，不要被其他事業部用掉。」

這兩件事看起來一個是合規、一個是財務，本質卻相同：**在上百個帳號的規模下，規則要由中央統一設定、自動套用到每個帳號，而且結果要能被證明。** 這一章依序處理備份、保存、持續合規、資料主權、tag 與成本，最後組成 Wanderly 的治理全貌。

## 43.2 治理的三個層次：規則、偵測、證據

治理工具很多，先用一個架構把它們分類，後面每一節都能放進這張圖裡：

| 層次 | 回答的問題 | 典型工具 | 本章章節 |
|---|---|---|---|
| 預防（preventive） | 怎麼讓錯誤的事做不出來？ | SCP、RCP、declarative policy、Control Tower preventive controls、Vault Lock、Object Lock | 43.5、43.8 |
| 統一設定（configuration） | 怎麼讓每個帳號都自動有正確的設定？ | Backup policy、tag policy、Security Hub central configuration、StackSets | 43.3、43.7、43.9 |
| 偵測與修正（detective／corrective） | 怎麼發現偏離規則的地方並修好？ | Config rules、conformance packs、Security Hub controls、remediation | 43.6、43.7 |
| 證據（evidence） | 怎麼向稽核員證明規則一直在運作？ | Config aggregator、Security Hub findings 歷史、Backup Audit Manager 報告、CloudTrail | 43.6、43.7 |
| 成本責任（accountability） | 錢花在哪裡、誰負責？ | Cost allocation tags、cost categories、CUR、Budgets、承諾共享設定 | 43.9–43.13 |

一個成熟的治理設計會在每一層都有對應的機制，而且彼此互補：SCP 擋住了不允許的 Region，Config 仍要能偵測 SCP 生效前就存在的資源；Object Lock 讓備份刪不掉，Backup Audit Manager 仍要證明「每個該備份的資源都真的有備份」。

## 43.3 組織層的 AWS Backup policies

第 34 章介紹了 AWS Backup 的 backup plan、vault 與跨帳號 copy。那時是「一個團隊為自己的 workload 建立備份計畫」；現在的問題是：**130 個帳號，每個帳號都要有符合公司標準的備份，新帳號一開出來就要有，而且帳號管理員不能自己把它關掉。**

### 為什麼不讓每個帳號自己建 backup plan

過去 Wanderly 讓各團隊依照 wiki 自己建 backup plan，稽核時發現：有的團隊保存 7 天、有的 35 天；有的沒有跨 Region copy；新帳號常常忘記建；還有團隊為了省錢把 plan 刪了。問題不是工程師不認真，而是**「靠每個人照文件做」在一百個帳號的規模下一定會漏**。

### Backup policy 怎麼運作

**Backup policy** 是 Organizations 的一種管理政策（第 14 章）。在 management account 啟用這個政策類型，並啟用 AWS Backup 的跨帳號管理功能後，就可以把 backup policy 附加到 root、OU 或帳號。AWS Backup 會在每個受影響的帳號、每個指定的 Region 中，自動建立對應的 backup plan。這些由政策產生的 plan 在成員帳號中可以看到，但**成員帳號無法修改或刪除**，只能由政策的管理者調整。

```text
 Management account（或 AWS Backup 的 delegated administrator）
   │ ① 撰寫 backup policy，附加到 OU
   ▼
 Root
  └─ Workloads OU ◄── 附加 policy「org-gold」（每日備份、保存 35 天、跨帳號 copy）
       ├─ Prod OU ◄── 附加 policy「prod-hourly」（每小時備份）
       │    ├─ payments-prod ──┐
       │    └─ booking-prod  ──┤ ② 依繼承規則計算 effective policy
       └─ NonProd OU            │
            └─ booking-dev ─────┤
                                ▼
 每個帳號、每個指定 Region：AWS Backup 自動建立 backup plan
   │ ③ 依 tag（backup-tier=gold）選取資源，使用帳號內的 IAM role
   ▼
 帳號內的本地 vault（recovery point） ── ④ copy action ──► Backup 帳號的中央 vault
```

① 政策由中央撰寫，可以由 management account 管理，也可以把 AWS Backup 的管理委派給專用帳號（delegated administrator），避免日常操作 management account。② 一個帳號可能同時繼承多層的政策，Organizations 依**繼承規則**合併成 **effective policy（有效政策）**，可以在 console 或用 `aws organizations describe-effective-policy` 查看某個帳號最終得到的內容。③ 產生的 plan 用 tag 選取資源，所以團隊只要替資源貼上 `backup-tier=gold`，資源就自動被保護。④ copy action 把 recovery point 複製到另一個帳號的 vault（43.4 節）。

### 一份 backup policy 長什麼樣子

```json
{
  "plans": {
    "org-gold": {
      "regions": { "@@assign": ["ap-northeast-1", "ap-southeast-1"] },
      "rules": {
        "daily": {
          "schedule_expression": { "@@assign": "cron(0 17 ? * * *)" },
          "start_backup_window_minutes": { "@@assign": "60" },
          "complete_backup_window_minutes": { "@@assign": "480" },
          "target_backup_vault_name": { "@@assign": "org-local-vault" },
          "lifecycle": {
            "delete_after_days": { "@@assign": "35" }
          },
          "copy_actions": {
            "arn:aws:backup:ap-southeast-1:999988887777:backup-vault:org-central-vault": {
              "target_backup_vault_arn": {
                "@@assign": "arn:aws:backup:ap-southeast-1:999988887777:backup-vault:org-central-vault"
              },
              "lifecycle": {
                "delete_after_days": { "@@assign": "365" }
              }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "gold-resources": {
            "iam_role_arn": { "@@assign": "arn:aws:iam::$account:role/OrgBackupServiceRole" },
            "tag_key": { "@@assign": "backup-tier" },
            "tag_value": { "@@assign": ["gold"] }
          }
        }
      }
    }
  }
}
```

讀這份政策要注意幾點：

- `regions` 決定在哪些 Region 建立 plan。每個 Region 的 plan 只保護該 Region 的資源，所以**允許使用的 Region 都要列進來**，否則某個 Region 的資源就沒有備份。
- `$account` 是政策支援的變數，套用到每個帳號時會替換成該帳號的 ID，讓同一份政策能指向「每個帳號自己的」IAM role。
- `@@assign` 是繼承運算子：子層的 `@@assign` 會覆蓋父層同一個欄位的值。另有 `@@append`（加到父層的清單後面）與 `@@remove`（移除）。父層可以用 `@@operators_allowed_for_child_policies` 限制子層能用哪些運算子，例如設為 `["@@none"]`，就是「子層不能修改這個欄位」，用來鎖住保存天數這類合規要求。
- 數字以字串表示（例如 `"35"`），這是 backup policy 語法的慣例。

### 政策不會幫你建立的東西

Backup policy 只建立 backup plan，**不會**建立它引用的資源。這是導入時最常見的失敗原因：政策附加成功了，但帳號裡一個 recovery point 都沒有。每個帳號、每個 Region 必須事先具備：

1. **政策引用的 vault**（例如 `org-local-vault`），以及它的 KMS key。
2. **政策引用的 IAM role**（例如 `OrgBackupServiceRole`），信任 `backup.amazonaws.com`，並附加 AWS Backup 的備份與還原受管政策。
3. 該 Region 的 AWS Backup **resource type opt-in** 設定中，啟用了要保護的資源類型。

Wanderly 把這三項放進帳號 baseline（第 40 章），由 CloudFormation StackSets 自動部署到 Workloads OU 的每個帳號與 Region，新帳號一加入 OU 就自動具備；再用 Config rule 檢查這些前提是否存在。

### 集中監控

啟用 AWS Backup 的 **cross-account monitoring** 後，management account 或 delegated administrator 可以在一個畫面看到全組織的備份、copy 與還原工作狀態，失敗的工作也能以 EventBridge 事件通知值班人員。這解決了「每天登入 130 個帳號看備份有沒有成功」的問題。

> [!tip] 考試提示
> 題目要求「所有帳號、包括未來新帳號，都要套用一致的備份計畫，且成員帳號不能修改」→ **Organizations backup policy**。若選項只說「用 StackSets 在每個帳號部署 backup plan」，它能做到自動部署，但成員帳號的管理員仍可修改或刪除這個 plan；StackSets 適合部署 backup policy 需要的前提（vault、role）。

## 43.4 跨帳號 vault：備份要放在攻擊者碰不到的地方

備份政策解決了「每個帳號都有備份」，下一個問題是「這些備份安全嗎？」勒索軟體的標準劇本是先取得帳號的管理權限、刪除備份，再加密正式資料。如果 recovery point 只存在 workload 帳號自己的 vault，取得該帳號管理權限的攻擊者就能刪掉它們。

### Wanderly 的備份帳號設計

```text
 Workload 帳號（payments-prod，東京）
 ┌──────────────────────────────────────┐
 │ RDS、DynamoDB、EBS（customer managed key 加密）│
 │   │ ① backup policy 產生的 plan          │
 │   ▼                                    │
 │ org-local-vault（保存 35 天，快速還原用）    │
 └───┼──────────────────────────────────┘
     │ ② copy action（跨帳號＋跨 Region）
     ▼
 Backup 帳號（Backup OU，新加坡）
 ┌──────────────────────────────────────┐
 │ org-central-vault                      │
 │  ③ access policy：只允許組織內帳號 copy 進來  │
 │  ④ Vault Lock（compliance）：最短 365 天    │
 │  ⑤ KMS key 在 Backup 帳號               │
 └──────────────────────────────────────┘
     ⑥ logically air-gapped vault（選用）── RAM 共享 ──► Recovery 帳號：在乾淨環境還原
```

① 每個 workload 帳號保留一份本地備份，用於日常的快速還原（例如誤刪一筆資料）。② 每份 recovery point 同時複製到 Backup 帳號、另一個 Region 的中央 vault。③ 中央 vault 的 access policy 允許組織內的帳號把備份複製進來，但不允許它們刪除：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCopyIntoFromOrg",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "backup:CopyIntoBackupVault",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-a1b2c3d4e5" }
      }
    }
  ]
}
```

④ Vault Lock 讓中央 vault 中的 recovery point 在保存期內無法被刪除（43.5 節）。⑤ 中央 vault 使用 Backup 帳號的 KMS key 重新加密副本，即使 workload 帳號的 key 被刪除或停用，中央副本仍能還原。⑥ 對最高等級的系統，可以使用 **logically air-gapped vault**，透過 AWS RAM 共享給獨立的 Recovery 帳號，在主要環境完全被入侵時，從一個乾淨的帳號還原（第 34 章）。

### 跨帳號 copy 的前提（考試常考）

第 34 章列過這些前提，這裡用「導入時最常卡住的地方」的角度再整理一次：

| 卡住的地方 | 原因 | 解法 |
|---|---|---|
| Copy job 失敗，提示無權限 | 未在 management account 啟用 cross-account backup，或目的 vault policy 未允許 | 啟用跨帳號功能；vault policy 允許 `backup:CopyIntoBackupVault` |
| RDS／Aurora 的 copy 失敗 | 來源以 AWS managed key（`aws/rds`）加密，這種 key 的 policy 無法修改、不能分享給其他帳號 | 來源改用 customer managed key，並在 key policy 中允許目的帳號使用 |
| Copy 到目的帳號的 default vault 失敗 | 跨帳號 copy 不能以 default vault 為目的地 | 建立專用的中央 vault |
| 已轉入冷儲存的備份無法 copy | 冷儲存中的 recovery point 不支援跨帳號 copy | 在轉冷之前完成 copy |

### 用 SCP 保護備份基礎設施

即使中央 vault 有 Vault Lock，workload 帳號的本地備份、IAM role、copy 設定仍可能被破壞。Wanderly 在 Workloads OU 加上一條 SCP，拒絕刪除或修改這些元件，只放行平台團隊的 role：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectOrgBackup",
      "Effect": "Deny",
      "Action": [
        "backup:DeleteBackupVault",
        "backup:DeleteBackupVaultAccessPolicy",
        "backup:DeleteRecoveryPoint",
        "backup:UpdateRecoveryPointLifecycle",
        "backup:PutBackupVaultAccessPolicy"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/platform-backup-admin"
        }
      }
    },
    {
      "Sid": "ProtectBackupRole",
      "Effect": "Deny",
      "Action": [
        "iam:DeleteRole",
        "iam:DetachRolePolicy",
        "iam:PutRolePolicy",
        "iam:UpdateAssumeRolePolicy"
      ],
      "Resource": "arn:aws:iam::*:role/OrgBackupServiceRole",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/platform-backup-admin"
        }
      }
    }
  ]
}
```

第一段拒絕刪除 vault、刪除 recovery point、縮短保存期與修改 vault access policy。這裡的 `Resource` 用 `*`，因為 recovery point 的 ARN 依資源類型而不同（例如 EBS snapshot 的 ARN 屬於 EC2），無法用 vault 名稱一次涵蓋。第二段只保護 backup policy 使用的那個 IAM role，避免有人刪掉 role 讓備份「靜靜地失敗」；這種以命名慣例劃定受保護資源的做法，要搭配 IaC 確保名稱一致。

## 43.5 法規保存：保存多久、誰能刪、怎麼證明

PCI DSS、金融法規、稅務法規常要求「某類紀錄保存 N 年，期間不得竄改或刪除」。個資法規則常要求「不再需要時就刪除」。治理設計要同時滿足這兩種方向相反的要求，所以第一步永遠是**資料分類**（第 16 章）：先決定每類資料的保存期與刪除義務，再選控制。

### 把保存需求對應到 AWS 控制

| 需求 | 控制 | 誰能提前刪除 | 注意 |
|---|---|---|---|
| S3 物件保存 N 年，連 root 都不能刪 | S3 Object Lock **compliance mode** + default retention | 沒有人；保存期只能延長 | 需要 versioning；保護的是物件版本 |
| S3 物件防誤刪，但保留管理例外 | S3 Object Lock **governance mode** | 有 `s3:BypassGovernanceRetention` 權限者，並在請求中明確 bypass | 適合測試設定或內部治理 |
| 訴訟期間凍結特定物件，期限不定 | S3 Object Lock **legal hold** | 有 `s3:PutObjectLegalHold` 權限者移除 hold 後 | 與保存期獨立，可同時存在 |
| 備份保存至少 N 天，任何人都不能刪 | AWS Backup **Vault Lock compliance mode** | 冷靜期（grace time，至少 72 小時）過後沒有人 | 冷靜期內可以修改或移除鎖定 |
| 備份的保存期不能被設定得太短或太長 | Vault Lock 的 min／max retention | — | 超出範圍的備份或 copy 會失敗 |
| 調查期間保留特定備份 | AWS Backup **legal hold** | 有權限者解除 hold 後 | 可依資源類型、日期範圍選取 recovery point |
| 原始 Glacier vault 的封存 | Glacier Vault Lock | 鎖定後政策不可變更 | 原始 vault 型 Glacier 服務不再接受新客戶，新設計用 S3 Glacier storage classes + Object Lock |

設定 Vault Lock 的指令很短，但後果很長：

```bash
# compliance mode：設定 changeable-for-days（至少 3 天）後，冷靜期結束即無法變更
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name org-central-vault \
  --min-retention-days 365 \
  --max-retention-days 2555 \
  --changeable-for-days 3
```

不帶 `--changeable-for-days` 時是 governance mode，有足夠權限的人可以移除鎖定。帶了之後，三天的冷靜期一過就是 compliance mode，連 root user 與 AWS 都無法縮短或移除。Wanderly 的做法是先在測試 vault 以 governance mode 驗證一個月，確認保存天數、copy 規則都正確，再對正式 vault 啟用 compliance mode。

### 保存與刪除的衝突

如果一位歐洲會員要求刪除他的個資，但他的資料存在 compliance mode 鎖定一年的備份中，怎麼辦？WORM 的設計就是「不能刪」，所以這個衝突要在**設計階段**處理，而不是事後：

- 只對法規確實要求保存的資料類別啟用 compliance 鎖定，不要把所有東西都鎖住。
- 備份的保存期設定為法規要求的最短期限，期滿自動刪除，讓「刪除」在可預期的時間內完成。
- 在隱私政策中明確告知備份中的資料何時會被刪除，並確保還原時不會讓已刪除的資料重新回到正式系統（例如還原後重放刪除紀錄）。

> [!warning] 常見誤解
> 「compliance mode 先開了再說，之後不合適再改。」Compliance mode 的保存期在期限內無法縮短，Vault Lock 在冷靜期後無法移除。設錯了，你就要為這些資料付費到期滿為止。正確順序是先 governance、驗證、再 compliance。

## 43.6 持續合規：Config conformance packs 與 aggregator

稽核員的第二個要求是「過去十二個月，所有帳號的設定符合程度」。這是**持續合規（continuous compliance）**的問題：不是稽核前一週檢查一次，而是每天、每次變更都檢查，並保留結果。

### Conformance pack：一組規則一起部署

第 16 章介紹了 Config rule 與 conformance pack 的概念。在組織層級，關鍵是 **organization conformance pack**：由 management account 或 Config 的 delegated administrator 部署，一次套用到組織內所有帳號（可以排除特定帳號），新帳號加入時也會自動部署。成員帳號看得到這些規則，但不能修改或刪除。

一個 conformance pack 是一份 YAML template，內容是一組 `AWS::Config::ConfigRule`，可以搭配 remediation 設定。Wanderly 以 AWS 提供的 PCI DSS 營運最佳實務範本為基礎，再加上公司自己的規則：

```yaml
Parameters:
  MaxAccessKeyAgeDays:
    Type: String
    Default: "90"
Resources:
  EbsVolumesEncrypted:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: encrypted-volumes
      Source:
        Owner: AWS
        SourceIdentifier: ENCRYPTED_VOLUMES
  S3VersioningEnabled:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: s3-bucket-versioning-enabled
      Source:
        Owner: AWS
        SourceIdentifier: S3_BUCKET_VERSIONING_ENABLED
  AccessKeysRotated:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: access-keys-rotated
      InputParameters:
        maxAccessKeyAge: !Ref MaxAccessKeyAgeDays
      Source:
        Owner: AWS
        SourceIdentifier: ACCESS_KEYS_ROTATED
```

由 delegated administrator 帳號部署到整個組織：

```bash
aws configservice put-organization-conformance-pack \
  --organization-conformance-pack-name wanderly-pci-baseline \
  --template-s3-uri s3://wanderly-governance-templates/pci-baseline.yaml \
  --excluded-accounts 444455556666
```

被排除的帳號（例如 sandbox）不會部署這套規則。每條規則對每個資源產生 `COMPLIANT` 或 `NON_COMPLIANT` 的結果，conformance pack 也會計算整體的**合規分數**，讓管理層看到趨勢。

### Aggregator：一個地方看全組織

**Aggregator** 把所有帳號、所有 Region 的 Config 資料與合規結果集中到一個帳號（通常是第 40 章的 Audit 帳號）。除了看儀表板，還能用 **advanced query**（類似 SQL 的查詢）跨帳號搜尋資源設定：

```bash
aws configservice select-aggregate-resource-config \
  --configuration-aggregator-name org-aggregator \
  --expression "SELECT accountId, awsRegion, resourceId WHERE resourceType = 'AWS::EC2::Volume' AND configuration.encrypted = false"
```

這條查詢在幾秒內回答「全組織哪些 EBS volume 沒加密」，結果可以匯出成稽核證據。

### 從偵測到修正

偵測到不合規之後，要有處理流程，稽核員要看的正是「不符合項目的處理紀錄」：

1. **自動修正**：低風險、確定性的修正（例如替 S3 bucket 開啟 versioning）以 SSM Automation runbook 自動執行。
2. **開單處理**：需要人判斷的（例如某個 security group 對外開放），以 EventBridge 接收 Config 的合規變更事件，建立工單並指派給帳號 owner（帳號 tag 中的 `owner`）。
3. **例外管理**：確實需要例外的資源，記錄核准人與到期日，而不是讓它永遠 `NON_COMPLIANT`。

### Config 的成本

Config 依記錄的 configuration item 數量與規則評估次數計費，在變動頻繁的環境（例如大量短命的 container 或 ENI）可能很可觀。可用的控制：只記錄合規需要的資源類型；對變動頻繁但合規要求較低的資源類型改用**每日記錄（periodic recording）**而不是持續記錄；sandbox 帳號排除不必要的規則。

## 43.7 Security Hub 標準與稽核證據

Config conformance pack 讓你自己決定要檢查什麼；**Security Hub CSPM**（原本的 Security Hub，第 16 章）則提供現成的安全標準，例如 AWS Foundational Security Best Practices（FSBP）、CIS AWS Foundations Benchmark、PCI DSS、NIST SP 800-53，每個標準由許多 control 組成，大多透過 Config 規則執行。

### Central configuration：依 OU 套用不同的標準

在多帳號環境，Security Hub 的 delegated administrator 可以使用 **central configuration**，建立 **configuration policy** 並關聯到 OU 或帳號，統一決定「哪些帳號、哪些 Region 啟用哪些標準與 control」：

| Configuration policy | 關聯目標 | 內容 |
|---|---|---|
| `baseline-all` | Root | 啟用 Security Hub CSPM、FSBP 標準，在所有允許的 Region |
| `pci-scope` | Payments OU | 在 `baseline-all` 之外再啟用 PCI DSS 標準 |
| `sandbox-light` | Sandbox OU | 只啟用 FSBP，並停用幾個在 sandbox 不適用的 control |

新帳號移入 OU 就自動套用對應的 policy；成員帳號不能自行停用。搭配 **cross-Region aggregation**，所有 Region 的 findings 集中到一個 aggregation Region，資安團隊在一個地方處理。

### Audit Manager 的現況與替代方案

傳統上，「自動收集證據、對應到合規框架、產生給稽核員的報告」是 **AWS Audit Manager** 的工作。但如第 16 章所述，Audit Manager 自 2026 年 4 月 30 日起不再開放新客戶設定，已在使用的客戶可以在原本的帳號與 Region 繼續使用。Wanderly 的新帳號與法蘭克福 Region 因此改用以下組合：

```text
 ① 技術控制的定義            ② 持續評估                    ③ 彙整與證據
 Config conformance packs ─► 每個帳號、每個 Region ─────► Config aggregator（Audit 帳號）
 （PCI DSS 營運最佳實務範本）    的 Config rules            advanced query 匯出合規快照
 Security Hub CSPM 標準 ───► Security Hub controls ────► Security Hub 跨 Region 彙整
 （PCI DSS、FSBP）                                         findings 歷史
                                                              │
 ④ 時間軸證據：CloudTrail organization trail（Log Archive，Object Lock）
 ⑤ 備份證據：AWS Backup Audit Manager 報告（每個資源是否有備份、保存期、copy、vault lock）
                                                              │
                                                              ▼
                              ⑥ 定期匯出到 Log Archive 的 S3（Object Lock），
                                 以 Athena 查詢、QuickSight 呈現，交給稽核員
```

① 技術控制以 conformance pack 與 Security Hub 標準定義。② 兩者都在每個帳號持續評估。③ 結果集中在 Audit 帳號。④ CloudTrail 提供「誰在何時改了什麼」的時間軸。⑤ **AWS Backup Audit Manager**（這是 AWS Backup 的功能，不是被關閉的 AWS Audit Manager 服務）持續檢查備份是否符合 framework 中的 control，並產生報告。⑥ 定期把合規快照與報告匯出到不可竄改的 S3，形成十二個月的證據。政策文件、人員訓練這類非技術控制，則由公司的 GRC（治理、風險與合規）流程或第三方工具管理。

**AWS Artifact** 仍是取得 AWS 自身合規報告（例如 PCI DSS 的 AOC、SOC 報告）的地方，它證明的是責任分擔模型中 AWS 那一側。

> [!note] 考試與實務的落差
> SAA-C03 與 SAP-C02 的題庫早於 Audit Manager 的這次變更。題目若問「自動收集稽核證據並對應到 PCI DSS 等框架、產生 assessment report」，答案仍是 Audit Manager。題目若明確說明是新客戶或新組織、無法使用 Audit Manager，則選 Config conformance packs 加 aggregator 與 Security Hub 的組合。

## 43.8 資料主權：讓資料留在該留的地方

稽核員的第三個要求，「歐洲客戶的個人資料如何確保不離開歐盟」，延續了第 42 章的架構決定。第 42 章從應用架構回答（依 home Region 分區、拆分 global table），這一節從**治理**回答：用什麼機制讓違規的配置做不出來、或至少會被發現。

### 第一層：限制可以使用的 Region

第 14 章的 Region 限制 SCP 以 `aws:RequestedRegion` 拒絕核准清單以外的 Region，並以 `NotAction` 排除全球服務。Wanderly 把它依 OU 分成兩份：亞太 OU 只允許東京與新加坡，歐洲 OU 只允許法蘭克福與愛爾蘭：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EuWorkloadsStayInEu",
      "Effect": "Deny",
      "NotAction": [
        "iam:*", "organizations:*", "account:*", "sts:*",
        "route53:*", "cloudfront:*", "globalaccelerator:*",
        "wafv2:*", "shield:*", "support:*", "budgets:*", "ce:*",
        "health:*", "trustedadvisor:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["eu-central-1", "eu-west-1"]
        },
        "ArnNotLike": {
          "aws:PrincipalARN": "arn:aws:iam::*:role/PlatformBreakGlass"
        }
      }
    }
  ]
}
```

使用 Control Tower 時，可以改用它的 **Region deny** 設定，由 Control Tower 維護全球服務的例外清單。Control Tower 也提供一組以資料落地為目的的 controls，可以依需求啟用。

### 第二層：限制資料「被複製」到哪裡

Region SCP 只限制「在這個帳號中呼叫哪個 Region 的 API」，但資料也可能透過服務的複寫功能離開。逐一檢查每個會跨 Region 搬資料的功能：

| 資料流 | 風險 | 控制 |
|---|---|---|
| S3 Cross-Region Replication | 複寫到歐盟以外的 bucket | 目的 bucket 若在組織內，Region SCP 讓它無法在歐盟以外被建立；目的 bucket 若在組織外，用 data perimeter（第 14、40 章）拒絕把資料寫到組織外；Config 規則檢查複寫設定 |
| AWS Backup copy | Copy 到亞太（新加坡）的中央 vault | 歐洲 OU 使用獨立的 backup policy，copy action 指向愛爾蘭的中央 vault；AWS Backup 提供可限制 copy 目的地的 IAM condition key，可在 SCP 中使用 |
| DynamoDB global tables、Aurora Global Database | 新增歐盟以外的 replica | Region SCP 阻止在歐盟以外建立 replica 資源（新增 replica 時，DynamoDB 會在 replica 所在 Region 評估 `dynamodb:CreateTableReplica` 等權限，所以 `aws:RequestedRegion` 條件有效）；架構上把歐洲資料放在獨立的 table（第 42 章） |
| 集中日誌 | 歐洲帳號的應用程式日誌含個資，被送到東京的 Log Archive | 應用日誌先去識別化；或在歐盟設立區域性的日誌 bucket |
| 生成式 AI 的 cross-Region inference | 推論請求可能被路由到其他 Region | 只使用限定地理範圍的 inference profile，或停用跨 Region 推論（第 47 章） |
| CloudFront 快取 | 含個資的 API 回應被快取在全球的 edge | 含個資的回應設定不快取，只快取公開內容 |

### 第三層：證明

最後，治理要能產生證據：Config aggregator 的 advanced query 可以列出歐洲 OU 中所有資源的 Region 分布；Config 規則持續檢查 S3 複寫目的地與 backup plan 的 copy 目的地；CloudTrail 記錄任何嘗試在歐盟以外建立資源而被 SCP 拒絕的請求（`AccessDenied` 事件本身就是控制有效的證據）。

> [!warning] 常見誤解
> 「資料加密了，就可以放在任何 Region。」加密保護的是機密性，不改變資料的所在地。多數資料落地的要求針對的是資料存放與處理的位置，加密後的副本仍然是「存在那個國家的資料」。另一個誤解是「SCP 限制了 Region 就萬無一失」：IAM、CloudFront、Route 53 等全球服務被排除在 SCP 之外，而且管理類 metadata（例如 CloudTrail 事件中的資源名稱）可能仍會流到其他地區，命名時不要把個資放進資源名稱或 tag。

## 43.9 Tagging 策略：先定字典，再談強制

處理完合規，回到財務長的問題。成本歸屬的第一個依據是**帳號**（每個帳號的費用天然分開），第二個依據是 **tag**。第 40 章比較過 tag policy、SCP、Config rule、cost allocation tags 四種工具各自能做什麼，這一節關心的是更前面的一步：**公司要有哪些 tag、值長什麼樣子。** 沒有字典，再多的強制工具也只會強制出一堆不一致的值。

### Wanderly 的 tag 字典

| Tag key | 必要 | 允許的值 | 用途 | 來源 |
|---|---|---|---|---|
| `cost-center` | 是 | 財務系統的成本中心代碼，例如 `CC-1200` | 成本分攤 | 帳號 tag 繼承到預設值；IaC 預設 tag |
| `application` | 是 | 應用目錄中的 ID，例如 `booking-api` | 成本分攤、事故影響分析 | IaC |
| `environment` | 是 | `prod`、`staging`、`dev`、`sandbox` | 政策條件、成本分攤 | IaC（依 pipeline 階段） |
| `owner` | 是 | 團隊信箱，例如 `team-booking@` | 不合規通知、事故聯絡 | IaC |
| `data-classification` | 是 | `public`、`internal`、`confidential`、`pci` | 安全控制、備份等級 | IaC，由資料擁有者決定 |
| `backup-tier` | 否 | `gold`、`silver`、`none` | backup policy 的資源選取（43.3 節） | IaC |

設計字典時的幾條原則：

- **key 一律小寫並以連字號分隔**。Tag key 區分大小寫，`CostCenter` 與 `costcenter` 在帳單中是兩個不同的維度。
- **值要能對應到公司的其他系統**：`cost-center` 的值就是財務系統裡的代碼，`application` 的值就是應用目錄裡的 ID，這樣 CUR 才能和其他資料 JOIN。
- **不要把會變的東西放進 tag**，例如人名；人會離職，團隊信箱比較穩定。
- **不要把個資放進 tag**：tag 會出現在帳單、CUR 與許多管理介面中，能看到的人遠多於能看到資料本身的人。

### 用 tag policy 規範值

有了字典，就能用 **tag policy** 規範 key 的大小寫與允許的值，並對指定資源類型開啟 enforcement：

```json
{
  "tags": {
    "environment": {
      "tag_key": { "@@assign": "environment" },
      "tag_value": { "@@assign": ["prod", "staging", "dev", "sandbox"] },
      "enforced_for": { "@@assign": ["ec2:instance", "ec2:volume"] }
    },
    "cost-center": {
      "tag_key": { "@@assign": "cost-center" },
      "tag_value": { "@@assign": ["CC-*"] }
    }
  }
}
```

`tag_value` 支援萬用字元（`CC-*`）。`enforced_for` 讓這些資源類型「如果帶了這個 tag，值不合規就拒絕」。如第 40 章所述，tag policy 不會強制資源一定要帶 tag；較新的 required tags 功能也只在 IaC 工具部署時檢查。要「沒帶就不能建立」，用 SCP 搭配 `aws:RequestTag`；要找出既有資源缺 tag，用 Config 的 `required-tags` 規則。

### 讓 tag 從源頭就正確

與其事後追查，不如讓資源一出生就帶 tag：

- **IaC 的預設 tag**：CloudFormation stack 層級的 tag 會傳播到支援 tag 的資源；CDK 可以用 `Tags.of(app).add(...)` 一次套用到整個 app；Terraform AWS provider 有 `default_tags`。
- **自動繼承**：Auto Scaling group 要設定 tag 的 `PropagateAtLaunch`，新啟動的 instance 才會帶 tag；ECS 要開啟 tag propagation，task 才會帶上 service 或 task definition 的 tag。
- **帳號 tag 作為最後的保障**：帳號 tag 啟用為 cost allocation tag 後，帳號內所有費用都帶上它，包含無法打 tag 的費用（第 40 章）。

### 啟用 cost allocation tags

Tag 要出現在帳單中，必須在 management（payer）帳號的 Billing console 中**啟用為 cost allocation tag**。啟用後才開始在帳單資料中出現；Wanderly 是在導入字典三個月後才啟用的，於是申請了 **backfill**，把過去最多 12 個月的帳單資料依這些 tag 重新分組（第 39 章）。另外，`aws:createdBy` 這類 AWS-generated tag 也可以啟用，用來找出「是誰建立了這個沒人認領的資源」。

## 43.10 Cost categories 與 chargeback：把帳單翻譯成組織的語言

有了帳號與 tag，下一步是把它們組合成財務看得懂的分類。財務長想看的不是「帳號 111122223333 花了多少」，而是「訂房事業部花了多少」。**Cost categories** 用規則把帳號、tag、服務等維度映射成你定義的類別值。

### 一個 cost category 的定義

```json
{
  "Name": "business-unit",
  "RuleVersion": "CostCategoryExpression.v1",
  "Rules": [
    {
      "Value": "shared-platform",
      "Rule": {
        "Dimensions": {
          "Key": "LINKED_ACCOUNT",
          "Values": ["210000000001", "210000000002", "210000000003"]
        }
      }
    },
    {
      "Value": "booking",
      "Rule": {
        "Or": [
          { "Dimensions": { "Key": "LINKED_ACCOUNT", "Values": ["310000000001", "310000000002"] } },
          { "Tags": { "Key": "application", "Values": ["booking-api", "booking-worker"] } }
        ]
      }
    },
    {
      "Value": "search",
      "Rule": {
        "Tags": { "Key": "application", "Values": ["search-api", "search-indexer"] }
      }
    }
  ],
  "DefaultValue": "unallocated",
  "SplitChargeRules": [
    {
      "Source": "shared-platform",
      "Targets": ["booking", "search"],
      "Method": "PROPORTIONAL"
    }
  ]
}
```

讀這份定義的重點：

- **規則依順序評估，第一個符合的規則決定類別值。** 所以把最明確的規則（例如共用平台帳號）放在前面。
- `DefaultValue` 接住所有沒被任何規則分到的費用。`unallocated` 這一類的金額就是「tag 治理還沒做好」的量化指標，Wanderly 把它列為每月檢討的 KPI。
- 規則也可以用 **inherited value** 類型，直接把某個 tag 或帳號名稱的值當作類別值，適合團隊很多、不想逐一列舉的情況。
- Cost categories 可以巢狀引用其他 cost category，例如「事業部」由多個「產品線」組成。

### 共用成本怎麼分：split charges

網路帳號（Transit Gateway、集中 egress、Direct Connect）、Security Tooling 帳號、Enterprise Support 費用，這些是所有事業部共用的成本。**Split charge rules** 把來源類別的成本分攤到目標類別，有三種方法：

| 方法 | 怎麼分 | 適合 |
|---|---|---|
| `PROPORTIONAL` | 依目標類別各自的費用比例 | 「用得多的人多付」，最常見 |
| `EVEN` | 平均分給每個目標 | 共用成本與用量無關，例如固定的工具授權 |
| `FIXED` | 依你指定的百分比 | 已和各單位談好固定比例 |

要注意，split charge 的分攤結果主要呈現在 cost category 的明細與其報表中，不會改寫 Cost Explorer 或 CUR 中每一列的原始費用。若要在自己的 CUR 報表中呈現分攤後的數字，需要在查詢中套用相同的分攤邏輯。

### 從 showback 到 chargeback

第 39 章定義過 **showback**（讓團隊看到成本）與 **chargeback**（實際計入團隊預算）。Wanderly 的導入順序是：

1. **第一季：showback。** 每週把各事業部的成本寄給負責人，`unallocated` 比例從 23% 逐步降到 5% 以下。這段期間的目的是讓大家相信數字。
2. **第二季：與財務約定規則。** 共用成本用 `PROPORTIONAL` 分攤；Savings Plans 的折扣如何分配（43.13 節）；未使用的承諾由誰負擔。
3. **第三季：chargeback。** 依約定的規則每月結算，計入各事業部的損益。

需要給各單位一份「看起來像 AWS 帳單」的模擬帳單時（例如子公司要依自己的價格表計費），使用 **AWS Billing Conductor** 建立 billing group 與 pricing rule，產生 pro forma 帳單；它不會改變實際付給 AWS 的金額（第 39 章）。

## 43.11 CUR 2.0 + Athena：自己算帳

Cost Explorer 能回答大部分的問題，但財務長還想要「每筆訂房的雲端成本」：這需要把帳單資料和公司的訂房量 JOIN 起來，Cost Explorer 做不到。這時就要用最細的帳單資料：**Cost and Usage Report（CUR）**。

### 資料流

```text
 Management（payer）帳號
   │ ① Data Exports：建立 CUR 2.0 export（Parquet、每日更新、含 resource ID）
   ▼
 S3：wanderly-cur（分區：BILLING_PERIOD=2026-09/…）
   │ ② S3 replication 到 FinOps 帳號（讓分析不必在 management account 進行）
   ▼
 FinOps 帳號
   │ ③ Glue Data Catalog table（Glue crawler 或 AWS 提供的 template）
   ▼
 Athena ── ④ SQL：依帳號、cost category、tag 彙總；JOIN 訂房量
   │
   ▼
 QuickSight ── ⑤ 公司、事業部、團隊三層儀表板；單位成本趨勢
```

① CUR 2.0 透過 **Data Exports** 建立，以 Parquet 格式每天更新數次地寫入 S3，可以選擇要包含的欄位與 resource ID。② Wanderly 不希望 FinOps 分析師登入 management account，所以把 CUR bucket 複寫到 FinOps 帳號。③ 在 Glue Data Catalog 建立 table 定義，Athena 才能查詢。④ 以 SQL 做任何維度的彙總。⑤ 用 QuickSight 呈現給不同層級的讀者。

### 一個查詢範例

CUR 2.0 中，tag 與 cost category 以 map 欄位存放（`resource_tags`、`cost_category`），用 `欄位['key']` 取值。只有啟用為 cost allocation tag 的 tag 才會出現在 `resource_tags` 中；map 中的 key 名稱可能經過正規化（例如使用者自訂 tag 加上 `user_` 前綴），撰寫查詢前先以 `map_keys(resource_tags)` 確認實際的 key。以下查詢計算 2026 年 9 月各事業部的攤提後成本（amortized cost），也就是把 Savings Plans 與 RI 的效益分配到實際使用它的用量上：

```sql
SELECT
  cost_category['business-unit']          AS business_unit,
  line_item_usage_account_id              AS account_id,
  ROUND(SUM(
    CASE
      WHEN line_item_line_item_type = 'SavingsPlanCoveredUsage'
        THEN savings_plan_savings_plan_effective_cost
      WHEN line_item_line_item_type = 'DiscountedUsage'
        THEN reservation_effective_cost
      WHEN line_item_line_item_type IN
           ('SavingsPlanNegation', 'SavingsPlanRecurringFee',
            'SavingsPlanUpfrontFee', 'RIFee')
        THEN 0
      WHEN line_item_line_item_type = 'Fee'
           AND COALESCE(reservation_reservation_a_r_n, '') <> ''
        THEN 0
      ELSE line_item_unblended_cost
    END
  ), 2)                                   AS amortized_cost
FROM wanderly_cur2
WHERE billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY amortized_cost DESC;
```

這個查詢的設計重點：

- 被 Savings Plans 覆蓋的用量，以 `savings_plan_savings_plan_effective_cost`（攤提後的實際成本）計算，而不是 On-Demand 價格。
- 承諾本身的月費、預付款與抵銷項目設為 0，避免重複計算。這代表**未使用的承諾不會分配給任何事業部**，它們留在中央 FinOps 的帳上。這正是 43.13 節要和財務約定的規則之一：未使用的承諾由買的人負責，這樣各團隊不會因為中央買多了而被懲罰。
- `billing_period` 是分區欄位，加上這個條件 Athena 只掃描一個月的資料，查詢費用低很多。

計算單位成本時，再把結果和訂房系統每日匯出到 S3 的訂房量 JOIN：「訂房事業部的雲端成本 ÷ 訂房筆數」就是每筆訂房的成本。

> [!tip] 考試提示
> 題目要求「最細的帳單資料」「與內部業務資料結合」「自訂分析」→ **CUR（Data Exports）+ S3 + Athena（+ QuickSight）**。只要求「依 tag 或帳號看趨勢」「預測」→ Cost Explorer 就夠了。

## 43.12 每個帳號的 Budgets 與異常偵測

成本可視化告訴你「花了多少」，**Budgets** 與 **Cost Anomaly Detection** 告訴你「什麼時候該擔心」。在 130 個帳號的規模下，關鍵是**自動化**：每個帳號都要有預算，而且不能靠人手動建立。

### 每個帳號都有預算

Wanderly 的做法：

1. 帳號建立時，帳號 tag 中帶有 `monthly-budget-usd`（由申請人填寫、主管核准）。
2. 帳號 baseline（第 40 章的 AFT customization 或 StackSets）讀取這個值，在帳號內以 CloudFormation 的 `AWS::Budgets::Budget` 建立 cost budget，在實際花費達 80% 與預測將超過 100% 時通知帳號 owner。
3. Management account 另外為每個 OU 建立彙總預算，篩選條件是該 OU 的帳號，通知事業部負責人。

### Budget actions：超標時自動踩煞車

對 sandbox 與 dev 帳號，Wanderly 設定 **budget action**：預算達 100% 時，自動對該帳號套用一條 SCP，拒絕建立新的 EC2、RDS 等資源（既有資源不受影響），並通知 owner。對 production 帳號則**只通知不阻擋**，因為正式服務被擋下來的損失通常大於超支。要記得 Budgets 依帳單資料評估，資料每天更新數次，不是即時的開關（第 39 章）；以 SCP 為動作的 budget action 要由 management account 設定。

### 異常偵測

**Cost Anomaly Detection** 以機器學習學習每個範圍的正常支出模式。Wanderly 建立了兩種 monitor：一個以 **linked account** 為維度，每個帳號的異常個別通知 owner；一個以 `business-unit` **cost category** 為維度，讓事業部負責人收到每日摘要。一位工程師誤開了一組 GPU instance 忘記關，三天後預算還沒超標，但 anomaly 告警已經在第一天晚上送到他的團隊。

## 43.13 承諾的共享：Savings Plans、RI 與關閉分享

最後是財務長最在意的錢：Wanderly 每年在 Savings Plans 與 RI 上承諾了數百萬美元。誰買、誰用、誰享受折扣，需要明確的規則。

### 預設的共享行為

在 Organizations 的 consolidated billing 下（第 14 章）：

1. 每個小時，RI 與 Savings Plans 的效益**先套用到購買它的帳號**中符合條件的用量。
2. 購買帳號用不完的部分，**再套用到組織內其他帳號**的符合用量。
3. 套用順序上，RI 先於 Savings Plans；Savings Plans 之間，EC2 Instance Savings Plans 先於 Compute Savings Plans（第 39 章）。

這個預設讓承諾的使用率最大化，也是集中購買策略的基礎。

### 集中購買

Wanderly 由 FinOps 團隊在專用的 FinOps 帳號集中購買 Compute Savings Plans 與資料庫的 RI：

- 以**全組織最佳化後的 baseline** 計算承諾量，而不是各團隊各自估算。各團隊自行購買容易重複，也容易因為架構改變而買錯。
- 承諾的效益透過共享流到各帳號。在 chargeback 中，各事業部以 43.11 節的 amortized cost 計費，未使用的承諾留在 FinOps 帳號。
- 資料庫用量的引擎或規格會變動時（例如旅行社的 Oracle 正在遷移到 Aurora PostgreSQL，第 45 章），考慮 **Database Savings Plans**：1 年期、No Upfront，最高約 35% 的折扣，涵蓋 Aurora、RDS、DynamoDB、ElastiCache 等多種資料庫服務，不論引擎、instance 規格或 Region 都自動適用（例如從 RDS for Oracle 換到 Aurora PostgreSQL），彈性比 RDS RI 高；同一個 workload 不能同時套用 Database Savings Plans 與 RDS RI。
- 用 SCP 拒絕一般帳號購買承諾（例如 `savingsplans:CreateSavingsPlan`、`ec2:PurchaseReservedInstancesOffering`、`rds:PurchaseReservedDBInstancesOffering`），只放行 FinOps 帳號，避免各團隊自行購買破壞整體規劃。

### 關閉分享：給需要獨立計算的帳號

旅行社子公司的要求「我們自己買的 RI 不要被別人用掉」，對應的功能是 **RI and Savings Plans discount sharing**（折扣共享）偏好設定。Management account 可以在 Billing preferences 中**對指定帳號關閉共享**：

- 關閉後，該帳號購買的 RI 與 Savings Plans **只套用到它自己的用量**，用不完也不會流到其他帳號。
- 同時，該帳號**也不會接收**其他帳號的承諾效益。共享是雙向的，關閉也是雙向的。
- 被關閉的帳號在 Cost Explorer 中看到的 RI／Savings Plans 使用率與覆蓋率，只反映它自己的情況。

適合關閉分享的情況：即將分拆或出售的子公司、合約要求獨立成本的客戶專屬帳號、需要獨立損益的事業單位。代價是整體使用率可能下降：子公司某個月沒用滿的承諾，原本可以抵其他事業部的用量，現在只能浪費。

> [!note] 更細的共享範圍
> AWS 近年另外推出以 cost category 定義群組、讓承諾優先在群組內共享（或只限群組內共享）的進階設定，介於「全組織共享」與「完全關閉」之間。考試題目仍以「開啟或對特定帳號關閉 discount sharing」為主；實務導入前請在 Billing and Cost Management 確認現行功能與條款。

## 43.14 組起來：Wanderly 的治理全貌

```text
 Management account（極少人登入）
   ├─ Organizations 政策：SCP（Region、保護備份與日誌、禁止自行購買承諾）
   │                     backup policy（依 OU）、tag policy
   ├─ Billing：cost allocation tags 啟用、discount sharing（子公司帳號關閉）
   │          Data Exports（CUR 2.0）──────────────────────────────┐
   │                                                              │
 Audit／Security Tooling 帳號                    FinOps 帳號 ◄──── ┘（複寫）
   ├─ Config aggregator、organization            ├─ 集中購買 Savings Plans／RI
   │  conformance packs（PCI、公司基準）            ├─ Athena + QuickSight 成本儀表板
   ├─ Security Hub CSPM central configuration    ├─ Cost categories、split charges
   │  （依 OU 套用 FSBP、PCI DSS）                 └─ Anomaly Detection、OU 層級 Budgets
   └─ 合規快照定期匯出 ─► Log Archive（Object Lock）
                                                 
 Backup 帳號（亞太：新加坡；歐洲：愛爾蘭）
   └─ 中央 vault：Vault Lock compliance、只允許組織內 copy、獨立 KMS key

 每個 workload 帳號（由 baseline 自動具備）
   ├─ 本地 vault 與 OrgBackupServiceRole（StackSets）
   ├─ Config recorder、Security Hub（自動啟用）
   ├─ 帳號預算（AWS::Budgets::Budget）與 owner 通知
   └─ IaC 預設 tag：cost-center、application、environment、owner、data-classification
```

這張圖把本章的元件放回第 40 章的帳號地圖：**規則**集中在 management account 的 Organizations 政策中；**合規偵測與證據**集中在 Audit 帳號；**成本分析與承諾**集中在 FinOps 帳號；**備份副本**集中在依地區分開的 Backup 帳號；每個 workload 帳號則透過 baseline 自動具備所有前提。稽核前六週，小芸能交出的不再是一堆截圖，而是一組可以查詢的證據：哪些資源有備份、保存期多久、不能被誰刪除；過去十二個月每天的合規分數；歐洲 OU 的每一個資源都在歐盟。

## 43.15 比較與選型

### 治理需求對應工具

| 需求 | 首選 | 容易混淆的選項 |
|---|---|---|
| 所有帳號一致的備份計畫，成員帳號不能改 | Organizations backup policy | StackSets 部署 backup plan（成員可改） |
| 備份在保存期內誰都不能刪 | Backup Vault Lock compliance mode | Vault access policy（管理員可修改 policy） |
| S3 物件法規保存 N 年 | Object Lock compliance mode | Governance mode（可 bypass）、lifecycle（只負責刪除） |
| 訴訟期間凍結特定資料 | Object Lock legal hold／AWS Backup legal hold | 延長 retention（會影響所有物件） |
| 全組織一致的設定合規規則 | Organization conformance pack | 每個帳號自己建 Config rule |
| 全組織的合規結果與跨帳號查詢 | Config aggregator + advanced query | 逐帳號登入 console |
| 依業界標準檢查安全設定、依 OU 差異化 | Security Hub CSPM central configuration | 只啟用 GuardDuty（偵測威脅，不檢查設定） |
| 自動收集證據並對應合規框架 | Audit Manager（既有客戶）；新客戶用 conformance packs + aggregator + Security Hub | AWS Artifact（只提供 AWS 自身的報告） |
| 只能使用特定 Region | SCP `aws:RequestedRegion`／Control Tower Region deny | Route 53 geolocation（只是流量） |
| 規範 tag 值與大小寫 | Tag policy | SCP（適合「必須帶 tag」） |
| 帳單依業務單位分類、分攤共用成本 | Cost categories + split charges | Cost allocation tags（只是維度，不會分攤） |
| 自訂分析、與業務資料 JOIN | CUR 2.0 + Athena + QuickSight | Cost Explorer（無法 JOIN 外部資料） |
| 子公司的承諾不與他人共享 | 對該帳號關閉 discount sharing | Billing Conductor（只改變呈現，不改變折扣套用） |

### 承諾共享的決策

```text
這個帳號需要獨立計算成本或即將離開組織嗎？
├─ 是 → 對它關閉 RI／Savings Plans discount sharing
│        （它的承諾只給自己，也不接收別人的）
└─ 否 → 維持共享，由 FinOps 集中購買
         └─ chargeback 時，團隊要看到怎樣的成本？
              ├─ 實際攤提後成本 → CUR amortized cost（未使用承諾留在 FinOps）
              ├─ 公開價格（折扣留在中央）→ Billing Conductor pricing rules
              └─ 只看趨勢 → Cost Explorer 依 cost category 分組
```

## 43.16 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 所有帳號、包含新帳號，都要有一致的備份，成員不能修改 | Organizations backup policy（搭配 StackSets 部署 vault 與 role） |
| 備份要能承受來源帳號被入侵 | 跨帳號 copy 到獨立 Backup 帳號的 vault + Vault Lock |
| 跨帳號 copy RDS 失敗 | 來源改用 customer managed key 並分享給目的帳號；vault policy 允許 `CopyIntoBackupVault` |
| 備份保存期內任何人（含 root）都不能刪 | Vault Lock compliance mode（冷靜期至少 72 小時） |
| S3 文件保存 7 年不可刪改 | Object Lock compliance mode + default retention |
| 調查期間保留特定物件，期限未定 | Object Lock legal hold |
| PCI 規則一次部署到全組織並看合規分數 | Organization conformance pack |
| 全組織哪些資源不合規，集中查詢 | Config aggregator + advanced query |
| 依 OU 啟用不同的安全標準 | Security Hub CSPM central configuration policy |
| 自動收集證據對應框架（舊題） | Audit Manager；新客戶改用 conformance packs + aggregator + Security Hub |
| 資料只能留在某地區 | Region SCP（`NotAction` 排除全球服務）+ 檢查複寫與 copy 目的地 |
| tag 值大小寫不一致、值不在清單內 | Tag policy（`enforced_for`） |
| 建立資源時沒帶 tag 就拒絕 | SCP + `aws:RequestTag` |
| tag 在 Cost Explorer 看不到 | 在 management account 啟用 cost allocation tags；需要歷史資料時申請 backfill |
| 共用網路帳號的成本分攤給各事業部 | Cost categories split charges |
| 每筆訂房的雲端成本 | CUR 2.0 + Athena，JOIN 業務資料 |
| sandbox 超出預算時自動阻止新建資源 | Budget action 套用 SCP |
| 子公司的 RI 只給自己用 | 對該帳號關閉 discount sharing |

**常見陷阱**：

1. 以為附加 backup policy 就會有備份：政策引用的 vault、IAM role 與 resource type opt-in 都要事先存在。
2. 以為 Vault Lock compliance mode 可以事後調整：冷靜期過後無法縮短保存期或移除鎖定。
3. 以為 Audit Manager 會阻擋或修正設定：它只收集證據；而且目前不再開放新客戶。
4. 以為 tag policy 能強制資源必須帶 tag：它規範的是「帶了的話值要正確」。
5. 以為關閉 discount sharing 只影響「分享出去」：它同時讓該帳號不再接收其他帳號的折扣。
6. 以為 Budgets 是即時的支出開關：帳單資料每天更新數次，budget action 只能盡快止血，不能保證不超支。
7. 以為加密就能滿足資料主權：加密不改變資料所在地。

## 本章重點整理

- 治理可以分成預防、統一設定、偵測與修正、證據、成本責任五個層次，每一層都要有對應的機制並互相補位。
- Organizations backup policy 由中央派送 backup plan 到每個帳號與 Region，成員帳號無法修改；政策引用的 vault、IAM role 與 resource type opt-in 必須由 baseline（例如 StackSets）事先建立。
- Backup policy 以 `@@assign`、`@@append`、`@@remove` 合併成 effective policy，父層可用 `@@operators_allowed_for_child_policies` 禁止子層修改關鍵欄位。
- 備份副本要複製到獨立 Backup 帳號的中央 vault，使用該帳號的 KMS key、只允許組織內帳號 copy 進來，並以 Vault Lock 防止刪除；RDS 類資源跨帳號 copy 需要 customer managed key。
- Object Lock compliance mode 與 Vault Lock compliance mode 在保存期內任何人都無法刪除；應先以 governance mode 驗證，再啟用 compliance mode。
- Legal hold 沒有到期日，適合訴訟或調查；保存要求與個資刪除義務的衝突要在設計階段以資料分類與保存期處理。
- Organization conformance pack 把一組 Config rules 一次部署到全組織；aggregator 與 advanced query 讓 Audit 帳號集中檢視並匯出合規證據。
- Security Hub CSPM 的 central configuration 讓 delegated administrator 依 OU 啟用不同標準，例如全組織 FSBP、支付 OU 再加 PCI DSS。
- Audit Manager 自 2026 年 4 月 30 日起不再開放新客戶，替代方案是 Config conformance packs 加 aggregator 與 Security Hub，並把證據定期匯出到不可竄改的 S3。
- 資料主權要分三層：以 SCP 限制 Region、逐一控制複寫與 copy 的目的地、以 Config 與 CloudTrail 產生證據；加密不改變資料所在地。
- Tag 治理先有字典再談強制：key 統一小寫、值對應公司其他系統、不放個資；tag policy 規範值，SCP 強制必須帶 tag，cost allocation tags 要在 payer 帳號啟用。
- Cost categories 依序評估規則把費用映射成業務類別，`DefaultValue` 量化未分配成本，split charges 以 proportional、even、fixed 分攤共用成本。
- CUR 2.0 透過 Data Exports 匯出到 S3，以 Athena 查詢、QuickSight 呈現，可計算攤提後成本並和業務資料 JOIN 出單位成本。
- 每個帳號都應由 baseline 自動建立預算；sandbox 可用 budget action 套用 SCP 止血，production 通常只通知；異常偵測以帳號與 cost category 為維度。
- RI 與 Savings Plans 先套用到購買帳號、再共享到組織；對某帳號關閉 discount sharing 後，它既不分享也不接收，適合需要獨立損益的子公司。

- A. 用 CloudFormation StackSets 把一份包含 backup plan 的 template 自動部署到 Workloads OU 的每個帳號與 Region
- B. 在每個帳號啟用 AWS Backup Audit Manager，偵測不符合公司標準的 backup plan 後通知帳號 owner 修正

### 練習 43-2｜SAP｜選兩項｜跨帳號 copy 失敗

Wanderly 的 backup policy 會把 recovery point 複製到 Backup 帳號的 `org-central-vault`。EBS 與 DynamoDB 的 copy 都成功，但 `payments-prod` 帳號中 RDS for PostgreSQL 的 copy job 一直失敗。調查發現該 RDS instance 以 `aws/rds` AWS managed key 加密；中央 vault 的 access policy 目前只允許 Backup 帳號自己的 principal。已確認 management account 已啟用 cross-account backup。

哪兩個步驟是讓 RDS copy 成功所必須的？（選兩項）

- A. 修改 `aws/rds` 的 key policy，允許 Backup 帳號使用這把 key
- B. 在中央 vault 的 access policy 中，允許組織內的 principal 執行 `backup:CopyIntoBackupVault`（以 `aws:PrincipalOrgID` 限定）
- C. 把 copy 的目的地改為 Backup 帳號的 default vault
- D. 把 RDS 改以 customer managed key 加密（例如以加密 snapshot copy 改用新 key 後還原），並在該 key 的 key policy 中允許 Backup 帳號使用
- E. 把 RDS 的備份改為 continuous backup，讓 copy 時保留 point-in-time restore 能力

> [!answer]- 答案：B、D
> **A ✗** AWS managed key 的 key policy 無法修改，因此無法分享給其他帳號。這正是 RDS 類資源跨帳號 copy 失敗最常見的原因。
>
> **B ✓** 跨帳號 copy 需要目的 vault 的 access policy 允許來源帳號把 recovery point 複製進來。用 `aws:PrincipalOrgID` 限定組織內帳號，是標準做法。
>
> **C ✗** 跨帳號 copy 不能以目的帳號的 default vault 為目的地，而且這不能解決金鑰問題。
>
> **D ✓** RDS 這類不是由 AWS Backup 完整管理的資源，跨帳號 copy 時來源必須使用可分享的 customer managed key，並在 key policy 中允許目的帳號使用。既有 instance 要透過加密 snapshot copy 改用新 key 再還原。
>
> **E ✗** Continuous backup 複製到其他帳號或 Region 後會變成 snapshot 型備份，不保留 point-in-time restore，也不能解決金鑰與權限問題。
>
> **考點**：SAP-2.2、SAP-2.3｜AWS Backup 跨帳號 copy 的金鑰與 vault policy

### 練習 43-3｜SAP｜單選｜防勒索的備份保存

Wanderly 的資安團隊擔心攻擊者取得 Backup 帳號的管理權限後刪除備份。法規要求支付系統的備份至少保存 365 天，保存期內任何人（包括 Backup 帳號的 root user）都不能刪除或縮短保存期。團隊已經在測試 vault 驗證過保存設定正確，現在要套用到正式的中央 vault。

最合適的做法是什麼？

- A. 對中央 vault 設定 Vault Lock：最短保存 365 天，並設定 `changeable-for-days` 為 3 天，冷靜期結束後即為 compliance mode
- B. 在中央 vault 的 access policy 中加入拒絕 `backup:DeleteRecoveryPoint` 的 statement
- C. 用 SCP 在 Backup 帳號拒絕所有 `backup:Delete*` 動作，只放行資安主管的 role
- D. 對中央 vault 設定 Vault Lock 但不設定 `changeable-for-days`，讓資安主管必要時能移除鎖定

> [!answer]- 答案：A
> **A ✓** 設定 `changeable-for-days` 後，冷靜期（至少 3 天，即 72 小時）一過，Vault Lock 就成為 compliance mode：任何人，包括 root user，都無法刪除保存期內的 recovery point、縮短保存期或移除鎖定。團隊已在測試環境驗證，正好可以直接進入 compliance。
>
> **B ✗** Vault access policy 能拒絕刪除，但擁有帳號管理權限的攻擊者可以先修改 policy 再刪除。
>
> **C ✗** SCP 保留了一個放行的 role，而且 management account 中有權限的人可以修改或移除 SCP；取得該 role 或能修改 SCP 的人仍能刪除，不符合「任何人都不能」。
>
> **D ✗** 不設定 `changeable-for-days` 是 governance mode，有足夠權限的人可以移除鎖定，不符合法規要求。
>
> **考點**：SAP-2.2、SAP-3.2｜Backup Vault Lock compliance mode

### 練習 43-4｜SAA｜單選｜訴訟期間保留資料

Wanderly 把訂單文件存在啟用 versioning 與 Object Lock 的 S3 bucket，預設保存期為 governance mode 3 年。法務部通知：一起消費爭議訴訟需要保留某位客戶的 40 份文件，直到法院結案，結案日期無法預估；其他文件維持原本的保存規則。

> **D ✗** 結案日期無法預估，固定的 retain-until date 可能太短或太長；設得太長也無法提前解除。

### 練習 43-8｜SAP｜單選｜歐洲帳號只能使用歐盟 Region

Wanderly 的歐洲業務帳號都在 Europe OU。合約要求這些帳號的 workload 只能部署在 `eu-central-1` 與 `eu-west-1`。團隊先試著附加一條 SCP：「當 `aws:RequestedRegion` 不是這兩個 Region 時拒絕所有動作」，結果工程師無法管理 IAM role、無法修改 Route 53 記錄，也看不到 Cost Explorer。平台團隊仍需要一條緊急通道。

應如何修正 SCP？

- A. 改用 tag policy，要求 Europe OU 的資源都帶上 `region=eu` tag
- B. 把 SCP 改成 Allow 語法，只允許 `eu-central-1` 與 `eu-west-1` 的動作，並附加到 Root
- C. 保留 Deny 與 `aws:RequestedRegion` 條件，改用 `NotAction` 排除 IAM、Organizations、STS、Route 53、CloudFront、Cost Explorer 等全球服務，並以 `aws:PrincipalARN` 條件放行 break-glass role，附加到 Europe OU
- D. 在 Europe OU 的帳號中，以 IAM permission boundary 限制所有使用者只能在歐盟 Region 操作

> [!answer]- 答案：C
> **A ✗** Tag policy 只規範 tag 的值，不能限制資源建立在哪個 Region。
>
> **B ✗** 附加到 Root 會影響所有 OU，包括亞太的帳號；只允許兩個 Region 的寫法同樣會擋住全球服務。
>
> **C ✓** 全球服務的 API 請求會被視為 `us-east-1` 等特定 Region，所以要用 `NotAction` 排除；同一個 Condition 區塊中加上 `aws:PrincipalARN` 條件保留緊急通道。附加到 Europe OU 只影響歐洲帳號。
>
> **D ✗** Permission boundary 要在每個 role 上設定，帳號管理員可以建立不受限制的 role，無法作為組織層的保證。
>
> **考點**：SAP-1.2、SAP-2.3｜以 SCP 實作資料主權並排除全球服務

### 練習 43-9｜SAP｜選兩項｜資料主權的漏洞

Wanderly 的 Europe OU 已附加只允許歐盟 Region 的 SCP。稽核員檢查後指出兩個問題：一、附加在 Workloads OU（Europe OU 位於其下）的 backup policy 把所有帳號的 recovery point 複製到亞太 Backup 帳號（新加坡）的中央 vault，包含歐洲會員的資料庫備份；二、一張歐洲會員的 DynamoDB global table 原本由亞太團隊建立，replica 在東京與法蘭克福。合約要求歐洲會員個資只能存放在歐盟。

哪兩個做法能修正這些問題？（選兩項）

- A. 調整 backup policy 的附加位置，讓含新加坡 copy action 的政策不再被 Europe OU 繼承（例如改附加到亞太 OU）；為 Europe OU 附加獨立的 backup policy，copy action 指向愛爾蘭的中央 vault，並禁止子層修改這個欄位
- B. 因為 recovery point 已經加密，向稽核員說明加密後的備份不受資料主權限制
- C. 在 Route 53 為歐洲使用者設定 geolocation routing，確保他們只連到法蘭克福
- D. 在新加坡的中央 vault 設定 Vault Lock，確保歐洲備份不會被刪除
- E. 在歐盟的兩個 Region 建立新的歐洲會員 global table，搬移資料後刪除含東京 replica 的舊 table，並以 SCP 防止在歐盟以外建立 replica

> [!answer]- 答案：A、E
> **A ✓** Backup policy 會沿著 OU 階層繼承，只新增一份 Europe 政策並不會移除從上層繼承來、指向新加坡的 copy action，所以要先讓那份政策不再套用到 Europe OU，再為 Europe OU 指定歐盟內的中央 vault，並用繼承控制運算子禁止子層修改，讓歐洲備份留在歐盟。
>
> **B ✗** 加密不改變資料所在地，加密的備份仍是存放在新加坡的歐洲個資。
>
> **C ✗** Geolocation 只影響流量入口，不影響資料複寫到哪裡。
>
> **D ✗** Vault Lock 讓備份更難刪除，反而讓不該存在新加坡的資料更難移除。
>
> **E ✓** Global table 會複寫整張 table，必須重新建立只在歐盟 Region 有 replica 的 table；SCP 讓 Europe OU 的帳號無法在歐盟以外建立資源，防止再次發生。
>
> **考點**：SAP-2.3、SAP-3.2｜資料主權涵蓋備份 copy 與資料庫 replica

### 練習 43-10｜SAA｜單選｜看不到 tag 分組的成本

Wanderly 的工程師三個月前開始在所有 EC2 與 RDS 資源上加上 `cost-center` tag，也在 Organizations 設定了 tag policy 規範值。但財務在 Cost Explorer 中依 tag 分組時，完全找不到 `cost-center` 這個維度。財務也希望看到過去幾個月依 `cost-center` 分組的成本。

應如何處理？

- A. 在每個成員帳號的 Billing console 中啟用 `cost-center` tag
- B. 在 management account 的 Billing console 中把 `cost-center` 啟用為 cost allocation tag，並申請 backfill 回填歷史資料
- C. 在 tag policy 中為 `cost-center` 加上 `enforced_for`，讓 tag 出現在帳單中
- D. 建立 Config 的 `required-tags` 規則，讓不合規的資源出現在 Cost Explorer

>
> **B ✓** Tag 必須在 payer 帳號啟用為 cost allocation tag，才會出現在 Cost Explorer、Budgets 與 CUR。啟用後預設只從之後的資料開始，可以申請 backfill 回填過去最多 12 個月。
>
> **C ✗** `enforced_for` 只是拒絕不合規的 tag 值，和 tag 是否出現在帳單中無關。
>
> **D ✗** Config rule 偵測缺少 tag 的資源，不影響帳單的分組維度。
>

### 練習 43-11｜SAP｜單選｜tag 值不一致

Wanderly 的 CUR 分析發現 `environment` tag 有 `prod`、`Prod`、`production`、`PRD` 等十幾種寫法，tag key 也有 `Environment` 與 `environment` 兩種，導致成本報表無法正確分組。平台團隊希望統一 key 的大小寫，只允許 `prod`、`staging`、`dev`、`sandbox` 四個值，並讓 EC2 instance 與 EBS volume 無法寫入不合規的值；團隊也希望找出既有資源中缺少這個 tag 的項目。

哪個組合最合適？

- A. 以 tag policy 規範 `environment` 的 key 大小寫與允許值，並對 `ec2:instance`、`ec2:volume` 設定 `enforced_for`；搭配 Config 的 `required-tags` 規則找出缺少 tag 的既有資源
- B. 以 SCP 拒絕所有不帶 `environment` tag 的 `RunInstances` 請求，並要求各團隊自行修正既有 tag
- C. 建立 cost category，把十幾種寫法都映射到 `prod` 等四個值，不修改資源上的 tag
- D. 以 Lambda 每天掃描所有帳號的資源，把不合規的 tag 值改成正確的值

> [!answer]- 答案：A
> **A ✓** Tag policy 正是用來規範 key 的大小寫與允許值，`enforced_for` 讓指定資源類型無法寫入不合規的值；tag policy 不會找出缺少 tag 的資源，所以搭配 Config 的 `required-tags` 規則偵測。
>
> **B ✗** SCP 能強制建立時必須帶 tag，但不檢查值是否在允許清單、也不規範大小寫，題目的主要問題是值不一致。
>
> **C ✗** Cost category 可以在報表層暫時修補，但資源上的 tag 仍然混亂，tag 用於政策條件或 backup policy 選取時仍會出錯。
>
> **D ✗** 自建掃描與修正的營運負擔高，也無法在寫入當下阻止不合規的值。
>
> **考點**：SAP-1.5、SAP-3.1｜tag policy 規範值與 Config 偵測缺漏

### 練習 43-12｜SAP｜單選｜共用網路成本的分攤

Wanderly 的 Network 帳號每月約 6 萬美元，包含 Transit Gateway、集中 egress 與 Direct Connect，服務所有事業部。財務要求：每個事業部的成本以帳號與 `application` tag 定義；Network 帳號的費用依各事業部自身成本的比例分攤；報表中要能看到尚未歸屬到任何事業部的成本有多少。團隊希望使用 AWS 原生功能並維持最低營運負擔。

最合適的做法是什麼？

- A. 在 Network 帳號的每個資源上加上所有事業部的 tag，讓 Cost Explorer 自動平分
- B. 用 AWS Billing Conductor 為每個事業部建立 billing group，並把 Network 帳號放進其中一個 billing group
- C. 每月由 FinOps 手動從 Cost Explorer 匯出 Network 帳號費用，在試算表中依比例分攤

>
> **C ✗** 手動分攤能做到，但每月重複、容易出錯，營運負擔最高。
>
> **D ✓** Cost categories 依序評估規則，把共用帳號、各事業部與未分配成本分開；split charge rule 以 `PROPORTIONAL` 依各事業部自身成本比例分攤共用成本；`DefaultValue` 讓未歸屬的金額可見。
>
> **考點**：SAP-1.5｜cost categories 與 split charges

### 練習 43-14｜SAP｜選兩項｜每個帳號的預算控管

哪兩個做法組合起來最能滿足需求？（選兩項）

- C. 在 management account 為 sandbox 帳號的預算設定 budget action，達 100% 時對該帳號套用拒絕建立新 EC2、RDS 資源的 SCP

>
> **E ✗** Anomaly Detection 只發出告警，不會阻止支出，也不是即時的。
>
> **考點**：SAP-1.5、SAP-3.1｜自動化建立帳號預算與 budget actions

- D. 用 SCP 拒絕集團其他帳號使用子公司購買的 RI

### 練習 43-16｜SAP｜單選｜集中購買承諾的 chargeback

Wanderly 由 FinOps 帳號集中購買 Compute Savings Plans，效益在組織內共享。事業部負責人抱怨：在 Cost Explorer 以 unblended cost 看自己的成本時，被 Savings Plans 覆蓋的用量仍以 On-Demand 價格顯示，看不出折扣；另一方面，財務不希望 FinOps 買多而沒用完的承諾被分攤到各事業部。財務要求各事業部的 chargeback 反映實際享受到的折扣。

最合適的做法是什麼？

- A. 以 CUR 2.0 計算各事業部的攤提後成本：被 Savings Plans 覆蓋的用量採用 Savings Plans 的有效成本，承諾本身的費用與未使用部分不分配給事業部，而是留在 FinOps 帳號
- B. 把 Compute Savings Plans 改由各事業部的帳號自行購買
- C. 對所有事業部帳號關閉 discount sharing，讓每個帳號只看到自己的成本
- D. 改用 Billing Conductor 的 pricing rule，讓所有事業部都以 On-Demand 價格計費

> [!answer]- 答案：A
> **A ✓** 攤提後成本（amortized）把 Savings Plans 的效益分配到實際使用它的用量上，事業部看到的是享受折扣後的成本；承諾費用與未使用部分不分配，留在購買的 FinOps 帳號，符合「買多的不懲罰事業部」。
>
> **B ✗** 各自購買容易重複或買錯，整體使用率下降，也違背集中購買策略。
>
> **C ✗** FinOps 帳號自己沒有運算用量，關閉事業部帳號的共享後，集中購買的承諾就完全無法被使用。
>
> **D ✗** 以 On-Demand 價格計費會把折扣全部留在中央，與「反映實際享受到的折扣」相反；它適合想讓折扣留在中央的情況。
>
> **考點**：SAP-1.5、SAP-2.6｜集中承諾的 amortized chargeback
