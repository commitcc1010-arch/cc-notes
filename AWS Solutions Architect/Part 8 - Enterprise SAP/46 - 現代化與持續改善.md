# 第 46 章　現代化與持續改善既有系統：Strangler Fig、拆分 Monolith 與 SAP Domain 3

> [!abstract] 本章地圖
> **你會學到**：
> - 說清楚「遷移」和「現代化」的差別，以及為什麼大爆炸式重寫幾乎總是最危險的選項
> - 把自管在 EC2 上的資料庫、訊息佇列、排程與檔案服務換成受管服務，並判斷相容性與取捨
> - 用 strangler fig 模式搭配 ALB、API Gateway 或 CloudFront 逐步取代 monolith，而且每一步都能回滾
> - 決定 monolith 的拆分順序與服務邊界，處理最困難的資料庫拆分（outbox、CDC、saga）
> - 在 EC2、ECS／Fargate、EKS 與 Lambda 之間為每個元件選擇運算平台
> - 用 Well-Architected review、Trusted Advisor、Compute Optimizer 找出改善點，並解出 SAP Domain 3 的五類「改善既有系統」題目
>
> **前置知識**：第 19 章（Lambda）、第 21 章（containers）、第 32–33 章（非同步解耦、saga）、第 38–39 章（營運自動化、成本最佳化）、第 44–45 章（遷移策略與工具）
> **考試比重**：SAA ★☆☆（Domain 2、4）｜SAP ★★★（Domain 3 持續改善、Domain 4 現代化）

## 46.1 故事：搬上來了，問題也跟著搬上來

第 44、45 章的 W6 裡，Wanderly 把併購旅行社的核心訂房系統 **TourBook** 搬到了 AWS：應用伺服器用 MGN 原封不動地 rehost 到 EC2，背後的核心 Oracle 資料庫則以 DMS 搬到 RDS for Oracle Multi-AZ（replatform，BYOL）。TourBook 是一個跑了十五年的 Java 應用程式：團體行程查詢、訂位、付款、出團通知、對帳報表全部在同一個程式裡。遷移當晚切換順利，所有人都鬆了一口氣。

第 44 章的 7Rs 分類裡，只有團體行程報價引擎（24 台 VM）被列為 refactor：它不改就無法和 Wanderly 的訂房平台整合，所以由另一個小組在遷移後段一邊搬、一邊用本章的 strangler fig 模式改寫。TourBook 當時刻意只做 rehost，因為資料中心退場的時程不允許同時重構；現在系統已經離開機房，輪到它了。

半年後，平台負責人阿哲在季度檢討會上列出一張清單：

- TourBook 每兩週才能部署一次，每次要在凌晨停機四小時，因為整個程式只能一起更新。
- 每天凌晨兩點的對帳批次會把 Oracle 的 CPU 吃滿，這時候的訂位請求延遲從 300 毫秒變成 8 秒。
- 訂位確認與出團通知靠兩台 EC2 上自管的 RabbitMQ 叢集，作業系統 patch、版本升級與故障處理都靠一位工程師手動進行，他下個月要休育嬰假。
- 為了撐住每年兩次的旅展檔期，TourBook 的 EC2 一直維持尖峰容量，平時 CPU 使用率不到 15%。
- 安全團隊發現程式設定檔裡寫著資料庫密碼，而且已經三年沒換。

CTO 的回應很直接：「不要跟我說要花兩年全部重寫。我要每一季都看得到改善，而且任何一步出問題都能退回去。」

這一章要回答的就是這件事：一個已經在 AWS 上運作的系統，要怎麼**一步一步變好**。前半章談**現代化（modernization）**，也就是改變系統的結構，讓它更容易演進；後半章談**持續改善（continuous improvement）**，也就是建立一套機制，持續找出安全、可靠性、效能、成本與營運上的缺口並修正。這兩件事正是 SAP-C02 Domain 3（Continuous Improvement for Existing Solutions）與 Domain 4 後半（modernization）的核心。

## 46.2 現代化是什麼：為什麼不直接重寫

**現代化**是指改變既有系統的架構、平台或開發方式，讓它更容易修改、擴展與維運。它和**遷移**不同：遷移把系統從 A 地搬到 B 地，現代化則是改變系統本身。第 44 章的 7Rs 裡，rehost 是純遷移，replatform 與 refactor 才開始涉及現代化。很多企業的路線是「先 rehost 離開資料中心，再在 AWS 上逐步現代化」，因為資料中心合約到期的時間壓力，通常比改造程式的時間短得多。

### 大爆炸重寫的陷阱

最直覺的做法是「另起爐灶，用微服務重寫一個新 TourBook，寫好後一次切換」。這種做法稱為 **big-bang rewrite（大爆炸式重寫）**，失敗率很高，原因有三個：

1. **舊系統的行為沒有完整文件。** 十五年來累積的特殊規則（某家航空公司的團體票要提前 21 天開票、某種折扣不能和早鳥價併用）只存在於程式碼裡。重寫時漏掉一條，上線當天就會出錯。
2. **舊系統不會停下來等你。** 重寫期間業務還在提新需求，團隊要同時改兩套系統，或凍結舊系統讓業務停擺。
3. **價值要到最後一天才出現。** 兩年內沒有任何改善上線，最後一次切換的風險又集中在一個晚上。

所以 AWS 與業界推薦的方式是**漸進式現代化**：每次只替換一小塊，新舊並存，每一步都可以獨立上線、量測與回滾。

### 現代化的四條路徑

現代化不等於「全部改成微服務」。對每個元件，可以依投入程度選擇不同路徑：

| 路徑 | 做什麼 | 程式修改 | 典型效益 |
|---|---|---|---|
| 換成受管服務 | 自管資料庫、佇列、快取換成 RDS、Amazon MQ、ElastiCache | 少（改連線字串、少量相容性調整） | 省下 patch、備份、高可用的維運工作 |
| Containers 化 | 把應用程式打包成 container，跑在 ECS 或 EKS | 少到中 | 部署一致、資源密度高、可以快速擴縮 |
| Serverless 化 | 事件驅動的片段改成 Lambda、Step Functions | 中到多 | 不用管伺服器、按用量付費、自動擴展 |
| 拆分 monolith | 依業務能力拆成獨立服務與資料 | 多 | 各團隊獨立部署、各自擴展、故障隔離 |

阿哲的策略是：**先做投入小、效益確定的事（受管服務），用省下來的人力去做投入大的事（拆分）**。接下來就依這個順序展開。

## 46.3 從自管到受管服務：最快見效的現代化

TourBook 的核心 Oracle 在遷移時已經換成 RDS for Oracle，但它周邊還有不少自管元件：兩台 EC2 上的 RabbitMQ、跑對帳批次的常駐 EC2、寫在設定檔裡的密碼。凡是自管的東西，作業系統、軟體 patch、備份、高可用與故障切換全部是 Wanderly 的責任。第 2 章的 shared responsibility model 在這裡最具體：**換成受管服務，等於把責任線往上推**，AWS 接手底層的維運工作，團隊只需要管資料模型、查詢效能與存取控制。

### 常見的替換對照

| 現在自管的東西 | 受管替代方案 | 需要注意的相容性 |
|---|---|---|
| EC2 上的 MySQL／PostgreSQL | RDS 或 Aurora（第 26 章） | 沒有作業系統存取權；部分 superuser 權限受限 |
| EC2 上的 Oracle／SQL Server | RDS for Oracle／SQL Server；需要作業系統或客製權限時用 RDS Custom | 授權模式（License Included 或 BYOL，第 44 章）；部分功能不支援 |
| Oracle 換成開源引擎 | Aurora PostgreSQL，用 DMS Schema Conversion／SCT 轉換 schema 與程式碼（第 45 章） | PL/SQL 改寫是主要工作量 |
| ActiveMQ／RabbitMQ | Amazon MQ | 支援原協定（AMQP、MQTT、STOMP、OpenWire 等），程式幾乎不用改 |
| 自建佇列且願意改程式 | SQS／SNS（第 32 章） | 要改用 AWS SDK，換來近乎無限擴展與更低營運負擔 |
| 自建 Kafka | Amazon MSK（第 31 章） | Kafka API 相容 |
| EC2 上的 Redis／Memcached | ElastiCache（第 28 章） | 部分管理指令受限 |
| 自建 Elasticsearch | Amazon OpenSearch Service | 版本相容性需確認 |
| Windows 檔案伺服器 | FSx for Windows File Server（第 24 章） | 需要 Active Directory 整合 |
| Linux NFS 伺服器 | EFS 或 FSx 系列 | 效能模式選擇 |
| EC2 上的 cron 排程 | EventBridge Scheduler 觸發 Lambda、ECS task 或 Step Functions | 長時間工作不適合 Lambda（15 分鐘上限） |
| 自建 Kubernetes | Amazon EKS | 控制平面由 AWS 管理，worker 可選 Fargate 或受管 node group |
| 設定檔裡的密碼 | Secrets Manager，搭配自動輪替（第 15 章） | 應用程式要改成執行時讀取 |
| Bastion host | Systems Manager Session Manager（第 38 章） | 機器需要 SSM agent 與網路路徑 |

讀這張表時，抓住一個判斷原則：**題目強調「程式不能修改」或「最少程式變更」時，選協定相容的受管服務（Amazon MQ、MSK、RDS 同引擎）；強調「最大擴展性、最低營運負擔」且允許改程式時，選雲原生服務（SQS、DynamoDB、Lambda）。**

### TourBook 的第一步：資料庫已在遷移時換成受管服務，接著換掉其餘自管元件

資料庫這一步其實在遷移的 W6 就做了。當時評估過兩個選項：直接換到 RDS for Oracle（同引擎、改連線字串即可），或一路轉到 Aurora PostgreSQL（免 Oracle 授權費，但 300 多支 PL/SQL stored procedure 要改寫）。資料中心退場有硬期限，而且 TourBook 的拆分計畫會在之後把大部分邏輯搬出 Oracle，在遷移時投入大量人力改寫 PL/SQL 並不划算，所以選擇 **RDS for Oracle Multi-AZ**：

- 用 DMS 的 full load + CDC（第 45 章）把資料同步到 RDS，切換時只需要短暫停寫。
- Multi-AZ 讓 standby 切換變成自動，不必再由 DBA 手動處理。
- 自動備份與 point-in-time recovery 取代手寫的備份腳本。

現代化階段的第一步，就是用同樣的思路處理剩下的自管元件：RabbitMQ 換成協定相容的 **Amazon MQ for RabbitMQ**（程式只改連線端點與憑證），設定檔裡的資料庫密碼搬進 Secrets Manager 並開啟自動輪替，順便解決安全團隊的發現。這些步驟都沒有改變 TourBook 的結構，但三個月內就把「中介軟體維運」從團隊的待辦清單上移除。後續等到大部分邏輯被拆出去，剩下的少量 Oracle 程式再評估轉 Aurora PostgreSQL。

> [!warning] 常見誤解
> 「換成受管服務就沒有責任了。」受管服務仍需要你決定 instance 大小、參數、備份保存期、加密、網路與 IAM 權限。例如 RDS 的 Multi-AZ 需要你自己開啟，自動備份保存期需要你設定，查詢寫得不好造成的效能問題也不會被 AWS 修好。受管服務移走的是**底層重複性維運工作**，不是架構決策。

> [!tip] 考試提示
> 「資料庫需要作業系統層級存取或安裝第三方代理程式，但仍希望 AWS 處理備份與自動化」→ **RDS Custom**（支援 Oracle 與 SQL Server）。「需要完全控制」且不在乎維運負擔 → EC2 自管。「不需要作業系統存取」→ 一般 RDS。

## 46.4 Strangler Fig：讓新系統慢慢包住舊系統

受管服務解決了維運負擔，但沒有解決「每兩週才能部署一次」的問題：TourBook 仍然是一整塊程式。要拆分它，第一個要學的模式是 **strangler fig（絞殺榕）**。

這個名字來自一種熱帶植物：絞殺榕的種子落在大樹上，根往下長、慢慢包住宿主，多年後宿主枯死，原地剩下一棵由絞殺榕構成的樹。軟體版本的做法是：在舊系統前面放一層**路由門面（facade）**，所有請求都先經過它；每完成一個新功能，就把對應的請求改送到新服務；舊系統負責的範圍越來越小，最後可以退役。

### 它怎麼運作

```text
                    使用者／合作夥伴
                           │
                           ▼
        ┌────────────────────────────────────┐
        │ ① 路由門面（ALB listener rules／      │
        │    API Gateway／CloudFront behaviors） │
        └───┬──────────────┬──────────────┬───┘
            │ /search/*    │ /notify/*    │ 其他所有路徑
            │ ② 90% → 新   │ ③ 100% → 新  │ ④
            │   10% → 舊   │              │
            ▼              ▼              ▼
     ┌────────────┐ ┌────────────┐ ┌─────────────────────┐
     │ 新：搜尋服務 │ │ 新：通知服務 │ │ 舊：TourBook monolith │
     │ ECS Fargate │ │ Lambda     │ │ EC2（範圍逐步縮小）    │
     └─────┬──────┘ └─────┬──────┘ └──────────┬──────────┘
           │ ⑤ 讀取資料    │                   │
           ▼              ▼                   ▼
     OpenSearch    ◄──── ⑥ 事件／CDC 同步 ──── RDS for Oracle
```

① 所有流量先經過路由門面。在 AWS 上最常用的是 **ALB 的 listener rules**（依路徑、host、header 轉送到不同 target group，第 10 章）、**API Gateway**（依 resource 與 method 整合到不同後端，第 20 章），或 **CloudFront 的 cache behaviors**（依路徑轉到不同 origin，第 11 章）。客戶端完全看不到後面換了什麼。

② 新的搜尋服務上線時，先用 ALB 的 **weighted target groups（加權目標群組）** 只分 10% 流量過去，觀察錯誤率與延遲，再逐步提高到 100%。這和第 37 章的 canary 部署是同一個概念。

③ 已經穩定的功能（通知）100% 由新服務處理，舊系統裡對應的程式可以刪除。

④ 還沒拆出來的功能照舊由 monolith 處理，業務不受影響。

⑤⑥ 新服務需要的資料，一開始通常仍然在舊資料庫裡。常見做法是用 DMS 的 CDC 或應用程式發出的事件，把資料同步到新服務自己的資料存放區。46.6 節會詳細討論這件事。

### 為什麼它能降低風險

- **每一步都能回滾**：新服務出問題，只要把路由規則改回指向舊系統，幾秒內就恢復。這是 CTO「任何一步出問題都能退回去」的答案。
- **價值提早出現**：搜尋服務第一季就上線，旅展期間可以獨立擴展。
- **舊系統仍在運作**：不用凍結業務需求。

### 防腐層（anti-corruption layer）

新服務常常需要呼叫舊系統（例如新的搜尋服務要查舊系統的團體行程規則）。如果新服務直接使用舊系統雜亂的資料模型，舊系統的設計問題就會「感染」新服務。**Anti-corruption layer（防腐層）** 是夾在兩者中間的一層轉換程式：它把舊系統的資料格式與呼叫方式翻譯成新服務定義的乾淨介面。等舊系統退役，只需要拿掉防腐層，新服務的核心程式不必改。

### 另一種切入方式：不改舊程式，從事件延伸

有時候舊系統根本不能改（例如是買來的套裝軟體）。這時可以讓舊系統把事件送出來（從資料庫 CDC、應用程式日誌，或在少數位置加一行發送事件的程式），新功能訂閱這些事件獨立運作。例如每筆訂位寫入 Oracle 後，DMS 把變更送到 Kinesis，新的「行前提醒」服務訂閱這些變更並用 EventBridge Scheduler 安排通知。這種「leave and layer（保留舊系統、在外面加層）」的方式不需要碰舊程式碼。

> [!warning] 常見誤解
> 「Strangler fig 就是在前面放一個 load balancer。」路由門面只是工具，真正的工作是：找出可以獨立出來的功能邊界、處理資料同步、建立回滾機制、最後**真的把舊程式碼刪掉**。只加新服務卻從來沒有退役舊功能，最後得到的是同時維護兩套系統的成本。

## 46.5 拆分順序：先拆哪一塊？

有了 strangler fig 這個「怎麼替換」的方法，接下來的問題是「先替換什麼」。拆錯了第一塊，團隊會在最困難的地方耗掉半年，然後失去信心。

### 用業務能力劃邊界，不是用技術層

新手最常見的拆法是依技術層拆：「前端一個服務、商業邏輯一個服務、資料存取一個服務」。這樣拆完，任何一個功能修改仍要同時改三個服務，部署還是綁在一起。

正確的邊界是**業務能力（business capability）**：搜尋行程、管理訂位、處理付款、發送通知、產生報表。每個服務擁有一項業務能力的完整邏輯與資料。Domain-driven design（領域驅動設計）把這種邊界稱為 **bounded context（限界上下文）**：在一個邊界內，「訂位」這個詞有明確且一致的意思；跨邊界時，透過明確的 API 或事件溝通。

### 挑選第一塊的評分方式

阿哲的團隊用第 44 章遷移時收集的相依資料、X-Ray 的呼叫關係圖（第 36 章），加上程式碼分析，為每個候選功能打分：

| 候選功能 | 與其他模組的耦合 | 變更頻率 | 獨立擴展需求 | 業務價值 | 判斷 |
|---|---|---|---|---|---|
| 照片縮圖處理 | 低（只讀寫檔案） | 低 | 高（旅展時大量上傳） | 中 | 第一批：最容易、能建立信心 |
| 行程搜尋 | 低（唯讀） | 高 | 高（流量占 70%） | 高 | 第一批：價值最高 |
| 出團通知 | 低（事件驅動） | 中 | 低 | 中 | 第二批 |
| 對帳報表 | 中（大量讀取） | 低 | 尖峰集中在凌晨 | 中 | 第二批：先改讀 read replica |
| 付款 | 中 | 中 | 中 | 高 | 第三批：牽涉 PCI DSS，需完整設計 |
| 訂位核心 | 高（所有模組都依賴） | 高 | 中 | 高 | 最後：等周邊都拆完，核心自然變小 |

從這張表可以歸納出拆分順序的原則：

1. **先拆耦合低、邊界清楚的邊緣功能**，用它建立 CI/CD、監控、資料同步的基礎設施與團隊經驗。
2. **在邊緣功能中，優先挑有明確效益的**：流量大、需要獨立擴展、或變更最頻繁、最常卡住部署的模組。
3. **最核心、最多模組依賴的部分最後拆。** 周邊功能拆完後，核心剩下的程式少了很多，拆起來也簡單得多。
4. **讀取路徑比寫入路徑容易拆。** 唯讀的搜尋可以用同步過來的資料副本運作；寫入路徑牽涉交易一致性，要等資料拆分的機制成熟。

### 小心「分散式 monolith」

如果拆出來的服務仍然共用同一個資料庫、互相同步呼叫一長串、必須一起部署，就得到了**分散式 monolith（distributed monolith）**：擁有微服務的所有複雜度（網路延遲、部分失敗、分散式除錯），卻沒有任何獨立部署的好處。判斷方式很簡單：**一個服務能不能在不通知其他團隊的情況下單獨部署？** 不能的話，邊界就還沒切乾淨。

> [!note] 團隊結構也是架構
> Conway's law 指出系統的結構會反映組織的溝通結構。如果搜尋服務和訂位服務由同一個團隊維護、共用同一個發布排程，它們很快會長回一個 monolith。拆分服務時，通常也要讓每個服務有一個明確的擁有團隊。

## 46.6 拆資料庫：現代化最難的一段

把程式拆開相對容易，把資料拆開才是真正的難關。TourBook 的 Oracle 裡有 400 張表，訂位、付款、行程、會員的資料互相 join，報表直接查所有表。如果新服務都繼續讀寫這個資料庫，任何一個 schema 修改都可能讓別的服務壞掉，這就是 **shared database（共享資料庫）反模式**。

目標是 **database per service（每個服務擁有自己的資料）**：其他服務只能透過 API 或事件取得資料，不能直接讀寫別人的表。這樣每個服務可以自由修改 schema，也能選擇最適合的資料庫類型（搜尋用 OpenSearch、購物車用 DynamoDB、帳務仍用關聯式資料庫，第 29 章）。

### 逐步拆分的步驟

```text
階段 1：程式拆開，資料仍共用         階段 2：邏輯分離
┌────────┐ ┌────────┐              ┌────────┐      ┌────────┐
│ 搜尋服務 │ │ 訂位核心 │              │ 搜尋服務 │ API  │ 訂位核心 │
└───┬────┘ └───┬────┘              └───┬────┘◄────►└───┬────┘
    └────┬─────┘                       │               │
         ▼                             ▼               ▼
   ┌───────────┐                 ┌──────────────────────────┐
   │ Oracle    │                 │ Oracle：schema search ／ │
   │ 所有表混用 │                 │ schema booking，禁止跨 join│
   └───────────┘                 └──────────────────────────┘

階段 3：實體分離，用事件或 CDC 同步
┌────────┐                       ┌────────┐
│ 搜尋服務 │ ◄── 訂位變更事件 ───── │ 訂位核心 │
└───┬────┘   （outbox／CDC）      └───┬────┘
    ▼                                 ▼
 OpenSearch                      RDS／Aurora
```

**階段 1**：程式先拆開，資料庫暫時共用。這是可以接受的過渡狀態，但要明確標記「哪些表屬於哪個服務」。

**階段 2**：邏輯分離。每個服務只能存取自己的 schema，跨服務的資料改用 API 取得。這一步最痛苦，因為所有跨模組的 SQL join 都要改寫成「先呼叫 API 再組合」，但它讓第三步變成單純的搬遷。

**階段 3**：實體分離。服務的資料搬到自己的資料庫（DMS 可以只搬特定 schema），其他服務需要的資料副本透過事件同步。

### 雙寫問題與 transactional outbox

訂位核心建立一筆訂位後，要同時「寫入自己的資料庫」並「發出 BookingCreated 事件」給搜尋服務。如果程式先寫資料庫、再呼叫 SNS 發事件，中間程式當掉，資料庫有訂位但事件沒發出去，搜尋服務的資料就永遠不一致。這稱為 **dual-write problem（雙寫問題）**。

**Transactional outbox（交易式寄件匣）** 的解法是：在同一個資料庫交易裡，同時寫入訂位資料與一筆「待發送事件」到 outbox 表；另一個程序讀取 outbox 表並把事件送出，送成功後標記完成。因為兩筆寫入在同一個交易裡，要嘛都成功、要嘛都失敗。在 AWS 上，讀取 outbox 的程序可以是：

- DMS 的 CDC 任務，把 outbox 表的新增資料送到 Kinesis；
- 如果服務用 DynamoDB，直接用 **DynamoDB Streams** 觸發 Lambda，DynamoDB 的寫入本身就會產生變更事件，不需要另外的 outbox 表。

消費端要設計成**冪等（idempotent）**：同一個事件收到兩次，結果和收到一次相同，因為事件傳遞通常保證「至少一次」。

### 跨服務交易與 saga

拆分後，「訂位 → 扣庫存 → 付款」不再是同一個資料庫交易。第 33 章介紹的 **saga** 把它變成一連串本地交易，任何一步失敗就執行前面步驟的**補償動作**（取消訂位、釋放庫存）。AWS 上常用 Step Functions 編排 saga，因為它把每一步的狀態、重試與補償都記錄下來，出問題時能看到停在哪一步。

### 報表怎麼辦？

資料拆散後，跨服務的報表不能再一條 SQL 搞定。常見解法是 **CQRS（命令查詢職責分離）** 的精神：寫入走各服務自己的資料庫，各服務把變更事件送到資料湖（S3 + Glue + Athena，或 Redshift，第 30 章），報表從那裡查。TourBook 凌晨的對帳批次搬到 Redshift 之後，訂位資料庫的 CPU 尖峰也一起消失了。

> [!tip] 考試提示
> 「拆分 monolith 後要讓資料庫變更可靠地通知其他服務，且不能遺失事件」→ transactional outbox 或 CDC（DMS、DynamoDB Streams）。「跨多個服務的業務流程需要失敗時回復」→ saga + Step Functions。「多個服務共用同一個資料庫造成 schema 變更互相影響」→ database per service。

## 46.7 Containers 還是 Serverless：為每個元件選運算平台

服務邊界與資料都規劃好了，下一個問題是「新服務跑在哪裡」。這不是全公司只能選一種的題目，而是**每個元件依它的特性各自選擇**。

### 判斷的幾個問題

1. **它是長時間執行的程序，還是由事件觸發的短工作？** 單次執行超過 15 分鐘的工作不能放 Lambda（第 19 章），要用 ECS／Fargate task、AWS Batch 或 Step Functions 拆成多步。
2. **流量是穩定的，還是忽高忽低、常常是零？** 間歇性的流量最適合 Lambda 按次計費；穩定高流量時，containers 或 EC2 搭配 Savings Plans 通常更便宜。
3. **程式能不能改？** 現有的 Java 或 .NET 應用程式通常可以「原封不動」打包成 container；改成 Lambda 則常常需要重新設計啟動方式、連線管理與狀態處理。
4. **團隊是否需要 Kubernetes？** 已有 Kubernetes 經驗、需要跨雲或地端一致的工具鏈、或要使用 Kubernetes 生態系的工具時選 EKS；否則 ECS 的學習與維運負擔較低。
5. **需不需要管理伺服器？** 不想管 EC2 節點的 patch 與容量時，ECS 或 EKS 搭配 **Fargate**，每個 task 或 Pod 由 AWS 提供運算資源。

| 平台 | 適合 | 不適合 | 營運負擔 |
|---|---|---|---|
| EC2（含 ASG） | 需要特定作業系統設定、授權綁定主機、尚未容器化的應用 | 想減少伺服器維運 | 高 |
| ECS on EC2 | 大量穩定流量、需要 GPU 或特殊 instance、想用 Savings Plans 壓成本 | 不想管節點 | 中 |
| ECS on Fargate | 大多數無狀態 web 服務與 worker，不想管節點 | 需要特殊核心參數或 privileged container | 低 |
| EKS（Fargate 或 node group） | 需要 Kubernetes API、可攜性、既有 Helm／operator 生態 | 小團隊、沒有 Kubernetes 經驗 | 中到高 |
| Lambda | 事件驅動、短時間、流量不穩定的工作 | 超過 15 分鐘、需要持續連線、極穩定高流量 | 最低 |

### TourBook 各元件的選擇

- **照片縮圖**：S3 上傳事件觸發 Lambda，處理時間只有幾秒，旅展時自動擴展，平時幾乎零成本。
- **行程搜尋**：穩定高流量、需要常駐連線到 OpenSearch，選 **ECS on Fargate**，搭配 target tracking auto scaling。
- **出團通知**：EventBridge Scheduler 在出發前三天觸發 Step Functions，依旅客偏好呼叫 SNS 或 SES。
- **對帳報表**：改成每天把資料匯出到 S3，用 Glue 與 Athena 處理，不需要任何常駐伺服器。
- **剩下的 monolith**：先容器化放到 ECS，好處是部署變成替換 task、不用再停機四小時；等它逐漸被拆小。

### 把舊應用程式容器化

容器化一個既有的 Java 或 .NET 應用，大致步驟是：把應用程式與執行環境寫成 Dockerfile、把設定與密碼從檔案移到環境變數或 Secrets Manager、把本機檔案存放改成 S3 或 EFS、把 session 從記憶體移到 ElastiCache 或 DynamoDB（讓 container 可以隨時被替換），最後推到 Amazon ECR 並用 ECS task definition 部署。AWS 過去提供 App2Container 這類命令列工具，自動分析伺服器上執行中的 Java 與 ASP.NET 應用並產生 Dockerfile 與部署範本；不過依 AWS 文件，App2Container（以及 Porting Assistant for .NET 等 .NET 現代化工具）自 2025 年 11 月 7 日起不再對新客戶開放，新專案改用以生成式 AI 協助程式轉換的 AWS Transform。舊題目若出現 App2Container，理解它是「不需要原始碼就能把既有應用打包成 container」的工具即可；考試重點在於理解「容器化需要把狀態移出 container」這個原則，而不是工具細節。

> [!warning] 常見誤解
> 「Serverless 一定比較便宜。」Lambda 按請求數與執行時間計費，對間歇流量非常划算；但對全天穩定的高流量，同樣的運算量用 Fargate 或 EC2 加 Savings Plans 常常更便宜。另一個常見問題是大量 Lambda 同時連線到 RDS 造成連線數爆滿，要用 **RDS Proxy** 共用連線池。

## 46.8 現代化之後：部署、觀測與平台

拆出服務只是開始。服務從一個變成十個，如果每個團隊都要自己想辦法寫部署腳本、設定監控、申請網路，複雜度很快會壓垮團隊。

### 每個新服務的基本配備

- **IaC 與 CI/CD**（第 37 章）：每個服務有自己的 pipeline，可以獨立部署；ECS 用內建的 blue/green 部署或 CodeDeploy 做 blue/green、canary，Lambda 用 alias 的流量權重。
- **可觀測性**（第 36 章）：統一的日誌格式、CloudWatch metrics 與 alarm、X-Ray 或 OpenTelemetry 分散式追蹤。服務拆開後，一個請求會經過五個服務，沒有 trace 幾乎無法找到變慢的那一段。
- **Feature flag**：用 AWS AppConfig 管理功能開關，新邏輯可以先對內部員工開啟，出問題時關掉開關就好，不需要重新部署。
- **API 與事件的版本管理**：新增欄位要向後相容；必須破壞相容時，同時提供新舊版本一段時間，等所有消費者都升級再移除。

### Platform team 與 golden path

SAP 等級的現代化是幾十個團隊、上百個服務一起進行。常見做法是成立 **platform team（平台團隊）**，把上述基本配備做成可自助使用的範本（例如 Service Catalog 產品、CDK construct 或 Control Tower 的 account baseline，第 40 章），稱為 **golden path（黃金路徑）**：產品團隊用這個範本建立新服務，就自動擁有 pipeline、監控、日誌、IAM 權限邊界與網路設定。平台團隊不替產品團隊寫程式，而是降低「做對的事」的成本。

## 46.9 持續改善：怎麼找出下一個該改的地方

現代化是一場有計畫的改造；**持續改善**則是日常機制：系統上線後，負載、成本、安全威脅、AWS 新功能都在變，今天合理的設計半年後可能已經不是最好的。重點是**有系統地找出改善點、排出優先順序、驗證效果**，而不是等出事才改。

### 改善迴圈

```text
   ┌──────────────────────────────────────────────────────────┐
   │                                                          │
   ▼                                                          │
① 建立基準 ──► ② 找出缺口 ──► ③ 排序 ──► ④ 小步變更 ──► ⑤ 量測驗證
 SLO、延遲、     WA review、    業務影響 ×    可回滾、      和基準比較，
 錯誤率、        Trusted        風險 ×        有 owner、    保存 milestone
 單位成本        Advisor、      投入成本      有期限
                Compute
                Optimizer、
                Security Hub
```

① **建立基準（baseline）**：先量清楚現況，包括關鍵使用者流程的 SLO、p99 延遲、錯誤率、部署頻率、事故次數，以及**單位成本**（例如每筆訂位的 AWS 成本）。沒有基準，就無法證明改善有效，也無法發現改善帶來的副作用。

② **找出缺口**：用下面介紹的工具與審查找出風險。

③ **排序**：依業務影響、風險高低與投入成本決定先做哪些。不是所有發現都要修；有些風險可以記錄為「接受」並設定複查日期。

④ **小步、可回滾地變更**：每個改善項目有負責人、期限與驗收條件。

⑤ **量測驗證**：和基準比較，確認真的變好，並保存結果作為下一輪的起點。

### 找改善點的工具

| 工具 | 回答什麼問題 | 重點 |
|---|---|---|
| **AWS Well-Architected Tool**（第 38 章） | 這個 workload 在六大 pillar 有哪些高風險設計？ | 以 workload 為單位審查，產生 high／medium risk issues 與改善計畫，用 milestone 追蹤進度；可用 custom lens 加入公司規範 |
| **AWS Trusted Advisor**（第 38 章） | 帳號裡有沒有閒置資源、開放的 port、接近上限的 quota、單 AZ 部署？ | 完整檢查需要 Business 以上的 Support 方案；可透過 Organizations 彙整多帳號 |
| **AWS Compute Optimizer** | EC2、Auto Scaling group、EBS、Lambda、ECS on Fargate、RDS 的規格是否合適？ | 用機器學習分析 CloudWatch 歷史指標，給出縮小、放大或換 instance 家族（例如 Graviton）的建議 |
| **Cost Explorer／Cost Optimization Hub**（第 39 章） | 錢花在哪裡、可以買多少 Savings Plans？ | Rightsizing 與承諾折扣建議 |
| **Security Hub、Config、Inspector、GuardDuty**（第 16 章） | 哪些資源不符合安全標準、有沒有漏洞與威脅？ | 持續偵測並集中彙整 findings |
| **CloudWatch、X-Ray**（第 36 章） | 哪一段最慢、哪裡錯誤最多？ | 用真實流量找出效能瓶頸 |
| **AWS Fault Injection Service**（第 34 章） | 系統真的撐得過 AZ 故障嗎？ | 主動注入故障驗證可靠性假設 |

### Compute Optimizer 的幾個細節

**Compute Optimizer** 需要先 **opt-in**（啟用），可以在 Organizations 的 management account 為所有成員帳號一次啟用。它預設分析 14 天的 CloudWatch 指標；付費的 **enhanced infrastructure metrics**（適用於 EC2、Auto Scaling group 中的 instance 與 RDS DB instance）可以把回溯期延長到最多 93 天（約三個月），適合有月週期的 workload（例如月底結帳尖峰）。

有一個常考的陷阱：EC2 的**記憶體使用率**不在預設的 CloudWatch 指標裡。要讓 Compute Optimizer 把記憶體納入考量，必須在 instance 上安裝 **CloudWatch agent** 回報記憶體指標（或從支援的外部監控工具匯入指標）。否則它只看 CPU、網路與磁碟，可能建議一個記憶體不夠的較小規格。

Compute Optimizer 的建議是「依過去的使用情況」推算，不知道下個月有旅展。阿哲的團隊因此規定：採用縮小規格的建議前，要先確認觀測期間涵蓋了業務尖峰，並在 staging 用負載測試驗證，再分批套用到 production。

> [!tip] 考試提示
> 「找出規格過大的 EC2 並建議合適的 instance type，且要考慮記憶體」→ Compute Optimizer + CloudWatch agent。「系統性審查 workload 的架構風險並追蹤改善」→ Well-Architected Tool。「檢查整個帳號的閒置資源、安全設定與 service quota」→ Trusted Advisor。

## 46.10 SAP Domain 3 題型：五類改善與常見模式

SAP-C02 的 Domain 3 占約四分之一的分數，題目格式高度一致：「公司有一個**既有**的系統，架構是……，現在出現某個問題，要以某個限制（最少營運負擔、最低成本、最少程式修改）改善。」五個 task 分別對應五類改善：

| Task | 題目在問 | 典型訊號 |
|---|---|---|
| SAP-3.1 營運卓越 | 部署、監控、事故處理、手動操作 | 「手動」「每次部署都要停機」「發現問題太慢」 |
| SAP-3.2 安全 | 憑證、權限、加密、修補、稽核 | 「密碼寫在程式裡」「權限太大」「沒有加密」「不符合稽核」 |
| SAP-3.3 效能 | 延遲、吞吐量、尖峰 | 「尖峰時變慢」「讀取延遲高」「全球使用者抱怨慢」 |
| SAP-3.4 可靠性 | 單點故障、故障擴散、資料遺失 | 「單一 AZ」「一個元件掛掉全部掛掉」「訊息遺失」 |
| SAP-3.5 成本 | 閒置、規格過大、傳輸費 | 「帳單持續上升」「平時使用率很低」「NAT 費用高」 |

解這類題目的步驟：**先找出題目中唯一真正的問題，再找出限制條件，最後選「直接解決該問題、且最符合限制」的選項。** 錯誤選項通常是「也能解決，但改動太大」（例如題目只要求解決讀取延遲，選項卻要整個重寫成微服務），或「看起來相關，但解決的是另一個問題」。

### 常見改善模式表

這張表是本章最值得考前複習的部分。左欄是題目描述的症狀，右欄是最常見的標準答案。

**營運卓越（SAP-3.1）**

| 症狀 | 改善模式 |
|---|---|
| 手動登入伺服器部署、每台設定不一致 | IaC（CloudFormation／CDK）+ CI/CD pipeline；不可變部署（替換而非修改） |
| 部署需要停機 | ALB 後的 rolling、blue/green 或 canary（CodeDeploy、ECS、Lambda alias） |
| 透過 bastion SSH 維運 | Session Manager、Run Command、Automation runbook |
| 告警太多或太晚發現問題 | 以 SLO 為準的 CloudWatch alarm、composite alarm、anomaly detection |
| 同一事故反覆發生 | 事後檢討 + EventBridge／Config 自動修復（第 38 章） |
| 多帳號的設定不一致 | StackSets、Control Tower controls、Config conformance packs |

**安全（SAP-3.2）**

| 症狀 | 改善模式 |
|---|---|
| 密碼或 access key 寫在程式或設定檔 | Secrets Manager（自動輪替）、IAM role 取代長期 key |
| 權限過大 | IAM Access Analyzer 依實際使用產生 least-privilege policy、permission boundary、SCP |
| EC2 用 IMDSv1 | 強制 IMDSv2 |
| 弱點修補不及時 | Inspector 掃描 + Patch Manager；或改用受管服務與定期替換 AMI |
| Web 應用被攻擊 | WAF（managed rules、rate-based rules）+ Shield；origin 只允許 CloudFront |
| 資料沒加密或不知道哪裡有個資 | KMS 加密、Macie 掃描 S3 |
| 資料庫可從過大範圍存取 | 移到 isolated subnet、security group 參照、VPC endpoint |

**效能（SAP-3.3）**

| 症狀 | 改善模式 |
|---|---|
| 資料庫讀取負載高 | Read replica、ElastiCache（cache-aside）；DynamoDB 用 DAX |
| Lambda 大量連線讓 RDS 連線數爆滿 | RDS Proxy |
| 報表查詢拖慢交易資料庫 | 報表移到 read replica 或資料倉儲（Redshift、Athena） |
| 全球使用者延遲高 | CloudFront（靜態與動態加速）、Global Accelerator、多 Region 讀取 |
| 同步處理造成請求逾時 | SQS 非同步化，前端立即回應、後端慢慢處理 |
| 尖峰時擴展太慢 | Predictive／scheduled scaling、warm pool、Aurora Serverless v2 |
| 儲存 IOPS 不足 | EBS gp3 獨立調整 IOPS、io2；共享檔案用 FSx 合適的類型 |

**可靠性（SAP-3.4）**

| 症狀 | 改善模式 |
|---|---|
| 資料庫或應用程式在單一 AZ | RDS Multi-AZ、Aurora replicas、ASG 跨多 AZ |
| 下游故障拖垮上游 | SQS 緩衝、timeout 與重試加退避、circuit breaker |
| 處理失敗的訊息遺失 | DLQ、冪等處理、Step Functions 的 retry／catch |
| 單 Region 無法達到 RTO／RPO | 第 34 章的 DR 策略（pilot light、warm standby），Aurora Global Database |
| 資料誤刪無法還原 | AWS Backup、PITR、S3 versioning 與 Object Lock |
| 不確定能否撐過故障 | FIS 故障演練、AWS Resilience Hub（依設定的 RTO／RPO 目標評估架構並給建議；舊題目中的 ARC readiness check 已不再對新客戶開放） |

**成本（SAP-3.5）**

| 症狀 | 改善模式 |
|---|---|
| EC2 長期低使用率 | Compute Optimizer rightsizing、Auto Scaling、改 Graviton |
| 穩定基礎負載 | Savings Plans 或 Reserved Instances |
| 可中斷的批次工作 | Spot Instances（搭配 checkpoint 或多 instance type） |
| 非上班時間的 dev／test 環境仍在跑 | 排程停機（EventBridge Scheduler、Instance Scheduler） |
| 大量 S3 資料很少讀取 | Lifecycle 轉換、S3 Intelligent-Tiering |
| NAT Gateway 處理費高且流量多到 S3／DynamoDB | Gateway VPC endpoint |
| EBS gp2 | 換 gp3（同樣效能、價格較低） |
| 商業資料庫授權費高 | 轉到 Aurora 或開源引擎（第 44、45 章） |

### 一道題的拆解示範

> 一家公司在單一 AZ 的 EC2 上執行一個訂單 API，訂單寫入同 AZ 的 EC2 自管 MySQL。每次促銷時 API 逾時，事後發現 MySQL 的 CPU 滿載，且大部分是商品資訊的重複讀取。公司希望改善效能與可靠性，並將營運負擔降到最低。

拆解：真正的問題有兩個，「重複讀取壓垮資料庫」（效能）與「全部在單一 AZ、資料庫自管」（可靠性與營運）。限制是「營運負擔最低」。所以答案的方向是：MySQL 遷移到 RDS for MySQL Multi-AZ 或 Aurora MySQL，商品資訊加 ElastiCache 或 Aurora replica 分擔讀取，EC2 放進跨多 AZ 的 ASG。選項中「把 EC2 換成更大的 instance」只解決一半且仍是單點；「全部改寫成 DynamoDB + Lambda」能解決但改動太大，不符合題目隱含的「改善既有系統」。

## 46.11 比較與選型

### 現代化路徑怎麼選

```text
這個元件現在的主要痛點是什麼？
├─ 維運負擔（patch、備份、高可用都靠人）
│    └─► 換成同引擎的受管服務（RDS、Amazon MQ、MSK、ElastiCache、FSx）
├─ 部署慢、一個改動要整個系統一起上線
│    ├─ 程式短期內不能拆 ─► 先容器化到 ECS／EKS，改成 rolling／blue-green
│    └─ 可以投資拆分 ─► strangler fig：路由門面 + 逐一拆出業務能力
├─ 某一段負載和其他部分差異很大（尖峰、批次）
│    ├─ 事件觸發、短時間 ─► Lambda／Step Functions
│    └─ 長時間、穩定 ─► ECS on Fargate 或 AWS Batch
└─ 資料庫被多個模組綁死、schema 不能動
     └─► database per service：邏輯分離 → outbox／CDC → 實體分離
```

### 易混淆的概念

| 比較 | A | B | 判斷 |
|---|---|---|---|
| Strangler fig vs big-bang rewrite | 漸進替換、可回滾、價值提早出現 | 一次切換、風險集中 | 題目要求「降低風險」「持續交付價值」→ strangler fig |
| Amazon MQ vs SQS | 協定相容（AMQP、MQTT 等），最少程式修改 | 雲原生、近乎無限擴展、需改用 SDK | 「不改程式」→ MQ；「最大擴展、最低營運」→ SQS |
| RDS vs RDS Custom | 全受管、沒有 OS 存取 | 受管但保留 OS 存取（Oracle、SQL Server）；EC2 自管則完全控制但負擔最高 | 「需要 OS 存取又要受管」→ RDS Custom |
| ECS vs EKS | AWS 原生、較簡單 | Kubernetes API、可攜性 | 「已使用 Kubernetes」「跨環境一致」→ EKS |
| Fargate vs EC2 launch type | 不管節點 | 自管節點，可用特殊 instance、可能更便宜 | 「最少營運負擔」→ Fargate |
| Transactional outbox vs 直接雙寫 | 同一交易寫入資料與事件，不遺失 | 中途失敗會不一致 | 「不能遺失事件」→ outbox／CDC |
| Well-Architected Tool vs Trusted Advisor | 以 workload 為單位的架構審查（問答） | 自動掃描帳號資源的最佳實務檢查 | 「審查架構與追蹤改善」→ WA Tool；「自動找出閒置與風險資源」→ TA |
| Compute Optimizer vs Cost Explorer rightsizing | 多種資源類型、可納入記憶體指標 | 偏重 EC2 與成本視角 | 「EBS、Lambda、Fargate 的規格建議」→ Compute Optimizer |

## 46.12 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 逐步取代 monolith、降低風險、可回滾 | Strangler fig + ALB path-based routing 或 API Gateway |
| 新服務先接一小部分流量再逐步增加 | ALB weighted target groups、CodeDeploy canary、Lambda alias 權重 |
| 新服務不想被舊系統的資料模型影響 | Anti-corruption layer |
| 舊系統不能修改，但要延伸新功能 | 從資料庫 CDC 或事件延伸（DMS → Kinesis、EventBridge） |
| 多個服務共用一個資料庫，schema 改不動 | Database per service，逐步分離 |
| 寫入資料庫並可靠地發事件，不能遺失 | Transactional outbox、DynamoDB Streams、DMS CDC |
| 跨服務的業務流程失敗要回復 | Saga + Step Functions 補償 |
| 自管 RabbitMQ／ActiveMQ，程式不能改 | Amazon MQ |
| 資料庫需要 OS 存取又想要受管 | RDS Custom |
| Lambda 造成 RDS 連線數爆滿 | RDS Proxy |
| 執行超過 15 分鐘的工作 | ECS／Fargate task、AWS Batch、Step Functions 拆步 |
| 已有 Kubernetes 工具鏈 | EKS |
| Rightsizing 建議要考慮記憶體 | Compute Optimizer + CloudWatch agent |
| 系統性找出架構風險並追蹤 | Well-Architected Tool（lens、milestone、improvement plan） |
| 密碼寫在設定檔 | Secrets Manager + 自動輪替 |

**常見陷阱**：

1. **選了改動最大的選項。** SAP Domain 3 題目問的是「改善既有系統」，若一個選項要求「全部重寫成微服務」而另一個選項用受管服務或快取就能解決問題，後者通常是答案。
2. **拆服務但共用資料庫。** 選項說「拆成多個 ECS 服務，繼續共用同一個資料庫與 schema」，看似現代化，其實是分散式 monolith。
3. **先寫資料庫再發事件，沒有 outbox。** 題目強調「不能遺失」「保證一致」時，這種選項是錯的。
4. **把 15 分鐘以上的工作放進 Lambda。** 不管其他部分多合理，這個限制會讓選項不可行。
5. **以為 Compute Optimizer 自動看得到記憶體。** 沒有 CloudWatch agent 時看不到。
6. **以為 Trusted Advisor 能取代架構審查。** Trusted Advisor 檢查的是資源設定，不會評估「這個 workload 的 DR 策略是否符合業務 RTO」。

## 本章重點整理

- 遷移是把系統搬到 AWS，現代化是改變系統本身；常見路線是先 rehost 離開資料中心，再在 AWS 上漸進式現代化。
- 大爆炸式重寫風險集中、價值延後出現，漸進式現代化讓每一步都能獨立上線、量測與回滾。
- 把自管資料庫、佇列、快取換成受管服務是投入最小、見效最快的現代化；「不能改程式」選協定相容的服務（RDS 同引擎、Amazon MQ、MSK），「允許改程式、要最大擴展」選 SQS、DynamoDB、Lambda。
- 需要作業系統存取的 Oracle 或 SQL Server 用 RDS Custom；受管服務仍需要你負責規格、參數、備份保存、加密與權限。
- Strangler fig 在舊系統前放路由門面（ALB、API Gateway、CloudFront），逐步把功能導向新服務，搭配加權路由做 canary，出問題時改回路由即可回滾。
- Anti-corruption layer 隔離舊系統的資料模型；舊系統不能修改時，可以從 CDC 或事件延伸新功能。
- 服務邊界依業務能力劃分；先拆耦合低、價值明確的邊緣功能，讀取路徑先於寫入路徑，最核心的部分最後拆。
- 共用資料庫、互相同步呼叫、必須一起部署的服務是分散式 monolith；判斷標準是能否獨立部署。
- 資料拆分依序是程式拆開、邏輯分離（禁止跨 schema 存取）、實體分離；跨服務的資料用 transactional outbox 或 CDC 可靠同步，消費端要冪等。
- 跨服務交易用 saga 與補償動作，常用 Step Functions 編排；跨服務報表改從資料湖或資料倉儲查詢。
- 運算平台依元件特性選：短時間事件驅動用 Lambda，長時間穩定服務用 ECS／Fargate，需要 Kubernetes 用 EKS，有特殊主機需求才用 EC2。
- 持續改善是「基準 → 找缺口 → 排序 → 小步變更 → 驗證」的循環，沒有基準就無法證明改善。
- Well-Architected Tool 審查 workload 架構風險，Trusted Advisor 掃描帳號資源，Compute Optimizer 提供規格建議（需 opt-in，記憶體指標需 CloudWatch agent）。
- SAP Domain 3 的題目先找出唯一真正的問題與限制，選「直接解決且改動最符合限制」的選項，不要被改動最大的方案吸引。

## 本章練習題

### 練習 46-1｜SAP｜單選｜漸進取代 monolith

Wanderly 併購的旅行社有一個 Java monolith「TourBook」，已用 MGN rehost 到 EC2，前面是一個 Application Load Balancer。業務單位要求在接下來一年持續推出新功能，CTO 則要求現代化過程中任何一步出問題都要能在幾分鐘內退回原狀，且不能凍結既有功能的維護。

哪個做法最符合需求？

- A. 成立新團隊用微服務完整重寫 TourBook，在新系統通過完整測試後利用 Route 53 一次把所有流量切到新系統
- B. 把 TourBook 的 EC2 換成更大的 instance type，並建立 AMI 作為回滾點，等系統穩定後再規劃重寫
- C. 用 ALB listener rules 作為路由門面，依路徑把個別功能逐一導向新服務，先以 weighted target groups 分配少量流量，出問題時把規則改回指向 monolith
- D. 把 TourBook 整個打包成單一 container 部署到 EKS，之後所有新功能都加在同一個 container image 中

> [!answer]- 答案：C
> **A ✗** 這是大爆炸式重寫：價值要到最後才出現，切換風險集中在一次操作；重寫期間還要同時維護舊系統，違反「持續推出新功能」的需求。
>
> **B ✗** 加大 instance 只是垂直擴展，沒有改變系統結構，也沒有開始任何現代化工作。
>
> **C ✓** 這是 strangler fig 模式。ALB 的路徑規則讓功能可以一個一個轉移，weighted target groups 讓新服務先承接一小部分流量；回滾只要修改 listener rule，幾分鐘內完成，且未拆出的功能照常由 monolith 處理。
>
> **D ✗** 容器化可以改善部署方式，但新功能繼續加在同一個 image 裡，系統仍是一個 monolith，沒有獨立部署與回滾單一功能的能力。
>
> **考點**：SAP-4.4、SAP-2.1｜strangler fig 與漸進式現代化

### 練習 46-2｜SAP｜單選｜不修改程式的訊息佇列遷移

TourBook 使用自管在兩台 EC2 上的 RabbitMQ 叢集，處理訂位確認與出團通知，程式透過 AMQP 函式庫與 RabbitMQ 溝通。最近一次 EC2 故障造成訊息延遲兩小時。團隊希望降低維運負擔並提高可用性，但這個季度沒有人力修改應用程式的訊息處理程式碼。

哪個方案最合適？

- A. 遷移到 Amazon MQ for RabbitMQ 的叢集部署，應用程式只需要更新連線端點與憑證
- B. 改用 Amazon SQS 標準佇列，並把應用程式改用 AWS SDK 傳送與接收訊息
- C. 把 RabbitMQ 叢集放進跨兩個 AZ 的 Auto Scaling group，並撰寫腳本在節點替換時自動重建叢集
- D. 改用 Amazon Kinesis Data Streams，讓訂位確認以 stream 方式處理

> [!answer]- 答案：A
> **A ✓** Amazon MQ 是受管的 message broker，支援 RabbitMQ 與 ActiveMQ 引擎及其原生協定（例如 AMQP）。應用程式繼續使用原本的 AMQP 函式庫，只需要改連線資訊；AWS 負責 broker 的 patch、故障替換，叢集部署跨多個 AZ。
>
> **B ✗** SQS 營運負擔最低、擴展性最好，但需要把程式改成使用 AWS SDK，違反「沒有人力修改程式」的限制。若允許改程式，這會是很好的長期選擇。
>
> **C ✗** 仍然是自管，還增加了自動重建叢集的腳本要維護，營運負擔反而更高。
>
> **D ✗** Kinesis 是串流服務，語意與 RabbitMQ 的佇列和路由不同，也需要大幅修改程式。
>
> **考點**：SAP-4.3、SAP-3.1｜協定相容的受管服務

### 練習 46-3｜SAA｜單選｜資料庫需要作業系統存取

Wanderly 有一套內部系統的 Oracle 資料庫自管在 EC2 上，團隊要把它改為受管服務以減少備份與 patch 工作。但這套資料庫需要安裝一個第三方的稽核代理程式到作業系統上，這是稽核單位的要求，短期內無法取消。

哪個選項能在滿足需求的前提下，盡可能減少維運負擔？

- A. Amazon RDS for Oracle，並把稽核代理程式安裝在一台獨立的 EC2 上遠端連線
- B. Amazon RDS Custom for Oracle
- C. 繼續使用 EC2 自管 Oracle，並用 AWS Backup 處理備份
- D. Amazon Aurora PostgreSQL，並用 DMS 轉換資料

> [!answer]- 答案：B
> **A ✗** 一般 RDS 不提供作業系統存取，無法把代理程式安裝在資料庫主機上；在另一台 EC2 遠端執行不符合「安裝到作業系統」的稽核要求。
>
> **B ✓** RDS Custom 支援 Oracle 與 SQL Server，讓你保有作業系統與資料庫環境的存取權，可以安裝客製軟體，同時仍由 AWS 提供自動化備份等受管功能，是兩者之間的折衷。
>
> **C ✗** 可行但維運負擔最高，patch、高可用仍要自己處理，沒有達到「盡可能減少維運負擔」。
>
> **D ✗** 轉換引擎需要大量改寫，而且 Aurora 同樣沒有作業系統存取，無法安裝代理程式。
>
> **考點**：SAA-3.3、SAA-2.2｜RDS 與 RDS Custom 的差異

### 練習 46-4｜SAP｜單選｜第一個拆分目標

Wanderly 的平台團隊準備拆分 TourBook，這是第一次拆分，團隊還沒有微服務的 CI/CD、監控與資料同步經驗。分析結果如下：訂位核心被所有模組依賴；付款模組牽涉 PCI DSS；行程搜尋是唯讀操作、占總流量 70%、旅展期間需要大幅擴展，與其他模組只透過幾張行程資料表耦合。

應該先拆哪一個模組？

- A. 訂位核心，因為它變更最頻繁，拆出來後效益最大
- B. 付款模組，因為合規風險最高，越早隔離越好
- C. 同時拆出所有模組，避免長期維護新舊兩套系統
- D. 行程搜尋，因為它耦合低、唯讀、需要獨立擴展且業務價值高

> [!answer]- 答案：D
> **A ✗** 被所有模組依賴的核心是最難拆的部分，作為第一個目標會讓沒有經驗的團隊在最複雜的地方卡住。核心通常最後拆，等周邊拆完後它自然變小。
>
> **B ✗** 付款的合規需求代表它需要最完整的設計與稽核準備，不適合當作團隊練習 CI/CD 與資料同步的第一個目標。合規隔離可以先用網路與帳號邊界處理。
>
> **C ✗** 一次拆出所有模組就回到大爆炸式改造，風險集中。
>
> **D ✓** 低耦合、唯讀的模組可以用同步過來的資料副本運作，風險最低；同時它流量大、需要獨立擴展，能立刻展現價值，並讓團隊建立後續拆分需要的基礎設施與經驗。
>
> **考點**：SAP-4.4、SAP-4.3｜拆分順序：低耦合、高價值的邊緣功能優先

### 練習 46-5｜SAP｜單選｜可靠地發出領域事件

拆分後的訂位服務使用 Aurora PostgreSQL。每建立一筆訂位，要通知搜尋服務與通知服務。目前的程式先 commit 資料庫交易，再呼叫 SNS publish。上週有一次 container 在兩個步驟之間被替換，導致一筆訂位存在但通知從未發出。團隊要求事件不能遺失，且不能因為 SNS 暫時無法使用就讓訂位失敗。

哪個設計最合適？

- A. 把 SNS publish 移到資料庫 commit 之前，SNS 成功後才 commit
- B. 在同一個資料庫交易中寫入訂位與一筆 outbox 紀錄，再由獨立的程序（例如 DMS CDC 或輪詢 worker）讀取 outbox 並發布到 SNS，消費端以事件 ID 做冪等處理
- C. 在 publish 失敗時重試三次，三次都失敗就寫入應用程式日誌
- D. 讓搜尋服務與通知服務每分鐘直接查詢訂位服務的資料表，取代事件通知

> [!answer]- 答案：B
> **A ✗** 順序對調只是把不一致換個方向：SNS 成功後 commit 失敗，就會發出一筆不存在的訂位事件；而且 SNS 不可用時訂位也會失敗，違反限制。
>
> **B ✓** Transactional outbox 讓「訂位資料」與「待發送事件」在同一個交易中寫入，兩者一定一致；發布由獨立程序負責，SNS 暫時不可用只會延後發送、不影響訂位。因為發布可能重複，消費端要依事件 ID 冪等處理。
>
> **C ✗** 重試能減少但不能消除問題：container 在 commit 後立刻被終止時根本沒有機會重試，寫日誌也不會讓事件被送出。
>
> **D ✗** 讓其他服務直接查詢訂位服務的資料表，回到共享資料庫反模式，訂位服務將無法自由修改 schema。
>
> **考點**：SAP-3.4、SAP-4.3｜transactional outbox 與冪等消費

### 練習 46-6｜SAP｜選兩項｜拆分共享資料庫

TourBook 的五個新服務仍然讀寫同一個 Oracle schema。每次訂位團隊修改資料表欄位，都會讓報表與搜尋服務出錯，因此所有服務必須協調後一起部署。公司希望各服務能獨立部署，並願意分階段投入。

- A. 為每個服務在 Oracle 中建立自己的 schema 並限制只能存取自己的 schema，跨服務資料改用 API 或事件取得
- B. 把 Oracle 升級為更大的 instance，並建立一個所有服務共用的 read replica
- C. 在共用的 schema 上建立更多 view，讓每個服務透過 view 讀取別人的資料表
- D. 讓所有服務改用同一個 Aurora PostgreSQL cluster 與同一個 schema，以降低授權成本

> [!answer]- 答案：A、E
> **A ✓** 邏輯分離是 database per service 的關鍵一步：每個服務只能存取自己的資料，跨服務改用 API 或事件。完成後，一個服務改自己的 schema 不會影響其他服務。
>
> **B ✗** 加大規格與 read replica 改善的是效能，不會解除服務之間的 schema 耦合。
>
> **C ✗** View 能暫時隔離部分欄位變化，但服務之間仍直接依賴彼此的資料表，屬於共享資料庫的變形，耦合沒有解除。
>
> **D ✗** 換引擎可以省授權費，但所有服務仍共用同一個 schema，問題完全沒有改變。
>
> **E ✓** 邏輯分離後再做實體分離，各服務可以選擇最適合的資料庫；其他服務需要的資料以 CDC 或事件同步成本地副本，實現真正的獨立部署。
>
> **考點**：SAP-4.3、SAP-4.4｜database per service 的分階段拆分

> **C ✓** Container 的本機儲存是暫時性的，task 停止後檔案就會遺失；共享的 S3 或 EFS 才能讓所有 task 存取同一批檔案。
>
> **D ✗** Sticky session 讓同一使用者固定到同一個 task，但 task 被替換時 session 仍會遺失，不能作為容器化的唯一解法。
>
> **E ✗** 容器化不需要改寫成 Lambda；monolith 改寫成 Lambda 的工作量遠大於容器化。
>
> **考點**：SAA-2.1、SAA-3.2｜無狀態設計與容器化前置工作

### 練習 46-16｜SAA｜單選｜降低非上班時間的開發環境成本

Wanderly 的 dev 與 test 環境有 40 台 EC2 與 6 個 RDS instance，只有週一到週五上午 9 點到晚上 8 點會被使用，其餘時間完全閒置。這些環境需要保留資料，每天早上要能自動回到可用狀態。團隊希望以最少的營運工作降低成本。

哪個做法最合適？

- A. 為所有 dev 與 test 的 EC2 購買 3 年期 Reserved Instances
- B. 把所有 instance 改為 Spot Instances
- C. 用 EventBridge Scheduler 在下班後停止 EC2 與 RDS instance，並在上班前自動啟動
- D. 每天下班時刪除整個環境，隔天早上由工程師手動重建

> [!answer]- 答案：C
> **C ✓** 環境每週只使用約三分之一的時間，排程停止與啟動直接省下閒置時段的運算費用（EBS 與資料庫儲存仍會計費），資料保留，且全部自動化。
>
> **A ✗** Reserved Instances 按整段期間收費，無論是否運作；對大多數時間閒置的環境反而不划算。
>
> **B ✗** Spot 可能被中斷，而且不能用於 RDS；它降低的是單價，沒有解決大量閒置時間的浪費。
>
> **D ✗** 每天手動刪除與重建營運負擔高、容易出錯，也會失去資料。
>
> **考點**：SAA-4.2、SAA-4.3｜排程停止閒置環境
