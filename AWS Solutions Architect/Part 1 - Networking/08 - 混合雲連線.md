# 第 8 章　混合雲連線：VPN、Direct Connect 與 Hybrid DNS

> [!abstract] 本章地圖
> **你會學到**：

## 8.1 故事：辦公室裡那台搬不走的伺服器

第 7 章把 AWS 內部的 VPC 都接通了，但那些工具有一個共同前提：兩端都在 AWS 裡。辦公室機房不在 AWS，它有自己的路由器、自己的 DNS，而且中間隔著 Internet。這一章要處理的就是這條跨出 AWS 的路。

Wanderly 的網站已經在 AWS 上跑得很順（第 5 章建好的 `10.20.0.0/16` production VPC），但台北辦公室的小機房裡還有三樣東西搬不走：財務部門的會計系統、全公司共用的 Active Directory（負責員工登入，也是內部網域 `corp.wanderly.internal` 的 DNS server），以及一台存放旅館合約掃描檔的檔案伺服器。辦公室網路是 `10.0.0.0/16`，小林在第 5 章規劃 CIDR 時刻意避開了它，現在這個決定要派上用場了。

新需求一個接一個出現。客服人員要從辦公室查詢 AWS 上的訂單資料庫，不能走 Internet；AWS 上的訂房服務每晚要把當天的交易匯出給會計系統，資料量從幾 GB 成長到幾百 GB；颱風天大家在家上班時，筆電也要能連到內部系統。還有一個最容易被忽略的問題：AWS 上的程式要用 `erp.corp.wanderly.internal` 這個名稱找到會計系統，而辦公室的同事要用 `orders-db.aws.wanderly.internal` 找到 AWS 上的資料庫。

技術主管把需求整理成三個問題交給小林：

1. **路怎麼接？** 用什麼實體或邏輯線路把辦公室和 VPC 連起來，頻寬、延遲、加密與建置時間各要多少。
2. **路由怎麼交換？** 兩邊怎麼知道「哪些位址在對面」，一條線斷了誰負責改走另一條。
3. **名稱怎麼解析？** 兩邊的 DNS 怎麼互相把查詢轉給對方。

本章依序回答這三個問題：先用 Site-to-Site VPN 在幾天內接通，再為員工加上 Client VPN，接著在流量成長後導入 Direct Connect 並設計備援，最後用 Route 53 Resolver 讓名稱解析跨越兩邊。

## 8.2 混合雲連線的基本功：IPsec 與 BGP

**混合雲（hybrid cloud）** 指的是同時使用雲端與自有資料中心（或辦公室機房），並讓兩邊像同一個網路一樣通訊。要做到這點，需要先理解兩個所有 hybrid 方案都會用到的技術：加密通道與動態路由。

### IPsec：在 Internet 上挖一條加密隧道

**IPsec** 是一組在 IP 層加密與驗證封包的協定。兩端的設備先用 **IKE（Internet Key Exchange）** 協商金鑰，之後把原本的封包整個加密、再包上一層新的 IP 標頭送出去。這種「封包裡面再包一個封包」的做法稱為 **tunnel（隧道）**：Internet 上的路由器只看得到外層標頭（兩端設備的 public IP），看不到裡面的 private IP 與資料內容。

IPsec 的好處是不需要專線，只要兩端都能上 Internet 就能建立；缺點是走的仍是 Internet，延遲與頻寬會隨網路狀況起伏，而且加密與封裝會吃掉一些封包大小（**MTU（Maximum Transmission Unit，最大傳輸單元）** 是一個封包能承載的最大位元組數，多包一層標頭就等於可用空間變小）與設備 CPU。

### BGP：讓兩邊自動交換「我這裡有哪些網段」

建好 tunnel 之後，AWS 那端還不知道 `10.0.0.0/16` 在辦公室，辦公室的路由器也不知道 `10.20.0.0/16` 在 AWS。告訴對方的方法有兩種：

- **Static routing（靜態路由）**：人工在兩邊寫死「`10.0.0.0/16` 走這條 tunnel」。簡單，但線路斷了不會自動改道，網段變動也要人工同步。
- **Dynamic routing（動態路由）**：兩端執行 **BGP（Border Gateway Protocol，邊界閘道協定）**，各自把自己的網段「宣告（advertise）」給對方。一條 tunnel 斷了，BGP session 中斷，透過它學到的路由就會被撤回，流量自動改走仍存活的路徑。

BGP 中每個參與者都有一個 **ASN（Autonomous System Number，自治系統編號）**，就像網路世界的身分證號碼。企業內部使用 private ASN（16-bit 範圍 64512–65534），AWS 端預設也是 64512（可自訂）。BGP 選路時有一套規則，本章會用到的有兩條：**prefix 越長越優先**（和 route table 的 longest prefix match 一樣），以及在 prefix 相同時，**AS path 越短越優先**。後者讓我們能用「AS path prepending（在宣告時故意重複自己的 ASN，讓路徑看起來比較長）」把流量推向另一條線。

> [!tip] 考試提示
> 題目只要出現「自動 failover」「兩條線路自動切換」「不想手動維護路由」，就要想到 **dynamic routing（BGP）**。Static routing 的 VPN 仍然有兩條 tunnel，AWS 會依 tunnel 狀態改用另一條，但地端設備怎麼切換、網段變動怎麼同步都要人工處理；要在 DX 與 VPN 這類「不同路徑」之間依路由撤回自動改道，或在 Transit Gateway 上用 ECMP 疊加頻寬，都必須使用 BGP。

有了這兩個工具，就可以來看 AWS 怎麼把它們包裝成受管服務。

## 8.3 Site-to-Site VPN：幾天內接通辦公室

**AWS Site-to-Site VPN** 是 AWS 受管的 IPsec VPN 服務，用來把一個「站點（site）」，也就是辦公室或資料中心的整個網路，接到 AWS。它是建置最快的 hybrid 方案：只要地端有一台支援 IPsec 的路由器或防火牆，通常幾個小時就能接通。

### 四個元件

| 元件 | 在哪裡 | 是什麼 |
|---|---|---|
| **Customer gateway device** | 地端 | 你的實體路由器或防火牆，負責地端那頭的 IPsec 與 BGP |
| **Customer gateway（CGW）** | AWS | 在 AWS 裡「描述」那台設備的資源：它的 public IP、BGP ASN、（可選的）憑證 |
| **Virtual private gateway（VGW）** 或 **Transit Gateway** | AWS | AWS 這頭的 VPN 終點。VGW 附加在單一 VPC 上；Transit Gateway 可以服務多個 VPC（第 7 章） |
| **VPN connection** | AWS | 把 CGW 和 VGW／TGW 串起來的連線，**每條固定包含兩條 IPsec tunnel** |

最常被考的就是最後一點：**一個 VPN connection 有兩條 tunnel，AWS 端的兩個 tunnel 終點位於不同的 AZ**。AWS 會定期維護其中一個終點，維護期間那條 tunnel 會短暫中斷，所以兩條 tunnel 都要在地端設備上設定好，才能真正做到不中斷。

```text
台北辦公室 10.0.0.0/16                              AWS ap-northeast-1
┌────────────────────────┐                        ┌─────────────────────────────┐
│                        │  ① Tunnel 1 (IPsec+BGP)│  [VGW] ASN 64512            │
│ [Customer gateway      │═══════════════════════►│   ├ 終點 A（AZ-a）          │
│  device]               │  ② Tunnel 2 (IPsec+BGP)│   └ 終點 B（AZ-c）          │
│  public IP 203.0.113.10│═══════════════════════►│        │                    │
│  ASN 65010             │      Internet          │        │ ③ route propagation│
└────────────────────────┘                        │        ▼                    │
                                                  │ VPC 10.20.0.0/16            │
                                                  │ rt-app：10.0.0.0/16 → vgw   │
                                                  └─────────────────────────────┘
```

① 和 ② 是同一個 VPN connection 的兩條 tunnel，各自有獨立的 IPsec 與 BGP session，終點在不同 AZ。辦公室路由器透過兩條 tunnel 都向 AWS 宣告 `10.0.0.0/16`，VGW 則向辦公室宣告 VPC 的 `10.20.0.0/16`。③ 在 VPC 的 route table 開啟 **route propagation（路由傳播）** 後，VGW 從 BGP 學到的 `10.0.0.0/16` 會自動出現在 route table 裡，target 是 VGW；不開啟的話，就要手動加一條 static route 指向 VGW。

### 用 CLI 建立一條 VPN

下面四個步驟依序是：描述地端設備（dynamic routing 要提供 BGP ASN）、建立 VGW 並附加到 VPC、建立 VPN connection（預設為 dynamic routing、兩條 tunnel），以及讓 app subnet 的 route table 自動學到地端網段。

```bash
aws ec2 create-customer-gateway --type ipsec.1 \
  --public-ip 203.0.113.10 --bgp-asn 65010

aws ec2 create-vpn-gateway --type ipsec.1 --amazon-side-asn 64512
aws ec2 attach-vpn-gateway --vpn-gateway-id vgw-0abc1234 --vpc-id vpc-0prod5678

aws ec2 create-vpn-connection --type ipsec.1 \
  --customer-gateway-id cgw-0def5678 --vpn-gateway-id vgw-0abc1234

aws ec2 enable-vgw-route-propagation \
  --route-table-id rtb-0app1111 --gateway-id vgw-0abc1234
```

建立後，從 console 下載對應廠牌（Cisco、Palo Alto、Fortinet 等）的設定檔，交給網管套用到地端設備。這裡也可以看出責任分界：AWS 負責 VGW 端兩個終點的可用性，**地端設備的備援是你的責任**。只有一台 customer gateway device 時，它就是單點故障；要更高可用，可以在地端放兩台設備，各自建立一個 VPN connection，總共四條 tunnel。

### 頻寬限制與 ECMP

每條 VPN tunnel 的頻寬有上限，考試常用的數字是 **每條 tunnel 最高約 1.25 Gbps**。這引出 VGW 與 Transit Gateway 的一個關鍵差異：

- **VGW**：即使兩條 tunnel 都 up，同一時間只會用一條傳送往同一目的地的流量，另一條是備援。總頻寬就是一條 tunnel 的上限。
- **Transit Gateway**：支援 **ECMP（Equal-Cost Multi-Path，等價多路徑）**。當多條 tunnel 用 BGP 宣告相同的 prefix 時，TGW 可以把流量分散到所有 tunnel 上。建立多個 VPN connection 就能把頻寬疊加上去。

所以題目若說「VPN 頻寬不夠，需要超過單一 tunnel 的吞吐量，但還不能等 Direct Connect」，答案通常是「改接 Transit Gateway，建立多個 VPN connection，用 BGP 搭配 ECMP」。

> [!note] 更高頻寬的 tunnel
> AWS 近年推出了 **large bandwidth tunnel**，單條 tunnel 最高約 5 Gbps（標準 tunnel 仍是約 1.25 Gbps），目前用於 Transit Gateway、Cloud WAN 等終點，VGW 不適用；支援範圍以官方文件為準。考試題目與大多數既有設計仍以「單條 tunnel 約 1.25 Gbps、VGW 不支援 ECMP」作為判斷依據。另外要注意：TGW 的 ECMP 只對使用 BGP（dynamic routing）的 VPN connection 生效，static routing 的 VPN 不支援 ECMP。

### Accelerated Site-to-Site VPN

一般 VPN 的封包從辦公室出發，沿著公共 Internet 一路走到 AWS Region，中間經過多少 ISP、塞不塞車都無法控制。**Accelerated Site-to-Site VPN** 讓 tunnel 改從離辦公室最近的 AWS edge location 進入，之後走 AWS 自己的全球骨幹網路到 Region，底層使用的是 Global Accelerator（第 11 章）的技術。

兩個限制一定要記：**只能搭配 Transit Gateway（不支援 VGW）**，而且只能在建立 VPN connection 時決定是否啟用（既有連線不能直接開關，只能新建一條再切換）。它也不能用在經 Direct Connect public VIF 建立的 VPN 上。適合的情境是「海外分公司連到遠方 Region，Internet 路徑品質不穩」。

### VPN CloudHub：用 AWS 當分公司之間的中繼

如果 Wanderly 在台北、台中、高雄都有辦公室，每間都建一條 VPN 到同一個 VGW，並使用 BGP 且 ASN 各不相同，VGW 就會把各站點學到的路由轉告給其他站點，讓分公司彼此也能透過 AWS 互通。這種 hub-and-spoke 拓樸稱為 **AWS VPN CloudHub**。它是低成本的分公司互連方案，但所有分公司之間的流量都繞經 AWS，延遲與頻寬受限於各條 VPN。

### 監控與費用

每條 tunnel 在 CloudWatch 都有 `TunnelState` 指標（1 表示 up，0 表示 down），應該為它設定 alarm：最常見的事故不是兩條同時斷，而是「一條斷了好幾週沒人發現，直到另一條遇到維護」。費用包含 **每個 VPN connection 每小時的費用**，加上從 AWS 傳出的資料傳輸費。

> [!warning] 常見誤解
> 「VPN connection 有兩條 tunnel，所以已經高可用。」兩條 tunnel 只保護 **AWS 端** 的終點故障與維護。地端只有一台設備、一條 ISP 線路時，那台設備或那條 ISP 斷掉，兩條 tunnel 一起斷。真正的端到端高可用要從地端設備與 ISP 開始做備援。

## 8.4 Client VPN：讓筆電連進 VPC

Site-to-Site VPN 解決了「辦公室整個網路」的連線，但颱風天在家上班的同事，筆電不在辦公室網路裡。每台筆電都去設定 IPsec 路由器顯然不實際，這時要用另一種服務。

**AWS Client VPN** 是受管的「遠端存取（remote access）」VPN：使用者在筆電上安裝 OpenVPN 相容的用戶端（AWS 提供免費的 AWS VPN Client），連到一個 **Client VPN endpoint**，就能存取 VPC 與透過 VPC 可達的網路（包含經 Site-to-Site VPN 連到的辦公室）。

### 關鍵設定

| 設定 | 說明 |
|---|---|
| **Client CIDR** | 分配給連線用戶端的位址範圍，大小介於 /12 到 /22，**不能與 VPC 或要存取的網路重疊**，建立後不能修改，所以要一開始就規劃 |
| **Target network association** | 把 endpoint 關聯到 VPC 的一個或多個 subnet（建議兩個 AZ），AWS 會在這些 subnet 建立 ENI。用戶端的流量會被做來源位址轉換（SNAT）成這些 ENI 的 IP 再送進 VPC |
| **Authentication** | 三種方式：Active Directory（透過 AWS Directory Service）、mutual certificate（雙向憑證）、SAML 2.0 federation（讓使用者用公司既有的帳號登入，例如接 Okta、Microsoft Entra ID 等 **IdP（identity provider，身份提供者）**，詳見第 13 章）；憑證驗證可與另一種方式搭配使用 |
| **Authorization rules** | 決定「哪些使用者（或群組）可以存取哪些目的網段」，類似一層存取控制 |
| **Route table** | Endpoint 自己的路由表，決定用戶端流量能被送往哪些目的地 |
| **Split-tunnel** | 開啟後只有往 endpoint 路由表中網段的流量走 VPN，其他（例如看 YouTube）直接走使用者自己的 Internet；關閉則全部流量都走 VPN |

Wanderly 的設定是：用 SAML 接公司的 IdP 做登入與 MFA，客服群組只授權存取 `10.20.64.0/23`（資料庫 subnet 所在範圍，再由 security group 進一步限制），財務群組授權存取辦公室的 `10.0.0.0/16`，並開啟 split-tunnel，避免所有員工的影音流量都繞進 AWS 產生不必要的資料傳輸費。

Client VPN 依「每個 subnet association 每小時」加上「每條用戶端連線每小時」收費。若關閉 split-tunnel 又要讓用戶端上網，endpoint 路由表要有 `0.0.0.0/0` 指向關聯的 subnet，該 subnet 也要能經 NAT Gateway 或 IGW 出去，並加上對應的 authorization rule。

> [!tip] 考試提示
> 「個別員工」「遠端工作者」「筆電」「使用者登入」→ **Client VPN**。「辦公室」「資料中心」「整個網路」「路由器」→ **Site-to-Site VPN**。兩者常一起出現在選項裡互相干擾。

## 8.5 Direct Connect：一條不走 Internet 的專用線

VPN 用了幾個月後，問題浮現：每晚的會計匯出從幾 GB 成長到 300 GB，VPN 吞吐量受 Internet 狀況影響，有時跑到早上還沒完成；客服查詢在尖峰時段延遲忽高忽低。這些都是「走 Internet」本質上的限制，加大 VPN 設備也解決不了。這時要考慮專用線路。

**AWS Direct Connect（DX）** 是一條從你的網路到 AWS 的 **私有實體連線**：流量完全不經過公共 Internet，延遲穩定、頻寬可預期，而且從 AWS 經 DX 傳出的資料傳輸費率低於經 Internet 傳出。

### 實體上怎麼接

Direct Connect 不是 AWS 直接拉一條光纖到你家。它的中間點是 **Direct Connect location**：位於全球各地第三方資料中心（colocation facility）的機房，AWS 在裡面放了自己的 DX 路由器。

```text
台北辦公室                電信商線路              DX location（colocation）          AWS Region
┌──────────┐         ┌──────────────┐        ┌────────────────────────────┐     ┌──────────┐
│ 地端路由器 │ ①──────│ 電信商／DX     │──────②│ [客戶或夥伴的路由器]          │     │          │
│ ASN 65010│         │ Partner 線路  │        │        │ ③ cross connect    │④────│ VGW／DXGW│
└──────────┘         └──────────────┘        │ [AWS DX 路由器（port）]      │     │ ／TGW    │
                                              └────────────────────────────┘     └──────────┘
                     ⑤ 在這條實體連線上，用 VLAN 切出多個 VIF，每個 VIF 一個 BGP session
```

① 從辦公室到 DX location 的這段線路，由你自己向電信商或 **AWS Direct Connect Partner** 採購。② 在 DX location 裡，你的路由器（或夥伴的設備）③ 用一條實體跳線 **cross connect** 接到 AWS DX 路由器的 port。申請 dedicated connection 後，AWS 會發一份 **LOA-CFA（Letter of Authorization and Connecting Facility Assignment）**，你拿它請機房業者施作 cross connect。④ AWS DX 路由器經 AWS 骨幹連到 Region。⑤ 這條實體連線上可以用 802.1Q VLAN 切出多個邏輯介面（VIF），每個 VIF 各自跑一個 BGP session，下一節詳細說明。

整個流程包含採購線路、機房施工與測試，**通常需要數週到數個月**。這是考試最愛的時間陷阱：題目說「下週就要上線」，DX 一定來不及，先用 VPN。

### Dedicated 與 Hosted connection

| 比較 | Dedicated connection | Hosted connection |
|---|---|---|
| 向誰申請 | 直接向 AWS 申請一個實體 port | 向 AWS Direct Connect Partner 申請，夥伴從它已有的大 port 切一段給你 |
| 速度 | 1、10、100 Gbps（部分地點有 400 Gbps） | 從 50 Mbps 起跳，依夥伴提供到 10 Gbps 以上 |
| 實體設備 | 你需要在 DX location 有路由器（或由夥伴代管） | 由夥伴處理，你不必進駐 DX location |
| VIF 數量 | 可建立多個 VIF | **每個 hosted connection 只有一個 VIF**；要多個 VIF 就要多個 hosted connection |
| MACsec | 支援（特定速度與地點） | 不支援 |
| 適合 | 大流量、需要多個 VIF、要 MACsec | 頻寬需求小於 1 Gbps、想快速導入、不想自管機房設備 |

Wanderly 的需求是每晚數百 GB、白天客服查詢，500 Mbps 已經很充裕，而且公司沒有人力進駐 DX location，所以小林選擇透過電信夥伴申請 hosted connection。

> [!warning] 常見誤解
> 「Direct Connect 是私有線路，所以資料已經加密。」**DX 預設不加密。** 它只保證流量不經過公共 Internet。若法規要求傳輸加密，要另外使用 MACsec、在 DX 上跑 IPsec VPN，或在應用層用 TLS（8.8 節）。

## 8.6 Virtual Interface：同一條線，三種目的地

實體線路接好了，但封包要去哪裡還沒決定。Direct Connect 用 **VIF（Virtual Interface，虛擬介面）** 決定這條線上的流量通往哪個網路。每個 VIF 是一個 VLAN 加上一個 BGP session。

| VIF 類型 | 連到 | 能存取什麼 | 位址 |
|---|---|---|---|
| **Private VIF** | VGW 或 Direct Connect Gateway | VPC 內的 private IP 資源 | private IP |
| **Public VIF** | AWS 的 public 網路 | AWS 服務的 public endpoint（S3、DynamoDB、各服務 API），甚至其他 Region 的 public 位址 | 需要 public IP（你自有的，或請 AWS 提供 BGP peering 用的小段位址） |
| **Transit VIF** | Direct Connect Gateway，再到 Transit Gateway | 透過 TGW 連到大量 VPC | private IP |

### Private VIF

最常見的用途：讓辦公室用 private IP 存取 VPC。直接連到 VGW 時，**VGW 必須位於該 DX location 所對應的同一個 Region**；要連其他 Region 或多個 VPC，就需要下一節的 Direct Connect Gateway。Private VIF 支援 jumbo frame（MTU 最大 9001），大量資料傳輸時能減少封包數量。

### Public VIF

Public VIF 讓地端透過 DX 存取 AWS 的 public 服務，而不經過 Internet。AWS 會透過 BGP 向你宣告 Amazon 的 public prefix，你也要宣告你擁有的 public prefix 給 AWS。例如 Wanderly 地端備份程式要大量上傳到 S3，走 public VIF 就能得到穩定頻寬與較低的資料傳出費率。

使用 public VIF 有一個容易忽略的副作用：AWS 預設會宣告全球的 Amazon public prefix，你的網路可能因此把所有往 AWS 的流量（包括員工逛 Amazon 購物網站）都導向 DX。AWS 會在宣告的路由上加 BGP community 標記它來自哪個範圍（8.9 節），地端路由器可以據此過濾，只接受需要的 prefix。

> [!note] Private VIF 也能存取 S3
> 另一種做法是在 VPC 建立 S3 的 interface endpoint（第 6 章），地端經 private VIF 連到這個 endpoint 的 private IP。這樣就不需要 public VIF 與 public IP，適合安全團隊不想在地端引入 Amazon public 路由的情境。注意 S3 的 gateway endpoint 不能被地端使用，因為它只作用在 VPC 的 route table 上。

### Transit VIF

Transit VIF 只能連到 Direct Connect Gateway，再由 DXGW 關聯到 Transit Gateway。當 VPC 數量多到要用 TGW 管理時（第 7 章），這是讓地端一次接到所有 VPC 的標準方式。Transit VIF 也支援 jumbo frame，但 MTU 上限是 8500。

## 8.7 Direct Connect Gateway：一條線接到全球

Wanderly 決定在新加坡 Region 建立第二個環境，給東南亞市場使用。DX 連線接在台北附近的 DX location，對應東京 Region。如果每個 Region 都要另外拉一條 DX，成本和建置時間都會翻倍。

**Direct Connect Gateway（DXGW）** 是一個 **全球資源**：你把 private VIF 或 transit VIF 接到 DXGW，再把 DXGW 和 **任何 Region**（中國 Region 除外）的 VGW 或 Transit Gateway 做 **association（關聯）**，地端就能透過同一條 DX 連到這些 VPC。

```text
                         ┌──────────────── Direct Connect Gateway（全球）─────────────────┐
台北辦公室 ── DX ── private VIF ──►│                                                    │
                         │  association ①           association ②                    │
                         └──────┬─────────────────────────┬───────────────────────────┘
                                ▼                         ▼
                     [VGW] 東京 VPC 10.20.0.0/16    [VGW] 新加坡 VPC 10.32.0.0/16
                                ✗ ③ 兩個 VPC 不能經由 DXGW 互通 ✗
```

① ② 一個 DXGW 關聯兩個不同 Region 的 VGW，地端經同一個 private VIF 就能到兩個 VPC。③ 最常考的限制：**DXGW 不提供 VPC 與 VPC 之間的轉送**。東京和新加坡的 VPC 都關聯到同一個 DXGW，它們彼此仍然不能互通；要 VPC 互通請用 VPC peering 或 Transit Gateway（第 7 章）。DXGW 的設計目的只是「讓地端到得了多個 VPC」。

### 搭配 Transit Gateway

規模更大時，結構會變成：

```text
地端 ── DX ── transit VIF ── DXGW ──┬── TGW（東京）── 30 個 VPC
                                    └── TGW（新加坡）── 15 個 VPC
```

這時 VPC 之間的互通與隔離由 TGW 的 route table 決定（第 7 章），DXGW 只負責把地端接進來。關聯 TGW 時要設定 **allowed prefixes**：列出要宣告給地端的 prefix（通常是彙總過的 VPC 網段，例如依第 5 章的位址規劃，東京 TGW 只宣告 `10.16.0.0/12`、新加坡 TGW 只宣告 `10.32.0.0/12`）。這份清單也是一道路由邊界，可以避免把不該讓地端看到的網段宣告出去。

### SiteLink

DXGW 的另一個限制是：連到同一個 DXGW 的兩個地端站點，預設不能經由 DXGW 互通。若 Wanderly 在台北與東京各有資料中心，都接 DX，想讓兩地之間走 AWS 骨幹，可以在 VIF 上啟用 **SiteLink**：流量在 DX location 之間沿 AWS 全球網路傳送，不必進入任何 Region。SiteLink 依用量另外收費。

## 8.8 Direct Connect 的加密

前面提到 DX 預設不加密。Wanderly 要處理會員個資與付款相關資料，資安團隊要求所有跨網路傳輸都要加密。可選的做法有三種，它們工作在不同層：

| 做法 | 層級 | 條件與特性 |
|---|---|---|
| **MACsec（IEEE 802.1AE）** | Layer 2（逐段） | 在你的路由器與 AWS DX 路由器之間的那一段加密；只支援特定速度的 **dedicated connection** 與支援的 DX location；幾乎不影響頻寬 |
| **IPsec VPN over DX** | Layer 3（端到端隧道） | 在 DX 上建立 Site-to-Site VPN。傳統做法是透過 public VIF 連到 VPN 的 public 終點；搭配 Transit Gateway 時可用 **Private IP VPN**，經 transit VIF 以 private IP 建立 tunnel，不需要 public VIF |
| **TLS** | 應用層 | 應用程式自己用 HTTPS、資料庫 TLS 連線加密；不依賴網路設計，但要每個應用都做到 |

選擇的邏輯：需要 **高吞吐又要加密**，且是 dedicated connection → MACsec。用 hosted connection 或合規要求 **IPsec** → VPN over DX（頻寬受 tunnel 上限影響，搭 TGW 可用多條 tunnel 加 ECMP）。只有少數應用需要保護 → TLS 通常是最簡單的。實務上常是「網路層加密 + 應用層 TLS」並用。

## 8.9 高可用設計：別讓一條線成為單點

Direct Connect 上線後，客服與會計流程都依賴它。小林意識到一個問題：一條 DX 連線包含很多可能故障的環節，包括電信商線路、地端路由器、cross connect、AWS DX 路由器，甚至整個 DX location 的電力。只要任何一環故障，整條連線就斷了。

### 層層加強的備援選項

1. **DX + Site-to-Site VPN 備援**：最常見也最便宜的做法。平時走 DX，DX 中斷時改走 Internet 上的 VPN。代價是備援期間頻寬與延遲較差。
2. **LAG（Link Aggregation Group）**：用 LACP 把多條 **相同速度、同一 DX location、終止在同一台 AWS 設備** 的 dedicated connection 綁成一條邏輯連線，增加頻寬並容忍單一 port 故障。可以設定 **minimum links**：存活的成員連線少於這個數字時，整個 LAG 會被視為 down，讓流量改走其他路徑，避免剩下的頻寬撐不住。LAG **不能** 抵抗整個 DX location 或 AWS 設備故障。
3. **多個 DX location**：在兩個不同的 DX location 各建立連線，抵抗單一機房故障。

AWS 的 **Direct Connect Resiliency Toolkit** 把這些組合整理成三種建議模型：

| 模型 | 拓樸 | 能承受 | 適合 |
|---|---|---|---|
| **Maximum resiliency** | 2 個 DX location × 每處 2 條連線，終止在不同 AWS 設備 | 單一設備、單一連線、整個 location 故障 | 關鍵正式環境 |
| **High resiliency** | 2 個 DX location × 每處 1 條連線 | 單一 location 故障 | 一般正式環境 |
| **Development and test** | 1 個 DX location × 2 條連線，終止在不同 AWS 設備 | 單一設備故障，但不能承受 location 故障 | 非關鍵環境 |

> [!warning] 常見誤解
> 「同一個 DX location 拉兩條線就是高可用。」兩條線若共用同一棟機房、同一家電信商的同一條管線，機房停電或施工挖斷光纜時會一起中斷。真正的備援要確認 **DX location、AWS 設備、電信商線路與地端路由器** 都是分開的。

### 相同 prefix 時，AWS 怎麼選路？

小林設定好 DX 與備援 VPN 後，兩條路徑都向 AWS 宣告了 `10.0.0.0/16`。VPC 的流量會走哪條？VGW 所在 VPC 的路由選擇依序是：

1. **Longest prefix match**：先比 prefix 長度。若 VPN 宣告了更精確的 `10.0.1.0/24`，往這段的流量就會走 VPN，不論 DX 是否正常。
2. Prefix 相同時，**route table 中的 static route 優先於 propagated route**。
3. 都是 propagated route 時，依序偏好：**Direct Connect 的 BGP route → VPN 的 static route → VPN 的 BGP route**。

所以只要兩邊宣告相同 prefix，AWS 往地端的方向會自動偏好 DX；DX 的 BGP session 斷掉、路由被撤回後，才改走 VPN。另一個方向（地端往 AWS）由地端路由器決定，網管要在地端設定讓 DX 路徑的 local preference 較高。

> [!tip] 考試提示
> 「DX 為主、VPN 為備援，但流量一直走 VPN」→ 先檢查 VPN 是否宣告了 **更精確的 prefix**。Longest prefix match 永遠在 DX 偏好規則之前。

### 多條 DX 之間：BGP community 與 AS path

如果有兩條 DX（例如 Maximum resiliency 的四條），想讓其中一條當主線、另一條當備援，可以用 BGP 屬性影響 AWS 的選路：

- **Local preference community**：在宣告給 AWS 的路由上加 `7224:7300`（高）、`7224:7200`（中）、`7224:7100`（低），AWS 會優先使用 local preference 高的那條。AWS 先評估這些 community，再看 AS path。
- **AS path prepending**：在備援連線上重複宣告自己的 ASN，讓路徑看起來較長，AWS 就會偏好較短的主線。

Public VIF 則有另一組 **scope community**，分兩個方向：

- **你宣告給 AWS 的 public prefix**：加上 `7224:9100`（只傳播到本地 Region）、`7224:9200`（同一個洲的所有 Region）或 `7224:9300`（全球，未加 tag 時的預設），控制你的 prefix 在 AWS 網路內傳播多遠。
- **AWS 宣告給你的 Amazon prefix**：AWS 會標上 `7224:8100`（來自 DX location 所對應的同一個 Region）或 `7224:8200`（來自同一個洲），其他洲的路由不加 tag。地端路由器可以依這些 tag 過濾，例如只接受 `7224:8100`，避免把往全球 AWS 的流量都導進 DX。

### 偵測故障要多快？BFD

BGP 本身靠 keepalive 偵測對方是否存活，預設要等數十秒才會判定 session 中斷。**BFD（Bidirectional Forwarding Detection，雙向轉送偵測）** 是一個輕量的存活偵測協定，能在一秒左右發現線路故障。AWS 在 DX VIF 上預設啟用非同步 BFD，但 **地端路由器也要設定 BFD 才會生效**。題目若提到「DX 故障時切換到備援太慢」，答案常是啟用 BFD。

## 8.10 Hybrid DNS：讓兩邊叫得出對方的名字

網路通了，小林以為大功告成，結果客服同事回報：「我在辦公室打 `orders-db.aws.wanderly.internal` 找不到主機。」AWS 上的匯出程式也報錯：「無法解析 `erp.corp.wanderly.internal`。」路由正確、security group 也開了，問題出在 DNS。

### 為什麼不會自動通？

AWS 這邊，VPC 裡的機器預設使用 **Route 53 Resolver**（VPC CIDR + 2 的那個位址，第 5 章），它知道 VPC 內部名稱、關聯到 VPC 的 private hosted zone（第 9 章）以及 Internet 上的 public 名稱，但完全不知道辦公室 AD 裡的 `corp.wanderly.internal`。

辦公室這邊，員工電腦問的是 AD 的 DNS server，它是 `corp.wanderly.internal` 的權威伺服器，但不知道 AWS private hosted zone 裡的 `aws.wanderly.internal`。而且 VPC 的 +2 resolver **只接受來自 VPC 內部的查詢**，地端無法直接對它發問。

### Route 53 Resolver endpoints

**Route 53 Resolver endpoint** 是放在你 VPC subnet 裡的一組 ENI，讓 Resolver 能和 VPC 以外的 DNS server 交換查詢。依方向分兩種：

- **Inbound endpoint（入站）**：讓 **VPC 外部**（地端）的 DNS server 把查詢送進來。地端 DNS 設定 **conditional forwarder（條件式轉送）**：「凡是 `aws.wanderly.internal` 的查詢，轉給 inbound endpoint 的 IP」。Resolver 收到後就能用該 VPC 關聯的 private hosted zone 回答。
- **Outbound endpoint（出站）**：讓 Resolver 把 **VPC 內部** 的查詢送出去。搭配 **forwarding rule（轉送規則）**：「凡是 `corp.wanderly.internal` 的查詢，經由 outbound endpoint 轉給地端 DNS `10.0.0.53`、`10.0.1.53`」。Rule 要 **associate（關聯）** 到 VPC 才會生效。

```text
             地端（10.0.0.0/16）                           AWS VPC 10.20.0.0/16
┌──────────────────────────────────┐            ┌──────────────────────────────────────┐
│ 員工電腦                          │            │ App EC2                              │
│   │ ① orders-db.aws.wanderly...?  │            │   │ ④ erp.corp.wanderly.internal?    │
│   ▼                              │            │   ▼                                  │
│ [AD DNS 10.0.0.53]               │            │ [Route 53 Resolver（VPC+2）]          │
│   conditional forwarder:         │  ② DX/VPN  │   ├ 比對 forwarding rule：corp.…     │
│   aws.wanderly.internal          │──────────► │   │   → ⑤ outbound endpoint ENI      │
│   → 10.20.70.10, 10.20.71.10     │            │   │          │                       │
│                                  │ ◄────────  │   │   ⑥ 轉給 10.0.0.53 ◄──────────────┤
│                                  │  ⑥ DX/VPN  │   └ ③ inbound endpoint ENI           │
│                                  │            │        → 查 private hosted zone       │
└──────────────────────────────────┘            └──────────────────────────────────────┘
```

① 員工查詢 AWS 上的名稱，先問自己的 AD DNS。② AD DNS 依 conditional forwarder，把查詢經 DX／VPN 送到 inbound endpoint 的兩個 IP。③ Resolver 以關聯的 private hosted zone 回答，答案沿原路回去。④ 反方向，App 問的是 VPC 的 Resolver。⑤ Resolver 發現名稱符合 forwarding rule，透過 outbound endpoint 的 ENI 把查詢送出。⑥ 地端 AD DNS 回答，Resolver 再交給 App。

### 設定細節與常見錯誤

- **至少兩個 IP、分散在兩個 AZ**：每個 endpoint 至少要指定兩個 IP 位址，放在不同 AZ 才有高可用。每個 IP 能處理的查詢量有上限（官方以每秒約一萬次查詢為參考），量大時可以增加 IP。
- **Security group 與路由**：endpoint 的 security group 要允許 **UDP 與 TCP 53**（回應較大時 DNS 會改用 TCP）；inbound endpoint 要允許地端 DNS 的來源，outbound endpoint 要允許出站到地端 DNS。路由上，VPC 到地端（經 DX／VPN）要雙向可達。
- **Rule 的比對**：Resolver 用 **最精確的網域** 比對 rule。同時有 `wanderly.internal` 與 `corp.wanderly.internal` 兩條 rule 時，查 `erp.corp.wanderly.internal` 會套用後者。除了 **forward rule**，還有 **system rule**：強制某個子網域由 Resolver 自己解析（例如在一條很寬的 forward rule 底下，把某個子網域留給 private hosted zone 回答）。
- **目標 DNS 要多台**：forwarding rule 的 target IP 至少填兩台地端 DNS，否則地端那台 DNS 一停，AWS 上所有查詢內部名稱的程式都會失敗。
- **Query logging**：Resolver query logging 可以把 VPC 內的 DNS 查詢記錄送到 CloudWatch Logs、S3 或 Firehose，排查「到底有沒有轉出去」時非常有用。

費用方面，每個 endpoint 的每個 ENI 按小時收費，另依查詢量計費。這也是為什麼多 VPC 時不應該在每個 VPC 都建 endpoint。

> [!warning] 常見誤解
> 「把 VPC 的 DHCP option set 改成地端 AD DNS 就好。」這樣做確實能讓 EC2 解析地端名稱，但所有查詢（包括 AWS 服務的 endpoint 名稱）都繞到地端，一旦 DX 中斷，AWS 上的應用連 S3 的名稱都解析不了，而且 private hosted zone 與 interface endpoint 的 private DNS 也會失效。保留 Amazon-provided DNS，再用 outbound endpoint 只轉送公司網域，故障範圍小得多。

### 多帳號：集中式 DNS 架構

公司成長到很多帳號與 VPC 後，標準做法是：

1. 在網路帳號的 **shared services VPC** 集中建立一組 inbound 與 outbound endpoint，這個 VPC 透過 TGW 與 DX 連到地端。
2. 在網路帳號建立 forwarding rule，透過 **AWS RAM** 共享給整個 Organization 或特定 OU。
3. 各帳號把共享來的 rule **關聯到自己的 VPC**。

關鍵在於：被關聯 rule 的 spoke VPC，查詢會經由 shared services VPC 裡的 outbound endpoint 送出，**spoke VPC 本身不需要自己的 endpoint**（但 rule 與 endpoint 必須在同一個 Region）。這讓 endpoint 數量、費用與管理點都集中在一處。第 41 章會把這個模式放進完整的企業級網路架構中。

近年 AWS 也推出 **Route 53 Profiles**，可以把 private hosted zone 關聯、Resolver rules、DNS Firewall 規則等 DNS 設定打包成一個 profile，透過 RAM 共享給其他帳號並套用到 VPC。概念上是「把 DNS 設定當成一組範本集中下發」，比逐條共享更容易治理。考試若以 RAM 共享 Resolver rules 為答案，概念仍然成立。

## 8.11 組起來：Wanderly 的 hybrid 架構

把本章所有元件放在一起，就是 Wanderly 目前的混合雲架構：

```text
                   台北辦公室 10.0.0.0/16（AD DNS 10.0.0.53 / 10.0.1.53）
                   ┌──────────────┐        ┌──────────────┐
                   │ 路由器 R1     │        │ 路由器 R2     │
                   └──────┬───────┘        └──────┬───────┘
              ① hosted DX │ 500 Mbps              │ ② Site-to-Site VPN（備援，BGP）
              （private VIF）                      │   經 Internet，兩條 tunnel
                          ▼                       ▼
                    [Direct Connect Gateway]      │
                          │ ③ association         │
                          ▼                       │
                       [VGW] ◄────────────────────┘（VPN 終止在同一個 VGW）
                          │
   VPC 10.20.0.0/16 ──────┼──────────────────────────────────────────
     rt-app / rt-data：10.0.0.0/16 → vgw（propagated，DX 優先）
     ④ Resolver inbound endpoint：10.20.70.10、10.20.71.10（兩個 AZ）
     ⑤ Resolver outbound endpoint + rule：corp.wanderly.internal → 10.0.0.53、10.0.1.53

   遠端員工筆電 ──⑥ Client VPN（SAML、split-tunnel）──► 關聯 app subnet（兩個 AZ）
```

① 主要路徑是一條 hosted DX connection，private VIF 接 DXGW，為日後新加坡 VPC 預留擴充。② 第二台地端路由器建立 BGP 的 Site-to-Site VPN 作為備援，與 R1 分開，避免地端單點。③ DXGW 關聯到 VPC 的 VGW，VPN 也終止在同一個 VGW；兩條路徑宣告相同的 `10.0.0.0/16`，AWS 端自動偏好 DX。④⑤ Resolver endpoint 放在新建的兩個小 subnet（`10.20.70.0/24`、`10.20.71.0/24`，各在一個 AZ），讓兩邊互相解析名稱。⑥ 遠端員工使用 Client VPN。

這個架構的弱點也要誠實列出：只有一條 DX，DX 故障時頻寬降為 VPN 的水準；若會計匯出不能等，下一步就是在第二個 DX location 再拉一條線，往 High resiliency 模型前進。

## 8.12 比較與選型

### 連線方式比較

| 比較 | Site-to-Site VPN | Accelerated VPN | Client VPN | Direct Connect |
|---|---|---|---|---|
| 連接對象 | 整個站點網路 | 整個站點網路（遠距） | 個別使用者裝置 | 整個站點網路 |
| 路徑 | 公共 Internet | Edge location + AWS 骨幹 | 公共 Internet | 私有實體線路 |
| 加密 | IPsec，預設加密 | IPsec | TLS（OpenVPN） | 預設不加密（可加 MACsec／VPN） |
| 建置時間 | 數小時到數天 | 數小時到數天 | 數小時 | 數週到數月 |
| 頻寬 | 每 tunnel 約 1.25 Gbps；TGW + ECMP 可疊加 | 同左 | 依連線數 | 50 Mbps–100 Gbps 以上 |
| 延遲穩定度 | 隨 Internet 起伏 | 比一般 VPN 穩定 | 隨使用者網路 | 穩定、可預期 |
| AWS 端終點 | VGW 或 TGW | **只能 TGW** | Client VPN endpoint | VGW、DXGW、TGW（經 DXGW） |
| 成本結構 | 每連線每小時 + 傳出流量 | 另加加速費用 | 每 association 與每連線每小時 | Port 每小時 + 較低的傳出費率 + 電信線路 |

### 選型決策流程

```text
要連的是「個別使用者裝置」嗎？
├─ 是 → Client VPN（SAML／AD／憑證驗證）
└─ 否（整個辦公室或資料中心）
     │
     需要在幾天內上線？
     ├─ 是 → Site-to-Site VPN（之後可再加 DX）
     │        └─ 站點離 Region 很遠、Internet 品質差 → Accelerated VPN（需 TGW）
     └─ 否 → 需要穩定延遲、大量持續流量、降低傳出費用？
              ├─ 是 → Direct Connect
              │        ├─ < 1 Gbps、不想自管機房設備 → hosted connection
              │        ├─ 需要多個 VIF、MACsec、大頻寬 → dedicated connection
              │        ├─ 目的地：單一 VPC → private VIF；多 Region → + DXGW；
              │        │          大量 VPC → transit VIF + DXGW + TGW；AWS public 服務 → public VIF
              │        └─ 高可用：DX + VPN 備援 → 兩個 location → Maximum resiliency
              └─ 否 → Site-to-Site VPN 即可
```

## 8.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 盡快建立加密連線、幾天內、中等流量 | Site-to-Site VPN |
| 一致的延遲、大量持續傳輸、不經 Internet | Direct Connect |
| 下週就要上線但長期需要穩定頻寬 | 先 VPN，DX 完成後改為主線、VPN 留作備援 |
| VPN 頻寬超過單一 tunnel 上限 | Transit Gateway + 多個 VPN connection + BGP + ECMP |
| 海外分公司、Internet 路徑不穩、VPN 效能差 | Accelerated Site-to-Site VPN（需 TGW） |
| 遠端員工筆電、SAML／AD 登入 | Client VPN |
| 多間分公司透過 AWS 互通、低成本 | VPN CloudHub（同一 VGW、不同 ASN、BGP） |
| 地端透過 DX 存取 S3 public endpoint | Public VIF（或 private VIF + S3 interface endpoint） |
| 一條 DX 連到多個 Region 的 VPC | Direct Connect Gateway |
| 地端經 DX 連到數十個 VPC 並做隔離 | Transit VIF + DXGW + TGW route tables |
| DX 傳輸要加密且高吞吐 | MACsec（dedicated connection） |
| DX 傳輸要求 IPsec、已有 TGW | Private IP VPN over transit VIF |
| DX 主、VPN 備、自動切換 | 兩邊宣告相同 prefix，AWS 偏好 DX BGP route |
| 承受整個 DX location 故障 | 至少兩個 DX location（Maximum／High resiliency） |
| DX 故障切換太慢 | 在地端路由器啟用 BFD |
| VPC 內程式要解析地端網域 | Resolver outbound endpoint + forwarding rule |
| 地端要解析 private hosted zone | Resolver inbound endpoint + 地端 conditional forwarder |
| 多帳號共用 DNS 轉送規則 | 集中 endpoint + RAM 共享 Resolver rules（或 Route 53 Profiles） |

**常見陷阱**：

1. 以為 Direct Connect 預設加密：它只是私有線路，加密要另外做。
2. 以為一個 VPN connection 的兩條 tunnel 就是端到端高可用：地端設備與 ISP 仍是單點。
3. 以為 Accelerated VPN 可以接 VGW：只能接 Transit Gateway。
4. 以為 DXGW 能讓關聯的 VPC 互通：它不提供 VPC 之間的轉送，VPC 互通要 peering 或 TGW。
5. 以為 LAG 能抵抗 DX location 故障：LAG 成員都在同一個 location、同一台 AWS 設備上。
6. 把 Resolver inbound 與 outbound 方向搞反：「查詢從外面進來」是 inbound，「查詢從 VPC 送出去」是 outbound。
7. 以為地端可以直接查 VPC 的 +2 resolver：它只接受 VPC 內部的查詢，地端要經 inbound endpoint。
8. 選擇「hosted connection 建立多個 VIF」：一個 hosted connection 只有一個 VIF。

## 8.14 SAP 加深：企業級 hybrid 連線

SAA 考的是「一個辦公室怎麼連一個 VPC」；SAP 考的是「一家有兩個資料中心、60 個帳號、3 個 Region 的公司，怎麼讓連線集中、隔離、可稽核，而且故障時有明確的行為」。

### 集中式網路帳號

標準做法是由 **網路帳號** 擁有 DX connection、DXGW 與各 Region 的 Transit Gateway，再透過 AWS RAM 把 TGW 共享給應用帳號，讓它們建立 VPC attachment。這樣：

- 實體連線與 BGP 只有一組，由網路團隊管理；應用團隊看不到也改不了。
- Prod、non-prod 與 shared services 的隔離由 TGW route table 的 association 與 propagation 控制（第 7 章）；地端只透過 DXGW allowed prefixes 看到核准的彙總網段。
- 在 TGW 上同時接 DX（經 DXGW）與 VPN 備援時，TGW 也有自己的路由偏好規則：同樣先比 longest prefix match，再來 static route（包含 static routing 的 VPN 寫進 TGW 的路由）優先於 propagated route；propagated route 中，從 DXGW 學到的路由優先於 VPN 以 BGP 學到的路由。所以要讓 TGW 偏好 DX，備援 VPN 應使用 BGP，而不是 static routing。設計時要讓兩條路徑宣告的 prefix 一致，並實際演練撤回 DX 路由後的收斂。

大規模設計時，Direct Connect 的幾個數量限制要先記住，而且其中多數**不能提高**：

- 每條 dedicated connection 最多 50 個 private 或 public VIF，不能提高。
- 每條 dedicated connection 最多 4 個 transit VIF（和 private／public VIF 合計最多 51 個）；需求更高時只能聯絡 AWS 的 Solutions Architect 或 TAM 評估，不能自助申請。Hosted connection 則只能有 1 個 VIF。
- 每個 Transit Gateway 最多關聯 20 個 DX gateway、每個 DX gateway 最多關聯 6 個 Transit Gateway，兩者都不能提高。

這也是為什麼大型環境會用「少數 transit VIF → DXGW → 各 Region 的 TGW」的結構，而不是每個 VPC 一個 VIF。

### 遷移時程與連線策略

併購資料中心時（第 44、45 章），連線常是第一個關鍵路徑。典型的時程設計是：

1. 第 1 週：Site-to-Site VPN 接通，開始做探索與小規模遷移測試。
2. 第 4–12 週：DX 完成後成為主線，VPN 保留作備援；大量資料遷移改走 DX。
3. 若資料量大到 DX 頻寬在時程內也傳不完，就用離線傳輸設備搬第一批資料（第 25 章），再用 DX 同步差異。

計算方式很直接：10 TB 經 1 Gbps 連線、利用率約 80% 時，大約需要 28 小時；100 TB 就超過 11 天。題目給出資料量與期限時，先做這個估算再選方案。

### 全球網路治理：Cloud WAN

當企業有十幾個 Region、數十個分公司，每個 Region 各自維護 TGW、peering 與路由表會變得難以一致。**AWS Cloud WAN** 用一份中央的 **core network policy** 描述 segment（隔離的路由網域，例如 prod、non-prod、shared）、哪些 Region 有 core network edge，以及 attachment 要加入哪個 segment，再由 AWS 在各 Region 實作。它不取代 DX 或 VPN，而是治理它們接進來之後的全球路由。單一或少數 Region 的 hub-and-spoke，TGW 仍是較簡單的選擇；第 41 章會再深入。

### 重疊網段與 hybrid

併購方的資料中心網段若與既有 VPC 重疊，第 5 章介紹的 private NAT Gateway 與第 7 章的 PrivateLink 同樣適用於 hybrid 情境：只需要單向存取少數服務時，用 PrivateLink 或 NAT 把來源位址轉換成不重疊的範圍，比重新編址整個資料中心快得多。

## 本章重點整理

- 混合雲連線要分別回答三件事：實體或邏輯的路徑、路由交換（static 或 BGP）、名稱解析（hybrid DNS）。
- Site-to-Site VPN 由 customer gateway、VGW 或 TGW、VPN connection 組成；每個 VPN connection 固定有兩條 tunnel，AWS 端位於不同 AZ，兩條都要在地端設定。
- 兩條 tunnel 只保護 AWS 端；地端設備與 ISP 線路的備援要自己設計。
- 單條標準 VPN tunnel 頻寬約 1.25 Gbps（考試常用數字）；VGW 不支援 ECMP，要疊加頻寬需改用 Transit Gateway 搭配多個 VPN connection 與 BGP。
- Accelerated Site-to-Site VPN 透過 edge location 與 AWS 骨幹改善遠距 VPN 品質，只能搭配 Transit Gateway。
- Client VPN 是給個別使用者的遠端存取 VPN，支援 AD、憑證與 SAML 驗證、authorization rules 與 split-tunnel；client CIDR 不能與目的網路重疊。
- Direct Connect 是不經 Internet 的私有實體線路，延遲穩定、傳出費率較低，但建置要數週到數月，而且預設不加密。
- Dedicated connection 直接向 AWS 申請 1／10／100 Gbps 等 port；hosted connection 由夥伴提供較小頻寬，每個只能有一個 VIF。
- Private VIF 連 VPC private IP，public VIF 連 AWS public 服務，transit VIF 經 DXGW 連 Transit Gateway。
- Direct Connect Gateway 是全球資源，讓一條 DX 連到多個 Region 的 VGW 或 TGW，但不提供 VPC 之間的轉送。
- DX 加密選項：MACsec（dedicated、Layer 2）、IPsec VPN over DX（含 TGW 的 Private IP VPN）、應用層 TLS。
- LAG 增加頻寬並容忍單一連線故障，但不能抵抗 DX location 故障；關鍵環境應採兩個 location、每處兩條連線的 Maximum resiliency 模型。
- 相同 prefix 時 AWS 偏好 DX BGP route，其次 VPN static、最後 VPN BGP；但 longest prefix match 永遠優先，BGP community 與 AS path 可影響多條 DX 的選路。
- Resolver inbound endpoint 讓地端查詢 AWS 私有名稱，outbound endpoint 加 forwarding rule 讓 VPC 查詢地端網域；endpoint 至少兩個 IP、跨兩個 AZ，security group 要開 UDP／TCP 53。
- 多帳號環境把 Resolver endpoint 集中在 shared services VPC，用 AWS RAM 共享 forwarding rule 給其他帳號關聯，spoke VPC 不需要自己的 endpoint。

## 本章練習題

### 練習 8-1｜SAA｜單選｜快速建立加密 hybrid 連線

Wanderly 的客服團隊要從台北辦公室以 private IP 存取 AWS VPC 中的內部查詢系統，預估流量約 200 Mbps，能接受延遲隨網路狀況小幅波動。專案必須在五個工作天內上線，且資安規範要求所有傳輸都要加密。辦公室已有一台支援 IPsec 與 BGP 的防火牆。

最合適的方案是什麼？

- A. 申請 dedicated Direct Connect connection 並建立 private VIF，因為私有線路已滿足加密要求
- B. 建立 customer gateway 與 virtual private gateway，以 BGP 設定 Site-to-Site VPN，並在地端防火牆設定兩條 tunnel
- C. 為每位客服人員的電腦建立一個 Site-to-Site VPN connection
- D. 在 VPC 中建立 VPC peering，對端指向辦公室防火牆的 public IP

> [!answer]- 答案：B
> **A ✗** Dedicated DX 通常需要數週到數月才能完成，趕不上五個工作天；而且 DX 預設不加密，「私有線路」不等於符合加密要求。若長期需要穩定頻寬，可以之後再導入 DX。
>
> **B ✓** Site-to-Site VPN 使用 IPsec 預設加密，只要地端設備支援就能在幾小時到幾天內建好；200 Mbps 在單條 tunnel 的能力範圍內。兩條 tunnel 都設定好，才能在 AWS 端維護時不中斷。
>
> **C ✗** Site-to-Site VPN 連的是整個站點網路，不是個別電腦；個別使用者的遠端存取應使用 Client VPN。辦公室已有防火牆，一條站點 VPN 就能服務所有客服人員。
>
> **D ✗** VPC peering 只能在兩個 VPC 之間建立，無法連到地端設備。
>
> **考點**：SAA-3.4、SAA-1.2｜Site-to-Site VPN 建置快速且預設加密

### 練習 8-2｜SAA｜單選｜VPN tunnel 維護造成中斷

一家公司用 Site-to-Site VPN 連接資料中心與 VPC。網管只在地端路由器上設定了 VPN connection 的第一條 tunnel，因為「第二條看起來沒有用到」。某天 AWS 進行例行維護，連線中斷了數分鐘，應用程式報錯。公司希望之後 AWS 端維護時連線不中斷，且不想增加新的線路費用。

應如何處理？

- A. 改用 static routing，讓 AWS 自動選擇可用的 tunnel
- B. 再建立一個新的 VPN connection，並同樣只設定第一條 tunnel
- C. 把 VGW 換成 NAT Gateway，以取得更高的可用性
- D. 在地端路由器上同時設定兩條 tunnel，並使用 BGP 讓路由在 tunnel 中斷時自動切換

> [!answer]- 答案：D
> **A ✗** 改成 static routing 不會解決問題：只設定一條 tunnel 時，另一條根本不存在可用路徑；static routing 也失去 BGP 撤回路由帶來的自動切換。
>
> **B ✗** 新的 VPN connection 一樣是兩條 tunnel，只設定第一條仍會在那條 tunnel 的 AWS 終點維護時中斷，問題沒有改變。
>
> **C ✗** NAT Gateway 用於 private subnet 主動連 Internet，不是 VPN 終點，無法終止 IPsec tunnel。
>
> **D ✓** 每個 VPN connection 的兩條 tunnel 終止在 AWS 不同 AZ 的終點，設計目的就是讓一條維護時由另一條接手。兩條都設定並使用 BGP，tunnel 中斷時路由會自動撤回並改走另一條，不需要額外費用。
>
> **考點**：SAA-2.2｜VPN connection 的兩條 tunnel 與 BGP failover

### 練習 8-3｜SAA｜單選｜VPN 頻寬疊加

Wanderly 透過 Site-to-Site VPN 連接到一個 VGW，夜間資料同步需要約 3 Gbps 的吞吐量，但監控顯示 VPN 流量始終卡在約 1.2 Gbps。Direct Connect 已申請，但三個月後才會完成。團隊需要在這段期間內提高 VPN 總頻寬。

哪個做法最合適？

- A. 改把 VPN 接到 Transit Gateway，建立多個使用 BGP 的 VPN connection，並啟用 ECMP 讓流量分散到多條 tunnel
- B. 在同一個 VGW 上增加第三條 tunnel
- C. 把 VGW 的 Amazon side ASN 改成 4-byte ASN 以提高頻寬
- D. 改用 static routing，讓兩條 tunnel 同時以 active-active 方式傳送

> [!answer]- 答案：A
> **A ✓** 單條標準 VPN tunnel 的頻寬約 1.25 Gbps，VGW 又不支援 ECMP，所以流量卡在約 1.2 Gbps。Transit Gateway 支援 ECMP，多條 tunnel 以 BGP 宣告相同 prefix 時，流量能分散到所有 tunnel 上，建立多個 VPN connection 就能把頻寬疊加到所需水準。
>
> **B ✗** 一個 VPN connection 固定是兩條 tunnel，不能自行增加第三條；而且 VGW 不支援 ECMP，就算有多條也不會同時用來疊加頻寬。
>
> **C ✗** ASN 只是 BGP 的身份編號，與 tunnel 頻寬無關。
>
> **D ✗** VGW 不會因為改成 static routing 而對多條 tunnel 做負載分散；ECMP 需要 Transit Gateway 與 BGP。
>
> **考點**：SAA-3.4｜VPN 頻寬上限與 TGW ECMP

### 練習 8-4｜SAA｜單選｜遠端員工存取

颱風季期間，Wanderly 約 150 位員工需要在家用公司筆電存取 VPC 中的內部管理系統。公司已經用 SAML 2.0 IdP 管理員工登入與 MFA。資安團隊要求只有財務群組能存取帳務系統所在的 subnet，其他員工只能存取一般內部系統；員工上網瀏覽一般網站的流量不應繞進 AWS。

最合適的方案是什麼？

- A. 在每位員工家中部署一台支援 IPsec 的路由器，並各自建立 Site-to-Site VPN
- B. 讓內部管理系統改放在 public subnet，以 security group 只允許員工家中的 public IP
- C. 建立 Client VPN endpoint，使用 SAML 驗證，以 authorization rules 依群組限制可存取的網段，並啟用 split-tunnel
- D. 建立 Direct Connect hosted connection，讓員工透過電信商連線

> [!answer]- 答案：C
> **C ✓** Client VPN 是為個別使用者設計的受管遠端存取 VPN。SAML 驗證能沿用既有 IdP 與 MFA，authorization rules 可依 IdP 群組限制目的網段，split-tunnel 讓只有往 VPC 網段的流量走 VPN，一般上網流量走員工自己的 Internet。
>
> **A ✗** 為 150 個家庭各部署路由器與 VPN 成本與營運負擔極高，也無法依使用者群組做授權。
>
> **B ✗** 把內部系統暴露在 public subnet 增加攻擊面；員工家中的 public IP 經常變動，無法可靠地列入允許清單。
>
> **D ✗** Direct Connect 是站點到 AWS 的實體線路，不是給個別員工在家使用的方案，建置時間也很長。
>
> **考點**：SAA-1.1、SAA-1.2｜Client VPN 的驗證、授權與 split-tunnel

### 練習 8-5｜SAA｜選兩項｜穩定頻寬與傳輸加密

Wanderly 的資料中心每晚要把約 2 TB 的交易資料傳到 AWS，要求延遲與吞吐量穩定、不受 Internet 影響，且傳輸期間至少需要 8 Gbps 的頻寬。法規要求資料在傳輸線路上必須加密，並希望加密不要明顯降低吞吐量。公司在 DX location 有自己的機房空間與路由器。

哪兩個做法組合起來能滿足需求？（選兩項）

- A. 向 AWS 申請一條 10 Gbps 的 dedicated Direct Connect connection
- B. 依賴 Direct Connect 本身的私有線路特性作為加密控制
- C. 改用一條標準 Site-to-Site VPN tunnel，因為它預設加密
- D. 在支援 MACsec 的 DX location 與路由器上，為該 dedicated connection 啟用 MACsec
- E. 申請一條 hosted connection，並在上面啟用 MACsec

> [!answer]- 答案：A、D
> **A ✓** Dedicated connection 提供私有、穩定的頻寬，10 Gbps 足以滿足 8 Gbps 的需求；公司在 DX location 有路由器，可以直接接上 AWS 的 port。
>
> **B ✗** Direct Connect 預設不加密，私有線路只代表不經過公共 Internet，不能作為法規要求的加密控制。
>
> **C ✗** 單條標準 VPN tunnel 的頻寬約 1.25 Gbps，且走 Internet、延遲不穩定，兩項要求都不滿足。
>
> **D ✓** MACsec 在你的路由器與 AWS DX 設備之間做 Layer 2 加密，幾乎不影響吞吐量，適合高頻寬又要加密的情境，但必須是支援的 dedicated connection 與 DX location。
>
> **E ✗** MACsec 不支援 hosted connection；而且 hosted connection 的頻寬通常也較低。
>
> **考點**：SAA-1.3、SAA-3.4｜Dedicated DX 與 MACsec

### 練習 8-6｜SAA｜單選｜經 DX 存取 AWS public 服務

一家公司已經有 Direct Connect 連線，並以 private VIF 存取 VPC。現在地端的備份伺服器要把大量資料直接上傳到 S3，並呼叫 DynamoDB 的 public API endpoint。公司要求這些流量不經過公共 Internet，且不想修改備份軟體使用的 S3 與 DynamoDB public endpoint 名稱。

應新增什麼？

- A. 在 VPC 中建立 S3 與 DynamoDB 的 gateway endpoint，地端經 private VIF 使用它們
- B. 在同一條 DX connection 上建立 public VIF，透過 BGP 接收 AWS 的 public prefix
- C. 在 VPC 中建立 NAT Gateway，地端經 private VIF 再透過 NAT 存取 S3
- D. 建立 transit VIF，並把 S3 加入 Transit Gateway route table

> [!answer]- 答案：B
> **A ✗** Gateway endpoint 只作用在 VPC 的 route table 上，地端經 VPN 或 DX 進來的流量無法使用它。地端要經 private VIF 私下存取 S3，需改用 S3 interface endpoint，並另外處理 DNS（使用 endpoint 專屬名稱，或透過 Resolver inbound endpoint 讓地端解析）。
>
> **B ✓** Public VIF 讓地端透過 DX 存取 AWS 服務的 public endpoint，AWS 會以 BGP 宣告 Amazon 的 public prefix，流量走 DX 而不經公共 Internet，應用程式也不需修改 endpoint。可以用 BGP community 與地端過濾控制路由範圍。
>
> **C ✗** NAT Gateway 是讓 VPC 內的資源主動連 Internet，地端流量繞進 VPC 再經 NAT 出 Internet，不但不符合「不經 Internet」，還多付 NAT 處理費。
>
> **D ✗** Transit VIF 用來經 DXGW 連到 Transit Gateway 與 VPC，S3 的 public endpoint 不是 TGW 的 attachment，無法加入 TGW route table。
>
> **考點**：SAA-3.4、SAA-4.4｜Public VIF 存取 AWS public 服務

### 練習 8-7｜SAA｜單選｜DX 為主、VPN 為備援

Wanderly 的 VPC 透過同一個 VGW 同時連接一條 Direct Connect private VIF 與一條使用 BGP 的 Site-to-Site VPN。兩條路徑都由地端宣告 `10.0.0.0/16`。團隊希望 AWS 往地端的流量平時走 DX，DX 中斷時自動改走 VPN，且營運負擔最低。

應如何設定？

- A. 在 VPC route table 加入一條指向 VPN 的 `10.0.0.0/16` static route，作為備援
- B. 讓 VPN 宣告更精確的 `10.0.0.0/17` 與 `10.0.128.0/17`，以確保 VPN 隨時可用
- C. 使用 Route 53 failover record 在 DX 與 VPN 之間切換
- D. 維持兩條路徑宣告相同的 prefix 並開啟 route propagation；VGW 會偏好 DX 的 BGP route，DX 路由撤回後自動改走 VPN

> [!answer]- 答案：D
> **A ✗** Route table 中的 static route 優先於 propagated route，這會讓流量平時就走 VPN，和需求相反。
>
> **B ✗** 更精確的 prefix 會因為 longest prefix match 而永遠勝出，導致所有往地端的流量都走 VPN，DX 反而閒置。
>
> **C ✗** Route 53 failover 決定的是 DNS 回答哪個 endpoint，不能選擇 VGW 往地端的網路路徑。
>
> **D ✓** Prefix 相同時，propagated route 的偏好順序是 DX BGP route、VPN static route、VPN BGP route，所以平時自動走 DX。DX 的 BGP session 中斷、路由撤回後，VPN 學到的路由就會成為唯一的選擇，切換不需人工介入。地端往 AWS 的方向則要在地端路由器設定偏好 DX。
>
> **考點**：SAA-2.2｜VGW 路由優先順序與 DX + VPN 備援

Wanderly 已經以 Direct Connect 連接 VPC 與辦公室。VPC 中的匯出程式需要以名稱 `erp.corp.wanderly.internal` 連到會計系統，這個網域由辦公室兩台 AD DNS server（`10.0.0.53`、`10.0.1.53`）負責。VPC 目前使用 Amazon-provided DNS，團隊不希望 AWS 服務的名稱解析受地端 DNS 可用性影響。

- B. 建立 Route 53 Resolver inbound endpoint，並在 AD DNS 設定 conditional forwarder
- C. 修改 VPC 的 DHCP option set，把 DNS server 改成兩台 AD DNS
- D. 建立名為 `corp.wanderly.internal` 的 private hosted zone，並手動複製會計系統的記錄

>
> **C ✗** 改 DHCP option set 會讓所有查詢都送到地端，DX 或地端 DNS 一出問題，連 S3 等 AWS 服務的名稱都無法解析，也會使 private hosted zone 失效。
>
> **D ✗** 手動複製記錄會與 AD 中的真實記錄不同步，每次地端變更都要人工維護，容易出錯。

### 練習 8-9｜SAA｜單選｜地端解析 private hosted zone

Wanderly 在 AWS 建立了 private hosted zone `aws.wanderly.internal`，並關聯到 production VPC，裡面有訂單資料庫的記錄。辦公室的員工電腦都使用 AD DNS。網路已經經由 VPN 互通，但員工查詢 `orders-db.aws.wanderly.internal` 時一律失敗。

應如何讓員工能解析這個名稱？

- A. 在 AD DNS 設定 conditional forwarder，把 `aws.wanderly.internal` 轉給 VPC CIDR + 2 的 Resolver 位址
- B. 把 private hosted zone 改成 public hosted zone，讓地端可以直接解析
- C. 在 VPC 建立 Route 53 Resolver inbound endpoint（兩個 AZ 各一個 IP），並在 AD DNS 設定 conditional forwarder，把 `aws.wanderly.internal` 轉給這兩個 IP
- D. 建立 Resolver outbound endpoint，並建立 `aws.wanderly.internal` 的 forwarding rule 指向 AD DNS

> **D ✗** Outbound endpoint 是把 VPC 內的查詢轉出去，方向相反；把 `aws.wanderly.internal` 轉給 AD DNS 也找不到答案。

### 練習 8-10｜SAA｜選兩項｜Client VPN 的驗證與流量

哪兩個設定是必要的？（選兩項）

- A. 在 Client VPN endpoint 啟用 split-tunnel
- B. 把 client CIDR 設為 `10.20.0.0/16`，讓用戶端直接使用 VPC 位址
- C. 為每位員工建立一個 customer gateway 與 Site-to-Site VPN connection
- D. 設定 Client VPN endpoint 使用 Active Directory 驗證，並以 authorization rule 允許對應群組存取 `10.20.0.0/16`

> **E ✗** `0.0.0.0/0` 會讓全部流量經 VPC 出去，與「只有 VPC 網段走 VPN」的需求相反，也增加 NAT 與傳輸費用。

### 練習 8-11｜SAP｜單選｜多帳號、多 Region 的 DX 拓樸

Wanderly 併購旅行社後，共有 45 個 AWS 帳號，VPC 分布在東京與新加坡兩個 Region。網路帳號擁有兩條 10 Gbps dedicated DX connection。要求：地端只用這組 DX 存取所有 VPC；production 與 non-production VPC 之間不能互通，但都要能存取 shared services VPC；應用帳號不能修改網路設定；新 VPC 加入時不需要新增 VIF。

最合適的設計是什麼？

- A. 為每個 VPC 在 DX connection 上建立一個 private VIF，直接連到各 VPC 的 VGW
- B. 在每個 Region 建立 Transit Gateway 並以 RAM 共享給應用帳號，DX 上建立 transit VIF 連到 DXGW，再把 DXGW 關聯到兩個 TGW；以 TGW route table 的 association 與 propagation 隔離 prod 與 non-prod
- C. 建立 private VIF 連到 DXGW，把所有 VPC 的 VGW 關聯到這個 DXGW，並依賴 DXGW 做 prod 與 non-prod 隔離
- D. 在每個 VPC 建立 Site-to-Site VPN 到地端，再用 VPN CloudHub 讓 VPC 之間依需求互通

> [!answer]- 答案：B

>
> **B ✓** Transit VIF + DXGW + TGW 是大量 VPC 的標準 hybrid 拓樸。DXGW 讓同一組 DX 到達兩個 Region 的 TGW，TGW route table 控制 prod、non-prod 與 shared services 之間的路由網域。TGW 由網路帳號擁有並以 RAM 共享，應用帳號只建立 attachment，新 VPC 加入也不需要新的 VIF。
>
> **C ✗** DXGW 只負責讓地端到達關聯的 VPC，不提供 VPC 之間的轉送，也沒有 route table 可用來做 segment 隔離；shared services 的存取需求無法經由 DXGW 達成。
>
> **D ✗** 45 個 VPC 各建 VPN 會產生大量 tunnel 與 BGP session，不使用既有 DX，也難以一致地表達隔離規則；CloudHub 用於分公司互通，不是 VPC 分段的工具。
>
> **考點**：SAP-1.1、SAP-1.4｜Transit VIF、DXGW 與 TGW 的多帳號拓樸

- B. 在地端路由器設定 hairpin 路由，把東京往新加坡的流量轉回 DX

### 練習 8-13｜SAP｜單選｜最高等級的 DX 韌性

一家處理支付的公司把核心結算系統放在 AWS，地端系統每秒都需要透過 Direct Connect 與它通訊。風險評估要求：任何單一 DX 設備、單一連線或整個 DX location 故障時，都仍要保有 DX 等級的頻寬與延遲，VPN 備援不被接受。公司希望依照 AWS 的建議模型設計。

哪個設計最符合要求？

- A. 在單一 DX location 建立一個包含四條連線的 LAG，並設定 minimum links 為 2
- B. 在單一 DX location 建立兩條連線，分別終止在不同的 AWS 設備
- C. 在兩個 DX location 各建立一條連線，並以 Site-to-Site VPN 作為第三條備援路徑
- D. 在兩個不同的 DX location 各建立兩條連線，每條終止在不同的 AWS 設備，並確認電信商線路與地端路由器也是分開的

> **C ✗** 兩個 location 各一條是 High resiliency 模型，能承受 location 故障，但其中一個 location 再發生單一連線故障時就只剩 VPN，而題目明確不接受 VPN 備援。

### 練習 8-14｜SAP｜選兩項｜集中式 hybrid DNS

Wanderly 有 30 個應用帳號，每個帳號在東京 Region 有自己的 VPC，全部經 Transit Gateway 連到網路帳號的 shared services VPC，再經 DX 到地端。所有 VPC 都要解析地端的 `corp.wanderly.internal`。目前每個 VPC 各自建了一組 outbound endpoint 與 rule，費用高且規則經常不一致。平台團隊希望集中管理並降低成本。

- A. 只在 shared services VPC 建立一組跨兩個 AZ 的 outbound endpoint，並在網路帳號建立 `corp.wanderly.internal` 的 forwarding rule
- B. 刪除所有 outbound endpoint，在每個 VPC 的 DHCP option set 指定地端 AD DNS
- C. 為每個應用 VPC 建立 inbound endpoint，讓地端 DNS 主動把 `corp.wanderly.internal` 推送到 AWS

>

> **考點**：SAP-1.1、SAP-1.4｜集中 Resolver endpoint 與 RAM 共享 rule

### 練習 8-15｜SAP｜單選｜DX 上的 IPsec 加密

一家公司透過 DX 夥伴取得 hosted connection，並以 transit VIF 經 DXGW 連到網路帳號的 Transit Gateway。新的合規要求規定：地端與 AWS 之間的所有流量都必須以 IPsec 加密，且不能經過公共 Internet。公司不想為此申請 public VIF 或引入 public IP 位址，並希望總加密吞吐量能超過單一 tunnel 的上限。

最合適的做法是什麼？

- A. 在 Transit Gateway 上建立 Private IP Site-to-Site VPN，經既有的 transit VIF 以 private IP 建立多條 tunnel，並以 BGP 與 ECMP 分散流量
- B. 在 hosted connection 上啟用 MACsec
- C. 在 Internet 上建立一般的 Site-to-Site VPN，並停用 DX
- D. 在 DXGW 上啟用加密選項，讓所有 VIF 流量自動加密

> [!answer]- 答案：A
> **A ✓** Private IP VPN 讓 Site-to-Site VPN 的 tunnel 以 private IP 經 transit VIF 建立在 DX 上，滿足 IPsec 與「不經公共 Internet」，也不需要 public VIF。終點是 Transit Gateway，因此可以建立多條 tunnel 並用 ECMP 疊加吞吐量。
>
> **B ✗** MACsec 只支援特定的 dedicated connection，不支援 hosted connection；它也是 Layer 2 加密，不是合規要求的 IPsec。
>
> **C ✗** 改走 Internet 違反「不能經過公共 Internet」的要求，也失去 DX 的穩定性。
>
> **D ✗** DXGW 是路由資源，沒有加密選項，不會加密經過它的流量。
>
> **考點**：SAP-2.3、SAP-1.1｜Private IP VPN over Direct Connect

### 練習 8-16｜SAP｜單選｜兩條 DX 的主備選路

Wanderly 在兩個 DX location 各有一條 private VIF，分別連到同一個 DXGW，兩條都向 AWS 宣告 `10.0.0.0/16`。台北的連線（DX-1）頻寬較大且離主要資料中心近，公司希望 AWS 往地端的流量平時全部走 DX-1，只有 DX-1 中斷時才使用 DX-2。網管希望使用 AWS 明確支援、優先順序最高的 BGP 控制方式。

應如何設定？

- A. 在 DX-2 宣告更精確的 `10.0.0.0/17` 與 `10.0.128.0/17`
- B. 在 VPC route table 中加入一條指向 DX-1 的 static route
- C. 在 DX-1 宣告的路由加上 local preference community `7224:7300`，在 DX-2 加上 `7224:7100`
- D. 在 DX-1 的宣告上做 AS path prepending，讓它的路徑看起來比較長

> [!answer]- 答案：C
> **A ✗** 更精確的 prefix 會因為 longest prefix match 而讓流量平時就走 DX-2，與需求相反。
>
> **B ✗** VPC route table 無法指定「走哪一條 DX」，它只能指向 VGW 或 TGW；DX 之間的選擇由 BGP 決定。
>
> **C ✓** AWS 支援以 BGP community 設定 local preference：`7224:7300` 為高、`7224:7100` 為低，且這些 community 會在 AS path 之前被評估。DX-1 標高、DX-2 標低，AWS 平時就會優先走 DX-1，DX-1 路由撤回後改走 DX-2。
>
> **D ✗** AS path prepending 是讓路徑「看起來較長」以降低偏好；對 DX-1 做 prepend 反而會把流量推向 DX-2。正確用法是在 DX-2 上 prepend，但它的優先順序仍低於 local preference community。
>
> **考點**：SAP-1.1、SAP-2.2｜DX 的 BGP local preference community
