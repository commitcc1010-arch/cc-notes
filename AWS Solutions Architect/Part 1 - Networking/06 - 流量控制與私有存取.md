# 第 6 章　流量控制與私有存取：Security Group、NACL、VPC Endpoint 與 Flow Logs

> [!abstract] 本章地圖
> **你會學到**：
> - 說清楚 security group 與 network ACL 在封包路徑上的位置、評估方式與適用場景，並能寫出三層式架構的最小權限規則
> - 看懂 stateless 防火牆為什麼需要放行 ephemeral ports，並在連線 timeout 時判斷是哪一層擋住
> - 用 gateway endpoint 與 interface endpoint 讓 private subnet 不經 NAT、不經 Internet 存取 AWS 服務，並知道兩者在路由、DNS、費用與可達範圍上的差異
> - 用 endpoint policy 與 `aws:SourceVpce` 條件把 S3 bucket 鎖在指定網路路徑內
> - 讀懂 VPC Flow Logs 的欄位，並分辨 Flow Logs、Reachability Analyzer、Network Access Analyzer 各自回答什麼問題
>
> **前置知識**：第 3 章（port、TCP、stateful 與 stateless 防火牆）、第 5 章（subnet、route table、NAT Gateway）
> **考試比重**：SAA ★★★（Domain 1 安全存取、Domain 4 網路成本）｜SAP ★★☆（Domain 1 網路與安全控制、Domain 3 改善安全）

## 6.1 故事：路通了，但誰都能走

第 5 章結束時，小林已經把 Wanderly 的 production VPC 建好：ALB 與 NAT Gateway 在 public subnet，應用程式在 private subnet，資料庫在完全沒有對外路由的 isolated subnet。資安顧問回來複測，資料庫已經無法從 Internet 掃到，大家鬆了一口氣。

但顧問的第二份報告列出了新的問題。第一，應用程式 EC2 的 security group 開著 `0.0.0.0/0` 的 8080 port；雖然 private subnet 沒有 IGW route，Internet 連不進來，可是 VPC 裡任何一台機器（包括某個測試用的跳板機）都能繞過 ALB 直接打應用程式。第二，資料庫的 security group 允許整個 `10.20.0.0/16`，等於信任 VPC 裡的每一台機器。第三，發生事件時，沒有任何紀錄能回答「昨晚是誰連過資料庫的 3306 port」。

同一週，財務也來找小林：NAT Gateway 的帳單比 EC2 還貴。調查後發現，照片處理 worker 每天經 NAT Gateway 讀寫好幾 TB 的 S3 資料，應用程式向 Secrets Manager 取密碼也走 NAT 出 Internet 再回到 AWS。

這些問題都不是「路不通」，而是「路太通」或「路走錯」。第 5 章用 route table 決定封包**能不能到**；這一章要處理三件事：封包到了之後**准不准進**（security group、NACL）、存取 AWS 服務時**能不能不繞 Internet**（VPC endpoint）、以及事後**能不能證明發生過什麼**（Flow Logs 與分析工具）。

## 6.2 兩道關卡：封包在 VPC 裡會被誰檢查

在講個別功能之前，先看全貌。VPC 裡有兩種內建的網路過濾機制，它們站在不同位置：

- **Security group（安全群組，簡稱 SG）**：套在 **ENI（虛擬網卡）** 上的防火牆。每台 EC2、每個 RDS instance、每個 ALB 節點、每個 interface endpoint 都有 ENI，SG 就貼在這張網卡上，決定哪些流量可以進出這張網卡。
- **Network ACL（網路存取控制清單，簡稱 NACL）**：套在 **subnet 邊界** 上的防火牆。封包要進入或離開一個 subnet 時，會經過這個 subnet 關聯的 NACL。

用大樓比喻：NACL 是每層樓樓梯口的門禁，SG 是每個房間門上的鎖。從 A 房間走到另一層樓的 B 房間，要依序經過 A 的房門、A 那層的樓梯口、B 那層的樓梯口、B 的房門。

```text
 subnet app-a（NACL: nacl-app）           subnet data-a（NACL: nacl-data）
┌──────────────────────────────┐        ┌──────────────────────────────┐
│ [App EC2]                    │        │                  [RDS]       │
│   │ ① SG-app 出站規則         │        │  ④ SG-db 入站規則 ▲          │
│   ▼                          │        │                   │          │
│ ──────── ② nacl-app 出站 ─────┼──────► ┼─ ③ nacl-data 入站 ─┘          │
└──────────────────────────────┘        └──────────────────────────────┘
        ⑧ SG-app 自動放行回應 ◄── ⑦ nacl-app 入站 ◄── ⑥ nacl-data 出站 ◄── ⑤ SG-db 自動放行回應
```

App 連資料庫時：① 封包離開 App 的 ENI，先檢查 SG-app 的出站規則；② 離開 app-a subnet，檢查 nacl-app 的出站規則；③ 進入 data-a subnet，檢查 nacl-data 的入站規則；④ 抵達 RDS 的 ENI，檢查 SG-db 的入站規則。

回應封包的路徑反過來：⑤ SG-db 是 stateful，記得這條連線是自己允許進來的，所以回應**自動放行**；⑥ nacl-data 是 stateless，**不記得**任何事，必須有出站規則允許這個回應；⑦ nacl-app 同樣要有入站規則允許；⑧ SG-app 記得是自己發起的連線，自動放行。

這張圖值得記住兩個結論。第一，跨 subnet 的一次連線會經過**四次** NACL 檢查（兩個 subnet 各一進一出）與兩個 SG；任何一處擋住都會讓使用者看到 timeout。第二，**同一個 subnet 內的兩台機器互連，不會經過 NACL**，因為封包沒有跨越 subnet 邊界，只有 SG 會檢查。

> [!note] 第 3 章的複習：stateful 與 stateless
> **Stateful（有狀態）** 防火牆會記住「這條連線是我允許的」，之後屬於同一條連線的回應封包自動通過。**Stateless（無狀態）** 防火牆每個封包都獨立判斷，不記得前後關係，所以去程和回程都必須各有一條規則放行。SG 是 stateful，NACL 是 stateless，這是本章最常被考的一句話。

## 6.3 Security Group：貼在網卡上的白名單

### 規則長什麼樣子

一個 SG 由兩組規則構成：**inbound rules（入站規則）** 與 **outbound rules（出站規則）**。每條規則包含：

| 欄位 | 說明 | 例子 |
|---|---|---|
| Protocol | TCP、UDP、ICMP，或全部 | TCP |
| Port range | 單一 port 或範圍 | 3306 |
| Source（入站）／Destination（出站） | CIDR、另一個 SG 的 ID，或 prefix list | `sg-0app...`、`10.20.0.0/16`、`pl-0a1b2c3d` |
| Description | 說明，方便稽核 | 「App tier 連 MySQL」 |

SG 有幾個一定要記住的行為：

1. **只有 allow，沒有 deny。** SG 是白名單：沒有被任何規則允許的流量，一律拒絕。你無法在 SG 裡寫「拒絕某個 IP」。
2. **規則之間沒有順序。** 一個 ENI 可以套多個 SG，所有規則合在一起成為一個大集合，只要有任何一條允許就通過。
3. **Stateful。** 允許進來的連線，回應自動可以出去；允許出去的連線，回應自動可以進來。
4. **修改立即生效**，不需要重新啟動 instance。
5. **SG 屬於某一個 VPC**，只能套在同一個 VPC 的 ENI 上。

新建立的 SG 預設**沒有任何入站規則**（全部拒絕），並**允許所有出站流量**。每個 VPC 還有一個 **default security group**，它的特殊之處是入站規則允許「來自同一個 default SG 的所有流量」，也就是套用 default SG 的資源彼此全通。正式環境不應該把資源掛在 default SG 上，很多公司會用 AWS Config 規則檢查 default SG 是否被清空。

數量上，每個 SG 的入站與出站規則數（預設各 60 條）、每個 ENI 可套用的 SG 數（預設 5 個）都是預設 quota，可以申請提高，但「每個 ENI 的 SG 數 × 每個 SG 的規則數」有總上限（1,000 條）。考試很少考精確數字，實務上要注意的是：規則越多越難稽核，應該用 SG 參照來減少規則數量。

### SG 參照：用「身份」而不是「位址」授權

SG 最強大的功能是**來源可以是另一個 SG**。在 SG-db 寫一條規則「允許來源為 SG-app 的 TCP 3306」，意思是：「任何掛著 SG-app 的網卡，都可以連我的 3306。」

這解決了雲端環境的一個核心問題：**IP 位址會變**。Auto Scaling 每天會開關幾十台 instance，每台的 private IP 都不同。如果用 CIDR 授權，你只能寫整個 subnet 範圍（太寬），或不斷更新 IP 清單（不可能）。用 SG 參照，新開的 instance 只要掛上 SG-app，自動就被資料庫信任；被終止的 instance 自動失去資格。

這就是 **SG chaining（SG 串接）** 的三層式寫法：

| SG | 入站規則 | 意義 |
|---|---|---|
| SG-alb | TCP 443，來源 `0.0.0.0/0` | 只有 ALB 面對 Internet |
| SG-app | TCP 8080，來源 SG-alb | 應用程式只接受 ALB 轉來的請求 |
| SG-db | TCP 3306，來源 SG-app | 資料庫只接受應用程式 |

這三條規則直接回應了 6.1 節顧問的前兩個問題：跳板機沒有掛 SG-alb，打不到 8080；VPC 裡其他機器沒有掛 SG-app，連不到 3306。

SG 參照有範圍限制：同一個 VPC 內一定可以；同 Region 的 **VPC peering** 對端的 SG 也可以參照（跨帳號時寫成「帳號 ID／SG ID」）；跨 Region peering 則不能參照，只能用 CIDR。Transit Gateway 自 2024 年起也支援連到同一個 TGW 的 VPC 之間做 SG 參照，但只能用在**入站**規則、不能跨 TGW peering，而且 TGW 與 VPC attachment 兩邊都要啟用此功能（第 7 章）。

### Prefix list：把一堆 CIDR 包成一個名字

**Prefix list（前綴清單）** 是一組 CIDR 的集合，可以當作 SG 規則的來源或目的地。它有兩種：

- **AWS-managed prefix list**：由 AWS 維護，例如 S3 在某 Region 的所有位址（gateway endpoint 會用到），或 CloudFront 回源使用的位址 `com.amazonaws.global.cloudfront.origin-facing`。把它放進 ALB 的 SG，就能做到「只有 CloudFront 能連我的 ALB」。
- **Customer-managed prefix list**：你自己定義，例如「台北與新竹辦公室的所有網段」。更新清單後，所有引用它的 SG 與 route table 一起生效，不用逐一修改。

### 常見誤解

> [!warning] 常見誤解
> - 「SG 擋住了，就加一條 deny。」SG 沒有 deny，要封鎖特定來源必須用 NACL（或第 16 章的 WAF、Network Firewall）。
> - 「SG 回程要開 ephemeral ports。」不用，SG 是 stateful。需要開 ephemeral ports 的是 NACL。
> - 「把出站規則全刪掉比較安全。」刪掉出站規則後，這台機器主動發起的連線（例如連資料庫、呼叫 API）全部失敗；只有「別人連進來的回應」因 stateful 仍能出去。限制出站是好習慣，但要明確列出需要的目的地。
> - 「NAT Gateway 也要掛 SG。」NAT Gateway 不支援 SG（第 5 章），要過濾它的流量要靠 NACL 或來源端的 SG。

## 6.4 Network ACL：subnet 邊界的無狀態清單

SG 已經能做到身份層級的最小權限，為什麼還需要 NACL？因為 SG 有兩件事做不到：**明確拒絕**，以及**由網路團隊在 subnet 層級統一設定、不依賴每個應用團隊把 SG 寫對**。NACL 就是補這兩個洞的粗粒度防線。

### NACL 怎麼評估

一個 NACL 有入站與出站兩組規則，每條規則有一個**規則編號（rule number）**，可以是 allow 或 deny：

| Rule # | Type | Protocol | Port | Source | Allow/Deny |
|---|---|---|---|---|---|
| 90 | All traffic | All | All | `198.51.100.23/32` | DENY |
| 100 | HTTPS | TCP | 443 | `0.0.0.0/0` | ALLOW |
| 110 | Custom TCP | TCP | 1024–65535 | `0.0.0.0/0` | ALLOW |
| `*` | All traffic | All | All | `0.0.0.0/0` | DENY |

評估規則是：**從編號最小的開始比對，第一條符合的規則就決定結果，後面的不再看**（first match）。最後的 `*` 規則無法刪除，代表「以上都不符合就拒絕」。

所以上表中，`198.51.100.23` 連 443 會先命中規則 90 被拒絕；如果把那條 deny 寫成編號 120，它會先命中規則 100 被允許，deny 就形同虛設。這和 IAM policy「explicit deny 永遠優先」的邏輯完全不同（第 12 章），考試很愛拿來混淆。實務上，規則編號建議以 10 或 100 為間隔，方便日後在中間插入新規則。

### Default NACL 與 custom NACL

- 每個 VPC 有一個 **default NACL**，預設**允許所有入站與出站流量**。沒有明確關聯 NACL 的 subnet 會使用它。這就是為什麼大多數人在第 5 章完全沒碰 NACL，網路也通。
- 你自己建立的 **custom NACL**，一開始只有 `*` deny 規則，也就是**全部拒絕**。把 subnet 關聯到一個剛建立、還沒加規則的 custom NACL，該 subnet 會立刻斷線。
- 一個 subnet 同一時間只能關聯一個 NACL；一個 NACL 可以關聯多個 subnet。

規則數量也有預設 quota（每個 NACL 每個方向預設 20 條，可申請提高），NACL 並不適合用來維護大量黑名單；要封鎖成千上萬個惡意 IP，應該用 WAF 的 IP set 或 Network Firewall（第 16 章）。

### Ephemeral ports：stateless 的代價

這是 NACL 最容易出錯的地方。當使用者瀏覽器連到 Wanderly 的 443 port，TCP 連線的兩端是：

- 伺服器端：目的 port 443。
- 用戶端：作業系統隨機挑一個 **ephemeral port（臨時 port）** 作為來源 port，例如 51234。

伺服器回應時，封包的目的 port 是 51234。對 stateless 的 NACL 來說，這個回應是一個全新的、要送往 51234 port 的出站封包；如果出站規則只允許 443，回應就被丟掉。

各系統使用的臨時 port 範圍不同：Linux 核心常見為 32768–60999，Windows 為 49152–65535，而 ELB 與 NAT Gateway 會使用 1024–65535。因為你通常不知道對端是什麼系統，AWS 文件建議 NACL 對回程流量放行 **1024–65535**。

以 public subnet（放 ALB）為例，一份能用的 NACL 是：

| 方向 | Rule # | Port | 對象 | 動作 | 用途 |
|---|---|---|---|---|---|
| 入站 | 100 | TCP 443 | `0.0.0.0/0` | ALLOW | 使用者連 ALB |
| 入站 | 110 | TCP 1024–65535 | `0.0.0.0/0` | ALLOW | ALB／NAT 主動連出後的回應 |
| 出站 | 100 | TCP 8080 | `10.20.16.0/20` | ALLOW | ALB 轉送到 app-a |
| 出站 | 110 | TCP 8080 | `10.20.32.0/20` | ALLOW | ALB 轉送到 app-c |
| 出站 | 120 | TCP 1024–65535 | `0.0.0.0/0` | ALLOW | 回應使用者 |
| 出站 | 130 | TCP 443 | `0.0.0.0/0` | ALLOW | NAT Gateway 轉送 private subnet 的對外請求 |

注意入站 110：public subnet 裡的 NAT Gateway 幫 private subnet 對外連線時，外部 API 的回應會以 1024–65535 的 port 回來，這也要放行。少了這條，ALB 正常，但應用程式呼叫金流 API 全部 timeout，這是一個非常典型的「只壞一半」故障。

### NACL 不檢查的流量

有一些流量不經過 NACL 過濾：送往 Amazon-provided DNS（Route 53 Resolver）的查詢、DHCP、instance metadata（`169.254.169.254`）、Amazon Time Sync Service，以及 Windows 授權啟用等 AWS 保留的服務流量。所以「用 NACL 擋住 DNS 查詢」這種想法是做不到的；要依網域名稱過濾 DNS 查詢，需要 Route 53 Resolver DNS Firewall（第 16 章）。

### 什麼時候真的需要 NACL

在 AWS 的設計建議中，**SG 是主要的存取控制**，NACL 是補充。適合用 NACL 的情境：

1. **緊急封鎖特定來源**：發現某個 IP 正在攻擊，在 public subnet 的 NACL 加一條編號很小的 deny。
2. **subnet 層級的硬邊界**：例如規定 data subnet 只接受來自 app subnet CIDR 的流量。即使某個應用團隊把 SG 寫成 `0.0.0.0/0`，NACL 仍會擋下其他來源。這是**縱深防禦（defense in depth）**：不依賴單一控制正確。
3. **合規要求**：某些稽核框架要求在網段之間有明確的網路層控制清單。

## 6.5 SG 與 NACL 一起用：比較與除錯

把兩者放在一起比較：

| 比較 | Security group | Network ACL |
|---|---|---|
| 套用位置 | ENI（instance 層級） | Subnet 邊界 |
| 狀態 | Stateful，回應自動放行 | Stateless，去回程都要規則 |
| 規則類型 | 只有 allow | Allow 與 deny |
| 評估方式 | 所有規則合併，任一允許即通過 | 依編號由小到大，第一條符合者決定 |
| 來源可以是 | CIDR、SG、prefix list | CIDR（不能用 SG ID） |
| 預設 | 新 SG：入站全拒、出站全開 | Default NACL 全開；custom NACL 全拒 |
| 同 subnet 內流量 | 檢查 | 不檢查 |
| 典型用途 | 精細的服務對服務授權 | 粗粒度 subnet 邊界、明確拒絕 |

### 除錯：連線 timeout 時怎麼判斷

網路層擋住封包時，大多數情況下對方不會回任何訊息，使用者只看到 timeout。這時可以用一個簡單的區分方法：

- **Timeout**：通常是網路層（route、SG、NACL）丟掉了封包。
- **Connection refused**：封包到了機器，但沒有程式在那個 port 監聽（或作業系統防火牆主動拒絕）。網路設定是通的。
- **HTTP 403／AccessDenied**：連線成功，是應用程式或 AWS 授權（IAM、bucket policy）拒絕。

以「App 連不到 RDS」為例，從內到外的檢查順序：

1. DNS 是否解析到預期的 private IP？
2. App 所在 subnet 的 route table 有沒有到資料庫 CIDR 的 route？（同 VPC 內有 local route，通常沒問題；跨 VPC 時要看第 7 章。）
3. SG-app 的出站規則是否允許 3306 到 SG-db 或資料庫 CIDR？
4. nacl-app 出站是否允許 3306、入站是否允許 1024–65535 回程？
5. nacl-data 入站是否允許來自 app CIDR 的 3306、出站是否允許回程？
6. SG-db 入站是否允許來源 SG-app？
7. 資料庫引擎本身是否在監聽、帳號是否允許從該來源登入？

這份清單手動檢查很耗時，6.11 節的 Reachability Analyzer 可以自動完成第 2–6 步。

## 6.6 為什麼需要 VPC endpoint：存取 AWS 服務不必繞出去

現在回到財務的問題。Wanderly 的 worker 在 private subnet 讀寫 S3，封包的路徑是：worker → NAT Gateway → IGW → S3 的 public endpoint。雖然 S3 和 worker 在同一個 Region，甚至流量實際上沒有離開 AWS 的骨幹網路，但從 VPC 的角度看，它走的是「對 Internet 的路」，所以：

- **費用**：每 GB 都要付 NAT Gateway 的資料處理費。
- **安全**：worker 的 subnet 必須有通往 Internet 的 default route；如果 worker 被入侵，攻擊者也能把資料送到 Internet 上的任何地方。
- **合規**：有些法規或客戶合約要求「資料不得經過公共網路路徑」，即使技術上 AWS 骨幹很安全，稽核人員看到 NAT 與 IGW 仍會要求說明。

**VPC endpoint（VPC 端點）** 讓 VPC 裡的資源可以用私有路徑存取 AWS 服務（或其他人發布的服務），不需要 IGW、NAT、public IP。它有兩種主要類型，運作方式完全不同：

| | Gateway endpoint | Interface endpoint |
|---|---|---|
| 運作方式 | 在 route table 加一條 route | 在 subnet 裡建立 ENI（使用 PrivateLink） |
| 支援服務 | 只有 S3 與 DynamoDB | 大多數 AWS 服務、第三方與自家服務 |
| 費用 | 免費 | 每個 AZ 每小時 + 每 GB |

還有第三種 **Gateway Load Balancer endpoint**，用來把流量導向防火牆設備，它屬於流量檢查架構，第 10 章與第 41 章會介紹。

## 6.7 Gateway endpoint：改路由，免費

### 怎麼運作

建立 S3 gateway endpoint 時，你選擇要關聯的 route table。AWS 會在這些 route table 自動加入一條 route：

| Destination | Target |
|---|---|
| `10.20.0.0/16` | local |
| `pl-0a1b2c3d`（S3 在本 Region 的 prefix list） | `vpce-0s3...` |
| `0.0.0.0/0` | nat-a |

Worker 送往 S3 的封包，目的地是 S3 的某個 public IP。VPC router 依照第 5 章的 longest prefix match，發現 prefix list 裡的 S3 CIDR 比 `0.0.0.0/0` 更精確，於是把封包交給 endpoint，而不是 NAT。其他往 Internet 的流量仍然走 NAT。

這裡有一個重要細節：**DNS 完全沒有改變**。Worker 解析 `wanderly-photos.s3.ap-northeast-1.amazonaws.com` 仍然得到 S3 的 public IP，是 route table 讓這些 public IP 改走私有路徑。所以應用程式不需要任何修改。

建立方式（CLI，`--vpc-endpoint-type` 預設就是 Gateway）：

```bash
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0wanderly \
  --service-name com.amazonaws.ap-northeast-1.s3 \
  --route-table-ids rtb-0appa rtb-0appc rtb-0data
```

### Gateway endpoint 的限制

1. **只支援 S3 與 DynamoDB。**
2. **只能存取同一個 Region 的服務**：東京 VPC 的 S3 gateway endpoint 不能用來存取新加坡的 bucket；跨 Region 的請求仍會走預設路由。
3. **只在這個 VPC 內有效，無法延伸出去**：地端經 VPN 或 Direct Connect 進來的流量、經 VPC peering 或 Transit Gateway 從其他 VPC 來的流量，都不能使用這個 VPC 的 gateway endpoint。因為它只是本 VPC route table 上的一條 route，別的網路看不到它。
4. **依 route table 生效**：沒有關聯到的 route table，其 subnet 不會走 endpoint。
5. 如果 instance 的 SG 限制了出站，記得允許到 S3 prefix list 的 443。

> [!tip] 考試提示
> 「private subnet 大量存取 S3 或 DynamoDB、NAT 費用高」→ gateway endpoint。「地端透過 Direct Connect 私有存取 S3」→ 不能用 gateway endpoint，要用 S3 **interface** endpoint。這兩題常一起出現，差別就在流量來自哪裡。

## 6.8 Interface endpoint：在你的 subnet 裡放一個服務入口

### 為什麼需要另一種 endpoint

Gateway endpoint 只支援兩個服務，而 Wanderly 還需要私有存取 Secrets Manager、SSM、CloudWatch Logs、ECR、KMS 等。這些服務用的是另一種機制：**AWS PrivateLink**。

**Interface endpoint** 會在你選擇的每個 subnet 中建立一張 ENI，這張網卡有一個你 VPC 裡的 private IP。應用程式把請求送到這個 private IP，AWS 在背後把流量私下轉給服務。從 VPC 的角度看，服務就像住在你 subnet 裡的一台機器。

```text
  VPC 10.20.0.0/16
  ┌─────────────────────────────────────────────────────────┐
  │ app-a 10.20.16.0/20                                     │
  │   [App EC2] ──① DNS: secretsmanager.ap-northeast-1      │
  │       │          .amazonaws.com → 10.20.16.200           │
  │       │ ② TCP 443 → 10.20.16.200                         │
  │       ▼                                                  │
  │   [Endpoint ENI 10.20.16.200]  ◄── ③ SG-endpoint 入站 443 │
  └───────┼─────────────────────────────────────────────────┘
          │ ④ PrivateLink（AWS 內部網路，不經 IGW/NAT）
          ▼
   [Secrets Manager 服務]  ── ⑤ 依 IAM、endpoint policy 授權
```

① 啟用 **private DNS** 後，服務的標準名稱在 VPC 內會解析到 endpoint ENI 的 private IP。② 應用程式照常呼叫 SDK，不用改程式。③ Endpoint ENI 有自己的 SG，必須允許應用程式來源的 443。④ 流量經 PrivateLink 在 AWS 內部送達服務。⑤ 服務端照常做 IAM 授權，endpoint policy 再加一層限制（6.9 節）。

### 關鍵設定

- **Subnet 與 AZ**：每選一個 subnet，就在那個 AZ 建一張 ENI。要高可用，至少選兩個 AZ。費用也是按「每個 AZ 每小時」計算，所以選三個 AZ 就付三份小時費。
- **Security group**：套在 endpoint ENI 上。最常見的錯誤是忘了允許應用程式 subnet 或 SG 的 TCP 443，結果 DNS 解析正確但連線 timeout。
- **Private DNS**：讓服務的預設名稱（例如 `secretsmanager.ap-northeast-1.amazonaws.com`）在 VPC 內解析到 endpoint。AWS 會替你建立並管理一個隱藏的 private hosted zone。前提是 VPC 的 `enableDnsSupport` 與 `enableDnsHostnames` 都開啟（第 5 章）。不開 private DNS 也能用，但應用程式要改成呼叫 endpoint 專屬的 DNS 名稱（`vpce-0abc...-xyz.secretsmanager.ap-northeast-1.vpce.amazonaws.com`）。
- **費用**：每個 endpoint 每個 AZ 按小時收費，加上每 GB 處理費。每 GB 費用遠低於 NAT Gateway，但服務數量一多，小時費會累積；一個 VPC 需要十幾個 endpoint 是常見的事。

### 一個服務常常需要好幾個 endpoint

讓完全沒有 NAT 的 isolated subnet 運作，要把應用程式依賴的服務全部列出來：

| 需求 | 需要的 endpoint |
|---|---|
| 從 ECR 拉 container image | `ecr.api`、`ecr.dkr`（interface），加上 **S3 gateway endpoint**（image layer 存放在 S3） |
| 用 Session Manager 登入 instance | `ssm`、`ssmmessages`；較舊版本的 SSM Agent 還需要 `ec2messages`（AWS 文件仍建議一併建立，第 38 章） |
| 寫 CloudWatch Logs | `logs` |
| 讀密碼 | `secretsmanager`（即使密碼用 KMS customer managed key 加密，解密也是 Secrets Manager 代你呼叫 KMS，應用程式不需要 `kms` endpoint；只有應用程式自己直接呼叫 KMS API 時才需要） |

少一個，就會有某個功能在 isolated subnet 裡默默 timeout。

### Interface endpoint 能從 VPC 外面使用

這是它和 gateway endpoint 最大的差別：interface endpoint 是一個有 private IP 的 ENI，**任何能路由到這個 IP 的地方都能用它**，包括經 VPN 或 Direct Connect 連進來的地端網路，以及經 peering 或 Transit Gateway 相連的其他 VPC。

所以「地端伺服器經 Direct Connect 私有存取 S3」的標準答案是 **S3 interface endpoint**。S3 和 DynamoDB 都同時支援 gateway 與 interface 兩種 endpoint：VPC 內的大流量用免費的 gateway endpoint，地端或其他 VPC 的存取用 interface endpoint，兩者可以並存。（地端要找到 endpoint 的 IP 有兩種做法：直接使用 endpoint 專屬的 DNS 名稱，或讓地端 DNS 把服務名稱轉送到第 8 章的 Route 53 Resolver inbound endpoint，由 VPC 內的 private DNS 回答。）

> [!warning] 常見誤解
> 「Interface endpoint 會修改 route table。」不會。Interface endpoint 靠 **DNS** 把流量導到 ENI 的 private IP，這個 IP 本來就在 VPC 範圍內，走 local route。會修改 route table 的是 gateway endpoint。考試題目若問「建立 endpoint 後要更新哪裡」，gateway 看 route table，interface 看 DNS 與 SG。

## 6.9 Endpoint policy 與 `aws:SourceVpce`：把網路路徑變成授權條件

Endpoint 解決了「路怎麼走」，但還沒回答「走這條路能做什麼」。如果 worker 被入侵，攻擊者仍可以透過 S3 endpoint 把資料寫進**攻擊者自己帳號的 bucket**，因為 S3 的 endpoint 對所有 bucket 都通。這種把資料偷偷送出去的行為稱為 **data exfiltration（資料外洩）**。要防止它，需要兩個方向的控制：

```text
   [Worker]  ── 透過 vpce-0s3 ──►  [S3]
      │                              │
      │  ① endpoint policy：           │  ② bucket policy：
      │  「從這個 endpoint 出去，      │  「只有從 vpce-0s3 來的
      │   只能碰 Wanderly 的 bucket」  │   請求，才能碰這個 bucket」
```

① 控制「從我的網路出去能去哪裡」；② 控制「我的資料只能從哪裡被存取」。兩者合起來，資料只在 Wanderly 的網路與 Wanderly 的 bucket 之間流動。

### Endpoint policy

**Endpoint policy** 是附加在 VPC endpoint 上的 resource-based policy（以資源為主體的權限政策，第 12 章），格式和 IAM policy 相同。預設的 endpoint policy 允許完全存取。限制為只能存取 Wanderly 的 bucket：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OnlyWanderlyPhotoBuckets",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::wanderly-photos-prod",
        "arn:aws:s3:::wanderly-photos-prod/*"
      ]
    }
  ]
}
```

理解 endpoint policy 最重要的一點：**它不授予任何權限，只是再加一道過濾。** 一個請求要成功，必須同時被 IAM（或 bucket policy）允許，**而且**被 endpoint policy 允許。Endpoint policy 寫了 `"Principal": "*"`，並不表示任何人都能讀這個 bucket；沒有 IAM 權限的 role 照樣被拒絕。

收緊 endpoint policy 時要小心依賴：Amazon Linux 的套件庫、ECR 的 image layer 等也透過 S3 提供。把 S3 endpoint policy 限制到只剩自家 bucket，可能讓 `dnf` 更新或 container 拉取失敗，需要把這些 AWS 提供的 bucket 一併列入。

### Bucket policy 的 `aws:SourceVpce`

另一個方向，在 bucket policy 中拒絕所有不是從指定 endpoint 來的請求：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnlessFromWanderlyVpce",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::wanderly-photos-prod",
        "arn:aws:s3:::wanderly-photos-prod/*"
      ],
      "Condition": {
        "StringNotEquals": { "aws:SourceVpce": "vpce-0s3wanderly1234" }
      }
    }
  ]
}
```

這樣即使某把 access key 外洩，攻擊者在自己的電腦上也無法讀這個 bucket，因為請求不是從 `vpce-0s3wanderly1234` 來的。

相關的條件鍵：

| Condition key | 比對什麼 | 用途 |
|---|---|---|
| `aws:SourceVpce` | 請求經過的 endpoint ID | 只允許特定 endpoint |
| `aws:SourceVpc` | 請求來自的 VPC ID | 允許某 VPC 內的任何 endpoint |
| `aws:VpcSourceIp` | 請求在 VPC 內的 private IP | 限制到特定 subnet 範圍 |
| `aws:SourceIp` | 請求的 **public** 來源 IP | 經 endpoint 的請求**不適用**，因為來源是 private IP |

> [!warning] 常見誤解
> - 「bucket policy 用 `aws:SourceIp` 限制 VPC 的 CIDR `10.20.0.0/16`。」行不通。經過 VPC endpoint 的請求，`aws:SourceIp` 不會是你的 private IP，條件永遠不符合。要用 `aws:SourceVpce`、`aws:SourceVpc` 或 `aws:VpcSourceIp`。
> - 「Deny 不是來自 endpoint 的請求，管理員還能從 console 修改 bucket。」不行。Console 的請求不經過你的 endpoint，也會被拒絕；連修改 bucket policy 本身都可能被擋。實務上要在條件中排除特定管理 role（例如加上 `aws:PrincipalArn` 例外），或保留 root user 修正的能力。

## 6.10 看見流量：VPC Flow Logs

設定都寫好了，最後一個問題是：怎麼證明它們如預期運作？出事時怎麼查？

### Flow Logs 記錄什麼

**VPC Flow Logs** 會記錄經過 ENI 的 IP 流量的**摘要（metadata）**：誰連誰、用哪個 port、傳了多少資料、被允許還是拒絕。它**不記錄封包內容**。可以在三個層級啟用：整個 VPC、某個 subnet、某張 ENI；在 VPC 層級啟用等於對其中所有 ENI 啟用。

紀錄可以送到三種目的地：

- **CloudWatch Logs**：方便即時查詢、建立 metric filter 與告警（第 36 章）。
- **Amazon S3**：便宜、適合長期保存，可以選 Parquet 格式與按小時分區，再用 Athena 查詢（第 30 章）。
- **Amazon Data Firehose**：串流到其他分析或 SIEM 系統。

預設格式（version 2）的一筆紀錄：

```text
2 111122223333 eni-0db12345 10.20.17.8 10.20.64.15 49821 3306 6 12 2840 1727760000 1727760060 ACCEPT OK
```

| 欄位 | 值 | 意義 |
|---|---|---|
| version | 2 | 格式版本 |
| account-id | 111122223333 | 帳號 |
| interface-id | eni-0db12345 | 被記錄的 ENI（這裡是 RDS 的網卡） |
| srcaddr／dstaddr | 10.20.17.8 → 10.20.64.15 | 來源與目的 IP |
| srcport／dstport | 49821 → 3306 | 來源 ephemeral port，目的 MySQL |
| protocol | 6 | IANA 協定編號，6 = TCP，17 = UDP，1 = ICMP |
| packets／bytes | 12／2840 | 這段時間內的封包數與位元組數 |
| start／end | Unix 時間 | 這筆紀錄涵蓋的時間窗 |
| action | ACCEPT | SG 與 NACL 共同的判定結果：ACCEPT 或 REJECT |
| log-status | OK | 紀錄狀態（NODATA 表示期間無流量，SKIPDATA 表示有紀錄被略過） |

除了預設欄位，可以自訂格式加入 `vpc-id`、`subnet-id`、`instance-id`、`tcp-flags`、`flow-direction`、`pkt-srcaddr`／`pkt-dstaddr`（經過 NAT 等轉換前的原始位址）、`traffic-path`（流量經哪種閘道離開）等欄位。

這一筆紀錄回答了 6.1 節的第三個問題：「昨晚 `10.20.17.8` 連過資料庫的 3306，被允許了。」再用 `instance-id` 欄位或 EC2 的 ENI 紀錄，就能找出是哪一台機器。

### 用 Flow Logs 分辨 SG 與 NACL

Flow Logs 的 action 欄位不會告訴你是 SG 還是 NACL 擋的，但 stateful 與 stateless 的差異會留下線索。假設你從 `203.0.113.12` ping 一台 instance，看到兩筆紀錄：

```text
... 203.0.113.12 10.20.0.10 0 0 1 4 336 ... ACCEPT OK
... 10.20.0.10 203.0.113.12 0 0 1 4 336 ... REJECT OK
```

入站被接受、回應出站被拒絕。如果是 SG 允許了入站，回應一定會自動放行（stateful），不可能出現出站 REJECT；所以這一定是 **NACL 的出站規則**擋住了回應。這個推理方式在官方文件與考試中都出現過。

### Flow Logs 的限制

- **不是即時的**：流量會先在聚合時間窗內彙總（最長聚合時間預設 10 分鐘，可設為 1 分鐘；Nitro 架構的 instance 一律 1 分鐘以內），再過幾分鐘才送達目的地。不適合拿來做「即時封鎖」。
- **沒有封包內容**：需要看 payload（例如做入侵偵測分析）要用 **VPC Traffic Mirroring**，把 ENI 的封包複製一份送到分析設備。
- **有些流量不記錄**：送往 Amazon-provided DNS 的查詢（DNS 查詢要用 Route 53 Resolver query logging，第 8 章）、instance metadata、Amazon Time Sync、DHCP、Windows 授權啟用等。
- **建立後不能修改設定**：要增減欄位、換 IAM role 或目的地，只能刪除後重建。
- Flow Logs 本身不影響網路效能或延遲，但會產生日誌儲存與傳送費用。

## 6.11 不送封包也能診斷：Reachability Analyzer 與 Network Access Analyzer

Flow Logs 記錄「已經發生的流量」。但很多問題在流量發生前就想回答：這兩台機器**應該**能互連嗎？有沒有任何**不該存在**的路徑？AWS 提供兩個以設定分析為基礎的工具。

### Reachability Analyzer：A 到得了 B 嗎？

**VPC Reachability Analyzer** 讓你指定一個來源（例如某台 EC2、某個 IGW）和一個目的地（例如 RDS 的 ENI、某個 port），它會**分析設定**（route table、SG、NACL、peering、Transit Gateway、endpoint 等），判斷封包理論上能不能到達。它**不會真的送封包**，所以不會影響正式流量，也不需要目的端在線上。

結果分兩種：

- **Reachable**：列出逐跳路徑，例如「ENI → SG-app 出站規則 #2 → nacl-app → route table rtb-0appa → nacl-data → SG-db 入站規則 #1 → ENI」。
- **Not reachable**：指出**第一個擋住的元件**，例如「nacl-data 入站沒有允許 TCP 3306 的規則」。

它非常適合變更後的驗證：小林每次修改網路設定後，都對「ALB → App:8080」「App → RDS:3306」跑一次分析，確認關鍵路徑仍然通。與 Organizations 整合後，還能分析跨帳號的路徑。

### Network Access Analyzer：有沒有不該存在的路？

Reachability Analyzer 回答「一條特定路徑通不通」；**Network Access Analyzer** 回答「整個環境裡，有沒有任何符合某個條件的路徑」。你定義一個 **Network Access Scope（網路存取範圍）**，例如：

- 「任何從 Internet Gateway 出發，能到達 data subnet 中 ENI 的路徑」
- 「任何從 development VPC 能到達 production VPC 的路徑」

它會分析所有相關設定，把符合條件的路徑列成 **findings（發現項目）**。如果 findings 是空的，就證明在設定層面沒有這種路徑。這正是稽核人員想要的證據：不是「我們檢查了幾台」，而是「設定上不存在這種路徑」。

| 工具 | 回答的問題 | 資料來源 | 典型使用時機 |
|---|---|---|---|
| VPC Flow Logs | 實際發生過哪些流量、被允許或拒絕 | 實際流量 metadata | 事件調查、流量分析、異常偵測 |
| Reachability Analyzer | A 能不能到 B，被誰擋住 | 設定分析 | 連線故障排除、變更驗證 |
| Network Access Analyzer | 有沒有不該存在的路徑 | 設定分析 | 合規稽核、找出意外暴露 |
| Traffic Mirroring | 封包內容是什麼 | 實際封包複本 | 深度封包檢查、入侵偵測 |
| CloudTrail | 誰在什麼時候改了 SG 或 route table | API 呼叫紀錄 | 追查設定變更（第 16 章） |

## 6.12 組起來：Wanderly 的上線後安全網路

把本章所有控制加到第 5 章的架構上：

```text
                         Internet
                            │
                   [Internet Gateway]
                            │
  VPC 10.20.0.0/16 ─────────┼───────────────────────────────────────────
  │ public-a/c  [nacl-public: 443 入、1024-65535 回程、封鎖名單]           │
  │   [ALB  SG-alb: 443 from 0.0.0.0/0]      [NAT-a] [NAT-c]             │
  │        │ ①                                  ▲ ④ 只剩外部金流 API       │
  │ app-a/c [nacl-app]                          │                       │
  │   [App  SG-app: 8080 from SG-alb] ──────────┘                       │
  │        │ ②                 │ ③                                       │
  │        │                   ├──► [vpce S3 gateway] ──► S3            │
  │        │                   └──► [vpce secretsmanager ENI             │
  │        ▼                          SG-vpce: 443 from SG-app]         │
  │ data-a/c [nacl-data: 只允許 app CIDR 的 3306 與回程]                  │
  │   [RDS  SG-db: 3306 from SG-app]                                    │
  │                                                                     │
  │  Flow Logs（VPC 層級）──► S3 log bucket（Parquet）──► Athena           │
  └─────────────────────────────────────────────────────────────────────┘
```

① ALB 只接受 443，並只能把請求送到掛 SG-app 的機器。② App 經 SG 參照連到 RDS；data subnet 的 NACL 再加一道 subnet 層級的限制，就算有人把 SG-db 寫錯，其他 subnet 的機器也到不了 3306。③ S3 流量經 gateway endpoint（免費），密碼讀取經 interface endpoint，兩者都不再經過 NAT；bucket policy 用 `aws:SourceVpce` 鎖住照片 bucket。④ NAT Gateway 只剩下呼叫外部金流 API 的流量，費用大幅下降。最後，VPC 層級的 Flow Logs 送到 S3，事後可以用 Athena 查詢任何連線紀錄。

SG chaining 的 CloudFormation 片段（注意 SG-db 與 SG-vpce 的來源都是 SG，而不是 CIDR）：

```yaml
Resources:
  AlbSg:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Public HTTPS to ALB
      VpcId: !Ref Vpc
      SecurityGroupIngress:

          FromPort: 443
          ToPort: 443
          CidrIp: 0.0.0.0/0
  AppSg:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: App tier, only from ALB
      VpcId: !Ref Vpc
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 8080
          ToPort: 8080
          SourceSecurityGroupId: !Ref AlbSg
  DbSg:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: MySQL, only from app tier
      VpcId: !Ref Vpc
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 3306
          ToPort: 3306
          SourceSecurityGroupId: !Ref AppSg
  VpceSg:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Interface endpoints, HTTPS from app tier
      VpcId: !Ref Vpc
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 443
          ToPort: 443
          SourceSecurityGroupId: !Ref AppSg
  SecretsEndpoint:
    Type: AWS::EC2::VPCEndpoint
    Properties:
      VpcId: !Ref Vpc
```

## 6.13 比較與選型

### 要擋流量，用哪一層？

```text
要控制的是什麼？
├─ 某個服務只接受特定上游（ALB→App→DB）→ Security group 參照
├─ 要「拒絕」特定 IP 或網段 → NACL deny（少量）；大量或 HTTP 層 → WAF（第 16 章）
├─ 整個 subnet 的硬邊界，不依賴各團隊的 SG → NACL
├─ 依網域名稱過濾出站（只准連 *.stripe.com）→ Network Firewall（第 16 章）
└─ 跨數百帳號統一 SG 規範 → Firewall Manager／Config（6.15 節）
```

### 要私有存取 AWS 服務，用哪種 endpoint？

```text
服務是 S3 或 DynamoDB 嗎？
├─ 是 → 流量只來自本 VPC 內？
│        ├─ 是 → Gateway endpoint（免費，改 route table）
│        └─ 否（地端經 DX/VPN、其他 VPC 經 TGW）→ Interface endpoint
│              （可與 gateway endpoint 並存：VPC 內走 gateway、外部走 interface）
└─ 否 → 服務支援 PrivateLink？
         ├─ 是 → Interface endpoint（記得 SG、private DNS、多 AZ）
         └─ 否 → 仍需 NAT Gateway 出站
```

### Gateway endpoint vs interface endpoint 完整比較

| 比較 | Gateway endpoint | Interface endpoint |
|---|---|---|
| 支援服務 | S3、DynamoDB | 大多數 AWS 服務、自家與 SaaS 服務 |
| 機制 | Route table 中的 prefix list route | Subnet 中的 ENI（PrivateLink） |
| DNS | 不變，仍解析 public IP | Private DNS 讓服務名稱解析到 private IP |
| Security group | 無（但來源端 SG 出站要允許 prefix list） | 有，套在 endpoint ENI 上 |
| 地端／其他 VPC 能否使用 | 不能 | 能（需路由與 DNS 配合） |
| 跨 Region | 不支援 | 主要用於同 Region 服務（PrivateLink 已逐步支援部分跨 Region 連線，見第 7 章） |
| 高可用 | 內建 | 自己選多個 AZ 的 subnet |
| Endpoint policy | 支援 | 多數服務支援 |
| 費用 | 免費 | 每 AZ 每小時 + 每 GB |

## 6.14 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 只允許 ALB 連到 app、只允許 app 連到 DB，instance 會擴縮 | SG 參照（source 設為上游的 SG） |
| 封鎖特定惡意 IP | NACL deny，規則編號要小於 allow |
| 回應被擋、連線 timeout，SG 已允許 | NACL 缺 ephemeral ports（1024–65535）回程規則 |
| 新建 NACL 後 subnet 全斷 | Custom NACL 預設全部拒絕 |
| Private subnet 大量存取 S3／DynamoDB，降低 NAT 成本 | Gateway endpoint |
| 地端經 Direct Connect／VPN 私有存取 S3 | S3 interface endpoint（DNS 用 endpoint 專屬名稱或 Resolver inbound endpoint） |
| Private subnet 呼叫 Secrets Manager／SSM／KMS 不經 Internet | Interface endpoint + private DNS |
| Interface endpoint 建好，名稱仍解析成 public IP | 開啟 private DNS，並確認 `enableDnsSupport`、`enableDnsHostnames` |
| DNS 解析到 endpoint IP 但 timeout | Endpoint ENI 的 SG 沒允許 443 |
| Bucket 只能從特定 VPC／endpoint 存取 | Bucket policy `aws:SourceVpce`／`aws:SourceVpc` |
| 防止從 VPC 把資料寫到其他人的 bucket | Endpoint policy 限制 Resource |
| 記錄誰連了資料庫、事件調查 | VPC Flow Logs（送 S3 + Athena 或 CloudWatch Logs） |
| 需要封包內容做 IDS 分析 | Traffic Mirroring |
| 不送流量就找出兩台機器為何不通 | Reachability Analyzer |
| 證明沒有從 Internet 到 DB 的路徑 | Network Access Analyzer |

**常見陷阱**：

1. 選項說「在 SG 加入 deny 規則」：SG 沒有 deny。
2. 選項說「NACL 的 deny 永遠優先」：NACL 是依編號 first match，編號大的 deny 會被前面的 allow 蓋過。
3. 選項說「建立 gateway endpoint 讓地端或 peered VPC 存取 S3」：gateway endpoint 不能延伸到 VPC 之外。
4. 選項說「bucket policy 用 `aws:SourceIp` 允許 VPC 的 private CIDR」：經 endpoint 的請求要用 `aws:SourceVpce`／`aws:SourceVpc`／`aws:VpcSourceIp`。
5. 選項說「endpoint policy 允許了，所以 role 不需要 IAM 權限」：endpoint policy 只限制、不授權。
6. 選項說「用 Flow Logs 即時封鎖攻擊」或「用 Flow Logs 看封包內容」：Flow Logs 有延遲、只有 metadata。

## 6.15 SAP 加深：多帳號的網路控制與資料邊界

SAA 題目通常只有一個 VPC；SAP 題目會問「數百個帳號、數百個 VPC 時，這些控制怎麼規模化」。

### 集中化 interface endpoints

每個 VPC 各自建立十幾個 interface endpoint，乘上數百個 VPC 與多個 AZ，小時費會非常可觀，管理也分散。常見的做法是在 **shared services VPC** 集中建立 interface endpoint，其他 VPC 經 Transit Gateway 連過來。這時 private DNS 不能直接用（AWS 管理的隱藏 hosted zone 只關聯 endpoint 所在的 VPC），要改為：關閉 endpoint 的 private DNS，自己建立服務名稱的 private hosted zone 指向 endpoint，再把這個 hosted zone 關聯到所有 spoke VPC（跨帳號關聯或透過 Route 53 Resolver 規則共享）。取捨是：省下大量 endpoint 小時費，但多了 TGW 的每 GB 處理費與一個共享的故障點。第 41 章會完整設計這個架構。

### 規模化管理 SG

- **AWS Firewall Manager**（需 Organizations）可以集中派發 SG 政策：例如替所有帳號的 ALB 套上共同的基準 SG、稽核並自動修正開放 `0.0.0.0/0` 的 SSH／RDP 規則、清理未使用或重複的 SG（第 16 章）。
- **AWS Config 規則**（例如檢查 SG 是否只開放授權的 port、default SG 是否為空）可以持續偵測，搭配自動修復。
- 在 VPC sharing（第 5、7 章）的環境中，多個帳號的資源在同一個 VPC 裡，SG 參照可以用來表達跨團隊的服務授權。

### 資料邊界（data perimeter）

SAP 的安全題常要求「公司資料只能被公司的身份、從公司的網路存取」。在網路這一側，作法就是本章的工具組合放大到組織層級：

- **Bucket policy／RCP 的網路條件**：用 `aws:SourceVpce`、`aws:SourceVpc` 確保資料只從預期網路被存取（RCP 見第 14 章）。
- **Endpoint policy 的資源條件**：用 `aws:ResourceOrgID` 限制只能存取屬於自家 Organization 的資源，比逐一列出 bucket ARN 更容易維護。
- **身份條件**：用 `aws:PrincipalOrgID` 確保只有自家 Organization 的身份能存取資源（第 13、14 章）。

三者依序封住三個方向：「從非預期的網路存取我的資料」「我的人把資料放到不屬於公司的資源」「外部身份存取我的資料」。

### 證據與稽核

在多帳號環境，Flow Logs 通常集中送到 log archive 帳號的 S3（第 40 章），用 Athena 查詢；Network Access Analyzer 的 scope 可以把「prod 與 dev 不能互通」「Internet 到 data subnet 無路徑」這類政策寫成可重複執行的檢查，搭配 Transit Gateway 等跨 VPC 元件，稽核整個組織的網路分段。

## 本章重點整理

- Security group 套在 ENI 上，stateful、只有 allow、規則不分順序；新 SG 入站全拒、出站全開。
- SG 的來源可以是另一個 SG，這讓 ALB→App→DB 的授權不依賴會變動的 IP，是三層式架構最小權限的標準寫法。
- NACL 套在 subnet 邊界，stateless、有 allow 與 deny，依規則編號由小到大 first match；同 subnet 內的流量不經過 NACL。
- Default NACL 全部允許；custom NACL 建立時全部拒絕；stateless 的 NACL 必須為回程放行 ephemeral ports（建議 1024–65535）。
- 封鎖特定 IP 用 NACL deny（編號要比 allow 小）；SG 做不到。
- Gateway endpoint 只支援 S3 與 DynamoDB，透過 route table 中的 prefix list 生效，免費、不改 DNS，但只能在本 VPC 內、同 Region 使用。
- Interface endpoint 在 subnet 中建立 ENI（PrivateLink），有 SG、可用 private DNS、按 AZ 小時與流量收費，地端與其他 VPC 也能經路由使用。
- Interface endpoint 的 private DNS 需要 VPC 開啟 `enableDnsSupport` 與 `enableDnsHostnames`；DNS 正確但 timeout 時先查 endpoint 的 SG。
- Endpoint policy 只限制、不授權；預設允許全部，可限制只能存取自家 bucket 以防資料外洩。
- Bucket policy 用 `aws:SourceVpce`／`aws:SourceVpc` 把存取鎖在指定網路路徑；經 endpoint 的請求不適用 `aws:SourceIp`。
- VPC Flow Logs 記錄 ENI 流量的 metadata（含 ACCEPT／REJECT），可送到 CloudWatch Logs、S3、Firehose；不含封包內容、非即時、不記錄 Amazon DNS 查詢。
- 入站 ACCEPT 但回應出站 REJECT 的 Flow Logs 組合，代表 NACL 擋住了回程。
- Reachability Analyzer 以設定分析兩點之間的路徑並指出擋住的元件；Network Access Analyzer 找出符合條件的所有意外路徑，適合合規證明。
- 多帳號環境用集中 interface endpoints、Firewall Manager、資料邊界條件鍵與集中 Flow Logs 把這些控制規模化。

## 本章練習題

### 練習 6-1｜SAA｜單選｜三層式 SG 最小權限

Wanderly 的架構是 Internet → ALB → 應用程式 EC2（Auto Scaling，每天替換多次）→ RDS for MySQL。安全團隊要求：應用程式只能接受來自 ALB 的 8080 流量，資料庫只能接受來自應用程式的 3306 流量，而且 instance 替換時不需要人工更新任何規則。

哪個設定最能滿足需求？

- A. 應用程式 SG 允許來源為 public subnet CIDR 的 8080；資料庫 SG 允許來源為 app subnet CIDR 的 3306
- B. 應用程式 SG 允許來源為 ALB SG 的 8080；資料庫 SG 允許來源為應用程式 SG 的 3306
- C. 應用程式 SG 允許 `0.0.0.0/0` 的 8080，再用 NACL 拒絕非 ALB 的來源；資料庫 SG 允許 VPC CIDR 的 3306
- D. 每次 Auto Scaling 啟動 instance 時，用 Lambda 把新 instance 的 IP 加入資料庫 SG

> [!answer]- 答案：B
> **A ✗** Subnet CIDR 比實際需要的範圍寬：public subnet 裡的 NAT Gateway 或其他資源、app subnet 裡不相關的機器都會被信任。它雖然不需要隨 instance 更新，但不是最小權限。
>
> **B ✓** SG 參照以「掛著哪個 SG」作為身份，新啟動的應用程式 instance 只要掛上應用程式 SG，就自動被資料庫允許，被終止的 instance 自動失去資格，完全不需要更新規則，也只信任真正的上游。
>
> **C ✗** NACL 只能用 CIDR，無法辨識「哪些封包來自 ALB」；資料庫允許整個 VPC CIDR 也過寬，正是 6.1 節顧問指出的問題。
>
> **D ✗** 技術上可行，但營運負擔高、有競態與失敗風險，而且 SG 參照本來就能原生做到同樣的事。
>
> **考點**：SAA-1.2｜SG chaining 與 SG 參照

### 練習 6-2｜SAA｜單選｜NACL ephemeral ports

一個 public subnet 放著 web server，NACL 已改成 custom NACL：入站規則 100 允許 `0.0.0.0/0` 的 TCP 443；出站規則 100 允許 `0.0.0.0/0` 的 TCP 443。Web server 的 SG 允許入站 443。使用者連線時一律 timeout，但工程師從同一個 subnet 內的另一台機器連 web server 卻正常。

最可能的原因與修正是什麼？

- A. NACL 出站沒有允許回應用戶端的 ephemeral ports；加入出站 TCP 1024–65535 到 `0.0.0.0/0` 的允許規則
- B. SG 是 stateless，需要在 SG 出站加入 1024–65535 的規則
- C. Subnet 需要 NAT Gateway 才能回應 Internet 上的使用者
- D. 同一個 subnet 的測試成功表示 NACL 沒有問題，應檢查 Internet Gateway 的頻寬

> [!answer]- 答案：A
> **A ✓** 伺服器回應的目的 port 是使用者電腦的 ephemeral port，不是 443。NACL 是 stateless，回應被出站規則當成新封包評估，只允許 443 就會被 `*` 規則拒絕。同 subnet 內的測試不經過 NACL，所以正常，這正好證明問題在 NACL。
>
> **B ✗** SG 是 stateful，允許入站的連線，其回應會自動放行，不需要出站 ephemeral 規則。
>
> **C ✗** 有 public IP 且 route table 指向 IGW 的 web server 可以直接經 IGW 回應，不需要 NAT。
>
> **D ✗** 同 subnet 流量不經過 NACL，因此無法證明 NACL 沒問題；IGW 也不會成為頻寬瓶頸。
>
> **考點**：SAA-1.2｜NACL stateless 與 ephemeral ports

### 練習 6-3｜SAA｜單選｜NACL 規則順序

Wanderly 的 public subnet NACL 入站規則如下：規則 100 允許 `0.0.0.0/0` 的 TCP 443；規則 200 拒絕 `198.51.100.0/24` 的所有流量。監控顯示 `198.51.100.0/24` 仍持續對 ALB 發送大量 443 請求並成功建立連線。

應如何修正？

- A. 在 ALB 的 SG 加入一條拒絕 `198.51.100.0/24` 的規則
- B. 把規則 200 改成更精確的 /32 規則，NACL 會優先比對 prefix 較長的規則
- C. 刪除規則 100，讓 `*` 規則處理其他流量
- D. 新增一條編號小於 100（例如 50）的規則，拒絕 `198.51.100.0/24` 的所有流量，再刪除規則 200

> [!answer]- 答案：D
> **A ✗** SG 只有 allow 規則，無法寫 deny。
>
> **B ✗** Longest prefix match 是 route table 的選路規則；NACL 是依規則編號由小到大，第一條符合者決定結果。
>
> **C ✗** 刪除規則 100 會讓所有使用者的 443 都被 `*` 規則拒絕，網站全面中斷。
>
> **D ✓** NACL 從最小編號開始評估，第一個符合的規則決定結果。把 deny 放在規則 50，惡意網段在碰到規則 100 之前就被拒絕；其他來源仍由規則 100 允許。
>
> **考點**：SAA-1.2｜NACL first match 與 explicit deny

### 練習 6-4｜SAA｜選兩項｜SG 與 NACL 的特性

一位新進工程師在整理網路安全文件，寫下了五個敘述。

哪兩個敘述是正確的？（選兩項）

- A. Security group 可以設定 deny 規則，並依規則編號由小到大評估
- B. Network ACL 是 stateless，回應流量必須由相反方向的規則明確允許
- C. 一個 ENI 只能套用一個 security group
- D. 同一個 subnet 內兩台 instance 之間的流量，會由 security group 評估，但不經過該 subnet 的 network ACL
- E. Network ACL 的規則可以把另一個 security group 指定為來源

> [!answer]- 答案：B、D
> **A ✗** 這描述的是 NACL。SG 只有 allow，所有規則合併評估，沒有編號與順序。
>
> **B ✓** NACL 不追蹤連線狀態，每個封包獨立評估，因此去程與回程（包含 ephemeral ports）都要有規則。
>
> **C ✗** 一個 ENI 可以套用多個 SG（預設 quota 為 5 個，可申請提高），規則合併生效。
>
> **D ✓** NACL 只在封包跨越 subnet 邊界時評估；同 subnet 內的流量不跨邊界，只有雙方 ENI 上的 SG 會檢查。
>
> **E ✗** NACL 規則的來源與目的只能是 CIDR，不能引用 SG。
>
> **考點**：SAA-1.2｜SG 與 NACL 的評估模型

### 練習 6-5｜SAA｜單選｜Custom NACL 預設行為

最可能的原因是什麼？

- A. Custom NACL 建立時只有最後的 `*` deny 規則，關聯後 data subnet 的所有進出流量都被拒絕
- B. 關聯新 NACL 時，AWS 會重新啟動 subnet 中的 RDS instance
- C. Custom NACL 會覆寫 data subnet 中所有 security group 的規則
- D. Custom NACL 只影響新建立的連線，因此問題一定出在 RDS 本身

> [!answer]- 答案：A
> **A ✓** 和 default NACL（全部允許）不同，custom NACL 建立時沒有任何 allow 規則，只有無法刪除的 `*` deny。Subnet 一關聯就等於全部封鎖。正確做法是先把規則加好，再進行關聯。
>
> **B ✗** NACL 是網路層過濾，關聯或修改不會重新啟動任何資源。

> **C ✗** NACL 與 SG 是兩道獨立的檢查，NACL 不會修改 SG；兩者都要允許，流量才能通過。

### 練習 6-6｜SAA｜單選｜地端私有存取 S3

最合適的做法是什麼？

- A. 在地端路由器加入指向 S3 gateway endpoint 的靜態路由
- B. 在 VPC 建立 S3 interface endpoint，讓地端經 Direct Connect 連到 endpoint 的 private IP，並設定地端的 DNS 解析到該 endpoint
- C. 讓地端流量經 Direct Connect 進入 VPC 後，再經 NAT Gateway 存取 S3
- D. 為 S3 bucket 啟用 Transfer Acceleration，讓地端經 edge location 上傳

> [!answer]- 答案：B
> **A ✗** Gateway endpoint 只是 VPC route table 中的一條 prefix list route，沒有可被外部路由的位址，無法從地端、VPN 或 peered VPC 使用。
>
> **B ✓** Interface endpoint 是有 private IP 的 ENI，任何能經 Direct Connect 路由到 VPC 的地端主機都能使用它。地端需要把 S3 名稱解析到 endpoint（例如透過 Route 53 Resolver inbound endpoint 或 endpoint 專屬 DNS 名稱）。既有的 gateway endpoint 可以繼續服務 VPC 內的 EC2。
>
> **C ✗** 即使設法讓地端流量經 VPC 轉到 NAT Gateway，最後仍是經 IGW 走到 S3 的 public endpoint，等於走 Internet 路徑，違反規定，還多了 NAT 每 GB 處理費。
>
> **D ✗** Transfer Acceleration 經由 Internet 上的 edge location 加速，正好違反「不經過公共 Internet」的規定，也會增加費用。
>
> **考點**：SAA-3.4、SAA-1.2｜gateway vs interface endpoint 的可達範圍

### 練習 6-7｜SAA｜單選｜Interface endpoint timeout

### 練習 6-8｜SAA｜單選｜Endpoint policy 防止資料外洩

Wanderly 的影像處理 worker 經 S3 gateway endpoint 存取 S3。資安團隊擔心：如果 worker 被入侵，攻擊者可以用 worker 的網路把照片上傳到攻擊者自己帳號的 bucket。Worker 只需要存取 `wanderly-photos-prod` 這個 bucket。

哪個做法最直接地降低這個風險？

- A. 在 `wanderly-photos-prod` 的 bucket policy 加入 `aws:SourceVpce` 條件
- B. 移除 worker 的 IAM role 對所有 S3 的權限
- C. 在 worker 的 SG 出站規則中，只允許到 S3 prefix list 的 443
- D. 修改 S3 gateway endpoint 的 endpoint policy，只允許對 `wanderly-photos-prod` 及其物件的必要動作

> [!answer]- 答案：D
> **A ✗** Bucket policy 保護的是「自家 bucket 只能從哪裡被存取」，控制不了 worker 把資料寫到「別人的 bucket」；攻擊者 bucket 的 policy 由攻擊者決定。
>
> **B ✗** 移除所有 S3 權限會讓 worker 無法運作；而且攻擊者可能使用自己帳號的 access key 寫入自己的 bucket，worker role 的權限擋不住。
>
> **C ✗** S3 prefix list 包含該 Region 所有 bucket 的位址，SG 無法區分是哪個帳號的 bucket。
>
> **D ✓** Endpoint policy 控制「經過這個 endpoint 能存取哪些資源」，不論請求用的是誰的憑證。只允許 `wanderly-photos-prod`，就能阻擋經由這條路徑寫入其他 bucket。
>
> **考點**：SAA-1.3、SAA-1.2｜endpoint policy 與資料外洩

### 練習 6-9｜SAA｜單選｜aws:SourceVpce 條件

Wanderly 的合規要求是：`wanderly-contracts` bucket 中的合約檔案只能從 production VPC 中的應用程式存取，即使某把 IAM access key 外洩，攻擊者也不能從外部下載。Production VPC 已有 S3 gateway endpoint `vpce-0abc1234`。

哪個 bucket policy 設計最合適？

- A. 加入 Deny 陳述，條件為 `aws:SourceVpce` 不等於 `vpce-0abc1234`，並為必要的管理 role 規劃例外
- B. 加入 Allow 陳述，條件為 `aws:SourceIp` 等於 production VPC 的 CIDR `10.20.0.0/16`
- C. 加入 Deny 陳述，條件為 `aws:SourceIp` 不等於 NAT Gateway 的 Elastic IP
- D. 開啟 S3 Block Public Access，即可阻擋所有不是來自 VPC 的請求

> [!answer]- 答案：A
> **A ✓** 經 VPC endpoint 的請求會帶有 `aws:SourceVpce`。用 Deny 拒絕所有不是從指定 endpoint 來的請求，外洩的 key 在其他地方使用時就會被拒絕。因為 Deny 也會擋住 console 操作，需要為管理 role 規劃例外。
>
> **B ✗** 經 VPC endpoint 的請求，`aws:SourceIp` 不是 VPC 的 private IP，條件不會符合；而且 Allow 無法阻止其他已有權限的身份從外部存取。
>
> **C ✗** S3 流量走 gateway endpoint 後不經過 NAT Gateway，來源不會是 NAT 的 EIP；這個條件會連合法流量都擋住。
>
> **D ✗** Block Public Access 阻擋的是「公開」（匿名或任何人）存取的設定，不會阻擋持有有效憑證的身份從外部網路存取。
>
> **考點**：SAA-1.3｜bucket policy 網路條件鍵

### 練習 6-10｜SAA｜單選｜Flow Logs 判讀

工程師從 `203.0.113.12` 對 Wanderly 一台 public subnet 的 instance 執行 ping，沒有收到回應。VPC Flow Logs 中出現兩筆紀錄：一筆是 `203.0.113.12 → 10.20.0.10` 的 ICMP，action 為 ACCEPT；另一筆是 `10.20.0.10 → 203.0.113.12` 的 ICMP，action 為 REJECT。

最可能是哪個設定造成的？

- A. Instance 的 SG 沒有允許入站 ICMP
- B. Instance 的 SG 沒有允許出站 ICMP 回應
- C. Subnet 的 route table 缺少指向 IGW 的 route
- D. Subnet 的 NACL 允許入站 ICMP，但出站規則沒有允許回應

> [!answer]- 答案：D
> **A ✗** 若 SG 沒有允許入站 ICMP，第一筆紀錄的 action 會是 REJECT，而不是 ACCEPT。
>
> **B ✗** SG 是 stateful：入站請求被允許後，回應會自動放行，不會因為出站規則而被拒絕。
>
> **C ✗** Flow Logs 的 action 只反映 SG 與 NACL 的判定，REJECT 代表被其中之一拒絕，缺少 route 不會讓 action 變成 REJECT。而且題目說這是 public subnet，本來就有指向 IGW 的 route。
>
> **D ✓** 入站 ACCEPT、回應出站 REJECT 的組合，只可能來自 stateless 的控制。NACL 不記得入站請求，回應需要獨立的出站規則；缺少時回應就被拒絕。
>
> **考點**：SAA-1.2｜Flow Logs 與 stateful／stateless 推理

Wanderly 剛修改了多張 route table、SG 與 NACL。工程師想在正式切換流量前，確認「App instance 到 RDS 的 TCP 3306」以及「ALB 到 App 的 TCP 8080」兩條路徑都可達；若不可達，要知道是哪個元件擋住。資料庫目前尚未接收正式流量。

### 練習 6-13｜SAP｜單選｜集中化 interface endpoints

> **A ✓** ECR 的 API 呼叫（取得授權 token、image manifest）與 Docker registry 流量分別需要 `ecr.api` 與 `ecr.dkr`；寫入日誌需要 `logs`。缺任何一個，對應功能都會在 isolated subnet 中 timeout。
>
> **B ✗** 規範禁止任何 Internet 出站路徑，暫時的 NAT 也違反規範；而且 endpoint 可以完全取代它。
>
> **C ✓** ECR 的 image layer 實際存放在 S3，拉取 image 時會直接從 S3 下載 layer。只建 ECR endpoint 而沒有 S3 endpoint，是拉取失敗最常見的原因；使用免費的 gateway endpoint 即可。
>
> **D ✗** Egress-only IGW 提供 IPv6 往 Internet 的出站路徑，同樣違反規範，也不是存取 AWS 服務的私有方式。
>
> **E ✗** ECR 是 AWS 服務，不能用 VPC peering 連線；私有存取要用 interface endpoint。
>
> **考點**：SAP-1.1、SAP-2.3｜isolated subnet 的 endpoint 依賴
