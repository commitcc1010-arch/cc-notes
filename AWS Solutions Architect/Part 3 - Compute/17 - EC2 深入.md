## 17.1 故事：促銷夜的那台 t3.medium

Wanderly 的第一版網站跑在一台 `t3.medium` 上。工程師小林當初選它的理由很簡單：便宜，而且平常 CPU 使用率只有 10%。三個月來一直很順，直到第一次大型促銷。

促銷開始後二十分鐘，CPU 使用率衝到 100%，網站還撐得住；但一個小時後，CPU 使用率的圖仍顯示 100%，網頁卻慢到幾乎打不開。小林重開機、加大 swap 都沒用。後來才發現，T 系列 instance 平常累積的「CPU credits」在高峰的第一個小時就用完了，instance 被限制回只有基準效能（baseline）的速度。機器沒有壞，只是「額度」花光了。

促銷結束後，問題接二連三。行銷部門要每晚把當天上傳的十萬張旅館照片轉成多種尺寸，這個批次工作如果晚一點跑完也無所謂；資料團隊要訓練推薦模型，需要多台機器之間極低延遲的網路；財務長則看著帳單問：「我們的機器 24 小時都開著，為什麼一直用最貴的計價方式？」最後，安全團隊在第 16 章的事件後提出要求：所有機器必須用統一、修補過的映像啟動，而且要防止應用程式漏洞被利用來偷走 instance 上的 IAM 憑證。

這一章就從「怎麼選一台對的機器」開始，接著處理「怎麼可重複且安全地啟動它」「資料放在哪裡才不會不見」「機器之間怎麼擺放」，最後回答財務長的問題：同一台 EC2，可以有六種不同的付費方式。

## 17.2 EC2 是什麼：instance、host 與 Nitro

**Amazon EC2（Elastic Compute Cloud）** 提供可隨時建立與刪除的虛擬機器，每一台稱為 **instance**。你決定它的 CPU、記憶體、網路與儲存規格（instance type）、作業系統與軟體（AMI）、放在哪個 subnet、套用哪些 security group，以及用什麼 IAM role 存取其他 AWS 服務。

Instance 實際跑在 AWS 資料中心的實體伺服器上，這台實體伺服器稱為 **host**。預設情況下，一台 host 可能同時跑著不同客戶的 instance，由 hypervisor 隔離。現代的 EC2 instance 大多建立在 **AWS Nitro System** 上：AWS 把網路、儲存、管理功能移到專用的 Nitro 硬體卡，hypervisor 變得非常輕量，所以 instance 幾乎能用到 host 全部的運算資源，也讓 AWS 能提供 `metal`（直接使用實體伺服器、沒有 hypervisor）這類規格。

理解「instance 在某台 host 上」很重要，因為本章很多行為都源自它：instance store 是 host 上的實體磁碟，所以 instance 換 host 時資料會消失；placement group 是在控制 instance 落在哪些 host 與機架；Dedicated Host 則是讓你獨佔一整台 host。

> [!note] EC2 屬於哪個範圍？
> Instance 是 **zonal** 資源：它跑在某個 AZ 的某個 subnet 裡。AMI 與 EBS snapshot 是 **Regional** 資源。Instance type 的供應情況則依 Region 與 AZ 而不同，新的 type 不一定在每個 AZ 都有。

## 17.3 Instance type：讀懂名字，就知道它擅長什麼

### 命名規則

以 `m7gd.2xlarge` 為例：

```text
  m    7    g d  .  2xlarge
  │    │    │ │      │
  │    │    │ │      └─ 大小：nano、micro、small、medium、large、xlarge、2xlarge … 48xlarge、metal
  │    │    │ └─ 額外屬性：d = 附 NVMe instance store
  │    │    └─ 處理器：g = AWS Graviton（Arm），i = Intel，a = AMD
  │    └─ 世代：數字越大越新，通常價格效能更好
  └─ Family（系列）：m = 一般用途
```

常見的額外屬性字母：`n` 表示網路頻寬更高，`e` 表示額外的記憶體或儲存，`z` 表示高時脈，`flex` 表示價格較低、適合不需要持續滿載的 workload。同一系列中，大小每升一級，vCPU、記憶體與通常的網路頻寬大約都翻倍，價格也跟著翻倍。

### Families 與用途

| 類別 | 常見 family | 特徵 | 適合 |
|---|---|---|---|
| 一般用途（general purpose） | M、T、Mac | CPU 與記憶體均衡，M 約每 vCPU 4 GiB | Web server、應用伺服器、小型資料庫 |
| 運算最佳化（compute optimized） | C | 高 CPU 比例，約每 vCPU 2 GiB | 批次運算、影像轉碼、遊戲伺服器、高效能 web |
| 記憶體最佳化（memory optimized） | R、X、z、High Memory（u） | 大記憶體，R 約每 vCPU 8 GiB | 記憶體內快取、大型關聯式資料庫、即時分析、SAP HANA |
| 儲存最佳化（storage optimized） | I、D、Im／Is | 大量本機 NVMe 或 HDD，極高 IOPS 或循序吞吐 | NoSQL 資料庫、資料倉儲、分散式檔案系統 |
| 加速運算（accelerated computing） | P、G、Trn、Inf、F | GPU、AWS Trainium／Inferentia 晶片、FPGA | 機器學習訓練與推論、圖形渲染 |
| HPC | Hpc | 為緊密耦合的 HPC 最佳化 | 流體力學、氣象模擬 |

選型的思考順序是：先找出 workload 的瓶頸（CPU、記憶體、本機 I/O、網路、GPU），選出對應的 family，再用代表性的負載測試決定大小。「選最大的一般用途 instance 就好」通常既貴又沒有解決真正的瓶頸。AWS 的 **Compute Optimizer** 會依 CloudWatch 指標建議更適合的 type 與大小（第 39 章）。

### Graviton：AWS 自己設計的 Arm 處理器

**AWS Graviton** 是 AWS 設計的 Arm 架構處理器，instance type 名稱帶 `g`（例如 `m7g`、`c7g`、`r8g`）。AWS 官方表示，Graviton2 相較同期的 x86 instance 價格效能最高可好 40%，之後的世代持續改進，同時更省電。

使用 Graviton 的前提是軟體能在 **arm64** 架構上執行：

- 直譯式或 JVM 語言（Python、Node.js、Java、Ruby、PHP）通常不必修改程式，只要相依套件有 arm64 版本。
- 編譯式語言（Go、Rust、C/C++）要重新以 arm64 編譯。
- Container image 要建置 arm64 或 multi-architecture image。
- AMI 必須是 arm64 架構；x86 的 AMI 不能用在 Graviton instance 上。
- 只提供 x86 二進位的商業軟體則無法使用。

許多 AWS 受管服務（RDS、ElastiCache、OpenSearch、Lambda、Fargate）也提供 Graviton 選項，通常只要改一個設定。考試看到「在不修改應用程式的情況下改善價格效能」且應用程式是 Java 或 Python，Graviton 往往是答案；若題目明確說「只有 x86 版本的第三方軟體」，就不是。

## 17.4 Burstable instance：T 系列與 CPU credits

回到促銷夜的問題。T 系列（`t3`、`t3a`、`t4g`）是 **burstable performance instance**：它不保證你隨時能用滿 vCPU，而是提供一個 **baseline（基準效能）**，例如某個大小的 baseline 是每個 vCPU 20%；平常使用率低於 baseline 時累積 **CPU credits**，需要時再用 credits **burst（爆發）** 到 100%。

### Credit 怎麼算

- **1 個 CPU credit = 1 個 vCPU 以 100% 使用率跑 1 分鐘**（也等於 2 個 vCPU 各跑 50% 一分鐘，以此類推）。
- 使用率低於 baseline 時，instance 以固定速率賺取 credits，累積有上限。
- 使用率高於 baseline 時，消耗 credits。
- CloudWatch 指標 `CPUCreditBalance` 顯示剩餘額度，`CPUCreditUsage` 顯示消耗量。

### 兩種模式

| 模式 | Credits 用完時 | 費用 | 預設 |
|---|---|---|---|
| **Standard** | 被限制回 baseline 效能 | 不會額外收費 | T2 預設 |
| **Unlimited** | 可以繼續 burst，使用「surplus credits」 | 若一段期間內平均使用率超過 baseline，超出部分按 vCPU 小時額外收費 | T3、T3a、T4g 預設 |

小林的 instance 若是 standard 模式，就會在 credits 用完後被限速；若是 unlimited 模式，網站不會變慢，但月底帳單會多出 surplus credits 費用（指標 `CPUSurplusCreditsCharged`）。

判斷原則很直接：**T 系列適合「平均使用率低、偶爾短時間尖峰」的 workload**，例如開發環境、小型網站、內部工具。如果一台 T instance 長期使用率都高於 baseline，在 unlimited 模式下額外費用累加起來，往往比直接用同等大小的 M 或 C 系列還貴；在 standard 模式下則會持續被限速。這時正確做法是改用固定效能的 family。

> [!warning] 常見誤解
> 「換成更大的 T instance 就不會被限速。」更大的 T instance 有較多 vCPU 與較高的 credit 累積上限，但 baseline 比例並不會變成 100%。只要負載長期高於 baseline，credits 遲早會用完。根本解法是改用 M／C 系列，或把負載分散到多台機器（第 18 章的 Auto Scaling）。

## 17.5 AMI：把「一台設定好的機器」變成可重複的範本

小林第一次架網站時，是開好 instance 後 SSH 進去手動安裝 nginx、設定檔與應用程式。第二台機器又手動做一次，結果兩台的套件版本不一樣。要讓每台機器都一樣，需要一個「範本」。

### AMI 裡有什麼

**AMI（Amazon Machine Image）** 是啟動 instance 用的映像，包含：

- 一個或多個 **EBS snapshot**（對 EBS-backed AMI 而言），其中 root volume snapshot 包含作業系統與已安裝的軟體。
- **Block device mapping**：啟動時要建立哪些 volume、大小與類型。
- **Launch permissions**：哪些帳號可以用這個 AMI 啟動 instance。
- 架構（x86_64 或 arm64）、虛擬化與開機模式等屬性。

AMI **不包含** instance type、subnet、security group、IAM role、key pair、user data，這些是在啟動時（通常透過 launch template，第 18 章）指定的。

AMI 有幾個來源：AWS 提供的（Amazon Linux 2023、Ubuntu、Windows Server 等）、AWS Marketplace 廠商提供的（可能附帶軟體授權費）、社群公開的，以及你自己從 instance 建立的。對自己建立的 AMI，建立前最好停止 instance 或確保檔案系統一致；預設情況下 EC2 會在建立 AMI 時重新開機以確保一致性。

### Region 範圍、複製與分享

**AMI 是 Regional 資源**，只能在它所在的 Region 啟動 instance。要在另一個 Region 使用（例如 DR），必須 **copy AMI** 到目標 Region：

- 複製後在目標 Region 得到一個**新的 AMI ID**，背後的 snapshot 也會被複製。
- 加密的 snapshot 複製時要指定目標 Region 可用的 KMS key（KMS key 也是 Regional 的，除非使用 multi-Region key，第 15 章）。
- Launch permissions 不會跟著複製。

**分享 AMI** 是修改 launch permissions，可以分享給特定帳號、整個 Organization 或特定 OU，也可以設為公開。分享加密的 AMI 時有一個常考的限制：**用 AWS managed key（`aws/ebs`）加密的 AMI 不能分享**；必須使用 customer managed key，並在 key policy 中授權對方帳號使用該 key。帳號層級可以啟用 **block public access for AMIs**，防止有人不小心把 AMI 設為公開。

Deregister（取消註冊）AMI 不會自動刪除背後的 snapshot，snapshot 會繼續收費，要另外清理。AMI 可以設定 **deprecation date** 讓它在一段時間後不再出現在搜尋結果，也可以啟用 deregistration protection 防止誤刪。

### Golden AMI 與 bake vs bootstrap

**Golden AMI** 是組織核准的標準映像：已安裝修補、強化設定（hardening）、監控與安全 agent，並經過測試。所有 workload 都從 golden AMI（或以它為基礎的應用程式 AMI）啟動，安全團隊就能確保每台機器的起點一致。

把軟體安裝到機器上有兩種策略：

| 策略 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **Bake（預先烘焙）** | 把作業系統、套件、甚至應用程式都裝進 AMI | 開機快，適合 Auto Scaling 快速擴展；每台完全一致 | 每次變更都要重做 AMI |
| **Bootstrap（開機時安裝）** | 用基本 AMI，開機時由 user data 或設定管理工具安裝 | 變更彈性大，不用頻繁重建映像 | 開機慢，安裝來源故障時新機器起不來 |

實務上多採折衷：把作業系統、修補與 agent 烘焙進 golden AMI，應用程式版本與設定在開機時拉取。題目若強調「新 instance 必須在最短時間內開始服務」，答案傾向 bake 進 AMI。

**EC2 Image Builder** 能自動化整個流程：定義 recipe（基礎映像 + 安裝元件）、執行測試、產生 AMI、複製到多個 Region 並分享給指定帳號或 OU，還能依排程或在基礎映像更新時自動重建。這就是安全團隊要的「統一、修補過的映像」流水線。

## 17.6 啟動時的設定：user data 與 instance metadata

### User data：第一次開機時執行的腳本

**User data** 是你在啟動 instance 時提供的腳本或設定，instance 第一次開機時由 cloud-init（Linux）或 EC2Launch（Windows）以管理員權限執行。常用來安裝套件、拉取設定、啟動服務：

```bash
#!/bin/bash
dnf install -y nginx
aws s3 cp s3://wanderly-config/prod/nginx.conf /etc/nginx/nginx.conf
systemctl enable --now nginx
```

重點：

- 預設**只在第一次開機時執行**，之後 reboot 或 stop／start 不會再跑（可另外設定 cloud-init 每次開機執行）。
- 大小上限 **16 KB**（未 base64 編碼前）。較大的腳本應放在 S3，由 user data 下載執行。
- User data 不是加密的機密儲存區，任何能讀取 instance metadata 的程式都看得到它。**不要把密碼或金鑰寫在 user data 裡**；改用 IAM role 搭配 Secrets Manager 或 Parameter Store（第 15 章）。
- 上面的 `aws s3 cp` 能執行，是因為 instance 透過 **instance profile** 取得了 IAM role 的臨時憑證，而不是因為腳本裡有 access key。

### Instance metadata 與 IMDSv2

**Instance Metadata Service（IMDS）** 是每台 instance 都能存取的本機 HTTP 端點，位址是 `169.254.169.254`（Nitro instance 也提供 IPv6 位址 `fd00:ec2::254`）。程式可以從這裡查到自己的 instance ID、AZ、private IP、user data，以及最重要的：**instance profile 對應之 IAM role 的臨時憑證**。AWS SDK 就是從這裡自動取得憑證的。

問題在於，舊版的 **IMDSv1** 只要一個簡單的 HTTP GET 就能讀取。如果應用程式有 **SSRF（Server-Side Request Forgery，伺服器端請求偽造）** 漏洞，例如一個「輸入網址、伺服器幫你抓圖片」的功能沒有檢查目的地，攻擊者只要讓伺服器去抓 `http://169.254.169.254/latest/meta-data/iam/security-credentials/角色名稱`，就能拿到 IAM 臨時憑證。這正是過去多起重大資料外洩事件的手法。

**IMDSv2** 改成 session 導向：必須先用 **HTTP PUT** 取得一個有時效的 token，之後每次 GET 都要在 header 帶上這個 token。

```text
 Instance 內的程式                        IMDS (169.254.169.254)
   │ ① PUT /latest/api/token
   │    X-aws-ec2-metadata-token-ttl-seconds: 21600
   │ ──────────────────────────────────────────►
   │ ◄────────────────────────────────────────── ② 回傳 token（IP TTL = hop limit）
   │ ③ GET /latest/meta-data/iam/security-credentials/WebRole
   │    X-aws-ec2-metadata-token: <token>
   │ ──────────────────────────────────────────►
   │ ◄────────────────────────────────────────── ④ 回傳臨時憑證
```

① 程式以 PUT 請求 token，並宣告有效期（最長 6 小時）。② IMDS 回傳 token；回應封包的 IP TTL 等於 **hop limit**（預設 1），所以 token 無法被轉送到 instance 以外的地方。③ 之後的查詢都必須帶 token。④ 驗證通過才回傳資料。

IMDSv2 擋住 SSRF 的原因有三：多數 SSRF 漏洞只能讓伺服器發出 GET，無法發出 PUT 並自訂 header；IMDS 會拒絕帶有 `X-Forwarded-For` header 的 token 請求，擋掉經過反向代理轉送的請求；hop limit 讓 token 無法跨越額外的網路跳點。

```bash
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/availability-zone
```

### 強制使用 IMDSv2

IMDSv2 要「強制」才有防護效果，否則攻擊者仍可用 v1：

```bash
aws ec2 modify-instance-metadata-options \
  --instance-id i-0abc1234def567890 \
  --http-tokens required \
  --http-put-response-hop-limit 2 \
  --http-endpoint enabled
```

- `--http-tokens required`：只接受 IMDSv2。
- `--http-put-response-hop-limit 2`：如果 instance 上跑的是 container，container 到 IMDS 多了一跳，hop limit 需設為 2，否則 container 內的程式拿不到 token。
- 新 instance 可以在 launch template 中設定 `HttpTokens: required`；也可以設定帳號層級的 IMDS 預設值，讓該 Region 新啟動的 instance 預設要求 IMDSv2。較新的 AMI（例如 Amazon Linux 2023）也預設要求 IMDSv2。
- 不需要 metadata 的 instance 可以直接 `--http-endpoint disabled`。
- 在多帳號環境，用 SCP 搭配 condition key `ec2:MetadataHttpTokens` 拒絕任何未要求 IMDSv2 的 `RunInstances`（17.16 節）。

> [!tip] 考試提示
> 題目出現「SSRF」「防止應用程式漏洞被用來取得 instance 的 IAM 憑證」，答案是「強制 IMDSv2（HttpTokens required）」。把 access key 寫進設定檔永遠是錯的答案；instance 存取 AWS 服務應該使用 instance profile（IAM role）。

## 17.7 資料放在哪裡：EBS-backed、instance store 與 instance 生命週期

### 兩種 root device

Instance 的磁碟有兩種本質不同的來源：

- **EBS（Elastic Block Store）volume**：透過網路連接的 block storage，資料存在 instance 以外，獨立於 instance 的生命週期。可以 detach 後掛到同 AZ 的另一台 instance，可以做 snapshot。EBS 的 volume types、效能與 snapshot 細節在第 24 章。
- **Instance store**：host 上實體連接的本機磁碟（通常是 NVMe SSD），只有部分 instance type 提供（名稱帶 `d` 的，例如 `m7gd`，以及 I、D 系列）。延遲極低、IOPS 極高，而且費用已包含在 instance 價格裡。但它是 **ephemeral（暫存）** 的。

**Instance store 的資料在以下情況會消失**：instance stop、hibernate、terminate，或底層磁碟故障；**reboot 時資料仍保留**。原因回到 17.2 節：stop 再 start 時 instance 通常會被放到另一台 host，原 host 上的本機磁碟自然帶不過去。

因此，instance store 適合「遺失也能重建」的資料：快取、暫存檔、批次運算的中間結果（shuffle）、或已在多個節點間複製的分散式資料庫資料。不能遺失的資料必須放在 EBS、EFS 或 S3。

現在絕大多數 AMI 都是 **EBS-backed**（root volume 是 EBS），可以 stop／start；舊式的 instance store-backed AMI 不能 stop，只能 reboot 或 terminate，考試偶爾會考這個差異。

### DeleteOnTermination

每個 EBS volume 有 `DeleteOnTermination` 屬性。預設情況下，**root volume 在 instance terminate 時會被刪除**，而在啟動時額外附加的 volume，或之後掛上去的 volume，預設會保留（若 AMI 的 block device mapping 已帶有自己的設定，則以 AMI 為準，建立前要確認）。如果 root volume 上有需要保留的資料（不建議這樣設計），或想保留某個 data volume 供鑑識，要在 launch template 的 block device mapping 中明確設定。

### 生命週期：reboot、stop、hibernate、terminate

| 動作 | Instance 狀態 | EBS root／data | Instance store | RAM | Public IPv4（非 EIP） | Private IP | 計費 |
|---|---|---|---|---|---|---|---|
| Reboot | 留在同一台 host | 保留 | 保留 | 清空 | 保留 | 保留 | 照常計費 |
| Stop／Start | 通常換 host | 保留 | **遺失** | 清空 | **改變** | 保留 | Instance 不計費，EBS 照常計費 |
| Hibernate／Start | 通常換 host | 保留 | **遺失** | **存到 root EBS，開機後還原** | **改變** | 保留 | 同 stop |
| Terminate | 刪除 | root 預設刪除 | 遺失 | 遺失 | 釋放 | 釋放 | 停止計費 |

Elastic IP 在 stop／start 後仍保持關聯（17.8 節）。

### Hibernate：保留記憶體狀態

有些應用程式啟動很慢：Java 應用程式要暖機、需要把大量資料載入記憶體快取，開機到能服務可能要十幾分鐘。**Hibernation（休眠）** 讓 instance 停止時把 RAM 內容寫到 EBS root volume，下次啟動時還原，程序直接從休眠前的狀態繼續執行，就像筆電闔上再打開。

使用條件：

- 必須在**啟動時**就啟用 hibernation；已存在的 instance（不論執行中或已停止）都不能再開啟。
- Root volume 必須是 **EBS 且已加密**，並有足夠空間容納 RAM 內容。
- 記憶體大小有上限：Linux instance 必須小於 150 GiB，Windows instance 最多 16 GiB；只支援部分 instance family 與 AMI，bare metal 不支援。
- 單次休眠不能超過 60 天；instance store 不能使用。

Wanderly 的 staging 環境每天晚上關機省錢，但隔天早上要等 15 分鐘暖機，改用 hibernate 後幾分鐘就能用。

## 17.8 網路介面：ENI、ENA、EFA 與 Elastic IP

### ENI：可以搬家的虛擬網卡

**ENI（Elastic Network Interface，彈性網路介面）** 是 VPC 中的虛擬網卡（第 5 章介紹過它會占用 subnet 的 IP）。每台 instance 都有一個 **primary ENI**（eth0），無法卸下。你可以額外附加 **secondary ENI**，數量與每張 ENI 可帶的 IP 數依 instance type 而定。

ENI 的屬性跟著網卡走，不跟著 instance：private IP、Elastic IP、MAC address、security groups、source/destination check。因此有兩個經典用途：

1. **Failover**：把 secondary ENI（帶著固定的 private IP 與 MAC）從故障的 instance 卸下，掛到同 AZ 的備援 instance，用戶端連線的 IP 不變。一些依 MAC address 綁定的舊軟體授權也靠這招。
2. **多網段**：一台 instance 同時連到管理網段與服務網段（兩張 ENI 在同 AZ 的不同 subnet），常見於網路設備或防火牆 appliance。

ENI 只能附加到**同一個 AZ** 的 instance。

### ENA：enhanced networking

**Enhanced networking** 使用 SR-IOV 技術讓 instance 更直接地存取網路硬體，提供更高頻寬、更高 PPS（packets per second，每秒封包數）與更低延遲。現代 instance 使用 **ENA（Elastic Network Adapter）**，依 instance type 提供從數 Gbps 到 100 Gbps 以上的頻寬。現代的 Nitro instance 都要求並預設使用 ENA，額外費用為零，你只要確認 AMI 有 ENA 驅動程式（AWS 提供的 AMI 都有）。

要注意的是，instance 宣傳的頻寬是總頻寬上限；**單一 flow（同一組來源／目的 IP、port 與協定的 TCP 或 UDP 連線）**的頻寬另有限制：不在同一個 cluster placement group 時最多 5 Gbps；同一個 cluster placement group 內最多可到 10 Gbps；同一個 AZ 內支援的 instance 啟用 **ENA Express** 後最多可到 25 Gbps。另外，經過 Internet Gateway 的多 flow 流量也有上限（32 vCPU 以下的 instance 約 5 Gbps）。需要高單流頻寬時，要搭配 cluster placement group 或 ENA Express，或把資料拆成多條平行連線。

### EFA：給 HPC 與機器學習的網卡

**EFA（Elastic Fabric Adapter）** 是在 ENA 之上增加 **OS-bypass** 能力的網路介面：應用程式（透過 libfabric）可以跳過作業系統的網路堆疊直接和網卡溝通，大幅降低延遲與 CPU 負擔。它是為 **MPI（Message Passing Interface）** 這類緊密耦合的 HPC 應用，以及多 GPU 分散式訓練（NCCL）設計的。

EFA 的限制：只有特定 instance type 支援；OS-bypass 流量不能跨 subnet 路由，所有節點要在同一個 subnet；security group 必須允許同一個 SG 內所有流量的進出；通常搭配 cluster placement group 使用。一般 web 應用不需要 EFA，用 ENA 即可。

| 介面 | 用途 | 一句話 |
|---|---|---|
| ENI | 所有 instance 的虛擬網卡 | 可搬移的 IP、MAC、SG 載體 |
| ENA | 高頻寬、低延遲網路 | 現代 instance 預設的 enhanced networking |
| EFA | HPC／ML 節點間通訊 | ENA + OS-bypass，給 MPI 與 NCCL |

### Elastic IP

**Elastic IP（EIP）** 是你帳號擁有的固定 public IPv4 位址，可以關聯到 instance 或 ENI，stop／start 也不會改變，直到你主動釋放；也可以在故障時快速改關聯到另一台 instance。每個 Region 的 EIP 預設上限是 5 個（預設值，可申請提高），且如第 5 章所述，所有 public IPv4 都按小時收費。

架構上應盡量避免依賴 EIP：對外服務用 Load Balancer 與 DNS 名稱，private instance 對外用 NAT Gateway。EIP 適合「必須有固定 IP 的單一 instance」，例如合作夥伴要求白名單、但又不適合放 NLB 的特殊情況。

## 17.9 Placement groups：控制 instance 擺在哪裡

一般情況下，EC2 會自動把 instance 分散在不同 host 上以降低同時故障的機率。但有兩種需求會希望你自己控制擺放：要更快的節點間網路（擺近一點），或要更確定的故障隔離（擺開一點）。**Placement group** 就是用來表達這種意圖。

```text
 Cluster（同一 AZ，擠在一起）     Spread（每台不同機架）          Partition（分區，區之間不共用機架）
 ┌─────────── AZ-a ─────────┐    AZ-a        AZ-b              ┌──────────── AZ-a ────────────┐
 │ [i][i][i][i]  同一區域    │    [Rack1:i]   [Rack4:i]         │ P1:[Rack1][Rack2]  i i i i i │
 │ [i][i][i][i]  高頻寬網路  │    [Rack2:i]   [Rack5:i]         │ P2:[Rack3][Rack4]  i i i i i │
 └──────────────────────────┘    [Rack3:i]   [Rack6:i]         │ P3:[Rack5][Rack6]  i i i i i │
  低延遲、高單流頻寬               每 AZ 最多 7 台運行中          └──────────────────────────────┘
  一個 AZ 故障 → 全部受影響         一台故障不影響其他             一個 partition 故障只影響該區
```

### Cluster placement group

把 instance 擠在同一個 AZ 內網路距離很近的區域，提供最低延遲與最高的節點間吞吐量（包括更高的單流頻寬）。適合 HPC、緊密耦合的分散式運算、需要極高節點間頻寬的工作。

代價是：所有 instance 都在同一個 AZ，甚至可能共用部分基礎設施，**故障範圍大**。另外容量可能不足：建議**一次啟動所有需要的 instance，並使用相同的 instance type**；若之後再加入新 instance 遇到 `InsufficientInstanceCapacity`，可以把整組 stop 再一起 start，讓 EC2 重新找一塊夠大的位置。

### Spread placement group

把每台 instance 放在**不同的實體機架**上（各自有獨立的網路與電源），適合少量但每台都很關鍵、絕不能同時故障的 instance，例如一組 primary／secondary 的伺服器、授權伺服器、小型叢集的節點。它可以跨同一 Region 的多個 AZ，但**每個 AZ 每個 group 最多 7 台運行中的 instance**。

### Partition placement group

把 instance 分成多個 **partition**，每個 partition 有自己的一組機架，**不同 partition 之間不共用機架**。每個 AZ 最多 7 個 partition，但每個 partition 可以放很多 instance，總數可達數百台。Instance 可以從 metadata 查到自己在哪個 partition，讓 **HDFS、HBase、Cassandra、Kafka** 這類具備「機架感知（rack awareness）」的分散式系統，把同一份資料的副本放在不同 partition，確保一組機架故障不會讓資料全部遺失。

| 策略 | 範圍 | 規模限制 | 目的 | 典型 workload |
|---|---|---|---|---|
| Cluster | 單一 AZ | 受容量影響 | 最低延遲、最高節點間頻寬 | HPC、MPI、分散式訓練 |
| Spread | 可跨 AZ | 每 AZ 每 group 7 台運行中 | 每台都在不同機架 | 少量關鍵 instance |
| Partition | 可跨 AZ | 每 AZ 7 個 partition，每個 partition 可多台 | 分組隔離、機架感知 | HDFS、Cassandra、Kafka |

> [!warning] 常見誤解
> 「Placement group 讓 instance 高可用。」只有 spread 和 partition 是在降低同時故障的機率；cluster 正好相反，它把 instance 集中，提升效能但擴大故障範圍。另外，placement group 不會改變 instance type 本身的頻寬上限，HPC 網路還要搭配支援的 instance type 與 EFA。

## 17.10 健康檢查與自動復原

EC2 對每台 instance 執行 **status checks**：

- **System status check**：檢查 AWS 這一側，例如 host 的硬體、電源、網路。失敗時通常需要把 instance 搬到新的 host：對 EBS-backed instance 做 stop／start，或使用 **automatic recovery**。
- **Instance status check**：檢查你這一側，例如作業系統開不了機、記憶體耗盡、網路設定錯誤。要由你修正，通常 reboot 或修改設定。
- **Attached EBS status check**：檢查掛載的 EBS volume 是否可存取。

**Automatic recovery** 會在 system status check 失敗時，把 instance 移到新的硬體並重新啟動，保留相同的 instance ID、private IP、Elastic IP 與 metadata；支援的 instance type 預設就啟用了簡化版的自動復原，也可以用 CloudWatch alarm 的 recover action 設定。Instance store 的資料不會保留。

不過，單台 instance 的自動復原只是基本保障。真正的高可用是讓 instance 可隨時替換，並放在跨多 AZ 的 Auto Scaling group 裡，由 ASG 偵測不健康的 instance 並自動替換（第 18 章）。

## 17.11 購買方式：同一台機器的六種付費方法

回到財務長的問題。EC2 的技術規格決定「機器長什麼樣」，**purchasing option（購買方式）**決定「怎麼付錢」以及「容量是否有保障」。這兩件事是分開的：同一台 `m7g.large`，可以用以下任何一種方式付費。

### On-Demand

**On-Demand** 按實際使用時間付費，沒有任何承諾，隨時開、隨時關。Linux 與 Windows 等多數作業系統**按秒計費（最低 60 秒）**。它最有彈性也最貴，適合短期、不可預測、不能中斷的工作，以及還不確定需要多少容量的新服務。

On-Demand 不保證容量：在某些 AZ、某些熱門 instance type 上，偶爾會遇到 `InsufficientInstanceCapacity`。另外，帳號在每個 Region 有以 vCPU 數計算的 On-Demand 與 Spot instance **service quota**（預設值，可申請提高）。

### Savings Plans

**Savings Plans** 是以「每小時花多少錢」為單位的 1 年或 3 年承諾，例如「承諾每小時 10 美元的運算用量」。承諾範圍內的用量以折扣價計算，超出部分以 On-Demand 計價；沒用滿的承諾仍要付，也不能累積到下一小時。付款方式可選 all upfront、partial upfront 或 no upfront，預付越多折扣越高。

| 類型 | 適用範圍 | 最高折扣（AWS 公布） |
|---|---|---|
| **Compute Savings Plans** | 任何 Region、任何 instance family、大小、作業系統、tenancy 的 EC2，以及 Fargate 與 Lambda | 約 66% |
| **EC2 Instance Savings Plans** | 指定 Region 中的指定 instance family（例如東京的 M7g），可換大小、作業系統、tenancy | 約 72% |
| SageMaker Savings Plans | SageMaker AI 的運算用量 | 第 39 章 |

Compute Savings Plans 彈性最大：Wanderly 明年要從 x86 換成 Graviton、從 EC2 搬一部分到 Fargate，承諾都還能適用。EC2 Instance Savings Plans 折扣較高，但被綁在一個 family 與 Region。

> [!warning] 常見誤解
> Savings Plans 是**純粹的帳單折扣，不保留任何容量**。若需要「保證某個 AZ 一定開得出 50 台」，要用 On-Demand Capacity Reservation（本節後段）。

### Reserved Instances

**Reserved Instances（RI）** 是較早的承諾折扣模式：承諾 1 年或 3 年使用特定的 instance 屬性（instance type、作業系統、tenancy、Region 或 AZ）。

- **Standard RI**：折扣最高（最高約 72%），可以修改部分屬性（例如 AZ、同 family 內的大小），不能換 family；可在 **Reserved Instance Marketplace** 轉賣給其他客戶。
- **Convertible RI**：折扣較低（最高約 66%），可以 **exchange** 換成不同 family、作業系統或 tenancy 的 RI，前提是新 RI 的價值相等或更高；不能在 Marketplace 轉賣。
- **Regional RI**：折扣適用於該 Region 任何 AZ；Linux／Unix、default tenancy 的 Regional RI 還有 **instance size flexibility**，同 family 不同大小都能套用折扣（依大小比例換算）。**不保留容量**。
- **Zonal RI**：指定 AZ，**同時在該 AZ 保留容量**，但失去 AZ 與大小彈性。

對新的 EC2 承諾，AWS 一般建議優先考慮 Savings Plans，因為管理更簡單、彈性更大。RI 在考試中仍常出現，而且 RDS、ElastiCache、OpenSearch、Redshift 等服務的承諾折扣仍以 reserved 形式提供（第 39 章）。

### Spot Instances

**Spot Instances** 使用 AWS 暫時沒用到的 EC2 容量，價格比 On-Demand 低很多（AWS 公布最高可省 90%）。代價是：**當 AWS 需要收回容量時，Spot instance 會被中斷**。

- **價格**：Spot 價格依各個 **capacity pool**（某 AZ 中的某個 instance type）的長期供需緩慢調整，不是競價。你可以設定願意付的最高價格（預設為 On-Demand 價格），但實際付的是當下的 Spot 價格。設定更高的最高價格**不會**讓 instance 免於中斷。
- **中斷通知**：EC2 會在中斷前 **2 分鐘**發出 **Spot instance interruption notice**，可以從 instance metadata（`spot/instance-action`）讀取，也會送到 EventBridge。程式應利用這段時間儲存進度、把自己從 load balancer 移除。
- **Rebalance recommendation**：當 instance 的中斷風險升高時，EC2 會更早發出這個訊號（不保證一定比中斷通知早），讓你提前啟動替代 instance。
- **中斷行為**：可設定為 terminate（預設）、stop 或 hibernate。

Spot 最重要的設計原則是 **分散（diversification）**：不要只用一種 instance type、一個 AZ。使用多種相容的 instance type（例如 `c6i.xlarge`、`c7i.xlarge`、`c6a.xlarge`、`m6i.xlarge`）與多個 AZ，可用的 capacity pool 越多，同時被中斷的機率越低。

要一次管理大量 Spot，使用 **EC2 Fleet**、**Spot Fleet** 或 Auto Scaling group 的 **mixed instances policy**（第 18 章），並選擇 **allocation strategy**：

| Allocation strategy | 行為 | 何時用 |
|---|---|---|
| `price-capacity-optimized` | 先挑容量充足的 pool，再從中挑價格最低的 | **AWS 建議的預設**，兼顧中斷率與價格 |
| `capacity-optimized` | 挑容量最充足的 pool | 中斷成本很高的工作 |
| `lowest-price` | 挑最便宜的 pool | 不建議；最便宜的 pool 往往中斷率較高 |

也可以使用 **attribute-based instance type selection**，只指定「4–8 vCPU、16–32 GiB 記憶體」這類屬性，讓 EC2 自動納入所有符合的 instance type，包括未來推出的新型號。

適合 Spot 的 workload：**無狀態、可中斷、可重試**，例如批次處理、影像轉碼、CI/CD 建置、大數據分析、容器化的無狀態 web 服務（搭配 On-Demand 底量）。不適合：單一資料庫、必須連續執行數小時且無法 checkpoint 的工作。Wanderly 每晚的照片轉檔正是 Spot 的理想場景：任務放在 SQS queue，worker 處理完一張才刪除訊息；worker 被中斷時，未完成的訊息會在 visibility timeout 後重新出現（第 32 章），由其他 worker 接手。

> [!note] Spot blocks 已停止
> 過去有可以「保證不中斷 1–6 小時」的 Spot blocks（defined duration），已不再提供給新的請求。考試若出現「保證不中斷的 Spot」，不是正確選項。

### Dedicated Instances 與 Dedicated Hosts

預設的 instance 跑在可能與其他客戶共用的 host 上（安全隔離由 Nitro 與 hypervisor 保證）。若法規或授權要求實體隔離，有兩種選擇：

- **Dedicated Instances**：你的 instance 跑在只屬於你帳號的硬體上，不與其他 AWS 帳號共用 host。但你**看不到也控制不了是哪一台 host**，同帳號的其他 instance 仍可能和它共用。按 instance 計費，另有每 Region 的 dedicated 費用。
- **Dedicated Hosts**：你租下一整台實體伺服器，能看到 host ID、**實體 socket 與 core 數量**，可以指定 instance 放在哪一台 host（**host affinity**），重新開機後仍留在同一台。按 host 計費，可以用 On-Demand 或 reservation 方式購買。

Dedicated Hosts 最主要的用途是 **BYOL（Bring Your Own License，自帶授權）**：Windows Server、SQL Server、Oracle 等商業軟體的授權常以「實體 socket 或 core」計算，或要求授權綁定在特定實體伺服器上一段時間，只有 Dedicated Hosts 能提供這種可見性。**AWS License Manager** 可以追蹤授權用量，並透過 host resource group 自動配置與釋放 Dedicated Hosts。

### On-Demand Capacity Reservations

**On-Demand Capacity Reservation（ODCR）** 在指定 AZ 為指定的 instance type、平台與 tenancy **保留容量**，可以隨時建立、隨時取消，不需要長期承諾（也可預約未來日期開始的保留，這類保留需要承諾一段期間）。不論有沒有 instance 在使用，保留的容量都**以 On-Demand 價格計費**。

ODCR 本身沒有折扣，但可以和 **Regional RI 或 Savings Plans 疊加**：Savings Plans 提供折扣，ODCR 提供容量保證。適合「黑色星期五當天東京 1a 一定要開得出 200 台」「DR 演練時必須保證目標 AZ 有容量」這類需求。

- **Open** reservation：任何符合屬性的 instance 自動使用。
- **Targeted** reservation：只有明確指定的 instance 使用。
- 可以透過 AWS RAM 分享給 Organization 中的其他帳號。

另外，機器學習團隊常用的 **EC2 Capacity Blocks for ML** 可以預約未來某段期間的 GPU instance（例如訓練用的 P 系列），適合短期大規模訓練。

### 把它們組合起來

```text
 instance 數量
   ▲
 60│                         ╭───╮              ← 尖峰：On-Demand（或 Spot 補充）
   │                    ╭────╯   ╰───╮
 40│          ╭─────────╯             ╰──────    ← 日常波動：On-Demand
   │──────────╯
 20│████████████████████████████████████████   ← 穩定底量：Savings Plans / RI
   │░░░░░ 22:00–06:00 照片轉檔批次 ░░░░░░░░░    ← 可中斷工作：Spot（多 type、多 AZ）
```

## 17.12 Tenancy 與授權

**Tenancy（租用模式）**有三種：`default`（共用硬體）、`dedicated`（Dedicated Instance）、`host`（Dedicated Host）。可以在 launch template 或啟動時設定；也可以在 VPC 層級設定 tenancy。要注意，VPC 的 tenancy 設為 dedicated 後，裡面所有 instance 都會是 dedicated（費用高），可以從 dedicated 改回 default，但反過來不行。已啟動的 instance 在 stop 後可以在 dedicated 與 host 之間切換。

授權上，Windows Server 與 SQL Server 有兩種主要方式：

- **License included**：授權費包含在 EC2 的每小時價格裡，可用於任何 tenancy，最簡單。
- **BYOL**：使用公司既有的授權。依軟體廠商的授權條款，有些授權必須在 Dedicated Hosts 上才能使用（例如以實體 core 計算的授權，或沒有授權移動性的 Microsoft 授權）。

遷移時，「公司有大量既有的 Windows／SQL Server／Oracle 授權想沿用」是 SAP 題目的典型訊號，答案通常是 Dedicated Hosts 加上 License Manager（第 44 章）。

## 17.15 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| T instance 一段時間後變慢、`CPUCreditBalance` 歸零 | Credits 用完；長期高負載改 M／C，或接受 unlimited 費用 |
| 改善價格效能、應用程式是 Java／Python／Node.js | Graviton（arm64） |
| SSRF、防止竊取 instance 的 IAM 憑證 | 強制 IMDSv2（`HttpTokens=required`） |
| Container 內的程式拿不到 IMDSv2 token | Hop limit 設為 2 |
| 在另一個 Region 啟動相同的 instance | Copy AMI 到目標 Region（加密時指定目標 KMS key） |
| 把加密 AMI 分享給另一個帳號 | 使用 customer managed key 並授權對方帳號；`aws/ebs` 加密的不能分享 |
| 標準化、修補過的映像，自動建置與分發 | Golden AMI + EC2 Image Builder |
| 新 instance 要最快開始服務 | 把軟體 bake 進 AMI，而非開機時安裝 |
| 極高 IOPS 的暫存資料、可重建 | Instance store |
| Stop／start 後本機資料不見了 | Instance store 是 ephemeral |
| 應用程式暖機很久、想快速恢復記憶體狀態 | Hibernate（啟動時啟用、root EBS 加密） |
| HPC、節點間低延遲 | Cluster placement group（+ EFA） |
| Kafka、HDFS、Cassandra 機架感知 | Partition placement group |
| 少量關鍵 instance 不同時故障 | Spread placement group（每 AZ 7 台） |
| MPI、OS-bypass | EFA |
| Failover 時保留相同的 private IP 與 MAC | 把 secondary ENI 移到備援 instance |
| 可中斷的批次、成本最低 | Spot（多 type、多 AZ、`price-capacity-optimized`） |
| 會換 family、Region，或也用 Fargate／Lambda | Compute Savings Plans |
| 指定 AZ 保證容量 | On-Demand Capacity Reservation |
| 以 socket／core 計費的授權、BYOL | Dedicated Hosts |

**常見陷阱**：

1. 以為 Savings Plans 或 Regional RI 會保留容量：它們只是折扣；容量保證要 ODCR 或 Zonal RI。
2. 以為設定很高的 Spot 最高價格就不會被中斷：中斷取決於 AWS 是否需要收回容量。
3. 把資料庫或無法 checkpoint 的長時間工作放在 Spot。
4. 把不可遺失的資料放在 instance store，或以為 instance store 在 stop 後還在。
5. 以為 cluster placement group 提升可用性：它集中在單一 AZ，故障範圍更大。
6. 把 Dedicated Instances 當成 BYOL 的答案：需要 socket／core 可見性時只有 Dedicated Hosts 能滿足。

## 17.16 SAP 加深：組織層級的 EC2 治理與容量策略

### 用 SCP 在整個組織強制 IMDSv2

單一帳號可以設定 IMDS 預設值，但在數十個帳號中要「保證沒有任何人能啟動 IMDSv1 instance」，要用 SCP：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireImdsV2OnLaunch",
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringNotEquals": { "ec2:MetadataHttpTokens": "required" }
      }
    },
    {
      "Sid": "DenyMetadataOptionChanges",
      "Effect": "Deny",
      "Action": "ec2:ModifyInstanceMetadataOptions",
      "Resource": "*",
      "Condition": {
        "StringNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/PlatformAdmin" }
      }
    }
  ]
}
```

第一段拒絕任何未要求 IMDSv2 的啟動；第二段防止有人在啟動後把設定改回 v1，只保留平台管理角色作為例外。既有的 instance 則用 Config rule（例如 `ec2-imdsv2-check`）找出仍允許 v1 的機器，再分批修改。改為 `required` 之前，要先確認 instance 上的 SDK 與 agent 版本都支援 IMDSv2，CloudWatch 指標 `MetadataNoToken` 可以顯示還有多少 v1 呼叫。

### 組織的 golden AMI 流水線

企業級的做法是由平台帳號用 EC2 Image Builder 建立 golden AMI，經 Inspector 掃描通過後，自動複製到所有使用中的 Region，並以 launch permissions 分享給指定的 OU。要讓這件事順利運作：

- AMI 用 **customer managed KMS key** 加密，key policy 允許目標 OU 的帳號使用（可用 `aws:PrincipalOrgPaths` 等條件）。
- 各帳號以 SSM Parameter Store 參數或 AMI 的 tag 找到「最新核准版本」，launch template 引用參數而非寫死 AMI ID。
- 用 SCP 或 IAM 條件（例如 `ec2:Owner`、`ec2:ImageID` 相關條件）限制只能從核准帳號擁有的 AMI 啟動，或使用 EC2 的 allowed AMIs 設定限制可用的 AMI 來源。
- 舊版本 AMI 設定 deprecation，並定期清理對應的 snapshot。

### 容量與承諾的組織策略

- **集中購買、共享折扣**：在 Organizations 的 consolidated billing 下，Savings Plans 與 RI 的折扣預設會跨帳號共享；可以在特定帳號關閉共享（第 39、43 章）。
- **覆蓋率與使用率**：coverage 表示合格用量中有多少被承諾覆蓋，utilization 表示買的承諾用掉了多少。高 utilization 但低 coverage，代表還有加購空間；低 utilization 代表買太多了。
- **關鍵事件的容量**：DR 的目標 Region 在平時不一定保有容量。若 RTO 要求很嚴格，可以在 DR Region 預先建立 ODCR（付 On-Demand 價格保留容量），或採用 warm standby 讓部分容量平時就在跑（第 34 章）。
- **遷移授權**：從資料中心遷移大量 Windows／SQL Server VM 時，比較「license included」與「BYOL on Dedicated Hosts」的總成本；用 License Manager 設定授權規則（例如每個 socket 能跑幾個 VM），防止超用。

## 本章重點整理

- Instance type 名稱依序表示 family、世代、處理器與屬性、大小，例如 `m7gd.2xlarge` 是第 7 代、Graviton、附 instance store 的一般用途 instance。
- 依瓶頸選 family：C 給 CPU 密集、R／X 給記憶體、I／D 給本機儲存、P／G／Inf／Trn 給加速運算、M 為均衡；Graviton 需要 arm64 版本的軟體與 AMI。
- T 系列靠 CPU credits 爆發，standard 模式 credits 用完會被限速、unlimited 模式會額外收費；長期高負載應改用固定效能的 family。
- AMI 是 Regional 資源，跨 Region 要 copy（得到新 AMI ID），分享加密 AMI 必須使用 customer managed KMS key 並授權對方帳號。
- Golden AMI 搭配 EC2 Image Builder 自動建置、測試、分發；把軟體 bake 進 AMI 能縮短開機到服務的時間。
- User data 預設只在第一次開機時以 root 執行，上限 16 KB，不應存放機密；instance 存取 AWS 服務應使用 instance profile。
- IMDSv2 以 PUT 取得的 token 保護 metadata，能防禦 SSRF 竊取 IAM 憑證；要設定 `HttpTokens=required` 才有效，container 環境 hop limit 設為 2。
- Instance store 是 host 上的暫存磁碟，reboot 保留，但 stop、hibernate、terminate 或硬體故障時資料遺失；不可遺失的資料放 EBS、EFS 或 S3。
- Root EBS volume 預設在 terminate 時刪除；stop／start 會改變非 EIP 的 public IPv4，但保留 private IP 與 EBS 資料。
- Hibernate 把 RAM 存到加密的 EBS root volume，必須在啟動時啟用，適合暖機很久的應用程式。
- Cluster placement group 提供單一 AZ 內最低延遲，spread 每 AZ 最多 7 台運行中的 instance 且各在不同機架，partition 讓機架感知的分散式系統隔離故障。
- ENI 可在同 AZ 的 instance 間搬移並帶著 IP、MAC 與 SG；ENA 是預設的 enhanced networking；EFA 加上 OS-bypass，給 HPC 與分散式 ML 使用。
- Savings Plans 與 Regional RI 只提供折扣不保留容量；Compute Savings Plans 涵蓋任何 family、Region、Fargate 與 Lambda，EC2 Instance Savings Plans 綁定 family 與 Region 但折扣較高。
- Spot 最高可省 90%，中斷前有 2 分鐘通知；要分散到多種 instance type 與 AZ，並使用 `price-capacity-optimized`，只放可中斷、可重試的工作。
- Dedicated Hosts 提供 socket／core 可見性與 host affinity，用於 BYOL；Dedicated Instances 只保證不與其他帳號共用硬體；On-Demand Capacity Reservation 保證指定 AZ 的容量，可與 Savings Plans 疊加折扣。

## 本章練習題

### 練習 17-1｜SAA｜單選｜依瓶頸選擇 instance family

Wanderly 的房價快取服務把約 200 GB 的熱門房價資料完全放在記憶體中，目前跑在 `m6i.16xlarge`（64 vCPU、256 GiB 記憶體）上。監控顯示 CPU 使用率長期低於 15%，但記憶體使用率接近 90%，服務是用 Java 撰寫。團隊希望在滿足記憶體需求的前提下降低成本。

最合適的選擇是什麼？

- A. `c7g.16xlarge`，compute optimized 系列的 Graviton instance
- B. `r7g.8xlarge`，memory optimized 系列的 Graviton instance（32 vCPU、256 GiB 記憶體）
- C. `t3.2xlarge`，在 unlimited 模式下執行
- D. `i4i.8xlarge`，把資料改放在 instance store

> [!answer]- 答案：B
> **A ✗** C 系列每 vCPU 的記憶體比例最低，要裝下 200 GB 資料需要非常多 vCPU，與「CPU 使用率很低」的特性正好相反，成本更高。
>
> **B ✓** 瓶頸是記憶體而非 CPU，R 系列約每 vCPU 8 GiB，用一半的 vCPU 就能提供相同的 256 GiB 記憶體。Java 應用程式通常不必修改就能在 Graviton 上執行，可進一步改善價格效能。
>
> **C ✗** `t3.2xlarge` 只有 32 GiB 記憶體，完全裝不下資料；T 系列也不適合長期運作的關鍵服務。
>
> **D ✗** 把記憶體內快取改到 instance store 會改變應用程式設計並增加延遲；而且 instance store 在 stop 時資料會遺失，這不是降低成本的直接做法。
>
> **考點**：SAA-3.2、SAA-4.2｜依瓶頸選擇 family 與 Graviton

### 練習 17-2｜SAA｜單選｜T 系列效能突然下降

Wanderly 的報表服務跑在一台 standard 模式的 `t3.large` 上。每天早上 9 點後的前 40 分鐘，報表產生速度正常；之後即使請求量沒變，處理時間卻變成原本的四倍。CloudWatch 顯示這段期間 CPU 使用率維持在 70% 左右，`CPUCreditBalance` 在 9:40 左右降到 0。這個工作每天會持續高負載約 6 小時。

最合適的改善方式是什麼？

- A. 改用 `t3.xlarge`，讓 instance 擁有更高的 credit 累積上限
- B. 每天早上 9 點前 reboot instance，重新取得 CPU credits
- C. 為 instance 加上一個大小更大的 gp3 EBS volume，提升 I/O 效能
- D. 改用固定效能的 instance family（例如 `m7i.large` 或 `c7i.large`），並以實際負載驗證大小

> [!answer]- 答案：D
> **A ✗** 較大的 T instance 雖然累積的 credits 較多，但 baseline 比例並不是 100%，連續 6 小時 70% 的使用率仍會耗盡 credits，只是延後發生。
>
> **B ✗** Reboot 不會補充 credits，也會中斷服務；credits 依使用率低於 baseline 的時間累積。
>
> **C ✗** 問題是 CPU credits 耗盡導致被限制到 baseline，與磁碟 I/O 無關。
>
> **D ✓** Workload 長時間高於 baseline，不符合 burstable 的使用模式。M 或 C 系列提供固定的 CPU 效能，不受 credits 限制；在 unlimited 模式下長期 burst 的額外費用通常也比改用固定效能 family 更高。
>
> **考點**：SAA-3.2｜T 系列 CPU credits 與 baseline

### 練習 17-3｜SAA｜單選｜防禦 SSRF 竊取憑證

資安測試發現，Wanderly 的「從網址匯入旅館照片」功能有 SSRF 漏洞：攻擊者可以讓伺服器對任意網址發出 HTTP GET 請求。這些 EC2 透過 instance profile 存取 S3。團隊要在修補程式碼之前，先以最小的變更防止攻擊者透過此漏洞取得 instance 的 IAM 臨時憑證。應用程式使用最新版的 AWS SDK。

最合適的做法是什麼？

- A. 修改 instance metadata options，將 `HttpTokens` 設為 `required`，強制使用 IMDSv2
- B. 移除 instance profile，改把 IAM user 的 access key 寫入應用程式的設定檔
- C. 在 instance 的 security group 加入拒絕連到 `169.254.169.254` 的出站規則
- D. 將 instance 移到沒有 NAT Gateway 的 isolated subnet

> [!answer]- 答案：A
> **A ✓** 強制 IMDSv2 後，讀取 metadata 必須先以 PUT 取得 token 並在 header 帶上它。SSRF 漏洞通常只能發出單純的 GET，無法完成這個流程，因此拿不到憑證。新版 SDK 原生支援 IMDSv2，不需修改程式。
>
> **B ✗** 長期 access key 寫進設定檔，一旦被讀取就是永久有效的憑證，風險更高，也違反最佳實務。
>
> **C ✗** Security group 只有 allow 規則，不能寫 deny；而且 IMDS 是 instance 的本機端點，不受 security group 控制。
>
> **D ✗** IMDS 在 instance 本機，與 subnet 是否能上網無關；isolated subnet 也會讓應用程式無法匯入外部照片。
>
> **考點**：SAA-1.2｜IMDSv2 防禦 SSRF

### 練習 17-4｜SAA｜單選｜暫存資料的儲存選擇

Wanderly 的資料團隊每晚執行 Spark 批次工作，處理過程中會產生大量中間 shuffle 檔案，需要極高的隨機讀寫 IOPS 與極低延遲。原始資料與最終結果都存在 S3，若某個節點故障，Spark 會自動從 S3 重新計算該節點的部分。團隊希望在滿足效能的前提下成本最低。

這些 shuffle 檔案應該存放在哪裡？

- A. 每個節點掛載一個高 IOPS 的 io2 EBS volume
- B. 所有節點共用一個 Amazon EFS 檔案系統
- C. 使用附 NVMe instance store 的 instance type（例如名稱帶 `d` 的 type），把 shuffle 檔案放在 instance store
- D. 直接把 shuffle 檔案寫入 S3

> [!answer]- 答案：C
> **A ✗** io2 能提供高 IOPS，但要另外支付高額的 provisioned IOPS 費用，而且是網路連接的儲存，延遲比本機 NVMe 高。資料可以重建時，不需要付這筆持久化的錢。
>
> **B ✗** EFS 是網路檔案系統，適合共享檔案，但延遲與每 IOPS 成本都不適合大量的暫存 shuffle 讀寫。
>
> **C ✓** Instance store 是 host 上的本機 NVMe，延遲最低、IOPS 極高，費用已含在 instance 價格裡。資料是暫存且可從 S3 重建，正好符合 instance store「ephemeral」的特性。
>
> **D ✗** S3 是物件儲存，不適合 shuffle 這種大量小型隨機讀寫，延遲與請求費用都不理想。
>
> **考點**：SAA-3.1、SAA-3.2｜instance store 的適用情境

### 練習 17-5｜SAA｜單選｜分散式系統的機架感知

Wanderly 在 EC2 上自建一個 Kafka 叢集，共 24 個 broker，分布在單一 AZ（受限於延遲需求）。團隊希望一組實體機架故障時，同一個 topic partition 的多份副本不會同時遺失，並讓 Kafka 能得知每個 broker 位於哪個故障區域，以設定 rack awareness。

應使用哪種 placement 策略？

- A. Cluster placement group，讓所有 broker 位於同一個高頻寬網路區域
- B. Partition placement group，建立多個 partition，並讓 Kafka 依 instance metadata 中的 partition 編號設定 broker 的 rack
- C. Spread placement group，讓每個 broker 都位於不同機架
- D. 不使用 placement group，讓 EC2 自動分散 instance

> [!answer]- 答案：B
> **A ✗** Cluster 把 instance 集中在一起，提升網路效能但擴大故障範圍，與「機架故障不能讓副本同時遺失」的目標相反。
>
> **B ✓** Partition placement group 讓不同 partition 不共用機架，每個 partition 可放多台 instance。Instance 可從 metadata 查到自己的 partition 編號，正好對應 Kafka 的 rack awareness，讓副本分散在不同 partition。
>
> **C ✗** Spread 每個 AZ 每個 group 最多只能有 7 台運行中的 instance，24 個 broker 放不下。
>
> **D ✗** 不使用 placement group 時無法得知或控制 instance 的機架分布，Kafka 無法正確設定 rack awareness。
>
> **考點**：SAA-2.2｜partition placement group

### 練習 17-6｜SAA｜選兩項｜可中斷批次工作的成本最佳化

Wanderly 每晚 22:00 到 06:00 要把約十萬張照片轉成多種尺寸。工作以 SQS queue 分派，每張照片處理約 20 秒、可以重試，結果寫入 S3。目前使用 30 台 On-Demand `c6i.xlarge`。團隊希望大幅降低成本，同時讓工作在早上前穩定完成。

哪兩個做法最合適？（選兩項）

- A. 改用 Spot instance，並讓 Auto Scaling group 或 EC2 Fleet 納入多種相容的 instance type 與多個 AZ，使用 `price-capacity-optimized` allocation strategy
- B. 改用 Spot instance，只使用最便宜的單一 instance type 與單一 AZ，並把最高價格設為 On-Demand 價格的三倍以避免中斷
- C. 為這 30 台 instance 購買 3 年期 Standard Reserved Instances
- D. 讓 worker 在處理完一張照片並寫入 S3 之後才刪除 SQS 訊息，並在收到 Spot 中斷通知時停止接新訊息

>
> **C ✗** 工作每天只跑 8 小時，購買全天候的 3 年期 RI 會在白天浪費大部分承諾；Spot 的折扣通常也更高。
>
> **D ✓** 處理完成才刪除訊息，被中斷的 worker 未完成的訊息會在 visibility timeout 後重新出現，由其他 worker 接手；利用 2 分鐘通知停止接新工作，減少重做。
>
> **E ✗** 被中斷的 Spot instance 的 instance store 資料會遺失，也不一定由同一台 instance 繼續；進度應保存在 SQS、S3 這類持久化服務。
>
> **考點**：SAA-4.2｜Spot 分散策略與中斷處理

### 練習 17-8｜SAA｜單選｜快速恢復暖機狀態

Wanderly 的 staging 環境每天 20:00 關機、隔天 08:00 開機以節省費用。每次開機後，Java 應用程式需要約 15 分鐘載入快取並完成 JIT 暖機，工程師因此每天早上都要等待。Instance 使用 EBS root volume，記憶體 32 GiB，不使用 instance store。

哪個做法能以最小的變更縮短等待時間？

- A. 以啟用 hibernation 的設定重新啟動這些 instance（root EBS volume 加密且空間足夠），每晚改用 hibernate 取代 stop
- B. 改成每晚 reboot instance 而不是 stop
- C. 把應用程式與快取資料存進 AMI，每天早上用新 AMI 重新啟動 instance
- D. 改用 instance store 作為 root volume，加快開機速度

> [!answer]- 答案：A

>
> **C ✗** AMI 保存的是磁碟內容，不保存記憶體與 JIT 狀態；每天重建 AMI 也增加維運負擔，應用程式開機後仍要暖機。
>
> **D ✗** Instance store-backed 的 instance 不能 stop 或 hibernate，而且資料是暫存的，不能縮短暖機時間。
>
> **考點**：SAA-3.2、SAA-4.2｜EC2 hibernation

應如何處理？

- B. 在大阪 Region 建立一個新的 KMS key，並把它加入東京 AMI 的 key policy

哪兩個做法能最有效改善節點間通訊？（選兩項）

- A. 把所有節點放進同一個 spread placement group
- B. 把所有節點以相同的 instance type 一次啟動到同一個 cluster placement group
- C. 為每個節點附加多張 secondary ENI，分散流量

### 練習 17-13｜SAP｜選兩項｜組織的 golden AMI 分發

- B. 把 AMI 的 launch permissions 設為公開，避免逐一管理帳號權限

>
> **E ✗** 每個帳號手動複製與管理 KMS key 的營運負擔高、容易出錯，也無法保證大家使用最新版本。

> **考點**：SAP-1.4、SAP-3.2｜跨帳號 AMI 分享與 KMS key policy

### 練習 17-14｜SAP｜單選｜大規模 Spot 渲染農場

Wanderly 的影片團隊每月有一次為期三天的 3D 旅遊影片渲染，需要約 2,000 個 vCPU，工作可切成上萬個可重試的小段。上次只用一種 instance type 的 Spot 時，頻繁遭遇中斷與容量不足，導致延誤。團隊希望在成本最低的前提下提高完成的可靠性，並減少每次手動挑選 instance type 的工作。

最合適的做法是什麼？

- A. 改用 On-Demand instance，並購買 3 年期 Compute Savings Plans 涵蓋 2,000 vCPU
- B. 繼續使用單一 instance type 的 Spot，但把最高價格設為 On-Demand 價格，確保不會被中斷
- C. 使用 Spot Fleet 的 `lowest-price` allocation strategy，並只選擇價格最低的兩個 AZ
- D. 使用 EC2 Fleet，以 attribute-based instance type selection 指定 vCPU 與記憶體範圍，涵蓋 Region 中所有 AZ，採用 `price-capacity-optimized` allocation strategy，並以 vCPU 作為 target capacity 單位

> [!answer]- 答案：D
> **A ✗** 每月只用三天卻承諾 3 年全天候用量，絕大部分承諾會被浪費，成本遠高於 Spot。
>
> **B ✗** 最高價格不影響中斷；中斷是因為 AWS 需要收回容量。單一 instance type 的 capacity pool 太少，是上次問題的根源。
>
> **C ✗** `lowest-price` 傾向選擇最便宜的 pool，這些 pool 往往容量少、中斷率高；只用兩個 AZ 也縮小了可用容量。
>
> **D ✓** Attribute-based selection 自動納入所有符合屬性的 instance type（包括新型號），大幅增加 capacity pool 數量，也免去手動挑選。涵蓋所有 AZ 與 `price-capacity-optimized` 能兼顧低中斷率與低價格；以 vCPU 為單位讓不同大小的 instance 都能計入目標容量。
>
> **考點**：SAP-2.6、SAP-3.5｜EC2 Fleet、attribute-based selection 與 Spot allocation strategy

### 練習 17-15｜SAP｜單選｜硬體隔離的合規需求

Wanderly 的支付卡處理系統要通過一份合作銀行的資安問卷，其中規定「處理持卡人資料的伺服器不得與其他組織共用實體硬體」。這些 instance 使用 Amazon Linux 與開源軟體，沒有任何以 socket 或 core 計費的授權，也不需要控制 instance 落在哪一台實體伺服器。團隊希望在滿足規定的前提下，營運負擔與成本最低。

最合適的做法是什麼？

- A. 以 `dedicated` tenancy 啟動這些 instance（Dedicated Instances），其餘系統維持 default tenancy
- B. 把整個 VPC 的 tenancy 設為 dedicated，讓所有系統都使用 Dedicated Instances
- C. 購買足夠的 Dedicated Hosts，並自行規劃每台 host 上的 instance 配置
- D. 維持 default tenancy，並以 Nitro Enclaves 處理持卡人資料，即可視為不與其他組織共用硬體

> [!answer]- 答案：A
> **A ✓** Dedicated Instances 保證 instance 跑在只屬於本帳號的硬體上，不與其他 AWS 帳號共用，滿足規定。沒有 host 層級的授權需求時，不需要 Dedicated Hosts 的 host 管理負擔。只對處理持卡人資料的 instance 使用，控制成本。
>
> **B ✗** VPC tenancy 設為 dedicated 會讓 VPC 中所有 instance 都成為 Dedicated Instances，包括不需要隔離的系統，大幅增加成本；而且之後只能從 dedicated 改回 default，設計彈性差。
>
> **C ✗** Dedicated Hosts 也能滿足規定，但要自行管理 host 容量與配置，營運負擔與成本較高；它的主要價值是 socket／core 可見性與 host affinity，題目明確不需要。
>
> **D ✗** Nitro Enclaves 在 instance 內建立隔離的運算環境，用於保護敏感資料處理，但 instance 仍在共用 tenancy 的 host 上，不符合「不與其他組織共用實體硬體」的字面規定。
>
> **考點**：SAP-2.3、SAP-2.6｜Dedicated Instances vs Dedicated Hosts

### 練習 17-16｜SAP｜單選｜組織層級強制 IMDSv2

Wanderly 有 70 個 AWS 帳號。在一次滲透測試後，安全團隊要求：所有帳號、所有 Region 新啟動的 EC2 都必須只使用 IMDSv2，任何人（包括各帳號的管理員）都不能啟動允許 IMDSv1 的 instance，也不能在啟動後把設定改回 v1；只有平台團隊的 `PlatformAdmin` role 可作為例外。既有 instance 要能被找出並分批修正。

最合適的做法是什麼？

- A. 在每個帳號設定帳號層級的 IMDS 預設值為 `required`，並要求各團隊自行遵守
- B. 在 golden AMI 中預設要求 IMDSv2，並禁止團隊使用其他 AMI
- C. 在 Organization 套用 SCP：當 `ec2:MetadataHttpTokens` 不等於 `required` 時拒絕 `ec2:RunInstances`，並拒絕非 `PlatformAdmin` 的 principal 呼叫 `ec2:ModifyInstanceMetadataOptions`；同時以 AWS Config rule 找出仍允許 IMDSv1 的既有 instance 並分批修正
- D. 在所有 instance 的作業系統防火牆封鎖 `169.254.169.254`，再由應用程式改用 access key 存取 AWS

> [!answer]- 答案：C
> **A ✗** 帳號層級的預設值只影響未明確指定的新 instance，帳號管理員可以在啟動時覆寫，或之後修改預設值，無法強制。
>
> **B ✗** AMI 的預設可以在啟動參數或之後被修改，也無法涵蓋使用其他來源 AMI 的情況，不能保證「任何人都不能」。
>
> **C ✓** SCP 是組織層級的預防控制，成員帳號的管理員也無法繞過。`ec2:MetadataHttpTokens` 條件拒絕未要求 IMDSv2 的啟動，拒絕 `ModifyInstanceMetadataOptions` 防止事後降級，並以 `aws:PrincipalArn` 條件保留平台角色例外。SCP 不影響既有 instance，因此要搭配 Config rule 找出並分批修正。
>
> **D ✗** 封鎖 IMDS 會讓 instance profile 失效，改用長期 access key 反而大幅增加憑證外洩的風險。
>
> **考點**：SAP-1.2、SAP-1.4｜以 SCP 強制 IMDSv2
