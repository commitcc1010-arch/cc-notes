## 13.1 故事：三種「外人」要進門

第 12 章的事故之後，Wanderly 把環境拆成兩個 AWS 帳號：`wanderly-prod`（帳號 ID `111122223333`）放正式系統，`wanderly-dev`（`444455556666`）給開發與測試。拆開之後，新的問題一個接一個出現。

第一，CI/CD 在 dev 帳號執行，但部署時要把程式推到 prod 帳號；工程師偶爾也需要到 prod 帳號查 log。小林的第一個念頭是「在 prod 帳號再開一批 IAM user」，但這等於把第 12 章才清掉的長期金鑰又請回來。

第二，行銷部簽約了一家營收分析廠商 TripMetrics，對方要每天讀取 prod 帳號 S3 裡的訂單匯出檔。對方說：「請給我們一組 access key，或是建一個 role 讓我們扮演。」該怎麼給才安全？第三，公司員工已經用 Microsoft Entra ID 登入 email 和各種 SaaS，HR 希望離職時只要在一個地方停用帳號，所有系統（包括 AWS）就一起失效。

最後，產品團隊準備推出會員 App：數十萬名旅客要能註冊、用 Google 帳號登入，並把行程照片直接上傳到 S3。這些旅客顯然不該成為 IAM user。

這四種需求分別是**跨帳號存取**、**第三方存取**、**員工身份聯合**與**終端使用者身份**。它們的共同核心是同一件事：**讓外部身份換到一組短期、範圍受限的 AWS 臨時憑證**。這一章就從負責發放臨時憑證的 STS 開始。

## 13.2 STS 與 AssumeRole：換一張臨時通行證

**AWS STS（Security Token Service）** 是發放臨時憑證的服務。第 12 章提過，role 沒有長期憑證，要使用 role，就必須呼叫 STS 的某個 `AssumeRole*` API，換到一組臨時憑證。

| STS API | 誰呼叫 | 用什麼證明身份 | 典型用途 |
|---|---|---|---|
| `AssumeRole` | 已經有 AWS 憑證的 principal | 自己的 AWS 簽章 | 同帳號或跨帳號切換 role、第三方存取 |
| `AssumeRoleWithSAML` | 企業 IdP 登入後的使用者 | SAML assertion | 員工以企業帳號登入 AWS |
| `AssumeRoleWithWebIdentity` | 外部 OIDC 身份 | OIDC token（JWT） | GitHub Actions、EKS Pod、Cognito identity pool |
| `GetSessionToken` | IAM user | 長期 access key（可附 MFA 碼） | 讓 CLI 使用經過 MFA 的臨時憑證 |
| `GetCallerIdentity` | 任何人 | 目前憑證 | 查詢「我現在是誰」，不需要任何權限 |

### 用 CLI 扮演一個 role

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::111122223333:role/prod-readonly \
  --role-session-name lin-investigation \
  --duration-seconds 3600
```

回傳的內容（節錄）：

```json
{
  "Credentials": {
    "AccessKeyId": "ASIAEXAMPLEKEYID1234",
    "SecretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",
    "SessionToken": "IQoJb3JpZ2luX2VjEXAMPLETOKEN",
    "Expiration": "2026-10-01T09:30:00Z"
  },
  "AssumedRoleUser": {
    "AssumedRoleId": "AROAEXAMPLEROLEID:lin-investigation",
    "Arn": "arn:aws:sts::111122223333:assumed-role/prod-readonly/lin-investigation"
  }
}
```

這組憑證和 IAM user 的 access key 有三個差別：access key ID 以 `ASIA` 開頭（長期金鑰是 `AKIA`）、多了一個必須一起送出的 **session token**、以及有明確的**到期時間**。`role-session-name` 會出現在 CloudTrail 的 ARN 中（`assumed-role/prod-readonly/lin-investigation`），所以應該填有意義的值，例如使用者名稱或工作編號，方便稽核。

### Session 時間

- `AssumeRole` 預設的 session 長度是 1 小時，可以用 `DurationSeconds` 指定，最短 15 分鐘。
- 最長不能超過 role 的 **maximum session duration** 設定，這個設定可以介於 1 到 12 小時。
- **Role chaining**（用一個 role 的臨時憑證再去扮演另一個 role）時，session 最長只有 1 小時，不受 maximum session duration 影響（13.12 節）。

實務上，CLI 使用者不必手動複製這些值。在 `~/.aws/config` 設定 profile，CLI 會自動呼叫 STS 並在到期前更新：

```ini
[profile wanderly-dev]
region = ap-northeast-1

[profile prod-readonly]
role_arn = arn:aws:iam::111122223333:role/prod-readonly
source_profile = wanderly-dev
mfa_serial = arn:aws:iam::444455556666:mfa/lin
region = ap-northeast-1
```

執行 `aws s3 ls --profile prod-readonly` 時，CLI 會先用 `wanderly-dev` 的身份呼叫 `AssumeRole`（並要求輸入 MFA 碼），再用拿到的臨時憑證執行指令。

## 13.3 跨帳號 role：兩道門都要開

知道 STS 怎麼發憑證之後，回到 Wanderly 的第一個需求：dev 帳號的 CI/CD role 要能部署到 prod 帳號。標準做法是在 **prod 帳號建立一個 role**，讓 dev 帳號的 CI/CD 來扮演它。

```text
   wanderly-dev（444455556666）                 wanderly-prod（111122223333）
  ┌─────────────────────────────┐              ┌──────────────────────────────────┐
  │ role: ci-runner             │              │ role: prod-deployer              │
  │                             │ ① AssumeRole │                                  │
  │ identity policy:            │─────────────►│ trust policy（第二道門）：         │
  │  Allow sts:AssumeRole       │   （經 STS）  │  Principal = dev 的 ci-runner     │
  │  on prod-deployer           │              │                                  │
  │ （第一道門）                  │◄─────────────│ ② STS 回傳 prod-deployer 的        │
  │                             │  臨時憑證     │    臨時憑證                       │
  │                             │              │                                  │
  │ ③ 用新憑證呼叫 prod 的 API ──┼─────────────►│ permissions policy：              │
  │                             │              │  Allow 部署所需的操作              │
  └─────────────────────────────┘              └──────────────────────────────────┘
```

① dev 帳號的 `ci-runner` 呼叫 `AssumeRole`。STS 會檢查**兩道門**：第一道是 dev 帳號這一側，`ci-runner` 的 identity policy 必須允許對這個 role ARN 執行 `sts:AssumeRole`；第二道是 prod 帳號這一側，`prod-deployer` 的 trust policy 必須信任 `ci-runner`。② 兩道門都通過，STS 才發出臨時憑證。③ 之後所有呼叫都是以 `prod-deployer` 的身份進行，能做什麼完全由 `prod-deployer` 的 permissions policy（加上 prod 帳號的 SCP 等上限）決定。

這是第 12 章「跨帳號時兩邊都要同意」的直接應用：dev 帳號不能單方面闖進 prod，prod 帳號也不能強迫 dev 的身份進來。

### 第一道門：呼叫者的 identity policy（在 dev 帳號）

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAssumeProdDeployer",
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::111122223333:role/prod-deployer"
    }
  ]
}
```

### 第二道門：目標 role 的 trust policy（在 prod 帳號）

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustDevCiRunner",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::444455556666:role/ci-runner"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

`Principal` 也可以寫成整個帳號（`arn:aws:iam::444455556666:root`），意思是「信任 dev 帳號，由 dev 帳號的 IAM 自己決定誰可以扮演」。這樣比較有彈性，但 prod 帳號就無法限制是 dev 帳號裡的哪個身份；需要時可以加上 `aws:PrincipalArn` condition 收窄。給人使用的 role，還可以在 trust policy 加上 `aws:MultiFactorAuthPresent` 條件，要求扮演前必須經過 MFA。

> [!warning] 常見誤解
> 「在 prod-deployer 的 permissions policy 加上 `sts:AssumeRole`，dev 就能扮演它。」錯。Permissions policy 決定的是**扮演之後**能做什麼；「誰可以扮演」只由 trust policy 決定。另一個常見錯誤是以為兩個帳號在同一個 Organization 或同一個 OU 就會自動互信，其實 Organizations 不會建立任何跨帳號信任。

## 13.4 第三方存取：external ID 與 confused deputy

第二個需求是讓 TripMetrics 讀取訂單匯出檔。給對方 access key 會重蹈第 12 章的覆轍，所以答案仍然是跨帳號 role：Wanderly 在 prod 帳號建立 `tripmetrics-reader` role，trust policy 信任 TripMetrics 的 AWS 帳號。但第三方情境多了一個特殊的風險。

### 什麼是 confused deputy

**Confused deputy（混淆代理人）** 指的是：一個擁有權限的代理人（這裡是 TripMetrics 的服務），被某個沒有權限的人騙去替他做事。

TripMetrics 有幾百家客戶，每家客戶都在自己帳號建了一個 role 讓 TripMetrics 扮演。客戶在 TripMetrics 的網頁後台輸入「我的 role ARN」，TripMetrics 的服務就去扮演那個 ARN 讀資料。問題是：role ARN 不是秘密。如果另一家公司（或攻擊者）也是 TripMetrics 的客戶，在後台輸入的卻是 **Wanderly** 的 role ARN，TripMetrics 的服務就會乖乖用自己的身份去扮演 Wanderly 的 role，把 Wanderly 的訂單資料顯示在對方的報表裡。Wanderly 的 trust policy 確實信任 TripMetrics，所以 AWS 沒有理由拒絕。

### External ID 怎麼解決

**External ID** 是一個在 `AssumeRole` 時一起送出的字串。做法是：

1. TripMetrics 為**每一家客戶產生一個唯一的 external ID**（例如 `tm-7f3c9a21-wanderly`），顯示在客戶的後台，而且客戶不能自己修改。
2. Wanderly 在 trust policy 加上條件：只有帶著這個 external ID 的 `AssumeRole` 才被接受。
3. TripMetrics 的服務每次替某客戶扮演 role 時，都帶上**該客戶**的 external ID。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustTripMetricsWithExternalId",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::999988887777:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "tm-7f3c9a21-wanderly"
        }
      }
    }
  ]
}
```

現在，攻擊者在 TripMetrics 後台輸入 Wanderly 的 role ARN，TripMetrics 送出的會是**攻擊者自己**的 external ID，和 Wanderly trust policy 要求的值不符，`AssumeRole` 被拒絕。

```text
  攻擊者在 TripMetrics 後台輸入「Wanderly 的 role ARN」
            │
            ▼
  TripMetrics 服務：AssumeRole(RoleArn = Wanderly 的 role,
                               ExternalId = 攻擊者帳戶的 ID "tm-1b2e...-evil")
            │
            ▼
  Wanderly 的 trust policy：Principal 是 TripMetrics ✓
                           sts:ExternalId 必須是 "tm-7f3c9a21-wanderly" ✗
            │
            ▼
  拒絕：攻擊者無法藉 TripMetrics 之手讀到 Wanderly 的資料
```

External ID 要注意三件事：它**不是密碼**，而是讓代理人把請求對應到正確客戶的識別碼，所以由廠商產生且每個客戶唯一才有意義；它只適用於第三方存取情境，自家帳號之間不需要；trust policy 的 Principal 仍然要限定為廠商的帳號或 role，不能因為有 external ID 就寫成 `"*"`。

### AWS 服務也會是「代理人」

同樣的問題也會發生在 AWS 服務身上。例如你允許 SNS 服務把訊息送進你的 SQS queue，若 queue policy 只寫 `Principal: {"Service": "sns.amazonaws.com"}`，理論上**任何帳號**的 SNS topic 都可能被設定成送到你的 queue。解法是在 resource-based policy 加上 `aws:SourceArn`（限定是哪個 topic）或 `aws:SourceAccount`（限定是哪個帳號的資源），這稱為**跨服務 confused deputy** 防護。

## 13.5 跨帳號存取 S3：扮演 role 還是 bucket policy

TripMetrics 的例子用了扮演 role，但對 S3 這類支援 resource-based policy 的服務，還有另一條路：直接在 bucket policy 授權給對方帳號的身份。兩種方式都正確，差異在細節，也是考試的熱門題型。

### 方式一：扮演資源帳號的 role

就是 13.3 與 13.4 節的做法：資源帳號建 role，呼叫者扮演它，再以 role 的身份存取 bucket。

### 方式二：resource-based policy 直接授權

Wanderly 的資料分析團隊有自己的 `wanderly-analytics` 帳號（`555566667777`），要讀取 prod 帳號的 `wanderly-exports` bucket。prod 帳號的 bucket policy：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAnalyticsEtlRead",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::555566667777:role/analytics-etl"
      },
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::wanderly-exports",
        "arn:aws:s3:::wanderly-exports/*"
      ]
    }
  ]
}
```

而且 analytics 帳號的 `analytics-etl` role 自己的 identity policy 也必須允許這些 S3 操作（跨帳號，兩邊都要同意）。這時 `analytics-etl` **不需要切換身份**，用自己的憑證就能存取 prod 的 bucket。

### 兩種方式比較

| 比較 | 扮演資源帳號的 role | Resource-based policy 直接授權 |
|---|---|---|
| 呼叫者的身份 | 暫時變成資源帳號的 role，**放下原本的權限** | 保持自己的身份與權限 |
| 同時存取兩個帳號的資源 | 不行（除非另一邊也授權給這個 role） | 可以，例如從自己的 bucket 讀、寫到對方 bucket |
| 適用服務 | 所有服務 | 只有支援 resource-based policy 的服務（S3、SQS、SNS、KMS、Lambda、Secrets Manager 等） |
| 權限在哪裡管理 | 集中在資源帳號的 role | 分散在每個資源的 policy，加上呼叫者 identity policy |
| CloudTrail 中的身份 | 資源帳號的 assumed-role session | 呼叫者帳號的原始 principal |
| 新寫入物件的擁有者 | 資源帳號（由該帳號的 role 寫入） | 新 bucket 預設 Bucket owner enforced，物件歸 bucket owner；舊式啟用 ACL 的 bucket 則歸寫入者，需要 `bucket-owner-full-control` |

考試最常見的情境是「把資料從帳號 A 的 bucket 複製到帳號 B 的 bucket」：如果 A 的程式扮演 B 的 role，它就失去讀 A bucket 的權限（除非 A 的 bucket policy 也允許 B 的 role）；用 B 的 bucket policy 授權給 A 的身份，A 的程式就能用同一組憑證讀 A、寫 B。

### 別忘了 KMS

如果 bucket 使用 **SSE-KMS 搭配 customer managed key** 加密，光有 S3 權限還不夠：呼叫者還需要對那把 KMS key 的 `kms:Decrypt`（讀）或 `kms:GenerateDataKey`（寫）權限，而且**key policy 必須允許跨帳號的 principal**，呼叫者的 identity policy 也要允許使用這把 key。用 AWS managed key（`aws/s3`）加密的物件無法跨帳號存取，因為你不能修改 AWS managed key 的 key policy。KMS 的細節在第 15 章。

### 授權整個組織：`aws:PrincipalOrgID`

當有幾十個帳號都需要讀同一個 bucket（例如共用的軟體套件或設定檔），把每個帳號寫進 Principal 既冗長又容易漏掉新帳號。這時可以用 `aws:PrincipalOrgID`：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadFromOurOrganization",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::wanderly-shared-artifacts/*",
      "Condition": {
        "StringEquals": {
          "aws:PrincipalOrgID": "o-a1b2c3d4e5"
        }
      }
    }
  ]
}
```

`Principal: "*"` 搭配 `aws:PrincipalOrgID` 的意思是「任何屬於這個 Organization 的帳號的身份」。新帳號加入組織後自動生效，離開組織後自動失效；各帳號的身份仍需要自己的 identity policy 允許 `s3:GetObject`。

## 13.6 身份聯合：讓外部身份換到 AWS 憑證

前面的例子中，呼叫者本身都是 AWS 身份。但 Wanderly 的員工帳號在 Entra ID，CI/CD 跑在 GitHub，這些身份都不在 AWS 裡。**Identity federation（身份聯合）** 的意思是：AWS 不自己管理這些使用者的密碼，而是**信任一個外部的身份提供者**，由它驗證使用者，AWS 只負責把驗證結果換成臨時憑證。

兩個名詞先定義清楚：

- **IdP（Identity Provider，身份提供者）**：負責驗證使用者身份的系統，例如 Microsoft Entra ID、Okta、Google Workspace、AD FS、GitHub。
- **SP（Service Provider，服務提供者）**：信任 IdP 驗證結果、提供服務的一方，在這裡是 AWS。

聯合登入的好處是使用者只有一組帳號密碼與 MFA（在 IdP），離職時在 IdP 停用即可；AWS 端沒有任何長期憑證。

### SAML 2.0 聯合

**SAML 2.0（Security Assertion Markup Language）** 是企業常用的 XML 格式聯合協定。IdP 驗證使用者後，簽發一份 **SAML assertion**（簽章過的 XML 文件），內容包含「這個人是誰、他可以扮演哪些 role」。

```text
  員工瀏覽器            企業 IdP（Entra ID）          AWS 登入端點 / STS
      │ ① 開啟 AWS 應用入口   │                              │
      │─────────────────────►│                              │
      │ ② 輸入帳密 + MFA      │                              │
      │◄────────────────────►│                              │
      │ ③ 回傳簽章的 SAML     │                              │
      │   assertion（含 role）│                              │
      │◄─────────────────────│                              │
      │ ④ 瀏覽器把 assertion POST 到 https://signin.aws.amazon.com/saml
      │─────────────────────────────────────────────────────►│
      │                       ⑤ AWS 用 IAM SAML provider 中的 IdP 憑證驗證簽章，
      │                          呼叫 AssumeRoleWithSAML，檢查 role 的 trust policy
      │ ⑥ 取得臨時憑證，導向 console                           │
      │◄─────────────────────────────────────────────────────│
```

① 員工從 IdP 的應用入口點選 AWS。② IdP 驗證帳密與 MFA，MFA 的責任在 IdP。③ IdP 依員工所屬群組，在 assertion 中列出他可以扮演的 role。④ 瀏覽器把 assertion 送到 AWS。⑤ AWS 事先在 IAM 建立了一個 **SAML identity provider**（上傳 IdP 的 metadata，裡面有驗證簽章用的憑證），據此驗證 assertion 確實出自這個 IdP，再檢查 role 的 trust policy。⑥ 驗證通過，員工以 role 的身份進入 console。

Role 的 trust policy 信任的是這個 SAML provider：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::111122223333:saml-provider/WanderlyEntra"
      },
      "Action": "sts:AssumeRoleWithSAML",
      "Condition": {
        "StringEquals": {
          "SAML:aud": "https://signin.aws.amazon.com/saml"
        }
      }
    }
  ]
}
```

這種「每個帳號各自設定 SAML provider 與 role」的做法在帳號少時可行；帳號一多，每個帳號都要重複設定，就該改用 13.7 節的 IAM Identity Center。

### OIDC 聯合：以 GitHub Actions 為例

**OIDC（OpenID Connect）** 是建立在 OAuth 2.0 之上、使用 JSON 格式 **JWT（JSON Web Token）** 的聯合協定，常見於 Web、行動 App 與雲端原生工具。Wanderly 的程式碼放在 GitHub，部署 workflow 原本把 access key 存在 GitHub secrets；改用 OIDC 後，GitHub 會在每次 workflow 執行時簽發一個短期 token，AWS 驗證後發出臨時憑證。

設定步驟是：在 IAM 建立一個 **OIDC identity provider**，URL 為 `https://token.actions.githubusercontent.com`、audience 為 `sts.amazonaws.com`；再建立一個 role，trust policy 如下：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::444455556666:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:wanderly/booking-api:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

`sub`（subject）條件是這份 policy 的安全關鍵：它限定只有 `wanderly/booking-api` repository 的 `main` 分支能扮演這個 role。少了這個條件，**任何 GitHub 使用者的 workflow** 都能拿到有效的 GitHub token 來扮演它。

同樣的 OIDC 機制也用在 EKS：Pod 透過 IRSA（IAM Roles for Service Accounts）或 EKS Pod Identity 取得 role 憑證（第 21 章）；Cognito identity pool 底層也是 `AssumeRoleWithWebIdentity`（13.9 節）。

### 地端伺服器：IAM Roles Anywhere

在地端資料中心或其他雲執行的程式，既不在 AWS 上（不能用 instance profile），也不一定有 OIDC IdP。**IAM Roles Anywhere** 讓這些機器用 **X.509 憑證**（由你信任的憑證機構簽發，例如 AWS Private CA 或公司內部 CA）換取 role 的臨時憑證。你在 Roles Anywhere 設定 **trust anchor**（信任哪個 CA）與 **profile**（可以換到哪些 role），機器上的程式透過 AWS 提供的 credential helper 取得憑證，不需要任何 access key。

## 13.7 IAM Identity Center：多帳號的員工登入入口

Wanderly 很快就從兩個帳號長到八個（prod、staging、dev、analytics、security、log archive、shared services、sandbox，第 14、40 章）。每個帳號都設 SAML provider 和一堆 role，再由 IdP 管理員把每個 role 對應到群組，維護成本迅速失控。**AWS IAM Identity Center**（前身是 AWS SSO）就是為了這個問題：**在一個地方管理員工能進哪些帳號、以什麼權限進去**。

### 核心概念

- **Identity source（身份來源）**：使用者與群組從哪裡來，同一時間只能選一種：
  - **Identity Center directory**：在 Identity Center 內直接建立使用者，適合沒有企業目錄的小公司。
  - **Active Directory**：連接 AWS Managed Microsoft AD，或透過 AD Connector 連接地端自管的 AD（13.8 節）。
  - **External IdP**：Entra ID、Okta、Google Workspace 等，以 SAML 2.0 做登入驗證，並以 **SCIM（System for Cross-domain Identity Management）** 自動同步使用者與群組。
- **Permission set（權限集）**：一份權限範本，可包含 AWS managed policy、customer managed policy（以名稱引用，必須在每個目標帳號存在同名 policy）、inline policy 與 permissions boundary，並設定 session 長度（預設 1 小時，最長 12 小時）。
- **Assignment（指派）**：「哪個使用者或群組 + 哪個 permission set + 哪個帳號」的三元組。
- **AWS access portal**：員工登入後看到的入口頁面，列出他能進的帳號與權限，點一下就進入 console，或取得 CLI 用的臨時憑證。

```text
   Entra ID（external IdP）
   ┌─────────────────────┐   SCIM：自動同步使用者與群組
   │ 群組：eng-booking    │─────────────────────────────┐
   │ 群組：finance        │   SAML：登入驗證（含 MFA）     │
   └─────────────────────┘─────────────────────────────┤
                                                       ▼
                                   ┌─────────── IAM Identity Center ───────────┐
                                   │ Permission sets：                         │
                                   │   Developer（PowerUser + boundary，8 小時）│
                                   │   ReadOnly（ViewOnlyAccess，4 小時）        │
                                   │   Billing（Billing 職能 policy）            │
                                   │                                           │
                                   │ Assignments：                              │
                                   │   eng-booking + Developer → dev、staging   │
                                   │   eng-booking + ReadOnly  → prod           │
                                   │   finance     + Billing   → management     │
                                   └───────┬───────────────┬───────────────┬───┘
                                ① 佈建 role │               │               │
                                           ▼               ▼               ▼
                                  dev 帳號           staging 帳號        prod 帳號
                           AWSReservedSSO_Developer_… 等 role，trust policy 自動信任 Identity Center
```

① 建立 assignment 時，Identity Center 會在每個目標帳號**自動建立對應的 IAM role**（名稱以 `AWSReservedSSO_` 開頭），trust policy 信任 Identity Center 的 SAML provider。這些 role 由 Identity Center 管理，不要手動修改；修改 permission set 後，Identity Center 會把變更推送到所有已指派的帳號。員工登入 access portal、選擇「prod／ReadOnly」時，背後其實就是扮演 prod 帳號裡的 `AWSReservedSSO_ReadOnly_…` role。

### 為什麼 SCIM 和 SAML 都需要

這是 SAP 的經典考點。**SAML 只負責登入那一刻的驗證**；Identity Center 要能在使用者第一次登入前就把他放進群組、指派權限，必須事先知道這些使用者與群組存在。**SCIM 負責持續同步**：IdP 新增員工、調整群組、停用離職者時，自動反映到 Identity Center。少了 SCIM，就要在 Identity Center 手動建立對應的使用者與群組，離職處理也會出現落差。

### CLI 與工具

開發者不需要任何 access key：

```bash
aws configure sso          # 第一次設定：輸入 access portal URL，選擇帳號與 permission set
aws sso login --profile wanderly-prod-readonly
aws s3 ls --profile wanderly-prod-readonly
```

CLI 會開啟瀏覽器走一次 IdP 登入，之後在 session 期間自動取得並更新臨時憑證。

### Identity Center 的其他要點

- 啟用在 Organizations 的 management account（**organization instance**），可以管理組織內所有帳號；也有只用於單一帳號應用程式的 **account instance**，但它不能管理多帳號的 AWS 存取。
- 可以把一個成員帳號註冊為 **delegated administrator**，日常管理在該帳號進行，減少使用 management account 的機會（13.12 節）。
- **Attributes for access control**：把 IdP 中的員工屬性（部門、專案）以 session tag 傳入，搭配第 12 章的 ABAC policy 使用。
- 除了 AWS 帳號，Identity Center 也能作為員工登入其他 SAML 應用程式與部分 AWS 應用程式的入口。

## 13.8 AWS Directory Service：當你需要真正的 Active Directory

Identity Center 解決「員工如何登入 AWS 帳號」。但很多企業還有另一種需求：Windows 伺服器要加入網域、SQL Server 使用 Windows 驗證、檔案伺服器依 AD 群組控制權限、虛擬桌面用公司帳號登入。這些需要的是一個**真正的 Active Directory 網域**，也就是 **AWS Directory Service**。

**Active Directory（AD）** 是微軟的目錄服務，負責管理網域中的使用者、電腦、群組，提供 Kerberos／LDAP 驗證與 Group Policy。Directory Service 提供三種選擇：

| 類型 | 是什麼 | 適合 | 限制與注意 |
|---|---|---|---|
| **AWS Managed Microsoft AD** | AWS 代管的真正 Microsoft AD，網域控制站部署在你 VPC 的兩個 AZ | AWS 上需要完整 AD 功能的 workload；與地端 AD 建立 trust | 有 Standard 與 Enterprise 兩種版本；Enterprise 支援多 Region 複寫 |
| **AD Connector** | 一個代理（proxy），把驗證請求轉送到地端既有的 AD | 想沿用地端 AD、不在雲端存放目錄資料 | 不快取資料；必須有穩定的 VPN 或 Direct Connect 連回地端，地端 AD 故障時驗證也會失敗 |
| **Simple AD** | 基於 Samba 的相容 AD 目錄 | 小型、只需要基本 AD 功能（網域加入、LDAP）的環境 | 不支援與其他 AD 網域建立 trust，功能為子集 |

選擇的關鍵問題：

1. **要不要在 AWS 跑依賴 AD 的 workload？** 例如 FSx for Windows File Server（第 24 章）、RDS for SQL Server 的 Windows 驗證、Amazon WorkSpaces。這些服務原生整合 AWS Managed Microsoft AD。如果企業同時有地端 AD，常見設計是 Managed AD 與地端 AD 建立 **trust（信任關係）**：使用者帳號仍在地端，AWS 上的資源信任地端網域的身份。
2. **只是想讓 AWS 服務用地端 AD 帳號登入？** AD Connector 最輕量：不複製任何目錄資料，只轉送驗證。代價是依賴連線與地端 AD 的可用性。
3. **沒有既有 AD，只要基本功能、規模小？** Simple AD 或直接用 Managed AD。

Identity Center 的 identity source 可以設為 Managed Microsoft AD，或透過 AD Connector 連接自管的 AD，讓員工用 AD 帳號登入所有 AWS 帳號。

> [!warning] 常見誤解
> 「AD Connector 會把地端 AD 複製到 AWS，所以地端斷線也能登入。」不會。AD Connector 只是代理，每一次驗證都要轉送到地端。需要「AWS 端在地端斷線時仍能驗證」，應使用 AWS Managed Microsoft AD（必要時與地端建立 trust）。

## 13.9 Amazon Cognito：網站與 App 的終端使用者

最後一個需求是會員 App 的數十萬名旅客。他們和員工完全不同：人數多、會自己註冊、可能用 Google 帳號登入，而且大部分時候只需要呼叫 Wanderly 的 API，不需要「進入 AWS 帳號」。把他們建成 IAM user 或 Identity Center 使用者都是錯的。**Amazon Cognito** 是專為終端使用者（customer identity）設計的服務，由兩個獨立元件組成，名稱相近，考試最愛混淆。

### User pool：使用者目錄與登入

**Cognito user pool** 是一個受管的使用者目錄，負責「讓使用者登入你的應用程式」：

- 註冊、登入、email／電話驗證、忘記密碼、MFA。
- 社群登入（Google、Facebook、Apple、Login with Amazon）與企業登入（SAML、OIDC）的聯合。
- 提供託管的登入頁面（hosted UI，新版稱 managed login），也可以用 SDK 自己做畫面。
- 用 Lambda trigger 客製流程，例如註冊前檢查、登入後寫入紀錄、在 token 中加入自訂欄位。
- 登入成功後發出三種 JWT：**ID token**（使用者是誰，含 email 等屬性）、**access token**（可以呼叫哪些 API scope）、**refresh token**（用來換新的 ID／access token）。ID 與 access token 預設 1 小時有效，可調整。

User pool 的輸出是 **JWT**，不是 AWS 憑證。這些 token 交給你的 API 驗證：API Gateway 可以用 **Cognito user pool authorizer**（REST API）或 JWT authorizer（HTTP API）直接驗證 token（第 20 章）；ALB 可以在 listener 規則中用 `authenticate-cognito` 動作，讓未登入的使用者先導向登入頁（第 10 章）。

> [!note]
> User pool 是 Regional 資源，但它已經支援 **multi-Region replication**：可以在另一個 Region 建立一個 secondary replica user pool，在主要 Region 故障時接手登入與發 token。前提是 user pool 使用 Essentials 或 Plus 方案、並以 KMS multi-Region key 加密；secondary 只能有一個，在 secondary 上不能註冊新使用者、重設密碼或修改使用者資料，使用 TOTP MFA 的使用者也無法在 secondary 登入。多 Region DR 怎麼處理這些限制，見第 53 章。

### Identity pool：把使用者換成 AWS 臨時憑證

**Cognito identity pool**（也稱 federated identities）負責「讓使用者**直接存取 AWS 服務**」：它接收已驗證的身份（user pool token、Google／Apple token、SAML assertion），透過 `AssumeRoleWithWebIdentity` 換成 IAM role 的**臨時 AWS 憑證**。

- **Authenticated role**：已登入使用者扮演的 role。
- **Unauthenticated role（guest）**：可選，讓未登入的訪客也能取得非常有限的權限（例如讀取公開的旅遊地圖資料）。
- 可以依規則或 token 中的群組資訊，對不同使用者指派不同 role。

Wanderly 的 App 要讓旅客把照片直接上傳到 S3，而且每個人只能存取自己的資料夾。Authenticated role 的權限用 policy variable 實現：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OwnPrefixOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::wanderly-trip-photos/private/${cognito-identity.amazonaws.com:sub}/*"
    }
  ]
}
```

`${cognito-identity.amazonaws.com:sub}` 會被替換成這位使用者在 identity pool 中的唯一 identity ID，所以每個人只能讀寫自己的路徑。這個 role 的 trust policy 信任 `cognito-identity.amazonaws.com`，並限定 identity pool ID 與「已驗證」狀態：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "cognito-identity.amazonaws.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "cognito-identity.amazonaws.com:aud": "ap-northeast-1:0f1e2d3c-4b5a-6978-8a9b-0c1d2e3f4a5b"
        },
        "ForAnyValue:StringLike": {
          "cognito-identity.amazonaws.com:amr": "authenticated"
        }
      }
    }
  ]
}
```

### 把兩者組起來：會員 App 的登入流程

```text
   旅客 App
     │ ① 帳密或「用 Google 登入」
     ▼
  [Cognito user pool] ── ② 回傳 ID / access / refresh token（JWT）
     │
     ├─ ③a 呼叫訂房 API：Authorization: Bearer <access token>
     │        ▼
     │   [API Gateway + Cognito authorizer] ── 驗證 JWT ──► [Lambda] ──► [DynamoDB]
     │
     └─ ③b 要直接上傳照片：把 ID token 交給 identity pool
              ▼
         [Cognito identity pool] ── ④ AssumeRoleWithWebIdentity
              ▼
         取得 authenticated role 的臨時 AWS 憑證
              ▼
         ⑤ App 用臨時憑證直接 PutObject 到 s3://wanderly-trip-photos/private/<identity ID>/
```

① 使用者在 user pool 登入，可能透過 Google 聯合。② User pool 發出 JWT。③a 一般 API 呼叫只需要 JWT，由 API Gateway 驗證，**不需要** identity pool。③b 只有 App 要直接呼叫 AWS 服務（S3、DynamoDB、IoT 等）時，才需要 identity pool 把 token 換成 AWS 憑證。④⑤ 換到的憑證只有 authenticated role 的權限，並被 policy variable 限制在自己的路徑。

另一種常見做法是不讓 App 直接拿 AWS 憑證，而是由後端 API 產生 **S3 presigned URL**（第 22 章）交給 App 上傳。這樣 App 只需要 user pool，權限控制集中在後端；需要 App 自己頻繁存取多種 AWS 服務時，identity pool 才比較划算。

> [!tip] 考試提示
> 題目關鍵字是「使用者註冊、登入、社群登入、JWT、API 授權」→ user pool。關鍵字是「行動 App 直接存取 S3／DynamoDB、臨時 AWS 憑證、guest 存取」→ identity pool。兩者都出現時，通常是「user pool 驗證 + identity pool 換憑證」的組合。

## 13.10 比較與選型

### 誰要登入？用哪一種機制

```text
要取得 AWS 存取權的是誰？
├─ 另一個自家 AWS 帳號的身份
│   ├─ 要用到多種服務、或想集中管理權限 → 跨帳號 role（AssumeRole）
│   └─ 只存取支援 resource policy 的資源、且要保留自己的權限 → resource-based policy
│        └─ 授權對象是整個組織 → aws:PrincipalOrgID
├─ 第三方廠商的 AWS 帳號 → 跨帳號 role + 廠商提供的唯一 external ID
├─ 員工
│   ├─ 多帳號、想集中管理 → IAM Identity Center（external IdP + SCIM 或 AD）
│   └─ 少數帳號、已有 SAML IdP → IAM SAML provider + role（較舊、較分散）
├─ 需要 Windows 網域、Kerberos、Group Policy 的 workload
│   ├─ AWS 上要有完整 AD → AWS Managed Microsoft AD（可與地端 trust）
│   ├─ 沿用地端 AD、不在雲端存目錄 → AD Connector
│   └─ 小型、基本功能 → Simple AD
├─ CI/CD（GitHub Actions 等）→ OIDC identity provider + role（限定 sub）
├─ 地端伺服器 → IAM Roles Anywhere（X.509）
└─ 網站／App 的終端使用者
    ├─ 登入、註冊、JWT → Cognito user pool
    └─ App 直接存取 AWS 服務 → 再加 Cognito identity pool
```

### 身份服務對照

| 服務 | 身份對象 | 輸出 | 典型規模 | 關鍵字 |
|---|---|---|---|---|
| IAM（user／role） | AWS 帳號內的身份、程式 | 長期或臨時 AWS 憑證 | 帳號內 | role、policy、instance profile |
| STS | 任何要換臨時憑證的身份 | 臨時 AWS 憑證 | — | AssumeRole、external ID、session |
| IAM Identity Center | 員工（workforce） | 各帳號 role 的臨時憑證 | 組織內所有帳號 | permission set、assignment、SCIM |
| Directory Service | Windows 網域的使用者與電腦 | Kerberos／LDAP 驗證 | 企業目錄 | domain join、trust、Group Policy |
| Cognito user pool | 終端使用者（customer） | JWT（ID／access／refresh） | 可達數百萬使用者 | sign-up、social login、authorizer |
| Cognito identity pool | 終端使用者或訪客 | 臨時 AWS 憑證 | 同上 | guest、直接存取 S3、`AssumeRoleWithWebIdentity` |

## 13.11 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 帳號 A 的身份要操作帳號 B 的資源 | B 建 role（trust policy 信任 A），A 的 identity policy 允許 `sts:AssumeRole` |
| 第三方廠商需要存取、防止 confused deputy | 跨帳號 role + `sts:ExternalId` 條件 |
| 允許 AWS 服務寫入資源，避免其他帳號利用 | `aws:SourceArn`／`aws:SourceAccount` |
| 從帳號 A 的 bucket 複製到帳號 B 的 bucket | B 的 bucket policy 授權 A 的身份（保留 A 的權限） |
| 跨帳號讀 SSE-KMS 物件被拒 | Key policy 允許對方 principal + 對方 identity policy 允許 `kms:Decrypt` |
| 整個組織的帳號都能讀一個 bucket | `Principal: "*"` + `aws:PrincipalOrgID` |
| 員工用企業帳號登入多個 AWS 帳號 | IAM Identity Center + permission sets + assignments |
| 外部 IdP 自動同步使用者與群組 | SCIM（SAML 只負責登入） |
| 地端 AD 帳號登入 AWS，不想在雲端存目錄 | AD Connector |
| AWS 上需要完整 AD（FSx for Windows、SQL Server Windows 驗證）並信任地端 | AWS Managed Microsoft AD + trust |
| CI/CD 不想存 access key | OIDC identity provider + `AssumeRoleWithWebIdentity`（限定 `sub`） |
| 地端伺服器要呼叫 AWS 但不想用 access key | IAM Roles Anywhere |
| App 使用者註冊、登入、社群登入 | Cognito user pool |
| 行動 App 直接上傳 S3、每人只能存取自己的資料 | Cognito identity pool + `${cognito-identity.amazonaws.com:sub}` |
| API Gateway 驗證使用者 JWT | Cognito user pool authorizer |

**常見陷阱**：

1. 以為只要在目標 role 的 trust policy 信任對方就夠了。跨帳號時呼叫者這一側也必須有 `sts:AssumeRole` 的 Allow。
2. 把 external ID 當成密碼，或讓客戶自己決定 external ID。它應由廠商為每個客戶產生、唯一且不可由客戶修改，Principal 仍然要限定廠商帳號。
3. 為終端使用者建立 IAM user 或 Identity Center 使用者。終端使用者一律用 Cognito。
4. 混淆 user pool 與 identity pool：user pool 發 JWT，identity pool 發 AWS 臨時憑證。
5. 以為 AD Connector 會快取或複製目錄。它只是代理，地端連線中斷就無法驗證。
6. 以為用 AWS managed key（`aws/s3`）加密的物件可以跨帳號分享。必須改用 customer managed key 並修改 key policy。

## 13.12 SAP 加深：大規模身份治理

### Role chaining 與 session 長度

**Role chaining** 是用一個 role session 的憑證再去扮演另一個 role，例如員工從 Identity Center 進入 security 帳號，再扮演各帳號的 audit role。Chaining 的 session 最長 1 小時；若 `DurationSeconds` 要求超過 3600 秒，`AssumeRole` 會直接失敗，調高目標 role 的 maximum session duration 也沒用。長時間的批次作業應減少 chaining 的層數，並在憑證到期前重新扮演 role 取得新憑證（AWS SDK 的 assume-role credential provider 可以自動更新）。

### 追溯真正的人：source identity 與 session tags

多人共用同一個 role 時，CloudTrail 只看到 `assumed-role/ops-admin/xxx`，session name 又可能由使用者自己填。SAP 題目常問「如何可靠地追溯是誰做的」：

- **Source identity**：在第一次扮演 role 時設定（例如由 IdP 透過 SAML 屬性帶入員工帳號），之後**整條 role chaining 都會保留、而且不能被修改**，CloudTrail 會記錄它。Role 的 trust policy 需要允許 `sts:SetSourceIdentity`，也可以用 condition 要求必須帶有 source identity。
- **Session tags**：扮演 role 時傳入的 key-value 屬性（trust policy 需允許 `sts:TagSession`），可用於 ABAC（`aws:PrincipalTag`）；標為 transitive 的 tag 會在 role chaining 中延續。

### 撤銷已發出的臨時憑證

臨時憑證發出後，在到期前都有效，刪除或修改 role 的 trust policy **不會**讓已經發出的憑證失效。需要立即止血時：

- IAM role：在 console 執行 **Revoke active sessions**，IAM 會在 role 上加一條 inline policy，Deny 所有在此時間點之前發出的憑證（以 `aws:TokenIssueTime` 判斷）。之後重新扮演的 session 不受影響。
- Identity Center：要分開處理「再取得新憑證的能力」與「手上已有的憑證」。前者靠在 IdP 停用使用者（由 SCIM 同步）、移除他的 assignment 與群組成員資格，並在 Identity Center console 刪除他的 **active session**（access portal 的登入狀態；只停用使用者而不刪除 session 時，他仍能用既有的 portal session 扮演新的 role）。後者因為帳號 role 憑證在 permission set 的 session 時間內仍有效，AWS 建議事先部署一份 explicit Deny：以 `identitystore:userId` 條件（Identity Center 中每位使用者唯一且不會變的 User ID）拒絕所有動作，放在 SCP 或 permission set 的 inline policy 中，需要時填入該使用者的 ID，並至少保留到所有可能的 session 都過期（最長 12 小時）。把 permission set 的 session 長度設短，也能縮小這個風險窗口。

### Identity Center 的委派與邊界

- 把 Identity Center 的日常管理委派給專門的 identity 或 security 帳號（**delegated administrator**），減少登入 management account 的需求。
- Delegated administrator **不能**管理指派到 management account 的 permission set；這些 assignment 仍須在 management account 中處理。這是刻意的設計，避免成員帳號的管理員取得 management account 的權限。
- Permission set 內引用 customer managed policy 時，每個目標帳號都必須有同名 policy，通常用 StackSets 或 Control Tower 的帳號 baseline 統一部署（第 37、40 章）。

### Break-glass：IdP 故障時怎麼進 AWS

如果所有員工都依賴外部 IdP 登入，IdP 故障或設定錯誤時，就可能沒有人能登入 AWS 處理事故。常見的 **break-glass（緊急存取）** 設計是：在少數關鍵帳號保留極少量的 IAM user 或專用的緊急身份，使用實體安全金鑰 MFA，憑證分開保管、雙人控管，每次使用都觸發 CloudTrail 警報並事後檢討。這些身份平時不用，也要定期演練確認仍可使用。

### 多帳號存取模式總整理

| 模式 | 適合 | 注意 |
|---|---|---|
| Identity Center permission set | 員工登入任何帳號 | 依職能與環境設計少量 permission set |
| 跨帳號 role（hub-and-spoke） | 中央工具（部署、稽核、備份）操作所有帳號 | 用 StackSets 在每個帳號部署相同的 role，trust policy 限定中央帳號的特定 role |
| Resource-based policy + `aws:PrincipalOrgID` | 共用資源（套件、映像、設定）給全組織 | 搭配 RCP 建立組織級資料邊界（第 14 章） |
| AWS RAM 共享 | 共享 subnet、TGW、Resolver rules 等資源本身 | 第 7、8、41 章 |

## 本章重點整理

- STS 把各種身份換成臨時憑證（`ASIA` 開頭的 key ID、session token、到期時間）；`AssumeRole` 預設 1 小時，最長為 role 的 maximum session duration（1–12 小時）。
- 跨帳號扮演 role 要開兩道門：呼叫者帳號的 identity policy 允許 `sts:AssumeRole`，目標 role 的 trust policy 信任呼叫者；扮演後的權限只由目標 role 決定。
- Organizations 或同一個 OU 不會自動建立任何跨帳號信任。
- 第三方存取用跨帳號 role 加上廠商為每個客戶產生的唯一 external ID，防止 confused deputy；AWS 服務作為代理人時用 `aws:SourceArn`／`aws:SourceAccount`。
- 跨帳號存取 S3 有兩種方式：扮演 role 會放下原本的權限，resource-based policy 讓呼叫者保留自己的權限，適合跨帳號複製資料。
- 跨帳號讀取 SSE-KMS 物件需要 customer managed key 的 key policy 允許對方，AWS managed key 無法跨帳號使用。
- `Principal: "*"` 搭配 `aws:PrincipalOrgID` 可以把資源開放給整個組織，新帳號自動適用。
- SAML 2.0 與 OIDC 讓外部 IdP 驗證使用者，AWS 只發臨時憑證；GitHub Actions 的 OIDC trust policy 必須限定 `sub`。
- 地端伺服器可以用 IAM Roles Anywhere 以 X.509 憑證取得臨時憑證，不需要 access key。
- IAM Identity Center 以 permission set + assignment 管理多帳號員工存取，會在每個帳號自動建立 `AWSReservedSSO_` role；外部 IdP 用 SAML 登入、SCIM 同步使用者與群組。
- Directory Service：Managed Microsoft AD 是真正的 AD（可與地端 trust），AD Connector 是不快取的代理，Simple AD 是基本功能的 Samba 相容目錄。
- Cognito user pool 是終端使用者目錄並發出 JWT，identity pool 把身份換成 AWS 臨時憑證並支援 guest 存取。
- Role chaining 的 session 最長 1 小時；source identity 在整條 chaining 中保留且不可修改，是追溯真人的可靠依據。
- 已發出的臨時憑證在到期前有效，要立即撤銷需用 Revoke active sessions 或 explicit Deny；Identity Center 使用者則以 `identitystore:userId` 條件的 Deny 搭配刪除 active session。

### 練習 13-1｜SAA｜單選｜跨帳號部署的必要設定

Wanderly 的 CI/CD 在 dev 帳號（`444455556666`）以 `ci-runner` role 執行，需要部署 CloudFormation stack 到 prod 帳號（`111122223333`）。資安團隊禁止在 prod 帳號建立 IAM user，並要求 prod 帳號能明確控制哪個身份可以進來、進來後能做什麼。

哪個設定組合正確且完整？

- A. 在 prod 帳號建立 `prod-deployer` role，trust policy 信任 dev 帳號的 `ci-runner` role，permissions policy 只給部署所需權限；在 `ci-runner` 的 identity policy 允許對 `prod-deployer` 執行 `sts:AssumeRole`
- B. 在 prod 帳號建立 `prod-deployer` role，在它的 permissions policy 中允許 `sts:AssumeRole`，Principal 設為 dev 帳號
- C. 在 prod 帳號建立 IAM user 並產生 access key，存放在 dev 帳號的 Secrets Manager，由 `ci-runner` 讀取
- D. 把兩個帳號放入同一個 OU，`ci-runner` 就能直接使用 prod 帳號的資源

> **A ✓** 跨帳號扮演 role 需要兩道門：目標 role 的 trust policy 信任呼叫者，呼叫者的 identity policy 允許 `sts:AssumeRole`。扮演後的權限由 `prod-deployer` 的 permissions policy 決定，prod 帳號因此同時控制「誰能進來」與「進來能做什麼」。
>
> **B ✗** Permissions policy 決定扮演之後能做什麼，不能決定誰可以扮演；identity-based policy 也沒有 Principal 欄位。「誰能扮演」只寫在 trust policy。
>
> **C ✗** 在 prod 建立 IAM user 違反資安規定，而且又引入長期憑證；存在 Secrets Manager 並不改變它是長期金鑰的事實。
>
> **D ✗** OU 只是組織帳號與套用 SCP 的方式，不會建立任何跨帳號信任或授權。
>
> **考點**：SAA-1.1｜跨帳號 AssumeRole 的兩道門

### 練習 13-2｜SAA｜單選｜第三方廠商的跨帳號存取

Wanderly 簽約了一家分析 SaaS 廠商，對方服務數百家客戶，需要每天讀取 Wanderly prod 帳號中 `wanderly-exports` bucket 的檔案。廠商提供了它的 AWS 帳號 ID，並在後台為 Wanderly 顯示一個專屬的識別字串。Wanderly 擔心其他客戶能透過廠商的服務讀到自己的資料。

最安全的做法是什麼？

- A. 建立 IAM user 並把最小權限的 access key 交給廠商，每 90 天輪替
- B. 在 bucket policy 中把 Principal 設為 `"*"`，並加上 `aws:SourceIp` 限定廠商的 IP 範圍
- C. 建立只能讀取該 bucket 的 role，trust policy 信任廠商的帳號，並以 `sts:ExternalId` 條件要求廠商提供的專屬識別字串
- D. 建立只能讀取該 bucket 的 role，trust policy 信任廠商帳號，並把 role ARN 設成難以猜測的長名稱

> [!answer]- 答案：C
> **A ✗** 長期 access key 交給第三方後很難掌握保管狀況，輪替也需要雙方協調；跨帳號 role 才是標準做法。
>
> **B ✗** `Principal: "*"` 搭配 IP 條件仍然讓任何從那些 IP 發出的請求都能讀取，廠商的其他客戶若透過同一服務發出請求，也無法區分；IP 也可能變動。
>
> **C ✓** 跨帳號 role 讓廠商使用臨時憑證；external ID 由廠商為每個客戶產生且唯一，廠商替其他客戶扮演 role 時會帶上那位客戶的 ID，無法通過 Wanderly 的 trust policy，從而防止 confused deputy。
>
> **D ✗** Role ARN 不是秘密，會出現在設定與紀錄中；靠名稱難猜無法阻止別人在廠商後台輸入這個 ARN。
>
> **考點**：SAA-1.1、SAA-1.2｜external ID 與 confused deputy

### 練習 13-3｜SAA｜單選｜跨帳號複製 S3 資料

Wanderly 的資料團隊在 analytics 帳號執行一個 ETL 作業，以 `etl-job` role 執行。作業要從 analytics 帳號自己的 `raw-events` bucket 讀取資料，處理後寫入 prod 帳號的 `wanderly-reports` bucket。兩個 bucket 都使用 SSE-S3 加密，`wanderly-reports` 的 Object Ownership 為 Bucket owner enforced。團隊希望作業只用一組憑證完成讀寫，並維持最小權限。

最合適的做法是什麼？

- A. 在 prod 帳號建立 role 讓 `etl-job` 扮演，以該 role 的身份同時讀取 `raw-events` 並寫入 `wanderly-reports`
- B. 在 `wanderly-reports` 的 bucket policy 允許 `etl-job` role 執行 `s3:PutObject`，並在 `etl-job` 的 identity policy 允許讀 `raw-events`、寫 `wanderly-reports`
- C. 把 `wanderly-reports` 的 Block Public Access 關閉，讓 `etl-job` 能直接寫入
- D. 在 analytics 帳號建立一個 IAM user，把它的 access key 加到 prod 帳號的 bucket ACL 中

> [!answer]- 答案：B
> **A ✗** 扮演 prod 帳號的 role 後，session 只剩 prod role 的權限，失去讀取 analytics 帳號 `raw-events` 的能力，除非 `raw-events` 的 bucket policy 也另外授權給那個 prod role，增加設定複雜度。
>
> **B ✓** Resource-based policy 讓 `etl-job` 保留自己的身份與權限：它用同一組憑證讀自己帳號的 bucket，並依 `wanderly-reports` 的 bucket policy 寫入對方 bucket。跨帳號時兩邊都要允許，所以 identity policy 也要允許寫入。Bucket owner enforced 確保寫入的物件歸 prod 帳號擁有。
>
> **C ✗** Block Public Access 是防止公開存取，與跨帳號授權無關；關閉它只會增加資料外洩風險，`etl-job` 仍然需要明確的授權。
>
> **D ✗** ACL 是舊式機制，新 bucket 預設停用；ACL 授權的對象是帳號而不是 access key，而且又引入長期憑證。
>
> **考點**：SAA-1.1、SAA-1.3｜跨帳號 S3 的 resource-based policy 與 assume role 比較

### 練習 13-11｜SAP｜單選｜Role chaining 的 session 長度

第二次 `AssumeRole` 的結果最可能是什麼？應如何改善？

- A. 成功並取得 4 小時的憑證，因為目標 role 的 maximum session duration 為 12 小時
- B. 成功但取得 12 小時的憑證，因為 STS 會自動使用 maximum session duration
- C. 失敗，因為 role chaining 的 session 最長 1 小時；應把 `DurationSeconds` 設為 3600 以內，並在作業執行期間於憑證到期前重新扮演 role 取得新憑證

>
> **C ✓** Role chaining 的 session 最長 1 小時，要求 14400 秒會讓 `AssumeRole` 失敗。長時間作業應把每次要求的時間控制在 1 小時內，並在到期前重新扮演 role（SDK 的 credential provider 可以自動處理），而不是要求一次拿到 4 小時的憑證。
>
> **D ✗** 15 分鐘是 `DurationSeconds` 的最小值，不是跨帳號的上限；改用長期 access key 違反最佳實務。

Wanderly 透過 IAM Identity Center 管理 30 個帳號的員工存取，identity source 是 Entra ID 並啟用 SCIM。一位擁有 prod 帳號管理權限的工程師因安全事件被立即解僱，他的 permission set session 長度設為 8 小時，而且他在一小時前剛取得過 prod 帳號的 CLI 臨時憑證。資安團隊要求立刻阻止他再登入，並讓他手上已取得的憑證盡快失效。

- B. 刪除他使用的 permission set，讓所有帳號中的對應 role 消失
- C. 不需要其他動作，因為停用使用者後 Identity Center 會讓所有已發出的 AWS 憑證立即失效

### 練習 13-13｜SAP｜單選｜跨帳號讀取 SSE-KMS 物件

Wanderly 的 analytics 帳號中，`bi-reader` role 要讀取 prod 帳號 `wanderly-orders` bucket 的物件。bucket 使用 SSE-KMS，金鑰是 prod 帳號的 customer managed key。prod 的 bucket policy 已允許 `bi-reader` 執行 `s3:GetObject`，`bi-reader` 的 identity policy 也允許對該 bucket 的 `s3:GetObject`，但讀取時仍然收到 AccessDenied。

應如何修正？

- A. 把 bucket 的預設加密改成 AWS managed key `aws/s3`，讓跨帳號存取不需要 KMS 權限
- B. 在 prod 帳號那把 customer managed key 的 key policy 允許 `bi-reader` 使用 `kms:Decrypt`，並在 `bi-reader` 的 identity policy 允許對該 key ARN 執行 `kms:Decrypt`

- D. 在 bucket policy 中把 Principal 改成 `"*"`，以排除 Principal 寫錯的可能

>
> **C ✗** 物件是用 prod 帳號的 key 加密的，analytics 帳號自己的 key 無法解密這些物件。
>
> **D ✗** 把 Principal 改成 `"*"` 會擴大授權範圍，而且問題不在 S3 權限，而在 KMS 權限。
>
> **考點**：SAP-2.3、SAA-1.3｜跨帳號 SSE-KMS 的 key policy

Wanderly 的平台團隊在 shared services 帳號維護 `wanderly-golden-artifacts` bucket，存放所有帳號部署時需要的套件。組織目前有 60 個帳號，每月還會新增數個帳號。目前 bucket policy 逐一列出每個帳號，新帳號常常因為被漏加而部署失敗。資安團隊要求只有組織內的身份能讀取，離開組織的帳號要自動失去存取權。

- A. 在 Principal 中逐一列出所有帳號 ID，並用 EventBridge 偵測新帳號後由 Lambda 自動更新 bucket policy

### 練習 13-15｜SAP｜單選｜追溯共用 role 背後的真人

Wanderly 的維運人員透過企業 SAML IdP 登入 security 帳號的 `ops-entry` role，再扮演各帳號的 `ops-admin` role 處理事故。稽核發現，CloudTrail 中只看得到 `assumed-role/ops-admin/<session name>`，而 session name 是由使用者自行輸入，無法可靠證明是誰執行了某個刪除操作。稽核要求每個操作都能可靠追溯到員工本人，即使經過多次 role 扮演也一樣。

最合適的做法是什麼？

- A. 由 IdP 在 SAML assertion 中帶入員工帳號作為 source identity，並在 `ops-entry` 與各 `ops-admin` role 的 trust policy 允許 `sts:SetSourceIdentity`、要求必須帶有 source identity
- B. 要求每位員工把 session name 設成自己的 email，並定期抽查
- C. 為每位維運人員在每個帳號建立個人 IAM user，取代 role 扮演
- D. 在 `ops-admin` 的 permissions policy 加上 `aws:username` 條件，只允許特定使用者名稱

> [!answer]- 答案：A
> **A ✓** Source identity 由 IdP 在第一次扮演時設定，之後在整條 role chaining 中保留且不能被使用者修改，CloudTrail 會記錄它，因此能可靠追溯到員工本人。Trust policy 要求必須帶有 source identity，可以避免有人繞過這個機制。
>
> **B ✗** Session name 由呼叫者決定，可以任意填寫，抽查無法提供可靠的稽核證據。
>
> **C ✗** 個人 IAM user 能追溯，但會在每個帳號產生大量長期憑證，違反集中身份管理與最小化長期憑證的原則。
>
> **D ✗** 聯合登入扮演 role 時，請求並不是由 IAM user 發出，`aws:username` 不會是員工帳號，這個條件無法達成追溯目的。
>
> **考點**：SAP-1.2、SAP-3.2｜source identity 與稽核追溯

### 練習 13-16｜SAP｜選兩項｜Identity Center 的委派管理

Wanderly 的 IAM Identity Center 啟用在 Organizations 的 management account，目前身份團隊每天都要登入 management account 來新增 permission set 與指派帳號。資安團隊希望大幅減少使用 management account 的次數，同時確保成員帳號的管理員無法藉此取得 management account 的權限。

哪兩個做法最合適？（選兩項）

- A. 刪除目前的 Identity Center，改在某個成員帳號重新啟用一個新的 organization instance
- B. 讓身份團隊改用 management account 的 root user 管理 Identity Center，以避免建立額外身份
- C. 把專門的 identity 帳號註冊為 Identity Center 的 delegated administrator，日常的 permission set 與成員帳號指派都在該帳號進行
- D. 授權 delegated administrator 管理指派到 management account 的 permission set，讓所有工作都能在成員帳號完成
- E. 指派到 management account 的 permission set 仍在 management account 中管理，並嚴格限制能進入 management account 的群組與權限

> [!answer]- 答案：C、E
> **A ✗** 刪除並重建 Identity Center 會中斷所有員工的存取並需要重新設定全部指派，風險高；organization instance 也必須由 management account 啟用並可委派，不需要重建。
>
> **B ✗** 使用 root user 做日常管理違反 root user 的使用原則，也無法減少對 management account 的依賴。
>
> **C ✓** Delegated administrator 讓身份團隊在專用成員帳號處理大多數日常工作，例如建立 permission set、指派成員帳號，不需要登入 management account。
>
> **D ✗** Delegated administrator 無法管理指派到 management account 的 permission set，這是刻意的限制，避免成員帳號的管理員取得 management account 的權限。
>
