# 第 16 章　邊界防護與威脅偵測：WAF、Shield、GuardDuty 與安全稽核

> [!abstract] 本章地圖
> **你會學到**：
> - 說清楚 security group、NACL、Network Firewall、WAF、Shield 各自看得到哪一層的流量，並為一個 web 系統設計分層防護
> - 用 WAF 的 managed rules 與 rate-based rules 擋下 SQL injection、credential stuffing 與爬蟲，並知道 WAF 能掛在哪些資源上
> - 分辨 Shield Standard 與 Shield Advanced，判斷什麼情況值得付費
> - 對照 GuardDuty、Inspector、Macie、Detective、Security Hub 的分工，選出題目要的那一個
> - 用 CloudTrail、AWS Config、Object Lock 建立「事後查得到、證據改不了」的稽核基礎，並把偵測結果接成自動回應
>
> **前置知識**：第 6 章（security group 與 NACL）、第 10 章（ALB）、第 11 章（CloudFront）、第 12 章（IAM policy）
> **考試比重**：SAA ★★★（Domain 1 安全設計）｜SAP ★★★（Domain 1 安全控制、Domain 3 改善既有系統的安全性）

## 16.1 故事：Wanderly 最漫長的一個週末

Wanderly 的暑假促銷在週五晚上八點開跑。九點左右，客服開始收到會員抱怨「帳號被登入、點數被換走」。工程師小林查 ALB 的 log，發現 `/api/login` 每秒收到上千次請求，來源 IP 分散在幾百個雲端主機上，帳號密碼組合看起來是從別家網站外洩的名單。這種攻擊叫 **credential stuffing（撞庫）**：攻擊者不需要破解你的系統，只要拿別處外洩的帳密來你這裡一個一個試。

同一時間，搜尋 API 的流量也暴增三倍。仔細一看，大部分不是真人，而是競爭對手的爬蟲在抓房價。週六清晨，帳單警報又響了：一把開發人員不小心推到公開 Git repository 的 access key，被人拿去在 `us-west-2` 開了 40 台 GPU instance 挖礦。那個 Region Wanderly 從來沒用過，所以根本沒人在看。

週一，金流合作夥伴寄來一封信：因為發生會員帳號盜用事件，他們要求 Wanderly 在兩週內提供「誰在什麼時間改過哪些安全設定」的紀錄，以及「交易紀錄沒有被竄改」的證明。小林這才發現，CloudTrail 只有 console 預設的 90 天事件歷史，沒有任何人能證明 log 沒被動過。

這個週末暴露了三種不同的問題：**擋不住**（攻擊流量直達應用程式）、**看不見**（陌生 Region 的異常活動沒人發現）、**證明不了**（事後拿不出可信的紀錄）。本章就依序處理這三件事：先在邊界建立分層防護，再用受管偵測服務找出異常，最後建立稽核與保存機制，並把偵測接成自動回應。

## 16.2 分層防禦：每一層看得到不同的東西

在挑服務之前，要先理解一個核心觀念：**每一種防護工具只看得到封包的某些部分。** 第 6 章的 security group 只看「來源 IP、目的 port、協定」，它完全不知道 HTTP 請求裡寫了什麼，所以不可能擋 SQL injection。反過來，WAF 能讀懂 HTTP，卻管不到資料庫的 3306 port。

這種「把多種控制疊在一起，任何一層失守還有下一層」的做法叫 **defense in depth（縱深防禦）**。Wanderly 的分層長這樣：

```text
           使用者 / 攻擊者
                 │
   ① Route 53 / CloudFront（edge location，Shield Standard 自動保護）
                 │   ← ② WAF web ACL：檢查 HTTP 內容、速率、來源國家
                 ▼
  ┌──────────────────── VPC ───────────────────────────┐
  │  ③ NACL（subnet 邊界，stateless，L3/L4）            │
  │        │                                           │
  │     [ALB] ← ④ security group：只允許 CloudFront     │
  │        │                                           │
  │     [App EC2] ← security group：只允許 ALB 的 SG    │
  │        │  主動連出                                  │
  │        ▼                                           │
  │  ⑤ Network Firewall endpoint：網域白名單、IPS 規則  │
  │        ▼                                           │
  │     [NAT Gateway] → IGW → Internet                 │
  └────────────────────────────────────────────────────┘
   ⑥ 偵測層（不擋流量，只觀察與告警）：
      GuardDuty、Inspector、Macie、Security Hub、CloudTrail、Config
```

① 流量先到 AWS 的邊緣網路。DNS 查詢由 Route 53 回答，HTTP 請求由 CloudFront 接住；這裡自動有 Shield Standard 吸收常見的網路層 DDoS。② WAF 掛在 CloudFront 上，在請求被轉到 origin 之前，先檢查內容與速率。③ 進入 VPC 後，NACL 在 subnet 邊界做粗略的 IP 與 port 過濾。④ Security group 在每個 ENI 上做精細的允許規則。⑤ 應用程式主動連到 Internet 時，Network Firewall 檢查目的網域與流量特徵。⑥ 偵測層不在流量路徑上，它們分析 log 與設定，負責「發現」而不是「阻擋」。

| 控制 | 位置 | 看得到什麼 | 擋不了什麼 |
|---|---|---|---|
| Security group | ENI | 來源／目的 IP、port、協定、其他 SG | HTTP 內容、網域名稱、deny 規則 |
| NACL | Subnet | IP、port、協定（可 deny） | 連線狀態、HTTP 內容 |
| Network Firewall | VPC 內的 firewall endpoint | L3–L7：五元組、網域（SNI／Host）、Suricata 特徵 | 未經過它路由的流量 |
| WAF | CloudFront、ALB、API Gateway 等 | HTTP 方法、路徑、header、body、query、來源國家、請求速率 | 非 HTTP 流量、未掛 WAF 的入口 |
| Shield | AWS 邊緣與受保護資源 | 流量模式（DDoS） | 應用程式邏輯漏洞 |

記住這張表，考試的大部分「選哪個防護服務」題目都能用「它看得到題目描述的那個東西嗎？」來刪去。接下來從最外層、也是 Wanderly 週五晚上最痛的地方開始：HTTP 層的攻擊。

## 16.3 AWS WAF：逐一檢查每個 HTTP 請求

**AWS WAF（Web Application Firewall，網頁應用程式防火牆）** 是一個受管的 L7 防火牆：它在請求到達你的應用程式之前，依照你寫的規則檢查請求內容，決定放行、阻擋或要求驗證。它不是一台你要部署的機器，而是「附加」在 CloudFront、ALB 等入口上的一組規則。

### Web ACL、rule 與 action

WAF 的設定單位是 **web ACL（web access control list）**，裡面依序放著多條 **rule**。每條 rule 有：

- **Statement**：比對條件，例如「URI 路徑以 `/api/login` 開頭」「來源國家是某些國家」「body 內含 SQL injection 特徵」。
- **Action**：符合時做什麼。`Allow`（放行）、`Block`（阻擋，可回自訂的回應碼與內容）、`Count`（只計數、不阻擋）、`CAPTCHA`（要求使用者解驗證題）、`Challenge`（在背景用瀏覽器挑戰驗證是不是真瀏覽器，使用者通常無感）。
- **Priority**：數字越小越先評估。

評估方式是：**依 priority 由小到大逐條比對，遇到第一條符合且 action 是終止型（Allow、Block，或尚未通過的 CAPTCHA／Challenge）的 rule 就停止**；`Count` 不會終止，只會記錄並繼續往下。若所有 rule 都沒有終止，就套用 web ACL 的 **default action**（Allow 或 Block）。

> [!warning] 常見誤解
> 「把最嚴格的規則放最後比較安全。」順序其實非常重要：如果 priority 1 是「Allow 公司辦公室 IP」，後面的 SQL injection 規則就永遠不會檢查來自辦公室的請求。另外，WAF 的規則不是「最精確的獲勝」或「投票制」，而是「第一個終止的獲勝」。

每條 rule 會消耗 **WCU（web ACL capacity unit）**，複雜的比對（例如 regex、檢查 body）消耗較多。每個 web ACL 有 WCU 上限，超過基本額度會額外收費。考試很少考數字，只要知道「規則越複雜越占容量」即可。

### WAF 能掛在哪裡？

這是考試最愛的考點之一。Web ACL 可以關聯（associate）到：

- **Amazon CloudFront distribution**
- **Application Load Balancer**
- **Amazon API Gateway REST API**（HTTP API 不支援直接掛 WAF）
- **AWS AppSync GraphQL API**
- **Amazon Cognito user pool**
- AWS App Runner service、AWS Verified Access instance、AWS Amplify 等

**不能**掛在 Network Load Balancer、EC2 instance、Classic Load Balancer 或 security group 上。題目若說「API 在 NLB 後面，要擋 SQL injection」，答案通常是在前面加 CloudFront 或改用 ALB，再掛 WAF。

範圍也要注意：給 CloudFront 用的 web ACL 是 **global** 範圍，用 API／CLI 建立時要在 `us-east-1` 以 `CLOUDFRONT` scope 建立；給 ALB、API Gateway 用的是 **regional** web ACL，必須和資源在同一個 Region。

### Managed rule groups：不必自己寫規則

自己寫 SQL injection 規則既困難又容易漏。WAF 提供 **managed rule groups**，由 AWS 或 AWS Marketplace 廠商維護、持續更新：

| Rule group | 用途 |
|---|---|
| Core rule set（CRS） | OWASP Top 10 常見攻擊的通用防護 |
| Known bad inputs | 已知惡意模式，例如 Log4j 漏洞利用字串 |
| SQL database | SQL injection |
| Amazon IP reputation list | AWS 威脅情報中的惡意來源 IP |
| Anonymous IP list | VPN、Tor、代理與雲端主機來源 |
| Bot Control | 辨識並分類爬蟲與自動化程式（付費） |
| Account takeover prevention（ATP） | 偵測登入頁的撞庫與暴力破解（付費） |
| Account creation fraud prevention（ACFP） | 偵測假帳號大量註冊（付費） |

Managed rule group 可以整組加入 web ACL，也可以把其中個別規則改成 `Count`，避免誤擋正常流量。

### Rate-based rules：限制同一來源的請求速率

撞庫攻擊的特徵是「同一個來源在短時間內送大量登入請求」。**Rate-based rule** 會在一個評估時間窗內（預設 5 分鐘，也可設 1、2 或 10 分鐘），依照 **aggregation key**（預設是來源 IP，也可以是 `X-Forwarded-For` 這類 header 中的 IP，或自訂的 header、cookie、query 參數組合）計算請求數；超過門檻的來源會被套用 action，直到速率降回門檻以下。

搭配 **scope-down statement**，可以只計算特定路徑。Wanderly 對登入 API 的規則如下：

```json
{
  "Name": "login-rate-limit",
  "Priority": 10,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 100,
      "EvaluationWindowSec": 300,
      "AggregateKeyType": "IP",
      "ScopeDownStatement": {
        "ByteMatchStatement": {
          "SearchString": "/api/login",
          "FieldToMatch": { "UriPath": {} },
          "TextTransformations": [{ "Priority": 0, "Type": "NONE" }],
          "PositionalConstraint": "STARTS_WITH"
        }
      }
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "login-rate-limit"
  }
}
```

這條規則的意思是：同一個來源 IP 在 5 分鐘內對 `/api/login` 送超過 100 次請求，就被暫時阻擋。其他路徑不受影響，所以正常瀏覽搜尋頁的使用者不會被誤傷。

> [!warning] 常見誤解
> WAF 掛在 CloudFront 後面的 ALB 上時，ALB 看到的來源 IP 是 CloudFront 節點，不是使用者。這時 rate-based rule 若用預設的來源 IP 計算，等於把成千上萬個使用者合併計數。正確做法是把 WAF 掛在 CloudFront 上（看得到真實來源），或在 ALB 上改用 forwarded IP 作為 key，並確認這個 header 只能由受信任的 proxy 設定。

攻擊者若把流量分散到幾千個 IP，每個 IP 都低於門檻，rate-based rule 就抓不到。這時要靠 IP reputation list、Anonymous IP list 擋掉雲端主機來源，或用 ATP 這類專門分析登入行為的 managed rule group。

### 其他常用比對條件

- **Geo match**：依來源國家放行或阻擋。也可以搭配 CloudFront 的 geo restriction（第 11 章），差別是 WAF 能和其他條件組合（例如「某國家且路徑是 `/admin`」）。
- **IP set**：自己維護的 IP 清單，例如合作夥伴或已知攻擊者。
- **Regex pattern set**、**size constraint**：比對特定格式或限制請求大小。
- **Labels**：一條 rule 可以替請求貼上 label（例如 Bot Control 貼上 `bot:category:search_engine`），後面的 rule 再依 label 決定動作，用來組合複雜邏輯。

WAF 檢查 request body 有大小上限：ALB 與 AppSync 固定只檢查前 8 KB；CloudFront、API Gateway 等預設 16 KB，可提高到 64 KB（另外收費）。超過的部分由 **oversize handling** 設定決定要視為符合、不符合，或繼續處理。題目若提到「攻擊把惡意內容放在大型 body 的後段」，就是在考這個限制。

### 上線方式與 log

新規則不要直接上 `Block`。標準流程是：先設為 `Count` 觀察一到兩週，用 log 確認沒有誤擋正常流量，再改成 `Block`。WAF 的 **logging** 可以送到 CloudWatch Logs（log group 名稱必須以 `aws-waf-logs-` 開頭）、S3 或 Data Firehose，內容包含每個請求符合了哪些 rule。另外，每條 rule 也會產生 CloudWatch metrics，可以設定警報。

小林在週五晚上做的事情就是：把 web ACL 掛到 CloudFront，加入 Core rule set、SQL database、IP reputation list，再加上 `/api/login` 的 rate-based rule 與搜尋 API 的 Bot Control。二十分鐘內，登入請求量降回平常水準。

## 16.4 DDoS 與 AWS Shield

WAF 解決的是「惡意內容」與「單一來源太快」，但還有一種攻擊根本不在乎內容：**DDoS（Distributed Denial of Service，分散式阻斷服務攻擊）**，也就是用大量來源同時送流量，把你的頻寬、連線數或伺服器資源塞爆，讓正常使用者進不來。

### DDoS 的三種類型

| 類型 | 層級 | 例子 | 主要防護 |
|---|---|---|---|
| 容量型（volumetric） | L3 | UDP reflection、DNS／NTP 放大攻擊，用巨量封包塞滿頻寬 | AWS 邊緣網路吸收、Shield |
| 協定型（protocol） | L4 | SYN flood，耗盡連線狀態表 | Shield、ELB／CloudFront 只接受完整連線 |
| 應用層（application） | L7 | HTTP flood，大量看似正常的 GET 請求 | WAF rate-based rule、CloudFront 快取、Shield Advanced 自動緩解 |

### Shield Standard：所有人都有、免費、自動

**AWS Shield Standard** 自動保護所有 AWS 客戶，不用啟用、不額外收費。它在 AWS 邊緣網路與 Region 邊界偵測並緩解最常見的 L3／L4 攻擊（例如 SYN flood、UDP reflection）。使用 CloudFront 與 Route 53 時，因為流量在全球數百個邊緣節點就被分散處理，得到的保護效果最好。

### Shield Advanced：付費的 DDoS 保險加專業團隊

**AWS Shield Advanced** 是付費服務（以組織為單位按月計費，需一年承諾，另有資料傳輸費用），只保護你明確指定的資源：CloudFront distribution、Route 53 hosted zone、Global Accelerator standard accelerator、ALB、Classic Load Balancer，以及 Elastic IP。EC2 instance 與 NLB 不能直接加入保護，要透過保護它們關聯的 Elastic IP 間接受保護。它比 Standard 多出：

1. **更進階的偵測與緩解**：針對你的資源建立流量基準，偵測更小、更複雜的攻擊，並提供即時攻擊可視性與報告。
2. **Shield Response Team（SRT，早期稱 DRT）**：AWS 的 DDoS 專家 24 小時支援，可以在攻擊期間協助分析並替你寫 WAF 規則。使用 SRT 需要 Business 或 Enterprise 等級的 AWS Support。
3. **DDoS cost protection**：攻擊造成 CloudFront、ELB、Route 53、EC2、Global Accelerator 用量暴增時，可申請服務抵免（credit），避免被攻擊還要付高額帳單。
4. **自動應用層 DDoS 緩解**：資源已關聯 WAF web ACL 時，Shield Advanced 可以在偵測到 L7 攻擊時自動建立並部署 WAF 規則。
5. **Proactive engagement**：把資源關聯 Route 53 health check 後，Shield 能用應用程式健康狀態輔助判斷攻擊，並在健康狀態受影響時由 SRT 主動聯絡你。
6. 受 Shield Advanced 保護的資源，其基本 WAF 用量（web ACL、規則與請求費用）不另外收費；Bot Control、ATP 這類進階付費 managed rule group 是否也包含在內，要以當時的價格頁為準。

> [!tip] 考試提示
> 看到「DDoS 期間的費用暴增要獲得補償」「需要 24/7 DDoS 專家支援」「需要攻擊的即時可視性」，答案就是 Shield Advanced。只說「防護常見 DDoS」而且要求最低成本，答案是 Shield Standard 已經內建，不需額外購買。

### 本身就耐打的架構

Shield 再強，也要架構配合。AWS 建議的 DDoS 韌性架構有幾個原則：

- **把入口放在邊緣**：使用 CloudFront、Route 53、Global Accelerator，讓攻擊流量在全球邊緣節點被分散吸收，不直接打到 Region 內的資源。
- **減少攻擊面**：後端放 private subnet、只開必要 port，不讓 EC2 直接有 public IP。
- **保護 origin 不被繞過**：攻擊者若知道 ALB 的 DNS 名稱，可以跳過 CloudFront 直接打 ALB。做法是 ALB 的 security group 只允許 CloudFront 的 **AWS managed prefix list**（`com.amazonaws.global.cloudfront.origin-facing`），並由 CloudFront 加上一個秘密 custom header、ALB listener rule 驗證它；或使用 CloudFront **VPC origins** 讓 ALB 完全不必是 internet-facing（第 11 章）。
- **可擴展**：ALB + Auto Scaling（第 18 章）在應用層攻擊期間能撐更久，搭配快取讓大部分請求根本不到 origin。

## 16.5 Firewall Manager：讓 50 個帳號套用同一套規則

Wanderly 只有一個帳號時，在 console 設定 WAF 就夠了。但到了企業期（第 40 章），公司有幾十個帳號、每個帳號都有自己的 ALB 與 CloudFront，總會有某個團隊忘了掛 WAF。**AWS Firewall Manager** 就是用來解決「規模化的一致性」：在一個地方定義安全政策，自動套用到整個 Organization。

### 前提與運作方式

1. 帳號必須在 **AWS Organizations** 中（啟用 all features）。
2. 指定一個 **Firewall Manager administrator account**（通常是安全帳號，不要用 management account）。
3. 各成員帳號與 Region 必須啟用 **AWS Config**，因為 Firewall Manager 靠 Config 發現資源與判斷合規。

接著建立 **policy**，指定範圍（全部帳號、特定 OU、特定 tag 的資源）與內容。Firewall Manager 會持續檢查範圍內的資源：新帳號加入、新 ALB 建立時自動套用；你可以選擇只回報不合規（identify），或自動修正（auto remediate）。

### 能管的政策類型

| Policy 類型 | 做什麼 |
|---|---|
| AWS WAF | 讓範圍內的 ALB、CloudFront、API Gateway 都關聯一組必備的 rule groups；帳號自己的規則可夾在中間 |
| Shield Advanced | 自動把資源加入 Shield Advanced 保護 |
| Security group | 套用共同 SG、稽核過寬的規則（例如 `0.0.0.0/0` 的 SSH）、找出未使用的 SG |
| Network Firewall | 在範圍內的 VPC 部署 firewall 與規則 |
| Route 53 Resolver DNS Firewall | 統一套用 DNS 網域過濾規則 |
| NACL、第三方防火牆 | 統一 NACL 規則，或管理 Marketplace 防火牆 |

WAF policy 的設計很實用：中央安全團隊定義「最先評估」與「最後評估」的 rule groups（例如最先檢查 IP reputation、最後是 Core rule set），各帳號的團隊仍可在中間加自己的業務規則，但不能移除中央規則。

> [!warning] 常見誤解
> Firewall Manager 本身不是防火牆，它不檢查任何流量，只是「替你在各帳號部署與稽核」WAF、SG、Network Firewall 等設定。另外，用 SCP 禁止刪除 web ACL 只能防止被刪，不能讓新資源自動掛上 web ACL，兩者解決的問題不同。

## 16.6 AWS Network Firewall：VPC 裡的網路防火牆

WAF 只處理進入 web 入口的 HTTP 請求。週末事件的另一個教訓是：如果某台 EC2 被植入惡意程式，它會主動連到攻擊者的 C2（command and control，指揮控制）伺服器，或把資料傳到外部。Security group 的出站規則只能寫 IP 與 port，攻擊者的伺服器 IP 天天換；NAT Gateway 則完全不過濾。Wanderly 需要的是：**應用程式只能連到少數允許的網域，其他一律擋掉，並能偵測已知的惡意流量特徵。**

**AWS Network Firewall** 是受管的、有狀態的網路防火牆與 **IPS（Intrusion Prevention System，入侵防禦系統）**，部署在 VPC 裡，能檢查進出 VPC 以及 VPC 之間的流量。

### 架構：靠路由把流量導進 firewall endpoint

Network Firewall 不像 security group 那樣「套在資源上」。你在每個 AZ 建一個專用的 **firewall subnet**，AWS 會在裡面建立 **firewall endpoint**，然後**修改 route table，讓要檢查的流量經過這個 endpoint**。沒經過它的流量，它就看不到。

Wanderly 的出站檢查架構（單一 AZ 示意）：

```text
 [App EC2 10.20.16.25]   app subnet
     │ ① app RT：0.0.0.0/0 → firewall endpoint (vpce-fw-a)
     ▼
 [Firewall endpoint]      firewall subnet
     │ ② 檢查：目的網域在允許清單？符合 IPS 特徵？
     │    firewall RT：0.0.0.0/0 → nat-a
     ▼
 [NAT Gateway nat-a]      public subnet
     │ ③ public RT：0.0.0.0/0 → IGW
     │              10.20.16.0/20 → vpce-fw-a（回程也要過防火牆）
     ▼
 [Internet Gateway] → Internet
```

① 應用程式 subnet 的 default route 改指向同一個 AZ 的 firewall endpoint。② Firewall 依規則決定放行或丟棄；放行的流量依 firewall subnet 的 route table 送往 NAT Gateway。③ NAT Gateway 所在的 public subnet route table 除了往 IGW 的 default route，還必須有一條「回到 app subnet 的流量先經過 firewall endpoint」的 route，讓去程與回程都經過同一個 endpoint。

這就是 Network Firewall 最重要的設計原則：**路由必須對稱**。Stateful 檢查需要看到同一條連線的雙向封包；若回程繞過 firewall 或走到另一個 AZ 的 endpoint，連線會被丟棄。也因此每個 AZ 都要有自己的 firewall endpoint，並讓同 AZ 的流量走同 AZ 的 endpoint（和 NAT Gateway 的原則一樣）。若要檢查從 Internet 進來的流量，則要在 IGW 上關聯一張 **ingress route table（edge association）**，把往 public subnet 的流量先導向 firewall endpoint。

### 規則引擎：stateless 先、stateful 後

Network Firewall 的 **firewall policy** 包含兩種 rule group：

1. **Stateless rule group**：逐一封包比對五元組（來源／目的 IP、來源／目的 port、協定），不記得連線狀態，依 priority 評估。動作是 pass（直接放行）、drop（丟棄）或 **forward to stateful**（交給 stateful 引擎）。通常只用來快速丟棄明確的惡意流量，其餘一律 forward。
2. **Stateful rule group**：追蹤連線狀態，能做更深的檢查：
   - **Domain list**：依 TLS 的 **SNI（Server Name Indication，用戶端在 TLS 握手時送出的目標主機名稱）** 或 HTTP 的 Host header 比對網域，做允許清單或拒絕清單，例如只允許 `.amazonaws.com` 與 `api.payment-partner.com`。
   - **五元組標準規則**：有狀態版本的 IP／port 規則。
   - **Suricata 相容規則**：Suricata 是開源 IPS 的規則語法，可以寫入侵特徵、協定偵測等進階規則，也能使用 AWS managed threat signatures。

Stateful 規則的評估順序建議使用 **strict order**（依你設定的優先順序），而非舊的 action order。若要檢查 HTTPS 內容本身（不只是 SNI），可以啟用 **TLS inspection**：firewall 解密、檢查、再加密，需要在 ACM 準備憑證，並讓用戶端信任對應的 CA。

Log 分為 flow log、alert log 與 TLS log，可送到 S3、CloudWatch Logs 或 Data Firehose。

### 集中式部署與 DNS Firewall

每個 VPC 都部署 Network Firewall 費用不低（按 endpoint 小時與處理量收費）。企業常見做法是建立一個集中 **inspection VPC**，所有 VPC 經 Transit Gateway 把流量送過去檢查；這時要在 TGW 的 inspection VPC attachment 上啟用 **appliance mode**，確保同一條連線雙向都送到同一個 AZ 的 firewall（第 7、41 章）。Network Firewall 現在也能以 **transit gateway attachment** 的形式直接掛到 Transit Gateway 上（transit gateway-attached firewall），不必自己建 inspection VPC 與 firewall subnet，能減少路由設定；考題中的經典架構仍以 inspection VPC + appliance mode 為主。

另一個較輕量的出站控制是 **Route 53 Resolver DNS Firewall**：在 VPC 的 DNS 解析層擋掉惡意或不允許的網域（例如已知的惡意網域清單）。它便宜、設定簡單，但只要攻擊者的程式直接用 IP 連線、不經 DNS，就繞得過去，所以常與 Network Firewall 一起使用。

| 比較 | Security group | NACL | Network Firewall | DNS Firewall | WAF |
|---|---|---|---|---|---|
| 狀態 | Stateful | Stateless | 兩者皆有 | 不適用（DNS 查詢） | 不適用（HTTP 請求） |
| 網域過濾 | 不行 | 不行 | 可以（SNI／Host） | 可以（DNS 名稱） | 可比對 Host header |
| IPS 特徵 | 不行 | 不行 | 可以（Suricata） | 不行 | HTTP 攻擊特徵 |
| Deny 規則 | 不行 | 可以 | 可以 | 可以 | 可以 |
| 部署方式 | 套在 ENI | 套在 subnet | 改路由經過 endpoint | 關聯 VPC | 關聯 web 入口 |

到這裡，「擋不住」的問題已經處理完：HTTP 層有 WAF、DDoS 有 Shield、網路層出站有 Network Firewall，Firewall Manager 讓這一切在多帳號下保持一致。但再好的防護也會漏，週六清晨那把外洩的 access key 就完全不經過任何防火牆。接下來要處理「看不見」的問題。

## 16.7 GuardDuty：持續分析異常行為的偵測服務

**Amazon GuardDuty** 是受管的 **威脅偵測（threat detection）** 服務：它持續分析 AWS 帳號裡的活動紀錄，用威脅情報、異常偵測與機器學習找出可疑行為，產生 **finding（發現）**。它不在流量路徑上，不會阻擋任何東西，只負責「發現並告訴你」。

### 它看哪些資料？

啟用 GuardDuty 後，它會自動分析以下 **foundational data sources（基礎資料來源）**：

- **CloudTrail management events**：例如有人從陌生國家用 root 登入、突然在從未使用的 Region 大量 `RunInstances`、關閉 CloudTrail。
- **VPC Flow Logs**：例如 EC2 對外連到已知的挖礦池或 C2 伺服器、進行 port scan。
- **Route 53 Resolver DNS query logs**：例如 EC2 查詢已知惡意網域、用 DNS 夾帶資料外洩。

重點是：**GuardDuty 直接從 AWS 內部取得這些資料流，你不需要自己啟用 VPC Flow Logs 或 DNS query logging，也不需要部署 agent。** 它也不會替你保存這些 log；你若需要自己查詢，仍要另外設定 trail 與 flow logs。

除了基礎來源，GuardDuty 還有可選的 **protection plans**，針對特定資源做更深的偵測：

| Protection plan | 分析什麼 |
|---|---|
| S3 Protection | S3 data events，偵測可疑的物件存取（例如從惡意 IP 大量 `GetObject`） |
| EKS Protection | EKS audit logs，偵測可疑的 Kubernetes API 操作 |
| Runtime Monitoring | 透過 agent 觀察 EC2、ECS（含 Fargate）、EKS 上的作業系統層活動，例如可疑程序、檔案存取 |
| Malware Protection for EC2 | 偵測到可疑行為時，對 EBS volume 做無 agent 的惡意程式掃描 |
| Malware Protection for S3 | 掃描新上傳到指定 bucket 的物件 |
| RDS Protection | 分析 Aurora／RDS 的登入活動，偵測暴力破解或異常登入 |
| Lambda Protection | 分析 Lambda 的網路活動，例如連到挖礦池 |

GuardDuty 也會把多個相關的 finding 串成一個 **attack sequence**（Extended Threat Detection），例如「access key 外洩 → 從陌生 IP 列出 S3 → 大量下載」，讓你看到整個攻擊鏈而不是零散的告警。

### 使用重點

- **它是 Regional 服務。** 要在每個 Region 都啟用，包括你「沒在用」的 Region。Wanderly 的挖礦事件就發生在沒人用的 `us-west-2`；若只在東京啟用 GuardDuty，這件事照樣看不見。
- **多帳號**：在 Organizations 中指定 **delegated administrator**（通常是安全帳號），開啟 auto-enable，新帳號加入時自動啟用。
- **Trusted IP list 與 threat list**：前者是你信任的 IP（例如公司的弱點掃描器），不會對它產生部分 finding；後者是你自己的惡意 IP 清單。
- **Suppression rules**：把確認無害的 finding 類型自動封存，降低雜訊，但要謹慎設定範圍。
- **輸出**：每個 finding 都會送到 **Amazon EventBridge**，可觸發 Lambda、Step Functions 或 SSM Automation 做自動回應（16.14 節），也會送到 Security Hub。
- 新帳號有 30 天免費試用，可以先估算費用。

> [!tip] 考試提示
> 題目出現「偵測被入侵的 EC2 在挖礦」「偵測異常 API 呼叫或外洩的 credentials」「最少營運負擔的威脅偵測」，幾乎都是 GuardDuty。選項若是「啟用 VPC Flow Logs 再寫 Lambda 分析」，通常是營運負擔較大的錯誤答案。

## 16.8 Inspector 與 Macie：找弱點、找敏感資料

GuardDuty 回答的是「現在有沒有人在做壞事」。但還有兩個問題同樣重要：「我的系統有沒有已知的漏洞，讓壞人有機會進來？」以及「我的敏感資料放在哪裡、有沒有暴露？」

### Amazon Inspector：持續的弱點管理

**Amazon Inspector** 是自動化的 **弱點管理（vulnerability management）** 服務，持續掃描 workload 是否有已知的軟體漏洞（**CVE，Common Vulnerabilities and Exposures**，公開的漏洞編號）以及不該有的網路暴露：

- **EC2 instance**：透過 SSM Agent 盤點作業系統套件（agent-based），或用 EBS snapshot 做無 agent 掃描（agentless）；也會分析 **network reachability**，例如「這台機器的 22 port 從 Internet 可達」。
- **ECR container image**：映像推送時掃描，之後在新 CVE 公布時自動重新評估。
- **Lambda function**：掃描函式的套件相依性，也可以啟用程式碼掃描，找出程式碼中的注入漏洞或寫死的 credentials。

Inspector 的關鍵字是 **「持續」與「自動」**：有新的 CVE 公布時，它會自動重新評估已盤點的資源，不需要你排程。每個 finding 有 **Inspector risk score**，會結合 CVE 嚴重度與實際網路暴露程度調整。Finding 同樣送到 EventBridge 與 Security Hub。

> [!warning] 常見誤解
> Inspector 找出漏洞，但不會替你修補。修補要靠 SSM Patch Manager（第 38 章）或重建映像。另外，「掃描過一次 golden AMI」不代表之後啟動的機器安全，因為新的 CVE 每天都在出現，這正是持續掃描的意義。

### Amazon Macie：S3 裡的敏感資料偵測

**Amazon Macie** 用機器學習與比對規則，找出 **S3 裡的敏感資料**，例如姓名、身分證字號、信用卡號、護照號碼、API key 等 **PII（Personally Identifiable Information，個人可識別資訊）** 與 credentials。它也會評估 bucket 層級的安全狀態，例如 bucket 是否公開、是否未加密、是否被分享給其他帳號。

- **Automated sensitive data discovery**：持續以抽樣方式掃描整個帳號的 S3，產生「哪些 bucket 可能有敏感資料」的地圖，成本較低。
- **Sensitive data discovery jobs**：針對指定 bucket 做完整或排程掃描。
- **Managed data identifiers**：內建的敏感資料類型；**custom data identifiers**：自己用 regex 與關鍵字定義，例如 Wanderly 的會員編號格式；**allow lists**：排除已知不敏感的字串，例如測試用的假卡號。

Macie **只掃描 S3**。題目若說「找出 RDS 資料表或 EBS 裡的個資」，Macie 不是答案（常見做法是把資料匯出到 S3 再掃，或使用資料庫本身的工具）。

## 16.9 Detective 與 Security Hub：調查與彙整

當偵測服務一多，新問題又來了：一個事件可能同時產生 GuardDuty、Inspector、Macie 的 finding，散落在幾十個帳號和多個 Region。安全團隊需要「一個地方看全部」以及「快速調查一個 finding 的來龍去脈」。

### Amazon Detective：調查用的關聯圖

**Amazon Detective** 自動從 CloudTrail、VPC Flow Logs、GuardDuty findings（以及可選的 EKS audit logs 等）建立 **behavior graph（行為圖）**，把 IAM principal、IP、EC2、角色之間的互動關係整理成可視化的時間軸。當 GuardDuty 回報「某個 role 從陌生 IP 呼叫 API」，分析師可以在 Detective 中直接看到：這個 IP 過去還碰過哪些資源？這個 role 平常的行為基準是什麼？同一時間還有哪些相關 finding（finding groups）？

Detective 是**調查工具**，它不會偵測新的威脅、也不會自動隔離或修補。要使用 Detective，帳號需要先啟用 GuardDuty。

### AWS Security Hub：彙整、標準檢查與優先排序

這裡要先說明名稱的變化，因為不同年份的教材寫法不同：

- 長期以來的 **AWS Security Hub**（2025 年起改名為 **AWS Security Hub CSPM**）有兩個核心功能。一是 **CSPM（Cloud Security Posture Management，雲端安全態勢管理）**：依照 **security standards** 自動檢查帳號設定，例如 AWS Foundational Security Best Practices、CIS AWS Foundations Benchmark、PCI DSS、NIST SP 800-53，每個標準由許多 **controls** 組成，例如「S3 bucket 應封鎖公開存取」「CloudTrail 應啟用 log file validation」。這些檢查大多透過 AWS Config 規則執行，所以**必須先啟用 AWS Config**。二是**彙整 findings**：把 GuardDuty、Inspector、Macie、Firewall Manager、IAM Access Analyzer 以及第三方產品的 findings，轉成統一格式 **ASFF（AWS Security Finding Format）** 放在一起。
- 2025 年 AWS 推出新一代的 **AWS Security Hub**，在上述服務之上做跨訊號的關聯分析：把 GuardDuty 的威脅、Inspector 的漏洞、CSPM 的設定問題、Macie 的敏感資料結合起來，判斷「哪些資源真的暴露且可被利用」，並用開放標準 **OCSF（Open Cybersecurity Schema Framework）** 表示資料。

對考試來說，SAA-C03 與 SAP-C02 題目裡的「Security Hub」大多指 CSPM 這一套能力：**集中檢視多帳號、多 Region 的安全 findings，並依業界標準自動檢查設定。** 實務設定重點：

- 用 Organizations 指定 **delegated administrator**，以 **central configuration** 統一設定各帳號與 Region 要啟用哪些標準與 controls。
- 設定 **cross-Region aggregation**，把各 Region 的 findings 集中到一個 aggregation Region。
- 用 **automation rules** 自動調整 finding 的嚴重度或狀態，例如把測試帳號的某類 finding 降級。
- Findings 送到 EventBridge，可以觸發自動修復或開工單。

> [!warning] 常見誤解
> Security Hub 不會自己產生 GuardDuty 那種威脅偵測，也不會掃描 CVE；它彙整其他服務的結果並做設定檢查。若 GuardDuty 沒啟用，Security Hub 裡就不會有 GuardDuty 的 finding。同理，「啟用 Security Hub 就自動啟用所有 Region 的 GuardDuty」也是錯的，每個服務都要各自啟用。

偵測服務的分工整理如下，這張表在考試時非常好用：

| 服務 | 一句話 | 資料來源 | 典型題目關鍵字 |
|---|---|---|---|
| GuardDuty | 偵測正在發生的威脅 | CloudTrail、Flow Logs、DNS logs、protection plans | 挖礦、異常 API、外洩 credentials、惡意 IP |
| Inspector | 找軟體漏洞與網路暴露 | EC2 套件、ECR 映像、Lambda | CVE、修補、container image 掃描 |
| Macie | 找 S3 裡的敏感資料 | S3 物件 | PII、信用卡號、資料分類 |
| Detective | 調查 finding 的根因 | CloudTrail、Flow Logs、GuardDuty | 調查、根因分析、視覺化關聯 |
| Security Hub | 彙整 findings 與標準合規檢查 | 上述服務 + Config | 單一檢視、多帳號彙整、CIS／FSBP 標準 |

## 16.10 CloudTrail：誰在什麼時候做了什麼

偵測服務告訴你「有異常」，但週一金流夥伴要的是另一件事：**可信、完整、可回溯的操作紀錄**。這是 AWS CloudTrail 的工作。

**AWS CloudTrail** 記錄 AWS 帳號中的 API 活動：不論是 console 點擊、CLI、SDK 或 AWS 服務代你呼叫，每次 API 呼叫都會產生一筆 **event**，內容包括誰（`userIdentity`，例如哪個 IAM role、哪個 session）、什麼時間、從哪個 IP、呼叫了哪個 API、帶了什麼參數、成功或失敗。

### 三種事件

| 事件類型 | 記錄什麼 | 預設 | 費用 |
|---|---|---|---|
| **Management events** | 對資源的管理操作（control plane），例如 `CreateBucket`、`RunInstances`、`AttachRolePolicy`、console 登入 | 自動記錄 | Event history 免費；每個 Region 第一份 trail 副本免費 |
| **Data events** | 資源內部的資料操作（data plane），例如 S3 `GetObject`／`PutObject`、Lambda `Invoke`、DynamoDB item 層級操作 | **不記錄**，需在 trail 或 event data store 明確啟用 | 按事件數收費，量大時費用高 |
| **Insights events** | 偵測 API 呼叫量或錯誤率異常，例如某個 API 呼叫量突然暴增 | 需啟用 | 另外收費 |

**Event history** 是 console 上預設就有的功能：保存過去 **90 天**的 management events，可以查詢但無法調整保存期限、也不包含 data events。要長期保存，必須建立 **trail**，把事件持續送到 S3 bucket（可選擇同時送到 CloudWatch Logs，以便設定 metric filter 與警報）。

> [!warning] 常見誤解
> 「CloudTrail 預設就會記錄誰讀了 S3 的哪個物件。」不會。S3 物件層級的讀寫是 data event，必須明確啟用，而且通常只對需要稽核的 bucket 啟用以控制費用。

### Trail 的關鍵設定

- **Multi-Region trail**：一條 trail 收集所有 Region 的事件（新增的 Region 也會自動納入）。這能避免「攻擊者在你沒用的 Region 活動卻沒有紀錄」，是建議的預設做法。
- **Organization trail**：在 management account 或 delegated administrator 帳號建立，自動涵蓋 Organization 中所有帳號，成員帳號看得到這條 trail 但**無法修改或刪除**。事件通常集中送到 **log archive 帳號**的 S3 bucket（第 40 章）。
- **Log file integrity validation**：CloudTrail 每小時產生一份 **digest file**，裡面有該時段每個 log 檔的 SHA-256 雜湊值，並用 CloudTrail 的私鑰數位簽章。之後用 `aws cloudtrail validate-logs` 即可驗證 log 檔是否被修改、刪除或偽造。這正是金流夥伴要的「證明 log 沒被動過」。
- **加密**：log 預設以 SSE-S3 加密，可改用 SSE-KMS 並用 key policy 控制誰能解密（第 15 章）。
- **保護 log bucket**：bucket policy 只允許 CloudTrail 寫入、放在獨立帳號、啟用 versioning 與 Object Lock（16.13 節），並用 SCP 禁止成員帳號 `cloudtrail:StopLogging`、`cloudtrail:DeleteTrail`。

```bash
aws cloudtrail validate-logs \
  --trail-arn arn:aws:cloudtrail:ap-northeast-1:111122223333:trail/org-trail \
  --start-time 2026-07-01T00:00:00Z
```

CloudTrail 送到 S3 通常有幾分鐘延遲，適合稽核與事後調查。若要即時反應某個 API 呼叫（例如有人關掉 GuardDuty），應使用 EventBridge 接收 CloudTrail 事件並觸發動作。要查詢大量歷史事件，常見做法是用 Athena 直接查 S3 中的 CloudTrail log。

> [!note] CloudTrail Lake 的現況
> CloudTrail Lake 是可以直接用 SQL 查詢事件的受管資料儲存。依 AWS 文件，它自 2026 年 5 月 31 日起不再開放給新客戶，既有客戶可繼續使用（只會收到重大錯誤修正與安全更新）；CloudTrail 本身的 trail、Insights 不受影響。AWS 建議的替代方案是把 CloudTrail 事件匯入 Amazon CloudWatch 集中查詢；本節的 trail 送到 S3、再用 Athena 查詢，也仍是可行且常考的做法。

## 16.11 AWS Config：資源設定的歷史與合規檢查

CloudTrail 回答「誰做了什麼動作」，**AWS Config** 回答另一個問題：「這個資源**現在**的設定是什麼？過去如何變化？符合公司規定嗎？」

### 它怎麼運作

在每個 Region 啟用 **configuration recorder** 後，Config 會為支援的資源（security group、S3 bucket、IAM role、EC2、RDS……）記錄 **configuration item**：某個時間點的完整設定、與其他資源的關係（例如這個 ENI 屬於哪台 EC2、套了哪些 SG），以及觸發變更的 CloudTrail 事件。你可以查詢任何資源的設定時間軸，例如「這個 security group 在 7 月 3 日下午被改過什麼」。設定歷史與快照會送到 S3。

### Config rules：持續判斷合規

**Config rule** 定義資源應該長什麼樣子，Config 會評估每個資源是 `COMPLIANT` 還是 `NON_COMPLIANT`：

- **Managed rules**：AWS 提供的數百條規則，例如 `restricted-ssh`（SG 不得對 `0.0.0.0/0` 開放 22）、`s3-bucket-public-read-prohibited`、`encrypted-volumes`、`cloudtrail-enabled`。
- **Custom rules**：用 Lambda 或 Guard（一種政策描述語言）自己寫。
- **觸發方式**：設定變更時評估（configuration change），或定期評估（periodic）。

### Remediation 與 conformance packs

不合規之後要修正。Config rule 可以關聯 **remediation action**，使用 **SSM Automation runbook**（例如 `AWS-DisableIncomingSSHOnPort22`）修正資源，可設定為手動觸發或自動執行（含重試次數）。

**Conformance pack** 是一組 Config rules 加上 remediation 的打包（YAML 範本），例如「PCI DSS 營運最佳實務」，可以一次部署到整個 Organization。**Aggregator** 則把多帳號、多 Region 的 Config 資料與合規結果集中到一個帳號檢視。

> [!warning] 常見誤解
> Config 是**偵測性（detective）**控制：資源被建立或修改之後，它才發現不合規，再透過 remediation 修正。它不會在 API 呼叫當下阻止變更。要「事前阻止」，用 IAM policy、SCP（第 14 章）或 Control Tower 的 preventive／proactive controls。考試常把 Config 與 SCP 放在同一題比較。

| 問題 | 服務 |
|---|---|
| 誰在何時從哪裡刪了這個 SG？ | CloudTrail |
| 這個 SG 上週三的規則是什麼？ | Config |
| 所有 S3 bucket 是否都加密？ | Config rule |
| 讓不合規的 SG 自動被修正 | Config rule + SSM Automation remediation |
| EC2 的 CPU 使用率 | CloudWatch（第 36 章） |
| 從根本禁止某帳號關閉 CloudTrail | SCP |

## 16.12 合規證據：Audit Manager 與 Artifact

金流夥伴的稽核還要兩類文件：一是「AWS 這一側的基礎設施安全嗎？」二是「Wanderly 自己的控制有沒有在運作？」根據第 2 章的責任分擔模型，這兩者分別由不同的來源證明。

**AWS Artifact** 是自助下載 AWS 合規文件的入口，提供兩類內容：**reports**，例如 SOC 1／2／3 報告、PCI DSS 的 Attestation of Compliance（AOC）、ISO 認證；以及 **agreements**，例如 HIPAA 的 BAA（Business Associate Addendum）。Organization 的 management account 可以代表所有帳號接受 agreement。Artifact 證明的是 **AWS 負責的部分**，它不會掃描你的資源，也不證明你的設定合規。

**AWS Audit Manager** 用來整理 **客戶自己這一側** 的稽核證據：選擇一個 **framework**（例如 PCI DSS、HIPAA、SOC 2、GDPR 的預建框架或自訂框架），Audit Manager 會從 Config、CloudTrail、Security Hub 等來源自動收集證據，對應到每個 control，最後產生可交給稽核員的 assessment report。它是「收集與整理證據」的工具，不會阻擋或修正任何設定。

> [!note] Audit Manager 的現況
> Audit Manager 已進入維護模式（maintenance mode）：自 2026 年 4 月 30 日起，新帳號無法再設定這個服務；已經在用的客戶可以在原本的帳號與 Region 繼續使用，但不能擴展到新的 Region 或新的 organization，服務也不再新增功能與框架。AWS 建議新客戶改用 **AWS Config conformance packs** 部署並監控各框架的技術控制（例如 PCI DSS、HIPAA、NIST；SOC 2、GDPR 目前沒有對應的 pack），並可用 Config 的 advanced query 匯出證據；需要完整稽核流程（包含政策文件等非技術控制）時，再搭配第三方 GRC（治理、風險與合規）產品。SAA-C03／SAP-C02 的題庫早於這次變更，題目若出現「自動收集稽核證據並對應到合規框架」，答案仍是 Audit Manager；實務上的新設計則要改用上述替代方案。

## 16.13 資料分類與保存：讓證據改不了

證據要可信，除了「有紀錄」，還要「紀錄不能被刪改」，即使是擁有管理權限的人也一樣。這就是 **WORM（Write Once Read Many，一次寫入、多次讀取）** 儲存的需求。

### 先分類，再決定控制

並不是所有資料都要 WORM。Wanderly 先做 **資料分類（data classification）**：

| 類別 | 例子 | 控制 |
|---|---|---|
| 公開 | 旅館照片、行銷頁面 | CloudFront 快取，一般 S3 |
| 內部 | 應用程式 log、報表 | 加密、存取限制、lifecycle 到期刪除 |
| 機密 | 會員個資、護照影本 | KMS 加密、Macie 掃描、最小權限、存取稽核 |
| 受法規保存 | 交易紀錄、CloudTrail log | WORM 保存固定年限，期滿才可刪除 |

每一類都要定義擁有者、保存期限與刪除方式。保存期限太短違反法規，太長則增加成本與外洩風險；個資法規通常要求「不再需要時刪除」，所以「全部永久保存」不是正確答案。

### S3 Object Lock

**S3 Object Lock** 讓 S3 物件版本在指定期間內無法被刪除或覆寫。它需要 bucket 啟用 versioning（啟用 Object Lock 時會自動啟用），保護的是**特定物件版本**：對受保護物件送出不帶版本號的刪除，只會新增一個 delete marker，原本的版本仍在。

- **Retention period（保存期限）**：設定 retain-until date，到期前不能刪除該版本。有兩種模式：
  - **Governance mode**：擁有 `s3:BypassGovernanceRetention` 權限的使用者，可在請求中明確帶上 bypass header 來刪除或縮短保存期。適合「防止誤刪，但保留特殊管理權限」或先測試設定。
  - **Compliance mode**：在保存期限內，**任何人都不能刪除或縮短期限，包括 root user**。只能延長，不能縮短或改回 governance。適合法規強制保存。
- **Legal hold（法律保全）**：沒有到期日，只要 hold 存在就不能刪除，直到具備 `s3:PutObjectLegalHold` 權限的人移除為止。它與 retention period 獨立，適合訴訟或調查期間凍結特定資料。
- 可以設定 bucket 的 **default retention**，讓新上傳的物件自動套用。

Wanderly 把 organization trail 的 bucket 設為 compliance mode、保存 7 年；搭配 CloudTrail log file validation，就能同時證明「log 沒被改」與「log 沒被刪」。第 23 章會更深入介紹 Object Lock 與 MFA delete、lifecycle 的搭配。

### Glacier Vault Lock 與 Backup Vault Lock

**S3 Glacier Vault Lock** 用於較早期、以 vault 為單位的 Glacier 服務（和現在 S3 的 Glacier storage classes 是不同的服務與 API）。這個 vault 型的原始 Glacier 服務**已不再接受新客戶**，既有資料仍可繼續存取；新的封存需求應使用 S3 Glacier storage classes。你為 vault 寫一份 **vault lock policy**（例如「拒絕刪除未滿 365 天的 archive」），啟動 lock 後有 **24 小時**的測試期（InProgress）；在期限內確認無誤並完成 lock，policy 就永遠無法修改或刪除。若在 24 小時內發現問題，可以中止並重來。新的設計應直接在 S3 使用 Glacier storage classes 搭配 Object Lock；考試仍可能出現 Vault Lock，只要記得它是「vault 層級、24 小時內可中止、鎖定後不可變更」即可。

AWS Backup 也有 **Backup Vault Lock**，讓 backup vault 中的 recovery points 無法被刪除或縮短保存期，同樣分 governance 與 compliance 模式，詳細設計在第 34、43 章。

## 16.14 把偵測接成回應：EventBridge 自動化

現在 Wanderly 看得見異常了，但如果 GuardDuty 半夜三點產生 finding，等到早上九點才有人處理，攻擊者已經有六個小時。最後一塊拼圖是**自動回應**：讓已知類型的事件在幾秒內被處理。

所有偵測服務都會把 finding 送到 **Amazon EventBridge**（第 32 章）。EventBridge rule 依事件內容比對，觸發 Lambda、Step Functions、SSM Automation 或 SNS。Wanderly 對「EC2 連到挖礦池」這類 finding 的處理流程：

```text
 ① GuardDuty finding：CryptoCurrency:EC2/BitcoinTool.B!DNS
        │
        ▼
 ② EventBridge rule（source = aws.guardduty，比對 finding type 與嚴重度）
        │
        ▼
 ③ Step Functions 隔離流程
        ├─ a. 把 instance 的 SG 換成「隔離 SG」（無任何 inbound／outbound）
        ├─ b. 對 EBS volumes 建立 snapshot，保留鑑識證據
        ├─ c. 為 instance 加上 tag：quarantine=true
        ├─ d. 從 ASG／target group 移除，讓服務改由健康的 instance 承接
        └─ e. 透過 SNS 通知 on-call，附上 finding 連結
        │
        ▼
 ④ 分析師用 Detective 調查根因；處理完成後在 Security Hub 更新 finding 狀態
```

① GuardDuty 偵測到 EC2 查詢挖礦池網域。② EventBridge rule 只比對特定 finding 類型，避免低風險事件也觸發隔離。③ 隔離流程刻意「先隔離、保留證據、不直接終止 instance」：直接 terminate 會連記憶體與磁碟證據一起消失，也無法調查入侵途徑。換掉 security group 能切斷 C2 連線，snapshot 則保存磁碟狀態。④ 自動化處理已知模式，人負責判斷與根因分析。

一個需要注意的細節：security group 是 stateful，已建立的連線在換 SG 後可能仍會持續一段時間；若需要立即切斷，可以同時在 subnet 的 NACL 加 deny 規則。

對外洩的 access key（週六的挖礦事件），自動化可以呼叫 IAM `UpdateAccessKey` 將它設為 inactive，並對該 user 附加一份「拒絕所有動作」的 inline policy；若是 role 的臨時憑證外洩，則在 role 上附加一份以 `aws:TokenIssueTime` 為條件、拒絕在某時間點前簽發之 session 的 policy（console 的「Revoke active sessions」就是做這件事）。

同樣的模式也用在設定合規：Config rule 偵測到「SG 對 Internet 開放 22」→ 自動 remediation 刪除該規則；CloudTrail 事件「有人呼叫 `StopLogging`」→ EventBridge 觸發 Lambda 重新啟用並告警。

### 防護服務：題目在擋什麼？

```text
要防護的是什麼？
├─ HTTP 請求內容（SQLi、XSS、爬蟲、撞庫、地理限制）
│    └─ WAF（掛在 CloudFront／ALB／API Gateway REST／AppSync／Cognito）

├─ DDoS
│    ├─ 常見 L3/L4、預算有限 → Shield Standard（已內建）+ CloudFront／Route 53
│    └─ 要費用保護、24/7 專家、進階可視性 → Shield Advanced
├─ VPC 進出流量的網域過濾、IPS
│    ├─ 深度檢查、TLS SNI、Suricata → Network Firewall（路由導入）
│    └─ 只需擋惡意網域的 DNS 查詢 → Route 53 Resolver DNS Firewall
├─ 資源之間的 IP/port 存取 → Security group（＋必要時 NACL deny）
└─ 多帳號一致套用上述政策 → Firewall Manager
```

## 16.16 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| SQL injection、XSS、OWASP Top 10 | WAF + AWS managed rule groups（Core、SQL database） |
| 同一 IP 大量請求、暴力破解登入 | WAF rate-based rule（scope-down 到登入路徑） |
| 只允許特定國家存取 | WAF geo match 或 CloudFront geo restriction |
| 爬蟲、bot | WAF Bot Control、CAPTCHA／Challenge |
| DDoS 費用補償、24/7 DDoS 專家（SRT） | Shield Advanced（SRT 需 Business／Enterprise Support） |
| 所有帳號的 ALB 自動掛 WAF、含新帳號 | Firewall Manager（需 Organizations + Config） |
| 出站只允許特定網域、IPS | Network Firewall stateful domain list／Suricata |
| 擋掉查詢惡意網域的 DNS | Route 53 Resolver DNS Firewall |
| 挖礦、異常 API、外洩 key、最少營運負擔 | GuardDuty（所有 Region 啟用） |
| CVE、container image 掃描 | Inspector |
| S3 中的個資、信用卡號 | Macie |
| 調查根因、視覺化關聯 | Detective |
| 集中檢視 findings、CIS benchmark | Security Hub（需先啟用 Config） |
| 誰刪了資源、API 稽核 | CloudTrail（長期保存要建 trail） |
| 誰讀了 S3 物件 | CloudTrail data events |
| 證明 log 未被竄改 | CloudTrail log file integrity validation |
| 所有帳號的 trail、成員不可關閉 | Organization trail + SCP |
| 設定是否合規、自動修正 | Config rules + remediation（SSM Automation） |
| 連 root 也不能刪除、法規保存 | S3 Object Lock compliance mode |
| AWS 的 SOC 2 報告 | Artifact |

**常見陷阱**：

1. 把 WAF 掛在 NLB 或 EC2 上：不支援。WAF 只能掛在 CloudFront、ALB、API Gateway REST API、AppSync、Cognito 等 web 入口。
2. 以為 Shield Advanced 會檢查 SQL injection：Shield 處理 DDoS，內容檢查是 WAF 的工作。
3. 以為 GuardDuty 需要先自己開 VPC Flow Logs：不需要，它直接取得資料流；而且它只偵測不阻擋。
4. 只在主要 Region 啟用 GuardDuty 或 trail：攻擊者常利用你沒在用的 Region。
5. 把 Config 當成預防控制：Config 是事後偵測與修正，事前阻止要用 IAM／SCP。
6. 把 governance mode 當成「任何人都不能刪」：有 bypass 權限的人可以刪；法規要求請選 compliance mode。

## 16.17 SAP 加深：組織層級的安全營運

SAA 題目多半是「單一帳號選對服務」；SAP 題目則是「幾百個帳號、多個 Region，怎麼讓安全控制不漏、不被關、可稽核，而且不讓 management account 變成日常工作帳號」。

### 集中化的委派管理模式

標準做法是建立一個 **Security Tooling（Audit）帳號**，把 GuardDuty、Security Hub、Inspector、Macie、Detective、Firewall Manager、Config aggregator 的 **delegated administrator** 都指定給它；log 則集中到 **Log Archive 帳號**（第 40 章）。要點：

- 每個服務各自指定 delegated administrator、各自設定 auto-enable，**而且逐 Region 生效**。最常見的漏洞是「新 Region 啟用了，但安全服務沒跟上」，所以 baseline 自動化（Control Tower、StackSets）要涵蓋所有允許的 Region，並用 SCP 拒絕使用不允許的 Region（第 14 章）。
- 用 SCP 禁止成員帳號關閉安全服務：例如拒絕 `guardduty:DeleteDetector`、`guardduty:DisassociateFromAdministratorAccount`、`cloudtrail:StopLogging`、`config:StopConfigurationRecorder`，例外只開給特定的平台角色。
- 建立一張 **coverage matrix**：每個服務 × 每個 Region × 新舊帳號的啟用狀態與負責人，定期檢查。

### 用 Security Lake 統一安全資料

**Amazon Security Lake** 把 CloudTrail、VPC Flow Logs、Route 53 resolver logs、Security Hub findings 以及第三方來源，自動轉成 OCSF 格式並存進你帳號中的 S3 資料湖，讓 SIEM 或 Athena 能以統一格式查詢、長期保存。SAP 題目若要求「把多帳號多 Region 的安全 log 以標準格式集中，交給第三方 SIEM 分析」，Security Lake 是好的答案。

### 集中 inspection 的取捨

Network Firewall 可以分散部署（每個 VPC 一個）或集中部署（inspection VPC + Transit Gateway）。分散式的故障範圍小、路由簡單，但費用與規則管理隨 VPC 數量增加；集中式費用與管理集中，但要處理 TGW appliance mode、跨 AZ 對稱路由，且 inspection VPC 成為關鍵路徑。Firewall Manager 可以同時管理兩種模式的規則一致性。第 41 章會完整設計這個架構。

### 改善既有系統的安全性（SAP Domain 3）

SAP 常給一個「已經在跑、但有安全缺口」的架構，問最有效的改善。思考順序：

1. **入口**：web 入口都有 WAF 嗎？origin 能被繞過嗎？
2. **偵測覆蓋**：GuardDuty、Security Hub、Config 是否所有帳號與 Region 都啟用？
3. **證據**：organization trail、log file validation、log archive 帳號的 Object Lock 是否到位？
4. **回應**：高風險 finding 是否有自動化的隔離流程與明確的負責人？
5. **防止關閉**：SCP 是否保護上述設定不被成員帳號移除？

## 本章重點整理

- 每種防護只看得到特定層：security group／NACL 看 IP 與 port，Network Firewall 看網域與流量特徵，WAF 看 HTTP 內容，Shield 處理 DDoS 流量模式；分層防禦就是把它們疊起來。
- WAF 的 web ACL 依 priority 由小到大評估，第一個終止型 action 決定結果；新規則先用 Count 觀察再改 Block。
- WAF 可掛在 CloudFront、ALB、API Gateway REST API、AppSync、Cognito user pool 等，不能掛在 NLB 或 EC2；CloudFront 用的 web ACL 是 global 範圍（us-east-1）。
- Rate-based rule 依 aggregation key 在時間窗內計數，搭配 scope-down 只限制登入等特定路徑；分散式低速攻擊要搭配 IP reputation、Bot Control 或 ATP。
- Shield Standard 對所有客戶免費自動提供 L3／L4 防護；Shield Advanced 提供 SRT、DDoS 費用保護、進階偵測與自動 L7 緩解。
- Firewall Manager 需要 Organizations 與 AWS Config，用來在多帳號一致部署 WAF、Shield Advanced、SG、Network Firewall、DNS Firewall 政策，本身不檢查流量。
- Network Firewall 靠修改 route table 讓流量經過每個 AZ 的 firewall endpoint，去程與回程必須對稱；stateless 規則先評估，stateful 規則可做網域過濾與 Suricata IPS。
- GuardDuty 自動分析 CloudTrail、VPC Flow Logs、DNS logs（不需自己開啟），偵測異常但不阻擋；它是 Regional 服務，所有 Region 都要啟用。
- Inspector 持續掃描 EC2、ECR、Lambda 的 CVE；Macie 只掃 S3 中的敏感資料；Detective 用於調查；Security Hub 彙整 findings 並依 CIS、FSBP 等標準檢查設定（需 Config）。
- CloudTrail management events 預設記錄、event history 只保存 90 天；data events 要明確啟用；長期保存要建立 multi-Region 或 organization trail。
- CloudTrail log file integrity validation 用簽章的 digest file 證明 log 未被修改或刪除，搭配 log archive 帳號與 Object Lock 保護證據。
- AWS Config 記錄資源設定歷史並用 rules 判斷合規，可用 SSM Automation 自動修正；它是偵測性控制，事前阻止要用 IAM 或 SCP。
- Artifact 提供 AWS 側的合規報告與協議；Audit Manager 收集客戶側證據對應框架，但已進入維護模式，自 2026 年 4 月 30 日起新帳號無法再設定，AWS 建議改用 Config conformance packs。
- S3 Object Lock compliance mode 在保存期內連 root 都不能刪除或縮短；governance mode 可由具 bypass 權限者覆寫；legal hold 沒有到期日。
- 偵測服務的 findings 都送到 EventBridge，可觸發 Step Functions／Lambda 自動隔離、保留證據與通知，讓已知威脅在幾秒內被處理。

## 本章練習題

### 練習 16-1｜SAA｜單選｜WAF 的掛載位置

Wanderly 的網站架構是 CloudFront → internet-facing ALB → EC2。資安掃描發現搜尋頁可能受到 SQL injection 攻擊。團隊希望在惡意請求到達 ALB 之前就被擋下，並且不想自己撰寫與維護攻擊特徵規則。

最合適的做法是什麼？

- A. 為 CloudFront 與 ALB 啟用 Shield Advanced，由 Shield Response Team 分析並阻擋 SQL injection
- B. 在 VPC 部署 Network Firewall，用 Suricata 規則檢查進入 ALB 的流量
- C. 建立 global 範圍的 WAF web ACL，加入 AWS managed 的 SQL database 與 Core rule set，並關聯到 CloudFront distribution
- D. 在 ALB 所在 subnet 的 NACL 加入 deny 規則，阻擋含有 SQL 關鍵字的請求

> [!answer]- 答案：C
> **A ✗** Shield Advanced 處理的是 DDoS；SRT 雖能協助撰寫 WAF 規則，但 SQL injection 的檢查仍由 WAF 執行，且單靠 Shield 不會檢查請求內容。
>
> **B ✗** Network Firewall 可以做 IPS，但要改路由、處理 TLS 檢查，營運負擔遠高於 WAF；而且部署在 VPC 內代表請求已經進入 VPC，不符合「到達 ALB 之前」與「不自己維護規則」。
>
> **C ✓** WAF 掛在 CloudFront 上，請求在邊緣節點就被檢查，不會到達 ALB。AWS managed rule groups 由 AWS 維護更新，不需要自己寫 SQL injection 特徵。CloudFront 用的 web ACL 必須是 global（CLOUDFRONT）範圍。
>
> **D ✗** NACL 只看 IP、port 與協定，看不到 HTTP 內容，不可能比對 SQL 關鍵字。
>
> **考點**：SAA-1.2｜WAF managed rules 與掛載位置

### 練習 16-2｜SAA｜單選｜撞庫攻擊的速率限制

Wanderly 的登入 API `/api/login` 遭到撞庫攻擊，攻擊來自數十個 IP，每個 IP 每分鐘送出數百次登入請求。網站其他頁面（搜尋、房型瀏覽）流量正常，團隊不希望影響一般使用者瀏覽。WAF web ACL 已關聯在 CloudFront 上。

應新增哪種規則？

- A. Rate-based rule，以來源 IP 為 aggregation key，搭配 scope-down statement 只計算 URI 以 `/api/login` 開頭的請求，超過門檻則 Block
- B. Rate-based rule，以來源 IP 為 aggregation key，對所有路徑一起計算，超過門檻則 Block
- C. Geo match rule，阻擋攻擊 IP 所在國家的所有請求
- D. IP set rule，把目前看到的攻擊 IP 手動加入阻擋清單

> [!answer]- 答案：A
> **A ✓** 攻擊特徵是「少數 IP 對登入路徑的高頻請求」。Rate-based rule 依來源 IP 計數，scope-down 讓計數只針對 `/api/login`，所以瀏覽其他頁面的使用者完全不受影響。WAF 掛在 CloudFront 上能看到真實的用戶端 IP。
>
> **B ✗** 不加 scope-down 時，所有頁面的請求都一起計數，門檻若設低會誤擋大量瀏覽的正常使用者，設高又擋不住登入攻擊。
>
> **C ✗** 攻擊 IP 通常是雲端主機或代理，所在國家很可能也有大量正常會員，整國封鎖會誤傷且容易被換 IP 繞過。
>
> **D ✗** 手動維護 IP 清單反應慢，攻擊者換一批 IP 就失效。IP set 適合長期固定的清單，不適合動態攻擊。
>
> **考點**：SAA-1.2｜WAF rate-based rule 與 scope-down

### 練習 16-3｜SAA｜單選｜Shield Advanced 的使用時機

Wanderly 去年在一次 DDoS 攻擊中，CloudFront 與 Route 53 的用量暴增，帳單多了數萬美元，而且團隊花了好幾個小時才搞清楚攻擊型態。管理層要求：未來遭受 DDoS 時，能獲得 AWS DDoS 專家 24 小時協助，並能申請攻擊造成的額外費用抵免。公司已購買 Business Support。

應採取什麼做法？

- A. 依賴預設的 Shield Standard，它已涵蓋所有 CloudFront 與 Route 53 資源
- B. 在 CloudFront 的 WAF web ACL 加入 rate-based rule，並設定 CloudWatch 警報
- C. 啟用 GuardDuty，讓它偵測 DDoS 並透過 EventBridge 通知團隊
- D. 訂閱 Shield Advanced，把 CloudFront distribution 與 Route 53 hosted zone 加入保護，並設定 SRT 存取權限與 Route 53 health checks

> [!answer]- 答案：D
> **A ✗** Shield Standard 免費提供 L3／L4 基本防護，但沒有 SRT 支援，也沒有 DDoS cost protection。
>
> **B ✗** Rate-based rule 有助緩解應用層 flood，但無法提供專家支援或費用抵免。
>
> **C ✗** GuardDuty 偵測帳號內的威脅活動，不是 DDoS 緩解服務，也沒有費用保護。
>
> **D ✓** Shield Advanced 提供 24/7 Shield Response Team（需 Business 或 Enterprise Support）、DDoS cost protection，以及進階的攻擊可視性。關聯 Route 53 health checks 可啟用以健康狀態輔助的偵測與 proactive engagement。
>
> **考點**：SAA-1.2｜Shield Standard vs Shield Advanced

### 練習 16-4｜SAA｜單選｜出站網域過濾

Wanderly 的付款處理 EC2 位於 private subnet，經 NAT Gateway 連到 Internet。PCI 稽核要求：這些 instance 只能連到 `api.payment-partner.com` 與 AWS 服務的網域，其他所有對外連線都必須阻擋並留下紀錄。合作夥伴 API 的 IP 經常變動。團隊希望使用受管服務。

最合適的做法是什麼？

- A. 修改 instance 的 security group 出站規則，只允許合作夥伴目前的 IP 位址
- B. 部署 AWS Network Firewall，在 stateful rule group 使用 domain list 允許清單，並修改 route table 讓 private subnet 的出站流量先經過 firewall endpoint 再到 NAT Gateway
- C. 在 NAT Gateway 上關聯 WAF web ACL，只允許目的 Host header 為合作夥伴網域的請求
- D. 把 NAT Gateway 改成 NAT instance，在作業系統中設定 iptables 依網域過濾

> [!answer]- 答案：B
> **A ✗** Security group 只能寫 IP 與 port，不支援網域名稱；合作夥伴 IP 經常變動時，規則會失效。
>
> **B ✓** Network Firewall 的 stateful domain list 可依 TLS SNI 或 HTTP Host header 比對網域，做允許清單，不受 IP 變動影響；alert／flow log 可留下紀錄。它需要靠路由讓流量經過 firewall endpoint，並確保回程也經過同一個 endpoint。
>
> **C ✗** WAF 不能關聯到 NAT Gateway，它只保護 CloudFront、ALB、API Gateway 等入站的 web 入口。
>
> **D ✗** NAT instance 需要自行維護作業系統、高可用與規則，違反「使用受管服務」的要求；iptables 本身也不擅長依 TLS 網域過濾。
>
> **考點**：SAA-1.2｜Network Firewall domain filtering

### 練習 16-5｜SAA｜單選｜偵測被入侵的 instance

Wanderly 的帳單在週末突然暴增，事後發現有人用外洩的 access key 在一個平常不用的 Region 啟動 GPU instance 挖礦。安全團隊希望未來能自動偵測類似的異常 API 活動與挖礦流量，營運負擔要最低，且不想在 instance 上安裝額外軟體。

最合適的做法是什麼？

- A. 在所有 Region 啟用 Amazon Inspector，掃描 EC2 instance 的軟體漏洞
- B. 在主要使用的 Region 啟用 VPC Flow Logs，寫 Lambda 分析是否連到已知挖礦池
- C. 在所有 Region 啟用 Amazon GuardDuty，並用 EventBridge 把高嚴重度的 finding 送到 on-call 通知
- D. 在所有帳號啟用 Amazon Macie，偵測 access key 是否出現在 S3 物件中

> [!answer]- 答案：C
> **A ✗** Inspector 找的是軟體漏洞與網路暴露，不會偵測外洩 key 的異常 API 呼叫或正在進行的挖礦行為。
>
> **B ✗** 自己分析 Flow Logs 營運負擔高，而且只在主要 Region 啟用，正好漏掉攻擊者使用的陌生 Region。
>
> **C ✓** GuardDuty 自動分析 CloudTrail management events、VPC Flow Logs 與 DNS logs，能偵測異常 API 活動與挖礦相關流量，不需安裝 agent 或自行啟用 log。它是 Regional 服務，必須在所有 Region 啟用，finding 可經 EventBridge 通知。
>
> **D ✗** Macie 能找出 S3 物件中的 credentials，但不會偵測 key 被使用的異常行為或挖礦流量。
>
> **考點**：SAA-1.2｜GuardDuty 與多 Region 啟用

### 練習 16-6｜SAA｜選兩項｜安全服務分工

Wanderly 的安全團隊有兩個新需求：(1) 每當 ECR 中的 container image 或執行中的 EC2 出現新公布的 CVE 時，自動通知負責團隊；(2) 找出所有 S3 bucket 中是否存有護照號碼與信用卡號。團隊希望使用受管服務、營運負擔最低。

應使用哪兩個服務？（選兩項）

- A. Amazon Inspector
- B. Amazon Detective
- C. AWS Config
- D. Amazon Macie
- E. AWS Artifact

> [!answer]- 答案：A、D
> **A ✓** Inspector 持續掃描 EC2 與 ECR image 的軟體漏洞，有新 CVE 公布時會自動重新評估，finding 可經 EventBridge 通知負責團隊。

>
> **C ✗** Config 記錄資源設定並檢查設定是否合規，例如 bucket 是否加密，但不會讀取物件內容，也不掃描套件 CVE。
>
> **D ✓** Macie 專門偵測 S3 中的敏感資料，有內建的護照號碼、信用卡號等 managed data identifiers，可用 automated discovery 或 discovery jobs 掃描。
>
> **E ✗** Artifact 提供 AWS 的合規報告與協議，不掃描客戶的資源。
>
> **考點**：SAA-1.2、SAA-1.3｜Inspector 與 Macie 的分工

### 練習 16-7｜SAA｜單選｜稽核物件存取

稽核員要求 Wanderly 提供過去一年中「哪些 IAM principal 讀取了 `wanderly-passport-scans` bucket 中的哪些物件」的紀錄。目前帳號只有 CloudTrail 預設的 event history，沒有建立任何 trail。

應如何設定，才能從現在開始滿足這類稽核需求？

- A. 在 CloudTrail event history 中把保存期限調整為一年
- B. 啟用 AWS Config，並為該 bucket 啟用 configuration recorder
- C. 為該 bucket 啟用 S3 server access logging，並把 log 保存在同一個 bucket
- D. 建立 CloudTrail trail，針對該 bucket 啟用 S3 data events（讀取事件），把 log 送到另一個受保護的 S3 bucket 並保存一年以上

> [!answer]- 答案：D
> **A ✗** Event history 固定保存 90 天的 management events，無法調整期限，也不包含 S3 物件層級的 data events。
>
> **B ✗** Config 記錄的是 bucket 的設定變化（例如 policy、加密設定），不記錄誰讀了哪個物件。
>
> **C ✗** Server access logging 能記錄請求，但它以 best-effort 方式遞送，不保證每筆請求都有紀錄，不適合作為稽核依據；把 log 寫回被稽核的同一個 bucket 還會產生 log 本身的存取紀錄，形成循環。
>
> **D ✓** `GetObject` 屬於 data event，預設不記錄，必須在 trail 中為特定 bucket 明確啟用。只對需要稽核的 bucket 啟用可以控制費用，log 送到另一個受保護的 bucket 長期保存，紀錄中的 `userIdentity` 欄位能回答「誰讀了什麼」。
>
> **考點**：SAA-1.3｜CloudTrail data events 與長期保存

### 練習 16-8｜SAA｜選兩項｜證明稽核紀錄未被竄改

金流合作夥伴要求 Wanderly 證明 CloudTrail log 在保存期間沒有被修改，而且在 7 年保存期內不可能被任何人刪除，包括擁有 AdministratorAccess 的帳號管理員。

哪兩個設定能滿足需求？（選兩項）

- A. 在 trail 啟用 log file integrity validation，定期用 `aws cloudtrail validate-logs` 驗證
- B. 把 log 改送到 CloudWatch Logs，並把 retention 設為 7 年
- C. 用 SSE-KMS 加密 log，並只允許安全團隊解密
- D. 把 log 送到啟用 S3 Object Lock 的 bucket，並以 compliance mode 設定 7 年的 default retention
- E. 把 log bucket 設為 Object Lock governance mode，並只把 `s3:BypassGovernanceRetention` 權限給 root user

> [!answer]- 答案：A、D
> **A ✓** Log file integrity validation 產生經數位簽章的 digest file，記錄每個 log 檔的 SHA-256 雜湊，能驗證 log 是否被修改、刪除或偽造，回答「沒有被改」。
>
> **B ✗** CloudWatch Logs 的 retention 決定保存多久，但具有足夠權限的管理員仍可刪除 log group，無法滿足「任何人都不能刪」。
>
> **C ✗** SSE-KMS 控制誰能讀取內容，是機密性控制；它不能證明完整性，也不能阻止有權限的人刪除物件。
>
> **D ✓** Compliance mode 的 Object Lock 讓物件版本在保存期內不能被任何人刪除或縮短期限，包括 root user，回答「刪不掉」。
>
> **E ✗** Governance mode 允許具 bypass 權限者刪除，而 root user 本來就有完整權限，無法滿足「任何人都不能刪」。
>
> **考點**：SAA-1.3｜CloudTrail log file validation 與 Object Lock compliance mode

### 練習 16-9｜SAA｜單選｜設定合規與自動修正

Wanderly 發現有開發人員為了除錯，把 security group 的 22 port 對 `0.0.0.0/0` 開放後忘記關閉。安全團隊希望：任何 security group 出現這種規則時，自動在幾分鐘內移除該規則，並保留合規紀錄。開發人員仍需要能自行管理其他 security group 規則。

最合適的做法是什麼？

- A. 啟用 AWS Config 的 `restricted-ssh` managed rule，並設定以 SSM Automation runbook 自動修正的 remediation action
- B. 以 SCP 拒絕所有成員帳號的 `ec2:AuthorizeSecurityGroupIngress` 動作
- C. 啟用 GuardDuty，當偵測到 SSH 暴力破解時通知開發人員自行關閉 port
- D. 啟用 Amazon Inspector，以 network reachability finding 找出開放 22 port 的 instance

> [!answer]- 答案：A
> **A ✓** `restricted-ssh` 在 SG 設定變更時評估，發現對 `0.0.0.0/0` 開放 22 即標記 NON_COMPLIANT；關聯的 remediation 可自動執行 SSM Automation 移除該規則。Config 也保留每次評估與修正的紀錄。
>
> **B ✗** 拒絕所有 `AuthorizeSecurityGroupIngress` 會讓開發人員無法管理任何 SG 規則，違反需求。SCP 適合精確的預防性限制，不適合這種粗粒度封鎖。
>
> **C ✗** GuardDuty 在攻擊發生後才偵測，且只通知不修正，無法保證規則在幾分鐘內被移除。
>
> **D ✗** Inspector 能指出網路暴露，但不會自動移除 SG 規則，也不是設定合規的紀錄工具。
>
> **考點**：SAA-1.2｜Config rules 與自動 remediation

### 練習 16-10｜SAA｜單選｜法規保存的 WORM 儲存

Wanderly 依法必須保存每筆訂單的交易紀錄 5 年。法務要求：保存期間任何人（包括 root user 與 AWS 帳號管理員）都不能刪除或修改紀錄；若遇到訴訟，特定紀錄要能在 5 年後繼續保留直到案件結束。紀錄存放在 S3。

最合適的設定是什麼？

- A. 啟用 versioning 與 MFA delete，並以 bucket policy 拒絕 `s3:DeleteObject`
- B. 啟用 S3 Object Lock，以 compliance mode 設定 5 年 default retention；遇到訴訟時對相關物件版本加上 legal hold
- C. 啟用 S3 Object Lock，以 governance mode 設定 5 年 default retention；遇到訴訟時延長 governance 期限
- D. 設定 lifecycle rule 在 5 年後把物件移到 Glacier Deep Archive，並以 IAM policy 拒絕刪除

> [!answer]- 答案：B
> **A ✗** Bucket policy 可以被具備權限的管理員修改，MFA delete 也只是增加刪除門檻，都無法保證「任何人都不能刪」。
>
> **B ✓** Compliance mode 在保存期內不允許任何人刪除或縮短期限，包括 root user。Legal hold 沒有到期日，與 retention 獨立，可在訴訟期間讓物件在 5 年後仍無法刪除，直到有權限者移除 hold。
>
> **C ✗** Governance mode 可由具 `s3:BypassGovernanceRetention` 權限者覆寫，不符合「任何人都不能刪」。
>
> **D ✗** Lifecycle 只負責轉換儲存類別或到期刪除，不提供 WORM 保護；IAM policy 同樣可被管理員修改。
>
> **考點**：SAA-1.3｜S3 Object Lock compliance mode 與 legal hold

### 練習 16-11｜SAP｜單選｜多帳號一致的 WAF 政策

Wanderly 併購後擁有 45 個 AWS 帳號，分布在 4 個 OU，每個月還會新增帳號。安全團隊要求：所有帳號中帶有 `exposure=public` tag 的 ALB 與 CloudFront distribution，都必須套用一組中央維護的 WAF rule groups，新建立的資源也要自動套用；各應用團隊仍可加入自己的業務規則，但不能移除中央規則。公司已使用 AWS Organizations（all features）。

最合適的做法是什麼？

- A. 在每個帳號以 CloudFormation StackSets 部署 web ACL，並用 SCP 拒絕 `wafv2:DeleteWebACL`
- B. 在安全帳號建立一個 regional web ACL，透過 AWS RAM 分享給所有帳號的 ALB 與 CloudFront 使用
- C. 指定安全帳號為 Firewall Manager administrator，確認各帳號已啟用 AWS Config，建立以 tag 為範圍的 WAF policy，定義最先與最後評估的中央 rule groups，並啟用 auto remediation
- D. 啟用 Security Hub 的 AWS Foundational Security Best Practices 標準，由 control 檢查 ALB 是否關聯 WAF

> [!answer]- 答案：C
> **A ✗** StackSets 可以部署 web ACL，但不會自動把新建立的 ALB 或 CloudFront 關聯上去；SCP 只能防止刪除，無法確保新資源被保護，也無法讓團隊在中央規則之間安全地加入自己的規則。
>
> **B ✗** Web ACL 不能透過 RAM 分享給其他帳號的資源關聯；而且 regional web ACL 不能關聯到 CloudFront。
>
> **C ✓** Firewall Manager 依 Organizations 與 Config 持續發現範圍內的資源（可依 OU、帳號、tag），自動關聯 WAF policy，新資源與新帳號也會被涵蓋。WAF policy 的 first／last rule groups 由中央控制，帳號團隊只能在中間加入自己的規則。
>
> **D ✗** Security Hub 的 control 能檢查並回報是否有 WAF，但不會自動部署或關聯 web ACL。
>
> **考點**：SAP-1.2、SAP-1.4｜Firewall Manager WAF policy

### 練習 16-12｜SAP｜選兩項｜組織層級的威脅偵測

Wanderly 有 80 個帳號，業務使用 3 個 Region，但 SCP 允許 6 個 Region。安全營運中心（SOC）位於專用的 security tooling 帳號，要求：GuardDuty 涵蓋所有帳號與所有允許的 Region（包括未來新帳號）；所有 findings 能在單一位置檢視；management account 不得作為 SOC 日常工作帳號。

哪兩個做法最合適？（選兩項）

- A. 在 management account 直接啟用 GuardDuty 與 Security Hub，讓 SOC 人員登入 management account 處理 findings
- B. 在每個允許的 Region，將 security tooling 帳號指定為 GuardDuty 的 delegated administrator，並設定對所有成員帳號（含新帳號）auto-enable
- C. 只在 3 個業務 Region 啟用 GuardDuty，其他 Region 由 SCP 保護即可
- D. 在 security tooling 帳號啟用 Security Hub，啟用 GuardDuty 後 Security Hub 會自動在所有帳號啟用 GuardDuty
- E. 將 security tooling 帳號指定為 Security Hub 的 delegated administrator，使用 central configuration 並設定 cross-Region aggregation 到一個 home Region

> [!answer]- 答案：B、E
> **A ✗** 讓 SOC 在 management account 日常作業違反最小權限與帳號分工原則；management account 不受 SCP 限制，應盡量少用。
>
> **B ✓** GuardDuty 是 Regional 服務，delegated administrator 與 auto-enable 需在每個 Region 設定。涵蓋所有「允許」的 Region 能防止攻擊者利用未使用的 Region；auto-enable 讓新帳號自動納入。
>
> **C ✗** SCP 允許的 Region 就可能被使用，包括外洩 credentials 的攻擊者；只啟用業務 Region 會留下盲點。
>
> **D ✗** Security Hub 彙整 GuardDuty 的 findings，但不會替任何帳號啟用 GuardDuty，各服務要各自設定。
>
> **E ✓** Security Hub 的 delegated administrator 搭配 central configuration 能統一各帳號與 Region 的設定，cross-Region aggregation 把 findings 集中到一個 Region，滿足單一位置檢視。
>
> **考點**：SAP-1.2、SAP-1.4｜GuardDuty 與 Security Hub 的 delegated administrator

### 練習 16-13｜SAP｜單選｜集中 inspection 的非對稱路由

Wanderly 透過 Transit Gateway 把 20 個 spoke VPC 的東西向流量送到一個 inspection VPC，由部署在兩個 AZ 的 Network Firewall endpoint 檢查。上線後發現，部分跨 VPC 的 TCP 連線會隨機失敗，flow log 顯示同一條連線的去程經過 AZ-a 的 firewall endpoint，回程卻進入 AZ-b 的 endpoint。

最合適的修正方式是什麼？

- A. 在每個 spoke VPC 各自部署 Network Firewall，取消集中 inspection
- B. 把 stateful rule group 改成 stateless rule group，讓 firewall 不需要追蹤連線狀態
- C. 刪除 AZ-b 的 firewall endpoint，讓所有流量都經過 AZ-a
- D. 在 Transit Gateway 的 inspection VPC attachment 啟用 appliance mode

> [!answer]- 答案：D
> **A ✗** 分散部署可以避開這個問題，但會大幅增加費用與規則管理負擔，屬於過度修改；問題只需修正路由的對稱性。
>
> **B ✗** 改成 stateless 會失去網域過濾與 IPS 等 stateful 檢查能力，降低安全性，是以犧牲需求換取可用性。
>
> **C ✗** 只留一個 AZ 的 endpoint 會造成單點故障，AZ-a 故障時所有跨 VPC 流量中斷，也增加跨 AZ 傳輸費用。
>
> **D ✓** Transit Gateway 預設會盡量讓流量留在來源 AZ，導致去程與回程可能進入不同 AZ 的 attachment。啟用 appliance mode 後，TGW 依連線的 flow hash 選擇同一個 AZ 的 attachment，讓雙向流量經過同一個 firewall endpoint，stateful 檢查才能正常運作。
>
> **考點**：SAP-1.1、SAP-3.4｜Network Firewall 集中部署與 TGW appliance mode

### 練習 16-14｜SAP｜單選｜事件的自動隔離與證據保存

Wanderly 的 GuardDuty 回報一台位於 Auto Scaling group 中的 EC2 正在與已知的 C2 伺服器通訊。資安政策要求：高嚴重度的此類 finding 要在 5 分鐘內自動切斷該 instance 的網路連線，保留磁碟證據供鑑識，同時不能讓服務容量下降。目前所有處理都靠人工。

最合適的做法是什麼？

- A. 建立 EventBridge rule 比對該類 GuardDuty finding，觸發 Step Functions：將 instance 從 ASG detach（同時讓 ASG 補上新 instance），把 SG 換成無規則的隔離 SG，對 EBS volumes 建立 snapshot，並以 SNS 通知 on-call
- B. 建立 EventBridge rule 比對該類 finding，觸發 Lambda 直接 terminate 該 instance，讓 ASG 自動啟動新的 instance
- C. 在 GuardDuty 建立 suppression rule，把該類 finding 自動封存，並每週由人工檢視封存清單
- D. 啟用 Detective，由分析師在 behavior graph 中確認攻擊範圍後，再手動隔離 instance

> [!answer]- 答案：A

>
> **C ✗** Suppression rule 是降低雜訊用的，把高嚴重度的真實威脅封存會讓攻擊持續，完全違反政策。
>
> **D ✗** Detective 適合事後調查根因，但人工流程無法保證 5 分鐘內隔離。正確做法是自動隔離後再用 Detective 調查。
>
> **考點**：SAP-1.2、SAP-3.2｜EventBridge 驅動的自動化事件回應

### 練習 16-16｜SAP｜單選｜防止繞過 CloudFront 的 DDoS 與 WAF

Wanderly 已為 CloudFront 訂閱 Shield Advanced 並關聯 WAF web ACL。但最近一次攻擊中，攻擊者直接對 internet-facing ALB 的 DNS 名稱發送大量 HTTP 請求，完全繞過了 CloudFront 與 WAF。ALB 必須維持 internet-facing（短期內無法改架構），團隊希望以最少變更阻止這種繞過。

最合適的做法是什麼？

- A. 在 ALB 也關聯同一個 CloudFront 用的 global web ACL
- B. 在 ALB 所在 subnet 的 NACL 中，逐一加入攻擊 IP 的 deny 規則
- C. 將 ALB 的 security group inbound 來源限制為 CloudFront origin-facing 的 AWS managed prefix list，並讓 CloudFront 加入一個秘密 custom header，由 ALB listener rule 只轉送帶有正確 header 的請求
- D. 為 ALB 啟用 GuardDuty Runtime Monitoring，偵測直接連線的來源

> [!answer]- 答案：C
> **A ✗** Global（CLOUDFRONT 範圍）的 web ACL 只能關聯 CloudFront，不能關聯 ALB；ALB 要用 regional web ACL。而且即使 ALB 掛上 WAF，攻擊者仍能直接打到 ALB。
>
> **B ✗** 攻擊來源 IP 大量且會變化，逐一封鎖不可行；NACL 規則數量也有限。
>
> **C ✓** Managed prefix list 讓 ALB 只接受來自 CloudFront 的連線，直接連線會被 security group 擋下；秘密 header 再確保請求來自「你的」distribution，而不是別人建立的 CloudFront。兩者合用即可在不改架構下阻止繞過。若之後能改架構，CloudFront VPC origins 可讓 ALB 改為 internal。
>
> **D ✗** GuardDuty 只偵測不阻擋，Runtime Monitoring 也不是用在 ALB 上的功能。
>
> **考點**：SAP-3.2、SAP-1.2｜保護 origin 不被繞過
