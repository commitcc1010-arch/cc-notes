# 第 15 章　加密與機密：KMS、CloudHSM、Secrets Manager 與 ACM

> [!abstract] 本章地圖
> **你會學到**：
> - 用 envelope encryption 解釋 S3、EBS、RDS 背後「加密資料」與「保護金鑰」是怎麼分工的
> - 選擇 AWS owned、AWS managed 或 customer managed KMS key，並寫出正確的 key policy
> - 設定跨帳號使用 KMS key、multi-Region key，並說明輪替、停用與刪除對既有資料的影響
> - 比較 S3 的 SSE-S3、SSE-KMS、DSSE-KMS、SSE-C 與 client-side encryption，知道 S3 Bucket Key 如何省錢
> - 在 Secrets Manager 與 Parameter Store 之間做選擇，並設計資料庫密碼的自動輪替
> - 用 ACM 管理 TLS 憑證，避開 Region 與匯入憑證的常見陷阱
>
> **前置知識**：第 3 章（TLS 與憑證）、第 12 章（IAM policy 與 resource policy）、第 13 章（跨帳號存取）
> **考試比重**：SAA ★★★（Domain 1 資料安全控制）｜SAP ★★★（Domain 1、2 安全控制）

## 15.1 故事：稽核員的三個問題

Wanderly 開始接受信用卡付款後，第一次 PCI DSS 稽核來了。稽核員坐下來，問了平台團隊三個問題。

第一個問題：「資料庫裡的卡片 token 與訂單資料有加密嗎？誰能解密？如果某位離職員工曾經有權限，你們怎麼證明他現在不能解密？」團隊回答 RDS 有勾選加密，但說不清楚金鑰在哪裡、誰能用。

第二個問題：「應用程式怎麼連資料庫？密碼存在哪裡？上一次換密碼是什麼時候？」答案有點尷尬：密碼寫在 EC2 的環境變數裡，三年沒換過，因為換密碼要停機改設定。

第三個問題：「上個月網站因為憑證過期中斷了兩小時，現在怎麼避免再發生？」那張憑證是向外部 CA 買的，手動安裝在 ALB 上，負責續約的同事剛好離職了。

這三個問題剛好對應本章的三條主線：**加密金鑰怎麼管（KMS、CloudHSM）**、**機密怎麼存與怎麼換（Secrets Manager、Parameter Store）**、**憑證怎麼自動續約（ACM）**。我們先從最基礎的加密概念開始，因為不了解 envelope encryption，就很難看懂 AWS 各服務的加密選項。

## 15.2 加密基礎：你需要知道的最少密碼學

### 保護的是哪一段：at rest 與 in transit

**加密（encryption）** 是用一把 **金鑰（key）** 把可讀的 **明文（plaintext）** 轉換成無法理解的 **密文（ciphertext）**；只有拿到正確金鑰的人，才能 **解密（decryption）** 回明文。資料在兩種狀態下需要保護：

- **Encryption at rest（靜態加密）**：資料存放在磁碟、資料庫、S3、備份裡時是加密的。防的是「有人拿到儲存媒體或備份檔」。
- **Encryption in transit（傳輸加密）**：資料在網路上傳送時是加密的，通常靠 TLS（第 3 章）。防的是「有人在網路中間竊聽或竄改」。

兩者互不取代。RDS 開了靜態加密，但應用程式用明文連線，密碼與查詢結果仍會在網路上裸奔；反過來，只開 TLS，備份檔外洩時資料一樣被看光。

### 對稱與非對稱

| 類型 | 原理 | 特性 | 典型用途 |
|---|---|---|---|
| **對稱加密（symmetric）** | 加密與解密使用同一把金鑰，例如 AES-256 | 速度快、適合大量資料；難題是「怎麼安全地把金鑰交給對方」 | 磁碟、資料庫、S3 物件加密 |
| **非對稱加密（asymmetric）** | 一對金鑰：public key 加密或驗章，private key 解密或簽章，例如 RSA、ECC | 速度慢；public key 可以公開，解決了金鑰交換問題 | TLS 握手、數位簽章、讓外部對象加密資料給你 |

TLS 就是兩者的組合：先用非對稱加密安全地協商出一把臨時的對稱金鑰，之後的大量傳輸用對稱加密。這個「用一種方法保護金鑰、用另一種方法加密資料」的想法，等一下在 envelope encryption 會再出現。

### 真正難的是金鑰管理

AES-256 本身幾乎不可能被暴力破解，現實中的資料外洩幾乎都不是演算法被破，而是**金鑰被偷、被誤用、或沒人知道誰能用**。所以實務上的問題是：

- 金鑰存在哪裡？會不會跟資料放在一起？
- 誰能使用金鑰？怎麼撤銷？
- 每次使用有沒有紀錄？
- 金鑰要不要定期更換？舊資料怎麼辦？

AWS KMS 就是為了回答這些問題而存在。

## 15.3 AWS KMS：集中管理金鑰的服務

### KMS 做什麼

**AWS KMS（Key Management Service）** 是一個受管的金鑰管理服務。它把金鑰保存在經 FIPS 140 驗證的 **HSM（Hardware Security Module，硬體安全模組，專門保護金鑰的防竄改硬體）** 中，金鑰材料不會以明文離開 KMS。你從來不會「拿到」KMS key 本身，只能呼叫 KMS API 請它代為加密、解密、產生 data key 或簽章。

KMS 有三個讓它成為 AWS 加密核心的特性：

1. **和 AWS 服務深度整合**：S3、EBS、RDS、DynamoDB、Lambda、Secrets Manager 等上百個服務都能直接指定 KMS key 加密資料。
2. **以 policy 控制使用權**：每把 key 都有 key policy，可以精確控制誰能管理、誰能使用（15.5 節）。
3. **所有使用都記錄在 CloudTrail**：每次 `Decrypt`、`GenerateDataKey` 都會留下紀錄，可以回答稽核員「誰在什麼時候解密了什麼」。

KMS key 是 **Regional** 資源：在東京建立的 key 只存在東京，不能直接在新加坡使用（multi-Region key 是例外，見 15.8 節）。

### KMS key 的類型

依用途，KMS key 分成幾種 **key spec**：

- **Symmetric encryption key**（預設，`SYMMETRIC_DEFAULT`）：256-bit 對稱金鑰，AWS 服務整合幾乎都用這種。
- **Asymmetric key**：RSA 或 ECC 金鑰對，用於簽章驗章，或讓 AWS 之外的對象用 public key 加密資料。你可以下載 public key，private key 永遠留在 KMS。
- **HMAC key**：產生與驗證訊息驗證碼，用來確認資料沒有被竄改。

### 誰擁有這把 key：三種擁有權

考試最常考的是「擁有權」分類：

| 類型 | 誰建立與管理 | 能否看到與稽核 | Key policy 可否修改 | 輪替 | 跨帳號使用 | 費用 |
|---|---|---|---|---|---|---|
| **AWS owned key** | AWS 服務自己，跨多個客戶帳號使用 | 你的帳號看不到，也沒有 CloudTrail 紀錄 | 不能 | 由 AWS 決定 | 不能 | 免費 |
| **AWS managed key** | AWS 服務代你在你的帳號建立，別名如 `aws/s3`、`aws/ebs`、`aws/rds` | 看得到，使用會記錄在 CloudTrail | 不能 | 每年自動輪替，不能關閉 | 不能（key policy 改不了） | 不收月費，使用時依請求量計費 |
| **Customer managed key** | 你自己 | 看得到，完整稽核 | 可以 | 可選自動輪替，可設定週期，也能隨選輪替 | 可以 | 每把 key 有月費，加上請求費 |

選擇的依據不是「哪個比較安全」，三者的加密強度相同；差別在於**控制權**。只要題目出現下列任一需求，就要用 customer managed key：

- 要自訂誰能使用（例如只有付款服務的 role 能解密）
- 要跨帳號分享加密的資源（例如分享加密的 EBS snapshot、AMI 或 RDS snapshot）
- 要控制輪替週期、能停用或排程刪除
- 要使用 imported key material 或 custom key store

> [!note] 新服務趨勢
> 近年許多 AWS 服務的預設加密改用 AWS owned key，而不是在你帳號裡建立 AWS managed key。這不影響安全性，但代表你在 CloudTrail 看不到這些服務的金鑰使用紀錄。稽核要求「看得到每次解密」時，一樣要改用 customer managed key。

### Alias 與 key ID

每把 KMS key 有一個唯一的 **key ID**（例如 `1234abcd-12ab-34cd-56ef-1234567890ab`）與 **key ARN**。為了方便人與程式使用，可以替 key 取 **alias（別名）**，例如 `alias/wanderly-payments`。Alias 可以隨時改指向另一把 key，應用程式只認 alias，就能在不改程式的情況下換 key（15.7 節手動輪替會用到）。Alias 只是名稱，刪除 alias 不會刪除 key，alias 本身也沒有權限控制的效果。

## 15.4 Envelope encryption：KMS 為什麼不直接加密你的資料

### KMS 的直接加密有限制

KMS 的 `Encrypt` API 一次最多只能加密 **4 KB** 的資料。這是刻意的設計：如果每個 5 GB 的影片都要整個傳到 KMS 加密，網路延遲、頻寬與 KMS 的負載都會無法承受。所以 KMS 的主要工作不是加密資料，而是**保護加密資料用的金鑰**。

### Envelope encryption 的流程

**Envelope encryption（信封加密）** 是「用 data key 加密資料，再用 KMS key 加密 data key」的做法。**Data key（資料金鑰）** 是 KMS 產生的一把對稱金鑰，真正拿來在本地加密大量資料。

```text
【加密】
應用程式 ── ① GenerateDataKey(KeyId=alias/wanderly-photos) ──► KMS
         ◄── ② 回傳兩份 data key：
                 ・plaintext data key（明文）
                 ・encrypted data key（已用 KMS key 加密）
   │
   ③ 用 plaintext data key 在本地以 AES 加密 5 GB 檔案
   ④ 立刻從記憶體清除 plaintext data key
   ⑤ 儲存：[密文檔案] + [encrypted data key]（放在一起，例如 metadata 或檔頭）

【解密】
應用程式 ── ⑥ Decrypt(encrypted data key) ──► KMS
                                    （KMS 檢查 key policy、記錄 CloudTrail）
         ◄── ⑦ 回傳 plaintext data key
   │
   ⑧ 在本地解密檔案，用完清除 plaintext data key
```

① 應用程式請 KMS 產生一把 data key，指定要用哪把 KMS key 保護它。② KMS 同時回傳明文與加密後的 data key。③ 大量資料在本地加密，不經過 KMS，速度快。④ 明文 data key 只短暫存在記憶體。⑤ 加密後的 data key 和密文存在一起，沒有 KMS 就打不開，所以放在一起是安全的，就像把上鎖的鑰匙盒和保險箱放在一起，鑰匙盒的鑰匙在 KMS 手上。⑥⑦ 解密時只需要把小小的 encrypted data key 送給 KMS 解開，這一步會檢查呼叫者的權限並留下紀錄。⑧ 用明文 data key 在本地解密資料。

這個設計帶來三個好處：

- **效能**：大量資料在本地加密，KMS 只處理幾百 bytes 的 data key。
- **集中控制**：誰能解密資料，等於誰能呼叫 KMS `Decrypt`，由 key policy 控制，撤銷權限立即生效。
- **可稽核**：每一次解密 data key 都在 CloudTrail 留下紀錄。

S3 的 SSE-KMS、EBS 加密、RDS 加密，背後都是這個流程，只是由 AWS 服務代你呼叫 KMS。若要自己在應用程式中實作，建議使用 **AWS Encryption SDK**，它會處理 data key 的產生、密文格式與 encrypted data key 的保存，還能快取 data key 以減少 KMS 呼叫次數。

### Encryption context：把密文綁在情境上

**Encryption context（加密情境）** 是加密時附帶的一組 key-value，例如 `{"tenant": "wanderly-tw", "orderId": "8812"}`。它不是秘密，不會被加密，但 KMS 會把它當作驗證資料綁進密文：**解密時必須提供完全相同的 encryption context，否則解密失敗**。

這有兩個用途。第一，防止密文被搬到別的情境使用，例如把 A 租戶的密文換到 B 租戶的紀錄下，因為 context 不同而解不開。第二，encryption context 會出現在 CloudTrail 紀錄中，讓稽核知道「解密的是哪個租戶的哪筆訂單」，也可以在 key policy 用 `kms:EncryptionContext:` 條件限制只能解密特定情境的資料。

## 15.5 誰能使用這把 key：key policy、IAM 與 grants

### Key policy 是一切的起點

**Key policy（金鑰政策）** 是附加在每把 KMS key 上的 resource-based policy。它和 S3 bucket policy 很像，但有一個關鍵差異：**KMS key 的存取一定要由 key policy 允許**。在 S3，帳號內的 IAM policy 就足以授權存取同帳號的 bucket；在 KMS，如果 key policy 沒有開啟這條路，IAM policy 寫什麼都沒用。

建立 customer managed key 時，預設的 key policy 包含這一段：

```json
{
  "Sid": "EnableIAMUserPermissions",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::111122223333:root"
  },
  "Action": "kms:*",
  "Resource": "*"
}
```

這段最常被誤解。`arn:aws:iam::111122223333:root` 在這裡代表的是**整個帳號**，不是 root user。它的意思是：「這把 key 信任帳號 `111122223333` 的 IAM，讓 IAM policy 可以決定帳號內誰能使用這把 key。」有了這段，帳號內的 role 只要 IAM policy 允許 `kms:Decrypt`，就能解密；沒有這段，就只有 key policy 裡直接列名的 principal 能使用 key。

Key policy 中的 `"Resource": "*"` 指的是「這把 key 本身」，不是帳號裡所有的 key，因為 key policy 只附加在一把 key 上。

### 分離管理者與使用者

Wanderly 的付款 key 要求「管理 key 的人不能解密資料，能解密的應用程式不能改 key 設定」，這是**職責分離（separation of duties）**。完整的 key policy：

```json
{
  "Version": "2012-10-17",
  "Id": "wanderly-payments-key-policy",
  "Statement": [
    {
      "Sid": "EnableIAMPolicies",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:root"
      },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "AllowKeyAdministration",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/SecurityKeyAdmin"
      },
      "Action": [
        "kms:Create*",
        "kms:Describe*",
        "kms:Enable*",
        "kms:List*",
        "kms:Put*",
        "kms:Update*",
        "kms:Revoke*",
        "kms:Disable*",
        "kms:Get*",
        "kms:Delete*",
        "kms:TagResource",
        "kms:UntagResource",
        "kms:ScheduleKeyDeletion",
        "kms:CancelKeyDeletion",
        "kms:RotateKeyOnDemand"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AllowPaymentsAppUseViaS3",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/PaymentsApp"
      },
      "Action": [
        "kms:Decrypt",
        "kms:GenerateDataKey",
        "kms:DescribeKey"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "s3.ap-northeast-1.amazonaws.com"
        }
      }
    },
    {
      "Sid": "AllowAttachmentOfPersistentResources",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/PaymentsApp"
      },
      "Action": [
        "kms:CreateGrant",
        "kms:ListGrants",
        "kms:RevokeGrant"
      ],
      "Resource": "*",
      "Condition": {
        "Bool": {
          "kms:GrantIsForAWSResource": "true"
        }
      }
    }
  ]
}
```

逐段說明：

- **`EnableIAMPolicies`**：保留讓 IAM 參與授權的路徑，也避免 key 因為 policy 寫錯而變成沒人能管理（unmanageable）。若公司要求「只有 key policy 能授權」，可以拿掉這段，但必須確保 key policy 裡有人能管理 key。
- **`AllowKeyAdministration`**：資安的 key 管理員能管理、停用、排程刪除 key，但動作清單裡**沒有** `kms:Decrypt`、`kms:Encrypt`、`kms:GenerateDataKey`，所以他無法直接解密付款資料。要注意這份清單是 AWS 主控台預設的管理員陳述，其中 `kms:Put*` 包含 `PutKeyPolicy`、`kms:Create*` 包含 `CreateGrant`：管理員仍有能力改 key policy 或建立 grant 把解密權限加給自己。要求嚴格職責分離時，要把這兩個動作從日常管理 role 拿掉（或改由另一個 role 執行），並用 CloudTrail 監控 `PutKeyPolicy`、`CreateGrant` 事件。
- **`AllowPaymentsAppUseViaS3`**：付款應用程式只能透過東京 Region 的 S3 使用這把 key，也就是讀寫以 SSE-KMS 加密的付款報表（15.10 節）。`kms:ViaService` 條件要求請求必須是 AWS 服務（這裡是 S3）代表應用程式發出，所以這段陳述不允許應用程式直接呼叫 `kms:Decrypt` 解開其他用這把 key 加密的東西。不過因為第一段 `EnableIAMPolicies` 讓 IAM 也能授權，前提是 `PaymentsApp` 的 IAM policy 沒有另外給它不帶條件的 `kms:Decrypt`；key policy 與 IAM policy 任一邊的 Allow 都會生效。
- **`AllowAttachmentOfPersistentResources`**：允許建立 grant，但限定 grant 是給 AWS 資源使用的（`kms:GrantIsForAWSResource`），下一段說明 grant 是什麼。

> [!warning] 常見誤解
> 「把 KMS 權限加到 IAM policy 就夠了。」只有在 key policy 包含信任帳號的 `EnableIAMPolicies` 這類陳述時才成立。題目描述「IAM policy 已允許 kms:Decrypt，仍然 AccessDenied」，第一個要檢查的就是 key policy。

### Grants：給 AWS 服務的臨時授權

**Grant（授權）** 是另一種授權機制：它讓某個 principal 在某把 key 上執行指定的動作，可以加上條件（例如只限特定 encryption context），而且隨時可以撤銷（revoke）或由使用者自行退休（retire）。和修改 key policy 相比，grant 適合**大量、短期、程式化**的授權。

最常見的使用者是 AWS 服務本身。例如 EBS：當你把一個加密的 volume 掛到 EC2 時，EBS 會建立一個 grant，讓這台 instance 所在的主機可以解密這個 volume 的 data key；volume 卸載後 grant 就被退休。你不需要每掛一個 volume 就改一次 key policy。

用 CLI 建立一個 grant，讓批次處理 role 只能解密 `tenant=wanderly-tw` 的資料：

```bash
aws kms create-grant \
  --key-id arn:aws:kms:ap-northeast-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --grantee-principal arn:aws:iam::111122223333:role/BatchWorker \
  --operations Decrypt GenerateDataKey \
  --constraints '{"EncryptionContextSubset":{"tenant":"wanderly-tw"}}'
```

Grant 建立後需要短暫時間才會在所有地方生效（最終一致性）。若要立刻使用，可以在 API 呼叫中帶入建立 grant 時回傳的 **grant token**。

## 15.6 跨帳號使用 KMS key

第 14 章的多帳號架構帶來一個常見需求：`security-tooling` 帳號的 key 加密了日誌，`log-archive` 帳號要讀；或者 `shared-services` 帳號產出加密的 golden AMI，要分享給所有 workload 帳號。

### 兩邊都要同意

跨帳號使用 KMS key 需要**兩邊**的授權，和第 13 章的跨帳號 S3 存取同樣的道理：

1. **Key 所在帳號（A）的 key policy** 允許外部帳號（B）或 B 裡的特定 role 使用這把 key。
2. **帳號 B 的 IAM policy** 允許它的 role 對 A 的 key ARN 執行對應動作。

帳號 A 的 key policy 加入：

```json
[
  {
    "Sid": "AllowAccountBToUseKey",
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::444455556666:root"
    },
    "Action": [
      "kms:Decrypt",
      "kms:DescribeKey",
      "kms:ReEncrypt*",
      "kms:GenerateDataKey*"
    ],
    "Resource": "*"
  },
  {
    "Sid": "AllowAccountBToCreateGrantsForAwsResources",
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::444455556666:root"
    },
    "Action": "kms:CreateGrant",
    "Resource": "*",
    "Condition": {
      "Bool": {
        "kms:GrantIsForAWSResource": "true"
      }
    }
  }
]
```

（以上兩段陳述要加進 key policy 的 `Statement` 陣列中。）

帳號 B 的 role 附加：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UseSharedAmiKeyFromAccountA",
      "Effect": "Allow",
      "Action": [
        "kms:Decrypt",
        "kms:DescribeKey",
        "kms:ReEncrypt*",
        "kms:GenerateDataKey*",
        "kms:CreateGrant"
      ],
      "Resource": "arn:aws:kms:ap-northeast-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab"
    }
  ]
}
```

在 key policy 寫帳號 B 的 `root`，表示「信任帳號 B 自己決定把權限給誰」，B 的管理員再用 IAM policy 分配給特定 role。若只想授權 B 的某一個 role，可以在 key policy 直接寫那個 role 的 ARN。跨帳號呼叫時必須使用 **key ARN**（或 alias ARN），不能只寫 key ID 或 alias 名稱，因為 KMS 會在呼叫者自己的帳號裡找。

`kms:CreateGrant` 在這個例子中是必要的：帳號 B 用分享來的加密 AMI 啟動 EC2 時，EBS 要建立 grant 才能解密 volume；加上 `kms:GrantIsForAWSResource` 條件，讓帳號 B 只能透過 AWS 服務建立 grant，不能自己任意建立。`kms:ReEncrypt*` 與 `kms:GenerateDataKey*` 則是 EBS 從 snapshot 建立 volume、或把 snapshot 複製成帳號 B 自己的 key 時需要的動作（AWS 文件列出的分享 snapshot 所需權限為 `DescribeKey`、`CreateGrant`、`GenerateDataKey`、`GenerateDataKeyWithoutPlaintext`、`ReEncrypt`、`Decrypt`）。

### AWS managed key 不能跨帳號

這是考試非常愛考的陷阱。**AWS managed key（例如 `aws/ebs`、`aws/rds`）的 key policy 不能修改**，所以無法授權其他帳號使用。用 `aws/ebs` 加密的 snapshot 或 AMI **不能直接分享給其他帳號**。正確做法：

1. 在來源帳號建立一把 customer managed key，並在 key policy 授權目標帳號。
2. 用 `copy-snapshot`（或 AMI copy）把 snapshot 重新加密成這把 customer managed key。
3. 分享新的 snapshot 給目標帳號，目標帳號通常會再複製一份用自己的 key 加密，避免長期依賴來源帳號的 key。

RDS 加密 snapshot 的跨帳號分享也是同樣的流程（第 26 章）。

## 15.7 Key 的生命週期：輪替、停用與刪除

### 自動輪替做了什麼

**Key rotation（金鑰輪替）** 是定期更換金鑰材料，降低單一金鑰材料長期使用的風險。KMS 的自動輪替對 customer managed 的對稱 key 可以啟用，預設每 365 天一次，也可以設定 90 天到 2,560 天之間的週期；另外還能用 `RotateKeyOnDemand` 隨選（on-demand）立即輪替，隨選輪替不影響原本的自動輪替排程，且次數有上限。AWS managed key 則每年自動輪替，不能關閉也不能調整。費用方面，輪替會讓這把 key 的月費增加，但只計算前兩次輪替，之後的輪替不再加價。

輪替的運作方式是理解考題的關鍵：

- 輪替後，**key ID、key ARN、alias、key policy 都不變**，應用程式完全不用改。
- KMS 為這把 key 產生新的金鑰材料，**之後的加密使用新材料**。
- **舊的金鑰材料會一直保留**，所以用舊材料加密的資料仍然可以解密。KMS 從密文中就知道該用哪一版材料。
- **既有資料不會被重新加密**。如果法規要求「舊資料也要用新金鑰重加密」，必須自己做資料遷移。

自動輪替只支援由 KMS 產生材料的對稱 key。使用 imported key material 的對稱 key 不能自動輪替，但可以匯入新材料後執行隨選輪替。非對稱 key、HMAC key 與 custom key store 中的 key 則自動與隨選輪替都不支援，需要**手動輪替**：建立一把新 key，把 alias 改指向新 key，讓新資料用新 key 加密；舊 key 保留給舊資料解密使用，直到確認所有舊資料都已遷移。

### 停用與排程刪除

- **Disable（停用）**：key 暫時不能用於任何加密操作，可以隨時重新啟用。適合「懷疑這把 key 已經沒人用，先停用觀察」。
- **Schedule key deletion（排程刪除）**：KMS 不允許立即刪除 key，必須設定 **7 到 30 天的等待期**（預設 30 天）。等待期間 key 處於 pending deletion 狀態、不能使用，可以取消。等待期結束後，**金鑰材料被永久刪除，所有用它加密的資料都永遠無法解密**，AWS 也無法恢復。

Wanderly 的刪除流程：先停用 key、設定 CloudWatch alarm 監控 CloudTrail 中針對這把 key 的嘗試使用（停用期間的使用嘗試會失敗並留下紀錄），觀察一段足夠長的時間，再排程刪除，並盤點所有備份、snapshot、跨 Region 副本是否還依賴它。要特別注意每年才執行一次的作業，例如年度結帳或 DR 演練，觀察期太短可能看不到它們。

## 15.8 Multi-Region key、imported key material 與 custom key store

### Multi-Region key

一般的 KMS key 只存在一個 Region。如果 Wanderly 在東京用 client-side encryption 加密資料後複製到新加坡，新加坡的應用程式要解密，就得跨 Region 呼叫東京的 KMS，東京故障時就解不開。

**Multi-Region key（多 Region 金鑰）** 是一組在不同 Region、但擁有**相同 key ID 與相同金鑰材料**的 KMS key：一把 **primary key** 加上在其他 Region 建立的 **replica key**。Key ID 以 `mrk-` 開頭。用東京的 primary 加密的資料，可以直接在新加坡用 replica 解密，不需要跨 Region 呼叫。

要注意的是什麼會同步、什麼不會：

| 屬性 | 是否在相關 key 之間共享 |
|---|---|
| Key ID、金鑰材料、key spec | 共享 |
| 自動輪替的設定與新材料 | 由 primary 控制並同步到 replica |
| Key policy、grants、alias、tag、啟用狀態 | **不共享**，每個 Region 各自管理 |

Multi-Region key 適合 client-side encryption 且資料跨 Region 流動、全球資料簽章驗章、DynamoDB global tables 搭配應用層加密等情境（第 42 章）。它不會幫你複製任何資料。至於 S3 Cross-Region Replication、Aurora Global Database 這類 AWS 服務的跨 Region 複寫，服務本身會在目的 Region 用目的地的 key 重新加密，用一般的單 Region key 就足夠；AWS 建議只在確實需要時才使用 multi-Region key，因為同一份金鑰材料存在多個 Region，也代表更大的管理範圍。

### Imported key material（BYOK）

有些法規要求「金鑰材料必須由我們自己產生」。KMS 允許建立一把沒有金鑰材料的 key（origin 為 `EXTERNAL`），再把你在自己的 HSM 產生的金鑰材料加密後匯入，這稱為 **BYOK（Bring Your Own Key）**。

代價是更多責任：你必須自己安全保存原始金鑰材料的副本；可以為匯入的材料設定到期時間，到期後 KMS 會刪除它，key 就不能用，直到你重新匯入**同一份**材料；也可以隨時主動刪除材料，達到立即讓資料無法解密的效果。若 KMS 中的材料被刪除而你手上沒有副本，資料就永遠無法解密。

### Custom key store

如果法規要求「金鑰必須存在我們專屬控制的 HSM」，KMS 提供 **custom key store（自訂金鑰存放區）**：

- **AWS CloudHSM key store**：KMS key 的金鑰材料存在你自己的 CloudHSM cluster 中。應用程式與 AWS 服務仍然透過 KMS API 使用 key，享有 KMS 的服務整合與 IAM 控制。
- **External key store（XKS）**：金鑰存在 AWS 之外、你自己的金鑰管理系統中，KMS 每次加解密都要透過 proxy 呼叫外部系統。

兩者都讓你取得更直接的金鑰控制權，但也把可用性、延遲與營運責任轉到你身上：你的 CloudHSM cluster 或外部系統故障時，依賴這些 key 的 AWS 服務也會失敗。

## 15.9 CloudHSM：需要專屬硬體時

### CloudHSM 是什麼

**AWS CloudHSM** 提供在你的 VPC 中執行、**單一租戶（single-tenant）** 的 HSM。和 KMS 最大的差別在於控制權：KMS 由 AWS 管理金鑰與存取控制，你透過 IAM 與 key policy 授權；CloudHSM 由你自己建立 HSM 上的使用者、自己管理金鑰，**AWS 無法存取你的金鑰**。如果你遺失了 HSM 使用者的憑證，AWS 也無法幫你取回。

### 運作方式

- HSM 以 **cluster** 形式部署在你 VPC 的 subnet 中，每個 HSM 位於一個 AZ。為了高可用，AWS 建議**至少兩個 HSM，分散在不同 AZ**；cluster 會自動在 HSM 之間同步金鑰。
- 應用程式透過 CloudHSM 的 client SDK，以業界標準介面使用金鑰：**PKCS #11**、**JCE（Java）**、**OpenSSL Dynamic Engine**、**Microsoft CNG／KSP**。
- AWS 負責硬體、修補 HSM 韌體與自動備份；你負責 HSM 使用者、金鑰、應用整合與容量規劃。

### 何時選 CloudHSM

| 需求 | 選擇 |
|---|---|
| AWS 服務（S3、EBS、RDS）的靜態加密，營運負擔最低 | KMS |
| 法規要求單一租戶 HSM，且金鑰只能由我們控制、雲端供應商不能存取 | CloudHSM |
| 需要 PKCS #11、JCE、CNG 等標準介面，例如自建的 PKI | CloudHSM |
| SSL/TLS offload：讓 web server 把 TLS 私鑰運算交給 HSM | CloudHSM |
| Oracle 或 SQL Server 的 TDE（Transparent Data Encryption）把主金鑰存在 HSM | CloudHSM |
| 想要專屬 HSM 的控制，又想讓 S3、EBS 等服務直接使用 | KMS custom key store（底層用 CloudHSM） |
| 需要非對稱 key 簽章，但不需要專屬硬體 | KMS asymmetric key |

> [!tip] 考試提示
> 關鍵字「single-tenant」「dedicated HSM」「customer has exclusive control of keys」「AWS cannot access the keys」「PKCS #11」指向 CloudHSM。關鍵字「integrated with AWS services」「least operational overhead」「audit with CloudTrail」指向 KMS。

KMS 與 CloudHSM 處理的是「金鑰」。接下來看金鑰最常用的地方之一：S3。

## 15.10 S3 加密選項全解

### 預設已經加密

自 2023 年 1 月起，所有新上傳到 S3 的物件都會自動以 **SSE-S3** 加密，新建 bucket 的預設加密也是 SSE-S3（第 22 章）。所以考題的重點不再是「有沒有加密」，而是「用哪種方式加密，才能滿足控制、稽核或合規要求」。

### 五種方式

| 方式 | 誰管金鑰 | 怎麼運作 | 適合 |
|---|---|---|---|
| **SSE-S3** | S3 自己 | S3 以每個物件的金鑰加密，再由 S3 管理的主金鑰保護；你看不到也控制不到這些金鑰 | 預設、零設定、沒有特別稽核要求 |
| **SSE-KMS** | KMS（AWS managed `aws/s3` 或 customer managed key） | S3 呼叫 KMS 產生 data key 做 envelope encryption | 要控制誰能解密、要 CloudTrail 稽核每次解密、要職責分離 |
| **DSSE-KMS** | KMS | 雙層伺服器端加密：用兩層不同實作的加密保護物件 | 法規明確要求多層加密（例如特定政府標準） |
| **SSE-C** | 你自己（每次請求提供） | 每次 PUT／GET 都在 header 帶上你的金鑰，S3 用它加解密後即丟棄，只保存金鑰的雜湊用來驗證 | 必須自行保管金鑰、但希望由 S3 執行加密運算；必須用 HTTPS。自 2026 年 4 月起新 bucket 預設封鎖 SSE-C，要使用必須先在 bucket 預設加密設定中明確解除封鎖 |
| **Client-side encryption** | 你自己（或用 KMS 搭配 Encryption SDK） | 資料在上傳前就在應用程式加密，S3 只收到密文 | 要求 AWS 永遠看不到明文 |

SSE-KMS 的一個重要特性：**讀取者除了 `s3:GetObject`，還需要對那把 KMS key 的 `kms:Decrypt` 權限**；上傳者需要 `kms:GenerateDataKey`。這讓 SSE-KMS 多了一層獨立的存取控制：即使 bucket policy 寫錯讓別人能 `GetObject`，沒有 KMS 權限也讀不到內容。這也是為什麼跨帳號讀取 SSE-KMS 物件時，除了 bucket policy，還要在 key policy 授權對方帳號，而且不能用 `aws/s3` 這把 AWS managed key。

### SSE-KMS 的成本與配額：S3 Bucket Key

SSE-KMS 的每次上傳與讀取都要呼叫 KMS，會產生 KMS 請求費用，而且 KMS 每個帳號每個 Region 的請求速率有配額（預設值，依 Region 不同，可申請提高）。Wanderly 的照片 bucket 每秒有數千次讀取，很快就遇到 `ThrottlingException`。

**S3 Bucket Key** 是解法：S3 向 KMS 取得一把 **bucket 層級的金鑰**，在一段時間內用它在 S3 內部產生各物件的 data key，而不是每個物件都呼叫 KMS。效果是 KMS 請求量大幅下降（AWS 說最多可降低 99% 的 KMS 請求成本），也就降低了被 throttle 的機率。

開啟 Bucket Key 後要注意：CloudTrail 中 KMS 事件的 encryption context 會變成 **bucket ARN** 而不是物件 ARN，如果你的 key policy 或 IAM 條件是用物件 ARN 的 encryption context 寫的，就需要調整；CloudTrail 中的 KMS 事件也會明顯變少。Bucket Key 只對開啟後的新物件生效，而且不支援 DSSE-KMS。

### 用 bucket policy 強制加密方式與 TLS

Wanderly 的付款報表 bucket 要求「只能用指定的 customer managed key 加密，且只能透過 HTTPS 存取」：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyNonKmsEncryptionHeader",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::wanderly-payments-reports/*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        }
      }
    },
    {
      "Sid": "DenyWrongKmsKey",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::wanderly-payments-reports/*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:ap-northeast-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab"
        }
      }
    },
    {
      "Sid": "DenyKmsWithoutKeyId",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::wanderly-payments-reports/*",
      "Condition": {
        "StringEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        },
        "Null": {
          "s3:x-amz-server-side-encryption-aws-kms-key-id": "true"
        }
      }
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::wanderly-payments-reports",
        "arn:aws:s3:::wanderly-payments-reports/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
```

這份 policy 搭配「bucket 預設加密設為 SSE-KMS＋這把 customer managed key」使用，前三段一起堵住上傳者自己指定加密方式的漏洞：

- **`DenyNonKmsEncryptionHeader`**：請求若帶了加密 header 但不是 `aws:kms`（例如 `AES256` 代表 SSE-S3），就拒絕。
- **`DenyWrongKmsKey`**：請求若指定了其他 KMS key，就拒絕。
- **`DenyKmsWithoutKeyId`**：請求寫了 `aws:kms` 卻沒指定 key ID 時，S3 會改用 AWS managed key `aws/s3`，而不是 bucket 預設的 key，所以也要拒絕。

前兩段使用 `IfExists`，是因為完全沒有帶加密 header 的請求會由 bucket 預設加密套用正確的 key，不應該被擋。最後一段：`aws:SecureTransport` 為 false 代表請求沒有使用 TLS，一律拒絕，這是「encryption in transit」的標準寫法。至於 SSE-C 使用另一組 header，這份 policy 擋不到；但自 2026 年 4 月起新 bucket 預設就封鎖 SSE-C，只要不主動解除封鎖即可。

> [!warning] 常見誤解
> 「修改 bucket 的預設加密後，既有物件會被重新加密。」不會。預設加密只影響之後的新物件。要把既有物件改用新的 key，需要重新複製物件，大量物件可以用 S3 Batch Operations 的 copy 作業（第 23 章）。

## 15.11 Secrets Manager：把密碼從程式碼裡拿出來

回到稽核員的第二個問題。資料庫密碼寫在環境變數裡有三個問題：任何能看到 instance 設定或 launch template 的人都能看到密碼；密碼會跟著 AMI、log、程式碼庫散落各處；要換密碼必須修改所有地方並重啟，所以沒人敢換。

### Secrets Manager 是什麼

**AWS Secrets Manager** 是專門保存 **secret（機密，例如資料庫帳密、API key、OAuth token）** 的受管服務。應用程式在執行時透過 API 取得 secret，不再把它寫在任何設定檔裡。它的主要功能：

- **以 KMS 加密保存**：每個 secret 用 KMS key 加密（預設 `aws/secretsmanager`，也可指定 customer managed key）。
- **精細的存取控制**：用 IAM 與 secret 的 resource policy 控制誰能讀；讀取需要 `secretsmanager:GetSecretValue`，以及對該 KMS key 的 `kms:Decrypt`。
- **自動輪替（rotation）**：依排程自動更換密碼，並同步更新資料庫。
- **版本管理**：每次更新保留版本，透過 staging label 區分新舊。
- **跨 Region 複寫**：把 secret 複寫到其他 Region，供 DR 使用。
- **稽核**：每次讀取都記錄在 CloudTrail。

Secrets Manager 依 secret 數量按月計費，加上 API 呼叫費用。

### 自動輪替怎麼運作

輪替由一個 **rotation Lambda function** 執行（對 RDS、Aurora、Redshift、DocumentDB 等，AWS 提供現成的 rotation function template，也有由服務代管的 managed rotation）。每次輪替依序執行四個步驟：

```text
                 Secrets Manager                          資料庫
                       │
 ① createSecret  ──── 產生新密碼，存成新版本
                       標記為 AWSPENDING
                       │
 ② setSecret     ──── 用新密碼更新資料庫使用者 ─────────► ALTER USER ... PASSWORD
                       │
 ③ testSecret    ──── 用 AWSPENDING 版本實際登入 ───────► 測試連線成功？
                       │
 ④ finishSecret  ──── 把 AWSCURRENT 標籤移到新版本
                       舊版本改標為 AWSPREVIOUS
                       │
應用程式 GetSecretValue（預設取 AWSCURRENT）──► 拿到新密碼
```

① 產生新密碼並以 `AWSPENDING` 標籤保存，此時應用程式拿到的仍是舊的 `AWSCURRENT`。② 到資料庫把使用者密碼改成新值。③ 用新密碼實際登入，確認可用。④ 只有測試成功，才把 `AWSCURRENT` 指向新版本，舊版本標為 `AWSPREVIOUS`，必要時可以回退。

Rotation Lambda 要能連到資料庫，所以通常放在資料庫所在的 VPC；它還要呼叫 Secrets Manager API，所以需要 Secrets Manager 的 interface VPC endpoint 或 NAT Gateway（第 5、6 章）。這是輪替失敗最常見的原因。

輪替策略有兩種：

- **Single user（單一使用者）**：直接更改同一個資料庫使用者的密碼。簡單，但在 ②～④ 之間的短暫時間，用舊密碼建立新連線可能失敗。
- **Alternating users（交替使用者）**：準備兩個資料庫使用者輪流使用，輪替時更新「另一個」使用者的密碼再切換。切換期間舊使用者仍可用，適合不能容忍任何連線失敗的系統；需要一個有權限修改其他使用者的管理 secret。

> [!note] RDS 的整合方式
> RDS 與 Aurora 可以直接讓 Secrets Manager 管理 master user 密碼：建立資料庫時選擇由 Secrets Manager 管理，RDS 就會建立 secret 並自動輪替，不需要自己部署 rotation Lambda。

### 應用程式這一端：快取與重試

應用程式不應該每個請求都呼叫 `GetSecretValue`，那會增加延遲與費用，也可能遇到 API 節流。AWS 提供各語言的 **Secrets Manager caching client**，在記憶體中快取 secret 一段時間。搭配輪替時的正確做法是：用快取的密碼連線；如果驗證失敗，強制重新讀取一次 secret 再重試。這樣即使輪替剛完成、快取還是舊值，也能自動恢復。

### 跨 Region 複寫與跨帳號存取

**Replica secret** 讓 secret 在其他 Region 有一份同步的副本，primary 輪替後副本會自動更新。Wanderly 的新加坡 DR 環境直接讀取本地的 replica，東京故障時不必跨 Region 取密碼。需要時也可以把 replica **提升（promote）** 為獨立的 secret。

跨帳號讀取 secret 需要三件事：secret 的 **resource policy** 允許對方帳號的 role；secret 必須用 **customer managed key** 加密，且 key policy 允許對方 `kms:Decrypt`（用 `aws/secretsmanager` 的 secret 無法跨帳號讀取，原因同 15.6 節）；對方帳號的 IAM policy 也要允許。

## 15.12 Parameter Store：設定與簡單機密

### Parameter Store 是什麼

**AWS Systems Manager Parameter Store** 是 Systems Manager 的一個功能，用來集中保存設定值與機密。它支援三種參數型別：

- **String**：一般字串，例如 `/booking/prod/api-timeout-ms` = `3000`。
- **StringList**：以逗號分隔的字串清單。
- **SecureString**：用 KMS key 加密保存的字串，適合密碼或 token。讀取時帶 `--with-decryption` 才會解密，並需要 `kms:Decrypt` 權限。

參數可以用路徑組成 **階層**，例如 `/booking/prod/db/host`、`/booking/prod/db/password`。IAM policy 可以用路徑限制權限，例如 booking 服務只能讀 `/booking/prod/*`；應用程式可用 `GetParametersByPath` 一次讀取整個路徑。

### Standard 與 Advanced tier

| 比較 | Standard | Advanced |
|---|---|---|
| 每帳號每 Region 參數數量 | 10,000 | 100,000 |
| 單一參數大小 | 4 KB | 8 KB |
| Parameter policies（到期時間、到期前通知、未更新通知） | 不支援 | 支援 |
| 費用 | 儲存免費 | 按參數數量按月計費 |
| 跨帳號分享 | 不支援 | 可透過 AWS RAM 唯讀分享（SecureString 必須用 customer managed key 加密，並另外在 key policy 授權對方） |

Standard 參數可以升級為 Advanced，但 Advanced 不能降回 Standard。API 吞吐量另有預設上限，可以開啟較高的 throughput 設定（另外計費）。

### Secrets Manager vs Parameter Store

| 需求 | Secrets Manager | Parameter Store |
|---|---|---|
| 自動輪替資料庫密碼 | 內建（rotation Lambda、RDS 整合） | 沒有內建，需自己寫排程與程式 |
| 跨 Region 複寫 | 內建 replica | 沒有內建 |
| Resource policy 與跨帳號存取 | 支援 | 只有 Advanced 參數可透過 RAM 唯讀分享；Standard 參數不能跨帳號 |
| 一般設定值（非機密） | 不適合（每個 secret 都收費） | 最適合 |
| 成本 | 每個 secret 月費 + API 費 | Standard 免費 |
| 加密 | 一律以 KMS 加密 | 只有 SecureString 加密 |

選擇規則很簡單：**需要自動輪替、跨 Region 複寫或跨帳號存取的機密，用 Secrets Manager；一般設定與不需輪替的簡單機密，用 Parameter Store**。兩者也能並用：Parameter Store 可以透過 `/aws/reference/secretsmanager/<secret 名稱>` 這種路徑讀取 Secrets Manager 的 secret，讓應用程式只用一套 API。

> [!tip] 考試提示
> 題目出現「automatically rotate database credentials」，答案幾乎都是 Secrets Manager。題目出現「store configuration values」「hierarchical」「at no additional cost」，答案是 Parameter Store。

## 15.13 ACM：讓憑證不再過期

### 為什麼需要 ACM

回到稽核員的第三個問題。TLS 憑證（第 3 章）有到期日，到期後瀏覽器會拒絕連線。手動購買、安裝、續約憑證，很容易因為人員異動或忘記而出事。

**AWS Certificate Manager（ACM）** 提供、保存並**自動續約**TLS 憑證，並能直接部署到 AWS 服務上。ACM 簽發的 public 憑證用在 **整合服務**（Elastic Load Balancing、CloudFront、API Gateway 等）上時不另外收費。

### 證明網域是你的：驗證方式

申請 public 憑證時，ACM 要先確認你擁有這個網域：

- **DNS validation（DNS 驗證）**：ACM 給你一筆 CNAME 記錄，加到網域的 DNS 中。如果 DNS 在 Route 53，主控台可以一鍵建立。**只要這筆 CNAME 一直存在，而且憑證正在被使用，ACM 就會自動續約，不需要任何人工操作**。這是建議的做法。
- **Email validation（電子郵件驗證）**：ACM 寄信到網域的管理信箱，需要有人點擊確認；續約時也需要再次確認，容易因為沒人收信而失敗。

### 一定要記住的 Region 規則

ACM 憑證是 **Regional** 資源，只能用在同一個 Region 的服務上：

- 東京的 ALB 只能使用東京 Region 的 ACM 憑證。如果 ALB 部署在東京與新加坡，兩個 Region 都要各自申請（或匯入）憑證。
- **CloudFront 使用的憑證必須在 `us-east-1`（維吉尼亞北部）申請或匯入**，不論你的 origin 在哪裡（第 11 章）。
- API Gateway 的 edge-optimized endpoint 背後使用 CloudFront，所以憑證也要在 `us-east-1`；Regional endpoint 則用同 Region 的憑證（第 20 章）。

### 匯入的憑證不會自動續約

公司若因政策要向特定 CA 購買憑證（例如 EV 憑證），可以把憑證與私鑰**匯入（import）**ACM，再部署到 ALB 或 CloudFront。但 **ACM 不會為匯入的憑證續約**，到期前必須自己取得新憑證再重新匯入（re-import 到同一個 ARN，綁定的服務會自動使用新憑證）。

防止再次過期的做法：ACM 會在憑證到期前透過 **EventBridge** 發出事件（預設在到期前 45 天開始，可調整天數），可以觸發 SNS 通知或自動化流程；AWS Config 也有 `acm-certificate-expiration-check` 規則檢查即將到期的憑證。

### 私鑰與 EC2

ACM 傳統上**不讓你匯出 public 憑證的私鑰**，所以不能把 ACM public 憑證直接安裝在 EC2 的 Nginx 上，應該在 EC2 前面放 ALB，在 ALB 上終結 TLS（第 10 章）。AWS 在 2025 年推出了 **exportable public certificate（可匯出的 public 憑證）**：申請時就要選擇可匯出，之後可以匯出憑證、私鑰與憑證鏈，裝在 EC2、container 或地端伺服器上。這種憑證要另外付費；ACM 仍會自動續約並發出通知，但把新憑證部署到伺服器上是你的責任。考試題目仍以「ACM public 憑證掛在 ALB、CloudFront 等整合服務上」為主要情境。

### 私有憑證：AWS Private CA

公司內部的服務之間（例如微服務的 mTLS、內部網站、IoT 裝置身份）需要的憑證不必由公開 CA 簽發。**AWS Private CA** 讓你建立自己的私有 CA 階層，並透過 ACM 簽發私有憑證。私有 CA 本身按月收費，簽發的私有憑證另外依數量計費；私有憑證的私鑰可以匯出，用在任何地方（例如 EC2 上的服務、IoT 裝置）。

### TLS 在哪裡終結

有了憑證，還要決定 TLS 在哪裡解開：

- **在 ALB 或 CloudFront 終結**：最常見。後端到 ALB 之間可以是 HTTP（在 VPC 內），或再用另一張憑證走 HTTPS。
- **端到端加密（end-to-end）**：法規要求「網路上任何一段都不能是明文」時，ALB 到後端也用 HTTPS，後端 instance 上安裝憑證（通常是 Private CA 簽發的私有憑證）。
- **TLS passthrough**：用 NLB 的 TCP listener 直接把加密流量轉給後端，由後端終結 TLS，負載平衡器完全看不到內容（第 10 章）。

資料庫連線的傳輸加密也要記得：RDS 支援 TLS 連線，可以用 parameter group 強制要求（例如 PostgreSQL 的 `rds.force_ssl`），應用程式再設定驗證伺服器憑證（第 26 章）。

## 15.14 比較與選型

### 金鑰與機密服務一覽

| 服務 | 管什麼 | 誰控制 | 典型考點 |
|---|---|---|---|
| KMS（AWS managed key） | AWS 服務的預設加密金鑰 | AWS 管理 policy 與輪替 | 不能跨帳號、不能改 policy |
| KMS（customer managed key） | 你自訂的加密金鑰 | 你（key policy、輪替、刪除） | 跨帳號、職責分離、可稽核 |
| KMS multi-Region key | 多 Region 共用材料的 key | 你（每個 Region 各自 policy） | client-side 加密資料跨 Region 解密 |
| KMS custom key store | 金鑰材料在 CloudHSM 或外部系統 | 你（含 HSM 營運） | 專屬 HSM + AWS 服務整合 |
| CloudHSM | 單一租戶 HSM | 你（使用者與金鑰），AWS 管硬體 | PKCS #11、TDE、TLS offload、AWS 不能存取金鑰 |
| Secrets Manager | 機密（含自動輪替） | 你 | 自動輪替 DB 密碼、跨 Region replica、跨帳號 |
| Parameter Store | 設定與簡單機密 | 你 | 階層式設定、Standard 免費 |
| ACM | TLS 憑證 | AWS 自動續約（ACM 簽發者） | Region 規則、CloudFront 要 `us-east-1`、匯入憑證不續約 |
| AWS Private CA | 私有 CA 與內部憑證 | 你 | 內部 mTLS、私鑰可匯出 |

### 選型決策

```text
要保護的是什麼？
├─ 靜態資料（S3、EBS、RDS…）
│   ├─ 沒有特別稽核或控制要求 → 服務預設加密（SSE-S3、AWS owned／managed key）
│   ├─ 要控制誰能解密、職責分離、CloudTrail 稽核、跨帳號分享 → customer managed KMS key
│   ├─ 法規要求單一租戶 HSM，且要 AWS 服務整合 → KMS custom key store（CloudHSM）
│   ├─ 法規要求金鑰由自己產生 → KMS imported key material
│   └─ AWS 永遠不能看到明文 → client-side encryption（Encryption SDK + KMS）
├─ 應用程式自己的加密運算
│   ├─ 標準介面（PKCS #11／JCE／CNG）、TDE、TLS offload → CloudHSM
│   └─ 一般 envelope encryption → KMS GenerateDataKey + Encryption SDK
├─ 密碼、API key
│   ├─ 要自動輪替／跨 Region／跨帳號 → Secrets Manager
│   └─ 一般設定或不需輪替 → Parameter Store（SecureString）
└─ TLS 憑證
    ├─ 公開網站，掛 ALB／CloudFront／API Gateway → ACM public（CloudFront 要 us-east-1）
    ├─ 公司政策指定外部 CA → 匯入 ACM + EventBridge 到期通知
    └─ 內部服務、mTLS → AWS Private CA
```

## 15.15 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 加密大檔案、KMS 4 KB 限制 | Envelope encryption：`GenerateDataKey`，本地加密 |
| 控制誰能解密、稽核每次解密 | Customer managed key + key policy + CloudTrail |
| IAM 允許 `kms:Decrypt` 仍 AccessDenied | Key policy 沒有允許該 principal 或沒有開啟 IAM 授權 |
| 分享加密 EBS snapshot／AMI 給其他帳號 | 改用 customer managed key 重新加密，key policy 授權對方帳號 |
| 管理 key 的人不能解密資料 | Key policy 職責分離：admin 與 user 分開 |
| 限制 key 只能透過某服務使用 | `kms:ViaService` 條件 |
| 輪替後舊資料能否解密 | 可以；舊材料保留，key ID 不變，資料不會重加密 |
| 不小心排程刪除 key | 等待期（7–30 天）內可取消；刪除後資料永遠無法解密 |
| client-side 加密資料要在另一個 Region 解密 | Multi-Region key |
| 單一租戶 HSM、PKCS #11、AWS 不能存取金鑰 | CloudHSM |
| SSE-KMS 被 throttle、KMS 費用高 | S3 Bucket Key |
| 強制 S3 只能 HTTPS | Bucket policy：`aws:SecureTransport` 為 false 時 Deny |
| 自己保管金鑰但讓 S3 加密 | SSE-C（必須 HTTPS；新 bucket 預設封鎖，需先解除） |
| 自動輪替資料庫密碼 | Secrets Manager rotation（RDS 可直接託管 master 密碼） |
| 階層式設定、免費 | Parameter Store Standard |
| CloudFront 自訂網域 HTTPS | ACM 憑證在 `us-east-1` |
| 憑證自動續約 | ACM 簽發 + DNS validation |
| 匯入的憑證快到期 | ACM 不會續約；EventBridge 事件／Config rule 提醒並 re-import |

**常見陷阱**：

1. 以為 AWS managed key 可以跨帳號分享。它的 key policy 不能修改，所以不能；要改用 customer managed key。
2. 以為自動輪替會重新加密舊資料，或輪替後舊資料無法解密。兩者都錯。
3. 以為 key policy 中的 `arn:aws:iam::帳號:root` 只授權 root user。它代表整個帳號，用來啟用 IAM policy 授權。
4. 以為 Parameter Store 有內建的資料庫密碼自動輪替。沒有，那是 Secrets Manager 的功能。
5. 在 ALB 所在 Region 之外申請 ACM 憑證，或把 CloudFront 的憑證申請在 origin 所在 Region。
6. 以為修改 S3 預設加密會重新加密既有物件。不會，需要重新複製。

## 15.16 SAP 加深：多帳號金鑰策略與資料邊界

### 金鑰放在哪個帳號

在第 14 章的多帳號架構中，KMS key 有兩種放法：

| 模式 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| 分散式 | 每個 workload 帳號建立自己的 key | 爆炸半徑小、團隊自主、KMS 配額分散 | 標準化與稽核較分散 |
| 集中式 | 由 security 帳號建立 key，以 key policy 授權各帳號使用 | 金鑰集中管理與稽核 | 跨帳號 key policy 複雜；所有請求計入 key 所在帳號的配額；security 帳號出錯影響大 |

AWS 一般建議 key 和使用它的資源放在同一個帳號，由中央團隊用 SCP、Config 與 IaC 範本確保每個帳號的 key 都符合標準（例如必須開啟輪替、key policy 必須包含資安的唯讀稽核 role）。集中式只用在確實需要共用同一把 key 的情境，例如集中日誌的加密。

### 用 SCP 與 RCP 保護 KMS

第 14 章的組織政策同樣能保護金鑰：

- **SCP** 拒絕成員帳號的一般 role 呼叫 `kms:ScheduleKeyDeletion`、`kms:DisableKey`、`kms:PutKeyPolicy`，只有資安的 key 管理 role 例外，防止誤刪或惡意刪除金鑰造成資料永久無法解密（這是一種勒索手法：攻擊者用自己的 key 加密你的資料，或刪除你的 key）。
- **RCP** 可以對 `kms:*` 拒絕組織外的 principal，即使某把 key 的 key policy 被寫成允許外部帳號，組織外的身份也無法使用。

### 多 Region DR 時的金鑰與機密

Wanderly 的新加坡 warm standby（第 34、42 章）需要把以下東西都準備好，否則資料複製過去也打不開：

1. **加密的資料在目的 Region 要有對應的 key**：S3 CRR 需要在 replication 設定中指定目的 Region 的 KMS key，replication role 要有來源 key 的 `kms:Decrypt` 與目的 key 的 `kms:Encrypt` 權限；Aurora Global Database 的次要 cluster 使用次要 Region 的 key；跨 Region 複製的 EBS snapshot 也要指定目的 Region 的 key。
2. **應用層加密的資料** 用 multi-Region key，讓新加坡可以在本地解密。
3. **Secrets** 用 Secrets Manager replica，確保新加坡在東京故障時仍能讀到最新密碼。
4. **憑證** 在新加坡另外申請 ACM 憑證給當地的 ALB；CloudFront 的憑證本來就在 `us-east-1`，不受影響。

### 多租戶與 crypto-shredding

SaaS 平台常見的設計是「每個租戶一把 KMS key」，或同一把 key 但每個租戶不同的 encryption context。前者的好處是可以做 **crypto-shredding（加密銷毀）**：租戶解約、要求刪除資料時，排程刪除該租戶的 key，所有用它加密的資料（包括散落在備份中的副本）就永遠無法解密。代價是 key 數量與月費隨租戶數成長，也要注意 KMS 的 key 數量與請求配額（預設值，可申請提高）。第 49 章會在多租戶 SaaS 案例中比較這兩種做法。

## 本章重點整理

- Encryption at rest 與 in transit 保護不同階段，兩者互不取代；實務上最難的不是演算法，而是金鑰管理。
- KMS key 存在 FIPS 140 驗證的 HSM 中且不以明文離開 KMS，是 Regional 資源，所有使用都記錄在 CloudTrail。
- AWS owned、AWS managed、customer managed 三種 key 的加密強度相同，差別在控制權；跨帳號、自訂 policy、控制輪替與刪除都需要 customer managed key。
- KMS `Encrypt` 最多 4 KB，大量資料用 envelope encryption：`GenerateDataKey` 取得 data key 在本地加密，只保存加密後的 data key。
- Encryption context 是綁進密文的驗證資料，解密時必須相同，也能用於 key policy 條件與稽核。
- Key policy 是 KMS 授權的起點；預設的 `arn:aws:iam::帳號:root` 陳述代表整個帳號，讓 IAM policy 能參與授權。
- Grant 提供可撤銷的程式化授權，AWS 服務（如 EBS）用它臨時取得使用 key 的權限。
- 跨帳號使用 KMS key 需要 key policy 與對方 IAM policy 兩邊授權；AWS managed key 不能跨帳號，因此加密的 snapshot 與 AMI 要先改用 customer managed key 才能分享。
- 自動輪替不改 key ID、保留舊材料、不重新加密既有資料；排程刪除有 7–30 天等待期，刪除後資料永遠無法解密。
- Multi-Region key 共享 key ID 與材料，但 key policy、grant、alias 在每個 Region 各自管理，且不會複製任何資料。
- CloudHSM 是單一租戶 HSM，客戶完全控制金鑰與使用者、AWS 無法存取，適合 PKCS #11、TDE、TLS offload；高可用需跨 AZ 至少兩個 HSM。
- S3 新物件預設以 SSE-S3 加密；SSE-KMS 讀取需要 `kms:Decrypt`，S3 Bucket Key 可大幅降低 KMS 請求量與成本；SSE-C 必須使用 HTTPS，且自 2026 年 4 月起新 bucket 預設封鎖 SSE-C。
- Secrets Manager 以 createSecret、setSecret、testSecret、finishSecret 四步驟自動輪替並以 staging label 切換版本，支援跨 Region replica 與跨帳號 resource policy。
- Parameter Store 適合階層式設定與簡單機密，Standard tier 免費但沒有內建輪替；需要自動輪替時選 Secrets Manager。
- ACM 憑證是 Regional 資源，CloudFront 必須用 `us-east-1` 的憑證；DNS validation 的 ACM 憑證會自動續約，匯入的憑證不會。

### 練習 15-1｜SAA｜單選｜Envelope encryption 流程

Wanderly 的影片服務要在上傳到 S3 之前，自行在應用程式中加密每個約 2 GB 的旅遊影片，並且要求每次解密都能在 CloudTrail 中被稽核。團隊已經建立一把 customer managed KMS key。

應用程式應該如何加密影片？

- A. 把整個影片分段，每段 4 KB 呼叫 KMS `Encrypt`，再把所有密文段落合併上傳
- B. 呼叫 KMS `GenerateDataKey` 取得明文與加密後的 data key，用明文 data key 在本地加密影片後清除它，把加密後的 data key 與影片密文一起保存
- C. 呼叫 KMS `GenerateDataKey`，把明文 data key 存在 S3 物件的 metadata 中，方便之後解密
- D. 把 KMS key 的 key ID 作為 AES 金鑰，在應用程式中直接加密影片

> [!answer]- 答案：B
> **A ✗** `Encrypt` 單次上限確實是 4 KB，但把 2 GB 拆成 50 萬次 KMS 呼叫會造成極高的延遲、費用與 throttling。KMS 的設計本來就不是用來直接加密大量資料。
>
> **B ✓** 這是 envelope encryption：KMS 只保護小小的 data key，大量資料在本地加密。解密時必須把加密的 data key 送給 KMS 解開，每次都會檢查權限並記錄在 CloudTrail，滿足稽核需求。
>
> **C ✗** 明文 data key 和密文放在一起，任何能讀物件的人都能解密，加密形同虛設。與密文放在一起的應該是「加密後」的 data key。
>
> **D ✗** Key ID 只是識別碼，不是金鑰材料。KMS key 的材料永遠不會離開 KMS。
>
> **考點**：SAA-1.3｜envelope encryption 與 data key

### 練習 15-2｜SAA｜單選｜Key policy 與 IAM

Wanderly 的安全團隊建立了一把 customer managed key，並自訂了 key policy：只列出 `SecurityKeyAdmin` role 為管理員，沒有其他陳述。之後工程師在 `ReportApp` role 的 IAM policy 加入了對這把 key 的 `kms:Decrypt` 權限，但 `ReportApp` 解密時仍收到 AccessDenied。

最可能的原因是什麼？

- A. IAM policy 的變更需要 24 小時才會套用到 KMS
- B. `ReportApp` 需要同時具有 `kms:Encrypt` 權限才能解密
- C. Key policy 既沒有直接允許 `ReportApp`，也沒有包含信任帳號以啟用 IAM policy 授權的陳述，所以 IAM 的 Allow 不會生效
- D. SCP 必須明確允許 `kms:Decrypt`，IAM policy 才能生效

> [!answer]- 答案：C
> **A ✗** IAM 變更通常在短時間內生效，不需要 24 小時；問題出在授權路徑。
>
> **B ✗** 解密只需要 `kms:Decrypt`，不需要 `kms:Encrypt`。
>
> **C ✓** KMS key 的存取一定要由 key policy 允許。只有 key policy 包含類似 `"Principal": {"AWS": "arn:aws:iam::帳號:root"}` 的陳述時，IAM policy 才能參與授權。這份自訂 policy 拿掉了這段，所以只有 key policy 直接列名的 principal 能使用 key。
>
> **D ✗** 預設的 `FullAWSAccess` SCP 已經允許所有動作；SCP 也不會授予權限，問題不在這裡。
>
> **考點**：SAA-1.3、SAA-1.1｜key policy 是 KMS 授權起點

### 練習 15-3｜SAA｜單選｜分享加密的 AMI

Wanderly 的 `shared-services` 帳號建立了 golden AMI，其 EBS snapshot 使用 AWS managed key `aws/ebs` 加密。平台團隊要把這個 AMI 分享給 20 個 workload 帳號使用，但分享時發現其他帳號無法用它啟動 instance。

應如何處理？

- A. 在 `aws/ebs` 的 key policy 中加入 20 個 workload 帳號
- B. 把 AMI 設定為公開，讓所有帳號都能使用
- C. 在每個 workload 帳號啟用 EBS 預設加密，就能自動解密分享的 AMI
- D. 建立一把 customer managed key 並在 key policy 授權 workload 帳號，用這把 key 重新加密複製 AMI 後再分享

> [!answer]- 答案：D
> **A ✗** AWS managed key 的 key policy 不能修改，所以無法授權其他帳號使用，這正是問題的根源。
>
> **B ✗** 加密的 AMI 不能公開分享；而且把公司的 golden AMI 公開也違反安全原則。
>
> **C ✗** 目標帳號的預設加密只影響它自己新建的 volume，無法讓它取得來源帳號 `aws/ebs` 的解密權限。
>
> **D ✓** Customer managed key 的 key policy 可以授權其他帳號（含 `kms:Decrypt`、`kms:CreateGrant` 等）。用它重新加密 AMI 的 snapshot 後分享，workload 帳號的 IAM 再允許使用這把 key，就能啟動 instance。
>
> **考點**：SAA-1.3、SAA-1.1｜AWS managed key 不能跨帳號

### 練習 15-4｜SAA｜單選｜自動輪替的效果

Wanderly 對一把 customer managed key 啟用了自動輪替。一年後，稽核員詢問：去年用這把 key 加密的 S3 物件與 EBS snapshot 會發生什麼事？應用程式需要修改嗎？

哪個敘述正確？

- A. KMS 會保留舊的金鑰材料，舊資料仍可正常解密，新的加密使用新材料；key ID 與 alias 不變，應用程式不需要修改，但既有資料不會被重新加密
- B. 輪替後舊資料無法解密，必須在輪替前先把所有資料解密並用新 key 重新加密
- C. KMS 會在背景自動用新材料重新加密所有 S3 物件與 EBS snapshot
- D. 輪替會產生新的 key ID，應用程式必須更新為新的 key ID

> [!answer]- 答案：A
> **A ✓** 自動輪替只改變金鑰材料，key ID、ARN、alias 與 key policy 都不變；舊材料保留以解密舊資料，KMS 從密文就能判斷該用哪一版。若法規要求舊資料也用新材料加密，必須另外重新加密資料。
>
> **B ✗** 舊材料會一直保留，輪替不會讓任何既有資料無法解密。
>
> **C ✗** KMS 不知道你的資料存在哪裡，也不會重寫任何資料。
>
> **D ✗** 自動輪替不改 key ID。只有手動輪替（建立新 key 並切換 alias）才會出現新的 key ID。
>
> **考點**：SAA-1.3｜KMS 自動輪替語意

### 練習 15-5｜SAA｜單選｜SSE-KMS 被節流

Wanderly 的照片 bucket 使用 SSE-KMS 搭配 customer managed key。旅遊旺季時，每秒有數千次物件讀寫，應用程式開始收到 KMS 的 `ThrottlingException`，KMS 的請求費用也明顯上升。資安團隊要求繼續使用同一把 customer managed key。

哪個做法最能以最少變更解決問題？

- A. 把 bucket 的預設加密改為 SSE-S3
- B. 改用 SSE-C，由應用程式在每個請求中提供金鑰
- C. 為 bucket 啟用 S3 Bucket Key
- D. 為每個 prefix 建立不同的 customer managed key，分散 KMS 請求

> [!answer]- 答案：C
> **A ✗** SSE-S3 不會呼叫 KMS，可以解決節流，但違反「繼續使用 customer managed key」的要求，也失去 key policy 控制與 CloudTrail 的解密稽核。
>
> **B ✗** SSE-C 要應用程式自行保管金鑰並在每次請求帶上，營運負擔大，也同樣不再使用 KMS key。
>
> **C ✓** S3 Bucket Key 讓 S3 以 bucket 層級的金鑰在一段時間內產生各物件的 data key，大幅減少對 KMS 的呼叫，同時仍使用原本的 customer managed key。只要在 bucket 設定開啟即可。
>
> **D ✗** KMS 請求配額是以帳號與 Region 計算，不是每把 key 各自一份，多建幾把 key 不會提高總配額，還增加管理負擔與月費。
>
> **考點**：SAA-1.3、SAA-4.1｜S3 Bucket Key 降低 KMS 請求

### 練習 15-6｜SAA｜單選｜資料庫密碼自動輪替

Wanderly 的訂單服務在 EC2 上執行，連線到 RDS for PostgreSQL。目前資料庫密碼寫在 launch template 的 user data 中，三年沒換過。資安團隊要求密碼每 30 天自動更換，應用程式不能因為換密碼而停機，並希望營運負擔最低。

哪個做法最合適？

- A. 把密碼存成 Parameter Store 的 SecureString，並撰寫 cron job 每 30 天更新參數與資料庫密碼
- B. 把密碼存進 Secrets Manager 並啟用 30 天的自動輪替，應用程式在執行時透過 caching client 讀取 secret，驗證失敗時重新讀取
- C. 把密碼用 KMS 加密後放在 user data，每 30 天用新的 KMS key 重新加密
- D. 把密碼存在 S3 bucket，以 SSE-KMS 加密並啟用 versioning，每 30 天上傳新版本

> [!answer]- 答案：B
> **A ✗** Parameter Store 沒有內建輪替，自己寫 cron job 要處理資料庫更新、測試與失敗回退，營運負擔較高。若只是儲存不需輪替的設定，Parameter Store 才是好選擇。
>
> **B ✓** Secrets Manager 提供 RDS 的現成輪替機制，四步驟流程會先測試新密碼再切換 `AWSCURRENT`。應用程式在執行時讀取並快取 secret，遇到驗證失敗再重新讀取，換密碼時不需停機或改設定。
>
> **C ✗** 重新加密的是「同一個密碼」，密碼本身沒有更換；而且密碼仍散落在 user data 中。
>
> **D ✗** S3 只是存放位置，不會更新資料庫裡的密碼，也沒有輪替流程。
>
> **考點**：SAA-1.2、SAA-1.3｜Secrets Manager 自動輪替

Wanderly 的微服務有約 300 個設定值，例如 API 逾時、功能開關、外部服務 URL，以及幾個不需要輪替的第三方 API token。團隊希望用階層化的路徑管理不同環境的設定、讓每個服務只能讀自己的路徑，並且成本最低。

哪個做法最合適？

### 練習 15-8｜SAA｜單選｜CloudFront 的 ACM 憑證

Wanderly 的網站 origin 是東京 Region 的 ALB。團隊在東京 Region 申請了 `www.wanderly.example` 的 ACM 憑證並成功掛到 ALB 上。接著要在前面加上 CloudFront distribution 並使用同一個自訂網域，但建立 distribution 時在憑證選單中看不到這張憑證。

應如何處理？

- A. 把東京的 ACM 憑證匯出，再匯入 CloudFront

>

### 練習 15-9｜SAA｜選兩項｜強制 S3 加密與傳輸安全

Wanderly 的付款報表 bucket 必須符合兩個要求：所有上傳的物件都只能以指定的 customer managed KMS key 加密，且所有存取都必須使用 TLS。團隊希望用 bucket 層級的設定強制實施，不依賴每個上傳程式自律。

哪兩項設定能滿足需求？（選兩項）

- A. 在 bucket policy 中，當 `aws:SecureTransport` 為 `false` 時拒絕所有 S3 動作
- B. 把 bucket 預設加密設為 SSE-S3，並啟用 S3 Bucket Key
- C. 把 bucket 預設加密設為 SSE-KMS 並指定該 customer managed key，再以 bucket policy 拒絕指定其他加密方式或其他 KMS key 的 `PutObject` 請求
- D. 在 bucket 啟用 versioning 與 MFA delete
- E. 在 IAM policy 中為上傳者加入 `kms:Encrypt` 權限

> [!answer]- 答案：A、C
> **A ✓** `aws:SecureTransport` 為 false 代表請求沒有使用 TLS，在 bucket policy 中對所有 principal 明確拒絕，就能強制傳輸加密。
>
> **B ✗** SSE-S3 由 S3 管理金鑰，不符合「指定的 customer managed key」；Bucket Key 只用於 SSE-KMS，對 SSE-S3 沒有意義。
>
> **C ✓** 預設加密確保沒有帶加密 header 的上傳也會用指定 key；bucket policy 拒絕指定 SSE-S3 等其他加密方式、指定其他 key ID，或只寫 `aws:kms` 卻沒帶 key ID（S3 會改用 `aws/s3`）的請求，堵住「用別的方式或別的 key 加密」的漏洞。
>
> **D ✗** Versioning 與 MFA delete 保護的是刪除與覆寫，和加密方式或 TLS 無關。
>
> **E ✗** 給上傳者 KMS 權限只是讓他們「能夠」使用 key，無法「強制」他們使用；而且 SSE-KMS 上傳需要的是 `kms:GenerateDataKey`。
>
> **考點**：SAA-1.3｜bucket policy 強制 SSE-KMS 與 TLS

### 練習 15-10｜SAA｜單選｜CloudHSM 的使用時機

一家與 Wanderly 合作的支付處理商要把系統搬到 AWS。法規要求加密金鑰必須存放在由該公司獨占控制的單一租戶 HSM 中，雲端供應商不得存取金鑰；既有的 Java 應用程式透過 JCE 介面呼叫 HSM 進行簽章。

哪個方案最合適？

- A. 使用 KMS customer managed key，並在 key policy 拒絕所有 AWS 服務 principal
- B. 使用 KMS asymmetric key 進行簽章，並啟用自動輪替
- C. 把金鑰存成 Secrets Manager 的 secret，由應用程式讀取後在記憶體中簽章
- D. 在 VPC 中部署 AWS CloudHSM cluster，於不同 AZ 至少放置兩個 HSM，應用程式透過 CloudHSM 的 JCE provider 使用金鑰

> [!answer]- 答案：D
> **A ✗** KMS 是多租戶的受管服務，HSM 由 AWS 管理，不符合「單一租戶、獨占控制」的要求；也不提供 JCE 介面。
>
> **B ✗** KMS asymmetric key 能簽章，但同樣不是單一租戶 HSM；而且 KMS 的自動輪替不支援 asymmetric key。
>
> **C ✗** 把金鑰材料放在 Secrets Manager 讓應用程式取出使用，金鑰會離開 HSM 進入應用程式記憶體，違反 HSM 保護金鑰的目的。
>
> **D ✓** CloudHSM 是單一租戶 HSM，客戶自己管理 HSM 使用者與金鑰，AWS 無法存取金鑰；它支援 PKCS #11、JCE、CNG 等標準介面，既有 Java 程式可直接整合。跨 AZ 至少兩個 HSM 才能高可用。
>
> **考點**：SAA-1.3｜CloudHSM 適用情境

### 練習 15-11｜SAP｜單選｜跨帳號讀取 SSE-KMS 物件

Wanderly 的 `data-lake` 帳號（111122223333）有一個 S3 bucket，物件以該帳號的 customer managed key 透過 SSE-KMS 加密。`analytics` 帳號（444455556666）的 `EtlRole` 需要讀取這些物件。目前 bucket policy 已允許 `EtlRole` 執行 `s3:GetObject`，`EtlRole` 的 IAM policy 也允許對該 bucket 的 `s3:GetObject`，但讀取時仍收到 AccessDenied。

還缺少什麼設定？

- A. 在 `analytics` 帳號建立同名的 KMS alias 指向自己的 key
- B. 在 `data-lake` 帳號啟用 S3 Bucket Key，讓跨帳號讀取不需要 KMS 權限
- C. 在 `data-lake` 帳號的 key policy 允許 `EtlRole`（或 `analytics` 帳號）使用 `kms:Decrypt`，並在 `EtlRole` 的 IAM policy 允許對該 key ARN 的 `kms:Decrypt`
- D. 把物件改用 `aws/s3` 重新加密，因為 AWS managed key 會自動授權 bucket policy 中的所有 principal

> [!answer]- 答案：C
> **A ✗** Alias 只在自己的帳號內有效，而且物件是用 `data-lake` 帳號的 key 加密，`analytics` 帳號自己的 key 無法解密。
>
> **B ✗** Bucket Key 只減少 S3 對 KMS 的呼叫次數，讀取者仍然需要對該 KMS key 的 `kms:Decrypt` 權限。
>
> **C ✓** SSE-KMS 物件的讀取需要 S3 與 KMS 兩組權限。跨帳號時，KMS 也要兩邊同意：key 所在帳號的 key policy 授權對方，對方帳號的 IAM policy 允許對該 key ARN 的操作。
>
> **D ✗** AWS managed key 的 key policy 不能修改，只允許同帳號內透過 S3 使用，無法授權其他帳號，改用它只會讓跨帳號讀取完全不可能。
>
> **考點**：SAP-1.2、SAP-2.3｜跨帳號 SSE-KMS 需 S3 與 KMS 雙重授權

### 練習 15-12｜SAP｜單選｜Multi-Region key 的語意

Wanderly 的會員服務在應用程式層用 AWS Encryption SDK 加密護照號碼後寫入 DynamoDB global table，資料會複寫到新加坡。DR 要求東京 Region 完全故障時，新加坡的應用程式仍能解密這些欄位。團隊打算使用 KMS multi-Region key。

哪個敘述正確？

- A. 建立 replica key 後，KMS 會自動把 DynamoDB 中的密文複寫到新加坡
- B. Primary key 的 key policy 修改後，會自動同步到所有 replica key
- C. Multi-Region key 是全球資源，同一把 key 可以在任何 Region 使用，不需要建立 replica
- D. 在新加坡建立東京 primary key 的 replica 後，兩者共享 key ID 與金鑰材料，新加坡可在本地解密；但 replica 的 key policy、grant 與 alias 需要在新加坡另外設定

> [!answer]- 答案：D
> **A ✗** KMS 只管理金鑰，不搬任何應用資料；資料的跨 Region 複寫由 DynamoDB global tables 負責。
>
> **B ✗** Key policy、grant、alias、tag 與啟用狀態不在相關 key 之間共享，每個 Region 獨立管理；這讓各 Region 可以有不同的授權，但也代表要確保 DR Region 的 policy 正確。
>
> **C ✗** Multi-Region key 不是全球資源，而是一組在各 Region 獨立存在、材料相同的 key，必須在需要的 Region 建立 replica。
>
> **D ✓** 相同的 key ID 與材料讓東京加密的密文可在新加坡直接用本地的 replica 解密，不需跨 Region 呼叫東京。授權設定則必須在新加坡各自配置，DR 演練時要一併驗證。
>
> **考點**：SAP-2.2、SAP-2.3｜multi-Region key 共享與不共享的屬性

### 練習 15-13｜SAP｜選兩項｜安全地淘汰 KMS key

Wanderly 的資安團隊發現一把三年前建立的 customer managed key，最近 90 天的 CloudTrail 中沒有任何使用紀錄。團隊打算刪除它以減少費用與管理範圍，但這個帳號中有每年執行一次的結帳批次，也有保存七年的 RDS 與 EBS 備份。

哪兩個做法能最大程度避免資料永久無法解密？（選兩項）

- A. 直接刪除這把 key 的 alias，因為刪除 alias 就等同刪除 key
- B. 先停用（disable）這把 key，並建立 CloudWatch alarm 監控 CloudTrail 中對這把 key 的使用嘗試，觀察期涵蓋年度批次的執行時間
- C. 盤點所有備份、snapshot、跨 Region 與跨帳號副本是否使用這把 key，必要時先用新 key 重新加密，再以 30 天等待期排程刪除
- D. 立即刪除 key，若之後發現需要，再請 AWS Support 恢復金鑰材料
- E. 只要 CloudTrail 90 天內沒有紀錄，就可以安全地排程最短 7 天的刪除

> [!answer]- 答案：B、C
> **A ✗** Alias 只是名稱，刪除 alias 不會刪除 key，也不會減少費用；反而可能讓仍在使用 alias 的程式失敗。
>
> **B ✓** 停用是可逆的操作。停用期間任何使用嘗試都會失敗並留下 CloudTrail 紀錄，用 alarm 偵測可以找出未知的依賴；觀察期要涵蓋年度批次，否則看不到低頻使用。
>
> **C ✓** 長期保存的備份可能多年才會還原一次，近期紀錄看不到它們。先盤點並把需要保留的資料改用新 key 重新加密，再使用最長的等待期排程刪除，保留取消的機會。
>
> **D ✗** KMS 不允許立即刪除，且刪除完成後金鑰材料永久消失，AWS 也無法恢復。
>
> **E ✗** 90 天的觀察期看不到每年一次的作業與多年後才還原的備份，最短的等待期也讓發現錯誤後取消的時間最短。
>
> **考點**：SAP-3.2、SAP-1.2｜KMS key 停用與排程刪除

### 練習 15-14｜SAP｜單選｜跨帳號共享資料庫機密

Wanderly 的 `payments-prod` 帳號在 Secrets Manager 中保存了付款資料庫的密碼，並啟用自動輪替，目前使用預設的 `aws/secretsmanager` key 加密。`reporting` 帳號的 Lambda 需要讀取這個密碼以連線唯讀副本。資安團隊要求不得複製密碼到其他帳號，輪替後 `reporting` 也要自動拿到新密碼。

應如何設定？

- A. 在 `reporting` 帳號建立一個同名 secret，並用 EventBridge 在每次輪替後複製新密碼過去
- B. 把 secret 改用 customer managed key 加密並在 key policy 允許 `reporting` 的 Lambda role 使用 `kms:Decrypt`；在 secret 的 resource policy 允許該 role `secretsmanager:GetSecretValue`；並在 `reporting` 帳號的 IAM policy 允許這兩個動作
- C. 保留 `aws/secretsmanager`，只在 secret 的 resource policy 允許 `reporting` 帳號讀取
- D. 把密碼搬到 Parameter Store 的 Advanced tier SecureString，並透過 AWS RAM 把參數分享給 `reporting` 帳號

> [!answer]- 答案：B
> **A ✗** 這等於把密碼複製到另一個帳號，違反資安要求；自建同步也增加失敗點與輪替時的不一致。
>
> **B ✓** 跨帳號讀取 secret 需要三方面授權：secret 的 resource policy、KMS key policy，以及呼叫者帳號的 IAM policy。因為 AWS managed key 的 key policy 不能修改，必須改用 customer managed key。`reporting` 每次都讀取同一個 secret，輪替後自然取得新值。
>
> **C ✗** Resource policy 允許了讀取 secret，但 `aws/secretsmanager` 無法授權其他帳號解密，讀取會因 KMS 權限而失敗。
>
> **D ✗** Parameter Store 沒有內建輪替，搬過去就失去「輪替後 `reporting` 自動拿到新密碼」的能力，必須自己寫輪替程式。而且 Parameter Store 的跨帳號分享只支援 Advanced 參數、要透過 AWS RAM 設定，SecureString 還得改用 customer managed key，並沒有比 Secrets Manager 更簡單。
>
> **考點**：SAP-1.2、SAP-2.3｜Secrets Manager 跨帳號存取

### 練習 15-15｜SAP｜選兩項｜多 Region DR 的金鑰與機密

Wanderly 要在新加坡建立 warm standby。東京的資料包括：以 customer managed key 透過 SSE-KMS 加密的 S3 bucket（以 CRR 複寫）、Aurora 加密資料庫（以 Global Database 複寫）、以及 Secrets Manager 中的資料庫密碼。DR 要求東京 Region 完全無法使用時，新加坡能在不呼叫東京任何 API 的情況下提供服務。

哪兩項設定是必要的？（選兩項）

- A. 在 S3 CRR 規則中指定新加坡 Region 的 KMS key 作為複本的加密金鑰，並讓 replication role 擁有來源 key 的解密與目的 key 的加密權限
- B. 把東京的 KMS key 設為 global，讓新加坡直接使用
- C. 為 Secrets Manager 的資料庫密碼建立新加坡 replica，讓新加坡的應用程式讀取本地 replica
- D. 讓新加坡的應用程式在啟動時跨 Region 呼叫東京的 Secrets Manager 取得密碼並寫入本地環境變數
- E. 把所有資料改用 SSE-S3 與未加密的 Aurora，避免 DR 時處理 KMS key

> [!answer]- 答案：A、C
> **A ✓** 一般 KMS key 是 Regional 資源。S3 CRR 會在目的 Region 用指定的目的 key 重新加密複本，這樣新加坡讀取時只需要本地的 KMS；replication role 必須同時能解密來源物件並用目的 key 加密。
>
> **B ✗** 一般 KMS key 不能設為 global；multi-Region key 是另一種需要建立 replica 的 key 類型，而且 S3 CRR 這類服務整合不需要它。
>
> **C ✓** Replica secret 由 Secrets Manager 自動同步，primary 輪替後也會更新。新加坡讀取本地 replica，東京故障時不受影響，必要時還能提升為獨立 secret。
>
> **D ✗** 跨 Region 讀取東京的 secret 違反「不呼叫東京 API」，東京故障時應用程式就無法啟動；把密碼寫進環境變數也會在輪替後過期。
>
> **E ✗** 為了簡化 DR 而放棄加密控制會違反付款資料的合規要求，而且 Aurora 的加密只能在建立時決定，不是可隨意切換的設定。
>
> **考點**：SAP-2.2、SAP-2.3｜DR 情境中的 KMS 與 Secrets Manager 規劃

### 練習 15-16｜SAP｜單選｜防止金鑰被刪除造成資料永久遺失

Wanderly 的資安團隊擔心一個情境：攻擊者取得某個成員帳號的管理員權限後，排程刪除用來加密 production 資料庫與備份的 KMS key，讓資料永久無法解密以進行勒索。公司有 60 個成員帳號，希望用集中的預防性控制降低這個風險，同時保留資安團隊在必要時管理 key 的能力。

哪個做法最合適？

- A. 在每把 key 的 key policy 中移除 `EnableIAMPolicies` 陳述，讓帳號管理員無法管理 key
- B. 在每個帳號啟用 AWS Config rule，偵測處於 pending deletion 狀態的 key 並通知資安團隊
- C. 把所有 key 改成 AWS managed key，因為 AWS managed key 無法被刪除
- D. 在 Workloads OU 附加 SCP，拒絕 `kms:ScheduleKeyDeletion`、`kms:DisableKey` 與 `kms:PutKeyPolicy`，只對資安團隊的 key 管理 role 例外

> [!answer]- 答案：D
> **A ✗** 這需要逐一修改 60 個帳號中的每把 key，容易遺漏；若 key policy 中沒有其他管理者，還可能讓 key 變成無法管理。
>
> **B ✗** Config 是偵測性控制。等待期內雖然可以取消刪除，但它不能阻止攻擊者發出刪除或停用請求，也無法阻止攻擊者修改 key policy 把資安團隊鎖在外面。它適合作為輔助的第二層防護。
>
> **C ✗** AWS managed key 無法跨帳號、無法自訂 policy，並非所有情境都能替換；把整個加密架構換掉的代價遠大於問題本身。
>
> **D ✓** SCP 是集中的預防性控制，連成員帳號的管理員與 root user 都無法違反。拒絕刪除、停用與修改 key policy，並以 `aws:PrincipalARN` 對資安的 key 管理 role 例外，就能阻止這類勒索手法，同時保留正常管理能力。
>
> **考點**：SAP-1.2、SAP-3.2｜以 SCP 保護 KMS key
