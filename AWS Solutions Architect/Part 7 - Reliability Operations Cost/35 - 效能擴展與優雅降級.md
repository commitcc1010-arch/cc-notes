# 第 35 章　效能擴展、配額與優雅降級

## 35.1 故事：賞櫻季開賣的那一個小時

每年二月，Wanderly 會在晚上八點開賣日本賞櫻季的限量優惠房。今年行銷部做了一支爆紅的短影片，開賣前五分鐘，同時在線人數已經是平常的 15 倍。

八點整，事情一件接一件發生。首先，訂房 API 背後的 Lambda 開始回傳 `TooManyRequestsException`：帳號在東京 Region 的 Lambda concurrency 達到上限，而且這個上限是所有函數共用的，連後台的寄信、對帳函數都搶不到執行機會。接著，RDS 的 CPU 衝到 100%，原因是每個人打開旅館頁面時，都會對資料庫跑一次一模一樣的「熱門旅館列表」查詢。

最糟的是第三件事。合作的日本旅館庫存 API 開始回傳 HTTP 429（Too Many Requests）。Wanderly 的程式碼一遇到錯誤就立刻重試三次，而呼叫鏈上有三層服務都各自這麼做，結果一次失敗的使用者請求變成了 27 次對庫存 API 的呼叫，對方乾脆把 Wanderly 的 IP 整個封鎖了十分鐘。與此同時，首頁的「為你推薦」區塊因為推薦服務逾時，讓整個首頁都轉不出來，即使使用者根本只想搜尋。

事後檢討時，小林把問題分成三類：**容量不夠擴**（資料庫、Lambda）、**不知道上限在哪**（quota、合作夥伴的限制）、**一個地方壞掉拖垮全部**（重試放大、推薦服務拖累首頁）。這一章依序處理這三類問題。

## 35.2 先找瓶頸，再談擴展

面對「系統變慢」，最常見的錯誤是直接加機器。如果瓶頸在資料庫，加十倍的應用程式伺服器只會讓資料庫承受十倍的連線，情況更糟。擴展的第一步永遠是**找出瓶頸（bottleneck）**：整條請求路徑上，最先達到極限的那一個資源。

### 看百分位數，不要只看平均

**Latency（延遲）** 要看百分位數。**p99** 是「99% 的請求都比這個快」的值。平均延遲 120 ms 看起來很好，但 p99 可能是 4 秒：每 100 個請求就有 1 個要等 4 秒。而且一個頁面往往要呼叫很多個後端 API，只要其中一個慢，整頁就慢：呼叫 20 個 API 時，約 18% 的頁面載入（1 − 0.99²⁰）會碰到至少一次 p99 等級的慢請求；呼叫 100 個時則約 63%。CloudWatch metric 可以直接選 p99 等百分位數統計（第 36 章）。

### 一個好用的公式：Little's Law

**Little's Law** 說：系統中同時處理中的請求數 = 每秒到達的請求數 × 每個請求的平均處理時間。如果訂房 API 每秒收到 2,000 個請求，每個請求在 Lambda 中執行 0.5 秒，那麼同時需要 2,000 × 0.5 = **1,000 個 concurrency**，剛好就是 Lambda 常見的預設 Region quota（可申請提高；新建立的帳號預設值可能更低）。這個公式也說明了一件反直覺的事：**下游變慢會讓上游需要的容量暴增**。如果資料庫變慢讓每個請求從 0.5 秒變成 2 秒，同樣的流量就需要 4,000 個 concurrency。

### 判斷瓶頸的線索

| 現象 | 可能的瓶頸 | 方向 |
|---|---|---|
| 資料庫 CPU 高，大部分是相同的 SELECT | 重複讀取 | Cache（35.3 節） |
| 資料庫讀取量大，查詢彼此不同 | 讀取容量 | Read replica（35.3 節） |
| 寫入 IOPS 或鎖等待高 | 寫入容量 | Scale up、sharding、queue 削峰（35.4 節） |
| 應用程式 CPU 高，資料庫正常 | 運算 | 水平擴展（35.5 節） |
| 錯誤是 429、ThrottlingException | Quota 或下游限流 | Quota 管理與 retry（35.6–35.8 節） |
| 資料庫連線數到上限，CPU 卻不高 | 連線管理 | RDS Proxy（connection pooling） |

工具方面，CloudWatch metrics 看資源使用率，X-Ray 的 trace 可以看出一個請求在哪個下游花了最多時間（第 36 章），RDS Performance Insights（AWS 正將其能力整合進 CloudWatch Database Insights）可以看出哪一條 SQL 占用最多資料庫負載。

找到瓶頸後，擴展手段大致分成兩個方向：**scale up（垂直擴展）** 換更大的機器，簡單但有上限，而且通常要短暫停機；**scale out（水平擴展）** 加更多機器分擔，幾乎沒有上限，但需要應用程式配合。下面幾節分別看讀、寫與運算層怎麼 scale out。

## 35.3 擴展讀取：cache 與 read replica

Wanderly 的旅館頁面是典型的「讀遠多於寫」：一間旅館的資料一天可能只改幾次，卻被讀取幾十萬次。對這種負載，最有效的手段是不要每次都去問資料庫。

### Cache：讓重複的讀取不碰資料庫

**Cache（快取）** 把最近讀過的結果存在比資料庫快得多的地方（通常是記憶體）。最常見的模式是第 28 章介紹的 **cache-aside（lazy loading）**：

```text
 App ──① GET hotel:123──► ElastiCache
  │                          │
  │ ◄──② miss（沒有資料）─────┘
  │
  ├──③ SELECT ... WHERE id=123 ──► RDS
  │ ◄───────────── 資料 ───────────┘
  │
  └──④ SET hotel:123（TTL 300 秒）──► ElastiCache
```

① 應用程式先查 cache。② 沒有（cache miss）時，③ 才查資料庫，④ 並把結果寫回 cache，設定 **TTL（存活時間）**。之後 5 分鐘內的相同查詢都在 ① 就得到答案（cache hit）。命中率 95% 時，資料庫只需要處理 5% 的讀取。

不同層級有不同的 cache：

| 層級 | 服務 | 快取什麼 |
|---|---|---|
| 邊緣 | CloudFront（第 11 章） | 圖片、靜態檔案、可快取的 API 回應 |
| API | API Gateway caching（REST API） | 整個 API 回應 |
| 應用程式 | ElastiCache（Redis OSS／Valkey／Memcached） | 查詢結果、session、排行榜 |
| DynamoDB 專用 | DAX（DynamoDB Accelerator） | DynamoDB 讀取，微秒級延遲，API 相容 |

Cache 有兩個要注意的風險。第一是**資料過期**：TTL 內資料可能不是最新的，所以庫存、價格這類必須即時正確的資料，要搭配寫入時主動刪除 cache（invalidation）或縮短 TTL。第二是 **cold cache（冷快取）**：cache 節點重啟或大量 key 同時過期時，所有請求同時穿透到資料庫，可能瞬間壓垮它。對策包括為 TTL 加上隨機值避免同時過期、讓同一個 key 只有一個請求去資料庫載入、以及 cache 本身做 Multi-AZ 與 replica（第 34 章）。

### Read replica：分擔不重複的讀取

如果讀取彼此都不一樣（例如每個使用者查自己的訂單歷史），cache 命中率會很低。這時用 **read replica（唯讀副本）**：資料庫以非同步方式把變更複寫到一或多個副本，讀取請求分散到副本上。

- RDS for MySQL、MariaDB、PostgreSQL 最多可以建立 15 個 read replica；Aurora 最多 15 個 Aurora Replica，並提供一個 **reader endpoint** 自動在 replica 之間分散連線。
- 複寫是**非同步**的，副本可能落後 primary（**replica lag**）。剛寫入就要讀到的資料（例如「付款完成後顯示訂單」）應該讀 primary，報表、搜尋、歷史紀錄才讀 replica。
- Read replica 只分擔讀取，**寫入仍然只有 primary 一台**。
- 應用程式要能區分讀寫連線，通常是設定兩個 endpoint（writer 與 reader）。

### RDS Proxy：連線也是一種瓶頸

Lambda 這類大量、短暫的運算，每個執行環境都可能開一條資料庫連線，很快就把資料庫的連線數用完。**RDS Proxy** 是一個受管的連線池（connection pool）：應用程式連到 proxy，proxy 用少量長期連線和資料庫溝通，並在 failover 時保持用戶端連線，縮短中斷時間。

## 35.4 擴展寫入：sharding 與 queue 削峰

讀取可以用副本分擔，寫入卻沒那麼簡單：每一筆寫入最後都要落在「擁有那筆資料的地方」。擴展寫入有三條路。

### 一、Scale up 與更適合的資料庫

最簡單的是換更大的 instance、改用 Aurora（寫入路徑效率較高），或是把高寫入的部分搬到 DynamoDB 這種原生水平擴展的資料庫（第 27 章）。這是考試裡最常見的答案，因為營運負擔最小。

### 二、Sharding：把資料切成多份

**Sharding（分片）** 是依某個鍵把資料分到多個獨立的資料庫，每個 shard 只負責一部分資料的讀寫。例如依會員 ID 的 hash 分成 4 個 shard，每個 shard 承受約 1/4 的寫入。

DynamoDB 在內部自動做 sharding：資料依 **partition key** 分到多個 partition，每個 partition 有自己的吞吐上限（每秒 3,000 RCU 與 1,000 WCU）。所以 partition key 要選**基數高、存取平均**的欄位。如果用「日期」當 partition key，所有今天的寫入都打到同一個 partition，形成 **hot partition（熱分區）**，即使整張表的容量還很充足也會被 throttle。

自己對關聯式資料庫做 sharding 則代價很高：跨 shard 的查詢與交易變得困難，重新分配 shard 很麻煩。除非題目明確描述了單一資料庫寫入已到極限，否則通常不是首選。

### 三、Queue 削峰：讓寫入用自己的速度進行

賞櫻季開賣的訂單在一分鐘內湧入，但每筆訂單其實不必在 100 毫秒內寫進資料庫，只要使用者先看到「訂單已收到，處理中」就可以。這時在中間放一個 **SQS queue**（第 32 章）：

```text
                 尖峰：每秒 5,000 筆
 使用者 ──► API ───────────────────► [SQS queue] ◄── ② 依資料庫能承受的速度拉取
                ① 寫入 queue 後            │           （每秒 800 筆）
                   立即回應「處理中」        ▼
                                     [Worker（ASG 或 Lambda）] ──► RDS
                                           ▲
                         ③ 依 backlog per instance 擴展 worker（有上限）
```

① API 只負責把訂單放進 queue，這一步很快而且 SQS 幾乎可以無限擴展，使用者立刻得到回應。② Worker 以資料庫能承受的速度處理，尖峰被 queue「攤平」成一段較長、較平緩的處理時間。③ Worker 的數量可以依照「每台 worker 平均分到的待處理訊息數（backlog per instance）」自動擴展，但要設定上限，否則 worker 擴太多一樣會壓垮資料庫。Lambda 搭配 SQS 時可以用 event source mapping 的 maximum concurrency 限制同時處理的數量。

Queue 不會讓容量變多，它只是把「現在做不完的」延後做。所以要監控 `ApproximateAgeOfOldestMessage`：如果最舊的訊息越來越舊，表示長期處理速度追不上流入速度，必須擴展下游或降低流入。

## 35.5 水平擴展的前提

加機器能解決問題，前提是「任何一台機器都能處理任何一個請求」。賞櫻季那晚，Wanderly 原本的應用程式就有幾個讓水平擴展失效的設計，下面逐一檢查。

- **Stateless（無狀態）**：使用者的 session 不能存在某台伺服器的記憶體。若存在本機，load balancer 只能用 sticky session 把同一使用者固定送到同一台，新加入的機器分不到既有使用者的流量，機器被縮減時使用者也會被登出。把 session 放到 ElastiCache 或 DynamoDB。
- **檔案不放本機磁碟**：使用者上傳的照片要直接寫入 S3（或共享的 EFS），否則下一個請求被送到另一台機器時就找不到檔案。
- **Idempotency（冪等性）**：同一個請求執行兩次和執行一次的結果相同。水平擴展的系統裡，重試、訊息重複投遞（SQS standard queue 是 at-least-once）都很常見。付款與建立訂單要用 **idempotency key**：用戶端為每個操作產生唯一 ID，伺服器記錄已處理過的 ID，重複的請求直接回傳上一次的結果。
- **設定與 secrets 外部化**：放在 Parameter Store、Secrets Manager 或 AppConfig，而不是寫在某台機器的檔案裡。
- **啟動要快、要能自我宣告就緒**：用預先做好的 AMI 或 container image，設定 health check 與 Auto Scaling 的 **instance warmup**，避免機器還沒準備好就被算進容量或收到流量（第 18 章）。
- **下游跟得上**：應用程式層可以無限擴展，資料庫、合作夥伴 API 和 quota 卻不行。每加一層擴展，都要問「它下面那一層撐得住嗎？」

最後一點直接帶出下一節的主題：在 AWS 上，很多「下面那一層」的極限不是硬體，而是帳號的 quota。

## 35.6 Service quotas：先知道上限在哪裡

**Service quota（服務配額，舊稱 service limit）** 是 AWS 對每個帳號、每個 Region（有些是全域）可以使用的資源數量或請求速率設定的上限。它的目的是保護 AWS 與你自己：避免程式錯誤一口氣開出一萬台 EC2，或某個帳號吃光共享容量。

### Quota 的分類

- **可調整（adjustable，俗稱 soft limit）**：可以申請提高的預設值，例如 Lambda 每 Region 的 concurrency（常見預設 1,000，新帳號可能更低）、EC2 On-Demand 的 vCPU 數。
- **不可調整（hard limit）**：服務設計上的固定限制，例如 Lambda 最長執行 15 分鐘、DynamoDB item 400 KB、S3 單一物件大小上限（考試用 5 TB；AWS 現已提高到約 50 TB，見第 22 章）。遇到它只能改設計。
- **資源數量 vs 速率**：有些 quota 限制「能有多少個」（VPC 數量、EIP 數量），有些限制「每秒能做多少次」（API 呼叫速率，超過就 throttle）。
- **Scope**：大多數 quota 是**每帳號、每 Region** 分開計算，所以東京的 quota 提高了，新加坡仍是預設值。

考試常見的幾個：

| 服務 | Quota | 預設值與說明 |
|---|---|---|
| Lambda | 每 Region concurrent executions | 常見預設 1,000（可申請提高；新帳號可能更低），所有函數共用 |
| EC2 | Running On-Demand instances | 以 vCPU 數計算，依 instance family 群組分開（可申請提高） |
| API Gateway | 每帳號每 Region 請求速率 | 穩定每秒 10,000、burst 5,000（可申請提高） |
| S3 | 每個 prefix 的請求速率 | 每秒 3,500 次寫入類（PUT／COPY／POST／DELETE）、5,500 次讀取類（GET／HEAD），prefix 數量不限 |
| DynamoDB | 每個 partition 吞吐 | 3,000 RCU、1,000 WCU（不可調整，要靠 partition key 分散） |
| Kinesis Data Streams | 每個 shard 寫入 | 每秒 1 MB 或 1,000 筆（以 shard 數擴展） |

### Service Quotas 服務：查詢、申請與監控

**Service Quotas** 是集中管理 quota 的 AWS 服務：

1. **查詢**：每個 quota 都有 quota code、預設值（default value）與目前套用值（applied value）。
2. **申請提高**：直接在 Service Quotas 提出 increase request，部分申請會自動核准，其他由 AWS 審核，需要一些時間，所以要**提前申請**，不要等到開賣當天。
3. **監控用量**：許多 quota 會在 CloudWatch 發布目前用量（多數在 `AWS/Usage` namespace，例如 EC2 vCPU 數、API 呼叫次數）。可以建立 CloudWatch alarm，用 metric math 的 `SERVICE_QUOTA()` 函數取得 quota 值並算出使用率，例如超過 80% 就通知。Lambda 則有自己的做法：AWS 建議用 `AWS/Lambda` 的 `ClaimedAccountConcurrency`（實際使用的非保留並行數加上所有 reserved／provisioned concurrency）除以 `SERVICE_QUOTA(ConcurrentExecutions)` 計算帳號 concurrency 使用率。
4. **Quota request template**：在 AWS Organizations 中設定一份範本，之後**新建立的帳號**會自動提出這些 quota 的提高申請，適合每個新 workload 帳號都需要較高 quota 的情況。

AWS Trusted Advisor 也有檢查 service limits 使用率的項目。Service Quotas 近年另外提供 **Automatic Management**：啟用後會監控支援的 quota，在使用率達 80%／95% 時透過 AWS Health、email 或 Slack 通知；選擇 Notify and Auto-Adjust 模式時，還會替可調整的 quota 自動提出提高申請（不保證核准）。

下面是 Wanderly 為 EC2 On-Demand（Standard 系列）vCPU 用量建立的使用率 alarm，確保開賣前加開的機器不會撞到上限：

```yaml
Ec2VcpuQuotaAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: ec2-ondemand-vcpu-over-80pct
    ComparisonOperator: GreaterThanThreshold
    Threshold: 80
    EvaluationPeriods: 3
    Metrics:
      - Id: usage
        ReturnData: false
        MetricStat:
          Metric:
            Namespace: AWS/Usage
            MetricName: ResourceCount
            Dimensions:
              - { Name: Service, Value: EC2 }
              - { Name: Resource, Value: vCPU }
              - { Name: Type, Value: Resource }
              - { Name: Class, Value: Standard/OnDemand }
          Period: 60
          Stat: Maximum
      - Id: pct
        Expression: (usage / SERVICE_QUOTA(usage)) * 100
        Label: EC2 On-Demand vCPU utilization
        ReturnData: true
```

`usage` 取得目前執行中 Standard 系列 On-Demand instance 的 vCPU 總數，`pct` 用 `SERVICE_QUOTA()` 算出它占 quota 的百分比，連續 3 分鐘超過 80% 就觸發。這讓團隊在撞到上限之前，而不是之後，知道要申請提高或調整設計。

> [!warning] 常見誤解
> 「DR Region 平時沒在用，quota 不重要。」正好相反。DR Region 的 quota 多半還是預設值，failover 時要一口氣啟動正式規模的容量，最容易撞到上限（第 34 章）。DR 計畫要包含「事先把 DR Region 的 quota 提高到能承受全部流量」。

## 35.7 Throttling：429、ThrottlingException 與 token bucket

Quota 是「上限是多少」，**throttling（限流）** 是「超過上限時發生什麼事」：服務拒絕多出來的請求，並告訴你「太快了，晚點再來」。常見的訊號：

| 來源 | 錯誤 |
|---|---|
| AWS API（EC2、IAM、CloudFormation…） | `ThrottlingException`、`RequestLimitExceeded`、`Rate exceeded` |
| API Gateway | HTTP 429 Too Many Requests |
| Lambda 同步呼叫 | HTTP 429 `TooManyRequestsException` |
| DynamoDB | `ProvisionedThroughputExceededException`（或 `ThrottlingException`） |
| S3 | HTTP 503 Slow Down |
| 第三方 API | 多半是 HTTP 429，可能附 `Retry-After` header |

### Token bucket：大多數限流背後的演算法

AWS 的很多限流（包括 API Gateway 與許多 AWS API）都以 **token bucket（權杖桶）** 演算法運作：

```text
              ① 以固定速率補充 token（例如每秒 100 個）
                          │
                          ▼
                  ┌───────────────┐
                  │ ● ● ● ● ● ● ● │  ② 桶子容量上限（burst，例如 200 個）
                  │ ● ● ● ● ●     │     滿了就不再增加
                  └───────┬───────┘
                          │
  請求 ──► ③ 每個請求拿走 1 個 token ──► 有 token：放行
                                    └──► 沒 token：throttle（429）
```

① 桶子以固定速率補充 token，這個速率就是**穩定速率（rate）**。② 桶子有容量上限，也就是 **burst（突發量）**：系統閒置一陣子後，可以一次放行最多 200 個請求。③ 每個請求取走一個 token，沒有 token 就被拒絕。所以一個「rate 100、burst 200」的限制，允許短暫衝到每秒 200 次，但長期平均只能每秒 100 次。

API Gateway 的限流分成幾層，請求必須全部通過：

1. **帳號層級**：每 Region 的預設 quota（上表）。
2. **Stage 與 method 層級**：你可以替某個 stage 或某個 method 設定更低的 rate 與 burst，例如讓 `/search` 不會吃光整個帳號的額度。
3. **Usage plan 與 API key**：替每個客戶（API key）設定 rate、burst 與每日／每月總量（quota），讓一個大客戶不會擠壓其他客戶。這是「依客戶分級限流」的標準答案。

### 不同服務的「熱點」限流

有些限流不是針對整個服務，而是針對一個熱點：

- **S3**：請求速率限制是**每個 prefix** 計算的。把所有物件放在同一個 prefix 下、每秒幾萬次讀取，就會看到 503 Slow Down；把物件分散到多個 prefix（例如 `photos/a1/`、`photos/b7/`），總速率就隨 prefix 數成長。S3 會自動調整，但需要一點時間，突然的尖峰仍可能短暫看到 503。
- **DynamoDB**：hot partition（35.4 節）。On-demand 模式能自動因應流量，但流量在極短時間內暴增到遠超過先前尖峰時，仍可能短暫 throttle。
- **Kinesis**：單一 shard 的上限，用更分散的 partition key 或增加 shard。

## 35.8 Retry 的正確寫法

被 throttle 或遇到暫時性錯誤時，重試是對的；但 Wanderly 的事故說明，**錯誤的重試比不重試更危險**。

### Exponential backoff 與 jitter

**Exponential backoff（指數退避）** 是每次重試前等待的時間呈指數成長：第一次等 100 ms、第二次 200 ms、第三次 400 ms……並設一個上限。這讓過載的服務有時間恢復。

但只有 backoff 還不夠。如果一萬個用戶端在同一刻失敗，它們會在同一刻等待 100 ms、在同一刻重試，造成一波又一波同步的尖峰。**Jitter（隨機抖動）** 在等待時間中加入隨機值，把重試打散。最常用的是 full jitter：

> 等待時間 = random(0, min(上限, 基礎時間 × 2^重試次數))

### AWS SDK 已經幫你做了

呼叫 AWS 服務時，AWS SDK 內建 retry 機制，有三種模式：

- **legacy**：舊預設，各語言 SDK 行為不完全一致。
- **standard**：跨 SDK 一致的行為，預設最多 3 次嘗試（含第一次），使用帶 jitter 的指數退避，並有一個 retry quota（也是 token bucket 的概念），在大量失敗時自動減少重試，避免放大。
- **adaptive**：在 standard 之上加入用戶端的速率限制，根據收到的 throttle 回應自動降低送出速率，適合「單一用戶端大量呼叫、經常被 throttle」的批次工作。

```python
import boto3
from botocore.config import Config

# 批次匯入工作：大量呼叫 DynamoDB，讓 SDK 依 throttle 回應自動調整速率
config = Config(retries={"max_attempts": 8, "mode": "adaptive"})
dynamodb = boto3.client("dynamodb", config=config)
```

### 重試放大與「只在一層重試」

Wanderly 的 27 倍放大來自**多層重試**：前端、訂房服務、庫存服務各重試 3 次（含第一次，每層 3 次嘗試），3 × 3 × 3 = 27。下游越慢、越接近崩潰，上游送來的流量反而越多，這就是 **retry storm（重試風暴）**。修正原則：

1. **只在一層重試**，通常是最靠近失敗點的那一層，其他層直接回傳錯誤。
2. **限制總次數與總時間**：重試次數加上 timeout 不能超過呼叫者願意等待的時間。
3. **只重試會成功的錯誤**：429、503、逾時值得重試；400（參數錯誤）、403（權限不足）重試一百次也一樣失敗。
4. **尊重 `Retry-After`**：對方告訴你要等多久，就照做。
5. **只重試冪等的操作**，或帶 idempotency key（35.5 節）。

### Circuit breaker：連續失敗時停止嘗試

**Circuit breaker（斷路器）** 監控對某個依賴的呼叫結果。失敗率超過門檻時「跳開」：接下來一段時間直接回傳錯誤或 fallback，完全不呼叫該依賴，讓它有時間恢復；過一陣子再放少量請求試探，成功了就「閉合」恢復正常。它和 retry 互補：retry 處理偶發的錯誤，circuit breaker 處理持續的故障。

## 35.9 過載時的保護：load shedding 與 graceful degradation

前面幾節讓系統能擴展、能正確重試。但總會有擴展跟不上的時刻：流量在幾秒內暴增，新機器還在開機。這時系統要能**主動放棄一部分工作**，保住最重要的那部分。

### Load shedding：寧可快速拒絕，也不要全部變慢

**Load shedding（負載卸除）** 是在伺服器過載時，主動拒絕一部分請求（回傳 503 或 429），讓剩下的請求能在正常時間內完成。

聽起來違反直覺，但想想不這麼做會怎樣：伺服器接下所有請求，每個請求都變慢，超過用戶端的 timeout，用戶端放棄並重試，伺服器卻還在處理那些已經沒人要的請求。最後伺服器 100% 忙碌，成功完成的請求卻是 0，這叫 **goodput（有效產出）崩潰**。

有效的 load shedding 有幾個原則：

- **越早拒絕越便宜**：在 load balancer 或 API 入口就拒絕，比做完一半的資料庫查詢再放棄好得多。
- **依優先級拒絕**：先丟掉不重要的流量（爬蟲、預先載入、推薦），保留付款與訂房。
- **丟掉已經過期的工作**：從 queue 拿到的請求，如果已經超過用戶端的 timeout，直接丟棄而不是處理。
- **限流與 load shedding 互補**：API Gateway 的限流是「依事先設定的上限拒絕」，load shedding 是「依伺服器當下的實際負載拒絕」。

### Graceful degradation：功能可以少，服務不能停

**Graceful degradation（優雅降級）** 是在依賴故障或過載時，提供**較少但仍然有用**的功能，而不是整個失敗。關鍵是事先把功能分成「核心」與「加值」：

| 功能 | 分類 | 依賴故障時的降級方式 |
|---|---|---|
| 搜尋旅館、訂房、付款 | 核心 | 不降級，優先保留資源 |
| 為你推薦 | 加值 | 改顯示靜態的熱門旅館清單 |
| 即時價格比較 | 加值 | 顯示快取的價格並標示「價格可能變動」 |
| 評論 | 加值 | 暫時隱藏，或顯示快取版本 |
| 圖片縮圖產生 | 加值 | 顯示原圖或預設圖 |

賞櫻季那晚，首頁轉不出來是因為頁面**同步等待**推薦服務。修正方式有三個層次：

1. **Timeout + fallback**：呼叫推薦服務設定短 timeout（例如 300 ms），逾時就顯示預設清單。搭配 circuit breaker，推薦服務持續故障時直接跳過不呼叫。
2. **Feature flag**：用 **AWS AppConfig**（第 37 章）的 feature flag 在開賣前或過載時直接關掉加值功能，不需要重新部署。
3. **靜態後備**：CloudFront 可以設定 origin failover（主要 origin 回傳錯誤時改用次要 origin，例如 S3 上的靜態頁面）與 custom error page，讓最壞情況下使用者至少看到一個說明頁而不是錯誤畫面。

> [!tip] 考試提示
> 題目說「某個非關鍵依賴故障時，核心功能必須繼續運作」，答案方向是 timeout、circuit breaker、fallback 與 feature flag，而不是「把非關鍵依賴也做成 Multi-Region」。

## 35.10 隔離故障：bulkhead、cell 與 shuffle sharding

Load shedding 和降級處理的是「過載時怎麼辦」。另一類問題是：**一個壞掉的部分，怎麼不讓它拖垮其他部分？**答案是隔離，而 AWS 架構中有三種常見的隔離設計，範圍由小到大。

### Bulkhead：分艙，讓一艙進水不會沉船

**Bulkhead（艙壁）** 的名稱來自船艙的隔板：一艙進水，其他艙不受影響。軟體裡的意思是**把資源分成獨立的池，各自服務不同的工作**。

Wanderly 賞櫻季的第一個問題，就是缺少 bulkhead：所有 Lambda 函數共用 1,000 個 concurrency，訂房函數把它吃光，寄信與對帳也停了。AWS 上的 bulkhead 做法：

- **Lambda reserved concurrency**：替每個函數設定保留的 concurrency。它有兩個作用：**保證**這個函數至少能用到這麼多，同時也是這個函數的**上限**。例如對帳函數保留 50，訂房函數最多 700，就算訂房暴增也搶不走對帳的額度；同時訂房最多 700 個 concurrency，也間接保護了後面的資料庫。
- **分開的 queue**：VIP 訂單、一般訂單、通知各用自己的 SQS queue 與 worker，一種工作的積壓不會拖慢其他種類。
- **分開的連線池與執行緒池**：呼叫推薦服務與呼叫付款服務各用自己的連線池，推薦服務變慢只會耗盡它自己的池。
- **分開的帳號**：不同 workload 放不同 AWS 帳號，quota 天然隔離（第 40 章）。

### Cell-based architecture：把整套系統複製成多個小格

Bulkhead 隔離的是一個系統內的資源。**Cell-based architecture（細胞式架構）** 走得更遠：把**整套系統**（應用程式、資料庫、queue）複製成多個完全獨立的 **cell（細胞）**，每個 cell 只服務一部分客戶。

```text
                      使用者請求（帶 member ID）
                                │
                     ┌──────────▼──────────┐
                     │ Cell router（薄層）  │ ① 依 member ID 決定 cell，邏輯越簡單越好
                     └───┬───────┬───────┬─┘
                         │       │       │
        ┌────────────────▼┐ ┌────▼────────┐ ┌▼────────────────┐
        │ Cell 1           │ │ Cell 2      │ │ Cell 3           │
        │ API→App→DB→Queue │ │ API→App→DB… │ │ API→App→DB→Queue │ ② 每個 cell 是完整的一套
        │ 會員 A–H         │ │ 會員 I–P    │ │ 會員 Q–Z         │
        └──────────────────┘ └─────────────┘ └──────────────────┘
               ③ Cell 2 因錯誤部署故障 → 只影響約 1/3 的會員
```

① **Cell router** 是唯一共享的元件，所以它要盡量簡單（例如查一張對應表或依 hash 計算），本身也要高可用。② 每個 cell 是完整、獨立的一套，cell 之間不互相呼叫。③ 任何一個 cell 因為錯誤部署、資料問題或過載而故障，影響範圍（**blast radius，爆炸半徑**）只有那個 cell 的客戶。

Cell 架構的另一個好處是**擴展方式可預測**：每個 cell 有固定的最大規模，並且被充分測試過；成長時是「加一個 cell」而不是「把一個系統越撐越大」，永遠不會跑到沒測試過的規模。部署也可以一次只更新一個 cell，搭配第 37 章的漸進式部署。代價是更多重複的基礎設施，以及 cell router 與跨 cell 功能（例如全站搜尋）的額外設計。

### Shuffle sharding：讓每個客戶分到不同的組合

**Shuffle sharding（洗牌分片）** 解決的是「吵鬧的鄰居（noisy neighbor）」問題，特別適合多租戶服務。

假設有 8 台 worker 服務很多客戶。如果用一般的 sharding，把 8 台分成 4 組、每組 2 台，某個客戶送來會讓 worker 當掉的「毒藥請求」，會搞垮它那一組，同組的所有客戶（約 1/4）都跟著受害。

Shuffle sharding 則讓**每個客戶隨機分到 8 台中的某 2 台**。從 8 台選 2 台的組合有 C(8,2) = **28 種**。某個客戶的毒藥請求搞垮了它的那 2 台 worker 時：

- 和它組合**完全相同**的客戶才會完全失去服務，機率約 1/28。
- 只有 1 台重疊的客戶，還有另一台 worker 可用，搭配重試仍能得到服務。

Worker 數量和每個客戶分到的數量越大，組合數就增加得越快，隔離效果越好。AWS 自己在 Route 53 等服務中就使用這個技巧，讓單一客戶遭受的 DDoS 攻擊不會影響其他客戶。

## 35.11 效能測試與 Compute Optimizer

前面所有的設計都基於一個假設：你知道系統的極限在哪裡。賞櫻季前 Wanderly 從沒做過壓力測試，所以這個假設不成立。

### 效能測試的種類

| 測試 | 怎麼做 | 回答的問題 |
|---|---|---|
| Load test（負載測試） | 以預期的尖峰流量持續一段時間 | 預期尖峰時延遲與錯誤率是否符合 SLO？ |
| Stress test（壓力測試） | 持續加壓直到出錯 | 極限在哪裡？第一個壞掉的是誰？壞掉的方式是否優雅？ |
| Spike test（尖峰測試） | 流量在幾秒內暴增 | Auto Scaling、quota、cache 能否跟上突然的變化？ |
| Soak test（長時間測試） | 正常負載持續數小時到數天 | 是否有記憶體洩漏、連線洩漏、磁碟慢慢塞滿？ |

做效能測試要注意幾件事：

- **在類似正式的環境測試**，包含相同的 instance 規格、資料量與 quota；在空資料庫上測出的結果沒有參考價值。
- **測到出錯為止**，並記錄是哪個元件、用什麼方式出錯，這就是你的下一個瓶頸。
- **大規模測試要事先確認**：測試流量本身也會撞到 quota 或觸發防護，要先確認 quota，並遵守 AWS 對網路壓力測試的政策。
- AWS 提供 **Distributed Load Testing on AWS** 解決方案，用 Fargate 上的多個容器產生大量流量；也可以使用你熟悉的開源工具。

### AWS Compute Optimizer：規格合不合適

效能問題的另一面是浪費：為了保險選了太大的 instance。**AWS Compute Optimizer** 用機器學習分析資源過去的 CloudWatch 使用率，提出規格建議，並把每個資源分類為 **under-provisioned（規格不足）**、**over-provisioned（規格過大）** 或 **optimized**。

- 支援的資源包括 EC2 instance、Auto Scaling group、EBS volume、Lambda function（記憶體大小）、Fargate 上的 ECS service，以及 RDS／Aurora 等。
- 需要先 **opt-in**（啟用），可以在 Organizations 的層級為所有帳號啟用。
- 預設分析過去 14 天的 metrics；付費的 **enhanced infrastructure metrics** 可以延長分析期間，對有月週期的工作負載更準確。
- **記憶體使用率不在 EC2 的預設 metrics 裡**，要安裝 CloudWatch agent 收集，Compute Optimizer 才能把記憶體納入建議。沒有記憶體資料時，它可能建議一個 CPU 足夠但記憶體不夠的規格。

Compute Optimizer 在第 39 章的成本最佳化會再次出現；在本章它的角色是幫你發現「規格不足」，也就是潛在的效能瓶頸。

## 35.12 比較與選型

### 擴展手段選擇

```text
瓶頸在哪一層？
├─ 讀取
│   ├─ 大量重複的相同查詢 → Cache（ElastiCache；DynamoDB 用 DAX；靜態內容用 CloudFront）
│   └─ 查詢各不相同、可接受些微延遲 → Read replica／Aurora reader endpoint
├─ 寫入
│   ├─ 可以非同步完成 → SQS 削峰 + 有上限的 worker
│   ├─ 單一資料庫到極限 → Scale up／Aurora／改 DynamoDB；最後才自建 sharding
│   └─ DynamoDB 某些 key 特別熱 → 重新設計 partition key
├─ 運算 → 水平擴展（先確認 stateless、idempotent、下游撐得住）
├─ 連線數 → RDS Proxy
└─ 429／Throttling
    ├─ 是自己帳號的 quota → Service Quotas 申請提高 + 用量 alarm
    ├─ 要依客戶分級限流 → API Gateway usage plan + API key
    └─ 是暫時性的 → SDK retry（standard／adaptive）+ backoff + jitter
```

### 韌性模式對照

| 模式 | 解決的問題 | AWS 上的實作 | 代價 |
|---|---|---|---|
| Retry + backoff + jitter | 暫時性錯誤 | AWS SDK retry modes | 重試過多會放大負載 |
| Circuit breaker | 依賴持續故障時不再浪費資源 | 應用程式程式庫、Step Functions 狀態 | 需要設計 fallback |
| Load shedding | 過載時保住有效產出 | 入口限流、依優先級拒絕 | 部分使用者被拒絕 |
| Graceful degradation | 非核心依賴故障拖垮核心 | Timeout、fallback、AppConfig feature flag、CloudFront origin failover | 需要事先分類功能 |
| Bulkhead | 一種工作吃光共享資源 | Lambda reserved concurrency、分開的 queue、分開的帳號 | 資源利用率較低 |
| Cell-based | 錯誤部署或故障影響所有客戶 | 每個 cell 一套 stack（常搭配獨立帳號）+ cell router | 重複的基礎設施 |
| Shuffle sharding | 吵鬧鄰居影響同組客戶 | 每個客戶分配不同的資源組合 | 分配邏輯較複雜 |

## 35.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 資料庫 CPU 高、大量重複讀取相同資料 | ElastiCache（cache-aside）；DynamoDB 用 DAX |
| 報表查詢拖慢交易資料庫 | Read replica（或 Aurora reader endpoint） |
| 寫入尖峰壓垮資料庫，可以非同步處理 | SQS 削峰 + 依 backlog 擴展的 worker |
| Lambda 大量連線耗盡 RDS 連線數 | RDS Proxy |
| Auto Scaling 加了機器但使用者被登出 | Session 外部化到 ElastiCache／DynamoDB |
| 提前知道快達到 quota | Service Quotas 的 CloudWatch 用量 alarm（`SERVICE_QUOTA()`）、Trusted Advisor |
| 所有新帳號都需要較高的 quota | Organizations 的 quota request template |
| 依客戶設定不同的 API 請求上限 | API Gateway usage plan + API key |
| 呼叫 AWS API 出現 ThrottlingException | SDK retry（exponential backoff + jitter；adaptive 模式） |
| S3 出現 503 Slow Down | 把物件分散到多個 prefix |
| DynamoDB 某些 key throttle，但整體容量充足 | Hot partition，重新設計高基數的 partition key |
| 一個 Lambda 函數吃光帳號 concurrency | Reserved concurrency（bulkhead） |
| 非關鍵功能故障導致整頁失敗 | Timeout + fallback、circuit breaker、feature flag |
| 限制錯誤部署或故障的影響範圍 | Cell-based architecture |
| 多租戶中單一租戶影響其他租戶 | Shuffle sharding、per-tenant 限流 |
| 找出規格過大或不足的 EC2／Lambda | Compute Optimizer（記憶體需 CloudWatch agent） |

**常見陷阱**：

1. 以為 read replica 可以分擔寫入：寫入永遠只在 primary。
2. 以為 queue 能增加處理能力：它只是延後處理，要監控最舊訊息的年齡。
3. 以為 quota 都能調整：Lambda 15 分鐘、DynamoDB 400 KB、partition 吞吐等是設計限制，只能改架構。
4. 每一層都加重試：多層重試會指數放大流量，應該只在一層重試並加上 jitter。
5. 以為 reserved concurrency 只是「保證」：它同時是上限，設太低會讓該函數自己被 throttle。
6. 以為 Compute Optimizer 的 EC2 建議一定包含記憶體：沒有 CloudWatch agent 就沒有記憶體資料。

## 35.14 SAP 加深：組織規模的容量與隔離

SAP 題目會把本章的模式放進多帳號、大規模的情境：上百個帳號的 quota 怎麼管？多租戶 SaaS 怎麼隔離？DR 時的容量怎麼保證？

### 多帳號的 quota 治理

- **帳號就是 quota 的邊界**：大多數 quota 以帳號為單位，所以把大型 workload 拆到多個帳號（第 40 章）本身就是一種擴展與隔離手段。但也代表每個帳號都要各自管理 quota。
- **Quota request template**：為新帳號自動申請一組標準 quota，配合 Control Tower 的帳號建立流程（Account Factory）使用。
- **集中監控**：每個帳號建立 `SERVICE_QUOTA()` 使用率 alarm（可用 CloudFormation StackSets 派送，第 37 章），並把事件集中到營運帳號；搭配第 36 章的 cross-account observability。

### 容量保證：On-Demand Capacity Reservations

Quota 只是「允許你用多少」，不代表 AWS 在那個 AZ 一定有空的容量。對 DR 或大型活動這種「那一刻一定要有機器」的需求，可以使用 **On-Demand Capacity Reservations（ODCR，隨需容量預留）**：在特定 AZ 預留特定 instance type 的容量，不需要長期承諾，但預留期間不論是否使用都要付費。它可以和 Savings Plans 或 Regional Reserved Instances 的折扣搭配（第 39 章）。這與第 34 章的 static stability 精神一致：重要的容量要在出事前就拿到手。

### 多租戶 SaaS 的隔離層次

第 49 章會深入多租戶 SaaS。與本章相關的設計選擇是：

| 隔離層次 | 做法 | 隔離程度 | 成本 |
|---|---|---|---|
| 共用一切，邏輯隔離 | 同一套 stack，以 tenant ID 區分，per-tenant 限流（usage plan） | 低 | 最低 |
| Shuffle sharding | 每個 tenant 分配不同的資源組合 | 中 | 低 |
| Cell | 每個 cell 服務一群 tenant | 中高 | 中 |
| 每個 tenant 一個帳號或一套 stack | 大客戶獨立部署 | 最高 | 最高 |

實務上常混用：小客戶共用 cell，大客戶（或有合規需求的客戶）獨立 cell 或帳號。

### 把韌性模式寫進架構決策

SAP 題目常描述一個「已經上線、問題頻傳」的系統，要你選出最有效的改善。判斷順序通常是：先找出共享的故障點（共用 quota、共用資料庫、同步呼叫鏈），再選擇最小改動就能隔離它的模式。例如「一個租戶的批次匯入讓所有租戶的 API 變慢」，答案是 per-tenant 限流加上把批次工作移到獨立 queue 與 worker（bulkhead），而不是把整個資料庫換成更大的規格。

> - [AWS SDK retry 行為](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html)

## 本章重點整理

- 擴展前先找瓶頸：看 p99 而不是平均延遲，用 Little's Law 估算需要的並行量，並記住下游變慢會讓上游需要的容量暴增。
- 重複讀取用 cache（ElastiCache、DAX、CloudFront），不重複的讀取用 read replica；read replica 是非同步的，寫入仍只在 primary。
- 寫入擴展依序考慮 scale up 或更適合的資料庫、DynamoDB 的高基數 partition key，最後才自建 sharding；可以非同步的寫入用 SQS 削峰。
- Queue 只是延後處理而不是增加容量，要監控最舊訊息的年齡，worker 擴展要有上限以保護下游。
- 水平擴展的前提是 stateless、檔案放 S3、操作冪等（idempotency key）、設定外部化、啟動快且下游撐得住；大量短連線用 RDS Proxy。
- Service quota 多為每帳號每 Region，分為可調整與不可調整；用 Service Quotas 提前申請，並以 CloudWatch 用量 metric 與 `SERVICE_QUOTA()` 建立使用率 alarm。
- Organizations 的 quota request template 讓新帳號自動申請標準 quota；DR Region 的 quota 必須事先提高。
- Throttling 的訊號包括 429、ThrottlingException、ProvisionedThroughputExceededException 與 S3 503 Slow Down；token bucket 以穩定速率加 burst 容量運作。
- API Gateway 限流分帳號、stage／method 與 usage plan（API key）三層；依客戶分級限流用 usage plan。
- Retry 要用 exponential backoff 加 jitter、只在一層重試、只重試暫時性錯誤與冪等操作；AWS SDK 的 standard 與 adaptive 模式已內建這些行為。
- Load shedding 在過載時越早、依優先級拒絕請求，避免 goodput 崩潰；graceful degradation 用 timeout、circuit breaker、fallback 與 feature flag 保住核心功能。
- Bulkhead 把資源分池隔離，Lambda reserved concurrency 同時是保證與上限；cell-based architecture 把整套系統切成獨立 cell 限制 blast radius；shuffle sharding 讓每個客戶分到不同資源組合以隔離吵鬧鄰居。
- 效能測試包括 load、stress、spike、soak，要在類似正式的環境測到出錯為止；Compute Optimizer 分析規格是否合適，記憶體資料需要 CloudWatch agent。

## 本章練習題

### 練習 35-1｜SAA｜單選｜重複讀取造成資料庫過載

Wanderly 的旅館詳細頁面每秒被瀏覽約 8,000 次，每次都會對 RDS for MySQL 查詢旅館的基本資料與設施清單。這些資料平均一天只更新數次，可以接受最多 5 分鐘的延遲。資料庫 CPU 在尖峰時長期超過 90%，且 Performance Insights 顯示負載幾乎都來自同一組查詢。

哪個做法最能降低資料庫負載？

- A. 部署 Amazon ElastiCache，應用程式以 cache-aside 模式先查快取，未命中時才查資料庫並寫回快取，TTL 設為 5 分鐘
- B. 為資料庫建立 5 個 read replica，並讓應用程式隨機選擇一個 replica 連線
- C. 把 RDS instance 升級到兩倍大的 instance class
- D. 啟用 RDS Multi-AZ，讓 standby 分擔讀取查詢

> [!answer]- 答案：A
> **A ✓** 負載幾乎都來自重複的相同查詢，且資料可以接受 5 分鐘延遲，這正是 cache 的最佳情境。命中率高時，資料庫只需處理極少數 cache miss，負載大幅下降，記憶體讀取的延遲也更低。
>
> **B ✗** Read replica 可以分擔讀取，但每個 replica 都還是要執行同樣的查詢，成本較高；對完全重複的查詢，cache 的效率高得多。若查詢彼此不同、命中率低時，read replica 才是較好的選擇。
>
> **C ✗** Scale up 可以暫時緩解，但成本加倍且仍有上限，沒有解決「重複做同一件事」的根本問題。
>
> **D ✗** RDS Multi-AZ（單一 standby 部署）的 standby 不能處理讀取，只用於 failover。
>
> **考點**：SAA-3.3、SAA-2.1｜cache-aside 降低資料庫讀取負載

### 練習 35-2｜SAA｜單選｜報表查詢與交易分離

Wanderly 的財務團隊每天上午會對 Aurora PostgreSQL 執行大量複雜的報表查詢，期間訂房交易的延遲明顯上升。報表可以接受資料延遲數秒，每次查詢的條件都不同。團隊希望以最少的應用程式修改解決問題。

最合適的做法是什麼？

- A. 在報表查詢前後暫時停止訂房服務
- B. 把報表查詢的結果全部放進 ElastiCache，並設定 24 小時的 TTL
- C. 在叢集中加入 Aurora Replica，並把報表工具的連線改為叢集的 reader endpoint
- D. 把 Aurora 叢集轉換成 Aurora Global Database，並在同一 Region 加入 secondary cluster

> [!answer]- 答案：C
> **C ✓** Aurora Replica 與 writer 共用儲存層，複寫延遲很低；reader endpoint 會自動在 replica 之間分散連線。把報表工具改連 reader endpoint，只需要修改一個連線設定，報表負載就離開了處理交易的 writer。
>
> **A ✗** 停止核心交易服務違反業務需求，不是可接受的做法。
>
> **B ✗** 每次報表查詢的條件都不同，cache 的命中率很低，無法有效分擔負載；而且 24 小時 TTL 會讓報表資料過舊。
>
> **D ✗** Aurora Global Database 的 secondary cluster 是放在其他 Region、用於跨 Region DR 與本地讀取，不是用來在同一 Region 分擔讀取；同 Region 加 Aurora Replica 更簡單也更便宜。
>
> **考點**：SAA-3.3｜read replica 與 Aurora reader endpoint

### 練習 35-3｜SAA｜單選｜寫入尖峰削峰

Wanderly 在限時優惠開賣的前 10 分鐘，每秒會收到約 6,000 筆訂單建立請求，平常只有每秒 200 筆。資料庫在尖峰時無法承受這麼多寫入，導致大量請求逾時。產品團隊同意使用者在送出訂單後先看到「訂單處理中」，並在 2 分鐘內收到確認。

哪個架構最合適？

- A. 把應用程式 Auto Scaling group 的最大容量提高到原本的 30 倍
- B. API 把訂單寫入 Amazon SQS queue 後立即回應，worker 以資料庫能承受的速度從 queue 處理訂單，並依 backlog 自動擴展到設定的上限
- C. 在資料庫前加入 ElastiCache，讓訂單先寫入快取
- D. 為資料庫建立多個 read replica，把訂單寫入分散到 replica

> [!answer]- 答案：B
> **A ✗** 瓶頸在資料庫的寫入能力，增加應用程式伺服器只會讓更多請求同時打到資料庫，情況更糟。
>
> **B ✓** SQS 幾乎可以無限擴展，API 寫入 queue 後立刻回應；worker 以穩定的速度處理，尖峰被攤平成較長的處理時間。依 backlog 擴展並設上限，既能在 2 分鐘內消化，又不會壓垮資料庫。
>
> **C ✗** ElastiCache 是用來加速讀取的快取，把訂單只寫在快取裡有遺失資料的風險，也沒有解決最終寫入資料庫的瓶頸。
>
> **D ✗** Read replica 是唯讀的，無法接受寫入。
>
> **考點**：SAA-2.1｜SQS 削峰與鬆耦合

### 練習 35-4｜SAA｜選兩項｜讓應用程式可以水平擴展

Wanderly 的會員網站在 Auto Scaling group 擴展後出現兩個問題：新加入的 instance 幾乎分不到既有使用者的流量，而 instance 被縮減時，使用者會被登出；另外，使用者上傳的大頭照有時候顯示不出來。調查發現應用程式把 session 存在本機記憶體，上傳的照片存在 instance 的 EBS volume。ALB 啟用了 sticky session。

哪兩個修改最能讓應用程式正確地水平擴展？（選兩項）

- A. 把 session 存到 Amazon ElastiCache 或 DynamoDB，並停用 ALB 的 sticky session
- B. 把 sticky session 的 cookie 有效期限延長到 7 天
- C. 把 Auto Scaling group 改為固定容量，停止縮減
- D. 讓應用程式把上傳的照片直接存到 Amazon S3，並以 S3（或 CloudFront）提供讀取
- E. 為每台 instance 建立更大的 EBS volume，並在 instance 之間用 rsync 同步照片

> [!answer]- 答案：A、D
> **A ✓** Session 外部化後，任何 instance 都能處理任何使用者的請求，新 instance 立即能分擔流量，縮減 instance 也不會讓使用者登出；不再需要 sticky session。
>
> **B ✗** 延長 sticky cookie 只會讓流量更固定在舊 instance 上，惡化新 instance 分不到流量的問題，縮減時使用者仍會被登出。
>
> **C ✗** 停止縮減只是迴避問題，喪失 Auto Scaling 的彈性與成本效益，也沒有解決照片的問題。
>
> **D ✓** 照片存在共享且高耐久的 S3，任何 instance 都讀得到，instance 被替換時也不會遺失資料。
>
> **E ✗** 用 rsync 同步多台 instance 的本機檔案既脆弱又有延遲，instance 被終止時尚未同步的照片會遺失，營運負擔高。
>
> **考點**：SAA-2.1、SAA-3.2｜stateless 設計與水平擴展前提

### 練習 35-5｜SAA｜單選｜提前發現 quota 不足

Wanderly 的 serverless 訂房平台在東京 Region 使用數十個 Lambda 函數。過去一次促銷中，帳號的 Lambda concurrency 達到上限，函數開始被 throttle，團隊卻是在客戶抱怨後才發現。團隊希望日後在用量達到 quota 的 80% 時就自動收到通知，且不需要自己撰寫程式定期查詢。

最合適的做法是什麼？

- A. 為每個 Lambda 函數設定 reserved concurrency，總和等於 Region quota
- B. 撰寫排程 Lambda，每 5 分鐘呼叫 Lambda API 計算所有函數的 concurrency 並與 quota 比較
- C. 開啟 Lambda 函數的 X-Ray tracing，在 trace 中觀察 throttle 事件
- D. 建立 CloudWatch alarm，以 metric math 將 Lambda 發布的 `ClaimedAccountConcurrency` 除以 `SERVICE_QUOTA(ConcurrentExecutions)` 算出使用率，超過 80% 時透過 SNS 通知

> [!answer]- 答案：D
> **A ✗** Reserved concurrency 用於隔離與限制個別函數，把總和設成 quota 不會產生通知，反而可能讓未設定的函數完全沒有 concurrency 可用。
>
> **B ✗** 技術上可行，但需要自己撰寫與維護程式，違反需求；CloudWatch 已經提供 concurrency metric 與 `SERVICE_QUOTA()` 函數。
>
> **C ✗** X-Ray 用來追蹤請求路徑與延遲，是事後觀察，不能在接近 quota 時主動通知。
>
> **D ✓** Lambda 會在 CloudWatch 發布 `ClaimedAccountConcurrency`（已被占用、無法再給一般呼叫使用的 concurrency），metric math 的 `SERVICE_QUOTA()` 則取得目前套用的 quota 值，兩者相除就是使用率，這也是 AWS 文件建議的做法。Alarm 在超過 80% 時觸發並透過 SNS 通知，全部是受管功能，不需要自己寫程式；quota 提高後，`SERVICE_QUOTA()` 也會自動反映新值。
>
> **考點**：SAA-2.1、SAA-3.2｜Service Quotas 用量監控

### 練習 35-6｜SAA｜單選｜AWS API 被限流

Wanderly 有一個每晚執行的批次工作，會對數十萬個 EC2 snapshot 呼叫 `DescribeSnapshots` 與 `CreateTags`。執行一段時間後，工作經常因為 `RequestLimitExceeded` 錯誤中斷。工作是用 Python 與 boto3 撰寫，目前遇到錯誤時會立即重試，最多 10 次。團隊希望工作能穩定完成，並對 EC2 API 造成最小的衝擊。

最合適的修改是什麼？

- A. 改用多執行緒同時發出更多請求，讓工作更早完成
- B. 移除自訂的立即重試，改用 boto3 的 standard 或 adaptive retry 模式，讓 SDK 以帶 jitter 的 exponential backoff 重試，並在被 throttle 時自動降低送出速率
- C. 向 AWS 申請把 EC2 API 的 throttling 完全停用
- D. 把重試次數從 10 次提高到 100 次

> [!answer]- 答案：B
> **A ✗** 同時發出更多請求會更快耗盡 API 的 token bucket，throttle 更嚴重。
>
> **B ✓** `RequestLimitExceeded` 是暫時性的限流錯誤。立即重試只會讓請求在 token 還沒補充前再次失敗；exponential backoff 加 jitter 讓請求分散在時間上，adaptive 模式還會依 throttle 回應在用戶端主動降速，讓工作穩定完成並減少對 API 的壓力。
>
> **C ✗** API 速率限制是 AWS 保護服務的機制，無法完全停用；部分 API 速率可以申請調整，但不能取消。
>
> **D ✗** 不加等待地增加重試次數，只會產生更多被拒絕的請求，讓限流持續更久。
>
> **考點**：SAA-2.1｜SDK retry 模式、exponential backoff 與 jitter

> **D ✗** 提高帳號層級的 quota 只會讓失控的夥伴能送出更多請求，無法隔離它對其他夥伴的影響。

### 練習 35-10｜SAA｜單選｜保護關鍵函數

Wanderly 在同一個帳號與 Region 執行約 40 個 Lambda 函數。促銷期間，搜尋函數的流量暴增並用掉幾乎所有的帳號 concurrency，導致處理付款回呼的函數被 throttle，部分付款狀態沒有更新。付款回呼函數平時最多只需要 100 個 concurrency。

哪個做法最能確保付款回呼函數在任何情況下都有足夠的執行容量？

- A. 為付款回呼函數設定 provisioned concurrency 為 10
- B. 把付款回呼函數的記憶體提高到 10,240 MB，讓它執行得更快
- C. 為付款回呼函數設定 reserved concurrency 為 100，並考慮為搜尋函數也設定 reserved concurrency 作為上限
- D. 把付款回呼改為由 SQS 觸發，並把 visibility timeout 提高到 12 小時

> [!answer]- 答案：C
> **C ✓** Reserved concurrency 從帳號的 concurrency 中切出一塊專屬於該函數的額度，其他函數無法使用，這是 bulkhead 的做法；它同時也是該函數的上限，所以設為平時尖峰需求 100 即可。替搜尋函數設定 reserved concurrency 則限制它最多能用多少，進一步保護其他函數與後端。
>
> **A ✗** Provisioned concurrency 的作用是預先初始化執行環境以降低 cold start 延遲，10 個也遠低於需求的 100；它不是用來防止其他函數搶走額度的主要機制。
>
> **B ✗** 提高記憶體可能縮短執行時間，但不能保證在帳號 concurrency 被用光時取得執行機會。
>
> **D ✗** SQS 能緩衝訊息，但若 concurrency 仍被搜尋函數吃光，付款訊息只會在 queue 裡越積越多；而且延長 visibility timeout 與取得執行容量無關。
>
> **考點**：SAA-2.1、SAA-3.2｜Lambda reserved concurrency 作為 bulkhead

### 練習 35-12｜SAP｜選兩項｜非核心依賴的故障

Wanderly 的首頁會同步呼叫三個服務：搜尋（核心）、個人化推薦與即時評論摘要（非核心）。過去一個月推薦服務發生兩次長時間的高延遲，每次都讓首頁的 p99 延遲超過 10 秒，使用者也無法開始搜尋。產品要求：非核心服務故障時首頁必須在 1 秒內載入，並能讓營運團隊在大型活動前不經部署就關閉非核心功能。

哪兩個做法最能滿足需求？（選兩項）

- A. 把推薦服務部署到第二個 Region，並以 Route 53 failover routing 在故障時切換
- B. 對非核心服務的呼叫設定短 timeout 與 circuit breaker，失敗或逾時時改顯示預設內容（例如熱門旅館清單）
- C. 把首頁所有呼叫的 timeout 提高到 30 秒，讓慢的請求最終也能完成
- D. 在首頁與推薦服務之間加入 SQS queue，讓首頁等待 queue 中的推薦結果
- E. 使用 AWS AppConfig 的 feature flag 控制推薦與評論摘要是否顯示，讓營運團隊可以在活動前或故障時直接關閉

> [!answer]- 答案：B、E
> **A ✗** 高延遲通常來自服務本身的問題，第二個 Region 的同一套程式碼可能一樣慢；而且 DNS failover 不能保證首頁 1 秒內載入，成本也很高。這是把非關鍵依賴當成關鍵依賴處理。
>
> **B ✓** 短 timeout 讓首頁不會被慢的依賴拖住，circuit breaker 在推薦服務持續故障時直接跳過呼叫，fallback 顯示預設內容，核心的搜尋功能不受影響。這就是 graceful degradation。

> **C ✗** 延長 timeout 會讓首頁更慢，並讓更多請求同時卡在等待中，佔用更多資源。
>
> **D ✗** 首頁需要同步回應，讓它等待 queue 的結果並沒有消除等待，只是增加了一層延遲與複雜度。
>
> **E ✓** AppConfig feature flag 可以在執行期間開關功能，不需要重新部署，並支援逐步套用與驗證，符合「活動前不經部署就關閉非核心功能」。
>
> **考點**：SAP-2.4、SAP-3.4｜graceful degradation、circuit breaker 與 feature flag

### 練習 35-13｜SAP｜單選｜限制故障的影響範圍

Wanderly 的 B2B 訂房平台服務 2,000 家企業客戶，目前是單一一套大型 stack：一組 ECS service、一個 Aurora 叢集與一組 SQS queue。過去一年發生三次全面中斷：一次是錯誤部署、一次是單一客戶的異常資料觸發程式錯誤、一次是資料庫達到連線上限。公司要求單一事件最多只能影響約 10% 的客戶，並希望每次成長都在已測試過的規模內進行。

最合適的架構方向是什麼？

- A. 改為 cell-based architecture：把整套 stack 複製成多個獨立的 cell，每個 cell 服務一部分客戶並有固定的最大規模；以簡單的 cell router 依客戶 ID 導向，部署時一次更新一個 cell
- B. 把 Aurora 叢集升級為最大的 instance class，並加入 15 個 Aurora Replica
- C. 把 ECS service 拆成更多微服務，但繼續共用同一個 Aurora 叢集與 queue
- D. 建立第二個 Region 的 warm standby，在全面中斷時 failover

> [!answer]- 答案：A

>
> **B ✗** 更大的資料庫只能延後連線上限問題，無法防止錯誤部署或毒藥資料影響所有客戶。
>
> **C ✗** 拆微服務但共用資料庫與 queue，共享的故障點仍在，錯誤部署與資料庫連線耗盡仍會影響所有客戶。
>
> **D ✗** Warm standby 處理 Region 等級的故障，但錯誤部署與毒藥資料會一起出現在 DR 端，而且 failover 期間所有客戶都受影響，無法把影響限制在 10%。

### 練習 35-14｜SAP｜單選｜多租戶的吵鬧鄰居

最合適的做法是什麼？

- A. 把 16 台節點合併為 1 組，讓所有租戶共用所有節點
- B. 把分組改成 4 組、每組 4 台，讓每組的容量更大
- C. 為每個租戶建立專屬的 2 台節點
- D. 改用 shuffle sharding：每個租戶分配到從 16 台中隨機選出的 2 台節點組合，用戶端在一台節點失敗時重試另一台

>

>
> **D ✓** 從 16 台中選 2 台有 C(16,2) = 120 種組合，與問題租戶組合完全相同的租戶比例約 1/120；只重疊一台的租戶還有另一台可用，搭配重試仍能得到服務。在不增加節點的情況下大幅縮小影響範圍。
>

### 練習 35-15｜SAP｜單選｜重試風暴

Wanderly 的訂房流程呼叫鏈為：行動 App → API Gateway → 訂房服務（ECS）→ 庫存服務（ECS）→ 外部旅館 API。每一層在收到錯誤時都會立即重試 3 次。某天外部旅館 API 變慢並開始回傳 429，監控顯示外部 API 收到的請求數暴增到正常的數十倍，對方最後封鎖了 Wanderly 的來源 IP。團隊希望避免再次發生，同時在外部 API 恢復後能盡快恢復服務。

哪個做法最合適？

- A. 把每一層的重試次數提高到 5 次，增加成功的機會
- B. 移除所有層的重試，任何錯誤都直接回傳給使用者
- C. 只在最靠近外部 API 的庫存服務重試，使用有上限的 exponential backoff 加 jitter 並遵守 `Retry-After`；其他層不重試；並在庫存服務加入 circuit breaker，持續失敗時直接回傳錯誤或 fallback
- D. 把外部 API 的呼叫改到更多個 NAT Gateway，讓請求來自不同的 IP 以避開封鎖

> [!answer]- 答案：C
> **A ✗** 多層重試的放大是相乘的，提高次數會讓放大倍數更大，正是造成重試風暴的原因。
>
> **B ✗** 完全不重試會讓偶發的暫時性錯誤也直接失敗，降低可用性；正確做法是控制重試，而不是取消它。
>
> **C ✓** 只在一層重試消除了相乘的放大；exponential backoff 加 jitter 分散重試時間，遵守 `Retry-After` 尊重對方的限流；circuit breaker 在外部 API 持續故障時停止呼叫，讓對方有時間恢復，並以半開狀態試探，恢復後能快速回到正常。
>
> **D ✗** 用更多 IP 繞過對方的限流不但違反合作規範，還會讓過載的外部 API 承受更多流量，問題更嚴重。
>
> **考點**：SAP-3.4、SAP-2.4｜重試放大、backoff、jitter 與 circuit breaker

### 練習 35-16｜SAP｜選兩項｜過載時保住核心交易

Wanderly 的訂房 API 在大型促銷時偶爾會在幾秒內湧入超過 Auto Scaling 能即時應付的流量。上次促銷時，伺服器 CPU 100%，但成功完成的訂房數量反而降到接近 0：大部分請求在伺服器處理完之前就已經超過 App 的 10 秒 timeout，App 又自動重送。流量中約 40% 是價格追蹤爬蟲與 App 的背景預先載入請求。

- A. 在入口依請求優先級做 load shedding：伺服器負載超過門檻時，優先以 503 或 429 快速拒絕爬蟲與背景預先載入，保留訂房與付款請求
- B. 把伺服器的請求佇列加長，讓所有請求都能排隊等待處理
- C. 把 App 的 timeout 縮短到 1 秒，並讓它在逾時後立即重送 5 次
- D. 讓伺服器在開始處理前檢查請求已經等待的時間，丟棄已經超過用戶端 timeout 的請求，不再浪費資源處理沒人等待的工作
- E. 關閉 Auto Scaling，改為固定容量以避免擴展時的不穩定

> [!answer]- 答案：A、D
> **A ✓** Load shedding 越早、依優先級拒絕越有效：在入口快速拒絕低優先級流量的成本很低，騰出的資源讓訂房請求能在 timeout 內完成，有效產出因此回升。
>
> **B ✗** 更長的佇列只會讓每個請求等更久，更多請求在處理完成前就超過 App 的 timeout，伺服器忙著處理沒人等待的請求，正是 goodput 崩潰的原因。
>
> **C ✗** 縮短 timeout 並立即重送 5 次會讓流量成倍增加，加劇過載。
>
> **D ✓** 用戶端已經放棄的請求，處理完也沒有人會收到結果。在處理前丟棄已過期的請求，可以把資源留給仍在等待的請求，這是 load shedding 的重要技巧。
>
> **E ✗** 關閉 Auto Scaling 會讓系統在流量持續升高時完全無法增加容量；突發尖峰的問題應該用 load shedding 處理，而不是放棄擴展。
>
> **考點**：SAP-2.4、SAP-3.3｜load shedding 與 goodput
