# 第 34 章　高可用與災難復原：Multi-AZ、Multi-Region 與 DR 策略

> [!abstract] 本章地圖
> **你會學到**：
> - 分辨 instance、AZ、Region 三種 fault domain，以及「部署錯誤、資料損毀、勒索軟體」這類不受地理位置限制的故障
> - 把一個三層式架構的每一層都正確攤到多個 AZ，並找出藏在架構裡的單 AZ 共享依賴
> - 用 static stability 的觀念計算「失去一個 AZ 後還夠不夠用」，避免故障時才依賴 control plane
> - 依 RTO、RPO 與預算，在 backup & restore、pilot light、warm standby、multi-site active-active 之間做選擇，並畫出各自的架構
> - 使用 AWS Backup（plan、vault、Vault Lock、跨 Region／跨帳號 copy、restore testing）與 Elastic Disaster Recovery 建立可驗證的復原能力
> - 用 Route 53 failover、Application Recovery Controller、FIS 與 game day 讓 failover 真的能在壓力下執行
>
> **前置知識**：第 4 章（RTO／RPO、availability 與 durability）、第 9 章（Route 53 routing policy 與 health check）、第 18 章（Auto Scaling）、第 26 章（RDS 與 Aurora）
> **考試比重**：SAA ★★★（Domain 2 高可用與容錯）｜SAP ★★★（Domain 1 可靠架構、Domain 2 業務持續、Domain 3 改善可靠性）

## 34.1 故事：東京的一個 AZ 停電了

Wanderly 上線一年多，架構已經是教科書式的三層：ALB 在兩個 AZ、應用程式 EC2 由 Auto Scaling 管理、資料庫是 RDS for MySQL Multi-AZ。某個週五晚上，`ap-northeast-1a` 的一部分設施發生電力問題。監控畫面上，1a 的 EC2 一台接一台變成 unhealthy，RDS 在一分多鐘內自動 failover 到 1c。

大部分功能撐住了，但有兩件事讓值班的小林整晚沒睡。第一，訂房確認信全部寄不出去：負責寄信的 worker 只有一台，剛好跑在 1a，而且它是手動開的 EC2，不在 Auto Scaling group 裡。第二，1c 剩下的應用程式 EC2 在晚上的尖峰流量下 CPU 飆到 95%，Auto Scaling 想加機器，卻因為同時有大量客戶在搶 1c 的容量，新 instance 啟動得很慢，使用者看到二十分鐘的 5xx 錯誤。

事後檢討會上，CTO 問了一個更大的問題：「如果不是一個 AZ，而是整個東京 Region 都出問題，或是有人誤刪了訂單資料表，我們要多久才能恢復？會掉多少訂單？」沒有人答得出來。公司確實每天備份資料庫，但從來沒有人真的從備份還原過一次完整系統。

這一章要回答 CTO 的問題。我們先釐清故障可能發生在哪些層級，接著把 Multi-AZ 做到真正沒有單點，再進入跨 Region 的災難復原（**DR，Disaster Recovery**）：四種標準策略、各服務的跨 Region 複寫能力、AWS 提供的備份與復原工具，最後是怎麼證明這一切在真正出事時有用。

## 34.2 Fault domain：故障會在哪一層發生

**Fault domain（故障域）** 是「會一起壞掉的一組資源」。設計高可用的第一步，不是挑服務，而是先回答：我要撐過哪一種範圍的故障？撐過的方法，就是讓同一份能力分布在兩個以上、彼此獨立的 fault domain 裡。

| Fault domain | 典型故障 | 影響範圍 | 主要對策 |
|---|---|---|---|
| 單一 instance／host | 硬體故障、作業系統當機、記憶體洩漏 | 一台機器 | Auto Scaling 自動替換、多台 instance 放在 load balancer 後面 |
| Rack（機架） | 同機架的電源或交換器故障 | 同機架的多台機器 | Spread placement group（每個 AZ 每群組最多 7 台運作中的 instance） |
| AZ | 電力、冷卻、網路設施故障 | 一個或一組資料中心 | Multi-AZ：每一層都至少放兩個 AZ |
| Region | 大範圍服務事件、天災、區域性網路問題 | 整個 Region | Multi-Region DR 或 active-active |
| 邏輯故障 | 錯誤部署、誤刪資料、資料損毀、勒索軟體、憑證過期 | 不受地理限制，會跟著複寫擴散 | 版本化部署與 rollback、point-in-time backup、不可竄改的備份 |

第 2 章介紹過，一個 **AZ（Availability Zone，可用區域）** 由一個或多個獨立電力、冷卻與網路的資料中心組成，同一 Region 的 AZ 之間有低延遲的專用網路，距離夠遠以避免一起受災，又夠近可以做同步複寫。這個「夠近可以同步」的特性，就是 Multi-AZ 可以做到幾乎零資料遺失的原因；跨 Region 距離遠，只能非同步複寫，所以 Multi-Region 幾乎一定要接受一點資料遺失，或付出延遲的代價。

表格最後一列最容易被忽略。Multi-AZ 與跨 Region 複寫保護的是「地點」，但如果工程師下了一個 `DELETE FROM bookings`，這個刪除會在幾毫秒內被同步到 standby、在一秒內被複寫到另一個 Region。**複寫不是備份**：複寫讓資料「多一份」，備份讓資料「回到過去」。完整的韌性設計兩者都需要。

> [!warning] 常見誤解
> 「我們有 Multi-AZ，所以不需要 DR。」Multi-AZ 只處理 AZ 等級的故障。Region 等級的事件、誤刪與勒索軟體都需要另外的設計。反過來說，「我們有跨 Region 複寫」也不等於能從資料損毀中復原，因為損毀會被一起複寫過去。

## 34.3 Multi-AZ 設計：每一層都要攤開，而且不能有共享的單點

Wanderly 的事故說明了一件事：Multi-AZ 不是某個服務的勾選框，而是**每一層、每一個依賴**都要回答「如果這個 AZ 不見了，誰接手？」只要有一個元件只活在一個 AZ，整個系統的可用性就被它拉低。

### 逐層檢查

| 層 | AWS 元件 | Multi-AZ 的正確做法 | 常見漏洞 |
|---|---|---|---|
| 入口 | ALB／NLB | 至少啟用兩個 AZ 的 subnet | NLB 預設不開 cross-zone，某 AZ target 少時流量不均 |
| 對外連線 | NAT Gateway | 每個 AZ 一台，各 AZ 走自己的（第 5 章） | 所有 private subnet 共用一台 NAT |
| 運算 | EC2 Auto Scaling | ASG 跨多個 AZ subnet，用 ELB health check | 手動開的單台 worker、排程主機 |
| Containers | ECS／EKS | service 或 node group 跨 AZ，設定 AZ 分散策略 | 所有 task 被排到同一個 AZ |
| 關聯式資料庫 | RDS Multi-AZ、Aurora | 開啟 Multi-AZ；Aurora 至少一個不同 AZ 的 replica | Aurora 只有 writer、沒有 replica，failover 要重建 instance |
| 快取 | ElastiCache | Multi-AZ 搭配自動 failover 與 replica | 單節點 cache，故障時大量請求直擊資料庫 |
| 檔案 | EFS（Regional） | 每個 AZ 建 mount target | 使用 One Zone 類別卻宣稱高可用 |
| 區塊儲存 | EBS | EBS 綁定單一 AZ，要靠 snapshot 或應用層複寫 | 把重要狀態放在單台 EC2 的 EBS 上 |

幾個細節值得展開：

- **RDS Multi-AZ（單一 standby）**：primary 以同步方式把資料寫到另一個 AZ 的 standby，standby **不能讀**，只為 failover 存在。故障時 AWS 自動把 DNS endpoint 指到 standby，通常在一到兩分鐘內完成，應用程式只要重新連線即可。
- **RDS Multi-AZ DB cluster**：一個 writer 加兩個位於不同 AZ、**可讀**的 standby，failover 通常比單一 standby 更快（AWS 文件寫通常在 35 秒內）。
- **Aurora**：儲存層本來就是 6 份副本跨 3 個 AZ（第 26 章），但運算層的 writer 只有一台。若叢集裡沒有 Aurora Replica，writer 故障時 Aurora 要新建一台 instance，時間較長；有 replica 時會直接把 replica 提升為 writer。
- **Read replica 不是 Multi-AZ 的替代品**：RDS read replica 是非同步複寫、用來分擔讀取（第 35 章），提升為 primary 要手動或自己寫自動化，而且可能遺失尚未複寫的交易。

### 尋找藏起來的單點

Wanderly 的寄信 worker 就是典型的**共享依賴（shared dependency）**：架構圖上看起來每層都有兩個 AZ，但有一個小元件只在一個地方。常見的藏身處包括：手動建立的 EC2（cron 主機、跳板機、license server）、只有一台的自建 Redis 或 Kafka、指向單一 IP 的設定檔、只在一個 AZ 有 mount target 的 EFS、以及「為了省錢先開一台」的 NAT Gateway。

找出它們的方法很樸素：把架構圖上每個元件列出來，逐一回答「它在哪幾個 AZ？誰會替換它？替換需要人做什麼？」答不出來的就是風險。AWS Resilience Hub（34.11 節）可以自動做一部分這樣的評估。

```text
                 使用者
                   │
            [Route 53 / ALB]
         ┌─────────┴─────────┐
   AZ-a  │                   │  AZ-c
 ┌───────▼───────┐   ┌───────▼───────┐
 │ App EC2 ×3    │   │ App EC2 ×3    │   ① ASG 跨兩個 AZ
 │ (ASG)         │   │ (ASG)         │
 └──┬─────────┬──┘   └──┬─────────┬──┘
    │         │         │         │
 ┌──▼────┐ ┌──▼────┐ ┌──▼────┐ ┌──▼────┐
 │Redis  │ │RDS    │ │RDS    │ │Redis  │   ② 快取與 DB 都有跨 AZ 副本
 │primary│ │primary│═│standby│ │replica│
 └───────┘ └───────┘ └───────┘ └───────┘
    │                                       ③ 寄信 worker 只有一台在 AZ-a
 ┌──▼──────────┐                               → 隱藏的單點
 │ Mail worker │
 └─────────────┘
```

① 應用程式層由 ASG 管理，AZ-a 故障時 AZ-c 的 instance 繼續服務。② Redis 與 RDS 都在另一個 AZ 有副本並能自動 failover，圖中 `═` 表示 RDS 的同步複寫。③ 寄信 worker 是唯一沒有備援的元件，AZ-a 一停，這個功能就完全中斷。修正方式是把它放進一個跨 AZ、`min=2` 的 ASG，或改成由 SQS 觸發的 Lambda，讓 AWS 處理跨 AZ 的問題。

### Cross-zone load balancing 與跨 AZ 費用

**Cross-zone load balancing（跨區負載平衡）** 決定 load balancer 的某個 AZ 節點是否可以把流量送到其他 AZ 的 target。ALB 預設開啟，NLB 與 GWLB 預設關閉。關閉時，如果 AZ-a 只剩 1 台 target、AZ-c 有 5 台，Route 53 仍會把大約一半的流量送到 AZ-a 的節點，那 1 台就會被壓垮。開啟後流量平均分給所有 target，但 NLB 的跨 AZ 流量會產生資料傳輸費（第 10 章）。

## 34.4 Static stability：故障時不需要「做事」的設計

Wanderly 事故的第二個問題，是 1c 的容量不夠，必須在故障當下臨時擴展。問題在於：故障發生的那一刻，正是所有人都在搶資源、AWS 的管理 API 最忙的時候。

### Control plane 與 data plane

第 2 章提過兩個名詞，這裡要真正用上：

- **Control plane（控制平面）**：建立、修改、刪除資源的 API，例如 `RunInstances`、修改 Auto Scaling desired capacity、變更 Route 53 記錄、建立 RDS instance。它比較複雜，可用性目標通常低於 data plane。
- **Data plane（資料平面）**：資源已經存在後提供服務的部分，例如已經在跑的 EC2 處理請求、ALB 轉送流量、Route 53 回答 DNS 查詢、Route 53 health check 的評估結果。

**Static stability（靜態穩定）** 的意思是：系統在依賴故障時，**不需要呼叫 control plane 做任何改變**，就能繼續正常運作。一個靜態穩定的系統，故障當下只靠「已經存在的東西」撐住。

### 預先配置容量：N+1 的算法

最直接的做法是**預先多配容量**，讓失去一個 AZ 時剩下的 AZ 已經足夠。計算方式：

> 每個 AZ 需要的容量 = 尖峰需求 ÷（AZ 數 − 1）

Wanderly 尖峰需要 12 台 EC2：

| AZ 數 | 每 AZ 台數 | 總台數 | 失去一個 AZ 後剩下 | 超額配置比例 |
|---|---|---|---|---|
| 2 | 12 | 24 | 12 | 100% |
| 3 | 6 | 18 | 12 | 50% |
| 4 | 4 | 16 | 12 | 33% |

這就是為什麼很多正式環境選擇 3 個 AZ：在可承受的成本下取得靜態穩定。只用 2 個 AZ 時，要做到靜態穩定需要兩倍容量。

```text
平時（3 AZ，各 6 台，共 18 台，尖峰只用 12 台的量）
  AZ-a [■■■■■■]   AZ-c [■■■■■■]   AZ-d [■■■■■■]

AZ-a 故障（不呼叫任何 API，不等任何新 instance）
  AZ-a [xxxxxx]   AZ-c [■■■■■■]   AZ-d [■■■■■■]  → 剩 12 台，剛好撐住尖峰
                        ▲               ▲
                        └── ALB health check 自動停止送流量到 AZ-a（data plane）
```

圖中重點是右邊那一行：ALB 依 health check 停止把流量送到故障的 target，這是 data plane 的行為，不需要任何人修改設定。剩下的 12 台本來就在跑，不需要等待 Auto Scaling 啟動新 instance。Auto Scaling 之後仍會嘗試補回容量，但那只是「錦上添花」，不是撐過故障的必要條件。

### 其他靜態穩定的設計習慣

- **故障切換靠 data plane**：Route 53 health check 與 failover record 在 data plane 運作；相反地，「出事時手動去改 DNS 記錄」依賴 control plane。
- **預先建立好所有資源**：DR Region 的 VPC、IAM role、security group、KMS key 平時就建好，而不是出事時才用 CloudFormation 建立。
- **不要在請求路徑上依賴 control plane API**：例如應用程式每次請求都呼叫 `DescribeInstances` 找服務位置，就把 data plane 綁到了 control plane 上。
- **憑證、設定提前快取**：IAM role 臨時憑證、設定值與 secrets 在本地快取並有合理的過期策略，依賴短暫失效時仍能運作。

> [!tip] 考試提示
> 題目出現「AZ 故障時不能有任何容量下降」或「failover 不能依賴 Auto Scaling 啟動新 instance」，答案是預先在剩餘 AZ 配足容量（over-provision），而不是調整 scaling policy。看到「Route 53 control plane 不可用時仍要能切換」，想到 Application Recovery Controller 的 routing control（34.10 節）。

## 34.5 RTO、RPO 與 DR 的共同語言

Multi-AZ 解決了一個 Region 內的故障。接下來回到 CTO 的問題：整個 Region 出事，或資料被破壞，要多久恢復、掉多少資料？要回答它，需要第 4 章學過的兩個數字：

- **RTO（Recovery Time Objective，復原時間目標）**：從中斷開始，到服務恢復可用之間，業務**可以接受的最長時間**。
- **RPO（Recovery Point Objective，復原點目標）**：業務可以接受**遺失多長時間的資料**。RPO 15 分鐘，代表恢復後的資料最多只能比故障時刻舊 15 分鐘。

### RPO 由資料怎麼離開原地決定

RPO 不是你在文件上寫多少就是多少，而是由**最後一份可用資料副本的新舊程度**決定：

| 資料保護方式 | 實際能達到的 RPO（量級） |
|---|---|
| 每日 snapshot | 最多 24 小時 |
| 每小時備份 | 最多 1 小時 |
| Continuous backup／point-in-time recovery | 數分鐘內（依服務） |
| 非同步跨 Region 複寫（Aurora Global、DynamoDB global tables） | 通常是秒級，取決於當下的複寫延遲 |
| 同步複寫（RDS Multi-AZ，同 Region） | 接近 0 |

注意「取決於當下的複寫延遲」。非同步複寫的延遲平常可能不到一秒，但在 primary 寫入暴增或網路異常時會變大。所以要監控 replication lag 並對它設 alarm，把它當成 RPO 的即時訊號，而不是保證。

### RTO 是一條關鍵路徑

RTO 也不只是「資料庫 failover 要幾分鐘」。從故障發生到使用者恢復使用，依序要經過：

1. **偵測**：alarm 觸發、值班人員收到通知（數分鐘）。
2. **決策**：確認不是誤報、決定是否切換 Region。跨 Region failover 多半需要人做決定，這一步常常比技術步驟還久。
3. **執行**：提升資料庫、啟動或擴展運算、切換 DNS。
4. **驗證**：確認核心交易（例如「訂房並付款」）可以完成，而不只是首頁打得開。

把各步驟的時間相加，才是真正的 RTO。任何一步只存在某位工程師腦中、沒有 runbook 或沒有演練過，它的時間就是未知數。

## 34.6 四種 DR 策略

AWS 的 DR 白皮書把跨 Region 的策略分成四種，從便宜慢速到昂貴即時排列。它們的差別在於：**DR Region 平時預先放了多少東西、是否在運作**。

### 策略一：Backup & Restore（備份與還原）

**Backup & restore** 只把備份（資料庫 snapshot、EBS snapshot、S3 物件、AMI）複製到 DR Region，平時 DR Region 幾乎沒有運作中的資源。災難時，用 Infrastructure as Code 從零建立網路與運算，再從備份還原資料。

```text
 Primary Region（東京）                    DR Region（新加坡）
 ┌──────────────────────────┐            ┌──────────────────────────┐
 │ ALB → App ASG → RDS      │  ① 定期備份  │  Backup vault             │
 │                    │     │ ──────────► │  （snapshot、AMI 複本）    │
 │  S3 ───────────────┼─────┼── ② CRR ──► │  S3 bucket                │
 └──────────────────────────┘            │                          │
                                         │  ③ 災難時：IaC 建 VPC、    │
                                         │     ALB、ASG，再從備份還原 │
                                         └──────────────────────────┘
```

① AWS Backup 依排程建立備份並複製到 DR Region 的 vault。② 靜態檔案可以用 S3 Cross-Region Replication 持續複製。③ 災難時才建立所有運算與網路資源，因此 RTO 包含「建立基礎設施 + 還原資料（大型資料庫可能要數小時）+ 驗證」。RPO 等於備份間隔。

- **RTO／RPO**：數小時（RPO 可透過 continuous backup 縮短到分鐘級，但 RTO 仍受還原時間限制）。
- **成本**：最低，只付備份儲存與跨 Region 傳輸費。
- **關鍵前提**：IaC template、AMI、設定與 secrets 都必須在 DR Region 可用；DR Region 的 service quotas 要事先確認。
- **適合**：內部系統、報表、可以停機半天的服務。

### 策略二：Pilot Light（指示燈）

**Pilot light** 的名稱來自瓦斯爐上那一小簇永遠點著的火。DR Region 平時保持**核心資料層持續複寫且運作中**（例如 Aurora Global Database 的 secondary cluster、DynamoDB global table），網路、IAM 等基礎也預先建好，但**應用程式運算層是關閉的或不存在**（ASG 的 desired capacity 為 0，或只有 AMI 與 template）。

```text
 Primary Region（東京）                    DR Region（新加坡）
 ┌──────────────────────────┐            ┌──────────────────────────┐
 │ ALB → App ASG(6) → Aurora│  ① 持續複寫  │  Aurora secondary（運作中）│
 │                  writer ─┼──────────► │                          │
 │                          │            │  ALB（已建立）             │
 └──────────────────────────┘            │  App ASG desired = 0     │ ② 關閉中
                                         │                          │
                                         │  ③ 災難時：提升 Aurora，   │
                                         │     ASG 0 → 6，切換 DNS   │
                                         └──────────────────────────┘
```

① 資料層持續複寫，所以 RPO 是秒到分鐘級。② 運算層沒有在跑，不能處理任何請求，平時幾乎不花運算費用。③ 災難時要「點火」：提升資料庫為可寫、把 ASG 從 0 擴到正式容量（要等 instance 啟動與暖機）、切換 Route 53。

- **RTO／RPO**：RTO 數十分鐘到數小時，取決於「點火」的自動化程度：運算層全部以 IaC 與預先建好的 AMI 自動化、並定期演練時，可以壓在數十分鐘；需要人工步驟、從零部署大型應用層或等待大量 instance 暖機時，就會到一小時以上（34.14 節的韌性分級中，Pilot light 的 Tier 1 以 1 小時為目標）。RPO 秒到分鐘級。
- **成本**：低到中，主要是資料層的持續費用。
- **和 backup & restore 的分界**：pilot light 的資料是**持續複寫、即時可用**的，不需要從備份還原。
- **和 warm standby 的分界**：pilot light 的 DR Region **不能直接處理請求**，一定要先啟動運算層。

### 策略三：Warm Standby（溫備援）

**Warm standby** 在 DR Region 維持一套**縮小版但功能完整、隨時可以接流量**的環境。運算層有少量 instance 在跑，可以接受健康檢查甚至少量真實流量，災難時把它擴展到正式規模。

```text
 Primary Region（東京）                    DR Region（新加坡）
 ┌──────────────────────────┐            ┌──────────────────────────┐
 │ ALB → App ASG(12)        │            │ ALB → App ASG(2)         │ ① 縮小但運作中
 │          → Aurora writer ┼── 複寫 ──► │        → Aurora secondary│
 └────────────▲─────────────┘            └────────────▲─────────────┘
              │ 100%                                   │ 0%（或少量）
          ┌───┴────────────── Route 53 ────────────────┴───┐
          │ ② 災難時：Aurora 提升、ASG 2 → 12、流量切到新加坡 │
          └────────────────────────────────────────────────┘
```

① 新加坡的 ASG 平時有 2 台 instance 在跑，整條路徑（ALB → App → DB）都是通的，可以用 synthetic 測試持續驗證。② 災難時，流量可以立即切過去讓 2 台先接住一部分請求，同時擴展到 12 台。因為擴展需要時間，切換初期可能要搭配限流或降級（第 35 章）。

- **RTO／RPO**：RTO 數分鐘；RPO 秒級。
- **成本**：中，持續付縮小版環境的費用。
- **優點**：DR 環境天天在跑，「切過去不會動」的風險最低。

> [!note] Hot standby
> 若 DR Region 平時就維持**完整規模**但不接流量，有時稱為 **hot standby**（active-passive 的極端形式）。它省去擴展時間，但成本接近兩倍。考試裡通常把它歸在 warm standby 與 active-active 之間，題目若說「DR 環境必須能立即承受 100% 流量，但只有一個 Region 對外服務」就是在描述它。

### 策略四：Multi-Site Active-Active（多站點同時運作）

**Multi-site active-active** 讓兩個以上的 Region **同時服務真實流量**，任何一個 Region 失效，其他 Region 繼續服務，只是需要承擔更多流量。

```text
            ┌────────── Route 53（latency / weighted + health check）──────────┐
            │                                                                  │
            ▼ 約 50%                                                    約 50% ▼
 ┌──────────────────────────┐                          ┌──────────────────────────┐
 │ 東京：ALB → App ASG       │                          │ 新加坡：ALB → App ASG     │
 │   → DynamoDB global table│ ◄══ 雙向非同步複寫 ═════► │   → DynamoDB global table│
 └──────────────────────────┘                          └──────────────────────────┘
   ① 兩邊都接受讀寫               ② 一邊故障：health check 失敗，流量全部導向另一邊
```

① 兩個 Region 都處理讀與寫，資料層必須支援多 Region 寫入，最典型的是 DynamoDB global tables。若用 Aurora Global Database，它只有一個可寫的 primary Region：write forwarding 只是把 secondary 收到的寫入轉送到 primary 執行，primary Region 故障時寫入仍會中斷，所以關聯式資料庫通常要靠應用層分區（每個 Region 只寫自己負責的資料）才能接近 active-active。② 一邊故障時，Route 53 的 health check 讓流量自動導向健康的 Region，RTO 接近 0。

- **RTO／RPO**：RTO 接近 0；RPO 接近 0 到秒級（非同步複寫仍可能遺失極短時間的寫入）。
- **成本**：最高，兩邊都要有足夠承受全部流量（或接近）的容量。
- **最大難點不是基礎設施，而是資料語意**：兩個 Region 同時修改同一筆訂單時聽誰的？DynamoDB global tables 預設用「最後寫入者勝出（last writer wins）」，對購物車也許可以接受，對庫存扣減與付款則可能造成超賣。常見做法是讓每筆資料有一個「歸屬 Region」（例如依會員所在地），只在歸屬 Region 寫入。

### 四種策略比較

| 項目 | Backup & Restore | Pilot Light | Warm Standby | Multi-Site Active-Active |
|---|---|---|---|---|
| DR Region 平時有什麼 | 只有備份 | 運作中的資料層 + 預建基礎 | 縮小但完整、運作中的整套環境 | 完整環境，且正在服務流量 |
| 能否立即接流量 | 否 | 否，要先啟動運算 | 能，但容量小 | 能，本來就在接 |
| 典型 RTO | 數小時 | 數十分鐘到數小時（依自動化程度） | 數分鐘 | 接近 0 |
| 典型 RPO | 數小時（備份間隔） | 秒到分鐘 | 秒 | 接近 0 到秒 |
| 成本 | $ | $$ | $$$ | $$$$ |
| 故障時要做的事 | 建基礎設施、還原資料、部署、切 DNS | 提升 DB、啟動運算、切 DNS | 提升 DB、擴展運算、切 DNS | 停止把流量送往故障 Region |
| 主要風險 | 還原時間超出預期、備份不可用 | 啟動運算時遇到 quota 或 AMI 問題 | 擴展速度跟不上 | 多 Region 寫入衝突、成本 |

選擇策略時，**先由業務定出 RTO／RPO，再找滿足它的最便宜策略**。不是每個系統都需要 active-active：Wanderly 的訂房與付款可能需要 warm standby，後台報表用 backup & restore 就夠了。同一家公司裡不同系統採用不同策略是正常的。

## 34.7 各服務的跨 Region 複寫能力

DR 策略決定「要不要在另一邊預先放東西」，而能不能做到某個 RPO，取決於每個資料服務提供的跨 Region 能力。以下整理考試最常出現的幾個。

| 服務 | 跨 Region 機制 | 複寫方式 | DR 時怎麼用 |
|---|---|---|---|
| S3 | Cross-Region Replication（CRR） | 非同步、物件層級 | DR 端 bucket 直接可讀；可搭配 Multi-Region Access Points |
| RDS（MySQL、PostgreSQL 等） | Cross-Region read replica | 非同步 | 提升（promote）為獨立 primary，之後無法再變回 replica |
| Aurora | Aurora Global Database | 儲存層非同步複寫，延遲通常低於 1 秒 | Switchover（計畫內）或 failover（計畫外） |
| DynamoDB | Global tables | 多 Region 皆可寫入，非同步 | 另一個 Region 本來就可讀寫 |
| EBS | Snapshot 跨 Region copy | 依排程 | 在 DR Region 由 snapshot 建立 volume |
| EC2 | AMI 跨 Region copy | 依排程 | 用 AMI 啟動 instance |
| EFS | EFS Replication | 非同步 | 把 replica file system 改為可寫 |
| ElastiCache（Redis OSS／Valkey） | Global Datastore | 非同步 | 提升 secondary cluster |
| KMS | Multi-Region keys | 金鑰材料一致 | 在 DR Region 解密跨 Region 複製的資料 |
| Secrets Manager | Secret replication | 自動同步 | DR Region 讀取同一份 secret |
| ECR | Registry replication | 自動 | DR Region 拉取 container image |

### S3 Cross-Region Replication 的細節

第 23 章詳細介紹過 S3 replication，這裡只整理 DR 相關的重點：

- 來源與目的 bucket **都必須啟用 versioning**。
- 設定 replication rule 之後**只複製新寫入的物件**；既有物件要用 **S3 Batch Replication** 補複製。
- 預設不保證完成時間；需要可預期的 RPO 時開啟 **S3 Replication Time Control（RTC）**，它提供 99.99% 的物件在 15 分鐘內完成複寫的 SLA，並提供複寫延遲的 metrics。
- Delete marker 可以選擇是否複寫；但**刪除特定版本的動作不會被複寫**，這是刻意設計：有人在來源刪掉某個版本，目的端仍保有它，可以防止惡意刪除擴散。

### Aurora Global Database：switchover 與 failover

**Aurora Global Database** 由一個 primary Region 的 cluster（可寫）和一個或多個 secondary Region 的 cluster（唯讀）組成。複寫在儲存層進行，不消耗資料庫 instance 的運算資源，延遲通常不到 1 秒。它有兩種切換方式：

- **Switchover**（以前稱為 managed planned failover）：計畫內的切換，例如演練或 Region 維護。Aurora 會先等 secondary 完全同步，再交換角色，**不會遺失資料**（RPO = 0），而且全球資料庫的拓撲保持完整。
- **Failover**：primary Region 真的不可用時使用。把某個 secondary 提升為新的 primary，**可能遺失尚未複寫過去的那一小段資料**（RPO 等於當時的複寫延遲）。

另外，**write forwarding** 讓 secondary Region 的應用程式可以送寫入請求，由 Aurora 轉送到 primary 執行，這讓「讀在本地、寫入轉送」的架構不必在應用程式裡處理兩組 endpoint，但寫入延遲包含跨 Region 往返。

### DynamoDB global tables

**DynamoDB global tables** 讓同一張表在多個 Region 都有完整副本，**每個副本都可以讀寫**，變更通常在一秒左右傳到其他 Region。預設模式下衝突以「最後寫入者勝出」解決，跨 Region 的讀取是最終一致的。DynamoDB 的 transaction 只在發起寫入的那個 Region 內具有 ACID 保證。AWS 近年另外推出了多 Region 強一致性（multi-Region strong consistency）的選項，適合不能接受衝突的場景，但它對 Region 組合與延遲有額外限制，選用前要確認需求。

> [!warning] 常見誤解
> 「DynamoDB 有 global tables，所以不用開 point-in-time recovery。」Global tables 會把誤刪與錯誤寫入同樣複製到所有 Region。要能回到過去，仍然要開 **PITR（point-in-time recovery，可還原到過去最多 35 天內的任一秒）** 或使用 AWS Backup。

## 34.8 AWS Backup：集中管理備份並證明它能還原

在 Wanderly，過去每個團隊用自己的方式備份：RDS 用自動備份、EBS 用自己寫的 Lambda 打 snapshot、DynamoDB 沒人管。CTO 要的「證明可以還原」在這種狀態下根本無從證明。**AWS Backup** 是一個集中的備份服務：用一套政策管理多種服務的備份、複製、保存期限與還原測試，並產生稽核報告。

### 核心元件

- **Backup plan（備份計畫）**：一組規則（**backup rule**）。每條規則定義排程（cron 或固定頻率）、**backup window**（開始時間與「必須在多久內開始／完成」）、**lifecycle**（多久後轉冷儲存、多久後刪除；只有部分資源類型支援冷儲存，且轉入後至少要存 90 天）、目標 vault，以及 **copy action**（複製到其他 Region 或帳號的 vault）。
- **Resource assignment（資源指派）**：決定哪些資源套用這個 plan，可以用 tag（例如 `backup=gold`）或資源 ARN 選取。用 tag 的好處是新資源只要貼上 tag 就自動被保護。
- **Backup vault（備份保管庫）**：存放 **recovery point**（每一次備份的結果）的容器，以 KMS key 加密，並有自己的 **access policy**（resource-based policy），可以拒絕任何人刪除 recovery point。
- **Continuous backup**：對支援的服務（例如 RDS、Aurora、S3）提供 point-in-time recovery，最長保存 35 天，讓 RPO 縮到分鐘級。注意：continuous backup 被複製到其他 Region 或帳號後，副本會變成一般的 snapshot 型備份，**不再保有 point-in-time restore 能力**。

一個 Wanderly 正式環境使用的 backup plan 長這樣：

```json
{
  "BackupPlanName": "wanderly-prod-gold",
  "Rules": [
    {
      "RuleName": "hourly-with-dr-copy",
      "TargetBackupVaultName": "prod-vault",
      "ScheduleExpression": "cron(0 * ? * * *)",
      "StartWindowMinutes": 60,
      "CompletionWindowMinutes": 180,
      "Lifecycle": { "DeleteAfterDays": 35 },
      "CopyActions": [
        {
          "DestinationBackupVaultArn": "arn:aws:backup:ap-southeast-1:222222222222:backup-vault:dr-vault",
          "Lifecycle": { "DeleteAfterDays": 90 }
        }
      ]
    }
  ]
}
```

這條規則每小時備份一次（RPO 最多 1 小時），在本地保存 35 天，並把每份 recovery point 複製到另一個帳號（`222222222222`）在新加坡的 vault，保存 90 天。把副本放在**不同帳號**，是為了在主要帳號被入侵、攻擊者取得管理權限時，備份仍然安全。

### 跨 Region 與跨帳號 copy 的前提

跨 Region copy 只要指定目的 Region 的 vault 即可。**跨帳號 copy** 則有幾個前提，考試常考：

1. 兩個帳號必須在**同一個 AWS Organization**，並在 management account 的 AWS Backup 設定中啟用 cross-account backup。
2. **目的 vault 的 access policy** 必須允許來源帳號把 recovery point 複製進來。
3. **加密金鑰**：來源資源若以 customer managed KMS key 加密，必須在該 key 的 key policy 中把它**分享給目的帳號**；複製完成後，AWS Backup 會用目的 vault 的 KMS key 重新加密副本。對於不是由 AWS Backup「完整管理」的資源類型（例如 RDS、Aurora），目的 vault 也必須使用 customer managed key，因為 AWS managed key 的 key policy 無法修改、不能跨帳號分享。這就是正式環境的 RDS 通常一開始就用 customer managed key 加密的原因（第 15 章）。另外，目的 vault 不能是帳號的 default vault，且已轉入冷儲存的備份不支援跨帳號 copy。

### Vault Lock 與 logically air-gapped vault：讓備份刪不掉

勒索軟體攻擊的標準劇本是：先刪掉備份，再加密正式資料。**AWS Backup Vault Lock** 讓 vault 成為 **WORM（Write Once Read Many，寫入後不可修改）** 儲存，並強制最短與最長保存期限：

| 模式 | 誰能移除鎖定 | 適用 |
|---|---|---|
| Governance mode | 擁有足夠 IAM 權限的使用者可以移除或修改 | 測試設定、內部治理 |
| Compliance mode | 經過 **grace time（冷靜期，最少 72 小時）** 後**任何人都無法修改或刪除**，包含 root user 與 AWS | 法規要求、防勒索 |

Compliance mode 一旦過了冷靜期就無法反悔，所以要先用 governance mode 或在冷靜期內確認設定正確。另一個選項是 **logically air-gapped vault**：它一律以 compliance mode 鎖定（不能選 governance mode），並可以透過 AWS RAM 共享給其他帳號，讓另一個（例如專門的復原帳號）直接從中還原，適合「主帳號完全被攻陷時仍要能復原」的情境。它支援的資源類型比一般 vault 少，設計前要先查 AWS Backup 的功能支援表，常見的限制有：RDS DB instance（非 Aurora 的 RDS）不能複製進去，Aurora 可以但未加密的 cluster 不行；DynamoDB 必須啟用 AWS Backup 的 advanced features；EC2、EBS 這類不是由 AWS Backup 完整管理的資源，來源必須以 customer managed KMS key 加密（AWS managed key 不行）。

### Restore testing 與稽核

有備份不等於能還原。**AWS Backup restore testing** 讓你建立 **restore testing plan**：指定頻率、要測試的資源類型與 recovery point 的選取方式（例如最新的一份），AWS Backup 會定期自動還原到測試環境、記錄還原花了多久，並在設定的保存時間後**自動刪除還原出來的資源**。你可以用 EventBridge 接收還原完成事件，觸發 Lambda 做驗證（例如查詢訂單筆數），再把驗證結果回報給 AWS Backup。這讓「RTO 是多少」從猜測變成每週量測一次的數字。

**AWS Backup Audit Manager** 則用 framework 與 control 持續檢查「每個資源是否有備份」「保存期限是否符合規定」「是否有跨 Region copy」「vault 是否鎖定」，並產生報告給稽核人員。在多帳號環境，可以用 Organizations 的 **backup policy** 由中央統一派送 backup plan（第 43 章）。

## 34.9 AWS Elastic Disaster Recovery：伺服器等級的持續複寫

AWS Backup 擅長「定期快照」，但有些系統不在 AWS 原生資料庫上：Wanderly 併購旅行社後（第 44 章），會接手一批在地端 VMware 上跑的訂票系統，作業系統裡裝著商用軟體，無法輕易改架構。對這類**整台伺服器**，需要的是持續、區塊層級的複寫。

**AWS Elastic Disaster Recovery（AWS DRS）** 在來源伺服器上安裝 replication agent，把磁碟的每一次寫入持續複寫到 AWS。來源可以是地端實體機、VMware 等虛擬機、其他雲端的機器，或另一個 AWS Region／AZ 的 EC2。

```text
 來源（地端資料中心或其他 Region）            AWS 復原 Region
 ┌──────────────────────┐               ┌──────────────────────────────────────┐
 │ Server + Agent       │ ① 持續區塊複寫 │ Staging area subnet                  │
 │ （磁碟每次寫入）       │ ────────────► │  replication server（小型 EC2）       │
 └──────────────────────┘               │  + 低成本 EBS + point-in-time 快照    │
                                        │              │                       │
                                        │              │ ② drill 或 recovery   │
                                        │              ▼                       │
                                        │ Recovery subnet                      │
                                        │  recovery instance（依 launch 設定）   │
                                        └──────────────────────────────────────┘
                                                       │ ③ 事件結束後 failback
                                                       └──────────► 回到來源
```

① Agent 把資料送到 staging area，那裡只有小型的 replication server 與低成本的 EBS，因此平時費用遠低於維持一整套 standby 伺服器。DRS 會保留一系列 point-in-time recovery point。② 需要演練（**drill**）或真正復原時，DRS 依照預先設定的 launch template 在 recovery subnet 啟動完整規格的 **recovery instance**，可以選最新狀態或某個過去的時間點（例如勒索軟體加密發生之前）。演練不會中斷來源伺服器的複寫。③ 事件結束後，可以把資料 **failback** 回地端（使用 failback client）或原本的 Region。

DRS 的典型指標是 **RPO 秒級、RTO 分鐘級**，成本模式類似 pilot light：平時只付低成本的複寫資源，災難時才付完整運算。它和第 45 章的 **AWS MGN（Application Migration Service）** 使用相似的複寫技術，但目的不同：MGN 是一次性的遷移，完成 cutover 後就不再需要來源；DRS 是長期的保護，來源持續存在並持續複寫。

| 需求 | 選擇 |
|---|---|
| AWS 原生資源（RDS、DynamoDB、EBS、EFS…）的定期備份與保存政策 | AWS Backup |
| 整台伺服器（含作業系統與商用軟體）的秒級 RPO、分鐘級 RTO | AWS Elastic Disaster Recovery |
| 把地端伺服器一次搬到 AWS | AWS MGN（第 45 章） |
| 資料庫層的跨 Region 低延遲複寫 | Aurora Global Database、DynamoDB global tables |

## 34.10 切換流量：Route 53 failover 與 Application Recovery Controller

資料準備好了，運算也能啟動，最後一步是讓使用者的請求真的到達 DR Region。

### Route 53 failover routing

第 9 章介紹的 **failover routing policy** 是最基本的做法：primary record 綁定 health check，health check 失敗時 Route 53 改回答 secondary record。它的優點是由 data plane 自動執行。要注意三件事：

1. **TTL**：用戶端與 resolver 會快取 DNS 答案直到 TTL 到期，所以 failover 記錄的 TTL 通常設 60 秒或更短，否則切換後還有大量使用者連到舊位置。
2. **健康檢查要檢查對的東西**：只檢查首頁的 health check，可能在資料庫已經壞掉時仍回報健康。比較好的做法是檢查一個會實際存取依賴的 deep health endpoint，或用 CloudWatch alarm 組合多個訊號。但 deep health check 也有風險：依賴短暫抖動時可能讓**所有 Region 同時被判定不健康**，所以要謹慎設計。
3. **自動 failover 不一定適合跨 Region 資料庫**：如果 DNS 自動切到新加坡，但 Aurora 還沒被提升為可寫，使用者只會看到錯誤；如果兩邊都以為自己是 primary，還可能產生「腦裂（split brain）」。很多團隊因此選擇「偵測自動化、切換由人決定、執行完全自動化」。

### Amazon Application Recovery Controller（ARC）

**Amazon Application Recovery Controller（ARC，舊稱 Route 53 Application Recovery Controller）** 是專門為「可靠地執行 failover」設計的服務，主要功能有：

- **Routing control**：一組由你手動開關的「開關」，每個開關對應一個 Route 53 health check。切換 Region 時，只要把東京的開關關掉、新加坡的打開，Route 53 failover record 就會依此回答。關鍵在於：routing control 的狀態由一個**跨 5 個 Region 的高可用叢集（cluster）** 提供 data plane API，你可以透過其中任何一個健康的 Regional endpoint 切換，**不需要依賴 Route 53 的 control plane 去修改 DNS 記錄**。這正是 34.4 節靜態穩定的精神。
- **Safety rules**：防止誤操作的規則。**Assertion rule** 例如「至少要有一個 Region 是開啟的」，避免把所有開關都關掉；**gating rule** 例如「只有總開關打開時，才能切換其他開關」。
- **Readiness check**：持續比對兩個 Region 的資源設定、容量與 quota 是否一致，提醒你 DR 端是否已經落後。注意：這個功能**已不再開放給新客戶**（既有客戶可繼續使用），AWS 建議新環境改用下面的 Region switch，它的 plan evaluation 會定期檢查切換計畫是否可執行。
- **Zonal shift**：針對 AZ 等級的問題，暫時把 ALB、NLB（等支援的資源）的流量從某個 AZ 移走，設定到期時間後自動恢復。適合「AZ 沒有完全壞，但表現異常（gray failure）」的情況：你的監控看出 1a 的延遲異常，就主動避開它，不需要等 AWS 宣告事件。
- **Zonal autoshift**：由 AWS 在偵測到 AZ 有問題時自動替你執行 zonal shift。啟用它要求你設定定期的 **practice run**（演練），由 ARC 定期實際把流量移開一個 AZ，證明你的應用程式在少一個 AZ 時撐得住，這也逼你做到靜態穩定。
- **Region switch**：較新的功能，讓你預先定義跨 Region 切換的步驟計畫（例如提升 Aurora Global Database、擴展 DR Region 的 ASG、切換 DNS），出事時從復原 Region 依序執行；它也會定期評估計畫是否仍可執行（plan evaluation）。

```text
  值班人員決定切換
        │ ① 透過任一健康的 cluster endpoint 呼叫 UpdateRoutingControlState
        ▼
  [ARC cluster：5 個 Regional endpoints]
        │ ② safety rules 檢查：至少一個 Region 開啟 ✓
        ▼
  routing control：Tokyo = Off、Singapore = On
        │ ③ 對應的 Route 53 health check 狀態改變（data plane）
        ▼
  Route 53 failover record 改回答 Singapore 的 ALB
```

① 切換請求送到 ARC 的 data plane，即使某個 Region 有問題也能透過其他 endpoint 完成。② Safety rules 擋下危險操作。③ Routing control 透過 health check 影響 Route 53 的回答，整條路徑都不需要修改 DNS 記錄。注意：ARC 只負責「流量往哪裡走」，資料庫的提升、運算的擴展仍要由 runbook 或自動化（Region switch、Systems Manager Automation，第 38 章）完成。

### 別忘了 failback

**Failback（回切）** 是把服務從 DR Region 移回原本的 Region。它往往比 failover 更難：DR 期間新寫入的資料都在新加坡，要先把資料複寫回東京、確認一致、再安排一個計畫內的切換（Aurora 用 switchover）。DR 計畫若只寫 failover 而沒寫 failback，就只完成了一半。

## 34.11 演練：game day、FIS 與 Resilience Hub

Wanderly 的 CTO 最後提出的要求是：「我不要文件，我要看到你們切過去一次。」這正是 DR 的核心原則：**沒有演練過的復原計畫，只是一份假設。**

### Game day

**Game day（演練日）** 是一次有計畫的故障演練：選定情境（例如「東京 Region 的資料庫不可用」）、事先定義成功標準（例如「30 分鐘內核心訂房交易恢復，資料遺失少於 1 分鐘」）、指定觀察者記錄每一步的時間，結束後寫檢討並更新 runbook。好的 game day 有三個特點：

- **量的是業務結果**：不是「Aurora 提升成功」，而是「使用者可以完成訂房並收到確認信」。
- **由不同的人執行**：讓不是最資深的工程師照 runbook 操作，才能發現 runbook 的漏洞。
- **有中止條件**：在正式環境演練時，事先定義什麼情況要立刻停止並回復。

### AWS Fault Injection Service（FIS）

**AWS Fault Injection Service（FIS）** 是受管的混沌工程（chaos engineering）服務，用來在受控的情況下注入故障。你建立一個 **experiment template**，包含：

- **Actions**：要注入的故障，例如停止或終止 EC2、讓 EBS I/O 暫停、增加網路延遲、讓 RDS failover、對 API 呼叫注入錯誤。FIS 也提供預先組好的情境，例如模擬 AZ 電力中斷。
- **Targets**：受影響的資源，用 tag 或資源 ID 選取，並可以只選一定比例。
- **Stop conditions**：一個或多個 CloudWatch alarm。只要 alarm 進入 ALARM 狀態，FIS 立即停止實驗。這是在正式環境安全演練的關鍵。
- **IAM role**：FIS 執行動作所用的權限，應該最小化。

### AWS Resilience Hub

**AWS Resilience Hub** 從架構面評估韌性。你把應用程式定義進去（例如從 CloudFormation stack 或 tag 匯入資源），設定 **resilience policy**：對「應用程式故障、基礎設施故障、AZ 故障、Region 故障」四種情況各自要求的 RTO 與 RPO。Resilience Hub 會評估目前架構估計能達到的 RTO／RPO 是否符合政策，指出缺口（例如「這個 RDS 沒有跨 Region 副本，Region 故障時無法達到 1 小時 RTO」），並建議 alarm、SOP 與 FIS 實驗。它的評估是**估算**，真正的數字仍要靠 restore testing 與 game day 量測。

把這些工具串起來，Wanderly 的韌性驗證變成一個循環：Resilience Hub 找出架構缺口 → 修正架構 → AWS Backup restore testing 每週量測還原時間 → FIS 每月注入 AZ 故障 → 每季做一次跨 Region game day → 結果回饋到 runbook 與 Resilience Hub。

## 34.12 比較與選型

### DR 策略選擇流程

```text
業務定出 RTO / RPO 了嗎？
├─ 否 → 先和業務定義（每小時停機損失、可接受的資料遺失）
└─ 是 → RTO 是否可以是數小時，RPO 可以是數小時？
        ├─ 是 → Backup & Restore（AWS Backup + 跨 Region copy + IaC）
        └─ 否 → 是否能接受數十分鐘到數小時的 RTO，且 DR 端平時不需要接流量？
                ├─ 是 → Pilot Light（資料層持續複寫，運算關閉）
                └─ 否 → 是否需要分鐘級 RTO，但只有一個 Region 對外服務？
                        ├─ 是 → Warm Standby（縮小版運作中環境）
                        └─ 否（RTO 接近 0、多 Region 同時服務）→ Multi-Site Active-Active
不論哪一種：另外準備 point-in-time backup 處理邏輯損毀，並定期演練。
```

### 易混淆的工具

| 比較 | A | B | 判斷關鍵 |
|---|---|---|---|
| RDS Multi-AZ vs read replica | 同步、standby 不可讀、自動 failover | 非同步、可讀、手動 promote | 高可用 → Multi-AZ；讀取擴展或跨 Region → read replica |
| Aurora Global switchover vs failover | 計畫內、RPO 0 | 計畫外、可能遺失複寫延遲內的資料 | Primary Region 還活著嗎？ |
| AWS Backup vs DRS | 原生資源的排程備份與保存政策 | 整台伺服器的持續區塊複寫 | 秒級 RPO 的 VM／地端伺服器 → DRS |
| DRS vs MGN | 長期 DR 保護 | 一次性遷移 | 來源之後還會存在嗎？ |
| Vault Lock governance vs compliance | 有權限者可移除 | 冷靜期後任何人都不能移除 | 法規、防勒索 → compliance |
| Route 53 failover vs ARC routing control | DNS health check 自動切換 | 手動但高可靠的開關、safety rules | 要避免依賴 control plane、要防誤操作 → ARC |
| Zonal shift vs zonal autoshift | 你主動移走 AZ 流量 | AWS 偵測後替你移走 | 是否要 AWS 自動處理 AZ 事件 |
| FIS vs Resilience Hub | 實際注入故障 | 評估架構與 RTO／RPO 政策 | 「驗證」→ FIS；「評估、找缺口」→ Resilience Hub |

## 34.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 資料庫要在 AZ 故障時自動 failover、不遺失已提交交易 | RDS Multi-AZ（同步 standby） |
| AZ 故障時容量不能下降，不能等 Auto Scaling | 靜態穩定：預先在剩餘 AZ 配足容量 |
| RTO／RPO 數小時、成本最低 | Backup & restore + 跨 Region copy |
| DR 端只保留資料庫複寫，運算平時關閉 | Pilot light |
| DR 端有縮小版、隨時能接流量的環境 | Warm standby |
| RTO 接近 0、多 Region 同時服務 | Multi-site active-active（DynamoDB global tables、Route 53 latency／health check） |
| 跨 Region 關聯式資料庫、RPO 約 1 秒、RTO 約 1 分鐘 | Aurora Global Database |
| 計畫內 Region 切換且不能遺失資料 | Aurora Global Database switchover |
| S3 跨 Region 複寫要有可預期的完成時間 | S3 Replication Time Control |
| 既有物件也要複寫到新 bucket | S3 Batch Replication |
| 備份不能被任何人刪除，包含 root | AWS Backup Vault Lock compliance mode |
| 跨帳號備份 copy | 同一 Organization、啟用 cross-account backup、目的 vault access policy、customer managed KMS key |
| 定期自動驗證備份可還原並量測時間 | AWS Backup restore testing |
| 地端／VM 秒級 RPO、分鐘級 RTO、不改架構 | AWS Elastic Disaster Recovery |
| Failover 不依賴 Route 53 control plane、防止誤關所有 Region | ARC routing control + safety rules |
| AZ 表現異常但未完全故障，要暫時避開 | ARC zonal shift |
| 在正式環境安全地注入故障，異常時自動停止 | AWS FIS + CloudWatch alarm stop condition |
| 評估應用程式是否達到 RTO／RPO 目標 | AWS Resilience Hub |

**常見陷阱**：

1. 把 read replica 當成高可用方案：它是非同步、要手動 promote，題目要「自動 failover、零資料遺失」時是 Multi-AZ。
2. 把 pilot light 與 warm standby 搞混：判斷點是「DR 端能不能在不啟動任何運算的情況下處理請求」。不能 → pilot light；能（容量較小）→ warm standby。
3. 以為複寫可以取代備份：誤刪與勒索加密會被複寫，必須有 point-in-time backup 或不可竄改的備份。
4. 以為 S3 CRR 會自動複製既有物件，或以為刪除版本也會被複寫。
5. Vault Lock compliance mode 在冷靜期後無法移除，題目若要求「之後可能需要調整保存期限」要選 governance mode。
6. 選 active-active 卻沒處理多 Region 寫入衝突，或在題目只要求數小時 RTO 時選了最貴的方案。

## 34.14 SAP 加深：組織層級的韌性

SAA 問的是「這個 workload 用哪種 DR 策略」，SAP 問的是「一家有 80 個帳號、上百個 workload 的公司，怎麼讓 DR 可治理、可證明、在最壞的情況下仍能執行」。

### 分級，而不是一體適用

企業不會讓所有系統都 active-active。常見做法是定義 3–4 個韌性等級（tier），每個等級對應 RTO／RPO、DR 策略、備份政策與演練頻率：

| Tier | 範例系統 | RTO／RPO | 策略 | 演練 |
|---|---|---|---|---|
| Tier 0 | 訂房、付款 | 15 分鐘／1 分鐘 | Warm standby 或 active-active | 每季跨 Region game day |
| Tier 1 | 會員、搜尋 | 1 小時／15 分鐘 | Pilot light | 每半年 |
| Tier 2 | 內部後台、報表 | 24 小時／24 小時 | Backup & restore | 每月自動 restore testing |

在 AWS 上，可以用 tag（例如 `resilience-tier=0`）串起一切：Organizations 的 backup policy 依 tag 派送對應的 backup plan，Resilience Hub 依 tier 套用不同的 resilience policy，Backup Audit Manager 依 tier 檢查是否合規。

### 隔離的復原帳號

勒索軟體情境下，攻擊者可能已經拿到正式帳號的管理權限。SAP 常見的設計是建立一個**獨立的 recovery／backup 帳號**：存放 logically air-gapped vault 或 compliance-locked vault，使用獨立的身份與權限（break-glass 流程），並用 SCP 禁止任何人在該帳號刪除 vault 或修改 Vault Lock（第 14 章）。復原時，在一個乾淨的帳號從這些備份重建，而不是在可能仍被入侵的原帳號內還原。

### DR Region 的隱藏依賴

跨 Region failover 失敗的常見原因，往往不是資料庫，而是被忽略的依賴：

- **Service quotas**：DR Region 的 EC2 vCPU、Lambda concurrency 等 quota 是分開計算的，平時用量低，quota 可能仍是預設值。要事先申請提高到能承受全部流量（第 35 章）。
- **AMI、container image、secrets、KMS key、憑證**：這些都要在 DR Region 存在（AMI copy、ECR replication、Secrets Manager replication、KMS multi-Region key；ACM 憑證是 Regional 的，要在 DR Region 另外申請）。
- **全域服務的 control plane**：某些服務的 control plane 集中在特定 Region（例如 Route 53 的 DNS 記錄變更、IAM 的變更）。復原計畫不應依賴「在出事時修改這些設定」，而是事先建好並用 data plane 機制（health check、ARC routing control）切換。
- **第三方依賴**：金流商、簡訊服務的 IP 允許清單（allowlist）是否包含 DR Region 的 NAT Gateway EIP？

### 多 Region 架構的延伸

本章聚焦 DR。第 42 章會更深入討論多 Region 應用程式的資料分區、全球流量管理與一致性取捨；第 53 章會把這些組成 Wanderly 最終的多 Region warm standby 架構。

## 本章重點整理

- 高可用設計先決定要撐過哪一種 fault domain：instance、AZ、Region，以及不受地理限制的邏輯故障（誤刪、錯誤部署、勒索軟體）。
- 複寫保護「地點」，備份保護「時間」；誤刪與資料損毀會被複寫擴散，所以跨 Region 複寫不能取代 point-in-time backup。
- Multi-AZ 要逐層檢查每個元件，找出手動建立的單台 worker、單一 NAT Gateway、單節點快取等藏起來的單點。
- RDS Multi-AZ 是同步複寫、standby 不可讀、自動 failover；read replica 是非同步、可讀、手動 promote，兩者用途不同。
- Static stability 讓系統在故障時不需要呼叫 control plane；預先配置容量的公式是「每 AZ 容量 = 尖峰需求 ÷（AZ 數 − 1）」。
- RPO 由最後一份可用副本的新舊決定，RTO 是偵測、決策、執行、驗證的總和；兩者都要量測，不能只寫在文件上。
- Backup & restore 最便宜、RTO／RPO 數小時；pilot light 保留運作中的資料層但運算關閉；warm standby 有縮小但可接流量的完整環境；active-active 多 Region 同時服務，成本最高且要處理寫入衝突。
- Aurora Global Database 提供秒級 RPO 的跨 Region 關聯式資料庫，switchover 計畫內不遺失資料，failover 計畫外可能遺失複寫延遲內的資料。
- DynamoDB global tables 是多 Region 可寫的 active-active 資料層，預設 last writer wins；S3 CRR 需要 versioning、不複製既有物件（用 Batch Replication），RTC 提供 15 分鐘 SLA。
- AWS Backup 以 backup plan、tag 指派、vault、copy action 集中管理備份；跨帳號 copy 需同一 Organization、目的 vault policy 與合適的 KMS key。
- Vault Lock compliance mode 在冷靜期後任何人都無法刪除備份，是防勒索的關鍵；restore testing 定期自動還原並量測時間。
- AWS Elastic Disaster Recovery 以持續區塊複寫保護整台伺服器，RPO 秒級、RTO 分鐘級，平時只付低成本的 staging 資源。
- Route 53 failover 依 health check 自動切換；ARC routing control 提供不依賴 DNS control plane 的高可靠開關與 safety rules，zonal shift／autoshift 處理 AZ 等級問題。
- 沒有演練過的 DR 計畫只是假設：用 game day 量測業務結果、FIS 搭配 CloudWatch alarm stop condition 安全注入故障、Resilience Hub 評估 RTO／RPO 缺口，並記得規劃 failback。

### 練習 34-1｜SAA｜單選｜RDS 高可用選擇

Wanderly 的訂單資料庫使用 RDS for PostgreSQL，目前是單一 instance。業務要求：若資料庫所在的 AZ 故障，資料庫必須在數分鐘內自動恢復可寫入，且不能遺失任何已經提交的交易。應用程式透過資料庫 endpoint 連線，團隊不想修改連線設定。

最合適的做法是什麼？

- A. 在另一個 AZ 建立 read replica，並用 CloudWatch alarm 觸發 Lambda 在故障時 promote replica
- B. 啟用 RDS Multi-AZ 部署，讓 AWS 在另一個 AZ 維護同步複寫的 standby 並自動 failover
- C. 每小時建立一次手動 snapshot，故障時在另一個 AZ 還原
- D. 在另一個 Region 建立 cross-Region read replica，故障時修改應用程式連線字串

> [!answer]- 答案：B
> **A ✗** Read replica 是非同步複寫，promote 時可能遺失尚未複寫的交易；promote 後的 endpoint 也和原本不同，應用程式需要修改連線設定。這是用來擴展讀取的工具，不是高可用方案。
>
> **B ✓** RDS Multi-AZ 以同步方式把每筆提交的交易寫到另一個 AZ 的 standby，故障時 AWS 自動 failover 並把原本的 DNS endpoint 指向新的 primary，應用程式只需要重新連線，不需要修改設定，也不會遺失已提交的交易。
>
> **C ✗** 每小時 snapshot 代表最多遺失一小時的資料，還原大型資料庫也需要較長時間，不符合「不遺失交易」與「數分鐘內自動恢復」。
>
> **D ✗** 跨 Region read replica 用於 Region 等級的 DR，複寫是非同步的，且需要手動修改連線字串；對 AZ 故障而言過度複雜，也不能保證零資料遺失。
>
> **考點**：SAA-2.2｜RDS Multi-AZ 與 read replica 的差異

### 練習 34-2｜SAA｜單選｜靜態穩定的容量計算

Wanderly 的搜尋服務在尖峰時需要 24 台 EC2 instance 才能維持延遲目標。服務部署在一個 Region 的 3 個 AZ，由 ALB 與 Auto Scaling group 管理。架構審查要求：任何一個 AZ 完全故障時，服務必須立即維持尖峰容量，不能依賴故障發生後才啟動新的 instance。

在滿足需求的前提下，Auto Scaling group 的最小容量至少應設為多少台（平均分布在 3 個 AZ）？

- A. 24 台
- B. 30 台
- C. 48 台
- D. 36 台

> [!answer]- 答案：D
> **A ✗** 24 台平均分布時每個 AZ 8 台，失去一個 AZ 後只剩 16 台，低於尖峰需要的 24 台，必須等 Auto Scaling 補容量，違反需求。
>
> **B ✗** 30 台每 AZ 10 台，失去一個 AZ 後剩 20 台，仍然不足。
>
> **C ✗** 48 台每 AZ 16 台，失去一個 AZ 後剩 32 台，能滿足需求但多配了不必要的容量；這是在 2 個 AZ 架構下才需要的「兩倍容量」思維。
>
> **D ✓** 靜態穩定的公式是每 AZ 容量 = 尖峰需求 ÷（AZ 數 − 1）= 24 ÷ 2 = 12 台，3 個 AZ 共 36 台。失去任何一個 AZ 後剩下 24 台，正好撐住尖峰，而且不需要呼叫任何 control plane API。
>
> **考點**：SAA-2.2｜static stability 與預先配置容量

### 練習 34-3｜SAA｜單選｜辨識 DR 策略

一家公司在 DR Region 部署了以下資源：一個持續接收主要 Region 複寫的 Aurora Global Database secondary cluster、預先建立好的 VPC 與 security group、一個 ALB，以及一個 desired capacity 為 0 的 Auto Scaling group。災難發生時，維運人員會提升資料庫、把 Auto Scaling group 擴展到正式容量，然後切換 Route 53 記錄。

這個架構屬於哪一種 DR 策略？

- A. Pilot light
- B. Warm standby
- C. Backup and restore
- D. Multi-site active-active

> [!answer]- 答案：A
> **A ✓** Pilot light 的特徵是資料層在 DR Region 持續複寫並運作中，基礎設施預先建立，但應用程式運算層關閉（desired capacity 為 0）。DR 端在啟動運算前不能處理任何請求。
>
> **B ✗** Warm standby 的 DR 端有縮小但正在運作的完整環境，包含正在執行的應用程式 instance，可以立即接受流量。本題的運算層是 0 台。
>
> **C ✗** Backup and restore 的 DR 端只有備份，資料要從 snapshot 還原；本題的資料庫是持續複寫且運作中的。
>
> **D ✗** Active-active 兩個 Region 都在服務真實流量；本題的 DR Region 平時不接流量。
>
> **考點**：SAA-2.2｜pilot light 與 warm standby 的分界

### 練習 34-4｜SAA｜單選｜最低成本的 DR

Wanderly 的內部報表系統由 EC2 與 RDS for MySQL 組成。業務可以接受 Region 故障時最多停機 8 小時、遺失最多 24 小時的資料。公司要求 DR 方案的成本最低，並由營運團隊以最少的人工管理備份。

哪個方案最合適？

- A. 在 DR Region 維持一套縮小版的 EC2 與 RDS cross-Region read replica，故障時擴展
- B. 使用 DynamoDB global tables 取代 RDS，在兩個 Region 同時服務
- C. 用 AWS Backup 每日備份 EC2 與 RDS，並以 copy action 複製到 DR Region；以 CloudFormation template 在故障時重建環境並還原
- D. 在 DR Region 建立 Aurora Global Database secondary cluster，運算層平時關閉

> [!answer]- 答案：C
> **A ✗** 這是 warm standby，能達到分鐘級 RTO，但要持續支付 DR 端運作中的運算與資料庫費用，遠超過 8 小時 RTO 所需。
>
> **B ✗** 改用 DynamoDB 並 active-active 需要重寫應用程式，成本與複雜度最高，與需求不符。
>
> **C ✓** RTO 8 小時、RPO 24 小時正是 backup and restore 的範圍。AWS Backup 以 plan 集中管理每日備份與跨 Region copy，營運負擔低；DR 端平時只付備份儲存費，故障時用 IaC 重建並還原。
>
> **D ✗** 這是 pilot light，持續複寫的資料庫需要長期付費，而且要從 MySQL 遷移到 Aurora；對 24 小時 RPO 來說沒有必要。
>
> **考點**：SAA-2.2、SAA-4.3｜依 RTO／RPO 選擇最低成本 DR 策略

### 練習 34-5｜SAA｜單選｜分鐘級 RTO 的 DR

Wanderly 的訂房 API 部署在東京 Region，使用 ALB、EC2 Auto Scaling 與 Aurora MySQL。新的業務要求是：東京 Region 不可用時，必須在 15 分鐘內於新加坡恢復服務，資料遺失不得超過 1 分鐘。團隊希望能持續驗證 DR 環境確實可以處理請求，但不希望平時在新加坡維持完整規模的運算容量。

哪個方案最合適？

- A. 在新加坡只保留 Aurora 的每小時 snapshot copy 與 AMI，故障時用 CloudFormation 建立所有資源
- B. 建立 Aurora Global Database，新加坡部署 ALB 與小規模、持續運作的 Auto Scaling group；故障時提升資料庫、擴展 Auto Scaling group 並切換 Route 53
- C. 在新加坡部署與東京相同規模的環境，並讓兩邊以 weighted routing 各接 50% 的寫入流量
- D. 在東京的另一個 AZ 部署 Aurora Replica，並啟用 cross-zone load balancing

> [!answer]- 答案：B
> **A ✗** 每小時 snapshot 代表 RPO 最多 1 小時，故障時建立整套環境並還原資料庫也很難在 15 分鐘內完成。
>
> **B ✓** 這是 warm standby：Aurora Global Database 的複寫延遲通常低於 1 秒，符合 1 分鐘 RPO；新加坡有縮小但運作中的完整環境，可以用 synthetic 測試持續驗證，故障時只需提升資料庫、擴展容量並切換流量，能達到分鐘級 RTO。
>
> **C ✗** 兩邊完整規模並同時接受寫入是 active-active，成本違反「不維持完整規模」的需求；而且 Aurora Global Database 的 secondary 並不能直接接受寫入。
>
> **D ✗** 同 Region 內的 Aurora Replica 只能處理 AZ 故障，無法應付整個東京 Region 不可用。
>
> **考點**：SAA-2.2｜warm standby 與 Aurora Global Database

### 練習 34-6｜SAA｜選兩項｜S3 跨 Region 複寫

Wanderly 的旅館照片存在東京的 S3 bucket，已經累積 4 億個物件。為了 DR，團隊在新加坡建立了新 bucket 並設定 Cross-Region Replication rule。一週後檢查發現，新加坡的 bucket 只有設定之後上傳的照片。此外，稽核要求必須能證明新物件會在可預期的時間內完成複寫。

哪兩個做法可以滿足需求？（選兩項）

- A. 使用 S3 Batch Replication 把設定 replication rule 之前就存在的物件複寫到新加坡
- B. 停用來源 bucket 的 versioning，讓 replication 改為複製物件的最新狀態
- C. 把 replication rule 改成同 Region replication（SRR），再從新加坡讀取
- D. 為 replication rule 啟用 S3 Replication Time Control，並監控它提供的複寫延遲 metrics
- E. 在新加坡 bucket 啟用 Transfer Acceleration 以加快複寫

> [!answer]- 答案：A、D
> **A ✓** Replication rule 只會複製設定之後新寫入的物件，既有物件需要用 S3 Batch Replication 補複製。
>
> **B ✗** S3 replication 要求來源與目的 bucket 都啟用 versioning；停用 versioning 會讓 replication 無法運作。
>
> **C ✗** SRR 是在同一 Region 內複寫，無法提供跨 Region 的 DR 保護。
>
> **D ✓** S3 Replication Time Control 提供 99.99% 的物件在 15 分鐘內完成複寫的 SLA，並發布複寫延遲與待複寫數量的 metrics，可以作為可預期 RPO 的證據。
>
> **E ✗** Transfer Acceleration 是透過 edge location 加速用戶端上傳到 S3，不影響 bucket 之間的 replication 速度。
>
> **考點**：SAA-2.2、SAA-1.3｜S3 CRR、Batch Replication 與 RTC

一家旅遊公司的會員系統使用 MySQL 相容資料庫，主要服務在法蘭克福 Region。公司要求 Region 故障時，在另一個 Region 的資料遺失通常不超過數秒，資料庫切換在數分鐘內完成；平時另一個 Region 也要能提供低延遲的唯讀查詢。團隊希望複寫不要消耗主要資料庫 instance 的運算資源。

- C. 遷移到 Aurora MySQL 並建立 Aurora Global Database，在另一個 Region 加入 secondary cluster
- D. 使用 DynamoDB global tables 並保留 MySQL 的 schema

> **D ✗** DynamoDB 是 NoSQL 服務，沒有 MySQL 相容性，需要重新設計資料模型與應用程式。

- A. DynamoDB global tables，在兩個 Region 各建立副本
- B. Aurora Global Database，兩個 Region 的應用程式都直接寫入本地 cluster
- C. RDS for MySQL，在奧勒岡建立 cross-Region read replica
- D. 在每個 Region 各建一張獨立的 DynamoDB table，以每日 export 到 S3 互相同步

### 練習 34-9｜SAA｜單選｜防止備份被刪除

一家受金融法規管理的公司使用 AWS Backup 保護 RDS 與 EBS。最近的資安演練顯示，攻擊者若取得帳號管理員權限，可以刪除所有 recovery point。法規要求備份必須保存 7 年，期間任何人（包含帳號 root user）都不能刪除或縮短保存期限。

哪個做法能滿足需求？

- A. 在 backup vault 的 access policy 中加入 `Deny backup:DeleteRecoveryPoint`，並只允許安全團隊修改此 policy
- B. 把 recovery point 複製到同帳號的另一個 Region，並為該 vault 啟用 KMS 金鑰輪替
- C. 為 backup vault 啟用 Vault Lock governance mode，設定最短保存期限 7 年
- D. 為 backup vault 啟用 Vault Lock compliance mode，設定最短保存期限 7 年，並在冷靜期結束前確認設定

> [!answer]- 答案：D

>
> **C ✗** Governance mode 允許擁有足夠 IAM 權限的使用者移除鎖定，不符合「任何人都不能刪除」。
>
> **D ✓** Compliance mode 在冷靜期（最少 72 小時）結束後變成不可變更：任何人，包含 root user 與 AWS，都無法刪除保存期限內的 recovery point 或修改鎖定。因為之後無法反悔，必須在冷靜期內確認設定。
>
> **考點**：SAA-1.3、SAA-2.2｜AWS Backup Vault Lock 模式

- B. 用 AWS Backup 每小時備份 VMware 虛擬機，並複製到 AWS Region 的 vault
- C. 在每台伺服器安裝 AWS Elastic Disaster Recovery agent，持續複寫到 AWS 的 staging area，定期以 drill 啟動 recovery instance 驗證，並規劃 failback 流程
- D. 在 AWS 為每台伺服器預先啟動相同規格的 EC2，並以應用程式層的檔案同步工具每分鐘同步

> [!answer]- 答案：C
> **A ✗** MGN 是一次性遷移工具，題目要求的是保留地端並建立 DR，不是搬遷；6 個月內遷移 200 台含商用軟體的伺服器也風險很高。
>
> **B ✗** 每小時備份的 RPO 最多 1 小時，還原 200 台虛擬機也難以在 30 分鐘內完成。
>
> **C ✓** Elastic Disaster Recovery 以持續的區塊層級複寫提供秒級 RPO，recovery instance 可以在數分鐘內啟動；平時只付 staging area 低成本的複寫資源。Drill 不會中斷來源複寫，可以每季演練；事件結束後可以 failback 回地端。
>
> **D ✗** 預先啟動 200 台完整規格的 EC2 成本很高，自建檔案同步也無法可靠地保護作業系統與資料庫狀態，營運負擔大。
>
> **考點**：SAP-2.2、SAP-1.3｜AWS Elastic Disaster Recovery

### 練習 34-12｜SAP｜選兩項｜跨帳號備份副本

Wanderly 使用 AWS Organizations 管理 40 個帳號。資安團隊建立了一個專用的 backup 帳號，要求所有 production 帳號的 RDS 備份都必須複製一份到 backup 帳號的 vault，以防 production 帳號被入侵。設定 copy action 後，copy job 一直失敗。RDS instance 使用 customer managed KMS key 加密。

哪兩個步驟是讓跨帳號 copy 成功的必要設定？（選兩項）

- A. 在每個 production 帳號建立 IAM user，並把 access key 交給 backup 帳號
- B. 在 Organizations management account 的 AWS Backup 設定中啟用 cross-account backup，並在 backup 帳號目的 vault 的 access policy 允許來源帳號（或整個 Organization）複製 recovery point
- C. 把 backup 帳號的 vault 改成使用 AWS managed key（`aws/backup`），讓所有帳號都能存取
- D. 在 production 帳號的 backup vault 啟用 Vault Lock compliance mode
- E. 在來源 RDS 使用的 customer managed KMS key 的 key policy 中允許 backup 帳號使用該金鑰，以便複製加密的 recovery point

> [!answer]- 答案：B、E
> **A ✗** AWS Backup 的跨帳號 copy 透過 Organizations 與資源政策授權，不需要也不應該建立長期 access key。
>
> **B ✓** 跨帳號 copy 要求來源與目的帳號在同一個 Organization，並在 management account 啟用 cross-account backup；目的 vault 的 access policy 也必須允許 `backup:CopyIntoBackupVault` 給來源帳號或 Organization。
>
> **C ✗** AWS managed key 的 key policy 無法修改、不能授權其他帳號使用；對 RDS 這類不是由 AWS Backup 完整管理的資源，跨帳號 copy 的目的 vault 必須使用 customer managed key，改成 `aws/backup` 反而會讓 copy 失敗。
>
> **D ✗** Vault Lock 保護的是 vault 內 recovery point 不被刪除，與 copy job 能否成功無關。
>
> **E ✓** AWS Backup 文件明確要求：來源資源若以 customer managed key 加密，必須把這把 key 分享給目的帳號（在 key policy 允許目的帳號使用），否則 copy job 會因為無法存取金鑰而失敗。副本到達後再以目的 vault 的 key 重新加密。
>
> **考點**：SAP-2.2、SAP-1.4｜AWS Backup 跨帳號 copy 與 KMS

### 練習 34-13｜SAP｜單選｜可靠的 Region 切換

Wanderly 的 Tier 0 訂房服務在東京與新加坡採 warm standby。過去演練發現兩個問題：一是有一次值班人員誤把兩個 Region 的流量都關閉，造成全面中斷；二是公司擔心在大型事件中，修改 Route 53 DNS 記錄的 API 可能無法使用。公司希望 Region 切換由人決定，但執行要可靠且防止誤操作。

最合適的做法是什麼？

- A. 使用 Amazon Application Recovery Controller 的 routing control 綁定 Route 53 failover record 的 health check，並設定 assertion safety rule 要求至少一個 Region 保持開啟
- B. 撰寫 Lambda 函數，在收到值班人員指令時呼叫 `ChangeResourceRecordSets` 修改 Route 53 記錄
- C. 把 Route 53 記錄改為 weighted routing，切換時由值班人員在 console 中把權重改為 0 與 100
- D. 使用 Route 53 failover routing 搭配檢查首頁的 health check，完全由 health check 自動決定切換

> [!answer]- 答案：A
> **A ✓** ARC routing control 的狀態透過跨 5 個 Region 的 cluster data plane 更新，可以從任一健康的 endpoint 切換，不需要依賴 Route 53 control plane 修改記錄；assertion safety rule 能阻止「所有 Region 都關閉」這類誤操作；切換仍由人決定。
>
> **B ✗** `ChangeResourceRecordSets` 屬於 Route 53 的 control plane，正是公司擔心在大型事件中可能無法使用的 API；Lambda 也沒有防誤操作的保護。
>
> **C ✗** 修改權重一樣是修改 DNS 記錄（control plane），而且人工在 console 輸入權重容易出錯，沒有 safety rule。
>
> **D ✗** 完全自動的切換不符合「由人決定」，而且只檢查首頁的 health check 可能無法反映資料庫狀態；warm standby 的 DB 尚未提升時自動切換只會造成錯誤。
>
> **考點**：SAP-2.2、SAP-3.4｜ARC routing control 與 safety rules

### 練習 34-14｜SAP｜單選｜AZ 灰色故障

Wanderly 的 API 部署在東京 3 個 AZ，前面是 ALB，每個 AZ 預先配置了足夠的容量以承受失去一個 AZ。某天監控顯示 `ap-northeast-1a` 的 target 延遲異常升高、部分請求逾時，但 ALB health check 仍然通過，AWS Health Dashboard 也尚未發布事件。團隊希望在幾分鐘內暫時把流量從 1a 移走，並在問題排除或到期後自動恢復，且日後 AWS 偵測到 AZ 問題時能自動處理。

最合適的做法是什麼？

- A. 修改 Auto Scaling group，移除 1a 的 subnet，等問題排除後再加回來
- B. 把 ALB 的 cross-zone load balancing 關閉，讓 1a 的流量只留在 1a
- C. 建立 Route 53 failover record，把東京 Region 的流量切到新加坡
- D. 使用 ARC zonal shift 把 ALB 的流量從 1a 移走並設定到期時間，並為該資源啟用 zonal autoshift 與定期 practice run

> [!answer]- 答案：D
> **A ✗** 修改 Auto Scaling group 會終止 1a 的 instance 並需要之後重新建立，屬於 control plane 操作，速度慢且不會自動恢復。
>
> **B ✗** 關閉 cross-zone 不會讓流量避開 1a，反而讓送到 1a 節點的流量只能使用 1a 的 target，使問題更嚴重。
>
> **C ✗** 問題只在一個 AZ，切換整個 Region 代價過大，且題目的架構已經能在少一個 AZ 時撐住。
>
> **D ✓** Zonal shift 專門用於暫時把支援的資源（例如 ALB）的流量從某個 AZ 移走，適合 health check 仍通過的灰色故障，到期後自動恢復。Zonal autoshift 讓 AWS 偵測到 AZ 問題時自動執行，practice run 則定期證明應用程式能在少一個 AZ 時運作。
>
> **考點**：SAP-3.4、SAP-1.3｜ARC zonal shift 與 autoshift

### 練習 34-15｜SAP｜單選｜在正式環境安全演練

Wanderly 想在正式環境驗證「失去一個 AZ 的 EC2 與 RDS primary 時，訂房成功率仍維持在 99% 以上」。管理階層同意演練，但要求：故障注入要可重複、權限最小化、並且只要訂房成功率低於 97% 或 ALB 5xx 錯誤率超過門檻，就必須立即自動停止。

最合適的做法是什麼？

- A. 由工程師在演練時手動終止 1a 的 EC2 並重新啟動 RDS with failover，同時觀看 dashboard，必要時手動停止
- B. 建立 AWS FIS experiment template，以 tag 選取 1a 的 EC2 與 RDS，使用最小權限的 IAM role，並把訂房成功率與 5xx 錯誤率的 CloudWatch alarm 設為 stop condition
- C. 使用 AWS Resilience Hub 執行 assessment，以其估算的 RTO 取代實際演練
- D. 在 staging 環境用相同的手動步驟演練，並假設正式環境的結果相同

> [!answer]- 答案：B
> **A ✗** 手動操作無法保證可重複，觀看 dashboard 再手動停止反應較慢，不符合「立即自動停止」。
>
> **B ✓** FIS 的 experiment template 讓故障注入可重複；targets 用 tag 精準選取範圍；IAM role 限制 FIS 能做的事；stop condition 綁定 CloudWatch alarm，alarm 一進入 ALARM 狀態實驗就自動停止。
>
> **C ✗** Resilience Hub 的 assessment 是根據架構估算韌性與找出缺口，不能取代實際注入故障並量測業務結果。
>
> **D ✗** Staging 的容量、流量與設定通常與正式環境不同，結果不能直接代表正式環境，也沒有自動停止機制。
>
> **考點**：SAP-3.4、SAP-3.1｜AWS FIS stop conditions 與 game day

### 練習 34-16｜SAP｜選兩項｜邏輯損毀的復原

Wanderly 的會員資料存在 DynamoDB global tables（東京與新加坡），訂單存在 Aurora Global Database。一次錯誤部署的程式在 20 分鐘內把數萬筆會員的 email 欄位覆寫成空值，訂單資料表也被一個錯誤的 migration 刪除了一個欄位的內容。錯誤在兩個 Region 都出現了。公司要求日後能把資料恢復到錯誤發生前的狀態，且要能定期證明復原流程有效。

哪兩個做法最合適？（選兩項）

- A. 把 Route 53 切換到新加坡 Region，因為新加坡的副本不受錯誤部署影響
- B. 增加 DynamoDB global tables 的 Region 數量，讓更多副本保有正確資料
- C. 為 DynamoDB table 啟用 point-in-time recovery，並為 Aurora 設定足夠的備份保存期限（或使用 AWS Backup continuous backup），以便還原到錯誤發生前的時間點
- D. 把 Aurora Global Database 的複寫延遲調高到 1 小時，讓 secondary 保留舊資料
- E. 建立 AWS Backup restore testing plan，定期自動還原到測試環境並以 Lambda 驗證資料內容與還原時間

> [!answer]- 答案：C、E
> **A ✗** Global tables 與 Aurora Global Database 都會把錯誤寫入複寫到新加坡，切換 Region 無法取回被覆寫的資料。
>
> **B ✗** 更多副本只會讓錯誤被複寫到更多地方；複寫保護地點，不保護時間。
>
> **C ✓** DynamoDB PITR 可以還原到過去 35 天內的任一秒；Aurora 的自動備份與 AWS Backup continuous backup 也支援 point-in-time restore。這讓團隊能把資料還原到錯誤部署之前，再把正確資料修補回正式表。
>
> **D ✗** Aurora Global Database 不提供刻意延遲複寫的設定，而且即使有，也會讓 Region 故障時的 RPO 變差。
>
> **E ✓** Restore testing 定期自動還原、記錄還原時間並在測試後清理資源，搭配 Lambda 驗證資料內容，能持續證明復原流程與 RTO 真的有效。
>
> **考點**：SAP-2.2、SAP-3.4｜複寫不等於備份、PITR 與 restore testing
