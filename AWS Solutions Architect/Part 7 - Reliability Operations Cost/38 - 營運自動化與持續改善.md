# 第 38 章　營運自動化：Systems Manager、事件驅動修復與持續改善

> [!abstract] 本章地圖
> **你會學到**：
> - 說清楚 Systems Manager 的 managed node 需要哪三個條件（agent、IAM 權限、網路路徑），並排除「instance 不出現在 Fleet Manager」的問題
> - 用 Session Manager 取代 bastion host，做到不開 inbound port、以 IAM 授權、完整留下操作紀錄
> - 分辨 Run Command、State Manager、Maintenance Windows、Patch Manager 與 Automation 各自解決什麼問題，並設計分批、可回報合規狀態的 patch 流程
> - 用 EventBridge、AWS Config remediation 與 Automation runbook 建立「偵測 → 判斷 → 修復 → 通知」的事件驅動修復，並避免修復迴圈
> - 用 runbook／playbook、事後檢討、Well-Architected Tool、Trusted Advisor 與 AWS Health 建立持續改善的營運節奏
>
> **前置知識**：第 12 章（IAM role 與 policy）、第 16 章（AWS Config、CloudTrail）、第 32 章（EventBridge）、第 36 章（CloudWatch）、第 37 章（IaC）
> **考試比重**：SAA ★★☆（Domain 1 安全存取、Domain 2 韌性）｜SAP ★★★（Domain 3 持續改善、Domain 1 多帳號治理）

## 38.1 故事：凌晨三點的 SSH 與第三次發生的同一個事故

Wanderly 上線一年，系統已經長成 60 台 EC2（web、批次 worker、幾台還沒容器化的舊服務），分散在 production、staging 兩個帳號。營運方式卻還停留在第一天：工程師要登入機器時，先 SSH 到一台放在 public subnet 的 **bastion host**（跳板機），再從那裡 SSH 進 private subnet。所有人共用同一把 SSH 金鑰，離職同事的金鑰到現在還沒換。

某個星期五，一個廣泛使用的 Java 函式庫爆出嚴重漏洞。資安團隊要求週末前修補全部機器。值班的小林只能寫一個 shell 迴圈逐台 SSH 進去跑 `yum update`，跑到第 40 台時發現有幾台的 SSH key 不對，有兩台更新後沒有重開機，還有一台重開後 Java 服務沒有起來。週一早上，沒有人能明確回答「現在到底有幾台已經修補完成」。

同一個月，staging 帳號裡有一個 S3 bucket 被人在測試時改成公開，三天後才被外部回報；這已經是今年第三次。每次事後大家都說「下次要小心」，但沒有任何機制改變。

技術主管把問題寫成三句話：**登入機器不該需要開 port 和共用金鑰；重複性的維運動作必須能大規模、可追蹤地執行；已知的錯誤設定應該被自動偵測並修好，而每次事故都要讓系統變得更好。** 這一章依序解決這三件事：先用 Systems Manager 把機器變成「可被管理的節點」，再用事件驅動修復處理錯誤設定，最後談營運卓越的持續改善機制。

## 38.2 Systems Manager 是什麼：先讓機器變成 managed node

**AWS Systems Manager（簡稱 SSM）** 是一組管理 EC2、地端伺服器與虛擬機的工具集合，包含遠端登入、批次執行指令、patch、設定維持、軟體盤點、自動化 runbook 等功能。它的共同前提是：機器必須先成為 **managed node（受管節點）**，也就是 Systems Manager 能看見、能下指令的機器。

### 成為 managed node 的三個條件

1. **SSM Agent**：一個在機器上執行的程式，負責主動向 Systems Manager 服務報到、領取指令、回報結果。Amazon Linux 2／2023、Ubuntu、Windows Server 等常見的 AWS 官方 AMI 已預先安裝；自訂 AMI 或地端伺服器要自己安裝。
2. **IAM 權限**：agent 呼叫 Systems Manager API 時需要身份。EC2 最常見的做法是掛一個 **instance profile**（裝著 IAM role 的容器，第 12 章），role 附上 AWS managed policy `AmazonSSMManagedInstanceCore`。
3. **網路路徑**：agent 必須能以 HTTPS（TCP 443）**主動連出**到 Systems Manager 的 endpoint。注意方向：是機器連出去，不是 Systems Manager 連進來，所以**不需要任何 inbound 規則**。

這三個條件缺一個，機器就不會出現在 Fleet Manager 的節點清單裡。考試很愛考第三點：private subnet 沒有 NAT Gateway 時，agent 根本連不到服務。

### Agent 的連線路徑

```text
            ┌──────────────── private subnet（無 NAT）────────────────┐
            │                                                         │
            │  [EC2 + SSM Agent]                                      │
            │     │ ① instance profile 提供暫時憑證                   │
            │     │ ② HTTPS 443 主動連出                              │
            │     ▼                                                   │
            │  [Interface endpoints]                                  │
            │    com.amazonaws.<region>.ssm          ← 註冊、API      │
            │    com.amazonaws.<region>.ssmmessages  ← Session 通道   │
            │    com.amazonaws.<region>.ec2messages  ← 指令派送       │
            │     │                                                   │
            └─────┼───────────────────────────────────────────────────┘
                  ▼ ③ 經 AWS 內部網路
          [AWS Systems Manager 服務] ── ④ 下發指令、接收結果與 inventory
                  │
          （若要把 session log 寫到 S3 / CloudWatch Logs，
             還需要 S3 gateway endpoint、logs、kms 等對應 endpoint）
```

① Agent 啟動後從 instance metadata 取得 role 的暫時憑證，不需要在機器上放任何 access key。② Agent 對外建立 443 連線；若 subnet 有 NAT Gateway，走 NAT 也可以，但流量會經過 Internet 路徑並產生 NAT 處理費。③ 在完全沒有對外路徑的 isolated subnet，就要建立三個 interface VPC endpoint（第 6 章），並開啟 VPC 的 DNS 屬性，讓服務名稱解析到 endpoint 的私有 IP。④ Systems Manager 透過 agent 已建立的長連線把指令「推」下去，這也是為什麼它能在沒有任何 inbound port 的情況下運作。

> [!note] Default Host Management Configuration
> 大規模環境裡，逐台確認 instance profile 很麻煩。**Default Host Management Configuration（DHMC）** 是帳號／Region 層級的設定：開啟後，Systems Manager 會用一個指定的 IAM role 自動管理該 Region 所有 EC2，即使 instance 沒有掛任何 instance profile。前提是 instance 使用 IMDSv2，且 agent 版本夠新。

### 地端與其他雲的機器：hybrid activation

Systems Manager 不只管 EC2。對地端伺服器或其他雲的 VM，先建立一個 **hybrid activation**（得到 activation code 與 ID），在機器上安裝 agent 並用這組代碼註冊，它就會以 `mi-` 開頭的 ID 成為 managed node。這些機器沒有 instance profile，靠的是 activation 時指定的 IAM service role。

地端節點預設屬於 standard-instances tier；若要對它們使用 Session Manager 等進階功能，需要把帳號的節點層級切換到收費的 **advanced-instances tier**。這在第 44、45 章的遷移情境很常用：機器還沒搬上雲之前，就先用同一套工具 patch 與盤點。

有了 managed node，第一個要解決的痛點就是那台 bastion host。

## 38.3 Session Manager：不開 port、不發金鑰的遠端登入

### Bastion host 的問題

Bastion host 的模式是「在 public subnet 開一台機器、開放 22 port、大家用 SSH key 跳進去」。它有幾個結構性問題：

- 必須有 inbound port 對外開放，即使限制來源 IP，仍是攻擊面。
- SSH key 是長期憑證，難以輪替、難以追蹤是誰在用；共用金鑰時更無法歸責。
- 誰在什麼時間打了什麼指令，要自己想辦法記錄。
- Bastion 本身要 patch、要高可用，是另一台需要照顧的機器。

### Session Manager 怎麼運作

**Session Manager** 是 Systems Manager 的遠端登入功能：使用者在 console、AWS CLI（搭配 Session Manager plugin）發起 session，服務透過 agent 已經建立好的連出通道，在機器上開一個 shell。整個過程：

1. 使用者用自己的 IAM 身份（通常是 IAM Identity Center 的 role）呼叫 `ssm:StartSession`。
2. IAM 決定這個人能不能對這台機器開 session，可以用 tag 條件限制範圍。
3. 服務經 `ssmmessages` 通道與 agent 建立雙向串流，使用者的鍵盤輸入與畫面輸出都走這條通道。
4. `StartSession` 這個 API 呼叫被 CloudTrail 記錄；session 內容則可以串流或上傳到 CloudWatch Logs 或 S3。

結果是：**security group 不需要任何 inbound 規則、不需要 public IP、不需要 SSH key、不需要 bastion**。這正是考題「LEAST operational overhead 且不得開放 inbound port 的安全遠端存取」的標準答案。

### 用 IAM 控制誰能登入哪些機器

下面的 policy 允許開發者只對 `Environment=staging` 的 instance 開 session，並只能結束自己開的 session：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StartSessionOnStagingOnly",
      "Effect": "Allow",
      "Action": "ssm:StartSession",
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringEquals": { "ssm:resourceTag/Environment": "staging" }
      }
    },
    {
      "Sid": "AllowSessionDocument",
      "Effect": "Allow",
      "Action": "ssm:StartSession",
      "Resource": "arn:aws:ssm:*:*:document/SSM-SessionManagerRunShell"
    },
    {
      "Sid": "ManageOwnSessions",
      "Effect": "Allow",
      "Action": ["ssm:TerminateSession", "ssm:ResumeSession"],
      "Resource": "arn:aws:ssm:*:*:session/${aws:userid}-*"
    }
  ]
}
```

第一段用 `ssm:resourceTag/...` 條件把範圍限縮到特定 tag 的機器，這是 ABAC（第 12 章）的典型用法。第二段允許使用預設的 session 設定文件。第三段讓使用者只能操作以自己 user ID 開頭的 session。

### Session 設定與稽核

**Session preferences**（帳號／Region 層級的 session 設定）可以決定：

- **Logging**：把 session 的輸出串流到 CloudWatch Logs，或在 session 結束後上傳到 S3；可要求目標 log group／bucket 必須加密。
- **KMS 加密**：用指定的 KMS key 對 session 資料做額外加密（在 TLS 之上再加一層）。
- **Idle timeout 與最長 session 時間**：避免忘記關閉的 session 一直掛著。
- **Run As**（Linux）：以指定的 OS 使用者身份登入，而不是預設的 `ssm-user`。

> [!warning] 常見誤解
> 「開了 Session Manager logging 就能錄下所有操作。」Session Manager 也支援 **port forwarding** 與 **SSH over Session Manager**（讓 `ssh`、`scp` 走 Session Manager 通道），但這兩種 session 的內容是在使用者端加密的資料流，**Session Manager 不會記錄其內容**。如果合規要求完整的指令紀錄，就要限制使用者只能開一般 shell session（在 IAM 裡不允許 `AWS-StartPortForwardingSession`、`AWS-StartSSHSession` 文件）。CloudTrail 仍然會記錄「誰在何時對哪台機器開了 session」。

### Port forwarding：不用 bastion 也能連 RDS

開發者有時需要從筆電用 GUI 工具連 private subnet 的資料庫。傳統做法是透過 bastion 做 SSH tunnel。Session Manager 提供 `AWS-StartPortForwardingSessionToRemoteHost` 文件：在筆電上開一個本地 port，經某台 managed node 轉送到遠端主機（例如 RDS endpoint 的 3306）。資料庫的 security group 只需要允許那台 managed node，而那台 managed node 不需要任何 inbound 規則。

```bash
aws ssm start-session \
  --target i-0abc1234def567890 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["wanderly-db.cluster-xxxx.ap-northeast-1.rds.amazonaws.com"],"portNumber":["3306"],"localPortNumber":["13306"]}'
```

> [!note] EC2 Instance Connect Endpoint
> 另一個免 bastion 的選項是 **EC2 Instance Connect Endpoint**：在 VPC 建立一個端點，讓使用者經 IAM 授權後直接 SSH／RDP 到 private subnet 的 instance，不需要 SSM Agent。它適合「必須用原生 SSH，但不想有 bastion」的情境；若重視 session 內容記錄、要同時管理地端機器，Session Manager 較合適。

登入問題解決了。但 Wanderly 真正痛的是「同一件事要在 60 台機器上做」，這需要 Run Command。

## 38.4 Run Command 與 SSM document：一次對一群機器下指令

### SSM document：把動作寫成文件

Systems Manager 的所有動作都由 **SSM document** 定義。Document 是一份 JSON 或 YAML，描述「要執行什麼步驟、需要哪些參數」。常見類型：

| Document 類型 | 用在哪裡 | 例子 |
|---|---|---|
| Command | Run Command、State Manager、Maintenance Windows | `AWS-RunShellScript`、`AWS-RunPatchBaseline` |
| Automation（runbook） | Automation、Config remediation | `AWS-RestartEC2Instance`、`AWS-CreateImage` |
| Session | Session Manager | `SSM-SessionManagerRunShell` |
| Package | Distributor 安裝軟體 | CloudWatch agent 套件 |

AWS 提供數百份現成 document（名稱以 `AWS-` 開頭），你也可以寫自己的 document 並分享給其他帳號。

### Run Command：可控速率的批次執行

**Run Command** 用來對一群 managed node **立即**執行一份 Command document。它比自己寫 SSH 迴圈好的地方在於：

- **用 tag 或 resource group 選目標**，例如 `tag:Role=web`，不必維護機器清單。
- **Rate control（速率控制）**：`max-concurrency` 決定同時執行幾台（數量或百分比），`max-errors` 決定失敗超過多少台就停止派送給剩下的機器。這讓一個有 bug 的腳本不會一次弄壞整個 fleet。
- **輸出與狀態集中**：每台機器的執行狀態（Success、Failed、TimedOut…）都在 console 或 API 上看得到，完整輸出可以寫到 S3 或 CloudWatch Logs。
- **可稽核**：`SendCommand` 被 CloudTrail 記錄，誰下了什麼指令一目了然。
- **不需要 SSH**：同樣走 agent 的連出通道。

```bash
aws ssm send-command \
  --document-name "AWS-RunShellScript" \
  --targets "Key=tag:Role,Values=web" "Key=tag:Environment,Values=production" \
  --parameters 'commands=["systemctl restart wanderly-web","systemctl is-active wanderly-web"]' \
  --max-concurrency "20%" \
  --max-errors "1" \
  --output-s3-bucket-name "wanderly-ssm-output" \
  --comment "Restart web service after config change"
```

這個指令每次最多對 20% 的 web 機器執行；只要有 1 台失敗，就不再派送給尚未開始的機器。Load Balancer 後面始終有 80% 的機器在服務，這就是「分批、可中止」的維運動作。

Run Command 是一次性的。但很多需求是「持續」的：例如每台機器都要裝著 CloudWatch agent，新開的機器也要。這就需要下一個工具。

## 38.5 State Manager、Inventory 與 Fleet Manager：維持狀態、看見全貌

### State Manager：宣告「應該長什麼樣子」

**State Manager** 用 **association（關聯）** 把一份 document 綁定到一群目標，並依排程**反覆套用**，讓機器持續維持在期望狀態。和 Run Command 的差別是：

- Run Command：「現在對這些機器做一次」。
- State Manager：「這些機器應該一直保持這個狀態；新加入符合條件的機器也要自動套用；每 30 分鐘（或你定義的排程）檢查並修正一次。」

典型用途：

- 確保所有 instance 都安裝並設定好 CloudWatch agent（第 36 章），用 `AWS-ConfigureAWSPackage` 安裝套件。
- 確保某個安全設定（例如關閉某個服務）維持不變，若有人手動改掉，下次執行會改回來。
- 定期收集 inventory。
- Auto Scaling 新開的機器啟動後自動加入 domain、安裝代理程式。

Association 的執行結果會進入 **Compliance**（合規報告）：哪些機器符合、哪些失敗，一眼可見。

### Inventory：機器上到底裝了什麼

漏洞事件裡最難回答的問題是「哪些機器裝了這個有問題的套件版本」。**Inventory** 透過 State Manager association（`AWS-GatherSoftwareInventory`）定期收集每台 managed node 的資訊：已安裝的應用程式與版本、網路設定、Windows 更新、服務、檔案、registry，以及你自訂的 inventory 類型。

單一帳號可以直接在 console 查詢。要跨帳號、跨 Region 彙整時，設定 **resource data sync**，把所有 inventory 資料匯入一個集中的 S3 bucket，再用 Athena（第 30 章）以 SQL 查詢：「列出所有 log4j 版本低於 2.17 的機器」。

### Fleet Manager：一個畫面管理所有節點

**Fleet Manager** 是 Systems Manager 的節點管理介面：列出所有 managed node 與其 agent 狀態、ping 狀態、作業系統，並能直接在瀏覽器裡檢視檔案系統、效能計數器、OS 使用者與群組、日誌；Windows 機器還能直接用瀏覽器開遠端桌面。它是排除「這台機器為什麼不受管」的第一站：看 ping 狀態是否 Online、agent 版本是否過舊。

### Parameter Store 與設定值

**Parameter Store** 也屬於 Systems Manager，提供階層式的設定值與 SecureString（以 KMS 加密）儲存，例如 `/wanderly/prod/payment/api-url`。Standard tier 免費（每帳號每 Region 最多 10,000 個參數、每個 4 KB）；advanced tier 收費，提供更大的參數與 parameter policies（例如到期提醒）。它和 Secrets Manager 的比較已在第 15 章詳細說明；在營運自動化裡，它的角色是讓 runbook、user data、Lambda 從同一個地方讀取設定，而不是把值寫死在腳本裡。至於需要漸進式推出、可自動回滾的應用程式設定或 feature flag，則用第 37 章的 AppConfig。

到這裡，Wanderly 能登入、能批次執行、能看見全貌。接著要處理那個週末的主角：patch。

## 38.6 Patch Manager 與 Maintenance Windows：可回報、可分批的修補

### Patch 為什麼難

修補不只是「執行更新指令」。真正的需求是：

1. **決定哪些 patch 該裝**：只裝安全性更新？等廠商釋出 7 天後再裝以避開有問題的 patch？某個 patch 已知會弄壞應用程式，要排除？
2. **決定何時裝、一次裝多少**：不能在尖峰時段，也不能同時讓所有 web server 重開。
3. **證明裝好了**：稽核要的是「每台機器目前缺哪些 patch」的報告，而不是「我有跑過指令」。

Patch Manager 依序回答這三個問題。

### Patch baseline：哪些 patch 被核准

**Patch baseline** 是一組核准規則，定義對某種作業系統而言「哪些 patch 算應該安裝」：

- **Approval rules**：依產品、分類（Security、Bugfix…）、嚴重度（Critical、Important…）篩選，並設定 **auto-approval delay**（例如發布 7 天後自動核准）或指定核准截止日期。
- **Approved patches／Rejected patches**：明確加入或排除特定 patch。
- **Compliance level**：缺少這個 baseline 的 patch 時，在合規報告中算什麼嚴重度。

AWS 為每種作業系統提供 **predefined baseline**（例如 Amazon Linux 2023 的預設 baseline），也可以建立 **custom baseline**。實務上，正式環境常用 custom baseline 並設定延遲核准，讓 staging 先裝、觀察幾天，再讓 production 自動跟上。

### AWS-RunPatchBaseline：Scan 與 Install

真正執行修補的是 Command document **`AWS-RunPatchBaseline`**，它有兩種 operation：

| Operation | 做什麼 | 什麼時候用 |
|---|---|---|
| `Scan` | 比對 baseline，回報缺少哪些 patch，**不安裝** | 每天執行，維持最新的合規報告 |
| `Install` | 安裝缺少且已核准的 patch，依 `RebootOption` 決定是否重開機 | 在維護時段執行 |

`RebootOption` 可設為 `RebootIfNeeded` 或 `NoReboot`。選 `NoReboot` 時，有些 patch 雖已安裝但尚未生效，合規報告會標示為「已安裝待重開機」，這是小林那兩台「更新了但沒重開」的機器在報告中應該呈現的樣子。

### Maintenance Windows：在對的時間、用對的速度

**Maintenance Window（維護時段）** 定義一個排程時間窗，在窗內依序執行註冊的工作：

- **Schedule**：cron 或 rate 表達式，例如每週二凌晨 2 點（可指定時區）。
- **Duration 與 cutoff**：時段長度，以及結束前多久停止派送新工作，避免工作跑到尖峰時段。
- **Targets**：用 tag 選擇目標。
- **Tasks**：可以是 Run Command、Automation、Lambda 或 Step Functions，各自設定 rate control 與優先順序。

```text
週二 02:00 ─────────── Maintenance Window（3 小時，cutoff 1 小時）────────── 05:00
   │
   ├─ Task 1（優先序 1）：AWS-RunPatchBaseline Install，targets: tag PatchWave=1
   │      max-concurrency 25%、max-errors 1、RebootIfNeeded
   │
   ├─ Task 2（優先序 2）：Run Command 健康檢查腳本，確認服務已起來
   │
   └─ 04:00 之後（進入 cutoff）不再啟動新的 task，已開始的 task 跑完
```

`PatchWave=1` 的機器先修；Wave 2 的機器放在隔天的時段。每個 AZ 都有機器分配在不同的 wave，確保任何時刻每個 AZ 都還有健康的機器在服務。

### Patch policy：用 Quick Setup 一次設定好

上面的元件（baseline、維護時段、scan 與 install 排程）可以逐一手動組合；較新的做法是用 **Quick Setup** 建立 **patch policy**：在一份設定裡指定 baseline、scan 排程、install 排程、目標（可以是整個 Organization、指定 OU 或帳號與 Region），由 Quick Setup 自動在各帳號建立需要的資源。舊做法用 `Patch Group` tag 把 instance 對應到 baseline，在既有環境中仍很常見；新設計優先使用 patch policy。

### Patch 的另一條路：不 patch，換掉

對無狀態的 web tier，還有一個更乾淨的做法：**不在原機器上 patch，而是建立新的 golden AMI，再滾動替換所有 instance**。EC2 Image Builder 可以定期以最新 patch 產生 AMI 並跑測試，Auto Scaling 的 instance refresh（第 18 章）負責滾動替換。這就是 immutable infrastructure：每台機器都是同一個 AMI 開出來的，不存在「某台沒裝好」的漂移問題。

| 方式 | 適合 | 優點 | 代價 |
|---|---|---|---|
| In-place（Patch Manager） | 有狀態、無法輕易替換的機器；地端伺服器 | 不需要重建流程 | 機器之間可能漂移、重開機有風險 |
| Immutable（新 AMI + instance refresh） | ASG 後面的無狀態機器 | 一致、可回滾到舊 AMI | 需要 AMI pipeline 與 ASG 設計 |

> [!tip] 考試提示
> 題目說「需要報告所有 instance 的 patch 合規狀態」→ Patch Manager 的 Scan + Compliance。「在指定時段、分批 patch」→ Maintenance Window + rate control。「確保 ASG 中所有 instance 都使用最新 patch 的 AMI」→ EC2 Image Builder + instance refresh，而不是對 ASG 的 instance 做 in-place patch。

Patch 是我們「預先排定」的維運。但很多維運動作是「事情發生了才需要做」，而且要依序做好幾步。下一節的 Automation 處理的就是這種多步驟流程。

## 38.7 Automation runbook：把操作手冊寫成程式

### 為什麼需要 runbook 自動化

Wanderly 的 wiki 上有一份「web server 記憶體耗盡時的處理步驟」：先做一份 AMI 留證據、從 target group 移除、重開機、確認健康後加回去、通知頻道。每次事故時，值班工程師半夜照著 wiki 一步一步做，常常漏掉第一步。

**Automation** 是 Systems Manager 執行多步驟流程的引擎，流程定義在 **Automation runbook**（Automation 類型的 SSM document）裡。和 Run Command 不同，Automation 主要呼叫 **AWS API**（建立 AMI、停止 instance、修改 security group），也能在步驟中呼叫 Run Command 進機器執行指令、執行 Python／PowerShell 腳本、等待條件成立、做條件分支，甚至暫停等待人工核准。

### 常用的步驟（actions）

| Action | 用途 |
|---|---|
| `aws:executeAwsApi` | 呼叫任意 AWS API，並把回傳值存成輸出 |
| `aws:runCommand` | 在 managed node 上執行 Command document |
| `aws:executeScript` | 執行一段 Python 或 PowerShell 腳本 |
| `aws:waitForAwsResourceProperty` | 等待某個資源屬性變成指定值 |
| `aws:branch` | 依條件走不同步驟 |
| `aws:approve` | 暫停，等待指定的 IAM 主體核准 |
| `aws:createImage`、`aws:changeInstanceState` | 建立 AMI、啟動／停止 instance |

### 一份簡化的 runbook

```yaml
description: Capture evidence and restart an unhealthy web instance
schemaVersion: '0.3'
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  InstanceId:
    type: String
  AutomationAssumeRole:
    type: String
  ApproverArn:
    type: StringList
mainSteps:
  - name: CreateEvidenceImage
    action: aws:createImage
    inputs:
      InstanceId: '{{ InstanceId }}'
      ImageName: 'evidence-{{ InstanceId }}-{{ global:DATE_TIME }}'
      NoReboot: true
  - name: ApproveRestart
    action: aws:approve
    timeoutSeconds: 3600
    inputs:
      Approvers: '{{ ApproverArn }}'
      MinRequiredApprovals: 1
      Message: 'Evidence AMI created. Approve restart of {{ InstanceId }}?'
  - name: RestartInstance
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: RebootInstances
      InstanceIds:
        - '{{ InstanceId }}'
  - name: WaitUntilRunning
    action: aws:waitForAwsResourceProperty
    inputs:
      Service: ec2
      Api: DescribeInstanceStatus
      InstanceIds:
        - '{{ InstanceId }}'
      PropertySelector: '$.InstanceStatuses[0].InstanceStatus.Status'
      DesiredValues:
        - ok
```

讀這份 runbook 要注意三點。第一，`assumeRole` 指定 Automation 用哪個 IAM role 執行；這個 role 的權限決定 runbook 能做什麼，應該依 least privilege 設計。第二，`aws:approve` 讓「破壞性步驟前需要人看一眼」成為流程的一部分，而不是靠口頭約定。第三，每次執行的每個步驟、輸入輸出、核准者都會被記錄，事後檢討時可以完整重建事故處理過程。

AWS 也提供大量現成 runbook，例如 `AWS-RestartEC2Instance`、`AWS-StopEC2Instance`、`AWS-CreateSnapshot`，以及給 Config remediation 用的 `AWSConfigRemediation-*` 系列。能用現成的就不要自己寫。

### Automation 的規模控制

Automation 也支援 rate control：對一個 tag 或 resource group 的多個目標執行時，可以設定同時執行數量與錯誤門檻。更進一步，它能**跨帳號、跨 Region** 執行（38.14 節）。

有了 runbook，下一步自然是：不要等人來按執行，讓事件自己觸發它。

## 38.8 事件驅動修復：偵測、判斷、修復、通知

### 三種控制：預防、偵測、矯正

先釐清修復在整個治理體系裡的位置：

| 控制類型 | 什麼時候作用 | AWS 工具例子 |
|---|---|---|
| **Preventive（預防）** | 錯誤發生前就擋下 | SCP、IAM policy、S3 Block Public Access、CloudFormation Hooks |
| **Detective（偵測）** | 發生後發現並告警 | AWS Config rules、Security Hub、GuardDuty |
| **Corrective（矯正）** | 發現後自動或半自動修正 | Config remediation、EventBridge + Lambda／Automation |

最理想的順序是：**能預防就預防**（例如在帳號層級開啟 S3 Block Public Access，讓公開 bucket 根本建不出來）；預防做不到或必須保留彈性的，再用偵測加矯正補上。考試常有一個陷阱：選項提供精美的事件驅動修復架構，但其實一條 SCP 或帳號層級設定就能從源頭阻止，後者才是 MOST effective 的答案。

### 事件從哪裡來

**Amazon EventBridge**（第 32 章）是 AWS 的事件匯流排。和修復相關的事件來源有三類：

1. **AWS 服務事件**：服務本身發出的狀態變化，例如 EC2 instance 狀態變更、GuardDuty finding、AWS Health 事件、Config 合規狀態變化。
2. **API 呼叫事件**：CloudTrail 記錄的 API 呼叫會以 `AWS API Call via CloudTrail` 的 detail-type 送到 EventBridge，例如有人呼叫 `AuthorizeSecurityGroupIngress` 或 `PutBucketPolicy`。前提是帳號中要有一個**啟用 logging 的 CloudTrail trail**；寫入類（會修改資源）的管理事件在預設的 rule 狀態就能比對。查詢類（Get／List／Describe）的唯讀事件則預設不會觸發規則，必須把 rule 狀態設為 `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` 才會比對。這類事件只送到 default event bus。
3. **排程**：EventBridge Scheduler 或排程規則，定時觸發檢查。

### 事件驅動修復的流程

```text
① 事件發生                      ② 比對規則                ③ 執行修復
[有人開放 SG 0.0.0.0/0:22] ──► [EventBridge rule]  ──►  [Lambda 或 SSM Automation]
  CloudTrail: Authorize...        event pattern 比對          │ 先檢查例外 tag、
                                   source / eventName          │ 再移除違規規則（冪等）
                                        │                      ▼
                                        │ target 失敗       ④ 通知與記錄
                                        └──► retry ──► DLQ   [SNS / Chat / OpsItem]
                                                               │
                                                     ⑤ 回頭修根因：IaC、SCP、教育
```

① 違規動作透過 CloudTrail 進入 EventBridge。② 規則用 event pattern 篩選出關心的事件。③ Target 執行修復；修復程式要**冪等**（idempotent），同一個事件被投遞兩次也不會造成錯誤，因為 EventBridge 的投遞是 at-least-once。④ 修復結果要通知負責的人並留下紀錄；EventBridge target 失敗時依 retry policy 重試，最後仍失敗的事件送進 **DLQ**（SQS dead-letter queue），避免修復默默消失。⑤ 最重要的一步常被忽略：如果違規是某條 pipeline 或某份 template 造成的，不修源頭，自動修復與 pipeline 會一直互相覆蓋。

對應的 EventBridge rule event pattern：

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["ec2.amazonaws.com"],
    "eventName": ["AuthorizeSecurityGroupIngress", "ModifySecurityGroupRules"]
  }
}
```

其他常見組合：

| 事件 | 修復動作 |
|---|---|
| GuardDuty finding：EC2 疑似與挖礦網域通訊 | Lambda 把 instance 換到「隔離用」security group、建立 EBS snapshot 留證、通知資安 |
| EC2 instance 狀態變成 `stopped`（非預期） | 通知 owner、建立 OpsItem |
| IAM access key 在公開 repo 被偵測（AWS Health 的 risk 事件） | Automation 停用 key、通知 |
| 新建立的 EBS volume 沒有加密 | 通知並建立 OpsItem；更好的做法是開啟帳號層級的 EBS 預設加密（預防） |

### AWS Config remediation：讓「不合規」自己變回合規

**AWS Config**（第 16 章）持續記錄資源設定，並用 **Config rules** 評估是否合規。Rule 的觸發方式有兩種：**configuration changes**（相關資源設定改變時評估）與 **periodic**（每隔 1、3、6、12、24 小時評估一次）。

當 rule 判定某資源 NON_COMPLIANT，可以設定 **remediation action**，以一份 SSM Automation runbook 修正它：

- **Manual remediation**：在 console 上由人按下「Remediate」執行。適合影響大、需要判斷的修正。
- **Automatic remediation**：一旦判定不合規就自動執行，可設定**最多自動重試次數**與重試間隔。

```yaml
Resources:
  S3NoPublicReadRemediation:
    Type: AWS::Config::RemediationConfiguration
    Properties:
      ConfigRuleName: s3-bucket-public-read-prohibited
      TargetType: SSM_DOCUMENT
      TargetId: AWS-DisableS3BucketPublicReadWrite
      Automatic: true
      MaximumAutomaticAttempts: 3
      RetryAttemptSeconds: 60
      Parameters:
        AutomationAssumeRole:
          StaticValue:
            Values:
              - arn:aws:iam::111122223333:role/ConfigRemediationRole
        S3BucketName:
          ResourceValue:
            Value: RESOURCE_ID
```

`ResourceValue: RESOURCE_ID` 代表把「被判定不合規的資源 ID」當作參數傳給 runbook，這是 Config remediation 和一般 Automation 執行最大的差別：你不需要自己寫程式找出是哪個 bucket。

> [!warning] 常見誤解
> 「Config rule 偵測到不合規就會自己修好。」Config rule 只負責**評估與記錄**，修正需要另外設定 remediation action；沒有設定時，資源會一直維持 NON_COMPLIANT。另一個誤解是「Config 會阻止違規變更」：Config 是事後偵測，不是預防；要在變更發生前擋下，用 SCP、IAM 或 CloudFormation Hooks／Control Tower 的 proactive controls（第 14 章）。

### 選 Config remediation 還是 EventBridge + Lambda？

| 情境 | 較適合 |
|---|---|
| 「資源設定應該符合某規則」，需要持續評估與合規報告 | Config rule + remediation |
| 對某個**動作**（API 呼叫）或**服務事件**（GuardDuty finding、Health 事件）立即反應 | EventBridge rule + Lambda 或 Automation |
| 修正邏輯簡單、有現成 runbook | Automation runbook（不用維護程式碼） |
| 修正需要複雜邏輯、呼叫外部系統 | Lambda，或 Automation 中的 `aws:executeScript` |
| 修正有風險，需要人確認 | Config manual remediation，或含 `aws:approve` 的 runbook |

### 修復迴圈與例外管理

自動修復最常見的事故是**修復迴圈**：pipeline 每次部署都加回一條違規的 security group 規則，自動修復每次都把它刪掉，兩邊無限拉鋸，而應用程式在這段期間時好時壞。避免方式：

- 修復時同時通知資源 owner，並把違規來源（哪個 IAM 主體、哪個 pipeline）寫進通知。
- 從源頭修正：改 IaC template、加上 pipeline 中的靜態檢查（例如 cfn-guard）、用 SCP 禁止該動作。
- 對**已核准的例外**用明確的機制排除，例如在 rule 的範圍中排除帶有核准 tag 的資源，並讓例外有到期日；不要靠「先把自動修復關掉」來處理例外。

## 38.9 AWS Health、Trusted Advisor 與 OpsCenter：讓訊號匯集到一處

### AWS Health：AWS 那邊發生了什麼

**AWS Health** 提供和你帳號相關的 AWS 事件：服務故障、會影響你資源的排定維護（例如 EC2 底層硬體的 **scheduled retirement**，instance 會在指定日期被停止）、安全通知（例如 access key 疑似外洩）、帳號事項。**AWS Health Dashboard** 分成兩部分：公開的服務健康狀態，以及只針對你帳號資源的個人化事件。

Health 事件會送到 EventBridge（source 為 `aws.health`），這讓「AWS 通知我某台 instance 兩週後要退役」可以直接觸發自動化：

```json
{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": {
    "service": ["EC2"],
    "eventTypeCategory": ["scheduledChange"]
  }
}
```

Target 可以是一份 Automation runbook，在維護時段把該 instance stop 再 start（EBS-backed instance 重新啟動後會落到新的底層主機），或者對 ASG 中的 instance 直接替換。

透過 Organizations 開啟 **organizational view** 後，管理帳號或 delegated administrator 可以看到所有成員帳號的 Health 事件。以程式查詢 **AWS Health API** 需要 Business 等級以上的 Support 方案；透過 EventBridge 接收事件則所有帳號都可以。

### Trusted Advisor：AWS 幫你做的定期健檢

**AWS Trusted Advisor** 依 AWS 最佳實務檢查你的帳號，分為幾個類別：**cost optimization**（閒置資源、低使用率 instance）、**performance**、**security**（開放的 security group port、root 未啟用 MFA、公開的 snapshot）、**fault tolerance**（單一 AZ 部署、沒有備份）、**service limits**（接近 quota 上限）、**operational excellence**。

可用的檢查範圍取決於 Support 方案：Basic（與 Developer）方案可以看到 service limits 類別的全部檢查，以及 security、fault tolerance 類別中的部分檢查，而且 security 檢查要手動重新整理；Business 等級以上可以使用完整檢查、Trusted Advisor API，並能把結果整合進自動化。Enterprise 等級方案另有 **Trusted Advisor Priority**，由 AWS 帳戶團隊挑出最重要的建議。

> [!note] Support 方案現況
> AWS 已調整 Support 方案：新增 Business Support+、Enterprise Support 與 Unified Operations，並宣布 Developer、Business 與 Enterprise On-Ramp 方案將於 2027 年 1 月 1 日停止（既有客戶在此之前可繼續使用）。考試與多數資料仍以「Business 以上才有完整 Trusted Advisor 與 Health API」來描述，本書沿用「Business 等級以上」的說法。

Trusted Advisor 的檢查結果變化也能送到 EventBridge，例如「service limit 檢查變成黃燈」時通知平台團隊申請提高 quota。

### OpsCenter：把待辦的營運問題集中

**OpsCenter** 是 Systems Manager 中彙整營運問題的地方。每個問題是一個 **OpsItem**，可以由 CloudWatch alarm、EventBridge rule、Config 不合規、Security Hub finding 自動建立，也能手動建立。OpsItem 會帶上相關資源、最近的 CloudTrail 事件、Config 變更歷史，並能直接從 OpsItem 執行相關的 Automation runbook。它解決的是「告警在 email、事件在 Slack、修復紀錄在 wiki，沒有人知道哪些問題還沒處理」的分散問題。

> [!note] 服務現況
> AWS 近年調整了 Systems Manager 部分功能的可用性：**Incident Manager**（事故應變計畫、on-call 升級）與 **Change Manager**（變更申請與核准）自 2025 年 11 月 7 日起不再開放給新客戶，既有客戶可以繼續使用；Incident Manager 也不再加入新功能。新設計中，變更核准可以用含 `aws:approve` 的 runbook 或 pipeline 的人工核准階段（第 37 章），事故應變則評估 CloudWatch 的事故調查功能或第三方 on-call 工具。考試舊題若出現這兩個服務，仍需理解它們的定位。

工具都有了。但工具本身不會讓團隊變好；讓營運持續改善的，是使用這些工具的流程。

## 38.10 營運卓越：runbook、playbook、事後檢討與 Well-Architected

### Operational Excellence pillar 的設計原則

Well-Architected Framework 的 **Operational Excellence pillar**（營運卓越支柱）列出幾個設計原則，每一個都能對應到本章的機制：

| 設計原則 | 白話意思 | 本章對應 |
|---|---|---|
| Perform operations as code | 維運動作寫成程式，不靠手動 | SSM document、Automation runbook、IaC |
| Make frequent, small, reversible changes | 小步、可回滾 | rate control、分批 patch、immutable 替換 |
| Refine operations procedures frequently | 程序要經常演練並更新 | 每次事故後更新 runbook |
| Anticipate failure | 預先演練失敗 | game day、FIS（第 34 章） |
| Learn from all operational events | 每次事件都要學到東西 | 事後檢討、行動項目追蹤 |
| Use managed services | 少管理底層 | Session Manager 取代 bastion |
| Implement observability for actionable insights | 可觀測、可行動的告警 | 第 36 章 |

### Runbook 與 playbook

兩個詞常被混用，但用途不同：

- **Runbook（操作手冊）**：為了達成**已知結果**的標準步驟。例如「輪替資料庫憑證」「擴充 EBS volume」「重啟卡住的 worker」。步驟明確，最適合自動化成 Automation runbook。
- **Playbook（應變手冊）**：為了**調查未知問題**的流程。例如「API 錯誤率升高時：先看哪個 dashboard、怎麼判斷是不是最近部署造成、何時升級給誰」。它引導判斷，裡面會引用多份 runbook。

成熟的團隊會讓每一個告警都連到一份 playbook：「這個 alarm 響了，第一步做什麼」。沒有對應 playbook 的告警，往往代表這個告警不夠具體，或根本不需要叫醒人。

### Operational readiness review

新服務上線前做 **operational readiness review（ORR，營運就緒審查）**：用一份檢查清單確認這個服務有 owner、有 SLO 與對應告警、有 dashboard、有 runbook 與 playbook、能回滾、備份與還原已測試、quota 有餘裕。ORR 的問題清單應該來自過去的事故：每次事後檢討找到的缺口，都要變成清單上的一題，讓下一個服務不再重蹈覆轍。

### 事後檢討：讓同一個事故不要發生第三次

Wanderly 的 S3 公開事件發生了三次，因為每次的「改善」都是「下次小心」。有效的 **post-incident analysis（事後檢討）** 有幾個特徵：

1. **Blameless（不責怪個人）**：焦點是「什麼機制讓這個錯誤可能發生」，而不是「誰犯錯」。人一定會犯錯，系統要讓錯誤做不到或很快被發現。
2. **完整時間軸**：從 CloudTrail、Config 歷史、Automation 執行紀錄重建「什麼時候發生、什麼時候發現、什麼時候修好」，算出偵測時間與修復時間。
3. **追問根因**：例如用「5 個為什麼」：bucket 為什麼公開？測試需要。為什麼測試能把它改成公開？帳號沒有開 Block Public Access。為什麼沒開？帳號是手動建立的，沒有 baseline。
4. **具體、有 owner、有期限的行動項目**：「在 organization 所有帳號開啟 S3 Block Public Access（預防）」「Config rule 加 automatic remediation（矯正）」「新帳號 baseline 自動化（第 40 章）」，而不是「加強宣導」。
5. **追蹤到完成**：行動項目進入團隊的待辦清單，定期檢查完成率。

### AWS Well-Architected Tool

**AWS Well-Architected Tool** 是 console 中免費的架構審查工具，用來對一個 workload 回答 Well-Architected Framework 的問題並找出風險：

- **Workload**：審查的對象（例如「Wanderly 訂房系統 production」）。
- **Lens**：問題集。預設是 Well-Architected Framework lens；另有 Serverless、SaaS 等官方 lens，以及企業自訂的 **custom lens**（例如把公司的 ORR 清單做成 lens）。
- **High／medium risk issues（HRI／MRI）**：依回答自動判定的風險，並產生 **improvement plan**（改善計畫），列出建議與參考資料。
- **Milestone**：在某個時間點保存審查結果的快照，用來比較「三個月前有 12 個 HRI，現在剩 4 個」。
- **Sharing**：把 workload 分享給其他帳號或整個 Organization，讓架構團隊集中檢視；**review templates** 與 **profiles** 幫助大規模、一致地進行審查。
- 可整合 Trusted Advisor，在回答問題時看到相關檢查結果。

持續改善的節奏可以是：每季對核心 workload 做一次 Well-Architected review，存成 milestone；HRI 轉成行動項目；下一季比較 milestone 看改善程度。

> [!tip] 考試提示
> 題目問「如何系統性地找出架構在五／六大面向的風險並追蹤改善」→ Well-Architected Tool（workload、lens、milestone、improvement plan）。問「自動檢查帳號中閒置資源、開放的 port、接近上限的 quota」→ Trusted Advisor。問「AWS 排定維護會影響我的 instance，怎麼自動處理」→ AWS Health 事件 + EventBridge + Automation。

## 38.12 比較與選型

### Systems Manager 功能對照

| 功能 | 一句話 | 觸發方式 | 典型用途 |
|---|---|---|---|
| Session Manager | 免 port 的互動式登入 | 人員發起 | 取代 bastion、port forwarding 到 RDS |
| Run Command | 立即對一群機器執行指令 | 人員或程式發起，一次性 | 緊急重啟服務、收集診斷資料 |
| State Manager | 持續維持期望狀態 | 排程反覆套用 | 確保 agent 已安裝、設定不漂移 |
| Maintenance Windows | 在時段內執行工作 | 排程時段 | 分批 patch、例行維護 |
| Patch Manager | 定義、安裝、回報 patch | 透過 Maintenance Window／patch policy | OS 修補與合規報告 |
| Automation | 多步驟流程，主要呼叫 AWS API | 人員、EventBridge、Config、排程 | 事故處理、remediation、AMI 建立 |
| Inventory | 收集機器上的軟體與設定 | State Manager association | 漏洞影響範圍查詢 |
| Parameter Store | 階層式設定與 SecureString | 程式讀取 | 設定值集中 |
| Fleet Manager | 節點管理介面 | 人員 | 排除 agent 問題、檢視檔案與效能 |
| OpsCenter | 營運問題彙整 | 告警、事件自動建立 | 追蹤待處理問題 |

### 遠端存取方式

| 方式 | Inbound port | 憑證 | Session 內容紀錄 | 營運負擔 |
|---|---|---|---|---|
| Bastion + SSH | 需要（22） | SSH key | 自行處理 | 高（要管 bastion） |
| Session Manager | 不需要 | IAM | 支援（shell session） | 低 |
| EC2 Instance Connect Endpoint | 不需要對外開放 | IAM + 暫時 SSH key | 不提供 session 內容 | 低 |

### 選型決策

```text
要對機器或資源做什麼？
├─ 人員要互動式登入 → Session Manager（需要原生 SSH 且不需錄製內容 → 也可用 EC2 Instance Connect Endpoint）
├─ 一次性對一群機器執行 → Run Command（設定 rate control）
├─ 持續確保某個狀態 → State Manager association
├─ 定期在特定時段執行 → Maintenance Window（patch 用 Patch Manager／patch policy）
├─ 多步驟、呼叫 AWS API、可能需要核准 → Automation runbook
└─ 對事件自動反應
     ├─ 「資源設定不合規」→ Config rule + remediation（manual 或 automatic）
     └─ 「某個動作或服務事件發生」→ EventBridge rule → Lambda／Automation
   （無論哪一種，先問：能不能用 SCP、Block Public Access 等預防控制從源頭擋掉？）
```

## 38.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 不開放 inbound port、不使用 bastion、稽核所有登入 | Session Manager + CloudTrail + session logging 到 S3／CloudWatch Logs |
| Instance 不出現在 Systems Manager、private subnet 無 NAT | 檢查 agent、instance profile（`AmazonSSMManagedInstanceCore`）、`ssm`／`ssmmessages`／`ec2messages` interface endpoints |
| 對數百台機器執行指令並控制失敗擴散 | Run Command + tag targets + max-concurrency／max-errors |
| 確保所有（含新建）instance 持續安裝某 agent | State Manager association |
| 每週固定時段 patch、需要合規報告 | Patch Manager（baseline、Scan／Install）+ Maintenance Window 或 patch policy |
| 整個 Organization 統一 patch | Quick Setup patch policy（指定 OU／Region） |
| 找出所有裝了某版本軟體的機器（跨帳號） | Inventory + resource data sync 到 S3 + Athena |
| 不合規資源自動修正 | Config rule + automatic remediation（SSM Automation） |
| 有人修改 security group 就立即反應 | EventBridge（CloudTrail API 事件）→ Lambda／Automation |
| 破壞性修復前需要人確認 | Automation runbook 的 `aws:approve`，或 Config manual remediation |
| AWS 排定維護、instance scheduled retirement | AWS Health 事件 → EventBridge → Automation |
| 自動找出閒置資源、開放 port、接近 quota | Trusted Advisor（完整檢查需 Business 以上 Support） |
| 系統性審查架構風險並追蹤改善 | Well-Architected Tool（lens、HRI、milestone、improvement plan） |
| 地端伺服器也要用同一套工具管理 | Hybrid activation（`mi-` 節點）；Session Manager 需 advanced-instances tier |

**常見陷阱**：

1. 以為 Session Manager 需要開放 22 或 443 inbound：agent 是主動連出，security group 不需要任何 inbound 規則。
2. 以為 Config rule 會自動修正或能事前阻止：它只評估；修正要設定 remediation，阻止要用 SCP 等預防控制。
3. 用事件驅動修復處理一個可以直接預防的問題：例如 S3 公開，帳號層級 Block Public Access 比「偵測後關閉」更好。
4. 對 ASG 中的無狀態 instance 做 in-place patch：instance 被替換後 patch 就消失，正解是更新 AMI 並 instance refresh。
5. 自動修復沒有冪等與 DLQ：重複投遞時出錯、失敗時默默消失。
6. 混淆 Trusted Advisor（帳號最佳實務檢查）、Well-Architected Tool（workload 架構審查問卷）、AWS Health（AWS 端事件）與 Compute Optimizer（rightsizing 建議，第 39 章）。

## 38.14 SAP 加深：多帳號、多 Region 的營運自動化

SAA 關心「一個帳號裡怎麼自動化」，SAP 關心「80 個帳號、4 個 Region、還有地端機房時，怎麼讓營運一致又不失控」。

### 集中但分權的 Systems Manager

- **Quick Setup 與 Organizations 整合**：從管理帳號或 delegated administrator，一次對指定 OU 與 Region 部署 patch policy、host management（agent 更新、inventory 收集、DHMC）等設定，新加入 OU 的帳號自動套用。
- **Automation 多帳號多 Region 執行**：在中央帳號啟動一次 Automation，就能對多個帳號、多個 Region 的目標執行，並設定同時執行的帳號／Region 數量與錯誤門檻。中央帳號需要 `AWS-SystemsManager-AutomationAdministrationRole`，每個目標帳號需要 `AWS-SystemsManager-AutomationExecutionRole`，並在 trust policy 中信任中央帳號。這和第 13 章的跨帳號 AssumeRole 是同一套原理。
- **跨帳號 inventory 與合規**：resource data sync 把各帳號的 inventory 與 compliance 資料匯入集中的 S3，搭配 Athena 與 QuickSight 做全公司的 patch 合規儀表板。
- **Explorer**：Systems Manager 中彙整多帳號 OpsData（OpsItem、patch 合規、inventory 摘要）的儀表板。

### 組織層級的 Config 與修復

- 用 delegated administrator 部署 **organization Config rules** 與 **conformance packs**（包含一組 rule 與 remediation 的套件，第 16、43 章），並用 **aggregator** 集中檢視所有帳號、Region 的合規狀態。
- 修復的「權限邊界」要設計清楚：中央安全團隊擁有低風險、可自動的修正（例如關閉公開存取）；會影響可用性的修正（例如刪除資源、替換資料庫）只建立 OpsItem 並通知該帳號的 owner，由他們以 manual remediation 處理。
- 例外要可治理：例外清單有 owner、理由與到期日，例如以 tag 標記並在 rule 範圍中排除，到期後自動恢復評估。

### 混合環境

遷移期間（第 44–45 章），地端 VM 用 hybrid activation 納入 Systems Manager，與 EC2 共用同一套 patch baseline、inventory 與 Session Manager；遷移完成後，同一份 runbook 不需要改寫。對需要經 Direct Connect 私有連線管理地端機器的情況，可以讓地端透過 VPC interface endpoint 存取 Systems Manager，而不是走 Internet。

### 持續改善的組織機制

- 以 custom lens 把公司的架構標準與 ORR 清單放進 Well-Architected Tool，透過 Organization 分享，讓所有團隊用同一套問題自我審查，架構團隊集中檢視 HRI 分布。
- 把事後檢討的行動項目分成「預防」「偵測」「矯正」三類並追蹤完成率；SAP 題目在 Domain 3（Continuous Improvement）常要求你選出「能防止同類問題再次發生」的選項，而不是只修好這一次的選項。

## 本章重點整理

- Systems Manager 管理機器的前提是 managed node：SSM Agent、IAM 權限（instance profile 或 DHMC）、能以 HTTPS 主動連出到 `ssm`、`ssmmessages`、`ec2messages` 的網路路徑。
- Private subnet 沒有 NAT 時，必須為 Systems Manager 建立 interface VPC endpoints 並開啟 VPC DNS 屬性，機器才會成為 managed node。
- Session Manager 以 IAM 授權、不需要 inbound port、SSH key 或 bastion，`StartSession` 被 CloudTrail 記錄，session 內容可記錄到 S3 或 CloudWatch Logs；port forwarding 與 SSH 型 session 的內容不會被記錄。
- Run Command 是一次性的批次執行，用 tag 選目標並以 max-concurrency 與 max-errors 控制影響範圍。
- State Manager 用 association 持續維持期望狀態，新加入的符合條件機器也會自動套用。
- Patch Manager 以 patch baseline 決定核准的 patch，`AWS-RunPatchBaseline` 的 Scan 產生合規報告、Install 執行安裝；Maintenance Window 控制時段與分批，patch policy 可一次套用到整個 Organization。
- ASG 後的無狀態機器優先用新 AMI 加 instance refresh 的 immutable 方式更新，而不是 in-place patch。
- Automation runbook 把多步驟操作寫成程式，可呼叫 AWS API、在機器上執行指令、等待條件、分支，並以 `aws:approve` 加入人工核准。
- 治理控制依序是預防（SCP、Block Public Access）、偵測（Config、GuardDuty）、矯正（remediation）；能預防的問題不應只靠事後修復。
- Config rule 只評估合規，要搭配 remediation action（SSM Automation，可 manual 或 automatic）才會修正，且無法事前阻止變更。
- EventBridge 可接收 AWS 服務事件、CloudTrail API 事件與 AWS Health 事件，觸發 Lambda 或 Automation；修復程式要冪等並設定 retry 與 DLQ。
- 修復迴圈要從源頭（IaC、pipeline、SCP）解決，已核准的例外要有明確、會到期的排除機制。
- Trusted Advisor 做帳號最佳實務檢查（完整檢查與 API 需 Business 以上 Support），AWS Health 提供影響你資源的 AWS 事件，Well-Architected Tool 以 lens、HRI、milestone 追蹤 workload 的架構改善。
- Runbook 處理已知步驟、適合自動化；playbook 引導調查未知問題；事後檢討要 blameless、有時間軸、有具體且被追蹤的行動項目。

## 本章練習題

### 練習 38-1｜SAA｜單選｜取代 bastion host

Wanderly 的工程師目前透過 public subnet 中的 bastion host，以共用的 SSH key 登入 private subnet 的 EC2。資安團隊要求：不得有任何對 Internet 開放的 inbound port、不得使用長期共用的金鑰、必須記錄誰在何時登入哪台機器以及執行了哪些指令。團隊希望營運負擔最低。

哪個做法最符合需求？

- A. 保留 bastion host，但把 security group 的 22 port 限制為公司辦公室 IP，並為每位工程師發放個人 SSH key
- B. 移除 bastion，為 instance 掛上含 `AmazonSSMManagedInstanceCore` 的 instance profile，使用 Session Manager 登入，並設定 session logging 到 S3 與 CloudWatch Logs
- C. 為每台 private instance 配置 Elastic IP，並使用 EC2 Instance Connect 從 Internet 直接連入
- D. 建立 Client VPN，讓工程師連上 VPN 後再用共用 SSH key 登入 instance

> [!answer]- 答案：B
> **A ✗** 限制來源 IP 與個人金鑰改善了一部分，但 22 port 仍對外開放，bastion 也要自行維護；指令紀錄仍要自己想辦法收集。
>
> **B ✓** Session Manager 由 agent 主動連出建立通道，security group 不需要任何 inbound 規則；登入以 IAM 授權，不需要 SSH key；`StartSession` 由 CloudTrail 記錄，shell session 的內容可以記錄到 S3 與 CloudWatch Logs。沒有 bastion 要維護，營運負擔最低。
>
> **C ✗** 給 private instance 配 public IP 並從 Internet 連入，直接違反「不得有對 Internet 開放的 inbound port」。
>
> **D ✗** Client VPN 解決了網路入口，但仍使用共用 SSH key，也沒有提供指令層級的紀錄。
>
> **考點**：SAA-1.1、SAA-1.2｜Session Manager 取代 bastion

### 練習 38-2｜SAA｜單選｜Managed node 不出現

Wanderly 在一個 isolated subnet（沒有 NAT Gateway、沒有 Internet Gateway route）中啟動了幾台 Amazon Linux 2023 instance，並掛上含 `AmazonSSMManagedInstanceCore` 的 instance profile。這些 instance 在 Fleet Manager 中一直沒有出現，也無法開 Session Manager session。VPC 的 `enableDnsSupport` 與 `enableDnsHostnames` 都已開啟。

最可能需要補上的設定是什麼？

- A. 在 instance 的 security group 加入允許來自 Systems Manager 服務的 inbound 443 規則
- B. 在 instance 上手動安裝 SSM Agent，因為 Amazon Linux 2023 AMI 沒有預先安裝
- C. 在 VPC 中為 `ssm`、`ssmmessages`、`ec2messages` 建立 interface VPC endpoint，並讓 endpoint 的 security group 允許來自 instance 的 443
- D. 建立 S3 gateway endpoint，因為 Systems Manager 的控制通道經由 S3 傳遞

> [!answer]- 答案：C
> **A ✗** Systems Manager 不會主動連進 instance；是 agent 主動連出。加 inbound 規則沒有幫助。
>
> **B ✗** Amazon Linux 2023 的官方 AMI 已預先安裝 SSM Agent。若是自訂 AMI 才需要確認。
>
> **C ✓** Agent 需要以 HTTPS 連到 Systems Manager 的 endpoint。在沒有任何對外路徑的 subnet，必須建立這三個 interface endpoint，並讓 endpoint 的 security group 允許來自 instance 的 443；DNS 屬性已開啟，private DNS 就會把服務名稱解析到 endpoint。
>
> **D ✗** S3 gateway endpoint 只在需要存取 S3 時有用（例如把 session log 或 Run Command 輸出寫到 S3），它不能取代 Systems Manager 本身的 endpoint。
>
> **考點**：SAA-1.2、SAA-3.4｜managed node 的網路路徑與 interface endpoints

### 練習 38-3｜SAA｜單選｜排程 patch 與合規報告

Wanderly 有 80 台位於兩個 AZ 的 Linux instance。稽核要求每週提供所有 instance 缺少哪些安全性 patch 的報告；安全性 patch 必須在發布 7 天後安裝，安裝只能在每週二凌晨 2 點到 5 點之間進行，且同一時間不能有超過 25% 的 instance 重開機。

哪個做法最合適？

- A. 建立 custom patch baseline，設定安全性分類 7 天後自動核准；每天以 `AWS-RunPatchBaseline` Scan 更新合規報告，並建立週二 02:00–05:00 的 Maintenance Window，以 Install 搭配 25% max-concurrency 執行
- B. 在每台 instance 的 cron 中加入 `yum update --security`，並設定每週二凌晨 2 點執行
- C. 使用 Run Command 在每週二手動對所有 instance 執行 `AWS-RunPatchBaseline` Install，max-concurrency 設為 100% 以縮短時間
- D. 建立 AWS Config rule 檢查 instance 的 patch 狀態，並以 automatic remediation 在偵測到缺少 patch 時立即安裝

> [!answer]- 答案：A
> **A ✓** Patch baseline 的 auto-approval delay 滿足「發布 7 天後」；Scan 產生每台機器的合規狀態供稽核；Maintenance Window 限制時段，task 的 max-concurrency 25% 控制同時重開機的比例。這是 Patch Manager 的標準組合。
>
> **B ✗** 各機器自行 cron 無法集中產生合規報告、無法控制同時重開機的比例，也沒有 7 天延遲核准的機制。
>
> **C ✗** 手動執行不符合排程要求；100% 同時執行會讓所有機器一起重開機，違反 25% 的限制。
>
> **D ✗** 偵測到缺少 patch 就立即安裝，無法限制在指定時段，也無法控制分批重開機。
>
> **考點**：SAA-2.2｜Patch baseline、Scan／Install 與 Maintenance Window

### 練習 38-4｜SAA｜選兩項｜Session 稽核

金融合作夥伴要求 Wanderly 證明：所有對 production instance 的互動式存取都能追溯到個人，而且能重現 session 中執行的指令。Wanderly 已全面改用 Session Manager。

哪兩個設定能滿足需求？（選兩項）

- A. 在 IAM 中允許工程師使用 `AWS-StartSSHSession` document，讓他們用熟悉的 SSH 用戶端連線
- B. 確保 CloudTrail 記錄 Systems Manager 的 API 活動，以追蹤每次 `StartSession` 的呼叫者、時間與目標 instance
- C. 為 instance 的 security group 開放 22 port 給 Session Manager 服務 IP 範圍
- D. 在 Session Manager preferences 中啟用 session logging 到 S3 或 CloudWatch Logs，並限制工程師只能使用標準 shell session
- E. 在每台 instance 上安裝 CloudWatch agent 收集 `/var/log/secure`，取代 Session Manager 的紀錄

> [!answer]- 答案：B、D
> **A ✗** 經由 Session Manager 的 SSH 與 port forwarding session 內容是使用者端加密的資料流，Session Manager 不會記錄其中的指令，反而破壞「重現指令」的要求。
>
> **B ✓** CloudTrail 記錄 `StartSession` 等 API 呼叫，包含 IAM 身份、時間與目標，滿足「追溯到個人」。
>
> **C ✗** Session Manager 不需要任何 inbound port；開放 22 只會增加攻擊面。
>
> **D ✓** Session logging 會保存 shell session 的輸入與輸出；搭配 IAM 只允許標準 shell session，才能確保所有 session 都有內容紀錄。
>
> **E ✗** `/var/log/secure` 記錄的是 OS 層登入事件，無法記錄 session 中執行的每個指令，也無法對應到 IAM 身份。
>
> **考點**：SAA-1.1、SAA-1.2｜Session Manager logging 與 CloudTrail

### 練習 38-5｜SAA｜單選｜不合規資源自動修正

>
> **C ✗** Trusted Advisor 只提供檢查結果，不會自動修正，週檢視也太慢。
>
> **D ✓** Config rule 在 bucket 設定變更時評估，不合規時 automatic remediation 以現成的 runbook 修正，並保留合規歷史。不需要撰寫程式碼。若公司其實不需要允許任何公開設定，帳號層級的 Block Public Access 是更強的預防手段。

### 練習 38-6｜SAA｜單選｜對 API 呼叫即時反應

Wanderly 的帳號已有一個記錄管理事件的 CloudTrail trail。安全團隊要在任何人新增 security group 規則、允許 `0.0.0.0/0` 存取 port 22 時，於一分鐘內自動移除該規則並通知資源 owner。修復程式要能處理同一事件被投遞兩次的情況，且修復失敗時不得默默遺失。

哪個設計最合適？

- A. 建立 EventBridge rule 比對 CloudTrail 的 `AuthorizeSecurityGroupIngress` 事件，target 為冪等的 Lambda 函式，並為 target 設定 retry policy 與 SQS dead-letter queue
- B. 每 24 小時執行一次 periodic Config rule 檢查 security group，並以 manual remediation 處理
- C. 開啟 VPC Flow Logs，用 metric filter 偵測 port 22 的流量後觸發 Lambda
- D. 在 CloudWatch 建立 alarm，監控 EC2 的 `NetworkIn` 指標突增時移除 security group 規則

> [!answer]- 答案：A
> **A ✓** 有啟用的 CloudTrail trail 時，寫入類的 API 呼叫會以 `AWS API Call via CloudTrail` 事件送到 EventBridge，可近即時觸發修復。EventBridge 是 at-least-once 投遞，因此 Lambda 要冪等（規則已不存在時直接成功）；retry policy 與 DLQ 確保最後失敗的事件會被保留、可追查。
>
> **B ✗** 24 小時的 periodic 評估與人工修復都達不到一分鐘內的要求。
>
> **C ✗** Flow Logs 記錄的是流量，不是設定變更；要等到有人實際連線才會發現，而且無法得知是誰新增規則。
>
> **D ✗** `NetworkIn` 與 security group 規則變更沒有直接關係，無法可靠偵測。
>
> **考點**：SAA-1.2、SAA-2.1｜EventBridge 事件驅動修復、冪等與 DLQ

### 練習 38-13｜SAP｜選兩項｜修復迴圈

Wanderly 的安全團隊部署了 automatic remediation：只要 security group 允許 `0.0.0.0/0` 的 port 22，就移除該規則。之後發現某個應用團隊的 CI/CD pipeline 每次部署都透過 CloudFormation 加回這條規則，兩邊每天互相覆蓋數十次，CloudFormation stack 也開始出現 drift。另外，有一個供應商的設備在合約到期前（下個月底）確實需要從固定 IP 範圍連入 port 22，已獲資安核准。

哪兩個改善最合適？（選兩項）

- C. 把 remediation 改為刪除整個 security group，讓 pipeline 無法再加回規則

> [!answer]- 答案：A、E
> **A ✓** 迴圈的根因是 template 本身違規。從源頭修正並在 pipeline 加入 policy-as-code 檢查，屬於預防控制，能阻止同類問題再次發生，也消除 drift。
>
> **B ✗** 停用自動修復會讓其他帳號的違規設定長期存在，等於移除了矯正控制。
>
> **C ✗** 刪除整個 security group 會中斷正常服務，修復本身成了事故。
>
> **D ✗** 加快修復頻率只會讓拉鋸更激烈，沒有處理根因。
>
> **E ✓** 已核准的例外需要明確、可稽核且會到期的排除方式；把來源限縮到供應商 IP，例外本身也就不再是 `0.0.0.0/0`。
>
> **考點**：SAP-3.1、SAP-3.2｜修復迴圈、源頭修正與例外治理

### 練習 38-14｜SAP｜單選｜多帳號多 Region 執行 runbook

Wanderly 的安全團隊要在 50 個帳號、3 個 Region 中，對所有帶有 `Exposure=public` tag 的 EC2 執行同一份 Automation runbook（建立 snapshot 並更換 security group）。團隊希望從中央安全帳號啟動一次就完成，並控制同時處理的帳號數量，避免錯誤擴散。

哪個做法最合適？

- A. 在每個帳號建立 EventBridge Scheduler，各自在同一時間執行 runbook
- B. 從中央帳號以 AWS CLI 迴圈 assume 每個帳號的 `OrganizationAccountAccessRole`，逐一執行 `ec2` API
- C. 把 runbook 複製到每個帳號，由各帳號的管理員手動執行
- D. 在中央帳號設定 `AWS-SystemsManager-AutomationAdministrationRole`，在每個目標帳號建立信任中央帳號的 `AWS-SystemsManager-AutomationExecutionRole`，再以多帳號多 Region Automation 執行，並設定同時執行與錯誤門檻

> [!answer]- 答案：D
> **A ✗** 各帳號各自排程無法集中控制速率與錯誤門檻，也無法在一處看到整體結果。
>
> **B ✗** 自寫迴圈可以運作，但要自行處理重試、錯誤門檻、紀錄與跨 Region；使用權限很大的 `OrganizationAccountAccessRole` 也不符合 least privilege。
>
> **C ✗** 手動執行無法規模化，也無法確保一致。
>
> **D ✓** Automation 原生支援多帳號、多 Region 執行：中央帳號的 administration role assume 各帳號的 execution role，依 target 參數（例如 tag）找出資源，並可設定同時執行的帳號／Region 數與錯誤門檻，所有結果集中在中央帳號。
>
> **考點**：SAP-1.4、SAP-3.2｜Automation 多帳號多 Region 執行

### 練習 38-15｜SAP｜單選｜遷移期間的地端伺服器管理

Wanderly 併購的旅行社還有 300 台地端 VM，預計 12 個月內分批遷移到 AWS。資安要求遷移期間地端 VM 必須和 EC2 使用相同的 patch baseline 與合規報告，工程師也要能以 IAM 授權、不開 inbound port 的方式登入地端 VM 並記錄 session。地端已透過 Direct Connect 連到 AWS。

哪個做法最合適？

- A. 以 hybrid activation 把地端 VM 註冊為 managed node，將帳號的節點層級設為 advanced-instances tier 以使用 Session Manager，並透過 VPC interface endpoint 經 Direct Connect 存取 Systems Manager
- B. 先把所有 VM 用 AWS Application Migration Service 複寫到 AWS，在遷移完成前不納入管理
- C. 在地端繼續使用既有的 patch 工具，只要求每月匯出報告上傳到 S3
- D. 在地端架設 bastion host，透過 Direct Connect 讓工程師從 VPC 內 SSH 到地端 VM

> [!answer]- 答案：A
> **A ✓** Hybrid activation 讓地端 VM 以 `mi-` 節點加入 Systems Manager，共用相同的 patch baseline、patch policy 與合規報告；對地端節點使用 Session Manager 需要 advanced-instances tier；經 Direct Connect 存取 interface endpoint，管理流量不必走 Internet。
>
> **B ✗** 遷移需要 12 個月，期間不納入管理違反資安要求；複寫也不等於 patch 與存取控制。
>
> **C ✗** 兩套工具無法提供一致的 baseline 與合規報告，也沒有解決以 IAM 授權登入的需求。
>
> **D ✗** Bastion 加 SSH 依賴金鑰，不是 IAM 授權，也沒有內建 session 紀錄。
>
> **考點**：SAP-4.2、SAP-1.4｜hybrid activation 與混合環境營運

### 練習 38-16｜SAP｜單選｜持續改善機制

Wanderly 的架構團隊希望各產品團隊每季自我審查 workload 的架構風險，使用公司自訂的上線標準（包含 ORR 檢查清單），並讓架構團隊能集中看到各團隊的高風險項目，比較每季的改善程度。

哪個做法最合適？

- A. 開啟 Trusted Advisor 的所有檢查，並把結果每季寄給各團隊
- B. 在 AWS Config 部署 conformance pack，以合規分數代表架構成熟度
- C. 請各團隊每季填寫共用試算表，由架構團隊人工彙整
- D. 在 Well-Architected Tool 建立公司的 custom lens 並透過 Organization 分享；各團隊對 workload 套用該 lens 審查，每季保存 milestone，架構團隊集中檢視各 workload 的 HRI 與 improvement plan

> [!answer]- 答案：D
> **A ✗** Trusted Advisor 是自動化的帳號檢查，無法表達公司自訂的上線標準，也不是以 workload 為單位的審查。
>
> **B ✗** Conformance pack 評估的是資源設定，無法涵蓋 ORR 中的流程問題（例如有沒有 runbook、有沒有 owner）。
>
> **C ✗** 試算表可以運作，但無法提供風險自動判定、milestone 比較與集中檢視。
>
> **D ✓** Custom lens 把公司標準變成審查問卷，Organization 分享讓所有團隊使用同一套問題；milestone 保存每季的結果以比較改善程度，HRI 與 improvement plan 讓架構團隊集中追蹤風險。
>
> **考點**：SAP-3.1｜Well-Architected Tool custom lens 與 milestone
