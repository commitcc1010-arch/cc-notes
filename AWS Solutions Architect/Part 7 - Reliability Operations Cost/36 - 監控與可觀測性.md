## 36.1 故事：客服比工程師先知道網站壞了

Wanderly 的架構在前幾章一路長大：CloudFront 後面是 ALB，ALB 後面是跑在 ECS 的訂房服務，訂單寫進 Aurora，付款流程經過 SQS 與 Step Functions。系統上線後的第三個週六晚上，客服主管在群組裡貼了一張截圖：「已經有 40 位客人說付款完成後畫面一直轉圈，是怎麼回事？」

值班工程師小林打開 AWS console，看到 EC2 與 ECS 的 CPU 都在 30% 左右，ALB 也沒有大量 5xx。所有「看得到的」數字都很正常，但客人就是付不了錢。他花了一個半小時，一台一台登入機器翻日誌，才發現第三方金流 API 回應從平常的 300 毫秒變成 25 秒，訂房服務的連線池被塞滿，請求在排隊而不是失敗，所以 CPU 不高、也沒有錯誤碼。

事後檢討時，技術主管問了三個問題：為什麼是客服先發現，而不是告警？為什麼要一台一台翻日誌？為什麼看不到「一個付款請求到底卡在哪一段」？這三個問題分別對應本章的三個主題：**告警要盯住使用者感受到的結果**、**日誌要集中且能查詢**、**分散式系統需要 tracing**。

這一章跟著小林把 Wanderly 從「出事了才去看」改造成「出事前就知道、出事時三分鐘內定位」。我們先建立觀念：系統會發出哪幾種訊號，然後逐一看 AWS 用哪個服務收集、保存與使用它們。

## 36.2 可觀測性的基本訊號：metrics、logs、traces 與 events

**監控（monitoring）** 是「針對已知會出問題的地方設定檢查」，例如 CPU 超過 80% 就通知。**可觀測性（observability）** 範圍更大，指的是「當出現沒預料到的問題時，能不能只靠系統送出來的資料找出原因」。小林的事故正是後者：沒有人事先想到要監控「金流 API 的延遲」，所以光有傳統監控不夠。

系統會送出四類主要訊號，每類回答不同的問題：

| 訊號 | 是什麼 | 回答的問題 | AWS 主要服務 |
|---|---|---|---|
| **Metric（指標）** | 隨時間變化的數值，例如每分鐘請求數、p99 延遲 | 「現在好不好？趨勢如何？」 | CloudWatch Metrics |
| **Log（日誌）** | 一筆一筆的文字或 JSON 事件紀錄 | 「這個請求發生了什麼事？錯誤訊息是什麼？」 | CloudWatch Logs |
| **Trace（追蹤）** | 一個請求穿過多個服務的完整路徑與每段耗時 | 「慢在哪一段？哪個下游服務出錯？」 | X-Ray、OpenTelemetry |
| **Event（事件）** | 狀態改變的通知，例如 instance 被終止、alarm 進入 ALARM | 「剛剛發生了什麼變化？要不要自動處理？」 | EventBridge |

另外還有一類容易混淆的資料：**稽核紀錄（audit log）**，也就是「誰在什麼時間呼叫了哪個 AWS API」。它不是用來看效能，而是用來追究責任與調查資安事件，由 CloudTrail 負責（36.11 節）。

### 從使用者結果出發：SLI 與 SLO

小林的告警全部盯在資源上（CPU、記憶體），而使用者在乎的是「付款能不能成功、要等多久」。業界的做法是先定義 **SLI（Service Level Indicator，服務水準指標）**：一個直接反映使用者體驗的量測，例如「付款 API 回應時間小於 2 秒且成功的請求比例」。再定義 **SLO（Service Level Objective，服務水準目標）**：這個指標的目標值，例如「30 天內 99.9% 的付款請求達標」。SLO 沒達到的那 0.1% 稱為 **error budget（錯誤預算）**，用完了就該暫停新功能上線、先處理穩定性。

這個觀念直接影響告警設計：**最重要的告警應該盯住 SLI**（付款成功率、p99 延遲），資源指標（CPU、磁碟）則是用來找原因或做容量規劃。CloudWatch 的 **Application Signals** 功能可以自動收集應用程式的請求量、延遲與錯誤，並直接在上面定義 SLO 與追蹤 error budget。

> [!tip] 考試提示
> 題目若說「使用者抱怨很慢，但所有 CPU 與記憶體指標都正常」，正確方向通常是加上**應用層**的量測：ALB 的 `TargetResponseTime` 百分位數、自訂業務指標、X-Ray tracing 或 Synthetics canary，而不是調高 instance 規格。

## 36.3 CloudWatch Metrics：數字怎麼被收集與保存

**Amazon CloudWatch** 是 AWS 的監控平台，**CloudWatch Metrics** 是其中儲存時間序列數值的部分。幾乎所有 AWS 服務都會自動把指標送進 CloudWatch，不用安裝任何東西：EC2 的 `CPUUtilization`、ALB 的 `RequestCount`、SQS 的 `ApproximateNumberOfMessagesVisible`、Lambda 的 `Duration` 與 `Errors`。

### 一個 metric 由什麼組成

| 元素 | 意義 | 例子 |
|---|---|---|
| **Namespace** | 指標的分類容器，`AWS/` 開頭的保留給 AWS 服務 | `AWS/EC2`、`AWS/ApplicationELB`、`Wanderly/Payments` |
| **Metric name** | 指標名稱 | `CPUUtilization`、`PaymentLatency` |
| **Dimension** | 用來區分同名指標的「名稱=值」標籤 | `InstanceId=i-0abc`、`LoadBalancer=app/web/123` |
| **Datapoint** | 某個時間點的值（含單位） | 2026-10-01T10:00:00Z，37.5 Percent |

關鍵觀念是：**namespace + metric name + 一組 dimension 的每一種組合，都是一個獨立的 metric**。`PaymentLatency` 加上 `Region=tokyo` 和 `PaymentLatency` 加上 `Region=osaka` 是兩個 metric；查詢時必須指定完全相同的 dimension 組合才查得到。這點在 36.13 節談成本時會再出現。

### Statistic 與 period：同一批資料，不同的看法

CloudWatch 不會讓你逐筆看原始資料點，而是用 **period（統計週期）** 把資料分桶，再對每桶套用 **statistic（統計方式）**：

- `Average`、`Sum`、`Minimum`、`Maximum`、`SampleCount`：基本統計。
- **百分位數（percentile）**，例如 `p50`、`p90`、`p99`：「99% 的請求都比這個值快」。

延遲類指標一定要看百分位數。假設 100 個請求中 98 個花 100 毫秒、2 個花 20 秒，平均約 0.5 秒，看起來還可以接受；但 p99 是 20 秒，代表每 100 位客人就有 1 位等了 20 秒。小林事故中的金流延遲，正是這種被平均值掩蓋的「長尾」。

### Standard 與 detailed monitoring

EC2 預設提供 **basic monitoring（基本監控）**：每 5 分鐘一個資料點，免費。啟用 **detailed monitoring（詳細監控）** 後改為每 1 分鐘一個資料點，需另外付費。許多受管服務（例如 ALB、RDS）預設就是 1 分鐘粒度。

為什麼粒度重要？Auto Scaling 依 metric 擴展，5 分鐘才有一個資料點，代表流量暴增時最慢要好幾分鐘才「看得到」。對尖峰陡峭的 workload，開啟 detailed monitoring 能讓 scaling 與 alarm 反應更快。

### Custom metrics 與 high resolution

應用程式可以用 `PutMetricData` API（或 SDK、CloudWatch agent）送出自己的 **custom metric（自訂指標）**，例如每分鐘成功付款數、購物車放棄數。

```bash
aws cloudwatch put-metric-data \
  --namespace Wanderly/Payments \
  --metric-name PaymentLatency \
  --dimensions Provider=PayCo \
  --unit Milliseconds \
  --value 312 \
  --storage-resolution 1
```

`--storage-resolution 1` 代表這是 **high-resolution metric（高解析度指標）**：以 1 秒粒度儲存，查詢時 period 可以是 1、5、10、30 秒；預設的 standard resolution 則是 1 分鐘。高解析度指標可以搭配 period 為 10 秒或 30 秒的 **high-resolution alarm**，適合「秒級」偵測的場景，例如交易系統。

### 資料保留多久

CloudWatch 會自動把舊資料「降低解析度」保存：

| 資料粒度 | 保留時間 |
|---|---|
| 小於 60 秒（high resolution） | 3 小時 |
| 60 秒 | 15 天 |
| 5 分鐘 | 63 天 |
| 1 小時 | 455 天（約 15 個月） |

也就是說，一年前的資料仍查得到，但只剩 1 小時粒度。Metric 不能手動刪除；連續 15 個月沒有新資料就會自然過期。若需要更久或更細的歷史資料（例如做年度容量分析），可以用 **metric streams** 把指標近即時串流到 Data Firehose，再存入 S3 或第三方監控平台。

### Embedded Metric Format：用日誌產生指標

在 Lambda 這類短暫執行的環境裡，每次呼叫 `PutMetricData` 會增加延遲與 API 費用。**EMF（Embedded Metric Format）** 讓程式只要寫一行特定格式的 JSON 日誌，CloudWatch Logs 就會自動從中萃取出 metric，同時保留完整日誌：

```json
{
  "_aws": {
    "Timestamp": 1790000000000,
    "CloudWatchMetrics": [{
      "Namespace": "Wanderly/Payments",
      "Dimensions": [["Provider"]],
      "Metrics": [{"Name": "PaymentLatency", "Unit": "Milliseconds"}]
    }]
  },
  "Provider": "PayCo",
  "PaymentLatency": 312,
  "orderId": "ord-88231",
  "userId": "u-551902"
}
```

這筆 JSON 產生了一個以 `Provider` 為 dimension 的 `PaymentLatency` 指標；`orderId`、`userId` 沒有列在 `Dimensions` 裡，只會留在日誌中供查詢，不會變成 metric。這個區分在成本上非常重要（見 36.13 節）。

## 36.4 CloudWatch agent：補上 EC2 看不到的指標

小林想加一個「記憶體使用率超過 90% 就告警」，卻發現 `AWS/EC2` namespace 裡根本沒有記憶體指標。

原因在於 EC2 的預設指標是由 **hypervisor（虛擬化層）** 從「機器外面」量的。Hypervisor 看得到 CPU 用了多少、網路與磁碟 I/O 流量多少、status check 是否通過，但看不到作業系統內部的狀態：記憶體被哪些程式用掉、檔案系統還剩多少空間、某個 process 是否還活著。這些都必須從作業系統內部回報。

**CloudWatch agent** 是一個安裝在 EC2（或地端伺服器）上的程式，負責：

- 收集系統層指標：記憶體使用率、磁碟空間使用率、swap、每個 process 的資源（`procstat`）等，送到 `CWAgent` namespace（可自訂）。
- 收集日誌檔案（例如 `/var/log/nginx/access.log`、Windows Event Log），送到 CloudWatch Logs。
- 接收應用程式透過 StatsD 或 collectd 協定送來的自訂指標。

部署時要注意三件事：

1. **權限**：instance profile 的 IAM role 需要能寫入 CloudWatch 與 CloudWatch Logs，最常用的是 AWS managed policy `CloudWatchAgentServerPolicy`。
2. **設定檔集中管理**：agent 的 JSON 設定可以存在 SSM Parameter Store，所有機器啟動時讀同一份，避免每台手改。
3. **大量部署**：用 Systems Manager 的 Run Command 或 State Manager 安裝與更新 agent（第 38 章），或直接把 agent 烤進 golden AMI（第 17 章）。

> [!warning] 常見誤解
> 「開啟 detailed monitoring 就看得到記憶體。」不會。Detailed monitoring 只是把同一批 hypervisor 指標從 5 分鐘改為 1 分鐘；記憶體與磁碟空間無論如何都需要 CloudWatch agent。考試看到「memory utilization」「disk space」幾乎就是 CloudWatch agent 的訊號。

容器與 serverless 環境不需要自己裝 agent 也能取得類似資料：**Container Insights** 為 ECS 與 EKS 收集 cluster、service、task、Pod 層級的 CPU、記憶體、網路與重新啟動次數（EKS 上透過 CloudWatch Observability add-on 部署 agent）；**Lambda Insights** 以 Lambda extension 形式收集每次呼叫的記憶體、CPU 時間與 cold start 等系統層指標。

## 36.5 CloudWatch Alarms：從數字到行動

有了指標，下一步是讓它在異常時「叫人」或「自動修復」。**CloudWatch alarm** 會持續評估一個 metric（或 metric math 運算結果），並處於三種狀態之一：

- **OK**：在閾值內。
- **ALARM**：超出閾值。
- **INSUFFICIENT_DATA**：資料不足以判斷，例如 alarm 剛建立或 metric 沒有資料。

狀態「改變」時才會觸發動作，所以一個持續處於 ALARM 的 alarm 不會每分鐘寄一次信。唯一的例外是 Auto Scaling 動作：只要 alarm 停留在 ALARM，它會每分鐘再觸發一次 scaling policy。

### 評估邏輯：period、evaluation periods 與 M of N

一個 alarm 的核心設定有四個：

| 設定 | 意義 | Wanderly 付款延遲的例子 |
|---|---|---|
| Period | 每個評估資料點的統計週期 | 60 秒 |
| Statistic | 每個 period 用什麼統計 | p99 |
| Evaluation periods（N） | 回看最近幾個資料點 | 5 |
| Datapoints to alarm（M） | N 個裡有幾個超標就進入 ALARM | 3 |

「5 個裡有 3 個超過 2 秒」稱為 **M of N**。它比「連續 3 個超標」更能容忍偶發的單點雜訊，又不會因為中間有一個資料點恰好正常就錯過持續惡化。

### Missing data 怎麼處理

如果某段時間沒有資料點，alarm 要怎麼解讀？設定 **treat missing data** 有四個選項：

| 選項 | 行為 | 適用 |
|---|---|---|
| `missing`（預設） | 不納入評估；全部缺資料時進入 INSUFFICIENT_DATA | 一般情況 |
| `notBreaching` | 當作正常 | 錯誤數這類「沒資料代表沒發生」的指標 |
| `breaching` | 當作超標 | **heartbeat（心跳）** 指標：沒收到就代表程式死了 |
| `ignore` | 維持目前狀態 | 資料本來就不規律的指標 |

Wanderly 的批次對帳程式每 5 分鐘送出一次 `ReconcileHeartbeat=1`，若程式當機就不會再送。這個 alarm 必須設定 `breaching`，否則程式死掉時 alarm 只會停在 INSUFFICIENT_DATA，沒有人被通知。

### Alarm 能觸發哪些動作

- **SNS topic**：寄 email、發簡訊、呼叫 webhook，或串到 Slack（透過 Amazon Q Developer in chat applications，舊名 AWS Chatbot）。
- **EC2 動作**：stop、terminate、reboot 或 **recover**。Recover 會在 `StatusCheckFailed_System`（底層硬體或主機問題）時把 instance 移到新的實體主機，保留 instance ID、private IP、Elastic IP 與 EBS。
- **Auto Scaling 動作**：觸發 step scaling 或 simple scaling policy（第 18 章；target tracking 會自己建立並管理 alarm）。
- **Lambda function**：直接呼叫 Lambda 做自動修復。
- **Systems Manager**：建立 OpsItem，交給 OpsCenter 追蹤（第 38 章）。

此外，每次 alarm 狀態改變都會送一個事件到 **EventBridge**，可以用規則接到任何 target，做更複雜的處理（36.10 節）。

### 用 CloudFormation 描述一個 p99 告警

```yaml
Resources:
  PaymentLatencyAlarm:
    Type: AWS::CloudWatch::Alarm
    Properties:
      AlarmName: payments-p99-latency-high
      Namespace: AWS/ApplicationELB
      MetricName: TargetResponseTime
      ExtendedStatistic: p99
      Dimensions:
        - Name: LoadBalancer
          Value: !GetAtt PaymentsAlb.LoadBalancerFullName
        - Name: TargetGroup
          Value: !GetAtt PaymentsTargetGroup.TargetGroupFullName
      Period: 60
      EvaluationPeriods: 5
      DatapointsToAlarm: 3
      Threshold: 2
      ComparisonOperator: GreaterThanThreshold
      TreatMissingData: notBreaching
      AlarmActions:
        - !Ref OnCallTopic
      OKActions:
        - !Ref OnCallTopic
```

百分位數用 `ExtendedStatistic`，一般統計才用 `Statistic`。`TreatMissingData: notBreaching` 的理由是：半夜沒有任何付款請求時，ALB 不會產生延遲資料點，這不代表出問題。

### Composite alarm：把多個訊號組合成一個判斷

小林把 20 個 alarm 都接到值班手機後，一次 Aurora failover 讓手機在一分鐘內響了 14 次：API 延遲、錯誤率、連線數、佇列深度……全部是同一個原因造成的。這種 **alert fatigue（告警疲勞）** 會讓真正重要的通知被忽略。

**Composite alarm（複合告警）** 用規則運算式組合其他 alarm 的狀態，例如：

```text
ALARM("payments-p99-latency-high") AND ALARM("payments-5xx-rate-high")
```

支援 `AND`、`OR`、`NOT` 與括號。常見做法是：底層 alarm 不設定任何通知動作，只用來「描述狀態」；只有 composite alarm 才通知值班人員。Composite alarm 也能設定 **actions suppressor**：例如當「計畫性維護中」這個 alarm 處於 ALARM 時，暫時抑制通知。Composite alarm 可以發 SNS 通知、建立 Systems Manager OpsItem 或 incident，但**不能執行 EC2 或 Auto Scaling 動作**；需要這類動作時，要放在底層的 metric alarm 上。

### Anomaly detection：閾值不是一條直線

Wanderly 的流量白天高、半夜低、週末又不一樣。若用固定閾值「每分鐘請求數小於 100 就告警」，半夜每天都會誤報；設太低又抓不到白天的異常下跌。

**Anomaly detection（異常偵測）** 會用機器學習模型分析 metric 的歷史資料，學出每天與每週的週期性，產生一條「預期範圍」的帶狀區間（band）。Alarm 可以設定為「高於 band」「低於 band」或「超出 band 任一側」才觸發，band 的寬度用標準差倍數調整。它適合有明顯週期、但沒有固定合理數值的指標，例如訂單量、登入次數。

### Metric math

Alarm 也可以建立在 **metric math** 運算結果上，例如錯誤率 = `5xx 數量 / 總請求數 × 100`。直接對「錯誤數」設閾值，流量大時容易誤報、流量小時又抓不到；對「錯誤率」設閾值則與流量規模無關。

## 36.6 CloudWatch Logs：集中保存、查詢與轉送日誌

小林那一個半小時花在「一台一台登入翻日誌」。若日誌都集中在 CloudWatch Logs，同一件事用一個查詢就能完成，而且機器被 Auto Scaling 終止後日誌也不會跟著消失。

### 結構：log group、log stream、log event

- **Log event**：一筆紀錄，包含時間戳記與訊息。
- **Log stream**：來自同一個來源的一串 log event，例如某一台 instance 或某個 Lambda 執行環境。
- **Log group**：一組有相同保留、權限與加密設定的 log stream，通常對應一個應用程式或元件，例如 `/wanderly/prod/payments`。

設定都在 log group 層級：

| 設定 | 說明 |
|---|---|
| **Retention（保留期間）** | 預設是**永不過期（Never expire）**，可設定 1 天到 10 年。忘記設定是 CloudWatch Logs 帳單持續變大的常見原因。 |
| **KMS 加密** | Log 資料一律在靜態加密；可另外關聯 customer managed KMS key，讓解密需要該 key 的權限（第 15 章）。 |
| **Log class** | **Standard** 支援全部功能；**Infrequent Access（IA）** 每 GB 擷取費用較低（儲存與查詢費用相同），適合很少查詢、事後鑑識用的日誌，可以用 Logs Insights 查詢、匯出到 S3，但**不支援 metric filter、subscription filter、Live Tail 與 EMF** 等即時處理功能。Log class 只能在建立 log group 時選擇，**之後不能更改**。 |
| **Data protection policy** | 偵測並遮罩日誌中的敏感資料，例如信用卡號、email。 |

### 日誌從哪裡來

- Lambda 會自動把 stdout／stderr 寫入 `/aws/lambda/<函式名稱>` log group（需要 execution role 有寫入權限）。
- ECS 使用 `awslogs` log driver 或 FireLens（Fluent Bit）送出容器日誌。
- EC2 與地端伺服器使用 CloudWatch agent。
- 許多 AWS 服務可以把自己的日誌送到 CloudWatch Logs，例如 VPC Flow Logs（第 6 章）、API Gateway access logs、Route 53 Resolver query logs、CloudTrail（選用）。

### Logs Insights：用查詢語言找答案

**CloudWatch Logs Insights** 讓你對一個或多個 log group 執行互動式查詢，按掃描的資料量計費。小林事後寫了這個查詢，找出最慢的付款請求與對應的金流商：

```text
fields @timestamp, orderId, provider, latencyMs
| filter path = "/api/payments" and latencyMs > 2000
| stats count(*) as slow, avg(latencyMs) as avgMs, pct(latencyMs, 99) as p99 by provider
| sort slow desc
| limit 20
```

這正是**結構化日誌（structured logging）**的價值：應用程式把日誌寫成 JSON，Logs Insights 會自動辨識欄位（`orderId`、`latencyMs`），查詢就能直接過濾與統計。若日誌是一行自由文字，就得先用 `parse` 拆欄位，既慢又容易漏。

### Metric filter：從日誌長出指標

有些訊號只存在日誌中，例如「應用程式記錄了 `PAYMENT_TIMEOUT`」。**Metric filter** 會用一個比對樣式（pattern）掃描**之後新進來**的 log event，符合時把某個 metric 加 1（或取出某個欄位的數值），之後就能對這個 metric 設 alarm。

```bash
aws logs put-metric-filter \
  --log-group-name /wanderly/prod/payments \
  --filter-name payment-timeouts \
  --filter-pattern '{ $.errorCode = "PAYMENT_TIMEOUT" }' \
  --metric-transformations \
      metricName=PaymentTimeouts,metricNamespace=Wanderly/Payments,metricValue=1,defaultValue=0
```

> [!warning] 常見誤解
> Metric filter **不會回溯**處理建立之前的日誌。如果要統計上週已經發生的錯誤數，要用 Logs Insights 查詢，而不是建立 metric filter 再等它出數字。

### Subscription filter：把日誌即時送出去

Metric filter 只產生數字；如果要把日誌「本身」近即時送到別處處理或保存，用 **subscription filter**。它把符合樣式的 log event 串流到：

- **Kinesis Data Streams**：自己寫 consumer 做即時處理，或跨帳號匯集。
- **Data Firehose**：近即時（有緩衝）送到 S3、OpenSearch Service、Redshift 或第三方平台，免寫程式。
- **Lambda**：輕量的即時處理，例如偵測到特定錯誤就發通知。

每個 log group 最多只能設定 5 個 subscription filter（不可調整的 quota），所以需要送往多個目的地時，通常先送進 Kinesis 或 Firehose 再分流。除了逐一設定 log group，也可以建立**帳號層級**的 subscription filter policy，一次套用到帳號內的 log group。

另一個常被拿來比較的功能是**匯出到 S3（export task）**：它是一次性、批次的匯出，不是即時串流。題目要求「近即時」「持續」把日誌送到 S3 時，答案是 subscription filter + Firehose，不是 export task。

### Live Tail 與 Contributor Insights

**Live Tail** 讓你在 console 即時看著日誌流進來並過濾，適合部署當下觀察。**Contributor Insights** 分析日誌找出「前 N 名貢獻者」，例如請求數最多的前 10 個來源 IP、錯誤最多的 API 路徑，對找出濫用者或熱點很有用。

## 36.7 Dashboards：給人看的全景

**CloudWatch dashboard** 是可自訂的圖表頁面，可以放 metric 圖、alarm 狀態、Logs Insights 查詢結果與文字說明。幾個實用特性：

- 一個 dashboard 可以同時顯示**多個 Region** 的指標，搭配 36.12 節的跨帳號設定也能顯示多個帳號的資料。
- 許多服務有 **automatic dashboard**，不用設定就能看到該服務的關鍵指標。
- Dashboard 可以分享給沒有 AWS 帳號的人（例如營運主管），透過受控的分享連結登入檢視。

小林重新設計 Wanderly 的值班 dashboard 時，把最上排換成使用者視角的 SLI：付款成功率、搜尋 p99 延遲、訂單建立數（和上週同時段比較）；第二排是各層的錯誤率與延遲；最下排才是資源指標。值班人員一打開就能先回答「使用者現在有沒有受影響」，再往下找原因。

## 36.8 Tracing：一個請求到底卡在哪一段

Metrics 告訴小林「付款 p99 延遲變高了」，logs 告訴他「某些請求超過 20 秒」，但一個付款請求會經過 API Gateway、訂房服務、庫存服務、SQS、付款 Lambda、第三方金流，到底是哪一段慢？這需要 **distributed tracing（分散式追蹤）**。

### 運作原理

Tracing 的核心是 **trace context propagation（追蹤上下文傳遞）**：請求進入系統時被分配一個唯一的 **trace ID**，每個服務在呼叫下一個服務時，都把這個 ID 放在 HTTP header 或訊息屬性裡傳下去。每個服務也記錄自己處理這個請求的開始時間、結束時間與結果，並送到 tracing 後端。後端再用 trace ID 把所有片段拼回一條完整的時間軸。

```text
使用者請求 POST /api/payments            trace ID = 1-6704a1b2-...
│
├─① API Gateway ─────────────────────────────── 25.4 s
│   └─② 訂房服務（ECS） ──────────────────────── 25.3 s
│        ├─③ 庫存服務 HTTP 呼叫 ── 0.08 s
│        ├─④ Aurora 查詢 ───────── 0.01 s
│        └─⑤ PayCo 金流 API ───────────────────── 25.1 s   ← 瓶頸
│
└─ 回應 504
```

① 進入點產生 trace ID，並把它放進 `X-Amzn-Trace-Id` header。② 訂房服務的 segment 涵蓋它處理請求的全部時間。③④⑤ 是訂房服務對下游的呼叫，各自記錄為 subsegment。只要看一眼時間軸，就知道 25 秒幾乎全花在 ⑤，而不是資料庫或庫存服務。小林那天花了一個半小時才找到的答案，有了 tracing 只需要點開一筆慢請求。

### AWS X-Ray 的概念

**AWS X-Ray** 是 AWS 的分散式追蹤服務，主要名詞如下：

| 名詞 | 意義 |
|---|---|
| **Trace** | 一個請求的完整紀錄，由 trace ID 串起所有 segment |
| **Segment** | 一個服務處理該請求的紀錄（主機、請求、回應、錯誤、耗時） |
| **Subsegment** | Segment 內更細的工作單位，例如一次 SQL 查詢或一次對外 HTTP 呼叫 |
| **Service map／trace map** | 由 trace 自動畫出的服務相依圖，每個節點標示延遲與錯誤率 |
| **Annotation** | 會被**索引**的鍵值，可用來搜尋 trace，例如 `provider=PayCo` |
| **Metadata** | 不被索引的附加資料，只在檢視單筆 trace 時看得到 |
| **Sampling rule** | 決定記錄多少比例的請求 |

**Sampling（取樣）** 很重要：記錄每一個請求的成本很高，X-Ray 預設規則是每秒記錄第一個請求，之後再記錄其餘請求的 5%。你可以為特定路徑設定較高的取樣率，例如付款 API 取樣 50%，健康檢查路徑取樣 0%。

### 各服務如何接上 tracing

- **Lambda**：在函式設定中啟用 **active tracing**，Lambda 會自動送出函式的 segment；程式內的下游呼叫需要 SDK 或 OpenTelemetry 的 instrumentation 才會產生 subsegment。
- **API Gateway**：在 stage 上啟用 X-Ray tracing。
- **ALB**：會在請求中加入或更新 `X-Amzn-Trace-Id` header，讓後端能延續同一個 trace，但 ALB 本身不會送 segment 到 X-Ray。
- **SQS、SNS、EventBridge、Step Functions**：可以傳遞 trace header，讓非同步流程的 producer 與 consumer 出現在同一個 trace 裡。
- **EC2、ECS、EKS 上的程式**：程式碼需要 instrumentation，並在旁邊執行一個收集器把資料送到 X-Ray。

### X-Ray SDK 與 OpenTelemetry 的現況

過去的標準做法是在程式中使用 X-Ray SDK，再於每台主機或每個 task 執行 **X-Ray daemon**（以 UDP 2000 port 接收資料後批次上傳）。現在 AWS 的方向是 **OpenTelemetry（OTel）**：一個由雲端原生社群維護、與廠商無關的 tracing、metrics 與 logs 標準。**AWS Distro for OpenTelemetry（ADOT）** 是 AWS 支援的 OpenTelemetry 發行版，包含 SDK 與 collector，可以把資料送到 X-Ray、CloudWatch 或其他相容後端。

X-Ray SDK 與 daemon 已於 2026 年 2 月進入維護模式（maintenance mode）：既有系統仍可運作，但新功能投資集中在 OpenTelemetry。新建的 workload 應優先採用 ADOT／OpenTelemetry instrumentation；X-Ray 本身作為 tracing 後端與 CloudWatch 中的 trace 檢視仍持續提供。

> [!tip] 考試提示
> 題目出現「microservices」「找出哪個下游服務造成延遲」「視覺化服務之間的呼叫關係」，答案是 X-Ray（或 ADOT 送到 X-Ray）。如果選項是「在每個服務加更多日誌再用 Logs Insights 關聯」，那是營運負擔較大的做法。

## 36.9 從使用者角度監控：Synthetics 與 RUM

到目前為止的訊號都來自「系統內部」。但有些問題只有從外面看才看得到：DNS 設定錯誤、CloudFront 憑證過期、某個國家的網路路徑變慢、前端 JavaScript 錯誤讓按鈕按不下去。這類問題，內部指標可能全部正常。

### CloudWatch Synthetics：機器人假扮使用者

**CloudWatch Synthetics** 讓你建立 **canary（金絲雀腳本）**：一段依排程執行的程式（Node.js 或 Python，可使用 Puppeteer、Playwright 或 Selenium 操作瀏覽器），模擬使用者行為並檢查結果。常見類型：

- **Heartbeat**：定期載入一個 URL，確認回應正常。
- **API canary**：呼叫 REST API 並檢查回應內容。
- **Broken link checker**：檢查頁面上的連結是否失效。
- **GUI workflow**：走完一段多步驟流程，例如「搜尋 → 選房 → 進入付款頁」。
- **Visual monitoring**：截圖與基準比對，偵測畫面跑版。

Canary 在 Lambda 上執行，結果（成功率、耗時）成為 CloudWatch metric，可以設 alarm；截圖、HAR 檔與日誌存在 S3。Canary 也可以放進 VPC 執行，監控只有內部能存取的端點。

Synthetics 最大的價值是**在沒有真實使用者時也能發現問題**：半夜三點流量很低，真實請求可能半小時才一筆，但 canary 每 5 分鐘就走一次付款流程，壞了馬上知道。這也是 Wanderly 補上的第一個告警：「付款流程 canary 連續兩次失敗」。

### CloudWatch RUM：真實使用者的體驗

**CloudWatch RUM（Real User Monitoring）** 則反過來：在網頁中加入一段 JavaScript snippet，從真實使用者的瀏覽器收集頁面載入時間、Core Web Vitals、JavaScript 錯誤、HTTP 錯誤與使用者 session 路徑，並可依國家、瀏覽器、裝置分析。瀏覽器送資料到 RUM 需要授權，常見做法是使用 Cognito identity pool 提供的暫時憑證。RUM 也可以設定 session 取樣比例控制成本。

| | Synthetics | RUM |
|---|---|---|
| 資料來源 | 你寫的腳本，依排程執行 | 真實使用者的瀏覽器 |
| 沒有流量時 | 照樣執行，能發現問題 | 沒有資料 |
| 回答的問題 | 「關鍵流程現在能不能走完？」 | 「真實使用者在各地、各裝置的體驗如何？」 |
| 典型告警 | Canary 成功率下降 | 某國家頁面載入時間或 JS 錯誤率上升 |

兩者互補：Synthetics 是固定路線的巡邏，RUM 是聽取每一位顧客的回饋。

## 36.10 EventBridge：讓事件觸發自動處理

監控的終點不一定是「通知人」。很多狀況可以自動處理，而 AWS 裡的「狀態改變」幾乎都會以事件形式送到 **EventBridge** 的 default event bus（第 32 章）：

- CloudWatch alarm 狀態改變。
- EC2 instance 狀態改變（running、stopping、terminated）、Auto Scaling 啟動或終止 instance。
- **AWS Health** 事件，例如「你的某台 EC2 所在的主機排定退役」「某服務在你使用的 Region 發生問題」。
- 透過 CloudTrail 記錄的 AWS API 呼叫（事件類型為 `AWS API Call via CloudTrail`）。
- 許多服務自己的事件，例如 ECS task 停止、CodePipeline 執行失敗、GuardDuty 發現。

一個實際例子：Wanderly 規定所有 security group 都不得開放 `0.0.0.0/0` 的 22 port。下面這條 EventBridge 規則會在有人呼叫 `AuthorizeSecurityGroupIngress` 時觸發 Lambda，由 Lambda 檢查規則內容並自動撤銷違規項目、通知資安團隊：

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["ec2.amazonaws.com"],
    "eventName": ["AuthorizeSecurityGroupIngress"]
  }
}
```

這個模式（事件 → 規則 → Lambda 或 SSM Automation）是自動修復的基礎，第 38 章會完整展開。這裡要記住的是分工：**CloudWatch 負責量測與判斷異常，EventBridge 負責把事件路由到處理者**。若要定期執行某件事（例如每天凌晨產生報表），則使用 EventBridge Scheduler。

## 36.11 誰做了什麼、設定變成怎樣：CloudTrail、Config 與 CloudWatch 的分工

考試最愛考這三個服務的差異，因為它們的名字都像「監控」。用一個情境來分辨：週一早上，Wanderly 的付款服務無法連到資料庫。

- 「從幾點開始連不上？連線錯誤率多少？」→ **CloudWatch**（metrics、logs）。
- 「資料庫的 security group 是被誰、在幾點、從哪個 IP 改掉的？」→ **CloudTrail**。
- 「這個 security group 在週五時的規則長什麼樣？目前有哪些 security group 不符合公司規定？」→ **AWS Config**。

**AWS CloudTrail** 記錄 AWS 帳號中的 API 呼叫：誰（IAM 身份）、何時、從哪個來源 IP、呼叫了哪個 API、帶了哪些參數、成功或失敗。重點如下（細節見第 16 章）：

- **Event history** 免費保留最近 90 天的 management events（管理事件，例如建立、修改、刪除資源），可以直接在 console 查詢。
- 要長期保存，建立 **trail** 把事件送到 S3（可選擇同時送到 CloudWatch Logs，以便設定 metric filter 與 alarm）。多帳號環境使用 **organization trail**。
- **Data events**（例如 S3 object 層級的 GetObject、Lambda Invoke）量大、另外收費，預設不記錄，要明確開啟。
- **CloudTrail Insights** 偵測 API 呼叫量或錯誤率的異常（例如某個 role 突然大量呼叫 `DeleteObject`）。
- **Log file validation** 用雜湊與數位簽章證明日誌檔未被竄改。
- CloudTrail 事件通常在數分鐘內送達，不是即時的；需要立即反應時用 EventBridge 規則接收。
- 另一個查詢功能 CloudTrail Lake 自 2026 年 5 月 31 日起不再接受新客戶（既有客戶可繼續使用）；新環境以 trail + S3（搭配 Athena 查詢）建立長期稽核資料，或依 AWS 建議把 CloudTrail 事件匯入 CloudWatch 集中查詢。

**AWS Config** 則持續記錄資源的**設定狀態與變更歷史**（configuration item、configuration timeline），並用 Config rules 判斷是否合規、搭配 remediation 自動修正（第 16 章）。

| 問題 | 服務 |
|---|---|
| 系統現在的效能與健康狀態？趨勢？ | CloudWatch Metrics |
| 應用程式發生了什麼、錯誤訊息？ | CloudWatch Logs |
| 誰呼叫了哪個 API？ | CloudTrail |
| 資源過去某時間點的設定？是否合規？ | AWS Config |
| AWS 自己的服務有沒有問題、會不會影響我？ | AWS Health |
| 我的帳號有沒有浪費、風險、配額快用完？ | Trusted Advisor |

### AWS Health Dashboard

小林的事故發生時，他曾懷疑「是不是 AWS 壞了」。**AWS Health Dashboard** 正是回答這個問題的地方，它包含兩個視角：

- **Service health**：公開的 AWS 各服務、各 Region 狀態，任何人都能看。
- **Your account health**：與**你的帳號資源**相關的事件，例如「你在東京 1a 的這三台 EC2 所在主機排定維護」「你的 RDS 需要強制升級」「某服務在你使用的 Region 發生延遲升高」。

Health 事件會送到 EventBridge，可以自動通知或處理（例如收到 EC2 退役通知就觸發 SSM Automation 換機）。程式化存取 **AWS Health API** 需要 Business 等級以上的付費支援方案（AWS 近年推出 Business Support+、Unified Operations 等新方案名稱，尚未轉換的 Business、Enterprise On-Ramp、Enterprise 方案仍可使用）；在 Organizations 中可以啟用 **organizational view**，由管理帳號或 delegated administrator 彙整所有成員帳號的 Health 事件。

### Trusted Advisor

**AWS Trusted Advisor** 會掃描帳號並依最佳實務提出建議，類別包括成本最佳化、效能、安全性、容錯、service limits（配額使用量）與營運卓越。例如：idle 的 load balancer、未啟用 MFA 的 root user、S3 bucket 權限過寬、EBS 沒有 snapshot、某項配額已用到 80%。Basic 與 Developer 支援方案只能使用核心的安全檢查與 service quotas 檢查；完整檢查與 API 需要 Business 以上的支援方案。第 38 章與第 39 章會說明如何把它的結果接進自動化與成本治理。

## 36.12 組起來：Wanderly 的可觀測性架構與多帳號集中

改造完成後，Wanderly 的可觀測性架構如下：

```text
           使用者瀏覽器 ──① RUM snippet──────────────┐

### CloudWatch cross-account observability

Wanderly 進入多帳號階段後（第 14 章），每個團隊有自己的 dev、staging、prod 帳號。值班人員若要在十幾個帳號之間切換角色才能看到完整畫面，事故處理會非常慢。

**CloudWatch cross-account observability** 的設計是：

- 指定一個帳號為 **monitoring account（監控帳號）**，在其中建立一個 **sink**。
- 其他帳號是 **source account（來源帳號）**，各自建立一個 **link** 連到 sink，並選擇要分享的資料類型：metrics、logs、traces、Application Signals 等。這套連結機制稱為 **Observability Access Manager（OAM）**。
- 連結完成後，在監控帳號中可以直接查詢、繪圖、設定 alarm、執行 Logs Insights、檢視跨帳號的 trace map，**不需要切換角色或複製資料**。
- 與 AWS Organizations 整合時，可以用 CloudFormation StackSets 或 Organizations 設定，讓整個 OU 的帳號自動連到監控帳號。
- 設定是**以 Region 為單位**：要在多個 Region 使用，每個 Region 都要建立 sink 與 link。

這個機制解決的是「**集中檢視**」；資料本身仍留在來源帳號，保留期間也依來源帳號的設定。若需求是「**長期、不可竄改的集中保存**」（例如法規要求 7 年），仍要用 subscription filter 或 trail 把資料複製到專用的 log archive 帳號。

### 我該用哪個服務？

│    ├─ 多個 alarm 同時響 → composite alarm 收斂
│    └─ 沒有流量時也要知道關鍵流程是否正常 → Synthetics canary
├─ 「為什麼壞了」
│    ├─ 錯誤訊息、單一請求細節 → CloudWatch Logs + Logs Insights

│    └─ 真實使用者在哪些地區、裝置有問題 → RUM
├─ 「誰做的、改了什麼」
│    ├─ API 呼叫者與時間 → CloudTrail

├─ 「是不是 AWS 的問題」→ AWS Health Dashboard / Health API

```

### 日誌處理方式比較

| 需求 | 做法 | 即時性 | 備註 |
|---|---|---|---|
| 臨時查詢、找原因 | Logs Insights | 互動式 | 按掃描量計費 |
| 日誌中某種事件的計數告警 | Metric filter + alarm | 近即時 | 不回溯舊資料 |
| 持續送到 S3／OpenSearch／第三方 | Subscription filter → Firehose | 近即時（有緩衝） | 免寫程式 |
| 即時自訂處理或跨帳號匯集 | Subscription filter → Kinesis Data Streams／Lambda | 即時 | 自己寫 consumer |
| 一次性把歷史日誌搬到 S3 | Export task | 批次 | 不適合持續需求 |
| 降低保存成本 | 設定 retention、Infrequent Access log class | — | 預設永不過期 |

### 指標收集方式比較

| 指標類型 | 收集方式 |
|---|---|
| EC2 CPU、網路、磁碟 I/O、status check | 內建（basic 5 分鐘／detailed 1 分鐘） |
| EC2 記憶體、磁碟空間、process | CloudWatch agent |
| ECS／EKS task、Pod 層級 | Container Insights |
| Lambda 系統層（記憶體、cold start） | Lambda Insights |
| 業務指標（付款數、轉換率） | PutMetricData 或 EMF |
| 秒級偵測 | High-resolution metric（1 秒）+ 10／30 秒 alarm |

### 遙測成本：cardinality 是隱藏的帳單

Custom metric 按「metric 數量」計費，而每一種 dimension 組合都是一個 metric。如果把 `userId` 放進 dimension，100 萬名使用者就會產生 100 萬個 metric，帳單會爆炸，而且這些 metric 幾乎都只有零星資料點，沒有人會看。這稱為 **high cardinality（高基數）** 問題。

正確做法是：dimension 只放基數低、需要聚合告警的屬性（服務、Region、金流商、API 路徑）；高基數的識別碼（userId、orderId、requestId）放在 EMF 的一般欄位或日誌裡，需要時用 Logs Insights 查詢。Tracing 則用 sampling 控制量，Logs 用 retention 與 log class 控制保存成本。

## 36.14 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| EC2 memory utilization、disk space usage | CloudWatch agent（不是 detailed monitoring） |
| 需要 1 分鐘粒度的 EC2 指標，讓 scaling 更快反應 | Detailed monitoring |
| 秒級指標、10 秒內告警 | High-resolution custom metric + high-resolution alarm |
| 從日誌中的特定錯誤字串產生告警 | Metric filter → metric → alarm |
| 日誌近即時送到 S3／OpenSearch／Splunk | Subscription filter → Data Firehose |
| 臨時分析日誌、找出最慢的請求 | CloudWatch Logs Insights |
| 日誌費用持續上升、舊日誌沒人看 | 設定 log group retention（預設永不過期） |
| 太多 alarm 同時響、要減少誤報 | Composite alarm（底層 alarm 不通知） |
| 流量有日夜週期，固定閾值誤報 | Anomaly detection alarm |
| Heartbeat 沒送出就要告警 | Treat missing data = breaching |
| EC2 底層硬體故障自動搬移、保留 IP | Alarm 的 EC2 recover 動作（StatusCheckFailed_System） |
| Microservices 找出延遲來自哪個下游 | X-Ray／ADOT tracing、service map |
| 沒有使用者時也要偵測網站或 API 故障 | CloudWatch Synthetics canary |
| 真實使用者頁面載入時間、前端 JS 錯誤 | CloudWatch RUM |
| 誰刪了資源、誰改了 security group | CloudTrail |
| 資源設定歷史、合規檢查 | AWS Config |
| AWS 排定維護、服務事件影響我的資源 | AWS Health Dashboard／Health 事件 + EventBridge |
| 集中檢視多個帳號的指標、日誌、trace | CloudWatch cross-account observability（monitoring account） |
| ECS／EKS 的 task、Pod 層級指標 | Container Insights |

**常見陷阱**：

1. 以為 detailed monitoring 會帶來記憶體指標。它只改變頻率，記憶體需要 agent。
2. 把 CloudTrail 當成效能監控，或把 CloudWatch 當成 API 稽核。前者回答「誰做的」，後者回答「好不好」。
3. 以為 metric filter 能統計建立之前的日誌。它只處理之後的新事件；歷史分析用 Logs Insights。
4. 選「export to S3」來滿足「即時」或「持續」送日誌的需求。Export task 是批次的，持續串流要用 subscription filter。
5. 用平均值監控延遲。長尾問題要看 p99 等百分位數。
6. 以為 cross-account observability 等於集中保存與不可竄改。它是集中檢視，法規保存仍要複製到 log archive 帳號。

## 36.15 SAP 加深：組織層級的可觀測性策略

SAA 題目通常只問「這個需求用哪個功能」；SAP 題目則會給你一個 80 個帳號的組織，要求設計集中化、可擴展、成本可控、且符合稽核要求的觀測平台。

### 集中檢視與集中保存是兩件事

| 目的 | 做法 | 特性 |
|---|---|---|
| 值班人員一處看全貌 | CloudWatch cross-account observability（每 Region 一個 sink） | 資料不複製、即時、權限依 link 分享範圍 |
| 長期保存、不可竄改、稽核 | Organization trail、Config aggregator、logs subscription → 中央 Kinesis／Firehose → log archive 帳號 S3（Object Lock） | 資料複製、可設 lifecycle 降成本 |
| 全公司日誌搜尋與安全分析 | 中央 S3 + Athena，或 OpenSearch Service；安全團隊另可用 Amazon Security Lake 以標準格式彙整安全日誌 | 可跨來源整合 |

跨帳號送日誌的傳統做法是：在中央帳號建立 CloudWatch Logs **destination**（背後是 Kinesis Data Streams 或 Firehose），並以 destination policy 允許來源帳號寫入；來源帳號的 subscription filter 指向這個 destination。用 service-managed StackSets 把 subscription filter 部署到 OU 內的每個帳號，新帳號加入 OU 時就能自動接上。

### Telemetry 治理

大型組織的觀測成本經常與運算成本同一個量級。SAP 情境中常見的改善方向：

- **標準化 instrumentation**：統一使用 OpenTelemetry（ADOT），換後端時不必改程式；在 collector 層集中設定 sampling、過濾與敏感資料移除。
- **限制 cardinality**：用平台層規範哪些屬性可以成為 metric dimension。
- **分級保存**：近期日誌留在 CloudWatch Logs 供查詢，長期日誌進 S3 並用 lifecycle 轉到 Glacier；很少查詢、也不需要 metric filter 或 subscription filter 的新 log group 在建立時就選用 Infrequent Access class（log class 建立後不能更改）。
- **SLO 驅動告警**：以 Application Signals 或自建 metric math 定義 SLO，依 error budget 消耗速度（burn rate）告警，取代成百上千個資源閾值告警。

### 事故處理流程

可觀測性最終是為了縮短 **MTTD（mean time to detect，平均偵測時間）** 與 **MTTR（mean time to recover，平均復原時間）**。SAP 題目會把監控與營運流程串在一起：composite alarm 觸發 → SNS／EventBridge → 建立 OpsItem 並附上相關 dashboard 與 runbook（第 38 章）→ 依 runbook 自動或半自動修復 → 事後檢討補上缺少的訊號。小林那次事故的檢討結論，就是在這個循環中補上了金流 API 延遲的 p99 alarm、付款流程 canary 與 tracing。

> [!sap] SAP 加深
> 題目若同時要求「各團隊自主管理自己帳號的監控」與「中央 SRE 團隊能在一個地方看到所有 prod 帳號」，答案是 cross-account observability：各帳號保有自己的 alarm 與 dashboard，中央監控帳號透過 OAM link 唯讀檢視。若再加上「保存 7 年、不可被帳號管理員刪除」，就要再加一條集中保存的資料路徑到 log archive 帳號。

## 本章重點整理

- Metrics 回答「好不好」、logs 回答「發生什麼事」、traces 回答「慢在哪一段」、events 用來觸發自動化；稽核「誰做的」則是 CloudTrail。
- 最重要的告警應盯住使用者感受到的 SLI（成功率、p99 延遲），資源指標用來找原因與做容量規劃。
- 一個 metric 由 namespace、名稱與 dimension 組合定義；每種 dimension 組合都是獨立 metric，也獨立計費。
- EC2 basic monitoring 每 5 分鐘、免費；detailed monitoring 每 1 分鐘、付費；兩者都沒有記憶體與磁碟空間，需要 CloudWatch agent。
- High-resolution custom metric 以 1 秒粒度儲存，可搭配 10 或 30 秒的 alarm；CloudWatch 指標最長保留 15 個月且會逐步降低解析度。
- Alarm 有 OK、ALARM、INSUFFICIENT_DATA 三種狀態；用 M of N 減少雜訊，用 treat missing data 正確處理沒有資料的情況（heartbeat 用 breaching）。
- Composite alarm 組合多個 alarm 以減少告警疲勞；anomaly detection 為有週期性的指標建立動態閾值；metric math 可以對錯誤率而非錯誤數告警。
- CloudWatch Logs 的 retention 預設永不過期，應依需求設定；metric filter 只處理新進日誌，歷史分析用 Logs Insights。
- 要把日誌近即時送到 S3、OpenSearch 或第三方，用 subscription filter 搭配 Firehose；export task 只適合一次性批次匯出。
- X-Ray 以 trace ID 串起 segment 與 subsegment，用 service map 找瓶頸、用 sampling 控制成本；新 workload 應採用 ADOT／OpenTelemetry instrumentation。
- Synthetics canary 依排程主動模擬使用者流程，沒有流量時也能發現問題；RUM 收集真實使用者瀏覽器的體驗資料。
- CloudTrail 記錄 API 呼叫，Config 記錄資源設定歷史與合規，CloudWatch 記錄效能與日誌，三者用途不同。
- AWS Health Dashboard 顯示影響你帳號的 AWS 事件，可透過 EventBridge 自動處理；Health API 與完整 Trusted Advisor 檢查需要 Business 以上的支援方案。
- CloudWatch cross-account observability 以 monitoring account 的 sink 與 source account 的 link 集中檢視多帳號資料（每個 Region 各自設定），但不取代集中保存與稽核用的 log archive。

## 本章練習題

### 練習 36-1｜SAA｜單選｜EC2 記憶體指標

Wanderly 的批次轉檔程式跑在一組 Amazon Linux EC2 上，最近常因記憶體不足被作業系統終止。團隊想在記憶體使用率超過 85% 時收到通知，但在 CloudWatch 的 `AWS/EC2` namespace 裡找不到任何記憶體相關的 metric。團隊希望使用 AWS 原生、營運負擔最低的做法。

應如何處理？

- A. 為這些 instance 啟用 detailed monitoring，等待 `MemoryUtilization` metric 出現後建立 alarm
- B. 在 instance 上安裝並設定 CloudWatch agent 收集記憶體使用率，再對 agent 送出的 metric 建立 alarm
- C. 建立 metric filter，從 `/var/log/messages` 中比對 `Out of memory` 字串並計數
- D. 使用 AWS Config rule 檢查 instance 的記憶體設定是否足夠

> [!answer]- 答案：B
> **A ✗** Detailed monitoring 只把 hypervisor 層指標的頻率從 5 分鐘改為 1 分鐘；hypervisor 看不到作業系統內部的記憶體使用量，所以不會出現記憶體 metric。
>
> **B ✓** 記憶體、磁碟空間等作業系統內部的指標必須由 CloudWatch agent 從 instance 內部收集，送到 CloudWatch 後就能像其他 metric 一樣建立 alarm。搭配 Parameter Store 集中管理 agent 設定，營運負擔很低。
>
> **C ✗** 這只能在記憶體已經耗盡、程式被終止「之後」才計數，無法在使用率達到 85% 時提前告警；而且還要先把系統日誌送進 CloudWatch Logs。
>
> **D ✗** AWS Config 記錄與評估資源設定（例如 instance type），不會量測執行期間的記憶體使用率。
>
> **考點**：SAA-2.2｜CloudWatch agent 收集記憶體與磁碟指標

### 練習 36-2｜SAA｜單選｜秒級偵測

Wanderly 的限時搶購 API 會在活動開始的前 30 秒湧入大量請求。團隊在應用程式中計算每秒的佇列等待時間，希望一旦等待時間在 10 秒內持續偏高就自動通知，而目前使用的 standard resolution custom metric 與 1 分鐘 alarm 反應太慢。

哪個做法能滿足需求？

- A. 為 EC2 啟用 detailed monitoring，並把 alarm period 改為 60 秒
- B. 改用 CloudWatch Logs metric filter 從日誌產生 metric，metric filter 會以 1 秒粒度評估
- C. 以 storage resolution 為 1 秒送出 high-resolution custom metric，並建立 period 為 10 秒的 alarm
- D. 建立 anomaly detection alarm，讓模型自動縮短評估週期

> [!answer]- 答案：C
> **A ✗** Detailed monitoring 只影響 EC2 內建指標，而且最細是 1 分鐘，不會讓自訂的佇列等待時間 metric 更快被評估。
>
> **B ✗** Metric filter 只是換一個「產生 metric」的方式，日誌還要經過擷取與處理才會變成資料點，並不會讓 alarm 自動以 10 秒週期評估，反應不會比直接送出 metric 更快。
>
> **C ✓** High-resolution custom metric 以 1 秒粒度儲存，可以搭配 period 為 10 秒或 30 秒的 high-resolution alarm，這是 CloudWatch 原生的秒級偵測做法。
>
> **D ✗** Anomaly detection 改變的是「閾值怎麼決定」（動態 band），不會改變 metric 的解析度或 alarm 的評估週期。
>
> **考點**：SAA-2.2、SAA-3.2｜high-resolution metric 與 alarm

### 練習 36-3｜SAA｜單選｜從日誌產生告警

Wanderly 的付款服務在逾時時會寫出一行 JSON 日誌，其中 `errorCode` 欄位為 `PAYMENT_TIMEOUT`。日誌已經透過 awslogs driver 送到 CloudWatch Logs 的 `/wanderly/prod/payments` log group。團隊希望 5 分鐘內出現超過 20 次逾時就通知值班人員，且不想修改應用程式。

最合適的做法是什麼？

- A. 在 log group 建立 metric filter，比對 `errorCode` 為 `PAYMENT_TIMEOUT` 的事件並轉成 metric，再對該 metric 建立 alarm 通知 SNS topic
- B. 每 5 分鐘以 EventBridge Scheduler 觸發 Lambda，用 Logs Insights 查詢逾時數量後判斷是否通知
- C. 建立 subscription filter 把日誌送到 Data Firehose，再存進 S3 用 Athena 查詢
- D. 在 CloudTrail 啟用 data events，記錄付款服務的每一次逾時

> [!answer]- 答案：A
> **A ✓** Metric filter 會持續掃描新進日誌，把符合樣式的事件轉成 CloudWatch metric，之後可以用一般 alarm 設定「5 分鐘 Sum 大於 20」並通知 SNS。不需改程式，也沒有額外要維護的程式碼。
>
> **B ✗** 技術上可行，但要自己寫與維護 Lambda、排程與判斷邏輯，營運負擔比內建的 metric filter 高；Logs Insights 較適合臨時分析。
>
> **C ✗** 這是長期保存與批次分析的路徑，無法提供近即時的告警。
>
> **D ✗** CloudTrail 記錄的是 AWS API 呼叫，不是應用程式內部發生的逾時。
>

### 練習 36-8｜SAA｜單選｜找出微服務延遲來源

- A. 以 ADOT／OpenTelemetry instrumentation 各服務、在 API Gateway 與 Lambda 啟用 tracing，把 trace 送到 X-Ray，使用 trace map 與慢請求的時間軸分析

> **D ✗** 告警可以告訴你「某處異常」，但不會呈現呼叫路徑，也無法解析單一請求在各段的耗時。

### 練習 36-13｜SAP｜單選｜Custom metric 成本暴增

> **D ✗** 合併後的值仍然是每個使用者與訂單都不同，metric 數量一樣龐大。

- E. 以 CloudFormation StackSets（service-managed）在 prod OU 的每個帳號部署 subscription filter 指向該 destination，新帳號加入 OU 時自動套用

> [!answer]- 答案：C、E
> **A ✗** Cross-account observability 提供的是集中「檢視」，資料仍留在來源帳號，來源帳號的管理員仍可刪除 log group，無法滿足不可竄改的保存要求。
>
> **B ✗** Export task 是批次的，無法在 5 分鐘內複製；每天排程也增加維運負擔。
>
> **C ✓** 跨帳號的 logs destination 讓多個來源帳號把 subscription filter 指向中央帳號；Firehose 近即時寫入 S3，Object Lock（compliance mode）防止任何人在保存期間刪除或修改。
>
> **D ✗** 在應用程式中使用長期 access key 有洩漏風險，也需要修改每個應用程式，不符合最佳實務。
>
> **E ✓** Service-managed StackSets 與 Organizations 整合，能在 OU 中所有帳號部署 subscription filter，並在新帳號加入時自動部署，滿足可擴展與自動化的需求。
>
> **考點**：SAP-1.4、SAP-2.3｜跨帳號 logs destination、Object Lock 與 StackSets

### 練習 36-15｜SAP｜單選｜新 tracing 平台的技術選擇

Wanderly 在 2026 年 10 月啟動一個預計使用五年的新微服務平台，橫跨 EKS、ECS 與 Lambda。平台團隊希望統一 tracing 與 metrics 的 instrumentation 方式，近期以 X-Ray 與 CloudWatch 作為後端，但保留未來改用其他後端的彈性，且不希望之後為此重寫程式。

最合適的方向是什麼？

- A. 在所有服務使用 X-Ray SDK，並在每個 Pod 與 task 旁執行 X-Ray daemon
- B. 只依賴 Lambda 的 active tracing，EKS 與 ECS 的服務改用日誌記錄 trace ID
- C. 為每個團隊各自選擇 instrumentation 方式，由後端負責整合
- D. 採用 AWS Distro for OpenTelemetry 的 SDK 與 collector 進行 instrumentation，由 collector 把資料送到 X-Ray 與 CloudWatch

> [!answer]- 答案：D
> **A ✗** X-Ray SDK 與 daemon 已於 2026 年 2 月進入維護模式，新功能投資集中在 OpenTelemetry；為一個五年的新平台鎖定這條路徑，未來遷移成本高，也綁定單一後端。
>
> **B ✗** EKS 與 ECS 服務只記錄 trace ID 而不產生 span，無法得到完整的跨服務時間軸，等於放棄大部分 tracing 能力。
>
> **C ✗** 各團隊各自為政會讓 trace context 傳遞格式不一致，跨服務的 trace 很容易斷掉，也違反「統一」的需求。
>
> **D ✓** OpenTelemetry 是與廠商無關的標準，ADOT 是 AWS 支援的發行版；collector 可以同時送到 X-Ray 與 CloudWatch，日後換後端只需修改 collector 設定，不必重寫程式。
>
> **考點**：SAP-3.1、SAP-4.4｜ADOT／OpenTelemetry 與 X-Ray SDK 現況

### 練習 36-16｜SAP｜單選｜特定地區使用者體驗變差

Wanderly 擴展到東南亞後，客服收到越南使用者抱怨「搜尋結果頁很慢」。Synthetics canary 從東京與新加坡執行都在 1.5 秒內完成，ALB 的 `TargetResponseTime` p99 也只有 400 毫秒。產品團隊要求找出哪些國家、哪些瀏覽器或裝置的使用者真正受到影響，以及是後端回應、資源下載還是前端 JavaScript 造成的。

最合適的做法是什麼？

- A. 在越南附近的 Region 增加更多 Synthetics canary，以涵蓋更多地點
- B. 在搜尋頁面加入 CloudWatch RUM，收集真實使用者的頁面載入時間、資源載入與 JavaScript 錯誤，並依國家、瀏覽器與裝置分析
- C. 把 X-Ray sampling rate 調到 100%，分析所有搜尋請求的後端 trace
- D. 對 CloudFront 的 `4xxErrorRate` 建立 anomaly detection alarm

> [!answer]- 答案：B
> **A ✗** 增加 canary 地點能補一部分外部視角，但 canary 走的是固定腳本、固定瀏覽器，無法反映真實使用者多樣的裝置、瀏覽器與網路環境，也無法回答「哪些使用者受影響」。
>
> **B ✓** RUM 從真實使用者的瀏覽器收集頁面載入時間、Core Web Vitals、資源與 HTTP 錯誤、JavaScript 錯誤，並可依國家、瀏覽器、裝置切分，正好回答受影響族群與問題出在前端或後端。
>
> **C ✗** 後端 p99 只有 400 毫秒，問題很可能不在後端；X-Ray 看不到瀏覽器端的資源下載與 JavaScript 執行時間，取樣 100% 只會增加成本。
>
> **D ✗** 抱怨是「很慢」而不是錯誤；4xx 錯誤率無法反映頁面載入速度。
>
> **考點**：SAP-3.3、SAP-3.1｜CloudWatch RUM 與 Synthetics 的差異
