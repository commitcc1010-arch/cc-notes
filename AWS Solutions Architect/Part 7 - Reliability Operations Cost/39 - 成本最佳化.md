# 第 39 章　成本最佳化：計價模型、購買方式與成本治理

>

## 39.1 故事：帳單三個月翻了三倍

Wanderly 的月帳單在三個月內從 2 萬美元漲到 6 萬美元。訂房量只成長了 40%，財務長在週會上問了三個問題：錢花到哪裡去了？是哪個團隊花的？下個月會是多少？沒有人答得出來。

平台團隊花了一週翻帳單，找到一連串「每個都不大，加起來很驚人」的項目：

- 影像處理 worker 在 private subnet 每天從 S3 讀寫數 TB 照片，全部經過 NAT Gateway，光是 NAT 的資料處理費就占了帳單的 12%。
- 搜尋服務和它的快取叢集分散在不同 AZ，彼此之間每秒都在交換資料，跨 AZ 傳輸費持續累積。
- 開發與 staging 環境的 EC2 和 RDS 24 小時開著，但工程師只在白天使用。
- Production 的 instance 平均 CPU 使用率 8%，當初「保險起見」選了大兩號的規格。
- 所有 EBS volume 都還是 gp2；還有 3 TB 已經沒有掛載任何 instance 的 volume，和兩年前的舊 snapshot。
- 穩定運作的 baseline 全部用 On-Demand 價格支付。
- 沒有任何 tag，所以無法回答「是哪個團隊花的」。

這一章依序處理這些問題：先理解 AWS 怎麼計價，特別是最容易被忽略的 data transfer；再談「同樣的資源怎麼買比較便宜」與「是不是真的需要這麼多資源」；最後建立讓成本可見、可歸屬、可控制的治理機制。

## 39.2 帳單從哪裡來：AWS 的計價模型

### 三大成本來源

AWS 採用 **pay-as-you-go（按用量付費）**：沒有預付的硬體成本，用多少付多少。但「用量」在不同服務有不同的計價維度。幾乎所有帳單都可以拆成三大類，再加上一類容易被忽略的請求費：

| 類別 | 計價維度 | 例子 |
|---|---|---|
| Compute（運算） | 執行時間 × 規格 | EC2 每秒計費、Lambda 依請求數與 GB-秒、Fargate 依 vCPU 與記憶體每秒 |
| Storage（儲存） | 每 GB-月 × 儲存類型 | S3 依 storage class、EBS 依 volume type 與佈建大小、snapshot 依實際使用量 |
| Data transfer（資料傳輸） | 每 GB × 傳輸路徑 | 到 Internet、跨 AZ、跨 Region、經 NAT Gateway |
| Requests／operations（請求） | 每千次或每百萬次 | S3 PUT／GET、API Gateway 請求、DynamoDB 讀寫單位、KMS API 呼叫 |

有三個觀念要先建立：

1. **佈建（provisioned）和使用（consumed）不同。** EBS 依「佈建的大小」收費，即使只寫了 10% 的資料；S3 依「實際存放的資料」收費。EC2 只要在 running 狀態就收費，不管 CPU 有沒有在跑。這就是為什麼閒置與過大的資源會浪費錢。
2. **停止不等於免費。** EC2 instance stop 後不收 compute 費，但掛著的 EBS volume、Elastic IP 等仍收費。
3. **資料移動要付錢，而且常常比想像中多。** 這是下一節的主題。

### Well-Architected 的成本最佳化原則

Well-Architected Framework 的 **Cost Optimization pillar**（成本最佳化支柱）提出五個設計原則，本章的結構就是依照它們展開：

| 設計原則 | 白話 | 本章對應 |
|---|---|---|
| Implement cloud financial management | 建立成本管理的組織能力與流程 | 39.9、39.10 |
| Adopt a consumption model | 只為用到的部分付費，不用就關掉 | 39.6 排程關機、serverless |
| Measure overall efficiency | 看「每筆業務的成本」而不只總額 | 39.10 unit economics |
| Stop spending money on undifferentiated heavy lifting | 用受管服務取代自己維運 | 39.8 |
| Analyze and attribute expenditure | 知道錢花在哪、歸屬給誰 | 39.9 tags 與 CUR |

> [!note] 估算工具
> 架構還沒上線前，用 **AWS Pricing Calculator** 依預期用量估算每月成本，並可匯出估算結果分享給財務。它只是估算；真實帳單以實際用量為準。

## 39.3 Data transfer：每一條路徑都要問「收不收費」

Data transfer 是 AWS 帳單中最容易被低估的項目，因為它不對應任何一個你「建立」的資源，而是資料在資源之間流動時產生的。規則看似複雜，其實可以用一個原則記住：**資料留在越小的範圍內越便宜；跨出邊界（AZ、Region、AWS 本身）就開始收費；經過受管的網路設備（NAT Gateway、Transit Gateway、interface endpoint）還要另付處理費。**

### 一張圖看懂各路徑

```text
                                   Internet 使用者
                                   ▲          │
                         ⑨ 收費    │          │ ① 免費（流入 AWS）
                       （依 GB 分級）│          ▼
   ┌──────────── Region A（東京）─────────────────────────────────────────────┐
   │                                                                         │
   │   [CloudFront] ◄── ⑧ 免費（S3／ALB 等 AWS origin 到 CloudFront）        │
   │       │ ⑧' 收費（CloudFront 到使用者，費率通常低於直接出 Internet）       │
   │                                                                         │
   │  ┌──── AZ-a ─────────────────┐        ┌──── AZ-c ──────────────────┐    │
   │  │ [EC2-1] ◄─② 免費─► [EC2-2]│◄─③ 收費─►│ [EC2-3]                    │    │
   │  │  （同 AZ、private IP）     │ （雙向各收）│                           │    │
   │  │    │                      │        │                            │    │
   │  │    │ ④ 處理費 + 時數費     │        │                            │    │
   │  │    ▼                      │        │                            │    │
   │  │ [NAT Gateway] ──► IGW ──► Internet（另計 ⑨ 的 Internet 傳出費）    │    │
   │  │    │                      │        │                            │    │
   │  │    │ ⑤ 免費               │        │                            │    │
   │  │    ▼                      │        │                            │    │
   │  │ [Gateway endpoint] ──► S3／DynamoDB（同 Region）                  │    │
   │  │ [Interface endpoint] ⑥ 每 AZ 時數費 + 每 GB 處理費                │    │
   │  └───────────────────────────┘        └────────────────────────────┘    │
   │                         │                                               │
   └─────────────────────────┼───────────────────────────────────────────────┘
                             │ ⑦ 收費（由來源 Region 傳出時計費；目的地流入不收）
                             ▼
                    ┌──── Region B（新加坡）────┐
                    │  S3 CRR 目的地、DR 環境     │
                    └────────────────────────────┘
```

逐條說明：

1. **從 Internet 流入 AWS：免費。** 使用者上傳照片到 S3、呼叫你的 API，流入方向不收傳輸費（但 S3 PUT 請求等仍各自計費）。
2. **同一個 AZ 內、使用 private IP：免費。** EC2 之間、EC2 到同 AZ 的 RDS，只要走 private IP 就不收傳輸費。注意：若經由 public IP 或 Elastic IP 通訊，即使兩台機器在同一個 AZ，也會依跨 AZ 的費率計費。
3. **同 Region、跨 AZ：收費，而且雙向各收一次。** 從 AZ-a 送 1 GB 到 AZ-c，傳出端和接收端各計一次（常見費率是每個方向每 GB 0.01 美元起）。VPC peering 也一樣：同 AZ 的 peering 流量免費，跨 AZ 依跨 AZ 費率計費。
4. **經過 NAT Gateway：每小時費用 + 每 GB 處理費**，不論方向、不論目的地是 Internet 還是同 Region 的 S3。若目的地是 Internet，還要再加上第 ⑨ 項的傳出費。
5. **經 Gateway endpoint 到同 Region 的 S3、DynamoDB：免費。** Gateway endpoint 本身也不收費，這是本章最經典的省錢手段。
6. **Interface endpoint（PrivateLink）：每個 AZ 每小時收費 + 每 GB 處理費。** 它通常比 NAT 的處理費便宜，但有固定的時數費，低流量時不一定划算。
7. **跨 Region：由來源 Region 傳出時收費**，目的地 Region 流入不收。S3 Cross-Region Replication、跨 Region 的 Aurora Global Database 複寫、跨 Region VPC peering 或 Transit Gateway peering 都屬於這一類。
8. **AWS origin 到 CloudFront：免費**（例如 S3、ALB、EC2 作為 origin 時，origin 送到 CloudFront edge 的流量不收傳輸費）。CloudFront 送到使用者要收費，但費率通常低於從 Region 直接送出，且有每月免費額度。
9. **從 AWS 傳出到 Internet：收費，依每月用量分級**，用量越大每 GB 單價越低。AWS 每月提供一定額度的免費傳出量（跨服務合計）。

其他常見路徑：

| 路徑 | 是否收傳輸費 | 備註 |
|---|---|---|
| 同 Region 的 EC2 ↔ S3（不經 NAT） | 免費 | 經 NAT 則有 NAT 處理費 |
| 同 Region 的 EC2 ↔ DynamoDB、SQS 等 Regional 服務 | 免費 | 同上 |
| S3 → Internet 下載 | 收費 | 可用 CloudFront 降低 |
| Transit Gateway | 每個 attachment 每小時 + 每 GB 處理費 | 處理費依送進 TGW 的資料計算 |
| Direct Connect 傳出 | 收費，但費率低於 Internet 傳出 | 傳入免費；另有 port 時數費 |
| RDS Multi-AZ 的同步複寫 | 免費 | 應用程式跨 AZ 連資料庫仍收跨 AZ 費 |
| Aurora 儲存層跨 AZ 複寫 | 免費 | 同上 |
| NLB 啟用 cross-zone load balancing | 跨 AZ 流量收費 | 第 10 章 |
| Public IPv4 位址 | 每個位址每小時收費 | 2024 年起，不論是否使用中 |

> [!warning] 常見誤解
> 「同一個 VPC 裡的流量都免費。」VPC 內同 AZ 的 private 流量才免費；跨 AZ 一樣收費。另一個誤解是「NAT Gateway 只對 Internet 流量收費」：只要經過 NAT Gateway 的位元組都要付處理費，包括到同 Region S3 的流量，這正是 Wanderly 影像 worker 的問題。

### 用 Wanderly 的影像 worker 算一次

影像 worker 每天經 NAT Gateway 讀寫 S3 共 5 TB，一個月約 150 TB。以 us-east-1 常見的 NAT 處理費每 GB 0.045 美元估算，光處理費就約 150,000 GB × 0.045 ≈ 6,750 美元／月（各 Region 價格不同、會調整，這裡只看量級）。加上 S3 gateway endpoint 後，這段流量完全不經過 NAT，處理費降為零，而 gateway endpoint 本身免費，程式也不需要修改。

這個計算說明了 data transfer 最佳化的方法：**先把每條路徑的「每月 GB 數 × 每 GB 單價」算出來，再找最大的項目。**

## 39.4 降低網路成本的手法

知道哪些路徑收費後，最佳化手法可以歸成幾類。

### 讓資料走免費或較便宜的路徑

- **S3 與 DynamoDB 用 gateway endpoint**（第 6 章）：私有 subnet 存取同 Region 的 S3、DynamoDB，不經 NAT。
- **其他 AWS 服務評估 interface endpoint**：例如 ECR、CloudWatch Logs、Secrets Manager 的大量流量。要算 break-even：interface endpoint 有「每個 AZ 每小時」的固定費用，若只有少量 API 呼叫，在多個 VPC、多個 AZ 都建 endpoint 反而比 NAT 貴。
- **ECR 映像拉取的細節**：ECR 的映像層實際存放在 S3。Private subnet 拉映像時，除了 ECR 的 `ecr.api` 與 `ecr.dkr` interface endpoint，還需要 S3 gateway endpoint，否則映像層的下載仍會走 NAT。
- **對外內容用 CloudFront**：origin 到 CloudFront 免費，CloudFront 快取命中時根本不需要回 origin，而且 CloudFront 到使用者的費率通常低於從 Region 直接傳出。

### 讓資料留在同一個 AZ

- **NAT Gateway 每 AZ 一台、各 AZ 走自己的 NAT**（第 5 章）：除了高可用，也避免 private subnet 的流量跨 AZ 去找另一個 AZ 的 NAT。
- **AZ affinity（同 AZ 優先）**：讓應用程式優先呼叫同 AZ 的下游服務或快取節點；例如 ElastiCache 的讀取導向同 AZ 的 replica、Kubernetes 使用 topology-aware routing。要和高可用取捨：不能為了省跨 AZ 費而把所有東西擠在一個 AZ。
- **聊天密集的叢集元件**：例如一個 batch 作業內部大量交換資料的節點，可以放在同一個 AZ（甚至 cluster placement group），把高可用交給「整個作業可以重跑」而不是跨 AZ 部署。

### 減少要傳的資料量

- 壓縮（HTTP gzip／Brotli、壓縮的資料檔格式）。
- 只取需要的欄位或範圍（S3 byte-range fetch、columnar 格式讓 Athena 少掃資料，第 30 章）。
- 快取：減少重複從遠端讀取（第 28 章）。

### 跨 Region 與 hybrid

- 跨 Region 複寫只複寫真正需要的資料（S3 replication 可以用 prefix 或 tag 篩選）。
- 大量往返地端的流量考慮 Direct Connect：DX 的傳出費率低於 Internet，對穩定的大流量更划算（第 8 章）。
- 集中式 egress 或 inspection（第 41 章）會讓流量多經過 Transit Gateway 與防火牆，各自產生處理費；設計時要把這些逐 hop 的費用算進去，與「每個 VPC 自己一台 NAT」的成本比較。

> [!tip] 考試提示
> 題目說「NAT Gateway 費用很高」→ 先看流量目的地：若是 S3／DynamoDB，用 gateway endpoint；若是其他 AWS 服務，評估 interface endpoint；若是 Internet 上的服務，才考慮減少流量或集中 egress。題目說「跨 AZ data transfer 費用高」→ 檢查是否每個 AZ 有自己的 NAT、是否能做 AZ affinity，但不能犧牲多 AZ 高可用。

網路的錢省下來後，帳單上最大的項目通常是 compute。下一節處理「同樣的 compute，怎麼買比較便宜」。

## 39.5 Compute 購買方式：同樣的機器，不同的價格

第 17 章介紹了 EC2 的各種購買方式；這裡從成本策略的角度把它們放在一起，回答「該買哪種、買多少」。

### On-Demand：彈性最大，單價最高

**On-Demand** 不需要任何承諾，按秒（Linux 等）或按小時計費，隨時開、隨時關。適合不可預測的短期需求、尖峰，以及還在觀察用量的新 workload。

### Savings Plans：承諾每小時花多少錢

**Savings Plans** 是一種承諾：「未來 1 年或 3 年，我每小時至少花 X 美元在某類運算上」，換取折扣。超出承諾的用量以 On-Demand 價格計費；未用滿承諾的部分仍要付費。付款方式有 All Upfront、Partial Upfront、No Upfront，預付越多、期限越長，折扣越大。

| 類型 | 適用範圍 | 最大折扣（相對 On-Demand） | 彈性 |
|---|---|---|---|
| **Compute Savings Plans** | EC2（任何 family、大小、Region、OS、tenancy）、Fargate、Lambda | 最高約 66% | 最高：換 family、換 Region、改用 containers 或 Lambda 都自動適用 |
| **EC2 Instance Savings Plans** | 指定 Region 的指定 instance family（例如東京的 m7g），大小、OS、tenancy 可變 | 最高約 72% | 中：family 與 Region 固定 |
| **SageMaker Savings Plans** | SageMaker AI 的運算用量 | 最高約 64% | 僅限 SageMaker |

Savings Plans 的折扣會**自動套用**到符合條件的用量上，不需要指定 instance。在 Organizations 的 consolidated billing 下，折扣預設可以在帳號之間共享。

### Reserved Instances：承諾特定的 instance 屬性

**Reserved Instances（RI）** 是較早的承諾方式：承諾 1 或 3 年使用某種 instance 屬性（instance type、platform、tenancy、Region 或 AZ）。

| 屬性 | Standard RI | Convertible RI |
|---|---|---|
| 最大折扣 | 最高約 72% | 最高約 66% |
| 能否換成不同 family／OS | 不能（同 family 內可修改大小等部分屬性） | 可以 exchange 成等值或更高價值的其他 Convertible RI |
| 能否在 RI Marketplace 賣出 | 可以 | 不可以 |

RI 的 **scope（範圍）** 影響很大：

- **Regional RI**：折扣套用到該 Region 任一 AZ 的符合用量；Linux 等平台在同 family 內有大小彈性（例如一個 `m5.xlarge` 的 RI 可以抵兩個 `m5.large`）。**不保留容量。**
- **Zonal RI**：綁定特定 AZ，**同時保留該 AZ 的容量**，但沒有大小彈性。

除了 EC2，RDS、ElastiCache、OpenSearch Service、Redshift 也有 reserved 計價（DynamoDB 則是 reserved capacity），這是資料庫降低 baseline 成本的主要方式。

> [!note] 套用順序
> 同一筆用量同時符合多種承諾時，AWS 先套用 Reserved Instances，再套用 Savings Plans；Savings Plans 之間先套用 EC2 Instance Savings Plans，再套用 Compute Savings Plans。

### Savings Plans 與 RI 怎麼選

新的 EC2 承諾，多數情況選 **Savings Plans**：管理簡單、自動套用。

- 預期會換 instance family、換 Region、或從 EC2 搬到 Fargate／Lambda → **Compute Savings Plans**。
- 確定長期使用某個 family 且 Region 固定，想要更多折扣 → **EC2 Instance Savings Plans**（或 Standard RI）。
- 需要**保留特定 AZ 的容量**並享折扣 → Zonal RI，或 **On-Demand Capacity Reservation** 搭配 Savings Plans。
- RDS、ElastiCache、Redshift、OpenSearch → 該服務的 reserved 計價（引擎或規格可能變動的資料庫用量，也可評估彈性較高、折扣較低的 Database Savings Plans）。

> [!note] 承諾類型持續增加：Database Savings Plans
> AWS 於 2025 年底推出 **Database Savings Plans**：承諾 1 年、No Upfront，對 Aurora、RDS、DynamoDB、ElastiCache、DocumentDB、Neptune、Keyspaces、Timestream、DMS、OpenSearch Service 等資料庫用量提供最高約 35% 的折扣，而且不論引擎、instance family、大小或 Region 都適用（例如從 RDS for Oracle 遷到 Aurora PostgreSQL 仍保有折扣）。同一筆用量不能同時套用 RDS RI 或 DynamoDB reserved capacity。它的折扣低於資料庫 RI，但彈性高得多。這是較新的服務，舊考題與多數教材仍以 Compute、EC2 Instance、SageMaker 三種 Savings Plans 與資料庫 RI 為主；實際購買前請在 Billing and Cost Management 確認現行條款。

### Spot Instances：用別人沒用的容量

**Spot Instances** 使用 AWS 暫時閒置的 EC2 容量，價格最高可比 On-Demand 低約 90%。代價是 AWS 需要容量時可以收回：收回前會發出 **2 分鐘的中斷通知**（instance metadata 與 EventBridge 都能收到），另外還可能提前發出 **rebalance recommendation**（容量風險升高的提示）。現在的 Spot 不需要出價，價格依長期供需緩慢變動。

適合 Spot 的工作有共同特徵：**可以被中斷而不造成損失**。

- 批次處理、影像轉檔、CI 建置：任務可以重試，最好有 checkpoint。
- 無狀態的 web 或 API 節點：在 ASG 中與 On-Demand 混用，被收回的節點由 ALB 移除。
- 大數據與 ML 訓練：EMR、SageMaker managed Spot training 有內建的中斷處理。
- Containers：ECS capacity provider、EKS（Karpenter）都能混用 Spot。

不適合：資料庫、單一不能中斷的長時間作業、需要固定主機的授權軟體。

使用 Spot 的關鍵設定：

- **多樣化**：在 ASG 的 mixed instances policy 或 EC2 Fleet 中列出多種 instance type 與多個 AZ，容量來源越多，被同時收回的機會越低。
- **Allocation strategy**：建議使用 `price-capacity-optimized`，在低價與容量充足之間取得平衡。
- **處理中斷**：收到通知後把任務還回 queue、從 Load Balancer 移除、儲存 checkpoint；ASG 可開啟 Capacity Rebalancing 提前補位。

### Capacity Reservation：保證有容量，但不是折扣

**On-Demand Capacity Reservation** 在指定 AZ 為指定 instance type 保留容量。立即生效的 Capacity Reservation 不需要任何期限承諾，可隨時建立或取消；若擔心到時候建不出來，也可以提前 5–120 天申請 **future-dated** Capacity Reservation，但它要求最少承諾期（多數 instance type 為 14 天），承諾期內取消可能有費用。它**本身不提供折扣**，不論是否有 instance 在用都以 On-Demand 價格計費；但可以搭配 Regional RI 或 Savings Plans 降低費用。適合大型活動、DR 演練、必須確保能開出機器的關鍵 workload。

### 分層購買策略

```text
  用量
   ▲
   │        ┌──┐      ┌──┐              ← 不可預測的尖峰：On-Demand
   │   ┌────┘  └──┐ ┌─┘  └───┐          （或可中斷的部分用 Spot）
   │───┘ ░░░░░░░░ └─┘ ░░░░░░ └────────  ← 可中斷的批次與彈性容量：Spot
   │ ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
   │▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  ← 穩定 24/7 的 baseline：
   │▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓    Savings Plans／RI
   └──────────────────────────────────────► 時間
```

最底層是整天都在跑的 baseline，用 Savings Plans 或 RI 覆蓋；中間層是可中斷的工作，用 Spot；最上層是不可預測的尖峰，用 On-Demand。

承諾要買多少？不要以尖峰或平均值為準，而是以**長期穩定的最低用量**為準，並且**先 rightsizing 再承諾**：如果先買了 3 年的大規格承諾，之後才發現機器可以縮小一半，承諾的錢已經付出去了。Cost Explorer 會依過去用量提供 Savings Plans 購買建議，並報告兩個指標：

- **Coverage（覆蓋率）**：符合條件的用量中，有多少比例被承諾折扣覆蓋。太低代表還有很多 On-Demand 可以轉成承諾。
- **Utilization（使用率）**：買下的承諾中，有多少比例真正被用到。低於 100% 代表買太多，多出的部分在浪費。

## 39.6 Rightsizing：先確定真的需要這麼多

購買方式解決的是「單價」，rightsizing 解決的是「數量與規格」。**Rightsizing（調整到合適規格）** 是依實際使用量，把資源調整到能滿足效能需求的最小規格或最合適的類型。

### 要看哪些指標

只看 CPU 平均值會做出錯誤決策。完整的 rightsizing 至少要看：

- **CPU**：看尖峰與 p95／p99，而不只是平均。
- **記憶體**：EC2 預設**不會**回報記憶體使用率，必須安裝 **CloudWatch agent**（第 36 章）才能取得。沒有記憶體資料就縮小規格，可能導致 OOM。
- **網路與 EBS 頻寬**：較小的 instance type 網路與 EBS 頻寬上限也較低。
- **觀察期間**：要涵蓋業務週期，例如月底結帳、促銷活動。

### AWS Compute Optimizer

**AWS Compute Optimizer** 用機器學習分析資源的 CloudWatch 指標，提供 rightsizing 建議並把每個資源標示為 Under-provisioned、Over-provisioned 或 Optimized。支援的資源包括 EC2 instance、Auto Scaling group、EBS volume、Lambda 函式、Fargate 上的 ECS service、RDS 與 Aurora 資料庫，以及部分商業軟體授權。

關鍵設定：

- **Opt-in**：需要先啟用，可在 Organizations 的管理帳號或 delegated administrator 為所有成員帳號啟用。
- **Lookback 期間**：預設分析過去 14 天的指標；啟用付費的 **enhanced infrastructure metrics** 可以延長到 93 天，適合有月度或季度週期的 workload。
- **記憶體指標**：安裝 CloudWatch agent 後，Compute Optimizer 才能把記憶體納入建議，否則建議只依 CPU 等指標。
- 建議會包含換成其他 family 的選項，例如換成 **Graviton**（AWS 自研的 ARM 處理器，通常有更好的性價比），但應用程式必須支援 ARM 架構。

> [!warning] 常見誤解
> 「Compute Optimizer 說可以縮小，就直接縮小。」建議是根據過去的指標推算，不保證未來的效能。正確做法是在非尖峰時段變更一部分機器（或在 staging 先驗證），觀察延遲與錯誤率等 SLO 指標，再全面套用；ASG 則更新 launch template 並用 instance refresh 滾動替換。

### Cost Optimization Hub

**Cost Optimization Hub** 把 Compute Optimizer 的 rightsizing、閒置資源、Graviton 遷移、Savings Plans／RI 購買等建議彙整在同一個地方，跨帳號、跨 Region 依預估節省金額排序，並避免同一筆節省被重複計算（例如先 rightsizing 再買承諾時，承諾建議會依縮小後的用量計算）。它是「這個月該先做哪件事」的起點。

### 不用就關掉

- **排程關機**：開發與測試環境只在上班時間開。可用 EventBridge Scheduler 搭配 Systems Manager Automation（第 38 章）、ASG 的 scheduled scaling，或 AWS 提供的 Instance Scheduler 解決方案。一週 168 小時中只開 50 小時，就省下約七成的 compute 費用。
- **RDS 可以暫時停止**：最長 7 天，之後會自動啟動；停止期間不收 instance 費，但儲存仍收費。長期不用的資料庫應改為 snapshot 後刪除。
- **閒置資源**：沒有掛載的 EBS volume、沒有關聯的 Elastic IP、沒有流量的 Load Balancer、閒置的 NAT Gateway。Trusted Advisor 與 Compute Optimizer 都能找出這些項目。
- **改用彈性架構**：用 Auto Scaling 跟著需求伸縮（第 18 章），或把間歇性工作改成 Lambda、Fargate 這類按實際執行時間計費的服務。

## 39.7 Storage 成本：放對地方、放對時間

### S3

S3 的成本由 storage class、請求數、取回費與傳輸費組成。第 23 章已詳細比較各 storage class；成本最佳化的重點是：

- **依存取模式選 storage class**：存取模式明確時，用 **lifecycle rule** 依物件年齡轉換（例如 30 天後轉 Standard-IA、180 天後轉 Glacier Deep Archive）。注意 IA 與 Glacier 類別有**最短存放天數**與**每次取回費**，經常被讀取的資料放進去反而更貴。
- **存取模式不明確時用 S3 Intelligent-Tiering**：自動在存取層之間移動物件，沒有取回費；但每個物件有小額的監控與自動化費用。小於 128 KB 的物件不收監控費，也不會被自動移到低頻層。
- **清理看不見的資料**：
  - 未完成的 multipart upload 碎片會一直計費，用 lifecycle 的 `AbortIncompleteMultipartUpload` 清除。
  - 開啟 versioning 後，舊版本（noncurrent versions）也計費，用 `NoncurrentVersionExpiration` 設定保留期限。
- **小物件的轉換成本**：lifecycle 轉換每個物件都有請求費，大量小物件轉到低頻類別可能不划算；S3 lifecycle 預設不會轉換小於 128 KB 的物件。
- **S3 Storage Lens** 提供組織層級的用量與成本最佳化建議，例如找出有大量未完成 multipart upload 或沒有 lifecycle rule 的 bucket。

```json
{
  "Rules": [
    {
      "ID": "photos-tiering-and-cleanup",
      "Status": "Enabled",
      "Filter": { "Prefix": "photos/" },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
```

這份 lifecycle 設定可以用 `aws s3api put-bucket-lifecycle-configuration --bucket wanderly-photos --lifecycle-configuration file://lifecycle.json` 套用：照片 30 天後轉 Standard-IA、一年後轉 Deep Archive，舊版本 30 天後刪除，7 天未完成的 multipart upload 自動清除。

### EBS

- **gp2 → gp3**：gp3 每 GB 價格比 gp2 低約 20%，而且不論容量大小都有 3,000 IOPS 與 125 MiB/s 的 baseline 效能，需要更多時可以獨立加購 IOPS 與 throughput。gp2 的 IOPS 和容量綁在一起（每 GB 3 IOPS），很多人為了 IOPS 而買大容量。可以用 Elastic Volumes **線上修改** volume type，不需要停機。
- **刪除未掛載的 volume**：instance 終止時，若 volume 的 `DeleteOnTermination` 為 false，volume 會留下來繼續計費。
- **Snapshot 管理**：snapshot 是增量的，但長期累積仍可觀。用 **Amazon Data Lifecycle Manager** 或 AWS Backup（第 34 章）自動建立與刪除；長期保存但很少還原的 snapshot 可以移到 **snapshot archive tier**，儲存費約低 75%，但最短保存 90 天、還原需要 24–72 小時。
- **選對 volume type**：大量循序讀寫（log、資料倉儲）可以考慮 st1；很少存取的冷資料考慮 sc1；不要讓一般 workload 使用 io2，除非真的需要高 IOPS 與高耐久度。

### EFS 與 FSx

EFS 依實際存放量計費，開啟 lifecycle management 把一段時間沒存取的檔案移到 Infrequent Access 或 Archive storage class；FSx 選擇 HDD 儲存、啟用 data deduplication（FSx for Windows）或使用 S3 整合的分層（FSx for Lustre、ONTAP）都能降低成本（第 24 章）。

## 39.8 Database 成本：選對計價模式

### Aurora：Standard 還是 I/O-Optimized

Aurora 有兩種儲存計價配置：

| 配置 | 計費方式 | 適合 |
|---|---|---|
| **Aurora Standard** | instance + 儲存 + **每百萬次 I/O 請求** | I/O 量低到中等 |
| **Aurora I/O-Optimized** | instance 與儲存單價較高，但 **I/O 不另外收費** | I/O 密集；I/O 費用超過 Aurora 總費用約 25% 時 |

I/O-Optimized 的價值在於可預測：I/O 突增不會讓帳單暴衝。兩種配置可以切換（從 Standard 切到 I/O-Optimized 每 30 天限一次）。

### Serverless 與按需容量

- **Aurora Serverless v2** 以 **ACU（Aurora Capacity Unit）** 為單位，依負載以小幅度自動伸縮，按實際使用的 ACU 秒計費。在支援的引擎版本上可設定最小 ACU 為 0，閒置一段時間後自動暫停（暫停期間不收運算費，只收儲存費；恢復需要數秒）適合開發環境與間歇性 workload。穩定高負載的資料庫，固定 instance 加 reserved 計價通常更便宜。
- **DynamoDB capacity mode**（第 27 章）：流量不可預測或很低時用 **on-demand**；流量穩定可預測時用 **provisioned + auto scaling**，並可購買 reserved capacity。若儲存成本是主要支出、讀寫不頻繁，可使用 **Standard-IA table class**。用 **TTL** 自動刪除過期資料，刪除不消耗寫入容量。

### 其他常見的資料庫成本項目

- **讀取擴展的選擇**：增加 read replica 會多一份 instance 費用；若讀取高度重複，加快取（ElastiCache 或 DAX）可能用更低成本吸收更多讀取（第 28 章）。
- **備份與快照**：自動備份在保留期內，與資料庫大小相同的備份儲存量不另收費，超出部分與手動 snapshot 依量計費；過期的手動 snapshot 要清理。
- **RDS Extended Support**：資料庫引擎主要版本結束標準支援後，若不升級，AWS 會自動納入 Extended Support 並收取額外費用。升級規劃也是成本管理的一部分。
- **授權**：Oracle、SQL Server 的授權費常占資料庫成本的大部分；評估 BYOL 或改用開源引擎（Aurora PostgreSQL／MySQL）能大幅降低成本（第 29、44 章）。
- **停用的資料倉儲**：Redshift provisioned cluster 可以 pause；用量不穩定時評估 Redshift Serverless（第 30 章）。

### 受管服務的總成本

「EC2 上自己裝 MySQL 比 RDS 便宜」只看了 instance 單價。總持有成本（TCO）還包含：備份、patch、高可用架構、監控、故障處理的人力時間。Well-Architected 的「不要把錢花在無差異化的繁重工作上」正是指這一點：受管服務把這些工作交給 AWS，通常讓總成本更低。

到這裡，Wanderly 已經知道「怎麼省」。但要讓節省持續發生，需要先「看得見」。

## 39.9 看見成本：Cost Explorer、Budgets、Anomaly Detection 與 Data Exports

### Cost Explorer：互動式查詢帳單

**AWS Cost Explorer** 是 Billing and Cost Management 中的視覺化分析工具：

- 依服務、帳號、Region、usage type、tag、cost category 篩選與分組，檢視日或月粒度的成本趨勢（可另外啟用小時粒度）。
- **預測**未來成本。
- **RI 與 Savings Plans 報告**：coverage、utilization，以及依過去用量計算的購買建議。
- 可選擇不同的成本呈現方式，例如 unblended（實際費率）、amortized（把預付款攤提到每天）、net（扣除折扣後）。要看「每天實際消耗多少」時，amortized 比較能反映預付承諾的真實成本。

### AWS Budgets：預算與告警

**AWS Budgets** 讓你設定預算並在超過或「預測將超過」門檻時通知：

- **預算類型**：cost budget、usage budget、Savings Plans 與 RI 的 utilization／coverage budget。
- **範圍**：可以篩選帳號、服務、tag、cost category，例如「staging 帳號每月 3,000 美元」。
- **通知**：email、SNS topic，或聊天工具整合。
- **Budget actions**：達到門檻時自動（或經核准後）執行動作：套用一個 IAM policy（例如禁止建立新 instance）、套用 SCP 到某個帳號或 OU，或停止指定的 EC2 或 RDS instance。

要注意，Budgets 依帳單資料評估，帳單資料每天更新數次，**不是即時的**。它適合「本月花費趨勢超標」的控制，不能當作即時阻止花費的開關。

### Cost Anomaly Detection：找出異常

**AWS Cost Anomaly Detection** 用機器學習學習你的正常支出模式，偵測異常增加並分析可能的根因（哪個服務、帳號、Region、usage type）。你建立 **monitor**（監控範圍，可以是所有 AWS 服務、特定 linked account、cost category 或 cost allocation tag），再設定 **alert subscription**（以 email 或 SNS 發送個別告警或每日／每週摘要，可設定金額或百分比門檻）。

它和 Budgets 的差別：Budgets 回答「是否超過我設定的數字」；Anomaly Detection 回答「這是否不像平常的模式」。一個每月 20 萬美元的帳號，某個服務突然多出每天 500 美元，可能遠低於預算門檻，但 Anomaly Detection 會發現。

### Data Exports 與 Cost and Usage Report

**AWS Cost and Usage Report（CUR）** 是最詳細的帳單資料：每個資源、每小時（或每天）、每一個 usage type 的用量與費用，包含 tag、RI／Savings Plans 套用情形。現在透過 **Data Exports** 建立 **CUR 2.0** 匯出，把資料以 Parquet 等格式定期送到 S3，可以選擇欄位、包含 resource ID。Data Exports 也支援 FOCUS 格式（跨雲的開放帳單資料規格）與成本最佳化建議的匯出。

CUR 本身只是資料；常見做法是用 **Athena** 直接查詢 S3 上的 CUR，再用 **QuickSight** 建立儀表板（第 30 章）。當 Cost Explorer 的分組方式不夠用、需要和公司內部資料（例如訂房數）結合計算時，就用 CUR。

### Cost allocation tags：知道是誰花的

**Cost allocation tags** 是被啟用為「帳單分組維度」的 tag。分兩種：

- **User-defined tags**：你自己加的 tag，例如 `CostCenter=search`、`Team=payments`。
- **AWS-generated tags**：AWS 自動加的，例如 `aws:createdBy`（記錄建立資源的身份）。

關鍵規則：

1. Tag 必須在**管理帳號（payer account）的 Billing console 中啟用**，才會出現在 Cost Explorer、Budgets 與 CUR 的分組中。
2. 新加的 tag key 可能要等最多約 24 小時才會出現在可啟用的清單中。
3. 啟用後才開始在帳單資料中出現；對啟用前的歷史資料，可以申請 **backfill**（回填過去最多 12 個月）。
4. 並非所有資源與費用都能 tag（例如部分 data transfer 費用），所以完全依 tag 分攤時，會有一部分「未分配」的成本，需要規則處理。

在 Organizations 中，**帳號本身就是最可靠的成本邊界**：每個團隊或產品一個帳號，成本天然分開，不依賴每個資源都 tag 正確。Tag 用來在帳號內做更細的分攤。強制 tag 一致性的方法（tag policies、SCP 要求建立時帶 tag）在第 14、43 章說明。

### Cost categories 與 split cost allocation

- **Cost categories** 用規則把帳號、tag、服務等組合映射成業務類別，例如「搜尋產品線 = 帳號 A + 帳號 B + `Product=search` 的資源」。它支援 **split charges**：把共用成本（例如共用的網路帳號、支援方案費用）依比例分攤到各類別。
- **Split cost allocation data** 針對 ECS 與 EKS：多個團隊的 container 共用同一批 EC2 時，依每個 task／pod 的 CPU 與記憶體保留量，把 EC2 成本分攤到各個 container，並出現在 CUR 中。

## 39.10 成本治理：showback、chargeback 與持續改善

### Showback 與 chargeback

- **Showback（成本展示）**：讓各團隊看到自己花了多少，但不實際從預算扣款。目的是建立成本意識。
- **Chargeback（成本計費）**：把成本實際計入各團隊或事業單位的預算。需要更精確的分攤規則，以及各方同意的共用成本計算方式。

多數公司從 showback 開始：先讓每個團隊每週看到自己的成本與趨勢，再逐步進到 chargeback。

### AWS Billing Conductor：自訂的帳單視圖

**AWS Billing Conductor** 讓管理帳號建立 **billing groups**（把帳號分組），並套用 **pricing rules**（例如在 AWS 公開價格上加成或折扣）與 **custom line items**（例如分攤共用的支援費用或平台費用），產生每個群組的 **pro forma（模擬）帳單**。它**不會改變**你實際付給 AWS 的金額，只改變各群組看到的成本。

典型用途：

- AWS 經銷商或 MSP 要依自己的價格向客戶開帳。
- 企業內部 chargeback 時，不希望把 Savings Plans 折扣的好處分給某些團隊，而是讓各團隊以公開價格計費，折扣留在中央；或把平台團隊的成本以固定費用分攤。

### 從總額到單位成本

財務長的第三個問題「下個月會是多少」背後，其實是在問「成本成長是否合理」。**Unit economics（單位經濟）** 把成本除以業務指標，例如「每筆訂房的雲端成本」「每千次搜尋的成本」。總成本成長 40% 而訂房量成長 60%，代表效率在提升；反過來就是警訊。用 CUR 加上業務資料計算單位成本，是成熟成本治理的核心指標。

### Wanderly 的成本治理流程

```text
 ① 看見                    ② 歸屬                     ③ 最佳化                  ④ 控制
 Cost Explorer          帳號邊界 + tags            Cost Optimization Hub      Budgets（含 actions）
 CUR 2.0 → Athena       cost categories            Compute Optimizer          Cost Anomaly Detection
 QuickSight 儀表板       split cost allocation      endpoints、gp3、lifecycle   SCP／tag policies
        │                      │                    Savings Plans（最後買）           │
        └──────────────────────┴──────────┬──────────────┴────────────────────────┘
                                          ▼
                         ⑤ 每週成本檢討：前 10 大成本變化、單位成本趨勢、
                            行動項目（owner + 期限），回到 ①
```

① 先讓所有人看得到同一份資料。② 把成本歸屬到團隊與產品，showback 給各團隊。③ 依預估節省金額排序最佳化項目：先處理浪費（閒置、過大、錯誤的傳輸路徑），**最後才買承諾**，因為承諾應該建立在最佳化後的用量上。④ 用預算與異常偵測及早發現問題，用 SCP 與 tag policy 防止不受控的支出。⑤ 固定節奏的檢討讓這個循環持續運作。

Wanderly 執行三個月後的結果：S3 gateway endpoint 消除了大部分 NAT 處理費；dev／staging 排程關機；production 依 Compute Optimizer 建議縮小規格並部分換成 Graviton；EBS 全部改 gp3、刪除未掛載的 volume；最後以縮小後的 baseline 購買 Compute Savings Plans。月帳單回到 3 萬美元以下，而每筆訂房的成本比半年前還低。

## 39.12 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| NAT Gateway 費用高、流量多到 S3／DynamoDB | Gateway VPC endpoint（免費） |
| Private subnet 拉 ECR 映像經 NAT 很貴 | ECR interface endpoints（`ecr.api`、`ecr.dkr`）+ S3 gateway endpoint |
| 跨 AZ data transfer 費用高 | 每 AZ 一台 NAT、AZ affinity；不能犧牲多 AZ |
| 全球使用者下載 S3 內容、傳出費用高 | CloudFront（origin 到 CloudFront 免費、快取減少回源） |
| 穩定 baseline、會改 instance family 或用 Fargate／Lambda | Compute Savings Plans |
| 穩定使用同一 family、同一 Region，要最大折扣 | EC2 Instance Savings Plans 或 Standard RI |
| 可中斷的批次、彈性工作、最低成本 | Spot（多樣化、處理 2 分鐘通知） |
| 需要保證某 AZ 有容量 | On-Demand Capacity Reservation（或 zonal RI） |
| 平均 CPU 很低、想縮小規格 | Compute Optimizer；記憶體需 CloudWatch agent |
| gp2 volume 成本高、IOPS 需求不大 | 線上改成 gp3 |
| I/O 費用占 Aurora 帳單很大比例 | Aurora I/O-Optimized |
| 開發環境只在上班時間使用 | 排程停止 EC2／RDS，或 Aurora Serverless v2 |
| 超過預算時自動限制 | Budgets actions（IAM policy、SCP、停止 instance） |
| 偵測不尋常的支出增加 | Cost Anomaly Detection |
| 最詳細的帳單資料、用 SQL 分析 | Data Exports（CUR 2.0）→ S3 → Athena |
| Tag 已加但 Cost Explorer 看不到 | 在管理帳號啟用 cost allocation tags |
| 依自訂價格產生內部或客戶帳單 | AWS Billing Conductor |
| 共用 EKS／ECS 叢集的成本分攤 | Split cost allocation data |

**常見陷阱**：

1. 以為 Savings Plans 或 Regional RI 會保留容量：只有 zonal RI 與 Capacity Reservation 會保留容量。
2. 以為 Capacity Reservation 有折扣：它以 On-Demand 價格計費，折扣要另外靠 Savings Plans 或 Regional RI。
3. 先買 3 年承諾再 rightsizing：承諾應建立在最佳化後的穩定 baseline 上。
4. 把 Budgets 當成即時阻止支出的機制：帳單資料每天更新數次，有延遲。
5. 以為同 VPC 的流量都免費、NAT 只對 Internet 流量收費：跨 AZ 收費，所有經過 NAT 的流量都收處理費。
6. 為了省跨 AZ 費用把所有資源放在單一 AZ：題目若同時要求高可用，這是錯誤答案。

## 39.13 SAP 加深：組織層級的成本策略

### 承諾在組織中的共享

在 Organizations 的 consolidated billing 下：

- 所有成員帳號的用量合併計算，享有用量分級的價格（例如 S3 與 data transfer 的量級折扣）。
- RI 與 Savings Plans 的折扣預設會在帳號之間共享：某帳號沒用到的承諾，會自動套用到其他帳號的符合用量。
- 管理帳號可以對特定帳號**關閉 RI 與 Savings Plans 折扣共享**。關閉後，該帳號的承諾只套用到自己，也不會接收其他帳號的折扣。這常用在需要獨立計算成本的子公司，或合約要求成本獨立的帳號。

承諾的購買策略：很多企業由中央 FinOps 團隊在一個專用帳號（或管理帳號）集中購買 Savings Plans，以整體 baseline 計算承諾量，讓折扣在組織內流動，達到最高的使用率；再用 Billing Conductor 或 cost categories 決定折扣如何分配給各團隊。各團隊自行購買則容易買重或買錯，整體使用率較低。

### 預防不受控的支出

- **SCP** 限制只能使用核准的 Region（同時滿足資料主權，第 43 章）、禁止啟動特別昂貴的 instance family、禁止購買承諾（只讓中央帳號購買）。
- **Budgets actions** 對沙盒帳號在超過預算時套用 SCP，阻止新建資源。
- **Tag policies** 與建立時要求 tag 的 SCP，讓成本歸屬資料可靠。

### 架構層級的成本取捨

SAP 題目經常要求在可用性、效能與成本之間做取捨：

- **集中式 egress 或 inspection**：省下每個 VPC 的 NAT Gateway 時數費，但增加 Transit Gateway 處理費與跨 AZ 流量；VPC 數量多、每個 VPC 流量少時通常較划算。
- **多 Region DR 策略**：backup & restore、pilot light、warm standby、active-active 的成本差異很大（第 34 章）。選擇能滿足 RTO／RPO 的最低成本策略，而不是預設最昂貴的 active-active。
- **跨 Region 複寫的資料量**：每 GB 都要付跨 Region 傳輸費，只複寫真正需要 DR 的資料。
- **從自管遷移到受管或 serverless**：計算總持有成本，包含人力與授權（第 44、46 章）。

### 成本可視化的企業架構

大型組織的標準做法是：CUR 2.0 匯出到集中的 S3 bucket，用 Athena 查詢、QuickSight 建立各層級（公司、事業單位、團隊）的儀表板；cost categories 定義業務分類與共用成本分攤；每個帳號設定 Budgets，並在組織層級設定 Cost Anomaly Detection monitor。完整的治理設計在第 43 章說明。

## 本章重點整理

- AWS 帳單主要由 compute、storage、data transfer 與請求費用組成；佈建型資源（EC2、EBS）即使閒置也持續計費。
- 從 Internet 流入 AWS 免費；傳出到 Internet 收費並依用量分級。
- 同 AZ 內以 private IP 通訊免費，跨 AZ 雙向各收費；經 public IP 通訊即使在同 AZ 也要收費。
- 跨 Region 傳輸由來源 Region 傳出時收費；AWS origin 到 CloudFront 免費，CloudFront 到使用者的費率通常較低。
- NAT Gateway 收時數費與所有經過流量的處理費；S3 與 DynamoDB 用免費的 gateway endpoint，其他服務評估 interface endpoint 的 break-even。
- Compute Savings Plans 彈性最高（EC2 任何 family 與 Region、Fargate、Lambda），EC2 Instance Savings Plans 與 Standard RI 折扣較高但綁定 family 與 Region。
- Savings Plans 與 Regional RI 不保留容量；需要容量保證用 On-Demand Capacity Reservation 或 zonal RI，Capacity Reservation 本身沒有折扣。
- Spot 最高可省約 90%，會在 2 分鐘通知後被收回，適合可中斷、可重試的工作，並要多樣化 instance type 與 AZ。
- 先 rightsizing 再購買承諾；承諾量以長期穩定的 baseline 為準，並以 coverage 與 utilization 追蹤。
- Compute Optimizer 依 CloudWatch 指標提供 rightsizing 建議，記憶體指標需要 CloudWatch agent，enhanced infrastructure metrics 可把 lookback 延長到 93 天。
- gp3 比 gp2 便宜且效能與容量脫鉤，可線上轉換；未掛載的 volume、舊 snapshot、未完成的 multipart upload 與舊版本物件都要清理。
- Aurora I/O-Optimized 適合 I/O 費用占比高的資料庫；Aurora Serverless v2 與 DynamoDB on-demand 適合變動或間歇的負載。
- Cost Explorer 看趨勢與承諾建議，Budgets 設定門檻與自動 actions（非即時），Cost Anomaly Detection 用機器學習找異常，Data Exports（CUR 2.0）提供最詳細的明細供 Athena 分析。
- Cost allocation tags 必須在管理帳號啟用才會出現在帳單分組中；帳號是最可靠的成本邊界，cost categories 與 split cost allocation data 處理共用成本。
- Billing Conductor 產生自訂價格的 pro forma 帳單，用於 chargeback 或經銷，不影響實際付給 AWS 的金額。

## 本章練習題

### 練習 39-1｜SAA｜單選｜判斷哪條路徑免費

Wanderly 正在檢視東京 Region 的網路成本。下列四種資料傳輸中，哪一種**不會**產生 data transfer 或資料處理費用？

- A. 位於 AZ-a 的 EC2 以 private IP 把資料送到位於 AZ-c 的 EC2
- B. Private subnet 的 EC2 經由 NAT Gateway 把檔案上傳到同 Region 的 S3 bucket
- C. Private subnet 的 EC2 經由 S3 gateway endpoint 從同 Region 的 S3 bucket 下載檔案
- D. 同一個 AZ 內的兩台 EC2 透過彼此的 Elastic IP 互相通訊

> [!answer]- 答案：C
> **A ✗** 同 Region 跨 AZ 的流量收費，而且傳出與接收兩端各收一次。
>
> **B ✗** 經過 NAT Gateway 的所有流量都要付每 GB 處理費，即使目的地是同 Region 的 S3。
>
> **C ✓** 同 Region 的 EC2 與 S3 之間不收傳輸費；經 gateway endpoint 時不經過 NAT，gateway endpoint 本身也不收費。
>
> **D ✗** 使用 public IP 或 Elastic IP 通訊時，即使兩台機器在同一個 AZ，也依跨 AZ 費率計費；改用 private IP 才免費。
>
> **考點**：SAA-4.4｜data transfer 計費規則

### 練習 39-2｜SAA｜選兩項｜ECR 映像拉取經 NAT 的成本

Wanderly 的 ECS on Fargate 服務位於 private subnet，每次部署與擴展都會從同 Region 的 Amazon ECR 拉取數 GB 的容器映像。帳單顯示 NAT Gateway 的資料處理費用持續上升，而這些 task 除了 ECR 之外不需要存取 Internet。

哪兩個步驟能讓映像拉取不再經過 NAT Gateway？（選兩項）

- A. 改用 NAT instance 取代 NAT Gateway
- B. 為 ECR 建立 `ecr.api` 與 `ecr.dkr` 的 interface VPC endpoint
- C. 為 ECR repository 啟用跨 Region replication
- D. 建立 S3 gateway endpoint 並關聯到 private subnet 的 route table
- E. 啟用 S3 Transfer Acceleration

> [!answer]- 答案：B、D
> **A ✗** NAT instance 沒有每 GB 處理費，但要自己維運與做高可用，而且流量仍經過 NAT 路徑，不是讓流量繞過 NAT 的做法。
>
> **B ✓** ECR 的 API 與 Docker registry 呼叫需要 `ecr.api` 與 `ecr.dkr` interface endpoint，task 才能在不經 NAT 的情況下與 ECR 通訊。
>
> **C ✗** 跨 Region replication 會增加跨 Region 傳輸費，與同 Region 拉取經 NAT 的問題無關。
>
> **D ✓** ECR 的映像層實際存放在 S3。沒有 S3 gateway endpoint 時，下載映像層仍會走 NAT；gateway endpoint 免費，能消除這部分最大的流量。
>
> **E ✗** Transfer Acceleration 是透過 edge location 加速遠距離傳輸，額外收費，也不影響 NAT 路徑。
>
> **考點**：SAA-4.4｜interface endpoint 與 gateway endpoint 降低 NAT 費用

### 練習 39-3｜SAA｜單選｜選擇 Savings Plans 類型

Wanderly 的 compute 用量穩定：EC2 每小時約 40 美元、Fargate 約 10 美元、Lambda 約 5 美元。架構團隊計畫在未來一年內把部分 EC2 從 x86 換成 Graviton，並可能把一部分服務搬到新加坡 Region。財務要求降低這些穩定用量的成本，且不希望之後因架構調整而浪費承諾。

哪個做法最合適？

- A. 購買 1 年期的 Compute Savings Plans，承諾金額以穩定的總 baseline 為準
- B. 購買 3 年期的 EC2 Instance Savings Plans，涵蓋目前東京使用的 x86 instance family
- C. 為目前使用的每種 instance type 購買 Standard Reserved Instances
- D. 全部改用 Spot Instances

> [!answer]- 答案：A
> **A ✓** Compute Savings Plans 適用於任何 instance family、Region、OS，也涵蓋 Fargate 與 Lambda。換成 Graviton 或搬到新加坡後，折扣仍會自動套用，不會浪費承諾。
>
> **B ✗** EC2 Instance Savings Plans 綁定 family 與 Region；換成 Graviton（不同 family）或搬到新加坡後就不再適用，也不涵蓋 Fargate 與 Lambda。
>
> **C ✗** Standard RI 綁定 instance 屬性，無法跟著 family 與 Region 調整，也不涵蓋 Fargate 與 Lambda。
>
> **D ✗** 穩定運作的服務不一定能承受中斷；Lambda 也沒有 Spot 選項。
>
> **考點**：SAA-4.2｜Compute Savings Plans 的彈性

### 練習 39-4｜SAA｜單選｜批次影像處理的最低成本

Wanderly 每天晚上要處理數十萬張旅館照片（產生縮圖與浮水印）。工作從 SQS queue 讀取，每張照片處理約 20 秒，失敗可以重試；只要在早上 8 點前完成即可。目前使用 20 台 On-Demand instance。團隊希望成本最低。

哪個做法最合適？

- A. 為這 20 台 instance 購買 3 年期 Standard Reserved Instances
- B. 建立 On-Demand Capacity Reservation 確保每晚有足夠容量

> **C ✓** On-Demand Capacity Reservation 不需要 1 年或 3 年的承諾，可以針對特定 AZ 與 instance type 保留容量；立即生效的 reservation 在活動結束後即可取消。保留期間以 On-Demand 價格計費，與容量保證相比是可接受的短期成本。若想提前數週預約，可以用 future-dated Capacity Reservation，但要接受最少 14 天的承諾期，成本仍遠低於 1 年期承諾。
>
> **D ✗** Savings Plans 只提供折扣，不保留任何容量；增加承諾也會在活動後造成浪費。
>
> **考點**：SAP-2.6、SAP-1.5｜Capacity Reservation 與承諾的差異

### 練習 39-16｜SAP｜單選｜多 VPC 的 egress 成本取捨

Wanderly 有 30 個 VPC，分布在東京 Region 的三個 AZ，每個 VPC 在每個 AZ 都有一台 NAT Gateway（共 90 台）。大多數 VPC 對 Internet 的流量很少，主要是下載 patch 與呼叫少數外部 API；所有 VPC 已透過 Transit Gateway 互連。安全團隊也希望集中檢查對外流量。財務要求降低成本，同時維持 AZ 層級的高可用。

哪個做法最合適？

- A. 把每個 VPC 的 NAT Gateway 減少為一台，放在 AZ-a，讓其他 AZ 的 subnet 跨 AZ 使用
- B. 建立集中 egress VPC，在三個 AZ 各部署 NAT Gateway（並依需要加入 inspection），各 workload VPC 的預設路由經 Transit Gateway 送往 egress VPC；評估 Transit Gateway 處理費後確認總成本較低
- C. 移除所有 NAT Gateway，改為每台 instance 配置 Elastic IP 並放在 public subnet
- D. 在每個 VPC 為所有可能用到的 AWS 服務建立 interface endpoint，取代 NAT Gateway

> [!answer]- 答案：B
> **A ✗** 每個 VPC 只剩一台 NAT 會變成 AZ 單點故障，違反高可用要求，也會增加跨 AZ 流量費用。
>
> **B ✓** 低流量的 VPC 多時，90 台 NAT 的時數費是主要成本。集中 egress 只需三台 NAT（每 AZ 一台）維持高可用，也方便集中檢查；新增的 Transit Gateway 每 GB 處理費在流量小時通常低於省下的時數費，但要實際計算確認。
>
> **C ✗** 把 instance 放進 public subnet 並配 public IP 會擴大攻擊面，也會為每個 public IPv4 付時數費。
>
> **D ✗** Interface endpoint 只能存取 AWS 服務，無法用於外部 API；在 30 個 VPC、每個 AZ 都建立多個 endpoint，時數費可能比 NAT 更高。
>
> **考點**：SAP-1.5、SAP-1.1｜集中 egress 的成本取捨
