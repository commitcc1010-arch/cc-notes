# 第 22 章　S3 基礎：Object 模型、一致性與存取控制

> [!abstract] 本章地圖
> **你會學到**：
> - 用 bucket、object、key 的模型解釋 S3 和檔案系統的差異，知道哪些 workload 適合、哪些不適合放 S3
> - 說清楚 S3 的 strong read-after-write consistency 保證了什麼、沒有保證什麼

> - 讓沒有 AWS 身份的使用者安全地上傳或下載（presigned URL、CORS），並用 CloudFront 提供 HTTPS 靜態網站
> - 設計事件驅動的處理流程（event notifications、EventBridge），並排除 503 Slow Down 等效能問題
>
> **前置知識**：第 4 章（block／file／object storage）、第 12 章（IAM policy 評估）
> **考試比重**：SAA ★★★（Domain 1 資料安全、Domain 3 儲存效能）｜SAP ★★☆（Domain 2、3 安全控制與改善）

## 22.1 故事：旅館照片要放哪裡？

Wanderly 進入成長期。合作旅館從 300 家增加到 4,000 家，每家旅館會上傳 20 到 200 張照片，行銷團隊還開始拍攝 4K 介紹影片。早期工程師把照片直接存在網站 EC2 的磁碟上，用 Nginx 提供下載。這個做法很快遇到三個問題：Auto Scaling 新開的機器上沒有舊照片；一台機器的磁碟壞掉，那台機器上的照片就沒了；磁碟每兩個月就要擴充一次，而且要停機。

技術主管小周決定把所有照片與文件搬到 **Amazon S3（Simple Storage Service）**。S3 是 AWS 的 object storage 服務：你透過 HTTPS API 存入和取出整個檔案，不需要管理磁碟容量，資料會自動存放在一個 Region 內的多個 AZ。容量看起來是無限的，你只為實際存放的量與請求次數付費。

但「把檔案丟上 S3」只是開始。小周列出團隊接下來要回答的問題：旅館上傳 2 GB 的影片時網路斷線怎麼辦？行銷人員不小心刪掉整個資料夾怎麼救？照片要讓全世界看到，但旅館的營業登記文件絕對不能外流，權限要怎麼切？旅館用瀏覽器直接上傳，要不要經過我們的伺服器？照片上傳後要自動產生縮圖，誰來觸發？

這一章就依照這些問題的順序，把 S3 的物件模型、一致性、上傳下載、版本、權限、公開存取、事件與效能一層一層建立起來。下一章（第 23 章）再處理成本與資料保護：儲存類別、生命週期、跨 Region 複寫與 Object Lock。

## 22.2 Object storage 的基本模型：bucket、object 與 key

### 三個核心名詞

- **Bucket（儲存桶）** 是存放 object 的容器。每個 bucket 建立在一個 Region，資料預設不會離開那個 Region。Bucket 名稱在整個 AWS partition（例如所有商用 Region）中**全域唯一**，只能用小寫字母、數字、`.` 與 `-`，長度 3 到 63 個字元。因為名稱全域唯一，`photos` 這種名字早就被別人用了，實務上會用 `wanderly-hotel-photos-prod` 這種帶公司與環境的名稱。
- **Object（物件）** 是存進 S3 的一份資料，由資料本身（bytes）、**metadata**（描述資料的鍵值，例如 `Content-Type: image/jpeg`，以及你自訂的 `x-amz-meta-hotel-id`）與一組 **tags**（最多 10 個鍵值標籤，可用於權限與生命週期篩選）組成。
- **Key（鍵）** 是 object 在 bucket 裡的完整名稱，例如 `hotels/1234/rooms/deluxe-01.jpg`，最長 1,024 bytes。Bucket 名稱加上 key（再加上 version ID，見 22.5 節）就能唯一定位一個 object。

一個 object 的網址形式是 `https://wanderly-hotel-photos-prod.s3.ap-northeast-1.amazonaws.com/hotels/1234/rooms/deluxe-01.jpg`。但能不能存取，要看權限，有網址不代表任何人都能讀。

### 沒有資料夾，只有 prefix

在 S3 console 裡你會看到「資料夾」，但 S3 的資料結構其實是**扁平的**：bucket 裡只有一大堆 key，沒有目錄樹。`hotels/1234/rooms/deluxe-01.jpg` 中的 `/` 只是 key 字串裡的一個普通字元。Console 和 LIST API 會用 **prefix（前綴）** 與 **delimiter（分隔字元，通常是 `/`）** 把 key 分組顯示，看起來就像資料夾。

這個差異有實際後果：

1. 「把資料夾 `hotels/1234/` 改名」在 S3 裡不是一個動作，而是把底下每個 object 複製到新 key 再刪掉舊的。有 10 萬個 object 就要做 10 萬次複製。
2. 權限、生命週期、事件通知都能用 prefix 篩選，所以 **key 的命名方式就是你的資料架構**。Wanderly 把公開照片放在 `public/`、旅館私密文件放在 `private/`，後面的 bucket policy 就能清楚地用 prefix 劃分。

### Object 是整份替換，不是檔案

S3 的寫入單位是**整個 object**。你不能打開一個 object、在第 500 個 byte 改一個字再存檔；要修改就得上傳一份完整的新內容（覆寫同一個 key）。S3 也沒有檔案鎖、`mmap`、`append` 這些作業系統檔案語意。

> [!warning] 常見誤解
> 「S3 容量無限、很耐久，所以資料庫檔案、需要多台機器同時改寫的共享檔案也可以放上去。」不行。需要 block device 的資料庫用 EBS；多台機器同時讀寫、需要 POSIX 檔案語意（鎖、rename、局部寫入）用 EFS 或 FSx（第 24 章）。S3 適合的是「整份寫入、整份或分段讀取」的資料：照片、影片、備份、日誌、資料湖、靜態網站資源。

### 耐久度與可用度

S3 Standard 的設計目標是 **99.999999999%（11 個 9）的耐久度（durability）** 與 **99.99% 的可用度（availability）**。第 4 章說過兩者的差別：耐久度是「資料不會遺失」的機率，可用度是「此刻能不能讀到」的機率。11 個 9 的耐久度意思是：存 1,000 萬個 object，平均要一萬年才可能遺失一個。S3 Standard 把資料分散存放在至少三個 AZ，所以一個 AZ 整個故障也不會遺失資料。

不過耐久度只保護你不受「AWS 硬體故障」影響，它**不保護你不受自己的錯誤影響**：你下了刪除指令，S3 會非常可靠地把資料刪掉。防誤刪要靠 versioning（22.5 節）、複寫與 Object Lock（第 23 章）。

### 兩種 bucket 類型

本章談的都是 **general purpose bucket（一般用途 bucket）**，也是絕大多數題目與實務的預設。另外還有 **directory bucket**，專門給 S3 Express One Zone 這個單一 AZ、極低延遲的儲存類別使用，它的 API 行為與功能和一般 bucket 有些差異，第 23 章再介紹。

## 22.3 一致性：寫完立刻讀得到嗎？

照片上傳後，Wanderly 的後端會馬上讀取它來產生縮圖。工程師小林擔心：「網路上說 S3 是 eventual consistency，剛寫入的檔案可能要等幾秒才讀得到，要不要在程式裡加 sleep？」

這是過時的資訊。**自 2020 年 12 月起，S3 對所有 GET、PUT、LIST 與 DELETE 提供 strong read-after-write consistency（強一致性）**，所有 Region 都適用、不需額外設定、不額外收費：

- PUT 一個新 object 成功後，接下來的 GET 一定讀得到它，LIST 也一定列得出它。
- 覆寫（overwrite）既有 object 成功後，接下來的 GET 一定拿到新內容，不會讀到舊版本。
- DELETE 成功後，接下來的 GET 會得到 404，LIST 不會再列出它。
- Object 的 metadata、tags、ACL 的變更也是強一致。

要注意的例外是 **bucket 層級的設定**（例如剛建立或刪除 bucket、剛啟用 versioning、修改 bucket policy 或 lifecycle）：這些設定的變更是最終一致的，可能要一小段時間才在所有地方生效。AWS 建議剛啟用 versioning 後等待約 15 分鐘再大量寫入。

所以小林不需要 sleep，也不需要「寫入後輪詢直到讀得到」的程式。

### 強一致性沒有保證的事

強一致性是**針對單一 object 的單一操作**。它不提供：

1. **跨多個 object 的交易（transaction）。** 資料管線寫入 `part-001` 與 `part-002` 兩個檔，可能第一個成功、第二個失敗。讀取端若要「全部到齊才處理」，常見做法是最後寫一個 `_SUCCESS` 或 manifest 檔，讀取端只看 manifest。
2. **同時寫入的協調。** 兩個 client 在同一時間覆寫同一個 key，S3 以時間較晚的那個為準（last writer wins），先寫的那份會被覆蓋，不會報錯。若要避免互相覆蓋，可以使用 **conditional writes（條件式寫入）**：PUT 時帶 `If-None-Match: *` 表示「只有這個 key 不存在才寫入」，帶 `If-Match: <ETag>` 表示「只有內容還是我讀到的那個版本才覆寫」，條件不成立時 S3 會回傳錯誤而不是默默覆蓋。
3. **跨 Region 的一致性。** 複寫到另一個 Region 是非同步的（第 23 章），另一個 Region 的副本可能落後。

> [!tip] 考試提示
> 選項若出現「S3 是 eventual consistency，寫入後應等待幾秒再讀」「改用 DynamoDB 才能讀到最新資料」，在現行 S3 都是錯的。題目若問「如何確保多個檔案全部完成才被處理」，答案是 manifest 或完成標記檔，而不是期待 S3 提供多 object 交易。

## 22.4 上傳與下載大檔：multipart upload 與 byte-range fetch

### 單次上傳的上限

- 單一 object 的大小上限傳統上是 **5 TB**，這也是 SAA-C03／SAP-C02 題目使用的數字。AWS 後來把上限提高到約 **50 TB**（官方文件寫 48.8 TiB），part 數量上限仍是 10,000、單一 part 仍最大 5 GiB。實務上以最新文件為準；考試題目若出現「5 TB 上限」，仍照題目作答。
- **單一 PUT 請求最多 5 GB。** 超過 5 GB 的 object 一定要用 multipart upload。
- AWS 建議 object **超過 100 MB 就考慮 multipart upload**。

### Multipart upload 怎麼運作

**Multipart upload（分段上傳）** 把一個大檔切成多個 part，分別上傳後再由 S3 組合成一個 object：

1. `CreateMultipartUpload`：取得一個 upload ID。
2. `UploadPart`：上傳每個 part，各自帶 part number（1 到 10,000）。每個 part 介於 5 MiB 到 5 GiB（最後一個 part 可以小於 5 MiB；官方文件的 part 大小以 MiB／GiB 表示，單一 PUT 上限則寫作 5 GB，考試時兩者都當成「約 5 GB」即可）。Part 之間**可以平行上傳**，順序不限。
3. `CompleteMultipartUpload`：告訴 S3 所有 part 的清單，S3 依 part number 組合成最終 object。在這之前，object 不會出現在 bucket 裡。
4. 若放棄，呼叫 `AbortMultipartUpload` 清掉已上傳的 part。

它解決三件事：**速度**（多條連線平行傳輸，吃滿頻寬）、**可靠性**（某個 part 失敗只要重傳那個 part，不必從頭來）、**可以邊產生邊上傳**（不必先知道完整檔案大小）。AWS CLI 的 `aws s3 cp` 與各語言 SDK 的高階傳輸工具，在檔案超過門檻時會自動使用 multipart upload。

> [!warning] 常見誤解：看不見的帳單
> 開始了但沒有 complete 也沒有 abort 的 multipart upload，已上傳的 part **持續占用儲存空間並計費**，而且在 console 的 object 列表中看不到。正確做法是在 bucket 加一條 lifecycle rule：`AbortIncompleteMultipartUpload`，例如上傳開始 7 天後自動清除（第 23 章）。

### 完整性檢查

網路傳輸可能出錯，S3 提供 **checksum（校驗碼）** 機制：上傳時指定 CRC32、CRC32C、CRC64NVME、SHA-1 或 SHA-256 等演算法，S3 在收到資料時驗證，不符就拒絕。新版 SDK 預設會自動計算並送出 checksum。注意 object 的 **ETag** 不一定是檔案的 MD5：multipart upload 或某些加密方式產生的 ETag 是另一種值，不要拿它當內容驗證。

### Byte-range fetch：只讀需要的那一段

下載方向也有對應的技巧。GET 請求可以帶 HTTP `Range` header，例如 `Range: bytes=0-1048575`，只取前 1 MB。這叫 **byte-range fetch**，用途有二：

- **平行下載大檔**：把 10 GB 的檔案分成 100 段，用 100 條連線同時抓，再在本地組合，大幅提升吞吐量；某段失敗只重抓那一段。
- **只讀檔案的一部分**：例如影片播放器只取開頭片段，或分析程式只讀 Parquet 檔尾端的欄位索引（footer）。

## 22.5 Versioning：讓「刪除」可以反悔

某個週五，行銷人員用同步工具整理檔案時，不小心把 `public/hotels/` 下 3 萬張照片刪掉了。S3 的 11 個 9 耐久度幫不上忙，因為刪除是「合法」指令。如果 bucket 有開 versioning，這件事只需要幾分鐘就能復原。

### Versioning 怎麼運作

**Versioning（版本控制）** 開啟後，S3 為同一個 key 保留每一次寫入的完整版本，每個版本有唯一的 **version ID**：

- **覆寫**：上傳同一個 key 會產生一個新版本，成為 **current version（目前版本）**；舊內容變成 **noncurrent version（非目前版本）**，仍然保存著。
- **一般刪除（不指定 version ID）**：S3 不會真的刪資料，而是放一個 **delete marker（刪除標記）** 成為目前版本。之後一般的 GET 會得到 404，看起來像被刪掉，但所有舊版本都還在。
- **復原**：刪除那個 delete marker，前一個版本就重新成為目前版本；或把指定的舊版本複製成新的目前版本。
- **永久刪除**：DELETE 時明確指定 version ID，才會真的移除那個版本。這個動作需要 `s3:DeleteObjectVersion` 權限，可以只授予少數人。

Bucket 的 versioning 有三種狀態：**未啟用（unversioned，預設）**、**啟用（enabled）**、**暫停（suspended）**。一旦啟用過，就**不能回到未啟用**，只能暫停；暫停後新寫入不再產生新版本（version ID 為 `null`），但已存在的舊版本仍保留。開啟 versioning 之前就存在的 object，version ID 也是 `null`。

### Versioning 的代價與搭配

每個版本都是一份完整的 object，**全部都要計費**。一個每天被覆寫一次的 1 GB 檔案，一年後會累積 365 GB 的舊版本。所以 versioning 幾乎一定要搭配 lifecycle rule 處理 noncurrent version，例如「非目前版本 30 天後刪除」或「只保留最近 3 個非目前版本」（第 23 章）。

Versioning 也是其他功能的前提：跨 Region 複寫（CRR／SRR）、Object Lock 都要求 versioning 已啟用。另外有 **MFA Delete**，要求永久刪除版本或變更 versioning 狀態時提供 MFA 驗證碼，第 23 章與 Object Lock 一起比較。

> [!warning] 常見誤解
> 「開了 versioning 就等於有備份。」Versioning 的所有版本都在**同一個 bucket、同一個 Region、同一個帳號**。帳號被入侵者拿到永久刪除權限、或整個 bucket 被刪除，版本一起消失。真正的備份還需要複寫到另一個帳號或 Region、Object Lock 或 AWS Backup（第 23、34 章）。

## 22.6 誰能存取：IAM policy、bucket policy 與 ACL

資料放好了，接下來是本章最重要也最常考的部分：權限。Wanderly 的需求是：

- 照片處理服務（一個 IAM role）可以讀寫整個 bucket。
- 資料分析團隊在另一個 AWS 帳號，只能讀 `public/` 下的照片做統計。
- 全世界的旅客可以看到公開照片，但只能經過 CDN，不能直接打 S3。
- 任何人都不能用未加密的 HTTP 存取。

S3 的權限可以從三個地方授予，再加上 22.7 節的 Block Public Access 作為最外層的保險。

### 三種授權方式

| 方式 | 附加在哪裡 | 寫法 | 典型用途 |
|---|---|---|---|
| **IAM policy（identity-based policy）** | IAM user／group／role | JSON，**沒有** `Principal` 欄位（附加的對象就是 principal） | 「這個 role 能做什麼」，管理同帳號內的存取 |
| **Bucket policy（resource-based policy）** | Bucket | JSON，**必須有** `Principal` 欄位，最大 20 KB | 跨帳號授權、AWS 服務存取、全 bucket 的強制規則（例如必須 HTTPS） |
| **ACL（Access Control List）** | Bucket 或每個 object | XML 授權清單，只能給帳號或預定義群組 | 舊機制，現在建議停用 |

### Policy 評估邏輯（S3 版）

第 12 章詳細說明了 IAM 的評估邏輯，套用在 S3 上可以濃縮成三條：

1. **預設拒絕**：沒有任何 Allow，就是拒絕。
2. **Explicit deny 最優先**：任何一條適用的 Deny（不論寫在 IAM policy、bucket policy、SCP 或 Access Point policy），都會拒絕，Allow 再多也沒用。
3. **同帳號與跨帳號不同**：
   - **同帳號**：IAM policy **或** bucket policy 其中一邊 Allow 即可（兩者是聯集）。
   - **跨帳號**：呼叫者自己帳號的 IAM policy **和** bucket 擁有者的 bucket policy **都**要 Allow（兩者是交集）。只在 bucket policy 寫了 Allow，對方帳號的管理者沒有給那個 role 對應的 IAM 權限，一樣會被拒絕。

如果 object 使用 SSE-KMS 加密，還有第三道關卡：呼叫者也需要 KMS key 的 `kms:Decrypt`（讀）或 `kms:GenerateDataKey`（寫）權限，跨帳號時 key policy 也要允許。細節見第 15 章。

```json
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E2QWRUHEXAMPLE"
        }
      }
    }
  ]
}
```

逐段解讀：

1. **DenyInsecureTransport**：`aws:SecureTransport` 為 `false` 代表請求走 HTTP 而非 HTTPS。用 Deny 加上 `Principal: "*"`，連 bucket 擁有者自己的 role 都不能用 HTTP，這是最常見的「強制加密傳輸」寫法。注意 `Resource` 同時列了 bucket 本身與 `/*`，因為有些動作作用在 bucket（例如 ListBucket），有些作用在 object。
2. **AllowAnalyticsListPublicPrefix**：`s3:ListBucket` 是**對 bucket 的動作**，Resource 必須是 `arn:aws:s3:::bucket-name`（沒有 `/*`）。`s3:prefix` 條件限制分析團隊只能列出 `public/` 底下的 key。
3. **AllowAnalyticsReadPublicObjects**：`s3:GetObject` 是**對 object 的動作**，Resource 必須是 `arn:aws:s3:::bucket-name/key-pattern`。這裡只開放 `public/*`。因為是跨帳號，帳號 `444455556666` 的管理者也必須在 `PhotoAnalyticsReader` role 的 IAM policy 中允許同樣的動作。
4. **AllowCloudFrontOACReadPublic**：讓 CloudFront 透過 **Origin Access Control（OAC）** 讀取公開照片。Principal 是 CloudFront 服務，再用 `AWS:SourceArn` 限定只有 Wanderly 自己的 distribution 可以讀，避免別人建立的 CloudFront distribution 也拿來讀你的 bucket。OAC 的設定流程見第 11 章。

照片處理服務的 role 在同一帳號，所以不必寫進 bucket policy，在它的 IAM policy 授權即可：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListPhotoBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::wanderly-hotel-photos-prod"
    },
    {
      "Sid": "ReadWritePhotoObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::wanderly-hotel-photos-prod/*"
    }
  ]
}
```

> [!warning] 常見誤解：ARN 寫錯一層
> 最常見的 S3 權限 bug 是把 `s3:ListBucket` 寫在 `bucket/*` 上，或把 `s3:GetObject` 寫在 `bucket` 上。兩種寫法 JSON 都合法、儲存也不會報錯，但永遠不會生效，結果就是 AccessDenied。記法：**動詞的受詞是誰，Resource 就寫誰**。List 的對象是 bucket，Get／Put／Delete 的對象是 object。

### 常用的 condition keys

| Condition key | 用途 |
|---|---|
| `aws:SecureTransport` | 強制 HTTPS |
| `aws:PrincipalOrgID` | 只允許同一個 AWS Organization 內的 principal（不必列出每個帳號 ID） |
| `aws:SourceVpce`／`aws:SourceVpc` | 只允許經由特定 VPC endpoint 或 VPC 進來的請求（第 6 章） |
| `aws:SourceIp` | 限制來源 public IP 範圍（經 VPC endpoint 的流量不適用，要改用 `aws:SourceVpce`） |
| `s3:prefix` | 限制 ListBucket 能列出的 prefix |
| `s3:x-amz-server-side-encryption`／`s3:x-amz-server-side-encryption-aws-kms-key-id` | 要求上傳時使用指定的加密方式或 KMS key |
| `s3:ExistingObjectTag/<key>`、`s3:RequestObjectTag/<key>` | 依 object tag 授權（ABAC） |

### ACL 與 Object Ownership：為什麼要停用 ACL

ACL 是 S3 最早的權限機制，比 IAM 還早。它的問題在於：每個 object 都可以有自己的 ACL，權限分散在數百萬個 object 上，無法集中稽核；而且在舊的預設行為下，**別的帳號上傳到你 bucket 的 object，擁有者是上傳者而不是你**，你可能連讀取自己 bucket 裡的檔案都需要對方授權。

**S3 Object Ownership** 這個 bucket 設定解決了這個問題，有三個選項：

| 設定 | ACL | Object 擁有者 |
|---|---|---|
| **Bucket owner enforced（建議，新 bucket 預設）** | 全部停用，ACL 不再影響權限 | 永遠是 bucket 擁有者 |
| Bucket owner preferred | 仍有效 | 上傳時帶 `bucket-owner-full-control` ACL 才歸 bucket 擁有者 |
| Object writer | 仍有效 | 上傳者 |

自 2023 年 4 月起，新建 bucket 預設就是 **Bucket owner enforced（ACL disabled）**。這時所有權限只由 policy 決定，跨帳號上傳的 object 也自動歸 bucket 擁有者。Bucket owner enforced 的 bucket 若收到帶有 ACL（除了 `bucket-owner-full-control` 這類等同於預設的值）的上傳請求，會直接被拒絕。

> [!note] 什麼時候還會碰到 ACL？
> 舊系統與部分 AWS 服務的舊式日誌投遞曾依賴 ACL。例如 S3 server access logging 過去需要授予 log delivery 群組寫入權限；現在可以改用 bucket policy 授權 logging 服務。要把舊 bucket 改成 ACL disabled 前，先確認沒有應用程式依賴 ACL 授權（可檢查現有 ACL、CloudTrail 或 server access logs 中的 ACL 相關請求），把需要的授權改寫進 bucket policy，再切換設定。

## 22.7 Block Public Access 與預設安全設定

S3 資料外洩事件，幾乎都不是 AWS 被駭，而是某人把 bucket 設成公開。**S3 Block Public Access（BPA）** 就是一道防止「有人不小心公開資料」的總開關，它**優先於任何 policy 與 ACL**：即使 bucket policy 寫了允許 `Principal: "*"`，只要 BPA 開著，這個公開存取就不會生效。

### 四個設定

| 設定 | 作用 |
|---|---|
| `BlockPublicAcls` | 拒絕任何設定公開 ACL 的請求（例如上傳時帶 `public-read`） |
| `IgnorePublicAcls` | 忽略已存在的公開 ACL，讓它們失效 |
| `BlockPublicPolicy` | 拒絕任何會讓 bucket 變成公開的 bucket policy 寫入 |
| `RestrictPublicBuckets` | 已經是公開 policy 的 bucket，只允許 AWS 服務與 bucket 擁有者帳號內的 principal 存取 |

前兩個處理 ACL，後兩個處理 policy；一個「阻止新的」，一個「讓既有的失效」。Console 上「Block all public access」就是四個一起開。

BPA 可以設在三個層級：**帳號層級**（套用到帳號內所有 bucket）、**bucket 層級**、**Access Point 層級**。多個層級時取最嚴格的組合。最佳實務是在**帳號層級全部開啟**，並用 SCP 禁止成員帳號關閉它（第 14 章）；真的需要公開內容時，用 CloudFront + OAC 而不是打開 BPA。

較新的做法是 **組織層級 BPA**：透過 AWS Organizations 的 S3 policy 統一套用到選定的成員帳號，會覆蓋帳號層級的設定，成員帳號無法自行關閉。組織層級只能「四項全開」或「全不開」，不能逐項挑選。多數考題仍以「帳號層級 BPA + SCP」作為標準答案，兩者的目的相同。

### S3 怎麼判斷「公開」

Policy 被視為公開，是指它對 `Principal: "*"`（或任何 AWS 帳號）授權，**而且沒有用固定值的條件把範圍收窄**。如果條件把存取限制在特定的 `aws:SourceVpce`、`aws:SourceVpc`、`aws:PrincipalOrgID`、`aws:SourceArn`、`aws:SourceAccount`，或固定的 `aws:SourceIp` 範圍（但比 IPv4 `/8` 更大的範圍，例如 `0.0.0.0/1`，仍會被視為公開），S3 不會把它視為公開。所以「`Principal: "*"` 但限定只能從 Wanderly 的 VPC endpoint 進來」的 policy，在 BPA 開著時仍然有效。

### 新 bucket 的預設安全基線

現在建立的新 bucket，預設就是安全的：

1. **Block Public Access 四項全開。**
2. **Object Ownership = Bucket owner enforced（ACL disabled）。**
3. **預設加密 SSE-S3**：自 2023 年 1 月起，所有新上傳的 object 都會以 S3 管理的金鑰在伺服器端加密，不額外收費，也無法關閉「預設一定加密」這件事（只能選擇改用 SSE-KMS 等方式）。

如果需要稽核誰在什麼時候解密了資料、或需要控制 key 的權限，就把預設加密改成 **SSE-KMS** 並啟用 **S3 Bucket Key** 降低 KMS 請求費用。SSE-S3、SSE-KMS、DSSE-KMS、SSE-C、client-side encryption 的比較與 KMS 原理都在第 15 章。

用 CloudFormation 描述 Wanderly 的 bucket 基線：

```yaml
Resources:
  HotelPhotosBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: wanderly-hotel-photos-prod
      OwnershipControls:
        Rules:
          - ObjectOwnership: BucketOwnerEnforced
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        IgnorePublicAcls: true
        BlockPublicPolicy: true
        RestrictPublicBuckets: true
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: aws:kms
              KMSMasterKeyID: !GetAtt PhotosKey.Arn
            BucketKeyEnabled: true
      VersioningConfiguration:
        Status: Enabled
```

範本中的 `PhotosKey` 是同一份範本裡另外定義的 KMS customer managed key（`AWS::KMS::Key`），這裡省略。雖然前三項現在已是預設值，在 IaC 中明確寫出來仍有價值：它讓意圖可被審查，也避免有人在 console 上改掉後 drift 沒人發現（第 37 章）。

> [!tip] 考試提示
> 題目說「確保公司內所有 S3 bucket 都不能被公開」，最佳答案是**帳號層級 Block Public Access**（多帳號再加上 SCP 防止被關掉，或直接用組織層級 BPA），而不是逐一檢查 bucket policy。要「找出」已經公開或分享給外部帳號的 bucket，用 **IAM Access Analyzer**；要找出 bucket 裡有沒有個資，用 **Amazon Macie**（第 16 章）。

## 22.8 給沒有 AWS 身份的人：presigned URL 與 CORS

### 問題：旅館要從瀏覽器上傳照片

旅館後台是一個網頁，旅館人員沒有 AWS 帳號。最直覺的做法是讓瀏覽器把照片傳到 Wanderly 的 API 伺服器，伺服器再轉存 S3。但 2 GB 的影片會讓伺服器的頻寬與記憶體吃緊，上傳期間還占著執行緒。更好的做法是**讓瀏覽器直接上傳到 S3**，伺服器只負責「授權這一次上傳」。

### Presigned URL 怎麼運作

**Presigned URL（預先簽章網址）** 是一個帶有簽章的 S3 網址：擁有權限的 principal 用自己的 credentials 對「某個動作（例如 PUT）＋某個 bucket／key＋有效期限」簽章，產生一個網址。任何人拿到這個網址，就能在有效期限內以簽章者的身份執行那一個動作，不需要自己的 AWS credentials。

```text
 旅館人員瀏覽器              Wanderly API（Lambda / EC2，IAM role）          S3
      │                                 │                                    │
      │ ① POST /upload-requests         │                                    │
      │   (已登入，hotelId=1234)         │                                    │
      │────────────────────────────────►│                                    │
      │                                 │ ② 檢查此人是否屬於 hotel 1234        │
      │                                 │ ③ 用 role credentials 在本機簽章     │
      │                                 │   PUT uploads/1234/<uuid>.jpg，15 分鐘│
      │ ④ 回傳 presigned URL             │                                    │
      │◄────────────────────────────────│                                    │
      │                                                                      │
      │ ⑤ PUT 檔案到 presigned URL（瀏覽器直接上傳）                          │
      │─────────────────────────────────────────────────────────────────────►│
      │                                       ⑥ S3 驗證簽章、期限、簽章者權限 │
      │ ⑦ 200 OK                                                             │
      │◄─────────────────────────────────────────────────────────────────────│
```

① 使用者先向 Wanderly 自己的 API 要求上傳。② 授權判斷（這個人能不能幫這家旅館上傳）在 Wanderly 的程式裡做。③ 簽章是在本機用 SDK 計算的，**不需要呼叫 AWS API**，key 由伺服器決定，使用者無法選擇寫到別處。④⑤ 瀏覽器拿到網址後直接 PUT 到 S3，大檔流量完全不經過 Wanderly 伺服器。⑥ S3 驗證簽章，並以**簽章者當下的權限**評估這個請求。

### Presigned URL 的規則

- **權限不會超過簽章者**：簽章的 role 沒有 `s3:PutObject` 權限，產生的網址也不能用；bucket policy 或 SCP 中的 explicit deny 依然生效。
- **有效期限**：用 SigV4 簽章最長 7 天；console 產生的最長 12 小時。若用 IAM role 的**臨時 credentials** 簽章，網址最晚在 credentials 到期時失效，即使你設的期限更長。Lambda 或 EC2 role 的臨時 credentials 通常只有數小時，所以長期分享不適合用 role 簽。
- **撤銷**：presigned URL 無法單獨撤銷。要讓它提早失效，可以撤銷簽章者的權限或 session，或在 bucket policy 加 Deny。
- **持有網址就能用**：它像一張無記名票券，所以有效期限要短、透過 HTTPS 傳遞。
- 下載也可以用 presigned URL（GET），例如讓旅館下載自己的營業登記文件 15 分鐘。
- 如果是 HTML 表單上傳，可以改用 **presigned POST**，在 policy 中加條件，例如限制檔案大小範圍（`content-length-range`）與 `Content-Type` 前綴。

### CORS：瀏覽器的另一道門

瀏覽器直接上傳時，還會遇到 **CORS（Cross-Origin Resource Sharing，跨來源資源共享）**。瀏覽器的安全規則規定，`https://partner.wanderly.com` 頁面上的 JavaScript 要呼叫另一個網域（`wanderly-hotel-photos-prod.s3.ap-northeast-1.amazonaws.com`）時，目標網域必須明確回應「我允許這個來源」，否則瀏覽器會擋下請求。注意這是**瀏覽器**的限制，用 CLI 或後端程式呼叫不會遇到。

在 bucket 設定 CORS configuration：

```json
{
  "CORSRules": [
    {
      "AllowedOrigins": ["https://partner.wanderly.com"],
      "AllowedMethods": ["PUT", "GET"],
      "AllowedHeaders": ["*"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3000
    }
  ]
}
```

這份設定可以用 `aws s3api put-bucket-cors --bucket wanderly-hotel-photos-prod --cors-configuration file://cors.json` 套用。CORS **不是權限控制**：它只告訴瀏覽器「可以從這個來源發請求」，請求本身是否被允許仍由 presigned URL 簽章與 policy 決定。考試看到「瀏覽器 console 出現 CORS 錯誤」「網站從另一個 bucket 載入字型失敗」，答案就是在**被呼叫的那個 bucket** 設定 CORS。

## 22.9 S3 Access Points：一個 bucket，多個入口

Wanderly 的資料湖 bucket 裡有訂單、點擊流、照片 metadata，十幾個團隊各自需要不同 prefix 的不同權限。全部寫在一份 bucket policy 裡，很快就遇到兩個問題：policy 越來越長，接近 **20 KB 的上限**；每次改權限都在動一份所有團隊共用的檔案，一個打錯字可能讓所有人無法存取。

**S3 Access Point** 為同一個 bucket 建立多個具名的存取入口，每個 access point 有：

- 自己的名稱與 ARN（例如 `arn:aws:s3:ap-northeast-1:111122223333:accesspoint/analytics-ap`）和專屬的網域名稱。
- 自己的 **access point policy**，只管這個入口的權限。
- 自己的網路來源設定：**Internet** 或 **VPC**。設為 VPC 時，這個 access point 只接受來自指定 VPC 的請求，適合「這份資料只能從內部網路存取」的要求。
- 自己的 Block Public Access 設定。

一個 access point policy 的例子，只允許分析團隊的 role 讀取 `clickstream/` 底下的資料：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AnalyticsReadClickstream",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/AnalyticsTeam" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:ap-northeast-1:111122223333:accesspoint/analytics-ap/object/clickstream/*"
    }
  ]
}
```

注意 access point 的 object ARN 格式是 `accesspoint/<名稱>/object/<key>`。請求透過 access point 進來時，**bucket policy 與 access point policy 都要允許**。常見做法是在 bucket policy 寫一條「把權限委派給本帳號的 access point」的規則（以 `s3:DataAccessPointAccount` 條件判斷請求是否經由本帳號的 access point），之後各團隊的細部權限都在各自的 access point policy 管理，bucket policy 不再需要經常修改。

> [!note] 相關功能
> **Multi-Region Access Points** 提供一個全球入口，把請求導向多個 Region 中延遲最低的 bucket，搭配跨 Region 複寫做多 Region 架構，見第 42 章。Directory bucket 與 S3 Express One Zone 也有各自的存取方式，見第 23 章。

## 22.10 Static website hosting：直接用 S3 架網站，還是交給 CloudFront？

Wanderly 的行銷團隊有一個純靜態的活動網站（HTML、CSS、JavaScript、圖片），想要用最便宜的方式上線。S3 本身就有 **static website hosting（靜態網站託管）** 功能：

- 在 bucket 啟用 website hosting，設定 **index document**（例如 `index.html`）與 **error document**（例如 `404.html`），也可以設定重新導向規則。
- S3 會提供一個 **website endpoint**，形式為 `http://<bucket>.s3-website-<region>.amazonaws.com`（部分 Region 寫成 `s3-website.<region>`）。
- 內容要讓匿名使用者讀取，就必須關閉該 bucket 的 Block Public Access，並用 bucket policy 允許 `Principal: "*"` 的 `s3:GetObject`。
- 若要用自己的網域（例如 `campaign.wanderly.com`）直接指到 website endpoint，bucket 名稱必須與網域名稱相同，再用 Route 53 alias record 指過去（第 9 章）。

但 website endpoint 有幾個重大限制：**只支援 HTTP，不支援 HTTPS**；只支援 GET、HEAD 等讀取請求；而且需要讓 bucket 公開。現代網站一定要 HTTPS，所以正式做法幾乎都是：

> **CloudFront distribution（HTTPS、自訂網域、ACM 憑證）→ OAC → 私有 S3 bucket（REST endpoint，BPA 全開）**

這個架構裡 bucket 完全不公開，只有 CloudFront 能讀取（22.6 節範例的最後一段 policy），全球使用者從最近的 edge location 拿到快取內容，還能掛 WAF。需要注意：**OAC 只能搭配 S3 的 REST endpoint**，不能搭配 website endpoint；如果需要 website endpoint 才有的重新導向規則，就要把 website endpoint 當成一般的 custom origin（此時 bucket 必須公開）。單頁應用程式的路由與預設首頁，通常改用 CloudFront 的 default root object、自訂錯誤回應或 CloudFront Functions 處理（第 11 章）。

> [!tip] 考試提示
> 「靜態網站、最低成本、最少維運」→ S3 static website hosting 是合理答案；但只要題目出現 **HTTPS**、**自訂網域憑證**、**bucket 不可公開**、**全球低延遲** 任一個，就選 CloudFront + OAC + 私有 bucket。

## 22.11 Event notifications：照片一上傳就自動處理

照片上傳後要自動產生三種尺寸的縮圖、偵測不當內容、更新搜尋索引。S3 可以在 object 發生變化時主動發出事件，讓下游服務處理，不需要定期掃描 bucket。

### 兩種發送方式

**1. S3 event notifications（直接通知）**：在 bucket 設定「哪些事件、哪些 prefix／suffix → 送到哪裡」。目的地有三種：

- **Amazon SQS** standard queue（不支援 FIFO queue）
- **Amazon SNS** topic
- **AWS Lambda** function

常見事件類型包括 `s3:ObjectCreated:*`（PUT、POST、COPY、multipart 完成）、`s3:ObjectRemoved:*`（刪除與 delete marker）、`s3:ObjectRestore:*`（從封存類別取回，第 23 章）、`s3:Replication:*`、`s3:LifecycleExpiration:*` 等。目的地本身要授權 S3 發送：SQS 需要 queue policy、SNS 需要 topic policy、Lambda 需要 resource-based permission，三者都允許 `s3.amazonaws.com` 並以 `aws:SourceArn`／`aws:SourceAccount` 限定來源 bucket。

**2. Amazon EventBridge**：在 bucket 開啟「send notifications to Amazon EventBridge」，**所有**事件都會送進 default event bus，再由 EventBridge rule 依 bucket、key prefix、object 大小等欄位做進階過濾，送到 Step Functions、SQS、Lambda、Kinesis 等二十多種目標，還支援 archive 與 replay（第 32 章）。

### 一個重要限制：同一事件不能送給兩個目的地

直接通知的設定中，**同一種事件類型的 prefix／suffix 篩選條件不能重疊**。也就是說，「`uploads/` 的 ObjectCreated」不能同時送到縮圖 Lambda 和內容審查 queue。要讓一個事件被多個消費者處理，有兩種做法：

```text
方案一：SNS fan-out
  S3 ──ObjectCreated──► SNS topic ──┬──► SQS: thumbnail-queue ──► 縮圖 worker
                                    ├──► SQS: moderation-queue ──► 內容審查
                                    └──► SQS: index-queue ──► 搜尋索引更新

方案二：EventBridge
  S3 ──所有事件──► EventBridge default bus ──rule A──► Lambda 縮圖
                                          ├─rule B──► Step Functions 審查流程
                                          └─rule C──► SQS 索引更新
```

方案一是經典的 fan-out（第 32 章）：一份事件發到 SNS，再複製到多個 SQS queue，各消費者用自己的速度處理，失敗可重試、可進 DLQ。方案二讓每個 rule 獨立過濾，新增消費者只要加一條 rule，不必修改 bucket 設定。

### 事件的交付特性

- 通常在數秒內送達，但**不保證即時，也不保證順序**；同一個 key 的多個事件，可以用事件中的 `sequencer` 欄位判斷先後。
- 交付語意是 **at-least-once**：偶爾會收到重複事件，處理程式要設計成**冪等（idempotent）**，重複處理同一張照片不會產生錯誤結果（第 33 章）。
- 小心**遞迴觸發**：Lambda 處理 `uploads/` 的照片後，把縮圖寫回同一個 bucket 的 `uploads/`，就會再觸發自己，形成無限迴圈。縮圖要寫到不同 prefix（例如 `thumbnails/`）或另一個 bucket。

## 22.12 效能：prefix、Transfer Acceleration 與平行化

### 每個 prefix 的請求速率

S3 會依 key 的 prefix 自動把資料分割（partition）到多個伺服器。每個分割後的 prefix 至少可以支援**每秒 3,500 個 PUT／COPY／POST／DELETE 與 5,500 個 GET／HEAD 請求**，而 bucket 裡的 prefix 數量沒有上限。所以要提高總吞吐量，就是**把請求分散到多個 prefix 並平行處理**：10 個 prefix 平行讀取，理論上可以達到每秒 55,000 個 GET。

當某個 prefix 的請求量突然暴增，S3 在自動擴展分割的過程中可能回傳 **HTTP 503 Slow Down**。正確處理方式是：

1. 用 **exponential backoff（指數退避）** 重試，SDK 預設就會做。
2. 讓 key 的設計能把負載分散到多個 prefix，例如 `hotels/<hotelId>/...` 而不是所有檔案都塞在 `uploads/2026-10-01/` 之下。

過去的建議是在 key 開頭加上隨機 hash 來分散負載。S3 在 2018 年大幅提升了請求速率後，這已經不再必要；**依業務意義設計 prefix，再平行化**即可。

如果瓶頸是讀取同一批熱門 object，與其逼 S3 承受更多請求，不如在前面放 **CloudFront** 快取（第 11 章）。

### S3 Transfer Acceleration：從遠方上傳

Wanderly 的 bucket 在東京，但歐洲與南美的旅館上傳大影片很慢，因為資料要經過許多不穩定的公共網路跳點才能到東京。**S3 Transfer Acceleration** 讓使用者先把資料上傳到離自己最近的 **CloudFront edge location**，再經由 AWS 的骨幹網路傳到 bucket 所在 Region。

- 在 bucket 啟用後，改用 `<bucket>.s3-accelerate.amazonaws.com` 這個 endpoint 上傳或下載。
- Bucket 名稱必須符合 DNS 規則，**且不能含有 `.`**。
- 依加速的傳輸量額外收費；若 AWS 判斷這次傳輸沒有比一般傳輸更快，就不收加速費。
- AWS 提供速度比較工具，可以從不同地點測試是否值得啟用。
- 對同一個 Region 內的傳輸沒有幫助。

Transfer Acceleration 通常和 multipart upload 一起使用：前者縮短長距離傳輸的延遲與丟包，後者平行化並讓失敗的 part 可以單獨重傳。如果要一次搬移數百 TB 的既有資料，則要考慮 DataSync、Direct Connect 或離線設備（第 25 章）。

## 22.13 其他常考功能：Requester Pays、S3 Select 與 Object Lambda

### Requester Pays：讓下載者付費

一般情況下，bucket 擁有者支付所有儲存、請求與資料傳出費用。Wanderly 想把匿名化後的旅遊趨勢資料集提供給大學與合作夥伴研究，但不想替所有下載者支付流量費。啟用 **Requester Pays** 後：

- bucket 擁有者仍付**儲存**費用；**請求費用與資料傳出費用由請求者支付**。
- 請求者必須是**已驗證的 AWS 身份**（不支援匿名存取），並在請求中帶上 `x-amz-request-payer: requester`（CLI 為 `--request-payer requester`），表示知道自己要付費。
- 跨帳號存取仍需要 bucket policy 授權對方的帳號或 role。

這是「把大型資料集分享給其他 AWS 帳號、成本由使用方承擔」的標準答案。

### S3 Select：已不推薦給新設計

**S3 Select** 允許用簡單的 SQL 從單一 CSV、JSON 或 Parquet object 中只取出符合條件的資料，減少傳輸量。但 **AWS 已自 2024 年 7 月起不再對新客戶開放 S3 Select**（既有客戶可以繼續使用）。同一時間停止對新客戶開放的還有 **S3 Glacier Select**（對 Glacier 封存資料下 SQL 的功能）。舊題目可能仍以 S3 Select 為答案；在新設計中，替代方案是：

- **Amazon Athena**：直接對 S3 上的資料下 SQL，可以跨大量檔案、使用分區與欄式格式（Parquet），按掃描量計費（第 30 章）。
- 在應用程式中自行讀取：用 byte-range fetch 只讀需要的部分，或使用 Parquet 這類格式讓程式只讀需要的欄位。

### S3 Object Lambda：讀取時即時轉換

**S3 Object Lambda** 讓你在 GET 請求的路徑上插入一個 Lambda function：應用程式透過 Object Lambda Access Point 讀取 object 時，Lambda 先取得原始資料，做轉換（例如遮蔽個資、浮水印、縮放圖片、轉換格式）後再回傳。這樣同一份原始資料可以依不同呼叫者呈現不同內容，不必預先產生多份副本。

自 2025 年 11 月 7 日起，S3 Object Lambda 只提供給既有客戶（與少數 AWS 合作夥伴方案），新客戶無法啟用，AWS 也不再為它新增功能。寫新設計時應改用 API 層的轉換：例如由 API Gateway 或 Lambda function URL 呼叫 Lambda 讀取 S3 後轉換回傳；圖片處理可用 AWS 提供的 Dynamic Image Transformation for Amazon CloudFront 解決方案；或乾脆在用戶端應用程式中處理。這些替代方案都繼續使用原本的 S3 bucket，不需要搬移資料。考試若出現「不同使用者讀同一份資料時要看到不同版本（例如遮蔽 PII），且不想存多份副本」，Object Lambda 仍是這個需求的典型對應功能。

## 22.14 組起來：Wanderly 的照片平台

把本章的元件組合起來：

```text
   旅館人員瀏覽器                                      旅客瀏覽器
        │ ①要求上傳                                        │ ⑥ https://img.wanderly.com
        ▼                                                  ▼
 [API Gateway + Lambda]                          [CloudFront + ACM 憑證]
   簽發 presigned PUT                                      │ ⑦ OAC（SigV4 簽章）

        └──► 瀏覽器直接 PUT ───► ┌──────────────────────────────────────────┐
                                │ S3: wanderly-hotel-photos-prod (東京)    │
                                │  BPA 全開｜ACL disabled｜SSE-KMS｜版本控制 │
                                │  uploads/   private/   public/           │
                                └───┬──────────────────────────────────────┘
                                    │ ③ ObjectCreated（uploads/）
                                    ▼
                          [EventBridge default bus]
                     ┌──────────────┼───────────────┐
                     ▼              ▼               ▼
              [縮圖 Lambda]   [審查 Step Functions] [SQS → 索引 worker]

                     ▼
```

① 旅館人員登入後向 API 要求上傳，API 判斷權限後回傳 presigned URL。② 瀏覽器直接把檔案 PUT 到 `uploads/`（大檔用 multipart upload，CORS 只允許 `partner.wanderly.com`）。③ 上傳完成觸發 EventBridge，三個獨立流程各自處理。④ 縮圖寫到 `public/`，不會再次觸發 `uploads/` 的規則。⑤ 分析團隊在另一個帳號，透過兩邊都授權的方式唯讀 `public/`。⑥⑦ 旅客透過 CloudFront 以 HTTPS 取得照片，bucket 本身從未公開。`private/` 的營業登記文件只有後台 role 能讀，必要時以 15 分鐘的 presigned GET 讓旅館下載。

## 22.15 比較與選型

### 權限機制對照

| 機制 | 控制對象 | 能授權嗎 | 能拒絕嗎 | 適合 |
|---|---|---|---|---|
| IAM policy | 某個 user／role 能做什麼 | 能 | 能 | 同帳號存取、一個 role 存取多個服務 |
| Bucket policy | 誰能存取這個 bucket | 能（含跨帳號、AWS 服務） | 能 | 跨帳號、強制 HTTPS／加密／VPC、CloudFront OAC |
| Access Point policy | 誰能經由這個入口存取 | 能（需 bucket policy 委派） | 能 | 多團隊共用 bucket、限定 VPC 入口 |
| ACL | 個別 bucket／object | 能（只限帳號／群組） | 不能 | 舊系統相容，建議停用 |
| Block Public Access | 公開存取 | 不能 | 能（只擋公開） | 防止意外公開的總開關 |
| SCP／RCP | 整個帳號或 OU | 不能 | 能（設上限） | 組織層級護欄（第 14 章） |
| Presigned URL | 單一 object、單一動作、限時 | 借用簽章者權限 | — | 沒有 AWS 身份的使用者上傳／下載 |

### 「讓外部的人存取 S3 資料」選型

```text
存取者是誰？
├─ 網際網路上的一般使用者（瀏覽器）
│   ├─ 公開內容（照片、網站） → CloudFront + OAC + 私有 bucket
│   └─ 個人化或私密檔案、限時 → presigned URL（或 CloudFront signed URL／cookie，第 11 章）
├─ 另一個 AWS 帳號
│   ├─ 同一 Organization 的所有帳號 → bucket policy + aws:PrincipalOrgID
│   ├─ 特定 role、資料量大且要對方付流量 → bucket policy + Requester Pays
│   └─ 很多團隊、各自不同權限 → S3 Access Points
└─ 公司內部網路（VPC）
    └─ gateway endpoint + bucket policy aws:SourceVpce，或 VPC-only Access Point（第 6 章）
```

### 上傳／下載效能手段

| 問題 | 手段 |
|---|---|
| 單檔超過 5 GB，或大檔上傳常中斷 | Multipart upload |
| 遠距離上傳慢 | Transfer Acceleration（+ multipart） |
| 大檔下載慢、只要部分內容 | Byte-range fetch 平行下載 |
| 503 Slow Down | 指數退避重試、分散 prefix |
| 同一批熱門內容被大量讀取 | CloudFront 快取 |
| 一次搬移數百 TB 既有資料 | DataSync；Snow 系列（Snowball Edge 已不開放新客戶，見第 25 章） |

## 22.16 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 寫入後立即讀取／LIST 要看到最新資料 | S3 已是 strong read-after-write consistency，不需額外機制 |
| 檔案大於 5 GB、上傳常失敗要續傳 | Multipart upload |
| 未完成的上傳占用費用 | Lifecycle `AbortIncompleteMultipartUpload` |
| 誤刪或誤覆寫要能復原 | Versioning（刪除 delete marker 或還原舊版本） |
| 確保任何 bucket 都不會被公開 | 帳號層級 Block Public Access（+ SCP） |
| 跨帳號上傳的 object 擁有權混亂、要停用 ACL | Object Ownership：Bucket owner enforced |
| 強制所有存取使用 HTTPS | Bucket policy Deny `aws:SecureTransport = false` |
| 只允許組織內帳號存取 | Bucket policy `aws:PrincipalOrgID` |
| 沒有 AWS 帳號的使用者限時上傳／下載 | Presigned URL |
| 瀏覽器呼叫 S3 出現跨來源錯誤 | 被呼叫的 bucket 設定 CORS |
| 靜態網站需要 HTTPS、bucket 不能公開 | CloudFront + OAC + 私有 bucket |
| 同一事件要給多個處理程序 | SNS fan-out 到多個 SQS，或 EventBridge |
| 全球各地上傳到單一 Region 很慢 | S3 Transfer Acceleration |
| 503 Slow Down、高請求率 | 分散 prefix、平行化、指數退避 |
| 下載者應負擔流量費 | Requester Pays |
| 多團隊共用 bucket、policy 太大 | S3 Access Points |
| 只能從 VPC 內存取 bucket | Gateway endpoint + `aws:SourceVpce`，或 VPC-only Access Point |
| 只取 object 中的部分資料（舊題 S3 Select） | 新設計用 Athena 或 byte-range fetch |

**常見陷阱**：

1. **ListBucket 與 GetObject 的 Resource 寫反**：前者是 bucket ARN，後者是 `bucket/*`。
2. **以為跨帳號只要 bucket policy 允許即可**：對方帳號的 IAM policy 也必須允許；SSE-KMS 加密的資料還需要 KMS key 權限。
3. **以為 presigned URL 可以擴大權限或繞過 Deny**：它只能做簽章者能做的事；用臨時 credentials 簽的網址會隨 credentials 一起失效。
4. **把 CORS 當成權限機制**：它只影響瀏覽器，不影響授權結果。
5. **把 versioning 當成完整備份**：版本和原資料在同一個 bucket、同一個帳號。
6. **為了讓 CloudFront 讀取而關閉 Block Public Access**：OAC 授權的是 CloudFront 服務，不是公開存取，BPA 可以維持全開。
7. **在新設計推薦 S3 Select 或 Object Lambda**：兩者都已不再開放給新客戶，要說明替代方案。

## 22.17 SAP 加深：大規模共享、組織護欄與遷移舊權限

### 資料邊界（data perimeter）

SAP 題目常要求「確保公司資料只能被公司的身份、從公司的網路存取」。這可以用三種條件組合成 **data perimeter（資料邊界）**：

- **身份邊界**：bucket policy 對 `aws:PrincipalOrgID` 不等於自己組織 ID 的請求 Deny，外部帳號即使被誤授權也無法存取。
- **網路邊界**：對不是來自公司 VPC endpoint（`aws:SourceVpce`）或公司 IP 範圍的請求 Deny。實務上要排除 AWS 服務代表你存取的情況（例如使用 `aws:PrincipalIsAWSService` 或 `aws:ViaAWSService` 條件），以免擋掉 CloudTrail 寫日誌這類合法流量。
- **資源邊界**：在 VPC endpoint policy 中只允許存取自己組織的 bucket（`aws:ResourceOrgID`），防止內部人員把資料上傳到外部的 bucket。

逐一在每個 bucket policy 寫這些規則難以維護，所以組織層級會用 **SCP** 限制「我的 principal 能做什麼」，用 **RCP（resource control policy）** 統一限制「我的資源能被誰存取」，兩者都在第 14 章說明。

### 大量團隊共用資料湖

當資料湖有數十個消費者帳號時，常見演進是：bucket policy 只保留強制規則（HTTPS、加密、組織邊界）並把存取委派給 Access Points；每個消費者團隊一個 access point，必要時設為 VPC-only；若需要表格與欄位層級的權限，改用 Lake Formation（第 30 章）。這樣權限變更被侷限在單一 access point，blast radius 小，也避免 bucket policy 20 KB 上限。

### 把舊 bucket 從 ACL 遷移到 policy

併購的旅行社有一個用了十年的 bucket，合作夥伴靠 object ACL 取得讀取權限。安全團隊要求停用 ACL，但不能讓夥伴中斷。安全的遷移步驟是：

1. 盤點：檢查 bucket 與 object 的 ACL、用 CloudTrail 或 server access logs 找出哪些請求依賴 ACL 授權。
2. 把 ACL 表達的授權改寫成 bucket policy（或 access point policy）。
3. 先切到 **Bucket owner preferred** 或直接驗證 policy 生效後，再切到 **Bucket owner enforced**。若發現問題，Object Ownership 可以改回，原本的 ACL 會恢復作用。
4. 用 IAM Access Analyzer 確認沒有預期之外的外部存取。

### 事件驅動架構的規模化

數十個團隊都想訂閱同一個 bucket 的事件時，直接通知會遇到「同事件不能重疊」的限制，而 SNS fan-out 需要每個團隊建立 queue 並向中央團隊申請訂閱。改成 EventBridge 後，可以把事件路由到各團隊帳號的 event bus（跨帳號 event bus），由各團隊自己寫 rule，中央團隊只維護 bucket 端的設定（第 32 章）。

## 本章重點整理

- S3 是以 HTTPS API 存取的 object storage：bucket 屬於一個 Region、名稱全域唯一，key 是扁平的字串，`/` 與「資料夾」只是 prefix 的顯示方式。
- Object 只能整份寫入或覆寫，不支援局部修改、檔案鎖或 POSIX 語意；需要這些時改用 EBS、EFS 或 FSx。
- S3 Standard 設計為 11 個 9 耐久度、99.99% 可用度並跨至少三個 AZ，但耐久度不保護你不被自己的刪除指令影響。
- S3 對 PUT、覆寫、DELETE、LIST 提供 strong read-after-write consistency，但不提供跨多個 object 的交易；同時寫入以最後一個為準，可用 conditional writes 避免覆蓋。
- 單一 PUT 上限 5 GB，大於 100 MB 建議 multipart upload，parts 可平行上傳、失敗可單獨重傳；未完成的上傳要用 lifecycle 自動清除。
- Versioning 讓一般刪除變成 delete marker、覆寫保留舊版本；啟用後只能暫停不能關閉，且所有版本都計費。
- 同帳號存取是 IAM policy 與 bucket policy 的聯集，跨帳號存取是兩者的交集；任何 explicit deny 都優先。
- `s3:ListBucket` 的 Resource 是 bucket ARN，object 動作的 Resource 是 `bucket/*`；Principal 只出現在 resource-based policy。
- 新 bucket 預設 Block Public Access 全開、ACL disabled（Bucket owner enforced）與 SSE-S3 加密；組織層級應在帳號層級開啟 BPA 並以 SCP 保護。
- Presigned URL 讓沒有 AWS 身份的人限時執行單一動作，權限不超過簽章者，臨時 credentials 到期網址也會失效。
- CORS 只是瀏覽器的跨來源規則，設定在被呼叫的 bucket，不是權限機制。
- S3 website endpoint 只支援 HTTP 且需公開 bucket；需要 HTTPS 與私有 bucket 時用 CloudFront + OAC。
- Event notifications 可送 SQS（standard）、SNS、Lambda，或全部送到 EventBridge；同一事件要給多個消費者時用 SNS fan-out 或 EventBridge，處理程式要冪等。
- 每個 prefix 每秒至少 3,500 個寫入與 5,500 個讀取請求，要更高吞吐量就分散 prefix 並平行化；遠距離上傳用 Transfer Acceleration。
- Requester Pays 讓請求者負擔請求與傳輸費；S3 Select 與 Object Lambda 已不再開放給新客戶，新設計改用 Athena 或 API 層轉換。

### 練習 22-1｜SAA｜單選｜S3 一致性模型

Wanderly 的訂房確認服務會把每筆訂單的 PDF 憑證寫到 S3，接著立刻由另一個服務以相同 key 讀取並寄給旅客。旅客修改訂單時，系統會用同一個 key 覆寫新的 PDF，再立刻讀取寄出。一位工程師提議在每次寫入後等待 5 秒，以免寄出舊版本的憑證。

關於這個設計，哪個敘述正確？

- A. 新 object 的 PUT 是強一致，但覆寫是最終一致，所以修改訂單時仍需等待
- B. S3 對新增、覆寫與刪除後的讀取都提供強一致性，寫入成功後立刻讀取就會得到最新內容，不需要等待
- C. 應改用 DynamoDB 儲存 PDF，因為只有 DynamoDB 支援 read-after-write consistency
- D. 應開啟 versioning，S3 才會對覆寫提供強一致性

> [!answer]- 答案：B
> **A ✗** 這是 2020 年以前的舊行為。現行 S3 對覆寫同樣提供 strong read-after-write consistency。
>
> **B ✓** 自 2020 年 12 月起，S3 對所有 PUT（新增與覆寫）、DELETE 與 LIST 提供強一致性，無需設定也不額外收費。寫入成功回應後的 GET 一定拿到最新內容，等待只會增加延遲。
>
> **C ✗** DynamoDB 單一 item 最大 400 KB，不適合存 PDF 檔；而且 S3 本身就已經強一致。
>
> **D ✗** 強一致性與 versioning 無關，未開啟 versioning 的 bucket 一樣適用。Versioning 解決的是誤刪與誤覆寫的復原。
>
> **考點**：SAA-3.1｜S3 strong read-after-write consistency

### 練習 22-2｜SAA｜選兩項｜大檔上傳與未完成上傳

Wanderly 的影片團隊每天從各地辦公室上傳 20 到 80 GB 的原始影片到 S3。目前使用自寫程式以單一 PUT 上傳，大檔一律失敗；改用分段上傳的測試版後，又發現帳單上的 S3 儲存量比 bucket 中實際檔案總和大很多。團隊希望上傳可靠，並避免為看不見的資料付費。

哪兩個做法最合適？（選兩項）

- A. 使用 multipart upload，把檔案分成多個 part 平行上傳，失敗時只重傳失敗的 part
- B. 把單一 PUT 的大小上限調整為 100 GB 的 service quota
- C. 開啟 versioning，讓失敗的上傳自動回到前一個版本
- D. 建立 lifecycle rule，使用 `AbortIncompleteMultipartUpload` 在上傳開始數天後清除未完成的上傳
- E. 啟用 S3 Transfer Acceleration，讓 S3 自動合併未完成的 part

> [!answer]- 答案：A、D
> **A ✓** 單一 PUT 最多 5 GB，大於這個大小必須使用 multipart upload。它能平行傳輸 part，任何一個 part 失敗只要重傳那一段，正好處理大檔與不穩定網路。
>
> **B ✗** 單一 PUT 5 GB 是固定的 API 限制，不是可以申請提高的 quota。
>
> **C ✗** Versioning 保存的是已完成 object 的歷史版本，與未完成的 multipart upload 無關，也不會讓失敗的上傳自動處理。
>
> **D ✓** 開始後沒有 complete 或 abort 的 multipart upload，已上傳的 part 會持續計費且不會出現在 object 列表中，正是儲存量比可見檔案大的原因。`AbortIncompleteMultipartUpload` lifecycle action 會自動清除它們。
>
> **E ✗** Transfer Acceleration 經由 edge location 加速長距離傳輸，可與 multipart 搭配，但它不會清理或合併未完成的 part。
>
> **考點**：SAA-3.1、SAA-4.1｜multipart upload 與 AbortIncompleteMultipartUpload

### 練習 22-3｜SAA｜選兩項｜瀏覽器直接上傳

Wanderly 的旅館後台網站位於 `https://partner.wanderly.com`，旅館人員沒有 AWS 帳號。團隊要讓他們從瀏覽器把照片直接上傳到私有 bucket 的 `uploads/<hotelId>/` 之下，不經過應用伺服器轉傳，且每次授權只能在短時間內寫入一個由系統決定的 key。測試時瀏覽器 console 顯示請求被跨來源規則阻擋。

哪兩個做法能滿足需求？（選兩項）

- A. 由後端 API 驗證使用者身份後，以具備 `s3:PutObject` 權限的 role 產生有效期 15 分鐘、指定 key 的 presigned URL
- B. 在 bucket policy 允許 `Principal: "*"` 對 `uploads/*` 執行 `s3:PutObject`，並關閉 Block Public Access
- C. 在 bucket 設定 CORS，允許來源 `https://partner.wanderly.com` 使用 PUT

> **C ✓** CORS 要設在**被呼叫的資源**上，也就是 S3 bucket，讓瀏覽器知道 S3 允許來自後台網域的 PUT 請求。CORS 只解決瀏覽器的跨來源阻擋，真正的授權仍由 presigned URL 簽章決定。
>
> **D ✗** CORS 回應標頭必須由被呼叫的一方（S3）提供；在發起請求的網站伺服器上設定沒有效果。
>
> **E ✗** 把長期 access key 放在前端程式碼中，任何人都能從瀏覽器取出，屬於嚴重的 credentials 外洩風險。
>
> **考點**：SAA-1.2、SAA-1.3｜presigned URL 與 S3 CORS

### 練習 22-4｜SAA｜單選｜跨帳號上傳的 object 擁有權

最合適的做法是什麼？

- A. 要求所有上傳者在 PUT 時加上 `public-read` ACL，讓稽核 role 可以讀取

- C. 把 Object Ownership 設為 Object writer，並在 bucket policy 允許稽核 role 讀取
- D. 把 Object Ownership 設為 Bucket owner enforced 以停用 ACL，並用 bucket policy 授權各 workload 帳號寫入、稽核 role 讀取

>
> **C ✗** Object writer 正是造成問題的設定：上傳者擁有 object，bucket 擁有者無法自動取得權限。
>
> **D ✓** Bucket owner enforced 停用所有 ACL，bucket 擁有者自動擁有所有 object，權限完全由 policy 決定，上傳端不需要帶任何 ACL header。跨帳號寫入與稽核讀取都在 bucket policy 中授權。

### 練習 22-6｜SAA｜單選｜Bucket policy 的 Resource

最可能的原因與修正方式是什麼？

- A. 同帳號存取時 bucket policy 也必須明確允許 ListBucket，需在 bucket policy 加上相同的 Allow
- B. ListObjectsV2 需要 `s3:ListObjectsV2` 權限，應把動作名稱改成它
- C. `s3:ListBucket` 是作用在 bucket 上的動作，Resource 必須是 `arn:aws:s3:::wanderly-reports`，應另加一條以 bucket ARN 為 Resource 的 Allow
- D. Block Public Access 會阻擋 LIST 操作，需要關閉 `RestrictPublicBuckets`

> [!answer]- 答案：C
> **A ✗** 同帳號時 IAM policy 與 bucket policy 是聯集，任一邊 Allow 即可，不必兩邊都寫。問題在 IAM policy 本身的 Resource。
>

>
> **C ✓** 列出 object 是對 bucket 的操作，Resource 寫成 `bucket/*` 永遠不會匹配，所以 LIST 被拒，而 GetObject 作用在 object 上所以正常。修正方式是把 ListBucket 的 Resource 改成 bucket ARN（不加 `/*`）。
>
> **D ✗** Block Public Access 只影響公開存取，對同帳號具名 role 的 LIST 沒有影響。
>
> **考點**：SAA-1.1、SAA-1.3｜S3 動作與 bucket／object ARN 的對應

>

> **D ✗** S3 Inventory 是每日或每週產生的清單報表，無法滿足上傳後立即處理的需求。
>

### 練習 22-8｜SAA｜單選｜503 Slow Down

### 練習 22-10｜SAA｜單選｜誤刪復原

Wanderly 的照片 bucket 已啟用 versioning。一位行銷人員執行同步工具時，誤把 `public/hotels/1234/` 下的 300 張照片刪除（工具送出的是不指定 version ID 的一般 DELETE）。網站上這些照片現在顯示 404，團隊要盡快恢復原本的照片。

- A. 從 S3 回收站（recycle bin）還原被刪除的 object
- B. 刪除這些 key 目前的 delete marker，讓前一個版本重新成為目前版本
- C. 暫停 versioning，S3 會自動把最近被刪除的 object 恢復

> **A ✗** S3 沒有 recycle bin 功能（Recycle Bin 是 EBS snapshot 與 AMI 的功能，見第 24 章）。Versioning 本身就扮演這個角色。

> **C ✗** 暫停 versioning 只影響之後的寫入，不會還原任何東西。
>
> **D ✗** 只有指定 version ID 的刪除才會永久移除版本；本題的一般 DELETE 可以復原。
>
> **考點**：SAA-1.3、SAA-2.2｜versioning 與 delete marker

### 練習 22-11｜SAP｜單選｜多團隊共用資料湖 bucket

Wanderly 的資料湖 bucket 由 14 個團隊共用，每個團隊只能存取自己的 prefix，其中 3 個團隊的資料規定只能從公司 VPC 存取。目前所有權限都寫在單一 bucket policy 中，大小已接近 20 KB 上限，且每次調整權限都需要中央平台團隊審查整份 policy，曾經因為一個錯字讓所有團隊中斷 30 分鐘。

哪個改善方式最合適？

- A. 為每個團隊複製一個獨立 bucket，並用 SRR 從資料湖 bucket 同步資料
- B. 把 bucket policy 拆成多份，以 policy 版本控制輪流套用
- C. 為每個團隊建立 S3 Access Point 與各自的 access point policy，需要內部存取的團隊使用 network origin 為 VPC 的 access point，bucket policy 只保留強制規則並委派存取給本帳號的 access points
- D. 改用 object ACL 為每個團隊的 object 授權，以避開 bucket policy 大小限制

> [!answer]- 答案：C
> **A ✗** 14 份資料副本會倍增儲存與複寫成本，還要處理同步延遲與資料一致性，不是權限管理問題的合理解法。
>
> **B ✗** 一個 bucket 只能有一份 bucket policy，無法拆成多份同時生效。
>
> **C ✓** Access Points 讓每個團隊有自己的入口與 policy，權限調整只影響那個 access point，縮小 blast radius；VPC network origin 讓指定 access point 只接受 VPC 內的請求。Bucket policy 只保留 HTTPS、加密等全域規則並委派給 access points，就不會再接近大小上限。
>
> **D ✗** ACL 分散在每個 object 上、無法集中稽核，也不支援條件（例如限制 VPC），與停用 ACL 的最佳實務相反。
>
> **考點**：SAP-2.3、SAP-3.2｜S3 Access Points 委派與 VPC-only 存取

### 練習 22-12｜SAP｜單選｜跨帳號讀取 SSE-KMS 資料

Wanderly 的財務資料 bucket 位於帳號 A，預設加密為 SSE-KMS，使用帳號 A 的 customer managed key。帳號 B 的對帳服務 role 需要讀取 `settlements/` 下的檔案。帳號 A 已在 bucket policy 中允許該 role 執行 `s3:GetObject`，帳號 B 也已在該 role 的 IAM policy 中允許同樣動作，但讀取時仍收到 AccessDenied。

還缺少什麼？

- A. 帳號 A 的 KMS key policy 需允許帳號 B（或該 role）使用該 key 解密，且帳號 B 的 role IAM policy 需允許對該 key ARN 執行 `kms:Decrypt`
- B. 帳號 A 需要把 Object Ownership 改為 Object writer，讓帳號 B 成為 object 擁有者
- C. 帳號 A 需要關閉 Block Public Access，跨帳號的 GetObject 才會被允許
- D. 帳號 B 需要在 bucket policy 中加入 `kms:Decrypt`，S3 會自動把該權限同步到 key policy

> [!answer]- 答案：A
> **A ✓** SSE-KMS 加密的 object 需要通過 S3 與 KMS 兩道授權。S3 這一層兩邊都已允許，但 KMS key 在帳號 A，跨帳號使用必須由 key policy 允許外部帳號或 role，外部帳號的 IAM policy 也必須允許對該 key 執行 `kms:Decrypt`（第 15 章）。
>
> **B ✗** Object Ownership 決定誰擁有新上傳的 object，與讀取 KMS 加密資料的授權無關；改成 Object writer 也違反停用 ACL 的最佳實務。
>
> **C ✗** BPA 只擋公開存取，對具名跨帳號 principal 的授權沒有影響。
>
> **D ✗** Bucket policy 只能控制 S3 動作，不能授權 KMS key 的使用；KMS 權限只能由 key policy、grants 與 IAM policy 授予，也沒有自動同步機制。
>
> **考點**：SAP-2.3、SAP-1.2｜跨帳號 S3 存取與 SSE-KMS 的雙重授權

### 練習 22-13｜SAP｜選兩項｜組織層級的 S3 護欄

Wanderly 已有 40 個 AWS 帳號，全部在同一個 AWS Organization 中。資安長要求：一、任何帳號都不能讓 S3 資料公開，且應用團隊不能自行取消這項保護；二、核心資料 bucket 只能被組織內的 principal 存取，即使有人誤在 bucket policy 中授權外部帳號也不能生效。團隊希望用最少的逐一維護達成。

哪兩個做法最合適？（選兩項）

- A. 在每個 bucket 啟用 versioning 與 MFA Delete
- B. 在每個帳號啟用帳號層級 S3 Block Public Access，並以 SCP 拒絕 `s3:PutAccountPublicAccessBlock` 等變更此設定的動作
- C. 在核心資料 bucket policy 加入一條 Deny，當 `aws:PrincipalOrgID` 不等於組織 ID 時拒絕所有 S3 動作
- D. 為每個 bucket 設定 CORS，只允許公司網域
- E. 在每個 bucket 將 Object Ownership 設為 Object writer，讓上傳者自行控管權限

> [!answer]- 答案：B、C
> **A ✗** Versioning 與 MFA Delete 保護資料不被誤刪，與公開存取及外部帳號授權無關。
>
> **B ✓** 帳號層級 BPA 一次套用到帳號內所有 bucket，優先於任何 bucket policy 與 ACL；用 SCP 禁止成員帳號修改這項設定，應用團隊即使有管理權限也無法關閉它。（組織層級 BPA 也能達到相同效果，是較新的集中化做法。）
>
> **C ✓** 以 `aws:PrincipalOrgID` 寫成的 explicit deny 會擋下所有組織外的 principal，即使同一份 policy 的其他 statement 誤授權外部帳號，Deny 仍然優先。若要擴大到所有 bucket 而不逐一修改，可進一步改用 RCP（第 14 章）。
>
> **D ✗** CORS 只影響瀏覽器的跨來源行為，不是權限控制，無法阻止 API 存取。
>
> **E ✗** Object writer 讓權限分散在上傳者手中，與集中控管的目標相反。
>
> **考點**：SAP-1.4、SAP-2.3｜帳號層級 BPA、SCP 與 aws:PrincipalOrgID 資料邊界

### 練習 22-14｜SAP｜單選｜S3 Select 的替代方案

Wanderly 剛為新併購的子公司建立一個全新的 AWS 帳號。子公司原本在另一家公司環境中有一支程式，使用 S3 Select 從每天數千個 CSV 檔中過濾出特定旅館的訂單，再匯總成報表。遷移到新帳號後，S3 Select 呼叫失敗。團隊希望用 SQL 繼續查詢、不管理伺服器，並能跨大量檔案查詢。

最合適的做法是什麼？

- A. 向 AWS Support 申請在新帳號啟用 S3 Glacier Select 作為替代
- B. 在 EC2 上部署 Presto 叢集，掛載 S3 作為檔案系統
- C. 把所有 CSV 匯入 DynamoDB，使用 Scan 搭配 filter expression 過濾
- D. 以 Glue Data Catalog 定義資料表結構，改用 Amazon Athena 直接對 S3 上的資料下 SQL，並考慮轉成 Parquet、依日期分區以降低掃描量

> [!answer]- 答案：D
> **A ✗** Glacier Select 同樣已不再開放給新客戶，而且它針對封存資料，不是日常報表的合適選擇。
>
> **B ✗** 自建 Presto 叢集需要管理伺服器與擴展，違反「不管理伺服器」；S3 也不是可直接掛載的檔案系統。
>
> **C ✗** 把檔案資料搬到 DynamoDB 並用 Scan 過濾，成本高、效率差，也失去 SQL 匯總能力。
>
> **D ✓** S3 Select 自 2024 年 7 月起不再開放給新客戶，新帳號無法使用。Athena 是 serverless 的 SQL 查詢服務，可跨大量 S3 檔案查詢、按掃描量計費；轉成欄式格式並分區能大幅降低掃描量與費用（第 30 章）。
>
> **考點**：SAP-4.4、SAP-3.3｜S3 Select 現況與 Athena 替代

### 練習 22-15｜SAP｜單選｜大型資料集分享

Wanderly 想把 400 TB 匿名化的歷史旅遊趨勢資料提供給 30 個大學研究團隊與合作夥伴，對方都有自己的 AWS 帳號，每個團隊每月可能下載數十 TB。財務部門要求 Wanderly 只負擔儲存費用，下載產生的請求與資料傳輸費用由使用方負擔。

最合適的做法是什麼？

- A. 把資料放在 S3，關閉 Block Public Access 並設為公開讀取，再請研究團隊自行負擔網路費用
- B. 對 bucket 啟用 Requester Pays，並在 bucket policy 中授權這些合作帳號讀取；對方在請求中確認自己支付費用
- C. 為每個研究團隊產生有效 7 天的 presigned URL，每週重新寄送
- D. 用 CRR 把資料複寫到每個研究團隊的帳號，由對方支付儲存費

> [!answer]- 答案：B
> **A ✗** 公開讀取時下載者是匿名的，資料傳出費仍由 bucket 擁有者支付，無法轉嫁費用；也違反預設安全基線。
>
> **B ✓** Requester Pays 讓 bucket 擁有者只付儲存費，請求與資料傳出費由已驗證的請求者支付。請求者必須在請求中帶上 `x-amz-request-payer` 確認付費，bucket policy 則控制哪些帳號能讀取。
>
> **C ✗** Presigned URL 的請求是以簽章者身份執行的，費用仍由 Wanderly 負擔；每週為大量 object 重新產生網址的營運負擔也很高。
>
> **D ✗** 複寫 400 TB 到 30 個帳號由 Wanderly 支付複寫請求費用（跨 Region 時還有傳輸費），還要維護 30 條複寫規則與 30 份完整副本，遠比讓對方按需讀取昂貴且難管理。
>
> **考點**：SAP-1.5、SAP-2.6｜S3 Requester Pays

### 練習 22-16｜SAP｜單選｜從 ACL 遷移到 policy

Wanderly 併購的旅行社有一個運作十年的 S3 bucket，Object Ownership 為 Object writer。其中約 80 萬個 object 透過 object ACL 授權給兩個合作夥伴帳號讀取。安全團隊要求停用 ACL，但遷移過程中不能讓合作夥伴的讀取中斷。

哪個做法最安全？

- A. 立即把 Object Ownership 改為 Bucket owner enforced，若合作夥伴回報錯誤再逐一處理
- B. 刪除 bucket 中所有 object 的 ACL，再要求合作夥伴改用 presigned URL
- C. 先盤點現有 ACL 並用 CloudTrail 或 server access logs 確認哪些請求依賴 ACL，把這些授權改寫進 bucket policy 並驗證合作夥伴可正常讀取，最後再把 Object Ownership 改為 Bucket owner enforced
- D. 開啟帳號層級 Block Public Access，S3 會自動把非公開的 ACL 轉換為 bucket policy

> [!answer]- 答案：C
> **A ✗** 一切換成 Bucket owner enforced，所有 ACL 立即失效，依賴 ACL 的合作夥伴會馬上 AccessDenied，違反「不能中斷」。
>
> **B ✗** 先刪 ACL 會立即造成中斷；改用 presigned URL 也要求合作夥伴大幅修改流程，且有網址到期與管理問題。
>
> **C ✓** 先找出 ACL 實際承載的授權，以 bucket policy 等價授予並驗證，再停用 ACL，這樣切換當下權限已經由 policy 提供，不會中斷。若切換後發現遺漏，Object Ownership 可以改回，原本的 ACL 會恢復作用，風險可控。
>
> **D ✗** BPA 只阻擋公開存取，不會轉換 ACL；授權給具名合作帳號的 ACL 也不受 BPA 影響。
>
> **考點**：SAP-3.2、SAP-4.3｜Object Ownership 遷移與停用 ACL
