# 第 25 章　資料移轉與混合儲存：Storage Gateway、DataSync、Transfer Family 與 Snow

> [!abstract] 本章地圖
> **你會學到**：
> - 用「資料量 ÷ 有效頻寬」估算線上傳輸需要幾天，判斷該走網路、Direct Connect 還是離線方式
> - 分辨 Storage Gateway 的 S3 File、Volume（cached／stored）、Tape 三種模式，以及 FSx File Gateway 的現況
> - 用 DataSync 設計一次性搬遷與持續增量同步：agent、location、task、篩選、頻寬限制、驗證與私有網路路徑
> - 用 Transfer Family 取代自管的 SFTP／FTPS／FTP／AS2 伺服器，並把每個合作夥伴限制在自己的目錄
> - 說明 Snow Family 的現況（Snowball Edge 不再開放新客戶、Snowcone 與 Snowmobile 已停止）與替代方案
>
> **前置知識**：第 22–24 章（S3、EBS、EFS、FSx）、第 8 章（VPN 與 Direct Connect）
> **考試比重**：SAA ★★☆（Domain 3 資料傳輸與儲存效能、Domain 4 成本）｜SAP ★★★（Domain 4 遷移、Domain 2 業務持續）

## 25.1 故事：台北辦公室的機房該退休了

Wanderly 的核心系統已經在 AWS 上跑了兩年，但台北辦公室的小機房裡還留著幾樣「歷史遺產」，每一樣都在提醒技術主管：雲端遷移還沒完成。

第一樣是一台 NAS，存著十年來攝影團隊拍的旅館原始照片與行銷影片，約 80 TB，而且攝影師每天還在往裡面加新檔案。第二樣是會計系統，它是一套只認得 NFS 路徑的老程式，每天把報表輸出到 NAS 的某個資料夾，供應商說「不可能改」。第三樣是一台磁帶機，備份軟體每週把重要資料寫到 LTO 磁帶，再由專人送去銀行保險箱。第四樣是一台跑了七年的 SFTP 伺服器，四百多家合作旅館每天把房價與空房檔案上傳到這裡。

主管給小林的目標很清楚：一年內讓這個機房只剩網路設備。但每一樣東西的搬法都不同：NAS 的資料要「搬過去」，會計系統要「繼續在辦公室用、資料卻存到雲端」，磁帶要「不改備份軟體、換掉實體磁帶」，SFTP 要「合作旅館什麼都不用改」。

這一章就是 AWS 為這些情境準備的工具箱。它們名稱相似、功能部分重疊，考試最常考的正是「分辨該用哪一個」。我們先從最根本的問題開始：資料到底要花多久才搬得過去？

## 25.2 先算一筆帳：線上傳輸要幾天？

所有資料移轉的決策，都從一個簡單的除法開始。網路頻寬的單位是 **bit per second（bps）**，資料量的單位是 **byte**，1 byte = 8 bits。這個 8 倍的差距是最常見的計算錯誤。

```text
             資料量（bytes）× 8
傳輸秒數 = ─────────────────────────────
           頻寬（bps）× 可用比例 × 傳輸效率

以 1 Gbps、100% 使用為例：
  1 Gbps = 1,000,000,000 bits/s ÷ 8 = 125 MB/s
  125 MB/s × 86,400 秒 ≈ 10.8 TB／天（理論上限）
```

**可用比例**是這條線路能分給搬遷用的比例：辦公室的網路白天還要給員工開會、上網，通常只能分出一部分。**傳輸效率**則反映 TCP 協定開銷、加密、檔案系統的 metadata 操作與重試，實務上抓 70%–80% 比較保險；大量小檔案的情況還會更低。

用 80% 效率估算的對照表：

| 有效頻寬 | 每天約可傳輸 | 10 TB | 100 TB | 1 PB |
|---|---|---|---|---|
| 100 Mbps | 0.86 TB | 約 12 天 | 約 116 天 | 約 3.2 年 |
| 1 Gbps | 8.6 TB | 約 1.2 天 | 約 12 天 | 約 116 天 |
| 10 Gbps | 86 TB | 約 3 小時 | 約 1.2 天 | 約 12 天 |

小林算了 NAS 的帳：辦公室是 1 Gbps 的 Internet 線路，主管同意搬遷期間撥出 500 Mbps。500 Mbps × 80% = 400 Mbps = 50 MB/s，每天約 4.3 TB，80 TB 大約 19 天。一個月的期限綽綽有餘，所以 NAS 這部分走網路就可以，不需要寄送實體裝置。

但同一個算式在 Part 8 會給出完全不同的答案：Wanderly 之後併購的旅行社要搬的資料約 200 TB（300 台 VM 的磁碟、Oracle 資料庫與檔案伺服器），只靠 100 Mbps 的線路要七、八個月，還不算業務流量。這時候就需要第 8 章的 Direct Connect（專線），或 25.9 節的離線傳輸。

> [!tip] 考試提示
> 題目給了資料量和頻寬，通常就是要你算天數再比較期限。記得三件事：bits 與 bytes 差 8 倍；頻寬常常只有一部分可用；**搬遷期間來源還在持續變更**，除了初次全量複製，還要規劃後續的增量同步。

除了「多久」，還有另一個維度：這是**一次性搬遷**，還是**長期的混合存取**？NAS 要搬完就退休，屬於前者；會計系統和磁帶備份要長期在辦公室運作、只是資料改存雲端，屬於後者。後者的答案是 Storage Gateway。

## 25.3 Storage Gateway：讓地端系統「以為」自己在用本機儲存

**AWS Storage Gateway** 是一個部署在你機房裡的軟體設備，對地端的伺服器提供熟悉的儲存介面（NFS、SMB、iSCSI、虛擬磁帶），背後把資料存進 AWS。地端應用程式完全不需要知道 AWS 的存在。

### 部署方式與共同元件

- Gateway 以虛擬機器形式部署在地端的 VMware ESXi、Microsoft Hyper-V 或 Linux KVM 上；也可以部署成 EC2 instance（例如讓 AWS 上的舊應用程式用 iSCSI 存取）。
- 你要為 gateway 配置**本機磁碟**作為 **cache（快取）**：最近寫入、常被讀取的資料留在本機，讀取不必每次都跨網路，寫入也先寫到本機再非同步上傳。Volume 與 Tape 模式還有一塊 **upload buffer**，暫存等待上傳的資料。
- Gateway 透過 Internet、Direct Connect 或 Storage Gateway 的 **VPC endpoint**（PrivateLink，第 6 章）連到 AWS。若要求流量不經 Internet，就在啟用（activation）時選擇 VPC endpoint。
- 傳輸一律以 TLS 加密，存到 AWS 的資料以 SSE-S3 或 SSE-KMS 加密。

```text
  台北辦公室                                         AWS 東京 Region
 ┌───────────────────────────────────────┐        ┌──────────────────────────┐
 │ [會計系統] ──NFS──┐                   │        │                          │
 │                   ▼  ①                │        │  ③                        │
 │           ┌───────────────────┐       │  TLS   │  [S3 bucket]             │
 │           │ S3 File Gateway   │═══════╪═②════► │   每個檔案 = 一個物件    │
 │           │  本機 cache 磁碟  │       │  DX 或 │                          │
 │           └───────────────────┘       │ Internet│                          │
 │ [備份軟體] ─iSCSI─┐                   │        │                          │
 │                   ▼                   │        │                          │
 │           ┌───────────────────┐       │        │  [虛擬磁帶庫（S3）]      │
 │           │ Tape Gateway      │═══════╪══════► │    └─ eject → Glacier    │
 │           │ cache + buffer    │       │        │       Deep Archive ④     │
 │           └───────────────────┘       │        │                          │
 └───────────────────────────────────────┘        └──────────────────────────┘
```

① 地端應用程式像往常一樣寫入 NFS 共享或 iSCSI 磁帶機，資料先落在 gateway 的本機 cache，因此寫入延遲是區網等級。② Gateway 在背景把資料非同步上傳到 AWS，途中以 TLS 加密，可以走 Direct Connect 或 Internet。③ S3 File Gateway 寫入的每個檔案，在 S3 裡就是一個同名的物件，AWS 上的其他服務可以直接處理。④ Tape Gateway 的虛擬磁帶平常放在 S3，備份軟體執行 eject（退出磁帶）後移到 Glacier 的封存層，成本降到最低。

接下來依序看三種（加上一種已收斂的）gateway 模式。

## 25.4 S3 File Gateway：NFS／SMB 進去，S3 物件出來

**S3 File Gateway** 提供 NFS（v3、v4.1）與 SMB 檔案共享，每個共享對應一個 S3 bucket（或 bucket 裡的 prefix）。關鍵特性是**檔案與物件一對一對應**：會計系統寫入 `/reports/2026/09/ledger.csv`，S3 裡就出現 key 為 `reports/2026/09/ledger.csv` 的物件，檔案的權限、時間戳等 metadata 存在物件的 metadata 中。

這讓「地端繼續用檔案、雲端用物件處理」成為可能：會計報表一進 S3，就能觸發 Lambda 處理（第 22 章的 event notifications）、用 Athena 查詢（第 30 章），或用 lifecycle 自動移到便宜的 storage class（第 23 章）。

### 需要知道的行為細節

- **寫入是非同步的。** 檔案先寫進本機 cache，再上傳到 S3。若要在「檔案已經完整進入 S3」時觸發後續流程，可以使用 gateway 的檔案上傳通知（透過 EventBridge），而不是假設寫入當下就已在 S3。
- **Cache 不會自動知道 S3 端的變化。** 如果另一個程式直接把物件寫進 bucket，gateway 的檔案清單不會馬上看到它。要讓共享看見新物件，需要執行 **RefreshCache**（可以手動、排程，或設定自動 cache refresh 的時間間隔）。
- **不要讓多個寫入端同時改同一批檔案。** 多台 gateway，或 gateway 與直接寫 S3 的程式之間，沒有分散式鎖定機制。安全的設計是讓每個 prefix 只有一個寫入者，其他人唯讀。
- **Storage class**：檔案可以直接寫成 S3 Standard、Standard-IA、One Zone-IA 或 Intelligent-Tiering。已經被 lifecycle 移到 Glacier Flexible Retrieval 或 Deep Archive 的物件，無法透過 gateway 直接讀取，必須先在 S3 取回。

S3 File Gateway 也是一個常見的「備份落地」：資料庫或應用程式把備份檔寫到 SMB／NFS 共享，就自動進入 S3，再用 lifecycle 降低長期保存成本。

> [!warning] 常見誤解
> 「S3 File Gateway 是一個雲端檔案系統，可以讓好幾個辦公室同時編輯同一份檔案。」不是。它是單一站點的快取閘道，沒有跨 gateway 的檔案鎖定。多個據點協同編輯共享檔案，應該考慮 FSx for Windows File Server 或 FSx for NetApp ONTAP 這類真正的檔案伺服器（第 24 章）。

### FSx File Gateway 的現況

**Amazon FSx File Gateway** 曾經是第四種模式：在地端提供低延遲的 SMB 快取，背後連到 AWS 上的 FSx for Windows File Server。AWS 已公告 FSx File Gateway 不再提供給新客戶，既有客戶可以繼續使用。新的設計若需要讓分公司使用 AWS 上的 Windows 檔案伺服器，通常直接透過 Direct Connect 或 VPN 存取 FSx for Windows File Server；需要在地端保留快取或與地端 NetApp 整合時，則評估 FSx for NetApp ONTAP 的相關功能。看到舊題目以它為答案時，要知道它代表的概念是「Windows 檔案伺服器的地端快取」。

## 25.5 Volume Gateway：iSCSI 磁碟，cached 還是 stored？

有些地端應用程式不吃檔案共享，而是要一顆「磁碟」，例如自己格式化成 NTFS 的資料庫伺服器。**Volume Gateway** 透過 **iSCSI**（把 SCSI 磁碟指令包在 TCP/IP 裡傳輸的協定）提供 block volume，背後的資料存在 AWS。

它有兩種模式，差別在於「完整的資料放在哪裡」：

| 比較 | Cached volumes | Stored volumes |
|---|---|---|
| 完整資料（primary） | 在 AWS（S3） | 在**地端**本機磁碟 |
| 地端保留什麼 | 常用資料的 cache | 全部資料 |
| AWS 端保留什麼 | 全部資料 | 非同步的 point-in-time 備份（EBS snapshot） |
| 單一 volume 上限 | 32 TiB | 16 TiB |
| 適合 | 地端儲存空間不足、只有部分資料常用 | 需要低延遲存取**整份**資料、AWS 當異地備份 |
| 網路中斷時 | 只能存取 cache 內的資料 | 地端照常運作，備份延後上傳 |

記法很簡單：**cached = 雲端是本體、地端是快取；stored = 地端是本體、雲端是備份**。

兩種模式都能對 volume 拍 snapshot，snapshot 以 **EBS snapshot** 的形式存在 AWS。這帶來一個很有用的 DR 能力：地端機房出事時，可以在 AWS 從這些 snapshot 建立 EBS volume，掛到 EC2 上把應用程式拉起來；也可以把 snapshot 還原成新的 gateway volume。

Volume Gateway 的資料存在 AWS 管理的儲存中，**不會以一般 S3 物件的形式出現在你的 bucket**，所以你不能用 S3 API 直接讀裡面的檔案。如果需求是「地端寫入、雲端以檔案或物件處理」，那是 S3 File Gateway 的工作。

## 25.6 Tape Gateway：不改備份軟體，換掉實體磁帶

許多企業的備份流程已經運作十幾年：Veeam、Veritas NetBackup、Commvault 這類備份軟體排程把資料寫到磁帶庫，磁帶再被運到異地保存。這套流程的問題在於實體磁帶：要買、要換、要運送、會老化，還原時要先把磁帶找回來。

**Tape Gateway** 對備份軟體提供一個 **VTL（Virtual Tape Library，虛擬磁帶庫）**：透過 iSCSI 呈現虛擬的磁帶機與換片機（media changer）。備份軟體看到的是熟悉的磁帶庫，不需要改備份工作，只是磁帶變成虛擬的：

1. 備份軟體把資料寫到虛擬磁帶，gateway 上傳到 AWS，虛擬磁帶存在 S3 中，可以隨時讀取（相當於「在磁帶庫裡」）。
2. 備份軟體對磁帶執行 eject 後，虛擬磁帶移到封存層：**S3 Glacier Flexible Retrieval** 或 **S3 Glacier Deep Archive**（相當於「送到異地保險箱」），儲存成本極低。
3. 要還原封存的磁帶時，先提出取回（retrieve），磁帶回到 gateway 可讀的狀態後，備份軟體再照常讀取。取回時間依封存層而定，Flexible Retrieval 通常數小時，Deep Archive 在 12 小時內。

小林把磁帶機換成 Tape Gateway 後，備份管理員的操作幾乎沒有改變，但每週送磁帶到銀行的工作消失了。法規要求保存 7 年的備份移到 Deep Archive，成本比原本的磁帶加保管費還低。

> [!tip] 考試提示
> 題目出現「現有備份軟體」「磁帶」「不想改變備份流程」「長期封存最低成本」，答案就是 Tape Gateway + Glacier Deep Archive。如果題目說「可以改備份流程、直接備份到雲端」，則可能是 AWS Backup（第 34 章）或 S3 File Gateway。

Storage Gateway 處理的是「長期混合」。NAS 的 80 TB 則是要「搬完就關機」，這需要一個專門的搬遷引擎。

## 25.7 DataSync：受管的線上資料搬遷引擎

**AWS DataSync** 是一個線上資料傳輸服務，用來在儲存系統之間搬移或同步大量檔案與物件。你也許會問：用 `rsync` 或 `aws s3 sync` 不行嗎？小量資料當然可以，但面對 80 TB、數千萬個檔案時，自己寫腳本會遇到一連串問題：單執行緒太慢、中斷後要從頭來、不知道哪些檔案傳失敗、權限與時間戳沒保留、無法證明「搬過去的跟原本一模一樣」。DataSync 把這些都做成受管功能。

### 四個核心概念

- **Agent**：部署在地端的虛擬機器（VMware、Hyper-V、KVM），負責讀取地端的儲存並把資料送到 AWS。只有存取「AWS 無法直接連到的儲存」時才需要 agent，例如地端的 NFS、SMB、HDFS、自建物件儲存，或在 EFS／FSx 與其他雲端的儲存之間傳輸。在同一帳號的 AWS 儲存服務之間傳輸（例如 S3 到 EFS、跨 Region 的 S3 到 S3）、S3 與另一個帳號的 AWS 儲存之間、以及 S3 與其他雲端的物件儲存之間，**都不需要 agent**。例外是跨帳號、且兩端都不是 S3（例如 EFS 到另一帳號的 FSx）時仍需要 agent。
- **Location**：來源或目的地的定義。支援 NFS、SMB、HDFS、自建的 S3 相容物件儲存、其他雲端的物件儲存，以及 AWS 端的 S3、EFS、FSx for Windows File Server、FSx for Lustre、FSx for OpenZFS、FSx for NetApp ONTAP。
- **Task**：一組「從哪個 location 到哪個 location、用什麼選項」的設定，可以重複執行。
- **Task execution**：task 的一次執行。每次執行都有完整的統計與日誌。

### 讓搬遷可控的選項

- **增量傳輸**：預設只傳輸有變更的檔案（`TransferMode=CHANGED`）。第一次執行是全量，之後每次只傳差異，這正是「初次全量 + 多輪增量 + 最後切換」的基礎。
- **篩選（filters）**：用 include／exclude 規則排除暫存目錄、鎖定檔等不需要的資料。
- **頻寬限制**：設定每秒最多使用多少頻寬，避免搬遷佔滿辦公室網路；也可以在 task 執行中調整。
- **排程**：依 cron 運算式定期執行，例如每晚 10 點跑一次增量。
- **Metadata 保留**：NFS 的 POSIX 權限、擁有者與時間戳；SMB 與 FSx for Windows 之間的 NTFS ACL（擁有者、DACL、SACL）。這是把 Windows 檔案伺服器搬到 FSx 時保留權限的關鍵。
- **資料驗證**：傳輸過程本身就有完整性檢查；另外可以選擇傳輸後再驗證「只驗證這次傳輸的檔案」或「驗證整個目的地與來源一致」。後者花時間較多，適合最後切換前的那一輪。
- **Task report 與日誌**：把每個檔案的傳輸、略過、驗證結果輸出到 S3，並把日誌送到 CloudWatch Logs，作為稽核證據。
- **Task mode**：DataSync 有 Basic 與 Enhanced 兩種 task mode。Enhanced mode 為大規模傳輸設計，可處理的檔案數量更多、效能更高，但支援的 location 組合有限制（例如以 S3、EFS、FSx for Lustre 為一端），而且要搭配對應模式的 agent；建立 task 時依來源與目的地選擇。
- **單一 task 的效能**：一個 DataSync task 可以吃滿約 10 Gbps 的線路；資料集有數千萬個小檔案時，可以把資料依目錄拆成多個 task 平行執行（每個 task 一個 agent）。

小林為 NAS 建立的 task：

```bash
aws datasync create-location-nfs \
  --server-hostname nas01.office.wanderly.internal \
  --subdirectory /export/photos \
  --on-prem-config AgentArns=arn:aws:datasync:ap-northeast-1:111122223333:agent/agent-0b1c2d3e4f5a6b7c8

aws datasync create-location-s3 \
  --s3-bucket-arn arn:aws:s3:::wanderly-photo-archive \
  --subdirectory /legacy-nas \
  --s3-storage-class INTELLIGENT_TIERING \
  --s3-config BucketAccessRoleArn=arn:aws:iam::111122223333:role/DataSyncS3Access

aws datasync create-task \
  --name nas-photos-to-s3 \
  --source-location-arn arn:aws:datasync:ap-northeast-1:111122223333:location/loc-0a1b2c3d4e5f60001 \
  --destination-location-arn arn:aws:datasync:ap-northeast-1:111122223333:location/loc-0a1b2c3d4e5f60002 \
  --options TransferMode=CHANGED,VerifyMode=ONLY_FILES_TRANSFERRED,BytesPerSecond=62500000 \
  --excludes FilterType=SIMPLE_PATTERN,Value="*/.snapshot|*.tmp" \
  --schedule ScheduleExpression="cron(0 14 * * ? *)"
```

三個指令分別定義 NFS 來源（透過已啟用的 agent 存取）、S3 目的地（DataSync 用一個 IAM role 寫入 bucket），以及 task 本身。`BytesPerSecond=62500000` 就是 500 Mbps（62.5 MB/s）的頻寬上限；排程的 cron 以 UTC 計算，`14:00 UTC` 是台北時間晚上 10 點。

### 網路路徑：public endpoint 還是 VPC endpoint？

Agent 啟用時要選擇它連到 DataSync 的方式，選了之後不能更改：

- **Public service endpoint**：經 Internet（或 Direct Connect 的 public VIF）連到 DataSync 的公開端點，資料以 TLS 加密。
- **VPC service endpoint**：在你的 VPC 建立 DataSync 的 interface VPC endpoint，agent 經 Direct Connect private VIF 或 Site-to-Site VPN 連到這個 endpoint，**流量完全不經過 Internet**。安全規範要求私有路徑時選這個。
- **FIPS endpoint**：需要符合 FIPS 140 規範時使用。

### 跨 Region 與跨帳號

在 AWS 儲存之間（例如東京的 S3 搬到新加坡的 S3，或搬到 EFS）建立 task 時不需要 agent。跨帳號的 S3 搬遷要注意權限是雙邊的：DataSync 在來源帳號執行，使用來源帳號的一個 IAM role；**目的地 bucket 的 bucket policy 必須授權這個 role 寫入**，並建議目的地 bucket 使用 Object Ownership 的 bucket owner enforced（ACL disabled，第 22 章），讓搬過去的物件歸目的地帳號所有。若物件使用 SSE-KMS，role 還需要對應 KMS key 的權限。

> [!warning] 常見誤解
> 「DataSync 可以搬資料庫。」DataSync 搬的是檔案與物件。正在運行的資料庫要用 **AWS DMS**（Database Migration Service）做全量載入加上持續的變更複寫（CDC）；伺服器整機搬遷用 **AWS Application Migration Service（MGN）**。兩者都在第 45 章介紹。

DataSync 解決了 NAS。下一個問題是 SFTP 伺服器：它不是要搬的資料，而是四百家合作旅館每天都在使用的「入口」。

## 25.8 Transfer Family：受管的 SFTP、FTPS、FTP 與 AS2

**AWS Transfer Family** 提供全受管的檔案傳輸協定端點，背後直接把檔案存到 **S3** 或 **EFS**。合作旅館繼續用他們的 SFTP 用戶端連線、上傳，不需要知道後端已經換成 AWS；Wanderly 則不再需要維護伺服器、修補 OpenSSH 或擔心磁碟爆滿。

### 支援的協定

| 協定 | 說明 | 端點限制 |
|---|---|---|
| **SFTP** | 透過 SSH 的檔案傳輸，最常見 | 可用 public 或 VPC endpoint |
| **FTPS** | 透過 TLS 的 FTP，需要 ACM 憑證 | VPC endpoint |
| **FTP** | 未加密的傳統 FTP | 只能是 VPC 內部（internal）endpoint |
| **AS2** | B2B 電子資料交換（EDI）用的協定，支援簽章、加密與 MDN 回執 | VPC endpoint；後端只支援 S3 |

**AS2（Applicability Statement 2）** 常見於零售、物流、醫療與供應鏈：雙方用憑證互相簽章與加密訊息，接收方回傳 **MDN（Message Disposition Notification）** 作為「已收到」的證明。合作夥伴明確要求 AS2 時，用 SFTP 替代是不行的。

### Endpoint 類型與固定 IP

- **Public endpoint**：AWS 提供的公開端點，只支援 SFTP，IP 位址由 AWS 管理、可能變動，也無法套用 security group。
- **VPC endpoint（internal）**：只在 VPC 內與透過 VPN／Direct Connect 連進來的網路可存取。
- **VPC endpoint（internet-facing）**：在 VPC 內建立，並綁定你的 **Elastic IP**，所以對外 IP 固定；可以用 security group 限制來源 IP。合作夥伴的防火牆需要把 Wanderly 的 IP 加入允許清單，或 Wanderly 只想讓特定夥伴 IP 連線時，選這種。

### 身份與授權：誰能登入、能看到什麼

**Identity provider（身份提供者）** 決定使用者怎麼驗證：

- **Service managed**：在 Transfer Family 內建立使用者並綁定 SSH public key，只適用 SFTP。
- **AWS Directory Service for Microsoft Active Directory**：讓 AD 帳號用密碼登入。
- **Custom identity provider**：透過 Lambda 函數（或 API Gateway）串接你既有的身份系統，例如 LDAP、Okta 或資料庫裡的帳號，可支援密碼、金鑰或兩者並用。

驗證成功只代表「你是誰」，**能讀寫哪裡由 IAM 決定**：每個使用者對應一個 IAM role（可再加 session policy 縮小範圍），role 必須有對應 S3 prefix（與 KMS key）的權限。再搭配 **logical directory（邏輯目錄）**，把使用者看到的 `/` 對應到 bucket 裡的專屬路徑，使用者看不到也無法切換到其他夥伴的目錄（類似 chroot）。

```bash
aws transfer create-user \
  --server-id s-0123456789abcdef0 \
  --user-name hotel-0042 \
  --role arn:aws:iam::111122223333:role/TransferPartnerUpload \
  --home-directory-type LOGICAL \
  --home-directory-mappings '[{"Entry":"/","Target":"/wanderly-partner-inbox/hotel-0042"}]' \
  --ssh-public-key-body "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExampleKeyOnly hotel-0042"
```

這位使用者登入後看到的根目錄，實際上是 `wanderly-partner-inbox` bucket 裡的 `hotel-0042/` prefix。

### 上傳之後：managed workflows 與其他功能

- **Managed workflows**：檔案上傳完成後自動執行一連串步驟，例如複製到另一個位置、加上 tag、PGP 解密、呼叫 Lambda 做格式檢查，最後刪除原檔。
- **SFTP connectors**：反方向，由 Wanderly 主動把檔案推到合作夥伴的 SFTP 伺服器。
- **Web apps**：給不熟悉 SFTP 工具的使用者一個瀏覽器介面上傳下載 S3 檔案。
- 計費包含「每個啟用協定的端點每小時」與傳輸量，即使沒人連線也會按小時收費。

小林把舊 SFTP 伺服器的 DNS 名稱改指向 Transfer Family 的 endpoint，並匯入每家旅館的 SSH key。合作旅館那邊什麼都沒改，上傳的房價檔直接進 S3，觸發 Lambda 解析後寫入資料庫。

## 25.9 Snow Family 與離線傳輸：現況與替代方案

當資料量大到網路要傳好幾個月，「把硬碟寄過去」反而比較快。這就是 **AWS Snow Family** 的概念：AWS 寄一台堅固、加密、防竄改的裝置給你，你在機房把資料複製進去，再寄回 AWS，由 AWS 匯入 S3。

### 現況：考試與現實的落差

這個家族近年變化很大，寫架構建議時必須留意：

- **AWS Snowball Edge**：Snow 家族的主力裝置，有儲存最佳化（Storage Optimized）與運算最佳化（Compute Optimized）兩種，單台可用容量在數十 TB 到約兩百 TB 的等級（依型號）。AWS 已公告 **Snowball Edge 不再提供給新客戶**；既有客戶可以繼續使用。
- **AWS Snowcone**：小型、可攜的邊緣裝置，已停止提供。
- **AWS Snowmobile**：用貨櫃車搬運 EB 等級資料的服務，已退役。

換句話說，AWS 已不再對新客戶提供任何 Snow 系列裝置。AWS 官方建議的替代方案是：線上傳輸用 DataSync（頻寬不足時搭配 Direct Connect hosted connection）、離線傳輸用 AWS Data Transfer Terminal 或 AWS Marketplace 上的合作夥伴離線傳輸服務、邊緣運算改用 AWS Outposts。

但 SAA-C03 與 SAP-C02 的許多題目是在這些變化前設計的，「資料量數十 TB 到 PB、網路要好幾週以上、要盡快完成」的標準答案仍可能是 Snowball Edge。解題時照題目的條件選；在實務上，則先確認你的帳號能否訂購，否則改用下面的替代方案。

### Snowball Edge 的運作流程（考試仍會考）

1. 在主控台建立 **job**，類型為匯入 S3（import）、從 S3 匯出（export）或本地運算與儲存。指定目的地 bucket 與 KMS key。
2. AWS 寄出裝置。裝置上的電子墨水標籤自動顯示寄送地址，裝置有防竄改設計與 TPM 晶片。
3. 裝置接上地端網路後，用 job 的 **manifest 檔與 unlock code** 解鎖（兩者要分開保管），再透過裝置提供的 S3 相容介面或 NFS 介面複製資料。資料在寫入裝置時就以 KMS 管理的金鑰加密，金鑰不存在裝置上。
4. 寄回 AWS，AWS 把資料匯入 S3，完成後依 NIST 標準抹除裝置。
5. 驗證匯入結果（job 報告與物件清單比對）之後，才刪除來源資料。

兩個常考細節：

- **不能直接匯入 Glacier**。Snowball 匯入的目的地是 S3 bucket；要長期封存，就在 bucket 設定 lifecycle rule，把物件轉到 Glacier Deep Archive（可設定 0 天後轉換）。
- **裝置只帶走某個時間點的資料**。寄出後來源新增或修改的檔案不會跟著過去，需要再用 DataSync 等線上方式補上增量。

Snowball Edge 還能在沒有網路或網路很差的地點執行 EC2 相容的 instance 與 Lambda，做邊緣運算（例如船上、礦場、災區的資料預處理）。

### 沒有 Snow 時的選擇

- **提高網路頻寬**：申請 Direct Connect（第 8 章），1／10／100 Gbps 的專用連線，再用 DataSync 傳輸。注意專線建置通常需要數週以上的前置時間，時程很趕時要提早申請，或透過合作夥伴的 hosted connection。
- **AWS Data Transfer Terminal**：AWS 在少數城市設置的實體據點，你把自己的儲存裝置帶過去，透過高速網路直接上傳到 AWS。適合手上已有大量硬碟資料、可以安排人員前往的情境。
- **合作夥伴的離線傳輸服務**：AWS Marketplace 上有儲存廠商提供寄送裝置、代為上傳的服務，概念和過去的 Snowball 類似。
- **邊緣運算需求**：過去用 Snowball Edge Compute Optimized 在現場跑運算的情境，AWS 建議改用 **AWS Outposts**（2U 的 Outposts server 或 42U 的 Outposts rack）。
- **重新計算**：很多時候算過之後會發現，用現有線路搭配 DataSync 的頻寬排程、加上足夠的時程，其實就能完成。不要預設「大資料就要寄裝置」。

> [!warning] 常見誤解
> 「Snowball 可以持續同步變更。」不行。Snow 裝置是一次性的離線搬運，寄出後的新資料必須用線上傳輸補齊。大型搬遷的標準做法是「離線（或專線）完成初次全量，線上傳輸多輪增量，最後凍結寫入做最終同步」。

## 25.10 網路路徑的加速：Direct Connect、VPN 與 S3 Transfer Acceleration

資料移轉工具決定「怎麼搬」，網路路徑決定「搬得多快、多穩、走不走 Internet」。

- **Site-to-Site VPN**：在 Internet 上建立加密 tunnel，幾分鐘就能建好，但頻寬與延遲受 Internet 影響，每條 tunnel 的頻寬有上限（第 8 章）。適合中小量、需要快速開始的搬遷，或作為 Direct Connect 的備援。
- **Direct Connect**：專用實體線路，頻寬穩定、延遲可預期，資料傳輸費率也比 Internet 出站便宜。DX 本身不加密，但 DataSync、Storage Gateway 的流量本來就以 TLS 加密；需要網路層加密時可在 DX 上跑 VPN 或使用支援的 MACsec。搭配 private VIF 與 interface VPC endpoint，可以讓 DataSync 與 Storage Gateway 的流量完全不經過 Internet。
- **S3 Transfer Acceleration**：讓使用者把檔案上傳到離他最近的 CloudFront edge location，再經 AWS 骨幹網路送到遙遠的 S3 bucket。啟用後使用專屬端點（`bucket-name.s3-accelerate.amazonaws.com`），按加速的傳輸量額外收費，而且 AWS 只在判斷有加速效果時才收這筆費用。它適合**全球分散的使用者上傳到單一 bucket**、距離越遠效果越明顯；對同 Region 內的傳輸沒有幫助。

上傳大檔案時，不論是否加速，都應該使用 **multipart upload**（第 22 章）：把檔案切成多段平行上傳，失敗只重傳那一段。超過 5 GB 的物件必須使用 multipart upload，100 MB 以上就建議使用。

## 25.12 比較與選型

### 服務對照

| 服務 | 解決什麼問題 | 地端介面 | AWS 端儲存 | 一次性或長期 |
|---|---|---|---|---|
| S3 File Gateway | 地端應用程式用檔案、資料存 S3 | NFS、SMB | S3（一檔案一物件） | 長期混合 |
| Volume Gateway（cached） | 地端空間不足，iSCSI 磁碟以雲端為本體 | iSCSI | AWS 儲存 + EBS snapshot | 長期混合 |
| Volume Gateway（stored） | 地端保留完整資料，雲端做備份 | iSCSI | EBS snapshot | 長期混合／DR |
| Tape Gateway | 取代實體磁帶、不改備份軟體 | iSCSI VTL | S3 → Glacier／Deep Archive | 長期備份 |
| DataSync | 大量檔案／物件的線上搬遷與定期同步 | Agent 讀 NFS／SMB／HDFS／物件儲存 | S3、EFS、FSx 全系列 | 一次性搬遷或排程同步 |
| Transfer Family | 外部夥伴用 SFTP／FTPS／FTP／AS2 交換檔案 | 夥伴的檔案傳輸用戶端 | S3、EFS | 長期服務 |
| Snowball Edge | 網路太慢的大量資料離線搬運、邊緣運算 | 裝置的 S3 介面／NFS | S3 | 一次性（不開放新客戶） |
| S3 Transfer Acceleration | 遠距離使用者上傳到單一 bucket | S3 API | S3 | 長期 |
| Direct Connect | 穩定、高頻寬、私有的網路路徑 | 網路 | — | 長期基礎設施 |
| DMS／MGN | 資料庫／整台伺服器的搬遷 | 資料庫連線／replication agent | RDS、EC2 等 | 一次性（第 45 章） |

### 選型決策流程

```text
外部夥伴要用 SFTP／FTPS／FTP／AS2 上傳或下載？
├─ 是 → Transfer Family
└─ 否 → 搬完就要關掉地端儲存（一次性）？
         ├─ 是 → 資料是資料庫或整台伺服器？
         │        ├─ 是 → DMS／MGN（第 45 章）
         │        └─ 否 → 算天數：線上能在期限內完成？
         │                 ├─ 能 → DataSync（必要時 DX、VPC endpoint）
         │                 └─ 不能 → 加大頻寬（DX）、Data Transfer Terminal，
         │                          或 Snowball Edge（僅限仍可訂購的既有客戶）
         │                          ＋ DataSync 補增量
         └─ 否，地端要長期繼續使用 → 應用程式用什麼介面？
                  ├─ NFS／SMB 檔案，資料想變成 S3 物件 → S3 File Gateway
                  ├─ iSCSI 磁碟 → Volume Gateway
                  │     ├─ 地端要有完整資料、低延遲 → stored
                  │     └─ 地端空間不足、雲端為本體 → cached
                  └─ 備份軟體寫磁帶 → Tape Gateway
全球使用者上傳到單一 bucket 太慢 → S3 Transfer Acceleration + multipart upload
```

## 25.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 地端應用程式用 NFS／SMB，資料要存成 S3 物件、本機低延遲快取 | S3 File Gateway |
| 直接寫進 bucket 的新物件在 file share 上看不到 | RefreshCache／自動 cache refresh |
| iSCSI、地端空間不足、常用資料留在本機 | Volume Gateway cached volumes |
| iSCSI、地端要低延遲存取整份資料、AWS 做非同步備份 | Volume Gateway stored volumes |
| 既有備份軟體、實體磁帶、長期封存最低成本 | Tape Gateway + Glacier Deep Archive |
| NFS／SMB／HDFS 大量檔案搬到 S3／EFS／FSx，要排程、增量、驗證 | DataSync |
| 搬遷流量不能走 Internet | DataSync／Storage Gateway 使用 VPC endpoint + DX private VIF 或 VPN |
| Windows 檔案伺服器搬到 FSx，要保留 NTFS 權限 | DataSync（SMB → FSx for Windows） |
| 夥伴用 SFTP 上傳到 S3、不想管伺服器 | Transfer Family（logical directory + IAM role） |
| 夥伴防火牆要固定 IP | Transfer Family VPC internet-facing endpoint + Elastic IP |
| 夥伴要求 AS2、MDN 回執、EDI | Transfer Family AS2 |
| 數十 TB 到 PB、網路要好幾週、要盡快 | 先算天數；考題常見答案為 Snowball Edge（現況不開放新客戶） |
| 離線匯入後要放 Glacier | 先匯入 S3，再用 lifecycle 轉換 |
| 全球使用者上傳大檔到遠端 bucket 很慢 | S3 Transfer Acceleration + multipart upload |
| 資料庫線上搬遷、持續同步變更 | DMS（不是 DataSync，第 45 章） |

**常見陷阱**：

1. 算傳輸時間時把 bits 當 bytes，或忽略頻寬只能部分使用。
2. 把 Volume Gateway 的 cached 和 stored 弄反：cached 的本體在雲端，stored 的本體在地端。
3. 以為 Volume Gateway 的資料可以用 S3 API 讀取：它以 EBS snapshot 形式提供，不是 bucket 裡的物件。
4. 用 DataSync 取代長期的混合存取：DataSync 是搬遷與同步工具，不提供給應用程式掛載的檔案共享。
5. 以為 Snowball 可以直接匯入 Glacier，或寄出後會自動同步新資料。
6. 以為 Transfer Acceleration 能加速 Region 內或從 EC2 的傳輸：它只對遠距離的 Internet 用戶端有效。
7. 用 DataSync 搬正在運行的資料庫：要用 DMS。

## 25.14 SAP 加深：大規模搬遷的時程、切換與治理

### 用增量把停機窗口縮到最小

SAP 題目常給這樣的組合：500 TB 的 NAS、每天變動 5 TB、週末只有 4 小時停機窗口。標準解法有四個階段：

1. **試跑（pilot）**：用一個具代表性的目錄（包含大量小檔案的部分）實際測量有效 throughput。小檔案多時，每個檔案的 metadata 操作會讓速度遠低於線路頻寬。
2. **初次全量**：用 DataSync（或專線、離線裝置）把大部分資料搬過去，這段期間來源照常營運。
3. **多輪增量**：排程每天執行增量 task，讓兩邊的差距保持在一天的變動量以內。用最近幾輪增量的實際耗時，估算最後一輪需要多久。
4. **切換**：凍結來源寫入（設為唯讀），跑最後一輪增量並驗證整個目的地，然後把 DNS 或 DFS namespace 指到新位置。保留來源在唯讀狀態一段時間作為 rollback 依據。

如果最後一輪的預估時間超過停機窗口，就要增加增量的頻率（例如每小時一次）、提高頻寬，或把資料依目錄分批切換。

### 多帳號與安全治理

- **私有路徑**：DataSync、Storage Gateway、Transfer Family（VPC endpoint）都能完全在私有網路中運作。企業常規定搬遷流量走 Direct Connect 加 interface VPC endpoint，並用 VPC endpoint policy 限制只能存取指定的 bucket。
- **最小權限**：DataSync 對 S3 使用的 IAM role、Transfer Family 每個使用者的 role 與 session policy，都應該只開放到特定 bucket 與 prefix；使用 SSE-KMS 時，KMS key policy 也要授權。
- **跨帳號落地**：搬遷的目的地常是 landing zone 中的專用帳號（第 40 章）。跨帳號寫入 S3 時，目的地 bucket policy 授權來源帳號的 role，並以 bucket owner enforced 確保物件所有權。
- **稽核證據**：DataSync 的 task report 與 CloudWatch 日誌、Transfer Family 的使用者活動日誌、CloudTrail 的 API 紀錄，共同構成「資料完整搬遷且只有授權者存取」的證明。

### 長期混合的取捨

並不是所有資料都要搬完。有些工廠、門市或醫院因為延遲或法規必須在地端保留處理能力，這時的選擇是：

- 地端應用程式只需要把資料「落到」雲端：S3 File Gateway。
- 多個據點要協同使用同一份檔案、需要 NetApp 等級的資料管理：FSx for NetApp ONTAP，搭配 SnapMirror 或其快取功能（第 24 章）。
- 需要在地端執行 AWS 服務本身（低延遲運算、資料不能離開機房）：AWS Outposts（第 2 章）。

Wanderly 在 Part 8 併購旅行社時，會再遇到這些問題的放大版：300 台 VM、Oracle 資料庫與 6 台共約 38 TB 的 Windows 檔案伺服器，並且需要完整的遷移計畫（第 44、45、51 章）。

> [!sap] SAP 加深
> SAP 的資料移轉題目很少只問「用哪個服務」，而是問「哪個組合能在期限內完成且停機最短」。答題順序是：先算線上傳輸天數，再決定全量用什麼方式（線上、專線、離線），最後一定要有增量同步與驗證的步驟。缺少增量計畫的選項，幾乎都是錯的。

## 本章重點整理

- 資料移轉決策從計算開始：傳輸秒數 = 資料量（bytes）× 8 ÷（頻寬 × 可用比例 × 效率）；1 Gbps 的理論上限約每天 10.8 TB。
- 先分清楚需求是「一次性搬遷」還是「地端長期混合使用」：前者用 DataSync（或離線、專線），後者用 Storage Gateway。
- Storage Gateway 部署在地端（VM）或 EC2，以本機 cache 提供低延遲，資料以 TLS 加密非同步上傳，可經 Internet、Direct Connect 或 VPC endpoint。
- S3 File Gateway 透過 NFS／SMB 把每個檔案存成一個 S3 物件；直接寫入 bucket 的變更需要 RefreshCache 才會出現在共享上，且沒有跨 gateway 的檔案鎖定。
- FSx File Gateway 已不再提供給新客戶，新設計直接存取 FSx for Windows File Server 或評估 FSx for ONTAP。
- Volume Gateway 提供 iSCSI 磁碟：cached volumes 以雲端為本體、地端快取常用資料；stored volumes 以地端為本體、非同步備份為 EBS snapshot，可在 AWS 還原成 EBS volume。
- Tape Gateway 提供虛擬磁帶庫，既有備份軟體不必修改，eject 後的磁帶封存到 Glacier Flexible Retrieval 或 Deep Archive。
- DataSync 用 agent 讀取地端 NFS、SMB、HDFS 或物件儲存（AWS 儲存之間不需要 agent），支援增量、篩選、頻寬限制、排程、metadata 保留、驗證與 task report。
- DataSync agent 啟用時選擇 public、VPC 或 FIPS endpoint；要求不經 Internet 時使用 VPC endpoint 搭配 DX private VIF 或 VPN。
- 跨帳號的 DataSync S3 搬遷需要目的地 bucket policy 授權來源帳號的 role，並建議以 bucket owner enforced 確保物件歸目的地帳號。
- Transfer Family 提供受管的 SFTP、FTPS、FTP、AS2 端點，後端為 S3 或 EFS；用 identity provider 驗證、IAM role 授權、logical directory 限制可見目錄。
- 夥伴需要固定 IP 時，使用 Transfer Family 的 internet-facing VPC endpoint 綁定 Elastic IP。
- Snowball Edge 已不再提供給新客戶，Snowcone 與 Snowmobile 已停止；考題中它仍是「網路太慢的大量資料」的常見答案，匯入目的地是 S3（要封存再用 lifecycle），寄出後的增量要用線上方式補上。
- S3 Transfer Acceleration 透過 edge location 加速遠距離用戶端上傳到單一 bucket，大檔案搭配 multipart upload。
- 大型搬遷的標準流程是試跑測速、初次全量、多輪增量、凍結寫入後最終同步與驗證，再切換並保留 rollback 能力。

### 練習 25-1｜SAA｜單選｜線上傳輸時間估算

Wanderly 要把辦公室 NAS 上的 150 TB 影片素材搬到 S3。辦公室有一條 1 Gbps 的 Internet 線路，但白天與晚上都有員工使用，主管只同意撥出 50% 的頻寬給搬遷。為了快速估算，先假設這 50% 的頻寬可以完全用滿、不考慮協定開銷。專案期限是兩週內完成。

下列哪個估算與結論正確？

- A. 約 3.5 天，可以在期限內用網路完成
- B. 約 14 天，剛好可以在期限內完成
- C. 約 28 天，超過兩週期限，需要增加頻寬、延長時程或改用其他傳輸方式
- D. 約 56 天，因為 TCP 協定會讓可用頻寬再減半

> [!answer]- 答案：C
> **A ✗** 這是把 500 Mbps 誤當成 500 MB/s 的結果，差了 8 倍。頻寬以 bit 計，資料量以 byte 計，必須先除以 8。
>
> **B ✗** 約 14 天是用完整 1 Gbps（每天約 10.8 TB）計算的結果，忽略了只能使用 50% 頻寬的限制。
>
> **C ✓** 500 Mbps ÷ 8 = 62.5 MB/s，每天約 62.5 MB × 86,400 ≈ 5.4 TB，150 TB ÷ 5.4 TB ≈ 28 天，超過兩週期限。實務上還有協定開銷，實際時間會更長。
>
> **D ✗** 題目已明確假設不考慮協定開銷；而且 TCP 開銷通常是一、二成，不是固定再減半。
>
> **考點**：SAA-3.5｜頻寬與傳輸時間計算

### 練習 25-2｜SAA｜單選｜地端 NFS 應用程式把資料寫進 S3

Wanderly 的會計系統只能把報表輸出到一個 NFS 路徑，供應商無法修改程式。公司希望這些報表能以 S3 物件的形式供 AWS 上的 Athena 查詢與 Lambda 處理，同時讓辦公室的使用者快速開啟最近幾天的報表。

最合適的方案是什麼？

- A. 在辦公室部署 S3 File Gateway，提供 NFS 共享給會計系統，並以本機 cache 加速最近的檔案
- B. 部署 Volume Gateway cached volumes，把 iSCSI 磁碟格式化後掛給會計系統
- C. 用 DataSync 每小時把 NAS 上的報表資料夾同步到 S3
- D. 建立 Transfer Family SFTP 端點，讓會計系統改用 SFTP 上傳

> [!answer]- 答案：A
> **A ✓** S3 File Gateway 對會計系統提供 NFS，程式不必修改；每個檔案都成為同名的 S3 物件，可以直接給 Athena 與 Lambda 使用；本機 cache 讓最近的檔案以區網速度開啟。
>
> **B ✗** Volume Gateway 提供的是 block 磁碟，資料以 volume 形式存放、以 EBS snapshot 提供，不會變成可直接查詢的 S3 物件。
>
> **C ✗** DataSync 能把檔案同步到 S3，但仍需要一台地端 NAS 提供 NFS，且每小時同步會造成延遲；它是搬遷與同步工具，不是給應用程式長期使用的檔案共享。
>
> **D ✗** 改用 SFTP 需要修改會計系統的輸出方式，違反「供應商無法修改程式」的限制。
>
> **考點**：SAA-3.1、SAA-3.5｜S3 File Gateway 的混合存取

### 練習 25-3｜SAA｜單選｜Volume Gateway 模式選擇

辦公室有一套使用 iSCSI 磁碟的影像索引系統，資料約 20 TB，系統需要以低延遲隨機存取整份資料，而且在辦公室網路斷線時仍要正常運作。辦公室有足夠的本機儲存空間。公司希望在 AWS 保留這份資料的定期 point-in-time 備份，並在必要時於 AWS 上還原。

應選擇哪種方案？

- A. Volume Gateway cached volumes，讓完整資料存放在 AWS，本機只保留常用部分
- B. S3 File Gateway，把 iSCSI 磁碟改成 NFS 共享
- C. Tape Gateway，每天把整份資料寫到虛擬磁帶
- D. Volume Gateway stored volumes，讓完整資料留在本機並非同步備份成 EBS snapshot

> [!answer]- 答案：D
> **A ✗** Cached volumes 的本體在 AWS，本機只有 cache；不在 cache 的資料要跨網路讀取，斷線時也無法存取，不符合「低延遲存取整份資料、斷線仍運作」。
>
> **B ✗** S3 File Gateway 提供檔案共享，不是 iSCSI block 磁碟，系統需要修改才能使用。
>
> **C ✗** Tape Gateway 是給備份軟體使用的虛擬磁帶庫，不是應用程式日常存取的線上磁碟。
>
> **D ✓** Stored volumes 把完整資料保存在地端，存取延遲低且不依賴網路；同時以非同步方式把 point-in-time snapshot 存成 EBS snapshot，必要時可以在 AWS 建立 EBS volume 還原。
>
> **考點**：SAA-2.2、SAA-3.1｜Volume Gateway cached vs stored

### 練習 25-4｜SAA｜單選｜取代實體磁帶備份

Wanderly 的辦公室用 Veeam 備份軟體每週把資料寫入 LTO 實體磁帶，再送到外部保管。法規要求備份保存 10 年，但幾乎不會還原；若需要還原，可以接受等待 12 小時。備份管理員不希望改變現有的備份工作與磁帶管理方式。

哪個方案能以最低成本滿足需求？

- A. 部署 S3 File Gateway，把備份改寫到 SMB 共享，再設定 lifecycle 轉到 Glacier Deep Archive
- B. 部署 Tape Gateway 作為虛擬磁帶庫，讓 Veeam 照常寫入並在 eject 後把虛擬磁帶封存到 S3 Glacier Deep Archive
- C. 部署 Volume Gateway stored volumes，讓 Veeam 備份到 iSCSI 磁碟並保留 EBS snapshot 10 年
- D. 每月訂購 Snowball Edge，把當月的磁帶內容複製後寄到 AWS

> [!answer]- 答案：B
> **A ✗** 備份到 SMB 共享再轉 Deep Archive 在成本上可行，但需要把備份工作從磁帶目標改成磁碟目標，違反「不改變現有備份工作與磁帶管理方式」。
>
> **B ✓** Tape Gateway 對 Veeam 呈現 iSCSI 虛擬磁帶庫，既有工作與磁帶操作不變；eject 後的虛擬磁帶封存到 Deep Archive，是長期保存成本最低的選擇，取回時間在 12 小時內，符合可接受的等待時間。
>
> **C ✗** 長期保留大量 EBS snapshot 的成本遠高於 Deep Archive，也改變了備份方式。
>
> **D ✗** Snowball Edge 是一次性的大量資料搬運，不適合每月例行備份，物流與營運負擔高；而且它已不再提供給新客戶。
>
> **考點**：SAA-4.1｜Tape Gateway 與 Glacier Deep Archive

### 練習 25-5｜SAA｜單選｜NFS 搬到 EFS 的增量遷移

Wanderly 要把辦公室一台 Linux NFS 伺服器上的 30 TB 共享資料搬到 Amazon EFS。搬遷期間使用者仍會持續修改檔案，團隊希望每晚自動同步變更、保留檔案的擁有者與權限、排除暫存目錄，並在每次同步後取得哪些檔案成功或失敗的報告。

哪個方案最合適？

- A. 在辦公室部署 S3 File Gateway，再設定 S3 到 EFS 的 replication
- B. 在一台 EC2 上掛載 EFS，用 cron 每晚執行 `rsync` 從辦公室拉資料
- C. 在辦公室部署 DataSync agent，建立 NFS 與 EFS 的 location 與排程 task，設定 exclude 篩選、metadata 保留、驗證與 task report
- D. 使用 S3 Transfer Acceleration 把 NFS 資料上傳到 S3，再由 EFS 自動匯入

> [!answer]- 答案：C
> **A ✗** S3 File Gateway 把檔案存到 S3，S3 與 EFS 之間也沒有「replication」功能；這條路多繞一層，且無法直接保留 NFS 權限到 EFS。
>
> **B ✗** 自己寫 rsync 腳本可以運作，但要自己處理平行化、重試、驗證與報告，30 TB 規模下的速度與可靠度都不如受管服務，營運負擔高。
>
> **C ✓** DataSync 正是為此設計：agent 讀取地端 NFS，task 可排程每晚只傳變更，支援 include／exclude 篩選、POSIX metadata 保留、傳輸後驗證，並輸出每個檔案的 task report。
>
> **D ✗** Transfer Acceleration 只加速 S3 上傳，EFS 也不會自動從 S3 匯入資料。
>
> **考點**：SAA-3.5、SAA-3.1｜DataSync 的增量同步與控制選項

### 練習 25-7｜SAA｜選兩項｜全球大檔案上傳加速

Wanderly 的簽約攝影師分布在歐洲、美洲與東南亞，每天要把 2–10 GB 的影片檔上傳到東京的一個 S3 bucket。歐美的攝影師回報上傳很慢，而且網路一斷就要整個檔案重傳。團隊希望以最少的營運負擔改善上傳速度與可靠度。

- B. 對東京的 bucket 啟用 S3 Transfer Acceleration，讓上傳程式改用 accelerate 端點

>
> **E ✗** 關閉驗證可以省一點時間，但失去「資料完整」的證據，錯誤要到使用者發現時才會暴露，增加 rollback 風險。

### 練習 25-16｜SAP｜選兩項｜以 Volume Gateway 建立 DR 能力

- A. 把 stored volumes 改成 cached volumes，讓 AWS 端自動提供一台可用的伺服器
- B. 用 S3 API 從 bucket 中直接讀取 volume 內的檔案，在 AWS 上重建資料

>

>
> **考點**：SAP-2.2、SAP-4.3｜Volume Gateway snapshot 作為 DR 來源
