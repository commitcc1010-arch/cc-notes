# 第 23 章　S3 儲存類別、生命週期、複寫與資料保護

## 23.1 故事：S3 帳單每個月都在長

第 22 章結束時，Wanderly 已經把照片、影片與訂單文件都放進 S3。一年後，財務長在月會上指著一張圖：S3 的費用每個月成長 8%，而且看不到停下來的跡象。存放量已經超過 900 TB，其中包括：

- 旅館照片：新照片頭兩週被大量瀏覽，三個月後幾乎沒人看，但不能刪。
- 訂單憑證與發票 PDF：依公司規範要保存 7 年，平常幾乎不讀，但稅務稽核時要在兩天內調出。
- 點擊流原始日誌：分析團隊只會查最近 90 天，之後只為了偶爾的重新計算保留一年。
- 縮圖：隨時可以從原始照片重新產生。

這些資料**全部都放在 S3 Standard**，價格最貴的那一種。同一場會議上，法務長又提出兩個要求：發票在保存期限內**任何人都不能刪除或修改**，包括系統管理員；而且東京 Region 發生災難時，要能在另一個 Region 拿到這些資料。

小周負責這個專案。他要回答三個問題：每種資料該放在哪個儲存類別、如何讓資料隨時間自動搬移與刪除、以及如何讓重要資料不被刪除且有異地副本。本章就依這個順序展開。

## 23.2 S3 的錢花在哪裡：先看懂帳單的組成

選儲存類別之前，要先知道 S3 收費的五個項目。只看「每 GB 每月多少錢」做決策，是最常見的錯誤。

1. **儲存費（storage）**：每 GB 每月的存放費用。越「冷」的類別越便宜。
2. **請求費（requests）**：每 1,000 個 PUT、COPY、LIST、GET 等請求的費用。越冷的類別，請求通常越貴。Lifecycle 把 object 轉到其他類別，也是一個要付費的請求。
3. **取回費（retrieval）**：從 IA 或 Glacier 類別讀取資料時，**每讀 1 GB 要另外付費**。Standard 沒有取回費。
4. **最短存放天數（minimum storage duration）**：某些類別規定 object 至少要算滿 N 天的儲存費。例如 Standard-IA 是 30 天：你存了 10 天就刪掉，仍要付 30 天的錢（剩下的 20 天以提前刪除費的形式收取）。
5. **最小計費大小（minimum billable object size）**：某些類別規定每個 object 至少以 128 KB 計費。一個 10 KB 的檔案放進 Standard-IA，會被當成 128 KB 收費。

另外還有**資料傳出費**（從 S3 傳到 Internet 或其他 Region），這和儲存類別無關，第 39 章再談。

這五個項目的意義是：**越冷的類別，存放越便宜，但「讀取」與「短期存放」越貴**。所以選類別的關鍵問題永遠是：

- 這份資料多久被讀一次？每次讀多少？
- 讀取時可以等多久（毫秒、分鐘、小時）？
- 它會存多久？
- 單一 object 多大？
- 資料可以重建嗎？能不能接受單一 AZ 損毀時遺失？

## 23.3 每種儲存類別在解決什麼問題

S3 所有儲存類別的**耐久度設計目標都是 11 個 9**。差別在於可用度、資料存放在幾個 AZ、讀取速度與費用結構。

### S3 Standard：預設、頻繁存取

**S3 Standard** 是預設類別，資料存在至少三個 AZ，毫秒讀取，沒有取回費、沒有最短存放天數、沒有最小計費大小。適合經常讀取或存放時間很短的資料：網站正在使用的照片、正在處理中的資料、剛上傳的檔案。

### S3 Standard-IA：不常讀，但讀的時候要快

**S3 Standard-IA（Infrequent Access，不常存取）** 的儲存費比 Standard 便宜，資料一樣存在至少三個 AZ、毫秒讀取，但有**取回費**、**30 天最短存放天數**與 **128 KB 最小計費大小**，設計可用度 99.9%。適合「大約每月讀一次以下，但需要時要立刻拿到」的資料，例如三個月前的旅館照片、每月才打開一次的報表、近期的備份。

### S3 One Zone-IA：可重建的不常存取資料

**S3 One Zone-IA** 和 Standard-IA 一樣有取回費、30 天、128 KB 的規則，但資料**只存在一個 AZ**，所以儲存費更便宜（約為 Standard-IA 的八成），設計可用度 99.5%。耐久度仍是 11 個 9，但這是**在那個 AZ 內**的耐久度：如果整個 AZ 因火災或水災損毀，資料就會遺失。

所以 One Zone-IA 只適合**可以重建**或**已有另一份副本**的資料：Wanderly 的縮圖（可從原始照片重新產生）、從其他 Region 複寫過來的次要備份。考試看到「資料可重新產生」「成本最低」「不常讀取但要毫秒存取」，就想到它；看到「唯一一份」「不可遺失」，它就是錯誤答案。

### S3 Intelligent-Tiering：不知道存取模式時

前面三種類別都要求你**事先知道**資料多常被讀。但很多資料無法預測：某家旅館突然上了電視，三年沒人看的照片一夜之間被點擊十萬次。如果它在 Standard-IA，每次讀取都要付取回費。

**S3 Intelligent-Tiering** 讓 S3 自動觀察每個 object 的存取情況並搬移：

- **Frequent Access tier**：新 object 先放這裡，價格與 Standard 相當。
- **Infrequent Access tier**：連續 30 天沒被存取，自動移到這裡，較便宜。
- **Archive Instant Access tier**：連續 90 天沒被存取，自動移到這裡，更便宜，仍是毫秒讀取。
- 被存取時，object 會自動回到 Frequent Access tier。
- **選用（opt-in）的 Archive Access tier 與 Deep Archive Access tier**：你可以設定連續 90 天以上（或 180 天以上）沒被存取的 object 進一步移入封存層，價格接近 Glacier Flexible Retrieval 與 Deep Archive。但進入這兩層的 object 要先**非同步 restore** 才能讀取，不再是毫秒存取，所以只有在應用程式能接受等待時才啟用。

它的費用特點是：**沒有取回費、沒有最短存放天數**，在各 tier 之間自動移動也不收轉換費；代價是每個 object 要付一筆小額的**監控與自動化費用**（按每 1,000 個 object 每月計）。**小於 128 KB 的 object 不會被監控、也不收監控費，永遠以 Frequent Access tier 計價**。

適合存取模式未知或會變化、object 不太小、存放超過一個月的資料，例如資料湖、使用者上傳內容。如果你很確定資料「90 天後就再也不會讀」，直接用 lifecycle 轉到 Glacier 類別通常更便宜，因為不必付監控費。

### 三種 Glacier：封存資料

**Glacier** 系列是給「長期保存、很少讀取」的封存資料，儲存費最低，但最短存放天數較長：

| 類別 | 讀取方式 | 最短存放 | 適合 |
|---|---|---|---|
| **S3 Glacier Instant Retrieval** | 毫秒，直接 GET | 90 天 | 每季讀一次以下、但讀的時候要立刻拿到（醫療影像、新聞圖庫、身份證件掃描檔） |
| **S3 Glacier Flexible Retrieval**（舊稱 S3 Glacier） | 要先 restore，分鐘到小時 | 90 天 | 每年讀一兩次、可以等幾分鐘到幾小時（備份、媒體封存） |
| **S3 Glacier Deep Archive** | 要先 restore，12 到 48 小時 | 180 天 | 保存多年、幾乎不讀、可以等一兩天（法規保存、磁帶取代） |

Glacier Instant Retrieval 和 Standard-IA 很像（毫秒讀取、128 KB 最小計費），差別在於它的儲存費更低、取回費更高、最短存放 90 天。粗略的判斷：**大約每月讀一次選 Standard-IA，每季或更少選 Glacier Instant Retrieval**。

Glacier Flexible Retrieval 與 Deep Archive 的 object 是「封存狀態」，不能直接 GET，必須先發出 restore 請求（23.5 節）。這兩個類別每個 object 還有約 **40 KB 的額外 metadata 計費**（其中 32 KB 以 Glacier 價格、8 KB 以 Standard 價格計），所以大量小檔案放進去可能反而不划算，常見做法是先打包成大檔（例如 tar）再封存。

> [!note] 名稱與舊服務
> 「S3 Glacier Flexible Retrieval」是 S3 的一個儲存類別，用一般的 S3 API 操作，lifecycle 中的代號是 `GLACIER`；Instant Retrieval 是 `GLACIER_IR`，Deep Archive 是 `DEEP_ARCHIVE`。另外有一個更早期、以 **vault（保管庫）** 為單位、有獨立 API 的獨立服務（現在官方稱為 **Amazon Glacier**，2012 年推出），以及它的 **Vault Lock** 功能。這個 vault 服務已不再接受新客戶，既有資料可以繼續保存與存取；新設計一律使用 S3 的 Glacier 儲存類別與 S3 Object Lock。考試若出現 Glacier Vault Lock，它代表的是「對 vault 套用不可變更的 WORM 政策」。

### S3 Express One Zone：極低延遲的單一 AZ 儲存

**S3 Express One Zone** 走另一個方向：它不是為了省儲存費，而是為了**速度**。它把資料存放在你指定的單一 AZ，使用專用的 **directory bucket**，提供穩定的個位數毫秒延遲與極高的每秒請求數，請求費比 Standard 低。適合把運算（例如 ML 訓練、互動式分析、高頻率讀寫的中間檔）放在同一個 AZ，反覆存取大量小檔案的情境。

需要注意的是：

- **單一 AZ** 的故障域：AZ 損毀時資料可能遺失，可用度設計為 99.95%。適合可重建的資料或工作資料，正式的原始資料仍放在一般用途 bucket。
- Directory bucket 和一般用途 bucket 的命名、endpoint、驗證方式（以 `CreateSession` 取得短期 session）與功能支援不完全相同。例如它的 key 是真正的目錄階層，並支援一般 bucket 沒有的 append 與 rename 操作。使用前要確認你需要的功能都支援。
- 它仍然是 object storage，不是共享檔案系統，不提供檔案鎖等 POSIX 語意。

## 23.4 儲存類別比較表

下表整理考試最常用的欄位。價格會隨 Region 與時間調整，這裡只比較相對高低。

| 類別 | 設計可用度 | 存放 AZ | 最短存放 | 最小計費大小 | 取得資料的時間 | 取回費 | 相對儲存費 |
|---|---|---|---|---|---|---|---|
| Standard | 99.99% | ≥ 3 | 無 | 無 | 毫秒 | 無 | 高 |
| Intelligent-Tiering | 99.9% | ≥ 3 | 無 | 無（< 128 KB 不自動分層） | 毫秒（選用封存層需 restore） | 無（但有監控費） | 依 tier 自動變化 |
| Standard-IA | 99.9% | ≥ 3 | 30 天 | 128 KB | 毫秒 | 每 GB | 中 |
| One Zone-IA | 99.5% | 1 | 30 天 | 128 KB | 毫秒 | 每 GB | 中低 |
| Glacier Instant Retrieval | 99.9% | ≥ 3 | 90 天 | 128 KB | 毫秒 | 每 GB（較高） | 低 |
| Glacier Flexible Retrieval | 99.99%（restore 後） | ≥ 3 | 90 天 | 40 KB metadata | Expedited 1–5 分鐘、Standard 3–5 小時、Bulk 5–12 小時 | Bulk 免費，其餘每 GB | 很低 |
| Glacier Deep Archive | 99.99%（restore 後） | ≥ 3 | 180 天 | 40 KB metadata | Standard 12 小時內、Bulk 48 小時內 | 每 GB | 最低 |
| Express One Zone | 99.95% | 1（directory bucket） | 無 | 無 | 個位數毫秒 | 無 | 高（請求費較低） |

讀這張表的方式是「先刪去不符合硬限制的，再比成本」：

1. **讀取時間**：需要毫秒讀取，就刪掉 Glacier Flexible Retrieval、Deep Archive（以及 Intelligent-Tiering 的選用封存層）。
2. **故障域**：資料不可重建、不能只有一份在單一 AZ，就刪掉 One Zone-IA 與 Express One Zone。
3. **存放時間**：只存 7 天的資料放進 30 天或 90 天最短存放的類別，會被收滿天數的錢。
4. **物件大小**：大量小於 128 KB 的 object，放 IA 或 Glacier IR 會被當成 128 KB 計費。
5. 剩下的選項，再依讀取頻率比較「儲存費 + 取回費 + 請求費」的總成本。

> [!example] 例子：Standard-IA 什麼時候反而更貴？
> 一批 1 TB 的資料每月被完整讀取三次。放 Standard 只付儲存費；放 Standard-IA 雖然儲存費便宜，但每月要付 3 TB 的取回費，加起來很可能比 Standard 更貴。Standard-IA 省錢的前提是「真的不常讀」。

## 23.5 從封存類別取回資料：restore

### Restore 怎麼運作

放在 Glacier Flexible Retrieval 或 Deep Archive 的 object，直接 GET 會得到錯誤（`InvalidObjectState`）。你要先送出 **RestoreObject** 請求，指定兩件事：

- **取回速度等級（retrieval tier）**：
  - Glacier Flexible Retrieval：**Expedited**（通常 1–5 分鐘）、**Standard**（3–5 小時）、**Bulk**（5–12 小時，免取回費）。
  - Deep Archive：**Standard**（12 小時內）、**Bulk**（48 小時內）。Deep Archive 沒有 Expedited。
- **暫時副本保留天數**：例如 `Days: 10`。

Restore 完成後，S3 會建立一份**暫時的可讀副本**，在指定天數內可以直接 GET；原本的 object **仍然留在封存類別**，沒有被搬走。在這段期間，你要同時支付封存類別的費用與暫時副本的儲存費。天數到期後暫時副本自動消失。

如果要讓資料永久回到 Standard，要在 restore 完成後，用 **CopyObject** 把它複製（可以複製到同一個 key）成 Standard 類別。Lifecycle 不能把資料從 Glacier「轉回」Standard。

### 追蹤與自動化

- 查詢 object 的 `x-amz-restore` 標頭，可以知道 restore 是否進行中以及暫時副本的到期時間。
- S3 會發出 `s3:ObjectRestore:Post`（開始）與 `s3:ObjectRestore:Completed`（完成）事件，可以觸發 Lambda 或通知（第 22 章）。比起輪詢，用事件驅動下一步處理更可靠。
- **Expedited** 的「1–5 分鐘」是指小於 250 MB 的 object；250 MB 以上的 object 以每秒最多約 300 MB 的速度取回，所以 1 GB 的檔案也只多花幾秒。它適合偶爾、最多數百個 object 的緊急取回，在需求高峰時可能因容量不足被拒絕。如果業務要求「任何時候都能在幾分鐘內取回」，可以購買 **provisioned capacity（預置取回容量）**：每一單位保證每 5 分鐘至少能執行 3 次 Expedited 取回，並提供最多 300 MB/s 的取回 throughput。
- 要一次 restore 數百萬個 object，用 **S3 Batch Operations**（23.10 節），不要自己寫迴圈逐一呼叫。S3 對 restore 請求有每秒約 1,000 次的帳號配額，Batch Operations 會自動用滿這個速率；透過 Batch Operations 發起的 Glacier Flexible Retrieval Standard 取回通常在數分鐘內就開始陸續完成。

> [!tip] 考試提示
> 「封存資料偶爾需要在幾分鐘內取回」→ Glacier Flexible Retrieval + Expedited（必要時加 provisioned capacity）。「需要時要毫秒讀取」→ Glacier Instant Retrieval，不需要 restore。「可以等 48 小時、要最低成本」→ Deep Archive + Bulk。

## 23.6 Lifecycle rules：讓資料自動變冷、自動消失

知道每種資料該放哪裡之後，下一個問題是：資料的「溫度」會隨時間改變。照片剛上傳時很熱，三個月後變冷；發票存滿七年就該刪掉。用人工搬移數億個 object 不可能，這就是 **S3 Lifecycle（生命週期規則）** 的工作。

### Lifecycle 能做的事

一個 bucket 可以設定多條 lifecycle rule，每條規則包含：

- **Filter（篩選）**：依 **prefix**、**object tags**、**object 大小**（`ObjectSizeGreaterThan`／`ObjectSizeLessThan`）或它們的組合選出適用的 object；不設篩選就套用到整個 bucket。
- **Actions（動作）**：
  - **Transition**：object 建立 N 天後轉到另一個儲存類別。
  - **Expiration**：object 建立 N 天後過期刪除。在 versioning 啟用的 bucket，過期只會加上 delete marker，舊資料變成 noncurrent version。
  - **NoncurrentVersionTransition**／**NoncurrentVersionExpiration**：針對非目前版本，在它「變成 noncurrent」N 天後轉換或刪除；可用 `NewerNoncurrentVersions` 指定保留最近幾個非目前版本。
  - **ExpiredObjectDeleteMarker**：清除「後面已經沒有任何版本」的孤立 delete marker。
  - **AbortIncompleteMultipartUpload**：清除開始 N 天後仍未完成的 multipart upload（第 22 章）。

### Wanderly 的 lifecycle 設計

```json
{
  "Rules": [
    {
      "ID": "invoices-archive-7-years",
      "Status": "Enabled",
      "Filter": { "Prefix": "invoices/" },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 180, "StorageClass": "GLACIER" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 2557 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 }
    },
    {
      "ID": "clickstream-raw-1-year",
      "Status": "Enabled",
      "Filter": { "Prefix": "clickstream/raw/" },
      "Transitions": [
        { "Days": 90, "StorageClass": "GLACIER_IR" }
      ],
      "Expiration": { "Days": 365 }
    },
    {
      "ID": "photos-old-versions",
      "Status": "Enabled",
      "Filter": { "Prefix": "photos/" },
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 30,
        "NewerNoncurrentVersions": 2
      }
    },
    {
      "ID": "bucket-housekeeping",
      "Status": "Enabled",
      "Filter": {},
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 },
      "Expiration": { "ExpiredObjectDeleteMarker": true }
    }
  ]
}
```

逐條說明：

1. **invoices-archive-7-years**：發票前 30 天偶爾會被客服調閱（Standard），30 天後轉 Standard-IA，半年後轉 Glacier Flexible Retrieval，一年後轉 Deep Archive，滿 7 年（2,557 天）過期。稅務稽核要求兩天內調出，Deep Archive 的 Bulk（48 小時內）或 Standard（12 小時內）都符合。非目前版本 30 天後刪除，避免覆寫產生的舊版本累積成本。實際上發票還要用 Object Lock 防止提前刪除（23.8 節）。在 versioning bucket 中，lifecycle 的過期動作只會加上 delete marker，Object Lock 保護中的版本不會因此被刪除。
2. **clickstream-raw-1-year**：最近 90 天分析團隊會查，之後轉 Glacier Instant Retrieval（偶爾重新計算時要能直接讀，不想等 restore），一年後刪除。
3. **photos-old-versions**：照片 bucket 啟用了 versioning 防誤刪。這條規則讓非目前版本在 30 天後刪除，但永遠保留最近 2 個非目前版本。
4. **bucket-housekeeping**：整個 bucket 清理未完成上傳與孤立 delete marker。這條用 `"Filter": {}` 套用到所有 object。

套用方式：`aws s3api put-bucket-lifecycle-configuration --bucket wanderly-docs-prod --lifecycle-configuration file://lifecycle.json`。注意這個 API 會**整份取代**既有的 lifecycle 設定，不是新增一條。

### Lifecycle 的限制與陷阱

- **轉換有方向**：只能從「熱」往「冷」轉（Standard → Standard-IA／Intelligent-Tiering／One Zone-IA → Glacier Instant → Glacier Flexible → Deep Archive），不能用 lifecycle 轉回 Standard。
- **轉到 Standard-IA 或 One Zone-IA 前，object 至少要在 Standard 待滿 30 天**。所以規則寫「建立後 7 天轉 Standard-IA」是不被接受的；若真的需要更早轉換，可以直接上傳到 Standard-IA，或改用 Intelligent-Tiering。
- **小 object 預設不轉換**：自 2024 年 9 月起，新建或修改的 lifecycle 設定預設**不會轉換小於 128 KB 的 object**，因為對小檔案來說轉換請求費與最小計費大小常常讓轉換得不償失。若確定划算，可以用 object 大小篩選明確納入。
- **每次轉換都是付費請求**：數億個小檔案的轉換請求費可能超過省下的儲存費。
- **最短存放天數仍然計算**：在 Standard-IA 待 10 天就被 lifecycle 轉到 Glacier，仍要付 Standard-IA 剩下 20 天的費用。
- **Lifecycle 是非同步的**：規則條件達成後，實際轉換或刪除可能延遲一段時間才執行；但過期的 object 從符合條件的那一刻起就不再計費。
- **Lifecycle 不會被複寫**：來源 bucket 的 lifecycle 動作不會套用到複寫目的地，目的地 bucket 要自己設定規則（23.7 節）。

### 不知道何時該轉換？用 Storage Class Analysis

如果不確定照片幾天後就很少被讀，可以對 bucket 或特定 prefix 開啟 **Storage Class Analysis（儲存類別分析）**。它會觀察實際的存取模式，經過一段時間後給出「多少天後轉到 Standard-IA 最划算」的建議，結果也能匯出到 S3 分析。存取模式完全無法預測時，就直接使用 Intelligent-Tiering。

## 23.7 Replication：把資料複製到另一個 bucket

### 為什麼需要複寫

法務長要求東京 Region 發生災難時仍能取得發票。另外，資安團隊擔心「有人拿到 production 帳號的管理權限，把整個 bucket 刪掉」。這兩個風險都不是 versioning 能解決的，因為版本和原資料在同一個 bucket、同一個 Region、同一個帳號。解法是 **S3 Replication（複寫）**：自動把 object 非同步複製到另一個 bucket。

- **CRR（Cross-Region Replication，跨 Region 複寫）**：目的地在另一個 Region。用途：災難復原、讓遠方使用者就近讀取、法規要求異地保存。
- **SRR（Same-Region Replication，同 Region 複寫）**：目的地在同一個 Region。用途：把多個 bucket 的日誌彙整到一個集中 bucket、在 production 與測試帳號之間同步資料、資料主權不允許離開某個 Region 但仍需要另一份副本。

兩者都可以**跨帳號**，這正是防止「單一帳號被入侵就全毀」的關鍵設計。

### 複寫的前提

1. **來源與目的 bucket 都要啟用 versioning。**
2. S3 需要一個 **IAM role**，讓它以這個 role 讀取來源 object、寫入目的 bucket。
3. **跨帳號時**，目的 bucket 的 bucket policy 要允許這個 role 寫入（`s3:ReplicateObject`、`s3:ReplicateDelete`、`s3:ReplicateTags` 等）。
4. **SSE-KMS 加密的 object 預設不會被複寫**，要在規則中明確啟用（`SseKmsEncryptedObjects`），指定目的地使用的 KMS key，並讓 replication role 有來源 key 的解密權限與目的 key 的加密權限（第 15 章）。
5. 如果來源 bucket 啟用了 Object Lock，目的 bucket 也要啟用 Object Lock。

### 複寫什麼、不複寫什麼

這是考試最愛考的細節：

| 會被複寫 | 不會被複寫 |
|---|---|
| 規則啟用**之後**新寫入的 object（含 metadata、tags） | 規則啟用**之前**就存在的 object（要用 Batch Replication） |
| Object Lock 的保留設定 | **指定 version ID 的刪除**（避免惡意永久刪除被同步到副本） |
| 選擇啟用時：delete marker（`DeleteMarkerReplication`） | 預設不複寫 delete marker（除非啟用） |
| 選擇啟用時：SSE-KMS 加密的 object | Lifecycle 動作（目的地要自行設定 lifecycle） |
| | 已在 Glacier Flexible Retrieval／Deep Archive 封存狀態的 object |

「指定 version ID 的刪除不會被複寫」是一個刻意的安全設計：攻擊者在來源 bucket 永久刪除了某個版本，目的地的那個版本仍然存在。

### 複寫的設定選項

- **Filter**：只複寫特定 prefix 或 tag 的 object。
- **目的地儲存類別**：副本可以直接存成較便宜的類別，例如來源是 Standard、DR 副本存 Standard-IA 或 Glacier。
- **Owner override（`AccessControlTranslation`）**：跨帳號時，讓副本的擁有者變成目的帳號。若目的 bucket 已使用 Bucket owner enforced，副本本來就歸目的帳號擁有。
- **多個目的地**：一個來源可以複寫到多個 bucket。
- **雙向複寫**：兩個 bucket 互相複寫（例如 active-active 多 Region），搭配 **replica modification sync** 讓 metadata 變更也能雙向同步。
- **S3 Replication Time Control（RTC）**：提供有 SLA 的複寫時間保證，**99.99% 的 object 在 15 分鐘內完成複寫**，並啟用複寫指標（待複寫的 object 數、bytes、延遲）與超過門檻時的事件通知。需額外付費。沒有 RTC 時，大多數 object 會在 15 分鐘內複寫完成，但偶爾可能需要數小時，且沒有任何時間保證。

### 補複寫既有資料：S3 Batch Replication

一般的複寫規則只處理「規則建立之後」的新 object。Wanderly 要把過去五年的發票也複寫到大阪，就要用 **S3 Batch Replication**：它是 S3 Batch Operations 的一種作業，可以依照 S3 產生的清單複寫：

- 規則建立前就已存在的 object；
- 之前複寫失敗的 object；
- 已經複寫過、但要再複寫到新目的地的 object。

### Wanderly 的複寫架構

```text
  生產帳號 111122223333（東京 ap-northeast-1）
  ┌──────────────────────────────────────┐
  │ wanderly-docs-prod                   │
  │  versioning ✓  Object Lock ✓  SSE-KMS │
  │  invoices/  orders/  photos/         │
  └──────┬───────────────────────────────┘
         │ ① 新 object（invoices/、orders/）
         │   replication role 讀取來源、以目的 KMS key 加密
         │ ② RTC：99.99% 在 15 分鐘內
         │ ③ 不複寫 delete marker、不複寫指定版本的刪除
         ▼
  備份帳號 999988887777（大阪 ap-northeast-3）
  ┌──────────────────────────────────────┐
  │ wanderly-docs-dr                     │
  │  versioning ✓  Object Lock ✓（compliance）│
  │  bucket policy 只允許 replication role 寫入 │
  │  副本儲存類別：Standard-IA             │
  │  owner = 備份帳號                      │
  └──────────────────────────────────────┘
  ④ 既有五年資料 → S3 Batch Replication 一次補齊
```

① 只複寫需要 DR 的 prefix，照片可以從旅館重新取得就不複寫。② RTC 讓稽核可以看到複寫延遲的指標與 SLA。③ 生產帳號的刪除不會傳到備份帳號，即使生產帳號被入侵，備份帳號的副本仍在。④ 規則只管新資料，舊資料用 Batch Replication 補。備份帳號的管理權限只交給少數人，生產帳號的管理者無法登入它。

對應的複寫設定：

```json
{
  "Role": "arn:aws:iam::111122223333:role/s3-replication-docs",
  "Rules": [
    {
      "ID": "docs-to-osaka-backup-account",
      "Priority": 1,
      "Status": "Enabled",
      "Filter": { "Prefix": "invoices/" },
      "DeleteMarkerReplication": { "Status": "Disabled" },
      "SourceSelectionCriteria": {
        "SseKmsEncryptedObjects": { "Status": "Enabled" }
      },
      "Destination": {
        "Bucket": "arn:aws:s3:::wanderly-docs-dr",
        "Account": "999988887777",
        "StorageClass": "STANDARD_IA",
        "AccessControlTranslation": { "Owner": "Destination" },
        "EncryptionConfiguration": {
          "ReplicaKmsKeyID": "arn:aws:kms:ap-northeast-3:999988887777:key/1234abcd-12ab-34cd-56ef-1234567890ab"
        },
        "ReplicationTime": {
          "Status": "Enabled",
          "Time": { "Minutes": 15 }
        },
        "Metrics": {
          "Status": "Enabled",
          "EventThreshold": { "Minutes": 15 }
        }
      }
    }
  ]
}
```

使用 `Filter` 的新版設定時，`DeleteMarkerReplication` 必須明確寫出；啟用 RTC 時也必須同時啟用 `Metrics`。`orders/` 若也要複寫，就再加一條不同 `Priority` 的規則。

> [!warning] 常見誤解
> 「設定好 CRR 就等於有了 RPO 為零的同步備份。」複寫是**非同步**的，來源寫入成功時副本可能還沒建立；RTC 也只保證 15 分鐘內完成 99.99%。另外，若啟用了 delete marker 複寫，一般刪除也會同步到副本。複寫解決的是「異地有另一份」，不是「任何操作都能回復」，要防誤刪還要搭配 versioning 與 Object Lock。

## 23.8 Object Lock：誰都刪不掉的資料

### WORM 是什麼

**WORM（Write Once, Read Many，一次寫入、多次讀取）** 是許多法規對紀錄保存的要求：資料寫入後，在保存期限內不能被修改或刪除。**S3 Object Lock** 就是 S3 的 WORM 機制。它保護的是**特定 object 版本**：在保護期間內，那個版本不能被刪除或覆寫。

幾個基本規則：

- Object Lock 需要 versioning，啟用 Object Lock 時 versioning 會自動啟用且之後不能暫停。新 bucket 可以在建立時啟用，既有 bucket 也可以啟用。**一旦啟用，就不能關閉 Object Lock。**
- 被鎖定的是版本。對受保護的 object 執行一般 DELETE（不指定 version ID）仍會成功，只是新增一個 delete marker；被保護的那個版本仍然存在，也無法被永久刪除。「覆寫」也一樣只是新增一個版本。
- 可以在 bucket 設定**預設保留模式與期間**，之後新上傳的 object 自動套用；也可以在上傳時為個別 object 指定。

### 兩種保留模式與 legal hold

| 機制 | 誰可以提前刪除或縮短期限 | 有到期日嗎 | 典型用途 |
|---|---|---|---|
| **Governance mode（治理模式）** | 擁有 `s3:BypassGovernanceRetention` 權限，並在請求中明確帶上 bypass 標頭的使用者 | 有（retain until date） | 防止一般使用者誤刪；測試保留政策；需要少數管理者保有例外權限 |
| **Compliance mode（合規模式）** | **沒有任何人**，包含 root user；只能延長，不能縮短（期限前要刪除，唯一的方法是關閉整個 AWS 帳號） | 有 | 法規要求的不可變紀錄（金融、醫療、稅務） |
| **Legal hold（法律保全）** | 擁有 `s3:PutObjectLegalHold` 權限的人可以移除 | **沒有**，直到被移除 | 訴訟或調查期間，不確定要保留多久 |

Legal hold 和保留模式是**獨立的**：一個版本可以同時有 compliance 保留期限與 legal hold，兩者都解除後才能刪除。保留期限到了但 legal hold 還在，仍然不能刪。

> [!warning] 常見誤解：compliance mode 是真的不能回頭
> 在 compliance mode 下設定了 10 年保留，如果設錯了（例如應該是 1 年），**沒有任何方法可以縮短**，你會為那份資料付 10 年的儲存費。所以正式套用 compliance mode 前，先用 governance mode 測試流程與期限，確認無誤再切換。

### Wanderly 的發票保護

小周的設計是：`wanderly-docs-prod` 的 `invoices/` 在上傳時套用 **compliance mode、7 年保留**；大阪的 DR bucket 也啟用 Object Lock，複寫過去的副本帶著相同的保留設定。這樣即使有人取得 production 帳號的 root 權限，也無法刪除保存期限內的發票，備份帳號裡的副本也一樣受保護。稅務糾紛發生時，法務再對相關發票加上 legal hold，直到案件結束。

## 23.9 MFA Delete：刪除前要多一道驗證

**MFA Delete** 是 versioning 的附加保護：啟用後，以下兩種操作都必須在請求中附上 MFA 裝置的驗證碼：

1. **永久刪除某個 object 版本**（指定 version ID 的 DELETE）。
2. **變更 bucket 的 versioning 狀態**（例如暫停 versioning）。

它的特殊規則：

- 只有 **bucket 擁有者帳號的 root user** 可以啟用或停用 MFA Delete，而且只能透過 **AWS CLI 或 API**（不能在 console 上設定），請求中要帶 root user 的 MFA 裝置序號與驗證碼。
- Bucket 必須已啟用 versioning。
- 一般的 DELETE（只新增 delete marker）不需要 MFA。
- 官方文件註明 MFA Delete 不能與 lifecycle 設定一起使用，所以需要自動清理舊版本的 bucket 通常改用 Object Lock 等其他保護。

| 比較 | MFA Delete | Object Lock |
|---|---|---|
| 保護對象 | 永久刪除版本、變更 versioning 狀態 | 指定版本在期限內不可刪除或覆寫 |
| 誰能繞過 | 有 root MFA 的人 | Governance：有 bypass 權限者；Compliance：沒有人 |
| 設定方式 | Root user 透過 CLI／API | Bucket 設定、預設保留或每個 object 設定 |
| 適合 | 額外防止誤刪的操作門檻 | 法規 WORM、防勒索 |

考試中，「防止意外永久刪除版本，額外要求 MFA」是 MFA Delete；「法規要求在一段期間內任何人都不能刪除」是 Object Lock compliance mode。

## 23.10 管理數億個 object：Inventory、Batch Operations 與 Storage Lens

Wanderly 的 bucket 裡已經有 12 億個 object。「有多少 object 還沒加密？」「把這 600 萬張照片的 tag 全部改掉」「哪個帳號的哪個 bucket 成本漲最多？」這類問題，用 LIST API 一頁一頁翻是不可行的。

### S3 Inventory：bucket 的清單報表

**S3 Inventory** 每天或每週產生一份 bucket（或特定 prefix）內所有 object 的清單，輸出為 CSV、ORC 或 Parquet 檔，放到你指定的 bucket（可以在另一個帳號）。清單可以包含每個 object 的大小、儲存類別、加密狀態、複寫狀態、Object Lock 設定、Intelligent-Tiering 的目前 tier、最後修改時間等。

常見用途：

- 用 **Athena** 查詢清單，例如「列出所有沒有加密的 object」「各 prefix 的容量分布」。
- 稽核複寫狀態：找出 `FAILED` 的 object。
- 作為 Batch Operations 的輸入清單（manifest）。

它比 LIST API 便宜得多，也不會對 bucket 造成大量請求負擔，但它是定期快照，不是即時資料。

### S3 Batch Operations：對大量 object 執行同一個動作

**S3 Batch Operations** 讓你對一份清單中的所有 object 執行同一個操作，由 S3 管理平行處理、重試與進度追蹤，完成後產生 **completion report（完成報告）**，列出每個 object 的成功或失敗。

- **清單來源**：S3 Inventory 報表、自己提供的 CSV，或讓 S3 依條件（prefix、建立時間、儲存類別等）自動產生。
- **可執行的操作**：複製 object（例如改變儲存類別或加密方式）、呼叫 Lambda function 做自訂處理、取代或刪除 tags、取代 ACL、**restore 封存的 object**、設定 Object Lock 保留期限與 legal hold、**Batch Replication**、計算 checksum 等。
- 作業以一個 IAM role 的權限執行，可以設定優先順序、需要確認後才開始。

典型情境：「把既有 2 億個未加密的 object 改成 SSE-KMS」→ 用 Inventory 找出未加密的 object 作為 manifest，Batch Operations 執行 Copy（就地複製並指定加密）。「稽核要在 30 天內查閱 600 萬個 Deep Archive 中的檔案」→ Batch Operations restore 作業，依 completion report 追蹤失敗項目並重試。

### S3 Storage Lens：整個組織的儲存儀表板

**S3 Storage Lens** 提供跨帳號、跨 Region 的儲存使用與活動分析：

- 可以在單一帳號使用，也可以與 **AWS Organizations** 整合，由 management account 或 **delegated administrator** 帳號查看整個組織所有帳號的 S3 使用情況。
- **免費指標（free metrics）**：容量、object 數、儲存類別分布、未加密或未啟用 versioning 等資料保護與成本相關指標，保留 14 天歷史。
- **進階指標與建議（advanced metrics and recommendations，付費）**：加上請求活動、prefix 層級的分析、詳細的狀態碼與成本最佳化建議（例如「這個 bucket 有大量未完成的 multipart upload」「這些 bucket 沒有 lifecycle 規則」），歷史保留 15 個月，並可發布到 CloudWatch。
- 指標可以每天匯出到 S3 做進一步分析。

三者的分工：**Storage Lens 告訴你「哪裡有問題」**（組織層級、趨勢），**Inventory 告訴你「具體是哪些 object」**（object 層級清單），**Batch Operations 負責「把它們全部修好」**。

```text
 治理：Storage Lens（組織層級）→ Inventory + Athena（找出問題 object）→ Batch Operations（修正）
```

照片的存取模式無法預測（某家旅館可能突然爆紅），所以交給 Intelligent-Tiering，避免 Standard-IA 的取回費風險；照片平均大於 128 KB，監控費也划算。縮圖剛產生時和照片一樣熱門，先留在 Standard；30 天後轉 One Zone-IA，因為可重建，比 Standard-IA 再省約兩成。發票的存取模式非常確定（越舊越少讀），用 lifecycle 一路轉到 Deep Archive，並以 Object Lock 加上跨帳號 CRR 滿足法務的兩個要求。點擊流 90 天後轉 Glacier Instant Retrieval，重新計算時不用等 restore。整套設計上線後，小周估算 S3 每月費用下降約六成，而且成長曲線從此跟著「熱資料量」而不是「總資料量」走。

## 23.12 比較與選型

### 儲存類別選擇流程

```text
資料可以重建，或已有其他副本？
├─ 是 → 需要極低延遲、與運算同 AZ、高請求率？
│        ├─ 是 → S3 Express One Zone
│        └─ 否 → 不常讀 → One Zone-IA
└─ 否（必須跨 AZ）→ 存取模式可預測嗎？
         ├─ 不可預測或會變化 → Intelligent-Tiering
         └─ 可預測 → 讀取頻率？
                  ├─ 頻繁（每月多次）→ Standard
                  ├─ 約每月一次、要毫秒 → Standard-IA
                  ├─ 每季或更少、要毫秒 → Glacier Instant Retrieval
                  ├─ 每年一兩次、可等分鐘到小時 → Glacier Flexible Retrieval
                  └─ 幾乎不讀、可等 12–48 小時 → Glacier Deep Archive
（再檢查：存放天數是否短於最短存放天數？object 是否大多小於 128 KB？）
```

### 資料保護機制比較

| 需求 | 機制 | 不能解決的 |
|---|---|---|
| 誤刪、誤覆寫可以復原 | Versioning | Bucket 被刪、帳號被入侵、Region 災難 |
| 永久刪除版本需要額外驗證 | MFA Delete | 擁有 root MFA 的人仍可刪除 |
| 法規 WORM，期限內任何人不能刪 | Object Lock compliance | 不會產生異地副本 |
| 防誤刪，但保留少數人的例外權限 | Object Lock governance | 有 bypass 權限者可刪除 |
| 期限不確定的保全 | Legal hold | 需要人工解除 |
| 另一個 Region 的副本（DR） | CRR（+ RTC） | 非同步，不是零 RPO |
| 帳號被入侵仍保有副本 | 跨帳號複寫 + 目的地 Object Lock | 來源寫入的錯誤資料一樣會被複寫 |
| 集中備份政策、跨服務 | AWS Backup（第 34 章） | — |

| Storage Lens | 組織哪裡在長、哪裡有風險 | 儀表板、指標、建議 |

## 23.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| 存取模式未知、會變化、不想管理 | S3 Intelligent-Tiering |
| 不常讀、要毫秒、資料不可重建 | Standard-IA（每季以下讀：Glacier Instant Retrieval） |
| 可重新產生的資料、最低成本、毫秒讀取 | One Zone-IA |
| 長期保存、幾乎不讀、可等 12–48 小時、最低成本 | Glacier Deep Archive |
| 封存資料偶爾要在數分鐘內取回 | Glacier Flexible Retrieval + Expedited（+ provisioned capacity） |
| 和運算同 AZ、單一位數毫秒、高請求率 | S3 Express One Zone（directory bucket） |
| 自動轉換類別、到期刪除 | Lifecycle rules |
| Versioning bucket 舊版本累積成本 | NoncurrentVersionExpiration（`NewerNoncurrentVersions`） |
| 跨 Region DR 副本 | CRR（兩邊都要 versioning） |
| 複寫要有時間 SLA（15 分鐘） | S3 Replication Time Control |
| 既有 object 沒有被複寫 | S3 Batch Replication |
| 法規要求任何人（含 root）都不能刪除 | Object Lock compliance mode |
| 調查期間保留、期限不明 | Object Lock legal hold |
| 永久刪除版本需要 MFA | MFA Delete（root、CLI 啟用） |
| 對數百萬個 object 執行 restore／複製／改 tag | S3 Batch Operations（manifest 用 Inventory） |
| 整個組織的 S3 使用與成本最佳化建議 | S3 Storage Lens（Organizations + delegated admin） |
| 找出所有未加密或複寫失敗的 object | S3 Inventory + Athena |

**常見陷阱**：

1. **把 One Zone-IA 用在唯一且不可重建的資料**：一個 AZ 損毀資料就遺失。
2. **只看儲存費**：短期存放（少於 30／90／180 天）或頻繁讀取的資料放進 IA／Glacier 類別，總成本反而更高。
3. **以為 lifecycle 可以把資料轉回 Standard**：要先 restore 再 copy。
4. **以為 CRR 會自動複製既有資料**：只處理規則建立後的新 object，舊資料用 Batch Replication。
5. **以為刪除一定會被複寫**：指定版本的刪除永遠不複寫，delete marker 預設不複寫。
6. **把 governance mode 當成不可刪除**：有 bypass 權限的人可以刪；法規要求要用 compliance mode。
7. **以為 MFA Delete 可在 console 啟用或由 IAM 管理員啟用**：只有 root user 透過 CLI／API。
8. **以為 Intelligent-Tiering 的所有 tier 都是毫秒讀取**：選用的 Archive Access 與 Deep Archive Access 需要 restore。

## 23.14 SAP 加深：防勒索備份、多帳號成本治理與合規證據

### 防勒索的 S3 備份架構

SAP 題目常問：「攻擊者取得 production 帳號的管理員權限，如何確保資料仍可復原？」關鍵是**讓攻擊者能碰到的權限，碰不到備份**：

1. **獨立的備份帳號**，位於獨立的 OU，以 SCP 限制只有少數 break-glass 身份能管理（第 14、40 章）。
2. **跨帳號複寫**到備份帳號，並使用 owner override 或 Bucket owner enforced，讓副本歸備份帳號擁有；production 帳號的 replication role 在目的地只有寫入複寫的權限，沒有刪除或修改 lifecycle、Object Lock 設定的權限。
3. **不複寫 delete marker**；指定版本的刪除本來就不會複寫。
4. **目的 bucket 啟用 Object Lock**（通常是 compliance mode，期限依 RPO 與保存政策），讓即使備份帳號被入侵，期限內的版本也無法刪除。
5. 定期演練復原，並用 RTC 指標與 Inventory 的複寫狀態證明副本完整。

勒索軟體的另一種攻擊是「用加密後的內容覆寫 object」。這時新版本（被加密的內容）也會被複寫，但因為 versioning 與 Object Lock 保留了舊版本，可以還原到攻擊前的版本。AWS Backup 也支援 S3，並提供 vault lock 與跨帳號複製，可作為集中化的替代或補充（第 34 章）。

### 多帳號的 S3 成本治理

當組織有上百個帳號時，成本最佳化的流程是：

1. 以 delegated administrator 啟用組織層級的 **Storage Lens**（含進階指標），找出成長最快、沒有 lifecycle、未完成上傳最多、非目前版本占比過高的 bucket。
2. 依建議為各團隊制定**標準 lifecycle 範本**，透過 IaC（CloudFormation StackSets、第 37 章）推送；以 AWS Config rule 偵測沒有 lifecycle 或沒有加密的 bucket。
3. 用 **cost allocation tags** 與 Cost Explorer 把 S3 費用分攤到團隊（第 39 章）。
4. 對大型、存取模式不明的資料湖，預設使用 Intelligent-Tiering，減少各團隊自行調整的負擔。

### 合規證據

稽核人員要的不只是「有開 Object Lock」，而是**證據**：S3 Inventory 可以列出每個 object 的 Object Lock 模式與到期日；Storage Lens 顯示組織內 Object Lock 與 versioning 的覆蓋率；CloudTrail 記錄任何嘗試修改保留設定的 API 呼叫；AWS Config 可以持續檢查 bucket 是否啟用 Object Lock、versioning 與複寫（第 16 章）。把這些產出集中到 log archive 帳號，就是一套可交給稽核的證據鏈。

## 本章重點整理

- S3 的成本由儲存費、請求費、取回費、最短存放天數與最小計費大小組成，越冷的類別存放越便宜但讀取與短期存放越貴。
- 所有儲存類別耐久度都是 11 個 9；One Zone-IA 與 Express One Zone 只存在一個 AZ，AZ 損毀時資料可能遺失，只適合可重建的資料。
- Standard-IA 與 One Zone-IA 有 30 天最短存放與 128 KB 最小計費；Glacier Instant 與 Flexible 為 90 天，Deep Archive 為 180 天。
- Intelligent-Tiering 自動在 Frequent、Infrequent、Archive Instant 之間移動，沒有取回費但有每個 object 的監控費；選用的封存層需要 restore。
- Glacier Flexible Retrieval 與 Deep Archive 的 object 要先 restore 才能讀，restore 產生有期限的暫時副本，原 object 仍留在封存類別。
- Glacier Flexible Retrieval 取回等級為 Expedited 1–5 分鐘、Standard 3–5 小時、Bulk 5–12 小時；Deep Archive 為 Standard 12 小時內、Bulk 48 小時內。
- Lifecycle 可依 prefix、tag、大小篩選，執行 transition、expiration、非目前版本處理、清除 delete marker 與未完成上傳；只能由熱往冷轉。
- 轉到 Standard-IA／One Zone-IA 前 object 至少要在 Standard 待 30 天；小於 128 KB 的 object 預設不會被 lifecycle 轉換。
- 複寫（CRR／SRR）需要兩邊都啟用 versioning 與一個 IAM role，是非同步的，只處理規則建立後的新 object，既有資料用 Batch Replication。
- 指定版本的刪除永遠不會被複寫，delete marker 預設不複寫，SSE-KMS object 需明確啟用才會複寫，lifecycle 動作也不會複寫。
- S3 RTC 保證 99.99% 的 object 在 15 分鐘內完成複寫，並提供複寫指標與事件通知。
- Object Lock 需要 versioning、啟用後不能關閉；governance mode 可由具 bypass 權限者繞過，compliance mode 任何人（含 root）都不能刪除或縮短；legal hold 沒有到期日。
- MFA Delete 只能由 root user 透過 CLI／API 啟用，要求永久刪除版本與變更 versioning 狀態時提供 MFA。
- Storage Lens 找出組織層級的問題、Inventory 列出具體 object、Batch Operations 對數百萬個 object 執行同一操作並產生 completion report。
- 防勒索的 S3 備份要點是跨帳號複寫到隔離的備份帳號、不複寫刪除、目的地啟用 Object Lock 並定期演練復原。

## 本章練習題

### 練習 23-1｜SAA｜單選｜Standard-IA 的適用條件

Wanderly 有兩批資料目前都放在 S3 Standard：第一批是每月產生的營運報表，每份約 200 MB，要保存兩年，平均每份每月只被打開約一次，但主管要看時必須立刻開啟；第二批是每天的匯入暫存檔，每份約 1 GB，存放 7 天就刪除，期間每天被讀取數次。財務部希望降低總成本。

最合適的調整是什麼？

- A. 兩批資料都改放 Standard-IA，因為它的儲存費較低
- B. 兩批資料都改放 Glacier Deep Archive，因為它是最便宜的儲存類別
- C. 營運報表改放 Standard-IA，匯入暫存檔維持 Standard
- D. 營運報表改放 One Zone-IA，匯入暫存檔改放 Standard-IA

> [!answer]- 答案：C
> **A ✗** 暫存檔只存 7 天，Standard-IA 的 30 天最短存放會讓它被收滿 30 天的錢，而且每天多次讀取會產生大量取回費，總成本反而更高。
>
> **B ✗** Deep Archive 要先 restore、等 12 小時以上才能讀，不符合「主管要立刻開啟」；暫存檔存 7 天也會被收 180 天的最短存放費用。
>
> **C ✓** 營運報表長期保存、大約每月讀一次且需要毫秒存取，正是 Standard-IA 的情境。暫存檔存放時間短又頻繁讀取，Standard 沒有最短存放與取回費，是最便宜的選擇。
>
> **D ✗** 營運報表是唯一的一份資料，放在單一 AZ 的 One Zone-IA 有 AZ 損毀時遺失的風險；暫存檔放 Standard-IA 仍有最短存放與取回費問題。
>
> **考點**：SAA-4.1｜Standard-IA 的最短存放天數與取回費

### 練習 23-2｜SAA｜單選｜可重建資料的儲存類別

Wanderly 會從每張原始旅館照片產生三種尺寸的縮圖，原始照片存在 S3 Standard 並有跨 Region 複寫。縮圖總量約 60 TB，三個月後就很少被讀取，但偶爾被讀取時必須在毫秒內回應。團隊確認若縮圖遺失，可以從原始照片重新產生，並希望把縮圖的儲存成本降到最低。

三個月後的縮圖應放在哪個儲存類別？

- A. S3 One Zone-IA
- B. S3 Standard-IA
- C. S3 Glacier Flexible Retrieval
- D. S3 Express One Zone

> [!answer]- 答案：A
> **A ✓** One Zone-IA 提供毫秒讀取，儲存費比 Standard-IA 更低，代價是資料只存在一個 AZ。縮圖可以從有異地副本的原始照片重新產生，正好可以接受這個故障域，是最低成本的選擇。
>
> **B ✗** Standard-IA 跨多個 AZ、同樣毫秒讀取，可以滿足需求，但儲存費比 One Zone-IA 高；在資料可重建的前提下，多 AZ 的耐久性是不必要的成本。
>
> **C ✗** Glacier Flexible Retrieval 需要 restore，最快也要數分鐘，不符合毫秒讀取。
>
> **D ✗** Express One Zone 是為低延遲、高請求率的工作負載設計，儲存費比 IA 類別高，不適合很少讀取的資料。
>
> **考點**：SAA-4.1｜One Zone-IA 用於可重建資料

### 練習 23-3｜SAA｜單選｜存取模式無法預測

Wanderly 的旅遊攻略平台讓使用者上傳文章附圖，平均每張 2 MB，目前共 300 TB。分析顯示大多數圖片上傳一個月後就很少被讀，但每週都會有一些舊文章因為社群分享突然爆紅，舊圖片被大量讀取。團隊希望降低儲存成本，同時所有圖片隨時都要能毫秒讀取，也不想自己維護存取分析與搬移程式。

最合適的做法是什麼？

- A. 以 lifecycle 在上傳 30 天後把圖片轉到 Standard-IA
- B. 以 lifecycle 在上傳 30 天後把圖片轉到 Glacier Flexible Retrieval，爆紅時再 restore
- C. 保留在 S3 Standard，並用 CloudFront 快取降低 S3 讀取次數
- D. 把圖片放在 S3 Intelligent-Tiering，不啟用需要 restore 的選用封存層

> [!answer]- 答案：D
> **A ✗** 轉到 Standard-IA 後，爆紅的舊圖片每次被讀取都要付取回費，大量讀取時可能抵銷甚至超過省下的儲存費。
>
> **B ✗** Glacier Flexible Retrieval 需要先 restore，最快也要數分鐘，無法滿足隨時毫秒讀取。
>
> **C ✗** CloudFront 能降低請求與傳輸成本，但 300 TB 資料仍以 Standard 價格存放，沒有解決儲存費的主要問題。
>
> **D ✓** Intelligent-Tiering 自動把一段時間沒被存取的圖片移到較便宜的 tier，被讀取時再移回 Frequent Access，沒有取回費；預設的 tier 都是毫秒讀取。圖片平均 2 MB，每個 object 的監控費相對於省下的儲存費很小。不啟用選用封存層，才能確保隨時毫秒讀取。
>
> **考點**：SAA-4.1｜Intelligent-Tiering 處理不可預測的存取模式

### 練習 23-4｜SAA｜單選｜極少讀取但要立刻取得

Wanderly 依法規保存旅客的身份證件掃描檔 5 年，每個檔案約 3 MB。這些檔案平均一年只會被客服調閱不到一次，但每次調閱都是旅客正在線上等候，必須在毫秒內開啟。檔案是唯一的一份，不能接受單一 AZ 故障造成遺失。團隊希望在滿足以上條件下儲存成本最低。

應選擇哪個儲存類別？

- A. S3 Standard-IA
- B. S3 Glacier Instant Retrieval
- C. S3 Glacier Flexible Retrieval，並使用 Expedited 取回
- D. S3 One Zone-IA

> [!answer]- 答案：B
> **A ✗** Standard-IA 也能毫秒讀取並跨多個 AZ，但它適合大約每月讀一次的資料；對每年不到一次的讀取，Glacier Instant Retrieval 的儲存費更低，總成本更划算。
>
> **B ✓** Glacier Instant Retrieval 為每季或更少讀取、但需要毫秒取得的長期資料設計，資料跨多個 AZ，儲存費低於 Standard-IA。5 年的存放期遠超過 90 天最短存放，每個檔案也大於 128 KB。
>
> **C ✗** Expedited 通常仍需 1–5 分鐘，不是毫秒；而且需求高峰時可能被拒絕，不適合旅客線上等候的情境。
>
> **D ✗** One Zone-IA 只存在一個 AZ，不符合「唯一一份、不能接受單一 AZ 故障遺失」。
>
> **考點**：SAA-4.1、SAA-1.3｜Glacier Instant Retrieval 的使用時機

### 練習 23-5｜SAA｜單選｜最低成本的長期封存

Wanderly 每天產生約 50 GB 的會計原始憑證壓縮檔，依法須保存 10 年，必須存放在多個 AZ。歷史經驗顯示這些檔案平均每三年才會被調閱一次，稽核規定調閱時可在 48 小時內提供。團隊希望長期儲存成本最低。

最合適的設計是什麼？

- A. 直接上傳到 S3 Glacier Deep Archive，調閱時以 Bulk 或 Standard 等級 restore
- B. 上傳到 S3 Glacier Instant Retrieval，確保隨時可以毫秒讀取
- C. 上傳到 S3 One Zone-IA，並以 lifecycle 在 10 年後刪除
- D. 上傳到 S3 Intelligent-Tiering，不啟用任何選用封存層

> [!answer]- 答案：A
> **A ✓** Deep Archive 是儲存費最低的類別，資料跨多個 AZ。Bulk 在 48 小時內、Standard 在 12 小時內完成 restore，都符合稽核時限；10 年的存放期也遠超過 180 天最短存放。檔案已壓縮成大檔，40 KB 的 metadata 額外計費可以忽略。
>
> **B ✗** Glacier Instant Retrieval 提供不需要的毫秒讀取能力，儲存費比 Deep Archive 高。
>
> **C ✗** One Zone-IA 只存在一個 AZ，違反「必須存放在多個 AZ」，而且儲存費也比 Deep Archive 高很多。
>
> **D ✗** 不啟用封存層時，Intelligent-Tiering 最便宜的是 Archive Instant Access tier，仍比 Deep Archive 貴，還要付監控費。
>

### 練習 23-7｜SAA｜選兩項｜Versioning bucket 的成本失控

Wanderly 的設定檔 bucket 已啟用 versioning，應用程式每 10 分鐘會覆寫同一批設定檔，偶爾也會上傳大型匯出檔。財務發現這個 bucket 的儲存量是目前可見 object 總量的 40 倍。調查發現兩個原因：大量的非目前版本，以及許多中途失敗、從未完成的大型上傳。團隊要求每個設定檔仍能回復到最近的幾個版本。

哪兩條 lifecycle 設定能解決問題？（選兩項）

- A. 對整個 bucket 設定 `Expiration`，讓目前版本在 1 天後過期
- B. 設定 `NoncurrentVersionExpiration`，讓非目前版本在數天後刪除，並以 `NewerNoncurrentVersions` 保留最近幾個版本
- C. 暫停 versioning，讓既有的非目前版本自動被刪除
- D. 設定 `AbortIncompleteMultipartUpload`，清除開始數天後仍未完成的 multipart upload
- E. 設定 `Transition`，把目前版本在 1 天後轉到 Standard-IA

>
> **B ✓** 非目前版本的處理要用專門的 `NoncurrentVersionExpiration`。搭配 `NewerNoncurrentVersions` 可以保留最近幾個版本供回復，其餘的在指定天數後刪除，直接解決版本累積問題。
>
> **C ✗** 暫停 versioning 只影響之後的寫入，已存在的非目前版本不會被刪除。
>
> **D ✓** 未完成的 multipart upload 已上傳的 part 會持續計費且不會出現在 object 列表中，`AbortIncompleteMultipartUpload` 會自動清除它們。
>
> **E ✗** Lifecycle 要求 object 在 Standard 至少待 30 天才能轉到 Standard-IA；何況這些設定檔每 10 分鐘就被覆寫，轉換只會產生請求費與最短存放費用。
>
> **考點**：SAA-4.1｜noncurrent version 與未完成上傳的 lifecycle 清理

### 練習 23-9｜SAA｜單選｜Object Lock 模式選擇

應如何設定？

- A. 使用 Object Lock compliance mode，保留 30 天
- B. 使用 Object Lock governance mode，保留 30 天，只授予兩位管理員 `s3:BypassGovernanceRetention` 權限

> **C ✗** Legal hold 沒有到期日，30 天後不會自動解除，需要人工逐一移除，不符合固定 30 天的政策。
>
> **D ✗** MFA Delete 只對永久刪除版本加上 MFA 驗證，沒有保留期限的概念；共用 root user 的 MFA 裝置也違反帳號安全最佳實務。
>
> **考點**：SAA-1.3｜Object Lock governance 與 compliance mode

### 練習 23-15｜SAP｜選兩項｜防勒索的 S3 備份設計

Wanderly 的資安團隊進行勒索軟體演練，假設攻擊者已取得 production 帳號的完整管理員權限，可能大量刪除 object、永久刪除版本，或用加密後的內容覆寫檔案。團隊要確保訂單文件 bucket 在這種情況下仍能完整復原，並盡量不影響現有應用程式。

> **考點**：SAP-2.2、SAP-3.2｜跨帳號複寫與 Object Lock 防勒索

### 練習 23-16｜SAP｜單選｜大量小檔案的 lifecycle 成本

Wanderly 的 IoT 行李追蹤服務每天產生約 3,000 萬個 8 KB 的定位紀錄 object，存 60 天後刪除，只有寫入後的前兩天會被讀取。團隊在 lifecycle 中新增「建立 30 天後轉到 Standard-IA」的規則，沒有設定任何 object 大小篩選。一個月後，帳單顯示沒有任何 object 被轉換。財務長詢問是否應該修正規則讓它生效。

最合適的建議是什麼？

- A. 規則錯誤，應改為建立 1 天後轉到 Standard-IA，才能吸收最短存放天數
- B. 規則錯誤，應改為轉到 Glacier Instant Retrieval，因為它沒有最小計費大小
- C. 這是預期行為：lifecycle 預設不轉換小於 128 KB 的 object；即使加上大小篩選強制轉換，8 KB 的 object 在 Standard-IA 會以 128 KB 計費並產生大量轉換請求費，維持 Standard 或把紀錄批次合併成大檔更划算
- D. 應改用 Intelligent-Tiering，讓這些小檔案自動進入 Infrequent Access tier

> [!answer]- 答案：C
> **A ✗** Lifecycle 要求 object 至少在 Standard 待 30 天才能轉到 Standard-IA，1 天的規則不被接受；而且轉換後仍有最小計費大小問題。
>
> **B ✗** Glacier Instant Retrieval 同樣有 128 KB 最小計費大小與 90 天最短存放；這些資料 60 天就刪除，還會被收提前刪除費。
>
> **C ✓** 自 2024 年 9 月起，lifecycle 預設不轉換小於 128 KB 的 object，所以規則沒有生效是預期行為。8 KB 的 object 在 Standard-IA 以 128 KB 計費，等於儲存費放大 16 倍，再加上每天數千萬次的轉換請求費，一定比留在 Standard 更貴。若要降低成本，應在寫入端把紀錄批次合併成較大的檔案。
>
> **D ✗** 小於 128 KB 的 object 在 Intelligent-Tiering 不會被監控，永遠以 Frequent Access tier 計價，不會自動移到較便宜的 tier。
>
> **考點**：SAP-1.5、SAP-3.5｜最小計費大小、128 KB 轉換預設與小檔案成本
