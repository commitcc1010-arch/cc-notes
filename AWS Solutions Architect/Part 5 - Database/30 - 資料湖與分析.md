## 30.1 故事：月報讓訂房網站變慢了

Wanderly 進入成長期之後，每天有幾十萬筆訂單、上千萬筆搜尋與點擊紀錄。行銷團隊每週一早上要看「上週各城市的訂房轉換率」，財務每月初要算「每家旅館的佣金與退款」，產品經理則隨時想知道「新的搜尋排序有沒有讓使用者更快下單」。

一開始，資料分析師小周直接連到 Aurora MySQL 的 read replica 跑 SQL。資料量小的時候還好，但當訂單表超過三億筆，一個「按城市、按週彙總兩年資料」的查詢要跑四十分鐘，而且把 replica 的 CPU 打到 100%，連帶讓同樣讀 replica 的會員中心變慢。更麻煩的是，點擊紀錄根本不在資料庫裡：它們是每天寫進 S3 的 JSON log，小周只能下載到筆電，用 Python 慢慢處理。

技術主管列出三個問題。第一，**分析查詢和線上交易搶資源**，影響使用者體驗。第二，**資料散在不同地方**（Aurora、DynamoDB、S3 log、第三方廣告平台的 CSV），沒有一個地方能一次 join。第三，**權限混亂**：為了讓分析師查資料，有人把含有會員電話與 email 的整張表匯出給外包廠商。

這一章要幫 Wanderly 建立一套分析平台：把所有資料匯集到 S3 上的 data lake，用 Glue 整理與編目，用 Athena 做臨時查詢，用 Redshift 支撐每天上千次的儀表板查詢，用 EMR 處理大型 Spark 工作，用 Lake Formation 控制誰能看到哪些欄位，最後用 QuickSight 把結果畫成圖表。我們會一路追問：每個元件解決了什麼問題？少了它會發生什麼事？要花多少錢？

## 30.2 為什麼分析需要另一套系統：OLTP、data warehouse 與 data lake

### 兩種完全不同的查詢

第 4 章介紹過，資料庫的工作負載大致分成兩類：

- **OLTP（Online Transaction Processing，線上交易處理）**：一次讀寫少量資料列，要求毫秒級回應與高併發。例如「建立一筆訂單」「查詢會員 12345 的最近三筆訂單」。RDS、Aurora、DynamoDB 都是為這種工作設計的。
- **OLAP（Online Analytical Processing，線上分析處理）**：一次掃描大量資料列，但通常只用到少數欄位，做加總、分組、排序。例如「過去兩年每個城市每週的訂單總金額」。回應時間可以是幾秒到幾分鐘，但資料量是 TB 甚至 PB 等級。

OLTP 資料庫通常是 **row-based（以列儲存）**：同一筆訂單的所有欄位存在磁碟上相鄰的位置，讀一筆完整訂單很快。可是 OLAP 查詢只要「城市」和「金額」兩個欄位，row-based 儲存卻得把每一列的二十個欄位全部讀進來，大部分 I/O 都浪費了。這就是小周的查詢慢的根本原因，而不是 Aurora 不夠大。

### Data warehouse：為分析而設計的資料庫

**Data warehouse（資料倉儲）** 是專門為分析查詢設計的資料庫。它有三個典型特徵：

1. **Columnar storage（欄式儲存）**：同一個欄位的值存在一起。查詢只用兩個欄位時，只讀兩個欄位的資料；同一欄的值型別相同、重複度高，也特別容易壓縮。
2. **MPP（Massively Parallel Processing，大規模平行處理）**：資料分散在多個運算節點，每個節點同時處理自己那一份，最後彙總結果。
3. **Schema-on-write（寫入時定義結構）**：資料進倉之前要先清洗、轉換成定義好的表格結構。好處是查詢者拿到的資料乾淨一致；代價是每接一個新資料來源都要先做 ETL。

AWS 的 data warehouse 是 **Amazon Redshift**（30.7 節）。

### Data lake：先把所有原始資料留下來

Data warehouse 很好用，但它有兩個限制：只適合結構化資料，而且「先定義 schema 才能寫入」讓新資料來源的接入速度很慢。點擊 log、旅館照片的 metadata、客服對話紀錄、第三方 CSV，格式各不相同，而且今天不知道明天會怎麼用。

**Data lake（資料湖）** 的做法是：**把所有原始資料以原本的格式、低成本地集中存放，等到要用時再決定怎麼解讀**，這稱為 **schema-on-read（讀取時套用結構）**。同一份原始點擊 log，行銷可以用來算轉換率，資料科學家可以拿來訓練推薦模型，兩者不必事先講好格式。

在 AWS 上，data lake 的儲存層幾乎都是 **S3**：容量無上限、11 個 9 的耐久性、按用量付費、可以用儲存類別與生命週期降低成本（第 23 章），而且幾乎所有 AWS 分析服務都能直接讀 S3。

> [!warning] 常見誤解
> 「Data lake 就是把檔案丟進 S3。」沒有目錄（catalog）、沒有權限治理、沒有品質控管的 data lake 很快就會變成 **data swamp（資料沼澤）**：沒有人知道哪個檔案是什麼、哪份是最新的、誰可以看。本章後半的 Glue Data Catalog 與 Lake Formation 就是為了避免這種情況。

### 為什麼 AWS 強調「儲存與運算分離」

傳統資料倉儲把資料和運算綁在同一組機器上：資料變多就得買更多機器，即使運算其實用不完。Data lake 架構把**資料放在 S3**，再讓**多種運算引擎讀同一份資料**：

| 運算引擎 | 適合 |
|---|---|
| Athena | 臨時、互動式 SQL，不想管任何伺服器 |
| Redshift（含 Spectrum） | 高併發、穩定低延遲的 BI 儀表板與複雜 join |
| EMR／Glue（Spark） | 大規模資料轉換、機器學習前處理 |
| QuickSight | 視覺化與報表 |

每個引擎可以獨立擴縮、獨立計費。這個概念也被稱為 **lake house（湖倉）** 架構：data lake 負責便宜、開放地存放所有資料，warehouse 負責高效能的結構化分析，兩者共用目錄與權限。

## 30.3 在 S3 上建 data lake：分層、分區與檔案格式

知道了為什麼要 data lake，下一個問題是：檔案要怎麼放？這個決定直接影響之後每一個查詢的速度與費用，而且一旦資料量變大就很難改。

### 分層：raw、curated、analytics

Wanderly 把 data lake bucket 切成三個區域（zone）：

| 區域 | 別名 | 內容 | 誰會寫 | 誰會讀 |
|---|---|---|---|---|
| `raw/` | bronze、landing | 原封不動的來源資料（JSON、CSV、資料庫匯出） | 擷取管線（Firehose、DMS、批次上傳） | 資料工程師、重新處理時 |
| `curated/` | silver、cleansed | 清洗、去重、型別正確、轉成 Parquet 並分區 | Glue／EMR ETL job | 分析師、Athena、Redshift Spectrum |
| `analytics/` | gold、consumption | 依業務需求彙總好的表（例如每日城市訂單彙總） | ETL job、Redshift UNLOAD | 儀表板、QuickSight |

為什麼要保留 raw？因為 ETL 程式一定會有 bug。保留原始資料，修好程式後就能重新產生 curated 層，不用回頭向來源系統要資料。Raw 層通常很少被讀，適合用 S3 lifecycle 轉到 Standard-IA 或 Glacier 類別（第 23 章）。

### 分區：讓查詢只讀需要的資料夾

**Partition（分區）** 是把資料依某個欄位的值放到不同的 S3 prefix（路徑）下，例如：

```text
s3://wanderly-lake/curated/clickstream/event_date=2026-09-28/region=apac/part-0001.parquet
s3://wanderly-lake/curated/clickstream/event_date=2026-09-28/region=eu/part-0001.parquet
s3://wanderly-lake/curated/clickstream/event_date=2026-09-29/region=apac/part-0001.parquet
```

`event_date=2026-09-28` 這種 `key=value` 寫法稱為 **Hive-style partition**，Athena、Glue、Spark、Redshift Spectrum 都認得。當查詢寫 `WHERE event_date = '2026-09-28'`，查詢引擎根本不會去列出、讀取其他日期的資料夾，這稱為 **partition pruning（分區裁剪）**。

選分區欄位的原則：

- 選**最常出現在 WHERE 條件**的欄位，通常是日期，其次是地區、租戶等低基數欄位。
- **不要選高基數欄位**（例如 user_id、order_id）：會產生上百萬個小資料夾，每個只有幾 KB，列出與開啟檔案的成本反而超過讀資料本身。
- 每個分區裡的檔案最好在數十 MB 到數百 MB 之間。大量小檔案（small files problem）是 data lake 最常見的效能殺手，要定期用 ETL job 合併（compaction）。

### 檔案格式：為什麼 Parquet 是預設答案

| 格式 | 類型 | 壓縮 | 只讀部分欄位 | 適合 |
|---|---|---|---|---|
| CSV | row、文字 | 可整檔 gzip | 不行 | 與外部交換、最原始的匯出 |
| JSON | row、文字 | 可整檔 gzip | 不行 | API log、半結構化原始資料 |
| Avro | row、二進位 | 支援 | 不行 | 串流、需要 schema 演進的寫入端 |
| **Parquet** | **columnar**、二進位 | 每欄獨立壓縮（Snappy、ZSTD、gzip） | **可以** | **分析查詢的預設選擇** |
| ORC | columnar、二進位 | 支援 | 可以 | Hive 生態系 |

**Apache Parquet** 是開放的 columnar 檔案格式。一個 Parquet 檔案內部把資料切成多個 row group，每個 row group 裡每個欄位各自存放、各自壓縮，還記錄了每段的最小值與最大值等統計資訊。查詢引擎因此能做到兩件事：

1. **Column pruning**：只讀查詢用到的欄位。
2. **Predicate pushdown**：根據統計資訊跳過「不可能符合條件」的區塊，例如某段 `amount` 最大值只有 500，查詢 `amount > 1000` 就整段跳過。

把 Wanderly 的點擊 log 從 gzip JSON 轉成 Snappy 壓縮的 Parquet 並按日期分區後，一個「查昨天、只用 5 個欄位」的查詢，掃描量從整個月的 JSON 降到一天裡 5 個欄位的資料，通常是幾十倍到上百倍的差距。在按掃描量計費的 Athena 上，這就是幾十倍的費用差距。

### Open table format：讓 S3 上的表也能更新與刪除

傳統 data lake 的檔案「只能新增、不能改」：要刪除一位會員的資料（例如個資法要求的刪除權），得重寫整個分區。**Open table format（開放表格式）** 在 Parquet 檔案之上加一層 metadata，記錄「這張表目前由哪些檔案組成」，因此能支援 ACID 交易、UPDATE／DELETE／MERGE、**time travel（查詢過去某個時間點的表）** 與 schema 演進。最常見的是 **Apache Iceberg**，另有 Apache Hudi 與 Delta Lake。

Athena、Glue、EMR、Redshift 都能讀寫 Iceberg 表。AWS 也推出了 **S3 Tables**：一種專門存 Iceberg 表的 table bucket，由 S3 自動做 compaction 等維護工作。考試若出現「data lake 中要支援資料列層級的更新、刪除與 time travel」，想到 Iceberg 類的 open table format。

到這裡，資料有了家，也有了好的格式。但 S3 只知道「有一堆 object」，並不知道 `curated/clickstream/` 是一張有 30 個欄位、按日期分區的表。下一節要解決的就是「讓查詢引擎知道資料長什麼樣子」。

## 30.4 AWS Glue：資料目錄、自動探索與 ETL

**AWS Glue** 是一組 serverless 的資料整合服務。它的名字就是「膠水」：把散落的資料黏成可以查詢、可以治理的資料集。Glue 包含好幾個元件，考試常把它們混在一起考，所以先分清楚：

| 元件 | 一句話 | 會不會動到資料本身 |
|---|---|---|
| Data Catalog | 存放「表的定義」的中央目錄 | 不會，只存 metadata |
| Crawler | 掃描資料、推斷 schema、自動建立或更新 catalog 表 | 不會 |
| ETL job | 執行 Spark 或 Python 程式，讀取、轉換、寫出資料 | 會 |
| DataBrew | 不寫程式的視覺化資料清理工具 | 會（輸出新資料集） |
| Data Quality | 定義並檢查資料品質規則 | 不會（產生檢查結果） |
| Workflows／triggers | 串接 crawler 與 job 的排程與相依性 | 不會 |

### Glue Data Catalog：所有引擎共用的「表格目錄」

**Glue Data Catalog** 是一個 Regional 的 metadata 儲存庫，結構是「database → table → partition」。每張 table 記錄：資料在哪個 S3 路徑、檔案格式、欄位名稱與型別、分區欄位、每個分區的位置。它相容於 Apache Hive metastore，所以 Athena、Redshift Spectrum、EMR、Glue job 都能直接使用同一份定義。

這帶來一個重要好處：**表只要定義一次，所有引擎看到的都是同一個結構**。Wanderly 的分析師在 Athena 查 `curated.clickstream`，資料工程師在 EMR 的 Spark 裡讀 `curated.clickstream`，兩邊不會因為各自維護 schema 而出現不一致。

### Crawler：自動探索 schema 與新分區

**Crawler（爬蟲）** 會連到指定的資料來源（S3 路徑、JDBC 資料庫、DynamoDB 等），用內建或自訂的 **classifier（分類器）** 判斷格式，推斷欄位與型別，然後在 Data Catalog 建立或更新表，並把新發現的分區加進去。可以排程執行（例如每小時），也可以由事件觸發。

> [!warning] 常見誤解
> Crawler **不會轉換資料**。它不會把 JSON 變成 Parquet、不會清洗或去重，只會更新 catalog 裡的 metadata。資料轉換是 ETL job 的工作。考試很喜歡出「用 crawler 把 CSV 轉成 Parquet」的錯誤選項。

當分區很多、而且分區值有規律（例如每天一個日期）時，每次都靠 crawler 或 `MSCK REPAIR TABLE` 加分區會變慢。Athena 的 **partition projection（分區投影）** 讓你在表屬性中直接描述分區的規則（例如 `event_date` 是從 2024-01-01 開始的每日日期），Athena 查詢時自行算出路徑，不必把每個分區登記在 catalog。

### ETL job：真正搬動與轉換資料

**ETL（Extract, Transform, Load，擷取、轉換、載入）** 是把資料從來源讀出、整理後寫到目的地的過程。**Glue ETL job** 是 serverless 的執行環境：

- 引擎主要是 **Apache Spark**（Python 或 Scala），適合大量資料；另有 **Python shell** 適合小型、單機的任務。也支援 **streaming ETL**，從 Kinesis 或 Kafka 持續讀取（第 31 章）。
- 運算量以 **DPU（Data Processing Unit）** 計費，按秒計費。不同的 **worker type**（如 G.1X、G.2X）代表每個 worker 的記憶體與運算大小。
- **Job bookmark（作業書籤）** 記錄上次處理到哪些檔案，下次只處理新進資料，避免每天重複處理整個歷史。
- **Glue Studio** 提供視覺化介面拖拉建立 job，背後產生 Spark 程式碼。
- **Flex execution** 使用閒置容量執行非急迫的 job，費用較低但啟動時間不保證，適合每晚的批次或測試。

Wanderly 每小時的 Glue job 做這些事：讀取 `raw/clickstream/` 的新 JSON（靠 bookmark），去掉重複事件、把時間字串轉成 timestamp、遮罩 IP 位址，寫成按 `event_date` 分區的 Parquet 到 `curated/`，最後更新 catalog。

### DataBrew：讓不寫程式的人也能清理資料

**AWS Glue DataBrew** 是視覺化的資料準備工具。分析師在類似試算表的介面上看到資料樣本，點選超過 250 種內建轉換（拆欄位、補缺值、標準化日期格式、偵測 PII），DataBrew 把這些步驟存成 **recipe（配方）**，再由 **job** 套用到整份資料。它也會產生 **data profile**，顯示每個欄位的缺值比例、分布與異常值。

選擇判斷很簡單：題目強調「分析師或業務人員、不寫程式、視覺化清理與正規化資料」→ DataBrew；強調「大規模、需要自訂程式邏輯、資料工程團隊」→ Glue ETL job（或 EMR）。

### Glue Data Quality 與 workflows

**Glue Data Quality** 讓你用規則語言（DQDL）描述「`order_id` 不能為空」「`amount` 必須大於 0」「今天的資料列數不能比昨天少一半以上」，在 ETL 流程中檢查，不合格就中止或告警，避免壞資料流進儀表板。

**Glue workflows** 與 **triggers** 可以把「crawler → job A → job B」串成有相依性的流程。若流程還牽涉其他服務（Lambda、EMR、人工核准），通常改用 Step Functions 編排（第 33 章），或用 Amazon Managed Workflows for Apache Airflow（MWAA）承接既有的 Airflow DAG。

資料已經有目錄、有乾淨的 Parquet 了，分析師終於可以開始查詢。最直接的方式，是完全不用管伺服器的 Athena。

## 30.5 Amazon Athena：直接對 S3 下 SQL

### Athena 怎麼運作

**Amazon Athena** 是 serverless 的互動式查詢服務：你寫標準 SQL，Athena 從 Glue Data Catalog 找到表的定義與 S3 位置，啟動一群分散式的查詢工作者平行讀取 S3 上的檔案，算出結果後把結果檔寫到你指定的 S3 路徑（query result location）。沒有 cluster 要建立、沒有容量要規劃，查完就結束。

```text
 分析師 / QuickSight / JDBC 應用程式
        │ ① SELECT city, SUM(amount) ... WHERE event_date >= '2026-09-01'
        ▼
 [Athena workgroup: analysts]  ── 套用每查詢掃描上限、結果加密設定
        │ ② 查 table 定義、分區位置
        ▼
 [Glue Data Catalog]  ── (若啟用 Lake Formation，在此檢查欄位/列權限)
        │ ③ 只列出 event_date >= 2026-09-01 的分區
        ▼
 [S3 curated/orders/event_date=.../*.parquet]
        │ ④ 平行讀取，只讀 city、amount 兩欄（columnar）
        ▼
 [Athena 分散式引擎] ── ⑤ 彙總
        │ ⑥ 結果寫到 s3://wanderly-athena-results/analysts/
        ▼
 回傳結果給呼叫端；帳單 = 本次掃描的資料量
```

① 呼叫端可以是 console、JDBC／ODBC driver、API 或 QuickSight。② Athena 不存資料，它依賴 Data Catalog 知道表在哪。③ partition pruning 讓不相關的日期完全不被讀取。④ Parquet 的 column pruning 讓 20 個欄位只讀 2 個。⑤⑥ 結果存成 S3 上的檔案，所以結果本身也要考慮加密與生命週期清理。

### 計費：按掃描量，所以檔案設計就是成本設計

Athena 的 SQL 查詢主要依**掃描的資料量**計費（多數 Region 為每 TB 數美元，每個查詢有 10 MB 的最小計費量）。DDL 語句（建立、修改表）與失敗的查詢不收費；被使用者取消的查詢則依取消前已掃描的量計費。這個計價方式有一個直接推論：

> 讓 Athena 便宜的方法，就是讓它少讀資料：**分區 + columnar 格式 + 壓縮 + 合併小檔案**。

一個常見誤解是加上 `LIMIT 10` 就會便宜。`LIMIT` 只限制回傳的列數，如果資料沒有分區、格式不是 columnar，引擎仍可能讀完大量資料才湊出那 10 列。

另外兩個省錢功能：**query result reuse**（相同查詢在指定時間內直接重用上次結果）以及 **CTAS（CREATE TABLE AS SELECT）**：把一個常用的大查詢結果直接寫成新的分區 Parquet 表，之後查詢新表即可。

若工作負載非常穩定、想要可預測的費用，Athena 也提供 **provisioned capacity**（以 DPU 預留查詢容量），但考試中 Athena 的典型特徵仍是「serverless、按掃描量付費、適合臨時查詢」。

### Workgroup：分團隊控管成本與設定

**Workgroup（工作群組）** 是 Athena 的隔離與治理單位。Wanderly 為財務、行銷、資料科學各建一個 workgroup：

- **強制 query result location 與加密**：可以設定「覆寫用戶端設定」，讓使用者無法把結果寫到別的 bucket，也確保結果用 SSE-KMS 加密（KMS 見第 15 章）。
- **Data usage controls**：設定**單一查詢掃描量上限**（超過就取消該查詢），以及**整個 workgroup 在一段時間內的掃描量門檻**（超過時觸發 CloudWatch 告警或 SNS 通知）。
- **分開的 CloudWatch 指標與查詢歷史**，搭配 cost allocation tag 讓帳單可以按團隊分攤。
- 用 IAM policy 限制使用者只能使用自己的 workgroup。

> [!tip] 考試提示
> 「某團隊的查詢偶爾掃描整個 data lake，要硬性阻止單一查詢超過 1 TB」→ Athena workgroup 的 per-query data usage control。AWS Budgets 只能事後通知，不能在查詢執行時中止它。

### Federated query：不搬資料也能 join

**Athena Federated Query** 透過部署在你帳號中的 Lambda 函數（**data source connector**）連到 S3 以外的資料來源，例如 DynamoDB、RDS／Aurora、Redshift、OpenSearch、CloudWatch Logs，甚至地端資料庫。一條 SQL 就能把 S3 上的點擊資料和 DynamoDB 裡的會員等級 join 在一起。

它適合「偶爾需要跨來源查詢、不想先建 ETL 管線」的情境。如果同樣的 join 每天要跑上千次，比較好的做法仍是把資料定期匯入 lake 或 warehouse，因為 federated query 每次都要從來源系統讀取，會增加來源的負載並受限於 connector 的效能。

### Athena 還能做什麼

- 查詢 **Iceberg** 表，支援 INSERT、UPDATE、DELETE、MERGE 與 time travel。
- 查詢 S3 server access logs、CloudTrail logs、VPC Flow Logs、ALB access logs：這是維運上非常常見的用法（第 36 章）。
- **Athena for Apache Spark**：在 Athena 的 notebook 介面中執行互動式 Spark，不必建 EMR cluster。

Athena 解決了「臨時查詢」的問題，但當行銷要求「200 位使用者的儀表板每 5 分鐘刷新、每個查詢要在 2 秒內回應」時，按查詢掃描的 serverless 模式就不一定是最佳選擇。這時要請出專門的 data warehouse。

## 30.6 Lake Formation：data lake 的權限中心

在介紹 Redshift 之前，先處理故事開頭的第三個問題：權限。Data lake 把所有資料集中在一起，也就把風險集中在一起。

### 只用 IAM 與 bucket policy 為什麼不夠

S3 的權限是以 **object 與 prefix** 為單位的。你可以讓分析師讀 `curated/orders/`，但無法表達「可以讀 orders 表，但看不到 `customer_phone` 欄位，而且只能看到 `country = 'TW'` 的資料列」。因為對 S3 來說，一個 Parquet 檔案就是一個 object，它不知道裡面有哪些欄位。

如果用 IAM 硬做，只能把同一份資料複製成很多版本（去掉敏感欄位的版本、只有台灣的版本……），每多一個需求就多一份複本與一條 ETL，很快就失控。

### Lake Formation 怎麼運作

**AWS Lake Formation** 在 Glue Data Catalog 之上提供集中的資料權限管理：

1. **Register（註冊）S3 location**：告訴 Lake Formation「`s3://wanderly-lake/curated/` 由你來管」，並指定一個 IAM role 讓 Lake Formation 代為存取該路徑。
2. **授權對象是 catalog 資源**：database、table、column，以及透過 **data filter** 定義的 row 與 cell 層級權限，用類似資料庫的 `GRANT SELECT ... ON TABLE ...` 方式授權給 IAM user、role、IAM Identity Center 的使用者或群組，或其他 AWS 帳號。
3. **查詢時檢查與 credential vending**：Athena、Redshift Spectrum、EMR、Glue 等整合服務查詢時，先向 Lake Formation 確認這個身份能看哪些欄位與資料列，Lake Formation 再發給查詢引擎一組**只能讀取對應 S3 路徑的暫時憑證**。查詢引擎依權限過濾結果，使用者本身完全不需要有 S3 讀取權限。

```text
 分析師 role（沒有任何 s3:GetObject 權限）
      │ SELECT * FROM curated.orders
      ▼
 [Athena] ──① 誰在查？要查什麼？──► [Lake Formation]
      ▲                               │ ② 檢查 grant：可讀 orders，排除 customer_phone，
      │                               │    data filter：country = 'TW'
      │ ③ 暫時 S3 憑證 + 允許欄位/列   │
      └───────────────────────────────┘
      │ ④ 用暫時憑證讀 S3（經由註冊時指定的 role）
      ▼
 [S3 curated/orders/] ── ⑤ 回傳過濾後的結果（看不到電話、只有台灣訂單）
```

① 整合服務把查詢者身份與目標表交給 Lake Formation。② 權限檢查發生在 catalog 層。③ Lake Formation 代發憑證。④ 讀 S3 的是 Lake Formation 授權的路徑，不是使用者自己的 IAM 權限。⑤ 使用者看到的是欄位與資料列都過濾後的結果。

> [!warning] 常見誤解
> 「設好 Lake Formation 的欄位權限，資料就安全了。」如果分析師的 IAM role 還保留 `s3:GetObject` 到 `curated/*` 的權限，他可以繞過 Athena，直接用 S3 API 下載整個 Parquet 檔，看到所有欄位。Lake Formation 只管「經由整合服務的查詢」，**導入時必須同時移除使用者直接存取 S3 的權限**。資料若用 SSE-KMS 加密，Lake Formation 註冊時使用的 role 也需要對應 KMS key 的解密權限。

### LF-Tags：用標籤管理上千張表

當表和團隊很多時，逐表授權會變成維護噩夢。**LF-Tags（Lake Formation tag-based access control，LF-TBAC）** 讓你先定義標籤，例如 `domain = orders | marketing`、`sensitivity = public | confidential | pii`，把標籤貼在 database、table 或 column 上，再授權「資料科學家可以讀所有 `sensitivity = public` 且 `domain = marketing` 的資源」。新建立的表只要貼上正確標籤就自動適用，不必重新授權。

### 跨帳號共享

Wanderly 在 Part 8 會變成多帳號架構，常見的設計是**集中式 data lake 帳號（producer）**，各業務帳號（consumer）來查詢。Lake Formation 的跨帳號共享是這樣做的：

- Producer 帳號在 Lake Formation 把 database／table（或 LF-Tag 表達式）授權給 consumer 帳號 ID、整個 Organization 或某個 OU。背後透過 **AWS RAM** 建立資源共享。
- Consumer 帳號的 data lake 管理員接受共享後，建立 **resource link**（指向共享表的捷徑），再把權限轉授給自己帳號內的 role。
- 資料留在 producer 的 S3 中，不需要複製；producer 隨時可以撤銷授權。

這也是 **data mesh（資料網格）** 的基礎：每個業務領域自己擁有並發布資料產品，中央平台提供目錄與權限機制。AWS 在這個方向還有 **Amazon DataZone**（以及整合進 SageMaker Unified Studio 的資料目錄功能），提供業務層的資料目錄、訂閱與核准流程；考試以 Lake Formation 的機制為主。

### Hybrid access mode

既有 data lake 導入 Lake Formation 時，不可能一次把所有使用者都切過去。**Hybrid access mode** 讓同一個 S3 location 可以同時被「既有 IAM／S3 policy 的使用者」與「已納入 Lake Formation 權限的使用者」存取，再逐步把使用者轉移過去。

## 30.7 Amazon Redshift：高效能的雲端資料倉儲

### 架構：leader node、compute nodes 與 managed storage

**Amazon Redshift** 是 AWS 的 columnar、MPP data warehouse，相容 PostgreSQL 的 SQL 方言與 JDBC／ODBC。Provisioned cluster 的結構是：

- **Leader node（領導節點）**：接收 SQL、產生查詢計畫、把工作分配給 compute nodes，最後彙總結果。
- **Compute nodes（運算節點）**：每個節點再分成多個 **slice**，各自處理一部分資料。

現在推薦的節點類型是 **RA3**：它把資料存在 **Redshift Managed Storage（RMS）**，底層是 S3，節點本地用 SSD 當快取。這代表**儲存和運算可以分開擴充**：資料長到 500 TB 不必買更多節點，查詢變多才需要更多運算。較舊的 DC2（本地 SSD、儲存與運算綁定）只適合資料量小（壓縮後約 1 TB 以下）且不太成長的情境，新設計通常以 RA3 或 Serverless 為主。

> [!note] 新節點類型 RG
> AWS 近年推出以 Graviton 處理器為基礎的 **RG** 節點，同樣使用 managed storage，官方文件目前建議依效能與資料量在 RG 與 RA3 之間選擇；RG cluster 以內建的 data lake 查詢引擎查 S3，而不是透過 Spectrum。考試題目仍以 RA3 為主，看到「儲存與運算分開擴充」就想到 managed storage 節點（RA3，或較新的 RG）。

### 讓查詢快的三個設計：distribution、sort key、materialized view

Redshift 是 MPP，**資料怎麼分散到各節點**決定了 join 時要不要在節點間搬資料：

| Distribution style | 做法 | 適合 |
|---|---|---|
| AUTO | Redshift 依表大小與使用情況自動選擇並調整 | 預設，多數情況的起點 |
| EVEN | 輪流平均分配 | 不參與 join 的表 |
| KEY | 依指定欄位的 hash 分配，相同 key 落在同一 slice | 大型 fact table 與 dimension 以同一欄位 join（co-locate） |
| ALL | 每個節點存一份完整複本 | 小型、少變動的 dimension table |

選 KEY 時要挑**高基數、分布平均**的欄位（例如 `customer_id`）。若用低基數欄位（例如只有 5 個值的 `country_code`），大部分資料擠在少數 slice，形成 **data skew（資料傾斜）**，整個查詢會等最慢的那個節點。

**Sort key（排序鍵）** 決定資料在磁碟上的排列順序。Redshift 為每個資料區塊記錄最小值與最大值（zone map），查詢 `WHERE event_time > 昨天` 時，若資料按 `event_time` 排序，就能跳過所有舊區塊。

**Materialized view（具體化檢視）** 預先算好並存放查詢結果，可以增量刷新，適合儀表板反覆執行的彙總查詢。

### 載入資料：COPY、zero-ETL 與串流

- **COPY 指令**：從 S3（或 DynamoDB、EMR）平行載入資料，是最標準的大量載入方式。把資料切成多個大小相近的檔案（數量為 slice 數的倍數）能讓所有 slice 同時工作。反過來，**UNLOAD** 把查詢結果平行匯出成 S3 上的 Parquet。
- **Zero-ETL integration**：從 Aurora MySQL／PostgreSQL、RDS for MySQL、DynamoDB 等來源，近即時地把交易資料複寫到 Redshift，不必自己建 DMS 或 ETL 管線。這正好解決故事開頭「分析查詢打在 Aurora 上」的問題：交易資料自動流進 Redshift，分析在 Redshift 上跑。
- **Streaming ingestion**：Redshift 可以直接從 Kinesis Data Streams 或 MSK 讀取資料到 materialized view（第 31 章）。
- **Federated query**：Redshift 也能直接查詢 RDS／Aurora 的 PostgreSQL 與 MySQL，適合少量即時參照資料。

### Redshift Spectrum：用 warehouse 查 data lake

**Redshift Spectrum** 讓 Redshift 透過 **external table（外部表）** 直接查詢 S3 上的資料，表的定義放在 Glue Data Catalog（以 external schema 對應）。查詢時，S3 的掃描由 Redshift 之外的 Spectrum 層執行，結果再送回 cluster 與本地表 join。

Wanderly 的用法是：最近 13 個月的訂單放在 Redshift 本地表，滿足高頻儀表板；更早的歷史資料留在 S3（便宜得多），偶爾需要做五年趨勢分析時，用 Spectrum 把兩邊 join 起來。Spectrum 按掃描量計費，所以 S3 上的資料同樣要分區、用 Parquet。

### 擴展：concurrency scaling、Serverless 與 WLM

**Concurrency scaling（併發擴展）**：當同時查詢太多、開始排隊時，Redshift 自動加開暫時的 cluster 處理查詢，尖峰過了就釋放。它處理讀取查詢，也支援常見的寫入（COPY、INSERT、UPDATE、DELETE、CTAS 等，限 RA3／RG 節點），在 WLM 佇列上把 concurrency scaling mode 設為 auto 即可啟用。每個 cluster 每天可累積約 1 小時的免費使用額度，超過的部分只在實際執行查詢時按秒計費。它解決的是「月底報表、週一早上大家同時開儀表板」這種**併發尖峰**，不是單一查詢太慢。

**WLM（Workload Management，工作負載管理）**：把查詢分到不同佇列與優先級，例如讓每小時的大型 ETL 不會擋住儀表板的短查詢。**Automatic WLM** 由 Redshift 自動分配記憶體與併發數，也可以設定 **query priority** 與 **query monitoring rules**（例如執行超過 30 分鐘的查詢自動中止）。

**Amazon Redshift Serverless**：不需要選節點類型與數量，以 **RPU（Redshift Processing Unit）** 表示運算容量，依實際查詢時間按秒計費，閒置時不收運算費用（儲存另計）。可以設定 base capacity 與 **max RPU-hours 的使用上限** 控制成本。適合使用量不穩定、間歇性、或團隊不想管理 cluster 的情境；全天候穩定高負載時，provisioned RA3 搭配 **reserved nodes（預留節點）** 通常更便宜。

### Data sharing：不複製資料的跨團隊共享

**Data sharing（資料共享）** 讓一個 Redshift（RA3 或 Serverless）作為 **producer**，把 schema、table、view 分享給其他 **consumer** cluster 或 workgroup，可跨帳號、跨 Region。Consumer 用自己的運算資源讀取 producer 的即時資料，**不需要複製或搬移資料**，producer 的效能也不受 consumer 查詢影響。

Wanderly 的設計：一個 ETL cluster（producer）負責載入與轉換，行銷與財務各自有一個 Serverless workgroup（consumer）讀取共享資料。這樣 ETL 負載、行銷的大量臨時查詢、財務的月結報表彼此隔離，各自付自己的運算費用。

### 可用性與備份

- **Automated snapshot**：增量備份到 S3，保留期間可設定（provisioned 預設 1 天，最長 35 天）；**manual snapshot** 保留到你刪除為止。
- **Cross-Region snapshot copy**：自動把 snapshot 複製到另一個 Region 作為 DR。加密的 cluster 要在目的 Region 設定可用的 KMS key（snapshot copy grant）。
- RA3 provisioned cluster 可以啟用 **Multi-AZ** 部署，在兩個 AZ 都有運算資源，一個 AZ 故障時自動接手。
- 單 AZ 的 cluster 在節點故障時會自動替換節點；整個 AZ 故障時可以從 snapshot 在其他 AZ 還原。

> [!note] Redshift 與第 29 章的關係
> 第 29 章把 Redshift 放在「purpose-built 資料庫」的選型地圖裡：它是分析型資料庫，不是 OLTP。本章則深入它的內部設計與擴展機制。看到「高併發 BI、複雜 join、PB 級結構化資料、SQL 分析」→ Redshift；看到「交易、毫秒級單筆讀寫」→ RDS／Aurora／DynamoDB。

Redshift 擅長 SQL；但有些工作不是 SQL 能優雅表達的，例如用 Spark 訓練推薦模型的特徵、處理數十 TB 的圖片 metadata、或是移植公司既有的 Hadoop 作業。這就是 EMR 的位置。

## 30.8 Amazon EMR：受管的 Spark 與 Hadoop

### EMR 是什麼

**Amazon EMR** 是受管的大數據平台，執行 Apache Spark、Hive、Presto／Trino、HBase、Flink 等開源框架。AWS 負責佈建與設定機器、安裝框架版本、整合 S3 與 IAM；你保有對框架參數、套件版本、程式碼的完整控制。

這也是 EMR 和 Glue 的主要差別：Glue 是「serverless、少設定、專注 ETL」，EMR 是「可以調整一切、支援整個 Hadoop 生態系」。題目若強調「既有 Hadoop／Spark 作業遷移、需要特定版本的開源元件、需要客製化 cluster 設定」，答案偏向 EMR。

### EMR on EC2 的節點角色

| 節點 | 角色 | 能不能用 Spot |
|---|---|---|
| Primary node（舊稱 master） | 管理 cluster、分派工作 | 不建議；遺失就失去整個 cluster（長期 cluster 可設定 3 個 primary node 做高可用） |
| Core node | 執行工作，並存放 HDFS 資料 | 謹慎使用；被回收會遺失 HDFS 上的資料區塊 |
| Task node | 只執行工作，不存 HDFS | **最適合 Spot** |

**EMRFS** 讓 EMR 直接把 S3 當作檔案系統讀寫。把資料放在 S3 而不是 HDFS，cluster 就可以是 **transient（暫時性）** 的：每晚啟動、處理完資料、寫回 S3、然後終止，只付處理時間的錢。只有需要極低延遲反覆讀寫中間資料的長期 cluster 才依賴 HDFS。

### 省錢關鍵：Spot 與 managed scaling

Spot Instance（第 17 章）可能被 AWS 以兩分鐘通知回收，但價格比 On-Demand 低很多。EMR 的典型省錢設計是：

- Primary node 與 core node 用 On-Demand（或 Reserved），維持 cluster 與 HDFS 穩定。
- **Task node 用 Spot**，而且使用 **instance fleets** 指定多種 instance type，降低某一種 type 容量不足的機率。Spark 的工作被回收時會在其他節點重試。
- **EMR managed scaling** 依工作負載自動增減節點。

### EMR on EKS 與 EMR Serverless

- **EMR on EKS**：把 Spark 作業跑在既有的 EKS cluster 上（第 21 章），讓分析和其他 container workload 共用運算資源與維運方式。
- **EMR Serverless**：指定 EMR 版本與應用程式類型（Spark 或 Hive），提交作業後自動配置與釋放資源，不必管理 cluster。適合「要用 EMR 的開源相容性，但不想管 cluster」的間歇作業。

| 需求 | 選擇 |
|---|---|
| 完全控制 cluster、長期運行、HBase 等需要常駐服務 | EMR on EC2 |
| 已經有 EKS 平台，想統一資源管理 | EMR on EKS |
| 間歇的 Spark／Hive 作業，不想管 cluster | EMR Serverless |
| Serverless ETL，與 Data Catalog、bookmark、DataBrew 緊密整合 | Glue ETL |

## 30.9 QuickSight：把資料變成儀表板

資料準備好、查詢引擎也就緒，最後一哩是讓業務人員看得懂。**Amazon QuickSight** 是 serverless 的 BI（Business Intelligence，商業智慧）服務，可以連接 Athena、Redshift、RDS、S3、第三方 SaaS 等資料來源，建立互動式儀表板。

需要記住的特性：

- **SPICE**（Super-fast, Parallel, In-memory Calculation Engine）：QuickSight 的記憶體內資料引擎。把資料集匯入 SPICE 後，儀表板查詢不必每次打到 Athena 或 Redshift，回應更快，也避免每次刷新都產生 Athena 掃描費用。SPICE 資料可以排程刷新。
- **Row-level security（RLS）**：依登入者顯示不同資料列，例如每家旅館的業務只看到自己負責的旅館。
- **Embedded analytics**：把儀表板嵌入自己的網站，例如 Wanderly 提供給合作旅館的「訂房表現」後台。
- 計費以使用者或讀者 session 為主，適合大量偶爾查看的讀者。
- 內建自然語言問答與 ML 洞察（如異常偵測、預測）。

> [!note] 名稱現況
> AWS 已把 QuickSight 演進為 AI 助理產品 **Amazon Quick**（推出時稱 Amazon Quick Suite）的一部分，BI 功能現在稱為 **Amazon Quick Sight**；既有的 QuickSight API 與整合不受影響。考試題目仍以「QuickSight 做 BI 視覺化」出題，本書沿用 QuickSight 這個名稱。

> [!tip] 考試提示
> 題目說「業務主管需要互動式儀表板、無伺服器、可嵌入應用程式、依使用者限制可見資料」→ QuickSight（加 RLS、embedding）。若題目說「儀表板刷新造成 Athena 費用很高」→ 把資料集匯入 SPICE 並排程刷新。

## 30.10 組起來：Wanderly 的分析平台

現在把所有元件組成完整架構：

```text
  資料來源                      擷取                    Data lake (S3)                    使用
 ┌──────────────┐                              ┌──────────────────────────┐
 │ Aurora 訂單   │──① zero-ETL ─────────────────────────────────────────────►┌─────────────┐
 │ DynamoDB 會員 │──② export to S3 ─────►│ raw/   (JSON, CSV)         │       │ Redshift    │
 │ 點擊事件      │──③ Firehose(第31章)──►│   │ ④ Glue job (Spark)     │       │ (RA3/       │
 │ 廣告平台 CSV  │──③ Transfer Family ──►│   ▼                        │       │  Serverless)│
 └──────────────┘                       │ curated/ (Parquet, 分區)   │◄─⑥───│  Spectrum   │
                                        │   │ ⑤ Glue job / EMR       │       └──────┬──────┘
                                        │   ▼                        │              │
                                        │ analytics/ (彙總表)         │              │
                                        └──────────────────────────┘              │
                                                ▲      ▲                           │
              [Glue Data Catalog + Lake Formation 權限] ⑦                          │
                                                │      │                           │
                                           [Athena]  [EMR / SageMaker]             │
                                                │                                  │
                                                └──────────► [QuickSight] ◄────────┘ ⑧
```

① 訂單資料用 zero-ETL 從 Aurora 近即時進入 Redshift，分析查詢不再打 Aurora。② DynamoDB 的會員資料用 export to S3（不消耗 table 的讀取容量，第 27 章）每日匯出到 raw 層。③ 點擊事件由 Data Firehose 寫入 raw（第 31 章），第三方 CSV 透過 Transfer Family（第 25 章）以 SFTP 上傳。④ Glue job 每小時把 raw 轉成分區 Parquet 寫入 curated。⑤ 再由 Glue 或 EMR 產生業務彙總表。⑥ Redshift 以 Spectrum 查詢 curated 層的歷史資料，與本地的近期訂單 join。⑦ 所有表的定義集中在 Glue Data Catalog，權限由 Lake Formation 統一控管，Athena、Redshift Spectrum、EMR 都遵守同一套欄位與資料列權限。⑧ QuickSight 從 Redshift 與 Athena（透過 SPICE）讀資料製作儀表板。

這個設計對應故事開頭的三個問題：分析與交易分離（①⑥）、資料集中可 join（②③④⑦）、權限集中而且到欄位層級（⑦）。

## 30.11 成本最佳化：分析平台的錢花在哪裡

分析平台的帳單通常由四個部分組成：S3 儲存、查詢掃描、ETL 運算、warehouse 運算。逐項來看：

| 成本來源 | 最佳化手段 |
|---|---|
| S3 儲存 | Raw 層用 lifecycle 轉 Standard-IA／Glacier Instant Retrieval 或更冷的類別；不確定存取模式時用 Intelligent-Tiering；Parquet 壓縮本身就能把儲存量降到原本的一小部分 |
| Athena／Spectrum 掃描 | 分區、Parquet + 壓縮、合併小檔案、partition projection、CTAS 預先彙總、query result reuse、workgroup 掃描上限 |
| Glue ETL | 用 job bookmark 只處理增量資料；非急迫 job 用 Flex execution；調整 worker 數量避免閒置 DPU |
| EMR | Transient cluster、task node 用 Spot、managed scaling；間歇作業改 EMR Serverless |
| Redshift | 穩定負載用 RA3 + reserved nodes；間歇負載用 Serverless 並設 max RPU-hours；冷資料移到 S3 用 Spectrum 查；provisioned cluster 在長時間不用時可以 pause |
| QuickSight | 高頻儀表板用 SPICE 避免重複查詢費用 |
| 資料傳輸 | 分析服務與 S3 放在同一 Region；跨 Region 複寫只複寫真正需要的資料 |

> [!example] 例子：同一個查詢的兩種帳單
> 小周的「每日城市訂單」查詢，在未分區的 gzip JSON 上每次掃描整整一年的 3 TB；轉成按日分區的 Parquet 後，查詢最近 7 天、只用 3 個欄位，掃描量降到數 GB。若儀表板一天刷新 100 次，再把結果匯入 SPICE 每小時刷新一次，查詢費用又少了一個數量級。

## 30.13 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| S3 上的資料、臨時 SQL 查詢、serverless、不想管基礎設施 | Athena |
| Athena 查詢慢又貴 | 轉 Parquet／ORC + 壓縮 + 分區 + 合併小檔案 |
| 限制某團隊單一查詢的掃描量、強制結果加密位置 | Athena workgroup |
| 自動探索 schema、發現新分區 | Glue crawler（不轉換資料） |
| Serverless ETL、只處理新資料 | Glue ETL job + job bookmark |
| 業務分析師視覺化清理資料、不寫程式 | Glue DataBrew |
| 欄位層級、資料列層級權限、集中治理 data lake | Lake Formation（data filter、LF-Tags） |
| 跨帳號共享 data lake、不複製資料 | Lake Formation cross-account + resource link |
| PB 級、高併發 BI、複雜 join、穩定低延遲 | Redshift |
| Redshift 查詢 S3 上的冷資料 | Redshift Spectrum |
| 儀表板在尖峰時段排隊 | Redshift concurrency scaling |
| 分析負載不穩定、不想管 cluster | Redshift Serverless |
| 多個 Redshift 之間共享即時資料、workload 隔離 | Redshift data sharing（RA3／Serverless） |
| Aurora 交易資料近即時進入分析、不建 ETL | Zero-ETL integration |
| 既有 Hadoop／Spark 遷移、需要控制框架版本 | EMR |
| EMR 降低成本 | Task node 用 Spot、transient cluster、managed scaling |
| 互動式儀表板、嵌入應用、依使用者限制資料 | QuickSight（SPICE、RLS、embedding） |
| Data lake 中要更新、刪除單筆資料、time travel | Apache Iceberg（Athena、Glue、EMR 都支援） |
| 跨 S3、DynamoDB、RDS 的 SQL join，不搬資料 | Athena Federated Query |

**常見陷阱**：

1. 以為 Glue crawler 會轉換格式：它只寫 metadata，轉換要用 ETL job。
2. 以為 `LIMIT` 能降低 Athena 費用：計費依掃描量，關鍵是分區與 columnar 格式。
3. 用高基數欄位（user_id、order_id）分區：會產生大量小檔案，反而更慢更貴。
4. 設好 Lake Formation 權限卻沒移除使用者直接讀 S3 的 IAM 權限：使用者可以繞過欄位限制。
5. 以為 concurrency scaling 能讓單一慢查詢變快：它處理的是併發排隊，單一查詢慢要看 distribution、sort key 與資料設計。
6. 把 EMR 的 core node 或 primary node 全部改成 Spot：被回收時會遺失 HDFS 資料或整個 cluster；Spot 應放在 task node。
7. 把 OLTP 交易放到 Redshift 或 Athena：它們是分析引擎，不適合高頻單筆寫入與毫秒級查詢。

## 30.14 SAP 加深：多帳號資料平台與既有平台現代化

### 集中式 vs 分散式（data mesh）

SAP 題目常見的情境是：「公司有 40 個帳號，每個業務單位都有自己的資料，要建立企業資料平台，同時符合各單位的資料所有權與合規要求。」兩種主要模型：

| 模型 | 做法 | 優點 | 代價 |
|---|---|---|---|
| 集中式 data lake | 所有資料複製到一個 data lake 帳號，中央團隊治理 | 治理簡單、一致 | 中央團隊成為瓶頸；資料所有權模糊 |
| Data mesh | 各領域帳號保有自己的 S3 與 catalog，透過中央 governance 帳號的 Lake Formation 發布與訂閱 | 領域自主、資料不必搬家 | 需要一致的標籤規範與帳號間權限設計 |

實務上常見混合：中央 governance 帳號定義 LF-Tags 標準與註冊目錄，各 producer 帳號保有資料並在 Lake Formation 授權，consumer 帳號透過 resource link 查詢。加密資料共享時，別忘了 KMS key policy 也要允許 consumer 端的存取路徑（第 15 章）。

### 既有平台現代化

- **地端 Hadoop 遷移**：HDFS 資料搬到 S3（DataSync 或 Snow，第 25 章），作業改跑在 EMR，並把常駐 cluster 改成 transient cluster + Spot，是典型的 replatform（第 44 章）。
- **地端資料倉儲（Teradata、Oracle、Netezza）遷移到 Redshift**：用 AWS SCT 轉換 schema 與程式，搭配 DMS 或 SCT data extraction agent 搬資料（第 45 章）。
- **把在 OLTP 上跑的報表搬走**：zero-ETL 是最低營運負擔的選擇；若來源不支援 zero-ETL，用 DMS 的 CDC 持續複寫到 S3 或 Redshift。
- **治理要求**：Lake Formation 的 grant 與資料存取都會記錄到 CloudTrail，可以提供稽核證據；搭配 Amazon Macie 掃描 S3 中的 PII（第 16 章），把發現的敏感欄位標上 `sensitivity = pii` 的 LF-Tag。

### 分析平台的 DR

- S3 data lake：用 S3 Cross-Region Replication 複寫 curated 與 analytics 層（raw 層視法規與重建成本決定），Glue Data Catalog 的定義用 IaC 在兩個 Region 都部署。
- Redshift：cross-Region snapshot copy（RPO 取決於 snapshot 頻率），或在第二個 Region 以 data sharing／重新載入維持一份可用的 warehouse。
- 第 34 章會把這些放進完整的 DR 策略比較。

## 本章重點整理

- OLTP 資料庫是 row-based、為少量資料列的高頻讀寫設計；分析查詢應該移到 columnar、MPP 的 data warehouse 或 data lake，避免和交易搶資源。
- Data warehouse 是 schema-on-write，適合結構化、高效能 SQL；data lake 是 schema-on-read，以 S3 低成本保存所有原始資料，多個運算引擎共用同一份資料。
- Data lake 依 raw、curated、analytics 分層；保留 raw 讓 ETL 有 bug 時可以重新處理。
- 分區選常用於過濾的低基數欄位（通常是日期），避免高基數欄位與大量小檔案；Parquet 的 column pruning 與 predicate pushdown 能大幅減少掃描量。
- Glue Data Catalog 是 Athena、Spectrum、EMR、Glue 共用的 metadata 目錄；crawler 只探索 schema 與分區，不轉換資料；ETL job 才會讀寫並轉換資料，job bookmark 讓 job 只處理新資料。
- DataBrew 給不寫程式的分析師做視覺化資料清理；大型、需自訂邏輯的轉換用 Glue ETL 或 EMR。
- Athena 是 serverless SQL on S3，按掃描量計費，`LIMIT` 不會降低費用；workgroup 可強制結果位置與加密，並設定單一查詢掃描上限。
- Athena Federated Query 透過 Lambda connector 查詢 S3 以外的來源，適合偶爾的跨來源 join。
- Lake Formation 提供表、欄位、資料列與 cell 層級權限，用 LF-Tags 管理大規模授權，透過 RAM 與 resource link 跨帳號共享；導入時必須移除使用者直接讀 S3 的權限。
- Redshift RA3 讓儲存（managed storage）與運算分開擴充；distribution style 與 sort key 決定 join 與掃描效率，低基數 distribution key 會造成資料傾斜。
- Redshift Spectrum 查 S3 外部表；concurrency scaling 處理併發尖峰；Serverless 以 RPU 計費、適合間歇負載；data sharing 讓多個 cluster 不複製資料共享即時資料。
- Zero-ETL integration 把 Aurora、RDS、DynamoDB 的交易資料近即時送進 Redshift，是讓分析離開 OLTP 的最低營運負擔做法。
- EMR 提供完整的 Spark／Hadoop 控制；省錢用 S3 + transient cluster、task node 用 Spot、managed scaling；不想管 cluster 用 EMR Serverless。
- QuickSight 是 serverless BI，SPICE 加速並減少底層查詢費用，RLS 依使用者限制資料，可嵌入應用程式。
- Open table format（Apache Iceberg）讓 S3 上的表支援 ACID、更新刪除與 time travel。

## 本章練習題

### 練習 30-1｜SAA｜單選｜分析查詢與 OLTP 分離

Wanderly 的分析師每天在 Aurora MySQL 的 read replica 上執行數十個彙總兩年訂單資料的查詢，每次需要數十分鐘，並讓同一個 replica 上的會員中心讀取變慢。訂單資料需要在交易發生後幾分鐘內可供分析。團隊希望分析查詢不再影響線上系統，並把維運工作降到最低。

最合適的做法是什麼？

- A. 再新增兩個 Aurora Replica，並建立 custom endpoint 讓分析師只連到這兩個 replica
- B. 建立 Aurora 到 Amazon Redshift 的 zero-ETL integration，讓分析師在 Redshift 上查詢
- C. 每天晚上用 mysqldump 匯出訂單表到 S3，再用 Athena 查詢 CSV 檔
- D. 把 Aurora 的 instance class 升級到最大規格，並為分析查詢開啟 query cache

> [!answer]- 答案：B
> **A ✗** Custom endpoint 能把分析流量隔離到專用 replica，確實可以保護會員中心，題目若只要求隔離這是可行做法。但 Aurora 仍是 row-based 的 OLTP 引擎，兩年資料的大型彙總依然很慢，也沒有解決分析效能問題。
>
> **B ✓** Zero-ETL integration 把 Aurora 的交易資料近即時複寫到 Redshift，不需要自己建 ETL 管線。分析查詢改在 columnar、MPP 的 Redshift 上執行，既不影響線上系統，也大幅提升彙總效能。
>
> **C ✗** 每晚匯出只能提供前一天的資料，不符合「幾分鐘內可分析」；CSV 也是 row-based 文字格式，Athena 掃描量大、費用高，還要自己維護匯出腳本。
>
> **D ✗** 單純放大 instance 只是延後問題，分析與交易仍在同一個 row-based 引擎上競爭資源；成本也顯著增加。
>
> **考點**：SAA-3.3、SAA-3.5｜OLTP 與分析分離、zero-ETL integration

### 練習 30-2｜SAA｜單選｜降低 Athena 掃描量

Wanderly 的點擊紀錄以 gzip 壓縮的 JSON 存在 S3，每天約 200 GB，全部放在同一個 prefix 下，裡面有數百萬個小檔案。幾乎所有 Athena 查詢都只用 6 個欄位，並且以 `event_date` 過濾最近 7 天。查詢又慢又貴。

哪個做法對降低成本與提升效能最有效？

- A. 在所有查詢加上 `LIMIT 1000`，並把 Athena 結果保存期限縮短為 1 天
- B. 把所有 JSON 合併成單一未壓縮的大型 CSV 檔，減少 Athena 開檔次數
- C. 用 Glue ETL job 把資料轉成 Snappy 壓縮的 Parquet，以 `event_date` 分區並合併成較大的檔案
- D. 把 Glue crawler 的執行頻率提高到每 10 分鐘一次，讓 catalog 統計資訊保持最新

> [!answer]- 答案：C
> **A ✗** `LIMIT` 只限制回傳列數，資料沒有分區、也不是 columnar 格式時，Athena 仍會掃描大量資料；結果保存期限與掃描費用無關。
>
> **B ✗** 單一大檔解決了小檔案問題，但未壓縮的 CSV 讓讀取量更大，也無法只讀需要的欄位或利用分區裁剪。
>
> **C ✓** Parquet 讓 Athena 只讀 6 個需要的欄位（column pruning），壓縮再減少位元組；按 `event_date` 分區讓查詢只讀最近 7 天的資料夾；合併小檔案降低列出與開檔的開銷。三者一起是 Athena 成本最佳化的標準答案。
>
> **D ✗** Crawler 只更新 metadata 與分區，不會改變資料格式或檔案大小，掃描量不會減少。
>
> **考點**：SAA-4.3、SAA-3.5｜Athena 按掃描量計費、分區與 columnar 格式

### 練習 30-5｜SAA｜選兩項｜Data lake 檔案設計

Wanderly 正在為訂單事件設計 data lake 的 curated 層。查詢模式是：九成的查詢以 `order_date` 過濾一週內的資料，偶爾按 `country` 過濾；每天約有 3 億筆事件、2,000 萬名不同會員。團隊希望 Athena 與 Redshift Spectrum 的查詢又快又便宜。

- B. 以 `member_id` 作為分區欄位，讓查詢單一會員時只讀一個資料夾

- D. 讓串流管線每秒寫出一個檔案，確保每個檔案都很小、查詢時能平行讀取
- E. 以壓縮的 Parquet 保存，並由 ETL job 定期把每個分區的檔案合併到數十 MB 以上

>
> **D ✗** 大量小檔案是 data lake 最常見的效能問題，每個檔案都有列出與開啟的固定開銷，平行度並不會因此變好。
>
> **E ✓** 壓縮的 Parquet 支援 column pruning 與 predicate pushdown；把小檔案合併成較大的檔案，減少固定開銷。
>
> **考點**：SAA-3.5、SAA-4.1｜分區設計、columnar 格式與小檔案問題

### 練習 30-8｜SAA｜單選｜EMR 成本最佳化

> **C ✓** Lake Formation 的模式是：使用者沒有直接讀 S3 的權限，查詢時由 Lake Formation 驗證欄位權限並代發暫時憑證給 Athena。移除分析師的 S3 與 KMS 直接權限後，繞過路徑就被堵住；註冊用的 role 必須能讀 S3 並使用 KMS key，查詢才會成功。
>
> **D ✗** 連註冊用的 role 一起拒絕，Lake Formation 也無法讀取資料，Athena 查詢會全部失敗。
>
> **考點**：SAP-2.3、SAP-3.2｜Lake Formation 權限模型與直接 S3 存取

### 練習 30-12｜SAP｜選兩項｜跨帳號 data lake 共享

Wanderly 採用多帳號架構，data lake 集中在 data-platform 帳號。行銷帳號與客服帳號的分析師要查詢部分表；未來會新增數百張表，資安團隊要求依資料敏感度分類授權，新表依分類自動適用，且資料不得複製到 consumer 帳號，producer 必須能集中撤銷存取。

哪兩個做法最合適？（選兩項）

- A. 在 data-platform 帳號的 S3 bucket policy 中逐一允許行銷與客服帳號所有 role 的 `s3:GetObject`
- B. 在 data-platform 帳號定義 LF-Tags（例如 domain、sensitivity），標記 database、table 與 column，並以 LF-Tag 表達式授權給行銷與客服帳號
- C. 每天用 S3 Cross-Region Replication 把表的資料複製到行銷與客服帳號的 bucket
- D. Consumer 帳號的 data lake 管理員接受透過 AWS RAM 的共享，建立指向共享資源的 resource link，再把權限授予自己帳號內的分析師 role
- E. 把 Glue Data Catalog 的表定義匯出成 JSON，在 consumer 帳號重新建立相同的表並指向 producer 的 S3 路徑

> [!answer]- 答案：B、D
> **A ✗** Bucket policy 只能控制 object 與 prefix 層級，無法依欄位或敏感度授權，還會建立繞過 Lake Formation 的直接存取路徑。
>
> **B ✓** LF-Tags 讓授權依標籤表達，新表只要貼上正確標籤就自動適用，適合數百張表的規模；可以直接授權給其他帳號，producer 撤銷 grant 即可收回存取。
>
> **C ✗** 複製資料違反「不得複製」的限制，也讓撤銷變得困難。
>
> **D ✓** 跨帳號共享透過 AWS RAM 完成。Consumer 帳號建立 resource link 後，在自己的 Athena 中就能看到共享表，並可把權限轉授給帳號內的 role。資料仍留在 producer。
>
> **E ✗** 在 consumer 帳號重建表定義時，consumer 需要直接讀 producer S3 的權限，等於繞過 Lake Formation 的集中治理，也無法依欄位控制。
>
> **考點**：SAP-1.4、SAP-2.3｜Lake Formation LF-Tags 與跨帳號共享

### 練習 30-13｜SAP｜單選｜Redshift workload 隔離

Wanderly 有一個 Redshift RA3 cluster，同時承擔每小時的 ETL、行銷團隊大量且不可預測的臨時查詢，以及財務的月結報表。行銷的大查詢經常拖慢 ETL，導致儀表板資料延遲。三個團隊的費用也需要分開計算。公司要求所有團隊看到的是同一份即時資料，不能維護多份複本。

最合適的做法是什麼？

- A. 保留現有 cluster 作為 producer 負責 ETL，透過 Redshift data sharing 把資料共享給行銷與財務各自的 Redshift Serverless workgroup，讓各團隊用自己的運算資源查詢
- B. 每晚把現有 cluster 的 snapshot 還原成行銷與財務專用的 cluster
- C. 在現有 cluster 中為三個團隊設定 WLM 佇列，並把 cluster 節點數加倍
- D. 用 UNLOAD 每小時把所有表匯出到 S3，讓行銷與財務改用 Athena 查詢

> [!answer]- 答案：A
> **A ✓** Data sharing 讓 consumer 直接讀取 producer 的即時資料而不複製，每個 consumer 使用自己的運算資源，因此行銷的大查詢不會影響 producer 上的 ETL。Serverless workgroup 適合行銷不可預測的負載，費用也自然按 workgroup 分開。
>
> **B ✗** Snapshot 還原產生的是複本，資料最晚落後一天，違反「同一份即時資料、不維護複本」。
>
> **C ✗** WLM 能在同一個 cluster 內分配優先級，對輕度競爭是合理的第一步；但所有團隊仍共用同一組運算資源，加倍節點又提高成本，也無法自然分開費用。
>
> **D ✗** 每小時匯出產生 S3 上的複本，資料有延遲，還要維護匯出與 Athena 表定義。
>
> **考點**：SAP-2.5、SAP-2.6｜Redshift data sharing 與 workload 隔離

### 練習 30-14｜SAP｜單選｜從 OLTP 卸載分析的現代化

Wanderly 併購的旅行社在 Aurora PostgreSQL 上執行訂單系統，夜間有數十個報表程式直接查詢正式資料庫，已經多次導致夜間批次訂單處理逾時。新的業務需求要求報表資料延遲不超過 15 分鐘，並與 Wanderly 既有 Redshift 中的資料 join。公司希望最少的自建元件與營運負擔，且不能修改訂單系統的程式碼。

最合適的做法是什麼？

- A. 在 Aurora 新增一個 Aurora Replica，把報表程式改連 reader endpoint
- B. 部署 DMS 複寫執行個體，以 full load + CDC 把資料寫入 S3，再用 Glue job 每 15 分鐘載入 Redshift
- C. 在訂單系統中加入程式，每次交易完成時同時寫一份到 Kinesis Data Streams，再由 Firehose 載入 Redshift
- D. 建立 Aurora PostgreSQL 到 Redshift 的 zero-ETL integration，把報表遷移到 Redshift 並與既有資料 join

> [!answer]- 答案：D
> **A ✗** Reader 可以讓報表不再打 writer，但報表仍在 row-based 的 OLTP 引擎上執行，也無法與 Redshift 中的資料直接 join。
>
> **B ✗** DMS + Glue 能達成需求，在來源不支援 zero-ETL 時是合理做法；但需要自行管理複寫執行個體、ETL job 與排程，營運負擔明顯較高。
>
> **C ✗** 題目明確禁止修改訂單系統程式碼，且雙寫還會帶來一致性問題。
>
> **D ✓** Zero-ETL integration 以近即時方式把 Aurora PostgreSQL 的資料複寫到 Redshift，不需要自建管線，也不改應用程式。報表搬到 Redshift 後可直接與既有資料 join，正式資料庫不再承擔分析負載。
>
> **考點**：SAP-4.4、SAP-3.3｜zero-ETL integration 卸載 OLTP 分析負載

### 練習 30-15｜SAP｜單選｜跨來源的偶發查詢

Wanderly 的詐欺調查小組每個月需要執行數次查詢，把 S3 data lake 中的訂單事件、DynamoDB 中的會員風險分數，以及 RDS for MySQL 中的退款紀錄 join 在一起。查詢頻率低、內容每次不同。公司希望不要為此建立新的 ETL 管線或複製資料，並盡量降低營運負擔。

最合適的做法是什麼？

- A. 建立 Glue ETL job，每小時把 DynamoDB 與 RDS 的資料全量匯出到 S3，再用 Athena 查詢
- B. 建立 EMR cluster 常駐運行，透過 Spark 連接三個資料來源
- C. 使用 Athena Federated Query，在帳號中部署 DynamoDB 與 MySQL 的 data source connector（Lambda），用一個 SQL 查詢 join 三個來源
- D. 把 DynamoDB 與 RDS 的資料用 zero-ETL 複寫到 Redshift，並把 S3 訂單事件也載入 Redshift

> [!answer]- 答案：C
> **A ✗** 每小時全量匯出建立了新管線並複製資料，對每月數次的查詢來說成本與維運負擔都過高。
>
> **B ✗** 常駐 EMR cluster 大部分時間閒置，且需要自行管理 cluster 與連線程式。
>
> **C ✓** Federated query 透過 Lambda connector 直接讀取 DynamoDB 與 MySQL，與 S3 上的表在同一個 SQL 中 join，不需要建管線或複製資料，按使用量計費，適合偶發的跨來源查詢。若同樣的查詢每天執行上千次，則應改為把資料匯入 lake 或 warehouse。
>
> **D ✗** 對高頻分析是好方向，但需要建立整合並把資料複製到 Redshift，違反「不複製資料」，對低頻查詢也過度投資。
>
> **考點**：SAP-2.5、SAP-2.6｜Athena Federated Query 的使用時機

### 練習 30-16｜SAP｜選兩項｜分析平台成本檢討

Wanderly 的分析平台年度成本檢討發現：(1) Redshift provisioned cluster 只在台灣時間白天被使用，夜間與週末幾乎沒有查詢，而且每天的負載量差異很大；(2) raw 層 S3 資料有 800 TB，超過 90 天的資料幾乎沒人讀，但法規要求保留 7 年，偶爾需要在數小時內取回供稽核；(3) Glue job 運作正常。公司希望在不影響白天使用體驗的前提下降低成本，並降低營運負擔。

哪兩個做法最合適？（選兩項）

- A. 為 Redshift provisioned cluster 購買三年期 reserved nodes，維持全天候運行
- B. 把 Redshift 工作負載遷移到 Redshift Serverless，設定合適的 base capacity 與 max RPU-hours 上限，閒置時不產生運算費用
- C. 把 raw 層全部改為 S3 One Zone-IA，以降低儲存單價
- D. 為 raw 層設定 S3 lifecycle rule，超過 90 天的物件轉移到 S3 Glacier Flexible Retrieval，並在 7 年後到期刪除
- E. 刪除超過 90 天的 raw 資料，改由 curated 層的 Parquet 作為法規保存資料

> [!answer]- 答案：B、D
> **A ✗** Reserved nodes 適合全天候穩定負載。這個 cluster 夜間與週末閒置、負載波動大，預留容量仍會為大量閒置時間付費。
>
> **B ✓** Redshift Serverless 依實際查詢時間以 RPU 計費，閒置時不收運算費用，自動依負載調整容量；max RPU-hours 上限避免費用失控，也省去管理 cluster 的工作。
>
> **C ✗** One Zone-IA 只存放在一個 AZ，AZ 故障時資料可能遺失，不適合法規要求保留 7 年的資料，對「幾乎不讀」的資料也不是最便宜的類別。
>
> **D ✓** Lifecycle rule 自動把冷資料轉到 Glacier Flexible Retrieval，儲存單價大幅降低，取回時間為分鐘到數小時，符合「數小時內取回」的稽核需求；expiration 規則在保存期滿後自動刪除。
>
> **E ✗** 法規要求保存原始資料時，經過轉換的 curated 資料通常不能取代；刪除 raw 也失去 ETL 修正後重新處理的能力。
>
> **考點**：SAP-2.6、SAP-3.5｜Redshift Serverless 與 S3 lifecycle 成本最佳化
