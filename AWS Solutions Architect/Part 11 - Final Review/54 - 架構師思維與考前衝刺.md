# 第 54 章　架構師思維：12 個通用模式與考前衝刺

> [!abstract] 本章地圖
> **你會學到**：

>

## 54.1 故事：Wanderly 的年度架構回顧

Wanderly 成立第五年，阿哲已經從當年那個「一個月內要把網站放上 AWS」的後端工程師，變成帶領平台團隊的首席架構師。公司現在有六十多個 AWS 帳號、兩個 Region、一個 AI 旅遊助理，還有一個剛搬遷完畢的舊資料中心。每年年底，阿哲都會主持一次架構回顧，把這一年的事故報告、帳單與設計決策攤開來看。

今年的新成員小米剛加入團隊，準備考 SAA。她翻著一疊事故報告問：「AWS 有兩百多個服務，每個都有幾十個設定，要怎麼記得住？」阿哲把五年來最痛的幾次事故寫在白板上：資料庫被 Internet 掃到、唯一的 NAT Gateway 跟著 AZ 一起倒、促銷時訂單 API 把資料庫壓垮、快取裡的庫存數字讓同一間房被賣了兩次、一次錯誤部署讓所有客戶同時當機、帳單上 NAT 處理費比 EC2 還貴……

然後他在每一條旁邊寫一個詞：網路分層、消除單點、queue 削峰、cache 不是真相、縮小影響範圍、成本是限制。再把五年來其他事故也一一歸類，最後白板上只剩十二個詞。「服務會改名、會出新功能，但這些問題和解法的形狀幾乎不變。你記住這十二個形狀，再把服務名稱放進去，考試和工作都會簡單很多。」

這一章就是那面白板。前半章逐一整理 12 個通用模式，每個模式都指回本書詳細講解的章節；後半章談怎麼把這些模式帶進考場：SAA 到 SAP 的心態轉換、考前一週清單與作答策略。

## 54.2 架構師思維：先找限制，再找模式，最後才找服務

新手看到架構題，第一反應通常是「這題在考哪個服務」。架構師的順序剛好相反：先找出題目裡的**限制**（必須成立的條件，例如 RPO 5 分鐘、不能改程式、資料不能離開某個 Region），再判斷這些限制屬於哪一類問題，最後才挑能落實它的服務。

**設計模式（design pattern）** 在這裡指的是「一類反覆出現的問題，加上一個已被證明有效的解法形狀」。它和服務名稱無關：「用 queue 吸收突波」在 AWS 上可以是 SQS 或 Kinesis，在別的雲上是別的名字，但它解決的問題（生產速度暫時大於消費速度）與它的極限（長期超載時 queue 只會越積越多）都一樣。

```text
  題目情境
     │ ① 圈出限制與最佳化目標
     ▼
 ┌───────────────────────────────┐
 │ 限制：RPO、RTO、合規、不能改程式 │
 │ 目標：MOST cost-effective、      │
 │       LEAST operational overhead │
 └──────────────┬────────────────┘
                │ ② 這是哪一類問題？
                ▼
 ┌───────────────────────────────┐
 │ 12 個模式之一（或兩三個的組合）  │
 │ 例：突波 → 模式 5；AZ 故障 → 模式 3│
 └──────────────┬────────────────┘
                │ ③ 把服務名稱放回來
                ▼
 ┌───────────────────────────────┐
 │ AWS 實作：SQS + ASG 依 backlog  │
 │ 擴展；Multi-AZ；gateway endpoint│
 └──────────────┬────────────────┘
                │ ④ 用目標比較剩下的選項
                ▼
            選出答案
```

① 第 1 章的四步驟讀題法在這裡變成第一步：限制是「刪掉不合格選項」的依據，最佳化目標是「在合格選項中挑最好的」依據。② 把限制歸類到模式，可以讓你在還沒看選項之前就預測答案的形狀，例如看到「突然湧入、後端處理不了」就預期答案裡會有 queue。③ 到這一步才需要服務知識：同樣是 queue，要嚴格順序就是 SQS FIFO 或 Kinesis，要多個消費者各自收到一份就是 SNS fan-out 或 EventBridge。④ 最後如果有兩個選項都符合限制，就用最佳化目標決勝負。

接下來的 12 個模式，每個都用同樣的四段整理：**問題**（它在解決什麼痛點）、**原理**（為什麼這樣做有效、極限在哪）、**AWS 實作**（常見服務組合與相關章節）、**考試訊號**（題目出現什麼字就該想到它）。我們依照系統生命週期把它們分成四組：建得穩、壞得小、守得住與看得見、付得起與搬得動。

## 54.3 建得穩：模式 1–3

第一組模式回答的問題是「系統平常要怎麼搭，才不會一碰就倒」。它們也是 SAA 出現頻率最高的三個模式。

### 模式 1：Managed service 優先，但保留 escape hatch

**問題**：自己在 EC2 上架 MySQL、Kafka 或 Redis，可以完全掌控每個參數，但同時也接下了作業系統 patch、版本升級、備份、failover、容量規劃與半夜被叫起來的責任。對 Wanderly 這種十幾人的團隊，這些工作會吃掉本來該拿來做產品的時間。

**原理**：**managed service（受管服務）** 把「無差別的繁重工作」移到 AWS 那一側的責任分擔線（第 2 章）。你付出的代價是控制權：不能登入作業系統、某些參數不能調、某些版本或擴充套件不支援。因此這個模式的完整說法是「預設用 managed service，只有在明確的需求做不到時，才退到自管」。這個退路叫 **escape hatch（逃生口）**：例如 RDS 不允許作業系統層級存取，但 Oracle 或 SQL Server 的第三方代理程式需要時，可以用 **RDS Custom**；還是不行，才回到 EC2 自管。

**AWS 實作**：資料庫用 RDS／Aurora 而不是 EC2 上的資料庫（第 26 章）；key-value 存取用 DynamoDB（第 27 章）；container 用 ECS／EKS 搭配 Fargate，不必管節點（第 21 章）；訊息用 SQS、SNS、EventBridge 或 Amazon MQ，而不是自己架 broker（第 32 章）；串流用 Kinesis 或 MSK（第 31 章）。第 46 章談現代化時，把「從 EC2 自管換成 managed service」列為最常見的改善手段。

**考試訊號**：`LEAST operational overhead`、`minimize management`、「團隊沒有資料庫管理員」、「不想管理伺服器」。看到這些字，自管 EC2 的選項幾乎都是錯的，除非題目同時說了 managed service 做不到的限制，例如「需要作業系統層級存取」「需要特定 kernel module」「授權綁定實體核心」（第 17 章的 Dedicated Hosts）。

> [!warning] 常見誤解
> 「Managed service 一定比較貴。」只看帳單上的單價常常如此，但把人力、停機風險與 patch 延遲算進去，總成本通常反而較低。SAA 題目寫 `MOST cost-effective` 時，若選項之間差在「自管 vs 受管」，要看題目有沒有提到營運人力；SAP 題目則常把總持有成本（TCO，第 44 章）當作明示的比較基準。

### 模式 2：解耦，讓元件可以各自擴展與各自失敗

**問題**：Wanderly 早期的訂房流程是一條同步呼叫鏈：網站呼叫訂單服務，訂單服務呼叫付款，付款呼叫寄信。只要寄信服務變慢，使用者就卡在「處理中」；只要付款服務掛掉，整個訂房就失敗。最慢的元件決定了整條鏈的速度，最脆弱的元件決定了整條鏈的可用性。

**原理**：**解耦（decoupling）** 是讓兩個元件不必同時在線、不必用同樣速度運作（第 4 章）。中間放一個可靠的緩衝（queue、topic、event bus 或 workflow），生產者只要把工作交出去就算完成，消費者用自己的步調處理。代價是系統變成**最終一致（eventually consistent）**：使用者按下「訂房」後，確認信可能幾秒後才到；而且訊息可能重複投遞，消費者必須是 **idempotent（冪等，同一個請求做一次和做多次結果相同）**（第 33 章）。

**AWS 實作**：一對一的工作佇列用 SQS；一個事件要通知多個系統用 SNS fan-out 到多個 SQS，或用 EventBridge 依規則路由（第 32 章）；多步驟、需要 retry、補償與人工核准的流程用 Step Functions（第 33 章）。消費端的運算可以依 queue 深度擴展：ASG 依「每台 instance 的 backlog」做 target tracking（第 18 章），Lambda 透過 event source mapping 自動調整並行數（第 19 章）。

**考試訊號**：`loosely coupled`、`decouple`、「一個元件變慢不能影響其他元件」、「各元件需要獨立擴展」、「下游系統偶爾無法使用，但不能遺失請求」。答案形狀是「在兩者之間插入 SQS／SNS／EventBridge」，錯誤選項通常是「把呼叫逾時調長」或「把下游 instance 換成更大的規格」。

### 模式 3：消除單點故障，包括你沒想到的那些單點

**問題**：**單點故障（single point of failure，SPOF）** 是「它壞了，整個系統就壞了」的元件。新手會想到單台 EC2 或單一資料庫，但 Wanderly 真正踩過的單點更隱蔽：只建一台的 NAT Gateway、只有一條的 Direct Connect、所有人都靠它登入的身份提供者、只有一個人知道怎麼操作的部署流程。

**原理**：消除單點有兩個步驟。第一步是**找出 failure domain（故障域）**：instance、AZ、Region、帳號、甚至一個人，都可能同時失效；備援元件必須放在不同的故障域，兩台 EC2 放在同一個 AZ 不算備援。第二步是**讓切換不依賴「故障時才做的動作」**：每個 AZ 預先有足夠容量，故障時不需要臨時啟動新機器，這就是第 2、18 章介紹的 **static stability（靜態穩定）**。

**AWS 實作**：

| 常見單點 | 消除方式 | 章節 |
|---|---|---|
| 單台 web server | ALB + 跨至少兩個 AZ 的 ASG | 第 10、18 章 |
| 單一資料庫 instance | RDS Multi-AZ、Aurora 跨 AZ replicas | 第 26 章 |
| 單台 NAT Gateway | 每個 AZ 一台，各 AZ 用自己的 route table | 第 5 章 |
| 單一 Direct Connect 連線 | 第二條 DX（最好在不同 DX location），或 Site-to-Site VPN 備援 | 第 8 章 |
| 單一 Region | 依 RTO／RPO 選 DR 策略（模式 10） | 第 34、42 章 |
| 單一身份提供者或 break-glass 缺失 | IdP 高可用、預先準備緊急存取帳號 | 第 13、40 章 |
| 手動部署 | IaC 與 pipeline，任何人都能重現 | 第 37 章 |

**考試訊號**：`highly available`、`fault tolerant`、「一個 AZ 故障時服務不能中斷」、「目前架構只有一台……」。最典型的錯誤選項是「把唯一的那台換成更大的規格」：scale up 解決的是容量，不是單點。

> [!tip] 考試提示
> `highly available` 與 `fault tolerant` 在題目中常被交替使用，但若題目強調「故障期間完全不能有任何中斷或效能下降」，就要選預先備好完整容量的設計（static stability），而不是「故障後幾分鐘內自動補回」的設計。

## 54.4 壞得小、恢復快：模式 4–7

第一組讓系統「平常穩」，但再穩的系統都會壞。第二組模式處理的是「壞的時候怎麼讓影響範圍最小、怎麼不靠人工也能恢復」。

### 模式 4：控制 blast radius，用帳號、cell 與分批部署切出邊界

**問題**：共享資源讓效率最高，但也讓一個錯誤影響所有人。Wanderly 曾經把一個錯誤的設定一次推到所有伺服器，全站同時當機；也曾因為一個大客戶的批次匯入把共用資料庫塞滿，讓所有客戶都變慢。

**原理**：**blast radius（爆炸半徑，影響範圍）** 是「一次故障最多會影響多少使用者或系統」。縮小它的方法都是同一個形狀：把系統切成彼此不共享關鍵資源的單位，讓故障停在單位內。切的維度可以是帳號、Region、AZ、部署批次，或是 **cell**：把整套 stack（運算、資料、queue）複製成多份，每份只服務一部分客戶，由一個盡量簡單的 router 依客戶 ID 決定要去哪個 cell（第 35 章）。一個 cell 只要還共用同一個資料庫或 queue，就不是真正的隔離。

**AWS 實作**：用多帳號隔離環境與團隊，SCP 限制每個帳號能做的事（第 14、40 章）；用 cell-based architecture 與 shuffle sharding 隔離租戶（第 35、49 章）；部署採 canary 或 linear，一次只更新一小部分，搭配自動 rollback（第 37 章）；Lambda reserved concurrency 或 API Gateway usage plans 限制單一來源能吃掉的容量（第 19、20 章）；AZ 出現灰色故障時用 Route 53 ARC 的 zonal shift 把流量移開（第 34 章）。

**考試訊號**：`blast radius`、`noisy neighbor`、「一個租戶的問題影響所有租戶」、「一次錯誤部署造成全面中斷」、「限制故障影響範圍」。SAP 題常把「帳號隔離」和「應用程式 cell 隔離」放在不同選項：帳號與 OU 是治理邊界，不會自動切分 runtime 的資料與流量，兩者要分清楚。

### 模式 5：queue 吸收突波，但不能吸收長期超載

**問題**：Wanderly 的限時促銷每次開賣，訂單 API 會在幾分鐘內收到平常幾十倍的請求，資料庫連線數瞬間爆滿。第一次的處理方式是把資料庫升級到最大規格，結果每個月為了那十分鐘付出整個月的費用。

**原理**：如果流量是「短暫的尖峰」，平均處理能力其實足夠，只是來得太集中。把請求先放進 queue，後端用穩定速度處理，尖峰就被攤平成一段較長的處理時間，這叫 **削峰填谷（load leveling）**。但這個模式有明確的極限：如果長時間「進來的速度 > 處理的速度」，queue 只會無限增長，訊息在被處理前就已經過期（使用者早就離開，或訊息超過 retention 被刪除）。所以 queue 一定要搭配兩件事：**監控 backlog 的年齡**，以及在長期超載時**擴充消費者或拒絕新工作（load shedding）**（第 35 章）。

```text
 請求量
   ▲      ┌┐
   │      ││ ← 促銷開賣的尖峰
   │      ││
   │ ─────┼┼──────────────── 後端處理能力
   │      ││
   │ ▁▁▁▁▁┘└▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁
   └──────────────────────────▶ 時間
            │
            ▼ 放進 queue 後
   │ ─────┬────────┬───────── 後端用固定速度處理
   │      └ backlog┘ 尖峰被攤平，幾分鐘內消化完
```

圖的上半部是沒有 queue 的情況：尖峰高過後端處理能力，超出的部分就是錯誤與逾時。下半部是加上 queue 後：同樣的總工作量被攤在較長的時間內處理，後端始終在能力範圍內運作。如果尖峰不是幾分鐘而是一整天，backlog 就會一路變大，這時答案不是更大的 queue，而是更多消費者或分流。

**AWS 實作**：SQS 作為緩衝，消費端 ASG 依 backlog per instance 擴展（第 18、32 章）；CloudWatch 監控 `ApproximateAgeOfOldestMessage`（最舊訊息等了多久）而不只是訊息數量（第 36 章）；處理失敗多次的訊息送到 DLQ（dead-letter queue），避免一筆壞訊息卡住整個佇列（第 32 章）；Lambda 消費 SQS 時用 maximum concurrency 或 reserved concurrency 保護下游資料庫（第 19 章）；大量事件流則用 Kinesis Data Streams（第 31 章）。

**考試訊號**：`sudden spikes`、`unpredictable traffic`、「後端資料庫在尖峰時過載」、「不能遺失任何訂單」、「請求可以非同步處理」。錯誤選項通常是「把資料庫換成最大規格」（貴且無法應對更大的尖峰）或「增加 API 的逾時時間」（只是讓使用者等更久）。

### 模式 6：cache 是效能工具，不是正確性來源

**問題**：Wanderly 的搜尋頁把每間旅館的剩餘房數放在 ElastiCache，讓搜尋飛快。某天快取更新延遲，兩位使用者都看到「剩 1 間」，都下單成功，旅館只好打電話給其中一位道歉。

**原理**：**cache（快取）** 是資料的副本，存在比較快但不保證完整的地方。副本可能過期（TTL 還沒到但來源已經改了）、可能被 **evict（因記憶體不足被淘汰）**、可能在節點故障時整批消失。因此要遵守三條規則：第一，**會影響金錢或庫存的決定，必須在 source of truth（真正的資料來源）上用原子操作確認**，例如在資料庫用條件式更新扣庫存；第二，**cache miss 的路徑必須能正常運作**，快取全空時系統可以變慢，但不能變錯；第三，要防止大量 key 同時過期時，所有請求一起打到資料庫的 **cache stampede（快取雪崩）**（第 28 章）。

**AWS 實作**：讀多寫少的資料用 ElastiCache cache-aside 加上 TTL（第 28 章）；DynamoDB 的熱讀取用 DAX，但要記得 DAX 提供的是最終一致讀取（第 27 章）；靜態內容與可快取的 API 回應用 CloudFront（第 11 章）；扣庫存用 DynamoDB condition expression 或 transaction，或在 Aurora 中用交易與列鎖（第 26、27 章）。需要「既要記憶體速度、又要當作耐久資料庫」時，才考慮 MemoryDB 這類耐久的記憶體資料庫（第 28 章）。

**考試訊號**：`reduce read latency`、`offload the database`（cache 是正解）；但如果題目同時提到「不能超賣」「必須是最新資料」「強一致」，答案就要把正確性放回資料庫，cache 只用在顯示層。

### 模式 7：分開 control plane 與 data plane，故障時只依賴 data plane

**問題**：Wanderly 第一版的 DR 計畫寫著：「主 Region 故障時，執行腳本建立新的 ASG、修改 DNS 記錄、建立新的資料庫 replica。」演練時才發現，大範圍事件發生時，這些「建立」與「修改」的 API 本身可能變慢或被大量請求擠爆，計畫中最關鍵的步驟恰好最不可靠。

**原理**：第 2 章介紹過，**control plane（控制平面）** 是管理資源的 API：建立、修改、刪除；**data plane（資料平面）** 是資源運作時處理每一個請求的路徑：EC2 執行程式、DNS 回答查詢、負載平衡器轉送封包。AWS 對 data plane 的可用性設計通常高於 control plane，而且 control plane 通常比較複雜、依賴更多元件。所以故障應變的原則是：**恢復路徑上只用 data plane 動作**，所有需要 control plane 的準備工作在平時就做好。這和模式 3 的 static stability 是同一個概念的兩面。

**AWS 實作**：Route 53 health check 與 failover routing 在 data plane 上自動切換，不需要在事件中修改記錄（第 9 章）；Route 53 ARC 的 routing control 讓你用高可用的 data plane API 切換流量，並可搭配 safety rules 避免誤切（第 34、42 章）；備援 Region 預先以 warm standby 保持運作中的容量，而不是故障時才用 CloudFormation 建立（第 34 章）；功能開關與動態設定用 AppConfig，讓應用程式在 data plane 上讀取設定（第 37 章）。

**考試訊號**：`static stability`、「故障時不能依賴建立新資源」、「failover 必須在主 Region 無法使用時仍可執行」、「最可靠的 failover 機制」。錯誤選項的共同特徵是「事件發生時才呼叫 API 建立或修改某個東西」。

## 54.5 守得住、看得見：模式 8–9

系統能撐過故障之後，下一個問題是「它安不安全」以及「我們怎麼知道它真的在正常服務使用者」。

### 模式 8：身份、網路、資料三層安全，任何一層失守都還有下一層

**問題**：Wanderly 的第一次資安事件不是被駭，而是一份把 S3 bucket 設成公開的設定。事後檢討發現，如果只依賴一層控制（例如只靠 bucket policy），任何一個人為錯誤都會直接變成資料外洩。

**原理**：**defense in depth（縱深防禦）** 的意思是用彼此獨立的多層控制保護同一份資料。三層各自回答不同的問題：**身份層**問「你是誰、可以做什麼」；**網路層**問「你從哪裡來、可以走哪條路」；**資料層**問「就算拿到了，看不看得懂、改不改得了、刪不刪得掉」。每一層都遵守 **least privilege（最小權限）**，而且還要有第四件事：**偵測**，因為預防一定有漏洞。

**AWS 實作**：

| 層 | 主要控制 | 章節 |
|---|---|---|
| 身份 | IAM role 與最小權限 policy、IAM Identity Center、SCP／RCP、permission boundary | 第 12、13、14 章 |
| 網路 | 三層 subnet、security group、NACL、VPC endpoint、WAF、Network Firewall | 第 5、6、16、41 章 |
| 資料 | KMS 加密與 key policy、S3 Block Public Access、Object Lock、Secrets Manager | 第 15、22、23 章 |
| 偵測 | CloudTrail、Config、GuardDuty、Security Hub、Macie | 第 16、40 章 |

三層會在同一份 policy 裡交會。例如 S3 bucket policy 可以同時要求「只接受透過特定 VPC endpoint 的請求」（`aws:SourceVpce`，網路層）與「只允許特定 role」（身份層），而物件本身用 SSE-KMS 加密，讀取者還必須有 KMS key 的使用權限（資料層）。

**考試訊號**：`least privilege`、`defense in depth`、「資料不能經過 Internet」、「即使憑證外洩也不能讀取資料」、「必須能稽核誰存取了什麼」。安全題最常見的錯誤選項是「用 IAM user 的長期 access key」（應改用 role）以及「把敏感資料加密，但 key 和資料放在同一個權限邊界」。

### 模式 9：observability 跟隨業務結果，而不是只看資源指標

**問題**：某個週末，Wanderly 的監控面板一片綠色：CPU 30%、記憶體正常、ALB 沒有 5xx 錯誤。但訂房數比上週少了四成。原因是金流商的 API 開始回傳「交易被拒」，而應用程式把它當成正常回應，顯示一個友善的錯誤頁面給使用者，回傳 HTTP 200。

**原理**：**observability（可觀測性）** 是「從外部輸出推斷系統內部狀態」的能力，由 metrics（指標）、logs（日誌）與 traces（追蹤）組成（第 36 章）。資源健康是必要條件，但不是使用者成功的充分條件。所以告警的優先順序應該是：先監控**業務結果**（訂房成功率、付款成功率、搜尋到下單的轉換率），再監控**使用者體驗**（延遲、錯誤率），最後才是**資源狀態**（CPU、記憶體）。這些目標可以寫成 **SLO（service level objective，服務水準目標）**，例如「30 天內 99.5% 的訂房請求在 2 秒內成功完成」。

**AWS 實作**：應用程式發布 custom metric（例如每分鐘成功訂房數），對它設定 alarm 或 anomaly detection；CloudWatch Synthetics canary 定期模擬使用者走完「搜尋 → 選房 → 付款」流程；RUM 收集真實使用者在瀏覽器端的體驗；X-Ray 或 ADOT 追蹤一個請求經過哪些服務、卡在哪裡；composite alarm 把多個訊號組合起來，減少誤報（第 36 章）。告警觸發後，用 EventBridge 與 Systems Manager Automation 執行既定的修復 runbook（第 38 章）。

**考試訊號**：「監控沒有異常，但使用者回報失敗」、「需要在客戶發現之前知道」、「找出延遲發生在哪個服務」、「EC2 的記憶體使用率」（這個要 CloudWatch agent，第 36 章）。錯誤選項常常是「提高 CPU 告警的敏感度」：再敏感的資源指標也看不到業務邏輯層的失敗。

## 54.6 付得起、搬得動：模式 10–12

最後一組模式處理的是架構以外、卻直接決定架構的力量：業務能接受多少損失、能付多少錢，以及既有系統要怎麼搬。這一組在 SAP 的比重特別高。

### 模式 10：RTO 與 RPO 決定 DR 策略，而不是服務名稱決定

**問題**：Wanderly 的董事會問：「我們有沒有災難復原？」工程團隊回答：「有，我們用 Aurora 和 S3，都有備份。」但沒有人能回答「東京 Region 整個無法使用時，幾分鐘可以恢復訂房」以及「最多會遺失多少筆訂單」。

**原理**：**RTO（Recovery Time Objective）** 是「可以接受停多久」，**RPO（Recovery Point Objective）** 是「可以接受遺失多久的資料」（第 4 章）。這兩個數字由業務決定，DR 策略再依它們選擇：RPO 由**資料複寫的方式與頻率**決定（每天備份一次，RPO 就是一天；持續非同步複寫，RPO 就是秒級）；RTO 由**備援環境預先準備到什麼程度**決定（什麼都沒有要從頭建，有運作中的縮小版只需擴大）。同樣用 Aurora，有沒有開 Global Database、備援 Region 有沒有預先跑著 app tier，恢復能力天差地遠。而且**沒有演練過的 DR 只是假設**。

**AWS 實作**：第 34 章的四種策略，由便宜到昂貴：

| 策略 | 備援 Region 平時有什麼 | 典型 RTO | 典型 RPO |
|---|---|---|---|
| Backup & restore | 只有備份（AWS Backup 跨 Region copy、snapshot） | 數小時 | 數小時（取決於備份頻率） |
| Pilot light | 資料持續複寫，運算資源不運作或極少 | 數十分鐘到數小時 | 秒到分鐘 |
| Warm standby | 縮小規模但完整運作的環境 | 分鐘級 | 秒到分鐘 |
| Multi-site active-active | 完整規模、同時服務流量 | 接近零 | 接近零（取決於資料層） |

資料層的跨 Region 能力：Aurora Global Database（第 26 章）、DynamoDB global tables（第 27 章）、S3 CRR（第 23 章）、EBS snapshot 跨 Region copy（第 24 章）；整台伺服器的持續複寫則可用 Elastic Disaster Recovery（第 34 章）。全球多 Region 的完整設計見第 42 章，Wanderly 最終的 warm standby 架構見第 53 章。

**考試訊號**：題目一定會給 RTO／RPO 數字，再加上 `MOST cost-effective`。解題方法是：先刪掉做不到 RPO／RTO 的選項，再在剩下的選項裡選最便宜的。常見陷阱是「多 AZ 就等於 DR」：Multi-AZ 處理的是 AZ 故障，不處理 Region 故障或誤刪資料；誤刪與勒索軟體要靠有版本、有隔離的備份（AWS Backup vault lock、S3 Object Lock）。

### 模式 11：成本是架構限制，在設計時就決定了大部分支出

**問題**：Wanderly 的帳單在一年內翻了三倍，但流量只增加五成。細看之後發現，最貴的不是運算，而是資料傳輸：private subnet 的 worker 經 NAT Gateway 讀寫 S3、跨 AZ 的大量內部呼叫、跨 Region 複寫了不需要複寫的資料。

**原理**：大部分雲端成本在畫架構圖時就決定了：資料走哪條路、放在哪個儲存類別、運算用哪種購買方式、要預留多少閒置容量。上線後的「清理」只能回收一部分。所以成本應該和延遲、可用性一樣被寫成需求，例如用 **unit economics（單位經濟）** 表達：「每筆訂房的雲端成本不超過 X 元」，讓團隊可以在流量成長時判斷成本是否健康（第 39 章）。

**AWS 實作**：

- **資料路徑**：S3 與 DynamoDB 走 gateway endpoint 避開 NAT 處理費（第 5、6 章）；減少不必要的跨 AZ、跨 Region 流量；用 CloudFront 降低從 origin 輸出的流量（第 11 章）。
- **購買方式**：穩定基線用 Savings Plans 或 Reserved Instances，可中斷的批次用 Spot，突發部分用 On-Demand（第 17、39 章）。
- **規格與類別**：用 Compute Optimizer 做 rightsizing、Graviton 提升性價比、gp2 換 gp3、S3 lifecycle 與 Intelligent-Tiering（第 23、24、39 章）。
- **治理**：cost allocation tags、Budgets 與 actions、Cost Anomaly Detection、CUR 搭配 Athena 分析、chargeback／showback（第 39、43 章）。

**考試訊號**：`MOST cost-effective`、`reduce costs`、「工作可以被中斷」、「使用量穩定且可預測」、「資料很少被存取但需要時要立即取得」。要注意成本永遠是在**滿足其他限制之後**才比較：一個便宜但做不到 RPO 的方案不是 cost-effective，而是不合格。

### 模式 12：遷移由業務價值與依賴關係驅動

**問題**：Wanderly 併購的旅行社有 300 台 VM，資料中心租約 18 個月後到期。第一版遷移計畫依照「哪台機器最好搬」排順序，結果第一波搬上去的報表伺服器，每個查詢都要穿過 Direct Connect 回到還在地端的 Oracle，延遲讓報表慢了十倍。

**原理**：遷移順序要同時考慮兩件事。第一是**業務價值與期限**：租約、授權到期、硬體汰換決定了必須完成的時間，而不是每個系統都值得重寫。第二是**依賴關係圖（dependency graph）**：彼此頻繁通訊的系統要放在同一個 **wave（遷移批次）**，否則會把原本在機房內的低延遲呼叫變成跨網路的高延遲呼叫。每個應用程式再依 **7Rs**（retire、retain、relocate、rehost、replatform、repurchase、refactor）決定搬遷方式：期限緊的先 rehost，之後再現代化（第 44、46 章）。

**AWS 實作**：用 Application Discovery Service 等探索工具收集伺服器規格、使用率與網路連線，建立依賴圖與 TCO 分析（第 44 章；ADS 與 Migration Hub 自 2025-11-07 起不再開放新客戶，考試仍以它們為標準答案，從未使用過的組織實務上改用 AWS Transform）；landing zone 與 hybrid 網路先行（第 40、41、8 章）；伺服器用 Application Migration Service（MGN）持續複寫並先做測試啟動，資料庫用 DMS 的 full load 加 CDC 縮短停機，異質引擎搭配 SCT 或 DMS Schema Conversion（第 45 章）；大量檔案用 DataSync，網路頻寬不足時評估離線傳輸（第 25 章）。完整案例見第 51 章。

**考試訊號**：`migrate with minimal changes`（rehost）、`minimal downtime`（DMS CDC、MGN 持續複寫）、「資料中心租約即將到期」、「需要了解伺服器之間的依賴」、「第一波應該選哪些應用程式」。錯誤選項常常是「全部先 refactor 成 serverless 再搬」（違反期限）或「依伺服器數量平均分配到各個 wave」（忽略依賴）。

## 54.7 把模式組起來：Wanderly 的最終架構

單一模式很少單獨出現。下面是 Wanderly 現在的主要訂房路徑，圈號標出每個位置用到的模式：

```text
 使用者
   │
   ▼
 Route 53（failover + health check）⑦⑩
   │
   ▼
 CloudFront + WAF ⑥⑧ ──────────── 靜態內容、可快取的搜尋結果
   │
   ▼
 ┌─── 東京 Region（primary）────────────────────────────────┐
 │ ALB（public subnet，跨 3 AZ）③                           │
 │   │                                                      │
 │   ▼                                                      │
 │ ECS on Fargate：搜尋 / 訂房 API ①③（private subnet）⑧    │
 │   │            │                                         │
 │   │ 讀          │ 寫訂單                                   │
 │   ▼            ▼                                         │
 │ ElastiCache ⑥  SQS 訂單佇列 ②⑤ ──▶ 訂單 worker（backlog 擴展）  │
 │                                     │                    │
 │                                     ▼                    │
 │                         Aurora（條件式扣庫存）⑥ + KMS ⑧    │
 │                                     │                    │
 │ CloudWatch 業務指標 / Synthetics ⑨  │ Global Database ⑩   │
 └─────────────────────────────────────┼────────────────────┘
                                       ▼
 ┌─── 新加坡 Region（warm standby）⑦⑩ ───────────────────────┐
 │ 縮小規模但運作中的 ALB + ECS；Aurora secondary cluster    │
 └──────────────────────────────────────────────────────────┘
 帳號：prod／staging／shared／security 分帳號，SCP 限制 Region ④⑧
 部署：canary，一次一個 cell ④　　成本：Savings Plans 涵蓋基線 ⑪
```

依請求的方向讀這張圖。使用者先經過 Route 53，它用 health check 決定把流量送到哪個 Region，切換發生在 data plane（⑦），切換的目標由 RTO／RPO 決定（⑩）。CloudFront 吸收大部分靜態與可快取的讀取（⑥），WAF 是網路層的第一道防線（⑧）。進入 Region 後，ALB 與 ECS 跨三個 AZ（③），運算用 Fargate 免除節點管理（①），API 放在 private subnet（⑧）。

搜尋讀取走 ElastiCache（⑥），但下單不信任快取：訂單先寫入 SQS（②⑤），worker 依 backlog 擴展，在 Aurora 中用條件式更新確認並扣除庫存（⑥），資料以 KMS 加密（⑧）。CloudWatch 監控的是「每分鐘成功訂房數」而不只是 CPU（⑨）。Aurora Global Database 把資料持續複寫到新加坡，那裡的 warm standby 環境平時就在運作（⑦⑩）。圖下方的兩行是看不見的模式：多帳號與 SCP 限制影響範圍與權限（④⑧），canary 部署讓錯誤只影響一個 cell（④），Savings Plans 把穩定基線的成本壓低（⑪）。舊資料中心的系統，則是依依賴關係分波搬進這個架構（⑫）。

> [!example] 例子：同一個需求，三個模式一起出現
> 「促銷期間訂單量是平常的 30 倍，不能遺失訂單，不能超賣，成本要最低。」這一句話同時觸發模式 5（queue 削峰、不遺失）、模式 6（扣庫存必須在資料庫做原子操作）與模式 11（不要為了尖峰常態使用最大規格）。正確答案會長得像「SQS + 依 backlog 擴展的 worker + 資料庫條件式更新」，而不是「把 Aurora 升級到最大的 instance class」。

## 54.8 比較與選型：12 個模式總表與衝突時的取捨

### 12 個模式總表

| # | 模式 | 題目訊號 | 常見正解形狀 | 常見錯誤選項 | 主要章節 |
|---|---|---|---|---|---|
| 1 | Managed service 優先 | LEAST operational overhead | RDS、DynamoDB、Fargate、SQS | EC2 自管同等軟體 | 2、21、26、46 |
| 2 | 解耦 | loosely coupled、獨立擴展 | SQS、SNS fan-out、EventBridge、Step Functions | 加長逾時、同步重試 | 32、33 |
| 3 | 消除單點 | highly available、AZ 故障 | 多 AZ、Multi-AZ、每 AZ 一台 NAT | 換更大的單台 | 5、18、26、34 |
| 4 | 控制 blast radius | noisy neighbor、錯誤部署全面中斷 | 多帳號、cell、canary、quota 隔離 | 共享資源加大規格 | 14、35、37、40 |
| 5 | Queue 削峰 | sudden spikes、不能遺失 | SQS + backlog 擴展、DLQ | 資料庫升到最大規格 | 18、32、35 |
| 6 | Cache 不是真相 | 降低讀取延遲；但不能超賣 | cache-aside + TTL；資料庫原子更新 | 用快取值做交易決定 | 27、28 |
| 7 | Control／data plane | static stability、可靠 failover | health check failover、ARC、預先容量 | 事件中才建立資源 | 2、9、34 |
| 8 | 三層安全 | least privilege、不經 Internet | role、endpoint + policy、KMS、偵測 | 長期 access key、單層控制 | 12、15、16 |
| 9 | 業務導向觀測 | 指標正常但使用者失敗 | custom metric、Synthetics、X-Ray | 調整 CPU 告警 | 36、38 |
| 10 | RTO／RPO 決定 DR | 給定 RTO／RPO + 最便宜 | 四種 DR 策略依數字選擇 | 把 Multi-AZ 當 DR | 34、42 |
| 11 | 成本是限制 | MOST cost-effective | endpoint、Savings Plans、Spot、lifecycle | 為尖峰常態超配 | 39、43 |
| 12 | 遷移依價值與依賴 | 租約到期、依賴、minimal downtime | 依賴分 wave、7Rs、MGN、DMS CDC | 全部先重寫、依數量分批 | 44、45、51 |

### 模式衝突時怎麼辦

模式之間會互相拉扯，題目的最佳化目標就是裁判：

| 衝突 | 例子 | 怎麼判斷 |
|---|---|---|
| 可用性 vs 成本（3、10 vs 11） | 多 Region active-active 很可靠也很貴 | 先滿足題目明寫的 RTO／RPO，再選最便宜；題目沒要求 Region 級容錯就不要多 Region |
| 解耦 vs 一致性（2 vs 6） | 非同步處理讓結果晚幾秒才確定 | 題目要求「立即回覆結果」時保留同步路徑，只把後續步驟非同步化 |
| 受管 vs 控制權（1） | managed service 不支援某個功能 | 題目明確說出 managed 做不到的限制時才選自管或 RDS Custom |
| 隔離 vs 效率（4 vs 11） | 每個租戶一套 stack 最隔離也最貴 | 依合規與租戶等級混用 silo 與 pool（第 49 章） |
| 安全 vs 營運負擔（8 vs 1） | 自建加密金鑰管理最可控但最累 | 沒有「必須單一租戶 HSM」等明確要求時，KMS 優先於 CloudHSM（第 15 章） |

## 54.9 SAP 加深：從 SAA 到 SAP 的心態轉換

已經通過 SAA 的讀者準備 SAP 時，最常遇到的困難不是知識不夠，而是解題的「單位」變了。

**從單一 workload 到整個組織。** SAA 題目的主角通常是一個應用程式；SAP 題目的主角是一家有幾十個帳號、既有資料中心、合規部門與預算審查的公司。同樣問「怎麼讓 S3 資料不被公開」，SAA 的答案可能是 Block Public Access，SAP 的答案則要能套用到所有帳號、新帳號自動生效、而且有人繞過時會被發現，例如 Organizations 層級的控制加上 Config 與 Security Hub 的偵測（第 14、40、43 章）。

**從選服務到選方案。** SAA 的四個選項常常差在一個服務名稱；SAP 的四個選項常常是四個都能運作的完整方案，差在「誰的營運負擔最低」「哪個不需要改應用程式」「哪個能在期限內完成」。讀 SAP 選項時，先找每個選項**和其他選項不同的那一句**，通常只有一兩個差異點需要判斷。

**從「能不能做到」到「在既有限制下怎麼做到」。** SAP 題目幾乎都帶著既有狀態：已經有 Direct Connect、已經用了某個 IdP、CIDR 已經重疊、應用程式不能修改。正確答案必須和這些既有狀態相容。一個技術上最漂亮、卻要求重新編址所有 VPC 的方案，在「三個月內完成」的限制下就是錯的。

**從單一模式到模式組合。** SAA 題目通常考一個模式；SAP 題目常常同時考兩三個，而且彼此有張力。例如「跨帳號集中檢查流量（模式 8）、不能成為單點（模式 3）、成本要可分攤到各部門（模式 11）」。先把每個限制對應到模式，再找同時滿足全部限制的那個選項。

> [!sap] SAP 加深
> SAP 的長題目建議先讀最後一句問句與最佳化目標，再回頭讀情境並逐句標記限制（第 1 章 1.12 節）。標記時直接寫模式編號，例如「RPO 15 分鐘 → ⑩」「不想管伺服器 → ①」。讀完題幹時，你應該已經能說出正確答案大概的形狀，再去選項裡找它。

## 54.11 考場策略

第 1 章已經介紹過時間預算與兩輪作答，這裡把它整理成考場上可以直接執行的步驟。

1. **第一輪：每題都作答，沒把握就標記。** SAA 每題約 2 分鐘、SAP 約 2.4 分鐘。超過預算的題目先選一個目前最可能的答案並標記，繼續往下。沒有倒扣，空白的題目一定沒有分數。
2. **讀題順序固定。** 先讀問句與最佳化目標，再讀情境、圈出限制，在腦中寫下模式編號，最後才看選項。
3. **刪去法依序使用。** 先刪違反明確限制的選項（做不到 RPO、需要改程式但題目說不能改），再刪營運負擔明顯較高的選項（自管、手動、自寫腳本），最後在剩下的選項中用最佳化目標比較。
4. **多選題分開判斷。** 題目寫「選兩項」時，把每個選項當成一個獨立的是非題，各自判斷它是否滿足需求；不要因為已經選了一個，就覺得另一個必須和它搭配。
5. **第二輪只看標記題。** 回頭看標記題時，只有在找到具體理由（例如發現漏看一個限制）時才改答案；單純的「感覺不對」通常不值得改。
6. **遇到沒見過的服務名稱不要慌。** 先用模式判斷這個選項想做什麼，再看它是否滿足限制。不計分題也可能混在其中，任何一題都不值得花掉五分鐘。

> [!tip] 考試提示
> 當兩個選項看起來都對時，回到題目的最佳化目標逐字比對：`LEAST operational overhead` 選受管、少元件、不需寫程式的；`MOST cost-effective` 選滿足限制下最便宜的；`MOST secure` 選控制層數最多、權限最小的。這一步能解決大部分「兩個都對」的困境。

## 54.12 考試這樣考

| 題目出現的關鍵字 | 優先想到 |
|---|---|
| LEAST operational overhead、不想管理伺服器 | 模式 1：managed service、serverless、Fargate |
| loosely coupled、一個元件變慢不能拖垮其他元件 | 模式 2：SQS、SNS fan-out、EventBridge |
| 一個 AZ 故障時服務不能中斷 | 模式 3：多 AZ、每 AZ 預留足夠容量（static stability） |
| 一個租戶或一次部署影響所有人 | 模式 4：cell、多帳號、canary 部署、quota 隔離 |
| 尖峰流量、不能遺失請求、後端會被壓垮 | 模式 5：SQS 緩衝 + 依 backlog 擴展 + DLQ |
| 讀取延遲高；但不能超賣、要最新資料 | 模式 6：cache 加速讀取，交易在資料庫原子確認 |
| failover 不能依賴主 Region 或建立新資源 | 模式 7：health check failover、Route 53 ARC、預先容量 |
| 資料不能經過 Internet、最小權限 | 模式 8：VPC endpoint + policy、IAM role、KMS |
| 監控正常但使用者失敗、要在客戶之前發現 | 模式 9：業務 custom metric、Synthetics canary |
| 給定 RTO／RPO 且要最便宜 | 模式 10：依數字選 DR 策略，再比成本 |
| 工作可中斷、用量穩定、資料很少存取 | 模式 11：Spot、Savings Plans、S3 lifecycle |
| 租約到期、伺服器依賴、最短停機 | 模式 12：依賴分 wave、rehost 先行、MGN、DMS CDC |

**常見陷阱**：

1. **用 scale up 解決可用性問題**：更大的單台機器仍然是單點。可用性問題的答案是多一個故障域，不是更大的規格。
2. **把 Multi-AZ 當成 DR**：Multi-AZ 不防 Region 故障，也不防誤刪；誤刪要靠有版本與保護的備份。
3. **用快取資料做交易決定**：任何會影響金錢或庫存的判斷都要在 source of truth 上確認。
4. **queue 被當成無限容量**：長期超載時要擴充消費者或拒絕新工作，queue 只能吸收短期突波。
5. **failover 計畫依賴事件中才呼叫的 control plane 操作**：能預先準備的都要預先準備。
6. **只比成本、不先檢查限制**：做不到 RPO 或違反合規的方案，再便宜也不是正解。

## 本章重點整理

- 架構題的解題順序是：先找限制與最佳化目標，再對應到設計模式，最後才把 AWS 服務名稱放回來。
- 模式 1：預設選 managed service 以降低營運負擔，只有在題目明確說出 managed 做不到的需求時才退到 RDS Custom 或 EC2 自管。
- 模式 2：解耦讓元件可以各自擴展與失敗，代價是最終一致與重複投遞，所以消費者必須是 idempotent。
- 模式 3：消除單點要把備援放在不同故障域，並以 static stability 預先準備容量；scale up 不能消除單點。
- 模式 4：用帳號、cell、分批部署與 quota 縮小 blast radius；共享同一個資料庫或 queue 的 cell 不算真正隔離。
- 模式 5：queue 能把短期尖峰攤平，但長期超載必須擴充消費者或拒絕新工作，並監控最舊訊息的等待時間。
- 模式 6：cache 只用來加速，會影響金錢與庫存的決定必須在資料庫用原子操作確認，cache 全空時系統也要正確。
- 模式 7：故障恢復路徑只依賴 data plane，例如 health check failover、Route 53 ARC routing control 與預先運作的備援容量。
- 模式 8：身份、網路、資料三層各自用最小權限控制，再加上 CloudTrail、Config、GuardDuty 等偵測。
- 模式 9：告警優先監控業務結果與使用者體驗，資源指標正常不代表使用者成功。
- 模式 10：RPO 由資料複寫方式決定，RTO 由備援預先準備的程度決定；先刪掉做不到 RTO／RPO 的選項，再選最便宜的。
- 模式 11：成本在設計資料路徑、購買方式與儲存類別時就已大致決定，但永遠是在滿足其他限制之後才比較。
- 模式 12：遷移順序依期限、業務價值與依賴關係決定，頻繁通訊的系統放在同一個 wave，期限緊時先 rehost 再現代化。
- SAP 與 SAA 的差別在於解題單位從單一 workload 變成整個組織，選項從「選服務」變成「選與既有限制相容的完整方案」。
- SAP-C02 的最後應考日是 2026 年 11 月 17 日，之後改考 SAP-C03（2026 年 10 月 27 日開放報名、exam guide 尚未公布）；本書 SAP 內容依 SAP-C02，架構知識仍適用，報名前要到官方頁面確認版本。
- 考前一週以模擬考、錯題本與附錄 A、B、C 鞏固既有知識；考場上每題都作答、沒把握先標記，改答案要有具體理由。

## 本章練習題

### 練習 54-1｜SAA｜單選｜以受管服務降低營運負擔

Wanderly 的會員資料庫目前是兩台 EC2 上自行安裝的 MySQL，一台 primary、一台以 replication 同步的 standby，放在同一個 Region 的兩個 AZ。每次 primary 故障，都要由值班工程師手動把 standby 升格並修改應用程式設定，平均需要 40 分鐘。團隊沒有專職資料庫管理員，希望 AZ 故障時能自動在幾分鐘內恢復，並讓營運負擔最低。

哪個方案最符合需求？

- A. 在兩台 EC2 上安裝叢集管理軟體並撰寫自動升格腳本，再用 Route 53 health check 切換資料庫的 DNS 名稱
- B. 把資料庫遷移到 Amazon RDS for MySQL 並啟用 Multi-AZ，應用程式改用 RDS 提供的 endpoint 連線
- C. 把兩台 EC2 換成更大的 instance type，降低 primary 因資源不足而故障的機率
- D. 保留現有架構，改用 AWS Backup 每小時備份 EC2 的 EBS volume，故障時從最新備份還原

> [!answer]- 答案：B
> **A ✗** 自動升格可以縮短恢復時間，但叢集軟體、腳本與 DNS 切換邏輯都要自己維護與測試，這正是題目想擺脫的營運負擔。當 managed service 能滿足需求時，自建高可用機制不是營運負擔最低的選項。
>
> **B ✓** RDS Multi-AZ 由 AWS 維護同步複寫的 standby，在 primary 或其所在 AZ 故障時自動 failover，並更新 endpoint 背後的 DNS 指向，應用程式不需要修改設定。patch 與備份也由服務處理，符合模式 1「managed service 優先」與模式 3「消除單點」。
>
> **C ✗** 換更大的規格只能降低因容量不足而出問題的機率，無法處理 AZ 故障或硬體故障，手動升格的流程與 40 分鐘的恢復時間都沒有改變。
>
> **D ✗** 從備份還原需要建立新 volume 與 instance，恢復時間通常比現狀更長，而且最多會遺失一小時的資料，不符合「幾分鐘內恢復」。
>
> **考點**：SAA-2.2、SAA-3.3｜managed service 優先與 RDS Multi-AZ

### 練習 54-2｜SAA｜單選｜用 queue 吸收促銷尖峰

Wanderly 每月舉辦一次限時促銷，開賣後的 10 分鐘內，訂單 API 會收到平常 25 倍的請求，Aurora 的連線數爆滿，部分訂單因逾時而遺失。其他時間的流量都很平穩。訂單可以在送出後的幾分鐘內完成處理，只要使用者立即收到「已收到訂單」的回應即可。公司希望不遺失訂單，同時成本最低。

哪個做法最合適？

- A. 把 Aurora writer 升級到最大的 instance class，並長期保持這個規格以應付每月的促銷
- B. 為 Aurora 新增 5 個 Aurora Replicas，讓訂單 API 把寫入平均分散到這些 replicas
- C. 讓訂單 API 把訂單寫入 Amazon SQS queue 後立即回應，由一組依 queue backlog 擴展的 worker 以穩定速度寫入 Aurora，並設定 DLQ 保存重複失敗的訊息
- D. 把訂單 API 的逾時時間從 3 秒延長到 60 秒，讓請求有更多時間等待資料庫連線

> [!answer]- 答案：C
> **A ✗** 最大規格能撐住尖峰，但每個月只需要 10 分鐘，卻要長期付最高的費用，不符合成本最低；下次尖峰更大時仍然可能不夠。
>
> **B ✗** Aurora Replicas 只提供讀取，所有寫入都必須送到 writer instance，增加 replicas 無法分擔寫入壓力。
>
> **C ✓** 這是模式 5 的標準形狀。SQS 把 10 分鐘的尖峰暫存起來，使用者立即得到回應；worker 依 backlog 擴展並以資料庫可承受的速度寫入，尖峰被攤平成幾分鐘的處理時間。訊息在被成功處理並刪除前都保留在 queue 中，處理失敗的訊息會重新出現或進入 DLQ，不會遺失。
>
> **D ✗** 延長逾時只是讓使用者等更久，資料庫的連線數上限沒有改變，更多請求同時等待反而讓情況惡化。
>
> **考點**：SAA-2.1、SAA-4.3｜queue 削峰與依 backlog 擴展

### 練習 54-3｜SAA｜選兩項｜找出隱藏的單點故障

Wanderly 的 web tier 是跨兩個 AZ 的 ALB 與 Auto Scaling group，資料庫是 RDS Multi-AZ。架構審查時發現：兩個 AZ 的 private subnet 共用一張 route table，`0.0.0.0/0` 指向位於 AZ-a 的唯一一台 NAT Gateway；應用程式產生的報表檔案寫在 AZ-a 中一台 EC2 的 EBS volume 上，再由其他 instance 透過 NFS 掛載讀取。公司要求任一 AZ 故障時，另一個 AZ 的功能都不受影響。

哪兩項變更能消除這些單點故障？（選兩項）

- A. 在 AZ-b 的 public subnet 新增第二台 NAT Gateway，為每個 AZ 的 private subnet 建立各自的 route table，指向同 AZ 的 NAT Gateway
- B. 把 AZ-a 的 NAT Gateway 改為更高頻寬的設定，並為它啟用跨 AZ 備援選項
- C. 為存放報表的 EBS volume 每小時建立 snapshot，AZ-a 故障時再從 snapshot 建立新 volume
- D. 把報表檔案改存到 Amazon S3（或跨多 AZ 的 Amazon EFS），讓所有 instance 直接存取，不再依賴單一 EC2
- E. 把 web tier 的 Auto Scaling group 最小容量從 2 提高到 6，全部放在 AZ-a

> [!answer]- 答案：A、D
> **A ✓** NAT Gateway 是 zonal 資源。每個 AZ 一台、每個 AZ 的 private subnet 使用自己 AZ 的 NAT，AZ-a 故障時 AZ-b 仍能對外連線，同時避免平時的跨 AZ 傳輸費用（第 5 章）。
>
> **B ✗** NAT Gateway 的頻寬會自動擴展，也沒有跨 AZ 備援的選項；只要仍然只有一台，它所在 AZ 故障時其他 AZ 就會失去對外連線。
>
> **C ✗** Snapshot 能保護資料，但 AZ-a 故障時仍需要人工建立 volume 與新的 NFS 伺服器，期間報表功能中斷，且會遺失最多一小時的檔案，不符合「功能不受影響」。
>
> **D ✓** S3 是 Regional 服務，資料跨多個 AZ 儲存；EFS 的 Regional 檔案系統也能讓多個 AZ 的 instance 同時掛載。兩者都移除了「單一 EC2 + 單一 EBS」這個單點（第 22、24 章）。
>
> **E ✗** 把更多 instance 放在同一個 AZ 增加的是容量，不是故障域；AZ-a 故障時這些 instance 會全部同時失效，反而讓問題更嚴重。
>
> **考點**：SAA-2.2｜消除隱藏單點：zonal NAT 與共享儲存

### 練習 54-4｜SAA｜單選｜快取不是庫存的真相來源

Wanderly 的搜尋頁從 Amazon ElastiCache 讀取每間旅館的剩餘房數，快取以 cache-aside 方式載入，TTL 為 60 秒。最近發生多起超賣：兩位使用者在同一分鐘內都看到「剩 1 間」，也都下單成功。房數的真實資料存放在 DynamoDB。團隊希望保留搜尋頁的低延遲，同時徹底避免超賣。

哪個做法最合適？

- A. 把 TTL 從 60 秒縮短為 1 秒，讓快取中的房數更接近即時
- B. 在 DynamoDB 前加入 DAX，讓下單流程從 DAX 讀取房數後再寫入訂單
- C. 改為 write-through，每次下單時先更新快取中的房數，再非同步更新 DynamoDB
- D. 搜尋頁繼續從快取讀取房數；下單時在 DynamoDB 以 condition expression 進行原子扣減（例如只有在剩餘房數大於 0 時才扣 1），條件不成立就告知使用者已售完

> [!answer]- 答案：D
> **A ✗** 縮短 TTL 只能縮小不一致的時間窗，無法消除兩個同時下單的請求都讀到同一個值的競態條件，而且會大幅增加資料庫讀取量。
>
> **B ✗** DAX 的 item 快取提供最終一致讀取，本質上仍是快取；用它的讀取結果來判斷能否下單，同樣會產生超賣。
>
> **C ✗** Write-through 讓快取更新得更快，但把快取當成先寫入的地方、再非同步更新資料庫，等於讓快取成為真相來源；快取節點故障或 evict 時資料會遺失，兩個並行請求也仍然可能同時成功。
>
> **D ✓** 這是模式 6 的做法：快取繼續負責讓搜尋頁變快，但扣庫存的決定在真相來源上用原子條件式寫入完成。DynamoDB 的 condition expression 保證只有一個請求能把最後一間房扣掉，另一個會收到條件失敗（第 27 章）。
>
> **考點**：SAA-3.3、SAA-2.1｜cache 不是正確性來源

### 練習 54-5｜SAA｜單選｜三層安全保護敏感文件

Wanderly 把旅客護照影本存放在一個 S3 bucket，只有位於 private subnet 的簽證處理服務需要讀寫。安全團隊要求：存取必須只透過 AWS 網路、不經過 Internet；只有簽證處理服務能存取；即使有人誤改 bucket policy，沒有額外的金鑰權限也無法讀取內容。

哪個方案最符合需求？

- A. 為簽證處理服務使用只授予該 bucket 所需動作的 IAM role；在 VPC 建立 S3 gateway endpoint；bucket policy 拒絕不是來自該 endpoint（`aws:SourceVpce`）的請求；物件使用 customer managed KMS key 的 SSE-KMS 加密，key policy 只允許該 role 使用
- B. 為簽證處理服務建立 IAM user 並把 access key 存在 instance 的設定檔中；bucket 啟用 SSE-S3 預設加密
- C. 讓簽證處理服務經由 NAT Gateway 存取 S3；bucket policy 只允許 NAT Gateway 的 Elastic IP 作為來源
- D. 啟用 S3 Block Public Access 並把物件設為 SSE-S3 加密；所有開發人員共用一個具有 S3 完整權限的 role 以方便除錯

> [!answer]- 答案：A
> **A ✓** 三層各自獨立：身份層用最小權限的 IAM role；網路層用 gateway endpoint 讓流量留在 AWS 網路內，並以 `aws:SourceVpce` 拒絕其他路徑；資料層用 customer managed KMS key，即使 bucket policy 被誤改，沒有 key 使用權限的人仍無法解密內容（第 6、12、15 章）。
>
> **B ✗** 長期 access key 存在設定檔有外洩風險，應改用 role；SSE-S3 的金鑰由 S3 管理，有 S3 讀取權限就能取得明文，無法提供「需要額外金鑰權限」這一層。
>
> **C ✗** 經由 NAT Gateway 存取 S3 會走 S3 的公開 endpoint，不符合「不經過 Internet 路徑」的要求，還會產生 NAT 處理費；Elastic IP 也無法區分同一 VPC 內的其他服務。
>
> **D ✗** Block Public Access 只能防止公開存取，無法限制內部人員；共用完整權限的 role 違反最小權限，也讓稽核無法分辨是誰存取了資料。
>
> **考點**：SAA-1.1、SAA-1.3｜身份、網路、資料三層安全

### 練習 54-6｜SAA｜單選｜監控業務結果

週末期間，Wanderly 的訂房數比上週同期少了 40%，但 CloudWatch 上的 EC2 CPU、ALB 5xx 錯誤數與 Aurora 連線數都正常，沒有任何告警。事後發現金流商的 API 開始拒絕交易，應用程式顯示錯誤頁面並回傳 HTTP 200。團隊希望下次能在客戶大量反映之前就自動發現這類問題。

哪個做法最有效？

- A. 把 EC2 CPU 告警門檻從 80% 降低到 50%，並為每台 instance 啟用 detailed monitoring
- B. 為 ALB 的 4xx 與 5xx 錯誤數設定更敏感的告警，並把 ALB access logs 送到 S3
- C. 由應用程式發布「每分鐘付款成功數」與「付款成功率」的 custom metric 並設定告警，再建立 CloudWatch Synthetics canary 定期以測試帳號走完搜尋、選房與付款流程
- D. 啟用 AWS CloudTrail 的 data events，記錄所有對 S3 與 Lambda 的 API 呼叫

> [!answer]- 答案：C
> **A ✗** 這次事件中資源完全健康，CPU 不會因為交易被拒而升高；更敏感的資源告警只會帶來更多誤報。
>
> **B ✗** 應用程式回傳的是 HTTP 200，ALB 看不到任何錯誤，再敏感的 4xx／5xx 告警也不會觸發。
>
> **C ✓** 這是模式 9：直接監控業務結果。付款成功率下降會立即反映在 custom metric 上；Synthetics canary 主動模擬使用者走完整個流程，在真實使用者流量少的時段也能發現問題（第 36 章）。
>
> **D ✗** CloudTrail 記錄的是 AWS API 的呼叫紀錄，用於稽核誰做了什麼操作，不會記錄應用程式與外部金流商之間的業務結果。
>
> **考點**：SAA-2.2｜observability 跟隨業務結果

### 練習 54-7｜SAP｜單選｜不依賴 control plane 的 Region failover

Wanderly 在東京（primary）與新加坡兩個 Region 運作訂房系統，資料層使用 Aurora Global Database。目前的 DR runbook 是：東京發生大範圍事件時，由維運人員執行腳本，在新加坡用 CloudFormation 建立 ECS service 與 ALB，再呼叫 Route 53 API 修改記錄指向新的 ALB。演練顯示整個流程需要 90 分鐘，且步驟依賴多個在事件中可能變慢的 API。業務要求 RTO 15 分鐘，且 failover 機制在東京完全無法使用時仍能可靠執行。

哪個方案最符合需求？

- A. 把 runbook 腳本改寫成 Lambda function，部署在東京 Region，由 CloudWatch alarm 觸發後自動執行原本的步驟
- B. 在新加坡預先以 warm standby 運作縮小規模的 ECS service 與 ALB，並設定 Auto Scaling；使用 Route 53 ARC routing control 搭配 failover 記錄切換流量，同時把 Aurora Global Database 的 failover 步驟納入演練過的 runbook
- C. 在新加坡保存最新的 CloudFormation template 與 container image，事件時改由另一位維運人員手動在 console 執行，以避免腳本錯誤
- D. 把兩個 Region 的 ALB 都放進同一個 Route 53 simple routing 記錄，讓 DNS 用戶端自行選擇可用的 Region

> [!answer]- 答案：B
> **A ✗** 把腳本自動化並沒有改變它依賴的 control plane 操作，仍需在事件中建立資源；更嚴重的是 Lambda 部署在東京，東京無法使用時觸發與執行都會失敗。
>
> **B ✓** 這是模式 7 與模式 10 的組合。新加坡平時就有運作中的容量，failover 時只需要擴展而不是從零建立；Route 53 ARC routing control 提供高可用的 data plane 切換，搭配 failover 記錄把流量移到新加坡。Aurora Global Database 讓資料持續複寫，RPO 通常在秒級，整體可以達到 15 分鐘的 RTO（第 34、42 章）。
>
> **C ✗** 改成手動操作更慢也更容易出錯，而且仍然依賴事件中的 control plane 建立資源，無法達到 15 分鐘 RTO。
>
> **D ✗** Simple routing 不做 health check，DNS 用戶端可能持續拿到東京的位址；這也不是受控的 active-passive failover，無法保證流量只送往健康的 Region。
>
> **考點**：SAP-2.2、SAP-3.4｜control plane 與 data plane 分離的 failover

### 練習 54-8｜SAP｜單選｜以 cell 限制 blast radius

Wanderly 對旅行社夥伴提供多租戶訂房 API，共有 3,000 個租戶，所有租戶共用一組 ECS service、一個 Aurora cluster 與一個 SQS queue。過去一季發生兩次全面中斷：一次是某租戶的大量匯入塞滿 queue，所有租戶的訂單都被延遲；另一次是一個錯誤的部署同時影響所有租戶。公司要求單次故障最多影響約 10% 的租戶，並維持單一的對外 API 網址。

哪個方案最符合需求？

- A. 把每個租戶放進獨立的 AWS 帳號，套用相同的 SCP，並繼續使用目前共享的 ECS service、Aurora cluster 與 SQS queue
- B. 把 Aurora 升級到更大的 instance class，並把 SQS queue 的 visibility timeout 延長，讓大量匯入不會影響其他租戶
- C. 為每個租戶在 SQS 訊息中加入 tenant ID 屬性，並在 CloudWatch dashboard 上依租戶分組顯示指標
- D. 建立約 10 個 cell，每個 cell 有自己的 ECS service、Aurora cluster 與 SQS queue；以輕量的 routing 層依租戶 ID 對應到固定 cell，部署時一次更新一個 cell 並在健康指標正常後才繼續

> [!answer]- 答案：D
> **A ✗** 帳號是治理與權限邊界，但題目中的 runtime 資源仍然全部共享，大量匯入與錯誤部署仍會影響所有租戶。帳號隔離不會自動切分應用程式的資料與流量。
>
> **B ✗** 更大的資料庫規格只能延後問題發生，共享的 queue 與部署仍讓每次故障影響全部租戶；visibility timeout 與租戶之間的隔離無關。
>
> **C ✗** 加上 tenant ID 只是讓觀測更細，並沒有改變任何資源的共享方式，不能限制故障範圍。
>
> **D ✓** 這是模式 4 的 cell-based architecture。每個 cell 擁有自己的運算、資料與 queue，一個租戶的大量匯入最多影響同一個 cell 約 10% 的租戶；逐 cell 部署讓錯誤版本在第一個 cell 就被發現並停止。Routing 層只負責依對應表轉送，保持單一對外網址（第 35 章）。
>
> **考點**：SAP-2.4、SAP-3.4｜cell-based architecture 限制 blast radius

### 練習 54-9｜SAP｜單選｜依 RTO 與 RPO 選擇 DR 策略

Wanderly 的會員積點系統在東京 Region 運作，使用 Aurora MySQL、ECS on Fargate 與 ALB。業務評估後要求：Region 故障時 RTO 4 小時、RPO 15 分鐘。這個系統的營收影響有限，財務部門要求在滿足 RTO 與 RPO 的前提下，選擇成本最低的 DR 方案。團隊已經用 CloudFormation 管理所有基礎設施，並定期演練從 template 建立整個環境，約需 1 小時。

哪個方案最符合需求？

- A. 使用 Aurora Global Database 在新加坡建立 secondary cluster 持續複寫資料，並把 container image 複寫到新加坡的 ECR；平時不在新加坡運作 ECS 與 ALB，事件時以 CloudFormation 建立應用層並切換 DNS
- B. 每天以 AWS Backup 建立 Aurora snapshot 並複製到新加坡，事件時從最新 snapshot 還原並以 CloudFormation 建立應用層
- C. 在新加坡建立與東京同規模的完整環境，兩個 Region 同時服務流量，並使用 Route 53 latency routing
- D. 在東京把 Aurora 改為跨三個 AZ 的部署並增加 Aurora Replicas，作為 Region 層級的 DR 方案

> [!answer]- 答案：A
> **A ✓** 這是 pilot light：資料層以 Aurora Global Database 持續複寫，RPO 通常在秒級，遠優於 15 分鐘；應用層平時不運作，事件時用已演練過、約 1 小時可完成的 CloudFormation 建立，加上資料庫 failover 與 DNS 切換，仍在 4 小時的 RTO 之內。平時只需支付 secondary cluster 與複寫的費用，是滿足限制下最便宜的方案（模式 10、11）。
>
> **B ✗** 每天一次的 snapshot 代表最多遺失 24 小時的資料，無法滿足 15 分鐘的 RPO。它很便宜，但先檢查限制就會被刪掉。
>
> **C ✗** Multi-site active-active 能達到接近零的 RTO 與 RPO，但需要完整規模的雙 Region 環境，並處理雙 Region 寫入的一致性，成本遠高於需求，違反成本最低的目標。
>
> **D ✗** 增加 AZ 與 replicas 提高的是 Region 內的可用性，整個東京 Region 無法使用時這些資源會一起失效，不是 Region 層級的 DR。
>
> **考點**：SAP-2.2、SAP-1.5｜RTO／RPO 決定 DR 策略

### 練習 54-10｜SAP｜選兩項｜依依賴關係規劃遷移 wave

Wanderly 併購的旅行社有 300 台 VM，資料中心租約在 18 個月後到期且不能延長。現有系統包括 Oracle 訂位資料庫、十多個頻繁呼叫該資料庫的應用程式、Windows 檔案伺服器，以及幾個已經沒有使用者的舊報表系統。Wanderly 已建好 landing zone，並以 Direct Connect 連接資料中心。第一版計畫依照「伺服器作業系統類型」分成 wave，結果測試時發現已搬上 AWS 的應用程式查詢地端 Oracle 的延遲大幅增加。

哪兩個做法最能改善遷移計畫？（選兩項）

- A. 在遷移前先把所有應用程式重寫成 serverless 架構，以一次到位的方式完成現代化
- B. 使用探索工具收集伺服器之間的網路連線，建立依賴關係圖，把頻繁通訊的應用程式與它們依賴的 Oracle 資料庫規劃在同一個 wave 切換
- C. 依伺服器數量把 300 台 VM 平均分成 10 個 wave，每個月搬一個 wave
- D. 先把所有應用程式搬到 AWS，Oracle 資料庫留在地端直到最後一個月，再單獨搬遷
- E. 依 7Rs 分類每個系統：沒有使用者的報表系統 retire，大部分應用程式先以 Application Migration Service rehost 以趕上租約期限，Oracle 以 DMS full load 加 CDC 搬遷以縮短切換停機時間

> [!answer]- 答案：B、E
> **A ✗** 300 台 VM 在 18 個月內全部 refactor 風險極高，幾乎不可能趕上租約期限。期限緊時的常見做法是先 rehost，搬上 AWS 後再逐步現代化（第 46 章）。
>
> **B ✓** 這是模式 12 的核心：遷移順序要依依賴關係圖決定。頻繁呼叫 Oracle 的應用程式若和資料庫分在不同 wave，原本機房內的低延遲呼叫就會變成跨 Direct Connect 的呼叫，這正是測試中出現的問題（第 44 章）。
>
