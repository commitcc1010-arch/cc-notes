# 第 14 章　Measuring Engineering Productivity without Gaming

> [!abstract] 本章地圖
> **核心問題**：要怎麼知道一個工程組織真的變好了，而不是只讓儀表板上的數字變漂亮？
>
> **你會學到**：
> - 在動手量測之前，判斷一個問題值不值得量、量完會導致什麼行動
> - 理解 Goodhart's law，並設計不容易被操弄的量測方式
> - 用 GSM（Goals／Signals／Metrics）從目標推導出指標，而不是從現成資料倒推目標
> - 用 QUANTS、DORA、SPACE、DevEx 等框架檢查量測是否只看到單一面向
> - 從部署紀錄計算 DORA 指標，並用對照組評估一項工具導入的效果
> - 評估 AI coding agent 的導入成效，避開「行數」「接受率」這類誤導性指標
>
> **前置知識**：第 9 章（心理安全）、第 12 章（Tech Lead 與 Manager）、第 13 章（Leading at Scale）
>
> **對應原書**：SWE 第 7 章〈Measuring Engineering Productivity〉

## 14.1 故事：一張「工程師生產力排行榜」

Harbor 長到 40 人的那一年，執行長在季會上問了一個問題：「我們的工程師一年內從 5 位變成 30 位左右，為什麼新功能上線的速度沒有跟著快上好幾倍？」工程經理 Kevin 答不出來。會後，財務部門的同事熱心地提議：「我們可以從 Git 拉資料，做一張每個工程師的 commit 數、程式碼行數和 PR 數的排行榜，就知道誰在拖慢進度了。」

同一個月，checkout 團隊開始試用 AI coding agent。供應商的儀表板顯示：建議接受率 35%，「AI 產生的程式碼占新增程式碼的 40%」。採購單位很高興，準備把這張截圖放進下一次的季會簡報，作為「導入 AI 提升 40% 生產力」的證據。

Kevin 把這兩件事拿去和 tech lead 美華、platform 團隊的志明討論。美華的第一個反應是：「如果真的用 commit 數排名，我明天就能讓 checkout 團隊的 commit 數翻三倍，每個 PR 拆成十個就好。但我們上線新功能的速度不會因此快一秒。」志明則提出另一個擔憂：「AI 產生的程式碼占 40%，那這 40% 裡有多少在一週內被改掉或 rollback？上個月 checkout 的 rollback 次數是前一個月的兩倍，沒有人把這兩件事放在一起看。」

Kevin 意識到真正的問題不是「要不要量」，執行長的問題是合理的，執行長確實需要知道錢花得值不值得。問題是**量什麼、怎麼量、量完要拿來做什麼**。量錯了東西，不只得不到答案，還會讓團隊開始為了數字而工作，把原本健康的行為扭曲掉。

這一章要回答 Kevin 的問題：如何建立一套量測方式，讓它能回答真正的問題、能指導投資決策，而且不會被操弄成一場數字遊戲。

## 14.2 為什麼要量，以及什麼時候不該量

### 量測是為了做決定

工程組織需要量測，最根本的理由是：**資源有限，必須做選擇**。Kevin 手上有一筆預算，可以拿來加人、買更快的 CI 機器、擴大 AI 工具的授權，或讓團隊花一季償還技術債。如果沒有任何資料，這些選擇只能憑感覺或憑誰的聲音比較大。

《Software Engineering at Google》第 7 章描述了 Google 如何處理這個問題：Google 有一個專門研究工程生產力的團隊，成員除了軟體工程研究者與一般軟體工程師，還包括具有社會科學背景（例如認知心理學、行為經濟學）的研究者。這個組成本身就說明了一件事：工程生產力不是單純的技術量測問題，它牽涉到人的行為、感受與動機，需要研究人類行為的方法。

### 先問：值得量嗎？

原書提出一個很實用的觀念：在投入資源量測之前，先**判斷這個問題值不值得量**。量測有成本：建立資料管線、設計問卷、分析資料都要時間，被量測的人也要付出注意力與信任。原書建議先回答幾個問題：

1. **你預期會得到什麼結果？為什麼？** 先寫下假設，避免看到資料後才編故事。
2. **如果資料支持你的預期，會採取什麼行動？**
3. **如果資料不支持你的預期，會採取什麼行動嗎？**
4. **誰會根據結果做決定？什麼時候做？**

第 3 個問題最有殺傷力。如果答案是「不管結果如何，我們都會照原計畫進行」，那這次量測就沒有意義，只是在為已經做好的決定找證據。Kevin 用這幾個問題檢查「工程師排行榜」的提議時發現：就算排出名次，Kevin 也不會因此開除排名最後的人（Kevin 很清楚，排名低的人裡有負責值班和帶新人的資深工程師），所以這份排行榜不會導致任何好的行動，只會帶來副作用。

原書也列出幾種不值得量的情況：目前根本負擔不起改變流程或工具，量了也無法行動；結果很快就會被其他因素淘汰（例如下個月就要換整套工具）；決策者已有強烈主見，而你不太可能拿出足夠且對的證據改變他們的想法；結果只會被當成好看的 vanity metric（虛榮指標），用來支持本來就要做的事；或者手上能取得的指標不夠精確，而且容易被其他因素干擾。

### 工程生產力為什麼特別難量

在工廠裡，生產力可以用「每小時生產幾個零件」來量，因為零件是一樣的。軟體工程的產出不是同質的：一個修好資料遺失 bug 的三行修改，可能比一個新增三千行的功能更有價值；一位資深工程師花一下午幫三個新人解開卡關，自己沒產生任何 commit，卻讓團隊整體前進了一大步。

更麻煩的是，軟體工程中很多最有價值的工作是「讓壞事不發生」：一次好的 code review 攔下的事故、一份設計文件避免的錯誤架構、一個刪除的功能省下的維護成本。這些東西很難被計數，因為你沒辦法計數一件沒有發生的事。所以 Kevin 學到的第一課是：**任何把工程師的價值簡化成單一數字的做法，都會系統性地低估一部分最重要的工作**。

## 14.3 Goodhart's Law：當指標變成目標

### 定義

經濟學家 Charles Goodhart 在 1970 年代提出一個觀察，後來被人類學家 Marilyn Strathern 濃縮成廣為流傳的一句話：「**When a measure becomes a target, it ceases to be a good measure.**」（當一個量測變成目標，它就不再是好的量測。）這就是 **Goodhart's law**。

背後的機制是這樣的：量測之所以有用，是因為它和我們真正在意的東西有關聯。commit 數和工程進展有一點關聯，因為做事的人通常會 commit。但當 commit 數變成考核標準，人們會找到「提高 commit 數但不增加進展」的方法，例如把一個變更拆成很多小 commit。關聯因此被破壞，指標不再代表原本的東西。

```text
  一開始：指標是觀察的窗口

  真正在意的東西 ───── 有關聯 ─────▶ 指標
  （交付使用者價值）                  （PR 數）

  變成目標之後：人們直接優化指標

  真正在意的東西        人的行為 ─────▶ 指標 ↑↑↑
  （沒有改變）          拆 PR、灌小修改
        ▲                    │
        └── 關聯斷了 ────────┘  指標上升，但不再代表價值
```

### 工程組織裡常見的操弄

Goodhart's law 在工程組織中無所不在，而且通常不是因為有人刻意作弊，而是人們合理地回應誘因：

| 被當成目標的指標 | 會出現的行為 | 被犧牲的東西 |
|---|---|---|
| 程式碼行數 | 寫冗長的程式、複製貼上、不願意刪除程式碼 | 可維護性；刪程式碼常常是最有價值的工作 |
| PR 或 commit 數 | 把一個變更拆成很多沒意義的小片段 | Review 的完整性；小 PR 本來是好事，被灌水後失去意義 |
| 關閉的 ticket 數 | 挑容易的 ticket，把大問題拆成很多小 ticket | 困難但重要的工作沒人做 |
| 測試覆蓋率 | 寫沒有 assertion 的測試，只為了讓程式碼「被執行過」 | 測試的實際保護能力（第 26 章） |
| 事故恢復時間 | 提早宣告事故結束，或把事故重新分類成「不算事故」 | 事故紀錄的真實性與後續學習（第 45 章） |
| Change failure rate | 不把出問題的部署標記為失敗，或改用「熱修」繞過紀錄 | 部署風險的可見度 |

最後兩項特別值得注意：連 DORA 這類經過研究驗證的好指標，一旦被當成考核目標，同樣會被操弄。問題不在於指標本身好不好，而在於**指標被如何使用**。

### 降低操弄的方法

既然 Goodhart's law 不可避免，量測設計的目標就是讓操弄變得困難、不划算、容易被發現：

- **量團隊與系統，不量個人。** 原書明確主張，生產力量測的目的是改善工程系統與流程，而不是評估個人。當指標被用在個人考核上，被量測的人有最強的動機去操弄它，也會開始避免做那些不被計數的共享工作，例如 code review、帶新人、處理值班。
- **用一組互相制衡的指標，而不是單一指標。** 如果同時看部署頻率與 change failure rate，靠拆小部署灌水會讓失敗率的分母變大，但失敗本身不會消失；靠不標記失敗來壓低 change failure rate，會在 rework rate 或事故紀錄上露出馬腳。這種用來偵測副作用的指標叫做 **counter-metric**（制衡指標）。
- **結合質化資料。** 數字可以被操弄，但很難同時操弄數字、問卷回答與訪談內容。當它們互相矛盾時，就是值得調查的訊號。
- **公開定義與用途。** 讓被量測的人知道量什麼、怎麼算、用來做什麼、不用來做什麼。不透明的量測會被懷疑，被懷疑的量測會被抵抗，第 9 章談的心理安全也會受損。
- **把指標當作觀察的起點，而不是結論。** 指標變差時，下一步是問「發生了什麼事」，而不是直接獎懲。

> [!warning] 常見誤解
> 「只要指標選得夠好，就不會被操弄。」任何指標，只要和獎懲直接連結，都會被優化到偏離原意。與其追求一個完美的指標，不如承認所有指標都是不完美的代理，並把它們放在一個鼓勵學習、而不是鼓勵表演的環境中使用。

## 14.4 GSM：從目標出發，而不是從資料出發

### 為什麼順序很重要

很多組織量測的方式是這樣的：先看手上有什麼資料（Git log、Jira、CI 紀錄），從裡面挑出容易計算的數字放上儀表板，然後再解釋這些數字代表什麼。這個順序的問題是，**容易取得的資料不一定和你在意的事有關**，而儀表板一旦做出來，大家就會開始盯著它，不管它量的是不是對的東西。

原書介紹的 **GSM 框架**（Goals／Signals／Metrics）把順序倒過來：

- **Goal**（目標）：你希望達成的結果，用不涉及量測方式的語言描述。例如「工程師能快速得到 code review 的回饋」。
- **Signal**（訊號）：如果目標達成了，你會觀察到什麼現象。訊號是你理想中想知道的事，不一定能直接量到。例如「工程師覺得等待 review 不再阻礙他們的工作」。
- **Metric**（指標）：訊號的可量測代理。例如「PR 從送出到第一則 review 回覆的時間中位數」。

```text
  Goal       工程師能快速得到 code review 的回饋，而 review 品質不下降
    │
    ├── Signal 1   等待 review 不再阻礙工作
    │     ├── Metric  PR 送出到第一次回覆的時間（p50、p90）
    │     └── Metric  問卷：「等待 review 多常讓你無法繼續工作？」
    │
    ├── Signal 2   Review 仍能攔下重要問題
    │     ├── Metric  上線後兩週內因 bug 被修改的 PR 比例
    │     └── Metric  抽樣 review 留言中屬於正確性／設計問題的比例
    │
    └── Signal 3   Review 負擔沒有集中在少數人身上
          └── Metric  每位 reviewer 每週 review 數量的分布
```

這張圖的關鍵在 Signal 2 與 Signal 3。如果 Harbor 只量「第一次回覆時間」，最快的改善方法是讓 reviewer 秒按 approve，速度變快了，品質卻崩壞了。GSM 強迫你在目標裡寫清楚「品質不下降」，並為它找訊號與指標，counter-metric 就自然出現了。

### 可追溯性

GSM 的另一個價值是 **traceability**（可追溯性）：每個指標都能往上追溯到它代表的訊號與目標。當有人問「為什麼我們要追蹤 reviewer 的工作量分布？」答案是清楚的：因為我們的目標包含「review 品質不下降」，而 review 集中在少數人身上會讓這些人疲於奔命、品質下滑。

反過來，沒有對應目標的指標就是可以刪除的候選。Kevin 檢查 Harbor 現有的工程儀表板，發現十二個圖表中有五個說不出對應哪個目標，例如「每週新增的程式碼行數」。這些圖表被刪除後，團隊討論儀表板的時間反而變得更有效率。

### 不是每個訊號都能量

GSM 允許一個訊號暫時沒有好的指標。原書強調，寫下目標與訊號本身就有價值：它讓團隊清楚知道自己「想知道什麼」，即使目前量不到，也比量錯東西好。例如「工程師對 codebase 的理解程度」很難量化，但寫下這個訊號，提醒團隊可以透過訪談或新人 onboarding 的回饋去了解它。

> [!example] 例子
> Harbor 的 search 團隊想知道「新的排序服務架構是否讓開發變得更容易」。用 GSM 寫下來：Goal 是「工程師能有信心地修改排序邏輯」；Signal 包括「修改排序的變更較少造成意外」「工程師覺得改動排序不再可怕」；Metric 是「排序相關變更的 rollback 率」與「季度問卷中對排序 codebase 的信心分數」。有了這張表，團隊在架構調整前後各量一次，就能回答原本只能靠感覺爭論的問題。

## 14.5 QUANTS：檢查有沒有漏掉的面向

### 五個面向

選指標時另一個常見的錯誤是只看某一個面向，例如只看速度。原書提供了一個檢查清單，叫做 **QUANTS**，提醒你在評估一項工程變化（例如導入新工具或新流程）時，至少考慮這五個面向：

| 面向 | 要問的問題 | Harbor 導入 AI coding agent 的例子 |
|---|---|---|
| **Q**uality of the code（程式碼品質） | 產出的程式碼品質如何？測試是否足夠、是否容易維護？ | AI 產生的程式碼在 review 中被要求修改的比例；上線後的缺陷 |
| **A**ttention from engineers（工程師的注意力） | 工程師能否專注？被打斷的頻率如何？ | 工程師是否花大量時間在檢查與修正 AI 建議上，反而更常被打斷 |
| I**n**tellectual complexity（智力複雜度） | 完成工作需要多少認知負擔？這些負擔是否必要？ | 理解 AI 產生的程式碼是否比自己寫的更費力 |
| **T**empo and velocity（節奏與速度） | 工程師完成工作有多快？ | PR 從開始到合併的時間；部署頻率 |
| **S**atisfaction（滿意度） | 工程師對工具與流程滿意嗎？ | 季度問卷中對 AI 工具的滿意度與信任度 |

QUANTS 的用法不是每次都要五個面向各選一個指標，而是作為「我們有沒有漏掉什麼」的檢查。Kevin 原本只打算看 Tempo（速度），用 QUANTS 檢查之後，才意識到 AI 工具可能在加快速度的同時，降低程式碼品質、增加審查負擔，而這些代價會在幾個月後以事故和技術債的形式出現。

### 原書的案例：readability 值不值得

原書用 Google 的 **readability** 制度說明這套方法如何應用。readability 是一種針對特定程式語言的認證：取得認證的工程師，自己的變更就滿足該語言的 readability 核准要求；沒有認證的人，變更除了一般的 code review，還需要一位具備該語言 readability 的 reviewer 核准（第 10 章介紹過這個制度）。這個制度顯然有成本：取得認證要時間，review 也可能因此變慢。問題是：它值不值得？

研究團隊沿著 QUANTS 的五個面向寫下目標，例如程式碼品質更好、更一致；工程師藉由這個過程學到 codebase 與最佳實務；有 readability 的工程師完成工作更快；工程師認為這個流程有價值。（在「注意力」這一項，研究團隊沒有設定目標，原書認為這也是可以接受的，不需要硬湊。）資料來自三個來源：工程師剛完成 readability 流程時填的問卷、每季的大型工程師問卷，以及開發工具的細部 log（例如 review、提交所花的時間）。整體結論是這個制度值得保留：工程師滿意並覺得有學到東西，log 也顯示具備 readability 的工程師 review 與提交得更快；研究同時找出了流程中的痛點，各語言的 readability 團隊據此讓流程更快、更透明。這個案例的重點不是結論本身，而是方法：**一個爭論已久、人人都有意見的制度，被轉成可以用證據回答的問題**。

## 14.6 DORA：軟體交付表現的四個（加一個）指標

### 從研究而來的指標

**DORA**（DevOps Research and Assessment）是一個長期研究軟體交付表現的研究計畫，從 2014 年起每年進行調查並發布報告，早期幾年的研究成果整理在 Nicole Forsgren、Jez Humble、Gene Kim 合著的《Accelerate》（2018）一書中。DORA 最廣為人知的是一組衡量軟體交付表現的指標，傳統上稱為**四大指標**（four key metrics）：

| 指標 | 定義 | 量的是什麼 |
|---|---|---|
| **Deployment frequency**（部署頻率） | 多久成功部署一次到 production | 吞吐量：能多常交付變更 |
| **Lead time for changes**（變更前置時間） | 從 commit 到該變更在 production 上執行所需的時間 | 吞吐量：一個變更要等多久才到使用者手上 |
| **Change failure rate**（變更失敗率） | 部署後造成服務降級、需要修補或 rollback 的比例 | 穩定性：每次變更的風險 |
| **Failed deployment recovery time**（失敗部署恢復時間） | 部署造成失敗後，恢復服務所需的時間 | 恢復能力：出錯後多快能修好 |

最後一項在早期報告中稱為 MTTR 或 time to restore service，2023 年改名為 failed deployment recovery time，把範圍收斂到「部署造成的失敗」，以和資料中心停電這類外部原因造成的事故區分。

2024 年的報告新增了第五個指標 **rework rate**（重工率，DORA 官方稱 deployment rework rate）：非計畫中、因為 production 事故而進行的部署占所有部署的比例。研究者原本把 change failure rate 視為「團隊要做多少重工」的代理，加入 rework rate 正是為了直接檢驗這一點。新的五指標模型把 deployment frequency、lead time 與 failed deployment recovery time 歸為**吞吐量**（throughput），change failure rate 與 rework rate 歸為**不穩定性**（instability）。注意 recovery time 在早期（2015 年起）的分組中屬於穩定性，在五指標模型裡則被放在吞吐量。Rework rate 補上了一個盲點：一個團隊可能從不標記「部署失敗」，卻不斷在發布後趕緊再發一個修補，這些修補會出現在 rework rate 裡。

### 最重要的研究結論：速度和穩定不是取捨

DORA 研究最常被引用、也最違反直覺的結論是：**在軟體交付上，速度和穩定性通常不是二選一**。表現最好的團隊往往同時有高部署頻率、短前置時間，以及低變更失敗率、快速恢復。

這個結論的直覺是：頻繁部署代表每次部署的變更很小，小變更比較容易 review、測試、定位問題與 rollback（第 19 章的 small batches、第 29 章的 continuous delivery 都建立在這個邏輯上）。反過來，一季只部署一次的團隊，每次部署都包含大量變更，出問題時很難找到原因，也很難回滾。所以「為了穩定而放慢部署」常常適得其反。

### 怎麼從資料計算

DORA 指標的好處是大部分可以從系統資料自動計算，不需要人工填報：

```text
資料來源                         可以算出
─────────────────────────────────────────────────────────────
版本控制（commit 時間）     ┐
CI/CD 系統（部署時間、結果） ├──▶ deployment frequency、lead time
                             ┘
事故系統（事故與部署的關聯）  ──▶ change failure rate、recovery time
部署標籤（計畫中／修補）      ──▶ rework rate
```

實務上最難的不是計算，而是**定義**。什麼算一次「部署」：每個服務分開算，還是一次發布多個服務算一次？什麼算「失敗」：只有觸發 rollback 的才算，還是任何需要後續修補的都算？lead time 從哪個 commit 開始算：第一個 commit 還是最後一個？這些定義沒有唯一正確答案，但必須寫下來、在團隊間一致，並在定義改變時註記，否則趨勢圖上的變化可能只是定義改了。這和第 32 章談 SLI 分母時的道理一樣。

### DORA 指標的正確用法

DORA 指標設計上是用來衡量**一個團隊或一個服務的交付系統**，而不是個人。它最適合的用法是：一個團隊用它觀察自己的趨勢，找出改善的方向（例如 lead time 很長，拆解後發現大部分時間花在等待人工核准）。

以下幾種用法則容易出問題：

- **跨團隊排名。** 一個負責金流的團隊和一個負責內部工具的團隊，合理的部署頻率本來就不同。拿它們直接比較，會鼓勵金流團隊用不安全的方式提高頻率。
- **作為個人或團隊的考核目標。** 這會直接觸發 14.3 節的 Goodhart's law：失敗不被標記、事故被重新分類。
- **只看平均值。** Lead time 的分布通常有很長的尾巴，平均值會被少數極端值拉偏，應該看中位數與 p90，並檢查長尾的成因。
- **忽略產品結果。** DORA 量的是交付系統的能力，不是交付的東西有沒有價值。一個每天部署十次、但做出的功能沒人用的團隊，DORA 指標可能很好看。

## 14.7 SPACE 與 DevEx：把人放回量測中

### SPACE：生產力有很多維度

DORA 指標聚焦在交付流水線，但工程生產力不只是交付。2021 年，Nicole Forsgren、Margaret-Anne Storey 等研究者發表了 **SPACE 框架**，主張開發者生產力至少有五個維度：

| 維度 | 意思 | 可能的量測方式 |
|---|---|---|
| **S**atisfaction and well-being（滿意度與身心狀態） | 工程師對工作、工具、團隊是否滿意，是否有過勞跡象 | 問卷、離職率、值班負荷 |
| **P**erformance（成果） | 工作的結果，例如品質、可靠性、對使用者的影響 | 缺陷率、SLO 達成情況、功能使用率 |
| **A**ctivity（活動量） | 完成的動作數量，例如 commit、PR、部署 | 系統資料 |
| **C**ommunication and collaboration（溝通與協作） | 資訊流動與合作的品質 | Review 品質、文件被查找的容易程度、跨團隊協作的問卷 |
| **E**fficiency and flow（效率與心流） | 工作是否能順暢進行，不被等待與打斷阻礙 | 等待時間、被打斷的次數、可專注的時間 |

SPACE 的核心建議是：**不要只用一個維度衡量生產力，至少同時看三個維度，並且至少包含一個來自工程師自身感受的量測**（例如問卷）。特別要注意的是 Activity：它最容易量（Git log 裡都有），也最容易被誤用。活動量本身不是壞的資料，它可以幫助理解發生了什麼，但單獨用活動量判斷生產力，就會回到 14.1 節的排行榜問題。

### DevEx：影響生產力的三個因素

SPACE 告訴你「生產力有哪些維度」，2023 年 Abi Noda、Margaret-Anne Storey、Nicole Forsgren、Michaela Greiler 提出的 **DevEx**（Developer Experience，開發者體驗）框架，則聚焦在「什麼因素影響開發者的日常工作」，歸納為三個維度：

- **Feedback loops**（回饋迴路）：工程師做了一個動作之後，多快能得到結果。CI 要跑 40 分鐘、code review 要等兩天、在本機啟動服務要十分鐘，都是緩慢的回饋迴路。
- **Cognitive load**（認知負荷）：完成工作需要記住、理解多少東西。文件不全、工具難用、系統過度複雜，都會提高認知負荷。
- **Flow state**（心流狀態）：工程師能否進入並維持深度專注。頻繁的會議、Slack 干擾、不明確的任務，都會破壞心流。

```text
  DevEx 三個維度與 Harbor 的觀察

  Feedback loops      CI 平均 38 分鐘；review 第一次回覆中位數 1.5 天
        │                    ↓ 工程師同時開三個 PR 等結果，切換成本高
  Cognitive load      checkout 有 4 種重試寫法、文件三年沒更新
        │                    ↓ 新人要問人才知道該用哪一種
  Flow state          每人每週平均 14 小時會議，干擾集中在上午
                             ↓ 整塊可專注的時間只剩週五下午
```

DevEx 的實用之處在於，這三個維度都直接指向可以改善的行動：回饋迴路慢，就投資 CI 速度與 review 流程；認知負荷高，就整理文件、統一做法（第 13 章的平台化）；心流被破壞，就保護專注時間（第 13 章的干擾輪值）。這比一個籠統的「生產力分數」更容易轉成行動。

### 框架之間的關係

這些框架不是互相競爭，而是看同一件事的不同角度：

| 框架 | 最適合回答 | 主要資料來源 |
|---|---|---|
| GSM | 「我們該量什麼？」（方法） | 依問題而定 |
| QUANTS | 「評估這項變化時有沒有漏掉面向？」（檢查清單） | 混合 |
| DORA | 「我們的軟體交付系統表現如何？」 | 系統資料為主 |
| SPACE | 「生產力有哪些維度，我們是否只看了一個？」 | 系統資料加問卷 |
| DevEx | 「是什麼在阻礙工程師的日常工作？」 | 問卷為主，系統資料為輔 |

Kevin 最後的做法是：用 GSM 決定要回答的問題，用 DORA 量交付系統，用 DevEx 問卷了解工程師的阻礙，用 QUANTS 與 SPACE 檢查有沒有漏看的面向。

## 14.8 質化與量化：讓數字和人說的話互相檢驗

### 為什麼兩者都需要

系統資料（log、Git、CI、部署紀錄）的優點是客觀、可以自動收集、可以看長期趨勢；缺點是它只能看到被系統記錄的東西，而且無法告訴你「為什麼」。問卷與訪談的優點是能捕捉感受、原因與系統看不到的工作；缺點是有回憶偏差、回應偏差，而且容易被問題的寫法影響。

兩者結合的方法叫做 **triangulation**（三角驗證）：用多種有不同偏差的資料來源觀察同一件事。當它們一致時，你對結論更有信心；當它們矛盾時，矛盾本身就是最值得調查的地方。

原書提到一個重要的做法：**用工程師的感受來驗證指標是否有意義**。如果 log 資料顯示某個流程很快，但工程師普遍覺得它很慢，可能是指標的定義有問題（例如只量了自動化的部分，漏掉了等待人工核准的時間），也可能是工程師的感受來自別的原因。無論哪一種，都比只看其中一邊更接近真相。

### 好的問卷怎麼寫

Harbor 開始做每季一次的工程師問卷，美華和志明在設計時學到幾件事：

- **問具體的經驗，不問抽象的評價。** 「過去兩週，你有幾次因為等待 CI 結果而切換去做其他事？」比「你對 CI 滿意嗎？」更能指向行動。
- **保持題目穩定。** 每季用相同的題目，才能比較趨勢；改了題目就要註記，就像 DORA 指標改定義一樣。
- **保護匿名並公開用途。** 說清楚結果只以團隊層級呈現、人數少於五人的團隊不單獨呈現、不會用於個人考核。否則回答會變成表演。
- **一定要回饋結果。** 問卷做完沒有任何行動，下一次的回應率與誠實度都會下降。Harbor 每次問卷後會公布「我們聽到了什麼、決定先處理哪兩件事」。

### 分群與分布

整體平均值經常隱藏最重要的訊息。Harbor 的整體 PR review 等待時間中位數是 6 小時，看起來還好；但分群之後發現，新進三個月內的工程師中位數是 26 小時，因為他們不知道該找誰 review，也不好意思催。這個問題在整體數字中完全看不到，卻是 onboarding 體驗的重大缺口。

常見的分群方式包括：團隊、年資、時區、變更類型（功能、修補、重構）、服務的成熟度。看分布時，除了中位數，也要看 p90 與最長的幾個案例，並抽樣打開那些案例本身。一個等了五天的 PR，打開來看往往比任何統計圖更能說明問題出在哪裡。

### 基準線與比較

要說「變好了」，必須有比較的對象。最基本的是**前後比較**：導入某項改變之前量一段時間，導入之後再量一段時間。但前後比較有一個大問題：同一段時間內，其他事情也在變化。如果 Harbor 在導入 AI 工具的同一個月也升級了 CI 機器，lead time 變短是誰的功勞？

更可靠的做法是加入**對照組**：找一個相似、但沒有導入這項改變的團隊，同時觀察兩組的變化。兩組變化的差異，才比較接近這項改變本身的效果。這種方法叫做 **difference-in-differences**（差異中的差異），是下一節程式的核心。最嚴謹的是隨機分派哪些團隊或個人先導入（隨機對照實驗），但在 40 人、30 位工程師的組織裡常常不實際，分階段導入加上對照組已經能排除很多錯誤歸因。

## 14.9 動手寫：從部署紀錄算 DORA，並評估一次 AI 導入

下面的程式模擬 Harbor 的情境：checkout 團隊（pilot）導入 AI coding agent，search 團隊（control）沒有導入。同一段時間公司也升級了 CI，兩個團隊都會受影響。程式從部署紀錄計算五個 DORA 指標，再用差異中的差異估計 AI 導入本身的影響。

```python
import random
from statistics import median

WEEKS = 8


def make_log(rng, deploys_per_week, lead_hours, fail_p, rework_p):
    """產生一個團隊 8 週的部署紀錄。每筆是一次 production 部署。"""
    log = []
    for _ in range(int(deploys_per_week * WEEKS)):
        failed = rng.random() < fail_p
        log.append({
            "lead_h": rng.lognormvariate(0, 0.6) * lead_hours,   # commit → production
            "failed": failed,                                   # 造成降級、需要修補或回滾
            "recover_min": rng.uniform(20, 120) if failed else 0,
            "rework": rng.random() < rework_p,                  # 非計畫、為修 production 問題而做的部署
        })
    return log


def dora(log):
    failed = [d for d in log if d["failed"]]
    return {
        "deploys/wk": len(log) / WEEKS,
        "lead_h(p50)": median(d["lead_h"] for d in log),
        "CFR": len(failed) / len(log),
        "recover_min(p50)": median(d["recover_min"] for d in failed) if failed else 0.0,
        "rework": sum(d["rework"] for d in log) / len(log),
    }


rng = random.Random(42)
# pilot：checkout 團隊導入 AI coding agent；control：search 團隊照舊
teams = {
    ("pilot", "before"): make_log(rng, 10, 30, 0.08, 0.06),
    ("pilot", "after"): make_log(rng, 14, 20, 0.15, 0.13),
    ("control", "before"): make_log(rng, 9, 32, 0.08, 0.07),
    ("control", "after"): make_log(rng, 10, 27, 0.08, 0.07),
}
m = {k: dora(v) for k, v in teams.items()}

print(f"{'':18}{'deploys/wk':>11}{'lead_h(p50)':>12}{'CFR':>7}{'recover(p50)':>13}{'rework':>8}")
for (team, period), r in m.items():
    print(f"{team + ' ' + period:18}{r['deploys/wk']:>11.1f}{r['lead_h(p50)']:>12.1f}"
          f"{r['CFR']:>7.0%}{r['recover_min(p50)']:>12.0f}m{r['rework']:>8.0%}")

print("\n差異中的差異（pilot 的變化 − control 的變化）：")
for key in ("deploys/wk", "lead_h(p50)", "CFR", "rework"):
    d_pilot = m[("pilot", "after")][key] - m[("pilot", "before")][key]
    d_ctrl = m[("control", "after")][key] - m[("control", "before")][key]
    unit = "pp" if key in ("CFR", "rework") else ""
    scale = 100 if unit else 1
    print(f"  {key:12} pilot {d_pilot * scale:+6.1f}{unit}  control {d_ctrl * scale:+6.1f}{unit}"
          f"  → 歸因於導入的估計 {(d_pilot - d_ctrl) * scale:+6.1f}{unit}")

suggested, accepted = 5200, 1820
print(f"\n建議接受率 {accepted / suggested:.0%}：只說明工具被用了多少，上面那張表才說明交付發生了什麼。")
```

執行結果：

```text
                   deploys/wk lead_h(p50)    CFR recover(p50)  rework
pilot before             10.0        26.4     4%          69m      2%
pilot after              14.0        21.3    12%          65m     16%
control before            9.0        33.5     6%          50m      8%
control after            10.0        26.5     8%          71m      4%

差異中的差異（pilot 的變化 − control 的變化）：
  deploys/wk   pilot   +4.0  control   +1.0  → 歸因於導入的估計   +3.0
  lead_h(p50)  pilot   -5.1  control   -7.0  → 歸因於導入的估計   +1.9
  CFR          pilot   +8.8pp  control   +1.9pp  → 歸因於導入的估計   +6.8pp
  rework       pilot  +13.6pp  control   -4.6pp  → 歸因於導入的估計  +18.2pp

建議接受率 35%：只說明工具被用了多少，上面那張表才說明交付發生了什麼。
```

逐段解讀：

1. `make_log` 產生每次部署的紀錄。lead time 用 `lognormvariate` 產生，因為真實的 lead time 分布有長尾：大部分變更很快，少數會卡很久。這也是 `dora` 用中位數（p50）而不是平均值的原因。
2. `dora` 從部署紀錄算出五個指標。真實系統中，`failed` 與 `rework` 來自事故系統與部署標籤，`lead_h` 來自 commit 與部署的時間差。這裡最需要團隊共同定義的是 `failed` 與 `rework` 的判斷標準，14.6 節談過定義不一致會讓趨勢失去意義。
3. 看表格的前兩列，pilot 團隊只做前後比較會得到一個漂亮的故事：部署頻率從每週 10 次增加到 14 次，lead time 從 26.4 小時降到 21.3 小時。如果 Kevin 只拿這兩個數字去季會，結論會是「AI 讓交付變快」。
4. 加入 control 組後，lead time 的故事就不成立了：沒導入 AI 的 search 團隊 lead time 也降了 7 小時，降得比 pilot 還多。這主要是同期 CI 升級的效果。差異中的差異是 +1.9 小時，代表在 lead time 上看不出 AI 帶來額外的改善。
5. 穩定性指標說出了另一面：pilot 的 change failure rate 從 4% 升到 12%，rework rate 從 2% 升到 16%，而 control 沒有同樣的惡化。在真實團隊裡，這種組合常代表部署頻率的增加有一部分其實是「出問題後趕緊再部署修補」，這正是 rework rate 被加入 DORA 指標要捕捉的情況。（這個模擬為了簡化，沒有讓修補部署和失敗部署彼此連動，兩者是各自依機率產生的。）
6. control 的 rework rate 從 8% 降到 4%，並不是 search 團隊做了什麼改善。每組只有 72 到 112 筆部署，這種規模下幾個百分點的波動很可能只是隨機雜訊。這提醒我們：小樣本的指標要謹慎解讀，最好搭配信賴區間（見 14.13 節練習），或拉長觀察時間。
7. 最後一行的接受率 35% 是供應商儀表板上的數字。它回答的是「工程師接受了多少建議」，不是「交付變得更好或更差」。在這個模擬中，接受率看起來健康，交付穩定性卻在惡化。

這個模擬的參數是虛構的，結論不代表 AI 工具一定會降低穩定性。它要示範的是方法：**前後比較會把同期的其他變化誤算成導入效果，只看吞吐量會漏掉品質的代價，而工具自己的使用率指標回答不了交付的問題**。Kevin 拿到這樣的結果後，正確的下一步不是停用 AI，而是去調查：那些 rework 部署修的是什麼問題？AI 產生的 PR 在 review 時是否被看得比較鬆？測試是否跟上了？

## 14.10 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會出問題 | 具體情境 | 對策 |
|---|---|---|---|
| 用系統資料自動計算指標 | 定義不一致或資料不完整，產生假趨勢 | Harbor 換了部署工具，新工具把每個 canary 階段都記成一次部署，部署頻率一夜之間翻三倍 | 寫下指標定義與資料來源，工具或定義改變時在圖上註記，並重新計算歷史資料或切開比較 |
| 把 DORA 指標當成團隊目標 | Goodhart's law：失敗不被標記、事故被重新分類 | 為了達成「change failure rate < 5%」的季度目標，團隊開始把部署後的問題改成「新需求」處理 | DORA 指標用於團隊自我改善與趨勢觀察，不做跨團隊排名或考核；搭配 rework rate 與事故紀錄交叉檢查 |
| 依賴問卷了解工程師體驗 | 回應率低、回應偏差，或因不信任而美化回答 | 只有不滿的人回問卷，結果過度負面；或因擔心被追究而全部回「滿意」 | 保護匿名、公開用途、每次都回饋行動；結合系統資料交叉驗證 |
| 建立單一綜合分數 | 權重任意、隱藏 trade-off，大家開始優化分數 | 「工程健康分數 78 分」，但沒有人知道 78 分代表什麼、要改善什麼 | 保留多個維度並列呈現，讓 tension 可見；需要摘要時用「哪些面向在變好、哪些在變差」 |
| 量測一切以求完整 | 量測成本與干擾超過收益，工程師覺得被監視 | 追蹤每個人每天開了幾次 IDE、打了幾個字，引發反彈與離職 | 每個指標都要能追溯到 GSM 中的目標；沒有對應決策的指標就停止收集 |
| 前後比較評估新工具 | 同期的其他變化被誤算成工具的效果 | 本章的 CI 升級與 AI 導入同時發生 | 加入對照組、分階段導入，並延長觀察時間以涵蓋品質問題浮現的延遲 |

## 14.11 AI 時代：什麼變了？

AI coding agent 讓「量測工程生產力」這件事在三個方面變得更困難，也更重要。

**第一，活動量指標的意義被徹底改變。** 在 AI 之前，程式碼行數與 PR 數雖然不是好指標，至少和人類投入的時間有一點關聯。現在一個 agent 可以在幾分鐘內產生上千行程式碼，活動量和工程投入之間的關聯幾乎消失。「AI 產生了 40% 的程式碼」說明的是程式碼的來源，不是價值；建議接受率說明的是工程師接受了多少建議，不是這些建議後來有沒有被改掉、有沒有造成事故。這些指標可以用來了解工具的使用情況，但不能用來回答「工程是否變得更有效率」。

**第二，自我感受和實際表現可能不一致。** AI 工具常常讓人覺得自己更快了，因為打字的工作變少、卡住的時間變短。但整體交付時間取決於整個流程：review、測試、除錯、整合。DORA 2024 年的報告觀察到，AI 採用程度越高，受訪者回報的個人生產力、心流與工作滿意度越高；但在團隊層級，AI 採用與軟體交付的吞吐量與穩定性呈現負面關聯。研究機構 METR 在 2025 年發表的一項隨機對照實驗也有類似的落差：16 位有經驗的開源開發者在自己熟悉的大型 repository 上完成 246 個真實任務，每個任務隨機決定可否使用 AI 工具。允許使用 AI 時，完成時間平均反而多了約 19%；但開發者事後仍自認被 AI 加速了約 20%。METR 也強調，這只是 2025 年初的工具在單一情境下的結果，不代表 AI 對多數開發者或其他情境都沒有幫助。這些研究的情境各有限制，不能直接套用到每個組織，但它們共同指出一件事：**只靠問卷或只靠系統資料都不夠，必須兩者都看**。

**第三，瓶頸會移動。** 第 13 章談過，AI 讓寫程式碼變快之後，瓶頸會集中到 review、測試與決策。如果只量「寫程式碼」這一段，會看到很大的改善；量整條交付流程，可能發現 review 佇列變長、reviewer 疲勞增加。DORA 2025 年的報告把 AI 的主要角色描述為一個放大器（amplifier），會放大組織既有的長處與弱點：流程健全、平台成熟的組織會更好，流程本來就有問題的組織，問題也會被放大。所以評估 AI 導入時，量測範圍必須涵蓋整條交付流程，而不只是程式碼產生的那一刻。

Harbor 為 AI coding agent 的評估設計了以下的做法：

1. **用 GSM 定義目標**：目標是「在不降低穩定性與可維護性的前提下，縮短功能從構想到上線的時間」，而不是「提高 AI 使用率」。
2. **分階段導入，保留對照組**：先讓兩個團隊導入，另外兩個團隊作為對照，至少觀察一季，因為品質問題往往在幾週到幾個月後才浮現。
3. **量整條流程**：DORA 五個指標、review 等待時間與 reviewer 負荷、PR 大小分布、上線後兩週內被修改的程式碼比例。
4. **搭配 DevEx 問卷與訪談**：問工程師「理解與驗證 AI 產生的程式碼花了多少心力」「你對自己合併的 AI 程式碼有多少信心」。
5. **明確禁止的用法**：不用 AI 使用率或接受率評估個人績效，不把「AI 產生的程式碼比例」當成目標。

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 從版本控制、CI、部署與事故系統彙整 DORA 指標，並產生可重現的查詢 | 指標的定義（什麼算失敗、什麼算 rework）由團隊共同決定並記錄；AI 的計算結果要能追溯到查詢與原始資料 |
| 分析問卷的開放式回答，歸納主題並引用代表性原文 | 保留原始回答供人工抽查；樣本數過少的團隊不單獨呈現，避免從回答反推個人 |
| 比較導入前後與對照組的差異，標出樣本量不足或同期有其他變化的地方 | 歸因判斷（「這是 AI 的效果嗎？」）由負責的人決定，並公開說明不確定性 |
| 偵測指標之間的矛盾，例如部署頻率上升同時 rework rate 上升，提出需要調查的案例 | 矛盾是調查的起點，不能直接轉成對團隊或個人的獎懲 |
| 草擬季度工程報告的初稿 | 報告中的結論與建議由 engineering leader 署名負責；不得用 AI 使用量指標評估個人 |

> [!ai] AI 提醒
> 小心兩種相反的錯誤。一種是只看工具供應商提供的使用率與接受率，就宣稱 AI 提升了生產力；另一種是看到短期的穩定性下降，就認定 AI 沒有價值。導入新工具的初期，團隊還在學習怎麼使用、怎麼 review、怎麼調整測試策略，指標常常會先變差再變好。正確的做法是用一組平衡的指標持續觀察，並把觀察到的問題變成具體的流程調整，例如限制 AI 產生的 PR 大小、要求 PR 說明附上測試證據（第 16 章）。

## 14.12 專家怎麼想

- **「這個數字變了，我們會做什麼不同的事？」** 資深的工程領導者在建立任何指標前都會問這個問題。如果答案是「什麼都不會改變」，就不建立。這能省下大量建立與維護儀表板的成本，也避免組織被一堆沒人用的數字淹沒。
- **量測是為了學習，不是為了評分。** 有經驗的人會把指標當作對話的起點：「lead time 變長了，我們一起看看發生了什麼。」一旦指標被用來評分，人們就會開始管理指標，而不是管理工作，資料也會變得不可信。
- **任何時候看到一個指標，就問它的 counter-metric 是什麼。** 部署頻率配 change failure rate 與 rework rate，review 速度配 review 品質，AI 接受率配上線後修改率。只看一邊的改善，常常是把成本轉移到看不見的地方。
- **相信工程師的感受，但也檢驗它。** 當問卷和系統資料矛盾時，專家不會直接選一邊相信，而是把矛盾當成線索。工程師覺得 CI 很慢、但資料說 CI 很快，可能是資料漏量了某一段，也可能是 CI 的不穩定性讓人感覺它很慢。
- **打開具體的案例。** 統計數字能告訴你哪裡有問題，但只有打開那個等了五天的 PR、那次 rollback 的部署，才能知道問題是什麼。資深工程師在看儀表板時，一定會要求「給我看三個最極端的案例」。
- **對「生產力提升 X%」保持懷疑。** 無論是內部報告還是供應商宣稱，專家都會追問：和什麼比較？怎麼量的？同期還有什麼變化？品質指標怎麼了？能回答這些問題的數字才值得引用。

## 14.13 動手練習

1. 用 GSM 為你團隊的一個問題寫出完整的目標、至少三個訊號、每個訊號至少一個指標，並為其中一個指標寫出 counter-metric。檢查每個指標是否都能追溯到目標。
2. 列出你目前看得到的所有工程指標（儀表板、週報、工具內建報表），逐一用 14.2 節的四個問題檢查：如果這個指標變好或變差，會導致什麼行動？找出至少一個可以停止追蹤的指標。
3. 延伸 14.9 節的程式：用 bootstrap（從部署紀錄中重複隨機抽樣，例如 1,000 次）為差異中的差異估計 90% 信賴區間，看看 rework rate 的估計在目前的樣本量下有多不確定。再把 `WEEKS` 改成 24，比較信賴區間的寬度。
4. 再延伸程式：加入一個「AI 產生的 PR 在 review 中平均被要求修改幾輪」的欄位，並設計一個 counter-metric 規則：當部署頻率上升、但 rework rate 也上升超過某個門檻時，輸出「需要調查」的警示。
5. 設計一份 8 題以內的 DevEx 季度問卷，每題都對應到 feedback loops、cognitive load 或 flow state 之一，並寫出每題的結果會導向什麼可能的改善行動。說明你會如何保護匿名，以及問卷後如何回饋。
6. 想像你的組織要決定是否全面採購某個 AI coding 工具。寫一頁評估計畫，包含：要回答的問題、對照組設計、觀察多久、要看的 QUANTS 五個面向的指標，以及哪些結果會讓你建議「不採購」。

## 本章重點整理

- 工程組織需要量測，是因為資源有限、必須做選擇；量測的價值在於它能改變決策。
- 量測之前先問：預期什麼結果、結果正面或負面時各會採取什麼行動、誰在什麼時候決定；若結果不會改變任何行動，就不值得量。
- 軟體工程的產出不同質，許多最有價值的工作是「讓壞事不發生」，任何單一數字都會系統性低估這些工作。
- Goodhart's law：指標變成目標就不再是好指標；連 DORA 這類經過研究的指標，被當成考核目標時一樣會被操弄。
- 降低操弄的方法：量團隊與系統而非個人、使用互相制衡的指標、結合質化資料、公開定義與用途、把指標當作觀察起點而非結論。
- GSM 從目標推導出訊號，再找可量測的指標；每個指標都應能追溯到目標，沒有對應目標的指標可以刪除。
- QUANTS（品質、注意力、智力複雜度、節奏與速度、滿意度）是評估工程變化時避免只看速度的檢查清單。
- DORA 指標包括 deployment frequency、lead time for changes、change failure rate、failed deployment recovery time，2024 年加入 rework rate，並分成吞吐量與不穩定性兩組。
- DORA 研究最重要的結論是速度與穩定通常不是取捨，表現好的團隊兩者兼具；其指標適合團隊觀察自身趨勢，不適合跨團隊排名或個人考核。
- 指標的定義（什麼算部署、什麼算失敗）比計算更難，必須寫下、保持一致，改變時要註記。
- SPACE 主張生產力至少同時看三個維度，並包含工程師自身感受；DevEx 用回饋迴路、認知負荷、心流三個維度指出可改善的阻礙。
- 用 triangulation 讓系統資料與工程師感受互相檢驗；看分群與分布，打開極端案例，而不只看整體平均。
- 前後比較會把同期變化誤算成效果；加入對照組（差異中的差異）或分階段導入，才能較可靠地評估一項改變。
- AI 讓活動量指標失去意義，接受率與 AI 產生的程式碼比例只代表使用情況；評估 AI 導入要量整條交付流程的吞吐量與穩定性，並結合工程師的感受。

## 延伸問答

> [!question]- Q1. 為什麼「程式碼行數」不適合衡量工程師的生產力？如果有人說「至少它是客觀的」，你會怎麼回應？
> 程式碼行數衡量的是產出的體積，不是價值。同樣的功能，寫得簡潔的人行數更少；刪除不再需要的程式碼、重構以降低複雜度，行數甚至是負的，但這些常常是最有價值的工作。此外，code review、設計討論、帶新人、處理值班這些對團隊至關重要的工作，完全不會反映在行數上。一旦行數成為考核標準，人們就會寫冗長的程式、避免刪除程式碼，並減少不被計數的共享工作。
>
> 至於「客觀」：一個指標客觀，只代表它的計算方式不受主觀影響，不代表它量到了你在意的東西。一把很精準的尺用來量溫度，結果再客觀也沒有意義。而且在 AI coding agent 普及之後，行數和人類投入的關聯幾乎消失，它連作為活動量的參考價值都大幅降低了。

> [!question]- Q2. 請用 GSM 框架，為「新人能快速上手」這個目標設計訊號與指標，並說明你會如何避免它被操弄。
> Goal 是「新進工程師能在合理時間內獨立、有信心地為團隊的服務做出變更」。訊號可以包括：新人能早一點完成第一個有意義的變更；新人遇到問題時能找到答案而不必一直問人；新人對自己理解 codebase 的程度有信心；團隊其他成員帶新人的負擔是可承受的。對應的指標可以是：從報到到第一個合併到 production 的非瑣碎 PR 的天數；新人 PR 的 review 等待時間與修改輪數；入職 30 天與 90 天的問卷中對 codebase 理解與信心的自評；資深成員每週花在回答新人問題上的時間。
>
> 防止操弄的方法：「第一個 PR 的天數」容易被灌水（例如讓新人第一天就提交一個改錯字的 PR），所以要限定「非瑣碎」並由 TL 判斷，同時搭配問卷中的信心分數作為 counter-metric。這些指標只用於改善 onboarding 流程，不用於評估新人或帶新人的資深成員。

> [!question]- Q3. 你的主管想把四個團隊的 DORA 指標做成排行榜，每季表揚第一名的團隊。你會怎麼回應？
> 我會說明這個做法的兩個主要風險。第一，不同團隊的合理指標本來就不同：負責金流的團隊需要更謹慎的發布流程，部署頻率自然較低；負責內部工具的團隊可以更頻繁地部署。直接排名會鼓勵金流團隊用不安全的方式追求頻率。第二，一旦指標和表揚連結，Goodhart's law 就會開始作用：團隊可能不把出問題的部署標記為失敗、把事故重新分類，指標變好看了，實際的可靠性與資料的可信度卻下降。
>
> 我會提出替代方案：讓每個團隊用 DORA 指標觀察自己的趨勢，每季分享「我們發現了什麼瓶頸、做了什麼改善、結果如何」。表揚的對象是改善的過程與學習，而不是指標的絕對值。若主管想要跨團隊的視角，可以看整體趨勢與各團隊遇到的共同阻礙，那往往指向平台層級的投資機會。

> [!question]- Q4. 計算題：某團隊一個月內部署了 60 次，其中 6 次部署後造成服務降級需要修補或 rollback，另外有 9 次部署是為了修正 production 問題而臨時進行的。請計算 change failure rate 與 rework rate，並說明兩者為什麼不一樣。
> Change failure rate 是部署後造成失敗的比例：6 ÷ 60 = 10%。Rework rate 是非計畫中、為了修正 production 問題而進行的部署比例：9 ÷ 60 = 15%。
>
> 兩者量的是不同的事。Change failure rate 看的是「部署本身」有多少比例造成問題；rework rate 看的是「部署的動機」有多少比例是為了收拾問題。兩者會有重疊，例如一次失敗的部署之後緊接著的修補部署，前者算進 change failure，後者算進 rework。但 rework rate 也能捕捉到 change failure rate 看不到的情況：有些問題不是在部署當下發現，而是幾天後才被使用者回報，團隊沒有把原本的部署標記為失敗，卻做了好幾次修補部署。這也是 2024 年 DORA 加入 rework rate 的原因之一。在這個例子中，rework 比 failure 多，值得調查是否有部署失敗沒被正確標記，或有問題在部署後很久才被發現。

> [!question]- Q5. 問卷顯示工程師普遍覺得 CI 很慢，但 CI 系統的資料顯示 pipeline 中位數只要 12 分鐘。你會相信哪一邊？
> 兩邊都不直接相信，而是把矛盾當成調查線索。可能的解釋有幾種：一是指標漏量了某些部分，例如中位數 12 分鐘只算了成功的 pipeline，失敗後重跑、排隊等待 runner、flaky test 導致的重試都沒算進去；二是中位數掩蓋了長尾，某些服務或某些時段的 CI 要跑 40 分鐘，而工程師的感受被最痛的經驗主導；三是問題不在速度而在可靠性，CI 偶爾無故失敗，讓工程師對每次結果都不信任，感覺上就很慢。
>
> 具體做法是：把 CI 資料依服務、時段、成功或失敗分群，看 p90 與重跑次數；從問卷中找出抱怨最多的團隊，訪談幾位工程師，請他們描述最近一次覺得 CI 很慢的具體經驗；然後比對那幾次 pipeline 的實際紀錄。通常這樣做之後，會發現真正的問題比「CI 快或慢」更具體，也更容易改善。

> [!question]- Q6. 供應商宣稱「使用我們的 AI 工具，開發者的生產力提升 55%」。你在決定是否採購時，會問哪些問題？
> 首先問「生產力」是怎麼定義與量測的：是完成一個特定的、範圍明確的小任務的時間，還是真實專案中從需求到上線的整體時間？前者常常在受控實驗中表現很好，但不代表在有大量既有程式碼、複雜依賴與 review 流程的真實環境中有同樣效果。其次問比較的對象與研究設計：有沒有對照組？參與者是誰？是新手還是資深工程師？任務和我們的工作類型相似嗎？
>
> 再來問品質面向：這個數字有沒有同時量測缺陷率、上線後的修改、review 負擔？只量速度、不量品質的研究無法回答我們真正在意的問題。最後，最可靠的答案來自自己的組織：與其依賴外部數字，不如在內部設計一個有對照組、觀察至少一季、同時量吞吐量、穩定性與工程師體驗的試點，用自己的資料做決定。

> [!question]- Q7. Harbor 導入 AI coding agent 一季後，部署頻率上升 40%，但 review 等待時間增加一倍、資深工程師在問卷中回報的疲勞程度明顯上升。你會怎麼解讀，下一步做什麼？
> 這是典型的瓶頸轉移：AI 讓寫程式碼這一段變快了，產出的 PR 變多、可能也變大，但 review 的人力沒有增加，負擔集中到資深工程師身上。部署頻率上升看起來是好消息，但若 review 品質因為疲勞而下降，接下來幾個月很可能會看到 change failure rate 與 rework rate 上升。資深工程師的疲勞也是一個長期風險，可能導致離職，而他們正是組織中最難取代的人。
>
> 下一步我會先確認資料：PR 大小的分布是否變大？AI 產生的 PR 在 review 中被要求修改的輪數是否較多？穩定性指標是否已經開始惡化？接著從流程著手：限制單一 PR 的大小、要求 PR 說明附上 AI 產生部分的範圍與測試證據、讓 linter 與自動測試先攔下機械性問題、擴大有資格 review 的人數並平衡分配。也要和資深工程師談，了解他們覺得最耗費心力的是什麼。這些調整後持續觀察，目標是讓吞吐量的提升不以穩定性與人的健康為代價。

> [!question]- Q8. 面試題：如果你被要求為一個 40 人的工程組織建立生產力量測，你的前三個月會怎麼做？
> 第一個月，我不會先建儀表板，而是先找出組織真正想回答的問題。和工程主管、TL、工程師分別談，了解他們覺得哪裡卡、想做哪些投資決定。用 14.2 節的問題篩選：哪些問題的答案會實際影響決策？然後挑一到兩個最重要的問題，用 GSM 寫出目標、訊號與指標，並公開說明這些量測的用途，明確承諾不用於個人考核。
>
> 第二個月，建立最基本的量測：從現有系統自動計算 DORA 指標，寫清楚每個指標的定義；同時做第一次 DevEx 問卷，建立基準線。第三個月，把量化資料與問卷結果放在一起分析，找出一致與矛盾的地方，打開幾個極端案例深入了解，然後和團隊一起決定先改善哪一兩件事，並公開回饋。回答時我會強調，前三個月的成功標準不是做出漂亮的儀表板，而是讓組織因為這些資料做出了至少一個更好的決定，並且讓工程師相信這套量測是在幫助他們，而不是在監視他們。
