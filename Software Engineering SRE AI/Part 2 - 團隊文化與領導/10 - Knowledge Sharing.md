# 第 10 章　Knowledge Sharing、Readability 與 Bus Factor

> [!abstract] 本章地圖
> **核心問題**：當重要的知識只存在少數人腦中時，團隊要怎麼讓它流動、被找到、保持正確，並且在那個人休假或離職時不會停擺？
>
> **你會學到**：
> - 辨認知識孤島、單點故障、「鬼屋程式碼」等阻礙學習的模式
> - 定義並估算 bus factor，知道該優先處理哪些「只有一個人懂」的地方
> - 用好的提問與回答方式，讓一次問答變成整個團隊的知識
> - 依情境選擇文件、mentoring、office hours、tech talk、codelab 等分享方式
> - 為知識建立 single source of truth，並設計文件的 owner 與新鮮度檢查
> - 理解 readability 制度如何把 mentoring 規模化，並設計一套 onboarding 流程
> - 評估 AI 作為知識檢索工具的價值與風險
>
> **前置知識**：第 8 章（bus factor 的初次介紹、ownership）、第 9 章（心理安全）
>
> **對應原書**：SWE 第 3 章〈Knowledge Sharing〉；第 2 章關於 bus factor 的段落

## 10.1 故事：志明去爬山的那兩週

Harbor 的 payments 服務透過 mTLS（雙向 TLS，連線雙方都要出示憑證）連到外部金流商。用來連線的 client 憑證每年要更新一次，從 Harbor 第一年串接金流商開始，這件事都是由負責基礎設施、現在在 platform 團隊的志明處理的。今年十月，志明排了兩週假去走嘉明湖，山上沒有訊號。志明出發前在團隊頻道說：「應該沒什麼事，有問題就找美華。」

志明出發後第四天早上九點，所有信用卡付款開始失敗，錯誤訊息是 `certificate expired`。值班的美華知道憑證要更新，但從沒做過。美華在 wiki 搜尋「憑證」，找到三份文件：一份一年前寫的，步驟中提到的管理介面已經改版；一份在 payments repo 裡，寫到一半就停了；還有一份在某個已離職同事的個人筆記頁，內容和前兩份互相矛盾。大家試著聯絡志明，只得到「不在服務區」。

最後，美華和阿凱花了三個半小時，從程式碼、舊 commit 和金流商的文件拼湊出流程，才把付款恢復。這段時間 Harbor 幾乎沒有任何信用卡訂單。事後檢討時，大家發現志明其實沒有隱藏任何東西：每次有人問，志明都很樂意回答。問題是那些回答都在私訊裡，流程的關鍵細節（新憑證要先上傳到金流商後台、等十分鐘生效，才能切換）只存在志明的腦中。

同一個月，新加入 checkout 團隊的工程師花了六週才完成第一次部署。不是因為新人能力不足，而是開發環境的設定文件過期了，每一步卡住都要找人問，而能回答的人總是很忙。

工程經理 Kevin 在檢討會上把兩件事放在一起看：「憑證事故和新人上手慢是同一個問題。我們的知識是靠『問那個人』在運作的。8 個人的時候這行得通，40 個人的時候就不行了。」這一章要回答的，就是怎麼把「問那個人」變成任何人都能走的路。

## 10.2 知識為什麼會卡住

### 組織需要學習，而不只是個人需要學習

《Software Engineering at Google》第 3 章的出發點很直接：組織比網路上任何陌生人都更了解自己的問題領域，所以應該能回答大部分自己的問題。要做到這點，需要兩樣東西：知道答案的專家，以及把專家知識散布出去的機制。原書接著提醒，一對一請教專家永遠很有價值，但專家一去休假或轉組，團隊就可能措手不及。對一個成長中的團隊，問題不是「有沒有人懂」，而是「懂的人能不能讓其他人也懂，而且不必每次都親自出馬」。

這裡需要區分兩種知識。**明確知識**（explicit knowledge）可以寫下來：API 的參數、部署步驟、憑證更新的指令。**隱性知識**（tacit knowledge）很難寫下來：看到某個 log 就知道「這不正常」的直覺、在兩個設計方案間取捨的判斷、知道「這個模組改了會影響哪裡」的經驗。原書用的詞是 **tribal knowledge**（部落知識）：存在於「成員腦中知道的」與「已經寫下來的」之間的落差。明確知識靠文件與工具傳遞；隱性知識主要靠一起工作傳遞，例如 pairing、code review、一起值班。原書的立場是兩者互補：即使文件完美，人類專家仍能判斷哪些資訊適用於眼前的情況、文件是否還有效、答案該去哪裡找。好的知識分享制度兩者都要照顧。

### 阻礙學習的六種模式

SWE 第 3 章列出幾種讓知識卡住的典型模式。用 Harbor 的例子來看：

| 模式 | 意思 | Harbor 的例子 |
|---|---|---|
| 缺乏心理安全 | 怕在別人面前冒險或犯錯會被懲罰，於是不敢問、不敢承認不懂 | 新人卡住時不好意思一直問，自己試了兩天（第 9 章） |
| **資訊孤島**（information islands） | 各團隊各自累積知識，彼此不相通。表現為：知識碎片化、重複、各說各話（skew） | 三份互相矛盾的憑證文件；search 與 checkout 各自寫了一套 retry 工具 |
| **單點故障**（single point of failure） | 關鍵知識只在一個人身上，所有問題都流向這個人 | 憑證更新只有志明會 |
| **全有或全無的專業** | 團隊分成「什麼都懂的人」和「什麼都不懂的人」，中間沒有人 | 資深者忙到沒時間教，新人一直只能做邊緣任務 |
| **鸚鵡學舌**（parroting） | 模仿而不理解，照抄別人的程式或設定 | 每個新服務都複製一段 `sleep(3)`，沒人知道為什麼要等三秒 |
| **鬼屋程式碼**（haunted graveyards，直譯「鬧鬼的墓地」） | 大家出於恐懼與迷信而不敢碰的地方（通常是程式碼），因為「改了可能會出事」，但沒人說得出為什麼 | 舊的訂單對帳 script，三年沒人敢改 |

這些模式彼此強化。原書特別指出，單點故障常常出於好意：「我來幫你處理就好」在短期內最快，代價是團隊永遠學不會。單點故障讓懂的人越來越忙，越忙越沒時間教，於是形成全有或全無的專業；沒有人理解的程式碼只好被複製（鸚鵡學舌）或被迴避（鬼屋）。打破循環需要同時處理人（提問文化、mentoring）、內容（文件、單一來源）與流程（readability、onboarding）。接下來從最容易量化的單點故障開始。

## 10.3 Bus Factor：把「只有那個人知道」量化

### 定義

第 8 章介紹過的 bus factor（巴士係數，也叫 truck factor）問的是：最少要有幾個人突然不在（例如被巴士撞了），這個專案就會因為沒人懂而停擺？這裡要把它從比喻變成可以估算、可以改善的東西。

現實中「不在」很少是因為意外，更常見的是休假、生病、轉調、離職，或只是同時被三個事故拉走。志明去爬山，就讓 payments 憑證這個模組的 bus factor 從 1 變成 0。

### 怎麼估算

完整的 bus factor 很難精確計算，但可以用程式碼歷史做出有用的近似：

1. 對每個模組，找出「懂它的人」。常見的代理指標是過去一段時間 commit 或 code review 的比例，例如「貢獻超過 25% 的人」。
2. 模擬最壞情況：每次移除「目前懂最多模組的人」，看移除幾個人之後，超過一半的模組變成沒人懂。
3. 除了整體數字，特別看**關鍵路徑**：結帳、付款這些一旦停擺就影響營收的模組，只要其中一個的 bus factor 是 1，整個結帳流程的 bus factor 就是 1。

```text
       整體 bus factor = 3                  結帳關鍵路徑 bus factor = 1
  ┌─────────────────────────────┐      ┌──────────────────────────────────┐
  │ checkout/api   美華、阿凱    │      │ 使用者按付款                       │
  │ inventory      阿凱、阿哲    │      │   → checkout/api   （2 人懂）      │
  │ search/indexer 柏翰、志明    │      │   → inventory      （2 人懂）      │
  │ payments/*     志明          │      │   → payments/cert  （1 人懂）◀── 斷點│
  │ ...                          │      │   → 金流商                         │
  └─────────────────────────────┘      └──────────────────────────────────┘
```

左邊的整體數字看起來還可以：要同時少三個人，一半的模組才會沒人懂。右邊才是 Harbor 真正的風險：結帳路徑像一條串聯的鏈，任何一環只有一個人懂，整條鏈的韌性就由那一環決定。這和第 32 章「依賴的可用性相乘」是同樣的結構。

### 這個估算的限制

用 commit 歷史估計「誰懂」有明顯的盲點。寫了很多 commit 的人不一定懂設計意圖；做 code review 的人雖然沒有 commit，卻可能非常熟悉；有些關鍵知識根本不在程式碼裡，例如憑證更新要在金流商後台操作，git log 完全看不到。所以程式算出來的數字只是起點，必須搭配人工盤點：「這個模組出事時，你會打給誰？如果那個人不在呢？」

> [!warning] 常見誤解
> 「提高 bus factor 就是讓人可以被替換。」不是。提高 bus factor 的目的是讓關鍵的人**可以休假、可以專心做新的事、可以不必在半夜被叫醒**。志明是最大的受益者：如果有第二個人會更新憑證，志明就能真正放心去爬山。專家不會因此變得不重要，而是從「唯一能做事的人」變成「讓別人也能做事的人」，後者對組織的價值更高。

### 怎麼提高 bus factor

提高 bus factor 的方法，本質上都是讓第二個人**真正做過一次**：

- **Pairing 與 shadowing**：下次憑證更新時，志明帶著美華做，美華操作、志明在旁邊看；隔年反過來，由美華主導、payments 的小林在旁邊看。
- **輪調值班與任務**：讓不同人輪流負責例行操作，避免「每次都讓最熟的人做比較快」。
- **讓非專家 review**：模組的 code review 刻意加入一位不熟的人，對方提出的問題本身就會暴露缺少的文件。
- **演練文件**：請一個沒做過的人「只照文件」完成操作，卡住的地方就是文件的缺口（第 46 章的 game day 是更大規模的版本）。
- **自動化**：最好的知識分享有時是讓知識變得不需要。Harbor 後來把憑證更新寫成每月自動檢查、到期前 30 天自動開 ticket 並附上 runbook 連結（第 31 章）。

## 10.4 問問題與回答問題的文化

知識流動最小的單位是一次問答。一個團隊的提問與回答習慣，決定了知識是在私訊裡蒸發，還是累積成大家都能用的資產。

### 提一個好問題

好問題能讓回答者花最少時間給出正確答案，也讓之後搜尋到這個問題的人看得懂。一個實用的格式：

```text
【我想做什麼】把 checkout 的 retry 次數從 3 改成 5
【我遇到什麼】改了 config/retry.yaml，但 staging 的行為沒變
【我已經試過】確認 config 有部署到 staging（附 commit 連結）；重啟過服務
【我的猜測】是不是有別的地方覆蓋了這個設定？
【環境】staging，checkout v2.14
```

這個格式有兩個效果。對回答者來說，不必再來回追問背景；對提問者來說，寫到「我已經試過」時，常常就自己找到答案了。

**花多久時間自己找，再開口問？** 沒有標準答案，很多團隊用「時間盒」的經驗法則：自己先試一段固定時間（例如 15 到 30 分鐘），沒有進展就問。這條規則保護了兩邊：新人不會為了不想打擾別人而卡兩天，資深者也不會被「沒試過就問」的問題淹沒。對新人來說時間盒應該更短，因為他們缺少判斷「這是不是很快能解決」的經驗。

### 在公開的地方問

志明回答過很多次憑證的問題，但每一次都在私訊裡。私訊的答案只幫到一個人，而且無法被搜尋。在公開頻道問有三個好處：其他人也能回答，減少單點故障；有同樣疑問但不敢問的人也看到了答案；回答可以被搜尋、被整理成文件。SWE 第 3 章描述 Google 用群組聊天、郵件群組與內部問答網站（YAQS，「Yet Another Question System」，類似 Stack Overflow 的內部系統）來擴大提問的範圍。原書也提醒，在郵件群組問到答案後，要把答案貼回原討論串，因為之後一定有人會需要同樣的資訊。原則相同：**讓一次回答服務很多人**。

### 理解脈絡：改之前先問為什麼

遇到看起來沒道理的程式碼時，例如那段 `sleep(3)`，初學者常有兩種反應：直接刪掉，或原封不動照抄。第 7 章介紹過的 Chesterton's fence（切斯特頓的籬笆）在這裡同樣適用：不知道一段程式為什麼存在時，先弄清楚理由，再決定要不要拆。SWE 第 3 章也在知識分享的脈絡下提到這個原則，因為「去問」本身就是一次知識流動。

這不表示舊程式不能改，原書也承認舊設計可能真的是錯的，只是工程師面對陌生程式碼時，往往太快下「這很爛」的結論。重點是**改之前要先問**：理解脈絡之後，若改動仍然合理就去改；若不合理，就把理由寫下來給未來的讀者。阿凱去問了那段 `sleep(3)`，才知道它是為了等外部金流商的非同步通知；更好的做法是改成輪詢狀態。問完之後，阿凱把理由寫成一行註解，下一個人就不必再問了。

### 回答問題：把答案變成資產

資深者回答問題時，可以多做一步：**回答完後問自己「這個答案應該放在哪裡？」** 如果這個問題被問過兩次以上，它應該變成文件、FAQ、程式註解，或甚至一個更清楚的錯誤訊息。Harbor 後來訂了一條規則：在頻道裡回答一個「應該寫在文件裡」的問題時，回答者附上文件的連結；如果文件不存在，提問者負責把答案補進文件，回答者 review。這讓新人在提問的同時也在貢獻知識，而資深者每回答一次，同類問題就少一次。

回答的語氣同樣重要。原書引用 Recurse Center 的社交守則（不假裝驚訝、不說「嗯，其實……」、不在背後指揮、不帶隱微的歧視），第 9.7 節已經逐條說明；放在問答文化裡，它的意思很簡單：如果有人因為問了「簡單問題」而被嘲笑一次，整個頻道的人都會學到「以後別在這裡問」。

## 10.5 一對多的知識擴散

一對一的問答很有效，但無法規模化。SWE 第 3 章有一個小節標題對初階工程師特別重要：**你永遠有東西可以教**。原書的理由是，專業不是「新手或專家」二選一，而是每個人在不同領域各有深淺。原書也建議，第一次學某件事的時候，正是發現文件哪裡有缺漏的最好時機；剛把開發環境設定好的新人，正是最適合更新設定文件的人，因為對方剛剛才踩過每一個坑。下面是常見的一對多分享方式，各有適合的情境：

| 方式 | 適合什麼 | 不適合什麼 | Harbor 的用法 |
|---|---|---|---|
| **Mentoring**（指導） | 隱性知識、職涯問題、「該問誰」 | 大量重複的明確知識 | 每位新人有一位 onboarding buddy 與一位 mentor |
| **Office hours**（固定答疑時段） | 某個領域有很多零散問題、專家時間有限 | 需要長時間深入的問題 | platform 團隊每週二下午開放一小時，回答部署與 CI 問題 |
| **Tech talk／課程** | 複雜但穩定、需求持續存在的主題 | 很快會改變的細節 | 每月一次內部分享，錄影存檔，例如「checkout 的資料流」 |
| **Codelab**（引導式動手教學） | 需要動手做一遍才能理解的技能 | 純概念性的知識 | 「30 分鐘部署你的第一個服務到 staging」 |
| **文件** | 參考資料、步驟、設計理由 | 需要即時判斷的情境 | 每個服務的 README、runbook、ADR（第 7、17 章） |
| **電子報／公告** | 讓大家知道「有這個東西存在」 | 傳遞細節本身 | 每兩週一封工程週報，介紹新工具與事故學習 |
| **程式碼本身** | 慣例、範例、清楚的命名與錯誤訊息 | 解釋為什麼這樣設計 | 範例服務 `hello-harbor` 示範所有標準做法 |

SWE 第 3 章對「什麼時候值得開課」有一個很實用的判準：主題夠複雜、經常造成誤解；內容相對穩定，不會下個月就過時；有老師能在場回答問題時，學得比自己讀文件好；而且有持續的需求，不是只有一個人需要。不符合這些條件的主題，寫成文件或 codelab 通常更划算。

Google 有兩個常被提到的例子。一個是 **go/ links**：內部的短網址系統，讓任何人都能把 `go/deploy` 指向部署指南，大家在對話中直接說「看 go/deploy」，入口好記、目標可以隨時更新。另一個是 **Testing on the Toilet**：貼在廁所隔間裡的單頁電子報，每期介紹一個測試技巧。兩者的共同點是降低「找到」與「接觸到」知識的成本。Harbor 規模小，但同樣可以做：在內部 wiki 建立短網址，把最常用的十個入口固定下來。

## 10.6 Single Source of Truth：讓知識有一個家

### 為什麼需要「唯一的來源」

憑證事故中，美華找到三份文件，問題不是沒有文件，而是**不知道該相信哪一份**。當同一件事有多份副本，每份副本會隨時間各自漂移：有人更新了 A 卻忘了 B，第三份根本沒人記得存在。最後讀者要自己判斷哪份是對的，而在事故當下，這正是最不該讓人做的判斷。

**Single source of truth**（單一事實來源，也叫 canonical source）的意思是：每一種知識有一個被指定的家，其他地方需要時**連結**過去，而不是**複製**一份。這和資料庫正規化的道理一樣：同一個事實只存一次，更新時就不會不一致。SWE 第 3 章談的 canonical sources of information（例如全公司的開發者指南、go/ links、codelab）是這個原則在組織層級的版本。原書也提醒這種集中來源很昂貴，需要明確的 owner 與領域專家持續維護，最適合「全公司工程師都需要」的資訊；只和單一團隊有關的知識，放在團隊自己的文件就好。不論哪個層級，「同一件事只有一個家」的原則都成立。

### 知識的分層

把所有東西放在同一份文件裡也不對，那會變成沒人讀得完的巨型文件。比較好的結構是**薄入口、深來源**：

```text
              ┌──────────────────────────────┐
  入口層      │ go/payments（一頁服務地圖）  │  ← 新人與值班者的第一站
              │ owner、SLO、儀表板、聯絡方式  │
              └──────┬────────┬────────┬─────┘
                     │        │        │      只放連結，不複製內容
            ┌────────▼──┐ ┌───▼─────┐ ┌▼──────────┐
  說明層    │ 設計文件   │ │ runbook │ │ ADR        │  ← 為什麼這樣做、出事怎麼辦
            │（第 17 章）│ │（第 43章）│ │（第 7 章）  │
            └────────┬──┘ └───┬─────┘ └┬──────────┘
                     │        │        │
            ┌────────▼────────▼────────▼──────────┐
  事實層    │ 程式碼、測試、schema、設定、CI 腳本    │  ← 可以被執行、被驗證的真相
            └─────────────────────────────────────┘
```

由下往上讀。**事實層**是最可信的，因為它會被執行：測試會失敗、設定會生效。**說明層**解釋事實層沒辦法說清楚的東西：設計理由、取捨、出事時的判斷流程。**入口層**只負責讓人找到正確的說明與事實。三層之間的原則是：上層引用下層，不重抄下層；能放在事實層的就放在事實層，例如與其在文件裡寫「retry 次數是 3」，不如連到設定檔，因為設定檔不會過時。

### 文件需要 owner 與新鮮度

沒有 owner 的文件一定會過期，只是時間早晚的問題。每份重要文件至少要記錄幾項 **metadata**（關於文件本身的資料）：owner（人或團隊）、最後驗證日期、適用的系統版本、風險等級，以及若被取代時指向新文件的連結。這裡最重要的區分是「最後**驗證**日期」與「最後**編輯**日期」：修正錯字也會更新編輯日期，但只有「有人照著做過一遍並確認可行」才算驗證。

新鮮度要求應該依風險不同。出錯會造成事故的 runbook，每季至少演練一次；設計文件主要記錄當時的理由，即使系統後來改了，它作為歷史紀錄仍有價值，只要標明「已被某 ADR 取代」即可。10.10 節的第二段程式示範如何自動檢查這些規則。把文件放進 repository、和程式碼一起 review 的 **docs as code** 做法，會在第 17 章完整說明；這裡只要記得它的核心好處：改程式時，同一個 pull request 裡就能看到相關文件，忘記更新的機率大幅降低。

## 10.7 Readability：透過 Code Review 規模化 Mentoring

### Google 的 readability 制度

SWE 第 3 章用了相當篇幅介紹 Google 的 **readability**（可讀性認證）制度。在 Google，readability 指的不只是「程式好不好讀」，而是一套全公司標準化的 mentoring 流程，用來傳遞各程式語言的最佳實務，範圍包括語言慣用法、程式結構、API 設計、常用函式庫的正確用法、文件與測試。它的核心規則是：Google 的 code review 本來就是強制的，而每個變更還需要 **readability approval**，也就是一位擁有該語言 readability 的人核准（作者本身有 readability 就自動算數）。工程師取得 readability 的方式，是把日常工作的變更送進 readability 流程，由一群集中的 readability reviewer 針對各項能力給意見；隨著作者把慣例內化，收到的意見越來越少，最後「畢業」並正式取得 readability。

這個制度有一段有趣的起源。原書提到，Google 早期由第 3 號員工 Craig Silverstein 親自坐下來，逐行 review 每位新人的第一個主要 commit；公司成長到一個人顧不過來之後，覺得這件事有價值的工程師自願加入，才擴展成正式制度。原書寫作時，任一時間約有 20% 的 Google 工程師以作者或 reviewer 身分參與這個流程，readability reviewer 約占工程師的 1% 到 2%，全部是志願者，而且被期待把 review 當成指導與合作，而不是把關或對抗。

這個制度的本質是**標準化的 mentoring**。每個工程師都會被一群熟悉語言最佳實務的人，在真實的程式碼上反覆指導，直到慣例內化。它解決了幾個問題：慣例在數萬人之間保持一致；最佳實務不只寫在 style guide 上，而是在 review 中被「教」出來；而且因為 reviewer 來自全公司而不是自己的團隊，工程師會接觸到團隊之外的做法，避免資訊孤島。原書的說法是，它結合了文件（有可引用的出處）與人類專家（知道該引用哪一條）兩者的優點。

Readability 也有成本，原書直接列出：團隊裡沒有人具備 readability 時，必須找外部 reviewer，增加摩擦；需要 readability review 的作者可能要多跑幾輪 review；集中式的設計讓這個制度只能隨組織線性成長。原書也承認它有爭議，有些工程師認為它是不必要的官僚。Google 的回應是請內部的 Engineering Productivity Research 團隊做研究，原書描述的結論是：控制年資等因素後，有 readability 的作者送出的變更，review 與提交所需的時間在統計上顯著較短；完成流程的工程師中，大多數認為值得。同時，凡是能被靜態分析偵測的問題（例如行尾空白）交給工具，讓 reviewer 專注在「外部讀者看不看得懂」這類需要判斷的部分（第 15 章）。值得注意的是，這些研究結果來自 Google 自己的環境，不能直接推論到其他規模的組織。

### 小一點的組織怎麼借用

40 人的 Harbor 不需要完整的認證制度，但可以借用它的精神：

- **領域 steward**：每種語言或每個關鍵領域（例如資料庫 migration、payments）指定兩三位 steward，負責維護該領域的 review 指南，並在相關變更中擔任 reviewer。
- **Review 指南**：把 review 中反覆出現的意見整理成一份清單，例如「Python 服務的 timeout 一定要明確設定」「SQL migration 要先 expand 再 contract」（第 29 章），新人在提交前自己對照。
- **Review 是教學**：reviewer 的留言要說明理由與參考連結，而不只是「改掉」。好的留言是「這裡建議用 `with` 管理連線，否則例外發生時連線不會被釋放；範例見 hello-harbor 的 db.py」。
- **自動化先行**：凡是能用工具檢查的慣例，就交給工具，讓人類的 review 時間花在設計與正確性（第 15、16 章）。

Readability 的目標不是讓程式碼「漂亮」，而是讓**任何一個團隊成員都能讀懂、修改別人的程式碼**。這直接提高了 bus factor：當程式碼的寫法一致、慣例清楚，阿凱讀 payments 的程式時，不需要先學會志明個人的寫作風格。

## 10.8 Onboarding：把新人的第一個月當成產品來設計

### 為什麼 onboarding 值得投資

新人的上手時間是知識系統健康度最誠實的量測。Harbor 那位花了六週才第一次部署的新人，暴露的是：文件過期、環境難以設定、問題沒有固定的提問管道、沒有適合入門的任務。每一個問題都不只影響那一個人，每個新人都會再經歷一次。一個 40 人、每季加入五六個新人的團隊，onboarding 的品質直接決定團隊能多快成長。

### 一份 onboarding 計畫的結構

Harbor 重新設計後的 onboarding 計畫如下：

| 時間 | 目標 | 具體安排 | 完成的證據 |
|---|---|---|---|
| 第 1 天 | 能在本機跑起服務 | 依 codelab 設定環境；buddy 在旁協助 | 本機看到 hello-harbor 的首頁 |
| 第 1 週 | 完成第一個小變更並上線 | 從標記為 `good-first-issue` 的清單挑一個；走完 review、CI、部署 | 第一個 PR 部署到 production |
| 第 2–4 週 | 理解團隊負責的系統 | 閱讀服務地圖與設計文件；參加一次 design review；shadow 一次 on-call | 能畫出負責服務的架構圖並說明主要依賴 |
| 第 2 個月 | 獨立完成一個中型任務 | 由 mentor 協助拆解；在 office hours 提問 | 任務上線，並更新至少一份文件 |
| 第 3 個月 | 加入值班輪值 | 先與資深者 pair 值班，再獨立值班 | 處理過一次真實 alert，並更新 runbook |

幾個設計重點值得說明。**第一週就上線**是刻意的：它讓新人走完整條變更路徑（review、CI、部署、監控），在最早的時間暴露路徑上的障礙，也讓新人很早就有「我的程式在服務使用者」的成就感。**Buddy 和 mentor 分開**：buddy 是同團隊的同事，負責回答日常問題（「這個工具怎麼用」）；mentor 通常不是直屬主管，負責較長期的成長問題，新人可以安心問一些不想問主管的事。SWE 第 3 章描述 Google 的做法更進一步：為新人指派的 mentor 刻意不是同團隊成員、主管或 tech lead，職責明確包含回答問題，讓新人不必擔心佔用同事太多時間。**每個階段都有可觀察的證據**，而不是「讀完某些文件」，因為讀過不代表理解。

### 讓新人修補 onboarding

最有效的一條規則是：**每位新人都要把 onboarding 文件中卡住的地方修好**。新人是唯一能看見文件缺口的人，因為資深者早就忘了自己當初卡在哪裡。Harbor 在 onboarding 清單的最後一項寫著：「列出你卡住超過 30 分鐘的三個地方，並提交修改文件的 PR。」一年後，開發環境的設定時間從兩天縮短到兩小時，而這些改進大多是新人做的。

團隊可以追蹤幾個簡單的指標來看 onboarding 是否在改善：新人第一次部署到 production 所需的天數、第一個月內提問最多的主題、新人獨立值班前所需的時間。這些數字只用來改善流程，不應用來比較新人的能力（第 14 章談量測的陷阱）。

## 10.9 讓分享被看見：誘因與認可

即使有了好的工具與流程，如果分享知識在績效評估裡完全不算數，大家自然會把時間花在「會被看見」的工作上。寫文件、回答問題、帶新人這類工作，常常是隱藏的：它們讓別人變得更有效率，但貢獻者自己的產出看起來沒有增加。

SWE 第 3 章描述了 Google 的做法：把知識分享明確納入工程師的職涯期望，越資深的職級越被期待擴大別人的影響力；並提供由下而上的認可機制：任何員工都可以給另一位員工 **peer bonus**（同儕獎金，一筆小額獎金加上正式的認可紀錄），例如感謝對方長期在郵件群組回答問題；比 peer bonus 更輕量的則是 **kudos**（公開致謝）。原書強調這類機制由員工而非管理層發起，因此有很強的基層效果：它讓「幫助別人」這件事被看見、被說出來。

Harbor 的做法比較簡單：每兩週的工程週報有一個「本期感謝」欄位，任何人都可以提名幫助過自己的同事，並寫一句具體的事（「柏翰更新了 search 的 runbook，讓我昨晚值班十分鐘就處理完」）；資深工程師的升遷說明裡，明確寫著「提升團隊其他成員的能力」是評估項目之一。具體的感謝比抽象的口號有效得多，因為它同時告訴其他人「什麼樣的分享是有價值的」。

## 10.10 動手寫：bus factor 與文件健康檢查

### 程式一：從 commit 歷史估算 bus factor

這段程式依 10.3 節的方法，從各模組的 commit 作者估算「誰懂這個模組」，計算整體與結帳關鍵路徑的 bus factor，並比較三個月的 pairing 與輪調之後的變化。

```python
from collections import Counter

# 過去一年每個模組的 commit 作者（虛構資料，簡化自 git log）；* 表示結帳關鍵路徑
COMMITS = {
    "checkout/api*":        ["美華"] * 30 + ["阿凱"] * 12 + ["小芸"] * 5,
    "checkout/pricing*":    ["美華"] * 25 + ["阿凱"] * 3,
    "payments/gateway*":    ["志明"] * 40 + ["美華"] * 2,
    "payments/refund":      ["志明"] * 18 + ["小芸"] * 3,
    "payments/cert-rotate*": ["志明"] * 6,
    "inventory/reserve*":   ["阿哲"] * 22 + ["阿凱"] * 10,
    "inventory/sync-job":   ["志明"] * 15,
    "search/indexer":       ["柏翰"] * 20 + ["志明"] * 8,
    "search/ranking":       ["柏翰"] * 26,
    "notification/push":    ["阿凱"] * 14 + ["美華"] * 6,
}
KNOWS = 0.25   # 一個人貢獻某模組 ≥ 25% 的 commit，才算「懂這個模組」


def experts(commits):
    result = {}
    for module, authors in commits.items():
        counts = Counter(authors)
        total = sum(counts.values())
        result[module] = {a for a, c in counts.items() if c / total >= KNOWS}
    return result


def bus_factor(who, threshold=0.5):
    """最少失去幾個人，就有超過 threshold 比例的模組沒人懂（每次移除最關鍵的人）。"""
    gone = []
    while True:
        orphaned = [m for m, people in who.items() if not people - set(gone)]
        if len(orphaned) / len(who) > threshold:
            return len(gone), gone
        remaining = Counter(p for people in who.values() for p in people - set(gone))
        # 懂最多模組的人先離開；同分時依名字排序，讓每次執行結果相同
        gone.append(min(remaining, key=lambda p: (-remaining[p], p)))


def show(title, commits):
    who = experts(commits)
    print(f"== {title}")
    for module, people in sorted(who.items(), key=lambda kv: len(kv[1])):
        print(f"  {len(people)} 人懂  {module:<22} {'、'.join(sorted(people))}")
    bf, gone = bus_factor(who)
    critical = min(len(p) for m, p in who.items() if m.endswith("*"))
    print(f"整體 bus factor = {bf}（最壞情況依序失去：{' → '.join(gone)}）")
    print(f"結帳關鍵路徑的 bus factor = {critical}")


show("現在", COMMITS)

# 三個月後：輪流值班、pairing 與 code review 讓第二個人開始在關鍵模組貢獻
after = {m: list(a) for m, a in COMMITS.items()}
after["payments/gateway*"] += ["小林"] * 15
after["payments/cert-rotate*"] += ["美華"] * 3
after["inventory/sync-job"] += ["阿哲"] * 6
after["search/ranking"] += ["家豪"] * 10
after["checkout/pricing*"] += ["小芸"] * 10
print()
show("三個月後", after)
```

執行結果：

```text
== 現在
  1 人懂  checkout/pricing*      美華
  1 人懂  payments/gateway*      志明
  1 人懂  payments/refund        志明
  1 人懂  payments/cert-rotate*  志明
  1 人懂  inventory/sync-job     志明
  1 人懂  search/ranking         柏翰
  2 人懂  checkout/api*          美華、阿凱
  2 人懂  inventory/reserve*     阿凱、阿哲
  2 人懂  search/indexer         志明、柏翰
  2 人懂  notification/push      美華、阿凱
整體 bus factor = 3（最壞情況依序失去：志明 → 美華 → 阿凱）
結帳關鍵路徑的 bus factor = 1

== 三個月後
  1 人懂  payments/refund        志明
  2 人懂  checkout/api*          美華、阿凱
  2 人懂  checkout/pricing*      小芸、美華
  2 人懂  payments/gateway*      小林、志明
  2 人懂  payments/cert-rotate*  志明、美華
  2 人懂  inventory/reserve*     阿凱、阿哲
  2 人懂  inventory/sync-job     志明、阿哲
  2 人懂  search/indexer         志明、柏翰
  2 人懂  search/ranking         家豪、柏翰
  2 人懂  notification/push      美華、阿凱
整體 bus factor = 5（最壞情況依序失去：志明 → 美華 → 阿凱 → 柏翰 → 阿哲）
結帳關鍵路徑的 bus factor = 2
```

逐段解讀：

1. `experts` 用「貢獻比例 ≥ 25%」判斷誰懂一個模組。注意 `payments/refund` 雖然有小芸的 3 個 commit，但只占 14%，不算懂。門檻是一個需要團隊討論的假設，練習 1 會讓你改用 code review 紀錄。
2. 「現在」的輸出最上面是 6 個只有一個人懂的模組，其中 4 個屬於志明；`search/ranking` 只有 search 團隊的柏翰懂。這就是單點故障的樣子：一個人身上集中了大量知識，所有相關問題也都會流向志明。
3. `bus_factor` 模擬最壞情況，每次移除「目前懂最多模組的人」；移除志明之後，美華和阿凱各懂 3 個模組，程式用名字排序打破平手（`set` 的走訪順序每次執行可能不同，不明確打破平手就會讓輸出不穩定），所以先移除美華；兩人誰先離開，對最後的數字沒有影響。整體 bus factor 是 3，看起來還好，但結帳關鍵路徑的 bus factor 只有 1，而且瓶頸正好是 `payments/cert-rotate`，也就是 10.1 節的事故。只看整體數字會錯過最重要的風險。
4. 三個月後的資料，模擬了 Harbor 做的事：志明帶 payments 的小林做 gateway 的變更、帶美華做一次憑證更新、阿哲接手 sync-job、search 的家豪參與 ranking、小芸開始參與 pricing。結帳路徑的 bus factor 從 1 變成 2。值得注意的是，`payments/cert-rotate` 只多了 3 個 commit，比例就超過門檻，因為這種「一年做一次」的操作本來就很少 commit，這也是為什麼它特別容易變成單點故障。

真實環境中，`COMMITS` 可以從 `git log --format='%an' -- <路徑>` 取得，也應該加入 code review 紀錄與值班紀錄。數字要和人工盤點一起看：程式只能找到程式碼裡的知識，憑證要在金流商後台怎麼操作，只有問人才知道。

### 程式二：文件健康檢查

第二段程式依 10.6 節的規則檢查文件的 metadata：依風險分級的驗證期限、owner 是否仍在團隊、同一主題是否恰好有一份 canonical 文件。

```python
from dataclasses import dataclass
from datetime import date

TODAY = date(2024, 10, 1)
MAX_AGE = {"high": 90, "medium": 180, "low": 365}   # 依風險決定多久要重新驗證一次
ACTIVE_PEOPLE = {"美華", "阿凱", "志明", "小芸", "阿哲", "小林", "柏翰", "家豪"}


@dataclass
class Doc:
    path: str
    topic: str
    owner: str
    risk: str              # high：照著做錯會造成事故，例如 runbook
    last_verified: date    # 最後一次「照著做過一遍」的日期，不是最後編輯日期
    canonical: bool


def audit(docs: list[Doc]) -> list[str]:
    problems = []
    by_topic: dict[str, list[Doc]] = {}
    for d in docs:
        by_topic.setdefault(d.topic, []).append(d)
        age = (TODAY - d.last_verified).days
        if age > MAX_AGE[d.risk]:
            problems.append(f"過期   {d.path}：{age} 天未驗證（{d.risk} 上限 {MAX_AGE[d.risk]} 天）")
        if d.owner not in ACTIVE_PEOPLE:
            problems.append(f"無主   {d.path}：owner「{d.owner}」已不在團隊")
    for topic, group in by_topic.items():
        canon = [d.path for d in group if d.canonical]
        if len(canon) != 1:
            problems.append(f"衝突   主題「{topic}」有 {len(canon)} 份 canonical：{canon or '無'}")
    return problems


docs = [
    Doc("wiki/payments/憑證更新步驟", "cert-rotation", "志明", "high", date(2023, 9, 12), True),
    Doc("repo/payments/docs/cert.md", "cert-rotation", "志明", "high", date(2024, 3, 2), True),
    Doc("repo/checkout/docs/runbook.md", "checkout-runbook", "美華", "high", date(2024, 8, 20), True),
    Doc("wiki/onboarding/開發環境", "dev-setup", "阿宏", "medium", date(2023, 11, 5), True),
    Doc("repo/search/docs/ranking.md", "ranking-design", "柏翰", "low", date(2024, 1, 15), True),
]
for line in audit(docs):
    print(line)
```

執行結果：

```text
過期   wiki/payments/憑證更新步驟：385 天未驗證（high 上限 90 天）
過期   repo/payments/docs/cert.md：213 天未驗證（high 上限 90 天）
過期   wiki/onboarding/開發環境：331 天未驗證（medium 上限 180 天）
無主   wiki/onboarding/開發環境：owner「阿宏」已不在團隊
衝突   主題「cert-rotation」有 2 份 canonical：['wiki/payments/憑證更新步驟', 'repo/payments/docs/cert.md']
```

逐段解讀：

1. `MAX_AGE` 把新鮮度要求和風險綁在一起。高風險的 runbook 90 天就要重新演練；低風險的設計說明一年檢查一次即可。用同一個期限管所有文件，結果通常是高風險文件太久沒驗證、低風險文件被無意義地反覆「更新日期」。
2. 憑證主題同時出現兩個問題：兩份文件都過期，而且兩份都宣稱自己是 canonical。這完整重現了美華在事故中遇到的狀況。程式無法判斷哪份是對的，但能在事故**之前**把衝突攤開，讓 owner 合併成一份、把另一份改成轉址。
3. 開發環境文件的 owner 已經離職，所以沒有人會主動更新它，這正是新人花六週才第一次部署的原因之一。人員異動時，交接清單應包含「轉移你擁有的文件」。
4. 檢查結果應該變成行動：在 CI 中每週執行，對每個問題自動開 ticket 給 owner（或 owner 所在團隊），而不是寄一封沒人讀的報表。

這段程式假設 metadata 是正確的。如果有人只是改了 `last_verified` 日期卻沒有真的演練，檢查就會被繞過。所以高風險文件的驗證最好綁定實際行為，例如 game day 的紀錄或自動化 smoke test 的結果（第 46 章）。

## 10.11 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會失敗 | 具體情境 | 對策 |
|---|---|---|---|
| 要求「所有知識都要寫成文件」 | 文件寫得比程式還多，沒人維護，很快全部過期 | 每個小改動都要更新三份 wiki，大家開始只改其中一份 | 只為高價值、會被重複查詢的知識寫文件；能放進程式碼、測試、設定的就放進去 |
| 把內容複製到多個入口 | 副本各自漂移，讀者不知道該信哪份 | 新人手冊、team wiki、README 各有一份部署步驟，三份不一樣 | 入口只放連結；每種知識指定一個 canonical 來源 |
| 只靠文件傳遞隱性知識 | 新人照文件操作，但不懂背後的判斷，遇到例外就出錯 | 照 runbook 重啟服務，但沒意識到當下正在跑資料遷移 | 高風險操作搭配 pairing、shadow 值班與演練；文件寫出「何時不要照做」 |
| 強制 readability 或嚴格的 review 關卡 | Review 等待時間變長，小團隊的變更速度被拖慢 | 只有一位 steward 能核准 SQL migration，這位 steward 休假時所有 migration 卡住 | 每個領域至少兩三位 steward；自動化處理機械性檢查；設定 review 的回應時間期望 |
| 用頁數、文章數量衡量知識分享 | 大量低品質、重複的文件被產出 | 為了季度目標，每人寫三篇 wiki，內容大多是複製貼上 | 量測「找到正確答案的時間」、重複提問數、新人上手時間 |
| 指定一位「知識管理員」負責所有文件 | 這個人變成新的單點故障，而且不懂每個系統的細節 | 文件都由一個人整理，這個人離職後整個 wiki 沒人敢動 | 文件 owner 是負責該系統的團隊；中央角色只負責結構、模板與檢查工具 |

## 10.12 AI 時代：什麼變了？

### AI 成為最常被問的「同事」

到了 AI coding agent 與內部 AI 助理普及的時候，新人的第一個問題常常不是問人，而是問 AI。這帶來真實的好處：AI 能在幾秒內讀完整個 repository、解釋一段陌生程式碼、從多份文件中找出相關段落。對 onboarding 來說，「這個函式在做什麼」「這個錯誤訊息通常代表什麼」這類問題，AI 可以大幅縮短等待時間，也降低了第 9 章談到的提問社交成本。

但 AI 回答的品質，取決於它能讀到的知識品質。在 Harbor 的憑證事故中，如果有一個 AI 助理能搜尋整個 wiki，它很可能會從三份互相矛盾的文件中挑一份，然後用非常流暢、有自信的語氣給出錯誤的步驟。**AI 不會修好混亂的知識，它只會讓混亂的知識讀起來更可信。**所以 10.6 節的 single source of truth、owner 與新鮮度，在 AI 時代不是比較不重要，而是更重要。

### 用 AI 做知識檢索的幾個原則

把 AI 接到團隊知識上，常見的做法是 **RAG**（Retrieval-Augmented Generation，檢索增強生成）：先從文件庫搜尋相關段落，再讓模型根據這些段落回答。要讓它可靠，有幾條原則：

- **回答要附來源**：每個答案都要列出它依據的文件與段落，讓人可以點進去確認。沒有來源的回答，不應被當成操作依據。
- **偏好 canonical 與新鮮的來源**：檢索時應優先採用被標記為 canonical、最近驗證過的文件；遇到互相衝突的來源時，應該指出衝突，而不是自己挑一個。
- **遵守原始權限**：AI 只能檢索提問者本來就有權限閱讀的文件。如果把所有文件都放進同一個索引，卻不檢查權限，等於讓任何人都能透過 AI 讀到薪資、客戶資料或資安文件。
- **知道何時說「不知道」**：對高風險操作（例如憑證更新、資料刪除），AI 應該提供經過驗證的 runbook 連結並建議聯絡 owner，而不是自己拼湊步驟。

### 給 coding agent 的知識

Coding agent 也是知識的讀者。很多團隊會在 repository 根目錄放一份給 agent 的說明檔（例如 `AGENTS.md`），寫明如何建置、如何跑測試、目錄結構、不可以碰的地方。這份檔案和給人看的 README 遵守同樣的原則：保持簡短，主要指向 canonical 的文件與指令，而不是把整個知識庫抄進去。OpenAI 的 Codex best practices 頁面也是類似的建議：一份簡短、正確的 `AGENTS.md` 比一份充滿模糊規則的長檔案有用，檔案變大時就把細節移到各任務專屬的文件、由主檔連結過去。這份說明檔也要進 version control、經過 review，並在建置方式改變時一起更新。一份過期的 agent 說明檔，會讓 agent 每次都用錯誤的指令跑測試。

### 新的風險：知識沒有在人之間流動

AI 讓「問人」的次數減少，也減少了隱性知識在人與人之間傳遞的機會。阿凱以前問志明「為什麼這裡要 `sleep(3)`」，志明會順便講到金流商的非同步通知、上次因此出的事故、以及志明會怎麼改。AI 可能只回答了字面上的問題。長期下來，團隊可能出現一群「什麼都能問 AI、但沒有人真正懂系統」的工程師，bus factor 在名義上提高了，實質上卻沒有。

實務上可以這樣平衡：把 AI 用在明確知識的檢索，把節省下來的時間用在隱性知識的傳遞，例如 pairing、design review、shadow 值班；新人的 onboarding 仍要包含和人一起完成的任務；團隊定期檢查「哪些問題只有 AI 回答過、沒有任何人確認過」。

### AI 也能幫忙維護知識

AI 很適合做知識維護中的繁瑣部分：從事故頻道與 postmortem 草擬 runbook 更新、比對文件內容與目前的程式碼或設定是否一致、找出頻道中被重複問的問題、建議哪些文件應該合併。關鍵是這些都是**草稿**，要由 owner review 後才成為 canonical 內容。

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 回答「這段程式在做什麼」「這個錯誤通常代表什麼」等明確知識問題，並附上來源 | 涉及 production 操作的答案，必須連到經過驗證的 runbook；AI 拼湊的步驟不能直接執行 |
| 從事故紀錄、postmortem、頻道討論草擬文件更新與 FAQ | 由文件 owner review 後才發布為 canonical；保留原始來源連結 |
| 比對文件與程式碼、設定，標記可能過期或互相矛盾的內容 | 判斷哪份是正確的、要不要合併，由 owner 決定 |
| 分析重複提問與搜尋失敗，建議缺少的文件或 codelab | 決定投資哪些知識分享方式，由團隊依優先順序決定 |
| 為新人產生個人化的學習路徑與練習題 | 新人仍需和人一起完成 pairing、shadow 值班等傳遞隱性知識的任務 |
| — | 檢索必須遵守原始文件的存取權限；索引與 embedding 不得成為繞過權限的管道 |
| — | 給 coding agent 的說明檔進 version control、經過 review，並和建置方式同步更新 |

> [!ai] AI 提醒
> 當 AI 助理的回答被大量使用後，它的回答本身也可能被貼回 wiki 或頻道，再被下一次檢索取用。如果原始答案有錯，錯誤會被複製並看起來越來越「有共識」。凡是由 AI 產生後被保存下來的內容，都應該標記來源並經過人類確認，避免知識庫被自己生成的內容污染。

## 10.13 專家怎麼想

- **「如果這個人明天不在，誰能接手？」** 資深的 lead 會定期對每個關鍵系統問這個問題，而且不接受「應該可以找到文件」這種答案，要的是一個具體的名字，以及那個人上次實際操作的時間。
- **回答第二次之前，先寫下來。** 很多專家有一個習慣：同一個問題被問第二次時，就寫成文件或改善錯誤訊息，下次直接給連結。這是把自己從單點故障中解放出來最省力的方法。
- **最好的文件是不需要的文件。** 與其寫一份長長的設定說明，不如寫一個設定腳本；與其在文件裡提醒「記得加 timeout」，不如加一條 linter 規則。專家會先問「能不能讓這個知識變成工具或程式碼」，不行才寫文件。
- **新人的困惑是最有價值的回饋。** 資深者早已看不見系統的難懂之處。專家會認真對待新人的每個「為什麼」，把它當成改善文件、命名與工具的線索，而不是新人的問題。
- **量測「找到答案要多久」，而不是「寫了多少」。** 知識系統的價值在於被使用。專家關心的是值班者多快能找到正確的 runbook、新人多快能第一次部署，而不是 wiki 有幾頁。
- **AI 是介面，不是知識本身。** 導入 AI 助理之前，專家會先整理 canonical 來源、owner 與權限，因為檢索與生成只會放大底層知識的品質，不論好壞。

## 10.14 動手練習

1. 修改 10.10 的程式一，加入 code review 紀錄：每次 review 算 0.5 次貢獻，重新計算「誰懂」與 bus factor，觀察哪些模組的結果改變了，並討論 review 是否應該算作「懂」。
2. 修改程式二，加入「被取代」欄位（`superseded_by`）：被取代的文件不算 canonical，但必須指向一份存在的文件；指向不存在的文件時要報錯。
3. 為你熟悉的一個服務畫一頁 10.6 節的「服務地圖」：只放連結，至少包含 owner、儀表板、runbook、設計文件、程式碼位置與聯絡方式，並標出哪些連結目前不存在。
4. 挑一個你最近在私訊中回答過（或問過）的問題，依 10.4 節的格式重寫成公開提問，並把答案補進最適合的文件。
5. 為一位下個月要加入你團隊的新人設計前五天的 onboarding 計畫，每天都要有可觀察的完成證據，並列出你預期新人會卡住的三個地方。
6. 讓 AI 助理回答一個你們團隊的操作問題（例如「怎麼回滾 checkout 的部署」），要求它逐句附上來源，再逐一檢查來源是否存在、是否最新、是否是 canonical，記錄你發現的問題。

## 本章重點整理

- 組織的知識會隨著人離開而消失，也不會自己流動，必須被刻意分享；成長中的團隊尤其需要把「問那個人」變成任何人都能走的路。
- 明確知識可以寫成文件與工具，隱性知識主要靠 pairing、code review、一起值班傳遞，好的制度兩者都要照顧。
- SWE 第 3 章描述的學習障礙包括缺乏心理安全、資訊孤島、單點故障、全有或全無的專業、鸚鵡學舌與鬼屋程式碼，它們會互相強化。
- Bus factor 是「最少失去幾個人專案就會停擺」；除了整體數字，更要看關鍵路徑，因為串聯的路徑由最弱的一環決定。
- 用 commit 歷史估算 bus factor 是有用的起點，但看不到不在程式碼裡的知識，必須搭配人工盤點。
- 提高 bus factor 的核心是讓第二個人真正做過一次：pairing、輪調、非專家 review、照文件演練，以及把知識變成自動化。
- 好問題說明目標、現象、已嘗試的方法與猜測；在公開管道提問與回答，讓一次答案服務很多人。
- 遇到看不懂的程式碼，先理解它為什麼存在再決定要不要改（Chesterton's fence），問完後把理由留下來。
- 依情境選擇分享方式：mentoring 傳遞隱性知識，office hours 處理零散問題，課程適合複雜穩定的主題，codelab 適合需要動手的技能，文件適合參考與理由。
- 每種知識要有單一的 canonical 來源，其他地方用連結而不複製；知識分成入口、說明、事實三層，能放進程式碼與設定的就放進去。
- 文件需要 owner、依風險分級的驗證期限，並區分「最後驗證」與「最後編輯」。
- Readability 制度把 mentoring 透過 code review 規模化，讓慣例一致、任何人都能讀懂別人的程式碼；小組織可借用 steward、review 指南與自動化先行的做法。
- Onboarding 應設計成每個階段都有可觀察的證據，第一週就走完整條變更路徑，並讓新人修補自己卡住的文件。
- 知識分享必須被看見、被認可，並納入職涯期望，否則會被「看得見的工作」排擠。
- AI 讓知識檢索更快，但只會放大底層知識的品質；檢索要附來源、遵守權限、偏好 canonical 來源，並刻意保留人與人之間的隱性知識傳遞。

## 延伸問答

> [!question]- Q1. 「我們的 wiki 有兩千頁文件，知識分享做得很好。」這個說法有什麼問題？
> 文件數量和知識分享的效果沒有直接關係，甚至可能是反向的。兩千頁文件如果沒有 owner、沒有 canonical 標記、大量重複且互相矛盾，讀者找到正確答案的成本反而更高，Harbor 憑證事故中的三份文件就是例子。頁數只衡量了「寫了多少」，沒有衡量「能不能被找到、是否正確、有沒有人在用」。
>
> 比較有意義的指標是：值班者找到正確 runbook 需要多久、新人第一次部署需要幾天、同一類問題在頻道中被重複問了幾次、文件中有多少比例在驗證期限內。如果這些指標不好，兩千頁可能需要的是合併與刪除，而不是再多寫。

> [!question]- Q2. 你是 Harbor 的 tech lead。團隊裡最資深的工程師阿哲是 inventory 的唯一專家，很樂意回答問題，但一直沒時間寫文件或帶人。你會怎麼處理？
> 首先要認識到這不是阿哲個人的問題，而是團隊的分工讓阿哲沒有時間分享。如果阿哲所有的時間都被開發與救火佔滿，要求阿哲「抽空寫文件」不會有效果。具體的做法是在規劃中明確保留阿哲的時間，例如這一季把「讓第二個人能獨立處理 inventory」列為阿哲的正式目標，並在績效評估中認可。
>
> 執行上，優先選擇讓第二個人「真正做過一次」的方法：下一個 inventory 的變更由同在 checkout 團隊的小芸主導、阿哲 review；值班時讓小芸先處理 inventory 的 alert，阿哲在旁支援；請小芸在過程中邊做邊寫文件，阿哲只負責 review 與補充，這比讓阿哲從頭寫有效率得多。三個月後，用「阿哲休假一週，inventory 是否能正常運作」來驗證成果。

> [!question]- Q3. 初階工程師常問：「我自己查多久才應該去問人？」你會怎麼回答？
> 沒有固定的答案，但可以用時間盒的經驗法則：先自己試一段固定時間（例如 15 到 30 分鐘），沒有進展就問。重點不是精確的分鐘數，而是避免兩種極端：一種是完全不試就問，讓回答者花時間在你自己幾分鐘就能查到的事上；另一種是為了不打擾別人卡上一兩天，這對團隊的成本遠高於打斷資深者五分鐘。
>
> 對新人來說，時間盒應該更短，因為他們還缺少判斷「這個問題是不是很快能解決」的經驗，而且很多卡住的原因是團隊特有的知識（例如某個內部工具的怪癖），不可能自己查到。問的時候說清楚你的目標、看到的現象、已經試過什麼，並盡量在公開頻道問。如果問題的答案應該寫在文件裡卻不存在，問完之後把它補上。

> [!question]- Q4. 計算題：Harbor 的結帳路徑經過 4 個模組，懂這些模組的人數分別是 3、2、2、1。結帳路徑的 bus factor 是多少？如果只能投資讓一個模組多一個人懂，應該投資哪個？
> 結帳路徑是串聯的，任何一個模組沒人懂，結帳出問題時就沒人能處理，所以路徑的 bus factor 是各模組人數的最小值，也就是 1。只要那位唯一懂第四個模組的人不在，整個結帳路徑就失去了應變能力。
>
> 投資應該放在第四個模組，讓它從 1 人變成 2 人，路徑的 bus factor 就提升到 2。投資在其他模組（例如把 3 人變成 4 人）對路徑的 bus factor 完全沒有幫助。這個推理和可用性相乘一樣：串聯系統的韌性由最弱的一環決定，改善要從瓶頸開始。實務上還要考慮各模組出事的頻率與影響，但先補 bus factor 為 1 的關鍵模組，幾乎總是正確的第一步。

> [!question]- Q5. Google 的 readability 制度讓每個變更多一道審核，會拖慢開發速度。一個 40 人的新創應該採用嗎？
> 不應該照搬，但值得借用它的精神。Readability 的價值在於透過 code review 規模化 mentoring，讓慣例在大量工程師之間保持一致；它的成本是取得認證的時間與每次 review 的額外等待。Google 有數萬名工程師與壽命很長的 codebase，一致性帶來的長期收益足以支付這些成本；40 人的新創，codebase 與人數都小得多，一套完整的認證制度很可能是過度設計。
>
> 比較合適的做法是：用 formatter、linter 與 type checker 自動處理所有機械性的慣例；在關鍵領域（例如 payments、資料庫 migration）指定兩三位 steward 擔任必要的 reviewer；把 review 中反覆出現的意見整理成指南。隨著團隊成長，若發現不同團隊的程式碼風格與品質差距越來越大，再逐步加強。重點是隨規模調整，而不是一開始就引入大公司的完整流程。

> [!question]- Q6. 同一份部署步驟同時出現在新人手冊、team wiki 與 README 中，而且三份內容略有不同。你會怎麼整理？
> 第一步是確認哪份是正確的，最可靠的方法是讓一個沒做過的人照每一份實際操作一次，或對照目前的部署腳本與 CI 設定。確認後選定一個 canonical 的位置，通常是離程式碼最近的地方（例如 repository 裡的 README 或 docs 目錄），因為它可以和程式碼一起被 review 與更新。
>
> 接著把其他兩份改成連結，而不是刪除：新人手冊與 wiki 的那一段改成「部署步驟見 X」，這樣舊的書籤與搜尋結果仍會導向正確內容。在 canonical 文件上標記 owner 與最後驗證日期。最後，如果步驟能被寫成一個腳本，就寫成腳本，文件只解釋何時使用與出錯時怎麼辦，因為腳本會被實際執行，比文字更不容易過時。

> [!question]- Q7. Harbor 導入了一個能搜尋所有內部文件的 AI 助理。一位工程師問它「怎麼更新金流商的 mTLS 憑證」，它給出了流暢但錯誤的步驟。這次失誤應該怎麼檢討？
> 用 blameless 的方式檢討，聚焦在系統而不是怪 AI 或怪提問者。首先檢查 AI 檢索到了哪些來源：很可能它取用了那份一年前的過期文件，或混合了多份互相矛盾的文件。這代表根本問題在知識本身：同一主題有多份 canonical、文件沒有驗證日期、過期文件沒有被標記或刪除。修正這些問題，人類讀者與 AI 都會受益。
>
> 其次檢查 AI 助理的設計：它的回答有沒有附來源？遇到衝突的來源時有沒有提出警告？對憑證更新這類高風險操作，是否應該只回傳經過驗證的 runbook 連結並建議聯絡 owner，而不是自己生成步驟？最後檢查使用規範：團隊是否明確規定 AI 拼湊的操作步驟不能直接在 production 執行？這三個層面的改進，比單純「提醒大家不要相信 AI」有效得多。

> [!question]- Q8. 面試題：如果你加入一個新團隊，發現大部分知識都在一位資深工程師腦中，你在前三個月會做什麼？
> 好的回答要展示你理解問題的本質，並且有具體、可行的步驟。例如：第一個月先學習，把每次向資深工程師請教的內容整理成公開的筆記或文件，並請對方 review，這同時幫助了自己與團隊，也不會增加對方太多負擔。在這個過程中，留意哪些知識最關鍵、最常被問，以及哪些模組只有這位資深工程師懂。
>
> 第二個月開始主動承擔：選一個只有對方懂的關鍵模組，請對方讓你主導下一次變更或操作、在旁邊支援，完成後更新 runbook。第三個月把這個模式擴大，例如提議團隊輪流值班、在 design review 中加入非專家 reviewer，並用簡單的盤點（每個關鍵模組有幾個人能處理）向主管展示 bus factor 的變化。面試官想看到的是你把知識分享當成可以量測、逐步改善的工程問題，並且尊重那位資深工程師，而不是把對方當成問題。
