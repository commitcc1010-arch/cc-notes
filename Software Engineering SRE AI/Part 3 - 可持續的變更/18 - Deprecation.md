# 第 18 章　Deprecation：如何安全淘汰舊世界

> [!abstract] 本章地圖
> **核心問題**：為什麼刪除一個舊系統常比建立新系統更難？要怎麼把「舊的那套」真正移除，而不是永遠同時維護兩套？
>
> **你會學到**：
> - 說明程式碼為什麼是負債，以及淘汰舊系統的成本與效益怎麼評估
> - 分辨 advisory 與 compulsory deprecation，並為不同情境選擇做法
> - 用靜態搜尋、runtime 遙測與 brownout 找出所有剩餘使用者，並決定靜默期要多長
> - 設計遷移工具、時程與溝通，讓遷移成本由最有能力的一方承擔
> - 讓 deprecation warning 真的有效，並用 ratchet 防止新的使用者加入
> - 完成最後的移除與清理，並安全地讓 AI agent 參與大規模遷移
>
> **前置知識**：第 5 章（Hyrum's Law）、第 17 章（API Contract 與相容性）
>
> **對應原書**：SWE 第 15 章〈Deprecation〉

## 18.1 故事：一個「早就 deprecated」的 API

Harbor 剛創業時，五位工程師花了一個週末寫出第一版付款 API：`POST /v1/pay`。它簡單直接：前端把信用卡號送到 Harbor 的伺服器，伺服器再轉給金流商。那時候這是最快能開始收錢的方法。

第二年初，公司開始快速擴張，剛成立的 payments 團隊推出了 `POST /v2/payments`。新版本有兩個重要改進：卡號由金流商的前端元件直接收下，Harbor 只拿到一個 **token**（代表那張卡的代號，本身不是卡號），大幅縮小了資安稽核的範圍；每個請求都必須帶 idempotency key（冪等鍵，同一個 key 的請求重送多次只會扣款一次，第 41 章詳談），不會因為網路重試而重複扣款。當時還在 payments 團隊的美華在 v1 的程式碼加上 `@deprecated` 註解，在文件頂端加了一行「請改用 v2」，然後團隊就去忙下一個功能了。

八個月後、那年九月的中秋檔期，問題爆發了。行動 app 的舊版本在網路不穩時自動重送 `/v1/pay` 請求，四百多位買家被重複扣款。客服花了三天手動退款，Lisa 在週會上問：「v1 不是早就淘汰了嗎？為什麼還有人在用？」

志明打開 API gateway 的日誌，結果讓所有人沉默：v1 仍然承擔約三成的付款流量。更糟的是，v1 的使用者在過去半年**增加**了：AI 客服 agent 的「送出退款申請」工具是三個月前新寫的（AI 客服只能送出申請，客服人員核准後，工具才呼叫付款 API 執行退款），寫它的工程師請 coding agent「參考現有的付款程式碼」，而 repo 裡範例最多的正是 v1。一個掛著 deprecated 標籤的 API，在沒有人注意的情況下又多了一個新使用者。

同一週，金流商寄來通知：他們將在明年 3 月 31 日關閉接收原始卡號的舊端點。這代表 Harbor 不管準備好沒有，v1 都會在那天停止運作。工程經理 Kevin 把 payments 的小林、v2 的原作者美華（現在是 checkout 的 tech lead）和 platform 團隊的志明找進會議室：「我們有六個月。這次要真的把它關掉。」

這一章要回答的就是 Kevin 的問題：一個系統被標為 deprecated 之後，要經過哪些步驟才會真正消失？為什麼大部分的淘汰計畫停在「標記」這一步？

## 18.2 為什麼淘汰這麼難

### 程式碼是負債，不是資產

SWE 書在 deprecation 那一章有一個核心觀點：**程式碼本身是負債（liability），它提供的功能才是資產**。每一行程式都需要被維護：依賴要升級、安全漏洞要修補、新人要理解它、測試要持續執行、值班者要知道它出事時怎麼處理。如果能用更少的程式碼提供同樣的功能，系統就更健康。

從這個角度看，Harbor 同時擁有 v1 與 v2 的成本非常具體：兩套程式碼要修補安全漏洞；兩套監控與告警；兩套行為讓客服與值班者都要記得「這個使用者走的是哪一條」；v1 處理原始卡號，讓整個服務都落在更嚴格的資安稽核範圍內；而每一個新功能（例如分期付款）都要決定是否也要在 v1 上做一次。

### 新增容易，刪除困難

建立 v2 只需要證明一件事：新的路徑可以運作。刪除 v1 卻要證明一件困難得多的事：**沒有任何重要的東西還依賴它**。這是一個「證明不存在」的問題，而不存在幾乎無法直接證明，只能靠累積足夠的證據。

讓證據難以累積的原因有好幾個：

- **Hyrum's Law（第 5 章）**：使用者依賴的不只是 v1 文件上寫的行為，還有它所有可觀察的行為，例如回應時間、錯誤訊息格式、甚至它「不檢查某個欄位」的寬鬆。v2 即使功能完整，也可能缺少某個沒人知道有人在用的特性。
- **看不見的使用者**：程式碼搜尋找得到 Harbor 自己 repo 裡的呼叫，找不到合作夥伴的系統、使用者手機上的舊 app、每季才跑一次的批次工作。
- **不對稱的成本與收益**：淘汰的收益（少一套系統）由提供方享有，遷移的成本（改程式、測試、上線）卻落在每一個使用方身上。對使用方來說，「繼續用 v1」通常是最省事的選擇。
- **組織誘因**：推出新系統是看得見的成就，刪除舊系統很少被慶祝。在績效評估裡，「上線了 v2」比「關掉了 v1」容易被看見，於是很多團隊停在 v2 上線那一刻。
- **情感與擁有感**：寫出 v1 的人可能還在公司，對它有感情；使用 v1 的團隊也可能懷疑新系統是否真的比較好。

結果是業界常見的「兩套並存」狀態：新系統上線了，舊系統沒關，團隊從此維護兩套，直到某個外部事件（安全事故、廠商停止支援、像 Harbor 這樣的重複扣款事故）逼大家正視它。

## 18.3 先問：這次淘汰值得嗎？

### Deprecation 與 obsolescence

先釐清兩個詞。**Obsolete**（過時）描述的是一種狀態：有更好的替代品出現了，舊系統不再是首選。**Deprecation**（淘汰）描述的是一個過程：有計畫地讓使用者從舊系統遷移到替代方案，並最終移除舊系統。一個系統可以過時很久而從未被淘汰，Harbor 的 v1 在 v2 上線那天就過時了，但真正的淘汰要到一年後才開始。

### 成本與效益

不是每個舊系統都值得淘汰。淘汰本身有成本，而且常被低估。評估時可以把兩邊攤開來：

| 繼續保留的成本 | 淘汰的成本 |
|---|---|
| 兩套系統的維護、修補、監控 | 替代方案補齊功能差距的工作 |
| 資安與法規風險（例如 v1 處理原始卡號） | 所有使用者的遷移工作（改程式、測試、上線） |
| 新功能要做兩次，或讓兩套行為分歧 | 溝通、支援、追蹤剩餘使用者的協調成本 |
| 新人與值班者的認知負擔 | 遷移過程中的事故風險 |
| 底層依賴（舊函式庫、舊語言版本）無法升級 | 機會成本：這段時間沒有做新功能 |

一個實用的判斷方式是看「保留成本」是否隨時間成長。如果舊系統只是安靜地在角落運作、不擋住任何人的升級、沒有安全風險，淘汰它的急迫性就不高。如果它像 v1 一樣持續產生事故、擋住資安稽核、而且還在吸引新使用者，保留成本每個月都在變大，越晚處理越貴（這和第 4 章「越晚升級越貴」的道理相同）。

### 替代方案必須先準備好

淘汰最常見的失敗原因之一，是替代方案還沒準備好就要求使用者搬家。使用者搬過去發現少了必要的功能，只好搬回來或卡在中間，從此不再相信下一次的遷移通知。

所以在宣布淘汰之前，提供方要先回答：v2 是否涵蓋了使用者**實際用到**的 v1 功能？Harbor 盤點時就發現，賣家的 POS 合作夥伴依賴 v1 一個沒寫在文件上的行為：金額可以帶小數點後一位，v1 會自動四捨五入。v2 嚴格拒絕非整數金額。這不代表 v2 要照抄這個行為，但遷移指南必須明確說明，並提供轉換方式。

### 拆之前先弄懂：Chesterton's fence

第 7 章介紹過切斯特頓的籬笆（Chesterton's fence）：不知道一道籬笆為什麼在那裡，就先別急著拆，弄清楚它當初為什麼被立起來，才有資格決定要不要拆。

淘汰舊系統時，這個原則提醒我們：舊系統裡那些看似多餘的檢查、奇怪的特例，可能正在保護某個沒被寫下來的需求。v1 裡有一段「同一張卡 30 秒內的同金額交易直接拒絕」的程式，看起來和 v2 的 idempotency 重複，差點在遷移時被忽略。追查後才發現，它是早年為了擋一種盜刷手法加上的，v2 需要用另一種方式提供同樣的保護。

### 設計時就想好怎麼淘汰

SWE 書也建議在設計新系統時就問：「將來要怎麼移除它？」容易淘汰的系統通常有幾個特徵：清楚的介面邊界（使用者只透過 contract 互動，而不是直接讀資料庫）、可以辨識每個呼叫者的身份、版本化的 API、以及 contract 中明確的淘汰政策（第 17 章）。Harbor 在 v2 的設計中加入了「每個 client 必須帶 client id」的規定，就是為了讓未來的 v3 遷移有能力知道誰還在用 v2。

## 18.4 Advisory 與 compulsory deprecation

SWE 書把淘汰分成兩種，它們的差別在於有沒有強制力。

**Advisory deprecation**（建議式淘汰）沒有截止日期，也不強制使用者遷移。提供方標記舊系統為 deprecated、提供替代方案，然後期待使用者因為新系統更好而主動搬家。Harbor 在 v2 上線時做的正是這種淘汰：一行註解、一行文件。

**Compulsory deprecation**（強制式淘汰）有明確的截止日期，到期後舊系統會被關閉，使用者必須在期限前完成遷移。它通常需要一個專責團隊推動，提供遷移工具、追蹤進度、處理例外，並在必要時直接替使用者完成遷移。

| | Advisory | Compulsory |
|---|---|---|
| 截止日期 | 沒有 | 有，且會執行 |
| 推動方式 | 靠新系統的吸引力 | 靠時程、工具與專責團隊 |
| 適合的情況 | 新系統明顯更好、遷移成本低、保留舊系統不急迫 | 安全風險、外部截止日、維護成本持續成長 |
| 典型結果 | 前期遷移快，之後長尾停滯 | 能真正歸零，但需要大量協調 |
| 常見失敗 | 永遠停在「大部分人搬了」 | 截止日沒有被尊重，或遷移成本全丟給使用者 |

SWE 書對 advisory deprecation 的觀察很直接：單靠建議，頂多讓新的使用稍微變少，卻很少讓團隊主動遷移，即使新系統有大幅改進也一樣，因為對使用者來說遷移是成本、而收益不明顯。原書也因此主張 compulsory deprecation 要有專責團隊負責到底。它適合當作淘汰的第一階段，讓願意搬的人先搬，也讓提供方從早期遷移者身上發現 v2 的缺口。但如果目標是「關掉舊系統」，最後幾乎都需要進入 compulsory 階段。

Compulsory deprecation 的關鍵設計是：**遷移成本要由最有能力承擔的一方承擔**。SWE 書第 1 章提到 Google 的一條規則（常被稱為 **Churn Rule**）：基礎設施團隊若要變更，就必須自己負責把內部使用者遷移到新版本，或以向後相容的方式原地更新。背後的道理是，提供方最懂新舊系統的差異，又能一次處理多個使用者，比讓每個使用方各自研究一遍有效率得多。Harbor 的 payments 團隊因此決定：所有在 Harbor repo 內的 v1 呼叫，由 payments 團隊親自送 PR 遷移；合作夥伴與舊 app 則由 payments 團隊提供工具與支援。

> [!warning] 常見誤解
> 「標上 `@deprecated` 就是在淘汰。」標記只是表達意圖，它本身不會讓任何人遷移。沒有 owner、沒有替代方案的遷移指南、沒有截止日期、沒有追蹤機制的「淘汰」，實際上只是給舊系統貼了一張不會被執行的告示。Harbor 的 v1 標記了八個月，使用者反而增加。

## 18.5 一個完整的淘汰流程

Harbor 為 v1 設計的淘汰計畫分成七個階段，每個階段都有明確的出口條件：

```text
 ① 評估與決策 ──► ② 宣布 ──► ③ 封住入口 ──► ④ 遷移 ──► ⑤ 強制 ──► ⑥ 關閉 ──► ⑦ 清理
   成本效益         時程、      阻止新使用者    工具、       brownout、   回 410、      刪程式、資料、
   替代方案就緒     替代方案、   （ratchet）    PR、支援     限流         保留回復路徑   權限、文件、告警
   指定 owner       支援管道
      │                                          ▲            │
      │                                          └────────────┘
      │                                       強制階段發現新的使用者
      ▼                                       → 回到遷移，必要時延期
  寫成 ADR（第 7 章）
```

從左到右讀：① 評估階段產出的是一份決策紀錄，說明為什麼要淘汰、替代方案是否就緒、誰是 owner。② 宣布讓所有使用者知道時程與替代方案。③ 封住入口是最常被跳過、卻最重要的一步：在處理既有使用者之前，先確保不會有新的使用者加入，否則遷移永遠追不上新增。④ 遷移是最長的階段，由工具、送 PR 與支援組成。⑤ 強制階段用越來越強的手段讓剩下的使用者浮現。⑥ 關閉後仍保留快速回復的能力一段時間。⑦ 清理把所有相關的東西真正刪掉。

圖中的回頭箭頭代表一個現實：強制階段幾乎一定會發現遷移階段沒找到的使用者。好的計畫預留了這個回頭的時間，而不是假設盤點一次就完整。

接下來幾節依序展開最困難的部分：找出使用者、遷移、溝通、警告，以及最後的強制與清理。

## 18.6 找出所有使用者

淘汰計畫的品質，取決於你對「誰在用」的了解有多完整。Harbor 用了四種互補的方法，每一種都看得到別人看不到的東西。

### 靜態搜尋：看得到程式碼

第一種是在程式碼中搜尋呼叫點：搜尋 `/v1/pay` 字串、v1 client 函式庫的 import、相關的設定檔。第 21 章會詳談 code search 與靜態分析如何在大型 codebase 中找到所有使用點。靜態搜尋的優點是精確、能直接指到檔案與行號；缺點是只看得到你擁有的 repo，看不到外部合作夥伴、使用者裝置上的舊版本，也看不到用字串拼接動態產生的 URL。

### Runtime 遙測：看得到真實流量

第二種是在 v1 的入口記錄每個請求的呼叫者身份：API key、client id、app 版本、來源服務名稱，彙整成「每個 consumer 最後一次呼叫的時間」與「每週呼叫量」。這是判斷能否關閉的主要證據，因為它反映真實世界，而不是程式碼裡的可能性。

設計遙測時要注意兩件事。第一，記錄的是**呼叫者**而不是**終端使用者**：你需要知道「iOS app 4.2 版還在呼叫」，不需要知道哪位買家在付款，後者會帶來不必要的隱私風險。第二，遙測要在淘汰計畫一開始就加上，因為你需要足夠長的歷史，才能看到低頻率的使用者。

### 低頻率的使用者與靜默期

最難找的是低頻率的使用者：每週一次的退款批次、每季一次的對帳、每年一次的稅務報表、只在雙十一啟用的促銷系統。它們在大部分時間裡完全安靜，讓人以為已經沒有人用了。

所以判斷「已經沒人用」時，要設定一個**靜默期**（quiet period）：某個 consumer 必須連續多久沒有呼叫，才被視為已遷移。靜默期至少要涵蓋你所知道的最長使用週期，再加上一些緩衝。如果系統可能被季度工作使用，30 天的靜默期就不夠；如果可能有年度工作，就需要一年的資料，或者直接聯繫 owner 確認。18.11 節的程式會示範靜默期太短時會發生什麼事。

### 主動聯繫與 brownout：讓看不見的人出現

第三種方法是主動聯繫：公告、寄信給合作夥伴、在內部頻道詢問。它能找到有人負責、會讀公告的使用者，但找不到沒人負責的系統，例如某個離職員工寫的腳本。

第四種方法是 **brownout**（計畫性短暫中斷）：在事先公告的時段，刻意讓舊 API 回傳錯誤，例如每天中午 12 點到 12 點 15 分回傳 HTTP 410 Gone，並在錯誤訊息中附上遷移指南的位置。還沒遷移的使用者會在這段時間看到失敗，於是主動跳出來問。Brownout 的時間通常從短到長、從低峰到一般時段逐步加強。

Brownout 很有效，但它只能找到「在那段時間剛好有呼叫」的使用者。一個只在每季第一個週一跑的對帳工作，不會被九月中旬的 brownout 抓到。這也是為什麼四種方法要一起用：靜態搜尋找程式碼、遙測找流量、聯繫找有 owner 的人、brownout 逼出剩下的人。

## 18.7 遷移：把搬家的成本降到最低

### 遷移指南

遷移指南是給使用者的 how-to 文件（第 17 章），它要回答使用者真正需要的問題：v1 的每個功能在 v2 裡對應什麼？哪些行為不同？要改哪些程式？怎麼測試？出問題找誰？Harbor 的遷移指南最有用的部分是一張對照表：

| v1 行為 | v2 對應 | 需要注意 |
|---|---|---|
| 送出原始卡號 | 使用金流商前端元件取得 token | 後端不再接觸卡號 |
| 無 idempotency | 必須帶 `Idempotency-Key` header | 同一筆付款重試要用同一個 key |
| 金額可帶一位小數，自動四捨五入 | 金額必須是整數 | 送出前自行四捨五入，或改用 v2 的 `amount` 物件 |
| 失敗回 200 加 `{"ok": false}` | 失敗回 4xx／5xx 與標準錯誤格式 | 檢查 HTTP 狀態碼，而不是只看 body |
| 同卡同額 30 秒內重複交易直接拒絕 | 由 v2 的風控規則處理 | 錯誤碼不同，客服話術要更新 |

最後兩列是 Hyrum's Law 的典型案例：沒有寫在 v1 文件裡，卻被使用者依賴的行為。指南把它們明確列出，讓使用者不必在 production 上自己發現。

### 讓提供方做遷移

對 Harbor 內部的呼叫，payments 團隊直接送 PR：用一個 **codemod**（自動改寫程式碼的工具，通常基於 AST，也就是程式碼的語法樹）把 v1 client 的呼叫替換成 v2，加上 idempotency key 的產生邏輯，再交給各團隊 review。使用方團隊只需要 review 與部署，而不需要自己研究 v2。第 21 章會詳談這種跨越整個 codebase 的 **large-scale change**（大規模變更）如何拆分、測試與核准。

### Adapter 與 shim

有時候使用者無法很快改程式，例如合作夥伴的系統一年才發布兩次。這時可以提供 **adapter**（轉接層，也常叫 shim）：一個保留 v1 介面、內部轉呼叫 v2 的薄層。它讓舊的呼叫方式繼續運作，同時讓 Harbor 可以先刪除 v1 的核心實作。

Adapter 的風險是它可能悄悄改變語意。v1 沒有 idempotency key，adapter 要自己產生一個；如果它為每次請求產生新的 key，重送的請求仍然會重複扣款，等於把 v1 最大的問題原封不動地帶進 v2。Harbor 的 adapter 改用「訂單編號＋金額」推導 key，並對這個推導邏輯寫了專門的測試。Adapter 也要有自己的淘汰日期，否則它會變成新的 v1。

### 資料與狀態的遷移

如果淘汰牽涉資料格式，例如 v1 的交易紀錄存在舊表格、v2 用新表格，遷移通常要經過 **expand／contract** 的步驟：先讓系統同時寫入新舊兩邊（expand）、回填歷史資料、驗證兩邊一致、把讀取切到新表格，最後才停止寫入並刪除舊表格（contract）。每一步都可以獨立回復。第 29 章會完整說明這個模式與 schema migration 的細節。

### 驗證新舊行為一致

遷移最怕「表面成功、行為已變」。降低風險的做法包括：對同一組輸入比較 v1 與 v2 的輸出（可以在測試環境重播 production 流量）；遷移後監控每個 consumer 的錯誤率與付款成功率；以及第 25 章的 contract test，讓使用方寫下自己依賴的行為，在 v2 上持續驗證。

## 18.8 時程與溝通

### 一份好的淘汰公告

公告的目標是讓每個使用者讀完就知道：發生什麼事、為什麼、對我有什麼影響、我要做什麼、什麼時候之前、遇到問題找誰。Harbor 的公告節錄如下：

```text
主旨：[行動需要] /v1/pay 將於 2025-03-15 關閉，請遷移至 /v2/payments

為什麼：v1 會在網路重試時重複扣款，且需要處理原始卡號；
       金流商將於 2025-03-31 關閉 v1 依賴的舊端點。
誰受影響：所有呼叫 POST /v1/pay 的服務、app 與合作夥伴。
           你可以在 v1 使用儀表板查詢自己的 client id 是否仍在使用。
要做什麼：依遷移指南改用 /v2/payments；Harbor 內部 repo 的呼叫
           由 payments 團隊直接送 PR，請協助 review 與部署。
時程：
  2024-10-01  公告；v1 停止接受新的 API key
  2024-11-01  回應加上 Sunset header；每週二 brownout 15 分鐘開始
  2025-01-15  iOS app 最低支援版本提高到 4.3（4.2 以下強制更新）
  2025-02-15  brownout 延長為每天 1 小時
  2025-03-15  v1 回傳 410 Gone
例外：需在 2025-01-31 前申請，最長延至 2025-03-25，需 Kevin 核准。
支援：#pay-v2-migration 頻道；每週四 office hours。
```

這份公告有幾個值得注意的設計：它說明了「為什麼」，讓使用者理解這不是任意的決定；它提供了查詢自己是否受影響的方法；時程是一連串逐步加強的里程碑，而不是一個遙遠的截止日；例外有申請期限、上限與核准人，而且例外的上限早於金流商的外部截止日，保留了緩衝。

### 時程怎麼訂

時程長短取決於使用者能多快改變。內部服務可能幾週就能遷移；合作夥伴受限於他們自己的發布週期，通常需要幾個月；行動 app 最慢，因為使用者不一定會更新，只能靠提高最低支援版本來強制。訂時程時，從最慢的那一群往回推，並預留強制階段發現新使用者的時間。

時程一旦公告，就要被尊重。如果截止日一延再延，使用者很快就學會「截止日只是建議」，下一次淘汰會更難。真的需要延期時，要公開說明原因與新的時程，並把延期限縮在少數有正當理由的使用者身上，而不是整體延後。

### 用機器可讀的方式告知

除了人讀的公告，也要讓程式能偵測淘汰。HTTP API 可以在回應中加上 `Sunset` header（RFC 8594 定義），告知這個資源預計停止服務的時間；RFC 9745（2025 年）則標準化了 `Deprecation` header，用來標示資源已被淘汰或將被淘汰的時間。函式庫可以在被呼叫時發出 deprecation warning（例如 Python 的 `DeprecationWarning`），或在型別與註解中標記，讓 IDE 顯示刪除線。這些訊號能被 client 的監控、linter 與 AI coding agent 讀到，比只靠公告可靠。

## 18.9 警告：為什麼大家都忽略 deprecation warning

### 警告疲勞

Harbor 的 v1 client 函式庫從年初就會在每次呼叫時印出一行 deprecation warning。結果沒有任何人因此遷移。原因很簡單：那行警告出現在每個服務的日誌裡，夾在每天數百萬行的輸出之間，沒有人會讀；即使讀到了，它也沒說要做什麼、什麼時候之前。

這和第 34 章的告警疲勞是同一個問題。SWE 書指出，deprecation warning 要有用，必須同時滿足兩個條件：**可行動**（actionable，讀到的人能依警告做出實際的動作，最好附上遷移指南或自動修復）與**相關**（relevant，在使用者正要做那個動作的時候出現，例如正要新增一個呼叫時）。一個不可行動或不相關的警告，只會訓練大家忽略所有警告。

### 讓警告出現在對的地方

同樣的資訊放在不同的位置，效果天差地遠：

| 位置 | 誰會看到 | 效果 |
|---|---|---|
| Runtime 日誌 | 幾乎沒有人 | 最差，只能當作遙測資料 |
| IDE 刪除線與提示 | 正在寫新程式的人 | 好，能阻止新的使用 |
| Code review 自動留言 | 修改相關程式的作者與 reviewer | 好，出現在決策的當下 |
| CI 失敗（針對新的使用） | 想新增呼叫的人 | 最強，直接擋下新增 |
| 直接寄給 owner 的追蹤 issue | 負責遷移的團隊 | 好，有明確的負責人與期限 |

原則是：**警告要出現在有人正在做決定的時候**。寫新程式時、review 時、合併時，都是可以改變行為的時刻；日誌是事後的紀錄，沒有人在那時做決定。

### Ratchet：只能變少，不能變多

最有效的「警告」其實是禁止。**Ratchet**（棘輪）是一種只能往一個方向轉的機制：建立一份目前所有舊使用者的名單，CI 允許名單上的使用者繼續存在，但任何不在名單上的新使用都會失敗；名單上的使用者遷移後就從名單移除，而且不能再加回去。這樣一來，使用者的數量只會減少，永遠不會增加。

SWE 書把這稱為防止 **backsliding**（倒退）：遷移進行到一半，卻有新的程式碼又開始使用舊系統。Harbor 的 AI 客服退款工具就是一次倒退。如果當時有 ratchet，coding agent 產生的 v1 呼叫會在 CI 就被擋下，並在錯誤訊息裡告訴它該改用什麼。在 build 系統層級也可以做到類似的事，例如限制哪些目錄可以依賴舊的 client 函式庫。

### 逐步升級的強制手段

Ratchet 處理新的使用，既有的使用則需要一系列逐步加強的手段：

```text
 強度 ▲
      │                                                   ┌── 關閉（410 Gone）
      │                                         ┌─────────┘
      │                               ┌─────────┘ brownout 延長、限流
      │                     ┌─────────┘ 定期 brownout
      │           ┌─────────┘ Sunset header、追蹤 issue 指派給 owner
      │ ┌─────────┘ 停止新 API key、ratchet 擋新使用
      │─┘ 公告、文件、遷移指南
      └──────────────────────────────────────────────────────────► 時間
```

每一階都讓「不遷移」的成本稍微提高，同時讓還沒現身的使用者有機會現身。越往右，被影響的使用者應該越少；如果到了 brownout 階段還有大量流量受影響，代表前面的遷移支援不夠，應該放慢而不是硬衝。

## 18.10 最後一哩：關閉、回復與清理

### 關閉前的檢查

Harbor 在 v1 回傳 410 之前，要求以下條件全部成立：遙測顯示所有 consumer 在靜默期內沒有呼叫，或已取得 owner 書面確認；所有例外都已到期或完成遷移；brownout 期間的錯誤都已追到來源；值班者與客服知道關閉的時間與可能的症狀；有一個能在幾分鐘內重新開啟 v1 的開關。

最後一項很重要。關閉不是一個不可逆的動作：在關閉後的幾週內，v1 的程式碼還在、開關還在，萬一發現遺漏的關鍵使用者，可以短暫重新開啟，讓對方有時間遷移。真正刪除程式碼要等到這段觀察期結束。

### 清理清單

關掉 endpoint 只是開始。如果只刪了路由，其他相關的東西仍然存在，維護成本與攻擊面並沒有真正消失。Harbor 的清理清單包括：

- v1 的程式碼、client 函式庫、adapter 與相關測試
- v1 專用的資料表與備份，依資料保存規範處理（付款紀錄可能有法定保存期限，不能直接刪除）
- v1 的 feature flag、設定、API key 與服務帳號權限
- 處理原始卡號的網路路徑與資安稽核範圍
- v1 的儀表板、告警、SLO 與 runbook
- 文件：遷移指南標為 archived，v1 reference 下架，第 17 章的文件 metadata 改為 `status: archived`
- 給 AI agent 的指引檔中關於 v1 的說明，以及 ratchet 名單本身

清理完成後，Harbor 在 ADR 中補上一段結果紀錄：淘汰花了多久、遇到哪些意外、哪些做法有效。這份紀錄是下一次淘汰最好的參考。

### 慶祝刪除

SWE 書提醒，淘汰計畫需要明確的 owner 與可衡量的漸進里程碑（不要把「完全移除」當成唯一的里程碑），否則很容易在中途失去動力。里程碑也是慶祝的時機：Harbor 在 v1 流量降到 1% 以下時、以及最後一行 v1 程式碼被刪除時，都在全公司週會上公開感謝參與遷移的團隊。這不只是禮貌，它在改變組織的誘因：讓「刪除」和「上線」一樣被看見。

## 18.11 動手寫：追蹤剩餘使用者與防止倒退

這一節用兩段程式模擬淘汰計畫中最需要證據的兩件事：判斷「誰還在用」與「靜默期夠不夠長」，以及用 ratchet 在 CI 擋下新的使用者。

### 程式一：靜默期、brownout 與燃盡預測

```python
# 模擬 Harbor 淘汰 /v1/pay：誰還在用、靜默期夠不夠長、brownout 抓到誰
from datetime import date, timedelta

TODAY = date(2024, 9, 30)

# 每個 consumer 呼叫 /v1/pay 的日期（真實系統來自 access log，依 API key／client id 彙整）
def every(start, end, step_days):
    d, out = start, []
    while d <= end:
        out.append(d)
        d += timedelta(days=step_days)
    return out

USAGE = {
    "web-checkout":       every(date(2024, 1, 1), date(2024, 5, 31), 1),   # 已遷移
    "ios-app<=4.2":       every(date(2024, 1, 1), date(2024, 9, 29), 1),   # 舊 app，長尾
    "refund-batch":       every(date(2024, 1, 4), date(2024, 8, 30), 7),   # 每週一次，已遷移
    "partner-pos-abc":    every(date(2024, 1, 1), date(2024, 9, 28), 3),
    "quarterly-settle":   [date(2024, 1, 1), date(2024, 4, 1), date(2024, 7, 1)],  # 每季一次
    "ai-support-refund":  every(date(2024, 6, 15), date(2024, 9, 12), 2),  # AI 客服的退款申請 tool，6 月新寫，被發現後 9/12 起改用 v2
}


def last_seen(dates):
    return max(dates)


def blockers(quiet_days):
    cutoff = TODAY - timedelta(days=quiet_days)
    return sorted(c for c, ds in USAGE.items() if last_seen(ds) > cutoff)


print("各 consumer 最後一次呼叫：")
for c, ds in sorted(USAGE.items(), key=lambda kv: last_seen(kv[1])):
    print(f"  {c:<18} {last_seen(ds)}  （{(TODAY - last_seen(ds)).days} 天前）")

for quiet in (30, 100):
    b = blockers(quiet)
    print(f"\n靜默期 {quiet} 天 → 仍在使用：{b}")
    print(f"  看起來「已遷移」：{sorted(set(USAGE) - set(b))}")


def brownout(start, days):
    """在 start 起連續 days 天，讓 /v1/pay 短暫回 410 Gone，看誰會撞到"""
    hit = set()
    for i in range(days):
        d = start + timedelta(days=i)
        for c, ds in USAGE.items():
            if d in ds:
                hit.add(c)
    return sorted(hit)

print("\nBrownout（2024-09-14 起 3 天）撞到：", brownout(date(2024, 9, 14), 3))
print("Brownout（2024-07-01 起 3 天）撞到：", brownout(date(2024, 7, 1), 3))


# 每週剩餘呼叫量與線性外推的「歸零週」
weekly = [5200, 4100, 3600, 3300, 3150, 3050, 2990, 2950]
drops = [a - b for a, b in zip(weekly, weekly[1:])]
recent = sum(drops[-3:]) / 3
print(f"\n最近 3 週平均每週減少 {recent:.0f} 次；照此速度還要約 {weekly[-1] / recent:.0f} 週才歸零")
```

執行結果：

```text
各 consumer 最後一次呼叫：
  web-checkout       2024-05-31  （122 天前）
  quarterly-settle   2024-07-01  （91 天前）
  refund-batch       2024-08-29  （32 天前）
  ai-support-refund  2024-09-11  （19 天前）
  partner-pos-abc    2024-09-27  （3 天前）
  ios-app<=4.2       2024-09-29  （1 天前）

靜默期 30 天 → 仍在使用：['ai-support-refund', 'ios-app<=4.2', 'partner-pos-abc']
  看起來「已遷移」：['quarterly-settle', 'refund-batch', 'web-checkout']

靜默期 100 天 → 仍在使用：['ai-support-refund', 'ios-app<=4.2', 'partner-pos-abc', 'quarterly-settle', 'refund-batch']
  看起來「已遷移」：['web-checkout']

Brownout（2024-09-14 起 3 天）撞到： ['ios-app<=4.2', 'partner-pos-abc']
Brownout（2024-07-01 起 3 天）撞到： ['ai-support-refund', 'ios-app<=4.2', 'partner-pos-abc', 'quarterly-settle']

最近 3 週平均每週減少 67 次；照此速度還要約 44 週才歸零
```

逐段解讀：

1. `USAGE` 是遙測彙整後的結果：每個 consumer 呼叫 v1 的日期。真實系統中這來自 API gateway 的 access log，依 API key 或 client id 分組。注意 key 是呼叫者（`ios-app<=4.2`），不是終端買家，符合 18.6 節的隱私原則。
2. 30 天靜默期把 `quarterly-settle` 判定為「已遷移」，這是一個**危險的錯誤**：它其實沒有遷移，只是每季才跑一次，下一次在 10 月初。如果 Harbor 依這個結果在 9 月底關閉 v1，季度對帳會在 10 月第一個週一失敗，而且可能沒有人立刻發現。
3. 100 天靜默期抓到了 `quarterly-settle`，但也把 `refund-batch` 留在名單上，雖然它在 8 月底已經遷移完成。這是**保守的錯誤**：只會讓關閉延後，不會造成事故。兩種錯誤的代價不對稱，所以靜默期寧可長，再用 owner 的書面確認把確定已遷移的項目提早移出名單。
4. 9 月中旬的 brownout 只撞到兩個 consumer。`quarterly-settle` 那幾天沒有呼叫，所以完全沒被影響；`ai-support-refund` 已經在 9/12 遷移。換成 7/1（季度工作執行的日子）的 brownout，就會撞到四個。這說明 brownout 的時段要刻意對準已知的週期性工作，或持續夠長的時間。
5. 最後的燃盡預測顯示典型的長尾：第一週減少了一千多次，之後每週減少的量越來越小，最近三週平均只剩 67 次。照這個速度，要 44 週才會歸零，遠超過金流商的截止日；而且每週減少的量本身還在變小，線性外推其實偏樂觀。這正是 advisory 階段停滯的樣子，也是 Harbor 必須進入 compulsory 階段（強制更新 app、brownout、直接聯繫合作夥伴）的數據依據。

### 程式二：用 ratchet 擋下新的使用者

```python
# Ratchet：只允許「已知的舊使用者」繼續呼叫 /v1/pay，新的使用一律擋下
import re

ALLOWLIST = {  # 2024-09 啟動淘汰計畫時登記的既有使用者，只能減少不能增加
    "ios/legacy/PaymentClient.swift",
    "jobs/quarterly_settle.py",
    "jobs/refund_batch.py",
    "support_agent/tools/refund.py",
}

REPO = {  # 檔案路徑 → 內容（真實系統從 code search 或 git ls-files 取得）
    "ios/legacy/PaymentClient.swift": 'let url = base + "/v1/pay"',
    "jobs/quarterly_settle.py": 'client.post("/v1/pay", body)',
    "jobs/refund_batch.py": 'client.post("/v2/payments", body, key=k)',      # 已遷移
    "support_agent/tools/refund.py": 'client.post("/v2/refunds", body, key=k)', # 已遷移
    "seller/promo/charge.py": 'http.post(BASE + "/v1/pay", data)',           # 新的使用！
}

PATTERN = re.compile(r"/v1/pay\b")

users = {path for path, src in REPO.items() if PATTERN.search(src)}
new_users = sorted(users - ALLOWLIST)
gone = sorted(ALLOWLIST - users)

for path in new_users:
    print(f"ERROR {path}: 新增了對 /v1/pay 的呼叫，請改用 /v2/payments（見 docs/payments/migrate-v2.md）")
for path in gone:
    print(f"INFO  {path}: 已不再使用 /v1/pay，請從 ALLOWLIST 移除（ratchet 收緊）")
print(f"\n目前使用者 {len(users)}／名單 {len(ALLOWLIST)}；結果：{'FAIL' if new_users else 'PASS'}")
```

執行結果：

```text
ERROR seller/promo/charge.py: 新增了對 /v1/pay 的呼叫，請改用 /v2/payments（見 docs/payments/migrate-v2.md）
INFO  jobs/refund_batch.py: 已不再使用 /v1/pay，請從 ALLOWLIST 移除（ratchet 收緊）
INFO  support_agent/tools/refund.py: 已不再使用 /v1/pay，請從 ALLOWLIST 移除（ratchet 收緊）

目前使用者 3／名單 4；結果：FAIL
```

逐段解讀：

1. `ALLOWLIST` 是盤點當下的既有使用者。它被放在 repo 裡、受 code review 保護，任何人想把新檔案加進名單，都要經過 payments 團隊核准。
2. `seller/promo/charge.py` 是一個新的 v1 呼叫，CI 直接失敗，錯誤訊息告訴作者該改用什麼、去哪裡看指南。這個訊息對人和 AI coding agent 同樣有用：agent 讀到 CI 錯誤後，可以依指南自行修正。
3. 兩個已遷移的檔案觸發 `INFO`，提醒把它們從名單移除。這是 ratchet 的關鍵：名單只會縮小。若不移除，未來有人在這兩個檔案裡重新加入 v1 呼叫，CI 就不會發現。
4. 這個 ratchet 有一個明顯的盲點：它只看得到 Harbor 自己的 repo。`partner-pos-abc` 是合作夥伴的系統，不在任何 Harbor repo 裡，所以不在名單上，也不會被這個檢查影響。外部使用者只能靠程式一的遙測與 18.8 節的溝通處理。
5. 真實系統中，`PATTERN` 這種字串比對容易漏掉動態拼接的 URL，也可能誤判註解裡的文字。比較穩健的做法是限制 v1 client 函式庫的依賴（build 系統的 visibility 規則），或用 AST 層級的靜態分析（第 21 章）。

兩段程式對應淘汰中兩種不同性質的證據：程式一回答「現在還有誰」，依賴 runtime 資料與足夠長的時間窗；程式二回答「會不會有新的人加入」，依賴 CI 的強制力。缺少任何一種，淘汰都會停在長尾。

## 18.12 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會出問題 | 具體情境 | 對策 |
|---|---|---|---|
| 只做 advisory deprecation | 長尾永遠不會歸零 | Harbor 的 v1 標記八個月，流量仍有三成，甚至增加新使用者 | 設定進入 compulsory 階段的條件與日期；先封住入口 |
| 靜默期太短 | 低頻率使用者被誤判為已遷移 | 30 天靜默期漏掉每季一次的對帳工作 | 靜默期涵蓋最長已知週期；低頻使用者取得 owner 書面確認 |
| 替代方案還沒準備好就強制遷移 | 使用者被迫搬家後發現缺功能，搬回或卡住 | v2 不支援某合作夥伴依賴的小數金額處理 | 先盤點實際使用的功能；以早期遷移者驗證 v2；遷移指南列出行為差異 |
| Adapter 改變語意 | 表面遷移成功，行為已經錯了 | Adapter 為每次請求產生新的 idempotency key，重送仍重複扣款 | 對 adapter 寫語意測試；比較新舊輸出；adapter 本身也有淘汰日期 |
| 遷移成本全丟給使用者 | 每個團隊各自研究、各自犯錯，進度緩慢 | 五個團隊各花一週研究 v2，其中兩個漏了 idempotency key | 提供方用 codemod 直接送 PR；提供 office hours 與範例 |
| 截止日一延再延 | 使用者學會忽略截止日 | 第三次延期後，剩下的團隊不再回應遷移通知 | 例外要有期限、上限與核准人；延期只針對個別使用者並公開理由 |
| 關閉後立即刪除程式碼 | 發現遺漏的關鍵使用者時無法快速恢復 | 關閉三天後才發現年度稅務報表依賴 v1 | 關閉與刪除分開；保留可快速重開的開關與觀察期 |
| 只刪 endpoint 不做清理 | 維護成本與攻擊面仍在 | v1 的服務帳號權限還能存取卡號資料庫 | 用清單逐項清理程式、資料、權限、告警、文件與 agent 指引 |
| 遙測記錄終端使用者身份 | 淘汰工作本身產生隱私風險 | 為了找出誰在用 v1，把每位買家的 ID 寫進分析表 | 只記錄呼叫者（client id、app 版本），並設定保存期限 |

## 18.13 AI 時代：什麼變了？

### 遷移的機械成本大幅下降

淘汰中最耗人力的部分，往往是重複性高的修改：在許多服務裡把 v1 呼叫換成 v2、補上 idempotency key、更新測試與文件。這正是 AI coding agent 擅長的工作。Harbor 的 payments 團隊讓 agent 依遷移指南為每個使用 v1 的服務產生 PR，原本預估需要兩個人做一個月的修改，幾天內就有了草稿。

但「產生 PR」只是遷移的一小部分。真正的成本在驗證：這個 PR 是否保留了原本的語意？idempotency key 的推導是否正確？測試是否真的涵蓋了改變的行為？所以 Harbor 的流程是讓 agent 產生小而獨立的 PR（每個服務一個），每個 PR 都必須通過 CI、contract test，並由該服務的 owner review；涉及金流的 PR 另外要求 payments 團隊的人核准。第 21 章會完整說明 AI agent 執行大規模變更的流程。

### AI 也會讓舊世界復活

Harbor 故事中最諷刺的一段，是 AI 客服的退款工具由 coding agent 寫成、卻用了已淘汰的 v1。原因很單純：agent 從 repo 裡的既有程式碼學習「該怎麼呼叫付款 API」，而 v1 的範例最多。在 AI 時代，**舊程式碼不只是維護負擔，還是會被模仿的範例**。repo 裡每一份還沒刪除的舊用法，都可能被 agent 複製到新的地方。

這讓防止倒退的機制變得更重要：ratchet 與 lint 規則要在 CI 擋下新的使用，錯誤訊息要寫成 agent 讀得懂、能照著修正的形式；文件要標上 `status: deprecated` 與替代方案；給 agent 的指引檔要明確寫出「不要使用 v1，改用 v2」。另一個常被忽略的措施是**盡早刪除**：遷移完成的舊程式碼越早刪掉，被模仿的機會就越少。

### AI 可以幫忙找使用者，但不能證明「沒有使用者」

Agent 可以搜尋所有 repo、分析遙測、整理每個 consumer 的狀態與聯絡人，產出一份清楚的盤點報告。但 agent 看到的範圍和靜態搜尋一樣有限：它看不到合作夥伴的系統、看不到使用者手機上的舊 app。如果 agent 回報「已找不到任何 v1 呼叫」，這只代表它能看到的範圍內沒有，不代表可以關閉。關閉的決定必須建立在 runtime 遙測、足夠長的靜默期與 owner 確認上，並由人類 owner 做出。

### 可執行的做法

1. 讓 agent 用三類來源產生盤點：靜態搜尋結果、遙測中的 client id、聯絡紀錄，並明確標示「只在一個來源出現」的項目，這些通常是最需要人工追查的。
2. 遷移 PR 要小、可獨立回復，每個 PR 的描述說明改了什麼行為、如何測試；agent 不能在同一個 PR 裡順便做其他重構。
3. 為 adapter 與 codemod 準備一組代表性的測試案例（包含重送、金額邊界、錯誤處理），agent 產生的修改必須全部通過。
4. 涉及資料轉換時，agent 可以草擬 migration 腳本，但執行前必須先 dry-run、驗證資料數量與 invariant，破壞性的步驟由人核准。
5. 若 AI 客服 agent 本身是舊 API 的使用者，它的工具定義也是遷移的一部分：更新工具、重新跑 agent eval（第 25 章），確認退款行為沒有改變。

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 跨 repo 搜尋呼叫點，整理盤點報告與每個 consumer 的 owner | 「已無使用者」的判定需要 runtime 遙測、靜默期與 owner 確認，不能只看 AI 搜尋結果 |
| 依遷移指南產生 codemod 與小型遷移 PR | 每個 PR 由服務 owner review；金流等高風險路徑需要額外核准；PR 必須通過 contract test |
| 分析遙測趨勢，預測燃盡時程並找出停滯的長尾 | 是否進入 compulsory 階段、截止日與例外由人決定並對外承諾 |
| 草擬公告、遷移指南、支援頻道的常見問答 | 對合作夥伴與客戶的正式承諾由負責人審核後發出 |
| 關閉前搜尋殘留的 flag、權限、告警、文件與 agent 指引 | 刪除資料前確認法定保存期限；破壞性操作需要 dry-run 與人類核准 |
| 讀取 CI 的 ratchet 錯誤並自行改用新 API | Ratchet 名單只能由 owner 核准修改，agent 不得把新檔案加入名單來讓 CI 通過 |

> [!ai] AI 提醒
> 小心 agent「讓 CI 變綠」的捷徑。面對 ratchet 失敗，最省事的修法是把新檔案加進 allowlist，或在呼叫處加上忽略規則的註解。這兩種修改都應該被 CODEOWNERS 規則保護，並在 review 時特別檢查：agent 的任務是遷移到新 API，不是說服檢查放行。

## 18.14 專家怎麼想

- **「誰在付這筆遷移的成本？」** 專家評估淘汰計畫時，第一個問題是成本落在哪裡。如果每個使用方都要自己研究、自己改，進度一定很慢；最有效的計畫通常是提供方用工具集中處理大部分遷移，只把無法自動化的部分留給使用方。
- **先封住入口，再處理存量。** 遷移速度比不上新增速度時，舊系統永遠不會消失。資深工程師在宣布淘汰的同一天就加上 ratchet，因為這是成本最低、效果最確定的一步。
- **相信遙測，但要懂它的盲點。** 「上週沒有流量」不等於「沒有使用者」。專家會問：最長的使用週期是多久？有沒有只在特定事件（雙十一、年底結算）才啟用的流程？有沒有離線的裝置？
- **把關閉和刪除分開。** 關閉是可回復的，刪除不是。保留一段可以快速重開的觀察期，代價很小，卻能把一次遺漏從事故降級成一通電話。
- **建新系統時就編列淘汰舊系統的預算。** 一個專案如果只計畫了 v2 的上線，卻沒有計畫 v1 的移除，它最後的結果很可能是兩套並存。專家會把「舊系統歸零」寫進專案的完成定義。
- **把刪除變成值得被看見的成就。** 組織若只獎勵上線，就會累積越來越多的舊系統。公開慶祝刪除、在績效評估中認可淘汰工作，是改變誘因最直接的方法。

## 18.15 動手練習

1. 選一個你熟悉的舊 API、函式庫或內部工具，寫一份一頁的淘汰簡報：為什麼要淘汰、替代方案是否就緒、使用者有哪些、遷移成本由誰承擔、advisory 還是 compulsory、時程與例外流程。
2. 擴充 18.11 節的程式一：為每個 consumer 加上「已知的使用週期」（每日、每週、每季、每年），讓程式自動為每個 consumer 計算合適的靜默期，並列出需要 owner 書面確認的項目。
3. 擴充程式二：改用 Python 的 `ast` 模組分析 `.py` 檔案，只在實際的函式呼叫參數中出現 `/v1/pay` 時才計入，忽略註解與文件字串，並比較兩種做法的結果差異。
4. 為 Harbor 的 v1 設計一個 brownout 計畫：每次的時段、長度、錯誤訊息內容、事前公告方式，以及如何確保它涵蓋每季的對帳工作。說明如果 brownout 期間發生重大促銷活動，你會怎麼調整。
5. 找一個你曾經參與或觀察過、最後沒有完成的遷移，分析它停在哪個階段（宣布、封住入口、遷移、強制、清理），以及缺少了哪一種證據或工具。
6. 請 AI 為一個舊函式的所有呼叫點產生遷移 PR，再設計至少五個測試案例檢查語意是否保留（包含錯誤處理與邊界值），記錄 AI 修改中被測試抓到的問題。

## 本章重點整理

- 程式碼是負債，它提供的功能才是資產；同時維護新舊兩套系統的成本會隨時間成長。
- 新增只需證明新路徑可運作，刪除卻要證明沒有重要的使用者，這是淘汰比建立更難的根本原因。
- Hyrum's Law、看不見的使用者、成本與收益的不對稱、以及只獎勵上線的組織誘因，讓舊系統很難真正消失。
- 淘汰前要評估成本與效益，確認替代方案涵蓋使用者實際用到的功能，並依 Chesterton's fence 先弄懂舊系統每個特例的原因。
- Advisory deprecation 靠新系統的吸引力，通常停在長尾；compulsory deprecation 有截止日與專責團隊，才能真正歸零。
- 遷移成本應由最有能力的一方承擔，提供方用 codemod 與送 PR 集中處理，比讓每個使用方各自研究有效率。
- 找使用者要結合靜態搜尋、runtime 遙測、主動聯繫與 brownout；每種方法都有其他方法補不了的盲點。
- 靜默期至少要涵蓋最長的已知使用週期；太短的靜默期會把低頻使用者誤判為已遷移，而這種錯誤的代價遠高於延後關閉。
- Adapter 能爭取時間，但可能悄悄改變語意，它需要語意測試與自己的淘汰日期。
- 好的淘汰公告說明原因、影響範圍、行動、逐步加強的里程碑與有期限的例外流程；截止日一旦公告就要被尊重。
- Deprecation warning 必須可行動且相關，並出現在有人正在做決定的地方：IDE、code review、CI，而不是日誌。
- Ratchet 讓使用者名單只減不增，是防止倒退最有效的機制。
- 關閉與刪除要分開，保留快速重開的觀察期；最後的清理要涵蓋程式、資料、權限、告警、文件與 agent 指引。
- AI agent 大幅降低遷移的機械成本，但也會模仿 repo 裡的舊用法讓舊系統復活；「已無使用者」與關閉的決定必須由人依證據做出。

## 延伸問答

> [!question]- Q1. 為什麼說「程式碼是負債，不是資產」？這是否代表程式碼越少越好？
> 這句話的意思是：使用者在意的是功能，而每一行程式碼都需要持續付出成本才能維持那個功能，包括依賴升級、安全修補、測試、理解與值班。如果能用更少的程式碼提供同樣的功能，系統就更容易修改與維運；同一個功能由兩套程式碼提供，成本就是兩倍，卻沒有多出任何價值。
>
> 但它不代表「程式碼越少越好」的極端版本。為了少寫幾行而把邏輯壓縮成難以理解的寫法，或刪掉必要的錯誤處理與測試，反而會增加理解與事故的成本。比較精確的理解是：評估程式碼時，要看它提供的功能是否值得它的維護成本；淘汰舊系統的價值，正在於去除那些不再提供獨特功能、卻持續產生成本的程式碼。

> [!question]- Q2. Advisory 與 compulsory deprecation 各適合什麼情況？Harbor 的 v1 為什麼需要轉成 compulsory？
> Advisory deprecation 適合新系統明顯更好、遷移成本低、而且保留舊系統沒有急迫風險的情況。它的好處是溫和、不需要大量協調，也能讓早期遷移者幫忙找出新系統的缺口。Compulsory deprecation 適合有安全或法規風險、外部截止日、或保留成本持續成長的情況，它需要截止日、專責團隊、遷移工具與例外流程。
>
> Harbor 的 v1 同時符合 compulsory 的三個條件：它造成重複扣款事故、讓服務落在處理原始卡號的嚴格稽核範圍、而且金流商設定了外部截止日。再加上遙測顯示 advisory 階段的燃盡已經停滯，照當時速度要將近一年才會歸零，還出現了新的使用者。這些都說明單靠建議已經無法達成目標。

> [!question]- Q3. 遙測顯示舊 API 已經連續 30 天沒有任何流量，你是負責人，可以關閉它嗎？
> 不一定，30 天只能證明「這 30 天內沒有人呼叫」。要先問幾個問題：這個 API 是否可能被季度或年度的工作使用（例如季度對帳、年度稅務報表）？是否有只在特定活動才啟用的流程？是否有離線裝置或久久才開一次的舊 app？遙測本身是否完整，例如是否涵蓋所有入口與區域？
>
> 如果答案不確定，做法是延長靜默期到涵蓋最長的已知週期，對已知的低頻使用者取得 owner 書面確認，並在關閉時保留可以快速重開的開關與觀察期。兩種錯誤的代價不對稱：太早關閉可能造成一個沒人立刻發現的事故，延後關閉只是多維護幾週，所以在證據不足時應該選擇保守。

> [!question]- Q4. Brownout 有什麼好處與風險？你會怎麼設計 Harbor v1 的 brownout？
> Brownout 的好處是讓看不見的使用者主動現身：沒有讀公告、沒有 owner 的系統，會在計畫性中斷時看到錯誤，於是有人來問。它也讓使用者在真正關閉前就體驗到失敗，提早修正自己的錯誤處理。風險是它確實會造成真實的失敗，對付款這類關鍵路徑尤其敏感，若時段選錯（例如促銷高峰）可能造成營收損失。
>
> Harbor 的設計可以是：事先公告時段，從每週一次 15 分鐘、低峰時段開始，逐步延長到每天一小時；錯誤回應使用 410 並在 body 附上遷移指南與聯絡方式；刻意安排一次涵蓋季度對帳工作的時段；避開雙十一等促銷期間；brownout 期間由值班者監控錯誤來源，並為每個被撞到的 consumer 開追蹤 issue。如果 brownout 影響的流量仍然很大，代表遷移支援不足，應該放慢而不是加強。

> [!question]- Q5. 為什麼「先封住入口」比「先處理既有使用者」更優先？
> 因為淘汰是一個流量問題：剩餘使用者的數量等於既有使用者減去已遷移者，再加上新加入者。如果不擋住新加入者，即使遷移團隊每週處理三個使用者，只要同時有兩個新使用者加入，進度就幾乎停滯；更糟的是，新加入者通常是不知道淘汰計畫的人，例如新進工程師或 AI coding agent，他們會從 repo 裡的範例學會舊用法。
>
> 封住入口的成本通常很低：一個 CI 的 ratchet 檢查、一條 lint 規則、停止發放新的 API key。它一旦生效，使用者數量就只會減少，遷移團隊的每一份努力都會反映在進度上。Harbor 的 AI 客服退款工具正是因為沒有這道防線，才在 v1 被標記淘汰半年後成為新的使用者。

> [!question]- Q6. Adapter（shim）讓舊的呼叫方式繼續運作，這不是正好解決了遷移問題嗎？它有什麼風險？
> Adapter 確實能爭取時間：使用者不必立刻改程式，提供方可以先刪除舊系統的核心實作，只保留一層轉接。對於發布週期很長的合作夥伴，這常常是必要的過渡手段。但它有三個風險。第一是語意可能悄悄改變：Harbor 的 v1 沒有 idempotency key，adapter 若為每次請求產生新 key，重送仍然會重複扣款，等於把舊問題帶進新系統。
>
> 第二是 adapter 本身也是程式碼，需要維護、測試與監控。第三是它可能讓使用者永遠不遷移，因為「反正還能用」，最後 adapter 變成了新的 v1。對策是為 adapter 寫專門的語意測試、比較新舊輸出，並在公告中給 adapter 一個明確的淘汰日期，把它定位成過渡而不是終點。

> [!question]- Q7. Harbor 讓 AI coding agent 為十幾個仍在使用 v1 的服務與 repo 產生遷移 PR。你會設計哪些 guardrails？
> 首先是範圍：每個服務一個小 PR，只做遷移這一件事，不順便重構，這樣 review 容易、出問題也能獨立回復。其次是驗證：每個 PR 必須通過 CI、contract test，以及一組針對遷移語意的代表性測試（重送時只扣一次款、金額邊界、錯誤處理），測試由人設計，而不是讓 agent 自己寫測試證明自己正確。
>
> 第三是權限與核准：每個 PR 由該服務的 owner review，涉及金流的路徑額外要求 payments 團隊核准；agent 不能修改 ratchet 名單、不能加忽略規則讓 CI 通過，這些檔案用 CODEOWNERS 保護。第四是上線節奏：PR 合併後依一般的 canary 流程漸進部署（第 29 章），並監控每個服務的付款成功率。最後，agent 回報「已完成所有遷移」時，仍要以 runtime 遙測確認 v1 流量確實下降，而不是只相信 PR 的數量。

> [!question]- Q8. 面試題：你負責淘汰一個被數十個內部團隊使用的舊函式庫。請說明你的完整計畫。
> 第一步是評估與盤點：確認替代方案涵蓋使用者實際用到的功能，用 code search 找出所有呼叫點，在函式庫中加入使用遙測，並寫一份 ADR 說明為什麼要淘汰、成本由誰承擔。第二步是宣布並封住入口：發出包含原因、時程、遷移指南與支援管道的公告，同時在 CI 加上 ratchet，讓新的使用無法加入。
>
> 第三步是集中遷移：用 codemod 或 AI agent 產生小型 PR，由我的團隊送給各使用方 review，只把無法自動化的部分留給他們，並舉辦 office hours。第四步是追蹤與強制：用儀表板追蹤剩餘使用者與燃盡趨勢，在停滯時升級手段，例如把 deprecation warning 移到 code review 與 IDE、指派追蹤 issue 給 owner，並處理有期限的例外。最後是移除與清理：確認靜默期與 owner 確認後刪除函式庫、相關設定與文件，記錄經驗並公開感謝參與的團隊。回答時可以強調兩個重點：遷移成本由提供方承擔，以及先封住入口。
