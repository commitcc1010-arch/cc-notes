## 42.1 故事：每個 job 都是綠燈，賣家的雙十一卻少了一截

Harbor 第四年的雙十一結束後兩天，賣家後台的客服信箱開始收到同一類信：「我 11/11 的營收怎麼只有預期的一半？」「我 11/10 根本沒什麼訂單，報表卻顯示破紀錄？」最先接到的是產品經理 Lisa。Lisa 打開內部的營收儀表板，看到的數字和賣家說的一樣奇怪。

seller 團隊負責的 `seller_revenue_daily` pipeline 每天凌晨跑一次：讀取前一天的訂單事件，依賣家與日期加總，寫進資料倉儲，再供賣家後台、平台抽成計算與月底的服務費電子發票使用。排程系統的紀錄顯示，過去一週每一次執行都是 `SUCCEEDED`，輸入筆數、輸出筆數都和平常的趨勢一致，沒有任何告警。

seller 團隊的阿凱花了一個下午才找到原因。三週前，checkout 團隊的阿哲做了一次「技術債清理」，把訂單事件的 `created_at` 從「台灣時間、沒有時區的字串」改成「UTC、帶時區的 ISO 格式」。這個變更通過了 code review，checkout 自己的測試也全過。但 `seller_revenue_daily` 一直是用 `created_at` 的日期部分直接分組，格式一換，每天 00:00 到 08:00（台灣時間）的訂單全被算到前一天。平常凌晨訂單不多，誤差被淹沒在日常波動裡；雙十一零點開賣的那一波搶購，卻整批被算成 11/10 的營收。

更糟的發現接著出現。對帳時阿凱發現，就算把時區修好，11/11 的總額仍比金流商的撥款明細多了約 1%。原因是訂單事件經過 message queue 傳遞時採用 at-least-once 語意（第 41 章），雙十一流量大、重試多，有一部分事件被送了兩次，而 pipeline 從來沒有去重。這個誤差平常只有 0.1% 左右，一直沒人注意。

修正也不簡單。倉儲裡的日報表是「每天覆寫」的，沒有保留舊版本，沒人說得出 11/10 那份錯誤的數字被哪些下游拿去用過；抽成計算已經依錯誤數字開出一批服務費電子發票，必須作廢重開；原始事件在 message queue 只保留 7 天，最早那幾天的資料要從 checkout 資料庫的備份裡撈，而那份備份從來沒有被還原過。

SRE 志明在事後檢討時寫下一句話：「我們監控了 pipeline 有沒有跑，沒有監控它跑出來的東西對不對。」這一章要回答的，就是怎麼讓資料系統在「程式成功」之外，還能證明「資料正確」，並且在資料真的壞掉時救得回來。

## 42.2 Data pipeline 的基本形狀

### 什麼是 pipeline

**Data pipeline**（資料管線）是一連串把資料從來源搬到目的地、途中做轉換的處理步驟。每一個步驟叫一個 **stage**（階段），stage 之間的依賴關係通常畫成一張 **DAG**（directed acyclic graph，有向無環圖：箭頭有方向、不會繞回自己）。Harbor 的營收管線長這樣：

```text
 checkout DB ──CDC──▶ 訂單事件 queue ──▶ ① raw 層（原樣保存）
                                             │
                                             ▼
                                   ② 清理：解析時間、去重、驗證 schema
                                             │
                          ┌──────────────────┼──────────────────┐
                          ▼                  ▼                  ▼
                 ③ 賣家日營收         ④ 平台抽成計算      ⑤ 搜尋排序特徵
                          │                  │
                          ▼                  ▼
                   賣家後台儀表板       服務費電子發票（外部副作用）
```

這張圖可以由左往右讀成一段資料的生命。最左邊的 **CDC**（change data capture，變更資料擷取）會把資料庫的每筆新增、修改轉成事件送出。① **raw 層**把事件原封不動地保存下來，不做任何解讀；它的價值在出錯時才顯現：只要原始資料還在，任何下游錯誤都能修好程式後重算。② 清理 stage 把原始資料變成可信的形式。③ 到 ⑤ 是各個用途的衍生資料。最右下角的電子發票特別標成「外部副作用」，因為它一旦發出去，就不是重跑 pipeline 可以收回的，必須走作廢、折讓這類業務流程。

Harbor 這次事故的錯誤發生在 ② 解析時間的那一步，但傷害一路擴散到 ③、④ 和外部世界。這就是 pipeline 的特性：**錯誤會沿著 DAG 往下游傳播，而且越往下游越貴**。

### Batch 與 streaming

依處理方式，pipeline 大致分兩種：

- **Batch**（批次）：每隔一段時間處理一批累積的資料，例如每天凌晨處理前一天的訂單。簡單、容易重跑，但結果天生有延遲。
- **Streaming**（串流）：資料一進來就持續處理，例如即時更新的「熱銷排行」。延遲低，但要處理亂序、遲到與重複的事件。

兩者的邊界越來越模糊：很多 streaming 系統以「小批次」實作，很多 batch 系統一小時跑一次。重點不是名稱，而是你的資料有多新才夠用。

### Event time 與 processing time

Streaming 裡最容易出錯的觀念，是兩種時間的差別。**Event time** 是事情真正發生的時間，例如使用者按下付款的那一刻；**processing time** 是 pipeline 處理到這筆資料的時間。使用者在 23:59 下單，手機網路不穩，事件 00:03 才到達，以 processing time 計算，這筆營收會掉到隔天。

營收、對帳這類「依日期歸屬」的計算一定要用 event time，而且要明確寫出時區。但 event time 帶來另一個問題：你永遠不確定某一天的資料到齊了沒。解法是 **watermark**（水位線）：pipeline 估計「event time 早於 T 的資料應該都到了」，到達 watermark 後才產生 T 之前的結果；之後才遲到的資料，依事先定好的規則處理，例如更新結果並通知下游，或寫進一個「遲到資料」表等待人工判斷。

> [!warning] 常見誤解
> 「時間戳記就是時間戳記。」不對。一個欄位叫 `created_at`，不代表它是 event time，也不代表它是 UTC。Harbor 的事故就是兩個團隊對同一個欄位的時區有不同的隱含假設。時間欄位的語意（哪一種時間、哪個時區、精度）應該寫進 schema 與資料契約，而不是靠口耳相傳。這也是 Hyrum's Law（第 5 章）在資料世界的版本：只要格式能被觀察到，就會有人依賴它。

## 42.3 Periodic 與 continuous pipeline

### Periodic pipeline 為什麼一開始很好用

最常見的 pipeline 是 **periodic pipeline**（定期管線）：用排程器每隔一段時間啟動一次，每次處理一批資料，處理完就結束。它容易理解、容易重跑、每一次執行都有清楚的邊界。Harbor 的營收日報、每晚的搜尋索引重建，一開始都是這種形式。SRE 書的看法是，只要 worker 足以應付資料量、運算需求在容量之內，periodic pipeline 通常很穩定，Google 內部也大量使用；問題出在規模變大、或需求變成「持續更新」之後。

### 規模變大後的四個典型問題

SRE 書第 25 章列舉了工作分配不均（hanging chunk）、共享叢集的排程與容量、監控困難、thundering herd 與 moiré load pattern 等問題。下面把它們和一個資料工程中很常見的問題（資料沒到齊）整理成四類。

**第一，工作分配不均。** 一次執行通常把資料切成很多 **chunk**（分片）平行處理。但資料常常是傾斜的：Harbor 有一個大賣家在雙十一的訂單量是其他賣家的一千倍。整個 job 必須等最慢的那個 chunk 完成，SRE 書把這種「一個分片卡住整批」的狀況稱為 **hanging chunk** 問題；它還提醒，看到 job 卡住就直接砍掉重跑，往往讓情況更糟，因為沒有 checkpoint 的 pipeline 會連已完成的分片一起重做。九十九個分片五分鐘就做完，最後一個要兩小時，整個 pipeline 就要兩小時。

**第二，執行時間追上排程間隔。** 一個每小時跑一次的 job，資料成長到每次要跑 70 分鐘，下一次就會在上一次還沒結束時啟動（第 41 章討論過重疊執行的處理方式）。延遲會一路累積，直到有人發現報表已經落後半天。SRE 書也指出 periodic pipeline 的監控天生困難：job 跑完就結束，執行中的指標來不及被觀察，常常只能在結束後才知道它慢了或錯了。

**第三，負載的尖峰互相疊加。** 很多 job 都排在整點或凌晨 2 點，它們會在同一時間搶共用的資料庫與運算資源。SRE 書把多個週期性負載疊出來的高低起伏形容成 **moiré load pattern**（疊紋般的負載型態），而大量 worker 同時啟動、同時重試，就是 **thundering herd**（第 41 章）。

**第四，「這次跑完了」不代表「資料到齊了」。** Periodic job 在固定時間啟動，但上游資料不一定準時到。如果凌晨 2 點啟動時，上游還有一個 partition（資料分區）沒寫完，job 會開心地處理「它看到的所有資料」，然後回報成功。

### Continuous pipeline 與 Workflow 的設計

當 periodic pipeline 撐不住時，下一步是 **continuous pipeline**（持續管線）：pipeline 一直在運作，資料到了就處理，不再依賴「每天一次」的排程。SRE 書介紹了 Google 在 2003 年開發的 **Workflow** 系統，它讓持續處理能在大規模下運作。書中用 model-view-controller 的比喻說明它：model 是一個叫 **Task Master** 的中央伺服器，保存所有工作的狀態；view 是不斷回報進度的 worker；controller 則是可選的、用來調整整體行為的元件。這套設計思想至今仍適用於大部分 pipeline 框架，核心有三點：

1. **集中的狀態，無狀態的 worker。** Task Master 把所有工作項目的狀態（待處理、處理中、完成）放在記憶體裡以便快速存取，並把每一次狀態變更同步寫進持久化的日誌；實際的輸入輸出資料放在共用的儲存系統，Task Master 只保存指向它們的指標。Worker 本身不保存狀態，只負責向 Task Master 認領工作、做完回報。Worker 隨時死掉都沒關係，工作會被重新分配。
2. **用 lease 認領工作。** Worker 認領的工作有期限（lease），超時沒回報就會被收回給別人；只有持有有效 lease 的 worker 才能提交結果。（書中還有一項保證：client 與 server 在每次操作時都會檢查 server token，確認自己對話的是正確的 Task Master。）這和第 40、41 章的 lease 與 fencing token 是同一個想法：防止一個以為自己還在工作的舊 worker 把過期的結果寫進去。
3. **輸出唯一命名，提交才生效。** 每個 worker 的輸出寫到唯一的檔名或暫存位置，Task Master 確認提交後，才把它當成正式結果。因此重試、重複執行都不會覆蓋掉別人的輸出，失敗的半成品也不會被下游讀到。

今天的開源工具，例如 Apache Airflow、Dagster、Argo Workflows 這類 workflow orchestrator（工作流程編排器），以及各種 streaming 框架，介面各不相同，但你評估它們時可以問同樣的問題：狀態存在哪裡？worker 死掉時工作怎麼收回？重複執行會不會產生重複輸出？下游能不能讀到寫到一半的結果？

### 讓 stage 可以安全重跑

不管 periodic 還是 continuous，每個 stage 都要能被安全地重跑，因為重跑是修復資料錯誤的主要手段。做法和第 41 章的 idempotency 一脈相承：

- **以「分區覆寫」取代「累加」。** 「把 11/11 這個分區整個重算並原子性替換」可以重跑任意次；「把今天的數字加到總額上」重跑一次就錯一次。
- **先寫到暫存位置，驗證通過才發布。** 這種 **write-audit-publish**（寫入、稽核、發布）模式讓下游永遠只看到通過檢查的版本。
- **用業務主鍵去重。** At-least-once 的來源一定會有重複，清理 stage 用 `order_id` 這類業務上的唯一識別去重，而不是相信來源「應該不會重送」。
- **外部副作用放在最後，並且有自己的 idempotency key。** 發票、通知、撥款這類動作不能和計算混在一起，否則重算一次就多發一次。

## 42.4 Pipeline 的 SLO：沒有請求的服務怎麼定義「好」

第 32 章提過，批次與資料管線沒有「請求」，需要不同形式的 SLI。這一節把它展開。資料管線的使用者在意三件事：資料夠不夠新、夠不夠完整、對不對。

| SLI 類型 | 問的問題 | Harbor 的例子 | 常見量法 |
|---|---|---|---|
| **Freshness**（新鮮度） | 資料落後現實多久？ | 賣家後台的營收落後不超過 2 小時 | 「最新一筆已發布資料的 event time」與現在的差距；或「新鮮度達標的分鐘比例」 |
| **Completeness**（完整性） | 該來的資料都到了嗎？ | 每個營業日的所有 partition 都在 06:00 前到齊 | 預期的 partition、來源數或筆數 vs 實際 |
| **Correctness**（正確性） | 算出來的結果對嗎？ | 每日營收與金流商撥款明細差異小於 0.1% | 與獨立來源對帳；抽樣人工驗證；業務規則檢查 |

也可以加上 **coverage**（涵蓋率），例如「搜尋索引包含 99.9% 的上架商品」。SLO 的寫法和線上服務一樣：「30 天內，95% 的營業日，前一天的賣家營收在 06:00 前發布，且與撥款明細差異 < 0.1%」。

Freshness 最容易量，但它無法抓到 Harbor 這次的事故：資料每天都準時發布，只是錯的。**Correctness 才是資料管線最重要、也最常缺席的 SLI。** 它難量，因為你需要一個「正確答案」來比較。實務上有三種來源：

1. **獨立的外部來源**：金流商的撥款明細、銀行對帳單、物流商的出貨紀錄。這是最強的證據，因為它和你的 pipeline 不共用任何程式碼或假設。
2. **不同算法的交叉驗證**：例如同時從訂單事件與付款事件各算一次營收，兩條路徑的結果應該一致。
3. **業務不變條件**（invariant）：退款金額不能大於原訂單金額；每個訂單必須屬於一個存在的賣家；一天的營收不會突然變成前一週平均的 0.3 倍或 3 倍，除非行事曆上標了促銷。

> [!note] 為什麼「獨立」這麼重要
> 如果驗證邏輯和產生資料的邏輯共用同一個時間解析函式，兩邊會一起錯，然後一起說「沒問題」。SRE 書談的 **out-of-band**（帶外）驗證就是這個想法：在提供服務的主要路徑之外，另外跑一套檢查資料的 pipeline，在資料之內與資料儲存之間互相核對。驗證越獨立，越能抓到主要路徑的 bug。

### 品質檢查：讓壞資料過不了關

每個 stage 的輸出在發布前應該通過一組 **data quality check**（資料品質檢查）。由便宜到昂貴大致是：

| 層次 | 檢查什麼 | 例子 | 能抓到 Harbor 的問題嗎？ |
|---|---|---|---|
| Schema | 欄位、型別、必填 | `created_at` 必須帶時區 | 能，如果 schema 有寫明時區 |
| 值域 | 範圍、格式、null 比例 | 金額 > 0；null 比例 < 0.1% | 不能 |
| 唯一性與參照 | 主鍵不重複、外鍵存在 | `order_id` 不重複 | 能抓到重複事件 |
| 量與分佈 | 筆數、總額與歷史比較 | 每小時訂單量與上週同時段相比 | 可能：00–08 時段的訂單突然變零 |
| 對帳與不變條件 | 與獨立來源或業務規則比對 | 與撥款明細差 < 0.1% | 能，而且最可靠 |

注意最常見的「row count 檢查」（輸入筆數夠不夠多）完全抓不到 Harbor 的問題：每一筆資料都在，只是被放錯日期。檢查要對準「這份資料被用來回答什麼問題」，而不是只看它有沒有東西。

檢查失敗時有兩種處理方式。**Fail closed**：停止發布，下游繼續使用上一個好的版本，並告警；適合營收、抽成這類錯了比晚到更糟的資料。**Quarantine**（隔離）：把不合格的資料列移到一個隔離區，其餘照常發布；適合少量髒資料不影響整體結論的情況，例如推薦系統的點擊紀錄。隔離區要有 owner、容量上限與處理期限，否則它會變成沒人管的資料墳場，而裡面可能正躺著真正的 bug 證據。

### 資料契約：把隱含假設寫下來

Harbor 的事故從根本上是一個沒有被寫下來的約定。**Data contract**（資料契約）是生產者與消費者之間對資料格式與語意的明文約定：欄位意義、時區、單位、可能的值、更新頻率、誰是 owner，以及變更要提前多久通知。它和第 17 章的 API contract 是同一件事，只是對象是資料。

契約的關鍵不在文件，而在強制執行：在生產者的 CI 裡檢查 schema 變更是否相容，不相容的變更必須升版本、並行一段時間，讓消費者遷移（第 18 章的 deprecation 流程）。如果 checkout 團隊當時的 CI 會提醒「這個欄位有 3 個下游消費者，語意變更需要通知」，這次事故很可能在 code review 階段就被攔下來。

## 42.5 Data integrity：資料會用哪些方式壞掉

### 定義

**Data integrity**（資料完整性）在 SRE 書中是以使用者為中心定義的：它大致可以說是「提供足夠服務水準所需的資料，能不能被存取、是不是正確」，而書中也強調，最終是使用者怎麼感受說了算。資料「在某個磁碟上的某個地方」不算數；書中舉的例子是，Gmail 的介面 bug 讓信箱看起來是空的太久，就算資料一筆沒少，對使用者而言也等於資料不見了。

SRE 書第 26 章的標題後半「What You Read Is What You Wrote」把它濃縮成一句話：讀到的，必須是寫進去的。

### 失敗模式的三個維度

SRE 書建議用三個維度分析資料會怎麼壞。其中「速度」分成兩種：**big bang**（一次性、瞬間發生，例如一分鐘內一百萬筆被換成十筆）與 **creeping**（緩慢蔓延，例如連續幾週每分鐘刪掉十筆）。

```text
  失敗原因（root cause）        影響範圍（scope）     發生速度（rate）
  ─────────────────────        ─────────────────     ────────────────
  使用者自己的操作              廣：大量資料           Big bang：一次性、瞬間
  維運人員的錯誤                窄：少數使用者或欄位   Creeping：緩慢蔓延
  應用程式的 bug
  基礎設施的缺陷
  硬體故障
  站點級災難（機房、區域）

  6 × 2 × 2 = 24 種組合，每一種需要的防禦不同
```

這個表的用途是逼你想清楚「我的防禦對哪一種組合有效」。幾個例子：

- **維運錯誤 × 廣 × big bang**：有人在 production 下錯 `DELETE` 指令。立刻就會被發現，需要的是能快速還原到幾分鐘前的備份。
- **應用程式 bug × 廣 × creeping**：Harbor 的時區 bug 就屬於這類。每個賣家都受影響，但每天只錯一點，持續三週才被發現。這種錯誤最可怕，因為等你發現時，所有「最近的」備份裡的資料都已經是錯的；你需要保留期夠長的備份，或者能從原始資料重算。
- **站點級災難 × 廣 × big bang**：整個雲端區域不可用。需要的是存在另一個區域、甚至另一個供應商的副本。
- **使用者操作 × 窄 × big bang**：賣家誤刪了自己的商品目錄。需要的是讓使用者自己能復原的機制，而不是半夜叫醒 SRE。

### 多層防禦

沒有一種機制能涵蓋 24 種組合，所以 SRE 書描述的是一組 **defense in depth**（縱深防禦：多層機制，每一層攔下前一層漏掉、也更少見的情況）：

```text
  第 1 層  Soft delete（軟刪除）     使用者與程式的誤刪，數天內可自行復原
     │
  第 2 層  Backup 與 restore         還原到過去某個時間點；保留期決定能退多遠
     │
  第 3 層  Out-of-band 驗證（及早偵測） 持續、獨立地檢查資料，縮短「出錯到發現」的時間
     │
  貫穿     Replication（複製）       讓每一層（包括備份本身）都有副本；不防邏輯錯誤
```

**Soft delete** 是指刪除時先不真的移除資料，只標記成「已刪除」並對使用者隱藏，保留一段期間後才由背景工作真正清除。它處理的是最常見的情況：使用者或程式誤刪。Harbor 的賣家刪掉商品後 30 天內都可以在「最近刪除」裡找回來，不需要動用備份。Soft delete 的代價是查詢都要記得過濾已刪除的資料，以及保留期間資料仍然存在，要和隱私與法規要求一起設計（42.6 節最後會談）。

**Replication**（複製）把資料即時同步到其他機器、機房或區域，防的是硬體與站點故障。SRE 書把它放在貫穿各層的位置：理想上連備份本身也要有副本，但資料復原計畫不應該依賴 replication。但它**不是備份**：錯誤的 `DELETE`、寫壞資料的 bug，會在幾秒內忠實地同步到所有副本。複製保護的是「資料還在不在」，不是「資料對不對」。

**Out-of-band 驗證**是第三層，SRE 書稱之為 early detection（及早偵測）。前兩層決定了「發現之後能救多少」，驗證決定了「多快發現」。Harbor 的時區 bug 如果在第一天就被對帳抓到，只要重算一天的資料；三週後才發現，要重算三週、作廢一批發票，還要擔心原始資料是否還在。**偵測時間直接決定了修復的成本**，這也是為什麼 SRE 書說，優秀資料完整性的關鍵在於主動偵測，以及快速修復與還原。

## 42.6 Backup 不是重點，restore 才是

### 「沒有人真的想要備份」

SRE 書引用了一句業界常被提起的話：沒有人真的想要做備份，大家想要的是還原（No one really wants to make backups; what people really want are restores）。書中因此主張要交付的是「復原系統」，而不是「備份系統」，並區分 backup 與 **archive**（歸檔）：backup 能被載回應用程式使用，archive 只是長期保存。備份只是手段，在需要時能把資料救回來才是目的。這句話的實務意義是：**一個沒有被還原過的備份，你只能假設它不存在。**

Harbor 在雙十一事故後的第三週就體會到這件事。一次資料庫 migration 的 bug 在下午 14:37 把商品評論表清空，16:10 才被發現。團隊信心滿滿地拿出每日備份，接著遇到一連串沒想過的問題：備份檔在另一個帳號，值班者沒有權限讀取；還原需要的加密金鑰放在一位已離職同事設定的 secret 裡；800 GB 的資料以實際速度還原要五個多小時，而 runbook 上寫的是「約 30 分鐘」，那是兩年前資料只有 40 GB 時量的。最後，因為只有每日 00:00 的快照，00:00 到 14:37 之間寫入的評論，只能從應用程式日誌一筆筆撈回來。

### RPO 與 RTO

設計備份前要先回答兩個問題：

- **RPO**（Recovery Point Objective，復原點目標）：最多能接受遺失多久的資料？RPO 是 1 小時，代表還原後最多少掉最近 1 小時的寫入。
- **RTO**（Recovery Time Objective，復原時間目標）：從事故發生到服務恢復，最多能花多久？這段時間包含發現問題、決定還原、真正搬資料與驗證，不只是機器還原的時間（第 46 章用的是同一個定義）。

```text
          最後一個可用的還原點         出事             恢復服務
  ──────────────●─────────────────────────✕───────────────────●──────▶ 時間
                │◀──── 實際遺失的資料 ────▶│◀── 實際還原時間 ──▶│
                        （要 ≤ RPO）                （要 ≤ RTO）
```

RPO 由「多久產生一個還原點」決定：每日快照的 RPO 最差接近 24 小時；持續保存資料庫的交易日誌（例如 PostgreSQL 的 WAL、MySQL 的 binlog），可以做到 **PITR**（point-in-time recovery，還原到任意時間點），RPO 降到幾分鐘以內。RTO 則由資料量、還原速度、重播日誌的時間，以及**人**決定：找到正確的備份、取得權限、決定還原到哪個時間點，往往比機器搬資料更花時間。

不同資料應該有不同的 RPO／RTO。Harbor 的訂單與付款資料 RPO 是 1 分鐘、RTO 是 1 小時；商品評論 RPO 15 分鐘、RTO 8 小時；推薦系統的特徵資料可以從 raw 層重算，根本不需要備份。把所有資料都設成最嚴格的目標，成本會失控；全部設成一樣寬鬆，關鍵資料就沒有保護。

### 3-2-1 原則

業界最常用的備份經驗法則是 **3-2-1**：

- **3** 份資料：production 一份，加上至少兩份備份。
- **2** 種不同的儲存媒介或系統：避免同一種故障（同一個 bug、同一個廠商的問題）同時毀掉所有副本。
- **1** 份放在異地：不在同一個機房、區域，最好也不在同一個帳號與權限範圍內。

雲端時代最常被忽略的是「**同一個帳號**」這個 failure domain（故障域：會一起失效的範圍）。如果攻擊者拿到 production 帳號的管理權限，或一支自動化腳本有權刪除帳號裡的所有資源，放在同一帳號的備份會和 production 一起消失。勒索軟體攻擊也常會先找出並刪除備份。因此很多組織把 3-2-1 延伸成 3-2-1-1-0：多一份 **immutable**（不可變：在保留期內任何人都無法修改或刪除，包括管理員）或與網路隔離（air-gapped）的副本，並且備份經過還原驗證後的錯誤數為 0。3-2-1 與 3-2-1-1-0 都是業界的經驗法則，不是 SRE 書的內容。

### 備份的種類

| 類型 | 做法 | 優點 | 代價 |
|---|---|---|---|
| 完整備份（full） | 每次複製全部資料 | 還原簡單 | 慢、佔空間 |
| 增量備份（incremental） | 只複製上次之後的變動 | 快、省空間 | 還原要串起一整串 |
| 快照（snapshot） | 儲存層在某一刻凍結的影像 | 幾乎瞬間完成 | 常和原資料在同一系統，需另外複製出去 |
| 交易日誌（WAL／binlog） | 持續保存每筆變更 | 可還原到任意時間點 | 需要搭配基礎備份，重播要時間 |
| 邏輯匯出（dump） | 匯出成 SQL 或檔案 | 可跨版本、可只還原部分資料 | 大型資料庫很慢 |

還有一個常被忽略的維度：**保留期要長於「偵測時間」**。如果一個 creeping 的 bug 平均三週才被發現，而備份只保留 7 天，所有備份裡都是壞資料。這時能救你的只剩下更長保留期的備份，或是 raw 層的原始資料加上可重算的 pipeline。

### 還原演練

證明備份可用的唯一方法是定期真的還原。一個有效的 **restore drill**（還原演練）包含：

1. **在隔離環境還原**，而不是只檢查備份檔「存在」或「大小正常」。
2. **驗證內容**：checksum 與筆數只是開始；還要跑業務查詢，例如「11/11 的訂單總額是否與帳務系統一致」。
3. **量測真實時間**，更新 runbook 裡的 RTO，並和目標比較。資料會成長，去年的數字不能用。
4. **由不同的人操作**：如果只有一位資深工程師會還原，那麼這位工程師休假時，你的 RTO 就是「等人回來」。
5. **把演練自動化並告警**：每週自動還原一份隨機挑選的備份並驗證，失敗就告警。這把「我們有備份」變成一個持續被證明的事實。

第 46 章的 disaster recovery 演練會把這件事擴大到整個服務與區域層級。

### 刪除也是完整性的一部分

完整性不只是「不要弄丟資料」，也包括「該刪除的時候真的刪掉」。使用者依個資相關法規要求刪除帳號時，資料不只在 production，也在 soft delete 區、備份、raw 層、衍生資料表、分析倉儲，甚至 AI 的向量索引裡。常見做法有兩種：在保留期到期時自然過期，並在政策中明確告知使用者；或者用 **crypto-shredding**（加密銷毀）：每位使用者的資料用專屬金鑰加密，刪除時銷毀金鑰，所有備份中的對應資料就再也無法解讀。不管哪種，都需要 lineage（下一節）才能知道一位使用者的資料流到了哪些地方。

## 42.7 Provenance 與 lineage：資料從哪裡來，又流到哪裡去

### 兩個相關的詞

**Provenance**（來源證明）回答的是「這份資料是怎麼產生的」：用了哪些輸入、哪個版本的程式與設定、什麼時候、由誰（哪個服務身份）執行。第 27 章談過建置產物（artifact）的 provenance：一個 container image 可以追溯到產生它的 commit 與 build 環境。資料也需要同樣的東西。

**Lineage**（血緣）是把所有 provenance 串起來的圖：資料集 A 由 B 與 C 產生，B 又由 D 產生。它讓你可以往兩個方向走：

- **往上游追**（root cause）：這份錯誤的報表，是哪個上游的哪個版本造成的？
- **往下游追**（impact analysis，影響分析）：如果 11/10 的清理結果是錯的，哪些報表、模型、發票、外部匯出用過它，需要重算或通知誰？

Harbor 的事故中，阿凱花最多時間的不是修 bug，而是回答第二個問題。因為日報表每天覆寫、沒有記錄誰讀過，團隊只能翻遍各團隊的 SQL 與排程，猜測有哪些下游可能受影響。

### 每次執行要記錄什麼

一份實用的 provenance 紀錄通常包含：

```text
dataset:        seller_revenue_daily / partition=2026-11-11 / version=7
produced_by:    payout-agg job, run_id=r-20261112-0200-a
code_version:   git commit 3f2c1e9（含 container image digest）
config:         timezone=Asia/Taipei, dedupe_key=order_id
inputs:         orders_clean / partition=2026-11-11 / version=4（內容 sha256: 5fbe…）
                sellers_dim  / snapshot=2026-11-12T00:00Z
checks:         schema PASS, uniqueness PASS, reconciliation PASS (diff 0.00%)
consumers:      seller_dashboard, commission_invoicing（由讀取紀錄自動收集）
```

這份紀錄有三個關鍵。第一，輸入要指向**特定版本**，而不是「orders_clean 這張表」，否則表被覆寫後紀錄就失去意義。第二，要包含**內容的指紋**（checksum／hash），證明輸入的位元組就是當時用的那些。第三，消費者最好由系統自動記錄，而不是靠各團隊自行登記，因為人工登記一定會漏。

實務上，很多資料平台與 orchestrator 會自動收集這些資訊，開放標準如 OpenLineage 定義了 job、run、dataset 之間的事件格式，讓不同工具產生的 lineage 能匯集在一起。工具不是重點，重點是**資料集要有版本、輸入要能追到版本、讀取要留下紀錄**。

### 版本化與不可變

Lineage 能運作的前提，是資料**不被原地覆寫**。如果 11/11 的分區每次重算都覆蓋舊值，你就無法回答「上週一那份報表看到的是哪個數字」。比較好的做法是把每次產出視為一個新的、不可變的版本，再用一個指標（「目前版本 = 7」）指向正式版本；回滾只要把指標移回去。現代的資料湖表格式與物件儲存的版本功能，都是在提供這種能力。版本化也有成本：儲存空間與敏感資料的保留期，所以要搭配清楚的保留政策。

## 42.8 AI 訓練資料與 RAG 的資料管線

AI 系統讓資料管線直接變成了產品行為。Harbor 的 AI 客服 agent 會根據 **RAG**（retrieval-augmented generation，檢索增強生成：先從知識庫找出相關文件，再讓模型根據這些文件回答）回答退貨政策問題。它的知識庫是一條標準的 pipeline：

```text
 政策文件、FAQ、訂單說明
        │  擷取（記錄 doc_id、版本、owner、存取權限 ACL）
        ▼
   切塊（chunking）  ──▶ 每個 chunk 記錄來源 doc_id + 版本 + 位置
        │
        ▼
   embedding（向量化） ──▶ 記錄 embedding 模型版本
        │
        ▼
   向量索引（index build #N） ──▶ 記錄包含哪些 doc 版本
        │
        ▼
   檢索 ＋ 模型回答 ──▶ 回答附上引用的 chunk 與 index 版本
```

這條管線出錯的方式，和營收管線驚人地相似：

- **Freshness**：退貨期限從 7 天改成 10 天，政策文件更新了，向量索引還是上週建的，agent 繼續告訴客人「7 天」。這是 freshness SLO 的問題，應該量測「文件更新到可被檢索」的延遲。
- **Correctness 與 lineage**：客人投訴 agent 給了錯的資訊時，你需要能回答「當時檢索到哪幾個 chunk、來自哪份文件的哪個版本、用哪個 index」。沒有這份 provenance，你連問題是出在資料、檢索還是模型都分辨不出來。
- **權限**：如果內部的「客服主管處理準則」被不小心放進同一個索引，agent 可能把內部規則說給客人聽。索引必須保留原始文件的 ACL，在檢索時依提問者身份過濾。OWASP 的 LLM 應用 Top 10（2025 年版）把這類問題列為 LLM08「Vector and Embedding Weaknesses」（向量與 embedding 的弱點，包括跨使用者或跨權限的資訊外洩）；有人把惡意或錯誤內容放進知識庫或訓練資料，則屬於 LLM04「Data and Model Poisoning」（資料與模型投毒）。
- **刪除**：使用者要求刪除個資時，含有該使用者對話內容的 chunk 也必須從索引移除。這需要 lineage 告訴你哪些 chunk 來自這位使用者的資料。

訓練或微調模型的資料也一樣需要 provenance：資料來源、取得授權與同意的依據、去重與過濾的步驟、資料集版本，以及**評估資料是否和訓練資料重疊**（contamination，污染：模型在考試前看過考題，eval 分數會虛高）。一個模型版本應該能追溯到它的訓練資料集版本，就像 container image 能追溯到 commit。

## 42.9 動手寫：會說謊的綠燈與救不回來的備份

這一節用兩段程式模擬本章的兩個核心機制。第一段重現 Harbor 的營收事故：同一份輸入，經過三個版本的 pipeline，看哪些檢查抓得到錯誤。

```python
import hashlib
import json
import random
from collections import Counter, defaultdict
from datetime import datetime, timedelta, timezone

TPE = timezone(timedelta(hours=8))          # 台灣時間，固定 UTC+8
rng = random.Random(42)

# 1. 來源資料：11/11 與 11/12（台灣時間）的訂單事件，時間戳記以 UTC 儲存
start = datetime(2026, 11, 10, 16, 0, tzinfo=timezone.utc)   # = 台灣 11/11 00:00
events = []
for i in range(6000):
    ts = start + timedelta(seconds=rng.randrange(2 * 86400))
    events.append({"order_id": f"o{i:05d}", "ts": ts.isoformat(),
                   "seller": f"s{rng.randrange(5)}", "amount": rng.randrange(100, 3000)})
# at-least-once 傳遞：約 1% 的事件被重送
events += [dict(e) for e in rng.sample(events, 60)]
rng.shuffle(events)

# 2. 獨立的對照來源：金流商依「台灣日期」回傳的撥款總額
settlement = defaultdict(int)
for e in {e["order_id"]: e for e in events}.values():
    day = datetime.fromisoformat(e["ts"]).astimezone(TPE).date().isoformat()
    settlement[day] += e["amount"]


def transform(rows, tz, dedupe):
    seen, out = set(), defaultdict(int)
    for e in rows:
        if dedupe:
            if e["order_id"] in seen:
                continue
            seen.add(e["order_id"])
        day = datetime.fromisoformat(e["ts"]).astimezone(tz).date().isoformat()
        out[day] += e["amount"]
    return dict(out)


def checks(name, output, rows_in):
    target_days = sorted(settlement)
    print(f"== {name}")
    print(f"  row count 檢查：輸入 {rows_in} 筆 → {'PASS' if rows_in > 5000 else 'FAIL'}")
    for day in target_days:
        got, want = output.get(day, 0), settlement[day]
        diff = (got - want) / want
        flag = "PASS" if abs(diff) < 0.001 else "FAIL"
        print(f"  {day} 對帳：pipeline {got:>9,} vs 金流商 {want:>9,} 差 {diff:+.2%} {flag}")
    extra = sorted(set(output) - set(target_days))
    if extra:
        print(f"  出現不在預期範圍的日期：{extra}")


def manifest(rows, code_version):
    raw = json.dumps(sorted(rows, key=lambda e: (e["order_id"], e["ts"])),
                     sort_keys=True).encode()
    return {"input_sha256": hashlib.sha256(raw).hexdigest()[:12],
            "input_rows": len(rows), "code": code_version}


checks("v1：UTC 日期分組、未去重", transform(events, timezone.utc, False), len(events))
checks("v2：台灣日期分組、未去重", transform(events, TPE, False), len(events))
checks("v3：台灣日期分組、依 order_id 去重", transform(events, TPE, True), len(events))
dups = sum(c - 1 for c in Counter(e["order_id"] for e in events).values() if c > 1)
print(f"\n重送事件數：{dups}")
print("v3 的 lineage 紀錄：", manifest(events, "payout-agg@3f2c1e9"))
```

  2026-11-11 對帳：pipeline 4,683,824 vs 金流商 4,625,290 差 +1.27% FAIL
  2026-11-12 對帳：pipeline 3,151,694 vs 金流商 4,638,469 差 -32.05% FAIL

  row count 檢查：輸入 6060 筆 → PASS

逐段解讀：

1. **三個版本的 row count 檢查全部 PASS。** 這就是 Harbor 事故中「每個 job 都是綠燈」的原因：筆數只能證明資料「來了」，不能證明它被正確解讀。
2. **v1 重現時區 bug。** 用 UTC 日期分組時，台灣時間 00:00–08:00 的訂單被歸到前一天，所以出現了一個不該存在的 `2026-11-10`，而 11/12 少了三成。程式產生的訂單在一天中均勻分佈，所以誤差約是 8/24；真實的雙十一零點搶購會讓 11/11 的誤差更集中、更大。「出現不在預期範圍的日期」本身就是一個便宜又有效的檢查。
3. **v2 修好時區，但仍有約 1% 的差異。** 這是 at-least-once 傳遞造成的重複。這種小誤差最危險：它小到看起來像正常波動，卻會讓每一份報表都系統性地偏高。
4. **v3 用業務主鍵 `order_id` 去重後，與金流商完全一致。** 對帳之所以有效，是因為 `settlement` 代表一個獨立的外部來源。在真實系統中，它是金流商每天提供的撥款明細檔，和 Harbor 的 pipeline 不共用任何程式碼。
5. **`manifest` 產生 lineage 紀錄。** 輸入內容的 hash 加上程式版本，可以證明「這份輸出是用哪些輸入、哪個程式產生的」。之後若有人質疑數字，可以用同樣的輸入與程式重算並比對 hash。注意它只證明位元組相同，不證明語意正確；語意要靠前面的對帳。

第二段程式模擬備份策略：同樣的三種資料事故，在四種備份設計下各能救回多少。

```python
from dataclasses import dataclass

HOUR, DAY = 60, 24 * 60          # 以「分鐘」為時間單位


@dataclass
class Strategy:
    name: str
    snapshot_every: int     # 多久做一次完整快照（分鐘）
    retention: int          # 快照保留多久（分鐘）
    has_log: bool           # 是否持續保存交易日誌，可還原到任意時間點（PITR）
    same_failure_domain: bool = False   # 是否和 production 共用同一套權限與帳號


DB_GB = 800                 # 資料庫大小
RESTORE_GB_PER_MIN = 2.5    # 從備份還原的速度（上次演練量到的數字）
LOG_REPLAY_SPEEDUP = 30     # 1 分鐘可以重播約 30 分鐘份量的交易日誌


def restore_plan(s: Strategy, bad_at: int, now: int, wiped_prod_account: bool):
    if s.same_failure_domain and wiped_prod_account:
        return None, "備份跟著 production 帳號一起被刪除"
    oldest_kept = now - s.retention
    if s.has_log and bad_at > oldest_kept:
        snap = ((bad_at - 1) // s.snapshot_every) * s.snapshot_every
        if snap < oldest_kept:
            return None, "最舊的快照已過保留期，無法開始重播日誌"
        point = bad_at - 1                       # 還原到出事前一分鐘
        replay = (point - snap) / LOG_REPLAY_SPEEDUP
    else:
        point = ((bad_at - 1) // s.snapshot_every) * s.snapshot_every
        if point < oldest_kept:
            return None, "所有未受污染的快照都已過保留期"
        replay = 0
    rto = DB_GB / RESTORE_GB_PER_MIN + replay
    return (bad_at - point, rto), ""


strategies = [
    Strategy("只有 replica（同步複製）", snapshot_every=1, retention=0, has_log=False),
    Strategy("每日快照，保留 7 天，同帳號", DAY, 7 * DAY, False, same_failure_domain=True),
    Strategy("每日快照，保留 7 天，獨立帳號", DAY, 7 * DAY, False),
    Strategy("每日快照＋交易日誌，保留 35 天，獨立帳號", DAY, 35 * DAY, True),
]

scenarios = [
    ("A. 錯誤 migration 於 14:37 刪掉 reviews 表，16:10 發現",
     10 * DAY + 14 * HOUR + 37, 10 * DAY + 16 * HOUR + 10, False),
    ("B. 同一事件，但攻擊者也刪除了 production 帳號下的所有資源",
     10 * DAY + 14 * HOUR + 37, 10 * DAY + 16 * HOUR + 10, True),
    ("C. 程式 bug 從 9 天前開始默默寫壞資料，今天才發現",
     1 * DAY, 10 * DAY, False),
]

for title, bad_at, now, wiped in scenarios:
    print(title)
    for s in strategies:
        if s.retention == 0:
            print(f"  {s.name}：無法還原，錯誤在幾秒內就同步到 replica")
            continue
        result, reason = restore_plan(s, bad_at, now, wiped)
        if result is None:
            print(f"  {s.name}：無法還原，{reason}")
        else:
            lost, rto = result
            print(f"  {s.name}：可回到出事前 {lost} 分鐘的狀態，"
                  f"還原約 {rto / HOUR:.1f} 小時；之後 {(now - bad_at) / HOUR:.1f} 小時的寫入要另外補")
    print()
```

執行結果：

```text

  只有 replica（同步複製）：無法還原，錯誤在幾秒內就同步到 replica
  每日快照，保留 7 天，同帳號：可回到出事前 877 分鐘的狀態，還原約 5.3 小時；之後 1.6 小時的寫入要另外補
  每日快照，保留 7 天，獨立帳號：可回到出事前 877 分鐘的狀態，還原約 5.3 小時；之後 1.6 小時的寫入要另外補

  每日快照，保留 7 天，同帳號：無法還原，所有未受污染的快照都已過保留期
  每日快照，保留 7 天，獨立帳號：無法還原，所有未受污染的快照都已過保留期
  每日快照＋交易日誌，保留 35 天，獨立帳號：可回到出事前 1 分鐘的狀態，還原約 6.1 小時；之後 216.0 小時的寫入要另外補
```

逐段解讀：

1. **Replica 在三種情境都救不了。** 這是「replication 不是 backup」最直接的證明：複製忠實地傳播了錯誤。
2. **情境 A 對應 Harbor 的評論表事故。** 每日快照只能回到 00:00，等於遺失 877 分鐘（約 14.6 小時）的評論；加上交易日誌就能回到出事前 1 分鐘。代價是 RTO 多了重播日誌的半小時。這就是 RPO 與 RTO 之間的取捨。
3. **情境 B 顯示 failure domain 的重要。** 兩個「每日快照、保留 7 天」的策略只差在備份放在哪個帳號，結果一個救得回來、一個完全沒有。3-2-1 的「1 份異地」不只是地理上的異地，也是權限上的異地。
4. **情境 C 是 creeping 的 bug。** 保留 7 天的備份全部已經是壞資料，只有保留期夠長的策略能找到乾淨的版本。但注意最後一句：還原到 9 天前，等於丟掉 216 小時的正常寫入。真實的修復通常不是整庫還原，而是把舊版本還原到旁邊的隔離環境，再依 lineage 找出受影響的資料列，選擇性地修補。
5. **每一行都有「之後的寫入要另外補」。** 還原只能回到出事之前，出事到發現之間的正常寫入不會自動回來。這段時間越長，補救越困難，所以偵測速度和備份設計一樣重要。
6. **`RESTORE_GB_PER_MIN` 的註解寫著「上次演練量到的數字」。** RTO 的估算只有在真的演練過之後才有意義；Harbor runbook 上的「30 分鐘」就是沒有更新的估算。

## 42.10 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會出問題 | 具體情境 | 對策 |
|---|---|---|---|
| 以 job 成功與 row count 當作健康指標 | 資料被錯誤解讀，但數量正常 | Harbor 的時區 bug：筆數正常，日期全錯 | 加上與獨立來源的對帳與業務不變條件，並把 correctness 列為 SLO |
| 檢查失敗一律 fail closed | 非關鍵資料的少量髒資料卡住整條 pipeline | 一筆格式錯誤的點擊紀錄讓推薦特徵整天沒更新 | 依資料的用途選擇 fail closed 或 quarantine，並為隔離區設 owner 與期限 |
| 把 replication 當作備份 | 邏輯錯誤被同步到所有副本 | 錯誤的 `DELETE` 一秒內傳到三個區域 | 另外建立有保留期、獨立權限的備份與 PITR |
| 備份與 production 在同一帳號 | 帳號被入侵或自動化腳本誤刪 | 清理腳本刪除「所有未標記的資源」，備份也在其中 | 獨立帳號、最小權限、immutable 保留 |
| 保留所有版本與所有原始資料 | 儲存成本與隱私風險持續增加 | Raw 層保存了三年的完整個資，被要求刪除時找不到所有副本 | 依資料類別訂保留期；敏感欄位加密或 crypto-shredding；以 lineage 追蹤副本 |
| 只在事故時才還原 | 權限、金鑰、工具、時間估算全部失效 | 值班者讀不到備份帳號、金鑰在離職同事的設定裡 | 定期自動還原演練，由不同的人操作，量測真實 RTO |
| 重跑 pipeline 修正資料 | 下游已產生外部副作用 | 重算抽成後又開了一次發票 | 外部副作用與計算分離，各自有 idempotency key 與更正流程 |
| 全面上 lineage 平台 | 收集了大量圖，卻沒人用來做決策 | 圖上有三千個節點，但沒有標出哪些是關鍵資料集 | 先從關鍵資料集與其消費者開始，確保事故時真的能回答「影響了誰」 |

## 42.11 AI 時代：什麼變了？

AI 從兩個方向改變這一章的工作：AI agent 開始操作資料管線，以及資料管線本身開始餵養 AI。42.8 節已經說明了後者需要的 provenance；這裡聚焦在「讓 AI 參與資料工作」時的做法與邊界。

**第一，AI coding agent 會大量產生資料轉換程式。** 寫一段 SQL 或 dataframe 轉換對 agent 來說很容易，但 Harbor 的事故提醒我們，資料程式最常見的錯誤不在語法，而在語意：時區、單位、重複、空值的意義。Agent 看不到這些隱含假設，除非它們被寫進資料契約與 schema。實務做法是：要求 agent 產生的轉換必須附上對帳查詢與業務不變條件的檢查，並在 CI 中以一份已知正確答案的樣本資料執行；資料契約的變更一律需要人類 owner 核准。

**第二，AI 可以讓資料品質規則從「沒有」變成「有一大堆」。** 讓模型讀過歷史資料後提出候選規則（「`amount` 從未出現負數」「每小時訂單量與上週同時段的比值通常在 0.7–1.4 之間」）是很好的起點，但規則太多會變成 alert fatigue。每條規則都要由資料 owner 確認它代表真實的業務約束，而不只是歷史上剛好成立的巧合。

**第三，AI 維運 agent 能加速事故中的影響分析。** 「11/10 的清理結果錯了，哪些下游受影響？」這個問題，agent 可以透過 lineage 圖、查詢紀錄與排程設定快速整理出候選清單與重算順序。但它只能整理已有的紀錄，lineage 沒記到的消費者，它也不會知道。

**第四，破壞性的資料操作必須有更嚴格的閘門。** 刪除、隔離、覆寫、重算並發布、還原，這些操作被 agent 誤判時的後果和第 40 章的雙 primary 一樣難以收拾。

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 依歷史資料提出候選的品質規則與異常偵測門檻 | 規則是否代表真實的業務約束，由資料 owner 確認；規則的數量與告警路由要控制 |
| 為新的轉換程式草擬對帳查詢、不變條件與測試樣本 | 「正確答案」的來源必須是獨立的外部資料或人工確認，不能由同一個 agent 生成 |
| 事故時根據 lineage 整理受影響的下游、重算順序與通知名單 | 實際重算、發布與更正外部副作用（發票、撥款）需要人類核准，並先在隔離環境預覽差異 |
| 執行還原演練、比對 checksum 與業務查詢，產出演練報告 | 還原到 production、刪除或隔離大量資料必須有範圍上限、預覽、雙人核准與稽核紀錄 |
| 為 RAG 索引產生 provenance 報告，找出過期或缺少 owner 的文件 | 文件的存取權限與能否進入客戶可見的知識庫，由文件 owner 與資安決定 |
| 偵測 schema 變更對下游的影響，在 PR 中自動留言 | 不相容的資料契約變更需要生產者與消費者共同同意遷移計畫 |

> [!ai] AI 提醒
> 讓 agent 檢查資料時，最容易犯的錯是讓它用同一套假設產生資料、又用同一套假設驗證資料。如果 agent 寫的轉換以 UTC 分組，它寫的檢查也很可能以 UTC 計算「預期值」，兩者會一起錯、一起通過。對帳的價值來自獨立性，這一點不會因為檢查者是 AI 而改變。

## 42.12 專家怎麼想

- **「這份資料錯了，最晚多久會有人發現？」** 資深的資料工程師會先問偵測時間，再問備份策略。偵測時間決定了錯誤會擴散多遠、備份要保留多久、要重算多少。把偵測從三週縮短到一天，價值往往超過任何備份升級。
- **「讓我看看你上次還原是什麼時候。」** 在專家眼中，沒有演練紀錄的備份只是一個假設。他們會要求看還原演練的日期、耗時、由誰執行，以及驗證了哪些業務查詢。
- **保留原始資料，讓錯誤可以被重算。** Raw 層看起來是浪費空間，但它讓幾乎所有下游錯誤都有退路：修好程式，重算即可。專家會為原始資料設定比衍生資料更長、更嚴格的保留與保護。
- **把外部副作用當成一級風險。** 資料可以重算，已經寄出的發票、匯出的撥款、送給合作夥伴的檔案不行。設計 pipeline 時，專家會先標出 DAG 上所有「出了門就收不回來」的節點，在它們前面放最嚴格的檢查。
- **獨立的證據勝過更多的檢查。** 十條共用同一個假設的檢查，不如一條來自外部來源的對帳。專家會刻意尋找「不是我們自己算的數字」來驗證自己。
- **資料契約是組織問題，不只是技術問題。** Harbor 的事故中沒有人寫錯程式，是兩個團隊對同一個欄位有不同的理解。專家會推動「誰擁有這份資料、變更前要通知誰」成為明文規定。

## 42.13 動手練習

1. 修改 42.9 第一段程式，讓訂單量集中在台灣時間 00:00–02:00（模擬雙十一零點搶購），觀察 v1 的誤差如何變化。再加上一個「每小時訂單量與前一天同時段相比」的分佈檢查，看它能不能在沒有外部對帳來源時抓到時區 bug。
2. 在第一段程式中加入「遲到事件」：讓 2% 的事件在 watermark 之後才到達。設計兩種處理方式（更新已發布的結果並記錄版本，或寫入遲到資料表），並比較它們對對帳結果的影響。
3. 修改第二段程式，加入一個「每 6 小時快照、保留 14 天、獨立帳號」的策略，並計算每種策略每月的儲存成本（自訂每 GB 價格），畫出 RPO、保留期與成本的取捨表。

5. 挑一份你們團隊每天產生的報表或資料表，畫出它的上游與下游 lineage，並標出所有「外部副作用」節點。試著回答：如果這份資料昨天是錯的，你需要通知誰？

## 本章重點整理

- Data pipeline 的錯誤會沿著 DAG 往下游傳播，越往下游越貴；外部副作用（發票、撥款、對外檔案）是重算也收不回的節點。
- 依日期歸屬的計算要用 event time 並寫明時區；watermark 決定何時產生結果，遲到資料要有事先定好的處理規則。
- Periodic pipeline 在規模變大後會遇到 hanging chunk、執行時間追上排程間隔、負載尖峰疊加，以及「跑完了但資料沒到齊」等問題。
- Workflow 式的設計以集中的狀態、lease 認領工作、唯一命名的輸出與提交機制，讓 worker 失敗與重複執行都不會產生錯誤結果。
- 每個 stage 都要能安全重跑：分區覆寫、write-audit-publish、用業務主鍵去重，外部副作用放在最後並有自己的 idempotency key。
- 資料管線的 SLO 包含 freshness、completeness 與 correctness；correctness 最重要也最常缺席，最強的證據來自獨立的外部來源。
- Row count 只證明資料「來了」，不證明它被正確解讀；品質檢查要對準資料被用來回答的問題。
- 資料契約把生產者與消費者之間的隱含假設寫下來，並在 CI 中強制執行相容性。
- 資料完整性的失敗可以用「原因 × 範圍 × 速度」分析；creeping（緩慢蔓延）的錯誤最難救，因為備份裡也可能都是壞資料。
- 多層防禦依序是 soft delete、backup 與 out-of-band 驗證（及早偵測），replication 貫穿各層但不能取代備份；replication 不是 backup。
- 沒有人想要備份，大家想要的是還原；沒有演練過的備份只能假設它不存在。
- RPO 決定能接受遺失多少資料，RTO 決定恢復要多久；不同資料應有不同目標，保留期必須長於錯誤的偵測時間。
- 3-2-1 中的「異地」也包括權限與帳號上的隔離；immutable 副本能抵擋誤刪與勒索軟體。
- Provenance 記錄資料如何產生，lineage 把它們串成圖，讓你能往上游找原因、往下游做影響分析；前提是資料有版本、不被原地覆寫。
- RAG 與模型訓練資料需要同樣的 provenance、freshness、權限與刪除紀律；讓 AI 參與資料工作時，驗證必須保持獨立。

## 延伸問答

> [!question]- Q1. Pipeline 每次都顯示 SUCCEEDED，為什麼不能代表資料正確？
> Job 的成功狀態只表示程式執行結束時沒有拋出錯誤，它不知道程式對資料的解讀是否正確。Harbor 的事故中，時區解析錯誤不會產生任何例外，程式只是把資料放進錯的日期；重複事件也不會讓任何東西失敗，只會讓總額偏高。
>
> 要判斷資料正確，需要從「資料被用來回答什麼問題」出發設計檢查：與獨立來源對帳（金流商撥款明細）、檢查業務不變條件（不該出現的日期、退款不大於訂單金額）、比較分佈（某個時段的訂單量突然消失）。這些檢查的結果應該成為 correctness SLI，和 freshness 一起列在 pipeline 的 SLO 裡。

> [!question]- Q2. 為什麼說 replication 不是 backup？兩者分別防什麼？
> Replication 把資料即時同步到其他機器或區域，它防的是硬體故障、機房斷電、區域不可用這類「資料所在的地方壞了」的問題。但它會忠實地複製所有寫入，包括錯誤的 `DELETE`、寫壞資料的 bug、被勒索軟體加密的內容，幾秒內所有副本就一起壞掉。
>
> Backup 保存的是過去某個時間點的狀態，它防的是邏輯錯誤：只要錯誤發生之前的備份還在保留期內，就能回到那個狀態。兩者解決不同的問題，所以需要同時存在。一個常見的反例是「我們有三個區域的 replica，所以很安全」，這對區域故障成立，對一次錯誤的 migration 完全無效。

> [!question]- Q3. 你是 Harbor 的值班者，下午 4 點發現一個 migration 在下午 2 點半刪掉了評論表的一半資料，而且服務還在持續寫入新評論。你會怎麼處理？
> 第一步是止血：暫停那個 migration 或相關的背景工作，確認刪除沒有在繼續；如果錯誤的寫入還在發生，考慮暫時把評論功能切成唯讀。接著保全現場：記錄當前的狀態與時間，不要急著在 production 上直接還原，以免覆蓋掉 2 點半之後的正常寫入。
>
> 然後把備份還原到一個隔離環境，用 PITR 回到 2:29 左右的狀態，比對出被刪掉的資料列，再把這些資料列選擇性地寫回 production，而不是把整張表替換成舊版本。這樣 2:30 到 4:00 之間的新評論會被保留。完成後用業務查詢驗證（評論總數、每個商品的評論數與事前趨勢相符），並在 postmortem 中記錄實際的 RPO、RTO 與 migration 缺少的防護。如果 PITR 不可用，就要評估接受每日快照之後的資料損失，或從應用程式日誌補回。

> [!question]- Q4. 計算題：一個 600 GB 的資料庫，還原速度每分鐘 3 GB，每天 00:00 做一次快照並持續保存交易日誌，重播速度是「1 分鐘重播 20 分鐘份量」。如果要還原到當天 18:00，RTO 大約多少？如果只有快照呢？
> 還原快照需要 600 ÷ 3 = 200 分鐘。從 00:00 重播到 18:00 是 18 小時，也就是 1,080 分鐘份量的日誌，以 20 倍速重播需要 1,080 ÷ 20 = 54 分鐘。合計約 254 分鐘，大約 4.2 小時，這還沒算上找備份、取得權限、決定還原點與驗證的人力時間。
>
> 如果只有快照，還原約 200 分鐘，但只能回到 00:00，等於遺失 18 小時的資料，RPO 遠差於前者。這個例子說明 PITR 讓 RPO 大幅改善，代價是 RTO 增加了重播時間；要縮短重播時間，可以提高快照頻率（例如每 6 小時一次），讓需要重播的日誌變少。

> [!question]- Q5. 為什麼 creeping（緩慢蔓延）的資料錯誤比 big bang 更難處理？
> Big bang 的錯誤（一次性大量刪除）通常很快被發現，最近的備份裡就有乾淨的資料，還原的範圍也很清楚。Creeping 的錯誤（每天錯一點）可能要幾週才被發現，這時三個問題同時出現：保留期內的備份可能全都是壞資料；錯誤已經沿著 lineage 擴散到許多下游與外部副作用；出錯到發現之間累積了大量正常寫入，不能整庫還原。
>
> 因此對付這類錯誤的關鍵在偵測，而不是備份：持續的對帳、不變條件檢查與分佈監控，把發現時間從幾週縮短到幾小時。其次是保留原始資料與夠長的備份保留期，讓修好程式後能重算。最後是 lineage，讓你知道哪些下游需要修正。

> [!question]- Q6. 面試題：請設計一個每日營收報表 pipeline，說明你會如何確保它的可靠性。
> 一個好的回答會從資料流開始：來源事件先原樣寫入 raw 層並設定足夠長的保留期；清理 stage 以 event time 與明確時區解析時間，用 order_id 去重；彙總 stage 以「分區覆寫」方式產生每天的結果，先寫到暫存版本，通過檢查後再原子性地發布；外部副作用（發票）放在獨立的下游步驟，有自己的 idempotency key 與更正流程。
>
> 可靠性部分要談 SLO 與檢查：freshness（每天 06:00 前發布）、completeness（所有 partition 到齊才開始）、correctness（與金流商撥款明細差異 < 0.1%）；檢查失敗時 fail closed，下游繼續用前一版。最後補上 lineage（每個分區記錄輸入版本與程式版本）、資料契約（上游 schema 變更要在 CI 中檢查相容性），以及 raw 層與倉儲的備份與還原演練。能講到「row count 抓不到語意錯誤」與「外部對帳要獨立」，通常會讓面試官印象深刻。

> [!question]- Q7. Harbor 的 AI 客服 agent 告訴客人「退貨期限是 7 天」，但政策上週已改成 10 天。你要如何找出原因並防止再發生？
> 先用回答的 provenance 紀錄確認當時檢索到哪些 chunk、它們來自哪份文件的哪個版本、用的是哪一次建立的索引。可能的原因有幾種：政策文件更新了，但索引還沒重建（freshness 問題）；新舊兩個版本的文件都在索引裡，檢索到了舊的（版本管理問題）；文件根本沒更新，只有公告更新了（來源問題）；或者檢索是對的，但模型沒有依據文件回答（生成問題）。沒有 provenance 紀錄，這四種情況幾乎無法區分。
>
> 防止再發生的做法包括：為知識庫設定 freshness SLO（文件更新後 N 小時內可被檢索），並監控「最新文件版本」與「索引中的版本」是否一致；文件更新時讓舊版本的 chunk 從索引移除；為重要政策建立固定的 eval 題目（「退貨期限是幾天？」），每次索引重建後自動執行；以及每份文件都要有 owner，政策變更流程中包含「確認 AI 知識庫已更新」這一步。

> [!question]- Q8. 團隊想讓 AI agent 自動修復資料品質問題，例如發現重複資料就自動刪除。你會怎麼評估這個提案？
> 先區分這個操作的風險。刪除是破壞性的、通常難以回復的動作，而「重複」的判斷可能出錯：兩筆看起來一樣的訂單，可能是同一位客人真的下了兩次單。如果 agent 的判斷規則有誤，它會以機器的速度、在大範圍內放大錯誤，這正是第 31 章提到的自動化風險。
>
> 比較安全的漸進做法是：第一階段讓 agent 只偵測並提出報告，附上判斷依據與受影響的資料列；第二階段允許它把疑似重複的資料移到隔離區（可回復），而不是刪除，並設定每次的數量上限；第三階段在累積足夠的正確率紀錄後，才對規則明確、影響小的類別允許自動處理。全程要保留稽核紀錄、預覽差異，並由資料 owner 定義什麼算「重複」。更根本的解法是回到上游：如果重複來自 at-least-once 傳遞，應該在清理 stage 用業務主鍵去重，而不是在下游清理。
