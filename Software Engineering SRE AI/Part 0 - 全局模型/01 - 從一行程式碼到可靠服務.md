# 第 1 章　從一行程式碼到可靠服務

> [!abstract] 本章地圖
> **核心問題**：一段在自己筆電上正確執行的程式碼，要經過哪些步驟、由誰負責，才會變成使用者可以長期信任的服務？
>
> **你會學到**：
> - 畫出一個 commit 從需求、設計、程式碼、review、測試、build、CI、release，到監控、事故、postmortem 再回到下一次變更的完整旅程
> - 說出每一站在回答什麼問題、產出什麼證據、能攔下哪一類錯誤
> - 分辨 software engineering 與 SRE 各自回答的核心問題，並解釋為什麼它們其實是同一條生命週期
> - 判斷 AI 在每一站適合做什麼、哪些責任必須留在人身上
> - 認識貫穿全書的 Harbor 港灣市集案例與人物，並用全書地圖規劃自己的讀法
>
> **前置知識**：會寫程式，知道 Git、HTTP 與資料庫是什麼；不需要任何團隊或值班經驗
>
> **對應原書**：SWE 第 1 章〈What Is Software Engineering?〉；SRE 第 1 章〈Introduction〉

## 1.1 故事：滿千免運上線的那個週五

Harbor 港灣市集剛成立十個月，整間公司八個人，工程師五位。某個週四下午，產品經理 Lisa 在群組裡丟了一個需求：「週末母親節檔期，想做『單筆滿 1,000 元免運』，週五晚上前能上嗎？」剛畢業加入的工程師阿凱接下了這個任務。

需求看起來很簡單。阿凱打開 checkout 的程式碼，找到算運費的函式，加了三行：如果購物車總額大於等於 1,000，運費設為 0。在自己筆電上用幾個購物車試了一下，金額都對。週五傍晚六點，阿凱照著公司慣例，SSH 登入唯一一台 production 主機，`git pull`、重啟服務，在群組回報：「免運上線了！」

晚上九點，Lisa 開始收到客服訊息。第一類抱怨是「我買 1,200 元，用了 300 元折價券，結果還是免運，可是朋友買 950 元卻要付運費」，這其實是規則沒講清楚：免運要看折扣前還是折扣後的金額？第二類比較嚴重：使用舊版 iOS app 的使用者完全無法結帳。原來阿凱順手把 API 回傳的 `shipping_fee` 從整數改成了 `null`（代表「免運」），而舊版 app 在解析時直接當掉。

更糟的是，沒有人知道問題從什麼時候開始、影響了多少人。Harbor 沒有任何監控，第一個發現問題的是客服，而客服是從使用者的抱怨中知道的。負責基礎設施的工程師志明想把程式退回上一版，卻發現沒人記得上一版是哪個 commit，主機上的程式碼還混著阿凱沒提交的修改。等到 tech lead 美華從外面趕回來、確認回退的版本並重啟，已經是晚上十一點。整整五個小時，有一部分使用者根本付不了錢。

週一的檢討會上，負責工程的共同創辦人 Kevin 問阿凱：「你的程式有錯嗎？」阿凱想了很久，說：「在我的電腦上，它是對的。」這句話其實沒有說錯。真正的問題是：從「在我的電腦上是對的」到「使用者可以安心付款」之間，還隔著一大段路，而 Harbor 那段路上幾乎什麼都沒有：沒有人確認需求的邊界、沒有人 review 程式碼、沒有測試舊版 app 的相容性、沒有可以回退的版本、沒有監控、事後也沒有一套方法把教訓留下來。

這本書要講的，就是這一大段路。這一章先把整條路畫出來，讓你知道後面四十多章分別在處理哪一段。

## 1.2 認識 Harbor：貫穿全書的案例

在畫那張地圖之前，先認識之後每一章都會出現的公司與人物。用一個持續成長的公司當案例，是因為本書的很多觀念只有在「時間」與「規模」中才看得出意義：八個人時合理的做法，到了兩百人可能變成災難。

### 公司與服務

**Harbor 港灣市集**是一個台灣的線上市集，讓中小型賣家在上面開店，買家用 web 或手機 app 購物。它的系統由幾個主要部分組成：

| 服務 | 做什麼 | 壞掉時使用者感受到什麼 |
|---|---|---|
| web／app | 使用者看到的網站與手機 app | 打不開、畫面錯誤 |
| search | 商品搜尋與排序 | 找不到商品、結果很慢 |
| cart | 購物車 | 加入的商品消失 |
| checkout | 結帳流程：算金額、運費、折扣、建立訂單 | 結不了帳、金額算錯 |
| payments | 串接外部金流商（信用卡、行動支付） | 扣款失敗或重複扣款 |
| inventory | 庫存 | 超賣、顯示有貨卻買不到 |
| notification | 訂單、出貨的 email 與推播 | 沒收到通知、重複收到 |
| recommendation | 推薦商品 | 推薦不相關，但通常不會擋住購物 |

這張表的第三欄值得多看一眼。同樣叫「服務壞了」，推薦壞掉與 payments 壞掉的嚴重程度天差地遠。後面討論可靠性目標（第 32 章）與降級設計（第 38 章）時，會反覆回到這個問題：哪些東西壞了使用者真的會痛？

Harbor 還有兩種 AI。第一種是工程團隊使用的 **AI coding agent**：一個能讀懂 repository、修改程式碼、執行測試、開 pull request 的 AI 助手。第二種是面向買家的 **AI 客服 agent**：現在只能幫使用者查詢訂單狀態，Lisa 正在規劃讓它也能「發起退款」。這兩種 AI 代表了本書討論 AI 的兩個方向：AI 如何改變工程師的工作方式，以及 AI 本身作為一個 production 服務時，要怎麼讓它可靠。第 48 章的 capstone 就是讓 AI 退款助理從設計走到上線。

### 人物

| 人物 | 角色 | 在故事中常扮演 |
|---|---|---|
| 阿凱 | 初階工程師，剛畢業；第 2 年起在 seller 團隊，第 5 年帶領客服平台小組 | 提出新手會有的疑問，犯新手會犯的錯，也是成長最多的人 |
| 美華 | Tech lead（技術負責人）；第 2 年分團隊時在 payments，之後成為 checkout 的 tech lead | 做技術決策、review 設計，在速度與長期品質之間取捨 |
| 志明 | 一開始兼管基礎設施的工程師；第 2 年在 platform 團隊，第 3 年帶領新成立的 SRE 團隊 | 從 production 的角度提問：壞了怎麼辦？怎麼知道壞了？ |
| Lisa | 產品經理 | 代表使用者與業務需求，也是最常問「到底穩不穩」的人 |
| Kevin | 負責工程的共同創辦人；團隊變大後專任工程經理，第 5 年升任工程副總 | 處理人、團隊、流程與資源分配 |

八人時期的 Harbor 有五位工程師（包括 Kevin、美華、志明與阿凱），其餘是產品、營運與客服同事。第 2 年起公司分成 checkout、payments、search、seller、platform 五個團隊，之後陸續出場的配角也都有固定的團隊：checkout 的小芸與阿哲、payments 的小林、search 的柏翰與家豪、seller 負責通知的思妤，以及第 4 年加入 SRE 團隊的俊宇。本書提到人物時一律用名字或「他們」，不做性別假設。

### 成長時間線

Harbor 的規模會隨著書的進度成長，每個階段遇到的問題不同：

```text
Part 0–1   第 1 年～第 2 年初   8 人新創         一台主機、手動部署、靠記憶運作
Part 2–3   第 2 年             40–45 人、五個團隊  團隊邊界、code review 爭議、依賴與淘汰問題
Part 4     第 2 年～第 3 年初   40–45 人         自動化測試、build、CI/CD
Part 5     第 3 年             約 60 人         4 人 SRE 團隊成立、SLO、告警
Part 6–7   第 4 年             約 120 人        雙十一流量、cascading failure、incident command
Part 8     第 5 年             約 200 人        平台工程、全面導入 AI agent、組織層級的可靠性
```

Part 0–1 的故事都發生在八人時期，但不完全照時間順序排列：本章的免運事故發生在公司成立第十個月；第 3 章的撥款腳本從公司上線第二個月寫起，事故發生在它被沿用半年之後；第 4 章的庫存同步事故則在成立第一年的年底。每章開頭會交代故事的時間點。

這條時間線也是一個提醒：本書介紹的做法不是「越多越好」。八個人的 Harbor 不需要 incident commander 與三層審批；兩百人的 Harbor 如果還靠 SSH 手動部署，就一定會出大事。判斷「現在需要什麼」本身就是工程能力，第 6 章會專門討論規模如何改變問題。

## 1.3 一個 commit 的完整旅程

回到免運事故。如果把「一個想法變成使用者可靠使用的功能」拆開來看，中間至少有十幾個站。下面這張圖是全書最重要的一張圖，後面幾乎每一章都在放大其中一站：

```text
                     ┌──────────────── 變更的流動（change flow） ───────────────┐
                     │                                                           ▼
 使用者需要 ─► 需求與設計 ─► 寫程式 ─► code review ─► 測試 ─► build ─► CI ─► release
     ▲          (design doc)   (commit)   (approval)    (test)   (artifact)  (gate)  (canary)
     │                                                                            │
     │                                                                            ▼
     │                                                                       production
     │                                                                            │
     │   ┌──────────────── 證據的流動（evidence flow） ──────────────┐           │
     │   │                                                             │           ▼
 下一次變更 ◄─ postmortem ◄─ 事故處理 ◄─ 告警 ◄─ 監控（metrics／logs／traces）
                (action items)  (incident)  (alert)
```

這張圖有兩股方向相反的流動。上面那條是**變更的流動**：一個想法逐漸被釐清、實作、檢查、打包，最後進到 production。下面那條是**證據的流動**：production 把真實世界發生的事（延遲、錯誤、使用者行為、事故）送回團隊，逼團隊修正自己對系統的理解，並改變下一次變更的做法。

免運事故的問題，可以在這張圖上一一標出來。需求與設計那一站幾乎是空的，所以「折扣前還是折扣後」沒有人問；code review 不存在，所以 `shipping_fee` 改成 `null` 沒有人看到；測試沒有涵蓋舊版 app，所以相容性問題沒被攔下；沒有 build 產物，所以不知道要回退到哪裡；沒有監控與告警，所以第一個知道的是客服；也沒有 postmortem，所以同樣的錯下次還會再發生。

下表把每一站整理成三個問題：這一站在回答什麼、留下什麼證據、最擅長攔下哪類錯。表格最後一欄是本書詳細討論它的章節：

| 站 | 回答的問題 | 留下的證據（artifact） | 最擅長攔下 | 本書章節 |
|---|---|---|---|---|
| 需求與設計 | 我們要解決什麼問題？邊界與限制是什麼？ | design doc、ADR、驗收條件 | 規則不清、架構選錯 | 第 7、17 章 |
| 寫程式 | 怎麼實作？ | commit | 由作者自己修正的錯誤 | 第 15、19 章 |
| Code review | 別人看得懂嗎？有沒有漏掉什麼？ | review 紀錄、approval | 邏輯錯誤、可讀性、知識只在一人腦中 | 第 16 章 |
| 測試 | 行為符合預期嗎？以後會不會被改壞？ | 測試程式與結果 | 邏輯錯誤、回歸（regression） | 第 22–26 章 |
| Build | 能不能產出一個確定、可重現的產物？ | artifact（例如容器映像） | 「我電腦上可以」的環境差異 | 第 27 章 |
| CI | 合併到主線後整體還正常嗎？ | CI 紀錄 | 整合錯誤、相依衝突 | 第 28 章 |
| Release | 怎麼讓變更安全地接觸真實使用者？ | 部署紀錄、canary 結果 | 只在真實流量出現的問題 | 第 29、35 章 |
| 監控 | 使用者現在過得好嗎？ | SLI、metrics、logs、traces | 已經發生、正在傷害使用者的問題 | 第 32、33 章 |
| 告警 | 需要有人立刻處理嗎？ | alert、page | 需要人介入的異常 | 第 34 章 |
| 事故處理 | 怎麼最快止血？ | incident 紀錄、時間線 | 擴大中的傷害 | 第 43、44 章 |
| Postmortem | 我們學到什麼？怎麼避免再發生？ | postmortem 文件、action items | 系統性弱點 | 第 45 章 |

有兩件事要先講清楚。第一，沒有任何一站能攔下所有錯誤。測試攔不住「規則本來就訂錯」，code review 攔不住「只在雙十一流量下才出現」的問題，監控也無法阻止錯誤發生，只能讓你更早知道。可靠性來自**多個獨立的關卡**，每一關攔下不同種類的問題。第二，越往後才被發現的錯誤，代價越高：在設計階段發現規則不清，只要一次對話；在 production 才發現，要付出使用者的信任、客服的人力、退款，以及深夜的緊急修復。

> [!warning] 常見誤解
> 「關卡越多越安全。」不一定。如果測試很慢又常常隨機失敗（第 26 章的 flaky test），工程師會開始累積大批變更一次送、或想辦法繞過檢查，結果反而更危險。好的關卡要快、可信、對應到具體風險；一個沒人相信的關卡，比沒有關卡更糟，因為它製造了「已經檢查過」的錯覺。

## 1.4 前半段：從想法到可以部署的產物

這一節沿著變更的流動，從需求走到 CI，說明每一站為什麼存在。每一站後面都有專章，這裡的目標是建立直覺：這一站不存在時，會發生什麼事？

### 需求與設計：先問清楚「什麼才算對」

免運事故的第一個錯誤發生在任何程式碼之前：沒有人定義「1,000 元」是折扣前還是折扣後的金額，也沒人問「免運」在 API 上要怎麼表示。這類錯誤寫再多測試也抓不到，因為測試只能驗證你以為的規則，無法驗證規則本身。

設計這一站的產出，最小可以只是一段寫在 pull request 描述裡的文字，大到可以是一份正式的 **design doc**（設計文件：說明要解決的問題、考慮過的方案、選擇的理由與風險的文件）。對阿凱的功能，一份五行的設計說明就夠了：

```text
目標：母親節檔期，單筆訂單「折扣後金額」≥ 1,000 元免運
不做：不改變其他運費規則；不支援跨賣家合併計算
API：shipping_fee 維持整數，免運時為 0（不得改為 null，舊版 app 依賴整數）
驗收：950 元＋折價券、1,000 元整、1,200 元－300 元折價券 三種情況的運費
回退：可用設定開關關閉，不需重新部署
```

這五行回答了事故中所有的問題。重點不是文件的格式，而是在動手之前，讓「會影響別人的決定」被說出來、被別人看到。第 7 章會介紹記錄重大技術決策的 **ADR**（Architecture Decision Record，架構決策紀錄），第 17 章會介紹 design doc 的寫法與 review。

### 寫程式與 code review：讓第二雙眼睛看見

**Code review** 是指程式碼合併到主線之前，由作者以外的人閱讀並同意的流程。新手常以為 code review 主要是「抓 bug」，但它真正的價值更廣：確保至少有第二個人理解這段程式碼（否則作者請假時沒人能維護）、維持整個 codebase 的一致性、讓資深者的經驗傳給新人。如果免運的變更經過美華 review，`shipping_fee` 變成 `null` 那一行幾乎一定會被問：「這會不會影響舊版 app？」

Code review 有效的前提是變更夠小。一個改了 30 行的 pull request，reviewer 可以仔細看完；一個改了 3,000 行的，reviewer 通常只能寫「LGTM」（Looks Good To Me，看起來沒問題）。這也是為什麼第 19 章會花很多篇幅講「小批次」（small batches）。

### 測試：把「我以為是對的」變成可重複的檢查

**測試**是用程式自動檢查程式的行為是否符合預期。它的價值有兩層：第一層是這次變更有沒有寫錯；第二層更重要，是**以後**有人改這段程式時，會不會不小心把它改壞。後者叫做防止 **regression**（回歸，原本正常的功能因為新的修改而壞掉）。

如果阿凱為免運寫了三個測試案例（就是設計說明裡的那三種情況），就等於把「折扣後金額」這條規則固定在程式碼旁邊。半年後有人重構運費計算，只要測試還在，規則就不會悄悄改變。Google 有一句廣為流傳的說法叫 Beyoncé Rule：「If you liked it, you should have put a CI test on it.」大意是在乎某個行為，就要用測試保護它（第 4 章會完整解釋這條規則）。第 22 到 26 章會完整討論測試。

### Build 與 CI：產出確定的產物，持續整合

**Build** 是把原始碼轉成可以部署的東西，這個東西叫 **建置產物（artifact）**，例如一個容器映像（container image）或一個打包好的執行檔。Artifact 最重要的性質是**不可變且可追溯**：版本 `checkout:2023.11.08-3f2a1c` 永遠指向同一份內容，你知道它是從哪個 commit、用哪些依賴建出來的。

免運事故中，志明無法回退的根本原因就是沒有 artifact。主機上跑的是「某個 commit 加上一些沒提交的修改」，這個狀態無法重現，也無法精確回到「上一個正常的狀態」。有了 artifact，回退就變成「重新部署上一個 artifact」，一個指令、幾分鐘。

**CI**（Continuous Integration，持續整合）是指每個變更都頻繁地合併到主線，而且每次合併都自動 build 與執行測試。CI 的重點不是某個工具，而是一種紀律：讓整合問題在變更還小、記憶還新鮮的時候就被發現。如果五個工程師各自在自己的分支上工作兩週再合併，衝突與整合錯誤會在最後一天一起爆發。第 27、28 章會討論 build 系統與 CI。

## 1.5 後半段：進入 production 之後

變更通過 CI，產出 artifact，代表它「看起來沒問題」。但真實世界有測試環境沒有的東西：真實使用者的行為、各種舊版 app、真實的流量高峰、外部金流商偶爾的抽風。所以旅程的後半段，重點從「證明它是對的」轉移到「在真實環境中小心地確認，出錯時能快速發現並恢復」。

### Release：先讓一小部分使用者試

**Deploy**（部署）是把新的 artifact 放到 production 的機器上執行；**release**（發布）是讓使用者實際用到新功能。這兩件事可以分開，而分開正是降低風險的關鍵。

常見的做法有兩種。第一種是 **canary**（金絲雀發布）：先把新版本部署給一小部分流量（例如 5%），觀察錯誤率與延遲是否正常，再逐步擴大到全部。名字來自礦工帶金絲雀下礦坑偵測毒氣的典故：小範圍先承受風險，讓大多數人免於受害。第二種是 **feature flag**（功能開關）：程式碼已經部署，但新功能藏在一個可以即時開關的設定後面，有問題時把開關關掉即可，不需要重新部署。

如果免運功能先只開給 5% 的使用者，舊版 app 當掉的問題只會影響一小群人；如果它藏在 feature flag 後面，Lisa 在晚上九點收到第一則客訴時，就能自己把功能關掉，而不是等到十一點。第 29 章會詳細討論 canary 分析、rollback 與資料庫 schema 的安全變更。

### 監控與告警：在使用者抱怨之前知道

**監控**（monitoring）是持續收集系統在 production 的行為資料。常見的三種是 **metrics**（指標：數值隨時間的變化，例如每秒請求數、錯誤率）、**logs**（日誌：一筆筆事件紀錄，例如「訂單 123 付款失敗，原因是逾時」）、**traces**（追蹤：一個請求穿過多個服務的完整路徑與耗時）。第 33 章會把它們放進 observability 的框架中討論。

監控資料本身不會救你，要有人在對的時間看到。**告警**（alert）就是在資料顯示「使用者正在受傷害」時主動通知人。這裡最關鍵的觀念是：告警應該基於**使用者感受到的症狀**（例如結帳成功率下降），而不是機器的內部狀態（例如 CPU 偏高）。免運事故中，主機的 CPU 與記憶體完全正常，但舊版 app 的結帳成功率掉到零。只看機器的監控，一樣不會發現問題。第 32 章會定義「使用者過得好不好」的量法（SLI 與 SLO），第 34 章會講怎麼設計不吵又可靠的告警。

### 事故處理：先止血，再找原因

**事故**（incident）是指服務出現使用者可感受、需要立即處理的問題。事故處理的第一原則是**先止血，再修復**：先把使用者的傷害停下來（回退、關掉 feature flag、把流量導走），之後再慢慢找根本原因。免運事故那晚，美華花了大量時間在看程式碼、試圖找出 bug 在哪，而正確的第一步其實是不管原因、先回到上一個正常版本。

事故規模變大時，還需要清楚的角色分工：誰負責指揮、誰負責操作、誰負責對外溝通。否則會出現五個人同時在 production 上修改東西、互相覆蓋的混亂。第 43 章討論值班與排查方法，第 44 章討論 incident command。

### Postmortem：把教訓變成系統的一部分

事故結束後，團隊要寫一份 **postmortem**（事後檢討）：記錄發生了什麼、時間線、影響範圍、哪些因素促成了事故，以及要採取哪些行動避免再發生。Postmortem 的核心原則是 **blameless**（不究責）：重點放在「系統為什麼允許這個錯誤發生」，而不是「誰犯了錯」。原因很實際：如果犯錯的人會被懲罰，大家就會隱藏錯誤，組織就永遠學不到東西。

免運事故的 postmortem 不應該寫「阿凱沒有注意相容性」，而應該寫「我們的流程中沒有任何一站會檢查 API 相容性」。前者的結論是「阿凱下次要小心」，這種 action item 幾乎沒有效果；後者的結論是「在 CI 加入 API 契約檢查」「部署改用 artifact 並保留前三個版本」「為結帳成功率加上告警」，這些會永久改變系統。第 45 章會討論 postmortem 的寫法與 action item 的品質。

Postmortem 是證據流動的終點，也是下一次變更流動的起點。一份好的 postmortem 產出的 action items 會變成新的測試、新的 CI 檢查、新的告警、新的文件，於是下一次類似的錯誤會在更前面、更便宜的地方被攔下。這個「從 production 學習，再改變前面的關卡」的迴圈，就是整張圖之所以畫成一個圓的原因。

## 1.6 Software Engineering 與 SRE 各自回答的問題

本書的書名結合了兩個領域，各自有一本經典：《Software Engineering at Google》（以下簡稱 SWE 書）與《Site Reliability Engineering》（以下簡稱 SRE 書）。理解它們各自在回答什麼，能幫你看清楚這張地圖上的分工。

### Software engineering：隨時間積分的程式設計

SWE 書對 software engineering 的定義是一句很有名的話：「**Software engineering is programming integrated over time.**」（軟體工程是隨時間積分的程式設計。）

這句話的意思是：**programming**（寫程式）是在某個時間點讓程式能動；**software engineering** 則要考慮這段程式在它整個壽命中會經歷什麼：會有多少人讀它、改它，依賴的套件與作業系統會更新，需求會變，原作者會離開。一個只跑一次的資料轉換腳本，寫得亂一點沒關係；一個要跑十年、有五十個人改過的結帳系統，每個決定都要考慮未來的維護成本。

SWE 書用三個維度來描述這件事：**時間與變更**（程式要活多久？期間會遇到多少被迫的變更？）、**規模與成長**（參與的人、程式碼量、使用量增加時，哪些做法會變得無法負擔？）、**取捨與成本**（每個決定在金錢、時間、人的注意力上的代價是什麼？）。Part 1 的第 3 到 7 章會逐一展開。

用一句話總結：software engineering 回答的是「**怎麼讓程式碼在多年、多人的修改之下，仍然可以安全、低成本地被修改？**」

### SRE：用軟體工程的方法做維運

SRE 書的作者之一 Ben Treynor Sloss 對 SRE 的描述是：「SRE is what happens when you ask a software engineer to design an operations team.」（SRE 就是請一位軟體工程師來設計維運團隊時會發生的事。）

傳統的維運（operations）模式是：開發團隊寫好程式，交給維運團隊上線與照顧。這個模式有一個結構性問題：開發團隊的目標是「快速推出功能」，維運團隊的目標是「系統不要壞」，而大部分的事故來自變更（SRE 書提到大約七成的 outage 是由對運作中系統的變更造成的），於是維運團隊自然傾向阻擋變更，兩邊的目標直接衝突。另一個問題是，服務成長時，人工維運的工作量會跟著線性成長，只能不斷加人。

SRE 的回答是用工程方法處理維運問題：把重複的手動工作自動化（第 31 章的 toil，瑣務），把「多可靠才夠」寫成可以計算的目標（第 32 章的 SLO 與 error budget），並限制 SRE 花在手動維運的時間不超過 50%，剩下的時間用來寫軟體改善系統。SRE 書列出 SRE 團隊負責的範圍：availability、latency、performance、efficiency、change management、monitoring、emergency response 與 capacity planning。

用一句話總結：SRE 回答的是「**服務在 production 中要多可靠才夠？怎麼用工程方法達到、量測並維持它，而不是靠加人與祈禱？**」SRE 書的導論開頭引用了一句 SRE 圈的傳統說法：「Hope is not a strategy.」（希望不是策略。）

### 兩者對照

| 面向 | Software engineering | SRE |
|---|---|---|
| 核心問題 | 程式碼如何在時間與規模下保持可修改 | 服務如何在 production 保持可靠 |
| 關心的對象 | codebase、團隊、開發流程 | 執行中的系統、使用者體驗、維運流程 |
| 主要工具 | code review、測試、build、版本控制、依賴管理、文件 | SLO、監控、告警、容量規劃、事故處理、postmortem |
| 典型的失敗 | 程式碼越來越難改，升級一次要半年 | 服務常常壞，或為了不壞而不敢改 |
| 在地圖上的位置 | 偏重變更的流動（上半圈） | 偏重證據的流動（下半圈）與 release |

## 1.7 為什麼它們是同一條生命週期

上面的對照表很容易讓人誤以為「SWE 管開發、SRE 管維運」是兩個獨立的世界。事實上，把它們拆開正是很多組織出問題的原因。

### 變更與可靠性不是對立的

直覺上，變更越多，出事的機會越大，所以「速度」和「穩定」似乎是此消彼長的。但 DORA（DevOps Research and Assessment，一個長期研究軟體交付績效的研究計畫）多年的研究反覆發現：表現最好的團隊，通常在交付速度與穩定性上**同時**表現好；兩者並不是二選一。原因在於，讓變更變快的那些做法，例如小批次、自動化測試、自動化部署、快速回退，同時也讓每次變更的風險變小、出事後恢復得更快。

這個發現把整張地圖串了起來。Software engineering 的實踐（小變更、好的測試、可重現的 build）讓 SRE 的目標更容易達成；SRE 的實踐（canary、監控、error budget）讓變更可以更快、更有信心地進行。第 14 章會介紹 DORA 的四大指標，用來同時量測速度與穩定性。

### 兩條迴路，一個系統

```text
            快、便宜、資訊少                            慢、貴、資訊最真實
   ┌──────────────────────────────────────┐   ┌─────────────────────────────────┐
   │ 開發者內迴路                           │   │ production 外迴路                │
   │ 寫程式 → 本機測試 → 修正（數秒到數分）   │   │ 發布 → 監控 → 事故 → postmortem  │
   │ review / CI（數分到數小時）             │   │（數小時到數週）                  │
   └──────────────────┬───────────────────┘   └──────────────┬──────────────────┘
                      │                                       │
                      └──── postmortem 把外迴路學到的 ─────────┘
                            教訓，變成內迴路的新檢查
```

可以把整個生命週期看成兩個嵌套的迴路。**內迴路**是開發者在變更進入 production 之前得到回饋的地方：本機測試幾秒鐘，CI 幾分鐘，code review 幾小時。它快而便宜，但只能檢查你預先想到的事。**外迴路**是 production 給的回饋：真實使用者、真實流量、真實故障。它慢而昂貴（有時代價是使用者的傷害），但資訊最真實。

成熟團隊的特徵是：**持續把外迴路學到的東西，搬進內迴路**。免運事故在外迴路發現了「API 相容性」這個問題；postmortem 之後，CI 多了一個 API 契約檢查，於是下一次同類錯誤會在 CI 的幾分鐘內被攔下，而不是在 production 的五小時後。下一節的程式會模擬這個效果。

### 分開管理時會發生什麼

如果開發與維運被拆成兩個互不相關的世界，會出現幾種典型的斷裂：

- **證據回不來**：維運團隊知道哪些服務常出事，但這些資訊沒有回到開發的優先順序裡，同樣的問題一再發生。
- **成本轉嫁**：開發團隊做了一個「上線很快、但很難操作」的設計，代價由值班的人在半夜承擔，而做決定的人感受不到。
- **互相防衛**：維運團隊為了保護穩定性，設下越來越多的審批與凍結期；開發團隊為了趕進度，累積更大批的變更一次上線，反而更危險。

本書把 software engineering 與 SRE 放在同一本書裡，就是為了讓你在做每一個決定時，同時看到它在兩條迴路上的影響。

```python
COST = {"design": 1, "review": 2, "test": 4, "ci": 4, "canary": 15, "production": 100}


def make_changes(n, seed=7):
    rng = random.Random(seed)
    # 每個變更有 30% 機率帶著一個缺陷
    return [rng.choice(KINDS) if rng.random() < 0.3 else None for _ in range(n)]


def run(name, stations, monitoring, learning, changes, seed=11):
    rng = random.Random(seed)
    detect = {s: dict(STATIONS[s]) for s in stations}
    cost = escaped = impact = 0
    per_quarter = []
    for i, defect in enumerate(changes):
        if defect is not None:
            for s in stations:
                if rng.random() < detect[s].get(defect, 0.0):
                    cost += COST[s]
                    break
            else:                                  # 一路漏到 production
                escaped += 1
                cost += COST["production"]
                impact += 15 if monitoring else 120  # 有監控：15 分鐘發現；沒有：等客訴
                if learning and "test" in detect:     # postmortem：把這類缺陷寫成測試
                    old = detect["test"].get(defect, 0.0)
                    detect["test"][defect] = min(0.9, old + 0.2)
        if (i + 1) % 60 == 0:
            per_quarter.append(escaped - sum(per_quarter))
    print(name)
    print(f"  漏到 production（每季）：{per_quarter}，共 {escaped} 個")
    print(f"  使用者受影響：{impact} 分鐘；修復成本：{cost}")


changes = make_changes(240)                         # 一年、每季 60 個變更
print(f"一年共 {len(changes)} 個變更，其中 {sum(c is not None for c in changes)} 個帶有缺陷\n")
run("A 寫完直接上線", [], False, False, changes)
run("B 加上 review 與測試", ["review", "test"], False, False, changes)
run("C 完整管線＋監控", list(STATIONS), True, False, changes)
run("D 完整管線＋postmortem 回饋", list(STATIONS), True, True, changes)
```

執行結果：

```text

A 寫完直接上線
  漏到 production（每季）：[18, 17, 16, 14]，共 65 個
  使用者受影響：7800 分鐘；修復成本：6500
B 加上 review 與測試
  漏到 production（每季）：[13, 12, 9, 9]，共 43 個
  使用者受影響：5160 分鐘；修復成本：4362
C 完整管線＋監控
  漏到 production（每季）：[7, 2, 8, 2]，共 19 個
  使用者受影響：285 分鐘；修復成本：2222
D 完整管線＋postmortem 回饋
  漏到 production（每季）：[5, 3, 3, 2]，共 13 個
  使用者受影響：195 分鐘；修復成本：1538
```

逐段解讀：

1. `STATIONS` 是整個模型的核心假設：**每一站只擅長抓某些類型的錯**。測試很會抓邏輯錯誤，但完全抓不到「容量不足」或「金流商故障」，那些只有在接近真實流量的 canary 才可能看到。這些機率是為了示範而設的，不是量測值，但「每一站有盲點」這個結構是真實的。
2. 狀態 A 就是免運事故時的 Harbor：所有缺陷都漏到 production，而且因為沒有監控，每次都要等客訴才知道（模擬中假設 120 分鐘），一年累積 7,800 分鐘的使用者傷害。
3. 狀態 B 加上 review 與測試，漏出的缺陷少了三分之一，但使用者傷害仍然很高。原因有兩個：設定錯誤、容量、依賴故障這三類，review 與測試幾乎抓不到；而漏出去的缺陷依然靠客訴發現。
4. 狀態 C 的最大改善其實來自**監控**：漏出的缺陷數從 43 降到 19，但使用者受影響的時間從 5,160 分鐘降到 285 分鐘，降幅遠大於缺陷數的降幅。這對應到 SRE 的一個重要觀念：你無法讓錯誤永遠不發生，但可以讓它被**快速發現與恢復**，把傷害縮小。
5. 狀態 D 和 C 用完全相同的變更與亂數，唯一差別是每次 production 事故後，postmortem 把那類缺陷「寫成測試」，提高測試站對它的偵測率。結果漏出的缺陷從 19 降到 13，修復成本也降了約三成。這就是 1.7 的「把外迴路的教訓搬進內迴路」。為了讓程式簡短，模型把所有教訓都記在 `test` 這一站；真實世界中，容量不足的教訓通常會變成 load test 或容量告警，依賴故障的教訓會變成 timeout 設定或降級機制，它們分別落在不同的關卡。
6. 注意 C 的每季數字是 `[7, 2, 8, 2]`，跳動很大。這是因為每季只有十多個缺陷，隨機性的影響很明顯。真實團隊看自己的事故數也會遇到同樣的情況：一季的數字下降，不一定代表做對了什麼，要看更長的趨勢（第 14 章談量測時會再討論）。

真實系統當然不是一個機率表。但這段程式的結構對應到真實的工程問題：**每一站的盲點在哪裡**（決定要投資哪種關卡）、**漏出去的錯多快被發現**（決定監控與告警的投資）、**事故的教訓有沒有回到前面的關卡**（決定 postmortem 是否真的有用）。

## 1.10 Trade-offs 與 Failure Modes

這張生命週期地圖本身也可能被誤用。下表列出幾種常見的失敗方式：

| 做法 | 什麼時候會出問題 | 具體情境 | 對策 |
|---|---|---|---|
| 每一站都加上嚴格的關卡 | 關卡太慢、太吵，大家開始繞過 | Harbor 規定每個變更都要兩位資深工程師 approve、跑完 40 分鐘的完整測試，結果大家把一週的修改擠成一個大 PR，review 品質反而下降 | 依風險分級：文件修改與 schema migration 不該走同一條流程；讓關卡快到不值得繞過 |
| 把「測試通過」當成「可以上線」 | 測試只驗證你想到的情況 | CI 全綠，但真實流量下新的查詢讓資料庫 CPU 飆高，測試環境的資料量只有 production 的千分之一 | 把 canary 與監控視為驗證的一部分，而不是上線後的附加品 |
| 只投資前半段，不投資監控 | 錯誤一定會漏出去，漏出去之後沒人知道 | 測試覆蓋率很高，但金流商的錯誤被包裝成「處理中」，三十分鐘後才從客訴發現 | 從使用者旅程定義成功率並設告警（第 32、34 章） |
| 只投資後半段，不投資前半段 | 一直救火，事故重複發生 | 每次都能快速 rollback，但同樣的相容性問題一季發生三次 | 用 postmortem 把教訓變成前段的檢查，並追蹤 action items 是否完成 |
| 八個人就照搬大公司流程 | 流程成本大於它防止的損失 | 八人新創導入正式的變更審查委員會（CAB），每次部署要等週三開會 | 從最小的版本開始：一個 reviewer、幾個關鍵測試、一個結帳成功率告警、一個可回退的 artifact |
| Postmortem 寫完就結束 | Action items 沒有 owner、沒有期限 | 每次事故都寫了「加強測試」，半年後檢查發現一項都沒做 | Action item 要具體、可驗證、有 owner 與期限，並定期追蹤（第 45 章） |

這些失敗方式有一個共同點：都把地圖上的某一站當成獨立的目標，而忘了整條路的目的。整條路只是手段，目的是讓使用者能可靠地使用服務、讓團隊能持續安全地修改它。

## 1.11 AI 時代：什麼變了？

AI coding agent 讓「寫程式」這一站變得非常快。一個描述清楚的功能，agent 可能幾分鐘就產出可以執行的程式碼與測試。但整條生命週期的其他站並沒有自動變快，於是瓶頸移動了：從「寫出程式碼」移到「確認需求對不對」「review 得完嗎」「測試真的有在驗證行為嗎」「上線後能不能快速發現問題」。

DORA 2024 年的研究報告觀察到一個值得注意的現象：團隊導入 AI 的程度提高時，個人感受到的生產力提升，但軟體交付的穩定性反而有下降的跡象（交付速度也略有下降，幅度較小）。報告推測的原因之一是 AI 讓變更變得更大、更多，而小批次正是穩定性的基礎。這個結果提醒我們：只把 AI 接在「寫程式」這一站，而不升級整條路，結果可能是更快地製造更多待 review、待修復的變更。DORA 之後提出的 AI capabilities model 也強調，AI 帶來的效益取決於既有的工程基礎，例如版本控制實踐、小批次工作與品質良好的內部平台。

### 每一站的角色與責任邊界

下表沿著 1.3 的地圖，整理 AI 在每一站適合做什麼，以及哪些事必須留給人：

| 站 | 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|---|
| 需求與設計 | 從需求草擬邊界案例清單（例如「折扣前還是折扣後」）、整理既有程式的資料流、草擬 design doc 初稿 | 產品規則與取捨由產品與 owner 決定；AI 列出的選項不等於完整的選項 |
| 寫程式 | 依清楚的規格實作小範圍變更、補上重複性的程式碼、在隔離分支中修改 | 任務描述要包含目標、限制與完成條件；agent 只拿到任務需要的 repository 與工具權限 |
| Code review | 摘要 diff、指出可能受影響的呼叫端、先跑一輪靜態檢查與常見問題 | 至少一位理解這段程式的人 approve；產生變更的同一個 agent 不能批准自己的變更 |
| 測試 | 根據規格產生測試案例、找出未覆蓋的邊界條件 | 人要檢查測試是在驗證**行為**還是只是重述實作；AI 寫的測試全綠不代表規格正確 |
| Build 與 CI | 分析失敗的 build log、建議修正 | 完成條件以確定性的 build、測試、lint 與安全掃描為準，不能以模型的自我評估取代 |
| Release | 整理變更清單與風險摘要、監看 canary 指標並提出暫停建議 | 擴大發布與資料庫 schema 變更等不可逆動作需要人核准；回退的權限與流程要事先定義 |
| 監控與告警 | 摘要大量指標與日誌、找出和事故時間點吻合的變更 | 告警門檻代表風險接受程度，由服務 owner 決定 |
| 事故處理 | 擔任記錄者整理時間線、根據 runbook 建議下一步、搜尋類似歷史事故 | 止血決策由事故指揮者做；agent 對 production 預設唯讀，寫入操作要經過人確認 |
| Postmortem | 草擬時間線與影響摘要、根據 action items 草擬新的測試或告警 | 「哪些因素促成事故」的判斷、action items 的優先順序與 owner 由人決定 |

### 三個具體做法

**第一，讓每個 AI 產生的變更都帶著證據。** 不論變更是人寫的還是 agent 寫的，進入下一站時都應該帶著可以被別人檢查的證據：測試結果、build 紀錄、它修改了哪些檔案、為什麼這樣改。Harbor 在第 16 章會在 pull request 範本加上「AI 參與」一欄，作者要說明哪些部分由 AI 產生、自己如何驗證，並讓 merge gate 對 AI 生成的變更自動加上額外的檢查。

**第二，把變更維持在小批次。** Agent 很容易一次產出幾千行修改，而人類 reviewer 的理解速度沒有變快。把 agent 的任務切成小的、可以獨立 review 與回退的步驟，比讓它一次做完更安全。這和第 19 章的小批次原則完全一致，只是在 AI 時代更重要。

**第三，責任跟著人走，而不是跟著工具走。** 免運事故如果是 agent 寫的程式碼造成的，postmortem 的問題依然是「我們的流程為什麼沒有攔下它」，而不是「AI 出錯了」。每個 agent 的動作都要能追溯到一位負責的人：誰交派了任務、誰 approve 了變更、誰決定上線。第 2 章會把這個原則整理成人、機器、agent 的責任分工模型，第 47 章會討論組織層級的 agent 授權。

> [!ai] AI 提醒
> AI 也會出現在證據流動的那一半。Harbor 的 AI 客服 agent 本身就是一個 production 服務：它會壞、會變慢，也可能「看起來正常但回答錯誤」。換模型、改 prompt、更新知識庫，都是變更，應該和程式碼變更一樣經過驗證、canary 與監控。第 25 章會把 AI 的 eval 視為一種新的測試，第 32 章會為 AI 服務定義 SLI。

## 1.12 專家怎麼想

- **「這個錯最早可以在哪一站被發現？」** 每次事故之後，資深工程師都會問這個問題。答案通常不是「更小心」，而是「在某一站加一個便宜的檢查」。能把錯誤往左移一站，就能省下一大筆成本。
- **「如果這次變更出事，我們要多久才會知道？多久能恢復？」** 在上線前問這兩個問題，比問「這次變更會不會出錯」更有用。變更一定偶爾會出錯，可以控制的是發現與恢復的速度。
- **「現在的規模需要什麼？」** 八人新創與兩百人組織需要的流程完全不同。專家不會照搬大公司的做法，而是找出當下最大的風險，用最小的成本處理它，並且知道什麼時候該升級。
- **「這個關卡大家相信嗎？」** 一個常常誤報的測試、一個天天響的告警、一個大家都隨便 approve 的 review，都已經失去作用。專家會定期檢查關卡的可信度，而不是只看它存不存在。
- **「開發與維運的回饋有沒有接起來？」** 看一個團隊健不健康，可以看事故的教訓多久會變成程式碼、測試或流程的改變。如果 postmortem 的 action items 半年都沒動，整條迴路就是斷的。

## 1.13 動手練習

1. 選一個你最近做過（或在學校做過）的功能，畫出它從需求到上線的真實路徑。標出每一站實際上有沒有存在、留下了什麼證據、等待了多久。
2. 在上面那張圖上，用另一種顏色標出「如果出錯，最晚會在哪裡被發現」。挑一個錯誤類型，想一想能不能用一個便宜的檢查把它往前移一站。
3. 修改 1.9 的程式：把 `canary` 從管線中拿掉，觀察哪一類缺陷漏出得最多，並解釋為什麼。再試著把 `monitoring` 改成 `False`，比較使用者受影響的分鐘數。
4. 在 1.9 的程式中加入「關卡成本」：每一站對**每一個變更**（不只是有缺陷的）都收取固定成本，例如 review 每次 0.5、canary 每次 2。找出在什麼成本設定下，完整管線反而比狀態 B 更貴，並思考這在真實世界代表什麼。
5. 為免運事故寫一份一頁的 blameless postmortem 草稿：時間線、影響、促成因素（至少三個，不能只寫「阿凱沒注意」）、三個具體可驗證的 action items。
6. 寫一份給 AI coding agent 的任務說明，讓它實作「滿千免運」。說明中要包含目標、不做的範圍、API 限制、驗收案例、禁止的操作，並說明你會用什麼證據判斷它完成了。

## 本章重點整理

- 一段在自己電腦上正確的程式碼，距離可靠的服務還有一整條生命週期：需求與設計、寫程式、code review、測試、build、CI、release、監控、告警、事故處理、postmortem。
- 生命週期有兩股方向相反的流動：變更的流動把想法變成 production 中的程式，證據的流動把 production 的真實情況帶回團隊。
- 每一站只擅長攔下某些類型的錯誤，可靠性來自多個獨立的關卡，而不是任何單一關卡。
- 錯誤越晚被發現越貴；在設計階段一次對話能解決的問題，到 production 可能要付出使用者的信任與深夜的緊急修復。
- 關卡要快、可信、對應具體風險；太慢或太吵的關卡會讓人繞過，反而製造「已經檢查過」的錯覺。
- Artifact 必須不可變且可追溯，回退才會是一個簡單的動作；deploy 與 release 分開（canary、feature flag）能大幅縮小錯誤的影響範圍。
- 監控與告警要基於使用者感受到的症狀，而不是機器的內部狀態；快速發現與恢復，往往比減少缺陷數量更能降低使用者的傷害。
- 事故處理先止血再修復；postmortem 要 blameless，並產出具體、有 owner 的 action items，把教訓變成前段的檢查。
- Software engineering 是「隨時間積分的程式設計」，回答程式碼如何在時間與規模下保持可修改；SRE 是「請軟體工程師來設計維運團隊」，回答服務如何在 production 保持可靠。
- 速度與穩定不是二選一：小批次、自動化測試與部署、快速回退這些做法同時改善兩者。
- 成熟團隊持續把外迴路（production）學到的教訓，搬進內迴路（測試、CI、review）。
- AI 讓寫程式變快，瓶頸就移到需求、review、驗證與上線後的回饋；AI 產生的變更同樣要帶著證據、維持小批次，而責任永遠追溯到人。
- Harbor 會從 8 人新創成長到 200 人組織；判斷「現在的規模需要什麼」本身就是工程能力。

## 延伸問答

> [!question]- Q1. 為什麼「測試全部通過」仍然不代表服務可靠？
> 測試只能驗證你事先想到、並且寫進測試的情況。它無法驗證規則本身是否正確（例如免運到底看折扣前還是折扣後的金額），也很難模擬 production 才有的條件：真實的流量規模、各種舊版 client、外部依賴的故障、真實資料的分佈與數量。
>
> 此外，「可靠」是指服務在一段時間內持續滿足使用者，這包含錯誤發生後多快被發現、多快恢復。一個測試完整但沒有監控、無法回退的服務，第一次出錯就可能造成數小時的傷害。所以可靠性需要發布前的證據（測試、review、CI）和發布後的證據（canary、監控、告警）一起運作，並讓 production 的教訓回到測試中。

> [!question]- Q2. 如果你是八人新創 Harbor 的 tech lead，只能在免運事故之後做三件事，你會選哪三件？
> 一個合理的選擇是：第一，讓部署使用不可變的 artifact，並保留前幾個版本，讓回退變成一個幾分鐘內完成的指令。這直接把那晚五小時的傷害縮到幾分鐘，成本也很低。第二，為結帳成功率加上一個告警，讓團隊在客訴之前就知道使用者付不了錢。第三，要求所有修改 checkout 與 payments 的變更至少經過一位其他人 review。
>
> 選這三件的理由是它們分別處理了「恢復」「發現」「預防」，而且都不需要大量投資。完整的 CI、canary、SLO 都很有價值，但在八人規模下，先做到這三件事的效益最大。這也示範了一個判斷原則：先處理讓傷害最大的那個環節，而不是一次把整條管線建好。

> [!question]- Q3. Software engineering 與 SRE 的分工是什麼？為什麼不能完全分開？
> Software engineering 主要回答「程式碼如何在多年、多人的修改之下保持可安全修改」，關注 codebase、測試、build、review、依賴；SRE 主要回答「服務在 production 要多可靠、怎麼用工程方法達到」，關注 SLO、監控、告警、容量與事故。在生命週期上，前者偏重變更的流動，後者偏重證據的流動與發布。
>
> 不能完全分開，是因為兩者互相決定對方的成本。難以操作的設計會把成本轉嫁給值班的人；沒有回到開發優先順序的事故會一再發生；為了穩定而設下大量審批，又會讓變更變大、風險變高。DORA 的研究也顯示交付速度與穩定性通常一起變好，正是因為兩邊的實踐互相支撐。

> [!question]- Q4. 「大部分事故來自變更」，那為什麼不乾脆少做變更？
> 少做變更短期內可能讓系統比較穩，但長期會帶來更大的風險。第一，安全漏洞修補、依賴升級、法規要求都是被迫的變更，你無法停止。第二，變更做得少，每次累積的修改就更多，一次上線的大變更比十次小變更更難 review、更難測試、出錯時也更難找出原因與回退。
>
> 第三，產品不前進，使用者與業務就會流失，這本身也是一種失敗。所以 SRE 的思路不是減少變更，而是讓變更變得**安全**：小批次、自動化測試、canary、快速回退，並用 error budget（第 32 章）決定什麼時候該放慢。目標是讓變更頻繁而無聊，而不是稀少而驚險。

> [!question]- Q5. Deploy 與 release 有什麼不同？為什麼要把它們分開？
> Deploy 是把新的程式（artifact）放到 production 的機器上執行；release 是讓使用者實際用到新功能。傳統做法中兩者同時發生：部署完成的那一刻，所有使用者都拿到新功能，出錯時也是所有人一起受害。
>
> 把它們分開的方法包括 feature flag 與 canary。用 feature flag，程式碼可以先部署但功能保持關閉，再逐步開給內部員工、5% 使用者、全部使用者，出問題時關掉開關就好，不需要重新部署。用 canary，新版本先只接收一小部分流量，指標正常才擴大。兩者的共同效果是縮小錯誤的影響範圍、縮短恢復時間，並讓「上線」從一個高風險的時刻，變成一個可以逐步觀察、隨時停止的過程。

> [!question]- Q6. 為什麼 postmortem 要 blameless？這樣不就沒人負責了嗎？
> Blameless 不是「沒有人負責」，而是「不把懲罰個人當成事故的解法」。如果犯錯的人會被責罵或影響考績，大家就會隱藏錯誤、延遲回報、在 postmortem 中避重就輕，組織最需要的資訊反而消失了。而且「某人不小心」很少是事故的完整解釋：為什麼流程允許一個人在週五晚上直接改 production？為什麼沒有任何檢查會發現 API 相容性問題？
>
> 責任依然存在，只是落在不同的地方：服務 owner 要負責推動 action items、組織要負責提供安全的流程與工具、每個人要負責誠實地說明發生了什麼。第 9 章與第 45 章會詳細討論 blameless 文化與 accountability 的關係。

> [!question]- Q7. 團隊開始大量使用 AI coding agent 之後，生命週期中哪一站最可能成為新的瓶頸？要怎麼處理？
> 最常見的新瓶頸是 code review 與驗證。Agent 產出程式碼的速度遠快於人閱讀與理解的速度，如果每個變更都很大、描述又不清楚，reviewer 不是被淹沒，就是開始隨便 approve，兩者都會讓錯誤漏到後面。另一個瓶頸是需求：agent 會忠實地實作你描述的東西，包括描述中的模糊與錯誤。
>
> 處理方式是升級整條路，而不是只加快寫程式那一站：把 agent 的任務切成小批次；要求每個變更附上它的驗證證據（測試結果、影響範圍、風險）；把能自動化的檢查（lint、型別、測試、安全掃描）放在 review 之前，讓人只需要判斷需要判斷的部分；任務說明中寫清楚驗收條件。最後，持續用 DORA 這類指標觀察變更失敗率與恢復時間，確認速度提升沒有以穩定性為代價。

> [!question]- Q8. 面試題：請描述一個 commit 從你的 IDE 到 production 的完整旅程，以及每一步可能出錯的地方。
> 一個好的回答會沿著生命週期走：先說明變更前的需求與設計（釐清規則與 API 影響）；寫程式並在本機測試；開 pull request 經過 code review；CI 自動 build 出不可變的 artifact 並執行測試與靜態檢查；合併後經由 canary 或 feature flag 逐步發布；上線後透過 metrics、logs、traces 監控使用者層級的指標；異常時告警通知值班者，先回退止血，再寫 postmortem 把教訓轉成新的測試或檢查。
>
> 加分的地方在於每一步都說出「它攔得住什麼、攔不住什麼」：測試攔不住錯誤的規則、CI 攔不住只在真實流量出現的問題、監控不能阻止錯誤但能縮短傷害時間。如果再補充「我會優先確保能快速發現與回退，因為錯誤一定會漏出去」，以及 AI 產生的變更同樣要通過這些關卡，面試官就能看出你理解的是整個系統，而不只是工具名稱。
