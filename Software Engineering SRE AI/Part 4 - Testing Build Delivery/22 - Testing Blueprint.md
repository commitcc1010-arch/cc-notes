# 第 22 章　Testing Blueprint：Size、Scope 與風險組合

> [!abstract] 本章地圖
> **核心問題**：測試要寫多少、寫在哪一層、花多少時間跑，才能用最低的成本換到「敢改程式碼」的信心？
>
> **你會學到**：
> - 說清楚自動化測試真正提供的價值：改變的信心、可執行的規格、設計回饋與發布速度
> - 分辨 test size（資源與隔離限制）與 test scope（驗證多少程式碼），並為測試正確分類
> - 理解 testing pyramid 的理由，以及冰淇淋甜筒、沙漏這些反模式為什麼會發生
> - 依風險（發生機率 × 影響）為每個重要行為選擇「最早、又足夠真實」的測試層
> - 從成本與信號品質評估一套測試，知道哪些測試在消耗信任而不是建立信任
> - 辨認 AI 生成測試的品質陷阱，並建立能證明測試有效的檢查
>
> **前置知識**：第 6 章（Beyoncé Rule）、第 16 章（code review）、第 19 章（小批次與 trunk-based development）、第 21 章（LSC）
>
> **對應原書**：SWE 第 11 章〈Testing Overview〉；延伸參考 SWE 第 14 章〈Larger Testing〉

## 22.1 故事：一千個綠燈，結帳還是壞了

Harbor 成立第二年下半，公司成長到四十多人、分成 checkout、payments、search、seller、platform 五個團隊，開始認真建立 CI／CD。工程經理 Kevin 在季度會議上展示了一個令人安心的數字：checkout 服務有超過一千個自動化測試，每次合併前都會跑。兩週後，一次例行發布讓所有使用信用卡分期的訂單失敗了三個小時。

事後調查發現，問題出在 checkout 與 payments 之間的介面。payments 團隊把回應欄位從 `amount` 改名為 `amount_cents`，同時在自己的測試中更新了所有斷言；checkout 的測試則全部使用一個手寫的假 payments 回應，裡面還是舊的 `amount`。兩邊各自的測試都是綠燈，因為兩邊各自都「正確」，只是對彼此的假設不一致。

更讓人沮喪的是，checkout 其實有一組端到端測試，用瀏覽器自動化模擬「加入購物車、結帳、付款」。這組 400 個測試要跑 90 分鐘，平均每三次執行就有一次有測試隨機失敗。工程師早就養成習慣：看到 E2E 紅燈就按「重跑」，跑到綠為止。事故當天，那組測試其實正確地失敗了，但值班的工程師以為又是老問題，重跑兩次後第三次剛好在一個不走分期的路徑上通過，變更就這樣被合併了。

剛從 payments 轉任 checkout tech lead 的美華在 postmortem 上說了一段話：「我們的問題不是測試太少。我們有一千個測試在保護『折扣怎麼算』，卻沒有一個便宜又可靠的測試在保護『checkout 和 payments 說同一種語言』。而唯一保護它的那層測試，因為太慢、太不穩，已經沒有人相信了。」

這一章要建立的，就是一份 **testing blueprint**（測試藍圖）：不是「多寫測試」，而是為每一種風險選擇合適的測試層，讓整套測試既能抓到該抓的問題，又快得足以每次變更都跑、穩得足以讓人相信紅燈。

## 22.2 為什麼要寫自動化測試

### 測試的真正產品是「信心」

最直覺的答案是「抓 bug」。這沒錯，但不完整。《Software Engineering at Google》第 11 章給的核心理由是：**自動化測試讓團隊能夠安心地改變程式碼**。當一個 codebase 由幾十個人、經過好幾年持續修改時（第 3 章「隨時間積分的程式設計」），沒有人能在腦中記住所有行為。測試就是把「這段程式碼應該怎麼表現」寫成機器可以反覆檢查的形式，讓下一個修改的人，不論是三年後的同事還是 AI coding agent，都能在幾分鐘內知道自己有沒有弄壞什麼。

從這個角度看，測試提供了四種價值：

| 價值 | 說明 | Harbor 的例子 |
|---|---|---|
| 抓到錯誤 | 在變更合併前發現 regression（回歸錯誤，原本正常的功能壞掉） | 折扣計算改版時，測試發現滿千折百的邊界值算錯 |
| 可執行的規格 | 測試描述「系統應該做什麼」，而且不會像文件一樣過時 | 新人讀 `test_refund_cannot_exceed_paid_amount` 就知道退款上限的規則 |
| 設計回饋 | 難寫測試的程式碼，通常也是耦合太緊、難以修改的程式碼 | 想測運費計算卻必須啟動整個資料庫，暴露出邏輯和資料存取綁在一起 |
| 發布速度 | 有可信的自動化測試，才能小批次、頻繁地發布（第 28、29 章） | 不必等 QA 團隊兩天的手動回歸測試 |

原書用 Google Web Server（GWS）的經驗說明最後一點。GWS 是負責回應 Google 搜尋請求的 web server。2005 年前後它沒有系統性的自動化測試，原書提到一度有超過 80% 的 production 發布帶著必須 rollback 的使用者可見錯誤，工程師對修改程式碼越來越恐懼。GWS 的 tech lead 後來訂下政策：所有新的程式碼變更都必須附帶測試，而且這些測試要持續執行。一年之內，緊急修補的發布次數減少了一半，而同一時期每季的變更數量還在創新高。重點不是測試數量，而是測試讓「改變」重新變成一件可以安心做的事。

### 為什麼手動測試無法規模化

8 人的 Harbor 可以在發布前由大家一起點一遍主要流程。四十多人、每天十幾次合併時，這種做法會遇到三個問題：一是手動測試的時間與功能數量成正比，每加一個功能，回歸測試就更久（第 6 章所說的線性成長警訊）；二是人會累、會漏，同一組步驟執行第一百次時，注意力已經不在了；三是手動測試只能在發布前做，發現問題時距離寫下那行程式碼已經過了好幾天，修復成本高得多。

這不代表手動測試沒有價值。**探索式測試**（exploratory testing，由人主動嘗試奇怪的操作、尋找沒想過的問題）、可用性評估、無障礙檢查（第 11 章）都需要人的判斷。原則是：**能夠寫成明確規則的檢查交給機器，需要好奇心與判斷的交給人**。

## 22.3 一個測試由什麼組成

在討論測試的分類之前，先把「一個測試」拆開。任何自動化測試都有四個部分：

```text
          ┌───────────────── 測試 ─────────────────┐
          │                                         │
 輸入／初始狀態 ──▶  SUT（被測系統） ──▶ 實際輸出 ──▶ oracle 比對 ──▶ pass / fail
 （Given）         （When：執行行為）              （Then：期望結果）
          │                                         │
          └── 環境：時間、網路、資料庫、其他服務 ───┘
```

**SUT**（System Under Test，被測系統）是這個測試要驗證的那部分程式碼，可能是一個函式、一個服務，或整個網站。**Oracle**（判定準則）是判斷結果對不對的依據：可能是一個寫死的期望值（`assert total == 900`），也可能是一條性質（「退款金額永遠不超過付款金額」）。圖下方的「環境」是測試最容易失控的部分：SUT 若依賴真實時間、網路或共享資料庫，測試結果就可能和程式碼本身無關。

一個測試的價值取決於它的**信號品質**（signal quality）：紅燈時代表程式碼真的有問題、綠燈時代表程式碼真的沒問題的程度。測試有兩種錯法：

- **False positive（假紅燈）**：程式碼沒問題，測試卻失敗。原因通常是 flaky（不穩定，同樣的程式碼有時過有時不過）、或測試綁死了實作細節（第 23 章）。代價是浪費時間，更嚴重的是讓人學會無視紅燈，Harbor 的事故正是如此。
- **False negative（假綠燈）**：程式碼有問題，測試卻通過。原因通常是 oracle 太弱（只檢查「沒有丟例外」）、測試資料沒有涵蓋關鍵情況，或者 SUT 被替換成和真實系統行為不同的假物件。Harbor 的假 payments 回應就是一個假綠燈的來源。

接下來談的 size、scope 與 pyramid，本質上都是在管理這兩種錯誤與測試成本之間的平衡。

## 22.4 Test Size：測試被允許使用多少資源

### 為什麼用 size 分類

「unit test」和「integration test」是業界最常用的名詞，但它們的定義因人而異。有人說「只測一個 class 就是 unit test」，即使它連了真的資料庫；有人說「跨兩個 module 就是 integration test」，即使它在一個 process 裡只花 5 毫秒。Google 因此另外定義了 **test size**（測試大小）：它描述的不是測了多少程式碼，而是**測試被允許使用哪些資源**。

| 限制 | Small | Medium | Large |
|---|---|---|---|
| 執行範圍 | 單一 process（許多語言進一步要求單一 thread） | 單一機器，可多個 process | 可跨多台機器 |
| 網路 | 不可 | 只能連 localhost | 可以 |
| 檔案系統、資料庫 | 不可（用記憶體內的替代品） | 可以使用本機上的 | 可以 |
| sleep、等待、阻塞式 I/O | 不可 | 可以 | 可以 |
| 外部系統 | 不可 | 不可 | 可以（但應盡量避免） |
| 典型時間 | 毫秒 | 秒 | 分鐘 |

Google 開源的 build 系統 Bazel（第 27 章）把 size 寫成測試 target 的一個屬性。測試沒有另外指定 timeout 時，Bazel 依 size 給預設的時間上限：small 60 秒、medium 300 秒、large 900 秒，另有第四種 enormous 3600 秒（原書說明 Google 內部其實有四種 size，large 與 enormous 的差別主要是歷史因素）。這個上限針對整個測試 target，而不是其中單一測試函式；超時就判為失敗。

### Size 的限制換來了什麼

這些限制看起來很嚴格，但每一條都是在買**速度**與**確定性**（determinism，同樣的輸入永遠得到同樣的結果）：

- 不能用網路，就不會因為網路抖動而失敗，也不需要等連線逾時。
- 不能用檔案系統與共享資料庫，就不會因為上一個測試留下的資料而失敗，測試可以任意順序、平行地跑。
- 不能 sleep，就不會有「等 2 秒應該就好了吧」這種在忙碌的 CI 機器上剛好不夠的等待。
- 單一 process，就能在幾毫秒內完成，一台機器每分鐘可以跑上萬個。

所以 small test 幾乎不會 flaky，而且非常便宜，可以在每次儲存檔案時就跑。Medium 與 large test 放寬了限制，換來更接近真實的環境，也付出了速度與穩定性的代價。第 26 章會更深入談 **hermetic test**（密閉測試，所有依賴都在測試自己控制之下）與 flakiness 的成因。

> [!warning] 常見誤解
> 「small test 就是測很小一段程式碼。」不對。Size 只關心資源。一個在記憶體中串起 checkout、折扣、運費、庫存四個 module 的測試，若完全不碰網路與磁碟、幾毫秒就跑完，它仍然是 small test。反過來，一個只測一個函式、卻呼叫了真實的匯率 API 的測試，它是 large test，而且很可能 flaky。

## 22.5 Test Scope：測試驗證了多少程式碼

### 三種 scope

**Test scope**（測試範圍）描述的是一個測試**驗證了多少程式碼路徑**，和它用了多少資源無關：

- **Narrow scope**（窄範圍，通常稱 unit test）：驗證一個小單位的邏輯，例如一個函式或一個 class。Harbor 例子：`calculate_discount(cart)` 在滿千折百的邊界值是否正確。
- **Medium scope**（中範圍，通常稱 integration test）：驗證少數元件之間的互動，例如服務與它的資料庫、或兩個服務之間的介面。Harbor 例子：checkout 以真實格式的 payments 回應解析分期資訊；或 checkout 寫入訂單後，能從資料庫正確讀回。
- **Large scope**（大範圍，常稱 end-to-end、system 或 functional test）：驗證整條使用者旅程，經過多個真實服務。Harbor 例子：使用者登入、加入購物車、以分期付款完成結帳，並收到訂單確認通知。

### Size 與 scope 是兩個獨立的軸

把兩個軸畫在一起，就能看出它們為什麼要分開：

```text
              scope（驗證多少程式碼）→
              narrow                 medium                    large
           ┌──────────────────────┬──────────────────────┬──────────────────────┐
  small    │ 折扣函式的 unit test   │ 記憶體中串起 checkout │ 用 in-memory fake    │
 （單一    │ ★ 最多、最便宜        │ + 折扣 + 運費模組     │ 串起整條結帳流程      │
  process）│                      │                      │                      │
           ├──────────────────────┼──────────────────────┼──────────────────────┤
  medium   │ 單一函式卻讀本機檔案   │ checkout + 本機的    │ 本機 docker 跑多個   │
 （單機）  │ （可以考慮改成 small） │ 真實 PostgreSQL       │ 服務的結帳流程        │
           ├──────────────────────┼──────────────────────┼──────────────────────┤
  large    │ 單一函式呼叫外部 API   │ 測試環境中的          │ staging 上的瀏覽器   │
 （多機）  │ ✗ 最該避免            │ checkout ↔ payments  │ E2E 測試 ★ 少而精     │
           └──────────────────────┴──────────────────────┴──────────────────────┘
```

這張表的左上角是理想的大多數：驗證範圍窄、資源限制嚴，又快又穩，失敗時一眼就知道哪裡壞了。右下角是必要但昂貴的少數：最接近使用者真實體驗，但慢、容易 flaky、失敗時要花時間定位。左下角是最該避免的組合：只驗證一小段邏輯，卻承擔了 large test 的所有成本與不穩定。

最有價值的觀念藏在對角線之外：**很多看起來需要 large size 的驗證，其實可以用 small size 做到**。例如右上角「用 in-memory fake 串起整條結帳流程」：scope 很大，但因為所有外部依賴都換成了記憶體中的 fake（第 24 章），它仍然在單一 process 中幾十毫秒完成。好的測試設計會不斷問：「這個驗證能不能往上移一格？」

## 22.6 Testing Pyramid 與它的反模式

### 金字塔的理由

**Testing pyramid**（測試金字塔，由 Mike Cohn 推廣）描述的是一個健康的測試組合：底層是大量窄範圍的 unit test，中間是較少的 integration test，頂端是少量的 end-to-end test。原書把它畫成「Google 版本的 Mike Cohn 金字塔」，並給了一個目標比例：大約 **80% narrow、15% medium、5% large scope**。原書特別說明這只是非常粗略的指引，以測試個數計算，每個團隊的組合都會有些不同。

```text
                 ▲  越往上：越接近真實、越慢、越貴、越容易 flaky、越難定位
                ╱ ╲
               ╱E2E╲          5%   保護關鍵使用者旅程
              ╱─────╲
             ╱ integ ╲       15%   保護元件之間的契約與設定
            ╱─────────╲
           ╱   unit    ╲     80%   保護邏輯與邊界條件
          ╱─────────────╲
                 ▼  越往下：越快、越穩、越便宜、失敗時越容易知道原因
```

金字塔的形狀來自一個簡單的推理：每一層能抓到的錯誤類型不同，但成本差了好幾個數量級。邏輯錯誤是最常見的錯誤，而 unit test 抓邏輯錯誤又快又準，所以應該有最多；跨元件的契約錯誤只有 integration 層看得到，必須有一定數量；E2E 能抓到「所有零件都對、組起來卻不對」的問題，但每個測試都昂貴，只值得用在最重要的旅程上。

### 冰淇淋甜筒與沙漏

兩種常見的反模式：

```text
   冰淇淋甜筒                       沙漏
  ┌───────────┐                  ╲───────────╱
  │  手動測試  │                   ╲   E2E   ╱    很多
  ├───────────┤                    ╲───────╱
  │    E2E     │  很多              ╲integ╱      很少
  ╲───────────╱                     ╱─────╲
   ╲  integ  ╱                     ╱ unit  ╲     很多
    ╲───────╱                     ╱─────────╲
     ╲unit ╱    很少
      ╲───╱
```

**冰淇淋甜筒**（ice cream cone）是倒過來的金字塔：大量手動測試與 E2E、很少 unit test。它通常發生在「先有產品、後補測試」的團隊：程式碼沒有為可測試性設計，邏輯和資料庫、網路綁在一起，唯一能測的方式就是從最外面點過去。結果是測試又慢又不穩，失敗了也不知道是哪裡壞。Harbor 的 checkout 正處在往這個方向滑落的路上：一千個 unit test 保護了邏輯，但 400 個 E2E 承擔了所有跨元件的驗證。

**沙漏**（hourglass）是兩頭大、中間細：很多 unit test、很多 E2E，幾乎沒有 integration test。它常見於元件之間的邊界沒有被好好設計的系統：unit test 只能用 mock 測一個元件，任何跨元件的問題都只能靠 E2E 驗證。Harbor 的 `amount_cents` 事故是典型的沙漏症狀：中間那層「checkout 與 payments 的契約測試」不存在。

### 金字塔不是教條

金字塔是一個起點，不是要精確符合的比例。有人主張「testing trophy」（以 integration 為主體）或微服務的「honeycomb」，理由是在大量串接服務的系統中，風險主要集中在元件之間。這些主張都有道理，它們和金字塔共享同一個原則：**用最便宜、又足夠真實的那一層，去抓每一種錯誤**。如果你的系統幾乎沒有自己的邏輯，主要是在轉接其他服務，那麼 integration 層的比例自然會高一些。要警覺的不是比例偏離 80/15/5，而是「某一種重要的錯誤只能靠最昂貴的那層測試才抓得到」。

## 22.7 Beyoncé Rule：測試也是一種所有權宣告

第 4、6 章提過 **Beyoncé Rule**：「If you liked it, you should have put a CI test on it」，如果你在乎某個行為，就應該用 CI 中的測試保護它。這是原書第 1 章的寫法；第 11 章則用更口語的版本「If you liked it, then you shoulda put a test on it」，並說明「在乎的行為」不只是功能正確，也包括效能、無障礙、安全性，以及系統如何處理失敗。從測試策略的角度看，這條規則說明了測試在大型組織中的另一個角色：**它是團隊之間的契約**。

Harbor 的 platform 團隊要把所有服務的 Python 版本從 3.11 升到 3.12，或是把 HTTP client 函式庫換成新版本。他們不可能理解每個服務的所有細節，只能依靠每個服務自己的測試判斷「這次升級有沒有弄壞你」。如果 search 團隊在乎「搜尋結果依相關度排序，同分時依上架時間排序」，卻沒有測試保護它，而升級後排序變了，Beyoncé Rule 的答案很明確：這是 search 團隊的責任，而不是 platform 團隊的。

這條規則有兩個實務上的推論。第一，**測試必須在 CI 裡跑**，只在某個人筆電上跑的測試不算數，因為別人的變更不會觸發它。第二，**測試必須可信**：如果一個團隊的測試經常 flaky，其他團隊會被迫忽略它的紅燈，等於這個團隊放棄了 Beyoncé Rule 的保護。這也是為什麼 flakiness 不只是一個團隊自己的問題（第 26 章）。

## 22.8 依風險配置測試

### 從「這段程式碼該寫什麼測試」改成「這個風險由哪一層保護」

新手常見的做法是對著程式碼寫測試：寫完一個函式，就為它補幾個 unit test。這會自然地產生大量保護邏輯的測試，卻完全忽略那些不存在於任何單一函式中的風險：介面契約、設定、部署、資料遷移。比較好的做法是反過來，從**風險**出發。

**風險**可以粗略估計為「發生的可能性 × 發生時的影響」。對每一個重要的行為，問三個問題：

1. **它會怎麼壞？** 列出具體的失敗方式，而不是抽象的「可能有 bug」。
2. **最早在哪一層能夠真實地發現它？** 「最早」代表最便宜、最快；「真實」代表那一層的環境足以重現這種錯誤。
3. **它壞了的影響有多大？** 影響大的風險值得多一層保護，甚至延伸到 production 驗證（canary、第 29 章）。

### Harbor 的風險地圖

美華帶著 checkout 團隊為結帳流程做了一次風險盤點：

| 風險（具體的失敗方式） | 可能性 | 影響 | 最早真實的層 | 補充保護 |
|---|---|---|---|---|
| 折扣與運費在邊界值算錯 | 高（規則常改） | 中 | Unit（small） | Property-based test 檢查「總額永不為負」（第 23 章） |
| payments 回應格式改變 | 中 | 高 | Contract test（small／medium，第 25 章） | Canary 觀察付款失敗率 |
| 資料庫 schema 與程式碼不一致 | 中 | 高 | Integration：本機真實資料庫（medium） | Migration 的 expand／contract 流程（第 29 章） |
| 金流商逾時時重複扣款 | 低 | 極高 | Integration：fake 金流商模擬逾時（medium） | Idempotency key 設計（第 41 章）＋ production 對帳 |
| 「加入購物車到付款」旅程斷掉 | 低 | 極高 | E2E（large），只測 3 條主要路徑 | Synthetic probe 在 production 每分鐘跑（第 32 章） |
| 設定錯誤（例如金流商 URL 指錯環境） | 中 | 高 | 部署後的 smoke test | Config 的 schema 驗證 |

這張表改變了團隊的投資方向。他們發現：一千個 unit test 中有一大半在重複測試同一組折扣規則的不同組合，其中很多可以用參數化測試或 property-based test 合併；真正缺少的是 payments 契約測試，而這種測試是 small 或 medium size，又快又穩。至於 400 個 E2E，大部分在測試「折扣顯示是否正確」這種 unit 層就能驗證的事，可以刪掉；留下三條最重要的旅程（一般信用卡、分期、超商取貨付款），並把它們修到穩定。

### 什麼不需要測

風險導向也意味著有些東西不值得寫自動化測試：純粹的資料類別、直接轉呼叫的 getter、第三方函式庫本身的行為（你應該測的是「你如何使用它」）、一次性的遷移腳本（用 dry run 與人工檢查更划算）、以及正在快速實驗、下週就可能刪掉的原型。不測不代表不在乎，而是承認測試有成本，把成本花在最可能出錯、出錯最痛的地方。

## 22.9 測試的成本與信號

### 測試的五種成本

每個測試都是一筆長期的投資，它的成本不只在「寫」的那一刻：

1. **撰寫成本**：寫測試、準備測試資料、建立 fake 的時間。
2. **執行成本**：CI 機器的時間與金錢，以及更重要的，開發者等待回饋的時間。
3. **維護成本**：每次合理的程式碼變更都要跟著修改測試。綁死實作細節的測試（例如斷言「呼叫了 `_compute_tax` 兩次」）維護成本最高（第 23、24 章）。
4. **Flaky 的成本**：不只浪費調查與重跑的時間，還會侵蝕所有測試的可信度。原書的經驗是，flaky 的比例接近 1% 時，測試就開始失去價值，因為工程師不再對紅燈做出反應；Google 自己的 flaky 比例約在 0.15% 上下，即使如此，每天仍有數以千計的 flaky 失敗需要處理。對測試組合而言，這筆成本會隨著測試數量累積，而且集中在最慢、最不 hermetic 的那幾層（22.10 節會算給你看）。
5. **虛假信心的成本**：一個永遠不會失敗的測試，可能是因為程式碼一直正確，也可能是因為它的 oracle 根本檢查不到任何東西。後者比沒有測試更糟，因為它讓人以為受到保護。

### 快速回饋的價值

回饋的時間直接影響開發行為。一套 2 分鐘的測試，開發者會在每次修改後跑；一套 90 分鐘的測試，開發者會把好幾個修改累積起來一起跑，或乾脆只在 CI 上跑，而發現問題時已經想不起那段程式碼的上下文了。這就是第 19 章「小批次」的另一面：**慢的測試會逼人做大的變更**。

所以測試組合也要依速度分層執行：small test 在開發者本機與每次 push 都跑；medium test 在 presubmit（合併前）跑；large test 可能在合併後（postsubmit）或發布前跑，但仍然要能阻止壞的版本前進。第 28 章會詳談 presubmit、postsubmit 與 test selection（只跑受變更影響的測試）。

### 健康檢查：用數據看你的測試組合

一套測試是否健康，可以從幾個數字看出來：

| 指標 | 看什麼 | 警訊 |
|---|---|---|
| 執行時間（p50／p90） | 開發者等多久 | Presubmit 超過 10–15 分鐘，開發者開始繞過 |
| Flaky 比例 | 同樣程式碼重跑結果不同的比例 | 「重跑直到綠燈」成為習慣 |
| 逃逸缺陷（escaped defect） | 漏到 production 的 bug 本該由哪一層抓到 | 同一類缺陷反覆從同一層漏出 |
| 失敗後的定位時間 | 測試紅燈到找出原因要多久 | E2E 失敗經常需要半天調查 |
| 從未失敗過的測試 | 一年內從沒紅過的測試 | 不一定沒用，但值得檢查 oracle 是否太弱 |

**逃逸缺陷分析**是最有價值的一項。每次 production 事故或使用者回報的 bug，都問一個問題：「哪一層測試應該最早抓到它？為什麼沒有？」答案會直接告訴你測試組合缺了什麼。Harbor 的 `amount_cents` 事故，答案是「缺少契約測試」以及「E2E 的紅燈不被信任」，而不是「unit test 不夠多」。

**Code coverage**（覆蓋率，測試執行過的程式碼比例）也常被拿來衡量測試，但它只能告訴你「哪些程式碼完全沒被執行過」，不能告訴你「被執行過的程式碼有沒有被正確檢查」。一個呼叫了所有函式卻不做任何斷言的測試，可以有 100% 的 coverage。Coverage 的正確用法見第 26 章（26.7 節）；要評估「測試抓不抓得到錯」，可以用 mutation testing（故意在程式碼中注入小錯誤，看測試能不能抓到），概念在 23.9 節，作為量測指標的 mutation score 在 26.8 節。

## 22.10 動手寫：比較四種測試組合

下面的程式用一個簡化的模型，比較四種測試組合在「漏出多少缺陷」「回饋多快」「假紅燈多常見」三方面的表現。模型的數字是示意用的假設，不是業界數據，但結構反映了本章的核心推理：不同層抓不同的錯、測試越多報酬遞減、flaky 會隨測試數量累積。

```python
import math
import unicodedata


def pad(text, width):
    """中文字在終端機佔兩格，補空白讓欄位對齊"""
    w = sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in text)
    return text + " " * (width - w)

# 每 100 個變更中，各類缺陷平均出現幾次，以及漏到 production 的代價（工程師小時）
DEFECTS = {
    #  名稱          次數  漏出代價
    "邏輯錯誤":     (6.0,   8),
    "介面契約不合": (2.0,  24),
    "設定／環境":   (1.0,  16),
    "使用者旅程斷": (0.5,  40),
}

# 每一層「單一測試」的特性：秒數、flaky 機率，以及對各類缺陷的最大偵測能力
LAYERS = {
    #         秒數   flaky   邏輯  契約  設定  旅程
    "unit":   (0.05, 0.0001, (0.95, 0.10, 0.00, 0.05)),
    "integ":  (3.0,  0.002,  (0.60, 0.90, 0.50, 0.20)),
    "e2e":    (45.0, 0.01,   (0.30, 0.60, 0.80, 0.90)),
}
SATURATION = {"unit": 150, "integ": 40, "e2e": 15}   # 多少個測試後涵蓋率接近飽和
WORKERS = 20                                          # CI 平行執行的機器數


def coverage(layer, n):
    """測試越多涵蓋越廣，但報酬遞減：1 - e^(-n/k)"""
    return 1 - math.exp(-n / SATURATION[layer])


def evaluate(portfolio):
    escaped_cost = escaped = 0.0
    for i, (name, (count, cost)) in enumerate(DEFECTS.items()):
        miss = 1.0
        for layer, n in portfolio.items():
            miss *= 1 - LAYERS[layer][2][i] * coverage(layer, n)
        escaped += count * miss
        escaped_cost += count * miss * cost
    seconds = sum(LAYERS[l][0] * n for l, n in portfolio.items())
    p_green = math.prod((1 - LAYERS[l][1]) ** n for l, n in portfolio.items())
    return escaped, escaped_cost, seconds / WORKERS / 60, 1 - p_green


PORTFOLIOS = {
    "金字塔 80/15/5":  {"unit": 400, "integ": 75,  "e2e": 25},
    "冰淇淋甜筒":      {"unit": 60,  "integ": 90,  "e2e": 350},
    "沙漏":            {"unit": 300, "integ": 10,  "e2e": 190},
    "只有 unit":       {"unit": 500, "integ": 0,   "e2e": 0},
}

print(pad("組合", 16) + "漏出缺陷  漏出代價(h)  回饋(分)  假紅燈")
for name, p in PORTFOLIOS.items():
    esc, cost, minutes, flaky = evaluate(p)
    print(pad(name, 16) + f"{esc:8.2f}{cost:13.1f}{minutes:10.1f}{flaky:8.0%}")

print("\n每類缺陷的漏出機率（金字塔 vs 只有 unit）：")
for i, name in enumerate(DEFECTS):
    rows = []
    for label in ("金字塔 80/15/5", "只有 unit"):
        miss = 1.0
        for layer, n in PORTFOLIOS[label].items():
            miss *= 1 - LAYERS[layer][2][i] * coverage(layer, n)
        rows.append(f"{miss:6.0%}")
    print("  " + pad(name, 14) + f"{rows[0]}  {rows[1]}")
```

執行結果：

```text
組合            漏出缺陷  漏出代價(h)  回饋(分)  假紅燈
金字塔 80/15/5      0.79         14.9       1.1     36%
冰淇淋甜筒          1.64         17.7      13.4     98%
沙漏                1.46         23.9       7.2     86%
只有 unit           3.79         82.4       0.0      5%

每類缺陷的漏出機率（金字塔 vs 只有 unit）：
  邏輯錯誤          4%      8%
  介面契約不合     11%     90%
  設定／環境       20%    100%
  使用者旅程斷     21%     95%
```

逐段解讀：

1. **模型的假設**寫在 `DEFECTS` 與 `LAYERS`。`DEFECTS` 說明每 100 個變更平均會帶進幾個各類缺陷，以及漏到 production 時要花多少工程師小時處理；契約與旅程類的缺陷較少見，但代價高。`LAYERS` 說明每一層單一測試的執行秒數、flaky 機率，以及對各類缺陷「最多能抓到多少」。注意 unit 對設定錯誤的偵測能力是 0：再多的 unit test 也看不到「金流商 URL 指錯環境」。
2. **`coverage` 函式**表達報酬遞減：前 100 個 unit test 涵蓋很多新的邏輯，第 1,000 個多半是在重測已經被測過的路徑。這對應 Harbor 一千個 unit test 大量重複測試折扣規則的情況。
3. **`evaluate` 的漏出機率**用「每一層都沒抓到」的機率相乘，這假設各層獨立偵測，是一個簡化。假紅燈率的計算也建立在同一個獨立假設上：一次執行要全綠，每個測試都必須同時通過，所以全綠機率是每個測試通過機率的乘積 `Π(1 - f)^n`，假紅燈率就是 1 減去它。這個乘積會讓單一測試很小的 flaky 機率隨數量累積：冰淇淋甜筒的 350 個 E2E 各只有 1% 的機率隨機失敗，合起來卻幾乎每次都有假紅燈（98%），這就是 Harbor 工程師「看到紅燈就重跑」的數學原因。這個公式在 suite 層級的完整推導、自動重試為什麼會掩蓋真正的 bug，以及不穩的測試怎麼 quarantine，第 26 章（26.5、26.6 節）詳談；本章只把它當成比較測試組合的一項成本。
4. **結果的解讀**：「只有 unit」的回饋最快、最穩定，但漏出代價是其他組合的好幾倍，因為契約、設定、旅程類的缺陷幾乎全部漏出。冰淇淋甜筒抓到的缺陷不算太少，問題在於 13 分鐘的回饋（實際上 E2E 還有啟動環境的時間，會更久）與幾乎每次都出現的假紅燈，它在實務上會因為不被信任而失效。沙漏則因為缺少 integration 層，契約錯誤只能靠昂貴的 E2E 碰運氣。
5. **金字塔也不完美**：36% 的假紅燈仍然太高。拆開來看，25 個 E2E 單獨就貢獻約 22%、75 個 integration test 約 14%，400 個 unit test 只有約 4%：數量最少的頂層，貢獻了最多的假紅燈，這正是金字塔頂端要窄的另一個理由。這提醒我們兩件事：測試組合的形狀只解決一半的問題，另一半要靠 flakiness 的治理（第 26 章）；以及頂端的 E2E 要「少而精」，每多一個都會提高整套測試的假紅燈率。

在真實系統中，這些參數不是猜的，而是量出來的：執行時間與 flaky 比例來自 CI 的歷史紀錄，各層的偵測能力來自逃逸缺陷分析（「這個 bug 本該由哪一層抓到」）。模型的價值不在精確的數字，而在讓團隊用同一種語言討論「多加一個 E2E」或「補一層契約測試」的得失。

## 22.11 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會失敗 | 具體情境 | 對策 |
|---|---|---|---|
| 把 80/15/5 當成硬性比例 | 系統的風險不在邏輯，而在元件之間 | 一個主要在轉接三個外部服務的閘道服務，被要求寫大量 unit test，結果大多在測 mock | 依風險地圖決定比例；轉接型服務多投資契約與 integration 測試 |
| 用大量 E2E 取代較小的測試 | 測試慢、flaky、失敗時無法定位，最後不被信任 | Harbor 400 個 E2E 跑 90 分鐘，紅燈被當成雜訊重跑 | 把能下移的驗證移到 unit 或 integration；E2E 只保留關鍵旅程 |
| 只用 mock 做跨元件測試 | 雙方的假設不一致時，兩邊測試都綠燈 | `amount` 改名 `amount_cents`，checkout 的 mock 仍是舊格式 | 用 contract test 或由 owner 維護的 fake（第 24、25 章） |
| 以 coverage 作為測試品質的目標 | 測試執行了程式碼卻沒有檢查結果 | 為了達到 80% coverage 補了一批沒有斷言的測試 | Coverage 只用來找「完全沒測的區域」；用 mutation score 與逃逸缺陷評估品質（第 26 章） |
| 測試只在本機跑 | 別人的變更弄壞你的功能時沒有人知道 | search 的排序測試只在一位工程師的筆電上跑，platform 升級後排序悄悄改變 | 所有測試進 CI；依 Beyoncé Rule 明確責任 |
| 測試綁死實作細節 | 每次重構都要大改測試，團隊開始不敢重構 | 斷言私有函式的呼叫次數，換個演算法就全部失敗 | 透過 public API 測行為（第 23 章） |
| 從不刪除測試 | Suite 越來越慢，很多測試在重複保護同一件事 | 一千個折扣測試中有幾百個測的是同一條規則的不同數字 | 定期檢視執行時間與重複度，合併為參數化或 property-based 測試 |

## 22.12 AI 時代：什麼變了？

AI coding agent 讓「寫測試」的成本大幅下降：給它一個函式，幾秒內就能產生十幾個測試。這是真正的進步，但也帶來一個新的風險：**測試的數量不再代表任何事**。當測試很便宜，稀缺的就變成了判斷：測什麼、用什麼當 oracle、放在哪一層。

### AI 生成測試的五個品質陷阱

**1. 鏡像測試（mirror test）。** 最常見也最危險的陷阱。Agent 讀了實作，再根據實作的行為寫出期望值。如果實作有 bug，測試就把 bug 寫成了規格。例如 Harbor 的運費函式在訂單剛好 1,000 元時錯誤地收了運費（應該免運），agent 讀了程式碼後寫出 `assert shipping_fee(1000) == 60`，這個測試會永遠通過，並且在有人修正 bug 時失敗，阻止正確的修正。

**2. 沒有真正檢查的斷言。** `assert result is not None`、`assert len(items) >= 0`、或只檢查「沒有丟例外」。這些測試讓 coverage 上升，卻幾乎抓不到任何錯誤，是 22.9 節「虛假信心」的典型來源。

**3. 過度 mock。** 為了讓測試快速通過，agent 傾向把所有依賴都 mock 掉，結果測試驗證的是「程式碼有照順序呼叫這些 mock」，而不是「系統做了正確的事」。Harbor 的 `amount_cents` 事故是同一個家族的問題：checkout 的測試依賴一份手寫、早已過期的假回應，測試綠燈只證明程式和這份假設一致。過度 mock 與 stub 漂移的機制，以及如何改用 fake 與 contract test，第 24 章（24.7、24.9、24.10 節）詳談。

**4. 放錯層。** Agent 對著函式寫測試，自然只產生 unit test。它很少主動提出「這裡真正的風險在 checkout 與 payments 的契約，應該寫一個 contract test」。換句話說，AI 會讓金字塔的底層越來越厚，卻不會自動補上中間那一層。

**5. 為了讓 CI 變綠而修改測試。** 當 agent 的任務是「修好這個 bug 並讓測試通過」時，它可能改的是測試的期望值，而不是程式碼；或把失敗的測試標成 skip。

### 讓測試品質可以被驗證

對策的核心是：**不要相信測試，要驗證測試**。幾個可執行的做法：

- **先失敗，再通過。** 修 bug 時，要求 agent 先寫一個在目前程式碼上**會失敗**的測試，證明它真的抓得到這個 bug，再修改程式碼讓它通過。CI 可以自動檢查：把修正 revert 後，新測試必須失敗。
- **Oracle 來自規格，不是實作。** 給 agent 寫測試時，提供需求文件、API contract、產品規則（例如「滿 1,000 元免運」），而不是只給程式碼。要求測試名稱與註解說明它對應哪一條規則。
- **用 mutation testing 檢查測試的辨識力。** 自動在程式碼中注入小錯誤（例如把 `>=` 改成 `>`），看新測試能不能抓到；抓不到的測試沒有實質檢查。機制見 23.9 節，如何當成量測指標見 26.8 節。
- **Review 測試的意圖，而不只是程式碼。** PR 描述要說明：這些測試保護哪些風險、在哪一層、為什麼不能放在更便宜的層。Reviewer 要檢查期望值是否和規格一致。
- **把「修改或刪除既有測試」設成需要人類核准的動作。** Agent 可以新增測試，但修改既有測試的期望值、加 skip、刪除測試，都必須在 PR 中明確標示並由 owner 核准。

### 測試是 agent 的控制訊號

還有一個更根本的變化：對 AI coding agent 而言，測試是它判斷「我做對了沒有」的主要依據。Agent 會反覆執行「修改、跑測試、看結果、再修改」的迴圈，它的工作品質上限，取決於測試的信號品質。一套快速、穩定、oracle 正確的 small test，讓 agent 能在幾分鐘內迭代數十次並收斂到正確的答案；一套 90 分鐘、經常 flaky 的 E2E，會讓 agent 要不是慢得無法使用，就是學會把隨機失敗當作正常。換句話說，**本章的測試藍圖，在 AI 時代同時是在為 agent 設計工作環境**。

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 根據需求文件與 API contract 產生邊界值、異常輸入與 property-based 測試案例 | 期望值必須來自規格；reviewer 逐一確認 oracle，不接受只從實作推導的期望值 |
| 從 postmortem 與 bug 紀錄整理逃逸缺陷，建議「本該由哪一層抓到」 | 測試組合的投資方向（補哪一層、刪哪些測試）由 tech lead 與團隊決定 |
| 為 bug 修正撰寫「先失敗、後通過」的 regression test | CI 自動驗證：revert 修正後新測試必須失敗 |
| 分析 CI 歷史，找出最慢、最 flaky、高度重複的測試，提出合併或下移的建議 | 刪除或合併測試前確認保護的行為仍被其他測試涵蓋；不得以降低覆蓋關鍵風險為代價換取速度 |
| 執行 mutation testing 並解釋存活的 mutant | 判斷存活的 mutant 是真正的測試缺口還是等價變更（不影響行為的改動） |
| 在修改程式碼後自行執行測試並修正失敗 | Agent 不得修改既有測試的期望值、加 skip 或刪除測試，除非 owner 明確核准並記錄理由 |

> [!ai] AI 提醒
> 「AI 幫我們把 coverage 從 60% 拉到 90%」是一個需要追問的成就。請問三個問題：新測試中有多少在 mutation testing 下真的會失敗？期望值是從規格還是從實作得到的？有沒有任何一個新測試在中間那層（契約、integration）？如果答不出來，coverage 的上升可能只是讓 dashboard 更好看。

## 22.13 專家怎麼想

- **「這個測試紅燈時，我會相信它嗎？」** 資深工程師評估一個測試時，先問信號品質而不是數量。一個不被相信的測試，價值是負的：它消耗時間，還教會大家忽略紅燈。他們寧可刪掉一個 flaky 的 E2E，也不願讓它繼續訓練團隊按「重跑」。
- **從逃逸缺陷反推測試組合。** 他們不問「我們的 unit test 比例夠不夠」，而是問「最近五個漏到 production 的 bug，本該在哪一層被抓到？」答案集中在哪一層，下一季的測試投資就放在哪裡。
- **不斷把驗證往下移。** 看到一個 E2E 測試，他們會問：它驗證的事有沒有可能在 integration 或 unit 層做到？用 fake 取代真實依賴後，能不能變成 small size？每往下移一層，速度與穩定性都提高一個數量級。
- **測試是寫給未來的人讀的。** 測試名稱與結構要讓三年後的同事一看就知道「這條規則是什麼、為什麼存在」。他們會把一個好的測試當成比註解更可靠的文件。
- **在乎速度，因為速度決定行為。** 他們知道 presubmit 從 5 分鐘變成 30 分鐘，不只是多等 25 分鐘，而是開發者會開始把變更累積得更大、更常繞過測試。測試套件的執行時間是需要被預算與守護的資源。
- **Beyoncé Rule 是雙向的。** 他們既要求自己的團隊用測試保護在乎的行為，也提醒自己：當別的團隊依賴我們時，我們的 flaky 測試就是在破壞他們的保護。

## 22.14 動手練習

1. 修改 22.10 的程式，加入第五種組合「金字塔＋契約測試」：在 integration 層之外新增一層 `contract`（每個 0.2 秒、flaky 0.0005、對契約錯誤的偵測能力 0.95、其他類型很低），比較它和原本金字塔的漏出代價與假紅燈率。
2. 在 22.10 的程式中把 E2E 的 flaky 機率從 1% 降到 0.2%，觀察冰淇淋甜筒的假紅燈率變化。再計算：要讓 350 個 E2E 一起跑的假紅燈率低於 10%，每個測試的 flaky 機率最高能是多少？
3. 為你的專案（或 Harbor 的搜尋服務）畫一張 22.8 節的風險地圖：至少 6 個具體的失敗方式，標出可能性、影響、最早真實的層與補充保護。
4. 找出你的專案中最慢的 10 個測試，依 22.5 節的 size × scope 表格分類，並為每一個寫下「能否往下移一格、怎麼移」。
5. 讓 AI coding agent 為一個你知道有 bug 的函式寫測試（例如故意讓 1,000 元的訂單收運費），觀察它產生的期望值是否把 bug 寫成了規格。再改成提供規格而非程式碼，比較兩次結果。
6. 挑一個最近的 production bug 做逃逸缺陷分析：它本該由哪一層抓到？當時為什麼沒有？要補什麼測試、放在哪裡？

## 本章重點整理

- 自動化測試的核心價值是讓團隊能安心地改變程式碼；它同時是抓錯工具、可執行的規格、設計回饋與發布速度的前提。
- 手動測試的成本隨功能數量線性成長、容易疲勞遺漏；能寫成明確規則的檢查交給機器，探索式與可用性測試留給人。
- 一個測試由輸入、SUT、oracle 與環境組成；它的價值取決於信號品質，假紅燈侵蝕信任，假綠燈製造虛假信心。
- Test size 描述資源限制（small：單一 process、無網路與磁碟；medium：單機、只能連 localhost；large：可跨機器），限制換來速度與確定性。
- Test scope 描述驗證了多少程式碼（narrow／unit、medium／integration、large／E2E），和 size 是兩個獨立的軸。
- 很多大範圍的驗證可以用 small size 完成，例如以 in-memory fake 串起整條流程；好的設計不斷把驗證往更便宜的層移動。
- Testing pyramid（Google 建議約 80/15/5）的理由是每層抓的錯不同、成本差好幾個數量級；它是起點而不是教條。
- 冰淇淋甜筒（大量 E2E 與手動測試）慢且不可信；沙漏（缺少中間層）讓跨元件的錯誤只能靠昂貴的 E2E 碰運氣。
- Beyoncé Rule 讓測試成為團隊間的契約：你在乎的行為要用 CI 測試保護，而 flaky 的測試等於放棄這份保護。
- 依風險配置測試：對每個重要行為問「會怎麼壞、最早在哪一層能真實發現、影響多大」，而不是對著程式碼補測試。
- 測試的成本包含撰寫、執行、維護、flaky 與虛假信心；慢的測試會逼人做大的變更。
- 逃逸缺陷分析是調整測試組合最有效的依據；coverage 只能找出完全沒測的區域，不能證明測試有效。
- AI 生成測試的主要陷阱是鏡像測試、空洞斷言、過度 mock、只補底層，以及為了讓 CI 變綠而修改測試。
- 驗證 AI 測試的做法包括先失敗再通過、oracle 來自規格、mutation testing，以及把修改既有測試設為需要人類核准的動作。
- 測試是 AI coding agent 判斷對錯的主要訊號；快速、穩定、oracle 正確的測試，決定了 agent 能做到多好。

## 延伸問答

> [!question]- Q1. Test size 和 test scope 有什麼不同？為什麼 Google 要另外定義 size，而不是只用 unit／integration／E2E？
> Size 描述的是測試被允許使用的資源：small test 必須在單一 process 中執行、不能使用網路與磁碟、不能 sleep；medium test 可以在單機上使用多個 process 與 localhost；large test 可以跨多台機器。Scope 描述的是測試驗證了多少程式碼路徑：一個函式、幾個元件的互動，還是整條使用者旅程。
>
> 另外定義 size 的原因是 unit、integration 這些名詞的定義因人而異，而且它們無法告訴你一個測試會多快、多穩。Size 直接對應到執行特性：只要知道一個測試是 small，就知道它幾乎不會因為環境而 flaky、可以平行執行、毫秒內完成。這讓 build 系統可以據此設定 timeout 與排程，也讓團隊能討論「這個大範圍的驗證能不能用 small size 做到」，這往往是提升測試品質最有效的方向。

> [!question]- Q2. 為什麼「測試越多越好」是錯的？請舉出一個增加測試反而讓情況變糟的例子。
> 每個測試都有撰寫、執行、維護、flaky 與虛假信心的成本，而且同一層的測試有報酬遞減：第一百個折扣測試涵蓋了新的邊界，第一千個多半在重測已經被保護的路徑。測試的價值來自它能抓到其他測試抓不到的錯誤，而不是它的數量。
>
> 一個具體的例子是持續增加 E2E 測試。每個 E2E 都有一點隨機失敗的機率，而一次執行要全綠，所有測試都必須同時通過，所以每多加一個，整套測試出現假紅燈的機率就再往上推一點；22.10 節的模型中，350 個 E2E 的冰淇淋甜筒幾乎每次執行都有假紅燈。團隊很快會學會「紅燈就重跑」，於是當某次紅燈是真的時，也被當成雜訊忽略。Harbor 的分期付款事故就是這樣發生的：測試正確地失敗了，但已經沒有人相信它。增加測試讓整套測試的信號品質下降，反而降低了保護。

> [!question]- Q3. 你是 Harbor checkout 團隊的新 tech lead。團隊有 1,200 個 unit test、10 個 integration test、300 個 E2E，presubmit 要跑 70 分鐘。你的前三個月計畫是什麼？
> 這是一個典型的沙漏，而且頂端已經重到拖垮回饋速度。第一步是量測而不是改：從 CI 歷史找出每個測試的執行時間與 flaky 比例，並對最近半年的 production bug 做逃逸缺陷分析，確認哪些錯誤從哪一層漏出。這些數據會讓後續的取捨有依據，也能說服團隊。
>
> 接下來依風險補中間層：為 checkout 與 payments、inventory 之間的介面建立 contract test，為資料庫互動建立使用本機真實資料庫的 integration test。同時整理 E2E：凡是驗證的事能在 unit 或 integration 層做到的，就移下去或刪除，只保留少數關鍵旅程，並把它們修到穩定，移到 postsubmit 或發布前執行，但仍然能阻止壞版本前進。Presubmit 的目標是 10 分鐘以內，由 small 與 medium test 組成。最後檢查重複的 unit test，合併成參數化或 property-based 測試。整個過程要追蹤逃逸缺陷，確認調整沒有讓保護變弱。

> [!question]- Q4. 有人說「我們是微服務架構，testing pyramid 不適用，應該以 integration test 為主」。你怎麼看？
> 這個說法有一部分是對的。在大量串接服務、自身邏輯不多的系統中，風險主要集中在服務之間的契約、設定與資料格式，unit test 能抓到的錯誤比例確實較低。如果硬要達到 80% unit test，很可能產生大量只在驗證 mock 的測試，這沒有價值。
>
> 但要小心兩件事。第一，「以 integration 為主」不等於「以 E2E 為主」：好的 integration test 可以是 small 或 medium size，例如用 contract test 驗證介面、用本機資料庫驗證查詢，仍然快速穩定；若變成大量跨多台機器的測試，就會落入冰淇淋甜筒。第二，金字塔與它的替代方案共享同一個原則：用最便宜、又足夠真實的那一層抓每一種錯誤。正確的做法不是爭論形狀，而是畫出風險地圖，讓比例由風險決定。

> [!question]- Q5. 什麼是 Beyoncé Rule？如果 platform 團隊升級函式庫後弄壞了你的功能，而你的功能沒有測試，責任在誰？
> Beyoncé Rule 是「If you liked it, you should have put a CI test on it」：如果你在乎某個行為，就應該用 CI 中的自動化測試保護它。在大型組織中，platform 或基礎設施團隊會頻繁地進行跨服務的升級與遷移，他們不可能理解每個服務的細節，只能依靠每個服務自己的測試來判斷有沒有造成破壞。
>
> 依照這條規則，如果你的功能沒有測試、因此在升級中被弄壞，主要責任在你的團隊，而不是 platform 團隊。這不是推卸，而是讓規模化成為可能的分工：platform 團隊承諾「不弄壞任何有測試保護的行為」，各團隊承諾「用測試表達自己在乎什麼」。當然，事後仍應做 blameless 的檢討（第 45 章），並且補上測試；platform 團隊也該檢討是否有足夠的漸進發布與監控，讓這類問題能更早被發現。

> [!question]- Q6. 計算題：一套測試有 500 個 small test（flaky 機率 0.01%）、80 個 medium test（0.2%）、40 個 large test（1%）。每次執行至少出現一個假紅燈的機率約是多少？哪一部分貢獻最大？
> 所有測試都通過（沒有假紅燈）的機率是各測試通過機率的乘積：0.9999^500 × 0.998^80 × 0.99^40。逐項計算約為 0.951 × 0.852 × 0.669 ≈ 0.542，所以至少一個假紅燈的機率約為 1 − 0.542 ≈ 46%。
>
> 貢獻最大的是 40 個 large test：單看它們，假紅燈率就有約 33%；80 個 medium test 約 15%；500 個 small test 只有約 5%。Large test 只占測試總數的 6% 左右，卻貢獻了大部分的假紅燈。
>
> 這對測試組合的設計有三個意涵。第一，每新增一個 large test 都要問：它保護的風險，是否值得它帶來的信任成本？能下移到 integration 或 unit 層的驗證，就應該下移。第二，穩定性的改善要優先投資在頂端少數測試，逐一修正它們的不穩定來源，而不是去優化已經很穩的 small test。第三，不必讓所有 large test 都在每次 presubmit 執行，可以依速度與穩定性分層（第 28 章）。至於怎麼量測單一測試的 flaky 率、為什麼自動重試會掩蓋真正的 bug、以及不穩的測試如何 quarantine，見第 26 章（26.5、26.6 節）。

> [!question]- Q7. AI agent 為一個函式產生了 15 個測試，全部通過，coverage 從 40% 升到 95%。你要怎麼判斷這些測試是否真的有價值？
> 首先檢查期望值的來源。如果 agent 是讀了實作再寫出期望值，這些測試可能只是把目前的行為（包括 bug）記錄下來。對照需求文件或產品規則，逐一確認每個期望值是否正確，尤其是邊界值。其次檢查斷言的強度：有沒有只檢查「不是 None」或「沒有丟例外」的測試？
>
> 接著用工具驗證辨識力：執行 mutation testing（23.9 節），看這些測試能殺掉多少 mutant；或手動做幾個小破壞，例如把 `>=` 改成 `>`、把折扣比例改掉，看測試會不會失敗。也要檢查測試是否過度 mock，以及是否綁死了實作細節，導致未來重構時大量失敗。最後問層次問題：這個函式真正的風險是否在它與其他元件的互動？若是，15 個 unit test 也不能取代一個 contract test。Coverage 的上升只說明程式碼被執行過，不說明它被正確檢查過。

> [!question]- Q8. 面試題：如果你只能為一個新服務寫 10 個測試，你會怎麼分配？
> 我會先花時間列出這個服務最重要的行為與最可能、最痛的失敗方式，而不是先寫測試。假設是 Harbor 的退款服務，最痛的失敗是「退款金額超過付款金額」「重複退款」「與 payments 的介面不一致」「整條退款流程斷掉」。
>
> 接著依風險分配：大約 5 個 small unit test 保護核心規則與邊界，例如退款上限、部分退款的計算，其中一個可以是 property-based test 檢查「累計退款永不超過付款金額」；2 到 3 個 integration 或 contract test，驗證與 payments 的介面格式與資料庫的寫入讀回，其中一個模擬金流商逾時以確認不會重複退款；1 到 2 個 E2E 測試覆蓋最主要的退款旅程。回答時強調三點：分配依據是風險而不是固定比例；每個測試都要有清楚的 oracle；以及所有測試都要進 CI，而且要快、要穩，因為不被信任的測試等於沒有。
