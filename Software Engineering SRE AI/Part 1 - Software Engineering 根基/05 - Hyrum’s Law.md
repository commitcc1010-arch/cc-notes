# 第 5 章　Hyrum’s Law：所有可觀察行為都可能成為依賴

> [!abstract] 本章地圖
> **核心問題**：為什麼沒有改任何欄位、沒有違反任何文件承諾的「內部重構」，也可能弄壞別人的程式？要怎麼設計與改變系統，才不會被這些看不見的依賴綁死？
>
> **你會學到**：
> - 說出 Hyrum’s Law 的原文與意思，分辨「宣告的契約」「事實上的契約」與「實作細節」
> - 辨認常見的隱性契約：順序、錯誤訊息、timing、格式細節、預設值與限制、bug
> - 用縮小可觀察面、明確契約、主動隨機化、機器可讀錯誤碼與版本化來設計防禦
> - 依「盤點使用者 → 分類 → 選策略 → 漸進改變 → 移除」的流程，安全地改變可觀察行為
> - 解釋 semantic versioning 能承諾什麼、不能承諾什麼，以及它與 Hyrum’s Law 的關係
> - 判斷 AI coding agent 與 LLM 應用如何放大或幫忙管理隱性依賴
>
> **前置知識**：第 3 章（軟體工程是隨時間積分的程式設計）、第 4 章（依賴與被迫的變更）
>
> **對應原書**：SWE 第 1 章〈What Is Software Engineering?〉中的 Hyrum’s Law 一節；延伸至 SWE 第 15、21、22 章

## 5.1 故事：沒有改任何欄位，卻弄壞了三個地方

Harbor 還是一家 8 人新創的時候，初階工程師阿凱接到一個看起來很單純的任務：inventory 服務的「預留庫存」API 太慢了。使用者把商品放進購物車按下結帳，checkout 服務會呼叫 `POST /reserve`，傳入一串商品編號（SKU），inventory 逐一查詢資料庫、扣住庫存後回傳結果。購物車裡有十件商品時，這個 API 要花 300 毫秒。

阿凱把逐一查詢改成一次批次查詢，回應時間降到 40 毫秒。API 的欄位一個都沒動，request 與 response 的格式完全一樣，所有單元測試都通過。順手之下，阿凱也把錯誤訊息從生硬的「庫存不足」改成比較親切的「商品已售完」，因為 tech lead 美華之前說過錯誤訊息太工程師口吻。Code review 過了，週二下午上線。

接下來三天，三個地方陸續出事。第一個是 app：商品頁上的「售完」標籤不見了，使用者看到的是「發生未知錯誤」。原來 app 的程式不是看錯誤碼，而是檢查錯誤訊息裡有沒有「庫存不足」四個字。第二個是一位大賣家：對方自己寫了一支同步腳本，每天把 Harbor 的預留結果抓回自家的 ERP（企業資源規劃系統），腳本假設回傳的第一筆就是編號最小的商品。以前逐一查詢時結果剛好照編號排序，批次查詢之後順序變成資料庫給的任意順序，對方的庫存帳整個亂掉。

第三個最難查。Checkout 在預留成功後，會立刻從資料庫的 **replica**（唯讀副本，主資料庫的複製品，通常會落後主庫一點點）讀取最新庫存，顯示給使用者「剩餘 N 件」。以前 reserve 要 300 毫秒，這段時間足夠讓 replica 追上；現在 40 毫秒就回來，checkout 讀到的常常是舊資料，使用者看到「剩餘 3 件」，重新整理變成「剩餘 2 件」，客服開始收到「你們的庫存數字亂跳」的投訴。

事後檢討時，阿凱很委屈：「我沒有改任何 API。文件裡沒寫順序，沒寫錯誤訊息的文字，更沒寫要花 300 毫秒。」這句話完全正確，但三個地方確實壞了。美華在白板上寫下一行英文，說這就是今天要學的東西：所有可觀察的行為，最後都會有人依賴。

## 5.2 Hyrum’s Law 說了什麼

### 原文與出處

這條規律以 Google 工程師 Hyrum Wright 命名，Hyrum Wright 也是《Software Engineering at Google》的編者之一。原文是：

> With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody.

意思是：**當一個 API 的使用者夠多時，你在契約裡承諾了什麼已經不重要了；系統所有可以被觀察到的行為，都會被某個人依賴。** 這裡的 API 要廣義理解：函式庫的函式、HTTP 端點、命令列工具的輸出、資料庫 schema、檔案格式、甚至一個 Slack 機器人的訊息格式，只要有別的程式或人會讀取它，它就是一種介面。

這句話不是在批評使用者不守規矩，而是在描述一個統計上幾乎必然的現象。每個使用者都是在「我觀察到系統怎麼表現」的基礎上寫程式，而不是在「文件承諾了什麼」的基礎上寫程式。大多數人不會逐字讀文件；他們試一次、看到結果、照著結果寫下去。只要某個行為穩定地出現，就會有人把它當成理所當然。

### 三層契約

要討論 Hyrum’s Law，先把「契約」拆成三層：

```text
                 ┌───────────────────────────────────────────┐
                 │  宣告的契約（declared contract）            │
                 │  文件、schema、型別簽名明確承諾的行為       │
                 │  例：回傳 items 陣列；缺貨時 code=OUT_OF_STOCK│
                 └───────────────────────────────────────────┘
                 ┌───────────────────────────────────────────┐
  使用者實際      │  事實上的契約（de facto contract）          │
  依賴的範圍 ───→ │  文件沒寫，但已被大量依賴、改了就會出事     │
                 │  例：items 依 SKU 排序；錯誤訊息是「庫存不足」│
                 └───────────────────────────────────────────┘
                 ┌───────────────────────────────────────────┐
                 │  實作細節（implementation detail）          │
                 │  作者認為可以自由改的部分                   │
                 │  例：查詢方式、回應時間、記憶體用量         │
                 └───────────────────────────────────────────┘
  使用者越多、時間越久，下面兩層被依賴的部分越大
```

最上層是作者主動承諾的 **宣告的契約**（declared contract），例如 OpenAPI 文件寫明的欄位與型別。最下層是作者心裡的 **實作細節**，理論上可以隨時改。Hyrum’s Law 指出的問題在中間：**事實上的契約**（de facto contract）是那些沒有人承諾、卻已經被足夠多使用者依賴，以至於實際上改不動的行為。

這三層的界線不是作者能單方面決定的。阿凱認為回應順序屬於實作細節，但對那位賣家來說，它是事實上的契約。界線由「誰依賴了什麼」決定，而作者往往看不到這件事。

### 「足夠多」有多多

「足夠多的使用者」聽起來模糊，可以用一個簡化模型感受。假設某個沒有承諾的行為（例如回應順序），每個使用者獨立地有 0.5% 的機率會不小心依賴它。只有 1 個使用者時，有人依賴的機率是 0.5%；10 個是約 5%；100 個約 39%；1,000 個已經超過 99%。公式是：

```text
P(至少一個使用者依賴) = 1 − (1 − p)^N
p = 0.005，N = 1,000 → 1 − 0.995^1000 ≈ 0.993
```

這個模型很粗糙，真實世界的依賴不是獨立事件，但它說明了關鍵直覺：**單一使用者依賴某個細節的機率很低，但使用者一多，「沒有人依賴」反而變成不可能的事。** 而且一個 API 的可觀察行為不只一種，順序、錯誤文字、延遲、欄位格式加起來有幾十種，每一種都在跑這個機率。

> [!warning] 常見誤解
> 「只要文件寫清楚『順序不保證』，責任就在使用者身上。」在法律或道德上也許如此，但在工程上沒有用。服務壞了，使用者不會先去查文件再決定要不要生氣；如果依賴的人是大客戶或公司內另一個團隊，你還是得處理。文件能降低依賴發生的機率，不能讓依賴消失。

## 5.3 隱性契約長什麼樣子

知道規律之後，下一步是學會看見它。下面這些類別，是實務上最常被不小心依賴的可觀察行為。把它們記成一張清單，每次改程式時對照一次，比事後追查便宜得多。

### 順序

沒有承諾的順序是最經典的隱性契約。資料庫查詢沒有 `ORDER BY` 時，結果常常「剛好」依照主鍵或插入時間排列，直到某天加了 index、做了分區或換了查詢計畫。Hash table（雜湊表）的迭代順序也是如此：它取決於 hash 函式與內部配置，看起來穩定，其實沒有承諾。

這方面有幾個很好的真實例子。Python 從 3.3 版起預設對字串的 hash 加入隨機種子（hash randomization），目的是防禦 **hash flooding** 攻擊（攻擊者刻意送出大量 hash 值相同的鍵，讓雜湊表退化成很慢的串列）；副作用是 `set` 裡字串的迭代順序在每次執行時都可能不同，依賴舊順序的程式就此暴露。另一個方向的例子是 `dict`：CPython 3.6 的新實作剛好會保留插入順序，官方起初說這只是實作細節，但到了 3.7，語言規格正式保證 dict 保留插入順序。實作細節變成了正式契約，部分原因正是大家已經開始依賴它。

Go 語言選擇了相反的策略：map 的迭代順序被刻意隨機化，讓程式設計師從第一天就無法依賴它。《Software Engineering at Google》第 1 章也用 hash 迭代順序當例子：一個長壽的大型 codebase 裡，只要 hash 的實作改變，就會有大量程式因為默默依賴舊順序而壞掉。

### 錯誤訊息與錯誤的形狀

Harbor 的 app 解析「庫存不足」四個字，就是錯誤訊息被當成契約的例子。錯誤訊息是寫給人看的，本來就應該可以改：修正錯字、翻譯成不同語言、寫得更清楚。可是當程式只能從文字判斷錯誤種類時，任何文字修改都是 breaking change（破壞相容性的變更）。

除了文字，錯誤的「形狀」也會被依賴：HTTP 狀態碼是 404 還是 400、錯誤時 response body 是 JSON 還是 HTML、拋出的是哪一種 exception 類別、失敗時有沒有留下部分寫入的資料。一個本來會拋 `ValueError` 的函式改成拋自訂的 `InvalidSkuError`，即使後者是前者的子類別而看似相容，捕捉 `type(e) is ValueError` 的呼叫者也會壞掉。

### Timing 與效能

第三個故事最反直覺：**變快也可能是 breaking change**。Timing（時間特性）包括延遲、處理順序、重試間隔、批次大小與 timeout。有些依賴是明顯的，例如呼叫者的 timeout 設得剛好比你的 p99 延遲多一點，你一變慢它就開始失敗。有些依賴是隱藏的 **race condition**（競態條件：結果取決於多個操作誰先完成），只是因為某個操作一直夠慢而沒有被觸發，Harbor 的 replica 讀取就是如此。

效能變好還可能改變下游的負載型態。一個原本每秒只能處理 100 個請求的服務變快之後，它呼叫的下游服務突然要承受兩倍流量；或者呼叫者原本用迴圈不斷輪詢，因為回應變快，輪詢頻率跟著暴增。第 36 章與第 38 章會談到容量與過載，這裡先記住：延遲與吞吐量都是可觀察行為。

### 格式細節

格式裡藏著大量可被依賴的細節：JSON 欄位的排列順序、數字是 `1.0` 還是 `1`、時間戳記用 UTC 還是本地時區、ID 是不是遞增的數字、字串有沒有前後空白、CSV 欄位的位置、日誌的每一行格式。Harbor 的訂單 ID 一開始是資料庫的自動遞增整數，很快就會有人寫出「ID 越大代表越新」或「用 ID 相減估算訂單量」的程式，哪天換成分散式產生的 ID，這些程式全部失效。

日誌與命令列輸出常被忽略。只要有人用 `grep` 或正規表示式處理你的輸出，輸出格式就成了介面。很多工具因此提供兩種輸出模式：給人看的漂亮格式可以隨時改，另外提供 `--json` 之類的機器可讀格式並承諾穩定。

### 預設值、限制與副作用

**預設值與限制**也是行為：清單 API 預設回傳 20 筆、上傳大小上限 10 MB、rate limit 每分鐘 600 次、某個欄位最多 255 個字元。使用者會依這些數字設計自己的程式。把預設分頁從 20 改成 50，可能讓某個只處理第一頁的報表突然「多出」資料；把限制從 10 MB 降到 5 MB，顯然會壞；但把限制提高也可能讓下游的儲存或處理撐不住。

**副作用**是 API 除了回傳值之外對世界造成的改變：寫入日誌、發出事件、送出通知、更新快取。如果 reserve 成功時一直會順便發一則「庫存變動」事件，某個報表服務可能已經依賴這則事件計算即時庫存；哪天改成批次發送，報表就會延遲。

### Bug 本身

最極端的例子是 bug 被依賴。一個廣為流傳的故事出自 Joel Spolsky 的文章：SimCity 有一個「釋放記憶體之後還繼續讀取」的 bug，在 DOS 上剛好不會出事；Windows 95 為了讓這款熱門遊戲繼續運作，會偵測 SimCity，並讓記憶體配置器以特別的模式執行。作業系統替一個應用程式的 bug 保留了相容性。

Linux kernel 的維護原則「不要破壞 user space」（we don’t break userspace）是同一件事的制度化版本：只要 kernel 的改變讓既有的使用者程式壞掉，就被視為 kernel 的回歸，即使那些程式依賴的是不合理的行為。這個原則讓 Linux 的使用者可以放心升級，代價是 kernel 開發者必須背負大量歷史行為。xkcd 有一則漫畫〈Workflow〉把這件事畫成笑話：某個使用者抗議修好了「按住空白鍵會讓 CPU 過熱」的 bug，因為那是他們工作流程的一部分。

### 網路協定的僵化

把規模放到整個網際網路，就會看到 **protocol ossification**（協定僵化）：協定本身預留了擴充空間，但因為中間的網路設備（防火牆、負載平衡器等）只見過固定的幾種值，看到新值就丟棄封包，擴充空間實際上無法使用。TLS 1.3 就遇到這個問題：早期測試時，部分中間設備看到新的版本號就中斷連線。最後的設計是讓 TLS 1.3 的 ClientHello 在舊的版本欄位裡繼續填 TLS 1.2 的值，真正的版本改放在一個擴充欄位中。

為了避免同樣的事再發生，IETF 定義了 **GREASE** 機制（RFC 8701）：實作者（主要是 client，server 也可以）會在 cipher suite、擴充、支援版本等可擴充的欄位中，隨機放入一批保留的無意義值，強迫對方的實作與中間設備從一開始就「正確忽略不認識的值」。這是「主動隨機化以防止依賴」在協定層的應用，5.5 節會把它變成一般的設計原則。

## 5.4 為什麼時間與規模會放大它

### 你不知道使用者是誰

Hyrum’s Law 最麻煩的地方在於，作者通常不知道誰依賴了什麼。公司內部的程式也許還能用 code search（程式碼搜尋，第 21 章）找到呼叫者；對外的 API、開源函式庫、手機 app 的舊版本、賣家自己寫的腳本，作者根本看不到它們的原始碼。Harbor 的工程師不可能讀到那位賣家的 ERP 腳本。

更麻煩的是依賴會複製。一個工程師寫了「解析錯誤訊息」的程式，同事參考它寫了第二個，新人從範例複製了第三個。隱性依賴就像程式碼裡的一種習慣，會透過複製貼上、內部範例、Stack Overflow 答案擴散；在 AI coding agent 普遍之後，擴散得更快（5.10 節）。

### 時間讓偶然變成必然

第 3 章說過，軟體工程是隨時間積分的程式設計。對一次性腳本來說，Hyrum’s Law 幾乎不重要：使用者只有自己，用完就丟。對一個要活十年的服務來說，它幾乎是必然的：每多一個月，就多一些使用者有機會觀察到某個行為並依賴它。

這也解釋了為什麼「越晚改越貴」（第 4 章的升級成本曲線）。一個行為剛上線一週就改，依賴它的人寥寥無幾；同一個行為存在三年之後再改，可能牽動幾十個團隊與外部客戶。對隱性依賴而言，時間不只是成本的乘數，還會不斷製造新的依賴。

### 內部 API 與公開 API 的差別

能不能看見並修改所有使用者，決定了應對策略。如果一個函式庫只在同一個 repository 內被使用，作者可以搜尋所有呼叫點，在同一個變更裡把它們全部改掉，再一起測試。Google 的 monorepo（單一大型程式碼庫，第 19 章）配合大規模變更工具（第 21 章），讓很多內部 API 能用這種方式演進：與其永遠維持舊行為，不如把所有呼叫者一起改。

公開 API 沒有這個選項。作者無法替使用者改程式，也無法強迫他們同時升級，只能靠版本化、長時間的相容期與淘汰流程（第 18 章）。所以同樣是「要不要改這個行為」，內部 API 與公開 API 的答案可能完全相反。這個差別值得在設計 API 時就想清楚：**一個介面打算給誰用，決定了你未來改變它的成本。**

## 5.5 設計防禦：讓不該被依賴的行為難以被依賴

Hyrum’s Law 無法被「解決」，只能被管理。管理的方向有兩個：在設計時減少多餘的可觀察行為，並讓真正重要的行為成為明確的契約。下面六種手法由簡單到複雜排列。

### 1. 縮小可觀察面

能不暴露的就不要暴露。每多回傳一個欄位、多一種錯誤類型、多一個可調參數，就多一個未來改不動的東西。API 只回傳使用者真正需要的資料，不要因為「反正資料庫有」就把整列資料丟出去；內部的資料庫 ID、內部狀態碼、除錯資訊不要出現在公開 response 裡。

一個常見的技巧是 **不透明的識別碼**（opaque identifier）。與其讓分頁 API 接受 `offset=40`，不如回傳一個 `next_page_token`，內容是經過編碼、使用者無法解讀的字串。使用者只能拿它去要下一頁，不能自己算、也不能依賴它的格式，你就保留了日後把分頁實作從 offset 改成 cursor 的自由。訂單 ID 也可以用不帶順序意義的格式，避免使用者從 ID 推論時間或數量。

### 2. 把重要的行為寫成明確契約

有些行為使用者真的需要，就不應該讓它停留在事實上的契約，而是正式承諾。如果使用者確實需要結果依 SKU 排序，就在文件與 schema 中寫明「items 依 sku 升冪排列」，並加上測試保證它。正式承諾的好處是：作者知道自己不能改它，改動時會被測試擋下；使用者知道可以安心依賴。

反過來，不承諾的部分要明確寫出「不保證」，例如「items 的順序不保證，請自行排序」。這不能阻止所有依賴，但能在 code review 與爭議時提供依據。第 17 章會詳細討論 API 契約與文件。

### 3. 主動隨機化沒有承諾的行為

文件寫「不保證」效果有限，因為大多數人不會讀到那一行。更有效的做法是讓沒有承諾的行為**真的不穩定**，讓依賴它的程式在開發與測試階段就失敗，而不是在三年後的 production 才失敗。Go 的 map 迭代順序、Python 的 hash randomization、TLS 的 GREASE 都屬於這一類。

在自己的系統裡，可以這樣做：在測試環境與開發環境中，把無序結果主動打亂；錯誤訊息加上隨機的追蹤編號，讓「比對整串文字」的程式無法通過；在 staging 環境注入隨機延遲，讓依賴 timing 的 race condition 提早出現。關鍵是在**使用者寫程式的當下**就給他們回饋。

> [!tip] 隨機化放在哪裡
> 不一定要在 production 隨機化。Production 的穩定順序有時對除錯與快取有好處；但開發環境、測試替身（test double，第 24 章）與 SDK 的 mock 回應應該刻意打亂。重點是讓錯誤的依賴在便宜的地方就失敗。

### 4. 給程式穩定的東西，給人可以改的東西

錯誤訊息的問題，根源是把「給程式判斷用的資訊」和「給人閱讀的資訊」混在同一個欄位。解法是分開：

```text
{
  "error": {
    "code": "OUT_OF_STOCK",          ← 給程式：穩定、列舉、寫進契約
    "message": "商品已售完",          ← 給人：可以改寫、翻譯
    "retryable": false,               ← 給程式：明確的重試語意
    "details": {"sku": "S-404"}       ← 給程式：結構化欄位，不用從文字解析
  }
}
```

`code` 是有限集合中的值，新增值要謹慎，刪除或改名就是 breaking change；`message` 明確標示為給人看、隨時可能改。`retryable` 把「這個錯誤可以重試嗎」這件事變成契約的一部分，否則每個呼叫者都會自己猜，有人看 HTTP 狀態碼、有人看訊息文字。很多公開 API 的錯誤格式都採用類似的分層，這也是第 17 章 API 契約的一部分。

### 5. 對輸入嚴格，從第一天開始

網路界有一句老話叫 **Postel’s law**（又稱 robustness principle）：「對自己送出的東西要保守，對別人送來的東西要寬容。」寬容地接受輸入在早期能提高互通性，卻是 Hyrum’s Law 的溫床。如果你的 API 默默接受 `quantity: "3"`（字串）和 `quantity: 3`（數字），一段時間後就會有使用者送字串；哪天你換了一個嚴格的解析器，他們就壞了。

比較可持續的做法是：從第一天起嚴格驗證輸入，不認識的欄位、錯誤的型別直接回傳清楚的錯誤。一開始嚴格、之後放寬是相容的變更；一開始寬鬆、之後收緊幾乎一定會弄壞某些人。

### 6. 版本化與契約測試

當行為必須改、又有大量使用者依賴時，**版本化**提供一條並行的路：同時提供 `/v1/reserve` 與 `/v2/reserve`，讓使用者在自己的時程內遷移。版本化的代價是維護多套行為，所以它是最後的手段，而不是預設的選項。版本的實作方式（URL、header、欄位）與淘汰流程在第 17、18 章討論。

**契約測試**（contract test）則把「使用者依賴什麼」變成可執行的檢查。最有效的形式是 consumer-driven contract：由使用者一方寫下「我會這樣呼叫你、我需要回應裡有這些東西」，提供者每次變更都要跑過所有使用者的契約（第 25 章會介紹 Pact 這類工具）。這把原本隱形的事實上契約，變成提供者在 CI 裡看得到的東西。注意「contract test」這個詞在本書有兩種用法：這裡與第 25 章的 consumer-driven contract，是由使用者寫下期待、在提供者那一側驗證；第 24 章的 contract test 則是讓測試替身（fake）和真實實作跑同一套測試，確認 fake 沒有偏離真實行為。兩者都在防止「各自的測試全綠、接起來卻壞」，但守的是不同的邊界。

## 5.6 安全地改變可觀察行為

設計防禦能減少未來的問題，但 Harbor 現在就有已經被依賴的行為要改。這一節給出一個可重複使用的流程。

```text
 ① 盤點使用者         ② 分類行為             ③ 選擇策略
 code search          宣告的契約？          保留並寫進契約
 存取日誌 / telemetry  事實上的契約？   ──→  遷移後再改
 User-Agent / API key  實作細節？            直接改並通知
        │                                          │
        └──────────────────────┬───────────────────┘
                               ▼
 ④ 漸進改變：flag / opt-in → 雙軌比對 → 小比例 rollout → 觀察
                               │
                               ▼
 ⑤ 收尾：通知、追蹤剩餘使用者、移除舊行為、補上防止再依賴的測試
```

### ① 盤點使用者：用證據取代猜測

第一步是回答「誰在用、怎麼用」。可以用的證據有幾種：code search 找出所有呼叫點與解析 response 的方式；存取日誌依 API key、User-Agent 或來源服務統計呼叫量；在 response 中加上實驗性欄位，觀察誰的行為改變。對外部使用者，最可靠的方式往往是直接聯絡流量最大的幾位，問他們如何處理回應。

Harbor 事後補做的盤點發現：reserve API 有 4 個內部呼叫者（checkout、app、後台、報表），以及 3 位大賣家的外部腳本。這份清單本身就是有價值的資產，下次改動時可以直接使用。

### ② 分類：這個行為現在屬於哪一層

對每個要改變的行為，判斷它目前在三層契約中的位置。判斷依據不只是文件，還包括：有多少使用者依賴、依賴者有多重要、依賴是否合理。依 SKU 排序的回應雖然沒寫在文件中，但若半數使用者都依賴，它實際上已經是契約；某個使用者依賴「API 要花 300 毫秒」，這種依賴不合理，應該由使用者修正。

### ③ 選擇策略

| 策略 | 適用情境 | Harbor 的例子 |
|---|---|---|
| **保留並升格為契約** | 依賴廣泛且合理，維持成本低 | 回應依 SKU 排序：成本只是一次排序，乾脆正式承諾 |
| **遷移後再改** | 依賴不合理但使用者重要，需要給時間 | 錯誤訊息：先提供 `code` 欄位，協助 app 改用 code，再修改文字 |
| **直接改並通知** | 依賴不合理、影響小，或為了安全必須改 | replica 讀取的 race：這是 checkout 的 bug，checkout 改成從主庫讀取或使用 reserve 回傳的數字 |
| **永久保留舊行為** | 使用者無法修改（例如已售出的硬體、無人維護的舊 app 版本） | 舊版 app 仍在使用者手機上：伺服器端對舊版 client 保留舊訊息格式 |

這張表的重點是：「不要改」和「直接改」都是合理選項，取決於依賴的廣度、合理性與修改成本。把所有歷史行為永久凍結，會讓系統無法修 bug 與演進；完全無視依賴，會不斷製造事故。

### ④ 漸進改變

決定要改之後，不要一次切換。常用的手法：

- **Feature flag 或 opt-in**：新行為先藏在一個開關後面，讓願意的使用者主動開啟（例如在 request 加上 `X-Harbor-Behavior: sorted-v2`），收集回饋。Feature flag 的機制在第 29 章詳談。
- **雙軌比對**（dual run 或 shadow comparison）：新舊實作同時執行，使用者只拿到舊結果，系統在背景比較兩者的差異並記錄下來。阿凱的批次查詢若先用這個方式跑一週，就會發現「順序不同」的比例是 100%，提早得知風險。
- **小比例 rollout**：先對 1% 的流量或特定幾個使用者啟用，觀察錯誤率與客訴，再逐步擴大。這就是 canary 的概念（第 29 章）。

### ⑤ 收尾

改變完成不代表結束。要通知所有已知使用者並記錄在 changelog（變更紀錄）裡，**行為變更要和欄位變更一樣寫清楚**；追蹤剩餘還在使用舊行為的使用者，直到可以安全移除；最後補上測試或隨機化，防止同樣的依賴再長出來。淘汰舊行為的完整流程，包括 advisory 與 compulsory deprecation 的差別，在第 18 章展開。

> [!example] 例子：Harbor 的修正版
> 美華與阿凱重新規劃了這次變更：先在 response 加上 `code` 欄位並通知負責 app 的同事改用（一週）；決定把「依 SKU 排序」寫進契約，因為成本極低而依賴者是重要賣家；checkout 的 replica 讀取被當成 checkout 自己的 bug 修正；最後才部署批次查詢，並先以雙軌比對確認除了延遲之外結果完全一致。整個過程多花了兩週，但沒有再引發任何客訴。

## 5.7 Hyrum’s Law 與 Semantic Versioning

### SemVer 承諾了什麼

**Semantic versioning**（語意化版本，簡稱 SemVer）用 `MAJOR.MINOR.PATCH` 三個數字溝通變更的性質：不相容的 API 變更升 MAJOR，向後相容的新功能升 MINOR，向後相容的 bug 修正升 PATCH。例如 `2.3.1 → 2.4.0` 代表「加了新東西，舊的用法應該都還能用」，`2.4.0 → 3.0.0` 代表「有東西被破壞了，升級前請讀說明」。

SemVer 的「API」指的是**宣告的公開 API**。它假設相容與否可以由作者判斷：作者看自己改了什麼，對照宣告的契約，決定升哪一個數字。

### Hyrum’s Law 對 SemVer 的挑戰

Hyrum’s Law 指出這個假設在使用者夠多時會失效。阿凱的變更以 SemVer 的標準是 PATCH 或 MINOR：沒有改任何公開欄位。但對依賴順序、訊息文字與 timing 的使用者來說，它是 MAJOR。換句話說，**當使用者夠多時，幾乎任何變更都是某個人的 breaking change**；作者依自己的契約判斷版本號，只能表達「依照我的承諾，這次應該相容」。

《Software Engineering at Google》第 21 章因此把 SemVer 的版本號描述為對相容性的一種估計：它是有用的溝通工具，但資訊是有損失的，無法保證你的特定用法不會壞。這不代表 SemVer 沒用。它仍然是目前開源生態系溝通變更意圖最好的共同語言，只是必須搭配其他證據：自動化測試、lock file、在升級前跑自己的測試套件。第 20 章會完整討論依賴管理與 SemVer 的限制。

### 實務上的結論

把兩者放在一起，實務上可以得到三個做法。作為提供者，版本號照宣告的契約升，但 changelog 要寫出「可能影響使用者的行為變更」，即使它們不在契約內，例如「回應順序改變」「錯誤訊息文字改變」「平均延遲大幅下降」。作為使用者，不要依賴宣告契約以外的行為；若不得不依賴，寫一個測試把這個假設鎖住，升級時就會第一時間發現。作為組織，盡可能讓使用者與提供者的變更在 CI 中相遇，讓測試而不是事故告訴你相容性出了問題。

## 5.8 動手寫：相容性矩陣與隨機化

下面的程式把本章的三個想法串起來：用簡化模型估計「有人依賴未承諾行為」的機率；用一個相容性矩陣，讓同一批 consumer 分別對 reserve API 的 v1 與 v2 執行，看誰壞了；最後示範在測試環境主動打亂順序，讓錯誤依賴提早曝光。

```python
import random
from dataclasses import dataclass


def p_someone_depends(p: float, consumers: int) -> float:
    """每個 consumer 獨立地以機率 p 依賴某個未承諾的行為。"""
    return 1 - (1 - p) ** consumers


print("== 有人依賴某個『未承諾行為』的機率（p = 0.5%）==")
for n in (1, 10, 100, 1_000, 10_000):
    print(f"consumers = {n:>6,}  → {p_someone_depends(0.005, n):6.1%}")


# ---- Provider：inventory 的 reserve API，v1 與 v2 ----
@dataclass
class Response:
    ok: bool
    code: str          # 文件承諾：機器判斷用的錯誤碼
    message: str       # 文件明說：給人看，可能改變
    items: list        # 文件明說：順序不保證
    latency_ms: int    # 文件沒提


def reserve_v1(sku_ids):
    if "S-404" in sku_ids:
        return Response(False, "OUT_OF_STOCK", "庫存不足", [], 300)
    return Response(True, "OK", "", sorted(sku_ids), 300)   # 剛好依 sku 排序


def reserve_v2(sku_ids, rng=None):
    if "S-404" in sku_ids:
        return Response(False, "OUT_OF_STOCK", "商品已售完", [], 40)
    items = list(sku_ids)
    (rng or random.Random(7)).shuffle(items)                # 批次查詢，順序不定
    return Response(True, "OK", "", items, 40)


# ---- Consumers：各自依賴了不同的可觀察行為 ----
def app_badge(api):                  # 解析錯誤訊息文字
    r = api(["S-404"])
    return "售完" if "庫存不足" in r.message else "未知錯誤"


def app_badge_fixed(api):            # 只看錯誤碼
    r = api(["S-404"])
    return "售完" if r.code == "OUT_OF_STOCK" else "未知錯誤"


def erp_first_item(api):             # 假設第一筆就是 sku 最小的
    r = api(["S-3", "S-1", "S-2"])
    return r.items[0]


def checkout_replica_read(api):      # 隱性依賴：reserve 夠慢，replica 才追得上
    r = api(["S-1"])
    replica_lag_ms = 120
    return "讀到新庫存" if r.latency_ms > replica_lag_ms else "讀到舊庫存"


consumers = {
    "app 售完標籤（解析訊息）": (app_badge, "售完"),
    "app 售完標籤（看錯誤碼）": (app_badge_fixed, "售完"),
    "賣家 ERP 取第一筆": (erp_first_item, "S-1"),
    "checkout 讀 replica": (checkout_replica_read, "讀到新庫存"),
}

print("\n== 相容性矩陣：同一批 consumer 對 v1 / v2 ==")
for name, (fn, expected) in consumers.items():
    v1, v2 = fn(reserve_v1), fn(reserve_v2)
    flag = "OK   " if v2 == expected else "BREAK"
    print(f"[{flag}] v1={v1} / v2={v2}  ← {name}")


# ---- 防禦：在測試環境主動打亂「不保證的順序」 ----
def flaky_rate(consumer, expected, trials=1000):
    rng = random.Random(42)
    fails = sum(consumer(lambda s: reserve_v2(s, rng)) != expected
                for _ in range(trials))
    return fails / trials


print("\n== 測試環境每次打亂順序，1,000 次中失敗比例 ==")
print(f"賣家 ERP 取第一筆：{flaky_rate(erp_first_item, 'S-1'):.1%}")
```

執行結果：

```text
== 有人依賴某個『未承諾行為』的機率（p = 0.5%）==
consumers =      1  →   0.5%
consumers =     10  →   4.9%
consumers =    100  →  39.4%
consumers =  1,000  →  99.3%
consumers = 10,000  → 100.0%

== 相容性矩陣：同一批 consumer 對 v1 / v2 ==
[BREAK] v1=售完 / v2=未知錯誤  ← app 售完標籤（解析訊息）
[OK   ] v1=售完 / v2=售完  ← app 售完標籤（看錯誤碼）
[BREAK] v1=S-1 / v2=S-2  ← 賣家 ERP 取第一筆
[BREAK] v1=讀到新庫存 / v2=讀到舊庫存  ← checkout 讀 replica

== 測試環境每次打亂順序，1,000 次中失敗比例 ==
賣家 ERP 取第一筆：67.9%
```

逐段解讀：

1. `p_someone_depends` 是 5.2 節的簡化模型。10,000 個使用者時顯示 100.0%，實際值是非常接近 1 但不等於 1，只是四捨五入後的結果。重點是曲線的形狀：從「幾乎沒人」到「幾乎一定有人」，中間只隔兩個數量級。
2. `Response` 的註解標出每個欄位屬於哪一層契約。`code` 是宣告的契約；`message` 與 `items` 的順序文件明說不保證；`latency_ms` 文件連提都沒提。真實系統中，latency 不會是 response 的欄位，這裡把它寫出來，是為了讓「timing 也是可觀察行為」在程式中看得見。
3. 相容性矩陣中，v2 沒有違反任何宣告的契約，四個 consumer 卻壞了三個。唯一沒壞的是只依賴宣告契約（`code`）的那一個，這就是 5.5 節「給程式穩定的東西」的效果。
4. `checkout_replica_read` 示範 timing 依賴：它沒有讀 `latency_ms` 做判斷的意圖，只是真實世界中「reserve 夠慢」掩蓋了 replica 延遲。程式裡用一個比較把這個隱形條件寫出來。
5. `flaky_rate` 示範主動隨機化。測試環境每次打亂順序後，依賴第一筆的 consumer 約有三分之二的機率失敗（三個元素中，第一筆剛好是 S-1 的機率是三分之一）。在 production 中「順序一直很穩定」的 API，若在測試中這樣打亂，錯誤依賴會在開發者寫程式的當天就被看到。

第二段程式示範 Python 自己的 hash randomization。它用三個不同的 `PYTHONHASHSEED` 啟動子程序，印出同一個 set 的迭代順序：

```python
import os
import subprocess
import sys

CODE = "print(list({'cart', 'search', 'checkout', 'payments', 'inventory'}))"

for seed in ("1", "2", "3"):
    env = {**os.environ, "PYTHONHASHSEED": seed}
    out = subprocess.run([sys.executable, "-c", CODE], env=env,
                         capture_output=True, text=True).stdout.strip()
    print(f"PYTHONHASHSEED={seed}: {out}")

# dict 的插入順序從 Python 3.7 起是語言保證，不受 hash seed 影響
d = {"cart": 1, "search": 2, "checkout": 3}
print("dict 迭代順序:", list(d))
```

在 Python 3.14 上的執行結果：

```text
PYTHONHASHSEED=1: ['inventory', 'payments', 'cart', 'search', 'checkout']
PYTHONHASHSEED=2: ['checkout', 'inventory', 'payments', 'cart', 'search']
PYTHONHASHSEED=3: ['search', 'cart', 'payments', 'inventory', 'checkout']
dict 迭代順序: ['cart', 'search', 'checkout']
```

同一個 set、同一段程式，三種順序。你在其他 Python 版本執行時，看到的順序可能和上面不同，這本身就是本章的重點：沒有承諾的行為，換一個版本就可能改變。相對地，dict 的插入順序是語言規格的一部分，在任何 3.7 以後的版本都一樣。

把這兩段程式對應到真實系統：相容性矩陣就是 consumer-driven contract test 的雛形，差別在於真實的 consumer 測試由各使用者團隊維護，並在提供者的 CI 中執行；隨機化對應到測試替身、SDK 的 mock 與 staging 環境刻意打亂無序結果的做法。

## 5.9 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會出問題 | 具體情境 | 對策 |
|---|---|---|---|
| 把所有歷史行為永久保留 | 系統無法修 bug、無法改善效能，維護成本持續累積 | 為了一個賣家依賴的錯誤排序，所有新功能都要繞過它，三年後沒人敢碰這段程式 | 依廣度與合理性分類，不合理的依賴給遷移期後移除 |
| 只靠文件寫「不保證」 | 使用者不讀文件，依賴照樣出現 | 文件寫順序不保證，但 SDK 範例程式直接取 `items[0]` | 範例、SDK 與 mock 都要遵守契約，並在測試環境隨機化 |
| 在 production 也隨機化 | 除錯困難、快取命中率下降、使用者看到結果跳動 | 搜尋結果每次重新整理順序都不同，使用者以為系統壞了 | 隨機化放在開發與測試環境；production 若要穩定順序，就正式承諾一種順序 |
| 過早版本化 | 同時維護多個版本，每個 bug 要修好幾次 | 為一個小改動開 v2，結果 v1、v2 各自分歧，兩年後還在並行 | 優先用相容的方式演進（只新增、不修改），版本化留給真正不相容的變更 |
| 對輸入寬容 | 不正確的輸入格式被依賴，之後無法收緊 | 接受字串型別的數量欄位，五年後有十萬筆整合在送字串 | 從第一天嚴格驗證；需要放寬時再放寬 |
| 只看自己的測試 | 提供者的測試全過，consumer 照樣壞 | 阿凱的單元測試只驗證欄位，沒有任何 consumer 的期待 | Consumer-driven contract test、雙軌比對、小比例 rollout |
| 依賴盤點只做內部 code search | 看不到外部使用者與舊版 client | 外部賣家腳本與手機上的舊版 app 都不在 repository 裡 | 加上存取日誌、API key 統計、主動聯絡大使用者 |

## 5.10 AI 時代：什麼變了？

AI 在三個方向改變了 Hyrum’s Law 的樣貌。

**第一，coding agent 會加速隱性依賴的擴散。** Coding agent 寫程式時，很大程度上是從 codebase 裡既有的呼叫方式學習。如果 Harbor 的 repository 中有三個地方用文字比對錯誤訊息，agent 很可能寫出第四個，因為這在它的上下文裡就是「這個團隊的做法」。過去一個壞模式要靠人慢慢複製，現在可能在一個下午的 agent 工作中出現十次。對策是讓正確的契約成為 agent 容易取得的資訊：機器可讀的 schema、明確的錯誤碼列舉、在專案的 agent 指示文件中寫明「錯誤判斷一律使用 `code`」，並用 lint 規則擋下文字比對錯誤訊息的寫法（第 15 章）。

**第二，LLM 本身是一個高度不確定的提供者。** Harbor 正在試做的 AI 客服原型，會呼叫模型產生回答，再由程式從回答中擷取「要不要發起退款」。如果擷取邏輯依賴模型「習慣」用某種格式回答，例如總是在最後一行寫「建議：退款」，那就是對模型行為的事實上依賴。模型供應商更新版本、調整預設參數，甚至只是同一個模型的隨機性，都可能讓格式改變。實務做法是：要求結構化輸出並用 schema 驗證，驗證失敗就走明確的失敗路徑；鎖定模型版本，把升級當成需要驗證的變更；用一組固定的 eval 案例（評估測試集）當作對模型行為的契約測試，每次換模型或改 prompt 都先跑過。

**第三，AI agent 也是 API 的使用者。** 當 AI 客服 agent 透過工具呼叫 Harbor 的訂單 API，它讀的不只是欄位值，還有欄位名稱、說明文字與錯誤訊息，並據此決定下一步。把錯誤訊息從「訂單不存在」改成「查無此訂單，請確認編號」，對人類是改善，卻可能改變 agent 的行為：它也許開始反覆要求使用者重新輸入。這代表給 agent 用的工具介面，其文字描述也屬於可觀察行為，修改時應該跑 agent 的 eval，觀察行為是否改變。

AI 也是管理隱性依賴的好幫手，前提是人類保留判斷：

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 搜尋 codebase 中解析錯誤訊息、依賴回應順序、寫死延遲數字（如 `sleep(0.3)`）的位置，列出候選清單 | AI 的搜尋結果只是候選；外部使用者與舊版 client 不在 repository 裡，必須用存取日誌與聯絡補上 |
| 比較新舊版本的 response（雙軌比對的差異），歸納差異類型並估計受影響的呼叫者 | 某個行為該保留、遷移還是直接改，涉及使用者關係與成本，由 API owner 決定 |
| 為每個已知 consumer 草擬 contract test，或替錯誤處理改寫成使用 `code` 的版本 | 不能因為測試失敗就讓 agent 擴大公開契約或改測試期望值；先判斷測試鎖住的是契約還是實作細節 |
| 從 diff 草擬 changelog 中的「行為變更」段落，包括順序、訊息、延遲等非欄位變更 | Changelog 與遷移公告由人確認後發布；涉及外部客戶的通知需要產品或業務參與 |
| 對 LLM 輸出執行 schema 驗證與 eval，偵測模型或 prompt 變更造成的格式漂移 | 模型版本升級、prompt 修改要像程式碼變更一樣經過 review 與漸進 rollout |

> [!ai] AI 提醒
> 請 agent「讓測試通過」時要特別小心 Hyrum’s Law。如果一個 consumer 的測試因為新版本的行為改變而失敗，agent 最快的解法可能是把舊行為加回去（擴大事實上的契約），或是把測試的期望值改掉（忽略真實使用者的依賴）。這兩種都可能是錯的。要求 agent 先說明失敗的原因屬於哪一層契約，再由人決定方向。

## 5.11 專家怎麼想

- **「這個行為有誰看得到？」** 資深工程師看到一個改動，第一個問題不是「有沒有改 API」，而是「有沒有改任何外面看得到的東西」：順序、文字、延遲、副作用。能列出這張清單，就已經避開大部分的意外。
- **預設會有人依賴，然後找證據推翻。** 與其假設「應該沒人用這個」，不如假設有人用，再用日誌與搜尋證明沒有。前者出錯的代價是事故，後者出錯的代價只是多花一點調查時間。
- **新介面先窄後寬。** 加東西容易，拿掉東西極難。新 API 只暴露確定需要的欄位、只接受嚴格的輸入；之後依需求擴充。每一個「順手多回傳」的欄位，都可能是十年的維護承諾。
- **區分「我能改所有使用者」和「我不能」。** 在同一個 repository、能用大規模變更一起修改的內部 API，可以積極演進；公開 API、SDK、手機 app 要用版本與淘汰流程。用錯策略，前者會綁手綁腳，後者會不斷出事。
- **讓錯誤的依賴在最便宜的地方失敗。** 隨機化、嚴格驗證、contract test 都是同一個想法：與其在 production 被使用者發現，不如在開發者寫下那行程式的當天就讓它失敗。

## 5.12 動手練習

1. 選一個你熟悉的 API（公司內的或公開的，例如某個 REST API），列出至少 10 個可觀察行為，標示它屬於宣告的契約、事實上的契約還是實作細節，並說明判斷依據。
2. 延伸 5.8 的程式：替 reserve API 加一個 v3，回傳的 `items` 改為物件（`{"sku": "S-1", "reserved": 2}`）而不是字串，再寫兩個新 consumer：一個只讀 `sku` 欄位、一個把整個 item 當字串印出。執行相容性矩陣，觀察哪些 consumer 壞了。
3. 修改 `flaky_rate`，把三個元素改成 2、5、10 個，計算失敗比例並解釋為什麼會接近 `1 − 1/n`。
4. 為 Harbor 的訂單查詢 API 設計一個錯誤格式，至少包含 5 種錯誤碼，每種註明是否可重試，並寫下哪些欄位屬於契約、哪些可以自由修改。
5. 在你的專案中搜尋三種脆弱模式：用字串比對 exception 訊息、對無序集合取第一個元素、用固定的 `sleep` 等待非同步結果。記錄找到的位置，並判斷哪些是真正的風險。
6. 假設你要把 Harbor 的訂單 ID 從遞增整數改成隨機字串。依 5.6 節的五個步驟寫一份一頁的遷移計畫，包括如何找出依賴「ID 遞增」的使用者。

## 本章重點整理

- Hyrum’s Law：當 API 的使用者夠多時，契約承諾了什麼已不重要，系統所有可觀察行為都會被某人依賴。
- 契約可分為三層：宣告的契約、事實上的契約與實作細節；中間那層的界線由使用者的實際依賴決定，而不是作者。
- 單一使用者依賴某個細節的機率很低，但使用者數量增加時，「沒有人依賴」幾乎不可能。
- 常見的隱性契約包括順序、錯誤訊息與錯誤形狀、timing 與效能、格式細節、預設值與限制、副作用，甚至 bug 本身。
- 變快也可能是 breaking change：效能改變會暴露 race condition 或改變下游負載。
- 時間與規模會放大 Hyrum’s Law；能否看到並修改所有使用者，決定了內部 API 與公開 API 不同的演進策略。
- 設計防禦包括縮小可觀察面、使用不透明識別碼、把重要行為寫成明確契約、主動隨機化未承諾的行為。
- 把給程式判斷的資訊（錯誤碼、retryable）與給人閱讀的資訊（訊息文字）分開，讓文字可以自由改善。
- 對輸入從第一天就嚴格驗證；一開始寬鬆之後再收緊，幾乎一定會弄壞某些使用者。
- 安全改變可觀察行為的流程是：盤點使用者、分類行為、選擇策略、漸進改變、收尾並防止再依賴。
- 「保留並寫進契約」「遷移後再改」「直接改並通知」都是合理選項，取決於依賴的廣度、合理性與成本。
- SemVer 依宣告的契約溝通變更意圖，是有用但有損的相容性估計；使用者夠多時，幾乎任何變更都是某人的 breaking change。
- Coding agent 會從既有程式學習，可能加速隱性依賴擴散；正確的契約要讓 agent 容易取得，並以 lint 與測試把關。
- LLM 輸出與 agent 的工具介面都是新型態的可觀察行為，需要結構化輸出、版本鎖定與 eval 作為契約測試。

## 延伸問答

> [!question]- Q1. Hyrum’s Law 和「使用者不應該依賴未文件化的行為」這句話衝突嗎？
> 不衝突，它們在回答不同的問題。「使用者不應該依賴未文件化的行為」是一條規範，告訴使用者該怎麼做才能減少自己升級時的風險；Hyrum’s Law 是一個觀察，描述當使用者夠多時實際會發生什麼。規範是對的，但總有一部分使用者沒讀文件、從範例複製、或在不知情的情況下依賴了某個行為。
>
> 作為 API 提供者，你不能只依靠規範。即使在道理上責任在使用者，事故發生時你還是要處理，尤其當依賴者是重要客戶或公司內的其他團隊。所以兩者要一起用：用文件與規範降低依賴發生的機率，用隨機化、嚴格驗證與 contract test 讓違反規範的依賴提早失敗，再用盤點與漸進 rollout 處理已經存在的依賴。

> [!question]- Q2. 為什麼把 API 變快也可能是 breaking change？請舉兩個不同機制的例子。
> 第一個機制是暴露隱藏的 race condition。本章 Harbor 的例子中，checkout 在 reserve 成功後立刻讀 replica；以前 reserve 要 300 毫秒，replica 有足夠時間追上，現在 40 毫秒就回來，checkout 讀到舊資料。Checkout 的程式一直有 bug，只是被「reserve 夠慢」掩蓋了，提供者的效能改善讓它浮現。
>
> 第二個機制是改變下游負載。如果呼叫者用迴圈不斷輪詢某個狀態，API 變快之後，同樣的迴圈每秒會送出更多請求；或者一個上游服務因為呼叫你變快，處理量變大，進而對它的其他下游送出更多流量。原本被你的延遲「限速」的系統，突然要承受新的負載。這兩個例子都說明 timing 是可觀察行為，效能變更也要經過漸進 rollout 並觀察整條鏈路的指標。

> [!question]- Q3. 你是 inventory 的 owner，發現有一位重要賣家依賴回應的順序，而你正想改成批次查詢。你會怎麼決定要保留、遷移還是直接改？
> 先把問題拆成三個面向。第一是依賴的廣度：只有這位賣家，還是內部也有很多呼叫者依賴？可以用 code search 與存取日誌找證據。第二是依賴的合理性：「結果有固定順序」是一個合理的需求，很多使用者會想要；第三是成本：在批次查詢後加一次排序，成本通常極低。
>
> 以這個情況來說，最划算的選擇很可能是「保留並升格為契約」：在文件中正式承諾依 SKU 排序，並加上測試保證。這樣賣家不用改程式，你也不用維護兩套行為，未來的使用者也能安心依賴。如果排序成本很高（例如結果有數萬筆），才考慮「遷移後再改」：提供一個 `sort` 參數，通知賣家改用，給一段遷移期後再移除預設排序。直接改並通知只適合依賴不合理或影響很小的情況，這裡兩者都不成立。

> [!question]- Q4. 錯誤碼也是一種契約，那新增一個錯誤碼算不算 breaking change？
> 可能算，取決於使用者如何處理未知的錯誤碼。如果使用者的程式寫成「`code` 是 A 就做 X，是 B 就做 Y，其他一律當作未知錯誤顯示給使用者」，新增錯誤碼 C 不會讓它崩潰，只是 C 的情況會被當成未知錯誤處理。但如果使用者用一個窮舉的 switch 並在遇到未知值時拋出例外，或把錯誤碼轉成固定的列舉型別而無法表示新值，新增錯誤碼就會讓程式崩潰。
>
> 所以實務上有兩件事要做。在設計契約時，明確寫出「未來可能新增錯誤碼，使用者必須能處理未知的值」，並在 SDK 中提供預設的處理方式。在新增錯誤碼時，把它當成需要溝通的變更：寫進 changelog，考慮先讓新錯誤碼在一段時間內對應到某個既有錯誤碼的行為。這和 TLS 的 GREASE 是同一個想法：讓使用者從第一天就必須正確處理「不認識的值」。

> [!question]- Q5. SemVer 規定不相容變更要升 major version。既然有 Hyrum’s Law，是不是每次變更都該升 major？
> 不應該。如果每次變更都升 major，版本號就失去溝通價值：使用者無法從版本號分辨「真的改了契約」和「理論上可能影響某些人」，結果就是大家都不敢升級，或乾脆忽略版本號。SemVer 的意義在於表達提供者依照宣告的契約所做的判斷，這個判斷雖然有損，仍然是有用的訊號。
>
> 比較好的做法是讓版本號照宣告的契約走，同時用其他方式補上 Hyrum’s Law 帶來的風險。提供者在 changelog 中寫出可能影響使用者的行為變更；使用者用 lock file 固定版本，升級時跑自己的測試，對自己依賴的非契約行為寫測試鎖住；組織層面盡可能在 CI 中讓提供者的新版本與使用者的程式相遇。第 20 章會說明「live at head」這種以持續測試取代對版本號過度信任的模型。

> [!question]- Q6. 「對輸入寬容」不是可以讓系統更健壯嗎？為什麼本章建議一開始就嚴格？
> 對輸入寬容在短期內確實減少錯誤，讓不同實作更容易互通，這是 Postel’s law 在早期網際網路受歡迎的原因。問題在於長期效果：每一種被默默接受的「不標準」輸入，都會被某些使用者開始使用，最後變成事實上的契約。等到你想換一個解析器、改成更嚴格的驗證，或把服務改寫成另一種語言時，就必須逐一重現所有寬容的行為，否則某些使用者會壞掉。
>
> 一開始嚴格，使用者在整合的當下就看到清楚的錯誤並修正，成本最低。之後如果確實有需求要放寬（例如接受新的日期格式），放寬是相容的變更，不會弄壞任何人。反過來從寬鬆收緊，幾乎一定是 breaking change。所以嚴格驗證不是不友善，而是把成本放在最便宜的時間點。友善可以透過清楚的錯誤訊息與文件來實現。

> [!question]- Q7. Harbor 試做中的 AI 客服原型用程式從模型回答中擷取「是否退款」。模型供應商宣布會升級預設模型版本。你會先做什麼？
> 先確認自己對模型行為有哪些依賴，這是 Hyrum’s Law 在 LLM 上的版本。檢查擷取邏輯是否依賴特定的措辭或格式（例如最後一行一定是「建議：退款」），是否依賴回答長度、語氣或某些關鍵字。這些都是模型的可觀察行為，沒有人承諾過它們不會變。
>
> 接著採取三個行動。第一，如果可以，先鎖定目前的模型版本，不讓升級自動生效，把升級變成一個需要驗證的變更。第二，把輸出改成結構化格式（例如要求模型輸出符合 JSON schema 的 `{"action": "refund" | "none", "reason": ...}`），並在程式中驗證，驗證失敗就轉人工，而不是猜。第三，用一組代表性的對話建立 eval 測試集，包含應該退款、不應該退款與模稜兩可的案例，新模型必須通過 eval 才能以小比例 rollout。退款涉及金錢，任何格式漂移造成的誤判都比一般 bug 嚴重。

> [!question]- Q8. 面試題：如果你要設計一個會被數百個外部開發者使用的新 API，會在第一版就做哪些事來應對 Hyrum’s Law？
> 一個完整的回答可以分成三組。第一組是縮小可觀察面：只回傳確定需要的欄位；ID 與分頁使用不透明 token，避免使用者從格式推論資訊；不在 response 中暴露內部狀態與除錯資訊。第二組是明確契約：用 OpenAPI 或 protobuf 定義 schema；錯誤使用穩定的錯誤碼並標示是否可重試，訊息文字明確標示為給人看；文件寫清楚哪些行為不保證（例如順序），以及使用者必須能處理未知的欄位與錯誤碼；輸入從第一天就嚴格驗證。
>
> 第三組是為未來的改變做準備：從第一版就規劃版本化方式；在 SDK、範例與 sandbox 環境中主動打亂未承諾的順序；記錄每個 API key 的呼叫模式，讓未來改變時能盤點使用者；建立 changelog 與淘汰政策。回答時可以補一句：這些做法無法讓依賴消失，只能讓依賴集中在你願意承諾的地方，並讓錯誤的依賴盡早失敗。這會讓面試官知道你理解 Hyrum’s Law 是被管理的，而不是被解決的。
