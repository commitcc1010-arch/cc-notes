## 32.1 故事：每台機器都是綠燈，使用者卻結不了帳

Harbor 成立第三年的一個週五晚上，客服群組突然湧進大量訊息：「付款一直轉圈」「刷卡失敗三次了」。值班的 SRE 志明打開監控儀表板，畫面上一片綠色：checkout 服務的 24 台機器全部在線，CPU 使用率 40%，記憶體正常，health check 全數通過。

志明花了二十分鐘才找到原因：外部金流商的 API 開始對約三成的請求回傳錯誤，而 checkout 服務把這些錯誤包裝成「付款處理中」回給使用者。從機器的角度看，一切正常；從使用者的角度看，Harbor 已經壞了三十分鐘。

事後檢討會上，產品經理 Lisa 問了一個所有人都答不出來的問題：「我們上個月到底算不算穩定？」開發團隊說他們的服務 uptime 是 99.99%；客服說投訴量是上季的兩倍；工程經理 Kevin 只知道這個月有三次事故。每個人手上都有數字，但沒有一個數字回答了 Lisa 的問題。

更麻煩的是接下來的決策。下週要上線新的折價券功能，開發團隊想照原計畫發布，SRE 團隊認為應該先修好錯誤處理。雙方都有道理，卻沒有共同的尺度可以判斷誰該讓步。

這一章要建立的，就是這把共同的尺子：用使用者的角度定義「好」（SLI），訂出一個合理的目標（SLO），再把「允許不完美的空間」（error budget）變成團隊共同遵守的決策規則。

## 32.2 為什麼「可靠」必須被定義

直覺上，服務當然越可靠越好，最好是 100%。但 SRE 的第一個核心觀念正好相反：**100% 幾乎永遠是錯的目標**。

第一個理由是使用者根本感受不到。Harbor 的使用者透過手機網路、家用 Wi-Fi、瀏覽器與作業系統連到 Harbor，這條路徑上的每一段本身就不是 100% 可靠。如果使用者自己的網路每個月有幾個小時不穩，Harbor 從 99.99% 提升到 99.999% 的差別，對他們來說幾乎不可察覺。

第二個理由是成本。可靠性的成本曲線不是線性的，而是越往上越陡。從 99% 到 99.9%，可能只需要加上 health check 與自動重啟；從 99.9% 到 99.99%，可能需要多區域部署、自動 failover、更嚴格的變更流程；再往上一個 9，往往需要多個獨立的資料中心、每個元件都有備援，以及幾乎凍結的發布節奏。每多一個 9，工程與營運成本可能翻好幾倍。

第三個理由最重要：**追求完美可靠會殺死變更**。大部分的事故來自變更：新版本、設定修改、資料遷移。一個團隊若不允許任何失敗，唯一的方法就是停止改變，而停止改變也意味著停止提供新功能、停止修補安全漏洞。

所以真正的問題不是「要不要可靠」，而是「**要多可靠才夠**」。這個答案必須明確寫下來，否則每個人都會用自己的標準判斷：開發者看 server uptime，使用者看交易成功，主管看投訴數。SRE 用三個名詞把這件事結構化：

| 名詞 | 是什麼 | 誰決定 | Harbor 的例子 |
|---|---|---|---|
| **SLI**（Service Level Indicator，服務水準指標） | 量測服務品質的指標，通常是一個比例 | 工程團隊定義量法 | 成功完成的 checkout ÷ 所有有效的 checkout 嘗試 |
| **SLO**（Service Level Objective，服務水準目標） | SLI 在一段時間內要達到的目標 | 產品與工程共同決定 | 30 天內 99.9% 的 checkout 嘗試成功 |
| **SLA**（Service Level Agreement，服務水準協議） | 對客戶的正式承諾，違反時有後果（例如退費） | 業務、法務與產品 | 對企業賣家承諾每月 99.5%，未達成則退還部分月費 |

三者的關係是：SLI 是量出來的事實，SLO 是內部的目標，SLA 是對外的合約。接下來依序把它們拆開。

## 32.3 SLI：從使用者的角度量測

### 好的 SLI 長什麼樣子

**SLI** 最常見的形式是一個比例：

```text
SLI = good events / valid events
```

**Valid events**（有效事件）是「服務有機會表現好或壞」的事件，例如一次 checkout 嘗試。**Good events**（好事件）是其中結果對使用者而言夠好的部分，例如成功完成付款且在 2 秒內回應。比例的好處是容易理解（0% 到 100%）、可以跨服務比較，而且直接對應到後面的 error budget。

SLI 要回答的是「使用者是否得到了想要的東西」，而不是「機器是否健康」。CPU 使用率、記憶體、process 是否在跑，都是 **診斷訊號**：它們幫助你找出問題在哪裡，但它們本身不代表使用者的體驗。Harbor 的週五事故正好說明了差別：24 台機器都健康，使用者卻在失敗。

### 從使用者旅程開始

找 SLI 的起點是 **CUJ**（Critical User Journey，關鍵使用者旅程）：使用者為了完成一件重要的事而經過的一連串步驟。Harbor 的幾個 CUJ：

| CUJ | 使用者在意什麼 | 候選 SLI |
|---|---|---|
| 搜尋商品 | 有結果、夠快 | 回應在 500 ms 內且非錯誤的搜尋請求比例 |
| 結帳付款 | 成功、不重複扣款 | 成功完成付款的 checkout 比例 |
| 賣家上架商品 | 上架後很快能被搜尋到 | 上架後 10 分鐘內可被搜尋到的商品比例 |
| 收到出貨通知 | 通知有送達、不延遲 | 出貨後 5 分鐘內送出通知的比例 |

注意 SLI 的種類不只一種。常見的有：

- **Availability**（可用性）：請求是否成功。
- **Latency**（延遲）：請求是否夠快。
- **Freshness**（新鮮度）：資料是否夠新，例如搜尋索引落後多久。
- **Correctness**（正確性）：結果是否正確，例如庫存數字與實際一致。
- **Throughput**（吞吐量）：批次系統每小時能處理多少資料。
- **Durability**（耐久性）：寫入的資料能否在之後被讀回。

一個 CUJ 通常只需要 1–3 個 SLI。數十個 SLI 不會讓服務更可靠，只會讓沒有人知道該看哪一個。

### 分母比分子更難

新手常把注意力放在「什麼算成功」，但真正難的是**分母：什麼算一次有效的機會**。以 Harbor 的 checkout 為例，下面每一種情況都要決定是否計入：

- 使用者輸入了過期的信用卡，金流商回傳「卡片無效」。這是使用者的問題，通常不算服務失敗，應從分母排除或算成 good。
- 惡意爬蟲每秒送一千個假的 checkout 請求，全部被 rate limit 擋下。如果算進分母，SLI 會被大量「被擋下的請求」扭曲。
- 使用者按下付款後立刻關閉 app，請求被取消。
- 健康檢查與內部測試流量。
- 服務回傳 HTTP 200，但內容是「系統繁忙，請稍後再試」的錯誤頁。這是最危險的情況：看起來成功，實際失敗。Harbor 週五事故中的「付款處理中」就是這種。

規則是：**分母的排除條件要明確寫下來，而且越少越好**。排除得太寬，真正的服務錯誤會被歸類成「使用者的錯」；排除得太窄，SLI 會被不受你控制的雜訊淹沒。排除規則本身也要版本化：改了規則，歷史數字就不能直接和新數字比較。

### 在哪裡量：measurement point

同一個 SLI 在不同位置量，會得到不同的數字：

```text
使用者手機 ─①─ 網際網路 ─②─ CDN／Load Balancer ─③─ checkout server ─④─ payments
   │                           │                      │
 client 端量測               LB 日誌                server 日誌
（最接近真實體驗）        （涵蓋 server 當機）     （最容易取得）
```

① **Client 端量測**（例如 app 回報或 RUM，Real User Monitoring）最接近使用者的真實感受，但會混入使用者自己網路的問題，資料也有延遲與遺失。

② **Load balancer 日誌**能看到 server 完全當機時的錯誤（server 自己死了就不會寫日誌），是很多團隊的預設選擇。

③ **Server 日誌**最容易取得、最精細，但看不到「請求根本沒到 server」的失敗。

④ 往 dependency 的呼叫是診斷訊號，不是使用者 SLI。

另外還有 **synthetic monitoring**（合成監控，也叫 probe）：定期由程式模擬使用者執行一次 CUJ。它在低流量時特別有用，因為不管有沒有真實使用者，都能持續產生事件。

實務上，Harbor 選擇以 load balancer 日誌作為 availability SLI 的主要來源，並用 synthetic probe 與 client 端資料作為交叉驗證。原則是：**選最接近使用者、又能可靠取得的那一點**。

## 32.4 Latency SLI：為什麼平均值會騙人

延遲是第二重要的 SLI，也是最容易量錯的。假設 Harbor 的搜尋服務在一分鐘內處理了 1,000 個請求：980 個花了 100 ms，20 個卡了 10 秒。平均延遲是：

```text
(980 × 0.1 秒 + 20 × 10 秒) / 1000 = 0.298 秒
```

平均約 300 ms 看起來還可以接受，但有 2% 的使用者等了 10 秒，這些人很可能已經離開了。平均值把少數極差的體驗稀釋掉，而這些極差的體驗正是使用者最在意的。

### 百分位數

**百分位數**（percentile）解決了這個問題。**p50**（中位數）是一半請求比它快、一半比它慢的值；**p99** 是 99% 請求比它快的值。上例中 p50 是 100 ms，p99 是 10 秒（最慢的 2% 都是 10 秒，第 99 百分位落在其中），一眼就能看出尾端的問題。

延遲的尾端特別重要，因為現代服務的一個頁面常常呼叫數十個後端。如果一個頁面要呼叫 20 個服務，每個服務都有 1% 的機率很慢，那麼這個頁面至少碰到一次慢回應的機率是：

```text
1 − 0.99^20 ≈ 18%
```

每個後端的 p99，會變成使用者端將近五分之一的體驗。這就是為什麼大型系統關心 p99 甚至 p99.9。

### 把延遲變成「好事件」

百分位數適合看圖，但要算 error budget，最好把延遲也轉成 good／valid 的比例。做法是訂一個門檻：

```text
latency SLI = 回應時間 ≤ 500 ms 的請求數 / 所有有效請求數
```

這個形式比「p99 ≤ 500 ms」更好用：它可以直接相加（每分鐘的 good 與 valid 加總就是一小時的），不像百分位數不能直接平均；也能和 availability 用同一套 error budget 邏輯處理。

有時一個門檻不夠描述體驗，可以設兩個：「90% 的搜尋在 200 ms 內」與「99% 的搜尋在 1 秒內」。前者保證一般體驗，後者防止長尾惡化。

> [!warning] 常見誤解
> 「把一分鐘的 p99 平均起來就是一小時的 p99。」錯。百分位數不能平均，必須從原始分佈（或 histogram）重新計算。這也是為什麼監控系統通常儲存 histogram bucket，而不是只存百分位數。

## 32.5 SLO：目標加上時間窗

### SLO 的兩個要素

**SLO** 由兩部分組成：目標值與時間窗。「99.9%」不是 SLO，「**過去 30 天內**，99.9% 的有效 checkout 嘗試成功」才是。時間窗決定了你衡量的範圍，也決定了 error budget 有多大。

時間窗有兩種：

- **Rolling window**（滾動窗口）：永遠看「過去 30 天」。好處是平滑、對最近的事件敏感，沒有「月初重置」的效應，大多數團隊用它做工程決策。
- **Calendar window**（日曆窗口）：例如「每個自然月」。好處是容易和業務報表、SLA 對帳；缺點是月初預算全滿、月底可能已經耗盡，容易誘發「月底先別發布」這種不健康的行為。

常見做法是：SLO 與告警用 28 或 30 天 rolling window，SLA 報表用 calendar month。

### 每個「9」值多少時間

把目標換算成時間，最能讓人體會差別。以 30 天、假設失敗均勻分佈來算：

| SLO | 每 30 天可容許的「完全中斷」時間 | 每週 |
|---|---|---|
| 99% | 7.2 小時 | 約 1.7 小時 |
| 99.5% | 3.6 小時 | 約 50 分鐘 |
| 99.9% | 43.2 分鐘 | 約 10 分鐘 |
| 99.95% | 21.6 分鐘 | 約 5 分鐘 |
| 99.99% | 4.32 分鐘 | 約 1 分鐘 |

99.99% 每週只有約 1 分鐘、每月約 4 分鐘。這代表只要發生一次需要人類介入的完全中斷（收到 page、打開筆電、登入、判斷），光是反應時間就足以用掉整個月的預算，只有完全自動化的偵測與恢復才可能達成。這就是「多一個 9」在營運上的真實意義。

### 怎麼選目標

選 SLO 不是比賽誰的 9 比較多，而是回答幾個問題：

1. **使用者需要什麼？** Harbor 的搜尋偶爾慢一點，使用者會重試；結帳失敗，使用者可能去別家買。所以 checkout 的目標應比搜尋高。
2. **歷史表現如何？** 先量一段時間，看現況大約多少。目標若遠高於現況，等於一上線就違反；若遠低於現況，則沒有約束力。好的起點是「略低於過去表現的穩定水準」。
3. **依賴能支撐嗎？** 這是最常被忽略的限制，下一小節展開。
4. **代價是多少？** 每提高一個 9，要增加多少成本、放慢多少發布速度？產品是否願意付？

SLO 也不是訂了就不動。產品改變、使用者期待改變、架構改變時，都要重新檢視。SRE Workbook 建議的做法是先從一個「夠好」的 SLO 開始，運作幾個月後再根據實際數據與使用者回饋調整。

### 依賴會把目標往下拉

如果 checkout 要成功，checkout 自己、payments 和 inventory 三個服務都要成功，而它們的可用性分別是 99.95%、99.9%、99.99%，假設三者的失敗彼此獨立，整條路徑的可用性大約是三者相乘：

```text
0.9995 × 0.999 × 0.9999 ≈ 0.9984 = 99.84%
```

三個元件各自都達到 99.9% 以上，串起來卻低於 99.9%。（如果失敗常常同時發生，例如三者共用同一個資料庫，實際數字會比相乘結果高一些；相乘是「各自獨立壞掉」時的估計。）結論是：**一個服務的 SLO 一般不應比它的關鍵依賴串聯起來的結果更嚴格**，除非它有降級或備援機制。例如 inventory 暫時不可用時，Harbor 可以先接受訂單、之後再確認庫存；這種設計讓 inventory 不再是 checkout 的「硬依賴」，checkout 的可用性也就不再被它拉低。

反過來，如果你的服務被很多人依賴，你的 SLO 也會影響他們能承諾什麼。這是 SLO 在組織內的價值：它讓依賴關係中的期望變得明確。

### SLO 與 SLA 的距離

**SLA** 是對外的合約承諾，違反時要付出代價，例如 service credit（退還部分費用）。因為它有法律與財務後果，通常由業務與法務參與訂定。

關鍵原則是：**內部 SLO 要比 SLA 嚴格**。如果 Harbor 對企業賣家承諾 99.5%，內部 SLO 就應該訂在 99.9% 左右。兩者之間的差距是緩衝：當 SLI 跌破 SLO 時，團隊還有時間在違反 SLA 之前修好問題。如果 SLO 和 SLA 一樣，第一次知道有問題的時候就已經要賠錢了。

並不是每個服務都需要 SLA。內部服務、免費產品通常只有 SLO。

## 32.6 Error Budget：把「允許的不完美」變成決策規則

### 定義

一旦有了 SLO，就自然得到 **error budget**（錯誤預算）：

```text
error budget = 1 − SLO
允許的壞事件數 = valid events × (1 − SLO)
```

99.9% 的 SLO 代表允許 0.1% 的事件是壞的。第 3 年的 Harbor，checkout 平日大約每分鐘 600 次結帳嘗試，30 天約 2,600 萬次有效嘗試，error budget 就是 26,000 次失敗。

Error budget 的力量在於把「穩定 vs 速度」這個永遠吵不完的問題，變成一個可以量測的資源。預算還很多，代表團隊可以承擔更多風險：更快發布、做實驗、進行有風險的遷移。預算快用完，代表要放慢、把力氣花在可靠性上。開發團隊與 SRE 團隊從此有了共同目標：不是「SRE 擋發布」，而是「大家一起管理同一筆預算」。

> [!warning] 常見誤解
> Error budget 不是「每個月一定要用完的額度」，也不是「可以故意製造失敗」。它的意思是：既然完美可靠的代價不值得付，我們接受這麼多的不可靠，並且用它來換取變更速度。若預算長期都用不到，可能代表 SLO 太寬，或團隊太保守，兩者都值得檢討。

### 消耗速度比剩餘量更重要

只看「還剩多少」不夠，還要看「用得多快」。如果 30 天的窗口才過了 12 天，就已經用掉 67% 的預算，照這個速度在第 18 天左右就會用完。衡量消耗速度的概念叫 **burn rate**（燃燒率）：

```text
burn rate = 實際錯誤率 / SLO 允許的錯誤率
```

Burn rate 等於 1，代表剛好在窗口結束時用完預算；等於 10，代表 3 天就會用完 30 天的預算。第 34 章會用 burn rate 設計告警，這裡先記住它的意義。

### Error budget policy

光算出數字不會改變任何事。真正讓 error budget 發揮作用的是 **error budget policy**：一份事先寫好、由產品、開發、SRE 主管共同簽署的規則，說明預算在不同狀態下團隊要做什麼。Harbor 的版本節錄如下：

```text
Harbor Checkout Error Budget Policy（v3，2025-09）
適用：checkout 服務，SLO = 30 天 rolling，99.9% availability、99% latency ≤ 2 s

1. 預算健康（預算尚未耗盡，且未觸發第 2 條）
   → 正常發布，可進行有風險的實驗與遷移。
2. 消耗過快（某週 burn rate > 2，或單一事故用掉 > 20% 預算）
   → 該事故必須完成 postmortem；下一次發布須通過 canary 分析。
3. 預算耗盡（30 天內用完）
   → 暫停非緊急功能發布，直到 SLI 回到 SLO 以上；
     安全修補、可靠性修復與資料修正不受限制；
     至少一位開發工程師加入可靠性工作，直到 postmortem 的 P0 action items 完成。
4. 例外
   → 重大業務需求（例如雙十一前的必要功能）可由 VP of Engineering 書面核准例外，
     並記錄於 policy 附錄。
5. 外部因素
   → 若預算主要因上游雲端供應商事故耗盡，仍適用第 3 條的發布暫停，
     但 action items 改為提升對該依賴的容錯能力。
```

這份 policy 有幾個值得注意的設計：它是事先同意的，所以事故發生時不需要臨時吵架；它不只「懲罰」開發，也要求可靠性投資；它有明確的例外流程，而不是假裝不會有例外；它處理了「不是我們的錯」的情況，因為使用者不在乎是誰的錯。

## 32.7 不典型的服務：低流量、批次、資料與多租戶

上面的方法對「大量、連續的請求」最好用。其他類型的服務需要調整。

**低流量服務**。如果一個管理後台每天只有 100 個請求，一次失敗就是 1%，SLI 會劇烈跳動，告警也會非常吵。對策包括：拉長時間窗、加上 synthetic probe 產生穩定的事件流、把多個相關的低流量服務合併成一個 SLO，或改用 time-based SLI（「每 5 分鐘一次 probe 都成功的時間比例」）。

**批次與資料管線**。夜間對帳工作沒有「請求」，比較合適的 SLI 是 freshness（「資料延遲小於 2 小時的時間比例」）、correctness（「對帳結果與金流商一致的比例」）或 completion（「在早上 6 點前完成的工作比例」）。第 42 章會展開資料管線的可靠性。

**多租戶服務**。Harbor 的賣家後台服務上萬個賣家。整體 SLI 99.9% 可能掩蓋「某個大賣家 100% 失敗」的情況。對策是另外觀察各租戶或各區域的 SLI 分佈，並對重要客戶設定個別目標。

**Time-based vs event-based**。Event-based SLI（壞請求數／總請求數）反映的是實際受影響的使用者比例；time-based SLI（服務「正常」的分鐘數／總分鐘數）比較直觀，但一分鐘內 1% 失敗與 100% 失敗會被同等看待（取決於「正常」的判斷門檻）。高流量服務通常用 event-based，低流量或內部服務用 time-based 比較穩定。

## 32.8 把 SLO 落地：文件、儀表板與檢討節奏

前面講的是「SLO 是什麼」，這一節講「一個團隊怎麼真的開始用」。很多組織訂了 SLO 卻沒有效果，原因通常不是數學錯了，而是缺少三樣東西：一份有 owner 的文件、一個大家會看的儀表板，以及固定的檢討節奏。

### SLO 文件

每個 SLO 都應該有一份短文件，放在服務的 repository 或 wiki 中，和程式碼一樣接受 review。Harbor 的 checkout SLO 文件包含以下欄位：

| 欄位 | 內容範例 | 為什麼需要 |
|---|---|---|
| 服務與 owner | checkout；owner：checkout 團隊（tech lead：美華） | 數字掉下來時知道找誰 |
| CUJ | 使用者從購物車按下付款，到看到「訂單成立」 | 讓 SLI 有可追溯的使用者意義 |
| SLI 定義 | good：LB 記錄的 POST /checkout 回應為 2xx 且 body 的 status 為 `confirmed`；valid：所有 POST /checkout，排除 rate limit 擋下的請求與卡片驗證失敗 | 精確到可以寫成查詢，避免各自解讀 |
| 量測來源 | Load balancer 日誌，synthetic probe 每分鐘交叉驗證 | 記錄量測點的盲區 |
| 目標與時間窗 | 99.9%，30 天 rolling | 決定 error budget 大小 |
| 理由 | 過去 6 個月穩定在 99.93%–99.97%；金流商 SLA 為 99.95% | 讓後來的人知道為何是這個數字 |
| Error budget policy | 連結到 policy 文件 | 數字與行動綁在一起 |
| 變更紀錄 | v1：2025-04；v2：2025-08 排除 rate limit 請求 | 歷史數據比較時知道定義變過 |
| 下次檢討日期 | 2025-12-01 | 避免 SLO 被遺忘 |

「理由」與「變更紀錄」是最常被省略、卻最有價值的兩欄。半年後有人想把目標改成 99.95% 時，需要知道當初為什麼訂 99.9%；分析一年的趨勢時，需要知道哪個月改過分母。

### 儀表板只放會用到的東西

SLO 儀表板的第一屏應該只回答三個問題：現在的 SLI 是多少、error budget 還剩多少、消耗速度是否異常。其他的 CPU、記憶體、各 endpoint 的細節放在下層的診斷儀表板。把兩者混在一起，是值班者在事故中找不到重點的主要原因之一（第 33 章會詳談儀表板設計）。

Harbor 的 SLO 儀表板第一屏只有四張圖：30 天 SLI 趨勢與目標線、剩餘 error budget 百分比、1 小時與 6 小時的 burn rate，以及最近 7 天的發布紀錄。最後一張圖很重要：預算突然下降時，第一個問題通常是「那時候發布了什麼」。

### 檢討節奏

SLO 不是設定一次就好。Harbor 採用的節奏是：

- **每週**：服務團隊在週會花 5 分鐘看 error budget。預算正常就跳過；消耗過快就決定本週的可靠性工作。
- **每次重大事故後**：postmortem 必須回答「這次事故有沒有被 SLI 捕捉到？用掉多少預算？」（第 45 章）。
- **每季**：產品、開發、SRE 一起檢視 SLO 是否仍代表使用者的體驗：投訴與 SLI 是否一致、目標是否太鬆或太緊、依賴是否改變。

導入初期最常見的錯誤，是一次替所有服務訂 SLO。比較好的方式是先挑一個重要、團隊願意合作的服務，跑完一整輪「定義 → 量測 → 違反 → 依 policy 行動 → 檢討」，讓組織看到它真的改變了決策，再推廣到其他服務。

## 32.9 動手寫：error budget 計算器

下面的程式把本章的幾個公式串起來：九的換算、error budget 消耗、policy 判斷，以及依賴的可用性相乘。

```python
from dataclasses import dataclass


@dataclass
class Window:
    valid: int       # 窗口開始到現在的有效請求數（分母）
    good: int        # 窗口開始到現在符合「好」定義的請求數（分子）


def nines_table(targets, days=30):
    minutes = days * 24 * 60
    for t in targets:
        allowed = minutes * (1 - t)
        print(f"SLO {t:.2%}  → 每 {days} 天可容許 {allowed:8.2f} 分鐘完全中斷")


def budget_report(w: Window, target: float, expected_valid: int):
    sli = w.good / w.valid
    allowed_bad = expected_valid * (1 - target)    # 整個窗口的預算：用預估的窗口總流量計算
    bad = w.valid - w.good
    consumed = bad / allowed_bad
    burn_rate = (bad / w.valid) / (1 - target)     # 實際錯誤率 ÷ 允許的錯誤率
    print(f"至今 SLI = {w.good:,} / {w.valid:,} = {sli:.4%}")
    print(f"整個窗口允許的壞請求 = {allowed_bad:,.0f}，至今實際 = {bad:,}，已用 {consumed:.0%} 的 error budget")
    print(f"至今的平均 burn rate = {burn_rate:.2f}")
    return consumed


def policy(consumed: float, days_elapsed: int, window_days: int = 30) -> str:
    expected = days_elapsed / window_days          # 照「均勻消耗」此時應該用掉的比例
    if consumed >= 1:                              # 門檻是簡化示範，真實 policy 依團隊約定
        return "預算耗盡：凍結非緊急發布，可靠性工作優先"
    if consumed > expected * 1.5:
        return "消耗過快：放慢 rollout，檢討最近的變更"
    return "正常：照常發布"


def chain(*availabilities: float) -> float:
    total = 1.0
    for a in availabilities:
        total *= a
    return total


nines_table([0.99, 0.999, 0.9995, 0.9999])
print()
# 30 天預估 2,600 萬次有效嘗試（每分鐘約 600 次）；第 12 天時已有 1,040 萬次，其中 17,400 次失敗
consumed = budget_report(Window(valid=10_400_000, good=10_382_600), target=0.999,
                         expected_valid=26_000_000)
print("第 12 天的判斷：", policy(consumed, days_elapsed=12))
print()
deps = chain(0.9995, 0.999, 0.9999)   # checkout 自己、payments、inventory
print(f"三個串聯元件各自達標、失敗互相獨立時，整體約 {deps:.4%}")
```

執行結果：

```text
SLO 99.00%  → 每 30 天可容許   432.00 分鐘完全中斷
SLO 99.90%  → 每 30 天可容許    43.20 分鐘完全中斷
SLO 99.95%  → 每 30 天可容許    21.60 分鐘完全中斷
SLO 99.99%  → 每 30 天可容許     4.32 分鐘完全中斷

至今 SLI = 10,382,600 / 10,400,000 = 99.8327%
整個窗口允許的壞請求 = 26,000，至今實際 = 17,400，已用 67% 的 error budget
至今的平均 burn rate = 1.67
第 12 天的判斷： 消耗過快：放慢 rollout，檢討最近的變更

三個串聯元件各自達標、失敗互相獨立時，整體約 99.8401%
```

逐段解讀：

1. `nines_table` 把目標換算成時間。這張表值得背下來，討論 SLO 時第一個問題往往是「這相當於每月可以壞幾分鐘」。
2. `budget_report` 示範兩件事。第一，整個窗口的預算要用**預估的窗口總流量**計算（2,600 萬 × 0.1% = 26,000 次），而不是用「到目前為止」的流量，否則在窗口前段算出來的預算會偏小。這裡以日曆窗口的第 12 天為例；rolling window 則永遠用「過去 30 天」的實際流量計算。第二，至今的 SLI 是 99.83%，和 99.9% 只差 0.07 個百分點，聽起來「差一點點」，換算成預算卻是 12 天就用掉三分之二。SLI 上的小差距，在預算上往往是大差距。
3. `policy` 用「實際消耗」與「均勻消耗時應有的消耗」比較。第 12 天照理應用掉 40%，實際用了 67%，超過 1.5 倍，所以判斷為消耗過快。這和程式印出的 burn rate 是同一件事：67% ÷ 40% ≈ 1.67。門檻 1.5 倍只是示範，32.6 節 Harbor policy 的條文用的是「某週 burn rate > 2」；真實系統會用多個時間窗的 burn rate 判斷，第 34 章會實作。
4. `chain` 示範依賴相乘。這裡用的是各依賴的 SLO，也就是它們「承諾的下限」；實際表現通常比承諾好，所以 checkout 過去仍能維持 99.9% 以上。但只看承諾值，checkout 的 99.9% 沒有保障：要嘛讓某些依賴變成非關鍵路徑（例如 32.5 節 inventory 的降級設計），要嘛請依賴提高它們的 SLO。

在真實系統中，`valid` 與 `good` 來自 metrics 系統（例如 Prometheus 的 counter），計算以查詢語言完成，policy 判斷則接到告警與發布系統。程式的結構不變：**定義事件 → 計算比例 → 比較目標 → 觸發事先同意的行動**。

## 32.10 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會出問題 | 具體情境 | 對策 |
|---|---|---|---|
| 用 server 健康度當 SLI | 機器健康但使用者失敗 | Harbor 週五事故：金流商回錯，server 一切正常 | 從 CUJ 出發，在 load balancer 或 client 端量使用者結果 |
| 目標訂得太高 | 成本暴增，發布被長期凍結 | 管理後台訂 99.99%，結果每次小事故都觸發 policy | 依使用者需求與依賴能力訂目標，接受不同服務有不同 SLO |
| 分母排除規則太寬 | 真正的錯誤被歸為「使用者錯」 | 把所有 4xx 都排除，連自己 bug 造成的 400 也被排除 | 逐一列出排除條件，定期抽樣檢查被排除的事件 |
| 只有一個整體 SLI | 局部嚴重問題被平均掉 | 一個國家的 CDN 壞了，全球 SLI 只降 0.3% | 依區域、平台、重要租戶分層觀察 |
| Policy 只懲罰開發 | 團隊開始規避或篡改量測 | 為了不被凍結，把錯誤改回 200 | Policy 同時要求可靠性投資，量測定義由 SRE 與開發共同維護 |
| SLO 訂了不再檢視 | 數字達標，使用者卻抱怨 | SLI 一直 99.95%，但投訴大增，原來是新功能的錯誤沒被量到 | 每季用事故、投訴、產品變化重新檢視 SLI 定義 |

## 32.11 AI 時代：什麼變了？

AI 從三個方向影響 SLO 的工作。

**第一，AI 產品本身需要新的 SLI。** Harbor 的 AI 客服 agent 能查訂單、送出退款申請（由客服人員核准）。它不只要「有回應」，還要「回答正確」「沒有做出不該做的動作」「在合理成本內」。傳統的 availability 與 latency 仍然需要，但還要加上：

| SLI | 定義範例 | 是否有 ground truth |
|---|---|---|
| Task success | 使用者的問題在對話中被解決，未轉人工的比例 | 部分有（可由後續行為推斷） |
| Groundedness | 回答內容能在訂單資料或知識庫找到依據的比例 | 需抽樣或用評估模型判斷 |
| Unsafe action rate | Agent 嘗試執行未授權動作（例如替不符資格的訂單送出退款申請，或試圖繞過人工核准）的比例 | 有（由 policy 檢查記錄） |
| Tool error rate | Agent 呼叫內部 API 失敗的比例 | 有 |
| Human takeover | 需要轉接真人客服的比例 | 有 |
| Cost per resolved task | 每個成功解決的對話所花的模型與 API 成本 | 有 |

這些 SLI 的難處在於「好」的定義常常沒有即時的正確答案。實務做法是組合：能自動判斷的（tool error、unsafe action）即時量測；需要判斷的（回答品質）用**離線 eval**（固定測試集）、線上抽樣人工標註，以及經過人工校準的 **LLM-as-judge**（用另一個模型評分）。

**第二，模型、prompt、retrieval 設定的變更都是變更。** 換一個模型版本、改一句 system prompt、更新知識庫，都可能讓 AI 服務的品質下降，而且不會出現任何錯誤碼。因此它們應該和程式碼變更共用同一套 error budget 與 rollout 流程：先在 eval 上驗證、再 canary、觀察品質 SLI，預算不足時一樣暫停。

**第三，AI 可以協助 SLO 工作，但不能決定 SLO。**

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 從使用者旅程與 API 日誌草擬候選 SLI 與分母的邊界情況 | SLO 目標代表風險接受程度，由產品與服務 owner 決定；AI 不能自行調低目標 |
| 分析 error budget 消耗，指出最主要的變更、區域或客群，並附上可重現的查詢 | AI 的分析結論要能被查詢結果驗證，不能只採信文字摘要 |
| 依 policy 草擬「預算耗盡」時的發布暫停公告與 action item 清單 | Policy 的例外核准必須由指定的人簽核並留下紀錄 |
| 在 AI 產品上自動執行 eval、比較新舊版本的品質 SLI | LLM-as-judge 需要定期以人工標註校準，並監控評分偏差 |

> [!ai] AI 提醒
> 小心「讓 AI 優化 SLI」這類目標。若 AI 客服 agent 的目標只有「降低轉人工比例」，它可能學會拒絕轉接或給出看似完整、實際錯誤的答案。品質、安全、成本與轉人工比例必須一起觀察，任何單一指標都會被最佳化到失去意義（這正是第 14 章的 Goodhart's law）。

## 32.12 專家怎麼想

- **「這個 SLO 能讓我們做出不同的決定嗎？」** SLO 是決策介面。如果一個 SLO 跌破時沒有人會改變行為，它就只是儀表板上的裝飾。資深 SRE 寧可只有兩個真正被使用的 SLO，也不要二十個沒人看的。
- **先接近使用者，再追求精確。** 一個不完美但從使用者端量測的 SLI，比一個精確但只看 server 的 SLI 更有價值。量測點可以逐步改進。
- **從現況開始，而不是從理想開始。** 先量三個月，把 SLO 訂在略低於歷史穩定水準，讓它一開始就有約束力但不會天天違反，再逐步調整。
- **問依賴，不只問自己。** 看到一個 SLO 時，專家會先問：關鍵路徑上有哪些依賴？它們的 SLO 是多少？有沒有降級方案？
- **把 SLO 當成談判的工具。** 當產品想要更多功能、SRE 想要更穩定時，error budget 讓雙方用同一份數據討論，而不是比誰嗓門大。
- **定期檢討「SLO 是否代表傷害」。** 每次重大事故後問：這次事故有沒有被 SLI 捕捉到？如果使用者很痛但 SLI 沒動，量測就錯了。

## 32.13 動手練習

1. 為你熟悉的一個服務（或 Harbor 的搜尋服務）列出 2 個 CUJ，各寫一個 SLI，明確寫出分母包含與排除哪些事件，至少列出 5 個分母的邊界情況。
2. 修改 32.9 的程式，加入 latency SLI：給定一組回應時間（可以用 `random.lognormvariate` 產生），計算「≤ 500 ms 的比例」與 p50、p99，觀察平均值與 p99 的差距。
3. 用程式計算：一個頁面要呼叫 5、20、50 個後端，每個後端 1% 的機率慢，頁面至少碰到一次慢回應的機率各是多少。
4. 為 Harbor 的 checkout 寫一份一頁的 error budget policy，至少包含：健康、消耗過快、耗盡、例外、外部因素五種情況，並說明每種情況下誰要做什麼。
5. 為 Harbor 的 AI 客服 agent 設計 5 個 SLI，標出哪些可以即時自動量測、哪些需要抽樣或離線 eval，並說明如何防止 agent 只優化其中一個指標。
6. 找出一個你參與過（或讀過）的事故，判斷當時若有正確的 SLI，事故會不會更早被發現。

## 本章重點整理

- 100% 幾乎永遠是錯誤的可靠性目標：使用者感受不到、成本極高，而且會阻止所有變更。
- SLI 是量測事實，SLO 是內部目標加時間窗，SLA 是含後果的對外承諾；三者由不同角色決定。
- 好的 SLI 從使用者旅程出發，形式通常是 good events ÷ valid events。
- 分母（什麼算一次有效機會）比分子更難定義，排除規則要明確、精簡並版本化。
- 量測點越接近使用者越好；load balancer 日誌、client 端資料與 synthetic probe 各有優缺點，常互相驗證。
- 延遲不要看平均值；用百分位數觀察，用「低於門檻的比例」計算 SLI。百分位數不能直接平均。
- 30 天窗口下，99.9% ≈ 43.2 分鐘、99.99% ≈ 4.32 分鐘；每多一個 9，營運方式都要改變。
- 串聯依賴的可用性會相乘，服務的 SLO 不能比關鍵依賴的串聯結果更嚴格，除非有降級設計。
- 內部 SLO 要比 SLA 嚴格，中間的差距是修復問題的緩衝。
- Error budget = 1 − SLO，它把「穩定 vs 速度」變成共同管理的資源。
- 看預算要同時看剩餘量與消耗速度（burn rate）。
- Error budget policy 必須事先由產品、開發、SRE 共同同意，包含例外與外部因素，且同時要求可靠性投資。
- 低流量、批次、資料與多租戶服務需要調整 SLI 形式與時間窗。
- AI 服務需要品質、安全、成本等新 SLI；模型、prompt 與知識庫變更應共用 error budget 與 rollout 流程。

## 延伸問答

> [!question]- Q1. SLI、SLO、SLA 各由誰決定？如果三者都由工程團隊自己決定，會有什麼問題？
> SLI 的量法主要由工程團隊定義，因為只有他們知道系統能在哪裡、用什麼方式量測；但「什麼算好」要和產品一起確認，否則會量到工程師在意、使用者不在意的東西。SLO 是風險接受程度的決策，需要產品與工程共同決定，因為它直接影響功能發布速度與可靠性投資。SLA 有財務與法律後果，必須有業務與法務參與。
>
> 如果三者都由工程團隊自己決定，最常見的結果是目標反映的是「工程團隊做得到的」而非「使用者需要的」：可能太鬆，讓使用者痛苦卻無人行動；也可能太緊，讓產品團隊莫名其妙被凍結發布。SLO 的價值正是讓不同角色在同一個數字上達成共識。

> [!question]- Q2. 為什麼 99.99% 不一定比 99.9% 好？
> 從 99.9% 到 99.99%，每月允許的中斷從 43 分鐘降到約 4 分鐘。這幾乎排除了任何需要人類介入的恢復方式，必須投資多區域部署、自動 failover、更嚴格的變更流程，成本與發布速度都會受影響。
>
> 如果使用者的體驗本身受限於他們自己的網路或裝置，這筆投資帶來的改善可能感受不到。更糟的是，若關鍵依賴只有 99.9%，自己訂 99.99% 根本無法達成。所以「更好」要看使用者是否需要、依賴是否支撐、業務是否願意付出代價。對結帳這類直接影響營收的旅程，多一個 9 可能值得；對內部報表工具，通常不值得。

> [!question]- Q3. 你是 Harbor 的值班者。SLI 顯示 checkout 在過去 30 天是 99.95%，高於 99.9% 的 SLO，但客服說投訴量暴增。你會怎麼判斷？
> 首先懷疑量測本身，而不是懷疑使用者。常見原因有幾個：一是錯誤被包裝成成功（例如回傳 HTTP 200 的錯誤頁），分子被高估；二是分母排除規則太寬，例如把某類真正的服務錯誤歸成使用者錯誤；三是問題集中在某個區域、平台或客群，被全球平均稀釋；四是使用者在意的面向（例如重複扣款、延遲出貨通知）根本不在現有 SLI 中。
>
> 具體做法是抽樣投訴對應的請求，追蹤它們在 SLI 中被如何計算，並依區域、app 版本、付款方式切分 SLI。如果確認是量測問題，要修正 SLI 定義並在 postmortem 中記錄「SLI 沒有捕捉到這次傷害」，這是很重要的學習。

> [!question]- Q4. 一個管理後台每天只有約 200 個請求，SLO 該怎麼訂？
> 低流量時，單次失敗就會讓 SLI 大幅波動（1 次失敗 = 0.5%），用一般的 event-based SLI 與短時間窗會讓告警非常吵、數字也沒有統計意義。可以考慮幾種調整：拉長時間窗（例如 90 天）；加入 synthetic probe，每分鐘模擬一次關鍵操作，讓事件數穩定；改用 time-based SLI，例如「probe 成功的分鐘比例」；或把幾個相關的低流量內部服務合併成一個 SLO。
>
> 也要問這個服務是否真的需要嚴格的 SLO。內部管理後台若短暫不可用，影響的是內部同事、可以稍後重試，目標可以訂得比較寬，把告警留給真正影響使用者的服務。

> [!question]- Q5. Error budget 用完了，但產品說下週一定要上線一個重要功能。該怎麼辦？
> 這正是 error budget policy 需要事先寫好「例外流程」的原因。理想狀況是 policy 已規定誰有權核准例外（例如 VP of Engineering）、需要什麼資訊（風險評估、rollback 計畫、為何不能延後），以及例外如何記錄。照流程走，就不必在壓力下臨時談判。
>
> 若決定例外上線，應同時降低風險：用 feature flag 小範圍開放、加強 canary 分析、準備好立即 rollback、避開高峰時段，並安排可靠性工作與之並行。若這類例外變得頻繁，代表 SLO 可能訂得太嚴，或系統的可靠性真的需要投資，兩者都應在下一次 SLO 檢討中處理，而不是每次都例外。

> [!question]- Q6. 為什麼不能把每分鐘的 p99 平均起來，當作一小時的 p99？
> 百分位數是分佈的特徵，不是可以相加的量。假設前 59 分鐘每分鐘只有 10 個請求、都很快，最後 1 分鐘有 10,000 個請求、其中很多很慢。平均 60 個「每分鐘 p99」時，最後一分鐘只占六十分之一的權重，但它其實包含了絕大多數請求，真實的一小時 p99 會由它主導。
>
> 正確做法是保留原始分佈，最常見的是 histogram（每個延遲區間的計數），計數可以相加，再從合併後的 histogram 算百分位數。另一個做法是把延遲 SLI 定義成「低於門檻的請求比例」，good 與 valid 都是計數，可以直接跨時間相加，這也是 SLO 實務中偏好門檻式 latency SLI 的原因之一。

> [!question]- Q7. AI 客服 agent 的「回答品質」沒有即時的正確答案，要怎麼放進 SLO？
> 把品質拆成可以量測的部分，再組合使用。能自動判斷的部分即時量測，例如 tool 呼叫失敗率、是否觸發 policy 阻擋、是否轉人工、使用者是否在對話後重新提出同樣的問題。需要判斷的部分（回答是否正確、是否有依據）則用三種方法：固定的離線 eval 測試集，在每次模型或 prompt 變更前執行；線上抽樣，由人工標註一小部分對話；以及經過人工標註校準的 LLM-as-judge，定期檢查它和人工判斷的一致程度。
>
> SLO 可以訂在能量測的部分（例如「抽樣品質分數 ≥ 4/5 的比例 ≥ 90%」），並接受它比 availability 更有延遲與不確定性。重點是品質、安全、成本與轉人工比例要一起看，避免 agent 為了優化一個指標而犧牲其他。

> [!question]- Q8. 面試題：如果只能為一個新服務做一件可靠性相關的事，你會做什麼？
> 一個好的回答是：先和產品一起找出最重要的使用者旅程，定義一個從使用者角度量測的 SLI，並開始收集數據。理由是在沒有量測之前，所有可靠性投資都是猜測：你不知道現在有多可靠、不知道問題出在哪、也無法判斷投資是否有效。
>
> 有了 SLI 與幾週的數據，才能訂出合理的 SLO、根據 error budget 決定下一步該投資告警、容量、降級設計還是變更流程。回答時可以補充：量測點要盡量靠近使用者（例如 load balancer 而非 server 內部），並且分母的排除規則要明確，這會讓面試官看到你理解 SLI 最容易出錯的地方。
