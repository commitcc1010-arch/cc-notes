# 第 35 章　Simplicity、Change Management 與 Error-budget Policy

> [!abstract] 本章地圖
> **核心問題**：既然大部分事故來自變更，可靠的團隊要怎麼繼續快速改變系統？當 error budget 用完時，「凍結」到底該凍結什麼、凍結多久、怎麼解凍？
>
> **你會學到**：
> - 區分 essential complexity 與 accidental complexity，並用具體做法讓系統保持「boring」
> - 理解為什麼變更是事故的主要來源，以及 code 之外的變更（設定、flag、資料、依賴、模型）
> - 用 release engineering 原則與「漸進、可觀測、可回復」三件事設計變更流程
> - 依 blast radius、可逆性與可偵測性為變更分級，而不是讓所有變更都經過同一道重量級審批
> - 把 error budget policy 變成可執行的機制：自動判定狀態、變更分類、消耗歸因、解凍條件
> - 正確使用 freeze，避免「凍結越久、解凍時越危險」的惡性循環
>
> **前置知識**：第 29 章（canary、rollback、feature flag）、第 32 章（error budget 與 error budget policy）、第 34 章（burn rate 告警）
>
> **對應原書**：SRE 第 8 章〈Release Engineering〉、第 9 章〈Simplicity〉；SRE Workbook 第 7 章〈Simplicity〉

## 35.1 故事：凍結了三週，解凍那天又出事

Harbor 成立第三年的九月，checkout 在一個週三下午中斷了 35 分鐘。起因看起來很小：阿凱要把折價券快取的過期時間從 60 秒調到 600 秒，以降低資料庫負載。這是一個設定變更，所以阿凱沒有走第 29 章建立的 canary pipeline，而是用一支兩年多前留下來的維運腳本，直接把設定推到所有區域。這支腳本是 Harbor 還是 8 人新創時寫的，當時「改設定」就等於「登入機器改檔案」，後來大家只是把它包裝成一個指令。

設定本身沒有錯，問題出在一個沒人記得的 feature flag。一年多前 checkout 團隊為了遷移計價邏輯加了 `legacy_pricing_v1`，遷移完成後 flag 在大部分區域關掉了，但南部區域因為一個大賣家的特殊需求一直開著。舊的計價路徑會讀取第三層快取（Harbor 的 checkout 這時已經有三層快取：程序內、Redis、以及 CDN 邊緣），而新的過期時間讓它在每次快取失效時同時打爆資料庫。南部區域先倒，流量被轉到其他區域，接著全部倒下。

35 分鐘的全面中斷，加上這個月稍早的兩次小事故，checkout 的 error budget 用掉了 121%。依照第 32 章簽過的 policy，工程經理 Kevin 宣布凍結非緊急發布。接下來的三週，團隊花在爭論上的時間幾乎和修 bug 一樣多：負責資安的工程師要升級一個有漏洞的套件，算不算緊急？行銷活動需要打開一個早就寫好的 flag，算不算發布？做到一半的資料庫 schema 遷移，要不要繼續？更糟的是，凍結期間沒人想等的人開始找捷徑，有兩個設定變更又是透過那支舊腳本推出去的。

凍結第 23 天，Lisa 問：「我們什麼時候可以恢復？」志明打開消耗紀錄算了一下：policy 寫的是「直到 SLI 回到 SLO 以上」，而 30 天 rolling window 裡還留著 9 月初的兩次小事故和那 35 分鐘。9 月 11 日那次依賴事故要到隔天才會滑出窗口，預算才會回到正值；那 35 分鐘本身則要等到 10 月中才會滑出。換句話說，什麼時候能解凍，取決於一個月前的舊事故何時滑出窗口，和團隊這三週修好了什麼幾乎無關。第 24 天預算一回正，團隊就解凍，把累積的 61 個 PR 在同一天全部部署。當晚 checkout 又出了一次事故，這次花了 50 分鐘才找出是 61 個變更中的哪兩個互相衝突。

事後美華在 postmortem 寫下兩個結論。第一，凍結沒有讓 Harbor 更安全，只是讓變更累積成一顆更大的炸彈。第二，真正的問題不在於「變更太多」，而在於系統太複雜（三層快取、遺忘的 flag、兩條部署路徑），以及有一條不受管理的變更通道。這一章就從這兩個結論出發：先談如何讓系統保持簡單，再談如何讓變更變安全，最後談 error budget policy 在真實世界裡怎麼執行，以及凍結的正確用法。

## 35.2 Simplicity 為什麼是可靠性問題

### Boring 是一種美德

SRE 原書在〈Simplicity〉一章提出一個違反工程師直覺的主張：對 production 軟體來說，**boring**（無聊、可預測）是好事。工程師喜歡新奇的設計，但在凌晨三點排查事故時，沒有人希望遇到驚喜。一個 boring 的系統是行為可以被預測的系統：看到輸入，就大致知道會發生什麼；出了問題，可能的原因只有少數幾個。

Harbor 的事故說明了反面。三層快取、一個兩年前的 flag、兩條部署路徑，每一個單獨看都有合理的理由，但它們組合在一起，產生了一個沒有人預測得到、也沒有人測試過的行為。事故中最花時間的不是修復，而是理解：值班者要先搞清楚「這個區域現在走的是哪一條計價路徑、讀的是哪一層快取」，才能開始判斷。

### Essential 與 accidental complexity

Fred Brooks 在〈No Silver Bullet〉一文中把軟體的複雜度分成兩種：

- **Essential complexity**（本質複雜度）：問題本身帶來的、無法去除的複雜度。Harbor 要處理多種付款方式、折價券規則、退款與部分退款，這些是業務本身的複雜度，任何實作都必須面對。
- **Accidental complexity**（偶然複雜度）：解法帶來的、原本可以避免的複雜度。三層快取中有一層是當年為了解決一個早已不存在的效能問題加的；兩條部署路徑是因為舊腳本從沒被淘汰。

可靠性工程的一個核心任務，就是持續找出並移除 accidental complexity。Essential complexity 不會消失，但可以被好的模組邊界隔離，讓每個人只需要理解自己負責的那一部分。

### 複雜度是怎麼長出來的

複雜度很少是一次決定的結果，通常是許多個「這次先這樣」累積起來的。幾個最常見的來源：

| 來源 | 為什麼會增加複雜度 | Harbor 的例子 |
|---|---|---|
| 狀態 | 每個保存狀態的地方都可能不一致，需要同步、失效與恢復機制 | 三層快取，每一層的過期策略都不同 |
| 設定與 flag | n 個獨立的布林 flag 有 2ⁿ 種組合，大部分組合從未被測試 | 42 個 flag，其中 17 個已經超過一年沒有改變過 |
| 並存的新舊路徑 | 遷移完成前，兩套邏輯同時存在，行為取決於流量走哪一條 | `legacy_pricing_v1` 在一個區域仍然開著 |
| 依賴 | 每個依賴都帶來自己的失效模式、版本與升級成本 | 三個 HTTP client 函式庫，各自有不同的 timeout 預設值 |
| 多條操作路徑 | 同一件事有兩種做法，其中一種通常沒有保護 | 設定可以經 pipeline，也可以經舊腳本 |

Flag 的組合數特別值得記住。10 個獨立的 flag 有 1,024 種組合，20 個就超過一百萬種。測試不可能覆蓋這些組合，所以每一個長期存在的 flag 都在增加「production 正在跑一個從未被測試過的組合」的機率。

### 複雜度能不能量測

程式碼層級的複雜度有現成的指標，例如 cyclomatic complexity（一段程式有幾條獨立的執行路徑）。但整個系統的複雜度很難用一個數字表示。SRE Workbook 的〈Simplicity〉一章建議用幾個代理指標來觀察：新成員要訓練多久才能值班、向別人解釋整個系統要花多久、同一件事有幾種不同的管理方式、部署了多少種不同的設定組合，以及系統存在多久（越老的系統，越多行為已經被別人依賴，也就是 Hyrum's Law）。這些指標都不精確，但它們的趨勢很有參考價值：如果 Harbor 新進的 SRE 從兩週能上手值班變成要兩個月，系統一定變複雜了。

Workbook 這一章還有兩個觀點值得記住。第一，複雜度在活著的系統中會自然增加，除非有人刻意投入反方向的力氣。第二，複雜度是一種外部性：加入它的人通常不是付出代價的人。寫下第三層快取的工程師得到了當時的效能改善，付出代價的卻是兩年後半夜被叫起來的值班者。這也是為什麼原書認為 SRE 適合擔任「端到端簡單性」的推動者：SRE 的工作本來就要求看整個系統，而不只是其中一個元件。

> [!warning] 常見誤解
> 「簡單就是程式碼越少越好、抽象越少越好。」不一定。把三套重複的重試邏輯合併成一個共用函式庫，程式碼可能沒有變少，但系統變簡單了，因為重試行為只剩一種。Simplicity 衡量的是**理解與預測系統行為需要多少心力**：有多少種狀態、多少條路徑、多少個需要同時記在腦中的概念。有時候多一層清楚的抽象，反而降低了整體複雜度。

## 35.3 讓系統保持簡單的具體做法

知道複雜度有害還不夠，團隊需要可以每天執行的做法。下面這些做法都來自同一個前提：**程式碼與機制是負債，不是資產**。資產是它提供的功能；每一行程式碼、每一個 flag、每一條路徑，都需要被閱讀、測試、維護、在事故中被理解。

### 刪除是一級工作

SRE 原書記錄了一種常見的抗拒：工程師對自己寫的程式碼有感情，不願意刪除「也許以後會用到」的東西。但被註解掉、被 flag 關掉的程式碼不是無害的，它會出現在搜尋結果裡、在重構時被誤改、在某個奇怪的組合下被重新啟用。原書把「藏在一個永遠關著的 flag 後面的程式碼」比喻成一顆定時炸彈，並以 Knight Capital 的交易事故為例：舊程式碼因為一個被重新使用的 flag 意外復活。原書也有一節談「負的程式碼行數」：每一行新增或修改的程式碼都可能帶來新的缺陷，所以刪掉不再有用的程式碼，常常是最有價值的改動之一。

Harbor 在事故後的做法是把刪除排進正式的工作計畫，而不是等有空：

- **每一個 flag 建立時就要有 owner 與到期日**。到期時，flag 管理系統自動開 ticket 給 owner：要嘛刪除 flag 與舊路徑，要嘛延長並寫下理由。
- **每一次遷移的完成定義包含「舊路徑已刪除」**。遷移到 90% 不是完成，舊路徑還在就代表兩套行為還在。
- **每季一次「刪除日」**：每個團隊列出可以移除的服務、endpoint、依賴、設定與 dashboard，用 telemetry 證明它們沒有被使用後刪除。

### 最小的 API

API 越小，使用者越不容易依賴到你不想承諾的行為（第 5 章的 Hyrum's Law），你也越容易改變內部實作。SRE 原書在這裡引用了 Antoine de Saint-Exupéry 的名言：完美不是無可增加，而是無可刪減。具體來說：一個新參數、一個新的設定選項、一個新的 endpoint，都要問「如果不加，使用者會怎樣？」如果答案是「少數人會不方便」，通常不值得用永久的複雜度去換。

### 一件事只有一條路

Harbor 事故的直接原因之一，是改設定有兩條路。事後的修正很簡單但很重要：舊腳本被移除，所有 production 設定都和程式碼一樣，放在版本控制中，經過 review，透過同一條 pipeline 漸進推出。同樣的原則適用於部署、資料庫遷移、權限變更：一件事只保留一條經過保護的路徑，其他路徑要嘛刪除，要嘛明確標示為緊急用途並在使用時告警。

### 模組化與清楚的邊界

Essential complexity 無法刪除，但可以被包起來。好的模組邊界讓 checkout 團隊不需要理解 pricing 的內部規則，只需要依賴一個穩定、有文件、有版本的介面（第 17 章）。邊界的品質可以用一個問題檢驗：一個模組改了內部實作，有多少其他模組需要跟著改？答案越接近零越好。

### 簡單也適用於發布

原書特別指出，發布本身也應該簡單：每次只改少量東西。一次發布包含一個變更，出問題時你知道是哪一個；一次發布包含 61 個變更，你需要先做一次「找兇手」的調查。小批次本身就是一種降低複雜度的手段，這和第 19 章的 small batches 是同一個原則在 production 端的版本。

## 35.4 變更是事故的主要來源

### 為什麼變更最危險

SRE 原書在導論（第 1 章）談 change management 的段落中提到，Google SRE 觀察到大約 70% 的 outage 是由對運作中系統（live system）的變更造成的。原書沒有說明這個數字的統計方法，它是 Google 內部的經驗值，不需要精確套用到每個組織，但方向幾乎普遍成立：一個沒有人碰的系統，通常會以相當穩定的方式運作，直到某個變更改變了它的行為。硬體故障、流量尖峰當然也會造成事故，但它們通常是系統設計時就預期要處理的情況；變更則是在一個已經運作的系統上，引入一個尚未在真實環境中驗證過的新狀態。

但結論不能是「少改變」。第 32 章已經說明，停止改變也意味著停止修補漏洞、停止升級依賴、停止回應使用者需求，而那些延遲本身也是風險（第 4 章的 time and change）。正確的結論是：**讓每個變更都變安全，而不是讓變更變少**。

### 不只是程式碼

很多團隊對程式碼部署有完整的保護，對其他種類的變更卻幾乎沒有。Harbor 的事故恰好就是一個設定變更。下表列出 production 常見的變更類型：

| 變更類型 | 例子 | 常見的保護缺口 |
|---|---|---|
| 程式碼 | 新版本的 checkout 服務 | 通常保護最完整：review、CI、canary |
| 設定 | 快取過期時間、timeout、連線池大小 | 常常即時生效、全域推送、沒有 canary |
| Feature flag | 打開新的折價券規則 | 「只是打開一個開關」，沒有被當成發布 |
| 資料與 schema | 新增欄位、回填資料、刪除舊表 | 難以 rollback，常常需要 expand／contract（第 29 章） |
| 基礎設施 | 升級 Kubernetes、改負載平衡規則、改 DNS | 影響範圍大，常由不同團隊執行 |
| 依賴 | 升級函式庫、上游服務改版 | 變更由別人發起，自己的團隊可能不知道 |
| 憑證與密鑰 | 憑證輪替、API key 更新 | 頻率低，流程容易被遺忘 |
| 模型與 prompt | 換模型版本、改 system prompt、更新知識庫 | 不會產生錯誤碼，品質下降不易察覺 |

設定變更特別值得警惕。它們通常比程式碼部署更快（幾秒內全域生效）、更少被測試（「只是改一個數字」），而且常常繞過 code review。不少大型公開事故的起因都是一個推送到全球的設定變更。最有效的做法是把設定當成程式碼：版本控制、review、驗證格式與範圍、漸進推出、可以一鍵回復。

### 安全變更的三件事

SRE 原書在同一段落接著指出，最佳實務是用自動化完成三件事，它們到今天仍是變更管理的骨架：

1. **漸進式推出**：先讓一小部分流量、一個區域或一部分使用者使用新版本，確認沒有問題再擴大（第 29 章的 canary 與 progressive delivery）。
2. **快速而準確地偵測問題**：在變更擴大之前就知道它有沒有造成傷害。這需要第 33 章的 observability 與第 34 章的告警，而且要能把指標變化和特定變更對應起來。
3. **出問題時安全地回復**：rollback 要快、要經過練習、要不需要特別的權限或知識。一個從未被執行過的 rollback 程序，等於沒有 rollback 程序。

這三件事合起來，等於把「這個變更有沒有問題」的判斷，從部署之前的猜測，移到部署之後的小範圍觀察。部署前的 review 與測試仍然重要，但它們永遠抓不到所有問題；漸進推出讓剩下的問題只傷害一小部分使用者。

## 35.5 Release engineering：讓發布成為可重複的工程

**Release engineering**（發布工程）是把「如何建置、打包、發布軟體」當成一門工程來做。SRE 原書描述了 Google release engineering 的幾個原則，它們決定了變更管理能不能落地：

- **Self-service**（自助）：團隊能自己發布，不需要排隊等一個集中的發布團隊。發布團隊的工作是提供工具與規則，而不是替每個人按按鈕。
- **High velocity**（高頻率）：頻繁發布讓每次發布更小、更容易理解。有些團隊每次通過測試就自動發布，有些按固定節奏發布，但方向都是讓發布變成日常事件而不是大事。
- **Hermetic builds**（封閉式建置）：同一份原始碼在任何時間、任何機器上建置都得到相同的結果，不依賴建置機器上剛好裝了什麼（第 27 章）。這讓「重新建置某個舊版本來 rollback」是可靠的。
- **Enforcement of policies and procedures**（強制執行政策）：誰能發布、發布前需要哪些檢查、需要誰核准，由工具強制執行並留下紀錄，而不是靠人記得。

從這些原則可以推導出幾個具體做法。**建置一次、到處晉升**：同一個建置產物（artifact）依序部署到 staging、canary、全量，而不是每個環境重新建置。**設定與程式碼分開發布但同樣受管**：設定也有版本、review 與漸進推出。原書的 release engineering 一章專門討論了設定管理：Google 的各種做法都把設定放在主要的版本庫中並強制 code review，差別只在設定要和 binary 包在一起發布、還是獨立打包或放在外部儲存。**發布紀錄是可查詢的資料**：每一次變更的內容、時間、範圍、發起人都能被查詢，事故時第一個問題「最近改了什麼」才能在幾秒內得到答案。

Harbor 在第 27 到 29 章已經建立了建置、CI 與 CD 的基礎，這一章事故暴露的缺口不在 pipeline 本身，而在於 pipeline 之外還有一條沒有被淘汰的路。Release engineering 的工作不只是把正確的路做好，還包括把錯誤的路關掉。

## 35.6 變更管理：漸進、可觀測、可回復

### 依風險分級，而不是一體適用

傳統的變更管理常見一種做法：所有 production 變更都要提交給 **CAB**（Change Advisory Board，變更諮詢委員會），由一群不直接參與開發的人每週開會核准。直覺上這很安全，但《Accelerate》與 DORA 的研究發現，依賴外部單位（例如 CAB 或上級主管）核准的重量級變更流程，對軟體交付表現有負面影響，而且找不到證據顯示它能降低變更失敗率。DORA 建議的替代做法是同儕 review 搭配自動化測試與監控。原因不難理解：委員會的人離程式碼太遠，無法真正評估風險；為了減少開會次數，變更被累積成大批次，反而更危險。

比較有效的方式是依變更的實際風險分級，讓低風險的變更快速通過自動化檢查，把人的注意力集中在高風險的少數。評估風險可以看三個維度：

| 維度 | 低風險 | 高風險 |
|---|---|---|
| **Blast radius**（影響範圍） | 一個服務、一個區域、1% 流量 | 全域、所有使用者、共用基礎設施 |
| **Reversibility**（可逆性） | 一鍵 rollback，幾分鐘內恢復 | 資料刪除、schema 收縮、對外 API 移除 |
| **Detectability**（可偵測性） | 有 SLI 與 canary 指標能直接看到影響 | 影響延遲出現，或不在任何指標中 |

Harbor 依此把變更分成三級：

- **標準變更**：小範圍、可逆、可偵測。例如一般的程式碼部署走 canary、調整 dashboard。同儕 review 加上自動化檢查即可，不需要額外核准。
- **重要變更**：影響範圍大或可偵測性較差。例如修改全域設定、升級共用函式庫、打開影響結帳的 flag。需要服務 owner 核准、指定觀察者、寫下 rollback 步驟，並在離峰時段執行。
- **高風險變更**：難以回復。例如刪除資料、schema 的 contract 階段、更換金流商。需要事前的 design review、演練過的回復計畫（或明確接受無法回復）、多人在場執行，以及事後確認。

### 每個變更都要回答的問題

不管哪一級，Harbor 的變更紀錄（通常就是 PR 描述加上部署系統自動補上的欄位）都要回答：

```text
改了什麼     ：coupon cache TTL 60s → 600s
為什麼       ：降低 coupon DB 讀取量約 40%（附 dashboard）
影響範圍     ：所有區域的 checkout；先推南部區域 5% 流量
怎麼知道它壞了：checkout burn rate、coupon DB QPS 與延遲、cache miss 尖峰
怎麼回復     ：設定 rollback（一鍵，約 1 分鐘生效）；不需資料修復
觀察多久     ：每階段 bake 15 分鐘，全量後觀察 1 小時
相關的 flag  ：legacy_pricing_v1（南部區域仍開啟）← 部署系統自動列出
```

最後一行是 Harbor 事故後新增的：部署系統會自動列出目標範圍內所有不一致的 flag 狀態。如果事故前就有這一行，阿凱很可能會注意到南部區域與其他區域的差別。

### 一條受保護的變更路徑

下面這張圖是 Harbor 重新設計後的變更路徑。所有種類的變更（程式碼、設定、flag、schema）都走同一條路，只是不同等級在中間的關卡不同：

```text
  PR（程式碼／設定／flag／schema）
     │
     ▼
  review + CI + 設定驗證 ──── 不通過 ──▶ 退回
     │
     ▼
  變更分級 ─── 重要／高風險 ──▶ owner 核准、rollback 步驟、觀察者
     │                                    │
     ▼                                    ▼
  error budget 閘門（讀取 SLO 系統的 policy 狀態）
     │   正常：放行  │ 消耗過快：縮小批次、強制 canary │ 耗盡：只放行允許類別
     ▼
  canary 5% ──▶ bake 15 分 ──▶ 25% ──▶ bake ──▶ 100%
     │                │
     └── 指標惡化 ────┴──▶ 自動 rollback，通知變更發起人與值班者
     │
     ▼
  變更事件寫入 change log（dashboard 標記、可依時間查詢）
```

從上往下讀這張圖：變更先經過 review 與自動化檢查；接著依風險分級決定是否需要額外核准；然後經過 error budget 閘門，它直接讀取 SLO 系統算出的 policy 狀態，決定這個變更能不能走、要用多保守的方式走；通過後進入漸進推出，每一階段有 bake time（觀察期），指標惡化就自動 rollback；最後變更事件被記錄下來，讓 dashboard 能在時間軸上標出「這裡有一次變更」，也讓事故時能查詢「過去兩小時內改了什麼」。

這張圖中間的 error budget 閘門，就是下一節的主題。

## 35.7 Error-budget policy 怎麼真正執行

第 32 章已經寫出 Harbor 的 error budget policy 條文：預算健康、消耗過快、耗盡、例外、外部因素各要做什麼。Harbor 的故事說明，有了條文不代表能執行。凍結期間的每一場爭論，都是條文沒有回答的問題：誰判定現在是什麼狀態？什麼樣的變更算「非緊急」？凍結到什麼時候？這一節談的是讓 policy 從文件變成機制的幾個部分。

### 狀態由系統判定，不由人宣布

Harbor 事故時，凍結是 Kevin 在群組裡宣布的；解凍也是開會決定的。這帶來兩個問題：狀態取決於有沒有人注意到，以及有沒有人願意當壞人。比較穩健的做法是讓 SLO 系統持續計算每個服務的 policy 狀態，並以機器可讀的方式發布：

```text
service: checkout
slo: availability 99.9% / 30d rolling
state: EXHAUSTED            # HEALTHY / BURNING / EXHAUSTED
budget_remaining: -21%
since: 2025-09-17T15:42+08:00
exit_criteria:
  - 7 天 SLI ≥ 99.9%（目前 99.86%）
  - postmortem P0 action items 完成（2 / 3）
owner_on_record: 美華（checkout owner、tech lead）
```

部署系統在每次變更前讀取這個狀態，依規則放行或阻擋，並把決定寫入變更紀錄。人仍然可以介入（例外核准），但介入本身是一個有紀錄的動作，而不是「預設什麼都不做」。這樣也避免了一個常見的弱點：policy 只在有人記得時才生效。

### 凍結的對象要事先分類

「暫停非緊急發布」這句話在事故當下會引發無數爭論，所以分類要事先寫好，並且盡量讓部署系統能自動判斷。Harbor 事後的分類表：

| 類別 | 預算耗盡時 | 判斷依據 |
|---|---|---|
| Rollback、關閉 flag、降低流量 | 一律允許 | 降低風險、回到已知狀態 |
| 安全修補 | 允許，但走 canary | 延遲修補本身是更大的風險 |
| 可靠性修復（postmortem action items） | 允許，但走 canary | 這正是凍結要換來的工作 |
| 資料修正 | 允許，需 owner 核准 | 使用者資料錯誤不能等 |
| 進行中的遷移 | 停在目前的安全階段，不進入下一個不可逆階段 | 例如 expand 已完成，contract 暫緩 |
| 新功能、打開新的 flag | 暫停 | 增加風險、與可靠性無關 |
| 純重構、依賴的例行升級 | 暫停，或依例外流程 | 有價值但可以等 |

這張表是第 32 章 policy 第 3 條的執行細則，而不是另一套規則。第 32 章寫「安全修補、可靠性修復與資料修正不受限制」，意思是它們不受凍結阻擋，並不代表可以跳過 canary 或 owner 核准；預算耗盡時系統特別脆弱，這些被放行的變更反而更應該走完整的保護。作為對照，SRE Workbook 的範例 policy 更嚴格：預算超支時只放行 P0 問題與安全修補。

其中「打開 flag」與「關閉 flag」的不對稱特別重要。關閉一個 flag 是回到舊行為，通常降低風險；打開一個 flag 是引入新行為，本質上就是一次發布。行銷活動要求打開的那個 flag，在這張表下答案很清楚：暫停，除非走例外流程。

分類還有一個容易被忽略的作用：防止「改名換姓」。如果「可靠性修復」可以繞過凍結，就會有人把功能變更標成可靠性修復。所以類別最好由變更內容與連結的 action item 判定（例如 PR 必須連到一個 postmortem 的 action item 才算可靠性修復），並由服務 owner 抽查。

### 消耗歸因：預算被誰用掉

一個健康的 policy 需要知道預算是怎麼被用掉的。Harbor 為每個 SLO 維護一份**消耗帳本**：每一次明顯的消耗都對應到一個事件，標記類別（自己的程式碼變更、設定變更、依賴、基礎設施、流量異常、原因不明）與消耗的比例。

```text
checkout 2025-09 消耗帳本（30 天窗口）
  09-03  coupon 服務部署錯誤，rollback       變更（程式碼）   18%
  09-11  payments 供應商 API 延遲            依賴             22%
  09-17  cache TTL 設定 + legacy flag 組合    變更（設定）     81%
  其他   背景錯誤                             —                 0%（計入其他）
  合計                                                       121%
```

帳本的用途有三個。第一，它讓 postmortem 與規劃有數據：如果一季下來變更造成的消耗占七成，投資方向是變更安全；如果依賴占七成，投資方向是容錯與降級。第二，它讓「這不是我們的錯」的爭論有了事實基礎，但不改變結論：第 32 章的 policy 已規定外部因素造成的耗盡仍適用發布暫停，因為使用者不在乎是誰的錯，帳本只是讓 action items 指向正確的地方。第三，它暴露量測問題：「原因不明」的比例長期偏高，代表 observability 有缺口。

### 解凍條件：rolling window 的陷阱

Harbor 凍結了 24 天，最大的原因是一個沒有人事先算過的數學問題。第 32 章 policy 第 3 條寫的是「暫停非緊急功能發布，直到 SLI 回到 SLO 以上」；SRE Workbook 附錄的 error budget policy 範例也用類似的寫法（直到服務回到 SLO 之內）。但當 SLO 是 30 天 rolling 時，「30 天 SLI 回到 SLO 以上」就等於「預算回正」，而預算剩餘量取決於過去 30 天消耗的總和：

```text
預算剩餘(第 d 天) = 1 − Σ（第 d−29 天 到 第 d 天 的消耗）

簡化情境（假設只有一次 81% 的事故，其餘每天 1% 背景消耗）：
  事故當天（第 0 天）窗口總和 = 81% + 前 29 天 × 1% = 110%
  第 1–29 天：每天滑出 1%、滑入 1%，總和維持 110% → 預算仍為 −10%
  第 30 天  ：81% 滑出，總和降到約 30% → 預算才回正

Harbor 的實際帳本（9/03 18%、9/11 22%、9/17 81%，背景約 0%）：
  第 16 天（10/03）：9/03 的 18% 滑出 → 總和 103%，仍為負
  第 24 天（10/11）：9/11 的 22% 滑出 → 總和 81%，預算回正（剩 19%）
  第 30 天（10/17）：81% 滑出
```

也就是說，如果解凍條件是「預算回正」，凍結長度由舊事故何時滑出窗口決定：Harbor 能在第 24 天解凍，只是因為一次與這次事故無關的依賴問題剛好在那天滑出；如果只有那一次 81% 的事故加上背景消耗，就要等滿 30 天。不管團隊是不是在第三天就已經修好了所有問題，結果都一樣。這不是 policy 想要的效果：凍結的目的是讓團隊把力氣放在可靠性上，而不是懲罰團隊等待時間經過。

比較好的解凍條件是看**可靠性是否真的恢復**，例如：

- 最近 7 天的 SLI 回到 SLO 以上（代表目前的系統是健康的）；
- postmortem 中標為 P0 的 action items 已完成（代表造成事故的弱點已處理）；
- 服務 owner 與 SRE 共同確認。

三個條件都滿足就解凍，即使 30 天預算還是負的。解凍後的一段時間（例如到 30 天預算回正為止）處於「消耗過快」狀態：可以發布，但批次較小、canary 較嚴格。這樣既保留了 policy 的約束力，又不會讓凍結長度取決於日曆。

> [!note] 這和 SLO 本身是兩件事
> 解凍條件改用 7 天 SLI，不代表 SLO 改了。30 天 SLO 依然違反，月報上依然要誠實記錄，SLA 依然照合約計算。改變的只是「什麼時候允許恢復發布」這個操作決策。

### 例外要讓風險變小，而不只是簽名

第 32 章的 policy 規定了誰能核准例外。執行上要補的是：例外核准不能只是一個簽名，而要附帶降低風險的條件。Harbor 的例外申請要回答：

```text
例外申請：雙十一前置的會員分級顯示（feature flag: tier_badge）
為什麼不能等 ：行銷活動 10/20 開始，素材已對外公告
風險評估     ：只影響商品頁顯示，不在 checkout 路徑；失敗時隱藏徽章
降低風險的做法：flag 先開 1% → 10% → 100%，每階段 bake 2 小時；
                 新增「tier_badge 錯誤率」指標，超過 0.5% 自動關閉 flag
回復方式     ：關閉 flag（即時生效）
核准         ：工程經理 Kevin、checkout owner 美華
紀錄         ：寫入 policy 附錄；下次 SLO 檢討時回顧
```

這份申請的重點不是格式，而是它迫使申請人把變更縮小、加上偵測與自動回復。如果一個例外申請寫不出「降低風險的做法」，它就不應該被核准。如果例外變得頻繁，代表 policy 或 SLO 本身需要重新檢討，這應該在季度檢討中處理。

## 35.8 Freeze 的正確用法

**Freeze**（凍結）是暫時停止某些變更的做法。它是一個有用的工具，但也是最容易被誤用的工具。Harbor 的經驗並不特別：很多團隊的凍結最後都變成了「累積變更、然後在解凍時一次爆發」。

### 三種不同的凍結

實務上有三種常被混為一談的凍結，它們的目的與正確做法都不同：

| 類型 | 目的 | 合理的長度 | Harbor 的例子 |
|---|---|---|---|
| **Error budget freeze** | 把工程力氣轉到可靠性工作上 | 直到可靠性恢復（不是直到日曆到期） | 本章故事中的凍結 |
| **Calendar freeze**（日曆凍結） | 在業務關鍵或人力不足的時段避免風險 | 短、範圍明確 | 雙十一前後各 3 天（T−3 到 T+3，與第 36 章預先擴容到縮回的時程一致）、農曆年連假 |
| **Incident freeze**（事故凍結） | 事故處理期間避免無關的變更干擾判斷 | 事故期間 | 事故進行中，暫停所有非事故相關部署 |

Incident freeze 幾乎沒有爭議：事故進行中，任何無關的變更都會讓「是什麼造成了現在的狀況」更難判斷（第 44 章）。Calendar freeze 是 Harbor 在 Part 6–7 面對雙十一時會大量使用的做法。Error budget freeze 則是本章的重點，也最需要設計。

### 凍結的常見失敗

**凍結但沒有人做可靠性工作**。Error budget freeze 的價值來自它換來的可靠性投資：開發者暫停功能工作，加入修復 postmortem action items、補測試、移除複雜度。如果凍結期間大家只是等待，或繼續寫功能只是不部署，凍結就只剩下成本。這也是為什麼第 32 章的 policy 要求「至少一位開發工程師加入可靠性工作」。

**凍結導致變更累積**。主幹上的程式碼持續合併，但沒有部署，生產環境與主幹的差距一天天拉大。解凍那天，一次部署的不是一個變更，而是三週的變更。35.3 已經說明大批次為什麼危險：出問題的機率上升，找出問題的時間也變長。Harbor 解凍當天的事故，就是 61 個變更中兩個互相衝突。

**凍結把變更推向沒有保護的路徑**。當正規的路被擋住，人會找其他的路。Harbor 凍結期間有兩個設定變更透過舊腳本推出，正好是最沒有保護的那條路。凍結越嚴、越久，這種壓力越大。

**凍結前的搶先潮**。日曆凍結常見的現象是凍結前一天大家搶著合併與部署，結果凍結期間一開始就在處理搶先部署造成的問題。這等於把風險集中到了最不想要風險的時段之前。

**長期不部署會讓部署能力退化**。部署流程、rollback 腳本、憑證、權限，這些東西在不使用時會悄悄壞掉。一個三週沒有部署的服務，第一次部署時遇到的問題可能與程式碼無關，而是 pipeline 本身出了狀況。

### 凍結的正確做法

把這些失敗反過來，就是正確使用凍結的方式：

1. **凍結範圍要窄**：凍結的是「增加風險的變更」，不是「所有變更」。35.7 的分類表就是範圍定義。
2. **凍結期間 pipeline 繼續運作**：允許的變更（修復、安全修補）照常走 canary 部署，讓部署能力保持活躍。
3. **凍結要有明確的工作內容**：凍結開始時就列出要完成的可靠性工作與負責人，凍結的長度由這些工作的完成度決定。
4. **控制累積**：凍結期間的功能變更可以合併到主幹但藏在 flag 後面，或者在凍結期間就限制合併量；解凍時依序、小批次、每天有上限地釋放，而不是一次全部推出。
5. **日曆凍結前不搶先**：凍結前就要逐步收斂，而不是在凍結前一天搶著上線。以 Harbor 的雙十一為例（第 36 章的時程），T−14 天容量計畫凍結、非必要變更開始收斂，只接受小而可逆的變更；大型變更要在這之前完成並經過一段穩定期；T−3 到 T+3 天才是真正的日曆凍結。
6. **與其完全停止，不如分級減速**：在預算消耗過快時就開始縮小批次、強制 canary、延長 bake time，讓多數情況不需要走到完全凍結。下一節的模擬會比較這兩種做法。

## 35.9 動手寫：比較三種凍結策略

下面的程式模擬 Harbor checkout 180 天的變更流量：每天有 6 個新的功能變更進入佇列，每天部署一次。每個變更有小機率本身有問題，同一批的變更兩兩之間也有小機率互相衝突；出問題時，批次越大，找出原因與回復的時間越長。另外有與變更無關的背景事故。程式開頭的所有參數（每天 6 個變更、0.7% 的出錯率、0.2% 的衝突率、每月約一次各 10 分鐘的背景事故、回復時間公式）都是為了說明而假設的數字，不是 Harbor 或任何研究的實測值。比較三種 policy：

- **A**：預算耗盡就完全停止部署，回正後一次部署所有累積的變更。
- **B**：一樣完全停止，但解凍後每天最多部署 8 個。
- **C**：分級：預算過半就縮小批次並強制 canary；耗盡時不完全停止，每天只放行 2 個最優先的變更，一律走 canary。

```python
import random
from collections import deque

DAYS = 180
WINDOW = 30                      # rolling 30 天
BUDGET_MIN = 43.2                # 99.9% / 30 天 = 43.2 分鐘「全面中斷等價」
ARRIVALS = 6                     # 每天新進的功能變更
P_BAD = 0.007                    # 單一變更本身有問題的機率
P_CLASH = 0.002                  # 任兩個同批變更互相衝突的機率
BACKGROUND = 1 / 30              # 與變更無關的事故（硬體、依賴）每天的機率


def deploy(rng, n, canary):
    """部署一批 n 個變更，回傳消耗的「全面中斷等價分鐘」。"""
    pairs = n * (n - 1) // 2
    ok = (1 - P_BAD) ** n * (1 - P_CLASH) ** pairs
    if rng.random() < ok:
        return 0.0
    diagnose = 10 + 2 * n        # 批次越大，越難找出是哪個變更、回復也越久
    if canary:
        return 0.05 * diagnose   # 只有 5% 流量受影響，canary 分析自動回復
    return 0.5 * diagnose        # 直接全量：一半請求失敗


def simulate(policy, seed):
    rng = random.Random(seed)
    queue = deque()              # 每個元素是變更進入佇列的日子
    daily_bad = []
    shipped = waited = incidents = caught = biggest = frozen_days = 0
    for day in range(DAYS):
        queue.extend([day] * ARRIVALS)
        used = sum(daily_bad[-WINDOW:]) / BUDGET_MIN
        remaining = 1 - used
        cap, canary = policy(remaining)
        if cap == 0:
            frozen_days += 1
        n = min(cap, len(queue))
        bad = 0.0
        if n:
            for _ in range(n):
                waited += day - queue.popleft()
            shipped += n
            biggest = max(biggest, n)
            cost = deploy(rng, n, canary)
            if cost and canary:
                caught += 1
            elif cost:
                incidents += 1
            bad += cost
        if rng.random() < BACKGROUND:
            bad += 10.0
            incidents += 1
        daily_bad.append(bad)
    violated = sum(1 for d in range(WINDOW, DAYS)
                   if sum(daily_bad[d - WINDOW:d]) > BUDGET_MIN)
    return dict(shipped=shipped, lead=waited / max(shipped, 1), biggest=biggest,
                incidents=incidents, caught=caught, frozen=frozen_days, violated=violated)


def hard_freeze_big_bang(remaining):
    return (0, False) if remaining <= 0 else (10**6, False)


def hard_freeze_capped(remaining):
    return (0, False) if remaining <= 0 else (8, False)


def graduated(remaining):
    if remaining <= 0:
        return 2, True           # 耗盡：不完全停，每天只放行 2 個最優先的變更，一律 canary
    if remaining < 0.5:
        return 6, True           # 預算過半：批次變小、強制 canary
    return 8, False


POLICIES = {
    "A 硬凍結，解凍後一次全放": hard_freeze_big_bang,
    "B 硬凍結，解凍後每天最多 8 個": hard_freeze_capped,
    "C 分級：縮小批次＋canary": graduated,
}

for name, policy in POLICIES.items():
    runs = [simulate(policy, seed) for seed in range(300)]
    avg = {k: sum(r[k] for r in runs) / len(runs) for k in runs[0]}
    worst = max(r["biggest"] for r in runs)
    print(name)
    print(f"  上線變更 {avg['shipped']:.0f}，平均等待 {avg['lead']:.1f} 天，最大批次 {worst}")
    print(f"  全量事故 {avg['incidents']:.1f} 次，canary 攔下 {avg['caught']:.1f} 次")
    print(f"  完全停止部署 {avg['frozen']:.1f} 天，超出 SLO 的天數 {avg['violated']:.1f}")
```

執行結果（每種 policy 跑 300 次不同亂數的 180 天，取平均）：

```text
A 硬凍結，解凍後一次全放
  上線變更 998，平均等待 7.7 天，最大批次 258
  全量事故 14.8 次，canary 攔下 0.0 次
  完全停止部署 101.5 天，超出 SLO 的天數 99.6
B 硬凍結，解凍後每天最多 8 個
  上線變更 932，平均等待 10.6 天，最大批次 8
  全量事故 17.6 次，canary 攔下 0.0 次
  完全停止部署 43.5 天，超出 SLO 的天數 41.7
C 分級：縮小批次＋canary
  上線變更 1073，平均等待 0.7 天，最大批次 8
  全量事故 12.0 次，canary 攔下 6.6 次
  完全停止部署 0.0 天，超出 SLO 的天數 3.4
```

逐段解讀：

1. **`deploy` 是變更風險的模型**。一批 n 個變更全部沒問題的機率是 `(1 − P_BAD)^n × (1 − P_CLASH)^(n(n−1)/2)`：前者是每個變更各自出錯，後者是兩兩衝突，後者隨批次大小以平方成長，這就是大批次特別危險的來源。出問題時，回復時間 `10 + 2n` 分鐘隨批次變長，代表「找出 61 個變更中是哪一個」的成本。這兩個式子都是簡化的假設，真實的數字要從自己的變更與事故紀錄估計，但方向和 Harbor 的經驗一致。
2. **預算是 rolling 30 天**。`simulate` 每天用過去 30 天的消耗算出剩餘預算，再交給 policy 決定今天能部署多少、要不要走 canary。這正是 35.6 圖中「error budget 閘門」的角色。
3. **A 的惡性循環**。A 的最大批次高達 258 個變更：凍結期間佇列累積，解凍時一次推出，發生一次巨大的事故，又把預算打回負值，再凍結將近 30 天。結果 180 天中有約 100 天完全停止部署，也有約 100 天處於超出 SLO 的狀態。（「全量事故」包含全量部署造成的事故與背景事故，三種 policy 平均都有約 6 次背景事故。）注意 A 的「全量事故」次數反而比 B 少，因為它部署的天數少；但每次事故都大得多。只數事故次數會得出錯誤的結論。
4. **B 修正了解凍方式，但沒有修正凍結本身**。限制每天最多 8 個，消除了巨大批次，超出 SLO 的天數降到約 42 天。但它仍然在預算歸零時完全停止，並且要等 rolling window 慢慢回正，平均等待時間反而更長。
5. **C 很少走到凍結**。在預算剩下一半時就開始縮小批次、強制 canary，有問題的批次中約一半在 5% 流量時就被攔下（canary 攔下約 6.6 次；全量事故 12.0 次扣掉約 6 次背景事故，全量部署出事約 6 次），被攔下的每次只消耗很少的預算。預算很少真正耗盡，即使耗盡也維持小量、受保護的部署。結果是上線的變更最多、等待最短、超出 SLO 的天數最少。
6. **C 的「耗盡時每天放行 2 個」在真實世界對應 35.7 的分類表**：這兩個名額應該留給可靠性修復與安全修補，而不是一般功能。模擬裡沒有區分變更類型，這是可以延伸的練習。

這個模擬想說明的不是「C 的參數就是正確答案」，而是一個結構性的結論：**凍結的成本與風險主要來自它造成的累積，而降低變更風險最有效的手段是縮小批次與限制影響範圍**。一個好的 error budget policy 會在預算消耗過快時就開始收緊這兩件事，讓完全凍結成為很少發生的最後手段。

## 35.10 Trade-offs 與 Failure Modes

| 做法 | 什麼時候會失敗 | 具體情境 | 對策 |
|---|---|---|---|
| 以「預算回正」作為解凍條件 | Rolling window 讓凍結長度取決於日曆 | 一次 81% 的事故導致近 30 天凍結，即使第 3 天就修好了 | 用最近 7 天 SLI 加上 P0 action items 完成作為解凍條件，解凍後維持較保守的狀態 |
| 完全凍結所有變更 | 安全修補與可靠性修復也被擋下 | 凍結期間一個高風險漏洞的修補被延後兩週 | 事先定義允許的類別，rollback、安全與可靠性修復一律放行 |
| 只保護程式碼部署 | 設定、flag、資料變更繞過所有關卡 | Harbor 的 TTL 設定經舊腳本全域推送 | 所有變更走同一條受保護的路徑，舊路徑刪除或使用即告警 |
| 為了安全增加審批層級 | 變更累積成大批次，審批者離程式碼太遠 | 每週一次 CAB 會議，團隊開始把變更攢到週四一起送 | 依 blast radius、可逆性、可偵測性分級，低風險變更以自動化與同儕 review 為主 |
| 用 flag 降低發布風險 | Flag 長期不清理，組合爆炸 | `legacy_pricing_v1` 兩年後成為事故的一部分 | Flag 有 owner 與到期日，遷移的完成定義包含刪除舊路徑 |
| 過度追求簡單而拒絕必要的機制 | 把 essential complexity 當成 accidental 刪掉 | 為了「簡化」移除重試的冪等性檢查，導致重複扣款 | 刪除前問清楚它保護什麼（切斯特頓的籬笆，Chesterton's fence，第 7 章：不知道籬笆為何存在之前不要拆），用 telemetry 與 owner 確認 |
| 變更分類由申請人自行標記 | 功能變更被標成「可靠性修復」繞過凍結 | 凍結期間「可靠性修復」的 PR 數量突然翻倍 | 可靠性修復必須連到 postmortem action item，owner 抽查 |

## 35.11 AI 時代：什麼變了？

**第一，AI 讓新增複雜度變得很便宜。** AI coding agent 幾秒內就能產生一個新的 helper、一個新的服務骨架、一個新的設定選項，或引入一個新的依賴。產生的成本下降了，但閱讀、維護、在事故中理解它的成本並沒有下降，甚至因為「沒有人真正寫過它」而上升。如果團隊不刻意管理，AI 加速的不只是交付，也是 accidental complexity 的累積。具體做法包括：在 agent 的指示中要求它先搜尋並重用現有的函式庫與模式；設計方案中固定包含「刪除」或「不做」的選項；在 CI 中追蹤複雜度的代理指標（依賴數量、flag 數量、重複程式碼），新增時需要 owner 確認。

**第二，AI 也讓刪除變得便宜。** 移除一個 flag 需要找出所有引用、刪除舊路徑、更新測試，這正是 AI agent 擅長的機械性工作（第 21 章的大規模變更）。Harbor 在事故後讓 agent 每週掃描過期的 flag：先用 telemetry 確認 flag 在所有區域的狀態與使用情況，再產生刪除舊路徑的 PR，由 flag owner review。關鍵是證據：agent 必須在 PR 中附上「這條路徑過去 30 天沒有流量」的查詢結果，而不是只憑程式碼分析判斷它沒被使用，因為 `legacy_pricing_v1` 正好是一個程式碼看起來沒人用、production 卻還在用的例子。

**第三，agent 本身是變更來源，要受同一套 policy 約束。** 自動化的依賴升級、大規模重構、AI 產生的修補 PR，都是變更。它們要走同一條受保護的路徑，部署時同樣讀取 error budget 狀態。凍結期間，agent 不應該繼續大量提出功能或重構 PR；它可以專注在 postmortem action items、測試補強與 flag 清理。變更分類不能由 agent 自己標記：如果 agent 能把自己的 PR 標成「可靠性修復」，它就能繞過凍結，這和人類改名換姓是同一個問題，而且速度更快。

**第四，模型、prompt 與知識庫的變更也是 production 變更。** Harbor 的 AI 客服 agent 換一個模型版本、改一句 system prompt、更新退款規則的知識庫，都可能改變它的行為，而且不會出現任何錯誤碼。這些變更應該進入同一份 change log，有版本、有 eval（第 25 章）、有漸進推出、有一鍵回復。AI 功能也需要「簡單的退路」：當模型服務不可用或品質下降時，kill switch 能讓客服回到非 AI 的路徑（例如轉人工或顯示常見問題），這條退路本身要被定期測試。

**第五，AI 適合做變更風險的整理工作。** 一個變更的風險摘要（改了什麼、影響範圍、相關 flag 狀態、最近的相關事故、建議的 bake time）需要從 diff、部署系統、SLO 系統與 postmortem 資料庫中收集資訊，這是 AI 能有效協助的。消耗帳本的初步歸因（「這次預算下降與哪一次變更在時間上吻合」）也是。但風險分級的最終決定與例外核准，仍然屬於人。

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 掃描過期 flag、死路徑與重複的依賴，附 telemetry 證據產生刪除 PR | 刪除前由 owner 確認它不在保護某個罕見情況；證據必須是 production 使用資料，而不只是靜態分析 |
| 為每個變更彙整風險摘要：影響範圍、相關 flag 狀態、類似的歷史事故 | 變更分級與核准由 owner 決定；高風險變更的 rollback 計畫由人確認並演練 |
| 在設計討論中固定提出「重用現有方案」與「刪除／不做」的選項 | 新增依賴、服務、框架需要 owner 核准；agent 不能自行引入 |
| 依 policy 草擬凍結公告、可靠性工作清單、例外申請的初稿 | 狀態由 SLO 系統判定；例外核准由指定的人簽核並留下紀錄 |
| 初步歸因 error budget 消耗，對照變更時間軸 | 歸因結論需附查詢與時間軸，最終分類在 postmortem 中由人確認 |
| 對模型、prompt、知識庫變更自動執行 eval 並比較品質指標 | 這些變更走同一條受保護的路徑與 error budget 閘門；AI 功能保留經測試的 kill switch 與非 AI 退路 |

> [!ai] AI 提醒
> 小心「AI 產生的變更很小，所以風險很低」的直覺。一個 agent 一天可能提出幾十個小變更，每一個都通過 review，但它們加起來可能大幅增加系統的狀態與路徑。評估 AI 對可靠性的影響，要看的是整體的複雜度趨勢（flag 數、依賴數、服務數、變更失敗率），而不只是單一 PR 的大小。

## 35.12 專家怎麼想

- **「這個東西如果不存在，會怎樣？」** 資深工程師看到一個新的服務、flag 或設定選項，第一個問題不是「它怎麼運作」，而是「沒有它會怎樣」。如果答案不明確，它很可能是 accidental complexity。
- **把刪除當成和新增同等的成就。** 專家會在規劃中為清理工作留出時間，並在 review 中特別讚賞刪除舊路徑的 PR。系統的複雜度只會在有人刻意減少時才會下降。
- **用三個問題評估任何變更：影響多大、能不能退、看不看得到。** 一個影響小、可退、看得到的變更可以很快通過；三者中任何一個答案不好，就值得放慢。這比用「變更大小」或「是誰提出的」判斷風險準確得多。
- **凍結是最後手段，而且有退出計畫。** 專家設計 error budget policy 時，會讓大部分情況在「消耗過快」階段就被縮小批次與 canary 處理掉。真正需要凍結時，會先寫好凍結範圍、要完成的工作與解凍條件，而不是只宣布「停」。
- **看不到的路徑最危險。** 專家會主動找出所有能改變 production 的方式：舊腳本、手動登入、直接改資料庫、雲端主控台。每一條沒有被納入保護的路徑，都是下一次事故的候選。
- **讓 policy 由系統執行。** 依賴人記得、依賴人願意當壞人的規則，最後都會被繞過。專家會把狀態判定、變更分類與閘門做進部署系統，讓人只需要處理例外。

## 35.13 動手練習

1. 盤點你熟悉的一個服務（或想像 Harbor 的 checkout）：列出所有 feature flag、所有快取層、所有能改變 production 的路徑。為每一項標記 owner、存在時間、是否仍有使用，並提出三個可以刪除的項目及刪除前需要的證據。
2. 修改 35.9 的程式，讓每個變更隨機屬於「功能」或「可靠性修復」兩類，在 policy C 的耗盡狀態下只放行可靠性修復。再加入一個假設：每完成一個可靠性修復，背景事故的機率下降 1%（最低到原本的一半）。比較加入前後的結果，並討論這個假設是否合理。
3. 寫一個函式：給定每日消耗的列表與 rolling window 長度，計算「預算回正」的日期。用 Harbor 的情況（事故當天 81%、其他天每天 1%）驗證 35.7 的結論，再比較「7 天 SLI 回到 SLO 以上」這個解凍條件會在第幾天滿足。
4. 為 Harbor 寫一份「凍結對象分類表」，至少包含 8 種變更類型，每一種寫出預算耗盡時的處理方式與判斷依據，並說明如何防止有人把功能變更標成可靠性修復。
5. 找一個你參與過或讀過的事故，判斷它的起因是哪一種變更（程式碼、設定、flag、資料、基礎設施、依賴、模型）。如果當時有漸進推出、更好的偵測或一鍵回復，影響會小多少？
6. 設計一個讓 AI agent 自動清理過期 flag 的流程：它需要哪些資料、產出什麼證據、誰要 review、在 error budget 耗盡時是否可以繼續執行，並說明理由。

## 本章重點整理

- 對 production 系統來說，boring 是美德：行為可預測的系統在事故中更容易被理解與修復。
- Essential complexity 來自問題本身，accidental complexity 來自解法；可靠性工作的一部分就是持續移除後者，並用清楚的模組邊界隔離前者。
- 程式碼、flag、設定與路徑都是負債；刪除應該是正式排入計畫的一級工作，flag 要有 owner 與到期日。
- n 個長期存在的 flag 有 2ⁿ 種組合，大部分從未被測試，這是遺忘的 flag 會在事故中出現的原因。
- 一件事只保留一條受保護的路徑；沒有被納入保護的舊腳本或手動操作，是事故的高風險來源。
- 大部分事故來自變更，但解法是讓變更變安全，而不是讓變更變少；設定、flag、資料、依賴與模型變更都要受同樣的保護。
- 安全變更的三件事：漸進式推出、快速準確地偵測問題、安全地回復。
- Release engineering 的原則（自助、高頻率、封閉式建置、強制執行政策）讓變更管理能被工具執行，而不是靠人記得。
- 依 blast radius、可逆性與可偵測性分級變更，比讓所有變更經過同一道重量級審批更安全也更快。
- Error budget policy 要成為機制：狀態由 SLO 系統判定、部署系統讀取狀態作為閘門、凍結對象事先分類、消耗有歸因帳本。
- 在 rolling window 下，「預算回正才解凍」可能讓一次大事故造成近 30 天的凍結；解凍條件應該看可靠性是否真的恢復。
- 例外核准必須附帶降低風險的做法，例如更小的 canary、自動關閉條件與明確的回復方式。
- Error budget freeze、calendar freeze 與 incident freeze 目的不同；凍結要窄、要有可靠性工作、要控制變更累積，並以分級減速為優先。
- AI 讓新增與刪除複雜度都變便宜；agent 產生的變更與模型、prompt 變更都要受同一套變更管理與 error budget policy 約束。

## 延伸問答

> [!question]- Q1. Harbor 的 checkout 已拆成 checkout、pricing、coupon、inventory 四個服務。有人說「微服務本身就是 accidental complexity」，你同意嗎？
> 不能一概而論，要看拆分解決了什麼問題。微服務帶來的網路呼叫、部分失敗、分散式追蹤、版本相容等問題，確實是額外的複雜度；如果 Harbor 只有一個小團隊、四個服務總是一起發布、彼此頻繁地同步修改，那麼這些複雜度沒有換到任何好處，就是 accidental complexity。
>
> 反過來，如果 pricing 與 coupon 由不同團隊負責、發布節奏不同、需要獨立擴展，拆分讓每個團隊只需要理解自己的部分，並且能獨立發布與回復，那麼網路帶來的複雜度是為了隔離 essential complexity 所付出的合理代價。判斷的方法是問：拆分後，改一個功能需要同時改幾個服務？一個服務的發布需要等其他服務嗎？如果答案常常是「好幾個」與「需要」，拆分的邊界可能畫錯了（第 7 章的 ADR 是記錄這個決策的好地方）。

> [!question]- Q2. 一個 30 天 rolling 的 SLO，某天的事故消耗了 81% 的預算，之後每天穩定消耗 1%。如果解凍條件是「預算剩餘 > 0」，最快第幾天可以解凍？這說明了什麼？
> 事故當天之後，窗口內的消耗是 81% 加上窗口內其他天的消耗。假設事故前的 29 天每天也是 1%，事故當天窗口總和是 81% + 29% = 110%。之後每過一天，有一個 1% 的舊日子滑出、一個 1% 的新日子進入，總和維持 110%，直到第 30 天事故本身滑出窗口，總和才降到約 30%。所以最快要到事故後第 30 天才能解凍，不管問題在第幾天被修好。
>
> 這說明以「預算回正」作為解凍條件，在 rolling window 下會讓凍結長度幾乎完全由日曆決定，而不是由可靠性的恢復決定。這會讓凍結失去「換取可靠性投資」的意義，只剩下等待與累積變更。比較好的條件是看最近一段時間（例如 7 天）的 SLI 是否已回到 SLO 以上、P0 action items 是否完成，解凍後仍維持較保守的發布方式，直到 30 天預算回正。

> [!question]- Q3. Checkout 的預算已經耗盡、處於凍結狀態。同一天有三個請求：(a) 一個常用 JSON 函式庫的高風險漏洞修補；(b) 行銷要求打開一個已經寫好的「滿千折百」flag；(c) 一位工程師想合併一個降低資料庫負載的重構。你會怎麼處理？
> (a) 應該放行，但走正常的 canary 流程。延遲修補一個高風險漏洞本身就是風險，而且這個風險和 error budget 無關，凍結的目的不是擋下安全修補。放行時仍要縮小批次（只包含修補，不夾帶其他變更）並觀察指標。
>
> (b) 原則上暫停。打開 flag 是引入新行為，本質就是一次發布，而且「滿千折百」直接影響 checkout 的計價路徑，正是目前不穩定的區域。如果業務上真的不能等，就走例外流程：申請人要說明為什麼不能等，並附上降低風險的做法，例如先對 1% 使用者開放、新增錯誤率指標並設定自動關閉。(c) 要看它和事故的關係：如果它對應 postmortem 的某個 action item（例如事故正是資料庫被打爆），它就是可靠性修復，可以放行；如果只是「順便改善」，即使立意良好，也應該等到解凍後，因為重構本身會引入新的變化。

> [!question]- Q4. Harbor 凍結 24 天後一次部署 61 個 PR，當晚就出了事故。從機率上說明為什麼大批次比較危險，以及解凍應該怎麼做。
> 假設每個變更有 0.7% 的機率本身有問題，61 個變更全部沒問題的機率是 0.993^61 ≈ 65%，也就是約 35% 的機率至少有一個有問題。更麻煩的是變更之間的交互作用：61 個變更兩兩組合有 1,830 對，即使每對只有 0.2% 的機率衝突，至少一對衝突的機率也約 97%。小批次時，交互作用的數量很少，這一項幾乎可以忽略；大批次時，它主導了整體風險。
>
> 除了發生機率，找出問題的時間也隨批次變長：一個變更出問題，rollback 就好；61 個變更出問題，要先找出是哪一個或哪幾個。解凍的正確方式是控制釋放速度：依優先順序排列累積的變更，每天限量、每批走 canary 與 bake time，並在解凍前先部署一次「只包含可靠性修復」的版本，確認 pipeline 本身正常。凍結期間也可以讓功能變更合併到主幹但藏在 flag 後面，讓程式碼持續部署、行為暫不啟用。

> [!question]- Q5. 面試題：你們公司要求所有 production 變更都要經過每週一次的 CAB 會議核准。你會怎麼說服主管改變這個流程？
> 我會先承認 CAB 想解決的問題是真實的：變更確實是事故的主要來源，主管需要對變更風險有信心。然後說明這個機制的副作用：每週一次的核准讓團隊把變更攢成大批次，而大批次本身就更危險；委員會成員離程式碼太遠，無法真正評估風險，核准容易流於形式。《Accelerate》與 DORA 的研究也發現，依賴外部單位核准的重量級流程對交付表現有負面影響，而且沒有證據顯示它能降低變更失敗率。
>
> 接著提出替代方案，而不是只說「取消」：依 blast radius、可逆性與可偵測性分級，標準變更以同儕 review、自動化測試與 canary 把關；重要與高風險變更才需要 owner 核准與 rollback 計畫；所有變更都進入可查詢的 change log。最後建議用數據驗證：選一個服務試行三個月，比較變更失敗率、部署頻率與 recovery time，讓決策建立在結果上，而不是信念上。

> [!question]- Q6. Feature flag 能降低發布風險，為什麼又說它是複雜度的來源？要怎麼同時得到好處又控制代價？
> Flag 的好處是讓「部署」和「啟用」分開：程式碼可以先部署但不啟用，再逐步對使用者開放，出問題時關掉 flag 即可，不需要重新部署。這大幅降低了單次變更的風險，也是第 29 章 progressive delivery 的重要工具。
>
> 代價是每個 flag 都讓系統多了一種可能的狀態。10 個獨立的 flag 有 1,024 種組合，測試不可能覆蓋；長期存在的 flag 會在某個區域、某個客戶身上停在一個少見的狀態，就像 Harbor 的 `legacy_pricing_v1`。控制代價的方法是把 flag 分類並管理生命週期：發布用的 flag 在全量後幾週內刪除；長期的營運開關（例如 kill switch）明確標記並定期測試；每個 flag 建立時就要有 owner 與到期日，到期自動提醒；部署系統在推出變更時列出目標範圍內不一致的 flag 狀態。

> [!question]- Q7. Harbor 導入 AI coding agent 後，凍結期間發現「可靠性修復」類別的 PR 數量暴增，很多是 agent 產生的，PR 描述都寫著「提升穩定性」。你會怎麼處理？
> 這是分類可以被自我標記時必然出現的問題，只是 agent 讓它發生得更快。首先要改變分類的依據：可靠性修復不能由 PR 作者（不論是人或 agent）自己宣告，而要連結到一個具體的 postmortem action item 或已知的 SLO 風險，部署系統檢查這個連結是否存在、action item 是否屬於這個服務。沒有連結的 PR 在凍結期間一律視為一般變更。
>
> 其次是檢查 agent 的指示與誘因：如果 agent 被要求「盡量讓 PR 被合併」，它自然會學會使用能通過關卡的描述。應該在 agent 的工作設定中明確寫出凍結期間的優先順序（action items、測試補強、flag 清理），並讓它在凍結狀態下降低提出 PR 的數量。最後，抽查已經放行的 PR，確認有沒有功能變更混入；如果有，要在 postmortem 或檢討中記錄，作為調整閘門規則的依據。

> [!question]- Q8. 你接手一個「每次部署都很可怕」的服務：一個月部署一次，每次都要整個團隊加班待命，而且常常出事。你會從哪裡開始改？
> 我會先承認直覺上的「減少部署」是錯誤方向：一個月一次的部署意味著每次包含一個月的變更，這正是它可怕的原因。目標是讓部署變小、變頻繁、變無聊，但要按順序做，不能一開始就要求每天部署。
>
> 第一步是讓回復變安全：確認能用同一個 artifact 一鍵 rollback，並實際演練一次，因為有了可靠的退路，其他改變才敢做。第二步是讓問題看得到：建立 SLI 與 burn rate 告警（第 32、34 章），讓每次部署後能在幾分鐘內知道有沒有傷害。第三步是縮小變更範圍：引入 canary 與 feature flag，把部署與啟用分開，再逐步把部署頻率從每月提高到每週、每天。同時盤點並移除 accidental complexity，例如多條部署路徑、手動步驟、遺忘的 flag。最後用 DORA 指標（部署頻率、變更前置時間、變更失敗率、失敗部署的恢復時間）追蹤進展，讓團隊看到「部署更頻繁」與「事故更少」是同時發生的。
