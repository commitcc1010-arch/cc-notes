## 30.1 故事：志明的第三百封告警信

Harbor 成立第三年，工程團隊已經有六十多人，分成搜尋、購物車與結帳、賣家後台、物流通知等幾個產品團隊。第 29 章的 delivery 改造很成功：每天有二、三十次部署，canary 會自動攔下大部分的壞版本，release night 成了老員工才懂的笑話。

但有一個人的生活沒有變好，那就是志明。志明是 Harbor 第一位、也是唯一一位「維運工程師」。從公司八個人的時候開始，凡是和機器有關的事都會落到志明頭上：開新機器、調資料庫參數、更新 TLS 憑證、清磁碟、半夜接告警電話、幫客服手動修正卡住的訂單。服務從三個變成二十二個之後，這些工作也跟著變成好幾倍。志明的信箱每週收到三百多封告警信，大部分已經沒人細看，因為十封裡有九封是「磁碟使用率 81%」這類不需要處理的通知。

三月的一個週日下午，Harbor 的 app 突然全面無法連線。原因是主網域的 TLS 憑證過期了。那張憑證是兩年前志明手動申請的，到期提醒寄到了一個已經沒有人看的信箱。修復只花了二十分鐘，但從使用者開始抱怨到有人發現原因，過了將近一個小時。

事後的檢討會上，結帳團隊的阿凱說了一句很多人心裡都在想的話：「我們部署完就不知道後面發生什麼事了。出事都是志明在處理，我們連 production 長什麼樣子都不太清楚。」志明則說：「我每天都在處理一樣的事情，根本沒有時間把它們自動化。再請一個人，也只是兩個人一起處理一樣的事情。」

工程經理 Kevin 意識到，問題不在於志明不夠努力，也不在於人手不夠，而在於整個組織處理 production 的方式。服務越多、部署越快，維運工作就會越多；如果處理方式是「人手一件一件做」，唯一的解法就是不斷加人，而每個新加入的人很快也會被淹沒。

這一章要回答 Kevin 接下來要做的決定：Harbor 需要什麼樣的 production 責任分工？Google 在二十多年前（2003 年前後）遇到同樣的問題，給出的答案叫做 **Site Reliability Engineering**（網站可靠性工程，簡稱 SRE）。在理解 SRE 之前，先看清楚志明每天面對的那個東西：production。

## 30.2 Production 環境：使用者與金錢所在的地方

### Production 和測試環境到底差在哪裡

**Production**（正式環境）是真實使用者、真實資料、真實金錢流動的那個環境。很多新進工程師以為 production 只是「規模比較大的 staging」，但兩者的差別是本質上的：

- **資料是真的，而且會一直累積。** Staging 的資料可以隨時清掉重建；production 的訂單、付款紀錄一旦寫錯，就要花人力修正，有時還有法律責任。
- **流量是不可控制的。** 使用者在什麼時間、以什麼組合、送什麼奇怪的輸入，都不是你決定的。雙十一的流量、爬蟲、惡意請求、某個網紅一則貼文帶來的突發流量，都只在 production 發生。
- **依賴是真的。** 外部金流商、物流商、簡訊服務在 production 中有自己的故障、限流與延遲，staging 通常只接 sandbox 或假的實作。
- **錯誤有後果。** Staging 的 timeout 是一個紅燈；production 的 timeout 可能讓使用者重複付款，或讓賣家錯過出貨時間。
- **它從不停止。** 你不能把 production 關掉來修東西。所有維護動作都必須在系統持續運作的情況下進行，就像在飛行中替飛機換引擎。

### Production 由哪些部分組成

SRE 書第 2 章用 Google 自己的環境介紹 production 的組成：成千上萬台機器組成叢集，由叢集管理系統 Borg 排程工作（Kubernetes 的設計受到 Borg 很大的影響），上面有分散式儲存、鎖服務 Chubby、RPC 框架 Stubby（gRPC 是它的開源後繼者），以及監控系統 Borgmon。書中特別區分了兩個詞：**machine**（機器）是一台實體硬體或 VM，**server**（伺服器）是實作某個服務的一支軟體。一台 machine 上可以跑很多個 server，server 可以被排程到任何 machine 上。這個區分很重要，因為它代表「服務健康」和「機器健康」是兩件事。

Harbor 不是 Google，但它的 production 有相同的結構：

```text
                    使用者（手機 app、瀏覽器）
                              │
                    ┌─────────▼─────────┐
                    │ DNS ─► CDN ─► WAF │  ← 邊緣層：靜態資源、擋惡意流量
                    └─────────┬─────────┘
                              │
             ┌────────────────▼────────────────┐
             │ Load Balancer（跨三個可用區）      │  ← 流量入口（第 37 章）
             └───┬────────────┬────────────┬───┘
                 │            │            │
   ┌─────────────▼────────────▼────────────▼─────────────┐
   │ Kubernetes 叢集（scheduler 決定每個 Pod 跑在哪台機器）   │  ← 運算層
   │  search  cart  checkout  inventory  notification   │
   │  seller  recommendation  AI 客服 agent               │
   └───┬──────────┬───────────┬──────────┬────────────┬──┘
       │          │           │          │            │
   ┌───▼───┐  ┌───▼───┐  ┌────▼────┐ ┌───▼────┐  ┌────▼─────┐
   │ 資料庫 │  │ 快取   │  │ 訊息佇列 │ │物件儲存 │  │ 外部依賴   │  ← 狀態層與依賴
   │ (主從) │  │       │  │         │ │        │  │ 金流 物流  │
   └───────┘  └───────┘  └─────────┘ └────────┘  │ 簡訊 LLM  │
                                                 └──────────┘
   ─────────────────── 控制平面（不處理使用者請求，但能改變一切）───────────────────
   CI/CD pipeline（第 29 章）│ 設定與 feature flag │ 憑證與 secrets │ 身分與權限
   監控、日誌、trace（第 33 章）│ 告警與 on-call（第 34、43 章）│ 容量與成本
```

這張圖由上往下讀，是一個使用者請求的路徑。請求先經過 DNS 找到 Harbor 的位址，經過 CDN 與 WAF（Web Application Firewall，網頁應用防火牆）的過濾，進入跨三個 **availability zone**（可用區，彼此電力與網路獨立的機房）的 load balancer，再被分配到 Kubernetes 叢集裡某個服務的 Pod。服務處理請求時會讀寫資料庫、快取、訊息佇列與物件儲存，也會呼叫外部的金流商、物流商，以及 AI 客服 agent 使用的 LLM API。

圖的最下方是另一個世界：**控制平面**（control plane）。它不處理使用者的請求，但它能改變上面所有東西：pipeline 能部署新版本，設定系統能改變行為，憑證系統決定 HTTPS 能不能建立連線，權限系統決定誰能碰什麼。與之相對，處理使用者請求的那條路徑叫**資料平面**（data plane）。志明的 TLS 憑證事故就發生在控制平面：所有服務都健康，但一張過期的憑證讓整個資料平面失去作用。很多嚴重事故都出自控制平面，因為它的一個錯誤會同時影響所有東西。

### 從維運的角度看 production

對維運者來說，production 不是一張架構圖，而是一連串持續發生的工作：

| 類別 | Harbor 的例子 | 頻率 |
|---|---|---|
| 變更 | 部署、設定修改、資料庫 migration、flag 切換 | 每天數十次 |
| 容量 | 開機器、擴大資料庫、為雙十一預留資源 | 每週到每季 |
| 監控與告警 | 調整門檻、處理告警、檢查儀表板 | 每天 |
| 事故處理 | 半夜被叫起來、止血、協調、事後檢討 | 每月數次 |
| 例行維護 | 更新憑證、修補作業系統、輪替密碼、清理日誌 | 每週 |
| 支援請求 | 客服請工程師修正訂單、賣家要求匯出資料 | 每天 |

這張表裡的每一項都和服務數量、流量、部署頻率成正比。這就是志明的處境：Harbor 成長得越成功，志明的工作就越多。

## 30.3 傳統維運模式：牆的兩邊

### 開發與維運分家

Harbor 目前的模式，是業界存在很久的傳統做法：開發團隊寫程式，**維運團隊**（operations，或 sysadmin，系統管理員）負責讓程式在 production 跑起來。兩邊的技能不同、目標不同，甚至坐在不同的辦公室。開發者把完成的程式「丟過牆」給維運，維運者負責部署、監控、處理事故。

這個模式的好處是直覺：術業有專攻，市場上也有很多有經驗的系統管理員可以招募，工具與流程都很成熟。SRE 書第 1 章分析了它的兩種成本。

**直接成本是人力會隨系統線性成長。** 如果每一個服務、每一千台機器、每一次部署都需要人手操作，維運團隊的規模就必須跟著服務一起長大。對一個快速成長的公司來說，這條成本曲線很快就無法負擔。30.10 節的程式會把這條曲線算出來。

**隱性成本是兩邊的目標互相衝突。** 開發團隊的成功是「推出新功能」，維運團隊的成功是「系統不要出事」。而大部分的事故來自變更，所以對維運者來說，最好的策略就是讓變更越少越好。於是維運開始設立關卡：上線前要填檢查表、要經過審核、每週只能部署一次。開發者則開始繞過關卡：把新功能包裝成「設定變更」、稱它為「beta」、拆成很多個小的「bug 修正」。雙方都在做對自己合理的事，整個組織卻陷入了互相防備的狀態。

> [!example] 例子
> Harbor 去年就發生過這種事。志明要求所有資料庫 schema 變更都要提前一週送審，因為志明被半夜的 migration 事故折磨過太多次。結帳團隊為了趕活動檔期，把一次 schema 變更寫成「應用程式啟動時自動執行」的程式碼，繞過了審核。那次變更在凌晨三點鎖住了訂單表二十分鐘。

### 為什麼加人解決不了

最直覺的解法是「幫志明多請幾個人」。但這只解決了直接成本的一部分，完全沒有處理隱性成本：牆還在，開發者仍然看不到 production，維運者仍然每天手動處理一樣的事。更糟的是，維運工作量會繼續隨著服務成長，今天請兩個人，明年就需要四個。

真正的問題是**回饋迴路斷了**（第 2 章）。寫程式的人看不到程式在 production 的表現，就不會在設計時考慮它的可維運性：沒有加上有意義的日誌、沒有處理依賴失敗的情況、沒有想過要怎麼回退。看得到 production 的人沒有權力也沒有時間改程式，只能用人力去彌補設計上的缺陷。

## 30.4 SRE：讓軟體工程師來設計維運團隊

### 定義

SRE 書第 1 章由 Google 的 Ben Treynor Sloss 撰寫，書中給 SRE 的定義是：**SRE 是當你請一位軟體工程師來設計維運團隊時會發生的事**（"SRE is what happens when you ask a software engineer to design an operations team."）。

這句話的重點在「設計」。軟體工程師面對重複的工作，第一個反應是寫程式讓它自動完成。SRE 團隊的成員具備軟體工程能力，而且被賦予寫程式的時間與責任，所以他們處理 production 的方式和傳統維運不同：不是把同一件事做得更快，而是讓那件事不再需要人做。

SRE 書描述 Google 早期的 SRE 招募：約 50–60% 是符合 Google 一般軟體工程師標準的人，其餘則是非常接近這個標準、同時具備系統管理相關技術能力（例如 Unix 系統內部與網路）的人。重點不是背景，而是這個組合：每個人都既懂軟體也懂系統，而且會因為一再做重複的手動工作而感到無聊，進而想辦法自動化。

> [!example] 例子
> 志明以前每三個月要手動更新一次 Harbor 十幾個網域的 TLS 憑證。傳統維運的改進是「在行事曆上設提醒」。SRE 的做法是寫一個系統：用 ACME 協定自動申請與續約憑證，每天檢查所有對外端點的憑證到期日，剩餘不到 14 天就開 ticket，不到 7 天就發 page。工作從「每三個月做一次」變成「永遠不需要做」，而且再也不會因為某個人離職或某個信箱沒人看而出事。

### SRE 團隊負責什麼

SRE 書列出 SRE 團隊對所負責的服務要處理的面向：**availability**（可用性）、**latency**（延遲）、**performance**（效能）、**efficiency**（效率）、**change management**（變更管理）、**monitoring**（監控）、**emergency response**（緊急應變），以及 **capacity planning**（容量規劃）。書中把 SRE 的原則整理成幾條，每一條在本書中都有專章展開：

| 原則 | 意思 | 本書章節 |
|---|---|---|
| 持續專注在工程 | 維運工作有上限，保留時間做工程改善 | 30.5 節、第 31 章 |
| 在不違反 SLO 的前提下追求最快的變更速度 | 用 error budget 化解開發與穩定的衝突 | 第 32、35 章 |
| 監控 | 由系統判斷問題，只在需要人行動時才通知人 | 第 33、34 章 |
| 緊急應變 | 降低恢復時間，用事先寫好的 playbook 取代臨場發揮 | 第 43、44 章 |
| 變更管理 | 漸進式 rollout、快速偵測、安全回退 | 第 29、35 章 |
| 需求預測與容量規劃 | 確保未來的需求有足夠容量與備援 | 第 36 章 |
| Provisioning（資源配置） | 快速且正確地加入新容量 | 第 36 章 |
| 效率與效能 | 用更少的資源服務同樣的需求 | 第 36 章 |

其中兩個數字值得記住。變更管理方面，SRE 書提到 Google 的經驗是約 70% 的 outage 來自對線上系統的變更，這正是第 29 章所有機制存在的理由。緊急應變方面，書中提到事先把最佳做法寫成 playbook，相較於臨場發揮，恢復時間大約能改善 3 倍。

### 常見誤解

> [!warning] 常見誤解
> 「SRE 就是換了名字的維運。」如果一個團隊叫 SRE，但成員每天都在處理 ticket、沒有時間寫程式，也沒有權力要求開發團隊修正設計，它就只是換了名字的維運。SRE 的核心不是職稱，而是三件事：工程時間有保障、維運工作量有上限，以及 SRE 與開發團隊有共同的目標與工具（SLO 與 error budget）。

另一個誤解是「有了 SRE，開發者就不用管 production 了」。這正好相反。SRE 的機制設計目的之一，就是讓開發者重新看到並承擔 production 的後果，下一節的 safety valve 就是這樣運作的。

## 30.5 50% 上限：保護工程時間的 safety valve

### 機制

SRE 最重要的一條規則是：**SRE 團隊花在「維運工作」上的時間，整體不超過 50%**。這裡的維運工作包括處理 ticket、on-call 值班、手動操作。剩下至少一半的時間，要用在能讓系統更可靠、更自動化的工程專案上。

這條規則需要一個執行機制，否則在忙碌時一定會被犧牲。SRE 書描述的做法是：當維運工作超過上限，多出來的部分**退回給開發團隊**。具體方式是把 bug 和 ticket 重新指派給開發團隊的主管，或讓開發者加入 on-call 輪值，直到維運量回到上限以下。書中把它稱為一個 **safety valve**（安全閥）。

```text
         服務成長、部署變多、新功能上線
                      │
                      ▼
            維運工作量（ticket、page、手動操作）
                      │
          ┌───────────┴───────────┐
          │ 是否超過 SRE 時間的 50%？│
          └───────────┬───────────┘
               否     │      是
        ┌─────────────┴─────────────┐
        ▼                           ▼
  SRE 吸收維運工作             多出來的部分退回開發團隊
  剩下的時間做工程               （ticket 轉給開發、開發者加入 on-call）
        │                           │
        ▼                           ▼
  自動化、簡化、修根因            開發者直接感受到系統的維運成本
        │                           │
        │                           ▼
        │                 優先修正造成維運負擔的設計
        │                           │
        └──────────► 每個服務的維運量下降 ◄──────┘
                              │
                              └──────► 回到最上方：同樣人力能支撐更多服務
```

這張圖是一個回饋迴路，從最上方往下讀。維運工作量來自服務的成長。當工作量在上限之內，SRE 吸收它，並用剩下的時間做工程，降低未來每個服務的維運量。當工作量超過上限，安全閥打開：多出來的工作回到開發團隊身上。這不是懲罰，而是讓成本回到產生它的地方。一個每天產生二十個 page 的服務，當開發者自己也要被叫起來，修正那些造成 page 的設計很快就會變成他們的優先事項。兩條路徑最後都通往同一個結果：每個服務的維運量下降，同樣的人力可以支撐更多服務。

### 為什麼是 50%

50% 不是物理定律，而是一個實務上的平衡點。如果維運時間太少，SRE 會失去對 production 的第一手感覺，做出脫離現實的工具。如果維運時間太多，工程時間不夠，維運量就會隨著服務成長，最後吞掉全部時間，SRE 退化成傳統維運。

另外，這個上限是**整個團隊、一段時間的平均**，不是每個人每週都要剛好一半。值班週的人可能 80% 時間在處理維運，其他週則全力投入專案。重點是長期追蹤這個比例，當它持續上升時要有人注意，並且真的啟動安全閥。

### On-call 的負荷上限

同樣的思維也套用在值班上。SRE 書建議，一個 on-call 班次（8–12 小時）平均**最多兩個事件**。理由是處理一個事件不只是修好它，還包括找出根因、寫 postmortem、規劃後續修正，這些都需要時間。如果每個班次有十個事件，值班者只能救火，永遠不會有時間防止下一場火。反過來，書中也提到如果長期每班次少於一個事件，代表值班安排可能浪費了工程師的時間。第 43 章會詳細討論 on-call 的設計。

> [!note]
> SRE 書把維運工作中「手動、重複、可自動化、沒有長期價值、隨服務線性成長」的那一部分稱為 **toil**（苦工）。不是所有維運工作都是 toil：處理一個從沒見過的事故需要判斷與學習，它是維運工作，但不是 toil。第 31 章會完整定義 toil、示範如何量測它，以及如何逐步把它自動化。

## 30.6 SRE、DevOps 與 platform engineering

讀者在職缺描述裡會同時看到 SRE、DevOps engineer、platform engineer 這幾個職稱，它們經常被混用。它們確實高度重疊，但各自起源於不同的問題。

### DevOps：一個文化運動

**DevOps** 大約在 2009 年前後興起，是一個業界運動，主張打破開發（development）與維運（operations）之間的牆，讓同一群人對軟體從寫程式到 production 運作的整個生命週期負責。它常被概括為幾個面向：文化（共同責任）、自動化、精實流程、量測，以及分享。Amazon 的 CTO Werner Vogels 在 2006 年的一次訪談中說過一句後來被廣泛引用的話：「**You build it, you run it**」，意思是寫服務的團隊也要負責運作它。

DevOps 的長處是方向清楚，短處是它刻意不規定具體做法。「開發與維運共同負責」要怎麼落實？誰值班？維運工作占多少時間？什麼時候該停止發布？每個組織的答案都不同，也有很多組織只是把維運團隊改名為「DevOps 團隊」，牆依然在那裡。

### SRE：DevOps 的一種具體實作

SRE 書第 1 章對兩者的關係有一句說明：可以把 SRE 看成 DevOps 的一種具體實作，再加上一些獨特的延伸。業界也流傳一個程式設計式的比喻：「class SRE implements interface DevOps」。DevOps 說「要共同負責」，SRE 則給出具體的機制：50% 維運上限與 safety valve 定義了責任如何分配，SLO 與 error budget 定義了「穩定」與「速度」如何取捨，postmortem 文化定義了如何從失敗中學習。

### Platform engineering：把常見需求做成自助產品

**Platform engineering**（平台工程）是近幾年才普及的詞，它回答的是另一個問題：當「you build it, you run it」讓每個產品團隊都要自己處理部署、監控、資料庫、憑證時，每個團隊都在重複解決同樣的問題，而且解法品質參差不齊。Platform engineering 的做法是由一個平台團隊建立 **internal developer platform**（內部開發者平台），把這些常見需求做成自助式的產品，並提供 **golden path**（黃金路徑）：一條預設的、受支援的、已經內建最佳實務的做事方式。產品團隊照著 golden path 走，就自動得到 CI/CD、canary、監控、告警與憑證管理。

關鍵是「當成產品」：平台團隊要把其他工程師當成使用者，研究他們的需求、量測使用情況，平台本身也要有 SLO。一個不可靠的平台，會讓所有依賴它的團隊一起不可靠。

### 三者的比較

| | DevOps | SRE | Platform engineering |
|---|---|---|---|
| 本質 | 文化與原則 | 一套具體的可靠性實務與職能 | 把基礎設施能力做成內部產品 |
| 回答的問題 | 開發與維運如何不再對立 | 服務要多可靠、如何用工程手段達成並維持 | 如何讓每個團隊不必重複造輪子 |
| 代表機制 | 共同責任、自動化、you build it you run it | SLO、error budget、50% 上限、blameless postmortem | Internal developer platform、golden path、自助服務 |
| 常見失敗 | 只改職稱，牆還在 | SRE 變成 ticket 處理中心 | 平台沒人用，或強迫大家用不好用的平台 |

在 *Team Topologies*（Matthew Skelton 與 Manuel Pais 的著作）的團隊分類裡，產品團隊是 **stream-aligned team**（對齊價值流的團隊），平台團隊是 **platform team**，而 SRE 團隊可以扮演 **enabling team**（賦能團隊）的角色：協助產品團隊建立可靠性能力，而不是永久替他們做事。

### Harbor 的選擇

這三者不是三選一。Kevin 最後的決定是一個組合：產品團隊對自己的服務負起 production 責任，包括參加 on-call（DevOps 的「you build it, you run it」）；成立一個四人的 SRE 團隊，由志明帶領，負責 SLO、告警設計、事故流程與最關鍵的 checkout 和 payments 服務（SRE 的具體機制）；SRE 團隊同時把重複出現的需求，例如部署 pipeline、憑證自動化、標準儀表板，逐步做成所有團隊都能自助使用的平台（platform engineering 的萌芽）。當 Harbor 長到兩百人時，這個平台會獨立成一個團隊，第 47 章會回到這個演進。

## 30.7 Reliability 是產品功能

### 使用者不會區分「功能壞了」和「服務不可靠」

產品經理 Lisa 在 SRE 團隊成立的會議上問：「可靠性不是工程團隊自己的事嗎？為什麼要在產品規劃裡討論？」

答案是：使用者感受到的是整體體驗。一個使用者在結帳時遇到錯誤，不會去區分這是「新功能的 bug」還是「資料庫的容量問題」，只知道 Harbor 不能用，然後去另一家買。從使用者的角度看，**reliability 就是最基本的功能**：如果服務不可用，其他所有功能都等於不存在。而且可靠性的損失不只是當下那一筆交易，還有信任。一個使用者被重複扣款一次，可能就再也不會把信用卡資料留在 Harbor。

### 把可靠性寫進產品需求

既然是功能，就應該像其他功能一樣被規劃、被取捨、被付錢。Harbor 開始在每份產品需求文件裡加一段「可靠性需求」，由 Lisa 和工程團隊一起填：

| 問題 | 結帳流程的答案 | 個人化推薦的答案 |
|---|---|---|
| 使用者對失敗有多敏感？ | 非常敏感，失敗等於失去訂單，重複扣款會失去信任 | 不敏感，推薦區塊空白時頁面仍可使用 |
| 失敗時的替代方案？ | 無，必須能完成 | 顯示熱門商品清單 |
| 能接受慢多少？ | 超過 3 秒使用者開始放棄 | 可以延後載入 |
| 失敗的成本？ | 每分鐘數萬元營收、客服量、信任 | 轉換率小幅下降 |
| 值得多少投資？ | 多區域備援、嚴格的變更流程 | 一般的 rolling update 即可 |

這張表讓「多可靠」變成一個可以討論的產品決策，而不是工程師各自的直覺。它也揭示了一件重要的事：**不同的功能需要不同程度的可靠性**。把推薦服務做得和結帳一樣可靠，是浪費；把結帳做得和推薦一樣隨便，是災難。

> [!warning] 常見誤解
> 「可靠性越高越好，所以應該盡量提高。」可靠性和其他功能一樣有成本，而且成本是非線性的。每多一個 9，所需的投資可能翻好幾倍，同時也會讓變更速度變慢。下一節會用具體的數字說明這件事。

## 30.8 Embracing risk：多可靠才夠

### 為什麼不追求 100%

SRE 書第 3 章的標題是〈Embracing Risk〉（擁抱風險）。核心論點是：追求 100% 的可靠性不但做不到，而且是錯誤的目標。使用者連到 Harbor 要經過手機、電信網路、家用 Wi-Fi，這些環節本身就不是 100% 可靠，Harbor 從 99.99% 提升到 99.999%，使用者幾乎感受不到；但這個提升的成本極高，而且需要大幅減少變更。第 32 章會把這個論點展開成 SLO 的完整方法，這裡先聚焦在一個更根本的問題：怎麼判斷一個服務能接受多少風險。

### 怎麼量測風險

要討論「多可靠」，先要有量測方式。SRE 書介紹了兩種：

```text
時間式可用性（time-based availability）
  availability = uptime / (uptime + downtime)
  例：一個月 30 天，停機 43 分鐘 → (43,200 − 43) / 43,200 ≈ 99.9%

請求式可用性（aggregate availability）
  availability = 成功的請求數 / 總請求數
  例：一天 250 萬個請求，失敗 250 個 → 99.99%
```

時間式的算法直觀，適合單一系統，但對於 Harbor 這種分散在多個可用區的服務不太合用：幾乎任何時候，總有一部分流量被正常處理，很少出現「整個服務完全停機」這種乾淨的狀態。SRE 書說明 Google 因此多半使用請求成功率。第 32 章會用 SLI 的形式把它精確化。

### 一個服務能承受多少風險

SRE 書列出判斷**消費者服務**風險容忍度時要問的幾個問題。用 Harbor 的結帳服務來回答：

- **使用者期待什麼可用性？** 結帳是付錢的地方，使用者期待它「幾乎總是能用」。服務是否直接與營收連動、是付費還是免費、競爭對手做到什麼程度，都會影響這個期待。
- **哪種失敗比較能接受？** 持續少量的錯誤（每一千筆失敗一筆，使用者重試就好）和偶爾一次完全中斷（整整二十分鐘不能結帳），對使用者的影響不同。對 Harbor 來說，任何會洩漏個人資料或造成重複扣款的失敗都是不可接受的，不管多罕見。
- **成本是多少？** 下一小節計算。
- **還有哪些指標重要？** 可用性不是唯一的維度。搜尋的使用者對延遲很敏感；結帳的使用者對正確性（金額算對、不重複扣款）比對速度更敏感。

**基礎設施服務**的判斷更複雜，因為它的使用者是其他服務，而且不同使用者的需求可能完全相反。SRE 書以 Bigtable 為例：有的使用者需要低延遲（線上服務），希望請求佇列幾乎永遠是空的；有的使用者需要高吞吐量（離線分析），希望佇列永遠有東西可做、機器被充分利用。用同一套叢集同時滿足兩者，成本極高。Google 的做法是分成兩類叢集：低延遲叢集保留大量閒置容量與備援，吞吐量叢集則跑得很滿、備援較少，成本只有前者的一部分。關鍵是讓服務等級**明確化**，讓使用者選擇剛好滿足需求的、最便宜的那一種。

Harbor 也遇到同樣的情況：訂單資料庫同時服務結帳（需要低延遲）和每天晚上的營收報表（需要大量掃描）。報表查詢一跑起來，結帳的延遲就上升。解法和 Bigtable 一樣：把報表移到一個專用的唯讀副本，兩種需求各自有不同的可靠性與成本。

### 多一個 9 值多少錢

SRE 書提供了一個簡單的估算方式：把可用性的提升乘以服務的營收，得到這個提升最多能挽回多少價值，再和它的成本比較。

```text
Harbor 結帳每月經手的交易額：NT$60,000,000（假設不可用期間的交易全部流失）

從 99.5% 提升到 99.9%：
  可挽回 = (0.999 − 0.995) × 60,000,000 = NT$240,000／月
  所需投資：自動 failover、更好的告警，約 NT$150,000／月 → 值得

從 99.9% 提升到 99.99%：
  可挽回 = (0.9999 − 0.999) × 60,000,000 = NT$54,000／月
  所需投資：多區域主動備援、更嚴格的變更流程，約 NT$900,000／月 → 不值得
```

這是一個刻意簡化的模型。它假設不可用期間的交易全部流失，實際上很多使用者會稍後重試，所以真實的損失更小；但它也忽略了信任損失與品牌影響，這部分可能讓損失更大。即使不精確，這個計算仍然很有用：它把「要不要多一個 9」從信仰問題變成一個可以討論的數字，而且通常會揭露一件事，越往上的 9 越昂貴，挽回的價值卻越少。

### 開發與 SRE 的張力，以及 error budget 的預告

就算算清楚了，開發團隊與 SRE 團隊仍然會在日常決策上拉扯。SRE 書列出幾個典型的爭議點：程式要多能容錯（太少則脆弱，太多則沒人想用）、測試要做多少（太少會出事，太多會錯失市場）、多常部署（每次部署都有風險）、canary 要跑多久、多大（第 29 章）。這些問題沒有放諸四海皆準的答案，如果每次都靠開會辯論，結果往往取決於誰的職位高或誰的嗓門大。

SRE 書第 1 章開頭引用了一句「傳統 SRE 格言」：「**Hope is not a strategy**」（希望不是一種策略）。它的解法是把這些爭議交給一個雙方事先同意的、客觀的數字：**error budget**。服務的可靠性目標訂在 99.9%，就代表允許 0.1% 的失敗，這 0.1% 是開發團隊可以用來承擔風險的預算。預算還有，就可以更快部署、做更多實驗；預算快用完，就放慢腳步、投資可靠性。決策從政治問題變成數學問題。第 32 章會完整說明如何定義 SLI、選擇 SLO、計算並使用 error budget。

## 30.9 SRE 如何和服務團隊合作：engagement 模式預告

Harbor 只有四位 SRE，卻有二十二個服務。SRE 不可能深入每一個服務，所以必須決定**和誰合作、用什麼方式合作**。這叫做 SRE 的 **engagement model**（參與模式）。SRE 書第 32 章描述了 Google 的模式如何從「上線前做一次 PRR」演進到更早期的參與，再到把最佳實務做成框架與平台；加上業界常見的派駐與顧問形式，可以整理成以下幾種：

| 模式 | 怎麼運作 | 適合 | Harbor 的例子 |
|---|---|---|---|
| **完整支援**（SRE 承接 on-call） | 服務達到標準後，SRE 接手主要的 on-call 與可靠性工作 | 最關鍵、規模最大的服務 | checkout、payments |
| **Embedded**（派駐） | 一位 SRE 暫時加入產品團隊幾個月，協助建立 SLO、告警與 runbook | 正在快速成長或剛出過大事故的服務 | 物流通知服務 |
| **Consulting**（顧問） | SRE 提供諮詢、設計審查，產品團隊自己運作服務 | 大部分中等重要的服務 | 賣家後台、推薦 |
| **Production readiness review**（PRR，上線準備度審查） | SRE 在服務上線或交接前，檢查監控、容量、回退、依賴等項目 | 新服務、重大改版 | 即將上線的 AI 退款功能 |
| **Platform**（平台） | SRE 把最佳實務做成框架與平台，服務照著用就自動具備可靠性基礎 | 所有服務 | 標準 pipeline、憑證自動化 |

這些模式有一個共同的前提：**SRE 的支援不是無條件的**。如果一個服務持續產生超過上限的維運量，而產品團隊不願意投入修正，SRE 可以把 on-call 交還給產品團隊，這叫做 **hand-back**（交還）。這是 safety valve 在組織層級的版本，它讓雙方都有動機維持服務的可維運性。

Kevin 在 SRE 團隊成立時和各團隊主管約定了幾件事：SRE 承接 checkout 與 payments 的主要 on-call，但前提是這兩個服務要通過 PRR；其他團隊自己值班，SRE 提供告警設計與 runbook 的協助；每季檢討一次 SRE 的時間分配與各服務的維運量。第 46 章會詳細說明 PRR 與 launch checklist，第 47 章會說明 engagement 模式在大型組織中的完整樣貌。

## 30.10 動手寫：維運工作量會不會吞掉整個團隊

下面的程式比較三種組織方式在 Harbor 服務成長下的表現。假設每個服務一開始每週需要 6 小時的人工維運，服務數量每季增加。模式 A 是傳統維運：所有維運工作由維運團隊吸收，不夠就加人。模式 B 與 C 是 SRE：四位 SRE、50% 上限，超出的部分退回開發團隊，工程時間用來降低每個服務的維運量；B 的自動化效果好，C 的自動化做得很慢。最後再用 30.8 節的方法估算「多一個 9」值不值得。

```python
import math

TEAM_HOURS = 4 * 40          # 4 位 SRE，每週 160 小時
OPS_CAP = 0.5                # 維運工作上限 50%
SERVICES = [8, 12, 16, 22, 30, 40]
TOIL_PER_SERVICE = 6.0       # 起始：每個服務每週需要 6 小時人工維運


def traditional_ops():
    """傳統做法：維運量全部由維運團隊吸收，不夠就加人。"""
    print("A. 傳統維運：人工處理一切，不夠就加人")
    for q, s in enumerate(SERVICES, 1):
        ops = s * TOIL_PER_SERVICE
        print(f"  Q{q} 服務 {s:2d}｜維運 {ops:5.1f}h/週｜需要 {math.ceil(ops / 40)} 人專職維運")
    print()


def sre_model(label, automation_gain):
    """SRE 做法：維運上限 50%，超出退回開發；工程時間用來降低每個服務的 toil。"""
    print(label)
    per_service = TOIL_PER_SERVICE
    for q, s in enumerate(SERVICES, 1):
        ops = s * per_service
        sre_ops = min(ops, TEAM_HOURS * OPS_CAP)
        overflow = ops - sre_ops                     # 超過上限的部分交回開發團隊
        eng = TEAM_HOURS - sre_ops
        print(f"  Q{q} 服務 {s:2d}｜維運 {ops:5.1f}h/週｜SRE 維運占比 {sre_ops / TEAM_HOURS:4.0%}"
              f"｜工程 {eng:5.1f}h｜退回開發 {overflow:4.1f}h")
        # 工程時間越多，下一季每個服務的 toil 降得越多
        per_service *= 1 - automation_gain * eng / TEAM_HOURS
    print()


def value_of_nines(revenue, current, target, cost):
    gained = (target - current) * revenue        # 假設不可用期間的交易全部流失
    verdict = "值得" if gained > cost else "不值得"
    print(f"{current:.2%} → {target:.2%}：每月最多挽回 NT${gained:,.0f}，"
          f"額外成本 NT${cost:,.0f}，{verdict}")


traditional_ops()
sre_model("B. SRE：守住 50% 上限，自動化效果好", automation_gain=0.4)
sre_model("C. SRE：守住 50% 上限，但自動化做得很慢", automation_gain=0.05)
value_of_nines(60_000_000, 0.995, 0.999, cost=150_000)
value_of_nines(60_000_000, 0.999, 0.9999, cost=900_000)
```

逐段解讀：

1. **模式 A 的維運量和服務數量完全成正比。** 服務從 8 個變成 40 個，維運時數從 48 小時變成 240 小時，需要的專職人力從 2 人變成 6 人。這就是 30.3 節說的直接成本：人力隨系統線性成長。而且這還沒算上隱性成本，那 6 個人和開發團隊之間的牆依然存在。
2. **模式 B 的維運總量幾乎不變。** 服務數量變成五倍，維運時數卻一直維持在 50 小時左右，因為 SRE 每季都有超過 100 小時的工程時間，用來把每個服務的維運量壓低。這是 SRE 的核心賭注：工程投資的效果會累積，而人工操作不會。
3. **模式 C 顯示安全閥如何運作。** 自動化做得慢，維運量從第三季開始超過上限，多出來的部分（10 小時、40 小時、一直到 128 小時）退回開發團隊。注意 SRE 的工程時間始終維持在 80 小時，沒有被吞掉。退回的工作會讓開發團隊直接感受到成本，這是組織層級的訊號：要嘛投入改善這些服務的可維運性，要嘛調整 SRE 的工作重點。如果沒有這個上限，模式 C 的 SRE 會把工程時間一路讓給救火，自動化更慢、維運量更快上升，大約在第五季就全部時間都在處理維運，退化成模式 A。
4. **`automation_gain` 是一個刻意簡化的假設。** 它代表「每小時的工程投入能降低多少維運量」。現實中這個效果差異極大：自動化憑證更新可能一次消除一整類工作，寫一個沒人用的工具則毫無效果。第 31 章會說明如何量測 toil、挑選最值得自動化的工作。
5. **`value_of_nines` 把 30.8 節的估算寫成程式。** 從 99.5% 到 99.9% 挽回的價值大於成本；從 99.9% 到 99.99%，可用性只提升了 0.09 個百分點，挽回的價值很小，成本卻高得多。真實的決策還要考慮使用者重試、信任損失與合約責任，但這個計算給了討論一個起點。

## 30.11 Trade-offs 與 Failure Modes

| 做法 | 什麼情況下會失敗 | 具體情境 | 對策 |
|---|---|---|---|
| 成立 SRE 團隊但不給工程時間 | SRE 變成換了名字的維運團隊 | SRE 每天處理產品團隊丟來的 ticket，從來沒有時間做自動化，半年後兩位成員離職 | 追蹤維運時間比例，超過上限時真的啟動 safety valve |
| Safety valve 只寫在文件上 | 上限被忽略，開發團隊從不感受維運成本 | 維運量超標三個月，但主管認為「把 ticket 轉回開發會影響功能進度」而作罷 | 由工程主管事先簽署，並在每季檢討中呈現維運量與退回情況 |
| 「You build it, you run it」但沒有平台支援 | 每個團隊重複造輪子，可靠性參差不齊 | 八個產品團隊各自寫了八套部署腳本與告警設定，其中三套沒有 rollback | 把常見需求做成 golden path，讓正確的做法也是最省力的做法 |
| 平台團隊閉門造車 | 平台沒人用，或強迫大家用不好用的東西 | 平台團隊花半年做了一個新部署系統，但它不支援 canary，產品團隊繼續用舊腳本 | 把平台當成產品：訪談使用者、量測採用率、平台本身有 SLO |
| SRE 只用 uptime 被評價 | SRE 傾向阻止所有變更 | SRE 的考核是「全年零重大事故」，於是開始要求每次部署都要一週前送審 | 用 SLO 與 error budget 評價，同時追蹤變更速度（第 29 章的 DORA 指標） |
| 把所有維運工作都當成該消除的 toil | 失去對 production 的理解，忽略需要判斷的工作 | SRE 把所有事故處理都外包給自動化與值班手冊，遇到新型事故時沒有人知道系統怎麼運作 | 分辨 toil 與有價值的維運工作；保留 SRE 直接接觸 production 的機會 |
| SRE 支援所有服務 | 力量分散，每個服務都只得到很淺的幫助 | 四位 SRE 平均分配給二十二個服務，最重要的 checkout 只分到幾小時 | 依服務重要性選擇 engagement 模式，最關鍵的服務完整支援，其他以顧問與平台為主 |

## 30.12 AI 時代：什麼變了？

AI 從三個方向改變了 production 與 SRE 的工作。

**第一，production 裡多了新的元件，也多了新的失敗方式。** Harbor 的 AI 客服 agent 是一個 production 服務，但它和其他服務不太一樣。它依賴外部的 LLM API，這個依賴有自己的延遲、限流與故障，而且回應時間可能是一般 API 的數十倍；它的成本隨使用量變動，一個迴圈錯誤可能在幾小時內燒掉一個月的預算；它的行為由 prompt、模型版本、知識庫內容共同決定，任何一項變更都可能讓品質下降，卻不會產生錯誤碼；最重要的是，它能呼叫工具，例如發起退款，這代表它的錯誤會直接造成金錢損失。對 SRE 來說，這些都是新的可靠性維度：除了可用性與延遲，還要看成本、品質、安全（第 32 章的 AI SLI）。30.2 節的 production 圖裡，外部依賴那一格寫著「LLM」，控制平面也多了 prompt 與模型版本的管理。

**第二，AI 可以承擔維運工作中資訊整理的部分。** 值班時最花時間的往往不是修復動作本身，而是搜集資訊：哪個服務先出問題、最近有什麼變更、log 裡出現什麼新錯誤、過去有沒有類似的事故。AI agent 很適合做這種跨來源的關聯整理，並產生一份調查摘要給值班者。它也能把大量重複的 ticket 分群，找出最值得自動化的那一類，讓第 31 章的 toil 量測更容易進行。

**第三，AI 讓「把 toil 做快」變得太容易，可能掩蓋「讓 toil 消失」的需要。** 這是 SRE 思維在 AI 時代最需要堅守的地方。如果 Harbor 每週有五十張「修正卡住的訂單」的 ticket，AI agent 可以自動處理它們，ticket 數量就從儀表板上消失了。但造成訂單卡住的 bug 還在，而且現在有一個 agent 每週對 production 資料庫執行五十次寫入操作。SRE 的問題應該是：為什麼訂單會卡住？能不能修好那個 bug，讓這類 ticket 根本不再出現？

| 適合交給 AI 的工作 | 必須保留的人類判斷與 guardrails |
|---|---|
| 事故發生時，彙整 log、指標、trace、最近變更與相似歷史事故，產生調查摘要 | 摘要中的每個結論都要能連回原始資料；值班者決定要採取什麼行動 |
| 把一段時間內的 ticket 與 page 分群，估計各類工作的時數，找出 toil 熱點 | 決定要投資自動化、修正根因，還是接受現狀，由服務 owner 與 SRE 共同判斷 |
| 以唯讀權限執行標準健康檢查，並導覽 runbook 的下一步 | 任何會改變 production 的動作，預設需要人類核准；agent 使用專用身分與最小權限 |
| 草擬 PRR 檢查結果、postmortem 初稿與 action item 清單 | 嚴重度判定、責任分配、是否接手或交還 on-call，由人決定 |
| 為 AI 客服 agent 監控成本、轉人工比例、工具錯誤率等指標，並偵測異常 | 退款等有金錢後果的工具要有單筆與總額上限、可隨時關閉的 kill switch，以及獨立於 agent 的稽核紀錄 |

導入 AI 維運 agent 時，Harbor 採取逐步授權的順序：先只讀，產生摘要與建議；接著在人類核准下執行少數已驗證的 runbook 動作；只有在動作可逆、影響範圍有限、而且過去建議的準確度經過量測之後，才考慮讓 agent 自主執行。第 31 章會把這個順序整理成自動化的層次，附錄 C 則有完整的 AI 授權等級。

> [!ai] AI 提醒
> 不要用「AI 處理了多少 ticket」或「省下多少小時」來衡量 AI 維運的成效。這兩個數字會獎勵把 toil 做快，而不是讓 toil 消失。更好的指標是：每個服務的維運量是否持續下降、AI 建議的錯誤率、人類需要接手或推翻的比例，以及 AI 動作是否曾經造成或擴大事故。

## 30.13 專家怎麼想

- **「這件事做第三次之前，能不能讓它不再需要做？」** 資深 SRE 對重複的手動工作有一種本能的不耐煩。他們不會問「怎麼做得更快」，而會問「為什麼需要做」。第一次手動做是為了理解，第二次是確認模式，第三次之前就應該有自動化或根因修正的計畫。
- **看維運時間比例，而不只看事故數。** 事故數少可能只是運氣好，維運時間比例持續上升則是結構性的警訊。專家會定期看這個數字，並在它接近上限之前就開始討論。
- **成本要回到產生它的地方。** Safety valve 與 hand-back 的設計不是為了懲罰誰，而是讓做決策的人感受到決策的後果。專家會檢查組織裡的回饋迴路是否完整：寫程式的人能不能看到程式在 production 的表現？
- **每個服務都問「多可靠才夠」，而不是「越可靠越好」。** 專家會先問使用者對失敗有多敏感、失敗時有沒有替代方案、多一個 9 值多少錢，再決定投資多少。他們也會注意同一個基礎設施上，不同使用者的需求可能完全相反。
- **注意控制平面。** 很多最嚴重的事故不是因為處理請求的服務壞了，而是因為部署系統、設定系統、憑證或權限出錯。專家會特別關心「什麼東西能同時改變所有服務」，並確保它們有和資料平面同樣嚴格的變更流程。
- **職稱不重要，機制才重要。** 判斷一個組織有沒有在實踐 SRE，不是看它有沒有叫 SRE 的團隊，而是看它有沒有工程時間的保障、維運量的上限，以及開發與維運共同遵守的可靠性目標。

## 本章重點整理

- Production 是真實使用者、資料與金錢所在的環境，它的資料會累積、流量不可控、依賴是真的、錯誤有後果，而且從不停止。
- Production 由資料平面（處理使用者請求）與控制平面（部署、設定、憑證、權限、監控）組成；控制平面的錯誤常會同時影響所有服務。
- 傳統的開發／維運分家有兩種成本：人力隨系統線性成長，以及兩邊目標衝突造成的互相防備。加人只能處理前者的一部分。
- SRE 的定義是「請軟體工程師設計維運團隊時會發生的事」：用工程手段讓重複的維運工作不再需要人做。
- SRE 團隊負責服務的可用性、延遲、效能、效率、變更管理、監控、緊急應變與容量規劃。
- SRE 的維運工作整體不超過 50%；超出的部分透過 safety valve 退回開發團隊，讓成本回到產生它的地方。
- 一個 on-call 班次平均最多兩個事件，才有時間做根因分析與後續改善。
- DevOps 是打破開發與維運隔閡的文化運動；SRE 是它的一種具體實作；platform engineering 則把常見的基礎設施需求做成自助的內部產品。三者可以組合使用。
- Reliability 是最基本的產品功能，應該和其他功能一樣被規劃、取捨與投資；不同功能需要不同程度的可靠性。
- 100% 可靠是錯誤的目標；每多一個 9，成本上升、挽回的價值卻變少，可以用「可用性提升 × 營收」與成本比較來估算。
- 判斷風險容忍度要看使用者期待、失敗類型、成本與其他重要指標；基礎設施服務的不同使用者可能需要完全相反的服務等級。
- Error budget 把開發速度與穩定性的爭論交給一個事先同意的客觀數字，這是第 32 章的主題。
- SRE 依服務的重要性選擇 engagement 模式（完整支援、派駐、顧問、PRR、平台），而且支援是有條件的，必要時可以交還 on-call。
- AI 讓 production 多了新的依賴與失敗方式，也能承擔維運中的資訊整理；但要警惕用 AI 把 toil 做快，而忘了讓 toil 消失。

## 延伸問答

> [!question]- Q1. SRE 和傳統的維運團隊，最本質的差別是什麼？
> 最本質的差別是處理重複工作的方式，以及支撐這種方式的機制。傳統維運面對重複的工作，會把它做得更熟練、寫成操作手冊、請更多人來做；SRE 面對重複的工作，會寫程式讓它自動完成，或修改系統讓它不再發生。這就是「請軟體工程師設計維運團隊」的意思。
>
> 但光有工程能力不夠，還需要機制保護工程時間。50% 維運上限確保 SRE 有時間做工程，safety valve 確保超出的維運量會回到開發團隊、而不是吞掉 SRE 的時間，SLO 與 error budget 則讓 SRE 與開發團隊有共同的目標，而不是一方追求功能、一方追求零變更。如果一個團隊叫 SRE 卻沒有這些機制，它實際上仍然是傳統維運。

> [!question]- Q2. DevOps、SRE、platform engineering 是互相競爭的做法嗎？一個新創該選哪一個？
> 它們不是互相競爭的，而是回答不同層次的問題。DevOps 是一組原則：開發與維運要共同負責整個生命週期。SRE 是實踐這些原則的一套具體機制：SLO、error budget、維運上限、blameless postmortem。Platform engineering 則解決規模問題：當每個團隊都要自己運作服務時，把共通的需求做成自助平台，避免大家重複造輪子。
>
> 對一個小新創來說，最實際的起點通常是 DevOps 的原則加上少數 SRE 的機制：寫服務的人負責值班，並為最重要的使用者旅程定義 SLO。等到團隊變多、重複的基礎設施工作明顯增加，再考慮成立專門的 SRE 或平台團隊。過早成立大型平台團隊，可能做出沒人需要的東西；太晚則每個團隊都在用不同的方式解決同樣的問題。

> [!question]- Q3. 你是 Harbor 的 SRE 主管。過去三個月，SRE 團隊的維運時間比例從 35% 升到 62%，主要來自賣家後台的 ticket。產品主管說這一季要趕新功能，不能分人力處理。你會怎麼做？
> 首先確認數據：62% 是整個團隊的平均，還是集中在少數人身上？賣家後台的 ticket 是哪幾類、各占多少時數？這些資訊會讓後面的討論具體，而不是變成「SRE 很忙」對「產品很忙」的爭執。
>
> 接著依照事先約定的 safety valve 處理：把超過上限的那部分 ticket 重新指派給賣家後台團隊，或讓他們的工程師加入處理這類 ticket 的輪值。這不是懲罰，而是讓成本回到產生它的地方。產品團隊直接感受到這些 ticket 的負擔後，通常會發現修正根因比持續處理更便宜。如果產品主管仍然反對，這就是一個需要往上呈報的取捨：要嘛接受 SRE 的工程工作停擺（以及長期的可靠性風險），要嘛暫時調整功能進度。重要的是這個決定要被明確地做出並記錄，而不是讓上限默默失效。如果這種情況經常發生，代表 safety valve 沒有被組織真正接受，需要在下一次 engagement 檢討中重新談。

> [!question]- Q4. 計算題：Harbor 的搜尋服務每月帶來約 NT$20,000,000 的成交額（假設搜尋不可用時有一半的使用者會改用分類瀏覽完成購買）。把搜尋從 99.9% 提升到 99.95% 需要每月多花 NT$30,000。值得嗎？
> 可用性提升 0.05 個百分點，也就是 0.0005。如果不可用期間的成交全部流失，最多可挽回 0.0005 × 20,000,000 = NT$10,000。但題目說有一半的使用者會改用分類瀏覽完成購買，真正流失的只有一半，所以可挽回的價值約 NT$5,000。這遠低於每月 NT$30,000 的成本，單從這個計算看並不值得。
>
> 不過，計算只是起點。還要問：搜尋的失敗是否集中在某些關鍵時段（例如雙十一），那時的損失遠高於平均？搜尋失敗是否影響使用者信任與回訪率？有沒有更便宜的方法提升使用者體驗，例如搜尋失敗時自動導向熱門分類？這個例子也說明了降級設計的價值：正因為有分類瀏覽作為替代方案，搜尋本身不需要極高的可靠性。

> [!question]- Q5. 為什麼說「控制平面的錯誤常常比資料平面的錯誤更嚴重」？請舉一個 Harbor 可能發生的例子。
> 資料平面的錯誤通常有局部性：一個服務的某個版本出錯，影響的是那個服務的部分流量，而且 canary、load balancer 的健康檢查等機制可以把它隔離。控制平面的元件則能同時改變所有服務，它的一個錯誤會繞過這些局部防護，一次影響全部。
>
> Harbor 的 TLS 憑證過期就是例子：所有服務都在正常運作，但一張過期的憑證讓所有使用者都無法建立連線。其他可能的例子包括：一次錯誤的設定推送把所有服務的資料庫連線池上限設成 1；權限系統的變更讓所有服務失去讀取 secrets 的權限；部署 pipeline 的 bug 把同一個錯誤版本同時推到所有可用區。對策是讓控制平面的變更也走漸進式 rollout、有 canary 與快速回退，並且特別監控「會在某個時間點同時失效」的東西，例如憑證、密碼、授權的到期日。

> [!question]- Q6. 有人說「有了 SRE，開發者就可以專心寫功能，不用管 production」。這個想法有什麼問題？
> 這個想法會重建 SRE 想要拆掉的那道牆。如果開發者完全不接觸 production，他們就看不到自己的設計在真實環境中造成什麼後果：哪段程式碼一直產生告警、哪個依賴的失敗沒被處理、哪個功能讓資料庫半夜被鎖住。沒有這些回饋，他們會繼續寫出難以維運的程式，SRE 則永遠在替這些設計收拾殘局。
>
> SRE 的機制刻意讓開發者保持與 production 的連結。Safety valve 讓超出上限的維運工作回到開發團隊；error budget 讓開發者的發布速度直接與服務的可靠性掛鉤；postmortem 的 action item 經常指派給開發團隊；hand-back 讓不願意投入可靠性的服務失去 SRE 的支援。SRE 是開發團隊的合作者與放大器，不是讓他們可以不負責的保險。

> [!question]- Q7. Harbor 打算導入一個 AI 維運 agent 處理「修正卡住的訂單」這類 ticket，預估每週能省下 20 小時。你會在導入前問哪些問題？
> 第一個問題是：為什麼訂單會卡住？如果原因是一個已知的 bug，修正它可能比導入 agent 更便宜，而且能讓這類 ticket 永遠消失。AI agent 把 toil 做快，但不會讓 toil 消失，甚至可能讓團隊失去修正根因的動機，因為 ticket 不再出現在任何人的待辦清單上。
>
> 如果確定短期內無法修正根因，接下來要問安全性：agent 需要什麼權限？它會直接寫入 production 資料庫嗎？如果判斷錯誤，最壞會發生什麼事，例如把一筆正常的訂單標成取消？有沒有單次與總量的上限、可以隨時停止的開關、獨立於 agent 的稽核紀錄？然後是量測：要怎麼知道 agent 處理得對？應該先以唯讀模式運作一段時間，讓它提出修正建議、由人執行，量測建議的準確度，再逐步授權。最後，成效不應該只用「省下 20 小時」衡量，還要追蹤錯誤處理的比例、人工推翻的次數，以及這類 ticket 的總量是否在下降。

> [!question]- Q8. 面試題：如果你加入一個沒有 SRE 的十五人新創，被要求「讓 production 更可靠」，你前三個月會做什麼？
> 第一個月，我會先理解現況，而不是急著導入工具。找出最重要的兩、三個使用者旅程（例如註冊、結帳），了解它們目前怎麼被監控；整理最近幾個月的事故與 production 相關的工作，看看時間花在哪裡、哪些事一再發生；畫出 production 架構圖，特別標出控制平面中的單點，例如手動管理的憑證、只有一個人知道的部署步驟。
>
> 第二個月，處理最大的風險與最重的 toil。通常會有幾個低成本、高回報的項目，例如自動化憑證更新、讓部署可以一鍵回退、刪掉沒人處理的告警並為關鍵使用者旅程加上真正有意義的告警。同時和產品一起為最重要的旅程定義第一個 SLO，開始收集數據。
>
> 第三個月，建立讓改善能持續的機制：簡單的事故流程與 blameless postmortem、讓寫服務的工程師參與 on-call 輪值、每週花幾分鐘檢視 SLO 與維運工作量。回答時要強調，在十五人的公司裡，目標不是成立一個 SRE 部門，而是把 SRE 的原則（量測使用者體驗、限制 toil、用工程手段解決重複問題、事先同意可靠性目標）融入現有團隊的日常工作。
