🌱 從零開始理解：什麼是 Concurrency？

生活比喻：一個廚師同時煮湯、切菜、烤麵包 — 他在三個任務之間切換（concurrency）。三個廚師各做一道菜 — 他們真的同時在做（parallelism）。

Concurrency ≠ Parallelism：

  • Concurrency：結構上能處理多件事（interleaving），即使只有一個 CPU core
  • Parallelism：物理上同時執行多件事，需要多個 CPU core

為什麼面試考：L5+ 工程師要能設計多執行緒系統、避免 race condition、保證 correctness。

1.2 Python GIL (Global Interpreter Lock)

# Python GIL：同一時間只有一個 thread 執行 Python bytecode
# 影響：CPU-bound 任務用 threading 沒有加速（因為只有一個 thread 跑）
# 解法：CPU-bound 用 multiprocessing；I/O-bound 用 threading 或 asyncio

import threading, time

counter = 0

def increment():
    global counter
    for _ in range(1_000_000):
        counter += 1  # NOT thread-safe! counter += 1 is NOT atomic

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Expected: 2000000, Got: {counter}")  # 通常 < 2000000 (race condition!)

1.3 Race Condition & Critical Section

# Race Condition: 多個 thread 同時讀寫共享資源，結果取決於執行順序
# Critical Section: 一次只能有一個 thread 進入的程式碼區段

# 修正上面的 race condition:
import threading

counter = 0
lock = threading.Lock()

def safe_increment():
    global counter
    for _ in range(1_000_000):
        with lock:  # Critical section
            counter += 1

threads = [threading.Thread(target=safe_increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(f"Result: {counter}")  # Always 2000000 ✓

1.4 Deadlock 四個條件（Coffman Conditions）

# 四個條件同時滿足才會 deadlock：
# 1. Mutual Exclusion: 資源不能共享
# 2. Hold and Wait: 持有資源的同時等待其他資源
# 3. No Preemption: 不能強制搶走別人的資源
# 4. Circular Wait: A 等 B、B 等 A 形成環

# 打破任一條件就能避免 deadlock：
# - 打破 Circular Wait: 所有 thread 按固定順序取鎖（最常用！）
# - 打破 Hold and Wait: 一次取得所有需要的鎖（try-lock with timeout）

1.5 Livelock & Starvation

# Livelock: 兩個人在走廊相遇，都讓路但都往同一邊讓 → 永遠走不過去
# 不是 deadlock（沒有阻塞），但也沒有進展

# Starvation: 低優先權的 thread 永遠等不到資源
# 例：Writer-preference RWLock 中 reader 永遠拿不到鎖
# 解法：Fairness — FIFO ordering, aging (提升等待久的 thread 優先權)

題目 1：LC 1115 - Print in Order

題意：三個 thread 分別印 first(), second(), third()，保證印出 "firstsecondthird"。

# Python 解法：用 Event (signal)
import threading

class Foo:
    def __init__(self):
        self.event1 = threading.Event()
        self.event2 = threading.Event()

    def first(self, printFirst):
        printFirst()
        self.event1.set()  # Signal: first is done

    def second(self, printSecond):
        self.event1.wait()  # Wait until first is done
        printSecond()
        self.event2.set()  # Signal: second is done

    def third(self, printThird):
        self.event2.wait()  # Wait until second is done
        printThird()

// Go 解法：用 channel
type Foo struct {
    ch1 chan struct{}
    ch2 chan struct{}
}

func NewFoo() *Foo {
    return &Foo{ch1: make(chan struct{}), ch2: make(chan struct{})}
}

func (f *Foo) First(printFirst func()) {
    printFirst()
    close(f.ch1) // Signal first done
}

func (f *Foo) Second(printSecond func()) {
    <-f.ch1 // Wait for first
    printSecond()
    close(f.ch2) // Signal second done
}

func (f *Foo) Third(printThird func()) {
    <-f.ch2 // Wait for second
    printThird()
}

題目 2：LC 1116 - Print Zero Even Odd

題意：三個 thread (zero, even, odd) 交替印出 0102030405。

import threading

class ZeroEvenOdd:
    def __init__(self, n: int):
        self.n = n
        self.zero_sem = threading.Semaphore(1)
        self.odd_sem = threading.Semaphore(0)
        self.even_sem = threading.Semaphore(0)

    def zero(self, printNumber):
        for i in range(1, self.n + 1):
            self.zero_sem.acquire()
            printNumber(0)
            if i % 2 == 1:
                self.odd_sem.release()
            else:
                self.even_sem.release()

    def odd(self, printNumber):
        for i in range(1, self.n + 1, 2):
            self.odd_sem.acquire()
            printNumber(i)
            self.zero_sem.release()

    def even(self, printNumber):
        for i in range(2, self.n + 1, 2):
            self.even_sem.acquire()
            printNumber(i)
            self.zero_sem.release()

// Go: channel-based coordination
func zeroEvenOdd(n int) {
    zeroCh := make(chan struct{}, 1)
    oddCh := make(chan struct{})
    evenCh := make(chan struct{})
    done := make(chan struct{})

    zeroCh <- struct{}{} // Start with zero

    go func() { // zero
        for i := 1; i <= n; i++ {
            <-zeroCh
            fmt.Print(0)
            if i%2 == 1 { oddCh <- struct{}{} } else { evenCh <- struct{}{} }
        }
    }()
    go func() { // odd
        for i := 1; i <= n; i += 2 {
            <-oddCh
            fmt.Print(i)
            zeroCh <- struct{}{}
        }
    }()
    go func() { // even
        for i := 2; i <= n; i += 2 {
            <-evenCh
            fmt.Print(i)
            zeroCh <- struct{}{}
        }
        close(done)
    }()
    <-done
}

題目 3：LC 1117 - Building H2O

題意：多個 hydrogen/oxygen thread，每次必須湊齊 2H + 1O 才能一起通過 barrier。

import threading

class H2O:
    def __init__(self):
        self.h_sem = threading.Semaphore(2)  # Allow 2 H
        self.o_sem = threading.Semaphore(1)  # Allow 1 O
        self.barrier = threading.Barrier(3)  # Wait for 3 threads

    def hydrogen(self, releaseHydrogen):
        self.h_sem.acquire()
        self.barrier.wait()      # Wait until 2H + 1O gathered
        releaseHydrogen()
        self.h_sem.release()

    def oxygen(self, releaseOxygen):
        self.o_sem.acquire()
        self.barrier.wait()
        releaseOxygen()
        self.o_sem.release()

題目 4：LC 1188 - Design Bounded Blocking Queue

題意：實作一個 thread-safe 的有界佇列，滿了就 block enqueue，空了就 block dequeue。

import threading
from collections import deque

class BoundedBlockingQueue:
    def __init__(self, capacity: int):
        self.queue = deque()
        self.capacity = capacity
        self.lock = threading.Lock()
        self.not_full = threading.Condition(self.lock)
        self.not_empty = threading.Condition(self.lock)

    def enqueue(self, element: int) -> None:
        with self.not_full:
            while len(self.queue) >= self.capacity:
                self.not_full.wait()  # Block until not full
            self.queue.append(element)
            self.not_empty.notify()   # Signal: queue not empty

    def dequeue(self) -> int:
        with self.not_empty:
            while len(self.queue) == 0:
                self.not_empty.wait()  # Block until not empty
            val = self.queue.popleft()
            self.not_full.notify()    # Signal: queue not full
            return val

    def size(self) -> int:
        with self.lock:
            return len(self.queue)

// Go: Naturally fits with buffered channels!
type BoundedBlockingQueue struct {
    ch chan int
}

func NewBBQ(capacity int) *BoundedBlockingQueue {
    return &BoundedBlockingQueue{ch: make(chan int, capacity)}
}

func (q *BoundedBlockingQueue) Enqueue(val int) {
    q.ch <- val // Blocks if channel full
}

func (q *BoundedBlockingQueue) Dequeue() int {
    return <-q.ch // Blocks if channel empty
}

func (q *BoundedBlockingQueue) Size() int {
    return len(q.ch)
}

題目 5：LC 1195 - Fizz Buzz Multithreaded

題意：4 個 thread (fizz, buzz, fizzbuzz, number) 合作印 1 到 n 的 FizzBuzz 序列。

import threading

class FizzBuzz:
    def __init__(self, n: int):
        self.n = n
        self.current = 1
        self.lock = threading.Lock()
        self.cond = threading.Condition(self.lock)

    def fizz(self, printFizz):
        for _ in range(self.n):
            with self.cond:
                while self.current <= self.n and not (self.current % 3 == 0 and self.current % 5 != 0):
                    self.cond.wait()
                if self.current > self.n: return
                printFizz()
                self.current += 1
                self.cond.notify_all()

    def buzz(self, printBuzz):
        for _ in range(self.n):
            with self.cond:
                while self.current <= self.n and not (self.current % 5 == 0 and self.current % 3 != 0):
                    self.cond.wait()
                if self.current > self.n: return
                printBuzz()
                self.current += 1
                self.cond.notify_all()

    def fizzbuzz(self, printFizzBuzz):
        for _ in range(self.n):
            with self.cond:
                while self.current <= self.n and not (self.current % 15 == 0):
                    self.cond.wait()
                if self.current > self.n: return
                printFizzBuzz()
                self.current += 1
                self.cond.notify_all()

    def number(self, printNumber):
        for _ in range(self.n):
            with self.cond:
                while self.current <= self.n and (self.current % 3 == 0 or self.current % 5 == 0):
                    self.cond.wait()
                if self.current > self.n: return
                printNumber(self.current)
                self.current += 1
                self.cond.notify_all()

📝 Ch1 理解確認

Q1: 為什麼 Python 的 counter += 1 不是 thread-safe？

A: counter += 1 編譯成 3 個 bytecode 操作：LOAD counter → ADD 1 → STORE counter。GIL 在任何一步之間都可能切換 thread。如果 Thread A LOAD 了 5，被切走，Thread B 也 LOAD 5，各自 +1 存回 6，結果本該是 7 卻變成 6。

Q2: Event vs Semaphore vs Condition — 什麼時候用哪個？

A: Event = 一次性信號（"X 已完成"），binary flag。Semaphore = 計數器（"最多 N 個可以同時進入"）。Condition = 等待某個條件成立（"queue 非空"），搭配 while loop 使用。經驗：排序用 Event，限量用 Semaphore，條件等待用 Condition。

Q3: Go channel 比 Python threading 簡單在哪？

A: Go channel 把同步和通訊合而為一（CSP model）。Python 需要 Lock+Condition+Queue 三件套，Go 只要一個 channel 就搞定（自帶 blocking semantics）。而且 goroutine 比 thread 輕量 1000x（2KB vs 2MB stack），可以開百萬個。

💬 Ch1 Follow-up 面試問題

Q1: How would you debug a race condition in production?

A: 1) ThreadSanitizer (TSan) for C++/Go — detects data races at runtime. 2) For Python: use logging with thread_id + timestamps to identify interleaving. 3) Stress testing: run the suspicious code path with many threads and random delays. 4) Code review: look for shared mutable state without synchronization. 5) In production: add metrics for inconsistent states (e.g., counter mismatch).

Q2: What's the performance impact of using locks?

A: Lock contention causes: 1) Thread blocking (context switch = ~1-10μs). 2) Cache invalidation (lock acquisition invalidates other cores' cache lines). 3) Reduced parallelism (only one thread in critical section). Mitigation: minimize critical section size, use read-write locks, lock-free structures for hot paths, or partition data to reduce contention.

Q3: Mutex vs Semaphore — when do you use each?

A: Mutex = binary, only the owner can unlock (mutual exclusion). Semaphore = counting, any thread can signal (resource counting). Use Mutex for protecting critical sections. Use Semaphore for limiting concurrency (connection pool = Semaphore(10)) or signaling between threads.

Q4: How do you prevent deadlock in a system with multiple locks?

A: 1) Lock ordering: always acquire locks in a fixed global order (breaks circular wait). 2) Lock timeout: tryLock with timeout, release all and retry (breaks hold-and-wait). 3) Single lock: coarse-grained lock covering all resources (simple but reduces parallelism). 4) Lock-free algorithms: eliminate locks entirely for hot paths.

Q5: Compare Python's GIL with Go's goroutine scheduling.

A: Python GIL: one thread executes bytecode at a time. Multiple threads help for I/O-bound only. Go: no GIL. Goroutines are M:N scheduled (M goroutines on N OS threads). Go scheduler does cooperative preemption at function calls and since Go 1.14, asynchronous preemption. Result: Go achieves true parallelism for CPU-bound work; Python needs multiprocessing for that.

VQ1: 以下程式碼有 bug，找出問題並修正： 
import threading
balance = 1000

def withdraw(amount):
    global balance
    if balance >= amount:
        balance -= amount
    return balance

# 兩個 thread 同時提款 800 元
t1 = threading.Thread(target=withdraw, args=(800,))
t2 = threading.Thread(target=withdraw, args=(800,))
t1.start(); t2.start()
t1.join(); t2.join()

答案：Race condition！兩個 thread 都可能通過 if balance >= amount 檢查（都看到 balance=1000），然後各自扣 800，導致 balance 變成 -600。
修正：用 Lock 保護整個 check-then-act 區段：

lock = threading.Lock()
def withdraw(amount):
    global balance
    with lock:  # 整個 check + modify 必須是 atomic
        if balance >= amount:
            balance -= amount
    return balance

核心概念：Check-then-act 必須在同一個 critical section 內完成。分開的 check 和 act 之間可以被其他 thread 插入。這叫做 TOCTOU (Time-of-Check to Time-of-Use) bug。

VQ2: 為什麼以下 deadlock 解法「讓 philosopher 4 先拿右邊」能避免 deadlock？用 Coffman 條件解釋。

答案：這打破了 Circular Wait（第 4 條件）。正常情況：P0 拿 fork0 等 fork1，P1 拿 fork1 等 fork2...P4 拿 fork4 等 fork0 → 形成環。如果 P4 改成先拿 fork0（右邊）再拿 fork4（左邊），那拿取順序變成：所有人都是「拿較小編號的 fork 先」。這等於建立了全局排序（Total Order），不可能形成環，因為環需要至少一個人拿大等小，但現在沒有人這樣做。

VQ3: Python 的 GIL 是否意味著 Python 程式永遠不需要 Lock？為什麼？

答案：錯！GIL 只保證「一次一個 thread 執行 bytecode」，但 不保證 一個 Python 語句是 atomic 的。例如 counter += 1 是 3 個 bytecode（LOAD → ADD → STORE），GIL 可以在任何兩步之間切換。GIL 保護的是 CPython 內部資料結構（如 reference count），不是你的應用邏輯。只有單一 bytecode 操作（如 x = []、L.append(x)）在 CPython 中是 atomic 的，但依賴這個是非 portable 的壞實踐。

VQ4: 設計題：如果你要實作一個 thread-safe 的計數器，有 Lock、Atomic、Channel 三種方式，各適合什麼場景？

答案：

  • Lock (Mutex)：適合 critical section 包含多步驟邏輯（如 check-then-modify-then-notify）。簡單好理解，但 contention 高時效能差。
  • Atomic (CAS)：適合純數值操作（increment, compare-and-swap）。零 overhead 在低 contention；高 contention 時 spin loop 浪費 CPU。Go 用 atomic.AddInt64，Java 用 AtomicLong。
  • Channel (Go)：適合 counter 的更新需要觸發其他邏輯（如通知、彙整）。用一個 goroutine 持有 counter，其他人透過 channel 發送 increment 請求。actor model 風格，零 shared state。

面試黃金答案：「對於簡單 counter，我用 atomic（最快）。如果要 check-then-act，用 Lock。如果是 Go 且 counter 變更需觸發後續流程，用 channel + owner goroutine。」

VQ5: 解釋為什麼 Bounded Blocking Queue 的 wait() 必須放在 while loop 裡而不是 if？

答案：因為 Spurious Wakeup（虛假喚醒）。OS 可能在沒有 notify 的情況下喚醒等待的 thread（POSIX 標準允許這樣做以簡化實作）。另外，即使是真正的 notify，也可能有其他 thread 在你被喚醒到你獲取 lock 之間，搶先消費了資源（Stolen Wakeup）。所以必須用 while 重新檢查條件：

# 錯誤：if 只檢查一次
if len(queue) == 0:
    condition.wait()  # 被喚醒後直接往下跑，但可能又是空的！

# 正確：while 持續檢查
while len(queue) == 0:
    condition.wait()  # 被喚醒後再檢查一次，確認真的有東西

題目 6：LC 1226 - Dining Philosophers 🍝

題意：5 個哲學家圍桌，每人需要左右兩支筷子才能吃飯。避免 deadlock。

import threading

class DiningPhilosophers:
    def __init__(self):
        # 5 支筷子（叉子），每支是一把鎖
        self.forks = [threading.Lock() for _ in range(5)]
        # 限制最多 4 人同時嘗試拿筷子 → 打破 circular wait
        self.limit = threading.Semaphore(4)

    def wantsToEat(self, philosopher: int, *actions):
        pickLeftFork, pickRightFork, eat, putLeftFork, putRightFork = actions
        left = philosopher
        right = (philosopher + 1) % 5

        self.limit.acquire()        # 最多 4 人同時嘗試
        self.forks[left].acquire()
        self.forks[right].acquire()

        pickLeftFork()
        pickRightFork()
        eat()
        putLeftFork()
        putRightFork()

        self.forks[right].release()
        self.forks[left].release()
        self.limit.release()

// Go 解法：Resource ordering（小號先拿）
type DiningPhilosophers struct {
    forks [5]sync.Mutex
}

func (dp *DiningPhilosophers) WantsToEat(id int, eat func()) {
    left, right := id, (id+1)%5
    // Always pick lower-numbered fork first → breaks circular wait
    first, second := left, right
    if first > second { first, second = second, first }

    dp.forks[first].Lock()
    dp.forks[second].Lock()
    eat()
    dp.forks[second].Unlock()
    dp.forks[first].Unlock()
}

Why this works：固定順序取鎖打破 Circular Wait（Deadlock 第 4 條件）。或用 Semaphore(4) 確保至少一人能拿到兩支筷子。

from collections import deque
from typing import List
from concurrent.futures import ThreadPoolExecutor

class Solution:
    def crawl(self, startUrl: str, htmlParser) -> List[str]:
        domain = startUrl.split('/')[2]
        visited = {startUrl}
        lock = threading.Lock()
        result = [startUrl]

        def get_domain(url):
            return url.split('/')[2]

        def worker(url):
            links = htmlParser.getUrls(url)
            new_urls = []
            with lock:
                for link in links:
                    if get_domain(link) == domain and link not in visited:
                        visited.add(link)
                        result.append(link)
                        new_urls.append(link)
            return new_urls

        with ThreadPoolExecutor(max_workers=8) as executor:
            while queue:
                futures = []
                while queue:
                    url = queue.popleft()
                    futures.append(executor.submit(worker, url))
                for f in futures:
                    for new_url in f.result():
                        queue.append(new_url)

        return result

題目 8：Implement Read-Write Lock

題意：實作 RWLock — 多個 reader 可以同時讀，但 writer 獨佔。

import threading

class ReadWriteLock:
    def __init__(self):
        self._lock = threading.Lock()
        self._readers = 0
        self._readers_lock = threading.Lock()
        self._writer_lock = threading.Lock()

    def acquire_read(self):
        with self._readers_lock:
            self._readers += 1
            if self._readers == 1:
                self._writer_lock.acquire()  # First reader blocks writers

    def release_read(self):
        with self._readers_lock:
            self._readers -= 1
            if self._readers == 0:
                self._writer_lock.release()  # Last reader unblocks writers

    def acquire_write(self):
        self._writer_lock.acquire()

    def release_write(self):
        self._writer_lock.release()

⚠️ 問題：這是 reader-preference — 持續有 reader 時 writer 會 starve。面試 follow-up 常問如何改成 fair（見 Ch5）。

💬 Ch2 Follow-up

Q1: Why is volatile/memory barrier needed for double-checked locking in Java/C++ but not Python?

A: In Java/C++, without volatile, the compiler/CPU may reorder instructions: the instance pointer could be assigned before the constructor finishes. Python's GIL provides implicit memory ordering for bytecode operations.

Q2: How would you implement a fair ReadWriteLock?

A: Add a "write_waiting" flag or turnstile semaphore. When a writer is waiting, new readers also block. This prevents writer starvation. (Full implementation in Ch5.)

Q3: What's the difference between threading.Lock and threading.RLock in Python?

A: Lock: same thread acquiring twice → deadlock. RLock (Reentrant): same thread can acquire multiple times (maintains count). Use RLock for recursive functions that need the lock.

Q4: How does Go's sync.Map compare to a regular map with RWMutex?

A: sync.Map optimized for: (1) key written once, read many times, (2) disjoint key sets. Uses read-only atomic copy + dirty map. For high write contention, sharded map with RWMutex per shard often performs better.

Q5: In Dining Philosophers, what's the throughput difference between Semaphore(4) vs ordered locking?

A: Semaphore(4): higher throughput (up to 4 attempt, 2 eat simultaneously). Ordered locking: slightly lower (philosopher 4 always waits for fork 0). Both correct; Semaphore(4) preferred for throughput.

🧪 Ch2 驗證測驗（Verification Quiz）

VQ1: 以下 RWLock 實作有什麼問題？在什麼場景下會出 bug？ 
class BadRWLock:
    def __init__(self):
        self.readers = 0
        self.writer_lock = threading.Lock()

    def acquire_read(self):
        self.readers += 1          # BUG HERE
        if self.readers == 1:
            self.writer_lock.acquire()

    def release_read(self):
        self.readers -= 1
        if self.readers == 0:
            self.writer_lock.release()

答案：self.readers += 1 本身就不是 thread-safe！兩個 reader thread 同時呼叫 acquire_read() 時，可能都讀到 readers=0，各自 +1 變成 1，然後兩個都嘗試 acquire writer_lock（但只有一個能拿到）。更糟：readers 最終可能是 1 而不是 2，導致第一個 reader release_read() 時 readers 變成 0，提前釋放 writer_lock，讓 writer 進入 — 此時另一個 reader 還在讀！
修正：用一個額外的 Lock 保護 readers 變數（如原版 ReadWriteLock 中的 _readers_lock）。

VQ2: Go 的 sync.Once 和 Python 的 Double-Checked Locking 的本質差異是什麼？為什麼 Go 不需要 double-check？

答案：sync.Once 內部使用 atomic.LoadUint32 做 fast path check + mutex + atomic.StoreUint32 做 slow path。本質上它 就是 double-checked locking，只是被封裝成一個 API 了。Go 的 memory model 保證 atomic store 之後的 load 一定能看到最新值（happens-before），所以不需要 volatile 這種額外標記。Python 因為有 GIL，bytecode 層面已經 serialized，所以 double-check 更像是效能優化（避免每次都搶 lock）而非 correctness 需求。

VQ3: Producer-Consumer 中，為什麼用 buffered channel/Queue 而不是 unbuffered？各自的 tradeoff 是什麼？

答案：

  • Unbuffered (size=0)：同步 rendezvous — producer 和 consumer 必須同時準備好。優點：zero latency handoff、backpressure 立即。缺點：吞吐量低（每次只能傳一個）。
  • Buffered (size=N)：解耦 producer 和 consumer 的速度差異。producer 可以突發 N 個不等 consumer。優點：higher throughput、容忍 burst。缺點：增加 latency（item 在 buffer 中等待）、memory 使用。
  • 選擇原則：如果 producer/consumer 速度差異大 → buffered。如果需要嚴格配對（如 request-response）→ unbuffered。Buffer size = 預期的 burst size / (consumer_rate - producer_rate)。
VQ4: 為什麼 Web Crawler 用 visited = set() + lock 比 sync.Map 更危險？什麼場景會出問題？

答案：Python set() + lock 的問題：lock 粒度。如果 lock 範圍太小（只保護 visited.add(link)），可能出現：Thread A check link not in visited = True，被 preempt，Thread B 也 check = True，兩個都 add 並爬同一個 URL。必須把 check + add 放在同一個 critical section（TOCTOU）。
Go 的 sync.Map.LoadOrStore() 是 atomic 的：check + store 一步完成，不會有 TOCTOU。所以 Go 版本天然正確，Python 版本需要手動保證。

import threading

class AtomicCounter:
    """Lock-free counter using CAS loop."""
    def __init__(self, initial=0):
        self._value = initial
        self._lock = threading.Lock()  # Python doesn't have real CAS

    def increment(self) -> int:
        while True:
            old = self._value
            new = old + 1
            with self._lock:
                if self._value == old:
                    self._value = new
                    return new
            # CAS failed, retry (spin)

    def get(self) -> int:
        return self._value

// Go: Real atomic CAS
import "sync/atomic"

type AtomicCounter struct {
    value int64
}

func (c *AtomicCounter) Increment() int64 {
    for {
        old := atomic.LoadInt64(&c.value)
        new := old + 1
        if atomic.CompareAndSwapInt64(&c.value, old, new) {
            return new
        }
    }
}

// Simpler: just use atomic.AddInt64
func (c *AtomicCounter) IncrementSimple() int64 {
    return atomic.AddInt64(&c.value, 1)
}

題目 12：Lock-Free Stack (Treiber Stack)

// Go implementation of Treiber Stack (lock-free using CAS)
import (
    "sync/atomic"
    "unsafe"
)

type node struct {
    value int
    next  *node
}

type LockFreeStack struct {
    top unsafe.Pointer // *node
}

func (s *LockFreeStack) Push(val int) {
    newNode := &node{value: val}
    for {
        oldTop := atomic.LoadPointer(&s.top)
        newNode.next = (*node)(oldTop)
        if atomic.CompareAndSwapPointer(&s.top, oldTop, unsafe.Pointer(newNode)) {
            return
        }
    }
}

func (s *LockFreeStack) Pop() (int, bool) {
    for {
        oldTop := atomic.LoadPointer(&s.top)
        if oldTop == nil {
            return 0, false
        }
        topNode := (*node)(oldTop)
        newTop := unsafe.Pointer(topNode.next)
        if atomic.CompareAndSwapPointer(&s.top, oldTop, newTop) {
            return topNode.value, true
        }
    }
}

        self._lock = threading.Lock()  # Simulating CAS

    def push(self, val):
        while True:
            old_top = self.top
            new_node = {'value': val, 'next': old_top}
            with self._lock:
                if self.top is old_top:
                    self.top = new_node
                    return

    def pop(self):
        while True:
            old_top = self.top
            if old_top is None:
                return None
            with self._lock:
                if self.top is old_top:
                    self.top = old_top['next']
                    return old_top['value']

from typing import Optional

class LockFreeRingBuffer:
    """Single-producer single-consumer ring buffer (no lock needed)."""
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.buffer = [None] * capacity
        self.head = 0  # Write pointer (producer owns)
        self.tail = 0  # Read pointer (consumer owns)

    def enqueue(self, item) -> bool:
        next_head = (self.head + 1) % self.capacity
        if next_head == self.tail:  # Full
            return False
        self.buffer[self.head] = item
        self.head = next_head
        return True

    def dequeue(self) -> Optional[any]:
        if self.head == self.tail:  # Empty
            return None
        item = self.buffer[self.tail]
        self.tail = (self.tail + 1) % self.capacity
        return item

# Why lock-free: Producer only writes head, Consumer only writes tail.
# No shared mutable state between them! (SPSC = Single Producer Single Consumer)

import time
import threading

class TokenBucketRateLimiter:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate          # Tokens per second
        self.capacity = capacity
        self.tokens = capacity
        self.last_refill = time.time()
        self._lock = threading.Lock()

    def allow(self) -> bool:
        with self._lock:
            now = time.time()
            elapsed = now - self.last_refill
            self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
            self.last_refill = now
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False

// Go: Atomic-based rate limiter
import (
    "sync/atomic"
    "time"
)

type TokenBucket struct {
    tokens   int64
    capacity int64
    rate     int64
    lastTime int64
}

func (tb *TokenBucket) Allow() bool {
    for {
        now := time.Now().UnixNano()
        last := atomic.LoadInt64(&tb.lastTime)
        elapsed := float64(now-last) / 1e9
        current := atomic.LoadInt64(&tb.tokens)
        newTokens := int64(elapsed * float64(tb.rate))
        updated := min64(tb.capacity, current+newTokens)
        if updated < 1 { return false }
        if atomic.CompareAndSwapInt64(&tb.tokens, current, updated-1) {
            atomic.StoreInt64(&tb.lastTime, now)
            return true
        }
    }
}

題目 15：Design Thread Pool

import threading
from queue import Queue
from typing import Callable

class ThreadPool:
    def __init__(self, num_workers: int):
        self.task_queue = Queue()
        self.workers = []
        self._shutdown = False

        for i in range(num_workers):
            w = threading.Thread(target=self._worker, daemon=True)
            w.start()
            self.workers.append(w)

    def _worker(self):
        while not self._shutdown:
            try:
                task, args, kwargs, future = self.task_queue.get(timeout=1)
                try:
                    result = task(*args, **kwargs)
                    future['result'] = result
                    future['done'] = True
                except Exception as e:
                    future['error'] = e
                    future['done'] = True
                finally:
                    self.task_queue.task_done()
            except:
                continue

    def submit(self, task: Callable, *args, **kwargs) -> dict:
        future = {'done': False, 'result': None, 'error': None}
        self.task_queue.put((task, args, kwargs, future))
        return future

    def shutdown(self, wait=True):
        self._shutdown = True
        if wait:
            self.task_queue.join()

// Go: Worker pool with channels
type WorkerPool struct {
    tasks chan func()
    wg    sync.WaitGroup
}

func NewWorkerPool(numWorkers int, queueSize int) *WorkerPool {
    pool := &WorkerPool{tasks: make(chan func(), queueSize)}
    for i := 0; i < numWorkers; i++ {
        pool.wg.Add(1)
        go func() {
            defer pool.wg.Done()
            for task := range pool.tasks {
                task()
            }
        }()
    }
    return pool
}

func (p *WorkerPool) Shutdown() { close(p.tasks); p.wg.Wait() }

💬 Ch3 Follow-up

Q1: When should you use lock-free vs lock-based?

A: Lock-free when: critical section is tiny (CAS on a pointer), contention is very high, or you can't afford priority inversion (real-time systems). Lock-based when: critical section is complex, correctness is hard to reason about, or contention is moderate. Rule of thumb: if you're not sure, use locks.

Q2: What's memory ordering and why does it matter?

A: CPUs/compilers may reorder memory operations. In concurrent code, one thread may see stale values. Memory ordering guarantees (relaxed, acquire, release, seq_cst) specify visibility. Go's sync/atomic provides sequential consistency. Without proper ordering, lock-free algorithms silently corrupt data.

Q3: SPSC vs MPMC ring buffer — what's the complexity difference?

A: SPSC: no synchronization needed (producer owns head, consumer owns tail). MPMC: need CAS on both. SPSC is O(1) guaranteed; MPMC may spin. SPSC for I/O pipelines; MPMC for thread pools.

Q4: How does Go's channel compare to a lock-free queue internally?

A: Go channels internally use a lock (runtime mutex) + ring buffer. They are NOT lock-free. The abstraction benefit (CSP model, select, range) outweighs raw performance for most apps.

Q5: CAS spin loops under high contention?

A: Low contention: CAS rarely spins, outperforms locks. High contention: many threads spin → waste CPU → slower than lock. Mitigation: exponential backoff or hybrid spin-then-park approach.

🧪 Ch3 驗證測驗（Verification Quiz）

VQ1: CAS loop 和 Mutex 在高 contention 下的效能差異是什麼？什麼時候 CAS 反而更慢？

答案：Mutex 在 contention 時讓 thread sleep（不佔 CPU），OS scheduler 會喚醒。CAS loop 在 contention 時 spin（佔 CPU 空轉）。當 critical section 很短（< 100ns）且 contention 低時，CAS 快（避免 context switch 的 1-10μs overhead）。但當 16+ threads 同時 CAS 同一個值時，所有失敗的 thread 都在 spin 浪費 CPU，且頻繁的 cache line invalidation（MESI protocol 的 exclusive→invalid 風暴）讓所有 core 的 L1 cache 失效。此時 Mutex + sleep 反而更有效率，因為只有一個 thread 在執行。

面試最佳答案：「低 contention 用 CAS（避免 syscall），高 contention 用 adaptive spinning（先 spin 100ns，拿不到就 park）。Go runtime 的 mutex 就是這樣實作的。」

VQ2: 為什麼 SPSC Ring Buffer 不需要任何同步原語？如果改成 MPSC 或 MPMC 會怎樣？

答案：SPSC 安全的原因：producer 只寫 head pointer，consumer 只寫 tail pointer。兩者互不干擾 — 即使同時存取也不會 corrupt（因為各自操作不同的記憶體位置）。唯一的「共享」是讀對方的 pointer 來判斷 full/empty，但讀是安全的（worst case 是看到稍微舊的值 → 誤判 empty/full → 下次再試）。
MPSC：多個 producer 同時寫 head → 需要 CAS 保護 head 推進。
MPMC：head 和 tail 都需要 CAS。還要處理「兩個 consumer 同時 pop 同一元素」的問題。複雜度從 O(1) guaranteed 變成 O(1) amortized with potential spin。

VQ3: Token Bucket vs Leaky Bucket — 兩種限流器的行為差異？什麼場景選哪個？

答案：

  • Token Bucket：允許 burst（桶裡有 token 就放行，可以瞬間放行 capacity 個 request），然後以 rate 速度補充。適合：允許突發流量但長期平均限速的場景（如 API Gateway: burst 100, sustained 10/s）。
  • Leaky Bucket：嚴格平滑輸出（不管輸入多 bursty，輸出永遠是固定速率）。像漏水的桶 — 水流出速度恆定。適合：需要嚴格恆定速率的場景（如 network traffic shaping, video streaming bitrate control）。
  • 面試陷阱：很多人搞混！Token Bucket 控制的是「平均速率 + 突發容忍」，Leaky Bucket 控制的是「絕對恆定速率」。AWS/GCP 用 Token Bucket，因為 API 呼叫天然有 burst 性質。
VQ4: 以下 Lock-Free Stack 的 Pop 操作有 ABA 問題嗎？什麼場景下會觸發？如何修復？ 
func (s *LockFreeStack) Pop() (int, bool) {
    for {
        oldTop := atomic.LoadPointer(&s.top)
        if oldTop == nil { return 0, false }
        topNode := (*node)(oldTop)
        newTop := unsafe.Pointer(topNode.next)
        if atomic.CompareAndSwapPointer(&s.top, oldTop, newTop) {
            return topNode.value, true
        }
    }
}

答案：是的，有 ABA 問題！場景：Thread A 讀到 top=NodeX(val=5, next=NodeY)，被 preempt。Thread B pop NodeX → pop NodeY → push 新的 NodeZ → push 回 NodeX（重用記憶體）。Thread A 醒來，CAS(top, NodeX, NodeY) 成功 — 但 NodeX.next 已經不是 NodeY 了（NodeX 被重用後 next 指向 NodeZ）！Stack 被 corrupt。
修復：(1) Tagged pointer — 在 pointer 旁邊附帶 version counter：CAS(ptr+version)，即使 ptr 相同 version 也不同。(2) Hazard Pointers — 標記正在使用的 node，延遲 free。(3) Epoch-based reclamation（Go 通常靠 GC 避免 — GC 不會 free 仍被引用的 node）。

VQ5: Thread Pool 的 queue 用 bounded 好還是 unbounded 好？各自的風險是什麼？

答案：

  • Bounded（推薦）：submit 時如果滿了就 block 或 reject。好處：memory 可控，自帶 backpressure。壞處：caller 可能被 block。適合：生產環境（避免 OOM）。
  • Unbounded：submit 永遠成功。好處：caller 不 block。壞處：如果 producer 速度 > consumer，queue 無限增長 → OOM → 整個 process crash。
  • 面試答案：「Always bounded in production。Size = num_workers × expected_processing_time × acceptable_latency。配合 rejection policy：CallerRunsPolicy（caller 自己做）或 DiscardOldestPolicy（丟最舊的）。」Java 的 ThreadPoolExecutor 就有這些 policy。

import concurrent.futures
from typing import List, Callable

def fan_out_fan_in(items: List, worker_fn: Callable, max_workers: int = 8):
    """Fan-out: distribute items to workers. Fan-in: collect results."""
    results = []
    with concurrent.futures.ThreadPoolExecutor(max_workers=max_workers) as executor:
        futures = {executor.submit(worker_fn, item): item for item in items}
        for future in concurrent.futures.as_completed(futures):
            try:
                results.append(future.result())
            except Exception as e:
                print(f"Error: {e}")
    return results

// Go: Fan-out/Fan-in with goroutines and channels
func fanOutFanIn(items []string, workerFn func(string) int, numWorkers int) []int {
    jobs := make(chan string, len(items))
    results := make(chan int, len(items))

    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for item := range jobs {
                results <- workerFn(item)
            }
        }()
    }

    for _, item := range items { jobs <- item }
    close(jobs)
    go func() { wg.Wait(); close(results) }()

    var output []int
    for r := range results { output = append(output, r) }
    return output
}

def pipeline_stage(input_q, transform_fn, output_q):

import threading
from typing import Callable

class Future:
    def __init__(self):
        self._result = None
        self._exception = None
        self._done = threading.Event()
        self._callbacks = []

    def set_result(self, result):
        self._result = result
        self._done.set()
        for cb in self._callbacks: cb(result)

    def set_exception(self, exc):
        self._exception = exc
        self._done.set()

    def result(self, timeout=None):
        self._done.wait(timeout)
        if self._exception: raise self._exception
        return self._result

    def add_callback(self, fn):
        if self._done.is_set(): fn(self._result)
        else: self._callbacks.append(fn)

def async_execute(fn, *args) -> Future:
    future = Future()
    def wrapper():
        try: future.set_result(fn(*args))
        except Exception as e: future.set_exception(e)
    threading.Thread(target=wrapper, daemon=True).start()
    return future

import threading
import time
from queue import Queue

class ConnectionPool:
    def __init__(self, max_size: int = 10):
        self.max_size = max_size
        self._pool = Queue(maxsize=max_size)
        self._semaphore = threading.Semaphore(max_size)
        for _ in range(max_size):
            self._pool.put(self._create_connection())

    def _create_connection(self):
        return {"id": id(object()), "in_use": False}

    def acquire(self, timeout=5.0):
        if not self._semaphore.acquire(timeout=timeout):
            raise TimeoutError("No connection available")
        return self._pool.get()

    def release(self, conn):
        self._pool.put(conn)
        self._semaphore.release()

    class _Ctx:
        def __init__(self, pool): self.pool = pool
        def __enter__(self): self.conn = self.pool.acquire(); return self.conn
        def __exit__(self, *a): self.pool.release(self.conn)

💬 Ch4 Follow-up

Q1: Fan-out/Fan-in vs Pipeline — when to use which?

A: Fan-out/Fan-in: items are independent, same transformation. Pipeline: sequential stages with different work. Use pipeline when stages have different compute profiles (I/O → CPU → I/O).

Q2: How does Go's context.Context work internally?

A: Context forms a tree. Parent cancelled → all children cancelled (via closing done channel). WithTimeout starts a timer goroutine that calls cancel(). select{case <-ctx.Done()} checks the internal done channel.

Q3: Future vs Promise vs async/await?

A: Future = read-only handle to a pending result. Promise = writable side (producer sets value). async/await = syntactic sugar over Futures. In Go: channels serve both roles.

Q4: How to implement connection pool health checking?

A: Background thread periodically: test idle connections (SELECT 1), replace dead ones, close connections older than max_lifetime, alert near capacity.

Q5: How does the Actor model avoid shared mutable state?

A: Each actor: private state + mailbox. Communicate via messages only. One message at a time (serial within actor). No shared memory = no races. Erlang/Akka built on this.

VQ2: Pipeline 中某個 stage 比其他 stage 慢 10x，會發生什麼？如何解決？

答案：慢 stage 成為瓶頸 — 它前面的 stage 的 output channel 會滿（block producer），整條 pipeline 的吞吐量 = 最慢 stage 的速度。
解法：

  • Parallel workers for slow stage：把慢 stage 變成 fan-out（多個 worker 讀同一個 input channel）。例如 stage 2 慢 10x → 開 10 個 stage 2 worker。
  • Buffered channel：增加慢 stage 前的 buffer size，容忍 burst。但只是推遲問題，不是根本解決。
  • Batch processing：慢 stage 改成批次處理（如 DB write 改成 batch insert）。

  • 監控 pool utilization，alert when > 80%

import threading

class FairReadWriteLock:
    """Fair RWLock: writers don't starve (using a service queue)."""
    def __init__(self):
        self._read_count = 0
        self._resource = threading.Lock()
        self._read_count_lock = threading.Lock()
        self._service_queue = threading.Lock()  # Fairness turnstile

    def acquire_read(self):
        self._service_queue.acquire()  # Wait in queue (fair)
        self._service_queue.release()  # Immediately release (just for ordering)
        with self._read_count_lock:
            self._read_count += 1
            if self._read_count == 1:
                self._resource.acquire()

    def release_read(self):
        with self._read_count_lock:
            self._read_count -= 1
            if self._read_count == 0:
                self._resource.release()

    def acquire_write(self):
        self._service_queue.acquire()  # Wait in queue (fair)
        self._resource.acquire()

    def release_write(self):
        self._resource.release()
        self._service_queue.release()

import threading, time, random

class BarberShop:
    def __init__(self, num_chairs: int):
        self.num_chairs = num_chairs
        self.waiting = 0
        self.lock = threading.Lock()
        self.barber_ready = threading.Semaphore(0)
        self.customer_ready = threading.Semaphore(0)
        self.done_cutting = threading.Semaphore(0)

    def barber(self):
        while True:
            self.customer_ready.acquire()  # Sleep until customer
            self.barber_ready.release()    # "Sit down"
            time.sleep(random.uniform(0.5, 1.5))  # Cut hair
            self.done_cutting.release()

    def customer(self, customer_id: int):
        with self.lock:
            if self.waiting >= self.num_chairs:
                print(f"Customer {customer_id}: leaving!")
                return
            self.waiting += 1
        self.customer_ready.release()  # Wake barber
        self.barber_ready.acquire()    # Wait for barber
        with self.lock: self.waiting -= 1
        self.done_cutting.acquire()
        print(f"Customer {customer_id}: done! ✂️")

題目 25：Priority Task Scheduler

import threading, heapq

class PriorityTaskScheduler:
    def __init__(self, num_workers=4):
        self._queue = []
        self._lock = threading.Lock()
        self._not_empty = threading.Condition(self._lock)
        self._shutdown = False
        self._counter = 0
        for _ in range(num_workers):
            threading.Thread(target=self._worker, daemon=True).start()

    def schedule(self, priority, task):
        with self._not_empty:
            self._counter += 1
            heapq.heappush(self._queue, (priority, self._counter, task))
            self._not_empty.notify()

    def _worker(self):
        while True:
            with self._not_empty:
                while not self._queue and not self._shutdown:
                    self._not_empty.wait()
                if self._shutdown and not self._queue: return
                _, _, task = heapq.heappop(self._queue)
            task()

VQ1: Fair RWLock 的 service_queue 為什麼 reader acquire 後要「立刻 release」？如果不 release 會怎樣？

答案：service_queue 的唯一目的是「排隊」— 確保 FIFO 順序。Reader 只需要排隊表明「我到了」，然後立刻讓出排隊權讓後面的人也能表態。如果 reader 不 release service_queue，則所有後續 reader 和 writer 都會 block 在 service_queue 上，直到這個 reader 離開 — 這等於把 RWLock 降級成了普通 Mutex（一次只能一個人操作），完全喪失「多 reader 同時讀」的好處。
Writer 則必須持有 service_queue 直到寫完（acquire_write 到 release_write），因為 writer 需要獨佔 — 持有 service_queue 的同時阻止新 reader 進入。

VQ2: Priority Task Scheduler 中使用 counter 作為 heapq 的第二排序鍵有什麼作用？不用會怎樣？

答案：Python heapq 比較 tuple 時逐元素比較。如果兩個 task 有相同 priority，heapq 會嘗試比較第三個元素（task function）。但 function 不支援 < 比較 → 拋出 TypeError！counter 作為 tiebreaker：同 priority 時按插入順序排（FIFO），且 int 永遠可比較。這是 Python heapq 使用 pattern 的標準技巧。Go 的 container/heap 用 Less() interface 可以自訂比較邏輯，不會有此問題。

VQ3: Sleeping Barber 中如果有多個理髮師（N barbers），需要如何修改同步原語？

答案：改 barber_ready 從 Semaphore(0) 改成「理髮師就緒 pool」的概念：

  • barber_ready = Semaphore(0) 不變（表示有幾個 barber 目前 ready）
  • customer_ready = Semaphore(0) 不變（表示有幾個客人在等）
  • 每個 barber 是一個獨立 thread，各自 loop：acquire customer → release barber_ready → cut → release done
  • 需要一個額外的 done_cutting 對應：每對 (barber, customer) 需要配對的 done signal。可以用一個 Queue 讓 barber 把自己的 done_semaphore 交給對應 customer。

核心：N barbers = N 個 worker thread + 1 個 shared customer queue，本質上就是 Thread Pool！

Q1: Why M:N scheduling?

A: 1:1 limits to ~10K goroutines. M:N maps millions onto few OS threads. Goroutine switch ~100ns vs OS thread switch ~1μs. Enables "goroutine per request".

Q2: When to use singleflight?

A: In front of expensive idempotent operations with high concurrent access to same key. NOT for side-effectful operations or unique results per caller.

Q3: select with multiple ready channels?

A: Go picks randomly (uniform). Prevents starvation. With default case: non-blocking. Without: blocks until one ready.

Q4: sync.Pool vs regular pool?

A: sync.Pool: temporary cache, GC can reclaim anytime. Per-P (no contention). NOT for connections (GC could reclaim). For: byte buffers, encoders, temporary objects on hot path.

Q5: Work stealing advantages over global queue?

A: No contention on common path, better cache locality (own tasks stay on same CPU), automatic load balancing. Used in Go runtime, Java ForkJoinPool, Tokio.

VQ1: singleflight 和 sync.Once 的差異？什麼場景用哪個？

答案：

  • sync.Once：函數在整個程式生命週期只執行一次（永遠返回第一次的結果）。適合：Singleton 初始化、一次性 setup。
  • singleflight：相同 key 的「並發」請求只執行一次，但之後新的請求會再次執行。適合：cache miss deduplication（100 個 request 同時 miss → 只打 1 次 DB，但 5 分鐘後 cache 過期又會重新 fetch）。

關鍵差異：sync.Once 是「全局只一次」，singleflight 是「當前這批並發只一次」。

VQ2: errgroup.WithContext 為什麼能做到「一個失敗取消全部」？內部機制是什麼？

答案：errgroup.WithContext(parent) 內部呼叫 context.WithCancel(parent) 建立子 context。每個 g.Go() 的 goroutine 用這個子 context。errgroup 在收到第一個 non-nil error 時呼叫 cancel()，關閉子 context 的 done channel。其他 goroutine 如果有 select { case <-ctx.Done(): } 就會收到取消信號。
注意：errgroup 只 cancel context，不會強制 kill goroutine。如果 goroutine 內部不 check ctx.Done()（如 blocking I/O without timeout），它不會被取消。所以 必須 在 goroutine 內用 http.NewRequestWithContext(ctx, ...) 或 select ctx.Done()。

VQ3: Go 的 channel 是 lock-free 的嗎？如果不是，為什麼還這麼快？

答案：Go channel 內部 不是 lock-free — 它用 runtime mutex（比 sync.Mutex 更輕量的 internal lock）。但它仍然很快因為：

  • Runtime mutex 是 adaptive：先 spin 幾次（避免 context switch），拿不到才 park goroutine
  • Park/unpark goroutine 比 park/unpark OS thread 快 100x（只是修改 G 的狀態，不涉及 syscall）
  • Unbuffered channel 用 direct copy（sender 直接把值 copy 到 receiver 的 stack，zero allocation）
  • Compiler 會 inline 小 channel operations

對比：如果用 lock-free MPMC queue（如 Disruptor），raw throughput 確實更高（~200M ops/s vs channel ~50M ops/s），但 channel 的 select/range/close 語義讓程式碼簡潔 10x。Trade-off: 可讀性 vs 極致效能。

VQ4: 為什麼 Go 的 goroutine leak 是一個嚴重問題？如何偵測和預防？

答案：Goroutine 不會被 GC 回收（它不是記憶體物件 — 它是一個執行 entity）。如果一個 goroutine 永遠 block 在 channel read/write 或 lock acquire，它佔用的記憶體永遠不會釋放。大量 leak → OOM。
偵測：runtime.NumGoroutine() 持續增長、pprof goroutine profile。
預防：

  • Always 用 context.WithTimeout/WithCancel 確保 goroutine 有 exit path
  • Channel 發送方 close channel（reader 端 for range 自然退出）
  • Buffered channel 而非 unbuffered（避免 sender 永遠 block）
  • goleak 測試工具：在 TestMain 中檢查 test 結束後是否有 leaked goroutine

import redis, time, uuid

class DistributedLock:
    def __init__(self, redis_client, key, ttl=10):
        self.redis = redis_client
        self.key = f"lock:{key}"
        self.ttl = ttl
        self.token = str(uuid.uuid4())

    def acquire(self, timeout=5.0):
        deadline = time.time() + timeout
        while time.time() < deadline:
            if self.redis.set(self.key, self.token, nx=True, ex=self.ttl):
                return True
            time.sleep(0.05)
        return False

    def release(self):
        # CAS via Lua: only delete if we own it
        lua = """
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else return 0 end
        """
        return self.redis.eval(lua, 1, self.key, self.token) == 1

    def __enter__(self):
        if not self.acquire(): raise TimeoutError("Lock acquire failed")
        return self
    def __exit__(self, *a): self.release()

題目 30：Retry with Exponential Backoff + Jitter

import time, random

def retry_with_backoff(fn, max_retries=5, base_delay=1.0, max_delay=30.0):
    for attempt in range(max_retries + 1):
        try:
            return fn()
        except Exception as e:
            if attempt == max_retries: raise
            delay = min(max_delay, base_delay * (2 ** attempt))
            delay = random.uniform(0, delay)  # Full jitter
            time.sleep(delay)

func RetryWithBackoff(ctx context.Context, fn func() error, maxRetries int) error {
    baseDelay := time.Second
    for attempt := 0; attempt <= maxRetries; attempt++ {
        if err := fn(); err == nil { return nil }
        if attempt == maxRetries { return err }
        delay := baseDelay * time.Duration(1<<attempt)
        if delay > 30*time.Second { delay = 30 * time.Second }
        jitter := time.Duration(rand.Int63n(int64(delay)))
        select {
        case <-ctx.Done(): return ctx.Err()
        case <-time.After(jitter):
        }
    }
    return nil
}

題目 31：Idempotent Request Handler

import threading, time

class IdempotentHandler:
    def __init__(self, ttl=86400):
        self._results = {}
        self._in_progress = {}
        self._lock = threading.Lock()
        self._ttl = ttl

    def execute(self, key, operation):
        with self._lock:
            if key in self._results:
                result, ts = self._results[key]
                if time.time() - ts < self._ttl:
                    return result
            if key in self._in_progress:
                event = self._in_progress[key]
                self._lock.release()
                event.wait()
                self._lock.acquire()
                return self._results[key][0]
            event = threading.Event()
            self._in_progress[key] = event

        try:
            result = operation()
        except:
            with self._lock: del self._in_progress[key]
            event.set()
            raise

        with self._lock:
            self._results[key] = (result, time.time())
            del self._in_progress[key]
        event.set()
        return result

💬 Ch7 Follow-up

Q1: Redis distributed lock limitations?

A: Single Redis: SPOF. Clock drift in Redlock. Network partition → two holders. Solution: fencing token (monotonic counter attached to lock, downstream checks latest token).

Q2: Full jitter vs equal jitter vs decorrelated jitter?

A: Full: random(0, backoff). Equal: backoff/2 + random(0, backoff/2). Decorrelated: random(base, prev_delay*3). AWS analysis: full jitter best for reducing total client work and server load.

Q3: How to implement exactly-once in a distributed system?

A: Theoretically impossible (Two Generals). Practical: at-least-once delivery + idempotent receiver = effectively-once. Kafka EOS: transactional producer + consumer read_committed + server-side dedup by sequence number.

🧪 Ch7 驗證測驗（Verification Quiz）

VQ1: Redis 分散式鎖的 release 為什麼必須用 Lua script？如果用兩個 command (GET + DEL) 會怎樣？

答案：GET + DEL 之間有 race condition！場景：Client A 的鎖 TTL 到期被自動刪除 → Client B 取得新鎖 → Client A 的 release 執行 GET（看到值不是自己的... 或者更糟：GET 返回 B 的 token 但 A 沒檢查就直接 DEL）→ 刪掉 B 的鎖！
即使 A 有 check token：A 做 GET 確認是自己的 → 被 suspend → TTL 到期 → B 取鎖 → A resume 執行 DEL → 刪掉 B 的鎖。
Lua script 在 Redis 中是 atomic 的（Redis 單線程執行 Lua），所以 check-and-delete 一步完成，不會被打斷。

VQ2: Idempotency Key 存在 server side 需要存多久？太短或太長各有什麼問題？

答案：

  • 太短（如 1 分鐘）：Client 的 retry 可能在 key 過期後才到達 → server 視為新 request → 重複執行（如重複收費）。必須 > client 的最大重試時間窗口。
  • 太長（如 永久）：Storage 無限增長 → 最終 OOM 或儲存成本爆炸。而且太舊的 key 永遠不會被 retry 了（client 早就放棄了）。
  • 最佳實踐：24-48 小時（Stripe 用 24h）。覆蓋所有合理的重試窗口，且不會無限增長。用 TTL 自動過期（Redis EXPIRE 或 DynamoDB TTL）。
VQ3: 為什麼 exponential backoff 沒有 jitter 會導致 thundering herd？畫出時間線說明。

答案：假設 1000 個 client 同時失敗：

Without jitter:
t=0s: 1000 clients fail
t=1s: 1000 clients retry simultaneously → server overloaded → all fail
t=2s: 1000 clients retry → fail again
t=4s: 1000 clients retry → fail again
(永遠沒有 client 能成功因為永遠一起打)

With full jitter (delay = random(0, backoff)):
t=0s: 1000 clients fail
t=0-1s: ~uniformly spread retries (each at random time) → ~100/s → server handles fine
t=0-2s: next round spread over 2s → even more diluted
(很快恢復正常)

核心洞見：沒有 jitter 時，所有 client 的重試是「同步的」（synchronized），形成 periodic burst。加 jitter 後變成「非同步的」，流量被時間軸平滑化。

import threading
from collections import OrderedDict

class ThreadSafeLRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = OrderedDict()
        self.lock = threading.Lock()

    def get(self, key):
        with self.lock:
            if key not in self.cache: return -1
            self.cache.move_to_end(key)
            return self.cache[key]

    def put(self, key, value):
        with self.lock:
            if key in self.cache:
                self.cache.move_to_end(key)
                self.cache[key] = value
            else:
                if len(self.cache) >= self.capacity:
                    self.cache.popitem(last=False)
                self.cache[key] = value

// Go: Striped LRU for better concurrency
type StripedLRU struct {
    shards    []*lruShard
    numShards int
}

type lruShard struct {
    mu    sync.Mutex
    cache map[int]*list.Element
    list  *list.List
    cap   int
}

func NewStripedLRU(capacity, numShards int) *StripedLRU {
    s := &StripedLRU{numShards: numShards, shards: make([]*lruShard, numShards)}
    perShard := capacity / numShards
    for i := range s.shards {
        s.shards[i] = &lruShard{cache: make(map[int]*list.Element), list: list.New(), cap: perShard}
    }
    return s
}

func (s *StripedLRU) getShard(key int) *lruShard {
    return s.shards[key%s.numShards]
}
// Each shard has its own lock → 16x less contention with 16 shards

題目 33：Concurrent HashMap (Striped Locks)

import threading

class ConcurrentHashMap:
    def __init__(self, num_stripes=16):
        self.num_stripes = num_stripes
        self.buckets = [{} for _ in range(num_stripes)]
        self.locks = [threading.Lock() for _ in range(num_stripes)]

    def _stripe(self, key): return hash(key) % self.num_stripes

    def get(self, key):
        s = self._stripe(key)
        with self.locks[s]: return self.buckets[s].get(key)

    def put(self, key, value):
        s = self._stripe(key)
        with self.locks[s]: self.buckets[s][key] = value

    def remove(self, key):
        s = self._stripe(key)
        with self.locks[s]: return self.buckets[s].pop(key, None)

    def size(self):
        return sum(len(self.buckets[i]) for i in range(self.num_stripes))

🧪 Ch8 驗證測驗（Verification Quiz）

VQ1: Thread-Safe LRU 用單一 Lock 的缺點是什麼？Striped LRU 如何改善？有沒有 Striped 也解決不了的情況？

答案：

  • 單一 Lock 缺點：所有 get/put 操作 serialized。16 core machine 只用 1 core 的 capacity。高 QPS 下 lock contention 成為瓶頸。
  • Striped LRU 改善：key 按 hash 分到 16 shard，各 shard 獨立 lock。16 shards = 16x parallelism。不同 key 的操作互不阻塞。
  • Striped 解決不了的情況：Hot key（某個 key 被大量存取），所有 request 打同一個 shard → 回到單鎖瓶頸。解法：singleflight（去重）、local cache（每個 thread 有 L1 cache）、或把 hot key 複製到多個 shard（read replica）。
VQ2: ConcurrentHashMap 的 size() 為什麼不精確？如何在不鎖全部 stripes 的情況下取得精確 size？

答案：遍歷 N 個 stripe 各自取 size 再加總 — 但在你加總的時候其他 stripe 的 size 可能已經變了（non-atomic read across stripes）。結果是「某個時間段內」的近似值，不是某個精確時刻的 snapshot。
精確 size 的方法：

  • 方法 A — 鎖全部 stripes：按順序 acquire 所有 lock → 加總 → release。代價：O(N) lock + 暫時 block 所有操作。JDK 7 ConcurrentHashMap.size() 就這樣做（先嘗試不加鎖的估算，不一致才鎖全部）。
  • 方法 B — Atomic counter：維護一個全局 atomic size counter（每次 put +1, remove -1）。精確但 high contention on single variable。可用 LongAdder（per-CPU counter + lazy sum）。
  • 面試答案：「大多數場景不需要精確 size。如果需要，用 atomic LongAdder（contended 場景）或 lock-all（rare operation）。」
VQ3: 面試時被問「你的解法在 10 million QPS 下表現如何？」你會怎麼分析和回答？

答案：結構化的回答框架：

  1. Identify bottleneck：「在 10M QPS 下，每個 request 的 critical path 有哪些 shared resources？」— Lock、atomic、network call、DB query。
  2. Quantify contention：「假設 16 shards，每 shard 承受 625K QPS。每次 lock hold time ~100ns。contention probability = 625K × 100ns / 1s = 6.25% → 可接受。如果 hold time 是 1μs → 62.5% → 需要更多 shards。」
  3. Propose optimization：根據分析提出：增加 shard 數（256 shards）、使用 lock-free read path（atomic load for cache hit）、per-CPU local cache（L1 → shared L2 兩級快取）、batch processing（amortize lock acquisition）。
  4. State limitations：「Hot key 無論幾個 shard 都打同一個 → 需要 replication 或 singleflight。Memory overhead 隨 shard 數線性增長。」

面試加分：主動提到 benchmarking（「I'd run pprof/mutex profile to confirm the bottleneck before optimizing」）和 tradeoffs（「more shards = more memory + size() less accurate」）。
