# P02 Audit — Chapters 21–31: Identity, Security, and Governance

Audit date: 2026-10-01
Scope: current chapter practice questions only, plus a replacement specification of exactly 10 original question intents per chapter.
Constraint: these are original scenario intents derived from public exam objectives and AWS documentation, not recalled or reconstructed exam questions.

## Executive findings

- Chapters 21 and 22 have five hand-written questions each. Chapters 23–31 fall back to the same five-question generator: service selection, configuration list, mechanism, “least operational overhead,” and a generic multi-account rollout. The repeated structure tests recognition of prose copied from the chapter profile rather than architecture judgment.
- The generic distractors recur almost verbatim: “deploy every option,” “the managed service understands all business requirements,” “resource creation guarantees success,” “grant organization-wide AdministratorAccess,” and “create a second Region without moving data.” They are implausible in many contexts and make the answer visible without knowing AWS.
- Several generated questions contain two true statements but mark only the more detailed one correct. Chapter 23 mechanism question is the clearest example: both “trust policy controls who can assume; permission policy controls what the session can do” and the longer STS flow are correct.
- Chapters 23–31 have no service-specific question source mapping. They inherit broad IAM and Security Reference Architecture links even when testing KMS, ACM, WAF, GuardDuty, Inspector, Macie, AWS Backup, Object Lock, Artifact, or Audit Manager.
- Five questions per chapter cannot cover the chapter titles. The worst compression occurs in chapters 28–31, each of which combines three to six services with materially different control planes, data paths, failure modes, and exam cues.
- Replacement questions must test observable effects and concrete policy/configuration details. A list of setting names is not itself a useful question unless the scenario forces the learner to select or diagnose a particular setting.

## Chapter 21 — IAM Principal, Role, Policy, and Least Privilege

### Defects in the current questions

- The five questions are generally correct, but three belong primarily to later chapters: workforce federation duplicates chapter 24, third-party delegation duplicates chapter 23, and delegated role creation duplicates chapter 26. The chapter therefore under-tests IAM fundamentals.
- There is no direct test of principal types, user versus role credentials, group semantics, policy statement matching, resource-level permissions, MFA conditions, `iam:PassRole`, service-linked roles, credential reports, Access Analyzer, or policy-generation evidence.
- The Lambda trust-policy question says Lambda can obtain the session even though an actual Lambda execution role also requires the service to create/use the execution environment correctly. The intended trust-versus-permission distinction is sound, but the wording should focus on authorization after successful role assumption.
- The EC2 instance-profile question is useful but should distinguish the role from the instance profile and should test IMDS/SDK retrieval rather than imply credentials are “attached” as static values.
- The question set overrepresents obviously dangerous long-term keys and public buckets. Real exam distractors should offer plausible but wrong alternatives, such as an overbroad managed policy, a resource ARN mismatch, or a correct role attached to the wrong workload identity.

### Ten replacement question intents

1. **Human and workload principal separation.** Scenario: engineers need console access while an EC2 application reads one S3 prefix. **Correct principle:** workforce uses federation/Identity Center; EC2 uses an IAM role through an instance profile and temporary credentials. **Distractors:** one IAM user per account; shared access keys in Secrets Manager; attach the engineer’s role to EC2. **Concrete coverage:** principal, IAM user, role, instance profile, temporary credentials, `s3:GetObject` object ARN. **Map:** SAA-1.1; SAP-1.2. **Sources:** `SAA-D1`, `IAM-ROLE`, `STS`.
2. **Action and resource granularity.** Scenario: a reporting job may list `reports/` and read its objects but nothing else. **Correct principle:** `s3:ListBucket` uses the bucket ARN plus `s3:prefix`; `s3:GetObject` uses `arn:aws:s3:::bucket/reports/*`. **Distractors:** use the object ARN for both actions; use bucket ARN for both; grant `s3:*` and constrain only by role name. **Concrete coverage:** JSON `Statement`, Action/Resource pairing, Condition. **Map:** SAA-1.1. **Sources:** `SAA-D1`, `IAM-RBP`.
3. **Role versus instance profile.** Scenario: a role exists but EC2 receives no credentials. **Correct principle:** associate an instance profile containing the role with the instance; SDK credential provider retrieves temporary credentials. **Distractors:** attach the policy directly to the AMI; add the role ARN to a security group; call `AssumeRole` with an embedded root key. **Concrete coverage:** role, instance profile, service trust, credential provider chain. **Map:** SAA-1.1. **Sources:** `IAM-ROLE`, `STS`.
4. **Service role and `iam:PassRole`.** Scenario: a deployment operator creates a Lambda function with an approved execution role but receives AccessDenied. **Correct principle:** the operator needs scoped `iam:PassRole` for that role, commonly constrained with `iam:PassedToService`; the Lambda service must be trusted by the role. **Distractors:** grant `sts:AssumeRole` to the operator; add `lambda:*` to the execution role; trust the operator in the execution role instead of Lambda. **Concrete coverage:** `iam:PassRole`, service principal, role trust, caller permission. **Map:** SAA-1.1; SAP-2.3. **Sources:** `IAM-ROLE`, `IAM-CONDITION`.
5. **Policy statement matching.** Scenario: an Allow uses the correct action but an ARN for a different Region/account. **Correct principle:** every required element must match the request; unmatched Allow leaves implicit deny. **Distractors:** any Action match is enough; AWS chooses the closest ARN; policy order makes the first statement win. **Concrete coverage:** Effect, Action, Resource, Condition, implicit deny. **Map:** SAA-1.1. **Sources:** `IAM-EVAL`.
6. **MFA-protected sensitive operation.** Scenario: administrators may delete a critical resource only in an MFA-authenticated session. **Correct principle:** use a condition such as `aws:MultiFactorAuthPresent` where supported, while preserving a recovery path and testing federated-session context. **Distractors:** require an MFA device only at IAM-user creation; rely on a VPC CIDR; encrypt the resource with KMS and assume deletion is prevented. **Concrete coverage:** condition operators, request context, explicit Deny/Allow design. **Map:** SAA-1.1; SAP-1.2. **Sources:** `IAM-CONDITION`, `IAM-EVAL`.
7. **Least privilege from usage evidence.** Scenario: a migration role began broad and must be reduced after observation. **Correct principle:** use CloudTrail/IAM Access Analyzer policy generation and last-accessed data as evidence, then validate in stages. **Distractors:** retain AdministratorAccess because no incident occurred; remove random actions until production fails; replace the role with a shared user. **Concrete coverage:** Access Analyzer, CloudTrail evidence, staged policy refinement. **Map:** SAP-3.2. **Sources:** `SAP-D3`, `TRAIL`.
8. **Service-linked role recognition.** Scenario: enabling an AWS service creates a role with a fixed service-linked trust and permissions model. **Correct principle:** service-linked roles are owned/used by the linked service and should not be repurposed as application roles. **Distractors:** add human principals to its trust policy; store application keys in it; use it as an organization SCP. **Concrete coverage:** service-linked role purpose and lifecycle. **Map:** SAA-1.1. **Sources:** `IAM-ROLE`.
9. **IAM group limitations.** Scenario: a team wants EC2 to “join an IAM group” to inherit permissions. **Correct principle:** groups contain IAM users, not roles or workloads; attach a role to the workload and reusable policies to appropriate identities. **Distractors:** nest IAM groups; add the instance profile to a group; put a resource policy on the group. **Concrete coverage:** users, groups, roles, policy attachment. **Map:** SAA-1.1. **Sources:** `SAA-D1`, `IAM-ROLE`.
10. **Emergency access without shared permanent credentials.** Scenario: the IdP is unavailable and production needs controlled break-glass access. **Correct principle:** pre-provision tightly controlled emergency identities/roles with MFA, monitoring, short use procedures, and post-event credential rotation/review. **Distractors:** publish root credentials to the on-call vault without MFA; grant all engineers permanent admin; disable CloudTrail during recovery. **Concrete coverage:** root-user protection, MFA, monitored emergency path, credential report/CloudTrail. **Map:** SAP-1.2; SAP-3.2. **Sources:** `SAP-D1`, `SAP-D3`, `TRAIL`.

## Chapter 22 — IAM Policy Evaluation Logic

### Defects in the current questions

- The same-account resource-policy question is dangerously imprecise. “Usually allowed” hides AWS’s documented distinction among a policy grant to an IAM user ARN, IAM role ARN, role-session ARN, or federated-user session. A role-ARN grant is still limited by an implicit deny in a permissions boundary or session policy, while a direct role-session principal grant is evaluated differently.
- The guardrail-debugging question lists SCP, RCP, boundary, session policy, endpoint policy, and KMS policy in one answer without specifying the resource, principal, or request context. It tests recognition of a long list rather than evaluation logic.
- The set omits `NotAction`/`NotResource` hazards, condition-key absence and `IfExists`, session-policy intersection, VPC endpoint policies, Organizations resource control policies, and service-specific authorization.
- Cross-account evaluation is reduced to “both sides allow,” without testing role assumption as two separate requests: `sts:AssumeRole`, then the role session’s resource request.
- Explanations should stop saying all policy types form one simple intersection. Identity and resource policies can form a union within an account; boundaries/SCPs/session policies constrain different principals and grants; explicit Deny remains decisive.

### Ten replacement question intents

1. **Explicit Deny precedence.** Scenario: identity policy permits S3 read while a bucket policy denies requests without TLS. **Correct principle:** an applicable explicit Deny overrides every Allow; HTTPS merely prevents that Deny condition from matching. **Distractors:** identity policy has priority; newest policy wins; same-account ignores bucket Deny. **Concrete coverage:** `aws:SecureTransport`, explicit Deny, request context. **Map:** SAA-1.1. **Sources:** `IAM-EVAL`, `IAM-RBP`.
2. **Same-account grant to role ARN.** Scenario: bucket policy grants an IAM role ARN, identity policy is silent, and a permissions boundary omits `s3:GetObject`. **Correct principle:** the role-principal grant does not escape the boundary’s implicit deny; evaluate the exact principal type. **Distractors:** resource Allow always bypasses boundaries; identity Allow is always mandatory; bucket policies cannot grant role principals. **Concrete coverage:** role ARN, resource-based policy, boundary. **Map:** SAA-1.1; SAP-2.3. **Sources:** `IAM-EVAL`, `IAM-BOUNDARY`.
3. **Direct grant to role-session ARN.** Scenario: a supported resource policy names a specific assumed-role session ARN while the role’s boundary does not allow the action. **Correct principle:** a direct session-principal grant is permission to the session and is not limited by an implicit deny in the role’s identity policy/boundary, though explicit Deny, SCP, and other applicable controls still matter. **Distractors:** identical to a role-ARN grant; every boundary omission is an explicit Deny; session ARNs can never be principals. **Concrete coverage:** principal ARN type, assumed-role session, explicit versus implicit deny. **Map:** SAP-1.2; SAP-2.3. **Sources:** `IAM-EVAL`, `IAM-RBP`.
4. **Cross-account resource request.** Scenario: Account A role reads Account B S3 object. **Correct principle:** A must permit the principal and B must trust/allow it; either side’s applicable explicit Deny blocks access. **Distractors:** same Organization automatically grants access; only B’s bucket policy matters; only A’s AdministratorAccess matters. **Concrete coverage:** two-account evaluation, bucket/object ARN, `aws:PrincipalOrgID`. **Map:** SAA-1.1; SAP-1.4. **Sources:** `IAM-XACCT`.
5. **Session policy as a ceiling.** Scenario: a role permits S3 and DynamoDB, but `AssumeRole` passes a session policy allowing only one S3 prefix. **Correct principle:** effective session permissions are the intersection of role permissions and session policies, never an expansion. **Distractors:** session policy adds DynamoDB; session policy replaces trust policy; session policy persists after session expiry. **Concrete coverage:** inline/managed session policy, duration, intersection. **Map:** SAA-1.1; SAP-1.2. **Sources:** `STS-ASSUME`, `IAM-EVAL`.
6. **SCP does not grant.** Scenario: an SCP allow-list includes EC2, but a member-account role has no EC2 Allow. **Correct principle:** SCP sets the organization maximum; the role still needs an identity/resource Allow. **Distractors:** SCP provisions permissions; SCP affects only billing; SCP can constrain management-account principals. **Concrete coverage:** SCP inheritance, management-account exclusion, effective permissions. **Map:** SAA-1.1; SAP-1.4. **Sources:** `SCP`, `IAM-EVAL`.
7. **Endpoint policy as another filter.** Scenario: IAM and S3 bucket policies permit access, but requests through a gateway endpoint fail only for one bucket. **Correct principle:** inspect the endpoint policy and its principal/resource/action conditions; it does not grant absent IAM permissions. **Distractors:** route tables supersede IAM; endpoint policy applies to internet requests too; disable Block Public Access. **Concrete coverage:** endpoint policy, route-specific request path, identity/resource policies. **Map:** SAA-1.1; SAP-2.3. **Sources:** `IAM-EVAL`.
8. **KMS service-specific dual authorization.** Scenario: S3 `GetObject` succeeds for SSE-KMS metadata but object download fails on decrypt. **Correct principle:** caller needs S3 permission and applicable KMS authorization; key policy/grant and IAM/SCP constraints must permit `kms:Decrypt`. **Distractors:** `s3:GetObject` implies KMS decrypt; bucket encryption removes authorization checks; KMS alias policy controls access. **Concrete coverage:** key policy, IAM policy, encryption context, CloudTrail. **Map:** SAA-1.3; SAP-2.3. **Sources:** `KMS-POLICY`, `IAM-EVAL`.
9. **Condition key absent from context.** Scenario: a Deny uses a negated condition on a key not present in some service requests. **Correct principle:** choose operators and `...IfExists`/`Null` logic deliberately; absent keys can produce surprising matches, especially with negated operators. **Distractors:** missing key always means Allow; all global condition keys exist on every request; statement order resolves ambiguity. **Concrete coverage:** `Null`, `IfExists`, set operators, explicit Deny. **Map:** SAP-1.2; SAP-3.2. **Sources:** `IAM-CONDITION`, `IAM-EVAL`.
10. **`NotAction` safety.** Scenario: a Deny guardrail uses `NotAction` to exempt global services while restricting Regions. **Correct principle:** interpret `NotAction` relative to the statement’s Effect, Resource, and Condition; an Allow+`NotAction` is not “deny everything else.” **Distractors:** `NotAction` always means explicit Deny; it is equivalent to wildcard Action; Region restrictions apply identically to every global service. **Concrete coverage:** Effect + `NotAction`, `aws:RequestedRegion`, exception review. **Map:** SAP-1.2; SAP-3.2. **Sources:** `IAM-EVAL`, `IAM-CONDITION`, `SCP`.

## Chapter 23 — STS, Cross-account Access, and Federation

### Defects in the current questions

- All five questions are generated. The mechanism question has two substantively correct options: the trust/permissions separation and the fuller `AssumeRole` flow.
- The “service selection” question combines two independent use cases—third-party SaaS and employee federation—so no single mechanism completely answers the prompt.
- “Select STS and configure role ARN, session name…” is not a realistic architecture choice. Applications invoke STS operations through a federation/role design; STS is not deployed as a standalone component.
- The SAP rollout question is generic and unrelated to federation. It does not test session duration, role chaining, source identity, session tags, external ID, SAML/OIDC claims, or revocation limits.
- Cross-account resource policies are presented as a generic alternative without identifying services that support them or explaining when direct resource access is preferable to role assumption.

### Ten replacement question intents

1. **Two gates of cross-account role assumption.** Scenario: Account A operator assumes a role in Account B. **Correct principle:** A-side permissions must permit `sts:AssumeRole`; B role trust must accept the principal/conditions; the resulting session then uses B role permissions. **Distractors:** only the trust policy is needed; only the role permissions are needed; Organizations membership supplies both. **Concrete coverage:** caller identity policy, trust policy, role permission policy. **Map:** SAA-1.1; SAP-1.4. **Sources:** `STS-ASSUME`, `IAM-XACCT`.
2. **Third-party confused deputy.** Scenario: one SaaS vendor serves many customers and assumes a customer role. **Correct principle:** trust a controlled vendor principal and require a unique customer-specific `sts:ExternalId`; scope role permissions to customer resources. **Distractors:** secret role ARN; shared external ID for all customers; IAM user access keys. **Concrete coverage:** Principal, ExternalId Condition, temporary credentials. **Map:** SAA-1.1; SAP-1.2. **Sources:** `IAM-TRUST`, `STS-ASSUME`.
3. **External ID is not authentication.** Scenario: a design exposes an ExternalId in IaC and treats it as a password. **Correct principle:** ExternalId mitigates confused deputy but is not secret authentication; principal restriction and least privilege remain required. **Distractors:** rotate it like an access key; wildcard Principal is safe with ExternalId alone; it encrypts STS credentials. **Concrete coverage:** trust policy threat model. **Map:** SAP-1.2; SAP-2.3. **Sources:** `IAM-TRUST`, `STS-ASSUME`.
4. **Role chaining duration.** Scenario: a user federation session assumes role A, then role B for a long-running operation. **Correct principle:** role chaining has a maximum one-hour session for the chained role, regardless of a larger role maximum. **Distractors:** durations add together; second role gets 12 hours automatically; chaining creates permanent credentials. **Concrete coverage:** `DurationSeconds`, max session duration, chained session. **Map:** SAP-1.2. **Sources:** `STS-ASSUME`.
5. **Session policy narrowing.** Scenario: a broker issues sessions for one tenant prefix from a broader role. **Correct principle:** pass a scoped session policy; it can reduce but not exceed role permissions. **Distractors:** session policy changes the role trust; session policy expands the role; attach customer policy to the STS service. **Concrete coverage:** session policy size/managed policy ARNs, intersection. **Map:** SAP-2.3. **Sources:** `STS-ASSUME`, `IAM-EVAL`.
6. **SourceIdentity for audit continuity.** Scenario: users traverse multiple roles and CloudTrail must preserve the initiating employee ID. **Correct principle:** require/set `SourceIdentity` in the trust/federation flow and propagate it through role chaining. **Distractors:** rely only on arbitrary session names; put employee ID in ExternalId; infer identity from source IP. **Concrete coverage:** `sts:SourceIdentity`, trust condition, CloudTrail session context. **Map:** SAP-1.2; SAP-3.2. **Sources:** `STS-ASSUME`, `TRAIL`.
7. **Session tags and ABAC.** Scenario: federated department claims must restrict access to similarly tagged resources across accounts. **Correct principle:** map controlled attributes to session tags, authorize with principal/resource tag conditions, and mark needed tags transitive. **Distractors:** let users choose unrestricted tags; use resource names as the only boundary; assume tags override SCP Deny. **Concrete coverage:** `sts:TagSession`, transitive tags, `aws:PrincipalTag`, tag governance. **Map:** SAP-1.4; SAP-2.3. **Sources:** `STS-ASSUME`, `IAM-CONDITION`.
8. **SAML versus OIDC/web identity.** Scenario: corporate workforce uses a SAML IdP while a mobile app uses an OIDC provider. **Correct principle:** select the federation operation/integration matching the identity protocol; do not create IAM users or distribute AWS keys to clients. **Distractors:** embed an IAM user in the mobile app; use Directory Service for every OIDC token; make the application call role credentials without token validation. **Concrete coverage:** SAML assertion, web identity token, temporary credentials. **Map:** SAA-1.1; SAP-1.2. **Sources:** `STS`, `IDC`.
9. **Direct resource policy versus assume-role.** Scenario: Account A needs to send to one SQS queue in B, while a separate administrator needs broad B-account operations. **Correct principle:** direct queue resource policy can fit the narrow service action; role assumption fits a coherent permission set and B-account identity/session. **Distractors:** every cross-account access requires role assumption; every service supports resource policies; resource policy grants unrelated B resources. **Concrete coverage:** resource-policy support, principal identity, CloudTrail attribution. **Map:** SAA-1.1; SAP-1.4. **Sources:** `IAM-RBP`, `IAM-XACCT`.
10. **Revocation and temporary-session reality.** Scenario: an employee is disabled at the IdP during an active session. **Correct principle:** disabling prevents new federation but issued credentials remain valid until expiry unless service/control-specific revocation techniques are applied; choose short appropriate durations and incident controls. **Distractors:** all STS credentials disappear instantly; deleting browser cookies revokes API credentials; rotating an unrelated IAM user key ends the role session. **Concrete coverage:** session expiry, role revocation policy, incident response. **Map:** SAP-1.2; SAP-3.2. **Sources:** `STS`, `IAM-ROLE`.

## Chapter 24 — IAM Identity Center and Enterprise Identity

### Defects in the current questions

- All questions use the generic template. They repeat chapter 21’s workforce scenario without testing how Identity Center actually provisions or authorizes access.
- The current mechanism description makes permission-set deployment look instantaneous and universal; it does not test assignments, account-specific provisioned IAM roles, session duration, or the distinction between the identity source and AWS-account authorization.
- Directory Service appears only as a wrong adjacent component. There is no scenario distinguishing AWS Managed Microsoft AD, AD Connector, external IdP federation, SCIM provisioning, and Cognito.
- No question covers identity-source change risk, MFA responsibility, group provisioning, deprovisioning delay, break-glass access, delegated administration, or application assignments.
- The generated SAP question about canary rollout and rollback is not a meaningful identity-governance test.

### Ten replacement question intents

1. **Workforce SSO across accounts.** Scenario: Entra ID groups need access to 80 AWS accounts without local users. **Correct principle:** connect the external IdP to IAM Identity Center, provision users/groups, create permission sets, and assign group + account + permission set. **Distractors:** replicate IAM users; use Cognito user pools; deploy Managed AD solely for console SSO. **Concrete coverage:** identity source, assignment tuple, temporary role sessions. **Map:** SAA-1.1; SAP-1.4. **Sources:** `IDC`, `IDC-ID`, `IDC-PSET`.
2. **Permission-set mechanics.** Scenario: editing a permission set does not change one account’s effective role. **Correct principle:** permission sets are templates provisioned into selected accounts as IAM roles; inspect provisioning status and reprovision/update affected accounts. **Distractors:** attach the permission set to an SCP; edit the user’s security group; change the AWS access portal URL. **Concrete coverage:** managed/inline policy, permissions boundary, session duration, provisioning. **Map:** SAA-1.1; SAP-1.4. **Sources:** `IDC-PSET`.
3. **SCIM versus SAML.** Scenario: authentication works, but terminated users remain in Identity Center. **Correct principle:** SAML handles sign-in assertions; SCIM automates user/group provisioning and deprovisioning. **Distractors:** Route 53 removes users; permission sets synchronize directories; CloudTrail performs deprovisioning. **Concrete coverage:** identity lifecycle, SCIM bearer-token protection, group sync. **Map:** SAP-1.2; SAP-1.4. **Sources:** `IDC-ID`, `IDC`.

4. **Rate-based rule scope.** Scenario: block abusive login rates per client while traffic passes through proxies. **Correct principle:** configure a rate-based rule with the correct aggregation key/scope-down statement and only trust forwarded IP headers from controlled proxies. **Distractors:** NACL rate limiting; global request count without login scope; trust any client-supplied `X-Forwarded-For`. **Concrete coverage:** rate limit, aggregation, forwarded IP position/fallback. **Map:** SAA-1.2; SAP-2.3. **Sources:** `WAF`.
5. **Shield Standard versus Advanced.** Scenario: a revenue-critical public application needs DDoS response assistance, enhanced visibility, health-based detection, and qualifying cost protection. **Correct principle:** Shield Advanced on supported resources plus health checks/contact readiness; Standard already supplies baseline common L3/L4 protection. **Distractors:** WAF subscription alone supplies DRT/SRT; Advanced protects private east-west traffic; Shield decrypts and validates application payloads. **Concrete coverage:** protected resources, health check, proactive engagement/cost protection. **Map:** SAA-1.2; SAP-1.2. **Sources:** `SHIELD`.
6. **Firewall Manager as organization control plane.** Scenario: every current and future account must attach approved WAF policies to in-scope ALBs. **Correct principle:** use Firewall Manager with Organizations, a delegated admin, scope, and remediation policy; it centrally manages supported controls but does not process packets itself. **Distractors:** manually copy ACLs; deploy one central WAF for every regional ALB; use an SCP to inspect HTTP. **Concrete coverage:** policy scope, tags/resource types, auto-remediation. **Map:** SAP-1.4; SAP-3.2. **Sources:** `FMS`, `ORG`.
7. **Network Firewall route insertion.** Scenario: private-subnet egress must be inspected before NAT/IGW. **Correct principle:** deploy firewall endpoints in inspection subnets and route both forward and return paths symmetrically through the endpoint, then NAT/IGW as designed. **Distractors:** associate firewall policy without routes; send only return traffic through firewall; replace NAT with WAF. **Concrete coverage:** endpoint per AZ, route tables, symmetric path. **Map:** SAA-1.2; SAP-1.2. **Sources:** `NFW`.
8. **Stateless and stateful processing.** Scenario: a packet should be dropped immediately by a simple tuple rule while allowed flows need domain/application-aware inspection. **Correct principle:** place deterministic tuple handling in stateless rules/default forwarding and deeper flow-aware logic in stateful rule groups; account for rule-order mode. **Distractors:** security groups perform Suricata inspection; stateful rules see no connection state; WAF processes arbitrary TCP. **Concrete coverage:** stateless action, stateful engine, Suricata/domain rules. **Map:** SAP-1.2; SAP-2.3. **Sources:** `NFW`.
9. **WAF versus Network Firewall versus security groups.** Scenario: choose controls for SQL injection, outbound domain filtering, and database-port reachability. **Correct principle:** WAF for supported HTTP(S) L7 requests, Network Firewall for routed VPC traffic inspection, SG for stateful resource-level allow rules. **Distractors:** one NACL solves all three; Shield handles database authorization; IAM replaces network reachability controls. **Concrete coverage:** OSI visibility and placement. **Map:** SAA-1.2. **Sources:** `WAF`, `NFW`.
10. **Layered origin protection.** Scenario: CloudFront has WAF but attackers call a public ALB origin directly. **Correct principle:** restrict the origin to CloudFront using supported origin-facing controls/design, maintain application authorization, and verify the WAF is on the real ingress path. **Distractors:** hide ALB DNS name; add more WAF rules only at CloudFront; trust `Host` header as identity. **Concrete coverage:** bypass path, secret/custom header limitations, SG/prefix-list/OAC where supported. **Map:** SAA-1.2; SAP-3.2. **Sources:** `WAF`, `SAP-D3`.

## Chapter 30 — GuardDuty, Inspector, Macie, Detective, and Security Hub

### Defects in the current questions

- Current questions test only a memorized one-line service taxonomy. No finding, telemetry source, resource type, or response path appears in a concrete scenario.
- The GuardDuty profile risks implying customers must enable/store VPC Flow Logs or DNS logs for GuardDuty. GuardDuty consumes supported telemetry independently; its protection plans and coverage should be tested explicitly.
- Inspector coverage is underspecified: EC2, ECR container images, and Lambda scanning have different prerequisites and findings. It is not a generic host antivirus scanner.
- Macie is correctly associated with S3 but there is no distinction between automated discovery, classification jobs, custom identifiers, allow lists, bucket posture, or sampling.
- Detective and Security Hub are treated as passive “aggregation.” Missing are Detective investigation graphs/timelines, ASFF findings, Security Hub standards/controls, aggregation/central configuration, automation rules, EventBridge response, suppression, and ownership.

### Ten replacement question intents

1. **Credential-compromise detection.** Scenario: an IAM access key calls APIs from unusual infrastructure and begins discovery. **Correct principle:** GuardDuty analyzes supported AWS telemetry and produces threat findings; route high-severity findings through EventBridge to an owned response workflow. **Distractors:** Inspector detects API behavior; Macie rotates the key; Security Hub itself observes every API call without a detector. **Concrete coverage:** detector, finding severity/type, EventBridge response. **Map:** SAA-1.2; SAP-3.2. **Sources:** `GD`, `TRAIL`.
2. **GuardDuty protection plans.** Scenario: organization needs S3 data-event, EKS audit/runtime, malware, and database-login threat coverage. **Correct principle:** enable the applicable GuardDuty protection plans per supported resource/Region and validate organization auto-enable settings; base GuardDuty does not imply every optional plan is enabled. **Distractors:** enable CloudTrail trail only; Inspector covers all runtime threats; Security Hub standard turns on every plan. **Concrete coverage:** delegated admin, member accounts, plan status. **Map:** SAP-1.2; SAP-3.2. **Sources:** `GD`.
3. **Trusted IP list versus threat list.** Scenario: approved scanner traffic creates findings while known malicious indicators should raise findings. **Correct principle:** trusted IP lists suppress findings for trusted sources; threat lists add indicators to detect—use both sparingly and govern changes. **Distractors:** swap their purpose; use suppression rules to authorize traffic; add all corporate NAT IPs without risk review. **Concrete coverage:** detector list association, false-positive control. **Map:** SAP-3.2. **Sources:** `GD`.
4. **Inspector resource coverage.** Scenario: prioritize CVEs across EC2, ECR images, and Lambda packages. **Correct principle:** enable the corresponding Inspector scan types, satisfy each resource’s prerequisites, and use risk context/fix availability in remediation. **Distractors:** GuardDuty is the vulnerability scanner; Inspector scans S3 objects for PII; one golden AMI scan permanently covers all running instances. **Concrete coverage:** scan type, inventory/agentless coverage as supported, ECR rescan duration. **Map:** SAA-1.2; SAP-3.2. **Sources:** `INSPECTOR`.
5. **Image pipeline response.** Scenario: a critical ECR image finding appears after deployment. **Correct principle:** block/promote by governed severity policy, rebuild from a patched base, redeploy immutable workloads, and retain finding evidence; do not patch only the running container. **Distractors:** suppress finding globally; enable WAF; encrypt the image with KMS. **Concrete coverage:** ECR continuous/scan configuration, EventBridge/Security Hub integration. **Map:** SAP-3.2. **Sources:** `INSPECTOR`, `SHUB`.
6. **Macie sensitive-data discovery.** Scenario: discover PII in a subset of a large S3 estate and identify exposed buckets. **Correct principle:** use Macie inventory/automated discovery or scoped classification jobs with managed/custom identifiers, sampling, and allow lists; it is S3-focused. **Distractors:** Inspector scans object content; GuardDuty classifies PII; Macie scans EBS/database rows universally. **Concrete coverage:** job scope, sampling, custom data identifier, findings. **Map:** SAA-1.3; SAP-1.2. **Sources:** `MACIE`.
7. **Detective investigation after a finding.** Scenario: analysts must connect a GuardDuty role-compromise finding to IPs, API activity, instances, and timeline. **Correct principle:** Detective supports graph/timeline investigation from integrated data; it does not block, isolate, or patch. **Distractors:** Detective replaces CloudTrail retention; Detective automatically revokes credentials; Macie builds the behavior graph. **Concrete coverage:** behavior graph, finding groups, member accounts. **Map:** SAP-3.2. **Sources:** `DETECTIVE`, `GD`.
8. **Security Hub ingestion and normalization.** Scenario: SOC needs one queue for GuardDuty, Inspector, Macie, and partner findings. **Correct principle:** Security Hub CSPM receives normalized ASFF findings, aggregates and routes them, while source services remain the detectors. **Distractors:** Security Hub scans hosts itself; CloudTrail findings are automatically vulnerabilities; enabling Security Hub automatically remediates everything. **Concrete coverage:** integrations, ASFF, aggregation Region, EventBridge. **Map:** SAA-1.2; SAP-1.2. **Sources:** `SHUB`.
9. **Security standards versus AWS Config.** Scenario: an enabled Security Hub control reports a noncompliant resource. **Correct principle:** understand the control/check and Config dependency where applicable; a finding is evidence, not necessarily prevention or remediation. **Distractors:** pass status proves no security risk; Config records API callers; an SCP is a detective scan. **Concrete coverage:** standards, controls, Config recorder/rules, finding workflow. **Map:** SAP-1.2; SAP-3.2. **Sources:** `SHUB`, `CONFIG`.
10. **Organization-wide detection operating model.** Scenario: hundreds of accounts/Regions need central findings without making the management account the SOC workstation. **Correct principle:** use supported delegated administrators, organization auto-enrollment/central configuration, regional aggregation where supported, severity routing, ticket owner, containment runbooks, and metrics. **Distractors:** export all findings manually monthly; share management-account root; centralize findings but assign no response owner. **Concrete coverage:** delegated admin, member coverage, automation rules/EventBridge, suppression governance. **Map:** SAP-1.2; SAP-1.4; SAP-3.2. **Sources:** `GD`, `INSPECTOR`, `MACIE`, `SHUB`, `ORG`.

## Chapter 31 — Data Classification, Backup, Retention, and Compliance

### Defects in the current questions

- The chapter spans data classification, AWS Backup, S3 Object Lock, Backup Vault Lock, Artifact, and Audit Manager but has only five generic questions. The existing source mapping is broad IAM/SRA material rather than service-specific documentation.
- The statement that replication “copies logical deletion” is too broad. Behavior depends on service and configuration; S3 replication has specific delete-marker and version-deletion semantics. It should not be taught as a universal rule.
- Current questions conflate backup, replication, archive, retention, legal hold, and compliance evidence. These controls have different objectives: availability, point-in-time recovery, cost tiering, immutability, and audit proof.
- Object Lock governance/compliance modes are mentioned only as a mechanism option. No question tests versioning, object-version scope, retention period/date, legal holds, bypass permission, or the irreversibility of compliance retention.
- AWS Backup lacks questions on plans, assignments, vault access/KMS, cross-account copy prerequisites, logically air-gapped vaults where applicable, Vault Lock, restore testing, and recovery credentials. Artifact and Audit Manager are almost absent.
- Existing task mapping to SAP-4.1 is only justified when the scenario explicitly evaluates data/compliance constraints before migration; it should not be attached to every chapter question.

### Ten replacement question intents

1. **Classify before selecting controls.** Scenario: public assets, customer PII, payment records, and transient cache have different obligations. **Correct principle:** classify confidentiality, integrity, availability, retention/deletion, residency, and recovery needs first; map each class to access, encryption, logging, backup, and lifecycle controls. **Distractors:** encrypt everything with one key and stop; retain every dataset forever; choose storage only by price. **Concrete coverage:** data owner, class/tag, retention schedule, RPO/RTO. **Map:** SAA-1.3; SAP-1.2; SAP-4.1 only when used in migration discovery. **Sources:** `SAA-D1`, `SAP-D1`.
2. **Backup versus replication.** Scenario: application must survive AZ failure and also recover yesterday’s uncorrupted state after ransomware. **Correct principle:** replication/HA serves availability; versioned backups/recovery points serve historical recovery, and both require tested isolation. **Distractors:** synchronous replica is immutable backup; backup alone provides zero-RTO failover; lifecycle archive is a live replica. **Concrete coverage:** RPO/RTO, failure domain, point-in-time recovery. **Map:** SAA-1.3; SAP-2.2. **Sources:** `BACKUP`, `BACKUP-TEST`.
3. **AWS Backup plan and assignment.** Scenario: tag-selected production resources need daily/weekly retention and cross-Region copies. **Correct principle:** define backup rules with schedule, lifecycle, vault, copy actions, and resource assignments; verify each resource type’s feature/Region support. **Distractors:** one S3 lifecycle rule backs up every service; Config snapshots are restorable backups; copying an AMI covers databases automatically. **Concrete coverage:** plan, rule, vault, tags, copy action. **Map:** SAA-1.3; SAA-4.1; SAP-2.2. **Sources:** `BACKUP`.
4. **Cross-account recovery isolation.** Scenario: ransomware in a workload account must not erase recovery points. **Correct principle:** copy to a dedicated backup account/vault with separately governed access and compatible KMS policies, then test restore by an emergency role. **Distractors:** another vault in the same admin boundary is always sufficient; an SCP Allow grants KMS decrypt; copy job success proves restore access. **Concrete coverage:** destination vault policy, KMS key, Organizations trust, restore role. **Map:** SAP-1.2; SAP-2.2; SAP-2.3. **Sources:** `BACKUP`, `KMS-POLICY`.
5. **Backup Vault Lock.** Scenario: recovery points must be protected from deletion or retention shortening. **Correct principle:** configure Vault Lock mode and retention controls deliberately; compliance mode becomes immutable after its grace period, whereas governance controls can be overridden by sufficiently authorized users. **Distractors:** vault access policy alone is WORM; KMS rotation locks retention; Object Lock settings apply automatically to all Backup resources. **Concrete coverage:** governance/compliance mode, changeable grace time, min/max retention. **Map:** SAP-1.2; SAP-2.2. **Sources:** `BACKUP-LOCK`.
6. **S3 Object Lock modes.** Scenario: records require seven-year WORM, while another bucket needs administrator-overridable protection during rollout. **Correct principle:** use compliance mode for non-bypassable retention and governance mode for privileged bypass; Object Lock applies to object versions in a versioned bucket. **Distractors:** legal hold has a fixed seven-year date; governance can never be bypassed; bucket policy Deny and Object Lock are identical. **Concrete coverage:** mode, retain-until date/period, version ID, `s3:BypassGovernanceRetention`. **Map:** SAA-1.3; SAP-1.2. **Sources:** `OBJECT-LOCK`.
7. **Retention versus legal hold.** Scenario: normal seven-year retention expires, but litigation requires selected records to remain indefinitely until release. **Correct principle:** retention uses a time period/date; legal hold is independent of time and remains until explicitly removed. **Distractors:** legal hold automatically expires with lifecycle; retention can only be set bucket-wide; deleting current version removes a locked prior version. **Concrete coverage:** object-version legal hold, retention coexistence, lifecycle/delete behavior. **Map:** SAA-1.3; SAP-1.2. **Sources:** `OBJECT-LOCK`.
8. **Automated restore testing.** Scenario: dashboards show every backup job completed, but auditors require proof of recoverability. **Correct principle:** schedule restore tests for representative resources, validate application/data integrity and dependencies, capture restore time/results, and clean up test resources safely. **Distractors:** backup completion equals restore proof; checksum of a recovery point proves application startup; replication lag is restore testing. **Concrete coverage:** restore-testing plan, selection, validation callback/evidence. **Map:** SAP-2.2; SAP-3.2. **Sources:** `BACKUP-TEST`.
9. **Artifact versus Audit Manager versus Config/CloudTrail.** Scenario: auditor requests AWS SOC report, customer-control evidence, resource configuration history, and API actor history. **Correct principle:** Artifact provides AWS reports/agreements; Audit Manager organizes customer evidence against frameworks; Config tracks resource configuration/compliance; CloudTrail records API activity. **Distractors:** Artifact scans customer resources; Audit Manager enforces every control; Config stores complete application logs. **Concrete coverage:** report, assessment/framework, configuration item/rule, trail/event. **Map:** SAA-1.3; SAP-1.2; SAP-3.2. **Sources:** `ARTIFACT`, `AUDIT`, `CONFIG`, `TRAIL`.
10. **Retention-aware migration/modernization.** Scenario: an on-prem archive moves to AWS but deletion obligations, legal holds, searchable hot window, and seven-year retention differ by record class. **Correct principle:** inventory/classify first, map retention and access requirements to storage/lifecycle/Object Lock/backup controls, migrate metadata and chain-of-custody evidence, and test retrieval/deletion exceptions. **Distractors:** place everything in one immutable tier forever; replication proves legal compliance; migrate bytes first and reconstruct retention dates later. **Concrete coverage:** retention metadata, lifecycle transitions, Object Lock, audit evidence, retrieval test. **Map:** SAA-4.1; SAP-4.1; SAP-2.3. **Sources:** `OBJECT-LOCK`, `BACKUP`, `AUDIT`, `SAP-D2`.
