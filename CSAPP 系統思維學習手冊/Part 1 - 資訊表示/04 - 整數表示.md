# 第 4 章　整數：Unsigned 與二補數

> [!abstract] 本章地圖
> **核心問題**：w 個位元怎麼同時表示正數與負數？同一組位元在 signed 與 unsigned 之間轉換時，數值為什麼會「突然變很大」？
>
> **你會學到**：
> - 用公式與手算，把位元串解讀成 unsigned 值與二補數值，並說出 TMin、TMax、UMax
> - 解釋 signed 與 unsigned 互轉時「位元不變、解讀改變」，手算轉換結果
> - 預測 C 的 integer promotion 與 usual arithmetic conversions，看出 `-1 < 0u` 這類比較陷阱
> - 分辨 sign extension、zero extension 與截斷，知道它們在組合語言裡長什麼樣
> - 避開 `size_t` 迴圈與 `read` 回傳值的經典 bug，判斷什麼時候該用 unsigned
>
> **前置知識**：第 3 章（位元、十六進位、位元運算與 shift）
>
> **對應 CS:APP 3e**：第 2 章 2.2 節

## 4.1 故事：CI 全綠，production 卻認不出 JPEG

`thumbd` 的 CI 最近改用 ARM64 Linux 的機器跑測試，速度快了一倍。某個週五，小安合併了一個小改動：把判斷檔案格式的程式從呼叫 libmagic 改成自己看檔頭，省下一次函式庫呼叫。測試全部通過，部署到 production。

半小時後，SRE 阿哲在頻道裡貼了一張圖：JPEG 的上傳失敗率從 0% 跳到 100%，錯誤訊息是 `unsupported format`，PNG 卻一切正常。production 的機器是 x86-64 Linux。

小安的程式長這樣：

```c
// not-runnable
const char *buf = read_head(fd, 2);
if (buf[0] == 0xFF && buf[1] == 0xD8)     /* JPEG 檔案以 FF D8 開頭 */
    return FORMAT_JPEG;
```

小安百思不解：同一份原始碼、同一個測試檔，為什麼在 ARM64 上判斷正確，在 x86-64 上永遠不成立？老周看了一眼說：「`char` 到底有沒有號，是平台決定的。在 x86-64 Linux 上，`0xFF` 這個 byte 讀進 `char` 是 -1，拿去和 255 比，當然不相等。」

老周順手又指出同一個檔案裡的另一行：

```c
// not-runnable
ssize_t n = read(fd, &hdr, sizeof hdr);
if (n < sizeof hdr)                        /* 讀不到完整的 header 就放棄 */
    return -1;
```

「`read` 失敗時回傳 -1。你猜 `-1 < sizeof hdr` 是真還是假？」答案是假：-1 被轉成一個巨大的 unsigned 數，這個檢查完全擋不住錯誤，程式會帶著沒讀到資料的 `hdr` 繼續往下跑。

這兩個 bug 都出自同一個主題：**整數在機器裡是固定寬度的位元串，「有沒有號」是解讀規則，不是位元本身的屬性；C 會在你沒注意的時候換掉解讀規則。**本章先講清楚兩種編碼，再看 C 什麼時候、怎麼在它們之間轉換。整數的加法、乘法與溢位留到第 5 章。

## 4.2 C 的整數型別

C 的整數型別有兩個維度：**寬度**（幾個位元）與**有無號**（signed 或 unsigned）。下表是 LP64（64 位元 Linux、macOS）上的實際範圍：

| 型別 | bytes | 最小值 | 最大值 |
|---|---|---|---|
| `signed char` | 1 | -128 | 127 |
| `unsigned char` | 1 | 0 | 255 |
| `short` | 2 | -32,768 | 32,767 |
| `unsigned short` | 2 | 0 | 65,535 |
| `int` | 4 | -2,147,483,648 | 2,147,483,647 |
| `unsigned int` | 4 | 0 | 4,294,967,295 |
| `long`、`long long` | 8 | -9,223,372,036,854,775,808 | 9,223,372,036,854,775,807 |
| `unsigned long`、`size_t` | 8 | 0 | 18,446,744,073,709,551,615 |

觀察兩件事。第一，同樣寬度的 signed 與 unsigned 能表示的「數量」相同，都是 2^w 個，只是範圍平移了。第二，signed 的範圍不對稱：負數比正數多一個，-128 存在但 +128 不存在。4.4 節會解釋為什麼。

這些數字不用背，`<limits.h>` 提供了 `INT_MIN`、`INT_MAX`、`UINT_MAX`、`LONG_MAX` 等巨集，`<stdint.h>` 則有 `INT32_MIN`、`UINT64_MAX` 等固定寬度版本。程式裡需要上下限時一律用巨集，不要手寫數字。

### 沒寫 signed 也沒寫 unsigned 的 `char`

`short`、`int`、`long` 沒有寫 unsigned 時就是 signed。唯一的例外是 `char`：C 標準規定 `char`、`signed char`、`unsigned char` 是三個不同的型別，而單純的 `char` 有沒有號**由平台決定**。這正是故事中第一個 bug 的根源。我們用 `clang -target <平台> -O1 -S` 編譯同一個函式 `int f(void) { char c = (char)0xFF; return c; }`，看編譯器在各平台上產生的回傳值：

| 平台 | 編譯器產生的指令 | `char` 是 | `(char)0xFF` 的值 |
|---|---|---|---|
| x86-64 Linux | `movl $-1, %eax` | signed | -1 |
| AArch64 Linux | `mov w0, #255` | unsigned | 255 |
| macOS on Apple Silicon | `mov w0, #-1` | signed | -1 |

ARM64 Linux 與 x86-64 Linux 正好相反，這就是 `thumbd` 在 CI 通過、在 production 失敗的原因。同樣是 ARM64，Apple 的平台卻選擇 signed，所以小安在自己的 Mac 上測試也會失敗，只是沒有人在 Mac 上跑過這個測試。gcc 與 clang 提供 `-fsigned-char` 與 `-funsigned-char` 強制指定，但更好的做法是：**處理原始 byte 時一律用 `unsigned char` 或 `uint8_t`，只有真正存放文字時才用 `char`。**

## 4.3 Unsigned 編碼：每一位都是正的權重

先從簡單的開始。一個 w 位元的位元串 x = [x_{w−1}, …, x_1, x_0]，用 **unsigned 編碼**解讀時，每一位的權重是 2 的冪，最低位權重 2^0，最高位權重 2^{w−1}：

```text
B2U(x) = x_{w−1}·2^{w−1} + x_{w−2}·2^{w−2} + … + x_1·2^1 + x_0·2^0
```

B2U 是 binary to unsigned 的縮寫。以 4 位元為例：

```text
 位元      1      0      1      1
 權重     2^3    2^2    2^1    2^0
          8      4      2      1
 B2U(1011) = 8 + 0 + 2 + 1 = 11
```

w 位元能表示的最小值是全 0，也就是 0；最大值是全 1，記為 **UMax**：

```text
UMax_w = 2^{w−1} + … + 2 + 1 = 2^w − 1
```

4 位元的 UMax 是 15，8 位元是 255，32 位元是 4,294,967,295。這個編碼是一對一的：每一個 0 到 UMax 之間的整數，恰好對應一個位元串，反之亦然。數學上稱為 **bijection**（雙射），它保證「位元串」和「值」之間可以來回轉換而不遺失資訊。

Unsigned 編碼就是第 3 章的十六進位換算，沒有新東西。真正需要動腦的是下一節：負數要放在哪裡？

## 4.4 二補數：最高位的權重是負的

### 先看兩個不成功的設計

最直覺的負數表示法是 **sign-magnitude**（符號-大小）：最高位當正負號，其餘位當絕對值。4 位元的 `1011` 就是 -3。它的問題有兩個：0 有兩種寫法（`0000` 是 +0，`1000` 是 -0），而且加法電路必須先看符號再決定要相加還是相減，硬體變得複雜。

另一個設計是 **ones' complement**（一補數）：把正數的每一位都翻轉就是它的負數，`0011`（3）的負數是 `1100`。它一樣有兩個 0（`0000` 與 `1111`），加法還要處理「端迴進位」。這兩種編碼今天只在少數地方看得到：IEEE 754 浮點數的正負號用的是 sign-magnitude 的概念（第 6 章），IP 封包的 checksum 用的是 ones' complement 加法。

### 二補數的定義

**二補數**（two's complement）用一個簡單的改動解決了這些問題：**最高位的權重改成負的** −2^{w−1}，其餘各位和 unsigned 完全相同。

```text
B2T(x) = −x_{w−1}·2^{w−1} + x_{w−2}·2^{w−2} + … + x_1·2^1 + x_0·2^0
```

B2T 是 binary to two's complement。同樣看 4 位元的 `1011`：

```text
 位元      1      0      1      1
 權重    −2^3    2^2    2^1    2^0
         −8      4      2      1
 B2T(1011) = −8 + 0 + 2 + 1 = −5
```

直覺可以這樣建立：最高位是 0 時，它和 unsigned 一模一樣，表示 0 到 2^{w−1} − 1 的正數；最高位是 1 時，先「欠」2^{w−1}，其餘位元再把值往回加。所以最高位雖然不是單純的「正負號」，卻剛好決定正負：它是 1，值就一定是負的。下面的 4 位元對照表完整列出 16 種位元串：

| 位元 | B2U | B2T | 位元 | B2U | B2T |
|---|---|---|---|---|---|
| 0000 | 0 | 0 | 1000 | 8 | **-8** |
| 0001 | 1 | 1 | 1001 | 9 | -7 |
| 0010 | 2 | 2 | 1010 | 10 | -6 |
| 0011 | 3 | 3 | 1011 | 11 | -5 |
| 0100 | 4 | 4 | 1100 | 12 | -4 |
| 0101 | 5 | 5 | 1101 | 13 | -3 |
| 0110 | 6 | 6 | 1110 | 14 | -2 |
| 0111 | 7 | **7** | 1111 | 15 | **-1** |

左半邊（最高位為 0）兩種解讀相同；右半邊兩種解讀剛好差 16，也就是 2^4。這個「差 2^w」的觀察是 4.5 節轉換規則的全部基礎。

把 16 個位元串排成一圈，更能看出二補數的結構：

```text
                       0000
                        0
             1111  -1        1  0001
         1110  -2                2  0010
       1101  -3                    3  0011
       1100  -4                    4  0100
         1011  -5                5  0101
             1010  -6        6  0110
                1001  -7  7  0111
                       -8
                      1000
     （順時針加 1。0111 再加 1 跳到 1000：從 TMax 7 跳到 TMin -8）
```

這個圈像一個只有 4 格的里程表：順時針走一步就是加 1，走到 `1111` 再加 1 會繞回 `0000`。在二補數的解讀下，-1 加 1 正好是 0，加法不需要任何特殊處理，和 unsigned 用的是同一套電路；這就是二補數勝出的原因。唯一的「斷點」在 `0111` 與 `1000` 之間：7 加 1 變成 -8，這就是溢位，第 5 章會詳細討論。

### TMin、TMax 與不對稱

二補數能表示的最大值 **TMax** 是最高位為 0、其餘全 1；最小值 **TMin** 是最高位為 1、其餘全 0：

```text
TMax_w = 2^{w−1} − 1        TMin_w = −2^{w−1}        UMax_w = 2^w − 1
```

| w | TMin | TMax | UMax | TMin 的 hex | -1 的 hex |
|---|---|---|---|---|---|
| 8 | -128 | 127 | 255 | `0x80` | `0xFF` |
| 16 | -32,768 | 32,767 | 65,535 | `0x8000` | `0xFFFF` |
| 32 | -2,147,483,648 | 2,147,483,647 | 4,294,967,295 | `0x80000000` | `0xFFFFFFFF` |
| 64 | -9,223,372,036,854,775,808 | 9,223,372,036,854,775,807 | 18,446,744,073,709,551,615 | `0x8000000000000000` | `0xFFFFFFFFFFFFFFFF` |

這張表有三個工作上很有用的規律：

1. **|TMin| = TMax + 1**。0 佔用了「非負」那一半的一個位置，所以負數多一個。後果是 TMin 沒有對應的正數：`-INT_MIN` 在 `int` 裡放不下，這是第 5 章溢位漏洞的常客。
2. **-1 是全部位元為 1**，無論寬度多少。看到 `0xFFFFFFFF` 或 `0xFF`，要立刻想到「這可能是 -1」。
3. **UMax = 2 × TMax + 1**。同寬度的 unsigned 最大值，剛好是 signed 最大值的兩倍再加一。

### 手算：16 位元的 -12345

給定一個負數，怎麼寫出它的二補數位元？一個方法是利用「右半邊的 B2T 與 B2U 差 2^w」：-12345 的 16 位元二補數，和 unsigned 的 2^16 − 12345 = 53191 是同一組位元。

```text
53191 = 0xCFC7
      = 1100 1111 1100 0111

驗算 B2T：
 −2^15 + 2^14 + 2^11 + 2^10 + 2^9 + 2^8 + 2^7 + 2^6 + 2^2 + 2^1 + 2^0
 = −32768 + 16384 + 2048 + 1024 + 512 + 256 + 128 + 64 + 4 + 2 + 1
 = −32768 + 20423
 = −12345   ✓
```

另一個常用的捷徑是「**全部翻轉，再加 1**」：12345 是 `0x3039` = `0011 0000 0011 1001`，翻轉後是 `1100 1111 1100 0110`，加 1 得到 `1100 1111 1100 0111` = `0xCFC7`。兩種方法結果相同；為什麼翻轉加一就是取負，要用到加法的性質，第 5 章會證明。

### C 標準與二補數

很長一段時間，C 標準允許三種有號整數表示法，二補數只是其中之一。實務上幾十年來所有主流 CPU 都用二補數，C23 終於正式規定有號整數必須是二補數。但要注意：**表示法是二補數，不代表 signed overflow 就會「繞一圈」**。C 仍然把 signed overflow 定為 undefined behavior，編譯器可以依此最佳化，第 5 章會看到這造成的後果。

> [!warning] 常見誤解
> 「寫 `-2147483648` 就能得到 `INT_MIN`。」C 會先看 `2147483648` 這個字面常數，它超出 `int` 的範圍，所以型別被定成 `long`（LP64）；接著才套用負號，得到的是一個 `long`。在 C90 的規則下、在 `long` 只有 32 位元的機器上，`2147483648` 的型別甚至會是 `unsigned long`，加上負號後仍是正的 2147483648。這就是 `<limits.h>` 把 `INT_MIN` 寫成 `(-INT_MAX - 1)` 或 `(-2147483647 - 1)` 這類形式的原因。需要 TMin 時用巨集，不要自己寫。

## 4.5 Signed 與 unsigned 的轉換：位元不變，解讀改變

在 C 裡把 signed 轉成同寬度的 unsigned（或反過來）時，**底層的位元一個都不變，只是換了解讀規則**。所以轉換結果可以直接從 4.4 節那張表讀出來：`1011` 從 B2T 的 -5 變成 B2U 的 11。

從兩個公式相減，就能得到轉換的通式。B2U 與 B2T 只差在最高位的權重：一個是 +2^{w−1}，一個是 −2^{w−1}，相差 2^w。所以：

```text
B2U(x) − B2T(x) = x_{w−1} · 2^w

T2U(x) = x + 2^w   若 x < 0
         x         若 x ≥ 0

U2T(u) = u − 2^w   若 u > TMax
         u         若 u ≤ TMax
```

用數線來看，非負的那一半原地不動，負的那一半整段平移 2^w：

```text
 二補數   TMin ─────────── −1  0 ─────────── TMax
                │                 │
                │  +2^w           │  不變
                ▼                 ▼
 unsigned          0 ─────────── TMax  TMax+1 ─────────── UMax
                   (原本的 0..TMax)    (原本的 TMin..−1)
```

讀這張圖時要注意方向：二補數的負數區間 [TMin, −1] 被搬到 unsigned 的上半段 [TMax+1, UMax]。所以 -1 變成 UMax，TMin 變成 TMax + 1。反過來，unsigned 的上半段轉回 signed 時會變成負數。

| 原始值與型別 | 位元 | 轉換後型別 | 結果 | 算法 |
|---|---|---|---|---|
| `int16_t` -12345 | `0xCFC7` | `uint16_t` | 53,191 | -12345 + 65536 |
| `int32_t` -1 | `0xFFFFFFFF` | `uint32_t` | 4,294,967,295 | -1 + 2^32 = UMax |
| `int32_t` TMin | `0x80000000` | `uint32_t` | 2,147,483,648 | TMax + 1 |
| `uint32_t` 3,000,000,000 | `0xB2D05E00` | `int32_t` | -1,294,967,296 | 3,000,000,000 − 2^32 |
| `uint8_t` 200 | `0xC8` | `int8_t` | -56 | 200 − 256 |

最後兩列是 unsigned 轉 signed 且超出範圍的情況。C17 規定這是 **implementation-defined**（由實作定義）的行為，不是 undefined behavior；gcc 與 clang 都明確定義為「取模 2^w」，也就是上表的結果。C23 規定了二補數表示法，但為了可攜性，仍不要寫出依賴這個轉換的程式；需要這種語意時，明確地寫出來並加上註解。

### 轉換在哪裡發生

C 的轉換分兩種。**顯式轉換**（explicit cast）是你寫出來的 `(unsigned)x`；**隱式轉換**（implicit conversion）是編譯器依規則自動做的，發生在：

- 把值指派給不同型別的變數：`unsigned u = -1;`
- 傳參數給函式：`void resize(size_t n)` 被呼叫成 `resize(-1)`
- 二元運算的兩邊型別不同：`n < sizeof hdr`（下一節）
- 函式回傳值和宣告的回傳型別不同

`printf` 是一個特殊陷阱：它是可變參數函式，不會轉換參數型別，只依格式字串去解讀位元。`printf("%u", -1)` 印出 4294967295，`printf("%d", 3000000000u)` 印出 -1294967296。開啟 `-Wall`（含 `-Wformat`）後，編譯器會在格式與型別不符時警告。

## 4.6 C 的隱式轉換：Integer Promotion 與比較陷阱

C 在做任何算術或比較之前，會先把兩邊的運算元轉成同一個型別。這套規則有兩層。

### 第一層：Integer promotion

**Integer promotion**（整數提升）：比 `int` 窄的型別（`char`、`short` 與它們的 unsigned 版本、`_Bool`），在運算前一律先轉成 `int`（如果 `int` 放得下它所有的值，在 LP64 上永遠如此）。

這解釋了故事裡的第一個 bug。`buf[0] == 0xFF` 的左邊是 `char`，右邊的字面常數 `0xFF` 是 `int`，值 255。比較前 `buf[0]` 先被提升成 `int`：

```text
 檔案中的 byte：1111 1111
                     │
       char 是 signed？
       ┌─────────────┴──────────────┐
      是（x86-64 Linux）           否（AArch64 Linux）
       │ sign extension            │ zero extension
       ▼                           ▼
 int: 0xFFFFFFFF = −1          int: 0x000000FF = 255
       │                           │
  −1 == 255 → 假                255 == 255 → 真
  （回報 unsupported format）  （測試通過）
```

同一個 byte，經過「擴展」的方式不同，提升後的值就不同（擴展的細節在 4.7 節）。修法是讓 buffer 的型別如實反映它的內容：`const unsigned char *buf`，提升後必定是 0 到 255。

### 第二層：Usual arithmetic conversions

提升之後，如果兩邊型別仍然不同，C 套用 **usual arithmetic conversions**（一般算術轉換）。對整數來說，簡化後的規則是：

```text
 兩邊都提升完了，型別還不一樣？
   │
   ├─ 有無號相同 → 轉成比較寬的那個
   │
   └─ 一個 signed、一個 unsigned
        │
        ├─ unsigned 那邊的寬度 ≥ signed 那邊 → 兩邊都轉成那個 unsigned 型別
        │      （例：int vs unsigned int、long vs size_t）
        │
        └─ signed 那邊比較寬，而且放得下 unsigned 的所有值 → 兩邊都轉成那個 signed 型別
               （例：long vs unsigned int，在 LP64 上）
```

最重要、也最危險的是中間那條：**寬度相同時，unsigned 贏。**負數一旦被轉成 unsigned，就變成一個很大的正數。下面這些比較全部是在 macOS arm64 上實際執行的結果（4.11 節有完整程式）：

| 運算式 | 轉換後實際比較的是 | 結果 | 解說 |
|---|---|---|---|
| `-1 < 0` | `int` 比 `int` | 1 | 正常 |
| `-1 < 0u` | `4294967295u < 0u` | **0** | -1 被轉成 unsigned 的 UMax |
| `2147483647u > -2147483647 - 1` | `2147483647u > 2147483648u` | **0** | TMin 轉成 unsigned 是 TMax + 1 |
| `(unsigned char)200 > (signed char)-1` | `200 > -1`（都提升成 `int`） | 1 | 窄型別先提升，沒有 unsigned 參與 |
| `1u > -1L` | `1L > -1L` | 1 | LP64 的 `long` 放得下所有 `unsigned int`，轉成 `long` |
| `n < sizeof hdr`（n 是 `ssize_t` 的 -1） | `18446744073709551615 < 24` | **0** | `ssize_t` 與 `size_t` 同寬，unsigned 贏 |

倒數第二列提醒我們規則依平台而定：在 Windows 的 LLP64 上 `long` 只有 32 位元，放不下所有 `unsigned int`，於是兩邊都轉成 `unsigned long`，`1u > -1L` 變成 0。

最後一列就是故事裡的第二個 bug。`sizeof` 的結果是 `size_t`，`read` 回傳的是 `ssize_t`，在 LP64 上兩者都是 64 位元，所以 -1 被轉成 2^64 − 1，比 24 大得多，檢查不成立，錯誤被放過。正確的寫法是先處理負數，再在確定非負後轉型比較：

```c
// not-runnable
ssize_t n = read(fd, &hdr, sizeof hdr);
if (n < 0)
    return -1;                        /* 錯誤：看 errno */
if ((size_t)n < sizeof hdr)
    return -1;                        /* short read：資料不夠（第 27 章） */
```

這兩個 bug 都有編譯器警告可以抓：clang 不加任何選項就會對 `char` 和 255 的比較發出「永遠為假」的警告，gcc 則由 `-Wextra` 啟用的 `-Wtype-limits` 提醒；在 C 中，`-Wextra` 也會開啟 `-Wsign-compare`，對 `n < sizeof hdr` 發出「比較不同有無號的整數」警告。`thumbd` 的建置當時有上百條既有警告，新的那兩條淹沒在裡面，沒有人看到。

## 4.7 擴展：Sign Extension 與 Zero Extension

把一個窄的整數放進寬的型別時（例如 `int16_t` 轉 `int32_t`），多出來的高位要填什麼？規則是：

- **Zero extension**（零擴展）：unsigned 數在高位補 0。這顯然不改變值，因為新加的位元權重都乘以 0。
- **Sign extension**（符號擴展）：二補數在高位補「原本的最高位」。正數補 0，負數補 1。

```text
 4 位元 −5 = 1011
             │
             └─ 最高位是 1 → 往左補 1
 8 位元     1111 1011

 驗算：−128 + 64 + 32 + 16 + 8 + 2 + 1 = −128 + 123 = −5   ✓
```

為什麼補 1 能保持值不變？看每多補一個位元的效果就知道了：原本最高位的權重是 −2^{w−1}；擴展一位之後，新的最高位權重是 −2^w，原本那一位變成 +2^{w−1}。兩者合計 −2^w + 2^{w−1} = −2^{w−1}，和原來一樣。每補一位都保持不變，所以補幾位都可以。

在 x86-64 上，擴展有專門的指令。下面是 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - ext.c` 的結果（刪去 directive），四個函式分別從指標讀一個 `int8_t`、`uint8_t`、`int32_t`、`uint32_t`，回傳更寬的型別：

```asm
load_signed:                    # int32_t load_signed(const int8_t *p)
	movsbl	(%rdi), %eax
	retq
load_unsigned:                  # int32_t load_unsigned(const uint8_t *p)
	movzbl	(%rdi), %eax
	retq
load_int:                       # int64_t load_int(const int32_t *p)
	movslq	(%rdi), %rax
	retq
load_uint:                      # uint64_t load_uint(const uint32_t *p)
	movl	(%rdi), %eax
	retq
```

`movsbl` 是 move with sign extension, byte to long（在 AT&T 語法中 `l` 指 32 位元），`movzbl` 是 zero extension 的版本，`movslq` 把 32 位元 sign-extend 成 64 位元。最後一個沒有專門的 zero extension 指令，是因為 x86-64 有一條規則：寫入 32 位元暫存器（如 `%eax`）時，硬體會自動把對應 64 位元暫存器（`%rax`）的高 32 位清成 0。這些指令第 7 章會再詳細介紹。重點是：**C 的型別決定了編譯器選哪一條指令**，和 3.9 節的 `sar`／`shr` 道理相同。

### 同時改變寬度與有無號

如果一次轉換同時改變寬度與有無號，例如把 `int16_t` 轉成 `uint32_t`，C 的規則等同於**先依原本的型別改變寬度，再改變有無號**。所以 `int16_t` 的 -12345 會先 sign-extend 成 32 位元的 `0xFFFFCFC7`，再解讀成 unsigned，得到 4,294,954,951，而不是先變成 `uint16_t` 的 53191 再 zero-extend。這個順序在 4.11 節的程式會實際驗證。

### 修好 `thumbd` 的 JPEG 判斷

下面這段程式重現故事中的 bug 並修好它：

```c
#include <stdio.h>

/* 從檔案讀進來的前兩個 byte：JPEG 的 SOI marker 是 0xFF 0xD8 */
static const char raw[2] = {(char)0xFF, (char)0xD8};

static int is_jpeg_buggy(const char *buf) {
    return buf[0] == 0xFF && buf[1] == 0xD8;      /* char 先被提升成 int */
}

static int is_jpeg_fixed(const unsigned char *buf) {
    return buf[0] == 0xFF && buf[1] == 0xD8;      /* unsigned char 提升後是 255 */
}

int main(void) {
    printf("char is %s on this platform\n", (char)0xFF < 0 ? "signed" : "unsigned");
    printf("buf[0] promoted to int = %d\n", raw[0]);
    printf("buggy: %d\n", is_jpeg_buggy(raw));
    printf("fixed: %d\n", is_jpeg_fixed((const unsigned char *)raw));
    return 0;
}
```

在 macOS arm64（Apple clang 21，`-O1 -Wall -Wextra`）上編譯，編譯器先發出兩條警告：

```text
warning: result of comparison of constant 216 with expression of type 'const char' is always false [-Wtautological-constant-out-of-range-compare]
warning: result of comparison of constant 255 with expression of type 'const char' is always false [-Wtautological-constant-out-of-range-compare]
```

執行結果：

```text
char is signed on this platform
buf[0] promoted to int = -1
buggy: 0
fixed: 1
```

Apple Silicon 的 `char` 和 x86-64 Linux 一樣是 signed，所以這裡重現了 production 的行為：`0xFF` 提升成 -1，和 255 不相等。警告訊息很直白地說「這個比較永遠為假」，編譯器其實早就知道答案了。若在 AArch64 Linux 上執行，第一行會是 `unsigned`，buggy 版本也會回傳 1，這正是 CI 沒有抓到的原因。

## 4.8 截斷：把寬的值塞進窄的型別

反方向的操作是**截斷**（truncation）：把 w 位元的值轉成 k 位元（k < w）時，C 直接丟掉高位的 w − k 位，只留下低 k 位，再用新型別的規則解讀。

```text
 int32_t 53191 = 0000 0000 0000 0000 1100 1111 1100 0111
                 └──────── 丟掉 ───────┘└────── 保留 ──────┘
 int16_t        =                       1100 1111 1100 0111
                 最高位是 1 → B2T = −12345
```

用數學描述：截斷後的 unsigned 值是原值 **mod 2^k**；如果目標是 signed，再把這個結果用 U2T 轉換。

| 原值 | 轉成 | 低位 | mod 2^k | 結果 |
|---|---|---|---|---|
| `int32_t` 53,191 | `int16_t` | `0xCFC7` | 53,191 | 53,191 − 65,536 = **-12,345** |
| 70,000 | `uint16_t` | `0x1170` | 70,000 − 65,536 = 4,464 | **4,464** |
| `int32_t` -1 | `uint8_t` | `0xFF` | 255 | **255** |
| `int64_t` 3,000,000,000 | `int32_t` | `0xB2D05E00` | 3,000,000,000 | 3,000,000,000 − 2^32 = **-1,294,967,296** |

截斷在工作上最常見的出處是「把 `size_t` 存進 `int`」：

```c
// not-runnable
int len = strlen(body);             /* body 超過 2 GiB 時，len 會變成負數或錯的值 */
char *copy = malloc(len + 1);
```

2 GiB 以下一切正常，所以這類 bug 很少在測試中出現。一旦有人上傳 3 GB 的檔案，`len` 被截斷成負數，`len + 1` 再被轉成 `size_t` 傳給 `malloc`，結果可能是配置失敗、配置一個很小的 buffer，接著溢位（第 5 章、第 11 章）。從 API 拿到的大小，就用 API 的型別（`size_t`、`ssize_t`、`off_t`）存起來，不要「順手」改成 `int`。

和 4.5 節一樣，unsigned 的截斷完全由標準定義；截斷成 signed 而值放不下時則是 implementation-defined，gcc 與 clang 的行為就是上表的結果。

## 4.9 `size_t` 與迴圈陷阱

`size_t` 是 unsigned 型別，這意味著它**永遠 ≥ 0**，而且 0 減 1 會繞到最大值。這兩個性質加起來，造成了 C 程式最常見的一類 bug。

**陷阱一：倒數迴圈永遠不會結束。** `thumbd` 的垂直翻轉功能要從最後一列往回處理：

```c
// not-runnable
for (size_t row = height - 1; row >= 0; row--)      /* row >= 0 永遠為真 */
    copy_row(dst, src, height - 1 - row);
```

`row` 減到 0 之後再減 1，變成 2^64 − 1，條件 `row >= 0` 依然成立，迴圈繼續用一個巨大的索引存取記憶體，最後 segfault。gcc 的 `-Wextra` 會透過 `-Wtype-limits` 警告「這個比較永遠為真」；clang 21 則要另外加 `-Wtautological-unsigned-zero-compare` 才會警告（實測 `-Wall -Wextra` 沒有提示），所以不能只靠預設警告。正確的倒數寫法是把減法移進條件：

```c
// not-runnable
for (size_t row = height; row-- > 0; )             /* 先判斷 row > 0，再減 1 */
    copy_row(dst, src, height - 1 - row);
```

**陷阱二：`len - 1` 在 len 為 0 時變成最大值。** `for (size_t i = 0; i < len - 1; i++)` 在 len 為 0 時會跑 2^64 − 1 次。改寫成 `i + 1 < len`，就不會有減法下溢的問題。

**陷阱三：兩個 unsigned 相減的結果永遠不是負的。** `if (strlen(a) - strlen(b) > 0)` 想判斷 a 是否比 b 長，但只要兩者不等長，結果都為真。直接寫 `strlen(a) > strlen(b)`。

下面這段程式把這些行為實際跑一次：

```c
#include <stdio.h>
#include <string.h>

int main(void) {
    size_t len = 0;
    printf("len - 1 = %zu\n", len - 1);                  /* 0 減 1 繞到 SIZE_MAX */

    const char *a = "jpg", *b = "jpeg";
    printf("strlen(a) - strlen(b) = %zu, > 0 ? %d\n",
           strlen(a) - strlen(b), strlen(a) - strlen(b) > 0);

    int rows[4] = {10, 11, 12, 13};
    size_t h = 4;
    for (size_t i = h; i-- > 0; )                        /* 正確的倒數迴圈 */
        printf("%d ", rows[i]);
    printf("\n");
    return 0;
}
```

在 macOS arm64（Apple clang 21，`-O1`）上執行：

```text
len - 1 = 18446744073709551615
strlen(a) - strlen(b) = 18446744073709551615, > 0 ? 1
13 12 11 10
```

`"jpg"` 比 `"jpeg"` 短，3 − 4 卻得到 18446744073709551615，所以「a 比 b 長」被判斷為真。倒數迴圈則正確地從索引 3 印到 0，最後一次 `i-- > 0` 看到 `i` 為 0 時條件不成立而結束（`i` 雖然隨後變成 `SIZE_MAX`，但已經不會再用到它）。注意 unsigned 的「繞一圈」是完全定義好的行為，不是 UB，所以編譯器不會幫你攔下來，只能靠警告與 code review。

## 4.10 什麼時候該用 unsigned

既然 unsigned 這麼容易出事，乾脆全部用 signed？這是一個業界一直有爭論的問題。比較務實的原則是：**選型別看「值的語意」和「會做什麼運算」**。

| 情境 | 建議 | 原因 |
|---|---|---|
| 位元遮罩、旗標、shift、雜湊、checksum | unsigned（`uint32_t` 等） | 位元運算與 shift 的行為完整定義；需要模 2^w 的語意 |
| 外部格式的欄位（檔頭、協定） | 照規格的寬度與有無號 | 位元布局由外部決定 |
| 呼叫 API 的大小與長度 | `size_t`，和 API 一致 | 避免截斷與比較時的轉換 |
| 可能相減、可能出現負數的量（座標差、時間差、偏移） | signed（`int64_t`、`ptrdiff_t`） | 差值可以是負的，減法不會意外繞到最大值 |
| 只是「不會是負數」的計數或索引 | 視專案慣例；若用 unsigned，所有減法與倒數迴圈要特別小心 | 「非負」不等於「需要 unsigned」 |
| 錯誤時要回傳 -1 的函式 | signed（`ssize_t`、`int`） | 需要一個不合法的值表示錯誤 |

`thumbd` 的團隊在這次事件後訂了三條規則：原始 byte 一律 `unsigned char`／`uint8_t`；寬高、像素數與 buffer 大小用 `size_t`，任何減法前先比較大小；座標與偏移量的計算用 `int64_t`，確定非負且在範圍內後才轉成 `size_t` 去索引陣列。

其他語言的選擇也反映了這個取捨。Java 沒有 unsigned 整數，`byte` 是 -128 到 127，所以 Java 讀二進位資料時常看到 `b & 0xFF`，那正是手動做 zero extension；從協定讀到的 `uint32` 通常要放進 `long`。Python 的整數沒有固定寬度，不會溢位也不會繞圈，但和 C 交換資料時要自己用 `struct` 指定寬度。Rust 與 Go 則乾脆**禁止**不同整數型別之間的隱式轉換，`u32` 和 `i64` 相比要明確轉型，從語言層面消滅了 4.6 節的整類 bug。

## 4.11 動手做：自己驗證編碼、轉換與比較

### 程式一：用 Python 產生 4 位元對照表

4 位元的世界小到可以全部列出來。這段 Python 程式直接實作 B2U、B2T 與 T2U 的公式，並驗證「轉換後位元不變」：

```python
W = 4  # 用 4 位元的小世界，所有規則都能一眼看完

def b2u(bits: str) -> int:
    return sum(int(b) << i for i, b in enumerate(reversed(bits)))

def b2t(bits: str) -> int:
    # 最高位的權重是 -2^(w-1)，其餘位元和 unsigned 相同
    return -int(bits[0]) * 2 ** (W - 1) + b2u(bits[1:])

def t2u(x: int) -> int:
    return x + 2 ** W if x < 0 else x

print("bits  B2U  B2T  T2U(B2T)")
for v in range(2 ** W):
    bits = format(v, f"0{W}b")
    t = b2t(bits)
    assert t2u(t) == b2u(bits)           # 驗證：轉換後位元不變
    print(f"{bits}  {b2u(bits):>3}  {t:>3}  {t2u(t):>3}")

tmin, tmax, umax = -2 ** (W - 1), 2 ** (W - 1) - 1, 2 ** W - 1
print(f"TMin={tmin} TMax={tmax} UMax={umax}  |TMin|=TMax+1: {abs(tmin) == tmax + 1}")
```

用 Python 3 在 macOS arm64 上執行：

```text

0000    0    0    0
0001    1    1    1
0010    2    2    2
0011    3    3    3
0100    4    4    4
0101    5    5    5
0110    6    6    6
0111    7    7    7
1000    8   -8    8
1001    9   -7    9
1010   10   -6   10
1011   11   -5   11
1100   12   -4   12
1101   13   -3   13

```

輸出和 4.4 節的表完全一致。`assert` 沒有觸發，代表對每一個位元串，先用 B2T 解讀、再用 T2U 轉換，得到的都是 B2U 的值：轉換確實只是換解讀規則。把 `W` 改成 8，就能得到 8 位元的完整對照表。

### 程式二：在 C 裡看位元如何被擴展與截斷

```c
#include <stdint.h>
#include <stdio.h>

/* 印出低 w 個位元，以及這組位元在該型別下代表的值 */
static void show(const char *label, uint64_t v, int w, long long value) {
    printf("%-28s ", label);
    for (int i = w - 1; i >= 0; i--)
        putchar((v >> i) & 1 ? '1' : '0');
    printf("  %lld\n", value);
}

int main(void) {
    /* 1. 有號 → 無號：位元不變，解讀改變 */
    int16_t s = -12345;
    uint16_t u = (uint16_t)s;
    show("int16 -12345", u, 16, s);
    show("same bits as uint16", u, 16, u);

    /* 2. 擴展：signed 補符號位元，unsigned 補 0 */
    int32_t sx = s;
    uint32_t zx = u;
    uint32_t both = (uint32_t)s;          /* 先依 int16 擴展，再改解讀成 unsigned */
    show("int16 -> int32 (sign ext)", (uint32_t)sx, 32, sx);
    show("uint16 -> uint32 (zero ext)", zx, 32, zx);
    show("int16 -> uint32", both, 32, both);

    /* 3. 截斷：只留下低位，再用新型別解讀 */
    int32_t big = 53191;
    int64_t three_g = 3000000000;
    show("int32 53191", (uint32_t)big, 32, big);
    show("(int16_t) 53191", (uint16_t)big, 16, (int16_t)big);
    show("(int32_t) 3000000000", (uint32_t)three_g, 32, (int32_t)three_g);
    return 0;
}
```

在 macOS arm64（Apple clang 21，`-O1`）上執行：

```text
int16 -12345                 1100111111000111  -12345
same bits as uint16          1100111111000111  53191
int16 -> int32 (sign ext)    11111111111111111100111111000111  -12345
uint16 -> uint32 (zero ext)  00000000000000001100111111000111  53191
int16 -> uint32              11111111111111111100111111000111  4294954951
int32 53191                  00000000000000001100111111000111  53191
(int16_t) 53191              1100111111000111  -12345
(int32_t) 3000000000         10110010110100000101111000000000  -1294967296
```

逐組對照：

1. 前兩行的位元完全相同，只是值從 -12345 變成 53191，相差 65536 = 2^16，正是 T2U 的公式。
2. 第三、四行是同一組 16 位元分別做 sign extension 與 zero extension：前者高位補了 16 個 1，值仍是 -12345；後者補 0，值仍是 53191。擴展都保持了「原型別下的值」。
3. 第五行驗證 4.7 節的轉換順序：`int16_t` 轉 `uint32_t` 時先 sign-extend（高位補 1），再解讀成 unsigned，得到 4294954951 = 2^32 − 12345。
4. 最後三行是截斷：53191 的低 16 位就是第一行那組位元，解讀成 `int16_t` 變回 -12345；3,000,000,000 塞進 `int32_t` 後最高位是 1，變成負數。

### 程式三：比較運算的轉換

```c
#include <stdint.h>
#include <stdio.h>
#include <sys/types.h>

struct img_header { uint32_t magic, width, height, flags, offset, size; };  /* 24 bytes */

/* 模擬 read()：失敗時回傳 -1 */
static ssize_t fake_read(int fail) { return fail ? -1 : (ssize_t)sizeof(struct img_header); }

#define SHOW(expr) printf("%-38s -> %d\n", #expr, (int)(expr))

int main(void) {
    SHOW(-1 < 0);
    SHOW(-1 < 0u);
    SHOW(-1 < (int)0u);
    SHOW(2147483647 > -2147483647 - 1);
    SHOW(2147483647u > -2147483647 - 1);
    SHOW((unsigned char)200 > (signed char)-1);
    SHOW((uint16_t)1 > (int16_t)-1);
    SHOW(1u > (int64_t)-1);
    SHOW(1u > -1L);

    ssize_t n = fake_read(1);
    if (n < sizeof(struct img_header))           /* 錯誤：n 被轉成 size_t */
        printf("buggy check: rejected n=%zd\n", n);
    else
        printf("buggy check: accepted n=%zd (as size_t: %zu)\n", n, (size_t)n);
    if (n < 0 || (size_t)n < sizeof(struct img_header))   /* 正確：先處理負數 */
        printf("fixed check: rejected n=%zd\n", n);
    return 0;
}
```

在 macOS arm64（Apple clang 21，`-O1 -Wall -Wextra`）上編譯時，編譯器對錯誤的那一行發出警告：

```text
warning: comparison of integers of different signs: 'ssize_t' (aka 'long') and 'unsigned long' [-Wsign-compare]
```

執行結果：

```text
-1 < 0                                 -> 1
-1 < 0u                                -> 0
-1 < (int)0u                           -> 1
2147483647 > -2147483647 - 1           -> 1
2147483647u > -2147483647 - 1          -> 0
(unsigned char)200 > (signed char)-1   -> 1
(uint16_t)1 > (int16_t)-1              -> 1
1u > (int64_t)-1                       -> 1
1u > -1L                               -> 1
buggy check: accepted n=-1 (as size_t: 18446744073709551615)
fixed check: rejected n=-1
```

前九行就是 4.6 節表格的來源。注意 `-1 < 0u` 與 `-1 < (int)0u` 只差一個轉型，結果就相反：把 unsigned 那邊明確轉成 signed，比較才回到「數學上的意思」。`(uint16_t)1 > (int16_t)-1` 為真，是因為兩者都先提升成 `int`，unsigned 根本沒有機會參與。最後兩行重現了故事中的 bug：`read` 失敗的 -1 被當成 18446744073709551615，順利通過「至少要有 24 個 byte」的檢查；修正後的版本先判斷負數，正確地拒絕。

## 4.12 在工作上怎麼用

### 讓編譯器幫你找轉換 bug

這類 bug 最便宜的抓法是編譯器警告。建議的設定與它們抓得到的問題：

| 選項 | 抓到什麼 | 備註 |
|---|---|---|
| `-Wall` | `printf` 格式與型別不符（`-Wformat`）、位元運算與比較混用沒加括號 | 所有專案都該開；clang 對 `char` 與超出範圍常數的比較不加選項就會警告 |
| `-Wextra` | `-Wsign-compare`：signed 與 unsigned 比較；gcc 另含 `-Wtype-limits`（unsigned `>= 0` 永遠為真） | C 中 `-Wsign-compare` 由 `-Wextra` 開啟（C++ 則由 `-Wall`） |
| `-Wconversion` | 可能遺失資料的隱式截斷（`int64_t` → `int16_t`） | 既有專案打開後警告可能很多，可以逐個目錄處理 |
| `-Wsign-conversion` | signed 與 unsigned 之間的隱式轉換 | 最嚴格，適合解析器、協定、安全相關的程式 |
| `-Werror` | 把警告當錯誤 | 避免新警告淹沒在舊警告裡，正是 `thumbd` 缺的那一環 |
| `-fsanitize=implicit-conversion`（clang） | 執行時偵測改變了值的隱式截斷 | 實際支援的檢查項目依 clang 版本與平台而定 |

以 clang 21 在 macOS 上用 `-fsanitize=implicit-conversion` 編譯 `int16_t s = big;`（big 是 70000），執行時會印出 `runtime error: implicit conversion from type 'int64_t' ... of value 70000 (64-bit, signed) to type 'int16_t' ... changed the value to 4464 (16-bit, signed)`。在測試環境開這個選項，等於讓每一次截斷都留下證據。

### 看到這些數字，先懷疑轉換

在 log、監控或除錯器裡看到下列數字，幾乎可以直接判斷是轉換問題：

| 看到的值 | 很可能是 | 常見原因 |
|---|---|---|
| 4,294,967,295 或 `0xFFFFFFFF` | 32 位元的 -1 被當成 unsigned | 錯誤碼 -1 存進 `uint32_t` 或用 `%u` 印出 |
| 18,446,744,073,709,551,615 | 64 位元的 -1 被當成 `size_t` | `read` 回傳 -1、`len - 1` 在 len 為 0 時 |
| 接近 2^32 或 2^64 的巨大值 | 小的負數轉成 unsigned | 兩個 `size_t` 相減，被減數比較小 |
| 65,535、255 | 16 位元或 8 位元的 -1 | 協定欄位、`uint8_t` 存了 -1 |
| -2,147,483,648 或 -1 這類「不該是負數」的值 | unsigned 大數轉成 signed，或截斷 | `int len = strlen(...)`、`uint32_t` 存進 `int` |
| -128、-1 出現在 byte 資料中 | `char` 是 signed，`0x80`～`0xFF` 被解讀成負數 | 用 `char` 處理二進位資料 |

### 跨語言與跨系統的整數邊界

後端工程師常遇到的情境是資料在系統之間流動時的寬度與有無號不一致：

- **協定與 IDL**：protobuf 的 `uint32` 在 Java 中對應 `int`，大於 2^31 − 1 的值在 Java 裡看起來是負數，要用 `Integer.toUnsignedLong` 這類方法取得正確值。
- **資料庫**：MySQL 有 `INT UNSIGNED`，PostgreSQL 沒有 unsigned 整數型別。從 MySQL 遷移到 PostgreSQL 時，`INT UNSIGNED` 的欄位要改成 `BIGINT`，否則大於 2^31 − 1 的值會放不下。
- **C 擴充模組與 FFI**：Python 呼叫 C 函式時，Python 的大整數傳進 `int32_t` 參數會被檢查或截斷，依綁定工具而定；從 C 回傳的 `size_t` 到 Python 是正確的大整數，但再傳回另一個接受 `int` 的 C 函式就可能截斷。
- **JSON**：JSON 數字本身沒有寬度，但 JavaScript 用 double 存放，超過 2^53 的整數 ID 會失去精度（第 6 章）。很多 API 因此把 64 位元 ID 當字串傳。

### Code review 檢查清單

審查 C／C++ 程式時，看到下列樣式就停下來：

- 用 `char` 或 `char *` 處理檔案、網路或影像的原始 byte。
- `ssize_t`／`int` 回傳值直接和 `sizeof`、`strlen`、`size_t` 比較，沒有先處理負數。
- 任何 `size_t` 或 unsigned 的減法，特別是 `len - 1`、`end - start`、`a - b > 0`。
- 倒數迴圈的索引是 unsigned，條件是 `>= 0`。
- 把 `size_t`、`ssize_t`、`off_t`、指標差存進 `int`。
- 用 `-1` 當「沒有值」的哨兵，卻存在 unsigned 變數裡（只能和 `(size_t)-1` 比較，容易寫錯）。

## 4.13 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 同一段程式在 ARM64 Linux 正確、在 x86-64 錯誤（或相反），和 byte 資料有關 | `char` 的有無號隨平台不同 | 印出 `(int)buf[i]`；在兩個平台加 `-fsigned-char`／`-funsigned-char` 重現 | 原始 byte 改用 `unsigned char`／`uint8_t` |
| 錯誤檢查形同虛設，失敗的 `read` 被當成成功 | `ssize_t` 的 -1 和 `size_t` 比較，被轉成 UMax | `-Wsign-compare` 警告；印出比較兩邊的值 | 先判斷 `n < 0`，再轉成 `size_t` 比較 |
| 倒數迴圈不會結束，最後 segfault | unsigned 索引的 `>= 0` 永遠為真 | gdb 中斷後看索引值接近 2^64 | 改成 `for (size_t i = n; i-- > 0; )` |
| 處理空字串或空陣列時當機 | `len - 1` 在 len 為 0 時下溢 | 用長度 0 的輸入寫單元測試 | 改寫成 `i + 1 < len`，或先檢查 len |
| 只有超大檔案出錯，小檔案都正常 | `size_t` 被截斷進 `int` | `-Wconversion`；用 > 2 GiB 的輸入測試 | 全程使用 `size_t`／`off_t` |
| log 裡出現 4294967295、65535 這類數字 | -1 被當成 unsigned 存放或印出 | 搜尋寫入該欄位的程式，看來源型別 | 統一型別；錯誤碼用 signed 型別 |
| Java 讀協定欄位得到負數 | Java 沒有 unsigned，`int`／`byte` 是 signed | 比對原始 byte 的 hex | 用 `long` 存放並 `& 0xFFFFFFFFL`，或用 `Integer.toUnsignedLong` |

## 4.14 動手練習

1. **手算**：寫出 8 位元下 -1、-100、-128、100 的二補數位元與 hex，並把 `0x9C`、`0x7F`、`0x80` 分別用 B2U 與 B2T 解讀。（驗證方法：把程式一的 `W` 改成 8。答案之一：-100 是 `1001 1100` = `0x9C`，B2U 是 156。）
2. **手算**：`int32_t x = -2;` 依序計算 `(uint32_t)x`、`(uint16_t)x`、`(int64_t)x`、`(uint64_t)(uint32_t)x` 的值。（提示：最後一個先轉成 unsigned 再擴展，所以是 zero extension。用程式二的 `show` 函式驗證。）
3. **預測再驗證**：在程式三加上 `SHOW(-1 > sizeof(int))`、`SHOW((short)-1 < (unsigned short)1)`、`SHOW(-1L < 1u)`，先寫下你的預測與理由，再執行比對。
4. **延伸程式**：寫一個 `int parse_u16_be(const unsigned char *p, size_t avail, uint16_t *out)`：資料不足時回傳 -1，否則依 big-endian 讀出 16 位元。用 `avail` 為 0、1、2 測試，並刻意把參數型別改成 `char *` 和 `int avail`，觀察哪些輸入會出錯、編譯器給了哪些警告。
5. **找錯**：下列程式想找出最後一個空白字元的位置，指出所有問題並修正。
   ```c
   // not-runnable
   int last_space(const char *s) {
       for (unsigned i = strlen(s) - 1; i >= 0; i--)
           if (s[i] == ' ') return i;
       return -1;
   }
   ```
   （提示：至少有三個問題，涉及空字串、迴圈條件與回傳型別。）
6. **工作情境**：在你的專案或任一開源 C 專案上加上 `-Wextra -Wconversion -Wsign-conversion` 重新編譯，數一數新增了多少警告，挑出三個分析它們是真正的 bug 還是可以安全忽略的轉換，並說明判斷依據。

## 本章重點整理

- C 的整數有寬度與有無號兩個維度；同寬度的 signed 與 unsigned 都能表示 2^w 個值，只是範圍不同，上下限用 `<limits.h>`、`<stdint.h>` 的巨集取得。
- 單純的 `char` 有沒有號由平台決定：x86-64 Linux 與 Apple Silicon 是 signed，AArch64 Linux 是 unsigned；處理原始 byte 一律用 `unsigned char` 或 `uint8_t`。
- Unsigned 編碼每一位的權重是 2^i，範圍 0 到 UMax = 2^w − 1。
- 二補數把最高位的權重改成 −2^{w−1}，範圍 TMin = −2^{w−1} 到 TMax = 2^{w−1} − 1；最高位為 1 時值必為負，-1 是全部位元為 1。
- 二補數的範圍不對稱，|TMin| = TMax + 1；它讓加法電路和 unsigned 共用，C23 已規定有號整數必須用二補數，但 signed overflow 仍是 undefined behavior。
- Signed 與 unsigned 的同寬度轉換不改變位元，只改變解讀：負數轉成 unsigned 會加上 2^w，大於 TMax 的 unsigned 轉成 signed 會減去 2^w。
- 比 `int` 窄的型別在運算前會先提升成 `int`；兩邊型別不同時，同寬度的 signed 與 unsigned 相遇會一起轉成 unsigned，這是 `-1 < 0u` 為假的原因。
- `read` 回傳的 `ssize_t` 和 `sizeof` 的 `size_t` 比較時，-1 會變成 2^64 − 1；必須先判斷負數，再轉型比較。
- 擴展時 unsigned 補 0（zero extension），signed 補最高位（sign extension），兩者都保持原值；同時改變寬度與有無號時，先依原型別改寬度，再改有無號。
- 截斷只留下低位，unsigned 的結果是原值 mod 2^k，再依目標型別解讀；把 `size_t` 存進 `int` 是大檔案才出現的經典 bug。
- `size_t` 永遠 ≥ 0，0 減 1 會繞到最大值：倒數迴圈用 `i-- > 0`，避免 `len - 1` 與 unsigned 相減後判斷正負。
- 選型別看值的語意：位元運算與外部格式用 unsigned，可能相減或出現負數的量用 signed；Rust 與 Go 直接禁止隱式整數轉換。
- 編譯器的 `-Wall -Wextra -Wconversion -Wsign-conversion` 搭配 `-Werror`，是抓轉換 bug 最便宜的方法；看到 4294967295、65535 這類數字要先懷疑轉換。

## 延伸問答

> [!question]- Q1. 為什麼二補數成為所有主流 CPU 的選擇，而不是 sign-magnitude 或 ones' complement？
> 關鍵在硬體成本。二補數的加法和 unsigned 加法使用完全相同的電路：把兩組位元相加、丟掉最高位的進位，不管把它們解讀成 signed 還是 unsigned，結果都正確。CPU 因此只需要一個加法器，減法也只是「加上負數」。
>
> 另外兩種編碼都有兩個 0（+0 與 -0），比較是否相等時要特別處理；sign-magnitude 的加法要先比較符號與大小再決定加或減，ones' complement 則要處理端迴進位。二補數只有一個 0，代價是範圍不對稱（多出一個 TMin），這個代價遠小於硬體上的好處。

> [!question]- Q2. 手算題：32 位元下，`(unsigned)-5`、`(int)4294967290u`、`(short)40000` 各是多少？
> `(unsigned)-5`：負數轉 unsigned 要加上 2^32，-5 + 4,294,967,296 = 4,294,967,291，位元是 `0xFFFFFFFB`。
>
> `(int)4294967290u`：這個值大於 TMax（2,147,483,647），轉成 signed 要減去 2^32，得到 -6，位元是 `0xFFFFFFFA`，正好比 -5 少 1。`(short)40000`：40000 超出 16 位元的 TMax 32767，截斷後的 16 位元是 `0x9C40`，最高位為 1，值為 40000 − 65536 = -25,536。後兩者在 C17 是 implementation-defined，gcc 與 clang 都給出這個結果。

> [!question]- Q3. 你在 production 看到 log 寫著 `allocated 18446744073709551615 bytes failed`，最可能的原因是什麼？
> 18,446,744,073,709,551,615 是 2^64 − 1，也就是 64 位元的 -1 被當成 `size_t`。最常見的來源有三種：某個回傳 `ssize_t` 的函式（例如 `read`、`recv`）失敗回傳 -1，程式沒檢查就拿來當大小；某個 `size_t` 的長度是 0，程式算了 `len - 1`；或者兩個 `size_t` 相減，被減數比減數小。
>
> 追查方式是從 log 的位置往回看這個大小怎麼算出來的，找出每一個減法與每一個從 signed 轉成 `size_t` 的地方。修正後建議加上 `-Wsign-conversion` 編譯該模組，並為長度 0 與 I/O 失敗的情況加上測試。這個值幸好太大，`malloc` 必然失敗；如果是 -1 加上某個數之後才傳進去，就可能變成一個小的、可以配置成功的值，那才是真正危險的情況（第 5 章）。

> [!question]- Q4. `char c = getchar(); if (c == EOF) break;` 有什麼問題？
> `getchar` 回傳 `int`，正常讀到的 byte 是 0 到 255，讀到檔案結尾時回傳 `EOF`（通常是 -1）。這個設計刻意讓 `EOF` 和所有合法的 byte 值不同，但前提是你用 `int` 接收。存進 `char` 之後，257 種可能被壓縮成 256 種，資訊就遺失了。
>
> 如果 `char` 是 signed（x86-64 Linux），byte `0xFF` 會變成 -1，和 `EOF` 無法區分，讀到這個 byte 就會被誤以為檔案結束；如果 `char` 是 unsigned（AArch64 Linux），`c` 永遠不會是 -1，`c == EOF` 永遠為假，迴圈在檔案結尾也停不下來。兩個平台出錯的方式不同，修法相同：用 `int c` 接收 `getchar` 的回傳值。

> [!question]- Q5. 為什麼 `(uint16_t)1 > (int16_t)-1` 為真，`1u > -1` 卻為假？
> 差別在 integer promotion。`uint16_t` 與 `int16_t` 都比 `int` 窄，運算前先提升成 `int`，而 `int` 放得下它們所有的值，所以比較的是 `int` 的 1 與 `int` 的 -1，結果為真，unsigned 根本沒有機會影響結果。
>
> `1u > -1` 的兩邊分別是 `unsigned int` 與 `int`，寬度相同，usual arithmetic conversions 規定 signed 那邊要轉成 unsigned，-1 變成 4,294,967,295，於是 1 > 4,294,967,295 為假。這個例子說明，同樣是「unsigned 和負數比較」，結果取決於型別寬度是否小於 `int`，這也是為什麼不應該依賴記憶規則，而是把兩邊轉成明確的同一型別。

> [!question]- Q6. 面試題：請解釋 sign extension 為什麼能保持值不變。
> 以 w 位元擴展成 w + 1 位元為例。如果最高位是 0，補一個 0，新的位元權重為負但乘以 0，值不變。如果最高位是 1，原本它貢獻 −2^{w−1}；擴展後新最高位（也是 1）的權重是 −2^w，原本那一位變成正權重 +2^{w−1}，兩者合計 −2^w + 2^{w−1} = −2^{w−1}，和原本相同。
>
> 既然擴展一位能保持值不變，用歸納法就能推到擴展任意位數。這也說明了 zero extension 為什麼不能用在 signed 負數上：補 0 會讓原本負權重的位元變成正權重，值會增加 2^w。x86-64 因此提供 `movsbl`、`movslq` 與 `movzbl` 等不同指令，由 C 的型別決定使用哪一種。

> [!question]- Q7. 程式找錯：`for (size_t i = 0; i < n - 1; i++) if (a[i] > a[i + 1]) swap(...);` 有什麼問題？
> 當 n 是 0 時，`n - 1` 是 `size_t` 的減法，結果繞到 2^64 − 1，迴圈條件 `i < n - 1` 幾乎永遠成立，程式會讀寫 `a[0]`、`a[1]`……一路越界，直到 segfault 或破壞其他資料。n 為 1 時則正確（`n - 1` 為 0，不進迴圈）。
>
> 修法是避免在 unsigned 上做可能下溢的減法：把條件改成 `i + 1 < n`，在 n 為 0 時也正確。另一種寫法是在迴圈前判斷 `if (n < 2) return;`。這類 bug 在測試中容易遺漏，因為大多數測試資料都不是空的，所以單元測試應該刻意加入長度 0 與長度 1 的情況。

> [!question]- Q8. 既然 unsigned 這麼危險，為什麼 `size_t` 要設計成 unsigned？
> 歷史上的主要理由是範圍：在 16 位元與 32 位元的時代，物件大小可能接近整個位址空間，用 unsigned 可以多一倍的範圍，例如 32 位元系統上可以表示大於 2 GiB 的物件大小。另一個理由是語意：大小永遠不會是負數，用 unsigned 看起來「更精確」。
>
> 今天在 64 位元系統上，多出的那一個位元幾乎沒有實際用途，而 unsigned 帶來的減法下溢與比較陷阱卻天天發生，所以有些團隊與語言（例如 Java 的陣列索引用 `int`）選擇 signed。C 的 `size_t` 已經無法改變，務實的做法是：和 API 交換大小時用 `size_t`，自己的計算若會出現減法或負數就用 signed 型別，並在兩者交界處明確檢查與轉型。
