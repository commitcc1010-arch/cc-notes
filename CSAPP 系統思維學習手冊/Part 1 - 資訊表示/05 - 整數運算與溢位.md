# 第 5 章　整數運算：加法、乘法、溢位與安全漏洞

> [!abstract] 本章地圖
> **核心問題**：電腦的整數只有固定的位元數，加法和乘法的結果放不下時會發生什麼事？為什麼一個看似無害的 `w * h * 4` 會變成可以被攻擊的漏洞？
>
> **你會學到**：

> - 看懂編譯器如何用 shift、`lea` 與「魔術數字乘法」取代乘除法，並解釋負數除以 2 的冪為什麼要加 bias
> - 說清楚 signed overflow 為什麼是 undefined behavior，以及它如何讓編譯器刪掉你的檢查
> - 用 `__builtin_mul_overflow`、C23 的 `ckd_mul` 與「先檢查再運算」的寫法，修好大小計算的漏洞
>
> **前置知識**：第 3 章（二進位、十六進位與位元運算、shift）、第 4 章（unsigned 與二補數編碼、轉換與截斷）
>

## 5.1 故事：一張「32768 × 32769」的 PNG

週五傍晚，SRE 阿哲在頻道裡貼了一段 crash log：`thumbd` 的 worker 在過去一小時內當機了四十幾次，每次都是 `SIGSEGV`，位置都在 PNG 解碼迴圈裡。更奇怪的是，當機前的請求都指向同一個使用者上傳的同一張圖。

小安把那張圖抓下來，檔案只有 30 KB，用看圖軟體打開卻顯示「圖片損毀」。用 `xxd` 看 PNG 的 IHDR 區塊，寬度欄位是 `0x00008000`、高度欄位是 `0x00008001`，也就是 32768 × 32769。小安心想：「這張圖大到不合理，但也只是會配置很多記憶體而已，為什麼會 segfault？」

老周看了 `thumbd` 配置像素緩衝區的那一行：

```c
// not-runnable
uint32_t w = png_width(hdr), h = png_height(hdr);
size_t bytes = w * h * 4;               /* RGBA，每個像素 4 bytes */
uint8_t *pixels = malloc(bytes);
```

「你算一下 `bytes` 是多少。」小安在 Python 裡打了 `32768 * 32769 * 4`，得到 4,295,098,368，約 4 GiB。老周搖頭：「Python 的整數沒有上限，C 的 `uint32_t` 有。`w * h * 4` 是在 32 位元裡算的，算完才放進 64 位元的 `size_t`。真正的結果是 131,072，也就是 128 KiB。」

`malloc` 很乾脆地給了 128 KiB。解碼器接著一列一列寫入像素：每一列 32768 × 4 = 131,072 bytes，第一列剛好填滿整個緩衝區，第二列開始就寫到 heap 上別人的資料。運氣好的時候程式當場 segfault；運氣不好的時候，它安靜地改寫了 allocator 的管理資料，幾千個請求之後才在不相干的地方爆炸。如果攻擊者精心安排寫入的內容，這就是一個可以執行任意程式碼的 heap overflow。

這一章要回答的就是這類問題：固定寬度的整數做加法、乘法、除法時，到底遵守什麼規則？哪些「溢位」是語言定義好的行為，哪些是 undefined behavior？編譯器會怎麼利用這些規則？以及在工作上，要怎麼寫出不會被一張惡意圖片打垮的大小計算。

## 5.2 Unsigned 加法：時鐘上的算術

先從最單純的情況開始。第 4 章說過，w 位元的 unsigned 整數可以表示 0 到 2^w − 1。兩個這樣的數相加，數學上的結果最大可以到 2^(w+1) − 2，需要 w + 1 個位元才放得下。CPU 的加法器只保留最低的 w 個位元，最高的那個進位直接丟掉。

**模運算**（modular arithmetic）是描述這件事的數學語言：「丟掉第 w 位以上的進位」等於「除以 2^w 取餘數」。所以 w 位元的 unsigned 加法定義為：

```text
x +u y = (x + y) mod 2^w

          ⎧ x + y           若 x + y < 2^w      （正常）
        = ⎨
          ⎩ x + y − 2^w     若 x + y ≥ 2^w      （溢位，繞回去）
```

最好的直覺是一個只有 2^w 格的時鐘。下圖是 4 位元的版本，0 到 15 排成一圈，加法就是順時針走幾格；走過 15 就回到 0。

```text
                       0
                15  ┌──────┐  1
            14      │      │      2
          13        │ 4 位 │        3       x +u y：從 x 順時針走 y 格
          12        │ 時鐘 │        4       走過 15 → 0 的那一刻就是溢位
          11        │      │        5       （數學結果被減去 16）
            10      │      │      6
                 9  └──────┘  7
                       8
     例：13 + 5 → 從 13 走 5 格：14、15、0、1、2 → 停在 2
```

手算一次：4 位元 unsigned，13 + 5。

```text
    1101   (13)
  + 0101   ( 5)
  ──────
  1 0010   數學結果 18，需要 5 個 bit
  ↑
  丟掉第 4 位的進位 → 0010 = 2 = 18 − 16
```

C 標準明確規定：unsigned 型別的運算一律以 2^w 取模，這是**定義良好**的行為，不是錯誤，也不是 undefined behavior。這一點很重要，後面會看到 signed 的規則完全不同。

### 怎麼知道 unsigned 加法溢位了？

既然結果會繞回來，能不能事後判斷？可以，而且很簡單：**溢位時，結果一定比任何一個運算元小**。理由是溢位時 s = x + y − 2^w，而 y < 2^w，所以 s = x − (2^w − y) < x。反過來，沒有溢位時 s = x + y ≥ x。所以判斷式就是：

```c
// not-runnable
int uadd_ok(unsigned x, unsigned y) { return x + y >= x; }   /* 1 表示沒有溢位 */
```

這個判斷在 C 裡是合法的，因為 unsigned 的繞回是定義好的。但更好的習慣是**在運算之前檢查**，例如 `if (y > UINT_MAX - x)`，因為事前檢查的寫法同樣適用於 signed 型別，也比較容易讓讀程式的人看懂意圖。

### 繞回不一定是 bug

時鐘算術有時正是你要的。Linux kernel 用一個叫 `jiffies` 的計數器記錄開機以來的 tick 數，它遲早會繞回 0。kernel 比較兩個時間點時不寫 `a > b`，而是用 `time_after(a, b)` 這個巨集，它的核心是 `(long)(b - a) < 0`：先做 unsigned 減法（繞回也沒關係），再把差值解讀成 signed。只要兩個時間點相差不到半圈，結果就是對的。kernel 甚至刻意把 `jiffies` 的初始值設成讓 32 位元的計數在開機後約五分鐘就繞回一次，讓沒處理好繞回的程式碼在測試時就現形，而不是在機器跑了幾十天後才出事。

同樣的技巧也用在網路協定：TCP 的 sequence number 是 32 位元，會繞回，比較時也是用這種「差值當 signed」的方法。雜湊函式、checksum、亂數產生器則直接依賴乘法與加法的取模行為。所以 unsigned 繞回本身沒有對錯，**問題在於你是否預期它**。`thumbd` 的大小計算顯然沒有。

## 5.3 二補數加法：位元一樣，溢位不一樣

二補數（第 4 章）的美妙之處在於：**signed 加法和 unsigned 加法用的是同一個加法器，產生完全相同的位元**。CPU 只有一條 `add` 指令，不管你在 C 裡宣告的是 `int` 還是 `unsigned`。差別只在於事後怎麼解讀結果，以及結果「對不對」的判斷標準。

w 位元二補數的範圍是 TMin = −2^(w−1) 到 TMax = 2^(w−1) − 1。兩個數相加，數學結果的範圍是 −2^w 到 2^w − 2，同樣可能放不下。把結果截斷成 w 位元再用二補數解讀，會得到三種情況：

```text
 數學上的 x + y（數線）
 
 −2^w          −2^(w−1)          0          2^(w−1)          2^w
  ├────────────────┼─────────────┼──────────────┼────────────────┤
  │   負溢位        │          正常範圍           │    正溢位       │
  │  結果 + 2^w     │        結果不變             │   結果 − 2^w    │
  │ （變成正數）     │                            │  （變成負數）    │
                  TMin                         TMax
```

- 結果在 TMin 到 TMax 之間：正常，截斷不影響數值。
- 結果大於 TMax：**正溢位**（positive overflow），截斷後被減去 2^w，兩個正數相加變成負數。
- 結果小於 TMin：**負溢位**（negative overflow），截斷後被加上 2^w，兩個負數相加變成正數或零。

用 4 位元（範圍 −8 到 7）手算三個例子，順便看清楚「進位」和「溢位」是兩回事：

| 算式 | 位元運算 | 截斷後的位元 | 二補數解讀 | 數學結果 | 判斷 |
|---|---|---|---|---|---|
| 5 + 6 | 0101 + 0110 = 0 1011 | 1011 | −5 | 11 | 正溢位：正 + 正 = 負 |
| −8 + −5 | 1000 + 1011 = 1 0011 | 0011 | 3 | −13 | 負溢位：負 + 負 = 正 |
| −3 + 5 | 1101 + 0101 = 1 0010 | 0010 | 2 | 2 | 正常（有進位，但沒有溢位） |
| −1 + −1 | 1111 + 1111 = 1 1110 | 1110 | −2 | −2 | 正常（有進位，但沒有溢位） |

第三、四列特別值得看：最高位有進位被丟掉，結果卻完全正確。對 signed 來說，「最高位有進位」不代表溢位。CPU 因此用兩個不同的旗標記錄這兩件事：**carry flag**（CF）記錄 unsigned 意義下的溢位，**overflow flag**（OF）記錄 signed 意義下的溢位。同一次 `add` 會同時設定兩者，要看哪一個由後續的指令決定（第 8 章會詳細介紹條件碼）。

### 溢位的判斷規則

從上面的表可以歸納出一個簡單的規則：

> **只有兩個同號的數相加才可能溢位；溢位的徵兆是結果的符號和運算元不同。**

異號相加永遠不會溢位，因為結果的絕對值不會超過較大的那個運算元。所以判斷 signed 加法是否溢位，只要檢查「正 + 正 得到負」或「負 + 負 得到非負」。

但在 C 裡有一個大陷阱：你**不能**先寫 `int s = x + y;` 再檢查 `s` 的符號。因為 signed overflow 在 C 裡是 undefined behavior（5.8 節），編譯器可以假設它不會發生，進而把你的檢查整個刪掉。正確的做法有兩種：事前檢查，或用編譯器提供的內建函式。

```c
// not-runnable
/* 事前檢查：在運算之前就判斷會不會超出範圍，整個過程沒有任何溢位 */
int tadd_ok(int x, int y) {
    if (y > 0 && x > INT_MAX - y) return 0;   /* 會正溢位 */
    if (y < 0 && x < INT_MIN - y) return 0;   /* 會負溢位 */
    return 1;
}
```

`INT_MAX - y` 在 y > 0 時不會溢位，`INT_MIN - y` 在 y < 0 時也不會，所以這個檢查本身是安全的。5.9 節會介紹更省事的內建函式。

## 5.4 負號：−x 與那個沒有相反數的 TMin

在二補數裡，取負號的位元層級做法是「**全部反轉再加一**」：−x = ~x + 1。用 4 位元驗證：5 是 0101，反轉得 1010，加一得 1011，正是 −5。再試 −3：1101 反轉得 0010，加一得 0011 = 3。

為什麼這樣做是對的？因為 x + ~x 的每一位都是 1，也就是全 1 的位元，在二補數裡是 −1。所以 x + ~x = −1，移項得 −x = ~x + 1。這也是 CPU 只需要加法器就能做減法的原因：x − y = x + (~y + 1)。

但二補數的範圍不對稱：4 位元的最小值是 −8，最大值只有 7。−8 的相反數 8 放不下。用規則算一次：−8 是 1000，反轉得 0111，加一得 1000，又回到 −8。所以：

| 型別 | TMin | −TMin 的位元結果 | `abs(TMin)` |
|---|---|---|---|
| 4 位元 | −8（1000） | 1000，仍是 −8 | 數學上應為 8，放不下 |
| `int`（32 位元） | −2,147,483,648 | 同樣的位元，仍是 TMin | C 裡是 undefined behavior |
| `long`（64 位元，LP64） | −9,223,372,036,854,775,808 | 同上 | 同上 |

在 C 裡，`-INT_MIN` 與 `abs(INT_MIN)` 都是 signed overflow，屬於 undefined behavior；實際上多數機器會得到 `INT_MIN` 本身，也就是「取絕對值之後還是負數」。這曾經造成很多真實的 bug，例如用 `abs(hash) % n` 計算陣列索引：當 hash 剛好是 `INT_MIN` 時，索引是負的，程式越界讀取。Java 的 `Math.abs(Integer.MIN_VALUE)` 也回傳負數，是同一個原因。

除法也有同樣的邊界：`INT_MIN / -1` 數學上是 2^31，放不下。這在 C 裡同樣是 undefined behavior，而且不同硬體的反應完全不同。在 x86-64 上，`idiv` 指令遇到這個情況會觸發除法錯誤的 exception，作業系統送出 `SIGFPE`，程式當場結束；在 ARM64 上，`sdiv` 不會觸發 exception，只是安靜地回傳 `INT_MIN`。作者在同一台 Apple Silicon Mac 上，用原生 arm64 與 Rosetta 執行 x86-64 版本，分別得到「印出 −2147483648」與「結束碼 136（128 + 8，也就是 SIGFPE）」。如果 `thumbd` 有一個「除以使用者給的值」的 API，這就是一個讓伺服器當機的方法。

## 5.5 乘法：截斷之後，unsigned 與 signed 的位元相同

兩個 w 位元的數相乘，數學結果最多需要 2w 個位元。C 的乘法和加法一樣，只保留最低的 w 位：

```text
unsigned： x *u y = (x · y) mod 2^w
二補數：   x *t y = 把 (x · y) 截斷成 w 位元，再以二補數解讀
```

一個很重要、也有點意外的事實是：**對同樣的輸入位元，unsigned 乘法和二補數乘法截斷後的位元完全相同**。差別只在完整的 2w 位元乘積的高半部，而那一半正好被丟掉了。用 4 位元手算確認，輸入位元是 1101 與 0101：

| 解讀 | x | y | 數學乘積 | 8 位元乘積 | 截斷成 4 位元 | 解讀結果 |
|---|---|---|---|---|---|---|
| unsigned | 13 | 5 | 65 | 0100 0001 | 0001 | 1 |
| 二補數 | −3 | 5 | −15 | 1111 0001 | 0001 | 1 |

高 4 位不一樣（0100 與 1111），低 4 位一樣（0001）。所以編譯器對 `int` 與 `unsigned` 的乘法可以用同一條 `imul` 指令；只有需要完整 2w 位元乘積時（例如偵測溢位、或 64 × 64 → 128 位元），才需要區分 signed 的 `imul` 與 unsigned 的 `mul`（第 8 章）。

再看一個 4 位元的二補數例子：5 × 3 = 15，超過 TMax = 7。完整乘積 0000 1111，截斷後 1111，解讀為 −1。兩個正數相乘得到負數，是乘法溢位最常見的徵兆，但**不是唯一的徵兆**：乘法溢位可能讓結果繞了好幾圈後又落回正數。例如 8 位元的 16 × 17 = 272，截斷後是 272 − 256 = 16，看起來還是正數，完全看不出出事。這也是為什麼「檢查結果是不是負數」不能用來偵測乘法溢位。

### 乘法溢位怎麼偵測

加法溢位可以用符號判斷，乘法不行。可靠的方法有三種：

1. **用兩倍寬的型別計算**：兩個 32 位元的數，轉成 64 位元相乘一定放得下，再檢查結果是否超出 32 位元的範圍。這是最直接的方法，但到了 64 位元就沒有更寬的標準型別可用。
2. **事前用除法檢查**：要算 a × b（皆為 unsigned），先檢查 `a != 0 && b > MAX / a`，成立就表示會溢位。這是 OpenBSD 的 `reallocarray` 與很多 `calloc` 實作用的邏輯。
3. **用硬體旗標**：x86-64 的 `mul`／`imul` 會在乘積超過目標寬度時設定 CF 與 OF，編譯器的內建函式（5.9 節）就是靠它，只多一兩條指令。

`thumbd` 的 `w * h * 4` 正是乘法溢位。32768 × 32769 × 4 = 4,295,098,368 = 2^32 + 131,072，截斷到 32 位元只剩 131,072。結果是一個看起來完全合理的正數，不會觸發任何「負數檢查」。

## 5.6 用 shift 與 lea 做乘法：編譯器的手法

在很多處理器上，整數乘法比加法與 shift 慢。現代 x86-64 的 `imul` 大約需要 3 個 cycle 的延遲，加法與 shift 只要 1 個。所以當乘數是編譯期常數時，編譯器常常把乘法改寫成 shift 與加減法的組合。

基本原理是：**左移 k 位等於乘以 2^k**，不論 unsigned 還是二補數，截斷後的位元都相同（溢位行為也一樣）。任何常數都可以拆成 2 的冪的和或差，例如：

```text
x * 12 = x * (8 + 4)  = (x << 3) + (x << 2)
x * 7  = x * (8 − 1)  = (x << 3) − x
x * 3  = x + x * 2    →  x86-64 可以用一條 leaq (%rdi,%rdi,2) 完成
```

實際看編譯器怎麼做。下面的組合語言由 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - file.c` 產生，原始碼是 `int mul12(int x) { return x * 12; }` 與 `int mul7(int x) { return x * 7; }`，刪去了 directive：

```asm
mul12:
	shll	$2, %edi
	leal	(%rdi,%rdi,2), %eax
	retq
mul7:
	leal	(,%rdi,8), %eax
	subl	%edi, %eax
	retq
```

逐行看：參數 x 在 `%edi`（System V ABI 的第一個整數參數），回傳值放 `%eax`。`mul12` 先把 x 左移 2 位得到 4x，再用 `leal (%rdi,%rdi,2)` 算出 4x + 4x × 2 = 12x。`lea`（load effective address，第 7 章）本來是計算位址的指令，但它能一次做「基底 + 索引 × 1、2、4、8」的運算，又不會改動條件碼，編譯器很喜歡拿它當便宜的乘加器。`mul7` 用 `leal (,%rdi,8)` 算出 8x，再減去 x，得到 7x。

這件事帶給工作上的啟示是：**不要自己把 `x * 12` 改寫成 shift**。編譯器比你更清楚目標處理器上哪種組合比較快，手動改寫只會讓程式更難讀，還可能在 signed 數上引入 undefined behavior（左移負數在 C17 是 UB）。

## 5.7 除以 2 的冪：shift 與 bias

除法比乘法更慢，在 x86-64 上一條 32 位元的 `idiv` 依處理器不同約需十幾到數十個 cycle 的延遲（近年的處理器已經快很多，但仍比乘法慢好幾倍）。所以除以 2^k 時，編譯器會想用右移代替。

對 unsigned 數，**邏輯右移 k 位就是除以 2^k 並向下取整**，完全正確。對 signed 數就有麻煩了：C 規定整數除法**向零捨入**（round toward zero），也就是把小數部分直接丟掉，−1.75 變成 −1。但算術右移（第 3 章）的效果是**向下取整**（向負無限大），−1.75 變成 −2。正數兩者一樣，負數且不能整除時就差 1。

用 8 位元手算 −7 / 4：

```text
 −7 的 8 位元二補數：     1111 1001
 算術右移 2 位：          1111 1110   = −2   （向下取整：floor(−1.75) = −2）
 C 要求的 −7 / 4：                      −1   （向零捨入）

 修正：先加 bias = 2^k − 1 = 3，再右移
 −7 + 3 = −4：            1111 1100
 算術右移 2 位：          1111 1111   = −1   ✓
```

加 bias 的道理是：對負數 x，(x + 2^k − 1) 右移 k 位 等於 ⌈x / 2^k⌉，也就是向上取整，而負數的向上取整正是向零捨入。如果 x 剛好能被 2^k 整除，加上 2^k − 1 不會跨過下一個倍數，結果不變；如果不能整除，加上去剛好推過一個倍數，抵消掉 floor 多減的那個 1。

| x | 數學 x / 4 | C 的 `x / 4` | `x >> 2`（算術） | `(x + 3) >> 2` |
|---|---|---|---|---|
| 7 | 1.75 | 1 | 1 | （正數不加 bias）1 |
| −7 | −1.75 | −1 | −2 | −1 |
| −8 | −2 | −2 | −2 | −2 |
| −1 | −0.25 | 0 | −1 | 0 |

編譯器產生的程式碼完全就是這樣。原始碼 `int div8(int x) { return x / 8; }` 與 `unsigned udiv8(unsigned x) { return x / 8; }`，同樣用上面那條 `clang -target x86_64-linux-gnu -O1 -S` 指令產生：

```asm
div8:
	leal	7(%rdi), %eax
	testl	%edi, %edi
	cmovnsl	%edi, %eax
	sarl	$3, %eax
	retq
udiv8:
	movl	%edi, %eax
	shrl	$3, %eax
	retq
```

`div8` 先算 x + 7 放進 `%eax`；`testl` 檢查 x 的符號；`cmovns`（conditional move if not sign，第 8 章）在 x 非負時把 `%eax` 換回原本的 x，也就是「只有負數才加 bias」；最後 `sarl $3` 做算術右移 3 位。unsigned 版本就單純得多，一條邏輯右移 `shrl` 就完成。這也是一個小小的效能理由：**確定不會是負數的除法，用 unsigned 型別可以讓編譯器產生更短的程式碼**。

### 除以任意常數：乘法加右移

除數不是 2 的冪時呢？編譯器仍然不會用 `div`，而是用一個預先算好的「魔術數字」做乘法，再取乘積的高位。原始碼 `unsigned udiv10(unsigned x) { return x / 10; }` 產生：

```asm
udiv10:
	movl	%edi, %ecx
	movl	$3435973837, %eax               # imm = 0xCCCCCCCD
	imulq	%rcx, %rax
	shrq	$35, %rax
	retq
```

0xCCCCCCCD ÷ 2^35 ≈ 0.1000000000058，是一個非常接近 1/10 的數。x × 0xCCCCCCCD 再右移 35 位，就等於 x × 0.1000000000058 再向下取整；編譯器選擇這個常數時已經證明了：對所有 32 位元的 x，誤差都不足以讓結果差 1。以 x = 1234 驗證：1234 × 3,435,973,837 = 4,239,991,714,858，除以 2^35 約為 123.4，取整得 123，正是 1234 / 10。第一次在 `objdump` 輸出裡看到這種奇怪的大常數時，就知道它其實是一個除法。

## 5.8 Signed overflow 是 undefined behavior

到目前為止，我們把二補數溢位描述成「截斷後繞回」。這是硬體實際做的事，但**不是 C 語言的規則**。C 標準規定：signed 整數運算的結果如果超出型別的範圍，行為是**未定義的**（undefined behavior，UB，第 2 章介紹過這個概念）。編譯器可以假設 UB 永遠不會發生，並依此做最佳化。

為什麼 C 要這樣規定？歷史上，C 要能在不使用二補數的機器上執行（例如一補數、sign-magnitude），那些機器的溢位行為各不相同，所以標準乾脆不規定。今天幾乎所有機器都用二補數，C23 也終於規定 signed 整數一律用二補數**表示**，但溢位**仍然是 UB**。保留的理由是最佳化：知道 `i + 1` 不會溢位，編譯器就能推論 `i + 1 > i` 永遠成立、迴圈的次數可以算出來、`int` 索引可以直接放大成 64 位元的位址計算而不必每次重新做 sign extension。這些最佳化對迴圈效能的影響很實際。

代價是：程式設計師以為「溢位會繞回」的程式碼，可能被編譯成完全不同的東西。看一個對照實驗，原始碼是：

```c
// not-runnable
int will_overflow(int len) { return len + 100 < len; }   /* 想檢查 len + 100 會不會溢位 */
```

用 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - file.c` 編譯，以及加上 `-fwrapv` 再編譯一次：

```asm
# -O1：
will_overflow:
	xorl	%eax, %eax
	retq
# -O1 -fwrapv：
will_overflow:
	xorl	%eax, %eax
	cmpl	$2147483548, %edi               # imm = 0x7FFFFF9C
	setge	%al
	retq
```

不加旗標時，整個函式變成「永遠回傳 0」。編譯器的推理是：如果沒有溢位，`len + 100 < len` 數學上不可能成立；如果溢位，那是 UB，怎麼做都可以。所以直接回傳 0 是合法的。這種「為了檢查溢位而寫的程式碼，因為依賴溢位而被刪掉」的情況，在真實的開源專案裡發生過很多次。加上 **`-fwrapv`**（告訴編譯器 signed overflow 一律以二補數繞回）之後，編譯器就必須真的比較：`len >= 2147483548`，也就是 `len > INT_MAX - 100`。

再看一個會改變執行結果的例子。數學上 `(x * 2) / 2` 永遠等於 x：

```c
#include <stdio.h>
#include <stdlib.h>

/* 數學上 (x * 2) / 2 == x；但 x * 2 溢位時是 undefined behavior */
__attribute__((noinline)) int twice_then_half(int x) { return (x * 2) / 2; }

int main(int argc, char **argv) {
    int x = argc > 1 ? atoi(argv[1]) : 1500000000;
    printf("twice_then_half(%d) = %d\n", x, twice_then_half(x));
    return 0;
}
```

這段程式含有 UB，**結果依編譯器與最佳化等級而定**。作者在 macOS arm64、Apple clang 21.0.0 上用不同選項編譯，得到：

```text
-O0:         twice_then_half(1500000000) = -647483648
-O1:         twice_then_half(1500000000) = 1500000000
-O2:         twice_then_half(1500000000) = 1500000000
-O2 -fwrapv: twice_then_half(1500000000) = -647483648
```

`-O0` 照字面計算：1,500,000,000 × 2 = 3,000,000,000，超過 INT_MAX，繞回成 3,000,000,000 − 2^32 = −1,294,967,296，再除以 2 得到 −647,483,648。`-O1` 以上，編譯器假設 `x * 2` 不會溢位，於是 `(x * 2) / 2` 化簡成 `x`，整個函式只剩一條 `mov`。同一份原始碼，debug build 和 release build 給出不同答案，這正是 UB 最難除錯的地方：你在 debug 模式下重現不了 production 的行為，或者反過來。

| 語言 | signed 整數溢位的規則 | 想要繞回時 | 想要偵測時 |
|---|---|---|---|
| C／C++ | undefined behavior | 轉成 unsigned 運算，或 `-fwrapv` | `__builtin_*_overflow`、C23 `ckd_*` |
| Java | 定義為二補數繞回 | 預設就是 | `Math.addExact`、`Math.multiplyExact` 溢位時丟例外 |
| Go | 定義為二補數繞回 | 預設就是 | 自行檢查，或用 `math/bits` |
| Rust | debug build panic；release build 預設繞回 | `wrapping_add` | `checked_add` 回傳 `Option` |
| Python | 整數沒有上限，不會溢位 | 自行 `% 2**32` | 不需要（但呼叫 C 擴充或 NumPy 時要注意） |

最後一列的但書很實際：NumPy 的 `int32` 陣列運算會照 C 的方式繞回，而且不一定有警告。小安在 Python 裡算出 4 GiB，正是因為 Python 整數沒有上限；同樣的式子放進 NumPy 的 `uint32` 陣列，就會得到和 `thumbd` 一樣的 131,072。

> [!warning] 常見誤解
> 「我的機器是二補數，所以 signed overflow 就是繞回。」硬體確實會繞回，但 C 編譯器不必照硬體的行為產生程式碼。只要原始碼裡的 signed 運算可能溢位，編譯器就可以做出「假設它不會溢位」的轉換。想要繞回，就用 unsigned 型別做運算；想要偵測，就用下一節的工具。

## 5.9 正確偵測溢位的工具

知道了陷阱，接下來是工具箱。在工作上，按照情境挑選：

**一、GCC 與 Clang 的內建函式。** `__builtin_add_overflow(a, b, &result)`、`__builtin_sub_overflow`、`__builtin_mul_overflow` 會以「無限精度」計算結果，存進 `result` 指向的型別（截斷後的值），並在結果放不下時回傳 true。它們接受任何整數型別的組合，不會觸發 UB，而且編譯器會用硬體旗標實作，代價很低。下面是 `__builtin_mul_overflow` 在兩個 `size_t` 上產生的程式碼（同樣以 `clang -target x86_64-linux-gnu -O1 -S` 產生）：

```asm
mul_checked:
	movq	%rdx, %rcx
	movq	%rdi, %rax
	xorl	%edi, %edi
	mulq	%rsi
	seto	%dil
	movq	%rax, (%rcx)
	movl	%edi, %eax
	retq
```

`mulq` 是 unsigned 的 64 × 64 位元乘法，完整的 128 位元結果放在 `%rdx:%rax`；乘積超過 64 位元時它會設定 OF 與 CF，`seto` 把 OF 存成 0 或 1 當作回傳值。整個檢查只比單純的乘法多一條指令。

**二、C23 的 `<stdckdint.h>`。** C23 把同樣的功能標準化成 `ckd_add`、`ckd_sub`、`ckd_mul`，用法是 `if (ckd_mul(&r, a, b)) { /* 溢位 */ }`。GCC 14 與較新的 Clang 已經支援（本書撰寫時，Apple clang 21 用 `-std=c2x` 可以編譯）。新專案可以優先使用標準寫法。

**三、事前檢查的手寫版本。** 在不能依賴編譯器擴充的環境（例如某些嵌入式編譯器），用前面介紹過的寫法：

| 運算 | 型別 | 會溢位的條件（事前檢查） |
|---|---|---|
| a + b | unsigned | `b > MAX - a` |
| a + b | signed | `(b > 0 && a > MAX - b) \|\| (b < 0 && a < MIN - b)` |
| a × b | unsigned | `a != 0 && b > MAX / a` |
| a × b | signed | 情況較多，建議轉成更寬的型別或用內建函式 |
| a − b | unsigned | `b > a` |

**四、讓工具幫你抓。** 編譯選項 `-fsanitize=signed-integer-overflow`（UBSan 的一部分）會在執行時偵測每一次 signed overflow 並印出位置。Clang 另外有 `-fsanitize=unsigned-integer-overflow`，因為 unsigned 繞回是合法的，這個檢查會有很多誤報（雜湊函式就是故意繞回），比較適合在特定模組上打開。`-ftrapv` 讓 signed overflow 直接終止程式，但各編譯器的實作品質不一、效能代價也高，現在多半用 UBSan 取代。

**五、從設計上避免。** 大小、長度、索引用 `size_t`；外部輸入先驗證範圍再參與運算；能用 `calloc(n, size)` 就不要自己寫 `malloc(n * size)`，因為現代 `calloc` 會檢查乘法溢位，溢位時回傳 NULL；需要重新配置陣列時用 `reallocarray(ptr, n, size)`（OpenBSD 首創，glibc 2.26 起也提供）。

## 5.10 真實世界的整數漏洞

`thumbd` 的 bug 不是虛構的極端例子，它是最常見的漏洞類型之一。整數溢位本身很少直接造成危害，危害來自溢位之後的那一步：**用錯誤的大小去配置記憶體，再用正確的大小去寫入**。

```text
 外部輸入（網路封包、檔案標頭、HTTP 參數）
        │  count = 0x40000001，elem_size = 4
        ▼
 大小計算  count * elem_size  ── 32 位元溢位 ──▶  4（應為 4,294,967,300）
        │
        ▼
 malloc(4)                    只配置了 4 bytes
        │
        ▼
 for (i = 0; i < count; i++)  迴圈仍然用原本的 count
     buf[i] = read_elem();    第二個元素起就寫出界 → heap overflow
        │
        ▼
 覆寫相鄰的 heap 資料 → 當機，或被攻擊者控制執行流程（第 11 章）
```

這張圖描述的正是 2002 年 Sun RPC 的 XDR 函式庫被發現的漏洞模式：`xdr_array` 用網路傳來的元素個數乘以元素大小來配置緩衝區，乘法溢位讓配置變小，後續的複製迴圈卻照原本的個數寫入。因為 XDR 被許多 RPC 服務共用，影響範圍很廣。2015 年 Android 的 Stagefright 系列漏洞中，也有多個是解析 MP4 檔案時長度計算的整數溢位：只要讓手機收到一段影片，媒體服務在產生縮圖、預覽時就會去解析它。這和 `thumbd` 的處境幾乎一樣：**任何會自動解析外部檔案的服務，都在處理不受信任的整數**。

另一類是 signed 與 unsigned 混用（第 4 章談過的轉換陷阱）。CS:APP 舉過 FreeBSD `getpeername` 的例子：程式用 signed 的長度和上限比較，負數通過了「不超過上限」的檢查，傳給 `memcpy` 時又被當成巨大的 unsigned 長度。溢位與轉換經常一起出現：先算錯，再用錯的型別解讀。

整數溢位也不只發生在記憶體配置上。外界普遍推測，2015 年 FAA 對波音 787 發布的適航指令（發電機控制單元連續通電 248 天後會進入保護模式而斷電）與一個以百分之一秒計數的 signed 32 位元計數器有關：2^31 ÷ 100 ÷ 86,400 ≈ 248.55 天。原因的細節沒有正式公開，但這個數字吻合得很好，是「計數器溢位」在嵌入式系統的典型樣貌。

修好 `thumbd` 的關鍵不只是「把乘法改成 64 位元」。在 64 位元的 `size_t` 裡，32768 × 32769 × 4 不會溢位，會得到正確的 4 GiB；但讓一個縮圖服務為一個 30 KB 的檔案配置 4 GiB，本身就是一種 denial of service。完整的修法有三層：

```c
// not-runnable
#define MAX_DIM    16384u                    /* 業務上限：單邊最多 16384 像素 */
#define MAX_BYTES  (256u * 1024 * 1024)      /* 單張圖最多 256 MiB 的像素緩衝區 */

uint8_t *alloc_pixels(uint32_t w, uint32_t h, size_t *out_bytes) {
    size_t bytes;
    if (w == 0 || h == 0 || w > MAX_DIM || h > MAX_DIM) return NULL;     /* 1. 驗證輸入範圍 */
    if (__builtin_mul_overflow((size_t)w, (size_t)h, &bytes) ||          /* 2. 有檢查的乘法 */
        __builtin_mul_overflow(bytes, (size_t)4, &bytes)) return NULL;
    if (bytes > MAX_BYTES) return NULL;                                  /* 3. 資源上限 */
    *out_bytes = bytes;
    return malloc(bytes);
}
```

第一層確保輸入在合理範圍，第二層確保運算本身不會溢位（即使未來有人調高 `MAX_DIM`），第三層確保資源使用有上限。解碼迴圈也要用 `*out_bytes` 當作寫入的邊界，而不是重新計算一次。

## 5.11 動手做：觀察加法、乘法與除法的邊界

這段程式把本章的四個主題各做一次實驗：unsigned 加法繞回、signed 加法溢位偵測、`thumbd` 的大小計算、以及除以 2 的冪的捨入。

```c
#include <inttypes.h>
#include <limits.h>
#include <stdint.h>
#include <stdio.h>

/* A：unsigned 加法溢位的判斷：結果比任何一個運算元小，就是繞回去了 */
static int uadd_ok(uint32_t x, uint32_t y) { return x + y >= x; }

/* B：signed 加法溢位的判斷。先用 unsigned 相加（定義良好），再看符號 */
static int tadd_ok(int32_t x, int32_t y) {
    int32_t s = (int32_t)((uint32_t)x + (uint32_t)y);   /* 轉回 signed：實作定義，主流編譯器取同樣位元 */
    if (x >= 0 && y >= 0 && s < 0) return 0;            /* 正 + 正 = 負：正溢位 */
    if (x < 0 && y < 0 && s >= 0) return 0;             /* 負 + 負 = 非負：負溢位 */
    return 1;
}

/* C：thumbd 的緩衝區大小。bad 版在 32 位元裡相乘；ok 版檢查溢位，並套用 256 MiB 上限 */
#define MAX_BYTES ((size_t)256 * 1024 * 1024)
static size_t bytes_bad(uint32_t w, uint32_t h) { return w * h * 4; }
static int bytes_ok(uint32_t w, uint32_t h, size_t *out) {
    size_t px;
    if (__builtin_mul_overflow((size_t)w, (size_t)h, &px)) return 0;
    if (__builtin_mul_overflow(px, (size_t)4, out)) return 0;
    return *out <= MAX_BYTES;
}

int main(void) {
    printf("== A. unsigned 加法 ==\n");
    uint8_t a = 200, b = 100;
    printf("uint8_t: 200 + 100 = %u\n", (uint8_t)(a + b));
    printf("uadd_ok(4000000000, 300000000) = %d\n", uadd_ok(4000000000u, 300000000u));
    printf("uadd_ok(4000000000, 200000000) = %d\n", uadd_ok(4000000000u, 200000000u));

    printf("\n== B. signed 加法 ==\n");
    int32_t xs[][2] = {{INT32_MAX, 1}, {INT32_MIN, -1}, {-5, 3}, {INT32_MAX, INT32_MIN}};
    for (int i = 0; i < 4; i++) {
        int32_t s = 0;
        int ovf = __builtin_add_overflow(xs[i][0], xs[i][1], &s);
        printf("%11" PRId32 " + %11" PRId32 " -> %11" PRId32 "  tadd_ok=%d builtin_overflow=%d\n",
               xs[i][0], xs[i][1], s, tadd_ok(xs[i][0], xs[i][1]), ovf);
    }

    printf("\n== C. 寬 x 高 x 4 ==\n");
    uint32_t dims[][2] = {{4000, 3000}, {32768, 32769}, {65536, 65536}};
    for (int i = 0; i < 3; i++) {
        size_t good = 0;
        int ok = bytes_ok(dims[i][0], dims[i][1], &good);
        printf("%5" PRIu32 " x %5" PRIu32 ": bad=%10zu  正確=%11zu  ok=%d\n",
               dims[i][0], dims[i][1], bytes_bad(dims[i][0], dims[i][1]), good, ok);
    }

    printf("\n== D. 除以 2 的冪 ==\n");
    int vals[] = {7, -7, -8, -1};
    for (int i = 0; i < 4; i++) {
        int x = vals[i];
        printf("x=%3d  x/4=%3d  x>>2=%3d  (x+3)>>2=%3d\n",
               x, x / 4, x >> 2, (x < 0 ? x + 3 : x) >> 2);
    }
    return 0;
}
```

在 macOS arm64（Apple clang 21.0.0，`cc -std=c17 -O1 -Wall -Wextra`）上執行：

```text
== A. unsigned 加法 ==
uint8_t: 200 + 100 = 44
uadd_ok(4000000000, 300000000) = 0
uadd_ok(4000000000, 200000000) = 1

== B. signed 加法 ==
 2147483647 +           1 -> -2147483648  tadd_ok=0 builtin_overflow=1
-2147483648 +          -1 ->  2147483647  tadd_ok=0 builtin_overflow=1
         -5 +           3 ->          -2  tadd_ok=1 builtin_overflow=0
 2147483647 + -2147483648 ->          -1  tadd_ok=1 builtin_overflow=0

== C. 寬 x 高 x 4 ==
 4000 x  3000: bad=  48000000  正確=   48000000  ok=1
32768 x 32769: bad=    131072  正確= 4295098368  ok=0
65536 x 65536: bad=         0  正確=17179869184  ok=0

== D. 除以 2 的冪 ==
x=  7  x/4=  1  x>>2=  1  (x+3)>>2=  1
x= -7  x/4= -1  x>>2= -2  (x+3)>>2= -1
x= -8  x/4= -2  x>>2= -2  (x+3)>>2= -2
x= -1  x/4=  0  x>>2= -1  (x+3)>>2=  0
```

逐段解說：

1. **A 段**：200 + 100 = 300，超過 `uint8_t` 的 255，結果是 300 − 256 = 44。注意 `a + b` 本身其實是在 `int` 裡算的（第 4 章的 integer promotion），是轉回 `uint8_t` 時才截斷。`uadd_ok` 的兩行分別是溢位（4.3 × 10^9 超過 2^32 ≈ 4.29 × 10^9）與剛好沒溢位，判斷式「結果 ≥ x」正確地區分了兩者。
2. **B 段**：前兩行是正溢位與負溢位，結果的符號都翻轉了；手寫的 `tadd_ok` 與內建函式的判斷一致。第四行 TMax + TMin = −1 是異號相加，永遠不會溢位。`tadd_ok` 刻意把加法放在 unsigned 裡做，避免判斷式本身含有 UB。
3. **C 段**：這是 `thumbd` 事件的重現。正常的 4000 × 3000 照片兩種算法一致；32768 × 32769 在 32 位元裡只剩 131,072；65536 × 65536 × 4 = 2^34，低 32 位全是 0，`bad` 算出 0，而 `malloc(0)` 可能回傳一個不能寫入的指標，下一步寫入就出事。`ok` 版本在 64 位元裡算出正確值，再被 256 MiB 的上限擋下。
4. **D 段**：對照 5.7 節的表。−7 / 4 在 C 裡是 −1，直接右移得到 −2，加上 bias 3 之後才對。程式裡 `x >> 2` 對負數的結果在 C17 是「實作定義」（implementation-defined），主流編譯器都做算術右移，但可攜的程式不該依賴它。

把 C 段改成你自己的數字試試看：找出讓 `bytes_bad` 剛好等於 4 的寬高組合（提示：w × h × 4 ≡ 4 (mod 2^32)）。

## 5.12 在工作上怎麼用

### Code review：看到大小計算就停下來

整數溢位漏洞幾乎都出現在同一種程式碼形狀：**一個來自外部的整數，經過算術，變成 `malloc`、`memcpy`、陣列索引或迴圈上限**。review 時遇到這種形狀，用下面的清單逐項檢查：

```text
 看到：malloc(a * b) / memcpy(dst, src, n + hdr) / buf[off + len] / for (i < count)
   │
   ├─ 1. 這些數字有沒有任何一個來自外部？（檔案標頭、封包、HTTP 參數、資料庫欄位）
   │      └─ 沒有 → 風險低，但仍確認型別寬度
   │
   ├─ 2. 運算在什麼型別裡進行？
   │      └─ 兩個 uint32_t 相乘就是 32 位元，結果放進 size_t 也救不回來
   │
   ├─ 3. 運算前有沒有檢查範圍？是否用了 __builtin_*_overflow／ckd_*／calloc？
   │
   ├─ 4. signed 與 unsigned 是否混用？負數會不會變成巨大的長度？（第 4 章）
   │
   ├─ 5. 配置用的大小與寫入用的大小，是不是同一個變數？
   │      └─ 分別計算兩次，是 XDR 型漏洞的典型結構
   │
   └─ 6. 有沒有業務上限？即使不溢位，4 GiB 的配置也是 DoS
```

### 讓編譯器與 sanitizer 替你找

在 CI 裡加一個開啟 UBSan 的建置，搭配單元測試與 fuzzing（例如 libFuzzer 或 AFL++ 餵入隨機的 PNG 標頭），是找出整數溢位最有效的方法。常用的旗標：

```bash
# 開發與 CI：遇到 signed overflow 就印出位置並中止
clang -O1 -g -fsanitize=undefined -fno-sanitize-recover=all -o thumbd_test ...

# 只檢查整數相關問題（含 unsigned 繞回，誤報較多，適合針對解析模組）
clang -O1 -g -fsanitize=integer -o parser_test ...

# 編譯期警告：隱式轉換造成的截斷與 signed/unsigned 比較
clang -Wall -Wextra -Wconversion -Wsign-compare ...
```

UBSan 抓到 signed overflow 時的實際輸出長這樣（macOS arm64，原始碼是 `int total = len + 100;`，`len` 為 `INT_MAX`）：

```text
ub.c:7:21: runtime error: signed integer overflow: 2147483647 + 100 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior ub.c:7:21
```

訊息直接告訴你檔名、行號、兩個運算元與型別。在 fuzzing 裡加上 `-fno-sanitize-recover=all`，第一次溢位就會讓程式中止，fuzzer 就能把觸發它的輸入存下來。

### 要不要加 `-fwrapv`？

有些大型專案選擇用 `-fwrapv` 或 `-fno-strict-overflow` 編譯整個程式，Linux kernel 就是其中之一。這樣 signed overflow 變成定義良好的繞回，編譯器不會再刪掉依賴繞回的檢查。代價是失去一部分迴圈最佳化，以及讓「溢位其實是 bug」的情況更安靜。比較好的分工是：

| 情境 | 建議 |
|---|---|
| 新寫的程式碼 | 不依賴繞回；需要偵測時用 `ckd_*` 或內建函式；CI 開 UBSan |
| 舊程式碼裡有大量依賴繞回的寫法 | 評估加 `-fwrapv` 作為過渡，並逐步改寫 |
| 雜湊、checksum、亂數 | 本來就要繞回，用 unsigned 型別寫，不需要任何旗標 |
| 時間戳、序號比較 | 用 unsigned 減法再轉 signed 的 `time_after` 寫法 |
| 解析外部檔案或封包 | 範圍驗證 ＋ 有檢查的運算 ＋ 資源上限，三層都要 |

### 跨語言邊界時特別小心

拾光相簿的 API 層是 Python，`thumbd` 是 C。Python 端驗證「寬度 × 高度 < 1 億」時用的是無限精度整數，檢查本身是對的；但如果 C 端重新計算一次、而且型別比較窄，兩邊的結論就會不一致。原則是：**在最靠近使用點的地方，用使用點的型別再驗證一次**。同理，資料庫的 `BIGINT` 欄位傳給 C 的 `int`、JSON 的數字傳給 32 位元的欄位時，都要明確檢查範圍，不能假設上游已經檢查過。

## 5.13 常見錯誤與除錯

| 症狀 | 常見原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 處理特定大檔案時 heap 損壞或 segfault | 大小計算在 32 位元裡溢位，配置太小 | 印出寬高與計算出的大小；用 ASan（第 26 章）重現，看第一次越界寫入的位置 | 用 `size_t` 計算並以 `__builtin_mul_overflow` 檢查；加業務上限 |
| 溢位檢查在 debug 正常、release 失效 | 檢查式依賴 signed overflow，被最佳化刪除 | 比較 `-O0` 與 `-O2` 的組合語言；開 UBSan | 改成事前檢查（`a > INT_MAX - b`）或用內建函式 |
| `abs(x)` 回傳負數、陣列索引為負 | x 是 `INT_MIN`，取負號仍是自己 | 加 `assert(x != INT_MIN)` 或 UBSan | 先轉成 unsigned 再取模：`(unsigned)x % n` |
| 服務收到特定參數就 `SIGFPE` | `INT_MIN / -1` 或除以零（x86-64 的 `idiv` 觸發 exception） | core dump 的 `bt` 停在除法；檢查除數來源 | 除法前檢查除數為 0 與 `INT_MIN / -1` 的組合 |
| 負數除法結果差 1 | 用 `>>` 代替 `/`，負數向下取整 | 用負的奇數測試 | 直接寫 `/`，讓編譯器處理 bias |
| 長時間運作後計數或計時異常 | 計數器繞回（32 位元的毫秒計數約 49.7 天繞回） | 計算計數器繞回所需的時間是否吻合 | 用 64 位元計數器，或用 `time_after` 式的差值比較 |
| NumPy 計算結果比預期小很多或變負數 | 陣列 dtype 是 `int32`／`uint32`，運算繞回 | 檢查 `arr.dtype`；用 Python 整數重算一次 | 運算前轉成 `int64`，或用 `np.errstate` 搭配檢查 |

> [!tip] 在 gdb 裡確認是不是溢位
> 當機在解碼迴圈時，先 `frame` 到配置緩衝區的那一層，用 `print w * h * 4` 與 `print (unsigned long)w * h * 4` 對照：前者是 gdb 依照 C 的型別規則算出的 32 位元結果，後者是正確值。兩者不同，就幾乎可以確定是大小計算溢位。

## 5.14 動手練習

1. **手算**：用 4 位元二補數計算 −6 + −4、7 + 1、−8 + 7、−2 × 5，寫出截斷後的位元與解讀值，並判斷哪些溢位。（驗證方法：寫一段 C，用 `int8_t` 做同樣的運算後取最低 4 位，或直接用 Python 的 `(x + y) & 0xF` 再轉回二補數。）
2. **手算**：不用計算機，判斷 `uint32_t` 的 65535 × 65537 會不會溢位，結果是多少？（提示：65535 × 65537 = 2^32 − 1。答案：不溢位，剛好是 UMax。）
3. **延伸程式**：在 5.11 節的程式 C 段加入一組你設計的寬高，讓 `bytes_bad` 剛好等於 4。再把 `bytes_bad` 的參數改成 `int`，用 `-fsanitize=undefined` 編譯，觀察 UBSan 的訊息有什麼不同，並解釋為什麼 unsigned 版本沒有被回報。
4. 寫一個函式 `int div_floor(int a, int b)`，回傳向下取整的除法結果（Python 的 `//` 語意）。用 −7 // 2、7 // −2、−8 // 2 驗證，並和 Python 的結果比較。
5. 把 `int will_overflow(int len) { return len + 100 < len; }` 和改寫成 `return len > INT_MAX - 100;` 的版本，分別用 `clang -target x86_64-linux-gnu -O2 -S` 產生組合語言，比較兩者，並解釋第一個版本為什麼變成常數。
6. 在你工作上的程式碼裡，用 `grep -nE 'malloc\([^)]*\*'` 找出所有在 `malloc` 參數裡做乘法的地方，依 5.12 節的清單逐一檢查，至少修好一處或確認它是安全的。

## 本章重點整理

- w 位元的 unsigned 加法與乘法定義為對 2^w 取模，這在 C 裡是定義良好的行為；溢位時加法結果會比任何一個運算元小。
- 二補數加法與 unsigned 加法產生相同的位元，CPU 只有一個加法器；差別在解讀，以及 carry flag 與 overflow flag 分別記錄兩種意義的溢位。
- 只有同號相加才會溢位：正 + 正得到負是正溢位，負 + 負得到非負是負溢位；最高位有進位不代表 signed 溢位。
- 二補數取負號是 ~x + 1；TMin 沒有相反數，`-INT_MIN`、`abs(INT_MIN)`、`INT_MIN / -1` 都是 undefined behavior，後者在 x86-64 上會觸發 SIGFPE。
- 截斷到 w 位元後，unsigned 與二補數乘法的位元完全相同；乘法溢位不一定讓結果變負數，不能用符號判斷。
- 編譯器會把常數乘法改寫成 shift、`lea` 與加減法，把常數除法改寫成魔術數字乘法；不需要也不應該手動做這種改寫。
- C 的整數除法向零捨入，算術右移向下取整；負數除以 2^k 要先加 bias 2^k − 1，所以確定非負的值用 unsigned 會讓除法更簡單。
- signed overflow 在 C 是 undefined behavior，編譯器會假設它不發生，可能刪除依賴溢位的檢查，讓 debug 與 release 的行為不同。
- 偵測溢位要在運算前檢查，或使用 `__builtin_*_overflow` 與 C23 的 `ckd_*`；它們以硬體旗標實作，成本很低。
- 整數漏洞的典型結構是「外部整數 → 溢位的大小計算 → 太小的配置 → 照原本的數量寫入」，最終成為 heap overflow。
- 修大小計算要三層：驗證輸入範圍、使用有檢查的運算、設定資源上限；配置與寫入要使用同一個大小變數。
- UBSan、`-Wconversion` 與 fuzzing 是在工作上找出整數錯誤最有效的組合；`-fwrapv` 可以作為舊程式碼的過渡手段。
- 高階語言的規則各不相同：Java 與 Go 定義為繞回，Rust 在 debug 會 panic，Python 沒有上限，但 NumPy 陣列仍照 C 的方式繞回。

## 延伸問答

> [!question]- Q1. 「最高位有進位」和「signed overflow」有什麼不同？各用什麼旗標記錄？
> 最高位的進位代表 unsigned 意義下的溢位：兩個 unsigned 數相加的結果超過 2^w − 1。CPU 用 carry flag（CF）記錄它。signed overflow 則是兩個二補數相加的結果超出 TMin 到 TMax，用 overflow flag（OF）記錄，判斷方式是「兩個運算元同號，但結果的符號不同」。
>
> 兩者互相獨立。4 位元的 −1 + −1（1111 + 1111）最高位有進位，CF = 1，但結果 −2 正確，OF = 0；5 + 6（0101 + 0110）沒有進位，CF = 0，但結果解讀為 −5，OF = 1。同一條 `add` 指令會同時設定兩者，後續用 `jc`／`jb` 還是 `jo`／`jl` 這類指令，決定了你把這次加法當成 unsigned 還是 signed（第 8 章）。

> [!question]- Q2. 手算：8 位元二補數中，100 + 50、−100 + −50、−100 + 50 的結果分別是什麼？
> 8 位元範圍是 −128 到 127。100 + 50 = 150 超過 127，正溢位，截斷後是 150 − 256 = −106。−100 + −50 = −150 小於 −128，負溢位，截斷後是 −150 + 256 = 106。−100 + 50 = −50 在範圍內，異號相加不會溢位，結果就是 −50。
>
> 用位元驗證第一個：100 = 0110 0100，50 = 0011 0010，相加得 1001 0110，最高位是 1，二補數解讀為 −128 + 22 = −106。可以用 Python 的 `((x + y + 128) % 256) - 128` 驗證三個答案。

> [!question]- Q3. 為什麼 `size_t bytes = w * h * 4;`（w、h 是 `uint32_t`）把結果放進 64 位元的變數，還是會溢位？
> C 的運算型別由運算元決定，而不是由「結果要存到哪裡」決定。`w * h` 的兩個運算元都是 `uint32_t`（在 LP64 上 `unsigned int` 是 32 位元），所以乘法在 32 位元的 unsigned 裡進行並取模；乘以 `4`（`int`）時，`int` 被轉成 `unsigned int`，運算仍是 32 位元。整個式子算完、已經截斷之後，才被 zero extension 放進 64 位元的 `size_t`。
>
> 修法是讓第一個運算元先變寬：`(size_t)w * h * 4`，這樣 `h` 與 `4` 都會被轉成 `size_t`，整個乘法在 64 位元進行。組合語言也看得出差別：錯誤版本用 32 位元的 `imull`，正確版本用 64 位元的 `imulq`。即使如此，仍然應該用有檢查的乘法並設定上限，因為 64 位元也有溢位的一天，而且過大的配置本身就是問題。

> [!question]- Q4. 你在 code review 看到 `if (offset + len < offset) return -EINVAL;`，offset 與 len 都是 `int`。這個檢查有什麼問題？
> 這個檢查想偵測加法溢位，但它依賴 signed overflow 會繞回。signed overflow 在 C 是 undefined behavior，編譯器可以推論：在沒有溢位的情況下，len ≥ 0 時 `offset + len < offset` 不可能成立，於是可能把檢查化簡掉或改成只看 `len < 0`。本章 5.8 節的 `will_overflow` 在 `-O1` 就被編譯成常數 0。
>
> 正確寫法是先確認 len 非負，再做事前檢查：`if (len < 0 || offset > INT_MAX - len) return -EINVAL;`，或用 `__builtin_add_overflow(offset, len, &end)`。更根本的做法是長度與位移改用 `size_t` 或固定寬度的 unsigned 型別，並在進入函式時就驗證範圍。

> [!question]- Q5. 編譯器把 `x / 8`（x 是 `int`）編譯成 `leal 7(%rdi)`、`testl`、`cmovns`、`sarl $3` 四條指令，為什麼不直接右移 3 位？
> 因為 C 規定整數除法向零捨入，而算術右移是向下取整。對正數兩者相同；對不能整除的負數，右移的結果會比除法小 1，例如 −9 >> 3 = −2，但 −9 / 8 = −1。
>
> 修正方法是對負數先加上 bias 2^3 − 1 = 7 再右移：(−9 + 7) >> 3 = −2 >> 3 = −1。四條指令分別是：算 x + 7、檢查 x 的符號、x 非負時改回原值（不加 bias）、最後右移。若把變數改成 `unsigned`，編譯器知道不會有負數，就只需要一條 `shrl $3`。這也說明了語意上確定非負的量，用 unsigned 型別有時能得到更簡單的程式碼。

> [!question]- Q6. 面試題：如何判斷兩個 `size_t` 相乘會不會溢位？至少說出兩種方法並比較。
> 第一種是事前用除法檢查：`if (a != 0 && b > SIZE_MAX / a)` 就表示 a × b 會溢位。它是純標準 C，任何編譯器都能用，但除法指令較慢，在熱路徑上可能有成本。第二種是用 `__builtin_mul_overflow(a, b, &r)`（GCC、Clang）或 C23 的 `ckd_mul(&r, a, b)`，編譯器會用硬體乘法指令的溢位旗標實作，在 x86-64 上就是 `mulq` 加一條 `seto`，幾乎沒有額外成本，也不會誤用。
>
> 第三種是在有更寬型別時使用它，例如兩個 `uint32_t` 轉成 `uint64_t` 相乘再比較；但 `size_t` 已經是 64 位元，要用 `unsigned __int128` 這種非標準擴充。實務上的建議是：能用 `calloc`／`reallocarray` 就讓函式庫處理；需要自己算時，新程式碼用 `ckd_mul`，舊編譯器用內建函式，最後才用除法檢查。

> [!question]- Q7. 一個用 32 位元 unsigned 毫秒計數器的嵌入式設備，大約多久會出問題？要怎麼寫比較時間的程式碼才不怕繞回？
> 2^32 毫秒 ≈ 4,294,967 秒 ≈ 49.7 天。如果程式用 `if (now > deadline)` 比較時間，在計數器繞回的那一刻，`now` 突然變得很小，所有「已經過期」的判斷都會失效，或反過來永遠不會過期，這類 bug 往往在設備連續運作一個多月後才出現。
>
> 不怕繞回的寫法是比較差值：`if ((int32_t)(now - deadline) >= 0)`。unsigned 減法在繞回時仍然得到正確的模 2^32 差值，再把它解讀成 signed，只要兩個時間點相差不到 2^31 毫秒（約 24.8 天），正負號就是正確的。這正是 Linux kernel `time_after` 巨集與 TCP sequence number 比較的做法。另一個選擇是直接改用 64 位元計數器，以毫秒計大約要數億年才會繞回。

> [!question]- Q8. 程式找錯：下面的函式想回傳陣列中「第 i 個到第 j 個元素」的長度，哪裡有問題？`int span(unsigned i, unsigned j) { return j - i + 1 > 0 ? j - i + 1 : 0; }`
> `j - i + 1` 的運算元都是 unsigned，所以整個運算是 unsigned 的。當 j < i 時，`j - i` 不會變成負數，而是繞回成一個接近 2^32 的大數，加 1 之後仍然大於 0（除非剛好 j = i − 1，得到 0）。所以 `> 0` 的判斷幾乎永遠成立，函式會回傳一個被轉成 `int` 的巨大值，在 LP64 上通常變成負數或很大的正數，再被拿去當長度就會越界。
>
> unsigned 數「大於 0」等於「不等於 0」，這個檢查本身就沒有意義。正確的寫法是在減法之前比較：`if (j < i) return 0; return (int)(j - i + 1);`，並視情況檢查 j − i + 1 不超過 `INT_MAX`。這個例子和第 4 章的 `size_t` 迴圈陷阱是同一類問題：對 unsigned 數，先比較大小，再做減法。
