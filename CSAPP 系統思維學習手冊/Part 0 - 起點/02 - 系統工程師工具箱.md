## 2.1 故事：只在長檔名時才當掉的 cache key

第二週，小安接到第一個真正的 bug。`thumbd` 的縮圖快取用一個字串當 key，格式是 `原圖路徑_寬x高`，例如 `cat.jpg_320x240`。最近 SRE 阿哲發現，有些使用者上傳的照片一請求縮圖，`thumbd` 的 worker 就整個掛掉，log 裡只有一行 `Aborted`，systemd 隨即把服務重啟。

小安在自己的筆電上用 `cat.jpg` 測試，一切正常。老周提示：「看一下出事的請求，路徑是不是特別長？」果然，出事的都是像 `2024/summer/beach_sunset.jpg` 這種放在多層資料夾裡的照片。小安翻出產生 key 的程式碼：

```c
// not-runnable：thumbd 裡的原始寫法（片段）
char key[16];
sprintf(key, "%s_%dx%d", path, w, h);
```

在 Python 裡，字串會自己長大；在 Java 裡，寫超過陣列範圍會丟出 `ArrayIndexOutOfBoundsException`。但在 C 裡，`key` 就是 stack 上連續的 16 個 byte，`sprintf` 不知道它有多大，只會一直往後寫。路徑一長，寫出去的部分就踩壞了 `key` 後面的東西。更奇怪的是：同一份程式，用 `-O0` 編譯時以 `Aborted` 結束，用 `-O2` 編譯時卻以另一個 signal 結束，在某些機器上甚至「看起來正常」地印出亂碼。

老周說：「C 不會保護你，所以你要自己帶工具。今天教你四樣東西：讀懂記憶體的模型、會開編譯器的警告、會用 sanitizer、會用 debugger。」這一章就是這個工具箱。它不是完整的 C 教學，而是挑出後面每一章都會用到的部分，從零講起，每個概念都配一段能跑的程式。

## 2.2 從 Python／Java 到 C：先換一個心智模型

學 C 最大的障礙不是語法，C 的語法和 Java 很像。真正的障礙是：Python 和 Java 把記憶體藏起來了，C 把它攤在你面前。要寫好 C，先要接受一個非常具體的模型：

> 記憶體是一大排有編號的格子，每格一個 byte。每個變數佔用其中連續的幾格，編號最小的那格的編號，就是這個變數的**位址**（address）。

在 Python 裡，`x = 640` 讓名字 `x` 指向一個整數物件，物件放在哪裡、佔多大，你不必知道。在 C 裡，`int x = 640;` 的意思是：「在記憶體裡找 4 個連續的格子，把 640 的二進位表示放進去，以後 `x` 就代表這 4 格。」型別決定了佔幾格、以及這幾格的位元要怎麼解讀（第 1 章 1.2 節）。

| 面向 | Python／Java | C | 後果 |
|---|---|---|---|
| 記憶體回收 | garbage collector 自動回收 | `malloc` 之後必須自己 `free` | 忘了 `free` 是 leak，`free` 兩次會毀掉 heap（第 26 章） |
| 陣列越界 | 丟出例外 | 不檢查，直接讀寫旁邊的記憶體 | 資料被悄悄改壞，或之後才當機（第 11 章） |
| 字串 | 物件，知道自己的長度 | 一串 `char`，靠結尾的 `\0` 判斷結束 | 少了 `\0` 或空間不夠就越界 |
| 錯誤處理 | 例外 | 回傳值（常是 −1 或 `NULL`）加上 `errno` | 不檢查回傳值，錯誤就被吞掉 |
| 整數 | Python 整數無限大；Java 溢位會繞回 | 大小依平台而定；signed 溢位是 undefined behavior | 看似正常的運算可能被編譯器「最佳化掉」（第 5 章） |
| 執行方式 | 直譯或 JIT，有 runtime 檢查 | 編譯成機器碼，幾乎沒有 runtime 檢查 | 快，但錯誤不會自動被抓到 |

這張表右邊那一欄，就是本書許多章節要處理的問題。C 的設計哲學是「相信程式設計師、不為你沒要求的檢查付代價」，這讓它成為作業系統、資料庫、`thumbd` 這類需要極致效能與控制力的軟體的語言，也讓它成為大多數安全漏洞的來源。

## 2.3 型別與大小：`sizeof`

C 的基本型別都有固定的大小，但「固定」是指在同一個平台上固定，不同平台可以不同。`sizeof` 運算子告訴你一個型別或變數佔幾個 byte，它在編譯時就算好，不會在執行時花任何成本。

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    printf("%-10s %zu\n", "char", sizeof(char));
    printf("%-10s %zu\n", "short", sizeof(short));
    printf("%-10s %zu\n", "int", sizeof(int));
    printf("%-10s %zu\n", "long", sizeof(long));
    printf("%-10s %zu\n", "long long", sizeof(long long));
    printf("%-10s %zu\n", "float", sizeof(float));
    printf("%-10s %zu\n", "double", sizeof(double));
    printf("%-10s %zu\n", "void *", sizeof(void *));
    printf("%-10s %zu\n", "size_t", sizeof(size_t));
    printf("%-10s %zu\n", "uint8_t", sizeof(uint8_t));
    printf("%-10s %zu\n", "uint32_t", sizeof(uint32_t));
    return 0;
}
```

在 macOS arm64 上的輸出：

```text
char       1
short      2
int        4
long       8
long long  8
float      4
double     8
void *     8
size_t     8
uint8_t    1
uint32_t   4
```

這組數字叫 **LP64** 模型（long 與 pointer 是 64 bits），64-bit 的 Linux 與 macOS 都採用它，所以在 x86-64 Linux 上你會看到一樣的結果。但 64-bit Windows 採用 LLP64，`long` 只有 4 bytes；32-bit 系統上指標是 4 bytes。C 標準只保證 `char` 是 1 byte、`short` 至少 16 bits、`int` 至少 16 bits、`long` 至少 32 bits。

| 型別 | LP64（Linux、macOS 64-bit） | 32-bit 系統 | 什麼時候用 |
|---|---|---|---|
| `char` | 1 | 1 | 字元、原始 byte（處理位元組時用 `unsigned char`） |
| `int` | 4 | 4 | 一般的計數與運算 |
| `long` | 8 | 4 | 不建議用來表達「固定 64 bits」，改用 `int64_t` |
| 指標（`T *`） | 8 | 4 | 存放位址 |
| `size_t` | 8 | 4 | 大小與索引，`sizeof` 和 `strlen` 的回傳型別 |
| `uint8_t`、`uint32_t` 等 | 1、4 | 1、4 | 檔案格式、網路協定這種位元數必須精確的場合 |

`thumbd` 解析 PNG header 時，寬與高是規格中明定的 32-bit 無號整數，所以程式裡一律用 `<stdint.h>` 的 `uint32_t`，而不是「應該是 4 bytes 吧」的 `unsigned int`。`printf` 印 `size_t` 要用 `%zu`，印指標要用 `%p`；格式字串和參數型別不符本身就是 undefined behavior，而 `-Wall` 會幫你抓出來。

> [!warning] 常見誤解
> 「`char` 一定是有號的。」不一定：x86-64 Linux 上 `char` 是有號的，ARM64 Linux 上預設是無號的（Apple 平台的 ARM64 則例外，`char` 是有號的）。處理影像像素、檔案內容這類「原始 byte」時，請明確寫 `unsigned char` 或 `uint8_t`，否則 `0xFF` 在某些平台上會被當成 −1（第 4 章會解釋為什麼）。

## 2.4 位址與指標：`&` 與 `*`

**指標**（pointer）是一個「存放位址的變數」。它本身也佔記憶體（LP64 上 8 bytes），裡面的值是另一個東西的位址。C 用兩個運算子在「東西」與「位址」之間轉換：

- `&x`：取 `x` 的位址（address-of）。
- `*p`：到 `p` 存的那個位址去，取出那裡的東西（dereference，解參考）。

宣告 `int *p;` 讀作「`p` 是一個指向 `int` 的指標」：`*p` 的型別是 `int`。把一個變數和指向它的指標畫出來：

```text
 位址（示意）   記憶體內容                 變數
 ──────────    ──────────────────────    ─────
 0x...d02c     ┌──────────────────────┐
               │ 640（4 bytes）        │  ← width
               └──────────────────────┘
                       ▲
                       │ p 的值就是 width 的位址
 0x...d040     ┌──────────────────────┐
               │ 0x...d02c（8 bytes）  │  ← p（型別 int *）
               └──────────────────────┘

 &width → 0x...d02c       p  → 0x...d02c
 *p     → 640             *p = 800 會把 width 改成 800
```

C 的函式呼叫一律是**傳值**（pass by value）：參數是呼叫者那邊的值的複本。想讓函式改到呼叫者的變數，就要把變數的位址傳進去，這是 C 用指標最常見的理由。下面的程式把這些放在一起：

```c
#include <stdio.h>

static void swap_wrong(int a, int b) {   /* 收到的是複本 */
    int t = a; a = b; b = t;
}

static void swap(int *a, int *b) {       /* 收到的是位址，可以改到原本的變數 */
    int t = *a; *a = *b; *b = t;
}

int main(void) {
    int width = 640, height = 480;
    int *p = &width;                     /* p 存的是 width 的位址 */

    printf("width 的值 = %d，位址 = %p\n", width, (void *)&width);
    printf("p 的值     = %p，*p = %d\n", (void *)p, *p);
    *p = 800;                            /* 透過指標改 width */
    printf("*p = 800 之後，width = %d\n", width);

    swap_wrong(width, height);
    printf("swap_wrong 之後：width=%d height=%d\n", width, height);
    swap(&width, &height);
    printf("swap 之後：      width=%d height=%d\n", width, height);

    int row[4] = {10, 20, 30, 40};
    int *q = row;                        /* 陣列名稱在運算式中會變成首元素的位址 */
    for (int i = 0; i < 4; i++)
        printf("q+%d = %p  *(q+%d) = %d  row[%d] = %d\n",
               i, (void *)(q + i), i, *(q + i), i, row[i]);
    printf("sizeof row = %zu，sizeof q = %zu\n", sizeof row, sizeof q);
    return 0;
}
```

在 macOS arm64 上的輸出（位址每次執行都不同）：

```text
width 的值 = 640，位址 = 0x16f67d02c
p 的值     = 0x16f67d02c，*p = 640
*p = 800 之後，width = 800
swap_wrong 之後：width=800 height=480
swap 之後：      width=480 height=800
q+0 = 0x16f67d030  *(q+0) = 10  row[0] = 10
q+1 = 0x16f67d034  *(q+1) = 20  row[1] = 20
q+2 = 0x16f67d038  *(q+2) = 30  row[2] = 30
q+3 = 0x16f67d03c  *(q+3) = 40  row[3] = 40
sizeof row = 16，sizeof q = 8
```

逐段解讀：

1. `p` 的值和 `&width` 完全相同，`*p` 讀出 640；透過 `*p = 800` 寫入後，`width` 真的變了。指標就是「另一條通往同一塊記憶體的路」。
2. `swap_wrong` 交換的是自己的複本，函式結束複本就消失，呼叫者看不到任何變化；`swap` 收到位址，透過 `*a`、`*b` 改的是呼叫者的變數。Java 裡「物件參數可以被改」的效果，在 C 裡就是明確地傳指標。
3. `q + 1` 的位址比 `q` 大 4，不是大 1。這是**指標運算**（pointer arithmetic）的規則：指標加 n，位址前進 `n × sizeof(*q)` 個 byte。`q` 是 `int *`，所以每步 4 bytes。
4. `*(q + i)` 與 `row[i]` 的值一樣。事實上 C 把 `a[i]` **定義**成 `*(a + i)`，中括號只是語法糖。
5. `sizeof row` 是 16（4 個 `int`），`sizeof q` 是 8（一個指標）。陣列和指標在多數運算式裡可以互換，但它們不是同一件事：陣列是那 16 個 byte 本身，指標只是一個記著位址的 8-byte 變數。

**NULL** 是一個保證不指向任何有效物件的特殊指標值。函式找不到結果或配置失敗時常回傳 `NULL`，對 `NULL` 解參考會觸發 segmentation fault（第 23 章解釋為什麼）。所以 `malloc` 之後一定要檢查是否為 `NULL`。

## 2.5 陣列退化與指標運算的陷阱

上一節的第 5 點有一個在工作上很常咬人的後果。陣列傳給函式時，傳過去的不是整個陣列，而是首元素的位址，這叫**陣列退化**（array decay）。即使參數寫成 `int pixels[64]`，在函式裡它也只是一個 `int *`：

```c
#include <stdio.h>

static void fill(int pixels[64]) {        /* 看起來是陣列，其實是 int * */
    printf("在 fill 裡：sizeof pixels = %zu\n", sizeof pixels);
}

int main(void) {
    int pixels[64] = {0};
    printf("在 main 裡：sizeof pixels = %zu\n", sizeof pixels);
    fill(pixels);
    return 0;
}
```

clang 在 `-Wall` 下直接警告：

```text
decay.c:4:59: warning: sizeof on array function parameter will return size of 'int *' instead of 'int[64]' [-Wsizeof-array-argument]
```

執行結果（macOS arm64）：

```text
在 main 裡：sizeof pixels = 256
在 fill 裡：sizeof pixels = 8
```

如果在 `fill` 裡寫 `for (i = 0; i < sizeof pixels / sizeof pixels[0]; i++)`，迴圈只會跑 2 次而不是 64 次。這就是為什麼 C 的函式介面幾乎都長成「指標加長度」：`read(fd, buf, n)`、`memcpy(dst, src, n)`、`snprintf(buf, cap, ...)`。函式自己無從得知陣列多大，長度必須由呼叫者明確傳入。

把一個 `int` 陣列的記憶體與指標運算畫出來：

```text
 row：             row[0]    row[1]    row[2]    row[3]
 位址：           0x...030  0x...034  0x...038  0x...03c   0x...040
                 ┌─────────┬─────────┬─────────┬─────────┐
                 │   10    │   20    │   30    │   40    │  （超出範圍）
                 └─────────┴─────────┴─────────┴─────────┘
 指標：            q         q+1       q+2       q+3        q+4
                                                           ▲
                         可以算出這個位址，但不能對它解參考 ┘
```

C 允許指標指向「最後一個元素的下一個位置」（例如當迴圈的終點），但對它解參考，或指到陣列之前、更後面的位置，都是 undefined behavior。編譯器與硬體都不會阻止你，`q[4]` 會讀到 `row` 後面剛好放著的任何東西。

## 2.6 字串與 `'\0'`

C 沒有字串型別。**C 字串**是一串 `char`，以一個值為 0 的 byte（寫成 `'\0'`，叫 null terminator）標示結束。所有字串函式（`strlen`、`strcpy`、`printf("%s")`）都是從起點開始一個一個讀，直到碰到 `\0` 為止。

```c
#include <stdio.h>
#include <string.h>

int main(void) {
    char name[] = "cat.jpeg";           /* 編譯器自動在結尾補上 '\0' */
    const char *ptr = "cat.jpeg";       /* 指向唯讀區的字串常數 */

    printf("sizeof name = %zu，strlen(name) = %zu\n", sizeof name, strlen(name));
    printf("sizeof ptr  = %zu，strlen(ptr)  = %zu\n", sizeof ptr, strlen(ptr));

    printf("name 的每個 byte：");
    for (size_t i = 0; i < sizeof name; i++)
        printf("%02x ", (unsigned char)name[i]);
    printf("\n");

    name[3] = '\0';                     /* 在中間放一個結束符號 */
    printf("把 name[3] 改成 '\\0' 之後：\"%s\"，strlen = %zu\n", name, strlen(name));

    char key[12];
    int need = snprintf(key, sizeof key, "%s_%dx%d", "sunset.png", 320, 240);
    printf("snprintf 需要 %d 個字元，實際寫入 \"%s\"（被截斷）\n", need, key);
    return 0;
}
```

在 macOS arm64 上的輸出：

```text
sizeof name = 9，strlen(name) = 8
sizeof ptr  = 8，strlen(ptr)  = 8
name 的每個 byte：63 61 74 2e 6a 70 65 67 00 
把 name[3] 改成 '\0' 之後："cat"，strlen = 3
snprintf 需要 18 個字元，實際寫入 "sunset.png_"（被截斷）
```

逐行解讀：

1. `"cat.jpeg"` 有 8 個字元，但 `name` 佔 9 bytes，多出來的是結尾的 `00`。**`strlen` 不算 `\0`，`sizeof` 算**。替字串配置空間時，永遠要加 1。
2. `sizeof ptr` 是 8，因為 `ptr` 是指標，跟字串多長無關；這裡剛好和 `strlen` 一樣是 8，純屬巧合，千萬別用 `sizeof` 指標來求字串長度。
3. 把 `name[3]` 改成 `\0` 之後，`printf` 只印出 `cat`：後面的 `jpeg` 還在記憶體裡，但字串函式在第一個 `\0` 就停了。
4. `snprintf` 最多寫 `cap − 1` 個字元再補 `\0`，絕不越界；它的回傳值是「如果空間足夠，本來要寫多少字元」。回傳值 ≥ `cap` 就代表被截斷了，這是 2.15 節修 bug 時要用的判斷。

`name` 與 `ptr` 的差別也值得記住：`char name[]` 在 stack 上建立一份可修改的複本；`const char *ptr = "..."` 指向字串常數，它放在唯讀區域，寫入會 segfault（第 23 章）。下表整理字串函式的安全性：

| 函式 | 會不會越界 | 問題 | 建議 |
|---|---|---|---|
| `gets` | 一定可能 | 完全不知道緩衝區大小，C11 已移除 | 永遠不要用，改 `fgets` |
| `strcpy`、`strcat`、`sprintf` | 可能 | 不知道目的地多大 | 改用有長度參數的版本 |
| `strncpy` | 不會越界，但 | 來源太長時**不補 `\0`**，結果不是合法字串 | 小心使用，或改 `snprintf` |
| `snprintf` | 不會 | 會截斷，要檢查回傳值 | 一般情況的首選 |

## 2.7 Struct、`malloc` 與 `->`

**Struct**（結構）把幾個不同型別的欄位綁成一個整體，像是只有資料、沒有方法的 class。`thumbd` 用一個 struct 表示解碼後的影像：

```c
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

struct image {
    uint32_t width;
    uint32_t height;
    uint8_t  channels;     /* 3 = RGB，4 = RGBA */
    uint8_t *pixels;       /* 指向 width*height*channels 個 byte */
};

static struct image *image_new(uint32_t w, uint32_t h, uint8_t ch) {
    struct image *img = malloc(sizeof *img);
    if (img == NULL) return NULL;
    img->width = w;                      /* img->width 等於 (*img).width */
    img->height = h;
    img->channels = ch;
    img->pixels = calloc((size_t)w * h * ch, 1);
    if (img->pixels == NULL) { free(img); return NULL; }
    return img;
}

static void image_free(struct image *img) {
    if (img == NULL) return;
    free(img->pixels);                   /* 先釋放裡面的，再釋放外面的 */
    free(img);
}

int main(void) {
    printf("sizeof(struct image) = %zu\n", sizeof(struct image));
    printf("offsetof width    = %zu\n", offsetof(struct image, width));
    printf("offsetof height   = %zu\n", offsetof(struct image, height));
    printf("offsetof channels = %zu\n", offsetof(struct image, channels));
    printf("offsetof pixels   = %zu\n", offsetof(struct image, pixels));

    struct image *img = image_new(4, 2, 3);
    if (img == NULL) return 1;
    size_t x = 1, y = 1;                 /* 第 1 列第 1 行的像素 */
    uint8_t *px = img->pixels + (y * img->width + x) * img->channels;
    px[0] = 255;                          /* 把它設成紅色 */
    printf("像素 (1,1) 在 pixels 的第 %td 個 byte，R=%u G=%u B=%u\n",
           px - img->pixels, px[0], px[1], px[2]);
    image_free(img);
    return 0;
}
```

在 macOS arm64 上的輸出（x86-64 Linux 相同）：

```text
sizeof(struct image) = 24
offsetof width    = 0
offsetof height   = 4
offsetof channels = 8
offsetof pixels   = 16
像素 (1,1) 在 pixels 的第 15 個 byte，R=255 G=0 B=0
```

這段程式有好幾個重點：

1. **欄位加起來不等於 struct 的大小**。4 + 4 + 1 + 8 = 17，但 `sizeof` 是 24。`offsetof` 顯示 `pixels` 從第 16 個 byte 開始，`channels` 後面空了 7 bytes。這叫 **padding**（填充）：8-byte 的指標必須放在 8 的倍數的位址上，編譯器只好在中間補空白。第 10 章會講對齊規則，以及怎麼重排欄位減少浪費。
2. **`->` 是「透過指標存取欄位」**：`img->width` 就是 `(*img).width` 的簡寫。手上拿的是 struct 本身就用 `.`，拿的是指向 struct 的指標就用 `->`。
3. **`malloc` 只配置、不初始化；`calloc` 會清成 0**。`malloc(sizeof *img)` 的寫法讓大小跟著 `img` 的型別走，以後改型別也不會算錯。兩者在空間不足時都回傳 `NULL`，必須檢查。
4. **二維影像存成一維陣列**：像素 (x, y) 的位置是 `(y × width + x) × channels`。(1, 1) 在 4 像素寬、3 通道的影像中，就是 (1 × 4 + 1) × 3 = 15，和輸出一致。這正是第 1 章實驗三 row-major 的排法。
5. **每個 `malloc` 都要有對應的 `free`，而且順序要對**：先釋放 `pixels`，再釋放 `img`。反過來的話，`img` 已經釋放，再讀 `img->pixels` 就是 use-after-free。

`image_new` 和 `image_free` 成對出現，這是 C 裡管理資源的基本模式：誰配置、誰負責釋放，要在介面上說清楚。這個概念叫**所有權**（ownership），C 不會幫你檢查，只能靠約定與工具（第 26 章）。

```text
 stack                         heap
 ┌──────────────┐              ┌───────────────────────────────┐
 │ img: 0x...a0 │─────────────▶│ struct image（24 bytes）       │
 └──────────────┘              │  width=4  height=2  channels=3│
                               │  (padding 7 bytes)            │
                               │  pixels: 0x...c0 ─────┐       │
                               └───────────────────────┼───────┘
                                                       ▼
                               ┌───────────────────────────────┐
                               │ 24 bytes 像素資料（4×2×3）     │
                               └───────────────────────────────┘
 image_free 的順序：先 free(pixels)，再 free(img)
```

## 2.8 標頭檔、宣告與 header guard

`thumbd` 有幾十個 `.c` 檔。檔案之間要互相呼叫，就需要**標頭檔**（header file，`.h`）。要理解標頭檔，先分清兩個詞：

- **宣告**（declaration）：告訴編譯器「有這個名字，型別長這樣」，不產生程式碼或配置空間。例如 `struct size2d fit_within(struct size2d src, uint32_t max_side);`。
- **定義**（definition）：真正的函式本體，或真正配置空間的變數。整個程式裡每個函式與全域變數只能定義一次。

標頭檔放宣告，`.c` 檔放定義。第 1 章說過，`#include` 只是把檔案內容原封不動貼進來，所以一個 `.c` 只要 include 了標頭檔，就知道該怎麼呼叫那些函式；本體則由 linker 在連結時從另一個 `.o` 找來。

```c
// not-runnable：thumb.h
#ifndef THUMB_H          /* header guard：第一次 include 時才會進來 */
#define THUMB_H

#include <stdint.h>

struct size2d { uint32_t w, h; };

/* 宣告（declaration）：告訴編譯器「有這個函式，長這樣」 */
struct size2d fit_within(struct size2d src, uint32_t max_side);

#endif
```

```c
// not-runnable：thumb.c
#include "thumb.h"

/* 定義（definition）：真正的程式碼，只能出現在一個 .c 裡 */
struct size2d fit_within(struct size2d src, uint32_t max_side) {
    uint32_t longest = src.w > src.h ? src.w : src.h;
    if (longest <= max_side) return src;
    struct size2d dst = {
        (uint32_t)((uint64_t)src.w * max_side / longest),
        (uint32_t)((uint64_t)src.h * max_side / longest),
    };
    return dst;
}
```

```c
// not-runnable：main.c，需要和 thumb.c 一起編譯
#include <stdio.h>
#include "thumb.h"
#include "thumb.h"       /* 故意 include 兩次：有 header guard 就沒事 */

int main(void) {
    struct size2d s = fit_within((struct size2d){4000, 3000}, 320);
    printf("%ux%u\n", s.w, s.h);
    return 0;
}
```

分別編譯再連結（macOS arm64）：

```text
$ cc -std=c17 -Wall -Wextra -c thumb.c
$ cc -std=c17 -Wall -Wextra -c main.c
$ cc thumb.o main.o -o fit
$ ./fit
320x240
```

如果忘了 `thumb.c`，只編 `main.c`，就會重現小安第一天的錯誤。macOS 的 linker 訊息長這樣，Linux 上則是 `undefined reference to 'fit_within'`：

```text
$ cc -std=c17 -Wall -Wextra main.c -o fit2
Undefined symbols for architecture arm64:
  "_fit_within", referenced from:
      _main in main-b28687.o
ld: symbol(s) not found for architecture arm64
```

**Header guard** 是標頭檔開頭的 `#ifndef THUMB_H`／`#define THUMB_H` 與結尾的 `#endif`。第一次 include 時 `THUMB_H` 還沒定義，內容被保留並順便定義 `THUMB_H`；第二次 include 時 `THUMB_H` 已經定義，整段被跳過。大型專案裡 A.h include B.h、C.h 也 include B.h 是家常便飯，沒有 guard 的話，`struct size2d` 會被定義兩次。把 guard 拿掉再編譯 `main.c`，clang 會報錯：

```text
./noguard.h:6:8: error: redefinition of 'size2d'
    6 | struct size2d { uint32_t w, h; };
      |        ^
```

很多編譯器也支援 `#pragma once` 達到同樣效果，寫起來比較短，但它不是 C 標準的一部分。另外兩個和多檔案有關的關鍵字：`static` 放在函式或全域變數前面，表示「只在這個 `.c` 檔內可見」，不會和別的檔案的同名符號衝突；`extern int counter;` 則是全域變數的宣告，告訴編譯器「這個變數定義在別處」。第 18 章會從 linker 的角度重新看這些規則。

## 2.9 Linux shell 基本功

本書的指令大多在 Linux 的 shell（通常是 bash 或 zsh）裡執行。shell 是一支「讀一行指令、執行、再讀下一行」的程式，第 21 章會親手寫一個。你需要先熟悉這些操作：

| 指令 | 用途 | 例子 |
|---|---|---|
| `pwd`、`cd`、`ls -l` | 目前在哪、切換目錄、列出檔案與權限 | `cd ~/thumbd && ls -l build/` |
| `cat`、`less`、`head`、`tail -f` | 看檔案內容；`tail -f` 持續看 log | `tail -f /var/log/thumbd.log` |
| `grep` | 搜尋文字 | `grep -n "make_key" *.c` |
| `find` | 找檔案 | `find . -name "*.h"` |
| `ps`、`top`、`kill` | 看 process、送 signal | `ps aux \| grep thumbd`、`kill -HUP 1234` |
| `which`、`echo $PATH` | 指令是從哪個路徑找到的 | `which cc` |
| `chmod +x` | 讓檔案可執行 | `chmod +x run_tests.sh` |
| `man` | 查手冊 | `man 2 read` |

shell 最強大的地方是**組合**：

```bash
./thumbd > out.log 2> err.log    # 標準輸出寫到 out.log，標準錯誤寫到 err.log
./thumbd > all.log 2>&1          # 兩者都寫到 all.log
grep -c "Aborted" err.log        # 數一數出現幾次
ps aux | grep thumbd | wc -l     # pipe：前一支程式的輸出當作下一支的輸入
./test_fit; echo "exit=$?"       # $? 是上一個指令的結束碼
```

每支程式結束時都會回報一個**結束狀態**（exit status）：0 代表成功，非 0 代表失敗，這就是 `main` 裡 `return 0` 的意義。shell 把它放在 `$?` 裡，本書把這個具體數字（例如 139）叫做**結束碼**（exit code）；兩者指的是同一件事，談概念時說結束狀態，談某個數值時說結束碼。如果程式是被 signal 殺掉的，shell 會回報 128 加上 signal 編號。這是 2.1 節那種當機在 log 裡最常見的線索：

| 結束碼 | 意義 | 常見原因 |
|---|---|---|
| 0 | 正常結束 | — |
| 1、2… | 程式自己回報的錯誤 | `return 1`、`exit(2)` |
| 134 = 128 + 6 | SIGABRT | `abort()`、`assert` 失敗、stack protector 或 libc 偵測到記憶體損壞（Linux glibc 的 `_FORTIFY_SOURCE` 檢查失敗也是這一類） |
| 139 = 128 + 11 | SIGSEGV | segmentation fault：存取不合法的位址（第 23 章） |
| 137 = 128 + 9 | SIGKILL | 被 `kill -9` 或 OOM killer 殺掉（第 24 章） |
| 133 = 128 + 5 | SIGTRAP | 執行到陷阱指令，例如 `__builtin_trap()` 或 macOS 上 `_FORTIFY_SOURCE` 檢查失敗（依平台而定） |

`>` 和 `|` 背後是第 27 章的 `dup2` 與 pipe，`kill` 背後是第 22 章的 signal。現在只要會用，後面會一一拆開。

## 2.10 編譯選項：讓編譯器替你抓錯

第 1 章用過 `cc -E`、`-S`、`-c`。日常開發還有幾類選項，決定了你能從編譯器得到多少幫助：

| 選項 | 作用 | 什麼時候用 |
|---|---|---|
| `-std=c17` | 指定 C 標準版本 | 一律加上，避免依賴編譯器的預設值 |
| `-Wall -Wextra` | 開啟大部分常用警告 | 一律加上；警告常常就是 bug |
| `-Werror` | 把警告當成錯誤 | CI 中使用，不讓新警告混進來 |
| `-O0`、`-O1`、`-O2`、`-O3`、`-Os` | 最佳化等級：不最佳化、到積極最佳化、針對大小最佳化 | 除錯時 `-O0` 或 `-Og`；正式版 `-O2` |
| `-g` | 產生 debug 資訊（變數名稱、行號） | 除錯一定要加；正式版也建議加，另外存放 |
| `-fsanitize=address` | AddressSanitizer：抓越界、use-after-free | 開發與測試 |
| `-fsanitize=undefined` | UBSan：抓 signed overflow、非法 shift 等 UB | 開發與測試 |
| `-fsanitize=thread` | ThreadSanitizer：抓 data race | 測試多執行緒程式（第 31 章） |
| `-I dir`、`-L dir`、`-l name` | 標頭檔搜尋路徑、函式庫搜尋路徑、連結某個函式庫 | `-I/usr/include/libpng -ljpeg` |
| `-D NAME=val` | 定義巨集，等於在檔案開頭寫 `#define` | `-DTHUMBD_VERSION=\"1.4.2\"` |

一個常用的開發組合是：

```bash
cc -std=c17 -Wall -Wextra -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer \
   -o thumbd_dev *.c -ljpeg -lpng
```

`-fno-omit-frame-pointer` 讓 sanitizer 與 profiler 印出的呼叫堆疊比較完整（第 9 章會解釋 frame pointer）。

**Sanitizer** 是編譯器在你的程式裡插入檢查碼的功能。例如 AddressSanitizer（ASan）會在每個陣列與 heap 區塊的前後放一段「禁區」（redzone），並在每次讀寫記憶體之前檢查目標是否落在禁區或已釋放的區域。代價是程式變慢約 2 倍、記憶體用量變多，所以只在開發與測試時使用，但它能把「之後某處莫名其妙當機」變成「在第一次越界的那一行立刻停下來，並告訴你是哪個變數」。第 26 章會詳細講它的原理。

> [!tip]
> 警告不是噪音。2.5 節的 `-Wsizeof-array-argument`、2.17 節表格裡的 `-Wreturn-stack-address`，都是編譯器在「程式還沒跑」之前就指出的真實 bug。在新專案一開始就開 `-Wall -Wextra -Werror`，成本最低；舊專案可以先把警告數量當成指標，逐步降到 0。

## 2.11 Undefined behavior：C 最危險的觀念

2.1 節的 bug 有一個讓人困惑的特徵：同一份程式，換個最佳化等級，症狀就不一樣。根源是 **undefined behavior**（未定義行為，UB）：C 標準對某些操作「不規定會發生什麼事」。不是「結果不確定」，而是**標準完全不再約束這個程式的任何行為**。編譯器可以假設正確的程式永遠不會觸發 UB，並根據這個假設做最佳化。

常見的 UB：

- 陣列越界讀寫、對 `NULL` 或已釋放的指標解參考
- signed 整數溢位（例如 `INT_MAX + 1`）
- shift 的位元數大於等於型別寬度，或為負數（第 3 章）
- 使用未初始化的區域變數
- 修改字串常數
- `printf` 的格式和參數型別不符
- 多個 thread 不加同步地讀寫同一個變數（data race，第 31 章）

看一個具體例子。有人想寫一個函式檢查「`x + 1` 會不會溢位」：

```c
int next_is_bigger(int x) {
    return x + 1 > x;          /* 寫的人想檢查「加 1 會不會溢位」 */
}

int next_is_bigger_u(unsigned x) {
    return x + 1 > x;          /* unsigned 溢位有定義：UINT_MAX + 1 == 0 */
}
```

用 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - ub.c` 產生的組合語言（刪去 directive）：

```asm
next_is_bigger:
	movl	$1, %eax
	retq
next_is_bigger_u:
	xorl	%eax, %eax
	cmpl	$-1, %edi
	setne	%al
	retq
```

`next_is_bigger` 被編譯成「直接回傳 1」：編譯器推理「signed 溢位是 UB，正確的程式不會溢位，所以 `x + 1` 永遠大於 `x`」，整個比較被刪掉了。`next_is_bigger_u` 則真的做了比較（`cmpl $-1, %edi` 檢查 `x` 是不是 `0xFFFFFFFF`），因為 unsigned 溢位有明確定義，結果會繞回 0。把它包成可執行的程式，用不同最佳化等級跑：

```c
#include <limits.h>
#include <stdio.h>

/* 示範 undefined behavior：結果依編譯器與最佳化等級而定 */
__attribute__((noinline)) static int next_is_bigger(int x) {
    return x + 1 > x;           /* x 是 INT_MAX 時，x + 1 是 signed overflow */
}

int main(void) {
    volatile int big = INT_MAX; /* volatile：避免編譯器在編譯期就算好 */
    printf("next_is_bigger(INT_MAX) = %d\n", next_is_bigger(big));
    return 0;
}
```

在 macOS arm64、Apple clang 21 上的實際結果（結果依編譯器而定）：

```text
-O0: next_is_bigger(INT_MAX) = 0
-O1: next_is_bigger(INT_MAX) = 1
-O2: next_is_bigger(INT_MAX) = 1
```

`-O0` 時編譯器老實做加法，結果繞回負數，比較得到 0；`-O1` 以上時比較被刪掉，得到 1。同一行原始碼，兩種答案，兩者都「符合標準」，因為程式觸發了 UB，標準已經不管了。加上 `-fsanitize=undefined` 編譯，UBSan 會在執行時直接指出問題：

```text
ubdemo.c:6:14: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior ubdemo.c:6:14 
next_is_bigger(INT_MAX) = 0
```

```text
 原始碼含 UB
     │
     ├── -O0：編譯器照字面翻譯 ──▶ 行為「看起來合理」（例如繞回）
     │
     └── -O2：編譯器假設 UB 不會發生
              ├─ 刪掉「不可能成立」的檢查
              ├─ 重排、合併記憶體存取
              └─▶ 行為完全不同，或在離 bug 很遠的地方才出事

 正確的處理：消除 UB（改寫程式、用 sanitizer 找出來），
            而不是「把最佳化關掉就好了」
```

這就是「debug build 正常、release build 當機」最常見的原因。第 5 章會介紹正確檢查溢位的方法（例如 `__builtin_add_overflow`），第 11、26 章會處理記憶體類的 UB。

## 2.12 除錯器：gdb 與 lldb

`printf` 除錯在 C 裡很快就不夠用了：程式可能在印出任何東西之前就當掉，或者你根本不知道該印什麼。**除錯器**（debugger）讓你在程式執行到一半時停下來，查看任何變數、記憶體與呼叫堆疊。Linux 上的標準是 **gdb**，macOS 上是 **lldb**，兩者概念相同、指令稍有不同。

用一個縮放尺寸的小程式示範：

```c
#include <stdio.h>

static int scale_dim(int src, int max_side, int longest) {
    int dst = src * max_side / longest;   /* 依比例縮小，至少 1 個像素 */
    return dst > 0 ? dst : 1;
}

int main(void) {
    int w = 4000, h = 3000, max_side = 320;
    int longest = w > h ? w : h;
    int tw = scale_dim(w, max_side, longest);
    int th = scale_dim(h, max_side, longest);
    printf("%dx%d → %dx%d\n", w, h, tw, th);
    return 0;
}
```

先用 `cc -std=c17 -O0 -g -Wall -Wextra -o scale scale.c` 編譯：`-g` 讓除錯器知道變數名稱與行號，`-O0` 讓變數不會被最佳化掉。以下是在 macOS arm64 上實際執行 lldb 的過程（刪去部分原始碼列表）：

```text
(lldb) finish
Return value: (int) $0 = 320
(lldb) next
-> 12  	    int th = scale_dim(h, max_side, longest);
(lldb) p tw
(int) 320
```

逐步解讀：

1. `breakpoint set --name scale_dim` 在函式入口設中斷點，`run` 啟動程式，執行到第 4 行時停下。箭頭 `->` 指的是**下一行要執行的**程式碼，它還沒執行，所以 `frame variable` 看到的 `dst` 是尚未賦值的 0（未初始化的值，可能是任何東西）。
2. `bt`（backtrace）列出**呼叫堆疊**：目前在 `scale_dim`（frame #0），它是被 `main` 的第 11 行呼叫的（frame #1），`main` 又是被載入器的 `start` 呼叫的。程式當機時，第一件事就是看 `bt`，它告訴你「怎麼走到這裡的」。第 9 章會講 stack frame 是什麼，`bt` 又是怎麼算出來的。
3. `p` 可以計算任意運算式。`src * max_side` 是 128 萬，還在 `int` 範圍內；但如果原圖是 10 萬像素寬、`max_side` 是 3 萬，這個乘積就會超過 `INT_MAX`，觸發 2.11 節的 signed overflow。在除錯器裡驗證中間值，常常就能看出這種隱藏的 bug。
4. `finish` 執行到目前函式返回，並顯示回傳值 320；`next` 執行一行（遇到函式呼叫不會跳進去）；`step` 則會跳進去。

接著在第 13 行停下（先 `breakpoint delete 1` 刪掉 `scale_dim` 的中斷點，或多打一次 `continue`），用 `x` 指令直接看記憶體：

```text
(lldb) p &w
(int *) 0x000000016fdfce28
(lldb) x/4xb &w
0x16fdfce28: 0xa0 0x0f 0x00 0x00
(lldb) p sizeof(w)
(unsigned long) 4
```

`x/4xb &w` 的意思是「從 `&w` 開始，以十六進位（x）印 4 個 byte（b）」。4000 的十六進位是 `0x00000FA0`，但記憶體裡的順序是 `a0 0f 00 00`，最低位的 byte 放在最低的位址。這叫 **little endian**（小端序），x86-64 與 ARM64（Linux、macOS 上的實際用法）都是如此。第 3 章會用這個現象解釋 `thumbd` 讀 PNG header 時的 byte order bug。

gdb 與 lldb 的常用指令對照：

| 目的 | gdb | lldb | 說明 |
|---|---|---|---|
| 設中斷點 | `break scale_dim`、`b scale.c:12` | `b scale_dim`、`b scale.c:12` | lldb 也接受 gdb 風格的簡寫 |
| 開始執行 | `run arg1 arg2` | `run arg1 arg2` | |
| 下一行（不進函式） | `next`（`n`） | `next`（`n`） | |
| 下一行（進入函式） | `step`（`s`） | `step`（`s`） | |
| 跑到函式返回 | `finish` | `finish` | |
| 繼續執行 | `continue`（`c`） | `continue`（`c`） | |
| 印變數或運算式 | `print x`（`p x`） | `p x` | |
| 看所有區域變數 | `info locals` | `frame variable` | |
| 呼叫堆疊 | `bt` | `bt` | 當機後第一個要打的指令 |
| 切到某一層 frame | `frame 1` | `frame select 1` | 看呼叫者當時的變數 |
| 看記憶體 | `x/4xb &w` | `x/4xb &w` | 格式：數量、顯示方式（x、d）、單位（b、w、g） |

在 Linux 上，程式當機時可以讓 kernel 留下 **core dump**（當機那一刻的記憶體快照），之後再用 gdb 打開它，就像在當機的瞬間按下暫停（示意輸出，細節依系統設定而定）：

```text
$ ulimit -c unlimited          # 允許產生 core dump（有些系統由 systemd-coredump 接手）
$ ./thumbd_dev
Segmentation fault (core dumped)
$ gdb ./thumbd_dev core
(gdb) bt
#0  0x000055555555a1f3 in resize_row (dst=0x0, src=0x7ffff7a00010, w=320) at resize.c:41
#1  0x000055555555a3c8 in resize (img=0x5555555592a0, tw=320, th=240) at resize.c:77
#2  0x0000555555556b10 in handle_thumb (req=0x7fffffffd9e0) at http.c:212
(gdb) frame 1
(gdb) print img->width

```

只看三行 `bt`，就知道是 `resize_row` 收到了 `dst=0x0`（NULL），而它是在 `resize.c` 第 77 行被呼叫的。在使用 systemd 的發行版上，core dump 通常由 `coredumpctl` 管理，`coredumpctl gdb thumbd` 可以直接打開最近一次的。

## 2.13 objdump：看編譯器實際產生了什麼

除錯器看的是「程式執行時的狀態」，`objdump -d` 看的是「編譯器產生的機器碼」。第 1 章用它看過 `hello.o`。在除錯時它特別有用，因為最佳化過的程式常常和原始碼長得完全不一樣。把 2.12 節的 `scale.c` 用 `-O1` 編成 x86-64 Linux 的目的檔（和第 1 章一樣，先在本機用 `clang -E` 展開標頭檔，再以 `clang -target x86_64-linux-gnu -O1 -c` 編譯），再用 `objdump -d --no-show-raw-insn` 反組譯：

```text
0000000000000000 <main>:
       0:      	pushq	%rax
       1:      	leaq	(%rip), %rdi            # 0x8 <main+0x8>
       8:      	movl	$0xfa0, %esi            # imm = 0xFA0
       d:      	movl	$0xbb8, %edx            # imm = 0xBB8
      12:      	movl	$0x140, %ecx            # imm = 0x140
      17:      	movl	$0xf0, %r8d
      1d:      	xorl	%eax, %eax
      1f:      	callq	0x24 <main+0x24>
      24:      	xorl	%eax, %eax
      26:      	popq	%rcx
      27:      	retq
```

`scale_dim` 整個消失了，連 `main` 裡的變數也都不見了。編譯器在編譯時就把所有結果算好：`0xfa0` = 4000、`0xbb8` = 3000、`0x140` = 320、`0xf0` = 240，直接當成 `printf` 的參數放進 `%esi`、`%edx`、`%ecx`、`%r8d`（第一個參數 `%rdi` 是格式字串的位址）。這說明了兩件事：

1. 為什麼除錯時要用 `-O0` 或 `-Og`：最佳化後，原始碼裡的變數與函式可能根本不存在，除錯器會顯示 `<optimized out>`，或在你意想不到的地方停下。
2. 為什麼 production 的 core dump 有時「對不上原始碼」：你看到的是最佳化後的程式。第 7 到 9 章學會讀組合語言之後，就能直接從 `objdump` 的輸出推回發生了什麼。

常用的 `objdump` 與相關工具：`objdump -d prog` 反組譯程式碼；`objdump -S prog`（需要 `-g`）把原始碼穿插在組合語言之間；`objdump -t` 或 `nm` 列出符號；`objdump -r` 看 relocation。Linux 上還有 `readelf`，第 18 章會用到。

## 2.14 如何讀 man page

**man page**（manual page，手冊頁）是 Unix 系統內建的文件，每個指令、system call 與函式庫函式都有一份。它分成幾個 section，同名的東西可能出現在不同 section：

| section | 內容 | 例子 |
|---|---|---|
| 1 | 使用者指令 | `man 1 ls`、`man 1 kill`（指令） |
| 2 | system call | `man 2 read`、`man 2 kill`（system call） |
| 3 | C 函式庫函式 | `man 3 printf`、`man 3 malloc` |
| 5 | 檔案格式 | `man 5 proc`（`/proc` 的說明） |
| 7 | 概觀與慣例 | `man 7 signal`、`man 7 tcp` |

不指定 section 時，`man kill` 會先給你 section 1 的指令版本；寫程式時要的通常是 `man 2 kill`。本書提到函式時常寫成 `read(2)`、`printf(3)`，括號裡就是 section 編號。

一份 man page 的結構幾乎固定，寫程式時最重要的是這幾段：

```text
 NAME          這個函式是什麼（一行）
 SYNOPSIS      要 include 哪些標頭檔、函式原型    ← 參數型別、要不要連結額外的函式庫
 DESCRIPTION   行為的完整說明                    ← 邊界情況藏在這裡
 RETURN VALUE  成功與失敗時分別回傳什麼          ← 最常被跳過，也最重要
 ERRORS        失敗時 errno 可能是哪些值         ← 決定哪些錯誤可以重試
 NOTES／BUGS   平台差異、歷史包袱、已知問題
 SEE ALSO      相關函式
```

以 `read(2)` 為例，macOS 版的 RETURN VALUES 寫著：

```text
     If successful, the number of bytes actually read is returned.  Upon
     reading end-of-file, zero is returned.  Otherwise, a -1 is returned and
     the global variable errno is set to indicate the error.
```

這三句話包含了第 27 章的全部重點：回傳值是「實際讀到的 byte 數」，可能比你要求的少（short count）；回傳 0 代表檔案結束，不是錯誤；回傳 −1 才是錯誤，這時要看 `errno`。許多新手寫 `read(fd, buf, 4096)` 之後就假設讀到了 4096 個 byte，這正是 `thumbd` 在第 27 章的 bug。讀 man page 的習慣是：**先看 SYNOPSIS 與 RETURN VALUE，再看 ERRORS，最後才是 DESCRIPTION 的細節**。Linux 的 man page 也可以在線上的 man7.org 查到，內容通常比 macOS 的更詳細。

## 2.15 動手做：重現並修好 cache key 的 bug

現在把整個工具箱用在 2.1 節的 bug 上，走一遍「重現、觀察、定位、修正、驗證」的流程。

### 步驟一：最小重現

先把出問題的程式碼抽成一個獨立的小程式，路徑從命令列傳入：

```c
// not-runnable：刻意示範 stack buffer overflow
#include <stdio.h>
#include <string.h>

static void make_key(char *out, const char *path, int w, int h) {
    sprintf(out, "%s_%dx%d", path, w, h);    /* 沒有檢查 out 的大小 */
}

int main(int argc, char **argv) {
    const char *path = argc > 1 ? argv[1] : "cat.jpg";
    char key[16];
    make_key(key, path, 320, 240);
    printf("cache key = %s\n", key);
    return 0;
}
```

在 macOS arm64、Apple clang 21 上，分別用 `-O0` 與 `-O2` 編譯並執行（結果依編譯器與平台而定）：

```text
$ cc -std=c17 -O0 -g -Wall -Wextra -o ck0 cachekey.c
$ ./ck0
cache key = cat.jpg_320x240
$ ./ck0 2024/summer/beach_sunset.jpg; echo "exit=$?"
exit=134
$ cc -std=c17 -O2 -Wall -Wextra -o ck2 cachekey.c
$ ./ck2 2024/summer/beach_sunset.jpg; echo "exit=$?"
exit=133
```

短路徑時一切正常：`cat.jpg_320x240` 剛好 15 個字元，加上 `\0` 剛好塞滿 16 bytes。長路徑時要寫 28 + 8 + 1 = 37 個 byte，超出 21 個。對照 2.9 節的表，134 是 SIGABRT，133 是 SIGTRAP：兩種最佳化等級下，不同的保護機制在不同的時間點抓到了損壞。

用 lldb 停在當機點可以看到：`-O0` 時是 **stack protector**（編譯器在 stack 上放的檢查值，第 11 章）在 `main` 返回前發現檢查值被改寫，呼叫 `__stack_chk_fail` 而 abort。`-O2` 時則是另一道防線：macOS 的 `<stdio.h>` 預設就把 `sprintf` 換成帶大小檢查的 `__sprintf_chk`（`_FORTIFY_SOURCE` 機制），但檢查只在編譯器知道目的地大小時才有作用。`-O0` 時 `make_key` 只拿到一個指標，大小未知，檢查形同虛設；`-O2` 時 `make_key` 被 inline 進 `main`，編譯器看得出 `key` 只有 16 bytes，`__sprintf_chk` 在寫入前就發現放不下而觸發 trap。

至於在沒有這些保護的環境（例如關掉 stack protector 的舊建置），程式甚至可能不當機，而是帶著被踩壞的資料繼續跑。這種「症狀隨環境改變」正是 undefined behavior 的特徵，也是只看症狀很難找到原因的理由。

### 步驟二：用 ASan 定位

用 `-fsanitize=address` 重新編譯，同樣的輸入（macOS arm64 實際輸出，刪去後半段的 shadow memory 說明）：

```text
$ cc -std=c17 -O0 -g -fsanitize=address -fno-omit-frame-pointer -o cka cachekey.c
$ ./cka 2024/summer/beach_sunset.jpg
==95580==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x00016da84f90 at pc 0x000102a62f7c bp 0x00016da848b0 sp 0x00016da84050
WRITE of size 28 at 0x00016da84f90 thread T0
    #0 0x000102a62f78 in memcpy+0x260 (libclang_rt.asan_osx_dynamic.dylib:arm64e+0x8ef78)
    #1 0x000187a5dd34 in __sfvwrite+0x158 (libsystem_c.dylib:arm64e+0x4d34)
    #2 0x000187a5d774 in __vfprintf+0x2d2c (libsystem_c.dylib:arm64e+0x4774)
    #3 0x000187a65754 in vsprintf_l+0xc8 (libsystem_c.dylib:arm64e+0xc754)
    #4 0x0001029f3428 in vsprintf+0x6c (libclang_rt.asan_osx_dynamic.dylib:arm64e+0x1f428)
    #5 0x0001029f3ae8 in sprintf+0x38 (libclang_rt.asan_osx_dynamic.dylib:arm64e+0x1fae8)
    #6 0x000102378aa4 in make_key cachekey.c:6
    #7 0x0001023789a0 in main cachekey.c:12
    #8 0x0001878004e0 in start+0x1b4c (dyld:arm64e+0x204e0)

Address 0x00016da84f90 is located in stack of thread T0 at offset 48 in frame
    #0 0x000102378814 in main cachekey.c:9

  This frame has 1 object(s):
    [32, 48) 'key' (line 11) <== Memory access at offset 48 overflows this variable
```

這份報告要從上往下讀：

1. **第一行告訴你錯誤的種類**：`stack-buffer-overflow`，寫入（`WRITE`）stack 上的緩衝區時越界。
2. **堆疊從 #0 往下找到第一個「你的程式碼」**：#0 到 #5 是 libc 與 ASan 內部的函式，#6 `make_key cachekey.c:6` 是第一個屬於我們的 frame，問題就在這一行的 `sprintf`。
3. **最後一段告訴你被踩的是哪個變數**：`main` 的 frame 裡有一個物件 `key`，佔 frame 的 [32, 48)，也就是 16 bytes。這次 28 bytes 的寫入（把路徑複製進 `key`）從 `key` 的開頭寫起，ASan 報告的位址是其中第一個越界的 byte：offset 48，剛好是 `key` 結尾之後的第一個 byte。

沒有 ASan 時，我們只知道「程式在某處 abort」；有了 ASan，它直接指出檔案、行號與變數名稱。這就是為什麼 2.10 節建議開發與測試時一律開 sanitizer。

### 步驟三：修正與驗證

修法有兩個層次：改用不會越界的 `snprintf`，並且檢查它的回傳值，決定「太長」時該怎麼辦。對 cache key 而言，被截斷的 key 可能讓兩張不同的圖撞在同一個 key 上，所以應該回報錯誤，而不是默默截斷：

```c
#include <stdio.h>
#include <string.h>

/* 成功回傳 0；out 放不下時回傳 -1，而且 out 仍然是合法的字串 */
static int make_key(char *out, size_t cap, const char *path, int w, int h) {
    int n = snprintf(out, cap, "%s_%dx%d", path, w, h);
    if (n < 0 || (size_t)n >= cap)       /* n 是「需要的長度」，不含 '\0' */
        return -1;
    return 0;
}

int main(void) {
    const char *paths[] = {"cat.jpg", "2024/summer/beach_sunset.jpg"};
    char key[16];
    for (size_t i = 0; i < sizeof paths / sizeof paths[0]; i++) {
        if (make_key(key, sizeof key, paths[i], 320, 240) == 0)
            printf("ok    key=\"%s\"\n", key);
        else
            printf("too long（%zu 字元的路徑），截斷成 \"%s\"\n", strlen(paths[i]), key);
    }
    return 0;
}
```

一般編譯與 ASan 編譯的輸出相同（macOS arm64），ASan 沒有回報任何錯誤：

```text
ok    key="cat.jpg_320x240"
too long（28 字元的路徑），截斷成 "2024/summer/bea"
```

注意新介面的變化：`make_key` 多了一個 `cap` 參數，呼叫者用 `sizeof key` 傳入真實大小，這正是 2.5 節「指標加長度」的模式；回傳值讓呼叫者知道失敗，這是 C 的錯誤處理慣例。`thumbd` 最後的正式修法是把 key 改成「路徑的 hash 加尺寸」，長度固定，從根本上避免長度問題，並在測試中加入一個 200 字元的路徑作為 regression test。

## 2.16 在工作上怎麼用

### 拿到一個 C 專案的第一個小時

接手 `thumbd` 這類專案時，小安從老周那裡學到的檢查清單：

1. **看建置方式**：讀 README 與 Makefile（或 CMakeLists.txt），找出編譯選項。有沒有 `-Wall -Wextra`？正式版是 `-O2` 還是 `-O3`？有沒有 `-g`？
2. **建一個除錯版**：`-O0 -g -fsanitize=address,undefined`，把測試全部跑一次。舊專案第一次開 sanitizer 常常會跳出好幾個既有的 bug，記下來，它們就是未來 production 事件的候選人。
3. **把警告當待辦清單**：統計 `-Wall -Wextra` 的警告數量。特別注意 `-Wformat`、`-Wsizeof-array-argument`、`-Wreturn-stack-address`、`-Wsign-compare` 這幾類，它們最常對應真實 bug。
4. **找出所有危險函式**：`grep -nE '\b(gets|strcpy|strcat|sprintf)\(' *.c`，逐一確認目的地大小。
5. **確認 core dump 能拿得到**：production 當機時，有沒有 core dump、有沒有對應版本的 debug symbol？沒有的話，下次當機你只會有一行 `Segmentation fault`。

### production 當機的第一輪判斷

```text
 服務當機（log 或監控看到 exit code / signal）
   │
   ├─ 139 / SIGSEGV ─▶ 有 core dump？
   │                    ├─ 有 → gdb prog core → bt → 看第一個自己的 frame 與參數
   │                    └─ 沒有 → 開啟 core dump，或在測試環境用 ASan 重現
   │
   ├─ 134 / SIGABRT ─▶ 看 stderr：assert 失敗？「stack smashing detected」？
   │                    「free(): invalid pointer」？→ 記憶體損壞，用 ASan 重現
   │
   ├─ 137 / SIGKILL ─▶ 不是 bug 造成的當機：OOM killer 或人為 kill
   │                    → 看 dmesg 與記憶體監控（第 24、26 章）
   │
   └─ 只有特定輸入會出事 ─▶ 從 log 找出觸發的請求，做成最小重現，
                           加進測試當作 regression test
```

## 2.17 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 字串尾巴出現亂碼，或 `strlen` 結果太大 | 字串沒有 `\0` 結尾（例如 `strncpy` 來源太長） | 在除錯器裡用 `x/32xb buf` 看有沒有 `00` | 改用 `snprintf`，或確保手動補上 `\0` |
| 函式裡用 `sizeof` 算陣列長度，結果是 2 或 1 | 陣列傳進函式後退化成指標 | `-Wall` 的 `-Wsizeof-array-argument` 警告 | 把長度當作參數傳入 |
| 函式回傳的字串一開始正常，之後變成亂碼 | 回傳了區域陣列的位址，函式結束後那塊 stack 被重用 | clang 警告 `address of stack memory associated with local variable 'buf' returned` | 由呼叫者提供緩衝區，或用 `malloc` 並說清楚誰負責 `free` |
| debug 版正常，release 版行為不同或當機 | undefined behavior 被最佳化放大 | 用 `-fsanitize=address,undefined` 跑同樣的輸入 | 消除 UB，而不是降低最佳化等級 |
| 修改字串時 segfault | 寫入字串常數（`char *s = "abc"; s[0] = 'A';`） | 除錯器看該位址所在區域是否唯讀 | 改成 `char s[] = "abc";` |
| `printf` 印出奇怪的數字 | 格式與型別不符，例如用 `%d` 印 `size_t`、用 `%d` 印指標 | `-Wall` 的 `-Wformat` 警告 | `size_t` 用 `%zu`、指標用 `%p` 並轉型成 `void *` |
| 除錯器顯示 `<optimized out>`、單步執行跳來跳去 | 用了 `-O2` 編譯 | 看編譯選項 | 除錯時用 `-O0 -g` 或 `-Og -g` |
| 多檔案編譯出現 `redefinition` 或 `multiple definition` | 標頭檔沒有 header guard，或在標頭檔裡放了定義 | 看錯誤指向的標頭檔 | 加 header guard；標頭檔只放宣告，定義放進 `.c` |

## 2.18 動手練習

1. **sizeof 預測**：不執行程式，先寫下 `sizeof(char[10])`、`sizeof(int *)`、`sizeof("thumbd")`、`strlen("thumbd")` 在 LP64 系統上的值，再寫程式驗證。（答案：10、8、7、6。）
2. **指標手算**：`uint32_t px[8]` 的起始位址是 `0x1000`。`&px[3]`、`px + 5`、`(char *)px + 5` 分別是多少？`(char *)(px + 1) - (char *)px` 是多少？（答案：`0x100c`、`0x1014`、`0x1005`、4。驗證方法：印出這些位址，看它們與 `px` 的差距。）
3. **延伸 2.7 節的程式**：替 `struct image` 寫一個 `image_get(const struct image *img, uint32_t x, uint32_t y, uint8_t out[4])`，越界時回傳 −1。用 `-fsanitize=address` 編譯，故意不做越界檢查並傳入 `x = width`，觀察 ASan 的報告是 `heap-buffer-overflow`，和本章的 `stack-buffer-overflow` 有什麼不同。
4. **除錯器練習**：用 `-O0 -g` 編譯 2.12 節的 `scale.c`，在 `scale_dim` 設中斷點，在第二次停下時用 `p src * max_side / longest` 驗證 `th` 會是 240。再用 `-O2 -g` 重新編譯並重複操作，記錄除錯器的行為有什麼不同。
5. **UB 實驗**：寫一個迴圈 `for (int i = 0; i >= 0; i++) count++;`，分別用 `-O0` 與 `-O2` 編譯並執行（可以加一個上限避免跑太久），觀察結果是否不同，再用 `-fsanitize=undefined` 確認 UBSan 的訊息。說明為什麼這是 UB。
6. **讀 man page**：讀 `man 3 snprintf`（或線上的 Linux 版本），找出回傳值的定義，並回答：如果 `cap` 是 0，`snprintf` 會不會寫入任何東西？它的回傳值有什麼用？

## 本章重點整理

- C 的心智模型是「記憶體是一大排有編號的格子」，每個變數佔用連續的幾個 byte，型別決定佔幾格以及如何解讀。
- 型別的大小依平台而定；64-bit Linux 與 macOS 使用 LP64，需要精確位元數時用 `<stdint.h>` 的 `uint32_t` 等型別，大小與索引用 `size_t`。
- 指標是存放位址的變數，`&` 取位址、`*` 解參考；C 一律傳值，想讓函式改到呼叫者的變數就傳指標。
- 指標加 n 會前進 `n × sizeof(元素)` 個 byte，`a[i]` 就是 `*(a + i)`；陣列傳給函式時退化成指標，所以長度必須另外傳。
- C 字串以 `\0` 結尾，`strlen` 不算它而 `sizeof` 算；`sprintf`、`strcpy` 不知道目的地大小，應改用 `snprintf` 並檢查回傳值。
- struct 的大小可能因為 padding 大於欄位總和；透過指標存取欄位用 `->`；每個 `malloc` 都要有對應的 `free`，並明確約定所有權。
- 標頭檔放宣告、`.c` 檔放定義，header guard 防止同一標頭檔被重複展開；`static` 讓名字只在本檔可見。
- shell 的重導向、pipe 與結束狀態是除錯的基本線索；被 signal 終止的程式結束碼是 128 加上 signal 編號，例如 139 是 SIGSEGV、134 是 SIGABRT。
- 一律開 `-Wall -Wextra`；除錯時用 `-O0 -g`，開發與測試時加 `-fsanitize=address,undefined`。
- Undefined behavior 讓標準完全不約束程式的行為，編譯器會假設它不發生而做最佳化，這是「debug 版正常、release 版出事」最常見的原因。
- gdb／lldb 的 `break`、`run`、`next`、`step`、`print`、`x`、`bt` 足以應付大多數除錯；production 當機要靠 core dump 加上 debug symbol。
- `objdump -d` 顯示編譯器實際產生的機器碼，最佳化後的程式可能和原始碼結構完全不同。
- 讀 man page 先看 SYNOPSIS 與 RETURN VALUE，再看 ERRORS；`read` 回傳的是實際讀到的 byte 數，可能少於要求。

## 延伸問答

> [!question]- Q1. `int a[10]; int *p = a;` 之後，`a` 和 `p` 有什麼相同、有什麼不同？
> 相同的是：在大多數運算式裡，`a` 會自動轉成首元素的位址，所以 `a[3]`、`p[3]`、`*(a + 3)`、`*(p + 3)` 都存取同一個元素，`a + 1` 與 `p + 1` 也都前進 4 個 byte。
>
> 不同的是本質：`a` 是 40 個 byte 的陣列物件本身，`p` 是一個 8 個 byte、裡面存著位址的變數。所以 `sizeof a` 是 40、`sizeof p` 是 8；`p` 可以被重新賦值（`p = p + 1`），`a` 不行；`&a` 的型別是「指向 10 個 int 的陣列的指標」，`&p` 則是「指向 `int *` 的指標」。最常在工作上造成問題的就是 `sizeof` 這一點：陣列一旦傳進函式就變成指標，再用 `sizeof` 求長度就錯了。

> [!question]- Q2. 程式找錯：下面的函式有什麼問題？`char *ext_of(const char *path) { char buf[16]; strcpy(buf, strrchr(path, '.') + 1); return buf; }`
> 這個函式至少有三個問題。第一，它回傳了區域陣列 `buf` 的位址。`buf` 放在 `ext_of` 的 stack frame 裡，函式一返回，這塊記憶體就可能被下一次函式呼叫重用，呼叫者拿到的是一個懸空指標（dangling pointer），讀它是 undefined behavior；clang 會以 `-Wreturn-stack-address` 警告。
>
> 第二，`strcpy` 不檢查長度，副檔名超過 15 個字元就會越界。第三，如果路徑裡沒有 `.`，`strrchr` 回傳 `NULL`，`NULL + 1` 再交給 `strcpy` 會當機。修法是讓呼叫者提供緩衝區與大小，例如 `int ext_of(const char *path, char *out, size_t cap)`，先檢查 `strrchr` 的結果，再用 `snprintf` 寫入並檢查回傳值；或者乾脆回傳指向 `path` 內部的指標（`const char *`），完全不複製。

> [!question]- Q3. 為什麼程式在 `-O0` 下正常、在 `-O2` 下就壞掉？是編譯器的 bug 嗎？
> 極少數情況下是編譯器 bug，但絕大多數時候是程式裡有 undefined behavior。C 標準規定，一旦程式觸發 UB，標準對整個程式的行為不再有任何要求。最佳化器會假設正確的程式不會觸發 UB，並據此推理：例如假設 signed 加法不會溢位，就把 `x + 1 > x` 簡化成 1；假設指標解參考之後就不會是 `NULL`，就刪掉後面的 `NULL` 檢查。
>
> 在 `-O0` 下，編譯器幾乎照字面翻譯，UB 的後果常常「剛好看起來合理」；在 `-O2` 下，這些推理被大量應用，後果就顯現出來。正確的做法是用 `-fsanitize=undefined,address` 跑同樣的輸入找出 UB，修掉它；而不是把 production 改成 `-O0`，因為那只是把問題藏起來，換一個編譯器版本它又會出現。

> [!question]- Q4. 標頭檔裡為什麼不應該放全域變數的定義（例如 `int cache_hits = 0;`）？該怎麼寫？
> 標頭檔會被很多 `.c` 檔 include，而 include 只是把文字貼進去。如果標頭檔裡寫 `int cache_hits = 0;`，每個 include 它的 `.c` 都會有一份 `cache_hits` 的定義，連結時 linker 會發現同一個名字被定義了好幾次，報出 `multiple definition of 'cache_hits'`。Header guard 幫不上忙，因為它只防止「同一個 `.c` 裡重複展開」，不能防止「多個 `.c` 各展開一次」。
>
> 正確寫法是在標頭檔放宣告 `extern int cache_hits;`，告訴編譯器「這個變數存在，定義在別處」；然後在恰好一個 `.c` 檔裡放定義 `int cache_hits = 0;`。第 18 章會從 linker 的角度解釋 strong／weak symbol，以及為什麼沒有初始值的 `int cache_hits;` 在舊版編譯器（GCC 10、Clang 11 之前預設 `-fcommon`）下有時不會報錯。

> [!question]- Q5. 你在 production 的 log 看到 `thumbd` 以結束碼 139 結束，接下來你會做什麼？
> 139 是 128 + 11，代表程式被 SIGSEGV 終止，也就是存取了不合法的記憶體位址，常見原因是 `NULL` 指標、use-after-free、越界或 stack overflow。第一步是取得證據：確認那台機器有沒有產生 core dump（可能在目前目錄、`/var/lib/systemd/coredump`，或用 `coredumpctl list` 查詢），以及有沒有和該版本 binary 對應的 debug symbol。
>
> 有 core dump 的話，用 `gdb ./thumbd core` 打開，先 `bt` 看呼叫堆疊，找到第一個屬於 `thumbd` 自己的 frame，用 `frame N` 切過去，`print` 看參數與區域變數，判斷是哪個指標壞了。沒有 core dump 的話，從 log 找出當機前處理的請求，在測試環境用 ASan 編譯的版本重放，通常能直接得到檔案與行號。最後把觸發的輸入加進測試，避免同樣的 bug 再次出現。

> [!question]- Q6. `malloc` 和 `calloc` 差在哪？`calloc(w * h, 4)` 和 `malloc(w * h * 4)` 是一樣的嗎？
> `malloc(n)` 配置 n 個 byte，內容不初始化，可能是任何值；`calloc(count, size)` 配置 count × size 個 byte，並保證全部清成 0。對影像緩衝區這種需要初始值的資料，`calloc` 能避免讀到未初始化的記憶體。
>
> 兩者在大小計算上還有一個重要差別：現代的 libc（glibc、musl、macOS）在 `calloc` 裡都會檢查 count × size 是否溢位，溢位時回傳 `NULL`；而 `malloc(w * h * 4)` 的乘法是你自己算的，如果 `w * h * 4` 溢位了，`malloc` 收到的是一個很小的數字，配置成功，之後寫入完整影像時就是 heap overflow。這正是第 5 章 `thumbd` 遇到的安全漏洞。所以當大小是乘出來的，`calloc` 或先檢查溢位再 `malloc` 都比直接相乘安全。

> [!question]- Q7. 在 lldb 裡用 `x/4xb &w` 看 `int w = 4000`，得到 `a0 0f 00 00`。為什麼順序是反的？這會在什麼時候造成問題？
> 4000 的十六進位是 `0x00000FA0`。x86-64 與 ARM64 都是 little endian：多 byte 的數值在記憶體中，最低位的 byte 放在最低的位址，所以從低位址往高位址讀，看到的是 `a0 0f 00 00`。除錯器的 `x` 指令是逐 byte 印出記憶體，因此看起來「反過來」；如果用 `x/1xw &w` 以 4-byte 為單位印，除錯器會幫你組回 `0x00000fa0`。
>
> 只要程式在單一機器上讀寫自己的變數，byte order 不會造成問題。問題出在跨越邊界時：檔案格式與網路協定規定了固定的 byte order（PNG 與 TCP/IP 都用 big endian），如果程式直接把檔案裡的 4 個 byte 當成 `uint32_t` 讀進來，在 little endian 機器上就會得到完全錯誤的數字。第 3 章 `thumbd` 讀錯 PNG 寬高的 bug 就是這樣發生的。

> [!question]- Q8. 面試題：ASan 怎麼知道程式越界了？它能抓到所有記憶體錯誤嗎？
> ASan 由兩部分組成。編譯時，編譯器在每一次記憶體讀寫之前插入檢查碼，並在每個 stack 陣列、全域變數與 heap 區塊的前後安排「redzone」；執行時，ASan 維護一份 shadow memory，用 1 個 shadow byte 記錄 8 個 byte 的應用程式記憶體是否可存取。每次讀寫前查一下 shadow memory，落在 redzone 或已釋放的區域就立刻停下來，印出錯誤種類、呼叫堆疊與被踩的變數。這也是為什麼本章的報告能精確說出 `key` 在 frame 的 [32, 48)。
>
> 它抓不到所有錯誤。越界的距離太遠、直接跳過 redzone 落到另一個合法物件裡，ASan 可能看不到；沒有用 ASan 編譯的程式碼（例如預先編好的第三方函式庫）裡的錯誤也抓不到；data race、signed overflow、未初始化的讀取分別要靠 TSan、UBSan、MSan。而且它只能抓到「測試時真的執行到」的路徑。所以 sanitizer 是強大的工具，但要搭配足夠的測試輸入，例如用 fuzzing 自動產生大量奇怪的輸入。
