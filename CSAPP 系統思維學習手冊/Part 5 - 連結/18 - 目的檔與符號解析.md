# 第 18 章　從原始碼到執行檔：目的檔與符號解析

> [!abstract] 本章地圖
> **核心問題**：每個 `.c` 檔各自編譯，彼此不知道對方的存在；連結器（linker）怎麼把它們拼成一個可執行檔，又是怎麼決定「這個名字指的是哪一個定義」？
>
> **你會學到**：
> - 說出 compiler driver 背後的前處理、編譯、組譯、連結四個步驟，並用 `-###`、`-save-temps` 親眼看到
> - 分辨 relocatable、executable、shared object 三種目的檔，畫出 ELF relocatable 檔的 section 配置
> - 用 `nm`、`objdump`（Linux 上還有 `readelf`）讀符號表，判斷一個符號是 global、local 還是 undefined
> - 用 strong／weak symbol 的規則預測重複定義會「報錯」還是「悄悄出錯」，並知道 `-fno-common` 的意義
> - 手動模擬連結器處理 static library 的過程，解釋為什麼 `-l` 的順序會讓連結成功或失敗
> - 讀懂 `undefined reference`、`multiple definition` 這兩類最常見的 link error，並有一套檢查流程
>
> **前置知識**：第 1 章（編譯的四個階段概觀）、第 2 章（C 的宣告與定義、標頭檔、`objdump`）、第 7 章（組合語言與 `-S`）
>
> **對應 CS:APP 3e**：第 7 章 7.1–7.6 節

## 18.1 故事：在我的 Mac 上明明可以編譯

小安接到一個新功能：讓 `thumbd` 支援 WebP 格式。團隊的慣例是把影像處理的程式碼包成一個 static library `libthumbcodec.a`，`thumbd` 主程式再連結它。小安在 MacBook 上寫好程式、跑完測試，信心滿滿地送出 pull request。

幾分鐘後 CI 亮紅燈。CI 跑在 Linux 上，錯誤訊息只有短短幾行：

```text
/usr/bin/ld: main.o: in function `handle_request':
main.c:(.text+0x1d4): undefined reference to `webp_decode'
collect2: error: ld returned 1 exit status
```

（示意輸出：GNU ld 的錯誤格式）

小安很困惑：`webp_decode` 明明就寫在 `webp.c` 裡，也確實被包進了 `libthumbcodec.a`，而且同樣的 Makefile 在 Mac 上完全沒問題。老周看了一眼 Makefile，指著其中一行：`cc -o thumbd -L. -lthumbcodec main.o`。「把 `-lthumbcodec` 移到 `main.o` 後面試試。」改完之後，CI 就綠了。

小安追問為什麼順序會有差，老周沒有直接回答，反而丟出另一個問題：「上個月有人在兩個檔案裡都寫了 `int thumb_quality;`，結果縮圖品質偶爾變成 0。編譯器沒有任何警告，連結也成功了。你覺得為什麼？」

這兩件事都發生在**連結**（linking）這個階段。大多數工程師把它當成黑盒子：編譯過了就好，連結失敗就上網查。但連結器其實遵守一套簡單而確定的規則。這一章把黑盒子打開：先看目的檔裡裝了什麼，再看連結器如何把名字（符號）對到定義。第 19 章會接著處理「對到之後，位址怎麼填進去」（relocation）與動態連結。

## 18.2 Compiler driver：一行 `cc` 背後的四個程式

我們平常輸入的 `cc -o thumbd main.c resize.c`，其實不是「一個編譯器」在工作。`cc`（或 `gcc`、`clang`）是一個 **compiler driver**（編譯器驅動程式）：它本身不做翻譯，而是依序呼叫好幾個程式，並把中間檔案在它們之間傳遞。

```text
 main.c ──▶ 前處理器（cpp）──▶ main.i ──▶ 編譯器本體（cc1）──▶ main.s ──▶ 組譯器（as）──▶ main.o ─┐
                                                                                                  │
 resize.c ─▶ 前處理器 ────────▶ resize.i ─▶ 編譯器本體 ─────────▶ resize.s ─▶ 組譯器 ───▶ resize.o ┤
                                                                                                  ▼
                                                     libc 等函式庫 ─────────────────────▶ 連結器（ld）
                                                                                                  │
                                                                                                  ▼
                                                                                    thumbd（可執行檔）
```

每個 `.c` 檔各自走過前三步，互相看不見對方，這叫 **separate compilation**（分別編譯）。只有最後一步的連結器會同時看到所有目的檔。這個設計讓大型專案只需要重新編譯修改過的檔案，代價是：有些問題（例如一個函式到底有沒有被定義）要到連結時才發現。

| 步驟 | 程式 | 輸入 → 輸出 | 做什麼 | 單獨執行這一步 |
|---|---|---|---|---|
| 前處理 | `cpp`（clang 內建） | `.c` → `.i` | 展開 `#include`、`#define`、處理 `#if` | `cc -E main.c -o main.i` |
| 編譯 | `cc1`（clang 用 `clang -cc1`） | `.i` → `.s` | 把 C 翻譯成組合語言，做最佳化 | `cc -S main.c` |
| 組譯 | `as` | `.s` → `.o` | 把組合語言翻譯成機器碼，產生 relocatable 目的檔 | `cc -c main.c` |
| 連結 | `ld` | 多個 `.o`、`.a` → 可執行檔 | 符號解析、relocation，產生 executable | `cc -o thumbd main.o resize.o` |

用 `-###` 可以看到 driver 實際呼叫了哪些程式（只印出、不執行）。在 macOS arm64 上執行，輸出很長，這裡截斷每一行：

```text
$ cc -### -o thumbd main.c resize.c
Apple clang version 21.0.0 (clang-2100.1.1.101)
Target: arm64-apple-darwin25.6.0
 ".../usr/bin/clang" "-cc1" "-triple" "arm64-apple-macosx26.0.0" ...   ← 編譯 main.c
 ".../usr/bin/clang" "-cc1" "-triple" "arm64-apple-macosx26.0.0" ...   ← 編譯 resize.c
 ".../usr/bin/ld" "-demangle" "-lto_library" ...                      ← 連結
```

clang 把前處理、編譯、組譯都整合在 `clang -cc1` 裡，所以只看到兩次 `-cc1` 和一次 `ld`；GCC 則會分別呼叫 `cc1`、`as`、`collect2`（它再呼叫 `ld`）。另一個好用的選項是 `-save-temps`，它會把中間檔案全部留下來：

```text
$ cc -save-temps -c resize.c
$ ls resize.*
resize.bc   resize.c   resize.i   resize.o   resize.s
```

`resize.i` 是前處理後的 C、`resize.s` 是組合語言、`resize.o` 是目的檔（`resize.bc` 是 clang 特有的 LLVM 中間碼）。遇到「巨集展開後到底長什麼樣」或「這個 `#include` 到底引入了哪個版本的標頭檔」這類問題時，直接看 `.i` 檔最快。

## 18.3 目的檔：三種類型與三種格式

**目的檔**（object file）是存放機器碼與資料的檔案。依照用途，它分成三種：

| 類型 | 由誰產生 | 能直接執行嗎 | 位址確定了嗎 | 例子 |
|---|---|---|---|---|
| **relocatable object file**（可重定位目的檔） | 組譯器（`cc -c`） | 不能 | 沒有，每個 section 都從 0 開始 | `main.o`、`resize.o` |
| **executable object file**（可執行目的檔） | 連結器 | 能，直接被載入執行 | 有（或在 PIE 中以載入位址為基準） | `thumbd`、`/bin/ls` |
| **shared object file**（共享目的檔） | 連結器（`-shared`） | 不能單獨執行，在載入或執行時被連結 | 與位置無關的程式碼（第 19 章） | `libjpeg.so`、`libc.so.6` |

relocatable 目的檔是本章的主角。它像一塊還沒拼上的拼圖：程式碼與資料都在，但它不知道自己最後會被放在哪個位址，也不知道它呼叫的外部函式在哪裡，只留下「這裡要填某個符號的位址」的記號，等連結器處理。

不同作業系統用不同的檔案格式包裝目的檔，但概念完全相同：

| 系統 | 格式 | relocatable | executable | shared object | static library |
|---|---|---|---|---|---|
| Linux、BSD | **ELF**（Executable and Linkable Format） | `.o` | 無副檔名 | `.so` | `.a` |
| macOS、iOS | **Mach-O** | `.o` | 無副檔名 | `.dylib` | `.a` |
| Windows | **PE/COFF** | `.obj` | `.exe` | `.dll` | `.lib` |

本書以 Linux 的 ELF 為主。但本機是 macOS，原生產生的是 Mach-O。幸好 clang 是一個跨平台編譯器，可以用 `-target x86_64-linux-gnu -c` 直接產生 x86-64 的 ELF relocatable 目的檔，再用 macOS 內建的 `objdump`（其實是 LLVM 的 `llvm-objdump`，它能讀 ELF）與 `nm` 檢視。**本章所有標註「ELF」的輸出，都是在 macOS arm64 上用這個方法實際產生的**；需要真正的 Linux 連結器（GNU ld）才能得到的輸出，會另外標明為示意輸出。

`file` 指令可以辨認格式：

```text
$ clang -target x86_64-linux-gnu -O0 -c resize.c -o resize.o
$ file resize.o
resize.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped

$ cc -c resize.c -o resize_mac.o        # 本機原生編譯
$ file resize_mac.o thumbd libthumb.dylib
resize_mac.o:   Mach-O 64-bit object arm64
thumbd:         Mach-O 64-bit executable arm64
libthumb.dylib: Mach-O 64-bit dynamically linked shared library arm64
```

`LSB` 表示 little-endian（第 3 章）。這三行分別對應前面表格的三種類型。

## 18.4 ELF relocatable 目的檔的內部

### 範例程式

本章用一個簡化版的 `thumbd` 當例子：`resize.c` 負責縮放，`main.c` 負責主流程與記錄 log。`resize.c` 刻意放了各種「會被放到不同地方」的東西：

```c
int thumb_quality = 85;            /* 有初值的全域變數 */
int resize_calls;                  /* 沒有初值的全域變數 */
static int scratch[256];           /* static：只有本檔看得到 */
const char resize_tag[] = "bilinear";

void log_msg(const char *msg);     /* 宣告：定義在別的檔案 */

static int clamp(int v, int lo, int hi) {
    return v < lo ? lo : v > hi ? hi : v;
}

int resize(int w, int h, int scale) {
    resize_calls++;
    scratch[0] = clamp(w / scale, 1, 4096);
    log_msg(resize_tag);
    return scratch[0] * clamp(h / scale, 1, 4096);
}
```

```c
// not-runnable（需要和 resize.c 一起連結）
int printf(const char *fmt, ...);   /* 宣告即可，定義在 libc */

int resize(int w, int h, int scale);
extern int thumb_quality;
extern int resize_calls;

void log_msg(const char *msg) { printf("[thumbd] %s\n", msg); }

int main(void) {
    int pixels = resize(4000, 3000, 10);
    printf("pixels=%d quality=%d calls=%d\n", pixels, thumb_quality, resize_calls);
    return 0;
}
```

`main.c` 直接寫出 `printf` 的宣告，而不是 `#include <stdio.h>`。原因很實際：macOS 上沒有 Linux 的標頭檔，交叉編譯時找不到 `stdio.h`。但這也正好示範了本章的重點：**編譯器只需要宣告就能編譯一個呼叫**，函式的定義在哪裡，是連結器的事。`#include <stdio.h>` 做的事情，本質上就是把一堆這樣的宣告貼進來。

### ELF 檔的布局

一個 ELF relocatable 目的檔的結構如下：

```text
 檔案開頭（offset 0）
 ┌─────────────────────────┐
 │ ELF header              │ 64 bytes：magic number、32/64 位元、endian、
 │                         │ 檔案類型（REL/EXEC/DYN）、機器類型、section header table 的位置
 ├─────────────────────────┤
 │ .text                   │ 機器碼
 ├─────────────────────────┤
 │ .rodata                 │ 唯讀資料：字串常數、const 陣列、switch 的 jump table
 ├─────────────────────────┤
 │ .data                   │ 有初值（且不是 0）的全域與 static 變數
 ├─────────────────────────┤
 │ .bss                    │ 未初始化或初值為 0 的全域與 static 變數：只記錄大小，不佔檔案空間
 ├─────────────────────────┤
 │ .symtab                 │ 符號表：本檔定義與參照的函式、全域變數
 ├─────────────────────────┤
 │ .rela.text              │ relocation 紀錄：.text 裡哪些位置要在連結時填入位址（第 19 章）
 ├─────────────────────────┤
 │ .debug_*、.line          │ 除錯資訊（用 -g 編譯時才有）
 ├─────────────────────────┤
 │ .strtab                 │ 字串表：符號名稱與 section 名稱的實際字串
 ├─────────────────────────┤
 │ section header table    │ 每個 section 一筆：名稱、類型、在檔案中的 offset、大小
 └─────────────────────────┘
```

讀這張圖要掌握一個原則：**ELF 是一個「目錄 ＋ 內容」的格式**。ELF header 告訴你 section header table 在哪裡；section header table 是目錄，列出每個 section 的名稱、位置與大小；其他部分都是內容。所以任何工具（連結器、`objdump`、除錯器）讀 ELF 的第一步，都是先讀 header、再讀目錄。18.8 節會用 Python 親手做一次。

**`.bss`** 這個奇怪的名字來自早期 IBM 組譯器的指令「block started by symbol」，一個好記的說法是「better save space」：未初始化的變數初值一定是 0，檔案裡不需要存一堆 0，只要記下「需要多少 bytes」，載入時由作業系統配置並清為零。`.data` 則不同，`thumb_quality = 85` 這個 85 必須真的存在檔案裡。

### 用 objdump 看 section

```text
$ objdump -h resize.o          # ELF，clang -target x86_64-linux-gnu -O0 -c 產生

resize.o:	file format elf64-x86-64

Sections:
Idx Name            Size     VMA              Type
  0                 00000000 0000000000000000
  1 .strtab         000000b1 0000000000000000
  2 .text           000000be 0000000000000000 TEXT
  3 .rela.text      00000090 0000000000000000
  4 .data           00000004 0000000000000000 DATA
  5 .rodata         00000009 0000000000000000 DATA
  6 .bss            00000410 0000000000000000 BSS
  7 .comment        00000031 0000000000000000
  8 .note.GNU-stack 00000000 0000000000000000
  9 .eh_frame       00000058 0000000000000000 DATA
 10 .rela.eh_frame  00000030 0000000000000000
 11 .llvm_addrsig   00000005 0000000000000000
 12 .symtab         00000108 0000000000000000
```

逐一對照原始碼，驗證我們對每個 section 的理解：

| section | 大小 | 從哪裡來 | 怎麼算出來 |
|---|---|---|---|
| `.data` | 4 | `thumb_quality = 85` | 一個 `int`，4 bytes |
| `.rodata` | 9 | `resize_tag[] = "bilinear"` | 8 個字元加上 `\0` |
| `.bss` | 0x410 = 1,040 | `resize_calls` 與 `scratch[256]` | 4 bytes，補齊到 16 bytes 對齊，再加 256 × 4 = 1,024 bytes |
| `.text` | 0xbe = 190 | `clamp` 與 `resize` 的機器碼 | `-O0` 沒有最佳化，所以比較長 |
| `.rela.text` | 0x90 = 144 | `.text` 中 6 個要在連結時填入的位址 | 每筆 24 bytes（ELF64 的 `Elf64_Rela`），6 × 24 = 144 |

注意 VMA（virtual memory address）全部是 0：relocatable 目的檔還不知道自己會被放在哪裡，每個 section 都假設從 0 開始。連結器合併所有目的檔之後，才會決定最終位址。

`objdump -s` 可以直接印出 section 的內容，確認 `.data` 與 `.rodata` 裡真的存著那些值：

```text
$ objdump -s -j .data -j .rodata resize.o
Contents of section .data:
 0000 55000000                             U...
Contents of section .rodata:
 0000 62696c69 6e656172 00                 bilinear.
```

`55000000` 是 85（0x55）的 little-endian 表示，`62 69 6c ...` 是 "bilinear" 的 ASCII 碼。至於 `.bss`，它在檔案裡根本沒有內容可以印。

> [!note] Mach-O 的對應名稱
> 在 macOS 上用 `objdump -h` 看原生的目的檔，會看到 `__text`、`__data`、`__const`、`__bss` 這些名字，它們分別屬於 `__TEXT` 與 `__DATA` 兩個 segment。名稱不同，角色與 ELF 的 `.text`、`.data`、`.rodata`、`.bss` 一一對應。

## 18.5 符號與符號表

### 三種符號

連結器眼中的世界是由**符號**（symbol）組成的：每一個函式與全域變數都有一個名字，連結器的工作就是把「用到這個名字的地方」和「定義這個名字的地方」接起來。從某個目的檔 m 的角度看，符號分三種：

| 種類 | 定義在哪 | 誰看得到 | C 原始碼中的樣子 | `resize.c` 中的例子 |
|---|---|---|---|---|
| **global symbol**（全域符號） | 本檔 | 所有目的檔 | 沒有 `static` 的函式與全域變數 | `resize`、`thumb_quality`、`resize_calls`、`resize_tag` |
| **external symbol**（外部符號） | 別的檔案 | 本檔參照它 | 只有宣告、沒有定義的函式與 `extern` 變數 | `log_msg` |
| **local symbol**（區域符號） | 本檔 | 只有本檔 | 加了 `static` 的函式與全域變數、函式內的 `static` 變數 | `clamp`、`scratch` |

這裡有一個常見的混淆：**local symbol 不是 local 變數**。函式裡一般的區域變數（例如 `resize` 的參數 `w`）放在 stack 上或暫存器裡，執行時才存在，連結器完全不知道它們，也不會出現在符號表中。local symbol 指的是加了 `static` 的東西：它們有固定的位址，會出現在符號表裡，只是標記為「不讓別的檔案看到」。

C 的 `static` 在這裡的意義和 Java、C++ class 裡的 `static` 完全不同。對全域變數與函式而言，`static` 的意思是「private to this file」，是 C 唯一的模組化與資訊隱藏機制。

### 讀符號表：objdump -t 與 nm

```text
$ objdump -t resize.o          # ELF

resize.o:	file format elf64-x86-64

SYMBOL TABLE:
0000000000000000 l    df *ABS*	0000000000000000 resize.c
0000000000000000 l    d  .text	0000000000000000 .text
0000000000000080 l     F .text	000000000000003e clamp
0000000000000010 l     O .bss	0000000000000400 scratch
0000000000000000 l    d  .bss	0000000000000000 .bss
0000000000000000 g     F .text	0000000000000079 resize
0000000000000000 g     O .bss	0000000000000004 resize_calls
0000000000000000 g     O .rodata	0000000000000009 resize_tag
0000000000000000         *UND*	0000000000000000 log_msg
0000000000000000 g     O .data	0000000000000004 thumb_quality
```

每一行依序是：值（在 section 內的 offset）、旗標（`l` local、`g` global；`F` 函式、`O` 資料物件、`d` section、`f` 檔名）、所屬 section、大小、名稱。對照原始碼：

- `clamp` 是 `l F .text`：本檔的 static 函式，位於 `.text` 的 offset 0x80，大小 0x3e bytes。
- `scratch` 是 `l O .bss`，大小 0x400 = 1,024 bytes，offset 0x10，正好接在 `resize_calls`（4 bytes，補齊到 16）後面，和 18.4 節算的 `.bss` 大小一致。
- `log_msg` 的 section 是 `*UND*`（undefined）：本檔用到了它，但沒有定義它。這是一個「待連結器解決」的參照。

`nm` 的輸出更精簡，用一個字母表示符號類型：

```text
$ nm resize.o                  # ELF
0000000000000080 t clamp
                 U log_msg
0000000000000000 T resize
0000000000000000 B resize_calls
0000000000000000 R resize_tag
0000000000000010 b scratch
0000000000000000 D thumb_quality

$ nm main.o                    # ELF
0000000000000000 r .L.str
000000000000000d r .L.str.1
0000000000000000 T log_msg
0000000000000030 T main
                 U printf
                 U resize
                 U resize_calls
                 U thumb_quality
```

| 字母 | 意義 | 大寫（global）的例子 | 小寫（local）的例子 |
|---|---|---|---|
| T／t | 在 `.text`（程式碼） | `resize`、`main` | `clamp` |
| D／d | 在 `.data`（有初值的資料） | `thumb_quality` | 有初值的 static 變數 |
| B／b | 在 `.bss`（初值為 0 的資料） | `resize_calls` | `scratch` |
| R／r | 在 `.rodata`（唯讀資料） | `resize_tag` | 編譯器產生的字串常數 `.L.str` |
| U | undefined：本檔參照、別處定義 | `log_msg`、`printf` | — |
| C | common：未初始化、尚未決定放哪（見 18.6 節） | `-fcommon` 時的 `resize_calls` | — |
| W／w | weak：可以被同名的 strong 定義取代（見 18.6 節） | `__attribute__((weak))` 的函式 | — |

把兩個 `nm` 的輸出放在一起看，就能預測連結結果：`main.o` 的四個 `U` 中，`resize`、`resize_calls`、`thumb_quality` 都能在 `resize.o` 找到大寫的定義，`printf` 要從 libc 找；`resize.o` 的 `U log_msg` 則由 `main.o` 的 `T log_msg` 解決。每一個 `U` 都必須恰好被一個定義解決，連結才會成功。這就是**符號解析**（symbol resolution）。

> [!tip] 每一個 link error 都可以先用 nm 檢查
> `nm -A *.o | grep 符號名` 會列出每個檔案中這個符號的狀態。看到全部都是 `U` 卻沒有任何 `T`／`D`／`B`，就是 undefined reference；看到兩個以上的大寫定義，就是 multiple definition。

### 組合語言裡的符號

符號表的資訊來自組合語言的 directive。下面是一個縮短版的 `resize`（`clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - sym.c`，省略部分 directive）：

```c
int thumb_quality = 85;
int resize_calls;
static int scratch[256];
void log_msg(const char *msg);
int resize(int w, int scale) {
    resize_calls++;
    scratch[0] = w / scale;
    log_msg("bilinear");
    return scratch[0];
}
```

```asm
	.text
	.globl	resize
	.type	resize,@function
resize:
	pushq	%rax
	movl	%edi, %eax
	incl	resize_calls(%rip)
	cltd
	idivl	%esi
	movl	%eax, scratch.0(%rip)
	leaq	.L.str(%rip), %rdi
	callq	log_msg@PLT
	movl	scratch.0(%rip), %eax
	popq	%rcx
	retq

	.data
	.globl	thumb_quality
thumb_quality:
	.long	85
	.size	thumb_quality, 4

	.bss
	.globl	resize_calls
resize_calls:
	.long	0
	.size	resize_calls, 4

	.local	scratch.0
	.comm	scratch.0,4,16
	.section	.rodata.str1.1,"aMS",@progbits,1
.L.str:
	.asciz	"bilinear"
```

`.globl` 讓一個標籤成為 global symbol；沒有 `.globl` 的標籤是 local。`.data`、`.bss`、`.section .rodata...` 決定後面的東西放進哪個 section。`log_msg` 從來沒有被定義，組譯器看到它被使用卻找不到定義，就在符號表裡記成 undefined。

這段輸出還有一個有趣的細節：`scratch[256]` 變成了 `scratch.0`，而且只有 4 bytes。因為 `scratch` 是 `static`，編譯器確定沒有別的檔案能存取它，又看到程式只用了 `scratch[0]`，於是大膽地把整個陣列縮成一個 `int`。如果 `scratch` 是 global，編譯器就不敢這樣做，因為別的檔案可能會讀寫其他元素。**`static` 不只是資訊隱藏，也給了最佳化器更大的自由**。

### C++ 的名稱修飾

C 的符號名稱就是函式名稱，所以 C 不能有兩個同名函式。C++ 支援函式重載與 namespace，編譯器會把型別資訊編進符號名稱，叫 **name mangling**（名稱修飾）。用 `clang++ -target x86_64-linux-gnu -c` 編譯一個小檔案：

```text
$ nm r.o                       # ELF
0000000000000000 T _ZN5thumb6resizeEiii
0000000000000030 T resize_c
$ nm -C r.o                    # -C：還原成人看得懂的名字（demangle）
0000000000000000 T thumb::resize(int, int, int)
0000000000000030 T resize_c
```

`_ZN5thumb6resizeEiii` 的意思是「namespace `thumb`（5 個字元）裡的 `resize`（6 個字元），參數是三個 `int`」。`resize_c` 用 `extern "C"` 宣告，保留了 C 的名稱，這是 C 與 C++ 互相呼叫的標準做法。C++ 專案的 link error 常常是因為一邊用 C 的名稱、一邊用修飾過的名稱，兩者永遠對不上。

## 18.6 符號解析：重複定義時，連結器選誰

### 解析的基本規則

連結器處理符號參照的規則很直接：

- **local symbol**：編譯器在編譯時就保證每個檔案內唯一，連結器只需要在同一個檔案內對應。
- **global symbol 的參照**：在所有輸入的目的檔中找定義。找不到 → **undefined reference** 錯誤；找到恰好一個 → 解析成功；找到多個 → 依照下面的 strong／weak 規則決定。

### Strong 與 weak symbol

全域符號依照定義方式分成兩種強度：

- **strong symbol**（強符號）：函式，以及**有初值**的全域變數。例如 `int thumb_quality = 85;`、`int resize(...) {...}`。
- **weak symbol**（弱符號）：用 `__attribute__((weak))` 標記的定義；以及在 `-fcommon` 模式下**沒有初值**的全域變數，例如 `int resize_calls;`（它在 ELF 中是一種特殊的 **COMMON** 符號，`nm` 顯示為 `C`，連結器對待它的方式和 weak 類似）。

Linux 連結器遇到同名的多個定義時，依照三條規則：

```text
規則 1：多個 strong 同名        → 錯誤：multiple definition
規則 2：一個 strong ＋ 多個 weak → 選 strong，其他檔案的參照都指向它
規則 3：多個 weak（common）同名  → 任選一個（common 符號會選大小最大的那個）
```

規則 1 很好理解，也很安全，連結器會直接拒絕。危險的是規則 2 與 3：連結器**不會報錯**，而且它只看名字，**不看型別**。在 C 裡，連結器根本不知道一個符號是 `int` 還是 `double`，它只知道「名字叫 `count` 的東西在這個位址」。

### 實驗：悄悄覆寫隔壁的變數

這正是老周說的那個 bug 的簡化版。兩個檔案都定義了 `count`，一個是有初值的 `int`（strong），另一個是沒有初值的 `double`（在 `-fcommon` 下是 weak）：

```c
// not-runnable（需要和 x2.c 一起連結）
/* x1.c */
#include <stdio.h>
int count = 1;      /* strong：有初值，4 bytes */
int limit = 100;    /* 很可能緊接在 count 後面 */
void reset(void);
int main(void) {
    reset();
    printf("count=%d limit=%d\n", count, limit);
    return 0;
}
```

```c
/* x2.c */
double count;       /* weak（common）：沒有初值，以為自己是 8 bytes 的 double */
void reset(void) { count = 0.0; }
```

在 macOS arm64 上實際編譯、連結、執行（Apple clang 21）：

```text
$ cc -fcommon -c x1.c x2.c && cc -o x x1.o x2.o && ./x
ld: warning: tentative definition of '_count' with size 8 from '/private/tmp/c18/mac/x2.o' is being replaced by real definition of smaller size 4 from '/private/tmp/c18/mac/x1.o'
count=0 limit=0

$ nm x1.o x2.o | grep -E "count|limit"
0000000000000058 D _count
000000000000005c D _limit
0000000000000008 C _count

$ cc -fno-common -c x1.c x2.c && cc -o x x1.o x2.o
duplicate symbol '_count' in:
    /private/tmp/c18/mac/x1.o
    /private/tmp/c18/mac/x2.o
ld: 1 duplicate symbols
clang: error: linker command failed with exit code 1 (use -v to see invocation)
```

逐步解讀：

1. `x1.o` 的 `_count` 是 `D`（strong，在 `.data`，4 bytes），`x2.o` 的 `_count` 是 `C`（common，大小 8）。依規則 2，連結器選了 strong 的那個，`x2.c` 裡對 `count` 的參照全部指向 `x1.c` 的 4-byte `int`。Apple 的連結器在這裡印出一行 warning（**tentative definition**，暫定定義，就是 C 標準對「沒有初值的檔案層級變數定義」的稱呼），但它只是警告，不是錯誤：執行檔照樣產生。不同連結器對這種情況的提示不一樣，有的完全不提示；在動輒上千行的建置輸出裡，一行 warning 也很容易被忽略。
2. 但 `x2.c` 的 `reset` 是用「寫一個 8-byte `double`」的指令寫入的。它寫入的 8 bytes 蓋過了 `count` 本身與緊鄰的 `limit`（`nm` 顯示 `_limit` 在 `_count` 後 4 bytes）。`limit` 從 100 變成 0，而 `x1.c` 裡沒有任何一行程式碼改過它。
3. 用 `-fno-common` 編譯時，沒有初值的 `double count;` 變成一般的 strong 定義（放在 `.bss`），依規則 1 直接報錯。問題在連結時就被抓到，而不是在 production 裡以「某個設定值偶爾變成 0」的形式出現。

這種 bug 極難除錯：症狀出現在 `limit`，原因卻在另一個檔案的 `count`，兩者在原始碼中毫無關聯。

> [!warning] 常見誤解
> 「沒有初值的全域變數一定是 weak。」這取決於編譯器的預設值。GCC 10 與上游 Clang 11 起，預設改成 `-fno-common`（Linux 上的工具鏈都是如此），`int x;` 會被當成 strong 定義放進 `.bss`，重複定義會直接報錯（本章用 `clang -target x86_64-linux-gnu` 產生的 `resize.o` 中，`resize_calls` 就是 `B` 而不是 `C`）。但 Apple clang 在 macOS 上仍然預設 `-fcommon`（前面 `cc -c` 不加任何選項時，`nm` 顯示 `resize_calls` 是 `C`）。舊的專案、舊的編譯器、刻意加了 `-fcommon` 的建置設定，都還會遇到規則 3 的行為。

### 刻意使用 weak：可覆寫的預設實作

weak symbol 也有正當用途：提供一個「預設實作」，讓使用者可以用同名的 strong 定義覆蓋它。例如 `thumbd` 提供一個 hook，預設什麼都不做：

```c
/* hook.c：預設的 hook，什麼都不做。標成 weak，使用者可以提供同名的 strong 版本取代它 */
__attribute__((weak)) void thumb_on_resize(int w, int h) { (void)w; (void)h; }
```

```text
$ nm hook.o                    # ELF
0000000000000000 W thumb_on_resize

# macOS 上實際連結執行：hookmain.c 呼叫 thumb_on_resize(4000, 3000)，
# myhook.c 提供一個會印出訊息的 strong 版本
$ cc -o h1 hookmain.o hook.o && ./h1
done
$ cc -o h2 hookmain.o hook.o myhook.o && ./h2
resize 4000x3000
done
```

沒有提供 `myhook.o` 時，連結器使用 weak 的預設版本；提供之後，依規則 2 選 strong 版本，而且不會報重複定義。libc 與嵌入式系統的啟動程式碼大量使用這個技巧，例如讓使用者可以覆寫中斷處理函式或記憶體配置函式。

## 18.7 Static library 與連結順序

### 為什麼需要 static library

`thumbd` 用到幾十個影像處理函式，libc 也有上千個函式。如果每次連結都要手動列出所有需要的 `.o` 檔，非常麻煩；如果把所有函式都放進一個巨大的 `.o`，每個程式都會包含大量用不到的程式碼。**static library**（靜態函式庫）是折衷：把一群 `.o` 檔打包成一個 **archive**（`.a` 檔），連結器只從裡面**挑出真正需要的成員**複製進執行檔。

```text
$ cc -c resize.c logger.c webp.c
$ ar rcs libthumb.a resize.o logger.o webp.o     # r：加入／取代成員，c：建立，s：建立符號索引
$ ar t libthumb.a
__.SYMDEF SORTED
resize.o
logger.o
webp.o
```

（macOS arm64 上實際執行。`__.SYMDEF SORTED` 是 macOS 版的符號索引；Linux 的 GNU ar 會把索引存成一個沒有名稱的特殊成員，`ar t` 不會列出它。）

接著讓 `main2.c` 只呼叫 `resize`，比較「連結 archive」與「直接連結全部 `.o`」的差別：

```text
$ cc -o thumbd main2.o libthumb.a && nm thumbd | grep -E "resize|log_msg|webp"
0000000100000748 T _log_msg
0000000100000638 T _resize
0000000100008404 S _resize_calls
00000001000007a0 S _resize_tag

$ cc -o thumbd2 main2.o resize.o logger.o webp.o && nm thumbd2 | grep -E "resize|log_msg|webp"
0000000100000748 T _log_msg
0000000100000638 T _resize
0000000100008404 S _resize_calls
00000001000007b8 S _resize_tag
000000010000077c T _webp_decode
```

連結 archive 時，`webp.o` 沒有被選中，因為沒有人參照 `webp_decode`；`logger.o` 被選中，因為 `resize.o` 參照了 `log_msg`。連結器是以**整個成員（`.o` 檔）**為單位挑選的，這也是為什麼 libc 的原始碼習慣把每個函式放在獨立的檔案裡：讓連結器能挑得更精細。

### 連結器怎麼處理 archive：E、U、D 三個集合

Linux 的 GNU ld 依照命令列的順序，**從左到右掃描一次**所有輸入檔，過程中維護三個集合：

- **E**：要合併進執行檔的目的檔。
- **U**：目前還沒解析的參照（undefined）。
- **D**：目前已經有定義的符號。

規則是：

```text
對命令列上的每個輸入檔 f（從左到右）：
  如果 f 是目的檔（.o）：
      無條件加入 E；f 的定義加入 D；f 的未定義參照加入 U；U 中被 f 定義的移除
  如果 f 是 archive（.a）：
      重複：在 f 的成員中找「定義了 U 中某個符號」的成員 m
            找到 → 把 m 當成目的檔處理（加入 E、更新 U 與 D）
            直到 U 不再變化為止
      f 中沒被選中的成員直接丟掉，之後不會再回頭看
掃描結束：U 不是空的 → undefined reference；否則把 E 合併成執行檔
```

**關鍵在最後一句「之後不會再回頭看」**。用這個規則手動模擬 18.1 節的兩種命令列（`main.o` 參照 `webp_decode`，它定義在 `libthumbcodec.a` 的 `webp.o` 中）：

| 步驟 | `cc -o thumbd -L. -lthumbcodec main.o` | `cc -o thumbd main.o -L. -lthumbcodec` |
|---|---|---|
| 1 | 處理 `libthumbcodec.a`：U 是空的，沒有成員被選中，整個 archive 被略過 | 處理 `main.o`：加入 E；U = {`webp_decode`, `printf`, …} |
| 2 | 處理 `main.o`：加入 E；U = {`webp_decode`, `printf`, …} | 處理 `libthumbcodec.a`：`webp.o` 定義了 `webp_decode` → 選中，U 移除它 |
| 3 | 處理 libc（driver 自動加在最後）：解決 `printf` | 處理 libc：解決 `printf` |
| 結果 | U 仍有 `webp_decode` → **undefined reference** | U 為空 → **成功** |

這就是 CI 失敗的原因：library 出現在使用它的目的檔之前，連結器處理 library 時還不知道有人需要 `webp_decode`。由此得到一條實用規則：**library 放在命令列的最後面，而且「使用者」放在「被使用者」前面**。如果 `libthumbcodec.a` 用到 `libpng.a`，就要寫 `main.o -lthumbcodec -lpng`。

如果兩個 library 互相依賴（A 用到 B、B 又用到 A），可以把 A 重複寫一次（`-lA -lB -lA`），或用 GNU ld 的 `-Wl,--start-group -lA -lB -Wl,--end-group`，讓連結器在群組內反覆掃描直到沒有變化。

> [!note] 為什麼在 Mac 上沒事
> 本章在 macOS 上用 `cc -o t2 libthumb.a main2.o`（library 寫在前面）實際測試，連結成功、程式正常執行。Apple 的連結器處理 archive 的方式不依賴命令列順序，所以小安在 Mac 上看不到這個錯誤。LLVM 的 `lld` 在 ELF 模式下也會記住先前看過的 archive，順序錯誤時通常仍能連結成功。但 GNU ld 是 Linux 上最常見的預設連結器，可攜的建置設定應該永遠依照「使用者在前、library 在後」的順序寫，不要依賴特定連結器的寬容。

## 18.8 動手做：親手讀 ELF，並看 section 在記憶體中的位置

### 程式一：用 Python 解析 ELF 的 section 與符號表

`objdump` 與 `readelf` 看起來很神秘，但它們做的事情其實很單純：按照 ELF 規格讀 header、讀 section header table、讀符號表。下面這支 Python 程式用不到 100 行做同樣的事。它會先用 `clang -target x86_64-linux-gnu`（或 Linux 上的 `cc`）編譯 18.4 節的 `resize.c`，再自己解析產生的 ELF 檔，不依賴任何第三方套件：

```python
import shutil
import struct
import subprocess
import sys
import tempfile
from pathlib import Path

SRC = """
int thumb_quality = 85;
int resize_calls;
static int scratch[256];
const char resize_tag[] = "bilinear";
void log_msg(const char *msg);
static int clamp(int v, int lo, int hi) { return v < lo ? lo : v > hi ? hi : v; }
int resize(int w, int h, int s) {
    resize_calls++;
    scratch[0] = clamp(w / s, 1, 4096);
    log_msg(resize_tag);
    return scratch[0] * clamp(h / s, 1, 4096);
}
"""
BIND = {0: "LOCAL", 1: "GLOBAL", 2: "WEAK"}
TYPE = {0: "NOTYPE", 1: "OBJECT", 2: "FUNC", 3: "SECTION", 4: "FILE"}


def build_object(tmp: Path) -> bytes:
    """產生 x86-64 ELF 目的檔：有 clang 就交叉編譯，Linux 上也可以直接用 cc。"""
    (tmp / "resize.c").write_text(SRC)
    cmds = [["clang", "-target", "x86_64-linux-gnu", "-O0", "-c"], ["cc", "-O0", "-c"]]
    for cmd in cmds:
        if shutil.which(cmd[0]):
            out = tmp / "resize.o"
            subprocess.run(cmd + ["resize.c", "-o", str(out)], cwd=tmp, check=True)
            data = out.read_bytes()
            if data[:4] == b"\x7fELF":
                return data
    sys.exit("找不到能產生 ELF 的編譯器")


def cstr(blob: bytes, off: int) -> str:
    return blob[off:blob.index(b"\0", off)].decode()


with tempfile.TemporaryDirectory() as d:
    elf = build_object(Path(d))

# ELF header：e_shoff 在第 0x28 byte，e_shentsize/e_shnum/e_shstrndx 在 0x3A 起
assert elf[4] == 2 and elf[5] == 1, "只處理 64-bit little-endian"
e_type, e_machine = struct.unpack_from("<HH", elf, 0x10)
e_shoff, = struct.unpack_from("<Q", elf, 0x28)
e_shentsize, e_shnum, e_shstrndx = struct.unpack_from("<HHH", elf, 0x3A)
print(f"magic={elf[:4]!r} type={e_type}(1=REL) machine={e_machine}(62=x86-64) sections={e_shnum}")

# section header：每筆 64 bytes
secs = [struct.unpack_from("<IIQQQQIIQQ", elf, e_shoff + i * e_shentsize) for i in range(e_shnum)]
shstr = secs[e_shstrndx]
names = [cstr(elf, shstr[4] + s[0]) for s in secs]
print(f"{'section':<12}{'type':>6}{'file off':>10}{'size':>8}")
for name, s in zip(names, secs):
    if name in (".text", ".data", ".bss", ".rodata", ".symtab", ".rela.text"):
        print(f"{name:<12}{s[1]:>6}{s[4]:>#10x}{s[5]:>#8x}")

# .symtab：每筆 24 bytes（name, info, other, shndx, value, size）
symtab = secs[names.index(".symtab")]
strtab = secs[symtab[6]]                       # sh_link 指向字串表
print(f"\n{'symbol':<14}{'bind':<8}{'type':<8}{'section':<10}{'size':>5}")
for off in range(symtab[4], symtab[4] + symtab[5], 24):
    st_name, st_info, _, st_shndx, _, st_size = struct.unpack_from("<IBBHQQ", elf, off)
    name = cstr(elf, strtab[4] + st_name)
    if not name or TYPE.get(st_info & 0xF) == "FILE":
        continue
    where = "UND" if st_shndx == 0 else names[st_shndx] if st_shndx < e_shnum else "ABS"
    print(f"{name:<14}{BIND[st_info >> 4]:<8}{TYPE[st_info & 0xF]:<8}{where:<10}{st_size:>5}")
```

在 macOS arm64（Python 3、Apple clang 21 交叉編譯成 x86-64 ELF）上執行：

```text
magic=b'\x7fELF' type=1(1=REL) machine=62(62=x86-64) sections=13
section       type  file off    size
.text            1      0x40    0xbe
.rela.text       4     0x2a8    0x90
.data            1     0x100     0x4
.rodata          1     0x104     0x9
.bss             8     0x110   0x410
.symtab          2     0x1a0   0x108

symbol        bind    type    section    size
clamp         LOCAL   FUNC    .text        62
scratch       LOCAL   OBJECT  .bss       1024
resize        GLOBAL  FUNC    .text       121
resize_calls  GLOBAL  OBJECT  .bss          4
resize_tag    GLOBAL  OBJECT  .rodata       9
log_msg       GLOBAL  NOTYPE  UND           0
thumb_quality GLOBAL  OBJECT  .data         4
```

逐步解說：

1. **ELF header**：檔案開頭 4 bytes 是 magic number `\x7fELF`，所有工具都靠它辨認 ELF。`type=1` 是 `ET_REL`（relocatable），可執行檔會是 2（`ET_EXEC`）或 3（`ET_DYN`，PIE 與 shared object 都是這種）。`machine=62` 是 x86-64。
2. **section header table**：位置寫在 header 的 `e_shoff` 欄位，每筆 64 bytes。section 的名稱不直接存在 header 裡，而是存一個「在 `.shstrtab` 字串表中的 offset」，所以程式要先找到字串表才能印出名稱。這種「存 offset、不存字串」的設計讓每一筆 header 都是固定大小，方便直接計算位置。
3. **section 類型**：1 是 `SHT_PROGBITS`（檔案中有實際內容），2 是 `SHT_SYMTAB`，4 是 `SHT_RELA`，8 是 `SHT_NOBITS`。`.bss` 正是 `NOBITS`。
4. **`.bss` 不佔檔案空間的證據**：`.bss` 的 file offset 是 0x110、大小 0x410，如果它真的佔空間，應該延伸到 0x520；但下一個 section `.symtab` 從 0x1a0 就開始了。`.bss` 只是一筆「載入時請配置 0x410 bytes 並清零」的紀錄。
5. **符號表**：每筆 24 bytes。`st_info` 的高 4 位元是 binding（LOCAL、GLOBAL、WEAK），低 4 位元是類型（OBJECT、FUNC…）；`st_shndx` 是所屬 section 的索引，0 代表 `SHN_UNDEF`。結果和 18.5 節的 `objdump -t` 完全一致：`log_msg` 是唯一的 undefined 符號。

這個練習的目的不是要你自己寫 `readelf`，而是讓你相信：**目的檔只是一個有規格的資料結構**，連結器、除錯器、profiler 讀到的資訊，都來自這些表格。

### 程式二：section 在執行時的位置

連結器把所有目的檔的同名 section 合併後，載入器（第 19 章、第 24 章）會把它們放進記憶體。下面的程式印出各種變數與函式在執行時的位址：

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

int thumb_quality = 85;                 /* .data：有初值 */
int resize_calls;                       /* .bss（或 macOS 的 common）：沒有初值 */
static char big_buffer[1 << 20];        /* .bss：1 MiB，但執行檔不會因此變大 */
const char resize_tag[] = "bilinear";   /* .rodata：唯讀常數 */

int resize(int w, int scale) { return w / scale; }   /* .text */

static void show(const char *what, const void *p) {
    printf("%-22s %p\n", what, p);
}

int main(void) {
    int local = 0;                       /* stack，不在任何 section */
    char *heap = malloc(16);             /* heap，不在任何 section */
    show("resize (.text)", (const void *)(uintptr_t)resize);
    show("resize_tag (.rodata)", resize_tag);
    show("thumb_quality (.data)", &thumb_quality);
    show("resize_calls (.bss)", &resize_calls);
    show("big_buffer (.bss)", big_buffer);
    show("heap (malloc)", heap);
    show("local (stack)", &local);
    printf("big_buffer[0] = %d（.bss 保證是 0）\n", big_buffer[0]);
    free(heap);
    return local;
}
```

在 macOS arm64（Apple clang 21，`-O1`）上執行，並用 `size -m` 看執行檔各 section 的大小（ASLR 讓每次執行的位址不同，但相對順序固定）：

```text
resize (.text)         0x1042e45e8
resize_tag (.rodata)   0x1042e4730
thumb_quality (.data)  0x1042ec000
resize_calls (.bss)    0x1043ec004
big_buffer (.bss)      0x1042ec004
heap (malloc)          0x104419ec0
local (stack)          0x16bb1905c
big_buffer[0] = 0（.bss 保證是 0）

$ /bin/ls -l where
-rwxr-xr-x@ 1 chouwleo  wheel  50232 Oct  2 10:26 where
$ size -m where
Segment __TEXT: 16384
	Section __text: 292
	Section __const: 9
	...
Segment __DATA: 1064960
	Section __data: 4
	Section __bss: 1048576 (zerofill)
	Section __common: 4 (zerofill)
```

1. **程式碼與唯讀資料在最低的位址，`.data` 與 `.bss` 緊接在後。** `resize` 與 `resize_tag` 相差不到 0x150，都在 `__TEXT` segment；`thumb_quality` 落在另一個 16 KiB 頁的開頭（`...ec000`，中間還隔著一個存放 `__got` 的 `__DATA_CONST` 頁），因為可寫與唯讀的資料必須放在不同的 page，才能設定不同的權限（第 23 章）。
2. **`big_buffer` 有 1 MiB，執行檔卻只有 50,232 bytes。** `size -m` 顯示 `__bss` 是 1,048,576 bytes 的 zerofill，也就是 18.4 節說的「只記大小、不存內容」。
3. **`resize_calls` 落在 `big_buffer` 之後 1 MiB 的位置。** Apple clang 預設 `-fcommon`，它被放在 `__common` 這個獨立的 zerofill section，排在 `__bss` 後面。在 Linux 的 GCC 10 以上，它會和 `big_buffer` 一起放在 `.bss`。
4. **heap 和 stack 不屬於任何 section。** 它們是執行時才由作業系統建立的區域，目的檔與執行檔裡完全沒有它們的內容。

在 Linux 上可以用 `readelf -S ./where` 看 section、`readelf -l ./where` 看 segment（載入時的單位），對照 `/proc/<PID>/maps`（第 24 章）就能看到每個 section 最後被映射到哪裡。

## 18.9 在工作上怎麼用

### 讀懂 link error

link error 的訊息格式固定，學會拆解就不再可怕。以 GNU ld 為例（示意輸出）：

```text
/usr/bin/ld: main.o: in function `handle_request':        ← 哪個目的檔、哪個函式在參照
main.c:(.text+0x1d4): undefined reference to `webp_decode' ← 在 .text 的哪個位置、找不到哪個符號
collect2: error: ld returned 1 exit status                 ← gcc 告訴你是連結階段失敗

/usr/bin/ld: stats.o:(.data+0x0): multiple definition of `thumb_quality';
resize.o:(.data+0x0): first defined here                   ← 兩個 strong 定義各在哪裡
```

`undefined reference` 的檢查流程：

```text
undefined reference to `X'
  │
  ├─ 1. X 到底有沒有被定義？
  │      nm -A *.o *.a 2>/dev/null | grep ' X$'
  │      ├─ 完全找不到大寫定義 → 忘了寫定義、忘了把那個 .c 加進建置、或拼錯名稱
  │      └─ 找到了 → 繼續
  │
  ├─ 2. 定義的那個檔案有被放進連結命令嗎？
  │      看建置系統實際執行的命令：make V=1、ninja -v、cmake --build . -- VERBOSE=1
  │
  ├─ 3. 順序對嗎？library 是否放在使用者之前？（18.7 節）
  │
  ├─ 4. 名稱真的一樣嗎？
  │      ├─ C++ 與 C 混用：nm 看到 _Z... 與純名稱 → 在標頭檔加 extern "C"
  │      ├─ 定義被寫成 static → nm 顯示小寫 t／d，別的檔案看不到
  │      └─ 定義在 inline 函式或巨集裡、條件編譯（#ifdef）沒有編進去
  │
  └─ 5. 架構與格式一致嗎？
         file *.o *.a：混了 x86-64 與 arm64、或 32 與 64 位元的目的檔，也會找不到符號
```

`multiple definition` 的常見原因幾乎都是「在標頭檔裡**定義**了東西」：標頭檔被多個 `.c` 檔 include，每個檔案都產生一個 strong 定義。正確的做法是標頭檔只放**宣告**，定義只放在一個 `.c` 檔裡：

```c
/* thumb_config.h：只宣告 */
extern int thumb_quality;
int resize(int w, int h, int scale);

/* thumb_config.c：唯一的定義 */
int thumb_quality = 85;
```

如果真的需要在標頭檔中放函式本體（例如很短的工具函式），寫成 `static inline`，讓每個檔案擁有自己的私有副本。

### 工作情境

- **CI 與本機行為不同**：本機是 macOS、CI 是 Linux 時，連結順序、`-fcommon` 預設值、符號是否加底線都可能不同。建置設定要在 Linux 上驗證，或在本機用 Docker 跑相同的工具鏈。
- **第三方函式庫的版本衝突**：兩個 static library 都內嵌了同一個開源元件（例如都帶了一份 zlib），連結時可能出現 multiple definition，也可能因為連結器只取第一個而悄悄混用兩個版本。`nm` 檢查兩個 `.a` 中是否有同名的 `T` 符號。
- **縮小執行檔、隱藏內部符號**：工具函式一律加 `static`；發布 library 時只讓公開 API 是 global（第 19 章會介紹 visibility）。符號越少，連結越快、衝突越少，編譯器也越能最佳化。
- **在 Go、Rust、Python 擴充模組裡也會遇到**：cgo、Rust 的 `extern "C"`、Python 的 C extension 最後都要經過同一個連結器，錯誤訊息的格式和本章完全相同。

## 18.10 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| `undefined reference to 'foo'`，但 `foo` 明明有寫 | 定義所在的 `.o` 或 `.a` 沒有被放進連結命令，或 library 順序在使用者之前 | 看建置系統的實際命令；`nm -A` 找出定義所在檔案 | 把檔案加進連結命令；library 放在最後，依賴者在前 |
| C++ 呼叫 C 函式時 `undefined reference to 'foo(int)'` | C++ 用修飾過的名稱找，C 的目的檔裡只有 `foo` | `nm` 比較兩邊：一邊 `_Z3fooi`、一邊 `foo` | C 的標頭檔用 `extern "C"` 包起來 |
| `multiple definition of 'x'` | 在標頭檔裡定義變數或非 inline 函式，被多個檔案 include | `nm -A *.o \| grep ' x$'` 看到多個大寫定義 | 標頭檔只放 `extern` 宣告，定義放進一個 `.c`；函式用 `static inline` |
| 某個全域變數莫名其妙被改掉 | 多個檔案定義同名全域變數，`-fcommon` 下被合併成同一個位址，型別甚至不同 | `nm` 看到同名的 `C` 與 `D`／`B`；檢查建置選項是否有 `-fcommon` | 用 `-fno-common`；變數改成 `static` 或只定義一次 |
| 改了 static library 的程式碼，執行檔行為卻沒變 | 連結到舊的 `.a`、或同名符號在更前面的檔案中已經被解析 | `-Wl,--trace` 或 map file 看實際用了哪個檔案 | 清除舊的建置產物；檢查 `-L` 搜尋路徑的順序 |
| `file format not recognized` 或 `incompatible` | 混用了不同架構或格式的目的檔（例如 arm64 與 x86-64） | `file *.o *.a` | 用同一個 target 重新編譯所有目的檔 |
| 加了 `static` 之後別的檔案出現 undefined reference | 函式其實是公開 API，被誤加 `static` 變成 local symbol | `nm` 顯示小寫 `t` | 拿掉 `static`，並在標頭檔宣告 |

## 18.11 動手練習

1. 用 `clang -target x86_64-linux-gnu -O0 -c`（Linux 上直接用 `cc -c`）編譯 18.4 節的 `resize.c`，再把 `thumb_quality` 的初值改成 0 重新編譯。用 `objdump -h` 與 `nm` 觀察它從哪個 section 搬到哪個 section，並解釋原因。
2. **手算**：一個檔案有以下全域定義：`int a[100];`、`static double b = 1.5;`、`const int c[10] = {1};`、`char *d = "hi";`，以及一個回傳 `&b` 的函式（讓 `b` 被使用）。在 `-fno-common` 下，`.data`、`.bss`、`.rodata` 各有多少 bytes？`nm` 會分別顯示什麼字母？（答案：`.bss` 400 bytes（`a`，`B`）；`.data` 16 bytes：指標 `d` 8 bytes（`D`）與 `b` 8 bytes（`d`）；`.rodata` 40 bytes（`c`，`R`）；字串 "hi" 的 3 bytes 在 clang 中放在另一個 section `.rodata.str1.1`。`d` 的初值是一個位址，所以還會多一個 `.rela.data`。驗證方法：實際編譯後用 `objdump -h` 與 `nm` 對照。注意：如果 `b` 完全沒被使用，即使 `-O0`，clang 也會直接刪掉它。）
3. **手算**：`main.o` 參照 `f`；`libA.a` 有 `a1.o`（定義 `f`，參照 `g`）；`libB.a` 有 `b1.o`（定義 `g`，參照 `h`）與 `b2.o`（定義 `h`）。用 E、U、D 模擬 GNU ld 處理 `main.o -lA -lB` 與 `main.o -lB -lA`，哪一個會成功？如果 `b2.o` 的 `h` 又參照了 `libA.a` 裡另一個成員的符號呢？（答案：前者成功，後者 `g` 未定義；循環依賴時要寫 `-lA -lB -lA` 或用 `--start-group`。）
4. 重現 18.6 節的 `x1.c`／`x2.c` 實驗，把 `limit` 換成 `char flags[4]`，用 `-fcommon` 連結執行，觀察哪些 byte 被改掉，並用 `nm` 的位址解釋。再加上 `-fno-common`，確認連結器會拒絕。
5. 延伸 18.8 節的 Python 程式：讀取 `.rela.text` section（每筆 24 bytes：`r_offset`、`r_info`、`r_addend`），印出每筆 relocation 的 offset、符號名稱（`r_info >> 32` 是符號表索引）與類型（`r_info & 0xffffffff`），再和 `objdump -r resize.o` 的輸出比對。第 19 章會解釋這些類型的意義。
6. 寫一個 C++ 檔案呼叫 18.4 節的 C 函式 `resize`，先不加 `extern "C"` 編譯連結，閱讀錯誤訊息；再用 `nm` 與 `nm -C` 說明兩邊的符號名稱為什麼對不上，最後修好它。

## 本章重點整理

- `cc` 是 compiler driver，它依序呼叫前處理器、編譯器、組譯器與連結器；`-###` 顯示實際命令，`-save-temps` 留下 `.i`、`.s`、`.o` 等中間檔。
- 每個 `.c` 檔各自編譯成 relocatable 目的檔，彼此看不見；只有連結器會同時看到所有目的檔，所以「有沒有定義」的問題要到連結時才發現。
- 目的檔分成 relocatable（`.o`）、executable 與 shared object（`.so`）三種；Linux 用 ELF、macOS 用 Mach-O、Windows 用 PE/COFF，概念相同。
- ELF 是「header ＋ section header table（目錄）＋ section（內容）」的格式；relocatable 檔中每個 section 的位址都從 0 開始，等連結器決定。
- `.text` 放機器碼、`.rodata` 放唯讀常數、`.data` 放有初值的全域與 static 變數、`.bss` 放初值為 0 的變數且不佔檔案空間、`.symtab` 是符號表、`.rela.text` 記錄待填的位址。
- 符號分成 global（本檔定義、別人可用）、external（別人定義、本檔參照）與 local（`static`，只有本檔可見）；函式內的一般區域變數不是符號。
- `nm` 用字母表示符號類型：大寫是 global、小寫是 local，`U` 是 undefined；每個 `U` 都必須被恰好一個定義解決，連結才會成功。
- C 的 `static` 讓全域變數與函式只在本檔可見，既是 C 的模組化工具，也讓編譯器能做更積極的最佳化。
- C++ 的 name mangling 把型別資訊編進符號名稱，C 與 C++ 互相呼叫要用 `extern "C"`，`nm -C` 可以還原名稱。
- 同名的多個 strong 定義會報 multiple definition；strong 與 weak 並存時選 strong；連結器只看名字不看型別，所以 `-fcommon` 下的同名全域變數可能悄悄覆寫隔壁的資料。
- GCC 10 與 Clang 11 起，Linux 上預設 `-fno-common`，但 Apple clang 在 macOS 上仍預設 `-fcommon`；可攜的程式不要依賴任何一種。
- Static library 是目的檔的 archive，連結器只挑出能解決未定義參照的成員，以整個 `.o` 為單位。
- GNU ld 從左到右掃描一次，處理 archive 時只解決「目前已知」的未定義參照，所以 library 要放在使用它的目的檔之後；循環依賴要重複列出或用 `--start-group`。
- 遇到 link error，先用 `nm -A` 確認符號在哪裡被定義、是不是大寫、名稱是否一致，再檢查連結命令中有沒有那個檔案、順序是否正確。

## 延伸問答

> [!question]- Q1. 為什麼「函式忘了定義」這種錯誤，編譯時不會報錯，要到連結時才發現？
> 因為 C 採用分別編譯：每個 `.c` 檔獨立被編譯成目的檔，編譯器只看得到這一個檔案（以及它 include 的標頭檔）。只要有函式的宣告，編譯器就知道參數與回傳型別，能產生正確的呼叫指令；至於函式本體在哪裡，它無從得知，也不需要知道，只在符號表中記一筆 undefined，並在呼叫指令裡留一個待填的位址。
>
> 只有連結器會同時看到所有目的檔與函式庫，才能判斷每個 undefined 符號是否真的有人定義。這個設計的好處是大型專案可以只重新編譯修改過的檔案，代價就是這類錯誤要等到最後一步才會出現。C99 以後，呼叫一個連宣告都沒有的函式在編譯時就會被警告或報錯，但「有宣告、沒定義」仍然只能靠連結器發現。

> [!question]- Q2. `.data` 與 `.bss` 都放全域變數，為什麼要分成兩個 section？
> 差別在於初值是否需要存在檔案裡。`.data` 放有非零初值的變數，例如 `int thumb_quality = 85;`，這個 85 必須真的寫在目的檔與執行檔中，載入時才能複製到記憶體。`.bss` 放初值為 0 或沒有初值的變數，C 標準保證它們從 0 開始，所以檔案只要記錄「需要多少 bytes」，載入時由作業系統配置並清零即可。
>
> 18.8 節的實驗中，一個 1 MiB 的 `static char big_buffer[1 << 20];` 讓 `__bss` 變成 1,048,576 bytes，執行檔卻只有約 50 KB；Python 解析 ELF 時也看到 `.bss` 的大小有 0x410，卻完全不佔檔案空間。如果把它們都放在 `.data`，每個大型的零初始化陣列都會讓執行檔膨脹，也會拖慢載入。

> [!question]- Q3. 手算題：一個目的檔有 `static int counter;`、`int total = 0;`、`extern int limit;`、`static void helper(void) {}`、`void api(void) { helper(); counter += limit; }`。在 `-fno-common` 下，`nm` 會分別顯示什麼？
> `counter` 是 static 且沒有初值，放在 `.bss`、local，顯示 `b`。`total` 雖然有寫初值，但初值是 0，編譯器通常把它放進 `.bss`，global，顯示 `B`。`limit` 只有 `extern` 宣告，是本檔參照、別處定義的符號，顯示 `U`。`helper` 是 static 函式，顯示 `t`；`api` 是一般函式，顯示 `T`。
>
> 有兩個細節要注意。第一，`helper` 很小，開最佳化時可能被內聯並完全消失，`nm` 就看不到它，這和 18.5 節 `scratch` 被縮小的道理相同。第二，`total = 0` 放進 `.bss` 是常見的編譯器行為而非語言規定，所以應該用 `nm` 實際確認，而不是死背。

> [!question]- Q4. 你的服務在本機 macOS 可以建置，但 CI（Linux）出現 `undefined reference`，而且只有在連結 static library 時發生。你會怎麼排查？
> 第一個懷疑對象是連結順序。GNU ld 由左到右掃描一次，處理 archive 時只會挑出能解決「目前已知」未定義參照的成員，處理完就不再回頭；Apple 的連結器沒有這個限制，所以 library 寫在目的檔之前時，Mac 上能過、Linux 上會失敗。先看 CI 實際執行的連結命令（`make V=1`、`ninja -v`），確認 `-l` 是否出現在使用它的 `.o` 之後，以及 library 之間的依賴順序。
>
> 如果順序正確，再用 `nm -A libx.a | grep 符號` 確認 Linux 版的 archive 裡真的有那個符號的大寫定義，排除條件編譯（`#ifdef __linux__`）、C 與 C++ 名稱修飾不一致、或 archive 是為別的架構建置的（`file` 檢查）等可能。循環依賴的 library 要用 `-Wl,--start-group ... -Wl,--end-group`。

> [!question]- Q5. 兩個檔案都寫了 `int buffer_size;`，程式能編譯連結嗎？會有什麼風險？
> 取決於編譯器的 common 設定。在 `-fcommon` 下（舊版 GCC、Apple clang 在 macOS 上的預設），兩個未初始化的定義都是 COMMON 符號，連結器會把它們合併成同一個變數，不報任何錯誤；在 `-fno-common` 下（GCC 10、Clang 11 起在 Linux 上的預設），兩者都是放在 `.bss` 的 strong 定義，連結器會報 multiple definition。
>
> `-fcommon` 的風險是：如果兩個檔案原本以為各自擁有一個私有變數，現在它們其實共用同一個；如果兩邊的型別不同（例如一邊是 `int`、一邊是 `double`），寫入時還會覆蓋相鄰的變數，18.6 節的實驗中 `limit` 就被這樣改成了 0。正確做法是只在一個 `.c` 檔定義，其他地方用 `extern` 宣告；如果是各自私有的變數，就加 `static`。建置時加上 `-fno-common` 能把這類問題提前到連結時抓到。

> [!question]- Q6. `static` 加在全域變數、函式、函式內區域變數上，意義有什麼不同？
> 加在全域變數與函式上時，`static` 控制的是**連結的可見範圍**（linkage）：符號變成 local，只有同一個檔案能用，別的檔案即使宣告了同名的 `extern` 也找不到它，`nm` 顯示小寫字母。這是 C 用來隱藏模組內部實作的主要方式，也能避免不同檔案之間的名稱衝突。
>
> 加在函式內的區域變數上時，`static` 控制的是**儲存期間**（storage duration）：變數不再放在 stack 上，而是放在 `.data` 或 `.bss`，在整個程式執行期間只有一份，函式返回後值仍然保留。它同樣會成為一個 local symbol，編譯器會修改它的名稱，避免和其他函式中同名的 static 變數衝突：例如函式 `tick` 裡的 `static int count;`，clang 產生的符號是 `tick.count`（`nm` 顯示 `b`），GCC 則會產生 `count.0` 這類加了編號的名稱。兩種用法共用一個關鍵字，但回答的是不同的問題。

> [!question]- Q7. 程式找錯：下面的標頭檔被三個 `.c` 檔 include，連結時出現 `multiple definition of 'default_quality'`。為什麼？怎麼修？`/* config.h */ int default_quality = 85; int get_quality(void) { return default_quality; }`
> `#include` 只是把標頭檔的文字貼進每個 `.c` 檔。三個 `.c` 檔各自編譯後，每個目的檔都有一份 `default_quality`（有初值，strong，在 `.data`）與一份 `get_quality`（函式，strong，在 `.text`）。連結器看到三個同名的 strong 定義，依規則 1 報 multiple definition。header guard（`#ifndef CONFIG_H`）也救不了，因為它只防止同一個 `.c` 檔重複 include，不能阻止不同 `.c` 檔各自 include 一次。
>
> 修法是把宣告與定義分開：`config.h` 只寫 `extern int default_quality;` 與 `int get_quality(void);`，在 `config.c` 裡寫唯一的定義。如果 `get_quality` 很短、希望被內聯，可以在標頭檔寫成 `static inline int get_quality(void) {...}`，讓每個檔案擁有自己的 local 副本，不會產生 global 符號衝突。

> [!question]- Q8. 面試題：解釋 static library 與「直接連結所有 .o 檔」的差別，以及為什麼 libc 習慣把每個函式放在獨立的原始檔裡。
> 直接把 `.o` 檔放在連結命令上時，連結器會無條件把每一個檔案都合併進執行檔，不管裡面的函式有沒有被用到。static library 則是一群 `.o` 檔的 archive，連結器只挑出能解決目前未定義符號的成員，其餘的完全不會進入執行檔。18.7 節的實驗中，連結 archive 時沒被用到的 `webp_decode` 不在執行檔裡，直接連結全部 `.o` 時它就在。
>
> 連結器挑選的單位是整個成員，不是單一函式：只要成員裡有一個符號被需要，整個 `.o` 都會被拉進來。如果 libc 把 `printf`、`scanf`、`qsort` 放在同一個 `.o`，任何只用 `printf` 的程式都會帶上其他函式。把每個函式放在獨立的檔案，讓連結器能挑得最精細，執行檔也最小。現代工具鏈也能用 `-ffunction-sections` 加上連結器的 `--gc-sections`，讓每個函式各自成為一個 section，在 section 層級做到類似的效果。
