# 第 14 章　程式效能最佳化：從編譯器限制到指令級平行

> [!abstract] 本章地圖
> **核心問題**：同一個 O(n) 的迴圈，為什麼可以有十倍、甚至幾十倍的速度差？要怎麼有系統地找出差距在哪裡，並在不犧牲正確性的前提下把它拿回來？
>
> **你會學到**：
> - 用 CPE（每元素 cycle 數）與可信的 benchmark 量測迴圈效能，避開最常見的量測陷阱
> - 說出編譯器為什麼不敢做某些最佳化（memory aliasing、函式副作用），以及你可以怎麼幫它
> - 畫出迴圈的 data-flow 圖，找出關鍵路徑，分辨 latency bound 與 throughput bound
> - 用 loop unrolling、多個累加器、reassociation 與 SIMD 讓迴圈接近硬體極限，並知道浮點數的代價
> - 判斷什麼時候該寫 branchless 程式碼，用 profiler 找熱點，並用 Amdahl's law 估算整體效益
>
> **前置知識**：第 8 章（組合語言與 conditional move）、第 13 章（pipeline、forwarding、分支預測、亂序執行）
>
> **對應 CS:APP 3e**：第 5 章 5.1–5.14 節

## 14.1 故事：縮圖服務的 CPU 帳單

月底，產品經理 Lisa 帶著雲端帳單來找小安：`thumbd` 的機器數量半年內翻了一倍，但流量只成長三成。SRE 阿哲補充：「尖峰時段 CPU 使用率長期 80% 以上，我們只能一直加機器。」

小安用 `perf` 對 production 的一台機器取樣了十分鐘，報告的前幾名是：JPEG 解碼 40%、`shrink_half`（把原圖縮成一半）和它呼叫的 `get_px`、`set_px` 加起來 35%、JPEG 編碼 17%，其他 8%。縮圖函式是早期為了「安全」而寫的：每讀一個像素都呼叫 `get_px`，裡面檢查座標有沒有越界。小安量了一下，縮一張 1200 萬像素的照片要 11.7 ms。

小安的第一個念頭是「改用 SIMD 組合語言重寫」。老周搖頭：「先別碰組合語言。你現在的程式連編譯器都幫不上忙，SIMD 是最後一步。我們照順序來：先量清楚，再把擋住編譯器的東西拿掉，再讓 CPU 的平行度發揮出來，最後才是 SIMD。每一步都要有數字。」

兩天後，同一張照片的縮圖時間降到 0.15 ms，快了將近 80 倍，輸出的每個像素都和原本一模一樣。但小安很快又發現一件令人沮喪的事：整個請求的 CPU 時間只少了大約三分之一。為什麼一個函式快了 80 倍，整體卻只快了 1.5 倍？這一章會把這兩天做的每一步拆開來看，也會用 Amdahl's law 解釋那個令人沮喪的結果。

## 14.2 先量測：CPE 與可信的 benchmark

最佳化的第一條規則是：**沒有量測，就沒有最佳化**。「感覺會快」的改動常常沒效，有時甚至更慢。而要量測一個迴圈，需要一個不受陣列長度影響的指標。

### CPE：每處理一個元素要幾個 cycle

CS:APP 用 **CPE**（cycles per element，每元素 cycle 數）描述迴圈的效能。一個處理 n 個元素的迴圈，總時間通常可以寫成：

```text
T(n) = a + b × n
       │    └─ b：每多一個元素要多花的時間，就是 CPE
       └─ a：固定開銷（函式呼叫、迴圈前的準備、最後的收尾）
```

為什麼用 CPE 而不是「每次迭代幾個 cycle」？因為後面會看到，一次迭代可能處理 1、2、4 或 8 個元素（loop unrolling），只有「每個元素」才能公平比較。為什麼用 cycle 而不是 ns？因為 cycle 數反映的是程式和處理器結構的關係，不受時脈高低影響；同一段程式在 3 GHz 與 4.5 GHz 的同一代 CPU 上，CPE 大致相同。

**手算例子**：量到一個迴圈在 n = 100 時花 560 cycles，n = 1,000 時花 3,260 cycles。

```text
b = (3260 − 560) ÷ (1000 − 100) = 2700 ÷ 900 = 3.0 cycles/元素
a = 560 − 3.0 × 100 = 260 cycles
```

所以 CPE 是 3.0，固定開銷約 260 cycles。n 很小時，固定開銷佔大部分時間；n 很大時，CPE 決定一切。這也是為什麼只量一個 n 的 benchmark 容易誤導：n = 100 時兩個版本的差異可能被 260 cycles 的固定開銷蓋過。

在 macOS 上，一般程式不容易直接讀到 cycle 計數器，本章的實驗改用 `clock_gettime` 量 ns，再換算：

```text
CPE ≈ (ns／元素) × 時脈（GHz）
```

本章的實驗機器是 Apple M4 Pro。Apple 沒有正式公布時脈，第三方量測的效能核心最高時脈約 4.5 GHz，所以本章的 ns 換算成 cycle 時只當作估計值。比較同一台機器上不同版本的 ns，結論完全一樣。

這也是 ns 不如 cycle 的地方：時脈一變，ns 就跟著變。本章的數字都是接上電源時量的；改用電池、開著低耗電模式重跑時，所有版本的 ns 都變成約 2.1–2.3 倍，但版本之間的倍數幾乎不變。換算回 cycle，CPE 是同一個值，只是時脈降到約一半。

### 可信的 benchmark

量測本身也會出錯。下面這張表是寫 microbenchmark 時最常踩到的坑：

| 陷阱 | 後果 | 本章程式的對策 |
|---|---|---|
| 編譯器把沒用到的計算整個刪掉 | 量到 0 ns，以為快得不可思議 | 把結果寫到記憶體並印出來 |
| 第一次執行包含 page fault、cache 冷啟動、CPU 升頻 | 第一個被量的版本吃虧 | 先暖機，每個版本跑多次取最快的一次 |
| 只跑一次 | 被系統中斷、其他程式干擾 | 重複多次，觀察變異；差異小於 10% 不下結論 |
| 測試資料太規律 | 分支預測永遠猜對（第 13 章） | 用和 production 一樣的資料分布 |
| 沒記錄編譯選項與機器 | 數字無法重現、無法比較 | 每個數字都附上機器、編譯器、選項 |
| 用 debug 版本量 | `-O0` 的瓶頸和正式版本完全不同 | 用正式部署的最佳化等級量 |

「取最快的一次」適合 microbenchmark，因為我們想知道程式本身的速度，干擾只會讓時間變長。量測整個服務的延遲時則相反，要看中位數與 p99，因為使用者感受到的正是那些被干擾的請求。

## 14.3 編譯器能做什麼、不能做什麼

現代編譯器非常聰明：`-O1` 就會把變數放進暫存器、刪掉沒用的計算、把簡單的不變量移出迴圈；`-O2` 更積極地 inline 小函式，並自動向量化簡單的迴圈（clang 早就在 `-O2` 開啟，GCC 從 12 版起才在 `-O2` 開啟較保守的版本）；`-O3` 再更積極地展開與向量化。很多「手動最佳化技巧」編譯器早就會了。

但編譯器有一條絕對不能違反的規則：**最佳化後的程式，對所有合法的輸入，都必須和原本的程式產生相同的結果**。只要有一種可能的輸入會讓最佳化改變結果，編譯器就不能做，即使那種輸入在你的程式裡永遠不會出現。這種擋住最佳化的因素叫 **optimization blocker**（最佳化障礙）。最常見的有兩種。

### 障礙一：memory aliasing

**Memory aliasing**（記憶體別名）指兩個指標可能指向同一塊記憶體。看 `thumbd` 調整亮度的函式：

```c
/* 把一整列像素乘上增益。gain 是從設定檔讀進來的 */
void scale_row(float *row, const float *gain, long n) {
    for (long i = 0; i < n; i++)
        row[i] = row[i] * *gain;
}
```

你知道 `gain` 指向設定結構裡的一個欄位，和 `row` 毫無關係。但編譯器不知道。從 C 的規則看，呼叫者完全可以寫 `scale_row(buf, &buf[3], n)`，讓 `gain` 指向 `row` 的第 3 個元素。這時迴圈跑到 `i = 3` 會修改 `*gain`，之後的元素要乘上**新的**增益。為了在這種情況下也正確，編譯器必須在每一圈都重新從記憶體讀 `*gain`。

用 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - alias.c` 產生組合語言（刪去 directive），可以看到差別：

```asm
scale_row:
	testq	%rdx, %rdx
	jle	.LBB0_3
	xorl	%eax, %eax
.LBB0_2:
	movss	(%rdi,%rax,4), %xmm0
	mulss	(%rsi), %xmm0
	movss	%xmm0, (%rdi,%rax,4)
	incq	%rax
	cmpq	%rax, %rdx
	jne	.LBB0_2
.LBB0_3:
	retq
scale_row_local:
	testq	%rdx, %rdx
	jle	.LBB1_3
	movss	(%rsi), %xmm0
	xorl	%eax, %eax
.LBB1_2:
	movss	(%rdi,%rax,4), %xmm1
	mulss	%xmm0, %xmm1
	movss	%xmm1, (%rdi,%rax,4)
	incq	%rax
	cmpq	%rax, %rdx
	jne	.LBB1_2
.LBB1_3:
	retq
```

`scale_row` 的迴圈裡，`mulss (%rsi), %xmm0` 每一圈都從 `gain` 指向的位址讀一次。`scale_row_local` 是把 `float g = *gain;` 先複製到區域變數的版本：`movss (%rsi), %xmm0` 被移到迴圈外，只讀一次。區域變數的位址從來沒有被取過，編譯器確定沒有任何指標能修改它，所以敢把它放在暫存器裡。

在 `-O3` 下，clang 對 `scale_row` 會產生兩份程式碼，在執行時先檢查兩塊記憶體是否重疊，不重疊才走向量化的快速版本。這叫 **runtime alias check**（執行期別名檢查），能挽回大部分效能，但多了檢查與程式碼大小，而且不是每種迴圈都做得到。

你可以用兩種方法幫編譯器：

| 方法 | 寫法 | 代價與風險 |
|---|---|---|
| 複製到區域變數 | `float g = *gain;` | 幾乎沒有；語意也更清楚：「迴圈裡增益不變」 |
| `restrict` 關鍵字 | `void scale_row(float *restrict row, const float *restrict gain, long n)` | 這是你對編譯器的**承諾**：兩者不重疊。違反承諾是 undefined behavior，結果可能錯得莫名其妙 |

> [!warning] 常見誤解
> 「`const float *gain` 已經說了不會改，編譯器應該知道。」`const` 只表示「不能透過**這個**指標修改」，不表示那塊記憶體不會透過別的指標（例如 `row`）被修改。`const` 不能解決 aliasing。另外，`char`、`unsigned char`（也就是 `uint8_t`）的指標在 C 的規則裡可以指向任何型別的物件，所以寫入 `uint8_t *` 時，編譯器必須假設它可能改到任何東西。影像處理大量使用 `uint8_t`，這一點特別值得注意。

### 障礙二：函式呼叫的副作用

第二種障礙是函式呼叫。看這個迴圈：

```c
for (long i = 0; i < vec_length(v); i++)
    total += v->data[i];
```

`vec_length(v)` 每一圈都回傳同樣的值，為什麼編譯器不把它移到迴圈外？因為如果它定義在另一個 `.c` 檔，編譯器看不到它的內容，它可能修改全域變數、印 log、改變 `v->len`，也就是有 **side effect**（副作用）。編譯器必須假設最壞情況，老老實實呼叫 n 次。

即使函式就在同一個檔案裡，編譯器也要先能證明它沒有副作用、或把它 inline 進來，才能移動它。實驗中有一個有趣的現象：14.12 節的 `v1` 版本把兩個存取函式標記為 `noinline`，在 `-O1` 下兩個呼叫每圈都會發生；到了 `-O3`，clang 分析出 `vec_length` 只是讀取 `v->len`，把它的結果移出迴圈（本機 arm64 的組合語言裡，迴圈中只剩 `get_elem` 的呼叫），所以 `v1` 在 `-O3` 下快了不少。`get_elem` 透過指標寫入結果，編譯器無法移除這個呼叫。

函式呼叫除了阻擋最佳化，本身也有成本：參數放進暫存器、`call` 與 `ret`、callee 保存暫存器（第 9 章）。對每個像素呼叫一次、每次只做一個比較加一次讀取的函式來說，呼叫成本可能比真正的工作還多好幾倍。

## 14.4 基本功：移出不變量、減少呼叫、減少記憶體存取

在動到任何「進階技巧」之前，有三件事幾乎總是值得做，而且不會讓程式變難讀。

### Code motion：把不變的計算移出迴圈

**Code motion**（程式碼移動）是把每圈結果都一樣的計算移到迴圈外，只算一次。最惡名昭彰的例子是在迴圈條件裡呼叫 `strlen`。`thumbd` 有一個把檔名中的空白換成底線的函式：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

/* 把字串裡的空白換成底線。慢版：每一圈都在迴圈條件裡呼叫 strlen */
static void underscore_slow(char *s) {
    for (size_t i = 0; i < strlen(s); i++)
        if (s[i] == ' ') s[i] = '_';
}

/* 快版：長度只算一次（code motion） */
static void underscore_fast(char *s) {
    size_t n = strlen(s);
    for (size_t i = 0; i < n; i++)
        if (s[i] == ' ') s[i] = '_';
}

static double ms_of(void (*fn)(char *), size_t n) {
    char *s = malloc(n + 1);
    for (size_t i = 0; i < n; i++) s[i] = (i % 8 == 7) ? ' ' : 'a';
    s[n] = '\0';
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    fn(s);
    clock_gettime(CLOCK_MONOTONIC, &t1);
    free(s);
    return (t1.tv_sec - t0.tv_sec) * 1e3 + (t1.tv_nsec - t0.tv_nsec) / 1e6;
}

int main(void) {
    printf("%10s %12s %12s\n", "長度", "slow (ms)", "fast (ms)");
    for (size_t n = 10000; n <= 160000; n *= 2)
        printf("%10zu %12.3f %12.3f\n", n, ms_of(underscore_slow, n), ms_of(underscore_fast, n));
    return 0;
}
```

在 macOS arm64（Apple M4 Pro，Apple clang 21，`cc -std=c17 -O1`）上執行：

```text
    長度    slow (ms)    fast (ms)
     10000        1.730        0.003
     20000        6.699        0.006
     40000       26.644        0.011
     80000      106.967        0.025
    160000      423.086        0.043
```

長度每加倍，慢版的時間就變成大約 4 倍，快版只變成 2 倍。原因是 `strlen` 每次都要從頭掃到 `'\0'`，長度 n 的字串在迴圈裡被掃 n 次，總共約 n²／2 個 byte。手算 n = 160,000：n²／2 = 1.28 × 10¹⁰ 個 byte，在 0.42 秒內掃完，相當於每秒約 30 GB，這已經是 `strlen` 用 SIMD 掃記憶體的速度了，問題在於做了太多次。

編譯器為什麼不幫你移？因為迴圈本身在修改 `s`，如果把某個字元改成 `'\0'`，長度就會變。編譯器無法證明迴圈不會寫入 `'\0'`（這裡寫入的是 `'_'`，聰明的編譯器理論上可以推論，但實際上通常不做）。這種 bug 平常完全隱形：檔名只有幾十個字元時，n² 也只是幾千。直到有人上傳一個帶著 10 萬字元 EXIF 註解的檔案，服務才突然卡住。這是一個「看起來是 O(n)，其實是 O(n²)」的經典陷阱，也是 code review 時值得特別留意的模式。

### 減少函式呼叫與邊界檢查

`thumbd` 原本的縮圖函式每讀一個像素都呼叫 `get_px(src, x, y)`，函式裡檢查 x、y 是否越界，再算 `y * width + x`。對一個 2000 × 1500 的輸出，這是每個輸出像素 4 次讀取呼叫、1 次寫入呼叫，總共 1,500 萬次函式呼叫和 1,500 萬次四重邊界檢查。

但迴圈的範圍本身就保證了不會越界：輸出座標 x 在 0 到 1999 之間，對應的原圖座標 2x、2x+1 一定在 0 到 3999 之間。邊界檢查是**多餘的**。改寫的方法是在每一列開始時算出這一列的起始指標，迴圈裡直接用指標加索引存取。這個改寫在 14.12 節實測。

> [!tip] 安全與效能不衝突
> 拿掉每個像素的邊界檢查，不等於放棄安全。正確的做法是把檢查**提到迴圈外**：在函式開頭確認 `src->width >= 2 * dst->width`、`src->height >= 2 * dst->height`，一次檢查涵蓋整個迴圈。這比每個像素檢查一次更清楚、也更容易在 code review 時驗證。

### 減少不必要的記憶體存取

如果迴圈每一圈都把累加結果寫回某個指標指向的位置（例如 `*dest += x`），而 `dest` 可能和資料陣列重疊，編譯器就必須每圈都真的寫入記憶體，可能還要讀回來。改用區域變數累加、迴圈結束後寫回一次，就消除了這些存取。CS:APP 原書（3e）在當時的 GCC 上量到這個改動有明顯效果；14.12 節會看到，在現代的 clang 上情況有點不同。

## 14.5 現代處理器的模型：功能單元、latency 與 issue time

前面的三個技巧是「少做事」。接下來要問的是：**當工作量已經精簡，處理器能多快做完它？** 答案取決於第 13 章介紹的亂序、超純量處理器。CS:APP 用一個簡化的模型描述它：

```text
         指令（依程式順序）
              │
    ┌─────────▼──────────┐
    │ 前端：fetch、decode、 │  ← 分支預測讓前端一直往前抓
    │ 分支預測、renaming   │
    └─────────┬──────────┘
              │ 每 cycle 送出數個 micro-op
    ┌─────────▼────────────────────────────────────────┐
    │ 執行單元（運算元就緒就執行）                        │
    │  ┌────────┐┌────────┐┌────────┐┌────────┐┌──────┐ │
    │  │整數 ALU││整數 ALU││浮點加法 ││浮點乘法 ││ load │ │
    │  │        ││ ＋乘法  ││        ││        ││store │ │
    │  └────────┘└────────┘└────────┘└────────┘└──────┘ │
    └─────────┬────────────────────────────────────────┘
              │ 結果依程式順序 retire
              ▼
         架構狀態（暫存器、記憶體）
```

每一種運算有三個關鍵數字：

- **Latency**（延遲）：從開始到結果可以被下一個運算使用，要幾個 cycle。
- **Issue time**（發射間隔）：同一個功能單元連續兩次開始這種運算，至少要隔幾個 cycle。issue time 為 1 表示單元是完全 pipelined 的（第 13 章的原理用在功能單元內部），每個 cycle 都能開始一個新運算。
- **Capacity**（容量）：有幾個能做這種運算的單元。

CS:APP 以 Intel Haswell 為參考機器，給出的數字如下（不同處理器的數字不同，但量級相近）：

| 運算 | latency | issue time | capacity | latency bound（CPE） | throughput bound（CPE） |
|---|---|---|---|---|---|
| 整數加法 | 1 | 1 | 4 | 1.00 | 0.50 |
| 整數乘法 | 3 | 1 | 1 | 3.00 | 1.00 |
| 整數除法 | 3–30 | 3–30 | 1 | 3–30 | 3–30 |
| 浮點加法 | 3 | 1 | 1 | 3.00 | 1.00 |
| 浮點乘法 | 5 | 1 | 2 | 5.00 | 0.50 |
| 浮點除法 | 3–15 | 3–15 | 1 | 3–15 | 3–15 |

最後兩欄是迴圈效能的兩個極限：

**Latency bound**（延遲界限）：如果每個運算都要等上一個運算的結果，就只能一個接一個做，CPE 不可能低於 latency。浮點加法的 latency 是 3，所以 `acc = acc + d[i]` 這種迴圈的 CPE 至少是 3.0，不管有多少個加法器。

**Throughput bound**（吞吐量界限）：即使所有運算互相獨立，硬體每個 cycle 能完成的數量也有上限，等於 issue time ÷ capacity。另外每個元素還需要從記憶體讀一次，Haswell 有 2 個 load 單元，所以 CPE 不可能低於 0.5；整數加法雖然有 4 個 ALU，throughput bound 卻是 0.50 而不是 0.25，就是被 load 卡住。

把這兩個界限記住，接下來幾節的目標就很清楚：**先把迴圈從 latency bound 解放出來，再逼近 throughput bound**。

> [!note] 除法為什麼這麼慢
> 整數與浮點除法的 latency 是範圍，而且 issue time 等於 latency，表示除法單元沒有 pipelined，一個除法做完才能開始下一個。`thumbd` 的 2×2 平均用 `(s + 2) / 4`，因為除數是常數 4，編譯器會把它換成 shift（第 5 章），完全不會用到除法指令。但如果除數是變數（例如任意比例的縮放），每個像素做一次除法就很可觀，常見的做法是先算一次倒數，迴圈裡改用乘法。

## 14.6 Data-flow 圖與關鍵路徑

要知道一個迴圈被哪個界限卡住，需要畫出它的 **data-flow 圖**（資料流圖）：把每條指令當作一個節點，用箭頭連起「誰的結果被誰用到」。以 14.12 節的 `v3`（單一累加器的加總）為例，它的 x86-64 迴圈只有四條指令：

```asm
.LBB0_2:
	addsd	(%rdi,%rax,8), %xmm0
	incq	%rax
	cmpq	%rax, %rsi
	jne	.LBB0_2
```

（以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - sums.c` 產生，`sums.c` 中的 `sum_local` 與 `v3` 是同一個迴圈。）

把每一圈用到的暫存器畫出來，並把「從上一圈來、往下一圈去」的值連起來：

```text
 第 i 圈                         第 i+1 圈                       第 i+2 圈
 %rax ─▶ load d[i] ─┐            %rax ─▶ load d[i+1] ─┐
   │                ▼              │                  ▼
   │  %xmm0 ───▶ [ addsd ] ──▶ %xmm0 ───▶ [ addsd ] ──▶ %xmm0 ───▶ ...
   │             latency 3         │       latency 3
   ▼                               ▼
 [incq] ──▶ %rax ──────────────▶ [incq] ──▶ %rax ──▶ ...
   │        latency 1                │
   ▼                                 ▼
 [cmp/jne]（被預測，不在關鍵路徑上）  [cmp/jne]
```

圖中有兩條跨越迴圈的依賴鏈，叫 **loop-carried dependency**（跨迭代依賴）：

1. `%xmm0` 的鏈：每一圈的 `addsd` 都要等上一圈的 `addsd` 結果，每一步 3 cycles。
2. `%rax` 的鏈：每一圈的 `incq` 要等上一圈的 `incq`，每一步 1 cycle。

其他的運算，例如 load `d[i]`，只依賴 `%rax`，可以提早做，不會拖慢任何東西；`cmp`／`jne` 由分支預測器猜好（迴圈幾乎每次都跳回去），處理器不必等它。所以真正決定速度的是最長的那條鏈，叫 **critical path**（關鍵路徑）。這裡是 `%xmm0` 的鏈，n 個元素要 3n cycles，CPE = 3.0，正好等於浮點加法的 latency bound。

這張圖給了一個重要的洞見：**處理器有好幾個加法器，但這個迴圈一次只能用一個**，因為每個加法都在等上一個。要更快，就必須打斷這條鏈。

## 14.7 Loop unrolling

**Loop unrolling**（迴圈展開）是把迴圈主體複製 k 次，每一圈處理 k 個元素。以 k = 2 為例（CS:APP 叫它 2×1 unrolling：展開 2 次、1 個累加器）：

```c
for (i = 0; i + 1 < n; i += 2)
    acc = (acc + d[i]) + d[i + 1];
for (; i < n; i++)          /* 處理 n 為奇數時剩下的元素 */
    acc = acc + d[i];
```

展開減少了迴圈控制的開銷：原本每個元素要一次 `incq`、一次 `cmp`、一次 `jne`，現在每兩個元素才一次。對整數加總這種計算本身只有 1 cycle 的迴圈，這可能有幫助。

但對浮點加總，畫出 data-flow 圖就會發現問題：

```text
 acc ─▶ [ + d[i] ] ─▶ [ + d[i+1] ] ─▶ acc ─▶ [ + d[i+2] ] ─▶ [ + d[i+3] ] ─▶ acc
         3 cycles      3 cycles               3 cycles       3 cycles
 關鍵路徑上仍然是每個元素一個加法 → CPE 仍然是 3.0
```

括號 `(acc + d[i]) + d[i + 1]` 規定了先加 `d[i]`、再加 `d[i+1]`，兩個加法仍然在同一條鏈上，一個接一個。展開只減少了迴圈開銷，沒有減少關鍵路徑的長度。14.12 節的實測會證實這一點：`v4`（2×1）和 `v3` 幾乎一樣快。

編譯器自己也會展開迴圈。用 `-O3` 產生同一個 `sum_local`：

```bash
clang -target x86_64-linux-gnu -O3 -S -fno-asynchronous-unwind-tables -o - sums.c
```

主迴圈（刪去 directive 與註解）：

```asm
.LBB0_9:
	addsd	(%rdi,%rcx,8), %xmm0
	addsd	8(%rdi,%rcx,8), %xmm0
	addsd	16(%rdi,%rcx,8), %xmm0
	addsd	24(%rdi,%rcx,8), %xmm0
	addsd	32(%rdi,%rcx,8), %xmm0
	addsd	40(%rdi,%rcx,8), %xmm0
	addsd	48(%rdi,%rcx,8), %xmm0
	addsd	56(%rdi,%rcx,8), %xmm0
	addq	$8, %rcx
	cmpq	%rcx, %rsi
	jne	.LBB0_9
```

編譯器展開了 8 次，但八個 `addsd` 全部累加到同一個 `%xmm0`，關鍵路徑一點都沒變。編譯器不是不懂得用多個累加器，而是**不被允許**：下一節會說明原因。

## 14.8 多個累加器與 reassociation

要打斷關鍵路徑，有兩種改寫方式。

### 多個累加器

**多個累加器**（multiple accumulators）的想法是：把元素分成幾組，各自累加到不同的變數，最後再合起來。CS:APP 把「展開 k 次、用 k 個累加器」寫成 k×k。以 4×4 為例：

```c
double a0 = 0, a1 = 0, a2 = 0, a3 = 0;
for (i = 0; i + 3 < n; i += 4) {
    a0 += d[i];     a1 += d[i + 1];
    a2 += d[i + 2]; a3 += d[i + 3];
}
for (; i < n; i++) a0 += d[i];
double acc = (a0 + a1) + (a2 + a3);
```

它的 data-flow 圖變成四條平行的鏈：

```text
 a0 ─▶ [+ d[0]] ─▶ [+ d[4]] ─▶ [+ d[8]]  ─▶ ...  ┐
 a1 ─▶ [+ d[1]] ─▶ [+ d[5]] ─▶ [+ d[9]]  ─▶ ...  │ 四條鏈互不依賴，
 a2 ─▶ [+ d[2]] ─▶ [+ d[6]] ─▶ [+ d[10]] ─▶ ...  │ 可以同時在加法器的
 a3 ─▶ [+ d[3]] ─▶ [+ d[7]] ─▶ [+ d[11]] ─▶ ...  ┘ pipeline 裡前進
         每條鏈長 n/4 個加法 → 關鍵路徑 3 × n/4 cycles → CPE 0.75
```

每條鏈只有 n/4 個加法，關鍵路徑縮短為四分之一。浮點加法器是 pipelined 的（issue time 1），所以四條鏈的加法可以錯開一個 cycle 依序進入同一個加法器，四個加法同時在不同的階段裡，這正是第 13 章 pipelining 的原理用在單一功能單元上。

要多少個累加器才夠？CS:APP 給出一個簡單的規則：要讓功能單元完全不閒著，需要的獨立鏈數至少是

```text
k ≥ C × L       （C = 這種運算的 capacity，L = latency）
```

Haswell 的浮點加法 C = 1、L = 3，所以 k ≥ 3，至少要 3 個累加器才能達到 throughput bound 1.0。浮點乘法 C = 2、L = 5，要 10 個。累加器也不是越多越好：x86-64 只有 16 個 SIMD 暫存器（未使用 AVX-512 時），累加器、迴圈索引、暫時值加起來超過暫存器數，編譯器就要把值放到 stack 上（**register spilling**），反而變慢。

### Reassociation

另一種方法只改一對括號。把 2×1 的 `(acc + d[i]) + d[i + 1]` 改成：

```c
acc = acc + (d[i] + d[i + 1]);      /* CS:APP 稱為 2x1a */
```

```text
 d[i] ──┐                d[i+2] ──┐
        ├─[ + ]──┐                ├─[ + ]──┐
 d[i+1]─┘        ▼        d[i+3] ─┘        ▼
 acc ───────▶ [ + ] ─▶ acc ─────────────▶ [ + ] ─▶ acc
              關鍵路徑：每兩個元素只有一個加法 → CPE 1.5
```

`d[i] + d[i + 1]` 不依賴 `acc`，可以提早算好；關鍵路徑上每兩個元素只剩一個加法，CPE 從 3.0 降到 1.5。這種改變運算結合順序的技巧叫 **reassociation**（重新結合）。

### 為什麼編譯器不自動做？

數學上 (a + b) + c = a + (b + c)，但浮點數不滿足結合律（第 6 章）。舉一個極端的例子：

```text
(1e20 + (−1e20)) + 3.14 = 0 + 3.14 = 3.14
1e20 + ((−1e20) + 3.14) = 1e20 + (−1e20) = 0     （3.14 被大數吸收）
```

多個累加器和 reassociation 都改變了加法的順序，結果可能在最後幾個位元不同，極端情況下差很多。C 標準要求編譯器保持原本的運算順序，所以編譯器不能自動做；這是程式設計師的決定。

| 型別 | 編譯器能自動 reassociate 嗎 | 原因 |
|---|---|---|
| unsigned 整數 | 能 | 模 2^w 的加法與乘法滿足結合律與交換律 |
| signed 整數 | 能 | 二補數的位元運算和 unsigned 相同；溢位是 UB，編譯器可以假設不發生 |
| `float`／`double` | 不能（除非 `-ffast-math` 或 `-fassociative-math`） | 改變順序會改變捨入結果 |

對 `thumbd` 的像素加總來說，影像亮度的平均值差在第 15 位有效數字根本無所謂，手動改寫是安全的。但對財務計算或需要可重現結果的科學計算，就必須想清楚。還有一點值得注意：多個累加器通常讓結果**更準**，因為每個累加器的值較小，大數吸收小數的情況較少。

## 14.9 SIMD 簡介

到目前為止，每條加法指令只處理一個 `double`。**SIMD**（single instruction, multiple data，單指令多資料）指令一次處理一整組資料：

```text
 純量（scalar）addsd：           SIMD addpd（SSE，128-bit）：
 ┌────────┐   ┌────────┐         ┌────────┬────────┐   ┌────────┬────────┐
 │  a0    │ + │  b0    │         │  a0    │  a1    │ + │  b0    │  b1    │
 └────────┘   └────────┘         └────────┴────────┘   └────────┴────────┘
     = a0+b0（一個結果）              = a0+b0 │ a1+b1（兩個結果，一條指令）

 AVX2（256-bit）：一次 4 個 double 或 8 個 float 或 32 個 uint8
 AVX-512（512-bit）：一次 8 個 double；ARM NEON（128-bit）：一次 2 個 double 或 16 個 uint8
```

SIMD 的威力在小型資料特別驚人：一個 128-bit 的暫存器可以放 16 個 `uint8_t` 像素，一條指令就處理 16 個像素。這正是 `thumbd` 縮圖迴圈在 `-O2` 下又快了 8 倍的原因（14.12 節）。

大多數情況下你不需要手寫 SIMD，編譯器的 **auto-vectorization**（自動向量化）會處理。條件是迴圈夠簡單：迭代之間沒有依賴（或只有可以 reassociate 的歸約）、記憶體存取連續、沒有 aliasing 的疑慮、沒有複雜的分支。想知道編譯器有沒有向量化、為什麼沒有，可以請它告訴你：

```bash
clang -target x86_64-linux-gnu -O3 -c -Rpass=loop-vectorize -Rpass-missed=loop-vectorize \
      -Rpass-analysis=loop-vectorize sums.c -o /dev/null
```

對 `sum_local` 的實際輸出（節錄）：

```text
sums.c:4:19: remark: loop not vectorized: cannot prove it is safe to reorder floating-point operations; allow reordering by specifying '#pragma clang loop vectorize(enable)' before the loop or by providing the compiler option '-ffast-math' [-Rpass-analysis=loop-vectorize]
sums.c:3:5: remark: loop not vectorized [-Rpass-missed=loop-vectorize]
```

編譯器說得很清楚：浮點加總需要改變順序才能向量化，它沒有得到許可。GCC 的對應選項是 `-fopt-info-vec-missed`。加上 `-ffast-math` 之後，同一個迴圈變成：

```asm
.LBB0_6:
	movupd	(%rdi,%rcx,8), %xmm2
	addpd	%xmm2, %xmm0
	movupd	16(%rdi,%rcx,8), %xmm2
	addpd	%xmm2, %xmm1
	addq	$4, %rcx
	cmpq	%rcx, %rax
	jne	.LBB0_6
```

（以 `clang -target x86_64-linux-gnu -O3 -ffast-math -S -fno-asynchronous-unwind-tables -o - sums.c` 產生。）`addpd` 一次加兩個 `double`，而且用了 `%xmm0`、`%xmm1` 兩個向量累加器，等於 4 條平行的鏈：編譯器自動做了 14.8 節的所有改寫，再加上 SIMD。

> [!warning] `-ffast-math` 不只是「允許重新排列」
> `-ffast-math` 同時開啟一整組假設，包括「程式裡不會出現 NaN 與無限大」。如果你的程式用 `isnan(x)` 檢查錯誤，在 `-ffast-math` 下這個檢查可能被編譯器直接刪掉。只需要 reassociation 時，用比較窄的 `-fassociative-math`（搭配 `-fno-signed-zeros -fno-trapping-math`），或在特定迴圈上用 `#pragma`，或乾脆手動寫多個累加器，影響範圍最可控。

另一個常見的坑是 `-march=native`：它讓編譯器使用**編譯機器**支援的所有指令（例如 AVX-512）。在 CI 機器上編譯、部署到較舊的 production 機器時，程式會在執行到那些指令時收到 `SIGILL`（illegal instruction）而當掉。部署用的二進位檔應該指定明確的目標，例如 x86-64 的 `-march=x86-64-v3`，並確認所有機器都支援。

## 14.10 分支預測與 branchless 程式碼

第 13 章量到：資料決定的、沒有規律的分支，可以讓同一段程式慢十倍。這一節看怎麼處理它。

**Branchless**（無分支）程式碼的想法是：與其讓 CPU 猜要走哪條路，不如兩條路都算，再用不需要預測的方式選一個。工具有三種：

| 技巧 | 例子 | 組合語言 |
|---|---|---|
| conditional move | `m = (a > b) ? a : b;` | `cmov`（x86-64）、`csel`（ARM64） |
| 把條件變成 0／1 參與運算 | `k += (alpha >= 128);` | `setcc` 或 shift |
| 位元遮罩 | `mask = -(uint32_t)(a < b); m = (a & mask) \| (b & ~mask);`（取較小值） | `and`、`or`、`neg` |

第 13 章的 `collect_opaque` 無法用 cmov，因為 `if` 裡有記憶體寫入。改寫的關鍵是**每次都寫，但只有條件成立時才讓索引前進**：

```c
long collect_branchless(const unsigned char *alpha, long n, int *out) {
    long k = 0;
    for (long i = 0; i < n; i++) {
        out[k] = (int)i;            /* 不管條件，先寫到 out[k] */
        k += alpha[i] >> 7;         /* alpha >= 128 時最高位元是 1，k 才前進 */
    }
    return k;
}
```

不成立的時候，`out[k]` 會在下一圈被覆寫，等於沒寫。代價是 `out` 的容量要比收集到的數量多一格：如果最後幾個像素都不成立，最後一次寫入會落在 `out[k]`，也就是有效資料的後面一格。（因為第 i 圈的 k 不會超過 i，`out` 若本來就配置了 n 格就不會越界。）用 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - bl_x.c` 確認迴圈裡沒有條件跳躍：

```asm
collect_branchless:
	testq	%rsi, %rsi
	jle	.LBB0_1
	xorl	%ecx, %ecx
	xorl	%r8d, %r8d
.LBB0_4:
	movl	%ecx, (%rdx,%r8,4)
	movzbl	(%rdi,%rcx), %eax
	shrl	$7, %eax
	addq	%r8, %rax
	incq	%rcx
	movq	%rax, %r8
	cmpq	%rcx, %rsi
	jne	.LBB0_4
	retq
.LBB0_1:
	xorl	%eax, %eax
	retq
```

迴圈裡唯一的跳躍是迴圈本身的 `jne`，它幾乎每次都跳回去，預測器不會猜錯。原本依資料而定的 `jns` 不見了，取而代之的是 `shrl $7` 與 `addq`：把條件變成算術。

branchless 不是免費的：每個元素都要做寫入，而且 `k` 現在是一條 loop-carried dependency（下一圈的寫入位址依賴這一圈的 `k`）。所以它**只在分支真的不可預測時才划算**。14.12 節會同時量隨機與排序過的資料，看清楚這個取捨。

另一種思路是不要改寫程式，而是**改變資料**，讓分支變得可預測：例如先把像素依不透明度分類、先檢查一整塊是否全透明或全不透明再決定走哪個迴圈。還有 **PGO**（profile-guided optimization）：先用 `-fprofile-generate` 編譯並跑一遍代表性的工作負載，再用 `-fprofile-use` 重新編譯，編譯器就知道哪些分支常走哪邊、哪些適合改成 cmov，並據此安排程式碼。

## 14.11 找出熱點：profiling 與 Amdahl's law

前面所有技巧都假設你知道要改哪個迴圈。在真實的服務裡，這需要 **profiler**（效能剖析工具）告訴你時間花在哪裡。

### 常用的 profiler

| 工具 | 原理 | 用法 | 適合 |
|---|---|---|---|
| `gprof` | 編譯時插入計數程式碼（`-pg`），加上定時取樣 | `gcc -O2 -pg`、執行、`gprof ./prog gmon.out` | 教學、單機程式；對 shared library 與多執行緒支援有限 |
| `perf`（Linux） | 用硬體計數器中斷做取樣，不必重新編譯 | `perf record -g ./prog`、`perf report` | production 服務、kernel 與使用者空間一起看 |
| Flame graph | 把 `perf` 的 call stack 取樣畫成火焰圖 | `perf script` 輸出後用 flame graph 工具轉換 | 一眼看出哪條呼叫路徑最寬 |
| Instruments、`sample`（macOS） | 取樣 | `sample <PID> 10`、Xcode Instruments 的 Time Profiler | 本機開發 |

取樣式 profiler 的原理很直覺：每隔固定時間（例如每 1 ms，或每 N 個 cycle）中斷程式一次，記錄當下正在執行哪個函式、call stack 是什麼。取樣夠多次之後，某個函式出現的比例就近似它佔用 CPU 時間的比例。這種方法對程式的干擾很小，所以可以在 production 上用。

`perf report` 的輸出大致長這樣（示意輸出）：

```text
# Overhead  Command  Shared Object       Symbol
    40.12%  thumbd   libjpeg.so.62       [.] decode_mcu
    21.30%  thumbd   thumbd              [.] get_px
    16.77%  thumbd   libjpeg.so.62       [.] encode_mcu
     9.85%  thumbd   thumbd              [.] shrink_half
     3.96%  thumbd   thumbd              [.] set_px
```

小安的報告中，`get_px`、`shrink_half`、`set_px` 加起來約 35%：這就是 14.1 節的數字。要注意，如果 `get_px` 被 inline 進 `shrink_half`，它就不會單獨出現；所以要用 `-g` 編譯保留除錯資訊，並用 `perf report --children` 或 flame graph 看包含子函式的總時間。

### Amdahl's law：局部加速的整體效益

**Amdahl's law**（阿姆達爾定律，第 1 章介紹過）回答的問題是：程式中佔時間比例 α 的部分加速 k 倍，整體加速多少？

```text
                    1
 整體加速 S = ─────────────────
               (1 − α) + α / k

 k → ∞ 時的上限：S_max = 1 / (1 − α)
```

套用到 `thumbd`：縮圖佔 α = 0.35，實測加速 k = 78.9（14.12 節 `-O2` 的結果）。

```text
S = 1 / (0.65 + 0.35 / 78.9) = 1 / (0.65 + 0.0044) = 1 / 0.6544 ≈ 1.53
S_max = 1 / 0.65 ≈ 1.54
```

縮圖快了 79 倍，整體只快 1.53 倍；就算縮圖變成零秒，整體也只能快 1.54 倍。這解釋了 14.1 節小安的沮喪，也說明了下一步該做什麼：

| 下一個目標 | α | 假設加速 k | 整體 S | 說明 |
|---|---|---|---|---|
| 縮圖（已完成） | 0.35 | 78.9 | 1.53 | 剩下的潛力只有 0.01 |
| 解碼加速 2 倍 | 0.40 ／ 0.654 = 0.61 | 2 | 1.44（在 1.53 之上再乘） | 例如換用 SIMD 版本的 JPEG 解碼函式庫，或解碼時直接縮小（JPEG 支援以 1/2、1/4、1/8 解碼） |
| 編碼加速 2 倍 | 0.17 ／ 0.654 = 0.26 | 2 | 1.15 | 降低品質參數或換編碼器 |

第二列的 α 要重新計算：縮圖最佳化之後，總時間變成原本的 0.654，解碼的 0.40 現在佔 0.40 ／ 0.654 ≈ 61%。每做完一次最佳化，就要重新 profile，因為比例已經變了。

> [!tip] 演算法層級的改變往往最有效
> 表中「解碼時直接縮小」是一個演算法層級的改變：JPEG 的格式允許解碼器只解出 1/2、1/4 或 1/8 解析度的影像，省下大部分解碼與縮圖的工作。這種「少做事」的改變，常常比任何指令層級的技巧都有效。最佳化的優先順序通常是：演算法與資料結構 → 消除不必要的工作 → 記憶體存取模式（第 17 章）→ 指令級平行 → SIMD。

## 14.12 動手做：一步一步加速加總迴圈與縮圖迴圈

### 程式一：七個版本的加總

這個程式把本章的每一種技巧寫成一個版本，對同一個 8,192 個 `double` 的陣列（64 KiB，放得進 M4 Pro 效能核心 128 KiB 的 L1 data cache，排除記憶體的影響）加總，每個版本重複 2,000 次，取 5 次中最快的一次。

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

/* 模仿 thumbd 的權重陣列：一個長度固定的 double 向量 */
typedef struct { long len; double *data; } vec_t;

__attribute__((noinline)) static long vec_length(const vec_t *v) { return v->len; }
__attribute__((noinline)) static int get_elem(const vec_t *v, long i, double *out) {
    if (i < 0 || i >= v->len) return 0;          /* 每次都做邊界檢查 */
    *out = v->data[i];
    return 1;
}

/* v1：每圈呼叫 vec_length 與 get_elem，結果累加到 *dest */
static void sum_v1(const vec_t *v, double *dest) {
    *dest = 0;
    for (long i = 0; i < vec_length(v); i++) {
        double x;
        get_elem(v, i, &x);
        *dest = *dest + x;
    }
}
/* v2：直接用陣列，但仍累加到 *dest（編譯器怕 dest 和 data 重疊） */
static void sum_v2(const vec_t *v, double *dest) {
    long n = vec_length(v);
    const double *d = v->data;
    *dest = 0;
    for (long i = 0; i < n; i++) *dest = *dest + d[i];
}
/* v3：用區域變數累加，最後寫回一次 */
static void sum_v3(const vec_t *v, double *dest) {
    long n = vec_length(v);
    const double *d = v->data;
    double acc = 0;
    for (long i = 0; i < n; i++) acc = acc + d[i];
    *dest = acc;
}
/* v4：2x1 unrolling，一圈做兩個元素，仍只有一個累加器 */
static void sum_v4(const vec_t *v, double *dest) {
    long n = vec_length(v), i;
    const double *d = v->data;
    double acc = 0;
    for (i = 0; i + 1 < n; i += 2) acc = (acc + d[i]) + d[i + 1];
    for (; i < n; i++) acc = acc + d[i];
    *dest = acc;
}
/* v5：2x1a reassociation，先把兩個元素相加，再加到累加器 */
static void sum_v5(const vec_t *v, double *dest) {
    long n = vec_length(v), i;
    const double *d = v->data;
    double acc = 0;
    for (i = 0; i + 1 < n; i += 2) acc = acc + (d[i] + d[i + 1]);
    for (; i < n; i++) acc = acc + d[i];
    *dest = acc;
}
/* v6：4x4，四個獨立的累加器 */
static void sum_v6(const vec_t *v, double *dest) {
    long n = vec_length(v), i;
    const double *d = v->data;
    double a0 = 0, a1 = 0, a2 = 0, a3 = 0;
    for (i = 0; i + 3 < n; i += 4) {
        a0 += d[i]; a1 += d[i + 1]; a2 += d[i + 2]; a3 += d[i + 3];
    }
    for (; i < n; i++) a0 += d[i];
    *dest = (a0 + a1) + (a2 + a3);
}
/* v7：8x8，八個獨立的累加器 */
static void sum_v7(const vec_t *v, double *dest) {
    long n = vec_length(v), i;
    const double *d = v->data;
    double a0 = 0, a1 = 0, a2 = 0, a3 = 0, a4 = 0, a5 = 0, a6 = 0, a7 = 0;
    for (i = 0; i + 7 < n; i += 8) {
        a0 += d[i];     a1 += d[i + 1]; a2 += d[i + 2]; a3 += d[i + 3];
        a4 += d[i + 4]; a5 += d[i + 5]; a6 += d[i + 6]; a7 += d[i + 7];
    }
    for (; i < n; i++) a0 += d[i];
    *dest = ((a0 + a1) + (a2 + a3)) + ((a4 + a5) + (a6 + a7));
}

typedef void (*sum_fn)(const vec_t *, double *);
static double now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e9 + ts.tv_nsec;
}

int main(void) {
    enum { N = 8192, REPS = 2000 };            /* 64 KiB：放得進 L1 data cache */
    vec_t v = { N, malloc(N * sizeof(double)) };
    for (long i = 0; i < N; i++) v.data[i] = (double)(i % 255) / 255.0;
    struct { const char *name; sum_fn fn; } tests[] = {
        {"v1 call per element", sum_v1}, {"v2 accumulate *dest", sum_v2},
        {"v3 local accumulator", sum_v3}, {"v4 unroll 2x1", sum_v4},
        {"v5 unroll 2x1a", sum_v5},       {"v6 unroll 4x4", sum_v6},
        {"v7 unroll 8x8", sum_v7},
    };
    double result = 0;
    for (size_t t = 0; t < sizeof tests / sizeof tests[0]; t++) {
        double best = 1e30;
        for (int trial = 0; trial < 5; trial++) {      /* 取 5 次中最快的一次 */
            double t0 = now_ns();
            for (int r = 0; r < REPS; r++) tests[t].fn(&v, &result);
            double per = (now_ns() - t0) / ((double)REPS * N);
            if (per < best) best = per;
        }
        printf("%-22s %6.3f ns/element  sum=%.1f\n", tests[t].name, best, result);
    }
    free(v.data);
    return 0;
}
```

執行環境：macOS arm64（Apple M4 Pro），Apple clang 21，`cc -std=c17 -O1 -Wall -Wextra`：

```text
v1 call per element     1.309 ns/element  sum=4065.9
v2 accumulate *dest     0.573 ns/element  sum=4065.9
v3 local accumulator    0.646 ns/element  sum=4065.9
v4 unroll 2x1           0.560 ns/element  sum=4065.9
v5 unroll 2x1a          0.334 ns/element  sum=4065.9
v6 unroll 4x4           0.166 ns/element  sum=4065.9
v7 unroll 8x8           0.094 ns/element  sum=4065.9
```

逐行解讀（括號內是以約 4.5 GHz 估算的 CPE，只供參考）：

1. **v1（1.309 ns，約 5.9 cycles）**：每個元素兩次函式呼叫加一次邊界檢查。這是「每個像素呼叫 `get_px`」的縮影，比 v3 慢一倍。
2. **v2 與 v3（0.573 與 0.646 ns，約 2.6–2.9 cycles）**：這裡有一個值得仔細看的結果，v2 並沒有比 v3 慢。查看本機的 arm64 組合語言，clang 對 v2 產生的迴圈是 `ldr`、`fadd`、`str`：它把累加值保留在暫存器裡，每圈只是**多一次寫入**，並沒有重新從 `*dest` 讀回來。寫入不在關鍵路徑上，所以不影響速度。CS:APP 原書在舊版 GCC 上量到的差距，在這個編譯器上已經被消除了。兩者內層迴圈的關鍵路徑完全相同，相差的約 10% 來自量測雜訊與程式碼對齊等因素，**10% 以內的差異不要下結論**。
3. **v3 就是 latency bound**：單一累加器的關鍵路徑是一連串的 `fadd`，所以 0.6 ns 左右這個數字，本身就是這顆核心「一次浮點加法 latency」的直接量測。不需要知道確切時脈，也能得到這個界限。
4. **v4（0.560 ns）**：2×1 unrolling 和 v3 幾乎一樣，證實 14.7 節的推論：展開不會縮短關鍵路徑。
5. **v5（0.334 ns）**：只改一對括號，時間減半，正如 14.8 節 data-flow 圖預測的「每兩個元素只剩一個加法在關鍵路徑上」。
6. **v6（0.166 ns）**：四個累加器，約為 v3 的 1/3.9，接近理想的 1/4。
7. **v7（0.094 ns）**：八個累加器，約為 v3 的 1/6.9，還在繼續改善。換算每個元素約 0.42 cycles，也就是每個 cycle 完成 2 個以上的浮點加法。依 k ≥ C × L 的規則，這表示這顆核心的浮點加法 capacity 大於 1，否則 v6 就已經到頂了。和 Haswell 的參考數字相比，這說明了「同一段程式在不同微架構上的極限不同」，以及為什麼最佳化要在目標機器上量。

所有版本的 `sum` 都印出 4065.9：在這組資料上，改變加法順序造成的差異小到在小數點後一位看不出來。

同一個程式用不同的編譯選項，結果如下（同一台機器，ns/元素，各執行一次）：

| 版本 | `-O0` | `-O1` | `-O2` | `-O3` | `-O3 -ffast-math` |
|---|---|---|---|---|---|
| v1 每圈呼叫函式 | 2.518 | 1.309 | 1.312 | 0.792 | 0.758 |
| v3 區域累加器 | 0.668 | 0.646 | 0.548 | 0.574 | 0.081 |
| v6 4×4 | 0.412 | 0.166 | 0.149 | 0.152 | 0.102 |
| v7 8×8 | 0.426 | 0.094 | 0.095 | 0.096 | 0.070 |

幾個觀察：`-O0` 下所有變數都放在 stack 上，每次累加都要存取記憶體，多個累加器的效果大打折扣，所以**絕對不要用 `-O0` 量效能**。`-O1` 到 `-O3`，v3 都卡在 latency bound，因為編譯器不被允許重新排列浮點加法。v1 在 `-O3` 下變快，是 14.3 節提到的：clang 把 `vec_length` 的結果移出了迴圈。`-O3 -ffast-math` 讓最簡單的 v3 直接從 0.574 降到 0.081 ns，因為編譯器自己做了多累加器加 SIMD，比手寫的 v7 標量版本還快。結論是：**手寫多累加器是在不能用 fast-math 時取回效能的方法；能接受改變捨入時，讓編譯器做通常更好。**

### 程式二：`thumbd` 的縮圖迴圈

這是 14.1 節的真實案例，簡化成灰階影像。A 是原本的版本，B 是改寫後的版本：把迴圈不變量（寬、高）移出迴圈，每一列算一次 row 指標，消除函式呼叫與多餘的邊界檢查。

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

/* thumbd 的灰階影像：每個像素 1 byte，row-major 排列 */
typedef struct { int width, height; uint8_t *data; } image_t;

/* 原始版本用的存取函式：每次都檢查邊界（模仿「安全的」API） */
__attribute__((noinline)) static int img_width(const image_t *im) { return im->width; }
__attribute__((noinline)) static int img_height(const image_t *im) { return im->height; }
__attribute__((noinline)) static uint8_t get_px(const image_t *im, int x, int y) {
    if (x < 0 || y < 0 || x >= im->width || y >= im->height) return 0;
    return im->data[(long)y * im->width + x];
}
__attribute__((noinline)) static void set_px(image_t *im, int x, int y, uint8_t v) {
    if (x < 0 || y < 0 || x >= im->width || y >= im->height) return;
    im->data[(long)y * im->width + x] = v;
}

/* A：原始版本，2x2 平均縮成一半 */
static void shrink_a(const image_t *src, image_t *dst) {
    for (int y = 0; y < img_height(dst); y++)
        for (int x = 0; x < img_width(dst); x++) {
            int s = get_px(src, 2 * x, 2 * y) + get_px(src, 2 * x + 1, 2 * y)
                  + get_px(src, 2 * x, 2 * y + 1) + get_px(src, 2 * x + 1, 2 * y + 1);
            set_px(dst, x, y, (uint8_t)((s + 2) / 4));
        }
}

/* B：迴圈不變量移出迴圈、直接用 row 指標，消除函式呼叫與邊界檢查 */
static void shrink_b(const image_t *src, image_t *dst) {
    int w = dst->width, h = dst->height, sw = src->width;
    for (int y = 0; y < h; y++) {
        const uint8_t *r0 = src->data + (long)(2 * y) * sw;
        const uint8_t *r1 = r0 + sw;
        uint8_t *out = dst->data + (long)y * w;
        for (int x = 0; x < w; x++) {
            int s = r0[2 * x] + r0[2 * x + 1] + r1[2 * x] + r1[2 * x + 1];
            out[x] = (uint8_t)((s + 2) / 4);
        }
    }
}

static double now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e9 + ts.tv_nsec;
}

static double bench(void (*fn)(const image_t *, image_t *), const image_t *s, image_t *d) {
    double best = 1e30;
    for (int t = 0; t < 7; t++) {                  /* 取 7 次中最快的一次 */
        double t0 = now_ns();
        fn(s, d);
        double el = now_ns() - t0;
        if (el < best) best = el;
    }
    return best / ((double)d->width * d->height);  /* 每個輸出像素幾 ns */
}

int main(void) {
    image_t src = {4000, 3000, malloc(4000 * 3000)};  /* 一張 1200 萬像素的原圖 */
    image_t da = {2000, 1500, malloc(2000 * 1500)}, db = {2000, 1500, malloc(2000 * 1500)};
    for (long i = 0; i < (long)src.width * src.height; i++) src.data[i] = (uint8_t)(i * 7 + i / 4000);
    double ta = bench(shrink_a, &src, &da);
    double tb = bench(shrink_b, &src, &db);
    long diff = 0;
    for (long i = 0; i < 2000L * 1500; i++) diff += da.data[i] != db.data[i];
    printf("A 原始版本：%.3f ns/輸出像素，整張 %.2f ms\n", ta, ta * 2000 * 1500 / 1e6);
    printf("B 改寫版本：%.3f ns/輸出像素，整張 %.2f ms\n", tb, tb * 2000 * 1500 / 1e6);
    printf("加速 %.1f 倍，兩版結果不同的像素數：%ld\n", ta / tb, diff);
    free(src.data); free(da.data); free(db.data);
    return 0;
}
```

在同一台 macOS arm64（Apple M4 Pro，Apple clang 21）上，先用 `cc -std=c17 -O1 -Wall -Wextra`：

```text
A 原始版本：3.923 ns/輸出像素，整張 11.77 ms
B 改寫版本：0.405 ns/輸出像素，整張 1.22 ms
加速 9.7 倍，兩版結果不同的像素數：0
```

再用 `cc -std=c17 -O2` 編譯同一個檔案執行：

```text
A 原始版本：3.894 ns/輸出像素，整張 11.68 ms
B 改寫版本：0.049 ns/輸出像素，整張 0.15 ms
加速 78.9 倍，兩版結果不同的像素數：0
```

解讀：

1. **正確性先確認**：兩版輸出逐像素比對，差異為 0。任何最佳化都要先過這一關，否則速度沒有意義。
2. **`-O1` 下快 9.7 倍**：這完全來自「少做事」：每個輸出像素少了 6 次函式呼叫（4 次 `get_px`、1 次 `set_px`，加上內層迴圈條件裡的 `img_width`）與 5 組邊界檢查，乘法 `y * width` 也從每個像素算一次變成每列算一次。
3. **`-O2` 下快 78.9 倍**：A 幾乎沒變（函式呼叫擋住了一切），B 卻又快了 8 倍。原因是 `-O2` 開啟了 auto-vectorization，B 的內層迴圈簡單、連續、沒有呼叫，編譯器把它改成 SIMD，一條指令同時處理許多個像素（ARM NEON 的 128-bit 暫存器可以放 16 個 `uint8_t`）。換句話說，**改寫的最大價值不是省下那幾次呼叫，而是讓編譯器能夠向量化**。這也是老周說「SIMD 是最後一步」的意思：你根本不必手寫，只要讓迴圈變得「編譯器看得懂」。
4. A 版本不管開多高的最佳化等級都一樣慢。這說明了一個常被忽略的事實：最佳化等級救不了寫法本身擋住的最佳化。

### 程式三：branchless 的取捨

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

/* 有分支的版本：只有不透明的像素才寫入 out */
__attribute__((noinline))
static long collect_branchy(const uint8_t *alpha, long n, int32_t *out) {
    long k = 0;
    for (long i = 0; i < n; i++)
        if (alpha[i] >= 128)
            out[k++] = (int32_t)i;
    return k;
}

/* branchless 版本：每個像素都寫，但只有條件成立時 k 才前進 */
__attribute__((noinline))
static long collect_branchless(const uint8_t *alpha, long n, int32_t *out) {
    long k = 0;
    for (long i = 0; i < n; i++) {
        out[k] = (int32_t)i;
        k += alpha[i] >> 7;                        /* alpha >= 128 時為 1，否則為 0 */
    }
    return k;
}

static double now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e9 + ts.tv_nsec;
}
static double bench(long (*fn)(const uint8_t *, long, int32_t *),
                    const uint8_t *alpha, long n, int32_t *out, long *count) {
    double best = 1e30;
    for (int t = 0; t < 9; t++) {
        double t0 = now_ns();
        *count = fn(alpha, n, out);
        double el = now_ns() - t0;
        if (el < best) best = el;
    }
    return best / n;
}

static int cmp_u8(const void *a, const void *b) {
    return *(const uint8_t *)a - *(const uint8_t *)b;
}

int main(void) {
    enum { N = 1 << 20 };
    uint8_t *alpha = malloc(N);
    int32_t *out = calloc(N + 1, sizeof(int32_t));   /* 多留一格：branchless 版會寫到有效資料後面一格 */
    long c1, c2;
    srand(42);
    for (long i = 0; i < N; i++) alpha[i] = (uint8_t)(rand() & 0xFF);
    for (int round = 0; round < 2; round++) {
        double tb = bench(collect_branchy, alpha, N, out, &c1);
        double tl = bench(collect_branchless, alpha, N, out, &c2);
        printf("%s  有分支 %.3f ns/像素   branchless %.3f ns/像素   (%ld / %ld)\n",
               round == 0 ? "隨機資料" : "排序資料", tb, tl, c1, c2);
        qsort(alpha, N, 1, cmp_u8);
    }
    free(alpha); free(out);
    return 0;
}
```

同一台機器，`cc -std=c17 -O1 -Wall -Wextra`：

```text
隨機資料  有分支 2.911 ns/像素   branchless 0.266 ns/像素   (523962 / 523962)
排序資料  有分支 0.259 ns/像素   branchless 0.272 ns/像素   (523962 / 523962)
```

1. **隨機資料**：branchless 快了約 11 倍，回到可預測分支的速度。兩版收集到的像素數相同（523,962），正確性沒問題。
2. **排序資料**：有分支的版本反而稍快（0.259 對 0.272 ns），因為分支可預測時幾乎免費，而 branchless 版本每個像素都要寫入。這個差距在多次執行之間會變動，但 branchless 從來沒有在可預測的資料上明顯勝出。
3. **決策原則**：branchless 是「用穩定的中等成本，換掉不穩定的高成本」。資料不可預測時大勝，可預測時打平或小輸。在不知道 production 資料分布時，branchless 版本的好處是**效能不再取決於輸入內容**，這對控制 p99 延遲很有價值。

## 14.13 在工作上怎麼用

### 一套有紀律的最佳化流程

```text
 1. 定義目標：要改善的是 p99 延遲、throughput、還是 CPU 成本？目標數字是多少？
      │
 2. 建立基準：代表性的輸入（真實資料分布）、正確性檢查、固定的機器與編譯選項
      │
 3. Profile：perf record -g（Linux）／Instruments（macOS），找出佔比最高的函式
      │      └─ 用 Amdahl 算：這個函式就算變成 0，整體能快多少？值得做嗎？
      │
 4. 解釋：為什麼這段慢？
      │      ├─ 做了不必要的工作？（重複計算、n² 的 strlen、多餘的檢查）→ 14.4
      │      ├─ 編譯器被擋住？（aliasing、函式呼叫）→ 看 -Rpass-missed／組合語言 → 14.3
      │      ├─ 被 latency 綁住？（單一依賴鏈）→ 畫 data-flow 圖 → 14.6–14.8
      │      ├─ 分支預測錯誤？（perf stat 的 branch-misses）→ 14.10
      │      └─ 等記憶體？（cache-misses 高、IPC 低）→ 第 16、17 章
      │
 5. 一次只改一件事，重新量測，確認正確性
      │
 6. 回到端到端指標驗證，在 production 上觀察（canary）
```

最常見的錯誤是跳過第 3 步，憑直覺挑一個「看起來很慢」的函式開始改。另一個是跳過第 6 步：microbenchmark 快了 10 倍，但在 production 上被其他因素（I/O、lock、cache 被其他執行緒擠掉）抵消。

### 讓編譯器幫你：實用的編譯選項

| 選項 | 作用 | 注意事項 |
|---|---|---|
| `-O2` | 一般 production 的預設最佳化等級，包含 inline、向量化（clang 與較新的 GCC） | 先確定正式版本用的是哪一級 |
| `-O3` | 更積極的展開與向量化 | 程式碼變大，不一定比 `-O2` 快，要量 |
| `-g` | 保留除錯資訊，不影響產生的程式碼 | production 版本也建議保留（或分離出 debug symbols），profile 與 core dump 才看得懂 |
| `-fno-omit-frame-pointer` | 保留 frame pointer（第 9 章） | 讓 `perf record -g` 的 call stack 更可靠，代價通常很小 |
| `-Rpass-missed=loop-vectorize`（clang）、`-fopt-info-vec-missed`（GCC） | 報告哪些迴圈沒向量化、為什麼 | 先讀報告，再改程式 |
| `-flto` | link-time optimization，跨檔案 inline 與分析 | 解決「函式在另一個檔案，編譯器看不到」的問題 |
| `-fprofile-generate`／`-fprofile-use` | PGO，用真實執行資料指導最佳化 | 需要代表性的訓練工作負載 |
| `-march=x86-64-v3` 等 | 允許使用指定世代的指令集（例如 AVX2） | 不要在部署版本用 `-march=native`；確認所有機器都支援 |

### Code review 時的效能檢查清單

在 review 熱點路徑的程式碼時，這幾個問題能抓出大部分的問題：

1. 迴圈條件裡有沒有每圈都會重算、但結果不變的呼叫（`strlen`、`size()`、`get_width()`）？
2. 最內層迴圈裡有沒有對每個元素呼叫的小函式？它們在另一個檔案嗎？
3. 迴圈裡是不是透過指標累加（`*total += ...`、`obj->sum += ...`）？能不能改用區域變數？
4. 參數裡有沒有兩個同型別的指標，讓編譯器無法確定它們不重疊？
5. 最內層迴圈裡有沒有依資料而定的分支？資料分布是什麼？
6. 迴圈裡有沒有除以變數的除法，可以改成先算倒數再乘？
7. 有沒有附上量測數字：改之前、改之後、機器、編譯選項、輸入資料？

## 14.14 常見錯誤與除錯

| 症狀 | 常見原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| benchmark 顯示 0 ns 或快得不合理 | 結果沒被使用，編譯器把整個計算刪掉 | 看組合語言，迴圈是否還在 | 把結果寫到 `volatile` 變數或印出來 |
| 改了程式，時間完全沒變 | 改的不是熱點，或編譯器本來就已經做了同樣的最佳化 | 先 profile；比較改前改後的組合語言 | 先找熱點；以組合語言為準 |
| 開 `-O3` 比 `-O2` 還慢 | 程式碼變大造成 instruction cache miss，或過度展開 | 兩種版本都量，用 `perf stat` 看 `L1-icache-load-misses` | 保留 `-O2`，或只對熱點函式調整 |
| 多累加器版本結果和原本不同 | 浮點加法順序改變，捨入不同 | 和高精度（例如 `long double` 或 Kahan summation）的參考值比較誤差 | 確認誤差可接受並寫進測試的容許範圍；不能接受就不要改順序 |
| 加了 `restrict` 後結果偶爾錯誤 | 呼叫者實際上傳入了重疊的指標，違反承諾 | 用 ASan 或在 debug 版本加斷言檢查重疊 | 移除 `restrict`，或在 API 文件與斷言中強制不重疊 |
| 新版本在部分機器上 `SIGILL` 當機 | 用了 `-march=native` 或較新的指令集 | `objdump -d` 找 AVX-512 等指令；比較機器的 CPU flags | 指定明確的 `-march` 目標，或做執行期 CPU 偵測 |
| 函式快了很多倍，整體幾乎沒變 | 這個函式佔總時間比例小（Amdahl） | 用 profile 的比例代入 Amdahl 公式 | 重新 profile，處理新的最大熱點 |
| 加了 `-ffast-math` 後 NaN 檢查失效 | fast-math 假設沒有 NaN，刪除了 `isnan` 檢查 | 看組合語言或寫測試餵入 NaN | 改用 `-fassociative-math` 等較窄的選項，或手動多累加器 |

## 14.15 動手練習

1. **手算 CPE**：一個迴圈在 n = 200 時花 1,100 cycles，n = 2,000 時花 3,350 cycles。算出 CPE 與固定開銷，並判斷這個迴圈比較可能被哪種運算的 latency 綁住（參考 14.5 節的表）。（答案：CPE = 2250 ÷ 1800 = 1.25，固定開銷 850 cycles；1.25 介於整數加法的 latency bound 1.0 與整數乘法的 3.0 之間，最可能是整數加法加上一些額外開銷。）
2. **畫 data-flow 圖**：對於計算多項式的迴圈 `result = result * x + a[i]`（Horner 法），畫出跨迭代的依賴鏈，用 Haswell 的數字算出 latency bound。再想想直接計算 `a[i] * xpwr`、`xpwr *= x` 的版本，關鍵路徑是哪一條？哪個版本比較快？
3. **延伸程式一**：加入 v8（12 個累加器）與 v9（16 個累加器），看 ns/元素是否繼續下降。從結果推論這台機器的浮點加法 C × L 大約是多少。再把資料型別改成 `long`（整數加總），比較 v3 與 v7 在 `-O1` 與 `-O2` 下的差異，並用 14.8 節的表解釋為什麼整數版本在 `-O2` 下就會自動向量化。
4. **延伸程式二**：把 B 版本的 `int w = dst->width, ...` 那一行刪掉，改回在迴圈條件裡直接寫 `dst->width`、`src->data`，觀察 `-O1` 與 `-O2` 下的時間。再加上 `-Rpass-missed=loop-vectorize` 看編譯器的報告。
5. **Amdahl**：一個服務的時間分布是 JSON 解析 25%、商業邏輯 15%、資料庫查詢等待 50%、其他 10%。只能選一項優化：把 JSON 解析加速 5 倍，或把資料庫查詢時間減半，哪個好？各自的整體加速是多少？（答案：前者 1 ÷ (0.75 + 0.05) = 1.25；後者 1 ÷ (0.5 + 0.25) = 1.33，資料庫較好。）
6. 在你工作上的一個服務（或任何開源 C／C++ 程式）上用 `perf record -g` 取樣 30 秒，產生 flame graph，找出前三名熱點，用 Amdahl's law 估算每一個熱點最多能帶來的整體加速。

## 本章重點整理

- 最佳化從量測開始；CPE（每元素 cycle 數）是 T(n) = a + b × n 中的斜率 b，能公平比較不同展開程度的迴圈。
- 可信的 microbenchmark 要防止編譯器刪除計算、要暖機、要重複量測、要用真實的資料分布，並記錄機器與編譯選項；10% 以內的差異不要下結論。
- 編譯器只做對所有合法輸入都正確的最佳化；memory aliasing 與函式副作用是最常見的兩種最佳化障礙。
- 把指標指向的值複製到區域變數，是解除 aliasing 最安全的方法；`restrict` 是對編譯器的承諾，違反就是 undefined behavior；`const` 不能解決 aliasing。
- 迴圈條件裡重複呼叫 `strlen` 這類函式，會讓 O(n) 的迴圈變成 O(n²)，實測中長度每加倍、時間變成四倍。
- 每種運算有 latency、issue time 與 capacity；迴圈的 CPE 受 latency bound（單一依賴鏈）與 throughput bound（功能單元與 load 單元的數量）限制。
- 畫出 data-flow 圖、找出跨迭代的關鍵路徑，就能預測迴圈被哪個界限卡住；單一累加器的浮點加總被浮點加法的 latency 綁住。
- Loop unrolling 減少迴圈開銷，但不縮短關鍵路徑；編譯器自動展開時也一樣。
- 多個累加器（k×k）與 reassociation（2×1a）把一條長鏈拆成多條平行的短鏈，讓 pipelined 的功能單元保持忙碌；需要的累加器數約為 capacity × latency。
- 浮點數不滿足結合律，所以編譯器不會自動重新排列浮點運算，除非用 `-ffast-math` 等選項；整數則可以。
- SIMD 一條指令處理多筆資料，對 `uint8_t` 像素特別有效；讓迴圈簡單、連續、沒有呼叫與 aliasing，編譯器就能自動向量化，常常比手寫更好。
- Branchless 程式碼在分支不可預測時大幅勝出，在可預測時打平或小輸；它的另一個好處是效能不再取決於輸入內容。
- 用取樣式 profiler（`perf`、Instruments）找熱點，用 Amdahl's law 估算整體效益；每完成一次最佳化，比例就會改變，要重新 profile。
- 最佳化的優先順序通常是：演算法 → 消除不必要的工作 → 記憶體存取模式 → 指令級平行 → SIMD。

## 延伸問答

> [!question]- Q1. 為什麼 loop unrolling 本身不一定降低 CPE？什麼時候它有效？
> Loop unrolling 減少的是迴圈控制的開銷：索引遞增、比較、跳躍的次數從每個元素一次變成每 k 個元素一次。如果迴圈的瓶頸是這些開銷，例如整數加總這種主體只有 1 cycle 的迴圈，展開就有幫助。
>
> 但如果迴圈被一條跨迭代的依賴鏈綁住，例如單一累加器的浮點加總，展開只是把同一條鏈的多個環節放進同一圈，關鍵路徑長度完全沒變，CPE 仍然等於浮點加法的 latency。14.12 節的 v3 與 v4 幾乎一樣快就是證據。要打斷依賴鏈，必須搭配多個累加器或 reassociation。展開還有代價：程式碼變大、需要處理剩餘元素、佔用更多暫存器。

> [!question]- Q2. 手算題：在 Haswell 上計算 n 個 double 的乘積（`acc = acc * d[i]`），單一累加器的 CPE 是多少？要幾個累加器才能達到 throughput bound？
> 單一累加器時，每個乘法都要等上一個乘法的結果，關鍵路徑是 n 個乘法串在一起。浮點乘法的 latency 是 5，所以 CPE = 5.0。
>
> 浮點乘法的 capacity 是 2、issue time 是 1，throughput bound 是 1 ÷ 2 = 0.5。依 k ≥ C × L = 2 × 5 = 10，至少需要 10 個獨立的累加器才能讓兩個乘法單元在每個 cycle 都有新的乘法可以開始。實務上還要注意 load 單元的限制（2 個 load 單元也是 CPE 0.5）與暫存器數量，累加器太多會造成 register spilling，反而變慢。

> [!question]- Q3. 你在 code review 看到 `void blend(uint8_t *dst, const uint8_t *src, const struct params *p, int n)`，迴圈裡每個像素都用到 `p->alpha`。這段程式可能有什麼效能問題？
> `dst` 是 `uint8_t *`，而 C 規定字元型別的指標可以指向任何物件，所以每次寫入 `dst[i]`，編譯器都必須假設它可能修改了 `*p` 的內容，包括 `p->alpha`。結果是 `p->alpha` 每一圈都要重新從記憶體讀取，而且這種不確定性還可能讓編譯器放棄向量化，或者需要額外的執行期重疊檢查。
>
> 最簡單的修法是在迴圈前寫 `int alpha = p->alpha;`，把它複製到區域變數，迴圈裡只用區域變數。這不改變語意（只要呼叫者沒有讓 `dst` 指向 `p`，而那本來就是錯誤的用法），而且讓「alpha 在迴圈中不變」這件事對讀者和編譯器都很明確。修完後可以用 `-Rpass=loop-vectorize` 確認迴圈有被向量化。

> [!question]- Q4. 為什麼編譯器不會自動把 `double` 的加總改成多個累加器，卻會對 `int` 的加總這麼做？
> 因為浮點加法不滿足結合律。多個累加器等於把 `((a + b) + c) + d` 改成 `(a + c) + (b + d)`，在浮點數中兩者的捨入結果可能不同；C 標準要求編譯器保持原本的運算順序，所以不允許這種改寫，除非使用者用 `-ffast-math`、`-fassociative-math` 或 pragma 明確許可。
>
> 整數加法是模 2^w 的運算，滿足結合律與交換律，無論怎麼重新排列，結果的位元都完全相同（signed 溢位是 undefined behavior，編譯器可以假設它不發生）。所以編譯器可以自由地展開、使用多個累加器和 SIMD 指令。這也是為什麼 14.15 節練習 3 中，整數版本在 `-O2` 下會自動向量化，浮點版本卻不會。

> [!question]- Q5. 你的服務有一個函式佔 CPU 時間 60%，你把它加速了 3 倍。上線後 p50 延遲改善了，但 p99 延遲幾乎沒變，可能是什麼原因？
> Amdahl's law 預測整體 CPU 時間會變成 0.4 + 0.6 ÷ 3 = 0.6，大約快 1.67 倍，這反映在 p50 上很合理。但 p99 代表的是最慢的那 1% 請求，它們慢的原因往往和平均請求不同：可能是在等鎖、等資料庫、等 I/O、遇到 GC 或 page fault，或者處理的是特別大或特別複雜的輸入。這些時間大多不在你最佳化的那個函式裡。
>
> 要改善 p99，需要針對慢請求做分析：在服務中記錄每個請求的分段時間，把 p99 請求挑出來看時間花在哪；用 off-CPU profiling（記錄執行緒在等待什麼）而不只是 CPU profiling；檢查慢請求的輸入是否有共同特徵，例如第 13 章那種資料決定的分支預測問題。平均 profile 會稀釋少數極慢的請求，這是只看 CPU profile 的盲點。

> [!question]- Q6. 程式找錯：同事寫了一個 benchmark，`for (r = 0; r < 1000000; r++) sum_v3(&v, &result);`，結果顯示 v3 每元素 0.001 ns。哪裡出錯了？
> 0.001 ns 相當於每個 cycle 處理幾百個元素，任何現代處理器都不可能做到，所以幾乎可以確定編譯器刪掉或合併了計算。可能的原因是：編譯器看得到 `sum_v3` 的本體並 inline 進來，發現每一次呼叫的輸入都相同、結果都寫到同一個 `result`，於是只算一次（或發現 `result` 之後沒被使用，整個刪掉）。
>
> 確認方法是看組合語言，檢查迴圈是否還在、加法是否真的執行了那麼多次。修法包括：每次呼叫後把結果累加到一個最後會印出的變數、讓輸入在每次迭代時有所變化、把被測函式放在另一個編譯單元並關閉 LTO，或者使用 benchmark 框架提供的「防止最佳化」工具函式。任何 benchmark 結果，都應該先和硬體的理論極限比較，看是否合理。

> [!question]- Q7. 什麼時候 branchless 程式碼反而比較慢？
> 第一種情況是原本的分支本來就可預測。預測正確的分支幾乎免費，而 branchless 版本必須無論如何都執行兩邊的工作，例如 14.12 節程式三在排序資料上，branchless 版本因為每個像素都要寫入而稍慢。第二種情況是兩邊的工作量差很多：如果 `if` 的一邊是昂貴的計算，而它很少成立，branchless 版本等於每次都做那個昂貴的計算。
>
> 第三種情況是 branchless 引入了新的依賴鏈：cmov 必須等條件與兩個值都準備好才能產生結果，而分支預測可以讓處理器「先猜一邊繼續做」。如果條件依賴一個很慢的 load，預測正確的分支版本反而能更早開始後面的工作。所以判斷的依據應該是量測：用真實的資料分布，分別看兩個版本的時間與 branch-misses。

> [!question]- Q8. 面試題：給你一個執行太慢的 C 程式，你會怎麼著手最佳化？
> 先釐清目標與量測方式：要改善的是延遲、吞吐量還是成本，目標數字是多少；然後建立可重現的基準，包括代表性的輸入、正確性檢查、固定的編譯選項與機器。接著用 profiler（Linux 上的 `perf record -g`）找出熱點，並用 Amdahl's law 判斷每個熱點最多能帶來多少整體效益，從效益最大的開始。
>
> 針對熱點，依序檢查：演算法與資料結構是否合適；有沒有不必要的工作（重複計算、迴圈裡的不變量、多餘的檢查）；編譯器是否被 aliasing 或函式呼叫擋住（看組合語言與向量化報告）；是否被依賴鏈的 latency 綁住（用多累加器打斷）；是否有分支預測錯誤或 cache miss（`perf stat` 看計數器）。每次只改一件事，重新量測並確認正確性，最後回到端到端指標驗證。能說出這個流程、並舉出具體的工具與數字，比背出任何單一技巧都更能展現系統思維。
