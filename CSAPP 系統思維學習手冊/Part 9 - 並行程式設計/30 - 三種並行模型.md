# 第 30 章　三種並行模型：Process、I/O Multiplexing 與 Thread

> [!abstract] 本章地圖

>

## 30.1 故事：一張全景照卡住了所有人

拾光相簿推出「全景照」功能後的第一個週末，SRE 阿哲在監控圖上看到一個奇怪的形狀：`thumbd` 的 p50 延遲（中位數）平常是 15 ms，每隔幾分鐘就突然跳到 2 秒，然後又掉回來。CPU 使用率卻一直只有 10% 左右，機器明明很閒。

小安翻出 `thumbd` 最早期的程式碼，主迴圈長這樣：

```c
// not-runnable：thumbd v0 的主迴圈（簡化）
for (;;) {
    int connfd = accept(listenfd, NULL, NULL);
    handle_request(connfd);   /* 解析 HTTP、讀原圖、縮放、回傳 */
    close(connfd);
}
```

老周看了一眼就說：「這是一台 **iterative server**，一次只服務一個 client。一張 40 MB 的全景照要解碼 2 秒，這 2 秒裡 `accept` 根本沒在跑，後面排隊的幾百個小縮圖請求只能乾等。CPU 很閒，是因為大部分時間它在等磁碟和網路，而不是在算。」

小安的第一個念頭是「那就開多一點 thread」。老周搖頭：「開 thread 是一種解法，但不是唯一一種，也不一定是最好的一種。這一章先把三種基本的並行模型講清楚：process、I/O multiplexing、thread。之後你才知道 `thumbd` 現在的 thread pool 為什麼長這樣，以及它前面的 nginx 為什麼用的是完全不同的模型。」

這一章解決的是「程式結構怎麼選」；第 31 章接著處理選了 thread 之後必然遇到的共享變數與同步問題；第 32 章再談並行的效能與 thread safety。

## 30.2 為什麼需要並行

### Concurrency 與 parallelism

先把兩個常被混用的詞分開。**Concurrency**（並行）指多個工作的執行時間互相重疊：工作 A 還沒做完，工作 B 就已經開始了。它不要求「同一瞬間真的一起跑」，單核心 CPU 輪流執行兩個程式，也叫 concurrency。**Parallelism**（平行）則是同一瞬間真的有多個工作在不同的硬體上執行，例如四個核心同時各算一部分影像。

用 `thumbd` 舉例：一個 thread 在等磁碟讀原圖時，另一個 thread 在縮放另一張圖，這是 concurrency；如果機器有 8 個核心，8 個 thread 同時在做像素運算，這是 parallelism。Parallelism 是 concurrency 的一種特例，需要多個執行單元才做得到。

第 20 章介紹過 **logical control flow**（邏輯控制流）：一個程式在執行時，PC（program counter）依序走過的那一串指令位址。兩條控制流在時間上重疊，就叫它們是 concurrent flows。作業系統的 context switch 讓多個 process 的控制流交錯執行，這是我們已經看過的 concurrency；這一章要學的是如何在**應用程式內部**刻意製造多條控制流。

### Iterative server 為什麼會塞車

回到故事。把 iterative server 的時間軸畫出來：

```text
 iterative server（一次一個）
 時間 →    0        1s        2s        2.1s
 client A  ├──── 全景照解碼 2 秒 ────┤
 client B  ·······(在 backlog 裡等)······├─┤ 15 ms
 client C  ·····························├─┤
                                           ↑ B、C 明明只要 15 ms，卻等了 2 秒

 concurrent server（多條控制流）
 時間 →    0        1s        2s
 client A  ├──── 全景照解碼 2 秒 ────┤
 client B  ├─┤ 15 ms
 client C   ├─┤ 15 ms
```

上半部是 iterative server：A 的請求佔住唯一的控制流，B 和 C 雖然已經連上（connection 在 kernel 的 listen backlog 裡排隊，第 28 章），但 server 程式沒有呼叫 `accept`，它們只能等。下半部是 concurrent server：每個請求有自己的控制流，B 和 C 不必等 A。

需要並行的情境不只是 server。整理成表：

| 情境 | 不並行會怎樣 | 例子 |
|---|---|---|
| 存取慢速 I/O | CPU 在等磁碟或網路時什麼都不做 | `thumbd` 讀原圖時，可以先處理別的請求 |
| 同時服務多個使用者 | 一個慢的使用者拖垮所有人 | web server、資料庫、遊戲伺服器 |
| 和人互動 | 介面在背景工作時凍結 | GUI 程式把存檔丟到背景 thread |
| 利用多核心 | 8 核機器只用到 1 核 | 影像轉檔、壓縮、編譯 |
| 延後工作降低延遲 | 每個請求都要等不急的工作做完 | 先回應使用者，再在背景寫 log、更新統計 |

現代作業系統提供三種在應用程式中建立並行的基本方法：**process**（每條控制流是一個獨立的 process）、**I/O multiplexing**（只有一條控制流，但自己在多個連線之間切換）、**thread**（同一個 process 裡有多條控制流）。接下來三節逐一拆解，最後再放在一起比較。

## 30.3 模型一：Process-based server

### 怎麼運作

最直接的做法是：每接受一條連線，就 `fork` 一個子行程去服務它，父行程立刻回去 `accept` 下一條。第 21 章學過 `fork` 呼叫一次、回傳兩次；第 27 章學過 fork 之後，子行程拿到父行程 descriptor table 的副本，兩邊的 fd 指向**同一個** open file table entry。

```c
// not-runnable：process-based server 的骨架
signal(SIGCHLD, reap_children);          /* handler 裡用 waitpid(-1, NULL, WNOHANG) 回收 */
for (;;) {
    int connfd = accept(listenfd, NULL, NULL);
    if (fork() == 0) {                   /* 子程序 */
        close(listenfd);                 /* 子程序不需要 listen socket */
        handle_request(connfd);
        close(connfd);
        exit(0);
    }
    close(connfd);                       /* 父程序：一定要關自己那份 */
}
```

有兩個細節決定這個 server 會不會出事。第一，**父行程必須 `close(connfd)`**。fork 之後，connfd 對應的 socket 被父、子兩個 descriptor 參照，reference count 是 2。子行程服務完關掉自己那份，count 降到 1，連線還不會真的關閉。如果父行程不關，每個連線都會永遠留著一份，最後耗盡 fd 上限（`ulimit -n`），而且 client 永遠等不到連線結束。

```text
 ① accept 之後、fork 之前
    父 fd 3 ──▶ listen socket（ref = 1）
    父 fd 4 ──▶ connection   （ref = 1）

 ② fork 之後：子程序複製了 fd 表，兩邊指向同一個 socket
    父 fd 3 ──┐
    子 fd 3 ──┴─▶ listen socket（ref = 2）
    父 fd 4 ──┐
    子 fd 4 ──┴─▶ connection   （ref = 2）

 ③ 子程序 close(3)、父程序 close(4) 之後
    父 fd 3 ────▶ listen socket（ref = 1）
    子 fd 4 ────▶ connection   （ref = 1）← 子程序結束時關閉，ref 歸零才真正送出 FIN
```

第 ① 步是 `accept` 之後：父行程有 listen socket（fd 3）與新連線（fd 4）。第 ② 步 fork 之後，兩個 socket 的 reference count 都變成 2。第 ③ 步是正確處理之後：子行程關掉 listen socket，父行程關掉 connection，於是每個 socket 只被「真正需要它的那一方」持有。子行程結束時關閉 fd 4，count 歸零，kernel 才真正送出 FIN，client 才會讀到 EOF。

第二，**必須回收子行程**。子行程結束後會變成 zombie（第 21 章），直到父行程 `waitpid` 它。server 是長期執行的，不能在 `accept` 迴圈裡阻塞地等某個子行程，所以通常在 `SIGCHLD` handler 裡用 `WNOHANG` 迴圈回收。第 22 章講過 signal 不排隊：同時結束三個子行程，handler 可能只被呼叫一次，所以 handler 裡一定要用 `while (waitpid(-1, NULL, WNOHANG) > 0)` 一次收乾淨，而不是只呼叫一次。

### 優點與代價

Process 模型最大的優點是**隔離**。每個子行程有自己的位址空間（第 23 章），一個請求踩壞記憶體、甚至 segfault，只會死掉那一個子行程，其他連線不受影響。程式也很好寫：`handle_request` 就是普通的循序程式，不必擔心共享變數。

代價有三個。一是**成本**：fork 要複製 page table、descriptor table 等 kernel 資料結構，即使有 copy-on-write（第 24 章），也比建立 thread 貴得多；在本機（macOS arm64）粗略量測，`fork` 加 `waitpid` 一次約 0.5–0.8 ms，`pthread_create` 加 `pthread_join` 約 15–35 µs，差了一個數量級以上（數字依平台、父行程大小與當下負載而變，只看量級）。二是**共享資訊困難**：子行程要回報統計數字、共用快取，都必須透過 pipe、共享記憶體、socket 這類 **IPC**（inter-process communication，行程間通訊），既麻煩又慢。三是**記憶體**：每個 process 至少有自己的 stack、heap 與 kernel 資料結構，一萬條連線就是一萬個 process。

真實系統中，process 模型仍然很常見：PostgreSQL 為每個 client 連線建立一個 backend process，每條連線的查詢都在自己的 process 裡用循序程式執行；OpenSSH 為每個登入 session fork 一個子行程，並刻意用權限分離讓處理網路輸入的子行程權限最小；Apache 的 prefork MPM 預先 fork 一批子行程，避免每條連線都付 fork 的成本。最後這個「預先建立、重複使用」的想法，會在 30.7 節以 thread pool 的形式再出現。

## 30.4 模型二：I/O multiplexing 與 event-driven server

### 核心想法：只在「確定不會卡住」時才做 I/O

Process 和 thread 模型都靠「多條控制流」解決塞車。I/O multiplexing（I/O 多工）走另一條路：**只用一條控制流，但絕不在某一條連線上傻等**。程式把所有要監看的 fd 交給 kernel，請 kernel 回報「哪些 fd 現在可以讀或寫而不會阻塞」，然後只處理那些 fd。

這個「問 kernel 誰準備好了」的系統呼叫，最早是 `select`：

```c
// not-runnable：select 版事件迴圈的骨架
fd_set all, ready;
FD_ZERO(&all);
FD_SET(listenfd, &all);
for (;;) {
    ready = all;                                   /* select 會改寫集合，每次要重設 */
    select(maxfd + 1, &ready, NULL, NULL, NULL);   /* 睡到至少一個 fd 可讀 */
    if (FD_ISSET(listenfd, &ready)) add_client(accept(listenfd, NULL, NULL), &all);
    for (int fd = 0; fd <= maxfd; fd++)
        if (fd != listenfd && FD_ISSET(fd, &ready)) handle_some_bytes(fd);  /* 只做一點就回來 */
}
```

`fd_set` 是一個位元陣列，第 k 個 bit 代表 fd k。`select` 會睡到集合中至少一個 fd 準備好，回來時把集合改寫成「準備好的那些」。對 listen socket 來說，「可讀」代表有新連線可以 `accept`；對一般連線來說，「可讀」代表有資料可以讀，或對方已經關閉（`read` 會回傳 0）。

### Event-driven：把每條連線變成狀態機

關鍵限制在 `handle_some_bytes`：它**只能處理現在已經到達的資料，然後立刻回到迴圈**。如果它呼叫一個會阻塞的 `read`，或花 2 秒解碼一張全景照，整個 server 就又變回 iterative server。

這帶來 event-driven 程式設計最大的負擔：每條連線的「進度」不能放在 stack 上的區域變數裡，因為函式每處理一小段就要 return。程式必須自己記住「這條連線讀到第幾個 byte、header 解析完了沒、回應寫出多少」。這種寫法叫 **state machine**（狀態機）：每條連線有一個狀態，每個 I/O 事件讓它從一個狀態轉移到另一個狀態。

```text
          每條連線的狀態機（HTTP 請求）
 ┌──────────────┐ 可讀：讀到部分 header ┌──────────────┐
 │ READING_HDR  │ ─────────────────────▶│ READING_HDR  │（還沒看到 \r\n\r\n）
 └──────┬───────┘                       └──────────────┘
        │ 可讀：header 讀完
        ▼
 ┌──────────────┐ 工作交給 worker      ┌──────────────┐ 可寫：寫出一部分
 │ PROCESSING   │ ─────────────────────▶│ WRITING_RESP │ ──┐
 └──────────────┘ （不能在迴圈裡做）    └──────┬───────┘ ◀─┘ 還沒寫完
                                               │ 全部寫完
                                               ▼
                                         ┌──────────┐
                                         │  CLOSED  │
                                         └──────────┘

 事件迴圈：poll/epoll_wait → 找到就緒的 fd → 依它的狀態做一小步 → 回到 poll
```

圖的上半部是一條連線的生命週期：讀 header 可能要好幾次「可讀」事件才讀完（第 28 章：TCP 是 byte stream，一次 `read` 不保證拿到完整訊息）；寫回應也可能要好幾次「可寫」事件（第 27 章的 short count）。下半部是事件迴圈本身：它一直重複同一件事，在所有連線的狀態機之間切換。注意 PROCESSING 狀態：真正的 CPU 密集工作（解碼、縮放）不能在事件迴圈裡做，否則會卡住所有連線；常見做法是把它交給另一組 worker thread，做完再通知事件迴圈。這正是後面「混合架構」的由來。

### select、poll、epoll

`select` 是 1980 年代的介面，有兩個嚴重限制。一是 `fd_set` 的大小固定為 `FD_SETSIZE`，在 Linux glibc 上是 1024，fd 編號大於等於 1024 就不能放進去（硬放會寫出陣列邊界）。二是每次呼叫都要把整個集合從 user space 複製到 kernel，kernel 掃過全部 fd，回來後程式又要再掃一次，成本和**監看的 fd 數量**成正比，而不是和**準備好的 fd 數量**成正比。

`poll` 改用 `struct pollfd` 陣列，拿掉了 1024 的上限，但每次呼叫仍然要傳入並掃描整個陣列。Linux 的 `epoll` 和 BSD／macOS 的 `kqueue` 則把「要監看哪些 fd」這個集合**存在 kernel 裡**：程式用 `epoll_ctl` 增刪 fd，之後每次 `epoll_wait` 只回傳準備好的那些。

做一個簡單的估算。`thumbd` 前面的 nginx 有 10,000 條 keep-alive 連線，某一時刻只有 50 條有新資料：

| 介面 | 每次等待要交給 kernel 的資料 | 每次等待的掃描量 | 10,000 條連線、50 條就緒時 |
|---|---|---|---|
| `select` | 整個 `fd_set` 位元陣列 | 所有 fd（直到 maxfd） | 不能用：fd 超過 1024 |
| `poll` | 整個 `pollfd` 陣列（每項 8 bytes） | 所有 fd | 每次複製約 80 KB、掃 10,000 項，只有 0.5% 有用 |
| `epoll`／`kqueue` | 不用傳集合，集合已在 kernel | 只有就緒的 fd | 回傳 50 項 |

`poll` 那一列的數字是這樣算的：`struct pollfd` 有一個 `int fd`、兩個 `short`，共 8 bytes；10,000 × 8 = 80,000 bytes。每次 `poll` 都要把這 80 KB 複製進 kernel，kernel 檢查 10,000 個 fd，程式回來後再掃 10,000 項找出那 50 個。`epoll_wait` 直接回傳 50 個就緒事件，工作量和就緒數成正比。這就是 1999 年 Dan Kegel 提出的 **C10K problem**（一台機器同時服務一萬條連線）最後的主流答案。

`epoll` 有兩種通知模式。**Level-triggered**（水平觸發，預設）：只要 fd 還有資料沒讀完，每次 `epoll_wait` 都會再回報它，和 `poll` 的語意一樣，比較不容易寫錯。**Edge-triggered**（邊緣觸發，`EPOLLET`）：只在 fd 的狀態有變化（例如有新資料到達）時通知，已經通知過、但還沒讀完的資料不會再被回報，程式必須把 fd 設成 nonblocking，並且一直讀到 `read` 回傳 `EAGAIN` 為止，否則剩下的資料永遠不會再被通知。Linux 5.1 之後還有 `io_uring`，它不是「通知你何時可以讀」，而是「你把讀寫請求排進佇列，kernel 做完再通知你」，屬於另一種非同步 I/O 模型。

### 優點與代價

Event-driven 的優點是**省**：一條控制流、一個 stack，一萬條連線只是一萬個小小的狀態 struct，沒有 context switch，也沒有 thread 之間的同步問題，因為同一時間只有一段程式在動共享資料。除錯也相對單純：用 gdb 停下來，只有一個 stack trace 要看。

代價是**程式難寫**：所有邏輯都要拆成「收到事件 → 推進一步 → return」，原本十行的循序程式可能變成分散在好幾個 callback 裡的狀態轉移。而且**任何一個阻塞操作都會卡住全部連線**：在事件迴圈裡呼叫一次同步的 DNS 查詢、一次磁碟讀取、一個慢的函式庫，就重演了 30.1 節的事故。最後，單一事件迴圈只能用一個核心，要用多核心就得開多個事件迴圈。

真實系統的例子：nginx 是「多個 worker process，每個 process 一個 epoll 事件迴圈」；Redis 用單一事件迴圈執行所有命令（6.0 版之後可以另開 I/O thread 處理網路讀寫，但命令本身仍在主迴圈執行），所以一個慢命令（例如對大集合做 `KEYS *`）會卡住所有 client；Node.js 的 JavaScript 程式跑在 libuv 的事件迴圈上，檔案 I/O 與 DNS 這類沒有好的非阻塞介面的操作，交給背後的 thread pool 做。

## 30.5 模型三：Thread-based server

### Thread 是什麼

**Thread**（執行緒）是在同一個 process 裡執行的一條邏輯控制流。它結合了前兩個模型的特點：像 process 一樣由 kernel 自動排程（不必自己寫狀態機）；又像 I/O multiplexing 一樣，所有 thread 共享同一個位址空間（不需要 IPC）。

每個 thread 有自己的 **thread context**（執行緒情境）：thread ID、stack、stack pointer、PC、通用暫存器與 condition codes。除此之外的東西全部共享：程式碼、全域變數、heap、共享函式庫、打開的 file descriptor。

```text
 一個有三個 thread 的 process 的位址空間
 ┌─────────────────────────────┐ 高位址
 │ main thread 的 stack         │ ← main thread 的 %rsp
 ├─────────────────────────────┤
 │ thread 1 的 stack            │ ← thread 1 的 %rsp（pthread_create 時配置）
 │ （guard page）               │
 ├─────────────────────────────┤
 │ thread 2 的 stack            │ ← thread 2 的 %rsp
 │ （guard page）               │
 ├─────────────────────────────┤
 │ 共享函式庫（libc、libjpeg）   │ ┐
 │ heap（malloc 的記憶體）       │ │ 所有 thread 共享，
 │ .data／.bss（全域變數）       │ │ 誰都能讀寫
 │ .text（程式碼）               │ ┘
 └─────────────────────────────┘ 低位址
 kernel 為每個 thread 另存：暫存器、PC、TID；fd table 整個 process 一份
```

這張圖要讀出兩件事。第一，每個 thread 的 stack 只是同一個位址空間裡的不同區域，彼此之間有一頁 **guard page**（不可存取的頁，stack 用超過時觸發 segfault，而不是悄悄踩到隔壁 thread 的 stack）。所以「stack 是私有的」只是慣例：如果 thread 1 把自己 stack 上變數的位址交給 thread 2，thread 2 完全可以讀寫它。第 31 章會從這裡出發，精確定義「哪些變數是共享的」。第二，thread 之間沒有 process 那種「父子」層級關係，同一個 process 的 thread 是一個對等的群組（peer），任何一個 thread 都可以 join 另一個 thread。

Thread 的 context 比 process 小得多：切換 thread 不必換 page table（同一個位址空間），建立 thread 不必複製位址空間。這就是 30.3 節量到的一個數量級差距。

### Posix threads：建立、等待、分離

C 程式用 **Pthreads**（POSIX threads）這組標準 API 操作 thread：

| 函式 | 作用 | 要注意的地方 |
|---|---|---|
| `pthread_create(&tid, attr, fn, arg)` | 建立 thread，從 `fn(arg)` 開始執行 | 失敗時**回傳錯誤碼**，不設定 `errno`、也不回傳 −1 |
| `pthread_join(tid, &ret)` | 等 `tid` 結束，取回 `fn` 的回傳值並回收資源 | 只能等一個指定的 thread，沒有「等任何一個」的版本 |
| `pthread_detach(tid)` | 宣告這個 thread 結束時自動回收，不會有人 join | detach 之後就不能再 join |
| `pthread_exit(ret)` | 結束目前的 thread | main thread 呼叫它，會等其他 thread 結束才結束 process |
| `pthread_self()` | 取得自己的 thread ID | 型別是 `pthread_t`，不一定是整數 |
| `exit()` 或 `main` return | 結束**整個 process** 與所有 thread | 最常見的「背景 thread 莫名消失」原因 |

Thread 預設是 **joinable**（可被等待）：結束後它的資源（例如 stack）會留著，直到有人 `pthread_join` 它，類似 process 的 zombie。Server 裡處理連線的 thread 沒有人會去 join，所以必須 detach，否則每處理一條連線就漏掉一份 thread 資源，長時間執行後就無法再建立新 thread。

Thread 的 stack 大小由 attribute 決定。在本機 macOS arm64 實測，新 thread 的預設 stack 是 512 KiB；Linux glibc 則在程式啟動時的 `ulimit -s`（`RLIMIT_STACK`）不是 unlimited 時沿用它，常見是 8 MiB；若是 unlimited，改用各架構內建的預設值（x86-64 是 2 MiB）。8 MiB 只是預留的虛擬位址範圍，真正佔用的實體記憶體只有用到的頁（第 23 章），所以 10,000 個 thread 的 VSZ 會高達約 80 GB，RSS 卻小得多。這也是第 23 章故事裡 VIRT 遠大於 RES 的原因之一。

### Thread-based server 與傳參數的陷阱

```c
// not-runnable：thread-based server 的骨架
static void *serve(void *arg) {
    int connfd = (int)(intptr_t)arg;    /* 把 fd 的「值」直接塞在指標裡傳進來 */
    pthread_detach(pthread_self());     /* 沒有人會 join 我，結束時自動回收 */
    handle_request(connfd);
    close(connfd);                      /* 和 process 模型不同：只有一份 fd，關一次就好 */
    return NULL;
}

for (;;) {
    int connfd = accept(listenfd, NULL, NULL);
    pthread_t tid;
    pthread_create(&tid, NULL, serve, (void *)(intptr_t)connfd);
}
```

這裡最經典的 bug，是把 `&connfd` 傳給新 thread：

```c
// not-runnable：錯誤示範
int connfd = accept(listenfd, NULL, NULL);
pthread_create(&tid, NULL, serve, &connfd);   /* 傳的是 main thread stack 上同一個變數的位址 */
/* serve 裡：int fd = *(int *)arg;  可能讀到下一次 accept 寫入的新值 */
```

問題在於時間差：新 thread 什麼時候開始執行、什麼時候讀 `*arg`，完全由排程決定。如果 main thread 在新 thread 讀取之前又 `accept` 了下一條連線，`connfd` 已經被改寫，兩個 thread 會處理同一條連線，而另一條連線沒人管、fd 也永遠不會被關。這是一種 **race**（競爭條件）：程式的正確性取決於兩條控制流誰先執行到某一點。它通常在測試時不出現，在 production 高流量時才出現。正確做法是傳值（如上面的 `intptr_t` 轉型），或 `malloc` 一塊專屬記憶體給新 thread，由新 thread 負責 `free`。

另一個差異：process 模型中父子各有一份 fd，**兩邊都要關**；thread 模型中整個 process 只有一份 fd table，**只能關一次**。在 thread 模型裡多關一次，可能關掉另一個 thread 剛好拿到同一個編號的新連線，這種 bug 極難追查。

### 在 Linux 上，thread 長什麼樣

Linux kernel 並沒有一個獨立的「thread」物件。glibc 的 `pthread_create` 底層呼叫 `clone` 系統呼叫，建立一個和原本 process 共享位址空間、fd table、signal handler 的 **task**。在 kernel 眼中每個 thread 都是一個 task，有自己的 TID；同一個 process 的所有 task 共用一個 TGID（thread group ID），也就是使用者看到的 PID。所以在 Linux 上：

- `ps -L -p <PID>` 或 `top -H -p <PID>` 會列出每個 thread，各自的 CPU 使用率分開算。
- `/proc/<PID>/task/` 底下每個目錄是一個 thread。
- `gdb -p <PID>` 之後用 `thread apply all bt` 可以一次看所有 thread 的 stack trace，這是排查「server 卡住了」最有用的第一個指令。

## 30.6 三種模型的比較

把三種模型放在一起：

| 面向 | Process-based | I/O multiplexing（event-driven） | Thread-based |
|---|---|---|---|
| 控制流 | 每連線一個 process | 一條（或每核一條） | 每連線（或每 worker）一個 thread |
| 誰負責排程 | kernel | 程式自己的事件迴圈 | kernel |
| 位址空間 | 各自獨立 | 一個 | 共享一個 |
| 共享資料 | 困難，要 IPC | 容易，且同一時間只有一段程式在動 | 容易，但必須同步（第 31 章） |
| 一個請求當機 | 只死一個子行程 | 整個 server 死 | 整個 server 死 |
| 一個請求阻塞或很慢 | 不影響其他人 | **卡住所有連線** | 不影響其他人（但佔住一個 thread） |
| 每條連線的成本 | 高（process、page table） | 很低（一個狀態 struct） | 中（stack、kernel task） |
| 程式寫法 | 循序，最簡單 | 狀態機，最難 | 循序，但要處理 race |
| 能否用多核 | 能 | 單一迴圈不能，要多個迴圈 | 能 |
| 代表系統 | PostgreSQL、OpenSSH、Apache prefork | nginx（每 worker）、Redis、Node.js | Apache worker、許多 Java server、`thumbd` |

讀這張表時有兩個重點。第一，沒有一種模型全面勝出：process 用成本換隔離，event-driven 用程式複雜度換規模，thread 用同步的風險換寫法簡單。第二，真實的高效能系統幾乎都是**混合**的。`thumbd` 自己就是一個例子：

```text
 拾光相簿的請求路徑（混合架構）
 client ──▶ nginx：每個 worker process 一個 epoll 迴圈
              │     （一萬條 keep-alive 連線，大多閒置；只做 HTTP 轉送，不做重活）
              ▼
            thumbd：一個 acceptor thread ──▶ 有界 queue ──▶ 16 個 worker thread
                                                         （解碼、縮放：CPU 與磁碟 I/O）
              │
              └──▶ 少數罕見格式：fork/exec 外部轉檔工具（process 隔離，見第 21 章）
```

nginx 擅長「大量閒置連線」，用 event-driven；`thumbd` 的工作是「少量但很重的計算」，用 thread pool；不可信任、容易當機的外部工具則放在獨立 process 裡，當掉也不會拖垮 `thumbd`。同一條請求路徑上，三種模型各司其職。

## 30.7 Thread pool 與 prethreading

### 為什麼不要「每個請求一個 thread」

30.5 節的 thread-based server 每接受一條連線就建立一個 thread。這有兩個問題。一是建立與銷毀 thread 雖然比 fork 便宜，仍然是每個請求都要付的固定成本。更嚴重的是第二個：**thread 的數量沒有上限**。流量暴增時，server 會建立幾千個 thread，每個都在搶 CPU 和記憶體，context switch 越來越多，每個請求都變慢，變慢又讓同時在處理的請求更多，最後記憶體耗盡或 thread 數達到上限。系統在過載時應該「拒絕一部分、服務好其他的」，而不是「接受全部、全部做不好」。

**Prethreading**（預先建立 thread）解決這兩個問題：server 啟動時就建立固定數量的 **worker thread**，它們組成一個 **thread pool**（執行緒池）。主 thread 只負責 `accept`，把 connfd 放進一個共享的 queue；worker 從 queue 取出 connfd 來服務，做完再回去取下一個。

```text
                   ┌───────── 有界 queue（容量 4）─────────┐
 acceptor thread   │  ┌────┬────┬────┬────┐               │    worker 1 ─▶ 處理 fd 9
 accept() ──put──▶ │  │ 12 │ 13 │ 14 │    │ ──take──▶     │ ─▶ worker 2 ─▶ 處理 fd 10
  （producer）      │  └────┴────┴────┴────┘               │    worker 3 ─▶ 處理 fd 11
                   │   queue 滿 → producer 等待             │    worker 4 ─▶ （等 queue 有東西）
                   │   queue 空 → consumer 等待             │    （consumers）
                   └───────────────────────────────────────┘
```

這是經典的 **producer-consumer**（生產者－消費者）結構：acceptor 是 producer，worker 是 consumer，中間的 queue 是共享資源。它有兩個等待條件：queue 滿時 producer 必須等，queue 空時 consumer 必須等。這兩個等待怎麼正確實作（semaphore 或 condition variable），是第 31 章的主題；這一章先關心它的架構意義。

### 有界 queue 就是 backpressure

Queue 一定要**有上限**。假設每秒進來 100 個請求，worker 每秒只能處理 80 個。若 queue 無上限，表面上沒有任何請求被拒絕，實際上 queue 每秒多 20 個，排隊時間每秒都在變長；client 等不及而 timeout 之後，worker 仍然在處理那些已經沒人要的請求，浪費的工作讓情況更糟，直到記憶體耗盡。

有界 queue 把「過載」變成一個看得見、可以處理的事件：queue 滿時 producer 會等，等待讓 `accept` 變慢，連線在 kernel 的 backlog 裡排隊，backlog 也滿了以後 client 會連線失敗或逾時，上游（例如 nginx 或 load balancer）就能察覺並把流量導到別台機器。這種「下游處理不及時，壓力沿著呼叫鏈往回傳」的機制叫 **backpressure**（背壓）。實務上 producer 不一定要無限期等，也可以設定等待上限，或直接回應 503，策略要明確設計，而不是讓無限 queue 默默吃掉記憶體。

### 手算：worker 要開幾個？

Worker 太少，請求在 queue 裡排隊；太多，浪費記憶體並增加 context switch。估算的工具是 **Little's law**（利特爾法則）：一個穩定系統中，平均同時在系統裡的工作數 L，等於平均到達率 λ 乘以每件工作在系統裡的平均時間 W，也就是 L = λ × W。

用 `thumbd` 的真實數字算一次。尖峰時每秒 400 個請求；每個請求平均處理 50 ms，其中 CPU 運算（解碼、縮放）10 ms，其餘 40 ms 在等磁碟讀原圖與寫回 client。機器有 8 個核心。

| 步驟 | 計算 | 結果 |
|---|---|---|
| 1. 同時在處理中的請求數 | L = λ × W = 400 /s × 0.050 s | 平均 20 個 |
| 2. 需要的 CPU | 400 /s × 0.010 s | 平均 4 個核心忙碌 |
| 3. CPU 使用率 | 4 ÷ 8 核 | 50% |
| 4. Worker 數下限 | 至少要能同時容納 L 個請求 | 20 個 |
| 5. 加上波動餘裕 | 尖峰常為平均的 1.5–2 倍（依服務而定） | 約 32–40 個 |

步驟 1 告訴我們，平均隨時有 20 個請求「正在被處理」（包含在等 I/O 的），所以 worker 少於 20 個時，queue 一定會持續累積。步驟 2 和 3 確認 CPU 不是瓶頸：就算 worker 開到 40 個，同時真的在用 CPU 的平均也只有 4 個。

對照兩種極端情況：如果工作**全是 CPU**（W 全部是運算），worker 數超過核心數不會更快，只會增加切換，通常設成核心數左右；如果工作**大多在等 I/O**，worker 數可以遠大於核心數，由 Little's law 決定。工作上不要只寫死一個數字，而是量測 W 和 λ、觀察 queue 長度與 worker 忙碌比例，再調整。

## 30.8 `thumbd` 的演進：從單執行緒到 thread pool

把這一章的模型套回 `thumbd` 的歷史，每一版都是為了解決上一版的具體問題：

| 版本 | 結構 | 解決了什麼 | 留下什麼問題 |
|---|---|---|---|
| v0 | iterative：`accept` → 處理 → `close` | 最簡單 | 一張全景照卡住所有人（30.1 節） |
| v1 | 每連線 `fork` 一個子行程 | 慢請求不再阻塞別人；子行程當機只死一個 | 每次 fork 的成本；快取無法在子行程間共享；忘記回收造成 zombie |
| v2 | 每連線一個 detached thread | 建立成本降低；縮圖快取可以共享 | 流量暴增時 thread 數量失控；共享快取開始出現 race（第 31 章） |
| v3 | acceptor ＋ 有界 queue ＋ 固定 worker pool | thread 數量固定；過載時有 backpressure | 需要正確的同步；worker 數要依量測調整（第 32 章） |

全景照事故之後，老周和小安做了兩件事：把 v0 的殘留路徑（一個管理用的 endpoint 仍然是 iterative 處理）改成走 thread pool；並把全景照這類超大圖導到一個獨立、worker 較少的 pool，讓它們不會佔滿一般縮圖的 worker。後者是 **bulkhead**（艙壁隔離）的做法：用分開的資源池隔離不同類型的工作，一類工作過載時，不會拖垮另一類。

## 30.9 動手做：三種 server，量出差別

### 程式一：iterative、process、thread 的總耗時

這段程式在同一個 process 裡依序啟動三種 server。每種 server 都用 `fork` 建立 8 個 client process 連進來，每個請求模擬 100 ms 的處理（用 `usleep` 代表等磁碟或解碼），最後印出 8 個請求全部完成的時間。

```c
#include <arpa/inet.h>
#include <netinet/in.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define NCLIENT 8
#define WORK_US 100000              /* 模擬每張圖要 100 ms 的解碼／讀檔 */

static double now(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static void handle(int fd) {        /* 讀一行請求、做事、回覆 */
    char buf[64];
    if (read(fd, buf, sizeof buf) > 0) {
        usleep(WORK_US);
        write(fd, "OK\n", 3);
    }
    close(fd);
}

static void *thread_main(void *arg) {
    int fd = (int)(long)arg;        /* 用值傳遞，不要傳 &connfd（見 30.5 節） */
    handle(fd);
    return NULL;
}

static int open_listen(int *port) {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in a = {.sin_family = AF_INET, .sin_addr.s_addr = htonl(INADDR_LOOPBACK)};
    socklen_t len = sizeof a;
    bind(fd, (struct sockaddr *)&a, sizeof a);          /* port 0：讓 kernel 挑一個空的 */
    listen(fd, 64);
    getsockname(fd, (struct sockaddr *)&a, &len);
    *port = ntohs(a.sin_port);
    return fd;
}

static void client(int port) {      /* 每個 client 是獨立的 process */
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in a = {.sin_family = AF_INET, .sin_port = htons(port),
                            .sin_addr.s_addr = htonl(INADDR_LOOPBACK)};
    char buf[8];
    if (connect(fd, (struct sockaddr *)&a, sizeof a) == 0) {
        write(fd, "GET /thumb\n", 11);
        read(fd, buf, sizeof buf);
    }
    _exit(0);
}

int main(void) {
    const char *names[] = {"iterative（一次一個）", "process（每連線 fork）", "thread（每連線一個 thread）"};
    for (int mode = 0; mode < 3; mode++) {
        int port, lfd = open_listen(&port);
        double t0 = now();
        for (int i = 0; i < NCLIENT; i++)
            if (fork() == 0) client(port);
        pthread_t tid[NCLIENT];
        for (int i = 0; i < NCLIENT; i++) {
            int cfd = accept(lfd, NULL, NULL);
            if (mode == 0) {
                handle(cfd);
            } else if (mode == 1) {
                if (fork() == 0) { close(lfd); handle(cfd); _exit(0); }
                close(cfd);         /* 父程序一定要關自己那份 connfd */
            } else {
                pthread_create(&tid[i], NULL, thread_main, (void *)(long)cfd);
            }
        }
        if (mode == 2)
            for (int i = 0; i < NCLIENT; i++) pthread_join(tid[i], NULL);
        while (wait(NULL) > 0) {}   /* 回收 client 與 handler 子程序，避免 zombie */
        printf("%s：%d 個請求共 %.3f 秒\n", names[mode], NCLIENT, now() - t0);
        close(lfd);
    }
    return 0;
}
```

在 macOS arm64（Apple clang 21）上執行兩次：

```text
iterative（一次一個）：8 個請求共 0.844 秒
process（每連線 fork）：8 個請求共 0.122 秒
thread（每連線一個 thread）：8 個請求共 0.112 秒
```

```text
iterative（一次一個）：8 個請求共 0.829 秒
process（每連線 fork）：8 個請求共 0.130 秒
thread（每連線一個 thread）：8 個請求共 0.109 秒
```

逐步解讀：

1. **Iterative 約 0.83 秒，剛好是 8 × 100 ms 再加一點額外開銷。** 每個請求必須等前一個做完，總時間是所有請求時間的總和。這就是 30.1 節全景照事故的縮小版。
2. **Process 和 thread 都約 0.11–0.13 秒，接近單一請求的 100 ms。** 8 個請求的等待重疊在一起，總時間由最慢的那一個決定，而不是總和。
3. 這裡的工作是「等待」（`usleep`），不吃 CPU，所以 8 條控制流即使只有一個核心也能完全重疊。如果把 `usleep` 換成純計算，在 8 核以上的機器仍會加速，在單核機器上則不會：concurrency 解決的是「等待重疊」，parallelism 才解決「計算加速」。
4. 注意 process 版本的父行程 `close(cfd)`，以及最後的 `while (wait(NULL) > 0)`：拿掉前者，父行程每處理一條連線就多留一個 fd；在真實 server 裡，要讀到 EOF 才算完成的 client 還會一直等不到連線關閉（這個程式的 client 讀到 `OK` 就結束，所以看不出來）。拿掉後者，子行程會變成 zombie。thread 版本則是 `pthread_join`，因為這裡需要知道它們全部完成；長期執行的 server 會改用 detach。
5. 兩次執行的數字略有不同，這是正常的：排程、process 建立時間都會波動。比較時要看數量級與趨勢，不要比較小數點第三位。

### 程式二：一條控制流同時服務三個 client

第二段程式（存成 `evloop.c`）用 `poll` 寫一個最小的事件迴圈。三個 client 各自分兩段送資料，中間停 60 ms，模擬慢速上傳；server 只有一條控制流，卻能讓三條連線交錯進行。每條連線的進度存在 `struct conn` 裡，這就是 30.4 節說的狀態機。

```c
#include <arpa/inet.h>
#include <netinet/in.h>
#include <poll.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <unistd.h>

#define NCLIENT 3
#define MAXFD 16

/* event-driven server 的關鍵：每條連線的「進度」要自己存起來 */
struct conn { int fd; int bytes; int chunks; };

static void client(int port, int id) {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in a = {.sin_family = AF_INET, .sin_port = htons(port),
                            .sin_addr.s_addr = htonl(INADDR_LOOPBACK)};
    if (connect(fd, (struct sockaddr *)&a, sizeof a) != 0) _exit(1);
    usleep(10000 + 20000 * id);                 /* 錯開三個 client 的起點 */
    for (int k = 0; k < 2; k++) {               /* 分兩段送，中間停 60 ms，模擬慢速上傳 */
        if (k == 1) usleep(60000);
        char msg[32];
        int n = snprintf(msg, sizeof msg, "c%d-part%d;", id, k);
        write(fd, msg, n);
    }
    close(fd);
    _exit(0);
}

int main(void) {
    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in a = {.sin_family = AF_INET, .sin_addr.s_addr = htonl(INADDR_LOOPBACK)};
    socklen_t len = sizeof a;
    bind(lfd, (struct sockaddr *)&a, sizeof a);
    listen(lfd, 16);
    getsockname(lfd, (struct sockaddr *)&a, &len);
    for (int i = 0; i < NCLIENT; i++)
        if (fork() == 0) client(ntohs(a.sin_port), i);

    struct pollfd pfd[MAXFD] = {{.fd = lfd, .events = POLLIN}};
    struct conn st[MAXFD] = {{0}};
    int nfds = 1, closed = 0;
    while (closed < NCLIENT) {
        poll(pfd, nfds, -1);                    /* 唯一會睡覺的地方 */
        if (pfd[0].revents & POLLIN) {          /* listen fd 可讀 = 有新連線 */
            int cfd = accept(lfd, NULL, NULL);
            pfd[nfds] = (struct pollfd){.fd = cfd, .events = POLLIN};
            st[nfds] = (struct conn){.fd = cfd};
            printf("accept  → 新連線 fd %d（目前監看 %d 個 fd）\n", cfd, nfds + 1);
            nfds++;
        }
        for (int i = 1; i < nfds; i++) {
            if (pfd[i].fd < 0 || !(pfd[i].revents & (POLLIN | POLLHUP))) continue;
            char buf[64];
            ssize_t n = read(pfd[i].fd, buf, sizeof buf - 1);   /* 不會阻塞：poll 說它可讀 */
            if (n > 0) {
                buf[n] = '\0';
                st[i].bytes += n;
                st[i].chunks++;
                printf("fd %d 可讀 → 讀到 \"%s\"（這條連線累計 %d bytes）\n", pfd[i].fd, buf, st[i].bytes);
            } else {                            /* n == 0：對方關閉連線 */
                printf("fd %d EOF   → 共 %d 段、%d bytes，關閉\n", pfd[i].fd, st[i].chunks, st[i].bytes);
                close(pfd[i].fd);
                pfd[i].fd = -1;                 /* poll 會忽略負的 fd */
                closed++;
            }
        }
    }
    while (wait(NULL) > 0) {}
    return 0;
}
```

在 macOS arm64 上執行：

```text
accept  → 新連線 fd 4（目前監看 2 個 fd）
accept  → 新連線 fd 5（目前監看 3 個 fd）
accept  → 新連線 fd 6（目前監看 4 個 fd）
fd 4 可讀 → 讀到 "c0-part0;"（這條連線累計 9 bytes）
fd 5 可讀 → 讀到 "c1-part0;"（這條連線累計 9 bytes）
fd 6 可讀 → 讀到 "c2-part0;"（這條連線累計 9 bytes）
fd 4 可讀 → 讀到 "c0-part1;"（這條連線累計 18 bytes）
fd 4 EOF   → 共 2 段、18 bytes，關閉
fd 5 可讀 → 讀到 "c1-part1;"（這條連線累計 18 bytes）
fd 5 EOF   → 共 2 段、18 bytes，關閉
fd 6 可讀 → 讀到 "c2-part1;"（這條連線累計 18 bytes）
fd 6 EOF   → 共 2 段、18 bytes，關閉
```

逐步解讀：

1. 三個 client 幾乎同時連上，事件迴圈連續三次發現 listen socket 可讀，各 `accept` 一次。fd 從 4 開始，是因為 0、1、2 是標準輸入輸出，3 是 listen socket。
2. 接下來三條連線的第一段資料分別在約 10、30、50 ms 到達，server 依序處理；第二段在約 70、90、110 ms 到達。輸出顯示 c0 的第二段排在 c2 的第一段之後：**三條連線同時在進行中，由同一條控制流交錯服務**。如果這是 iterative server，c1 必須等 c0 整條連線結束才能開始。
3. `read` 永遠不會阻塞，因為只有 `poll` 回報可讀的 fd 才去讀。整支程式唯一會睡覺的地方是 `poll` 本身。
4. `read` 回傳 0 代表對方關閉，這時要 `close` 並把該項的 fd 設成 −1，`poll` 會忽略負的 fd。真正的 server 還要把陣列空位回收再利用。
5. 想像把 `read` 之後的處理改成 `usleep(2000000)`：三條連線全部會被卡住 2 秒。這就是事件迴圈「不能有阻塞操作」的原因，可以在練習 2 親自驗證。

### 程式三：固定大小的 thread pool

第三段程式（存成 `pool.c`）是 30.7 節 thread pool 的最小版本：容量 4 的有界 queue、1 到 8 個 worker，處理 16 個各需 50 ms 的工作。`put` 和 `take` 用的 mutex 與 condition variable，第 31 章會逐行解釋為什麼要這樣寫；這裡先觀察行為。

```c
#include <pthread.h>
#include <stdio.h>
#include <time.h>
#include <unistd.h>

#define NJOBS 16
#define QCAP 4                       /* 有界 queue：最多排 4 個工作 */

static int queue[QCAP], head, tail, count, producer_waits;
static pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;

static void put(int job) {           /* producer：main thread（相當於 accept 迴圈） */
    pthread_mutex_lock(&mu);
    while (count == QCAP) {          /* queue 滿：等，這就是 backpressure */
        producer_waits++;
        pthread_cond_wait(&not_full, &mu);
    }
    queue[tail] = job; tail = (tail + 1) % QCAP; count++;
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&mu);
}

static int take(void) {              /* consumer：worker thread */
    pthread_mutex_lock(&mu);
    while (count == 0) pthread_cond_wait(&not_empty, &mu);
    int job = queue[head]; head = (head + 1) % QCAP; count--;
    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&mu);
    return job;
}

static void *worker(void *arg) {
    (void)arg;
    for (;;) {
        int job = take();
        if (job < 0) return NULL;    /* 負數是「下班」訊號 */
        usleep(50000);               /* 模擬一張縮圖：50 ms，大多在等 I/O */
    }
}

static double seconds(void) {       /* 單調時鐘：不受系統時間調整影響 */
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return (double)t.tv_sec + t.tv_nsec * 1e-9;
}

int main(void) {
    int sizes[] = {1, 2, 4, 8};
    for (int s = 0; s < 4; s++) {
        int n = sizes[s];
        pthread_t tid[8];
        producer_waits = 0;
        double t0 = seconds();
        for (int i = 0; i < n; i++) pthread_create(&tid[i], NULL, worker, NULL);  /* prethreading */
        for (int j = 0; j < NJOBS; j++) put(j);
        for (int i = 0; i < n; i++) put(-1);                 /* 每個 worker 一個下班訊號 */
        for (int i = 0; i < n; i++) pthread_join(tid[i], NULL);
        printf("%d 個 worker：%d 個工作耗時 %.3f 秒，producer 因 queue 滿等待 %d 次\n",
               n, NJOBS, seconds() - t0, producer_waits);
    }
    return 0;
}
```

在 macOS arm64 上執行兩次：

```text
1 個 worker：16 個工作耗時 0.829 秒，producer 因 queue 滿等待 13 次
2 個 worker：16 個工作耗時 0.411 秒，producer 因 queue 滿等待 14 次
4 個 worker：16 個工作耗時 0.210 秒，producer 因 queue 滿等待 11 次
8 個 worker：16 個工作耗時 0.107 秒，producer 因 queue 滿等待 9 次
```

```text
1 個 worker：16 個工作耗時 0.843 秒，producer 因 queue 滿等待 13 次
2 個 worker：16 個工作耗時 0.436 秒，producer 因 queue 滿等待 14 次
4 個 worker：16 個工作耗時 0.205 秒，producer 因 queue 滿等待 13 次
8 個 worker：16 個工作耗時 0.105 秒，producer 因 queue 滿等待 13 次
```

逐步解讀：

1. **時間和 worker 數成反比**：16 × 50 ms ÷ worker 數，分別約 0.8、0.4、0.2、0.1 秒。這是 Little's law 的直接體現：每個工作 W = 50 ms，worker 數就是同時能處理的工作數 L，吞吐量 λ = L ÷ W。
2. **Producer 一直在等**：queue 只有 4 格，producer 放工作的速度遠快於 worker 消化的速度，所以很快就填滿，之後每放一個都要等一個 worker 取走。這正是 backpressure：producer 被自動放慢到 worker 的速度，記憶體不會無限增長。
3. 等待次數每次執行都略有不同（這兩次在 9 到 14 次之間），因為它取決於 producer 與 worker 誰先被排程，這是 thread 程式的常態：**行為的細節不可重現，但正確的程式在任何排程下結果都一樣**（16 個工作都做完）。
4. 下班訊號用 −1 表示，每個 worker 各放一個。這是 thread pool 優雅關閉的常見做法，也叫 poison pill：比從外面強制終止 thread 安全得多，因為 worker 會在兩個工作之間、而不是工作做到一半時離開。

## 30.10 在工作上怎麼用

### 情境一：替新服務挑選並行模型

設計一個新服務或審查別人的設計時，用這個流程判斷：

```text
 每條連線大多在閒置（長連線、WebSocket、推播）？
   ├─ 是 → 連線數上萬？
   │        ├─ 是 → event-driven（epoll／kqueue，或用現成框架）
   │        └─ 否 → thread pool 也可以，選團隊熟的
   └─ 否 → 每個請求是 CPU 重活或會呼叫阻塞的函式庫？
            ├─ 是 → thread pool（前面可以再加 event-driven 的接入層）
            └─ 否 → event-driven 或 thread pool 都可以
 處理的資料不可信任、函式庫容易當機、需要權限分離？
   └─ 是 → 把那一部分放進獨立 process（worker process、sandbox、子程序）
```

在使用 Go、Java 21 的 virtual thread、Python asyncio 這類執行環境時，底層仍是這三種模型的組合：Go 的 goroutine 由 runtime 排程到少量 OS thread 上，網路 I/O 背後是 epoll；asyncio 是 event-driven，在 coroutine 裡呼叫同步的阻塞函式會卡住整個事件迴圈，和 30.4 節講的問題一模一樣。

### 情境二：服務卡住了，但 CPU 不高

這是 thread pool 服務最常見的事故型態：所有 worker 都在等某個慢的下游（資料庫、外部 API、NFS 上的檔案），新請求在 queue 裡排隊。排查步驟：

```bash
# 1. 看有幾個 thread、各自在做什麼狀態（Linux）
ps -L -o tid,stat,wchan:20,comm -p "$(pidof thumbd)"
top -H -p "$(pidof thumbd)"

# 2. 一次抓所有 thread 的 stack trace，看大家卡在哪個函式
gdb -p "$(pidof thumbd)" -batch -ex "thread apply all bt" > /tmp/thumbd-bt.txt

# 3. 看 fd 與連線：是不是有大量連線在等下游
ls /proc/"$(pidof thumbd)"/fd | wc -l
ss -tnp | grep thumbd
```

如果 `thread apply all bt` 顯示 16 個 worker 中有 16 個都停在 `read` 一個 NFS 檔案，問題就不在 `thumbd` 的 CPU，而是 I/O 下游。解法通常是替下游呼叫設定 timeout、把不同下游的工作分到不同的 pool（bulkhead），而不是盲目加 worker。

### 情境三：thread pool 的監控指標

一個 thread pool 至少要輸出這些指標，否則出事時無從判斷：

| 指標 | 意義 | 異常時代表 |
|---|---|---|
| queue 長度 | 等待中的工作數 | 持續增長：處理速度跟不上到達速度 |
| queue 等待時間 | 工作從放入到被取走的時間 | 延遲主要花在排隊，而不是處理 |
| 忙碌 worker 數 | 正在處理工作的 worker | 長期等於上限：容量不足或下游卡住 |
| 拒絕次數 | queue 滿而被拒絕或逾時的工作 | 已經在過載，backpressure 正在生效 |
| 每個工作的處理時間分布 | p50、p99 | p99 突增：少數慢請求佔住 worker |

### 情境四：event-driven 程式碼審查清單

審查 Node.js、Redis 模組、nginx 模組或自己寫的 epoll 迴圈時，逐項檢查：

- 事件 callback 裡有沒有同步的磁碟 I/O、DNS 查詢、`sleep`、大量計算？
- 所有 socket 是否都設成 nonblocking？使用 edge-triggered 時，是否一直讀到 `EAGAIN`？
- 每條連線的狀態 struct 在連線關閉時有沒有釋放（event-driven 版的 memory leak）？
- 對單一連線的 buffer 有沒有大小上限，避免一個 client 送超大 header 吃光記憶體（第 29 章）？
- 寫回應遇到 short write 時，是否改成監看「可寫」事件，而不是在迴圈裡重試？

## 30.11 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| process-based server 的 fd 數持續上升，client 收不到 EOF | 父行程 fork 後沒有 `close(connfd)` | `ls /proc/PID/fd \| wc -l` 持續增加；`lsof -p PID` 看到大量 ESTABLISHED socket | fork 之後父行程立刻關閉 connfd，子行程關閉 listenfd |
| `ps` 看到大量 `<defunct>` 子行程 | 沒有回收子行程，或 SIGCHLD handler 只呼叫一次 `waitpid` | `ps -o pid,ppid,stat,comm` 看到 `Z` 狀態 | handler 裡用 `while (waitpid(-1, NULL, WNOHANG) > 0)` 迴圈回收 |
| 偶爾兩個 thread 處理同一條連線，另一條連線卡住 | 把 `&connfd` 傳給 `pthread_create` | 高並行壓測時重現；ThreadSanitizer 會報告 data race（第 31 章） | 傳值，或為每個 thread `malloc` 一份參數 |
| 長時間執行後 `pthread_create` 失敗（`EAGAIN`） | thread 沒有 detach 也沒有 join，資源不斷累積；或 thread 數無上限 | 檢查 `pthread_create` 的回傳值；`ps -L` 看 thread 數 | detach 或 join；改用固定大小的 thread pool |
| event-driven server 所有連線偶爾同時卡住數百 ms | 事件迴圈裡有阻塞操作 | 用 profiler 或 `strace -T` 找出迴圈中耗時的系統呼叫 | 把阻塞工作移到 worker thread；改用非阻塞 API |
| fd 超過 1024 之後 server 行為怪異或當機 | 使用 `select`，fd 超過 `FD_SETSIZE` | 檢查程式是否用 `select`；看當機時的 fd 編號 | 改用 `poll` 或 `epoll`／`kqueue` |
| 背景 thread 的工作做到一半就消失 | `main` return 或呼叫 `exit`，整個 process 結束 | 在 `main` 結尾加 log；檢查是否有 join | `main` 結束前 join 必要的 thread，或設計明確的關閉流程 |

## 30.12 動手練習

1. **延伸程式一**：把 `handle` 裡的 `usleep(WORK_US)` 換成一段約 100 ms 的純計算（例如一個大迴圈對陣列求和，記得用結果避免被最佳化掉）。三種模型的耗時會怎麼變？在你的機器上，process 與 thread 版本仍然接近 0.1 秒嗎？用核心數解釋結果。
2. **延伸程式二**：在 `evloop.c` 讀到資料之後加上 `usleep(200000)`，重新執行並記錄每一行輸出的時間（可用 `clock_gettime`）。說明為什麼一條慢的連線會拖慢其他兩條。
3. **手算**：一個 API 服務尖峰每秒 1,200 個請求，平均每個請求花 80 ms，其中 5 ms 是 CPU。用 Little's law 算出平均同時處理中的請求數，以及平均需要幾個核心。（答案：L = 1,200 × 0.08 = 96 個；CPU = 1,200 × 0.005 = 6 個核心。所以 worker 至少約 96 個，但 CPU 只要 6 核；若 worker 只開 16 個，queue 會持續累積。）
4. **延伸程式三**：把 `pool.c` 的 `QCAP` 改成 1 和 16，觀察 producer 等待次數與總時間。總時間為什麼幾乎不變？什麼情況下 queue 容量會影響延遲？
5. 在 Linux 上執行任何一個 thread pool 服務（例如 Java 應用或資料庫），用 `ps -L`、`top -H` 和 `/proc/PID/task` 找出它有幾個 thread，並用 `gdb -p` 的 `thread apply all bt`（或 Java 的 `jstack`）看它們分別在做什麼。
6. 讀 `select(2)`、`poll(2)` 與 `epoll(7)` 的 man page，用 `epoll` 改寫程式二（Linux 限定，第一行加 `// linux-only`），並比較兩者需要傳給 kernel 的資料。

## 本章重點整理

- Concurrency 是多個工作在時間上重疊，parallelism 是同一瞬間在多個硬體上執行；concurrency 讓等待重疊，parallelism 才讓計算加速。
- Iterative server 一次只服務一個 client，任何一個慢請求都會讓後面所有請求排隊，即使 CPU 很閒。
- Process-based server 每條連線 fork 一個子行程，隔離最好、程式最簡單；代價是建立成本高、共享資料要靠 IPC，而且父行程必須關閉 connfd 並回收子行程。
- I/O multiplexing 只用一條控制流，由 `select`、`poll`、`epoll` 或 `kqueue` 告訴程式哪些 fd 已經準備好，每條連線的進度要寫成狀態機。
- `select` 受 `FD_SETSIZE` 限制且成本與監看數成正比；`epoll`／`kqueue` 把監看集合存在 kernel，成本與就緒數成正比，是 C10K 問題的主流答案。
- Event-driven server 中任何一個阻塞操作都會卡住所有連線，CPU 重活必須移到事件迴圈之外。
- Thread 是同一個 process 內的控制流，各自有 stack 與暫存器，共享程式碼、heap、全域變數與 fd table；建立與切換都比 process 便宜。
- `pthread_create` 失敗時回傳錯誤碼；joinable thread 必須被 join，否則要 detach；`main` return 或 `exit` 會結束所有 thread。
- 傳 `&connfd` 給新 thread 是經典的 race，應該傳值或為每個 thread 配置專屬的參數。
- 三種模型各有取捨，真實系統通常混合使用：nginx 用多個事件迴圈，`thumbd` 用 thread pool，不可信任的外部工具放在獨立 process。
- Thread pool 預先建立固定數量的 worker，用 producer-consumer 的有界 queue 分配工作，既省下建立成本，也限制了過載時的資源用量。
- 有界 queue 提供 backpressure，把過載轉成可觀察、可處理的等待或拒絕，無界 queue 只是把問題延後成高延遲與記憶體耗盡。
- Worker 數可以用 Little's law（L = λ × W）估算：CPU 密集的工作約等於核心數，I/O 密集的工作可以遠大於核心數。

## 延伸問答

> [!question]- Q1. 單核心的機器上，開 8 個 thread 有沒有意義？
> 要看工作是在「等」還是在「算」。如果每個請求大部分時間在等磁碟、網路或下游服務，8 個 thread 可以讓這些等待互相重疊：一個 thread 在等 I/O 時，kernel 把 CPU 交給另一個 thread，總完成時間會大幅縮短。這是 concurrency 的好處，不需要多核心，30.9 節程式一用 `usleep` 模擬的正是這種情況。
>
> 如果工作是純計算，單核心一次只能執行一條指令流，8 個 thread 只是輪流使用同一顆 CPU，總時間不會變短，反而多了 context switch 與 cache 被互相擠掉的成本。所以「開多少 thread」的判斷依據是工作中等待與計算的比例，而不是單純越多越好。

> [!question]- Q2. 為什麼 process-based server 的父行程一定要 `close(connfd)`，而 thread-based server 卻只能關一次？
> fork 會複製 descriptor table，父子兩個 fd 指向同一個 open file table entry，該 entry 的 reference count 變成 2。kernel 只有在 count 降到 0 時才真正關閉 socket、送出 FIN。子行程服務完關掉自己那份只會讓 count 降到 1，如果父行程不關，連線永遠不會結束，父行程的 fd 也會一直累積直到耗盡。
>
> Thread 共享同一張 descriptor table，connfd 只有一份，count 是 1。服務的 thread 關一次就真正關閉了。如果別的 thread 再關一次同樣的編號，可能剛好關掉 kernel 已經重新分配給另一條新連線的 fd，造成極難追查的錯誤。兩種模型的差異，根源在於 fork 複製表、thread 共享表。

> [!question]- Q3. 你在 production 看到一個 Node.js 服務每隔幾分鐘所有請求延遲同時跳到 1 秒，CPU 也同時尖峰。最可能的原因是什麼？
> Node.js 的 JavaScript 程式跑在單一事件迴圈上，同一時間只有一段 callback 在執行。所有請求「同時」變慢，代表事件迴圈本身被卡住，而不是某些請求的下游慢；CPU 同時尖峰，代表卡住它的是一段同步的計算，例如對大 JSON 做 `JSON.parse`、同步壓縮、複雜的正規表示式，或一個排程任務在迴圈裡處理大量資料。
>
> 確認方式是在尖峰時用 profiler 取樣（或監控 event loop lag 指標），找出佔住迴圈的函式。修法是把重計算移到 worker thread 或獨立服務，或把它切成小塊分次執行。如果 CPU 沒有尖峰、只有延遲跳高，則要懷疑迴圈裡有同步 I/O 呼叫。

> [!question]- Q4. `select` 有什麼限制，為什麼 `epoll` 在大量連線時快得多？
> `select` 用固定大小的位元陣列表示 fd 集合，在 Linux glibc 上 `FD_SETSIZE` 是 1024，fd 編號超過就無法使用，硬放會寫出陣列邊界。更根本的問題是成本：每次呼叫都要把整個集合複製進 kernel，kernel 檢查所有 fd，回來後程式又要掃一遍找出就緒的，而且集合會被改寫，每次都要重新建立。成本和監看的 fd 數成正比。
>
> `epoll` 把監看集合存在 kernel 裡，只在增刪時呼叫 `epoll_ctl`，`epoll_wait` 只回傳已就緒的事件。當 10,000 條連線中只有 50 條活躍時，`poll` 每次要處理 10,000 項，`epoll_wait` 只回傳 50 項，成本和就緒數成正比。這就是 nginx 這類服務能以少量 thread 撐住大量閒置連線的原因。

> [!question]- Q5. 程式找錯：下面的程式想讓 4 個 thread 各印出自己的編號 0–3，實際卻常印出重複的數字，為什麼？`for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, show, &i);`，`show` 裡印出 `*(int *)arg`。
> 4 個 thread 拿到的都是同一個變數 `i` 的位址，而這個變數在 main thread 的 stack 上持續被迴圈修改。每個新 thread 什麼時候開始執行、什麼時候讀 `*arg`，由排程決定；如果它在 main thread 已經把 `i` 加到 2 之後才讀，就會印出 2。多個 thread 可能讀到同一個值，迴圈結束後讀到的甚至是 4，而且 `i` 的生命週期在迴圈結束後就已結束，嚴格來說還是存取已失效物件。
>
> 修法是讓每個 thread 有自己的一份資料：傳值，例如 `(void *)(intptr_t)i`，在 thread 裡轉回整數；或準備一個 `int ids[4]` 陣列，傳 `&ids[i]`；或為每個 thread `malloc` 一個 int，由 thread 自己 `free`。這是第 31 章「共享變數」與 race 的第一個實例。

> [!question]- Q6. 為什麼 nginx 用 event-driven，而 PostgreSQL 用 process-per-connection？哪個比較好？
> 兩者面對的工作完全不同。nginx 作為反向代理，手上有大量連線，大多處於閒置或在等網路，每個請求需要的 CPU 很少；用少數 worker process 各跑一個 epoll 迴圈，每條連線只佔一個小狀態 struct，就能用很少的記憶體撐住數萬條連線。
>
> PostgreSQL 的每條連線背後是複雜、長時間、可能大量使用 CPU 與記憶體的查詢執行，程式碼也是以循序方式寫成的，每個 backend 在自己的 process 裡執行，彼此不會踩到對方的私有記憶體（不過 backend 若異常終止，postmaster 為了保護共享記憶體，會讓所有 backend 重新啟動）。代價是每條連線成本高，所以實務上常在前面加連線池（例如 PgBouncer），用少量 backend 服務大量 client。沒有哪個比較好，只有哪個更符合工作的形狀，這也是 30.6 節比較表的重點。

> [!question]- Q7. Thread pool 的 queue 設成無上限，有什麼問題？設成 0（沒有 queue）又會怎樣？
> 無上限的 queue 在到達速度持續高於處理速度時，長度會無限增長。表面上沒有請求被拒絕，但每個請求的排隊時間越來越長，client 早已 timeout，worker 仍在處理沒人要的工作；最後記憶體耗盡，整個服務當掉。它把一個本來可以「拒絕一部分」的過載，變成「全部失敗」。
>
> 沒有 queue（producer 必須直接交給一個空閒的 worker）則走向另一個極端：只要瞬間所有 worker 都忙，新工作就要立刻等待或被拒絕，無法吸收短暫的流量波動，吞吐量會因為 worker 偶爾閒置而下降。合理的做法是一個有限但能吸收正常波動的 queue，加上明確的過載策略（等待上限、回應 503、丟棄低優先工作），並監控 queue 長度。

> [!question]- Q8. 面試題：比較 process、thread 與 event-driven 三種並行模型，並說出一個你會選擇各自的情境。
> Process 模型的每條控制流有獨立位址空間，隔離最好，一個請求當機不會拖垮其他請求，程式也是普通的循序寫法；代價是建立成本高、共享資料要靠 IPC。我會在處理不可信任輸入、或要呼叫容易當機的外部工具時選它，例如 `thumbd` 用子行程呼叫外部轉檔工具。
>
> Thread 模型共享位址空間，建立與切換便宜，資料共享容易，程式仍是循序寫法，但必須用同步機制處理共享資料，任何一個 thread 的記憶體錯誤都會讓整個 process 當掉。CPU 與 I/O 混合、需要共享快取的服務（例如縮圖服務）適合用 thread pool。Event-driven 只用一條控制流，每條連線成本極低，沒有同步問題，但程式要寫成狀態機，且不能有任何阻塞操作，適合大量閒置連線的接入層，例如反向代理或推播服務。能補充「實務上常混合使用」並舉例，是加分的回答。
