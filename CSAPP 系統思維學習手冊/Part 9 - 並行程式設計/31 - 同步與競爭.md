# 第 31 章　同步：共享變數、Race、Semaphore 與 Deadlock

> [!abstract] 本章地圖
> **核心問題**：多個 thread 同時讀寫同一份資料時，怎麼保證結果在任何排程下都正確，而且程式不會永遠卡住？
>
> **你會學到**：
> - 判斷一個變數在多執行緒程式中是不是共享的，依據是「記憶體中的那一份被誰碰到」，而不是宣告在哪裡
> - 用組合語言與 progress graph 解釋 `cnt++` 為什麼會遺失更新，並手算所有可能的交錯
> - 用 semaphore、mutex 與 condition variable 保護臨界區，寫出正確的 producer-consumer 與 readers-writers
> - 說出 deadlock 的四個必要條件，用一致的鎖順序避免它，並在卡住的服務上找出鎖的循環
> - 用 ThreadSanitizer 抓出 data race，理解它為什麼能抓到「這次結果剛好正確」的 race
>
> **前置知識**：第 30 章（thread 與 thread pool）、第 7–8 章（組合語言與指令）、第 22 章（signal handler 與 async-signal-safe）
>
> **對應 CS:APP 3e**：第 12 章 12.4、12.5、12.7.5 節（deadlock）

## 31.1 故事：少了三萬兩千個請求

`thumbd` 換成 thread pool（第 30 章）一個月後，產品經理 Lisa 拿著兩份報表來找小安。nginx 的 access log 顯示，昨天送到 `thumbd` 的請求有 1,000,000 個；`thumbd` 自己的 `/stats` 頁面卻說 `requests_total` 是 968,000。「我們是不是漏了三萬多個請求沒處理？」

小安查了 log，每一個請求都有正常回應。真正的問題在計數器本身：

```c
// not-runnable：thumbd 的統計程式碼（有 bug 的版本）
static long requests_total, cache_hits, cache_misses;

static void record(int hit) {      /* 每個 worker thread 處理完請求都會呼叫 */
    requests_total++;
    if (hit) cache_hits++; else cache_misses++;
}
```

同一週，`thumbd` 還在半夜當機了兩次。core dump 的 stack trace 停在縮圖快取的 LRU 串列操作 `lru_move_to_front` 裡，某個節點的 `prev` 指標指向一塊已經被 `free` 的記憶體。這段程式在單執行緒的 v0 時代跑了好幾年都沒事。

老周看完說：「兩個問題是同一件事。16 個 worker 同時改同一個 `requests_total`，有些加法被別的 thread 蓋掉了；同時改同一條串列的指標，串列就被改壞了。統計少算只是數字不準，串列壞掉就是當機。在 thread 的世界裡，『我先讀、再改、再寫回去』這三步，中間隨時可能有別人插進來。」

這一章從「哪些變數是共享的」開始，一步一步解釋 `requests_total++` 怎麼遺失更新，再介紹修正它的工具：semaphore、mutex、condition variable，以及用錯它們時會出現的 deadlock。

## 31.2 哪些變數是共享的

### 定義：看「那一份」被誰碰到

第 30 章說過，thread 共享程式碼、heap、全域變數與 fd table，各自有 stack 與暫存器。但「全域變數共享、區域變數私有」只是粗略的說法，真正的判斷要更精確：

> 一個變數的某一份**實體**（instance，記憶體中的一份）如果被**兩個以上的 thread** 存取，它就是**共享**的。

這個定義看的是記憶體中真正的那一份，而不是原始碼的宣告位置。C 的變數依照儲存方式可以分成三類，它們在多執行緒程式中各有幾份：

| 變數種類 | 記憶體中有幾份 | 放在哪裡 | 共享嗎 |
|---|---|---|---|
| 全域變數（函式外宣告） | 整個 process 一份 | `.data` 或 `.bss` | 只要兩個 thread 都會用到，就是共享 |
| 區域 `static` 變數 | 整個 process 一份（不管幾個 thread 執行該函式） | `.data` 或 `.bss` | 同上，容易被誤以為是私有的 |
| 區域自動變數（一般的區域變數） | 每個 thread 執行該函式時各有一份 | 各自 thread 的 stack | 通常私有；但位址一旦被交給別的 thread，就變成共享 |
| `malloc` 配置的物件 | 一份 | heap | 看指標被交給了誰 |

用 `thumbd` worker 的實際程式來判斷：

```c
// not-runnable：判斷下面每個變數是不是共享的
static struct config *g_config;              /* 全域：啟動時載入 */

static void *worker(void *arg) {
    static long served;                      /* 區域 static */
    struct pool *pool = arg;                 /* 區域自動變數，指向 main 配置的 pool */
    char path[256];                          /* 區域自動變數 */
    for (;;) {
        struct job *job = take(pool);        /* job 是 acceptor thread malloc 的 */
        snprintf(path, sizeof path, "%s/%s", g_config->root, job->name);
        thumbnail(path, job);
        served++;
        free(job);
    }
}
```

| 變數 | 實體數量 | 被誰存取 | 結論 |
|---|---|---|---|
| `g_config` | 1 | 所有 worker 讀；SIGHUP 重新載入時被寫（第 22 章） | 共享，讀寫並存時需要同步 |
| `served` | 1（不是每個 thread 一份！） | 所有 worker 都會 `served++` | 共享，而且有 race |
| `pool` | 每個 worker 一份 | 各自的 thread | 指標本身私有，**指向的 pool 物件共享** |
| `path` | 每個 worker 一份 | 只有自己 | 私有 |
| `*job` | 每個工作一份 | acceptor 寫入，再交給一個 worker | 在交接的那一刻共享，交接必須經過同步（queue） |

這張表最容易錯的是 `served`：它寫在函式裡面，看起來像區域變數，但 `static` 讓它在整個 process 只有一份。第二容易錯的是 `pool`：變數本身在每個 thread 的 stack 上各有一份，但它們全部指向同一個物件。判斷共享時，永遠要問「這塊記憶體還有誰拿得到它的位址」。

如果真的需要「每個 thread 一份」的全域狀態（例如每個 worker 自己的統計，最後再加總），可以用 C11 的 `_Thread_local`（或 GCC／Clang 的 `__thread`）宣告 **thread-local storage**：每個 thread 存取同一個名字時，拿到的是自己的那一份。

## 31.3 `cnt++` 為什麼不是 atomic

### 一行 C，三個步驟

先看編譯器把 `cnt++` 翻成什麼。下面是 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - inc.c` 的結果，`inc.c` 裡宣告了 `volatile long cnt; atomic_long acnt;` 和兩個函式：

```c
// not-runnable：inc.c
#include <stdatomic.h>
volatile long cnt;
atomic_long acnt;
void inc_plain(void)  { cnt++; }
void inc_atomic(void) { atomic_fetch_add(&acnt, 1); }
```

```asm
inc_plain:
	incq	cnt(%rip)
	retq
inc_atomic:
	lock		incq	acnt(%rip)
	retq
```

`inc_plain` 只有一條 `incq cnt(%rip)` 指令，看起來是不可分割的。但在多核心處理器上，這條指令內部仍然是「從記憶體讀出 → 加 1 → 寫回記憶體」三個動作；兩個核心同時執行它，可能都讀到同一個舊值。只有加上 `lock` 前綴（`inc_atomic` 的版本），處理器才保證整個讀－改－寫期間沒有其他核心能插手這個位址。

在 ARM64 上這三個步驟直接寫成三條指令。用同一個檔案、把 target 換成 `-target aarch64-linux-gnu` 產生（省略 directive，`//` 之後的中文註解是另外加上的）：

```text
inc_plain:                       // ARM64：三步驟一目了然
	adrp	x8, cnt
	ldr	x9, [x8, :lo12:cnt]      // L：load 到暫存器 x9
	add	x9, x9, #1               // U：update（暫存器 +1）
	str	x9, [x8, :lo12:cnt]      // S：store 寫回記憶體
	ret
inc_atomic:
	adrp	x8, acnt
	add	x8, x8, :lo12:acnt
.LBB1_1:
	ldaxr	x9, [x8]                 // 獨占地讀
	add	x9, x9, #1
	stlxr	w10, x9, [x8]            // 若期間有人寫過這個位址，寫入失敗（w10 ≠ 0）
	cbnz	w10, .LBB1_1             // 失敗就重來
	ret
```

ARM64 的 atomic 版本用的是「獨占讀、條件寫」：`stlxr` 只有在讀出之後沒有別人寫過這個位址時才會成功，否則整段重做。兩種架構做法不同，但目的相同：讓讀、改、寫三步在其他核心眼中像一步。

### 關於 volatile 的提醒

本章的實驗程式把計數器宣告成 `volatile`。原因是沒有 `volatile` 時，編譯器很聰明。用同樣的指令編譯下面這兩個「跑 1,000,000 次 `cnt++`」的迴圈：

```c
// not-runnable：loop.c
long cnt;
volatile long vcnt;
int count_plain(void)    { for (int i = 0; i < 1000000; i++) cnt++;  return 0; }
int count_volatile(void) { for (int i = 0; i < 1000000; i++) vcnt++; return 0; }
```

```asm
count_plain:                     # long cnt;  迴圈被整個摺疊掉
	addq	$1000000, cnt(%rip)
	xorl	%eax, %eax
	retq
count_volatile:                  # volatile long vcnt;  每一圈都真的讀寫記憶體
	movl	$1000000, %eax
.LBB1_1:
	incq	vcnt(%rip)
	decl	%eax
	jne	.LBB1_1
	xorl	%eax, %eax
	retq
```

（`#` 之後的中文註解是另外加上的。）`count_plain` 被編譯器改成一次加一百萬，race 的窗口變得極小，實驗就很難看到遺失。`volatile` 強迫每一圈都真的存取記憶體，讓 race 容易重現。

> [!warning] 常見誤解
> 「把共享變數宣告成 `volatile` 就是 thread-safe。」不是。`volatile` 只要求編譯器不要省略或合併對該變數的存取，它**不會**讓讀－改－寫變成 atomic，也不會在 thread 之間建立任何順序保證。上面的 `count_volatile` 仍然是沒有 `lock` 的 `incq`，31.9 節會實際量到它遺失了將近一半的更新。在 C 裡，跨 thread 的同步要用 mutex 或 `<stdatomic.h>` 的 atomic 型別。

### 把交錯攤開來看

把 `cnt++` 抽象成三步：**L**（load 到暫存器）、**U**（暫存器加 1）、**S**（store 回記憶體）。兩個 thread 各執行一次，`cnt` 初值是 0，正確答案是 2。下面是其中一種交錯：

| 時間 | 執行的步驟 | thread 1 的暫存器 | thread 2 的暫存器 | 記憶體中的 `cnt` |
|---|---|---|---|---|
| 1 | L1 | 0 | — | 0 |
| 2 | U1 | 1 | — | 0 |
| 3 | L2 | 1 | 0 | 0 |
| 4 | S1 | 1 | 0 | 1 |
| 5 | U2 | 1 | 1 | 1 |
| 6 | S2 | 1 | 1 | **1** |

thread 2 在時間 3 讀到的是 0，因為 thread 1 的結果在時間 4 才寫回。之後 thread 2 把自己算出的 1 寫回，蓋掉了 thread 1 的更新。最後 `cnt` 是 1，一次加法消失了。這就是 **lost update**（遺失更新），也正是 `requests_total` 少了三萬多的原因。

### 手算：20 種交錯中有幾種是對的？

兩個 thread 各有 3 步，總共 6 步。每一種交錯，等於從 6 個時間點中選出 3 個給 thread 1（各自內部的順序固定），所以共有 C(6, 3) = 6! ÷ (3! × 3!) = 720 ÷ 36 = 20 種。

哪些交錯會得到 2？只有當某個 thread 的 L 發生在另一個 thread 的 S **之後**，它才會讀到已經加過的值。也就是說，必須「thread 1 的 L1、U1、S1 全部做完，thread 2 才開始 L2」，或反過來。每個方向各只有 1 種排法，所以 20 種中只有 **2 種**正確，其餘 18 種都得到 1。

用 Python 把 20 種交錯全部列舉出來驗證（存成 `inter.py`）：

```python
from collections import Counter
from itertools import combinations

# 兩個 thread 各執行一次 cnt++，拆成三步：L（load 到暫存器）、U（暫存器 +1）、S（store 回記憶體）
STEPS = ["L", "U", "S"]


def run(order):
    """order 是長度 6 的 thread 編號序列，例如 [1,1,2,1,2,2]。"""
    cnt, reg, pc = 0, {1: 0, 2: 0}, {1: 0, 2: 0}
    trace = []
    for t in order:
        step = STEPS[pc[t]]
        if step == "L":
            reg[t] = cnt
        elif step == "U":
            reg[t] += 1
        else:
            cnt = reg[t]
        trace.append(f"{step}{t}")
        pc[t] += 1
    return cnt, " ".join(trace)


results = Counter()
examples = {}
for pos in combinations(range(6), 3):          # 選出 thread 1 佔用的三個時間點
    order = [1 if i in pos else 2 for i in range(6)]
    final, trace = run(order)
    results[final] += 1
    examples.setdefault(final, []).append(trace)

total = sum(results.values())
print(f"所有可能的交錯：{total} 種")
for final in sorted(results):
    print(f"最後 cnt = {final}：{results[final]:2d} 種，例如 {examples[final][0]}")
print("正確（cnt = 2）的全部交錯：", " | ".join(examples[2]))
```

```text
所有可能的交錯：20 種
最後 cnt = 1：18 種，例如 L1 U1 L2 S1 U2 S2
最後 cnt = 2： 2 種，例如 L1 U1 S1 L2 U2 S2
正確（cnt = 2）的全部交錯： L1 U1 S1 L2 U2 S2 | L2 U2 S2 L1 U1 S1
```

這不代表真實程式有 90% 的更新會遺失。真實的排程不是 20 選 1 的均勻抽籤：在單核心上，一個 thread 通常會連續執行好幾毫秒才被切換，大部分 `cnt++` 都在「另一個 thread 沒在跑」時完成；在多核心上兩個 thread 真的同時執行，交錯就密集得多。重點不在比例，而在於**只要有任何一種壞的交錯存在，它遲早會在 production 發生**。

## 31.4 Progress graph：把交錯畫成路徑

CS:APP 用 **progress graph**（進度圖）把兩個 thread 的執行畫成平面上的路徑。橫軸是 thread 1 已經完成的步數，縱軸是 thread 2 已經完成的步數。每執行一步，路徑就向右（thread 1 前進）或向上（thread 2 前進）走一格，從左下角 (0, 0) 走到右上角 (3, 3)。每一條路徑就是一種交錯。

```text
 thread 2 已完成的步數
   3 ┤ ●────●────●────●  ← 終點：兩個 thread 都做完
     │ │    │    │    │
   2 ┤ ●────■────■────●     ■：unsafe region（不安全區）
     │ │    │    │    │        兩個 thread 都已 load、都還沒 store
   1 ┤ ●────■────■────●
     │ │    │    │    │
   0 ┤ ●────●────●────●
     └─┬────┬────┬────┬──▶ thread 1 已完成的步數
       0    1    2    3
         L1   U1   S1   （走過這一格代表執行了該步驟）
```

讀這張圖的方法：點 (2, 1) 表示 thread 1 做完了 L1、U1，thread 2 做完了 L2。在 L 與 S 之間的這段指令，會讀寫共享變數，叫 **critical section**（臨界區）。兩個 thread 同時位於各自的 critical section 時（圖中的 ■），兩邊都已經讀了舊值、都還沒寫回，從這裡出發不管怎麼走，最後都會遺失一次更新。

所以「正確的交錯」就是**完全不碰到 ■ 的路徑**。從圖上很容易看出只有兩條：沿著底邊走到 (3, 0) 再往上，或沿著左邊走到 (0, 3) 再往右。這和 31.3 節手算的 2 種完全一致。

Progress graph 把同步問題變成一個幾何問題：**同步的目標，是讓所有可能的路徑都繞過 unsafe region**。我們不能控制排程器，但可以在 critical section 前後加上「關卡」，讓某些路徑根本不可能被走到。下一節的 semaphore 就是這種關卡。

## 31.5 Semaphore：用一個計數器擋住路徑

### 定義

**Semaphore**（號誌）是 Dijkstra 在 1960 年代提出的同步工具：一個非負整數 s，只能用兩個操作改變它。

- **P(s)**：如果 s 大於 0，把 s 減 1 並立刻返回；如果 s 等於 0，就暫停這個 thread，直到 s 變成大於 0，再減 1 並返回。
- **V(s)**：把 s 加 1；如果有 thread 正在 P 裡等待，叫醒其中一個。

名稱來自荷蘭文 Proberen（測試）與 Verhogen（增加）。關鍵在於 P 的「檢查並減 1」與 V 的「加 1」都是**不可分割**的：系統保證不會有兩個 thread 同時看到 s = 1 然後都把它減成 0。因此 semaphore 永遠滿足一個不變量：s ≥ 0。

用一個比喻記住它：s 是停車場剩下的車位數。P 是開車進去，有空位就進、沒空位就在門口排隊；V 是開車離開，空位加一，門口排第一的那台車可以進去。

### 用 binary semaphore 做互斥

把 s 的初值設為 1，並在 critical section 前後各放一個 P 和 V：

```c
// not-runnable：用 semaphore 保護計數器
sem_t mutex;                  /* 初值 1 */
sem_init(&mutex, 0, 1);       /* 第二個參數 0：只在同一 process 的 thread 之間使用 */

P(&mutex);                    /* 也就是 sem_wait(&mutex) */
requests_total++;
V(&mutex);                    /* 也就是 sem_post(&mutex) */
```

值只會在 0 與 1 之間變動的 semaphore 叫 **binary semaphore**（二元號誌），用來實現 **mutual exclusion**（互斥）：同一時間最多一個 thread 在 critical section 裡。在 progress graph 上，它的效果是：

```text
 thread 2 已完成的步數
   5 ┤ ·    ·    ·    ·    ·    ·
   4 ┤ ·    ▒    ▒    ▒    ▒    ·
   3 ┤ ·    ▒    ■    ■    ▒    ·      ▒：forbidden region（兩邊都通過 P、都還沒 V，s 會是 −1）
   2 ┤ ·    ▒    ■    ■    ▒    ·      ■：unsafe region，被禁區完全包住
   1 ┤ ·    ▒    ▒    ▒    ▒    ·
   0 ┤ ·    ·    ·    ·    ·    ·      縱軸：thread 2 依序執行 P2、L2、U2、S2、V2
     └─┬────┬────┬────┬────┬────┬──▶ thread 1 已完成的步數
       0    1    2    3    4    5
         P1   L1   U1   S1   V1
```

現在每個 thread 有 5 步：P、L、U、S、V。兩個 thread 都通過 P、都還沒到 V 的那一片區域（圖中的 ▒ 與 ■，也就是兩個座標都在 1 到 4 之間），s 會是 1 − 2 = −1，違反 s ≥ 0，所以 semaphore 會讓第二個想進入的 thread 在 P 停下來，路徑根本走不進去。這一片 **forbidden region**（禁區）完全包住了 unsafe region，於是所有可能的路徑都只能從禁區的右下方（thread 1 先做完整段 critical section）或左上方（thread 2 先做完）繞過去，也就自動繞過了 unsafe region。

### POSIX API 與平台差異

POSIX 的 semaphore 函式是 `sem_init`、`sem_wait`（P）、`sem_post`（V）、`sem_destroy`。這裡有一個實務陷阱：**macOS 不支援未命名的 semaphore**。在本機 macOS arm64 上實測，`sem_init` 編譯時會出現 deprecated 警告，執行時回傳 −1、`errno` 是 `ENOSYS`（Function not implemented）；之後對它呼叫 `sem_wait` 會立刻回傳 −1（本機的 `errno` 是 `EBADF`），完全不會阻塞。如果程式沒有檢查 `sem_init` 的回傳值，就會在 macOS 上悄悄失去所有同步。

可攜的做法有三種：在 macOS 上用 `dispatch_semaphore`（Grand Central Dispatch）或具名的 `sem_open`；或者像 31.7 節的程式，用 mutex 加 condition variable 自己實作一個 semaphore。這也順便說明一件事：semaphore、mutex、condition variable 的表達能力是相通的，可以互相建構。

## 31.6 Mutex 與 condition variable

### Mutex：有主人的鎖

用 semaphore 做互斥是可行的，但 Pthreads 提供了專門的 **mutex**（互斥鎖）：

```c
// not-runnable：用 mutex 修好 thumbd 的計數器
static pthread_mutex_t stats_mu = PTHREAD_MUTEX_INITIALIZER;

static void record(int hit) {
    pthread_mutex_lock(&stats_mu);
    requests_total++;
    if (hit) cache_hits++; else cache_misses++;
    pthread_mutex_unlock(&stats_mu);
}
```

Mutex 和 binary semaphore 的關鍵差別是**擁有者**：mutex 由 lock 它的那個 thread 擁有，只能由同一個 thread unlock；semaphore 沒有擁有者，任何 thread 都可以 V。這個限制讓 mutex 能做到 semaphore 做不到的事：用 `PTHREAD_MUTEX_ERRORCHECK` 屬性時，重複 lock 或由別的 thread unlock 會回傳錯誤；搭配 priority inheritance 等機制時，系統也知道「是誰擋住了大家」。

Mutex 的效能大多數時候很好。在 Linux 上，glibc 的 mutex 建立在 **futex**（fast userspace mutex）之上：沒有競爭時，lock 與 unlock 只是一條 atomic 指令，完全不進 kernel；只有真的要等待時，才透過 `futex` 系統呼叫讓 thread 睡覺。所以「mutex 很慢」通常指的是**競爭激烈**時的成本，而不是鎖本身。第 32 章會量化這件事。

注意 `record` 裡三個計數器用**同一把鎖**一起保護。如果三個欄位各用一把鎖，`requests_total` 與 `cache_hits + cache_misses` 之間的一致性（兩者應該相等）在別人讀取時仍然可能被看到不一致的中間狀態。一把鎖保護的，應該是一組必須一起維持的 **invariant**（不變量），而不是單一變數。

### Condition variable：等待一個條件成立

Mutex 解決「不要同時進去」，但很多時候 thread 需要的是「等到某個條件成立再繼續」，例如 worker 要等 queue 裡有工作。用 mutex 硬寫，只能不停地 lock、檢查、unlock、再 lock，白白浪費 CPU。

**Condition variable**（條件變數）讓 thread 可以在 mutex 旁邊睡覺，等別人通知「條件可能改變了」。回顧第 30 章 `pool.c` 的 `take`：

```c
// not-runnable：第 30 章 thread pool 的 take，逐行說明
pthread_mutex_lock(&mu);                       /* ① 先拿鎖，才能安全地看 count */
while (count == 0)                             /* ② 條件不成立就等；一定要用 while */
    pthread_cond_wait(&not_empty, &mu);        /* ③ 原子地「放鎖並睡覺」，醒來時重新拿鎖 */
int job = queue[head]; head = (head + 1) % QCAP; count--;   /* ④ 此時持有鎖，且 count > 0 */
pthread_cond_signal(&not_full);                /* ⑤ 通知 producer：多了一個空位 */
pthread_mutex_unlock(&mu);
```

第 ③ 步是整個機制的核心。`pthread_cond_wait` 必須**原子地**完成「釋放 mutex」與「開始睡覺」兩件事。如果它是分開的兩步，就會出現 **lost wakeup**（遺失喚醒）：

```text
 若「放鎖」與「睡覺」分成兩步：
 worker（consumer）                      acceptor（producer）
 lock; 看到 count == 0
 unlock                       ──────▶    lock; 放入工作; count = 1
                                          signal(not_empty)   ← 此時沒有人在睡，訊號消失
                                          unlock
 開始睡覺                     ◀──────    （之後 producer 不會再 signal）
 永遠睡下去，明明 queue 裡有工作
```

worker 在「決定要睡」和「真的睡著」之間，producer 插進來放了工作並發出 signal。condition variable 不會記住過去的訊號，所以這個 signal 白白浪費，worker 之後睡著就再也不會被叫醒。`pthread_cond_wait` 把兩步合成一步，並要求呼叫時持有 mutex，正是為了關閉這個窗口。

第 ② 步一定要用 `while` 而不是 `if`，原因有兩個。一是 POSIX 允許 **spurious wakeup**（虛假喚醒）：thread 可能在沒有任何人 signal 的情況下醒來。二是即使真的被 signal 叫醒，從醒來到重新拿到鎖之間，可能已經有另一個 worker 搶先把工作拿走了。所以醒來後必須重新檢查條件。記住一句話：**condition variable 只表示「條件可能變了」，條件本身要由共享狀態決定**。

`pthread_cond_signal` 至少叫醒一個等待者，`pthread_cond_broadcast` 叫醒全部。等待者都在等同一件事、任何一個都能處理時用 signal；條件改變可能讓多種等待者都要重新檢查（例如關閉 pool 時，所有 worker 都要醒來下班）時用 broadcast。

三種工具的整理：

| 工具 | 本質 | 誰能釋放 | 適合用來 | 典型錯誤 |
|---|---|---|---|---|
| mutex | 一把鎖，有擁有者 | 只有持有者 | 保護一組共享資料的 invariant | 忘記 unlock（尤其錯誤路徑）、鎖的範圍太大或太小 |
| semaphore | 非負計數器，P 減、V 加 | 任何 thread | 計數資源（空位、項目數）、跨 thread 的通知 | 忘記檢查 `sem_init` 回傳值；P 的順序錯造成 deadlock |
| condition variable | 等待條件的地方，本身不存狀態 | 不適用（搭配 mutex） | 「等到某條件成立」 | 用 `if` 而不是 `while`；沒有持鎖就修改條件 |

## 31.7 用 semaphore 排程共享資源

Semaphore 除了互斥，還能用計數表示「還剩多少資源」，讓 thread 依照資源的狀態排隊。CS:APP 用兩個經典問題說明：producer-consumer 與 readers-writers。

### Producer-consumer：有界 buffer

第 30 章的 thread pool 中，acceptor 是 producer、worker 是 consumer，中間是一個有 N 格的環狀 buffer。需要維護三件事：

| semaphore | 初值 | 代表 | P 的意義 | V 的意義 |
|---|---|---|---|---|
| `slots` | N | 空格數 | producer 要一個空格，沒有就等 | consumer 拿走一項後歸還一個空格 |
| `items` | 0 | 項目數 | consumer 要一個項目，沒有就等 | producer 放入一項後通知 |
| `mutex` | 1 | buffer 的互斥 | 修改 `front`／`rear` 前上鎖 | 改完解鎖 |

下面的程式完整實作它。因為 macOS 不支援 `sem_init`，程式開頭用 mutex 加 condition variable 自己做了 P 和 V，寫法正好是 31.6 節的標準模式。兩個 producer 各放入 20,000 個不同的數字，兩個 consumer 各取 20,000 個並加總（存成 `sbuf.c`）：

```c
#include <pthread.h>
#include <stdio.h>

/* macOS 不支援 sem_init，所以用 mutex + condition variable 自己做一個計數 semaphore */
typedef struct { pthread_mutex_t m; pthread_cond_t c; int value; } sem;
static void sem_setup(sem *s, int v) {
    pthread_mutex_init(&s->m, NULL); pthread_cond_init(&s->c, NULL); s->value = v;
}
static void P(sem *s) {                       /* 等到 value > 0，再減 1 */
    pthread_mutex_lock(&s->m);
    while (s->value == 0) pthread_cond_wait(&s->c, &s->m);
    s->value--;
    pthread_mutex_unlock(&s->m);
}
static void V(sem *s) {                       /* 加 1，叫醒一個等待者 */
    pthread_mutex_lock(&s->m);
    s->value++;
    pthread_cond_signal(&s->c);
    pthread_mutex_unlock(&s->m);
}

#define N 8                                   /* buffer 容量 */
#define PER_PRODUCER 20000
static int buf[N], front, rear, occupied, max_occupied;
static sem mutex, slots, items;               /* 初值：1、N、0 */
static long consumed_sum[2];

static void insert(int x) {
    P(&slots);                                /* 先拿一個空位，沒有就等 */
    P(&mutex);
    buf[rear] = x; rear = (rear + 1) % N;
    if (++occupied > max_occupied) max_occupied = occupied;
    V(&mutex);
    V(&items);                                /* 通知：多了一個項目 */
}
static int removeitem(void) {
    P(&items);
    P(&mutex);
    int x = buf[front]; front = (front + 1) % N; occupied--;
    V(&mutex);
    V(&slots);
    return x;
}

static void *producer(void *arg) {
    int base = (int)(long)arg * PER_PRODUCER;
    for (int i = 1; i <= PER_PRODUCER; i++) insert(base + i);
    return NULL;
}
static void *consumer(void *arg) {
    long id = (long)arg;
    for (int i = 0; i < PER_PRODUCER; i++) consumed_sum[id] += removeitem();
    return NULL;
}

int main(void) {
    sem_setup(&mutex, 1); sem_setup(&slots, N); sem_setup(&items, 0);
    pthread_t t[4];
    for (long i = 0; i < 2; i++) pthread_create(&t[i], NULL, producer, (void *)i);
    for (long i = 0; i < 2; i++) pthread_create(&t[2 + i], NULL, consumer, (void *)i);
    for (int i = 0; i < 4; i++) pthread_join(t[i], NULL);
    long n = 2L * PER_PRODUCER, expect = n * (n + 1) / 2;
    printf("兩個 consumer 各拿到的總和：%ld + %ld\n", consumed_sum[0], consumed_sum[1]);
    printf("合計 %ld，預期 1+2+…+%ld = %ld → %s\n", consumed_sum[0] + consumed_sum[1], n, expect,
           consumed_sum[0] + consumed_sum[1] == expect ? "沒有遺失也沒有重複" : "錯誤！");
    printf("buffer 中同時存在的項目最多 %d 個（容量 %d），結束時剩 %d 個\n", max_occupied, N, occupied);
    return 0;
}
```

在 macOS arm64 上執行兩次：

```text
兩個 consumer 各拿到的總和：400952411 + 399067589
合計 800020000，預期 1+2+…+40000 = 800020000 → 沒有遺失也沒有重複
buffer 中同時存在的項目最多 8 個（容量 8），結束時剩 0 個
```

```text
兩個 consumer 各拿到的總和：405218255 + 394801745
合計 800020000，預期 1+2+…+40000 = 800020000 → 沒有遺失也沒有重複
buffer 中同時存在的項目最多 8 個（容量 8），結束時剩 0 個
```

逐步解讀：

1. **總和每次都是 800,020,000**：1 到 40,000 的和是 40,000 × 40,001 ÷ 2 = 800,020,000。每個數字都剛好被取出一次，沒有遺失、沒有重複。這是正確性的證據。
2. **每個 consumer 分到的部分每次不同**：誰拿到哪些項目由排程決定。正確的同步不保證「每次行為一樣」，而是保證「每次都滿足 invariant」。
3. **最多同時 8 個**：`slots` 的初值 8 讓 producer 最多領先 consumer 8 格，buffer 永遠不會溢位。這就是第 30 章 backpressure 的實作。
4. **P 的順序很重要**：`insert` 先 `P(&slots)` 再 `P(&mutex)`。如果反過來，producer 先拿到 mutex，再發現沒有空格而在 `P(&slots)` 睡著，它會**抱著 mutex 睡覺**；consumer 要取項目必須先拿 mutex，永遠拿不到，於是誰也無法前進。這是 31.8 節 deadlock 的一個實例。原則是：**先等資源，再拿鎖；不要拿著鎖去等可能很久的事**。

### Readers-writers：多人讀、一人寫

`thumbd` 的縮圖快取被讀取的次數遠多於寫入：大部分請求只是查詢「這張縮圖是否已經有了」，只有 miss 時才插入新項目。如果用一把 mutex，所有查詢都要排隊，即使它們彼此根本不衝突。

**Readers-writers 問題**允許多個 reader 同時讀，但 writer 必須獨占：writer 在寫時，其他 reader 和 writer 都不能進來。最經典的解法（偏向 reader 的版本）：

```c
// not-runnable：偏向 reader 的 readers-writers（P、V 同 31.7 節程式）
static int readcnt;          /* 正在讀的 reader 數，受 mutex 保護 */
static sem mutex, w;         /* 初值都是 1；w 保證 writer 獨占 */

void cache_lookup(void) {
    P(&mutex);
    if (++readcnt == 1) P(&w);     /* 第一個進來的 reader 替所有 reader 擋住 writer */
    V(&mutex);
    /* ……讀取快取，可以和其他 reader 同時進行…… */
    P(&mutex);
    if (--readcnt == 0) V(&w);     /* 最後一個離開的 reader 放行 writer */
    V(&mutex);
}

void cache_insert(void) {
    P(&w);
    /* ……修改快取，獨占…… */
    V(&w);
}
```

這個版本有一個嚴重的公平性問題：只要 reader 源源不絕地進來，`readcnt` 就永遠不會降到 0，writer 永遠拿不到 `w`。這叫 **starvation**（飢餓）：某個 thread 一直有機會前進，卻始終輪不到它。另一種版本偏向 writer：只要有 writer 在等，新的 reader 就不准進來；它反過來可能餓死 reader。

實務上直接用 Pthreads 的 `pthread_rwlock_rdlock`、`pthread_rwlock_wrlock` 與 `pthread_rwlock_unlock`。它在不同平台偏向 reader 或 writer 的策略並不相同。例如 glibc 預設是 `PTHREAD_RWLOCK_PREFER_READER_NP`（偏向 reader，writer 可能餓死）；非標準的 `pthread_rwlockattr_setkind_np` 可以調整，但要注意 glibc 會忽略 `PTHREAD_RWLOCK_PREFER_WRITER_NP`，真正避免 writer 飢餓的是 `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`（前提是不遞迴地拿 read lock）。在意公平性時要查清楚自己平台的行為。另外，rwlock 本身的管理成本比 mutex 高，critical section 很短時不一定比較快，要量測再決定（第 32 章）。

## 31.8 Deadlock：所有人都在等別人

### 什麼是 deadlock

**Deadlock**（死結）是一組 thread 全部被阻塞，每一個都在等另一個持有的資源，因此誰也無法前進。`thumbd` 加上鎖之後，很快就遇到了：

```c
// not-runnable：兩條路徑以相反順序拿兩把鎖
void evict_old_entries(void) {           /* 快取淘汰：先鎖快取，再更新統計 */
    pthread_mutex_lock(&cache_lock);
    pthread_mutex_lock(&stats_lock);
    /* ... */
}
void render_stats_page(void) {           /* /stats 頁面：先鎖統計，再讀快取大小 */
    pthread_mutex_lock(&stats_lock);
    pthread_mutex_lock(&cache_lock);
    /* ... */
}
```

如果 thread A 執行 `evict_old_entries` 拿到 `cache_lock`，同一時間 thread B 執行 `render_stats_page` 拿到 `stats_lock`，接下來 A 等 `stats_lock`、B 等 `cache_lock`，兩者永遠互等。服務沒有當機、CPU 是 0%，但所有碰到這兩把鎖的請求全部卡住。

### 在 progress graph 上看 deadlock

把兩把鎖 s（`cache_lock`）與 t（`stats_lock`）的禁區畫在同一張 progress graph 上。thread 1 依序 P(s)、P(t)、V(t)、V(s)；thread 2 依序 P(t)、P(s)、V(s)、V(t)：

```text
 thread 2 已完成的步數
   4 ┤ ·    ·    ·    ·    ·
   3 ┤ ·    ·    T    ·    ·      S：s 的禁區（兩邊都持有 cache_lock）
   2 ┤ ·    S    X    S    ·      T：t 的禁區（兩邊都持有 stats_lock）
   1 ┤ ·    D    T    ·    ·      X：兩個禁區重疊
   0 ┤ ·    ·    ·    ·    ·      D：deadlock 狀態
     └─┬────┬────┬────┬────┬──▶ thread 1 已完成的步數
       0    1    2    3    4
         P(s) P(t) V(t) V(s)      縱軸：thread 2 依序執行 P(t)、P(s)、V(s)、V(t)
```

s 的禁區是「兩個 thread 都持有 s」的狀態：thread 1 已經 P(s)、還沒 V(s)（橫座標 1 到 3），同時 thread 2 已經 P(s)、還沒 V(s)（縱座標 2）。t 的禁區同理：thread 1 持有 t 只在橫座標 2，thread 2 持有 t 在縱座標 1 到 3。兩個禁區交叉成一個十字。

D 所在的狀態 (1, 1) 就是 **deadlock region**：thread 1 已經拿到 s、還沒拿到 t；thread 2 已經拿到 t、還沒拿到 s。路徑一旦走進 D，往右（thread 1 前進，要拿 t）會撞上 t 的禁區，往上（thread 2 前進，要拿 s）會撞上 s 的禁區，再也走不出去。進不進得了 D 取決於排程，所以 deadlock 和 race 一樣，可能在測試中跑一萬次都沒事，在 production 某天突然發生。

### 四個必要條件

Deadlock 只有在以下四個條件**同時成立**時才會發生（Coffman 條件）。只要打破任何一個，就不會有 deadlock：

| 條件 | 意義 | `thumbd` 的例子 | 怎麼打破 |
|---|---|---|---|
| Mutual exclusion（互斥） | 資源一次只能給一個 thread | mutex 本來就是互斥的 | 用不需要鎖的設計（每個 thread 一份資料、不可變資料） |
| Hold and wait（持有並等待） | 拿著一個資源去等另一個 | 拿著 `cache_lock` 等 `stats_lock` | 一次拿齊所有鎖，或先放掉手上的再拿 |
| No preemption（不可搶奪） | 不能強行拿走別人持有的資源 | mutex 無法被別人強制釋放 | 用 `pthread_mutex_trylock`，拿不到就放掉手上的鎖、退讓、重試 |
| Circular wait（循環等待） | 等待關係形成環 | A 等 B 的鎖，B 等 A 的鎖 | **規定全域一致的鎖順序** |

實務上最常用、也最可靠的是打破最後一個條件。CS:APP 稱之為 **mutex lock ordering rule**（鎖順序規則）：替所有鎖定義一個全域的順序，每個 thread 同時需要多把鎖時，一律依照這個順序取得。這樣等待關係永遠只會「由小往大」，不可能形成環。`thumbd` 的修法是規定「`cache_lock` 永遠在 `stats_lock` 之前」，並把 `render_stats_page` 改成先拿 `cache_lock`；更好的做法是讓 `/stats` 先在 `cache_lock` 底下複製一份快取大小、放掉鎖，再去拿 `stats_lock`，從根本上不再同時持有兩把鎖。

### 實際跑一次：相反的鎖順序

下面的程式讓兩個 thread 以相反順序拿兩把鎖，並刻意讓雙方都先拿到第一把。為了讓示範能自己結束，第二把鎖改用 `pthread_mutex_trylock` 嘗試 100 ms；換成普通的 `pthread_mutex_lock`，第一組就會永遠卡住。程式存成 `deadlock.c`：

```c
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <unistd.h>

static pthread_mutex_t cache_lock = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t stats_lock = PTHREAD_MUTEX_INITIALIZER;
static atomic_int arrived, decided;

struct plan { const char *name; pthread_mutex_t *first, *second; int stuck; };

/* 拿第一把鎖 → 等對方也拿到它的第一把 → 用 trylock 試第二把最多 100 ms →
 * 等兩邊都試完才放鎖，讓結果固定。用 trylock 只是為了讓示範能自己結束；
 * 換成 pthread_mutex_lock，「鎖順序相反」那一組會永遠卡住。 */
static void wait_for(atomic_int *v) {
    for (int i = 0; i < 200 && atomic_load(v) < 2; i++) usleep(1000);
}

static void *run(void *arg) {
    struct plan *p = arg;
    pthread_mutex_lock(p->first);
    atomic_fetch_add(&arrived, 1);
    wait_for(&arrived);
    p->stuck = 1;
    for (int i = 0; i < 100; i++) {
        if (pthread_mutex_trylock(p->second) == 0) { p->stuck = 0; break; }
        usleep(1000);
    }
    atomic_fetch_add(&decided, 1);
    wait_for(&decided);
    if (!p->stuck) pthread_mutex_unlock(p->second);
    pthread_mutex_unlock(p->first);
    return NULL;
}

static void trial(const char *title, struct plan *a, struct plan *b) {
    pthread_t ta, tb;
    atomic_store(&arrived, 0);
    atomic_store(&decided, 0);
    pthread_create(&ta, NULL, run, a);
    pthread_create(&tb, NULL, run, b);
    pthread_join(ta, NULL);
    pthread_join(tb, NULL);
    printf("%s\n  %s：%s\n  %s：%s\n", title, a->name, a->stuck ? "等第二把鎖 100 ms 仍拿不到" : "完成",
           b->name, b->stuck ? "等第二把鎖 100 ms 仍拿不到" : "完成");
}

int main(void) {
    struct plan evict  = {"evict （cache → stats）", &cache_lock, &stats_lock, 0};
    struct plan report = {"report（stats → cache）", &stats_lock, &cache_lock, 0};
    trial("鎖順序相反：", &evict, &report);
    struct plan report2 = {"report（cache → stats）", &cache_lock, &stats_lock, 0};
    trial("統一鎖順序：", &evict, &report2);
    return 0;
}
```

在 macOS arm64 上執行：

```text
鎖順序相反：
  evict （cache → stats）：等第二把鎖 100 ms 仍拿不到
  report（stats → cache）：等第二把鎖 100 ms 仍拿不到
統一鎖順序：
  evict （cache → stats）：完成
  report（cache → stats）：完成
```

第一組重現了 progress graph 上的 D 區：兩個 thread 各拿到一把鎖，都在等對方的那一把。第二組統一順序之後，後來的 thread 會在**第一把鎖**就停下來等，而不是拿著一把鎖去等另一把，因此不可能形成循環。程式用 `arrived` 計數讓兩邊都先拿到第一把鎖，是為了讓壞的交錯每次都發生；真實程式沒有這個安排，壞交錯只是偶爾發生，這正是 deadlock 難以重現的原因。

### 其他常見的 deadlock

鎖順序相反是最典型的情況，但不是唯一的情況：

- **自己鎖自己**：同一個 thread 對一個預設型別的 mutex lock 兩次（例如 A 函式持鎖呼叫了 B 函式，B 又去拿同一把鎖）。預設 mutex 的這種行為是未定義或直接卡住；用 `PTHREAD_MUTEX_ERRORCHECK` 可以在開發時抓出來。
- **semaphore 的順序錯**：31.7 節提過，producer 先拿 mutex 再等 `slots`，會抱著鎖睡覺。
- **拿著鎖等 I/O 或等別的 thread**：持有 `cache_lock` 時去 `pthread_join` 一個也需要 `cache_lock` 的 thread。
- **signal handler 裡拿鎖**：handler 打斷了正持有 malloc 內部鎖的 thread，handler 裡又呼叫 `malloc`，同一個 thread 等自己。這就是第 22 章要求 handler 只能用 async-signal-safe 函式的原因之一。

## 31.9 動手做：重現 race、修好它、用 ThreadSanitizer 抓出來

### 程式一：計數器的三種寫法

這段程式讓 2 個 thread 各對共享計數器加 1,000,000 次。第一種沒有同步，執行 5 次；第二種用 mutex；第三種用 C11 的 `atomic_fetch_add`。每種都量測耗時（存成 `race.c`）。

```c
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <time.h>

#define NITERS 1000000
#define NTHREADS 2

/* volatile 只是讓編譯器每次真的去記憶體讀寫，方便看到 race；它「不能」修好 race */
static volatile long cnt_racy;
static long cnt_mutex;
static atomic_long cnt_atomic;
static pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;

static void *racy(void *arg)  { (void)arg; for (int i = 0; i < NITERS; i++) cnt_racy++; return NULL; }
static void *locked(void *arg) {
    (void)arg;
    for (int i = 0; i < NITERS; i++) {
        pthread_mutex_lock(&mu);
        cnt_mutex++;
        pthread_mutex_unlock(&mu);
    }
    return NULL;
}
static void *atomic(void *arg) {
    (void)arg;
    for (int i = 0; i < NITERS; i++) atomic_fetch_add(&cnt_atomic, 1);
    return NULL;
}

static double run(void *(*fn)(void *)) {
    struct timespec a, b;
    pthread_t t[NTHREADS];
    clock_gettime(CLOCK_MONOTONIC, &a);
    for (int i = 0; i < NTHREADS; i++) pthread_create(&t[i], NULL, fn, NULL);
    for (int i = 0; i < NTHREADS; i++) pthread_join(t[i], NULL);
    clock_gettime(CLOCK_MONOTONIC, &b);
    return (b.tv_sec - a.tv_sec) * 1e3 + (b.tv_nsec - a.tv_nsec) / 1e6;
}

int main(void) {
    printf("預期結果：%d\n", NITERS * NTHREADS);
    for (int r = 1; r <= 5; r++) {
        cnt_racy = 0;
        double ms = run(racy);
        printf("沒有同步   第 %d 次：%8ld（少了 %7ld）%7.1f ms\n",
               r, cnt_racy, (long)NITERS * NTHREADS - cnt_racy, ms);
    }
    double ms = run(locked);
    printf("mutex             ：%8ld              %7.1f ms\n", cnt_mutex, ms);
    ms = run(atomic);
    printf("atomic_fetch_add  ：%8ld              %7.1f ms\n", atomic_load(&cnt_atomic), ms);
    return 0;
}
```

在 macOS arm64（Apple clang 21，`-O1`）上執行兩次。注意：**沒有同步的那幾行，結果每次都不同，在不同機器、不同負載下也會不同**，下面只是本機某兩次的實際數字：

```text

沒有同步   第 1 次： 1005129（少了  994871）    1.1 ms
沒有同步   第 2 次： 1030023（少了  969977）    1.3 ms
沒有同步   第 3 次： 1005005（少了  994995）    1.1 ms
沒有同步   第 4 次： 1007027（少了  992973）    1.1 ms
沒有同步   第 5 次： 1089890（少了  910110）    1.2 ms
mutex             ： 2000000                 14.5 ms
atomic_fetch_add  ： 2000000                  8.3 ms
```

```text
預期結果：2000000
沒有同步   第 1 次： 1005686（少了  994314）    1.1 ms
沒有同步   第 2 次： 1042732（少了  957268）    1.1 ms
沒有同步   第 3 次： 1088030（少了  911970）    1.3 ms
沒有同步   第 4 次： 1004364（少了  995636）    1.1 ms
沒有同步   第 5 次： 1017079（少了  982921）    1.1 ms
mutex             ： 2000000                 14.2 ms
atomic_fetch_add  ： 2000000                  8.1 ms
```

逐步解讀：

1. **在這兩次執行中，沒有同步的版本遺失了約 45% 到 50% 的更新**，而且 10 次執行的結果沒有一次相同。這台機器有 14 個核心，兩個 thread 真的同時在兩個核心上跑，L、U、S 交錯得非常密集，遺失比例遠高於 `thumbd` 的 3%（`thumbd` 的計數器只在每個請求結束時加一次，兩次加法之間隔著數毫秒的其他工作，撞在一起的機會小得多）。在單核心或負載不同的機器上，數字會完全不同。不要把這些數字當成規律，要記住的是「結果不確定」本身。
2. **`volatile` 沒有任何幫助**。計數器宣告為 `volatile long`，每一圈都真的讀寫記憶體，但讀－改－寫仍然不是 atomic，31.3 節的組合語言已經說明原因。
3. **mutex 與 atomic 都每次正確**。代價是時間：沒有同步約 1 ms，atomic 約 8 ms，mutex 約 14 ms。後兩者慢，是因為兩個核心不斷爭奪同一個 cache line 與同一把鎖，這是第 32 章的主題。對 `thumbd` 而言，每個請求只加一次，這點成本完全可以忽略；正確性永遠優先。
4. **atomic 適合單一變數，mutex 適合一組 invariant**。`record` 要同時更新三個計數器並維持「總數 = 命中 + 失誤」，三個各自 atomic 仍然可能讓讀取的人看到中間狀態；這時用一把 mutex 更簡單、也更正確。

### 程式二：用 ThreadSanitizer 抓 race

Race 最麻煩的是「測試時通常不出現」。**ThreadSanitizer**（TSan）是 Clang 與 GCC 內建的 race 偵測工具：編譯時在每次記憶體存取與同步操作旁邊插入檢查，執行時記錄每個 thread 對每個位址的存取，以及 thread 之間透過鎖、`pthread_create`、`pthread_join` 建立的 **happens-before**（先發生於）關係。只要兩個 thread 存取同一個位址、至少一個是寫入、而且兩次存取之間沒有 happens-before 關係，就報告 data race。

下面是 `thumbd` 計數器的縮小版，每個 thread 只加 1,000 次（存成 `stats.c`）：

```c
#include <pthread.h>
#include <stdio.h>

static long cache_hits;                 /* thumbd 的快取命中計數器，沒有任何保護 */

static void *worker(void *arg) {
    (void)arg;
    for (int i = 0; i < 1000; i++) cache_hits++;
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, worker, NULL);
    pthread_create(&b, NULL, worker, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("cache_hits = %ld\n", cache_hits);
    return 0;
}
```

用 TSan 編譯並執行（macOS arm64，Apple clang 21）：

```bash
clang -fsanitize=thread -g -O1 stats.c -o stats-tsan
./stats-tsan
```

```text
==================
WARNING: ThreadSanitizer: data race (pid=23747)
  Write of size 8 at 0x000104564000 by thread T2:
    #0 worker stats.c:8 (stats-tsan:arm64+0x10000074c)

  Previous write of size 8 at 0x000104564000 by thread T1:
    #0 worker stats.c:8 (stats-tsan:arm64+0x10000074c)

  Location is global 'cache_hits' at 0x000104564000 (stats-tsan+0x100008000)

  Thread T2 (tid=54684136, running) created by main thread at:
    #0 pthread_create <null> (libclang_rt.tsan_osx_dynamic.dylib:arm64e+0x33834)
    #1 main stats.c:15 (stats-tsan:arm64+0x1000006bc)

  Thread T1 (tid=54684135, finished) created by main thread at:
    #0 pthread_create <null> (libclang_rt.tsan_osx_dynamic.dylib:arm64e+0x33834)
    #1 main stats.c:14 (stats-tsan:arm64+0x1000006a8)

SUMMARY: ThreadSanitizer: data race stats.c:8 in worker
==================
cache_hits = 2000
ThreadSanitizer: reported 1 warnings
```

逐步解讀這份報告：

1. **最關鍵的一行是 `cache_hits = 2000`**：這次執行的結果是正確的。T1 被報告為 `finished`，表示 T2 寫入時 T1 已經跑完，這次很可能根本沒有真的交錯。TSan 仍然報告了 race，因為它檢查的是「兩次存取之間有沒有同步」，而不是「結果有沒有錯」。這是 TSan 最大的價值：**它能在 race 還沒造成錯誤時就抓到它**，不必靠運氣碰到壞的交錯。
2. 前兩段指出兩次衝突的存取：T2 在 `stats.c` 第 8 行寫入，T1 之前也在同一行寫入同一個 8-byte 位址。
3. `Location is global 'cache_hits'` 直接說出是哪個變數。如果是 heap 上的物件，這裡會顯示它是在哪裡 `malloc` 的。
4. 最後兩段說明兩個 thread 分別是在 `main` 的第 14、15 行建立的，幫助你從呼叫路徑追回是哪一段程式碼啟動了它們。
5. 程式的結束碼不是 0（本機 macOS 為 134：macOS 上 TSan 預設 `abort_on_error=1`，回報後呼叫 `abort`；改成 `TSAN_OPTIONS=abort_on_error=0` 時，本機實測以 TSan 的預設結束碼 66 結束），所以在 CI 中跑 TSan 版本的測試，發現 race 時測試會失敗。

TSan 的成本不低：Clang 文件指出典型的執行速度會慢 5–15 倍、記憶體用量增加 5–10 倍，所以它適合跑在測試與壓測環境，而不是 production。另外 TSan 只能抓到**執行時真的走過**的程式路徑；沒被測試覆蓋到的 race，它看不見。在 Linux 上，TSan 也會偵測鎖順序相反（報告 `lock-order-inversion (potential deadlock)`），即使那次執行沒有真的卡住；本機 macOS 的 TSan 實測不會報告這類問題（即使把 31.8 節的程式改成一般的 `pthread_mutex_lock`、讓兩種順序先後執行而不真的卡住，也沒有報告），這部分要在 Linux 上做；測試時用一般的 lock，不要用 trylock，因為 trylock 拿不到時會退讓，本身不構成 deadlock。

## 31.10 在工作上怎麼用

### 情境一：數字對不上、偶發當機，懷疑 race

`thumbd` 的兩個症狀（計數少算、串列損壞當機）是 race 最典型的表現。排查流程：

```text
 症狀：統計數字對不上 / 偶發、無法重現的當機 / 只在高流量時出錯
   │
   ├─ 1. 列出共享狀態：全域變數、static、在 thread 間傳遞的指標（31.2 節的表）
   │
   ├─ 2. 用 TSan 建置並跑測試與壓測
   │      clang -fsanitize=thread -g -O1 ...
   │      └─ 有報告 → 依報告的兩個存取位置找出缺少同步的地方
   │
   ├─ 3. TSan 沒報告但仍懷疑 → 增加並行壓力
   │      更多 thread、更多核心、壓測時間拉長、在可疑位置附近插入 sched_yield()
   │
   └─ 4. 修正：決定每份共享資料由哪把鎖保護（寫進註解），
            或改成不共享（thread-local 統計、最後再加總；不可變資料）
```

`thumbd` 這一次的修法：三個統計計數器改由同一把 `stats_mu` 保護（31.6 節的 `record`），先求正確。第 32 章會看到，thread 變多之後這類共享計數會變成效能瓶頸，屆時再改成每個 worker 一份計數、`/stats` 被呼叫時加總；那時要注意兩個細節：`_Thread_local` 變數別的 thread 無法用名字讀到，必須讓每個 worker 把自己那份的位址登記起來，而且 `/stats` 讀取時 worker 仍在寫，每份計數器要宣告成 atomic（relaxed 的讀寫即可），否則加總本身又是一個 data race。LRU 串列則統一由 `cache_lock` 保護，並在程式碼中寫明「`lru_*` 函式呼叫前必須持有 `cache_lock`」。修完之後，在 CI 中加入一個以 TSan 建置、跑 10 秒壓測的 job。

### 情境二：服務卡住、CPU 為 0，懷疑 deadlock

當服務完全不回應、CPU 使用率卻接近 0 時，大家都在等某件事。在 Linux 上：

```bash
# 抓所有 thread 的 stack trace
gdb -p "$(pidof thumbd)" -batch -ex "thread apply all bt" > /tmp/bt.txt

# 找出停在拿鎖的 thread（glibc 中常見的函式名稱，依版本而異）
grep -n -B2 -A8 "pthread_mutex_lock\|__lll_lock_wait\|futex_wait" /tmp/bt.txt
```

判讀方式：如果看到 thread A 的 stack 是 `render_stats_page → pthread_mutex_lock`，而它拿著 `stats_lock`；thread B 是 `evict_old_entries → pthread_mutex_lock`，拿著 `cache_lock`，就找到了循環。在 gdb 中可以用 `print cache_lock` 看 glibc mutex 內部的 `__owner` 欄位，得知目前是哪個 TID 持有這把鎖（欄位名稱依 glibc 版本而定）。修法是依照 31.8 節統一鎖順序，並把鎖順序寫進團隊的程式規範。

如果大家不是停在拿鎖，而是停在 `pthread_cond_wait`，就要懷疑 lost wakeup 或「條件永遠不會成立」：例如 producer 已經結束，但沒有人 broadcast 讓 consumer 下班。

### 情境三：審查多執行緒程式碼的檢查清單

審查有 thread 的 pull request 時，逐項問：

| 檢查項目 | 要找的問題 |
|---|---|
| 每份共享資料由哪一把鎖保護？有寫下來嗎？ | 沒有明確規則的共享變數，遲早會有人忘記上鎖 |
| 所有讀取路徑也有上鎖嗎？ | 「只鎖寫入、不鎖讀取」仍然是 data race，而且可能讀到撕裂的值 |
| 錯誤處理與提早 return 的路徑都有 unlock 嗎？ | 錯誤路徑忘記 unlock，下一個人就永遠卡住 |
| 會同時持有兩把以上的鎖嗎？順序一致嗎？ | 鎖順序不一致就有 deadlock 風險 |
| 持有鎖時有沒有做 I/O、呼叫外部函式、等待別的 thread？ | 鎖的範圍太大造成卡頓，也可能形成 deadlock |
| condition wait 有用 `while` 嗎？修改條件時有持鎖嗎？ | 虛假喚醒、lost wakeup |
| 「先檢查再動作」（check-then-act）是否在同一個 critical section 裡？ | 兩個 thread 都檢查到「快取沒有」，然後都去解碼同一張圖並重複插入 |
| 有沒有用 `volatile` 或 `sleep` 當作同步？ | 兩者都不是同步 |

最後一列的 check-then-act 值得特別說明。即使每個操作各自是 atomic 或各自有鎖，「查詢快取沒有 → 解碼 → 插入」這三步如果分開上鎖，兩個 thread 仍然可能同時查到「沒有」，各自解碼一次，再各自插入，造成重複工作或重複項目。這叫 **race condition**（競爭條件）：結果取決於 thread 的執行時序。它比 **data race**（兩個 thread 未經同步存取同一個位址，且至少一個是寫入）更廣：沒有 data race 的程式，仍然可能有 race condition。在 C11 中，data race 是 undefined behavior；race condition 則是邏輯錯誤，TSan 不一定抓得到。

## 31.11 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 計數器的值偏低，且每次執行都不同 | 多個 thread 對共享變數做讀－改－寫，沒有同步 | TSan 報告 data race；把迴圈次數加大更容易重現 | 用 mutex 或 `atomic_fetch_add`；或改成 thread-local 計數最後加總 |
| 偶發當機，core dump 停在串列或樹的操作 | 共享資料結構被多個 thread 同時修改 | TSan；在資料結構操作中加入 invariant 檢查（例如 `node->next->prev == node`） | 以一把鎖保護整個資料結構的所有讀寫路徑 |
| 服務卡住、CPU 為 0 | deadlock：鎖順序相反，或拿著鎖等待 | `gdb` 的 `thread apply all bt` 找出互相等待的 thread；Linux 上 TSan 報告 lock-order-inversion | 統一鎖順序；縮小持鎖範圍；避免同時持有多把鎖 |
| 某些 thread 永遠在 `pthread_cond_wait` 不醒 | lost wakeup（修改條件時未持鎖）、只 signal 一個但需要 broadcast、關閉時沒通知 | `thread apply all bt` 看等待的 condition；檢查修改條件的程式是否持有同一把 mutex | 修改條件與 signal 都在持鎖下進行；關閉時用 broadcast |
| 在 macOS 上同步完全失效，Linux 上正常 | `sem_init` 在 macOS 回傳 −1（`ENOSYS`），程式沒檢查 | 檢查 `sem_init` 的回傳值與 `errno`；編譯時的 deprecated 警告 | 改用 mutex＋condition variable、`dispatch_semaphore` 或 `sem_open` |
| writer 一直等不到，寫入延遲極高 | readers-writers 偏向 reader，reader 源源不絕造成 writer starvation | 量測 writer 等待鎖的時間 | 改用偏向 writer 或公平的策略；縮短讀取的 critical section |
| 加了 `volatile` 之後 race 還在 | `volatile` 不提供 atomicity 與跨 thread 的順序 | 看組合語言：沒有 `lock` 前綴或獨占指令 | 用 `<stdatomic.h>` 或 mutex |

## 本章重點整理

- 一個變數是否共享，取決於記憶體中的那一份是否被兩個以上的 thread 存取；全域變數與區域 `static` 變數整個 process 只有一份，區域自動變數的位址一旦傳出也會變成共享。
- `cnt++` 是讀出、加一、寫回三個步驟，即使編譯成一條 x86-64 的 `incq` 指令，在多核心上也不是 atomic；只有 `lock` 前綴或 ARM64 的獨占讀寫才保證不可分割。
- 兩個 thread 各做一次 `cnt++` 共有 20 種交錯，只有 2 種得到正確結果；只要存在壞的交錯，它遲早會在 production 發生。
- Progress graph 把交錯畫成路徑，unsafe region 是兩個 thread 同時位於 critical section 的區域；同步的目標是讓所有路徑都繞過它。
- Semaphore 是只能用 P、V 操作的非負計數器，binary semaphore 可以實現互斥，counting semaphore 可以表示可用資源的數量。
- macOS 不支援 `sem_init`，呼叫會回傳 −1 並設定 `ENOSYS`；可攜的程式要檢查回傳值，或用 mutex 加 condition variable 實作。
- Mutex 有擁有者，用來保護一組共享資料的 invariant；Linux 的 mutex 建立在 futex 上，沒有競爭時不進 kernel。
- Condition variable 讓 thread 等待條件成立，`pthread_cond_wait` 原子地釋放鎖並睡覺以避免 lost wakeup，而且必須在 `while` 迴圈中重新檢查條件。
- Producer-consumer 用 `slots`、`items`、`mutex` 三個 semaphore 實作有界 buffer；必須先等資源、再拿鎖，否則會抱著鎖睡覺。
- Readers-writers 允許多個 reader 同時讀、writer 獨占，偏向某一方的策略可能讓另一方 starvation。
- Deadlock 需要互斥、持有並等待、不可搶奪、循環等待四個條件同時成立；全域一致的鎖順序可以打破循環等待，是最實用的預防方法。
- `volatile` 和 `sleep` 都不是同步工具；跨 thread 的正確性要靠 mutex、condition variable、semaphore 或 atomic 操作。
- Data race 是兩個 thread 未經同步存取同一位址且至少一個是寫入，在 C 中是 undefined behavior；race condition 範圍更廣，包含 check-then-act 這類邏輯錯誤。
- ThreadSanitizer 依 happens-before 關係判斷 data race，能在結果剛好正確時就抓到 race，但只能檢查執行時真的走過的路徑，並有顯著的執行成本。

## 延伸問答

> [!question]- Q1. 為什麼 x86-64 上只有一條 `incq cnt(%rip)` 指令，仍然會發生 race？
> 「一條指令」是指令集層級的描述，不代表硬體執行時不可分割。`incq` 對記憶體運算元的操作，在處理器內部仍然是讀出 cache line 中的值、在執行單元加 1、再寫回三個動作。在多核心系統上，兩個核心可以各自讀到同一個舊值，各自加 1 再寫回，其中一次更新就被蓋掉了。
>
> 要讓整個讀－改－寫不可分割，x86-64 必須使用 `lock` 前綴（例如 `lock incq`），處理器會在操作期間獨占該 cache line，其他核心無法插入。C 語言中用 `atomic_fetch_add` 或 `atomic_long` 的 `++` 會產生這種指令。在 ARM64 上，普通的 `++` 甚至直接是 `ldr`、`add`、`str` 三條指令，atomic 版本則用獨占讀寫的重試迴圈或 LSE 的原子指令。

> [!question]- Q2. 手算題：三個 thread 各執行一次 `cnt++`（各 3 步），總共有幾種交錯？最後 `cnt` 可能是哪些值？
> 總共 9 步，分給三個 thread 各 3 步，交錯數是 9! ÷ (3! × 3! × 3!) = 362,880 ÷ 216 = 1,680 種。最後的值取決於每個 thread 讀到的值：如果三個 thread 的 L 都在任何 S 之前，三者都讀到 0，最後是 1；如果三者完全依序執行，最後是 3；中間的情況可以得到 2，例如前兩個 thread 交錯而遺失一次，第三個在兩者都寫回後才讀。
>
> 所以可能的值是 1、2、3，只有完全不交錯的 3! = 6 種排法（三個 thread 的先後順序）會得到正確的 3。用程式列舉全部 1,680 種的結果是：1,404 種得到 1、270 種得到 2、6 種得到 3。這個題目可以用 31.3 節的 `inter.py` 擴充成三個 thread 驗證。它也說明 thread 越多，正確的交錯所佔比例越小，race 越容易顯現。

> [!question]- Q3. Mutex 和 binary semaphore 都能做互斥，實務上為什麼保護共享資料時偏好 mutex？
> 最根本的差別是擁有者。Mutex 由 lock 它的 thread 擁有，只能由同一個 thread unlock，這讓系統與工具能理解「誰持有這把鎖」：錯誤檢查型的 mutex 能偵測重複 lock 或錯誤的 unlock，priority inheritance 能讓持鎖的低優先 thread 暫時提高優先權，除錯器與 TSan 也能把持鎖者與等待者連起來分析。
>
> Semaphore 沒有擁有者，任何 thread 都能 V，這讓它適合用來做計數與跨 thread 的通知（例如 producer-consumer 的 `slots` 與 `items`），但用來做互斥時，誤用（例如別的 thread 意外地 V）就無法被偵測。此外 macOS 不支援未命名的 POSIX semaphore，mutex 的可攜性更好。所以慣例是：互斥用 mutex，計數資源用 semaphore 或 condition variable。

> [!question]- Q4. 程式找錯：consumer 寫成 `pthread_mutex_lock(&mu); if (count == 0) pthread_cond_wait(&cv, &mu); item = buf[--count]; pthread_mutex_unlock(&mu);`，有什麼問題？
> 問題在於用 `if` 只檢查一次條件。`pthread_cond_wait` 返回不代表條件一定成立：POSIX 允許虛假喚醒，thread 可能在沒有人 signal 時醒來；即使真的被 signal，在它醒來到重新拿到 mutex 之間，另一個 consumer 可能已經先把唯一的項目拿走。這兩種情況下 `count` 仍然是 0，`--count` 會變成 −1，讀到 `buf[-1]`，造成越界存取與後續的資料損壞。
>
> 正確寫法是 `while (count == 0) pthread_cond_wait(&cv, &mu);`，醒來後重新檢查，條件不成立就繼續睡。這個 bug 在只有一個 consumer、且平台很少出現虛假喚醒時幾乎不會發生，增加 consumer 數量後才會出現，是典型的「測試沒問題、上線才出事」。

> [!question]- Q5. 你在 production 看到 `thumbd` 每隔幾天就完全不回應，CPU 接近 0%，重啟後恢復。你會怎麼查？
> CPU 接近 0 而且不回應，代表所有 worker 都在等待，而不是在忙著計算，最可疑的是 deadlock，其次是所有 worker 都在等一個卡住的下游 I/O。在重啟之前，先保留現場：用 `gdb -p PID -batch -ex "thread apply all bt"` 抓所有 thread 的 stack trace，或用 `gcore` 產生 core dump 事後分析。
>
> 分析時看每個 thread 停在哪裡。如果多個 thread 停在 `pthread_mutex_lock`，就找出各自持有哪些鎖（從 stack 上的呼叫路徑判斷，或在 gdb 中檢查 mutex 的 owner 欄位），畫出「誰等誰」的圖，找出循環。如果停在 `read`、`recv` 之類，則是下游 I/O 問題，要加 timeout。找到鎖的循環之後，統一鎖順序，並在 Linux 的測試環境以 TSan 跑壓測確認不再有 lock-order-inversion 報告。

> [!question]- Q6. 計數器改用 `atomic_long` 之後，TSan 不再報告了。`thumbd` 的快取「查詢 → 沒有就解碼並插入」流程是不是也安全了？
> 不一定。Atomic 只保證單一變數的單一操作不可分割，不保證多個操作組成的流程不可分割。「查詢快取、發現沒有、解碼、插入」如果查詢和插入分別在不同的 critical section 裡，兩個 thread 可以同時查到「沒有」，各自花時間解碼同一張圖，再先後插入，造成重複工作，甚至重複的快取項目或記憶體洩漏。
>
> 這是 race condition（check-then-act），不是 data race，所以 TSan 不會報告。修法有幾種：把查詢與插入放在同一把鎖保護的 critical section 中（但不要在持鎖時解碼，以免卡住其他人）；或在快取中先插入一個「解碼中」的佔位項目，其他 thread 看到它就等待結果，而不是自己再解碼一次。判斷標準是：一個 invariant 需要的所有讀寫，必須在同一個 critical section 中完成。

> [!question]- Q7. 面試題：什麼是 deadlock？列出發生的條件，並說明你在實務上怎麼避免。
> Deadlock 是一組 thread 全部阻塞，每一個都在等其他成員持有的資源，因此永遠無法前進。它需要四個條件同時成立：互斥（資源一次只給一個 thread）、持有並等待（拿著一個資源等另一個）、不可搶奪（不能強行拿走別人的資源）、循環等待（等待關係形成環）。打破任何一個就不會發生。
>
> 實務上最常用的是打破循環等待：替所有鎖定義全域順序，同時需要多把鎖時一律依序取得，並把順序寫進文件與程式註解。其次是避免持有並等待：縮小 critical section，不在持鎖時做 I/O 或呼叫外部程式碼，盡量不要同時持有兩把鎖（先複製需要的資料、放鎖，再拿下一把）。第三是用 `pthread_mutex_trylock` 加退讓重試來打破不可搶奪，但要小心退讓策略造成 livelock。再搭配 TSan 的 lock-order-inversion 偵測與 deadlock 時的 `thread apply all bt`，就能從預防與診斷兩端處理。

> [!question]- Q8. 為什麼 `pthread_cond_wait` 要求呼叫時持有 mutex，並且由它負責釋放與重新取得？
> 因為「檢查條件」和「開始等待」之間必須沒有空隙。consumer 在持鎖時檢查到 queue 是空的，決定要睡覺；如果它先自己 unlock，再呼叫一個單純的「睡覺」函式，在這兩步之間 producer 可能拿到鎖、放入工作、發出 signal。此時還沒有人在等，condition variable 也不會記住過去的 signal，這次通知就消失了；consumer 隨後睡著，可能永遠不會再被叫醒，這就是 lost wakeup。
>
> `pthread_cond_wait` 把「釋放 mutex」與「進入等待」合成一個不可分割的操作，producer 要修改條件（放入工作）就必須先拿到 mutex，而它拿到 mutex 時 consumer 必然已經在等待名單上，訊號就不會遺失。醒來時它重新取得 mutex 再返回，讓呼叫者可以在持鎖的情況下安全地重新檢查條件。這也是為什麼修改條件的一方，也必須在持有同一把 mutex 時修改。
