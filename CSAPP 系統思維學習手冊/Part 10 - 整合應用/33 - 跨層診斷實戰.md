# 第 33 章　跨層診斷實戰：從症狀一路追到根因

> [!abstract] 本章地圖
> **核心問題**：production 出事時，你只看得到最上層的症狀（當機、變慢、記憶體上升、連線卡住），根因卻可能在任何一層。怎麼有系統地一路往下追，再把答案帶回上層驗證？
>
> **你會學到**：
> - 用「定義症狀、縮小範圍、提出可反證的假設、逐層收集證據」的方法處理任何系統事故
> - 為六種最常見的 production 症狀各自走一遍完整的診斷流程，知道每一步該用哪個工具、看哪個數字
> - 熟練 core dump 與 gdb、`perf`、`/proc`、`strace`、`ss`、ASan、TSan 這些跨層工具，知道它們各自回答什麼問題
> - 把症狀對應回本書的章節，知道卡住時該回頭複習哪一章
> - 建立事前準備（符號、core dump、sanitizer、指標）與事後檢討的習慣
>
> **前置知識**：全書，尤其第 2 章（工具箱）、第 14 章（profiling）、第 23–26 章（虛擬記憶體與記憶體錯誤）、第 27–28 章（I/O 與 socket）、第 31–32 章（同步與並行效能）
>
> **對應 CS:APP 3e**：全書（第 1–12 章）的綜合應用

## 33.1 故事：一個月、六張事故單

小安在 `thumbd` 團隊滿一年，第一次排進 on-call。SRE 阿哲把上一季的事故單整理成一份清單交給小安，說：「這六件事，每一件都花了我們至少一個晚上。你把它們從頭走一遍，下次遇到就不會慌。」

| 編號 | 第一個警報或回報 | 最後找到的根因所在 |
|---|---|---|
| 事件一 | `thumbd` 每天當機幾次，systemd 自動重啟 | 整數溢位造成 heap overflow |
| 事件二 | 上線新功能後 p99 延遲變成三倍 | 存取模式毀掉 cache 與 TLB |
| 事件三 | RSS 三天內從 1.2 GB 漲到 6 GB，被 OOM killer 殺掉 | 錯誤路徑的 memory leak，加上 allocator 保留記憶體 |
| 事件四 | 半夜流量很低，某台機器 CPU 卻一直 100% | event loop 空轉 |
| 事件五 | 部分上傳請求卡住 60 秒後被 nginx 回 504 | short read 與遺失的緩衝資料 |
| 事件六 | 使用者回報偶爾看到別人的縮圖 | refcount 的 race 造成 use-after-free |

老周看了清單說：「你注意到沒有？第二欄全部是使用者看得到的現象，第三欄全部在本書的某一章裡。on-call 的工作就是在這兩欄之間搭橋。橋不能用猜的，要一層一層用證據鋪過去。」

這一章就是這六座橋。每一個事件都依同樣的格式寫：症狀、診斷流程圖、用到的工具與指令、根因、修復與驗證、對應的章節。先在 33.2、33.3 節建立通用的方法與工具地圖。

## 33.2 診斷的方法：往下鑽要有證據，往上走要能驗證

新手處理事故最常見的兩種失敗，一種是**亂槍打鳥**：看到延遲高就調 thread 數、看到記憶體高就重啟，問題暫時消失就結案；另一種是**一頭栽到最底層**：還沒確認是哪個版本、哪類請求出問題，就開始讀組合語言。成熟的做法是由上往下、一次一層，每往下一層都要有上一層的證據支持：

```text
 ① 使用者可見的症狀：錯誤率、延遲、當機、資源用量
      │  先回答：哪個版本？哪些機器？哪類請求？從什麼時候開始？最近改了什麼？
      ▼
 ② 應用層：請求路徑、log、指標、哪一段程式變慢或出錯
      │  證據：分路徑的延遲、錯誤 log、request id
      ▼
 ③ 執行期與函式庫：allocator、thread pool、鎖、佇列、動態連結的 library
      │  證據：thread backtrace、malloc 統計、鎖競爭、ldd
      ▼
 ④ 作業系統邊界：system call、page fault、signal、排程、file descriptor、socket
      │  證據：strace、/proc、ss、vmstat、dmesg
      ▼
 ⑤ 機器層：指令、分支、cache、TLB、記憶體頻寬
      │  證據：perf stat 的硬體計數器、perf record 的熱點、組合語言
      ▼
 ⑥ 找到根因 → 修復 → 回到 ① 用同樣的指標驗證症狀消失
```

這張圖有三個要點。第一，**最上面那一步最常被跳過**，卻最省時間：如果問題只出現在新版本、只出現在直式照片、只出現在某一台機器，搜尋範圍立刻縮小一大半。第二，**每一層都要提出可以被反證的假設**，例如「如果是 leak，那麼應用層的 live bytes 也應該一起上升」；然後去找能推翻它的證據，而不是只找支持它的證據。第三，**修好之後要回到最上層驗證**，同一個指標要恢復正常，而且要有回歸測試確保它不會再發生。

「可以被反證」具體長什麼樣？以事件二（33.5 節）為例，延遲上升時小安列出了四個假設，每個假設都寫下「如果它成立，我應該看到什麼」，再去看實際的證據：

| 假設 | 如果成立，應該看到 | 實際看到 | 結論 |
|---|---|---|---|
| 機器變慢或被其他服務搶資源 | 所有請求類型一起變慢；同機器其他服務也變慢 | 只有直式照片變慢 | 排除 |
| 新程式碼多了鎖或 I/O | thread 在等待，CPU 使用率不升；`strace` 有新的 system call | CPU 時間增加，沒有新的 system call | 排除 |
| 新功能的演算法做了太多工作 | 指令數大幅增加，IPC 正常 | 指令數只多一點，IPC 大降 | 不太可能 |
| 存取模式造成大量 cache 與 TLB miss | IPC 低，LLC 與 dTLB miss 高，熱點在新函式 | 全部吻合 | 保留，繼續驗證 |

這張表的價值在於它逼你在看證據之前先決定「什麼結果會推翻我」。只找支持證據的人，幾乎總能找到一些；能被推翻卻沒有被推翻的假設，才值得花時間深入。

還有一條鐵則：**先保存證據，再恢復服務**。重啟能讓服務恢復，也會毀掉 process 的記憶體、thread 狀態與 socket 狀態。只要情況允許，重啟前花一兩分鐘抓下 backtrace、`/proc` 資訊與 `ss` 的輸出（33.12 節有一份收集腳本），之後才有東西可以分析。

## 33.3 工具地圖：每一層用什麼看

工具很多，但每一個工具只回答特定層的特定問題。下表是本章會用到的工具，以及它們在本書的出處：

| 工具 | 看哪一層 | 回答的問題 | 本書章節 |
|---|---|---|---|
| core dump ＋ gdb（`bt`、`info locals`、`x`） | 應用、機器 | 當機那一刻在哪個函式、變數與記憶體是什麼 | 第 2、9 章 |
| ASan、UBSan | 應用 | 第一個越界、use-after-free、整數溢位發生在哪一行 | 第 5、11、26 章 |
| TSan | 應用、執行期 | 哪兩個 thread 沒有同步地存取同一個位址 | 第 31、32 章 |
| `perf stat` | 機器 | IPC、cache miss、TLB miss、分支預測失誤是否異常 | 第 12–14、16、17、23 章 |
| `perf record`／`perf top` | 應用、機器 | CPU 時間花在哪些函式（含 kernel） | 第 14 章 |
| `top -H`、`pidstat` | 作業系統 | 哪個 thread 在吃 CPU、context switch 多不多 | 第 20、32 章 |
| `/proc/PID/status`、`smaps_rollup`、`pmap` | 作業系統 | RSS 是匿名記憶體還是檔案頁、哪個區域在長 | 第 23、24 章 |
| `malloc_stats`、heaptrack、Valgrind | 執行期 | heap 裡活著的有多少、allocator 保留了多少 | 第 25、26 章 |
| `strace` | 作業系統邊界 | process 在做哪些 system call、卡在哪一個、回傳什麼 | 第 20、27 章 |
| `ss`、`lsof`、`/proc/PID/fd` | 作業系統 | 連線狀態、佇列中的位元組、fd 有沒有洩漏 | 第 27、28 章 |
| `dmesg`、`journalctl` | 作業系統 | kernel 記錄的 segfault、OOM kill | 第 22、24 章 |
| `ldd`、`readelf`、`nm` | 連結與載入 | 實際載入了哪個版本的 library、符號從哪來 | 第 18、19 章 |

工具本身會改變被觀察的系統。`strace` 會讓每個 system call 變慢許多倍，只適合短時間附加；`perf` 的取樣成本低，適合在 production 使用；sanitizer 會讓程式變慢數倍、記憶體用量變大，通常只在測試或 staging 環境使用。挑工具時要把這些成本算進去。

## 33.4 事件一：每天當機幾次的 segfault

**症狀。** 從某個週一開始，`thumbd` 每天當機三到五次，systemd 會自動重啟，所以使用者只看到零星的 502。`journalctl -u thumbd` 顯示 `code=dumped, status=11/SEGV`。

```text
 SIGSEGV（status=11）
   │
   ├─ 1. dmesg：kernel 記錄的 fault 位址、指令位址、在哪個 .so 裡
   │
   ├─ 2. 取得 core dump：coredumpctl list → coredumpctl gdb <PID>
   │      └─ bt：當機在哪？ ─┬─ 在自己的程式碼、指標是 NULL 或很小 → 直接看那一行
   │                          └─ 在 malloc／free 內部，或每次位置都不同 → heap 已被破壞
   │                               （當機點是受害者，不是兇手）
   ├─ 3. 找出觸發輸入：用 log 中當機前的 request id 找出那張圖
   │
   ├─ 4. 用 ASan 版本在 staging 重送那張圖 → 指出第一個越界寫入的那一行
   │
   └─ 5. 修復：大小計算改用 size_t 並檢查溢位；限制圖片尺寸；加回歸測試與 fuzzing
```

**工具與指令。** 先看 kernel 留下的紀錄，再打開 core dump：

```bash
dmesg | grep thumbd
# 示意輸出：thumbd[48213]: segfault at 7f2c3a400000 ip 00007f2c4b1e2a10 sp 00007f2c39ffe8d8 error 6 in libc.so.6
coredumpctl list thumbd
coredumpctl gdb 48213
(gdb) bt
(gdb) frame 3
(gdb) info locals
(gdb) p $_siginfo._sifields._sigfault.si_addr
```

`error 6` 是 x86 page fault 錯誤碼的位元組合：bit 1 表示寫入、bit 2 表示 user mode、bit 0 為 0 表示頁不存在，也就是「user mode 寫入一個不存在（沒有映射）的頁」；page fault 與 segfault 的關係見第 23 章。fault 位址落在 heap 區域的結尾附近，`bt` 顯示當機在 `libc` 的 `free` 內部，呼叫者是快取淘汰函式 `cache_evict`。另一個 core dump 卻當在 PNG 解碼的迴圈裡。

**根因。** 當機位置每次不同、而且在 allocator 內部，是 heap 被破壞的典型特徵：某段程式寫過了自己配置的範圍，蓋掉了相鄰 chunk 的 metadata（第 25 章），等到別人 `free` 或 `malloc` 時才出事。從 log 找出當機前處理的圖片，都是寬高異常大的 PNG。ASan 版本一跑就指出兇手：

```c
// not-runnable
uint32_t bytes = width * height * 4;   /* 32768 × 32768 × 4 = 2^32 → 溢位成 0 */
unsigned char *pixels = malloc(bytes);
```

`uint32_t` 的乘法是模 2^32 運算（第 5 章），32,768 × 32,768 × 4 = 2^32 剛好變成 0，`malloc(0)` 回傳一塊極小的記憶體，解碼器卻照 32,768 × 4 bytes 一列寫進去。這張圖是有人刻意構造的，這個 bug 同時也是一個安全漏洞（第 11 章）。

**排除了什麼。** 老周一開始懷疑是同一週的系統更新換掉了 libpng（第 19 章的 ABI 問題），但用 `ldd` 與 core dump 中記錄的 library 路徑比對，載入的 libpng 版本和更新前相同，而且只有特定圖片會觸發，所以排除。也有人懷疑是 stack overflow（遞迴太深），但 fault 位址在 heap 區域、不在任何 thread 的 stack 附近，同樣排除。

**修復與驗證。** 大小計算改用 `size_t` 並以 `__builtin_mul_overflow` 檢查；解碼前先拒絕超過上限（例如 1 億像素）的圖片；把這張圖加進回歸測試；在 CI 對解碼路徑加上 ASan 與 fuzzing。上線後 SEGV 歸零。

**對應章節：** 第 2 章（gdb）、第 5 章（整數溢位）、第 9 章（stack trace 從哪來）、第 11 章（記憶體安全）、第 23 章（page fault 與 segfault）、第 25 章（heap metadata）、第 26 章（ASan）。

## 33.5 事件二：新功能上線後 p99 延遲變成三倍

**症狀。** 「依 EXIF 自動轉正」功能上線後，整體 p99 從 40 ms 升到 120 ms。CPU 使用率只多了一點，程式也沒有新增任何鎖或 I/O。

```text
 p99 延遲上升
   │
   ├─ 1. 拆開看：按請求類型分組的延遲 → 只有需要旋轉 90° 的直式照片變慢
   │
   ├─ 2. perf record -g（只取樣那段時間）→ 熱點在 rotate90()
   │
   ├─ 3. perf stat 比較旋轉與不旋轉的請求
   │      ├─ IPC 很低、LLC miss 與 dTLB miss 很高 → 記憶體存取模式問題
   │      └─ IPC 正常、指令數暴增 → 演算法或多做了工作
   │
   ├─ 4. 讀程式：寫入的 stride 是多少？ → 每次寫入跨一整列
   │
   └─ 5. 改成 tiling（分塊），重跑 perf stat 與延遲指標驗證
```

**工具與指令。**

```bash
perf record -g -p $(pidof thumbd) -- sleep 30
perf report --no-children --sort symbol
perf stat -e cycles,instructions,LLC-load-misses,dTLB-load-misses -p $(pidof thumbd) -- sleep 30
```

`perf report` 顯示七成的取樣落在 `rotate90`。`perf stat` 的 IPC（instructions ÷ cycles）在旋轉請求下降到 0.4 左右，正常的縮放路徑約為 2；LLC miss 與 dTLB miss 都高出一個數量級。（以上為示意數字，實際依 CPU 而定。）

**根因。** 程式依序讀來源的每一列，寫到目的地的每一**行**：

```c
// not-runnable
for (int y = 0; y < h; y++)
    for (int x = 0; x < w; x++)
        dst[x * h + (h - 1 - y)] = src[y * w + x];   /* 讀是 stride 1，寫是 stride h */
```

手算一張 4,000 × 3,000、每像素 4 bytes 的照片：目的地每一列有 3,000 像素，寫入的 stride 是 3,000 × 4 = 12,000 bytes。每一次寫入都落在不同的 cache line（64 bytes），而且大約每一次都落在不同的 4 KiB page，因為 12,000 > 4,096。內層迴圈跑完一列來源就寫了 4,000 條不同的 cache line、4,000 個不同的 page，遠超過 L1 的容量與 TLB 的 entry 數（第 16、23 章）。下一列來源寫入的是緊鄰的位址，但那些 line 早就被擠出 cache 了。

**修復與驗證。** 改成第 17 章的 blocking：把影像切成 64 × 64 的方塊，一次轉完一個方塊。一個方塊的來源與目的地各 64 × 64 × 4 = 16 KiB，可以同時留在 L1 或 L2 裡，每條 line 被搬進來後會被用滿。修改後重跑同樣的 `perf stat`，IPC 回到接近縮放路徑的水準，p99 回到 42 ms。

**對應章節：** 第 12–13 章（IPC）、第 14 章（profiling）、第 15 章（locality）、第 16 章（cache 組織與 miss 類型）、第 17 章（stride、blocking）、第 23 章（TLB）。

## 33.6 事件三：RSS 三天漲到 6 GB

**症狀。** 監控顯示 `thumbd` 的 RSS 每天穩定增加約 1.5 GB，第三天被 kernel 的 OOM killer 殺掉，`dmesg` 有 `Out of memory: Killed process ... (thumbd)`。

這類事件最重要的第一步是**分辨三種完全不同的「記憶體上升」**：真的 leak、allocator 保留或碎片、以及被算進來的檔案頁。

```text
 RSS 持續上升
   │
   ├─ 1. /proc/PID/smaps_rollup（或 status）：分開看 RssAnon 與 RssFile
   │      ├─ 長的是 RssFile → mmap 的檔案頁，kernel 可回收，通常不是 leak（第 24 章）
   │      └─ 長的是 RssAnon → heap 或匿名 mmap，繼續往下
   │
   ├─ 2. 比較「程式認為自己用了多少」與「allocator 向 OS 要了多少」
   │      ├─ 應用層 live bytes（快取大小指標）、malloc 的 in-use 一起長 → leak
   │      └─ in-use 平穩，但 allocator 的 system bytes 一直長 → 碎片或保留（第 25 章）
   │
   ├─ 3. leak：在 staging 用 heaptrack、Valgrind 或 LeakSanitizer 重放流量，找出配置點
   │
   └─ 4. 修復後在固定負載下觀察 RSS 曲線：應該在某個水位持平
```

**工具與指令。**

```bash
grep -E 'Rss|Pss' /proc/$(pidof thumbd)/smaps_rollup
pmap -x $(pidof thumbd) | sort -k3 -n | tail -5
gdb -p $(pidof thumbd) -batch -ex 'call (void) malloc_stats()'   # glibc：輸出寫到 thumbd 的 stderr
free -m
```

`smaps_rollup` 顯示 RssAnon 約 5.6 GB、RssFile 只有 0.3 GB，所以不是檔案頁。阿哲一開始指著 `free -m` 裡 20 GB 的 `buff/cache` 說「記憶體都被吃掉了」，那其實是整台機器的 page cache（第 27 章），kernel 在需要時會回收，和 `thumbd` 的 OOM 無關。`malloc_stats` 顯示 in-use 的位元組一直在長，但 `thumbd` 自己的快取大小指標持平在 1 GB，兩者的差距就是沒有人記得的記憶體。

**根因。** 在 staging 用 heaptrack 重放一小時的 production 流量，最大的「配置了卻沒釋放」來源指向 JPEG 解碼函式：

```c
// not-runnable
unsigned char *buf = malloc(len);
if (decode_jpeg(src, buf, len) != 0)
    return -1;                /* bug：錯誤路徑忘了 free(buf) */
```

只有損壞的 JPEG 會走到這條路徑，流量中約 0.5% 是這種檔案，所以 leak 的速度很穩定（第 26 章）。另外，heap 的 system bytes 比 in-use 多出不少：glibc 會為多個 thread 建立多個 arena（第 25 章），每個 arena 各自保留釋放後的空間，這部分是保留而不是 leak。

**為什麼 RSS 不會在 free 之後立刻下降。** 即使沒有 leak，`free` 也不一定把記憶體還給作業系統：allocator 會把釋放的區塊留在自己的 free list 裡供下次使用，只有位於 heap 頂端的大塊空間、或用 `mmap` 單獨配置的大區塊，才比較容易被歸還（第 25 章）。所以「流量高峰過後 RSS 沒有降回來」本身不是 leak 的證據；**在固定負載下持續上升、沒有水位**才是。

**修復與驗證。** 錯誤路徑改成統一的 `goto cleanup` 釋放資源；在 CI 加入損壞檔案的測試，並在 Linux 的 ASan 版本中開啟 LeakSanitizer。修復後在固定負載下 RSS 在約 1.8 GB 持平。arena 的保留量是另一個議題，可以評估 `MALLOC_ARENA_MAX` 或改用 jemalloc 等 allocator，但要先量測，不要和 leak 混為一談。

**對應章節：** 第 23 章（VSZ 與 RSS）、第 24 章（匿名頁與檔案頁、PSS、OOM killer）、第 25 章（allocator、arena、碎片）、第 26 章（leak 與檢測工具）、第 27 章（page cache）。

## 33.7 事件四：流量很低，CPU 卻一直 100%

**症狀。** `thumbd` 改成用 epoll 處理連線（第 30 章）之後，半夜流量只有白天的十分之一，某幾台機器的 CPU 卻有一個核心一直 100%。

```text
 CPU 100%
   │
   ├─ 1. top -H -p PID：是哪個 thread？ → thumbd-io（event loop thread）
   │
   ├─ 2. 是 user 還是 sys？（top 的 %us／%sy，或 pidstat -u -t）
   │      ├─ 主要是 user → perf top -t TID：哪個函式在跑？
   │      │     └─ 例如倒數迴圈用 size_t、i >= 0 永遠成立（第 4 章），或自旋等鎖
   │      └─ 主要是 sys → 在瘋狂做 system call：看第 3 步
   │
   ├─ 3. strace -c -p TID（只附加 10 秒）：哪個 system call 最多？
   │      └─ epoll_wait 每秒數十萬次，幾乎每次立刻回傳
   │
   ├─ 4. strace -p TID -e trace=epoll_wait：回傳了什麼事件？ → 一直是 EPOLLOUT
   │
   └─ 5. 修復：只有在有資料待送時才註冊 EPOLLOUT，送完就移除
```

**工具與指令。**

```bash
top -H -p $(pidof thumbd)
perf top -t <TID>
timeout 10 strace -c -p <TID>
timeout 2 strace -p <TID> -e trace=epoll_wait
```

`perf top` 顯示時間大多在 kernel 的 epoll 相關函式與 system call 進出的路徑上。`strace -c` 的摘要中，`epoll_wait` 佔了 99% 以上的呼叫次數；逐筆看則是每次回傳 1 個事件，事件類型是 `EPOLLOUT`。（以上為 Linux 上的示意情況。）

**根因。** 新的 event loop 在接受連線時，把每個 socket 都註冊成 `EPOLLIN | EPOLLOUT`，而且是預設的 level-triggered 模式。socket 的傳送緩衝區只要還有空間就是「可寫」，幾乎永遠成立，所以只要有任何一條閒置的 keep-alive 連線，`epoll_wait` 就會立刻回傳「這個 fd 可寫」，loop 發現沒有東西要寫，又回去呼叫 `epoll_wait`。這是一個不睡覺的忙碌迴圈，流量越低反而越明顯，因為白天時 loop 至少在做有用的事。

**修復與驗證。** 平時只註冊 `EPOLLIN`；當 `write` 遇到 short write 或 `EAGAIN`、有資料留在應用層的輸出緩衝時，才用 `epoll_ctl` 加上 `EPOLLOUT`，送完再移除。修復後閒置時 CPU 降到接近 0，`strace -c` 中 `epoll_wait` 的次數與實際事件數相符。

如果第 2 步發現是 user time，就是另一條路：`perf top` 找出熱點函式後，用 `gdb -p` 附加、隔幾秒取幾次 `thread apply all bt`，看那個 thread 是否一直停在同一個迴圈裡，再印出迴圈變數。第 4 章的 `for (size_t i = n - 1; i >= 0; i--)` 就會讓 `i` 變成一個極大的數字，並且永遠繞不出去。

**對應章節：** 第 4 章（unsigned 迴圈陷阱）、第 14 章（profiling）、第 20 章（user mode 與 kernel mode、system call）、第 30 章（epoll 與 event-driven server）。

## 33.8 事件五：上傳請求卡住 60 秒

**症狀。** 大約 1% 的上傳請求（POST 一張原圖）卡住，直到 nginx 的 60 秒 upstream timeout 才回 504。同時監控顯示 `thumbd` 的 open fd 數量每天緩慢上升。

```text
 請求卡住、最後 timeout
   │
   ├─ 1. nginx log：upstream timed out → 卡在 thumbd，不是 client 端
   │
   ├─ 2. ss -tanp：卡住的連線狀態？Recv-Q 有沒有資料？
   │      ├─ ESTABLISHED、Recv-Q 為 0 → thumbd 在等「不會再來」的資料
   │      └─ CLOSE_WAIT 一直累積 → 對方已關閉，thumbd 沒有 close（fd 洩漏）
   │
   ├─ 3. gdb -p PID -batch -ex 'thread apply all bt'：worker 停在哪？
   │      └─ 好幾個 worker 卡在 read_body() 裡的 read()
   │
   ├─ 4. strace -f -p PID -e trace=read：read 要求多少 bytes？阻塞在哪個 fd？
   │
   └─ 5. 讀程式：header 讀取多讀到的 body 去哪了？read 回傳 0 時怎麼處理？
```

**工具與指令。**

```bash
ss -tanp state established '( sport = :8080 )'
ss -tan state close-wait '( sport = :8080 )' | wc -l
ls /proc/$(pidof thumbd)/fd | wc -l
gdb -p $(pidof thumbd) -batch -ex 'thread apply all bt' > /tmp/thumbd-bt.txt
timeout 5 strace -f -p $(pidof thumbd) -e trace=read,close
```

`ss` 顯示卡住的連線是 ESTABLISHED，`Recv-Q` 是 0：kernel 裡沒有任何待讀的資料，`thumbd` 卻還在 `read`。backtrace 證實 worker 停在 `read_body` 的 `read`。

**根因。** 讀 header 的程式一次 `read` 4 KiB 到緩衝區，找到 `\r\n\r\n` 後就開始解析。但 TCP 是 byte stream（第 28 章），那一次 `read` 很可能已經把 body 的前幾百 bytes 一起讀進來了。`read_body` 卻直接從 socket 讀 `Content-Length` 個 bytes，**忽略了緩衝區裡已經讀到的部分**，於是永遠在等最後那幾百 bytes，而那些 bytes 早就躺在 header 緩衝區裡。client 送完了在等回應，server 在等不會再來的資料，雙方都在等，直到 nginx 放棄。

fd 洩漏是同一段程式的第二個 bug：nginx timeout 後關閉連線，`read` 回傳 0（EOF），程式把它當成錯誤直接 `return`，卻沒有 `close(fd)`。這條連線就留在 CLOSE_WAIT：對方已經關了，我方從來沒關（第 27、28 章）。

**為什麼只有 1% 的請求卡住。** 這個 bug 只在「header 那次 `read` 剛好也讀到部分 body」時發生，而那取決於時序。nginx 轉送上傳時通常先送出 header、再陸續送出 body；如果 worker 在 body 到達之前就呼叫 `read`，只會拿到 header，後面的程式剛好正確。只有當 worker 晚了一點才 `read`（例如前一個請求剛處理完、或機器正忙），kernel 的接收緩衝裡已經同時有 header 和一部分 body，一次 `read` 全部拿到，bug 才會觸發。所以它在尖峰時段比較多，在開發機上幾乎不會出現：本機的 loopback 連線太快、太整齊了。這也是 short count 類 bug 的共同特性。

**修復與驗證。** 改用第 27 章 RIO 那種帶緩衝的讀取：header 與 body 都從同一個 per-connection 緩衝區取資料，緩衝區空了才呼叫 `read`；`read` 的每一種回傳值都明確處理（大於 0 累加、等於 0 是 EOF、小於 0 看 `errno`，`EINTR` 重試）；所有離開路徑都經過同一個 `close`；並用 `poll` 或 `SO_RCVTIMEO` 設定讀取逾時，讓任何等待都有上限。驗證方法是寫一個測試 client，故意把 request 切成很多小段、在任意位置停頓再送，33.11 節的程式就是它的縮影。

**對應章節：** 第 27 章（short count、RIO、fd 與關閉）、第 28 章（TCP byte stream、連線狀態、`ss`）、第 29 章（HTTP 解析、header 與 body）、第 30 章（逾時與並行模型）。

## 33.9 事件六：偶爾看到別人的縮圖

**症狀。** 每天有一兩位使用者回報「縮圖顯示的是陌生人的照片」，另外有極少量的 500 錯誤。這是隱私事故，優先級最高。問題無法在開發機上重現，只在尖峰時段出現。

```text
 偶發、無法重現、只在高併發出現
   │
   ├─ 1. 關聯：出錯的請求有什麼共同點？
   │      └─ 都命中快取、同一個快取分片、時間上和快取淘汰重疊
   │
   ├─ 2. 假設：快取項目在傳送途中被釋放並重新使用（use-after-free）
   │      └─ 為什麼會被提早釋放？→ 檢查 refcount 怎麼增減
   │
   ├─ 3. 在 staging 用 TSan 版本跑壓測（高併發、小快取、加速淘汰）
   │      └─ 數分鐘內回報 data race：refcount 在 shard 鎖外被修改
   │
   ├─ 4. 用 ASan 版本跑同樣壓測 → heap-use-after-free，確認後果
   │
   └─ 5. 修復：在持有分片鎖時就把 refcount 加一；refcount 改用 atomic；CI 加 TSan 壓測
```

**工具與指令。**

```bash
clang -g -O1 -fsanitize=thread -o thumbd-tsan *.c -lpthread
./thumbd-tsan --cache-size=64MB &
wrk -t16 -c256 -d300s http://staging:8080/thumb?id=...
```

把快取刻意調小，是為了讓淘汰更頻繁、讓 race 出現的機率提高；TSan 不需要真的撞上錯誤的交錯，只要兩個存取之間沒有 happens-before 關係就會回報（第 31 章）。

**根因。** 查快取的程式在分片鎖內找到項目，解鎖之後才把 `refcount` 加一；淘汰的 thread 則在鎖內檢查 `refcount == 0` 才釋放。兩個問題疊在一起：第一，「找到」與「加一」之間有一段空窗，淘汰者可能剛好在這段空窗看到 0 並釋放；第二，`refcount++` 本身沒有任何同步，兩個 worker 同時加一可能遺失一次更新（第 31 章），之後兩次減一就讓它提早歸零。被釋放的記憶體很快被 `malloc` 分配給下一張縮圖，正在傳送的 worker 於是把別人的影像送了出去。

**修復與驗證。** 規則改成「在鎖內拿到指標的同時就增加 refcount」，讓空窗消失；`refcount` 改成 `atomic_int`，減到 0 的那個 thread 負責釋放，遞減用 acq_rel 順序，確保釋放前看得到其他 thread 對項目的所有寫入（第 32 章）。TSan 壓測從此不再回報，並被加進每晚的 CI。上線後一個月內沒有再收到回報。

**對應章節：** 第 26 章（use-after-free）、第 31 章（race、mutex、TSan）、第 32 章（atomic 與 memory ordering）。

## 33.11 動手做：事故演練場

下面的程式把三個事件濃縮成可以在自己電腦上操作的版本。不帶參數執行時跑事件五的 short read 示範；`overflow` 模式重現事件一的整數溢位；`race` 模式重現事件六的 refcount race。

```c
#include <pthread.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <unistd.h>

/* 事件一的縮影：寬×高×4 用 32-bit 算，32768×32768×4 = 2^32 → 溢位成 0 */
static void incident_overflow(void) {
    uint32_t w = 32768, h = 32768;
    uint32_t bytes = w * h * 4;                  /* bug：應該用 size_t 並檢查溢位 */
    unsigned char *pixels = malloc(bytes);
    printf("要配置 %u bytes\n", bytes);
    for (uint32_t x = 0; x < w * 4; x++) pixels[x] = 0xFF;  /* 寫第一列就越界 */
    printf("第一列寫完，最後一個像素 = %u\n", pixels[w * 4 - 1]);
    free(pixels);
}

/* 事件六的縮影：兩個 worker 不加鎖地遞增同一個快取項目的 refcount */
static struct { volatile int refcount; } entry;   /* volatile 只為了讓迴圈不被最佳化掉 */
static void *incident_race(void *arg) {
    (void)arg;
    for (int i = 0; i < 1000000; i++) entry.refcount++;   /* 取得一個 reference */
    return NULL;
}

/* 事件五的縮影：client 分三段送出 request，server 只 read 一次 */
static void *slow_client(void *arg) {
    int fd = *(int *)arg;
    const char *parts[] = {"GET /thumb?id=42 HT", "TP/1.1\r\nHost: thumbd\r\n", "\r\n"};
    for (int i = 0; i < 3; i++) {
        write(fd, parts[i], strlen(parts[i]));
        usleep(20000);                           /* 模擬網路把資料切成好幾個 segment */
    }
    return NULL;
}

static void incident_short_read(void) {
    int sv[2];
    char buf[256];
    pthread_t t;
    if (socketpair(AF_UNIX, SOCK_STREAM, 0, sv) < 0) { perror("socketpair"); exit(1); }
    pthread_create(&t, NULL, slow_client, &sv[1]);
    usleep(5000);
    ssize_t n = read(sv[0], buf, sizeof buf - 1); /* 天真的寫法：以為一次就讀完 */
    if (n <= 0) { perror("read"); exit(1); }
    buf[n] = '\0';
    printf("只 read 一次：拿到 %zd bytes：\"%s\"\n", n, buf);
    size_t total = (size_t)n;                     /* 正確的寫法：讀到 header 結尾為止 */
    while (!strstr(buf, "\r\n\r\n") && (n = read(sv[0], buf + total, sizeof buf - 1 - total)) > 0) {
        total += (size_t)n;
        buf[total] = '\0';
        printf("  再 read 一次：+%zd bytes，累計 %zu\n", n, total);
    }
    printf("讀到完整 header，共 %zu bytes\n", total);
    pthread_join(t, NULL);
    close(sv[0]);
    close(sv[1]);
}

int main(int argc, char **argv) {
    const char *mode = argc > 1 ? argv[1] : "shortread";
    if (strcmp(mode, "overflow") == 0) incident_overflow();
    else if (strcmp(mode, "race") == 0) {
        pthread_t a, b;
        pthread_create(&a, NULL, incident_race, NULL);
        pthread_create(&b, NULL, incident_race, NULL);
        pthread_join(a, NULL);
        pthread_join(b, NULL);
        printf("refcount 最後是 %d（應該是 2000000）\n", entry.refcount);
    } else incident_short_read();
    return 0;
}
```

以下輸出都在 macOS arm64（Apple clang 21）上實際執行取得，存成 `drill.c`，用 `cc -std=c17 -O1 -Wall -Wextra -o drill drill.c` 編譯。

### 演練一：short read（不帶參數）

```text
只 read 一次：拿到 19 bytes："GET /thumb?id=42 HT"
  再 read 一次：+22 bytes，累計 41
  再 read 一次：+2 bytes，累計 43
讀到完整 header，共 43 bytes
```

client 分三次送出 43 bytes，第一次 `read` 只拿到 19 bytes，連 request line 都斷在 `HT` 中間。如果程式在這裡就開始解析，會得到一個無效的 HTTP 版本；如果它以為 header 已經讀完、轉去讀 body，就會像事件五一樣一直等下去。正確的寫法是在迴圈中讀到 `\r\n\r\n` 為止，而且每次都從上次的結尾接著放。真實的網路比 socketpair 更容易切段：TCP segment 大小、nginx 的緩衝、client 的寫法都會影響每次 `read` 拿到多少（第 27、28 章）。

### 演練二：整數溢位與 heap overflow（`overflow`）

先直接執行（把 stdout 導向檔案，模擬 systemd 或 CI 收集 log 的情況），再在 lldb 裡執行：

```bash
./drill overflow > out.txt; echo "exit=$?"; cat out.txt
lldb --batch -o "run overflow" ./drill
```


```text

第一列寫完，最後一個像素 = 255

Process 21815 exited with status = 0 (0x00000000)
```

這兩段輸出本身就是一堂課：

1. **直接執行時 process 死於 signal**：138 = 128 + 10，macOS 上 10 號是 SIGBUS（在 Linux 上同樣的 bug 通常表現為 SIGSEGV）。而且因為 stdout 被導向檔案而不是終端機，stdio 改用完整緩衝，`printf` 的內容還在 stdio 緩衝區裡就隨著 process 一起消失了（第 27 章），所以 `out.txt` 是空的，連「要配置 0 bytes」都沒有留下（如果 stdout 直接接終端機，是行緩衝，這一行會先印出來）。production 中「當機前最後幾行 log 不見了」常常就是這個原因。
2. **在 debugger 裡執行卻完全正常**，越界寫入沒有碰到未映射的位址，程式安然結束。debugger 會改變環境（記憶體配置、環境變數、時序），越界寫入是否立刻當機取決於它剛好蓋到哪裡。這就是為什麼事件一的 core dump 每次當在不同地方。
3. 結論：**沒當機不代表沒 bug**，要用工具直接抓住第一次越界。

改用 ASan 編譯（`clang -g -O0 -fsanitize=address -o drill_asan drill.c`），執行 `./drill_asan overflow`：


ASan 的報告回答了 core dump 回答不了的三個問題：**哪一行寫壞的**（第 15 行，越界寫入的迴圈）、**寫到哪裡**（一塊 1-byte 區域的正後方；ASan 把 `malloc(0)` 當成 1 byte 處理）、**這塊記憶體從哪裡配置的**（第 13 行）。看到「1-byte region」再對照第 12 行，溢位成 0 的大小計算就無所遁形。若用 `-O1` 編譯，迴圈會被換成 `memset`、函式被 inline 進 `main`，報告會指向 `main` 並顯示一次 131,072 bytes 的寫入，資訊一樣足夠，但 `-O0` 的行號最直觀。

### 演練三：refcount race（`race`）

## 33.12 在工作上怎麼用

### 事前準備：讓下一次事故可以被診斷

事故發生時能不能診斷，大半取決於平常有沒有準備。下面這份清單是 `thumbd` 團隊在六個事件之後補齊的：

| 準備項目 | 做法 | 解決什麼問題 |
|---|---|---|
| 保留符號 | 用 `-g` 編譯，把 debug info 拆成獨立檔案保存，並保留 build-id 對應 | core dump 與 perf 報告能顯示函式名稱與行號 |
| 保留 frame pointer | 編譯加 `-fno-omit-frame-pointer` | `perf record -g` 的呼叫鏈完整（第 9 章） |
| 開啟 core dump | systemd 的 `LimitCORE=infinity` 搭配 systemd-coredump，或設定 `ulimit -c` | 當機後有現場可以看 |
| 每個請求有 request id | 寫進 log 與錯誤回應 | 能從當機或錯誤回推是哪個輸入 |
| 關鍵指標 | 分路徑延遲、RSS、RssAnon、open fd 數、thread 數、快取大小 | 趨勢一開始偏離就看得到 |
| sanitizer 測試 | CI 執行 ASan、UBSan 測試；每晚執行 TSan 壓測 | 很多事件在上線前就被抓到 |
| 錯誤路徑測試 | 損壞檔案、切成小段的請求、client 中途斷線 | 事件三、五都藏在錯誤路徑 |

### 事故當下：先保存現場

服務還活著但行為異常時，先跑一次收集腳本再決定要不要重啟。以下是 Linux 上的版本：

```bash
#!/bin/sh
# 用法：collect.sh <PID>；只做讀取，耗時約 30 秒
P=$1; D=/tmp/incident-$(date +%s); mkdir -p $D
ps -o pid,stat,rss,vsz,nlwp,min_flt,maj_flt -p $P > $D/ps.txt
cat /proc/$P/status /proc/$P/smaps_rollup > $D/mem.txt
ls /proc/$P/fd | wc -l > $D/fd_count.txt
ss -tanp > $D/ss.txt
top -H -b -n 1 -p $P > $D/threads.txt
gdb -p $P -batch -ex 'thread apply all bt' > $D/bt.txt 2>&1   # 會暫停 process 數秒
perf record -g -p $P -o $D/perf.data -- sleep 20
dmesg | tail -100 > $D/dmesg.txt
```

注意 `gdb` 附加時會讓整個 process 暫停，在 thread 很多的服務上可能要數秒，要在服務已經不健康、或先把它移出 load balancer 之後再做。收集完再重啟，之後就能在不影響使用者的情況下慢慢分析。

### 事後檢討：把整條因果鏈寫下來

每個事件的檢討報告都寫出跨層的因果鏈，而不是只寫「修了一個 bug」。以事件一為例：「構造過的 PNG 寬高 32768 → 32-bit 乘法溢位成 0（第 5 章）→ `malloc(0)` → 解碼寫越界、破壞 heap metadata（第 25 章）→ 之後的 `free` 存取無效位址 → SIGSEGV → systemd 重啟 → 使用者看到 502」。接著回答兩個問題：為什麼上線前沒抓到（沒有 fuzzing、沒有尺寸上限）？為什麼花了一晚才找到（core dump 沒有符號、沒有 request id）？這兩個問題的答案就是下一季的改善項目。

## 33.13 常見錯誤與除錯

這一章的「錯誤」是診斷過程本身的錯誤。這些都在 `thumbd` 團隊身上真實發生過：

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 修了 crash 的那一行，還是一直當 | 把當機點當成 bug 所在，其實那裡只是受害者 | 當機位置每次不同、或在 allocator 內部 | 用 ASan 找第一次越界或 use-after-free |
| 在 debugger 或開發機上重現不了，就結案 | 記憶體配置、時序、輸入不同，bug 沒有被觸發 | 收集 production 的輸入與環境差異 | 用 sanitizer 版本、重放真實輸入、壓測放大機率 |
| 看到 VIRT 或 `buff/cache` 很大就判定 leak | 混淆位址範圍、page cache 與真正的匿名記憶體 | `smaps_rollup` 的 RssAnon 與 RssFile | 只用 RssAnon、PSS 與 allocator 統計判斷 |
| 加了 `sleep` 或 log，偶發錯誤就消失了 | 改變了時序，race 只是被藏起來 | 拿掉之後又出現；TSan 回報 | 修同步本身，不要依賴時序 |
| 只看平均延遲，看不出問題 | 慢的只是一小類請求，被平均掉 | 按路徑、類型拆開看 p99 | 指標要分路徑，profiling 只取慢請求那段時間 |
| 在 production 長時間開著 `strace`，服務變得更慢 | `strace` 讓每個 system call 變慢很多倍 | 開關前後比較延遲 | 只用 `timeout` 短時間附加，長期觀察改用 `perf` 或 eBPF 工具 |
| `perf` 報告全是十六進位位址 | 執行檔沒有符號，或 stack 沒有 frame pointer | `file` 看是否 stripped；呼叫鏈只有一層 | 保留 debug info、加 `-fno-omit-frame-pointer` |
| 一出事就重啟，事後什麼都查不到 | 沒有保存現場 | 事後沒有 core、沒有 backtrace | 先跑收集腳本；開啟 core dump |

## 33.14 動手練習

1. **手算**：事件二的影像若改成 6,000 × 4,000、每像素 4 bytes，旋轉 90° 時寫入的 stride 是多少 bytes？在 4 KiB page 下，內層迴圈連續兩次寫入會不會落在同一個 page？若用 64 × 64 的方塊做 blocking，一個方塊的來源與目的地共多少 KiB？（答案：目的地每列 4,000 像素，stride 為 16,000 bytes；不會，因為 16,000 > 4,096；來源與目的地各 16 KiB，共 32 KiB。）
2. **手算**：事件一中，若改成 `uint32_t bytes = w * h * 3`（RGB），寬高都是 37,837 時 `bytes` 是多少？寬高都是 37,838 時呢？（答案：37,837 × 37,837 × 3 = 4,294,915,707，比 2^32 − 1 = 4,294,967,295 小，剛好不溢位；37,838 × 37,838 × 3 = 4,295,142,732，超過 2^32，取模後只剩 175,436 bytes，配置出來的空間連一列都放不下。可以寫一行 Python 驗證。這說明溢位檢查必須在乘法時做，而不是憑感覺設一個「夠大」的型別。）
3. 延伸 33.11 節的程式：加入 `leak` 模式，在迴圈中模擬「解碼失敗就 return、忘了 free」的錯誤路徑。在 Linux 上用 `-fsanitize=address` 編譯（LeakSanitizer 預設開啟）、在 macOS 上用 `leaks --atExit -- ./drill leak`，分別讀懂報告指出的配置位置。
4. 延伸 33.11 節的程式：把 `race` 模式的 refcount 改成 `atomic_int` 並用 `atomic_fetch_add`，確認結果是 2,000,000、TSan 不再回報。再改成在 mutex 內遞增，比較兩者的執行時間（對照第 32 章的實驗）。
5. 在 Linux 機器上寫一個只註冊 `EPOLLOUT`、但從不寫資料的 epoll 程式，接受一條連線後觀察 `top` 與 `strace -c`，重現事件四；再改成只在有資料時註冊 `EPOLLOUT`，比較兩者。
6. 挑一個你工作上的服務，對照 33.12 節的「事前準備」表格逐項檢查：有沒有符號？core dump 會不會被保存？有沒有 request id？哪一項最容易補上？

## 本章重點整理

- 跨層診斷是由上往下、一次一層：先定義症狀與範圍（版本、機器、請求類型、時間），再進入應用層、執行期、作業系統與機器層，每往下一層都要有上一層的證據。
- 每一層都要提出可以被反證的假設，並主動尋找推翻它的證據；修好之後回到最上層，用同一個指標驗證症狀消失，並加上回歸測試。
- 恢復服務之前先保存現場：backtrace、`/proc` 資訊、`ss` 輸出、`perf` 取樣與 core dump，重啟會毀掉這些證據。
- 每個工具只回答特定問題，也各有成本：`perf` 取樣成本低可在 production 使用，`strace` 很重只能短時間附加，sanitizer 適合測試與 staging。
- 當機位置每次不同、或在 malloc／free 內部，代表 heap 已被破壞，當機點是受害者；用 ASan 重放輸入才能找到第一次越界的兇手。
- 延遲上升時先按請求類型拆開，再用 `perf record` 找熱點、`perf stat` 看 IPC 與 cache、TLB miss，判斷是演算法問題還是存取模式問題。
- RSS 上升要先分開匿名頁與檔案頁，再比較應用層與 allocator 的統計，才能分辨 leak、碎片與保留、以及 page cache。
- CPU 100% 要先分 user 與 sys：user 用 profiler 找熱點迴圈，sys 用 `strace -c` 找忙碌的 system call，例如 level-triggered 的 `EPOLLOUT`。
- 連線卡住要同時看兩邊：`ss` 看 kernel 中的連線狀態與佇列，backtrace 與 `strace` 看程式卡在哪個呼叫；short read 與遺失的緩衝資料是常見根因，CLOSE_WAIT 累積代表沒有 close。
- 只在高併發出現的偶發錯誤，用 TSan 壓測比在 production 等待重現有效得多；TSan 不需要真的撞上錯誤的交錯就能回報。
- 在 debugger 裡不當機、加了 log 就消失，都不代表 bug 不存在，而是環境或時序被改變了。
- 事前準備決定事故能不能被診斷：保留符號與 frame pointer、開啟 core dump、每個請求有 request id、分路徑的指標、CI 中的 sanitizer 測試。
- 事後檢討要寫出跨層的完整因果鏈，並回答「為什麼沒有更早抓到」與「為什麼花了這麼久才找到」。

## 延伸問答

> [!question]- Q1. 為什麼 heap overflow 造成的 segfault，core dump 的 backtrace 常常指向 `free` 或 `malloc`，而不是真正寫壞記憶體的那一行？
> heap overflow 寫越界的那一刻，通常寫到的是相鄰 chunk 的資料或 allocator 的 metadata，這些位址都還屬於合法的 heap 頁面，MMU 不會觸發任何 fault，程式繼續正常執行。被破壞的 metadata 要等到之後某次 `free` 或 `malloc` 去讀它、依照錯誤的大小或指標存取記憶體時，才會碰到無效位址而 SIGSEGV，或被 glibc 的完整性檢查發現而 abort。
>
> 所以 core dump 記錄的是「受害者」被發現的時間點，兇手早就離開現場了，而且每次當機的位置可能不同。要找兇手，需要在寫越界的那一刻就攔下來的工具：ASan 在每個 heap 區塊周圍放 redzone，第一次寫進 redzone 就立刻回報，並附上這塊記憶體的配置位置。

> [!question]- Q2. 你在 production 看到某服務的 RSS 一直上升，同事說「`free -m` 顯示記憶體快用光了，一定是它 leak」。你會怎麼回應與確認？
> `free -m` 看的是整台機器，其中 `buff/cache` 是 kernel 的 page cache，可以在需要時回收，真正該看的是 `available` 欄位，以及這個服務自己的數字。先看 `/proc/PID/smaps_rollup`，把 RssAnon（heap、匿名 mmap）與 RssFile（mmap 的檔案頁）分開：如果長的是 RssFile，大多是檔案映射，不是 leak。
>
> 如果長的是 RssAnon，再比較應用層自己的統計（例如快取大小）和 allocator 的 in-use 與 system bytes：in-use 一起長是 leak，要用 heaptrack、Valgrind 或 LeakSanitizer 在 staging 找配置點；in-use 平穩但 system bytes 長，是碎片或 arena 保留，要從 allocator 的設定著手。在固定負載下觀察 RSS 是否在某個水位持平，也是分辨 leak 與暖機成長的好方法。

> [!question]- Q3. 一個 thread CPU 100%，`top` 顯示大部分是 `%sy`。這告訴你什麼？下一步用什麼工具？
> `%sy` 是 kernel mode 的時間，表示這個 thread 大部分時間花在 kernel 裡，最常見的原因是它在非常頻繁地做 system call，每次 system call 本身很快，但次數多到佔滿一個核心。這和 user mode 的熱迴圈（`%us` 高）要用不同的工具追。
>
> 下一步是短時間附加 `strace -c -p TID`（用 `timeout` 限制在幾秒），看哪個 system call 的次數異常地多，再用 `strace -e trace=<那個呼叫>` 看它的參數與回傳值。例如 `epoll_wait` 每次立刻回傳 `EPOLLOUT`，代表 level-triggered 模式下註冊了永遠成立的可寫事件；`read` 一直回傳 `EAGAIN`，代表在 nonblocking fd 上忙碌輪詢。`perf top -t TID` 也能顯示 kernel 函式，用來確認時間花在哪條 kernel 路徑上。

> [!question]- Q4. `ss` 顯示 `thumbd` 有上千條 CLOSE_WAIT 連線，而且越來越多。這是什麼狀態？問題在 client 還是 server？
> CLOSE_WAIT 表示對方（client 或 nginx）已經送出 FIN 關閉了它那一端，我方的 kernel 已經確認收到，正在等**我方的應用程式**呼叫 `close`。只要應用程式不 close，這條連線就永遠停在 CLOSE_WAIT，佔用一個 fd 和 kernel 的資源，所以問題幾乎一定在 server 自己的程式。
>
> 常見原因是錯誤路徑漏掉 `close`：例如 `read` 回傳 0（EOF）時直接 return，或例外情況提早離開函式。確認方法是看 `/proc/PID/fd` 的數量是否同步增加，再用 `ss -tanp` 找出 fd 編號，配合 backtrace 或程式碼審查找出哪條路徑沒關。修法是讓所有離開路徑都經過同一段清理程式。放著不管，最後會撞到 `ulimit -n` 的上限，新的 `accept` 開始失敗。

> [!question]- Q5. 為什麼「在 gdb 或 lldb 裡執行就不會當機」不代表程式沒有 bug？33.11 節的演練二說明了什麼？
> 越界寫入、use-after-free 這類 bug 的後果取決於被蓋掉的是什麼：蓋到沒有人在用的記憶體，什麼事都不會發生；蓋到 allocator 的 metadata，之後才會出事；寫到沒有映射的頁，才會立刻 fault。debugger 會改變程式的環境，例如關閉 ASLR、改變環境變數與記憶體配置、改變 thread 的時序，越界寫入的落點跟著改變，結果就可能從「當機」變成「沒事」。
>
> 演練二中，同一個執行檔直接執行時死於 SIGBUS，在 lldb 裡卻正常結束。這說明「能不能觀察到症狀」與「有沒有 bug」是兩件事。可靠的做法是讓 bug 一發生就被攔下來：ASan 不依賴寫越界剛好碰到什麼，而是檢查每一次存取是否落在合法範圍內，所以在任何環境都能指出同一行。

> [!question]- Q6. 情境題：上傳請求偶爾卡住直到 timeout，`ss` 顯示連線是 ESTABLISHED、Recv-Q 為 0，而 worker 卡在 `read`。你會懷疑什麼？
> Recv-Q 為 0 表示 kernel 的接收佇列裡沒有任何待讀的資料，也就是 client 該送的可能都已經送到並被 `thumbd` 讀走了，但程式仍在 `read` 等更多資料。這通常不是網路問題，而是應用程式對「還要讀多少」算錯了：最典型的是讀 header 時一次讀進了部分 body，解析 body 的程式卻直接從 socket 讀完整的 `Content-Length`，忽略緩衝區裡已有的部分，於是永遠在等那些早已讀到的 bytes。
>
> 確認方法是在測試環境把 request 切成小段送出，或用 `strace` 看 `read` 要求的長度與累計讀到的長度。修法是使用帶緩衝的讀取（第 27 章的 RIO 思路），header 與 body 從同一個緩衝區取資料；同時為每次讀取設定逾時，避免任何等待沒有上限。

> [!question]- Q7. 為什麼事件六要在 staging 用 TSan 跑壓測，而不是在 production 加更多 log 等它重現？
> 這類 race 的錯誤交錯發生的機率很低，production 每天才出現一兩次，加 log 等待重現可能要好幾天，而且 log 本身會改變時序，可能讓問題暫時消失或出現得更少。更重要的是，這是隱私事故，每多等一天就多一些使用者看到別人的照片。
>
> TSan 的做法不同：它追蹤每次記憶體存取與每個同步操作之間的 happens-before 關係，只要兩個 thread 對同一位址的存取（至少一個是寫入）之間沒有同步，就會回報，**不需要真的撞上**會造成錯誤結果的交錯。再把快取調小、提高併發，讓相關程式碼路徑頻繁執行，通常幾分鐘內就能得到報告，而且報告直接指出兩邊存取的程式位置與 thread 建立位置。代價是 TSan 版本通常慢 5–15 倍、記憶體用量大（第 31 章），所以適合 staging 而不是 production。

> [!question]- Q8. 面試題：給你一個「服務延遲變高」的告警，請描述你的診斷步驟。
> 第一步是定義與縮小範圍：是 p50 還是 p99 變高？從什麼時候開始？和部署、流量、設定變更有沒有時間上的關聯？只影響某些機器、某類請求，還是全部？把延遲按請求路徑拆開，往往就能把問題縮小到一段程式。同時看資源指標：CPU、記憶體、I/O、網路、下游依賴的延遲，判斷是自己變慢還是在等別人。
>
> 第二步依證據往下鑽。CPU 也上升，就用 `perf record -g` 找熱點；CPU 沒升、IPC 很低，用 `perf stat` 看 cache 與 TLB miss，檢查存取模式與工作集；CPU 沒滿而 thread 在等，看鎖競爭、context switch 與 thread backtrace；如果時間花在 system call 或 page fault，看 `strace -c`、`min_flt`／`maj_flt` 與 swap。第三步修復後回到原來的延遲指標驗證，並加上能提前發現同類問題的監控或測試。回答時強調「每一步都有證據、會排除其他假設」，比列出工具名稱更重要。
