## 25.1 故事：free 了，RSS 卻不降

第 24 章把原圖改成 `mmap` 之後，`thumbd` 的 OOM 消失了，但監控面板上又出現一條讓人不安的曲線。晚上尖峰時段，`thumbd` 的縮圖快取會塞滿，RSS 升到 5.8 GB；尖峰過後，快取依 LRU 淘汰大部分項目，程式也確實對每一個被淘汰的縮圖呼叫了 `free`。但 RSS 停在 5.6 GB，一整夜都沒有降下來。

SRE 阿哲的第一個判斷是 memory leak。小安用 AddressSanitizer 的 leak 檢查（第 26 章）跑了一整天的流量重播，結果是零 leak：每一塊配置的記憶體最後都被 `free` 了。那 5.6 GB 到底被誰拿著？

老周說：「被 `malloc` 拿著。你 `free` 的時候，記憶體是還給 allocator，不是還給 kernel。allocator 要不要、能不能把它還給 kernel，看它怎麼管理這些空間。」接著補了一句：「而且 `perf` 上 `malloc` 和 `free` 加起來佔了 9% 的 CPU，你也該知道它們在做什麼。」

這一章就從 allocator 的視角，看 `malloc` 和 `free` 到底做了什麼：它從哪裡拿到記憶體、怎麼記錄哪些區塊在用、哪些空著，怎麼在「快」和「省」之間取捨。最後我們會親手寫一個迷你 allocator，並回來解釋 `thumbd` 那條不降的曲線。

## 25.2 Heap：allocator 向 kernel 要記憶體的兩種方式

**動態記憶體配置器**（dynamic memory allocator，以下簡稱 allocator）是一段使用者空間的程式碼，通常是 C 標準函式庫的一部分，負責管理 process 的 **heap**：位址空間中一塊用來在執行期間配置記憶體的區域。對 kernel 來說，heap 只是一個或幾個匿名的 VMA（第 24 章）；切成小塊、記錄誰在用，全是 allocator 自己的事。

allocator 向 kernel 要記憶體的方式有兩種：

**`brk`／`sbrk`**：每個 process 有一個 **program break**（程式斷點），標示 heap 的結尾。`sbrk(n)` 把 break 往高位址推 n bytes，heap 這個 VMA 就跟著變大，回傳舊的 break；`sbrk(0)` 只查詢目前位置。這是最古老的方法，只能在一端延伸或縮小，heap 必須是一整塊連續的區域。

**`mmap`**：用匿名 mapping 拿一塊獨立的區域（第 24 章），用完可以單獨 `munmap`。它不受「只能在一端延伸」的限制，現代 allocator 越來越依賴它。

```text
 位址空間（Linux x86-64，簡化）
 ┌────────────────────────────┐ 高位址
 │ stack                       │
 ├────────────────────────────┤
 │ mmap 區域                   │
 │  ┌──────────────────────┐   │ ← 大配置（例如 ≥ 128 KiB）：一次 mmap 一塊，
 │  │ 300 KB 的解碼緩衝區   │   │    free 時直接 munmap，立刻還給 kernel
 │  └──────────────────────┘   │
 │  ┌──────────────────────┐   │ ← 其他 thread 的 arena：allocator 用 mmap
 │  │ thread arena（64 MiB）│   │    預留一大塊，自己再切小
 │  └──────────────────────┘   │
 ├────────────────────────────┤
 │        （未使用）           │
 ├────────────────────────────┤ ← program break（sbrk 移動這條線）
 │ heap（main arena）          │    [blk][blk][free][blk][free]...
 ├────────────────────────────┤
 │ .bss .data .text            │
 └────────────────────────────┘ 低位址
```

這張圖是 glibc 的 allocator（ptmalloc）的做法：小配置來自用 `brk` 延伸的 main heap，或用 `mmap` 預留的 thread arena；大配置超過一個門檻（**mmap threshold**，預設 128 KiB，執行期間會依使用情況動態上調，64-bit 上最高到 32 MiB）就直接 `mmap` 一整塊。這個分工直接影響 RSS：直接 `mmap` 的大配置在 `free` 時立刻 `munmap`，RSS 馬上下降；切在 heap 裡的小配置被 `free` 後只是回到 allocator 的 free list，heap 的 VMA 和實體頁都還在。

> [!warning] 常見誤解
> 「`free` 會把記憶體還給作業系統。」大多數情況下不會。`free` 把區塊還給 allocator，下一次 `malloc` 可以重複使用。只有在某些條件下（區塊是獨立 `mmap` 的、heap 頂端空出夠大一段、或 allocator 主動對整頁的空閒區域呼叫 `madvise`），實體記憶體才會真的還給 kernel。

## 25.3 malloc 與 free 的約定

先把介面講清楚。C 標準函式庫提供四個函式：

```c
#include <stdlib.h>

void *malloc(size_t size);               /* 配置 size bytes，內容未初始化 */
void *calloc(size_t n, size_t size);     /* 配置 n × size bytes，內容全為零 */
void *realloc(void *ptr, size_t size);   /* 改變大小，可能搬到新位址 */
void  free(void *ptr);                   /* 釋放；free(NULL) 什麼都不做 */
```

幾個規則初學者常常不知道。`malloc` 回傳的位址必須對齊到任何基本型別都能放的邊界（C 標準用 `alignof(max_align_t)` 表示這個邊界），所以存 `double` 或 `long double` 都不會出錯（第 10 章）。在 x86-64 Linux 上這個值是 16，glibc 的 `malloc` 也對齊 16 bytes；Apple Silicon 上 `alignof(max_align_t)` 其實只有 8（`long double` 和 `double` 一樣大），但 macOS 的 `malloc` 仍然保證 16 bytes 對齊。失敗時回傳 `NULL`，但在 Linux 預設的 overcommit 策略下很少發生（第 24 章）。`calloc` 會檢查 `n × size` 是否溢位，而自己寫 `malloc(w * h * 4)` 不會，這正是第 5 章 `thumbd` heap overflow 的根源。`realloc` 失敗時回傳 `NULL` 但**原本的區塊仍然有效**，所以 `p = realloc(p, n)` 的寫法會在失敗時遺失原指標。

從 allocator 的角度，這個介面給它設下了很嚴格的限制：

| 限制 | 意思 | 帶來的難題 |
|---|---|---|
| 處理任意的請求序列 | `malloc` 與 `free` 可以任意交錯，只保證 `free` 的指標來自先前的 `malloc` | 無法預知未來，不能假設「先配的先放」 |
| 立即回應 | 每個請求要馬上處理，不能先累積再一起排 | 不能為了排得更緊而延後或重排請求 |
| 只能用 heap | allocator 自己的簿記資料也要放在 heap 裡 | 每個區塊要額外存 metadata，佔用空間 |
| 對齊 | 回傳位址必須 16 bytes 對齊 | 區塊大小要往上取整，產生浪費 |
| 不能移動已配置的區塊 | 程式手上持有指標，allocator 不知道有誰指向它 | 無法像 GC（第 26 章）那樣把區塊搬攏消除空洞 |

最後一項是 C allocator 和 Java、Go 的記憶體管理最大的不同：C 程式可以把指標存在任何地方、轉成整數、做運算，allocator 根本無從追蹤，所以一旦配置出去，區塊就固定在那個位址，直到 `free`。

## 25.4 兩個互相拉扯的目標：throughput 與 utilization

衡量 allocator 有兩個指標，而且它們常常互相衝突。

**Throughput**（吞吐量）是單位時間能完成多少個請求。例如 1 秒內完成 500 萬次 `malloc` 加 500 萬次 `free`，throughput 就是每秒 1,000 萬次操作。`thumbd` 每處理一張圖要配置數十次，allocator 慢一點，整個服務就慢一點。

**Peak utilization**（峰值使用率）衡量 heap 用得多有效率。設 P_k 是前 k 個請求之後，所有「還沒 free 的 payload」的總和（**payload** 是程式要求的 bytes 數），H_k 是到那時為止 heap 的大小（假設 heap 只增不減）。

```text
U_k = （前 k 個請求中最大的 P_i） ÷ H_k
```

分子是程式在任一時刻「真正需要」的最大量，分母是 allocator 為此動用的空間，U 越接近 1 越好。

### 手算：一段請求序列的 peak utilization

用本章 25.16 節迷你 allocator 的規則：block 大小 = payload ＋ 16 bytes 的 header 與 footer，往上取整到 16 的倍數。heap 從 0 開始，找不到合適的 free block 就在尾端延伸。

| 步驟 | 請求 | block 大小 | 發生什麼事 | 存活 payload P | heap 大小 H |
|---|---|---|---|---|---|
| 1 | `a = malloc(40)` | 40 ＋ 16 = 56 → 64 | 延伸 heap | 40 | 64 |
| 2 | `b = malloc(100)` | 116 → 128 | 延伸 heap | 140 | 192 |
| 3 | `free(a)` | — | 前面空出 64 bytes | 100 | 192 |
| 4 | `c = malloc(200)` | 216 → 224 | 64 的空洞放不下，延伸 heap | 300 | 416 |
| 5 | `free(b)`、`free(c)` | — | 全部空出 | 0 | 416 |

P 的最大值出現在步驟 4，等於 300；最後 H = 416，所以 U = 300 ÷ 416 ≈ 72%。另外 28% 去了哪裡？一部分是每個 block 的 header、footer 與取整（例如 `a` 只用 40 bytes 卻佔了 64），另一部分是步驟 4 那個用不上的 64 bytes 空洞。這兩種浪費就是下一節的兩種 fragmentation。

兩個目標為什麼衝突？想把 utilization 做高，就要仔細挑選最合適的空位，這需要花時間搜尋；想把 throughput 做高，就要盡快隨便給一塊，空間就容易浪費。本章後面的每一個設計，都是在這條光譜上選一個位置。

## 25.5 Fragmentation：記憶體浪費在哪裡

**Fragmentation**（碎片化）是指記憶體雖然沒有被使用，卻無法拿來滿足請求的現象。它分成兩種。

**Internal fragmentation**（內部碎片）發生在已配置的 block 內部：block 比 payload 大，多出來的部分沒人用。來源包括 header 與 footer、為了對齊而取整、allocator 規定的最小 block 大小，以及「剩下的太小不值得切開，整塊給你」的決定。它很好算：block 大小減 payload。上表中 `a` 的內部碎片就是 64 − 40 = 24 bytes。

**External fragmentation**（外部碎片）發生在 free block 之間：所有 free block 加起來夠大，但沒有任何一塊**連續**的空間夠大。步驟 4 就是例子：heap 裡明明有 64 bytes 空著，但 `c` 需要 224，只好延伸 heap。

```text
 internal：block 裡面的浪費
 ┌──────┬────────────────────────────┬───────┬──────┐
 │header│ payload 40 bytes            │ 對齊   │footer│   block 64 bytes
 └──────┴────────────────────────────┴───────┴──────┘
          程式真正用到的部分            浪費 8   簿記

 external：block 之間的浪費
 ┌──────┬────────┬──────┬────────┬──────┬────────┐
 │ used │free 192│ used │free 384│ used │free 384│   free 共 960 bytes
 └──────┴────────┴──────┴────────┴──────┴────────┘
   malloc(800) 需要 816 bytes 的連續空間 → 失敗，只能向 kernel 要更多
```

External fragmentation 比較難處理，因為它取決於**未來**的請求：同樣的空洞，接下來若都是小請求就毫無問題，若來一個大請求就很糟。allocator 無法預知未來，只能用啟發式的策略（placement、coalescing、依大小分類）降低它發生的機率。

## 25.6 設計一個 allocator 要回答的四個問題

任何一個實際的 allocator，都要對下面四個問題給出答案。後面幾節逐一討論：

| 問題 | 為什麼重要 | 本章的選項 |
|---|---|---|
| free block 怎麼組織？ | 決定找空位要掃描多少 block | implicit list、explicit list、segregated lists（25.7、25.11、25.12 節） |
| 要放進哪個 free block？ | 影響 utilization 與搜尋時間 | first fit、next fit、best fit（25.8 節） |
| 放進去之後，剩下的空間怎麼辦？ | 太大不切會浪費，太小切開也用不上 | splitting 與最小 block 大小（25.9 節） |
| 剛 free 的 block 怎麼處理？ | 相鄰的空洞不合併，就會有「假的」external fragmentation | coalescing 與 boundary tag（25.10 節） |

還有一個問題貫穿全部：`free(p)` 只給一個指標，allocator 怎麼知道這塊有多大？答案是把大小記在 block 自己身上，放在 payload 前面的 **header**（標頭）裡。`free(p)` 往回看幾個 bytes 就讀到了。

## 25.7 Implicit free list：用 header 把所有 block 串起來

最簡單的組織方式：每個 block 開頭放一個 8-byte 的 header，記錄這個 block 的總大小（含 header）和「已配置或空閒」。因為 block 大小一定是 16 的倍數，二進位最低 4 個 bit 一定是 0，可以拿最低位當作 allocated bit：

```text
 header（64 bits）
 63                                           4  3  2  1  0
 ┌──────────────────────────────────────────────┬──┬──┬──┬──┐
 │ block 大小（16 的倍數，所以低 4 bits 必為 0） │ 0│ 0│ 0│ a│
 └──────────────────────────────────────────────┴──┴──┴──┴──┘
                                                            a = 1：已配置
                                                            a = 0：空閒
 一個 block：
 ┌─────────┬───────────────────────────┐
 │ header  │ payload（＋padding）       │   malloc 回傳的是 payload 的位址
 └─────────┴───────────────────────────┘
 ↑ block 起點                               payload = block 起點 ＋ 8
```

有了大小，從第一個 block 出發，「目前位址 ＋ 目前 block 大小」就是下一個 block 的位址。所有 block，不論空閒或已配置，就這樣隱含地串成一條串列，所以叫 **implicit free list**（隱式空閒串列）：free block 之間沒有直接的連結，要找它們就得把所有 block 走一遍。

### 手算：編碼與走訪 header

編碼：一個 48 bytes、已配置的 block，header = 48 | 1 = `0x30 | 0x1` = `0x31`。一個 1,008 bytes 的 free block，header = `0x3f0`。

解碼：讀到 header `0xa1`，大小 = `0xa1 & ~0xF` = `0xa0` = 160，最低位 1，所以是 160 bytes 的已配置 block。

走訪：下表是 heap 從位移 8 開始的幾個 header（也就是 25.16 節程式在 `free(b)` 之後的狀態），heap 在位移 1,016 結束：

| block 起點 | 讀到的 header | 大小 | 狀態 | 下一個 block 起點 |
|---|---|---|---|---|
| 8 | `0x41` | 64 | 已配置 | 8 ＋ 64 = 72 |
| 72 | `0x80` | 128 | 空閒 | 72 ＋ 128 = 200 |
| 200 | `0x31` | 48 | 已配置 | 200 ＋ 48 = 248 |
| 248 | `0x300` | 768 | 空閒 | 248 ＋ 768 = 1,016 = 結尾，停止 |

這個走訪也說明了 implicit list 的弱點：要找一塊夠大的 free block，最壞情況要走過**所有** block，包括已配置的。heap 裡有一百萬個 block 時，每次 `malloc` 都可能掃一百萬次。它的優點是極度簡單，適合拿來理解原理。

為什麼 block 起點在位移 8 而不是 0？因為 payload 在 header 之後 8 bytes，要讓 payload 落在 16 的倍數，block 起點就得是 16k ＋ 8。這是所有使用 8-byte header 又要求 16-byte 對齊的 allocator 都會遇到的小細節。

## 25.8 Placement：要放進哪個 free block

`malloc(n)` 先把 n 換算成需要的 block 大小，再找一個夠大的 free block。怎麼挑，叫 **placement policy**（放置策略）：

- **First fit**：從頭開始找，第一個夠大的就用。簡單，但小碎片容易堆積在 heap 前段，讓之後的搜尋越來越長。
- **Next fit**：從上一次找到的位置繼續往下找。避免每次都掃過前段的碎片，通常比較快，但研究與實驗都顯示 utilization 往往比 first fit 差。
- **Best fit**：檢查所有 free block，挑「夠大且最小」的那個。utilization 通常最好，但在 implicit list 上每次都要掃完整條串列。

### 手算：三種策略的不同選擇

heap 中依位址順序有四個 free block：A 64、B 256、C 96、D 160 bytes。最小 block 大小 32，剩下不到 32 bytes 就不切。依序來了三個請求，需要的 block 大小分別是 80、144、240：

| 請求 | First fit | Best fit |
|---|---|---|
| 80 | A 不夠 → B（256）切成 80 ＋ 176 | 夠大的有 B、C、D，最小的是 C（96），剩 16 不切，整塊給出（內部碎片 16） |
| 144 | A 不夠 → B 剩下的 176 切成 144 ＋ 32 | 夠大的有 B、D，最小的是 D（160），剩 16 不切，整塊給出 |
| 240 | A、32、C、D 都不夠 → **延伸 heap** | 只有 B（256），剩 16 不切，整塊給出 |
| 結果 | heap 變大，留下 A、32、C、D 四塊碎片 | heap 不變，三個請求都放進既有空間 |

這個例子中 best fit 明顯勝出，代價是每個請求都檢查了全部四個 free block。first fit 把大塊 B 拿去切小請求，等真正需要大塊時已經沒有了。這也是一般的觀察：「保留大塊給大請求」對 utilization 很重要。不過情況也可以反過來設計，沒有一種策略在所有序列上都最好；25.16 節的 Python 模擬會在一段較長的隨機序列上比較三者。

## 25.9 Splitting 與向 kernel 要更多記憶體

找到的 free block 比需要的大時，有兩個選擇：整塊給出（簡單，但多出的部分成為內部碎片），或 **splitting**（切割）：前段標記為已配置，後段變成一個新的 free block。

切割有下限。一個 free block 至少要放得下自己的 header 和 footer（下一節），還要符合 16 的倍數，所以本章的迷你 allocator 規定最小 block 是 32 bytes。剩下不到 32 bytes 的空間就不切，連同請求一起給出去，這就是上一節 best fit 「剩 16 不切」的原因。

如果所有 free block 都不夠大，allocator 只好向 kernel 要更多記憶體：用 `sbrk` 延伸 heap 或 `mmap` 一塊新區域，把新空間當作一個大 free block。如果 heap 尾端原本就有一塊 free block，新空間應該先和它合併，否則尾端會出現兩塊相鄰卻沒合併的空洞。這是自己實作 allocator 時最容易忘記的一步。

## 25.10 Coalescing 與 boundary tag

`free` 一個 block 之後，如果它的前後鄰居也是空的，三塊應該合併成一大塊，這叫 **coalescing**（合併）。不合併的話，heap 裡會出現很多相鄰的小 free block，加起來夠大卻都用不上，叫 **false fragmentation**（假碎片）。

和**後一塊**合併很容易：header 裡有大小，「目前位址 ＋ 大小」就是後一塊的 header，看一眼就知道它空不空。和**前一塊**合併卻是個問題：implicit list 只能往後走，要知道前一塊在哪，得從 heap 開頭重新掃一遍。

**Boundary tag**（邊界標記）是 Knuth 提出的解法：在每個 block 的**尾端**也放一份 header 的副本，叫 **footer**（標尾）。前一塊的 footer 就緊貼在目前 block 的 header 前面，讀它就知道前一塊的大小與狀態，往回減就是前一塊的起點。

```text
 ... ┌──────┬──────────────┬──────┐┌──────┬──────────────┬──────┐ ...
     │header│  前一塊      │footer││header│  目前的 block │footer│
     └──────┴──────────────┴──────┘└──────┴──────────────┴──────┘
                                ▲     ▲
                目前 block 起點 − 8   目前 block 起點
                 讀到前一塊的大小 s  → 前一塊起點 = 目前起點 − s
```

有了 footer，`free` 時的四種情況都能在常數時間內處理：

```text
 情況 1：前 used、後 used     [used][ 剛 free ][used]   → 只改自己的 header/footer
 情況 2：前 used、後 free     [used][ 剛 free ][free]   → 和後一塊合併
 情況 3：前 free、後 used     [free][ 剛 free ][used]   → 和前一塊合併
 情況 4：前 free、後 free     [free][ 剛 free ][free]   → 三塊合成一塊

 合併後只需要寫兩個 tag：新的大 block 的 header（在最左塊的起點）
                          和 footer（在最右塊的尾端）
```

footer 的代價是每個 block 多 8 bytes，對大量小配置來說很可觀：一個 16-byte 的 payload，header 加 footer 就佔了 16 bytes。一個常見的最佳化是：**只有 free block 需要 footer**。因為只有在「前一塊是空的」時才需要讀前一塊的 footer，所以在每個 header 的另一個低位元記錄「前一塊是否已配置」；已配置的 block 就可以省掉 footer，把空間給 payload 用。glibc 的 malloc 就是這樣設計的：chunk 的 size 欄位有一個 `PREV_INUSE` bit，前一個 chunk 空閒時才有意義的 `prev_size` 欄位就是那個 footer。

coalescing 的時機也有兩種：**立即合併**（每次 `free` 都合併）簡單、heap 隨時乾淨；**延遲合併**（等到找不到空位時才一次合併）避免「剛合併又馬上被切開」的反覆成本。glibc 對很小的 chunk 採用延遲的做法（fastbin），一般大小的則立即合併。

## 25.11 Explicit free list：只串 free block

implicit list 的搜尋時間和「所有 block 數」成正比，包括一大堆已配置的。既然只關心 free block，何不只把它們串起來？free block 的 payload 區域反正沒人用，可以拿來存兩個指標：前一個與下一個 free block。這就是 **explicit free list**（顯式空閒串列），一條雙向串列：

```text
 heap 中的實際位置（依位址）：
 ┌──────┬───────────┬──────┬───────────┬──────┬───────────┐
 │used  │ free X    │used  │ free Y    │used  │ free Z    │
 └──────┴───────────┴──────┴───────────┴──────┴───────────┘

 free block 的內部：
 ┌────────┬────────┬────────┬────────────────┬────────┐
 │ header │ pred   │ succ   │  （未使用）     │ footer │
 └────────┴────────┴────────┴────────────────┴────────┘

 explicit list（LIFO 順序，和位址無關）：
   head → Z ⇄ X ⇄ Y → NULL
```

搜尋時只走 free block，時間和「free block 數」成正比，heap 很滿時差別巨大。代價有兩個：最小 block 變大了（header 8 ＋ pred 8 ＋ succ 8 ＋ footer 8 = 32 bytes，剛好仍是 16 的倍數），以及每次配置、釋放都要維護串列指標。

free block 放進串列的哪裡，有兩種常見策略：

| 策略 | free 的成本 | utilization | 說明 |
|---|---|---|---|
| LIFO（剛 free 的放最前面） | 常數時間 | 通常較差 | 剛釋放的 block 可能還在 cache 裡，馬上被重用，對 locality 有利 |
| 依位址排序 | 要找插入位置，線性時間 | 接近 best fit | 搭配 first fit 時，研究顯示 utilization 比 LIFO 好 |

不論哪種，coalescing 仍然要用 boundary tag 找到位址上相鄰的鄰居，因為串列上的相鄰和位址上的相鄰是兩回事；合併時要把鄰居從串列中拆下來，再把合併後的大 block 放回去。

## 25.12 Segregated free lists 與 buddy system

即使只串 free block，一條串列上大小混雜，找一塊 64 bytes 的空間仍可能要跳過一堆太小的。下一步是**依大小分類**：維護多條 free list，每條只放某個大小範圍的 block，叫 **size class**（大小類別）。例如：

```text
 size class   串列
 ─────────    ────────────────────────────────
  32          ● → ● → ● → ●
  48          ● → ●
  64          ● → ● → ●
  65–128      ● → ●
  129–256     ●
  257–512     （空）
  513–1024    ● → ●
  > 1024      ● → ●           ← 大小不一，在這條串列內用 first 或 best fit

 malloc(50) → 需要 64 → 直接看 64 那條；空的才往更大的類別找，找到後切割，
              剩下的部分放回它所屬的類別
```

這類設計統稱 **segregated free lists**（分離空閒串列），有兩個極端：

- **Simple segregated storage**：每個類別的 block 大小完全相同，從不切割也不合併。向 kernel 要一頁，整頁切成同樣大小的格子串起來；`malloc` 拿第一格，`free` 放回最前面，都是常數時間，block 也不需要 header（從位址就能查出它屬於哪一頁、哪個類別）。缺點是不合併，某個類別用過的頁被其他類別借不走，容易有 external fragmentation。
- **Segregated fits**：每個類別的串列中 block 大小不一，配置時在該類別裡找、需要時切割，釋放時合併後放到正確的類別。搜尋範圍小，又接近 best fit 的 utilization。glibc 的 small bin 與 large bin 屬於這一類。

現代高效能 allocator 的小配置幾乎都走「simple segregated storage」這條路，因為速度最快、而且同大小的物件放在一起對 cache 友善。

### Buddy system：手算一次

**Buddy system**（夥伴系統）是 segregated fits 的一個特例：所有 block 大小都是 2 的冪，切割時一分為二，合併時只跟自己的「夥伴」合併。它的妙處是夥伴的位址可以直接算出來：大小 2^k 的 block，若起點（相對於 heap 開頭）是 x，它的夥伴就是 `x XOR 2^k`。

假設 heap 有 1 MiB（`0x100000`），請求 100 KiB：

```text
1. 100 KiB 往上取 2 的冪 → 128 KiB（0x20000）
2. 1 MiB 切成兩個 512 KiB：[0x00000] [0x80000]
3. 0x00000 的 512 KiB 再切成兩個 256 KiB：[0x00000] [0x40000]
4. 0x00000 的 256 KiB 再切成兩個 128 KiB：[0x00000] [0x20000]
5. 配置 0x00000 那塊；free list 上留下 128K@0x20000、256K@0x40000、512K@0x80000
```

釋放時，0x00000 的夥伴是 `0x00000 XOR 0x20000 = 0x20000`。它是空的，就合併成 256 KiB@0x00000；再找它的夥伴 `0x00000 XOR 0x40000 = 0x40000`，也空的，再合併……一路合回 1 MiB。若有另一塊 128 KiB 在 `0x60000`，它的夥伴是 `0x60000 XOR 0x20000 = 0x40000`。

buddy system 配置與合併都很快，但內部碎片可能很大：要 100 KiB 給 128 KiB，浪費 28 KiB；要 129 KiB 會給 256 KiB，浪費將近一半。Linux kernel 管理實體頁的 page allocator 就是 buddy system（以頁為單位，2^0 到 2^10 頁），用 `cat /proc/buddyinfo` 可以看到每個大小還有幾塊空的。

## 25.13 Heap checker：先寫檢查器，再寫 allocator

allocator 的 bug 有一個特性：出錯的地方和當機的地方通常相隔很遠。`free` 時少寫了一個 footer，可能要等幾千次操作之後，某次合併讀到錯誤的大小，把兩個已配置的 block 合在一起，再過一陣子程式的資料被覆蓋，最後在完全無關的地方 segfault。

對付這種 bug 最有效的工具是 **heap checker**（heap 一致性檢查器）：一個走訪整個 heap、檢查所有不變量（invariant）的函式。在開發階段，每次 `malloc` 與 `free` 之後都呼叫它，bug 一出現就立刻被抓到，而不是在幾千步之後。

一個 implicit list allocator 至少要檢查：

- 每個 block 的大小是對齊單位的倍數，而且不小於最小 block。
- 每個 block 的 header 與 footer 一致。
- 每個 payload 位址都正確對齊。
- 沒有兩個相鄰的 free block（否則代表 coalescing 漏了）。
- 從 heap 起點一路走，剛好停在 heap 結尾，不多不少（否則某個大小寫錯了）。

explicit 或 segregated list 還要再加：每個 free block 都在某條串列上、串列上的每個 block 都標記為 free、pred 與 succ 指標互相一致、每個 block 都在正確的 size class、指標都落在 heap 範圍內。

這不只是寫 allocator 才用得到的技巧。任何維護複雜不變量的資料結構（自己寫的 hash table、ring buffer、B-tree），在開發與測試階段都值得附一個 `check()`，在 debug build 裡頻繁呼叫。

## 25.14 真實世界的 allocator：ptmalloc、jemalloc、tcmalloc

前面講的是原理；真實的 allocator 還必須面對**多執行緒**。如果整個 heap 只有一把鎖，`thumbd` 的 16 個 worker 同時 `malloc` 就會排隊。現代 allocator 都用某種方式讓各 thread 盡量不搶同一把鎖：

```text
 thread 1   thread 2   thread 3   …   thread 16
    │          │          │               │
    ▼          ▼          ▼               ▼
 ┌──────┐  ┌──────┐  ┌──────┐        ┌──────┐   ① thread 自己的小快取：
 │cache │  │cache │  │cache │   …    │cache │      最常見的小 size class，
 └──┬───┘  └──┬───┘  └──┬───┘        └──┬───┘      不需要鎖，最快
    └────┬────┘         └──────┬────────┘
         ▼                     ▼
     ┌────────┐            ┌────────┐            ② arena：各自有鎖與 free list，
     │arena 0 │            │arena 1 │   …          多個 thread 分散到不同 arena
     └───┬────┘            └───┬────┘
         └──────────┬──────────┘
                    ▼
          ┌────────────────────┐                 ③ 向 kernel 要／還整頁：
          │ brk / mmap / madvise│                   mmap 新區域、madvise 歸還
          └────────────────────┘
```

| allocator | 誰在用 | 主要設計 | 記憶體歸還行為 |
|---|---|---|---|
| ptmalloc2 | glibc（大多數 Linux 發行版的預設） | 每個 thread 有 tcache（小 chunk 的快取）；多個 arena（64-bit 上預設最多約 8 × CPU 核心數）；bins 依大小分類；大配置直接 `mmap` | heap 頂端空出超過門檻才縮小；中間的空洞要 `malloc_trim` 才會用 `madvise` 歸還 |
| jemalloc | FreeBSD 的 libc、Redis 在 Linux 的預設建置 | 細緻的 size class、thread cache、多個 arena；同大小物件放在同一個 slab | 依時間衰減（decay）的策略，把閒置的整頁以 `madvise` 歸還 |
| tcmalloc | Google 的 C++ 服務 | thread 或 CPU 層級的快取；中央 free list；以 span（連續頁）為單位管理 | 背景或按需把閒置的 span 歸還 |
| mimalloc | Microsoft 開源，也用在多個語言 runtime | free list 依頁分片，配置路徑極短 | 閒置頁延遲歸還 |
| libmalloc | macOS | 依大小分 nano、tiny、small、large 等區域；最小的幾類以 16 bytes 為單位 | 大配置以頁為單位，可直接歸還 |

上表的細節會隨版本改變，重點是共通的設計：小配置走 size class 加 thread 快取（simple segregated storage 的變形），中型配置走 segregated fits，大配置直接 `mmap`。

這些設計都用空間換時間：每個 thread 的快取、每個 arena 都可能持有一些空閒記憶體，別人用不到。這就是 25.1 節那條不降曲線的一部分原因。

## 25.15 Malloc Lab 的學習目標

CS:APP 的 Malloc Lab 要學生在給定的介面下（初始化、配置、釋放、重新配置四個函式，以及一個模擬 `sbrk` 的函式庫）實作自己的 allocator，由驅動程式用一組預先準備好的請求 trace 評分，分數同時看 utilization 與 throughput。它是整本書最需要「自己設計」的一個 Lab，本書不提供解答，只整理它要你練的能力：

| 練的能力 | 為什麼重要 | 怎麼確認自己真的懂 |
|---|---|---|
| 用位元運算操作 header 與指標 | 一個型別轉換或加法單位錯了，整個 heap 就壞 | 能手算任一個 block 的 header、payload、下一個 block 的位址 |
| 維護不變量 | allocator 的正確性全靠不變量 | heap checker 能在 bug 發生的那一步就報錯 |
| 在 throughput 與 utilization 之間取捨 | 兩者會互相拉扯 | 能解釋每個設計決定讓哪個指標變好、哪個變差 |
| 依 trace 的特性調整 | 真實工作負載不是隨機的 | 能說出每個 trace 的請求模式（大小分佈、壽命、`realloc` 的比例） |

常見的卡關點：把指標運算的單位搞錯（`char *` 加 1 是 1 byte，`size_t *` 加 1 是 8 bytes）；延伸 heap 之後忘記和尾端的 free block 合併；`realloc` 只考慮搬家，沒考慮原地延伸或縮小；只追求分數而針對特定 trace 寫特例。建議的節奏是：先做最簡單、正確的版本並配上完整的 heap checker，在每一步都通過檢查之後，才一項一項加入最佳化，並記錄每項最佳化對兩個分數的影響。第 34 章有九個 Labs 的整體學習路線。

## 25.16 動手做：教學用迷你 allocator、真實 malloc 的尺寸、placement 策略模擬

### 程式一：implicit free list ＋ boundary tag 的迷你 allocator

這是一個刻意簡化的教學版本，不是 Malloc Lab 的解答：它使用固定的 1 KiB 靜態 arena、不向 kernel 要更多空間、沒有 `realloc`，介面也和 Lab 不同。它實作了本章 25.7 到 25.13 節的核心：8-byte header 與 footer、first fit、splitting、四種情況的 coalescing，以及一個 heap checker。

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>

/* 教學用迷你 allocator：固定 1 KiB 的 arena、implicit free list、
 * header + footer（boundary tag）、first fit、splitting、立即 coalescing。
 * 每個 block：[header 8B][payload ...][footer 8B]，大小是 16 的倍數，
 * 最低位元記錄「已配置」。 */
#define ARENA_SIZE 1024
#define ALIGN      16
#define TAG        8                       /* header 或 footer 的大小 */
#define MIN_BLOCK  32

static _Alignas(16) unsigned char arena[ARENA_SIZE];
static unsigned char *heap_lo, *heap_hi;  /* 第一個 block 的 header、heap 結尾 */

/* 用 memcpy 讀寫 8-byte 的 tag，避免違反 C 的 strict aliasing 規則 */
static uint64_t get_tag(const unsigned char *p) { uint64_t w; memcpy(&w, p, TAG); return w; }
static void put_tag(unsigned char *p, uint64_t w) { memcpy(p, &w, TAG); }

static size_t blk_size(unsigned char *b) { return get_tag(b) & ~(uint64_t)0xF; }
static int    blk_used(unsigned char *b) { return get_tag(b) & 1; }
static unsigned char *blk_next(unsigned char *b) { return b + blk_size(b); }
static void set_tags(unsigned char *b, size_t size, int used) {
    put_tag(b, size | (uint64_t)used);                     /* header */
    put_tag(b + size - TAG, size | (uint64_t)used);        /* footer */
}

void mini_init(void) {
    heap_lo = arena + TAG;                 /* 讓 payload（header 之後）落在 16 的倍數 */
    heap_hi = arena + ARENA_SIZE - TAG;
    set_tags(heap_lo, (size_t)(heap_hi - heap_lo), 0);   /* 一開始只有一個大 free block */
}

void *mini_alloc(size_t n) {
    if (n > ARENA_SIZE) return NULL;       /* 先擋掉過大的請求，避免下一行取整時溢位 */
    size_t need = (n + 2 * TAG + ALIGN - 1) & ~(size_t)(ALIGN - 1);
    if (need < MIN_BLOCK) need = MIN_BLOCK;
    for (unsigned char *b = heap_lo; b < heap_hi; b = blk_next(b)) {     /* first fit */
        if (blk_used(b) || blk_size(b) < need) continue;
        size_t rest = blk_size(b) - need;
        if (rest >= MIN_BLOCK) {           /* 剩下的夠大才切，否則整塊給出去（內部碎片） */
            set_tags(b, need, 1);
            set_tags(b + need, rest, 0);
        } else {
            set_tags(b, blk_size(b), 1);
        }
        return b + TAG;
    }
    return NULL;                           /* 沒有夠大的連續空間 */
}

void mini_free(void *p) {
    unsigned char *b = (unsigned char *)p - TAG;
    size_t size = blk_size(b);
    unsigned char *next = b + size;
    if (next < heap_hi && !blk_used(next)) size += blk_size(next);       /* 和後一塊合併 */
    if (b > heap_lo) {
        uint64_t prev_footer = get_tag(b - TAG);                   /* 靠 footer 找前一塊 */
        if (!(prev_footer & 1)) {
            b -= prev_footer & ~(uint64_t)0xF;
            size += blk_size(b);
        }
    }
    set_tags(b, size, 0);
}

int mini_check(void) {                     /* heap checker：檢查每一條不變量 */
    int prev_free = 0;
    unsigned char *b;
    for (b = heap_lo; b < heap_hi; b = blk_next(b)) {
        size_t s = blk_size(b);
        if (s < MIN_BLOCK || s % ALIGN || s > (size_t)(heap_hi - b)) { printf("  ✗ %td 大小 %zu 不合法\n", b - arena, s); return 0; }
        if (get_tag(b) != get_tag(b + s - TAG)) { printf("  ✗ header/footer 不一致\n"); return 0; }
        if ((uintptr_t)(b + TAG) % ALIGN) { printf("  ✗ payload 沒對齊\n"); return 0; }
        if (prev_free && !blk_used(b)) { printf("  ✗ 兩個相鄰 free block 沒合併\n"); return 0; }
        prev_free = !blk_used(b);
    }
    return b == heap_hi;                   /* block 要剛好鋪滿整個 heap */
}

static void dump(const char *label) {
    printf("%-22s", label);
    for (unsigned char *b = heap_lo; b < heap_hi; b = blk_next(b))
        printf(" [%s %zu]", blk_used(b) ? "used" : "free", blk_size(b));
    printf("  check=%s\n", mini_check() ? "ok" : "FAIL");
}

int main(void) {
    mini_init();                                   dump("init");
    char *a = mini_alloc(40);                      dump("a = alloc(40)");
    char *b = mini_alloc(100);                     dump("b = alloc(100)");
    char *c = mini_alloc(24);                      dump("c = alloc(24)");
    mini_free(b);                                  dump("free(b)");
    char *d = mini_alloc(48);                      dump("d = alloc(48)");
    mini_free(a);                                  dump("free(a)");
    mini_free(d);                                  dump("free(d)");
    printf("payload 位址 %% 16：a=%td c=%td\n", (a - (char *)arena) % 16, (c - (char *)arena) % 16);
    size_t total = 0, largest = 0;
    for (unsigned char *p = heap_lo; p < heap_hi; p = blk_next(p))
        if (!blk_used(p)) { total += blk_size(p); if (blk_size(p) > largest) largest = blk_size(p); }
    char *big = mini_alloc(800);                   /* 需要 816 bytes 的 block */
    printf("alloc(800) %s：free 總共 %zu bytes，最大的連續 free block 只有 %zu\n",
           big ? "成功" : "失敗", total, largest);
    mini_free(c);                                  dump("free(c)");
    big = mini_alloc(800);
    printf("alloc(800) %s\n", big ? "成功" : "失敗");
    return 0;
}
```

在 macOS arm64（Apple clang 21）上執行：

```text
init                   [free 1008]  check=ok
a = alloc(40)          [used 64] [free 944]  check=ok
b = alloc(100)         [used 64] [used 128] [free 816]  check=ok
c = alloc(24)          [used 64] [used 128] [used 48] [free 768]  check=ok
free(b)                [used 64] [free 128] [used 48] [free 768]  check=ok
d = alloc(48)          [used 64] [used 64] [free 64] [used 48] [free 768]  check=ok
free(a)                [free 64] [used 64] [free 64] [used 48] [free 768]  check=ok
free(d)                [free 192] [used 48] [free 768]  check=ok
payload 位址 % 16：a=0 c=0
alloc(800) 失敗：free 總共 960 bytes，最大的連續 free block 只有 768
free(c)                [free 1008]  check=ok
alloc(800) 成功
```

逐行對照前面的觀念：

1. **init**：arena 1,024 bytes，前後各留 8 bytes（讓 payload 對齊 16），所以一開始是一個 1,008 bytes 的 free block。
2. **alloc(40)**：需要 40 ＋ 16 = 56，取整到 64。first fit 找到唯一的 free block，切成 64（已配置）＋ 944（free）。`alloc(100)` 與 `alloc(24)` 同理，分別得到 128 與 48。
3. **free(b)**：b 的前後（a、c）都已配置，是 coalescing 的情況 1，只把自己標成 free。這一行就是 25.7 節手算走訪的那張表。
4. **alloc(48)**：需要 64。first fit 從頭找，a 已配置，接著是 b 留下的 128 → 切成 64 ＋ 64。新的 d 就住進 b 原本的位置，這就是 use-after-free 為什麼危險（第 26 章）：舊指標 `b` 現在指向 d 的資料。
5. **free(a)**：a 的後面是已配置的 d，前面是 heap 開頭，情況 1。
6. **free(d)**：d 的前面是 free 的 a（靠 footer 找到）、後面是 free 的 64，情況 4，三塊合成 192。這一行完整示範了 boundary tag 的用途。
7. **alloc(800) 失敗**：free 總共 960 bytes，但最大的連續 free block 只有 768，而 800 bytes 的請求需要 816 bytes 的 block。這就是 external fragmentation，罪魁禍首是夾在中間的 c。
8. **free(c)** 之後，c 的前後都是 free，三塊合併回 1,008，同一個請求就成功了。每一步的 `check=ok` 表示 heap checker 確認所有不變量都成立。

程式用 `memcpy` 讀寫 tag，而不是把 `unsigned char *` 直接轉成 `uint64_t *` 再取值。後者是許多 allocator 程式碼的寫法，但嚴格來說違反 C 的 strict aliasing 規則（第 10 章），是 undefined behavior；`memcpy` 寫法在 `-O1` 以上會被編譯器變成一條普通的 load／store，沒有額外成本。

### 程式二：真實的 malloc 給了你多少

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#if defined(__APPLE__)
#include <malloc/malloc.h>
#define USABLE(p) malloc_size(p)
#else
#include <malloc.h>
#define USABLE(p) malloc_usable_size(p)
#endif

int main(void) {
    size_t asks[] = {1, 24, 25, 100, 1000, 200000};
    for (size_t i = 0; i < sizeof asks / sizeof asks[0]; i++) {
        void *p = malloc(asks[i]);
        if (!p) return 1;
        printf("malloc(%6zu) → 可用 %6zu bytes，位址 %% 16 = %ju\n",
               asks[i], (size_t)USABLE(p), (uintmax_t)((uintptr_t)p % 16));
        free(p);
    }
    char *x = malloc(24), *y = malloc(24);         /* 連續兩次小配置，相距多遠？ */
    printf("兩個 malloc(24) 相距 %jd bytes\n", (intmax_t)((uintptr_t)y - (uintptr_t)x));
    free(x);
    free(y);
    return 0;
}
```

在 macOS arm64（Apple clang 21，系統 libmalloc）上執行：

```text
malloc(     1) → 可用     16 bytes，位址 % 16 = 0
malloc(    24) → 可用     32 bytes，位址 % 16 = 0
malloc(    25) → 可用     32 bytes，位址 % 16 = 0
malloc(   100) → 可用    112 bytes，位址 % 16 = 0
malloc(  1000) → 可用   1024 bytes，位址 % 16 = 0
malloc(200000) → 可用 212992 bytes，位址 % 16 = 0
兩個 malloc(24) 相距 32 bytes
```

macOS 的小配置以 16 bytes 為單位：`malloc(1)` 實際可用 16 bytes，`malloc(24)` 與 `malloc(25)` 都是 32，兩個 `malloc(24)` 剛好相距 32 bytes，代表 block 之間沒有夾著 header（macOS 把小配置的 metadata 放在別處）。這一行多跑幾次偶爾會變成負數或非常大的數字：macOS 的小配置會依 thread 當下所在的 CPU 選擇不同的區域，兩次 `malloc` 之間若被排到另一顆核心，兩塊就來自不同區域，相距多遠沒有意義。`malloc(200000)` 可用 212,992 bytes，正好是 13 個 16 KiB 的頁，說明大配置是以頁為單位直接取得的。所有位址都對齊 16。

同一支程式在 Linux x86-64 的 glibc 上，結果可以依 glibc 的 chunk 規則推算出來（這是推算，不是本機輸出）：chunk 大小是「請求 ＋ 8 bytes 的 size 欄位」往上取整到 16 的倍數、最少 32 bytes，可用大小是 chunk 減 8（下一個 chunk 的 `prev_size` 欄位在本 chunk 使用中時，可以被拿來放 payload，這就是 25.10 節「已配置的 block 省掉 footer」的最佳化）。

| 請求 | glibc chunk 大小 | 可用大小 | 推算過程 |
|---|---|---|---|
| 1 | 32 | 24 | 1 ＋ 8 = 9 → 取整 16，但最小 32 |
| 24 | 32 | 24 | 24 ＋ 8 = 32 |
| 25 | 48 | 40 | 25 ＋ 8 = 33 → 48 |
| 100 | 112 | 104 | 100 ＋ 8 = 108 → 112 |
| 1,000 | 1,008 | 1,000 | 1,000 ＋ 8 = 1,008 |
| 200,000 | 200,704 | 200,688 | 超過 mmap threshold，直接 `mmap`：200,016 ＋ 8 往上取整到 4 KiB 的頁（49 頁），可用大小再扣 16 bytes 的 chunk 標頭 |

兩種平台給出的數字不同，但原則一樣：你拿到的空間幾乎都比要求的多一點，差額就是 internal fragmentation。依賴「多出來的部分」是錯誤的：`malloc_usable_size` 與 `malloc_size` 只適合用來觀察，程式只能使用自己要求的 bytes 數。

### 程式三：在一段長序列上比較三種 placement 策略

25.8 節的手算只有三個請求。下面的 Python 程式產生 4,000 次配置（大小從 32 bytes 到 16 KiB 不等）與交錯的釋放，用三種策略各跑一次，比較最終 heap 大小、peak utilization 與搜尋時掃過的 block 數：

```python
import random

def simulate(policy, trace):
    """blocks: [start, size, free]，依位址排序；找不到合適的 free block 就擴大 heap。"""
    blocks, heap_end, rover = [], 0, 0
    where, live, peak_live, scanned = {}, 0, 0, 0
    for op, rid, size in trace:
        if op == "free":
            addr = where.pop(rid)
            i = next(k for k, b in enumerate(blocks) if b[0] == addr)
            blocks[i][2] = True
            live -= blocks[i][1]
            if i + 1 < len(blocks) and blocks[i + 1][2]:       # 和後一塊合併
                blocks[i][1] += blocks.pop(i + 1)[1]
            if i > 0 and blocks[i - 1][2]:                     # 和前一塊合併
                blocks[i - 1][1] += blocks.pop(i)[1]
            continue
        order = list(range(len(blocks)))
        if policy == "next":                                   # 從上次的位置接著找
            order = order[rover:] + order[:rover]
        fits = []
        for k in order:
            scanned += 1
            if blocks[k][2] and blocks[k][1] >= size:
                fits.append(k)
                if policy != "best":
                    break
        if fits:
            k = min(fits, key=lambda j: blocks[j][1]) if policy == "best" else fits[0]
            start, bsize, _ = blocks[k]
            blocks[k] = [start, size, False]
            if bsize > size:                                   # splitting
                blocks.insert(k + 1, [start + size, bsize - size, True])
            rover = k
        else:                                                  # 向 OS 要更多 heap
            start = heap_end
            blocks.append([start, size, False])
            heap_end += size
        where[rid] = start
        live += size
        peak_live = max(peak_live, live)
    return heap_end, peak_live / heap_end, scanned

def make_trace(seed, n=4000):
    rng, trace, alive = random.Random(seed), [], []
    for rid in range(n):
        size = rng.choice([32, 48, 64, 256, 1024, 4096]) * rng.randint(1, 4)
        trace.append(("alloc", rid, size))
        alive.append(rid)
        while len(alive) > 200 or (alive and rng.random() < 0.4):
            trace.append(("free", alive.pop(rng.randrange(len(alive))), 0))
    return trace

trace = make_trace(seed=213)
print(f"{'policy':<8}{'heap 大小':>12}{'peak utilization':>18}{'掃描的 block 數':>16}")
for policy in ("first", "next", "best"):
    heap, util, scanned = simulate(policy, trace)
    print(f"{policy:<8}{heap:>12,}{util:>18.1%}{scanned:>16,}")
```

在 macOS arm64（Python 3.14）上執行：

```text
policy       heap 大小  peak utilization     掃描的 block 數
first        643,488             90.1%         473,858
next         889,248             65.2%          36,423
best         633,248             91.5%         851,850
```

這組結果符合本章的預期：best fit 的 utilization 最高（91.5%），但掃描次數最多，因為它每次都要看完整條串列；next fit 掃描次數少了一個數量級，但 heap 大了約四成、utilization 只有 65.2%，因為它總是從上次的位置往後切，把大塊空間切碎；first fit 介於兩者之間。換一個 `seed` 或改變大小分佈，數字會變，但排序通常相同。這也說明了為什麼真實 allocator 不在一條長串列上做 best fit，而是用 segregated lists 縮小搜尋範圍：在小範圍裡做 best fit，同時拿到快和省。

## 25.17 在工作上怎麼用

### 情境一：free 了，RSS 卻不降

回到 25.1 節。小安照著下面的流程，一步步排除可能性：

```text
RSS 不降
  │
  ├─ 1. 先確認不是 leak：ASan／LeakSanitizer 或 heaptrack（第 26 章）
  │      └─ 有 leak → 修 leak
  │
  ├─ 2. 看是哪一種記憶體：/proc/PID/smaps_rollup（第 24 章）
  │      └─ Anonymous 佔大部分 → allocator 管理的 heap／arena
  │
  ├─ 3. 看 allocator 自己的統計
  │      ├─ glibc：在程式裡呼叫 malloc_stats() 或 malloc_info(0, stdout)
  │      └─ jemalloc：MALLOC_CONF=stats_print:true
  │      └─ 「in use」遠小於「system bytes」→ 空閒記憶體被 allocator 留著
  │
  ├─ 4. 做實驗確認：在淘汰快取後呼叫一次 malloc_trim(0)（glibc）
  │      └─ RSS 明顯下降 → 確定是保留，不是 leak
  │
  └─ 5. 選擇對策（每一項都要用真實流量量測）
         ├─ 限制 arena 數：MALLOC_ARENA_MAX=4 或 GLIBC_TUNABLES=glibc.malloc.arena_max=4
         ├─ 換 allocator：LD_PRELOAD=libjemalloc.so ./thumbd（第 19 章）
         ├─ 調整歸還策略：jemalloc 的 dirty_decay_ms 等參數
         └─ 改變配置模式：長壽命的小物件和短壽命的大緩衝區分開
```

`thumbd` 的根因是三件事疊在一起。第一，16 個 worker 分散在多個 arena，每個 arena 都留著一些空閒空間。第二，縮圖本身多在 50 KB 到 300 KB 之間，而 glibc 的 mmap threshold 會動態上調：一個用 `mmap` 配置的 chunk 被 `free` 後，門檻就提高到那個大小，之後同樣大小的縮圖改成從 arena 配置，不再走「`free` 即歸還」的路。第三，每個縮圖旁邊都配了一個長壽命的小 metadata 物件，零散地釘在 arena 各處，讓 arena 無法從頂端縮小。

小安的實驗中，`malloc_trim(0)` 讓 RSS 降了一大截，確認了是 allocator 保留而非 leak。最後的修法是：縮圖的像素緩衝區改用固定大小的物件池（自己的 simple segregated storage），metadata 集中配置，並在測試環境比較了 glibc 加 `MALLOC_ARENA_MAX` 與 jemalloc 兩種設定，選了在真實流量重播下 RSS 與延遲都比較好的那個。

### 情境二：allocator 成為效能瓶頸

`perf` 上 `malloc`、`free` 或 allocator 內部函式（例如 glibc 的 `_int_malloc`、`_int_free`）佔了明顯比例時，依序檢查：

1. **是不是配置太多次**：熱路徑上每個像素、每個 token 都 `malloc` 一次？改成一次配置整批、重用緩衝區，比任何 allocator 調校都有效。
2. **是不是鎖競爭**：`perf` 中看到 futex 或 allocator 的鎖相關函式？thread 很多時，換用 thread 快取更積極的 allocator（jemalloc、tcmalloc）通常有明顯改善。
3. **是不是跨 thread 釋放**：A thread 配置、B thread 釋放，會讓 thread 快取失效、甚至造成記憶體在 arena 間移動。producer-consumer 架構（第 30 章）特別容易出現。
4. **是不是 false sharing**：兩個 thread 頻繁寫入的小物件被配置在同一條 cache line 上（第 32 章）。

### 情境三：用 arena（bump）配置處理「一個請求的所有暫存」

`thumbd` 處理一張圖要配置很多暫存：解析後的 header、色彩表、中間的縮放緩衝區。它們的壽命都剛好等於「這個請求」。對這種模式，最有效的做法是 **arena allocator**（也叫 region 或 bump allocator）：請求開始時拿一大塊記憶體，配置只是把指標往前推，請求結束時一次全部丟掉。

```c
typedef struct { unsigned char *base; size_t used, cap; } req_arena_t;

/* 配置就是把 used 往前推；不支援單獨 free，請求結束時 used = 0 一次釋放全部 */
static void *req_alloc(req_arena_t *a, size_t n) {
    size_t start = (a->used + 15) & ~(size_t)15;     /* 維持 16-byte 對齊 */
    if (start > a->cap || n > a->cap - start) return NULL;  /* 先比較再相加，避免溢位 */
    a->used = start + n;
    return a->base + start;
}
```

這段程式沒有 header、沒有 free list、沒有 coalescing，配置只要幾條指令，也不可能有碎片或 leak（整塊一起釋放）。代價是你必須確定這些物件的壽命真的不會超過請求，否則就是 use-after-free。編譯器、遊戲引擎、資料庫的查詢執行器都大量使用這個技巧。

## 25.18 常見錯誤與除錯

| 症狀 | 常見原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| `free` 了很多，RSS 卻不降 | allocator 保留空閒記憶體；arena 中間有長壽命物件釘住 | `malloc_stats`、`malloc_info` 的 in-use 對 system；試 `malloc_trim(0)` | 限制 arena 數、換 allocator、分離長短壽命物件 |
| thread 數增加後 RSS 大幅上升 | 每個 arena／thread 快取各自保留記憶體 | 比較不同 thread 數下的 RSS；glibc 看 arena 數 | `MALLOC_ARENA_MAX`；改用 thread pool 控制 thread 數 |
| `malloc` 佔大量 CPU | 熱路徑頻繁配置；鎖競爭 | `perf record -g` 看呼叫者；看 futex | 重用緩衝區、批次配置、物件池、換 allocator |
| 程式在 `malloc` 或 `free` 內當機 | 先前有 heap overflow 或 double free，寫壞了 allocator 的 metadata | 用 ASan 重新執行，它會指出真正寫壞的那一行（第 26 章） | 修正越界寫入；不要只看當機的位置 |
| glibc 印出 `free(): invalid pointer` 或 `double free detected` | `free` 了不是 `malloc` 來的指標、`free` 兩次、或 `free` 了 payload 中間的位址 | ASan；檢查指標是否被加減過 | 每個指標只 `free` 一次，`free` 後設成 `NULL` |
| `p = realloc(p, n)` 失敗後資料不見 | `realloc` 失敗回傳 `NULL`，原指標被覆蓋，造成 leak | 讀程式碼 | 先用暫存變數接回傳值，確認非 `NULL` 再指派 |
| 自寫的 allocator 偶發性地把兩個物件疊在一起 | split 或 coalesce 時大小寫錯、footer 沒更新 | 每次操作後跑 heap checker | 修正後持續在 debug build 開著 heap checker |

## 25.19 動手練習

1. **手算**：用本章迷你 allocator 的規則（block = payload ＋ 16，取整到 16，最小 32），計算 `malloc(1)`、`malloc(17)`、`malloc(48)`、`malloc(49)` 的 block 大小與 internal fragmentation，並寫出每個已配置 block 的 header 十六進位值。（答案：32／31、48／31、64／16、80／31；header 為 `0x21`、`0x31`、`0x41`、`0x51`。）
2. **手算**：在 buddy system 中，heap 為 1 MiB，依序配置 200 KiB、60 KiB、300 KiB。畫出每次切割後的 free list，算出每個請求的 internal fragmentation，並指出位於 `0x40000`、大小 256 KiB 的 block 的夥伴位址。（驗證方法：用 Python 寫一個 20 行的 buddy 模擬器，印出 free list。）
3. 修改 25.16 節程式一，把 first fit 改成 best fit，用同一個 `main` 跑一次，比較每一步的 heap 狀態。再設計一組請求序列，讓 best fit 的結果反而比 first fit 差。
4. 延伸程式一：在 header 的 bit 1 記錄「前一塊是否已配置」，讓已配置的 block 不再寫 footer，並相應更新 coalescing 與 heap checker。用 `alloc(40)` 驗證：block 大小應該從 64 變成多少？
5. 修改 25.16 節程式三，加上一個「segregated fit」策略：依大小分成 8 個類別，各自用 best fit。比較它和其他三種策略的 heap 大小與掃描數。
6. 在 Linux 上寫一個多執行緒程式：16 個 thread 各自配置並釋放大量 100 KB 的區塊，結束前印出 `malloc_stats()`。分別在預設設定、`MALLOC_ARENA_MAX=1`、以及 `LD_PRELOAD` 載入 jemalloc 的情況下執行，比較執行時間與 RSS。

## 本章重點整理

- allocator 是使用者空間的程式，用 `brk`／`sbrk` 延伸 heap，或用 `mmap` 取得獨立區域；glibc 的大配置超過 mmap threshold 時直接 `mmap`，`free` 時立刻歸還。
- `free` 通常只把區塊還給 allocator，而不是 kernel，所以 `free` 之後 RSS 不下降不一定是 leak。
- `malloc` 回傳的位址在 x86-64 Linux（glibc）與 macOS 上都對齊 16 bytes；`calloc` 會檢查乘法溢位，`realloc` 失敗時原區塊仍然有效。
- C allocator 必須處理任意請求序列、立即回應、對齊，且不能移動已配置的區塊，這是它和 GC 最大的差別。
- 衡量 allocator 的兩個指標是 throughput 與 peak utilization，兩者常常互相衝突。
- Internal fragmentation 是 block 內部的浪費（header、對齊、最小 block、不切割），external fragmentation 是 free 空間足夠但不連續。
- Implicit free list 在每個 block 的 header 記錄大小與 allocated bit，靠大小隱含地串起所有 block，簡單但搜尋時間和全部 block 數成正比。
- First fit 簡單、next fit 較快但 utilization 通常較差、best fit utilization 最好但搜尋最久。
- Splitting 把過大的 free block 切開，但剩餘部分必須不小於最小 block；heap 延伸後要和尾端的 free block 合併。
- Boundary tag 在 block 尾端放 footer，讓 coalescing 的四種情況都能在常數時間完成；只讓 free block 帶 footer 是常見的空間最佳化。
- Explicit free list 只串 free block，segregated free lists 依大小分類，buddy system 用 2 的冪與 XOR 快速找到夥伴，每一種都是在速度與空間之間換取不同的平衡。
- 寫 allocator 或任何維護複雜不變量的資料結構時，先寫 heap checker 並在每次操作後呼叫，才能在 bug 發生的當下抓到它。
- 現代 allocator（ptmalloc、jemalloc、tcmalloc、mimalloc）用 thread 快取與多個 arena 降低鎖競爭，代價是保留更多空閒記憶體。
- 診斷 allocator 問題時，先排除 leak，再用 allocator 統計與 `malloc_trim` 這類實驗確認保留量，最後才調整 arena 數、換 allocator 或改變配置模式。

## 延伸問答

> [!question]- Q1. 為什麼 `free(p)` 不需要傳入大小，allocator 就知道要釋放多少？
> 因為 allocator 在配置時就把大小記在 block 自己身上。最常見的做法是在 payload 前面放一個 header，記錄整個 block 的大小與狀態；`malloc` 回傳的是 header 之後的位址，所以 `free(p)` 只要從 `p` 往回讀固定的幾個 bytes 就能拿到大小。
>
> 另一種做法是不放 header，而是從位址推算：simple segregated storage 把同大小的 block 放在同一頁，allocator 用「位址所在的頁」查表就知道 block 大小，macOS 與 jemalloc 的小配置都屬於這類。這也解釋了為什麼 `free` 一個不是 `malloc` 回傳的指標（例如 payload 中間的位址）會出大錯：allocator 讀到的「header」其實是你的資料。

> [!question]- Q2. 手算題：一個 allocator 的規則是「block = payload ＋ 8 bytes header，取整到 16 的倍數，最小 32 bytes」。程式依序 `malloc(10)`、`malloc(30)`、`malloc(100)`，總共會有多少 internal fragmentation？
> 逐一計算。`malloc(10)`：10 ＋ 8 = 18，取整到 32；最小也是 32，所以 block 32，internal fragmentation = 32 − 10 = 22。`malloc(30)`：30 ＋ 8 = 38，取整到 48，fragmentation = 48 − 30 = 18。`malloc(100)`：100 ＋ 8 = 108，取整到 112，fragmentation = 112 − 100 = 12。
>
> 總共 22 ＋ 18 ＋ 12 = 52 bytes 的 internal fragmentation，三個 block 合計 192 bytes 只裝了 140 bytes 的 payload，約 73%。這個算例也顯示小配置的浪費比例特別高：`malloc(10)` 的 block 有三分之二是浪費。這是為什麼大量小物件的程式會選擇物件池或專用的 slab，而不是一個一個 `malloc`。

> [!question]- Q3. 你在 production 看到一個 Java 服務的 RSS 比 `-Xmx` 設定的 heap 上限高出好幾 GB，而且 thread 數很多。你會懷疑什麼？
> Java 的 heap 由 JVM 自己管理，但 JVM 本身、JIT 編譯器、NIO 的 direct buffer、JNI library 等 native 程式碼仍然透過 glibc 的 `malloc` 配置記憶體，這部分不受 `-Xmx` 限制。glibc 在多執行緒下會建立多個 arena（64-bit 上最多約 8 × CPU 核心數），每個 arena 都可能保留空閒記憶體，thread 很多時加總可以很可觀。
>
> 確認方法：用 `pmap -x` 看是否有很多 64 MiB 左右的匿名區域（glibc thread arena 的典型大小），或開啟 JVM 的 Native Memory Tracking 區分 JVM 各部分的用量。常見對策是設定 `MALLOC_ARENA_MAX`（例如 2 或 4）、或用 `LD_PRELOAD` 換成 jemalloc，然後量測 RSS 與延遲是否改善。這是第 24 章「RSS 的組成」與本章 arena 設計結合的典型情境。

> [!question]- Q4. Boundary tag 解決了什麼問題？為什麼已配置的 block 可以不要 footer？
> implicit list 只能從一個 block 往後找下一個，因為 header 記錄的是自己的大小。`free` 時要和**前一個** block 合併，就得知道前一個 block 在哪、是否空閒，沒有 footer 的話只能從 heap 開頭重新掃描，`free` 變成線性時間。footer 把大小與狀態複製到 block 尾端，緊貼在下一個 block 的 header 前面，所以從任何一個 block 往回讀 8 bytes 就能知道前一塊的資訊，四種 coalescing 情況都變成常數時間。
>
> 只有「前一塊是空閒的」時才需要讀它的 footer，因為只有空閒的鄰居要合併。所以只要在每個 header 多記一個 bit「前一塊是否已配置」，已配置的 block 就不需要 footer，那 8 bytes 可以給 payload 用。glibc 的 `PREV_INUSE` bit 與 `prev_size` 欄位就是這個設計。

> [!question]- Q5. First fit、next fit、best fit 各適合什麼情況？為什麼真實 allocator 很少直接用其中任何一種？
> First fit 實作最簡單，搜尋在找到第一塊時就停止，utilization 通常不錯，但小碎片會堆在 heap 前段，讓搜尋越來越慢。Next fit 從上次的位置繼續，避免反覆掃過前段，速度較快，但會把後段的大塊不斷切碎，utilization 通常較差。Best fit 挑最貼合的那一塊，utilization 最好，但在單一串列上每次都要掃完整條。
>
> 真實 allocator 把問題拆小：依大小分成許多 size class，小配置在單一 class 內直接拿第一塊（幾乎不需要搜尋，且每塊大小相同，first 和 best 沒有差別），中型配置在相近大小的 bin 裡找最合適的。這樣搜尋範圍很小，又接近 best fit 的效果。所以三種策略的價值主要在理解取捨，真實系統則是用 segregated lists 同時取得兩邊的好處。

> [!question]- Q6. 程式找錯：`char *buf = malloc(len); ... buf = realloc(buf, len * 2); if (!buf) return -1;` 有什麼問題？
> 有兩個問題。第一，`realloc` 失敗時回傳 `NULL`，但原本的區塊**仍然有效、沒有被釋放**。這段程式直接把回傳值指派給 `buf`，失敗時原指標就遺失了，造成 memory leak，而且原本的資料也拿不回來。正確寫法是先用暫存變數接住：`char *tmp = realloc(buf, len * 2); if (!tmp) { /* buf 仍可用，自行處理 */ } buf = tmp;`。
>
> 第二，`len * 2` 可能溢位（第 5 章）。如果 `len` 是很大的 `size_t`，乘以 2 會繞回成一個很小的數，`realloc` 成功回傳一個很小的區塊，之後程式以為有 `len * 2` bytes 可寫，就造成 heap overflow。應該先檢查 `len > SIZE_MAX / 2`。此外，`realloc` 成功時可能把資料搬到新位址，任何先前指向舊區塊內部的指標都會失效。

> [!question]- Q7. 面試題：如果要你為一個「每秒處理數十萬個請求，每個請求配置大量小物件，請求結束後全部丟棄」的服務設計記憶體配置策略，你會怎麼做？
> 這個模式的關鍵是「物件的壽命和請求一致」，最適合 arena（region）配置：每個請求開始時取得一塊連續記憶體（可以從一個 per-thread 的 arena 池中取），配置只是把指標往前推並維持對齊，完全不需要個別 `free`；請求結束時把整塊歸還池中重用。這樣配置是幾條指令的成本，沒有碎片、不可能 leak，也沒有鎖競爭（每個 thread 用自己的 arena）。
>
> 需要注意的是邊界情況：單一請求需要的量超過 arena 大小時要能串接新的區塊；有少數物件的壽命必須超過請求（例如放進全域快取）時，它們必須改用一般 allocator 配置並複製過去，否則就是 use-after-free；arena 池本身要有上限，避免某次尖峰把記憶體永久撐大。對其餘無法用 arena 的部分，選擇一個 thread 快取良好的 allocator（jemalloc、tcmalloc），並用真實流量量測。

> [!question]- Q8. 為什麼 C 的 allocator 不能像 Java 的 GC 那樣「整理」heap、把 block 搬到一起來消除 external fragmentation？
> 搬動一個物件之後，所有指向它的指標都必須更新成新位址。Java、Go 這類語言的 runtime 知道每一個指標存在哪裡（物件欄位、stack 上的變數都有型別資訊），所以 compacting GC 可以在搬完之後逐一修正（第 26 章）。
>
> C 沒有這種資訊：指標可以存在任何記憶體位置、被轉成整數、和其他資料一起做雜湊、甚至被寫到檔案再讀回來。allocator 無法找出所有指向某個 block 的指標，所以一旦配置出去，block 就只能留在原位直到被 `free`。這是 25.3 節「不能移動已配置的區塊」這條限制的來源，也是 C allocator 必須靠 placement、coalescing 與 size class 這些「事前」策略來對抗碎片的原因。
>
> 有些 C／C++ 系統用「handle」（間接索引）取代直接指標，讓自己的記憶體可以搬動，但那是應用層的設計，不是 `malloc` 能做到的事。
