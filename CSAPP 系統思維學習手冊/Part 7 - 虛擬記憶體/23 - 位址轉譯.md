# 第 23 章　位址轉譯：Page Table、TLB 與 Page Fault

> [!abstract] 本章地圖
> **核心問題**：程式裡的每一個指標都是「虛擬位址」，CPU 怎麼在每一次讀寫時，把它變成記憶體晶片上真正的位置，又不讓程式變慢？
>
> **你會學到**：
> - 說清楚虛擬記憶體同時解決的三個問題：把 DRAM 當快取、讓每個 process 有一致的位址空間、提供隔離與保護
> - 把一個虛擬位址切成 VPN 與 VPO，並用 page table 手算出實體位址
> - 分辨 TLB hit、TLB miss、page fault 與 segmentation fault，知道每一種的代價
> - 算出單層 page table 為什麼放不下，以及多層 page table 怎麼省空間
> - 在工作上正確解讀 VSZ、RSS 與 page fault 指標，診斷「第一次請求特別慢」這類問題
>
> **前置知識**：第 15 章（記憶體階層與 cache 的一般概念）、第 16 章（cache 的位址切分）、第 20 章（exception 與 kernel mode）
>
> **對應 CS:APP 3e**：第 9 章 9.1–9.6 節

## 23.1 故事：30 GB 的縮圖服務

小安入職第三個月，某天早上收到 SRE 阿哲的訊息：「`thumbd` 是不是有 memory leak？`top` 上它吃了 30 GB 記憶體，但那台機器只有 16 GB。」

小安打開 `top`，看到 `thumbd` 那一列：`VIRT` 寫著 30.2g，`RES` 卻只有 1.8g。小安第一個反應是「這兩個數字差太多，一定是工具有 bug」。老周走過來看了一眼，說：「工具沒錯。30 GB 是 `thumbd` *可以用*的位址範圍，1.8 GB 才是它*真的佔用*的實體記憶體。這兩件事中間隔著一整層機制，叫虛擬記憶體。」

同一週還有另一件怪事：`thumbd` 重啟後，前幾百個請求的延遲是平常的五倍，之後才慢慢恢復。程式碼沒有任何「暖機」邏輯，為什麼第一次處理圖片會特別慢？

這兩個問題的答案都在本章。程式裡看到的每一個位址都不是真的實體位址，而是經過一張「對照表」翻譯出來的。翻譯平常幾乎免費，但在某些情況下代價很高。理解這層翻譯怎麼運作，才能正確解讀記憶體指標，也才能解釋為什麼「同一段程式，第一次跑比較慢」。

## 23.2 為什麼需要虛擬記憶體

先想像一個沒有虛擬記憶體的世界：每個程式直接用實體位址存取記憶體晶片。這會立刻遇到三個問題。

**第一，程式之間會互相踩到。** `thumbd` 把資料寫到位址 `0x5000`，同一台機器上的 log 收集程式也想用 `0x5000`。誰先搶到誰用？一個程式的 bug 寫壞了別人的資料，要怎麼防止？

**第二，每個程式都要知道「自己被放在哪裡」。** 如果 `thumbd` 這次被載入到 `0x40000000`、下次被載入到 `0x80000000`，程式裡所有寫死的位址都要跟著改。編譯器和連結器（第 18 章）會變得非常複雜。

**第三，實體記憶體不夠時怎麼辦。** 機器只有 16 GB，但所有程式加起來想用 40 GB。沒有任何機制可以把暫時不用的資料先放到磁碟上。

**虛擬記憶體**（virtual memory，VM）一次解決這三個問題。它的核心想法很簡單：**每個 process 看到的是自己專屬的、從 0 開始的一大片位址空間（虛擬位址），由硬體和作業系統在背後把它翻譯成實體記憶體上的位置（實體位址）。**

| 問題 | 虛擬記憶體的解法 | 在 `thumbd` 身上的例子 |
|---|---|---|
| 程式互相干擾 | 每個 process 有自己的翻譯表，A 的位址 `0x5000` 和 B 的 `0x5000` 對到不同的實體位置；表上還記錄權限，不能讀寫別人的記憶體 | `thumbd` 的 bug 最多弄壞自己，不會改到 nginx 的資料 |
| 每個程式位置不同 | 每個 process 看到的位址空間配置都一樣（程式碼、heap、stack 各在固定區域），連結器不必知道程式最後落在實體記憶體的哪裡 | 不管 `thumbd` 被放在實體記憶體哪裡，它的虛擬位址空間格局都相同；現代 Linux 的 ASLR 會隨機挪動各區起點（第 24 章），但這是刻意的安全措施，不是因為實體位置改變 |
| 實體記憶體不夠 | 只有「真的被用到」的部分才佔實體記憶體；暫時不用的可以留在磁碟，需要時再載入 | 那 30 GB 只是位址範圍，實際只佔 1.8 GB |

CS:APP 把這三個用途整理成虛擬記憶體的三個角色：**把 DRAM 當成磁碟的快取**、**簡化記憶體管理**、**提供記憶體保護**。這一章先專心看翻譯本身怎麼運作，第 24 章再看 Linux 怎麼利用這套機制做出 `mmap`、copy-on-write 這些功能。

## 23.3 Page：把位址空間切成固定大小的塊

如果要替每一個位元組都記錄「它被翻譯到哪裡」，翻譯表會比資料本身還大。所以虛擬記憶體以固定大小的塊為單位做翻譯，這個塊叫 **page**（頁）。Linux 在 x86-64 上的標準 page 大小是 4 KiB（4,096 bytes）；Apple Silicon 的 macOS 則用 16 KiB。

切成 page 之後，一個虛擬位址可以拆成兩部分：

```text
 虛擬位址（以 4 KiB page、48-bit 位址為例）
 47                               12 11              0
 ┌──────────────────────────────────┬────────────────┐
 │  VPN：virtual page number (36)   │ VPO：offset(12)│
 └──────────────────────────────────┴────────────────┘
           「第幾頁」                    「頁內第幾個 byte」
```

**VPN**（virtual page number，虛擬頁號）告訴你這個位址在第幾頁；**VPO**（virtual page offset，頁內位移）告訴你在這一頁裡的第幾個 byte。因為 page 大小是 2 的冪，切分只需要看位元：4 KiB = 2^12，所以最低 12 個 bit 就是 offset，其餘是 VPN。

實體記憶體也被切成同樣大小的塊，叫 **physical page** 或 **page frame**（實體頁框）。翻譯只發生在「頁號」這一層：VPN 被換成 **PPN**（physical page number），offset 原封不動。這是整個機制最重要的觀察：

> 翻譯只換頁號，不換頁內位移。同一頁裡相鄰的兩個 byte，翻譯之後在實體記憶體裡仍然相鄰。

用一個例子確認：位址 `0x7f3a12345abc`，page 4 KiB。最低 12 bits 是 `0xabc`，所以 VPO = `0xabc`、VPN = `0x7f3a12345`。不管它被翻譯到哪一個實體頁，最後的實體位址結尾一定還是 `abc`。

| page 大小 | offset 位元數 | 48-bit 位址的 VPN 位元數 | 常見系統 |
|---|---|---|---|
| 4 KiB | 12 | 36 | Linux x86-64、Windows、大部分 ARM Linux |
| 16 KiB | 14 | 34 | macOS on Apple Silicon、部分 Android |
| 2 MiB（huge page） | 21 | 27 | Linux 大頁，資料庫與 JVM 常用 |
| 1 GiB（huge page） | 30 | 18 | 需要極大連續記憶體的特殊用途 |

## 23.4 Page table：每個 process 的對照表

知道要「換頁號」之後，下一個問題是：VPN 要換成哪個 PPN？答案記錄在 **page table**（頁表）裡。每個 process 有自己的一張 page table，由作業系統建立與維護，放在實體記憶體中。

Page table 可以想成一個以 VPN 為索引的陣列，每一格叫 **PTE**（page table entry，頁表項目）。一個 PTE 至少記錄：

| 欄位 | 意義 | 例子 |
|---|---|---|
| valid（present）bit | 這個虛擬頁現在是否在實體記憶體中 | 1：在 DRAM；0：還沒分配、或被換到磁碟 |
| PPN | 對應的實體頁號（valid 為 1 時才有意義） | `0x2A` |
| 權限位元 | 讀、寫、執行、user／kernel | 程式碼頁只能讀與執行，不能寫 |
| dirty bit | 這頁被寫過嗎？換出前要不要寫回磁碟 | 寫入時由硬體設為 1 |
| accessed bit | 最近被存取過嗎？作業系統用來挑選要換出的頁 | 讀寫時由硬體設為 1 |

查表的結果有三種：

```text
                       用 VPN 查 page table
                                │
            ┌───────────────────┼─────────────────────────┐
            ▼                   ▼                         ▼
     valid = 1，權限允許   valid = 0                 權限不允許
     → page hit           → page fault              （例如寫入唯讀頁）
     直接得到 PPN         → 交給 kernel 處理          → protection fault
                          ├─ 這頁「應該存在」        → kernel 通常送出 SIGSEGV
                          │                            （例外：copy-on-write，第 24 章）
                          │  （還沒載入、在磁碟上）
                          │  → 載入後重新執行指令
                          └─ 這頁根本不屬於任何區域
                             → SIGSEGV（segmentation fault）
```

**Page hit**（頁命中）是最常見的情況：PTE 有效、權限允許，直接拿到 PPN。**Page fault**（缺頁例外）表示這個虛擬頁目前不在實體記憶體中，硬體無法自己完成翻譯，必須觸發一個 exception（第 20 章）交給作業系統處理。

這裡要特別注意：**page fault 不等於程式出錯**。大部分 page fault 是完全正常的：程式剛 `malloc` 一大塊記憶體，作業系統並沒有立刻分配實體頁，而是等程式第一次寫入時才觸發 page fault、分配一頁、填零，再讓程式繼續執行。只有當位址不屬於任何合法區域，或違反該區域的權限時，作業系統才會送出 `SIGSEGV`，也就是大家熟悉的 segmentation fault。protection fault 也有一個「正常」的例外：copy-on-write 的頁在 PTE 上被刻意設成唯讀，第一次寫入時 kernel 會複製一份再讓程式繼續，第 24 章會詳細說明。

### 把 DRAM 想成磁碟的快取

CS:APP 用一個很有用的角度看 page table：DRAM 是虛擬位址空間的**快取**，磁碟是後面的大儲存。從這個角度，虛擬記憶體的許多設計就變得合理：

| 快取設計問題 | 一般 CPU cache（第 16 章） | 虛擬記憶體（DRAM 當快取） | 原因 |
|---|---|---|---|
| 塊大小 | 64 bytes | 4 KiB 以上 | 磁碟第一次存取很慢，一次多搬一點比較划算 |
| 放置方式 | direct-mapped 或 set associative | fully associative（任何虛擬頁可以放到任何實體頁） | miss 的代價極大，值得用複雜的放置換取更少的 miss |
| 替換決策 | 硬體電路 | 作業系統軟體 | 軟體可以用更聰明的演算法 |
| 寫入策略 | write-back 或 write-through | 只能 write-back | 每次寫入都寫磁碟太慢 |
| miss 代價 | 約 100 ns（到 DRAM） | 從 SSD 約數十 µs 以上，從 HDD 約數 ms | 差了好幾個數量級 |

## 23.5 一次完整的位址轉譯

現在把各元件串起來。負責翻譯的硬體叫 **MMU**（memory management unit，記憶體管理單元），它在 CPU 晶片上。CPU 每執行一條會存取記憶體的指令，MMU 就做一次翻譯：

```text
   CPU 核心                                     記憶體
 ┌────────────┐  ① 虛擬位址 VA     ┌──────┐
 │ 執行指令   │ ─────────────────▶ │ MMU  │
 │ mov (%rdi) │                    │      │ ② 用 VPN 找 PTE 的位址
 └────────────┘                    │      │ ─────────────────────▶ page table
        ▲                          │      │ ③ 讀回 PTE（含 PPN）  （在 DRAM 中）
        │                          │      │ ◀─────────────────────
        │                          │      │ ④ 實體位址 PA = PPN ∥ VPO
        │                          │      │ ─────────────────────▶ cache／DRAM
        │ ⑤ 資料                   └──────┘
        └──────────────────────────────────────────────────────── 資料
```

① CPU 送出虛擬位址。② MMU 用 VPN 算出 PTE 在 page table 中的位置。page table 的起點存在一個特殊暫存器（x86-64 上是 `CR3`），每個 process 不同；context switch（第 20 章）時作業系統會切換它，所以每個 process 自動用自己的表。③ MMU 從記憶體讀回 PTE。④ 如果有效，MMU 把 PPN 接上原本的 offset，得到實體位址，再把它送到 cache 與記憶體系統。⑤ 資料回到 CPU。

用公式寫就是：

```text
VPN = VA >> p            （p = log2(page size)）
VPO = VA & (page size − 1)
PTE 位址 = page table 起點 + VPN × PTE 大小
PA  = (PPN << p) | VPO
```

這個流程有一個明顯的問題：**每一次記憶體存取，都要先額外讀一次記憶體（讀 PTE）**。如果 PTE 不在 cache 裡，一次讀取就變成兩次 DRAM 存取，程式慢一倍。這顯然不能接受，下一節的 TLB 就是為了解決它。

## 23.6 TLB：翻譯結果的快取

**TLB**（translation lookaside buffer，轉譯後備緩衝區）是 MMU 裡一個小而快的快取，專門存「最近用過的 VPN → PPN 對照」。它通常只有幾十到幾千個 entry，但因為程式有 locality（第 15 章），同一頁會被連續存取很多次，所以 TLB 的命中率通常非常高。

TLB 本身就是一個 set associative cache（第 16 章），所以 VPN 會被再切一次：

```text
 VPN
 ┌──────────────────────────┬──────────────┐
 │ TLBT：TLB tag            │ TLBI：set 索引│
 └──────────────────────────┴──────────────┘
   在 set 裡比對是不是同一頁     決定去哪一個 set 找
   （剩下的位元）                （log2(set 數) 個位元）
```

有了 TLB，翻譯流程變成：

```text
         VPN
          │
          ▼
    ┌───────────┐   hit（大多數情況，約 1 個 cycle）
    │   TLB     │ ──────────────────────────────▶ 直接得到 PPN
    └───────────┘
          │ miss
          ▼
    查 page table（page walk，讀記憶體，可能要數十到數百個 cycle）
          │
     ┌────┴──────────────┐
     ▼                   ▼
  PTE 有效            PTE 無效
  → 填入 TLB          → page fault
  → 得到 PPN          → kernel 處理（數 µs 到數 ms）
```

這張圖裡有三種代價差很多的事件，工作上很容易混為一談：

| 事件 | 發生在哪 | 誰處理 | 典型代價 | 是不是錯誤 |
|---|---|---|---|---|
| TLB hit | MMU 內部 | 硬體 | 約 1 cycle，幾乎免費 | 否 |
| TLB miss | MMU 查記憶體裡的 page table | 硬體（x86、ARM 都有硬體 page walker） | 數十到數百 cycle | 否 |
| page fault（minor） | 頁面「應該存在」但還沒對應到實體頁，例如第一次寫入新配置的記憶體 | kernel | 約數百 ns 到數 µs | 否，正常行為 |
| page fault（major） | 資料要從磁碟讀進來（被換出的頁、mmap 的檔案） | kernel ＋ 磁碟 I/O | 數十 µs 到數 ms | 否，但很慢 |
| segmentation fault | 位址不合法或違反權限 | kernel 送出 SIGSEGV | 程式通常結束 | 是 |

**minor fault**（輕微缺頁）不需要讀磁碟，**major fault**（嚴重缺頁）需要。這兩個數字作業系統都會統計，下面的動手做會量到它們。

> [!warning] 常見誤解
> 「TLB miss 就是 page fault。」不是。TLB miss 只表示翻譯結果不在 TLB 裡，硬體會自己去 page table 查，查到有效的 PTE 就完成了，作業系統完全不知道。只有 PTE 無效時，才會變成 page fault 交給 kernel。

## 23.7 多層 page table：為什麼不能只有一張表

到目前為止，我們把 page table 想成一個「以 VPN 為索引」的大陣列。算一下它有多大：x86-64 目前使用 48-bit 虛擬位址，page 4 KiB，所以 VPN 有 36 bits，也就是 2^36 個虛擬頁；每個 PTE 8 bytes。

```text
2^36 個 PTE × 8 bytes = 2^39 bytes = 512 GiB
```

**每一個 process** 都要一張 512 GiB 的表，這當然不可能。關鍵觀察是：絕大多數 process 只用到位址空間裡很小的幾塊（程式碼、heap、幾個 library、stack），中間大片空白根本沒用。一個連續的大陣列會為這些空白也配置 PTE。

**多層 page table**（multi-level page table）用「目錄的目錄」解決這個問題，就像書的目錄先分章、章再分節。x86-64 用四層，把 36-bit VPN 切成四段，每段 9 bits：

```text
 48-bit 虛擬位址
 ┌────────┬────────┬────────┬────────┬────────────┐
 │ VPN1(9)│ VPN2(9)│ VPN3(9)│ VPN4(9)│ VPO (12)   │
 └───┬────┴───┬────┴───┬────┴───┬────┴─────┬──────┘
     │        │        │        │          │
 CR3 ▼        ▼        ▼        ▼          │
 ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐   │
 │ L1 表 │→│ L2 表 │→│ L3 表 │→│ L4 表 │→ PPN ──┐
 │512 項 │ │512 項 │ │512 項 │ │512 項 │        ▼
 └───────┘ └───────┘ └───────┘ └───────┘    PA = PPN ∥ VPO
```

每一張表都剛好是一個 page 的大小：512 個 entry × 8 bytes = 4 KiB。第 1 層的每個 entry 管 512 GiB 的範圍；如果這個範圍完全沒用到，entry 就標記為無效，**底下的三層表都不必存在**。

用 `thumbd` 估算一下：假設它用了程式碼、heap 與 library 共約 2 GiB 的連續區域，加上 stack。2 GiB 需要 2 GiB ÷ 4 KiB = 524,288 個 L4 PTE，也就是 1,024 張 L4 表；往上只需要少量 L3、L2 表和 1 張 L1 表。總共大約 1,030 多張表、4 MiB 左右，遠小於 512 GiB。

| 方案 | 每個 process 的表大小 | 代價 |
|---|---|---|
| 單層陣列 | 512 GiB（無論用多少） | 不可行 |
| 四層 page table | 只與實際使用量成正比，`thumbd` 約數 MiB | TLB miss 時要讀四次記憶體 |

多層表的代價是：TLB miss 時要依序讀四層，等於四次記憶體存取。這再次說明 TLB 為什麼重要，也說明為什麼 CPU 還會額外快取中間層的 entry（叫 page-walk cache 或 paging-structure cache）。較新的 Intel 與 AMD 處理器支援 57-bit 位址的五層 page table，原理相同，只是多一層。

## 23.8 保護：PTE 的權限位元如何隔離 process 與 kernel

到目前為止，我們把 PTE 當成「頁號對照表」。但 23.2 節提到虛擬記憶體的第三個角色是保護，這個角色同樣靠 PTE 完成：每一次存取，MMU 除了查 PPN，也同時檢查權限位元，不符合就觸發 fault。因為這個檢查發生在每一次存取、由硬體完成，程式沒有任何方法繞過它。

x86-64 的 PTE 有三個和保護直接相關的位元：

| 位元 | 意義 | 違反時 | 典型用途 |
|---|---|---|---|
| R/W（可寫） | 0 表示唯讀 | 寫入時 protection fault | 程式碼與 `.rodata` 設為唯讀，防止被意外或惡意修改 |
| U/S（user／supervisor） | 0 表示只有 kernel mode 能存取 | user mode 存取時 fault | kernel 的資料雖然映射在每個 process 的位址空間裡，user 程式卻碰不到 |
| XD／NX（不可執行） | 1 表示這頁的內容不能當作指令執行 | 跳到這頁執行時 fault | stack 與 heap 設為不可執行，資料頁不能被當成指令執行（第 11 章） |

這三個位元合起來，形成作業系統最基本的保護模型：

```text
 process 的虛擬位址空間（簡化）
 ┌──────────────────────────────┐ 高位址
 │ kernel 程式碼與資料           │ U/S = kernel only
 ├──────────────────────────────┤
 │ stack                        │ 可讀、可寫、不可執行
 │   ...                        │
 │ 共享 library 的程式碼         │ 可讀、可執行、不可寫
 │ heap                         │ 可讀、可寫、不可執行
 │ .data／.bss                  │ 可讀、可寫、不可執行
 │ .rodata                      │ 只能讀
 │ .text（程式碼）               │ 可讀、可執行、不可寫
 └──────────────────────────────┘ 低位址
```

這個配置有一個重要原則叫 **W^X**（write xor execute）：同一頁不應該同時可寫又可執行。如果攻擊者能把資料寫進一頁，那一頁就不該能被執行；能執行的頁，就不該能被寫入。現代作業系統替程式碼、stack、heap 預設的權限都遵守這個原則，但強制程度不同：OpenBSD 與 Apple Silicon 上的 macOS 會直接限制同時可寫又可執行的映射；Linux 預設仍允許程式自己用 `mmap`／`mprotect` 要求可寫又可執行的頁，是否遵守由程式（或 SELinux 等安全模組）決定。因此需要在執行時產生機器碼的程式（例如 JavaScript 引擎、JVM 的 JIT 編譯器），好的做法是先寫入、再用 `mprotect` 把頁改成可執行，而不是兩者同時開啟。

kernel 的頁也映射在每個 process 的位址空間裡，只是標記為 kernel only。這樣 system call 進入 kernel 時不必切換 page table，速度比較快。2018 年公開的 Meltdown 漏洞顯示，部分處理器在推測執行（第 13 章）時，可能在權限檢查完成前就讀到 kernel 資料並留下 cache 痕跡。因此 Linux 加入了 KPTI（kernel page-table isolation）：在 user mode 時使用一張幾乎不含 kernel 映射的 page table。這是一個很好的例子，說明硬體的權限檢查並不是「有就安全」，它和 pipeline、cache 的實作細節會互相影響。

## 23.9 手算一次：迷你系統的完整轉譯

教科書的位元數太大，不好手算。我們設計一個迷你系統，用它把整個流程走一遍。這也是 23.11 節程式模擬的系統。

| 參數 | 值 | 推導出的位元數 |
|---|---|---|
| 虛擬位址 | 16 bits | — |
| 實體位址 | 14 bits | — |
| page 大小 | 256 bytes | VPO = log2(256) = 8 bits，VPN = 16 − 8 = 8 bits |
| 實體頁 | — | PPN = 14 − 8 = 6 bits |
| TLB | 8 entries、2-way | 8 ÷ 2 = 4 sets → TLBI = 2 bits，TLBT = 8 − 2 = 6 bits |

Page table 中目前有效的三個 entry：

| VPN | valid | PPN |
|---|---|---|
| 0x12 | 1 | 0x2A |
| 0x13 | 1 | 0x07 |
| 0x40 | 1 | 0x15 |
| 其他 | 0 | — |

TLB 一開始是空的。現在依序翻譯 `0x1234`、`0x12F0`、`0x7777`。

**第一個：`0x1234`**

```text
0x1234 = 0001 0010 0011 0100
         └ VPN ─┘ └ VPO ──┘
VPN  = 0x12，VPO = 0x34
TLBI = VPN mod 4 = 0x12 & 0b11 = 2      → 去 set 2 找
TLBT = VPN >> 2  = 0x04
```

TLB 是空的 → TLB miss → 查 page table：VPN 0x12 有效，PPN = 0x2A → 把 (tag 0x04 → PPN 0x2A) 填進 TLB 的 set 2。

```text
PA = (0x2A << 8) | 0x34 = 0x2A34
   = 10 1010 0011 0100（14 bits）
```

**第二個：`0x12F0`**。VPN 還是 0x12（同一頁），VPO = 0xF0。set 2 裡剛好有 tag 0x04 → **TLB hit**，PA = `0x2AF0`。這就是 locality 的效果：同一頁的第二次存取不必再查表。

**第三個：`0x7777`**。VPN = 0x77，TLB miss，查表發現 VPN 0x77 無效 → **page fault**。如果作業系統判斷這個位址屬於合法區域（例如 heap 剛擴大），它會分配一個實體頁、更新 PTE，然後讓 CPU 重新執行這條指令；如果不屬於任何合法區域，就送出 `SIGSEGV`。

## 23.10 Page fault 發生時，作業系統做了什麼

Page fault 是一種 fault 類型的 exception（第 20 章）：它發生在指令執行到一半，處理完之後，CPU 會**重新執行同一條指令**，而不是跳到下一條。對程式來說，它只是「這條指令花了比較久」，完全不知道中間發生了什麼。

```text
 使用者程式                        kernel
 ──────────                        ──────
 mov %eax, (%rdi)   ── page fault ──▶ ① 這個位址屬於哪個區域？
   （暫停）                             ├─ 不屬於任何區域 → 送 SIGSEGV
                                        ├─ 違反區域權限（寫 .rodata）→ SIGSEGV
                                        └─ 合法 → ② 找一個空的實體頁
                                                    （不夠就挑一頁換出）
                                                 ③ 需要時從檔案或 swap 讀入
                                                    （這一步才是 major fault）
                                                 ④ 更新 PTE，valid = 1
 mov %eax, (%rdi)   ◀── 返回，重新執行 ──
   （這次成功）
```

注意圖中檢查的是「區域」的權限，而不只是 PTE 的權限位元：寫入一個 PTE 唯讀、但所屬區域可寫的 copy-on-write 頁，kernel 會複製一頁後重新執行，而不是送 `SIGSEGV`。第 24 章會詳細看 Linux 怎麼記錄「合法區域」（VMA）、怎麼處理檔案映射與 copy-on-write。這裡先記住三件事：

1. page fault 由硬體觸發、作業系統處理，程式不需要也無法自己處理。
2. 大多數 page fault 是正常的，是作業系統「用到才給」（demand paging，需求分頁）策略的一部分。
3. 只有 major fault 需要磁碟 I/O，那才是真正昂貴的情況。

## 23.11 動手做：模擬 TLB，並量測真實的 page fault

### 程式一：迷你系統的 TLB 與 page table

這段 C 程式實作 23.9 節的迷你系統：8-entry、2-way 的 TLB 用 LRU 替換，page table 只有三個有效項目。

```c
#include <stdint.h>
#include <stdio.h>

/* 迷你系統：16-bit 虛擬位址、256-byte page、14-bit 實體位址。
 * VPN = 8 bits、VPO = 8 bits；PPN = 6 bits。
 * TLB：8 個 entry、2-way set associative → 4 個 set（TLBI 2 bits、TLBT 6 bits）。 */
#define PAGE_BITS 8
#define TLB_SETS 4
#define TLB_WAYS 2

typedef struct { int valid; uint8_t ppn; } pte_t;
typedef struct { int valid; uint8_t tag; uint8_t ppn; int last_used; } tlb_entry_t;

static pte_t page_table[256];
static tlb_entry_t tlb[TLB_SETS][TLB_WAYS];
static int clock_tick;

static int translate(uint16_t va, uint16_t *pa) {
    uint8_t vpn = va >> PAGE_BITS, vpo = va & 0xFF;
    uint8_t set = vpn % TLB_SETS, tag = vpn / TLB_SETS;
    clock_tick++;
    for (int w = 0; w < TLB_WAYS; w++) {
        tlb_entry_t *e = &tlb[set][w];
        if (e->valid && e->tag == tag) {           /* TLB hit：不用查 page table */
            e->last_used = clock_tick;
            *pa = (uint16_t)(e->ppn << PAGE_BITS | vpo);
            printf("VA 0x%04x  VPN 0x%02x  TLB hit           → PA 0x%04x\n", va, vpn, *pa);
            return 0;
        }
    }
    if (!page_table[vpn].valid) {                 /* page fault：交給 OS */
        printf("VA 0x%04x  VPN 0x%02x  TLB miss, PTE 無效 → page fault\n", va, vpn);
        return -1;
    }
    int victim = 0;                               /* LRU：挑最久沒用的 way */
    for (int w = 1; w < TLB_WAYS; w++)
        if (tlb[set][w].last_used < tlb[set][victim].last_used) victim = w;
    tlb[set][victim] = (tlb_entry_t){1, tag, page_table[vpn].ppn, clock_tick};
    *pa = (uint16_t)(page_table[vpn].ppn << PAGE_BITS | vpo);
    printf("VA 0x%04x  VPN 0x%02x  TLB miss, 查表   → PA 0x%04x\n", va, vpn, *pa);
    return 0;
}

int main(void) {
    page_table[0x12] = (pte_t){1, 0x2A};
    page_table[0x13] = (pte_t){1, 0x07};
    page_table[0x40] = (pte_t){1, 0x15};
    uint16_t trace[] = {0x1234, 0x12F0, 0x1301, 0x4008, 0x1210, 0x7777};
    uint16_t pa;
    for (size_t i = 0; i < sizeof trace / sizeof trace[0]; i++)
        translate(trace[i], &pa);
    return 0;
}
```

執行結果：

```text
VA 0x1234  VPN 0x12  TLB miss, 查表   → PA 0x2a34
VA 0x12f0  VPN 0x12  TLB hit           → PA 0x2af0
VA 0x1301  VPN 0x13  TLB miss, 查表   → PA 0x0701
VA 0x4008  VPN 0x40  TLB miss, 查表   → PA 0x1508
VA 0x1210  VPN 0x12  TLB hit           → PA 0x2a10
VA 0x7777  VPN 0x77  TLB miss, PTE 無效 → page fault
```

逐行對照：

1. 前兩行就是 23.9 節的手算結果：第一次碰 VPN 0x12 是 miss，第二次同一頁就 hit。
2. `0x1301` 的 VPN 是 0x13，TLBI = 0x13 mod 4 = 3，放進 set 3。`0x4008` 的 VPN 是 0x40，TLBI = 0，放進 set 0。三個頁分別落在不同的 set，互不干擾。
3. `0x1210` 又回到 VPN 0x12，set 2 裡的 entry 還在，所以 hit。
4. 最後 `0x7777` 的 PTE 無效，模擬器在這裡回報 page fault；真實系統會在這一刻進入 kernel。

真實的 MMU 做的事完全一樣，只是位元數更多、用電路在一個 cycle 內完成比對。

### 程式二：量測真實的 page fault

第二段程式向作業系統要 64 MiB 的虛擬記憶體，然後一頁一頁寫入，觀察 minor fault 次數的變化。

```c
#include <stdio.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <unistd.h>

static long minor_faults(void) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(void) {
    long page = sysconf(_SC_PAGESIZE);
    size_t len = 64UL * 1024 * 1024;               /* 要 64 MiB 的虛擬空間 */
    char *p = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANON, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    /* 先量完再印：printf 本身也可能碰到新頁，混在量測區間裡會多算 */
    long before = minor_faults();
    long after_mmap = minor_faults() - before;
    for (size_t off = 0; off < len / 2; off += (size_t)page)   /* 只寫前半段 */
        p[off] = 1;
    long after_first = minor_faults() - before;
    for (size_t off = 0; off < len / 2; off += (size_t)page)   /* 再寫一次同樣的 page */
        p[off] = 2;
    long after_second = minor_faults() - before;

    long touched = (long)(len / 2 / (size_t)page);
    printf("page size = %ld bytes，mmap 完成，還沒有碰任何一頁\n", page);
    printf("mmap 之後新增的 minor fault：%ld\n", after_mmap);
    printf("寫了前半段 %ld 個 page 之後：%ld 次 minor fault\n", touched, after_first);
    printf("再寫一次同樣的 page 之後：%ld 次（沒有增加）\n", after_second);
    munmap(p, len);
    return 0;
}
```

在一台 Apple Silicon 的 macOS 上執行（page 大小 16 KiB）：

```text
page size = 16384 bytes，mmap 完成，還沒有碰任何一頁
mmap 之後新增的 minor fault：0
寫了前半段 2048 個 page 之後：2048 次 minor fault
再寫一次同樣的 page 之後：2048 次（沒有增加）
```

這個結果直接回答了 23.1 節的兩個問題：

1. **`mmap` 64 MiB 不會產生任何 fault，也不佔實體記憶體。** 作業系統只是記下「這段位址範圍是合法的」，PTE 全部是無效的。這就是 `top` 裡 VIRT 很大、RES 很小的原因：VIRT 算的是所有合法範圍，RES 算的是真正有實體頁的部分。
2. **第一次寫入每一頁都觸發一次 minor fault**，剛好一頁一次：32 MiB ÷ 16 KiB = 2,048。作業系統在每次 fault 時才分配實體頁並填零。
3. **第二次寫同樣的頁不再 fault**，因為 PTE 已經有效。

在 Linux x86-64 上執行，page 大小是 4,096 bytes，預期會看到約 8,192 次 minor fault，原理相同。但如果系統的 Transparent Huge Pages（23.12 節）設為 `always`，kernel 可能直接用 2 MiB 大頁滿足這段匿名映射，一次 fault 就對上 512 個 4 KiB 頁，次數會少很多；可以用 `cat /sys/kernel/mm/transparent_hugepage/enabled` 確認設定。`thumbd` 重啟後前幾百個請求變慢，部分原因正是這個：每個 worker thread 第一次碰到影像緩衝區、快取、library 的資料頁時，都要付一次 page fault 的代價；之後就不必再付。

## 23.12 在工作上怎麼用

### 正確解讀記憶體指標

這是最常見、也最容易誤判的情境。Linux 上的幾個數字分別代表：

| 指標 | 出處 | 意義 | 常見誤解 |
|---|---|---|---|
| VSZ／VIRT | `ps`、`top` | 所有合法虛擬位址範圍的總和 | 「VIRT 很大就是 leak」：不一定，`mmap` 預留、thread stack、library 都算在內 |
| RSS／RES | `ps`、`top` | 目前真的在實體記憶體中的頁 | RSS 包含共享 library 的頁，多個 process 加總會重複計算 |
| PSS | `/proc/PID/smaps_rollup` | 共享頁按共享的 process 數平均分攤 | 要估算「這個服務真正佔多少」時比 RSS 準 |
| minflt／majflt | `ps -o min_flt,maj_flt`、`/proc/PID/stat` | 累計的 minor／major fault 次數 | major fault 持續增加通常代表記憶體不夠、在換頁，minor fault 多通常是正常的 |

所以阿哲那句「吃了 30 GB」的正確解讀是：`thumbd` 預留了 30 GB 位址空間（例如每個 thread 的 stack、allocator 的預留區），真正佔用 1.8 GB。要判斷是否 leak，應該看 RSS 或 PSS 是否隨時間持續上升，而不是看 VIRT（第 26 章會教怎麼確認 leak）。

### 診斷「第一次比較慢」

當一個服務重啟、或第一次處理某類請求時特別慢，可以用這個流程確認是否和 page fault 有關：

```text
症狀：重啟後 / 第一次請求 延遲特別高
  │
  ├─ 1. 觀察 fault：ps -o min_flt,maj_flt -p <PID>，請求前後各看一次
  │      └─ major fault 大量增加？→ 資料從磁碟讀入（mmap 的檔案、被換出的頁）
  │      └─ 只有 minor fault 增加？→ 第一次觸碰新記憶體
  │
  ├─ 2. 用 perf 觀察（Linux）：perf stat -e page-faults,dTLB-load-misses -p <PID>
  │
  └─ 3. 對策
         ├─ 啟動時預先觸碰（pre-fault）需要的緩衝區
         ├─ mmap 時用 MAP_POPULATE 讓 kernel 預先載入
         ├─ 對延遲極度敏感的服務用 mlock 鎖住記憶體，避免被換出
         └─ 啟動後先送暖機流量，再把服務加入 load balancer
```

`thumbd` 最後的做法是：啟動時預先配置並觸碰每個 worker 的影像緩衝區，並在 health check 通過前先處理幾張內建的測試圖片。重啟後前幾百個請求的延遲就恢復正常了。

### TLB 與 huge page

當程式隨機存取非常大的資料集（例如幾十 GB 的資料庫 buffer pool 或 in-memory cache），TLB 只能覆蓋其中很小一部分：假設 TLB 有 1,536 個 entry、page 4 KiB，總共只能涵蓋 6 MiB。超出這個範圍的存取幾乎每次都 TLB miss，要走四層 page walk。

**Huge page**（大頁）把 page 改成 2 MiB，同樣 1,536 個 entry 可以涵蓋 3 GiB，TLB miss 大幅減少。這是 PostgreSQL、Oracle、JVM 等系統常建議開啟 huge page 的原因。Linux 有兩種方式：

| 方式 | 怎麼用 | 優點 | 風險 |
|---|---|---|---|
| 明確配置的 huge page（hugetlbfs） | 開機或執行時預留，程式用 `MAP_HUGETLB` 或設定檔啟用 | 可預測，不會被拆開 | 預留的記憶體不能給一般程式用 |
| Transparent Huge Pages（THP） | kernel 在 fault 時直接配 2 MiB 頁，或由背景執行緒把連續的 4 KiB 頁合併成 2 MiB | 不用改程式 | 合併與記憶體壓縮可能造成延遲尖峰，`fork` 後的 COW 也可能變貴；Redis 官方建議關閉，MongoDB 則從 8.0 起改為建議開啟（7.0 以前建議關閉），可見結論取決於軟體與版本 |

判斷要不要用 huge page 的依據是量測：用 `perf stat -e dTLB-load-misses` 看 TLB miss 是否真的是瓶頸，而不是看到「資料庫建議」就開。

## 23.13 常見錯誤與除錯

| 症狀 | 常見原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 「VIRT 好大，是不是 leak？」 | 把位址範圍當成實際使用量 | 看 RSS／PSS 是否隨時間成長；`pmap -x` 看各區域 | 用 RSS／PSS 判斷，VIRT 只用來發現位址空間耗盡 |
| 程式剛啟動時延遲特別高 | 大量 minor fault（第一次觸碰新頁） | 請求前後比較 `min_flt`；`perf stat -e page-faults` | 預先觸碰緩衝區、`MAP_POPULATE`、暖機流量 |
| 延遲偶爾暴增到數十毫秒 | major fault：記憶體不足在換頁，或 mmap 的檔案不在 page cache | `maj_flt` 持續增加；`vmstat` 的 `si`／`so` 欄 | 增加記憶體、減少使用量、對關鍵記憶體 `mlock` |
| Segmentation fault | 存取未映射的位址（NULL、已釋放、越界） | core dump ＋ `gdb` 的 `bt` 與 `info proc mappings` | 修正指標錯誤；開 ASan 重現（第 26 章） |
| 寫入時 segfault，但讀取正常 | 寫入唯讀頁（例如改字串常數） | gdb 中看該位址屬於哪個區域與權限 | 不要寫入 `.rodata`；需要可寫時複製一份 |
| 大資料集隨機存取很慢、CPU 卻不忙 | TLB miss 頻繁 | `perf stat -e dTLB-load-misses,dTLB-loads` | 改善存取的 locality，或評估 huge page |

> [!tip] 在 gdb 裡看位址屬於哪裡
> 程式 segfault 後，在 gdb 中用 `info proc mappings`（Linux）可以列出 process 的所有映射區域，再對照當機的位址：它是落在 heap、某個 library、stack，還是根本不在任何區域。這通常是判斷「NULL 指標」「use-after-free」還是「stack overflow」的第一步。

## 23.14 動手練習

1. **手算**：在 23.9 節的迷你系統中，翻譯 `0x13A0` 與 `0x40FF`。寫出 VPN、VPO、TLBI、TLBT，判斷在 23.11 節 trace 結束後它們是 TLB hit 還是 miss，並算出實體位址。（驗證方法：把位址加進程式一的 `trace` 陣列重新執行。）
2. **手算**：一個系統使用 39-bit 虛擬位址、4 KiB page、8-byte PTE，每張 page table 剛好一個 page。需要幾層 page table？每層的 VPN 段是幾個 bit？（提示：先算每張表有幾個 entry。答案是三層，每層 9 bits，這正是 RISC-V Sv39 的設計。）
3. 修改程式一，把 TLB 改成 direct-mapped（`TLB_WAYS` 為 1、`TLB_SETS` 為 8），再設計一個存取序列讓兩個不同的頁不斷互相把對方擠出 TLB。觀察 hit 次數的變化，並解釋這和第 16 章的 conflict miss 有什麼關係。
4. 修改程式二，把寫入改成「每隔 page 大小的一半寫一次」。minor fault 次數會變嗎？為什麼？
5. 在 Linux 上執行 `cat /proc/self/maps` 與 `cat /proc/self/smaps_rollup`，找出 stack、heap 與 libc 的位址範圍，並比較 `Rss` 與 `Pss`。
6. 挑一個你工作上的服務，記錄它的 VSZ、RSS、`min_flt`、`maj_flt`。重啟它，並在前 100 個請求前後再記錄一次，判斷它是否有「第一次比較慢」的問題。

## 本章重點整理

- 虛擬記憶體讓每個 process 擁有專屬、配置一致的位址空間，同時扮演三個角色：把 DRAM 當作磁碟的快取、簡化記憶體管理、提供保護與隔離。
- 位址以 page 為單位翻譯：虛擬位址拆成 VPN 與 VPO，翻譯只把 VPN 換成 PPN，頁內位移原封不動。
- 每個 process 有自己的 page table，PTE 記錄 valid bit、PPN 與權限；CPU 的 MMU 在每次存取記憶體時查表，page table 起點存在 `CR3` 這類暫存器中，context switch 時切換。
- PTE 有效且權限允許是 page hit；PTE 無效是 page fault，交給 kernel 處理；違反權限或位址不合法時，kernel 送出 SIGSEGV。
- 大多數 page fault 是正常的 demand paging；minor fault 不需要磁碟，major fault 需要磁碟，後者才真正昂貴。
- 從快取的角度看，虛擬記憶體使用大區塊、fully associative 放置、軟體決定替換、只能 write-back，因為 miss 的代價極大。
- TLB 快取最近的 VPN → PPN 翻譯，讓大多數存取不必額外讀記憶體；TLB miss 由硬體查 page table，不等於 page fault。
- 單層 page table 在 48-bit 位址、4 KiB page 下需要 512 GiB；x86-64 用四層 page table，只為實際使用的區域配置表。
- 多層 page table 的代價是 TLB miss 時要讀多次記憶體，因此 TLB 命中率對效能很重要。
- VIRT／VSZ 是位址範圍，RSS 是實際在實體記憶體的頁，PSS 把共享頁分攤；判斷 leak 要看 RSS 或 PSS 是否持續成長。
- 服務重啟後「第一次比較慢」常常是大量 minor fault，可以用預先觸碰、`MAP_POPULATE` 或暖機流量處理。
- PTE 的權限位元（可寫、user／kernel、不可執行）讓 MMU 在每次存取時檢查保護，W^X 原則讓可寫的頁不能執行。
- 大資料集隨機存取時 TLB 可能成為瓶頸，huge page 能擴大 TLB 覆蓋範圍，但要先量測再決定。

## 延伸問答

> [!question]- Q1. 為什麼 TLB miss 不等於 page fault？兩者的代價差多少？
> TLB 只是翻譯結果的快取。TLB miss 表示「最近沒查過這一頁」，x86-64 與 ARM 的 MMU 會自己去記憶體中的 page table 查，整個過程由硬體完成，作業系統完全不知道，代價大約是數十到數百個 CPU cycle（取決於 page table 的各層是否在 cache 裡）。
>
> Page fault 則是查到的 PTE 無效或權限不允許，硬體無法完成翻譯，必須觸發 exception 進入 kernel。即使是不需要磁碟的 minor fault，也要經過 kernel 的處理流程，代價通常是數百 ns 到數 µs；需要讀磁碟的 major fault 更是數十 µs 到數 ms。所以兩者可以差上好幾個數量級。

> [!question]- Q2. 一個 process 的 VIRT 是 30 GB，但機器只有 16 GB 記憶體，這怎麼可能？
> VIRT 計算的是 process 所有合法虛擬位址範圍的總和，不是實際佔用的實體記憶體。作業系統在 `mmap` 或配置 thread stack 時，只是在 process 的記錄中標記「這段範圍合法」，並不會立刻分配實體頁；只有程式真的寫入某一頁時，才透過 page fault 分配。
>
> 所以一個 process 可以預留遠超過實體記憶體的位址空間，例如 allocator 一次預留大區塊、每個 thread 預留 8 MiB stack、映射大型檔案。真正需要關心的是 RSS 或 PSS，以及系統整體是否開始大量 major fault。

> [!question]- Q3. 手算題：64-bit 系統若真的使用全部 64 bits 虛擬位址、4 KiB page、8-byte PTE，每張表一個 page，需要幾層 page table？
> 每張表 4 KiB ÷ 8 bytes = 512 個 entry，所以每層可以處理 9 bits 的 VPN。64 bits 減去 12 bits 的 page offset，剩 52 bits 的 VPN。52 ÷ 9 ≈ 5.8，需要 6 層（最上層只用到部分 bits）。
>
> 這說明了為什麼 x86-64 實際只用 48 bits（四層）或 57 bits（五層）：每多一層，TLB miss 時就要多讀一次記憶體。在目前的記憶體容量下，48 bits（256 TiB）或 57 bits（128 PiB）的位址空間已經足夠，沒必要付出更多層的代價。

> [!question]- Q4. 為什麼虛擬記憶體的 page 大小是 4 KiB，而不是像 CPU cache 一樣用 64 bytes？
> 因為兩者面對的 miss 代價差太多。虛擬記憶體最初是把 DRAM 當作磁碟的快取，而磁碟（尤其是 HDD）第一次存取的延遲非常高，但之後連續讀取相對快。一次多搬一點資料，可以把昂貴的第一次存取分攤到更多 bytes 上。
>
> 另一個原因是 page table 的大小：page 越小，需要的 PTE 越多，表越大、TLB 能涵蓋的範圍也越小。反過來，page 太大會造成浪費（只用到一點點也要佔整頁）。4 KiB 是早期折衷的結果；現代系統則提供 2 MiB、1 GiB 的 huge page 給需要的場景，Apple Silicon 也改用 16 KiB 作為預設。

> [!question]- Q5. 你在 production 看到一個服務的 `maj_flt` 每秒增加幾百次，同時延遲變高。你會怎麼判斷？
> major fault 表示資料要從磁碟讀進記憶體。常見的來源有兩種：一是系統記憶體不足，作業系統把匿名記憶體換到 swap，之後又要換回來；二是服務用 `mmap` 存取檔案，而這些檔案頁不在 page cache 中（例如剛重啟、或被其他程式擠出 cache）。
>
> 可以先用 `vmstat 1` 看 `si`／`so` 欄位判斷是否在 swap，用 `free` 看可用記憶體；再用 `pmap -x` 或 `/proc/PID/smaps` 看是哪些區域在增長。若是 swap，要減少系統的記憶體壓力（調整服務的記憶體上限、移走其他程式、加記憶體）；若是 mmap 的檔案，可以考慮預先載入（`MAP_POPULATE`、`madvise(MADV_WILLNEED)`）或增加記憶體讓檔案留在 page cache。

> [!question]- Q6. 兩個 process 都存取虛擬位址 `0x4000`，會讀到同一份資料嗎？
> 通常不會。每個 process 有自己的 page table，同一個虛擬位址會被翻譯到不同的實體頁，所以兩者看到的是各自的資料，這正是虛擬記憶體提供隔離的方式。
>
> 但作業系統也可以刻意讓兩個 process 的 PTE 指向同一個實體頁，達到共享：例如兩個 process 都載入同一個 libc，它的程式碼頁在實體記憶體中只有一份；或兩個 process 用 `mmap` 以 `MAP_SHARED` 映射同一個檔案、或建立共享記憶體。第 24 章會詳細介紹這些機制，以及 fork 之後的 copy-on-write。

> [!question]- Q7. 程式寫入一個字串常數 `char *s = "hello"; s[0] = 'H';` 為什麼會 segfault？
> 字串常數被編譯器放在 `.rodata`（唯讀資料）區段，載入時作業系統把這些頁的 PTE 設為「可讀、不可寫」。執行 `s[0] = 'H'` 時，MMU 查到 PTE 有效，但權限不允許寫入，觸發 protection fault；kernel 判斷這不是可以修復的情況，於是送出 SIGSEGV。
>
> 這個例子說明 segfault 不一定是「位址不存在」，也可能是「位址存在但權限不對」。修法是改用可寫的陣列：在函式內寫 `char s[] = "hello";`，會在 stack 上建立一份可修改的副本（若寫在函式外，副本則放在可寫的 `.data`）。

> [!question]- Q8. 面試題：解釋一下 context switch 對 TLB 有什麼影響？
> 每個 process 的虛擬位址對應不同的實體頁，切換到另一個 process 時，TLB 裡舊 process 的翻譯結果就不再適用。最簡單的做法是 context switch 時清空 TLB（flush），但這會讓新 process 一開始大量 TLB miss，降低效能。
>
> 現代處理器提供 tag 機制來避免完全清空：x86-64 的 PCID（process-context identifier）與 ARM 的 ASID 會在每個 TLB entry 上標記它屬於哪個位址空間，切換時不必清空，只比對目前 process 的 entry。此外，多核心系統修改 page table 時，還需要通知其他核心清掉相關 entry（TLB shootdown），這是頻繁 `munmap` 或改權限時會出現的額外成本。回答時能提到這些，代表你理解 TLB 不只是快取，也牽涉到多核心的一致性。
