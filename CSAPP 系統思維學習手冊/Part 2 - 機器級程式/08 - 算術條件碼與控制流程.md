# 第 8 章　算術、條件碼與控制流程

> [!abstract] 本章地圖
> **核心問題**：CPU 沒有 `if`、`while`、`switch`，只有算術指令和「跳到某個位址」。C 的控制流程是怎麼用這些東西拼出來的？為什麼同一段程式，換一組輸入資料就慢了十倍？
>
> **你會學到**：
> - 讀懂算術與邏輯指令，以及 `imul`、`cqto`、`idiv` 這些有隱含運算元的乘除法
> - 手算 CF、ZF、SF、OF 四個 condition codes，並推導出 `jl`、`jb` 等條件為什麼這樣定義
> - 把組合語言中的 `cmp`／`test`、`set`、條件跳躍還原成 C 的 `if`、迴圈與 `switch`
> - 判斷編譯器什麼時候會用 conditional move，什麼時候不能用
> - 量測並解釋 branch misprediction 的代價，知道什麼時候值得改寫成無分支的程式
>
> **前置知識**：第 4、5 章（二補數、有號與無號、溢位）、第 7 章（暫存器、addressing mode、`mov` 與 `lea`）
>
> **對應 CS:APP 3e**：第 3 章 3.5–3.6 節

## 8.1 故事：夜景照片慢了十倍

產品經理 Lisa 在週會上丟出一張圖表：拾光相簿新上線的「高光預覽」功能，處理一般白天照片時，每張只要十幾毫秒；但只要是夜景照片，同樣解析度，卻要一百多毫秒。「使用者上傳夜景照片的比例越來越高，這個功能的 p99 延遲已經超標了。」

小安先懷疑是 JPEG 解碼，但量測後發現解碼時間差不多。真正變慢的是一個很簡單的迴圈：把亮度大於等於 128 的像素挑出來，存到另一個緩衝區給後面的光暈效果使用。

```c
long keep_bright(const uint8_t *px, uint8_t *out, long n) {
    long k = 0;
    for (long i = 0; i < n; i++)
        if (px[i] >= 128)
            out[k++] = px[i];
    return k;
}
```

小安困惑地說：「像素數量一樣，迴圈次數一樣，每次做的事也一樣，為什麼夜景會慢這麼多？」老周把兩張照片的直方圖拉出來：白天照片的天空、牆面是大片連續的亮區與暗區；夜景照片則滿是零碎的燈光、招牌與反光，再加上高 ISO 的雜訊，亮暗交錯得非常細碎，相鄰像素一下大於 128、一下小於 128，幾乎沒有規律。

「CPU 在執行到 `if` 之前，就已經先猜好要往哪邊走了。」老周說，「白天的照片好猜，夜景的雜訊讓它每兩次就猜錯一次，每猜錯一次都要把做到一半的工作丟掉重來。」

要理解這句話，得先知道 `if` 在機器裡長什麼樣子：比較是怎麼做的、結果存在哪裡、「跳」到底是什麼。這就是本章的內容。8.11 節會回到這個問題，8.12 節會實際量到這十倍的差距。

## 8.2 算術與邏輯指令

第 7 章看過 `mov` 和 `lea`。真正做計算的指令也很直觀，大多數是**兩個 operand**：`addq %rsi, %rdi` 表示 `rdi = rdi + rsi`，目的同時也是其中一個來源。這和 C 的 `a += b` 很像，而不是 `c = a + b`。

| 指令 | 效果 | 說明 |
|---|---|---|
| `inc D`、`dec D` | D = D + 1、D − 1 | |
| `neg D` | D = −D | 二補數取負 |
| `not D` | D = ~D | 逐位元反相 |
| `add S, D` | D = D + S | |
| `sub S, D` | D = D − S | 注意順序：是 D 減 S |
| `imul S, D` | D = D × S | 兩運算元形式，只保留低位 |
| `imul $Imm, S, D` | D = S × Imm | 三運算元形式，乘一個常數 |
| `xor S, D`、`or S, D`、`and S, D` | D = D ^ S、D \| S、D & S | |
| `sal k, D`、`shl k, D` | D = D << k | 左移，兩者相同 |
| `sar k, D` | D = D >> k（算術） | 補符號位元，用於有號數 |
| `shr k, D` | D = D >> k（邏輯） | 補 0，用於無號數 |

和 `mov` 一樣，每條指令都有 `b`／`w`／`l`／`q` 四種大小。shift 的位移量 k 可以是立即數，或放在 `%cl`；位移量只看低 6 位元（64-bit 運算）或低 5 位元（32-bit 以下），所以 C 中位移超過寬度是 undefined behavior（第 3 章），在硬體層面就是「結果不一定是你以為的」。

一個值得注意的細節：同一條 `add` 指令同時處理有號與無號加法。第 5 章講過，二補數加法和無號加法在位元層面完全相同，所以 CPU 不需要兩種加法器，差別只在於事後怎麼解讀結果，以及要看哪一個 condition code（8.4 節）。右移則不同，`sar` 和 `shr` 的結果不一樣，所以編譯器必須依型別選擇。

用 `thumbd` 的兩個像素函式看編譯器怎麼使用這些指令：

```c
#include <stdint.h>
int luma(int r, int g, int b) {               /* RGB 轉亮度的整數近似 */
    return (77 * r + 150 * g + 29 * b) >> 8;
}
uint32_t pack_rgb(uint32_t r, uint32_t g, uint32_t b) {
    return (r << 16) | (g << 8) | b;
}
long neg_not(long x) { return ~(-x); }
```

以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生（刪去編譯器的 `# kill:` 註解）：

```asm
luma:
	imull	$77, %edi, %eax
	imull	$150, %esi, %ecx
	addl	%eax, %ecx
	leal	(%rdx,%rdx,8), %eax
	leal	(%rax,%rax,2), %eax
	addl	%edx, %edx
	addl	%edx, %eax
	addl	%ecx, %eax
	sarl	$8, %eax
	retq
pack_rgb:
	movl	%esi, %eax
	shll	$16, %edi
	shll	$8, %eax
	orl	%edi, %eax
	orl	%edx, %eax
	retq
neg_not:
	leaq	-1(%rdi), %rax
	retq
```

`luma` 的 `77 * r` 和 `150 * g` 用三運算元的 `imull`；`29 * b` 卻被拆成 `lea` 與加法：`b + 8b = 9b`，`9b + 2 × 9b = 27b`，再加上 `2b`，得到 `29b`。最後的 `sarl $8` 是算術右移，因為結果是有號的 `int`。`pack_rgb` 的參數都是 `uint32_t`，就是單純的左移與 OR。

`neg_not` 最有意思：`~(-x)` 被編譯成 `x − 1`。這是一個二補數恆等式：對任何 y，`~y = −y − 1`，所以 `~(−x) = x − 1`。編譯器知道這些代數規則，會把你寫的運算換成更便宜的等價運算。這也提醒我們：讀組合語言時不要期待和原始碼一模一樣，要用代數去驗證兩者等價。

## 8.3 特殊的乘法與除法

兩個 64-bit 數相乘，完整的結果需要 128 bits。兩運算元的 `imulq` 只保留低 64 bits（這就是 C 的 `long * long`，溢位時位元被截掉）。需要完整結果時，x86-64 提供**單運算元**的乘法：

- `mulq S`（無號）、`imulq S`（有號）：計算 `%rax × S`，結果的高 64 bits 放 `%rdx`、低 64 bits 放 `%rax`。寫成 `R[%rdx]:R[%rax]`，冒號表示兩個暫存器拼成一個 128-bit 值。

除法只有單運算元形式，而且被除數一定是 128-bit 的 `%rdx:%rax`：

- `idivq S`（有號）、`divq S`（無號）：商放 `%rax`，餘數放 `%rdx`。
- `cqto`（Intel 稱為 `cqo`）：把 `%rax` sign-extend 到 `%rdx:%rax`，也就是把 `%rax` 的最高位元複製到 `%rdx` 的每一個位元。有號除法前一定會看到它。

```text
 有號除法 a / b、a % b（64-bit）

   %rdx               %rax                     %rsi
 ┌────────────────┬────────────────┐        ┌──────────┐
 │ a 的符號延伸   │       a        │   ÷    │    b     │
 └────────────────┴────────────────┘        └──────────┘
   ▲ cqto 填入（全 0 或全 1）
                         │ idivq %rsi
                         ▼
   %rdx = a % b（餘數）    %rax = a / b（商）
```

讀這張圖：被除數是 128 bits，但 C 的 `long` 只有 64 bits，所以先用 `cqto` 把 `a` 延伸成 128 bits，再除。一條 `idivq` 同時產生商與餘數，所以編譯器在同一個函式裡同時需要 `a / b` 和 `a % b` 時，只會做一次除法。

```c
long div_s(long a, long b)          { return a / b; }
long rem_s(long a, long b)          { return a % b; }
unsigned long div_u(unsigned long a, unsigned long b) { return a / b; }
unsigned __int128 mul_full(unsigned long a, unsigned long b) {
    return (unsigned __int128)a * b;
}
```

以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 編譯，四個函式的指令：

```asm
div_s:
	movq	%rdi, %rax
	cqto
	idivq	%rsi
	retq
rem_s:
	movq	%rdi, %rax
	cqto
	idivq	%rsi
	movq	%rdx, %rax
	retq
div_u:
	movq	%rdi, %rax
	xorl	%edx, %edx
	divq	%rsi
	retq
mul_full:
	movq	%rsi, %rax
	mulq	%rdi
	retq
```

`div_s` 和 `rem_s` 只差最後一行：要商就回傳 `%rax`，要餘數就把 `%rdx` 搬到 `%rax`。`div_u` 是無號除法，高 64 bits 應該是 0，所以用 `xorl %edx, %edx` 清零而不是 `cqto`。`mul_full` 回傳 128-bit 值，依呼叫慣例放在 `%rdx:%rax`，`mulq` 的結果剛好就在那裡。

> [!warning] 除法會讓程式當掉
> 除以 0 時，`idiv`／`div` 會觸發硬體 exception（第 20 章），Linux 會送出 `SIGFPE` 讓程式結束，即使是整數運算也是這個 signal。另一個比較少人知道的情況是 `LONG_MIN / -1`：數學上的答案是 2^63，超出 `long` 的範圍，x86-64 同樣會觸發 exception。在 C 裡這兩者都是 undefined behavior，處理外部輸入的除數時一定要先檢查。

### 除以常數：編譯器避開除法指令

整數除法很慢：在 x86-64 處理器上，64-bit 除法的延遲從較新處理器的十幾個 cycle 到較舊處理器的數十個 cycle 不等，加法只要 1 個 cycle（確切數字依微架構而定）。所以除數是常數時，編譯器會想辦法完全不用 `div`。

**除以 2 的冪**：無號數直接 `shr`。有號數則要小心：C 的除法向零捨入，但算術右移是向負無限大捨入。第 5 章講過解法是對負數先加上 bias（2^k − 1）。`long div8(long x) { return x / 8; }` 以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生：

```asm
div8:
	leaq	7(%rdi), %rax
	testq	%rdi, %rdi
	cmovnsq	%rdi, %rax
	sarq	$3, %rax
	retq
```

先算 `x + 7`；如果 x 不是負數（`cmovns`，8.8 節會解釋），就改用原本的 x；最後算術右移 3 位。手算 x = −9：`−9 + 7 = −2`，`−2 >> 3 = −1`，正確（−9 ÷ 8 = −1.125，向零捨入是 −1）。如果沒有 bias，`−9 >> 3 = −2`，就錯了。

**除以其他常數**：編譯器把除法換成「乘以一個魔術數，再右移」。以 `unsigned div10(unsigned x) { return x / 10; }` 為例，同樣用 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生（刪去 `# kill:` 註解）：

```asm
div10:
	movl	%edi, %ecx
	movl	$3435973837, %eax               # imm = 0xCCCCCCCD
	imulq	%rcx, %rax
	shrq	$35, %rax
	retq
```

這段程式碼計算 `(x × 3435973837) >> 35`。魔術數的來源是 2^35 ÷ 10 = 3435973836.8，向上取整得到 3435973837，所以這個運算近似於 `x × (2^35 / 10) / 2^35 = x / 10`。手算驗證：

| x | x × 3435973837 | 右移 35 位（÷ 34359738368） | x / 10 |
|---|---|---|---|
| 99 | 340161409863 | 9.9 → 9 | 9 |
| 12345 | 42417097017765 | 1234.5 → 1234 | 1234 |
| 4294967295 | 14757395256390660915 | 429496729.5 → 429496729 | 429496729 |

編譯器會選擇夠大的位移量，保證對所有 32-bit 輸入都得到精確結果，而不只是近似。實務上的啟示是：看到一個奇怪的大常數接著 `imul` 和 `shr`，通常就是除以常數；而除數在執行時才知道的除法（例如 `x % table_size`）才會真的用到昂貴的 `div`，這也是很多 hash table 偏好用 2 的冪當大小、改用位元遮罩的原因之一。

## 8.4 Condition codes：上一個運算留下的痕跡

到目前為止，指令都是一條接著一條執行。要做 `if`，CPU 需要「根據某個條件決定下一條指令是誰」。x86-64 的做法是：算術指令在計算結果的同時，順便在一個特殊暫存器（`RFLAGS`）中設定幾個 1-bit 的旗標，叫 **condition codes**（條件碼）。後續的指令可以讀這些旗標，決定要不要跳躍。

最重要的四個：

| 旗標 | 名稱 | 什麼時候是 1 | 對誰有意義 |
|---|---|---|---|
| CF | carry flag（進位） | 最高位元產生進位（加法），或需要借位（減法） | 無號數：結果超出範圍 |
| ZF | zero flag（零） | 結果是 0 | 兩者都適用 |
| SF | sign flag（符號） | 結果的最高位元是 1 | 有號數：結果是負的 |
| OF | overflow flag（溢位） | 有號運算溢位：兩個同號數相加得到異號結果 | 有號數：結果超出範圍 |

同一個運算會同時設定這四個旗標，CPU 不知道你把數字當成有號還是無號，所以兩種解讀需要的資訊都準備好。用 8-bit 加法手算四個例子：

| 運算 | 二進位 | 結果 | CF | ZF | SF | OF | 解讀 |
|---|---|---|---|---|---|---|---|
| `0x7F + 0x01` | 0111 1111 + 0000 0001 | `0x80` | 0 | 0 | 1 | 1 | 有號：127 + 1 溢位成 −128；無號：127 + 1 = 128 正確 |
| `0xFF + 0x01` | 1111 1111 + 0000 0001 | `0x00` | 1 | 1 | 0 | 0 | 無號：255 + 1 溢位成 0；有號：−1 + 1 = 0 正確 |
| `0x80 + 0x80` | 1000 0000 + 1000 0000 | `0x00` | 1 | 1 | 0 | 1 | 兩種解讀都溢位：128 + 128、−128 + −128 |
| `0x05 + 0xFD` | 0000 0101 + 1111 1101 | `0x02` | 1 | 0 | 0 | 0 | 無號：5 + 253 溢位；有號：5 + (−3) = 2 正確 |

逐列確認 OF 的判斷規則：第一列兩個正數相加得到負數，OF = 1；第四列一正一負相加，不可能有號溢位，OF = 0，即使 CF = 1。CF 和 OF 是互相獨立的：一個描述無號解讀，一個描述有號解讀。

哪些指令會設定 condition codes？

- 算術與邏輯指令（`add`、`sub`、`and`、`xor`、`neg` 等）都會設定。`imul` 是例外之一：它只用 CF 與 OF 表示「乘積是否超出目的的寬度」，ZF 與 SF 在 Intel 手冊中標為未定義，不能拿來判斷結果。
- 邏輯運算（`and`、`or`、`xor`）把 CF 和 OF 設為 0。
- `inc` 和 `dec` 設定 ZF、SF、OF，但**不改 CF**（這是沿襲自 8086 的設計，常見的解釋是讓多精度加法的迴圈可以用 `inc`／`dec` 當計數器而不破壞進位）。
- shift 把 CF 設為最後一個被移出的位元；OF 只在位移量為 1 時有定義。
- `mov`、`lea`、`push`、`pop` **完全不改** condition codes。

最後一點很重要，因為編譯器會利用它：在比較指令和跳躍指令之間插入 `mov`，condition codes 不受影響。8.9 節會看到實際的例子。

## 8.5 讀取 condition codes：`cmp`、`test` 與 `set`

用加減法設定旗標有個問題：會改掉目的暫存器。所以 x86-64 提供兩條「只設旗標、不存結果」的指令：

- `cmp S, D`：計算 `D − S`，只設定 condition codes，結果丟掉。注意順序：`cmpq %rsi, %rdi` 比較的是 `rdi` 相對於 `rsi`，也就是 `rdi − rsi`。
- `test S, D`：計算 `D & S`，只設定 condition codes。最常見的用法是 `testq %rax, %rax`，用來檢查 `%rax` 是零、正數還是負數。

讀出旗標的第一種方式是 `set` 指令：根據旗標的組合，把一個 byte 暫存器設為 0 或 1。這正是 C 的比較運算子（`a < b` 的值是 0 或 1）需要的東西：

```c
int less_s(long a, long b)                   { return a < b; }
int less_u(unsigned long a, unsigned long b) { return a < b; }
int is_zero(long x)                          { return x == 0; }
```

三個函式以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生：

```asm
less_s:
	xorl	%eax, %eax
	cmpq	%rsi, %rdi
	setl	%al
	retq
less_u:
	xorl	%eax, %eax
	cmpq	%rsi, %rdi
	setb	%al
	retq
is_zero:
	xorl	%eax, %eax
	testq	%rdi, %rdi
	sete	%al
	retq
```

三個函式的結構相同：先把 `%eax` 清零（`set` 只寫 1 個 byte，高位元要先清乾淨），再比較，最後把旗標組合寫進 `%al`。`less_s` 和 `less_u` 的 `cmpq` 完全一樣，唯一的差別是 `setl`（less，有號）與 `setb`（below，無號）。CPU 用同一個減法同時準備了兩種答案，由編譯器根據 C 的型別挑一個。另外注意清零的 `xorl` 放在 `cmpq` **之前**，因為 `xor` 會改掉 condition codes。

### 為什麼「有號小於」是 SF ^ OF

`set` 與條件跳躍共用同一套條件。下表列出常用的條件，以及它們讀取的旗標：

| 後綴 | 同義名 | 條件（看旗標） | 在 `cmp S, D` 後的意義 |
|---|---|---|---|
| `e` | `z` | ZF | D == S |
| `ne` | `nz` | ~ZF | D != S |
| `s` | | SF | 結果為負 |
| `ns` | | ~SF | 結果非負 |
| `l` | `nge` | SF ^ OF | D < S（有號） |
| `le` | `ng` | (SF ^ OF) \| ZF | D <= S（有號） |
| `g` | `nle` | ~(SF ^ OF) & ~ZF | D > S（有號） |
| `ge` | `nl` | ~(SF ^ OF) | D >= S（有號） |
| `b` | `nae`、`c` | CF | D < S（無號） |
| `be` | `na` | CF \| ZF | D <= S（無號） |
| `a` | `nbe` | ~CF & ~ZF | D > S（無號） |
| `ae` | `nb`、`nc` | ~CF | D >= S（無號） |

無號的「below」很好理解：`D − S` 需要借位，表示 D 比 S 小，這正是 CF。有號的「less」為什麼是 `SF ^ OF`？分兩種情況推導 `t = D − S`：

1. **沒有溢位**（OF = 0）：t 就是真正的差，`D < S` 等價於 t 是負的，也就是 SF = 1。
2. **有溢位**（OF = 1）：真正的差超出範圍，t 的符號和真正的差相反。這時 `D < S` 等價於 t 看起來是正的，也就是 SF = 0。

把兩種情況合起來：`D < S` 恰好在 SF 和 OF 不同時成立，也就是 `SF ^ OF = 1`。用一個溢位的例子驗證：8-bit 的 D = −128（`0x80`）、S = 1，`t = 0x80 − 0x01 = 0x7F`，看起來是正數（SF = 0），但這是溢位（OF = 1），所以 `SF ^ OF = 1`，判斷為「小於」，正確。8.12 節的程式會把這些情況全部跑一遍。

> [!warning] 常見誤解
> 「`cmp` 會分有號和無號。」不會。`cmp` 只做減法並設定所有旗標，有號或無號是由後面的 `set`／`j`／`cmov` 指令決定的。所以讀組合語言時，看到 `jl`、`jg` 表示原始碼是有號比較，看到 `jb`、`ja` 表示是無號比較，這是反推型別的另一條重要線索。

## 8.6 跳躍：改變下一條指令

讀出旗標的第二種方式，也是控制流程的核心，是**跳躍指令**（jump）。正常情況下，CPU 執行完一條指令後，`%rip` 指向緊接著的下一條；跳躍指令則把 `%rip` 改成別的位址。

- `jmp Label`：**無條件跳躍**，直接跳到標籤。
- `jmp *%rax`、`jmp *(%rax)`：**間接跳躍**（indirect jump），目標位址在暫存器或記憶體裡，執行時才知道。8.10 節的 `switch` 會用到。
- `je`、`jne`、`jl`、`jb`……：**條件跳躍**，條件和上一節的表相同；條件成立就跳，不成立就繼續執行下一條。

### 跳躍目標怎麼編碼

組合語言中寫的是標籤，但機器碼裡存的是什麼？大多數跳躍用 **PC-relative**（相對於 PC）編碼：指令中存的是「目標位址減去**下一條指令**的位址」，一個有號的位移量。用 8.9 節 `count_bright` 函式的 `objdump -d` 輸出（`clang -target x86_64-linux-gnu -O1 -c` 產生的目的檔，`...` 處省略了中間幾行）實際驗證：

```text
0000000000000060 <count_bright>:
      60: 48 85 f6                      testq   %rsi, %rsi
      63: 7e 26                         jle     0x8b <count_bright+0x2b>
      65: 31 c9                         xorl    %ecx, %ecx
      67: 31 c0                         xorl    %eax, %eax
      69: 0f 1f 80 00 00 00 00          nopl    (%rax)
      70: 44 0f b6 04 0f                movzbl  (%rdi,%rcx), %r8d
      ...
      85: 48 39 ce                      cmpq    %rcx, %rsi
      88: 75 e6                         jne     0x70 <count_bright+0x10>
      8a: c3                            retq
      8b: 31 c0                         xorl    %eax, %eax
```

兩個跳躍逐一手算：

```text
 jle（位址 0x63）：機器碼 7e 26
   7e = 「jle，1-byte 位移」   26 = +38
   下一條指令位址 0x65 + 0x26 = 0x8b   ✓（往高位址跳到函式尾端）

 jne（位址 0x88）：機器碼 75 e6
   75 = 「jne，1-byte 位移」   e6 = 二補數的 −26
   下一條指令位址 0x8a − 0x1a = 0x70   ✓（往回跳到迴圈開頭）
```

第二個例子是迴圈的「回頭跳」，位移是負數，用二補數表示（第 4 章）。位移量只有 1 byte 時能跳 −128 到 +127；更遠的目標會用 4-byte 位移的長格式。PC-relative 編碼的好處是程式碼搬到任何位址都不必修改，這是 shared library 能被載入到任意位置的基礎之一（第 19 章）。

順帶一提，位址 `0x69` 的 `nopl (%rax)` 是一條什麼都不做的 7-byte 指令，編譯器用它把迴圈開頭（`0x70`）對齊到 16 bytes 的邊界，讓 CPU 取指令比較有效率。看到 `nop` 不用緊張，它不是 bug。

## 8.7 `if` 的翻譯

有了比較和條件跳躍，`if` 的翻譯就很直接。CS:APP 用一個有用的技巧來理解它：先把 C 改寫成只有 `if (...) goto` 的形式，這種形式和組合語言幾乎一對一。

```text
 C 的 if-else                    goto 形式                     組合語言的形狀
 ──────────────                  ──────────                    ──────────────
 if (test)                       t = test;                         cmp ...
     then-part;                  if (!t) goto false;               j(相反條件) .Lfalse
 else                            then-part;                        （then-part）
     else-part;                  goto done;                        jmp .Ldone
                               false:                          .Lfalse:
                                 else-part;                        （else-part）
                               done:                           .Ldone:
```

重點在中間那一欄的第二行：組合語言通常是「條件**不**成立就跳過 then-part」，所以跳躍指令的條件和 C 的條件相反。讀組合語言時看到 `jl .L2`，要想成「如果小於，就跳過下面這段」，下面那段對應的是 C 的 `if (x >= ...)`。

看一個 `thumbd` 的例子：把像素值截斷到 255，並統計被截斷的次數。

```c
long clipped_count;   /* 統計被截斷的像素數 */

int clamp_u8_counted(int v) {
    if (v > 255) {
        clipped_count++;
        return 255;
    }
    return v;
}
```

以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生的結果，只有一個條件跳躍：

```asm
clamp_u8_counted:
	movl	%edi, %eax
	cmpl	$256, %edi
	jl	.LBB1_2
	incq	clipped_count(%rip)
	movl	$255, %eax
.LBB1_2:
	retq
```

編譯器先假設答案是 `v`（放進 `%eax`），然後比較 `v` 和 256：如果 `v < 256`，跳到 `.LBB1_2` 直接返回。否則才執行 then-part：全域變數 `clipped_count` 加一（RIP-relative 定址，第 7 章），把回傳值改成 255。兩個細節值得注意：C 寫的是 `v > 255`，編譯器改成等價的 `!(v < 256)`；而 `jl` 是有號比較，因為 `v` 是 `int`。

### 從組合語言看出型別錯誤

`if` 的翻譯也讓一個常見 bug 現形。`thumbd` 解析上傳檔案時有這段檢查：

```c
#include <stddef.h>
int body_too_short(size_t len, size_t header) {
    return len - header < 0;          /* 想檢查 len 是否小於 header */
}
int body_too_short_fixed(size_t len, size_t header) {
    return len < header;
}
```

兩個函式以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生：

```asm
body_too_short:
	xorl	%eax, %eax
	retq
body_too_short_fixed:
	xorl	%eax, %eax
	cmpq	%rsi, %rdi
	setb	%al
	retq
```

第一個函式的檢查**整個消失了**，只剩「回傳 0」。`size_t` 是無號型別，`len - header` 的結果也是無號的，永遠不會小於 0，編譯器據此把比較刪掉。當 `len < header` 時，減法回繞成一個巨大的正數，後面的程式就會讀超過緩衝區的範圍（第 4、5 章）。修正版直接比較 `len < header`，組合語言裡出現了 `setb`（無號小於），檢查回來了。GCC 的 `-Wextra`（其中包含 `-Wtype-limits`）會對這種「永遠為假」的比較發出警告；clang 即使開了 `-Wall -Wextra` 也不會警告，需要另外加 `-Wtype-limits` 或 `-Wtautological-unsigned-zero-compare`，所以光靠常用的警告組合不一定抓得到。

## 8.8 Conditional move：不跳躍的 `if`

條件跳躍有一個代價（8.11 節會詳細說明）：CPU 必須在知道比較結果之前就猜測要往哪裡走，猜錯就要付出十幾到二十幾個 cycle。所以當 `if` 的兩邊都很簡單時，編譯器會改用另一種做法：**兩邊都算，最後再挑一個**。

挑選的指令叫 **conditional move**（條件搬移）`cmov`：`cmovl S, D` 表示「如果 SF ^ OF 成立，就 `D = S`，否則什麼都不做」。條件後綴和 `set`、`j` 完全相同。

```c
int clamp_u8(int v) {            /* 只算值，沒有副作用 */
    if (v > 255) return 255;
    if (v < 0)   return 0;
    return v;
}
```

`clamp_u8` 以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生，裡面一條跳躍指令都沒有：

```asm
clamp_u8:
	xorl	%ecx, %ecx
	testl	%edi, %edi
	cmovgl	%edi, %ecx
	cmpl	$255, %ecx
	movl	$255, %eax
	cmovll	%ecx, %eax
	retq
```

兩個 `if` 變成了兩個 `cmov`，整個函式沒有任何跳躍：

1. `%ecx = 0`；如果 `v > 0`，改成 `v`。現在 `%ecx = max(v, 0)`。
2. `%eax = 255`；如果 `%ecx < 255`，改成 `%ecx`。現在 `%eax = min(max(v, 0), 255)`。

不論 `v` 是多少，執行的指令都一樣，CPU 不需要猜任何東西。注意第二步：`movl $255, %eax` 夾在 `cmpl` 和 `cmovll` 之間，因為 `mov` 不改 condition codes，這樣排是安全的。

### 什麼時候不能用 `cmov`

「兩邊都算」只有在兩邊都**安全**而且**便宜**的時候才可行。編譯器在下面幾種情況不會用 `cmov`：

| 情況 | 例子 | 為什麼不行 |
|---|---|---|
| 某一邊可能出錯 | `p ? *p : -1` | 先算 `*p` 的話，`p` 是 NULL 時會 segfault |
| 某一邊有副作用 | `clamp_u8_counted` 的 `clipped_count++` | 不能在條件不成立時也去修改全域變數 |
| 某一邊很昂貴 | `x > 0 ? expensive(x) : 0` | 兩邊都算的成本高於猜錯的代價 |
| 結果是寫入而非選值 | `if (c) out[k++] = v;` | `cmov` 只能選擇值放進暫存器，不能「有條件地寫記憶體」 |

第一種情況可以直接驗證：

```c
int read_or_default(const int *p) {
    return p ? *p : -1;
}
```

同樣以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生：

```asm
read_or_default:
	testq	%rdi, %rdi
	je	.LBB2_1
	movl	(%rdi), %eax
	retq
.LBB2_1:
	movl	$-1, %eax
	retq
```

這裡用的是條件跳躍：先檢查 `p` 是否為 0，是的話跳到 `.LBB2_1` 回傳 −1，否則才讀 `*p`。如果改用 `cmov`，`movl (%rdi), %eax` 會在檢查之前執行，NULL 指標就會當機。

> [!note] `cmov` 不一定比較快
> `cmov` 消除了猜錯的風險，但也把「兩邊都算」與「等待比較結果」加進了資料的相依鏈。如果分支本來就很好猜（例如 99% 的像素都不需要截斷），條件跳躍幾乎不花成本，`cmov` 反而可能稍慢。這也是為什麼編譯器有時候不聽你的：它是根據對分支可預測性的估計來選擇的，而它不一定知道你的資料長什麼樣子。

## 8.9 迴圈的翻譯

組合語言沒有迴圈指令，迴圈就是「往回跳」的條件跳躍。C 的三種迴圈會被翻成幾種固定的形狀，認得這些形狀，讀組合語言時就能快速找出迴圈的邊界。

```text
 do-while                    while／for（guarded-do）       while／for（jump-to-middle）
 ────────                    ────────────────────────       ────────────────────────────
 loop:                           if (!test) goto done;          goto test;
   body                        loop:                          loop:
   if (test) goto loop;          body                           body
                                 if (test) goto loop;         test:
                               done:                            if (test) goto loop;
```

`do-while` 最簡單：先執行 body，再判斷要不要回頭。`while` 和 `for` 的差別是「條件可能一開始就不成立」，所以需要額外處理第一次的判斷。有兩種做法：**guarded-do** 先檢查一次，不成立就跳過整個迴圈，之後就是 do-while；**jump-to-middle** 一開始就無條件跳到迴圈尾端的判斷。CS:APP 指出 GCC 在 `-Og` 時常用後者、在 `-O1` 以上常用前者；guarded-do 的好處是編譯器知道迴圈至少執行一次，可以做更多最佳化。`for (init; test; update) body` 則等於 `init; while (test) { body; update; }`。

用三個函式各看一次：

```c
#include <stdint.h>
long digits_do(unsigned long n) {          /* do-while：至少執行一次 */
    long d = 0;
    do {
        d++;
        n /= 10;
    } while (n != 0);
    return d;
}

long gcd_while(long a, long b) {           /* while：條件可能一開始就不成立 */
    while (b != 0) {
        long t = a % b;
        a = b;
        b = t;
    }
    return a;
}

long count_bright(const uint8_t *row, long n, int threshold) {   /* for */
    long count = 0;
    for (long i = 0; i < n; i++)
        if (row[i] > threshold)
            count++;
    return count;
}
```

三個迴圈以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生的結果：

```asm
digits_do:
	xorl	%ecx, %ecx
	movabsq	$-3689348814741910323, %rsi     # imm = 0xCCCCCCCCCCCCCCCD
.LBB0_1:
	incq	%rcx
	movq	%rdi, %rax
	mulq	%rsi
	shrq	$3, %rdx
	cmpq	$9, %rdi
	movq	%rdx, %rdi
	ja	.LBB0_1
	movq	%rcx, %rax
	retq
gcd_while:
	movq	%rdi, %rax
	testq	%rsi, %rsi
	je	.LBB1_4
	movq	%rsi, %rdx
.LBB1_2:
	movq	%rdx, %rcx
	cqto
	idivq	%rcx
	movq	%rcx, %rax
	testq	%rdx, %rdx
	jne	.LBB1_2
	movq	%rcx, %rax
.LBB1_4:
	retq
count_bright:
	testq	%rsi, %rsi
	jle	.LBB2_1
	xorl	%ecx, %ecx
	xorl	%eax, %eax
.LBB2_4:
	movzbl	(%rdi,%rcx), %r8d
	xorl	%r9d, %r9d
	cmpl	%r8d, %edx
	setl	%r9b
	addq	%r9, %rax
	incq	%rcx
	cmpq	%rcx, %rsi
	jne	.LBB2_4
	retq
.LBB2_1:
	xorl	%eax, %eax
	retq
```

找迴圈的方法是：**找往回跳的跳躍**。三個函式各有一個：`ja .LBB0_1`、`jne .LBB1_2`、`jne .LBB2_4`，跳躍目標就是迴圈開頭。

- **`digits_do`** 是 do-while 的形狀，沒有開頭的檢查。`n /= 10` 被換成乘以魔術數 `0xCCCCCCCCCCCCCCCD` 再取 `%rdx` 右移 3 位（8.3 節的技巧，64-bit 版）。迴圈條件 `n != 0` 被巧妙地改寫：與其算完除法再看結果是否為 0，編譯器直接比較「除之前的 n 是否大於 9」（`cmpq $9, %rdi; ja`），兩者等價。中間那條 `movq %rdx, %rdi` 不影響 condition codes，所以可以安全地夾在 `cmpq` 和 `ja` 之間。
- **`gcd_while`** 是 guarded-do：先 `testq %rsi, %rsi; je .LBB1_4`，如果 `b` 一開始就是 0，直接返回 `a`。之後的迴圈用 `cqto` + `idivq` 算餘數，`testq %rdx, %rdx; jne` 判斷新的 `b` 是否為 0。
- **`count_bright`** 也是 guarded-do：`n <= 0` 時直接回傳 0。最有趣的是迴圈裡的 `if` 不見了：`cmpl %r8d, %edx` 比較 `threshold` 和像素值，`setl %r9b` 在 `threshold < row[i]` 時得到 1，再用 `addq` 加到 `count`。`count++` 這種「條件成立就加一」被改寫成「每次都加上比較的結果（0 或 1）」，沒有任何分支。

最後一個例子和 8.1 節的故事有直接關係：同樣是「挑出亮像素」，`count_bright` 只需要計數，編譯器能把它變成無分支的程式碼；`keep_bright` 需要**有條件地寫記憶體**，對應到 8.8 節表格的最後一列，編譯器就做不到了。

## 8.10 `switch` 與 jump table

`switch` 可以翻成一連串的 `if-else`，但當 case 很多而且值很密集時，有更好的方法：**jump table**（跳躍表）。它是一個存在記憶體中的陣列，第 i 個元素是「case i 的程式碼位址」。執行時用 `switch` 的值當索引查表，再做一次間接跳躍，不管有多少個 case，都只要固定幾條指令。

`thumbd` 處理 EXIF orientation 時有一個典型的 `switch`：相機會在照片中記錄拍攝時的方向（1 到 8），縮圖時要依照方向把輸出座標對回原圖：

```c
/* EXIF orientation 1–8：把輸出座標 (x, y) 對回原圖的索引。
 * w、h 是原圖寬高；只示範 x 方向的計算。 */
long src_x(int orientation, long x, long y, long w, long h) {
    switch (orientation) {
    case 1: return x;              /* 正常 */
    case 2: return w - 1 - x;      /* 水平翻轉 */
    case 3: return w - 1 - x;      /* 旋轉 180 度 */
    case 4: return x;              /* 垂直翻轉 */
    case 5: return y;              /* 轉置 */
    case 6: return y;              /* 順時針 90 度 */
    case 7: return h - 1 - y;      /* 反轉置 */
    case 8: return h - 1 - y;      /* 逆時針 90 度 */
    default: return -1;            /* 不合法的值 */
    }
}
```

以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生（保留 `.rodata` 區段中的 jump table）：

```asm

	cmpl	$7, %edi
	ja	.LBB0_5
	movq	%rdx, %rax
	leaq	.LJTI0_0(%rip), %rdx
	movslq	(%rdx,%rdi,4), %rdi
	addq	%rdx, %rdi
	jmpq	*%rdi
.LBB0_2:
	movq	%rsi, %rax
	retq
.LBB0_3:
	notq	%rsi
	addq	%rsi, %rcx
	movq	%rcx, %rax
	retq
.LBB0_4:
	notq	%rax
	addq	%r8, %rax
	retq
.LBB0_5:
	movq	$-1, %rax
.LBB0_6:
	retq
	.section	.rodata,"a",@progbits
.LJTI0_0:
	.long	.LBB0_2-.LJTI0_0
	.long	.LBB0_3-.LJTI0_0
	.long	.LBB0_3-.LJTI0_0
	.long	.LBB0_2-.LJTI0_0
	.long	.LBB0_6-.LJTI0_0
	.long	.LBB0_6-.LJTI0_0
	.long	.LBB0_4-.LJTI0_0
	.long	.LBB0_4-.LJTI0_0
```

整個流程畫成圖：

```text
 orientation（%edi）
      │ decl：減 1，讓 case 1–8 變成索引 0–7
      ▼
 cmpl $7 ; ja default ──── 索引 > 7（無號）→ .LBB0_5：回傳 −1
      │ 0 ≤ 索引 ≤ 7
      ▼
 .LJTI0_0（在 .rodata）        每格存「目標 − 表格起點」的 4-byte 位移
 ┌────┬──────────────┐
 │ 0  │ .LBB0_2      │ case 1、4 → return x
 │ 1  │ .LBB0_3      │ case 2、3 → return w − 1 − x
 │ 2  │ .LBB0_3      │
 │ 3  │ .LBB0_2      │
 │ 4  │ .LBB0_6      │ case 5、6 → return y（%rax 已經是 y）
 │ 5  │ .LBB0_6      │
 │ 6  │ .LBB0_4      │ case 7、8 → return h − 1 − y
 │ 7  │ .LBB0_4      │
 └────┴──────────────┘
      │ movslq 讀出位移，加上表格起點 → jmpq *%rdi
      ▼
   對應 case 的程式碼
```

逐步解說：

1. **範圍檢查只用一次比較**。`decl` 把 orientation 減 1，然後 `cmpl $7` 加上 `ja`（**無號**大於）。如果 orientation 是 0 或負數，減 1 之後當成無號數會變成一個巨大的值，同樣大於 7。一條無號比較同時檢查了上界與下界，這是第 4 章「有號與無號轉換」的一個漂亮應用。
2. **查表**。`leaq .LJTI0_0(%rip), %rdx` 取得表格位址；`movslq (%rdx,%rdi,4), %rdi` 讀出第 i 格（每格 4 bytes，所以 scale 是 4）；加上表格起點，得到目標位址；`jmpq *%rdi` 間接跳過去。表格存的是相對位移而不是絕對位址，所以程式被載入到任何位址都不用修改表格（position-independent code，第 19 章）。GCC 在不需要 PIC 時常用 8-byte 絕對位址的表格，寫成 `jmp *.L4(,%rdi,8)` 的形式。
3. **重複的 case 共用程式碼**。case 2 和 3 的程式碼相同，表格中兩格指向同一個標籤 `.LBB0_3`。`w − 1 − x` 被寫成 `w + ~x`（因為 `~x = −x − 1`）。
4. **預先放好的回傳值**。查表之前的 `movq %rdx, %rax` 已經把 `y` 放進回傳值暫存器，所以 case 5、6 只要跳到 `.LBB0_6` 直接 `retq`。

編譯器什麼時候用 jump table？大致的規則是 case 數量夠多（通常至少四、五個）而且值夠密集。如果 case 值很稀疏（例如 1、100、5000），jump table 會有大量空格，編譯器會改用二分搜尋式的比較樹。如果每個 case 只是回傳一個常數，編譯器甚至可能直接建一張「值的表」而不是「位址的表」，連跳躍都省了。

## 8.11 分支預測：為什麼資料會影響速度

現在可以回答 8.1 節的問題了。現代 CPU 用 **pipeline**（管線）執行指令：一條指令的執行被拆成很多個階段，就像工廠的生產線，前一條指令還在計算時，後面好幾條已經在讀取與解碼了（第 13 章會詳細講）。這讓 CPU 平均每個 cycle 能完成一條指令；再加上一次發出多條指令的 superscalar 設計，甚至能完成好幾條。

條件跳躍打斷了這條生產線：在 `cmp` 的結果出來之前，CPU 不知道下一條指令是哪一條。如果停下來等，pipeline 裡就會出現好幾個 cycle 的空檔。所以 CPU 會**猜**：**branch predictor**（分支預測器）根據這個分支過去的行為預測它這次會不會跳，然後沿著預測的方向繼續執行，這叫**推測執行**（speculative execution）。

```text
 預測正確                                  預測錯誤
 ─────────                                 ─────────
 cmp  ─▶ jl（猜：不跳）─▶ 繼續執行 ─▶ …    cmp ─▶ jl（猜：不跳）─▶ 執行了 10 幾條「錯的」指令
                       結果出來：確實不跳                          結果出來：其實要跳！
                       → 什麼都不用做                              → 丟掉這些指令的結果
                                                                   → 從正確位址重新開始
 代價：約 0 cycle                          代價：大約十幾到二十幾個 cycle（依微架構而定）
```

預測器很聰明，能學會「總是跳」「總是不跳」「每三次跳一次」這類規律。迴圈的回頭跳躍、錯誤檢查（幾乎從不成立）、白天照片中大片連續的亮區與暗區，都很好預測。但它無法預測**真正隨機**的東西：夜景照片的雜訊讓 `px[i] >= 128` 這個條件大約一半成立、一半不成立，而且沒有規律，預測器最多只能猜對一半。

看 `keep_bright` 的兩個版本實際的組合語言：

```c
#include <stdint.h>
long keep_bright_branchy(const uint8_t *px, uint8_t *out, long n) {
    long k = 0;
    for (long i = 0; i < n; i++)
        if (px[i] >= 128)
            out[k++] = px[i];
    return k;
}
long keep_bright_branchless(const uint8_t *px, uint8_t *out, long n) {
    long k = 0;
    for (long i = 0; i < n; i++) {
        out[k] = px[i];          /* 每次都寫 */
        k += (px[i] >= 128);     /* 只有符合時 k 才前進 */
    }
    return k;
}
```

兩個版本以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生（分支版的迴圈主體從 `.LBB0_4` 開始）：

```asm
keep_bright_branchy:
	testq	%rdx, %rdx
	jle	.LBB0_1
	xorl	%ecx, %ecx
	xorl	%eax, %eax
	jmp	.LBB0_4
.LBB0_6:
	incq	%rcx
	cmpq	%rcx, %rdx
	je	.LBB0_2
.LBB0_4:
	movzbl	(%rdi,%rcx), %r8d
	testb	%r8b, %r8b
	jns	.LBB0_6
	movb	%r8b, (%rsi,%rax)
	incq	%rax
	jmp	.LBB0_6
.LBB0_1:
	xorl	%eax, %eax
.LBB0_2:
	retq
keep_bright_branchless:
	testq	%rdx, %rdx
	jle	.LBB1_1
	xorl	%ecx, %ecx
	xorl	%r8d, %r8d
.LBB1_4:
	movzbl	(%rdi,%rcx), %eax
	movb	%al, (%rsi,%r8)
	movzbl	(%rdi,%rcx), %eax
	shrl	$7, %eax
	addq	%r8, %rax
	incq	%rcx
	movq	%rax, %r8
	cmpq	%rcx, %rdx
	jne	.LBB1_4
	retq
.LBB1_1:
	xorl	%eax, %eax
	retq
```

分支版的關鍵是 `testb %r8b, %r8b; jns .LBB0_6`：編譯器發現「一個 byte 大於等於 128」等價於「最高位元是 1」，也就是 SF = 1，所以直接用 `test` 看符號位元。`jns`（不是負的，也就是 < 128）就跳過寫入。這個 `jns` 就是那個在夜景照片上猜錯一半的分支。

無分支版的迴圈裡只剩迴圈本身的 `jne`（除了最後一次之外都會跳，非常好預測）。`px[i] >= 128` 被編成 `shrl $7`：右移 7 位後剩下的就是最高位元，剛好是 0 或 1。代價是每個像素都會寫一次 `out[k]`，所以 `out` 必須有 `n` 個 bytes 的空間，而不只是「亮像素的數量」。

你可能注意到無分支版讀了 `px[i]` 兩次：`movb %al, (%rsi,%r8)` 寫入之後又 `movzbl (%rdi,%rcx), %eax` 重讀一次。這是因為編譯器無法確定 `out` 和 `px` 有沒有指向重疊的記憶體，寫入 `out[k]` 可能改到 `px[i]`。這叫 memory aliasing，第 14 章會講如何用 `restrict` 告訴編譯器它們不重疊。

## 8.12 動手做：模擬 condition codes，量測猜錯的代價

### 程式一：condition codes 模擬器

這段程式模擬 8-bit 的 `cmpb`：計算 `a − b`，算出四個旗標，再用 8.5 節的公式算出 `setl`、`setb`、`sete`，並和 C 自己的比較結果核對。

```c
#include <stdint.h>
#include <stdio.h>

/* 模擬 8-bit 的 cmpb：計算 a - b，只留下四個 condition code。 */
typedef struct { int cf, zf, sf, of; } flags_t;

static flags_t cmp8(uint8_t a, uint8_t b) {
    uint8_t t = (uint8_t)(a - b);
    flags_t f;
    f.cf = a < b;                          /* 無號減法需要借位 */
    f.zf = t == 0;
    f.sf = (t >> 7) & 1;                   /* 結果的最高位元 */
    /* 有號溢位：a、b 符號不同，而且結果符號和 a 不同 */
    f.of = (((a ^ b) & (a ^ t)) >> 7) & 1;
    return f;
}

static void report(uint8_t a, uint8_t b) {
    flags_t f = cmp8(a, b);
    printf("a=0x%02x(%4d/%3u) b=0x%02x(%4d/%3u) | CF=%d ZF=%d SF=%d OF=%d | ",
           a, (int8_t)a, a, b, (int8_t)b, b, f.cf, f.zf, f.sf, f.of);
    /* setl 看 SF^OF（有號小於），setb 看 CF（無號小於） */
    printf("setl=%d setb=%d sete=%d\n", f.sf ^ f.of, f.cf, f.zf);
    /* 和 C 自己的比較核對，確認公式正確 */
    if ((f.sf ^ f.of) != ((int8_t)a < (int8_t)b) || f.cf != (a < b))
        printf("  !! 公式和 C 的比較不一致\n");
}

int main(void) {
    report(3, 5);       /* 一般情況：兩種解讀都是「小於」 */
    report(5, 5);       /* 相等 */
    report(0xFF, 1);    /* -1 對 1：有號小於，無號卻是 255 > 1 */
    report(0x80, 1);    /* -128 - 1：有號溢位 */
    report(0x7F, 0xFF); /* 127 - (-1)：有號溢位的另一個方向 */
    return 0;
}
```

在 macOS arm64（Apple clang 21，`cc -std=c17 -O1 -Wall -Wextra`）上的輸出：

```text
a=0x03(   3/  3) b=0x05(   5/  5) | CF=1 ZF=0 SF=1 OF=0 | setl=1 setb=1 sete=0
a=0x05(   5/  5) b=0x05(   5/  5) | CF=0 ZF=1 SF=0 OF=0 | setl=0 setb=0 sete=1
a=0xff(  -1/255) b=0x01(   1/  1) | CF=0 ZF=0 SF=1 OF=0 | setl=1 setb=0 sete=0
a=0x80(-128/128) b=0x01(   1/  1) | CF=0 ZF=0 SF=0 OF=1 | setl=1 setb=0 sete=0
a=0x7f( 127/127) b=0xff(  -1/255) | CF=1 ZF=0 SF=1 OF=1 | setl=0 setb=1 sete=0
```

逐行解說（每行括號中是「有號／無號」兩種解讀）：

1. **3 對 5**：差是 −2，沒有溢位，SF = 1；無號減法需要借位，CF = 1。兩種解讀都是「小於」。
2. **5 對 5**：差是 0，ZF = 1，`sete = 1`，兩種「小於」都不成立。
3. **`0xFF` 對 1**：同一組位元，有號是 −1 < 1（`setl = 1`），無號是 255 > 1（`setb = 0`）。這一行就是「`-1 < 0u` 為假」這類 C 陷阱（第 4 章）在硬體上的樣子。
4. **−128 對 1**：結果 `0x7F` 看起來是正的（SF = 0），但發生了有號溢位（OF = 1），`SF ^ OF = 1`，仍然正確判斷為「小於」。這驗證了 8.5 節的推導。
5. **127 對 −1**：結果 `0x80` 看起來是負的（SF = 1），但同樣是溢位，`SF ^ OF = 0`，正確判斷為「不小於」。無號解讀是 127 < 255，`setb = 1`。

程式沒有印出任何「不一致」，表示公式在這五個情況下都和 C 的比較一致。練習 2 會請你把它擴充成窮舉所有 65,536 種組合。

### 程式二：量測 branch misprediction

這段程式重現 8.1 節的問題：同樣的 1 MiB 像素，比較隨機（夜景）與排序後（像白天大片連續區域，而且更極端）兩種資料，以及無分支版本。

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N (1 << 20)          /* 1 MiB 的像素，約一張 1024×1024 灰階圖 */
#define ROUNDS 50

/* 把「夠亮」的像素收集到 out：分支版 */
__attribute__((noinline))
static long keep_bright_branchy(const uint8_t *px, uint8_t *out, long n) {
    long k = 0;
    for (long i = 0; i < n; i++)
        if (px[i] >= 128)
            out[k++] = px[i];
    return k;
}

/* 無分支版：每次都寫，但只有符合條件時 k 才前進 */
__attribute__((noinline))
static long keep_bright_branchless(const uint8_t *px, uint8_t *out, long n) {
    long k = 0;
    for (long i = 0; i < n; i++) {
        out[k] = px[i];
        k += (px[i] >= 128);
    }
    return k;
}

static int cmp_u8(const void *a, const void *b) {
    return *(const uint8_t *)a - *(const uint8_t *)b;
}

static double run_ms(long (*fn)(const uint8_t *, uint8_t *, long),
                     const uint8_t *px, uint8_t *out, long *kept) {
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (int r = 0; r < ROUNDS; r++)
        *kept = fn(px, out, N);
    clock_gettime(CLOCK_MONOTONIC, &t1);
    return (t1.tv_sec - t0.tv_sec) * 1e3 + (t1.tv_nsec - t0.tv_nsec) / 1e6;
}

int main(void) {
    uint8_t *noisy = malloc(N), *sorted = malloc(N), *out = malloc(N);
    if (!noisy || !sorted || !out) return 1;
    srand(42);
    for (long i = 0; i < N; i++)
        noisy[i] = sorted[i] = (uint8_t)(rand() & 0xFF);   /* 雜訊很多的照片 */
    qsort(sorted, N, 1, cmp_u8);                           /* 同一批值，排序後 */

    long kept;
    double a = run_ms(keep_bright_branchy, noisy, out, &kept);
    printf("分支版   × 隨機資料：%7.1f ms（保留 %ld 個）\n", a, kept);
    double b = run_ms(keep_bright_branchy, sorted, out, &kept);
    printf("分支版   × 排序資料：%7.1f ms（保留 %ld 個）\n", b, kept);
    double c = run_ms(keep_bright_branchless, noisy, out, &kept);
    printf("無分支版 × 隨機資料：%7.1f ms（保留 %ld 個）\n", c, kept);
    free(noisy); free(sorted); free(out);
    return 0;
}
```

在 macOS arm64（Apple M4 Pro，Apple clang 21，`cc -std=c17 -O1 -Wall -Wextra`）上的一次輸出：

```text
分支版   × 隨機資料：  147.3 ms（保留 523962 個）
分支版   × 排序資料：   13.3 ms（保留 523962 個）
無分支版 × 隨機資料：   14.6 ms（保留 523962 個）
```

逐行解說：

1. **三次都保留了 523,962 個像素**，大約是 1,048,576 的一半，因為隨機 byte 有一半 ≥ 128。排序只是改變順序，不改變內容，所以工作量完全一樣。
2. **分支版在隨機資料上慢了 11 倍**。排序後的資料前半全是暗像素、後半全是亮像素，分支只在中間「轉換」一次，預測器幾乎每次都猜對；隨機資料則大約每兩個像素就猜錯一次。
3. **估算一次猜錯的代價**：50 輪 × 1,048,576 個像素，約一半猜錯，大約 2,600 萬次猜錯；多花的時間是 147.3 − 13.3 = 134 ms，平均每次約 5 ns。以這顆處理器數 GHz 的時脈換算，大約是二十個 cycle 左右的量級，和 8.11 節說的「十幾到二十幾個 cycle」一致。（這是粗估，確切數字依微架構與時脈而定。）
4. **無分支版在隨機資料上幾乎和「分支版加上完美預測」一樣快**。它每次都多寫一個 byte，但完全不會猜錯，所以不在乎資料的分佈。

這個實驗是在 ARM64 上跑的，但現象和 x86-64 完全相同，因為分支預測是所有高效能 CPU 的共同設計。你的數字會因機器而不同，但「隨機資料明顯較慢」的結論應該都成立。如果你用 `-O2` 或 `-O3` 重新編譯，編譯器可能會自動向量化或改寫迴圈，差距會改變，這正好說明了「讀組合語言確認編譯器做了什麼」的重要性。

## 8.13 在工作上怎麼用

### 解開故事：高光預覽的修正

小安把 `thumbd` 的 `keep_bright` 換成無分支版本，並把輸出緩衝區的大小改成和輸入一樣（這是無分支版的前提）。部署後，夜景與白天照片的處理時間都穩定在十幾毫秒，p99 回到目標內。

老周補充了兩件事。第一，改寫前要先**確認瓶頸真的是分支預測**，而不是 cache miss 或其他原因；第二，改寫後要**看組合語言確認**，因為編譯器可能在不同版本或不同最佳化等級下自動做了類似的轉換，也可能把你的無分支寫法又變回分支。

### 判斷是不是 branch misprediction

在 Linux 上，`perf` 可以直接讀 CPU 的硬體計數器：

```bash
# 整體統計：分支總數與猜錯次數
perf stat -e branches,branch-misses ./thumbd-bench night.jpg

# 找出是哪一條分支猜錯最多
perf record -e branch-misses ./thumbd-bench night.jpg
perf annotate keep_bright
```

判斷流程：

```text
 症狀：某類輸入特別慢，但工作量（迴圈次數、資料量）相同
   │
   ├─ 1. perf stat -e branches,branch-misses
   │      └─ branch-misses 佔 branches 的比例
   │           ├─ 很低（約 1% 以下）→ 大概不是分支問題，改查 cache（第 17 章）
   │           └─ 明顯偏高，且慢的輸入比快的高很多 → 繼續
   │
   ├─ 2. perf record -e branch-misses ＋ perf annotate
   │      └─ 找出猜錯集中在哪一條 j 指令，對回 C 的哪個 if
   │
   ├─ 3. 這個條件是否依賴「不可預測的資料」？
   │      （像素值、雜湊值、使用者輸入、隨機 ID）
   │
   └─ 4. 對策（擇一，改完重新量測）
          ├─ 改寫成無分支：用比較結果當 0／1 參與運算，或讓編譯器產生 cmov
          ├─ 讓資料變得可預測：先分組或排序（若本來就需要排序）
          ├─ 把分支移出迴圈：例如依類型先分批，再對每批跑無分支的迴圈
          └─ 用 SIMD 一次處理多個像素（第 14 章）
```

macOS 上沒有 `perf`，可以用 Instruments 的 CPU Counters 觀察類似的計數器。沒有工具時，8.12 節的「打亂資料 vs 排序資料」對照實驗本身就是一個很好的診斷方法：如果排序後明顯變快，而工作量不變，分支預測就是主要嫌疑。

### `__builtin_expect` 與 PGO

GCC 與 clang 提供 `__builtin_expect(cond, 1)`（C++20 有 `[[likely]]`），告訴編譯器某個條件幾乎總是成立。要注意它主要**不是**靠改變 CPU 的預測器起作用：編譯器在 x86-64 上通常不會因此產生任何「提示」給硬體，硬體預測器仍然只看分支過去的實際行為。它影響的是編譯器的**程式碼排列**：把常見路徑排成不需要跳躍的直線，把罕見路徑（例如錯誤處理）移到函式尾端。這對 instruction cache 與取指令有幫助，但對「真正隨機」的分支沒有用。

更系統化的方法是 **PGO**（profile-guided optimization）：先用 `-fprofile-generate` 編譯並跑代表性的工作負載，收集每個分支的實際走向，再用 `-fprofile-use` 重新編譯。編譯器會依照真實資料決定程式碼排列、要不要用 `cmov`、哪些函式要 inline。很多大型專案（瀏覽器、資料庫、程式語言直譯器）的 release build 都會使用 PGO。

### Code review 時檢查比較與溢位

本章的知識在 code review 時也很實用。看到下面這些寫法要停下來想一想：

1. **無號數相減後和 0 比較**（`len - n < 0`、`len - n >= 0`）：永遠為假或永遠為真，8.7 節的 `body_too_short`。
2. **有號與無號混合比較**（`int i` 和 `size_t n`）：C 的轉換規則會把有號數轉成無號，`-1` 變成很大的數（第 4 章），組合語言中會出現 `jb`／`ja` 而不是 `jl`／`jg`。
3. **自己寫溢位檢查**（`if (a + b < a)`）：對有號數這是 undefined behavior，編譯器可能刪掉它（第 5 章）。改用 `__builtin_add_overflow`、`__builtin_mul_overflow`，它們會直接編成「運算 + `seto`／`jo`」，正確又便宜。下面是 `int area_overflows(long w, long h, long *area) { return __builtin_mul_overflow(w, h, area); }` 以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生的結果：

```asm
area_overflows:
	xorl	%eax, %eax
	imulq	%rsi, %rdi
	seto	%al
	movq	%rdi, (%rdx)
	retq
```

`imulq` 做乘法，`seto` 直接把 OF 讀成回傳值：OF = 1 表示有號溢位。這就是第 5 章 `thumbd` 計算「寬 × 高 × 4」時應該使用的方式。

## 8.14 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 某類輸入特別慢，工作量卻相同 | 分支依賴不可預測的資料，大量 branch misprediction | `perf stat -e branches,branch-misses`；排序 vs 隨機的對照實驗 | 改成無分支寫法、分批處理、SIMD；改完看組合語言並重新量測 |
| 邊界檢查「沒有作用」，越界存取照樣發生 | 無號數相減後與 0 比較，編譯器把檢查刪除 | 看 `-O1 -S` 輸出，比較指令是否消失；開 `-Wextra`（GCC） | 改成 `len < n` 這種不會回繞的比較 |
| 負數索引通過了 `i < n` 的檢查 | 有號與無號混合比較，`-1` 被轉成無號的大數 | 組合語言中是 `jb`／`ja` 還是 `jl`／`jg` | 統一型別；先檢查 `i < 0` |
| 程式收到 `SIGFPE`，但沒有浮點運算 | 整數除以 0，或 `LONG_MIN / -1` | gdb 中 `x/i $pc` 看到 `idiv`／`div`，檢查除數暫存器 | 除法前檢查除數；對外部輸入特別小心 |
| 讀組合語言時 if 的條件看反了 | 編譯器產生「條件不成立就跳過」的程式碼 | 把組合語言改寫成 goto 形式對照 | 記住跳躍條件通常與 C 相反 |
| 「我寫的是無分支版本，怎麼組合語言裡還有跳躍？」 | 編譯器依自己的成本模型把它改回分支，或迴圈本身的跳躍被誤認 | 找出迴圈的回頭跳躍以外的條件跳躍 | 調整寫法、檢查不同最佳化等級；以量測結果為準 |

## 8.15 動手練習

1. **手算旗標**：對下列 8-bit 運算，算出結果與 CF、ZF、SF、OF：`0x40 + 0x40`、`0xC0 + 0xC0`、`0x01 − 0x02`、`0x80 − 0x80`。（答案：`0x80`／0 0 1 1；`0x80`／1 0 1 0；`0xFF`／1 0 1 0；`0x00`／0 1 0 0。驗證減法：用 8.12 節程式一的 `report` 函式。）
2. **延伸程式一**：把 `main` 改成兩層迴圈，窮舉所有 256 × 256 種 `(a, b)` 組合，並對 `setle`、`setg`、`seta`、`setbe` 也加上公式與 C 比較的核對。程式應該完全不印出「不一致」。
3. **延伸程式二**：在 8.12 節的程式二加入第四種資料：「每 64 個像素為一組，組內全亮或全暗，組與組之間隨機」，模擬照片中的小區塊。預測它的速度會落在隨機與排序之間的哪裡，再實際量測。
4. **讀 jump table**：把 8.10 節的 `src_x` 加上 `case 9: return x + y;`，以及一個 `case 100:`，重新用 `clang -target x86_64-linux-gnu -O1 -S` 產生。觀察範圍檢查的常數與表格大小怎麼變化，case 100 是用表格還是額外的比較處理？
5. **反推 C**：用 `clang -target x86_64-linux-gnu -O1 -S` 編譯 `long abs_diff(long a, long b) { return a < b ? b - a : a - b; }`，說明編譯器用了跳躍還是 `cmov`，並解釋原因。接著把其中一邊改成呼叫一個外部函式，再比較一次。
6. **找迴圈**：用 `objdump -d` 反組譯 8.9 節三個函式的目的檔，為每個條件跳躍手算目標位址（下一條指令位址加上位移），並標出哪一個是迴圈的回頭跳躍。

## 本章重點整理

- 算術與邏輯指令大多是兩運算元形式，目的同時也是來源；同一條 `add`／`sub` 同時適用於有號與無號數，右移則要依型別選 `sar` 或 `shr`。
- 單運算元的 `mulq`／`imulq` 產生 128-bit 結果放在 `%rdx:%rax`；除法以 `%rdx:%rax` 為被除數，商在 `%rax`、餘數在 `%rdx`，有號除法前用 `cqto` 做符號延伸。
- 除以常數時，編譯器會用 shift 加 bias（2 的冪）或乘以魔術數再右移來取代昂貴的除法指令；除以 0 或 `LONG_MIN / -1` 會觸發 `SIGFPE`。
- 算術指令會設定 condition codes：CF 描述無號溢位、OF 描述有號溢位、ZF 表示結果為 0、SF 是結果的最高位元；`mov`、`lea` 不改它們，`inc`／`dec` 不改 CF。
- `cmp` 做減法、`test` 做 AND，兩者只設定旗標不存結果；`set` 把旗標組合寫成 0 或 1。
- 有號小於是 `SF ^ OF`，無號小於是 `CF`；從 `jl`／`jg` 與 `jb`／`ja` 可以反推原始碼用的是有號還是無號比較。
- 跳躍目標通常以 PC-relative 位移編碼，目標等於下一條指令的位址加上有號位移，這讓程式碼可以被載入到任意位址。
- `if` 通常被翻成「條件不成立就跳過 then-part」，所以組合語言中的跳躍條件常和 C 的條件相反。
- conditional move 讓 `if` 變成「兩邊都算再選一個」，沒有猜錯的風險；但某一邊可能出錯、有副作用、很昂貴或需要條件式寫入時，不能使用。
- 迴圈就是往回跳的條件跳躍；`while` 與 `for` 常被翻成 guarded-do 或 jump-to-middle 的形狀，找回頭跳躍就能找到迴圈。
- case 多且密集的 `switch` 會編成 jump table：先用一次無號比較做範圍檢查，再查表做間接跳躍。
- CPU 會在比較結果出來前預測分支並推測執行，猜錯要丟掉工作重來，代價約十幾到二十幾個 cycle；依賴隨機資料的分支可能讓同一段程式慢上一個數量級。
- 處理效能問題時，先用 `perf stat` 確認 branch-misses 是瓶頸，再改寫成無分支或調整資料，最後看組合語言並重新量測。
- `__builtin_mul_overflow` 這類內建函式會編成「運算 + 讀 OF」，是檢查整數溢位最正確也最便宜的方式。

## 延伸問答

> [!question]- Q1. `cmpq %rsi, %rdi` 之後，`jl` 和 `jb` 會不會對同一組暫存器值做出不同的決定？舉例說明。
> 會。`cmp` 只做一次減法 `rdi − rsi` 並設定所有旗標，`jl` 看 `SF ^ OF`（把兩者當有號數），`jb` 看 `CF`（把兩者當無號數）。只要兩個值的最高位元不同，兩種解讀就可能得出相反的結論。
>
> 例如 `%rdi = 0xFFFFFFFFFFFFFFFF`、`%rsi = 1`。有號解讀是 −1 < 1，所以 `jl` 會跳；無號解讀是 2^64 − 1 > 1，減法不需要借位，CF = 0，所以 `jb` 不跳。這正是 C 中 `-1 < 1u` 為假的硬體根源：編譯器把比較轉成無號後，就會選 `jb`／`setb`。讀組合語言時可以反過來利用這點，從跳躍指令判斷原始碼中變數的有號性。

> [!question]- Q2. 手算題：8-bit 加法 `0x90 + 0x90` 之後，四個 condition codes 各是多少？用有號與無號兩種角度解釋。
> `0x90 + 0x90 = 0x120`，只保留低 8 bits 得到 `0x20`。最高位元有進位，CF = 1；結果不是 0，ZF = 0；結果最高位元是 0，SF = 0；兩個負數（有號 `0x90` 是 −112）相加得到正數，OF = 1。
>
> 無號角度：144 + 144 = 288，超過 255，CF = 1 正確表示無號溢位，結果 32 = 288 − 256。有號角度：−112 + (−112) = −224，小於 −128，OF = 1 正確表示有號溢位，結果 32 = −224 + 256。這題同時展示了 CF 與 OF 的獨立性，以及兩種溢位都是「模 256」的同一個位元結果。

> [!question]- Q3. 為什麼編譯 `x / 8`（`long x`）時不能只用一條 `sarq $3`？編譯器實際上怎麼做？
> C 規定整數除法向零捨入：−9 / 8 = −1。算術右移則是向負無限大捨入：−9 >> 3 = −2。對非負數兩者相同，但對不能整除的負數會差 1。
>
> 解法是對負數先加上 bias 2^k − 1（這裡是 7）再右移：(−9 + 7) >> 3 = −2 >> 3 = −1。clang 產生的程式碼是 `leaq 7(%rdi), %rax`、`testq %rdi, %rdi`、`cmovnsq %rdi, %rax`、`sarq $3, %rax`：先算 x + 7，如果 x 非負就改回 x，最後右移。用 `cmov` 而不是分支，是因為兩邊都只是簡單的值，沒有出錯或副作用的風險。如果 x 是 `unsigned long`，就只需要一條 `shrq $3`，這也是為什麼「確定不會是負數」的值用無號型別有時能讓程式碼更簡單。

> [!question]- Q4. 編譯器什麼時候不能把 `if` 改成 conditional move？
> `cmov` 的本質是「兩邊都先算好，最後選一個」，所以只有當計算兩邊都安全而且便宜時才可行。不能使用的典型情況有四種：某一邊可能觸發錯誤（例如解參考可能是 NULL 的指標、除以可能是 0 的數）；某一邊有副作用（修改全域變數、寫記憶體、呼叫函式）；某一邊很昂貴，兩邊都算的成本超過猜錯的代價；以及需要「有條件地寫入記憶體」，因為 `cmov` 只能選擇放進暫存器的值。
>
> 8.8 節的 `read_or_default` 就是第一種情況，編譯器用了 `test` 加 `je`；`clamp_u8_counted` 因為要更新 `clipped_count`，屬於第二種。另外，即使可以用，編譯器也會評估分支是否可預測：對很好預測的分支，條件跳躍幾乎不花成本，`cmov` 反而延長了資料相依鏈。

> [!question]- Q5. 你在 production 用 `perf stat` 發現某個服務的 branch-misses 比例很高。你會怎麼判斷這是不是真正的瓶頸、以及怎麼處理？
> 首先要確認它和延遲有關，而不只是「比例看起來高」。比較快與慢的請求（或不同輸入）的 branch-misses 數量，如果慢的請求明顯高很多，而指令數與資料量差不多，分支預測就是可疑的瓶頸。接著用 `perf record -e branch-misses` 與 `perf annotate` 找出猜錯集中在哪一條跳躍指令，對回原始碼的哪個條件。
>
> 再判斷這個條件依賴什麼：如果依賴的是隨機性很高的資料（雜湊值、像素、使用者輸入），可以改寫成無分支（比較結果當 0／1 參與運算、讓編譯器產生 `cmov`）、先把資料分組再分別處理，或用 SIMD。如果是程式碼排列的問題（例如錯誤處理路徑和熱路徑混在一起），可以用 `__builtin_expect` 或 PGO。每一種改法都要看組合語言確認編譯器真的照做，並用相同的工作負載重新量測，因為無分支寫法也有代價（多做的計算、多寫的記憶體）。

> [!question]- Q6. `switch` 什麼時候會被編成 jump table？為什麼範圍檢查用的是 `ja` 而不是 `jg`？
> 當 case 數量夠多、而且 case 值落在一個夠密集的範圍內時，編譯器會建一張以 case 值為索引的位址表，用一次查表加間接跳躍取代一連串比較。case 很少時，幾次比較就夠了；case 值很稀疏時，表格會有大量浪費的空格，編譯器會改用比較樹。確切的門檻由編譯器的成本模型決定。
>
> 範圍檢查先把值減去最小的 case（8.10 節是減 1），讓合法範圍變成 0 到 k，再用一次**無號**比較判斷是否大於 k。如果原本的值小於最小 case，減完之後是負數，當成無號數就是一個巨大的值，同樣會大於 k。所以一條 `ja` 同時處理了上界與下界，用 `jg` 則需要另外檢查負數。這是有號與無號轉換的一個實用技巧，你自己寫邊界檢查時也可以用 `(unsigned)(x - lo) <= (unsigned)(hi - lo)` 這種寫法。

> [!question]- Q7. 程式找錯：下面的檢查為什麼在 `-O1` 下完全沒有作用？`int body_too_short(size_t len, size_t header) { return len - header < 0; }`
> `size_t` 是無號型別，`len - header` 的結果也是 `size_t`，無號數永遠大於等於 0，所以 `< 0` 永遠為假。編譯器依照 C 的語意推導出這一點，產生的組合語言只剩 `xorl %eax, %eax; retq`，也就是「無條件回傳 0」，檢查整個消失了。
>
> 當 `len < header` 時，`len - header` 會回繞成一個接近 2^64 的大數，後續若用它當長度，就會讀寫超出緩衝區的範圍，這是實際漏洞的常見模式。正確的寫法是直接比較 `len < header`，組合語言會出現 `cmpq` 加 `setb`。這類 bug 可以靠 GCC 的 `-Wextra`（包含 `-Wtype-limits`）或 clang 的 `-Wtype-limits`／`-Wtautological-unsigned-zero-compare`（clang 的 `-Wextra` 不包含它們）抓到，也可以在 review 時直接看組合語言確認檢查是否還在。

> [!question]- Q8. 面試題：為什麼處理排序過的陣列比處理未排序的陣列快？兩者執行的指令數不是一樣嗎？
> 指令數確實一樣，差別在於 CPU 執行它們的效率。現代 CPU 用 pipeline 同時處理多條指令，遇到條件跳躍時不會停下來等比較結果，而是由 branch predictor 猜測方向並推測執行。猜對幾乎沒有成本；猜錯則要丟掉已經執行的錯誤路徑上的工作，從正確位址重新開始，代價大約十幾到二十幾個 cycle。
>
> 如果迴圈中有一個依賴元素值的分支（例如 `if (a[i] >= 128)`），排序後的陣列會讓這個分支先連續不成立、再連續成立，預測器幾乎每次都猜對；未排序的隨機資料則讓預測器猜對的機率只有一半左右。8.12 節的實驗中，同樣的工作量相差約 11 倍。解決方法包括改寫成無分支程式碼（用比較結果當 0 或 1 參與運算、`cmov`）或用 SIMD；面試時能進一步說明「為什麼不能總是用 `cmov`」（副作用、可能出錯的運算、可預測分支時反而較慢），會是加分的回答。
