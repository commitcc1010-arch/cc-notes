# 第 11 章　記憶體安全：Buffer Overflow 的成因、偵測與防護

> [!abstract] 本章地圖
> **核心問題**：C 程式寫超過陣列的尾端時，被蓋掉的是什麼？為什麼這類 bug 被視為最嚴重的一類安全問題，現代工具鏈又提供哪些方法及早發現並擋下它？
>
> **你會學到**：
> - 從 stack frame 的配置，算出一個 local 陣列和 saved 暫存器、return address 之間差幾個 byte

> - 看懂 variable-size stack frame 的組合語言，知道 VLA 長度不受控為什麼危險
> - 用有界的字串處理、`_FORTIFY_SOURCE`、AddressSanitizer 與 fuzzing 從源頭找出並修掉越界寫入
> - 在工作上檢查一個 binary 開了哪些防護，並在看到 `stack smashing detected` 時正確處理
>
> **前置知識**：第 9 章（stack frame、`call`／`ret` 與 return address）、第 10 章（陣列與指標運算）、第 5 章（整數溢位造成的錯誤長度）
>

## 11.1 故事：一張照片讓 thumbd 自己結束了

週五下午，SRE 阿哲在頻道裡貼了一段 log：`thumbd` 的某個 worker 在處理一張使用者上傳的照片時結束了，systemd 自動把它拉起來，前後中斷不到一秒。log 最後一行是：

```text
*** stack smashing detected ***: terminated
```

小安搜尋這段訊息，找到的第一個結果寫著「這表示你的程式有 buffer overflow」。小安有點困惑：`thumbd` 沒有當掉在什麼奇怪的位址，也沒有 segfault，而是「自己」偵測到問題然後結束。是誰偵測的？偵測到了什麼？

老周把那張照片抓下來，用 `exiftool` 看了一下：照片的 EXIF 資料裡，「相機型號」欄位長達 300 個字元，正常的相機型號只有十幾個字。再翻 `thumbd` 的程式碼，找到這段：

```c
static void save_camera_model(const char *exif_model) {
    char model[32];
    strcpy(model, exif_model);      /* 相機型號「應該」不會超過 31 個字 */
    log_photo_meta(model);
}
```

老周說：「這一行讓使用者可以寫超過 `model` 陣列的尾端。這次我們運氣好，編譯器放的『警報器』響了，程式在造成更大傷害前就自己結束。資安團隊會問兩個問題：第一，這個 bug 的影響範圍有多大？第二，還有沒有其他地方有同樣的問題？」

要回答這兩個問題，小安需要知道：越界寫入在 stack 上蓋掉了什麼、那個「警報器」是怎麼運作的、作業系統和編譯器還準備了哪些防線，以及怎麼在程式上線前就找出這類 bug。這就是本章的內容。

## 11.2 C 不會幫你檢查邊界

在 Python 或 Java 裡，`a[100]` 超出陣列長度會立刻丟出例外。C 不會。第 10 章說過，`a[i]` 就是 `*(a + i)`：取陣列起點、加上 `i × sizeof(元素)`，然後直接讀寫那個位址。這個計算裡沒有任何地方知道陣列有多長，硬體也不知道。

**越界存取**（out-of-bounds access）指的是讀寫了陣列範圍之外的記憶體。例如 `char model[32]` 的合法索引是 0 到 31，寫入 `model[32]` 就是越界。在 C 標準裡，越界存取是 **undefined behavior**（未定義行為，第 2 章）：標準不規定會發生什麼，可能什麼事都沒有、可能讀到垃圾值、可能當掉，也可能悄悄改掉別的資料。

「undefined」聽起來很抽象，但在真實機器上，結果其實很具體：**你會讀寫到記憶體裡剛好排在陣列旁邊的那個東西**。所以要理解越界的後果，就要問「陣列旁邊是什麼」。

| 陣列放在哪裡 | 旁邊通常是什麼 | 越界寫入的典型後果 | 常見名稱 |
|---|---|---|---|
| stack（local 變數） | 其他 local 變數、saved 暫存器、return address | 函式 return 時跳到錯誤位址而當機 | stack buffer overflow |
| heap（`malloc`） | 下一個 heap 區塊的資料、allocator 的 metadata | 別的物件被改壞；之後 `free` 時當掉 | heap buffer overflow（第 25、26 章） |
| global／static | 其他全域變數 | 設定值、函式指標被改掉 | global buffer overflow |

讀和寫的危險程度不一樣。**越界讀取**（over-read）會把不該給人看的資料送出去；2014 年 OpenSSL 的 Heartbleed 漏洞就是這一類：伺服器根據對方宣稱的長度回傳資料，沒有檢查實際長度，結果把相鄰記憶體裡的私鑰、密碼等內容送了出去。**越界寫入**（overflow）則會改掉旁邊的資料，如果旁邊剛好是「控制程式下一步去哪裡」的資料（例如 return address），程式的行為就不再可預期，這也是它被列為最高風險的原因。

> [!warning] 常見誤解
> 「越界一點點沒關係，反正程式沒當掉。」沒當掉只代表這次被蓋掉的東西剛好沒被用到，或剛好被蓋成差不多的值。換一個編譯器、換一個最佳化等級、換一個輸入，結果就可能完全不同。沒有當掉不是正確的證據。

## 11.3 Stack 上的鄰居：local 陣列和 return address 差幾個 byte

第 9 章說過，每次函式呼叫，`call` 指令會把 **return address**（函式結束後要回去的位址）push 到 stack 上，函式再往下（往低位址）配置自己的 local 變數。我們用 `thumbd` 那段程式的簡化版，看編譯器實際怎麼配置。

```c
char *strcpy(char *dst, const char *src);
void log_model(const char *model);

void save_model(const char *src) {
    char model[32];
    strcpy(model, src);
    log_model(model);
}
```

先關掉本章後面才會介紹的防護，看最原始的樣子。以下由 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -fno-stack-protector -o - canary.c` 產生（刪去無關的 directive）：

```asm
save_model:
	pushq	%rbx
	subq	$32, %rsp
	movq	%rdi, %rsi
	movq	%rsp, %rbx
	movq	%rbx, %rdi
	callq	strcpy@PLT
	movq	%rbx, %rdi
	callq	log_model@PLT
	addq	$32, %rsp
	popq	%rbx
	retq
```

逐行看：`pushq %rbx` 保存 callee-saved 暫存器 `%rbx`（第 9 章），`subq $32, %rsp` 在 stack 上挖出 32 bytes 給 `model`。接著 `movq %rsp, %rbx` 說明 `model` 的起點就是目前的 `%rsp`，它被當成 `strcpy` 的第一個參數（`%rdi`），來源字串 `src` 被搬到第二個參數 `%rsi`。把這些畫成圖：

```text
 高位址
 ┌────────────────────────┐
 │  main 的 frame          │
 ├────────────────────────┤ 
 │  return address (8)     │  rsp+40 ～ rsp+47   ← call save_model 時 push 的
 ├────────────────────────┤
 │  saved %rbx (8)         │  rsp+32 ～ rsp+39   ← pushq %rbx
 ├────────────────────────┤
 │  model[31]              │  rsp+31
 │  ...                    │      ▲
 │  model[1]               │      │ strcpy 從這裡開始，往高位址寫
 │  model[0]               │  rsp+0
 └────────────────────────┘ ← %rsp
 低位址
```

這張圖有一個關鍵的方向問題：**stack 往低位址長，但陣列的索引往高位址走**。`strcpy` 從 `model[0]` 開始一個 byte 一個 byte 往上寫，寫到第 33 個 byte 時就跨出 `model`，開始蓋 saved `%rbx`；再寫 8 個 byte，就開始蓋 return address。

用這個配置算一下，不同長度的輸入會蓋到哪裡（`strcpy` 會連字串結尾的 `\0` 一起寫，所以寫入量是「字元數 + 1」）：

| 輸入字元數 | 實際寫入 bytes | 寫到的最高位置 | 被蓋掉的東西 |
|---|---|---|---|
| 12（`Canon EOS R5`） | 13 | rsp+12 | 沒有，完全在 `model` 內 |
| 31 | 32 | rsp+31 | 沒有，剛好填滿 |
| 32 | 33 | rsp+32 | saved `%rbx` 的最低 1 byte（被寫成 0） |
| 40 | 41 | rsp+40 | 整個 saved `%rbx`，加上 return address 的最低 1 byte |
| 47 以上 | 48 以上 | rsp+47 以上 | 整個 return address |

這張表說明了為什麼 off-by-one（第 26 章）也危險：只多一個 `\0`，就改到了 caller 的 `%rbx`。caller 回來以後如果用 `%rbx` 存著一個指標，它就變成一個錯的指標，當機的位置會在離 bug 很遠的地方，非常難查。

## 11.4 編譯器的偵測：stack canary

`thumbd` 那行 `*** stack smashing detected ***` 是編譯器插入的檢查產生的。這個機制叫 **stack canary**（堆疊金絲雀）：名字來自早年礦工帶金絲雀下礦坑，金絲雀先出事，礦工就知道要撤離。編譯器在 local 陣列和 saved 暫存器之間放一個隨機值，函式 return 之前檢查它有沒有被改過；如果被改過，代表有越界寫入跨過了陣列的邊界，程式立刻結束，而不是帶著損壞的資料繼續執行。

同一段 `save_model` 程式，加上 `-fstack-protector-strong` 後，由 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -fstack-protector-strong -o - canary.c` 產生（刪去 directive 與編譯器註解）：

```asm
save_model:
	pushq	%rbx
	subq	$48, %rsp
	movq	%rdi, %rsi
	movq	%fs:40, %rax
	movq	%rax, 40(%rsp)
	movq	%rsp, %rbx
	movq	%rbx, %rdi
	callq	strcpy@PLT
	movq	%rbx, %rdi
	callq	log_model@PLT
	movq	%fs:40, %rax
	cmpq	40(%rsp), %rax
	jne	.LBB0_2
	addq	$48, %rsp
	popq	%rbx
	retq
.LBB0_2:
	callq	__stack_chk_fail@PLT
```

和 11.3 節沒有防護的版本比較，多了三件事：

1. `subq $48, %rsp`：frame 從 32 bytes 變成 48 bytes，多出的空間用來放 canary。
2. 函式一開始，`movq %fs:40, %rax` 從 thread-local storage（每個 thread 專屬的一塊記憶體，用 `%fs` 暫存器定位）讀出 canary 值，存到 `40(%rsp)`，也就是陣列上方、saved `%rbx` 下方。
3. return 之前再讀一次 `%fs:40`，和 stack 上的那份比較；不相等就跳到 `__stack_chk_fail`，由它印出錯誤訊息並呼叫 `abort`。

```text
 高位址
 ┌────────────────────────┐
 │  return address        │
 ├────────────────────────┤
 │  saved %rbx            │
 ├────────────────────────┤
 │  canary（隨機值）        │  rsp+40    ← 越界寫入要先經過這裡
 ├────────────────────────┤
 │  （對齊用的空間）        │  rsp+32
 ├────────────────────────┤
 │  model[0..31]          │  rsp+0
 └────────────────────────┘ ← %rsp
 低位址
```

因為 canary 放在陣列和控制資料之間，從陣列往高位址的連續越界寫入一定會先改到 canary。canary 的值在程式啟動時隨機產生，而且通常讓最低位元組是 `\0`，所以用字串函式寫入時很難剛好寫出同樣的值。

Canary 是一種**偵測**機制，它有清楚的能力範圍：

| 情況 | canary 能偵測嗎 | 原因 |
|---|---|---|
| 從 stack 陣列往高位址連續寫超過 | 可以，在函式 return 前 | 越界寫入會先改到 canary |
| 越界寫入只改到同一個 frame 裡的其他 local 變數 | 不行 | 那些變數可能在 canary 下方，檢查不到 |
| 不連續的寫入（例如用錯的索引寫到更遠的位置） | 不一定 | 可能跳過 canary |
| heap 或 global 的越界 | 不行 | canary 只保護 stack frame |
| 越界讀取（over-read） | 不行 | 讀取不會改變 canary |

所以看到 `stack smashing detected`，正確的理解是：「這裡確定有 stack 越界寫入，而且程式在造成更多損壞前被終止了」，而不是「沒事了」。bug 本身仍然要修。

GCC 與 Clang 有幾個等級：`-fstack-protector` 只保護含字元陣列（預設 8 bytes 以上）或呼叫 `alloca` 的函式；`-fstack-protector-strong` 擴大到任何含陣列或取了 local 變數位址的函式，是大部分 Linux 發行版的預設；`-fstack-protector-all` 保護每個函式，代價較高。

## 11.5 作業系統的防護：NX、ASLR 與 PIE

Canary 只負責偵測一種情況。作業系統另外提供兩層防護，讓記憶體錯誤更難被利用、也更容易以當機的形式提早暴露。

**NX**（no-execute，也叫 DEP 或 W^X）的硬體細節在第 23 章：page table entry（PTE，記錄每一頁權限的表項）有一個「不可執行」位元，作業系統把 stack、heap 與資料區段都標成不可執行。資料就是資料，CPU 不會把這些頁的內容當成指令執行。

**ASLR**（address space layout randomization，位址空間配置隨機化）讓 stack、heap、共享 library 的起始位址在每次執行時都不同。**PIE**（position-independent executable，位置無關執行檔）讓程式本身的程式碼與資料也能被載入到隨機位置；沒有 PIE 的執行檔，程式碼永遠在固定位址，ASLR 只能隨機化其他區域。第 19 章會說明 PIE 怎麼靠 PC-relative 定址與 GOT 做到這件事。

| 防護 | 由誰提供 | 做什麼 | 它的限制 |
|---|---|---|---|
| stack canary | 編譯器（`-fstack-protector-strong`） | 函式 return 前檢查 stack 是否被連續越界寫入 | 只偵測 stack，只在 return 時檢查 |
| NX／W^X | CPU 的 PTE 位元＋作業系統 | 資料頁不能當成指令執行 | 不處理資料本身被改壞 |
| ASLR | 作業系統 | 每次執行時隨機化各區域的位置 | 位址若被洩漏，隨機化的效果會降低 |
| PIE | 編譯器與連結器（`-fPIE -pie`） | 讓程式本身也能被隨機化 | 少量效能代價（現代 x86-64 上很小） |
| `_FORTIFY_SOURCE` | glibc＋編譯器 | 已知緩衝區大小時，把 `strcpy`、`memcpy` 換成會檢查長度的版本 | 只在編譯器知道目的地大小時有效 |
| sanitizer（ASan） | 編譯器 | 測試時在每次存取檢查邊界與生命週期 | 有效能與記憶體成本，不適合直接用在 production |

這些防護是**縱深防禦**（defense in depth）的概念：沒有一層是完美的，但層層疊加後，一個越界寫入在 production 上最可能的結果，是被偵測到並立刻結束，而不是安靜地改壞資料。真正的解法仍然是在源頭消除 bug，也就是 11.7 節的內容。

較新的硬體還加入了更多保護控制流的機制，例如 Intel 與 AMD 的 CET（control-flow enforcement technology，包含 shadow stack：在另一個受保護的 stack 上保留一份 return address，return 時兩份必須一致），以及 ARM64 的 PAC（pointer authentication，在指標的高位元加上密碼學簽章）。它們的共同目標，是讓「控制資料被改掉」這件事能被硬體偵測。

## 11.6 Variable-size stack frame：長度不受控的 VLA

到目前為止，每個函式的 stack frame 大小都是編譯時就決定的常數（例如 `subq $48, %rsp`）。C99 的 **VLA**（variable-length array，可變長度陣列）讓陣列長度可以是執行時才知道的值，這時 frame 的大小也只能在執行時計算。

```c
void fill(char *buf, long n);
long checksum(const char *buf, long n);

long process_row(long width) {
    char row[width];          /* 長度由呼叫者決定的 variable-length array */
    fill(row, width);
    return checksum(row, width);
}
```

由 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -fno-stack-protector -o - vla.c` 產生：

```asm
process_row:
	pushq	%rbp
	movq	%rsp, %rbp
	pushq	%r14
	pushq	%rbx
	movq	%rdi, %rbx
	movq	%rsp, %r14
	leaq	15(%rdi), %rax
	andq	$-16, %rax
	subq	%rax, %r14
	movq	%r14, %rsp
	movq	%r14, %rdi
	movq	%rbx, %rsi
	callq	fill@PLT
	movq	%r14, %rdi
	movq	%rbx, %rsi
	callq	checksum@PLT
	leaq	-16(%rbp), %rsp
	popq	%rbx
	popq	%r14
	popq	%rbp
	retq
```

逐段解讀：

1. `pushq %rbp; movq %rsp, %rbp`：因為 frame 大小不固定，函式需要一個固定的參考點（frame pointer，第 9 章）來找回自己的 frame，所以這裡一定會用 `%rbp`。
2. `leaq 15(%rdi), %rax; andq $-16, %rax`：把 `width` 向上取整到 16 的倍數，維持 stack 的 16-byte 對齊。例如 `width = 100` 時，`(100 + 15) & ~15 = 112`。
3. `subq %rax, %r14; movq %r14, %rsp`：把 `%rsp` 往下移動這麼多 bytes，這塊空間就是 `row`。
4. `leaq -16(%rbp), %rsp`：結束時直接用 `%rbp` 把 `%rsp` 恢復到固定位置，不需要知道當初配置了多少。

```text
 高位址
 ┌──────────────────────┐
 │ return address       │  %rbp + 8
 ├──────────────────────┤
 │ saved %rbp           │  %rbp + 0  ← %rbp 指向這裡
 ├──────────────────────┤
 │ saved %r14           │  %rbp − 8
 │ saved %rbx           │  %rbp − 16 ← 結尾 leaq -16(%rbp), %rsp 回到這裡
 ├──────────────────────┤
 │ row[width-1]         │
 │ ...                  │  大小 = width 向上取整到 16
 │ row[0]               │  （執行時才決定）
 └──────────────────────┘ ← %rsp = %r14 = row
 低位址
```

VLA 的風險在於長度。如果 `width` 來自使用者上傳的圖片標頭，而沒有上限，一個寬度為一億的圖片會讓 `%rsp` 一次往下移動約 100 MB，遠超過 thread stack 的大小（第 9 章提過 `thumbd` 的 worker stack 只有 256 KiB）。結果可能是直接撞進 guard page 而 segfault，也可能在沒有 guard page 保護的環境裡跨進別的記憶體區域。GCC 與 Clang 的 `-fstack-clash-protection` 會在大幅移動 `%rsp` 時逐頁觸碰，確保一定會碰到 guard page；但更根本的做法是：**來自外部的長度一律先檢查上限，大的緩衝區改用 heap 配置**。Linux kernel 已經全面禁止使用 VLA，也是基於同樣的理由。

## 11.7 從源頭修：讓越界寫入不會發生

前兩節的防護都是「出事時盡量降低損害」。對工程師來說，更重要的是讓 bug 不要進到 production。這需要三件事一起做：寫法、工具、測試。

### 寫法：每一次寫入都要知道目的地有多大

C 標準函式庫裡有一批函式本身就無法安全使用，因為它們不知道目的地緩衝區的大小：

| 危險的函式 | 問題 | 替代做法 |
|---|---|---|
| `gets` | 完全無法限制長度，C11 已從標準移除 | `fgets(buf, sizeof buf, stdin)` |
| `strcpy`、`strcat` | 只看來源的 `\0`，不管目的地多大 | 先檢查長度再 `memcpy`，或用 `snprintf`；BSD 與 macOS 有 `strlcpy`，glibc 2.38 起也提供 |
| `sprintf` | 輸出長度不受限 | `snprintf`，並檢查回傳值判斷是否截斷 |
| `scanf("%s", buf)` | 沒有寬度限制 | `scanf("%31s", buf)` 或改用 `fgets` 加解析 |
| `strncpy` | 常被誤用：來源太長時不會補 `\0` | 不要當成「安全的 strcpy」，改用上述做法 |

比函式選擇更重要的是一個習慣：**長度永遠和指標一起傳遞**。像 `void save_model(const char *src)` 這樣的介面，呼叫者沒辦法告訴函式「這段資料有多長」，函式也沒辦法知道「目的地放得下多少」。改成 `int save_model(const char *src, size_t len)`，並在函式裡和 `sizeof model` 比較，錯誤就變成一個可以處理的回傳值。

處理來自外部的長度（檔案標頭、網路封包、使用者輸入）時，還要記得第 5 章的整數溢位：`len + 1`、`width * height * 4` 這類運算本身就可能溢位，讓檢查失效。檢查要寫成不會溢位的形式，例如 `if (len >= sizeof model) return -1;`。

### 工具：讓編譯器替你找

| 工具 | 什麼時候用 | 抓得到什麼 |
|---|---|---|
| `-Wall -Wextra`，以及 GCC 的 `-Wstringop-overflow` | 每次編譯 | 編譯器能推算出的明顯越界 |
| `-D_FORTIFY_SOURCE=2`（或 3）加上 `-O1` 以上 | production build | 目的地大小已知時的越界寫入，執行時終止 |
| `-fsanitize=address`（ASan） | 測試、CI、fuzzing | stack／heap／global 越界、use-after-free，指出是哪一行 |
| `-fsanitize=undefined`（UBSan） | 測試、CI | 整數溢位、shift 量錯誤等 undefined behavior |
| 靜態分析（clang-tidy、Coverity 等） | code review 前 | 危險函式、可能的越界路徑 |

### 測試：用 fuzzing 找出你沒想到的輸入

`thumbd` 的 bug 是一個「相機型號 300 個字」的照片觸發的，這種輸入很少會出現在手寫的測試案例裡。**Fuzzing**（模糊測試）讓程式自動產生大量變形的輸入，搭配 ASan 執行，只要有任何一個輸入造成越界，ASan 就會報告。libFuzzer 與 AFL++ 是最常用的工具；處理圖片、壓縮檔、網路協定這類「解析外部資料」的程式，最值得用 fuzzing 測試。

最後，如果一個新元件需要大量解析不受信任的輸入，選擇 **記憶體安全語言**（Rust、Go、Java、Python 等）是最根本的做法：這些語言在執行時或編譯時保證陣列存取不會越界。很多組織現在的策略是：既有的 C／C++ 程式碼加強工具與測試，新的解析元件改用記憶體安全語言撰寫。

## 11.8 動手做：有界複製、ASLR 觀察與 ASan

### 程式一：有界的複製，並且知道有沒有被截斷

這段程式示範 11.7 節的寫法：用 `snprintf` 複製字串，並用它的回傳值判斷是否被截斷。`snprintf` 回傳的是「完整輸出需要的長度」，所以只要回傳值大於等於緩衝區大小，就代表被截斷了。

```c
#include <stdio.h>
#include <string.h>

/* 把 src 複製進 dst（容量 cap bytes），永遠以 '\0' 結尾。
 * 回傳 0 表示完整複製，1 表示被截斷：呼叫者必須決定截斷是否可以接受。 */
static int copy_bounded(char *dst, size_t cap, const char *src) {
    int needed = snprintf(dst, cap, "%s", src);   /* 回傳「需要的」長度，不含 '\0' */
    if (needed < 0) return -1;
    return (size_t)needed >= cap;
}

int main(void) {
    const char *inputs[] = {
        "Canon EOS R5",
        "0123456789012345678901234567890",            /* 31 個字：剛好放得下 */
        "0123456789012345678901234567890123456789",   /* 40 個字：會被截斷 */
    };
    char model[32];
    for (size_t i = 0; i < sizeof inputs / sizeof inputs[0]; i++) {
        int truncated = copy_bounded(model, sizeof model, inputs[i]);
        printf("輸入 %2zu 字 → 存入 %2zu 字，%s\n", strlen(inputs[i]), strlen(model),
               truncated ? "被截斷（應記錄或拒絕）" : "完整");
    }
    return 0;
}
```

在 macOS arm64（Apple clang 21）執行：

```text
輸入 12 字 → 存入 12 字，完整
輸入 31 字 → 存入 31 字，完整
輸入 40 字 → 存入 31 字，被截斷（應記錄或拒絕）
```

31 個字元加上 `\0` 剛好 32 bytes，所以第二筆完整；40 個字元時只存入前 31 個字，並回報截斷。對 `thumbd` 來說，相機型號被截斷只影響顯示，可以接受並記錄一筆 log；但如果是檔名或路徑，截斷可能改變意義，應該直接拒絕這張照片。這個判斷必須由呼叫者做，所以函式要把「有沒有截斷」回傳出來，而不是默默吞掉。

### 程式二：觀察 ASLR

這段程式重新執行自己兩次，每次印出程式碼、全域變數、heap 與 stack 的位址。

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static int global_counter;
static void marker(void) {}

static void show(const char *who) {
    int local = 0;
    void *heap = malloc(16);
    printf("%-6s code=%p global=%p heap=%p stack=%p\n",
           who, (void *)marker, (void *)&global_counter, heap, (void *)&local);
    free(heap);
}

int main(int argc, char **argv) {
    if (argc > 1) { show(argv[1]); return 0; }
    /* 重新執行自己兩次：每次 exec 都是全新的位址空間，ASLR 會選新的位置 */
    for (int i = 1; i <= 2; i++) {
        pid_t pid = fork();
        if (pid == 0) {
            char tag[8];
            snprintf(tag, sizeof tag, "run%d", i);
            execl(argv[0], argv[0], tag, (char *)NULL);
            _exit(127);
        }
        waitpid(pid, NULL, 0);
    }
    return 0;
}
```

在 macOS arm64 執行的一次結果（每次執行都會不同）：

```text
run1   code=0x1000945f8 global=0x10009c000 heap=0x1007a1d90 stack=0x16fd69060
run2   code=0x102e545f8 global=0x102e5c000 heap=0x103451d90 stack=0x16cfa9060
```

兩次執行的四個位址都不一樣，這就是 ASLR。注意幾個細節：

1. `code` 與 `global` 的差距在兩次執行中都是 `0x7a08`：程式本身是作為一整塊被搬動的，內部的相對位置不變。這也是為什麼 PIE 要用相對定址（第 19 章）。
2. 位址的最低幾個十六進位位數（例如 `5f8`、`060`）沒有變，因為隨機化是以 page 為單位進行的。
3. 在 Linux x86-64 上執行，stack 位址通常在 `0x7ff…` 附近、程式碼在 `0x55…` 或 `0x56…` 附近（PIE 開啟時），同樣每次不同。

### 程式三：用 ASan 抓出越界寫入

這段程式重現 `thumbd` 的 bug：長度來自檔案，沒有和目的地大小比較。因為它會被 ASan 終止、回傳非 0，所以標為不執行，下面貼的是實際編譯執行的輸出。

```c
// not-runnable
#include <stdio.h>
#include <string.h>

static void save_model(const char *src, size_t len) {
    char model[32];
    memcpy(model, src, len);         /* bug：len 來自檔案，沒有和 sizeof model 比較 */
    model[sizeof model - 1] = '\0';
    printf("model = %.10s...\n", model);
}

int main(void) {
    static char exif_model[300];     /* 模擬 EXIF 裡長度 300 的相機型號 */
    memset(exif_model, 'A', sizeof exif_model);
    save_model(exif_model, sizeof exif_model);
    return 0;
}
```

用 `cc -std=c17 -O0 -g -fsanitize=address -o overflow overflow.c` 編譯後執行（macOS arm64，節錄）：

```text
==52426==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x00016bc7cfa0 at pc 0x000104a02bb4 bp 0x00016bc7cf50 sp 0x00016bc7c700
WRITE of size 300 at 0x00016bc7cfa0 thread T0
    #0 0x000104a02bb0 in __asan_memcpy+0x330 (libclang_rt.asan_osx_dynamic.dylib:arm64e+0x3ebb0)
    #1 0x0001041809d4 in save_model overflow.c:7
    #2 0x000104180894 in main overflow.c:15

Address 0x00016bc7cfa0 is located in stack of thread T0 at offset 64 in frame
    #0 0x0001041808b4 in save_model overflow.c:5

  This frame has 1 object(s):
    [32, 64) 'model' (line 6) <== Memory access at offset 64 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow overflow.c:7 in save_model
```

逐段讀這份報告：

1. 第一行說明錯誤類型：`stack-buffer-overflow`，也就是 stack 上的陣列越界。
2. `WRITE of size 300`：一次寫入了 300 bytes。
3. 呼叫堆疊指出是 `overflow.c` 第 7 行的 `memcpy`，從 `main` 第 15 行呼叫。
4. 最後一段最有用：這個 frame 裡的 `model` 佔 offset 32 到 64，寫入超出了它的尾端。

沒有 ASan 時，同一支程式用 `-O1 -fstack-protector-strong` 編譯，在這台 macOS 上會被 fortify 版本的 `memcpy` 檢查攔下，以 SIGTRAP 結束（結束碼 133），只告訴你「出事了」，沒有行號。這就是為什麼測試與 CI 要開 ASan：它把一個模糊的當機變成一份精確到行號的報告。

## 11.9 在工作上怎麼用

### 檢查一個 binary 開了哪些防護

接手一個服務、或稽核一個第三方 binary 時，第一件事是確認它的編譯防護。Linux 上常用的檢查方式：

| 要確認什麼 | 指令（Linux） | 看什麼 |
|---|---|---|
| 是否為 PIE | `readelf -h ./thumbd \| grep Type` | `DYN`（PIE）或 `EXEC`（非 PIE） |
| stack 是否不可執行 | `readelf -lW ./thumbd \| grep GNU_STACK` | 權限欄應為 `RW`，不應有 `E` |
| 是否有 stack canary | `nm -D ./thumbd \| grep __stack_chk_fail` | 有這個符號，代表至少部分函式有 canary |
| 是否有 fortify | `nm -D ./thumbd \| grep _chk` | 出現 `__memcpy_chk`、`__strcpy_chk` 等 |
| RELRO（GOT 唯讀） | `readelf -lW ./thumbd \| grep GNU_RELRO`，以及 `readelf -d` 中的 `BIND_NOW` | 兩者都有代表 full RELRO |
| 系統是否開了 ASLR | `cat /proc/sys/kernel/randomize_va_space` | `2` 表示完整隨機化 |

上表的輸出格式依 binutils 版本略有不同；也有整合這些檢查的工具，例如 `checksec`。拾光相簿的平台團隊也在 CI 裡加了一步檢查，確保 production binary 一定帶著下面這組旗標：

```bash
# 建議的 production 編譯旗標（GCC／Clang，Linux）
CFLAGS="-O2 -D_FORTIFY_SOURCE=2 -fstack-protector-strong -fstack-clash-protection -fPIE"
LDFLAGS="-pie -Wl,-z,relro,-z,now"
```

### 處理 `stack smashing detected`

當 production 出現這個訊息，處理流程大致如下：

```text
看到 *** stack smashing detected *** 或 fortify 失敗
   │
   ├─ 1. 保留證據：core dump、觸發的輸入（請求、上傳的檔案）、版本與時間
   │
   ├─ 2. 定位：在測試環境用 ASan build 重放同一個輸入
   │      └─ ASan 會指出哪一行、哪個陣列、越界多少
   │
   ├─ 3. 評估影響：輸入是否來自不受信任的來源？能否由外部任意觸發？
   │      └─ 是 → 依公司的安全事件流程通報，優先處理
   │
   ├─ 4. 修正：加上長度檢查、改用有界 API；用同一個輸入驗證修正
   │
   └─ 5. 防止再發：
          ├─ 把這個輸入加進回歸測試與 fuzzing corpus
          └─ grep 整個 codebase 找同樣的寫法（strcpy、sprintf、未檢查的 memcpy 長度）
```

`thumbd` 最後的處理：老周在 EXIF 解析的入口加上每個欄位的長度上限；小安用 `grep -rn "strcpy\|sprintf" src/` 找出另外 7 個類似的地方，一起改成有界的寫法；團隊再把 EXIF 解析器接上 libFuzzer，在 CI 裡每天跑 30 分鐘。

### Code review 時要注意什麼

審查 C／C++ 的變更時，看到以下寫法要停下來確認：

- 任何寫入陣列的操作，長度來自哪裡？有沒有和目的地大小比較？
- 長度的計算（加法、乘法）會不會溢位？比較時有沒有 signed／unsigned 混用（第 4 章）？
- 用了 VLA 或 `alloca`，長度有沒有上限？
- 新增的解析器（檔案格式、網路協定）有沒有對應的 fuzz target？

## 11.10 常見錯誤與除錯

| 症狀 | 常見原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| `*** stack smashing detected ***` | stack 陣列被連續越界寫入 | 用 ASan build 重放同一個輸入 | 加上長度檢查，改用有界 API |
| `*** buffer overflow detected ***` | `_FORTIFY_SOURCE` 的檢查失敗 | core dump 的 backtrace 會停在 `__*_chk` | 同上，找出寫入的長度來源 |
| 當機位置離 bug 很遠，變數值莫名其妙 | 越界寫入改到 saved 暫存器或別的 local 變數，之後才被使用 | ASan；或在 gdb 對可疑變數設 watchpoint | 找出真正的寫入點，而不是修當機的地方 |
| 處理大圖片時 segfault，backtrace 很短 | VLA 或 `alloca` 用了過大的長度，超過 thread stack | 看 `%rsp` 是否落在 guard page；檢查長度來源 | 限制長度，大緩衝區改用 heap |
| 只在 production 出事，測試環境正常 | 最佳化等級、編譯旗標或輸入不同 | 用 production 的旗標建一個 ASan 版本重現 | 在 CI 中跑 ASan 測試與 fuzzing |
| 改用 `strncpy` 後字串印出亂碼 | 來源太長時 `strncpy` 不補 `\0` | 印出最後一個 byte | 改用 `snprintf` 或手動補 `\0` |

## 本章重點整理

- C 的陣列存取不檢查邊界，越界存取是 undefined behavior，實際結果是讀寫到記憶體中剛好排在旁邊的東西。
- stack 往低位址成長，陣列索引往高位址走，所以 local 陣列的越界寫入會依序改到 saved 暫存器與 return address。
- `retq` 不驗證 return address，這是 stack 越界寫入被列為高風險的原因。
- stack canary 在陣列與控制資料之間放一個隨機值，函式 return 前檢查；它只偵測 stack 上的連續越界寫入，無法偵測 heap、越界讀取或跳過 canary 的寫入。
- `stack smashing detected` 代表確定發生了越界寫入並被及時終止，bug 本身仍必須修正。
- NX 讓資料頁不可執行，ASLR 與 PIE 讓每次執行的記憶體配置不同；它們與 canary、fortify 共同構成縱深防禦。
- 較新的硬體機制（CET 的 shadow stack、ARM64 的 PAC）讓控制資料被修改這件事能被硬體偵測。
- VLA 的 frame 大小在執行時才決定，需要 frame pointer；來自外部的長度必須有上限，大緩衝區應改用 heap。
- 避免 `gets`、`strcpy`、`sprintf` 等不知道目的地大小的函式；長度永遠和指標一起傳遞，並注意長度計算本身的整數溢位。
- `snprintf` 的回傳值可以用來判斷截斷，截斷是否可接受要由呼叫者決定。
- ASan 能把模糊的當機變成精確到行號的報告；fuzzing 搭配 ASan 是找出解析器越界問題最有效的方法。
- 工作上要在 CI 中確認 production binary 帶有 PIE、NX、canary、fortify、RELRO 等防護，並把觸發過問題的輸入加進回歸測試。

## 延伸問答

> [!question]- Q1. 為什麼 stack 上的越界寫入比 heap 上的越界寫入更常被拿來討論？
> 因為 stack 上，緊鄰 local 陣列的就是 saved 暫存器與 return address 這類「控制程式下一步去哪裡」的資料，而且它們的相對位置由編譯器固定決定（11.3 節可以精確算出差幾個 byte）。`retq` 又完全不驗證讀出的值，所以 stack 越界寫入直接威脅到控制流程。
>
> heap 越界一樣嚴重，只是後果比較間接：通常會改壞相鄰物件或 allocator 的 metadata，等到之後的 `free` 或使用時才出問題（第 25、26 章）。兩者都要修，只是 stack 越界有 canary 這類專門的偵測，heap 越界主要靠 ASan 與 allocator 的完整性檢查。

> [!question]- Q2. 手算：`char buf[32]` 加上 `-fstack-protector-strong`，11.4 節的組合語言中 frame 為什麼是 48 bytes 而不是 40？
> 陣列 32 bytes 加上 8 bytes 的 canary 是 40 bytes。但 x86-64 System V ABI 要求在 `call` 之前 `%rsp` 必須 16-byte 對齊。進入函式時 `call` 已經 push 了 8 bytes 的 return address，函式又 `pushq %rbx` 了 8 bytes，所以此時 `%rsp` 剛好又是 16 的倍數；接下來配置的空間也必須是 16 的倍數，才能讓函式內部呼叫 `strcpy` 時仍然對齊。
>
> 40 向上取整到 16 的倍數是 48，所以 `subq $48, %rsp`。canary 放在 `40(%rsp)`，`32(%rsp)` 到 `39(%rsp)` 是對齊產生的空間。

> [!question]- Q3. 程式開了 stack canary，為什麼還需要 ASan？
> 兩者目的不同。canary 是 production 用的低成本偵測：它只在函式 return 時檢查一個值，只能發現「從 stack 陣列往上的連續越界寫入」，而且發現時已經寫完了，只能終止程式，也不會告訴你是哪一行。
>
> ASan 是測試用的高精度工具：它在每一次記憶體存取前檢查邊界與生命週期，涵蓋 stack、heap、global、use-after-free，並在第一次越界的那一刻就報告確切的行號與陣列。代價是約兩倍的速度與數倍的記憶體，所以通常用在測試、CI 與 fuzzing，而不是直接放在 production。

> [!question]- Q4. 看到 `stack smashing detected` 時，可以把它當成「已經被擋住了，不嚴重」嗎？
> 不行。這個訊息代表兩件事：一是程式中確定存在 stack 越界寫入的 bug；二是這一次在 return 前被偵測到並終止了。它不代表所有路徑都會被偵測到：越界可能只改到 canary 下方的其他 local 變數，或以不連續的方式寫入，這些 canary 都看不到。
>
> 而且，只要觸發輸入來自外部（例如使用者上傳的圖片），任何人都可以反覆觸發，讓服務不斷重啟，本身就是可用性問題。正確做法是保留觸發輸入、用 ASan 定位、修正、加入回歸測試，並依輸入來源評估是否需要走安全事件流程。

> [!question]- Q5. `strncpy(dst, src, sizeof dst)` 為什麼不是安全的 `strcpy`？
> `strncpy` 的設計原本是用來處理固定寬度、不一定以 `\0` 結尾的欄位。當 `src` 的長度大於等於 `n` 時，它會複製剛好 `n` 個字元，**不會補 `\0`**，`dst` 就變成一個沒有結尾的字串，之後的 `printf`、`strlen` 會繼續往後讀，造成越界讀取。另外當 `src` 很短時，它會用 `\0` 填滿整個剩餘空間，對大緩衝區有不必要的成本。
>
> 比較好的替代是 `snprintf(dst, sizeof dst, "%s", src)`，它永遠以 `\0` 結尾，並回傳完整長度讓你判斷截斷；或先檢查 `strlen(src) < sizeof dst` 再 `memcpy`。

> [!question]- Q6. 為什麼 Linux kernel 禁止使用 VLA？一般應用程式也該禁止嗎？
> kernel 的 stack 很小（x86-64 Linux 上每個 thread 的 kernel stack 是 16 KiB），而且 kernel 裡 stack 溢位的後果是整台機器當機或記憶體損壞。VLA 讓 frame 大小取決於執行時的值，難以在編譯時保證不超過 stack；此外 VLA 也讓編譯器產生較複雜的程式碼。所以 kernel 社群移除了所有 VLA。
>
> 一般應用程式不一定要全面禁止，但規則相同：只要長度可能來自外部或可能很大，就不該放在 stack 上。常見的做法是設一個合理上限（例如 4 KiB 以下才用 stack，否則用 `malloc`），或直接在 coding standard 中禁止 VLA，並用 `-Wvla` 讓編譯器警告。

> [!question]- Q7. ASLR 開啟後，為什麼程式二輸出的 `code` 與 `global` 差距在兩次執行中完全相同？
> ASLR 隨機化的是每個「區域」的起始位置，而不是區域內部的配置。整個執行檔（程式碼、資料、bss）是作為一個整體被載入到隨機的基底位址，內部各段之間的相對距離在連結時就決定了。所以 `marker` 函式與 `global_counter` 之間的距離永遠一樣，只是整塊的位置每次不同。
>
> 這正是 PIE 能運作的原因：程式碼用相對於目前指令位置的方式（PC-relative addressing）存取全域變數，不需要知道絕對位址（第 19 章）。反過來說，這也表示只要知道其中一個位址，就能推算同一區域內的其他位址，所以避免洩漏位址（例如在錯誤訊息中印出指標）也是安全實務的一部分。

> [!question]- Q8. 面試題：如果要你為一個用 C 寫的圖片解析服務降低記憶體安全風險，你會怎麼規劃？
> 可以分成三層回答。第一層是寫法：解析外部資料的每一個長度都先檢查上限、長度與指標一起傳遞、禁用 `gets`／`strcpy`／`sprintf`、注意長度計算的整數溢位、禁止使用來自外部長度的 VLA。第二層是工具與測試：CI 中以 ASan 與 UBSan 執行所有測試；為每個檔案格式的解析器寫 fuzz target，持續用 libFuzzer 或 AFL++ 執行；production build 開啟 `_FORTIFY_SOURCE`、stack protector、PIE、full RELRO，並在 CI 驗證。
>
> 第三層是架構：把解析器放在權限最小的獨立 process（沙箱）中，即使出問題也限制影響範圍；長期則評估用記憶體安全語言（例如 Rust）重寫最常處理不受信任輸入的元件。能說出「預防、偵測、隔離、長期替換」這幾個層次，代表你理解這不是單一技巧能解決的問題。
