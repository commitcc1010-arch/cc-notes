# 第 7 章　從 C 到組合語言：x86-64 基礎

> [!abstract] 本章地圖
> **核心問題**：編譯器把 C 程式翻譯成什麼樣的指令？當手上只有一行組合語言和一堆暫存器的值時，要怎麼讀懂程式剛才在做什麼？
>
> **你會學到**：

## 7.1 故事：只剩一行組合語言的 segfault

週五晚上，`thumbd` 在 production 當了三次。SRE 阿哲把 core dump 抓下來交給小安。`thumbd` 的 release build 是 `-O2` 編譯、沒有附 debug 資訊，所以 gdb 只能告訴小安這些（Linux x86-64 上的示意輸出）：

```text
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x000055d1c6a4b1f1 in get_gray ()
(gdb) x/i $pc
=> 0x55d1c6a4b1f1 <get_gray+17>:   movzbl (%rax,%rcx,1),%eax
(gdb) info registers rax rcx rsi
rax            0xffffffff          4294967295
rcx            0x7f3c2a400c80      139896383605888
rsi            0xffffffff          4294967295
```

`get_gray` 是一個很短的函式：從灰階影像中讀出座標 `(x, y)` 的像素。小安看著那行 `movzbl (%rax,%rcx,1),%eax`，完全不知道從何下手：括號、逗號、百分號是什麼意思？`%rax` 和 `%eax` 是同一個東西嗎？為什麼 `rax` 剛好是 `0xffffffff`？

老周看了十秒就說：「`x` 被當成無號的 4294967295 了。上禮拜是不是有人把 `x` 的型別改成 `uint32_t`？」小安去翻 git log，真的有。

老周不是通靈。他知道這行指令在算「`%rcx` 加上 `%rax`，到那個位址讀一個 byte」，知道 `%rcx` 看起來像是某一列像素的起點，也知道一個 32 位元的 `-1` 在被「補零」延伸成 64 位元時，會變成 `0x00000000ffffffff`，而不是 `-1`。這三件事加起來，就是本章的內容：組合語言的格式、暫存器、addressing mode 與資料搬移指令。7.13 節會帶著這些知識回來，把這次當機完整解開。

## 7.2 ISA：軟體和硬體之間的合約

寫 Python 或 Java 時，我們很少問「CPU 實際上執行了什麼」。但 CPU 不懂 C，也不懂 Python，它只懂一種非常簡單的語言：一連串編碼成 bytes 的**指令**（instruction），每條指令做一件小事，例如「把兩個數加起來」「從記憶體讀 8 個 bytes」「如果上一次比較的結果是小於，就跳到某個位址」。

哪些指令存在、每條指令的編碼與行為、CPU 有哪些可以讓程式看見的狀態，這整套規定叫做 **ISA**（instruction set architecture，指令集架構）。ISA 是軟體和硬體之間的合約：編譯器只要產生符合 ISA 的指令，任何實作這份 ISA 的 CPU 都必須給出相同的結果。例如一支 2010 年為 x86-64 編譯的程式，今天在最新的 Intel 或 AMD 處理器上仍然能跑，因為它們實作的是同一份 ISA。

合約之下的實作細節叫 **微架構**（microarchitecture）：pipeline 有幾級、一個 cycle 能同時執行幾條指令、cache 多大、分支預測器怎麼設計。這些每一代都在變，但都藏在 ISA 底下，程式看不見（只看得到速度的差別）。第 12、13 章會往下看微架構；這一章和第 8 到 11 章都站在 ISA 這一層。

| 層次 | 定義了什麼 | 誰會在意 | 例子 |
|---|---|---|---|
| 程式語言 | 變數、型別、函式、迴圈 | 所有程式設計師 | C、Rust、Go |
| ISA | 指令、暫存器、記憶體模型、指令編碼 | 編譯器、作業系統、除錯器、安全研究 | x86-64、ARM64（AArch64）、RISC-V |
| 微架構 | pipeline、cache、分支預測、執行單元數量 | 效能工程、CPU 設計者 | Intel 的 Golden Cove、Apple 的 M 系列核心 |

### 程式看得見的機器狀態

在 C 裡，我們看得到變數、陣列、struct。在 ISA 這一層，程式看得見的只有下面幾樣東西：

```text
 CPU 內部（程式看得見的部分）                    記憶體（從程式角度看）
 ┌────────────────────────────────────┐        ┌────────────────────────┐
 │ %rip：下一條要執行的指令位址        │        │ 一個巨大的 byte 陣列   │
 │       （program counter，PC）       │        │ 位址 0 … 2^48 − 1      │
 ├────────────────────────────────────┤ 位址   │                        │
 │ 16 個 64-bit 通用暫存器             │ ─────▶ │  程式碼（指令本身）    │
 │ %rax %rbx %rcx %rdx %rsi %rdi       │        │  全域變數              │
 │ %rbp %rsp %r8 … %r15                │ ◀───── │  heap                  │
 ├────────────────────────────────────┤ 資料   │  stack                 │
 │ condition codes（CF ZF SF OF…）     │        │                        │
 │ 最近一次運算的結果特徵，第 8 章     │        └────────────────────────┘
 ├────────────────────────────────────┤
 │ 向量暫存器 %xmm0…（浮點數與 SIMD） │
 └────────────────────────────────────┘
```

從上到下看：**`%rip`** 記錄下一條要執行的指令在哪裡，CPU 不斷「讀出 `%rip` 指向的指令、執行、更新 `%rip`」，這就是程式在跑。**通用暫存器**（general-purpose register）是 CPU 內部 16 個 8-byte 的小格子，存取幾乎不花時間，是所有計算的工作區。**Condition codes** 記錄上一個算術運算的結果是不是零、是不是負的、有沒有溢位，是 `if` 和迴圈的基礎，第 8 章會專門講。**向量暫存器**用來做浮點運算與一次處理多筆資料的 SIMD 指令（第 14 章）。

記憶體則是一個以 byte 為單位編號的大陣列。x86-64 的位址暫存器是 64 位元，但目前的處理器實際只使用 48 位元（新款支援 57 位元）的虛擬位址，所以圖中寫成 2^48。這裡的位址是虛擬位址，第 23 章會講它怎麼翻譯成實體位址；在這一章，把它當成「一個很大的陣列」就夠了。

最值得注意的是**少了什麼**：沒有型別、沒有變數名稱、沒有陣列邊界、沒有 struct。`int`、`long`、指標，在這一層都只是「幾個 bytes 的資料」，差別只在於編譯器選了哪一條指令去處理它。這就是為什麼讀組合語言時，要從指令反推型別，而這也是 7.7 節的重點。

### x86-64 從哪裡來

x86-64 這個名字背後有一段歷史，理解它可以解釋很多奇怪的命名。1978 年的 Intel 8086 是 16-bit 處理器，暫存器叫 `ax`、`bx`；1985 年的 i386 擴充成 32-bit，暫存器加上字首 e（extended），變成 `eax`、`ebx`，這一代的 ISA 叫 IA32；AMD 設計了 64-bit 擴充 AMD64，並在 2003 年推出第一顆支援它的處理器，暫存器再加上字首 r，變成 `rax`、`rbx`，並多了 `r8` 到 `r15` 八個新暫存器。Intel 後來也採用了這套設計，業界統稱為 **x86-64**。

因為每一代都要相容上一代，x86-64 至今仍能執行 16-bit 與 32-bit 的指令，指令長度從 1 到 15 bytes 不等，格式非常複雜。這種「指令多、格式複雜、一條指令可以同時讀記憶體並計算」的風格叫 **CISC**（complex instruction set computer）。相對地，ARM64 與 RISC-V 屬於 **RISC**（reduced instruction set computer）：指令一律 4 bytes、只有 load／store 指令能存取記憶體。7.11 節會對照兩者。

## 7.3 看見組合語言：`-S`、`objdump -d` 與跨平台產生

組合語言（assembly language）是機器碼的文字版：一行對應一條指令，用人看得懂的助記符（mnemonic，例如 `addq`）取代 bytes。它和機器碼幾乎是一對一的，所以讀組合語言就等於讀 CPU 實際執行的東西。

第 1 章講過，`gcc` 和 `clang` 把 C 變成執行檔要經過四個階段。其中「compile」這一步的產物就是組合語言，用 `-S` 可以讓編譯器停在這裡：

```text
 thumb.c ──(preprocess)──▶ thumb.i ──(compile, -S)──▶ thumb.s ──(assemble, -c)──▶ thumb.o ──(link)──▶ thumbd
  C 原始碼                  展開巨集                   組合語言文字              機器碼 + 符號      執行檔
                                                        ▲                          ▲
                                                 gcc -S 停在這裡          objdump -d 把它反組譯回文字
```

圖中有兩個「看組合語言」的入口。用 `-S` 看的是**編譯器的輸出**，保留了標籤名稱與編譯器的註解，最好讀；用 `objdump -d` 看的是**反組譯**（disassemble）的結果，它從目的檔或執行檔的 bytes 解碼回文字，會同時列出每條指令的位址與機器碼。當你手上只有 production 的執行檔或 core dump 時，只能用後者。

### 在任何機器上產生 x86-64 組合語言

`gcc -S` 預設產生的是「這台機器」的組合語言。在 Apple Silicon 的 Mac 上，你會得到 ARM64 的指令，不是本書要讀的 x86-64。好消息是 clang 是一個跨平台編譯器，加上 `-target` 就能為別的架構產生程式碼，不需要真的有那台機器：

```bash
# 產生 x86-64 Linux 的組合語言，印到螢幕上
clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - add3.c

# 產生 x86-64 的目的檔，再反組譯
clang -target x86_64-linux-gnu -O1 -c add3.c -o add3.o
objdump -d add3.o
```

本書所有 x86-64 組合語言都用第一行指令產生。`-O1` 打開基本最佳化，讓輸出接近真實程式碼又不會太難讀；`-fno-asynchronous-unwind-tables` 去掉一堆給例外處理與除錯器用的 `.cfi_` 指示。在 Linux x86-64 上，直接用 `gcc -O1 -S file.c` 也可以，輸出的風格略有不同，但指令的意義一樣。另一個好用的選擇是 Compiler Explorer（godbolt）這個網站，可以即時對照不同編譯器與最佳化等級的輸出。

拿最簡單的例子試試：

```c
long add3(long a, long b, long c) { return a + b + c; }
```

以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生（刪去 `.file`、`.p2align` 等與理解無關的 directive）：

```asm
	.text
	.globl	add3
	.type	add3,@function
add3:
	leaq	(%rdi,%rsi), %rax
	addq	%rdx, %rax
	retq
```

以 `.` 開頭的行是 **directive**（組譯器指示），不是指令：`.text` 表示接下來的東西放在程式碼區段，`.globl add3` 讓 `add3` 這個名稱可以被其他檔案連結到（第 18 章）。`add3:` 是**標籤**（label），代表下一條指令的位址。真正的指令只有三條：第一條把 `a + b` 算進 `%rax`（7.9 節會解釋為什麼用 `leaq`），第二條加上 `c`，第三條 `retq` 返回呼叫者。

參數在哪裡？依照 x86-64 Linux 的 **calling convention**（呼叫慣例，第 9 章），前三個整數參數放在 `%rdi`、`%rsi`、`%rdx`，回傳值放在 `%rax`。所以 `a`、`b`、`c` 一進函式就已經在暫存器裡，不用從記憶體讀。

再用 `objdump -d` 看同一個函式的機器碼：

```text
0000000000000000 <add3>:
       0: 48 8d 04 37                   leaq    (%rdi,%rsi), %rax
       4: 48 01 d0                      addq    %rdx, %rax
       7: c3                            retq
```

最左邊是位址（目的檔還沒連結，所以從 0 開始），中間是機器碼，右邊是解碼後的指令。三條指令分別佔 4、3、1 個 bytes，這就是 x86-64 的「變長編碼」。CPU 讀到 `c3` 就知道這是 `ret`，讀到 `48` 開頭就知道後面跟著一條 64-bit 運算的指令。

> [!note] 為什麼不用 `-O0`？
> 很多教學用 `-O0`（不最佳化）是因為它和原始碼一一對應，但它會把每個變數都存進 stack 再讀回來。同一個 `add3` 在 `-O0` 下有 10 條指令，其中 6 條會存取 stack 上的參數副本（3 條存進去、3 條讀出來）。production 的程式都是最佳化過的，讀 `-O1`／`-O2` 的輸出才是工作上會遇到的樣子。

## 7.4 AT&T 與 Intel 語法

同一條機器指令有兩種常見的文字寫法。Linux 的工具（GCC、GNU binutils、gdb）預設用 **AT&T 語法**；Intel 的手冊、Windows 的工具和很多逆向工程工具用 **Intel 語法**。本書使用 AT&T 語法，因為那是你在 Linux 上用 `gcc -S`、`objdump`、gdb 預設會看到的。

下面三條指令取自 7.10 節會完整讀懂的 `get_gray` 函式，左邊是預設的 AT&T 輸出，右邊是同一個檔案加上 `-masm=intel` 產生的結果：

```text
AT&T（本書）                          Intel
movslq  8(%rdi), %rcx                 movsxd  rcx, dword ptr [rdi + 8]
addq    16(%rdi), %rcx                add     rcx, qword ptr [rdi + 16]
movzbl  (%rax,%rcx), %eax             movzx   eax, byte ptr [rax + rcx]
```

| 差異 | AT&T | Intel | 讀的時候要注意 |
|---|---|---|---|
| 運算元順序 | `指令 來源, 目的` | `指令 目的, 來源` | 最容易搞錯的一點：`subq %rsi, %rdi` 是 `rdi = rdi − rsi` |
| 暫存器 | 加 `%`：`%rax` | 不加：`rax` | — |
| 立即數（常數） | 加 `$`：`$16` | 不加：`16` | AT&T 中沒有 `$` 的數字代表**記憶體位址** |
| 記憶體運算元 | `16(%rdi,%rcx,8)` | `[rdi + rcx*8 + 16]` | Intel 寫法比較直觀，兩者意義相同 |
| 運算大小 | 指令後綴：`movq`、`movl`、`movb` | 運算元前加 `qword ptr`、`dword ptr`、`byte ptr` | 當暫存器已決定大小時，兩者都可省略 |

在 gdb 裡可以用 `set disassembly-flavor intel` 切換，`objdump` 用 `-M intel`。建議選一種當作主要的閱讀習慣，遇到另一種時只要先確認「誰是目的」就不會讀錯。

## 7.5 暫存器：16 個 64-bit 的工作區

x86-64 有 16 個通用暫存器，每個 64 bits。因為歷史相容的關係，每個暫存器的低 32、16、8 位元都有自己的名字，可以單獨存取：

```text
 位元  63                    32 31          16 15     8 7      0
      ┌────────────────────────┬──────────────┬────────┬────────┐
 %rax │                        │              │  %ah   │  %al   │
      └────────────────────────┴──────────────┴────────┴────────┘
                               └────────── %eax（低 32 bits）───┘
                                              └──── %ax（低 16）┘
                                                       └─ %al ─┘（低 8）

 %r8  ┌────────────────────────┬──────────────┬─────────────────┐
      │                        │              │      %r8b       │
      └────────────────────────┴──────────────┴─────────────────┘
                               └────── %r8d ──┘   %r8w = 低 16 bits
```

讀這張圖的方式是：`%al`、`%ax`、`%eax`、`%rax` 不是四個暫存器，而是**同一個暫存器的四種寬度**。寫入 `%al` 就是改 `%rax` 的最低 8 位元。新的 `%r8`–`%r15` 用後綴表示寬度：`d`（double word，32）、`w`（word，16）、`b`（byte，8）。`%ah` 是 8086 時代留下來的「第 8 到 15 位元」，只有 `%rax`、`%rbx`、`%rcx`、`%rdx` 有，現代編譯器很少用到。

| 64-bit | 32-bit | 16-bit | 8-bit | Linux x86-64 呼叫慣例中的角色（第 9 章） |
|---|---|---|---|---|
| `%rax` | `%eax` | `%ax` | `%al` | 回傳值；乘除法的隱含運算元（第 8 章） |
| `%rbx` | `%ebx` | `%bx` | `%bl` | callee-saved |
| `%rcx` | `%ecx` | `%cx` | `%cl` | 第 4 個參數；shift 的位移量 |
| `%rdx` | `%edx` | `%dx` | `%dl` | 第 3 個參數；乘除法的高半部 |
| `%rsi` | `%esi` | `%si` | `%sil` | 第 2 個參數 |
| `%rdi` | `%edi` | `%di` | `%dil` | 第 1 個參數 |
| `%rbp` | `%ebp` | `%bp` | `%bpl` | callee-saved；有時當 frame pointer |
| `%rsp` | `%esp` | `%sp` | `%spl` | stack pointer，永遠指向 stack 頂端 |
| `%r8` | `%r8d` | `%r8w` | `%r8b` | 第 5 個參數 |
| `%r9` | `%r9d` | `%r9w` | `%r9b` | 第 6 個參數 |
| `%r10`、`%r11` | `%r10d`… | `%r10w`… | `%r10b`… | caller-saved 的暫存用 |
| `%r12`–`%r15` | `%r12d`… | `%r12w`… | `%r12b`… | callee-saved |

這張表現在不必背。先記住三件事：前幾個參數依序在 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`；回傳值在 `%rax`；`%rsp` 是 stack pointer，不拿來做一般計算。**callee-saved**（被呼叫者保存）的意思是「函式如果要用這個暫存器，返回前必須還原原值」，**caller-saved** 則是「呼叫別的函式之後，這個暫存器的值可能被改掉」。第 9 章會完整說明這套規則。

### 最重要的寬度規則：寫 32 位元會清掉高 32 位元

寫入子暫存器時，其他位元會怎樣？x86-64 的規則不對稱，而且是讀組合語言時最常卡住的地方：

| 寫入的目的 | 其他位元 | 例子（`%rax` 原本是 `0x1122334455667788`） |
|---|---|---|
| 8-bit（`%al`） | 保留 | `movb $0xAA, %al` → `0x11223344556677AA` |
| 16-bit（`%ax`） | 保留 | `movw $0xBBBB, %ax` → `0x112233445566BBBB` |
| 32-bit（`%eax`） | **高 32 位元清為 0** | `movl $0xCCCCCCCC, %eax` → `0x00000000CCCCCCCC` |
| 64-bit（`%rax`） | 整個覆寫 | `movq $-1, %rax` → `0xFFFFFFFFFFFFFFFF` |

為什麼 32-bit 這麼特別？常見的解釋是：如果寫 `%eax` 時保留高 32 位元，CPU 就必須把新舊兩個值合併，這讓 out-of-order 執行（第 13 章）多了一個不必要的相依關係；直接清零可以讓每次寫入都是一個「全新的值」。8-bit 與 16-bit 則為了相容舊程式維持原樣。

這條規則有兩個直接的後果。第一，編譯器處理 `unsigned int` 時可以直接用 32-bit 指令，結果自動是正確的 64-bit 無號值，不需要額外的延伸指令。第二，你會常常看到 `xorl %eax, %eax` 這種寫法：它把 `%eax` 和自己做 XOR 得到 0，同時清掉高 32 位元，等於把整個 `%rax` 歸零，而且編碼比 `movq $0, %rax` 短。

## 7.6 Operand 與 addressing mode

大部分指令有一或兩個 **operand**（運算元）：要處理的資料從哪裡來、結果放到哪裡。x86-64 的 operand 只有三種：

1. **立即數**（immediate）：寫死在指令裡的常數，AT&T 語法用 `$` 開頭，例如 `$16`、`$-1`、`$0xFF`。
2. **暫存器**：例如 `%rdi`、`%eax`，代表暫存器裡的值。
3. **記憶體**：一個由公式算出來的位址，代表「那個位址上的資料」。

第三種是讀組合語言的關鍵。x86-64 的記憶體 operand 最完整的形式是：

```text
            Imm(rb, ri, s)
             │   │   │   └─ scale：只能是 1、2、4、8
             │   │   └───── index 暫存器
             │   └───────── base 暫存器
             └───────────── displacement：常數位移

 有效位址（effective address）= Imm + R[rb] + R[ri] × s
```

這個公式不是隨便設計的，它剛好對應 C 最常見的存取模式：`rb` 是陣列或 struct 的起點，`ri` 是索引，`s` 是元素大小（`char`、`short`、`int`、`long` 分別是 1、2、4、8），`Imm` 是 struct 欄位的位移。所以 `a[i]`（`long` 陣列）是 `(%rdi,%rsi,8)`，`p->data`（`data` 在位移 16）是 `16(%rdi)`。

四個部分都可以省略（但至少要有一個），於是產生各種形式。下面用 `%rdi = 0x1000`、`%rcx = 3`，並假設記憶體位址 `0x1000` 開始存著一些資料，逐一手算：

| 形式 | 名稱 | 有效位址的算法 | 手算結果 | 典型的 C |
|---|---|---|---|---|
| `$0x10` | 立即數 | 不是位址，就是值 16 | 值 0x10 | 常數 `16` |
| `%rdi` | 暫存器 | 不是位址，就是暫存器的值 | 值 0x1000 | 區域變數 `p` |
| `0x1000` | 絕對位址 | Imm | 0x1000 | 很少見 |
| `(%rdi)` | 間接 | R[rdi] | 0x1000 | `*p` |
| `16(%rdi)` | base + displacement | 16 + R[rdi] | 0x1010 | `p->data` |
| `(%rdi,%rcx)` | base + index | R[rdi] + R[rcx] | 0x1003 | `buf[i]`（`char`） |
| `(%rdi,%rcx,8)` | scaled index | R[rdi] + R[rcx]×8 | 0x1018 | `a[i]`（`long`） |
| `16(%rdi,%rcx,8)` | 完整形式 | 16 + R[rdi] + R[rcx]×8 | 0x1028 | `a[i + 2]` |
| `(,%rcx,4)` | 只有 index | R[rcx]×4 | 0xC | 少見，常配合 `lea` |
| `name(%rip)` | RIP-relative | 下一條指令位址 + 位移 | 由連結器決定 | 全域變數 |

逐步看最後一個完整形式：`16 + 0x1000 + 3 × 8 = 16 + 4096 + 24 = 4136 = 0x1028`。如果這是 `long *a = 0x1000`，那麼 0x1028 正好是 `a[5]` 的位址，也就是 C 裡的 `a[i + 2]`（`i = 3`）：編譯器把 `+2` 乘上 8 得到 16，放進了 displacement。

最後一列的 **RIP-relative**（相對於 `%rip` 的定址）是 x86-64 新增的形式：全域變數的位址寫成「距離目前指令多遠」。這樣程式被載入到任何位址都不用修改指令，是 position-independent code 的基礎（第 19 章）。在組合語言中你會看到 `clipped_count(%rip)` 這種寫法，意思是「`clipped_count` 這個全域變數」。

> [!warning] 常見誤解
> 「括號就是讀記憶體。」大多數指令確實如此：`movq 16(%rdi), %rax` 會讀出位址 `R[rdi] + 16` 上的 8 個 bytes。但 `leaq 16(%rdi), %rax` 只計算位址 `R[rdi] + 16` 本身，完全不碰記憶體，這是 7.9 節的主題。另外，scale 只能是 1、2、4、8；遇到 24-byte 的 struct 陣列，編譯器會先用其他指令把索引乘以 3，再用 scale 8。

## 7.7 資料搬移：`mov` 家族

`mov` 是最常見的指令，它把資料從來源複製到目的：`movq %rdi, %rax` 是「`%rax = %rdi`」，`movq (%rdi), %rax` 是「`%rax = *(long *)rdi`」，`movq %rax, 8(%rsi)` 是「`*(long *)(rsi + 8) = rax`」。

指令最後一個字母是**大小後綴**，表示一次搬幾個 bytes。名稱來自 16-bit 時代：當時一個「word」是 16 bits，所以 32 bits 叫 double word，64 bits 叫 quad word。

| 後綴 | 名稱 | 大小 | C 型別（LP64） | 例子 |
|---|---|---|---|---|
| `b` | byte | 1 byte | `char`、`uint8_t` | `movb %sil, (%rdi)` |
| `w` | word | 2 bytes | `short`、`uint16_t` | `movw %si, (%rdi)` |
| `l` | long（double word） | 4 bytes | `int`、`uint32_t`、`float` 以外的 4-byte 整數 | `movl (%rdi), %eax` |
| `q` | quad word | 8 bytes | `long`、指標、`size_t` | `movq %rax, 8(%rsi)` |

注意 AT&T 的 `l` 是 4 bytes，和 C 的 `long`（LP64 上是 8 bytes）不一樣，這是歷史名稱造成的混淆。

`mov` 有兩個限制：**目的不能是立即數**（不能寫入一個常數），**來源和目的不能同時是記憶體**。要把一個記憶體位置複製到另一個，必須先讀進暫存器再寫出去。另外，大多數指令的立即數最多 32 bits（會被 sign-extend 成 64 bits）；需要完整 64-bit 常數時，編譯器會用特殊的 `movabsq`。

用 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 編譯下面幾個小函式，看編譯器怎麼依照型別選指令：

```c
#include <stdint.h>
void  store_u8(uint8_t *dst, long v)   { *dst = (uint8_t)v; }
void  store_u16(uint16_t *dst, long v) { *dst = (uint16_t)v; }
long  big_const(void)                  { return 0x123456789abcLL; }
uint32_t replace_pixel(uint32_t *px, uint32_t new_px) {
    uint32_t old = *px;
    *px = new_px;
    return old;
}
```

```asm
store_u8:
	movb	%sil, (%rdi)
	retq
store_u16:
	movw	%si, (%rdi)
	retq
big_const:
	movabsq	$20015998343868, %rax           # imm = 0x123456789ABC
	retq
replace_pixel:
	movl	(%rdi), %eax
	movl	%esi, (%rdi)
	retq
```

`store_u8` 只把第二個參數的最低 byte（`%sil`）寫進記憶體：C 的 `(uint8_t)v` 截斷在這裡完全不需要額外指令，只要選一個比較窄的暫存器名稱就好。`big_const` 的常數超過 32 bits，只能用 `movabsq`。`replace_pixel` 是「讀出舊像素、寫入新像素、回傳舊值」：第一條 `movl (%rdi), %eax` 把 `*px` 讀進回傳值暫存器，第二條把 `new_px`（在 `%esi`）寫回 `*px`。兩條都用 `l`，因為像素是 4-byte 的 `uint32_t`。

> [!tip] 括號就是暫存器與記憶體的分界
> `replace_pixel` 的兩條指令只差在括號的位置：`movl (%rdi), %eax` 是「讀記憶體到暫存器」，`movl %esi, (%rdi)` 是「寫暫存器到記憶體」。讀組合語言時，括號有沒有出現、出現在哪一邊，就決定了資料的流向，一個字元都不能看漏。

### 變寬：`movz` 與 `movs`

把較窄的值放進較寬的暫存器時，多出來的高位元要填什麼？第 4 章講過兩種方式：無號數用 **zero extension**（補 0），有號數用 **sign extension**（複製最高位元）。x86-64 用兩組指令對應：

- `movz` 系列：`movzbw`、`movzbl`、`movzwl`、`movzbq`、`movzwq`，第一個後綴是來源大小，第二個是目的大小。
- `movs` 系列：`movsbw`、`movsbl`、`movswl`、`movsbq`、`movswq`、`movslq`。另有 `cltq`，等於 `movslq %eax, %rax` 的短編碼。

```c
#include <stdint.h>
long  load_s8(const int8_t *p)            { return *p; }
unsigned long load_u8(const uint8_t *p)   { return *p; }
long  load_s32(const int32_t *p)          { return *p; }
unsigned long load_u32(const uint32_t *p) { return *p; }
```

四個載入函式的輸出（同樣以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生，只保留指令）：

```asm
load_s8:
	movsbq	(%rdi), %rax
	retq
load_u8:
	movzbl	(%rdi), %eax
	retq
load_s32:
	movslq	(%rdi), %rax
	retq
load_u32:
	movl	(%rdi), %eax
	retq
```

四個函式都回傳 64-bit 值，但指令各不相同，而且每一條都可以用 7.5 節的規則解釋：

1. `load_s8`：有號 byte 要 sign-extend 到 64 bits，用 `movsbq`。
2. `load_u8`：無號 byte 要 zero-extend，理論上是 `movzbq`，但編譯器用了 `movzbl`：先補零到 32 bits，再靠「寫 `%eax` 清掉高 32 位元」的規則得到完整的 64-bit 結果，而且編碼少一個 byte。
3. `load_s32`：有號 32-bit 延伸成 64-bit 要用 `movslq`（Intel 語法叫 `movsxd`）。
4. `load_u32`：x86-64 沒有 `movzlq` 這條指令，因為根本不需要：`movl` 寫入 `%eax` 就已經自動補零了。

手算一次：記憶體中的 byte 是 `0xFD`。當成 `int8_t` 是 −3，`movsbq` 複製最高位元 1，結果是 `0xFFFFFFFFFFFFFFFD`（仍然是 −3）；當成 `uint8_t` 是 253，`movzbl` 補零，結果是 `0x00000000000000FD`（仍然是 253）。兩條指令讀的是同一個 byte，差別只在於編譯器根據 C 的型別選了哪一條。

反過來說，**看到延伸指令就能反推型別**：`movs` 代表來源是有號型別，`movz` 或 32-bit `movl` 代表無號型別或剛好不需要延伸。這是讀沒有 debug 資訊的程式時非常有用的線索，7.13 節會用它解開故事中的當機。

## 7.8 `push` 與 `pop`：stack 上的資料

**Stack**（堆疊）是記憶體中一塊後進先出的區域，用來存放函式的 return address、區域變數和需要暫存的暫存器值（第 9 章會完整說明 stack frame）。在 x86-64 上，stack **往低位址長**，`%rsp` 永遠指向目前的頂端，也就是最後放進去的那個值。

兩條指令專門操作 stack：

- `pushq S`：先把 `%rsp` 減 8，再把 S 寫到 `(%rsp)`。等於 `subq $8, %rsp` 加上 `movq S, (%rsp)`。
- `popq D`：先從 `(%rsp)` 讀出 8 bytes 放到 D，再把 `%rsp` 加 8。等於 `movq (%rsp), D` 加上 `addq $8, %rsp`。

假設一開始 `%rsp = 0x7ffe0010`，`%rbx = 0xABC`：

```text
     pushq %rbx 之前                pushq %rbx 之後                popq %rbx 之後
 高位址                         高位址                         高位址
 ┌──────────────┐ 0x7ffe0018   ┌──────────────┐ 0x7ffe0018   ┌──────────────┐ 0x7ffe0018
 │ （舊資料）   │              │ （舊資料）   │              │ （舊資料）   │
 ├──────────────┤ 0x7ffe0010   ├──────────────┤ 0x7ffe0010   ├──────────────┤ 0x7ffe0010
 │ （頂端的值） │ ← %rsp       │ （頂端的值） │              │ （頂端的值） │ ← %rsp
 ├──────────────┤ 0x7ffe0008   ├──────────────┤ 0x7ffe0008   ├──────────────┤ 0x7ffe0008
 │ （未使用）   │              │ 0xABC        │ ← %rsp       │ 0xABC（殘留）│
 └──────────────┘              └──────────────┘              └──────────────┘
 低位址                         低位址                         低位址
```

逐步看：`pushq` 讓 `%rsp` 從 `0x7ffe0010` 變成 `0x7ffe0008`，再把 `0xABC` 寫到那裡；`popq` 從 `0x7ffe0008` 讀出 `0xABC` 放回 `%rbx`，`%rsp` 回到 `0x7ffe0010`。注意最右邊的 `0xABC` 還留在記憶體裡，`pop` 只是移動 `%rsp`，不會清除資料。這也是為什麼讀取「已經返回的函式的區域變數」有時候還能讀到舊值，但那是 undefined behavior，下一次函式呼叫就會把它蓋掉。

編譯器什麼時候會用 `push`／`pop`？最常見的情況是函式需要一個「呼叫別的函式之後仍然保留」的值：

```c
long cache_lookup(long key);   /* 定義在別的檔案 */

long lookup_plus_key(long key) {
    long v = cache_lookup(key);
    return v + key;            /* 呼叫之後還要用到 key */
}
```

`lookup_plus_key` 以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生的結果如下，`callq` 那一行就是呼叫外部函式：

```asm
lookup_plus_key:
	pushq	%rbx
	movq	%rdi, %rbx
	callq	cache_lookup@PLT
	addq	%rbx, %rax
	popq	%rbx
	retq
```

`key` 一開始在 `%rdi`，但 `%rdi` 是 caller-saved，呼叫 `cache_lookup` 之後可能被改掉。所以編譯器把 `key` 搬到 callee-saved 的 `%rbx`，而因為 `%rbx` 是 callee-saved，`lookup_plus_key` 自己用之前必須先 `pushq %rbx` 保存呼叫者的值，返回前 `popq %rbx` 還原。`@PLT` 是動態連結的細節，第 19 章會解釋。這裡還藏著一個細節：進入函式時 `%rsp` 距離 16 的倍數差 8（因為 `call` 推入了 8-byte 的 return address），`pushq %rbx` 剛好把它補回 16-byte 對齊，滿足呼叫 `cache_lookup` 之前的對齊要求（第 9 章）。

## 7.9 `leaq`：算位址，不讀記憶體

`leaq`（load effective address）的名字讓很多人誤會。它的 operand 寫法和記憶體存取一模一樣，但它只做「算出有效位址」這一步，把結果放進目的暫存器，**不讀記憶體，也不改 condition codes**：

```text
 movq 16(%rdi,%rcx,8), %rax      leaq 16(%rdi,%rcx,8), %rax
 ─────────────────────────       ─────────────────────────
 ① 算位址 A = 16 + rdi + rcx×8   ① 算位址 A = 16 + rdi + rcx×8
 ② 讀記憶體 M[A] 的 8 bytes      ② rax = A（到此為止）
 ③ rax = M[A]
 對應 C：x = a[i + 2]             對應 C：p = &a[i + 2]
```

`leaq` 的本意是取位址，C 的 `&a[i + 2]` 就會編譯成它。但編譯器很快發現：「加一個數、再加另一個數乘以 1、2、4、8」這個公式本身就是很有用的算術，而且 `leaq` 可以把結果放到第三個暫存器、不破壞來源。所以在最佳化過的程式中，`leaq` 最常被拿來做整數運算，跟位址完全無關：

```c
long mul5_plus3(long x)            { return x * 5 + 3; }
long mul9(long x)                  { return x * 9; }
long mul12(long x)                 { return x * 12; }
uint8_t *nth_data(const image_t *imgs, long i) { return imgs[i].data; }
```

四個函式都以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生；`nth_data` 用的 `image_t` 定義和 7.12 節程式相同（24 bytes，`data` 在位移 16）：

```asm
mul5_plus3:
	leaq	(%rdi,%rdi,4), %rax
	addq	$3, %rax
	retq
mul9:
	leaq	(%rdi,%rdi,8), %rax
	retq
mul12:
	shlq	$2, %rdi
	leaq	(%rdi,%rdi,2), %rax
	retq
nth_data:
	leaq	(%rsi,%rsi,2), %rax
	movq	16(%rdi,%rax,8), %rax
	retq
```

逐一手算：`mul5_plus3` 的 `(%rdi,%rdi,4)` 是 `x + x×4 = 5x`，再加 3。`mul9` 是 `x + x×8 = 9x`，一條指令完成。`mul12` 先左移 2 位得到 `4x`，再算 `4x + 4x×2 = 12x`。編譯器偏好這種寫法，因為在大多數 x86-64 處理器上，簡單形式的 `lea` 和 shift 的延遲比乘法指令短；但這是微架構的選擇，不同編譯器、不同 `-mtune` 可能會直接用 `imul`。

`nth_data` 把兩種用法合在一起：`image_t` 是 24 bytes，不是合法的 scale，所以先用 `leaq` 算 `t = 3i`，再用 `16(%rdi,%rax,8)` 讀出 `16 + imgs + 24i`，也就是 `imgs[i].data`。第一條 `leaq` 是純算術，第二條才真的讀記憶體。

> [!warning] 常見誤解
> 「看到 `leaq (%rdi,%rsi), %rax` 就表示程式在處理指標。」不一定。7.3 節的 `add3` 就是用它算 `a + b`。`leaq` 只是一個「三運算元的加法器」，運算元是位址還是普通整數，要從上下文判斷。

## 7.10 讀懂一個完整函式：`get_gray`

現在把前面的東西組起來，讀故事中當機的那個函式。`thumbd` 的灰階影像用一個 struct 描述：

```c
#include <stdint.h>
typedef struct {
    int width;          /* offset 0 */
    int height;         /* offset 4 */
    int stride;         /* offset 8：每一列佔幾個 byte */
    uint8_t *data;      /* offset 16 */
} image_t;

uint8_t get_gray(const image_t *img, int x, int y) {
    return img->data[(long)y * img->stride + x];
}
```

`stride` 是每一列在記憶體中佔多少 bytes，通常大於或等於 `width`（為了對齊會在每列尾端補幾個 bytes）。`data` 是一個 8-byte 指標，前面三個 `int` 只佔 12 bytes，所以編譯器在中間補了 4 bytes 讓指標對齊到 8 的倍數，`data` 的位移是 16 而不是 12（第 10 章詳細講對齊）。

這個函式以 `clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生的組合語言只有 7 條指令：

```asm
get_gray:
	movslq	%edx, %rax
	movslq	8(%rdi), %rcx
	imulq	%rax, %rcx
	movslq	%esi, %rax
	addq	16(%rdi), %rcx
	movzbl	(%rax,%rcx), %eax
	retq
```

讀一個函式時，第一步永遠是**標出參數**：`img` 在 `%rdi`，`x` 在 `%esi`（32-bit 的 `int`，所以用 32-bit 名稱），`y` 在 `%edx`，回傳值放在 `%eax`。接著一行一行把它翻成 C 的運算：

| 指令 | 做了什麼 | 對應的 C |
|---|---|---|
| `movslq %edx, %rax` | 把 32-bit 有號的 `y` 延伸成 64-bit | `(long)y` |
| `movslq 8(%rdi), %rcx` | 讀位移 8 的 4 bytes，sign-extend | `(long)img->stride` |
| `imulq %rax, %rcx` | `rcx = rcx × rax` | `(long)y * img->stride` |
| `movslq %esi, %rax` | 把有號的 `x` 延伸成 64-bit | `(long)x` |
| `addq 16(%rdi), %rcx` | 讀位移 16 的 8 bytes 加到 `rcx` | `img->data + y * stride`（這一列的起點） |
| `movzbl (%rax,%rcx), %eax` | 讀 `rcx + rax` 位址的 1 byte，補零 | `row[x]`，結果是 `uint8_t` |

每一條指令都對得回 C 的某個部分，也看得出型別：`8(%rdi)` 用 `movslq` 讀 4 bytes，所以 `stride` 是有號 32-bit；`16(%rdi)` 用 `addq` 讀 8 bytes，是指標；最後的 `movzbl` 說明讀的是無號 byte。即使沒有原始碼，這些線索也足以重建出 struct 的大致樣子。

讀到這裡也看得出編譯器的一個習慣：它不一定照原始碼的順序計算。`x` 的延伸被排在乘法之後，`data` 的加法被排在 `x` 之後。只要結果相同，編譯器可以自由重排，所以讀最佳化過的程式碼時，要追「資料從哪裡來、流到哪裡去」，而不是期待一行對一行。

## 7.11 ARM64 對照：另一種 ISA 長什麼樣

你的筆電很可能是 Apple Silicon，雲端上也越來越多 ARM 伺服器（例如 AWS Graviton）。同一個 `get_gray` 用 `clang -target aarch64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables` 產生：

```text
get_gray:
	ldrsw	x8, [x0, #8]          // x8 = (long)img->stride
	ldr	x9, [x0, #16]         // x9 = img->data
	smaddl	x8, w8, w2, x9        // x8 = (long)w8 * (long)w2 + x9，也就是 data + y*stride
	ldrb	w0, [x8, w1, sxtw]    // w0 = 讀 x8 + (long)x 位址的 1 byte
	ret
```

（註解是本書加的。）同樣的邏輯，ARM64 只用了 5 條指令。`ldrsw` 是「load 有號 word 並延伸」，等於 `movslq`；`smaddl` 一條指令做完「有號 32×32 乘法再加 64-bit 值」；最後的 `ldrb` 在定址時就順便把 `w1`（`x`）sign-extend（`sxtw`），不需要額外的 `movslq`。

| 項目 | x86-64 | ARM64（AArch64） |
|---|---|---|
| 指令長度 | 1–15 bytes 不等 | 一律 4 bytes |
| 通用暫存器 | 16 個：`%rax`…`%r15` | 31 個：`x0`–`x30`，另有 `sp` 與恆為 0 的 `xzr` |
| 32-bit 子暫存器 | `%eax` 等，寫入時清掉高 32 位元 | `w0` 等，寫入時同樣清掉高 32 位元 |
| 記憶體存取 | 大多數指令都能直接讀寫記憶體 | 只有 `ldr`／`str` 系列能存取記憶體（load／store 架構） |
| 參數與回傳 | `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`；回傳 `%rax` | `x0`–`x7`；回傳 `x0` |
| return address | `call` 推到 stack 上 | `bl` 放進 `x30`（link register），需要時才存到 stack |
| 語法慣例 | AT&T：來源在前 | 目的在前，類似 Intel 語法 |

兩者的設計哲學不同，但讀法相同：先找參數暫存器，再追每個值從哪裡來、到哪裡去。學會讀一種 ISA，第二種通常只要一個下午就能上手。

## 7.12 動手做：模擬子暫存器與驗證 addressing mode

這一節有兩個實驗。第一個用 C 模擬 7.5 與 7.7 節的寬度規則，第二個用你自己的機器產生並反組譯 x86-64 程式碼。

### 程式：子暫存器寫入與位址公式

```c
#include <inttypes.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

/* 用一個 64-bit 整數模擬 %rax，觀察寫入不同寬度子暫存器的效果。 */
static uint64_t rax = 0x1122334455667788;

static void show(const char *what) { printf("%-28s %%rax = 0x%016" PRIx64 "\n", what, rax); }

/* 寫 %al、%ax：只改低位，其他位元保留 */
static void write_al(uint8_t v)  { rax = (rax & ~0xFFull)   | v; }
static void write_ax(uint16_t v) { rax = (rax & ~0xFFFFull) | v; }
/* 寫 %eax：x86-64 規定高 32 位元一律清為 0 */
static void write_eax(uint32_t v) { rax = v; }

typedef struct { int width, height, stride; uint8_t *data; } image_t;

int main(void) {
    show("initial");
    write_al(0xAA);           show("movb $0xAA, %al");
    write_ax(0xBBBB);         show("movw $0xBBBB, %ax");
    write_eax(0xCCCCCCCC);    show("movl $0xCCCCCCCC, %eax");

    int8_t neg = -3;          /* 位元樣式 0xFD */
    rax = (uint64_t)(uint8_t)neg;  show("movzbq 0xFD (zero-extend)");
    rax = (uint64_t)(int64_t)neg;  show("movsbq 0xFD (sign-extend)");

    /* addressing mode：Imm(rb,ri,s) = Imm + rb + ri*s，s 只能是 1、2、4、8。
     * sizeof(image_t) = 24 不是合法的 s，所以編譯器分兩步（見 7.9 節的 nth_data）：
     *   leaq (%rsi,%rsi,2), %rax      → t = i*3
     *   movq 16(%rdi,%rax,8), %rax    → 讀 16 + base + t*8 */
    image_t imgs[4];
    printf("sizeof(image_t) = %zu, offsetof(image_t, data) = %zu\n",
           sizeof(image_t), offsetof(image_t, data));
    uintptr_t rb = (uintptr_t)imgs;                /* base：陣列起點 */
    for (long i = 0; i < 4; i += 3) {
        uintptr_t t = (uintptr_t)(i + i * 2);      /* leaq (ri,ri,2) */
        uintptr_t formula = 16 + rb + t * 8;       /* 16(rb,t,8) */
        uintptr_t real = (uintptr_t)&imgs[i].data;
        printf("i=%ld: 16 + 0x%" PRIxPTR " + %2lu*8 = 0x%" PRIxPTR "  &imgs[%ld].data = 0x%" PRIxPTR "  %s\n",
               i, rb, (unsigned long)t, formula, i, real, formula == real ? "match" : "MISMATCH");
    }
    return 0;
}
```

在 macOS arm64（Apple clang 21，`cc -std=c17 -O1 -Wall -Wextra`）上執行的輸出：

```text
initial                      %rax = 0x1122334455667788
movb $0xAA, %al              %rax = 0x11223344556677aa
movw $0xBBBB, %ax            %rax = 0x112233445566bbbb
movl $0xCCCCCCCC, %eax       %rax = 0x00000000cccccccc
movzbq 0xFD (zero-extend)    %rax = 0x00000000000000fd
movsbq 0xFD (sign-extend)    %rax = 0xfffffffffffffffd
sizeof(image_t) = 24, offsetof(image_t, data) = 16
i=0: 16 + 0x16b52cfe8 +  0*8 = 0x16b52cff8  &imgs[0].data = 0x16b52cff8  match
i=3: 16 + 0x16b52cfe8 +  9*8 = 0x16b52d040  &imgs[3].data = 0x16b52d040  match
```

逐段解說：

1. **前四行**驗證 7.5 節的寬度規則。寫 `%al` 只換掉最低的 `88`，寫 `%ax` 只換掉最低的 `77aa`，但寫 `%eax` 讓高 32 位元的 `11223344` 整個變成 0。
2. **接下來兩行**是同一個 byte `0xFD` 的兩種延伸。zero-extend 得到 253，sign-extend 得到 −3 的 64-bit 二補數。這就是 `movzbq` 與 `movsbq` 的差別。
3. **最後三行**驗證 addressing mode。`image_t` 是 24 bytes、`data` 在位移 16，和 7.10 節推導的一致。`i = 3` 時，`t = 9`，位址 = `16 + 0x16b52cfe8 + 72` = `0x16b52d040`，和 C 編譯器算出的 `&imgs[3].data` 相同。陣列的位址每次執行都不同，因為 stack 位址有隨機化（ASLR，第 11 章），但「公式算的等於實際的」這件事每次都成立。

這段程式是在 ARM64 上跑的，它模擬的是 x86-64 的規則，而不是讀取真正的 `%rax`。真正的暫存器要用除錯器看，這正是下一個實驗的內容。

### 實驗：在自己的機器上產生、反組譯 x86-64

把 7.10 節的 `get_gray` 存成 `gray.c`，然後執行：

```bash
clang -target x86_64-linux-gnu -O1 -S -fno-asynchronous-unwind-tables -o - gray.c
clang -target x86_64-linux-gnu -O1 -c gray.c -o gray.o
objdump -d gray.o
objdump -d --x86-asm-syntax=intel gray.o    # macOS 的 objdump 是 LLVM 版；GNU objdump 用 -M intel
```

在 macOS arm64 上，`objdump -d gray.o` 的實際輸出：

```text
gray.o:	file format elf64-x86-64

Disassembly of section .text:

0000000000000000 <get_gray>:
       0: 48 63 c2                     	movslq	%edx, %rax
       3: 48 63 4f 08                  	movslq	0x8(%rdi), %rcx
       7: 48 0f af c8                  	imulq	%rax, %rcx
       b: 48 63 c6                     	movslq	%esi, %rax
       e: 48 03 4f 10                  	addq	0x10(%rdi), %rcx
      12: 0f b6 04 08                  	movzbl	(%rax,%rcx), %eax
      16: c3                           	retq
```

`file format elf64-x86-64` 說明這是一個 Linux 的 x86-64 目的檔，雖然它是在 Mac 上產生的。機器碼中可以直接看到位移：`movslq 0x8(%rdi), %rcx` 的最後一個 byte 是 `08`，`addq 0x10(%rdi), %rcx` 的最後一個 byte 是 `10`。`movzbl` 從位址 `0x12` 開始，也就是函式起點加 18 bytes。

接著做一個小修改：把 `int x` 改成 `uint32_t x`，重新反組譯。你會看到位址 `0xb` 的 `movslq %esi, %rax`（3 bytes）變成 `movl %esi, %eax`（2 bytes，`89 f0`），後面的 `movzbl` 因此往前移到 `0x11`，也就是 `<get_gray+17>`。這個位移正是故事中 gdb 印出的位置。

## 7.13 在工作上怎麼用

### 解開故事：從暫存器值推回 bug

回到 7.1 節的 core dump。用本章的知識，可以一步一步推理：

```text
 當機指令：movzbl (%rax,%rcx,1),%eax   at <get_gray+17>
      │
      ├─ 1. 這條指令在算什麼？ 位址 = rcx + rax×1，讀 1 byte
      │
      ├─ 2. 誰是 base、誰是 index？
      │      rcx = 0x7f3c2a400c80  ← 像是 heap 或 mmap 區的位址，應該是「這一列的起點」
      │      rax = 0xffffffff      ← 像是索引 x
      │
      ├─ 3. 位址 = 0x7f3c2a400c80 + 0xffffffff = 0x7f3d2a400c7f
      │      比列起點多了將近 4 GiB → 落在沒有映射的區域 → SIGSEGV
      │
      ├─ 4. 為什麼 rax 是 0x00000000ffffffff 而不是 0xffffffffffffffff？
      │      → x 被 zero-extend，不是 sign-extend
      │      → 往前看：get_gray+11 是 movl %esi,%eax（2 bytes），不是 movslq
      │      → x 的型別是無號 32-bit
      │
      └─ 5. 結論：呼叫者傳入 x = −1（例如邊界像素的 x − 1），
             在 uint32_t 下變成 4294967295，一路被當成合法的大索引
```

如果 `x` 還是 `int`，同樣的 −1 會被 `movslq` 延伸成 `0xffffffffffffffff`，位址變成「列起點減 1」，通常不會當機，而是悄悄讀到前一列的最後一個 byte（可能是像素，也可能是列尾補齊用的 padding），產生一條肉眼難以察覺的錯誤邊線。兩種行為都是 bug，但型別改變把「靜默的錯誤」變成了「當機」。真正的修法是在呼叫端處理邊界（clamp 座標），並在 `get_gray` 加上 `assert(x < img->width)`。這次的教訓不是「不要用 unsigned」，而是「看到暫存器的值長得像 `0xffffffff`、`0xffff`，先懷疑寬度與延伸」。

### 讀當機現場的標準流程

在 gdb（Linux）或 lldb（macOS）中遇到 crash，這幾個指令最常用：

| 目的 | gdb | lldb |
|---|---|---|
| 看當機的那一條指令 | `x/i $pc` | `disassemble --pc` |
| 反組譯整個函式 | `disassemble`、`disassemble get_gray` | `disassemble --name get_gray` |
| 看暫存器 | `info registers`、`p/x $rax` | `register read`、`register read rax` |
| 看記憶體 | `x/8xb $rcx`、`x/4gx $rsp` | `memory read --size 1 --count 8 $rcx` |
| 切換語法 | `set disassembly-flavor intel` | `settings set target.x86-disassembly-flavor intel` |
| 原始碼與組合語言交錯 | `disassemble /s`（需要 `-g`） | `disassemble --mixed`（需要 `-g`） |

拿到當機指令後，用這份檢查清單：

1. **它要存取哪個位址？** 把 addressing mode 展開成公式，代入暫存器的值算出來。
2. **哪個暫存器的值看起來不對？** 常見的可疑值：0 或很小的數（NULL 指標或 NULL 加欄位位移）、`0xffffffff`／`0xffff`（寬度或延伸問題）、`0xdeadbeef` 或重複的位元樣式（未初始化或已釋放的記憶體，第 26 章）。
3. **那個值是從哪裡來的？** 往前讀幾條指令，找出最後一次寫入它的指令，必要時一路追到函式參數。
4. **對回 C**：參數在哪個暫存器、struct 位移對應哪個欄位、延伸指令代表什麼型別。

> [!tip] 不要從函式中間往回反組譯
> x86-64 的指令長度不固定，從一個任意位址開始解碼可能會從某條指令的中間開始，得到一串看起來合理但完全錯誤的指令。要看當機點之前的指令，用 `disassemble` 反組譯整個函式，不要用 `x/10i $pc-20` 這種方式猜起點。

### 確認編譯器實際做了什麼

工作上另一個常見的用途，是確認編譯器有沒有照你以為的方式產生程式碼：

- **效能**：用 `perf record` 加 `perf annotate`（Linux）看熱點落在哪幾條指令上，確認迴圈有沒有被向量化（出現 `%xmm`、`%ymm` 暫存器與 `vpaddd` 這類指令）、函式有沒有被 inline。第 14 章會大量使用這個技巧。
- **正確性**：懷疑編譯器「最佳化掉」某段程式時（例如第 5 章的 signed overflow 檢查），直接看 `-O2 -S` 的輸出，檢查那段比較指令還在不在。
- **跨架構**：在 Mac 上開發、部署到 x86-64 Linux 時，用 `-target x86_64-linux-gnu` 檢查關鍵函式在兩邊的差異，不需要準備另一台機器。
- **確認 build 設定**：`objdump -d` 正式環境的執行檔，看是不是真的用了預期的最佳化等級（`-O0` 的程式碼充滿 `-8(%rbp)` 這種 stack 存取，一眼就認得出來）。

## 7.14 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 把 `subq %rsi, %rdi` 讀成 `rsi − rdi`，推理全錯 | AT&T 與 Intel 的運算元順序相反 | 看工具用哪種語法（有 `%` 就是 AT&T） | 固定一種語法閱讀；AT&T 記住「目的在最後」 |
| 以為 `leaq` 會讀記憶體，在當機分析時懷疑錯指令 | 把 `lea` 當成 load | `lea` 永遠不會因為位址無效而 segfault | 把 `lea` 讀成「三運算元加法」 |
| 以為寫 `%eax` 後高 32 位元還保留 | 不知道 32-bit 寫入清零規則 | 在 gdb 中 `p/x $rax` 前後比較 | 記住：8／16-bit 保留，32-bit 清零 |
| 暫存器值是 `0xffffffff`，索引卻應該是 −1 | 32-bit 無號值被 zero-extend | 往前找延伸指令：`movl`／`movz` 還是 `movslq` | 修正型別，並在邊界檢查負數或過大的值 |
| 反組譯結果亂七八糟、出現 `(bad)` | 從指令中間開始解碼，或把資料當成程式碼 | 對照函式起點與符號表重新反組譯 | 用 `disassemble 函式名`；注意 jump table 等資料區 |
| `-O2` 的組合語言對不上原始碼的行 | 指令被重排、合併、inline，變數只活在暫存器 | 用 `-O1` 或 `-Og -g` 重新產生，比較差異 | 追資料流而不是逐行對照；需要時加 `-g` 並用 `disassemble /s` |
| 在 Mac 上 `gcc -S` 看到 `ldr`、`x0` 而不是 `%rax` | 產生的是本機（ARM64）組合語言 | 看輸出中暫存器的命名 | 加 `-target x86_64-linux-gnu`（clang） |

## 7.15 動手練習

1. **手算 addressing mode**：設 `%rdi = 0x2000`、`%rsi = 5`、`%rdx = 0x10`。計算 `(%rdi)`、`8(%rdi)`、`(%rdi,%rsi)`、`(%rdi,%rsi,4)`、`-4(%rdi,%rsi,8)`、`(,%rsi,2)`、`0x20(%rdi,%rdx,2)` 的有效位址。（答案：0x2000、0x2008、0x2005、0x2014、0x2024、0xA、0x2040。驗證方法：在 7.12 節的程式中加入幾行 `printf` 照公式計算。）
2. **預測指令**：寫出下列函式在 `-O1` 下最關鍵的那條指令，再用 `clang -target x86_64-linux-gnu -O1 -S` 驗證：`long f1(const int16_t *p) { return *p; }`、`unsigned long f2(const uint16_t *p) { return *p; }`、`void f3(int32_t *p, long v) { *p = (int32_t)v; }`。（提示：`movswq`、`movzwl`、`movl %esi, (%rdi)`。）
3. **反推 C**：下面是某個函式以 `clang -target x86_64-linux-gnu -O1 -S` 產生的組合語言。寫出它的 C 原型與函式本體，再編譯驗證。
   ```asm
   mystery:
   	leaq	(%rsi,%rsi,2), %rax
   	leaq	(%rdi,%rax,4), %rax
   	movslq	(%rax,%rdx,4), %rax
   	incq	%rax
   	retq
   ```
   （答案：`long mystery(const int32_t *a, long i, long j) { return a[i * 3 + j] + 1; }`。第二條 `leaq` 算出 `a + 12i`，也就是「每列 3 個 `int`」的第 `i` 列起點。）
4. **延伸程式**：在 7.12 節的程式加上 `write_ah(uint8_t v)`，模擬寫入 `%ah`（第 8 到 15 位元），並印出 `movb $0x99, %ah` 之後的 `%rax`。
5. **跨 ISA 比較**：把 7.8 節的 `lookup_plus_key` 用 `-target aarch64-linux-gnu` 編譯，找出 ARM64 把 return address 存在哪裡、用哪個暫存器保存 `key`，並和 x86-64 的 `pushq %rbx` 對照。
6. **指令長度**：用 `objdump -d` 反組譯 7.7 節的函式，找出最長與最短的指令各是幾個 bytes，並解釋為什麼 `movabsq` 特別長。

## 本章重點整理

- ISA 是軟體與硬體之間的合約，規定指令、暫存器與記憶體模型；微架構是合約底下的實作，每一代都可以不同而不影響程式的正確性。
- 在 ISA 這一層沒有型別與變數名稱，只有 `%rip`、16 個通用暫存器、condition codes、向量暫存器與一個以 byte 為單位的記憶體陣列。
- 用 `-S` 可以看到編譯器輸出的組合語言，用 `objdump -d` 可以把目的檔或執行檔反組譯；clang 加上 `-target x86_64-linux-gnu` 可以在任何機器上產生 x86-64 程式碼。
- AT&T 語法是「來源在前、目的在後」，暫存器加 `%`、立即數加 `$`，大小用指令後綴 `b`／`w`／`l`／`q` 表示 1／2／4／8 bytes。
- `%al`、`%ax`、`%eax`、`%rax` 是同一個暫存器的不同寬度；寫入 8 或 16 位元保留其他位元，寫入 32 位元會把高 32 位元清為 0。
- Linux x86-64 的前六個整數參數依序在 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，回傳值在 `%rax`，`%rsp` 指向 stack 頂端。
- 記憶體 operand 的一般形式 `Imm(rb,ri,s)` 代表位址 `Imm + rb + ri × s`，scale 只能是 1、2、4、8，剛好對應陣列索引與 struct 欄位位移。
- `mov` 不能直接從記憶體搬到記憶體；`movz` 做 zero extension、`movs` 做 sign extension，從延伸指令可以反推 C 的有號或無號型別。
- `pushq` 先把 `%rsp` 減 8 再寫入，`popq` 先讀出再把 `%rsp` 加 8；stack 往低位址長，`pop` 不會清除資料。
- `leaq` 只計算位址、不讀記憶體也不改 condition codes，編譯器常用它做「加法加上乘以 1、2、4、8」的整數運算。
- 最佳化過的程式碼會重排、合併指令，讀的時候要追資料流，先標出參數與回傳暫存器，再追每個值的來源。
- ARM64 是固定 4-byte 指令的 load／store 架構，有 31 個通用暫存器，參數在 `x0`–`x7`，return address 放在 `x30`。
- 分析 crash 時，把當機指令的位址公式代入暫存器值，找出可疑的值（0、`0xffffffff`、重複樣式），再往前追它的來源。

## 延伸問答

> [!question]- Q1. ISA 和微架構的差別是什麼？為什麼同一支執行檔可以在 Intel 和 AMD 的 CPU 上都能跑？
> ISA 規定的是「程式看得到的行為」：有哪些指令、每條指令怎麼編碼、執行後暫存器與記憶體會變成什麼。微架構則是「怎麼做到」：pipeline 深度、同時能發出幾條指令、cache 大小、分支預測器設計。只要兩顆 CPU 實作同一份 ISA，同一串指令就會得到相同的結果。
>
> Intel 和 AMD 的處理器都實作 x86-64 ISA，所以同一個執行檔在兩者上都能正確執行，差別只在於速度：同樣的指令序列，在不同微架構上的 cycle 數可能差很多。這也是為什麼效能調校（第 14 章）有時需要針對特定微架構，而正確性只需要依賴 ISA。少數較新的擴充指令（例如某些 AVX-512 指令）不是每顆 CPU 都有，程式使用前必須先檢查 CPU 支援。

> [!question]- Q2. `movl $1, %eax` 和 `movw $1, %ax` 執行後，`%rax` 的值有什麼不同？
> 假設 `%rax` 原本是 `0xFFFFFFFFFFFFFFFF`。`movl $1, %eax` 寫入 32-bit 子暫存器，x86-64 規定高 32 位元會被清為 0，所以結果是 `0x0000000000000001`。`movw $1, %ax` 寫入 16-bit 子暫存器，其他 48 位元保留，所以結果是 `0xFFFFFFFFFFFF0001`。
>
> 這個不對稱是 AMD 設計 x86-64 時的選擇，常見的解釋是：清零可以讓每次 32-bit 寫入產生一個與舊值無關的新值，避免 out-of-order 執行時的假相依；8 與 16 位元的行為則為了相容舊程式而保留。實務上，這解釋了為什麼編譯器喜歡用 `movl`、`xorl %eax, %eax` 處理 64-bit 暫存器，也解釋了為什麼一個 32-bit 的 −1 經過 `movl` 會變成 4294967295。

> [!question]- Q3. 手算題：`%rbx = 0x7000`、`%rcx = 0x3`，`leaq 0x20(%rbx,%rcx,4), %rax` 與 `movq 0x20(%rbx,%rcx,4), %rax` 各做什麼？
> 兩條指令都先算有效位址：`0x20 + 0x7000 + 3 × 4 = 0x7000 + 0x20 + 0xC = 0x702C`。
>
> `leaq` 到此為止，把 `0x702C` 這個數字放進 `%rax`，不會存取記憶體，所以即使 `0x702C` 不是合法位址也不會出錯。`movq` 則會再到位址 `0x702C` 讀出 8 個 bytes，把那個值放進 `%rax`；如果這個位址沒有映射，就會觸發 segfault。在 C 裡，前者像 `p = &a[i] + 8`（`a` 是 `int *`，`0x20` 等於 8 個 `int`），後者像是讀取那個位置上的資料。分析 crash 時，`lea` 永遠不會是「讀到壞位址」的那條指令。

> [!question]- Q4. 為什麼 x86-64 有 `movzbq`、`movzwq`，卻沒有 `movzlq`？
> 因為不需要。`movzlq` 的意思是「把 32-bit 值 zero-extend 成 64-bit」，而 x86-64 的任何 32-bit 寫入本來就會把高 32 位元清零，所以一條普通的 `movl %esi, %eax` 或 `movl (%rdi), %eax` 就已經完成了 zero extension。
>
> 相對地，sign extension 沒有這種「自動」行為，所以需要 `movslq`（Intel 稱為 `movsxd`）。這個不對稱讓讀組合語言時有一個實用的判斷規則：看到 `movslq` 表示來源是有號 32-bit 整數（例如 `int`）；看到 `movl` 後直接把 64-bit 暫存器當索引或位址使用，表示來源很可能是無號 32-bit（例如 `unsigned`、`uint32_t`）。7.13 節的當機分析就是靠這個區別找出型別被改掉的。

> [!question]- Q5. 你在 production 的 core dump 中看到當機指令是 `movq 0x18(%rax), %rdx`，而 `%rax = 0`。這代表什麼？
> 這條指令要讀位址 `0 + 0x18 = 0x18` 上的 8 bytes。位址 0 附近的頁面在 Linux 上刻意不映射，所以任何存取都會觸發 SIGSEGV。`%rax` 是 0、加上一個小位移，幾乎可以確定是「透過 NULL 指標存取 struct 欄位」：某個 struct 指標是 NULL，程式卻讀了它位移 0x18 的欄位。
>
> 下一步是往前找 `%rax` 最後一次被寫入的指令：它可能是函式參數（從 `%rdi` 搬來）、另一個函式的回傳值（`call` 之後的 `%rax`），或從記憶體讀出的某個欄位。如果是回傳值，通常代表某個查找或配置函式失敗回傳了 NULL，而呼叫端沒有檢查。再依照位移 0x18 對照 struct 定義（例如用 `offsetof` 或 `pahole` 工具），就能知道是哪個欄位。

> [!question]- Q6. 為什麼編譯器會用 `leaq (%rdi,%rdi,4), %rax` 來算 `x * 5`，而不是用 `imulq`？
> `leaq` 的位址公式 `base + index × scale` 本身就是「加法加上乘以 1、2、4、8」，所以 `x + x × 4` 剛好一條 `lea` 就能算出 `5x`。在大多數 x86-64 處理器上，這種簡單形式的 `lea` 延遲約 1 個 cycle，而整數乘法通常要 3 個 cycle 左右，而且 `lea` 可以把結果放到第三個暫存器、不修改 condition codes，給編譯器更多排程彈性。
>
> 但這是依微架構而定的選擇，不是語意上的必要。對乘數不是這些小常數組合的情況（例如 `x * 77`），編譯器會直接用 `imul`；不同的 `-mtune` 設定也可能改變選擇。讀組合語言時，看到 `lea` 要先問「這是位址還是算術」，再從上下文判斷。

> [!question]- Q7. 程式找錯：下面這段組合語言是想把 `*src`（`long`）複製到 `*dst`，為什麼組譯器拒絕它？
> 原始碼是 `movq (%rsi), (%rdi)`。x86-64 的 `mov` 不允許來源和目的同時是記憶體 operand，組譯器會回報 operand 組合不合法。這是 ISA 的限制：一條 `mov` 指令的編碼中只有一個位置可以描述記憶體位址。
>
> 正確的寫法是先讀進暫存器再寫出去，例如 `movq (%rsi), %rax` 然後 `movq %rax, (%rdi)`，這也是編譯器編譯 `*dst = *src;` 時產生的程式碼。同樣地，`mov` 的目的也不能是立即數。這些限制在讀編譯器輸出時不會遇到（編譯器不會產生非法指令），但在手寫 inline assembly 或組合語言檔案時很重要。

> [!question]- Q8. 面試題：x86-64 和 ARM64 在設計上最主要的差異是什麼？對工程師有什麼實際影響？
> x86-64 是 CISC：指令長度 1 到 15 bytes 不等，大多數指令可以直接把記憶體當 operand，有 16 個通用暫存器，`call` 會把 return address 推到 stack 上。ARM64 是 RISC 風格的 load／store 架構：指令固定 4 bytes，只有 `ldr`／`str` 能存取記憶體，有 31 個通用暫存器，return address 放在 link register `x30`。
>
> 對工程師的實際影響有幾個面向。第一，同一份 C 程式碼在兩者上產生的指令與效能特性不同，效能調校要分開量測。第二，ABI 不同（參數暫存器、對齊、`char` 預設有號或無號等），寫 inline assembly、FFI 或讀 core dump 時必須知道是哪一種。第三，記憶體模型不同：ARM64 允許更多的記憶體存取重排，在 x86-64 上「剛好正確」的無鎖程式，搬到 ARM64 上可能出錯（第 32 章）。雲端越來越多 ARM 伺服器，這些差異已經是日常會遇到的事。
