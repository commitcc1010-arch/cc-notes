# 第 2 章　面試流程與溝通：從題目到通過

> [!abstract] 本章地圖
> **核心問題**：同樣寫出正確解，為什麼有人拿到強烈推薦、有人只是勉強通過？一場 45 分鐘的 coding interview，每一分鐘該做什麼、說什麼？
>
> **你會學到**：
> - 45 分鐘的時間分配，以及每個階段的產出
> - 釐清題目的問題清單：輸入範圍、重複、空輸入、回傳格式
> - 先講暴力解再優化，以及怎麼說出瓶頸
> - 邊寫邊說、手動追蹤、用暴力解對拍找 bug（附可執行範例）
> - 複雜度怎麼講才完整
> - 卡住時的具體脫困步驟
> - 面試官的四個評分維度與 L5 等級的表現
> - 常見扣分行為與 follow-up 的應對

## 2.1 一場 45 分鐘面試的時間分配

一場典型的 coding interview 約 45 分鐘，扣掉開場自我介紹與最後留給你提問的時間，真正解題的時間大約 35–40 分鐘。公開面經普遍描述的形式是：面試官給一道題（有時是一道題加上延伸，有時是兩道獨立的題），你在共享編輯器或白板上寫程式，過程中面試官會觀察、提問、必要時給提示。

時間分配的重點是「每個階段都要有明確的產出，而且不要讓任何一個階段吃掉其他階段」。最常見的失敗模式是：前 5 分鐘沒問清楚就開始寫、寫到一半發現理解錯了重來；或是想最佳解想了 20 分鐘，最後沒時間寫完。下面是本書建議的分配，以一道 Medium 為例：

```text
 0 ─ 3 分   開場：簡短自我介紹（面試官主導，不要講太長）
 3 ─ 8 分   釐清題目：重述題意、問限制、用小例子確認輸入輸出
 8 ─ 15 分  設計解法：暴力解 → 瓶頸 → 最佳解；說出複雜度，取得面試官同意
15 ─ 30 分  寫程式：邊寫邊說，結構先於細節
30 ─ 37 分  驗證：用範例手動追蹤，補邊界測試，修 bug
37 ─ 42 分  複雜度總結與 follow-up
42 ─ 45 分  你的提問
```

如果是一輪兩題的形式，每題的時間大約減半，釐清與設計要壓縮到 3–5 分鐘，這時核心題的熟練度就是決定性的。如果題目是 Hard，設計階段可能拉長到 10–15 分鐘，但仍要盡量在 25 分鐘前開始寫程式，因為「有正確思路但沒寫完」通常比「寫完一個次佳解」更難拿到好評。

有兩個時間點要特別留意。第一是 15 分鐘：如果到這時還沒有任何可行解，就先把暴力解寫出來，同時說明你接下來想怎麼優化，因為有能動的程式比完全沒有好。第二是 35 分鐘：如果到這時程式還沒寫完，主動跟面試官說明剩下的部分要怎麼完成，把剩餘時間留給驗證已經寫好的部分。

## 2.2 釐清題目：問什麼、怎麼問

面試題目常刻意留下模糊的地方，看你會不會問。釐清題目有兩個目的：避免解錯題，以及讓面試官看到你會先理解需求再動手，這在 senior 職級特別重要。好的釐清問題是具體、會影響解法的問題，而不是為了問而問。

| 類別 | 要問的問題 | 為什麼重要 |
|---|---|---|
| 輸入範圍 | n 最大多少？數值範圍？有負數嗎？ | 決定可接受的複雜度與是否會溢位（第 3 章） |
| 重複 | 元素會重複嗎？重複時怎麼算？ | 影響計數、去重、two pointers 的跳過邏輯 |
| 空與極端 | 輸入可能為空嗎？只有一個元素？ | 決定回傳預設值，避免索引錯誤 |
| 已排序嗎 | 輸入有排序嗎？可以修改輸入嗎？ | 排序陣列是 binary search 與 two pointers 的訊號 |
| 回傳格式 | 回傳索引還是值？多組解要回傳哪一組？順序重要嗎？ | 避免最後格式錯 |
| 無解 | 如果不存在答案要回傳什麼？ | 常見是 -1、空陣列或例外 |
| 資料型態 | 字串只有小寫英文嗎？圖有環嗎？是否連通？ | 決定能否用固定大小陣列、要不要處理環 |

問完之後，用一個你自己設計的小例子重述題意，例如：「我確認一下，輸入 [2, 7, 11, 15]、目標 9，回傳 [0, 1]，也就是索引，而且保證恰好一組解，對嗎？」這一步很便宜，卻能抓出大部分的理解錯誤。

不要一次問十個問題。挑最可能影響解法的三到五個，其他的可以說出你的假設並繼續，例如：「我先假設輸入不為空，寫完再補空輸入的處理。」說出假設比沉默地假設好得多，因為面試官可以當場糾正你。

本章用一道貫穿的範例示範整個流程。題目是：

> 給一個整數陣列 `nums` 和整數 `k`，回傳有多少組索引對 `(i, j)` 滿足 `i < j` 且 `nums[i] + nums[j] == k`。

這題看起來簡單，但有幾個值得問的地方：元素會不會重複（例如 `[1, 1, 1]`、`k = 2` 答案是 3 而不是 1）？有沒有負數？n 多大？答案會不會很大？下面是一段釐清的對話示範。

```text
候選人：我先確認題意。是計算索引對的數量，不是不同數值組合的數量，對嗎？
        例如 nums = [1, 1, 1]、k = 2，三組 (0,1)、(0,2)、(1,2) 都算，答案是 3？
面試官：對。
候選人：數值可能是負數或 0 嗎？n 最大大概多少？
面試官：可能有負數，n 最多 10^5。
候選人：好，那 O(n^2) 會到 10^10，太慢，我需要 O(n log n) 或 O(n)。
        答案最多是 n(n-1)/2，大約 5×10^9，Python 不會溢位，
        如果是 Java 我會用 long。空陣列回傳 0，可以嗎？
面試官：可以。
```

注意候選人在聽到 n 的範圍後立刻換算出可接受的複雜度，這是第 3 章的核心技巧，也是面試官很喜歡看到的訊號：你不是在猜做法，而是從限制推出方向。

## 2.3 先講暴力解，再找瓶頸

除非你非常確定最佳解而且題目很標準，否則先用一兩句話講出暴力解與它的複雜度。這有三個好處：證明你理解題意；給面試官一個「保底」的訊號；最重要的是，暴力解通常直接指出瓶頸在哪，而優化的方向就藏在瓶頸裡。

講暴力解不需要寫出來，一兩句話即可：「最直接的做法是兩層迴圈枚舉所有 (i, j)，O(n²) 時間、O(1) 空間。」接著要說出**瓶頸**：哪一步在重複做工？對範例題來說，內層迴圈其實是在問「在 i 之前，有幾個數等於 k - nums[j]」，而這個問題每次都重新掃一遍，這就是重複的工作。

```text
暴力解在做什麼（nums = [1, 5, 3, 3, 7]，k = 6）：

j = 1 (5)：往前掃 [1]          找 1 → 1 個
j = 2 (3)：往前掃 [1, 5]       找 3 → 0 個
j = 3 (3)：往前掃 [1, 5, 3]    找 3 → 1 個   ← 又掃了一次 1、5
j = 4 (7)：往前掃 [1, 5, 3, 3] 找 -1 → 0 個 ← 又掃了一次 1、5、3

瓶頸：每個 j 都重新掃描前綴，只為了問「某個值出現幾次」。
觀察：如果邊掃邊用 hash map 記錄「每個值出現幾次」，
      這個問題就變成 O(1) 查詢。

j = 0 (1)：查 5 → 0   ；count = {1:1}
j = 1 (5)：查 1 → 1   ；count = {1:1, 5:1}            累計 1
j = 2 (3)：查 3 → 0   ；count = {1:1, 5:1, 3:1}       累計 1
j = 3 (3)：查 3 → 1   ；count = {1:1, 5:1, 3:2}       累計 2
j = 4 (7)：查 -1 → 0  ；count = {..., 7:1}            累計 2
```

從瓶頸推到最佳解的常見問句有這幾個，練習時可以逐一套用：

- **哪個查詢在重複做？** 能不能用 hash map、prefix sum 或預先排序把它變成 O(1) 或 O(log n)？（第 4、7 章）
- **能不能排序？** 排序後很多問題可以用 two pointers 或 binary search（第 5、8 章）。
- **答案有單調性嗎？** 如果「答案 x 可行則 x+1 也可行」，可以對答案做 binary search（第 8 章）。
- **能不能只保留有用的候選？** 這是 monotonic stack、monotonic deque 與 heap 的出發點（第 10、14 章）。
- **子問題重疊嗎？** 暴力遞迴中同樣的參數被算很多次，就是 DP 的訊號（第 21–24 章）。

說出最佳解之後，先講複雜度並確認面試官同意，再開始寫程式：「用 hash map 記錄已看過的值出現次數，一次掃描，O(n) 時間、O(n) 空間。我可以開始寫嗎？」這個確認很重要，因為有時面試官會在這裡告訴你「可以，但我們假設記憶體很少」，那就要換做法（例如先排序再 two pointers，O(n log n) 時間、O(1) 額外空間）。

## 2.4 邊寫邊說：寫程式時的溝通

寫程式時的沉默是最常見的扣分來源之一，因為面試官無法評估他看不到的思考。但「邊寫邊說」不是把每個字元唸出來，而是說出**意圖**與**決策**：這一段在做什麼、為什麼這樣處理邊界、這個變數代表什麼。

建議的節奏是「先說結構，再填細節」。開始寫之前用一句話講出程式的骨架：「我會用一個 dict 記錄次數，一個迴圈掃過陣列，每一步先查再更新，最後回傳累計值。」然後在寫每一段時，用一句話說明關鍵的決策：

```text
寫的程式碼                         同時說的話
─────────────────────────────────  ─────────────────────────────────────────
count = {}                         「count 記錄目前為止每個值出現幾次。」
pairs = 0
for x in nums:
    pairs += count.get(k - x, 0)   「先查再更新，這樣保證只配對 i < j，
                                     也不會把自己和自己配對。」
    count[x] = count.get(x, 0) + 1
return pairs                       「空陣列時迴圈不執行，直接回傳 0。」
```

上面「先查再更新」那一句是整段程式最容易錯的地方，所以值得主動說。面試官很在意你能不能指出自己程式中的關鍵 invariant（不變量，也就是每一輪迴圈結束時一定成立的條件），這裡的 invariant 是「處理完第 j 個元素後，`pairs` 等於右端點不超過 j 的合法索引對 (i, j') 的數量（也就是 i < j' ≤ j），`count` 是 `nums[0..j]` 的次數表」。

寫程式時的其他好習慣：

- **用有意義的變數名**。`count`、`pairs`、`left`、`right` 比 `d`、`a`、`i2` 更容易讓面試官跟上，也減少你自己的錯誤。
- **長邏輯抽成輔助函式**。例如 graph 題的 `neighbors(r, c)`、解析題的 `parse_number()`。先寫呼叫，說「這個函式等一下補」，讓主流程先完整。
- **不要過早優化常數**。先寫清楚的版本，最後再說「這裡可以再省一個 pass」。
- **遇到不確定的語法就說出來**。例如「我不確定 `bisect_left` 的參數順序，我假設是 (list, x)」，面試官通常不在意語法細節，但在意你是否誠實。

## 2.5 手動追蹤與測試

寫完程式不代表完成。L5 等級的期待是你主動驗證，而不是等面試官指出 bug。很多面試環境不能執行程式，所以要練習「手動追蹤」：拿一個小範例，一行一行模擬變數的變化。

手動追蹤的順序建議是：先用題目範例確認主邏輯，再用你自己設計的邊界案例確認特殊情況。邊界案例的來源可以用一張固定清單：空輸入、單一元素、全部相同、全部不同、最大或最小值、答案不存在、答案在頭或尾。對範例題來說，`[1, 1, 1]`、`k = 2` 這個「全部相同」的案例特別有價值，因為它直接測試重複計數是否正確。

```text
手動追蹤 nums = [1, 1, 1]，k = 2：

x   查 count[k - x]   pairs   count（更新後）
1   count[1] = 0      0       {1: 1}
1   count[1] = 1      1       {1: 2}
1   count[1] = 2      3       {1: 3}

結果 3，符合 (0,1)、(0,2)、(1,2) 三組。
如果「先更新再查」，第一步就會把自己配對到自己，得到錯誤答案。
```

練習時（以及在可以執行程式的面試中），有一個非常有效的技巧叫**對拍**（brute-force cross check）：寫一個簡單到不可能錯的暴力解，再用隨機產生的小輸入比對最佳解與暴力解。隨機輸入要刻意讓值的範圍很小，這樣才會產生大量重複與邊界情況。下面是範例題的完整做法，也示範了本書每段程式的測試寫法：

```python
import random


def count_pairs(nums: list[int], k: int) -> int:
    """O(n)：一次掃描，用 hash map 記錄已看過的值出現次數。"""
    count: dict[int, int] = {}
    pairs = 0
    for x in nums:
        pairs += count.get(k - x, 0)   # 先查：只和左邊的元素配對
        count[x] = count.get(x, 0) + 1  # 再更新：避免自己配自己
    return pairs


def count_pairs_brute(nums: list[int], k: int) -> int:
    """O(n^2)：簡單到不會錯，用來對拍。"""
    n = len(nums)
    return sum(1 for i in range(n) for j in range(i + 1, n) if nums[i] + nums[j] == k)


# 1. 題目範例與手動設計的邊界
assert count_pairs([1, 5, 3, 3, 7], 6) == 2
assert count_pairs([1, 1, 1], 2) == 3          # 全部相同：測重複計數
assert count_pairs([], 5) == 0                 # 空輸入
assert count_pairs([3], 6) == 0                # 單一元素不能自己配自己
assert count_pairs([-2, 2, 0, 0], 0) == 2      # 負數與 0

# 2. 隨機對拍：值域刻意很小，製造大量重複
rng = random.Random(2026)
for _ in range(2000):
    n = rng.randint(0, 8)
    nums = [rng.randint(-3, 3) for _ in range(n)]
    k = rng.randint(-6, 6)
    assert count_pairs(nums, k) == count_pairs_brute(nums, k), (nums, k)

print("all tests passed")
```

對拍的價值在於它把「我覺得是對的」變成「在兩千組隨機輸入上和一個不可能錯的版本一致」。練習時每當你的最佳解沒通過，先寫暴力解對拍，找出最小的失敗輸入，再手動追蹤這個輸入，這通常比盯著程式看快得多。面試中如果可以執行程式，也可以簡短提到「如果有時間，我會寫一個暴力解來做隨機對拍」，這是很成熟的驗證訊號。

## 2.6 複雜度分析怎麼講

複雜度分析是每場 coding interview 都會出現的環節，講得完整與否差異很大。完整的複雜度說明包含四個部分：時間複雜度、空間複雜度、**為什麼**是這個複雜度、以及它是最壞情況、平均還是 amortized（攤銷）。

```text
不完整：「O(n)。」

完整：「時間 O(n)：每個元素處理一次，每次是一個 dict 查詢和一個 dict 更新，
       平均 O(1)。空間 O(n)：最壞情況所有值都不同，dict 存 n 個鍵。
       這裡的 O(1) 是 hash table 的平均情況，最壞情況理論上會退化，
       但面試中通常以平均情況討論。」
```

幾個常被問到或常講錯的點：

- **空間要說清楚算不算輸出**。回傳一個長度 n 的陣列時，通常說「額外空間 O(1)，不計輸出」。
- **遞迴的空間要算 call stack**。DFS 遞迴深度可能到 n，空間就是 O(n)，即使沒有開額外陣列。
- **排序要算進去**。Python 的 `sort` 是 O(n log n) 時間，空間最壞 O(n)。
- **字串操作不是 O(1)**。字串切片、`+` 串接、把字串當 dict 鍵（要先算 hash）都和長度成正比。
- **多個變數要分開寫**。例如矩陣是 O(m·n)，字串陣列是 O(n·L)，不要都寫成 O(n)。
- **Amortized 要說出理由**。例如 monotonic stack「每個元素最多 push 一次、pop 一次，所以總共 O(n)」。第 3 章 3.4 節會詳細說明。

最後，如果你的解不是最佳解，要主動說出來：「這是 O(n log n)，我猜可能有 O(n) 的做法，但需要再想一下。」知道自己的解還有改進空間，比宣稱它是最佳的更好。

## 2.7 卡住時怎麼辦

每個人都會卡住，面試官看的是你卡住時的處理方式。最糟的反應是長時間沉默，因為面試官既無法評估你，也無法給你適當的提示。下面是一套具體的脫困步驟，依序嘗試：

```text
1. 說出你卡在哪裡
   「我知道要找某種單調性，但還不確定該維護什麼。」
   → 讓面試官知道你的狀態，他可能會給方向性的提示。

2. 縮小問題
   n = 1、2、3 時答案是什麼？如果數值只有 0 和 1 呢？
   → 小案例常常會讓規律浮現。

3. 手算一個例子，觀察自己怎麼做
   你的大腦用什麼方法算出答案？把那個方法形式化。

4. 換一個 pattern 試試
   用第 3 章的決策樹，逐一問：排序有用嗎？能 binary search 答案嗎？
   能建成圖嗎？有重疊子問題嗎？

5. 放寬限制
   如果可以用 O(n) 額外空間呢？如果陣列有排序呢？
   先解簡化版，再想怎麼去掉假設。

6. 先寫暴力解
   超過約 15 分鐘還沒有方向，就寫出可行解，邊寫邊找瓶頸。
```

接受提示不是失敗。面試官給提示通常代表他希望你繼續前進，接住提示並迅速推進是正面訊號；反過來，忽略提示或堅持原本的方向才會扣分。接住提示的方式是複述並延伸：「所以你的意思是，如果我先依結束時間排序，就可以貪婪地選……對，因為最早結束的區間留給後面最多空間。」

另一個常見的卡住情況是寫到一半發現做法有漏洞。這時不要默默刪掉重寫，先說出你發現的問題：「我發現有負數時窗口的單調性不成立，所以 sliding window 不行，我要改用 prefix sum 加 hash map。」能自己發現並修正問題，本身就是很好的訊號。

## 2.8 面試官的評分維度

各公司的評分表細節不公開，但公開的準備資料與面經普遍描述，coding interview 的回饋大致圍繞四個維度：problem solving（解題能力）、coding（程式能力）、verification（驗證）、communication（溝通）。面試官寫回饋時，通常需要用具體的觀察支持每個維度的評價，例如「候選人在沒有提示的情況下指出 O(n²) 的瓶頸並改用 hash map」，所以你的每一個好行為都要讓面試官「看得到」。

| 維度 | 面試官在看什麼 | 弱的表現 | L5 等級的表現 |
|---|---|---|---|
| Problem solving | 能否把模糊問題變成清楚的演算法、能否自己推到最佳解 | 需要多次提示、直接跳到背過的答案卻說不出理由 | 主動釐清、從暴力解推導、說得出關鍵觀察與取捨 |
| Coding | 程式是否正確、結構是否清楚、語言是否熟練 | 邏輯散亂、變數命名不清、大量臨時修補 | 一次寫出結構清楚的程式，邊界處理自然融入，能抽出輔助函式 |
| Verification | 是否主動測試、能否自己找到 bug | 宣稱完成但沒測，bug 由面試官指出 | 主動手動追蹤範例與邊界，自己發現並修正錯誤 |
| Communication | 思考過程是否透明、能否接收與回應回饋 | 長時間沉默、或不斷說話卻沒有資訊 | 說出意圖與決策、適時確認方向、清楚接住提示 |

有幾點值得補充。第一，這四個維度不是各自獨立打分後平均：一個正確但需要大量提示的解，problem solving 的評價會偏低，即使 coding 很漂亮。第二，速度是隱含的因素：在時間內完成最佳解，加上有餘裕回答 follow-up，通常是強烈推薦的前提。第三，senior 職級的期待會更強調主導性，也就是你推著解題往前走，而不是由面試官一步一步牽著走。

本書在每題的「思路」都按照這個順序寫：暴力解、瓶頸、關鍵觀察、invariant。讀的時候可以把它當成「如果我在面試中，要依序說出哪些話」的腳本。

## 2.9 常見扣分行為

下面這些行為在公開面經與面試官分享中經常被提到。大多數不是能力問題，而是習慣問題，所以可以透過練習修正。

| 扣分行為 | 為什麼扣分 | 怎麼改 |
|---|---|---|
| 沒問就開始寫 | 容易解錯題，也顯示不重視需求 | 固定先花 3–5 分鐘釐清，並用小例子重述題意 |
| 長時間沉默 | 面試官無法評估思考，也無法給提示 | 卡住時說出「我正在考慮什麼」 |
| 直接寫出背過的最佳解卻說不出原因 | 看起來像背題，problem solving 評價低 | 仍然簡述暴力解與瓶頸，說出關鍵觀察 |
| 程式寫完不測試 | verification 維度直接失分 | 固定用範例＋一個邊界手動追蹤 |
| 用面試官當編譯器 | 每改一行就問「這樣對嗎」 | 自己追蹤，有把握後再說明 |
| 忽略提示或和面試官爭論 | 顯示難以合作 | 先複述提示，理解後再表達不同意見並給理由 |
| 宣稱錯誤的複雜度 | 讓人懷疑基本功 | 每個迴圈與資料結構操作逐一說明 |
| 過度工程 | 浪費時間，例如為簡單題設計複雜類別 | 先寫最直接的正確版本，再談擴展 |
| 放棄或明顯慌亂 | 剩下的時間無法提供任何訊號 | 用 2.7 節的步驟，至少完成暴力解 |

特別說明「直接寫出背過的最佳解」這一項。如果你一眼就認出題目，直接講最佳解本身沒問題，但仍要用一兩句話交代為什麼：「暴力解是 O(n²)，因為瓶頸是重複查詢前綴中某個值的次數，所以用 hash map。」這樣面試官看到的是理解，而不是記憶。

## 2.10 Follow-up 的應對

在主要題目完成後，面試官通常會追問變形。Follow-up 的目的有兩個：如果主題目做得很順，用它來測試理解的深度；如果時間剩很多，用它來取得更多訊號。所以 follow-up 是加分的機會，而不是額外的考驗。

常見的 follow-up 類型與應對方式：

| 類型 | 例子（以本章範例題為例） | 應對方式 |
|---|---|---|
| 改變限制 | 「如果記憶體只能 O(1)？」 | 先原地排序再用 two pointers，O(n log n) 時間；要說明 Python 的 `sort` 最壞需要 O(n) 暫存，嚴格 O(1) 要改用 heapsort。和為 k 時，若兩端值不同，對數是兩個相同值區段長度的乘積；若兩端值相同（例如都是 k/2），區段長度 m 貢獻 m(m-1)/2 |
| 改變輸出 | 「回傳所有索引對，而不只是數量？」 | dict 改存索引清單；指出輸出本身可能是 O(n²)，所以時間下限也是 O(n²) |
| 改變輸入形式 | 「如果 nums 是串流，每來一個數就要回報目前的對數？」 | 原本的一次掃描就是線上算法，每個新數 O(1) 更新 |
| 擴展維度 | 「如果是三個數的和？」 | 枚舉中間或第一個數，剩下變成二數問題，O(n²)；對應第 5 章 3Sum |
| 規模放大 | 「如果資料大到放不進單機記憶體？」 | 依 min(x, k - x) 的雜湊值分桶，讓 x 和它的配對值 k - x 一定落在同一桶，各桶可以獨立在單機計算再加總 |

應對 follow-up 的原則是：先確認問題（「你是指每來一個數就要回報，對嗎？」），再說出從原解法到新問題的差異在哪裡，最後給出具體做法與複雜度。如果時間允許而且面試官希望，再寫程式。不要只說「可以用更好的資料結構」這種空泛的答案，要說出是哪個資料結構、為什麼、複雜度變成多少。

本書每題都附至少三個 follow-up，而且都是針對那一題的具體變形。練習時請先蓋住答案自己回答，再對照，這是最接近真實面試的練習方式。

## 本章重點整理

- 45 分鐘的典型分配：釐清 5 分鐘、設計 7 分鐘、寫程式 15 分鐘、驗證 7 分鐘、複雜度與 follow-up 5 分鐘；15 分鐘還沒方向就先寫暴力解。
- 釐清題目要問會影響解法的問題：輸入範圍、重複、空輸入、是否排序、回傳格式、無解時的處理，並用小例子重述題意。
- 聽到 n 的範圍就換算可接受的複雜度，這是從限制推出方向的關鍵動作（第 3 章）。
- 先講暴力解與複雜度，再說出瓶頸；優化的方向通常藏在瓶頸裡：重複查詢、可排序、單調性、只保留有用候選、重疊子問題。
- 寫程式時說出意圖與決策，先講骨架再填細節，並主動指出關鍵 invariant。
- 寫完一定要驗證：用範例與邊界清單手動追蹤；練習時用暴力解隨機對拍找出最小失敗輸入。
- 完整的複雜度說明包含時間、空間、理由，以及是最壞、平均還是 amortized。
- 卡住時說出卡在哪、縮小問題、手算觀察、換 pattern、放寬限制，最後至少寫出暴力解；接住提示是正面訊號。
- 評分大致圍繞 problem solving、coding、verification、communication 四個維度，L5 的關鍵是主導性。
- Follow-up 要先確認問題、說出和原解法的差異，再給具體做法與複雜度。

## 延伸問答

> [!question]- Q1. 如果一看到題目就知道最佳解，還需要先講暴力解嗎？
> 需要，但可以非常簡短。用一兩句話交代「暴力解是 O(n²)，瓶頸在每次都重新掃描前綴」，然後直接說最佳解與它解決瓶頸的方式，整個過程不超過一分鐘。這樣做的價值在於讓面試官看到你理解為什麼要這樣解，而不是背出答案；problem solving 維度看的正是推導過程。如果面試官明確說「直接講你的最佳解」，就照做，但仍然要說出關鍵觀察，例如「因為只需要知道某個值出現幾次，所以 hash map 足夠」。

> [!question]- Q2. 面試環境不能執行程式，要怎麼確定自己寫對？
> 靠系統化的手動追蹤。先選一個小但有代表性的範例（三到五個元素，包含重複），列一張表追蹤每個變數在每一輪迴圈後的值，就像 2.5 節的表格那樣。接著從邊界清單挑兩三個案例：空輸入、單一元素、全部相同、答案在頭或尾，只追蹤和邊界相關的那幾行。追蹤時特別注意迴圈的起點與終點、更新與查詢的順序、遞迴的終止條件，這三處是 bug 最集中的地方。平常練習也要偶爾關掉執行環境，強迫自己用這種方式驗證。

> [!question]- Q3. 面試官一直不說話也不給回應，我該怎麼辦？
> 有些面試官的風格是盡量不干擾，沉默不代表你做錯。你可以在關鍵節點主動確認，例如設計完成時問「這個方向和複雜度可以接受嗎？我準備開始寫了」，寫完時說「我用範例追蹤一次，然後補邊界測試」。這樣即使面試官不主動回應，你也給了他介入的機會，同時讓回饋紀錄裡有清楚的溝通證據。不要因為沒有回應就停止說話，持續說出你的意圖與決策，評分仍然看得到。

> [!question]- Q4. 時間快到了程式還沒寫完，該怎麼處理？
> 先主動告訴面試官現況與剩下的計畫，例如「主流程已經完成，剩下的是處理環的情況，我打算用 visited 集合在進入節點時檢查」。接著判斷剩餘時間：如果只剩幾分鐘，用註解或口頭描述把缺的部分補完，把時間留給追蹤已完成部分的正確性；如果還有五分鐘以上，就優先寫完最核心的邏輯，次要的輸入檢查可以口頭帶過。一個結構清楚、說明完整但缺一小段的解，通常比一個勉強寫完但充滿 bug 的解評價更好。

> [!question]- Q5. 兩題的面試形式要怎麼調整節奏？
> 兩題形式的關鍵是壓縮釐清與設計，保留驗證。每題大約 18–20 分鐘：釐清 2–3 分鐘、設計 2–3 分鐘、寫程式 8–10 分鐘、驗證 3 分鐘。這種節奏只有在核心題非常熟練時才做得到，所以準備時要把每章的核心題練到 10–15 分鐘一次寫對。另一個技巧是釐清時只問真正影響解法的兩三個問題，其他用「我假設……」帶過。第一題不要拖太久，如果第一題超時，第二題通常沒有機會完成，整體評價會受影響。

> [!question]- Q6. 面試官給的提示和我的想法不同，我該照他的方向還是堅持自己的？
> 先確認你理解提示的意思，例如複述「你是建議我先排序嗎？」。如果你的方向也能走通而且複雜度一樣好，可以簡短說明：「我原本想用 hash map，也是 O(n)，差別在空間；如果你希望 O(1) 空間，我就改用排序加 two pointers。」讓面試官選擇。如果你不確定自己的方向是否可行，就跟著提示走，因為提示通常代表面試官看到你的方向有問題，或希望看到某個特定技巧。無論如何，不要忽略提示或和面試官爭論。

> [!question]- Q7. 怎麼練習「邊寫邊說」？自己練的時候覺得很彆扭。
> 彆扭是正常的，因為同時思考和說話需要額外的練習。建議從錄音開始：每天選一道已經會的核心題，計時並錄下完整的解題過程，從重述題意到複雜度分析。回放時檢查三件事：有沒有超過 30 秒的沉默、有沒有說出關鍵決策的理由、複雜度說明是否完整。熟悉之後再找朋友或用模擬面試平台練習，讓對方隨機打斷你提問。第 31 章的六場模擬面試附有評分重點，可以作為練習的對照表。

> [!question]- Q8. 寫程式時要不要處理所有的輸入檢查，例如 None 或型態錯誤？
> 通常不需要，但要說出來。面試題的重點是演算法，大量的防禦性檢查會稀釋主邏輯，也浪費時間。好的做法是在釐清階段確認輸入的保證，例如「我假設輸入是合法的整數陣列，可能為空」，然後只處理題目語意上的邊界：空輸入、單一元素、無解。如果面試官關心健壯性，他會追問，這時再說明你會怎麼加入檢查，例如在函式開頭驗證參數並丟出明確的例外。對 senior 職級來說，說得出取捨比寫滿檢查更重要。
