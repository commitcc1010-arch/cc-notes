# 第 1 章　如何使用本書：21 天看完所有 Pattern

> [!abstract] 本章地圖
> **核心問題**：在 2–3 週內，怎麼把 26 個 pattern、260 道題讀成「看到新題也會拆」的能力，而不是一堆背過的答案？
>
> **你會學到**：
> - 本書以 Google L5 等級 coding interview 為標準，這個標準具體要求什麼
> - 全書結構，以及核心題與難題各自該怎麼讀
> - 21 天的讀書節奏（細節在附錄 D）與每天的練習流程
> - 怎麼練：先自己寫、計時、再看解答，以及怎麼判斷「真的會了」
> - 怎麼複習：錯題本與間隔重複（附一個可執行的排程小程式）
> - Google、Meta、Amazon、Microsoft、Apple 在 coding interview 上的公開傾向
> - 本書選題的方法與它的限制

## 1.1 本書的標準：Google L5 等級的 coding interview

本書把目標設在 Google L5（senior software engineer）同等級的 coding interview。選這個標準不是因為每個人都要去 Google，而是因為它在公開面經中的描述相對一致：題目多半是 Medium 到 Hard、會有連續的 follow-up、面試官重視推導過程而不只是最後的程式。只要能在這個標準下穩定表現，其他公司同等級（例如 Meta E5、Amazon SDE II 到 Senior、Microsoft Senior）的 coding 回合通常也能應付。

要注意的是，coding 回合本身的題目難度，在 L4 和 L5 之間不一定差很多。公開面經普遍描述的差別在於「表現的成熟度」：L5 候選人被期待主動釐清需求、自己提出暴力解並說明瓶頸、不需要提示就走到最佳解或接近最佳解、程式結構乾淨、主動測試，並且在 follow-up 中能討論取捨。換句話說，同一題答對，L4 的表現可能是「在提示下寫出正確解」，L5 的表現則是「主導整個解題過程」。L5 的面試流程通常還包含 system design 與 behavioral，那些不在本書範圍內。

本書用下面這張表把 L5 的期待拆成可練習的行為。這張表是本書的寫作標準，不是任何公司的官方評分表；第 2 章會再把它展開成每個評分維度的具體做法。

| 面向 | 勉強通過的表現 | L5 等級的表現 |
|---|---|---|
| 理解題目 | 聽完直接寫 | 先問輸入範圍、重複、空輸入、回傳格式，並用一個小例子確認理解 |
| 找解法 | 需要提示才想到關鍵資料結構 | 主動說出暴力解與複雜度，指出瓶頸，自己推到最佳解 |
| 寫程式 | 能動但變數命名混亂、邏輯散落 | 結構清楚、有輔助函式、邊界處理一次到位 |
| 驗證 | 面試官指出 bug 才修 | 寫完自己拿範例與邊界手動追蹤，主動找到並修掉 bug |
| 複雜度 | 只說時間複雜度 | 時間與空間都講，說得出為什麼，知道最壞情況在哪 |
| Follow-up | 卡住或只能說「可以優化」 | 能針對變形給出具體做法、複雜度與取捨 |

本書每一題的思路、follow-up 與心得都依照右欄撰寫。讀的時候不要只看程式，要特別注意「為什麼想到這個做法」「瓶頸在哪」「面試官接著會問什麼」這三件事，因為它們才是 L5 和 L4 表現的分水嶺。

## 1.2 全書結構

全書分成八個 Part 和四個附錄。Part 0 是面試作業系統，也就是你正在讀的三章：本章講怎麼讀，第 2 章講一場面試怎麼進行與溝通，第 3 章講怎麼從 constraints（題目限制條件）推出可接受的複雜度與 pattern。Part 1 到 Part 6 是 26 個 pattern 章，從第 4 章到第 29 章，每章一個 pattern。Part 7 是衝刺：第 30 章整理各公司題型與考前準備，第 31 章是六場模擬面試。

| Part | 章 | 內容 | 讀法 |
|---|---|---|---|
| Part 0　面試作業系統 | 1–3 | 讀法、面試流程、從限制推 pattern | 第一天讀完，之後每週回頭看一次第 2、3 章 |
| Part 1　線性結構 | 4–11 | Hashing、two pointers、sliding window、prefix sum、binary search、intervals、stack、linked list | 最高頻的基礎，務必全部自己寫過 |
| Part 2　樹與堆積 | 12–14 | Binary tree、BST 與 Trie、heap | 遞迴思維的基礎，DP 章會反覆用到 |
| Part 3　圖 | 15–18 | BFS／DFS、topological sort、union-find、shortest path 與 MST | 重點在「把題目建模成圖」 |
| Part 4　搜尋與貪婪 | 19–20 | Backtracking、greedy | 要能說明 greedy 為什麼正確 |
| Part 5　Dynamic Programming | 21–24 | 一維與狀態機、二維與序列、背包與區間、樹／bitmask／數位 | 花最多時間的一段，重點在狀態定義 |
| Part 6　進階主題 | 25–29 | 字串演算法、range query、資料結構設計、bit 與數學、模擬與解析 | 難題比例高，依目標公司取捨 |
| Part 7　衝刺 | 30–31 | 大廠題型、模擬面試 | Day 21 讀完，考前一週再依附錄 D 的 7 天版使用 |

附錄 A 是 Python 面試工具箱，附錄 B 是複雜度與 constraints 速查，附錄 C 是全題索引，附錄 D 是 21 天、14 天與 7 天讀書計畫。附錄是工具，不必從頭讀到尾，遇到需要時翻查即可。

Pattern 章的順序有刻意安排：後面的章會用到前面的工具。例如第 6 章 sliding window 會用到第 4 章的計數 hash map；第 14 章的 heap 是第 18 章 Dijkstra 的基礎；第 12 章的 tree DFS 是第 24 章 tree DP 的前身。所以第一次讀建議照順序，第二輪複習時再依弱點跳著讀。

## 1.3 一個 pattern 章怎麼讀：核心題與難題

每個 pattern 章都有相同的骨架：先用四到五個編號小節講這個 pattern 解決什麼問題、辨識訊號、模板與原理、常見錯誤；接著是 5 道核心題與 5 道難題；最後是 Pattern 歸納與本章重點整理。固定結構的好處是你可以預期每一節要拿到什麼，複習時也能直接跳到需要的位置。

**核心題**代表「這個 pattern 一定要會的標準形」。它們的特徵是：題目一讀完就應該想到 pattern，難的地方在細節（邊界、invariant、off-by-one）。核心題的目標是寫到不看解答、10–20 分鐘內一次寫對。讀法是先自己寫，再對照書上的思路與程式，特別比較自己的邊界處理和書上有什麼不同。

**難題**代表「這個 domain 的上限與主要變形」。它們的難點通常不是程式長，而是需要一個額外的觀察：換一個角度定義狀態、把問題轉成另一個 pattern、或是組合兩個 pattern。難題的目標不是背下來，而是理解「突破點是怎麼被想到的」。所以每道難題都有三段漸進提示，請一次只展開一段，展開後再想五分鐘，真的想不出來才看下一段。

| 項目 | 核心題 | 難題 |
|---|---|---|
| 目標 | 熟練、一次寫對 | 理解突破點，能在新題上複製思考方式 |
| 第一次限時 | 15–20 分鐘 | 30–40 分鐘（含看提示的時間） |
| 卡住時 | 看「思路」的第一段，再自己寫 | 依序展開提示 1、2、3 |
| 讀完要能說出 | 模板的 invariant、邊界怎麼處理 | 為什麼直覺做法不行、突破點是什麼 |
| 複習頻率 | 依錯題本排程 | 至少重寫一次，之後只複習「心得」 |
| 是否所有人都要做 | 是 | 依目標調整：目標 L5 建議 Part 1–5 每章至少自己寫 3 題，Part 6 依目標公司取捨（附錄 D 預設每章 2 題） |

每題最後的 follow-up 請不要跳過。原題可能靠記憶就能寫出來，但當限制被改動（例如「陣列有負數怎麼辦」「如果要回傳所有解」「如果資料是串流」），能不能順利推導，才是判斷你真正理解的方式。面試中的 follow-up 也多半長這樣，所以把 follow-up 當成「同一題的第二、第三個版本」來練。

## 1.4 21 天節奏

本書預設每天 2–3 小時、21 天讀完，詳細的每日分配在附錄 D（另有 14 天快速版與 7 天考前衝刺版）。這裡先給整體節奏，讓你知道每一週的重心在哪裡。

```text
第 1 週：基礎與線性結構（Part 0、Part 1）
  Day 1      第 1–3 章：建立讀法、面試流程、constraints 判讀
  Day 2–7    第 4–11 章：每天 1–2 章，核心題全部自己寫
  Day 7 晚上 回顧本週錯題，重寫 3 題

第 2 週：樹、圖、搜尋（Part 2、Part 3、Part 4）
  Day 8–10   第 12–14 章
  Day 11–14  第 15–20 章：圖要畫出來，greedy 要說出為什麼對
  Day 14 晚上 用第 3 章的決策樹，隨機抽 5 題只做「判斷 pattern」

第 3 週：DP、進階、衝刺（Part 5、Part 6、Part 7）
  Day 15–18  第 21–24 章：每題先寫出狀態定義再寫程式
  Day 19–20  第 25–29 章：依目標公司挑重點
  Day 21     第 30–31 章：模擬面試兩場，回顧錯題本
```

這個節奏的設計原則有三個。第一，先廣後深：第一輪讓所有 pattern 都見過一次，比把某一章讀到完美更重要，因為辨識 pattern 需要知道「有哪些選項」。第二，每週留一段時間只做判斷不寫程式，因為面試中最常卡住的地方是「不知道該用什麼」，而不是「知道了卻寫不出來」。第三，DP 放在最後一週並給最多時間，因為它最依賴前面的遞迴與狀態思維。

如果時間不夠，優先保留的是：Part 0 全部、每章核心題、每章的「辨識訊號」與「Pattern 歸納」。難題可以只做每章 2–3 題，其餘讀提示與心得即可。反過來，如果你有更多時間，不要急著加新題，而是把錯題本裡的題目重寫到穩定，這通常比多做二十題新題更有效。

## 1.5 怎麼練：先自己寫、計時、再看解答

讀解答的感覺很像學會了，但面試考的是「沒有解答時能不能做出來」。所以每一題請照下面的四步流程練，即使題目看起來很簡單也一樣，因為簡單題正是練習完整流程的好機會。

```text
步驟 1　讀題（2 分鐘）
        只讀「題目」小節，遮住思路。寫下你會問面試官的釐清問題。

步驟 2　自己解（核心題 15–20 分鐘，難題 30–40 分鐘）
        先在紙上或註解中寫出：暴力解與複雜度 → 瓶頸 → 你的做法 → 複雜度
        再寫程式，寫完用範例手動追蹤一次。
        計時，時間到就停，記下卡在哪一步。

步驟 3　對照（10 分鐘）
        讀思路與解法，比較：
        - 你的暴力解和瓶頸分析是否一致？
        - 你漏了哪個邊界？
        - 書上的程式哪裡比你的乾淨？

步驟 4　關掉解答重寫（10 分鐘）
        不看任何東西重寫一次並執行測試。
        寫不出來，代表你記住的是答案，不是推導。
```

計時很重要，因為面試的壓力主要來自時間。本書建議的時間對應第 2 章的 45 分鐘分配：一道 Medium 在面試中大約有 20–25 分鐘可以寫程式與測試，所以平常練習要做到 15–20 分鐘內完成，才留得下緊張與溝通的餘裕。

練習時請在真正會執行的環境寫，並且養成自己寫測試的習慣。本書每段程式都附 `assert` 測試，你自己的版本也應該這樣：至少放題目範例、一個邊界情況（空輸入、單一元素、全部相同），以及一個你覺得最容易出錯的情況。第 2 章 2.5 節會示範如何用暴力解對拍（brute-force cross check）快速找出最佳解的 bug。

一個常被忽略的練習是「出聲解題」。面試時你必須邊想邊說，而這需要練習：很多人安靜時能解出來，一開口講話就亂掉。建議每天至少一題，用錄音或對著空氣講完整個過程，從釐清問題講到複雜度分析。第 2 章會給每個階段該說什麼。

怎麼判斷一題「真的會了」？本書用三個標準：一、隔三天以上，不看任何提示能在時間內寫對；二、能用兩三句話講出為什麼這樣解（關鍵觀察是什麼）；三、能回答書上至少兩個 follow-up。三個都達成，這題才從錯題本畢業。

## 1.6 怎麼複習：錯題本與間隔重複

做過一次的題目，一週後通常會忘掉一大半細節，這是正常的。對抗遺忘最有效的方式是間隔重複（spaced repetition）：在快忘記的時候重做一次，每次成功就把下次複習的間隔拉長，失敗就縮短。這比「做完一輪再從頭做一輪」省時間得多，因為已經穩定的題目不必反覆浪費時間。

錯題本不是收集「做錯的題目」，而是收集「做錯的原因」。同一題可能因為完全不同的原因錯：沒辨識出 pattern、知道 pattern 但狀態定義錯、邏輯對但邊界錯、超時。原因不同，複習方式也不同。建議每筆紀錄包含下面這些欄位：

| 欄位 | 範例 | 用途 |
|---|---|---|
| 題目與章節 | 第 7 章核心題 2（560） | 定位 |
| 錯誤類型 | 辨識、建模、邊界、複雜度、程式細節 | 決定複習方式 |
| 一句話原因 | 有負數所以 sliding window 不成立，要用 prefix sum ＋ hash map | 下次讀這一句就能回想 |
| 下次複習日 | 由排程決定 | 間隔重複 |
| 階段 | 0–4 | 決定下次間隔 |

錯誤類型對應的複習方式：「辨識」錯的題目，複習時只讀題目、說出 pattern 和理由，不必重寫；「建模」錯的題目，要重新寫出狀態定義與轉移；「邊界」與「程式細節」錯的題目，一定要重寫並執行測試；「複雜度」錯的題目，重看第 3 章對應的分析方法。

下面是一個最小的間隔重複排程器。它用 1、3、7、14、30 天的間隔：成功就進到下一階段，失敗就退回第 0 階段，通過第 4 階段即畢業。你可以直接拿它管理自己的錯題本，或照這個規則在紙本或試算表上執行。

```python
from dataclasses import dataclass, field
from datetime import date, timedelta

INTERVALS = [1, 3, 7, 14, 30]  # 每個階段到下次複習的天數


@dataclass
class Card:
    problem: str
    reason: str
    stage: int = 0
    due: date = field(default_factory=date.today)
    graduated: bool = False

    def review(self, today: date, success: bool) -> None:
        """記錄一次複習結果，更新階段與下次複習日。"""
        if success:
            if self.stage == len(INTERVALS) - 1:
                self.graduated = True
                return
            self.stage += 1
        else:
            self.stage = 0
        self.due = today + timedelta(days=INTERVALS[self.stage])


def due_today(cards: list[Card], today: date) -> list[Card]:
    """回傳今天該複習的題目，越早到期的越前面。"""
    pending = [c for c in cards if not c.graduated and c.due <= today]
    return sorted(pending, key=lambda c: (c.due, c.problem))


d0 = date(2026, 1, 1)
card = Card("第 7 章核心題 2（560）", "有負數，sliding window 不成立", due=d0)
card.review(d0, success=True)
assert card.stage == 1 and card.due == d0 + timedelta(days=3)
card.review(card.due, success=False)          # 失敗退回第 0 階段
assert card.stage == 0 and card.due == d0 + timedelta(days=4)

other = Card("第 8 章核心題 1（34）", "左右邊界寫反", due=d0 + timedelta(days=2))
cards = [card, other]
assert [c.problem for c in due_today(cards, d0 + timedelta(days=4))] == [other.problem, card.problem]
assert due_today(cards, d0) == []             # 還沒到期

g = Card("畢業測試", "x", due=d0)
day = d0
for _ in range(len(INTERVALS) - 1):      # 0→1→2→3→4
    g.review(day, success=True)
    day = g.due
assert not g.graduated and g.stage == 4
g.review(day, success=True)
assert g.graduated and due_today([g], day + timedelta(days=100)) == []
print("all tests passed")
```

實務上，每天先處理到期的錯題（通常 20–40 分鐘），再讀新的章節。如果某天到期的題目太多，優先處理「辨識」類，因為它們只需要幾分鐘；寫程式類的可以延到隔天。不要因為進度落後就跳過複習，第三週的 DP 會大量用到前兩週的工具，前面忘光會讓後面更慢。

## 1.7 大廠題型傾向總覽

不同公司的 coding interview 在形式與偏好上有差異，但差異沒有很多人想像的大：26 個 pattern 在各大廠都可能出現。下面整理的是公開資訊（公司招募頁面、官方說明）與公開面經中反覆出現的普遍描述，全部是定性傾向，不是統計。面試形式會隨時間、職級、團隊與地區改變，請以招募人員（recruiter）提供的說明為準。第 30 章會再把每家公司的傾向對應到本書具體題目。

| 公司 | 公開資訊與普遍描述的形式 | 題型傾向（定性） | 準備重點 |
|---|---|---|---|
| Google | 技術初篩後進入多輪面試，每輪約 45 分鐘；senior 職級通常加入 system design 與行為面試；面試回饋交由 hiring committee 審查 | 題目常從簡單版本開始，再用 follow-up 層層加難；graph、DP、資料結構設計、需要自己建模的題目常見；通常在共享編輯器寫程式，不一定能執行 | 推導過程與溝通；能在沒有執行環境的情況下手動驗證；follow-up 的深度 |
| Meta | 公開面經常描述一輪 coding 約 45 分鐘、常有兩題；另有 system design（或 product architecture）與行為面試 | 常見題型的標準形或小變形：陣列、字串、hashing、tree、graph BFS／DFS、intervals、two pointers | 速度與一次寫對；核心題要非常熟練 |
| Amazon | 官方強調 Leadership Principles，面試團隊中有 Bar Raiser 角色；公開面經常描述行為問題會穿插在技術回合中，面試前常有線上測驗（OA） | 題目常帶實務情境（處理 log、排程、設計小型類別）；heap、BFS、hashing、物件導向設計常見 | 程式可讀性與可擴充性；準備好 LP 故事 |
| Microsoft | 公開面經普遍描述形式依團隊而異，面試官多為未來團隊成員 | 偏實務的中等難度題：字串、linked list、tree、矩陣、設計題 | 程式品質、溝通、和團隊領域相關的討論 |
| Apple | 公開面經普遍描述高度依團隊而異，常包含領域知識 | coding 題難度多為中等，但會深挖實作細節、效能與邊界 | 熟悉目標團隊的技術領域；把基本題寫得非常扎實 |

從這張表可以得到兩個實用結論。第一，核心題的熟練度在各家都重要：Meta 類型的面試要求速度，Google 類型的面試則用核心題當起點再追問，兩者都需要你把標準形寫到不用想。第二，難題的價值在於「思考方式」：遇到 Google 式的 follow-up 或沒看過的題目時，你需要的是難題教你的轉換技巧，而不是某一題的答案。

如果你只準備一家公司，可以依上表調整比例，但不建議完全放棄任何一個 Part。面試官出題有很大的個人差異，公開面經裡也經常看到同一家公司出現風格很不同的題目。

## 1.8 本書選題的方法與限制

本書 260 道題的選擇依據是公開資料：Blind 75、NeetCode 150、Grind 169、LeetCode Top Interview 150 等常見準備清單，以及 Google、Meta、Amazon、Microsoft、Apple 公開面經中反覆出現的題型。選題流程是先依 pattern 分類，再為每個 pattern 選出兩組題目：核心題選「最能代表標準形、在多份清單中都出現」的題目；難題選「代表這個 pattern 主要變形與上限」的題目，例如需要組合兩個 pattern、需要額外觀察、或需要進階資料結構的題目。

這個方法有幾個你應該知道的限制：

- **公開面經有偏差**。願意分享的通常是印象深刻的經驗，太簡單或太奇怪的題目可能被低估或高估；不同地區、職級的樣本也不平均。
- **題庫會變動**。公開面經中常提到，被大量公開討論的題目可能會被汰換，所以實際面試中很可能遇到沒看過的題目。這正是本書強調 pattern 辨識而非背題的原因。
- **本書不提供頻率數字**。我們無法取得可靠的公司內部出題統計，所以全書只用「常見」「公開面經中經常出現」這類定性描述，不會寫出某題在某公司出現的比例。
- **LeetCode 難度標籤只是參考**。難題區的題目不一定標 Hard；有些 Medium 題在加上 follow-up 後比很多 Hard 更能測出理解程度。
- **coding 回合只是面試的一部分**。L5 等級的流程通常還有 system design 與行為面試，本書不涵蓋。

最後一個提醒：本書的題目都用自己的話重述並重新設計範例，程式都經過執行測試。但演算法題的解法通常不只一種，如果你的做法和書上不同，先確認它的正確性與複雜度，再思考兩種做法的取捨，這本身就是很好的 follow-up 練習。

## 本章重點整理

- 本書以 Google L5 等級 coding interview 為標準：L5 和 L4 的差別多半不在題目難度，而在是否能主導釐清、推導、驗證與 follow-up。
- 全書分成 Part 0 到 Part 7：第 1–3 章是方法論，第 4–29 章是 26 個 pattern，第 30–31 章是衝刺；附錄是查詢用的工具。
- 核心題的目標是熟練到 10–20 分鐘一次寫對；難題的目標是理解突破點是怎麼被想到的，提示一次只展開一段。
- 21 天節奏是先廣後深：第一週線性結構、第二週樹圖搜尋、第三週 DP 與衝刺；時間不夠時優先保留核心題、辨識訊號與 Pattern 歸納。
- 每題照四步練：讀題寫下釐清問題、限時自己解、對照解答、關掉解答重寫；並練習出聲解題。
- 一題「真的會了」的標準：隔三天後能在時間內寫對、能說出關鍵觀察、能回答至少兩個 follow-up。
- 錯題本記錄的是錯誤原因與類型，並用間隔重複（1、3、7、14、30 天）安排複習。
- 各大廠的 coding interview 有傾向差異，但 26 個 pattern 都可能出現；公司資訊以 recruiter 說明為準。
- 本書選題依據公開清單與公開面經，不提供頻率數字；實際面試很可能遇到沒看過的題目，所以重點是辨識與推導。

## 延伸問答

> [!question]- Q1. 我只有 10 天，應該怎麼砍內容？
> 先保留 Part 0 全部，因為它決定你能不能把會的東西在面試中表現出來。接著每個 pattern 章只做 5 道核心題，並讀完「辨識訊號」「常見錯誤」與「Pattern 歸納」，難題只讀提示與心得、不必寫程式。Part 6 依目標公司取捨，例如字串演算法與 range query 可以只看核心題。最後兩天保留給第 31 章的模擬面試與錯題重寫。附錄 D 的 7 天與 14 天版本可以直接拿來改。

> [!question]- Q2. 核心題我都寫得出來，但要 30 分鐘以上，怎麼加速？
> 慢通常有三個來源，要先分辨是哪一個。第一是想解法慢：代表 pattern 辨識還不夠熟，複習時多做「只看題目、30 秒內說出 pattern 和理由」的練習。第二是寫程式慢：代表模板不夠熟，把每章第 3 個編號小節（例如 8.3 節）的模板默寫到不用想，邊界寫法固定成習慣。第三是 debug 慢：代表寫之前沒想清楚 invariant，試著在寫程式前先用一兩句話寫下迴圈每一輪結束時什麼條件成立。三者分開練，比單純多刷題有效。

> [!question]- Q3. 看提示算作弊嗎？什麼時候應該直接看答案？
> 看提示不算作弊，提示的設計目的就是讓你在最少的幫助下自己走完推導，這比直接看答案的學習效果好得多。原則是展開一段提示後至少再想五分鐘，真的沒有新進展才看下一段。三段提示都看完仍然沒有方向，就直接讀詳解，但讀完一定要關掉解答重寫一次，並在錯題本記下「卡在哪一段提示」，因為那正是你缺少的觀察。如果同一章有多題卡在同一種觀察，回頭重讀該章的模板與原理。

> [!question]- Q4. 書上的解法和我的不一樣，但我的也通過測試，要改成書上的嗎？
> 不一定。先確認三件事：複雜度是否一樣好、邊界是否都處理了（可以用第 2 章 2.5 節的暴力解對拍隨機測試）、程式是否同樣容易解釋。如果三者都沒問題，保留你自己的做法，因為你寫得最熟的版本在面試中最可靠。但仍然要讀懂書上的做法，因為它通常是在 follow-up 中更容易擴展的那一個；面試官也可能問「有沒有別的做法」，能比較兩種解法的取捨是很好的加分。

> [!question]- Q5. 為什麼要以 Google L5 為標準？我面的是其他公司或 L4。
> 因為這個標準涵蓋了大多數公司 coding 回合要求的能力，而且在公開面經中描述得相對清楚：中高難度題、連續 follow-up、重視推導與驗證。用較高的標準準備，面對要求較低的面試時會比較從容，反過來則不成立。如果你面 L4 或新鮮人職位，可以降低難題的比例，但第 2 章的溝通流程與第 3 章的 constraints 判讀仍然完全適用，因為它們影響的是你把會的東西表現出來的能力，跟職級無關。

> [!question]- Q6. 間隔重複的間隔一定要是 1、3、7、14、30 天嗎？
> 不必。這組間隔只是常見且好記的起點，重點是「成功就拉長、失敗就縮短」這個機制。如果你的準備時間只有兩到三週，30 天的間隔永遠不會到，可以改成 1、2、4、7、12 天，讓每題在考前至少複習三到四次。另一個調整是依錯誤類型分開：辨識類錯誤的複習成本低，可以更頻繁；寫程式類錯誤每次要花十幾分鐘，間隔可以稍長。1.6 節的程式只要改 `INTERVALS` 就能套用。

> [!question]- Q7. 面試會用的語言不是 Python，讀這本書還有用嗎？
> 有用。pattern 的辨識、invariant、複雜度分析與 follow-up 的思路都和語言無關，書上的思路與視覺化可以直接套用。你需要額外做的是把每章的模板翻譯成你的語言，並特別注意語言差異造成的細節：例如 Python 整數不會溢位但 Java 與 C++ 會，Python 的 `heapq` 是 min-heap，Java 的 `PriorityQueue` 預設也是 min-heap 但比較器寫法不同。建議第一輪就用你面試的語言寫，不要先用 Python 再翻譯，因為面試中的流暢度來自實際寫過。

> [!question]- Q8. 公開面經上看到某公司「最常考」某些題，可以只準備那些嗎？
> 不建議。公開面經有樣本偏差，而且公開面經中經常提到，被大量討論的題目可能會被汰換，所以實際面試很可能是你沒看過的變形。那些題目可以當成優先練習的清單，但準備的重點仍應該是 pattern：知道一個 pattern 的所有主要變形，比背十道熱門題更能應付新題。比較好的用法是拿熱門題當測驗：讀完一個 Part 後，挑幾道該公司常見的題目，看自己能不能在時間內判斷 pattern 並寫出來，以此檢驗準備是否到位。
