# 第 30 章　大廠題型與最後衝刺

> [!abstract] 本章地圖

>
> **你會學到**：

> - 每家公司常見的 pattern，以及本書中對應的練習題
> - Google L5 coding 回合的評分重點，以及 senior 等級多出來的期待

> - 面試當天的檢查清單

## 30.1 先讀這一節：怎麼解讀各公司的面試資訊

本章前半整理五家公司的面試形式與題型傾向。這些內容全部來自公開資訊（公司招募頁面與官方準備說明）與公開面經中反覆出現的普遍描述，**不是**任何公司內部的出題統計。我們沒有可靠的頻率數字，所以本章只用「常見」「公開面經中經常提到」這類定性描述，也不會說某一題在某家公司「出現幾次」。

讀這些資訊時有三個前提要記住。第一，面試流程會變動：輪數、每輪長度、是否有線上測驗、能不能執行程式、是否允許使用 AI 工具等細節，會隨年份、職級、地區與團隊改變，一切以 recruiter（招募人員）告知的為準。拿到面試邀請後，直接問 recruiter「coding 回合有幾輪、每輪多長、用什麼編輯器、能不能執行程式、使用什麼語言」，這些都是正常且受歡迎的問題。第二，面試官的個人差異往往大於公司差異：同一家公司的兩位面試官，出題風格可能完全不同。第三，公開面經有樣本偏差，印象深刻的題目被分享得比較多，所以「常見」只代表值得優先練，不代表一定會考。

基於這三點，本章對各公司的建議是「調整比例」，而不是「只準備某些題」。第 1 章 1.7 節已經給過一張總覽表，本章在那張表的基礎上，把每家公司的傾向對應到本書具體題目，並說明這些傾向對你的作答方式有什麼影響。不論目標是哪一家，下面這組能力是共通的底線：

```text
各家共通的底線（不論公司）
─────────────────────────────────────────────────────────
1. 核心題熟練：每章 5 道核心題能在 15–20 分鐘內一次寫對
2. 溝通流程：釐清 → 暴力解 → 瓶頸 → 最佳解 → 寫 → 驗證（第 2 章）
3. 從限制推複雜度：聽到 n 的範圍就換算上限（第 3 章）
4. 手動驗證：不能執行程式時，能用小例子追蹤到抓出 bug
5. Follow-up：能針對變形說出具體做法與複雜度
```

## 30.2 Google：從簡單版本出發，用 follow-up 層層加深

**形式。** 公開資訊與面經普遍描述的流程是：recruiter 聯繫後，先有一到兩輪技術初篩（通常是線上 coding），通過後進入多輪面試，每輪約 45 分鐘。軟體工程職位的面試以 coding 為主，senior 職級通常另有 system design，以及評估合作與領導方式的行為面試。Google 官方的準備說明中提到，面試回饋會交由 hiring committee 綜合審查，而不是由單一面試官決定，所以每一輪的書面回饋都很重要。coding 回合常見的環境是共享文件或簡單的線上編輯器，公開面經中經常提到不一定能執行程式，因此手動追蹤的能力格外關鍵。

**題型傾向。** 公開面經中常描述的風格是「題目一開始看起來不難，接著用 follow-up 把它推向更難的版本」。例如先問一個網格上的連通問題，接著改成「格子會一個一個變成陸地，每次都要回報島嶼數」，再問「如果網格大到放不進記憶體」。另一個常被提到的特色是題目常需要自己建模：題目不會直接說「這是一張圖」，你要從描述中看出節點與邊是什麼。graph、DP、需要額外觀察的 binary search、資料結構設計都常見。

**對作答的影響。** 因為題目會層層加深，第一版的解法要寫得容易擴充：變數命名清楚、邏輯抽成輔助函式，這樣 follow-up 來的時候你只需要改一小塊。也因為回饋要經過 committee 審查，你的推導過程要「說出來留下紀錄」，例如明確講出「n 到 10⁵，所以 O(n²) 不行」。

| 連通性與動態合併 | 「逐步加入」型 follow-up 的標準答案 | 第 17 章核心題 3（721）、第 17 章難題 2（778） |

## 30.3 Meta：兩題、速度與一次寫對

**形式。** 公開面經中經常描述的形式是：一輪技術初篩，接著是包含多輪 coding、system design（或 product architecture）與行為面試的完整面試。一個常被提到的特色是一輪 45 分鐘的 coding 常要做兩題，所以每題實際可用的時間只有約 20 分鐘。公開討論中也提到近年有試行不同形式的 coding 回合，這類變化更新得很快，務必以 recruiter 的說明為準。

**題型傾向。** 公開面經中經常提到的題目多半是常見題型的標準形或小變形：陣列與字串、hashing、two pointers、tree 的遍歷與 LCA、graph 的 BFS／DFS、intervals、heap 的 top-k。題目本身不一定很難，難的是在 20 分鐘內完成釐清、寫程式、驗證，還要應付一兩個 follow-up。

**對作答的影響。** 這種形式下，第 2 章 Q5 提到的「壓縮釐清與設計、保留驗證」是關鍵。核心題要熟到不必推導，一看到題目就能說出做法與複雜度。另一個重點是 follow-up 常是同一題的小變化，例如「如果樹的節點有指向父節點的指標，LCA 怎麼做」或「如果要求 O(1) 額外空間」，所以每題的 Follow-up 小節在這裡特別有用。

|---|---|---|
| Hashing 與計數 | 很多題的基礎工具 | 第 4 章核心題 1（1）、第 4 章核心題 2（49）、第 7 章核心題 2（560） |

## 30.4 Amazon：情境題、可讀性與 Leadership Principles

**形式。** Amazon 公開的面試準備說明強調 Leadership Principles（領導準則），公開面經中經常描述行為問題會穿插在每一輪，包括 coding 回合：可能前 15–20 分鐘是行為問題，後面才是寫程式。面試團隊中有一位 Bar Raiser，這是官方公開說明過的角色，負責維持招募標準。很多職位在面試前會有線上測驗（OA），公開面經中常描述為限時的兩題左右加上其他評量，細節依職位而異。

**題型傾向。** 公開面經中常提到題目帶有實務情境：處理訂單或 log、排程、倉儲與配送的路徑、設計一個小型類別或 API 介面。底下的 pattern 通常是 heap、BFS、hashing、topological sort 與物件導向設計。情境的包裝會讓題目看起來陌生，但剝掉包裝後常是標準形。

**對作答的影響。** 因為一輪的 coding 時間可能被行為問題壓縮，題目要寫得快而且乾淨。情境題的第一步是把故事翻譯成資料結構，例如「每個倉庫有到其他倉庫的運送時間」就是加權圖，「找出最常被購買的 k 個商品」就是 top-k。程式可讀性在這種題目中特別重要：用有意義的類別與方法名稱，面試官常會追問「如果需求改了，你的程式要改哪裡」。另外要準備好 Leadership Principles 的故事，那不在本書範圍內，但公開資訊與面經都顯示它在評估中份量很重，不能只靠 coding 表現。

## 30.5 Microsoft 與 Apple：依團隊而異，重視實作細節

**Microsoft 的形式與傾向。** 公開面經普遍描述 Microsoft 的流程依團隊而異：一輪初篩後是多輪面試，面試官多半是未來團隊的成員，有時最後一輪會由較資深的面試官負責。題目常是偏實務的中等難度題，例如 linked list 與 tree 的操作、字串處理、矩陣模擬，以及和團隊領域相關的小型設計題。公開面經中也經常提到面試官會和你討論程式品質，例如命名、錯誤處理、怎麼測試。

**Apple 的形式與傾向。** 公開面經普遍描述 Apple 的面試高度由團隊主導，流程、輪數與題目差異都很大，而且常包含和團隊領域相關的技術問題（例如系統、效能、平台相關知識）。coding 題的難度在公開描述中多為中等，但面試官常會深挖細節：為什麼用這個資料結構、記憶體用量、邊界情況、如果在資源受限的環境下要怎麼改。

**對作答的影響。** 這兩家的共同點是「把基本題寫得非常扎實」比「會很多難題」更重要。linked list 的指標操作、tree 的遞迴、矩陣的索引計算，要寫到沒有 off-by-one，並且能主動說出邊界處理。準備時也要花時間了解目標團隊的產品與技術領域，那部分常和 coding 回合交織在一起。

## 30.6 跨公司的優先清單：最後一週先練哪些

如果最後一週只能挑一部分題目重寫，建議先挑「在多家公司的傾向中都出現」的 pattern，因為它們的投資報酬率最高。下面這張表把上面五節交叉比對，列出出現在兩家以上傾向中的 pattern，以及每個 pattern 最值得重寫的一題。這仍然是定性的整理，不是頻率排名。

## 30.7 Google L5 的評分重點：四個維度與 senior 的額外期待

第 2 章 2.8 節介紹過 coding 回合普遍的四個評分維度：problem solving、coding、verification、communication。各公司的評分表細節不公開，這裡依照公開的準備資料與面經中普遍的描述，整理 L5 等級在每個維度上「被看到」的具體行為，以及 senior 等級多出來的期待。同樣地，這是本書的整理，不是任何公司的官方評分表。

| 維度 | L4 等級常見的好表現 | L5 等級額外被期待的表現 |
|---|---|---|
| Problem solving | 在少量提示下找到最佳解 | 不需提示；主動比較兩種以上做法的取捨；能說出下限（「至少要讀過每個元素，所以不可能低於 O(n)」） |
| Coding | 程式正確、可讀 | 結構一開始就為 follow-up 留好位置；輔助函式切得自然；語言特性用得恰當但不炫技 |
| Verification | 寫完後用範例追蹤 | 先設計測試清單再追蹤；自己找到 bug 並說明成因；指出哪些輸入會讓解法變慢 |
| Communication | 思考過程透明 | 主導節奏：知道什麼時候該確認方向、什麼時候該直接推進；能把複雜的 invariant 用一句話講清楚 |

senior 等級多出來的期待，可以歸納成三個關鍵字。第一是**主導性**：你推著解題往前走，面試官的角色是確認與追問，而不是一步一步引導。實際做法是在每個階段結束時主動宣告下一步，例如「做法和複雜度確定了，我開始寫，先寫主流程，BFS 的鄰居函式最後補」。第二是**取捨意識**：L5 候選人被期待能說出「為什麼不用另一種做法」，例如「也可以用 heap 做到 O(n log k)，但 k 接近 n 時 quickselect 的平均 O(n) 更好，代價是最壞情況 O(n²)」。第三是**面對模糊的能力**：題目刻意留下模糊時，senior 候選人會先列出可能的解讀，選一個合理的並說明理由，而不是等面試官決定。

另一個常被忽略的點是：L5 的 coding 回合題目難度不一定比 L4 高很多，差距主要在 follow-up 的深度與你的表現成熟度。所以最後一週練習時，不要只看「有沒有解出來」，而要用上表右欄逐項檢查自己的錄音或練習紀錄。一個實用的自我評分法是每練完一題，就在四個維度各寫一句「我做到了什麼」，寫不出來的維度就是下一題要特別注意的地方。第 31 章的模擬面試附有更細的自我檢討表。

## 30.8 考前一週複習法

最後一週的目標不是學新東西，而是把已經會的東西變穩，同時把作答流程練成習慣。這一週最常見的錯誤有兩個：一是焦慮地刷大量新題，結果每題都只做一半；二是只做自己擅長的 pattern，因為做起來有成就感。下面的安排假設你已經讀完一輪全書，每天約 2–3 小時。

```text
考前 7 天
─────────────────────────────────────────────────────────────
D-7  跨公司優先清單（30.6）的 8 題各重寫一次，限時 20 分鐘
     記錄：哪幾題超時、哪幾題有 bug
D-6  弱點 pattern：錯題本中錯最多的兩章，核心題全部重寫
D-5  交錯練習：4 題來自 4 個不同章，題目順序打亂，
     先只看題目、30 秒內說出 pattern 與理由，再寫其中 2 題
D-4  目標公司傾向（30.2–30.5）的表格，挑 4 題限時寫
     第 31 章模擬面試一場（完整 45 分鐘、出聲）
D-3  交錯練習 4 題；複習每章「辨識訊號」與「Pattern 歸納」
D-2  第 31 章模擬面試一場；錯題本中「辨識」類全部過一遍
D-1  輕量：只讀各章模板與本章重點整理，寫 2 題最熟的核心題暖身
     不做新題、不熬夜
D-0  面試當天：30.9 的檢查清單
```

這個安排背後有三個理由。第一，**交錯練習**（interleaving）比區塊練習更接近面試：連續寫五題 sliding window 時你不必判斷 pattern，但面試時判斷 pattern 正是最難的一步，所以最後一週要刻意把不同章的題目混在一起。第二，**模擬面試要完整進行**：從釐清到 follow-up 全部出聲、計時，因為面試的壓力主要來自時間與說話，只寫程式練不到這兩件事。第三，**最後一天要輕**：前一天的睡眠對表現的影響通常比多做幾題大，這時讀模板與重點整理就夠了。

如果最後只剩三天，保留 D-7、D-5 與 D-1 的內容：先找出不穩的 pattern，再做交錯練習，最後一天暖身。附錄 D 的 7 天衝刺版有更細的每日分配，可以搭配使用。

下面是一個交錯練習的排程小程式。輸入是每章待複習的題目（依優先順序排列）與弱點章號，輸出是每天的題目清單，同一天的題目一定來自不同章，弱點章排在最前面。你可以把錯題本的內容填進去直接使用。

```python
from collections import deque


def build_week(problems: dict[int, list[str]], weak: set[int],
               days: int = 7, per_day: int = 4) -> list[list[str]]:
    """交錯練習排程：每天最多 per_day 題，且同一天的題目來自不同章。

    problems：章號 -> 該章待複習題目（越前面越優先）
    weak：弱點章號，在輪轉順序中排在最前面
    """
    order = sorted(problems, key=lambda c: (c not in weak, c))
    queues = {c: deque(problems[c]) for c in order}
    ring = deque(c for c in order if queues[c])  # 每章在 ring 中最多出現一次
    plan: list[list[str]] = []
    for _ in range(days):
        today = []
        # 一天最多從 ring 前端取 len(ring) 個不同的章，放回的章排到尾端，
        # 所以同一天不會取到同一章兩次。
        for _ in range(min(per_day, len(ring))):
            c = ring.popleft()
            today.append(queues[c].popleft())
            if queues[c]:
                ring.append(c)
        plan.append(today)
    return plan


wrong_book = {
    8: ["8-核心4", "8-難題2"],
    15: ["15-核心3", "15-難題1", "15-核心1"],
    21: ["21-核心4", "21-核心2", "21-難題1"],
    4: ["4-核心1"],
}
plan = build_week(wrong_book, weak={15, 21}, days=4, per_day=3)
assert plan[0] == ["15-核心3", "21-核心4", "4-核心1"]  # 弱點章先排
assert plan[1] == ["8-核心4", "15-難題1", "21-核心2"]
assert plan[3] == []                                    # 題目用完後是空的一天
chapter_of = {p: c for c, ps in wrong_book.items() for p in ps}
for day in plan:                                         # 同一天不重複章
    assert len({chapter_of[p] for p in day}) == len(day)
all_scheduled = [p for day in plan for p in day]
assert sorted(all_scheduled) == sorted(chapter_of)       # 每題剛好排一次
assert build_week({}, weak=set()) == [[]] * 7            # 空的錯題本
print("all tests passed")
```

面試當天的表現有很大一部分取決於「不被意外打斷」。下面的清單分成三段：前一天晚上、面試前一小時、面試中。建議把它印出來或抄在紙上，面試前逐項打勾。

## 30.10 遇到沒看過的題目：拆解流程

公開面經中經常提到，被大量公開討論的題目可能會被汰換，所以面試很可能遇到沒看過的題目。好消息是：「沒看過的題目」幾乎都是已知 pattern 的新包裝或組合，真正全新的演算法在 45 分鐘的面試中很少出現。本書每章的「辨識訊號」與「Pattern 歸納」就是為這一刻準備的。下面是一套固定的拆解流程，它整合了第 2 章的溝通流程與第 3 章的決策樹：

```text
步驟 1　剝掉包裝：把故事翻譯成資料結構
        「倉庫與運送時間」→ 加權圖；「每天開花的日子」→ 整數陣列
        問自己：輸入是什麼形狀？輸出是一個值、一個序列還是一個計數？

步驟 2　從限制推複雜度上限（第 3 章 3.2 節）
        n ≤ 20 → 指數；≤ 500 → n^3；≤ 10^4 → n^2；≤ 10^6 → n log n；≤ 10^8 → n
        值域很大（≤ 10^9）但 n 不大 → 可能要對答案做 binary search

步驟 3　找最強的結構訊號（第 3 章 3.5 節決策樹）
        單調性？連續區段？依賴關係？「每次選最小／最大」？重疊子問題？

步驟 4　列出兩三個候選 pattern，逐一用反例或複雜度排除
        「如果用 greedy，這個例子會錯嗎？」「這個 DP 的狀態數超過上限嗎？」

步驟 5　確認做法後，用一個小例子手動走一次，再寫程式
        這一步會抓出大部分的理解錯誤與漏掉的邊界

步驟 6　驗證與 follow-up：列出容易出錯的邊界，預想面試官會改哪個限制
```

這個流程的關鍵在步驟 4：不要一想到一個 pattern 就開始寫，而是至少考慮一個替代方案，並說出為什麼排除它。這同時是 L5 等級「取捨意識」的展現，也是避免寫到一半才發現做法錯誤的保險。第 3 章 3.8 節用三道自創題示範了「從 constraints 到 pattern」的判斷，下面三節用三道本書沒有收錄的 LeetCode 題目，示範完整的六個步驟，特別著重候選 pattern 的排除與驗證。三題都只給思路與骨架，不給完整程式，請讀完後自己實作作為練習。

## 30.11 示範一：花束的最早完成日（1482. Minimum Number of Days to Make m Bouquets）

**題目。** 花園裡有 n 朵花排成一排，`bloomDay[i]` 是第 i 朵花開的日子。要做 m 束花，每束需要 k 朵**相鄰**且已經開的花，每朵花只能用一次。求最少要等到第幾天才能做出 m 束；如果花不夠，回傳 -1。限制：n ≤ 10⁵，`bloomDay[i]` ≤ 10⁹，m ≤ 10⁶，k ≤ n。例如 `bloomDay = [7, 7, 7, 7, 12, 7, 7]`、m = 2、k = 3，答案是 12；`bloomDay = [1, 10, 3, 10, 2]`、m = 3、k = 2，因為需要 6 朵花但只有 5 朵，答案是 -1。

**步驟 1–2：剝掉包裝、從限制推上限。** 輸入是一個整數陣列，輸出是一個天數。n 到 10⁵，所以要 O(n log n) 或 O(n log V)；天數到 10⁹，直接逐天模擬是 O(n · V)，不可行。「值域很大但 n 不大」本身就是 binary search on answer 的提示。

**步驟 3：找結構訊號。** 關鍵的觀察是單調性：如果第 d 天可以做出 m 束，第 d + 1 天開的花只會更多，一定也可以。題目問的是「最小的可行天數」，這正是第 8 章核心題 4（875）與第 8 章核心題 5（1011）的形狀：答案空間上有一個可行與不可行的分界點。

**步驟 4：候選 pattern 與排除。**

```text
候選 A：sliding window 找長度 k 的窗口
  問題：要同時選 m 個不重疊的窗口，而且答案是「天數」不是「位置」
  → 窗口本身不能直接回答「最早第幾天」，排除

候選 B：排序花的開花日，逐一加入並維護連續區段（類似 union-find）
  可行：每加入一朵花合併左右區段，追蹤目前能做幾束
  複雜度 O(n log n)，但要處理區段合併時束數的增減，程式較長

候選 C：binary search on answer ＋ 線性判定
  判定 can(d)：從左到右掃描，開了的花累計連續長度，
  滿 k 朵就做一束並歸零，沒開就歸零
  複雜度 O(n log V)，log V 約 30 次判定 → 選 C，程式最短也最好解釋
```

候選 B 也是正確的，在面試中可以提出來作為取捨討論：「也可以按開花日排序後用 union-find 合併區段，O(n log n)，但 binary search 的判定比較簡單，我先寫這個。」

**判定的正確性。** 判定函式用的是 greedy：在每一段連續開花的區段中，從左邊開始每湊滿 k 朵就做一束。為什麼不會比最佳少？一段長度 L 的連續區段最多做 ⌊L / k⌋ 束（每束占 k 朵，不能重疊），而從左邊貪婪地切剛好達到這個上限；不同區段之間被沒開的花隔開，互不影響。所以 greedy 計算出的束數就是第 d 天能做的最大束數。

**步驟 5：手動走一次。**

```text
bloomDay = [7, 7, 7, 7, 12, 7, 7]，m = 2，k = 3
搜尋範圍：lo = min = 7，hi = max = 12（m·k = 6 ≤ 7，有解）

can(9)：開了？ T T T T F T T
        連續：1 2 3→做 1 束，歸零 1   F→歸零  1 2
        束數 = 1 < 2 → 不可行，lo = 10
can(11)：同上，束數 = 1 → 不可行，lo = 12
lo = hi = 12 → 答案 12
can(12)：全部開了，連續 7 → 1 2 3(束) 1 2 3(束) 1 → 2 束 ✓
```

**步驟 6：邊界與 follow-up。** 第一個要先處理的邊界是 m · k > n，直接回傳 -1；注意 m 可以到 10⁶、k 可以到 10⁵，乘積到 10¹¹，在 Python 沒問題，但在 Java 或 C++ 要用 64 位元整數。搜尋範圍用 `[min(bloomDay), max(bloomDay)]` 即可，因為最晚的那天所有花都開了，若 m · k ≤ n 一定可行。預想的 follow-up：如果每束的 k 朵花不需要相鄰，答案就是排序後第 m · k 小的開花日（O(n) quickselect 或 O(n log n) 排序），不再需要 binary search；如果有多筆查詢、k 固定而只有 m 不同，可以用候選 B 依開花日逐一加入花朵、維護「到第 t 天為止能做幾束」這條非遞減曲線，每筆查詢在曲線上 binary search，總共 O(n log n + q log n)；如果 k 也各不相同，束數 Σ⌊L / k⌋ 無法共用，最直接的做法是每筆查詢各做一次 O(n log V) 的 binary search。

## 30.12 示範二：單執行緒 CPU 的執行順序（1834. Single-Threaded CPU）

**題目。** 有 n 個任務，`tasks[i] = [enqueueTime, processingTime]`：任務 i 在 enqueueTime 時刻變成可執行，需要連續執行 processingTime 單位時間。CPU 一次只能執行一個任務，而且任務一旦開始就不會中斷。每當 CPU 空閒，它會在所有已經可執行、還沒執行的任務中，選 processingTime 最短的；一樣短就選索引最小的。如果沒有可執行的任務，CPU 就閒置到下一個任務出現。回傳任務的執行順序（索引）。限制：n ≤ 10⁵，時間值 ≤ 10⁹。例如 `tasks = [[1, 2], [2, 4], [3, 2], [4, 1]]`，答案是 `[0, 2, 3, 1]`；`tasks = [[7, 10], [7, 12], [7, 5], [7, 4], [7, 2]]`，所有任務同時出現，答案是 `[4, 3, 2, 0, 1]`。

**步驟 1–2：剝掉包裝、從限制推上限。** 輸入是 n 個（時間，長度）對，輸出是一個排列。n 到 10⁵，每次空閒時線性掃描所有任務找最短的是 O(n²) ≈ 10¹⁰，太慢，目標是 O(n log n)。時間值到 10⁹，所以不能逐個時間單位模擬，時間要「跳著走」。

**步驟 3：找結構訊號。** 題目有兩個訊號。第一，「每次從目前可用的候選中選最小的」，而候選集合會不斷加入新元素，這是 heap 的標準訊號（第 14 章）。第二，任務依 enqueueTime 陸續出現，這是「排序後用指標依序釋放」的事件模擬，和第 9 章核心題 5（253）以及第 14 章難題 3（502）的結構相同：一條按時間排序的事件流，加上一個存放「目前可用候選」的 heap。

**步驟 4：候選 pattern 與排除。**

```text
候選 A：直接依 processingTime 排序
  反例：tasks = [[1, 5], [2, 1]]
        依長度排序會先做任務 1，但時刻 1 只有任務 0 可執行，
        CPU 不能等，所以正確答案是 [0, 1] → 排除

候選 B：依 enqueueTime 排序後依序執行
  反例：題目第一個範例，時刻 3 時任務 1（長 4）與任務 2（長 2）都可用，
        應選任務 2 → 排除

候選 C：依 enqueueTime 排序 ＋ min-heap(processingTime, index)
  每次 CPU 空閒：把所有 enqueueTime ≤ 現在時刻 的任務推進 heap，
  heap 空就把時刻跳到下一個任務的 enqueueTime，否則彈出最小的執行
  每個任務進出 heap 各一次 → O(n log n) → 選 C
```

候選 A 與 B 各用一個小反例排除，這是步驟 4 最有效的方式：greedy 類的錯誤做法通常用兩三個元素的例子就能打破。heap 的鍵用 `(processingTime, index)` 的 tuple，剛好同時處理「最短優先」與「同長度選索引小」兩個規則，這個細節值得在寫程式前說出來。

**步驟 5：手動走一次。**

```text
tasks = [[1,2], [2,4], [3,2], [4,1]]
依 enqueueTime 排序（帶索引）：(1,2,0) (2,4,1) (3,2,2) (4,1,3)

time = 0，heap 空 → 跳到 time = 1
time = 1：推入 (2,0)            heap = [(2,0)]
          彈出 0，time = 1+2 = 3      順序 [0]
time = 3：推入 (4,1)、(2,2)     heap = [(2,2), (4,1)]
          彈出 2，time = 3+2 = 5      順序 [0, 2]
time = 5：推入 (1,3)            heap = [(1,3), (4,1)]
          彈出 3，time = 5+1 = 6      順序 [0, 2, 3]
time = 6：沒有新任務            heap = [(4,1)]
          彈出 1，time = 6+4 = 10     順序 [0, 2, 3, 1] ✓
```

**步驟 6：邊界與 follow-up。** 最容易錯的邊界是 CPU 閒置：heap 空的時候，時刻要跳到下一個任務的 enqueueTime，而不是 +1，否則時間值 10⁹ 會讓迴圈跑不完。第二個邊界是多個任務同時出現，要用 while 迴圈一次推入所有 enqueueTime ≤ time 的任務，而不是只推一個。預想的 follow-up：如果有 c 個 CPU，就再加一個存放「CPU 何時空閒」的 min-heap，每次取最早空閒的 CPU，形狀和第 9 章核心題 5（253）的會議室分配相同；如果任務可以被中斷（preemptive），每次有新任務出現時都要比較剩餘時間，變成 shortest remaining time first，事件點變成「任務出現」與「任務完成」兩種。

## 30.13 示範三：最短路徑的數量（1976. Number of Ways to Arrive at Destination）

**題目。** 一座城市有 n 個路口（編號 0 到 n - 1）與若干條雙向道路，`roads[i] = [u, v, time]` 表示 u 與 v 之間的道路需要 time 分鐘（time ≥ 1）。保證任兩個路口之間連通，且沒有重複的道路。求從路口 0 到路口 n - 1 的**最短時間**路徑有幾條，答案對 10⁹ + 7 取餘數。限制：n ≤ 200，道路數 ≤ n(n - 1) / 2，time ≤ 10⁹。例如 n = 4，道路 `0-1(1)、0-2(1)、1-3(1)、2-3(1)、0-3(2)`，最短時間是 2，共有三條路徑：0→1→3、0→2→3、0→3，答案是 3；n = 2、只有一條道路 `0-1(5)`，答案是 1。

**步驟 1–2：剝掉包裝、從限制推上限。** 輸入是加權無向圖，輸出是一個計數。n ≤ 200 看起來很小，O(n³) ≈ 8 × 10⁶ 也能接受，所以 Floyd–Warshall 求出最短距離是可行的；但路徑數量可能是指數級（例如分層的完全二分圖），所以**枚舉所有路徑**絕對不行。題目要求取餘數，本身就暗示答案很大，必須用計數的方式累加，而不是一條一條列舉。

**步驟 3：找結構訊號。** 「最短路徑」＋「正權重」→ Dijkstra（第 18 章）；「有幾種方法」→ 計數型 DP（第 21 章）。這題的關鍵是把兩者組合：只保留滿足 `dist[u] + w == dist[v]` 的邊，這些邊構成一張有向無環圖（shortest-path DAG），因為權重都是正的，沿著這些邊 dist 嚴格遞增，不可能形成環。在 DAG 上數從 0 到 n - 1 的路徑數，就是依拓樸順序做 `ways[v] += ways[u]` 的 DP，和第 16 章難題 5（2050）在 DAG 上沿拓樸順序做 DP 是同一個想法。

**步驟 4：候選 pattern 與排除。**

```text
候選 A：BFS 數最短路徑（無權圖的經典做法）
  問題：邊有權重，BFS 的「層」不等於距離 → 排除

候選 B：DFS 枚舉所有路徑，記錄最短的數量
  問題：路徑數可能是指數級，n = 200 時完全不可行 → 排除

候選 C：先 Dijkstra 求 dist，再把節點依 dist 排序，在 DAG 上做 DP
  正確，O(E log V)，但要兩個階段

候選 D：Dijkstra 過程中同時維護 ways
  鬆弛 u→v 時：
    dist[u] + w <  dist[v]：dist[v] 更新，ways[v] = ways[u]
    dist[u] + w == dist[v]：ways[v] += ways[u]
  Dijkstra 依 dist 由小到大確定節點，剛好就是 DAG 的拓樸順序
  → 選 D，一次完成；C 可以作為說明正確性的方式
```

**正確性的關鍵。** 候選 D 成立的理由要能說清楚：當節點 u 從 heap 中被彈出（且不是過期的項目）時，dist[u] 已經是最終值，而所有能以最短路徑到達 u 的前驅節點 p 都滿足 dist[p] = dist[u] - w < dist[u]（因為 w ≥ 1），所以它們都比 u 更早被彈出並鬆弛過 u。也就是說，u 被彈出時 ways[u] 已經累加完所有前驅的貢獻，接下來用它去更新鄰居是安全的。這段論證依賴「權重嚴格為正」，如果題目允許 time = 0，相同 dist 的節點之間可能互相貢獻，順序就不再保證，這是很好的 follow-up 討論點。

**步驟 5：手動走一次。**

```text
n = 4，道路 0-1(1)、0-2(1)、1-3(1)、2-3(1)、0-3(2)

初始：dist = [0, ∞, ∞, ∞]，ways = [1, 0, 0, 0]
彈出 0 (d=0)：
  →1：0+1 < ∞  dist[1]=1, ways[1]=1
  →2：0+1 < ∞  dist[2]=1, ways[2]=1
  →3：0+2 < ∞  dist[3]=2, ways[3]=1      （路徑 0→3）
彈出 1 (d=1)：
  →3：1+1 == 2  ways[3] = 1 + 1 = 2      （加上 0→1→3）
彈出 2 (d=1)：
  →3：1+1 == 2  ways[3] = 2 + 1 = 3      （加上 0→2→3）
彈出 3 (d=2)：終點，答案 ways[3] = 3 ✓
```

**步驟 6：邊界與 follow-up。** 邊界有三個：n = 1 時起點就是終點，答案是 1；time 可以到 10⁹，路徑長度可能到 2 × 10¹¹，在 Java 或 C++ 要用 64 位元整數存 dist；heap 中的過期項目（彈出時 d > dist[u]）要跳過，否則會重複累加 ways，這是這題最常見的 bug。預想的 follow-up：如果要回傳其中一條最短路徑，記錄每個節點的前驅即可；如果要數「最短時間路徑中邊數最少的有幾條」，就把 dist 改成 (時間, 邊數) 的 tuple 做字典序比較；如果允許 time = 0，要先和面試官釐清「路徑」的定義：無向圖中一條 0 權重邊就能來回走而不增加時間，最短時間的 walk 會有無限多條，所以只能數簡單路徑，而在一般圖上數簡單路徑沒有已知的多項式解法；若題目改成有向圖且 0 權重邊不形成環，則可以在 shortest-path DAG 上先做拓樸排序，再依拓樸序累加 ways。

## 30.14 三個示範的共同模式

回頭看三個示範，可以看到幾個重複出現的判斷，這些判斷比任何一道題的答案都更值得記住：

| 判斷 | 示範一（1482） | 示範二（1834） | 示範三（1976） |
|---|---|---|---|
| 限制給的提示 | 值域 10⁹、n 10⁵ → 對答案搜尋 | 時間值 10⁹ → 時間要跳著走 | 答案要取餘數 → 計數而非枚舉 |
| 最強訊號 | 可行性對天數單調 | 「從可用候選中選最小」 | 最短路徑＋計數 |
| 被排除的直覺 | sliding window | 只依某一個欄位排序 | BFS、DFS 枚舉 |
| 組合的 pattern | binary search ＋ greedy 判定 | 排序事件流 ＋ heap | Dijkstra ＋ DAG 上的 DP |
| 正確性要說的話 | 連續區段最多 ⌊L / k⌋ 束 | heap 鍵同時編碼兩個規則 | 正權重保證彈出順序是拓樸順序 |

三題都不是單一 pattern 的標準形，而是兩個 pattern 的組合，這正是「沒看過的題目」最常見的樣子。也因此，本書每章「Pattern 歸納」中「與其他 pattern 的關係」那一段，在最後一週值得重讀：組合題的突破點，通常就是看出這一題的某個子問題屬於另一個 pattern。另一個共同點是每題都用一個兩三個元素的小反例排除錯誤做法，這在面試中說出來非常有說服力，也是最便宜的驗證。

## 本章重點整理

- 各公司的面試資訊只能當定性傾向參考，流程會隨年份、職級、地區與團隊變動，一切以 recruiter 告知為準；拿到邀請就問清楚輪數、時間、編輯器、能否執行程式。
- Google 常從簡單版本出發再用 follow-up 層層加深，題目常需要自己建模；第一版程式要寫得容易擴充，推導過程要說出來留下紀錄。
- Meta 常見一輪兩題，題目多為標準形或小變形，關鍵是速度與一次寫對；核心題要熟到不必推導。
- Amazon 強調 Leadership Principles 並常與 coding 回合結合，題目常帶實務情境；先把故事翻譯成資料結構，並重視程式可讀性。
- Microsoft 與 Apple 依團隊差異很大，重視實作細節與領域知識；把 linked list、tree、矩陣、小型設計題寫到沒有 off-by-one。
- 最後一週先重寫跨公司優先清單的八題，某題不穩就重寫該章全部核心題。
- L5 和 L4 的差距主要不在題目難度，而在主導性、取捨意識與面對模糊的能力；練習後用四個維度逐項自評。
- 考前一週用交錯練習取代區塊練習，至少做兩場完整出聲的模擬面試，最後一天只暖身、不做新題。
- 面試當天用檢查清單排除意外；一輪表現不好要重新開始，不確定的地方誠實說出推測。
- 遇到沒看過的題目用六步驟拆解：剝掉包裝、從限制推上限、找最強訊號、列候選並用反例排除、手動走一次、驗證與預想 follow-up。
- 沒看過的題目多半是兩個 pattern 的組合，例如 binary search ＋ greedy、排序事件流 ＋ heap、Dijkstra ＋ DAG 上的 DP。

## 延伸問答

> [!question]- Q1. 我同時面好幾家公司，要怎麼分配準備時間？
> 先用 30.6 節的跨公司優先清單打底，因為那些 pattern 在各家的傾向中都出現，練一次對每家都有用。接著依面試日期排序：最早的那家先針對它的傾向表格挑題練習，例如先面 Meta 就多練兩題一輪的速度，先面 Google 就多練沒有執行環境時的手動追蹤與 follow-up。如果日期很接近，就以形式差異最大的部分為優先，例如 Amazon 的 Leadership Principles 故事需要獨立準備，不能靠刷題補上。另外，先安排一兩家不是首選的公司當作實戰練習，通常能明顯降低後面面試的緊張程度。

> [!question]- Q2. 面試前一天才發現某個 pattern 完全不熟，要不要臨時惡補？
> 只做有限度的補強。前一天的目標是讓狀態穩定，大量學新東西通常只會增加焦慮，而且一天內很難把新 pattern 練到能在面試中穩定使用。建議的做法是只讀該章的「辨識訊號」「模板與原理」與「Pattern 歸納」，再把模板默寫一次並執行測試，讓自己至少能認出它、寫出暴力解並說出方向。萬一面試真的考到，你能說出「這看起來是 bitmask DP，因為 n ≤ 20 且狀態是子集」並寫出可行的版本，就已經比完全沒概念好很多。剩下的時間還是用來暖身熟悉的題目與好好睡覺。

> [!question]- Q3. Google 的面試不能執行程式，要怎麼練習手動驗證？
> 最直接的方法是在練習時關掉執行環境：寫完程式後，先在紙上或註解中列一張變數追蹤表，用一個三到五個元素的例子逐行模擬，寫下你預期的輸出，最後才執行測試對照。如果執行結果和你手動追蹤的不一樣，代表你的追蹤漏掉了某個細節，這正是要練的地方。追蹤時優先檢查迴圈邊界、更新與查詢的順序、遞迴的終止條件，這三處是 bug 最集中的地方。也可以練習「說出測試清單」：寫完程式立刻列出要測的輸入（空、單一元素、全部相同、答案在頭尾），面試中這樣做會讓 verification 維度的表現非常明顯。

> [!question]- Q4. 遇到完全沒看過的題目，緊張到腦袋一片空白，第一步該做什麼？
> 第一步是把題目用自己的話重述一次，並用一個很小的例子手算答案。這兩個動作不需要任何靈感，卻能讓你重新開始思考，也讓面試官知道你正在處理問題。手算時注意你的大腦是怎麼得出答案的，那個過程常常就是暴力解。接著照 30.10 節的步驟：先問 n 的範圍並換算可接受的複雜度，再找最強的結構訊號。即使到最後只寫出暴力解，只要你說清楚瓶頸在哪、想往哪個方向優化，面試官仍然能看到 problem solving 的訊號。沉默才是最糟的結果。

> [!question]- Q5. 拆解新題時，候選 pattern 想不出兩三個怎麼辦？
> 用第 3 章的決策樹當作檢查清單逐一詢問，而不是等靈感出現：答案有沒有單調性？輸入能不能排序？是不是連續區段？有沒有依賴關係或連通關係？是不是「每次選最小或最大」？暴力遞迴中有沒有重複的子問題？每個問題只要回答是或否，通常幾個問題之內就會冒出兩三個候選。另一個方法是從輸出形式反推：回傳一個最佳值常是 DP、greedy 或對答案搜尋；回傳所有解常是 backtracking；回傳計數常是 DP 或組合計數。平常練習時，可以對每道題刻意說出一個「看起來可以但其實不行」的 pattern 與它的反例，久了候選自然就多了。

> [!question]- Q6. 面試官問「還有沒有更好的做法」，但我覺得已經是最佳解了，怎麼回答？
> 先用下限論證支持你的判斷，例如「每個元素至少要讀一次，所以時間不可能低於 O(n)，目前的解已經是 O(n)」，或「輸出本身就有 n² 個元素，所以 O(n²) 是下限」。有了下限，你的回答就不是主觀的「我覺得」，而是有理由的結論。接著可以主動討論其他維度的改進：空間能不能從 O(n) 降到 O(1)、常數能不能減少一次掃描、如果輸入有額外性質（例如已排序或值域很小）能不能更快。這樣既回答了問題，也展現了 L5 等級的取捨意識。如果面試官仍然暗示有更好的做法，就把它當成提示，重新檢查題目是否有你沒用到的條件。

> [!question]- Q7. 公司允許使用 AI 工具或可以執行程式時，準備方式要改嗎？
> 先向 recruiter 確認具體規則，因為這類形式還在變動，不同公司與職位的規定差異很大。如果可以執行程式，練習時就要熟悉「寫小測試、快速執行、讀錯誤訊息」的節奏，並準備好第 2 章 2.5 節的暴力解對拍技巧，這在可執行的環境中是很強的驗證訊號。如果允許使用 AI 工具，評估重點通常會轉向你能否判斷產出的程式是否正確、能否說明它的複雜度與邊界、能否修改它來應付 follow-up，所以本書強調的推導、invariant 與驗證能力反而更重要。無論形式如何，能清楚解釋每一行程式為什麼這樣寫都是不變的基本要求。

> [!question]- Q8. 面試結束後覺得表現不好，接下來該怎麼做？
> 先在當天把題目、你的做法、卡住的地方與面試官的提示寫下來，記憶會很快模糊。接著像處理錯題本一樣分析錯誤類型：是沒辨識出 pattern、建模錯、邊界錯，還是時間分配出問題，再把它排進間隔重複的複習排程。如果後面還有其他輪或其他公司的面試，不要讓這一輪的情緒影響下一輪，各輪通常是分開評估的，自己覺得不好的一輪也不一定真的不好。最後，如果結果不理想，可以問 recruiter 是否能提供回饋與再次申請的時間限制；很多人是第二次面試才通過的，把這次經驗變成下一次準備的具體清單，比反覆回想更有幫助。
