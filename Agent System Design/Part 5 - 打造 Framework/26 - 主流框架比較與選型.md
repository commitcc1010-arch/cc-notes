# 第 26 章　主流框架與託管服務：比較與選型

> [!abstract] 本章地圖
> **核心問題**：市面上有十幾個 agent 框架與好幾個託管 agent 服務，青鳥手上又有自己的 `loom`；要怎麼選，才能今天上線得快、明年換得掉？
>
> **你會學到**：
> - 把 agent 技術堆疊拆成可以分開「自建或外包」的幾層，先決定外包哪一層，再談選哪個產品
> - 用九個維度（抽象層級、狀態管理、multi-agent、HITL、durable、可觀測性、部署、生態、lock-in）評估框架，並知道每個維度在 POC 裡要怎麼驗證
> - 用一段話說出主流框架與託管服務的設計哲學與核心抽象，判斷它們適合與不適合的場景
> - 走一遍 build vs buy 決策流程，並估算總持有成本，而不只看授權費
> - 用 adapter 隔離框架、用契約測試保護遷移，讓框架選擇變成可以回頭的決定
> - 寫一個加權決策矩陣工具，以及把同一份 tool 定義匯出成各家格式的 adapter
>
> **前置知識**：第 4 章（agent loop）、第 5 章（tool 設計與副作用分級）、第 19 章（graph 與 checkpoint）、第 21 章（human-in-the-loop）、第 22 章（durable execution）、第 23–25 章（`loom` v0.5 的核心抽象、runtime 與 model adapter）

## 26.1 故事：三份評估報告，三個結論

`loom` v0.5 重構完成的那週，阿哲在週會上丟出一個問題：「好幾家大廠都推出託管的 agent 服務了，loop、sandbox、session 全部幫你管。我們還要自己維護 loom 嗎？能不能全公司統一用一套，大家不要各做各的？」會議室安靜了幾秒。這個問題很合理：青鳥現在有三個 agent，客服 agent 跑在 `loom` 上，內部 coding agent 小組私下試了一套完整的 harness SDK，營運 research agent 則有人在某個託管服務上做了 demo。

阿哲要大家兩週內交評估報告。結果交上來三份，結論各不相同。Iris 負責客服 agent，報告推薦一個 graph 式框架，理由是退款流程需要明確的狀態機、人工核准與 checkpoint。coding agent 小組推薦完整的 harness SDK，因為檔案讀寫、shell、權限與 context 壓縮都是現成的，自己寫要好幾個月。research agent 的報告推薦託管服務，因為任務一跑就是一兩個小時，最怕 process 中途掛掉，而託管服務把 session 持久化做好了。

Maya 看完三份報告，在客服那份旁邊用紅筆加了一行：「客服對話含有顧客姓名、電話與地址，資料必須留在青鳥自己的雲端帳號與區域內，不能被第三方保留。」這一行直接讓 research 報告推薦的託管服務出局，至少對客服 agent 是如此。更麻煩的是 Iris 在 POC（proof of concept，概念驗證）裡發現的一件事：Iris 把客服 agent 搬到 graph 框架上試跑，退款會跳出核准卡片，但「取消訂閱」卻直接執行了。原因是 `cancel_subscription` 這個 tool 沒有標註副作用等級，`loom` 依全書的規則把未標註的 tool 一律當 destructive 處理，新框架卻預設它是安全的。

老陳把三份報告排在桌上。「三份報告可能都是對的，」老陳說，「因為它們回答的是三個不同 agent 的需求。問題不是哪個框架最好，而是哪一層要自己擁有、哪一層可以租；選了之後，要能在不改業務程式的情況下換掉。Iris 發現的那個核准漏洞，就是我們把業務規則和框架綁在一起的代價。」

這一章就是青鳥做選型的過程。我們先把 agent 技術堆疊拆成可以分開決定的層，再定義九個選型維度，接著用一段話說清楚每個主流框架與託管服務的設計哲學；然後走一遍 build vs buy 的決策流程，談遷移與避免 lock-in 的做法。最後在「動手做」寫一個加權決策矩陣，替三個 agent 跑選型，並示範一個 adapter 層：同一份 tool 定義匯出成不同框架需要的格式，再用契約測試抓出 Iris 遇到的核准漏洞。

## 26.2 先決定「外包哪一層」：agent 技術堆疊

談選型之前，先把幾個常被混用的名詞分開。**library**（函式庫）是你呼叫它，例如一個把函式轉成 tool schema 的工具；**framework**（框架）是它呼叫你，你把 agent、tool、callback 註冊進去，由框架的 runtime 決定什麼時候執行，例如 graph 框架依照你定義的邊決定下一個節點。**SDK** 是廠商提供的開發套件，可能只是 library，也可能是完整的 framework。**託管服務**（managed service）則是連執行環境都由廠商營運：你送出設定與請求，loop 在對方的機器上跑。這四者的差別在於「控制流在誰手上」以及「程式跑在誰的機器上」，這兩件事決定了你能改什麼、出事時能查什麼。

```text
 層                          回答的問題                      可以自建或外包的例子
 ┌───────────────────────────────────────────────────────────────────────────────────┐
 │ ⑥ 平台服務               identity、gateway、memory、     託管平台的獨立服務、
 │                          policy、eval 由誰營運？         自家平台團隊
 ├───────────────────────────────────────────────────────────────────────────────────┤
 │ ⑤ 執行環境（runtime）     process 掛了怎麼辦？sandbox？   durable 引擎、託管 runtime、
 │                          並行與排程？                    自家 worker＋佇列
 ├───────────────────────────────────────────────────────────────────────────────────┤
 │ ④ 編排（orchestration）   多步驟、多 agent、暫停與恢復？  graph 框架、workflow、
 │                                                          handoff、自家 loom.graph
 ├───────────────────────────────────────────────────────────────────────────────────┤
 │ ③ harness（agent loop）  停止條件、錯誤回填、context、   code-first SDK、完整 harness
 │                          權限、compaction？              SDK、託管 harness、loom
 ├───────────────────────────────────────────────────────────────────────────────────┤
 │ ② 能力（tools、prompts）  agent 能做什麼、照什麼規則做？  永遠是你的業務邏輯
 ├───────────────────────────────────────────────────────────────────────────────────┤
 │ ① 模型與低階 API          誰負責推理？                    各家模型 API、model gateway
 └───────────────────────────────────────────────────────────────────────────────────┘
   託管 harness 通常一次包下 ③④⑤，部分還包 ⑥；graph 框架主要是 ③④；
   code-first SDK 主要是 ③；第 ② 層無論怎麼選都要自己擁有
```

由下往上讀這張圖。第 ① 層是模型，幾乎沒有團隊會自建，但要不要透過 model gateway 隔離各家 API，第 25 章已經談過。第 ② 層是 tools 與 prompts，也就是青鳥的退款規則、訂單查詢、客服語氣，這一層是業務本身，任何框架或服務都不會替你寫，所以它必須以「不屬於任何框架」的形式存在。第 ③ 層是第 4 章那個 loop 長大後的樣子：停止條件、錯誤回填、context 管理、權限檢查。第 ④ 層是第 18 到 21 章的編排：workflow、graph、multi-agent、人工核准。第 ⑤ 層是第 22 章的 durable execution 與第 17 章的 sandbox。第 ⑥ 層是第 33 章會談的 identity、tool gateway、policy 等平台服務。

這張圖讓選型問題變得具體。阿哲問「要不要統一用一套」，其實是在問「③ 到 ⑥ 層要不要一起外包給同一家」。coding agent 小組想外包的是 ③（完整 harness），research 小組想外包的是 ③④⑤（託管 harness），Iris 想外包的是 ④（graph 編排）。三份報告推薦的東西根本不在同一層，自然無法互相比較。先回答「外包哪一層」，再回答「選哪個產品」，討論才會收斂。

另一個常見的分類方式是看**抽象層級**：框架替你決定了多少事。越低階，你寫的程式越多、控制越細；越高階，上手越快，但遇到框架沒預想到的需求時，就要繞路或「逆向」框架。

```text
 低階／顯式控制                                                         高階／自主
 ◄──────────────────────────────────────────────────────────────────────────────►
 模型 API       graph／state machine    code-first agent SDK   角色式多 agent   託管 harness
 直接呼叫       框架                     （Agent＋Runner）       ／完整 harness    （雲端 loop）
   │               │                         │                     │                 │
 你寫 loop、     你畫節點與邊、            你寫 tools 與指令，    你描述角色或     你只送設定、
 狀態、重試      框架負責 checkpoint        loop 由 SDK 跑          給目標，框架      tools 與任務，
                 與恢復                                            決定怎麼協作      其餘由服務營運
 ────────────────────────────────────────────────────────────────────────────────
 控制力、可除錯性 ▲                                          上手速度、內建能力 ▲
```

這條光譜沒有「越右越好」或「越左越好」。左端的代價是工程量：每一個停止條件、每一種錯誤處理都要自己寫，而且要自己測。右端的代價是透明度與彈性：當託管 harness 的 compaction 把某段關鍵資訊摘要掉，你可能只能從輸出推測發生了什麼。Anthropic 在〈Building effective agents〉中建議先直接使用模型 API，因為許多 pattern 只要幾行程式就能實作；若要用框架，務必理解它底層做了什麼。這句話的重點不是反對框架，而是提醒你：框架替你做的每個決定，你都要知道它是什麼，才能判斷它適不適合你的產品。

> [!warning] 常見誤解
> 「選框架就是選一個最好的，全公司統一。」統一的好處是共用知識與工具，但不同 agent 的需求可能落在不同層、不同光譜位置。比較好的統一方式是統一「契約」：tool 定義格式、approval 政策、trace schema、eval 格式；runtime 可以依 agent 而不同。這正是本章後半要做的事。

## 26.3 選型維度（一）：抽象層級、狀態管理與 multi-agent

選型維度是你評估每個候選方案時要問的問題。本章用九個維度，分三節介紹；每個維度都講它在問什麼、為什麼重要、POC 裡怎麼驗證，以及常見的陷阱。第一組三個維度關於「控制」：誰決定流程、狀態放在哪裡、多個 agent 怎麼協作。

**抽象層級**問的是：框架的核心抽象是什麼，你能不能在需要時往下一層走？例如一個以「Agent＋Runner」為核心的 SDK，loop 由 SDK 執行，你通常可以透過 hooks 或 callback 在模型呼叫前後插入邏輯；一個以 graph 為核心的框架，你要把流程拆成節點與邊，換來的是每一步都可以 checkpoint。判斷好壞的標準不是抽象多寡，而是**逃生艙口**（escape hatch）：當你需要框架沒提供的行為，例如在 tool 執行前檢查顧客的退款額度，能不能用一個掛鉤點做到，而不必 fork 框架原始碼。POC 時的驗證方法很直接：挑一個你確定框架沒內建的需求，量量看要改多少地方。

**狀態管理**問的是：一次對話或任務的狀態存在哪裡、用什麼格式、誰能讀？這裡有三種常見做法。第一種是 **message history**：狀態就是 messages 清單，存在你的資料庫，簡單透明，第 4 章的 `loom` v0.1 就是這樣。第二種是 **checkpoint**（檢查點，在每一步之後保存整份 state 的快照）：graph 框架常用，可以從任何一步恢復或分岔，第 19 章做過。第三種是 **server-side session**：狀態存在廠商那端，用 id 串接，你的程式變得很輕，但資料的位置、保留期限與匯出方式都由對方決定。狀態格式是 lock-in 最深的地方之一，因為程式可以重寫，幾百萬筆歷史 session 卻很難搬家。

**multi-agent** 問的是：框架提供哪些多 agent 原語，它們的 context 是怎麼共享的？第 20 章談過，主流原語大致收斂為 agents-as-tools（把子 agent 包成一個 tool，主 agent 呼叫後拿回結果）、handoff（把對話控制權整個交給另一個 agent）、graph 中的多個 agent 節點，以及角色式的群組協作。比較時要看的不是「支不支援 multi-agent」，因為幾乎都支援；要看的是子 agent 能不能有獨立的 context、能不能平行、失敗時怎麼回報，以及 trace 能不能把父子關係串起來。如果你的 agent 根本不需要 multi-agent，這個維度的權重就該是零或接近零，不要因為框架的 demo 很炫而加分。

> [!tip] POC 的最小驗證集
> 每個候選方案都用同一組任務驗證，而且要包含「不愉快的路徑」：tool 丟例外、模型呼叫不存在的 tool、需要人工核准時使用者離開三小時、process 在第七步被殺掉。只跑 happy path 的 POC，量到的只是「上手速度」，量不到你上線後真正會付出的成本。

## 26.4 選型維度（二）：HITL、durable 與可觀測性

第二組三個維度關於「可靠性」：需要人時能不能停下來、出事時能不能接著跑、事後能不能查清楚。這三件事在 demo 裡幾乎看不到，上線後卻決定了營運成本。

**HITL**（human-in-the-loop，人在迴圈中）問的是：agent 需要人工核准或補充資料時，框架怎麼暫停、怎麼恢復？第 21 章把它做成 approval gate 與 interrupt。各框架的做法差異很大：有的在 tool 上標記「需要核准」，run 會帶著 interruption 結束，你把狀態序列化保存，核准後再恢復；有的在 graph 節點中呼叫 interrupt，由 checkpointer 保存；有的用權限模式加一個「能不能使用這個 tool」的 callback。要驗證三件事：暫停時是否真的不佔用 process（使用者可能三小時後才回來）；核准是否綁在具體的動作與參數上（避免核准 A 卻執行 B）；以及預設值是什麼，Iris 遇到的漏洞就是預設值的問題。

**durable**（持久執行）問的是：process 在任務中途當掉、重新部署或被限流時，任務能不能從中斷點繼續，而且不重複執行有副作用的動作？第 22 章講過兩種恢復方式：以 state 快照恢復（粒度是 graph 的節點）與以 event history 重播恢復（粒度是每一次模型或 tool 呼叫）。框架內建的 checkpoint 通常只負責「狀態存得下來」，不負責 worker 排程、計時器與跨服務重試；這些仍需要 durable execution 引擎或託管 runtime。POC 時一定要做「殺 process」測試：在退款 tool 執行前後各殺一次，看恢復後會不會漏做或重做。

**可觀測性**問的是：每一次 run 的每一步，你能不能看到模型收到什麼、回了什麼、呼叫了哪個 tool、花了多少 token？第 29 章會談 trace 與 span。比較框架時，重點在兩件事：trace 能不能匯出成開放格式（例如 OpenTelemetry），還是只能在廠商的儀表板上看；以及敏感資料能不能在匯出前遮蔽。前者決定你換框架時歷史 trace 還能不能用，後者決定 Maya 會不會簽字。

| 維度 | 在 POC 裡怎麼驗證 | 紅旗訊號 |
|---|---|---|
| HITL | 讓使用者在核准前離開三小時再回來；核准後檢查執行的參數是否與核准的一致 | 暫停期間 process 必須一直活著；核准不綁參數；未標註的 tool 預設不需核准 |
| durable | 在有副作用的 tool 前後各殺一次 process，再恢復 | 恢復後重做了退款；只能從頭重跑；checkpoint 存在無法匯出的地方 |
| 可觀測性 | 從一次失敗的 run 反查哪一步出錯，計時；嘗試把 trace 匯出到自家系統 | 只能在廠商 UI 看；看不到送給模型的完整 context；無法遮蔽 PII |

這張表的每一列都是「把不愉快的路徑搬進 POC」。三個紅旗中最常被忽略的是 durable 那一列的「恢復後重做了退款」：很多框架能恢復狀態，但恢復時會重新執行最後一個尚未記錄完成的步驟。如果那一步是退款，而 tool 沒有 idempotency key（第 5 章），就會退兩次。所以 durable 能力不能只看框架宣稱，要用你自己的 destructive tool 實測。

## 26.5 選型維度（三）：部署、生態與 lock-in

第三組三個維度關於「營運與長期」：能部署在哪裡、周邊有多少現成的東西、將來換不換得掉。

**部署**問的是：agent 能跑在哪些環境、資料會經過哪裡？自託管框架可以跑在你的容器、你的雲端帳號、你選的區域；託管服務則跑在廠商的基礎設施上，你要確認它支援的區域、資料保留政策、是否支援 **ZDR**（zero data retention，零資料保留，廠商不保存請求與回應的內容）、能否接上你的私有網路。這個維度經常以「硬性限制」的形式出現：Maya 說客服資料不能離開青鳥的帳號，任何做不到的選項就直接淘汰，不需要打分數。區分「可以打分數的偏好」與「不能妥協的限制」，是 26.11 節決策矩陣的第一個設計。

**生態**問的是：框架周邊有多少現成的整合、範例、社群與人才？包括它支援哪些模型供應商、能不能當 MCP client（第 14 章）、有沒有 A2A 或 AG-UI 的整合（第 15 章）、有沒有 durable 引擎的官方整合、團隊裡有沒有人用過。生態也包括語言：TypeScript 全端團隊與 .NET 企業團隊的選項很不一樣。還要看**維護健康度**：發版節奏、breaking change 的頻率、是否仍是 0.x 版本、主要維護者是誰。發版很快代表活躍，也代表你每季都要付升級成本。

**lock-in**（供應商鎖定）問的是：如果一年後要換掉這個選項，要付出多少代價？lock-in 不是只有一種，26.9 節會細分成 API、狀態、行為、營運與模型五類。評估時最實用的問題是：「我們的業務程式有多少行直接 import 這個框架？我們的 session 與 trace 能不能匯出成自己的格式？我們的 prompt 與 eval 是否依賴這個 harness 的特定行為？」lock-in 本身不一定是壞事，用得越深通常省得越多；問題是你有沒有意識到自己在付這個代價，以及有沒有留下退路。

| 維度 | 核心問題 | 典型的取捨 | 誰最在意 |
|---|---|---|---|
| 抽象層級 | 核心抽象是什麼？能不能往下走一層？ | 上手速度 vs 控制力與逃生艙口 | 工程師 |
| 狀態管理 | 狀態在哪裡、什麼格式、誰能讀？ | 輕量的 server-side session vs 自己掌握的 checkpoint | 工程師、資安 |
| multi-agent | 有哪些原語？context 怎麼共享？ | 高階協作原語 vs 可預測性 | 工程師 |
| HITL | 怎麼暫停、怎麼恢復、預設值是什麼？ | 開箱即用的核准 vs 綁定業務規則的彈性 | 產品、資安 |
| durable | 中途當掉能否續跑且不重做副作用？ | 框架內建 checkpoint vs 外部 durable 引擎 | SRE |
| 可觀測性 | 能否看到每一步、能否匯出與遮蔽？ | 廠商儀表板的便利 vs 開放格式 | SRE、資安 |
| 部署 | 跑在哪裡、資料經過哪裡？ | 託管的省事 vs 資料駐留與合規 | 資安、法務 |
| 生態 | 整合、範例、人才、維護健康度？ | 大生態的便利 vs 快速變動的升級成本 | 技術主管 |
| lock-in | 換掉要多少代價？ | 用得越深省得越多 vs 退路越少 | 技術主管、財務 |

這張總表的「誰最在意」一欄很重要。選型會議常常吵不出結果，是因為每個人心裡的權重不同：工程師看抽象與控制，資安看部署與狀態，技術主管看生態與 lock-in。把權重明確寫下來，讓大家先爭論權重、再看分數，比直接爭論「哪個框架比較好」有效得多。這也是加權決策矩陣真正的價值：它不是算出答案的機器，而是把隱含的假設攤在桌上的工具。

## 26.6 主流框架的設計哲學與核心抽象

有了維度，接下來看主流框架各自做了哪些取捨。每個框架背後都有一個設計哲學，也就是它認為「agent 最重要的是什麼」；核心抽象則是這個哲學的具體化。理解哲學比記住 API 有用，因為 API 每季都在變，哲學很少變。以下依公開文件整理，版本與近期新功能集中在 26.10 節。

```text
                         涵蓋範圍：從 library 到平台
                                    ▲
                   平台／託管        │  託管 harness（雲端 loop＋sandbox＋session）
                                    │  AgentCore、Gemini Agent Runtime（平台積木）
                                    │
                   all-in-one       │  Mastra（TS）        MAF（.NET／Python）
                                    │  ADK（多語言）        CrewAI（Crews＋Flows）
                                    │
                   harness          │                       Claude Agent SDK
                                    │
                   SDK／library     │  LangGraph   LlamaIndex Workflows   OpenAI Agents SDK
                                    │  Pydantic AI    AG2    Strands    DSPy（prompt 編譯）
                                    └──────────────────────────────────────────────────────►
                              程式碼決定控制流                         模型決定控制流
                              （graph、workflow、event）               （model-driven loop）
```

這張地圖有兩個軸。橫軸是「控制流主要由誰決定」：越左越像第 18、19 章的 workflow 與 graph，由程式碼畫好路徑；越右越像第 4 章的 agent loop，由模型決定下一步。縱軸是「涵蓋範圍」：最下面是你在自己程式裡呼叫的 SDK，往上是附帶檔案與 shell 工具的完整 harness，再往上是包含 workflow、memory、eval、部署的 all-in-one 框架，最上面是託管平台。注意很多框架橫跨兩端：近年的共同方向是「模型自主的 agent」與「確定性的 graph／workflow」並存並允許互相嵌套，所以位置只表示它的重心，不是邊界。

**OpenAI Agents SDK**：哲學是「Python-first，用程式碼編排，primitive 越少越好」。核心抽象只有幾個：`Agent`（指令、tools、handoffs、guardrails、輸出型別）、`Runner`（執行 loop）、**handoff**（把控制權轉給另一個 agent，被設計成一種特殊的 tool call，由模型決定路由）、guardrails（與主 agent 並行執行以降低延遲）、sessions 與內建 tracing。HITL 的做法是在 tool 上標記需要核准，run 帶著 interruption 結束，把 run state 序列化後再恢復。它沒有顯式的 graph 抽象，複雜流程用程式碼或 handoff 組合；可以透過 provider 設定接其他模型，但最順的路徑仍在 OpenAI 生態。適合以 OpenAI 模型為主、需要快速做出客服分流這類產品型 agent 的團隊。

**Claude Agent SDK**：哲學是「harness-first」，把 Claude Code 當成 library 使用。你拿到的不是一組抽象，而是一個經過大規模使用的完整 harness：檔案讀寫、shell、搜尋等內建 tools，permission modes 與「能不能使用這個 tool」的 callback，在 tool 前後執行的 hooks，subagents、skills、以檔案（例如 `CLAUDE.md`）承載的專案記憶，以及 session 的 resume 與 fork。它的底層是啟動並驅動 Claude Code 的 CLI 程式，所以多一個 process 邊界，也主要綁定 Claude 模型。適合 coding、ops、文件處理這類需要檔案系統與 shell 的通用 agent；純對話型的客服 agent 用它會顯得厚重。

**Google ADK**（Agent Development Kit）：哲學是「以 event 串流作為唯一的真相」，session 就是 event log，state 由 event 推導。核心抽象包括 `LlmAgent`、workflow agents（循序、平行、迴圈）、較新版本的顯式 graph workflow、產生 event 串流的 `Runner`，以及 session、memory、artifact 三種 service；callbacks 與 plugins 是擴充點。它支援多種語言，原生支援 A2A，與 Google Cloud 的託管 runtime 整合最順。概念數量多是它的學習成本。適合 Google Cloud 上的企業、需要多語言或 A2A 互通的多 agent 系統。

**LangGraph**（與建在它之上的 LangChain）：哲學是「state machine 加持久化 checkpoint 是 agent 可靠性的核心」。核心抽象是 `StateGraph`：state 用型別定義，每個欄位指定合併方式（reducer），節點與條件邊決定流程；checkpointer 在每一步保存 state，以 thread 隔離，支援從歷史 checkpoint 分岔（time travel）；`interrupt` 讓暫停與恢復成為 runtime 原語，而不是應用層的權宜做法。LangChain 的高階 agent 建構函式就建在 LangGraph 的 graph 之上，用 middleware 插入核准、摘要等行為。它是最成熟的低階、可控編排方案之一，代價是 reducer、super-step 這些概念的學習曲線，以及部署與觀測平台多半要搭配同一家的商業產品。適合需要精確流程控制、長時間運行與 HITL 的生產 agent。

**Microsoft Agent Framework**（MAF）：官方定位是 AutoGen 與 Semantic Kernel 的後繼，結合前者簡潔的 agent 抽象與後者的企業功能（session 狀態、型別安全、middleware、telemetry），再加上 graph 式 workflows（executors 與 edges，支援 checkpoint 與 request／response 形式的人工介入）。.NET 是一等公民，部署與 Microsoft 的雲端平台整合。它的官方文件有一個少見的明確立場：如果一個函式就能處理這件事，就寫函式，不要用 AI agent。適合 .NET 或 Microsoft 生態的企業，以及需要型別化 workflow 的多 agent 系統。

**CrewAI**：哲學是「角色扮演」式的心智模型。核心抽象是 `Agent`（角色、目標、背景故事、tools）、`Task`（描述與預期產出）、`Crew`（循序或階層式協作），非常容易向非工程背景的人解釋。它後來加入了 **Flows**：事件驅動、確定性的流程控制，可以持久化 state。這個「Crews 自主協作＋Flows 確定流程」的雙模式，等於承認純自主不足以支撐生產環境。適合原型、內容與研究類的多角色協作，以及商務自動化 PoC；需要精細調校時，高階抽象會變成阻力。

**AG2**：源自 AutoGen 社群分支，較新的主線版本是一個重新設計的框架，哲學是「protocol-first」：把 MCP、A2A、AG-UI 等標準協定當成 agent 的對外介面，框架內部的抽象相對薄。這個方向很值得自建框架的人參考。它的風險在於品牌與 API 經歷過多次分裂與重寫，舊版程式並不能直接升級，選它之前要特別評估長期維護。

**Pydantic AI**：哲學是「agent 是一個有型別的函式」：輸入是依賴（資料庫連線、HTTP client 等，透過 `RunContext` 注入），輸出是經過驗證的 schema。核心抽象是 `Agent`（帶有依賴型別與輸出型別的泛型）、用裝飾器註冊的 tools、toolsets（含 MCP），以及可以逐節點迭代的執行介面；另有獨立的 graph 套件。它把 durable execution 做成可插拔的後端，agent 程式碼不必為了換持久化方案而改動。適合重視型別與可測試性的 Python 後端團隊，以及結構化輸出密集的業務 agent；多 agent 的高階 pattern 較少，需要自己組。

**DSPy**：它不是 orchestration 框架，而是「把 prompt 當成可以編譯、可以優化的參數」。核心抽象是 Signature（宣告輸入與輸出，例如「問題 → 答案」）、Module（例如鏈式推理、ReAct）、Optimizer（依 metric 自動調整指令與範例）。在 agent system 裡，它最適合用來優化個別模組：router、資訊抽取器、judge。第 30 章會談 prompt optimization 時再回來。把它和 LangGraph 放在同一張比較表上選「二擇一」，是常見的類別錯誤。

**Strands Agents**：哲學是「相信模型」，盡量不寫 orchestration 程式碼。核心是 model-driven loop：`Agent(model, tools, system_prompt)`，由模型自己規劃；需要確定性時再用它提供的 Graph、Swarm、Workflow 等多 agent 模式，或 agents-as-tools。它支援多家模型供應商，預設偏向 AWS 生態，與 AWS 的託管 agent 平台整合最順。適合 AWS 上的生產 agent，以及「強模型＋好 tools 就夠」的任務。

**Mastra**：TypeScript 生態的 all-in-one agent server。核心抽象包括 `Agent`、用 schema 函式庫定義的 tools、可以 suspend 與 resume 的 workflows、多種 memory（thread、working memory、語意召回）、把 guardrail 與路由統一起來的 processor 管線、scorers 與 eval，以及本機開發用的 Studio。適合 Next.js 或 Node 全端團隊在 SaaS 內嵌 agent；API 表面積大、變動快，Python 團隊用不到。

**LlamaIndex**：哲學是用「事件與 step」描述流程，而不是「節點與邊」。Workflow 中每個 step 接收與發出有型別的 event，控制流由 event 型別隱式決定；`Context` 保存 state，可以序列化後恢復，也能等待外部 event 實作 HITL。agent 層有 function calling agent、ReAct agent 與多 agent 的 handoff workflow。它與 RAG、文件解析的整合最深，適合 document agent 與資料抽取 pipeline。

| 框架 | 設計哲學（一句話） | 核心抽象 | 最強的維度 | 不適合的情況 |
|---|---|---|---|---|
| OpenAI Agents SDK | 少量 primitive，用程式碼編排 | Agent、Runner、handoff、guardrail、session | 上手速度、tracing | 需要顯式 graph 與 checkpoint 的長流程 |
| Claude Agent SDK | harness-first，直接繼承完整 coding harness | 內建 tools、permissions、hooks、subagents、skills | 生態與內建能力 | 純對話型、需要多模型供應商 |
| Google ADK | event log 是唯一真相 | LlmAgent、workflow agents、graph、Runner、services | 多語言、A2A | 不想學大量概念的小團隊 |
| LangGraph | state machine＋checkpoint | StateGraph、reducer、checkpointer、interrupt | 狀態、HITL、durable | 只需要單一 agent 的簡單任務 |
| MAF | agent 與 typed workflow 分層 | Agent、workflow（executors／edges）、middleware | .NET、企業整合 | 非 Microsoft 生態、要求 API 穩定 |
| CrewAI | 角色扮演＋確定性 Flows | Agent、Task、Crew、Flow | 原型速度、易溝通 | 需要精細控制與可預測性 |
| AG2 | protocol-first | 以協定為介面的 agent | 協定互通 | 重視長期 API 穩定 |
| Pydantic AI | agent 是有型別的函式 | Agent[Deps, Output]、RunContext、toolsets | 型別安全、可插拔 durable | 需要大量現成多 agent pattern |
| DSPy | prompt 是可編譯的參數 | Signature、Module、Optimizer | 模組級優化 | 當成 orchestration 框架使用 |
| Strands | 相信模型 | model-driven Agent、Graph、Swarm | 簡潔、AWS 整合 | 需要從頭到尾的確定性流程 |
| Mastra | TS 的 batteries-included server | Agent、workflow、memory、processor | TS 全端一站式 | Python 團隊 |
| LlamaIndex | event 與 step | Workflow、Event、Context、AgentWorkflow | RAG 與文件 | 與檢索無關的通用 agent |

這張表最後兩欄比前面幾欄更有用。「最強的維度」告訴你它在 26.3 到 26.5 節的哪個維度可能拿高分；「不適合的情況」則是 POC 之前就能先排除的訊號。表中的判斷是依公開的設計文件與定位歸納，屬於本書的整理，不是官方說法；而且框架演進很快，某一欄的弱點下一季可能就被補上。正確用法是把它當成提出 POC 假設的起點，例如「LangGraph 在客服退款流程的 HITL 應該很強，我們用殺 process 測試驗證」，而不是當成結論。

> [!warning] 常見誤解
> 「框架的 GitHub 星數越多越好。」星數反映的是關注度，不是適合度，也不是維護健康度。更有參考價值的是：最近半年的發版與 breaking change 紀錄、issue 的回應速度、核心維護者是誰、文件是否與程式同步。有些框架曾經非常熱門，之後維護節奏明顯放緩；也有框架因為重寫或品牌分裂，讓早期使用者面臨不能直接升級的遷移。

## 26.7 託管 agent 服務：連 harness 一起外包

框架之外，另一類選項是託管 agent 服務。它們又可以分成兩種，差別在「loop 由誰跑」。**託管 harness** 連 agent loop 都在雲端執行：你定義 agent（模型、指令、tools、MCP 連線、skills），建立 session，送出任務，透過事件串流看進度，loop、context 壓縮、sandbox、session 持久化都由服務處理。**託管平台積木**則不跑你的 loop，而是提供可以分開使用的服務：託管 runtime（把你用任何框架寫的 agent 部署上去）、memory、tool gateway、identity、policy、eval。兩者可以混用：用平台的 runtime 跑你的框架，同時用它的 gateway 管理 tools。

```text
                 責任分擔：誰負責什麼

   你永遠負責                       託管 harness 接手              託管平台積木提供
 ┌──────────────────────────┐   ┌──────────────────────────┐   ┌───────────────────────┐
 │ 業務 tools 與其副作用     │   │ agent loop 與停止條件     │   │ runtime（跑你的框架） │
 │ approval 政策的「內容」   │   │ context 壓縮              │   │ tool gateway          │
 │ prompts 與其版本          │   │ sandbox 的配置與回收      │   │ identity／OAuth 代管  │
 │ eval set 與成功標準       │   │ session 持久化與恢復      │   │ memory 服務           │
 │ 資料分類與合規判斷        │   │ 事件串流、中途 steer      │   │ policy、eval、registry│
 │ 事故處理與對使用者的承諾  │   │                          │   │                       │
 └──────────────────────────┘   └──────────────────────────┘   └───────────────────────┘
          ▲                                  │                              │
          └──────────── 兩種託管都不會替你決定：什麼動作需要人核准、成功是什麼樣子 ──┘
```

這張圖的左欄是任何選擇都不會改變的責任。託管 harness 可以替你跑 loop，但它不知道「500 元以上的退款要客服核准」，這條規則仍然要由你寫進 tool 的設定或 approval callback；它也不知道「回答正確」對青鳥代表什麼，eval 仍然是你的。中欄是託管 harness 接手的部分，也就是第 4、10、17、22 章花大量篇幅自己做的東西。右欄是平台積木，它們的好處是可以只拿需要的那一塊，例如只用 identity 服務代管 OAuth token，而 loop 仍然跑在自家的框架上。

託管 harness 的設計值得框架作者學習。Anthropic 在〈Scaling Managed Agents〉中描述了把「brain」（harness 與模型）、「hands」（sandbox 與 tools）、「session」（持久的事件紀錄）三者分開的設計：harness 本身無狀態，任何一台機器都能用 session id 喚醒並從事件紀錄恢復；sandbox 只在需要 tool 時才配置，壞了就重建，以 tool 錯誤的形式回報給模型。這正是第 10 章「context 是 session log 的可重建視圖」與第 22 章 durable execution 的雲端版本。換句話說，託管 harness 不是魔法，它是把本書 Part 2 到 Part 4 的原則做成了服務。

| 取捨面向 | 自建或自託管框架 | 託管 harness | 託管平台積木＋自家框架 |
|---|---|---|---|
| 上線速度 | 慢：loop、sandbox、session 都要自己做 | 快：定義 agent 即可執行 | 中：框架要自己寫，營運交給平台 |
| 控制力與透明度 | 最高：每一行都看得到 | 最低：compaction、重試策略由服務決定 | 高：loop 是你的，基礎設施是平台的 |
| 資料駐留與合規 | 完全自己決定 | 受限於服務支援的區域、保留政策、ZDR | 依平台；通常可選區域與私有網路 |
| 模型選擇 | 任意 | 通常以該廠商模型為主，部分支援多家 | 依框架；平台通常與模型無關 |
| 狀態 lock-in | 低：格式自己定 | 高：session 與事件紀錄在對方那端 | 中：memory 與 session 服務各自評估 |
| 營運負擔 | 高：on-call、擴展、升級都是你的 | 低 | 中 |
| 成本結構 | 工程人力為主 | 用量計費為主，含 sandbox 與儲存 | 兩者混合 |

讀這張表時要注意一個不對稱：託管 harness 在「上線速度」與「營運負擔」上的優勢，在第一個月最明顯；「控制力」與「狀態 lock-in」上的劣勢，則要到第一次出事故或第一次想換廠商時才會感受到。所以評估託管服務時，請特別測兩件事：出事時你能拿到什麼（完整的事件紀錄？送給模型的 context？），以及要離開時你能帶走什麼（session 能不能匯出？格式是什麼？）。

> [!warning] 常見誤解
> 「用了託管服務，安全與合規就是廠商的責任。」託管只轉移了基礎設施層的責任。tool 的權限範圍、哪些動作需要核准、資料是否應該送進模型、prompt injection 的防禦設計，仍然是你的責任（第 31、32 章）。還要特別確認服務的資料處理條款：某些託管 harness 在特定階段不支援 ZDR 或特定合規協議，這對處理個資或醫療資料的 agent 是硬性限制。

## 26.8 Build vs buy：決策流程

**build vs buy** 是軟體業的老問題：自己做，還是買現成的？放在 agent system 裡，選項不只兩個，而是一條光譜：完全自建、站在低階框架上自建、採用高階框架、託管平台積木搭配自家框架、託管 harness。下面的流程圖把前面幾節的維度排成提問順序：先用硬性限制淘汰，再問差異化，再依任務形態選位置。

```text
 開始：針對「一個 agent」做決策（不是整間公司）
   │
   ▼
 (1) 有不可妥協的限制嗎？資料駐留、ZDR、地端部署、指定語言、指定模型
   │   有 ──► 淘汰做不到的選項（不打分數，直接出局）
   ▼
 (2) loop／harness 本身就是產品的差異化嗎？（例如你在賣 coding agent）
   ├─ 是 ──► 自建核心 harness（可站在低階框架或模型 API 上），把工程投資集中在這裡
   │ 否
   ▼
 (3) 任務需要檔案系統＋shell 的通用 harness 嗎？（coding、ops、文件處理）
   ├─ 是 ──► 完整 harness SDK，或託管 harness（若 (1) 允許）
   │ 否
   ▼
 (4) 流程需要顯式狀態機、長時間暫停、從任一步恢復嗎？（退款、審批、長研究）
   ├─ 是 ──► graph／state machine 框架＋durable 引擎，或託管 runtime
   │ 否
   ▼
 (5) 單一 agent、少量 tools、要快速上線？
   ├─ 是 ──► 輕量 code-first SDK；營運人力不足時考慮託管 harness
   ▼
 不論走哪條路：tool 定義、approval 政策、prompts、eval、trace、session log 格式自己擁有，
 框架放在 adapter 後面（26.9 節），並把這次決策寫成可在一季後重新檢視的紀錄
```

逐步看這張圖。第 (1) 步把硬性限制放在最前面，因為它們不能被分數補償：一個在其他八個維度都拿滿分、但資料不能留在指定區域的選項，對 Maya 來說就是零分。第 (2) 步問差異化：如果 harness 就是你的產品，例如你在賣 coding agent，那麼 loop 的每一個細節都是競爭力，外包等於外包核心能力；反之，青鳥的差異化在電商的 tools 與政策，loop 本身不是賣點。第 (3) 到 (5) 步依任務形態選光譜上的位置，順序反映「最特殊的需求先決定」。最後一行是所有分支的共同結論：不論選了什麼，第 ② 層與幾份關鍵資料的格式要留在自己手上。

這張流程圖刻意從「一個 agent」開始，而不是「整間公司」。這回應了阿哲的問題：青鳥的客服、coding、research 三個 agent 走流程圖會走到不同分支，這是正常的。公司層級要統一的是流程圖最後一行的那些契約，而不是 runtime。

決策時還要算清楚 **TCO**（total cost of ownership，總持有成本）：不只是授權費或用量費，還包括建置、整合、營運、升級與將來遷移的成本。

| 選項 | 初期投入 | 持續成本 | 隱性成本 | 適合的團隊與情境 |
|---|---|---|---|---|
| 完全自建（模型 API＋自家 harness） | 高：loop、錯誤處理、context、sandbox、durable 全部自己做 | 中：維護與跟進模型 API 變動 | 人才集中風險；容易重造別人已經做好的輪子 | harness 是差異化；或需求極特殊 |
| 低階框架＋自家抽象 | 中 | 中：跟進框架升級 | 框架概念的學習曲線；升級 breaking change | 需要精確控制流程的生產 agent |
| 高階框架 | 低 | 中：升級、繞過框架限制 | 需求超出框架預想時的「逆向工程」 | 原型、標準形態的 agent |
| 託管平台積木＋自家框架 | 中 | 中：用量費＋框架維護 | 平台服務各自的 lock-in | 有合規要求、想減少基礎設施營運 |
| 託管 harness | 最低 | 用量費（模型、sandbox、儲存） | 透明度低；狀態 lock-in；服務條款與功能變動 | 營運人力少、合規允許、要快速驗證 |

表中的「隱性成本」一欄最容易被低估。高階框架的隱性成本，常在 agent 品質卡在某個水準時出現：12-Factor Agents 的作者觀察到，用框架很快能達到不錯的品質，但要再往上突破，往往得逆向理解框架、甚至繞過它，所以它主張「own your control flow」「own your prompts」「own your context window」。託管 harness 的隱性成本則是變動風險：服務仍在 beta、功能與條款可能調整，你的路線圖會跟著對方走。這些成本無法精確估算，但至少要寫進決策紀錄，讓一季後的檢視有依據。

## 26.9 遷移策略與避免 lock-in

即使今天的選擇是對的，一年後也可能不再是對的：模型換代、框架停止維護、託管服務改條款、合規要求改變。遷移策略的目標不是「永不 lock-in」，那代價太高；而是讓 lock-in 集中在少數、已知、可替換的地方。先把 lock-in 拆開來看。

| lock-in 類型 | 例子 | 怎麼量 | 怎麼降低 |
|---|---|---|---|
| API lock-in | 業務程式到處直接 import 框架的類別與裝飾器 | 掃描框架 import 出現在 adapter 目錄外的次數 | 中立的 ToolSpec、Runtime port；框架相依只放在 adapter |
| 狀態 lock-in | session、memory、checkpoint 存在框架或廠商的專屬格式與位置 | 試著匯出一週的 session，計算能還原的比例 | 自家擁有 session log 格式；託管端只當快取或執行者 |
| 行為 lock-in | prompt 與 eval 依賴某個 harness 的預設 compaction、內建 tools 或核准預設值 | 換 runtime 跑同一組 eval，看成功率掉多少 | 契約測試；把預設值寫成顯式設定；prompt 不提框架細節 |
| 營運 lock-in | trace 只在廠商儀表板、部署管線與權限綁定在平台 | 列出事故時必須登入的廠商系統 | 匯出開放格式的 trace；IaC 管理部署 |
| 模型 lock-in | SDK 或 harness 只支援單一模型家族 | 列出換模型時要改的檔案 | 第 25 章的 model adapter；把模型選擇放在設定裡 |

這張表裡最隱蔽的是**行為 lock-in**。API lock-in 很容易看見，搜尋 import 就知道；行為 lock-in 卻藏在「它剛好這樣做」裡。Iris 在 POC 遇到的漏洞就是一例：`loom` 把未標註的 tool 當 destructive，新框架當 safe，兩邊的程式都沒有錯，但業務規則在搬家時悄悄改變了。同樣的事會發生在 context 壓縮的時機、tool 錯誤的回填格式、重試次數上。降低行為 lock-in 的唯一可靠方法是**契約測試**（contract test）：用同一組劇本在新舊 runtime 上跑，驗證「可觀察的行為」一致，26.11 節會實作。

降低 API lock-in 的標準做法是 **adapter**（轉接層），也就是軟體架構裡的 ports and adapters（又稱 hexagonal architecture）：核心程式只依賴自己定義的介面（port），每個外部系統各寫一個 adapter 實作這個介面。放到 agent system 裡，port 就是 `loom` 在第 23 到 25 章定義的那些抽象：中立的 tool 定義、Runtime 的 `run()`、model adapter。

```text
            青鳥擁有（穩定、長期）                         可替換（adapter 後面）
 ┌──────────────────────────────────────────┐
 │ 業務 tools：ToolSpec（含副作用分級、      │        ┌──────────────────────────────┐
 │            intent_fields）               │  ──►   │ loom 原生 runtime             │
 │ approval 政策：哪些動作需要誰核准         │        ├──────────────────────────────┤
 │ prompts（版本化）、eval set、成功標準     │  ──►   │ graph 框架 adapter            │
 │ session log 與 trace 的 schema            │        ├──────────────────────────────┤
 └───────────────────┬──────────────────────┘  ──►   │ harness SDK adapter           │
                     │                                ├──────────────────────────────┤
          ports：Runtime.run()、ToolExporter、  ──►   │ 託管 harness adapter          │
                 ModelPort、TraceSink                 └──────────────────────────────┘
                     │
          契約測試：同一組劇本在每個 adapter 上的可觀察行為必須一致
```

這張圖左邊是青鳥長期擁有、不隨框架改變的東西，右邊是可以替換的 runtime。中間的 port 是兩邊唯一的接觸面：`Runtime.run()` 接收任務、回傳結果與 trace；`ToolExporter` 把中立的 tool 定義轉成某個框架或 API 要的格式；`ModelPort` 是第 25 章的 model adapter；`TraceSink` 接收 span 並轉成開放格式。底部的契約測試是這個架構的安全網：adapter 寫錯一個預設值，測試就會失敗。注意 adapter 本身要保持「薄」，只做格式與呼叫方式的轉換，業務判斷（例如什麼需要核准）一律留在左邊，否則換框架時就要重寫業務規則。

要知道 API lock-in 現在有多深，可以寫一個小工具掃描 repo，找出框架 import 出現在 adapter 目錄外的地方。下面的程式用標準函式庫的 `ast` 分析原始碼，`acme_agents` 代表任何第三方 agent 框架。

```python
from __future__ import annotations

import ast

# 青鳥 repo 的簡化版：檔案路徑 → 原始碼。acme_agents 代表任何第三方 agent 框架。
REPO = {
    "loom/adapters/acme.py": "from acme_agents import Agent, function_tool\nimport acme_agents.tracing\n",
    "loom/tools/orders.py": "from loom.tools import ToolSpec\n",
    "support/refund_flow.py": "from loom.tools import ToolSpec\nfrom acme_agents import RunContext\n",
    "support/prompts.py": "SYSTEM = '你是青鳥客服'\n",
    "research/report.py": "import acme_agents.extensions.memory as mem\n",
}
VENDORS = {"acme_agents"}
ALLOWED_PREFIX = "loom/adapters/"          # 只有 adapter 目錄可以直接相依框架


def vendor_imports(source: str) -> list[str]:
    found = []
    for node in ast.walk(ast.parse(source)):
        names = [a.name for a in node.names] if isinstance(node, ast.Import) else \
                [node.module or ""] if isinstance(node, ast.ImportFrom) else []
        found += [n for n in names if n.split(".")[0] in VENDORS]
    return found


leaks = {path: vendor_imports(src) for path, src in REPO.items()
         if not path.startswith(ALLOWED_PREFIX) and vendor_imports(src)}
inside = sum(len(vendor_imports(s)) for p, s in REPO.items() if p.startswith(ALLOWED_PREFIX))
print(f"adapter 內的框架相依：{inside} 處（允許）")
for path, names in leaks.items():
    print(f"洩漏到業務程式：{path:<24} {names}")
assert set(leaks) == {"support/refund_flow.py", "research/report.py"}
```

```text
adapter 內的框架相依：2 處（允許）
洩漏到業務程式：support/refund_flow.py   ['acme_agents']
洩漏到業務程式：research/report.py       ['acme_agents.extensions.memory']
```

輸出的第一行是允許的相依：adapter 目錄裡有兩處 import，這是預期中的位置。後兩行是洩漏：`support/refund_flow.py` 在業務流程裡直接用了框架的 `RunContext`，`research/report.py` 則直接用了框架的 memory 擴充。前者會讓退款規則在換框架時必須重寫，後者會讓 research 的記憶資料綁在框架的格式上。這種掃描很適合放進 CI，當成一條 lint 規則：新的洩漏需要在 code review 時說明理由，舊的洩漏列入清理清單。

有了 adapter 與契約測試，實際的遷移可以分階段進行，每一步都可以回頭。這是 **strangler fig**（絞殺榕）模式在 agent system 的應用：新系統逐步包住舊系統，流量一點一點移過去，直到舊路徑可以移除。

```text
  ┌────────┐    ┌──────────┐    ┌──────────┐    ┌────────┐    ┌────────┐    ┌────────┐
  │ 盤點   │──► │ 包 adapter│──► │ 契約測試 │──► │ shadow │──► │ canary │──► │ 切換   │
  │ 耦合點 │    │ 業務程式  │    │ 全數通過 │    │ 並跑   │    │ 5%→50% │    │ 移除舊 │
  └────────┘    │ 不再 import│    └────┬─────┘    └───┬────┘    └───┬────┘    └────────┘
                │ 框架      │         │ 失敗          │ 差異超標    │ 指標退化
                └──────────┘         ▼              ▼             ▼
                                  修 adapter      回到契約測試    切回舊 runtime（一個設定值）
```

逐步看這條路線。「盤點」用上面的掃描工具列出耦合點，並決定哪些狀態要搬、哪些可以讓舊 session 自然結束。「包 adapter」讓業務程式只依賴 port。「契約測試」用一組代表性劇本（正常路徑、錯誤回填、需要核准、預算超支）驗證新 runtime。**shadow**（影子流量）是讓新 runtime 在背景處理同樣的請求，但結果不回給使用者，也不執行任何有副作用的動作，只比較兩邊的 trajectory 與輸出差異；有副作用的 tool 在 shadow 模式下一律換成記錄意圖的假實作。**canary**（金絲雀發布）則是讓一小部分真實流量走新路徑，觀察成功率、成本、延遲與轉真人比例。每一個箭頭都有回頭路，而最後的切換只是一個設定值，所以出問題時可以在幾分鐘內切回去。第 36 章會更完整地談 canary 與 shadow 的基礎設施。

> [!tip] 狀態的遷移策略
> session 狀態通常不值得逐筆轉換格式。對短 session（客服對話），讓進行中的 session 在舊 runtime 上自然結束、新 session 走新 runtime，最省事。對長 session（數天的 research 任務），讓它在舊 runtime 跑完，或在一個安全的 checkpoint 匯出成自家的 session log 格式，再由新 runtime 從 log 重建 context。這也是為什麼 session log 的格式要自己擁有：它是唯一能在不同 runtime 之間攜帶的狀態。

> - **Gemini Enterprise Agent Platform 的 Agent Runtime**：原 Vertex AI Agent Engine 的文件頁面現在使用這個名稱（是否為正式更名，頁面未明說）；提供託管部署、Sessions、Memory Bank、Code Execution、Evaluation，支援 ADK、LangChain、LangGraph、LlamaIndex、AG2 等框架。
>
> 同一時期的幾件事，正好說明為什麼要避免 lock-in：OpenAI Assistants API 已於 2026-08-26 停止服務，改用 Responses 與 Conversations；OpenAI 的視覺化 Agent Builder 宣布預計 2026-11-30 關閉（ChatKit 保留）；MCP 2026-07-28 版的無狀態改版帶動多數框架在 2026-08 到 09 月發布支援新版 MCP SDK 的版本，其中部分是 breaking change。

這兩個區塊的資訊會很快過時，但它們揭露的模式不會：0.x 版本與每週發版代表持續的升級成本；重寫與品牌分裂代表遷移風險；平台 API 的停止服務代表狀態 lock-in 的真實代價。把這些訊號放進 26.5 節的「生態」與「lock-in」維度打分，比記住任何一個版本號都更有用。

## 26.11 動手做：加權決策矩陣與 tool adapter

這一節把前面的方法寫成三段程式。第一段是加權決策矩陣，替青鳥的三個 agent 跑選型；第二段是 tool adapter，把同一份中立的 tool 定義匯出成不同 API 與協定需要的格式；第三段用 ScriptedModel 寫契約測試，重現 Iris 在 POC 遇到的核准漏洞並修好它。三段程式都只做資料轉換與模擬，不連網、不 import 任何框架。

### 第一段：加權決策矩陣與敏感度分析

矩陣的候選方案用五種「類型」而不是具體產品，因為分數必須來自你自己的 POC，而不是別人的評比。對照 26.6 節，B 大致對應 OpenAI Agents SDK、Pydantic AI、Strands 這類 code-first SDK；C 對應 LangGraph、MAF workflows、ADK graph 這類 graph 框架；D 對應 Claude Agent SDK 這類完整 harness；E 對應託管 harness。程式有三個設計：硬性能力用 gate 先淘汰，不進入加權；分數是加權平均；最後做敏感度分析，看權重稍微變動時第一名會不會換人。

```python
from __future__ import annotations

import unicodedata
from dataclasses import dataclass, field

# 九個選型維度（26.3–26.5 節）。分數 1–5 是青鳥團隊 POC 後的評估，不是業界通用分數。
DIMS = ["抽象", "狀態", "多 agent", "HITL", "durable", "觀測", "部署", "生態", "可攜"]


@dataclass
class Candidate:
    name: str
    scores: dict[str, int]          # 每個維度 1–5 分
    caps: set[str]                  # 硬性能力：有或沒有，不打分數


@dataclass
class Requirement:
    agent: str
    weights: dict[str, int]         # 0–5：這個維度對這個 agent 有多重要
    gates: set[str] = field(default_factory=set)   # must-have：缺一項就淘汰，不進入加權


def S(*vals: int) -> dict[str, int]:
    return dict(zip(DIMS, vals))


CANDIDATES = [
    #                               抽象 狀態 多 agent HITL durable 觀測 部署 生態 可攜
    Candidate("A 自建 loom",       S(5, 4, 3, 4, 3, 3, 5, 2, 5), {"self_host", "approval", "multi_provider", "durable"}),
    Candidate("B code-first SDK",  S(4, 3, 4, 4, 3, 4, 4, 4, 3), {"self_host", "approval", "multi_provider"}),
    Candidate("C graph 框架",      S(4, 5, 4, 5, 4, 4, 4, 4, 3), {"self_host", "approval", "multi_provider", "durable"}),
    Candidate("D harness SDK",     S(2, 3, 5, 4, 3, 4, 3, 5, 2), {"self_host", "approval", "sandbox"}),
    Candidate("E 託管 harness",    S(2, 4, 3, 3, 5, 4, 5, 4, 1), {"approval", "sandbox", "durable"}),
]

REQUIREMENTS = [
    # 客服：PII 必須留在青鳥自己的 VPC（Maya 的要求），退款要人工核准，未來要能換模型
    Requirement("客服 agent", S(3, 5, 1, 5, 2, 4, 4, 2, 5), {"self_host", "approval", "multi_provider"}),
    # coding：重點是檔案、shell 與 sandbox 這些現成能力，寫入動作在 sandbox 內
    Requirement("coding agent", S(2, 2, 3, 3, 2, 3, 2, 5, 2), {"sandbox", "approval"}),
    # research：跑幾十分鐘到數小時，要能從中斷處恢復、多個 subagent 平行
    Requirement("research agent", S(3, 4, 5, 2, 5, 4, 2, 3, 3), {"durable"}),
]


def pad(text: str, width: int) -> str:
    """中文字在終端機佔兩格，str.ljust 會對不齊，所以自己算寬度。"""
    w = sum(2 if unicodedata.east_asian_width(ch) in "WF" else 1 for ch in text)
    return text + " " * max(0, width - w)


def score(c: Candidate, r: Requirement) -> float:
    total_w = sum(r.weights.values())
    return sum(r.weights[d] * c.scores[d] for d in DIMS) / total_w   # 加權平均，仍是 1–5 分


def rank(r: Requirement, weights: dict[str, int] | None = None) -> list[tuple[str, float]]:
    req = Requirement(r.agent, weights or r.weights, r.gates)
    alive = [c for c in CANDIDATES if r.gates <= c.caps]           # 先過 gate，再比分數
    return sorted(((c.name, score(c, req)) for c in alive), key=lambda x: -x[1])


def flips(r: Requirement, delta: int = 2) -> list[str]:
    """敏感度分析：每個維度的權重各自 ±delta，看第一名會不會換人。"""
    winner = rank(r)[0][0]
    out = []
    for d in DIMS:
        for sign in (+1, -1):
            w = dict(r.weights)
            w[d] = max(0, w[d] + sign * delta)
            new = rank(r, w)[0][0]
            if new != winner:
                out.append(f"{d}{'+' if sign > 0 else '-'}{delta}→{new.split()[0]}")
    return out


results = {}
for r in REQUIREMENTS:
    ranked = rank(r)
    out = [c.name for c in CANDIDATES if not r.gates <= c.caps]
    results[r.agent] = ranked
    print(f"── {r.agent}  gate={sorted(r.gates)}")
    print(f"   淘汰：{', '.join(out) or '無'}")
    for name, s in ranked:
        print(f"   {pad(name, 18)} {s:.2f}")
    gap = ranked[0][1] - ranked[1][1] if len(ranked) > 1 else 9.0
    verdict = "差距小，視為平手，改看 lock-in 與團隊熟悉度" if gap < 0.15 else "領先明確"
    print(f"   第一名領先 {gap:.2f}：{verdict}")
    print(f"   權重 ±2 會翻盤的維度：{', '.join(flips(r)) or '無'}\n")

assert results["客服 agent"][0][0] == "C graph 框架"
assert "E 託管 harness" not in dict(results["客服 agent"])            # 被資料駐留的 gate 擋下
assert results["coding agent"][0][0] == "D harness SDK"
assert results["research agent"][0][0] == "C graph 框架"
```

   淘汰：D harness SDK, E 託管 harness
   C graph 框架       4.16
   A 自建 loom        4.03
   B code-first SDK   3.61

逐段看輸出。**客服 agent** 的三個 gate 淘汰了 D 與 E：D 這類完整 harness 主要綁定單一模型家族，過不了「未來要能換模型」；E 過不了資料必須留在青鳥自己帳號的限制。剩下的三個候選中，C graph 框架以 4.16 分領先 A 自建 loom 的 4.03 分，但差距只有 0.13，程式判定為平手。敏感度分析更說明問題：只要「生態」的權重降 2，或「可攜」的權重升 2，第一名就換成 A。這代表結論取決於一個價值判斷：青鳥有多在乎將來換得掉？這不是矩陣能回答的，要由人決定。

**coding agent** 的 gate 是 sandbox 與核准，淘汰了 A、B、C，剩下 D 與 E；D 以 3.75 對 3.50 明確領先，而且權重 ±2 都不會翻盤。D 贏在「多 agent」與「生態」：現成的檔案工具、shell、subagents 正是 coding agent 最需要的東西。**research agent** 的 gate 是 durable，淘汰了 B 與 D；C 以 4.10 明確領先：research 最看重的 multi-agent、狀態與 durable 三個維度中，C 在前兩項高於 E，E 只在 durable 多 1 分，又在抽象層級與可攜性上明顯落後。A 雖然有第 22 章的 `loom.durable`，但這是教學等級的實作，團隊給它 3 分。

青鳥最後的決定是這樣的。客服 agent 留在 `loom`：分數平手，而客服的退款與核准規則正是青鳥的差異化，加上 Maya 的資料駐留要求，自己擁有最穩妥。coding agent 採用完整的 harness SDK，包在 `loom` 的 runtime adapter 後面，讓 tool 定義、核准政策與 trace 仍然走 `loom` 的契約。research agent 用 graph 框架做下一輪 POC，同樣放在 adapter 後面，一季後依實測資料重新檢視。三個 agent 三個答案，但它們共用同一份 tool 定義格式、同一套 approval 政策、同一種 trace schema，這就是阿哲要的「統一」。

### 第二段：同一份 tool 定義，匯出成各家格式

第二段是 `loom.tools` 裡的 exporter：中立的 `ToolSpec` 記錄名稱、描述、參數、副作用分級與推導 idempotency key 用的 `intent_fields`（第 5 章），exporter 把它轉成 OpenAI Responses、Anthropic Messages、Gemini 與 MCP 各自的 tool 定義格式；importer 則把各家回傳的 tool call 轉回中立的 `ToolCall`。欄位名稱依 2026-10 的公開文件撰寫，實際整合時請以官方文件為準。

```python
from __future__ import annotations

import copy
import json
from dataclasses import dataclass, field
from typing import Any


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class Param:
    name: str
    type: str                       # string｜integer｜number｜boolean
    description: str
    required: bool = True
    enum: list[str] | None = None


@dataclass
class ToolSpec:
    """loom.tools 的中立 tool 定義：青鳥自己擁有的契約，不屬於任何框架。"""
    name: str
    description: str
    params: list[Param]
    side_effect: str = "destructive"            # read｜write｜destructive；未標註一律當 destructive
    intent_fields: list[str] = field(default_factory=list)   # 推導 idempotency key 用，不給模型看

    def json_schema(self) -> dict[str, Any]:
        props = {}
        for p in self.params:
            props[p.name] = {"type": p.type, "description": p.description}
            if p.enum:
                props[p.name]["enum"] = p.enum
        return {"type": "object", "properties": props,
                "required": [p.name for p in self.params if p.required]}


# ── exporters：純資料轉換，不 import 任何 SDK ──────────────────────────
def strictify(schema: dict[str, Any]) -> dict[str, Any]:
    """strict 模式的常見限制：關閉額外欄位、所有欄位列入 required，選填欄位改成可為 null。"""
    s = copy.deepcopy(schema)
    for name, prop in s["properties"].items():
        if name not in s["required"]:
            prop["type"] = [prop["type"], "null"]
            if "enum" in prop:
                prop["enum"] = prop["enum"] + [None]     # 不補 None，null 會被 enum 擋掉
    s["required"] = list(s["properties"])
    s["additionalProperties"] = False
    return s


def to_openai_responses(t: ToolSpec) -> dict[str, Any]:
    return {"type": "function", "name": t.name, "description": t.description,
            "parameters": strictify(t.json_schema()), "strict": True}


def to_anthropic(t: ToolSpec) -> dict[str, Any]:
    return {"name": t.name, "description": t.description, "input_schema": t.json_schema()}


def to_gemini(t: ToolSpec) -> dict[str, Any]:
    return {"type": "function", "name": t.name, "description": t.description,
            "parameters": t.json_schema()}


def to_mcp(t: ToolSpec) -> dict[str, Any]:
    # MCP 的 annotations 只是給 host 的提示，真正的權限仍由我們的 approval policy 決定
    return {"name": t.name, "description": t.description, "inputSchema": t.json_schema(),
            "annotations": {"readOnlyHint": t.side_effect == "read",
                            "destructiveHint": t.side_effect == "destructive"}}


# ── importers：把各家的 tool call 轉回中立的 ToolCall ───────────────────
def from_openai(item: dict[str, Any]) -> ToolCall:
    return ToolCall(item["call_id"], item["name"], json.loads(item["arguments"]))  # arguments 是字串


def from_anthropic(block: dict[str, Any]) -> ToolCall:
    return ToolCall(block["id"], block["name"], block["input"])


def normalize(args: dict[str, Any], t: ToolSpec) -> dict[str, Any]:
    """strict 模式下模型會對選填欄位填 null；回到中立格式時把 null 拿掉，業務程式不必知道差異。"""
    optional = {p.name for p in t.params if not p.required}
    return {k: v for k, v in args.items() if not (k in optional and v is None)}


REFUND = ToolSpec(
    "refund_order", "對未出貨訂單退款。已出貨的訂單請改用 create_return。",
    [Param("order_id", "string", "訂單編號，例如 B-1042"),
     Param("amount", "integer", "退款金額（新台幣元）"),
     Param("reason", "string", "退款原因", required=False, enum=["damaged", "late", "other"])],
    side_effect="destructive", intent_fields=["order_id", "amount"])

exports = {"openai": to_openai_responses(REFUND), "anthropic": to_anthropic(REFUND),
           "gemini": to_gemini(REFUND), "mcp": to_mcp(REFUND)}
SCHEMA_KEY = {"openai": "parameters", "anthropic": "input_schema", "gemini": "parameters", "mcp": "inputSchema"}
for target, d in exports.items():
    key = SCHEMA_KEY[target]
    extra = {k: v for k, v in d.items() if k not in ("name", "description", key)}
    print(f"{target:<9} {key:<12} required={d[key]['required']}  其他={extra}")
reason = exports["openai"]["parameters"]["properties"]["reason"]
print("openai 的 reason：", reason["type"], reason["enum"])

# 同一個意圖，兩家回傳的格式不同，轉回來必須一模一樣
oa = {"type": "function_call", "call_id": "c1", "name": "refund_order",
      "arguments": '{"order_id": "B-1042", "amount": 1200, "reason": null}'}
an = {"type": "tool_use", "id": "c1", "name": "refund_order",
      "input": {"order_id": "B-1042", "amount": 1200}}
a, b = from_openai(oa), from_anthropic(an)
a.args = normalize(a.args, REFUND)
print("openai    →", a)
print("anthropic →", b)

assert a == b
assert all("intent_fields" not in json.dumps(d) for d in exports.values())   # 內部欄位不外洩給模型
assert exports["openai"]["parameters"]["additionalProperties"] is False
assert exports["mcp"]["annotations"] == {"readOnlyHint": False, "destructiveHint": True}
assert to_anthropic(REFUND)["input_schema"]["required"] == ["order_id", "amount"]
```

```text

anthropic input_schema required=['order_id', 'amount']  其他={}
gemini    parameters   required=['order_id', 'amount']  其他={'type': 'function'}
mcp       inputSchema  required=['order_id', 'amount']  其他={'annotations': {'readOnlyHint': False, 'destructiveHint': True}}
openai 的 reason： ['string', 'null'] ['damaged', 'late', 'other', None]
openai    → ToolCall(id='c1', name='refund_order', args={'order_id': 'B-1042', 'amount': 1200})
anthropic → ToolCall(id='c1', name='refund_order', args={'order_id': 'B-1042', 'amount': 1200})
```

前四行是四種匯出結果。最明顯的差異是 schema 放在不同的欄位：OpenAI 與 Gemini 叫 `parameters`，Anthropic 叫 `input_schema`，MCP 叫 `inputSchema`。比較細的差異在 OpenAI 那一行：`required` 多了選填的 `reason`，並帶著 `strict: True`。這是 strict 模式的常見要求：所有欄位都要列在 `required`，選填欄位改成可以為 null。第五行顯示 `reason` 的型別變成 `['string', 'null']`，而且 enum 裡多了 `None`；如果忘了補，模型依規則填入的 null 會被 enum 擋下，這是手寫 adapter 時很容易漏掉的細節。MCP 那一行多了 annotations，由副作用分級推導出 `readOnlyHint` 與 `destructiveHint`；注意它們只是給 host 的提示，真正的核准仍由青鳥的政策決定。

最後兩行是反方向：同一個退款意圖，OpenAI 回傳 `function_call` item，`arguments` 是 JSON 字串，而且依 strict 規則對選填欄位填了 null；Anthropic 回傳 `tool_use` block，`input` 是物件、沒有 `reason`。經過 importer 與 `normalize()` 之後，兩者變成一模一樣的 `ToolCall`，業務程式完全不需要知道它來自哪一家。assert 還鎖住一件事：`intent_fields` 不會出現在任何匯出結果裡，因為 idempotency key 由 harness 推導，不能讓模型看見或填寫。這正是 adapter 的價值：格式差異被關在一個檔案裡，換供應商時只改這個檔案。

### 第三段：契約測試，抓出搬家時改變的業務規則

第三段重現 Iris 的 POC 漏洞。`VendorAgent` 模擬一個第三方框架：它的歷史是 item 清單、tool call 的參數是 JSON 字串、每個 tool 有自己的 `needs_approval` 旗標。adapter 負責把青鳥的 `ToolSpec` 與 approval 政策翻譯成這個框架的設定。契約測試用同一份劇本，在 `loom` 原生 runtime 與兩個版本的 adapter 上執行，比較執行序列、核准紀錄與最終回覆。

```python
from __future__ import annotations

import json
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"          # end_turn｜tool_use｜max_tokens
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    """依劇本回應的假模型。劇本的每一步是 ModelResponse，或「收到 messages 後回傳 ModelResponse」的函式。"""

    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    """劇本小工具：產生一個「呼叫 name 工具」的回應。"""
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    """劇本小工具：產生一個「直接回答並結束」的回應。"""
    return ModelResponse(text=text)


# ── 青鳥擁有的部分：中立的 tool 定義與 approval 政策 ──────────────────
@dataclass
class ToolSpec:
    name: str
    fn: Callable[..., Any]
    side_effect: str | None = None             # 未標註一律當 destructive（第 5 章）


def needs_approval(spec: ToolSpec) -> bool:
    return spec.side_effect != "read"          # 客服 agent 是 L3：每個寫入動作都要人核准


@dataclass
class Record:
    executed: list[str] = field(default_factory=list)
    approvals: list[str] = field(default_factory=list)
    output: str = ""


TOOLS = [
    ToolSpec("get_order", lambda order_id: {"order_id": order_id, "plan": "月訂"}, "read"),
    ToolSpec("cancel_subscription", lambda order_id: "已取消"),           # 忘了標註 side_effect
    ToolSpec("refund_order", lambda order_id, amount: "已退款", "destructive"),
]


# ── runtime 1：loom 原生 loop ─────────────────────────────────────────
def run_loom(model, user_input: str, approve: Callable[[ToolCall], bool]) -> Record:
    rec, specs = Record(), {t.name: t for t in TOOLS}
    messages: list[dict] = [{"role": "user", "content": user_input}]
    for _ in range(8):
        resp = model.complete(messages)
        messages.append({"role": "assistant", "content": resp.text, "tool_calls": [vars(tc) for tc in resp.tool_calls]})
        if not resp.tool_calls:
            rec.output = resp.text
            return rec
        for tc in resp.tool_calls:
            spec = specs[tc.name]
            if needs_approval(spec):
                rec.approvals.append(tc.name)
                if not approve(tc):
                    messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name, "content": "客服拒絕此動作"})
                    continue
            rec.executed.append(tc.name)
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name,
                             "content": json.dumps(spec.fn(**tc.args), ensure_ascii=False)})
    return rec


# ── runtime 2：模擬某個第三方框架。它有自己的 tool 格式與 needs_approval 旗標 ──
class VendorAgent:
    """第三方框架的內部長相：歷史是 item 清單，tool call 的 arguments 是 JSON 字串。"""

    def __init__(self, tools: list[dict]):
        self.tools = {t["name"]: t for t in tools}

    def run(self, model, user_input: str, on_approval: Callable[[dict], bool]) -> tuple[list[str], str]:
        items: list[dict] = [{"type": "message", "role": "user", "content": user_input}]
        executed = []
        for _ in range(8):
            resp = model.complete(items)
            if not resp.tool_calls:
                return executed, resp.text
            for tc in resp.tool_calls:
                item = {"type": "function_call", "call_id": tc.id, "name": tc.name, "arguments": json.dumps(tc.args)}
                items.append(item)
                tool = self.tools[item["name"]]
                if tool["needs_approval"] and not on_approval(item):
                    items.append({"type": "function_call_output", "call_id": tc.id, "output": "rejected"})
                    continue
                executed.append(item["name"])
                out = tool["handler"](**json.loads(item["arguments"]))
                items.append({"type": "function_call_output", "call_id": tc.id, "output": json.dumps(out)})
        return executed, ""


def make_vendor_runner(approval_rule: Callable[[ToolSpec], bool]):
    """adapter：把青鳥的 ToolSpec 與政策翻譯成第三方框架的設定。所有框架相依都只在這裡。"""
    def run(model, user_input: str, approve: Callable[[ToolCall], bool]) -> Record:
        rec = Record()

        def on_approval(item: dict) -> bool:
            rec.approvals.append(item["name"])
            return approve(ToolCall(item["call_id"], item["name"], json.loads(item["arguments"])))

        vendor_tools = [{"name": t.name, "handler": t.fn, "needs_approval": approval_rule(t)} for t in TOOLS]
        rec.executed, rec.output = VendorAgent(vendor_tools).run(model, user_input, on_approval)
        return rec
    return run


naive_rule = lambda t: t.side_effect == "destructive"     # 看起來合理，其實漏了未標註與 write


# ── 契約測試：同一份劇本，在每個 runtime 上的可觀察行為必須一致 ─────────
def script() -> ScriptedModel:
    return ScriptedModel([
        call("get_order", "c1", order_id="B-2077"),
        call("cancel_subscription", "c2", order_id="B-2077"),
        call("refund_order", "c3", order_id="B-2077", amount=299),
        say("已取消月訂並退款 299 元。"),
    ])


def contract(name: str, runner) -> list[str]:
    ref = run_loom(script(), "取消訂閱並退款", approve=lambda tc: True)
    got = runner(script(), "取消訂閱並退款", approve=lambda tc: True)
    problems = []
    if got.executed != ref.executed:
        problems.append(f"執行序列不同：{got.executed}")
    for tool in got.executed:
        if needs_approval({t.name: t for t in TOOLS}[tool]) and tool not in got.approvals:
            problems.append(f"{tool} 未經核准就執行")
    if got.output != ref.output:
        problems.append("最終回覆不同")
    print(f"{name:<14} executed={got.executed}")
    print(f"{'':<14} approvals={got.approvals}  →  {'PASS' if not problems else 'FAIL：' + '；'.join(problems)}")
    return problems


assert contract("loom", run_loom) == []
assert contract("vendor(naive)", make_vendor_runner(naive_rule)) == ["cancel_subscription 未經核准就執行"]
assert contract("vendor(fixed)", make_vendor_runner(needs_approval)) == []
```

```text
loom           executed=['get_order', 'cancel_subscription', 'refund_order']
               approvals=['cancel_subscription', 'refund_order']  →  PASS
vendor(naive)  executed=['get_order', 'cancel_subscription', 'refund_order']
               approvals=['refund_order']  →  FAIL：cancel_subscription 未經核准就執行
vendor(fixed)  executed=['get_order', 'cancel_subscription', 'refund_order']
               approvals=['cancel_subscription', 'refund_order']  →  PASS
```

第一組兩行是基準：`loom` 原生 runtime 執行了三個 tool，其中 `cancel_subscription` 與 `refund_order` 都先要求核准，因為客服 agent 是 L3，每個寫入動作都要人核准，而未標註的 `cancel_subscription` 依全書規則被當成 destructive。第二組是 naive adapter：執行序列與最終回覆都一樣，如果只看 happy path 的輸出，你會以為遷移成功了；但核准紀錄只有 `refund_order`，契約測試回報「cancel_subscription 未經核准就執行」。原因就在 `naive_rule` 那一行：`t.side_effect == "destructive"` 看起來合理，卻把未標註與 write 都當成不需要核准。第三組改用青鳥自己的 `needs_approval` 政策函式，三項契約全部通過。

這段程式的教訓有兩個。第一，adapter 不應該重新詮釋業務規則，而是直接呼叫青鳥擁有的政策函式；fixed 版本與 naive 版本的差別，就是「翻譯格式」與「重寫規則」的差別。第二，契約要比對「可觀察的行為」，而不只是最終輸出：這個漏洞的最終回覆完全正確，只有核准紀錄露出了破綻。實務上，契約測試的劇本要涵蓋每一種副作用等級、每一種停止條件，以及至少一個核准被拒絕的情境；每次升級框架版本或換 runtime，都先跑一遍。

## 26.12 實務應用

選型的方法在不同產業的結論可能完全不同，以下四個情境說明本章的維度與流程怎麼落地。

**情境一：新創 SaaS 的客服 agent，兩個月內要上線**。團隊三位工程師，沒有專職 SRE，合規要求是一般的個資保護。走 26.8 節的流程：沒有不可妥協的資料駐留限制（但要確認服務的資料保留條款）；loop 不是差異化；不需要檔案系統；退款需要人工核准但流程不複雜。合理的選擇是輕量 code-first SDK，或者營運人力真的不足時用託管 harness。要特別投資的是 tool 設計（第 5 章）與 eval（第 27 章），因為它們不會隨框架改變。即使用了託管服務，也要從第一天就把 tool 定義寫成中立格式、把對話紀錄同步一份到自己的資料庫：前者讓你換得掉，後者讓你能做 eval 與事故調查。

**情境二：金融或醫療業的內部 agent**。資料不能離開指定區域、需要完整稽核紀錄、所有寫入動作都要可追溯的核准。流程圖第 (1) 步就會淘汰一批選項：不支援 ZDR、不能指定區域或無法接上私有網路的託管服務。常見的組合是自託管的 graph 框架或 typed workflow 框架，搭配 durable 引擎與企業既有的 identity 系統；若使用雲端平台，傾向只用平台積木（runtime、identity、gateway），而不用託管 harness。這類組織最該投資的是 trace 的開放格式與 PII 遮蔽（第 29 章）、approval 稽核（第 21、33 章）。主要雲端廠商的託管平台都把私有網路、客戶自管金鑰、資料駐留列為賣點，具體支援範圍要逐項確認。

**情境三：把 coding agent 做成產品的公司**。這時 harness 就是產品的差異化：context 策略、tool 設計、sandbox 啟動速度、模型路由都是競爭力。流程圖第 (2) 步會導向自建核心 harness。公開資料中，主流 coding agent 多半有自己的 harness：OpenAI 的 Codex CLI 以 Rust 實作並開源，Google 的 Gemini CLI 也開源，GitHub 的 Copilot coding agent 在 GitHub Actions 的臨時環境中執行。法律 AI 公司 Harvey 在 2026 年的公開文章中描述自建 cloud agent runtime，把各家 harness 在 tool 格式、停止條件、串流與失敗模式上的差異抽象掉，並說明採用多模型的原因包括客戶的利益衝突限制與避免單一供應商風險。反過來，內部使用的 coding agent（例如青鳥的）不必自建，用完整的 harness SDK 就好。

**情境四：TypeScript 全端團隊在 SaaS 內嵌 agent**。團隊的產品是 Next.js 應用，沒有 Python 服務。生態維度會主導選擇：TypeScript 生態中有 Mastra 這類 all-in-one 框架、Vercel AI SDK 這類較輕量的工具組，以及多數主流 SDK 的 TS 版本。要注意的是，TS 框架常與前端串流深度整合，第 15 章的 AG-UI 這類事件協定可以把前端與 agent backend 解耦，讓將來換後端框架時前端不必重寫。這是 adapter 思維在前端邊界的應用。

| 情境 | 決定性的維度 | 常見選擇 | 一定要自己擁有的部分 |
|---|---|---|---|
| 新創客服 agent | 上線速度、營運人力 | code-first SDK 或託管 harness | 中立 tool 定義、對話紀錄副本、eval |
| 金融／醫療內部 agent | 部署與合規、HITL、可觀測性 | 自託管 graph／workflow 框架＋durable 引擎；平台積木 | trace 格式、approval 稽核、資料分類 |
| coding agent 產品 | harness 是差異化 | 自建核心 harness | 幾乎全部 |
| TS 全端內嵌 agent | 生態（語言） | TS all-in-one 框架或輕量 TS SDK | tool 定義、前端事件協定邊界 |

這張表的最後一欄在四個情境中都不是空的，這正是本章的核心主張。不論買多少，總有一部分必須自己擁有；而且越是把 runtime 外包，這部分越要做得紮實，因為它是你唯一能帶走的東西。

## 26.13 設計檢查清單

做選型決策或審查別人的選型報告時，逐項回答下面的問題。

1. 這次決策針對的是哪一個 agent？要外包的是技術堆疊的哪幾層（harness、編排、runtime、平台服務）？
2. 不可妥協的限制（資料駐留、ZDR、地端、語言、模型）是否列成 gate，而不是混在加權分數裡？
3. 九個維度的權重是否由產品、工程、資安、SRE 共同寫下，並記錄理由？
4. POC 是否包含不愉快的路徑：tool 例外、核准等待數小時、在有副作用的 tool 前後殺 process？
5. 未標註副作用等級的 tool，在候選框架中的預設行為是什麼？是否與自家政策一致？
6. session 與 trace 能否匯出成自家擁有的格式？是否實際匯出過一次並還原？
7. 業務程式中有多少處直接 import 框架？是否有 lint 或 CI 規則阻止新的洩漏？
8. tool 定義、approval 政策、prompts、eval set 是否以不依賴框架的形式存在？
9. 是否有一組契約測試，能在升級框架版本或更換 runtime 時驗證可觀察行為不變？
10. 遷移計畫是否有 shadow 與 canary 階段，且切回舊 runtime 只需要改一個設定值？
11. TCO 是否包含升級、繞過框架限制與將來遷移的成本，而不只是授權費或用量費？
12. 候選框架的維護健康度（發版節奏、breaking change 頻率、主要維護者）是否列入評估？
13. 是否設定了重新檢視這個決策的時間點（例如一季後）與觸發條件（例如合規要求改變、成功率下降）？

## 26.14 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 搬到新框架後，某個寫入動作沒有跳出核准 | 新框架對未標註或 write 等級的 tool 有不同預設值 | 用契約測試比對新舊 runtime 的核准紀錄 | adapter 直接呼叫自家的 approval 政策函式；所有 tool 補上副作用分級 |
| 選型會議反覆爭論、沒有結論 | 每個人心中的權重不同，卻直接爭論產品 | 請每位與會者各自寫下九個維度的權重，比較差異 | 先對權重達成共識，再看分數；硬性限制獨立成 gate |
| 框架升級後 agent 成功率下降，但沒有任何錯誤 | 行為 lock-in：prompt 或 eval 依賴舊版的預設 compaction、重試或回填格式 | 固定模型與 prompt，只換框架版本跑同一組 eval | 把依賴的預設值改成顯式設定；升級前先跑契約測試與 eval |
| 想換託管服務，卻發現歷史 session 帶不走 | 狀態只存在廠商端，沒有自家副本 | 嘗試匯出一週的 session 並在自家系統還原 | 從現在起同步寫一份自家格式的 session log；舊 session 讓其自然結束 |
| 事故時無法判斷是模型、框架還是 tool 的問題 | trace 只在廠商儀表板，看不到送給模型的完整 context | 拿一次失敗的 run，計時從症狀找到出錯步驟 | 匯出開放格式的 trace；在 adapter 層記錄送出與收到的原始內容（遮蔽 PII 後） |
| 換模型供應商時，tool call 解析失敗或多輪對話壞掉 | adapter 沒處理格式差異（JSON 字串參數、strict 的 null）或丟掉了不透明的推理欄位 | 對每家寫往返轉換的單元測試 | 用 26.11 節的 exporter／importer 模式，並保留 provider 的不透明欄位（第 25 章） |
| POC 很順，上線一個月後卡在品質天花板 | 高階框架的抽象擋住了你需要調整的地方 | 列出想做但做不到的改動，以及繞路的成本 | 往光譜左邊移一層：保留 tool 與 eval，把 loop 或編排換成更低階的方案 |

## 本章重點整理

- 選型的第一個問題不是「哪個框架最好」，而是「技術堆疊的哪一層要外包」：harness、編排、runtime、平台服務可以分開決定。
- tools 與 prompts 這一層是業務本身，無論選什麼都必須以不依賴框架的形式自己擁有。
- 抽象層級是一條光譜，越低階控制力越高、工程量越大，越高階上手越快、透明度與彈性越低；沒有絕對的好壞。
- 九個選型維度分三組：控制（抽象、狀態、multi-agent）、可靠性（HITL、durable、可觀測性）、營運與長期（部署、生態、lock-in）。
- POC 一定要包含不愉快的路徑，尤其是核准等待與在有副作用的 tool 前後殺 process，否則量到的只是上手速度。
- 理解每個框架的設計哲學比記住 API 有用：code-first、harness-first、event log、state machine、角色扮演、protocol-first、型別化函式、prompt 編譯、相信模型。
- 託管服務分成託管 harness（連 loop 一起外包）與託管平台積木（只外包 runtime、identity、gateway 等），兩者可以混用。
- 託管只轉移基礎設施的責任；approval 政策的內容、成功標準、資料是否該送進模型，仍然是你的責任。
- build vs buy 要針對單一 agent 決策，先以硬性限制淘汰，再問 harness 是否為差異化，最後依任務形態選擇光譜位置。
- TCO 要包含升級、繞過框架限制與將來遷移的隱性成本，並把決策寫成可以定期重新檢視的紀錄。
- lock-in 分成 API、狀態、行為、營運、模型五類，其中行為 lock-in 最隱蔽，只能靠契約測試發現。
- adapter 要保持薄：只翻譯格式與呼叫方式，業務判斷一律呼叫自家擁有的政策函式。
- 遷移用 strangler fig 模式分階段進行：盤點、包 adapter、契約測試、shadow、canary、切換，每一步都能回頭。
- 加權決策矩陣的價值不在算出答案，而在把權重這個隱含假設攤開，並用敏感度分析找出真正需要人來判斷的地方。

## 延伸問答

> [!question]- Q1. 「framework」「完整 harness SDK」「託管 harness」「託管平台積木」這四者的差別是什麼？選錯類別會有什麼後果？
> 判斷的兩個軸是「控制流在誰手上」與「程式跑在誰的機器上」。framework 是它呼叫你：你註冊 agent、tool、節點，由框架的 runtime 在你的機器上決定執行順序。完整 harness SDK 也跑在你的機器上，但它附帶整套現成的 loop、內建 tools、權限與 context 管理，你主要是在設定它，而不是組裝它。託管 harness 把 loop 也搬到廠商的雲端，你只送設定與任務。託管平台積木則不跑你的 loop，只提供 runtime、identity、gateway、memory 等可以分開使用的服務。
>
> 選錯類別的典型後果有兩種。一是把需要精確流程控制的退款 agent 放進託管 harness，結果核准時機、compaction 時機都無法照業務需求調整，只能繞路。二是把只需要部署與 identity 代管的需求，誤解成「要換掉整個框架」，於是做了一次不必要的大遷移。先用 26.2 節的分層圖確認要外包的是哪一層，類別自然就清楚了。

> [!question]- Q2. 青鳥的客服 agent 在 graph 框架與 code-first SDK 之間，你會怎麼選？依據是什麼？
> 先看任務形態。客服 agent 的退款流程有明確的狀態：查訂單、判斷是否出貨、建立退款或退貨單、等待核准、執行、通知。其中「等待核准」可能持續數小時，而且恢復時不能重做已經完成的步驟。這些需求落在狀態管理、HITL、durable 三個維度，graph 框架的 checkpoint 與 interrupt 原語正好對應；code-first SDK 也能透過序列化 run state 做到暫停與恢復，但流程越長，狀態越容易散落在程式各處。
>
> 再看反向的考量。如果客服 agent 大多數對話只是查詢、只有少數需要退款，那麼 graph 帶來的建模成本可能不划算；code-first SDK 搭配一個獨立的退款 workflow（第 18 章）也是合理的設計。最後用 POC 決定：兩個候選都跑同一組劇本，包括「核准前使用者離開三小時」與「退款 tool 執行後立刻殺 process」，看哪個方案在不寫額外基礎設施的情況下通過。分數接近時，像 26.11 節的結果一樣，就要由「將來換不換得掉」這類價值判斷決定。

> [!question]- Q3. 研究團隊很喜歡某個託管 harness，但它目前不支援 ZDR，而 research agent 會讀取內部營運數據。你會怎麼處理？
> 第一步是釐清資料分類，而不是直接說可以或不可以。research agent 讀的營運數據是否包含個資？是否有合約限制不能交給第三方保存？如果是去識別化的彙總數據，而公司的資料政策允許在供應商端保留一段時間，那麼不支援 ZDR 也許可以接受，但要由資安與法務書面確認，並寫進決策紀錄。
>
> 如果資料不允許被保留，就把它當成 26.8 節流程圖第 (1) 步的 gate，這個託管服務對 research agent 直接出局，分數再高也沒用。這時可以退一步看研究團隊真正喜歡它什麼：通常是 session 持久化、長時間任務不怕中斷、sandbox 現成。這些能力可以用自託管的 graph 框架加 durable 引擎，或雲端平台提供的、可以指定區域與資料政策的 runtime 積木取得。另一個常見折衷是資料分流：讓託管 harness 只處理不含敏感資料的任務，敏感任務走自託管路徑，兩者共用同一份 tool 定義與 eval。

> [!question]- Q4. 面試題：「如果請你替公司的第一個 agent 選框架，你會怎麼做？」請說明你的流程。
> 我會先問清楚三件事：這個 agent 要做什麼（任務形態、互動是同步還是非同步）、有哪些不可妥協的限制（資料駐留、合規、語言、指定模型），以及 harness 本身是不是產品的差異化。這三題決定了要外包哪一層，以及哪些選項直接出局。接著和產品、資安、SRE 一起把九個維度的權重寫下來，因為選型爭議多半來自權重不同。
>
> 然後挑兩到三個候選方案做 POC，用同一組劇本驗證，劇本一定包含 tool 例外、長時間核准、殺 process、trace 匯出這些不愉快的路徑。用加權矩陣整理結果並做敏感度分析，差距小時把關鍵的價值判斷交給決策者。最後，不論選了什麼，都會要求三件事：tool 定義與 approval 政策以中立格式存在、session 與 trace 有自家副本、有一組契約測試。並約定一季後依實際營運數據重新檢視。面試官通常想聽到的不是某個框架名稱，而是「你怎麼讓這個決定可以被驗證、也可以被推翻」。

> [!question]- Q5. 程式找錯：下面這個 OpenAI strict 模式的 exporter 有兩個問題，請指出並說明後果。
> ```python
> def to_openai(t):
>     s = t.json_schema()
>     s["required"] = list(s["properties"])
>     s["additionalProperties"] = False
>     s["properties"]["idempotency_key"] = {"type": "string"}
>     return {"type": "function", "name": t.name, "parameters": s, "strict": True}
> ```
> 第一個問題是選填欄位只被加進 `required`，卻沒有改成可以為 null。在 strict 模式下，所有欄位都必須出現，模型對原本選填的 `reason` 就被迫填一個非 null 的值，可能隨便選一個 enum 值，等於替使用者捏造了退款原因。正確做法是像 26.11 節的 `strictify()` 那樣把型別改成 `[type, "null"]`，有 enum 時也要把 `None` 加進 enum，並在 importer 端把 null 拿掉。
>
> 第二個問題更嚴重：把 `idempotency_key` 加進模型看得到的 schema。依第 5 章的規則，idempotency key 由 harness 依業務意圖推導，不能讓模型填。讓模型填的話，它可能每次重試都產生新的 key，去重完全失效；也可能在不同的退款上重用同一個 key，讓第二筆合法退款被當成重複而丟棄。而且這行程式還在 `required` 計算之後才加，所以 `idempotency_key` 不在 `required` 裡，又違反了 strict 模式的規則，請求可能直接被拒絕。

> [!question]- Q6. 估算題：一個營運 agent 預估每月 2 萬次 session。自建方案要 2 位工程師花 3 個月建置、之後每月約 0.5 人月維護；託管方案每次 session 的平台費用（不含模型）假設為 0.05 美元。工程師的全載成本假設每人月 1.5 萬美元。兩年的 TCO 怎麼比？還要考慮什麼？
> 先算自建：建置 2 人 × 3 個月 × 1.5 萬 ＝ 9 萬美元；維護 0.5 人月 × 1.5 萬 × 21 個月（建置完後剩下的時間）＝ 15.75 萬美元，兩年合計約 24.75 萬美元，還沒算自建 sandbox 與儲存的基礎設施費用。託管：2 萬次 × 0.05 美元 × 24 個月 ＝ 2.4 萬美元，加上整合工作，假設 1 位工程師 1 個月 ＝ 1.5 萬美元，合計約 3.9 萬美元。兩種方案的模型費用大致相同，所以不列入比較。在這組假設下，託管便宜很多；即使 session 量成長五倍，託管的平台費用也才約 12 萬美元。
>
> 但這個比較漏掉了幾項不容易量化的東西。第一，託管方案的隱性成本：服務仍在 beta 時的功能與價格變動、狀態 lock-in 讓將來遷移要付出的成本、事故時透明度不足而多花的調查時間。第二，自建方案的附加價值：如果 harness 是差異化，那 24.75 萬美元是在累積核心能力，而不是單純的成本。第三，限制條件：如果合規不允許託管，比較本身就不成立。所以估算的作用是確認數量級，例如「在這組假設下託管便宜約六倍」，再把無法量化的項目列在旁邊，交給決策者判斷。這裡的單價都是假設，實際數字要查當時的價目表。

> [!question]- Q7. 你們用的框架仍是 0.x，幾乎每個 minor 版本都有 breaking change。要怎麼管理升級，才不會每次都提心吊膽？
> 第一是把升級變成例行工作，而不是事件。鎖定確切的版本號，不使用浮動範圍；固定節奏（例如每兩週或每月）評估一次升級，閱讀 release notes 中的 breaking change 段落。一次跳很多版的升級最痛苦，因為多個 breaking change 交互作用，很難判斷是哪一個造成問題。
>
> 第二是讓升級有安全網。adapter 把框架相依集中在少數檔案，breaking change 的影響範圍就只在這些檔案；契約測試驗證可觀察行為不變，抓出預設值改變這類行為 lock-in；eval 驗證品質沒有下降。升級的 PR 要同時附上契約測試與 eval 的結果。第三是在決策層面承認這個成本：0.x 與快速發版代表持續的升級人力，應該寫進 TCO。如果升級成本持續高過框架帶來的價值，就是重新檢視選型的訊號，而 adapter 讓這個重新檢視變得可行。

> [!question]- Q8. 既然有這麼多成熟框架與託管服務，青鳥為什麼還要維護自己的 loom？這是不是重造輪子？
> 要分清楚 `loom` 的哪些部分是「輪子」、哪些不是。`loom` 最有價值的部分不是 loop 本身，而是契約：中立的 tool 定義格式、副作用分級與 approval 政策、session log 與 trace 的 schema、eval 格式。這些是青鳥的業務規則與營運知識，沒有任何框架能提供，而且必須跨越框架存在，否則每次換框架都要重寫。這部分不是重造輪子，而是 12-Factor Agents 所說的「own your prompts、own your context window、own your control flow」。
>
> loop、durable、sandbox 這些 runtime 部分，則確實可能是重造輪子。所以青鳥的決定是：客服 agent 的 loop 留在 `loom`，因為它簡單、與業務規則緊密，而且分數與外部框架平手；coding agent 的 runtime 用現成的 harness SDK；research agent 用 graph 框架做 POC。它們都放在 `loom` 的 adapter 後面。這樣 `loom` 的定位就從「自己做一切的框架」變成「青鳥的契約層，加上一個夠用的原生 runtime」。還有一個長期的理由：harness 是有保存期限的，每個元件都編碼了某一代模型的弱點假設，模型變強後可能需要拆掉。自己擁有契約層，才能在換 runtime、拆元件時不動到業務規則。
