# 第 13 章　大量工具與能力擴充

> [!abstract] 本章地圖
> **核心問題**：當 agent 的能力從 6 個 tools 長到 60 個、甚至上千個，怎麼讓模型在需要時找得到、用得對，又不必每一輪都為用不到的能力付 token？
>
> **你會學到**：
> - 說清楚 tool 數量上升時，成本、選擇正確率與 prompt cache 三方面各自怎麼壞掉
> - 設計 tool registry，把「系統有哪些能力」和「這一輪模型看得到哪些能力」分開管理
> - 實作 tool search 與 deferred loading：只載入被搜尋到的 tool 定義，且不破壞 cache 前綴
> - 用 Skills 的三層漸進揭露管理程序知識：先只放名稱與描述，需要時才讀完整內容
> - 實作 code-as-action：讓模型寫一段受限的 Python 一次呼叫多個 tool，並量測它和多次 tool call 在 token 與步數上的差異
> - 判斷什麼時候該用 code 取代多次 tool call，什麼時候不該，並知道受限執行器為什麼不是安全 sandbox
>
> **前置知識**：第 4 章（agent loop、dispatch、token 預算）、第 5 章（tool 的命名、描述與粒度）、第 9 章（context 分層與 cache-friendly 版面）、第 11 章（BM25 與檢索品質量測）、第 12 章（procedural memory）

## 13.1 故事：從 6 個工具到 59 個工具

客服 agent 上線三個月後，阿哲帶來一個好消息和一個大需求。好消息是客服的轉真人比例降了一半；大需求是：「店家也想要一個營運助理。查庫存、開優惠券、看報表、叫物流取件，全部用講的。」青鳥科技內部有七個團隊各自維護 API，Iris 花了兩週把它們全部包成 tools：五家物流商各有查貨態、預約取件、印標籤三個操作，再加上庫存、優惠券、會員、報表、商品、退款、商店設定，一共 59 個 tools。第 4 章的 `loom` v0.1 完全不用改，把清單丟進去就能跑。

內部試用的第一週，問題一個接一個冒出來。第一個是成本：店家只問「B-1042 到哪了」，每一次模型呼叫也要帶著 59 份 tool 定義，光是這些說明書就佔掉 input 的大半。第二個是選錯工具：店家說「新竹物流的包裹」，模型卻呼叫了黑貓的 `tcat_track`；店家要「開一張滿千折百的券」，模型呼叫了 `coupon_disable`。名稱和描述相近的 tools 一多，模型就開始在它們之間猜。

Iris 想到一個直覺的解法：每一輪先用關鍵字比對使用者的話，只把最相關的 10 個 tools 送給模型。選錯的情況少了，帳單卻沒有降多少，追查之後發現 prompt cache 的命中率從九成多掉到不到兩成：每一輪的 tool 清單都不一樣，快取的前綴每一輪都被打斷。更糟的是，歷史訊息裡留著上一輪呼叫過的 `hct_track`，這一輪的清單裡卻沒有它，模型開始在回覆裡提到「我剛剛用過的那個工具」卻叫不出來。

同一週還有兩件事。營運團隊寫了一份三千字的「促銷活動設定 SOP」，要求放進 system prompt，「因為模型老是忘記滿額門檻要用未稅金額算」；可是一百則對話裡只有三則和促銷有關，其餘九十七則都在為它付錢。另一位店家問：「9 月出貨、超過 7 天還沒送達的有幾筆？」agent 先列出 40 張訂單，再一張一張查貨態，模型被呼叫了 42 次，跑了將近三分鐘，最後那次呼叫的 input 已經塞滿 40 份貨態。

老陳看完 trace，在白板上寫了三行：「能力要有目錄，用到才拿出來；做事的方法也一樣；需要迴圈的事，讓程式去跑迴圈。」這三行就是本章的三個機制：tool registry 加上 tool search、Skills 的漸進揭露，以及 code-as-action。Maya 在旁邊補了一句：「讓模型寫程式來跑可以，但在第 17 章的 sandbox 做好之前，那個執行器不准碰 production 資料。」這句話也會貫穿本章。

## 13.2 工具變多時，壞掉的是什麼

先把問題拆清楚。tool 定義是 context 的一部分，第 4 章的版面圖裡，它和 system prompt 一起放在最前面的穩定前綴，每一輪都會送出。所以 tool 數量的成本不是「一次性」的，而是「每一輪、每一個 session 都付」。一份寫得好的 tool 定義（名稱、說明、參數、例子）通常是幾百 tokens；60 個 tools 就是數萬 tokens，在一個 10 步的任務裡要重送 10 次。

```text
 營運助理每一輪送給模型的內容（59 個 tools 全部載入）

 ┌─ system（約 600 tokens）──────────────────────────────┐
 │ 你是青鳥科技的營運助理……                              │
 ├─ tools（59 份定義，約數萬 tokens）────────────────────┤
 │ get_order  search_orders                              │ ◄ 真正常用的只有少數
 │ tcat_track  tcat_pickup  tcat_label                   │
 │ hct_track   hct_pickup   hct_label   ……（物流 15 個） │ ◄ 名稱相近，容易選錯
 │ inventory_* 6 個  coupon_* 6 個  member_* 6 個        │
 │ report_* 6 個  product_* 6 個  refund_* 6 個  store_* │
 ├─ messages ────────────────────────────────────────────┤
 │ [0] user 「我的新竹物流包裹 HC-5521 到哪了？」         │ ◄ 真正和任務有關的
 │ ……                                                    │   內容反而是最小的一塊
 └───────────────────────────────────────────────────────┘
```

這張版面圖顯示了三種成本。第一是 **token 成本與延遲**：tools 區塊是整個請求裡最大的一塊，就算有 prompt caching 打折，第一次寫入快取與每次讀取仍要計費，而且越長的輸入，模型產生第一個 token 前要處理的內容就越多。第二是 **選擇正確率**：模型要在 59 個選項裡挑一個，相近的名稱（五個 `*_track`）與重疊的描述（「建立折扣碼」與「停用優惠券」都有「優惠券」三個字）會稀釋注意力。第 9 章談過的 **context rot**（context 越長，模型對其中個別資訊的掌握越差）在這裡具體化成「選錯 tool」。第三是 **可維護性**：七個團隊各自加 tools，沒有人知道總數已經多到影響行為，直到正確率下滑。

| tool 數量 | 典型症狀 | 主要原因 | 常見對策 |
|---|---|---|---|
| 個位數 | 幾乎沒有選擇問題 | 選項少、差異明顯 | 全部載入，專心寫好描述（第 5 章） |
| 十幾到三十個 | 偶爾選錯相近的 tool | 命名與描述重疊 | 加命名空間、合併成 workflow 級 tool |
| 數十到上百個 | 成本明顯上升、選錯變常態 | 定義佔滿前綴、注意力被稀釋 | tool search 與 deferred loading |
| 上百到上千個（接很多 MCP server） | 定義放不進 context 或擠掉任務內容 | 生態系整合（第 14 章） | 只放目錄、按需載入，或改成 code API |
| 需要一次處理大量資料或多步串接 | 步數暴增、中間結果塞爆 context | 每個結果都要經過模型 | code-as-action |

表格的最後一列和前面幾列性質不同：它不是「tools 太多」，而是「呼叫太多次」。前四列的問題出在 tool 定義（說明書），最後一列的問題出在 tool 結果（觀察）。本章前半段處理說明書，後半段處理觀察。

> [!warning] 常見誤解
> 「現在的 context window 有幾十萬 tokens，放 100 個 tools 也才用掉一小部分。」context window 夠大只代表「放得下」，不代表「用得好」。選擇正確率會隨選項與干擾項增加而下降，成本與延遲也和輸入長度成正比。把 context 當成預算而不是容量（第 9 章），問題就從「放不放得下」變成「這些 tokens 值不值得」。

## 13.3 Tool registry：把「有哪些能力」和「這一輪看得到什麼」分開

Iris 的第一版裡，「系統有哪些 tools」和「送給模型的 tools 清單」是同一個 Python list。這個設計在 6 個 tools 時沒問題，到了 59 個就成為所有麻煩的根源：要動清單，就是在動系統的能力邊界；要讓模型少看一點，就得把能力拿掉。解法是引入一層 **tool registry**（工具註冊表）：一個集中記錄所有 tools 的目錄，每筆紀錄除了 schema 與實作，還有搜尋、權限與載入政策需要的 metadata（中介資料）。例如 `hct_track` 在 registry 裡除了參數 schema，還標著「領域：物流」「副作用：唯讀」「載入方式：deferred」「擁有者：物流整合組」。

```text
                     ┌──────────────── Tool Registry（全部 59 個）──────────────┐
  七個團隊註冊 ────► │ name、description、schema、fn                            │
  （或 MCP server，  │ tags、namespace、side_effect、always_loaded、owner、版本 │
    第 14 章）       └──────┬──────────────────────────────┬────────────────────┘
                            │ 曝光政策：常駐哪些？           │ 搜尋索引（BM25／embedding）
                            ▼                                ▼
                 ┌─ 本 session 的已載入集合 ─┐ ◄─────── tool_search(query) 命中
                 │ 常駐 2 個 ＋ tool_search  │          只追加、不重排
                 │ ＋ 搜尋到的（依序追加）    │
                 └────────────┬──────────────┘
                              │ 每一輪送出的 tools 參數
                              ▼
                            Model ──► tool_call ──► Dispatcher
                                                     │ 1. 名稱在 registry 嗎？
                                                     │ 2. 已載入嗎？沒有就提示先搜尋
                                                     │ 3. 權限與副作用政策（第 21、32 章）
                                                     ▼
                                                   執行 fn
```

這張架構圖由上往下讀。最上面是 registry，它是唯一的事實來源（single source of truth）：任何團隊新增 tool，都是在這裡註冊，而不是去改 agent 的程式。中間有兩條路：左邊的**曝光政策**決定哪些 tools 每一輪都常駐（例如查訂單），右邊的**搜尋索引**讓其他 tools 可以被找到。兩者匯合成「本 session 的已載入集合」，這才是每一輪真正送給模型的清單。最下面的 dispatcher 仍然對照完整的 registry 做檢查，而不是只看已載入集合：名稱存在但尚未載入的 tool，回填「請先用 tool_search 載入」；權限與副作用政策則不論載入與否都照常生效。

把 registry 獨立出來有三個好處。第一，載入政策可以調整而不改變能力邊界：把 `report_*` 從常駐改成 deferred，只是改一個欄位。第二，metadata 讓 harness 能做模型做不到的保證，例如 `side_effect` 為 write 或 destructive 的 tool，一律交給第 21 章的核准政策決定是否要人核准，也一律不開放從程式呼叫，不管它是怎麼被載入的。第三，registry 是治理的入口：哪些 tools 半年沒被呼叫、哪些描述太相近、哪個團隊加了一個參數多達二十個的 tool，都能從這裡統計出來。

| 欄位 | 用途 | 例子 | 誰會讀它 |
|---|---|---|---|
| name、namespace | 唯一識別，前綴讓相近的 tools 分群 | `hct_track`（`hct_` 代表新竹物流） | 模型、搜尋、dispatcher |
| description | 讓模型與搜尋判斷「什麼時候用」 | 「用新竹物流的物流單號查詢貨態與預計送達時間」 | 模型、搜尋 |
| parameters | 參數 schema，執行前驗證 | `{"tracking": string, required}` | 模型、dispatcher |
| tags | 補充同義詞與使用者的說法 | 「物流、貨態、包裹」 | 搜尋 |
| side_effect | read（唯讀）、write（可回復的寫入）、destructive（不可逆或對外）；未標註一律當 destructive（第 5 章） | `read` | dispatcher、核准政策 |
| always_loaded | 是否常駐在每一輪的清單 | 查訂單：是；印標籤：否 | 曝光政策 |
| code_callable | 能否在 code-as-action 中被程式呼叫；write 與 destructive 一律為否 | 查貨態：是；退款：否 | 執行器（13.6 節） |
| owner、version | 出事時找誰、描述改版追蹤 | 物流整合組、v3 | 人、評估（第 27 章） |

表中的命名空間值得多說一句。第 5 章談過 tool 名稱要清楚，在大量 tools 的情境裡還要加上一致的前綴，例如所有新竹物流的 tools 都以 `hct_` 開頭。前綴對模型是分群的線索，對搜尋是可以比對的關鍵字，對 harness 則是做政策的單位（「`store_` 開頭的全部需要店長權限」）。有些系統甚至只靠前綴就能做到「整組遮蔽」，13.4 節會談到。

## 13.4 Tool search 與 deferred loading：用到才載入

有了 registry，下一步是讓大多數 tools **延遲載入**（deferred loading）：它們登記在 registry 裡、可以被找到，但在被需要之前，完整定義不會出現在送給模型的 tools 清單中。模型怎麼知道有哪些 tools 可以找？靠一個常駐的 **tool search**（工具搜尋）tool：模型用自然語言描述想做的事，harness 在 registry 裡搜尋，把命中的 tools 加入已載入集合，下一輪模型就看得到它們的完整定義，可以正常呼叫。例如店家問新竹物流的包裹，模型先呼叫 `tool_search(query="新竹物流 包裹 貨態")`，下一輪清單裡就多了 `hct_track`。

```text
 店家             loom（harness）                     Model                 Registry
  │── HC-5521 到哪？──►│                                │                      │
  │                    │── 第 1 輪 tools=[常駐 2 個,     │                      │
  │                    │      tool_search] ────────────►│                      │
  │                    │◄─ tool_search("新竹物流 貨態") ─│                      │
  │                    │── search ─────────────────────────────────────────────►│
  │                    │◄──────────────── [hct_track, hct_label, hct_pickup] ───│
  │                    │ 已載入集合尾端追加 3 個                                 │
  │                    │ 回填：名稱＋一句描述                                    │
  │                    │── 第 2 輪 tools=[常駐 2 個, tool_search,               │
  │                    │      hct_track, hct_label, hct_pickup] ───►│            │
  │                    │◄──────────────── hct_track(HC-5521) ───────│            │
  │                    │ 執行、回填貨態                                          │
  │                    │── 第 3 輪（清單不變）───────────────────────►│            │
  │◄─ 預計明天送達 ────│◄──────────────────────────── end_turn ─────│            │
```

逐步看這張時序圖。第 1 輪，模型只看到兩個常駐 tools 與 `tool_search`，它判斷查訂單的 tool 不適用（使用者給的是物流單號），於是搜尋。harness 在 registry 裡找到三個新竹物流的 tools，把它們**追加到已載入集合的尾端**，並回填一則簡短的結果（名稱與一句描述），讓模型知道下一輪會有哪些新能力。第 2 輪，模型看到 `hct_track` 的完整定義，正常呼叫。第 3 輪的清單和第 2 輪完全相同，模型回答並結束。和全部載入相比，這個任務多了一步（搜尋本身），換來每一輪少送五十幾份定義。

這張圖最重要的細節是「只追加、不重排」。第 9 章說過，prompt cache 靠的是請求開頭的內容和上一次完全相同；Iris 失敗的「每輪動態過濾」之所以讓命中率崩盤，是因為清單每一輪都被重組，變動發生在前綴的中段，從那裡之後的所有內容都無法重用。deferred loading 則只在清單尾端加東西，前一輪的清單永遠是下一輪的前綴，之前快取的部分可以完整重用。本書把這條規則稱為**前綴不變式**（prefix invariant）：載入新 tool 時只追加到 tool 清單尾端，不重排、不刪除，前一輪的 tool 清單永遠是下一輪的開頭；後面章節提到「前綴不變式」，指的都是這條規則。有些模型 API 更進一步，把搜尋到的定義放在對話中的 tool 結果位置，而不是動 tools 參數，效果相同：既有的前綴不變。

```text
 一個 tool 在 session 中的狀態

   registered ──(曝光政策：常駐)──────────────────────────► loaded
       │                                                    ▲   │
       │(預設)                                               │   │ compaction 時
       ▼                                                    │   │ 可選擇卸載（第 10 章）
   deferred ──(tool_search 命中)──► discovered ──(下一輪)──┘   ▼
       ▲                                                     deferred
       │
       └── 直接呼叫未載入的 tool：不執行，回填「請先搜尋」，狀態不變
```

這個狀態機說明了 tool 在一次 session 中的生命週期。大多數 tools 從 deferred 開始；被搜尋命中後成為 discovered，下一輪起是 loaded，之後一直留著，不會因為「這一輪好像用不到」就移除，因為移除同樣會破壞前綴，而且歷史訊息裡可能還引用著它。唯一適合卸載的時機是 compaction（第 10 章）：既然整段歷史都要重寫、快取本來就會重建，可以順便把不再需要的定義清掉。圖底部的邊處理一個常見情況：模型憑記憶或歷史直接呼叫了一個尚未載入的 tool，harness 不應該默默執行（模型沒看過它的 schema，參數很可能是猜的），而是回填提示，讓模型先搜尋。

搜尋本身怎麼做？最簡單的是比對名稱與描述的關鍵字或正規表示式，適合 tools 命名規律、使用者也會講出 tool 名稱的開發者工具。其次是 BM25（第 11 章），對「描述裡有沒有出現使用者的用詞」很敏感，不需要模型、不需要向量資料庫，是很好的預設。再來是 embedding 語意搜尋，能處理「包裹到哪」對上「查詢貨態」這種用詞不同的情況，代價是要維護索引與模型。實務上常用 hybrid：BM25 加 embedding 再做 rerank。不論哪一種，**搜尋的召回率就是 agent 能力的上限**：搜不到的 tool，對模型而言就不存在。所以 tool search 一定要有自己的評估集，13.9 節會實際量 recall@3，並看到一個描述寫法如何讓它從 0.83 變成 1.00。

哪些 tools 應該常駐？原則是「幾乎每個 session 都會用到的少數幾個」，例如客服的查訂單。常駐太多，又回到原本的問題；常駐太少，每個任務都要先搜尋一次，多付一輪延遲。常見的做法是從 trace 統計各 tool 的使用率，把使用率最高、且最常出現在第一步的幾個設為常駐，其他全部 deferred。另外要注意，搜尋結果的回填只放名稱與一句描述，不要把完整定義也塞進 tool 結果；完整定義由下一輪的 tools 清單提供，避免同一份內容出現兩次。

| 策略 | 怎麼做 | cache 友善 | 選擇正確率 | 適用情境 | 主要風險 |
|---|---|---|---|---|---|
| 全部載入 | 所有定義每輪都送 | 是（清單固定） | tools 一多就下降 | 個位數到十幾個 tools | 成本隨數量線性上升 |
| 每輪動態過濾 | harness 依輸入挑子集 | 否（前綴每輪變動） | 視過濾品質 | 幾乎不建議 | cache 失效、歷史引用消失的 tool |
| tool search＋deferred | 模型主動搜尋，命中後追加 | 是（只追加） | 高，前提是搜尋召回率夠 | 數十到上千個 tools | 搜不到就用不到、多一輪延遲 |
| 遮蔽（masking） | 定義全部保留，在解碼時限制可選的 tool | 是 | 高 | 需要依狀態開關能力 | 需要模型服務支援，實作門檻高 |
| 分領域 sub-agent | 每個 sub-agent 只帶一個領域的 tools（第 20 章） | 是（各自固定） | 高 | 領域邊界清楚、任務可切分 | 跨領域任務要多次交接，成本倍增 |

表中的「遮蔽」值得補充。有些團隊主張「遮蔽，而不是移除」：tools 定義全部固定在前綴，靠狀態機在模型產生 tool 名稱時限制可選的範圍（一種 constrained decoding，第 7 章），並用一致的前綴（`browser_`、`shell_`）讓遮蔽可以整組進行。它和 tool search 不衝突：遮蔽解決「依狀態開關能力」，tool search 解決「定義太多放不下」。對多數自建 agent 而言，tool search 只需要 harness 層的程式，門檻低得多。

> [!warning] 常見誤解
> 「deferred 的 tool 模型看不到，所以比較安全。」不對。deferred loading 是 context 管理，不是權限控制。模型只要搜尋就能載入任何 registry 裡的 tool，被 prompt injection（第 31 章）操控的模型也一樣會搜尋。權限必須在 dispatcher 依使用者身分與副作用等級檢查；不該讓這個使用者用的 tool，根本不應該出現在這個使用者的 registry 視圖裡。

> [!note] 2026 現況
> 截至 2026 年 10 月，依各家公開文件與工程部落格：Anthropic 的 Tool Search Tool（2025-11 以 beta 推出）讓標記 `defer_loading: true` 的 tools 不放進初始 prompt，內建 regex 與 BM25 兩種搜尋，也可自訂（例如 embeddings），並可整個 MCP server 延遲載入；官方說明 deferred tools 不在初始前綴，因此不影響 prompt cache，並建議最常用的 3 到 5 個 tools 常駐。該文舉的例子是 5 個 MCP server、58 個 tools 約 55K tokens，改用搜尋後約 8.7K；內部 MCP eval 上，Claude Opus 4 從 49% 提升到 74%，Opus 4.5 從 79.5% 提升到 88.1%（廠商自報）。Claude Code 的 MCP tool 定義預設 deferred，只有 tool 名稱與 server instructions 佔 context。Cursor 在 2026 年 9 月公開表示，先前把 MCP tools 改為延遲載入，讓有使用 MCP 的 session 總 token 降低 46.9%，之後把使用率低於 20% 對話的內建 tools 也改為按需載入。OpenAI Codex 的開源程式碼中有 tool search 相關模組，AG2 也支援 tool search 加 deferred loading。Manus 在 2025 年的 context engineering 文章中提出「Mask, don't remove」。確切參數與限制請以各家官方文件為準。

## 13.5 Skills：程序知識的漸進揭露

tool search 解決了「能力的說明書太多」，但營運團隊那份三千字的促銷 SOP 是另一類東西：它不是一個可以呼叫的函式，而是「做某類事情的方法」，包括步驟、規則、注意事項，甚至輔助的腳本。第 12 章把這類知識稱為 **procedural memory**（程序性記憶，「怎麼做事」的記憶）。把它寫進 system prompt，每一輪都要付錢；做成 tool 又不對，因為它沒有要執行的動作。**Skill**（技能包）是為這類知識設計的格式：一個資料夾，裡面有一份 `SKILL.md`，開頭用 frontmatter（檔案最前面以 `---` 包起來的 YAML 中介資料）寫名稱與描述，正文寫流程，同一個資料夾還可以放參考文件與腳本。例如 `promo-setup/` 資料夾裡有 `SKILL.md`（流程）、`rules.md`（折抵規則）與 `checklist.md`（上線前檢查）。

Skills 的核心機制是 **progressive disclosure**（漸進揭露）：資訊分層，模型先只看到最上層，判斷需要時才往下讀。這和好的使用者介面設計同一個道理：設定頁面先列出分類，點進去才看到細項。

```text
 第 1 層：索引（永遠在 system prompt）            約數十 tokens × skill 數
 ┌────────────────────────────────────────────────────────────┐
 │ - promo-setup：設定滿額折抵、折扣碼等促銷活動時使用……       │
 │ - bulk-return：處理單一顧客一次退 5 件以上……               │
 │ - invoice-void：作廢或折讓電子發票時使用……  （共 9 個）     │
 └───────────────────────┬────────────────────────────────────┘
                         │ 模型判斷「雙 11 滿千折百」和 promo-setup 相關
                         ▼ load_skill("promo-setup")
 第 2 層：SKILL.md 本體（需要時才讀）              數百到數千 tokens
 ┌────────────────────────────────────────────────────────────┐
 │ 1. 先用 promo_list 確認檔期沒有重疊                         │
 │ 2. 門檻與折抵規則照 rules.md 填寫……                         │
 │ （同目錄還有：rules.md、checklist.md）                      │
 └───────────────────────┬────────────────────────────────────┘
                         │ 本體指向 rules.md，模型需要具體規則
                         ▼ read_skill_file("promo-setup", "rules.md")
 第 3 層：附加檔案與腳本（更需要時才讀或執行）       不限
 ┌────────────────────────────────────────────────────────────┐
 │ rules.md：滿千折百 門檻 1000，不可與會員折扣疊加……         │
 │ checklist.md（這次沒讀）  scripts/validate.py（可執行）     │
 └────────────────────────────────────────────────────────────┘
```

逐層看這張圖。第 1 層是索引，每個 skill 只佔一行名稱加描述，永遠放在 system prompt 裡，所以就算有幾十個 skills，成本也只是幾百 tokens，而且這一段在 session 中固定不變，對快取友善。第 2 層是 `SKILL.md` 本體，模型判斷某個 skill 和目前的任務相關時，才透過一個 tool（例如 `load_skill`，在檔案系統型的 agent 裡就是直接讀檔）把它讀進 context。第 3 層是附加檔案：本體只寫流程骨架並指向細節，模型需要具體規則時才讀 `rules.md`，用不到的 `checklist.md` 永遠不會進 context。因為每一層都按需載入，一個 skill 能攜帶的知識量實質上沒有上限，真正進入 context 的只有和這一次任務相關的部分。

這裡的關鍵是**描述就是觸發條件**。模型完全靠第 1 層的那一行描述決定要不要載入，所以描述要寫「什麼時候用」，而不只是「這是什麼」。「促銷活動設定流程」是在說它是什麼；「設定滿額折抵、折扣碼等促銷活動時使用；含檔期檢查與常見設定錯誤」則告訴模型觸發的情境與它能得到什麼。這和 13.4 節的 tool 描述是同一個問題：搜尋與觸發都依賴描述裡有沒有出現「使用者會講的話」。

Skill 和其他放知識的地方有什麼不同？下表是選擇的依據。

| 放在哪裡 | 適合的內容 | 何時進入 context | 例子 | 不適合 |
|---|---|---|---|---|
| system prompt | 每次都適用的角色、原則、禁止事項 | 每一輪 | 「退款超過 500 元一律找人核准」 | 只有少數任務用得到的長流程 |
| tool | 可執行的動作，有參數與結果 | 定義每輪（或 deferred），結果在呼叫後 | `coupon_create` | 純知識、流程說明 |
| skill | 某類任務的做法：流程、規則、範本、腳本 | 索引每輪，本體與檔案按需 | 促銷設定 SOP、發票作廢流程 | 每次都要用的規則、頻繁變動的資料 |
| memory（第 12 章） | 從互動中學到、因使用者或組織而異的事實 | 依檢索或規則注入 | 「這家店偏好用黑貓」 | 人工維護的標準流程 |
| 知識庫檢索（第 11 章） | 大量、非結構化、以查詢取用的文件 | 檢索命中時 | 商品說明、政策條文全文 | 有固定步驟的操作流程 |

這張表最常被問的是 skill 和知識庫檢索的差別。檢索是「用查詢去大量文件裡找片段」，適合事實型問題；skill 是「人寫好、針對某類任務的完整做法」，由模型依描述決定整份載入，適合流程型問題。另一個常見的誤解是把 skill 和 memory 混為一談：memory 是 agent 從互動中學到並寫入的，skill 通常是人審查過的標準流程；不過兩者的邊界在變模糊，有些系統會讓 agent 把成功的做法萃取成新的 skill，這時就要套用第 12 章的寫入政策與審查。

Skills 也和本章後半段的 code-as-action 相連。skill 資料夾可以放腳本，例如 `scripts/validate.py` 檢查優惠券設定是否合法；模型不必讀懂腳本的每一行，只要執行它並讀結果。這把「需要確定性」或「用 token 生成很貴」的工作（排序、驗證、格式轉換）交給程式。反過來，agent 在 code-as-action 中寫出一段好用的程式，也可以存成 skill 供日後重用，這是 procedural memory 最具體的形態。

> [!warning] 常見誤解
> 「skill 只是文件，不會有安全問題。」skill 會被模型當成指示來遵循，裡面的腳本還會被執行，所以一個來路不明的 skill 等同於一段會被執行的指令加程式碼。它可能誘導模型把資料送到外部，或在腳本裡做描述沒提到的事。只從可信來源安裝 skill，審查腳本、相依套件與任何連外的動作；組織內的 skill 要有擁有者與審查流程，和程式碼一樣進版本控制（第 31 章談供應鏈風險）。

> [!note] 2026 現況
> 截至 2026 年 10 月，依公開資料：Anthropic 於 2025 年 10 月推出 Agent Skills，結構為資料夾加 `SKILL.md`（frontmatter 必填 `name` 與 `description`），採三層漸進揭露（metadata 預載、相關時讀本體、附加檔案與腳本按需開啟或執行），並於 2025 年 12 月以開放標準形式發布規格。Claude Code 的 skill 可設定 `disable-model-invocation: true`，讓描述不佔 context、只能由使用者手動觸發。之後多個產品陸續支援 skills：Gemini CLI 的原始碼有 skill 啟用與「從對話萃取 skill」的 subagent，GitHub Copilot coding agent、OpenAI 的 agents 文件、Codex 與 Letta 都列出 skills。MCP 也有 Skills over MCP 擴充，透過 resources 探索與讀取 skills（第 14 章）。plugin 則是把 skills、MCP server、hooks 等打包成可安裝的單位。各平台的欄位與觸發細節不完全相同，請以官方文件為準。

## 13.6 Code-as-action：讓模型寫程式來呼叫工具

回到店家的問題：「9 月出貨、超過 7 天還沒送達的有幾筆？」傳統的 tool calling 裡，每個 tool 呼叫都是一次「模型推論 → harness 執行 → 結果回到模型」的往返。查 40 張訂單的貨態，就是 40 次往返；就算模型支援 parallel tool calls（第 4 章），一次送出 40 個查詢，40 份完整的貨態仍然全部進入 context，而模型真正需要的只是「7 筆逾期、各物流商幾筆、最慢的 3 筆」。**code-as-action**（以程式碼作為動作）的想法是：讓模型輸出一段程式，程式在執行環境中呼叫 tools、跑迴圈、做篩選與彙總，最後只把印出的結果帶回 context。

```text
 (A) 多次 tool call：每個結果都經過模型

  Model ─list_orders─► harness ─► 40 個編號 ─► Model ─get_shipment(B-2001)─► harness ─► 貨態 ─► Model
        ─get_shipment(B-2002)─► …… 重複 40 次 ……  每一輪都重送前面所有貨態
                                                    → 42 次推論，context 越來越長

 (B) code-as-action：中間結果留在執行環境

  Model ──run_code("for oid in list_orders(...): s = get_shipment(oid) ...")──► 受限執行器
                                                                                 │ 程式內呼叫 41 次 tool
                                                                                 │ （經過同一個 dispatcher）
                                                                                 │ 迴圈、篩選、計數
  Model ◄────────────── 只有 print 的 4 行：逾期 7 筆、各物流商筆數、最慢 3 筆 ──┘
        → 2 次推論，context 裡沒有任何一份完整貨態
```

這張資料流對照圖顯示 code-as-action 省在哪裡。在 (A) 裡，每個 tool 結果都必須流經模型：模型讀它、決定下一步、產生下一個呼叫，而且因為每一輪都重送完整歷史，第 40 次推論要重讀前 39 份貨態，累計 input tokens 接近平方成長。在 (B) 裡，模型只做一次「規劃」：把整個流程寫成程式。迴圈、條件判斷、計數都在執行環境裡完成，中間結果是程式的變數，不是 context 的內容。圖中特別標出「經過同一個 dispatcher」：程式裡的 `get_shipment` 不是繞過 harness 直接打 API，而是由 harness 提供的函式，參數驗證、權限、記錄全部照舊。

code-as-action 有三種常見形態，背後是同一個想法。第一種是把程式當成**唯一的動作空間**：模型的每一步都是一段程式，tools 是程式裡可以呼叫的函式，研究文獻稱為 CodeAct。第二種是 **programmatic tool calling**（程式化的工具呼叫）：模型仍然有一般的 tool calls，另外多了一個執行程式的 tool，程式裡可以呼叫被標記為「允許從程式呼叫」的 tools，這些呼叫回到 harness 執行，結果交回給程式而不是模型。第三種常被稱為 **code mode**：把整組 tools（例如一個 MCP server）呈現成檔案樹裡的程式碼 API，模型用列目錄、讀檔的方式找到需要的函式簽名，再寫程式呼叫；這同時也是一種漸進揭露，因為模型只讀它需要的那幾個 tool 檔案，和 13.4 節的 tool search 解決的是同一個問題。

為什麼要讓模型寫程式，而不是讓工程師把「查逾期訂單」寫成一個新的 tool？如果這個問題每天都被問，確實應該做成 workflow 級的 tool（第 5 章）。但店家的問題組合是開放的：今天問「逾期 7 天各物流商幾筆」，明天問「退貨率最高的 5 個商品裡，哪些是同一個供應商」。code-as-action 讓模型把現有的細粒度 tools 即時組合成一次性的小程式，這正是第 1 章說的「步驟無法事先列舉」的情況。另外，程式語言本身就是模型在訓練中大量看過的「動作語言」，用迴圈與變數表達多步流程，比用一連串 JSON 呼叫更自然。

它的代價也很明確。第一，你需要一個能執行模型所寫程式的環境，而這個環境的隔離是全書最嚴肅的安全議題之一（13.7 節與第 17 章）。第二，**副作用的核准變難**：一段程式可能在迴圈裡呼叫 40 次退款，人工核准不可能逐筆進行，所以本書的規則是：有副作用（write、destructive）的 tools 一律 `code_callable=False`，不開放從程式呼叫；需要批次寫入時，改成「程式只產生待執行清單，由一般 tool call 經核准後執行」。第三，**模型失去逐步判斷**：在 (A) 中，模型看到每一筆貨態，可以注意到「這筆的備註寫著地址錯誤」；在 (B) 中，只有程式明確 print 的東西會被看見。第四，除錯與觀測要多一層：trace 不只要記錄 `run_code` 這一個呼叫，還要記錄程式內部的每一次 tool 呼叫（第 29 章）。

> [!warning] 常見誤解
> 「code-as-action 能讓 agent 更聰明。」它主要改善的是效率與可擴展性：更少的推論次數、更小的 context、更確定的計算。正確率可能因此提高（模型不再被大量中間結果干擾、加總不再靠模型心算），也可能下降（程式寫錯而模型沒看到原始資料）。是否提高，要用自己的任務評估（第 27 章），而不是假設。

> [!note] 2026 現況
> 截至 2026 年 10 月，依公開資料：CodeAct 論文（Wang 等人，2024）提出以可執行 Python 作為統一的 action space，並報告在其評估中成功率優於 JSON 或文字形式的動作；Hugging Face smolagents 的 CodeAgent 是知名實作，Microsoft Agent Framework 與 LlamaIndex 也提供 CodeAct 類型的 agent。Anthropic 於 2025 年 11 月發表〈Code execution with MCP〉，把 MCP server 呈現為檔案樹中的程式碼 API，文中的例子 token 從約 150,000 降到約 2,000；Cloudflare 稱同樣的做法為「Code Mode」。Anthropic 同月推出 programmatic tool calling（beta）：在 code execution 環境中，程式可以呼叫標記了 `allowed_callers` 的 tools，tool 結果回給程式，只有輸出進入模型 context；官方報告的平均 token 由 43,588 降到 27,297。OpenAI 的 Agents API 文件列出 programmatic tool calling（以 JavaScript 編排），Codex 的開源程式碼中有 code mode 相關模組。DSPy 以 RLM 模組取代已 deprecated 的 CodeAct 模組，並明說其 `LocalInterpreter` 不是 sandbox。Harvey 在 2026 年 9 月公開以 REPL 遍歷大型文件集的 RLM harness，屬於單一廠商自建 benchmark 的結果。以上數字皆為各來源自報，參數名稱請以官方文件為準。

## 13.7 受限執行：先說清楚，這不是安全 sandbox

13.9 節要實作的執行器，會對模型寫的程式做四件事：用 `ast`（Python 標準函式庫的語法樹模組）檢查語法，只允許指派、迴圈、條件、函式呼叫等少數節點，拒絕 `import`、函式定義、類別定義與底線開頭的屬性存取；只提供一小組安全的內建函式（`len`、`sorted`、`sum` 等），沒有 `open`；用 `sys.settrace` 數執行了幾行，超過預算就中止；把 `print` 換成收集輸出，並限制回傳長度。tools 以函式的形式注入，而且只注入 `code_callable` 的唯讀 tools；退款這類有副作用的 tool，即使被呼叫也只會得到「請改用一般 tool call」的錯誤。

這些限制的目的是**讓 agent 的行為可預期、讓錯誤變成可讀的觀察**：模型寫了 `import os`，得到「不允許的語法：Import」，它就知道要改寫；寫了無窮迴圈，執行器會中止並回報，而不是把 agent 卡死。這和第 4 章「把例外變成觀察」是同一個原則。但這些限制**不是安全邊界**。這個說法不是謙虛，而是有具體理由的，下面這段程式示範其中一個：

```python
from __future__ import annotations

import sys


def count_lines(code: str) -> int:
    """用 sys.settrace 數「執行了幾行 Python」，這正是 13.9 節執行器的預算單位。"""
    used = [0]

    def tracer(frame, event, arg):
        if event == "line":
            used[0] += 1
        return tracer

    sys.settrace(tracer)
    try:
        exec(code, {"__builtins__": {"sum": sum, "range": range, "len": len}})
    finally:
        sys.settrace(None)
    return used[0]


loop_code = "total = 0\nfor i in range(3000):\n    total += i\n"
one_liner = "total = sum(range(3 * 10**6))\nn = len('x' * 10**6)\n"
print("Python 迴圈 3,000 次：", count_lines(loop_code), "行")
print("C 層級做 300 萬次加法、配置 1 MB 字串：", count_lines(one_liner), "行")
assert count_lines(loop_code) > 6000 and count_lines(one_liner) == 2
```

```text
Python 迴圈 3,000 次： 6002 行
C 層級做 300 萬次加法、配置 1 MB 字串： 2 行
```

第一行是一般的 Python 迴圈：3,000 次迭代，每次都會觸發行事件，執行器數到 6,002 行，預算機制有效。第二行是同樣性質的計算換一種寫法：`sum(range(...))` 與字串乘法都在 C 實作的內建函式裡完成，三百萬次加法加上配置 1 MB 字串，執行器只看到 2 行。把數字再放大幾個量級，就能讓 CPU 或記憶體耗盡，而行數預算完全察覺不到。這說明了受限執行器的本質：它在**同一個 process** 裡、用**語言層級**的規則限制程式，而 CPU、記憶體、檔案系統、網路、process 本身都不在它的控制範圍內。

| 面向 | 本章的受限執行器 | 安全 sandbox（第 17 章） |
|---|---|---|
| 隔離邊界 | 同一個 Python process，靠語法與名稱規則 | 獨立的 process、container、gVisor 或 microVM |
| CPU 與時間 | 只數 Python 行數，C 層級的計算看不到 | 作業系統層級的 CPU 配額與 wall-clock 逾時 |
| 記憶體 | 不限制 | cgroup 等機制設定硬上限 |
| 檔案系統 | 只靠「沒有提供 open」 | 只掛載指定目錄，其他看不到 |
| 網路 | 只靠「沒有提供連網函式」 | egress 控制，預設不通 |
| secrets | 和 agent 共用同一個 process 的記憶體 | secrets 不進 sandbox |
| 適合用途 | 教學、離線測試、開發期間探索 code-as-action 的效果 | 執行任何來自模型或使用者的程式 |

這張表的每一列都是 Maya 不准它碰 production 的理由。尤其是「隔離邊界」那一列：Python 是高度可內省的語言，物件之間有許多相互引用，只靠「沒有提供某些名稱」和「禁止某些語法」來阻止程式碰到不該碰的東西，歷史上一再被證明擋不住；這也是為什麼業界的做法是把隔離交給作業系統與虛擬化層，而不是交給語言規則。我們保留這些語言層級的檢查，是因為它們在真正的 sandbox **裡面**仍然有價值：它們把常見的錯誤提早轉成清楚的回饋，讓模型少浪費幾輪。安全來自外層的隔離，可預期性來自內層的規則，兩者是分工，不是替代。

> [!warning] 常見誤解
> 「把 `__builtins__` 設成空的 dict，再擋掉 import，就是一個 sandbox。」這是最常見、也最危險的誤解。語言層級的限制只能減少意外，不能抵擋刻意的繞過；被 prompt injection 操控的模型，正好會產生刻意的程式。任何會執行模型所寫程式的環境，都要假設程式可能是惡意的，並在作業系統或虛擬化層隔離，第 17 章會實作這一層。

## 13.8 怎麼選：token、步數與正確率的取捨

本章的三個機制都在用一種成本換另一種成本。tool search 用「多一輪推論、可能搜不到」換「每一輪少送大量定義」；skills 用「模型要判斷何時載入」換「平常不付流程的錢」；code-as-action 用「需要執行環境、模型看不到中間結果」換「更少的推論與更小的 context」。選擇時要同時看三個量：token（成本）、步數（延遲，每一步都是一次推論）、正確率（是否做對）。

```text
 一個任務需要的能力 → 該用哪個機制？

 這個能力是「動作」還是「做法」？
   │
   ├─ 做法（流程、規則、範本）──► 每次都適用？ ── 是 ──► system prompt
   │                               └─ 否 ──► skill（索引常駐，本體按需）
   │
   └─ 動作（tool）
        │
        ├─ tools 總數夠少（定義總量只佔 context 一小部分）？ ── 是 ──► 全部載入
        │    └─ 否 ──► 高使用率的常駐，其他 deferred＋tool search（先量 recall）
        │
        └─ 這次要呼叫幾次、結果要不要逐筆判斷？
             ├─ 一兩次，或每筆結果都需要模型判斷 ──► 一般 tool call
             ├─ 多次但彼此獨立、結果小 ──► parallel tool calls
             └─ 多次、要迴圈或篩選、中間結果大、只需要彙總
                  └─ 有安全的執行環境？ ── 是 ──► code-as-action（唯讀 tools）
                                          └─ 否 ──► 先做成 workflow 級 tool（第 5 章）
```

這張決策圖的第一個分岔最容易被忽略：先問「這是動作還是做法」。很多團隊把 SOP 寫成一個回傳長文字的 tool，或把可執行的動作寫在 system prompt 裡要模型「照著做」，都是放錯地方。第二個分岔處理 tool 定義的數量，門檻不是固定的數字，而是「定義總量相對於 context 預算的比例」與「選擇正確率有沒有下降」，兩者都要量。第三個分岔處理呼叫次數：當每一筆結果都需要模型的判斷（例如逐筆閱讀客訴內容決定怎麼回），code-as-action 反而會讓模型看不到它需要看的東西；當工作本質是機械性的迴圈與彙總，code-as-action 的優勢最大。最後一個條件是硬性的：沒有安全的執行環境，就不要讓模型寫的程式碰真實資料，退而求其次是把常見的組合做成 workflow 級 tool。

估算可以讓取捨更具體。設任務要對 N 個項目各呼叫一次 tool，每個結果約 r tokens，固定前綴（system 加 tools）約 P tokens。逐一呼叫需要約 N＋2 次推論，第 k 次要重讀前面 k 個結果，累計 input 約為（N＋2）× P ＋ r × N² / 2；平行呼叫需要約 3 次推論，但最後一次要讀全部 N 個結果，累計約 3P ＋ rN（另加 N 個呼叫請求本身的長度）；code-as-action 約 2 次推論，累計約 2P 加上程式與輸出的長度，和 N 幾乎無關。N 越大、r 越大，差距越懸殊；N 只有 2 或 3 時，三者差距很小，code-as-action 還要多付寫程式的 output tokens 與執行環境的啟動時間，不見得划算。

| 方式 | 推論次數 | 累計 input tokens 的量級 | 模型看得到每筆結果嗎 | 適合 |
|---|---|---|---|---|
| 逐一 tool call | N＋2 | 約 rN² / 2，隨 N 平方成長 | 是 | N 小、每步要依結果決定下一步 |
| parallel tool calls | 約 3 | 約 rN，隨 N 線性成長 | 是 | N 中等、結果小、彼此獨立 |
| code-as-action | 約 2 | 幾乎和 N 無關 | 只看到 print 的內容 | N 大、結果大、只需彙總或篩選 |

prompt caching 會改變這張表的金額，但不會改變推論次數。逐一呼叫因為只在尾端追加，大部分 input 能命中快取，金額可能比表面數字低很多；然而 42 次推論的延遲是實實在在的，每一次都要等模型產生下一個 tool call。這就是為什麼 code-as-action 在「使用者在線上等」的情境特別有價值：它省下的不只是錢，還有好幾十次往返的時間。

正確率則必須量。三個機制各有自己的失敗模式：tool search 的失敗是搜不到（召回率不足）或搜到太多相近的（排序不好）；skills 的失敗是該載入時沒載入（描述沒寫好觸發條件）；code-as-action 的失敗是程式邏輯錯（篩選條件寫反、欄位名稱猜錯）而模型沒有察覺。對應的評估方法分別是：為 tool search 建立「查詢 → 正確 tool」的評估集量 recall@k；為 skills 建立「任務 → 應該載入的 skill」的評估集；為 code-as-action 比對程式輸出和以確定性程式算出的標準答案。第 27 章會把這些整合進 agent 的評估流程。

## 13.9 動手做：tool registry、Skills 與 code-as-action

這一節分三段程式，每段都可以單獨執行。第一段實作 tool registry、BM25 tool search 與 deferred loading，並量測搜尋品質與 token；第二段實作 skills 的三層漸進揭露；第三段實作受限執行器，並在同一個任務上比較逐一呼叫、平行呼叫與 code-as-action 三種方式。三段都使用全書統一的 ScriptedModel，所以模型的「決定」是劇本寫好的；我們量測的是 harness 的行為與成本，而不是模型的聰明程度。

### 第一段：tool registry 與 deferred loading

registry 裡有青鳥營運助理的 59 個 tools，內容由樣板產生，但結構和真實目錄相同：五家物流商各三個 tools，七個業務領域各六個，加上兩個常駐的訂單 tools。搜尋用 BM25；中文沒有空白分詞，所以用相鄰兩字（bigram）當詞，英數字取整個字。`run()` 是第 4 章 loop 的精簡版，差別在於每一輪送出的 tools 清單由「常駐＋`tool_search`＋已載入」組成，而已載入集合只往尾端追加。

```python
from __future__ import annotations

import json
import math
import re
from collections import Counter
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"          # end_turn｜tool_use｜max_tokens
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    """依劇本回應的假模型。劇本的每一步是 ModelResponse，或「收到 messages 後回傳 ModelResponse」的函式。"""

    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    """劇本小工具：產生一個「呼叫 name 工具」的回應。"""
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    """劇本小工具：產生一個「直接回答並結束」的回應。"""
    return ModelResponse(text=text)


def tokens(obj: Any) -> int:
    """粗估 token：JSON 字元數 ÷ 2（和第 4 章相同的簡化）。"""
    return len(json.dumps(obj, ensure_ascii=False)) // 2


# ───────── tool registry：能力的目錄，和「這一輪送給模型的清單」分開 ─────────
@dataclass
class Tool:
    name: str
    description: str
    parameters: dict[str, Any]
    fn: Callable[..., Any]
    tags: list[str] = field(default_factory=list)
    always_loaded: bool = False             # 常駐：每一輪都放完整定義

    def schema(self) -> dict[str, Any]:
        return {"name": self.name, "description": self.description, "parameters": self.parameters}


def terms(text: str) -> list[str]:
    """英數字取整個字（底線拆開），中文取相鄰兩字（bigram）；不需要斷詞字典。"""
    out = re.findall(r"[a-z0-9]+", text.lower().replace("_", " "))
    for run in re.findall(r"[一-鿿]+", text):
        out += [run[i:i + 2] for i in range(len(run) - 1)] or [run]
    return out


class ToolRegistry:
    def __init__(self, tools: list[Tool]):
        self.tools = {t.name: t for t in tools}
        self.docs = {t.name: terms(f"{t.name} {t.description} {' '.join(t.tags)}") for t in tools}
        self.df = Counter(w for d in self.docs.values() for w in set(d))
        self.avg_len = sum(map(len, self.docs.values())) / len(self.docs)

    def search(self, query: str, k: int = 3) -> list[str]:
        """BM25：詞越少見、在文件中出現越多次，分數越高；文件太長會被懲罰。"""
        n, scores = len(self.docs), {}
        for name, doc in self.docs.items():
            if self.tools[name].always_loaded:
                continue                    # 常駐 tool 已經在 context 裡，不必再搜
            tf, s = Counter(doc), 0.0
            for w in set(terms(query)):
                if tf[w]:
                    idf = math.log(1 + (n - self.df[w] + 0.5) / (self.df[w] + 0.5))
                    s += idf * tf[w] * 2.2 / (tf[w] + 1.2 * (0.25 + 0.75 * len(doc) / self.avg_len))
            if s > 0:
                scores[name] = s
        return sorted(scores, key=lambda x: -scores[x])[:k]

            "required": list(props)}

class RecordingModel(ScriptedModel):
    """額外記下每一輪收到的 tool 清單，好量測 token 與檢查前綴是否穩定。"""

    def __init__(self, script):
        super().__init__(script)
        self.tool_lists: list[list[str]] = []
        self.tool_tokens: list[int] = []

    def complete(self, messages, tools=None, system=""):
        self.tool_lists.append([t["name"] for t in tools])
        self.tool_tokens.append(tokens(tools))
        return super().complete(messages, tools, system)


def run(model, registry: ToolRegistry, user_input: str, deferred: bool = True, max_steps: int = 6):
    messages: list[dict] = [{"role": "user", "content": user_input}]
    loaded: list[str] = []                  # 依「被搜尋到的順序」追加，不重排、不移除
    for _ in range(max_steps):
        if deferred:
            # 常駐 tools 與 tool_search 在最前面；搜尋到的定義只往尾端追加 → 前綴不變
            resident = [t.schema() for t in registry.tools.values() if t.always_loaded]
            tools = resident + [TOOL_SEARCH] + [registry.tools[n].schema() for n in loaded]
        else:
            tools = [t.schema() for t in registry.tools.values()]
        resp = model.complete(messages, tools=tools)
        messages.append({"role": "assistant", "content": resp.text, "tool_calls": [vars(tc) for tc in resp.tool_calls]})
        if not resp.tool_calls:
            return resp.text, messages
        for tc in resp.tool_calls:
            if tc.name == "tool_search":
                found = registry.search(tc.args["query"])
                loaded += [n for n in found if n not in loaded]
                content = json.dumps([{"name": n, "description": registry.tools[n].description} for n in found],
                                     ensure_ascii=False)
            elif tc.name not in [t["name"] for t in tools]:
                hint = "請先用 tool_search 載入。" if tc.name in registry.tools else "沒有這個工具。"
                content = f"{tc.name} 目前不在可用清單中，{hint}"
            else:
                content = json.dumps(registry.tools[tc.name].fn(**tc.args), ensure_ascii=False)
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name, "content": content})
    return "步驟用完", messages
```

先看搜尋品質。第一行是 v1 唯一失敗的查詢：「滿千折百 優惠券」的前三名是停用、查使用次數、設定適用商品，正確的 `coupon_create` 不在其中。原因是 v1 的描述寫「建立折扣碼或滿額折抵優惠券」，和使用者的說法「滿千折百」沒有共同的詞（bigram 是「滿千、千折、折百」對「滿額、額折、折抵」），只剩「優惠券」三個字能比對，而 `coupon_create` 的描述較長，被 BM25 的長度正規化懲罰，排到後面。修法不是改搜尋演算法，而是在描述裡加入使用者會講的說法「例如滿千折百、滿額免運」，v2 的 recall@3 就到了 1.00。這是 tool search 最重要的一課：**描述同時是寫給模型看的說明，也是搜尋的索引**；用系統內部的術語寫描述，搜尋就找不到使用者的說法。

接著是 token。全部載入時，兩輪各送 5,598 tokens 的 tool 定義；deferred 版本第 1 輪只有 304 tokens（兩個常駐 tools 加 `tool_search`），搜尋命中三個新竹物流 tools 後變成 620，三輪合計 1,544，約為全部載入的七分之一。代價是多了一輪推論（3 輪對 2 輪），這正是 13.8 節說的「用步數換 token」。這裡的定義刻意寫得很短，真實的 tool 定義含參數說明與例子，每份常常是數百 tokens，差距會更懸殊。

三行「第 N 輪送出的 tools」是前綴不變式成立的證據：第 2 輪的清單以第 1 輪的清單開頭，第 3 輪和第 2 輪完全相同。程式最後的 assert 對每一對相鄰的輪次檢查「前一輪是下一輪的前綴」，這一行保證了 Iris 的「每輪動態過濾」事故不會發生。最後一行測試模型跳過搜尋、直接呼叫 deferred 的 `tcat_pickup`：harness 不執行，而是回填「請先用 tool_search 載入」，因為模型沒看過這個 tool 的 schema，它填的參數很可能是猜的。

### 第二段：Skills 的三層漸進揭露

```python
from __future__ import annotations

import json
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"          # end_turn｜tool_use｜max_tokens
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    """依劇本回應的假模型。劇本的每一步是 ModelResponse，或「收到 messages 後回傳 ModelResponse」的函式。"""

    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    """劇本小工具：產生一個「呼叫 name 工具」的回應。"""
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    """劇本小工具：產生一個「直接回答並結束」的回應。"""
    return ModelResponse(text=text)


def tokens(text: str) -> int:
    return len(text) // 2                  # 和第 4 章相同的粗估

def parse_frontmatter(text: str) -> dict[str, str]:
    head = text.split("---")[1]
    return dict(line.split(": ", 1) for line in head.strip().splitlines())


class SkillLibrary:
    """三層漸進揭露：索引（永遠在）→ SKILL.md 本體（需要時）→ 附加檔案（更需要時）。"""

    def __init__(self, files: dict[str, str]):
        self.files = files
        self.meta = {}
        for path, text in files.items():
            if path.endswith("/SKILL.md"):
                m = parse_frontmatter(text)
                self.meta[m["name"]] = m["description"]
        self.loaded: list[str] = []

    def index(self) -> str:                # 第 1 層：只有名稱與描述，放在 system prompt
        lines = [f"- {n}：{d}" for n, d in self.meta.items()]
        return "可用的 skills（需要時用 load_skill 讀取完整內容）：\n" + "\n".join(lines)

    def load_skill(self, skill: str) -> str:  # 第 2 層：SKILL.md 本體，並列出可再讀的檔案

        body = self.files[f"{skill}/SKILL.md"].split("---", 2)[2]
        return body + f"\n（同目錄還有：{extra}，需要時用 read_skill_file 讀取）"

    def read_skill_file(self, skill: str, path: str) -> str:  # 第 3 層
        key = f"{skill}/{path}"
        if key not in self.files:
            return f"{key} 不存在"
        self.loaded.append(key)
        return self.files[key]
```

「載入順序」顯示這次任務只讀了兩個檔案：promo-setup 的本體，以及本體指向的 rules.md；同一個 skill 的 checklist.md 和其他 8 個 skills 都沒有進入 context。下一行是成本對照：實際讀進 context 的是 760 tokens（索引加兩個檔案），如果把 17 個檔案全部塞進 system prompt，是 3,189 tokens，而且每一輪、每個和促銷無關的對話都要付。劇本的第二步是一個函式：只有在本體的回傳裡看到 rules.md 時，才去讀它，這模擬了「第 2 層告訴模型第 3 層有什麼」的導航作用；如果本體沒有列出附加檔案，模型就不會知道它們存在。

### 第三段：code-as-action 與多次 tool call 的對比

最後一段回到店家的問題。假後端有 9 月的 40 張已出貨訂單，用固定 seed 產生，所以每次執行結果相同。同一個問題用三種方式回答：A 是一次一個 tool call，B 是把 40 個查詢放進同一輪的 parallel tool calls，C 是模型寫一段程式交給 `run_restricted` 執行。三種方式都實際執行了 41 次 tool（1 次列訂單加 40 次查貨態），差別只在結果流向哪裡。程式最後再用五段不合規的程式測試執行器的限制。

```python
from __future__ import annotations

import ast
import json
import random
import sys
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"          # end_turn｜tool_use｜max_tokens
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    """依劇本回應的假模型。劇本的每一步是 ModelResponse，或「收到 messages 後回傳 ModelResponse」的函式。"""

    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    """劇本小工具：產生一個「呼叫 name 工具」的回應。"""
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    """劇本小工具：產生一個「直接回答並結束」的回應。"""
    return ModelResponse(text=text)


class MeteredModel(ScriptedModel):
    """用「字元數 ÷ 2」粗估 input 與 output tokens（第 4 章的同一個簡化）。"""

    def complete(self, messages, tools=None, system=""):
        resp = super().complete(messages, tools, system)
        out = resp.text + json.dumps([vars(t) for t in resp.tool_calls], ensure_ascii=False)
        resp.usage = {"input_tokens": len(json.dumps([tools, messages], ensure_ascii=False)) // 2,
                      "output_tokens": len(out) // 2}
        return resp


# ───────── 受限執行器：限制語法、名稱、步數與輸出。注意：這不是安全 sandbox（見第 17 章）─────────
ALLOWED = (ast.Module, ast.Expr, ast.Assign, ast.AugAssign, ast.For, ast.While, ast.If, ast.Break,
           ast.Continue, ast.Pass, ast.Compare, ast.BoolOp, ast.BinOp, ast.UnaryOp, ast.Call, ast.keyword,
           ast.Name, ast.Load, ast.Store, ast.Constant, ast.List, ast.Tuple, ast.Dict, ast.Subscript,
           ast.Slice, ast.Attribute, ast.ListComp, ast.DictComp, ast.GeneratorExp, ast.comprehension,
           ast.Lambda, ast.arguments, ast.arg, ast.JoinedStr, ast.FormattedValue, ast.IfExp,
           ast.operator, ast.cmpop, ast.boolop, ast.unaryop)
SAFE_BUILTINS = {f.__name__: f for f in (len, sorted, sum, min, max, range, round, enumerate, list, dict,
                                          str, int, abs, any, all, zip)}


def run_restricted(code: str, functions: dict[str, Callable], max_lines: int = 5_000,
                   max_output: int = 1_500) -> tuple[bool, str]:
    """回傳 (is_error, 輸出)。只有 print 的內容會回到模型的 context。"""
    try:
        tree = ast.parse(code)
    except SyntaxError as exc:
        return True, f"語法錯誤：第 {exc.lineno} 行 {exc.msg}"
    for node in ast.walk(tree):
        if not isinstance(node, ALLOWED):
            return True, f"不允許的語法：{type(node).__name__}（第 {getattr(node, 'lineno', '?')} 行）"
        if isinstance(node, ast.Attribute) and node.attr.startswith("_"):
            return True, f"不允許存取底線開頭的屬性：{node.attr}"
    out: list[str] = []
    budget = [max_lines]

    def tracer(frame, event, arg):        # 每執行一行扣一點，防止無窮迴圈卡死 agent
        if event == "line":
            budget[0] -= 1
            if budget[0] < 0:
                raise TimeoutError(f"超過 {max_lines} 行的執行預算")
        return tracer

    env = {"__builtins__": {**SAFE_BUILTINS, "print": lambda *a: out.append(" ".join(map(str, a)))},
           **functions}
    sys.settrace(tracer)
    try:
        exec(compile(tree, "<agent-code>", "exec"), env)
    except Exception as exc:              # 程式的錯誤也是觀察：回填給模型修正
        return True, f"{type(exc).__name__}: {exc}\n已輸出：{' | '.join(out)[-300:]}"
    finally:
        sys.settrace(None)
    text = "\n".join(out)
    return False, text if len(text) <= max_output else text[:max_output] + f"…（已截斷，原長 {len(text)}）"


# ───────── 青鳥的假後端：9 月的 40 張已出貨訂單 ─────────
rng = random.Random(7)
CARRIERS = ["黑貓", "新竹物流", "嘉里大榮", "中華郵政"]
SHIP = {}
for i in range(40):
    days = rng.randint(1, 12)
    SHIP[f"B-{2001 + i}"] = {"order_id": f"B-{2001 + i}", "carrier": rng.choice(CARRIERS), "days_in_transit": days,
                             "delivered": days <= 4 or rng.random() < 0.5, "location": rng.choice(["台中轉運中心", "桃園集貨場", "高雄營業所"]),
                             "events": [f"9/{d} 貨件已到 {loc}" for d, loc in ((3, "集貨場"), (4, "轉運中心"), (5, "營業所"))]}
tool_log: list[str] = []

def list_orders(month: str) -> list[str]:
    tool_log.append("list_orders")
    return list(SHIP)

def get_shipment(order_id: str) -> dict:
    tool_log.append("get_shipment")
    return SHIP[order_id]

def refund(order_id: str) -> str:
    raise PermissionError("refund 有副作用，不開放在程式中呼叫；請改用一般 tool call（會經過人工確認）")

def obj(**props: str) -> dict:
    return {"type": "object", "properties": {k: {"type": "string", "description": v} for k, v in props.items()},
            "required": list(props)}

TOOLS = [{"name": "list_orders", "description": "列出某月已出貨的訂單編號", "parameters": obj(month="例如 2026-09")},
         {"name": "get_shipment", "description": "查一張訂單的貨態", "parameters": obj(order_id="訂單編號")},
         {"name": "refund", "description": "未出貨訂單退款", "parameters": obj(order_id="訂單編號")}]
CODE_TOOL = [{"name": "run_code", "parameters": obj(code="Python 程式"), "description":
              "執行一段受限 Python。可呼叫 list_orders(month) -> list[str]、get_shipment(order_id) -> dict"
              "（欄位 carrier、days_in_transit、delivered、location）。只有 print 的內容會回傳給你。"}]
FUNCS = {"list_orders": list_orders, "get_shipment": get_shipment, "refund": refund}


def run(model, tools, user_input: str, max_steps: int = 50) -> dict:
    messages: list[dict] = [{"role": "user", "content": user_input}]
    usage = {"input_tokens": 0, "output_tokens": 0}
    for step in range(1, max_steps + 1):
        resp = model.complete(messages, tools=tools)
        for k in usage:
            usage[k] += resp.usage[k]
        messages.append({"role": "assistant", "content": resp.text, "tool_calls": [vars(t) for t in resp.tool_calls]})
        if not resp.tool_calls:
            return {"steps": step, **usage, "answer": resp.text, "messages": messages}
        for tc in resp.tool_calls:
            if tc.name == "run_code":
                is_error, content = run_restricted(tc.args["code"], FUNCS)
            else:
                is_error, content = False, json.dumps(FUNCS[tc.name](**tc.args), ensure_ascii=False)
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name, "content": content,
                             "is_error": is_error})
    raise RuntimeError("步數用完")


QUESTION = "9 月出貨、超過 7 天還沒送達的訂單，各物流商各幾筆？最慢的 3 筆是哪些？"
late = sorted([s for s in SHIP.values() if not s["delivered"] and s["days_in_transit"] > 7],
              key=lambda s: -s["days_in_transit"])
ANSWER = f"共 {len(late)} 筆逾期，最慢的是 {', '.join(s['order_id'] for s in late[:3])}。"

# A. 一次一個 tool call：模型每看完一筆貨態，才決定下一步
tool_log.clear()
seq = [call("list_orders", "c0", month="2026-09")]
seq += [call("get_shipment", f"c{i}", order_id=o) for i, o in enumerate(SHIP, 1)] + [say(ANSWER)]
a = run(MeteredModel(seq), TOOLS, QUESTION)
a["tools"] = len(tool_log)

# B. 平行 tool calls：一輪送出 40 個查詢，步數少了，但 40 份完整貨態全部進 context
tool_log.clear()
batch = ModelResponse(tool_calls=[ToolCall(f"c{i}", "get_shipment", {"order_id": o}) for i, o in enumerate(SHIP, 1)],
                      stop_reason="tool_use")
b = run(MeteredModel([call("list_orders", "c0", month="2026-09"), batch, say(ANSWER)]), TOOLS, QUESTION)
b["tools"] = len(tool_log)

# C. code-as-action：模型寫一段程式，迴圈與篩選在執行器裡跑完，只有 print 回到 context
CODE = '''
late = []
for oid in list_orders(month="2026-09"):
    s = get_shipment(order_id=oid)
    if not s["delivered"] and s["days_in_transit"] > 7:
        late.append(s)
count = {}
for s in late:
    count[s["carrier"]] = count.get(s["carrier"], 0) + 1
print("逾期", len(late), "筆", count)
for s in sorted(late, key=lambda s: -s["days_in_transit"])[:3]:
    print(s["order_id"], s["carrier"], s["days_in_transit"], "天", s["location"])
'''
tool_log.clear()
c = run(MeteredModel([call("run_code", "c1", code=CODE), say(ANSWER)]), CODE_TOOL, QUESTION)
c["tools"] = len(tool_log)
print("run_code 回傳給模型的內容：\n" + c["messages"][2]["content"] + "\n")

print(f"{'方式':<14}{'模型呼叫':>6}{'tool 執行':>8}{'input tokens':>14}{'output tokens':>14}")
for label, r in (("A 逐一呼叫", a), ("B 平行呼叫", b), ("C code-as-action", c)):
    print(f"{label:<16}{r['steps']:>6}{r['tools']:>9}{r['input_tokens']:>14,}{r['output_tokens']:>14,}")
assert a["tools"] == b["tools"] == c["tools"] == 41
assert c["steps"] == 2 and c["input_tokens"] * 10 < b["input_tokens"] < a["input_tokens"]
assert c["messages"][2]["content"].splitlines()[1].startswith(late[0]["order_id"])

# 受限執行器擋下的東西（每一行都是「回填給模型的錯誤」，不是讓 agent 崩潰）
print()
for bad in ['import os', 'print(list_orders.__name__)', 'open("orders.csv")',
            'refund(order_id="B-2001")', 'while True:\n    pass']:
    is_error, msg = run_restricted(bad, FUNCS)
    print(f"{bad.splitlines()[0]:<28} → {msg.splitlines()[0]}")
    assert is_error
```

第一段輸出是 `run_code` 回傳給模型的全部內容：4 行，包含逾期筆數、各物流商的筆數，以及最慢的 3 筆。40 份完整的貨態（每份都有事件紀錄）從頭到尾沒有進入 context，它們只是程式裡的變數 `s`。程式的 assert 也確認了這 4 行的第一筆和用確定性程式直接算出的最慢訂單一致，這是檢查 code-as-action 正確率最基本的方法：和標準答案比對。

接著是三種方式的對照表。A 逐一呼叫需要 42 次模型呼叫，累計 input 約 19.6 萬 tokens，因為第 k 次呼叫要重讀前面 k 份貨態，這就是 13.8 節公式裡的平方項。B 平行呼叫把模型呼叫降到 3 次，input 降到約 8,800 tokens，但第 3 次呼叫仍要讀完 40 份貨態。C 只需要 2 次模型呼叫，input 約 780 tokens，連 B 的十分之一都不到。output tokens 也值得看：A 與 B 約 1,450，是 41 個 tool call 的 JSON 累積起來的；C 只有 280，因為一段 11 行的程式就表達了整個流程。再提醒一次，這些數字來自「字元數 ÷ 2」的粗估與很小的假資料，重點是量級與趨勢；真實系統還有 prompt caching 的折扣，但 A 的 42 次推論延遲不會因為快取而消失。

最後五行是執行器擋下的程式，每一行都變成一則回填給模型的錯誤，agent 不會崩潰。`import os` 在語法檢查時被拒；存取 `__name__` 這類底線開頭的屬性被拒；`open` 不在提供的內建函式中，得到 `NameError`；`refund` 雖然有函式名稱，但它不是 `code_callable` 的 tool，呼叫時得到「請改用一般 tool call（會經過人工確認）」的 `PermissionError`，這保證了有副作用的動作不會藏在迴圈裡繞過核准；無窮迴圈在 5,000 行的預算用完時中止。再強調一次 13.7 節的結論：這些都是讓行為可預期的規則，不是安全邊界。

## 13.10 實務應用

本章的三個機制在不同產品裡的比重差很多。以下四個情境說明怎麼依任務特性取捨。

**情境一：電商 SaaS 的營運助理（青鳥的主線）**。店家的需求橫跨物流、庫存、優惠券、報表等領域，tools 數量多但每次對話只用到其中一兩個領域，是 tool search 最典型的場景。常駐的只有查訂單與搜尋訂單；其他 tools 依領域加命名空間前綴，描述裡刻意寫入店家的說法（「滿千折百」「叫貨運來收」），並用從真實對話抽樣的查詢維護 tool search 的評估集。營運 SOP 做成 skills，由營運團隊擁有、經過審查才上線。報表類問題允許 code-as-action，但只開放唯讀的查詢 tools；開券、退款這類寫入動作只能用一般 tool call，並走第 21 章的核准流程。

**情境二：接上大量 MCP server 的 coding agent 與 IDE**。開發者常常一次接上 GitHub、issue tracker、資料庫、雲端平台等多個 MCP server（第 14 章），每個 server 帶來數十個 tools，全部載入很容易佔掉可觀的 context，擠壓真正重要的程式碼與錯誤訊息。依公開資料，主流 coding agent 已把 MCP tool 定義改成預設 deferred，透過 tool search 按需載入，只保留讀檔、搜尋、編輯、shell 這類核心 tools 常駐（見 13.4 節的 2026 現況）。這類產品的 skills 多半是團隊的工作慣例，例如「怎麼跑這個 repo 的測試」「發版流程」，和程式碼放在同一個 repo、一起審查。

**情境三：試算表與財務分析**。使用者問「這 2,000 筆費用明細裡，哪些部門超出預算」，資料量大、操作是機械性的篩選與彙總，是 code-as-action 優勢最大的場景。把 2,000 筆明細逐筆交給模型，既貴又容易在心算加總時出錯；讓模型寫程式在執行環境中算完，只回傳超支的部門與金額，正確率與成本都更好。依 Anthropic 公開的說明，其試算表產品使用 programmatic tool calling 來處理這類大量資料的操作。要注意的是，這類資料常含個資與機密，執行環境必須是第 17 章的 sandbox，而且輸出也要經過檢查，避免程式把整份明細 print 回 context。

**情境四：企業內部的 IT 與營運支援**。公司有上百份 runbook：重設 VPN、申請權限、處理資安事件。把它們做成 skills，索引只佔幾百 tokens，員工問「VPN 一直斷線」時，agent 依描述載入對應的 runbook，再依步驟呼叫 tools。這裡最大的風險是 skill 的來源與品質：過期的 runbook 會讓 agent 自信地執行錯誤的步驟，惡意或被竄改的 skill 則等同於注入的指令。所以 skill 要有擁有者、最後審查日期與版本，並和 tool 一樣納入 registry 治理。依公開文件，GitHub Copilot coding agent 與 OpenAI 的 agents 相關文件都已支援 skills（見 13.5 節的 2026 現況），組織可以用同一份 skill 格式跨產品共用。

| 產品類型 | 主要機制 | 常駐什麼 | 特別注意 |
|---|---|---|---|
| 電商營運助理 | tool search＋skills，報表用 code-as-action | 查訂單、搜尋訂單、tool_search | 描述寫入使用者說法；寫入動作不開放程式呼叫 |
| coding agent／IDE | MCP tools 預設 deferred | 讀檔、搜尋、編輯、shell | 核心 tools 固定順序；skills 和 repo 一起審查 |
| 試算表與財務分析 | code-as-action | 少數資料存取 tools | 必須在 sandbox 執行；輸出也要檢查 |
| 企業 IT 支援 | skills（runbook） | skill 索引 | skill 要有擁有者與審查日期，防過期與竄改 |

這張表的共同點是：沒有一個產品只用一種機制。tool search 管理「能做什麼」，skills 管理「該怎麼做」，code-as-action 管理「怎麼做得有效率」，三者都依賴同一件事：registry 裡的 metadata 是正確、被維護的。

## 13.11 設計檢查清單

設計或審查一個能力會持續擴充的 agent 時，逐項回答下面的問題。

1. 是否有一個 tool registry 作為唯一的事實來源，記錄每個 tool 的擁有者、副作用等級、載入政策與能否被程式呼叫？
2. 目前 tool 定義的總 tokens 是多少？佔每輪 input 的比例是多少？是否定期量測？
3. 哪些 tools 常駐？依據是 trace 中的使用率，還是直覺？
4. deferred 的 tools 被載入後，是否只往清單尾端追加、在 session 中不重排也不移除？是否有測試檢查「前一輪清單是下一輪的前綴」？
5. tool search 是否有自己的評估集（查詢 → 正確 tool），並在每次新增或修改 tool 描述時重跑 recall@k？
6. tool 描述與 tags 是否包含使用者實際會講的說法，而不只是系統內部術語？
7. 模型直接呼叫尚未載入的 tool 時，harness 是回填提示，還是默默執行？
8. 權限檢查是否在 dispatcher 依使用者身分與副作用等級進行，而不是依賴「沒載入就看不到」？
9. 每個 skill 的描述是否寫明「什麼時候用」？是否有擁有者、版本與最後審查日期？
10. 第三方或社群的 skill 是否經過腳本、相依套件與連外動作的審查才安裝？
11. 哪些 tools 開放從程式呼叫（code_callable）？有副作用的 tools 是否一律排除？
12. 執行模型所寫程式的環境，是否在作業系統或虛擬化層隔離（第 17 章），而不是只靠語言層級的限制？
13. code-as-action 的輸出是否有長度上限？程式內部的每一次 tool 呼叫是否寫入 trace？
14. 對於需要逐筆判斷的任務，是否刻意保留一般 tool call，而不是一律改成程式？

## 13.12 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 新增一批 tools 後，選錯 tool 的比例上升 | 新 tools 的名稱或描述和既有的重疊 | 在 trace 中統計「實際呼叫」與「應該呼叫」的混淆對 | 加命名空間前綴、改寫描述的使用情境；必要時合併相近 tools |
| 改成動態挑選 tools 後，帳單沒降反升 | 每輪清單不同，prompt cache 前綴被打斷 | 比較變更前後的 cache 命中率 | 改用 deferred loading，只在尾端追加 |
| 模型說「找不到可以做這件事的工具」，但 registry 裡明明有 | tool search 召回率不足，描述沒有使用者的說法 | 用該查詢跑 tool search，看正確 tool 的排名 | 描述與 tags 加入同義詞；把失敗查詢加入評估集；考慮 hybrid 搜尋 |
| 模型呼叫 deferred tool 時參數常錯 | 未載入就呼叫，模型沒看過 schema | 在 trace 中找「未載入即呼叫」的事件 | dispatcher 回填「請先搜尋」，不執行 |
| skill 存在但模型從不載入 | 描述只寫「是什麼」，沒寫「什麼時候用」 | 用評估集統計該載入而未載入的比例 | 改寫描述為觸發情境；在本體開頭重述適用範圍 |
| code-as-action 的答案和實際資料對不上 | 程式邏輯錯（欄位猜錯、條件寫反），模型沒看到原始資料 | 用確定性程式重算標準答案比對 | 在 run_code 的描述中列出欄位與型別；程式輸出附上樣本列供模型檢查 |
| 一段程式讓 agent 卡住或 host 資源耗盡 | 執行器只有語言層級限制，C 層級計算與記憶體不受控 | 觀察 host 的 CPU 與記憶體曲線 | 移到第 17 章的 sandbox，設 OS 層級的 CPU、記憶體與 wall-clock 上限 |
| 程式裡迴圈呼叫了寫入動作，繞過人工核准 | 有副作用的 tools 被開放給程式呼叫 | 檢查 registry 的 code_callable 欄位與內部呼叫 trace | 寫入 tools 一律不開放程式呼叫；程式只產生待辦清單，再走一般 tool call |

## 本章重點整理

- tool 定義放在每一輪都送出的前綴，tool 數量的成本是「每一輪、每個 session 都付」，而且會稀釋模型選擇 tool 的注意力。
- context window 夠大只代表放得下，不代表用得好；把 tool 定義當成 context 預算的一部分來量測與管理。
- tool registry 把「系統有哪些能力」和「這一輪模型看得到哪些能力」分開，metadata 讓 harness 能做搜尋、權限與治理。
- deferred loading 讓大多數 tools 只登記不載入，模型透過常駐的 tool search 找到需要的 tools，命中後才把完整定義加入清單。
- 已載入的 tools 只往清單尾端追加、在 session 中不重排不移除，前一輪的清單永遠是下一輪的前綴，prompt cache 才不會被打斷。
- tool search 的召回率就是 agent 能力的上限；描述同時是給模型的說明與搜尋的索引，要寫入使用者實際會講的說法並用評估集量 recall。
- deferred loading 是 context 管理不是權限控制，權限一律在 dispatcher 依使用者身分與副作用等級檢查。
- Skills 用三層漸進揭露管理程序知識：索引常駐、本體按需、附加檔案與腳本更需要時才讀，描述就是觸發條件。
- 每次都適用的規則放 system prompt，某類任務的做法放 skill，可執行的動作做成 tool，從互動學到的事實放 memory。
- code-as-action 讓模型寫程式在執行環境中呼叫 tools、跑迴圈與彙總，中間結果留在程式變數裡，只有輸出進入 context。
- 在大量項目的任務上，逐一 tool call 的累計 input 隨項目數平方成長，code-as-action 幾乎和項目數無關，同時大幅減少推論次數與延遲。
- code-as-action 的代價是需要安全的執行環境、模型看不到中間結果、副作用難以逐筆核准，所以寫入 tools 不開放程式呼叫。
- 語言層級的受限執行器只讓行為可預期，不是安全 sandbox；執行模型所寫的程式必須在作業系統或虛擬化層隔離（第 17 章）。
- 三個機制都是以一種成本換另一種成本，選擇時同時量 token、步數與正確率，並用各自的評估集驗證。

## 延伸問答

> [!question]- Q1. Iris 的「每輪依關鍵字挑 10 個 tools」和 tool search 都只送一部分 tools，為什麼前者讓 cache 命中率崩盤、後者不會？
> 差別在於「誰改變了清單、改在哪裡」。每輪動態過濾是 harness 每一輪都重新組一份清單，第 3 輪的 10 個和第 2 輪的 10 個可能只有一半相同，順序也不同。prompt cache 依賴請求開頭的內容逐字相同，清單在前綴的中段就開始不同，從那裡之後的 messages 全部無法重用，等於每一輪都重新付全價。
>
> tool search 的清單只會在模型搜尋命中時，往尾端追加新的定義，既有的部分不重排也不移除，所以前一輪的請求永遠是下一輪請求的前綴，之前快取的內容可以完整重用。動態過濾還有第二個問題：歷史訊息裡引用了上一輪清單中的 tool，這一輪卻消失了，模型會困惑或嘗試呼叫不存在的 tool；deferred loading 一旦載入就留到 session 結束（或 compaction），沒有這個問題。

> [!question]- Q2. 59 個 tools 分屬七個領域，你可以用 tool search，也可以為每個領域做一個 sub-agent，由上層 agent 分派。怎麼選？
> 關鍵是任務會不會跨領域，以及跨領域時需要共享多少 context。如果大多數請求只落在單一領域（查物流、開優惠券），而且領域之間的資料很少交錯，分領域 sub-agent 讓每個 sub-agent 只帶十個以內的 tools，選擇正確率高、清單固定、cache 友善，也方便各團隊各自維護 prompt 與評估。
>
> 但青鳥的營運問題常常跨領域，例如「熱銷商品裡哪些快缺貨了，幫我開一張搭配的優惠券」，同時涉及報表、庫存、優惠券。分成 sub-agent 時，上層要多次交接，每次交接都要重新傳遞上下文，第 20 章會談到這類 multi-agent 的成本可能是單一 agent 的數倍，而且資訊在交接中流失。tool search 讓單一 agent 依需要逐步載入三個領域的 tools，context 連續。實務上兩者可以並用：領域邊界清楚、可以獨立完成的子任務（例如產生一份完整報表）交給 sub-agent，其餘留在主 agent 用 tool search。

> [!question]- Q3. 你在 production 看到：上週物流整合組新增了 12 個 tools，之後「選錯 tool」的比例從 2% 升到 9%。你會怎麼排查？
> 第一步是從 trace 抽樣選錯的案例，整理成「應該呼叫 → 實際呼叫」的混淆對，看錯誤是否集中在新 tools 和既有 tools 之間。如果多數錯誤是新的 `*_track_v2` 和舊的 `*_track` 互相混淆，問題在命名與描述重疊；如果是新 tools 讓搜尋的前幾名被擠掉，問題在 tool search 的排序。
>
> 第二步是把這些案例的使用者查詢加進 tool search 的評估集，重跑 recall@k，確認正確 tool 是根本沒被搜到，還是搜到了但模型選了另一個。前者改描述與 tags，後者要讓相近 tools 的描述清楚寫出差異（「只用於國際件」），或乾脆合併成一個帶參數的 tool。第三步檢查是否有人把新 tools 設成常駐，讓常駐清單變長。修完後，把代表性的案例寫成回歸測試，並在 registry 的審查流程中加入「新 tool 的描述是否和既有 tools 相似度過高」的檢查。

> [!question]- Q4. 估算題：營運助理有 80 個 tools，每份定義平均 400 tokens；平均每個 session 10 次模型呼叫，每天 2 萬個 session。全部載入與 deferred loading（常駐 3 個、每個 session 平均搜尋載入 4 個）各要送出多少 tool 定義 tokens？
> 全部載入時，每次呼叫送 80 × 400 ＝ 32,000 tokens，每個 session 10 次是 320,000，每天 2 萬個 session 是 64 億 tokens，全部花在說明書上。deferred loading 時，常駐 3 個加上 tool_search 約 4 × 400 ＝ 1,600 tokens；假設第 2 次呼叫起多了 4 個搜尋到的定義（1,600 tokens），每個 session 約為 1,600 × 10 ＋ 1,600 × 9 ＝ 30,400 tokens，每天約 6.1 億 tokens，大約是全部載入的十分之一。
>
> prompt caching 會讓兩者的實際金額都低很多，因為 tool 定義在 session 內是穩定前綴，大部分能以快取價格計費；但快取不是免費的，寫入與讀取仍要付費，而且快取有存活時間，session 之間的間隔長了就要重新寫入。更重要的是，金額之外還有兩個快取無法消除的成本：每次呼叫要處理的輸入長度影響延遲，以及 80 個選項對選擇正確率的影響。deferred loading 的代價是每個 session 平均多一兩次搜尋推論，要和這些節省一起放進估算。

> [!question]- Q5. 程式找錯：同事把 deferred loading 改成「搜尋命中後，把已載入集合依名稱排序再送出，比較整齊」。這有什麼問題？
> 排序會破壞「只追加」的不變式。假設第 2 輪已載入 `hct_track`，第 4 輪又搜尋到 `coupon_create`，依名稱排序後 `coupon_create` 會插到 `hct_track` 前面，清單從中段開始和上一輪不同，從插入點之後的前綴全部無法命中快取，包括後面所有的 messages。每多搜尋一次，就可能讓快取失效一次，症狀就是 Iris 那次「選錯少了、帳單沒降」的事故。
>
> 正確的做法是依載入順序追加，在 session 內不重排；如果真的需要整齊（例如方便除錯時閱讀），在 trace 或除錯介面上排序顯示，而不是改變送給模型的內容。測試上可以加一個 assert：每一輪的 tools 名稱清單必須以前一輪的清單開頭，就像 13.9 節第一段程式那樣，這樣任何破壞前綴的修改都會在 CI 被擋下來。

> [!question]- Q6. 面試追問：「你的 agent 會執行模型寫的 Python，怎麼保證安全？」請給出分層的回答。
> 先說清楚原則：任何模型所寫的程式都要假設可能是惡意的，因為模型會讀到不可信的內容（網頁、客訴、文件），可能被 prompt injection 操控。所以安全不能靠「模型不會寫壞程式」，也不能靠語言層級的限制。最外層是隔離：程式在獨立的 sandbox（container、gVisor 或 microVM）中執行，只掛載需要的資料，網路預設不通或只允許特定目的地，設定 CPU、記憶體與 wall-clock 上限，secrets 不進 sandbox（第 17 章）。
>
> 第二層是能力：程式能呼叫的 tools 由 registry 的 code_callable 欄位決定，只開放唯讀 tools，而且這些呼叫回到 harness，經過同一套參數驗證、權限與記錄；有副作用的動作只能走一般 tool call 與人工核准。第三層是輸入輸出：程式輸出有長度上限並檢查是否夾帶不該回傳的資料，內部的每次 tool 呼叫都寫入 trace 以便稽核。最內層才是語言層級的規則（語法 allowlist、行數預算），它的角色是讓常見錯誤提早變成清楚的回饋，而不是安全邊界。

> [!question]- Q7. 營運團隊有三份文件：「退款超過 500 元一律找人核准」「雙 11 促銷設定 SOP」「各物流商的理賠流程」。分別應該放在 system prompt、skill，還是別的地方？
> 「退款超過 500 元一律找人核准」是每次都適用、而且涉及安全的規則，應該寫在 system prompt 讓模型知道，但更重要的是在 harness 的核准政策裡用程式強制（第 21 章）；只寫在 prompt 裡的規則，模型可能忘記或被誘導忽略。規則越關鍵，越不能只靠模型遵守。
>
> 「雙 11 促銷設定 SOP」只有少數對話用得到，內容是流程與規則，是 skill 的典型；描述要寫成「設定滿額折抵、折扣碼等促銷活動時使用」，細節規則放附加檔案。「各物流商的理賠流程」看兩種情況：如果是五家物流商各有固定步驟，做成一個 carrier-claim skill，本體寫共同流程，各家差異放在各自的附加檔案；如果內容是大量條款、店家常問具體條文，則放進知識庫用檢索取用（第 11 章）。判斷的依據是「這是一套要照著做的步驟，還是一堆要查的事實」。

> [!question]- Q8. code-as-action 在什麼情況下反而比多次 tool call 差？有什麼折衷做法？
> 最典型的是每一筆結果都需要模型的語意判斷。例如「把這 40 則客訴裡語氣最激動、可能要求賠償的挑出來」，判斷標準難以寫成程式條件；如果模型寫一段用關鍵字篩選的程式，就會漏掉沒有用到關鍵字的客訴，而且模型看不到原始內容，無法察覺漏掉。其他情況還包括：呼叫次數很少（兩三次，寫程式的成本不划算）、每一步要依上一步結果做截然不同的決定（程式很難預先寫好分支）、以及沒有安全的執行環境。
>
> 折衷做法是讓程式負責機械性的部分、模型負責判斷的部分。例如程式先把 40 則客訴依確定性規則（金額、是否已有退款紀錄）分組，並只 print 每則的摘要或前幾十個字，模型讀這份精簡的清單再做判斷；或者程式呼叫一個由 harness 提供的分類 tool，把語意判斷交給小模型逐筆處理，只回傳分類結果。這和 13.8 節的決策圖一致：先問「中間結果是否需要模型看」，需要的部分保留給模型，不需要的部分交給程式。
