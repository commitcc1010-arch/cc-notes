# 第 37 章　產品化：UX、信任與回饋迴圈

> [!abstract] 本章地圖
> **核心問題**：一個在 eval 上表現良好的 agent，要怎麼變成使用者願意依賴、組織願意導入、公司又賺得到錢的產品？
>
> **你會學到**：
> - 依任務長度與主動權，在 chat、copilot、background、ambient 四種互動模式之間做選擇，並知道每種模式的 UX 責任
> - 設計串流與進度呈現：把 runtime 事件轉成使用者聽得懂的步驟、心跳與狀態機，讓等待變得可以理解
> - 用計畫、引用與 diff 提供「證據式」的可解釋性，並用撤回窗口、補償動作與草稿優先把副作用變得可以後悔
> - 為錯誤、不確定與轉人工設計誠實且可行動的 UX，而不是假裝有信心
> - 把讚／倒讚、使用者修改、撤銷與升級轉人工轉成可用的 eval 案例，同時遵守同意、去識別化與保留期限
> - 比較 per seat、per task、per outcome 與混合定價的單位經濟，算出毛利與損益兩平點，並規劃組織導入的變革管理
>
> **前置知識**：第 1 章（autonomy 等級 L0–L5）、第 5 章（副作用分級 read／write／destructive）、第 15 章（AG-UI 事件串流）、第 21 章（核准卡片與 approval fatigue）、第 22 章（background agent 與補償動作）、第 27 章（eval set 與回歸測試）

## 37.1 故事：技術指標全綠，店家卻把 agent 關掉了

客服 agent 上線第三個月，青鳥科技決定把它從「青鳥自己的客服用」變成「賣給店家用」的產品：數千家網店的店主可以在後台開啟「智慧客服」，讓 agent 直接回覆買家的訂單、物流與退款問題。內部的數字很漂亮：Iris 維護的 eval set 通過率超過九成，第 29 章的 tracing 儀表板上，平均每次對話不到 6 步，成本也在預算內。阿哲挑了 200 家店做 beta，預期一個月後就能全面開放。

六週後，beta 名單裡有將近四成的店家把功能關掉了。阿哲一家一家打電話問原因，聽到的抱怨幾乎沒有一則和「答錯」有關。第一種是「它看起來當機了」：遇到物流商 API 慢的時候，買家盯著一個轉圈圈十幾秒，以為壞了，直接改打電話。第二種是「我不知道它做了什麼」：agent 在 L4 範圍內自動退了一筆 450 元，店主隔天對帳才發現，那張訂單其實已經出貨，錢退了也收不回來。第三種是「它不懂裝懂」：買家問能不能改寄送地址，agent 回了一句含糊的「我無法處理」，既沒說原因，也沒有轉給店主，買家留了一星負評。

同一時間，財務找上門。beta 採用的是傳統 SaaS 的 **per seat**（按帳號數）定價，每個客服帳號每月 1,500 元。小店一個帳號、每月幾百則對話，毛利不錯；但一家大型店家開了 8 個帳號，每月卻有三萬則對話由 agent 處理，光是模型與基礎設施成本就是營收的好幾倍。「我們賣得越好，虧得越多。」財務長把試算表推到阿哲面前。

更諷刺的是，產品裡其實早就有回饋按鈕。資料表裡躺著四萬多筆讚與倒讚，但從來沒有人用過：沒有人知道一個倒讚到底代表答錯、語氣不好，還是買家只是不爽退款被拒。店主在後台手動改寫 agent 草稿的紀錄、撤銷退款的紀錄、買家要求轉真人的紀錄，分散在三個不同的系統裡，沒有一筆被接回 eval set。

老陳聽完阿哲的整理，在白板上畫了一條線：「eval 回答的是『它做得對不對』，產品要回答的是『使用者敢不敢交給它、交給它之後過得好不好、我們做這件事划不划算』。」這一章就是青鳥把 agent 從「能用」變成「產品」的過程：先選對互動模式，再讓進度、決策與副作用都看得見、改得回來；把錯誤與不確定誠實地交代給使用者；把散落的回饋接成資料飛輪；重新設計定價；最後規劃怎麼讓店家的客服團隊真正接受它。

## 37.2 四種互動模式：chat、copilot、background、ambient

產品化的第一個決定不是 UI 長什麼樣子，而是**互動模式**（interaction mode）：使用者和 agent 之間誰先開口、使用者要等多久、結果在哪裡出現。同一個客服 agent 能力，可以包裝成買家面前的聊天視窗，也可以包裝成店主後台的草稿建議，或是每晚自動跑的「異常訂單巡檢」。能力相同，使用者的期待與產品的責任完全不同。

```text
                        誰先開口？
              使用者發起 ◄──────────────────► 事件／排程發起
             ┌──────────────────────────┬──────────────────────────┐
  秒級       │ ① Chat（同步對話）       │ ④ Ambient（背景感知）     │
  使用者     │   買家問「B-1042 到哪了」 │   新進退貨單自動預審，   │
  在等       │   等待：數秒             │   有疑慮才推到店主收件匣 │
             ├──────────────────────────┤   等待：不等，被通知     │
  分鐘到     │ ② Copilot（嵌入工作流）   │                          │
  小時       │   店主回信時 agent 擬草稿 │                          │
  使用者     │   人按送出才算數          │                          │
  不一定在等 ├──────────────────────────┤                          │
             │ ③ Background（委派任務）  │                          │
             │   「整理上月退貨原因報告」│                          │
             │   提交後離開，完成時通知  │                          │
             └──────────────────────────┴──────────────────────────┘
       往右下：agent 的自主時間越長、人越不在場，進度、通知與可撤銷越重要
```

這張圖用兩個軸把四種模式攤開。縱軸是時間尺度：使用者願意等多久。橫軸是主動權：任務是使用者開口發起，還是由事件或排程觸發。左上角的 **chat** 是最熟悉的形態，使用者在畫面前等，所以延遲是第一級需求，任務必須短。**copilot**（副駕駛）把 agent 嵌進使用者既有的工作流程裡，例如店主回覆買家時，agent 在旁邊擬好草稿、附上查到的訂單資訊；決定權永遠在人手上，對應第 1 章的 L1 建議等級。**background agent**（背景 agent）是委派模式：使用者交代一個要跑幾分鐘到幾小時的任務就離開，完成時收到通知，第 22 章講過它在 runtime 上需要 durable execution。右側的 **ambient agent**（環境式 agent）不等使用者開口，而是監聽事件（新訂單、新退貨單、庫存變化），自己判斷要不要處理，只在需要人的時候把一張卡片推到收件匣。

越往右下，人越不在場，agent 在沒人看著的狀態下做事的時間越長。這不代表右下角比較進步，而是代表產品要負的責任不同：chat 的失敗會被使用者立刻看到，ambient 的失敗可能好幾天都沒人發現。所以模式的選擇要回到第 1 章的任務適合度三問：任務越可驗證、越可回復，越適合往右下移。

| 模式 | 典型延遲容忍 | 誰核准副作用 | 最重要的 UX 責任 | 常見失敗 | 青鳥的對應 |
|---|---|---|---|---|---|
| Chat | 數秒 | 使用者或政策即時決定 | 首字延遲、串流、清楚的轉人工 | 轉圈圈太久被當成當機 | 買家端智慧客服 |
| Copilot | 不阻塞使用者 | 人（按下送出） | 建議要好改、好拒絕、不打斷 | 建議太多變成噪音 | 店主後台的回覆草稿 |
| Background | 分鐘到小時 | 預先授權的範圍＋關鍵點核准 | 提交確認、進度查詢、完成通知、可取消 | 跑完才發現方向錯了 | 月度退貨分析報告 |
| Ambient | 無（事件觸發） | 政策；超出範圍推收件匣 | 只在值得時打擾、可以批次處理 | 通知疲勞、靜默失敗 | 退貨單自動預審 |

這張表的第四欄是本章後面各節的索引。chat 需要 37.3 節的串流與進度；copilot 需要 37.4 節的可解釋性，因為人要在幾秒內判斷建議能不能用；background 需要進度與 37.5 節的可撤銷；ambient 需要 37.6 節的「什麼時候該打擾人」。一個常見的誤解是「先做 chat，其他都是 chat 的變形」。實際上 background 和 ambient 需要的是另一套基礎建設：任務佇列、通知、收件匣、任務狀態頁，這些在 chat 產品裡都不存在。另一個誤解是把 ambient 做成「主動傳訊息給使用者的 chat」：如果每個事件都推一則通知，使用者很快就會把通知關掉，和第 21 章的 approval fatigue 是同一種現象。

青鳥最後的決定是：買家端維持 chat，但把「有副作用的退款」從買家端拿掉，改成 ambient 的退貨單預審：agent 先做完查訂單、比對政策、計算金額，把結果整理成一張卡片推給店主，店主一鍵核准或修改。這個改動同時解決了「不知道它做了什麼」與「退了收不回來」兩個抱怨，代價是買家要多等店主一個核准，所以卡片上要顯示「店主通常在幾小時內回覆」，管理買家的期待。

> [!note] 2026 現況
> 截至 2026 年 10 月，四種模式都有公開的代表產品（以下依各產品公開文件與發布說明整理）：一般的 ChatGPT、Claude、Gemini 對話介面是 chat；程式編輯器內的行內補全與編輯建議是 copilot；GitHub Copilot coding agent（文件改稱 Copilot cloud agent）在 GitHub Actions 的臨時環境中執行，每個任務對應一個 branch 與 pull request，是典型的 background 模式，OpenAI Codex 的雲端任務與 Devin 也屬於這一類；各家 deep research 功能在開始前先提出澄清問題，然後在背景執行數分鐘並顯示進度。ambient agent 一詞由 LangChain 在 2025 年初的文章中推廣，搭配「agent inbox」的收件匣介面；這個名稱還不是業界標準用語，不同公司會用 proactive、event-driven 等說法描述類似的概念。

## 37.3 串流與進度：讓等待變得可以理解

使用者對延遲的感受，取決於「我知不知道現在發生什麼事」，而不只是秒數。同樣是 15 秒，看著一個轉圈圈和看著「✓ 查訂單　… 查物流（物流商較慢）」是完全不同的體驗。第 4 章講過 **streaming**（串流）在 loop 層面的意思：文字可以邊產生邊顯示。產品層面的串流範圍更廣，要串的不只是文字，而是整個任務的進度。

這裡要區分三種延遲。**TTFT**（time to first token，首個 token 的延遲）決定使用者多久看到第一個字；**首個有意義回饋的時間**決定使用者多久確定「它在處理我的事」，例如顯示「正在查詢 B-1042」；**完成時間**決定任務何時真正結束。對 agent 來說，後兩者常常差很多，因為中間有好幾輪 tool call，而 tool call 期間模型不會輸出任何給使用者看的文字。如果 UI 只串流文字，使用者就會在每次 tool call 時看到一段沉默。

```text
 Model           Runtime（loom）                        UI（買家看到的）
   │                 │                                      │
   │──tool_use──────►│ step_started(查訂單) ───────────────►│ …查訂單
   │                 │──► get_order ──► 0.7 s               │
   │◄──tool_result───│ step_finished(查訂單) ──────────────►│ ✓查訂單 …查物流
   │──tool_use──────►│ step_started(查物流)                 │
   │                 │──► get_shipment ──► 12 s（物流商慢）  │
   │                 │   （5 秒沒有新事件）── heartbeat ────►│ 仍在查物流（已 8 秒）
   │◄──tool_result───│ step_finished(查物流) ──────────────►│ ✓查物流
   │──text delta────►│ text_delta ─────────────────────────►│ 「B-1042 已出貨…」逐字出現
   │──end_turn──────►│ run_finished(status=done) ──────────►│ 顯示回饋按鈕
```

這張時序圖有三層。最左邊是模型，它只會產生 tool call 與文字；中間是 runtime 加上一層轉譯：第 24 章 `loom.runtime` 送出的串流事件（`tool_started`、`tool_finished`、`model_delta`）被翻譯成**語意事件**（semantic event），例如 `step_started(查訂單)`，這是第 15 章 AG-UI 事件模型與第 24 章 event stream 在產品上的用途；最右邊是 UI，它只認得這些語意事件，不需要知道 token 或 tool schema。值得注意的是中段：物流商 API 花了 12 秒，這段期間沒有任何新事件，所以 runtime（或 UI 本身）要在沉默超過門檻時送出 **heartbeat**（心跳）訊息，說明還在做什麼、做了多久。最後的 `run_finished` 帶著 status，UI 才知道要顯示回饋按鈕、轉人工按鈕還是錯誤訊息。

把進度翻譯成人話要有分寸。原則一：步驟名稱用使用者的語言（「查物流」），不用 tool 名稱（`get_shipment`）。原則二：只顯示使用者在意的步驟，內部的重試、參數修正、context 壓縮不必顯示，但要算進時間。原則三：不要顯示原始的推理內容當作進度。推理模型的思考內容可能很長、可能包含被丟棄的假設，部分供應商也只提供摘要版本；把它直接串給買家，看起來像在偷看草稿，還可能洩漏 system prompt 的內容。給內部人員除錯的 trace 介面可以顯示，給終端使用者的介面不應該。

下面這段程式示範 UI 如何從事件算出進度列，並在沉默時加上心跳說明。它只看事件，不看任何模型內部狀態，這正是「語意事件」這一層的價值：同一份事件可以同時驅動買家的聊天視窗、店主的任務頁與內部的監控面板。

```python
from __future__ import annotations

# agent runtime 送出的事件（時間單位：秒）。UI 不看 token，只看這些「使用者聽得懂」的事件
EVENTS = [
    (0.0, "plan", ["查訂單", "查物流", "比對退貨政策", "擬回覆"]),
    (0.4, "step_started", "查訂單"),
    (1.1, "step_finished", "查訂單"),
    (1.2, "step_started", "查物流"),
    (14.0, "step_finished", "查物流"),        # 物流商 API 很慢：中間 12 秒沒有任何事件
    (14.1, "step_started", "比對退貨政策"),
    (15.0, "step_finished", "比對退貨政策"),
    (15.1, "step_started", "擬回覆"),
    (15.3, "text_delta", "B-1042 已出貨"),
]
HEARTBEAT_AFTER = 5.0   # 超過 5 秒沒有新事件，就主動說明「還在做什麼、做了多久」


def render(now: float) -> str:
    seen = [e for e in EVENTS if e[0] <= now]
    plan = next(p for _t, k, p in seen if k == "plan")
    done = [p for _t, k, p in seen if k == "step_finished"]
    running = [(t, p) for t, k, p in seen if k == "step_started" and p not in done]
    line = f"[{len(done)}/{len(plan)}] " + " ".join(("✓" if s in done else "…" if any(s == p for _t, p in running) else "○") + s
                                                    for s in plan)
    if any(k == "text_delta" for _t, k, _p in seen):
        return line + "  ｜回覆串流中"
    last_event = seen[-1][0]
    if running and now - last_event > HEARTBEAT_AFTER:
        started, step = running[-1]
        line += f"  ｜仍在{step}（已 {now - started:.0f} 秒，通常 3 秒內，外部系統較慢）"
    return line


for t in (0.5, 3.0, 9.0, 13.0, 15.5):
    print(f"t={t:>4}s  {render(t)}")
assert "仍在查物流" in render(9.0) and "仍在" not in render(3.0)
```

```text
t= 0.5s  [0/4] …查訂單 ○查物流 ○比對退貨政策 ○擬回覆
t= 3.0s  [1/4] ✓查訂單 …查物流 ○比對退貨政策 ○擬回覆
t= 9.0s  [1/4] ✓查訂單 …查物流 ○比對退貨政策 ○擬回覆  ｜仍在查物流（已 8 秒，通常 3 秒內，外部系統較慢）
t=13.0s  [1/4] ✓查訂單 …查物流 ○比對退貨政策 ○擬回覆  ｜仍在查物流（已 12 秒，通常 3 秒內，外部系統較慢）
t=15.5s  [3/4] ✓查訂單 ✓查物流 ✓比對退貨政策 …擬回覆  ｜回覆串流中
```

t=0.5 秒時，計畫已經出現，使用者馬上知道接下來有四步，這比任何轉圈圈都更能降低焦慮。t=3 秒查訂單完成、查物流進行中，此時距離上一個事件不到 5 秒，不加說明。t=9 秒與 t=13 秒是關鍵：物流商很慢，超過 5 秒沒有新事件，進度列加上「仍在查物流（已 8 秒，通常 3 秒內，外部系統較慢）」。這句話同時做了三件事：證明系統沒當機、說明慢的原因不在使用者、給出正常的參考時間。t=15.5 秒開始串流回覆文字，進度列改成「回覆串流中」。assert 鎖住了心跳只在沉默超過門檻時出現，避免畫面一直跳說明。

長任務還需要一個明確的**任務狀態機**。chat 的狀態只有「回答中」與「回答完」；background 與 ambient 任務會經過排隊、執行、等待使用者補資料、等待核准、完成、失敗與取消，每個狀態在 UI 上都要有對應的呈現與可用動作。

```text
              submit
                │
                ▼
           ┌─────────┐  worker 取走   ┌─────────┐  需要補資料   ┌────────────────┐
           │ queued  │───────────────►│ running │──────────────►│ input_required │
           └─────────┘                └─────────┘◄──────────────└────────────────┘
               │ cancel                │  │  │      使用者回覆
               ▼                       │  │  │ 需要核准       ┌────────────────┐
           ┌──────────┐◄── cancel ─────┘  │  └───────────────►│ needs_approval │
           │cancelled │                   │◄──────────────────└────────────────┘
           └──────────┘                   │       核准／修改後核准       │ 拒絕
                       ┌──────────────────┴─────┐                        ▼
                       ▼                        ▼                  ┌──────────┐
                  ┌─────────┐              ┌─────────┐             │ rejected │
                  │  done   │              │ failed  │             └──────────┘
                  └─────────┘              └─────────┘
          每個狀態都要回答三件事：顯示什麼、使用者能做什麼、是否通知
```

這張狀態機和第 15 章 A2A 的 task 生命週期刻意相近，因為它們描述的是同一件事的兩個面向：A2A 是 agent 之間的協定狀態，這裡是給人看的產品狀態。兩個中斷態 `input_required` 與 `needs_approval` 是 background 任務最容易做壞的地方：如果任務停在這裡卻沒有通知使用者，它會永遠卡住，使用者還以為 agent 在努力。所以進入中斷態時一定要通知，而且通知要帶著「要你做什麼」的完整資訊，讓使用者不必點進去才知道。`cancelled` 要能從 `queued` 與 `running` 進入，從 `running` 取消時，已經產生的副作用要依 37.5 節的方式處理。`done` 與 `failed` 都是終態，但 `failed` 一定要附上「下一步可以怎麼做」，這是 37.6 節的主題。

> [!warning] 常見誤解
> 「串流越細越好，最好每個 token 都即時推給使用者。」對文字回答是對的，對 tool 參數與中間決策則不然。第 4 章說過 tool 參數要完整才執行；同理，「我要退款 450 元」這類內容在模型還沒確定之前就顯示給使用者，可能在下一秒被推翻，反而損害信任。可以串流的是「已經發生的事實」（查完了什麼、正在等什麼）與「已確定要輸出的文字」，不要串流「還在變動的決定」。

## 37.4 可解釋性：給證據，不給故事

使用者信任一個 agent，不是因為它說得頭頭是道，而是因為使用者能用很少的力氣確認它說的是真的。這一節的原則是：**可解釋性要給證據，不給故事**。故事是模型對自己做了什麼的敘述（「我已仔細檢查了您的訂單並確認符合退款政策」），證據是使用者可以獨立核對的東西：它打算怎麼做（計畫）、它根據什麼（引用）、它改了什麼（diff）。

為什麼不能只靠模型的說明？第一，模型的說明是生成出來的，它可能和實際做了什麼不一致。Anthropic 在 2025 年發表的研究顯示，推理模型在思考內容中並不總是承認自己用了某個提示，也就是說，思考內容不一定忠實反映模型的決策過程。第二，第 21 章談過的 OWASP ASI09 Human-Agent Trust Exploitation：說明本身可能被 tool 輸出裡的惡意內容操控。第三，說明讀起來很花力氣，使用者很快就會只看第一句。證據則可以由確定性程式直接從 trace 渲染，既不會說謊，也可以設計成一眼看懂的格式。

```text
 ┌─ 退貨預審 RV-2291 ─────────────────────────────── 待店主核准 ─┐
 │ 計畫（agent 執行前提出，已完成 3/4）                           │
 │   ✓ 1 查訂單 B-1077            ✓ 2 查物流：已於 9/28 簽收     │
 │   ✓ 3 比對退貨政策 §2.1         ○ 4 建立退貨單（等你核准）     │
 │                                                                │
 │ 依據（點擊可展開原文）                                         │
 │   [1] 訂單系統：B-1077 實付 NT$ 450，簽收 9/28                 │
 │   [2] 店家退貨政策 §2.1「簽收 7 日內可退，商品須未使用」       │
 │   [3] 買家訊息：「尺寸不合，吊牌還在」                         │
 │                                                                │
 │ 將要執行的變更（由參數直接渲染）                               │
 │   退貨單   + 新增 R-? 訂單 B-1077，退款 NT$ 450，原路退回      │
 │   訂單狀態   delivered → return_requested                      │
 │                                                                │
 │ ┄ AI 說明（可能有誤）：符合 7 日鑑賞期，建議同意 [1][2][3] ┄   │
 │ [ 核准 ]  [ 修改金額 ]  [ 拒絕並回覆買家 ]   [ 查看完整紀錄 ]  │
 └────────────────────────────────────────────────────────────────┘
```

這張卡片把三種證據由上而下排列。計畫區顯示 agent 打算走的步驟與目前進度，最後一步停在「等你核准」，店主馬上知道自己在流程中的位置。依據區是**引用**（citation）：每一個判斷都對回一個可以點開的原始來源，訂單資料來自系統、政策來自店家自己設定的條文、買家說法來自原始訊息。變更區是 **diff**：用「之前 → 之後」的形式顯示實際要改的資料，由 tool call 的參數直接渲染，而不是讓模型描述。最下面才是 AI 的說明，用虛線隔開並標明可能有誤，而且說明本身也帶著引用編號，店主可以檢查它引用的東西是否真的支持結論。

這三種證據各自回答不同的問題，在不同產品中的形態也不同。

| 證據 | 回答的問題 | 客服產品 | Coding agent | Research agent | 常見陷阱 |
|---|---|---|---|---|---|
| 計畫 | 它打算做什麼？方向對嗎？ | 步驟清單，執行前可編輯 | 待辦清單、先 plan 後實作 | 研究大綱與要回答的子問題 | 計畫寫完就不更新，和實際脫節 |
| 引用 | 它根據什麼？來源可信嗎？ | 訂單欄位、政策條文 | 讀過的檔案與行號 | 網頁、文件段落 | 引用存在但不支持結論 |
| Diff | 它改了什麼？影響多大？ | 訂單狀態、退款金額 | 程式碼 diff 與測試結果 | 報告版本差異 | 只顯示摘要，沒有實際變更 |
| 紀錄 | 出事時能重建嗎？ | 完整對話與 trajectory | session log、指令輸出 | 搜尋與閱讀紀錄 | 只存在內部，使用者看不到 |

表中的「常見陷阱」值得多說一句。計畫的陷阱是**計畫漂移**：agent 執行到一半改變做法，卻沒有更新顯示的計畫，使用者看到的是過時的版本。解法是讓計畫成為 runtime 的狀態而不是一段文字，每個 step 事件都對回計畫中的項目，對不上的就標示「計畫外的步驟」。引用的陷阱是**引用不支持結論**：模型附上了真實存在的來源，但來源內容其實沒有說它聲稱的事。第 11 章講過 grounding 檢查，產品層的對策是讓引用可以一鍵展開原文，並在 eval 中加入「引用是否支持該句」的檢查。diff 的陷阱是只給摘要：「已修正退款金額」不是 diff，「NT$ 4,500 → NT$ 450」才是。

可解釋性有成本，所以要分級提供。copilot 模式下，使用者每天要處理幾十張卡片，卡片的預設狀態只能顯示最關鍵的事實（金額、動作、可否撤回），其餘收在「展開」裡；background 模式下，使用者回來看結果時有比較多耐心，可以顯示完整的計畫與引用。判斷標準是第 21 章的風險分級：動作越不可逆、金額越大，預設展開的證據越多。

## 37.5 可撤銷：把不可逆的動作變得可以後悔

信任的另一半是「萬一它錯了，我能不能收回來」。如果每個動作都能便宜地撤銷，使用者就願意讓 agent 多做一點；如果每個動作都覆水難收，使用者只會要求每一步都核准，最後陷入 approval fatigue。第 1 章的任務適合度三問之一就是「可回復」，這一節要談的是：產品設計可以主動把不可回復的動作變得可以回復。

第 5 章把副作用分成 read、write、destructive 三級。從產品角度，可以再細分出四種撤銷機制，依可靠程度由高到低排列。**草稿優先**（draft-first）：agent 只產生草稿，真正的動作由人觸發，例如 copilot 擬的回信要店主按下送出，這是最徹底的可撤銷，因為什麼都還沒發生。**撤回窗口**（undo window）：動作提交後延遲一小段時間才真正執行，窗口內撤回等於沒發生，Gmail 的「復原傳送」就是這種設計。**補償動作**（compensating action）：動作已經執行，但有一個對應的反向動作可以抵銷，例如發出的優惠券可以作廢，這是第 22 章 saga 的概念。**不可撤銷**：退款匯出、對外寄送的實體包裹、已讀的訊息，只能靠事前核准與事後人工處理。

```text
 時間 ─────────────────────────────────────────────────────────────►
 submit           窗口結束（例如 30 秒）
   │◄──── 撤回窗口 ────►│
   │  pending           │ executed ──────────────────────────────────
   │                    │
   │  undo → cancelled  │  undo → 有補償動作？
   │  （沒有任何副作用） │          ├─ 是 → compensated（作廢優惠券）
   │                    │          └─ 否 → 轉人工＋如實告知使用者
   │                    │
 UI：「已排程，30 秒內可撤回 [撤回]」  UI：「已執行。[作廢] 或 [聯絡店主]」
```

這張時間軸說明同一個「撤回」按鈕在不同時間點的意義。窗口內，撤回只是把佇列中的動作取消，系統不需要做任何補救；窗口結束後，撤回變成另一個動作，可能是補償，也可能根本做不到。UI 必須如實反映這個差別：窗口內按鈕寫「撤回」，窗口後寫「作廢優惠券」或「聯絡店主」，而不是用同一個按鈕假裝什麼都能復原。下面的程式用模擬時鐘實作這個佇列。

```python
from __future__ import annotations

from dataclasses import dataclass, field


@dataclass
class PendingAction:
    action_id: str
    kind: str                 # send_message｜issue_coupon｜refund
    execute_at: int           # 模擬時鐘（秒）
    state: str = "pending"    # pending → executed｜cancelled；executed → compensated
    log: list[str] = field(default_factory=list)


COMPENSATION = {"issue_coupon": "revoke_coupon", "send_message": None, "refund": None}  # None：做了就收不回


class ActionQueue:
    """有撤回窗口的動作佇列：時間到才真正執行，窗口內撤回等於什麼都沒發生。"""

    def __init__(self, window: int):
        self.window, self.now, self.items = window, 0, {}

    def submit(self, action_id: str, kind: str) -> None:
        self.items[action_id] = PendingAction(action_id, kind, self.now + self.window)

    def tick(self, seconds: int) -> None:
        self.now += seconds
        for a in self.items.values():
            if a.state == "pending" and self.now >= a.execute_at:
                a.state = "executed"
                a.log.append(f"t={a.execute_at} 執行")

    def undo(self, action_id: str) -> str:
        a = self.items[action_id]
        if a.state == "pending":
            a.state = "cancelled"
            return "窗口內撤回：沒有任何副作用發生"
        if a.state == "executed" and COMPENSATION[a.kind]:
            a.state = "compensated"
            return f"已執行，改做補償動作 {COMPENSATION[a.kind]}"
        return "已執行且不可補償：轉人工處理，並告知使用者實情"


q = ActionQueue(window=30)
q.submit("m1", "send_message")
q.submit("c1", "issue_coupon")
q.tick(10)
print("t=10 撤回 m1 →", q.undo("m1"))
q.submit("r1", "refund")
q.tick(40)
print("t=50 撤回 c1 →", q.undo("c1"))
print("t=50 撤回 r1 →", q.undo("r1"))
print({k: v.state for k, v in q.items.items()})
assert [v.state for v in q.items.values()] == ["cancelled", "compensated", "executed"]
```

```text
t=10 撤回 m1 → 窗口內撤回：沒有任何副作用發生
t=50 撤回 c1 → 已執行，改做補償動作 revoke_coupon
t=50 撤回 r1 → 已執行且不可補償：轉人工處理，並告知使用者實情
{'m1': 'cancelled', 'c1': 'compensated', 'r1': 'executed'}
```

訊息 m1 在第 10 秒撤回，仍在 30 秒窗口內，狀態變成 cancelled，買家永遠不會收到。優惠券 c1 在第 0 秒提交、第 30 秒執行，第 50 秒撤回時已經執行，但它有對應的補償動作 `revoke_coupon`，所以狀態變成 compensated。退款 r1 也已經執行，而退款在青鳥的設定裡不可補償，撤回只能轉人工，並且要告訴使用者實情，而不是顯示「已撤回」。這段程式刻意把 `COMPENSATION` 寫成一張表：每加一個有副作用的 tool，就必須回答「它的補償動作是什麼」，答不出來的就是不可撤銷，要走事前核准。

撤回窗口不是免費的。它延後了動作，對「買家要立刻收到回覆」的場景不適用；它也讓系統多了一個「已提交但未執行」的中間狀態，worker 在窗口中途重啟時，必須從 durable 的佇列恢復，否則會發生「使用者以為撤回了，其實已經送出」或反過來的情況。所以撤回窗口最適合「延遲幾十秒無妨，但錯了代價很高」的動作：對外寄信、批次發優惠券、修改商品價格。青鳥的做法是：小額退款不再即時執行，而是排進一個 10 分鐘的窗口，店主後台會出現「10 分鐘後退款 NT$ 450 給 B-1077，[取消]」的通知；窗口結束才呼叫金流。

> [!tip]
> 設計可撤銷性時，先列出每個有副作用的 tool，填一張四欄表：草稿優先可不可行？可接受的延遲窗口多長？補償動作是什麼？都不行時誰核准？這張表會直接決定第 21 章 approval policy 的內容，也會決定 37.9 節的成本：每一個需要人核准的動作，都是一筆人力成本。

## 37.6 錯誤與不確定時的 UX

agent 一定會失敗，產品的品質很大一部分取決於失敗時使用者經歷了什麼。故事裡那句「我無法處理」同時犯了三個錯：沒說原因、沒給下一步、沒有把對話交給能處理的人。好的錯誤 UX 要回答三個問題：發生了什麼（用使用者的語言）、這是誰的問題（使用者、店家政策、還是系統故障）、現在可以怎麼做。

失敗可以依「誰能修好它」分類，這和第 4 章判斷 tool 錯誤要不要回填給模型的標準是同一個邏輯，只是對象從模型換成了人。使用者能修好的（訂單編號打錯、缺少照片），要明確請使用者補資料，並且保留已經做完的部分，不要讓使用者從頭說起。店家政策不允許的（已超過退貨期限），要說明政策並引用條文，必要時提供例外申請管道。系統暫時故障的（物流商 API 逾時），要誠實說明，提供「稍後通知你」或轉人工的選項。agent 能力範圍外的（改寄送地址），要直接轉人工，而不是含糊地拒絕。

```text
 agent 準備回覆
     │
     ▼
 有足夠證據支持答案？ ── 否 ──► 缺的是使用者知道的資訊？ ── 是 ──► 追問（一次問完，附範例）
     │ 是                              │ 否
     ▼                                 ▼
 屬於能力與政策範圍？ ── 否 ───────► 轉人工（warm handoff：附摘要、已查到的資料）
     │ 是
     ▼
 動作可撤銷或金額在邊界內？ ── 否 ──► 提出計畫，等待核准（第 21 章）
     │ 是
     ▼
 執行並回覆，附依據；提供「這不對」與「找真人」的出口
```

這張決策流程的每一個「否」都對應一種誠實的 UX。第一個判斷是證據：agent 是否真的查到了支持答案的資料，而不是憑印象回答。證據不足時，先看缺的是不是使用者能提供的資訊，是的話追問，而且要一次問完，例如「請提供訂單編號（B 開頭的 4 位數字）與商品照片」，不要每輪問一個。第二個判斷是範圍：不在能力或政策範圍內的請求要轉人工。這裡的關鍵是 **warm handoff**（溫轉接）：轉給真人時附上對話摘要、已查到的訂單資料與 agent 判斷卡住的原因，真人接手時不必重問；相對的 cold handoff 只是把使用者丟進客服佇列。第三個判斷是風險：超出邊界的動作改成提出計畫等待核准。最後即使一切順利，也要在回覆中保留兩個出口：「這不對」與「找真人」，讓使用者永遠有退路。

「不確定」是錯誤 UX 中最難的部分。直覺的做法是讓模型輸出一個信心分數，顯示「信心 87%」。這通常是壞主意：研究普遍發現，模型口頭表達的信心與實際正確率不一定一致，而使用者看到精確的數字，會以為它經過校準。比較可靠的做法是用**可觀察的訊號**決定行為，而不是請模型自評：有沒有查到資料、資料之間是否矛盾、問題是否落在 eval 覆蓋過的意圖、使用者是否已經重問兩次。這些訊號決定 agent 要直接回答、加上保留語氣、追問，還是轉人工。呈現給使用者的則是具體的保留理由，例如「物流商的最新紀錄是兩天前，實際位置可能已更新」，而不是一個百分比。

| 情況 | 不好的回應 | 好的回應 | 背後的機制 |
|---|---|---|---|
| 證據不足 | 編一個看似合理的物流狀態 | 「查不到 B-1O42，請確認是數字 0 還是字母 O」 | tool 查無資料時禁止臆測，改為追問 |
| 超出範圍 | 「我無法處理」 | 「改地址需要店主確認，已轉給店主並附上你的新地址」 | 能力範圍清單＋warm handoff |
| 系統故障 | 轉圈圈 30 秒後空白 | 「物流商系統暫時沒有回應，10 分鐘內查到會通知你」 | 逾時分類＋background 補查 |
| 政策拒絕 | 「不符合退款資格」 | 「簽收已超過 7 日（政策 §2.1），可申請例外審核」 | 引用政策條文＋例外管道 |
| 使用者連續重問 | 重複相同回答 | 「看來我的回答沒有幫上忙，要幫你轉給真人嗎？」 | 重問偵測當作不確定訊號 |

這張表的最後一欄說明了一件事：好的錯誤 UX 幾乎都不是 prompt 寫得好就能得到的，而是 harness 有對應的機制。「查無資料時禁止臆測」需要 tool 回傳明確的空結果與第 6 章的指令；「warm handoff」需要轉人工的 tool 能帶摘要；「10 分鐘內通知你」需要 background 任務與通知管道。青鳥修掉「我無法處理」的方式，是加了一個 `handoff_to_merchant` tool，並在 system prompt 中列出能力範圍外的請求類型，eval set 裡也加上了「改地址應該轉店主」的案例，這些案例正是從下一節的回饋資料中產生的。

## 37.7 回饋收集與資料飛輪

青鳥那四萬筆沒人用的讚與倒讚，問題不在數量，而在於它們沒有被設計成可以使用的資料。**回饋迴圈**（feedback loop）指的是：從使用者的行為中收集訊號，判斷 agent 哪裡做錯，把錯誤轉成改進的依據，改完之後再驗證。當這個迴圈能持續轉動，使用越多、資料越多、產品越好、使用又越多，就是常說的**資料飛輪**（data flywheel）。

訊號分成三類，強度與偏誤各不相同。**明確回饋**（explicit feedback）是使用者主動表態：讚、倒讚、選一個倒讚原因、寫一句評語。它意圖清楚，但很稀少，而且有選擇偏誤：會按的人往往是特別滿意或特別生氣的人。**隱含回饋**（implicit feedback）是從行為推斷的：店主修改了 agent 的草稿、按了重新生成、撤銷了 agent 的動作、買家要求轉真人、對話中途離開。它量大、比較誠實，但需要詮釋：草稿被改可能是答錯，也可能只是店主習慣加一句問候語。**結果訊號**（outcome signal）是事後才知道的業務結果：退貨單最後是否成立、買家 24 小時內是否又來問同一件事、這筆退款後來有沒有被店家追回。它最接近真正的品質，但來得慢，也最難歸因到某一次對話。

| 訊號 | 類型 | 強度 | 主要偏誤或雜訊 | 可以轉成的 eval 案例 |
|---|---|---|---|---|
| 讚 | 明確 | 弱正向 | 只代表「當下滿意」，可能之後被撤銷 | 「保持現有行為」的回歸樣本 |
| 倒讚＋原因 | 明確 | 中等負向 | 稀少；原因可能是對政策不滿而非 agent 錯 | 送人工標註後成為案例 |
| 修改草稿 | 隱含 | 強（若改動大） | 小幅修改常只是風格偏好 | 以修改後版本當參考答案 |
| 撤銷動作 | 隱含 | 很強負向 | 少數是使用者改變主意 | 「不得再這樣做」的檢查 |
| 升級轉人工 | 隱含 | 中等 | 有些使用者一開始就只想找真人 | 送人工標註：該處理還是該更早轉 |
| 24 小時內重問 | 結果 | 中等負向 | 可能是新問題 | 抽樣檢查後加入 |

這張表的第三、四欄是設計回饋系統的核心：每一種訊號都要有詮釋規則。最重要的一條是**行為優先於表態**：同一則回答，買家當下按了讚，店主隔天卻撤銷了那筆退款，這則回答就是錯的，讚要被覆蓋。第二條是**過濾雜訊**：只改了一個標點的修改不是品質訊號；使用者在對話第一句就說「我要找真人」，轉人工不代表 agent 失敗。第三條是**不是每個訊號都能自動變成標準答案**：撤銷與大幅修改可以直接產生檢查條件，但倒讚與轉人工只能告訴你「這裡有問題」，正確行為是什麼，要由人判斷。

```text
 production trace ──┐
                    ├─► 回饋事件（trace_id、種類、時間、內容）
 使用者行為 ────────┘        │
                             ▼
                  ┌─ 同意與去識別化閘門 ─┐  沒同意 → 丟棄；PII → 遮蔽
                  └──────────┬───────────┘
                             ▼
                  逐 trace 合成標籤（行為 > 表態）
                             │
              ┌──────────────┼───────────────┬───────────────┐
              ▼              ▼               ▼               ▼
         must_not        reference      needs_label     keep_working
        （撤銷）        （大幅修改）    （倒讚、轉人工）    （讚）
              │              │               │               │
              │              │          人工標註佇列         │
              └──────┬───────┴───────────────┘               │
                     ▼                                       ▼
          依意圖與失敗類型去重、排序 ──► eval set ◄── 抽樣的正向回歸樣本
                                           │
                                           ▼
                     改 prompt／tool／政策 ──► 回歸測試（CI gate）──► canary 上線
                                                                         │
                                         新的 production trace ◄─────────┘
```

這張資料流是本章「動手做」第一段程式的藍圖。左上角的兩個來源匯成統一格式的**回饋事件**，每一筆都帶著 `trace_id`，因為沒有 trace 的回饋無法使用：你不知道 agent 當時看到什麼、說了什麼。接著是同意與去識別化閘門，下一節詳談。通過閘門的事件依 trace 合成一個標籤，分成四個桶：撤銷產生 must_not 檢查，大幅修改產生參考答案，倒讚與轉人工進人工標註佇列，讚成為正向回歸樣本。然後依「意圖 × 失敗類型」去重：同樣是「對已出貨訂單直接退款」，十筆撤銷只需要一個案例，但要記住它出現了十次，作為排序依據。最後案例進入第 27 章的 eval set，任何 prompt、tool 或模型的變更都要先通過回歸測試，再經第 36 章的 canary 上線，新的 trace 又回到起點。

這個迴圈裡最容易被省略的一步，是把案例的**環境狀態**一起保存下來。「B-1042 可以退款嗎」本身不是一個完整的 eval 案例，因為正確答案取決於 B-1042 當時的狀態：已出貨就不能退。如果只存使用者的那句話，日後重跑時訂單狀態已經變了，案例就失去意義。實務上要從 trace 中擷取當時 tool 回傳的結果，作為案例的 fixture（固定的測試資料），讓第 27 章的 eval harness 用假的 tool 重現當時的環境。

> [!warning] 常見誤解
> 「回饋資料夠多，就拿去 fine-tune。」回饋最直接、最安全的用途是 eval，而不是訓練。拿來訓練需要更強的同意、更嚴格的去識別化，而且會把使用者的偏誤（例如店主偏好的語氣、對政策的不滿）一起學進模型。先讓回饋變成可重跑的 eval 案例，確認改進真的有效；要不要用於訓練，是另一個需要法務與資安參與的決定，第 30 章談 fine-tuning 時也強調過訓練資料的來源與清洗。

## 37.8 隱私與同意：飛輪的燃料不是免費的

回饋資料的本質是使用者的對話，裡面有姓名、電話、地址、訂單內容，有時還有買家的抱怨與私事。青鳥的情況更複雜：資料的主體是買家，但和青鳥簽約的是店家。所以青鳥要回答的不只是「能不能用」，而是「誰同意了、同意做什麼用途、用多久、怎麼刪」。

第一個原則是**用途分級**。同一筆對話，用於「即時提供服務」、用於「除錯與事故調查」、用於「建立 eval 案例改善品質」、用於「訓練模型」，是四種不同的用途，需要的同意與保護等級遞增。合約與隱私權政策要逐項寫清楚，產品後台也要讓店家能分別開關。青鳥的做法是：服務與除錯是合約的基本範圍；eval 用途預設關閉，店家在後台勾選同意後才啟用；訓練用途目前不提供。動手做的程式中，沒有同意的 shop-c 連去識別化都不做，直接在閘門外丟棄，就是這個原則的實作：沒同意的資料不應該存在於任何下游資料集中，即使已經遮蔽。

第二個原則是**資料最小化與去識別化**。eval 案例需要的是「問題的形狀」，不是買家的身分。電話、email、地址、姓名在進入資料集之前就要遮蔽成佔位符；訂單編號這類半識別資訊可以換成一致的假編號，保留案例之間的關聯。遮蔽要用確定性規則加上抽查，不能只靠模型判斷，而且要記得遮蔽會改變案例：如果問題本身就是「我的 email 打錯了」，遮蔽後的案例可能就測不到原本的錯誤，這類案例要人工改寫。

第三個原則是**保留期限與刪除權**。第 12 章談過 memory 的刪除權，回饋資料也一樣：買家要求刪除個資時，從其對話衍生出的 eval 案例要能追溯並移除。這就是為什麼程式中的 EvalCase 保留了 `sources` 欄位：每個案例都記得自己來自哪些 trace，刪除時才找得到。此外，eval set 中的案例也要有保留期限，過期的案例要重新確認仍有同意，或者改寫成不含原始資料的合成案例。

第四個原則是**租戶隔離**。不同店家的資料不能出現在彼此的 eval 結果或範例中，跨租戶的共用 eval set 只能放合成資料或經過明確授權的去識別化案例。這和第 33 章的多租戶隔離是同一件事在資料管線上的延伸。

> [!note] 2026 現況
> 截至 2026 年 10 月，主要模型供應商的商用 API 條款通常預設不使用客戶的 API 資料訓練模型，但消費者產品的資料政策不同，且過去幾年調整過不只一次；導入前要以當時的條款與資料處理協議（DPA）為準。法規面，歐盟 GDPR 對個人資料的用途限制、資料最小化與刪除權仍是設計回饋系統的基準；EU AI Act 第 50 條的透明義務（例如讓人知道自己在和 AI 互動）自 2026 年 8 月起適用，第 34 章有概念層級的整理。主流的 observability 與 eval 平台（如 LangSmith、Langfuse、Braintrust）都提供把使用者回饋掛在 trace 上、再加入 dataset 的流程，具體功能以各平台文件為準。

## 37.9 定價與單位經濟

傳統 SaaS 的邊際成本接近零：多一個使用者登入，伺服器成本幾乎不變，所以按帳號收費、毛利很高。agent 產品不一樣，每一次任務都要付推理費用，而且成本隨任務的複雜度大幅波動。第 4 章算過，agent 每一步都要重送完整歷史，累計 input tokens 接近步數的平方成長；一個 9 步的對話，成本可能是 5 步對話的兩倍以上。這讓定價從「行銷決定」變成「架構決定」：你選的定價模式，決定了誰承擔成本的波動。

**單位經濟**（unit economics）是用「一個單位」來看收入與成本：一次對話、一個成功解決的問題、一個客戶一個月。最核心的兩個數字是**毛利率**（gross margin）＝（營收 − 銷貨成本）÷ 營收，以及**損益兩平點**（break-even）：收入剛好抵掉成本的那個量。agent 產品的銷貨成本（COGS，cost of goods sold，直接因提供服務而產生的成本）通常包括：模型推理費用、tool 與外部 API 費用、sandbox 與基礎設施、人工品管抽檢，以及由產品方負責的人工處理（例如人工核准或轉人工的成本）。研發團隊的薪資不算在毛利裡，而是在損益兩平的固定成本中。

```text
 一次對話的成本堆疊（青鳥中店，假設值，單位：新台幣）

 ┌──────────────────────────────┐
 │ 人工品管抽檢 1% × 20 = 0.20   │ ◄── 人力成本，隨品質要求變動
 ├──────────────────────────────┤
 │ tool 與基礎設施      0.40     │ ◄── 外部 API、session store、tracing
 ├──────────────────────────────┤
 │ output tokens        0.54     │ ◄── 步數 × 每步輸出
 ├──────────────────────────────┤
 │ input tokens（含快取）0.60    │ ◄── 步數的平方效應；快取命中率是最大槓桿
 └──────────────────────────────┘
   合計約 1.74 元／次對話；resolution rate 65% → 每次「成功解決」的成本約 2.7 元
```

這張成本堆疊有兩個重點。第一，最下層的 input tokens 對步數與快取命中率最敏感：步數增加時它接近平方成長，第 9 章的 cache-friendly 版面能把它壓低一大截。第二，最右下角那行換算才是定價的關鍵：如果你按「成功解決」收費，失敗的對話也要付成本，所以每次成功的真實成本是每次對話成本除以成功率。成功率從 65% 掉到 40%，成本就變成原來的 1.6 倍。

四種主流的定價模式，差別在於「收入跟著什麼走」，因此也決定了成本波動由誰承擔。

| 定價模式 | 收入跟著什麼走 | 成本波動由誰承擔 | 對客戶的吸引力 | 主要風險 |
|---|---|---|---|---|
| Per seat（按帳號） | 帳號數 | 供應商 | 好預算、好採購 | 重度使用者虧錢；agent 越成功、需要的人越少，帳號數反而下降 |
| Per task／usage（按次或按量） | 對話數、token、credits | 客戶 | 用多少付多少 | 帳單難預測；客戶為了省錢而少用 |
| Per outcome（按結果） | 成功解決的數量 | 雙方（供應商承擔失敗成本） | 只為價值付費 | 「結果」的定義爭議；誘因扭曲（例如不轉人工） |
| 混合（平台費＋額度＋超量） | 基本費＋用量 | 分攤 | 可預測又能擴張 | 方案複雜，需要好的用量儀表板 |

這張表最值得注意的是 per seat 的第二個風險。agent 的價值主張往往是「讓同樣的人處理更多事」，甚至「需要更少的人」；如果按帳號收費，產品越成功，客戶需要的帳號越少，收入就越低。這是許多 agent 產品從 per seat 轉向按量或按結果的根本原因。per outcome 的誘因看起來最對齊，但它把「結果」的定義變成合約條款：買家沒有回覆算不算解決？轉給店主後店主處理好了算誰的？如果定義成「沒有轉人工就算解決」，agent 就有了不轉人工的誘因，這正好和 37.6 節的誠實 UX 衝突。所以按結果計價時，「resolution」的定義要包含品質條件，例如「沒有轉人工，且 24 小時內沒有再來詢問同一件事」，並且定期抽查。

把定價和成本放在一起算，需要一個試算器，這是 37.11 節第二段程式的內容。先看結論的形狀：在 per seat 下，小店有健康的毛利，但每月三萬則對話的大店毛利是大幅負值；在 per task 與 per outcome 下，三種店的毛利都是正的，但 per outcome 的毛利對 resolution rate 很敏感；混合方案對小店的毛利較低（平台費包含的額度用不完，但固定成本還在），對大店則因為超量收費而健康。沒有一種模式在所有客群都最好，這也是為什麼許多產品同時提供兩種方案。

估算時有三個常被忽略的成本。一是**重試與失敗的成本**：模型 API 的重試、格式修復迴圈、被 guardrail 擋下後重新生成，都會增加 token，但不會出現在「平均一次成功對話」的估算裡。二是**長尾**：成本分布通常有長尾，少數極複雜的對話可能占總成本的一大塊，所以要看 p95 與 p99，而不只是平均值，必要時在方案中設定單次任務的上限。三是**模型降價不等於毛利改善**：模型價格下降時，tool、基礎設施與人工成本不會跟著降，而且競爭對手也會降價；更穩定的毛利來源是架構：快取命中率、第 25 章的 model routing（簡單問題用小模型）、減少不必要的步數。

> [!note] 2026 現況
> 截至 2026 年 10 月，公開資料中可以看到各種定價模式並存（以下依各公司公開的價目表與發布說明整理，價格與方案變動頻繁，本書撰寫時未逐一重新查證，請以官方最新資訊為準）：Intercom Fin 長期以「每次 resolution」計價，公開價格曾為每次 0.99 美元；Salesforce Agentforce 在 2024 年推出時以每次對話計價，之後加入以 credits 計算動作的方案；Zendesk 宣布過針對 AI agent 的按結果計價；Cognition 的 Devin 以 ACU（Agent Compute Unit）計量；GitHub Copilot 採帳號訂閱加上進階請求額度，其 coding agent 同時消耗 GitHub Actions 分鐘數與 AI credits。整體趨勢是從純 per seat 走向「訂閱＋用量」或「按結果」的混合。

## 37.10 導入組織的變革管理

即使 UX、回饋與定價都做對了，agent 進入一個組織時，最後的障礙往往是人。店家的客服人員會問：這東西會不會取代我？出錯了誰負責？我要怎麼知道什麼時候該相信它？這些問題如果沒有被回答，最常見的結果不是抗議，而是安靜地不用：功能開著，但每則回覆都被手動重寫，或者乾脆把它關掉。**變革管理**（change management）指的是有計畫地帶領組織從舊的工作方式走到新的工作方式，在 agent 導入中，它的核心是讓信任以可驗證的方式逐步建立。

```text
 階段        ① 觀察（shadow）   ② 建議（copilot）   ③ 監督式執行      ④ 有邊界的自主
 autonomy    無（不上線）       L1                 L3                 L4
 agent 做什麼 背景試答，不送出   擬草稿，人按送出   執行，寫入要核准   邊界內自動，超出才找人
 人做什麼    照常工作；週會比對  審閱、修改、送出   核准卡片           抽查、處理例外、調邊界
 前進條件    試答與人的答案一致  草稿免修改率穩定    核准率高且駁回     邊界內的撤銷率與
             率達標              達標                原因可解釋         客訴率低於門檻
 退回條件    ─                  修改率上升          駁回率異常上升     撤銷或客訴超過門檻
                ──────────────────────────────────────────────────►
                   每一步都由資料決定，而且可以退回上一步
```

這張導入階梯把第 1 章的 autonomy 等級變成組織導入的時間軸。第一階段是 **shadow mode**（影子模式）：agent 在背景對真實問題試答，但答案不送給任何人，只在週會上和真人的回答比對。這個階段的目的不只是驗證品質，更是讓客服人員看到 agent 的能力與弱點，建立有根據的期待。第二階段進入 copilot：agent 擬草稿，人修改後送出；這時候的「草稿免修改率」就是 37.7 節的隱含回饋，同時也是前進到下一階段的依據。第三階段是 L3 監督式執行，第四階段才是 L4 有邊界的自主。每一階段都有明確的前進條件與退回條件，而且條件是數據，不是主管的感覺。

這個階梯有兩個常被忽略的設計。第一，**按動作導入，而不是按系統導入**：第 1 章強調 autonomy 是依動作決定的，同一個店家可以讓「查物流回覆」在 L4、「退款」停在 L3。這讓組織可以從風險最低、量最大的動作開始，而不是整個 agent 一起上線。第二，**退回是正常的**：當模型版本更換、政策改變或新商品上架時，某些動作的品質可能下降，系統要能自動把該動作退回上一階段，並通知相關的人。把退回設計成例行機制，比出事後緊急關閉整個功能好得多。

角色重新定義是另一個關鍵。導入 agent 之後，客服人員的工作從「回答每一則問題」變成「處理 agent 處理不了的問題、審核 agent 的高風險動作、教 agent 變得更好」。最後一項要具體化：讓客服人員能直接在後台標註錯誤、修改政策條文、補充知識庫，並且看到自己的修改讓哪些案例從失敗變成通過。這讓 37.7 節的飛輪有了人的參與，也讓客服人員從「被取代的人」變成「訓練與監督 agent 的人」。青鳥在每個店家的後台加了一個「本週 agent 從你的修改學到了什麼」的區塊，列出由店家回饋產生、而且已經通過回歸測試的案例。

| 利害關係人 | 主要擔憂 | 需要的證據 | 導入時要提供的東西 |
|---|---|---|---|
| 第一線客服 | 會不會被取代；出錯誰負責 | agent 處理的問題類型與錯誤率 | 明確的責任分界、標註與回饋工具、新角色的培訓 |
| 店主（決策者） | 會不會得罪買家；值不值得 | 客訴率、處理時間、成本對比 | shadow 期報告、分階段方案、隨時可退回 |
| 買家（終端使用者） | 是不是在跟機器講話；能不能找到真人 | 不需要報告，需要體驗 | AI 身分揭露、隨時轉真人的出口 |
| 法務與資安 | 資料用途、責任歸屬、法規 | 資料流圖、稽核紀錄 | DPA、同意設定、第 33 章的稽核日誌 |
| 財務 | 成本是否可控 | 單位經濟與用量預測 | 用量儀表板、預算上限與告警 |

這張表提醒我們：每個利害關係人要的證據不同。對第一線客服而言，最有說服力的不是「agent 很厲害」的簡報，而是 shadow 期間的逐題比對：哪些題 agent 答得比人好，哪些題明顯不行。對買家而言，最重要的是 AI 身分的揭露與隨時能找到真人，這既是信任問題，也越來越是法規要求。

> [!note] 2026 現況
> 公開報導中最常被引用的案例之一是 Klarna：該公司在 2024 年公開宣傳其 AI 客服助理處理了大部分客服對話，2025 年執行長又公開表示要確保顧客隨時都能找到真人服務。這類案例常被拿來討論「自動化比例」與「服務品質」之間的取捨；具體數字與後續發展請以該公司的公開說明為準。

## 37.11 動手做：回饋事件變成 eval 案例，以及單位經濟試算器

這一節有兩段程式。第一段實作 37.7 與 37.8 節的回饋管線：收集讚／倒讚、修改、撤銷與轉人工事件，經過同意閘門與 PII 遮蔽，逐 trace 合成標籤，依意圖去重，產生四種 eval 案例，最後用 ScriptedModel 模擬新舊兩個版本的 agent，跑一次回歸測試。第二段實作 37.9 節的單位經濟試算器：在四種定價模式下計算三種店家的毛利率、損益兩平點與敏感度。

### 第一段：從回饋事件到 eval 案例

資料是青鳥故事的縮影。t1 是「已出貨卻直接退款」：買家當下按了讚，店主之後撤銷了退款；t7 是同一種錯誤發生在另一家店。t3 是改地址失敗，買家按倒讚並轉人工。t4 與 t5 都是店主大幅改寫了退款回覆，但 t4 所屬的 shop-c 沒有同意 eval 用途。t6 是店主只補了一個句號。

```python
from __future__ import annotations

import difflib
import json
import re
from collections import defaultdict
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    """依劇本回應的假模型。"""

    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def say(text: str) -> ModelResponse:
    return ModelResponse(text=text)


# ── 線上資料：trace（agent 當時看到與說出的內容）與回饋事件 ──
TRACES = {
    "t1": ("shop-a", "B-1042 可以退款嗎？電話 0912-345-678", "已為您退款 NT$1,280。"),
    "t2": ("shop-a", "B-2001 到哪了", "已出貨，預計明天送達。"),
    "t3": ("shop-b", "可以改寄送地址嗎？amy@example.com", "抱歉，我無法處理這個問題。"),
    "t4": ("shop-c", "B-3300 能退款嗎", "已為您退款 NT$990。"),
    "t5": ("shop-a", "B-1077 可以退款嗎", "已為您退款 NT$450。"),
    "t6": ("shop-b", "B-5120 到哪了", "已出貨，預計後天送達"),
    "t7": ("shop-b", "B-6001 退款", "已為您退款 NT$2,100。"),
}
CONSENT = {"shop-a": True, "shop-b": True, "shop-c": False}   # 租戶是否同意把對話用於品質改善
EVENTS = [  # (trace_id, 時間, 種類, 內容)
    ("t1", 10, "thumbs_up", {}),
    ("t1", 95, "undo", {"reason": "訂單已出貨，不應直接退款"}),
    ("t2", 12, "thumbs_up", {}),
    ("t3", 20, "thumbs_down", {"reason": "不會改地址"}),
    ("t3", 21, "escalate", {}),
    ("t4", 30, "edit", {"final": "B-3300 已出貨，已為您建立退貨單。"}),
    ("t5", 40, "edit", {"final": "B-1077 已出貨，無法直接退款，已為您建立退貨單 R-88。"}),
    ("t6", 50, "edit", {"final": "已出貨，預計後天送達。"}),
    ("t7", 60, "undo", {"reason": "訂單已出貨，不應直接退款"}),
]
PII = [(re.compile(r"09\d{2}-?\d{3}-?\d{3}"), "<PHONE>"), (re.compile(r"[\w.]+@[\w.]+"), "<EMAIL>")]


def redact(text: str) -> str:
    for pattern, token in PII:
        text = pattern.sub(token, text)
    return text


def intent(text: str) -> str:
    return "refund" if "退款" in text else "tracking" if "到哪" in text else "other"


@dataclass
class EvalCase:
    case_id: str
    kind: str              # reference｜must_not｜needs_label｜keep_working
    input: str
    expected: str
    sources: list[str]


def label(events: list[tuple]) -> tuple[str, str] | None:
    """一條 trace 的所有回饋合成一個標籤。行為訊號（undo、escalate、edit）優先於讚／倒讚。"""
    kinds = {k: p for _tid, _ts, k, p in sorted(events, key=lambda e: e[1])}
    if "undo" in kinds:
        return "must_not", kinds["undo"]["reason"]
    if "escalate" in kinds:
        return "needs_label", kinds.get("thumbs_down", {}).get("reason", "")
    if "edit" in kinds:
        return "reference", kinds["edit"]["final"]
    if "thumbs_down" in kinds:
        return "needs_label", kinds["thumbs_down"].get("reason", "")
    if "thumbs_up" in kinds:
        return "keep_working", ""
    return None


def build_cases() -> tuple[list[EvalCase], dict[str, int]]:
    by_trace: dict[str, list[tuple]] = defaultdict(list)
    for e in EVENTS:
        by_trace[e[0]].append(e)
    stats = {"no_consent": 0, "cosmetic_edit": 0, "merged": 0}
    clusters: dict[tuple[str, str], EvalCase] = {}
    for tid, events in by_trace.items():
        tenant, user_input, output = TRACES[tid]
        if not CONSENT[tenant]:                  # 沒同意就不進資料集，連去識別化都不做
            stats["no_consent"] += 1
            continue
        kind, expected = label(events)
        if kind == "reference" and difflib.SequenceMatcher(None, output, expected).ratio() > 0.9:
            stats["cosmetic_edit"] += 1          # 只改標點的修改不是品質訊號
            continue
        key = (intent(user_input), kind)
        if key in clusters:                      # 同一意圖、同一種失敗只留一個案例，記下來源數
            clusters[key].sources.append(tid)
            stats["merged"] += 1
            continue
        if kind == "must_not":
            expected = output.split("NT$")[0].strip()   # 被撤銷的那句話，就是不該再說的話
        clusters[key] = EvalCase(f"fb-{len(clusters) + 1}", kind, redact(user_input), redact(expected), [tid])
    return sorted(clusters.values(), key=lambda c: -len(c.sources)), stats


cases, stats = build_cases()
print("過濾：", stats)
for c in cases:
    shown = {"must_not": f"不得出現「{c.expected}」", "reference": f"參考答案「{c.expected}」",
             "needs_label": f"送人工標註（{c.expected}）", "keep_working": "保持現有行為"}[c.kind]
    print(f"{c.case_id} {c.kind:<12} 來源={','.join(c.sources):<6} 輸入={c.input}\n     → {shown}")


def grade(case: EvalCase, answer: str) -> bool:
    if case.kind == "must_not":
        return case.expected not in answer
    if case.kind == "reference":
        return difflib.SequenceMatcher(None, answer, case.expected).ratio() >= 0.5
    return True                                  # keep_working 的檢查在別處；needs_label 先不自動評分


gradable = [c for c in cases if c.kind in ("must_not", "reference")]
v1 = ScriptedModel([say("已為您退款 NT$450。"), say("已為您退款 NT$450。")])
v2 = ScriptedModel([say("B-1042 已出貨，無法直接退款，已為您建立退貨單 R-90。"),
                    say("B-1077 已出貨，無法直接退款，已為您建立退貨單 R-91。")])
passed = {}
for name, model in (("v1", v1), ("v2", v2)):
    results = [grade(c, model.complete([{"role": "user", "content": c.input}]).text) for c in gradable]
    passed[name] = sum(results)
    print(f"{name} 回歸：{sum(results)}/{len(results)} 通過 {results}")

assert stats == {"no_consent": 1, "cosmetic_edit": 1, "merged": 1}
assert [c.kind for c in cases] == ["must_not", "keep_working", "needs_label", "reference"]
assert all("0912" not in c.input and "@" not in c.input for c in cases)
assert cases[0].sources == ["t1", "t7"]
assert passed == {"v1": 0, "v2": 2}
```

fb-1 must_not     來源=t1,t7  輸入=B-1042 可以退款嗎？電話 <PHONE>
     → 不得出現「已為您退款」
fb-2 keep_working 來源=t2     輸入=B-2001 到哪了
     → 保持現有行為
fb-3 needs_label  來源=t3     輸入=可以改寄送地址嗎？<EMAIL>
     → 送人工標註（不會改地址）
fb-4 reference    來源=t5     輸入=B-1077 可以退款嗎
     → 參考答案「B-1077 已出貨，無法直接退款，已為您建立退貨單 R-88。」

第一行的過濾統計說明了三件被刻意丟掉或合併的事。`no_consent: 1` 是 shop-c 的 t4：即使店主的修改是很好的參考答案，沒有同意就不進資料集。`cosmetic_edit: 1` 是 t6：修改前後的相似度超過 0.9，只是補了句號，不是品質訊號。`merged: 1` 是 t7：它和 t1 是同一個意圖（退款）、同一種失敗（被撤銷），所以合併成一個案例，來源記成 `t1,t7`。

接下來四個案例依來源數排序，出現越多次的問題排越前面。fb-1 是 must_not 案例：t1 雖然有一個讚，但撤銷事件優先，讚被覆蓋；期望條件是「不得出現『已為您退款』」，也就是被撤銷的那句話。輸入中的電話已經被遮蔽成 `<PHONE>`。fb-2 是 keep_working：只有讚的 t2 成為正向回歸樣本，確保修好退款問題時沒有弄壞物流查詢。fb-3 是 needs_label：t3 同時有倒讚與轉人工，程式無法自動決定正確行為（應該轉給店主，還是應該能直接處理），所以送人工標註，email 同樣被遮蔽。fb-4 是 reference：t5 的店主改寫內容成為參考答案。

最後兩行是回歸測試。只有 must_not 與 reference 兩種案例可以自動評分。v1 是舊版 agent 的行為，兩題都回「已為您退款」，0/2 通過；v2 改成先檢查出貨狀態、改建退貨單，兩題都通過。這就是飛輪的一圈：使用者的撤銷與修改，變成了下一個版本必須通過的測試。

這段程式有兩個刻意的簡化，實際系統要補上。第一，`intent` 用關鍵字判斷意圖，實務上會用分類器或 embedding 分群，並由人審查群組。第二，案例沒有保存環境狀態：fb-1 的正確答案取決於訂單「已出貨」，真正的案例要把 trace 中 `get_order` 的回傳結果存成 fixture，讓第 27 章的 harness 用假 tool 重現，否則一年後重跑時，案例的意義已經不同。

### 第二段：單位經濟試算器

試算器的每個價格都是假設值，重點是計算方法：把 37.9 節的成本堆疊寫成函式，再套上四種定價模式。三種店家的差別在於對話量、平均步數、resolution rate 與帳號數。

```python
from __future__ import annotations

from dataclasses import dataclass

# 價格一律是假設值（新台幣），用來示範計算方法；實際請代入當期價目表與自己的 trace 統計
PRICE = {"input": 0.06, "cached": 0.006, "output": 0.30}   # 每 1K tokens


@dataclass
class Workload:
    name: str
    conversations: int      # 每月對話數
    steps: float            # 每次對話平均 loop 步數
    resolution_rate: float  # 不需轉人工、且 24 小時內未再來訊的比例
    seats: int              # 店家開通的客服帳號數


def cost_per_conversation(steps: float, base: int = 3_000, per_step: int = 600, out_per_step: int = 300,
                          cache_hit: float = 0.7, tools_infra: float = 0.40, price_scale: float = 1.0) -> float:
    """第 k 步送出 base + per_step*(k-1) 個 input tokens；累計約與步數平方成正比。"""
    n = steps
    total_in = n * base + per_step * n * (n - 1) / 2
    input_cost = total_in / 1000 * (PRICE["input"] * (1 - cache_hit) + PRICE["cached"] * cache_hit)
    output_cost = n * out_per_step / 1000 * PRICE["output"]
    return (input_cost + output_cost) * price_scale + tools_infra


def revenue(model: str, w: Workload) -> float:
    resolved = w.conversations * w.resolution_rate
    if model == "per_seat":
        return 1_500 * w.seats
    if model == "per_task":
        return 6 * w.conversations
    if model == "per_outcome":
        return 10 * resolved
    if model == "hybrid":                        # 平台費含 300 次 resolution，超出每次 12 元
        return 990 + 12 * max(0, resolved - 300)
    raise ValueError(model)


def cogs(w: Workload, **kw) -> float:
    qa_review = 0.01 * w.conversations * 20      # 抽 1% 對話給人工品管，每則 20 元
    return w.conversations * cost_per_conversation(w.steps, **kw) + qa_review


SHOPS = [Workload("小店", 300, 5, 0.55, 1), Workload("中店", 3_000, 6, 0.65, 3),
         Workload("大店", 30_000, 9, 0.70, 8)]
MODELS = ["per_seat", "per_task", "per_outcome", "hybrid"]

print("每次對話成本：" + "  ".join(f"{w.name} {cost_per_conversation(w.steps):.2f}" for w in SHOPS))
print(f"{'毛利率':<8}" + "".join(f"{m:>13}" for m in MODELS))
margins: dict[tuple[str, str], float] = {}
for w in SHOPS:
    row = []
    for m in MODELS:
        r = revenue(m, w)
        margins[(w.name, m)] = (r - cogs(w)) / r
        row.append(f"{margins[(w.name, m)]:>12.0%} ")
    print(f"{w.name:<8}" + "".join(row))

# 損益兩平一：per_outcome 下，resolution rate 至少要多少，毛利率才達 60%？
for w in SHOPS:
    unit = cogs(w) / w.conversations
    need = unit / (10 * (1 - 0.60))
    print(f"{w.name} per_outcome 要達 60% 毛利，resolution rate ≥ {need:.0%}（目前 {w.resolution_rate:.0%}）")

# 損益兩平二：每月固定成本（團隊、平台）要多少家中店才能打平（hybrid 方案）
FIXED = 2_400_000
mid = SHOPS[1]
contribution = revenue("hybrid", mid) - cogs(mid)
print(f"hybrid 每家中店貢獻 {contribution:,.0f} 元／月 → 需要 {FIXED / contribution:,.0f} 家中店打平固定成本")

# 敏感度：大店在 per_seat 下，模型降價 50% 或步數再增加 50%
big = SHOPS[2]
for label, kw, steps in (("基準", {}, big.steps), ("模型降價50%", {"price_scale": 0.5}, big.steps),
                         ("步數+50%", {}, big.steps * 1.5)):
    cost = big.conversations * cost_per_conversation(steps, **kw) + 0.01 * big.conversations * 20
    print(f"大店 per_seat {label:<8} 成本 {cost:>9,.0f}  營收 {revenue('per_seat', big):>7,.0f}"
          f"  毛利率 {(revenue('per_seat', big) - cost) / revenue('per_seat', big):>6.0%}")

assert margins[("大店", "per_seat")] < 0 < margins[("小店", "per_seat")]
assert all(margins[(w.name, "per_outcome")] > 0.5 for w in SHOPS)
assert contribution > 0
```

第一行是每次對話的成本。大店的平均步數是 9，比小店的 5 多不到一倍，成本卻從 1.32 元升到 2.29 元，而且其中固定的 0.40 元基礎設施費用沒有變，增加的部分全部來自 token：這就是步數的平方效應。

毛利率表是本章最重要的一張數字表。per seat 欄位一路從 70% 掉到 −16% 再到 −522%：大店 8 個帳號每月付 12,000 元，成本卻是 74,668 元，這正是故事裡財務長看到的試算表。per task 與 per outcome 在三種店都是正毛利，因為收入跟著用量走。注意 per outcome 的每次 resolution 10 元，在 65% 的成功率下約等於每次對話 6.5 元，和 per task 的 6 元相近；兩者的差別在於風險分配：resolution rate 下降時，per outcome 的供應商收入減少，per task 則由客戶多付錢。hybrid 對小店只有 54%，因為小店的 165 次 resolution 用不完平台費包含的 300 次額度，收入固定在 990 元，這不見得是壞事，平台費本來就是在賣「可預測」。

中間三行是第一種損益兩平：在 per outcome 下，要達到 60% 的目標毛利，resolution rate 至少要多少。小店只要 38%，大店卻要 62%，而大店目前是 70%，安全邊際只剩 8 個百分點。這告訴阿哲：如果要對大店採用按結果計價，就必須持續監控 resolution rate，而且 resolution 的定義要寫進合約。

下一行是第二種損益兩平：每月 240 萬元的固定成本（團隊與平台），在 hybrid 方案下每家中店每月貢獻約 15,572 元，需要約 154 家中店才能打平。這個數字讓產品決策變得具體：beta 的 200 家店如果大多是小店，固定成本就打不平。

最後三行是敏感度分析。對 per seat 的大店，模型降價 50% 只能把毛利從 −522% 改善到 −286%，仍然深度虧損；步數增加 50%（例如加了新功能，每次對話多查幾個系統）則讓它惡化到 −859%。這說明了 37.9 節的論點：定價模式選錯時，等模型降價是救不回來的，架構與定價要一起設計。程式最後的 assert 鎖住了三個結論：per seat 對小店是正、對大店是負；per outcome 在三種店的毛利都超過 50%；hybrid 對中店的貢獻為正。

## 37.12 實務應用

本章的原則在不同產品中有不同的重心。以下四個情境說明互動模式、可解釋性、回饋與定價如何隨產品類型改變。

**情境一：電商客服 agent（青鳥的主線）**。買家端是 chat，延遲與轉人工是第一優先：首個有意義回饋要在一兩秒內出現，tool 慢的時候要有心跳說明，任何時候都要能找到真人。店主端是 copilot 與 ambient 的混合：日常回覆以草稿呈現，退貨單由 ambient agent 預審後推到收件匣，退款排入撤回窗口。回饋的主力是店主的修改與撤銷，因為它們量大且意圖明確；買家的讚與倒讚只作輔助，因為常和政策不滿混在一起。定價上，客服產業的公開案例普遍從 per seat 走向按 resolution 或按對話計價，關鍵是把 resolution 的定義與品質條件寫進合約；例如依公開資料，Intercom Fin 以 resolution 作為計價單位（價格見 37.9 節的 2026 現況）。

**情境二：background coding agent**。開發者把 issue 指派給 agent，agent 在 sandbox 中工作，完成後開一個 pull request。這是 background 模式的典型：提交後立刻顯示任務頁，執行中可以查看進度與 session log，完成時通知。可解釋性的主力是 diff 與測試結果，而不是 agent 的說明；可撤銷性由 git 天然提供，pull request 本身就是「草稿優先」，合併前什麼都沒改。公開文件中，GitHub Copilot coding agent 每個任務對應一個 branch 與 pull request，使用者可以在 PR 留言要求它繼續修改。回饋訊號是 PR 被合併、被要求修改、被關閉，以及人在合併前額外做了多少修改，這些都可以轉成第 27 章的 eval 案例。定價多以用量（compute 或 credits）計量，因為任務長度差異極大。

**情境三：企業內部 research 與分析 agent**。營運人員請 agent「分析上月退貨率上升的原因」，這是 background 加上互動澄清：開始前先提出澄清問題（哪個品類、和哪個月比較），確認後在背景執行，中途有重要發現時可以提前通知。可解釋性的主力是引用：每個數字都要能點回查詢與資料來源，因為讀者會拿這份報告去做決策。主流的 deep research 產品都採用「先澄清、背景執行、附引用」的模式。回饋訊號是報告被分享、被引用、被追問的內容；內部產品通常不單獨定價，但仍要算單位經濟，因為每份報告的成本差異很大，要用部門預算上限控制。

**情境四：IT 與營運的 ambient agent**。agent 監聽監控告警或工單佇列，自動做初步診斷，把結果整理成一張卡片推給值班工程師。這種模式最大的風險是通知疲勞，所以要嚴格控制「什麼時候打擾人」：只有在診斷有明確結論，或者需要人做決定時才推送，其餘批次彙整成每日摘要。可撤銷性很重要，任何修復動作都要先以計畫形式呈現，執行後保留回滾指令。回饋訊號是值班工程師是否採納 agent 的診斷、是否改走其他方向，這需要在卡片上設計「採納／不採納＋原因」的一鍵回饋，否則訊號會散落在聊天紀錄裡。

| 產品類型 | 主要互動模式 | 可解釋性主力 | 可撤銷機制 | 最有價值的回饋訊號 | 常見定價 |
|---|---|---|---|---|---|
| 電商客服 | Chat＋ambient 收件匣 | 政策引用、金額 diff | 撤回窗口、草稿優先 | 店主修改與撤銷 | 按 resolution 或對話 |
| Background coding | Background | 程式碼 diff、測試結果 | Pull request（未合併前） | 合併、要求修改、人工補改量 | 帳號＋用量 |
| Research 分析 | Background＋澄清 | 引用與查詢紀錄 | 報告版本 | 追問、分享、被引用 | 內部預算或用量 |
| IT／營運 ambient | Ambient | 診斷依據、執行計畫 | 回滾指令 | 採納與否＋原因 | 平台費＋用量 |

這張表的共同點是：每一列的「可解釋性主力」與「可撤銷機制」都是由確定性程式產生的，不是由模型描述的。產品的信任建立在這些不會說謊的東西上，模型的說明只是輔助。

## 37.13 設計檢查清單

把 agent 產品化時，逐項回答下面的問題。

1. 這個產品的主要互動模式是 chat、copilot、background 還是 ambient？選擇的依據是任務長度、主動權與可回復性，而不是「大家都做 chat」？
2. 首個有意義回饋（例如「正在查詢 B-1042」）在多少秒內出現？tool 呼叫期間沉默超過多久會顯示心跳說明？
3. UI 是否只依賴語意事件（step_started、needs_approval、run_finished），而不直接顯示原始推理內容或 tool 名稱？
4. 長任務的狀態機是否包含 input_required、needs_approval 與 cancelled？進入中斷態時是否一定通知使用者，且通知帶有完整的待辦資訊？
5. 每個高風險動作是否同時顯示計畫、引用與由參數直接渲染的 diff？AI 的說明是否清楚標示並放在次要位置？
6. 每個有副作用的 tool 是否都填過「草稿優先／撤回窗口／補償動作／事前核准」四欄表？撤回按鈕的文字是否如實反映窗口內外的差別？
7. 錯誤訊息是否回答了「發生什麼、誰的問題、可以怎麼做」？轉人工是否為 warm handoff（附摘要與已查到的資料）？
8. 不確定時的行為是否由可觀察的訊號決定，而不是顯示模型自評的信心百分比？
9. 每筆回饋事件是否都帶 trace_id？詮釋規則是否寫明「行為優先於表態」與雜訊過濾條件？
10. 回饋進入 eval set 之前，是否經過用途同意、PII 遮蔽與租戶隔離？每個 eval 案例是否記錄來源 trace，以便執行刪除權？
11. eval 案例是否保存了當時的環境狀態（tool 回傳結果）作為 fixture？
12. 定價模式下，各客群（輕度、中度、重度使用者）的毛利率是多少？是否看過成本分布的 p95，而不只是平均？
13. 若採用按結果計價，resolution 的定義是否包含品質條件，並且不會產生「不轉人工」的誘因？
14. 組織導入是否按動作分階段（shadow → copilot → L3 → L4），每階段都有數據化的前進與退回條件？

## 37.14 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 使用者在 tool 呼叫期間離開或重新整理 | UI 只串流文字，tool 期間沒有任何進度 | 對照 trace 的 tool 時間與前端離開事件的時間點 | 加入步驟事件與心跳；顯示計畫與參考時間 |
| background 任務停在「進行中」好幾天 | 進入 input_required 或 needs_approval 卻沒有通知 | 查詢狀態停留過久的任務分布 | 中斷態必發通知，加上逾時提醒與預設行為 |
| 使用者核准後才發現改的不是預期的東西 | 卡片只顯示 AI 摘要，沒有 diff | 抽查被事後撤銷的核准，比對卡片內容與實際參數 | 由參數直接渲染 diff，摘要降為次要資訊 |
| 「撤回」後副作用仍然發生 | 窗口結束後撤回被當成取消；worker 重啟遺失佇列 | 比對撤回時間與實際執行時間 | 窗口內外分開處理；佇列 durable 化；補償動作表 |
| 回饋很多，但 eval set 沒有變好 | 讚／倒讚沒有 trace_id 或沒有詮釋規則 | 統計可對回 trace 的回饋比例 | 回饋事件綁 trace_id；定義行為優先與雜訊過濾 |
| eval 案例重跑結果與當初不同 | 沒有保存當時的環境狀態 | 檢查案例是否依賴即時查詢的資料 | 把 trace 中的 tool 結果存成 fixture |
| 買家要求刪除個資，卻找不到衍生的 eval 案例 | 案例沒有記錄來源 trace | 抽查案例是否有 sources 欄位 | 案例保留來源；建立刪除的追溯流程 |
| 大客戶越成長，毛利越差 | per seat 定價，成本隨用量成長 | 依客群計算毛利率與每次對話成本 | 改為混合或按量計價；設定方案的用量上限 |
| 按結果計價後轉人工率下降，但客訴上升 | resolution 定義只看「沒轉人工」，產生錯誤誘因 | 比對轉人工率、重問率與客訴率的趨勢 | resolution 定義加入品質條件並抽查 |
| 功能開著但沒人用，草稿幾乎都被重寫 | 跳過 shadow 與 copilot 階段，信任沒有建立 | 看草稿免修改率與功能使用率 | 回到前一階段，用 shadow 比對報告重建信任 |

## 本章重點整理

- 互動模式（chat、copilot、background、ambient）由任務長度與主動權決定；越往人不在場的方向走，進度、通知與可撤銷越重要。
- background 與 ambient 需要另一套基礎建設：任務佇列、狀態頁、通知與收件匣，不是 chat 的變形。
- 使用者對延遲的感受取決於是否知道發生什麼事；要串流的是整個任務的進度，而不只是文字。
- runtime 應該把模型與 tool 的活動翻譯成語意事件，UI 只依賴這些事件，並在沉默超過門檻時送出心跳說明。
- 長任務的狀態機一定要有 input_required、needs_approval 與 cancelled，進入中斷態時必須通知使用者。
- 可解釋性要給證據而不是故事：計畫、引用與由參數直接渲染的 diff，AI 的說明只放在次要位置。
- 可撤銷性有四種機制，依可靠程度是草稿優先、撤回窗口、補償動作、不可撤銷；每個有副作用的 tool 都要明確歸類。
- 錯誤 UX 要回答發生什麼、誰的問題、可以怎麼做；轉人工要是附帶摘要與資料的 warm handoff。
- 不確定時用可觀察的訊號決定行為，而不是顯示模型自評的信心數字。
- 回饋訊號分成明確、隱含與結果三類；詮釋時行為優先於表態，並過濾雜訊。
- 回饋最安全的用途是變成可重跑的 eval 案例，案例要保存當時的環境狀態與來源 trace。
- 回饋資料要經過用途同意、去識別化與租戶隔離，並且能依來源執行刪除權。
- agent 產品的邊際成本不為零且波動大，定價模式決定成本波動由誰承擔；per seat 在重度使用者上容易虧損。
- 按結果計價要把 resolution 的定義與品質條件寫清楚，避免產生不轉人工的錯誤誘因。
- 組織導入要按動作分階段推進，每階段都有數據化的前進與退回條件，並重新定義第一線人員的角色。

## 延伸問答

> [!question]- Q1. 同一個客服 agent，為什麼放在買家端要用 chat，放在店主端卻適合 copilot 或 ambient？
> 關鍵在於使用者的期待與責任歸屬。買家是來解決自己問題的，人就在畫面前等，最在意的是快速得到答案或找到真人，所以 chat 的同步互動與低延遲是第一優先；但買家沒有權限決定退款，也無法判斷 agent 的動作對不對，讓有副作用的動作在買家端自動執行，等於讓一個無法驗證的人承擔風險。
>
> 店主是要對結果負責的人，有判斷能力，但時間有限。copilot 讓店主保有最終決定權，ambient 則讓 agent 先把查詢與計算做完，只在需要決定時才打擾店主。這樣的分工把「回應速度」放在買家端，把「判斷與核准」放在店主端，各自用最適合的互動模式。代價是買家等待核准的時間變長，所以買家端要清楚說明「店主通常在幾小時內回覆」，管理期待。

> [!question]- Q2. 為什麼不建議在 UI 上顯示「信心 87%」這類數字？如果產品經理堅持要顯示不確定性，你會怎麼設計？
> 模型口頭表達的信心不一定和實際正確率一致，而精確的數字會讓使用者以為它經過校準，結果是使用者在 87% 時過度信任、在 60% 時又不知道該怎麼辦。數字本身也不可行動：使用者看到 87%，下一步要做什麼？
>
> 比較好的設計是把不確定性轉成具體理由與具體行動。決定行為的是可觀察的訊號：有沒有查到資料、來源是否矛盾、問題是否落在 eval 覆蓋過的意圖、使用者是否重問。呈現給使用者的則是理由，例如「物流商最新紀錄是兩天前，實際位置可能已更新」，加上行動選項，例如「要我 2 小時後再查一次嗎？」。如果產品經理需要一個整體指標，可以在內部儀表板上用 eval 與線上回饋統計各意圖的實際正確率，那才是經過校準的數字。

> [!question]- Q3. 店主按了讚，隔天卻撤銷了 agent 做的退款。這筆回饋該怎麼處理？如果反過來，先撤銷再按讚呢？
> 第一種情況應該以撤銷為準，產生 must_not 案例。讚只代表當下看起來滿意，撤銷則是使用者付出成本做出的行為，而且通常發生在得到更多資訊之後（例如對帳時發現訂單已出貨）。這就是「行為優先於表態」的規則，也是動手做程式中 t1 的處理方式。
>
> 反過來的情況比較少見，可能是店主撤銷後發現 agent 其實是對的，或者撤銷的原因與 agent 無關（例如買家改變主意）。這時不應該自動產生任何案例，而是送人工標註，並在撤銷的 UI 上加一個可選的原因欄位，例如「agent 判斷錯誤」與「買家改變主意」，讓之後的詮釋不必猜。詮釋規則要有明確的時間順序與衝突處理，不能只看最後一個事件。

> [!question]- Q4. 估算題：青鳥中店每次對話成本約 1.74 元（含品管），resolution rate 65%。若採按結果計價且目標毛利率 60%，每次 resolution 至少要收多少？若 resolution rate 掉到 50% 呢？
> 按結果計價時，失敗的對話也要付成本，所以每次 resolution 的真實成本是 1.74 ÷ 0.65，約 2.68 元。目標毛利率 60% 代表成本只能占營收的 40%，所以價格至少是 2.68 ÷ 0.4，約 6.7 元。本章試算器使用 10 元，毛利率 73%，與這個估算一致。
>
> 若 resolution rate 掉到 50%，每次 resolution 的成本變成 1.74 ÷ 0.5 ＝ 3.48 元，要維持 60% 毛利，價格至少 8.7 元。成功率下降 15 個百分點，所需價格就上升約 30%。這說明了按結果計價時，resolution rate 不只是品質指標，也是財務指標，要和成本一起監控；而且定價要留安全邊際，因為新功能上線或模型更換時，成功率可能短暫下降。

> [!question]- Q5. 程式找錯：下面這段把回饋轉成 eval 案例的程式，有哪些會在 production 出問題的地方？
> ```python
> for fb in feedback_rows:
>     if fb["thumb"] == "down":
>         eval_set.append({"input": fb["user_message"], "expected": "（待補）"})
> ```
> 第一，它只看倒讚，忽略了更強的隱含訊號（撤銷、大幅修改、轉人工），也沒有處理「讚後撤銷」的衝突，會漏掉最重要的錯誤。第二，沒有檢查同意與租戶：沒有同意 eval 用途的店家資料也會進入資料集；第三，`user_message` 直接寫入，沒有 PII 遮蔽，電話與 email 會留在 eval set 裡，而且沒有記錄來源 trace，日後無法執行刪除權。
>
> 第四，`expected` 是「待補」，這樣的案例無法自動評分，會在 eval set 中堆積成沒人處理的待辦；應該分成可以自動產生檢查條件的案例（must_not、reference）和需要人工標註的案例，後者進標註佇列而不是直接進 eval set。第五，沒有去重，同一種錯誤出現一百次就會產生一百個案例，讓 eval 結果被單一問題主導。最後，沒有保存當時的 tool 結果作為 fixture，案例重跑時環境已經不同。

> [!question]- Q6. 你在 production 看到：改成按 resolution 計價三個月後，轉人工率從 18% 降到 9%，但店家的一星評價變多了。你會怎麼排查與修正？
> 這個組合強烈暗示誘因扭曲：如果 resolution 的定義是「沒有轉人工」，任何讓 agent 少轉人工的改動都會提高營收，即使那些對話其實沒有被解決。第一步是查這三個月內的變更：prompt 是否加了「盡量自行處理」之類的指令、轉人工的門檻是否被調高、tool 是否被修改。第二步是抽樣「被算成 resolution」的對話，看買家在 24 小時內是否又來詢問同一件事，或者在其他管道（電話、評價）抱怨。
>
> 修正分兩層。產品層：把 resolution 的定義改成包含品質條件，例如「沒有轉人工、24 小時內沒有重問、沒有負評」，並定期人工抽查。工程層：把轉人工率、重問率與客訴率放在同一個儀表板上一起看，任何一個指標的改善伴隨另一個指標的惡化，就要觸發審查。這個案例也說明了為什麼 37.6 節強調「找真人」的出口永遠要存在，它是防止誘因扭曲的最後一道防線。

> [!question]- Q7. 撤回窗口和事前核准都能降低錯誤動作的傷害，兩者怎麼選？
> 兩者的差別在於預設值與人力成本。事前核准是預設不做，人說好才做，每一個動作都要消耗人的注意力，適合不可逆、金額大或出錯代價極高的動作。撤回窗口是預設會做，人不阻止就做，只有在使用者覺得不對時才需要介入，適合大多數情況下是對的、偶爾錯了代價很高、而且延遲幾十秒到幾分鐘可以接受的動作。
>
> 選擇時看三件事。一是 agent 在這類動作上的歷史正確率：正確率高，撤回窗口能大幅減少人力；正確率低，撤回窗口只是把核准變成事後撤銷，反而更糟。二是延遲容忍度：買家立刻需要的回覆不適合延遲。三是使用者是否真的會看到撤回提示：如果通知沒人看，撤回窗口形同虛設。青鳥把小額退款從即時執行改成 10 分鐘撤回窗口，正是因為這類退款大多正確、延遲無妨，而店主後台的通知有人在看。

> [!question]- Q8. 面試追問：設計一個 agent 產品的回饋系統，你會怎麼確保它真的能讓產品變好，而不只是收集資料？
> 我會從「回饋要被哪個流程消化」倒推。資料面，每筆回饋都是帶 trace_id 的事件，種類涵蓋明確、隱含與結果訊號；有明確的詮釋規則（行為優先於表態、雜訊過濾），並在進入任何資料集之前經過同意、PII 遮蔽與租戶隔離。流程面，事件依 trace 合成標籤，可自動產生檢查條件的案例直接進候選 eval set，其餘進人工標註佇列，佇列要有負責人與處理時限，否則會變成另一個沒人看的資料表。
>
> 驗證面，案例保存當時的環境狀態作為 fixture，進入第 27 章的回歸測試，任何 prompt、tool 或模型的變更都要通過，再經 canary 上線，並在上線後觀察同類回饋是否減少，這才算完成一圈。最後是可見性：追蹤幾個飛輪指標，例如「回饋到案例的轉換時間」「由回饋產生的案例數」「修復後同類回饋的下降幅度」，並讓提供回饋的人看到自己的回饋造成了什麼改變，這會提高回饋的質與量，讓飛輪持續轉動。
