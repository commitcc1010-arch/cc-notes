# 第 38 章　從 Prototype 到 Production 的路線圖

> [!abstract] 本章地圖
> **核心問題**：一個在 demo 上表現亮眼的 agent，要經過哪些階段、拿出哪些量化證據、由哪些人把關，才能放心交給真實使用者，並一步步拿到更多自主權？
>
> **你會學到**：
> - 把 agent 專案拆成探索、prototype、內部試用、有限上線、規模化五個階段，說清楚每階段的目標、產出、團隊與常見陷阱
> - 為每個階段寫出量化的退出條件：eval 成功率、pass^k、升級率、每件成本、事故數，並用樣本數與信賴區間避免「數字好看但證據不足」
> - 用上線前檢查清單從功能、eval、安全、營運、法務五個面向審查一個 agent
> - 規劃組織與角色：AI engineer、eval owner、domain expert、SRE、security 各自在哪個階段進場、負責什麼
> - 用證據把單一動作從 L3 晉升到 L4，並設計降級條件
> - 用 Python 實作 stage gate 評估器：輸入各項指標，判斷能否進入下一階段並列出未達項目
>
> **前置知識**：第 1 章（autonomy 等級 L0–L5、任務適合度三問）、第 21 章（approval policy、核准修改率與事後抽查）、第 27 章（outcome eval、pass^k、regression suite）、第 29 章（trace 與線上指標）、第 34 章（SLO 與事故處理）、第 35 章（設計方法論）、第 36 章（canary、shadow 與回滾）

## 38.1 故事：「下個月可以全面上線嗎？」

三家網店的試用結束後的那個週一，阿哲在會議室的白板上寫了一個日期：雙 11 前一個月。「客服團隊旺季一天上萬則留言，去年加了二十個臨時人力還是回不完。如果 agent 能在雙 11 前接下一半，今年就不用再招臨時工。」阿哲轉頭問 Iris：「下個月可以全面上線嗎？」

Iris 想起第 2 章那兩週的試用：隔天不記得承諾、ERP 逾時造成重複退款、改了 system prompt 之後跳過查訂單、以及 Maya 那句「這筆退款是誰授權的」。四件事都修了，可是修完之後到底「好到什麼程度」，Iris 說不出一個數字，只能說：「我覺得比之前好很多。」阿哲接著問：「那要好到什麼程度才能上？」會議室安靜下來。客服主管說「錯誤率要比真人低」，Maya 說「要先做完 threat model」，負責平台維運的 SRE 說「我連它的 SLO 是什麼都不知道，半夜出事要叫誰？」每個人心裡都有一條線，但沒有人把線寫下來，更沒有人知道現在離那條線多遠。

老陳等大家說完，在白板上畫了五個方塊，方塊之間畫上閘門。「我們在第 2 章犯的錯，不是程式寫得不好，而是跳階段。那兩週我們叫它『內部試用』，可是用的是真實顧客、退的是真的錢，那其實已經是有限上線；而我們連 prototype 該有的 eval set 都沒有。」老陳說，每個閘門要有一張單子，上面是可以量測的條件和門檻，由事先指定的人簽核；數字沒到，日期再重要也不開門。「雙 11 是一個很好的目標日期，但它應該決定我們每週要補哪些洞，而不是決定門檻要降多低。」

這一章就是那張白板的完整版本。我們先說明為什麼 agent 專案特別需要階段與關卡，再定義退出條件的「語言」：哪些指標、門檻怎麼定、樣本要多少才算數。接著逐一走過五個階段，整理上線前檢查清單與團隊角色，把青鳥客服 agent 從第 1 章的下午 demo 到小額退款移到 L4 的完整歷程攤成一條時間線。最後在動手做一節，用 Python 寫出老陳要的那張單子：一個 stage gate 評估器，輸入指標就告訴你能不能開門、還差什麼。

## 38.2 為什麼 agent 專案需要階段與關卡

傳統軟體從 prototype 到上線，最大的不確定性通常在需求與規模；功能一旦寫對，同樣的輸入會一直得到同樣的輸出。agent 不一樣，它有三種傳統軟體沒有的不確定性。第一是**行為的非決定性**：同一個問題問三次，模型可能走三條不同的路，其中一條是錯的。第二是**輸入的長尾**：demo 用的是十個典型問題，真實顧客會問一萬種你沒想過的問法，還會夾帶情緒、錯字、兩張訂單混在一起講。第三是**自主權放大錯誤**：L1 的錯誤只是一份被人刪掉的草稿，L4 的錯誤是一筆已經退出去的款項。這三件事加起來，造成了業界常說的 **demo gap**（demo 落差）：demo 證明的是「它做得到」，上線需要證明的是「它幾乎每次都做得對，做錯時損失有限，而且我們會知道」。

demo gap 有一個可以算出來的版本。假設 agent 在單一任務上的成功率是 90%，而一位顧客的完整對話需要 agent 連續正確處理三個子任務（找到訂單、判斷政策、執行動作），三步彼此獨立時整段對話全對的機率只有 0.9 的 3 次方，約 73%。同樣的道理，一位每週回來問三次的老顧客，三次體驗都良好的機率也遠低於單次成功率。這就是第 27 章介紹的 **pass^k**（同一題連跑 k 次全部成功的比例）在 production 的意義：使用者感受到的是一致性，而不是平均值。

因為不確定性要靠證據逐步消除，合理的做法是把專案切成幾個階段，每個階段只回答一組問題，回答完了才往下走。業界把這種做法稱為 **stage gate**（階段關卡）：每兩個階段之間有一道閘門，閘門有明確的 **退出條件**（exit criteria，離開這個階段前必須成立的條件），而且條件要事先寫下、可以量測、由指定的人判定。例如「內部試用 → 有限上線」的其中一條退出條件是「regression set 上 pass^3 ≥ 0.80」，而不是「大家覺得穩定了」。

這張圖由左往右讀。上排是五個階段，方塊之間的 G1 到 G4 是四道閘門；第二列是每階段要回答的核心問題，從「值不值得做」一路收斂到「怎麼做得更便宜、更自主」。第三列是 autonomy 等級：注意它不是一開始就給滿，而是隨著證據增加才往上加，而且第 5 階段的 L3→L4 是「依動作」逐一晉升，不是整個系統一起升級，這和第 1 章的定義一致。第四列是流量：從完全離線的 eval set，到影子流量，再到依租戶分批開放，每一步都限制了出錯時的**爆炸半徑**（blast radius，一次失誤最多會影響多少使用者或金額）。最下面那條往回走的箭頭最常被忽略：閘門不只是往前開的門，也是往回退的依據，例如有限上線時嚴重違規超過門檻，就退回內部試用。

| 階段 | 核心問題 | 主要產出 | 典型團隊 | 典型時長（青鳥實際） |
|---|---|---|---|---|
| 1 探索 | 這個任務值不值得用 agent？成功長什麼樣？ | 一頁式提案、50 件以上已標註真實案例、人工基準、kill criteria | PM、domain expert、1 位 AI engineer | 1–2 週 |
| 2 Prototype | 在固定的 eval set 上做不做得到？ | 可跑的 agent、capability eval set、第一輪 error analysis、成本估算 | AI engineer 1–2 位、domain expert 兼任標註 | 3–6 週 |
| 3 內部試用 | 面對真實輸入時可不可靠？人會不會被它拖累？ | regression suite、shadow 報告、threat model、核准 UX、runbook | 加入 eval owner、security、SRE | 4–8 週 |
| 4 有限上線 | 真實使用者、真實副作用下，指標是否守得住？ | canary 計畫、SLO、on-call、線上 eval、回滾演練紀錄 | 加入客服營運、法務簽核 | 4–8 週 |
| 5 規模化 | 怎麼全量、降成本、擴大自主權而不退步？ | 多租戶設定、成本儀表板、autonomy 晉升紀錄、平台化元件 | 穩定的產品團隊＋平台團隊 | 持續 |

這張總表是本章的骨架，後面每一節展開其中一列。「典型時長」那欄是青鳥的實際數字，不是業界標準：任務越簡單、副作用越可回復，階段就越短；碰到金流、醫療、法律這類高風險領域，第 3、4 階段常常要拉長好幾倍。表裡最值得注意的是團隊那欄：人數隨階段增加，而且新加入的角色（eval owner、security、SRE、法務）都是在「還沒有真實使用者受影響」之前就進場。等到出事才找資安與 SRE，通常已經晚了一個階段。

> [!warning] 常見誤解
> 「階段與關卡是大公司的官僚流程，小團隊快速迭代就好。」閘門的成本是一張單子和一次半小時的審查，跳過閘門的成本是第 2 章那種「用真實顧客做實驗」的事故。小團隊可以讓同一個人兼任好幾個角色、可以讓階段很短，但不應該省略「事先寫下門檻」這一步：它是唯一能讓「我覺得好多了」變成可討論、可反駁的東西。

## 38.3 退出條件的語言：指標、門檻與樣本

退出條件要能被機器判定，就得先有一套共同的指標詞彙。下面這張表是青鳥客服 agent 用到的主要指標；它們大多在第 27 章（eval）與第 29 章（observability）定義過，這裡重點放在「當作閘門門檻時要注意什麼」。

| 指標 | 定義 | 為什麼重要 | 當門檻時的陷阱 |
|---|---|---|---|
| eval 成功率 | 固定題庫上，outcome grader 判定成功的比例 | 能力的基本盤 | 題庫太小或太舊，分數高不代表線上好 |
| pass^k | 同一題連跑 k 次全部成功的比例 | 衡量一致性，面向使用者的 agent 要看這個 | k 要固定且寫明；不同 k 不可比 |
| 升級率（escalation rate） | 轉給真人處理的對話比例 | 反映 agent 接得住多少、知不知道自己接不住 | 太高是能力不足，太低可能是該轉沒轉 |
| 正確解決率 | 抽查中被判定「正確且完整解決」的比例 | 防止「沒升級但其實答錯」 | 只看沒升級的對話會高估 |
| 核准修改率 | L3 核准時，人修改了 agent 提議參數的比例 | 判斷 agent 的提議是否可信、能否晉升 L4 | 核准率高不代表可信（第 21 章的 approval fatigue） |
| 嚴重政策違規數 | 違反硬性政策的次數（例如超額退款、洩漏他人資料） | 安全底線 | 要用「零事件時的上限」解讀，不能只看 0 |
| 每件成本 | 一件任務的模型、tool、sandbox 成本總和 | 單位經濟能不能成立 | 要含重試與升級後真人處理的成本 |
| p95 延遲 | 95% 的回應在多少秒內完成 | 同步客服的體驗 | 平均值會掩蓋長尾 |

這些指標分成兩種角色。**目標指標**是這個階段要「爬上去」的東西，例如 eval 成功率、正確解決率；**護欄指標**（guardrail metric）是「不准變差」的東西，例如嚴重違規數、CSAT（顧客滿意度分數）與真人基準的差距、成本上限。一道閘門通常同時包含兩種：只看目標指標，團隊會為了衝分數犧牲安全或成本；只看護欄指標，永遠沒有人知道離目標還多遠。另一個維度是**硬性與建議**：硬性條件未達就不能過；建議條件未達可以「有條件通過」，但要寫下例外理由、負責人與補齊期限。青鳥把 p95 延遲放在建議條件，因為慢一點的正確答案比快速的錯誤答案好，但延遲不能無限期地被豁免。

門檻怎麼定？有三個來源，最好同時參考。第一是**人工基準**：真人客服處理同類問題的正確率、升級率與成本，這是探索階段就要量的東西，沒有基準，「agent 夠好」就沒有參照。第二是**商業條件**：如果真人處理一件的成本是 C，agent 每件成本加上升級後真人處理的分攤成本，必須明顯低於 C，專案才成立。第三是**風險承受度**：嚴重違規的門檻不是「比真人少」，而是由 domain expert 與 security 依損失大小訂定，通常是零容忍再加上偵測與補救的要求。

有了門檻，還要問「這個數字可信嗎？」這是最常被跳過的一步。用 20 題測出 95% 成功率，和用 1,000 題測出 95%，證據強度完全不同。解法是比較 **信賴區間**（confidence interval，在給定信心水準下真實比例可能落在的範圍）中對自己最不利的那一端：要證明「成功率 ≥ 90%」，就看下限是否 ≥ 90%；要證明「升級率 ≤ 30%」，就看上限是否 ≤ 30%。比例型指標常用 **Wilson score interval**，它在樣本少或比例接近 0、1 時比教科書的常態近似穩定。對「零事件」也有一條好記的經驗法則，叫 **rule of three**：n 次觀察中一次都沒發生，95% 信心下真實發生率的上限約為 3/n。觀察了 300 件零違規，只能說違規率大概不超過 1%，不能說是 0。

```python
from __future__ import annotations

from math import comb, sqrt


def pass_hat_k(trials: list[list[bool]], k: int) -> float:
    """pass^k 的無偏估計：每題跑 n 次、成功 c 次，該題 k 次全成功的機率估為 C(c,k)/C(n,k)。"""
    return sum(comb(sum(t), k) / comb(len(t), k) for t in trials) / len(trials)


def pass_at_k(trials: list[list[bool]], k: int) -> float:
    """pass@k：k 次中至少成功一次，估為 1 − C(n−c,k)/C(n,k)。"""
    return sum(1 - comb(len(t) - sum(t), k) / comb(len(t), k) for t in trials) / len(trials)


def wilson_lower(successes: int, n: int, z: float = 1.96) -> float:
    """成功率 95% 信賴區間的下限（Wilson score interval），樣本少時比直接看比例保守。"""
    p = successes / n
    denom = 1 + z * z / n
    centre = p + z * z / (2 * n)
    half = z * sqrt(p * (1 - p) / n + z * z / (4 * n * n))
    return (centre - half) / denom


# 兩組題目的平均成功率相同（80%），但失敗的分布不同
spread = [[True] * 4 + [False]] * 10                         # 每題都偶爾失敗
concentrated = [[True] * 5] * 8 + [[False] * 5] * 2           # 8 題穩定、2 題永遠失敗
for name, trials in [("失敗分散", spread), ("失敗集中", concentrated)]:
    print(f"{name}: pass^1={pass_hat_k(trials, 1):.2f}  pass^3={pass_hat_k(trials, 3):.2f}  "
          f"pass@3={pass_at_k(trials, 3):.2f}")

print("\n觀察到 95% 成功率時，樣本數與 95% 信賴下限：")
for n in (20, 60, 200, 1000):
    print(f"  n={n:<5} 下限={wilson_lower(round(0.95 * n), n):.3f}")

assert abs(pass_hat_k(spread, 1) - pass_hat_k(concentrated, 1)) < 1e-9
assert pass_hat_k(spread, 3) < pass_hat_k(concentrated, 3)
assert wilson_lower(19, 20) < 0.90 < wilson_lower(950, 1000)
```

```text
失敗分散: pass^1=0.80  pass^3=0.40  pass@3=1.00
失敗集中: pass^1=0.80  pass^3=0.80  pass@3=0.80

觀察到 95% 成功率時，樣本數與 95% 信賴下限：
  n=20    下限=0.764
  n=60    下限=0.863
  n=200   下限=0.910
  n=1000  下限=0.935
```

第一段輸出說明 pass^k 為什麼不能用成功率代替。兩組題目的平均成功率都是 80%，但「失敗分散」那組每題都有 20% 的機率出錯，連跑 3 次全對只剩 0.40；「失敗集中」那組的失敗全部集中在兩題，其餘八題穩定，所以 pass^3 仍是 0.80。對使用者來說，前者代表「每位顧客都可能隨機碰到錯誤」，後者代表「某兩類問題 agent 根本不會，應該直接轉真人」，兩者的修法完全不同。順帶一提，pass@3（3 次中至少對一次）在前者是 1.00，這就是為什麼 pass@k 適合「有 verifier 可以挑出正確答案」的場景（例如 coding agent 跑測試），卻不適合當客服 agent 的上線門檻。

第二段輸出是樣本數的效果：同樣觀察到 95% 的成功率，20 題時信賴下限只有 0.764，連 80% 都不敢保證；200 題時下限 0.910，才足以支持「≥ 90%」的主張。這直接決定了閘門的設計：每條比率型條件都要附帶最小樣本數，樣本不足時判定為「樣本不足」而不是「通過」。它也決定了時程：如果有限上線每天只抽查 45 件，要累積 300 件就得一週，這是阿哲「下個月全面上線」在統計上做不到的原因之一。

## 38.4 階段一：探索

探索階段要回答的問題只有兩個：這個任務值不值得用 agent 做，以及「做好了」具體長什麼樣子。第 1 章的任務適合度三問在這裡派上用場：任務是不是開放的（步驟無法事先列舉）、結果是不是可驗證的、錯誤是不是可回復的。青鳥客服的「查貨態、判斷能否退貨、建立退貨單」三問都過；但「處理顧客對網店老闆的投訴」不可驗證、也沒有明確的正確答案，就被排除在 v1 範圍之外。三問不過的部分，答案可能是 workflow（第 18 章），也可能是根本不做。

這個階段最重要的產出是一批**已標註的真實案例**：從歷史客服紀錄中抽出至少 50 件，由 domain expert（青鳥的資深客服主管）標上「正確的處理方式是什麼」「需要查哪些系統」「什麼情況要轉真人」。這批案例同時是三樣東西的起點：prototype 的第一版 eval set、人工基準的量測樣本、以及成功標準的具體化。第 27 章引用的公開建議也是從 20 到 50 個真實失敗或真實任務開始，而不是先寫一千題合成資料。另一個產出是 **kill criteria**（停損條件）：事先寫下「出現什麼情況就停止這個專案」，例如「prototype 結束時 capability set 成功率低於 50%，且 error analysis 顯示主因是資料缺失而非 prompt」。停損條件讓「放棄」變成一個有尊嚴的決定，而不是拖到沒人敢提。

| 退出條件（G1） | 門檻 | 判定者 |
|---|---|---|
| 已標註的真實案例 | ≥ 50 件，涵蓋前 80% 的問題類型 | domain expert |
| 任務適合度三問 | 範圍內的任務三問全過 | AI engineer＋PM |
| 預估效益／成本 | ≥ 3 倍（含升級後真人處理的成本） | PM |
| 成功標準 | 已寫成可量測的定義並簽核 | domain expert＋PM |

效益／成本要求 3 倍而不是 1.1 倍，是因為探索階段的成本估算幾乎一定偏低：還沒算重試、還沒算長對話、還沒算升級後真人要從頭讀一遍對話的時間。常見陷阱有三個。第一是**用興奮選題**：挑最酷的任務而不是最痛、最可驗證的任務。第二是**沒有基準**：不量真人的表現，之後所有「agent 比較好」的主張都無從驗證。第三是**範圍無限**：「它什麼都能回答」不是範圍，「訂單、物流、退貨三類，其他轉真人」才是。

## 38.5 階段二：Prototype

prototype 要回答「在固定的題目上，做不做得到」。這裡的關鍵字是「固定」：把探索階段的標註案例變成可重跑的 **capability eval set**（能力題庫，起始通過率可以很低，作為往上爬的目標），每改一次 prompt、tool 或模型就重跑一次，用數字而不是印象判斷進步。第 4 章的 `loom` v0.1、第 5 章重構的 tools、第 6 章的 system prompt、第 7 章的 structured output，都是在這個階段長出來的。

這個階段最有價值的活動是 **error analysis**（錯誤分析）：把失敗的 trajectory 一條條讀過，歸類成失敗模式，再依頻率與嚴重度排序。青鳥第一輪讀了 38 條失敗，歸出五類：找錯訂單（顧客有多張訂單時）、政策判斷錯誤（鑑賞期與退貨期混淆）、tool 參數錯誤、過早宣告完成、以及答非所問。其中「政策判斷錯誤會導致錯誤退款」被標為**嚴重失敗類別**：只要有一條這類失敗沒有對策，不論總分多高都不能進入下一階段。這個設計讓團隊不會因為修好一堆小錯、總分漂亮，就帶著一個會亂退款的 bug 往前走。

| 退出條件（G2） | 門檻 | 判定者 |
|---|---|---|
| capability set 成功率 | 信賴下限 ≥ 0.70，n ≥ 50 | AI engineer（eval owner 若已指派） |
| 未處理的嚴重失敗類別 | 0 | domain expert |
| tool 副作用標註 | 100% 的 tool 標好 read／write／destructive | AI engineer＋security |
| 每件成本估算 | ≤ 新台幣 6 元（prototype 允許寬鬆） | AI engineer |

prototype 的成本門檻比較寬，是因為這時還沒做 prompt caching、model routing 與 context 壓縮（第 9、25、30 章），成本通常還有很大的下降空間；但要有門檻，免得一個本質上就要燒二十步的設計混過去。常見陷阱：**demo 驅動開發**，也就是為了週五的 demo 把 prompt 調到只對那五題有效，這正是 eval set 要防的事；**太早做 framework**，在只有一個 agent 時就抽象出一整套 `loom` 模組，第 23 章說明過為什麼要等到第二、第三個 agent 出現再抽；以及**沒標副作用**，讓「退款」和「查訂單」在 harness 裡一視同仁，到下一階段才發現核准流程無從掛起。

## 38.6 階段三：內部試用

內部試用要回答「面對真實輸入時可不可靠」，同時保證「出錯時沒有真實顧客受害」。真實輸入的長尾只有真實流量才有，所以這個階段的核心技巧是讓 agent 接觸真實輸入，但把它的輸出攔在人的手上。常見有三種做法，強度由弱到強：**dogfooding**（自家員工當使用者，例如青鳥員工用它查自己在合作網店的訂單）、**shadow mode**（影子模式：agent 對真實流量產生決策，但不送出、不執行，只和真人的實際處理比對）、以及 **copilot 模式**（agent 擬好回覆與動作，由內部客服核准後才送出，相當於 L1 到 L3）。

```text
 shadow mode 的資料流（真實流量，零副作用）

  顧客留言 ──┬──────────────────────────────► 真人客服 ──► 實際回覆與動作 ──► 顧客
            │                                                  │
            │ 複製一份（遮蔽 PII 後）                            │ 寫入決策紀錄
            ▼                                                  ▼
       agent（tool 走 dry-run：讀取照常，寫入只記錄不執行）   ┌──────────────┐
            │                                                │   比對器      │
            └──── 提議的回覆、提議的動作與參數 ──────────────►│ 動作一致嗎？  │
                                                             │ 參數一致嗎？  │
                                                             │ 該轉真人嗎？  │
                                                             └──────┬───────┘
                                                                    ▼
                                         shadow 一致率、分歧樣本 → error analysis → regression set
```

這張圖的重點在兩條線的分岔點。顧客的留言照常走上面那條線，由真人客服處理並回覆，顧客完全不知道 agent 存在；同一則留言複製一份給 agent，agent 可以呼叫讀取類 tool（查訂單、查物流），但所有寫入類 tool 都走 **dry-run**（只回傳「如果執行會發生什麼」，不真正執行），這需要第 5 章的副作用標註才做得到。右下角的比對器把 agent 的提議和真人的實際決定對齊，算出 **shadow 一致率**（agent 與真人決定相同的比例），並把分歧的案例送去人工判讀。注意分歧不一定是 agent 錯：青鳥第一週的分歧樣本裡，約有兩成是真人客服自己違反了退貨政策，這些案例反過來修正了標註準則。

shadow 的限制也要知道。它看不到「如果 agent 這樣回覆，顧客接下來會怎麼說」，所以多輪對話的後半段無法評估；它也無法測量核准 UX 與客服的工作負擔。因此青鳥在 shadow 跑兩週後，改為 copilot 模式讓內部客服核准每一個寫入動作，這時就能量測第 21 章的核准修改率與決定時間。內部試用的另一半工作在 agent 之外：Maya 完成第 31 章的 threat model，SRE 寫好 runbook 並演練 **kill switch**（一鍵關閉 agent 或某個 tool 的開關），eval owner 把試用中蒐集到的失敗加進 **regression suite**（回歸題庫，目標接近 100% 通過，用來守住已經會的事）。

| 退出條件（G3） | 門檻 | 判定者 |
|---|---|---|
| regression set 成功率 | 信賴下限 ≥ 0.85，n ≥ 200 次試驗 | eval owner |
| pass^3 | ≥ 0.80 | eval owner |
| shadow 一致率 | 信賴下限 ≥ 0.85，n ≥ 300 | domain expert |
| 核准修改率 | 信賴上限 ≤ 0.10，n ≥ 100 | 客服主管 |
| 近 14 天 P0 事故 | 0 | SRE |
| 每件成本 | ≤ 新台幣 4 元 | AI engineer |
| threat model | 已簽核，高風險項目都有對策 | security |
| runbook 與 kill switch | 已演練 | SRE |
| p95 延遲（建議） | ≤ 20 秒 | PM |

這個階段的陷阱特別隱晦。**友善使用者偏誤**：內部員工會用「正確的方式」提問，也比真實顧客寬容，試用數字因此偏高；對策是 shadow 一定要接真實顧客流量，而不只是員工測試。**把試用當上線**：第 2 章的事故正是如此，只要碰到真實顧客的錢，就已經是第 4 階段，必須先過 G3。**沒有回饋管道**：客服按了「修改後核准」卻沒有地方記下為什麼改，這些最有價值的訊號就流失了；核准卡片上要有一個必填的修改理由欄位。

## 38.7 階段四：有限上線

有限上線第一次讓 agent 在真實使用者面前產生真實副作用，所以這個階段的設計核心是**限制爆炸半徑並保證退得回去**。限制的維度有很多：租戶（先開 3 家、再 30 家）、流量比例、問題類型（先只開查詢與退貨單，不開退款）、時段（先避開旺季尖峰）、以及 autonomy（寫入一律 L3）。第 36 章講過 canary、A/B 與 shadow 的機制，這裡把它們排成一條有自動回滾的推進路徑。

```text
 有限上線的推進狀態機（每一格都要停留到樣本足夠）

        ┌──────────── 護欄指標觸發（嚴重違規、錯誤率、成本暴增）────────────┐
        │                                                               │
        ▼                                                               │
  ┌──────────┐  G3 通過  ┌─────────┐  達標＋n≥300  ┌─────────┐  達標  ┌──────────┐  G4 通過
  │ 關閉     │─────────►│ 3 家網店 │─────────────►│ 30 家   │──────►│ 25% 租戶 │─────────► 規模化
  │(kill)    │          │ ~1% 流量 │              │ ~5% 流量 │       │          │
  └──────────┘          └────┬────┘              └────┬────┘       └────┬─────┘
        ▲                    │ 未達標：停留、修正      │                  │
        │                    ▼                        ▼                  ▼
        └──── 手動或自動回滾：關 flag、退回上一格、未完成的對話轉真人 ◄───────┘
```

這張圖由左往右是推進，往下、往回是退路。每一格是一個穩定狀態，進到下一格的條件是「本格的指標達標且樣本足夠」，而不是「過了一週」；所以時間只是累積樣本的手段，不是推進的理由。圖上方的回饋線是自動回滾：任何一格的護欄指標觸發（例如嚴重政策違規出現、錯誤率超過 SLO、單日成本暴增三倍），就自動關掉 feature flag，回到「關閉」狀態，進行中的對話轉給真人並附上摘要。回滾路徑本身必須在進入第一格之前演練過；沒演練過的回滾，就和沒備份過的還原一樣，只是一個願望。

這個階段要開始用第 34 章的 **SLO**（service level objective，服務水準目標）來營運：例如「每週正確解決率 ≥ 90%」「p95 延遲 ≤ 15 秒」「嚴重違規 0」。SLO 讓 on-call 知道什麼時候該被叫醒，也讓閘門與日常營運使用同一套數字。另一個關鍵是**線上 eval**：從真實對話中每天抽樣，由 domain expert 與校準過的 LLM judge（第 27 章）判定是否正確解決；只看「沒有升級、顧客沒抱怨」會嚴重高估，因為很多答錯的顧客只是默默離開。

| 退出條件（G4） | 門檻 | 判定者 |
|---|---|---|
| 抽查判定正確解決率 | 信賴下限 ≥ 0.90，n ≥ 300 | domain expert＋eval owner |
| 升級率 | 信賴區間落在 0.05–0.30 之間，n ≥ 300 | 客服營運 |
| 嚴重政策違規 | 0（並以 rule of three 檢視上限） | security＋domain expert |
| CSAT 與真人基準差 | ≥ −0.10（5 分制） | PM |
| 每件成本 | ≤ 新台幣 3.5 元 | PM＋AI engineer |
| 回滾演練 | 在 production 環境演練通過 | SRE |
| p95 延遲（建議） | ≤ 15 秒 | PM |

升級率同時有上限與下限，這是客服 agent 特有的設計。升級率太高，代表 agent 接不住，效益不成立；升級率太低也很危險，常見原因是 agent 把應該轉真人的情況（顧客明確要求真人、涉及法律爭議、情緒激動）硬接下來。所以下限不是要求 agent 多轉，而是一個警報：低到不合理時，要抽樣檢查那些「沒轉的對話」是否其實該轉。陷阱方面，**擴張太快**是最常見的，一週內從 3 家跳到全部，等於沒有有限上線；**樣本代表性不足**也常見，先開的 3 家都是合作關係好、商品單純的網店，數字好看但無法推論到賣生鮮、跨境商品的網店，所以第二格的 30 家要刻意涵蓋不同類型。

## 38.8 階段五：規模化

規模化不是「上線完成」，而是進入一個持續運轉的狀態：全量開放後，問題從「能不能上」變成「怎麼更便宜、更自主、而且不退步」。這個階段有四條主線。第一是**多租戶與配置**：每家網店的退貨政策不同，政策要變成租戶設定而不是 prompt 裡的分支（第 36、42 章）。第二是**成本優化**：prompt caching 命中率、model routing（簡單問題給小模型）、context 壓縮，第 30 章的手段在這裡才真正值得投資，因為流量夠大，省下的每一分錢會乘上百萬次。第三是**持續評估**：production trace 中的失敗不斷加入 regression suite，模型、prompt、tool 的任何變更都要先過 CI 中的 eval gate。第四是**autonomy 晉升**：用累積的證據把特定動作從 L3 移到 L4。

```text
 規模化階段的持續改進迴圈

   production 流量 ──► trace（第 29 章）──► 線上抽樣評分 ──► 失敗與分歧樣本
        ▲                                                       │
        │                                                       ▼
   漸進 rollout ◄── CI eval gate ◄── regression suite ◄── error analysis 與標註
   （canary）       （必須不退步）    （持續變大）          （domain expert）
        │
        └─► autonomy 晉升／降級審查（每月，依每個動作的證據）
```

這個迴圈是第 37 章「資料飛輪」在營運面的樣子。每一條 production 中的失敗都可能變成一道 regression 題目，所以題庫會隨時間變大、變得更像真實流量；任何變更都要通過 CI 中的 eval gate 才能進 canary，canary 的線上指標再回到 trace。迴圈中最容易斷掉的是「error analysis 與標註」那一格，因為它需要 domain expert 的時間，而 domain expert 通常有自己的正職；所以在組織上要把這件事寫進某個人的職責（38.10 節）。最下面那條支線是 autonomy 審查：晉升與降級都依證據，而且是逐個動作審查。

autonomy 晉升為什麼要逐個動作？因為同一個 agent 的不同動作，風險與證據量完全不同。建立退貨單可回復、量大、客服幾乎從不修改；500 元以上的退款不可回復、量少、客服常常修改金額。第 21 章已經示範用核准率、修改率與事後抽查錯誤率判斷「人在這裡有沒有增加資訊」；這裡把它寫成晉升與降級的規則，並加上**遲滯**（hysteresis，晉升線比降級線嚴格，避免指標在門檻附近抖動時等級來回切換）。

```text
 單一動作的 autonomy 狀態機（例：refund ≤ 500 元）

             件數 ≥ 500、修改率 ≤ 2%、抽查錯誤 ≤ 1%、零嚴重事故
   ┌────────┐ ───────────────────────────────────────────────► ┌────────┐
   │   L3   │                                                   │   L4   │ 邊界內自動執行
   │每筆核准│ ◄─────────────────────────────────────────────── │每日抽查│ 超出邊界仍走核准
   └────────┘    抽查錯誤 > 3%，或任何一件嚴重事故（立即降級）    └────────┘
      ▲                                                           │
      └───────────── 政策或模型重大變更後：重新累積證據 ◄───────────┘
```

這張狀態機有三個要點。晉升條件是四個條件同時成立，其中「件數 ≥ 500」保證證據量，修改率與抽查錯誤率分別回答「人有沒有在改」和「人沒改的那些到底對不對」。降級條件比晉升寬鬆得多（3% 對 1%），但只要一件嚴重事故就立即降級，因為嚴重事故的代價不對稱。最下面那條線最容易被忘記：退款政策改版或換模型時，舊的證據就不再代表新的行為，應該重新在 L3 累積證據，或至少提高抽查比例，第 30 章談模型升級時也討論過這點。

```python
from __future__ import annotations

from dataclasses import dataclass


@dataclass
class ActionStats:
    action: str
    level: str               # 目前等級：L3（每筆核准）或 L4（邊界內自動）
    decisions: int           # 觀察期內的件數（L3 是核准件數，L4 是自動執行件數）
    edit_rate: float         # L3：核准者修改參數的比例
    audit_error: float       # 事後抽查判定「當初不該這樣做」的比例
    severe_incidents: int    # 觀察期內的嚴重事故


def next_level(s: ActionStats) -> tuple[str, str]:
    """晉升門檻比降級門檻嚴格（遲滯），避免在邊界上來回切換。"""
    if s.level == "L3":
        if s.decisions >= 500 and s.edit_rate <= 0.02 and s.audit_error <= 0.01 and s.severe_incidents == 0:
            return "L4", "證據足夠：件數、修改率、抽查錯誤率都達標"
        return "L3", "維持：證據不足或人仍在修正 agent 的決定"
    if s.severe_incidents > 0 or s.audit_error > 0.03:
        return "L3", "降級：抽查錯誤率或事故超過降級線"
    return "L4", "維持：在降級線以內（晉升線 1%，降級線 3%）"


cases = [
    ActionStats("create_return", "L3", 600, 0.00, 0.000, 0),
    ActionStats("refund<=500", "L3", 820, 0.01, 0.006, 0),
    ActionStats("refund>500", "L3", 140, 0.09, 0.040, 0),
    ActionStats("refund<=500", "L4", 2400, 0.0, 0.021, 0),
    ActionStats("refund<=500", "L4", 2600, 0.0, 0.012, 1),
]
for s in cases:
    lvl, why = next_level(s)
    print(f"{s.action:<14}{s.level} → {lvl}  {why}")
results = [next_level(s)[0] for s in cases]
assert results == ["L4", "L4", "L3", "L4", "L3"]
```

```text
create_return L3 → L4  證據足夠：件數、修改率、抽查錯誤率都達標
refund<=500   L3 → L4  證據足夠：件數、修改率、抽查錯誤率都達標
refund>500    L3 → L3  維持：證據不足或人仍在修正 agent 的決定
refund<=500   L4 → L4  維持：在降級線以內（晉升線 1%，降級線 3%）
refund<=500   L4 → L3  降級：抽查錯誤率或事故超過降級線
```

前兩列是晉升：建立退貨單 600 件零修改、零抽查錯誤，正是第 21 章分析過的「人在這裡沒有增加資訊」；500 元以下退款 820 件、修改率 1%、抽查錯誤 0.6%，也通過。第三列是 500 元以上的退款：140 件證據不足，而且 9% 的修改率說明客服仍在實質修正 agent 的決定，留在 L3。第四列已經在 L4，抽查錯誤率 2.1% 超過晉升線 1%，但沒超過降級線 3%，所以維持 L4 並觀察；如果沒有遲滯，它會在 L3 和 L4 之間每週切換一次，客服和顧客都會很困惑。最後一列抽查錯誤率雖然只有 1.2%，但發生了一件嚴重事故，立即降級。

規模化階段的陷阱多半是「慢慢腐化」型的。**autonomy 蠕變**：沒有經過審查，就因為「最近都沒事」把邊界從 500 元調到 2,000 元。**題庫老化**：regression suite 停在半年前的樣子，新的商品類型、新的詐騙話術都不在裡面，分數永遠漂亮。**換模型不重測**：供應商發布新版本或下架舊版本時，直接切換 alias；公開的工程事故報告一再顯示，即使是降低延遲的預設值調整，也可能讓品質明顯下降（見本節的 2026 現況）。**成本悄悄長大**：對話變長、tool 變多、重試變頻繁，每件成本每月漲一點，等到月帳單才發現。

> [!note] 2026 現況
> 截至 2026 年 10 月，Anthropic 在 2026-04-23 發布的 Claude Code 品質事故 postmortem 是公開資料中很具體的一份「規模化階段變更管理」教材：一次為了降低延遲而調低預設 reasoning effort 的變更，以及一個裁掉舊 thinking 的快取優化 bug，都讓使用者感受到品質下降；報告提出的改進包括對每個模型做更廣的 eval、做 ablation、設 soak period（新版本在小範圍長時間觀察）與漸進 rollout。這和本章的 G4 與規模化迴圈是同一套邏輯：任何可能影響「聰明程度」的變更，都要當成一次小型上線來處理。

## 38.9 上線前檢查清單：功能、eval、安全、營運、法務

閘門的量化條件回答「夠不夠好」，但上線還需要回答「有沒有漏掉什麼」。第一次讓真實使用者接觸 agent 之前（也就是 G3），青鳥用下面這份清單逐項確認，每一項都要有負責人簽名與證據連結；附錄 D 收錄了完整版本。

這份清單之所以把法務列成獨立面向，是因為 agent 說出口的話會被當成公司的話。公開判例中最常被引用的是 2024 年加拿大的 Moffatt v. Air Canada 案：航空公司網站上的聊天機器人給了錯誤的退款政策資訊，裁決認定航空公司要對其網站上的資訊負責，不能把聊天機器人當成獨立的個體推卸責任。對青鳥來說，這代表「agent 承諾的補償」必須有政策邊界、有紀錄，而且超出邊界的承諾要有人工補救流程。隱私方面，trace 裡充滿了顧客的姓名、地址、訂單內容，保存多久、誰能看、能不能拿去訓練或做 eval，都要在上線前和法務對齊，並符合所在地的個人資料保護法規。

> [!note] 2026 現況
> 截至 2026 年 10 月，歐盟 AI Act 經 AI Omnibus 修正後（2026-07-27 生效），第 50 條的透明義務自 2026-08-02 起適用：與人互動的 AI 系統要讓使用者知道自己在和 AI 互動（既有生成式系統的合成內容標示義務延到 2026-12-02）；Annex III 高風險系統的義務延到 2027-12-02。客服 agent 通常不屬於高風險類別，但若服務歐盟使用者，透明告知是上線前就要處理的項目。各國法規的適用範圍要由法務依產品與市場判斷，本書只提供概念層級的整理（第 34 章）。

## 38.10 組織與角色

agent 專案失敗的原因，常常不是沒有人會寫程式，而是某件必要的工作「不是任何人的工作」。最典型的是 eval：大家都同意 eval 很重要，但如果沒有一個人的績效與 eval 題庫的品質綁在一起，題庫就會在第三個月停止更新。所以青鳥在進入內部試用之前，就把下面五個角色明確指派出去；小團隊可以一人兼多職，但每個角色都要有名字。

- **AI engineer**：負責 agent 本身，包括 loop、tools、prompt、context 與成本。從探索階段就在，是唯一全程參與的工程角色。青鳥是 Iris。
- **eval owner**：負責題庫、grader、judge 校準與 eval 報告，並在閘門會議上報告數字。最好不是 AI engineer 本人，原因和「寫程式的人不該只靠自己 review」一樣：自己出的題自己考，容易無意間迎合。青鳥在 prototype 後期指派了一位資料工程師兼任。
- **domain expert**：定義什麼是正確答案，標註案例、判讀分歧、審查政策類失敗。青鳥是資深客服主管，每週固定撥出半天。沒有這個角色，eval 只能測「格式對不對」，測不到「處理得對不對」。
- **SRE**：負責 SLO、告警、on-call、容量、回滾與 kill switch。agent 的事故和一般服務不同：服務沒掛，但開始一本正經地答錯，所以 SRE 要和 eval owner 一起定義「品質型」的告警。
- **security**：負責 threat model、權限設計、稽核與紅隊測試，對 G3 以後的每道閘門有否決權。青鳥是 Maya。

除了這五個角色，PM 負責範圍、時程與商業指標，並主持閘門會議；法務在 G3 前完成審查；客服營運負責核准者的排班、訓練與回饋。下表是各角色在各階段的參與程度。

| 角色 | 1 探索 | 2 Prototype | 3 內部試用 | 4 有限上線 | 5 規模化 |
|---|---|---|---|---|---|
| AI engineer | 主導技術可行性 | 主導 | 主導 | 主導 | 主導，逐步移交平台團隊 |
| eval owner | — | 建立題庫（可由 AI engineer 暫代） | 主導 regression 與 shadow 報告 | 主導線上 eval | 主導飛輪與 eval gate |
| domain expert | 主導標註與成功標準 | 標註、判讀失敗 | 判讀分歧、簽核 G3 | 抽查、簽核 G4 | 定期抽查、政策變更 |
| SRE | — | 諮詢 | 寫 runbook、演練 | on-call、SLO | 容量、成本、多租戶 |
| security | 風險初評 | 審查 tool 副作用 | threat model、簽核 G3 | 監控、事故處理 | 定期紅隊、autonomy 審查 |

這張表要直的讀，也要橫的讀。直的讀，每一欄是「這個階段的閘門會議上該有誰」：G3 的會議如果沒有 security 和 SRE，那就不是 G3。橫的讀，每一列是一個人的工作負荷曲線：domain expert 在探索階段最忙，SRE 在有限上線最忙，eval owner 的工作則隨規模一路增加，這也是為什麼 eval owner 不能只是「有空時順便做」。

```text
  eval owner 報告指標 ──► stage gate 評估器（38.12 節）──► 判定結果

        全部達標              只有建議項未達          必要項未達           任何角色行使否決
```

這張圖把「誰說了算」講清楚。數字由 eval owner 報告、由評估器機械地判定，所以會議不是在爭論「夠不夠好」，而是在處理判定結果：全部達標就開門；只有建議項未達，可以帶著書面例外進入下一階段，例外要有負責人和期限，期限到了自動複查；必要項未達，就列出每一項的負責人與下次會議日期。最右邊的否決權是刻意設計的不對稱：任何人都不能把未達標的必要項「討論」成通過，但 security 可以把已達標的閘門擋下，因為有些風險（例如新發現的資料外洩路徑）還沒來得及變成指標。PM 握有時程，卻沒有降低門檻的權力，這是避免「雙 11 決定門檻」的組織設計。

## 38.12 動手做：stage gate 評估器

這一節把閘門變成程式。設計重點有四個：每條條件是資料而不是 if-else，方便審查與版本化；比率型條件要有最小樣本數，並用 Wilson 信賴區間中對自己不利的那一端比較；沒有量測的指標一律當成未達標，因為「沒量」是最常見的漏洞；結果分成「可進入」「有條件通過」「不可進入」三種，並列出每一個未達項目與差距。為了讓輸入有真實感，regression set 的 pass^3 直接從試驗矩陣算出（50 題、每題 5 次），而不是手填一個數字。

```python
from __future__ import annotations

from dataclasses import dataclass
from math import comb, sqrt


@dataclass(frozen=True)
class Criterion:
    metric: str
    op: str                  # ">=" 或 "<="
    threshold: float
    label: str
    hard: bool = True        # hard 未達就不能過；soft 未達可「有條件通過」，要有書面例外與期限
    min_n: int = 0           # >0 代表比率型指標：要有足夠樣本，並用信賴區間的保守端比較


@dataclass
class Obs:
    value: float
    n: int = 0               # 比率型指標的樣本數


def wilson(p: float, n: int, z: float = 1.96) -> tuple[float, float]:
    denom = 1 + z * z / n
    centre = (p + z * z / (2 * n)) / denom
    half = z * sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / denom
    return centre - half, centre + half


def pass_hat_k(trials: list[list[bool]], k: int) -> float:
    return sum(comb(sum(t), k) / comb(len(t), k) for t in trials) / len(trials)

def check(c: Criterion, obs: Obs | None) -> str | None:
    """回傳 None 代表達標，否則回傳未達原因。"""
    if obs is None:
        return "未量測（沒有數字就當作未達標）"
    value = obs.value
    if c.min_n:
        if obs.n < c.min_n:
            return f"樣本不足：n={obs.n} < {c.min_n}"
        lo, hi = wilson(obs.value, obs.n)
        value = lo if c.op == ">=" else hi       # 用對自己最不利的那一端比較
    ok = value >= c.threshold if c.op == ">=" else value <= c.threshold
    if ok:
        return None
    shown = f"{obs.value:g}" + (f"（保守端 {value:.3f}）" if c.min_n else "")
    return f"實際 {shown}，門檻 {c.op} {c.threshold:g}"


def evaluate(gate: str, metrics: dict[str, Obs]) -> tuple[str, list[str]]:
    hard_fail, soft_fail = [], []
    for c in GATES[gate]:
        if (why := check(c, metrics.get(c.metric))) is not None:
            (hard_fail if c.hard else soft_fail).append(f"{'[必要]' if c.hard else '[建議]'} {c.label}：{why}")
    if hard_fail:
        decision = "不可進入下一階段"
    elif soft_fail:
        decision = "有條件通過（建議項需書面例外與補齊期限）"
    else:
        decision = "可進入下一階段"
    return decision, hard_fail + soft_fail


def report(title: str, gate: str, metrics: dict[str, Obs]) -> tuple[str, list[str]]:
    decision, gaps = evaluate(gate, metrics)
    print(f"── {title}｜{gate}\n   判定：{decision}")
    for g in gaps:
        print("   ", g)
    return decision, gaps
```

逐段解說這份輸出。

**情境 P（第 9 週，prototype → 內部試用）**：capability set 成功率 0.82、120 題，Wilson 下限約 0.74，高於 0.70 的門檻；嚴重失敗類別、副作用標註與成本也都達標，所以可以開門。注意這裡的 0.82 對上線來說遠遠不夠，但 G2 只問「做不做得到」，門檻本來就比較低；每道閘門只回答自己那一組問題。

**regression set 的兩行**是從試驗矩陣算出來的。修正前，50 題中有 30 題 5 次全對、14 題錯 1 次、4 題錯 2 次、2 題錯 4 次，平均成功率 0.88，看起來不差；但 pass^3 只有 0.72，因為失敗分散在 20 題上。修正多訂單選擇的問題後，成功率 0.96、pass^3 0.892。

**情境 A（第 12 週）**列出四個必要項未達。第一項很有教育意義：成功率 0.88 本身高於 0.85，但 250 次試驗的 Wilson 下限是 0.834，證據還不足以支持「≥ 0.85」。第二項是 pass^3 0.72。第三項是核准修改率 0.14，上限 0.198，客服仍在大量修改 agent 的提議。第四項是 runbook 沒有任何數字，評估器把「未量測」當作未達標，而不是忽略它；這正是第 2 章「Maya 的問題沒人答得出來」那一類的漏洞。

**情境 B（第 15 週）**所有必要項都過了，只剩 p95 延遲 22 秒超過建議門檻 20 秒，所以判定為「有條件通過」：可以進入有限上線，但要寫下例外理由、負責人與補齊期限。

**情境 C、D、E** 是同一道 G4 在三個時間點的樣子。C 是有限上線第 1 週，正確解決率 0.95 看起來已經過關，但只有 60 件抽查，評估器直接判定「樣本不足」，連信賴區間都不算。D 是第 6 週，正確解決率在 1,200 件上站穩了，卻冒出新問題：升級率 3%，信賴下限 0.022 低於 0.05 的下限，代表 agent 可能把該轉真人的對話硬接下來。E 是修正轉真人規則後的第 8 週，升級率回到 12%，全部條件達標。

| 設計選擇 | 這份評估器的做法 | 替代做法 | 為什麼這樣選 |
|---|---|---|---|
| 條件的表示 | 資料（`Criterion` 清單） | 寫死在程式邏輯 | 可以做 code review、版本化、在閘門會議上直接展示 |
| 比率的比較 | 信賴區間的保守端 | 直接比較觀察值 | 避免小樣本的好運氣被當成證據 |
| 缺少的指標 | 當作未達標 | 略過或當作 0 | 略過會讓「沒量」變成通過；當 0 對「≤」條件反而會通過 |
| 結果分級 | 可進入／有條件／不可進入 | 只有通過與否 | 讓非關鍵項有可追蹤的例外，而不是被私下忽略 |
| 兩側界限 | 同一指標可有上下限（升級率） | 只設單側 | 有些指標太低也是警訊 |

這份評估器刻意沒有做的事也值得列出：它不檢查指標是怎麼算出來的（題庫是否過時、judge 是否校準），那是 eval owner 與第 27 章的責任；它沒有處理多重比較的問題（同時檢查很多條件時，總有一條會因為運氣不好而失敗或通過）；它也沒有記錄閘門判定的歷史。實際導入時，建議把每次判定結果連同指標快照、條件版本與簽核人寫進稽核日誌，第 33 章的稽核 middleware 可以直接沿用。

## 38.13 實務應用

五階段與閘門的骨架在不同產品上都適用，但每個階段的重點、門檻與時長會跟著任務的風險與可驗證性改變。以下四個情境說明同一份路線圖要怎麼調整。

**情境一：電商與 SaaS 客服 agent（青鳥的主線）**。客服 agent 的特點是量大、同步、面向消費者，且有退款這類不可逆動作。因此 pass^k 與升級率是核心門檻，有限上線要依租戶分批，寫入動作從 L3 開始、逐個動作晉升。公開資料中，Sierra 的研究團隊發表了 τ-bench 系列，用模擬使用者、領域政策與工具環境評估客服 agent，並推廣以 pass^k 衡量一致性；這和本章 G3 用 pass^3 當門檻是同一個思路。要注意的是，benchmark 分數不能取代自家的 regression set，因為政策與工具都是你自己的（第 28 章）。

**情境二：內部 coding agent**。開發者是內部使用者，產出要經過 code review 與 CI 才會合併，所以「有限上線」的爆炸半徑天然就小，階段可以比客服短很多。重點門檻變成：在自家 repo 的任務集上 PR 被接受的比例、CI 通過率、reviewer 需要修改的程度，以及 sandbox 的安全審查。公開文件中，GitHub 的 Copilot coding agent 在 GitHub Actions 的臨時環境中執行，每個任務對應一個 branch 與 PR，由人 review 後才合併；這種「產出一定要經過人的合併動作」的設計，等於把 L3 的核准內建在既有的開發流程裡，第 39、43 章會詳談。

**情境三：保險理賠或金融文件處理 agent**。這類任務受法規監管、錯誤代價高，而且需要可稽核的決策理由。路線圖的形狀不變，但第 3 階段的 shadow 要跑得更久（常常要涵蓋完整的季度或業務週期），G3 與 G4 加入法遵與稽核單位的簽核，autonomy 可能長期停在 L3 甚至 L1（agent 只做初審與摘要，決定權一律在人）。這時「升級率」的意義改變：它不再是要壓低的成本，而是確保人有實質參與的指標。若服務對象涉及受規範的高風險用途，還要在探索階段就請法務判斷適用的法規類別。

**情境四：企業內部 IT helpdesk agent**。使用者是員工，容錯度比消費者高，但 agent 會碰到帳號、權限這類敏感動作。適合的路線是：探索階段先找出「高頻、低風險」的子任務（查 VPN 狀態、重設印表機佇列），prototype 與內部試用只開放唯讀與可回復動作；重設密碼、停用帳號這類動作即使到了規模化也維持 L3，並要求 step-up 驗證（第 33 章）。這個情境的常見陷阱是把「員工很寬容」當成可以跳過 G3 的理由，結果 agent 的權限設計從未經過 threat model。

| 產品類型 | 最關鍵的門檻 | 最長的階段 | autonomy 終點 | 特別注意 |
|---|---|---|---|---|
| 電商客服 | pass^k、升級率雙側界限、嚴重違規 | 有限上線 | 小額動作 L4 | 依租戶分批，樣本要涵蓋不同商品類型 |
| 內部 coding agent | PR 接受率、CI 通過率、sandbox 審查 | prototype | sandbox 內 L4，合併仍要人 | 既有 code review 就是 L3 核准 |
| 保險／金融文件 | 決策正確率、可稽核性、法遵簽核 | 內部試用（shadow） | 常停在 L1–L3 | 升級率是「人有參與」的證據 |
| IT helpdesk | 權限動作的錯誤率、step-up 覆蓋 | 內部試用 | 唯讀 L4，敏感動作 L3 | 不因使用者寬容而跳過 threat model |

這張表的共同點是：五個階段與「事先寫下、可量測、有樣本要求」的閘門都沒有變，變的是門檻的內容與每個階段停留的時間。所以導入時，最好的做法是先把 38.12 節的評估器結構拿過去，再和 domain expert 一起把條件改寫成自己領域的語言。

## 38.14 設計檢查清單

規劃或審查一個 agent 專案的上線路線時，逐項回答下面的問題。

1. 專案目前處於五個階段中的哪一個？團隊對這個答案是否一致，而且「是否碰到真實使用者的真實副作用」與階段名稱相符？
2. 每道閘門的退出條件是否在進入該階段之前就寫下，並有版本與簽核人？
3. 每條比率型條件是否有最小樣本數，並以信賴區間的保守端判定？
4. 面向使用者的動作，門檻是否包含 pass^k（並寫明 k），而不只有平均成功率？
5. 是否同時設定了目標指標與護欄指標（嚴重違規、成本、CSAT 與真人基準的差距）？
6. 升級率是否同時有上限與下限，並定期抽查「沒有升級的對話」？
7. 是否有事先寫好的 kill criteria，讓專案在證據不足時能被正式停止？
8. 有限上線的推進是否依樣本與指標，而不是依日期？自動回滾是否在第一格之前就演練過？
9. autonomy 是否逐個動作晉升，晉升與降級門檻是否有遲滯，政策或模型變更後是否重新累積證據？
10. eval owner、domain expert、SRE、security 是否都有具名的負責人，並出現在對應閘門的會議上？
11. 上線前檢查清單的五個面向（功能、eval、安全、營運、法務）是否每一項都有證據與簽名？
12. 「有條件通過」的例外是否有負責人與期限，期限到時是否會自動複查？
13. 規模化階段的 regression suite 是否持續從 production 失敗中補題，任何模型、prompt、tool 變更是否都要通過 CI eval gate？

## 38.15 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 試用期間就出現真實金錢損失 | 階段名稱與實際風險不符，把有限上線叫成試用 | 檢查試用中是否有真實顧客、真實寫入 | 先退回 shadow 或 copilot，補過 G3 再對外 |
| eval 分數很高，上線後投訴不斷 | 題庫太小、太舊或太像 demo；只看成功率不看 pass^k | 比較題庫與線上流量的問題類型分布；計算 pass^k | 從 production 失敗補題；門檻改用 pass^k 與信賴下限 |
| 閘門會議每次都在爭論「夠不夠好」 | 退出條件沒有事先寫下或不可量測 | 檢查閘門單上是否每一項都有數字與判定者 | 把條件資料化（38.12 節），會議只處理判定結果 |
| 升級率很低，PM 很滿意，但客訴變多 | agent 把該轉真人的對話硬接下來 | 抽樣檢查沒升級的對話，看是否有明確要求真人的情況 | 加上升級率下限警報；把「要求真人」列為必轉規則與 regression 題 |
| L4 動作的錯誤在數週後才被發現 | 晉升後沒有事後抽查，或抽查比例太低 | 查 L4 動作的抽查紀錄與比例 | 晉升時同時設定抽查比例與降級線；嚴重事故立即降級 |
| 換模型後品質悄悄下降 | 直接切換 alias，沒有跑 regression 與 canary | 比對換版前後的 trace 與線上抽樣分數 | 鎖定模型 snapshot；換版當成一次小型上線，過 eval gate 與 canary |
| eval 題庫半年沒更新 | eval 不是任何人的職責 | 查題庫的最後修改時間與負責人 | 指派 eval owner，把「production 失敗轉題目」寫進每週流程 |
| 回滾時才發現進行中的對話全部斷掉 | 回滾從未演練，沒有設計轉真人的交接 | 在 staging 與 production 做回滾演練 | 回滾流程包含對話轉交與摘要，列為 G4 必要條件 |

## 本章重點整理

- agent 專案有三種傳統軟體沒有的不確定性：行為非決定性、輸入長尾、自主權放大錯誤，所以需要用階段與證據逐步消除。
- 五個階段各自只回答一組問題：探索問值不值得、prototype 問做不做得到、內部試用問在真實輸入下可不可靠、有限上線問真實副作用下守不守得住、規模化問怎麼更便宜更自主而不退步。
- 每道閘門的退出條件要事先寫下、可以量測、由指定的人判定；PM 握有時程，但沒有降低門檻的權力。
- 面向使用者的 agent 要用 pass^k 衡量一致性；平均成功率相同時，失敗分散在多題上的 agent，使用者體驗會差很多。
- 比率型條件要有最小樣本數，並以信賴區間的保守端判定；零事件只能用 rule of three 推出上限，不能說發生率是 0。
- 閘門同時包含目標指標與護欄指標，並分成硬性與建議兩級；建議項未達可以有條件通過，但要有負責人與期限。
- 升級率要有上下限：太高代表接不住，太低可能代表該轉真人的對話被硬接下來。
- 只要碰到真實使用者的真實副作用，就已經是有限上線，不論它叫什麼名字。
- 有限上線依樣本與指標推進、而不是依日期推進，並在第一格之前演練過自動回滾與對話轉交。
- autonomy 依動作逐一晉升，晉升線比降級線嚴格（遲滯），嚴重事故立即降級，政策或模型重大變更後重新累積證據。
- 上線前檢查清單涵蓋功能、eval、安全、營運、法務五個面向，每一項都要有證據與簽名；agent 說出口的承諾會被當成公司的承諾。
- eval owner、domain expert、SRE、security 要在影響真實使用者之前就進場，而且每個角色都要有具名的負責人。
- 規模化是一個持續迴圈：production 失敗變成 regression 題，任何變更都要過 eval gate 與 canary。

## 延伸問答

> [!question]- Q1. 阿哲說「我們的 eval 成功率已經 88%，比真人客服的 85% 還高，為什麼不能上線？」你怎麼回答？
> 先檢查兩個數字是否可比。真人客服的 85% 通常是從線上紀錄抽查得來，涵蓋真實流量的長尾；agent 的 88% 是在 regression set 上量的，題庫的分布可能和真實流量不同，也可能因為反覆調 prompt 而對題庫過度擬合。比較之前要確認題目來源、grader 與判定標準一致，最好讓 domain expert 用同一套標準在同一批案例上評分兩者。
>
> 即使可比，88% 也只是平均值。青鳥第 12 週的數字是成功率 0.88、pass^3 0.72：失敗分散在 20 道題上，代表很多類問題都可能隨機出錯，而真人的錯誤通常集中在少數難題。加上 250 次試驗的信賴下限只有 0.834，證據還不足以支持「至少 85%」。所以答案不是「還不夠好」，而是「目前的證據還不能證明它夠好」，並指出要補的是哪些項目。

> [!question]- Q2. 估算題：有限上線時，你要證明嚴重政策違規率低於 0.1%（95% 信心）。如果一件都沒發生，至少要觀察多少件對話？以每天 900 件對話、每件都有自動規則檢查計算，要幾天？
> 用 rule of three：n 件中零事件時，95% 信心下真實發生率的上限約為 3/n。要讓 3/n ≤ 0.001，n 至少約 3,000 件。每天 900 件，大約需要 3.3 天，實務上會取整到至少一週，以涵蓋平日與週末的流量差異。
>
> 這個估算有一個重要前提：每一件對話都被檢查到。如果嚴重違規只能靠人工抽查發現，而抽查比例是 5%，每天只有 45 件被檢查，要 3,000 件就得兩個多月。這說明了兩件事：一是能用確定性規則自動偵測的違規（例如退款金額超過政策上限、回覆中含有其他顧客的資料）要盡量自動化，因為它決定了你能多快累積證據；二是閘門的樣本要求會直接決定時程，PM 排時程時要把它算進去。

> [!question]- Q3. shadow mode 和直接以 L3 copilot 模式內部試用，怎麼選？
> shadow 的優點是零副作用、零人力負擔：agent 只是旁觀，真人照常工作，可以用大量真實流量測量 agent 的決策與真人一致的比例。它的限制是看不到多輪互動的後半段（agent 的回覆沒送出，顧客不會回應它），也測不到核准 UX、客服的負擔與信任感。copilot 則相反：agent 的草稿真的會被客服看到、修改、送出，可以量測核准修改率與決定時間，但每一筆都要客服花時間，流量受限於人力，也有客服直接按核准而把錯誤送出去的風險。
>
> 實務上兩者是先後關係而不是二選一。先用 shadow 跑一到兩週，篩掉明顯的錯誤、建立一致率的基準；一致率夠高之後再進 copilot，量測人與 agent 的協作。如果一開始就上 copilot，客服會被大量低品質草稿拖累，對 agent 的信任一旦崩掉，後面很難挽回。只有在流量很小、寫入動作很少的情況下，才值得跳過 shadow。

> [!question]- Q4. 你在規模化階段看到某週升級率從 18% 掉到 4%，同時每件成本下降。產品經理想在週報上報喜，你會怎麼處理？
> 先不報喜，先排查。升級率驟降有好的原因，也有壞的原因。好的原因是新上線的 tool 或知識庫讓 agent 真的能處理以前處理不了的問題；壞的原因包括：prompt 或模型變更讓 agent 更「自信」，把該轉的對話硬接；轉真人的入口壞了（例如轉接 tool 失敗後模型改為自己回答）；或者流量組成改變（某類需要真人的問題剛好變少）。成本下降也符合壞的情境，因為不轉真人就省下了真人的分攤成本。
>
> 排查順序是：比對時間點與變更紀錄（prompt、模型、tool 版本）；按問題類型拆開升級率，看下降集中在哪幾類；抽樣那些「以前會升級、現在沒升級」的類型，由 domain expert 判斷是否正確解決；檢查轉接 tool 的錯誤率。這正是 G4 為升級率設下限的原因：低於下限本身就是一個需要調查的警報，而不是一個值得慶祝的數字。

> [!question]- Q5. 程式找錯：下面的閘門檢查有兩個會讓不合格的版本通過的錯誤，請指出來。
> ```python
> def passes(gate, metrics):
>     for metric, op, threshold in gate:
>         value = metrics.get(metric, 0)
>         if op == ">=" and value < threshold:
>             return False
>         if op == "<=" and value > threshold:
>             return False
>     return True
> ```
> 第一個錯誤是 `metrics.get(metric, 0)`：缺少的指標被當成 0。對「≥」條件這會正確失敗，但對「≤」條件（例如 P0 事故數 ≤ 0、核准修改率 ≤ 0.10、每件成本 ≤ 4）反而會通過。結果是：沒有量事故數的版本，被判定為「零事故」。正確做法是缺少就判定為未達標，並在報告中標示「未量測」。
>
> 第二個錯誤是直接比較觀察值，沒有考慮樣本數。60 件抽查得到的 0.95，和 1,500 件得到的 0.95 被當成同一件事；小樣本的好運氣會讓閘門提早打開。修法是比率型條件附帶最小樣本數，樣本不足時判定為「樣本不足」，足夠時用信賴區間的保守端比較。另外，這個函式只回傳 True／False，閘門會議需要的是「哪幾項沒過、差多少」，所以回傳值應該是未達項目的清單。

> [!question]- Q6. 面試追問：你怎麼設計 autonomy 的「降級」機制？誰可以觸發？要多快？
> 降級要比晉升快、比晉升容易觸發，因為錯誤自動化的代價不對稱。我會設計三種觸發方式。第一是自動觸發：L4 動作的事後抽查錯誤率超過降級線（例如 3%），或任何一件嚴重事故，系統直接把該動作的政策改回 L3，不等會議。第二是人工觸發：security、domain expert、on-call SRE 都可以一鍵降級，事後補寫理由。第三是變更觸發：退款政策改版、換模型或大幅改 prompt 時，相關動作自動回到 L3 或提高抽查比例，直到重新累積證據。
>
> 實作上，autonomy 等級要是 policy engine 的設定（第 21 章），而不是寫在 prompt 裡，這樣降級是改一個設定值、立刻生效，不需要部署。降級時進行中的待執行動作要轉成核准單，而不是被丟掉。最後，晉升與降級的門檻要有遲滯，避免在邊界附近來回切換；每一次晉升、降級都寫進稽核日誌，附上當時的指標快照。

> [!question]- Q7. 團隊只有三個人：一位 AI engineer、一位兼任 PM 的創辦人、一位後端工程師。38.10 節的角色要怎麼分？哪些不能合併？
> 可以合併的角色很多：後端工程師兼任 SRE 與 security 的初步工作很常見；創辦人兼任 PM 與 domain expert 也合理，前提是對方真的懂業務規則。但有兩組合併要避免。第一組是 AI engineer 兼 eval owner：自己出題自己考，會不自覺地挑自己做得好的題目、用自己理解的標準判分；至少讓後端工程師或創辦人負責題庫與判分，AI engineer 只負責讓分數變高。第二組是讓決定時程的人同時判定閘門：創辦人最想趕上市時間，如果由對方一個人說了算，門檻很容易被時程壓低。
>
> 小團隊的補償做法是把判定交給程式（38.12 節的評估器），讓會議只處理例外；security 方面，在 G3 前請外部顧問或友好團隊做一次 threat model review。人少不代表可以省略角色，而是要讓每個角色的責任落在一個明確的名字上，並避免利益衝突的合併。

> [!question]- Q8. 模型供應商推出了明顯更強的新版本，而你的 agent 已在規模化階段。換模型需要重新走一次五個階段嗎？
> 不需要從探索重新走，但要把換模型當成一次「小型上線」，重走後半段的閘門。原因是模型是 agent 行為的最大變因：新模型可能更強，也可能在你的特定政策上表現不同，例如更積極地自己解決問題（升級率下降）、對錯誤訊息的反應不同、或讓某些 harness 補丁變得多餘甚至有害。公開的工程事故也顯示，即使是看似無害的預設值調整，都可能讓使用者感受到品質下降。
>
> 具體流程是：先在完整的 regression set 上比較新舊模型（含 pass^k 與成本），檢查分歧的 trajectory；再用 shadow 在真實流量上比對一段時間；然後以 canary 從小比例推進，用 G4 的同一組條件判定。已經在 L4 的動作，要提高抽查比例或暫時回到 L3，直到新模型累積足夠證據。換模型時也是簡化 harness 的好時機：一次拿掉一個為舊模型加的補丁，用 eval 確認哪些仍然必要（第 30 章）。
