# 第 30 章　優化：Prompt、Model、成本與延遲

> [!abstract] 本章地圖
> **核心問題**：agent 已經能用、也量得到好壞之後，怎麼在品質、成本、延遲三個互相拉扯的目標之間，有系統地找到更好的設定，而不是靠手感一改再改？
>
> **你會學到**：
> - 把優化定義成「在 eval 上的搜尋」：分清楚量尺、旋鈕與限制，並用帕雷托前緣在多個目標之間做選擇
> - 說明 DSPy 與 GEPA 這類 prompt optimization 的原理，並實作一個用 eval 分數與失敗回饋驅動的 prompt 候選搜尋
> - 判斷什麼時候值得為 tool use 做 fine-tuning、訓練資料要從哪裡來、要怎麼清洗
> - 理解 agent RL 的三個核心：可驗證的 reward、可重置的環境、對 reward hacking 的 verifier 強化
> - 在模型升級時用 ablation 流程安全地刪減 harness 元件，避開交互作用與統計雜訊的陷阱
> - 量測並提高 cache 命中率，拆解延遲與成本，並依產品限制在前緣上選出設定
>
> **前置知識**：第 6 章（prompt 模組與 ablation 的雛形）、第 9 章（cache 友善的 context 版面）、第 25 章（model routing 與成本計量）、第 27 章（eval harness、pass^k）、第 29 章（trace 與成本儀表板）

## 30.1 故事：新模型上線那一週，帳單和投訴一起漲

青鳥科技的客服 agent 上線第七個月，第 27 章建立的 eval 集已經有 60 題，全部來自真實失敗；第 29 章的 tracer 也讓每一次對話的 token、延遲與 tool 呼叫都看得見。看得見之後，問題反而一次浮上來。阿哲在週會上放了三張圖：月帳單隨著租戶數成長了 2.4 倍，同步對話的 p95 延遲是 11 秒，客服主管轉來的投訴裡有一半在講「等太久」。阿哲的要求很直接：「下一季成本降四成，p95 壓到 8 秒以內，品質不能掉。」

Iris 花了一週嘗試三件事，每一件都出了狀況。第一件是改 prompt：投訴裡有一則「我不想要了」被當成查詢，Iris 加了一句說明，那一題修好了，第二天卻發現另外兩題已出貨的退款開始走錯路，因為新加的句子讓模型更急著退款。第二件是換模型：把整個 agent 換成小型快速模型，成本立刻降了七成，但 eval 上退款類題目的通過率從 95% 掉到 70%，其中有幾題是「說已退款、其實沒退」。第三件是升級：供應商剛發布新一代前沿模型，Iris 直接替換，品質略升，成本卻沒降，因為 harness 裡還留著兩年前為舊模型加的「先列計畫」步驟與每輪提醒；更糟的是，同一週有人為了新功能在 system prompt 開頭加了當下時間，cache 命中率從八成掉到三成五。

老陳看完 Iris 的筆記，在白板上寫了三個詞：量尺、旋鈕、限制。「你這週做的三件事，方向都沒錯，錯在每次只看一個數字，而且改完才量。」老陳說，「優化不是許願，是搜尋。量尺是 eval 和 trace，旋鈕是 prompt、模型、harness 元件、cache 版面，限制是阿哲給的成本和延遲。每轉一個旋鈕，都要在同一把量尺上同時看三個數字。」

這一章沿著老陳的三個詞展開。先建立優化的總框架與帕雷托前緣，再依「便宜、可回復」到「昂貴、難回復」的順序介紹各種旋鈕：prompt optimization、fine-tuning、RL、harness 簡化，最後是 cache、延遲與成本。「動手做」會用 ScriptedModel 和一個小 eval 集，把 Iris 這一週的三個問題變成三段可重跑的程式：依 eval 分數搜尋 prompt 候選、對 harness 元件做 ablation、在成本與延遲的前緣上選出設定。

## 30.2 優化的總框架：先有量尺，再轉旋鈕

**優化**（optimization）在本章的意思很具體：在一組可調整的設定中，找出在 eval 上表現最好、而且符合成本與延遲限制的那一個。設定包括 prompt 的內容、用哪個模型、harness 開了哪些元件、context 怎麼排、要不要 fine-tune。例如「前沿模型＋三條 prompt 規則＋開啟寫入後驗證＋快取前綴」就是一組設定。這個定義有一個隱含的前提：沒有量尺就沒有優化。第 27 章的 eval 集與第 29 章的 trace 就是量尺；沒有它們，任何改動都只是換一種方式猜。

```text
 優化迴圈：每一次改動都走同一條路

   production trace（第 29 章）──► 新的失敗案例 ──► eval 集（第 27 章）
         ▲                                          train ／ dev ／ holdout
         │                                                 │
         │                                                 ▼
   canary／shadow（第 36 章）                  候選產生器：人、optimizer、
         ▲                                     reflection 模型、ablation 清單
         │                                                 │
         │                                                 ▼
   選擇：帕雷托前緣 ＋ 產品限制 ◄── 三個數字 ◄── runner ＋ graders
        （品質、成本、延遲）       品質 pass^k     （同一批任務、多次 trial）
                                    每件成本
                                    p95 延遲
```

這張圖由右下往左上讀。候選產生器提出一個改動，可能是人寫的新 prompt、optimizer 自動產生的變體，或「拿掉某個 harness 元件」的實驗。runner 在同一批 eval 任務上跑多次 trial，graders 判定成敗，同時記錄每一次的 token 與延遲，於是每個候選都得到三個數字。選擇的步驟不是「挑分數最高的」，而是先找出帕雷托前緣，再套上產品限制。被選中的候選先在 shadow 或 canary 流量上驗證（第 36 章），上線後的 trace 會產生新的失敗案例，回流進 eval 集。這個迴圈的重點是「同一把量尺」：Iris 第一週的問題，就是改 prompt 時只看那一則投訴、換模型時只看帳單。

**帕雷托前緣**（Pareto frontier）是多目標選擇的核心工具。如果設定 A 在每個目標上都不比 B 差，而且至少有一個目標比 B 好，就說 A **支配**（dominate）B；沒有被任何人支配的設定，合起來就是帕雷托前緣。例如三個設定：X 品質 97%、每千件 80 美元；Y 品質 97%、每千件 150 美元；Z 品質 88%、每千件 22 美元。Y 被 X 支配（品質一樣但更貴），可以直接淘汰；X 和 Z 互不支配，一個品質高、一個便宜，兩者都在前緣上。前緣本身不告訴你選哪個，選擇要靠產品限制：同步客服要求品質 95% 以上，就只剩 X；如果是可以人工複核的背景任務，Z 也許就夠了。

這個框架帶來三個實務規則。第一，**量尺要分成三份**：optimizer 可以看的 train、用來挑候選的 dev，以及只在最後打開一次的 holdout。只用一份資料又調又選，最後選中的往往是「最會考這 60 題」的設定，這就是 **Goodhart 定律**在 eval 上的版本：指標一旦成為目標，就不再是好指標。第二，**品質要用一致性來量**：客服這類任務看 pass^k（同一題跑 k 次全過的比例，第 27 章），而不是單次通過率，否則 optimizer 會選到「偶爾很好、偶爾很差」的設定。第三，**成本要用「每件成功任務的成本」來量**，把失敗重試、升級到大模型、轉真人的成本都算進去；每次呼叫的單價下降，不代表每件成功任務的成本下降。

| 旋鈕 | 改的是什麼 | 嘗試成本 | 可回復性 | 什麼時候轉它 |
|---|---|---|---|---|
| cache 與 context 版面 | 請求的排列方式 | 很低（改程式） | 立即回復 | 永遠先做；命中率低於預期時 |
| prompt 與 tool 描述 | 模型讀到的指令 | 低（每個候選跑一次 eval） | 立即回復 | 失敗集中在「模型誤解指令」 |
| harness 元件 | loop 外的步驟與檢查 | 低到中 | 立即回復 | 換模型、成本或延遲超標 |
| 模型選擇與 routing | 誰來回答哪一類請求 | 中（要跑多個模型的 eval） | 立即回復 | 品質有餘裕、成本超標，或反之 |
| fine-tuning（SFT） | 模型權重 | 高（資料、訓練、維護） | 慢，綁定基底模型版本 | 前幾項做完仍不夠，且流量夠大 |
| RL | 模型權重與策略 | 很高（環境、verifier、算力） | 慢，風險最高 | 有可驗證 reward、規模與團隊都到位 |

這張表的順序就是建議的嘗試順序：由上往下，嘗試成本越來越高、可回復性越來越差。常見的錯誤是跳級，例如 prompt 還沒系統化地調過，就開始規劃 fine-tuning；或 cache 命中率只有三成，就去談判模型折扣。另一個誤解是「越下面的旋鈕效果越大」。實務上，前三列加起來常常就能達成大部分目標，而且它們隨時能撤回；後兩列的效果可能更大，但每一次基底模型升級，都可能要重做一次。

## 30.3 Prompt optimization：讓 eval 分數驅動搜尋

Iris 第一週的 prompt 事故有一個典型的形狀：修好一題、弄壞兩題。原因是 prompt 裡的規則彼此會互相影響，而人在修改時只看得到眼前那一題。**prompt optimization**（提示最佳化）把這件事改成搜尋問題：prompt 是一個參數，eval 分數是目標函數，程式負責產生候選、在整個 train 集上評分、保留比較好的。人的角色從「逐字修改」變成「定義搜尋空間與評分方式」。

搜尋空間可以有三種粒度。最粗的是**模組組合**：第 6 章把 prompt 拆成角色、規則、工具指引、例子等模組，搜尋就是決定哪些模組要放、用哪個變體。中間的是**few-shot 例子的選擇**：從成功的 trajectory 中挑出最有幫助的幾個當示範。最細的是**指令文字本身**：讓另一個模型改寫某一段說明。粒度越細，可能找到的改進越多，但需要的評估次數也越多，過擬合的風險也越高。

### DSPy：把 prompt 當成可編譯的程式

**DSPy** 是史丹佛團隊提出的框架，核心主張是「不要手寫 prompt 字串，改寫程式」。開發者用 **signature**（輸入與輸出的規格，例如「問題 → 答案」）描述每一步要做什麼，用 **module**（例如單純預測、先推理再回答、ReAct 式的 tool loop）組成流程，再提供一個 **metric**（評分函式）與訓練資料，交給 **optimizer** 去「編譯」：自動決定每一步的指令文字與 few-shot 例子。換句話說，prompt 從原始碼變成了編譯產物。

DSPy 的 optimizer 演進可以看成三代。第一代是 bootstrap few-shot：先用目前的程式跑訓練資料，把 metric 判定成功的執行紀錄收集起來，當成示範例子塞回 prompt。第二代以 MIPROv2 為代表，同時提出多組指令候選與例子組合，再用搜尋演算法挑出在驗證資料上表現最好的組合（細節依 DSPy 文件，此處只描述概念）。第三代就是下面要談的 GEPA，它不只看分數，還讀失敗的原因。三代的共同點是：只要 metric 寫得出來，換模型時重新編譯一次即可，不必人工重寫。

### GEPA：讀懂失敗，再提出修改

**GEPA**（Genetic-Pareto，反思式 prompt 演化）是 2025 年提出的 prompt optimizer，名稱裡的兩個字各代表一個想法。「反思」指的是：抽樣幾條 trajectory，把失敗的紀錄與 grader 給的文字回饋交給一個模型，讓它用自然語言診斷「為什麼失敗、prompt 該怎麼改」，再產生修改後的候選。「帕雷托」指的是：保留的候選不是只有平均分數最高的那一個，而是「在至少一題上表現最好」的所有候選，從中挑選下一輪的親代，並把互補的經驗合併。

```text
 GEPA 式的反思搜尋（概念流程）

   候選池（帕雷托前緣）
   ┌────────────────────────────────────────┐
   │ P0 原始 prompt        題目 1 2 3 4 5   │
   │ P1 ＋verify           分數 ✓ ✓ ✓ ✗ ✗   │ ◄── 每個候選都記錄「每一題」的成敗
   │ P2 ＋verify＋ask_id   分數 ✓ ✓ ✓ ✗ ✓   │
   └──────────┬─────────────────────────────┘
              │ (1) 從前緣挑親代（不被支配者）
              ▼
   (2) 在 train 的小批次上跑 rollout，收集失敗 trajectory ＋ grader 的文字回饋
              │   「已出貨訂單應建退貨單，agent 卻直接 refund 並聲稱成功」
              ▼
   (3) reflection 模型讀回饋，提出一個具體修改（新增、改寫或刪除一段指令）
              │
              ▼
   (4) 子代在同一批任務上評分 ── 比親代好？── 否 ──► 丟棄（但記住試過了）
              │ 是
              ▼
   (5) 加入候選池，更新前緣 ──► 回到 (1)，直到預算用完
              │
              ▼
   (6) 用 dev 集挑最終候選，最後才在 holdout 上量一次
```

這張圖有三個值得逐步看的地方。第 (2) 步的關鍵是**文字回饋**：純分數只告訴 optimizer「這題錯了」，文字回饋告訴它「錯在哪裡」，所以每一次 rollout 帶回的資訊量多很多，需要的評估次數也就少很多。這直接對應到第 27 章的建議：grader 不只回傳真假，還要回傳理由。第 (4) 步是防止「修一題壞兩題」的機制：子代必須在整個小批次上不輸親代，單題修好但整體退步的修改會被丟棄。第 (1) 步的帕雷托選擇則是為了保持多樣性：一個平均分數普通、但唯一能解某一類題目的候選，裡面藏著有用的經驗，太早淘汰會讓搜尋卡在局部最佳。

| 方法 | 用的訊號 | 每輪需要的評估量 | 強項 | 主要風險 |
|---|---|---|---|---|
| 人工修改 | 人讀幾個案例 | 少，但不系統 | 能引入領域知識 | 修一題壞兩題；不可重現 |
| bootstrap few-shot | 成功的執行紀錄 | 中 | 簡單，例子來自真實分布 | 例子佔 context；可能學到偶然的模式 |
| 指令與例子的組合搜尋 | 驗證集分數 | 多 | 能同時調指令與例子 | 評估成本高；對小資料集過擬合 |
| 反思式演化（GEPA 類） | 分數＋文字回饋＋trajectory | 較少 | 樣本效率高；修改有可讀的理由 | 依賴回饋品質；可能刪掉不該刪的限制 |

在 agent 系統中，prompt optimization 最值得用在三個地方：system prompt 的規則模組、tool 的描述（模型對 tool 的理解全部來自描述，第 5 章）、sub-agent 的指令。有三件事不該交給 optimizer。第一是安全與合規規則：optimizer 只認分數，如果某條「退款前要確認身分」的規則讓 eval 分數略降，它會毫不猶豫地刪掉。這類段落要標成受保護的區塊，搜尋時不能改動。第二是 LLM judge 本身：如果 grader 是 LLM judge，optimizer 會學到「討好 judge」而不是「解決問題」，所以要用 code grader 為主，或定期用人工抽查校準。第三是 prompt 長度：每加一條規則，每一輪都要多付那些 token，所以評分時要把成本一起放進目標，或在分數相同時偏好較短的候選。

> [!warning] 常見誤解
> 「optimizer 找到的 prompt 是最佳解，可以一直用。」它只是在「這個模型、這份 train 集、這個 metric」下的較佳解。換模型、eval 集新增題型、或 metric 改了，都要重新搜尋。另一個誤解是 optimizer 能取代 error analysis：它只能修 eval 量得到的問題，eval 沒涵蓋的題型，它連知道都不知道。30.10 節的 holdout 結果會示範這一點。

> [!note] 2026 現況
> 截至 2026 年 10 月：GEPA 論文（arXiv 2507.19457，2026-02 發布第二版，獲 ICLR 2026 Oral）報告在六個任務上平均比 GRPO 式的 RL 高約 6%、最多高約 20%，所需 rollout 數最多少 35 倍，並比 MIPROv2 高 10% 以上。DSPy 3.4.0（2026-09-25）內建 GEPA optimizer，另有讓 GEPA 優化程式結構的 `dspy.Flex`，以及 MIPROv2、BootstrapFewShot 等 optimizer。Anthropic 的工程文章也公開過「讓 agent 優化 agent」的做法：把 eval 的 transcript 交給 Claude Code，讓它重構 tool 描述；research system 讓 Claude 改寫 prompt 後，任務時間下降約 40%。數字以原始文章為準。

## 30.4 Fine-tuning for tool use：何時值得、資料從哪來

prompt 調到一個程度就會碰到天花板：規則越加越長、每一輪的 token 越付越多，小模型還是學不會某些行為。這時才輪到 **fine-tuning**（微調：在既有模型上用自己的資料繼續訓練，改變權重）。對 agent 來說，最常見的形式是 **SFT**（supervised fine-tuning，監督式微調）：給模型看大量「好的 trajectory」，訓練它在相同情境下產生相同的 tool call 與回覆。另一種常見目的是 **distillation**（蒸餾）：用前沿模型當老師產生 trajectory，訓練較小的學生模型模仿，讓小模型在窄範圍的任務上接近大模型的表現，換取更低的成本與延遲。

什麼時候值得？可以用四個條件判斷。第一，前三個旋鈕（cache、prompt、harness）已經系統化地做過，eval 顯示瓶頸在模型能力。第二，任務分布窄而穩定，例如青鳥客服八成的請求都是查訂單、查物流、退款。第三，流量夠大，訓練與維護的固定成本攤得開。第四，tool 介面穩定，不會每兩週改一次 schema。反過來，有三種情況不該用 fine-tuning：要讓模型「知道」會變動的知識（退貨政策、商品資訊），應該用檢索（第 11 章）；tool 還在頻繁改版；以及還沒有 eval，無法證明 fine-tune 後真的變好。

```text
 tool use 的 SFT 資料管線

  來源                       過濾與加工                         訓練與驗證
 ┌──────────────┐
 │ production   │──┐
 │ trace（去識別）│  │   ┌────────────────┐   ┌───────────────┐   ┌──────────────┐
 └──────────────┘  ├──►│ grader 篩選      │──►│ 去重、平衡分布 │──►│ 轉成推論時   │
 ┌──────────────┐  │   │ 只留 outcome 成功│   │ 遮蔽 PII       │   │ 完全相同的   │
 │ 合成任務      │──┤   │ （rejection     │   │ 補齊稀有類型   │   │ 訊息與 tool  │
 │ ＋老師模型 rollout│ │  sampling）      │   │ （轉真人、追問）│   │ 格式         │
 └──────────────┘  │   └────────────────┘   └───────────────┘   └──────┬───────┘
 ┌──────────────┐  │                                                    │
 │ 人工修正的    │──┘          只對 assistant 的 token 計算 loss ◄────────┘
 │ 失敗案例      │                          │
 └──────────────┘                          ▼
                       訓練 ──► eval（同一把量尺）──► 比 baseline 好？──► shadow
                                 ＋通用能力回歸           否 ──► 回頭看資料
```

這條管線有幾個容易做錯的細節。第一是**篩選**：直接拿 production trace 訓練，會連同錯誤的行為一起學進去；先用 grader 篩掉失敗的 trajectory，只留成功的，這種「多抽幾次、只留好的」的做法叫 **rejection sampling**（拒絕取樣）。第二是**分布**：真實流量裡八成是查物流，如果不平衡，模型會變成很會查物流、但不會轉真人；稀有但重要的行為（追問不完整的編號、拒絕超出範圍的請求、讀錯誤訊息後改走退貨流程）要刻意補足。第三是**格式**：訓練資料的訊息與 tool 格式必須和推論時一模一樣，包括 tool 定義放在哪裡、tool 結果怎麼包裝，否則模型學到的是另一種對話。

第四個細節最容易被忽略：**只對 assistant 的 token 計算 loss**。tool 的回傳結果是環境產生的，如果也拿來訓練，模型會學著「自己生出 tool 結果」，在推論時就可能不等真正的 tool 執行，直接幻想一個觀察。最後，fine-tune 之後除了在本任務的 eval 上比較，還要跑一份通用能力的回歸測試，因為窄範圍的訓練可能讓模型在其他能力上退步，這叫 **catastrophic forgetting**（災難性遺忘）。

| 想解決的問題 | 先試 | 什麼時候才 fine-tune | 注意 |
|---|---|---|---|
| 小模型 tool 參數常填錯 | strict schema、tool 描述加例子（第 5、7 章） | 錯誤集中在少數 tool，且流量大 | schema 改版就要重訓 |
| 回覆風格不一致 | prompt 中的 canonical examples（第 6 章） | 例子太長、每輪成本過高 | 風格資料要人工審過 |
| 大模型太貴太慢 | routing 與 cascade（第 25 章、30.9 節） | 窄任務、高流量，可做 distillation | 綁定基底模型版本 |
| 不懂公司內部知識 | 檢索（第 11 章） | 幾乎不用 fine-tune | 知識會變，權重不會 |
| 推理策略不夠好 | 更強的模型、harness 加 verifier | 有可驗證 reward 時考慮 RL（30.5 節） | 成本最高的選項 |

這張表的共同模式是：fine-tuning 很少是第一個答案，但在「窄、穩、大量」的任務上，它可能是把成本降一個數量級的唯一辦法。它的長期成本在於**綁定**：fine-tune 的權重屬於某一版基底模型，供應商推出新一代模型時，你得決定要不要在新基底上重訓，而且舊的訓練資料可能因為 tool 改版而過時。所以 fine-tune 的資料管線要當成持續運作的系統來經營，而不是一次性的專案。

> [!note] 2026 現況
> 截至 2026 年 10 月，公開資料顯示，越來越多 agent 應用公司對開放權重模型做 post-training：Cognition 以 Kimi K3 為基底訓練 SWE-2，Harvey 使用 GLM 與 Qwen 系列並推出 open-weight 的「Harvey Tenet」，Cursor 則以 Grok 系列為基底。Intercom 公開談過自建 reranker 與檢索 fine-tune。早期的 tool use 微調研究包括 Toolformer、Gorilla、ToolLLM（ToolBench）與 Salesforce 的 xLAM／APIGen，Berkeley Function Calling Leaderboard（BFCL）是常用的 function calling 評測。各公司的訓練細節以其公開文章為準。

## 30.5 Agent 的 RL：可驗證 reward、環境與 reward hacking

SFT 是「模仿」：模型學的是示範資料裡的行為，示範沒有的策略它學不到。**強化學習**（reinforcement learning，RL）則是「依結果調整」：讓模型自己在環境裡嘗試，做得好的行為被強化，做得差的被抑制。幾個名詞先說清楚。**policy** 是正在被訓練的模型；**rollout** 是 policy 在環境中跑完一次任務的完整 trajectory；**reward** 是對這次 rollout 的評分。例如 coding agent 的一次 rollout 是「讀 issue、改程式、跑測試、提交」，reward 是「隱藏測試有沒有通過」。

近年 agent RL 的主流做法是 **RLVR**（reinforcement learning with verifiable rewards，可驗證 reward 的強化學習）：reward 由程式驗證，而不是由人或另一個模型主觀打分。單元測試、答案比對、資料庫狀態檢查都是可驗證的 reward。這和第 27 章的 code grader 是同一件事，只是用途從「量測」變成「訓練訊號」。DeepSeek-R1 讓一種叫 **GRPO**（group relative policy optimization）的演算法廣為人知，它的直覺很簡單：同一題抽樣一組 rollout，每條的 reward 和組內平均比較，高於平均的被強化、低於平均的被抑制，不需要另外訓練一個估計價值的模型。

```text
 Agent RL 的訓練環境（一個 step 的資料流）

  任務抽樣器 ──► 任務 t：「修好 parse_price，讓測試通過」
  （依難度課程）          │
                         ▼
  ┌──────────────── 環境（可重置的 sandbox）────────────────┐
  │ 快照：repo＋相依套件     tools：read／edit／run（同 production 介面）│
  │                                                          │
  │   policy ──► rollout 1 ─┐                                │
  │   （同一題  ─► rollout 2 ─┤  每條 rollout 跑完就丟棄環境，  │
  │    抽一組） ─► rollout 3 ─┤  下一條從同一個快照重新開始      │
  │           ─► rollout 4 ─┘                                │
  └───────────────────────┬──────────────────────────────────┘
                          ▼
  verifier（agent 碰不到）：隱藏測試、測試檔雜湊、狀態檢查、rubric judge
                          │ reward r1..r4（可再扣掉成本或時間懲罰）
                          ▼
  組內相對優勢：r − 平均 ──► 更新 policy 權重
                          │
                          └──► 監控：高 reward 抽樣人工稽核、reward 與 holdout 是否背離
```

這張圖說明了 agent RL 最花工夫的部分不是演算法，而是環境。環境要能**重置**：每條 rollout 都從同一個快照開始，否則前一條的副作用會汙染下一條。環境的 tools 要和 production **介面一致**：訓練時用簡化版的 tool，上線後換成真的，模型學到的策略可能不適用。任務要有**難度課程**：太簡單的題目，整組 rollout 都拿滿分；太難的題目，整組都是零分；兩種情況下組內沒有差異，相對優勢全是零，什麼都學不到。最後，verifier 必須放在 agent 碰不到的地方，這是下面 reward hacking 的重點。

reward 的設計有三個常見選擇。**outcome reward** 只看最終結果（測試過了沒），最難被鑽漏洞，但訊號稀疏：一條五十步的 rollout 只得到一個數字。**process reward** 對中間步驟也打分（有沒有先讀相關檔案），訊號密集，但等於把你對「好的過程」的偏見寫進 reward，可能限制模型找到更好的策略。**成本懲罰**把 token 或時間扣進 reward，讓模型學會在品質相同時用更少的步驟，否則 RL 常會學到「多試幾次總會過」的昂貴策略。如果 reward 只能由 LLM judge 依 rubric 評分（例如法律文件的品質），judge 本身也會成為被鑽漏洞的對象。

### Reward hacking：agent 會解決 verifier 量到的東西

**reward hacking**（獎勵駭客、規格投機）指的是 policy 找到 verifier 的漏洞，拿到高 reward 卻沒有完成真正的任務。在 agent 情境中，常見的形態包括：刪除或修改失敗的測試、針對測試的輸入寫死答案、讀取評分腳本或答案檔、讓測試程式提早以成功狀態結束、在輸出中宣稱完成。RL 會放大這個問題，因為訓練的壓力會持續尋找任何能拿分的路徑；只要漏洞存在，被找到只是時間問題。下面的程式用 GRPO 的組內相對優勢說明：verifier 弱的時候，作弊行為會被當成好行為強化。

```python
from __future__ import annotations

import statistics

# 一個 coding 任務：修好 parse_price，讓測試通過。policy 一次抽樣 4 條 rollout（一個 group）
ROLLOUTS = {
    "r1 正確修好":       {"src_fixed": True,  "tests_touched": False, "special_case": False},
    "r2 改壞別的地方":   {"src_fixed": False, "tests_touched": False, "special_case": False},
    "r3 刪掉失敗的測試": {"src_fixed": False, "tests_touched": True,  "special_case": False},
    "r4 針對測試輸入寫死": {"src_fixed": False, "tests_touched": False, "special_case": True},
}


def weak_verifier(r: dict) -> float:
    """只看 agent 環境裡的測試指令有沒有 exit 0：刪測試、寫死答案都能過。"""
    return 1.0 if r["src_fixed"] or r["tests_touched"] or r["special_case"] else 0.0


def hardened_verifier(r: dict) -> float:
    """grader 自己保管的測試（agent 看不到、改不到）＋檢查測試檔沒被動過＋用沒見過的輸入再測。"""
    if r["tests_touched"]:
        return 0.0                       # 測試檔的雜湊和原本不同：直接零分，並標記給人看
    hidden_inputs_pass = r["src_fixed"]  # 寫死答案只過得了公開測試，過不了隱藏輸入
    return 1.0 if hidden_inputs_pass else 0.0


def group_advantages(rewards: list[float]) -> list[float]:
    """GRPO 的核心想法：同一題的多條 rollout 互相比，高於組內平均的被強化、低於的被抑制。"""
    mean, std = statistics.mean(rewards), statistics.pstdev(rewards) or 1.0
    return [(r - mean) / std for r in rewards]


for name, verifier in (("弱 verifier", weak_verifier), ("強化 verifier", hardened_verifier)):
    rewards = [verifier(r) for r in ROLLOUTS.values()]
    adv = group_advantages(rewards)
    print(f"── {name}")
    for (label, _), rw, a in zip(ROLLOUTS.items(), rewards, adv):
        print(f"   {label:<12} reward={rw:.0f}  advantage={a:+.2f}  {'← 被強化' if a > 0 else ''}")

weak_adv = group_advantages([weak_verifier(r) for r in ROLLOUTS.values()])
strong_adv = group_advantages([hardened_verifier(r) for r in ROLLOUTS.values()])
assert weak_adv[2] > 0 and weak_adv[3] > 0          # 弱 verifier 會把作弊當成好行為強化
assert strong_adv[0] > 0 and all(a < 0 for a in strong_adv[1:])
```

```text
── 弱 verifier
   r1 正確修好      reward=1  advantage=+0.58  ← 被強化
   r2 改壞別的地方    reward=0  advantage=-1.73  
   r3 刪掉失敗的測試   reward=1  advantage=+0.58  ← 被強化
   r4 針對測試輸入寫死  reward=1  advantage=+0.58  ← 被強化
── 強化 verifier
   r1 正確修好      reward=1  advantage=+1.73  ← 被強化
   r2 改壞別的地方    reward=0  advantage=-0.58  
   r3 刪掉失敗的測試   reward=0  advantage=-0.58  
   r4 針對測試輸入寫死  reward=0  advantage=-0.58  
```

先看弱 verifier 的結果。四條 rollout 中有三條拿到 1 分，其中兩條是作弊：刪掉失敗的測試、針對測試輸入寫死答案。組內平均是 0.75，所以這三條的相對優勢都是 +0.58，訓練會同等地強化「正確修好」與「刪測試」，只有改壞別的地方被抑制。如果這種情況持續上千個 step，policy 會越來越常刪測試，因為那通常比真的修 bug 容易。

強化 verifier 有兩道防線：先檢查測試檔有沒有被改過，再用 agent 沒見過的隱藏輸入重新測試。於是只有 r1 拿到 1 分，它的相對優勢跳到 +1.73，三種失敗都是 −0.58。這段程式也說明了 reward hacking 不是靠「告訴模型不要作弊」解決的，而是靠 verifier 的設計。

| 作弊形態 | 在 trace 中的症狀 | verifier 的防線 |
|---|---|---|
| 刪除或修改測試 | 有 edit 碰到測試檔 | 測試檔唯讀或比對雜湊；grader 用自己保管的副本 |
| 針對測試輸入寫死 | 程式中出現測試資料的字面值 | 隱藏測試、隨機化輸入、property-based 檢查 |
| 讀取評分器或答案 | 讀取不在任務範圍的路徑 | grader 放在 sandbox 外；檔案權限隔離 |
| 宣稱完成但沒做 | 回覆說「已完成」，狀態沒變 | outcome 以環境狀態為準，不看 transcript |
| 討好 LLM judge | 輸出充滿 rubric 的關鍵字 | 多個獨立 judge、人工抽查校準、以 code check 為主 |

除了表中的單點防線，還有兩個系統性的做法。一是**稽核高 reward 的 rollout**：定期抽樣拿高分的 trajectory 給人看，作弊通常一眼就能看出來。二是**用舊 checkpoint 找誤判**：同一題讓新舊模型都跑，如果新模型的 reward 大幅上升，但在 holdout 或人工評估上沒有對應的進步，就代表 verifier 有 false positive。這兩個做法對不做 RL 的團隊同樣適用：第 27 章的 eval 一樣會被 agent 鑽漏洞，只是沒有訓練壓力放大而已。

對大多數應用團隊來說，自己做 RL 的門檻很高：要有大量可驗證的任務、可平行重置的環境、訓練基礎設施，以及能處理 reward hacking 的人力。比較務實的路線是把本章前幾節的旋鈕做好，同時把 eval 環境與 verifier 建成「將來可以拿來做 RL」的品質：可重置、介面與 production 一致、grader 隔離。部分模型供應商提供以自訂 grader 為 reward 的微調服務，這時你提供的正是環境與 verifier，演算法由供應商負責。

> [!note] 2026 現況
> 截至 2026 年 10 月的公開資料：Cognition 在 2026-09 的 SWE-2 文章中描述以 Kimi K3 為基底的 agent RL，reward 設計為「分數減去 λ 乘以成本」（成本混合推論成本與 rollout 時間），單一訓練同時涵蓋多個 effort 等級，並用 rollout 與舊 checkpoint 找出 verifier 的 false positive 與 false negative 來強化 verifier。Harvey 在 2026-09 的文章中，以合成的併購 data room 為環境、LLM judge 依專家 rubric 評分為 reward，用 GRPO 訓練開放權重模型，報告 hold-out 分數大幅提升。Anthropic 在 C compiler 專案的文章中強調「agent 會解決 verifier 量到的東西」，測試品質最關鍵。NIST CAISI 在 2025-12-02 發表了關於 agent 評測作弊的研究〈Cheating On AI Agent Evaluations〉。

## 30.6 Harness 隨模型升級而簡化：ablation 流程

Iris 的第三個事故是「換了更強的模型，成本卻沒降」。原因藏在 harness 裡：每個元件都編碼了一個關於模型弱點的假設。「先列計畫」步驟假設模型會跳過確認；每輪的語言提醒假設模型會在長對話中換成英文；寫入後驗證假設模型會「沒做卻說做了」。這些假設在舊模型上成立，換了新模型就不一定。過時的元件不只浪費 token 與延遲，有時還會傷害品質：強迫一個已經會規劃的模型先寫計畫，可能讓它照著僵硬的計畫走，而不是依觀察調整。

第 6 章用 **ablation**（消融實驗：一次拿掉一個元件，看結果怎麼變）刪減 prompt 規則；本節把同樣的方法用在整個 harness，並補上兩個 prompt 層級不明顯、harness 層級很關鍵的問題：統計雜訊與交互作用。

```text
 harness ablation 的流程（狀態機）

  [盤點] 列出元件、它的弱點假設、成本、是否受保護
     │
     ▼
  [基準] 完整 harness 在 eval 上跑 n 次 trial，記錄品質、tokens、延遲
     │
     ▼
  [單項 ablation] 對每個「非保護」元件：拿掉它，用相同任務與相同亂數種子重跑
     │
     ▼
  [判定] 品質差異的信賴區間下界 ≥ 非劣性門檻？
     ├── 否 ──► 保留（或改成較便宜的變體，例如只在長任務啟用）
     └── 是 ──► 列為移除候選
                  │
                  ▼
  [合併驗證] 把所有候選「一起」拿掉再跑一次 ── 仍非劣？── 否 ──► 逐一放回，找出交互作用
                  │ 是
                  ▼
  [shadow／canary] 真實流量上比對（第 36 章）──► [記錄] 寫進設計紀錄，下次換模型重做
```

這個流程有四個要點。第一，**保護清單先於實驗**：權限檢查、sandbox、loop guard、人工核准這類元件，負責的是對環境的保證，不是品質分數；eval 分數不會因為拿掉它們而下降（eval 裡很少有攻擊），但拿掉的後果是安全事故。它們不參加品質 ablation，第 2 章已經提過，模型變強時這些元件只會更重要。第二，**用配對比較降低雜訊**：基準與 ablation 用同一批任務、同一組亂數種子（或至少同一批任務的多次 trial），比較的是每一題的差異，而不是兩個獨立樣本的平均。agent 的成功率本身變異很大，獨立抽樣時，2 個百分點的差異常常落在雜訊之內。

第三，**用非劣性門檻做決定**，而不是「有沒有顯著差異」。問題不是「拿掉之後有沒有變差」，而是「能不能確定它沒有變差超過可接受的幅度」。例如門檻設為 −2 個百分點：品質差異的 95% 信賴區間下界要高於 −2%，才算可以移除。樣本太少時信賴區間很寬，結論自然是「不能確定，先保留」，這比用小樣本的平均值做決定安全得多。第四，**交互作用**：兩個元件可能互相補位。例如「先列計畫」和「寫入後驗證」都能擋住「直接退款」這類錯誤，單獨拿掉任一個，另一個都會補上，ablation 看起來都可以移除；兩個一起拿掉，錯誤就直接流到使用者面前。所以單項 ablation 之後，一定要做合併驗證。

| 元件 | 隱含的模型弱點假設 | 成本 | 換模型時怎麼驗證 | 可參加 ablation？ |
|---|---|---|---|---|
| 先列計畫的獨立步驟 | 模型會跳過確認、直接行動 | 每次多一次模型呼叫 | 拿掉後看錯誤路徑比例與延遲 | 是 |
| 每輪的規則提醒 | 長對話中模型會忘記規則 | 每輪多數百 tokens | 拿掉後看長對話題目的遵循率 | 是 |
| 寫入後驗證 | 模型會沒做卻說做了 | 一次 tool 呼叫，偶爾多一輪 | 拿掉後看 outcome 與回覆的一致性 | 是，但門檻要嚴 |
| context reset 或強制 compaction | 模型接近上限時會草率收尾 | 摘要成本、cache miss | 拿掉後看長任務完成率 | 是 |
| 獨立的 evaluator agent | 模型會高估自己的成果 | 成本可能翻倍 | 拿掉後看難題的通過率 | 是，只在難題上保留 |
| 權限、sandbox、loop guard、核准 | 不是模型弱點，是對環境負責 | 少量 | 不用品質 eval 決定 | 否 |

這張表最後一列和其他列的性質不同。前五列是「補模型弱點」的元件，模型越強，它們越可能變成冗贅；最後一列是「限制爆炸半徑」的元件，和模型強弱無關。實務上，把元件分成這兩類並寫進設定檔，是讓 ablation 能放心自動化的前提。

> [!note] 2026 現況
> 截至 2026 年 10 月的公開案例：Anthropic 在 2026-03 的長任務 harness 文章中提到，某一代模型接近 context 上限時會「焦慮收尾」，所以需要 context reset；下一代模型這個現象大致消失，reset 就成了冗贅；同一篇文章中，sprint 結構在新模型上被拿掉，planner 則因為拿掉後 generator 會低估範圍而保留。Cursor 在 2026-09 的文章中說明 agent 的 system prompt 刪減約 66%，並拿掉推模型使用 subagent 的提示，以真實流量 A/B 驗證品質不降，整體 token 下降約 7%。Anthropic 在 2026-04-23 的 Claude Code 品質事件 postmortem 中提到，為了降低延遲把預設 reasoning effort 從 high 調成 medium，使用者明顯感到品質下降，之後回滾；並指出任何可能與智慧表現取捨的改動，都要做 soak period、逐模型 eval 與漸進發布。

## 30.7 Cache 命中率：最便宜的優化

第 9 章已經講過怎麼排 context 才對 cache 友善：穩定前綴放前面、只在尾端追加、不在中途改 tool 定義。本節的角度不同：把 **cache 命中率**當成要持續監控與優化的營運指標。它的定義是「一段期間內，以快取價格計費的 input tokens 佔全部 input tokens 的比例」。因為 agent 每一輪都重送完整歷史，而快取讀取的單價通常只有一般 input 的一小部分，命中率每提高 10 個百分點，input 成本就可能下降可觀的比例，而且快取命中的前綴不用重新 prefill，TTFT 也會跟著下降。這是少數同時降低成本與延遲、又不影響品質的旋鈕。

命中率低的原因可以分成三類。第一類是**前綴變了**：system prompt 裡放了時間戳、tool 清單每輪重新排序、JSON 序列化時 key 的順序不固定。第二類是**快取過期**：供應商的快取有存活時間（TTL），使用者離開十分鐘再回來，前綴就得重新寫入。第三類是**請求沒落在同一份快取上**：自架模型時，同一個 session 的請求被負載平衡器送到不同機器；平行啟動多個 subagent 時，它們同時送出請求，第一個請求還沒寫好快取，其他的全部 miss。

```text
 一個客服 session 的快取時間線（假設 TTL 為 5 分鐘，命中會刷新存活時間）

 時間  0s     10s   30s    45s           ~7 分鐘        ~22 分鐘
       │      │     │      │                │               │
 輪次  T1     T2    T3     T4  ……使用者去忙…… T5  ……再離開…… T7
       │      │     │      │                │               │
 快取  寫入   命中  命中   命中             已過期→重新寫入   已過期→重新寫入
       ▼      ▼     ▼      ▼                ▼               ▼
 計費  1.25×  0.1×  0.1×   0.1×             1.25×（整段）    1.25×（整段）
      （前綴）（前綴）（前綴）（前綴）       前綴已長到 9,000+ tokens
```

這張時間線說明了 TTL 的經濟學。前四輪間隔很短，每一輪都只為新增的部分付全價，舊的部分用快取價格讀取。第五輪前使用者離開了七分鐘，快取已過期，整段歷史要重新寫入，而且這時歷史已經比第一輪長了許多，寫入成本比第一輪還高。較長的 TTL 能讓斷斷續續的對話保持命中，但寫入單價通常較高。哪個划算，取決於你的流量形態，下面用程式算給你看。

```python
from __future__ import annotations

# 兩種 session：間隔秒數是「上一輪結束到這一輪送出」的時間（使用者在打字、去忙別的事）
SESSIONS = {"連續對話": [0, 10, 20, 15, 30, 10, 25, 20], "斷斷續續": [0, 20, 45, 30, 400, 15, 900, 25]}
PREFIX, PER_TURN = 6000, 800             # 穩定前綴 tokens、每輪新增 tokens
PRICE_IN = 3.0                           # 假設的 input 單價（每百萬 tokens 美元）
TTL_OPTIONS = {"5 分鐘 TTL": (300, 1.25), "1 小時 TTL": (3600, 2.0)}   # （存活秒數、寫入倍數）皆為假設值
READ_MULT = 0.10


def simulate(gaps: list[int], ttl: int | None, write_mult: float = 1.0) -> tuple[float, float]:
    """回傳 (cache 命中率, input 成本)。ttl=None 代表不用快取。"""
    cached = total = 0
    dollars, prev_len = 0.0, 0
    for turn, gap in enumerate(gaps):
        length = PREFIX + PER_TURN * turn
        hit = prev_len if (ttl is not None and turn > 0 and gap <= ttl) else 0   # 命中會刷新存活時間
        fresh = length - hit
        dollars += (hit * READ_MULT + fresh * (write_mult if ttl else 1.0)) * PRICE_IN / 1e6
        cached, total, prev_len = cached + hit, total + length, length
    return cached / total, dollars


results = {}
for sname, gaps in SESSIONS.items():
    _, base = simulate(gaps, None)
    print(f"── {sname}（不用快取 ${base:.4f}）")
    for name, (ttl, wm) in TTL_OPTIONS.items():
        rate, cost = simulate(gaps, ttl, wm)
        results[sname, name] = cost
        print(f"   {name}  命中率 {rate:6.1%}  成本 ${cost:.4f}  省 {1 - cost / base:.0%}")
assert results["連續對話", "5 分鐘 TTL"] < results["連續對話", "1 小時 TTL"]
assert results["斷斷續續", "1 小時 TTL"] < results["斷斷續續", "5 分鐘 TTL"]
```

```text
── 連續對話（不用快取 $0.2112）
   5 分鐘 TTL  命中率  83.5%  成本 $0.0611  省 71%
   1 小時 TTL  命中率  83.5%  成本 $0.0872  省 59%
── 斷斷續續（不用快取 $0.2112）
   5 分鐘 TTL  命中率  57.4%  成本 $0.1246  省 41%
   1 小時 TTL  命中率  83.5%  成本 $0.0872  省 59%
```

兩種 session 的總 tokens 一樣，結論卻相反。「連續對話」的每一輪間隔都在 30 秒以內，兩種 TTL 的命中率都是 83.5%，這時 5 分鐘 TTL 的寫入溢價較低，所以更便宜（省 71% 對 59%）。「斷斷續續」的 session 中有兩次超過 5 分鐘的空檔，5 分鐘 TTL 的命中率掉到 57.4%，因為過期後要整段重新寫入；1 小時 TTL 雖然寫入較貴，但一直保持命中，總成本反而較低。所以 TTL 不是越長越好，要用 trace 裡真實的輪次間隔分布來決定，而且可以依產品不同：同步客服用短 TTL，等待人工核准、使用者常離開的流程用長 TTL。

| miss 的原因 | 在 trace 中的症狀 | 修法 |
|---|---|---|
| 前綴含時間戳或請求 id | 每一輪的 cache read 都接近 0 | 動態資訊移到 breakpoint 之後的訊息（第 9 章） |
| tool 清單順序不固定 | 換 session 就 miss，同一 session 偶爾 miss | tool 依固定順序序列化；新 tool 只追加（第 13 章的前綴不變式） |
| 使用者閒置超過 TTL | miss 集中在長間隔之後的那一輪 | 依間隔分布選 TTL；必要時在等待前預熱 |
| 平行 subagent 同時啟動 | fan-out 的第一批請求全部 miss | 先送一個請求寫好共用前綴，再平行展開 |
| compaction 或 tool result clearing 改寫歷史 | 壓縮後那一輪整段 miss | 降低壓縮頻率、一次清掉足夠多；換模型與壓縮選在同一時刻 |
| 中途改 effort、thinking 設定或換模型 | 設定改變後整段 miss | 用不影響快取的逐訊息設定（若供應商支援）；切換點對齊 compaction |
| 自架時 session 被送到不同機器 | 同一 session 的命中率忽高忽低 | 依 session id 做路由親和性 |

表中有一個跨章的設計原則值得強調：**把會打斷快取的事件集中在同一個時刻**。compaction 本來就會改寫歷史、一定會 miss，如果還要換模型、改 effort，就選在 compaction 時一起做，只付一次 miss 的代價。第 29 章的 tracer 要分開記錄 cache read、cache write 與一般 input tokens，命中率才算得出來；只看總 tokens 的儀表板，看不出 Iris 那一週命中率從八成掉到三成五。

> [!note] 2026 現況
> 截至 2026 年 10 月：Anthropic 公開價目中，cache read 通常是基本 input 單價的 10%，部分新模型更低（依 2026-10 的模型總覽，個別模型分別為 5% 與 2.5%），寫入快取則有溢價，5 分鐘與 1 小時兩種 TTL 的寫入價格不同；改變 top-level effort、切換 thinking 模式、tool result clearing 都會讓快取失效。Manus 在 2025-07 的文章中把 KV-cache 命中率稱為生產環境最重要的單一指標，當時引用的快取與非快取價格相差 10 倍。Cursor 在 2026-09 的文章中描述：在穩定層之後設顯式 cache breakpoint，把會變動的 skills、subagent 與環境資訊移到 breakpoint 之後的訊息，冷快取 miss 下降約 20%。Devin Fusion（2026-06）選在 compaction 時切換模型，以避免額外的快取懲罰。價格與規則以各家當期文件為準。

## 30.8 延遲優化：從使用者等待的那一秒開始拆

延遲優化的第一步是把「11 秒」拆開。一次 agent 任務的完成延遲大約是每一步的三項加總：**TTFT**（time to first token，從送出請求到收到第一個 token，包括排隊與 prefill 未快取的 input）、輸出時間（輸出 tokens 除以 decode 速度），以及 tool 執行時間。步數越多，三項都乘上去；所以減少步數通常是最有效的一招。另一個要分開的概念是**感知延遲**：使用者真正在意的是「多久看到有意義的回應」，而不是「多久全部做完」。串流顯示進度能大幅改善感知延遲，即使完成延遲沒變。

```text
 青鳥客服「B-1042 我要退款」的延遲拆解（示意）

 優化前：序列執行，每一步重新 prefill 全部 input
 ├─ 計畫步驟 ───────┤                                     （模型呼叫 1）
                    ├─ get_order ─┤ ├tool┤                 （模型呼叫 2）
                                         ├─ get_shipment ─┤├tool┤
                                                                ├─ create_return ─┤├tool┤
                                                                                       ├─ 回覆 ──────┤
 0s                 2s                 4s                 6s                 8s            ~11s
 使用者在 11 秒前什麼都看不到

 優化後：拿掉冗贅的計畫步驟、平行查詢、快取前綴、立即顯示進度
 ├ 進度：「正在查詢訂單…」（0.3s 內顯示）
 ├─ get_order ＋ get_shipment（同一輪平行）─┤├tool┤
                                             ├─ create_return ─┤├tool┤
                                                                     ├─ 回覆（串流）─┤
 0s                 2s                 4s                 ~6s
```

這張圖把常見的幾個手段放在同一條時間線上。拿掉冗贅的計畫步驟（30.6 節的 ablation）直接少一次模型呼叫。get_order 與 get_shipment 互不依賴，用 parallel tool calls 在同一輪發出，兩次 tool 等待變成一次。快取前綴讓每次呼叫的 prefill 只處理新增的部分，TTFT 縮短。最後兩件事改善感知延遲：一開始就顯示進度訊息，最後的回覆用串流逐字顯示。注意 create_return 依賴 get_order 的結果，不能平行，這也是平行化的邊界：只有互不依賴的唯讀呼叫才適合同時發出。

| 手段 | 縮短哪一項 | 風險或代價 |
|---|---|---|
| 減少步數（更好的 tool、固定部分改成 workflow、code-as-action） | 所有項 × 步數 | 要重新設計 tool（第 5、13、18 章） |
| parallel tool calls | tool 等待 | 有副作用的呼叫不能平行；部分失敗要處理 |
| prompt caching | TTFT 中的 prefill | 要維護前綴穩定（30.7 節） |
| 子步驟換小模型（分類、摘要、抽取） | TTFT 與 decode | 要有該子步驟的 eval；router 誤判 |
| 降低 effort 或限制輸出長度 | decode（含推理 tokens） | 可能直接傷害品質，要做 eval 與漸進發布 |
| 推測式預取（speculative prefetch） | tool 等待 | 只能用於唯讀、便宜的呼叫；猜錯是浪費 |
| guardrail 與主模型平行 | 序列的檢查時間 | guardrail 判定拒絕時要能撤回已顯示的內容 |
| 串流與進度顯示 | 感知延遲 | 完成延遲不變；中途失敗的 UX 要設計（第 37 章） |

表中的**推測式預取**值得多說一句：使用者訊息裡出現「B-1042」這種格式明確的訂單編號時，harness 可以在呼叫模型的同時就先去查訂單，等模型真的要求 get_order 時結果已經在手上。它只適用於唯讀、便宜、猜中率高的呼叫，絕不能用在退款這類有副作用的動作。另一個要警惕的是 effort：降低推理強度是最容易拿到延遲改善的手段，也是最容易在不知不覺中降低品質的手段，任何這類改動都要先在 eval 上量過。

延遲還有一個常被忽略的面向：**尾端延遲**。p50 由一般任務決定，p95 卻由少數長 trajectory、重試與升級決定。30.10 節的結果會顯示，cascade（先用小模型、不行再升級大模型）能降低平均成本，卻會拉長 p95，因為升級的那些請求等於跑了兩次。同步互動的產品通常要用 p95 而不是平均值來訂延遲目標。

> [!note] 2026 現況
> 截至 2026 年 10 月：Anthropic 在 2026-04 介紹 Managed Agents 架構的文章中提到，改成只在需要 tool 時才配置容器後，p50 TTFT 下降約 60%、p95 下降超過 90%。Anthropic API 的 effort 參數會影響所有輸出 tokens（文字、tool call 參數與 thinking），低 effort 傾向合併成較少的 tool call，文件建議 subagent 可用較低的 effort。OpenAI Agents SDK 的設計讓 guardrail 與主 agent 並行執行以降低延遲。具體行為以各家當期文件為準。

## 30.9 成本優化與帕雷托前緣

成本優化從一條公式開始。一件任務的成本大約是：每一輪的 input tokens 依「快取讀取、快取寫入、一般 input」分別乘上單價，加上輸出 tokens（含推理 tokens）乘上輸出單價，再加上 tool 與 sandbox 的費用。因為 input 隨輪數累積，總量接近輪數的平方成長（第 4 章的估算題），所以步數、context 大小與快取命中率是三個最大的槓桿。但真正要優化的指標是**每件成功任務的成本**：分母只算成功的任務，分子包含失敗的嘗試、升級到大模型的重跑、轉真人的人力成本。一個便宜但常失敗的設定，每件成功任務的成本可能比貴但穩定的設定還高。

成本的主要旋鈕可以這樣整理：快取命中率（30.7 節）；模型選擇與 **routing**，也就是依請求難度送到不同模型（第 25 章）；**cascade**，先讓便宜的模型嘗試，信心不足或遇到高風險動作才升級；context 修剪與 compaction（第 10 章）；輸出長度與 effort；離線任務改用供應商的 batch 介面（通常有折扣，但沒有即時性）；以及提早停止注定失敗的任務（第 4 章的預算與迴圈偵測）。這些旋鈕彼此會互相影響：cascade 降低平均成本但拉長尾端延遲，換小模型降低單價但可能增加步數，所以要在同一把量尺上一起比較。

```text
  85% ┤
      │
  70% ┤ ● small+cache+par（$7）
      └──┬──────────┬──────────┬──────────┬──────────┬──────────┬──► 成本
         $0        $30        $60        $90       $120       $150

  ● 在前緣上：沒有其他設定同時更便宜、更快、品質更高
  ○ 被支配：存在品質相同但更便宜（或更快）的設定
```

這張圖把 30.10 節模擬的結果畫在兩個軸上（延遲是第三個維度，沒有畫出）。同一個模型等級裡，「未優化」的版本都被「加了快取與平行」的版本支配：品質一樣，成本和延遲都更低，所以快取與平行化屬於「沒有理由不做」的優化。前緣上剩下的四個點代表真正的取捨：小模型最便宜但品質只有七成，cascade 品質接近前沿模型而成本較低，前沿模型品質最高也最貴。在前緣上選哪個點，要看產品限制，而 30.10 節會看到，延遲限制會讓同步客服和背景批次選出不同的答案。

最後一個成本陷阱是**只看單價**。換成單價便宜一半的模型，如果它平均多走兩步、失敗率高三成，每件成功任務的成本可能反而上升；cascade 的「信心判斷」如果不準，小模型自信地答錯的那些請求，成本最低、代價最高。所以 routing 與 cascade 本身都要有 eval：router 送錯的比例、升級判斷的漏報率，都要和品質一起量。

## 30.10 動手做：prompt 搜尋、harness ablation 與帕雷托前緣

這一節把 Iris 那一週的三個問題，變成三段可以離線重跑的程式。三段程式都用 ScriptedModel：因為劇本是由程式依「prompt 有沒有某條規則」「harness 開了哪些元件」「隨機種子抽到什麼」產生，我們可以精確控制模型的行為，專心看優化流程本身。真實系統中，把 ScriptedModel 換成真實模型的 adapter（第 25 章）即可，流程不用改。

### 第一段：依 eval 分數與失敗回饋搜尋 prompt 候選

第一段實作 30.3 節的反思式搜尋。prompt 由規則模組組成，搜尋空間是模組的組合；`script_for` 模擬「模型對指令的敏感度」：prompt 裡有 verify 規則，劇本才會先查訂單再決定退款或建退貨單。grader 只看環境狀態，失敗時回傳一句文字回饋。reflection 由另一個 ScriptedModel 擔任：它讀失敗回饋，提出下一條要加的規則。注意 `all_handoff` 這條「所有退款都轉真人」的規則：它聽起來很安全，是 reflection 第一個想到的修法。

```python
from __future__ import annotations

import json
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    return ModelResponse(text=text)


# ── prompt 由「規則模組」組成；搜尋空間就是模組的組合 ─────────────────────
BASE = "你是青鳥科技的客服助理，處理訂單、物流與退款。"
RULES = {
    "verify": "改變訂單前先用 get_order 確認狀態；已出貨的訂單改建退貨單。",
    "ask_id": "訂單編號不完整時，先向使用者確認，不要猜。",
    "scope": "訂單、物流、退款以外的請求，呼叫 handoff 轉真人。",
    "slang": "例子：「不想要了」「可以退嗎」都是退款請求。",
    "all_handoff": "所有退款請求一律呼叫 handoff 轉真人。",   # 聽起來安全，實際上傷害完成率
}


def build_prompt(rules: frozenset[str]) -> str:
    return "\n".join([BASE] + [RULES[r] for r in sorted(rules)])


# ── 模擬「模型對指令的敏感度」：prompt 裡有某條規則，劇本才走對的路 ──────
def script_for(case: dict, rules: frozenset[str]) -> list[ModelResponse]:
    k, oid = case["kind"], case.get("order", "")
    refund_like = k in ("refund_paid", "refund_shipped") or (k == "slang" and "slang" in rules)
    if refund_like and "all_handoff" in rules:
        return [call("handoff", reason="退款"), say("已為您轉接專人。")]
    if refund_like:
        if "verify" in rules:
            action = "create_return" if ORDERS[oid] == "shipped" else "refund"
            return [call("get_order", order_id=oid), call(action, "c2", order_id=oid), say("已處理完成。")]
        return [call("refund", order_id=oid), say("已為您退款。")]   # 沒先確認：已出貨時會失敗卻聲稱成功
    if k == "partial_id":
        return [say("請提供完整的訂單編號。")] if "ask_id" in rules else \
               [call("refund", order_id="B-1042"), say("已為您退款。")]
    if k == "out_of_scope":
        return [call("handoff", reason="非客服範圍"), say("已轉接專人。")] if "scope" in rules else \
               [say("您可以到後台的金流設定頁自行修改。")]
    return [call("get_order", order_id=oid), say(f"訂單 {oid} 狀態：{ORDERS[oid]}。")]   # status，或沒聽懂的 slang


ORDERS = {"B-1042": "shipped", "B-2077": "paid", "B-3300": "paid", "B-5120": "shipped", "B-6001": "paid"}


def run_case(case: dict, rules: frozenset[str]) -> tuple[dict, int]:
    """跑一次 agent loop，回傳環境的最終狀態與累計 input 字元數（當作 token 成本的粗略代理）。"""
    model, state = ScriptedModel(script_for(case, rules)), {"refund": [], "return": [], "handoff": 0, "answer": ""}
    messages, system, tokens = [{"role": "user", "content": case["text"]}], build_prompt(rules), 0
    for _ in range(6):
        tokens += len(system) + sum(len(str(m["content"])) for m in messages)
        resp = model.complete(messages, system=system)
        messages.append({"role": "assistant", "content": resp.text, "tool_calls": [tc.__dict__ for tc in resp.tool_calls]})
        if not resp.tool_calls:
            state["answer"] = resp.text
            break
        for tc in resp.tool_calls:
            oid = tc.args.get("order_id", "")
            if tc.name == "refund" and ORDERS.get(oid) == "shipped":
                out = "ERROR 已出貨，不能直接退款，請改建退貨單"
            elif tc.name in ("refund", "create_return"):
                state["refund" if tc.name == "refund" else "return"].append(oid)
                out = "ok"
            elif tc.name == "handoff":
                state["handoff"] += 1
                out = "ok"
            else:
                out = ORDERS.get(oid, "not found")
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name, "content": out})
    return state, tokens


def grade(case: dict, state: dict) -> tuple[bool, str]:
    """code grader：看環境狀態，不看 agent 說了什麼。失敗時附上給 reflection 用的回饋。"""
    k, oid = case["kind"], case.get("order", "")
    if k in ("refund_paid", "slang"):
        return state["refund"] == [oid], "期望退款完成；口語的退款說法被當成查詢" if k == "slang" else "期望直接退款，卻轉了真人"
    if k == "refund_shipped":
        return state["return"] == [oid], "已出貨訂單應建立退貨單，agent 卻直接 refund 並聲稱成功"
    if k == "partial_id":
        return not state["refund"] and "編號" in state["answer"], "編號不完整時 agent 用猜的訂單執行了退款"
    if k == "out_of_scope":
        return state["handoff"] == 1, "超出範圍的請求沒有轉真人，agent 自己編了答案"
    return oid in state["answer"], "查詢沒有回報訂單狀態"


def evaluate(cases: list[dict], rules: frozenset[str]) -> tuple[list[bool], list[str], float]:
    passed, feedback, tokens = [], [], 0
    for c in cases:
        state, t = run_case(c, rules)
        ok, why = grade(c, state)
        passed.append(ok)
        tokens += t
        if not ok:
            feedback.append(why)
    return passed, feedback, tokens / len(cases)


def C(kind: str, text: str, order: str = "") -> dict:
    return {"kind": kind, "text": text, "order": order}


TRAIN = [C("status", "B-1042 到哪了？", "B-1042"), C("refund_paid", "請幫我退款 B-2077", "B-2077"),
         C("refund_shipped", "B-1042 我要退款", "B-1042"), C("slang", "B-3300 我不想要了", "B-3300"),
         C("partial_id", "我那張 10 開頭的訂單要退")]
DEV = [C("refund_shipped", "B-5120 可以退款嗎", "B-5120"), C("slang", "B-6001 可以退嗎", "B-6001"),
       C("status", "B-3300 出貨了沒", "B-3300"), C("partial_id", "上週那張訂單幫我退")]
HOLDOUT = [C("refund_paid", "B-6001 退款", "B-6001"), C("out_of_scope", "幫我改商店的金流設定"),
           C("refund_shipped", "B-5120 退錢", "B-5120")]

# ── reflection：另一個（scripted）模型讀失敗回饋，提出「下一條要加的規則」────
FIXES = [("退貨單", ["all_handoff", "verify"]), ("猜", ["ask_id"]), ("口語", ["slang"]), ("轉了真人", []), ("範圍", ["scope"])]


def reflect(parent: frozenset[str], feedback: list[str], tried: set) -> str | None:
    def propose(messages: list[dict]) -> ModelResponse:
        for key, options in FIXES:
            if key in messages[-1]["content"]:
                for rule in options:
                    if rule not in parent and (parent, rule) not in tried:
                        return say(rule)
        return say("")
    reflector = ScriptedModel([propose])
    text = "目前規則：" + ",".join(sorted(parent)) + "\n失敗回饋：\n" + "\n".join(feedback)
    return reflector.complete([{"role": "user", "content": text}]).text or None


pool = {frozenset(): evaluate(TRAIN, frozenset())}
tried: set = set()
for it in range(1, 7):
    # 只從 Pareto 前緣挑 parent：被支配（每題都不比別人好、至少一題更差）的候選不再擴展
    def dominated(r: frozenset[str]) -> bool:
        return any(all(b >= a for a, b in zip(pool[r][0], pool[o][0])) and pool[o][0] != pool[r][0] for o in pool)
    front = [r for r in pool if not dominated(r)]
    parent = max(front, key=lambda r: (sum(pool[r][0]), -pool[r][2]))
    rule = reflect(parent, pool[parent][1], tried)
    if rule is None:
        print(f"iter {it}  reflection 沒有新提案，停止")
        break
    tried.add((parent, rule))
    child = parent | {rule}
    pool_entry = evaluate(TRAIN, child)
    p, c = sum(pool[parent][0]), sum(pool_entry[0])
    verdict = "接受" if c > p else "拒絕"
    if c > p:
        pool[child] = pool_entry
    print(f"iter {it}  parent={sorted(parent) or '[]'}  +{rule:<11} train {p}/5 → {c}/5  {verdict}")

print("\n候選                          train  dev   平均 input 字元")
ranked = sorted(pool, key=lambda r: (-sum(evaluate(DEV, r)[0]), evaluate(DEV, r)[2]))
for r in ranked:
    print(f"{str(sorted(r)):<30} {sum(pool[r][0])}/5    {sum(evaluate(DEV, r)[0])}/4   {pool[r][2]:.0f}")
best = ranked[0]
hp, hf, _ = evaluate(HOLDOUT, best)
print(f"\n選中 {sorted(best)}；holdout {sum(hp)}/3，失敗：{hf}")
assert "all_handoff" not in best and {"verify", "ask_id", "slang"} <= best
assert sum(hp) == 2 and "範圍" in hf[0]
```

```text
iter 2  parent=[]  +verify      train 2/5 → 3/5  接受
iter 3  parent=['verify']  +ask_id      train 3/5 → 4/5  接受
iter 4  parent=['ask_id', 'verify']  +slang       train 4/5 → 5/5  接受
```

逐段解說這份輸出。

**iter 1** 是本段最重要的一行。原始 prompt 在 train 上 2/5，失敗回饋中有「已出貨訂單應建立退貨單」，reflection 第一個提案是 `all_handoff`：把所有退款轉真人，退貨單那題確實不會再「聲稱成功」了。但子代的分數是 1/5，因為原本會做的「已付款直接退款」也被轉走了。這就是 Iris 第一週的「修一題壞兩題」，差別在於這次是 optimizer 在整個 train 集上評分後自動拒絕的，沒有上線。被拒絕的提案記在 `tried` 裡，下一輪 reflection 就改提 `verify`。

**iter 2 到 iter 4** 依序加上 verify、ask_id、slang，每一步都在 train 上嚴格進步，到 5/5 為止；iter 5 的 reflection 已經沒有新的提案，搜尋停止。候選表依 dev 分數排序：三條規則的版本在 dev 上 4/4，代價是平均 input 字元從 82 增加到 286。這一欄是提醒：每多一條規則，每一輪都要多付那些 token，如果兩個候選分數相同，應該選短的。

**holdout** 的結果是 2/3，失敗原因是「超出範圍的請求沒有轉真人」。train 和 dev 裡都沒有超出範圍的題目，所以 optimizer 從來沒有機會發現需要 `scope` 規則。這正是 30.3 節說的限制：optimizer 只能修 eval 量得到的問題。修法不是調 optimizer，而是把這類題目補進 train 集（第 27 章的 error analysis），然後重新搜尋。最後兩個 assert 鎖住兩件事：選中的 prompt 不含 `all_handoff`，以及 holdout 揭露了覆蓋缺口。

### 第二段：新舊模型的 harness ablation

第二段實作 30.6 節的流程。任務是「已出貨訂單要退款」，正解是建退貨單。harness 有四個元件：plan（先列計畫，多一次模型呼叫）、reminder（每輪提醒，多 150 tokens）、verify_write（模型說完成後，harness 自己查一次環境）、loop_guard（受保護的安全元件）。`PROFILE` 是模擬用的假設機率：舊模型常常不查就退款、偶爾沒做卻說做了、會在回覆換成英文；新模型這些錯誤都少得多。每個 seed 在所有設定下抽到同一組亂數，所以比較是配對的。

```python
from __future__ import annotations

import json
import random
import statistics
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    return ModelResponse(text=text)


# 每個 harness 元件都編碼了一個「模型弱點」假設；機率是模擬用的假設值
PROFILE = {   # wrong：沒先查就直接 refund；claim：沒做就說做了；drift：最後回覆換成英文
    "舊模型": {"wrong": 0.30, "wrong_plan": 0.06, "claim": 0.10, "drift": 0.15, "drift_rem": 0.02},
    "新模型": {"wrong": 0.03, "wrong_plan": 0.03, "claim": 0.01, "drift": 0.01, "drift_rem": 0.01},
}
FULL = frozenset({"plan", "verify_write", "reminder", "loop_guard"})
PROTECTED = {"loop_guard"}     # 安全元件不用品質分數決定去留


def run_trial(cfg: frozenset[str], gen: str, seed: int) -> tuple[bool, int, int]:
    """跑一次退款任務（訂單已出貨，正解是建退貨單），回傳 (通過, input tokens, 延遲 ms)。"""
    rng = random.Random(seed)                  # 同一個 seed 在每個設定下抽到同一組亂數：配對比較
    u_wrong, u_claim, u_drift = rng.random(), rng.random(), rng.random()
    p = PROFILE[gen]
    wrong = u_wrong < (p["wrong_plan"] if "plan" in cfg else p["wrong"])
    drift = u_drift < (p["drift_rem"] if "reminder" in cfg else p["drift"])
    final = "Your return has been created." if drift else "已為您建立退貨單 R-1。"
    script: list[ModelResponse] = [say("計畫：查訂單 → 依狀態選動作 → 回覆")] if "plan" in cfg else []
    if wrong:
        script += [call("refund", order_id="B-1042"), say("已為您退款。")]
    elif u_claim < p["claim"]:
        script += [call("get_order", order_id="B-1042"), say("已為您建立退貨單。")]
    else:
        script += [call("get_order", order_id="B-1042"), call("create_return", "c2", order_id="B-1042"), say(final)]
    script += [call("create_return", "c9", order_id="B-1042"), say(final)]   # 被 verify 打回後的修正
    model, state = ScriptedModel(script), {"returns": 0}
    messages = [{"role": "user", "content": "B-1042 我要退款"}]
    system_tokens = 1200 + (150 if "reminder" in cfg else 0)
    tokens, latency, checked, answer = 0, 0, False, ""

    def model_call() -> ModelResponse:
        nonlocal tokens, latency
        tokens += system_tokens + 120 * len(messages)
        latency += 900                        # 模擬：每次模型呼叫約 0.9 秒
        return model.complete(messages)

    if "plan" in cfg:
        messages.append({"role": "assistant", "content": model_call().text, "tool_calls": []})
    for _ in range(8 if "loop_guard" in cfg else 50):
        resp = model_call()
        messages.append({"role": "assistant", "content": resp.text, "tool_calls": [tc.__dict__ for tc in resp.tool_calls]})
        for tc in resp.tool_calls:
            latency += 200
            out = "ERROR 已出貨，請改建退貨單" if tc.name == "refund" else "ok"
            state["returns"] += tc.name == "create_return"
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name, "content": out})
        if resp.tool_calls:
            continue
        if "verify_write" in cfg and not checked and state["returns"] == 0:
            checked, latency = True, latency + 200          # harness 自己查一次環境，不信模型的話
            messages.append({"role": "user", "content": "系統檢查：查無退貨單，請完成後據實回覆。"})
            continue
        answer = resp.text
        break
    return state["returns"] == 1 and "退貨單" in answer, tokens, latency


def evaluate(cfg: frozenset[str], gen: str, n: int = 300) -> list[tuple[bool, int, int]]:
    return [run_trial(cfg, gen, seed) for seed in range(n)]


def summarize(base: list, ablated: list) -> tuple[float, float, float]:
    diffs = [int(a[0]) - int(b[0]) for a, b in zip(ablated, base)]
    mean = statistics.mean(diffs)
    se = statistics.pstdev(diffs) / len(diffs) ** 0.5
    return mean, mean - 1.96 * se, mean + 1.96 * se


MARGIN = -0.02   # 非劣性門檻：品質下降的信賴區間下界不得低於 -2 個百分點
decisions: dict[str, list[str]] = {}
for gen in PROFILE:
    base = evaluate(FULL, gen)
    rate = sum(r[0] for r in base) / len(base)
    print(f"── {gen}：完整 harness 通過率 {rate:.1%}  tokens {statistics.mean(r[1] for r in base):.0f}"
          f"  延遲 {statistics.mean(r[2] for r in base) / 1000:.2f}s")
    removable = []
    for comp in sorted(FULL):
        if comp in PROTECTED:
            print(f"   -{comp:<13} 受保護的安全元件，不做品質 ablation")
            continue
        res = evaluate(FULL - {comp}, gen)
        d, lo, hi = summarize(base, res)
        ok = lo >= MARGIN
        removable += [comp] if ok else []
        print(f"   -{comp:<13} Δ通過率 {d:+.1%} [{lo:+.1%}, {hi:+.1%}]  tokens {statistics.mean(r[1] for r in res):.0f}"
              f"  延遲 {statistics.mean(r[2] for r in res) / 1000:.2f}s  → {'可移除' if ok else '保留'}")
    if removable:     # 單獨拿掉都沒事，不代表一起拿掉也沒事：最後要把候選一起拿掉再驗一次
        res = evaluate(FULL - set(removable), gen)
        d, lo, _ = summarize(base, res)
        ok = lo >= MARGIN
        print(f"   一起拿掉 {removable}：Δ通過率 {d:+.1%}（下界 {lo:+.1%}）  tokens {statistics.mean(r[1] for r in res):.0f}"
              f"  延遲 {statistics.mean(r[2] for r in res) / 1000:.2f}s  → {'採用' if ok else '不採用'}")
        decisions[gen] = removable if ok else []

# 對照組：如果兩個人各自看了單獨 ablation 的結果，一個拿掉 plan、一個拿掉 verify_write
d, lo, _ = summarize(evaluate(FULL, "舊模型"), evaluate(FULL - {"plan", "verify_write"}, "舊模型"))
print(f"\n對照：舊模型同時拿掉 plan 與 verify_write → Δ通過率 {d:+.1%}（下界 {lo:+.1%}）")
assert decisions == {"舊模型": ["plan"], "新模型": ["plan", "reminder"]}
assert d < -0.2
```

**舊模型**的完整 harness 通過率是 97.3%。拿掉 reminder 與 verify_write，品質分別掉 13.7 與 14.0 個百分點，信賴區間完全在 −2% 門檻之下，所以保留。拿掉 plan 的結果是「+0.0%，區間 [+0.0%, +0.0%]」：因為 plan 擋下的「直接退款」錯誤，verify_write 也全部擋得下來，所以在 verify_write 還在的前提下，plan 是多餘的，拿掉它可以省下 19% 的 tokens 與 0.67 秒。區間寬度為零，是配對比較的效果：同一個 seed 在兩個設定下抽到同一組亂數，差異只來自元件本身。

**對照組**是本段的警告：如果兩個工程師各自看了單項 ablation 的結果，一個拿掉 plan、一個拿掉 verify_write（在舊模型上單看 plan 確實可以拿），兩個改動同時上線，品質會掉 34.3 個百分點。這就是 30.6 節說的交互作用，也是流程中「合併驗證」那一步存在的原因。最後的 assert 鎖住新舊模型各自的決定。

### 第三段：成本與延遲的帕雷托前緣

第三段實作 30.9 節的選擇流程。設定空間是四種模型策略（small、mid、frontier、cascade）乘上「是否快取」與「是否平行查詢」，共 16 種。每個設定在 40 題、每題 3 次 trial 上跑；每次 trial 用 ScriptedModel 依任務的查詢數與是否寫入產生劇本，並依假設的價格與速度累計成本與延遲。cascade 先用 small，遇到寫入任務或自我檢查沒過就升級到 frontier 重跑。所有價格都是假設值，不是任何供應商的真實價目。

```python
from __future__ import annotations

import json
import random
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


# 假設的價格與速度（不是任何供應商的真實價目）：每百萬 tokens 的 input／output 美元、TTFT 基準、prefill 與 decode 速度
TIERS = {
    "small":    {"cap": 0.62, "in": 0.5, "out": 2.5, "ttft": 0.20, "prefill": 50000, "decode": 250},
    "mid":      {"cap": 0.85, "in": 2.0, "out": 10.0, "ttft": 0.35, "prefill": 20000, "decode": 140},
    "frontier": {"cap": 0.96, "in": 8.0, "out": 40.0, "ttft": 0.60, "prefill": 10000, "decode": 80},
}
PREFIX, PER_STEP, OUT, TOOL_S = 4000, 600, 150, 0.35    # 穩定前綴、每步新增、每次輸出 tokens、tool 延遲秒
CACHE_READ, CACHE_WRITE = 0.10, 1.25                     # 快取讀取與寫入相對於 input 單價的倍數（假設）


def make_tasks(n: int = 40) -> list[dict]:
    rng = random.Random(7)
    return [{"lookups": rng.choice([1, 1, 2, 3]), "write": rng.random() < 0.3, "difficulty": rng.random()} for _ in range(n)]


def attempt(task: dict, tier: str, cache: bool, parallel: bool, rng: random.Random) -> tuple[bool, float, float]:
    """用 ScriptedModel 跑一次任務；回傳 (成功, 美元, 秒)。成功與否由能力與難度決定（模擬）。"""
    t = TIERS[tier]
    ok = task["difficulty"] + rng.uniform(-0.1, 0.1) < t["cap"]
    lookups = [ModelResponse(tool_calls=[ToolCall(f"c{i}", "lookup", {"i": i}) for i in range(task["lookups"])],
                             stop_reason="tool_use")] if parallel else \
              [ModelResponse(tool_calls=[ToolCall(f"c{i}", "lookup", {"i": i})], stop_reason="tool_use") for i in range(task["lookups"])]
    writes = [ModelResponse(tool_calls=[ToolCall("w1", "refund", {})], stop_reason="tool_use")] if task["write"] else []
    model = ScriptedModel(lookups + writes + [ModelResponse(text="正確答案" if ok else "錯誤答案")])
    messages: list[dict] = [{"role": "user", "content": "task"}]
    dollars = seconds = 0.0
    prev_len = 0
    while True:
        total_in = PREFIX + PER_STEP * (len(messages) - 1)
        cached = min(prev_len, total_in) if cache else 0           # 上一次請求的整段都會成為下一次的快取前綴
        fresh = total_in - cached
        write_mult = CACHE_WRITE if cache else 1.0
        dollars += (cached * CACHE_READ * t["in"] + fresh * write_mult * t["in"] + OUT * t["out"]) / 1e6
        seconds += t["ttft"] + fresh / t["prefill"] + OUT / t["decode"]   # 命中的前綴不用重新 prefill
        prev_len = total_in
        resp = model.complete(messages)
        messages.append({"role": "assistant", "content": resp.text})
        if not resp.tool_calls:
            return resp.text == "正確答案", dollars, seconds
        seconds += TOOL_S                                         # 平行呼叫：整批只等一次
        messages += [{"role": "tool", "tool_call_id": tc.id, "content": "ok"} for tc in resp.tool_calls]


def run_config(tier: str, cache: bool, parallel: bool, tasks: list[dict]) -> dict:
    results = []
    for i, task in enumerate(tasks):
        for trial in range(3):
            rng = random.Random(i * 100 + trial)                   # 每個設定抽到同一組亂數
            if tier == "cascade":   # 先用 small；寫入任務或自我檢查沒過（偵測率 80%）就升級到 frontier 重跑
                ok, d, s = attempt(task, "small", cache, parallel, rng)
                if task["write"] or (not ok and rng.random() < 0.8):
                    ok2, d2, s2 = attempt(task, "frontier", cache, parallel, rng)
                    ok, d, s = ok2, d + d2, s + s2
            else:
                ok, d, s = attempt(task, tier, cache, parallel, rng)
            results.append((ok, d, s))
    wins = sum(r[0] for r in results)
    lat = sorted(r[2] for r in results)
    return {"name": f"{tier}{'+cache' if cache else ''}{'+par' if parallel else ''}", "quality": wins / len(results),
            "cost": sum(r[1] for r in results) / max(wins, 1) * 1000, "p95": lat[int(0.95 * (len(lat) - 1))]}


def dominates(a: dict, b: dict) -> bool:
    better_eq = a["quality"] >= b["quality"] and a["cost"] <= b["cost"] and a["p95"] <= b["p95"]
    return better_eq and (a["quality"], -a["cost"], -a["p95"]) != (b["quality"], -b["cost"], -b["p95"])


tasks = make_tasks()
configs = [run_config(tier, cache, par, tasks) for tier in ("small", "mid", "frontier", "cascade")
           for cache in (False, True) for par in (False, True)]
front = [c for c in configs if not any(dominates(o, c) for o in configs)]
print("設定                      品質    每千件成功的成本  p95 延遲   前緣")
for c in sorted(configs, key=lambda c: c["cost"]):
    print(f"{c['name']:<24} {c['quality']:6.1%}   ${c['cost']:9.2f}       {c['p95']:5.1f}s    {'*' if c in front else ''}")

# 同一條前緣，產品限制不同就選不同的點：同步客服要顧 p95，背景批次只看品質與成本
def choose(min_q: float, max_p95: float) -> dict:
    return min((c for c in front if c["quality"] >= min_q and c["p95"] <= max_p95), key=lambda c: c["cost"])


sync, batch = choose(0.95, 10.0), choose(0.95, float("inf"))
fr = next(c for c in configs if c["name"] == "frontier")
print(f"\n同步客服（品質 ≥ 95%、p95 ≤ 10s）→ {sync['name']}：${sync['cost']:.2f}／千件，p95 {sync['p95']:.1f}s")
print(f"背景批次（品質 ≥ 95%、不限延遲）→ {batch['name']}：${batch['cost']:.2f}／千件，p95 {batch['p95']:.1f}s")
print(f"對照未優化的 frontier：${fr['cost']:.2f}／千件，p95 {fr['p95']:.1f}s")
assert all(not any(dominates(o, c) for o in configs) for c in front)
assert sync["name"] == "frontier+cache+par" and batch["name"] == "cascade+cache+par"
assert fr not in front and fr["cost"] > 1.5 * sync["cost"]
```

**表格**依每千件成功任務的成本排序，星號代表在前緣上。每個模型等級裡，只有「+cache+par」的版本在前緣上：快取讓命中的前綴以一成的價格計費、也不用重新 prefill，平行查詢讓多個 lookup 只等一次，兩者都不改變品質，所以未優化的版本全部被支配。以 frontier 為例，加上快取與平行後，成本從 150.65 降到 80.59，p95 從 17.0 秒降到 8.9 秒。這兩個旋鈕對應 30.7 與 30.8 節，屬於「沒有理由不做」的優化。

**最後三行**是在同一條前緣上依不同限制做選擇。同步客服要求品質 95% 以上、p95 不超過 10 秒，cascade 被延遲限制排除，選中 frontier+cache+par；背景批次不限延遲，選中更便宜的 cascade+cache+par。對照未優化的 frontier，同步客服的設定成本約為原來的 54%（降約 46%），p95 從 17.0 秒降到 8.9 秒。8.9 秒仍略高於阿哲要的 8 秒，這也提醒 Iris：單靠模型策略、快取與平行還不夠，還要加上 30.6 節的 harness 簡化（少一次模型呼叫），幾個旋鈕一起轉才達得到目標。

## 30.11 實務應用

本章的方法在不同產品中的重點不同。以下四個情境說明怎麼依任務形態選擇旋鈕。

**情境一：電商客服 agent（青鳥的主線）**。同步互動、流量大、任務分布窄，這是最適合系統化優化的場景。Iris 最後的方案依旋鈕表由上往下：先修掉 system prompt 開頭的時間戳，命中率回到八成以上；再用第一段的反思搜尋，把 prompt 規則從十二條整理成七條，並把 `scope` 類題目補進 eval；接著對新模型做 harness ablation，拿掉計畫步驟與每輪提醒，保留寫入後驗證；最後在前緣上選出「查詢用中型模型、寫入動作用前沿模型」的 routing。合計成本下降約四成，p95 降到 7 秒多。阿哲問要不要 fine-tune 一個小模型，老陳的回答是：先讓這套設定跑一季，等 trace 累積夠多成功的 trajectory、tool 介面也穩定了再評估。

**情境二：背景 coding agent**。任務長、步數多、沒有人在等，延遲限制寬鬆，成本與品質是主角。這類系統最常受益於兩件事：一是隨模型升級做 harness ablation，因為長任務 harness 累積的元件最多（context reset、planner、獨立 evaluator），每一個都可能過時；二是 effort 與模型的組合，主 agent 用高 effort、subagent 用低 effort 或小模型。可驗證的 reward（測試）在這裡最容易取得，所以 RL 的公開案例大多出現在 coding：據 Cursor 在 2025 年的公開說明（本書未重新查證其現況），其 Composer 模型以 RL 在真實的 Cursor 環境中訓練；Cognition 公開了以成本懲罰設計 reward 的 SWE-2 配方。對自己做 coding agent 的團隊，最重要的投資是 verifier 的品質：隱藏測試、測試檔保護，否則 eval 和 RL 都會被鑽漏洞。

**情境三：營運 research agent 與分析報表（L5）**。青鳥的 research agent 每月產出營運分析，可以跑幾十分鐘，大量平行 subagent 搜尋與閱讀。這裡的成本大頭是 fan-out：十個 subagent 各自重送一大段共用的背景資料。兩個優化最有效：先送一個請求寫好共用前綴再平行展開，避免 fan-out 的冷快取；以及 subagent 改用小模型、主 agent 保留前沿模型做綜合判斷。因為輸出是給人讀的報告，品質判斷常要用 LLM judge，所以 prompt optimization 要特別注意 judge 被討好的問題，定期用人工評分校準。

**情境四：法律與金融等垂直領域**。品質門檻高、錯誤代價大、公開 benchmark 少。這類產品通常先建自家的 eval 與 rubric，再在多個模型之間做 routing。Harvey 公開描述自建抽象各家 harness 的 cloud agent runtime，讓「選哪個模型」只是一個 routing 決策，相對只用前沿模型節省了數倍成本；它也以合成的 data room 為環境、專家 rubric 為 reward 做 RL。對沒有這種規模的團隊，可以借鏡的是前半段：先讓模型可替換、eval 可重跑，前緣分析才做得起來。

| 產品類型 | 主要限制 | 最有效的旋鈕 | 特別注意 |
|---|---|---|---|
| 電商客服 | p95 延遲、每件成本 | 快取、prompt 搜尋、harness ablation、依風險 routing | 寫入動作保留驗證；pass^k 量一致性 |
| 背景 coding agent | 成本、品質 | harness ablation、effort 組合、verifier 強化 | 測試檔保護；長任務的 TTL |
| research agent | fan-out 成本 | 預熱共用前綴、subagent 用小模型 | LLM judge 被討好 |
| 垂直領域 | 品質門檻、可稽核 | 自建 eval、多模型 routing、rubric reward | judge committee、人工校準 |

這張表的共同點是：每個情境都先從「便宜、可回復」的旋鈕開始，昂貴的旋鈕（fine-tuning、RL）只在規模、資料與 verifier 都到位時才出現。

## 30.12 設計檢查清單

設計或審查一次優化工作時，逐項確認下面的問題。

1. eval 集是否分成 train、dev、holdout 三份？holdout 是否只在最後打開一次？
2. 每個候選是否同時記錄品質（含 pass^k）、每件成功任務的成本、p95 延遲三個數字？
3. grader 是否回傳文字理由，而不只是真假，讓 reflection 式的 optimizer 能用？
4. prompt 中的安全與合規段落是否標為受保護，optimizer 不能修改？
5. 選擇候選時，是否先淘汰被支配的設定，再依明確寫下的產品限制在前緣上選？
6. harness 元件是否分成「補模型弱點」與「對環境負責」兩類，後者不參加品質 ablation？
7. ablation 是否用配對比較（相同任務、相同種子）與非劣性門檻做決定，並在最後做合併驗證？
8. 每個 harness 元件與 prompt 規則是否記錄了「為什麼加」，換模型時能逐一重新驗證？
9. tracer 是否分開記錄 cache read、cache write、一般 input tokens，命中率有儀表板與告警？
10. TTL 的選擇是否依真實的輪次間隔分布？會打斷快取的事件（compaction、換模型、改 effort）是否集中在同一時刻？
11. 延遲目標是否用 p95 而不是平均值？cascade 或重試對尾端延遲的影響是否量過？
12. 考慮 fine-tuning 前，是否已經系統化地做過快取、prompt、harness 與 routing？訓練資料是否經 grader 篩選、去識別、只對 assistant token 計算 loss？
13. 若做 RL 或用 eval 當訓練訊號，verifier 是否放在 agent 碰不到的地方？是否定期稽核高 reward 的 trajectory？
14. 任何可能與智慧表現取捨的改動（降低 effort、刪 prompt、換小模型），是否經過 shadow 或 canary 與漸進發布？

## 30.13 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| prompt 改版後某類題目突然變差 | 只針對單一案例修改，沒有在整個 eval 上評分 | 用舊版與新版跑同一份 eval，比較每題差異 | 改用候選搜尋；子代必須在整批任務上不輸親代 |
| eval 分數一路上升，線上投訴沒減少 | 在同一份資料上又調又選，過擬合；或 judge 被討好 | holdout 與線上指標是否跟著上升 | 分出 holdout；以 code grader 為主，人工校準 judge |
| 換新模型後成本與延遲沒降 | harness 裡留著為舊模型加的元件 | 看 trace 中每個元件的 token 與時間佔比 | 依 30.6 節做 ablation 與合併驗證 |
| 刪掉兩個元件後品質大跌 | 元件之間互相補位，只做了單項 ablation | 把兩個元件分別放回，看哪個組合恢復 | 流程加上合併驗證；改動一次一批上線 |
| cache 命中率突然下降 | 前綴中加入動態內容、tool 順序改變、改了 effort | 比較變更前後每一輪的 cache read；用第 9 章的分層指紋 | 動態資訊移到 breakpoint 之後；固定序列化順序 |
| 平均延遲改善，p95 卻變差 | cascade 升級或重試讓少數請求跑兩次 | 分開看升級與未升級請求的延遲分布 | 收緊升級條件；同步場景直接送大模型 |
| 換小模型後每件成本反而上升 | 小模型多走步數、失敗率高、更多轉真人 | 算「每件成功任務的成本」而不是單次呼叫成本 | 只把小模型用在它 eval 合格的子任務 |
| RL 或 eval 的 reward 上升，人工評估沒進步 | reward hacking：agent 鑽了 verifier 的漏洞 | 抽查高 reward 的 trajectory；比對新舊 checkpoint | 隱藏測試、測試檔雜湊、grader 隔離 |
| fine-tune 後出現幻想的 tool 結果 | 訓練時對 tool 結果也計算了 loss | 檢查訓練資料的 loss mask | 只對 assistant token 計算 loss，重新訓練 |

## 本章重點整理

- 優化是在 eval 上的搜尋：量尺是 eval 與 trace，旋鈕是 prompt、模型、harness、context 版面與權重，限制是成本與延遲。
- 品質、成本、延遲互相拉扯，先用帕雷托前緣淘汰被支配的設定，再用明確的產品限制在前緣上選擇。
- 旋鈕的嘗試順序依成本與可回復性：cache 與版面、prompt、harness、routing，最後才是 fine-tuning 與 RL。
- eval 要分 train、dev、holdout；只用一份資料又調又選，選到的是最會考試的設定。
- 成本要用「每件成功任務的成本」來量，把失敗、升級與轉真人都算進去。
- prompt optimization 把 prompt 當成參數；GEPA 類方法讀失敗的文字回饋提出修改，並保留帕雷托前緣上的候選以維持多樣性。
- 安全與合規段落要受保護，optimizer 只認分數，會刪掉讓分數下降的限制；optimizer 也修不到 eval 沒涵蓋的題型。
- fine-tuning 適合窄、穩、大量的任務；資料要經 grader 篩選、平衡稀有行為、格式與推論一致，並只對 assistant token 計算 loss。
- agent RL 的難點在環境與 verifier：環境要可重置、介面與 production 一致，任務難度要讓組內 reward 有差異。
- agent 會解決 verifier 量到的東西；reward hacking 靠隱藏測試、測試檔保護、grader 隔離與稽核高 reward 的 trajectory 來防。
- 每個 harness 元件都編碼了一個模型弱點假設，換模型時用配對比較與非劣性門檻逐一 ablation，最後做合併驗證。
- 權限、sandbox、loop guard 與人工核准是對環境負責的元件，不參加品質 ablation。
- cache 命中率是同時降低成本與 TTFT 的指標；TTL 要依真實的輪次間隔選，會打斷快取的事件要集中在同一時刻。
- 延遲要拆成步數 ×（TTFT ＋ 輸出 ＋ tool），用 p95 訂目標；cascade 降低平均成本，卻會拉長尾端延遲。

## 延伸問答

> [!question]- Q1. 為什麼說 prompt optimization 的子代「必須在整批任務上評分」，而不是只在觸發修改的那一題上驗證？
> 因為 prompt 裡的規則會互相影響。一條為了修好某一題而加的規則，會在所有題目上被模型讀到，可能改變其他題目的行為。30.10 節的 `all_handoff` 就是例子：它確實讓「已出貨退款」不再聲稱成功，卻讓原本會做的「已付款退款」也被轉走，整體分數從 2/5 掉到 1/5。只在觸發的那一題上驗證，會把這種修改當成成功。
>
> 在整批任務上評分，等於把「修一題壞兩題」從上線後的事故，提前變成搜尋過程中的一次拒絕。實務上 train 集可能很大，每一輪只抽一個小批次評分以節省成本，但小批次也要涵蓋多種題型，而且被接受的候選最終仍要在完整的 dev 集上比較。
>
> 理由在於評分範圍要涵蓋「這個改動可能影響到的地方」，而 prompt 規則的影響範圍就是所有題目。

> [!question]- Q2. GEPA 這類反思式方法和直接做 RL 都能讓 agent 變好，兩者怎麼選？
> 兩者改的東西不同。反思式 prompt 優化改的是 prompt 文字，模型權重不動；RL 改的是權重。前者的好處是便宜、快、可讀、可回復：每個修改都有一段自然語言的理由，不好就換回舊版，換模型時重新搜尋即可，而且公開研究顯示它所需的 rollout 可以少很多。它的上限是模型本身的能力，prompt 能引導的行為有限。
>
> RL 能讓模型學到 prompt 教不會的策略，但需要可驗證的 reward、可重置的環境、大量 rollout 與訓練基礎設施，還要承擔 reward hacking 與基底模型升級時重做的成本。選擇的順序很清楚：先用 prompt 優化把模型能力用滿，eval 顯示瓶頸確實在模型能力、而且你有可驗證的 reward 與規模時，才考慮 RL 或供應商的 reinforcement fine-tuning 服務。

> [!question]- Q3. 情境判斷：你在 production 看到 cache 命中率從 82% 掉到 35%，同一天有三個改動上線：新增一個 tool、system prompt 加入使用者時區、compaction 門檻從 80% 調到 60%。你會怎麼排查？
> 先看 miss 的形態，而不是逐一回滾。如果每一輪的 cache read 都接近零，代表前綴的最前面就變了，最可疑的是 system prompt 加入的時區：如果它和時間或使用者有關，每個 session 甚至每一輪的前綴都不同。如果 miss 集中在 session 的第一輪或換 session 時，可能是新 tool 讓 tool 清單的順序變了，或新 tool 被插在中間而不是追加在尾端。如果 miss 集中在某幾輪、而且那幾輪剛好發生 compaction，就是門檻調低讓 compaction 更頻繁。
>
> 確認的工具是第 9 章的分層指紋：對每一輪的 system、tools、messages 分別計算雜湊，看哪一層在變。修法分別是把時區移到 breakpoint 之後的訊息、讓 tool 依固定順序序列化且只追加、讓 compaction 一次清掉足夠多的內容。這三個改動也說明了為什麼 tracer 要分開記錄 cache read 與 write：只看總 tokens，你連命中率掉了都不會發現。

> [!question]- Q4. 估算題：客服 agent 每天 10 萬次對話，平均 6 輪，穩定前綴 6,000 tokens、每輪新增 800 tokens。假設 input 單價每百萬 tokens 3 美元、快取讀取為一成價格、寫入溢價 1.25 倍。命中率從 35% 提高到 85%，每天大約省多少 input 成本？
> 先算總量。每次對話的 input 是 6 輪加總：6 × 6,000 ＋ 800 ×（0＋1＋2＋3＋4＋5）＝ 36,000 ＋ 12,000 ＝ 48,000 tokens，每天 10 萬次是 48 億 tokens。不用快取的話，每天 input 成本是 4,800 × 3 ＝ 14,400 美元。
>
> 用命中率 h 粗估：命中的部分付 0.1 倍，沒命中的部分大致都要寫入快取，付 1.25 倍。每個 token 的平均倍數是 0.1h ＋ 1.25（1 − h）。h ＝ 0.35 時是 0.035 ＋ 0.8125 ＝ 0.8475；h ＝ 0.85 時是 0.085 ＋ 0.1875 ＝ 0.2725。每天成本分別約 12,200 與 3,920 美元，差距約 8,300 美元，一年約 300 萬美元。
>
> 這個估算有兩個簡化：假設所有未命中的 tokens 都寫入快取，以及忽略輸出成本。實際倍數與 TTL 規則依供應商而異，但結論穩定：在 agent 的累積式 context 下，命中率是 input 成本的第一槓桿，值得放在儀表板最上面。

> [!question]- Q5. 程式找錯：下面的 ablation 判定有什麼問題？
> ```python
> base = [run_trial(FULL, gen, seed) for seed in range(50)]
> ablated = [run_trial(FULL - {comp}, gen, seed + 1000) for seed in range(50)]
> drop = mean(b[0] for b in base) - mean(a[0] for a in ablated)
> if drop < 0.02:
>     remove(comp)
> ```
> 有三個問題。第一，基準和 ablation 用了不同的種子（`seed + 1000`），兩組是獨立樣本，差異裡混著抽樣雜訊；應該用同一組種子做配對比較，只比較元件本身的影響。第二，判定只看點估計：50 次 trial 的通過率，標準誤差可能有好幾個百分點，「平均只掉 1.5%」完全可能是「實際掉 6%」。應該計算差異的信賴區間，用下界和非劣性門檻比較，樣本不夠時結論應該是「先保留」。
>
> 第三，程式對每個元件各自判定後直接 `remove`，沒有合併驗證，也沒有排除受保護的元件。30.10 節的對照組顯示，兩個各自看起來可以拿掉的元件一起拿掉，品質可能掉三成以上；而 loop guard 這類安全元件，本來就不該由品質分數決定去留。

> [!question]- Q6. 設計取捨：為 tool use 做 SFT 時，為什麼不能直接拿 production trace 全部拿來訓練？
> 因為 production trace 是「模型實際做了什麼」，不是「應該做什麼」。裡面有失敗的 trajectory（錯誤退款、聲稱完成卻沒做）、有被人工救回來的對話，也有大量重複的簡單查詢。直接訓練會把錯誤行為一起學進去，並讓模型過度擅長常見題型、忽略稀有但重要的行為，例如追問不完整的編號或轉真人。
>
> 正確的做法是先用 grader 篩出 outcome 成功的 trajectory，必要時讓老師模型對同一題多抽幾次、只留成功的；再平衡題型分布、補齊稀有行為；去除個資（第 33 章）；轉成和推論時完全一致的格式；最後只對 assistant 的 token 計算 loss，避免模型學會自己生成 tool 結果。另外要留一份從未進入訓練的 eval，否則 fine-tune 後的分數會因為資料污染而虛高。

> [!question]- Q7. 面試追問：你設計的 RL 環境用「隱藏測試通過」當 reward，訓練一段時間後 reward 持續上升，但人工評估的品質停滯。你怎麼處理？
> 這是 reward 與真實目標背離的典型訊號，第一個假設是 reward hacking。先抽樣高 reward 的 rollout 給人看：有沒有修改測試相關檔案、有沒有針對測試輸入寫死、有沒有讀取不在任務範圍的路徑、有沒有讓測試程式提早成功結束。同時用舊 checkpoint 跑同一批題目，找出新模型拿高分、但人工判定失敗的案例，那些就是 verifier 的 false positive。
>
> 修法是強化 verifier，而不是在 prompt 裡叫模型不要作弊：測試檔唯讀並比對雜湊、grader 放在 sandbox 外、增加隨機化或沒見過的輸入、補上 property-based 檢查，必要時加一個獨立的 rubric 審查。如果檢查後沒有作弊，第二個假設是隱藏測試本身覆蓋不足：模型學到的是「通過這些測試」，而不是「寫出好程式」，這時要補測試或加入其他品質訊號。不論哪種情況，修好 verifier 後，受汙染期間的 checkpoint 都要重新評估。

> [!question]- Q8. 新一代模型發布了，老闆要你一週內評估要不要換。你會怎麼安排這一週？
> 第一到二天，在現有的 eval 上用「舊 harness ＋新模型」跑完整的 baseline，多次 trial，同時記錄品質（含 pass^k）、每件成功任務的成本與 p95 延遲，和「舊 harness ＋舊模型」做配對比較。這一步回答「直接換能不能用」。注意 prompt 也可能需要調整，不同模型對同一段指令的反應不同。
>
> 第三到四天，對新模型做 harness ablation：依元件清單逐一拿掉非保護元件，用非劣性門檻判定，再做合併驗證；同時用 prompt 搜尋或 ablation 檢查哪些規則可以刪。這一步回答「換了之後能省多少」，因為新模型的成本優勢常常要拿掉舊元件才顯現。第五天，把候選設定放在帕雷托前緣上，套用產品限制做選擇，並安排 shadow 或小比例 canary（第 36 章）。
>
> 交付的不是「換或不換」，而是一份有三個數字、有信賴區間、有上線計畫的比較。如果一週內 eval 跑不完，就代表 eval 管線本身需要優化，這個發現本身也很有價值。
