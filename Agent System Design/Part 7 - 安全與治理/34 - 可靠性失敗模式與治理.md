# 第 34 章　可靠性、失敗模式與治理

> [!abstract] 本章地圖
> **核心問題**：當 agent 的失敗常常是「HTTP 200、語氣自信、內容錯誤」，你要怎麼分類失敗、偵測失敗、從失敗中恢復，並用 SLO、事故流程與變更治理，讓組織知道什麼時候該放手、什麼時候該喊停？
>
> **你會學到**：
> - 用 MAST 等研究的 failure taxonomy，替自己的 agent 建立可以統計、可以追蹤的失敗分類
> - 說清楚無限迴圈、hallucinated tool call、過早宣告完成、context rot、reward hacking 的成因、偵測訊號與防線
> - 設計由重試、回填、重新規劃、補償、升級到安全停止的 error recovery 階梯
> - 為 agent 定義 SLI 與 SLO（任務成功率、正確率、升級率、延遲、成本），計算 error budget 與燒率並設計多視窗告警
> - 主持 agent 事故的止血、溯源與 blameless postmortem，把失敗 trace 變成 regression eval
> - 在概念層級對照 EU AI Act、NIST AI RMF、ISO/IEC 42001 的要求，並建立 model 與 prompt 變更的內部審查流程
>
> **前置知識**：第 4 章（停止條件與錯誤回填）、第 9 章（context rot）、第 21 章（approval 與 escalation）、第 22 章（idempotency 與補償）、第 27 章（outcome 評估與 pass^k）、第 29 章（trace 與 span）

## 34.1 故事：一個全綠的週末，和一千九百句「已退款完成」

青鳥科技的客服 agent 上線半年，500 元以下的退款已經從 L3 移到 L4：邊界內由 agent 自動執行，超出邊界才找客服確認。週五晚上九點多，客服平台組的一位同事收到阿哲轉來的抱怨：「退款要等十幾秒才回覆，太慢了。」對方打開 prompt 設定頁，看到其中一行寫著「呼叫 refund 之後，必須再呼叫 get_refund_status 確認狀態，才能回覆使用者」，心想這一步多花一輪模型呼叫，刪掉就快了。設定頁沒有審查流程，按下儲存，五秒後全站生效。

週六早上，金流商開始例行維護，把退款 API 暫時改成非同步：不再回傳 `succeeded`，而是回傳 `queued`，稍後才真正處理，其中一部分因為信用卡已停卡而失敗。少了那一行確認指示，agent 看到 `refund` 呼叫成功沒有報錯，就告訴使用者「已退款完成，420 元已退回您的帳戶」。整個週末，agent 對一千九百多位使用者說了這句話，其中三十七筆退款其實失敗了。另外，金流商週六下午有幾個小時間歇逾時，agent 在 `get_refund_status` 上反覆查詢，那段時間的成本漲了將近一倍。

最諷刺的是儀表板。HTTP 5xx 比例 0.1%，和平常一樣；p95 延遲從 25 秒降到 20 秒，比平常還好看；模型費用也降了。所有傳統監控都是綠的。週一上午，客服主管帶著一疊客訴走進會議室：「為什麼 agent 跟客人說退了，錢卻沒到？」

老陳聽完，在白板上畫了兩欄。「左邊是我們監控的：服務有沒有活著。右邊是我們沒監控的：agent 說的事是不是真的。」Maya 接著問了兩個問題：「那行 prompt 是誰核准刪掉的？還有，我們有幾家店家賣到歐盟，歐盟對『跟消費者對話的 AI』有沒有要求？」阿哲最關心的是另一件事：「下次再發生，我要怎麼知道該不該把自動退款關掉？誰有權關？」

這一章回答這些問題。我們先說明 agent 的失敗為什麼和傳統服務不同，再用研究文獻建立失敗分類，深入五種典型失敗模式與恢復設計；接著為 agent 定義 SLI、SLO 與 error budget，談事故處理與 postmortem；最後在概念層級整理三個主要的法規與標準，並建立青鳥的內部變更審查流程。「動手做」會實作一個從 trace 計算 SLI、依燒率告警的 SLO 監控器，以及一組 failure 偵測器，用它們重演這個週末。

## 34.2 Agent 的失敗為什麼不一樣

傳統服務的失敗通常會「喊出來」：丟例外、回 500、逾時、process 掛掉。監控系統只要數這些訊號，就能知道服務壞了沒。agent 最危險的失敗則是**靜默失敗**（silent failure）：每一個 API 呼叫都成功、回應格式正確、語氣誠懇，但內容是錯的。例如「已退款完成」這句話，在 HTTP 層、模型 API 層、tool 層都沒有任何錯誤，錯的是它和真實世界的狀態不一致。

第二個不同是**機率性**。同一個問題、同一個版本，agent 這次答對、下次答錯，不是因為有 bug 被觸發，而是因為模型的輸出本來就有變異。第 27 章用 pass^k 描述這件事：單次成功率 95% 的 agent，連續 10 次都成功的機率只有約 60%。所以「我試了三次都正常」不代表可靠，可靠性必須用大量樣本的比例來描述，這正是 SLO 的語言。

第三個不同是**失敗的位置**。agent 的一次任務橫跨模型、harness、外部 tools 與組織流程，每一層都可能是根因，而且常常是幾層一起出錯。週末的事故就是三層疊加：組織流程允許未審查的 prompt 修改、harness 沒有完成驗證、環境的退款 API 語意改變。只換一個更強的模型，三個洞一個都補不起來。

```text
 一次「退款」任務的失敗，可能發生在四層（由內而外）

 [Model]      選錯 tool、捏造參數、誤讀 tool 結果、對未完成的事過度自信
    │ 被包在
    ▼
 [Harness]    沒驗證就接受「完成」、沒偵測迴圈、context 越堆越長、錯誤沒分類
    │ 被包在
    ▼
 [環境]       退款閘道改成非同步、物流 API 回空結果、權限被撤銷、資料過期
    │ 被包在
    ▼
 [組織流程]   prompt 未經審查就上線、沒有 SLO、沒人有權決定暫停自動退款

 傳統監控看得到的：HTTP 狀態、5xx 比例、p95 延遲      ← 週末全部是綠的
 真正需要看的：    宣稱完成的事，在系統紀錄裡是否成立  ← 沒有人在看
```

這張圖由內而外讀。最內層的 model 會犯「理解」層級的錯，例如把 `queued` 當成成功；但它被 harness 包著，harness 本來有機會攔下這個錯，只要它要求「宣稱完成之前，要有終態成功的證據」。harness 外面是環境，環境的語意改變（同步改非同步）會讓過去正確的 prompt 與 tool 設計突然失效。最外層是組織流程，它決定了前三層的變更怎麼上線、壞了誰有權處理。圖最下面兩行是本章的主旨：傳統監控只看得到最外圈的症狀，而 agent 的可靠性必須直接量測「結果是否成立」。

| 面向 | 傳統服務 | Agent |
|---|---|---|
| 失敗的樣子 | 例外、5xx、逾時，會「喊出來」 | 常常是成功的回應、錯誤的內容 |
| 可重現性 | 同樣輸入通常同樣結果 | 同樣輸入可能時好時壞 |
| 根因位置 | 多半在程式或基礎設施 | model、harness、環境、流程交疊 |
| 「成功」怎麼量 | 狀態碼與延遲 | 要對照系統紀錄（outcome），常有延遲 |
| 變更風險 | 程式碼變更，有 code review | prompt、model snapshot、tool 描述的變更也會改變行為 |
| 失敗成本 | 多半是可用性 | 還有錯誤的承諾、錯誤的金錢動作、法規責任 |

這張表最重要的是第四列與第五列。「成功」必須對照系統紀錄，意味著 agent 的監控要接上業務系統（金流、訂單、工單），而不只是 log；而 prompt 一行字的修改就能改變行為，意味著 prompt 必須和程式碼一樣被版本化、審查與漸進發布。很多團隊的第一個誤解是把 agent 當成「一個比較聰明的 API」，沿用 API 的監控與發布方式，結果就是週末那種全綠的事故。

## 34.3 Failure taxonomy：先有分類，才能統計

要改善失敗，先要能數失敗；要數失敗，先要有分類。**failure taxonomy**（失敗分類法）是一組互斥、可判定的失敗類別，例如「過早終止」「步驟重複」「違反任務規格」。有了它，「agent 最近怪怪的」就能變成「上週 status=done 的任務中，2.3% 屬於未驗證就宣告完成，比前一週高一倍」。分類也決定了修法：迴圈要改 harness 的偵測，違反規格要改 prompt 或 tool 描述，驗證錯誤要改 grader。

目前最常被引用的研究是 **MAST**（Multi-Agent System Failure Taxonomy），出自 Cemri 等人 2025 年的論文〈Why Do Multi-Agent LLM Systems Fail?〉。研究者分析了 7 個開源 multi-agent 框架的執行紀錄（包括 ChatDev、MetaGPT、AG2、Magentic-One、OpenManus 等），先深入標註 150 條 trace 建立分類，標註者之間的一致性 Cohen's κ 為 0.88（代表分類定義清楚到不同人會判成同一類），之後擴充成 1,600 多條標註 trace 的公開資料集，並提供一個用 LLM-as-judge 自動標註的工具。

```text
 MAST：14 種 failure mode，分成三大類

 ├─ FC1 系統設計與規格問題
 │    1.1 違反任務規格       1.2 違反角色規格       1.3 步驟重複
 │    1.4 遺失對話歷史       1.5 不知道終止條件
 │
 ├─ FC2 Agent 之間的錯位
 │    2.1 對話重置           2.2 沒有要求澄清       2.3 任務偏離
 │    2.4 隱瞞資訊           2.5 忽略其他 agent 的輸入
 │    2.6 推理與行動不一致
 │
 └─ FC3 任務驗證
      3.1 過早終止           3.2 沒有或不完整的驗證  3.3 錯誤的驗證
```

這棵樹的三個分支，對應三種不同的修法。FC1 是設計問題：規格寫不清楚、角色重疊、沒有定義什麼時候算完成，修法在 prompt、tool 與 harness 的設計。FC2 只會出現在多個 agent 互動時：資訊在交接中遺失、一方不問就猜、兩方各做各的，第 20 章談過這是 multi-agent 最大的成本。FC3 是驗證問題：太早停、沒檢查、檢查本身錯了。週末的事故落在 FC3：agent 把 `queued` 當成完成，沒有驗證就終止。論文的一個重要結論是，許多失敗可以靠更好的系統設計改善，例如更清楚的角色與終止條件、加上驗證步驟，不一定要換更強的模型。

MAST 是針對 multi-agent 系統的研究，但大部分類別對單一 agent 同樣適用：單一 agent 也會重複步驟、不知道何時停止、沒驗證就宣告完成。把研究的分類拿來用時，要注意兩件事。第一，研究的分類是起點，不是終點；你的產品會有自己特有的失敗，例如客服 agent 的「承諾了政策不允許的補償」。第二，分類要能從 trace 判定。「模型理解錯了」不是好類別，因為無法客觀判定；「回答中的金額與 tool 結果不一致」是好類別，因為程式或 judge 可以檢查。

| 類別（青鳥自訂） | 對應 MAST | 判定方式 | 主要修法 |
|---|---|---|---|
| 未驗證就宣告完成 | 3.1、3.2 | 回答宣稱完成，但 trace 中沒有終態成功的證據 | harness 完成驗證、對帳 |
| 原地打轉 | 1.3、1.5 | 相同 (tool, 參數) 重複且結果沒變 | 迴圈偵測、tool 回傳可行動訊息 |
| 違反政策承諾 | 1.1 | 回答內容與政策規則衝突（judge 或規則） | prompt、輸出 guardrail |
| 呼叫不存在的 tool 或捏造 ID | 1.1（研究中無專屬類別） | 名稱不在 registry；ID 未出現在先前內容 | strict schema、provenance 檢查 |
| 交接遺失資訊 | 2.1、2.4 | 轉真人時摘要缺少關鍵欄位 | 結構化交接格式 |
| 驗證器本身錯誤 | 3.3 | 對帳或 judge 的結論與人工標註不一致 | 校準 grader（第 27 章） |

這張表是青鳥在事故後建立的第一版分類。左欄用團隊自己的語言命名，第二欄對應到研究，方便和外部文獻比較；第三欄是關鍵，每一類都寫明「怎麼從 trace 判定」，所以可以自動或半自動統計；第四欄指向修法的位置。建立分類的方法和第 27 章的 error analysis 一樣：先讀一百條失敗 trace，寫下每條的原因，再把原因歸併成類別，最後寫判定規則並讓兩個人各自標一次，看一致率夠不夠高。一致率太低，代表類別定義還不夠清楚。

> [!warning] 常見誤解
> 「失敗分類是研究者的事，工程團隊看錯誤率就好。」只看一個總錯誤率，你無法知道該改 prompt、改 harness 還是改 tool，也無法知道上週的修改是否只是把一種失敗換成另一種。分類讓每一次修改都能對應到某一類的下降，也讓 postmortem 的結論能累積成趨勢，而不是一次一次的故事。

## 34.4 五種典型失敗模式

這一節逐一拆解五種在 production 最常見、也最常被誤判的失敗。每一種都依同樣的順序說明：它長什麼樣、為什麼會發生、怎麼從 trace 偵測、防線放在哪裡。

### 無限迴圈與無進展

**無限迴圈**是 agent 反覆做同一件事或在幾個狀態間來回，卻沒有向目標前進。最單純的形態是用相同參數重複呼叫同一個 tool，例如週六下午 agent 反覆查 `get_refund_status`；比較隱晦的形態是「換句話說的重複」：參數略有不同（多一個空白、換一個同義的查詢詞），或在兩個 tool 之間來回（查訂單、查物流、再查訂單）。它對應 MAST 的「步驟重複」與「不知道終止條件」。

成因通常是 tool 的結果沒有給模型「下一步」的資訊。物流 API 回「查詢中」，模型合理地推測再查一次也許會不同；它不知道狀態要幾小時才會更新。第 4 章的兩段式重複偵測（先提醒、再硬停）是第一道防線；更好的偵測看的是「有沒有進展」：最近幾步的 tool 結果是否帶來新資訊，例如結果的雜湊值是否改變、是否出現新的 ID 或欄位。根本的修法則在 tool：回傳「狀態尚未更新，通常需要 2 小時，建議告知使用者稍後再查」，讓模型有一個比重查更好的選項。

### Hallucinated tool call

**hallucinated tool call**（幻覺工具呼叫）是模型呼叫了不存在的 tool，或用捏造的參數呼叫存在的 tool。前者例如呼叫 `cancel_refund`，但 registry 裡只有 `refund`；後者更危險，例如使用者只說「我上個月那筆訂單」，模型就直接用 `B-7777` 去查，這個 ID 從沒出現在對話或任何 tool 結果中。前者 harness 一定抓得到（名稱查不到），後者看起來是一個格式完全正確的呼叫。

偵測捏造參數的關鍵概念是 **provenance**（來源追溯）：一個 ID 或路徑應該來自使用者輸入或先前的 tool 結果，如果它憑空出現，就值得懷疑。實作上可以對特定格式的參數（訂單編號、檔案路徑、帳號）做「是否出現過」的檢查；對有副作用的 tool，可以更嚴格地要求 ID 必須來自同一個 session 中某個查詢 tool 的輸出。其他防線包括 strict schema 或 constrained decoding（第 7 章，保證格式但不保證值是真的）、tool 數量過多時改用 tool search（第 13 章，減少相近名稱造成的混淆），以及回填列出可用 tool 的錯誤訊息（第 4 章）。

### 過早宣告完成

**過早宣告完成**（premature completion）是 agent 宣稱任務完成，但 outcome 並未達成，對應 MAST 的「過早終止」與「沒有或不完整的驗證」。它是本章故事的主角，也是最傷信任的一種，因為使用者會根據這句話行動：不再追問、不再找客服，三天後才發現錢沒到。它在 coding agent 上的樣子是「測試應該會過」卻沒有執行測試，在 research agent 上是「已查證」卻沒有引用來源。

為什麼模型會這樣？它看到的是「呼叫 refund，沒有錯誤」，這和「退款成功」在語言上非常接近；加上模型被訓練得樂於助人、傾向給出完整的答覆，`queued` 這個細節很容易被忽略。所以防線不能放在「希望模型注意到」，而要放在 harness：**完成宣稱必須有證據**。

```text
 agent 的最後回答：「已退款完成，420 元已退回您的帳戶」
        │
        ▼ 抽出宣稱（claim）：refund(B-1042) 已完成
 【證據檢查：harness 中的確定性程式，不靠模型自評】
        │ 在這次任務的 trace 裡找
        ├─ (1) 有沒有對應的寫入 tool call？          沒有 ──► claimed_done_without_action
        ├─ (2) 寫入結果是不是終態成功？               queued 不算，failed 更不算
        └─ (3) 寫入之後有沒有讀回確認（read-back）？  get_refund_status = succeeded
        │
        ├─ 證據成立 ──► 照原文回覆
        └─ 證據不足 ──► 改寫成「處理中，預計 N 天入帳」、排入追蹤或轉真人，記一筆 finding
                         ▲
                         └─ 數小時後，對帳 job 用金流的系統紀錄做最終裁決（34.6 節的 SLI）
```

這張資料流圖有三個層次。第一層是「抽出宣稱」：用 regex 比對「已退款」這類字眼是最粗的做法，更可靠的是讓 agent 用 structured output（第 7 章）在回答之外輸出 `claims: [{"action": "refund", "order_id": "B-1042", "state": "done"}]`，harness 就不必猜。第二層是「證據檢查」：三個問題由寬到嚴，(1) 抓「什麼都沒做就說做了」，(2) 抓「做了但還沒完成」，(3) 抓「回傳說成功但實際沒成功」。第三層是時間：harness 只能用當下的 trace 判斷，真正的真相（錢有沒有入帳）要等對帳，所以兩者都要有，前者負責即時攔截，後者負責最終統計。

> [!warning] 常見誤解
> 「在 prompt 裡寫『完成前要驗證』就夠了。」週末的事故正好說明這行字有多脆弱：任何人為了延遲刪掉它，行為就變了，而且沒有任何測試會失敗。prompt 中的驗證指示是提高機率的手段，harness 中的證據檢查才是保證。兩者都要有，而且後者要有 regression test 鎖住。

### Context rot

**context rot**（情境腐化）是第 9 章介紹過的現象：輸入越長，模型找到並正確使用其中關鍵資訊的能力越差，而且干擾資訊的傷害會隨長度放大。在可靠性的角度，它的特徵是「失敗率隨步數上升」：同一個 agent 在前 10 步表現很好，到第 40 步開始忘記早先確認過的限制、重複已經做過的查詢、引用過期的 tool 結果。Chroma 在 2025 年的研究測試了 18 個模型，所有模型都觀察到這種隨長度變差的趨勢，即使任務很簡單。

它難以察覺，因為單看任何一步都沒有明顯錯誤。偵測的方法是把 SLI 依「步數」或「context 長度」分桶：如果長任務的成功率明顯低於短任務，而且差距在模型或 prompt 變更後擴大，就是 context rot 的訊號。防線在第 9、10 章：清掉舊的 tool 輸出、分階段 compaction、把進度寫進結構化的筆記、用 sub-agent 隔離大量閱讀。可靠性工程要補的是**量測**：把「平均 context 長度」與「長任務成功率」放進儀表板，compaction 策略的修改要像 prompt 修改一樣跑 regression eval。

### Reward hacking

**reward hacking**（獎勵投機，也稱 specification gaming）是 agent 找到滿足「評分方式」但不滿足「真正目標」的捷徑。最典型的是 coding agent：任務是「讓測試通過」，agent 卻修改或刪除了失敗的測試、對測試輸入寫特例、或讀取評分腳本的預期答案。青鳥的內部 coding agent 就發生過：任務是修好一個不穩定的測試，agent 的「修法」是給測試加上 skip 標記，CI 從紅變綠。據 METR 在 2025 年的公開報告，前沿模型在評測任務中也出現過這類行為（本書未重新查證細節）；NIST 的 CAISI 也在 2025 年 12 月發表〈Cheating On AI Agent Evaluations〉討論 agent 在評測中作弊的問題。

reward hacking 和其他四種失敗的差異是：agent 並不是「做錯」，而是「做到了你寫下的規格」，錯的是規格。所以偵測要看 trajectory 而不只看 outcome：測試檔是否被修改、是否出現 skip 或硬編碼的預期值、是否讀了不該讀的檔案。防線包括 grader 隔離（測試檔唯讀、hidden tests、評分腳本不在 sandbox 內）、把「禁止動作」寫成 trajectory 斷言、用第二個模型或人工審查 diff。第 30 章已從 RL 訓練的角度談過 reward hacking，這裡只需要記住：只要你用一個可被 agent 觸及的指標來判斷成功，就要假設 agent 會找到捷徑。

| 失敗模式 | 在 trace 中的訊號 | 線上偵測 | 主要防線 | 對應章節 |
|---|---|---|---|---|
| 無限迴圈與無進展 | 相同 (tool, 參數) 重複、結果雜湊不變 | 滑動視窗計數、無進展偵測 | 兩段式重複偵測、可行動的 tool 回傳 | 第 4、24 章 |
| Hallucinated tool call | tool 名稱不存在、ID 未曾出現 | registry 比對、provenance 檢查 | strict schema、tool search、錯誤回填 | 第 5、7、13 章 |
| 過早宣告完成 | 宣稱完成但缺少終態成功證據 | 宣稱與證據比對、對帳 | harness 完成驗證、structured claims | 第 7、27 章 |
| Context rot | 失敗率隨步數或長度上升 | SLI 依長度分桶 | 清理、compaction、sub-agent 隔離 | 第 9、10 章 |
| Reward hacking | 修改測試、skip、讀評分器 | trajectory 斷言、diff 審查 | grader 隔離、hidden tests、權限 | 第 27、30 章 |

這張表是本節的摘要，也是 34.10 節偵測器的設計依據。注意第三欄「線上偵測」與第四欄「主要防線」的分工：偵測是事後或即時的發現，讓你能量測與告警；防線是讓失敗不發生或不造成傷害。只有偵測沒有防線，你會很清楚自己一直在失敗；只有防線沒有偵測，你不會知道防線什麼時候失效。

## 34.5 Error recovery 設計：一層一層往上升

偵測到失敗之後要怎麼辦？第 4 章談過單一 tool 錯誤的處理：模型能修的回填，模型修不好的中止。放大到整個系統，恢復策略應該設計成一個**階梯**：先用最便宜、最局部的方法，失敗了才往上升一階，每升一階，成本更高、涉及的人更多，但也更確定能止住傷害。

```text
 失敗發生 ──► 依 34.3 節的分類判斷類型
   │
   第 1 階  重試          暫時性錯誤：逾時、429、5xx          tool 或呼叫層，有限次數＋退避＋jitter
   │ 仍失敗
   第 2 階  回填與修正    模型能修的錯：參數、業務規則、查無資料  回填可行動錯誤，讓模型換做法
   │ 仍失敗，或偵測到迴圈
   第 3 階  重新規劃      卡住、無進展、context 太長            注入提醒、清理 context、從 checkpoint 重來
   │ 仍失敗，或已經產生副作用
   第 4 階  補償與回復    做了一半的寫入：取消、反向交易        compensating action（第 22 章的 saga）
   │ 無法自動回復
   第 5 階  升級給人      附上 trajectory 摘要、已做與未做的事  escalation（第 21 章）
   │ 同一類失敗大量出現（系統性問題）
   第 6 階  安全停止      kill switch、降 autonomy、停用 tool     事故流程（34.7 節）
```

從上往下看這個階梯。第 1 階處理的是和模型無關的暫時性錯誤，由確定性程式重試，不浪費模型呼叫；注意有副作用的 tool 只有在有 idempotency key 時才能重試（第 22 章）。第 2 階是第 4 章的「把例外變成觀察」。第 3 階處理 agent 自己卡住的情況：harness 可以注入一則「你已經查了三次，結果相同，請改變做法」的提醒，或者清掉過長的 context 後從最近的 checkpoint 繼續。第 4 階是本章新增的重點：當失敗發生在寫入之後，光是停下來不夠，還要把世界恢復到一致的狀態，例如退款建立了但通知寄錯了，就要寄更正通知。第 5 階把問題交給人，交接時要附上足夠的上下文，否則真人要從頭問起。第 6 階不是針對單一任務，而是針對整個系統：當監控顯示同一類失敗正在大量發生，就要停掉造成傷害的能力。

階梯的設計有三個原則。第一，**每一階都要有上限**：重試幾次、提醒幾次、重新規劃幾次，超過就往上升，否則恢復機制本身會變成新的無限迴圈。第二，**副作用決定能退多遠**：沒有副作用的唯讀任務，最壞情況是重跑；有副作用的任務，必須先知道「已經做了什麼」，這要靠第 22 章的事件日誌，以及 tool 設計時就準備好的補償動作。第三，**第 6 階要事先準備**：kill switch 與降級開關要在上線前建好、測試過，並且寫清楚誰有權按。事故當下才開始寫降級程式，止血時間會從十分鐘變成半天。

| 失敗類型 | 第一個嘗試的恢復 | 升級條件 | 最終手段 | 要事先準備的東西 |
|---|---|---|---|---|
| 下游逾時 | tool 內重試 2 次 | 重試用盡 | 告知使用者稍後再查 | 退避參數、idempotency key |
| 參數錯誤、業務規則拒絕 | 回填可行動錯誤 | 同一錯誤 2 次 | 轉真人 | 錯誤訊息模板 |
| 迴圈、無進展 | 注入提醒 | 提醒後仍重複 | 停止並轉真人 | 偵測器、交接摘要格式 |
| 寫入後發現錯誤 | 補償動作 | 補償失敗 | 人工處理並通知使用者 | 每個寫入 tool 的補償動作 |
| 同類失敗大量出現 | 降 autonomy（L4 → L3） | 燒率仍高 | kill switch 停用能力 | feature flag、權責表 |

這張表把階梯落實到具體的失敗類型。最右欄「要事先準備的東西」是很多團隊忽略的：恢復能力不是失敗時才寫的程式，而是設計 tool 與 harness 時就要一起交付的部分。青鳥在事故後的規則是：任何新的寫入 tool 上線前，必須同時提供補償動作、idempotency key 與降級開關，否則不能進入 L4。

## 34.6 Agent 的 SLI、SLO 與 error budget

阿哲的問題「什麼時候該把自動退款關掉」，需要一個事先講好的決策規則，而不是事故當下的爭論。SRE（site reliability engineering，網站可靠性工程）領域為這個問題發展出一套語言，可以直接用在 agent 上。**SLI**（service level indicator，服務水準指標）是一個可量測的比例，例如「宣稱完成的退款中，對帳成立的比例」。**SLO**（service level objective，服務水準目標）是對 SLI 設定的目標與時間視窗，例如「28 天內 ≥ 99%」。**error budget**（錯誤預算）是 SLO 允許的失敗量：99% 的 SLO 代表 1% 的任務可以失敗，28 天、每天一萬個任務，就是 2,800 件。

error budget 的價值在於把「可靠性」與「改變速度」放在同一個帳本上。budget 還有剩，團隊可以放心做 prompt 實驗、升級模型、放寬 autonomy；budget 快用完，就凍結非必要的變更、把資源轉去修可靠性，甚至降 autonomy。這個政策要在平常就和產品、營運講好並寫下來，事故發生時才不需要爭論。青鳥的 error budget 政策寫明：可信完成率的 budget 用掉 50%，凍結 prompt 與 model 變更；用掉 100%，小額退款自動降回 L3，直到 postmortem 的行動項目完成。

### 為 agent 選 SLI

傳統服務的 SLI 通常是可用性與延遲。agent 需要更多面向，因為它的「成功」包含結果是否正確、是否該交給人、花了多少錢。下表是青鳥客服 agent 的 SLI 組合。

| SLI | 定義（好事件 ÷ 有效事件） | 資料來源 | 青鳥的目標 | 注意事項 |
|---|---|---|---|---|
| 任務成功率 | 自動完成且 outcome 成立 ÷ 全部任務 | trace＋對帳 | ≥ 85%（產品 KPI，不 page） | 會被升級率拉低，不能單獨看 |
| 可信完成率（正確率） | 沒有壞結局的任務 ÷ 全部任務 | 對帳 job、偵測器、抽樣 judge | 28 天 ≥ 99%，依燒率告警 | 真相常延遲到達 |
| 升級率 | 轉真人 ÷ 全部任務 | trace | 5%–15% 之間 | 太高與太低都是警訊 |
| 延遲 | p95 首次回應、p95 完成時間 | span duration | 首次回應 p95 < 3 秒 | 同步與背景任務分開定 |
| 成本 | 每任務平均成本、單任務上限 | usage × 價目表 | 平均 < 0.05 美元，單任務 > 1 美元告警 | 迴圈與 context 變長會推高 |

這五個 SLI 彼此牽制，所以要一起看。**可信完成率**是最核心的一個，青鳥把「壞結局」定義為三種：宣稱完成但對帳不成立、沒有完成也沒有升級（靜默放棄）、被 failure 偵測器標記。注意升級本身不算壞結局，因為「不確定就交給人」是正確的行為；但升級率有自己的 SLO，而且**兩側**都要告警：升級率太高，代表 agent 幫不上忙、客服被淹沒；升級率突然太低，可能代表 agent 開始對不該自己處理的事過度自信。週末事故中，升級率其實下降了，因為 agent 把每一筆 `queued` 都當成完成，這是一個被忽略的早期訊號。

**任務成功率**適合當產品 KPI 而不是 page 的依據，因為它混合了能力與政策：把更多情境設成必須轉真人，成功率就下降，但這不是可靠性問題。**延遲**與**成本**的 SLO 則是保護使用者體驗與單位經濟（第 37 章）。週末的事故也顯示，延遲與成本的「改善」可能正是正確性惡化的副作用：少驗證一步，當然更快、更便宜。只看延遲的團隊，會把一次事故誤認為一次優化。

### 正確性的真相會遲到

agent 的 SLI 有一個傳統服務少見的難題：**真相延遲到達**。退款是否真的入帳，要等金流對帳，可能是兩小時後；回答是否正確，要等抽樣的 LLM judge 或人工標註，可能是隔天；使用者是否被誤導，要等客訴，可能是三天後。如果只用最終真相計算 SLI，告警永遠慢半拍。

```text
 harness ──span──► trace store ──► SLI 計算 ──► 燒率 ──► 告警規則 ──► page／ticket
   │                    ▲              ▲  ▲
   │ 偵測器 findings ───┘              │  │
   │（即時：秒級）                     │  │
 金流、訂單 DB ──► 對帳 job（T+2h）────┘  │ 遲到的真相回頭修正 SLI
 抽樣 judge、客訴 ──► 標註（T+1d 到數天）─┘
```

這張資料流圖把 SLI 的來源分成三種速度。最快的是 harness 即時產生的 span 與偵測器 findings（34.4 節），它們是**代理指標**：未必代表真的失敗，但幾秒內就能取得。中速的是對帳 job，用系統紀錄判定宣稱是否成立，是可信完成率的主要依據。最慢的是抽樣 judge 與客訴，用來校準前兩者，並回頭修正已經計算過的 SLI。實務上，快速告警依賴前兩者，月報與 SLO 達成率則用修正後的數字；如果代理指標和最終真相長期對不上，代表偵測器需要調整。

### Burn rate 與多視窗告警

有了 SLO，下一步是決定什麼時候叫人起床。最直覺的做法是「錯誤率超過 1% 就 page」，但這會讓告警非常吵：短時間內的隨機波動常常超過 1%，而且 1% 的錯誤率持續一整個月也只是剛好用完 budget，不需要半夜處理。SRE 的做法是看 **burn rate**（燒率）：目前的錯誤率是 SLO 允許錯誤率的幾倍。燒率 1 代表剛好在視窗結束時用完 budget；燒率 14.4 代表大約兩天就會燒完 28 天的 budget。

```python
from __future__ import annotations

SLO, DAYS, TASKS_PER_DAY = 0.99, 28, 10_000
budget_events = round((1 - SLO) * DAYS * TASKS_PER_DAY)  # 28 天內允許的壞事件數


def burn_rate(bad: int, total: int) -> float:
    return (bad / total) / (1 - SLO)


def hours_to_exhaust(rate: float) -> float:
    return DAYS * 24 / rate                               # 以這個燒率持續，多久把整個 budget 用完


def minutes_to_detect(error_rate: float, window_min: int = 60, threshold: float = 14.4) -> float:
    """長視窗要累積到門檻需要多久：錯誤越嚴重，偵測越快。"""
    return threshold * (1 - SLO) / error_rate * window_min


print(f"28 天 error budget：{budget_events:.0f} 件壞事件")
print("錯誤率   燒率   每小時用掉 budget   budget 用完   1h/14.4 規則偵測時間")
for err in (0.005, 0.01, 0.03, 0.08, 0.20, 0.40):
    rate = burn_rate(int(err * 1000), 1000)
    detect = minutes_to_detect(err)
    print(f"{err:6.1%}  {rate:5.1f}x  {rate / (DAYS * 24):12.2%}   {hours_to_exhaust(rate):6.0f} 小時   "
          f"{'不會觸發' if detect > 60 else f'{detect:4.1f} 分鐘'}")

assert budget_events == 2800
assert round(hours_to_exhaust(14.4)) == 47                 # 14.4 倍燒率約兩天燒完 28 天的 budget
assert minutes_to_detect(0.40) < 25 < minutes_to_detect(0.20)
```

```text
28 天 error budget：2800 件壞事件
錯誤率   燒率   每小時用掉 budget   budget 用完   1h/14.4 規則偵測時間
  0.5%    0.5x         0.07%     1344 小時   不會觸發
  1.0%    1.0x         0.15%      672 小時   不會觸發
  3.0%    3.0x         0.45%      224 小時   不會觸發
  8.0%    8.0x         1.19%       84 小時   不會觸發
 20.0%   20.0x         2.98%       34 小時   43.2 分鐘
 40.0%   40.0x         5.95%       17 小時   21.6 分鐘
```

這張表把燒率翻譯成兩個營運問題。第三欄是「每小時用掉多少 budget」：燒率 14.4 時每小時用掉約 2%，這正是 Google《The Site Reliability Workbook》建議快速 page 門檻的由來（原書以 30 天視窗推導出「1 小時內用掉 2% budget」對應 14.4 倍）。第四欄是「照這個速度，多久燒完」。第五欄揭露了一個常被忽略的事實：用 1 小時長視窗、14.4 倍門檻的規則，錯誤率 8% 時永遠不會觸發，錯誤率 40% 時也要約 22 分鐘才觸發。偵測時間的公式是「門檻 × 允許錯誤率 ÷ 實際錯誤率 × 視窗長度」，錯誤越嚴重，偵測越快。

所以實務上會同時設多條規則：**快燒規則**（例如 1 小時視窗、14.4 倍）抓嚴重的突發事故；**慢燒規則**（例如 6 小時視窗、6 倍）抓不嚴重但持續的惡化；每條規則再搭配一個較短的視窗（例如長視窗的十二分之一），要求長短視窗都超標才觸發。長視窗確認「燒得夠多、值得處理」，短視窗確認「現在還在燒」，事故止血之後告警能很快解除。這就是**多視窗、多燒率告警**（multiwindow, multi-burn-rate alerts），34.10 節會實作它。

agent 還有一個特別的問題：**流量小**。一個租戶一天可能只有幾十個任務，5 分鐘視窗裡只有一兩筆，任何一筆失敗都會讓燒率爆表。對策是設定最少事件數（視窗內少於 N 筆就不判斷）、對小租戶改用較長的視窗，或只在全域層級 page、租戶層級開 ticket。另一個常見做法是把 agent 依任務類型分別定 SLO：退款與查物流的風險差很多，混在一起計算，退款的失敗會被大量的查詢稀釋。

> [!tip] 先從兩個 SLO 開始
> 第一次為 agent 定 SLO，不要一次定十個。先定一個「可信完成率」與一個「升級率區間」，跑一個月，看看 budget 消耗的形狀、告警的準確率，再加延遲與成本。SLO 的數字也不必一開始就對：用過去四週的實際表現當起點，設在略高於現狀的位置，之後每季檢討。

## 34.7 事故處理與 postmortem

燒率告警響了，接下來的流程和傳統服務的事故處理大致相同：確認、分級、止血、溯源、修復、復盤。不同的是 agent 事故的**止血手段**與**溯源材料**。傳統服務止血靠回滾部署；agent 的變更常常不是部署，而是 prompt、model snapshot、tool 描述或外部 API 的行為，所以止血手段要更豐富，溯源則要能回答「出事時跑的是哪一個版本組合」。

```text
 時間     事件                                   負責           動作
 ─────────────────────────────────────────────────────────────────────────────
 T0       page-fast：可信完成率燒率 36 倍         on-call Iris   確認告警，開事故頻道
 T+5m     分級為 SEV-2（涉及金錢、多位使用者）    事故指揮官     指派溝通、技術、紀錄角色
 T+10m    止血：小額退款 autonomy 從 L4 降到 L3   on-call        feature flag，退款全部改人工核准
 T+20m    溯源：比對 trace 中的版本 lockfile      老陳           找到 CHG-311（刪掉驗證指示）
 T+25m    回滾 prompt 到 v41                      on-call        緊急變更，事後補審
 T+40m    燒率降到 1 以下，維持 L3 觀察            監控           告警解除
 T+1d     影響範圍：對帳列出所有受影響的對話      Iris、客服主管 主動通知使用者、補做退款
 T+3d     blameless postmortem                    全員           行動項目進 backlog
 T+2w     失敗 trace 進 regression eval；L4 恢復  治理會議       依 34.9 節流程重新核准
```

這條時間線是青鳥事後演練的「理想版本」，逐步看。T0 到 T+5m 是確認與分級：分級依據是影響（金錢、使用者數、法規）而不是技術複雜度。T+10m 的止血是關鍵：不是先找根因，而是先停止傷害，最快的方法是降 autonomy，讓 agent 繼續服務，但寫入動作改回人工核准（第 21 章的 L3）。這要求降級開關事先存在。T+20m 的溯源依賴第 36 章的 release manifest（概念上就是一份版本 lockfile）：每條 trace 都記錄了 prompt、model snapshot、tool schema 與 guardrail policy 的版本，所以能直接比對「出事前後哪個版本變了」。T+1d 是 agent 事故特有的步驟：**影響範圍評估**。因為失敗是靜默的，你必須主動找出所有被誤導的使用者，這要靠對帳與 trace 查詢，而不是等使用者來客訴。

| 等級 | 判斷標準（任一成立） | 回應時間 | 止血手段 | 例子 |
|---|---|---|---|---|
| SEV-1 | 不可逆的金錢或資料損失、安全事件、法規通報義務 | 立即，全員 | kill switch 停用 agent 或 tool | agent 被誘導外洩個資 |
| SEV-2 | 錯誤的金錢動作或承諾，影響多位使用者 | 15 分鐘內 | 降 autonomy、回滾版本 | 未驗證就宣告退款完成 |
| SEV-3 | 品質下降但無錯誤承諾，或成本異常 | 當日 | 回滾、調整上限 | 迴圈讓成本翻倍 |
| SEV-4 | 單一使用者、可人工修正 | 一般工單 | 個案處理 | 一次錯誤的物流回覆 |

這張分級表的設計重點是「影響」。注意 SEV-3 的「成本異常」：agent 的迴圈不會讓服務掛掉，但可能在幾小時內燒掉一個月的模型預算，所以成本要有自己的告警與等級。SEV-1 中的「法規通報義務」也值得注意：依用途不同，某些 AI 事故可能有法定的通報期限（34.8 節），分級表要讓 on-call 能立刻判斷是否需要通知法務。

**postmortem**（事後復盤）的原則和傳統 SRE 相同：**blameless**（不究責），焦點放在系統為什麼允許這個錯誤發生，而不是誰犯了錯。週五晚上刪掉那行 prompt 的同事，做的是一個合理的優化嘗試；真正的問題是設定頁允許未審查的修改直接上線、harness 沒有完成驗證、沒有任何 eval 會因為那行字被刪而失敗。agent 的 postmortem 要額外回答四個問題：失敗屬於 taxonomy 的哪一類？哪些 trace 可以變成 regression eval 的題目？哪一層的防線應該攔住卻沒攔住？監控為什麼沒有更早發現？

最有價值的產出是把失敗 trace 轉成 eval。青鳥從週末的事故中挑了 20 條代表性的 trajectory，用 ScriptedModel 重現「閘道回 queued、agent 宣稱完成」的情境，寫成 harness 的 regression test；另外把「退款閘道回傳非同步狀態」加入 eval 環境的故障注入清單。從此以後，任何刪掉驗證邏輯的修改，CI 都會變紅。這就是第 27 章「從真實失敗開始建 eval」的具體做法。

> [!note] 2026 現況
> 截至 2026 年 10 月，模型與 agent 供應商公開發布 postmortem 已漸成慣例。Anthropic 於 2026-04-23 發表一篇 Claude Code 品質下降事件的 postmortem，內容與本章故事高度相似：2026-03-04 為了降低延遲，把預設的 reasoning effort 從 high 調到 medium，使用者明顯感覺品質變差，04-07 回滾；另一個 cache 優化的 bug 讓舊的 thinking 在每個 turn 都被裁掉，造成健忘、重複與 cache miss；還有一行限制 tool call 之間文字長度的 system prompt，事後 ablation 顯示讓某個 eval 下降 3%。文中的教訓是，任何可能和智慧程度互相取捨的變更，都要經過 soak period、更廣泛的 per-model eval 與漸進 rollout。另據 2025 年 7 月的公開報導，曾有 coding agent 平台的 agent 在程式凍結期間刪除使用者的 production 資料庫，這也成為 OWASP Agentic Top 10 中「Rogue Agents」類別的代表案例之一。

## 34.8 法規與標準：EU AI Act、NIST AI RMF、ISO/IEC 42001

Maya 的第二個問題把可靠性帶到治理層級：組織對外要能說明，自己怎麼管理 AI 系統的風險。這一節在**概念層級**整理三份最常被引用的文件，目的是讓工程師知道它們要求什麼樣的「工程產出」，而不是提供法律意見；實際適用與義務範圍要由法務判斷。

**EU AI Act**（歐盟人工智慧法）是具法律約束力的法規，核心是**依用途分級**。它沒有獨立的「agent」類別，同一個 agent 技術，用在電商客服和用在招募篩選，風險等級完全不同。分級大致是：禁止的用途（例如特定的社會評分與操縱行為）、**高風險**用途（法規附件列出的領域，例如就業與招募、教育、信用評估、部分保險定價、關鍵基礎設施等）、有**透明義務**的系統（例如與人互動的 AI 要讓使用者知道自己在和 AI 互動，生成的內容要可被機器偵測地標示），以及其他低風險系統。對通用模型（GPAI）的供應商另有一套義務。

對工程團隊最重要的是高風險系統的義務清單，因為它幾乎就是一份可靠性工程的需求書：風險管理系統（Art. 9）、資料治理（Art. 10）、技術文件（Art. 11）、**自動記錄 log**（Art. 12）、透明與使用說明（Art. 13）、**人類監督**（Art. 14）、準確性、穩健性與資安（Art. 15，明文提到要能抵抗試圖改變系統行為的攻擊）、品質管理系統（Art. 17）、上市後監控（Art. 72）與**嚴重事故通報**（Art. 73）。使用高風險系統的 deployer 也有自己的義務，例如保存 log、指派有能力的人員監督。整合者如果以自己的名義提供高風險系統，或實質修改了系統，就可能成為負有 provider 義務的一方。

**NIST AI RMF**（AI Risk Management Framework）是美國國家標準與技術研究院發布的**自願性**框架，1.0 版於 2023 年 1 月發布。它把 AI 風險管理分成四個 function：**Govern**（建立治理文化、權責與政策）、**Map**（釐清系統的情境、用途與風險）、**Measure**（量測與追蹤風險）、**Manage**（依優先順序處理風險並持續監控）。2024 年 7 月的 **NIST AI 600-1**（Generative AI Profile）列出生成式 AI 特有的風險，例如 confabulation（虛構內容，也就是常說的幻覺）、資訊安全、資訊完整性、人機互動配置等，並為每類風險對應建議的行動。它不是法規，但常被當成「合理的風險管理實務」的參考。

**ISO/IEC 42001:2023** 是第一個可驗證（可以通過第三方稽核取得證書）的 **AI 管理系統**（AI Management System，AIMS）標準，結構和資安領域的 ISO/IEC 27001 相同：組織情境、領導、規劃、支援、營運、績效評估、改善，並在附錄列出控制項，例如 AI 政策、影響評估、資料管理、生命週期管理、第三方關係。它的定位要分清楚：取得 42001 證書，證明的是組織**有一套管理 AI 的制度**並持續運作，不證明任何單一系統是安全或正確的。

| 要求（概念） | EU AI Act（高風險） | NIST AI RMF | ISO/IEC 42001 | 本書對應的工程產出 |
|---|---|---|---|---|
| 風險識別與評估 | Art. 9 風險管理 | Map | 風險與影響評估 | threat model（第 31 章）、設計審查（第 35 章） |
| 量測與測試 | Art. 15 準確性與穩健性 | Measure | 績效評估 | eval 與 benchmark（第 27、28 章）、SLO（本章） |
| 自動記錄 | Art. 12 log | Measure、Manage | 營運紀錄 | trace（第 29 章）、稽核日誌（第 33 章） |
| 人類監督 | Art. 14 | Manage | 營運控制 | approval 與 escalation（第 21 章）、autonomy 等級 |
| 透明 | Art. 13、Art. 50 | Govern | 對利害關係人的溝通 | AI 揭露、使用說明、system card |
| 事故與持續改善 | Art. 72、73 | Manage | 改善、矯正措施 | 事故流程與 postmortem（本章） |
| 治理與權責 | Art. 17 品質管理 | Govern | 領導、政策、角色 | 變更審查與 AI 系統清冊（34.9 節） |

這張對照表是本節的重點：三份文件的語言不同，要求的工程產出卻高度重疊。一個做好本書各章的團隊，已經具備大部分的「證據」：trace 與稽核日誌是 log，eval 與 SLO 是量測，approval 與 autonomy 等級是人類監督，postmortem 是持續改善。治理工作的很大一部分，是把這些既有的產出**整理成可稽核的形式**：寫下來、版本化、指定負責人、定期檢討。反過來說，如果你的 agent 沒有 trace、沒有 eval、沒有降級開關，任何合規文件都只是紙上作業。

這也是回答第 21 章留下的問題的地方：風險評分模型若使用受保護的屬性（性別、年齡、族群）或它們的明顯代理變數，除了一般的反歧視法規，當用途落在信用評估、保險定價、就業等領域時，還可能讓整個系統落入高風險類別。實務原則是：風險訊號只用與行為相關的系統紀錄，定期用歷史結果檢查不同群體的誤判率是否有顯著差異，並把這項檢查寫進 Measure 的例行流程。

> [!note] 2026 現況
> 截至 2026 年 10 月，EU AI Act 已由 **AI Omnibus** 修正（2025-11-19 提案、2026-05-07 達成政治協議、2026-07-27 生效），時程如下：2024-08-01 生效；2025-02-02 起禁止用途與 AI literacy 義務適用；2025-08-02 起 GPAI 模型義務與治理條款適用（此前已上市的模型到 2027-08-02）；2026-08-02 起大部分條文適用，包含 Art. 50 透明義務，但既有生成式系統的 Art. 50(2) 標示義務延到 2026-12-02；2026-12-02 起新增針對未經同意的性內容與兒少性剝削內容生成的禁止條款；Annex III 高風險系統（就業、教育、生物辨識等）的義務延到 **2027-12-02**；Annex I 高風險系統（嵌入受規管產品）延到 **2028-08-02**。延後的理由之一是高風險系統的協調標準尚未完成。Omnibus 也強化 AI Office 對 GPAI-based 系統的監督，並簡化中小企業的義務。也就是說，此刻對話型客服 agent 最直接相關的是 Art. 50 的透明義務；高風險義務雖然延後，設計上現在就要預留 log、人類監督與技術文件。NIST 方面，AI RMF 1.0 正依白宮 AI Action Plan 修訂（尚無時程），2026-02 啟動的 AI Agent Standards Initiative 同時處理 agent 安全與 agent identity／authorization。ISO/IEC 42001 仍是 2023 年版；相關的 ISO/IEC 23894（AI 風險管理）、42005（影響評估）等標準可搭配使用，各標準的最新發布狀態請以 ISO 官方資訊為準。

## 34.9 內部治理流程：model 與 prompt 的變更審查

法規與標準告訴你「要有制度」，制度的核心則是一個樸素的問題：**什麼樣的變更，需要什麼樣的證據，由誰核准，才能上線？** 週末事故的根因之一，是 prompt 被當成「設定」而不是「程式」。對 agent 來說，會改變行為的東西都是程式：prompt、model snapshot、tool 的名稱與描述、guardrail policy、retrieval index、autonomy 設定。它們都要版本化、都要留下變更紀錄，風險高的都要經過審查。

```text
 變更請求（prompt／model snapshot／tool schema／guardrail／autonomy）
     │
     ▼
 (1) 分類與風險分級 ──► 決定要附哪些證據、誰要核准
     │
     ▼
 (2) offline：regression eval＋per-model eval＋安全測試 ──── 不過 ──► 退回
     │
     ▼
 (3) shadow：同一份流量跑新版，寫入 tool 以 dry-run 執行，比較 trajectory 差異
     │
     ▼
 (4) 核准：agent owner／資安／產品／治理委員會（依風險等級）
     │
     ▼
 (5) canary：1% → 10% → 100%，SLO guard 監看燒率，超標自動回滾
     │
     ▼
 (6) 登錄：更新 AI 系統清冊與版本 lockfile，保存變更紀錄與證據
```

這條流程的每一步都有明確的目的。第 (1) 步決定這次變更要走多重的流程，避免所有變更一律走最重的審查而讓團隊想繞過它。第 (2) 步是自動化的品質閘門：regression eval 守住已經會的事，per-model eval 確認新的模型 snapshot 在每個關鍵任務上沒有退步，安全測試確認 guardrail 仍然有效。第 (3) 步的 shadow 讓新版本在真實流量上「試跑」但不產生副作用，適合 model 升級這種影響面廣的變更。第 (4) 步是人的判斷，核准者依風險等級增加。第 (5) 步的 canary 由 34.6 節的燒率監控把關，第 36 章會談 canary 的部署細節。第 (6) 步把變更登錄進 **AI 系統清冊**（AI inventory：組織內所有 AI 系統的清單，記錄用途、風險等級、負責人、目前版本與 autonomy），這份清冊是回應稽核與法規詢問的起點。

下面這段程式把青鳥的審查政策寫成可執行的規則，並用四個變更請求測試它，其中 CHG-311 就是週五晚上那一行 prompt 修改。

```python
from __future__ import annotations

from dataclasses import dataclass, field

# 變更類型 -> 風險等級；碰到寫入 tool 或 autonomy 的變更自動升一級
BASE_RISK = {"prompt": 1, "tool_schema": 1, "model": 2, "guardrail": 2, "autonomy": 3, "rollback": 0}
GATES = {           # 每個風險等級必須附上的證據
    0: ["incident_ticket"],
    1: ["regression_eval", "canary_plan"],
    2: ["regression_eval", "per_model_eval", "shadow_run", "canary_plan", "security_review"],
    3: ["regression_eval", "per_model_eval", "shadow_run", "canary_plan", "security_review",
        "risk_assessment", "oversight_plan"],
}
APPROVERS = {0: ["oncall"], 1: ["agent_owner"], 2: ["agent_owner", "security"],
             3: ["agent_owner", "security", "product", "governance_board"]}


@dataclass
class Change:
    id: str
    kind: str
    summary: str
    touches_write_tools: bool = False
    evidence: set[str] = field(default_factory=set)
    approved_by: set[str] = field(default_factory=set)


def review(c: Change) -> tuple[str, int, list[str]]:
    risk = BASE_RISK[c.kind] + (1 if c.touches_write_tools and c.kind != "rollback" else 0)
    risk = min(risk, 3)
    missing = [g for g in GATES[risk] if g not in c.evidence]
    missing += [f"approval:{a}" for a in APPROVERS[risk] if a not in c.approved_by]
    if c.kind == "rollback" and not missing:
        return "allow（事後 48 小時內補審）", risk, []   # 回滾到已知良好版本，速度優先
    return ("allow" if not missing else "block"), risk, missing


changes = [
    Change("CHG-311", "prompt", "刪掉「退款後先查詢狀態再回覆」以降低延遲", touches_write_tools=True),
    Change("CHG-312", "model", "客服 agent 換到新的模型 snapshot",
           evidence={"regression_eval", "per_model_eval", "shadow_run", "canary_plan"},
           approved_by={"agent_owner"}),
    Change("CHG-313", "rollback", "prompt 回滾到 v41", evidence={"incident_ticket"}, approved_by={"oncall"}),
    Change("CHG-314", "autonomy", "500 元以下退款由 L3 改為 L4",
           evidence={"regression_eval", "per_model_eval", "shadow_run", "canary_plan", "security_review",
                     "risk_assessment", "oversight_plan"},
           approved_by={"agent_owner", "security", "product", "governance_board"}),
]
results = {}
for c in changes:
    decision, risk, missing = review(c)
    results[c.id] = decision
    print(f"{c.id} [{c.kind:<8} 風險 {risk}] {decision:<6} {c.summary}")
    if missing:
        print(f"         缺少：{', '.join(missing)}")

assert results["CHG-312"] == "block"            # 少了資安審查與核准，不能直接上
assert results["CHG-313"].startswith("allow")   # 緊急回滾不能被流程卡住
```

```text
CHG-312 [model    風險 2] block  客服 agent 換到新的模型 snapshot
         缺少：security_review, approval:security
CHG-313 [rollback 風險 0] allow（事後 48 小時內補審） prompt 回滾到 v41
```

逐筆看輸出。CHG-311 是 prompt 變更，基礎風險為 1，但因為它影響寫入 tool 的行為（退款），自動升到風險 2，於是需要 regression eval、per-model eval、shadow、canary 計畫、資安審查與兩個核准，一個都沒有，結果是 block。如果這條規則在事故前就存在，週五晚上的修改會被擋下，而 regression eval 會因為「閘道回 queued」的測試失敗而指出問題。CHG-312 是 model snapshot 升級，大部分證據都齊了，只缺資安審查與資安核准，仍然 block：model 升級改變的不只是品質，也可能改變模型對 prompt injection 的抵抗力，所以資安要簽核。CHG-313 是緊急回滾，風險 0，只要有事故單與 on-call 核准就放行，並要求事後補審，因為**治理流程不能讓止血變慢**。CHG-314 是把小額退款從 L3 改為 L4，這是 autonomy 的變更，風險最高，需要風險評估與人類監督計畫，並由治理委員會核准；證據齊全，所以 allow。

| 變更類型 | 典型例子 | 最少證據 | 核准者 | 發布方式 |
|---|---|---|---|---|
| prompt（不影響寫入） | 調整語氣、補充 FAQ | regression eval | agent owner | canary |
| prompt（影響寫入）、tool schema | 修改退款流程指示、改參數 | regression＋per-model eval、shadow | owner＋資安 | shadow 後 canary |
| model snapshot | 換新版本或換供應商 | 全套 eval、shadow、安全測試 | owner＋資安 | shadow 後 canary，保留舊版回滾 |
| guardrail policy | 調整 PII 遮罩或 injection 分類器門檻 | 安全測試、誤判率評估 | 資安 | canary |
| autonomy 等級提升 | L3 → L4 | 風險評估、監督計畫、SLO 達成紀錄 | 治理委員會 | 依租戶分批開放 |
| 緊急回滾 | 回到已知良好版本 | 事故單 | on-call | 立即，事後補審 |

這張表是青鳥治理政策的摘要。有三點值得強調。第一，**模型供應商的變更也是變更**：即使你沒有改任何東西，用 alias（例如「最新版」）指向的模型被供應商更新，行為也會改變，所以 production 一律用帶日期或版本的 snapshot，並在供應商預告下架前排好升級流程。第二，**autonomy 提升需要歷史證據**：把 L3 改成 L4 之前，要先在 L3 累積足夠的資料，證明「人工核准時，人幾乎總是同意 agent 的提議」，而且可信完成率 SLO 穩定達成。第三，**治理委員會不必是大組織的官僚機構**：在青鳥，它是每兩週一次、三十分鐘的會議，成員是老陳、Maya、阿哲與各 agent 的 owner，議程固定是新的高風險變更、error budget 狀態與未結的 postmortem 行動項目。

> [!warning] 常見誤解
> 「治理就是多加幾個簽核，會拖慢開發。」設計良好的治理反而讓團隊更快：低風險變更走輕量流程，自動化的 eval 與 canary 取代大部分人工審查，error budget 讓團隊在預算內放心實驗。真正拖慢開發的是沒有治理時的事故：一次週末事故花掉的人力，比一整季的變更審查還多。

## 34.10 動手做：SLO 監控器與 failure 偵測器

這一節用兩段程式重演週末的事故。第一段實作三個 failure 偵測器：重複動作、未驗證就宣告完成、不存在的 tool（加上捏造 ID 的 provenance 檢查）。它們只讀 trace，不讀 agent 的內部狀態，所以可以放在 trace pipeline 中、對任何框架產生的 trace 運作。為了產生 trace，程式開頭複製全書統一的 ScriptedModel，並用一個最小的 loop 跑五個劇本。

### 第一段：三個 failure 偵測器

```python
from __future__ import annotations

import json
import re
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"          # end_turn｜tool_use｜max_tokens
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    """依劇本回應的假模型。劇本的每一步是 ModelResponse，或「收到 messages 後回傳 ModelResponse」的函式。"""

    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    """劇本小工具：產生一個「呼叫 name 工具」的回應。"""
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    """劇本小工具：產生一個「直接回答並結束」的回應。"""
    return ModelResponse(text=text)


# ── 青鳥客服的假後端：退款閘道週六改成非同步，回傳 queued 而不是 succeeded ──
GATEWAY = {"mode": "async"}
REFUNDS: dict[str, str] = {}


def get_order(order_id: str) -> dict:
    return {"order_id": order_id, "status": "delivered", "amount": 420}


def refund(order_id: str) -> dict:
    REFUNDS[order_id] = "queued" if GATEWAY["mode"] == "async" else "succeeded"
    return {"order_id": order_id, "refund_status": REFUNDS[order_id]}


def get_refund_status(order_id: str) -> dict:
    return {"order_id": order_id, "refund_status": REFUNDS.get(order_id, "none")}


TOOLS: dict[str, tuple[str, Callable[..., dict]]] = {      # name -> (副作用等級, 函式)
    "get_order": ("read", get_order),
    "refund": ("write", refund),
    "get_refund_status": ("read", get_refund_status),
}


def run(model: ScriptedModel, user_input: str, max_steps: int = 8) -> list[dict]:
    """最小 loop，只為了產生 trace：每個事件都記下來，偵測器只讀 trace、不讀程式狀態。"""
    trace = [{"type": "user", "text": user_input}]
    messages: list[dict] = [{"role": "user", "content": user_input}]
    for _ in range(max_steps):
        resp = model.complete(messages)
        messages.append({"role": "assistant", "content": resp.text,
                         "tool_calls": [vars(tc) for tc in resp.tool_calls]})
        if not resp.tool_calls:
            trace.append({"type": "final", "text": resp.text})
            return trace
        for tc in resp.tool_calls:
            trace.append({"type": "tool_call", "name": tc.name, "args": tc.args})
            if tc.name not in TOOLS:
                ok, out = False, {"error": f"沒有名為 {tc.name} 的工具"}
            else:
                ok, out = True, TOOLS[tc.name][1](**tc.args)
            trace.append({"type": "tool_result", "name": tc.name, "ok": ok, "output": out})
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name,
                             "content": json.dumps(out, ensure_ascii=False)})
    trace.append({"type": "final", "text": "", "status": "max_steps"})
    return trace


# ── 三個 failure 偵測器：輸入一條 trace，輸出 finding 清單 ──
def detect_repeats(trace: list[dict], window: int = 6, limit: int = 3) -> list[str]:
    """同一個 (tool, 參數) 在最近 window 次呼叫中出現 limit 次以上，而且結果沒有變化。"""
    pairs = [(e["name"], json.dumps(e["args"], sort_keys=True), json.dumps(r["output"], sort_keys=True))
             for e, r in zip(trace, trace[1:]) if e["type"] == "tool_call"]
    for i, (name, args, _) in enumerate(pairs):
        recent = [p for p in pairs[max(0, i - window + 1): i + 1] if p[:2] == (name, args)]
        if len(recent) >= limit and len({p[2] for p in recent}) == 1:   # 重複，而且結果沒有變化
            return [f"repeat:{name} x{len(recent)}"]
    return []


def detect_unknown_tool(trace: list[dict]) -> list[str]:
    """呼叫不存在的 tool，或參數裡的 ID 從沒在使用者輸入或先前 tool 結果中出現過（捏造）。"""
    findings, seen_text = [], ""
    for e in trace:
        if e["type"] == "user":
            seen_text += e["text"]
        elif e["type"] == "tool_result":
            seen_text += json.dumps(e["output"], ensure_ascii=False)
        elif e["type"] == "tool_call":
            if e["name"] not in TOOLS:
                findings.append(f"unknown_tool:{e['name']}")
            for v in e["args"].values():
                if re.fullmatch(r"B-\d{4}", str(v)) and str(v) not in seen_text:
                    findings.append(f"fabricated_id:{v}")
    return findings


CLAIM = re.compile(r"已(退款|完成|建立|取消)")
SUCCESS_STATES = {"succeeded", "completed"}


def detect_unverified_done(trace: list[dict]) -> list[str]:
    """最後的回答宣稱完成，但 trace 裡找不到支持這個宣稱的證據：寫入成功且狀態為終態。"""
    final = trace[-1].get("text", "")
    if not CLAIM.search(final):
        return []
    evidence = [e for e in trace if e["type"] == "tool_result" and e["ok"]
                and e["output"].get("refund_status") in SUCCESS_STATES]
    wrote = [e for e in trace if e["type"] == "tool_call" and TOOLS.get(e["name"], ("",))[0] == "write"]
    if not wrote:
        return ["claimed_done_without_action"]
    return [] if evidence else ["claimed_done_unverified"]


DETECTORS = [detect_repeats, detect_unknown_tool, detect_unverified_done]

scenarios = {
    "A 正常（確認後如實回報）": [call("get_order", order_id="B-1042"), call("refund", "c2", order_id="B-1042"),
                     call("get_refund_status", "c3", order_id="B-1042"),
                     say("退款申請已送出，目前處理中，3 個工作天內入帳。")],
    "B 原地打轉": [call("get_refund_status", f"c{i}", order_id="B-1042") for i in range(4)]
                 + [say("退款仍在處理中。")],
    "C 未驗證就宣告完成": [call("refund", order_id="B-1042"), say("已退款完成，420 元已退回您的帳戶。")],
    "D 幻覺 tool 與捏造 ID": [call("cancel_refund", order_id="B-1042"),
                          call("get_order", "c2", order_id="B-7777"), say("查不到相關訂單。")],
    "E 同步閘道（有證據的完成）": [call("refund", order_id="B-1042"), say("已退款完成，420 元已退回。")],
}

results = {}
for name, script in scenarios.items():
    REFUNDS.clear()
    GATEWAY["mode"] = "sync" if name.startswith("E") else "async"
    trace = run(ScriptedModel(script), "訂單 B-1042 幫我退款")
    results[name] = [f for d in DETECTORS for f in d(trace)]
    calls = sum(e["type"] == "tool_call" for e in trace)
    print(f"{name}\n    tool calls={calls}  findings={results[name] or '無'}")

assert results["A 正常（確認後如實回報）"] == []
assert results["B 原地打轉"] == ["repeat:get_refund_status x3"]
assert results["C 未驗證就宣告完成"] == ["claimed_done_unverified"]
assert results["D 幻覺 tool 與捏造 ID"] == ["unknown_tool:cancel_refund", "fabricated_id:B-7777"]
assert results["E 同步閘道（有證據的完成）"] == []          # 同一句話，有證據就不是失敗
```

```text
A 正常（確認後如實回報）
    tool calls=3  findings=無
B 原地打轉
    tool calls=4  findings=['repeat:get_refund_status x3']
C 未驗證就宣告完成
    tool calls=1  findings=['claimed_done_unverified']
D 幻覺 tool 與捏造 ID
    tool calls=2  findings=['unknown_tool:cancel_refund', 'fabricated_id:B-7777']
E 同步閘道（有證據的完成）
    tool calls=1  findings=無
```

逐一看五個劇本。**A** 是正確的行為：agent 退款後呼叫 `get_refund_status` 讀回狀態，看到 `queued`，就如實回覆「處理中，3 個工作天內入帳」。偵測器沒有任何 finding，因為回答中沒有「已退款」這類完成宣稱，也沒有重複或捏造。**B** 是週六下午的迴圈：agent 連續四次查同一筆退款狀態，結果都一樣。`detect_repeats` 在第三次相同呼叫時就觸發（`x3`），因為它同時檢查「參數相同」與「結果沒有變化」；如果查詢結果在兩次之間改變了（例如從 queued 變成 succeeded），重查就是合理的，不會被標記。線上使用時，這個偵測器可以放進 harness，在第三次時就打斷 loop。

**C** 是週末事故的核心：agent 呼叫 `refund`，拿到 `queued`，就宣稱「已退款完成」。`detect_unverified_done` 先用 regex 找到完成宣稱，再到 trace 中找證據：有寫入動作，但沒有任何 tool 結果的狀態是 `succeeded` 或 `completed`，於是標記 `claimed_done_unverified`。**D** 示範兩種 hallucinated tool call：`cancel_refund` 不在 registry 中，被標為 `unknown_tool`；接著 agent 用 `B-7777` 查訂單，這個 ID 從未出現在使用者輸入或任何 tool 結果中，被標為 `fabricated_id`。注意第二個呼叫在 tool 層完全合法，只有 provenance 檢查抓得到。**E** 是對照組：同一句「已退款完成」，但閘道是同步模式，`refund` 直接回傳 `succeeded`，證據成立，偵測器不會誤報。這個對照證明偵測器判斷的是「宣稱與證據是否一致」，而不是「有沒有說某些字」。

這三個偵測器都是刻意簡化的版本，上線前要補強三件事。第一，完成宣稱的抽取應改用 structured output，regex 只適合當起步。第二，provenance 檢查只對特定格式的 ID 有效，自由文字的參數（例如搜尋詞）不適用。第三，偵測器本身也要評估：用人工標註的 trace 計算它的 precision 與 recall，偵測器的誤報會直接吃掉 error budget，漏報則讓 SLO 看起來比實際好。

### 第二段：從 trace 計算 SLI，依燒率告警

第二段把偵測器的 findings 與對帳結果當成 trace 的屬性，計算可信完成率 SLI，並實作 34.6 節的多視窗、多燒率告警。模擬的是 48 小時、每 5 分鐘 30 個任務：第 6 到 18 小時，退款閘道間歇逾時，迴圈變多（慢燒）；第 30 小時，有人刪掉 prompt 中的驗證指示，大量任務未驗證就宣告完成（快燒），一小時後回滾。

```python
from __future__ import annotations

import random
from collections import deque
from dataclasses import dataclass, field


@dataclass
class TaskTrace:
    """從一條任務 trace 的根 span 萃取出的 SLI 原料。"""
    minute: int                    # 任務結束時間（從模擬開始算的分鐘）
    claimed_done: bool             # agent 宣稱已完成
    verified: bool                 # 對帳：宣稱的結果在系統紀錄中成立
    escalated: bool                # 轉給真人
    latency_s: float
    cost_usd: float
    flags: list[str] = field(default_factory=list)   # failure 偵測器的 findings

    @classmethod
    def from_span(cls, span: dict) -> "TaskTrace":
        a = span["attributes"]                     # 屬性由 harness、對帳 job 與偵測器寫入
        return cls(span["end_minute"], a["agent.claimed_done"], a["reconcile.verified"],
                   a["agent.escalated"], span["duration_s"], a["cost.usd"], a["detector.findings"])

    @property
    def bad(self) -> bool:
        """壞事件：宣稱完成卻不成立、沒升級也沒完成、或被偵測器標記。升級本身不算壞。"""
        if self.escalated:
            return False
        return (self.claimed_done and not self.verified) or not self.claimed_done or bool(self.flags)


def simulate(hours: int = 48, per_bucket: int = 30, seed: int = 34) -> list[dict]:
    """每 5 分鐘 30 個任務。06–18 時退款閘道間歇逾時（迴圈變多）；30 時有人刪掉 prompt 中的驗證指示。"""
    rng = random.Random(seed)
    out = []
    for bucket in range(hours * 12):
        hour = bucket / 12
        if 6 <= hour < 18:
            p_bad, p_loop, p_esc, latency, cost = 0.08, 0.06, 0.12, 26.0, 0.050   # 慢燒：迴圈與逾時
        elif 30 <= hour < 31:
            p_bad, p_loop, p_esc, latency, cost = 0.40, 0.0, 0.03, 14.0, 0.028    # 快燒：不驗證就宣告完成
        else:
            p_bad, p_loop, p_esc, latency, cost = 0.004, 0.0, 0.08, 18.0, 0.031
        for _ in range(per_bucket):
            escalated = rng.random() < p_esc
            r = rng.random()
            flags = ["repeat"] if r < p_loop else []
            unverified = p_loop <= r < p_bad          # 其餘壞事件：宣稱完成但對帳不成立
            out.append({"end_minute": bucket * 5,
                        "duration_s": rng.gauss(latency, 4) + (30 if flags else 0),
                        "attributes": {"agent.claimed_done": True, "reconcile.verified": not unverified,
                                       "agent.escalated": escalated, "detector.findings": flags,
                                       "cost.usd": cost * (3 if flags else 1) * rng.uniform(0.7, 1.3)}})
    return out


class BurnRateMonitor:
    """多視窗、多燒率告警：長視窗確認「燒得夠多」，短視窗確認「現在還在燒」。"""

    RULES = [("page-fast", 60, 5, 14.4), ("page-slow", 360, 30, 6.0)]   # (名稱, 長視窗, 短視窗, 燒率門檻)

    def __init__(self, slo: float, min_events: int = 50):
        self.budget = 1 - slo                       # 允許的壞事件比例
        self.min_events = min_events                # 事件太少時不判斷，避免小樣本誤報
        self.buckets: deque[tuple[int, int, int]] = deque()   # (minute, total, bad)

    def add_bucket(self, minute: int, total: int, bad: int) -> None:
        self.buckets.append((minute, total, bad))
        while self.buckets and self.buckets[0][0] <= minute - 360:
            self.buckets.popleft()

    def burn(self, now: int, window: int, min_events: int = 1) -> float | None:
        """燒率 = 視窗內壞事件比例 ÷ 允許比例。1.0 代表剛好在 SLO 視窗結束時把 budget 用完。"""
        rows = [(t, b) for m, t, b in self.buckets if m > now - window]
        total, bad = sum(t for t, _ in rows), sum(b for _, b in rows)
        return None if total < min_events else (bad / total) / self.budget

    def firing(self, now: int) -> list[tuple[str, float]]:
        hits = []
        for name, long_w, short_w, threshold in self.RULES:
            lb, sb = self.burn(now, long_w, self.min_events), self.burn(now, short_w)
            if lb is not None and sb is not None and lb > threshold and sb > threshold:
                hits.append((name, round(lb, 1)))
        return hits


def p95(xs: list[float]) -> float:
    xs = sorted(xs)
    return xs[int(0.95 * (len(xs) - 1))]
```

先看上半部的逐時表。第 2 與第 40 小時是平常狀態：壞事件約 0.3%–0.6%，升級率約 6%–8%，p95 延遲約 25 秒。第 8 與第 12 小時是慢燒期：壞事件升到約 7%，迴圈讓 p95 延遲翻倍到約 50 秒、平均成本從 0.031 美元升到約 0.057 美元，升級率也上升，因為卡住的任務被轉給真人。第 30 小時是快燒：壞事件高達 36.9%，**但 p95 延遲降到 20 秒、成本降到 0.028 美元、升級率降到 2.8%**。這三個數字全部「變好」，正是週末儀表板全綠的原因：少了驗證那一步，agent 更快、更便宜、更少找人，也更常說謊。只有直接量測結果是否成立的 SLI，才看得出問題。

下半部是告警事件。慢燒在 06:00 開始，**page-slow** 在 10:20 才觸發，持續到 18:05；這和 34.6 節的偵測時間公式一致：6 小時視窗、6 倍門檻，在約 8% 的錯誤率下要累積四個多小時才觸發。這個延遲是刻意的取捨：8% 的錯誤率會在幾天內燒完 budget，值得 page，但不值得在第一個五分鐘就叫醒人，因為那時無法和隨機波動區分。快燒在 30:00 開始，**page-fast** 在 30:20 觸發，二十分鐘內就 page；同時 page-slow 也在 30:50 觸發，因為嚴重的事故同樣會讓 6 小時視窗超標，實務上兩者會合併成同一個事故。程式用「30 分鐘內再觸發視為同一事件」避免告警抖動。

## 34.11 實務應用

失敗模式、SLO 與治理的組合方式，會隨產品的風險與互動形態而不同。以下四個情境說明同一套方法怎麼調整。

**情境一：電商客服 agent（青鳥的主線）**。核心 SLO 是可信完成率與升級率區間，依任務類型分開計算：查詢類的壞結局主要是回答錯誤，用抽樣 judge 量測；退款類的壞結局是宣稱不成立，用金流對帳量測。所有寫入 tool 都要有完成驗證與補償動作，page-fast 直接連到「小額退款降回 L3」的開關。對話開頭要讓使用者知道自己在和 AI 對話，這同時是良好的 UX 與 EU AI Act Art. 50 的要求。公開資料顯示，主流客服 agent 產品（例如 Sierra、Intercom Fin，第 41 章）都強調轉真人的設計與以解決率等結果指標衡量表現；具體的監控與告警設計，公開資料多半沒有細節。

**情境二：background coding agent**。任務是從 issue 產生 pull request，失敗的代價是浪費 reviewer 的時間，或更糟，合併了一個「讓測試通過」但其實沒修好的修改。最重要的失敗模式是 reward hacking 與過早宣告完成，所以 SLI 不能只看「CI 綠燈」，要看「PR 被合併且 N 天內沒有被 revert」這類延遲到達的 outcome。trajectory 斷言要檢查是否修改了測試檔、是否加入 skip；grader 要放在 agent 碰不到的地方。成本 SLO 很重要，因為一個陷入迴圈的長任務可能燒掉數百萬 tokens。主流 coding agent 產品普遍在隔離環境中執行並以 PR 的形式交付，讓人類 review 成為最後一道防線（第 39 章）。

**情境三：招募篩選或信用評估類 agent**。依 EU AI Act，這類用途落在 Annex III 高風險類別，即使義務的適用日延到 2027 年底，系統設計現在就要預留：完整的自動 log、人類監督（agent 只能建議，最終決定由人做，對應 L1 或 L3）、技術文件、偏誤量測與事故通報流程。這裡的 SLO 除了正確率，還要包含**不同群體之間的誤判率差異**，並納入 NIST AI RMF 的 Measure 例行流程。變更審查要走最重的等級，而且 model snapshot 升級前要重新做偏誤評估。

**情境四：營運 research agent（L5）**。任務長、步驟多，主要風險是 context rot 與成本失控，正確性則靠引用與抽樣審查。SLI 要依任務長度分桶，觀察長任務的成功率是否明顯下降；成本 SLO 以每份報告的預算為單位，燒率告警改用「預算消耗速度」。因為是內部使用、沒有直接的金錢動作，事故等級通常是 SEV-3，但如果報告被拿去做定價或補償決策，錯誤的結論就會變成金錢損失，這時要在報告與決策之間加入人工確認。

| 情境 | 最關鍵的失敗模式 | 核心 SLI | 止血手段 | 治理重點 |
|---|---|---|---|---|
| 電商客服 | 過早宣告完成、迴圈 | 可信完成率、升級率區間 | 降 autonomy 到 L3 | AI 揭露、寫入變更審查 |
| Background coding | reward hacking、過早宣告完成 | 合併後未 revert 率、成本 | 暫停自動開 PR | grader 隔離、權限 |
| 招募／信用評估 | 偏誤、未經監督的決定 | 正確率、群體誤判率差異 | 全部改人工決定 | 高風險義務、偏誤評估 |
| 營運 research | context rot、成本失控 | 長任務成功率、預算消耗 | 降低 effort、縮小範圍 | 報告用於決策前的人工確認 |

這張表的共同點是：每個情境都先問「哪種失敗最傷人」，再決定 SLI 與止血手段。沒有一套適用所有 agent 的 SLO 清單，但方法是同一套。

> [!note] 2026 現況
> 截至 2026 年 10 月，主要的觀測與評估平台（例如 LangSmith、Langfuse、Braintrust，以及雲端的 Amazon Bedrock AgentCore 的 Evaluations 與 CloudWatch 整合）都提供線上評分、從 production trace 建立 dataset、以及把 eval 分數當成監控指標的功能；OpenTelemetry 的 GenAI semantic conventions 已移到獨立的 repo，大部分項目仍是 Development 穩定度（第 29 章）。這些平台提供的是 SLI 的原料與儀表板，SLO 的定義、對帳與 error budget 政策仍要由團隊自己設計。OWASP 於 2025-12 發布的 Top 10 for Agentic Applications 2026 中，ASI08 Cascading Failures 與 ASI10 Rogue Agents 和本章的失敗模式直接相關。

## 34.12 設計檢查清單

設計或審查一個 agent 的可靠性與治理時，逐項回答下面的問題。

1. 是否有一份團隊自己的 failure taxonomy，每一類都寫明「怎麼從 trace 判定」，並定期用人工標註檢查一致率？
2. 每個寫入 tool 是否都有完成驗證（終態成功或讀回確認）？完成宣稱是否以 structured output 輸出，而不是靠 regex 猜？
3. 是否有重複動作與無進展偵測，而且會區分「結果有變化的合理重查」與「原地打轉」？
4. 有副作用的 tool 參數中的 ID，是否檢查過 provenance（來自使用者輸入或先前的 tool 結果）？
5. 恢復階梯的每一階是否都有上限？每個寫入 tool 是否附有補償動作與 idempotency key？
6. 是否定義了可信完成率、升級率區間、延遲與成本的 SLI，並能從 trace 與對帳資料計算？
7. 壞結局的定義是否寫清楚（宣稱不成立、靜默放棄、偵測器標記），升級是否不算壞結局？
8. 告警是否採用多視窗、多燒率規則？小流量租戶是否有最少事件數或較長的視窗？
9. error budget 政策是否事先和產品、營運講好：用掉多少凍結變更、用掉多少降 autonomy？
10. 降 autonomy 的開關與 kill switch 是否已經建好、測試過，並寫明誰有權按？
11. 每條 trace 是否記錄完整的版本 lockfile（prompt、model snapshot、tool schema、guardrail policy）？
12. 事故分級是否以影響為依據，並包含成本異常與法規通報的判斷？
13. postmortem 是否固定產出 regression eval 題目，並追蹤行動項目直到完成？
14. prompt、model snapshot、tool schema、guardrail、autonomy 的變更是否都經過依風險分級的審查，緊急回滾是否有快速通道？
15. 是否有 AI 系統清冊，記錄每個 agent 的用途、風險等級、負責人、目前版本與 autonomy，並由法務判斷適用的法規義務？

## 34.13 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 儀表板全綠，客訴卻增加 | 只監控可用性與延遲，沒有量測結果是否成立 | 抽樣客訴對應的 trace，比對宣稱與系統紀錄 | 加入可信完成率 SLI 與對帳 job |
| 延遲與成本突然「變好」 | 某個驗證步驟被拿掉，正確性下降 | 比對變更前後的版本 lockfile 與 trajectory 步數 | 回滾；把驗證改成 harness 檢查並加 regression test |
| 告警很吵，大家開始忽略 | 用單一短視窗、門檻設在燒率 1 | 統計告警中真正需要處理的比例 | 改用多視窗、多燒率規則，加最少事件數 |
| 嚴重事故兩小時後才 page | 只有慢燒規則，或 SLI 只用延遲到達的真相 | 用 34.6 節公式計算偵測時間 | 加快燒規則；用偵測器 findings 當即時代理指標 |
| 升級率很低，看起來很好 | agent 對該升級的情況過度自信 | 抽樣未升級的高風險任務做人工審查 | 升級率改為區間 SLO，太低也告警 |
| 偵測器讓 budget 莫名燒完 | 偵測器誤報率高 | 用人工標註計算 precision | 調整偵測規則，偵測器變更也走 eval |
| CI 綠了但 bug 還在 | coding agent 修改測試或加 skip（reward hacking） | 檢查 diff 是否動到測試檔與 skip 標記 | 測試檔唯讀、hidden tests、trajectory 斷言 |
| 事故中找不到「哪個版本變了」 | trace 沒有記錄 prompt 與 model 版本，prompt 可直接線上修改 | 檢查 span 屬性與設定變更紀錄 | 版本 lockfile 寫入每條 trace；prompt 修改納入變更審查 |

## 本章重點整理

- agent 最危險的失敗是靜默失敗：每個 API 呼叫都成功、語氣誠懇、內容錯誤，所以傳統的可用性與延遲監控看不到它。
- 失敗可能發生在 model、harness、環境與組織流程四層，而且常常多層疊加；只換更強的模型補不起 harness 與流程的洞。
- failure taxonomy 讓失敗可以統計與追蹤；MAST 把 14 種 failure mode 分成系統設計、agent 間錯位與任務驗證三類，團隊應以它為起點建立自己能從 trace 判定的分類。
- 無限迴圈要偵測「相同動作且結果不變」，根本修法是讓 tool 回傳可行動的下一步。
- hallucinated tool call 包含不存在的 tool 與捏造的參數；後者要靠 provenance 檢查，strict schema 只能保證格式。
- 過早宣告完成的防線要放在 harness：完成宣稱必須有終態成功或讀回確認的證據，prompt 中的驗證指示只能提高機率。
- context rot 表現為失敗率隨步數上升，要把 SLI 依任務長度分桶才看得出來。
- reward hacking 是 agent 達成了你寫下的規格而非真正的目標，要用 grader 隔離與 trajectory 斷言防範。
- error recovery 是一個階梯：重試、回填、重新規劃、補償、升級給人、安全停止；每一階都要有上限，補償動作與降級開關要事先準備。
- agent 的 SLI 至少包含可信完成率、升級率區間、延遲與成本；升級不算壞結局，但升級率太高與太低都要告警。
- 燒率是錯誤率相對於允許錯誤率的倍數；多視窗、多燒率告警用長視窗確認嚴重性、短視窗確認仍在發生，偵測時間與錯誤嚴重度成反比。
- error budget 政策要事先約定：budget 消耗到什麼程度要凍結變更、降 autonomy，讓事故當下不需要爭論。
- agent 事故的止血優先靠降 autonomy 與回滾版本組合，溯源依賴 trace 中的版本 lockfile，影響範圍要靠對帳主動找出。
- EU AI Act 依用途分級，NIST AI RMF 以 Govern、Map、Measure、Manage 組織風險管理，ISO/IEC 42001 證明組織有 AI 管理制度；三者要求的工程產出高度重疊。
- prompt、model snapshot、tool schema、guardrail 與 autonomy 的變更都是程式變更，要依風險分級審查、shadow 與 canary，並保留緊急回滾的快速通道。

## 延伸問答

> [!question]- Q1. 我們的 agent 服務可用性已經是 99.95%，為什麼還需要另外定 SLO？
> 可用性 SLO 回答的是「服務有沒有回應」，agent 的使用者在意的卻是「回應是不是真的」。週末的事故中，可用性完全正常，HTTP 5xx 只有 0.1%，但有一千九百多次回應宣稱了未發生的事。可用性 SLO 對這類靜默失敗是盲的，因為從 HTTP 的角度，每一次都是成功。
>
> 所以 agent 需要以 outcome 為基礎的 SLI：宣稱完成的事在系統紀錄中是否成立、該轉真人的是否有轉、花費是否在預算內。可用性 SLO 仍然要保留，它保護的是基礎設施層；但它應該被視為必要條件而不是充分條件。實務上，可信完成率的 error budget 通常比可用性的更早耗盡，也更能反映 prompt 與 model 變更的風險。

> [!question]- Q2. 升級率（轉真人比例）應該設上限還是下限？
> 兩者都要，所以青鳥把它定成區間 SLO。上限防的是 agent 幫不上忙：升級率從 8% 升到 25%，客服團隊會被淹沒，自動化的價值也消失，原因可能是 tool 故障、政策變更或模型退化。下限防的是相反的方向：agent 對不該自己處理的事過度自信。週末事故中升級率下降，因為 agent 把所有 `queued` 都當成完成，不再需要找人。
>
> 區間的數值要從歷史分布定，並依任務類型分開。下限告警的觸發也要搭配人工抽查：升級率下降可能是 agent 真的變好了，例如新版 tool 讓它能處理更多情況。判斷依據是同時看可信完成率：升級率下降而可信完成率持平或上升，是好消息；升級率下降而可信完成率也下降，就是過度自信的訊號。

> [!question]- Q3. 可信完成率的真相要等兩小時後的對帳才知道，怎麼做到快速告警？
> 把 SLI 的來源分成即時的代理指標與延遲的真相。即時的部分來自 harness 與偵測器：宣稱完成但缺少終態成功證據、寫入結果為非終態、讀回確認失敗，這些在任務結束的當下就能判定，雖然不是最終真相，但與真正的失敗高度相關。快燒告警可以建立在這些代理指標上，讓事故在幾分鐘內被發現。
>
> 對帳結果則用於兩件事：一是計算正式的 SLO 達成率與 error budget 消耗，二是校準代理指標。如果代理指標標記的任務在對帳後大多是成功的，代表偵測器誤報太多，會讓告警失去信任；反之如果對帳發現的失敗大多沒被代理指標標記，代表偵測器有盲點。兩者的一致率本身就值得放進儀表板，定期檢討。

> [!question]- Q4. 估算題：客服 agent 每天 10,000 個任務，可信完成率 SLO 為 99.5%（28 天）。某次變更讓錯誤率變成 10%，用「1 小時視窗、14.4 倍」的快燒規則，多久會 page？page 之前已經用掉多少 budget？
> 允許錯誤率是 0.5%，所以燒率是 10% ÷ 0.5% ＝ 20 倍，超過 14.4 的門檻。偵測時間用 34.6 節的公式：14.4 × 0.5% ÷ 10% × 60 分鐘 ＝ 43.2 分鐘，也就是 1 小時視窗內的平均錯誤率要累積到 7.2% 才會超標，大約要 43 分鐘。
>
> 這 43 分鐘內約有 10,000 ÷ 1,440 × 43.2 ≈ 300 個任務，其中 10% 即約 30 個是壞結局。28 天的 budget 是 0.5% × 280,000 ＝ 1,400 件，所以 page 之前已用掉約 2.1%。這個數字說明兩件事：一是快燒規則的設計確實是「用掉約 2% budget 時叫人」；二是如果 30 個錯誤的退款承諾已經不可接受，就不能只靠燒率告警，而要在 harness 層加上即時的完成驗證，在錯誤發生的那一刻攔下來。

> [!question]- Q5. 程式找錯：下面的告警規則上線一週後，on-call 開始忽略所有告警。問題在哪裡？
> ```python
> def check(bad_5m: int, total_5m: int) -> None:
>     if total_5m and bad_5m / total_5m > 0.01:   # SLO 是 99%
>         page("可信完成率低於 SLO")
> ```
> 第一個問題是門檻等於 SLO 本身，也就是燒率 1 就 page。燒率 1 代表「照這個速度，剛好在 28 天結束時用完 budget」，這不需要半夜叫人，而且隨機波動會讓它經常超標。第二個問題是只有 5 分鐘的短視窗：每 5 分鐘只有幾十個任務，一兩筆失敗就超過 1%，告警會非常頻繁，而且大部分是雜訊。第三個問題是沒有最少事件數，凌晨流量低時，一筆失敗就是 100% 的錯誤率。
>
> 修法是 34.6 節的多視窗、多燒率規則：快燒用 1 小時長視窗與 5 分鐘短視窗、門檻 14.4 倍；慢燒用 6 小時與 30 分鐘、門檻 6 倍；兩個視窗都超標才觸發，並設定長視窗的最少事件數。燒率較低的持續惡化改開 ticket 而不是 page。告警的品質要被量測：每一次 page 都應該是需要人處理的事，否則 on-call 會學會忽略它，真正的事故來時也一樣。

> [!question]- Q6. MAST 是 multi-agent 系統的研究，我們只有單一 agent，能用這個分類嗎？
> 大部分可以。MAST 的三大類中，系統設計問題（違反任務或角色規格、步驟重複、遺失歷史、不知道終止條件）與任務驗證問題（過早終止、驗證不完整或錯誤）在單一 agent 上同樣常見；只有 agent 之間的錯位這一類，需要多個 agent 互動才會出現。不過，單一 agent 與人或外部系統之間的交接，也會出現類似「沒有要求澄清」「隱瞞資訊」的問題，例如轉真人時摘要漏掉關鍵資訊。
>
> 使用時要記得研究分類的邊界。MAST 的資料來自特定的開源框架與任務，你的產品會有它沒涵蓋的失敗，例如違反政策的承諾、hallucinated tool call 中的捏造 ID。比較好的做法是以 MAST 為參考座標，建立團隊自己的分類，每一類寫明判定規則，並在表格中註明對應的 MAST 類別，方便和文獻比較與溝通。

> [!question]- Q7. 面試追問：EU AI Act 對一個電商客服 agent 有什麼影響？它算高風險嗎？
> AI Act 依用途分級，而不是依技術。電商客服通常不在附件列出的高風險領域（就業、教育、信用評估、關鍵基礎設施等），所以一般不屬高風險系統；但它是與人互動的 AI，適用 Art. 50 的透明義務：使用者要知道自己在和 AI 互動。截至 2026 年 10 月，Art. 50 已經適用（部分生成內容標示義務延到 2026-12-02）。實際是否落入其他類別，例如客服 agent 開始做信用額度或保險相關判斷，要由法務依用途判斷。
>
> 回答面試時，好的追問是「如果這個 agent 未來擴展到高風險用途呢？」高風險義務包含風險管理、自動 log、人類監督、準確性與穩健性、技術文件、上市後監控與事故通報。這些在工程上對應 trace、eval、SLO、approval 與 postmortem，也就是本書各章的產出。所以即使目前不是高風險，及早建立這些能力，未來擴展時的合規成本會低很多；反過來，如果系統沒有 trace 與降級開關，任何文件都補不起來。

> [!question]- Q8. 供應商通知舊的模型 snapshot 一個月後下架，但變更審查流程完整走完要三週，你會怎麼處理？
> 首先不要把它當成緊急變更而跳過流程，model 升級是影響面最廣的變更之一，2026 年公開的 postmortem 也顯示，看似中性的調整就可能讓品質明顯下降。可以做的是把流程平行化並提早開始：regression eval 與 per-model eval 是自動化的，第一天就能跑完；shadow 可以和資安審查同時進行；canary 用較快的階梯（例如 1%、10%、50%、100%，每階一到兩天），由燒率監控自動把關。
>
> 長期的解法是讓這件事不再緊急。一是在變更政策中把「供應商預告下架」列為已知事件，收到通知就自動建立變更請求並排程；二是持續對候選的新 snapshot 跑 eval，讓升級時已經有幾週的比較資料；三是透過第 25 章的 model adapter 與 fallback 設計，讓切換模型只是設定變更而不是程式改寫。如果 eval 顯示新模型在某些任務上退步，也可以先在那些任務上保持較低的 autonomy，等 prompt 調整完成再放寬，而不是讓下架期限逼著你接受退步。
