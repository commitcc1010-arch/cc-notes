## D.1 怎麼使用這些清單

清單的價值不在「全部打勾」，而在於把「我覺得應該沒問題」變成「這一題的證據在哪裡」。所以本附錄的每一題都要求可以回答，而且回答要附證據：一份 eval 報告、一段 design doc、一次演練紀錄、一個測試名稱。答得出「是」卻拿不出證據的題目，審查時當作「否」處理；答不出來的題目，就是 design doc 的待辦事項。這也是第 35 章的原則：每一題都應該能在 design doc 中找到對應的段落，找不到就是審查意見。

等級的判定規則可以寫成程式，這樣審查結論就不會因為開會的氣氛而改變。下面這段程式把一份清單的回答變成三種結論：通過、有條件通過、不通過。它刻意處理了三個常見的漏洞：回答「通過」卻沒有證據、把題目標成「不適用」卻不寫理由、建議項沒過卻沒有人負責。

```python
from __future__ import annotations

from dataclasses import dataclass


@dataclass
class Answer:
    item_id: str
    level: str               # 必要｜建議
    result: str              # pass｜fail｜na
    evidence: str = ""       # 證據連結：eval 報告、演練紀錄、設計文件段落
    owner: str = ""          # 建議項未過時的負責人
    due: str = ""            # 建議項未過時的補齊期限
    na_reason: str = ""      # 標成不適用時的理由


def decide(answers: list[Answer]) -> tuple[str, list[str]]:
    """把一份清單的回答變成審查結論：必要項未過就擋；建議項未過要有負責人與期限。"""
    blockers: list[str] = []
    exceptions: list[str] = []
    for a in answers:
        if a.result == "na":
            if not a.na_reason:                       # 「不適用」也要能被質疑
                blockers.append(f"{a.item_id} 標為不適用但沒有理由")
        elif a.result == "pass":
            if not a.evidence:                        # 沒有證據的「是」等於沒回答
                blockers.append(f"{a.item_id} 回答通過但沒有證據")
        elif a.level == "必要":
            blockers.append(f"{a.item_id} 必要項未通過")
        elif a.owner and a.due:
            exceptions.append(f"{a.item_id}（{a.owner}，{a.due} 前補齊）")
        else:
            blockers.append(f"{a.item_id} 建議項未通過，缺負責人或期限")
    if blockers:
        return "不通過", blockers
    if exceptions:
        return "有條件通過", exceptions
    return "通過", []


reviews = {
    "客服 v1 設計審查": [
        Answer("DR-08", "必要", "pass", evidence="design doc §2 動作清冊"),
        Answer("SC-10", "必要", "pass", evidence="threat model §4"),
        Answer("DR-72", "建議", "fail", owner="阿哲", due="2026-11-15"),
        Answer("DR-17", "必要", "na", na_reason="單一 agent，不採 multi-agent"),
    ],
    "退款 L4 晉升": [
        Answer("GL-31", "必要", "pass", evidence="autonomy 晉升報告"),
        Answer("CH-31", "必要", "fail"),
    ],
    "報表 agent 上線": [
        Answer("OB-13", "必要", "pass"),
        Answer("DR-06", "建議", "fail"),
        Answer("SC-59", "必要", "na"),
    ],
}
verdicts = {}
for name, answers in reviews.items():
    verdict, notes = decide(answers)
    verdicts[name] = verdict
    print(f"{name}：{verdict}")
    for note in notes:
        print(f"  - {note}")

assert verdicts == {"客服 v1 設計審查": "有條件通過", "退款 L4 晉升": "不通過", "報表 agent 上線": "不通過"}
```

```text
客服 v1 設計審查：有條件通過
  - DR-72（阿哲，2026-11-15 前補齊）
退款 L4 晉升：不通過
  - CH-31 必要項未通過
報表 agent 上線：不通過
  - OB-13 回答通過但沒有證據
  - DR-06 建議項未通過，缺負責人或期限
  - SC-59 標為不適用但沒有理由
```

第一份審查有條件通過：必要項都有證據，multi-agent 那題寫了不適用的理由，唯一沒過的是建議項 DR-72（互動模式的選擇依據），而且有負責人與期限，依第 38 章的規則，期限到時要自動複查。第二份是退款從 L3 晉升 L4：晉升證據齊了，但 CH-31（autonomy 提升要經過治理委員會核准）沒過，是必要項，所以不通過。第三份同時踩了三個漏洞，三條都被列成阻擋原因。實務上可以把本附錄的表格匯出成這種結構，存在 design doc 或變更單旁邊，讓每次審查的結論都可以重算。

## D.2 設計審查

設計審查回答「這個系統該不該這樣蓋」。它依第 35 章的七步驟排列：任務與成功標準、autonomy 與風險、架構選型，再加上 harness 細節、orchestration、production 架構與產品體驗。context、tools 與安全的細項另外成表（D.3 到 D.5），設計審查時一起打開。

## D.3 Tool 審查

tool 是 agent 對世界產生影響的唯一管道，所以 tool 審查同時是介面審查與風險審查。新增一個 tool、修改描述或參數、接上一個 MCP server，都要走這份清單；涉及對外通訊或不可信內容的 tool，還要回到 D.5.2 重做 lethal trifecta 的標註。

## D.4 Context 與 memory 審查

## D.5 安全審查

安全審查的出發點是第 35 章的那一題：「模型被完全誘導時，最壞能做什麼？」這份清單依序走過 threat model、lethal trifecta、防禦設計、身分與授權、核准、sandbox、供應鏈與稽核。答案中只要出現「我們在 prompt 裡要求它不要這樣做」，那一題就還沒有過：影響為高的威脅，至少要有一項確定性的控制。

## D.6 Eval 審查

eval 審查回答「我們憑什麼相信它變好了」。它涵蓋三件事：題目與環境是否代表真實任務、grader 是否真的抓得到錯、比較與發布閘門的統計方法是否站得住。引用公開 benchmark 分數的題目也放在這裡，因為它們常被拿來當選型或升級模型的論據。

## D.7 可觀測性審查

agent 的失敗常常是 HTTP 200、延遲正常、沒有例外，但退款判斷錯了。所以可觀測性審查不只問「有沒有 trace」，還要問 trace 能不能重建一次決策、能不能算出每次成功任務的成本、會不會洩漏個資、以及語意失敗能不能被告警抓到。

## D.9 變更審查（prompt／model／tool）

對 agent 來說，會改變行為的東西都是程式：prompt、model snapshot、tool 的名稱與描述、guardrail policy、retrieval index、harness 設定、autonomy 等級。變更審查的目的不是讓每次修改都走最重的流程，而是依風險分級，讓低風險變更走得快、高風險變更有證據，而且緊急回滾永遠不被流程卡住。

### D.9.1 依風險分級的變更流程

下表整理第 34 章 34.9 節的變更類型與最少證據。影響寫入 tool 行為的變更（例如修改退款流程的 prompt 指示）自動升一級，這是第 34 章週末事故的直接教訓。

| 變更類型 | 典型例子 | 最少證據 | 核准者 | 發布方式 |
|---|---|---|---|---|
| prompt（不影響寫入） | 調整語氣、補充 FAQ | regression eval | agent owner | canary |
| prompt（影響寫入）、tool schema | 修改退款流程指示、改參數 | regression＋per-model eval、shadow | owner＋資安 | shadow 後 canary |
| model snapshot | 換新版本或換供應商 | 全套 eval、shadow、安全測試 | owner＋資安 | shadow 後 canary，保留舊版回滾 |
| guardrail policy | 調整 PII 遮罩或 injection 分類器門檻 | 安全測試、誤判率評估 | 資安 | canary |

## D.10 事故處理

agent 事故和傳統服務事故的流程大致相同：確認、分級、止血、溯源、修復、復盤。不同的是止血手段（降 autonomy、關掉單一 tool、回滾 release，而不只是回滾部署）、溯源材料（trace 中的版本 lockfile），以及一個傳統服務很少需要的步驟：因為失敗常常是靜默的，你必須主動找出所有受影響的使用者。

### D.10.1 事故分級

| 等級 | 判斷標準（任一成立） | 回應時間 | 止血手段 | 例子 |
|---|---|---|---|---|
| SEV-1 | 不可逆的金錢或資料損失、安全事件、法規通報義務 | 立即，全員 | kill switch 停用 agent 或 tool | agent 被誘導外洩個資 |
| SEV-2 | 錯誤的金錢動作或承諾，影響多位使用者 | 15 分鐘內 | 降 autonomy、回滾版本 | 未驗證就宣告退款完成 |
| SEV-3 | 品質下降但無錯誤承諾，或成本異常 | 當日 | 回滾、調整上限 | 迴圈讓成本翻倍 |
| SEV-4 | 單一使用者、可人工修正 | 一般工單 | 個案處理 | 一次錯誤的物流回覆 |

這是第 34 章 34.7 節的分級表，回應時間是青鳥的設定。分級依據是影響（金錢、使用者數、法規），不是技術複雜度；成本異常有自己的等級，因為 agent 的迴圈不會讓服務掛掉，卻可能在幾小時內燒掉一個月的模型預算。
