# 第 46 章　趨勢、開放問題與持續學習

> [!abstract] 本章地圖
> **核心問題**：agent 技術每個月都有新模型、新協定、新服務，設計者要怎麼判斷哪些變化會改變自己的架構、哪些只是噪音，並用自己的證據決定要不要跟？
>
> **你會學到**：
> - 分辨「不會過時的原理」與「會一直換的介面與產品」，知道本書哪些內容要定期重新查證
> - 說出八個有公開證據支撐的趨勢，每一個都能講清楚證據、對設計的影響、現在該做什麼
> - 說明可靠性、長期記憶、prompt injection、評估、責任歸屬這五個尚未解決的問題，以及目前最好的應對方式
> - 用證據階梯與自家 eval 判斷新技術，把結果放進 adopt／trial／assess／hold 四個環
> - 為 harness 元件建立定期 ablation 的排程與報告，讓過時的元件能被安全地拿掉
> - 把全書當成設計與審查時的參考書使用，知道遇到什麼問題回到哪一章
>
> **前置知識**：第 1 章（autonomy 等級與任務適合度）、第 27 章（eval 與 pass^k）、第 30 章（harness 隨模型升級而簡化）、第 32 章（架構層的防禦）、第 45 章（loom v1.0 的完整組裝）

## 46.1 故事：一年後的回顧會議

`loom` v1.0 上線滿一年的那個週五，老陳在會議室白板上畫了一條時間軸，請大家把這一年「追過的新東西」一張一張貼上去。便利貼很快就貼滿了：新一代前沿模型、協定的大改版、讓模型寫程式來呼叫工具的 code-as-action、一家廠商主打「全自主、會自我修復」的 agent 平台、自動 prompt 優化、託管的 agent runtime、新的 reranker，還有好幾個在社群上紅過一陣子、現在已經沒人提的框架。數一數，一共十一張。

接著老陳請 Iris 在每張便利貼旁邊寫上一個數字：「它讓我們自己的 eval 變好了多少？」結果讓大家都安靜下來。十一項裡，只有四項有自家 eval 的前後比較；其中 code-as-action 讓營運 research agent 的報表題通過率明顯上升、token 也少了一大截，這是唯一一項大家沒有異議的成功。協定改版是被迫的：舊版功能被標成 deprecated，`loom.mcp` 花了三週才把「每條連線有自己的 session」這個隱含假設拔乾淨。那個全自主平台的 demo 很漂亮，但拿青鳥的客服題去跑，同一題連跑三次都對的比例（第 27 章的 pass^k）比現有系統差很多，最後沒有導入。

最讓 Iris 在意的是兩件「拿掉」的事。換到新一代模型後，團隊做了一次 ablation（一次拿掉一個元件，看結果變化），發現當初為了防止模型在 context 快滿時草率收尾而加的 context reset，對新模型已經沒有作用，只是白白多花 token；但同一輪他們也順手刪掉 system prompt 裡一條看似囉嗦的提醒「退款後要再查一次狀態」，結果 canary 階段就抓到客服 agent 開始把「退款已受理」講成「已退款」。阿哲問：「所以明年我們該追什麼？」老陳搖頭：「我不想預測明年流行什麼。我想要的是一個流程，讓任何新東西進門之前，都要先過我們自己的 eval。」

Maya 補了另一個角度。這一年最驚險的一次事故，是有人在商品評論裡藏了一段指令，想讓 research agent 把客戶名單寄出去；擋下它的不是任何分類器，而是第 31、32 章那套「讀過不可信內容的 context 不能對外寄信」的架構規則。「模型每一代都更強，」Maya 說，「但 prompt injection 沒有因此消失。有些問題是會被模型進步解決的，有些不會，我們要分得清楚。」

這一章就是那場回顧會議的整理。我們先建立一個分辨「會變」與「不會變」的框架，接著逐一看八個有公開證據的趨勢，再談五個還沒有解法的開放問題，然後建立判斷新技術的方法。動手做會實作兩個工具：一個是依證據強度、自家 eval 改善與遷移成本給出 adopt／trial／assess／hold 的技術雷達，另一個是 harness 元件的定期 ablation 排程與報告。最後一節是全書回顧，說明這本書往後可以怎麼用。

## 46.2 先分清楚：會變的與不會變的

追蹤趨勢的第一步不是收集新聞，而是知道自己手上的知識各有多長的保存期限。本書從第 1 章開始就刻意把內容分成兩種：正文講原理與取捨，版本、價格、分數與產品細節放在「2026 現況」區塊。這個分法不只是排版習慣，它對應的是知識的半衰期。所謂**半衰期**，這裡是指一項知識有一半內容變得不正確或不再重要所需的時間；例如「tool call 要用 id 對回結果」幾年內都成立，而「某個 API 的某個參數叫什麼名字」可能下一季就改了。

```text
 半衰期長（以「年」計）                                         半衰期短（以「月」計）
 ┌──────────────┬──────────────┬──────────────┬──────────────┬──────────────┐
 │ ① 原理        │ ② 抽象        │ ③ 協定        │ ④ 產品與服務   │ ⑤ 版本與分數   │
 │ loop、停止條件 │ Agent、Tool、 │ MCP、A2A、    │ 託管 runtime、 │ 模型名稱、     │
 │ 有效權限交集   │ Session、     │ AG-UI、支付   │ SDK、框架、    │ benchmark 分數 │
 │ outcome 評估  │ Event、       │ 協定的版本與   │ 觀測與評估平台 │ 價格、預設值   │
 │ lethal trifecta│ Approval      │ 欄位名稱       │               │               │
 └──────┬───────┴──────┬───────┴──────┬───────┴──────┬───────┴──────┬───────┘
        │              │              │              │              │
   寫進設計文件     寫進 framework    包在 adapter    包在可替換的    只寫在
   與審查清單       的核心介面        後面、釘版本    整合層後面      設定與現況筆記
```

這張圖由左到右是半衰期由長到短。第 ① 層是原理：模型提議、harness 執行（第 4 章）；有效權限是三方交集（第 33 章）；評分看 outcome 而不是 agent 自己說了什麼（第 27 章）。這些不會因為換模型而失效，所以應該寫進設計文件與審查清單。第 ② 層是抽象，也就是第 23 章 `loom` 的核心型別；它們會演進，但演進要經過 API 相容性的設計。第 ③ 層是協定，會有 breaking change，所以要包在 adapter 後面並釘住版本。第 ④ 層是產品，會被收購、改名、退場；第 ⑤ 層是數字，幾個月就過時。

圖下方那一列是對應的工程動作，也是本章最重要的一句話：**半衰期越短的東西，越要放在越容易替換的位置**。一個常見的錯誤是把第 ⑤ 層的東西寫進第 ② 層，例如在 framework 的核心型別裡寫死某家模型的 thinking 欄位名稱，或在 eval 的通過門檻上寫死某個 benchmark 分數；下一次模型升級，整個 framework 都要跟著改。反過來的錯誤也有：把第 ① 層的原理當成可以隨產品更換的細節，例如因為新的託管服務「內建安全」，就拿掉自己的 egress 限制。

| 層 | 例子 | 典型變化速度 | 變了會怎樣 | 你的防線 |
|---|---|---|---|---|
| 原理 | 停止條件要多重、不可逆動作不完全自動 | 很少變 | 幾乎不會「變」，只會被遺忘 | 設計審查清單、新人訓練 |
| 抽象 | Session log、Approval、Tool registry | 每年小幅演進 | 介面改動，波及所有使用者 | 向後相容、deprecation 週期 |
| 協定 | MCP 的 session 模型、A2A 的 task 狀態 | 一年數次改版 | 整合壞掉、需要遷移 | adapter、版本釘選、契約測試 |
| 產品 | 託管 runtime、SDK、觀測平台 | 季度級變動 | 功能改名、定價變、退場 | 可替換的整合層、資料可匯出 |
| 數字 | 模型分數、價格、預設 effort | 月級變動 | 判斷依據失效 | 只寫在設定檔與現況筆記，附日期 |

這張表把每一層的「變了會怎樣」與「防線」配對起來。讀到任何新消息時，先問它屬於哪一層：如果是第 ⑤ 層的新分數，改設定或更新筆記就好；如果是第 ③ 層的協定改版，排一次遷移；只有極少數消息會動到第 ① 層，例如有人提出可證明安全的新防禦模式，那才值得重讀第 32 章並修改審查清單。下面八個趨勢，大多數落在第 ②、③、④ 層，但它們對第 ① 層的原理都有一點啟示。

## 46.3 趨勢一：模型能自主工作的時間變長

**證據**。過去兩年最一致的變化，是 agent 能在沒有人介入的情況下連續工作的時間越來越長：從幾分鐘的客服對話，到數十分鐘的程式修改，再到公開報告中長達數小時的應用程式開發。評估界也出現了專門描述這件事的指標：以「人類完成同一任務需要多久」來衡量 agent 能以一定成功率完成的任務長度，常被用來觀察趨勢。模型廠商的 API 也開始為「長時間、百萬 token 級」的任務提供專門的推理強度設定。這些證據來自不同來源，方向一致，所以證據強度高；但具體的成長速度各家說法不一，本書不做外推。

**對設計者的影響**。任務一旦從分鐘級變成小時級，第 4 章那個同步的 loop 就不夠了。崩潰、部署、rate limit 在一小時內幾乎一定會發生至少一次，所以第 22 章的 durable execution 從選配變成必要；使用者不可能盯著畫面等，所以第 37 章的非同步互動與進度呈現變成主要 UX；context 一定會滿，所以第 10 章的 compaction 與進度檔要成為預設行為。更隱微的影響在驗證：任務越長，錯誤越可能在中途發生並被後續步驟放大，驗證點必須分布在過程中，而不是只在最後檢查一次。

```text
 任務長度        主要風險                        harness 必須具備                     對應章節
 ─────────────────────────────────────────────────────────────────────────────────────
 秒～分鐘   ──► 步驟錯、tool 參數錯         ──► 錯誤回填、步數與 token 上限          第 4、5 章
    │
 數十分鐘   ──► context 滿、原地打轉        ──► compaction、進度檔、重複偵測         第 10、24 章
    │
 數小時     ──► crash、部署、限流、         ──► durable log、可重播、checkpoint、     第 22、36 章
    │           錯誤在中途累積                    過程中的驗證點、非同步通知
    │
 數天以上   ──► 目標漂移、預算失控、        ──► 預算與里程碑、定期人工檢查點、       第 21、34、38 章
                權限長期有效                      短效憑證、可撤銷的授權
```

這張圖由上往下是任務長度增加的方向，每往下一層，上一層的機制都還要保留，再加上新的機制。秒到分鐘級的風險是單步出錯，第 4、5 章的錯誤回填就夠用。數十分鐘級開始要面對 context 有限的問題。到了數小時，基礎設施本身的失敗成為主角，event log 與重播讓 agent 能從中斷處繼續，而不是從頭再燒一次 token。數天以上的任務，最大的風險是「方向」：目標在多次 compaction 後慢慢偏移、預算在沒人注意時用完、一開始授權的憑證到第三天還有效，所以要有里程碑式的人工檢查點與短效、可撤銷的授權（第 33 章）。

**你現在該做什麼**。第一，即使你今天的任務只有幾分鐘，也把 session log 做成 append-only 並與 context 分開（第 10 章的不變式），這是將來支援長任務最便宜的投資。第二，預算不要只設 token 上限，要設 wall-clock 與里程碑，並讓 agent 在里程碑寫進度檔。第三，為長任務設計「過程中的驗證」：例如 coding agent 每完成一個子目標就跑一次測試，research agent 每完成一個章節就檢查引用。第四，autonomy 等級（第 1 章）要依動作決定，不要因為 agent 能跑得更久，就順手把它在每個動作上的權限都調高。

> [!note] 2026 現況
> 截至 2026 年 10 月的公開資料：Anthropic〈Harness design for long-running application development〉（2026-03）報告，用完整的 generator／evaluator harness 開發一個遊戲製作工具約花 6 小時、約 200 美元，簡化 harness 搭配較新模型開發一個數位音訊工作站約 3 小時 50 分；Anthropic 的 effort 參數中，`xhigh` 定位為超過 30 分鐘、token 預算達百萬級的長程 agentic 任務；Cursor〈Towards self-driving codebases〉（2026-02）描述峰值數百個並行 agent、每小時約 1,000 個 commit 的實驗。METR 的 time-horizon 指標（50% 成功率對應的人類任務時長）常被用於趨勢分析，本書未查證其最新數值。以上都是單一實驗或廠商自述，引用時請附來源與日期。

## 46.4 趨勢二：harness 元件隨模型升級而過時

**證據**。這是 2026 年公開證據最具體的一個趨勢。模型廠商在工程文章中說明：某一代模型在 context 接近上限時會「焦慮」而草率收尾，所以 harness 需要 context reset；到了下一代，這個現象大致消失，reset 變成白做工。coding 工具廠商報告，模型變強之後，冗長的禁止事項與提醒變得不必要，大幅刪減 system prompt 後以真實流量 A/B 驗證品質沒有下降。早期為了讓模型「停下來想一想」而設計的 no-op 工具，也大致被模型原生的交錯推理取代。這和 Rich Sutton〈The Bitter Lesson〉的觀察一致：手工加進去的知識，長期會被更通用、隨算力擴展的方法超越。

但同一批證據也有反方向的教訓。有廠商的事故檢討公開說明：為了降低延遲而調低預設推理強度、在 system prompt 加一行限制 tool 之間文字長度的規則，都讓使用者感覺品質下降，其中一項經 ablation 證實讓某個 eval 掉了數個百分點。也就是說，**harness 的改動同時可能是負擔，也可能承重**，憑直覺判斷不了，只能量。

**對設計者的影響**。每一個 harness 元件都編碼了一個關於模型弱點的假設：重複偵測假設模型會原地打轉，結果驗證假設模型會把「受理」當成「完成」，長篇規則假設模型需要被提醒。模型換代時，這些假設有些仍然成立、有些已經失效、有些甚至變成干擾。所以 framework 的設計要讓元件**可拆卸**：能用設定開關，能單獨量測效果，能記錄當初為什麼加。第 23 章的 middleware 與 hooks 設計，價值就在這裡。

```text
              新模型弱點被觀察到
                     │
                     ▼
              ┌─────────────┐   ablation：拿掉後 eval 下降
   ┌─────────►│ 承重         │◄───────────────────────────┐
   │          │ load-bearing │                            │
   │          └──────┬──────┘                            │
   │                 │ 換模型世代，或距上次 ablation 超過 N 天
   │                 ▼                                    │
   │          ┌─────────────┐                            │
   │ canary   │ 待驗證       │────────────────────────────┘
   │ 發現回歸  │ under review │
   │          └──────┬──────┘
   │                 │ 拿掉後 eval 不變且省成本，或拿掉後反而變好
   │                 ▼
   │          ┌─────────────┐   canary／shadow 通過   ┌─────────────┐
   └──────────│ 候選移除     │───────────────────────►│ 已移除       │
              │ candidate    │                        │（保留設定開關 │
              └─────────────┘                        │  與紀錄）     │
                                                      └─────────────┘
```

這是一個 harness 元件的生命週期狀態機。元件因為觀察到某個模型弱點而被加入，進入「承重」狀態。每當模型換代，或距離上次 ablation 太久，它就進入「待驗證」，重新做 ablation：拿掉後 eval 下降，回到承重；拿掉後 eval 不變但省成本，或拿掉反而變好，進入「候選移除」。候選移除不是直接刪程式碼，而是先在 canary 或 shadow 流量上確認（第 36 章）；如果 canary 發現回歸，就回到承重。真正移除之後，最好保留設定開關與紀錄，因為某些任務或某些較小的模型可能還需要它。青鳥那條「退款後再查一次狀態」的提醒，就是在候選移除階段被 canary 救回來的。

**你現在該做什麼**。為 `loom` 的每個 harness 元件登記三個欄位：它在補哪個模型弱點（假設）、為哪一代模型加入、上次 ablation 是什麼時候。把「換模型」定義成一個會觸發 ablation 的事件，而不是改一行設定檔。ablation 要一次拿掉一個、在同一組題目上配對比較、每題多跑幾次；46.13 節會把這個流程寫成程式。第 6 章「隨模型升級刪減 prompt」與第 30 章「harness 隨模型升級而簡化」講的是同一件事的兩個面向，本章把它變成定期執行的營運流程。

> [!note] 2026 現況
> 截至 2026 年 10 月：Anthropic〈Scaling Managed Agents〉（2026-04）提到 Sonnet 4.5 接近 context 上限時會草率收尾，需要 context reset，Opus 4.5 大致沒有這個現象，reset 變成 dead weight；Cursor（2026-09）報告 system prompt 刪減約 66%，A/B 驗證品質不降，並拿掉了「推模型使用 subagent」的提示；Anthropic 2026 年 4 月的 Claude Code 品質事故 postmortem 說明，預設 reasoning effort 從 high 降到 medium 後使用者明顯覺得變差並回滾，一行限制 tool 之間文字長度的 system prompt 經 ablation 讓某個 eval 下降 3%。這些是廠商自述，但方向在多家之間一致。

## 46.5 趨勢三：託管 agent 服務成為主流形態

**證據**。主要模型廠商與雲端平台都推出了**託管 agent 服務**（managed agent service）：由服務商代管 agent loop、sandbox、session 與 compaction，你只要用 API 定義模型、指令與工具，就能在雲端跑一個長時間的 agent。換句話說，第 4 章到第 22 章你親手寫的那些零件，現在可以整包租用。同一時期，舊式的「助理」API 被新的有狀態介面取代，視覺化 no-code agent builder 也有退場的案例，code-first 的託管 harness 成為主流。多家廠商在同一年做出相同的產品形態，這是證據強度很高的訊號。

**對設計者的影響**。build vs buy（第 26 章）的界線往上移了：以前要不要自己寫 loop 是個問題，現在連 sandbox pool 與 session store 都可以買。但託管服務有自己的 harness 預設值，而上一節剛說過，harness 預設值會直接左右品質；青鳥用託管 runtime 的預設 harness 跑客服題，結果就比自家調過的版本差。更大的風險是鎖定：如果 session log、trace 與 eval 資料都只存在服務商那裡，日後要換就很難。

```text
            ┌───────────────── 可以租用（託管服務代管）────────────────┐
            │                                                        │
            │   Brain（harness／loop）      Hands（sandbox、工具執行）  │
            │        │  無狀態，可隨時重啟        │ 用完即銷毀           │
            │        └──────────┬────────────────┘                    │
            │                   ▼                                     │
            │           Session（事件日誌）                            │
            └───────────────────┬────────────────────────────────────┘
                                │ 匯出（必須能做到）
            ┌───────────────────▼────────────────────────────────────┐
            │ 必須自己擁有                                            │
            │  ① 任務定義與 eval set   ② trace 與 session log 副本     │
            │  ③ tool 與業務邏輯       ④ 政策：approval、權限、預算     │
            │  ⑤ 模型與 harness 選擇的決策紀錄                         │
            └────────────────────────────────────────────────────────┘
```

圖的上半部是託管服務擅長代管的三件事，這個 Brain／Hands／Session 的三分法來自公開的託管服務設計：harness 無狀態、sandbox 像牲畜而不是寵物、所有進度記在 session 事件日誌裡。下半部是無論租不租都必須自己擁有的五樣東西。eval set 是你判斷任何服務好壞的唯一標準；trace 與 session log 的副本讓你能離開；tool 與業務邏輯是你的產品本身；approval 與權限政策是你的責任，不能外包給服務商的預設值；最後，為什麼選這個模型、這個 harness 的紀錄，是下一次重新評估的起點。

**你現在該做什麼**。第一，評估託管服務時用自家 eval 跑它的預設 harness 與你調過的設定，兩者分開記錄。第二，在合約與架構上都確認 session log 與 trace 能以標準格式（例如第 29 章的 OTel GenAI 慣例）匯出。第三，把 tool 做成與 runtime 無關的形式（例如 MCP server），這樣同一組 tool 可以給自家 `loom` 與託管服務共用。第四，政策引擎留在自己的 gateway（第 36 章），不要只依賴服務內建的設定。

| 層 | 適合租用的情況 | 適合自建的情況 | 不論哪種都要守住 |
|---|---|---|---|
| loop／harness | 任務通用、團隊小、要快上線 | harness 是產品差異化所在、需要細緻 ablation | 能用自家 eval 比較 |
| sandbox | 需要強隔離但沒有基礎設施團隊 | 有特殊網路或合規要求 | secrets 不進 sandbox、egress 預設拒絕 |
| session／memory | 標準對話與長任務 | 需要特殊保留期限、資料落地 | 可匯出、可刪除（第 12 章） |
| eval 與觀測 | 想快速有儀表板 | 要和內部資料、業務指標結合 | 原始 trace 自己留一份 |
| 政策與核准 | 很少適合完全外包 | 幾乎總是 | deny-overrides、稽核鏈（第 21 章） |

這張表是第 26 章選型表的一年後版本，重點在最右欄：不論租或建，有幾條線一定要握在自己手上。

> [!note] 2026 現況
> 截至 2026 年 10 月，託管 agent harness 的代表包括 Claude Managed Agents（beta）、OpenAI Agents API（託管的 Codex harness）、Amazon Bedrock AgentCore Harness、Microsoft Agent Framework 的 Harness Agent，以及 Gemini Interactions API 上的 agents（例如 Deep Research）。OpenAI Assistants API 已於 2026-08-26 停止服務，改用 Responses 與 Conversations；OpenAI 也宣布 Agent Builder 的視覺化 canvas 將退場。Brain／Hands／Session 的說法來自 Anthropic〈Scaling Managed Agents〉（2026-04）。各服務的功能與計價變化很快，選型前請重新查證。

## 46.6 趨勢四：協定標準化，但還在變

**證據**。第 14、15 章介紹的三個協定，分別處理三條邊：MCP 是 agent 到工具與資料，A2A 是 agent 到 agent，AG-UI 是 agent 到前端。這一年它們都進入了「正式版」階段：A2A 與 AG-UI 先後發布 1.0，MCP 則做了一次架構級改版，從有狀態的連線改成無狀態的請求加上顯式 handle。治理也在往中立組織移動，規格有正式的提案流程與 deprecation 政策。框架幾乎全面支援這些協定，相關 SDK 也一起發了大版本。標準化的方向是確定的，證據強度高。

但「標準化」不等於「穩定」。MCP 的改版拿掉了原本的初始化握手與 session，並把幾個功能標為 deprecated；A2A 從 0.x 到 1.0 也有大量 breaking change。對實作者來說，這意味著協定本身就是一個會定期要求你遷移的依賴。青鳥花三週遷移 `loom.mcp`，原因不是新版本難寫，而是舊程式到處默默假設「同一條連線上的呼叫共享狀態」。

```text
            使用者／前端
                 ▲  AG-UI：事件流（文字、tool 呼叫、state 快照與差異、interrupt）
                 │
          ┌──────┴──────┐  A2A：task 生命週期（submitted → working → completed，
          │  你的 agent  │◄─────────────────────────────────────►  另一個 agent
          │  （loom）    │        中斷態 input-required、auth-required）
          └──────┬──────┘
                 │  MCP：tools、resources、prompts；無狀態請求＋顯式 handle；
                 ▼        需要補資料時回 input_required，client 補上後重送
          工具與資料（ERP、物流、知識庫）
                 │
                 ▼  支付協定（46.8 節）：授權證明、商務流程、HTTP 402 傳輸層支付
          商家與金流
```

這張圖是 agent 的協定堆疊。三條邊各有分工：AG-UI 把 agent 內部的事件串流給前端，前端不必理解 agent 用什麼框架；A2A 把遠端 agent 當成不透明的服務，只透過 task 互動；MCP 讓同一組工具可以被不同的 host 使用。圖中最值得注意的共通點是「暫停並等待外部輸入」：AG-UI 的 interrupt、A2A 的 input-required 與 auth-required、MCP 的 input_required，都是同一個概念的不同寫法。這說明第 21、22 章把「可恢復的中斷」做成一級原語是對的：協定怎麼換，這個抽象都用得上。

**你現在該做什麼**。第一，每個協定都包在 `loom` 的 adapter 後面，核心型別不出現任何協定的欄位名稱。第二，釘住協定版本，並為每個整合寫契約測試（contract test，用固定的請求與預期回應驗證雙方仍然相容），升級前先跑。第三，訂閱規格的 changelog 與 deprecation 清單，把「某功能被標為 deprecated」當成工單，而不是等它被移除才處理。第四，不要因為協定支援某功能就啟用它：協定讓整合變容易，也讓攻擊面變大（第 31 章的 tool poisoning 與供應鏈風險）。

> [!note] 2026 現況
> 截至 2026 年 10 月：MCP 以 2026-07-28 版為目前版本，改為 stateless（移除 `initialize` 握手與 `Mcp-Session-Id`、新增 `server/discover`、以 Multi Round-Trip Requests 取代 server 主動發出的請求），Sampling、Roots、Logging 被標為 deprecated，Tasks 改為官方 extension；MCP 的 feature lifecycle 政策規定 deprecated 功能至少保留 12 個月。A2A v1.0 於 2026-03-12 發布、目前為 v1.0.1，規格頁面標示將加入 Agentic AI Foundation。AG-UI 1.0 於 2026-09-17 同步發布 TypeScript、Python、.NET 版本。2026 年 8 到 9 月間，多個主流框架為支援 MCP SDK 2.x 發布了含 breaking change 的版本。

## 46.7 趨勢五：code-as-action

**證據**。**code-as-action** 是讓模型寫一段程式，在 sandbox 裡一次呼叫多個工具、過濾與彙整資料，只把結果帶回 context，而不是一次一個 tool call、把每個中間結果都塞進 context（第 13 章）。學術研究早已報告用可執行程式當動作空間能提升成功率；這一年，多家模型廠商、雲端平台與開源 coding agent 都各自推出了同一方向的設計，名稱各異，例如 programmatic tool calling、code mode。不同團隊在不同產品上獨立收斂到同一個做法，這是很強的訊號。

**對設計者的影響**。工具的呈現方式從「給模型看的 JSON schema 清單」擴展成「給程式 import 的函式庫」，sandbox 從選配變成 framework 的核心元件（第 17 章）。這也改變了成本結構：大量資料留在 sandbox 裡，context 裡只剩摘要，token 可以大幅下降。但安全模型要跟著調整：程式能做的組合遠多於單一 tool call，所以本書（第 13 章）規定有副作用的 tool 一律 `code_callable=False`，必須走一般 tool call 與核准流程；否則一段迴圈就能在沒有任何人看見的情況下退款一千次。

**你現在該做什麼**。先找出自家任務中「讀大量資料、做確定性彙整」的部分，例如青鳥 research agent 的報表查詢，這是 code-as-action 最划算的地方；用自家 eval 比較 token 與通過率。registry 裡每個 tool 都標好 `code_callable`，預設為否。sandbox 依第 17 章的原則：用完即銷毀、secrets 不進 sandbox、egress 預設拒絕。最後，把程式的 stdout 也當成不可信內容處理，因為它可能包含工具回傳的外部資料。

> [!note] 2026 現況
> 截至 2026 年 10 月：Anthropic〈Code execution with MCP〉（2025-11）以一個例子說明 token 從約 150,000 降到約 2,000；Anthropic 的 programmatic tool calling（2025-11 起 beta）報告平均 token 下降約 37%；Cloudflare 稱同一做法為 Code Mode；OpenAI Codex 的開源程式碼中有 code mode 相關模組；Harvey（2026-09）報告以 Python REPL 為核心的遞迴 harness 在自建 benchmark 上大幅超過一般 tool loop，屬自報、自建 benchmark 的單一來源。CodeAct（Wang 等，2024）是較早的學術代表。

## 46.8 趨勢六：agent 經濟與支付

**證據**。當 agent 要代表使用者買東西、付 API 費用，就需要回答三個問題：使用者授權了什麼、商家怎麼和 agent 完成交易、錢怎麼在機器之間移動。這一年出現了多套協定並存的局面，大致分成三層：**授權證明**（用可驗證的數位憑證記錄使用者允許 agent 做什麼）、**商務流程**（agent 與商家的 checkout API，商家仍是交易的責任方）、**傳輸層支付**（在 HTTP 402 Payment Required 狀態碼上做機器對機器的小額支付）。多數協定仍在 beta 或 0.x 階段，主要玩家同時押注好幾套，所以證據強度是「方向明確、細節未定」。

```text
 使用者            你的 agent（loom）              支付／商務協定             商家與金流
   │── 「幫我訂補貨，        │                            │                        │
   │    上限 5,000 元」 ───►│ 記錄授權：上限、品項、期限    │                        │
   │                        │ （授權證明層）               │                        │
   │                        │── 建立 checkout ──────────►│── 商務流程層 ─────────►│
   │                        │◄─ 需要付款（中斷）──────────│◄─ 金額、條款 ──────────│
   │                        │ policy：金額 ≤ 上限？         │                        │
   │                        │ 新商家？超過自動核准門檻？     │                        │
   │◄── 核准卡片（step-up）─│                            │                        │
   │── 核准 ───────────────►│── 付款（憑證由 proxy 加上）─►│── 傳輸層支付 ─────────►│
   │                        │◄─ 收據 ─────────────────────│◄─ 結算 ───────────────│
   │                        │ 收據寫入稽核鏈                │                        │
```

這張時序圖說明支付在 agent 裡的位置。使用者先給出有邊界的授權（金額上限、品項、期限），這是授權證明層要記錄的東西。agent 透過商務流程層建立 checkout，商家回應需要付款，對 agent 來說這是一個**中斷**，和 MCP 的 input_required、A2A 的 auth-required 是同一類事件。接著由確定性的 policy 判斷：金額是否在授權範圍內、是否超過自動核准門檻；需要時發出 step-up 核准（第 33 章的單筆、短效、一次性 token）。付款憑證由 sandbox 外的 proxy 加上，模型永遠看不到；收據寫進 append-only 的稽核鏈。

**對設計者的影響與你現在該做什麼**。支付是 destructive 動作的極端形式：不可逆、對外、牽涉金錢。所以不論採用哪一套協定，第 21 章的規則都適用：未登記的動作預設拒絕、destructive 動作至少要核准、逾時不得自動執行、核准綁定參數 hash。在 tool 層只需要抽象出「需要付款時的中斷與授權」，不要讓任何協定的細節滲進 agent 的核心邏輯；模型不能持有支付憑證，也不能自己填寫金額上限。第 15 章的支付協定概覽與信任問題可以和這一節一起讀。

> [!note] 2026 現況
> 截至 2026 年 10 月：AP2（Agent Payments Protocol，Google 發起，已捐給 FIDO Alliance）為 v0.2；ACP（Agentic Commerce Protocol，OpenAI 與 Stripe）為 beta，最新穩定版為 2026-04-17，商家仍是 merchant of record；UCP（Universal Commerce Protocol）有 draft 文件；x402 已移交 x402 Foundation；MPP（Machine Payments Protocol）提供多語言 SDK。Amazon Bedrock AgentCore Payments 支援 x402 與 MPP，並可設定支出上限。各協定的 mandate 名稱與流程仍在變動，實作前請以最新規格為準。

## 46.9 趨勢七：評估方法的演進

**證據**。公開 benchmark 的生命週期越來越短：一個 benchmark 推出後，前沿模型在一兩年內就把分數推到接近天花板，社群於是推出更難、更抗污染的版本，或乾脆改成持續更新的 benchmark。題目錯誤被修正、評分方式被重做，同一個 benchmark 前後版本的分數已經不能直接比較。另一個方向是評估方法本身的成熟：以 outcome 而不是 transcript 評分、看 pass^k 而不只看 pass@k、從真實失敗建題、防範 agent 在評估中作弊，都已經寫進主要廠商與研究機構的公開指南。託管平台也開始內建 eval 服務。

**對設計者的影響**。第 28 章說過，benchmark 分數和你的任務之間有落差；這個趨勢讓落差更難忽視。同一個模型換一個 harness，分數可以差很多；同一個 benchmark 換一個版本，排名可以重排。所以「某模型在某 benchmark 上贏了」最多只是「值得用自家 eval 測一次」的理由。反過來，自家 eval 的價值越來越高：它是唯一能同時回答「換模型、換 harness、換服務、換協定之後，我的使用者會不會受影響」的工具。

**你現在該做什麼**。把自家 eval 當成產品資產維護：題目有版本、來源（哪一次事故或哪一類使用者請求）、grader 的版本也要記錄。每次比較都在同一組題目上做配對比較，每題多跑幾次，報告信賴區間而不是單一數字（46.13 節的雷達程式就是這樣做）。capability 題穩定通過後畢業進 regression suite（第 27 章）。引用任何外部分數時，連同 benchmark 版本、harness、日期一起記。最後，eval 也要防作弊：測試檔唯讀、hidden tests、trajectory 檢查（第 34 章的 reward hacking）。

> [!note] 2026 現況
> 截至 2026 年 10 月：SWE-bench Verified 已被普遍視為飽和，前沿比較轉向 SWE-Bench Pro 等較新的 benchmark；Terminal-Bench 改為 continuous benchmark；τ-bench 系列演進到 τ³，2026-07 的重新評分讓前後分數不可比；OSWorld 2.0 於 2026-06 釋出。Anthropic〈Demystifying evals for AI agents〉（2026-01）建議從 20 到 50 個真實失敗開始建題，並以 pass^k 衡量一致性；NIST CAISI 於 2025-12 發表關於 agent 評估作弊的研究；Cursor 以真實流量 A/B 驗證 prompt 刪減。AgentCore 與 Google 的 Agent Platform 都提供託管的 eval 功能。

## 46.10 趨勢八：安全仍然靠架構

**證據**。模型每一代都更擅長辨識惡意指令，但 prompt injection 在本質上仍未被解決：模型沒辦法依「來源」可靠地區分指令與資料。公開的紅隊結果顯示，在誘導情境下 agent 仍會高比例地外洩憑證；以模型為基礎的動作分類器在真實流量上有可觀的漏判率；同時，學術界提出的架構式防禦（控制流與資料流分離、能力標籤）能在標準測試集上提供可證明的安全保證，代價是部分任務效用下降。這些證據來自廠商、獨立研究者與學術界，結論一致：**模型層的防禦降低機率，架構層的防禦提供邊界**。

**對設計者的影響**。這是八個趨勢中最反直覺的一個，因為它是「不變」的趨勢。前面幾節都在說模型變強之後 harness 可以變薄；安全是例外。模型越強、能做的事越多，一旦被誘導，損害也越大，所以 sandbox、egress、憑證隔離、有效權限交集這些確定性的邊界不但不能拆，反而要隨能力成長而加強。一個值得記住的公開教訓是「allowlist 等同授權」：允許連到某個網域，就等於允許 agent 透過那個網域做任何那個網域支援的事，包括把資料上傳到別人的帳號。

**你現在該做什麼**。對每個 context 做第 31 章的 lethal trifecta 檢查，審查單位是 context，不是 agent；讀過不可信內容的 context 只能有 none 或 bound 等級的 egress。把分類器定位成第二道防線，用來減少打擾使用者的核准次數，而不是安全邊界（第 32 章）。為安全建立自己的 regression eval，每次換模型或改 harness 都跑，因為上一節說過 harness 改動會影響行為，安全行為也不例外。最後，在 harness ablation 的流程中，把安全元件標成「不參與自動移除」：它們的假設是「環境中有攻擊者」，不是「模型有弱點」，不會因為模型升級而失效。

> [!note] 2026 現況
> 截至 2026 年 10 月：Anthropic〈How we contain Claude across products〉（2026-05）提到紅隊 phishing 測試中 25 次有 24 次外洩 AWS 憑證，只有 egress 與檔案邊界擋得住，並以「allowlist 等同 capability grant」總結一次透過允許網域外洩的案例；Claude Code auto mode（2026-03）的分類器在真實流量上的誤攔率約 0.4%，對真實越權行為的漏判率約 17%；CaMeL（Debenedetti 等，2025）在 AgentDojo 上以 77% 的任務達到可證明安全，未防禦系統的任務完成率為 84%。OWASP Agentic Top 10（2026 版，2025 年 12 月發布）是目前 agent 安全的主要參考清單。

| 趨勢 | 外部證據強度 | 對架構的主要影響 | 現在最該做的一件事 |
|---|---|---|---|
| 自主時間變長 | 高（多來源一致） | durable log、過程中驗證、非同步 UX | session log 與 context 分開 |
| harness 元件過時 | 高（多家實證） | 元件可拆卸、可量測 | 為每個元件登記假設並定期 ablation |
| 託管 agent 服務 | 高（多家同形態） | build vs buy 界線上移、鎖定風險 | 確保 trace 與 log 可匯出 |
| 協定標準化 | 高（但仍有 breaking change） | adapter 層、版本管理 | 契約測試與 deprecation 追蹤 |
| code-as-action | 高（獨立收斂） | sandbox 成為核心、tool 變函式庫 | 標註 `code_callable`，從報表類任務試起 |
| agent 支付 | 中（方向明確、細節未定） | 付款是中斷加核准 | 抽象出付款中斷，不綁特定協定 |
| 評估方法演進 | 高 | 自家 eval 是核心資產 | eval 版本化、配對比較、報告信賴區間 |
| 安全靠架構 | 高（多方一致） | 確定性邊界隨能力加強 | 每個 context 做 trifecta 檢查 |

這張總表把八個趨勢壓成一頁，適合貼在設計審查的會議室。注意「外部證據強度」只告訴你這個趨勢是否真實，不告訴你它對你的任務有沒有幫助；後者要靠 46.12 節的方法和 46.13 節的工具。

## 46.11 尚未解決的問題

趨勢是「正在發生的變化」，開放問題則是「目前沒有人有可靠解法的問題」。區分兩者很重要：對趨勢，你要準備跟上；對開放問題，你要設計成「即使它一直沒被解決，系統也能安全地運作」。下面五個問題，在本書不同章節都出現過，這裡把它們放在一起看。

**可靠性**。單步的可靠度再高，長任務的整體可靠度也會隨步數衰減，這是最基本的機率事實。下面的小程式估算每步獨立成功時，整體成功率如何隨步數變化，以及每隔一段距離插入驗證點能挽回多少。

```python
from __future__ import annotations


def run_success(p_step: float, steps: int, checkpoint_every: int = 0, catch_rate: float = 0.0) -> float:
    """估算長任務整體成功率。每步獨立以 p_step 成功；
    每 checkpoint_every 步驗證一次，能以 catch_rate 的機率抓到並修好這一段的錯。"""
    if not checkpoint_every:
        return p_step ** steps
    total, done = 1.0, 0
    while done < steps:
        seg = min(checkpoint_every, steps - done)
        ok = p_step ** seg                       # 這一段完全沒出錯
        total *= ok + (1 - ok) * catch_rate      # 出錯了，但被驗證抓到並修正
        done += seg
    return total


for p in (0.99, 0.995, 0.999):
    for n in (20, 100, 500):
        print(f"p={p:<6} n={n:<4} 無驗證 {run_success(p, n):6.1%}   每 10 步驗證 {run_success(p, n, 10, 0.9):6.1%}")
assert run_success(0.99, 100) < 0.37
assert run_success(0.99, 100, 10, 0.9) > 0.9
```

```text
p=0.99   n=20   無驗證  81.8%   每 10 步驗證  98.1%
p=0.99   n=100  無驗證  36.6%   每 10 步驗證  90.8%
p=0.99   n=500  無驗證   0.7%   每 10 步驗證  61.9%
p=0.995  n=20   無驗證  90.5%   每 10 步驗證  99.0%
p=0.995  n=100  無驗證  60.6%   每 10 步驗證  95.2%
p=0.995  n=500  無驗證   8.2%   每 10 步驗證  78.3%
p=0.999  n=20   無驗證  98.0%   每 10 步驗證  99.8%
p=0.999  n=100  無驗證  90.5%   每 10 步驗證  99.0%
p=0.999  n=500  無驗證  60.6%   每 10 步驗證  95.1%
```

第一列說明，即使每步有 99% 的成功率，20 步的任務還有約 82% 能完成，100 步就只剩約 37%，500 步幾乎一定會在某處出錯。這就是為什麼 46.3 節說任務變長時驗證要分布在過程中：同樣 99% 的單步可靠度，每 10 步驗證一次、驗證能抓到並修好 90% 的錯誤，100 步的整體成功率就回到約 91%。最後三列顯示單步可靠度提升的效果：從 99% 到 99.9%，500 步任務從幾乎不可能變成約六成。這個模型很粗糙（真實的錯誤不獨立，有些錯誤會被後續步驟自然修正，有些會連鎖放大），但它給出兩個不會過時的結論：長任務需要過程中的驗證，而驗證器的品質決定了上限。

**長期記憶**。第 12 章的 memory 系統解決了「記得」，但沒有解決「記對」與「忘記」。錯誤或惡意的內容一旦寫進長期記憶，會在之後每一次 session 被當成事實（OWASP Agentic Top 10 把它列為 memory poisoning）；使用者的偏好會變，舊記憶什麼時候該失效沒有通用規則；刪除權要求你能找出並刪掉某個人的所有記憶，包括被摘要、被衍生的部分。目前最好的做法是第 12 章的來源權威與優先順序、寫入時標記來源、設定 TTL，以及把記憶做成可檢視、可編輯的檔案，但這些都是緩解，不是解法。

**prompt injection**。上一節已經說明：沒有模型層的可靠解法，目前最好的是架構層的邊界。開放的部分在於代價：可證明安全的設計會犧牲部分任務能力，而且需要人寫 policy；如何在不犧牲太多效用的情況下得到保證，是活躍的研究方向。

**評估**。開放式任務（研究報告、設計建議）很難有確定性的 grader；LLM-as-judge 有偏誤，而且 judge 本身也可能被受測內容誘導；有研究機構指出模型可能察覺自己正在被評估；長時間任務的 eval 成本極高，每題可能就要數小時。目前的應對是 outcome 優先、rubric 拆成可判定的二元檢查、judge 與人工定期校準（第 27 章），但「怎麼可靠地評估一個工作了三天的 agent」仍沒有公認的答案。

**責任歸屬**。agent 代表使用者退了一筆不該退的款、寄出一封不該寄的信，責任是使用者的、部署方的、模型廠商的，還是工具提供者的？法律與標準仍在形成中，agent 應該有自己的身分還是繼承使用者的權限，也被模型廠商公開列為開放問題。架構上你能做的，是讓「誰授權了什麼、agent 根據什麼做了什麼」在事後可以被完整重建：有效權限交集、核准綁定參數 hash、append-only 的稽核鏈、trace 中的業務屬性（第 21、29、33 章）。法律答案會變，但能重建事實的系統，在任何答案下都站得住。

| 開放問題 | 為什麼難 | 目前最好的做法 | 值得留意的進展訊號 |
|---|---|---|---|
| 可靠性 | 錯誤隨步數累積，模型輸出非確定 | 過程中驗證、pass^k、可回復設計 | 長任務 eval 的 pass^k 持續上升 |
| 長期記憶 | 寫錯難察覺、遺忘無通用規則、刪除權 | 來源標記、優先順序、TTL、可檢視檔案 | 有公開評估的記憶衝突與遺忘機制 |
| prompt injection | 模型無法依來源區分指令與資料 | 架構隔離、trifecta 檢查、egress 控制 | 效用損失更小的可證明防禦 |
| 評估 | 開放任務無 grader、judge 偏誤、成本高 | outcome 優先、rubric、人工校準 | 長任務與開放任務的公認評估方法 |
| 責任歸屬 | 法律與標準未定、agent 身分模型未定 | 授權交集、核准綁定、稽核鏈 | agent identity 標準與法規的具體要求 |

這張表的第四欄是讀新聞時的過濾器：與其追「新模型又刷新了什麼分數」，不如追這幾欄的訊號是否出現。

> [!note] 2026 現況
> 截至 2026 年 10 月：NIST 於 2026-02 啟動 AI Agent Standards Initiative，同時處理 agent 安全與 agent identity 和授權；EU AI Act 經修正後，Annex III 高風險義務延到 2027-12-02，Art. 50 的透明義務自 2026-08-02 起適用；Anthropic（2026-05）把 multi-agent 的信任升級與 agent identity 列為開放問題；MAST（Cemri 等，2025）從多個框架的 trace 歸納出 14 種 multi-agent 失敗模式，指出許多失敗來自系統設計與驗證，而非模型本身。

## 46.12 訊號與噪音：追蹤新技術的判斷框架

青鳥那十一張便利貼的共同問題，不是追得太多，而是每一項都沒有經過同一道判斷流程。一項新技術的消息，從出現到值得你投入，中間隔著好幾層證據。我們把它整理成一個**證據階梯**：每往上一階，消息是真的、而且對別人有用的機率就越高；但只有最上面那一階能告訴你，它對你有沒有用。

```text
  ④ 自家 eval 驗證   在你的任務、你的資料、你的 harness 上，配對比較後有顯著改善
        ▲                       ← 只有這一階能決定 adopt
  ③ 多方獨立採用     不同團隊、不同產品各自得到類似結果；有人公開了失敗與限制
        ▲
  ② 可重現的公開實驗  有方法、有資料或程式碼；別人可以照著做一遍
        ▲
  ① 廠商自報數字     有數字，但 benchmark、harness、比較對象由發布者決定
        ▲
  ⓪ 宣傳或 demo      影片、發表會、「效果驚人」；沒有方法與失敗案例
```

階梯由下往上看。第 ⓪ 階的 demo 可以展示可能性，但 demo 是挑過的最好案例，不告訴你失敗率。第 ① 階有數字，但要問：比較對象是什麼、用了什麼 harness、成本算了沒有。第 ② 階可重現，意思是你原則上可以驗證，這時才值得花時間讀細節。第 ③ 階有多方獨立結果，46.3 到 46.10 節的趨勢大多在這一階，所以我們稱它們「有證據」。第 ④ 階是你自己的 eval，沒有任何外部證據能取代它，因為你的任務分布、資料與 harness 都和別人不同。青鳥的「全自主平台」停在第 ⓪ 階，code-as-action 走到了第 ④ 階。

| 訊號的特徵 | 噪音的特徵 |
|---|---|
| 說明方法、比較對象與成本 | 只有結果，沒有比較對象或成本 |
| 公開失敗案例與限制 | 只有成功案例，宣稱「全面」「完全自主」 |
| 不同團隊獨立得到類似結論 | 只有單一來源，或大量轉述同一來源 |
| 和已知原理一致，或明確說明為何不一致 | 宣稱推翻原理，卻不解釋機制 |
| 有版本、日期、harness 等可追溯資訊 | 數字沒有版本與日期，無法比較 |
| 解決你在 eval 或事故中真實遇過的問題 | 解決一個你沒有的問題 |

這張表可以直接當成讀文章時的檢查表。最後一列最常被忽略：即使是真實、可重現、多方採用的技術，如果它解決的問題不在你的失敗清單上，導入它的優先順序也應該很低。老陳的說法是：「先看自己的 error analysis，再看別人的 release note。」

**資訊來源的選擇**也有高低。優先讀一手來源：規格的 changelog 與 deprecation 清單、附 ablation 的工程文章、附方法與資料的論文、開源專案的原始碼與 release note。二手來源（摘要、轉貼、排行榜截圖）適合用來發現消息，但不適合用來做判斷。追蹤的頻率也可以分層：你直接依賴的協定與 SDK，每次發版都要看；模型更新，換代時觸發 eval；其他領域的新技術，累積到一個季度一起評估一次即可。

```text
  新技術消息 ──► 屬於哪一層？（46.2 節）──► 只是版本或數字 ──► 更新設定與現況筆記
                      │
                      ▼ 協定、產品、抽象或方法
               對應我們的哪個失敗或成本問題？── 沒有 ──► hold（記下，季度回顧）
                      │ 有
                      ▼
               外部證據到第幾階？── ⓪ 或 ① ──► hold 或 assess（等待更多證據）
                      │ ② 以上
                      ▼
               建 eval 題目，配對比較（同一組題目、多次 trial、信賴區間）
                      │
           ┌──────────┼───────────────┐
           ▼          ▼               ▼
         變差       不顯著           顯著改善 ──► 遷移成本低或可退回？
          │          │                            │是          │否
          ▼          ▼                            ▼            ▼
         hold   trial 或 assess                 adopt        trial（試點、canary）
```

這張流程圖是「新技術進門的閘道」，也是 46.13 節雷達程式的邏輯。第一關把只影響版本或數字的消息分流出去，它們不需要決策會議。第二關問「它對應我們的哪個問題」，沒有就先擱置。第三關看外部證據，低於第 ② 階就先觀察。通過這三關的才值得花工程時間建 eval。eval 結果分三種：變差就 hold；差異不顯著，便宜的可以小範圍試、貴的先繼續評估；顯著改善時，再看遷移成本與能否退回，決定直接 adopt 還是先試點。這四個環的名稱借自 Thoughtworks Technology Radar：adopt 是建議採用、trial 是在可控範圍內試用、assess 是值得研究、hold 是暫緩。

> [!warning] 常見誤解
> 「我們只用最成熟的技術，所以不用追趨勢。」不追也是一種選擇，但它有成本：協定的 deprecated 功能會在你不注意時被移除，模型換代會讓你的 harness 元件悄悄變成負擔，而競爭對手可能用你沒評估過的做法把成本降了一半。追蹤的目的不是追新，而是讓「不採用」也是一個有證據的決定。

## 46.13 動手做：技術雷達與 harness ablation 排程

這一節實作兩個工具。第一個是技術雷達：輸入每項候選技術的外部證據等級、自家 eval 的配對結果、遷移成本與能否退回，輸出 adopt／trial／assess／hold 與理由。第二個是 harness 元件的 ablation 排程與報告：依模型世代與上次 ablation 的時間決定這一輪要驗證哪些元件，用 ScriptedModel 跑一個縮小版的青鳥客服 eval，一次拿掉一個元件，判斷它是承重、負擔還是有害。

### 技術雷達：證據、eval 與遷移成本

雷達程式的核心是 `paired_ci`：同一組題目上，舊版與新版各得一個 0／1 結果，對「題目」做 bootstrap 重抽樣，得到改善幅度的 95% 信賴區間。配對很重要，因為題目難度差異很大；如果兩個版本各自抽不同的題，難度差異就會混進結果。為了讓程式可以離線重現，`simulate` 用固定 seed 產生配對的 eval 結果，實務上這裡換成第 27 章的 eval harness。

```python
from __future__ import annotations

import random
from dataclasses import dataclass, field

# 外部證據階梯：只看「別人說了什麼、怎麼證明的」，還不涉及你自己的任務
EVIDENCE = {0: "宣傳或 demo", 1: "廠商自報數字", 2: "可重現的公開實驗", 3: "多方獨立採用或複現"}


@dataclass
class Candidate:
    name: str
    evidence: int                       # 0–3，見 EVIDENCE
    migration_weeks: float              # 估計遷移成本（人週）
    reversible: bool                    # 能不能用 feature flag 一鍵退回
    baseline: list[int] = field(default_factory=list)    # 自家 eval：每題 0／1（同一組題目）
    candidate: list[int] = field(default_factory=list)   # 換上新技術後，同一組題目的結果
    cost_ratio: float = 1.0             # 每題平均成本：新／舊


def paired_ci(base: list[int], cand: list[int], seed: int = 46, rounds: int = 2000) -> tuple[float, float, float]:
    """配對 bootstrap：每次重抽「題目」，兩個版本一起抽，避免題目難度差異混進結果。"""
    rng = random.Random(seed)
    diffs = [c - b for b, c in zip(base, cand)]
    means = sorted(sum(rng.choice(diffs) for _ in diffs) / len(diffs) for _ in range(rounds))
    return sum(diffs) / len(diffs), means[int(rounds * 0.025)], means[int(rounds * 0.975)]


def classify(c: Candidate) -> tuple[str, str]:
    if not c.baseline:                                    # 還沒有自家 eval 的資料
        if c.evidence >= 2:
            return "assess", "外部證據夠，值得花時間建 eval 驗證"
        return "hold", "只有宣傳或自報數字，先觀察"
    delta, lo, hi = paired_ci(c.baseline, c.candidate)
    cheap = c.migration_weeks <= 2 or c.reversible
    if hi < 0:
        return "hold", f"自家 eval 變差 {delta:+.1%}（CI {lo:+.1%}～{hi:+.1%}）"
    if lo > 0:                                            # 改善在統計上站得住
        if c.cost_ratio > 1.5 and delta < 0.10:
            return "trial", f"改善 {delta:+.1%} 但成本 ×{c.cost_ratio}，先小範圍試"
        if cheap:
            return "adopt", f"改善 {delta:+.1%}（CI {lo:+.1%}～{hi:+.1%}），遷移可退回"
        return "trial", f"改善 {delta:+.1%}，但遷移 {c.migration_weeks} 週且難退回，先試點"
    return ("trial" if cheap else "assess"), f"差異 {delta:+.1%} 未達顯著（CI {lo:+.1%}～{hi:+.1%}）"


def simulate(n: int, p_base: float, p_cand: float, seed: int) -> tuple[list[int], list[int]]:
    """產生可重現的配對 eval 結果（真實情境中，這裡換成跑你自己的 eval harness）。"""
    rng = random.Random(seed)
    pairs = []
    for _ in range(n):
        u = rng.random()                                  # 同一個 u：同一題的難度對兩個版本相同
        pairs.append((int(u < p_base), int(u < p_cand)))
    return [b for b, _ in pairs], [c for _, c in pairs]


b1, c1 = simulate(60, 0.62, 0.80, seed=1)    # 報表查詢改成 code-as-action
b2, c2 = simulate(60, 0.78, 0.80, seed=2)    # 換一個新的 reranker
b3, c3 = simulate(60, 0.85, 0.70, seed=3)    # 託管 runtime 的預設 harness，跑青鳥客服題
b4, c4 = simulate(60, 0.70, 0.86, seed=4)    # 協定新版：多輪輸入改成 input_required
radar = [

    Candidate("新 reranker", 2, 1, True, b2, c2),
    Candidate("託管 runtime 預設 harness", 2, 6, False, b3, c3),
    Candidate("協定新版遷移", 3, 4, False, b4, c4),

    Candidate("『全自主自我修復』平台", 0, 8, False),
]
rings: dict[str, list[str]] = {}
for c in radar:

    print(f"{ring:<7}{c.name}｜證據：{EVIDENCE[c.evidence]}｜{why}")
print()
for ring in ("adopt", "trial", "assess", "hold"):
    print(f"{ring:>6}：{'、'.join(rings.get(ring, [])) or '（無）'}")

assert "『全自主自我修復』平台" in rings["hold"] and "託管 runtime 預設 harness" in rings["hold"]
assert classify(radar[3])[0] == "trial"
```

逐行看輸出。code-as-action 報表查詢的外部證據在第 3 階，自家 eval 改善約 17 個百分點，信賴區間的下界也明顯大於 0，加上成本只有原本的六成、能用 feature flag 退回，所以進 adopt。新 reranker 平均改善約 3 個百分點，但信賴區間下界碰到 0，代表在 60 題的規模下分不出是真的改善還是運氣；因為它便宜又可退回，放進 trial，讓更多流量累積證據。託管 runtime 的預設 harness 外部證據不差，但在青鳥的客服題上變差約 12 個百分點，信賴區間整段在 0 以下，所以是 hold；注意 hold 的是「預設 harness」，不是託管服務本身，這正是 46.5 節說的「預設值與你調過的設定要分開評估」。

協定新版遷移的改善是顯著的，但遷移要四週而且難以退回，所以是 trial：先在一兩個整合上試點，而不是一次全部換掉。這也點出雷達的一個限制：協定的 deprecated 功能終究會被移除，有些遷移不是「要不要」而是「何時」，雷達只能幫你決定節奏。自動 prompt 優化有可重現的公開實驗但還沒跑自家 eval，所以是 assess，意思是值得花時間建題驗證。最後，「全自主自我修復」平台只有 demo，沒有任何可驗證的數據，直接 hold。

這個工具刻意把決策規則寫成幾行 if，而不是一個加權分數。原因是加權分數會讓「證據很弱但 demo 很驚豔」與「證據很強但改善很小」得到相同的分數，而這兩者需要完全不同的行動。規則化的另一個好處是可以審查：當阿哲問「為什麼這個是 trial」，答案就是輸出那一行的理由。實務上你可以把門檻（多少週算便宜、成本增加多少要先試點）做成團隊共同認可的設定，每季檢討一次。

### harness 元件的 ablation 排程與報告

第二個程式把 46.4 節的狀態機落地。每個元件都登記了它的假設、為哪一代模型加入、上次 ablation 日期與成本。`due` 決定這一輪要驗證哪些元件：模型世代變了，或距離上次 ablation 超過 90 天。eval 用 ScriptedModel 模擬「新一代模型在某組 prompt 規則下的行為」，跑三個縮小版的青鳥客服題：查訂單、物流一直回「查詢中」、對已出貨訂單退款。

```python
from __future__ import annotations

import json
from dataclasses import dataclass, field
from datetime import date
from typing import Any, Callable


@dataclass
class ToolCall:
    id: str
    name: str
    args: dict[str, Any]


@dataclass
class ModelResponse:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    stop_reason: str = "end_turn"
    usage: dict[str, int] = field(default_factory=lambda: {"input_tokens": 0, "output_tokens": 0})


class ScriptedModel:
    def __init__(self, script: list[ModelResponse | Callable[[list[dict]], ModelResponse]]):
        self.script = list(script)
        self.calls: list[list[dict]] = []

    def complete(self, messages: list[dict], tools: list[dict] | None = None, system: str = "") -> ModelResponse:
        self.calls.append(json.loads(json.dumps(messages)))
        if not self.script:
            raise RuntimeError("劇本已用完：agent 呼叫模型的次數比預期多")
        step = self.script.pop(0)
        return step(messages) if callable(step) else step


def call(name: str, call_id: str = "c1", **args: Any) -> ModelResponse:
    return ModelResponse(tool_calls=[ToolCall(call_id, name, args)], stop_reason="tool_use")


def say(text: str) -> ModelResponse:
    return ModelResponse(text=text)


@dataclass
class Component:
    name: str
    assumption: str          # 這個元件在補哪個模型弱點：每個元件都必須寫得出來
    tuned_for: str           # 當初為哪一代模型加的
    last_ablation: date
    prompt_tokens: int = 0   # 放進 system prompt 的成本（每一步都要付）
    step_tokens: int = 0     # 每一步額外的處理成本（例如摘要）


ORDERS = {"B-1": "paid", "B-3": "shipped"}
TOOLS = {
    "get_order": lambda order_id: {"status": ORDERS[order_id]},
    "get_shipment": lambda tracking: {"state": "查詢中"},     # 物流商一直回「查詢中」
    "refund": lambda order_id: {"accepted": True},           # 非同步受理，不代表真的退成
}


def last_tool(msgs: list[dict]) -> str:
    return msgs[-1]["content"] if msgs[-1]["role"] == "tool" else ""


# 劇本模擬「新一代模型在某組 prompt 規則下的行為」，所以接收啟用中的 prompt 規則
TASKS: dict[str, tuple[Callable[[set[str]], list], Callable[[str], bool]]] = {
    "查訂單": (lambda rules: [call("get_order", order_id="B-1"),
                           lambda m: say("已查到。" if "brevity_rule" in rules else "訂單 B-1 已付款，待出貨。")],
            lambda text: "已付款" in text),
    "物流卡住": (lambda rules: [lambda m: say("物流仍在查詢中，建議明天再查。") if "重複" in last_tool(m)
                              else call("get_shipment", f"c{len(m)}", tracking="TC-1")] * 8,
             lambda text: "明天" in text),
    "已出貨退款": (lambda rules: [call("refund", order_id="B-3"),
                              lambda m: say("此單已出貨，無法直接退款，已改建退貨單。") if "refunded=False" in last_tool(m)
                              else say("已為您退款。")],
              lambda text: "無法" in text),
}


def run(task: str, enabled: dict[str, Component], max_steps: int = 6) -> tuple[bool, int]:
    script, check = TASKS[task]
    model = ScriptedModel(script(set(enabled)))
    messages: list[dict] = [{"role": "user", "content": task}]
    tokens, seen = 0, {}
    for _ in range(max_steps):
        tokens += 300 + sum(c.prompt_tokens + c.step_tokens for c in enabled.values())
        tokens += len(json.dumps(messages, ensure_ascii=False)) // 4
        resp = model.complete(messages)
        messages.append({"role": "assistant", "content": resp.text,
                         "tool_calls": [{"id": t.id, "name": t.name, "args": t.args} for t in resp.tool_calls]})
        if not resp.tool_calls:
            return check(resp.text), tokens
        for tc in resp.tool_calls:
            out = json.dumps(TOOLS[tc.name](**tc.args), ensure_ascii=False)
            key = (tc.name, json.dumps(tc.args, sort_keys=True))
            seen[key] = seen.get(key, 0) + 1
            if "repeat_guard" in enabled and seen[key] >= 2:
                out += f"［harness］相同呼叫已重複 {seen[key]} 次且結果沒變，請換做法或告知使用者。"
            if "verify_refund" in enabled and tc.name == "refund":
                out += f"［harness 驗證］refunded={ORDERS[tc.args['order_id']] == 'paid'}"
            messages.append({"role": "tool", "tool_call_id": tc.id, "name": tc.name, "content": out})
    return False, tokens                                   # 步數用完：算失敗


def evaluate(enabled: dict[str, Component]) -> tuple[float, int]:
    results = [run(t, enabled) for t in TASKS]
    return sum(ok for ok, _ in results) / len(results), sum(tok for _, tok in results)


def due(components: list[Component], current_model: str, today: date, max_age_days: int = 90) -> list[Component]:
    """換了模型世代，或距離上次 ablation 太久，就排入這一輪。"""
    return [c for c in components if c.tuned_for != current_model or (today - c.last_ablation).days > max_age_days]


HARNESS = [
    Component("repeat_guard", "模型會用相同參數反覆查詢", "gen-B", date(2026, 9, 1)),
    Component("verify_refund", "模型會把『受理』當成『完成』", "gen-A", date(2026, 3, 2)),
    Component("context_reset", "模型接近 context 上限會草率收尾", "gen-A", date(2026, 2, 1), step_tokens=120),
    Component("verbose_rules", "模型需要冗長的禁止事項清單", "gen-A", date(2026, 2, 1), prompt_tokens=400),
    Component("brevity_rule", "模型回覆太囉嗦", "gen-A", date(2026, 5, 10), prompt_tokens=30),
]
today, model = date(2026, 10, 1), "gen-B"
queue = due(HARNESS, model, today)
print("本輪 ablation：", "、".join(c.name for c in queue))
full = {c.name: c for c in HARNESS}
base_pass, base_tok = evaluate(full)
print(f"完整 harness：通過率 {base_pass:.0%}，tokens {base_tok}\n")
verdicts = {}
for comp in queue:
    p, tok = evaluate({k: v for k, v in full.items() if k != comp.name})
    saved = 1 - tok / base_tok
    if p < base_pass:
        verdicts[comp.name] = "load-bearing：保留，更新 last_ablation"
    elif p > base_pass:
        verdicts[comp.name] = "有害：拿掉反而變好，優先移除"
    elif saved >= 0.05:
        verdicts[comp.name] = "dead weight：排入移除（先 canary）"
    else:
        verdicts[comp.name] = "中性：保留觀察"
    print(f"拿掉 {comp.name:<14} 通過率 {p:>4.0%}（{p - base_pass:+.0%}）  省 tokens {saved:>4.0%}  → {verdicts[comp.name]}")
    print(f"   假設：{comp.assumption}（為 {comp.tuned_for} 加入）")

assert [c.name for c in queue] == ["verify_refund", "context_reset", "verbose_rules", "brevity_rule"]
assert verdicts["verify_refund"].startswith("load-bearing")
assert verdicts["context_reset"].startswith("dead") and verdicts["verbose_rules"].startswith("dead")
assert verdicts["brevity_rule"].startswith("有害")
```

第一行是排程結果。`repeat_guard` 不在清單裡，因為它是為目前這一代模型（gen-B）加的，上個月才驗證過；其他四個元件都是為上一代模型加的，換代之後必須重新驗證。第二行是完整 harness 的基準：三題只通過兩題，這件事本身就值得注意，ablation 不只能找出可以拿掉的元件，也能找出正在傷害你的元件。

接著是四個 ablation 結果。拿掉 `verify_refund` 後，已出貨退款題失敗了：模型看到「受理」就告訴使用者「已為您退款」，這正是故事中 canary 抓到的回歸，所以它是承重元件，保留並更新驗證日期。拿掉 `context_reset` 與 `verbose_rules`，通過率不變，分別省下約 13% 與 44% 的 token，判定為 dead weight，排入移除，但要先過 canary。拿掉 `brevity_rule` 反而讓通過率升到 100%：這條「回覆要精簡」的規則讓模型在查訂單時省略了訂單狀態，被 outcome grader 判為失敗。它是為上一代模型的囉嗦而加的，對新模型則變成干擾，判定為有害、優先移除。

這個程式為了能在幾毫秒內跑完，只有三題、每題一次，而且劇本是寫死的。真實的 ablation 至少要注意四件事。第一，題目要有數十到數百題，每題多跑幾次，用上一個程式的配對信賴區間判斷差異，而不是看單一數字。第二，一次只拿掉一個元件只能找出「單獨」的效果；兩個元件可能互相補位，拿掉其中一個沒事、兩個一起拿掉就出事，所以決定移除多個元件後，要對「全部移除後」的設定再跑一次。第三，安全元件（egress 限制、核准、權限檢查）不參與這個流程，理由見 46.10 節。第四，判定為 dead weight 不等於立刻刪除：先在 canary 或 shadow 流量上觀察一段時間，確認線上指標沒有回歸，才真正移除，並保留設定開關。

| 判定 | 條件 | 下一步 | 常見例子 |
|---|---|---|---|
| 承重 | 拿掉後 eval 下降 | 保留，更新驗證日期 | 結果驗證、重複偵測 |
| dead weight | eval 不變，且省下可觀成本 | 排入移除，先 canary | 舊模型需要的 context reset、冗長規則 |
| 有害 | 拿掉後 eval 上升 | 優先移除，查清楚何時引入 | 過時的長度限制、強迫格式 |
| 中性 | eval 不變，成本差異小 | 保留，下次再看 | 便宜的格式提示 |
| 不參與 | 安全與政策元件 | 用安全 regression eval 另外驗證 | egress、核准、權限交集 |

這張表是 ablation 報告的判讀規則，也可以直接當成 `loom` 中這個排程工作的設定說明。

## 46.14 實務應用

**情境一：電商客服平台的模型換代（青鳥的主線）**。客服 agent 對一致性的要求最高，所以換模型時不能只看新模型的公開分數，而要依 46.12 節的流程走：先用 regression suite 跑 pass^k，再對所有為舊模型加入的 harness 元件做 ablation，然後才在 canary 上逐步放量。青鳥把這個流程寫成換代時的固定 runbook，結果是每次換代大約要兩週，但從此沒有再發生「換了模型、退款話術出錯」的事故。公開資料中，模型廠商自己的事故檢討也採取同樣的教訓：可能和品質互相取捨的改動，要經過 soak period、per-model eval 與漸進 rollout。

**情境二：企業內部 coding agent 平台的技術雷達**。一家有數百位工程師的公司，每個月都有人提議導入新的 coding agent、新的 MCP server 或新的 code review 工具。平台團隊用技術雷達作為唯一的進門流程：任何提議都要填外部證據等級，並在公司內部的 benchmark（從過去的真實 PR 與事故建成，第 28 章）上跑配對比較。這讓討論從「我覺得這個比較好」變成「在我們的 200 題上改善多少、信賴區間是多少」。主流 coding agent 的公開做法也支持這個方向：它們普遍提供可在自家環境執行的 headless 模式與 CI 整合，讓企業能用自己的題目評估。

**情境三：金融或保險業的協定與支付整合**。受監管的產業最在意可稽核與可回復。當支付協定還在 beta 或 0.x 階段時，合理的做法是只在 `loom` 中實作「付款中斷加核准」的抽象，並在沙盒或測試金流中試點一套協定，正式交易仍走既有的人工核准流程。協定穩定、第三方稽核報告出來之後，再依雷達把它從 assess 移到 trial。公開資料中，商務協定的設計普遍讓商家仍是交易責任方、支付憑證不經過 agent，這正好對應本書「secrets 不進 sandbox（第 17 章）、核准綁定參數（第 21 章）」的原則。

**情境四：研究與分析團隊的長任務 agent**。營運分析或市場研究 agent 的任務越來越長，常常一跑就是數小時。這類團隊最值得導入的是 46.3 節的過程中驗證與 46.7 節的 code-as-action：前者讓長任務不會在第三小時因為第一小時的錯誤而作廢，後者讓大量資料留在 sandbox 裡。公開的 deep research 系統普遍採用「先規劃、平行搜尋、最後綜合並附引用」的架構（第 40 章），並把引用驗證當成獨立的步驟，這就是一種分布在過程中的驗證點。

| 情境 | 最相關的趨勢 | 最大的開放問題 | 進門流程的重點 |
|---|---|---|---|
| 客服平台換代 | harness 元件過時 | 可靠性（pass^k） | regression suite＋ablation＋canary |
| 企業 coding 平台 | 託管服務、code-as-action | 評估 | 內部 benchmark 配對比較 |
| 金融支付整合 | 協定標準化、agent 支付 | 責任歸屬 | 只實作抽象，沙盒試點 |
| 研究分析 agent | 自主時間變長、code-as-action | 評估、可靠性 | 過程中驗證、引用檢查 |

這張表說明同一套方法在不同產業的重點不同：客服重一致性，coding 重評估規模，金融重責任與稽核，研究重長任務的中途驗證。

## 46.15 設計檢查清單

每季的技術回顧，或每次換模型、換協定、換服務之前，逐項回答下面的問題。

1. 每一項新技術的提議，是否都標了屬於哪一層（原理、抽象、協定、產品、數字）？
2. 提議是否對應到 error analysis 或成本分析中的一個具體問題？如果沒有，是否先放進 hold？
3. 外部證據到證據階梯的第幾階？引用的數字是否附了 benchmark 版本、harness 與日期？
4. 自家 eval 的比較是否在同一組題目上配對進行、每題多次 trial，並報告信賴區間？
5. 遷移成本估算了嗎？能不能用 feature flag 一鍵退回？不能退回的是否先試點？
6. 每個 harness 元件是否登記了假設、為哪一代模型加入、上次 ablation 的日期？
7. 換模型是否會自動觸發 ablation 排程，而不只是改一行設定？
8. 判定為可移除的元件，是否先經過 canary 或 shadow 驗證，並保留設定開關？
9. 安全與政策元件是否排除在自動移除流程之外，並有獨立的安全 regression eval？
10. 使用託管服務時，session log 與 trace 是否能以標準格式匯出？政策引擎是否留在自己的 gateway？
11. 每個協定整合是否包在 adapter 後面、釘住版本、有契約測試？是否追蹤 deprecation 清單？
12. 付款或其他不可逆的對外動作，是否一律走中斷加核准，且模型碰不到憑證與上限設定？
13. 對五個開放問題，系統是否都設計成「即使問題一直沒被解決，也能安全運作」？

## 46.16 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 換了更強的模型，某類任務反而變差 | 為舊模型加的 harness 元件或 prompt 規則干擾新模型 | 對換代前加入的元件逐一 ablation | 依 46.13 節移除有害元件，先 canary |
| 刪掉「看似多餘」的提醒後出現回歸 | 元件其實承重，只是沒有被量測過 | 比對刪除前後的 regression eval 與線上指標 | 回復元件，補上 eval 題目並登記假設 |
| 導入新工具後，團隊說不清是否有幫助 | 沒有基準、沒有配對比較 | 檢查導入前是否有同一組題目的結果 | 補跑舊版本，建立配對比較流程 |
| 協定升級後整合在 production 壞掉 | 沒有釘版本、沒有契約測試，或忽略 deprecation | 查升級紀錄與規格 changelog | adapter 隔離、版本釘選、升級前跑契約測試 |
| 想換託管服務卻搬不走 | trace 與 session 只存在服務商端 | 試著匯出一個完整 session 並在本地重建 | 架構上加一份標準格式的 log 副本 |
| 評估分數上升，但使用者投訴增加 | eval 題目過時或被「刷題」，outcome 沒被檢查 | 抽樣讀 transcript，比對 outcome | 從新的事故補題、改用 outcome grader、防作弊 |
| 因為新模型「更安全」而放寬 egress | 把模型層的改善當成架構邊界 | 跑安全 regression eval 與 trifecta 檢查 | 恢復確定性邊界，分類器只當第二道防線 |
| 每週都在追新框架，產品沒有進展 | 沒有進門流程，以消息驅動而非問題驅動 | 數一數這一季導入且有 eval 證據的項目 | 建立技術雷達，季度集中評估 |

## 本章重點整理

- 知識有不同的半衰期：原理以年計，版本與分數以月計；半衰期越短的東西，越要放在越容易替換的位置。
- 模型能自主工作的時間變長，使 durable log、過程中的驗證點、非同步 UX 與里程碑式的人工檢查點成為長任務的必要元件。
- 每個 harness 元件都編碼了一個關於模型弱點的假設；模型換代時，元件可能仍承重、變成負擔，甚至有害，只能用 ablation 量測。
- harness 的移除與加入一樣危險，判定為可移除的元件要先經過 canary 或 shadow 驗證，並保留設定開關。
- 託管 agent 服務讓 loop、sandbox 與 session 可以租用，但 eval set、trace 副本、tool、政策與決策紀錄必須自己擁有。
- MCP、A2A、AG-UI 正在標準化但仍有 breaking change；協定要包在 adapter 後面、釘版本、有契約測試並追蹤 deprecation。
- code-as-action 在多個團隊獨立收斂，讓 sandbox 成為核心元件；有副作用的 tool 一律 `code_callable=False`。
- agent 支付是 destructive 動作的極端形式，不論採用哪套協定，都應抽象成「中斷加核准」，模型碰不到憑證與上限。
- 公開 benchmark 會飽和、改版與漂移，外部分數只是「值得用自家 eval 測一次」的理由；自家 eval 是最重要的長期資產。
- 安全是「不變」的趨勢：模型層防禦降低機率，架構層邊界提供保證，而且邊界要隨能力增強而加強。
- 可靠性、長期記憶、prompt injection、評估與責任歸屬仍是開放問題，系統要設計成即使問題一直未解也能安全運作。
- 證據階梯從宣傳、自報數字、可重現實驗、多方採用，到自家 eval 驗證；只有最後一階能決定 adopt。
- 技術雷達的決策應寫成可審查的規則，結合外部證據、配對比較的信賴區間、遷移成本與可退回性。
- 不追蹤也是一種選擇；追蹤的目的是讓「採用」與「不採用」都成為有證據的決定。

## 延伸問答

> [!question]- Q1. 為什麼說「每個 harness 元件都編碼了一個關於模型弱點的假設」？這個想法要怎麼變成團隊的固定流程？
> harness 元件之所以存在，是因為某個時候觀察到模型會犯某種錯：會原地打轉，所以加重複偵測；會把「受理」當成「完成」，所以加結果驗證；會在 context 快滿時草率收尾，所以加 context reset。換句話說，每個元件都是對「這一代模型做不好什麼」的一個賭注。模型換代時，賭注的前提可能已經不成立，元件就從保護變成負擔；有時甚至會干擾新模型的正常行為，變成有害。
>
> 要變成流程，需要三樣東西。第一是登記：每個元件寫明它的假設、為哪一代模型加入、上次驗證日期，寫不出假設的元件本身就值得懷疑。第二是觸發：把「換模型世代」與「距上次驗證超過 N 天」定義成會自動排入 ablation 的事件。第三是判讀與安全網：用配對比較判定承重、負擔或有害，可移除的先過 canary，並保留開關。安全與政策元件則排除在這個流程之外，因為它們的假設是「環境中有攻擊者」，不會隨模型進步失效。

> [!question]- Q2. 一年前青鳥選擇自建 loom，現在託管 agent 服務越來越成熟，要怎麼重新評估 build vs buy？
> 重新評估不是在「全部自建」與「全部託管」之間二選一，而是逐層看。loop 與 sandbox 這類通用的基礎設施，託管服務往往做得更好也更便宜，特別是 sandbox 的隔離與 pool 管理；而 harness 中與產品差異化相關的部分（青鳥調過的客服規則、驗證步驟）、政策與核准、eval 與決策紀錄，則應該留在自己手上。所以合理的結果常常是混合：tool 做成 MCP server 讓兩邊共用，政策留在自己的 gateway，部分 agent 跑在託管服務上。
>
> 判斷依據要用證據而不是印象。用自家 eval 分別跑託管服務的預設 harness 與移植過去的自家設定，比較 pass^k、成本與延遲；估算遷移成本與退回成本；確認 session log 與 trace 能以標準格式匯出，這決定了將來能不能離開。如果託管服務在自家 eval 上不輸、遷移可退回、資料可匯出，就可以把它放進雷達的 trial，從風險最低的 agent 開始試點。

> [!question]- Q3. 一家廠商宣稱它的 agent 平台在某個公開 benchmark 上比你現在的系統高 15 分，你會怎麼判斷要不要導入？
> 先放在證據階梯上看。這是廠商自報的數字，屬於第 ① 階，要追問：用的是 benchmark 的哪個版本、什麼 harness、比較對象是誰、每題跑幾次、成本與 token 算了沒有。公開 benchmark 會飽和與改版，同一模型換 harness 分數可以差很多，所以 15 分本身說明不了它在你的任務上會怎樣。再看它解決的問題是否在你的 error analysis 上：如果你的主要失敗是退款流程的政策遵循，而那個 benchmark 測的是網頁瀏覽，相關性就很低。
>
> 如果外部證據至少到第 ② 階、且對應你的問題，下一步是在自家 eval 上做配對比較：同一組題目、每題多次 trial、看信賴區間與 pass^k，並記錄成本。結果變差就 hold；不顯著就看成本決定 trial 或 assess；顯著改善再看遷移成本與能否退回。整個過程中，「15 分」只扮演一個角色：讓這項技術值得你花時間建 eval。

> [!question]- Q4. 估算題：某個長任務 agent 每步成功率 99.5%，平均 200 步。整體成功率大約多少？如果每 20 步驗證一次、驗證能抓到並修好 80% 的錯誤，會變成多少？
> 假設每步獨立，整體成功率是 0.995 的 200 次方。用 ln(0.995) 約等於 −0.005 估算，200 步是 e 的 −1.0 次方，約 0.37，也就是只有約 37% 的任務能從頭到尾不出錯。這說明單步可靠度看起來很高，長任務的整體可靠度卻會快速衰減。
>
> 加上驗證後，把任務切成 10 段、每段 20 步。每段完全沒出錯的機率是 0.995 的 20 次方，約 0.905；出錯的機率約 0.095，其中 80% 被抓到並修好，所以每段最終成功的機率約 0.905 ＋ 0.095 × 0.8 ≈ 0.981。10 段都成功約為 0.981 的 10 次方，約 0.82。從 37% 到 82%，代價是十次驗證的成本。這個估算假設錯誤獨立、修正不引入新錯誤，真實情況會更複雜，但結論穩定：驗證器的抓錯率與驗證的密度，往往比再提升一點單步可靠度更有效。

> [!question]- Q5. 程式找錯：下面這段 ablation 程式有三個問題，會讓結論不可靠。請指出並說明後果。
> ```python
> base = run_eval(all_components, tasks=random.sample(TASKS, 30))
> for comp in components:
>     score = run_eval(all_components - {comp}, tasks=random.sample(TASKS, 30))
>     if score >= base:
>         remove(comp)
> ```
> 第一個問題是每次 eval 都重新隨機抽 30 題，基準和每個 ablation 用的是不同題組。題目難度差異會直接混進分數，拿掉一個承重元件也可能因為剛好抽到簡單的題而「分數不變」。正確做法是固定同一組題目，做配對比較。第二個問題是每題只跑一次、只比單一分數，`score >= base` 會把隨機波動當成結論；應該每題多次 trial，用配對的信賴區間判斷差異是否顯著。
>
> 第三個問題是判定之後直接 `remove`，而且是在迴圈中逐一移除：沒有 canary 或 shadow 驗證，也沒有考慮元件之間的互相補位。兩個元件各自拿掉都沒事，一起拿掉可能就出事；而且安全元件也被放進同一個自動移除流程。修正方式是：迴圈內只產生「候選移除」清單，對全部候選一起移除後的設定再跑一次 eval，排除安全與政策元件，通過後才進 canary，最後保留設定開關。

> [!question]- Q6. 你依賴的協定把某個功能標成 deprecated，而你的整合大量使用它。你會怎麼處理？
> 先確認時程與替代方案。成熟的規格會有 deprecation 政策，說明功能被標為 deprecated 後至少保留多久，並在 changelog 中建議替代做法；把這個期限當成工單的截止日，而不是等它被移除那天才發現。接著盤點影響範圍：哪些整合用到這個功能、有沒有隱含假設建立在它上面。青鳥遷移 MCP 時花最多時間的，正是找出到處默默依賴「連線有 session」的程式。
>
> 實作上，如果 `loom` 有 adapter 層，遷移應該只動 adapter：在 adapter 裡實作新的替代做法，核心邏輯不變。先為現有行為寫契約測試，確保遷移前後對上層的行為一致，再在一兩個整合上試點（雷達的 trial），確認後全面切換。如果發現核心型別裡出現了協定的欄位名稱，那就是這次遷移最該修的設計問題，因為下一次改版還會再發生。

> [!question]- Q7. 面試追問：請設計一個「新一代模型上線前」的評估流程，要涵蓋品質、成本、安全與 harness。
> 流程可以分成五步。第一步是離線 regression：在固定的 regression suite 上跑新舊模型的配對比較，每題多次 trial，看 pass^k 而不是平均，因為面向使用者的 agent 重一致性；同時記錄 token、延遲與成本，用有版本的價目表計算。第二步是 capability 題：看新模型在舊模型做不好的題目上是否進步，這決定了升級的價值。第三步是安全 regression：prompt injection、越權、外洩相關的題目單獨跑，安全結果不能用整體平均掩蓋。
>
> 第四步是 harness ablation：對所有為舊模型加入的元件，在新模型上逐一拿掉，判定承重、負擔或有害，候選移除的元件組合起來再跑一次。這一步常常能同時降低成本並提升品質。第五步是線上驗證：先 shadow 再 canary，觀察業務指標（退款正確率、轉真人率、使用者回饋）與成本，設定自動回滾條件。整個流程的產出是一份決策紀錄：比較了什麼、結果如何、為什麼上線或不上線，下一次換代時就從這份紀錄開始。

> [!question]- Q8. agent 出錯造成使用者損失時，責任歸屬目前沒有定論。在這種情況下，架構上能預先做什麼？
> 法律與標準還在形成，但不論最後的答案是什麼，判斷責任都需要事實：誰授權了什麼範圍、agent 根據哪些輸入做了哪個動作、哪一步的保護機制應該攔下卻沒有攔下。所以架構上能做的，是讓這些事實在事後可以被完整、可信地重建。具體包括：有效權限是使用者、agent 與任務範圍的交集，並記錄在每次動作上；不可逆動作的核准綁定參數 hash，執行時不符即拒絕；稽核日誌 append-only 並以 hash chain 防竄改；trace 中記錄業務結果與宣稱，而不只是技術成敗。
>
> 另一部分是把責任邊界設計進產品：不可逆或金額較大的動作永遠要人核准，讓「誰做了決定」清楚；授權有範圍與期限，讓「agent 被允許做什麼」清楚；對使用者揭露 agent 的能力與限制，讓期待清楚。這些設計不只是為了事後追責，它們同時降低了出錯的機率與損害。能重建事實、邊界清楚的系統，在任何一種責任歸屬的規則下都站得住。
