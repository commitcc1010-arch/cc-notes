# 第 16 章　系統內的名稱解析與服務發現

> [!abstract] 本章地圖
> **核心問題**：程式呼叫 `connect("api.shengsheng.example")` 之後，在送出第一個 DNS 封包之前與之後，作業系統、語言 runtime 與容器平台各自做了什麼決定？
>
> **你會學到**：
> - 說出 `getaddrinfo` 從應用程式到 recursive resolver 的完整路徑，並用 `getent` 而不是 `dig` 驗證「程式實際看到的答案」
> - 讀懂並調整 `/etc/hosts`、`nsswitch.conf`、`resolv.conf`（nameserver、search、ndots、timeout、attempts）
> - 手算 search domain 與 ndots 的展開順序，算出一次解析實際發出幾個 DNS 請求，並解釋 Kubernetes `ndots:5` 的代價
> - 找出 runtime 與連線池造成「DNS 已切換，程式還連舊 IP」的原因，並設計修正方式
> - 比較 DNS、registry、平台內建與 service mesh 四種服務發現模式的取捨
> - 用 DNS-01 與 TXT record 證明網域所有權，並避開傳播與權限的常見陷阱
>
> **前置知識**：第 14 章（DNS 階層、stub 與 recursive resolver、record types、TTL）、第 15 章（negative caching、split-horizon DNS）、第 9 章與第 10 章（UDP、TCP 與 socket API）

## 16.1 故事：搬上 Kubernetes 之後，DNS 變成瓶頸

聲聲 Live 把 Flask API 與即時服務從虛擬機搬進 Kubernetes 的第二週，平台工程師阿德在 dashboard 上看到一條不對勁的曲線：叢集內 CoreDNS 的每秒查詢數從搬家前估計的兩千左右漲到九千以上，其中超過七成的回應是 NXDOMAIN（名稱不存在）。服務本身沒有變多，使用者也沒有暴增，DNS 流量卻多了好幾倍。

同一週還發生三件事。第一，處理金流 webhook 時，API 要回頭呼叫金流供應商 `pay.example.net` 確認訂單，這個請求偶爾卡住整整 5 秒才送出，重試後又正常；第二，推薦服務 `reco` 做了藍綠切換，DNS 早已指向新版，用 Java 寫的課程排程服務卻在接下來幾個小時繼續打舊版，直到舊版被關掉、排程服務開始大量報錯；第三，資安工程師 Rita 要求把 `*.shengsheng.example` 的 wildcard 憑證改成自動更新，憑證機構卻說 wildcard 只能用「DNS 驗證」，沒有人知道那是什麼。

剛入職的小晴被分到第一個問題。小晴先在筆電上跑 `dig pay.example.net`，答案正常、延遲只有十幾毫秒，於是回報「DNS 沒問題」。阿德看了只說一句：「`dig` 不會走你程式走的那條路。」接著請小晴進到 Pod 裡看 `/etc/resolv.conf`，最後一行寫著 `options ndots:5`。

這一章就是要把「程式要一個名字，系統怎麼把它變成 IP」這段路完整攤開。第 14 章講的是 DNS 封包在網路上怎麼跑；本章往回看到封包送出之前的那一段：libc 的 `getaddrinfo`、`/etc/hosts`、`nsswitch.conf`、`resolv.conf` 的每個選項、語言 runtime 的快取、連線池，以及容器平台加上的 search domain。不懂這一段，就會像小晴一樣，用一個繞過所有本機規則的工具，去證明一條自己根本沒走的路是好的。

## 16.2 從 connect 到 IP：getaddrinfo 的旅程

大多數程式不會自己組 DNS 封包。Python 的 `socket.create_connection(("api.shengsheng.example", 443))`、Java 的 `InetAddress.getByName`、curl、ssh，最後都會呼叫作業系統 C 函式庫提供的 **`getaddrinfo`**：一個「給我主機名稱與服務名稱，還你一串可以直接拿去建立 socket 的位址」的函式。例如輸入 `("localhost", 8080)`，它可能回傳兩筆：IPv6 的 `::1` 埠 8080，與 IPv4 的 `127.0.0.1` 埠 8080。

```text
  應用程式：requests.get("https://api.shengsheng.example/")
        │
        ▼
  語言 runtime（Python socket／JVM InetAddress／Node dns.lookup）
        │   有些 runtime 在這裡先查自己的快取（例如 JVM）
        ▼
  libc：getaddrinfo(host, service, hints)
        │   1. 若 host 是數字位址 → 直接轉換，不查任何東西
        │   2. 讀 /etc/nsswitch.conf 的 hosts 行，決定來源順序
        ▼
  ┌──────────────┬────────────────┬───────────────────┐
  │ files        │ dns            │ mdns／resolve／...  │
  │ /etc/hosts   │ 讀 resolv.conf  │ 其他外掛模組          │
  └──────────────┴───────┬────────┴───────────────────┘
                         │ 套用 search、ndots，送出 A 與 AAAA 查詢
                         ▼
          nameserver（本機 stub、node-local cache、CoreDNS、VPC resolver）
                         │
                         ▼
          recursive resolver ──► root／TLD／authoritative（第 14 章）
        ▲
        │ 回傳：多筆 (family, type, proto, canonname, sockaddr)
        │ 依 RFC 6724 規則與 /etc/gai.conf 排序
  應用程式依序嘗試 connect，第一個成功的就用
```

這張圖由上往下讀。第一層是應用程式，只知道一個名稱。第二層是語言 runtime，大多數直接把名稱交給 libc，但有些會先查自己的快取，這是 16.6 節「舊 IP」問題的來源之一。第三層 libc 的 `getaddrinfo` 先判斷輸入是不是數字位址，是的話直接轉換，完全不碰網路；不是的話讀 `nsswitch.conf`，決定要依序問哪些來源。只有輪到 `dns` 來源時，才會讀 `resolv.conf`、套用 search domain 與 ndots、真正送出 DNS 封包。最後回傳的是一個**清單**而不是單一 IP，排序由 libc 依 RFC 6724 的位址選擇規則決定，應用程式應該依序嘗試。

`getaddrinfo` 的第三個參數 **hints** 是「我只要哪一種結果」的過濾條件。常用的欄位有：`family`（`AF_INET` 只要 IPv4、`AF_INET6` 只要 IPv6、`AF_UNSPEC` 兩種都要）、`socktype`（`SOCK_STREAM` 給 TCP、`SOCK_DGRAM` 給 UDP）、以及 flags。flags 裡最實用的有四個：`AI_PASSIVE` 表示「我要 bind 當 server」，host 給 None 時回傳 `0.0.0.0` 或 `::`；`AI_NUMERICHOST` 表示「host 一定是數字位址，不准查名稱」；`AI_ADDRCONFIG` 表示「本機沒有設定 IPv6 位址就不要回 IPv6 結果」；`AI_CANONNAME` 會把 CNAME 追到底的正式名稱放進結果。

`family=AF_UNSPEC` 有一個常被忽略的效果：對 DNS 來源來說，每個要查的名稱都得同時問 A 與 AAAA 兩種 record，請求數直接變兩倍。glibc 預設把這兩個查詢從同一個 UDP socket 幾乎同時送出，這個「同時」在 16.7 節會變成 Kubernetes 上 5 秒延遲的元兇之一。

| 誰在解析 | 走 getaddrinfo？ | 讀 /etc/hosts？ | 自己快取？ | 備註 |
|---|---|---|---|---|
| Python `socket` | 是 | 依 nsswitch | 否 | asyncio 的 `getaddrinfo` 丟到 thread pool 執行 |
| JVM `InetAddress` | 是（透過 JDK 原生程式） | 依 nsswitch | 是 | 成功結果預設快取約 30 秒，見 16.6 節 |
| Node.js `dns.lookup` | 是 | 依 nsswitch | 否 | 在 libuv thread pool 執行，pool 小時會排隊 |
| Node.js `dns.resolve4` | 否，直接送 DNS | 否 | 否 | 用 c-ares，繞過 `/etc/hosts` 與 nsswitch |
| Go `net`（pure Go resolver） | 否，自己讀設定檔 | 是 | 否 | 可用 `GODEBUG=netdns=cgo` 改走 libc |
| `dig`、`nslookup`、`host` | 否 | 否 | 否 | 直接對 nameserver 送 DNS，用來測 DNS 本身 |
| `getent hosts`、`getent ahosts` | 是 | 依 nsswitch | 否 | 用來重現「程式看到的答案」 |

這張表是本章最重要的除錯依據。`dig` 是一把專門測 DNS 伺服器的工具，它不看 `/etc/hosts`、不看 nsswitch，甚至預設不套用 search domain（要加 `+search`）。所以「`dig` 正常、程式卻失敗」的情況，問題常常出在 `dig` 跳過的那幾層。在 Linux 上要模擬程式的視角，用 `getent ahosts api.shengsheng.example`，它走的就是 `getaddrinfo` 與 nsswitch 這一條路。

> [!warning] 常見誤解
> 「名稱解析就是 DNS。」其實 DNS 只是 `getaddrinfo` 的其中一個來源。`/etc/hosts`、mDNS（區域網路裡 `.local` 結尾的名稱）、systemd-resolved、LDAP 都可能先回答，DNS 甚至可能完全沒被問到。

最後一個細節是**排序與嘗試**。`getaddrinfo` 回傳多筆位址時，libc 會依 RFC 6724 排序：同類型的位址優先、範圍（scope）相符的優先，在常見設定下 IPv6 排在 IPv4 前面。Python 的 `socket.create_connection` 會依序嘗試每一筆，直到成功；瀏覽器與 curl 則用 **Happy Eyeballs**（RFC 8305）：IPv6 先送出連線，隔一小段時間還沒成功就同時試 IPv4，誰先成功用誰，避免 IPv6 路徑壞掉時使用者要等完整的 TCP 逾時。只拿清單第一筆、失敗就放棄的程式，在 dual stack 環境裡會出現「有時候連得上、有時候連不上」的怪現象。

## 16.3 /etc/hosts 與 nsswitch：誰先回答

**`/etc/hosts`** 是最古老的名稱來源：一個純文字檔，每行一個 IP，後面接一個或多個名稱。在 DNS 出現之前，整個網際網路共用一份這樣的清單；今天它主要用來定義 `localhost`、本機名稱，以及開發測試時的臨時覆寫。例如 `10.20.3.16 api.shengsheng.example` 會讓這台機器上的程式把 API 名稱解析到內部測試機，完全不問 DNS。

**`/etc/nsswitch.conf`**（Name Service Switch）決定 libc 查詢各種名稱資料時，要依序問哪些來源。和本章相關的是 `hosts:` 這一行。一行典型的 Ubuntu 桌機設定是 `hosts: files mdns4_minimal [NOTFOUND=return] dns`，意思是先查 `/etc/hosts`（files），再問 mDNS，若 mDNS 明確說「找不到」就停止，否則才問 DNS。中括號裡的 **action** 是「某個來源回某種狀態時要怎麼做」：狀態有 `SUCCESS`、`NOTFOUND`、`UNAVAIL`（來源無法使用）、`TRYAGAIN`（暫時失敗），動作有 `return`（停止並回傳）與 `continue`（繼續問下一個）。

```text
  getaddrinfo("api.shengsheng.example")
        │
        ▼
  hosts: files  mdns4_minimal [NOTFOUND=return]  dns
        │
   ┌────┴──────────┐
   │ files         │ 在 /etc/hosts 找到？──是──► 回傳（DNS 完全沒被問）
   └────┬──────────┘
        │ 否
   ┌────┴──────────┐
   │ mdns4_minimal │ 只處理 *.local 名稱；
   │               │ 是 .local 但找不到 ──► [NOTFOUND=return] 直接失敗
   └────┬──────────┘
        │ 不是 .local（UNAVAIL）→ 繼續
   ┌────┴──────────┐
   │ dns           │ 讀 resolv.conf，套 search／ndots，送出 A＋AAAA
   └────┬──────────┘
        ▼
     回傳結果或 EAI_NONAME（名稱不存在）
```

這張流程圖說明了兩件事。第一，`files` 排在 `dns` 前面，所以 `/etc/hosts` 裡的任何一行都會「蓋掉」DNS，而且沒有 TTL、永不過期。第二，中間的 action 會讓查詢提早結束，例如 `.local` 名稱在 mDNS 找不到時直接失敗，不會再送到 DNS。不同發行版與不同映像檔的 `hosts:` 行差異很大，有的會加上 `resolve [!UNAVAIL=return]`（交給 systemd-resolved），有的加上 `myhostname`（讓本機名稱永遠解析得到）。

使用 systemd 的 Linux 發行版，常見另一種架構：**systemd-resolved** 在本機 `127.0.0.53` 開一個 stub resolver，`/etc/resolv.conf` 只寫 `nameserver 127.0.0.53`，真正的上游 DNS、search domain 與快取都由 systemd-resolved 管理。這時看 `/etc/resolv.conf` 只會看到本機位址，要用 `resolvectl status` 才看得到真正的上游。macOS 又不一樣：多數程式透過 mDNSResponder 解析，`/etc/resolv.conf` 主要是給少數直接讀檔案的工具參考，要看實際生效的設定得用 `scutil --dns`。

下面這段程式把 `/etc/hosts` 與 `resolv.conf` 的格式解析出來，並模擬 `hosts:` 行的順序如何改變答案。範例重現小晴筆電上的狀況：半年前為了測試加在 `/etc/hosts` 的一行，讓 API 名稱一直指向一台內部測試機。

```python
# 解析 resolv.conf 與 nsswitch 的 hosts 行，模擬「應用程式實際看到的解析順序」
import ipaddress

HOSTS = """\
127.0.0.1   localhost
::1         localhost
10.20.3.16  api.shengsheng.example   # 小晴半年前為了測試加的，忘了刪
"""
RESOLV_CONF = """\
nameserver 10.20.0.2
nameserver 10.20.0.3
search shengsheng.example
options ndots:1 timeout:2 attempts:3 rotate
"""
DNS = {"api.shengsheng.example": "203.0.113.80", "www.shengsheng.example": "203.0.113.10"}

def parse_hosts(text):
    table = {}
    for line in text.splitlines():
        line = line.split("#", 1)[0].split()
        if len(line) >= 2:
            ipaddress.ip_address(line[0])            # 格式錯的行會直接報錯，正好提醒
            for name in line[1:]:
                table.setdefault(name.lower(), []).append(line[0])
    return table

def parse_resolv(text):
    conf = {"nameserver": [], "search": [], "ndots": 1, "timeout": 5, "attempts": 2}
    for line in text.splitlines():
        key, *vals = line.split()
        if key == "nameserver":
            conf["nameserver"].append(vals[0])
        elif key == "search":
            conf["search"] = vals                    # 後出現的 search 會蓋掉前面的
        elif key == "options":
            for opt in vals:
                k, _, v = opt.partition(":")
                if k in ("ndots", "timeout", "attempts"):
                    conf[k] = int(v)
    return conf

def lookup(name, nsswitch_hosts):
    hosts = parse_hosts(HOSTS)
    for source in nsswitch_hosts.split():
        if source == "files" and name in hosts:
            return source, hosts[name]
        if source == "dns" and name in DNS:
            return source, [DNS[name]]
    return None, []

conf = parse_resolv(RESOLV_CONF)
print("resolv.conf:", conf)
worst = conf["timeout"] * conf["attempts"] * len(conf["nameserver"])
print(f"所有 nameserver 都沒回應時，單一名稱最壞約等 {worst} 秒（粗略模型，實際依實作而定）")
for order in ("files dns", "dns files"):
    src, addrs = lookup("api.shengsheng.example", order)
    print(f"hosts: {order:<10} -> api.shengsheng.example 來自 {src}: {addrs}")
assert lookup("api.shengsheng.example", "files dns") == ("files", ["10.20.3.16"])
assert lookup("www.shengsheng.example", "files dns")[0] == "dns"
```

```text
resolv.conf: {'nameserver': ['10.20.0.2', '10.20.0.3'], 'search': ['shengsheng.example'], 'ndots': 1, 'timeout': 2, 'attempts': 3}
所有 nameserver 都沒回應時，單一名稱最壞約等 12 秒（粗略模型，實際依實作而定）
hosts: files dns  -> api.shengsheng.example 來自 files: ['10.20.3.16']
hosts: dns files  -> api.shengsheng.example 來自 dns: ['203.0.113.80']
```

第一行是解析出來的設定，注意 `rotate` 不在我們關心的三個數值裡，被略過了。第二行是一個粗略的最壞情況：兩台 nameserver、每台等 2 秒、重試 3 輪，一個名稱最多卡 12 秒；真實的 glibc 在後續輪次會調整每台的等待時間，而且 A 與 AAAA、每個 search 候選都可能各自等待，所以實際數字依實作而定，但數量級是對的。最後兩行是重點：同一個名稱，`files` 在前時得到 `/etc/hosts` 裡的 `10.20.3.16`，`dns` 在前時才得到真正的 API LB `203.0.113.80`。小晴的筆電屬於前者，所以本機測試一直打到測試機，而 `dig` 因為不看 `/etc/hosts`，顯示的卻是正確答案。

## 16.4 resolv.conf：nameserver、search、ndots、timeout、attempts

輪到 `dns` 來源時，libc 的 stub resolver 讀 **`/etc/resolv.conf`**，這個檔案回答三個問題：要問誰（nameserver）、名稱不完整時要補什麼（search 與 ndots）、問不到時要等多久與重試幾次（timeout 與 attempts）。這個檔案通常不是人手寫的：DHCP client、NetworkManager、systemd-resolved、雲端的開機程式、Docker 與 kubelet 都會產生或改寫它，手動修改常在重開機或重建容器後被蓋掉。

```text
# Pod 裡的 /etc/resolv.conf（kubelet 產生）
nameserver 10.96.0.10
search live.svc.cluster.local svc.cluster.local cluster.local compute.internal.example
options ndots:5
```

這是小晴在聲聲 Live 某個 Pod 裡看到的內容，也是後面幾節的主角。第一行指向 CoreDNS 的 Service IP；第二行有四個 search domain，前三個是 Kubernetes 依 Pod 所在的 namespace `live` 產生的，第四個是從節點（雲端虛擬機）的 resolv.conf 繼承來的雲端內部網域（這裡用範例名稱）；第三行把 ndots 設成 5。下表列出 glibc 支援的主要設定與預設值。

| 設定 | 意義 | glibc 預設 | 實務注意 |
|---|---|---|---|
| `nameserver IP` | 要問的 DNS 伺服器，可寫多行 | 沒寫時問本機 | glibc 最多用前 3 台；預設依序問，不是負載分散 |
| `search d1 d2 …` | 名稱「不夠完整」時依序補上的網域 | 由主機名稱推出 | 和 `domain` 互斥，後出現的生效；舊版 glibc 最多 6 個 |
| `options ndots:N` | 名稱裡的點少於 N 個，就先套 search | 1 | 上限 15；Kubernetes 預設給 Pod 設成 5 |
| `options timeout:N` | 等一台 nameserver 回應的秒數 | 5 | 上限 30；第一台掛掉時每次查詢都先白等這麼久 |
| `options attempts:N` | 把整份 nameserver 清單重試幾輪 | 2 | 上限 5 |
| `options rotate` | 每次查詢輪流從不同 nameserver 開始 | 關 | 可分散負載，但讓問題更難重現 |
| `options single-request` | A 與 AAAA 依序送出，不同時送 | 關 | 用來避開某些 NAT／conntrack 的競態 |
| `options single-request-reopen` | A 與 AAAA 用不同 socket 送 | 關 | 同上，16.7 節說明 |
| `options edns0` | 啟用 EDNS(0)，允許較大的 UDP 回應 | 關 | 回應大於 512 bytes 時減少改走 TCP 的次數 |
| `options use-vc` | 一律用 TCP 查詢 | 關 | 少用；某些網路限制 UDP 時的權宜之計 |

表格裡最容易踩雷的是 `nameserver` 與 `timeout` 的組合。很多人以為寫兩台 nameserver 就有「備援」，但 glibc 預設**每次查詢都先問第一台**；第一台沒回應時，要等滿 timeout 才換第二台。下面的時間軸說明第一台掛掉時發生什麼事。

```text
 時間 →   0s        2s        4s
 查詢 1   ├─ 問 10.20.0.2（沒回應）─┤
                   ├─ 問 10.20.0.3 ─► 回應（2.01s 完成）
 查詢 2            ├─ 問 10.20.0.2（沒回應）─┤
                             ├─ 問 10.20.0.3 ─► 回應
 （timeout:2 attempts:3；每一次查詢都重新從第一台開始，每次多等 2 秒）
 若 A 與 AAAA 依序送出，或名稱要展開成多個 search 候選，等待會再疊加
```

這張圖從左往右是時間。查詢 1 先送到 `10.20.0.2`，對方不回應，resolver 等到 2 秒逾時，才把同一個查詢送到 `10.20.0.3`，後者立刻回答；查詢 2 不會記得「第一台壞了」，又從第一台開始，再白等 2 秒。在一個每次請求都要解析名稱、又沒有快取的程式裡，這代表每個 API 呼叫都穩定地慢 2 秒，而監控上看起來只是「上游變慢」。若 timeout 用預設的 5 秒，就會出現「剛好 5 秒」這個很有辨識度的延遲，小晴看到的金流 webhook 卡 5 秒，正是這類線索。

`timeout` 與 `attempts` 的取捨很直接：設太大，nameserver 故障時應用程式會卡很久；設太小，在負載高或封包偶爾遺失時，查詢會過早失敗或重試，反而增加 nameserver 負擔。常見做法是讓本機有一層可靠的快取（systemd-resolved、node-local cache），把 timeout 調成 1 到 2 秒，attempts 保持 2 到 3。除了檔案，glibc 也接受環境變數 `RES_OPTIONS`（覆寫 options）與 `LOCALDOMAIN`（覆寫 search），容器裡的程式偶爾因為帶了這些變數而行為不同，除錯時值得檢查。

另一個常被忽略的是 libc 實作差異。以 Alpine Linux 為基礎的容器映像用的是 **musl** 而不是 glibc：musl 會把查詢**同時**送給所有 nameserver、採用最先回來的答案，不支援 `single-request` 這類選項；舊版 musl 不會在回應被截斷時改用 TCP（較新版本已加入）。同一份 resolv.conf，在 glibc 與 musl 上的行為可能不同，換基礎映像後 DNS 行為改變，要先想到這一點。

## 16.5 search domain 與 ndots 的展開規則

**search domain** 讓人可以只打短名稱。例如 search 清單有 `shengsheng.example`，在終端機打 `ssh db1`，resolver 會先試 `db1.shengsheng.example`。這在辦公室網路與 Kubernetes 裡非常方便：同一個 namespace 的服務只要寫 `chat` 就能找到 `chat.live.svc.cluster.local`。但 resolver 需要一條規則判斷「這個名稱已經完整，還是要補上 search domain」，這條規則就是 **ndots**：名稱裡的點（`.`）少於 ndots 個時，視為短名稱，先套 search；點的數量大於或等於 ndots 時，先當成完整名稱查。

```text
                getaddrinfo(name)
                      │
           name 以「.」結尾？──是──► 只查 name 本身（絕對名稱，不套 search）
                      │否
           name 的點數 ≥ ndots？
             │是                         │否
             ▼                           ▼
   1. 先查 name 本身              1. name + search[0]
   2. 失敗再依序套 search          2. name + search[1] …
                                 n. 最後才查 name 本身
                      │
       每個候選都送 A 與 AAAA（AF_UNSPEC）
       某個候選「名稱存在」就停止；NXDOMAIN 就換下一個
```

這張流程圖有三個分支。最上面的分支是**絕對名稱**：結尾帶點的 `pay.example.net.` 明確表示「從 root 起算的完整名稱」，resolver 不會套任何 search domain。中間的分支是點數夠多的名稱，先原樣查，查不到才套 search。右邊的分支是點數不夠的名稱，先把每個 search domain 都試一遍，最後才查原名。無論哪個分支，只要某個候選的回應表示名稱存在（NOERROR，即使沒有該類型的 record），就停止；只有 NXDOMAIN 才會換下一個候選。

用一段小程式把規則寫成函式，就能手算各種情況。

```python
# 模擬 glibc 風格的 search domain 與 ndots 展開順序
def expand(name, search, ndots):
    """回傳 resolver 會依序嘗試的完整名稱（FQDN，結尾帶點）。"""
    if name.endswith("."):            # 結尾有點：絕對名稱，不套 search
        return [name]
    as_is = name + "."
    with_search = [f"{name}.{d}." for d in search]
    if name.count(".") >= ndots:      # 點夠多：先當完整名稱試
        return [as_is] + with_search
    return with_search + [as_is]      # 點不夠：先套 search，最後才試原名

POD_SEARCH = ["live.svc.cluster.local", "svc.cluster.local", "cluster.local"]
for name, ndots in [("chat", 5), ("api.shengsheng.example", 5),
                    ("api.shengsheng.example", 1), ("api.shengsheng.example.", 5)]:
    order = expand(name, POD_SEARCH, ndots)
    print(f"{name!r} ndots={ndots}: 共 {len(order)} 個候選")
    for i, fqdn in enumerate(order, 1):
        print(f"  {i}. {fqdn}")

assert expand("chat", POD_SEARCH, 5)[0] == "chat.live.svc.cluster.local."
assert expand("api.shengsheng.example", POD_SEARCH, 1)[0] == "api.shengsheng.example."
assert expand("api.shengsheng.example.", POD_SEARCH, 5) == ["api.shengsheng.example."]
```

```text
'chat' ndots=5: 共 4 個候選
  1. chat.live.svc.cluster.local.
  2. chat.svc.cluster.local.
  3. chat.cluster.local.
  4. chat.
'api.shengsheng.example' ndots=5: 共 4 個候選
  1. api.shengsheng.example.live.svc.cluster.local.
  2. api.shengsheng.example.svc.cluster.local.
  3. api.shengsheng.example.cluster.local.
  4. api.shengsheng.example.
'api.shengsheng.example' ndots=1: 共 4 個候選
  1. api.shengsheng.example.
  2. api.shengsheng.example.live.svc.cluster.local.
  3. api.shengsheng.example.svc.cluster.local.
  4. api.shengsheng.example.cluster.local.
'api.shengsheng.example.' ndots=5: 共 1 個候選
  1. api.shengsheng.example.
```

第一組是短名稱 `chat`，沒有點，先套 search，第一個候選 `chat.live.svc.cluster.local.` 就是正確答案，這正是 search domain 想要的效果。第二組是聲聲 Live 自己的對外網域，有兩個點，少於 5，所以前三個候選都是不存在的名稱，第四個才是真的；這三個注定 NXDOMAIN 的查詢就是 CoreDNS 流量暴增的來源。第三組把 ndots 改成 1，兩個點已經夠，第一個候選就是原名。第四組在名稱結尾加一個點，候選只剩一個，完全不套 search。

> [!warning] 常見誤解
> 「名稱裡有點，就不會套 search。」這是 ndots:1 時代留下的直覺。在 ndots:5 的 Pod 裡，`api.shengsheng.example` 有兩個點仍然會先套 search；只有點數達到 5 個以上、或結尾帶點的名稱，才會先原樣查。

> [!tip]
> 在設定檔裡把外部名稱寫成結尾帶點的絕對名稱（例如 `pay.example.net.`），是最直接的省查詢方法。但不是每個程式都正確處理結尾的點：HTTP 的 Host header、TLS 的 SNI 與憑證名稱比對可能因此出錯，改之前要測試。

## 16.6 應用程式與 runtime 的 DNS 快取

第 14 章說過，DNS 靠 TTL 讓各層快取知道答案能用多久。問題是，從應用程式到 authoritative server 之間有很多層可能快取，而其中幾層**不看 TTL**，或者根本沒有「重新解析」這個動作。

```text
  ┌───────────────────────────────────────────────────────────┐
  │ 應用程式：已建立的長連線（HTTP keep-alive、gRPC、DB pool）     │ ← 不重新解析
  ├───────────────────────────────────────────────────────────┤
  │ 應用程式自己的快取（例如啟動時解析一次存在變數裡）             │ ← 常常永久
  ├───────────────────────────────────────────────────────────┤
  │ 語言 runtime（JVM InetAddress 快取）                         │ ← 自訂 TTL
  ├───────────────────────────────────────────────────────────┤
  │ 本機 OS（systemd-resolved、nscd、mDNSResponder）             │ ← 大致遵守 TTL
  ├───────────────────────────────────────────────────────────┤
  │ 節點層（NodeLocal DNSCache）→ 叢集層（CoreDNS cache 外掛）    │ ← 遵守 TTL，可設上限
  ├───────────────────────────────────────────────────────────┤
  │ recursive resolver（VPC resolver、ISP、公共 DNS）            │ ← 遵守 TTL
  └───────────────────────────────────────────────────────────┘
        DNS 改了之後，要「每一層」都過期或重建，流量才會真正移動
```

這張分層圖由下往上看：越下層越標準，大致都遵守 TTL；越上層越接近應用程式，行為越依實作而定。最上面一層最特別，它根本不是 DNS 快取，而是**已經建立的 TCP 連線**。一條 HTTP keep-alive 連線、一條 gRPC 的 HTTP/2 連線、或連線池裡的資料庫連線，一旦連上，就跟 DNS 再也沒有關係；只要對端沒關、連線沒出錯，程式就會一直用它，DNS 改幾次都一樣。

語言 runtime 的快取以 Java 最常見。JVM 的 `InetAddress` 有自己的名稱快取，由安全性屬性 `networkaddress.cache.ttl` 控制成功結果要保留幾秒、`networkaddress.cache.negative.ttl` 控制失敗結果保留幾秒（預設 10 秒）。成功結果的預設值依 JDK 實作而定：沒有啟用 security manager 時通常是 30 秒；設成 -1 代表永久快取，舊系統或某些安全強化設定裡偶爾會看到。這個 TTL 和 DNS record 的 TTL 無關，是 JVM 自己的規則。Python、Go、Node.js 的標準函式庫則不快取，每次都重新呼叫解析，但它們上面的 HTTP client 與連線池仍然會保留連線。

| 層 | 快取什麼 | 預設行為 | 怎麼控制 |
|---|---|---|---|
| JVM `InetAddress` | 名稱到 IP | 成功約 30 秒（依版本與設定）、失敗 10 秒 | `networkaddress.cache.ttl`、`networkaddress.cache.negative.ttl` |
| HTTP client 連線池 | 已建立的 TCP／TLS 連線 | 閒置逾時前一直重用 | 設定 idle timeout 與連線最長壽命 |
| 資料庫連線池（例如 HikariCP） | 資料庫連線 | 依池設定；HikariCP 的 `maxLifetime` 預設 30 分鐘 | 調整 max lifetime，比 DNS 切換的容忍時間短 |
| gRPC channel | HTTP/2 連線與解析結果 | 連線斷了或收到 GOAWAY 才重新解析 | server 端設定 max connection age |
| nginx `proxy_pass` 寫死主機名稱 | 啟動或 reload 時解析一次 | 直到下次 reload | 用 `resolver` 指令搭配變數，或支援動態解析的 upstream 設定（依版本而定） |
| systemd-resolved／nscd | 名稱到 IP | 遵守 TTL | `resolvectl flush-caches` 等指令 |

表格裡的每一列都對應一種「DNS 已經切換，流量卻沒動」的事故。故事裡的課程排程服務用 Java 寫，HTTP client 的連線池沒有設定最長壽命，推薦服務藍綠切換時 DNS 改了，舊版也還開著，於是排程服務的連線安安穩穩地繼續送到舊版；等舊版被關掉，所有連線同時斷開、同時重連，才終於解析到新 IP，這段時間的錯誤率尖峰就是監控看到的那一團紅。

修正要同時處理兩層。第一層是**讓連線有壽命**：連線池設定最長壽命（例如 5 到 10 分鐘），到期就關掉重建；或由 server 端主動在一段時間後請 client 換連線，HTTP/2 與 gRPC 用 GOAWAY 訊號做這件事。第二層是**讓重建時拿到新答案**：runtime 的名稱快取不能是永久，應該短於或接近 DNS TTL。只做第一層不夠，因為重建連線時若 runtime 還快取舊 IP，新連線仍然連到舊版；只做第二層也不夠，因為已建立的連線根本不會去查。16.10 節的動手做會用程式把這兩層的效果並排呈現。

還有一個營運面的配合：切換 DNS 之後，**舊版不能立刻關**。舊版至少要繼續服務「DNS TTL＋各層快取上限＋連線最長壽命」這段時間，並在關閉前做 graceful shutdown（停止接新連線、讓舊連線處理完再關，第 43 章詳述）。這段等待時間應該寫進部署 runbook，而不是靠每次憑感覺。

> [!warning] 常見誤解
> 「把 DNS TTL 調成 60 秒，切換就會在一分鐘內完成。」TTL 只控制遵守 TTL 的那幾層快取。已建立的長連線、永久快取的 runtime、啟動時解析一次的設定，都不受 TTL 影響。

## 16.7 容器與 Kubernetes 的 DNS

容器讓 resolv.conf 多了一個產生者。Docker 在預設 bridge 網路上會把主機的 resolv.conf 複製進容器（過濾掉本機位址，例如 `127.0.0.53` 這種在容器裡連不到的 stub）；在使用者自建的網路上，Docker 改用內建的 DNS server，容器的 resolv.conf 會寫 `nameserver 127.0.0.11`，讓容器可以用名稱互相找到對方。

Kubernetes 的做法更完整。叢集裡跑著 **CoreDNS**（叢集內的 DNS server，通常有兩個以上的 Pod），前面有一個名為 `kube-dns` 的 Service，提供固定的 ClusterIP（範例裡是 `10.96.0.10`）。kubelet 建立 Pod 時，依 Pod 的 **dnsPolicy** 產生 resolv.conf：預設的 `ClusterFirst` 會把 nameserver 指向 `kube-dns`、依 namespace 產生 search 清單、附加節點的 search domain，並設定 `ndots:5`。

```text
  Pod（namespace: live）                   CoreDNS Pod ×2（kube-system）
  ┌───────────────────────┐   UDP 53    ┌──────────────────────────────┐
  │ app → getaddrinfo      │──────────►│ kubernetes 外掛：             │
  │ resolv.conf:          │  經 kube-dns│   *.cluster.local 從 API 回答 │
  │  nameserver 10.96.0.10│  Service   │ cache 外掛：快取 30 秒        │
  │  search live.svc...   │  （DNAT）   │ forward 外掛：其他名稱轉給上游 │
  │  options ndots:5      │            └──────────────┬───────────────┘
  └───────────────────────┘                           │
                                                      ▼
                                        節點的 resolv.conf 指向的 resolver
                                        （雲端 VPC resolver → 網際網路）
```

這張拓撲圖從左往右看。Pod 裡的程式照常呼叫 `getaddrinfo`，libc 依 resolv.conf 把查詢送到 `10.96.0.10`；這個 IP 是 Service 的虛擬位址，節點上的 kube-proxy 規則把封包 DNAT（改寫目的位址，第 7 章）到某一個 CoreDNS Pod。CoreDNS 的 kubernetes 外掛監看 Kubernetes API，直接回答叢集網域 `cluster.local` 底下的名稱；其他名稱經過 cache 外掛，再由 forward 外掛轉給節點設定的上游 resolver。Kubernetes 的 Service、kube-proxy 與 Pod 網路模型本身在第 44 章詳談，本章只看名稱。

CoreDNS 的設定檔叫 Corefile，常見的預設內容如下，每一行就是一個外掛。

```text
.:53 {
    errors
    health
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}
```

`kubernetes` 那一段負責叢集網域與反查網域；`forward . /etc/resolv.conf` 表示其他所有名稱都轉給 CoreDNS Pod 本身 resolv.conf 裡的上游；`cache 30` 把快取上限設為 30 秒；`prometheus :9153` 暴露 metrics，阿德看到的 QPS 與 NXDOMAIN 比例就是從這裡來的；`loop` 偵測「上游又指回自己」的轉送迴圈。

Kubernetes 為 Service 產生的名稱有固定格式，下表整理常見的幾種。

| 名稱格式 | record | 回答內容 | 用途 |
|---|---|---|---|
| `chat.live.svc.cluster.local` | A／AAAA | Service 的 ClusterIP | 一般 Service，由 kube-proxy 分散到後端 Pod |
| `chat.live.svc.cluster.local`（headless，`clusterIP: None`） | A／AAAA | 每個就緒 Pod 的 IP | client 自己挑後端，例如 gRPC client 端負載分散 |
| `chat-0.chat.live.svc.cluster.local` | A／AAAA | StatefulSet 中特定 Pod 的 IP | 需要穩定身分的服務（資料庫叢集、聊天分片） |
| `_grpc._tcp.chat.live.svc.cluster.local` | SRV | 具名 port 的埠號與目標名稱 | 同時發現位址與 port |
| `10-20-1-5.live.pod.cluster.local` | A | 把名稱裡的 IP 直接轉回 IP | 少用，依 CoreDNS 設定開啟 |

接下來回到故事。為什麼 Kubernetes 要把 ndots 設成 5？官方的考量是讓叢集內各種相對名稱都先套 search：`chat`、`chat.live`、`chat.live.svc`，甚至點數更多的 SRV 形式相對名稱，都能在 search 清單裡找到正確的完整名稱。代價是所有點數不到 5 的**外部名稱**，都要先把每個 search domain 試過一輪。下面的時序圖是一次 `getaddrinfo("pay.example.net")` 在 Pod 裡實際發生的事。

```text
 app/libc                         CoreDNS                         上游 resolver
   │── A    pay.example.net.live.svc.cluster.local ─►│  （叢集網域，直接回）
   │── AAAA pay.example.net.live.svc.cluster.local ─►│
   │◄──────────── NXDOMAIN ×2 ──────────────────────│
   │── A／AAAA pay.example.net.svc.cluster.local ───►│
   │◄──────────── NXDOMAIN ×2 ──────────────────────│
   │── A／AAAA pay.example.net.cluster.local ───────►│
   │◄──────────── NXDOMAIN ×2 ──────────────────────│
   │── A／AAAA pay.example.net.compute.internal.example ►│── 轉送 ──────────►│
   │◄──────────── NXDOMAIN ×2 ──────────────────────│◄──────────────────│
   │── A／AAAA pay.example.net. ────────────────────►│── 轉送（或命中快取）►│
   │◄──────────── NOERROR：198.51.100.20 等 ─────────│◄──────────────────│
   │  共 10 個查詢，其中 8 個注定失敗                  │                   │
```

這張時序圖由上往下是時間順序。前三組候選屬於叢集網域，CoreDNS 自己就能回 NXDOMAIN，便宜但不是免費；第四組是節點繼承來的雲端網域，CoreDNS 必須轉給上游才知道不存在，這一步多了一段網路往返，也增加上游 resolver 的負擔；第五組才是真正的名稱。每組都有 A 與 AAAA 兩個查詢，所以一次解析送出 10 個請求，成功的只有最後 2 個。對一個每秒呼叫外部 API 數百次、又沒有快取的服務，這就是 CoreDNS 流量放大的機制。

故事裡的 5 秒延遲則是另一個問題疊上來。glibc 預設從同一個 UDP socket 幾乎同時送出 A 與 AAAA，兩個封包的五元組完全相同；在 Linux 的 conntrack（連線追蹤表，第 7 章）做 DNAT 時，這兩個封包在某些核心版本上會產生競態（race condition），其中一個封包被丟掉。libc 等不到那個回應，只好等滿 timeout（預設 5 秒）再重送，於是出現「偶爾剛好卡 5 秒」的症狀。較新的核心已修補部分情況，但實際是否受影響依核心版本與網路外掛而定。

針對這兩個問題，常見的緩解方式有幾種，通常會組合使用：

1. **降低 ndots**：在 Pod spec 的 `dnsConfig.options` 把 ndots 設成 2，讓 `pay.example.net` 這類名稱直接先原樣查。代價是 `chat.live.svc` 這種三段的相對名稱會先往外查一次，所以團隊要約定叢集內名稱寫短名稱或完整名稱。
2. **外部名稱寫成絕對名稱**：設定檔裡寫 `pay.example.net.`，完全跳過 search，但要先確認程式與 TLS 處理沒問題。
3. **NodeLocal DNSCache**：在每個節點跑一個本機快取（以 DaemonSet 部署，監聽一個 link-local 位址），Pod 的查詢不經過 Service DNAT 就在節點上命中快取，對上游 CoreDNS 改用 TCP，避開 conntrack 競態，也讓 NXDOMAIN 在本機就被快取。
4. **`single-request-reopen`**：在 dnsConfig 加這個選項，讓 glibc 用不同 socket 送 A 與 AAAA，避開同一五元組的競態；對 musl 無效。
5. **CoreDNS 的 autopath 外掛**：由 CoreDNS 在伺服器端代為走完 search 清單，一次回答最終結果，減少來回；需要開啟 `pods verified`，CoreDNS 會監看所有 Pod，記憶體用量增加。
6. **應用程式層快取或連線重用**：讓服務不要每個請求都解析一次，例如重用 HTTP 連線，這也減少 TCP 與 TLS 交握。

`dnsPolicy` 本身也值得認識：`ClusterFirst`（預設）如上所述；`Default` 直接沿用節點的 resolv.conf，Pod 就看不到叢集內的 Service 名稱；`ClusterFirstWithHostNet` 給使用主機網路（`hostNetwork: true`）但仍要解析叢集名稱的 Pod；`None` 則完全由 `dnsConfig` 指定 nameserver、search 與 options。

## 16.8 服務發現模式

前面幾節談的是「給一個名稱，找到 IP」。在微服務系統裡，問題更進一步：服務的實例會隨部署、擴縮與故障不斷變動，呼叫方要怎麼知道**現在**有哪些健康的實例、各自在哪個 IP 與 port？這個問題叫**服務發現**（service discovery）。例如聲聲 Live 的聊天服務有 6 個 Pod，滾動更新時每分鐘都有 Pod 換 IP，呼叫方必須持續拿到最新清單。

服務發現有兩個維度。第一個維度是**誰挑後端**：**client-side discovery** 由呼叫方拿到所有實例清單、自己做負載分散；**server-side discovery** 由呼叫方把請求送到一個固定的入口（load balancer、Kubernetes Service 的 ClusterIP），由入口挑後端。第二個維度是**清單從哪裡來**：DNS、專門的 registry（例如 Consul、etcd、ZooKeeper、Eureka）、平台內建的 API（Kubernetes 的 EndpointSlice），或 service mesh 的控制平面。

```text
 server-side discovery                      client-side discovery
 ┌────────┐   chat.live.svc   ┌─────────┐    ┌────────┐ 1. 查 registry／headless DNS
 │ caller │──► ClusterIP ────►│ kube-   │    │ caller │──────────────►┌──────────┐
 └────────┘   （固定位址）     │ proxy   │    │        │◄── 實例清單 ───│ registry │
                              │ 挑一個  │    │        │               └────▲─────┘
                              └──┬──┬───┘    │        │ 2. 自己挑一個實例     │ 註冊／
                                 ▼  ▼        │        │──────────►┌──────┐ │ 健康檢查
                              Pod A Pod B    └────────┘           │ Pod B│─┘
  優點：caller 很簡單                         優點：可做精細的負載分散（例如每個請求挑）
  缺點：多一跳；長連線只綁住一個後端           缺點：每種語言的 client 都要實作發現邏輯
```

左半邊是 server-side：呼叫方只認得一個固定位址，挑後端的工作交給中間的 kube-proxy 或 load balancer，呼叫方程式最簡單。但對長連線來說有一個陷阱：kube-proxy 的分散發生在**建立連線時**，一條 gRPC 的 HTTP/2 連線會帶著所有請求固定送到同一個 Pod，負載分散失效。右半邊是 client-side：呼叫方先從 registry 或 headless Service 的 DNS 拿到所有實例，再自己挑；gRPC 的 client 端負載分散就是這種模式，能做到每個請求挑不同後端，代價是每種語言的 client 都要有正確的發現與健康檢查邏輯。

| 模式 | 例子 | 更新速度 | 帶 port 與健康資訊 | 主要取捨 |
|---|---|---|---|---|
| DNS（A／AAAA、SRV） | Kubernetes Service 名稱、headless Service、內部 DNS zone | 受 TTL 與各層快取限制 | A 不帶 port；SRV 帶 port；健康要另外做 | 所有語言都支援；但 client 常不遵守 TTL，長連線更不會重查 |
| 專用 registry | Consul、etcd、ZooKeeper、Eureka | 可以接近即時（watch／long poll） | 可以帶 port、metadata、健康狀態 | 多一個要維運的關鍵系統；client 要整合 SDK |
| 平台內建 | Kubernetes EndpointSlice＋kube-proxy | 秒級 | 有就緒狀態（readiness） | 綁定平台；跨叢集要額外方案 |
| service mesh | sidecar 或節點 proxy，由控制平面推送設定 | 秒級，推送式 | 有，並含流量規則、mTLS | 功能最完整，複雜度與資源成本也最高（第 30 章、第 44 章） |

DNS 是最通用的服務發現，因為每種語言都會解析名稱，但它天生有三個限制：A record 不帶 port；DNS 本身不知道後端健不健康，除非 authoritative 端做健康檢查（第 15 章）；更新速度取決於整條快取鏈裡最不聽話的那一層。專用 registry 與 mesh 正是為了補這三個洞而存在。選型時可以這樣想：服務數量少、實例變動不頻繁，DNS 加 load balancer 最省事；在 Kubernetes 裡，Service 名稱加 kube-proxy 已經足夠大多數 HTTP 服務；需要每個請求層級的負載分散、細緻的流量切換或跨叢集，才值得引入 registry 或 mesh。

> [!example] 例子
> 聲聲 Live 的即時聊天服務用 gRPC 互相呼叫。搬上 Kubernetes 後，Joe 發現 6 個 Pod 裡有 1 個 CPU 滿載、其他幾乎閒置。原因是呼叫方透過一般 Service 建了一條長期 HTTP/2 連線，所有請求都落在同一個 Pod。改成 headless Service 加 gRPC 的 client 端負載分散，並在 server 端設定連線最長壽命讓 client 定期重新解析，負載才平均。

## 16.9 用 DNS 證明網域所有權：ACME DNS-01 與 TXT 驗證

DNS 除了把名稱變成 IP，還常被拿來回答另一個問題：「你真的控制這個網域嗎？」能在網域的 DNS zone 裡新增一筆 record，通常就代表擁有修改這個網域設定的權限，所以憑證機構（CA）、SaaS 服務、郵件服務都用「請你放一筆指定內容的 TXT record」來驗證所有權。**TXT record** 是第 14 章介紹過的自由文字 record，可以放任意字串。

**ACME**（Automatic Certificate Management Environment，RFC 8555）是自動申請與更新憑證的協定，Let's Encrypt 等 CA 都支援；完整的憑證營運流程在第 19 章。ACME 提供幾種驗證方式，其中 **HTTP-01** 要求在網站的固定路徑放一個檔案，**DNS-01** 要求在 `_acme-challenge.<網域>` 放一筆 TXT record。DNS-01 有三個獨特的能力：可以申請 wildcard 憑證（Let's Encrypt 對 wildcard 只接受 DNS-01）、可以替沒有對外開放 HTTP 的內部主機申請憑證、驗證時不需要把流量導到任何伺服器。

```text
 ACME client（cert-manager 等）        DNS 供應商 API         CA
   │── 1. 建立訂單：*.shengsheng.example、shengsheng.example ─────────►│
   │◄─ 2. 每個名稱各給一個 challenge token ────────────────────────────│
   │  3. 計算 TXT 值 = base64url(SHA-256(token + "." + 帳號金鑰 thumbprint))
   │── 4. 新增 TXT：_acme-challenge.shengsheng.example ─►│
   │  5. 等待所有 authoritative server 都看得到這筆 record（傳播）
   │── 6. 通知 CA：可以驗證了 ──────────────────────────────────────►│
   │                                     │◄── 7. CA 查詢 TXT ────────│
   │                                     │─── 8. 回傳 TXT 值 ───────►│
   │◄─ 9. 驗證成功，簽發憑證 ──────────────────────────────────────────│
   │── 10. 刪除 TXT record ─────────────►│
```

這張時序圖有十步。第 1 到 2 步，client 向 CA 下訂單，CA 為每個要驗證的名稱發一個 challenge token。第 3 步，client 把 token 與自己 ACME 帳號公鑰的 thumbprint 接起來，算 SHA-256 再做 base64url，這個值綁定了「這次挑戰」與「這個帳號」，別人的帳號拿到同一個 token 也算不出相同的值。第 4 到 5 步，透過 DNS 供應商的 API 新增 record，並等待所有 authoritative server 都看得到。第 6 到 8 步，client 通知 CA，CA 自己去查 TXT。第 9 到 10 步，簽發憑證並清除 record。注意 `*.shengsheng.example` 與 `shengsheng.example` 的 TXT 都放在同一個名稱 `_acme-challenge.shengsheng.example` 下，同時申請時那個名稱底下會有兩筆不同的 TXT，這是正常的。

第 3 步的計算可以用標準函式庫做出來。下面的金鑰與 token 都是範例值，重點是看清楚每一步的輸入與輸出。

```python
# 計算 ACME DNS-01 要放進 TXT record 的值（金鑰與 token 都是範例值）
import base64, hashlib, json

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

# 帳號公鑰（JWK）。thumbprint 只取必要欄位、key 依字典序、不留空白（RFC 7638）
account_jwk = {"kty": "EC", "crv": "P-256",
               "x": b64url(b"\x01" * 32), "y": b64url(b"\x02" * 32)}
canonical = json.dumps({k: account_jwk[k] for k in ("crv", "kty", "x", "y")},
                       separators=(",", ":"), sort_keys=True)
thumbprint = b64url(hashlib.sha256(canonical.encode()).digest())

token = "evaGxfADs6pSRb2LAv9IZf17Dt3juxGJ-PCt92wr-oA"   # CA 給的 challenge token（範例）
key_authorization = f"{token}.{thumbprint}"
txt_value = b64url(hashlib.sha256(key_authorization.encode()).digest())

print("canonical JWK  :", canonical[:60] + "...")
print("thumbprint     :", thumbprint)
print("keyAuthorization 長度:", len(key_authorization))
print("要建立的 record :")
print(f'  _acme-challenge.shengsheng.example. 60 IN TXT "{txt_value}"')
assert len(txt_value) == 43 and "=" not in txt_value   # 32 bytes 的 base64url 不補等號
```

```text
canonical JWK  : {"crv":"P-256","kty":"EC","x":"AQEBAQEBAQEBAQEBAQEBAQEBAQEBA...
thumbprint     : kOFKxjJdOqJD5G4Yuw-cxHe64VGyxKEO_hoV83QfGj0
keyAuthorization 長度: 87
要建立的 record :
  _acme-challenge.shengsheng.example. 60 IN TXT "27AvKg1wo7cWvULgmdETv4VPbdCePn_c4tiKi9a6xXY"
```

第一行是 JWK 的標準化 JSON：只留必要欄位、依字母排序、沒有空白，這樣不同程式算出的 thumbprint 才會一致。第二行是 thumbprint，SHA-256 的 32 bytes 經 base64url 編碼成 43 個字元。第三行的 keyAuthorization 是「token、一個點、thumbprint」，長度 43＋1＋43＝87。最後一行就是要放進 DNS 的 record，TTL 設短一點（例如 60 秒），因為它只是暫時存在。

DNS-01 在實務上有幾個常見陷阱。第一是**傳播**：DNS 供應商的 API 回應「成功」，不代表每一台 authoritative server 都已更新，CA 可能剛好查到還沒更新的那一台；好的 ACME client 會先自己查遍每一台 NS 再通知 CA。第二是 **split-horizon**（第 15 章）：公司內部看到的 zone 和外部不同，在內部 DNS 新增 record，CA 從網際網路上查不到。第三是**權限**：自動化需要一把能改 DNS 的 API 憑證，若這把憑證能修改整個 zone，外洩時攻擊者就能改走所有流量。常見的降低風險作法是把 `_acme-challenge.shengsheng.example` 用 CNAME 指到一個專門的驗證用 zone，ACME client 只拿到那個小 zone 的權限，CA 會跟著 CNAME 去查。第四是 **CAA record**：它宣告「哪些 CA 可以替這個網域發憑證」，設錯會讓 CA 拒絕簽發；支援相關擴充的 CA 還能進一步限定帳號與驗證方式。

其他 TXT 驗證的原理相同：SaaS 服務給一段隨機字串，請你放在網域或某個子網域的 TXT 裡。兩個好習慣：驗證完成後若服務不需要持續檢查，就刪掉 record，避免 zone 裡堆滿無人知道用途的 TXT；以及記錄每筆驗證 record 是哪個團隊、為了哪個服務加的，否則某天有人「清理」掉仍需要持續驗證的 record，服務就會突然失效。

> [!note] 2026 現況
> 截至 2026 年 10 月，CA/Browser Forum 的規則正逐步縮短公開信任憑證的最長效期與網域驗證結果可重用的期限：2026 年 3 月 15 日起兩者都是 200 天，預計 2027 年 3 月 15 日降為 100 天、2029 年 3 月 15 日憑證效期 47 天、網域驗證重用期限 10 天（依 2026 年 10 月查證）。這代表 DNS-01 與 HTTP-01 驗證會越來越頻繁，DNS API 的自動化與權限設計不再是可有可無的細節。公開信任的 CA 也被要求從多個網路位置交叉驗證網域控制權，因此只在部分地區或部分 authoritative server 生效的 record 更容易驗證失敗。

## 16.10 動手做：數 ndots 造成的請求、觀察 getaddrinfo、修正長連線

這一節有三段程式，對應本章三個主軸，都在 127.0.0.1 上離線執行。

### 用假 DNS server 數實際發出的請求

16.5 節的函式只列出候選名稱。這段程式更進一步：在 127.0.0.1 開一個假的 UDP DNS server（只認得兩個名稱，其他一律回 NXDOMAIN），再寫一個會套 search 與 ndots 的 stub resolver，真的把 DNS 封包送出去，讓 server 記下每一個收到的查詢。DNS 訊息格式沿用第 14 章的手組方式。

```python
# 本機假 DNS server + 會套 search/ndots 的 stub resolver，數實際發出的 DNS 請求
import socket, struct, threading, ipaddress

ZONE = {  # 假的權威資料：名稱 -> {qtype: 位址}
    "chat.live.svc.cluster.local.": {1: "10.96.12.7"},             # Service 只有 IPv4
    "pay.example.net.": {1: "198.51.100.20", 28: "2001:db8::20"},  # 外部金流
}

def encode_name(name):
    out = b""
    for label in name.rstrip(".").split("."):
        out += bytes([len(label)]) + label.encode()
    return out + b"\x00"

def decode_name(buf, off):
    labels = []
    while buf[off]:
        n = buf[off]; labels.append(buf[off + 1:off + 1 + n].decode()); off += n + 1
    return ".".join(labels) + ".", off + 1

def server(sock, log):
    while True:
        try:
            data, peer = sock.recvfrom(512)
        except OSError:
            return                                   # socket 已關閉，結束 thread
        qid, flags = struct.unpack("!HH", data[:4])
        qname, off = decode_name(data, 12)
        qtype, = struct.unpack("!H", data[off:off + 2])
        question = data[12:off + 4]
        records = ZONE.get(qname)
        rcode = 3 if records is None else 0          # 3 = NXDOMAIN；名稱存在但沒這型別 = NODATA
        answer = b""
        if records and qtype in records:
            rdata = ipaddress.ip_address(records[qtype]).packed
            answer = b"\xc0\x0c" + struct.pack("!HHIH", qtype, 1, 30, len(rdata)) + rdata
        header = struct.pack("!HHHHHH", qid, 0x8180 | rcode, 1, 1 if answer else 0, 0, 0)
        log.append((qname, {1: "A", 28: "AAAA"}[qtype], "NXDOMAIN" if rcode else "NOERROR"))
        sock.sendto(header + question + answer, peer)

def query(addr, qid, fqdn, qtype):
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
        s.settimeout(1)
        s.sendto(struct.pack("!HHHHHH", qid, 0x0100, 1, 0, 0, 0)
                 + encode_name(fqdn) + struct.pack("!HH", qtype, 1), addr)
        reply = s.recv(512)
    return struct.unpack("!H", reply[2:4])[0] & 0xF  # 回傳 rcode

def resolve(addr, name, search, ndots):
    if name.endswith("."):
        candidates = [name]
    elif name.count(".") >= ndots:
        candidates = [name + "."] + [f"{name}.{d}." for d in search]
    else:
        candidates = [f"{name}.{d}." for d in search] + [name + "."]
    sent = 0
    for fqdn in candidates:
        rcodes = [query(addr, sent + i, fqdn, t) for i, t in enumerate((1, 28))]
        sent += 2                                    # AF_UNSPEC：每個候選都問 A 與 AAAA
        if 0 in rcodes:                              # 只要名稱存在就停，不再試下一個
            return fqdn, sent
    return None, sent

srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
srv.bind(("127.0.0.1", 0))
log = []
t = threading.Thread(target=server, args=(srv, log), daemon=True)
t.start()
addr = srv.getsockname()
SEARCH = ["live.svc.cluster.local", "svc.cluster.local", "cluster.local",
          "compute.internal.example"]                # 最後一個是從節點繼承來的
results = {}
for name, ndots in [("chat", 5), ("chat.live", 5), ("pay.example.net", 5),
                    ("pay.example.net.", 5), ("pay.example.net", 2)]:
    log.clear()
    found, sent = resolve(addr, name, SEARCH, ndots)
    results[(name, ndots)] = sent
    print(f"{name:<18} ndots={ndots}  -> {found}  共 {sent} 個請求")
    if name == "pay.example.net" and ndots == 5:
        for q in log:
            print(f"      {q[1]:<4} {q[0]:<45} {q[2]}")
srv.close()
t.join(1)
assert results[("chat", 5)] == 2
assert results[("pay.example.net", 5)] == 10
assert results[("pay.example.net.", 5)] == 2 and results[("pay.example.net", 2)] == 2
print("NXDOMAIN 浪費比例（外部名稱、ndots=5）:", f"{8 / 10:.0%}")
```

```text
chat               ndots=5  -> chat.live.svc.cluster.local.  共 2 個請求
chat.live          ndots=5  -> chat.live.svc.cluster.local.  共 4 個請求

      AAAA pay.example.net.svc.cluster.local.            NXDOMAIN
```

逐行解讀輸出。第一行，同 namespace 的短名稱 `chat` 在第一個候選就命中，A 回位址、AAAA 回 NODATA（名稱存在但沒有 IPv6），總共 2 個請求，這是 search domain 的理想情況。第二行，`chat.live` 有一個點，第一個候選 `chat.live.live.svc.cluster.local.` 不存在，第二個 `chat.live.svc.cluster.local.` 才命中，4 個請求。第三行是故事裡的金流網域，下面的十行 log 正是 server 端實際收到的封包：前八個全部 NXDOMAIN，最後兩個才成功，與 16.7 節的時序圖一致。最後兩行是兩種修正：名稱結尾加點，或把 ndots 降到 2，都只需要 2 個請求。最後一行把浪費量化：外部名稱在 ndots:5 下有 80% 的查詢注定失敗。

這段程式省略了真實 resolver 的很多細節：沒有快取、沒有逾時重送、A 與 AAAA 依序而非同時送出、server 不處理 EDNS(0)。但「每個候選兩個查詢、名稱存在就停」這兩條規則與 glibc 一致，所以請求數的手算結果可以直接拿來估算 CoreDNS 的負載：每秒解析外部名稱的次數乘以 5，大約就是 CoreDNS 要承受的查詢數。

### 用 socket.getaddrinfo 觀察 localhost

第二段程式只用 `localhost` 與數字位址，答案來自 `/etc/hosts` 與系統設定，不需要網路。

```python
# 用 socket.getaddrinfo 觀察 localhost：不需要網路，結果來自 /etc/hosts 與系統設定
import socket

FAMILY = {socket.AF_INET: "AF_INET ", socket.AF_INET6: "AF_INET6"}

def show(title, *args, **kwargs):
    print(title)
    for family, type_, proto, _canon, sockaddr in socket.getaddrinfo(*args, **kwargs):
        print(f"  {FAMILY.get(family, family)}  {socket.SocketKind(type_).name:<11} proto={proto:<2} {sockaddr}")

# 1) 不限型別：同一個位址會因 SOCK_STREAM／SOCK_DGRAM 等出現多筆
show("localhost:8080（不指定 type）", "localhost", 8080)
# 2) 指定 TCP：這才是一般 client 會拿到、依序嘗試的清單
show("localhost:8080 SOCK_STREAM", "localhost", 8080, type=socket.SOCK_STREAM)
# 3) 只要 IPv4
show("localhost:8080 AF_INET", "localhost", 8080, socket.AF_INET, socket.SOCK_STREAM)
# 4) AI_PASSIVE + host=None：給 server bind 用的「所有介面」位址
show("None:8080 AI_PASSIVE", None, 8080, socket.AF_INET, socket.SOCK_STREAM, 0, socket.AI_PASSIVE)

# 5) AI_NUMERICHOST：只接受數字位址，保證不會觸發任何名稱查詢
info = socket.getaddrinfo("127.0.0.1", 8080, type=socket.SOCK_STREAM, flags=socket.AI_NUMERICHOST)
assert info[0][4] == ("127.0.0.1", 8080)
try:
    socket.getaddrinfo("localhost", 8080, flags=socket.AI_NUMERICHOST)
except socket.gaierror as exc:
    print("AI_NUMERICHOST 給名稱 ->", type(exc).__name__, exc.errno == socket.EAI_NONAME)

# 實際連線時，客戶端應該依序嘗試 getaddrinfo 給的每個位址
srv = socket.create_server(("127.0.0.1", 0))
port = srv.getsockname()[1]
with socket.create_connection(("localhost", port), timeout=2) as c:
    print("create_connection 最後連上:", c.getpeername()[0])
srv.close()
```

```text
  AF_INET6  SOCK_DGRAM  proto=17 ('::1', 8080, 0, 0)
  AF_INET6  SOCK_STREAM proto=6  ('::1', 8080, 0, 0)
  AF_INET   SOCK_DGRAM  proto=17 ('127.0.0.1', 8080)
  AF_INET   SOCK_STREAM proto=6  ('127.0.0.1', 8080)
localhost:8080 SOCK_STREAM
  AF_INET6  SOCK_STREAM proto=6  ('::1', 8080, 0, 0)
  AF_INET   SOCK_STREAM proto=6  ('127.0.0.1', 8080)

  AF_INET   SOCK_STREAM proto=6  ('0.0.0.0', 8080)
```

這份輸出是在 macOS 上執行得到的；Linux 上筆數與順序會依 `/etc/hosts`、`/etc/gai.conf` 與是否啟用 IPv6 而不同，這正是要觀察的重點。第一組沒有指定 type，同一個位址因 UDP 與 TCP 各出現一次，共四筆；IPv6 的 sockaddr 是四元組，多了 flowinfo 與 scope id。第二組指定 `SOCK_STREAM`，只剩兩筆，而且 `::1` 排在前面，這是 RFC 6724 排序的結果。第三組限定 `AF_INET`，只剩 IPv4。第四組是 server 端用法，`AI_PASSIVE` 加上 host 為 None，得到 `0.0.0.0`，代表 bind 所有 IPv4 介面。第五組說明 `AI_NUMERICHOST` 遇到名稱會直接報 `EAI_NONAME`，不會偷偷查詢，適合「設定裡只該出現 IP」的場合。

最後一行最值得玩味。server 只聽在 `127.0.0.1`，但 `localhost` 的清單第一筆是 `::1`，所以 `create_connection` 先試 `::1` 被拒絕，再試 `127.0.0.1` 才成功。如果程式只拿第一筆，這裡就會連線失敗。實務上「server 只 bind IPv4、client 用 localhost 連」的組合，在 Node.js 17 改變 `dns.lookup` 預設回傳順序之後，曾讓許多開發環境突然出現連線被拒；理解 `getaddrinfo` 回傳的是有序清單，就知道該修的是「依序嘗試」或「兩種位址都 bind」。

### 長連線不會重新解析 DNS：問題與修正

第三段程式重現故事裡的推薦服務切換。兩個本機 TCP server 扮演舊版與新版；一個假的 DNS 表格在 t=45 秒從舊版改指新版；三個連線池用不同策略持續發請求，時間用模擬時鐘推進，不需要真的等待。

```python
# 長連線不會重新解析 DNS：連線池保留舊 IP 的問題與修正（模擬時鐘）
import socket, socketserver, threading

class Backend(socketserver.ThreadingTCPServer):
    daemon_threads = True
    allow_reuse_address = True

def start_backend(label):
    class Handler(socketserver.StreamRequestHandler):
        def handle(self):
            for _line in self.rfile:                 # 同一條連線可以問很多次（keep-alive）
                self.wfile.write(label.encode() + b"\n")
    srv = Backend(("127.0.0.1", 0), Handler)
    threading.Thread(target=srv.serve_forever, daemon=True).start()
    return srv

old, new = start_backend("old-v1"), start_backend("new-v2")
now = 0                                               # 模擬時鐘（秒）
dns = {"reco.shengsheng.example": old.server_address} # 權威資料，TTL 30 秒
TTL = 30

class Resolver:
    """有快取的 resolver；cache_ttl=None 代表永久快取（像 JVM 設成 -1）。"""
    def __init__(self, cache_ttl):
        self.cache_ttl, self.cache = cache_ttl, {}
    def lookup(self, name):
        hit = self.cache.get(name)
        if hit and (self.cache_ttl is None or now < hit[1]):
            return hit[0]
        addr = dns[name]
        self.cache[name] = (addr, now + (self.cache_ttl or 0))
        return addr

class Pool:
    """只有一條連線的連線池；max_age=None 代表連線永遠不汰換。"""
    def __init__(self, resolver, max_age):
        self.resolver, self.max_age = resolver, max_age
        self.sock = self.born = None
    def request(self, name):
        if self.sock and self.max_age is not None and now - self.born >= self.max_age:
            self.sock.close(); self.sock = None      # 連線太老：關掉，下次重新解析
        if self.sock is None:
            self.sock = socket.create_connection(self.resolver.lookup(name), timeout=2)
            self.reader, self.born = self.sock.makefile("rb"), now
        self.sock.sendall(b"GET\n")
        return self.reader.readline().decode().strip()
    def close(self):
        if self.sock:
            self.reader.close(); self.sock.close()

pools = {
    "no-recycle": Pool(Resolver(TTL), max_age=None),
    "recycle+forever": Pool(Resolver(None), max_age=60),
    "recycle+ttl": Pool(Resolver(TTL), max_age=60),
}
print(f"{'t(s)':>5}  " + "  ".join(f"{k:<16}" for k in pools))
history = {k: [] for k in pools}
for now in range(0, 181, 30):
    if now > 45:                                     # 藍綠切換發生在 t=45：DNS 改指新版
        dns["reco.shengsheng.example"] = new.server_address
    row = [p.request("reco.shengsheng.example") for p in pools.values()]
    for k, v in zip(pools, row):
        history[k].append(v)
    mark = "  <- DNS 已在 t=45 切換" if now == 60 else ""
    print(f"{now:>5}  " + "  ".join(f"{v:<16}" for v in row) + mark)

for p in pools.values():
    p.close()
old.shutdown(); new.shutdown(); old.server_close(); new.server_close()
assert set(history["no-recycle"]) == {"old-v1"}
assert set(history["recycle+forever"]) == {"old-v1"}
assert history["recycle+ttl"][-1] == "new-v2"
print("遵守 TTL 的池在第", history["recycle+ttl"].index("new-v2") * 30, "秒換到新版")
```

```text
 t(s)  no-recycle        recycle+forever   recycle+ttl     
    0  old-v1            old-v1            old-v1          
   30  old-v1            old-v1            old-v1          
   60  old-v1            old-v1            new-v2            <- DNS 已在 t=45 切換
   90  old-v1            old-v1            new-v2          
  120  old-v1            old-v1            new-v2          
  150  old-v1            old-v1            new-v2          
  180  old-v1            old-v1            new-v2          
遵守 TTL 的池在第 60 秒換到新版
```

三欄分別是三種策略。`no-recycle` 是故事裡課程排程服務的設定：連線建立後永不汰換，即使 resolver 本身遵守 TTL，也從來沒有機會被呼叫，所以整整 180 秒都打舊版。`recycle+forever` 給連線設了 60 秒壽命，t=60 時確實關掉舊連線重建了，但 resolver 是永久快取（模擬 JVM 設成 -1 的情況），重建時拿到的還是舊位址，結果一樣。`recycle+ttl` 兩層都修好：t=60 連線到期，resolver 的快取在 t=30 就已過期，重新查詢拿到新位址，從此打新版。

這個結果說明兩件事。第一，連線壽命與 runtime 快取 TTL 缺一不可。第二，即使兩者都設對，從 DNS 切換到流量完全移動，仍需要「TTL＋連線壽命」量級的時間，本例是 15 秒（從 t=45 到 t=60）；真實系統裡有很多 client、每個連線建立的時間不同，流量會在這段期間內逐步移動。所以舊版必須至少撐過這段時間，這是 16.6 節「舊版不能立刻關」的量化依據。

## 16.11 在工作上怎麼用

**情境一：後端服務「解析很慢」或「偶爾卡 5 秒」。** 先分清楚是 DNS 本身慢，還是本機這幾層的問題。依序做：

```bash
# 1. 看程式實際用的設定（在容器裡要 kubectl exec 進 Pod 看）
cat /etc/resolv.conf
grep '^hosts:' /etc/nsswitch.conf
# 2. 用程式的視角解析（走 getaddrinfo + nsswitch），量時間
time getent ahosts pay.example.net
# 3. 用 dig 測 DNS 本身；+search 會套 search domain，可對照差異
dig pay.example.net
dig +search pay.example.net
# 4. 在 Pod 所在節點抓 DNS 封包，看實際送出的候選名稱與重送
sudo tcpdump -ni any port 53
```

判斷方式：`getent` 慢但 `dig` 快，問題在 search 展開、`/etc/hosts`、nsswitch 或 nameserver 的順序；兩者都慢，問題在 nameserver 或上游；延遲集中在 5 秒、10 秒這種 timeout 倍數，優先懷疑封包遺失與 conntrack 競態。tcpdump 若看到一連串 `pay.example.net.live.svc.cluster.local` 之類的查詢，就是 ndots 展開。

**情境二：調整 Kubernetes Pod 的 DNS 設定。** 對大量呼叫外部 API 的服務，在 Pod spec 加上 dnsConfig：

```yaml
spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    options:
      - name: ndots
        value: "2"
      - name: single-request-reopen
```

改完後進 Pod 確認 resolv.conf 真的變了，並觀察 CoreDNS 的查詢數與 NXDOMAIN 比例是否下降。同時檢查服務內部是否有人用 `chat.live.svc` 這種三段名稱，ndots:2 時它會先往外查一次，要改成短名稱或完整名稱。

**情境三：部署藍綠切換或資料庫 failover 的檢查清單。**

1. 列出所有會連到這個名稱的 client，確認它們的連線池有最長壽命，並記下最大值。
2. 確認 runtime 的名稱快取（JVM 的 `networkaddress.cache.ttl`）不是永久，數值接近 DNS TTL。
3. 計算「DNS TTL＋各層快取上限＋連線最長壽命」，作為舊版至少保留的時間，寫進 runbook。
4. 切換後在舊版上觀察連線數，確認逐步下降到零才關閉；有長連線不降的，就是漏網的 client。
5. 資料庫 failover 若用 DNS 指向新的 primary，連線池必須能偵測斷線並重建，否則寫入會一直送到已降級的 replica。

**情境四：本機開發「只有我這台怪怪的」。** 先查 `/etc/hosts` 有沒有遺留的覆寫；macOS 用 `scutil --dns` 看實際生效的 resolver 與 search domain（VPN 常會加上自己的網域與 nameserver），用 `dscacheutil -q host -a name api.shengsheng.example` 看系統解析結果；Linux 桌機用 `resolvectl status` 與 `resolvectl query`。清快取前先確認是哪一層的快取，否則清了 OS 快取，瀏覽器或 JVM 仍然記得舊答案。

**情境五：設定 wildcard 憑證的 DNS-01 自動化。** 檢查清單：ACME client 使用的 DNS API 憑證只能修改 `_acme-challenge` 相關的 record 或專用的驗證 zone；有設定 CAA 且包含要用的 CA；內部與外部 zone 分開時，record 加在外部看得到的那一份；用 `dig +short TXT _acme-challenge.shengsheng.example @<每一台 NS>` 確認每台 authoritative server 都看得到；監控憑證到期日，而不是只監控更新任務有沒有跑。

## 16.12 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| `dig` 正常，程式解析到錯的 IP | `/etc/hosts` 有遺留覆寫，或 nsswitch 先問了其他來源 | `getent ahosts 名稱` 與 `dig` 對照；`grep 名稱 /etc/hosts` | 刪除覆寫；開發用的覆寫集中管理並加註解 |
| 叢集 CoreDNS 查詢暴增、大量 NXDOMAIN | Pod 的 `ndots:5` 讓外部名稱先套每個 search domain | CoreDNS metrics 的 rcode 分布；Pod 內 tcpdump 看候選名稱 | 調低 ndots、外部名稱寫絕對名稱、NodeLocal DNSCache、autopath |
| 請求偶爾剛好慢 5 秒或 10 秒 | 第一台 nameserver 沒回應，或 A／AAAA 同時送出遇到 conntrack 競態而遺失 | 延遲分布集中在 timeout 倍數；tcpdump 看到重送 | 移除壞掉的 nameserver、調小 timeout、`single-request-reopen`、NodeLocal DNSCache |
| DNS 切換後，部分服務長時間還連舊版 | 長連線不重新解析、連線池沒有壽命，或 runtime 永久快取 | 舊版上看連線來源；檢查 JVM 安全性屬性與池設定 | 設定連線最長壽命、runtime 快取 TTL；server 端定期 GOAWAY；舊版延後關閉 |
| 換成 Alpine 映像後 DNS 行為改變 | musl 與 glibc 對 nameserver、選項、TCP fallback 的處理不同 | 比對兩種映像的 `getent` 結果與封包 | 換回 glibc 映像，或調整 resolv.conf 使兩者行為一致 |
| `localhost` 有時連得上、有時被拒 | server 只 bind IPv4，client 先試 `::1` 且沒有依序嘗試 | `getaddrinfo` 輸出看順序；`ss -ltn` 看 bind 位址 | client 依序嘗試所有位址，或 server 同時 bind IPv4 與 IPv6 |
| Pod 解析不到叢集內 Service 名稱 | dnsPolicy 是 `Default` 或 hostNetwork Pod 沒設 `ClusterFirstWithHostNet` | Pod 內 resolv.conf 的 nameserver 不是 kube-dns | 改用正確的 dnsPolicy |
| DNS-01 驗證失敗，但自己查得到 TXT | 只有部分 authoritative server 更新，或 record 加在內部 zone | 對每台 NS 分別 `dig TXT`；從外部網路查 | 等待傳播完成再通知 CA；在外部 zone 新增；用 CNAME 委派到驗證 zone |
| 憑證簽發被 CA 拒絕，驗證本身成功 | CAA record 不包含該 CA，或限制了帳號與驗證方式 | `dig CAA shengsheng.example` | 修正 CAA，加入要使用的 CA |

除錯時最重要的原則，是先確定自己在觀察哪一層。`dig` 測的是 DNS 伺服器；`getent` 測的是 libc 與 nsswitch；程式內 log 解析結果，測的才是 runtime 與應用程式快取；而已經建立的連線，要從 `ss -tnp` 或對端的連線清單看。四層的答案可能各自不同，而每一層都可能是對的，只是時間點不一樣。

## 16.13 動手練習

1. **延伸請求計數程式。** 修改 16.10 節的假 DNS server 程式，讓 resolver 加上一個簡單的 negative cache：NXDOMAIN 的答案保留 30 秒（模擬時鐘即可）。連續解析 `pay.example.net` 兩次，第二次實際送出幾個請求？
   答案要點：第一次 10 個；第二次前四個候選都命中 negative cache，不送出，只剩最後一個候選的 A 與 AAAA，共 2 個。若再加上正面答案的快取，第二次會是 0 個。這說明 NodeLocal DNSCache 與 CoreDNS cache 為什麼能大幅降低 ndots 的成本。

2. **加入 timeout 模擬。** 在同一支程式加入第二個「永遠不回應」的 nameserver，排在清單第一位，resolver 設 `timeout` 為 0.2 秒、`attempts` 為 2。量測 `chat` 與 `pay.example.net` 的總耗時。
   驗證方法：`chat` 約多等 2 次 timeout（A 與 AAAA 各一次），`pay.example.net` 約多等 10 次，耗時與「候選數 × 2 × timeout」成正比；這就是第一台 nameserver 故障時，ndots 讓延遲放大的機制。

3. **用真實工具觀察 search 展開。** 在一台 Linux 機器或容器內，執行 `sudo tcpdump -ni any port 53`，另開一個終端機執行 `getent ahosts www.example.com`，再執行 `getent ahosts www.example.com.`（結尾有點）。比較兩次抓到的查詢名稱。
   驗證方法：若 resolv.conf 有 search domain 且 ndots 大於名稱的點數，第一次會看到帶 search 後綴的查詢，第二次沒有。若在 Kubernetes Pod 內做，能看到與 16.7 節時序圖相同的序列。

4. **比較 dig 與 getent。** 在 `/etc/hosts` 暫時加一行 `192.0.2.10 test.shengsheng.example`，分別執行 `dig test.shengsheng.example` 與 `getent hosts test.shengsheng.example`，然後刪除這一行。
   答案要點：`getent` 回傳 `192.0.2.10`，`dig` 回傳 NXDOMAIN 或其他結果，因為 `dig` 不讀 `/etc/hosts`。練習結束務必刪除，這正是故事裡小晴遇到的陷阱。

5. **為長連線程式加上抖動。** 修改 16.10 節的連線池程式，改成 5 個 `recycle+ttl` 的池，每個池的連線壽命在 45 到 75 秒之間隨機（用固定亂數種子），印出每個時間點打到新版的池數。
   答案要點：流量會在一段時間內逐步移到新版，而不是同一秒全部切換；加入隨機抖動可以避免所有 client 同時重連，造成新版瞬間的連線尖峰。

## 本章重點整理

- 多數程式透過 libc 的 `getaddrinfo` 解析名稱，它依 nsswitch 決定來源順序，只有輪到 `dns` 來源時才讀 resolv.conf 並送出 DNS 封包。
- `dig` 直接對 nameserver 送 DNS，不讀 `/etc/hosts`、不走 nsswitch、預設不套 search；要重現程式看到的答案，用 `getent ahosts`。
- `getaddrinfo` 回傳的是排序過的位址清單；client 應依序嘗試，dual stack 環境下只用第一筆會造成間歇性連線失敗。
- `/etc/hosts` 在常見設定裡優先於 DNS，而且沒有 TTL；遺留的測試覆寫是「只有我這台怪怪的」的常見原因。
- resolv.conf 的多個 nameserver 預設是依序嘗試而不是負載分散；第一台故障時，每次查詢都會先白等 timeout 秒。
- 名稱的點數少於 ndots 就先套 search domain；結尾帶點的絕對名稱完全不套 search。
- `AF_UNSPEC` 讓每個候選名稱都問 A 與 AAAA，Kubernetes 的 `ndots:5` 加上四個 search domain，會讓一次外部名稱解析送出 10 個請求，其中 8 個是 NXDOMAIN。
- Kubernetes 上偶發的 5 秒 DNS 延遲，常見原因是 A 與 AAAA 同時送出時遇到 conntrack 競態；NodeLocal DNSCache 與 `single-request-reopen` 是常用緩解。
- 已建立的長連線不會重新解析 DNS；要讓 DNS 切換生效，連線池需要最長壽命，runtime 快取（例如 JVM）也不能是永久。
- DNS 切換後，舊版至少要保留「TTL＋各層快取上限＋連線最長壽命」的時間，並以 graceful shutdown 結束。
- 服務發現可以由 client 或 server 端挑後端，清單可以來自 DNS、registry、平台 API 或 service mesh；DNS 最通用，但不帶 port 與健康資訊，且受快取限制。
- ACME DNS-01 在 `_acme-challenge` 放一筆 TXT，值是 token 與帳號金鑰 thumbprint 的 SHA-256，可用來申請 wildcard 與內部主機的憑證。
- DNS-01 的常見失敗來自傳播未完成、split-horizon 與 CAA；DNS API 憑證要限縮權限，可用 CNAME 委派到專用驗證 zone。

## 延伸問答

> [!question]- Q1. `getaddrinfo` 和「DNS 查詢」差在哪裡？為什麼除錯時要區分？
> `getaddrinfo` 是 libc 提供的通用名稱解析介面，它依 nsswitch 的 `hosts:` 行依序詢問多個來源，DNS 只是其中一個；在問 DNS 之前，它還會判斷輸入是否為數字位址、查 `/etc/hosts`、可能問 mDNS 或 systemd-resolved。輪到 DNS 時，它還要套用 resolv.conf 的 search 與 ndots，把一個名稱展開成多個候選，每個候選再分別問 A 與 AAAA。
>
> 除錯時區分的原因是，「DNS 查詢」這個詞通常指 `dig` 做的事：對某台 nameserver 送一個指定名稱與型別的封包。這和程式實際走的路徑可能完全不同。`dig` 正常只能證明 DNS 伺服器能回答那個完整名稱，不能證明程式的解析是對的；要驗證程式的視角，要用 `getent ahosts`，或在程式裡印出解析結果。

> [!question]- Q2. 手算題：Pod 的 search 清單有三個 Kubernetes 網域，ndots:5。程式解析 `db.internal.shengsheng.example`（存在，有 A 也有 AAAA），會送出幾個 DNS 查詢？改成 ndots:3 呢？
> 這個名稱有三個點。ndots:5 時三個點少於 5，所以先套 search：`db.internal.shengsheng.example.live.svc.cluster.local`、`…svc.cluster.local`、`…cluster.local` 三個候選都會 NXDOMAIN，最後才查原名並成功。每個候選問 A 與 AAAA 兩次，共 4 個候選乘以 2，等於 8 個查詢，其中 6 個注定失敗。
>
> 改成 ndots:3 時，三個點大於或等於 3，先原樣查，第一個候選就成功，只需要 2 個查詢。若節點還繼承了額外的 search domain，ndots:5 的情況會再多 2 個查詢。手算時記住三件事：點數與 ndots 的比較方向、每個候選乘以 2、名稱存在（NOERROR）就停止。

> [!question]- Q3. 你在 production 看到某服務的 p99 延遲剛好落在 5.0x 秒，其他時候正常。你會怎麼懷疑與確認？
> 延遲精確地落在 5 秒附近，強烈暗示某個預設 5 秒的逾時被觸發，而 glibc resolver 的預設 timeout 正是 5 秒。最常見的兩種原因是：resolv.conf 的第一台 nameserver 偶爾不回應，resolver 等滿 5 秒才換下一台；或者 A 與 AAAA 從同一個 socket 同時送出，在 conntrack 做 DNAT 時遇到競態，其中一個封包被丟掉，resolver 等滿 5 秒再重送。
>
> 確認方法：在 Pod 所在節點用 tcpdump 抓 port 53，找出相隔 5 秒的重送查詢；檢查 conntrack 的插入失敗統計；看 CoreDNS 本身的延遲 metrics 是否正常，若 CoreDNS 很快，問題就在 Pod 到 CoreDNS 之間。修正方向包括 `single-request-reopen`、NodeLocal DNSCache，以及調小 timeout 讓失敗更快重試。

> [!question]- Q4. 為什麼說「DNS TTL 設短一點，切換就會很快」是不完整的？
> TTL 只約束遵守 TTL 的快取，例如 recursive resolver、CoreDNS 的 cache 外掛、systemd-resolved。但在應用程式這一側，還有幾層不受 TTL 影響：JVM 的 `InetAddress` 快取依自己的 `networkaddress.cache.ttl` 決定，可能被設成永久；有些程式或 nginx 設定只在啟動時解析一次；最重要的是，已建立的 TCP 連線完全不會重新解析，只要連線還活著，流量就繼續送到舊 IP。
>
> 所以真正的切換時間是「DNS TTL、runtime 快取、連線最長壽命」三者綜合的結果，最慢的那個 client 決定何時能關舊版。完整的作法是 DNS TTL 適度縮短、runtime 快取設為有限、連線池設定最長壽命、server 端定期請 client 換連線，再在舊版上觀察連線數降到零才關閉。

> [!question]- Q5. 面試題：Kubernetes 為什麼預設 ndots:5？如果是你，會把它改掉嗎？
> 預設 ndots:5 的目的是讓叢集內的各種相對名稱都能先透過 search 清單找到：同 namespace 的 `chat`、跨 namespace 的 `chat.live`、`chat.live.svc`，以及點數較多的 SRV 形式相對名稱，都不需要寫出完整的 `cluster.local` 名稱。對叢集內的服務來說，這讓設定很簡潔，也讓同一份設定在不同 namespace 裡自動指向各自的服務。
>
> 代價是點數少於 5 的外部名稱都要先試完所有 search domain，查詢量放大數倍，並在上游 resolver 增加負擔。是否改掉取決於工作負載：大量呼叫外部 API 的服務，值得用 dnsConfig 把 ndots 降到 2 左右，或在設定裡使用絕對名稱；主要呼叫叢集內服務的元件可以保留預設。全叢集層級則可以先部署 NodeLocal DNSCache，降低放大後的成本，再針對熱點服務個別調整。

> [!question]- Q6. 看 log 找原因：某 Java 服務在資料庫 failover 後持續報「read-only transaction」錯誤 20 分鐘，之後自己恢復。可能發生了什麼？
> 這個症狀表示服務在 failover 後仍持續連到舊的 primary，而舊 primary 已經降為唯讀的 replica，所以寫入失敗。資料庫 failover 常透過 DNS 把同一個 endpoint 名稱改指新的 primary，但服務的連線池裡已經有一批建立好的連線，它們不會重新解析 DNS，只要連線沒斷，就會繼續送到舊節點。
>
> 20 分鐘後自己恢復，通常對應連線池的最長壽命或閒置逾時：舊連線逐一到期被關掉，重建時解析到新 primary。修正方向是縮短連線最長壽命、讓連線池在收到唯讀錯誤時主動丟棄連線，並確認 JVM 的名稱快取不是永久；若使用的資料庫驅動支援 failover 感知，也可以啟用它。

> [!question]- Q7. client-side discovery 與 server-side discovery 各適合什麼情況？gRPC 為什麼常搭配 headless Service？
> server-side discovery 讓呼叫方只認一個固定位址，由 load balancer 或 kube-proxy 挑後端，適合多語言、多團隊、呼叫方很難統一實作的情況，HTTP/1.1 的短請求在這種模式下也能自然分散。client-side discovery 讓呼叫方拿到完整實例清單並自己挑，能做到每個請求層級的負載分散、依延遲挑選或區域優先，但每種語言的 client 都要有發現與健康檢查邏輯。
>
> gRPC 建在 HTTP/2 上，一條長連線承載大量請求。若透過一般 Service 的 ClusterIP 連線，kube-proxy 只在建立連線時挑一次後端，之後所有請求都落在同一個 Pod，負載分散失效。改用 headless Service，DNS 會回傳所有就緒 Pod 的 IP，gRPC client 對每個 Pod 建立連線並以 round robin 分散請求；再搭配 server 端的連線最長壽命，讓 client 定期重新解析，新加入的 Pod 才分得到流量。

> [!question]- Q8. 設計取捨：DNS-01 自動化需要一把 DNS API 憑證，怎麼降低它外洩的風險？
> 能修改 DNS 的憑證等同能把網域的流量導到任何地方，也能替網域申請任何憑證，所以它的權限必須盡量小。第一步是限縮範圍：若 DNS 供應商支援 record 層級的權限，只允許修改 `_acme-challenge` 相關的 TXT record；若不支援，就把 `_acme-challenge.shengsheng.example` 用 CNAME 指到一個專門的驗證 zone，ACME client 只拿那個 zone 的權限，CA 會跟著 CNAME 去查 TXT。
>
> 第二步是限縮使用者與時間：憑證只存在執行 ACME client 的那個元件裡（例如 Kubernetes 的 cert-manager），透過 secrets 管理系統注入並定期輪替，盡量用工作負載身分取代長期金鑰（第 30 章）。第三步是縱深防禦：設定 CAA 限制可簽發的 CA，必要時再限定帳號；並監控 Certificate Transparency log（第 19 章），發現非預期的憑證時能及早處理。
