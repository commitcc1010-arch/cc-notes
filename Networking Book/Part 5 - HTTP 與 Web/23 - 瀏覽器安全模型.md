# 第 23 章　瀏覽器安全模型：Same-Origin、CORS 與 CSP

> [!abstract] 本章地圖
> **核心問題**：同一個瀏覽器裡同時開著聲聲 Live 和任意陌生網站，瀏覽器靠哪些規則讓陌生網站讀不到學生的資料、也冒用不了學生的身分？伺服器又該送出哪些 header 來配合？
>
> **你會學到**：
> - 精確說出 origin 與 site 的定義，判斷兩個 URL 是否 same-origin、是否 same-site
> - 解釋 same-origin policy 擋的是「讀取」而不是「送出」，以及這個設計如何導出 CSRF 問題
> - 逐步走完 CORS 的 simple request、preflight 與 credentials 規則，寫出允許清單、preflight 快取與 `Vary: Origin` 都正確的 API server
> - 依 `Secure`、`HttpOnly`、`Domain`、`Path`、`SameSite` 與 `__Host-` 前綴設計 session cookie，預測每種跨站情境下 cookie 會不會被送出
> - 用 synchronizer token、signed double-submit、Origin 與 Fetch Metadata 組出 CSRF 防禦；用輸出編碼與 nonce-based CSP 防禦 XSS；用 `frame-ancestors` 防禦 clickjacking
> - 看懂 DevTools 的 CORS 錯誤與 CSP 違規報告，知道該改前端、改 server 還是改 CDN
>
> **前置知識**：第 1 章（打開網頁的流程與 CORS 預告）、第 18 章（TLS 與 HTTPS）、第 20 章（HTTP 請求與回應、method 語意）、第 21 章（cookie 語法、快取與 `Vary`）

## 23.1 故事：只差一個 header 的預約按鈕

聲聲 Live 要上線「預約試聽」：學生在 `www.shengsheng.example/booking` 選好老師與時段，頁面的 JavaScript 呼叫 `api.shengsheng.example` 的 `POST /v1/bookings`，body 是 JSON，header 帶著登入後拿到的短效 JWT（`Authorization: Bearer …`，第 27 章）。access token 過期時，頁面再呼叫 `POST /v1/session/refresh`，靠一個 `HttpOnly` 的 refresh cookie 換新的 token。小晴在本機開發時一切順利，因為前端的開發伺服器把 `/v1` 代理到本機的 Flask，瀏覽器以為頁面和 API 是同一個來源。

部署到 staging 的第一天，按鈕按下去沒有反應。DevTools 的 Console 一片紅，錯誤訊息的後半段寫著「has been blocked by CORS policy: Response to preflight request doesn't pass access control check」。小晴先在 Flask 的 `after_request` 加上 `Access-Control-Allow-Origin: *` 與 `Access-Control-Allow-Headers: *`，預約還是失敗；refresh 也失敗，錯誤訊息換成「The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'」。小晴上網搜尋，找到一段被大量轉貼的程式：把請求的 `Origin` 原封不動寫回 `Access-Control-Allow-Origin`，再加上 `Access-Control-Allow-Credentials: true`。這次全部都通了。

程式碼審查時，資安工程師 Rita 直接擋下：「這等於告訴瀏覽器，**任何網站**都可以帶著學生的 cookie 呼叫 refresh，而且可以讀到回應裡的新 token。現在沒出事只是運氣：refresh cookie 沒寫 `SameSite`，Chrome 剛好把它當成 `Lax`，外站的 `fetch()` 帶不出它；但同 site 的子網域、或允許第三方 cookie 又沒有這個預設的瀏覽器，都擋不住。」阿德補了第二個問題：團隊為了扛住晚上八點的尖峰，讓 CDN 也快取公開的 `GET /v1/courses`，而 API 的回應沒有 `Vary: Origin`。老師後台 `teach.shengsheng.example` 那天下午開始偶發 CORS 錯誤，原因是 CDN 把一份 `Access-Control-Allow-Origin` 寫著 www 的 origin 的回應，交給了來自老師後台的請求。

```text
 ① 本機開發：同一個 origin，沒有 CORS
    瀏覽器 ──► http://localhost（前端 dev server）──代理 /v1──► Flask

 ② staging：跨 origin，preflight 失敗
    www.shengsheng.example 的頁面 ──OPTIONS /v1/bookings──► api.shengsheng.example
                                    ◄── 200，沒有任何 Access-Control-* ──  ✗ 實際請求沒送出

 ③ 「修好」之後：反射 Origin ＋ Allow-Credentials
    任何網站的頁面 ──POST /v1/session/refresh（帶 cookie）──► api
                   ◄── ACAO: <你的 origin>、ACAC: true ──      ✗ 讀得到新 token

 ④ CDN 快取沒有 Vary: Origin
    www 的請求 ──► CDN ──► api：ACAO = www  ─┐ 存進快取
    teach 的請求 ──► CDN（命中）◄─────────────┘ 拿到 ACAO = www  ✗ 被瀏覽器擋下
```

這張圖由上往下是事件的時間順序。① 解釋了「本機都正常」：同一個 origin 的請求不受 CORS 管。② 是真正的起點：JSON body 與 `Authorization` header 讓瀏覽器先送出 preflight（預檢請求），server 沒有正確回答，瀏覽器就連實際請求都不送。③ 是最危險的一步：錯誤的修法把瀏覽器最重要的保護整個關掉了。④ 則提醒我們，CORS header 也是回應的一部分，會被快取，必須和 `Vary` 一起設計。

阿德把事情拆成三個問題讓小晴回去研究：瀏覽器到底在保護什麼？CORS 的每一個 header 在回答瀏覽器的什麼問題？cookie 為什麼會被跨站送出，又要怎麼防止別人借用它？這一章會依序回答，並在 23.11 節把瀏覽器的 CORS 演算法、一個正確的 API server、SameSite 規則、CSRF token 與 CSP nonce 都在 127.0.0.1 上實作一次。

## 23.2 Origin 與 site：瀏覽器的兩把尺

瀏覽器的安全規則幾乎都建立在兩個概念上。第一個是 **origin**（來源）：URL 的 **scheme**（協定，例如 `https`）、**host**（主機名稱）與 **port**（埠號）三者合起來。三者完全相同才算 **same-origin**（同源）；路徑、query string 與 fragment 不在 origin 裡。例如 https 的 `www.shengsheng.example/booking` 和 `www.shengsheng.example/teachers/美咲` 是同源，`api.shengsheng.example/v1` 則和它們不同源，因為 host 不同。為了不在正文放網址，本章正文提到 origin 時只寫 host，沒有特別註明的，scheme 都是 https、port 都是預設的 443；完整的 origin 字串（scheme、冒號、兩個斜線、host）只出現在圖與程式裡。

```text
   https :// www.shengsheng.example : 443 /booking ? teacher=7 # slots
   └─┬─┘    └─────────┬──────────┘   └┬┘ └───────────┬─────────────────┘
   scheme            host            port   不屬於 origin（path、query、fragment）
   └──────────────── origin ─────────────┘
                     origin 字串寫成：https://www.shengsheng.example（預設 port 省略）

   host 再拆：   www . shengsheng . example
                       └────────┬────────┘
                 registrable domain（eTLD+1）＝ shengsheng.example
                                  └──┬──┘
                      public suffix（eTLD）＝ example
   site ＝ scheme ＋ registrable domain ＝ (https, shengsheng.example)
```

這張圖由上而下讀。第一列把 URL 切成 origin 與其餘部分；origin 以字串表示時，預設 port（https 的 443、http 的 80）會省略，所以網址裡明寫 `:443` 和省略 port 的 https 網址是同一個 origin。下半部引入第二把尺 **site**（站點）：先找出 host 的 **public suffix**（公共後綴，又稱 eTLD，例如 `com`、`co.uk`，以及託管平台登記的使用者子網域後綴），再往左多取一段，就是 **registrable domain**（可註冊網域，又稱 eTLD+1）。site 由 scheme 加上 registrable domain 組成，所以 `www.shengsheng.example`、`api.shengsheng.example`、`teach.shengsheng.example` 全部是同一個 site。

公共後綴來自瀏覽器內建、由社群維護的 **Public Suffix List**（公共後綴清單），除了 `com`、`tw` 這類頂級網域，也收錄讓使用者各自擁有子網域的託管平台後綴。如果 `pages.example` 在清單上，`alice.pages.example` 和 `bob.pages.example` 就是不同 site，不能共享 cookie；反過來，聲聲 Live 的所有子網域都在同一個 site 裡，任何一個出問題都會影響 site 層級的保護。

| 比較對象（基準：https、`www.shengsheng.example`、443） | same-origin？ | same-site？ | 原因 |
|---|---|---|---|
| https、`www.shengsheng.example`，路徑 `/teachers/美咲` | 是 | 是 | 只有路徑不同 |
| https、`www.shengsheng.example`、port 8443 | 否 | 是 | port 不同；site 不看 port |
| http、`www.shengsheng.example` | 否 | 否 | scheme 不同；現行規格的 site 包含 scheme |
| https、`api.shengsheng.example` | 否 | 是 | host 不同，但 registrable domain 相同 |
| https、`shengsheng.example` | 否 | 是 | host 不同，registrable domain 相同 |
| https、`phish.example` | 否 | 否 | registrable domain 不同 |
| https、`alice.pages.example` 對 `bob.pages.example` | 否 | 否 | `pages.example` 是公共後綴 |

這張表裡最常被搞錯的是第三列與第四列。早期的 site 定義不看 scheme，`http` 與 `https` 版本算同一個 site；現行的 cookie 規格與主流瀏覽器改用 **schemeful same-site**，http 頁面對 https 的請求被當成跨站，這讓明文網路上的攻擊者更難利用 cookie。第四列則是本章的核心張力：`www` 與 `api` 是**跨 origin、但同 site**，所以 CORS 要管（它看 origin），而 SameSite cookie 不擋（它看 site）。

> [!warning] 常見誤解
> 「同一個公司的子網域彼此信任，所以是安全的」。瀏覽器的 origin 邊界不認公司，只認 scheme、host 與 port。行銷活動用的 `promo.shengsheng.example` 如果託管在外部平台而被人接管，它和 `api` 同 site，能替整個 `shengsheng.example` 設 cookie、送出不受 SameSite 限制的請求。site 是比 origin 弱得多的邊界，不要把它當成信任邊界。

## 23.3 Same-origin policy：擋的是「讀」，不是「送」

瀏覽器同時替使用者保管許多網站的身分：聲聲 Live 的 session cookie、公司內網的登入狀態、家裡路由器的管理介面。這些身分有一個共同特性：瀏覽器會**自動**把它們附在請求上，網頁不用、也無法事先徵求使用者同意。這種「不必出示就自動生效的權限」稱為 **ambient authority**（環境權限），例如學生只要登入過，任何送往 `api.shengsheng.example` 的請求都可能帶著 cookie。如果任何網頁都能對任何網站發請求並讀回應，陌生網站就能在學生不知情時讀走課表、私訊與付款紀錄。

**Same-origin policy**（同源政策，SOP）就是瀏覽器對這個問題的基本回答：一個 origin 的腳本，**不能讀取**另一個 origin 的資源內容，也不能操作對方的 DOM 與儲存空間（`localStorage`、IndexedDB 都以 origin 為單位隔離）。但它是在 1990 年代的 Web 上補上去的規則，當時網頁早就能用 `<img>` 載入別站圖片、用 `<form>` 把資料送到別站、用 `<script src>` 執行別站的程式。為了不破壞既有網站，SOP 選擇只擋「讀」，而保留「嵌入」與「送出」。

```text
   phish.example 的頁面（在學生的瀏覽器裡）               api.shengsheng.example
        │
        │ ① 嵌入：<img src=…>、<script src=…>、<link rel=stylesheet>   ──► 允許送出，結果只能「用」不能「讀」
        │ ② 送出：<form method=post action=…> 自動送出                ──► 允許送出，而且可能帶著 cookie
        │ ③ 讀取：fetch() 後讀 response.json()                         ──► 請求可能已送到 server，
        │                                                                   但瀏覽器不把回應交給腳本
        │ ④ DOM：window.open() 後讀對方頁面內容                        ──► 禁止
        ▼
   瀏覽器的判斷：送出幾乎都可以；讀取要對方用 CORS 明確同意
```

這張圖的四條箭頭由寬到嚴。① 嵌入的資源可以被頁面「使用」：圖片會顯示、腳本會執行，但頁面讀不到圖片的像素或腳本的原始碼（canvas 遇到跨源圖片會被標為「汙染」而無法匯出）。② 是安全問題的根源：跨站送出的表單會帶著目標網站的 cookie（是否帶，要看 23.5 節的 SameSite），server 會照常處理，這就是 23.6 節的 CSRF。③ 最容易誤會：SOP 並不阻止請求抵達 server，很多情況下 server 已經執行了，只是瀏覽器不讓腳本看結果。④ 跨源的視窗之間只能透過 `postMessage` 這類明確的訊息通道溝通。

| 動作 | 同源 | 跨源（沒有 CORS） | 防禦重點 |
|---|---|---|---|
| 嵌入圖片、腳本、樣式、iframe | 可以 | 可以（內容不可讀） | `X-Content-Type-Options: nosniff`、CORP、`frame-ancestors` |
| 送出表單、導覽到某 URL | 可以 | 可以，可能帶 cookie | SameSite、CSRF token、Origin 檢查 |
| `fetch()`／XHR 送出 simple request | 可以 | 送得出去，回應不可讀 | server 端授權；變更操作不能只靠 CORS |
| `fetch()` 送出非 simple request | 可以 | 先 preflight，被拒就不送 | 正確的 CORS 允許清單 |
| 讀取對方回應、DOM、storage | 可以 | 禁止 | CORS 只放寬回應讀取，不放寬 DOM |

這張表要記住的是最右一欄：每一種被允許的跨源行為，都需要某種伺服器端或 header 的配合來防禦。SOP 本身不是防火牆，它是一套「預設不讓讀」的規則，加上幾個由伺服器決定是否放寬的開口。

還有兩個例外要知道。舊的 `document.domain` 設定能讓同 site 的頁面互讀 DOM，主要瀏覽器已逐步讓它失效，跨源溝通改用 `postMessage` 並檢查訊息的 `origin`。另一個是 WebSocket：瀏覽器建立 WebSocket 時**不做 CORS 檢查**，只在握手請求裡帶上 `Origin` header，所以聲聲 Live 的即時服務 `rt.shengsheng.example` 必須自己用允許清單檢查 `Origin`，否則任何網站都能用學生的 cookie 開一條教室連線（第 32 章）。

## 23.4 CORS：伺服器主動放寬讀取

SOP 把跨源讀取全部擋掉，但現代網站本來就由許多 origin 組成：聲聲 Live 的頁面在 `www`，API 在 `api`，登入在 `auth`。**CORS**（Cross-Origin Resource Sharing，跨來源資源共享）是一套讓 server 用 HTTP header 告訴瀏覽器「我允許哪個 origin 讀我的回應」的協議。它的規格現在寫在 WHATWG 的 Fetch Standard 裡，舊的 W3C CORS 文件已被取代。關鍵觀念是：CORS **只會放寬**瀏覽器的限制，永遠不會讓請求變得更安全；決定權在 server，執行者是瀏覽器。

瀏覽器把跨源的 `fetch()` 分成兩類。第一類是 **simple request**（簡單請求，業界通用的稱呼，Fetch 規格裡沒有這個正式名稱）：瀏覽器直接送出，再檢查回應。第二類要先送 **preflight**（預檢請求）：一個 `OPTIONS` 請求，先問 server「我等一下要用這個 method、帶這些 header，可以嗎」，得到同意才送真正的請求。分界線很務實：1990 年代的 `<form>` 本來就送得出去的請求，多做一次 preflight 也擋不住什麼，所以直接送；表單送不出來的請求（`PUT`、自訂 header、`application/json`），舊的 server 從沒預期會從別的網站收到，所以要先問。

| 條件 | simple request 的範圍 | 超出就需要 preflight 的例子 |
|---|---|---|
| method | `GET`、`HEAD`、`POST` | `PUT`、`PATCH`、`DELETE` |
| 自訂 header | 只能有 CORS-safelisted 的 `Accept`、`Accept-Language`、`Content-Language`、`Content-Type`（另有少數特例，值有長度限制） | `Authorization`、`X-CSRF-Token`、`X-Request-Id` |
| `Content-Type` | `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain` | `application/json` |
| 其他 | 沒有可讀串流 body、沒有上傳進度監聽 | `ReadableStream` body |

這張表的每一列都對應故事裡的現象。預約 API 用 `application/json` 加上 `Authorization`，兩個條件都超出範圍，所以必定 preflight。反過來看，`Content-Type: text/plain` 的 `POST` 不會 preflight，這解釋了為什麼「我的 API 只收 JSON，所以外站送不進來」是錯的：如果 server 不檢查 `Content-Type`、拿到任何 body 都當 JSON 解析，外站就能用不需 preflight 的 `text/plain` 請求觸發同樣的處理。server 應該對不符的 `Content-Type` 回 415。

### simple request：先送，再看能不能讀

```text
 www 頁面裡的 JavaScript         瀏覽器                              api.shengsheng.example
   │ fetch(GET /v1/courses)       │                                        │
   │─────────────────────────────►│── GET /v1/courses ────────────────────►│
   │                              │   Origin: https://www.shengsheng.example
   │                              │                                        │ 照常處理請求
   │                              │◄── 200 OK ─────────────────────────────│
   │                              │   Access-Control-Allow-Origin: https://www.shengsheng.example
   │                              │   Vary: Origin                         │
   │                              │ CORS 檢查：ACAO 等於本頁 origin？        │
   │◄──── 通過：交出 response ─────│                                        │
   │      失敗：TypeError，看不到狀態碼與 body                               │
```

這張時序圖說明了 simple request 的三個事實。第一，`Origin` 由瀏覽器自動加上，頁面無法偽造或移除，所以它可信地代表「發出請求的頁面」（但不代表使用者，curl 可以送任何 `Origin`）。第二，server 在 CORS 檢查之前就已經處理完請求，會改變狀態的 `POST` 此時副作用已經發生。第三，檢查失敗時 JavaScript 只拿到籠統的 `TypeError`，連狀態碼都看不到，詳細原因只出現在 DevTools 的 Console，這是為了不讓外站藉錯誤細節探測內網。

回應即使通過檢查，腳本預設也只能讀到少數 **CORS-safelisted response header**：`Cache-Control`、`Content-Language`、`Content-Length`、`Content-Type`、`Expires`、`Last-Modified`、`Pragma`。聲聲 Live 用來串接 log 的 `x-request-id`（第 20 章用它串起 nginx 與 Flask 的 log）要讓前端讀到並附在錯誤回報裡，server 必須加上 `Access-Control-Expose-Headers: x-request-id`。

### preflight：先問，再送

```text
 瀏覽器                                                        api.shengsheng.example
   │ 預檢快取裡沒有 (www, /v1/bookings, POST, authorization+content-type)
   │── OPTIONS /v1/bookings ──────────────────────────────────────────►│
   │   Origin: https://www.shengsheng.example                          │ 不需要登入，
   │   Access-Control-Request-Method: POST                             │ 也收不到 cookie
   │   Access-Control-Request-Headers: authorization,content-type      │
   │◄── 204 No Content ────────────────────────────────────────────────│
   │   Access-Control-Allow-Origin: https://www.shengsheng.example     │
   │   Access-Control-Allow-Methods: DELETE, GET, POST                 │
   │   Access-Control-Allow-Headers: authorization, content-type, x-csrf-token
   │   Access-Control-Allow-Credentials: true                          │
   │   Access-Control-Max-Age: 600                                     │
   │   Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers
   │ 檢查通過 → 寫入預檢快取 600 秒                                      │
   │── POST /v1/bookings（Authorization、JSON body）───────────────────►│
   │◄── 201 Created ＋ ACAO ＋ ACAC ───────────────────────────────────│
   │ 再做一次 CORS 檢查，通過才交給 JavaScript                            │
```

這張圖要分兩段讀。上半段是 preflight：瀏覽器把等一下要用的 method 與「非 safelisted 的 header 名稱」（小寫、排序、逗號分隔）告訴 server，server 用 `Allow-Methods` 與 `Allow-Headers` 回答允許的範圍。preflight 的回應必須是 2xx，而且 **preflight 本身不會帶 cookie 或 `Authorization`**，所以 server 絕不能要求 `OPTIONS` 先通過登入驗證；很多團隊把驗證 middleware 套在所有路由上，結果 `OPTIONS` 拿到 401，這是 preflight 失敗最常見的原因之一。下半段是真正的請求，它的回應還要再過一次 CORS 檢查，preflight 通過不代表實際回應可以省略 `Access-Control-Allow-Origin`。

`Access-Control-Max-Age` 讓瀏覽器把預檢結果快取一段時間，省掉後續同樣請求的一個 RTT，對第 1 章那位 RTT 180 ms 的美國學生是感受得到的。快取以 origin、URL、credentials 模式為範圍，記下被允許的 method 與 header，換一個 URL 或多帶一個沒被允許過的 header 都要重新 preflight。沒有這個 header 時只快取約 5 秒，各瀏覽器也都設有上限（Chromium 約 2 小時，Firefox 約 24 小時，依實作而定）。

> [!tip] 減少 preflight 的方法
> 把 API 放在同一個 origin 之下（例如 `www.shengsheng.example/api`，由 CDN 或 LB 轉送）可以完全避開 CORS。保持跨源時，設定合理的 `Max-Age`、讓同類請求用固定的 header 集合；不要為了省 preflight 把 JSON 改成 `text/plain`，那等於親手拿掉一層保護。

### credentials：帶身分的跨源請求有更嚴格的規則

跨源 `fetch()` 預設不帶 cookie，前端要明確寫 `credentials: "include"`（XHR 是 `withCredentials = true`），這種請求稱為 **credentialed request**（帶憑證的請求）。回應這時可能含有私人資料，所以規格收緊成三條：`Access-Control-Allow-Origin` 必須是明確的 origin 而不能是 `*`；必須有 `Access-Control-Allow-Credentials: true`；`Allow-Methods`、`Allow-Headers`、`Expose-Headers` 裡的 `*` 不再是萬用字元。另有一條無論如何都成立的特例：`Access-Control-Allow-Headers: *` **永遠不涵蓋 `Authorization`**，必須明列。

```text
                      ┌─────────────────────────────────┐
                      │ 回應有 Access-Control-Allow-Origin？│── 否 ──► ✗ 擋下
                      └───────────────┬─────────────────┘
                                      │ 是
                      ┌───────────────▼─────────────────┐
                      │ 值是 "*"？                       │
                      └───────┬─────────────────┬───────┘
                           是 │                 │ 否
              ┌───────────────▼──────┐   ┌──────▼──────────────────────┐
              │ 請求帶 credentials？  │   │ 逐字等於本頁 origin？（單一值）│── 否 ──► ✗
              └───┬──────────────┬───┘   └──────┬──────────────────────┘
               否 │              │ 是           │ 是
                  ▼              ▼       ┌──────▼──────────────────────┐
               ✓ 可讀         ✗ 擋下     │ 請求帶 credentials？          │── 否 ──► ✓ 可讀
                                         └──────┬──────────────────────┘
                                                │ 是
                                         ┌──────▼──────────────────────┐
                                         │ Allow-Credentials 是 "true"？│── 否 ──► ✗
                                         └──────┬──────────────────────┘
                                                ▼ 是
                                              ✓ 可讀
```

這張流程圖就是瀏覽器的 **CORS check**，preflight 回應與實際回應都要過一次，23.11 節的實驗一會把它寫成 Python 函式。從上往下看，第一個判斷說明「server 什麼都不寫」等於拒絕；第二層區分萬用字元與明確 origin；最右邊的「逐字等於」很嚴格：大小寫、port、結尾多一個斜線都算不同，`Access-Control-Allow-Origin` 也只能放**一個** origin，寫成逗號分隔的清單會直接失敗。所以要允許多個 origin，server 必須在程式裡比對允許清單，命中時回寫那一個 origin。

這也正是故事裡「反射 Origin」修法的問題所在。反射本身是允許多個 origin 的標準做法，錯在**沒有比對允許清單**：把任何 `Origin` 都寫回去，再加上 `Allow-Credentials: true`，等於對全世界的網站開放「用學生身分讀取回應」。故事中的 refresh endpoint 會在回應裡給出新的 access token，外站讀得到它，就等於拿到了學生的帳號。同樣要避免的還有 `Access-Control-Allow-Origin: null`：sandbox 的 iframe 與本機檔案的 origin 都會序列化成 `null`，允許它就是允許一大群無法辨識的來源。

### 快取與 `Vary: Origin`

第 21 章講過，`Vary` 告訴快取「這份回應依哪些請求 header 而不同」。只要 `Access-Control-Allow-Origin` 的值會隨 `Origin` 改變，回應就必須帶 `Vary: Origin`，否則 CDN 或瀏覽器的 HTTP 快取會把為 A 產生的回應交給 B，這正是故事裡老師後台偶發錯誤的成因。容易漏掉的細節是：**不允許**的 origin 拿到的回應（沒有 ACAO）也要加 `Vary: Origin`，否則一個沒有 ACAO 的版本被快取後，允許的 origin 也會被擋。如果某個公開資源永遠回 `Access-Control-Allow-Origin: *`，回應不隨 origin 變化，就不需要 `Vary: Origin`，CDN 的命中率也最好；這是公開課表這類資料的較佳選擇。

### CORS 不是什麼

最後要把 CORS 的定位講清楚，因為它是 junior 最常誤用的安全機制。第一，CORS **不是 server 的存取控制**：curl、行動 App、其他 server 根本不執行 CORS，它們想送什麼就送什麼，所以每個 API 仍然要做自己的驗證與授權。第二，CORS **不是 CSRF 防禦**：simple request 會在檢查之前就抵達 server 並執行，CORS 只決定回應能不能被讀。第三，CORS 錯誤**不是 server 錯誤**：server log 裡可能是一筆完全正常的 200，問題在回應少了 header，要用 DevTools 或 curl 看 header 才找得到。

> [!note] 2026 現況：CORS 規格與私有網路請求
> 截至 2026 年 10 月，CORS 的權威規格是 WHATWG Fetch Standard（living standard，沒有版本號，引用時寫存取日期）。對「公開網站存取使用者區網或本機服務」這類請求，Chrome 過去推動的 Private Network Access 方案改以「Local Network Access」權限提示的方式推進，細節與時程仍在變動，導入相關功能前要查最新的瀏覽器文件。`Access-Control-Allow-Headers: *` 不含 `Authorization` 的規則仍然有效。

## 23.5 Cookie 的安全屬性與 SameSite

CORS 決定「回應能不能被讀」，cookie 的屬性則決定「身分會不會被帶出去」。第 21 章已經講過 cookie 的語法：server 用 `Set-Cookie` 設定，瀏覽器在之後符合條件的請求中用 `Cookie` header 帶回。這一節從安全的角度看每一個屬性在防什麼。先看 Rita 替聲聲 Live 訂的 refresh cookie 設定：

```text
 Set-Cookie: __Host-refresh=7f3c…; Secure; HttpOnly; Path=/; SameSite=Lax; Max-Age=1209600
             └─────┬──────┘ └─┬─┘  └──┬─┘  └──┬──┘  └──┬───┘  └───┬────┘ └──────┬──────┘
          前綴：要求 Secure、 只在 HTTPS   JS 讀不到  整個網站   跨站時只在   沒有 Domain：   14 天後過期
          Path=/、不可有 Domain   上送出   （document    （前綴要求） 頂層 GET 導覽   只送回設定它的
                                           .cookie）                 才送出        host（host-only）
```

這張圖由左往右逐一解說。**`__Host-` 前綴**是給瀏覽器的約束：名稱以它開頭的 cookie，只有在 HTTPS 上設定、帶 `Secure`、`Path=/` 而且沒有 `Domain` 時才會被接受，於是它一定是只屬於 `api.shengsheng.example` 這個 host 的 cookie，兄弟子網域無法用同名 cookie 蓋掉它。**`Secure`** 讓 cookie 只在 HTTPS 上送出，也禁止非安全來源覆寫它。**`HttpOnly`** 讓 JavaScript 讀不到 cookie，即使頁面發生 XSS，攻擊程式也無法直接把 refresh token 帶走（但仍能在頁面上以使用者身分發請求，見 23.7 節）。不寫 **`Domain`** 的 cookie 稱為 **host-only cookie**，只送回設定它的 host；寫了 `Domain=shengsheng.example` 反而會擴大範圍，讓所有子網域都收到。

| 屬性 | 防的是什麼 | 常見錯誤 |
|---|---|---|
| `Secure` | 明文網路上被竊聽、被 http 頁面覆寫 | 本機開發用 http 而拿掉 `Secure`，上線時忘了加回 |
| `HttpOnly` | XSS 直接讀走 session cookie | 前端需要讀的值（例如 CSRF token）也設成 `HttpOnly`，導致讀不到 |
| `Domain` | 不寫才是最窄的範圍 | 為了「方便子網域共用」寫 `Domain=shengsheng.example`，把 session 送給所有子網域 |
| `Path` | 只用於分流，**不是**安全邊界 | 以為 `Path=/admin` 能隔離權限；同 origin 的頁面一樣能讀到 |
| `SameSite` | 跨站請求帶出 cookie（CSRF、跨站資訊洩漏） | 為了 iframe 嵌入改成 `None` 卻沒補 CSRF 防禦 |
| `__Host-`／`__Secure-` | 被兄弟子網域或明文連線植入、覆寫 | 用了前綴卻同時寫 `Domain`，瀏覽器直接拒收 |
| `Max-Age`／`Expires` | 限制被竊後可用的時間 | refresh cookie 設成一年 |

這張表的 `Path` 一列要特別記住：同 origin 下 `/blog` 的頁面可以開一個 `/admin` 的 iframe 讀出它的 cookie，權限隔離只能靠不同的 origin。

### SameSite：依「請求從哪個 site 發起」決定送不送

**SameSite** 屬性讓 cookie 知道自己被帶到哪種情境。瀏覽器先判斷這個請求是 **same-site** 還是 **cross-site**：比較目標 URL 的 site 與「發起請求的頂層頁面」的 site（包含 iframe 的所有祖先都要同 site 才算）。接著依屬性值決定：`Strict` 只在 same-site 請求送出；`Lax` 在 same-site 請求送出，跨站時只在**頂層導覽**（網址列改變，例如點連結）而且 method 是安全方法（`GET`、`HEAD`）時送出；`None` 任何情境都送，但必須同時有 `Secure`，而且仍受第三方 cookie 政策限制。

```text
          請求要送往 api.shengsheng.example，cookie 符合 host、Path、Secure？ ── 否 ──► 不送
                                       │ 是
                     目標 site ＝ 頂層頁面的 site（且所有祖先 frame 同 site）？
                        │ 是（same-site）                    │ 否（cross-site）
                        ▼                                    ▼
                      送出                    SameSite 值是什麼？（沒寫：Chromium 當作 Lax）
                                 ┌───────────────┼──────────────────────┐
                              Strict            Lax                    None
                                 │               │                      │
                               不送    頂層導覽且 GET／HEAD？    瀏覽器允許第三方 cookie？
                                          │是        │否            │是        │否
                                         送出       不送           送出   不送（或只送 Partitioned）
```

這張決策圖可以當成檢查清單。最上層先過「這個 cookie 屬不屬於這個請求」，`Secure` cookie 遇到 http 目標就在這一步出局。第二層用 23.2 節的 site 定義判斷同站與否；注意 `www` 頁面對 `api` 的 `fetch()` 雖然跨 origin，卻是 same-site，所以 `Strict` 的 cookie 一樣會送（前提是 `fetch()` 用了 `credentials: "include"`）。第三層的 `Lax` 分支是它最實用的地方：學生從 email 點連結進聲聲 Live 時，`Lax` 的 session cookie 會跟著頂層 `GET` 送出，使用者不必重新登入；但外站自動送出的跨站 `POST` 表單，`Lax` cookie 不會被帶上。

`Strict` 看起來最安全，代價是從 email 或搜尋結果點進來的第一個頁面不會帶 cookie，網站以為使用者沒登入；常見折衷是 session 用 `Lax`，另設一個 `Strict` 的 cookie 才允許改密碼、改付款方式。`None` 只用在真的需要跨站送出的情境，例如白板被合作夥伴以 iframe 嵌入，而且一定要搭配 23.6 節的 CSRF 防禦。

| 情境（cookie 屬於 `api.shengsheng.example`） | Strict | Lax | None（允許第三方 cookie 時） |
|---|---|---|---|
| `www` 頁面 `fetch()` api（同 site） | 送 | 送 | 送 |
| 學生從外部信箱點連結，頂層 `GET` 到 api | 不送 | 送 | 送 |
| 外站頁面的表單跨站 `POST` 到 api | 不送 | 不送 | 送 |
| 外站頁面 `fetch()`／`<img>` 打 api | 不送 | 不送 | 送 |
| 合作夥伴頁面裡的白板 iframe 發請求 | 不送 | 不送 | 送（瀏覽器封鎖第三方 cookie 時不送） |
| http 版的 `www` 頁面 `fetch()` https 的 api | 不送 | 不送 | 送 |

這張矩陣就是 23.11 節實驗三要用程式重現的結果。最後一列是 schemeful same-site 的效果：http 的頁面和 https 的 API 被視為不同 site。表中也看得出 SameSite 防不了什麼：所有同 site 的請求都會帶 cookie，包括來自 `promo.shengsheng.example` 這類較不受控子網域的請求；頂層 `GET` 會帶 `Lax` cookie，所以任何會改變狀態的 `GET` endpoint 都是漏洞。SameSite 是很好的第一層，但不是完整的 CSRF 防禦。

> [!note] 2026 現況：cookie 規格與第三方 cookie（依 2026 年 10 月查證）
> - **規格**：現行標準仍是 RFC 6265，將由 6265bis 取代。截至 2026 年 10 月，`draft-ietf-httpbis-rfc6265bis-22` 已送 IESG、在 RFC Editor queue，尚未取得 RFC 編號；`SameSite`、`__Host-`／`__Secure-` 前綴、「非安全來源不得覆寫 `Secure` cookie」都寫在 6265bis 裡。
> - **Lax-by-default**：Chrome 自 2020 年起把沒寫 `SameSite` 的 cookie 當成 `Lax`（並對剛設定的 cookie 保留短暫的跨站 `POST` 例外）；Firefox 與 Safari 並未完全採用相同預設。不要依賴預設值，每個 cookie 都明確寫出 `SameSite`。
> - **Chrome**：2024 年 7 月放棄直接淘汰第三方 cookie，2025 年 4 月宣布不推出獨立的選擇提示；2025 年 10 月宣布逐步停用 Topics、Protected Audience、Related Website Sets 等多項 Privacy Sandbox 技術，保留 CHIPS、FedCM 與 Private State Tokens。所以 Chrome 一般視窗預設仍允許第三方 cookie，無痕視窗預設封鎖。
> - **Safari 與 Firefox**：Safari 的 ITP 自 2020 年起預設封鎖第三方 cookie；Firefox 的 Total Cookie Protection 自 2022 年起預設依頂層網站分區儲存第三方 cookie。
> - **CHIPS 與 Storage Access API**：`Partitioned` 屬性讓第三方 cookie 依頂層網站分開存放（Chrome／Edge 114 起、Firefox 141 起支援；Safari 18.4 支援、18.5 到 26.1 標示不支援、26.2 起再度支援，中間有空窗）。Flask 3.1 起有 `SESSION_COOKIE_PARTITIONED` 設定。需要在嵌入情境使用未分區 cookie 時，標準做法是 Storage Access API。
> - **對聲聲 Live 的意義**：白板 iframe 不要假設第三方 cookie 一定可用；設計上改用 `Partitioned` cookie，或在 iframe 內以 Storage Access API 取得授權，或改成由父頁面以 `postMessage` 傳遞短效 token。

## 23.6 CSRF：借用使用者身分的請求

**CSRF**（Cross-Site Request Forgery，跨站請求偽造）的成因可以從前兩節直接推導出來：SOP 允許跨站「送出」，瀏覽器會自動附上 cookie，server 只看 cookie 就認定「這是學生本人的操作」。於是外站只要讓學生的瀏覽器送出一個請求，例如一個自動送出的表單，聲聲 Live 就會以學生的身分執行它，即使外站完全讀不到回應。受影響的永遠是**會改變狀態**的操作：取消預約、改 email、把課程點數轉給別人。

```text
 學生的瀏覽器（已登入聲聲 Live）                                     api.shengsheng.example
   │ 1. 學生在另一個分頁打開外站頁面                                        │
   │ 2. 外站頁面讓瀏覽器送出跨站 POST /v1/bookings/42/cancel               │
   │── POST /v1/bookings/42/cancel ───────────────────────────────────────►│
   │   Cookie: session=…（如果 SameSite 允許）                              │
   │   Origin: 外站的 origin        Sec-Fetch-Site: cross-site              │
   │                                                                       │ 防線一：Sec-Fetch-Site／Origin
   │                                                                       │   不在允許清單 → 403
   │                                                                       │ 防線二：沒有有效的 CSRF token
   │                                                                       │   → 403
   │                                                                       │ 防線三：session cookie 是 Lax，
   │                                                                       │   跨站 POST 根本沒帶 cookie → 401
   │◄── 403 Forbidden ─────────────────────────────────────────────────────│
```

這張時序圖畫的是「防禦成功」的樣子，三道防線彼此獨立，任何一道都足以擋下這次請求。攻擊者不需要偷到任何東西，只需要學生在登入狀態下打開一個頁面。第一道看瀏覽器附上、頁面無法偽造的來源資訊；第二道要求外站拿不到的秘密值；第三道讓 cookie 根本不跟著跨站請求出去。設計成多層，是因為每一層都有盲點：舊瀏覽器沒有 Fetch Metadata，同 site 的子網域能繞過 SameSite，token 機制可能因實作錯誤而失效。

**第一種防禦是 synchronizer token**（同步權杖）。server 在 session 裡存一個隨機值，渲染表單時放進隱藏欄位，或由 API 提供給前端放進 `X-CSRF-Token` header；收到變更請求時比對兩者。外站拿不到這個值，因為讀取聲聲 Live 的頁面或 API 回應正是 SOP 擋住的事。token 要用 `secrets` 產生足夠長的隨機值（第 17 章），比對要用 `hmac.compare_digest` 這種固定時間比較，避免透過時間差逐字猜出。

**第二種是 double-submit cookie**（雙重提交 cookie），適合不想在 server 端存狀態的服務：server 把 token 放在一個 JavaScript 讀得到的 cookie 裡，前端讀出後再放進 header，server 只檢查 cookie 與 header 是否相同。外站無法讀取聲聲 Live 的 cookie，所以無法在 header 放入正確的值。但「天真版」有一個成因清楚的弱點：同 site 的子網域可以替整個 site **設定** cookie（稱為 cookie tossing），它不需要讀到原本的值，只要自己設一個已知的 cookie，再在 header 放同一個值就能通過。修正方法是 **signed double-submit**：token 由 server 用 HMAC 綁定 session ID 簽章，被植入的值驗不過簽章；cookie 再加上 `__Host-` 前綴，兄弟子網域就無法覆寫它。

**第三種是檢查請求來源**。現代瀏覽器在請求上附帶 **Fetch Metadata** header：`Sec-Fetch-Site` 說明請求來自 `same-origin`、`same-site`、`cross-site` 還是使用者自己輸入網址的 `none`；`Sec-Fetch-Mode` 說明是 `navigate`、`cors` 還是 `no-cors`；`Sec-Fetch-Dest` 說明結果要用在 `document`、`iframe`、`image` 等哪裡。頁面無法修改這些以 `Sec-` 開頭的 header，server 可以據此實作「資源隔離政策」：變更操作只接受 same-origin 或允許清單內的 same-site 請求。沒有 Fetch Metadata 的舊瀏覽器，退回檢查 `Origin`（大多數瀏覽器在 `POST` 上都會送）或 `Referer`；兩者都缺時，保守的做法是拒絕變更請求。

| 防禦 | 原理 | 擋不住的情況 | 聲聲 Live 的用法 |
|---|---|---|---|
| SameSite=Lax／Strict | 跨站請求不帶 cookie | 同 site 子網域、會改狀態的 `GET`、`SameSite=None` 的 cookie | 所有 session cookie 明寫 `Lax` |
| Synchronizer token | 外站讀不到 session 裡的秘密 | 頁面本身有 XSS（攻擊程式能讀 token） | Flask 表單頁 |
| Signed double-submit | HMAC 綁定 session，植入的值驗不過 | 同上；未簽章的天真版擋不住 cookie tossing | 無狀態的 API |
| Fetch Metadata／Origin | 瀏覽器附上頁面無法偽造的來源 | 不送這些 header 的舊瀏覽器 | API gateway 的統一規則 |
| 自訂 header（需 preflight） | 外站送自訂 header 必須先過 CORS | CORS 設定錯誤（例如反射任意 Origin） | API 要求 `X-CSRF-Token` 或 `Authorization` |
| 重新驗證 | 高風險操作要求密碼、TOTP 或 passkey | 無（成本是使用者體驗） | 改付款方式、改 email |

「自訂 header」一列和故事直接相關：API 只接受 `Authorization: Bearer`、token 放在記憶體時，外站的請求沒有身分，CSRF 的前提就消失了；但 refresh 這種靠 cookie 的 endpoint 仍在 CSRF 的射程內，而反射 Origin 的 CORS 設定又讓「自訂 header 需要 preflight」這道防線一起失效。安全設計上的錯誤經常這樣互相放大。

還有兩種容易被忽略的 CSRF。**Login CSRF** 是讓受害者登入**攻擊者的帳號**，之後受害者輸入的資料（例如付款資訊、學習紀錄）都進了攻擊者的帳號；防法是登入表單也要有 CSRF 保護，登入成功後輪替 session ID（第 26 章）。另一種是**會改變狀態的 `GET`**：例如 `GET /v1/bookings/42/cancel?confirm=1`，它會被 `Lax` cookie 的頂層導覽例外放行，也可能被瀏覽器預先載入或被爬蟲觸發。第 20 章講過 `GET` 是 safe method，這不只是語意上的潔癖，也是安全模型的前提。

## 23.7 XSS：資料被當成程式執行

如果說 CSRF 是「外站借用身分」，**XSS**（Cross-Site Scripting，跨站腳本）就是「攻擊者的程式碼跑進了聲聲 Live 自己的 origin」。一旦發生，SOP 完全幫不上忙，因為對瀏覽器而言那段程式就是聲聲 Live 的程式：它能讀頁面上的私訊、讀 CSRF token、以學生的身分呼叫所有 API。XSS 的成因只有一句話：**不受信任的資料，被瀏覽器當成 HTML、JavaScript 或 URL 解讀了**。例如老師簡介裡的一段文字，被 server 直接拼接進 HTML，瀏覽器就會把其中的標籤當成頁面結構。

| 類型 | 惡意資料從哪裡來 | 在哪裡被當成程式 | 聲聲 Live 的例子 | 主要修法 |
|---|---|---|---|---|
| Reflected（反射型） | 這次請求的參數 | server 產生的 HTML | 搜尋頁把 `q` 參數原樣印在「找不到 … 的結果」 | 模板自動跳脫 |
| Stored（儲存型） | 資料庫裡存過的內容 | 每個看到它的人的頁面 | 老師簡介、課程評論、聊天訊息 | 輸出時依情境編碼；富文字用 sanitizer |
| DOM-based（DOM 型） | URL fragment、`postMessage`、前端狀態 | 前端 JavaScript 寫入 DOM | 前端用 `innerHTML` 顯示從網址取出的老師名稱 | 用 `textContent`、避免危險的 DOM API |

三種類型的差別在於資料的來源與「變成程式」的位置。Reflected 與 Stored 發生在 server 拼接 HTML 時，DOM-based 完全發生在瀏覽器裡，server log 可能看不到任何異常。Stored 的影響最大，一則評論可能被上千名學生看到，聊天訊息還會經 WebSocket 即時推送給每個人。

防禦的第一層是**依輸出情境編碼**（contextual output encoding）：同一段資料，放進 HTML 文字、HTML 屬性、JavaScript 字串、URL 時，需要不同的編碼。Flask 的 Jinja2 模板對 `.html` 檔預設開啟自動跳脫，正確使用模板就涵蓋了最常見的 HTML 文字與加引號屬性情境；危險在於繞過它的地方，例如對使用者內容用 `|safe` 或 `Markup()`，或在 `<script>` 區塊裡直接嵌入資料。下面的小程式示範兩種情境：HTML 文字用 `html.escape`，要給前端 JavaScript 的資料則用 JSON 編碼，並把 `<`、`>`、`&` 轉成 `\u` 形式，讓字串無法提前結束 `<script>` 區塊。

```python
import html
import json

note = '老師備註：<b>重要</b> & "請準時"，</p> 也只是文字'

# 情境一：HTML 文字或加了引號的屬性值 → 跳脫 < > & " '
text_ctx = html.escape(note, quote=True)

# 情境二：嵌入 <script> 給前端用的資料 → JSON 編碼，再把 HTML 有特殊意義的字元轉成 \u 形式
json_ctx = (json.dumps({"note": note}, ensure_ascii=False)
            .replace("<", "\\u003c").replace(">", "\\u003e").replace("&", "\\u0026"))

print("HTML 文字：", text_ctx)
print("script 資料：", json_ctx)
assert "<" not in text_ctx and "<" not in json_ctx
assert json.loads(json_ctx)["note"] == note        # 前端解析回來仍是原本的文字
```

```text
HTML 文字： 老師備註：&lt;b&gt;重要&lt;/b&gt; &amp; &quot;請準時&quot;，&lt;/p&gt; 也只是文字
script 資料： {"note": "老師備註：\u003cb\u003e重要\u003c/b\u003e \u0026 \"請準時\"，\u003c/p\u003e 也只是文字"}
```

兩行輸出都不再含有任何 `<`，所以瀏覽器不會把它們解讀成標籤；最後一個 `assert` 確認 JSON 版本被前端解析後，仍然是一字不差的原始文字，編碼只改變了「表示法」而沒有改變資料。其他情境還有各自的規則：放進 `href` 的 URL 要檢查 scheme 只允許 `https`（`html.escape` 擋不住非 http 的 scheme）；需要保留粗體、連結的富文字評論，要用維護良好的 HTML sanitizer 依允許清單過濾，而不是自己寫正規表示式。前端則用 `textContent` 取代 `innerHTML`，React、Vue 這類框架預設也會跳脫，危險在於 `dangerouslySetInnerHTML`、`v-html` 這些刻意繞過的 API。

第二層是限制 XSS 發生後的傷害。`HttpOnly` 讓攻擊程式讀不到 session cookie，但要清楚它的極限：攻擊程式仍然可以在頁面上直接以學生身分呼叫 API，只是不能把 cookie 帶走離線使用。真正能在瀏覽器層級擋住「注入的程式被執行」的，是下一節的 CSP。

## 23.8 CSP：限制頁面能執行什麼

**CSP**（Content Security Policy，內容安全政策）是 server 用 `Content-Security-Policy` 回應 header 宣告的一份政策，告訴瀏覽器這個頁面可以從哪裡載入腳本、樣式、圖片，可以連線到哪裡，可以被誰嵌入。它是 XSS 的**第二道防線**：即使攻擊者成功把一段 `<script>` 塞進頁面，只要它不符合政策，瀏覽器就拒絕執行，並可以回報違規。政策由分號分隔的 **directive**（指令）組成，每個 directive 後面接 **source list**（來源清單）。

```text
 Content-Security-Policy:
   script-src 'nonce-q8VbW0+1kX4mZr2PqS9yHg==' 'strict-dynamic';
   │          └─ 只有帶這個 nonce 的 script 能執行     └─ 被信任的腳本再載入的腳本也被信任，
   │             （每個回應重新產生）                       host 清單與 'self' 失效
   object-src 'none';                         ← 禁止 <object>、<embed>
   base-uri 'none';                           ← 禁止用 <base> 改寫相對網址的基準
   frame-ancestors 'self' https://partner.example;  ← 只有自己與合作夥伴能用 iframe 嵌入
   report-to csp                              ← 違規報告送到名為 csp 的 Reporting 端點
```

這是聲聲 Live 教室頁的政策，實際上是一行，這裡依 directive 拆開，由上往下讀。`script-src` 是最重要的 directive，這裡用的是 **nonce-based strict CSP**：**nonce**（number used once，只用一次的隨機值）由 server 每次回應重新產生，同時寫在 header 與頁面合法的 `<script nonce="…">` 上；攻擊者注入的腳本不知道這次的 nonce，所以不會被執行。`'strict-dynamic'` 讓被 nonce 信任的腳本所載入的其他腳本也被信任，免去維護一長串 CDN 網域的麻煩，同時讓 host 允許清單與 `'self'` 失效，這是刻意的：Google 在 2016 年對大量真實政策的研究發現，以網域允許清單撰寫的政策絕大多數都能被繞過，因為清單裡的網域常常託管了可被利用的腳本。`object-src 'none'` 與 `base-uri 'none'` 關掉兩個古老的繞過管道，`frame-ancestors` 留給 23.9 節，`report-to` 讓違規被送到回報端點。

| directive | 控制什麼 | 沒寫時 | 聲聲 Live 的設定 |
|---|---|---|---|
| `default-src` | 其他 `*-src` 沒寫時的預設值 | 不限制 | `'self'`（較寬鬆的頁面） |
| `script-src` | JavaScript 的來源與 inline script | 退回 `default-src` | `'nonce-…' 'strict-dynamic'` |
| `style-src` | CSS 的來源與 inline style | 退回 `default-src` | `'self' 'nonce-…'` |
| `connect-src` | `fetch()`、WebSocket、EventSource 能連到哪 | 退回 `default-src` | api、rt 的 origin |
| `img-src`／`media-src` | 圖片與影音 | 退回 `default-src` | `'self'`、CDN、`blob:` |
| `object-src` | 外掛內容 | 退回 `default-src` | `'none'` |
| `base-uri` | `<base>` 能把相對網址改指向哪 | **不退回**，不限制 | `'none'` |
| `form-action` | 表單能送到哪 | **不退回**，不限制 | `'self'` |
| `frame-ancestors` | 誰能用 iframe 嵌入本頁 | **不退回**，不限制 | `'self'` 加合作夥伴 |
| `report-to`／`report-uri` | 違規回報送到哪 | 不回報 | 指向內部收集服務 |

這張表的「沒寫時」一欄是最常見的陷阱：`base-uri`、`form-action`、`frame-ancestors` 不會退回 `default-src`，以為寫了 `default-src 'self'` 就全部封鎖，其實這三項仍然完全開放。同一個 directive 重複出現時只有第一個有效；送出多個 `Content-Security-Policy` header 時，瀏覽器會**同時**執行每一份政策，只會越來越嚴，不會互相放寬。

舊式 CSP 常寫成 `script-src 'self' 'unsafe-inline'`，對 XSS 幾乎沒有防護，因為注入的正是 inline script。現行規則有一個相容設計：source list 只要出現 nonce 或 hash，`'unsafe-inline'` 就被忽略，所以業界會在 strict 政策後附上 `'unsafe-inline' https:` 給只懂舊規格的瀏覽器。不會變動的靜態頁面可以改用 **hash**（`'sha256-…'`，列出允許的 inline script 內容雜湊），不需要每次產生新值。

```text
 每個 HTML 回應：
   Flask view ──► nonce = base64(secrets.token_bytes(16))   ← 128 bit，每次不同
        │
        ├──► 回應 header：Content-Security-Policy: script-src 'nonce-<nonce>' 'strict-dynamic'; …
        └──► 模板：<script nonce="<nonce>" src="/static/classroom.js">
                         │
 瀏覽器：                ▼
   解析 header → 遇到 <script>：nonce 相符？ ──是──► 執行（它再載入的腳本也被信任）
                                       └──否──► 封鎖，送出違規報告（不執行）

 ✗ 錯誤做法：nonce 寫死在設定檔、或整頁 HTML 被 CDN 快取 → 每個人看到同一個 nonce，形同沒有
```

這張流程圖強調 nonce 的兩個要求。第一，它必須**不可預測**，用 `secrets` 產生至少 128 bit；第二，它必須**每個回應不同**，而且 header 與 HTML 用同一個值。聲聲 Live 的教室頁是 `Cache-Control: private` 的個人化頁面（第 21 章的快取策略），本來就不會被 CDN 共用快取；但如果把帶 nonce 的公開頁面交給 CDN 快取，所有人都會拿到同一份 nonce，攻擊者讀一次頁面就知道它，這時要改用 hash 或讓 HTML 不被共用快取。

導入 CSP 最穩的路徑是先送 `Content-Security-Policy-Report-Only`：瀏覽器照政策檢查，但只回報、不封鎖。收集一兩週的報告，修掉合法但違規的程式（例如寫在 HTML 屬性裡的 `onclick` 事件處理器，它們不能帶 nonce，必須改成 `addEventListener`），再切換成正式的 header。違規報告裡常混有瀏覽器擴充功能造成的雜訊，判讀時要依來源分組。

> [!note] 2026 現況：CSP 規格與 Trusted Types
> 截至 2026 年 10 月，CSP Level 3 仍是 W3C 的工作草案，但 nonce、hash、`'strict-dynamic'` 與 `frame-ancestors` 已被主要瀏覽器廣泛支援。`report-uri` 已被標為 deprecated，新的寫法是 `report-to` 搭配 `Reporting-Endpoints` header，實務上常兩者並列以相容舊瀏覽器。針對 DOM 型 XSS 的 **Trusted Types**（`require-trusted-types-for 'script'`，強制危險的 DOM API 只能接收經過審核的值）在 Chromium 系瀏覽器已支援多年，其他瀏覽器的支援在 2025–2026 年陸續推進；導入前請查最新的相容性資料。

## 23.9 Clickjacking 與 frame-ancestors

**Clickjacking**（點擊劫持）的成因是 SOP 允許「嵌入」：外站可以用 iframe 載入聲聲 Live 的頁面，把它設成透明，疊在一個誘導點擊的按鈕上方。學生以為自己在點外站的「領取優惠」，實際點到的是 iframe 裡聲聲 Live 的「確認付款」。iframe 裡的頁面若能帶上學生的 cookie（同 site 的嵌入，或 `SameSite=None` 的 cookie），點擊就會以學生身分生效。

```text
    學生眼中看到的                          實際的圖層（由下往上）
 ┌──────────────────────────┐          ┌──────────────────────────────────┐
 │  外站頁面                  │          │ 第 1 層：外站頁面與誘導按鈕         │
 │                          │          │ 第 2 層：iframe 載入聲聲 Live 頁面  │
 │     [ 領取免費課程 ]       │   ═══►   │          透明度 0，對齊「確認付款」 │
 │                          │          │          點擊落在這一層             │
 └──────────────────────────┘          └──────────────────────────────────┘
 防禦：聲聲 Live 回應 frame-ancestors 'self' → 瀏覽器拒絕在外站的 iframe 裡顯示這個頁面
```

這張圖左邊是使用者的視角，右邊是圖層的真相。關鍵在於「點擊落在哪一層」由透明的 iframe 決定，而 SOP 不阻止嵌入，所以防禦必須由**被嵌入的頁面**自己宣告。CSP 的 `frame-ancestors` 列出允許嵌入本頁的祖先 origin：`'none'` 完全禁止，`'self'` 只允許自己，也可以列出合作夥伴的 origin。舊的 `X-Frame-Options` header（`DENY` 或 `SAMEORIGIN`）功能較少，不能列出多個 origin；兩者同時存在時，支援 `frame-ancestors` 的瀏覽器以它為準。實務上兩個都送，相容最舊的瀏覽器。

聲聲 Live 的登入、付款、帳號設定一律 `frame-ancestors 'none'`；白板頁列出合作夥伴的 origin，高風險操作（例如刪除整份白板）另外要求在新視窗中確認。`frame-ancestors` 不能寫在 `<meta http-equiv>` 裡，因為瀏覽器讀到 meta 時頁面早已被嵌入，只能用 HTTP header 送出。

## 23.10 其他安全 header：把隔離補齊

除了 CORS 與 CSP，還有一組 header 各自補上瀏覽器隔離模型的一塊。它們大多是一行設定，但每一個背後都有一個具體的攻擊成因。

| header | 典型值 | 防的是什麼 |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | 瀏覽器猜測內容類型，把使用者上傳的「圖片」當成腳本或 HTML 執行 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 完整網址（含 query 裡的 token、搜尋字詞）透過 `Referer` 洩漏給第三方 |
| `Cross-Origin-Resource-Policy`（CORP） | `same-site` | 外站以 `<img>`、`<script>` 嵌入你的私有資源，搭配旁路攻擊推測內容 |
| `Cross-Origin-Opener-Policy`（COOP） | `same-origin` | 你開啟的跨源視窗（或開啟你的視窗）透過 `window.opener` 互相操作 |
| `Cross-Origin-Embedder-Policy`（COEP） | `require-corp` | 與 COOP 一起啟用 cross-origin isolation，才能使用 `SharedArrayBuffer` 等高精度功能 |
| `Strict-Transport-Security` | `max-age=…; includeSubDomains` | 第一次連線被降級成 http（第 19 章） |
| `Permissions-Policy` | `camera=(self)` | 嵌入的第三方 iframe 擅自使用相機、麥克風 |

COOP 與 COEP 一起設定後，頁面進入 **cross-origin isolation**（跨源隔離）：瀏覽器保證頁面所在的 process 裡沒有未經同意的跨源資料，才敢開放 `SharedArrayBuffer` 與高精度計時器，這是 Spectre 類旁路攻擊之後的設計；Joe 若要在瀏覽器裡做多執行緒的影音處理就會碰到它。`Permissions-Policy` 則讓教室頁控制哪些 frame 能要求相機與麥克風，避免嵌入的第三方 iframe 取得 WebRTC 權限。

## 23.11 動手做：在 127.0.0.1 上實作瀏覽器的安全規則

這一節用五個實驗把本章的規則寫成能執行的 Python：瀏覽器端的 CORS 演算法、CORS 正確的 API server 與 preflight 快取、SameSite 送出規則、CSRF token 驗證，以及 CSP 解析與 nonce。每段程式都能單獨執行，不連外網。

### 實驗一：瀏覽器的 CORS 演算法

這段程式把 23.4 節的規則逐條翻成函式：`needs_preflight` 判斷是否為 simple request，`cors_check` 是流程圖裡的 CORS check，`preflight_check` 再加上 method 與 header 的判斷。九個案例涵蓋故事裡的每一種錯誤；為了聚焦，程式省略了 `Range` header 的特例與 redirect。

```python
from dataclasses import dataclass, field
from urllib.parse import urlsplit

DEFAULT_PORT = {"http": 80, "https": 443}
SAFE_METHODS = {"GET", "HEAD", "POST"}                      # CORS-safelisted methods
SAFE_HEADERS = {"accept", "accept-language", "content-language", "content-type"}
SAFE_CONTENT_TYPES = {"application/x-www-form-urlencoded", "multipart/form-data", "text/plain"}


def origin_of(url: str) -> str:
    """origin = scheme + host + port；預設 port 省略，host 一律小寫。"""
    u = urlsplit(url)
    port = u.port or DEFAULT_PORT[u.scheme]
    suffix = "" if port == DEFAULT_PORT[u.scheme] else f":{port}"
    return f"{u.scheme}://{u.hostname}{suffix}"


@dataclass
class Req:
    page: str                      # 發出請求的頁面 URL
    method: str
    url: str
    headers: dict = field(default_factory=dict)
    credentials: str = "same-origin"   # fetch 的 omit / same-origin / include

    @property
    def origin(self):
        return origin_of(self.page)

    @property
    def credentialed(self):
        # 跨 origin 時只有 include 會帶 cookie；same-origin 模式對跨 origin 等於 omit
        return self.credentials == "include"


def unsafe_headers(req: Req) -> list[str]:
    """回傳不在 safelist 內的 header 名稱（小寫、排序），也就是 preflight 要問的那些。"""
    bad = []
    for name, value in req.headers.items():
        n = name.lower()
        if n not in SAFE_HEADERS or len(value) > 128:
            bad.append(n)
        elif n == "content-type" and value.split(";")[0].strip().lower() not in SAFE_CONTENT_TYPES:
            bad.append(n)
    return sorted(bad)


def needs_preflight(req: Req) -> bool:
    return req.method not in SAFE_METHODS or bool(unsafe_headers(req))


def cors_check(req: Req, resp: dict) -> str | None:
    """回應能不能交給 JavaScript 讀？None 代表通過，否則回傳原因。"""
    acao = resp.get("access-control-allow-origin")
    if acao is None:
        return "沒有 Access-Control-Allow-Origin"
    if acao == "*" and not req.credentialed:
        return None
    if acao == "*":
        return "帶 credentials 時 ACAO 不能是 *"
    if "," in acao:
        return "ACAO 只能放一個 origin，收到清單"
    if acao != req.origin:                       # 逐字比對：大小寫、port、結尾斜線都算
        return f"ACAO={acao} 不等於 {req.origin}"
    if req.credentialed and resp.get("access-control-allow-credentials") != "true":
        return "帶 credentials 時需要 Access-Control-Allow-Credentials: true"
    return None


def split_list(value: str | None) -> set[str]:
    return {v.strip().lower() for v in (value or "").split(",") if v.strip()}


def preflight_check(req: Req, status: int, resp: dict) -> str | None:
    if not 200 <= status <= 299:
        return f"preflight 狀態碼 {status} 不是 2xx"
    if (why := cors_check(req, resp)):
        return why
    methods = split_list(resp.get("access-control-allow-methods"))
    wildcard_m = "*" in methods and not req.credentialed
    if req.method not in SAFE_METHODS and req.method.lower() not in methods and not wildcard_m:
        return f"方法 {req.method} 不在 Allow-Methods"
    allowed = split_list(resp.get("access-control-allow-headers"))
    wildcard_h = "*" in allowed and not req.credentialed
    for h in unsafe_headers(req):
        # 規格特例：* 永遠不涵蓋 authorization，必須明列
        if h not in allowed and not (wildcard_h and h != "authorization"):
            return f"header {h} 不在 Allow-Headers"
    return None


WWW = "https://www.shengsheng.example/booking"
API = "https://api.shengsheng.example/v1"
JSON = {"Content-Type": "application/json"}
CASES = [
    ("1 GET 公開課表", Req(WWW, "GET", f"{API}/courses"), 200, {"access-control-allow-origin": "*"}),
    ("2 POST text/plain", Req(WWW, "POST", f"{API}/feedback", {"Content-Type": "text/plain"}), 200,
     {"access-control-allow-origin": "*"}),
    ("3 POST JSON", Req(WWW, "POST", f"{API}/bookings", JSON), 204,
     {"access-control-allow-origin": "https://www.shengsheng.example",
      "access-control-allow-methods": "POST", "access-control-allow-headers": "content-type"}),
    ("4 Bearer + Allow-Headers:*", Req(WWW, "GET", f"{API}/me", {"Authorization": "Bearer x"}), 204,
     {"access-control-allow-origin": "*", "access-control-allow-headers": "*"}),
    ("5 include + ACAO:*", Req(WWW, "POST", f"{API}/session/refresh", credentials="include"), 200,
     {"access-control-allow-origin": "*", "access-control-allow-credentials": "true"}),
    ("6 include + 正確回應", Req(WWW, "POST", f"{API}/session/refresh", credentials="include"), 200,
     {"access-control-allow-origin": "https://www.shengsheng.example",
      "access-control-allow-credentials": "true"}),
    ("7 PUT 沒被允許", Req(WWW, "PUT", f"{API}/bookings/42", JSON), 204,
     {"access-control-allow-origin": "https://www.shengsheng.example",
      "access-control-allow-methods": "GET, POST", "access-control-allow-headers": "content-type"}),
    ("8 OPTIONS 被要求登入", Req(WWW, "DELETE", f"{API}/bookings/42"), 401, {}),
    ("9 ACAO 放兩個值", Req(WWW, "GET", f"{API}/courses"), 200,
     {"access-control-allow-origin": "https://www.shengsheng.example, https://teach.shengsheng.example"}),
]

print("案例 | 類型 | preflight 問什麼 | 結果")
results = {}
for name, req, status, resp in CASES:
    kind = "preflight" if needs_preflight(req) else "simple"
    why = preflight_check(req, status, resp) if kind == "preflight" else cors_check(req, resp)
    results[name[0]] = why is None
    asked = " + ".join([req.method] + unsafe_headers(req)) if kind == "preflight" else "-"
    print(f"{name} | {kind} | {asked} | {'可讀取' if why is None else '擋下：' + why}")

print("origin_of:", origin_of("HTTPS://API.shengsheng.example:443/v1?x=1"), "|",
      origin_of("http://127.0.0.1:5173/"))
assert results == {"1": True, "2": True, "3": True, "4": False, "5": False,
                   "6": True, "7": False, "8": False, "9": False}
```

案例 1 與 2 是 simple request，回應的 `*` 在沒有 credentials 時有效。案例 2 說明 `POST` 本身不會觸發 preflight，觸發的是 `Content-Type` 與自訂 header；案例 3 只因為 `application/json` 就要 preflight，而且瀏覽器只問了 `content-type`。

案例 4 重現故事裡第一次修法失敗的原因：`Allow-Headers: *` 不涵蓋 `authorization`。案例 5 與 6 是 refresh 的兩個版本，帶 credentials 時必須回寫明確的 origin 並加上 `Allow-Credentials: true`。案例 7 的 `PUT` 不在允許的 method 裡；案例 8 是 `OPTIONS` 被要求登入而回 401；案例 9 把多個 origin 寫在同一個 header 裡。最後一行驗證 origin 的正規化：scheme 與 host 轉小寫、預設 port 省略、路徑與 query 丟棄，非預設的 5173 則保留。

### 實驗二：CORS 正確的 API server 與 preflight 快取

這是 Rita 審查後的版本：允許清單逐字比對，不反射任意 `Origin`；preflight 不檢查登入、回 204 並帶 `Max-Age: 600`；所有回應都加 `Vary`，包括被拒絕的。client 端是一個精簡的「迷你瀏覽器」，用模擬時鐘管理 preflight 快取，並在每次實際請求後做 CORS 檢查；server 用 `hits` 計數，讓我們看到「瀏覽器擋下」與「server 有沒有收到」是兩回事。

```python
import http.client
import json
import threading
from collections import Counter
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

ALLOWED_ORIGINS = {"https://www.shengsheng.example", "https://teach.shengsheng.example"}
ALLOWED_METHODS = {"GET", "POST", "DELETE"}
ALLOWED_HEADERS = {"authorization", "content-type", "x-csrf-token"}
MAX_AGE = 600
hits = Counter()


class Api(BaseHTTPRequestHandler):
    def log_message(self, *args):          # 安靜一點，改用 hits 計數
        pass

    def cors_headers(self, preflight=False):
        origin = self.headers.get("Origin")
        # Vary 一定要加，連「不允許」的回應也要，否則快取會把 A 的版本交給 B
        vary = "Origin, Access-Control-Request-Method, Access-Control-Request-Headers" if preflight else "Origin"
        out = {"Vary": vary}
        if origin in ALLOWED_ORIGINS:      # 允許清單逐字比對，絕不反射任意 Origin
            out["Access-Control-Allow-Origin"] = origin
            out["Access-Control-Allow-Credentials"] = "true"
        return out

    def send(self, status, extra, body=b""):
        self.send_response(status)
        for k, v in extra.items():
            self.send_header(k, v)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_OPTIONS(self):                  # preflight：不需要也不檢查登入
        hits["OPTIONS"] += 1
        h = self.cors_headers(preflight=True)
        method = self.headers.get("Access-Control-Request-Method", "")
        asked = {x.strip().lower() for x in self.headers.get("Access-Control-Request-Headers", "").split(",") if x.strip()}
        if "Access-Control-Allow-Origin" in h and method in ALLOWED_METHODS and asked <= ALLOWED_HEADERS:
            h["Access-Control-Allow-Methods"] = ", ".join(sorted(ALLOWED_METHODS))
            h["Access-Control-Allow-Headers"] = ", ".join(sorted(ALLOWED_HEADERS))
            h["Access-Control-Max-Age"] = str(MAX_AGE)
            return self.send(204, h)
        self.send(403, {"Vary": h["Vary"]})   # 不給任何 Allow-*，瀏覽器就會擋

    def do_GET(self):
        hits["GET"] += 1                    # 注意：不允許的 origin 也會走到這裡
        body = json.dumps({"student": "stu_1024", "credits": 3}).encode()
        h = self.cors_headers() | {"Content-Type": "application/json", "x-request-id": "r-77",
                                   "Access-Control-Expose-Headers": "x-request-id"}
        self.send(200, h, body)

    def do_POST(self):
        hits["POST"] += 1
        self.rfile.read(int(self.headers.get("Content-Length", 0)))
        self.send(201, self.cors_headers() | {"Content-Type": "application/json"}, b'{"booking":42}')


class MiniBrowser:
    """只模擬本實驗需要的部分：preflight、preflight 快取（模擬時鐘）、CORS 檢查。"""

    def __init__(self, port):
        self.port, self.now, self.cache = port, 0, {}

    def request(self, method, path, headers):
        conn = http.client.HTTPConnection("127.0.0.1", self.port, timeout=3)
        conn.request(method, path, body=b"{}" if method == "POST" else None, headers=headers)
        r = conn.getresponse()
        r.read()
        conn.close()
        return r.status, {k.lower(): v for k, v in r.getheaders()}

    def fetch(self, origin, method, path, headers):
        names = ",".join(sorted(k.lower() for k in headers if k.lower() != "cookie"))
        note = "simple"
        if method != "GET" or names:
            key = (origin, path, method, names, "include")
            if self.cache.get(key, -1) > self.now:
                note = "preflight 快取命中"
            else:
                st, h = self.request("OPTIONS", path, {"Origin": origin, "Access-Control-Request-Method": method,
                                                       "Access-Control-Request-Headers": names})
                if st != 204 or h.get("access-control-allow-origin") != origin:
                    return f"preflight {st}，實際請求沒送出"
                self.cache[key] = self.now + min(int(h["access-control-max-age"]), 7200)
                note = "送 preflight"
        st, h = self.request(method, path, {"Origin": origin, "Cookie": "__Host-sid=abc"} | headers)
        readable = h.get("access-control-allow-origin") == origin and h.get("access-control-allow-credentials") == "true"
        return f"{note} → {st}，JS {'可讀，Vary=' + h['vary'] if readable else '讀不到（CORS 擋下）'}"


srv = ThreadingHTTPServer(("127.0.0.1", 0), Api)
threading.Thread(target=srv.serve_forever, daemon=True).start()
b = MiniBrowser(srv.server_address[1])
WWW, BAD = "https://www.shengsheng.example", "https://phish.example"
book = {"Content-Type": "application/json", "Authorization": "Bearer t"}
steps = [  # (模擬時間秒, 頁面 origin, method, path, headers)
    (0, WWW, "GET", "/v1/me", {}),
    (0, WWW, "POST", "/v1/bookings", book),
    (30, WWW, "POST", "/v1/bookings", book),
    (601, WWW, "POST", "/v1/bookings", book),     # 超過 Max-Age 600 秒
    (601, BAD, "GET", "/v1/me", {}),
    (601, BAD, "POST", "/v1/bookings", book),
]
out = []
for t, origin, method, path, headers in steps:
    b.now = t
    out.append(b.fetch(origin, method, path, headers))
    who = "www" if origin == WWW else "phish"
    print(f"t={t:<4} {who:<5} {method:<4} {path:<13} {out[-1]}")
print("server 收到：", dict(hits))
srv.shutdown()
srv.server_close()
assert out[2].startswith("preflight 快取命中") and out[3].startswith("送 preflight")
assert "讀不到" in out[4] and out[5].startswith("preflight 403")
assert hits == {"GET": 2, "OPTIONS": 3, "POST": 3}
```

前四列是合法的 `www` 頁面。`GET /v1/me` 是 simple request，直接成功；預約請求先送 preflight，30 秒後重送命中快取、省掉一個 RTT，601 秒時超過 `Max-Age` 而再送一次。這就是 production 上「每隔一段時間某個請求會多一個 OPTIONS」的由來。

後兩列是 `phish.example`。第 5 列最值得注意：server **照常回了 200**，只是回應沒有 `Access-Control-Allow-Origin`，瀏覽器不讓腳本讀；`hits` 裡 `GET` 的 2 次就包含這一次。如果這是會改變狀態的 simple request，副作用早已發生，所以變更操作要靠 CSRF 防禦而不是 CORS。第 6 列需要 preflight，server 回 403 而且不給 `Allow-*`，瀏覽器就不送實際請求，`POST` 的 3 次全部來自 `www`。

### 實驗三：SameSite 的送出規則

這段程式實作 23.5 節的決策圖：用迷你 Public Suffix List 計算 site，判斷六種情境下 `Strict`、`Lax`、`None` 與「沒寫」四種 cookie 會不會送出。`pages.example` 模擬託管平台的公共後綴；`legacy` 沒寫 `SameSite`，依 Chromium 的 Lax-by-default 處理（省略剛設定的 cookie 可短暫跨站 `POST` 的例外）。

```python
from dataclasses import dataclass
from urllib.parse import urlsplit

# 迷你 Public Suffix List：真實清單有上萬筆，pages.example 模擬「每個使用者一個子網域」的託管平台
PUBLIC_SUFFIXES = {"example", "test", "pages.example"}


def registrable_domain(host: str) -> str:
    """eTLD+1：最長的公共後綴再往左多一段。"""
    labels = host.lower().split(".")
    for i in range(len(labels)):
        if ".".join(labels[i:]) in PUBLIC_SUFFIXES:
            return ".".join(labels[max(i - 1, 0):])
    return host


def site(url: str) -> tuple[str, str]:
    u = urlsplit(url)
    return (u.scheme, registrable_domain(u.hostname))   # schemeful：http 與 https 是不同 site


@dataclass
class Cookie:
    name: str
    samesite: str | None      # "Strict" / "Lax" / "None" / None（沒寫）
    secure: bool = True
    host: str = "api.shengsheng.example"   # host-only cookie


def accept_cookie(c: Cookie) -> bool:
    # SameSite=None 必須搭配 Secure；__Host- 必須 Secure、Path=/、不可有 Domain
    if c.samesite == "None" and not c.secure:
        return False
    if c.name.startswith("__Host-") and not c.secure:
        return False
    return True


def should_send(c: Cookie, target: str, top_level: str, method: str, navigation: bool,
                block_third_party: bool = False) -> bool:
    u = urlsplit(target)
    if u.hostname != c.host or (c.secure and u.scheme != "https"):
        return False
    same_site = site(target) == site(top_level)
    mode = c.samesite or "Lax"                 # Lax-by-default（Chromium 行為）
    if same_site:
        return True
    if mode == "Strict":
        return False
    if mode == "Lax":
        # 跨 site 只放行「頂層導覽 + 安全方法」，例如點信裡的連結
        return navigation and method in ("GET", "HEAD")
    return not block_third_party               # None：是否送出取決於第三方 cookie 政策


JAR = [Cookie("__Host-sid", "Lax"), Cookie("prefs", "Strict"),
       Cookie("embed", "None"), Cookie("legacy", None)]
assert not accept_cookie(Cookie("bad", "None", secure=False))
API = "https://api.shengsheng.example/v1/me"

    # (說明, 目標 URL, 頂層頁面, method, 是否為頂層導覽, 是否封鎖第三方 cookie)

    ("D 外站頁面 fetch api", API, "https://phish.example/", "GET", False, False),
    ("E 同 D，瀏覽器擋第三方", API, "https://phish.example/", "GET", False, True),

]
grid = {}

    row = [should_send(c, target, top, method, nav, block) for c in JAR]
    grid[label[0]] = row
    print(label + " | " + " | ".join("送" if x else "-" for x in row))

print("site:", site("https://www.shengsheng.example/"), site("https://api.shengsheng.example/"))

E 同 D，瀏覽器擋第三方 | - | - | - | -
F http 版 www fetch api | - | - | 送 | -
site: ('https', 'shengsheng.example') ('https', 'shengsheng.example')
site: ('https', 'alice.pages.example') ('https', 'bob.pages.example')
```

情境 A 雖然跨 origin 卻是 same-site，連 `Strict` 的 `prefs` 都送出，證實 SameSite 管不到同 site 的子網域。情境 B 是從信箱點連結的頂層 `GET`，`Lax` 與沒寫屬性的 cookie 會送、`Strict` 不送，學生不必重新登入。情境 C 的跨站表單 `POST` 只剩 `None` 的 `embed` 會送，所以 `None` cookie 必須自帶 CSRF 防禦。

情境 D 與 E 只差在瀏覽器是否封鎖第三方 cookie，對應 2026 現況裡 Chrome 與 Safari 的預設差異。情境 F 是 http 版的 `www`，schemeful same-site 把它當成跨站，結果和外站一樣。最後兩行顯示 `www` 與 `api` 同 site，而 `pages.example` 底下的兩個使用者各自是獨立的 site。

### 實驗四：CSRF token 與 signed double-submit

這段程式實作 23.6 節的三種防禦，組成一個 `verify` 函式：先做來源檢查（Fetch Metadata 優先、沒有時退回 `Origin`），再驗證 synchronizer token 或 double-submit token。為了比較天真版與 signed 版 double-submit，兩個「植入 cookie」的案例刻意關掉來源檢查，單獨測試 token 層。

```python
import hashlib
import hmac
import secrets

SERVER_KEY = secrets.token_bytes(32)      # 只存在 server；輪替時要支援舊 key 一段時間
TRUSTED_ORIGINS = {"https://www.shengsheng.example", "https://teach.shengsheng.example"}
UNSAFE = {"POST", "PUT", "PATCH", "DELETE"}


# ① Synchronizer token：token 存在 server 端 session，表單或 header 帶回來比對
def new_session():
    return {"id": secrets.token_urlsafe(16), "csrf": secrets.token_urlsafe(32)}


def check_synchronizer(session, submitted):
    return submitted is not None and hmac.compare_digest(session["csrf"], submitted)


# ② Signed double-submit：server 不必存 token，但 token 必須用 HMAC 綁定 session
def issue_double_submit(session_id):
    nonce = secrets.token_urlsafe(16)
    mac = hmac.new(SERVER_KEY, f"{session_id}!{nonce}".encode(), hashlib.sha256).hexdigest()
    return f"{nonce}.{mac}"                # 放進 __Host-csrf cookie，JS 讀出後放進 header


def check_double_submit(session_id, cookie_value, header_value, signed=True):
    if not cookie_value or not header_value or not hmac.compare_digest(cookie_value, header_value):
        return False
    if not signed:
        return True                        # 天真版：只比「兩者相同」
    nonce, _, mac = cookie_value.partition(".")
    expect = hmac.new(SERVER_KEY, f"{session_id}!{nonce}".encode(), hashlib.sha256).hexdigest()
    return hmac.compare_digest(mac, expect)


# ③ 來源檢查：Fetch Metadata 優先，沒有時退回 Origin
def origin_ok(method, headers):
    if method not in UNSAFE:
        return True
    sfs = headers.get("Sec-Fetch-Site")
    if sfs is not None:
        return sfs in ("same-origin", "same-site") and headers.get("Origin") in TRUSTED_ORIGINS
    origin = headers.get("Origin")
    return origin in TRUSTED_ORIGINS       # 缺 Origin 的變更請求一律拒絕（保守策略）


def verify(method, headers, session, cookies, mode, origin_layer=True):
    if origin_layer and not origin_ok(method, headers):
        return "拒絕：來源不可信"
    if method in UNSAFE:
        token = headers.get("X-CSRF-Token")
        ok = (check_synchronizer(session, token) if mode == "sync"
              else check_double_submit(session["id"], cookies.get("__Host-csrf"), token, mode == "signed"))
        if not ok:
            return "拒絕：CSRF token 無效"
    return "通過"


sess = new_session()
good_cookie = issue_double_submit(sess["id"])
site_hdr = {"Origin": "https://www.shengsheng.example", "Sec-Fetch-Site": "same-site"}
# 被植入的 cookie：同 site 底下某個被接管的子網域，可以替整個 site 設 cookie（cookie tossing）。
# 下面兩個案例關掉來源檢查（origin_layer=False），單獨比較 token 層本身擋不擋得住
planted = "AAAA.forged"
promo = {"Origin": "https://promo.shengsheng.example", "Sec-Fetch-Site": "same-site"}
cases = [
    ("正常：sync token", "POST", site_hdr | {"X-CSRF-Token": sess["csrf"]}, {}, "sync"),
    ("正常：signed double-submit", "POST", site_hdr | {"X-CSRF-Token": good_cookie},
     {"__Host-csrf": good_cookie}, "signed"),
    ("外站表單（cross-site）", "POST", {"Origin": "https://phish.example", "Sec-Fetch-Site": "cross-site"},
     {}, "sync"),
    ("同 site 但沒帶 token", "POST", site_hdr, {}, "sync"),
    ("植入 cookie＋天真 double-submit", "POST", promo | {"X-CSRF-Token": planted},
     {"__Host-csrf": planted}, "naive", False),
    ("植入 cookie＋signed double-submit", "POST", promo | {"X-CSRF-Token": planted},
     {"__Host-csrf": planted}, "signed", False),
    ("同上，打開來源檢查", "POST", promo | {"X-CSRF-Token": planted},
     {"__Host-csrf": planted}, "naive", True),
    ("舊瀏覽器、沒有 Origin", "POST", {"X-CSRF-Token": sess["csrf"]}, {}, "sync"),
    ("GET 讀取（安全方法）", "GET", {"Sec-Fetch-Site": "cross-site"}, {}, "sync"),
]
results = []
for label, method, headers, cookies, mode, *layer in cases:
    results.append(verify(method, headers, sess, cookies, mode, *layer))
    print(f"{label}：{results[-1]}")
assert results == ["通過", "通過", "拒絕：來源不可信", "拒絕：CSRF token 無效", "通過",
                   "拒絕：CSRF token 無效", "拒絕：來源不可信", "拒絕：來源不可信", "通過"]
n, _, m = good_cookie.partition(".")
print(f"sync token {len(sess['csrf'])} 字元；double-submit = nonce {len(n)} 字元 + '.' + HMAC {len(m)} 字元")
```

```text
正常：sync token：通過
正常：signed double-submit：通過
外站表單（cross-site）：拒絕：來源不可信
同 site 但沒帶 token：拒絕：CSRF token 無效
植入 cookie＋天真 double-submit：通過
植入 cookie＋signed double-submit：拒絕：CSRF token 無效
同上，打開來源檢查：拒絕：來源不可信
舊瀏覽器、沒有 Origin：拒絕：來源不可信
GET 讀取（安全方法）：通過
sync token 43 字元；double-submit = nonce 22 字元 + '.' + HMAC 64 字元
```

前兩列是正常請求。第 3 列的跨站表單在第一道防線就被 `Sec-Fetch-Site: cross-site` 擋下；第 4 列來源可信但沒有 token，被 token 層擋下，說明來源檢查不能取代 token。

第 5 到 7 列是重點。被接管的 `promo` 子網域與 api 同 site，可以用 `Domain=shengsheng.example` 替整個 site 設一個值由它決定的 CSRF cookie。真實的 cookie 名稱若帶 `__Host-` 前綴，兄弟子網域根本設不了它；但許多天真的實作沒有用前綴，所以程式沿用同一個名稱、直接假設植入已經成功，只測 token 層。天真版只比較 cookie 與 header 是否相同而通過；signed 版重算 HMAC，被植入的值驗不過；打開來源檢查後，`promo` 不在允許清單，同樣被擋。三層各自擋下不同的失誤。

第 8 列是不送 `Origin` 與 Fetch Metadata 的舊瀏覽器，保守策略直接拒絕；若還要支援這類瀏覽器，可以退回檢查 `Referer`，但部分使用者會因隱私設定而不送它。第 9 列的 `GET` 不需要 token，前提是所有 `GET` 都不改變狀態。最後一行是 token 的格式：32 bytes 隨機值的 base64url 是 43 字元；double-submit 是 nonce 加上 64 個十六進位字元的 HMAC-SHA256。

### 實驗五：CSP 解析、nonce 產生與執行判斷

最後一個實驗在 127.0.0.1 上跑一個教室頁 server，每次回應產生新的 nonce，同時寫進 `Content-Security-Policy` 與 `<script>` 標籤。client 請求兩次確認 nonce 不同且 header 與 HTML 一致，再用 `parse_csp` 與 `script_allowed` 模擬瀏覽器的判斷。

```python
import base64
import http.client
import re
import secrets
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


def make_nonce() -> str:
    return base64.b64encode(secrets.token_bytes(16)).decode()   # 128 bit，每個回應重新產生


def parse_csp(header: str) -> dict[str, list[str]]:
    policy = {}
    for part in header.split(";"):
        tokens = part.split()
        if not tokens:
            continue
        name = tokens[0].lower()
        policy.setdefault(name, tokens[1:])      # 重複的 directive：只有第一個有效
    return policy


def sources_for(policy, directive):
    # script-src-elem → script-src → default-src 的退回順序
    for d in (f"{directive}-elem", directive, "default-src"):
        if d in policy:
            return policy[d]
    return None                                  # 完全沒限制


def script_allowed(policy, page_origin, *, src=None, nonce=None) -> bool:
    srcs = sources_for(policy, "script-src")
    if srcs is None:
        return True
    if nonce and f"'nonce-{nonce}'" in srcs:
        return True
    has_nonce_or_hash = any(s.startswith(("'nonce-", "'sha256-", "'sha384-", "'sha512-")) for s in srcs)
    if src is None:                              # inline script
        return "'unsafe-inline'" in srcs and not has_nonce_or_hash   # 有 nonce 時 unsafe-inline 被忽略
    if "'strict-dynamic'" in srcs:               # strict-dynamic：host 與 'self' 清單全部失效
        return False
    origin = re.match(r"https?://[^/]+", src).group(0)
    return ("'self'" in srcs and origin == page_origin) or origin in srcs


def frame_allowed(policy, page_origin, ancestor_origin) -> bool:
    srcs = policy.get("frame-ancestors")         # 不會退回 default-src
    if srcs is None:
        return True
    if "'none'" in srcs:
        return False
    return ("'self'" in srcs and ancestor_origin == page_origin) or ancestor_origin in srcs


class Page(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def do_GET(self):
        nonce = make_nonce()
        csp = (f"script-src 'nonce-{nonce}' 'strict-dynamic'; object-src 'none'; base-uri 'none'; "
               "frame-ancestors 'self' https://partner.example; report-to csp")
        body = f'<script nonce="{nonce}" src="/static/classroom.js"></script>'.encode()
        self.send_response(200)
        self.send_header("Content-Security-Policy", csp)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


srv = ThreadingHTTPServer(("127.0.0.1", 0), Page)
threading.Thread(target=srv.serve_forever, daemon=True).start()
seen = []
for _ in range(2):
    conn = http.client.HTTPConnection("127.0.0.1", srv.server_address[1], timeout=3)
    conn.request("GET", "/classroom/42")
    r = conn.getresponse()
    html, csp = r.read().decode(), r.getheader("Content-Security-Policy")
    conn.close()
    header_nonce = re.search(r"'nonce-([^']+)'", csp).group(1)
    assert f'nonce="{header_nonce}"' in html         # header 與 HTML 用同一個 nonce
    seen.append(header_nonce)
srv.shutdown()
srv.server_close()
print("兩次回應的 nonce 不同：", seen[0] != seen[1], "；長度", len(seen[0]), "字元")

ORIGIN = "https://www.shengsheng.example"
p = parse_csp(csp)
print("解析結果：", {k: len(v) for k, v in p.items()})
checks = [
    ("帶正確 nonce 的 <script src>", script_allowed(p, ORIGIN, src=ORIGIN + "/static/classroom.js", nonce=seen[1])),
    ("注入的 inline script（沒有 nonce）", script_allowed(p, ORIGIN)),
    ("注入的 inline script（猜舊 nonce）", script_allowed(p, ORIGIN, nonce=seen[0])),
    ("同 origin 但沒有 nonce 的 src", script_allowed(p, ORIGIN, src=ORIGIN + "/static/x.js")),
    ("被 partner.example 嵌入 iframe", frame_allowed(p, ORIGIN, "https://partner.example")),
    ("被 phish.example 嵌入 iframe", frame_allowed(p, ORIGIN, "https://phish.example")),
]
for label, ok in checks:
    print(f"{label}：{'允許' if ok else '封鎖'}")
legacy = parse_csp("default-src 'self'; script-src 'self' 'unsafe-inline'; script-src *")
print("舊式政策允許 inline：", script_allowed(legacy, ORIGIN), "；重複的 script-src 被忽略：", legacy["script-src"])
assert [ok for _, ok in checks] == [True, False, False, False, True, False]
```

```text
兩次回應的 nonce 不同： True ；長度 24 字元
解析結果： {'script-src': 2, 'object-src': 1, 'base-uri': 1, 'frame-ancestors': 2, 'report-to': 1}
帶正確 nonce 的 <script src>：允許
注入的 inline script（沒有 nonce）：封鎖
注入的 inline script（猜舊 nonce）：封鎖
同 origin 但沒有 nonce 的 src：封鎖
被 partner.example 嵌入 iframe：允許
被 phish.example 嵌入 iframe：封鎖
舊式政策允許 inline： True ；重複的 script-src 被忽略： ["'self'", "'unsafe-inline'"]
```

第一行確認 nonce 的兩個要求：兩次回應的值不同，`assert` 也驗證了 header 與 HTML 用同一個值；16 bytes 的隨機值 base64 後是 24 字元。第二行是 `parse_csp` 解析出的五個 directive 與各自的 source 數量。

接著六個判斷。帶正確 nonce 的腳本被允許；沒有 nonce 的 inline script 被封鎖，這就是注入的腳本會遇到的情況；舊 nonce 也無效，nonce 只對自己那份回應有效。同 origin 的 `/static/x.js` 沒有 nonce 也被封鎖，因為 `'strict-dynamic'` 讓 `'self'` 失效；真實瀏覽器裡，由被信任的 `classroom.js` 動態建立的 script 則會被放行，這個傳遞行為程式沒有模擬。`frame-ancestors` 讓合作夥伴可以嵌入、外站不行。最後一行對照舊式政策：`'unsafe-inline'` 讓 inline script 全部放行，重複的 `script-src *` 被忽略。

## 23.12 在工作上怎麼用

事情處理完之後，阿德請小晴和 Rita 把本章的規則整理成各角色都能直接用的做法。

**後端工程師：把 CORS 集中成一個 middleware。** 允許清單放在設定檔並依環境分開；比對用完整 origin 字串的集合查詢，不要用 `endswith("shengsheng.example")`，它會讓 `evilshengsheng.example` 通過。`OPTIONS` 排在驗證 middleware 之前處理，依 `Origin` 改變的回應都加 `Vary: Origin`。用 curl 模擬 preflight，不開瀏覽器就能驗證設定：

```bash
# 模擬 www 的 preflight：看 status 與所有 Access-Control-* header（示意）
curl -si -X OPTIONS https://api.shengsheng.example/v1/bookings \
  -H 'Origin: https://www.shengsheng.example' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: authorization,content-type' | grep -iE '^(HTTP|access-control|vary)'

# 用不允許的 origin 再打一次：不應該出現任何 Access-Control-Allow-Origin
curl -si https://api.shengsheng.example/v1/me -H 'Origin: https://phish.example' | grep -i '^access-control'
```

第一個指令應該得到 2xx、ACAO 等於 www 的 origin、`Allow-Headers` 明列 `authorization`，並有 `Vary`；第二個指令應該沒有輸出，若 ACAO 回寫了 phish.example 的 origin，就是故事裡的反射漏洞。這兩行適合放進部署後的 smoke test。

**前端工程師：分清楚三種紅字。** CORS 錯誤在 Console 與 Network 面板（CORS error），點進去看是 preflight 還是實際請求失敗、缺哪一個 header；CSP 違規在 Console 會寫「Refused to execute inline script because it violates the following Content Security Policy directive」並點名 directive；cookie 沒送出則沒有紅字，要到請求的 Cookies 分頁看被過濾的原因（SameSite、Secure 等）。判斷流程如下：

```text
 前端呼叫 api 失敗
   │
   ├─ Console 有「blocked by CORS policy」
   │     ├─ 「Response to preflight request …」→ 看 OPTIONS：status 是 2xx 嗎？（401／404 → 修 server 路由或驗證順序）
   │     ├─ 「… not allowed by Access-Control-Allow-Headers」→ server 允許清單補上該 header（authorization 要明列）
   │     ├─ 「… must not be the wildcard '*' …」→ 帶 credentials：改成回寫允許清單內的 origin ＋ ACAC: true
   │     └─ 偶發、只有部分 origin → 檢查 Vary: Origin 與 CDN 快取
   │
   ├─ 沒有 CORS 錯誤，但 server 說沒登入
   │     └─ 請求的 Cookies 分頁：cookie 被過濾？（SameSite、Secure、Domain）fetch 有沒有 credentials: "include"？
   │
   └─ Console 有「Refused to … Content Security Policy」
         └─ 看違規的 directive：缺 nonce？inline 事件處理器？connect-src 沒列 api？
```

這張流程圖的第一刀是錯誤出現在哪裡，因為 CORS、cookie、CSP 的修正位置完全不同。CORS 的訊息本身就說明缺什麼；「偶發、只有部分 origin」最難查，幾乎都和快取有關。CSP 則依 directive 判斷是頁面寫法要改，還是政策漏列了合法來源。

**資安工程師：審查清單。** Rita 審查前端或 API 變更時檢查：CORS 是否逐字比對允許清單、沒有反射也沒有允許 `null`；session cookie 是否 `Secure`、`HttpOnly`、明寫 `SameSite`，能用 `__Host-` 就用；改變狀態的 endpoint 是否不是 `GET`，並有 token 或 Fetch Metadata 檢查；模板有沒有 `|safe`、前端有沒有 `innerHTML`；回應是否有 nonce-based CSP、`frame-ancestors`、`nosniff`；WebSocket 握手是否檢查 `Origin`。

**SRE：把瀏覽器的回報接進監控。** CSP 違規報告暴增，可能是某次部署漏了 nonce，也可能是有人正在嘗試注入；`OPTIONS` 的比例在調整 `Max-Age` 後應明顯下降。CDN 的 cache key 沒有納入 `Origin` 時，要確認 origin server 一定送 `Vary: Origin`。

## 23.13 常見錯誤與除錯

下表整理聲聲 Live 與一般團隊最常遇到的瀏覽器安全模型問題。多數症狀出現在瀏覽器，根因卻在 server、CDN 或 cookie 設定。

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| preflight 失敗，`OPTIONS` 回 401 或 404 | 驗證 middleware 套在 `OPTIONS` 上，或框架沒有註冊 `OPTIONS` 路由 | DevTools 看 OPTIONS 的 status；用 curl 送 preflight | 在驗證之前處理 `OPTIONS`，回 204 與 `Allow-*` |
| 加了 `Allow-Headers: *` 仍說 authorization 不被允許 | `*` 永遠不涵蓋 `Authorization` | 錯誤訊息點名 `authorization` | 明列 `authorization` |
| 帶 cookie 的請求報「must not be the wildcard」 | credentials 模式下 ACAO 用了 `*` | 前端是否 `credentials: "include"` | 允許清單比對後回寫單一 origin，加 `Allow-Credentials: true` |
| 只有某些 origin 偶發 CORS 錯誤 | 回應缺 `Vary: Origin`，CDN 或瀏覽器快取混用 | 比對錯誤回應的 ACAO 是否是別的 origin；看 CDN 的命中標記 | 所有 CORS 回應加 `Vary: Origin`，或公開資源固定回 `*` |
| 任何網站都能讀到登入使用者的 API 回應 | 反射任意 `Origin` 加 `Allow-Credentials: true`，或允許 `null`、用字尾比對 | 用不允許的 `Origin` 送 curl，看是否回寫 | 逐字比對允許清單；拒絕 `null` |
| 登入後 API 仍說未登入 | cookie 是 `Lax`／`Strict` 而請求跨站、缺 `Secure`、fetch 沒有 `credentials: "include"`，或第三方 cookie 被封鎖 | 請求的 Cookies 分頁看被過濾原因 | 調整 SameSite 與部署架構；嵌入情境用 `Partitioned` 或 Storage Access API |
| 外站能取消學生的預約 | 改變狀態的 endpoint 沒有 CSRF 防禦，或用了 `GET` | 審查路由的 method 與驗證；看 log 裡的 `Origin`、`Sec-Fetch-Site` | 改成 `POST`／`DELETE`，加 token 與 Fetch Metadata 檢查 |
| 開啟 CSP 後整個頁面壞掉 | inline script 與 `onclick` 沒有 nonce，或 `connect-src` 漏列 api、rt | Console 的違規訊息與 directive | 先用 Report-Only 收集，改寫成 `addEventListener`，補 nonce |
| CSP 有 nonce 卻沒擋住注入 | nonce 寫死，或帶 nonce 的頁面被共用快取 | 連續請求兩次比對 nonce | 每個回應用 `secrets` 產生；帶 nonce 的頁面不共用快取 |
| 頁面在外站 iframe 裡被嵌入 | 沒有 `frame-ancestors` 或 `X-Frame-Options` | curl 看回應 header | 依頁面類型設定 `frame-ancestors`；同時送 `X-Frame-Options` |
| WebSocket 被外站開啟並帶著 cookie | WebSocket 不受 CORS 保護，server 沒檢查 `Origin` | 用不同的 `Origin` 做握手測試 | 握手時以允許清單檢查 `Origin`，並要求 token |

除錯的通則是把「誰在擋」分清楚。CORS 是瀏覽器在擋**讀取**，看回應 header；SameSite 是瀏覽器在擋**送出 cookie**，看請求的 cookie；CSP 是瀏覽器在擋**執行**，看 Console 的 directive；CSRF 防禦與授權則是 server 在擋，看 server 的 log。從錯誤出現的位置倒推回去，幾乎都能在幾分鐘內定位。

## 23.14 動手練習

1. **用 DevTools 觀察 preflight 與快取**（真實工具）。找一個呼叫跨源 API 的網頁（或用本章實驗二的 server 加上一個本機 HTML 頁面），在 Network 面板勾選 Preserve log，連續觸發兩次同樣的跨源 `POST`。
   答案要點：第一次有 `OPTIONS` 與實際請求兩筆，`Max-Age` 內的第二次只有實際請求。觀察前先關掉 DevTools 的 Disable cache，它可能讓 preflight 每次都重送。

2. **延伸實驗一：加上 `Expose-Headers` 的檢查**。替實驗一的模擬器加一個函式 `readable_headers(req, resp)`，回傳腳本能讀到的回應 header：CORS-safelisted response header，加上 `Access-Control-Expose-Headers` 列出的名稱；帶 credentials 時 `*` 不算萬用字元。
   答案要點：沒有 `Expose-Headers` 時，`x-request-id` 讀不到；`Expose-Headers: *` 在不帶 credentials 時可讀到全部（`Set-Cookie` 永遠讀不到），帶 credentials 時 `*` 只被當成一個叫做 `*` 的 header 名稱。

3. **延伸實驗二：重現 CDN 的 `Vary` 問題**。在實驗二的 server 與迷你瀏覽器之間加一個簡單的快取（以 URL 為 key 的 dict），先讓 www 請求 `GET /v1/courses`，再讓 teach 請求同一個 URL。先關掉 server 的 `Vary`，再讓快取依 `Vary` 列出的 header 組成 key。
   答案要點：沒有 `Vary` 時 teach 拿到 ACAO 等於 www 的快取回應而被擋；cache key 納入 `Origin` 後各自一份。被拒絕的回應也要帶 `Vary: Origin`，否則它被快取後會擋住合法的 origin。

4. **用 curl 審查一個網站的安全 header**（真實工具）。對你負責的服務執行 `curl -sI` 看首頁與 API 的回應 header，列出 `Content-Security-Policy`、`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy`、`Strict-Transport-Security` 與所有 `Set-Cookie` 的屬性。
   答案要點：對照 23.5、23.8、23.10 節的表格，標出缺少的 header、沒寫 `SameSite` 的 cookie、只有 `'unsafe-inline'` 的 CSP，以及漏了 `frame-ancestors`、`base-uri` 的政策。

5. **延伸實驗四：加上 key 輪替**。讓 `check_double_submit` 接受一個 key 清單（目前的 key 加上前一把 key），簽發只用目前的 key，驗證時依序嘗試清單中的每一把。
   答案要點：先把新 key 加入驗證清單並開始用它簽發，舊 token 都過期後再移除舊 key，和 Flask 3.1 的 `SECRET_KEY_FALLBACKS` 思路相同；每一把都用 `hmac.compare_digest` 比較。

6. **設計題：白板嵌入**。合作夥伴要在自己的網站嵌入聲聲 Live 的白板，學生需要保持登入狀態。列出你需要的 `frame-ancestors`、cookie 屬性、CSRF 防禦，以及在封鎖第三方 cookie 的瀏覽器上的替代方案。
   答案要點：`frame-ancestors` 列出合作夥伴的 origin；iframe 內是跨站情境，cookie 需要 `SameSite=None; Secure`，最好加 `Partitioned`；變更請求用 token 與 Fetch Metadata 檢查；封鎖第三方 cookie 的瀏覽器上，改用 Storage Access API，或由父頁面以 `postMessage` 傳入短效 token 並檢查訊息的 `origin`。

## 本章重點整理

- origin 是 scheme、host、port 的組合，三者相同才是 same-origin；site 是 scheme 加上 registrable domain，`www` 與 `api` 跨 origin 卻同 site。
- same-origin policy 擋跨源讀取，不擋嵌入與送出；加上瀏覽器自動附 cookie，就是 CSRF 的成因。
- CORS 是 server 用 header 放寬讀取限制、由瀏覽器執行的協議；它不是 server 的存取控制，也不是 CSRF 防禦。
- simple request 會直接送出；其他請求先送不帶 cookie 的 `OPTIONS` preflight，server 必須在驗證之前回 2xx。
- ACAO 只能是單一 origin 或 `*`；帶 credentials 時不能用 `*`、要有 `Allow-Credentials: true`，而 `Allow-Headers: *` 永遠不含 `Authorization`。
- 允許多個 origin 要逐字比對允許清單後回寫；反射任意 `Origin` 加上 credentials，等於讓任何網站以使用者身分讀取回應。
- CORS header 隨 `Origin` 改變時，所有回應（包括被拒絕的）都要加 `Vary: Origin`；preflight 用 `Max-Age` 快取，瀏覽器另有上限。
- session cookie 用 `Secure`、`HttpOnly`、明寫 `SameSite`，能用 `__Host-` 就用；不寫 `Domain` 範圍最窄，`Path` 不是安全邊界。
- `Lax` 只在跨站的頂層安全方法導覽時送出，`Strict` 只在同站送出，`None` 需要 `Secure` 且受第三方 cookie 政策限制；SameSite 管不到同 site 子網域與會改狀態的 `GET`。
- CSRF 要分層防禦：SameSite、synchronizer token 或 HMAC 綁定 session 的 signed double-submit、Fetch Metadata 與 `Origin` 檢查。
- XSS 的根本修法是依輸出情境編碼、避免危險的 DOM API；`HttpOnly` 防偷不防用。
- nonce-based strict CSP 用每個回應不同的 nonce 只放行合法腳本；`base-uri`、`form-action`、`frame-ancestors` 不退回 `default-src`。
- clickjacking 由被嵌入的頁面以 `frame-ancestors` 防禦，只能用 HTTP header 送；WebSocket 不受 CORS 保護，server 要自己檢查 `Origin`。

## 延伸問答

> [!question]- Q1. 為什麼 same-origin policy 允許跨站送出表單，卻不允許跨站讀取回應？這個設計今天還合理嗎？
> SOP 是在 Web 已經普及之後才補上的規則。當時的網站早已大量依賴跨站嵌入圖片、腳本，以及把表單送到別的網域（例如付款頁面送到金流商），如果連「送出」都禁止，會立刻破壞大量既有網站。另一方面，「讀取」別站內容在當時是新出現的能力（XHR），可以從一開始就設成預設禁止。所以 SOP 選擇保護最直接的資料洩漏：讀取。
>
> 這個妥協的代價就是 CSRF：送得出去、又會自動帶 cookie 的請求，被 server 當成使用者本人的操作。今天的瀏覽器用 SameSite 預設值、Fetch Metadata 等方式逐步補強，但沒有、也不能直接禁止跨站送出，因為 OAuth 的 redirect、金流的表單回傳等合法流程仍然需要它。因此設計 API 時要假設「任何網站都能讓使用者的瀏覽器送出 simple request」，並在 server 端防禦。

> [!question]- Q2. 你在 production 的 API log 裡看到大量 Origin 是陌生網域的請求，而且狀態碼都是 200。CORS 不是應該擋住它們嗎？
> CORS 擋的是瀏覽器把回應交給腳本，不是請求抵達 server。simple request（例如沒有自訂 header 的 `GET`）會直接送出，server 照常處理並回 200，瀏覽器收到回應後發現沒有符合的 `Access-Control-Allow-Origin`，才拒絕讓腳本讀取。所以 log 裡出現這些請求是正常的，重點是要確認兩件事：回應沒有把那些陌生 origin 寫進 ACAO，以及這些請求沒有造成副作用。
>
> 接著要判斷它們是什麼。如果是 `GET` 公開資料，可能是別人的網站直接嵌用你的 API，只要回應讀不到，影響主要是流量成本；如果是會改變狀態的 `POST`，就要檢查它們是否被 CSRF 防禦擋下（應該看到 403 而不是 200），否則就是漏洞。也要記得 `Origin` 可以被 curl 任意偽造，它只代表「瀏覽器裡的頁面來源」，不能當作身分驗證。

> [!question]- Q3. 面試題：為什麼帶 credentials 的 CORS 回應不能用 Access-Control-Allow-Origin: *？
> `*` 的語意是「這份回應是公開的，任何網站都可以讀」。對不帶 credentials 的請求，這是合理的：回應不含使用者的身分，內容和直接用 curl 打一次沒有差別。但帶 credentials 的請求附上了使用者的 cookie，回應很可能是個人化的私人資料，例如課表、私訊、token。如果允許 `*`，就等於宣告任何網站都可以用這位使用者的身分讀取他人無法取得的資料。
>
> 所以規格要求 server 在這種情況下必須「明確點名」一個 origin，並另外用 `Access-Control-Allow-Credentials: true` 表示同意，兩個條件缺一不可，目的是逼開發者有意識地做出決定。這也是為什麼「反射任意 Origin」特別危險：它在形式上滿足了點名的要求，實質上卻把同意權交給了每一個請求者。

> [!question]- Q4. 手算：www 頁面在 t=0 對 /v1/bookings 送出帶 Authorization 的 POST，preflight 回應 Max-Age 600；接著在 t=300 送同樣的 POST、t=500 送多帶 X-CSRF-Token 的 POST、t=700 再送原本的 POST。總共會有幾個 OPTIONS？
> t=0 時快取是空的，送出第一個 OPTIONS，快取 (www, /v1/bookings, POST, authorization+content-type) 到 t=600。t=300 的請求 method 與 header 都相同，命中快取，不送 OPTIONS。t=500 的請求多了 `x-csrf-token`，瀏覽器要確認這個新 header 是否被允許：如果先前的 preflight 回應已經在 `Allow-Headers` 裡列了 `x-csrf-token`（實驗二的 server 就是這樣），快取中的 header 允許清單已涵蓋它，可以不送新的 preflight；如果沒有列，就要再送一次。
>
> t=700 已超過 600 秒的有效期，再送一次 OPTIONS。所以答案是 2 或 3 個，取決於第一次回應是否已列出 `x-csrf-token`。這題的重點是：預檢快取記的是「server 允許的 method 與 header」，新請求只要落在允許範圍內就能重用；這也是為什麼 server 一次回完整的允許清單，比只回剛好被問到的 header 更省 RTT。

> [!question]- Q5. 看 log 找原因：老師後台 teach 偶爾在打開課程頁時出現 CORS 錯誤，重新整理後又好了；www 從來沒有問題。你會怎麼查？
> 「偶發、重新整理就好、只影響部分 origin」三個特徵合起來，幾乎都指向快取：某一層快取存了一份 ACAO 等於 www 的回應，再交給 teach 的請求。查法是先在 DevTools 找一個失敗的請求，看回應 header 裡 `Access-Control-Allow-Origin` 的值是不是 www，再看 CDN 的快取命中 header（例如 `Age` 或供應商自訂的 cache status）是否顯示命中。
>
> 確認後的修法有兩種。如果這份資料是公開的，最簡單的是固定回 `Access-Control-Allow-Origin: *`，回應不再隨 origin 變化，快取怎麼共用都正確；如果必須點名 origin，就讓 origin server 對所有回應加上 `Vary: Origin`，並確認 CDN 會依 `Vary` 分開快取，或在 CDN 設定把 `Origin` 加入 cache key。修完後要清除 CDN 上已經被汙染的快取，否則舊的錯誤回應會持續到 TTL 到期。

> [!question]- Q6. 設計取捨：既然 SameSite=Lax 已經擋住大部分跨站 POST，聲聲 Live 還需要 CSRF token 嗎？
> 需要，因為 SameSite 的保護邊界是 site 而不是 origin，而且有幾個明確的缺口。第一，同 site 的子網域發出的請求不受 SameSite 限制，聲聲 Live 有行銷活動頁、外部託管的說明中心等較不受控的子網域，任何一個被接管或有 XSS，都能對 api 發出帶 cookie 的請求。第二，`Lax` 放行跨站的頂層 `GET` 導覽，只要有一個會改變狀態的 `GET` 就會被利用。第三，白板嵌入等需求會讓部分 cookie 必須是 `None`，它們完全沒有 SameSite 保護。
>
> 第四是瀏覽器差異：沒寫 `SameSite` 時，各瀏覽器的預設行為並不一致，舊瀏覽器甚至不支援這個屬性。所以合理的設計是把 SameSite 當作第一層，再加上 token 或 Fetch Metadata 檢查作為不依賴 cookie 行為的第二層；成本只是一個 header 與一個 HMAC 運算，換來的是不必擔心單一機制的例外情況。

> [!question]- Q7. 為什麼 CSP 的 nonce 每個回應都要重新產生？用一個長期固定、但夠長夠隨機的 nonce 不行嗎？
> nonce 的安全性來自「攻擊者在注入時不知道它」。固定的 nonce 只要被任何人看過一次就失效：攻擊者可以自己註冊帳號、打開聲聲 Live 的頁面，從 HTML 原始碼裡讀到它，接下來在儲存型 XSS 的內容裡寫上同一個 nonce，瀏覽器就會乖乖執行。長度再長、隨機性再好都沒有用，因為問題不是被猜到，而是被公開了。
>
> 每個回應重新產生，攻擊者讀到的只是自己那一次的值，對其他使用者的頁面無效；這也是實驗五「用舊 nonce 被封鎖」那一行的意義。同樣的邏輯解釋了快取的陷阱：帶 nonce 的 HTML 被 CDN 共用快取，等於讓大量使用者共享同一個 nonce。如果頁面必須被快取，就改用 hash-based CSP，它允許的是「特定內容的腳本」，不依賴每次回應的秘密值。

> [!question]- Q8. 情境判斷：前端同事建議把 access token 存在 localStorage，「這樣就不用處理 CSRF 了」。你怎麼評估？
> 這個說法有一半是對的：token 放在 localStorage、由 JavaScript 放進 `Authorization` header 時，瀏覽器不會自動附上它，外站送出的跨站請求沒有身分，CSRF 的前提確實消失了。而且帶 `Authorization` 的跨源請求需要 preflight，只要 CORS 允許清單正確，外站也無法讀到回應。
>
> 另一半的代價是 XSS 的影響變大：localStorage 對同 origin 的任何腳本都可讀，一次 XSS 就能把 token 帶走，攻擊者可以在自己的機器上持續使用，直到 token 過期；相比之下，`HttpOnly` cookie 至少不會被帶走。所以這是「用 CSRF 風險換 XSS 風險」的取捨，不是免費的。聲聲 Live 在本章的做法是 access token 短效並只放在記憶體、refresh token 放在 `__Host-` 前綴的 `HttpOnly` cookie 並用 CSRF 與嚴格的 CORS 保護，再用 nonce-based CSP 降低 XSS 的機率；第 27 章會更進一步把網站改成 BFF，讓 token 完全不進 JavaScript、瀏覽器只持有 `__Host-sid` session cookie，第 28 章再從 OAuth 的角度討論一次。
