# 第 12 章　擁塞控制與 Head-of-Line Blocking

> [!abstract] 本章地圖
> **核心問題**：TCP 不知道網路中間有多寬、塞了多少人，它怎麼決定「一次能送多少」，又為什麼一個掉包就能讓整頁停住？
>
> **你會學到**：
> - 用 bandwidth-delay product（BDP）手算一條路需要多大的視窗，判斷「慢」是不是視窗太小造成的
> - 說清楚 slow start、congestion avoidance、fast recovery 與逾時的 cwnd 變化，並用 Python 模擬 Reno 與 CUBIC
> - 解釋 AIMD 為什麼會讓多條流走向公平、RTT 不同時又為什麼不公平
> - 看出 bufferbloat 的症狀，知道 AQM、ECN、pacing 與 BBR 各解決哪一段問題
> - 分辨 HTTP 層與 TCP 層兩種 head-of-line blocking，並知道 HTTP/2、HTTP/3 各解掉哪一種
> - 在 Linux 上用 `ss -ti`、`sysctl`、`tc` 觀察與調整擁塞控制
>
> **前置知識**：第 10 章（TCP 連線與 header）、第 11 章（序號、ACK、重傳、滑動視窗與流量控制）

## 12.1 故事：歐洲學生的 2 Mbps 與老師家裡的 600 ms

聲聲 Live 開始經營歐洲市場的第二個月，客服轉來一張單：「在德國的學生下載課程回放，速度只有 2 Mbps 左右，可是對方家裡是 100 Mbps 光纖，看 YouTube 完全沒問題。」回放檔放在台灣機房的 origin（203.0.113.70，平常位於 CDN 後方），因為是付費內容、要即時驗證簽章，這條下載路徑沒有經過 CDN 快取，學生直接從台北的 origin 拉檔案。小晴先在台北用 `curl` 測同一個檔案，跑到 300 Mbps 以上，於是直覺是「歐洲那邊網路不好」。

阿德看了一眼就搖頭：「先算 BDP。台北到歐洲 RTT 大約 250 ms，你要跑 100 Mbps，同時在路上飛的資料要 3 MB 左右。你看一下 nginx 的 `listen` 有沒有人設過 `sndbuf`？」小晴打開設定，真的有一行 `sndbuf=64k`，是幾年前有人為了「省記憶體」加的。64 KiB 除以 250 ms，剛好就是 2 Mbps。台北的測試之所以快，是因為 RTT 只有 1 ms，同樣的 64 KiB 一秒能來回一千次。

同一週，Joe 也遇到怪事：一位老師上課時視訊一直卡，WebRTC 統計顯示 RTT 從平常的 40 ms 一路漲到 600 ms，但丟包率幾乎是 0。追問之下，老師的另一台電腦正在把上週的錄影同步到雲端硬碟。上傳流量把家用路由器的 buffer 塞滿，視訊封包得在幾百毫秒長的隊伍後面排隊。這叫 **bufferbloat**，丟包率低反而是症狀的一部分。

第三件事來自手機使用者：在捷運上打開課程頁，常常整頁「卡一下」才一次全部出來，連很小的 JSON 都在等。課程頁走 HTTP/2，所有資源共用一條 TCP 連線，一個封包掉了，後面所有 stream 的資料都要等它重傳。這是 TCP 層的 **head-of-line blocking**。

這三個問題的共同根源，是 TCP 必須在「看不見網路中間」的情況下決定送多快。本章從這個問題出發：先算清楚管子有多大，再看 TCP 如何試探管子、遇到壅塞怎麼退讓、buffer 太大時為什麼退讓得太晚，最後回到 head-of-line blocking，說明為什麼 HTTP/2 與 HTTP/3 的設計會長成現在的樣子。

## 12.2 為什麼需要擁塞控制

第 11 章的**流量控制（flow control）**解決的是「不要淹沒接收端」：接收端在每個 ACK 裡告訴對方自己的接收視窗（**rwnd**，receive window），也就是 buffer 還剩多少空間。可是 sender 與 receiver 之間還有一長串路由器與交換器，它們的 buffer 也會滿，而且它們不會在 TCP header 裡告訴你任何事。**擁塞控制（congestion control）**解決的是「不要淹沒網路」：sender 自己維護一個**擁塞視窗（cwnd，congestion window）**，代表它認為網路此刻能承受多少還沒被確認的資料。

真正能送出的量是兩者取小：

```text
  可以在路上飛的 bytes（in-flight） ≤ min( cwnd , rwnd )

          sender 自己猜的              receiver 告訴你的
          「網路吃得下多少」            「我的 buffer 剩多少」
               │                            │
               ▼                            ▼
  ┌────────┐  cwnd  ┌──────┐ ┌──────┐ ┌──────┐  rwnd  ┌──────────┐
  │ sender │═══════►│ R1   │►│ R2   │►│ R3   │═══════►│ receiver │
  └────────┘ 1 Gbps └──────┘ └──┬───┘ └──────┘ 1 Gbps └──────────┘
                                │
                         瓶頸 100 Mbps
                    （佇列在這裡長出來）
```

這張圖要看三件事。第一，整條路的速度由最慢的那一段決定，這一段叫**瓶頸（bottleneck）**；sender 的網卡是 1 Gbps 沒有用，R2 往下只有 100 Mbps。第二，送得比瓶頸快的部分不會消失，而是在 R2 的佇列裡排隊；佇列滿了，新來的封包就被丟掉（這種「滿了就丟尾巴」的佇列叫 **drop-tail**）。第三，sender 看不到 R2，只能從結果推測：ACK 回來的速度、RTT 是否變長、有沒有封包遺失。

如果大家都不管網路、只看 rwnd 狂送，會發生什麼事？1986 年 10 月，網際網路真的發生過：LBL 到 UC Berkeley 之間的吞吐量從 32 kbps 掉到 40 bps，掉了將近一千倍。這叫**擁塞崩潰（congestion collapse）**：路由器滿載丟包，sender 逾時就重傳，重傳又讓佇列更滿，線路上大部分頻寬都在送「已經送過、注定被丟」的副本，有效吞吐量趨近於零。Van Jacobson 隨後在 1988 年的論文〈Congestion Avoidance and Control〉提出 slow start、congestion avoidance 與更好的 RTO 估計，這套機制經過多次修訂，就是今天 RFC 5681 的基礎。

sender 能用的壅塞訊號有三種，後面介紹的每個演算法都可以用「它看哪個訊號」來分類：

| 訊號 | 意義 | 誰在用 | 缺點 |
|---|---|---|---|
| 丟包（loss） | 某個佇列已經滿到丟東西 | Reno、CUBIC | 太晚：佇列已經塞滿才知道；無線網路的隨機丟包會被誤判 |
| 延遲增加（delay） | 佇列正在變長 | Vegas、BBR（部分）、HyStart | 會被 RTT 的雜訊干擾；和 loss-based 流共存時容易吃虧 |
| ECN 標記 | 路由器主動說「我快滿了」 | 搭配 AQM 的各種演算法、DCTCP、L4S | 需要路徑上的設備都支援並正確設定 |

> [!warning] 常見誤解
> 「cwnd 是 TCP header 裡的欄位」——不是。header 裡的 Window 欄位是 rwnd（第 10 章）。cwnd 只存在 sender 的 kernel 裡，封包上看不到，只能用 `ss -ti` 這類工具從 sender 那端讀出來。這也代表擁塞控制是 sender 決定的：聲聲 Live 的 server 換演算法，只影響下載方向；學生上傳作業的方向由學生的作業系統決定。

## 12.3 Bandwidth-Delay Product：管子有多大

**BDP（bandwidth-delay product，頻寬延遲乘積）**是頻寬乘上 RTT，代表「要把管子塞滿，路上需要同時有多少還沒被確認的資料」。可以把網路想成一條水管：頻寬是管子的粗細，RTT 是從送出到 ACK 回來的時間，BDP 就是管子的容積。sender 每個 RTT 最多只能送出一個視窗的資料，所以：

```text
  吞吐量上限 ≈ min(cwnd, rwnd, 傳送 buffer) ÷ RTT

  例：100 Mbps、RTT 250 ms
      BDP = 100 × 10⁶ bit/s ÷ 8 × 0.25 s = 3,125,000 bytes ≈ 3 MB

  時間 ─────────────────────────────────────────────────►
  視窗 64 KiB： [■]..........................[■]..........................[■]
                 ↑送完 64 KiB 就停，等 250 ms 的 ACK         → 約 2 Mbps
  視窗 3 MB：   [■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■]
                 ↑ACK 回來時下一批剛好送完，線路不停            → 約 100 Mbps
```

圖中每個 `■` 是一段正在送的資料，`.` 是線路空著、sender 在等 ACK 的時間。視窗小的時候，sender 很快送完配額，然後枯等一個 RTT；視窗等於 BDP 時，第一個 ACK 回來的那一刻剛好送完最後一個 byte，線路一直有東西在跑。這就是「視窗至少要等於 BDP」的直觀理由。

下面這段程式把聲聲 Live 常見的幾條路徑算一遍，也驗證故事裡 2 Mbps 的來源：

```python
# 計算 bandwidth-delay product（BDP），以及「視窗太小」時的吞吐量上限
MSS = 1448  # 常見的 TCP payload 大小（1500 - 20 IP - 20 TCP - 12 timestamp option）

def bdp_bytes(mbps: float, rtt_ms: float) -> float:
    return mbps * 1e6 / 8 * rtt_ms / 1000

def ceiling_mbps(window_bytes: float, rtt_ms: float) -> float:
    # 每個 RTT 最多送出一個視窗的資料
    return window_bytes * 8 / (rtt_ms / 1000) / 1e6

paths = [
    ("同機房 10.20.0.0/16 內", 10_000, 0.5),
    ("台北 → 東京 edge", 100, 35),
    ("台北 → 歐洲學生家", 100, 250),
    ("4G 手機（同城）", 30, 60),
]
print("    頻寬      RTT        BDP   MSS 數  路徑")
for name, mbps, rtt in paths:
    b = bdp_bytes(mbps, rtt)
    print(f"{mbps:>6} M {rtt:>6} ms {b/1024:>6.0f} KiB {b/MSS:>6.0f}   {name}")

print()
for window in (64 * 1024, 1 * 1024 * 1024, 4 * 1024 * 1024):
    c = ceiling_mbps(window, 250)
    print(f"視窗 {window//1024:>5} KiB、RTT 250 ms → 最多 {c:6.1f} Mbps")

assert round(bdp_bytes(100, 250)) == 3_125_000          # 100 Mbps × 250 ms = 3.125 MB
assert ceiling_mbps(64 * 1024, 250) < 2.2               # 64 KiB 視窗在長 RTT 上只剩 2 Mbps
```

```text
    頻寬      RTT        BDP   MSS 數  路徑
 10000 M    0.5 ms    610 KiB    432   同機房 10.20.0.0/16 內
   100 M     35 ms    427 KiB    302   台北 → 東京 edge
   100 M    250 ms   3052 KiB   2158   台北 → 歐洲學生家
    30 M     60 ms    220 KiB    155   4G 手機（同城）

視窗    64 KiB、RTT 250 ms → 最多    2.1 Mbps
視窗  1024 KiB、RTT 250 ms → 最多   33.6 Mbps
視窗  4096 KiB、RTT 250 ms → 最多  134.2 Mbps
```

逐步看輸出。第一張表的「MSS 數」是 BDP 換成封包數，cwnd 在 Linux 裡就是用封包數（MSS）計量。同機房 10 Gbps 的 BDP 只有 610 KiB，因為 RTT 很短；台北到歐洲雖然只有 100 Mbps，BDP 卻有 3 MB、兩千多個封包，是同機房的五倍。這種「頻寬大、RTT 長」的路徑叫**長肥管線（long fat network，LFN）**，是擁塞控制最難處理的情況，後面講 CUBIC 時會再回來。

第二段輸出就是故事的答案。64 KiB 的視窗在 250 ms 的路徑上最多 2.1 Mbps，和客服單的數字吻合；要跑滿 100 Mbps，視窗必須到 3 MB 以上。注意 TCP header 的 Window 欄位只有 16 bits，最多表示 65,535 bytes，所以超過 64 KiB 一定要靠交握時協商的 **window scale** 選項（第 10 章）；任何一端關掉 window scale，長 RTT 的路徑就會被鎖死在這個上限。

> [!tip]
> 判斷「慢」是不是視窗問題的快速心算：吞吐量 × RTT 大約等於某個整齊的數字（64 KiB、128 KiB、4 MB）時，幾乎一定是某個 buffer 上限，而不是網路壅塞。壅塞造成的慢通常會抖動，而且和 RTT 的乘積不會剛好是 2 的冪次。

## 12.4 Slow Start：從小開始，指數成長

新連線剛建立時，sender 完全不知道 BDP 是多少。直接送一個巨大的視窗可能瞬間塞爆瓶頸，送太小又浪費時間。**slow start（慢啟動）**的策略是：從一個小的**初始視窗（initial window，IW）**開始，每收到一個 ACK，cwnd 就增加 1 個 MSS。因為每個送出去的封包都會換回一個 ACK，結果是每個 RTT 的 cwnd 大約翻倍。名字叫「慢」，其實是相對於「一開始就送滿 rwnd」而言，成長速度是指數的。

```text
 Server（sender）                               Client（receiver）
   │ cwnd=10 ──── seg 1..10 ──────────────────────►│   RTT 1：送 10 個
   │◄──────────── ACK × 10 ──────────────────────── │
   │ cwnd=20 ──── seg 11..30 ─────────────────────►│   RTT 2：每個 ACK +1 → 20
   │◄──────────── ACK × 20 ──────────────────────── │
   │ cwnd=40 ──── seg 31..70 ─────────────────────►│   RTT 3：40
   │◄──────────── ACK × 40 ──────────────────────── │
   │ cwnd=80 ──── seg 71..150 ────────────────────►│   RTT 4：80
   │           ……直到 cwnd ≥ ssthresh 或發生丟包……  │
```

這張時序圖說明了兩件事。第一，成長是由 ACK 驅動的：ACK 回來得越快，cwnd 長得越快，所以 RTT 短的連線 slow start 結束得早。這個「用 ACK 的節奏決定送出節奏」的性質叫 **ACK clocking**，ACK 自然地以瓶頸的速度回來，sender 也就自然地以瓶頸的速度送出。第二，要長到台北到歐洲需要的 2,158 個封包，從 10 開始翻倍需要約 8 個 RTT，也就是 2 秒；一個 300 KB 的網頁在 slow start 期間就傳完了，永遠用不到整條線路的頻寬。這就是為什麼短連線對 RTT 這麼敏感，也是第 13 章與第 46 章一直強調連線重用的原因。

初始視窗本身也演進過。RFC 5681 規定的上限大約是 4 個封包；Google 在 2010 年前後的實驗顯示提高到 10 個封包能明顯縮短網頁載入時間，後來寫成 RFC 6928，Linux 在 2011 年前後把預設值改成 10（**IW10**）。10 個 MSS 大約 14 KB，這也是網頁效能圈常說「首屏關鍵資源最好壓在 14 KB 內」的由來。

slow start 何時停止？sender 有一個門檻 **ssthresh（slow start threshold）**。cwnd 小於 ssthresh 時用 slow start，達到 ssthresh 後改用下一節的 congestion avoidance。新連線的 ssthresh 通常設成非常大，所以第一次 slow start 往往一路翻倍到丟包為止，然後把 ssthresh 設成丟包時的一半。因為最後一個 RTT 是翻倍送出，衝過頭的量可能是瓶頸容量的一倍，第一次丟包常常是一整串。Linux 的 CUBIC 實作因此加入 **HyStart**：在 slow start 期間觀察 RTT，一旦發現延遲開始上升（佇列在長）就提早離開 slow start；改良版 HyStart++ 已寫成 RFC 9406。

還有一個常被忽略的細節：連線閒置一段時間（超過一個 RTO）後再送資料，Linux 預設會把 cwnd 降回初始視窗重新 slow start，理由是閒置期間網路狀況可能已經改變。控制它的是 `net.ipv4.tcp_slow_start_after_idle`，預設 1。對聲聲 Live 這種「長連線上偶爾送一大包」的服務（例如 HTTP/2 連線在使用者閒置後突然要拉一張投影片），這會讓每次突發都重付 slow start 的成本；是否關閉要看路徑是否穩定，常見做法是在內部服務或 CDN 到 origin 的連線上關掉。

> [!note]
> 現代 Linux 的 slow start 是依「被確認的 byte 數」成長（appropriate byte counting，RFC 3465），而不是單純數 ACK 的個數。因為 delayed ACK（第 11 章）可能兩個封包才回一個 ACK，若只數 ACK，cwnd 每個 RTT 只會變成 1.5 倍；依 byte 計算才會接近翻倍。

## 12.5 Congestion Avoidance、AIMD 與 Reno 的丟包反應

離開 slow start 後，sender 已經接近瓶頸的容量，再翻倍就會塞爆。**congestion avoidance（壅塞避免）**改成線性成長：每個 RTT 只增加 1 個 MSS（實作上是每個 ACK 增加 MSS × MSS ÷ cwnd，累積一個 RTT 剛好 1 個 MSS）。一旦偵測到丟包，就把 cwnd 砍半。這個「加法增加、乘法減少」的規則叫 **AIMD（additive increase, multiplicative decrease）**，是 TCP Reno 以來所有 loss-based 演算法的骨架。

偵測到丟包有兩種情況，嚴重程度不同，反應也不同：

```text
                   ┌────────────────────────────────────────────┐
                   │                                            │
  新連線 ──► ┌─────▼──────┐  cwnd ≥ ssthresh   ┌──────────────┐ │
             │ Slow Start │───────────────────►│  Congestion  │ │
             │ 每 RTT ×2  │                    │  Avoidance   │ │
             └─────┬──────┘                    │  每 RTT +1   │ │
                   │  3 個 dupACK              └──────┬───────┘ │
                   │                                  │ 3 個 dupACK
                   ▼                                  ▼         │
             ┌──────────────────────────────────────────────┐   │
             │ Fast Retransmit + Fast Recovery              │   │
             │ ssthresh = flight/2；cwnd = ssthresh（+3）   │   │
             │ 立刻重傳遺失的那一段                          │   │
             └───────────────────────┬──────────────────────┘   │
                                     │ 收到新資料的 ACK          │
                                     └──────────────────────────┘
                                         回到 Congestion Avoidance

  任何狀態 ── RTO 逾時 ──► ssthresh = flight/2；cwnd = 1；回到 Slow Start
```

依圖逐一看。第 11 章講過，receiver 收到亂序的封包時會重複 ACK 最後一個連續的位置，連續三個 **duplicate ACK（dupACK）**表示「後面的封包都到了，只有中間一個不見」。這代表網路還在流動，只是某個佇列短暫溢出，所以 Reno 只砍一半：ssthresh 設成在途資料量（flight size）的一半，cwnd 也降到這附近，然後立刻重傳遺失的封包（**fast retransmit**），不必等逾時；在等待重傳確認的期間繼續依 dupACK 送新資料（**fast recovery**）。RFC 5681 的細節是 cwnd 先設成 ssthresh + 3 個 MSS，每多一個 dupACK 再加 1，收到新資料的 ACK 後收回到 ssthresh。

**RTO（retransmission timeout）**逾時則嚴重得多：連 dupACK 都沒有，代表整批資料或整批 ACK 都消失了，sender 對網路狀況一無所知。這時 cwnd 直接降為 1 個 MSS，從頭 slow start 到新的 ssthresh。這也是為什麼一次 RTO 對吞吐量的傷害遠大於一次 fast retransmit，第 11 章介紹的 SACK、RACK-TLP 等機制的主要價值，就是讓更多丟包能用快速路徑恢復、避免掉進 RTO。原版 Reno 在一個視窗內掉多個封包時容易退化成 RTO，**NewReno**（RFC 6582）修正了這點，今天說「Reno」時通常指 NewReno 的行為。

| 事件 | 判斷依據 | ssthresh | cwnd | 之後的階段 |
|---|---|---|---|---|
| 收到新資料的 ACK（slow start） | cwnd < ssthresh | 不變 | 每個 ACK +1 MSS | Slow Start |
| 收到新資料的 ACK（avoidance） | cwnd ≥ ssthresh | 不變 | 每 RTT +1 MSS | Congestion Avoidance |
| 3 個 duplicate ACK | 只掉了少數封包 | flight ÷ 2 | 約 ssthresh | Fast Recovery → Avoidance |
| RTO 逾時 | 完全沒有回音 | flight ÷ 2 | 1 MSS | Slow Start |
| 收到 ECN-Echo | 路由器標記壅塞 | flight ÷ 2 | 約 ssthresh（不必重傳） | Avoidance |

長期來看，Reno 的 cwnd 會畫出經典的**鋸齒（sawtooth）**：線性爬升到塞爆 buffer，砍半，再線性爬升。12.10 的模擬會把它印出來。這個鋸齒有一個重要推論，叫 **Mathis 公式**：在丟包率 p 穩定的情況下，Reno 的吞吐量大約是 (MSS ÷ RTT) × 1.22 ÷ √p。代入台北到歐洲的 RTT 250 ms、MSS 1448 bytes、丟包率 0.01%，得到約 5.7 Mbps。意思是：在長 RTT 的路徑上，萬分之一的丟包就足以讓 Reno 跑不到 100 Mbps 的零頭。這是 CUBIC 與 BBR 出現的直接動機。

AIMD 還有第二個好處：**公平性（fairness）**。Chiu 與 Jain 在 1989 年證明，多條流共享瓶頸時，加法增加讓每條流長得一樣快，乘法減少讓大的流減得比小的流多，兩者反覆作用，差距每經過一次丟包就縮小一半，最後收斂到平分頻寬。換成「乘法增加、乘法減少」就不會收斂，因為比例永遠不變。12.10 的模擬會驗證這點，也會看到 AIMD 的弱點：每條流是「每個 RTT」才加 1，RTT 短的流長得快，在同一個瓶頸上會拿走遠多於公平份額的頻寬。

```text
  流 B 的 cwnd
    ▲
 100│╲            公平線（A = B）
    │  ╲         ╱
    │    ╲  ●  ╱      ● 起點：A 小、B 大
    │      ╲ ╲╱        ↗ 加法增加：沿 45° 往右上（兩條一起 +1）
    │      ╱╲ ↗        ↙ 乘法減少：沿原點連線往左下（各自 ÷2）
    │    ╱ ↙ ╲         每來回一次，就更靠近公平線
    │  ╱       ╲
    │╱  效率線（A + B = 容量）
    └─────────────────────────────► 流 A 的 cwnd
```

這張相位圖是 Chiu–Jain 論證的圖像版本。橫軸與縱軸是兩條流的 cwnd，斜線 A + B = 容量是效率線，越過它就會丟包；45° 的虛線是公平線。加法增加讓點沿 45° 方向移動，不改變兩者的差距；乘法減少讓點朝原點縮，差距跟著減半。來回幾次之後，點就被「擠」到兩條線的交叉處：既不浪費頻寬，也平分頻寬。

## 12.6 CUBIC：為長肥管線設計

Reno 的問題在 12.5 已經露出端倪：每個 RTT 才加 1 個 MSS，在 BDP 兩千個封包的路徑上，砍半之後要花一千個 RTT（250 秒）才能長回來。**CUBIC** 換了一個思路：成長速度不再綁 RTT，而是以「距離上次丟包經過的真實時間 t」決定 cwnd，形狀是一條三次曲線：

```text
  W(t) = C × (t − K)³ + W_max          K = ∛( W_max × (1 − β) ÷ C )
  β = 0.7（丟包時 cwnd 乘上 0.7）、C = 0.4（RFC 9438 建議值）

  cwnd
    ▲                                          ╱  ③ 凸區：越過 W_max 後
    │                                        ╱      試探性地加速
 W_max ─ ─ ─ ─ ─ ─ ─ ─ ───────────────── ─╱─ ─ ─ ─
    │                ╱   ② 平台：在上次出事的
    │             ╱        高度附近小心慢慢走
    │          ╱ ① 凹區：離 W_max 遠時快速長回去
 0.7×W_max ●
    │      ↑丟包
    └──────┴──────────────────┬───────────────────────► 時間 t
           0                  K
```

依曲線的三段來看。丟包後 cwnd 降到 0.7 × W_max（比 Reno 的 0.5 溫和），W_max 是丟包前的大小。① 剛開始距離 W_max 還遠，三次函數的斜率很大，快速長回去；② 接近 W_max 時曲線變平，因為上次就是在這個高度出事，CUBIC 在這裡停留較久、慢慢試；③ 若過了 K 秒還沒丟包，表示網路可能多了空間，曲線再度變陡，開始探索新的上限。K 只和 W_max、β、C 有關，與 RTT 無關，所以 RTT 20 ms 與 250 ms 的連線，丟包後都在差不多的秒數內回到原本的大小，這大幅緩解了 Reno 的 RTT 不公平。

CUBIC 也不想在短 RTT、小 BDP 的網路上比 Reno 慢，所以它同時計算一個「如果我是 Reno 會到哪裡」的估計值，取兩者較大者，這段叫 **Reno-friendly region**（舊文件稱 TCP-friendly region）。實務上，在資料中心或同城這類短 RTT 路徑，CUBIC 的行為和 Reno 很接近；差異主要出現在長肥管線。

CUBIC 由 Linux 2.6.19（2006 年）起成為預設演算法，2018 年寫成 RFC 8312，2023 年更新為 Standards Track 的 RFC 9438。今天大部分 server 端的 TCP 預設就是 CUBIC；其他作業系統的預設依版本而定，新版的主流平台多半也已採用 CUBIC。它仍然是 loss-based：一定要把 buffer 塞到丟包才會退，這個本質會在下一節變成問題。

## 12.7 Bufferbloat：buffer 越大，延遲越長

為了避免丟包，路由器、家用 Wi-Fi 分享器、數據機、手機基地台都配了 buffer。直覺上 buffer 越大越好：突發流量來時先存起來，就不會丟包。但對 loss-based 的 TCP 來說，丟包是唯一的「停」訊號；buffer 越大，訊號越晚出現，TCP 就越會把 buffer 塞滿。佇列滿著的時候，每個經過這裡的封包都要先排完前面的隊，延遲因此暴增。這就是 **bufferbloat（緩衝膨脹）**。

```text
  老師家的上傳線路：20 Mbps，家用路由器 buffer 1000 個封包

  雲端硬碟上傳（CUBIC）──┐
                         ▼
               ┌──────────────────────────────────────────┐
  視訊封包 ───►│▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓│──► 20 Mbps ──► 網際網路
   （WebRTC）  └──────────────────────────────────────────┘
                 ↑ 新封包排在最後          最前面的封包每 0.6 ms 送出一個

  排隊延遲 = 佇列中的 bytes ÷ 線路速度
           = 1000 × 1500 B × 8 ÷ 20,000,000 bit/s = 0.6 秒
```

照圖手算一次。20 Mbps 的線路每秒送出約 1667 個 1500-byte 封包，一個封包佔 0.6 ms；佇列裡排了 1000 個，最後一個要等 600 ms 才輪到。視訊封包和上傳的封包共用同一個 FIFO 佇列，所以一起排。這就是故事裡 Joe 看到的數字：基本 RTT 40 ms 加上 600 ms 的排隊；而且因為 buffer 夠大，幾乎沒有丟包。對視訊、語音、遊戲、甚至 DNS 查詢來說，延遲才是關鍵；大檔上傳只在乎吞吐量。drop-tail 大 buffer 讓前者為後者買單。

那 buffer 要多大才對？傳統的經驗法則是「一條 Reno 流需要一個 BDP 的 buffer 才能維持滿載」：cwnd 在丟包後減半，如果 buffer 至少一個 BDP，減半後仍然 ≥ BDP，線路不會空下來。12.10 的模擬會驗證：buffer 只有 ¼ BDP 時利用率掉到約 89%，1 BDP 時 100%，但再大下去只會增加延遲，不會增加吞吐量。設備廠商傾向把 buffer 做大（不丟包看起來比較好），而家用上行線路速度慢，同樣大小的 buffer 換算成的排隊時間特別長，所以 bufferbloat 最常出現在家用網路的上傳方向。

對策分成三層，各管一段：

- **AQM（active queue management，主動佇列管理）**：路由器不等 buffer 滿，而是在佇列「持續排太久」時就提早丟包或標記。**CoDel**（RFC 8289）看封包在佇列裡停留的時間（sojourn time），若持續超過目標值（預設 5 ms）達一個 interval（預設 100 ms），就開始丟包。**FQ-CoDel**（RFC 8290）再加上 **fair queueing**：每條流各有自己的小佇列輪流送，視訊封包不必排在上傳後面。Linux 上許多發行版透過 systemd 把 `fq_codel` 設為預設 qdisc，不少家用路由器韌體也提供「SQM」選項。
- **ECN（Explicit Congestion Notification，RFC 3168）**：IP header 的兩個 bits 讓路由器把封包標成「經歷壅塞（CE）」而不是丟掉，receiver 在 TCP 的 ECE flag 回報，sender 照樣減速但不必重傳。AQM 搭配 ECN，可以在不丟包的情況下維持短佇列。
- **sender 端的改變**：pacing（把封包平均分散在整個 RTT，而不是一口氣送出一整個 cwnd）可以避免瞬間把佇列打滿；model-based 的 BBR 則試圖讓在途資料剛好等於 BDP，根本不排隊。

| 情境 | 吞吐量 | 排隊延遲 | 誰受害 |
|---|---|---|---|
| buffer 太小（< BDP） | 單條流跑不滿 | 很低 | 大檔傳輸 |
| buffer 約 1 BDP，drop-tail | 滿載 | 最多約 1 個 RTT | 輕微影響互動流量 |
| buffer 遠大於 BDP，drop-tail | 滿載 | 數百毫秒以上 | 視訊、語音、遊戲、DNS |
| 大 buffer＋FQ-CoDel／ECN | 接近滿載 | 約 5 ms 量級 | 單條流在極端情況下少量損失 |

> [!warning] 常見誤解
> 「延遲高一定是頻寬不夠，升級方案就好」——bufferbloat 時，頻寬加倍只讓排隊時間減半，只要還有一條 loss-based 流在塞 buffer，延遲依然在百毫秒等級。判斷方法是看「有負載時的延遲」：空閒時 ping 40 ms、開始上傳後變 600 ms，就是佇列問題，不是頻寬問題。

> [!note] 2026 現況
> 截至 2026 年 10 月，L4S（Low Latency, Low Loss, Scalable throughput）架構已在 2023 年以 RFC 9330–9332 發布（依 2026 年 10 月的知識整理，未逐一查證），它用 ECN 搭配雙佇列，讓支援的流能維持極短的佇列。部分寬頻與行動業者已開始試行，但端到端支援仍在擴展中，不能假設使用者的路徑上有 L4S。

## 12.8 BBR：用模型而不是丟包

Reno 與 CUBIC 都把「丟包」當成壅塞的定義，但丟包發生時佇列早已滿了，這是 bufferbloat 的根源；反過來在淺 buffer 或有隨機丟包的無線路徑上，它們又會把非壅塞造成的丟包誤判為壅塞，速度掉得太兇。Google 在 2016 年提出 **BBR（Bottleneck Bandwidth and Round-trip propagation time）**，改問另一個問題：瓶頸的頻寬是多少、沒有排隊時的 RTT 是多少？知道這兩個數，就知道 BDP，也就知道最佳的送法。

```text
  送出速率／RTT
    ▲
    │                       ┌─────────────── 吞吐量：到瓶頸頻寬就不再增加
    │                     ╱ │
    │                   ╱   │          ╱ RTT：開始排隊後線性上升
    │                 ╱     │        ╱
    │   RTprop ─────────────┼──────╱
    │             ╱         │    ╱
    │           ╱           │  ╱
    │         ╱             │╱              ✕ buffer 滿 → 丟包
    └───────────────────────┼───────────────┼────────► 在途資料量
                         BDP（BBR 想停的點）  BDP + buffer（Reno／CUBIC 停的點）
```

這張圖把 12.3 與 12.7 合在一起。在途資料小於 BDP 時，送越多吞吐量越高，RTT 不變（還沒排隊）；超過 BDP 後吞吐量不再增加，多出來的資料全部進佇列，RTT 線性上升；到 BDP 加上 buffer 才丟包。loss-based 演算法在最右邊才知道要退，BBR 想停在左邊那個轉折點：吞吐量最大、延遲最小。這個最佳操作點的概念來自 Kleinrock 在 1970 年代的分析。

難處在於兩個量無法同時量測：要量瓶頸頻寬就得把管子塞滿（會排隊，RTT 失真），要量最低 RTT 就得讓佇列清空（頻寬沒用滿）。BBR 用輪流試探解決：

```text
  ┌──────────┐ 頻寬連續 3 輪不再成長  ┌───────┐ 在途量降到 BDP ┌──────────────────────┐
  │ STARTUP  │──────────────────────►│ DRAIN │──────────────►│      PROBE_BW         │
  │ 速率×2.89│                       │ 排空  │               │ 速率增益依序循環：     │
  └──────────┘                       └───────┘               │ 1.25 → 0.75 → 1 ×6    │
                                                             └───────┬──────▲────────┘
                              約 10 秒沒有看到更低的 RTT              │      │ 200 ms 後
                                                             ┌───────▼──────┴────────┐
                                                             │      PROBE_RTT        │
                                                             │ cwnd 降到 4 個封包     │
                                                             └───────────────────────┘
```

依狀態看。STARTUP 類似 slow start，以約 2.89 倍的增益快速提升速率，直到量到的送達速率連續幾輪不再增加，表示到頂了。DRAIN 把 STARTUP 期間灌進佇列的資料排掉。之後大部分時間在 PROBE_BW：用一個 RTT 的 1.25 倍速率試探有沒有更多頻寬，下一個 RTT 用 0.75 倍把試探造成的佇列排空，再用 1 倍穩定送六個 RTT。每隔約 10 秒，若沒有量到更低的 RTT，就進入 PROBE_RTT，把 cwnd 壓到 4 個封包約 200 ms，讓佇列清空、重新量最小 RTT。整個過程中 BBR 以 **pacing rate**（估計頻寬乘上增益）平滑地送出封包，cwnd 只當作上限（約 2 倍 BDP），所以 BBR 非常依賴 pacing；早期 Linux 需要搭配 `fq` qdisc，後來 kernel 內建了 TCP 層的 pacing。

BBR 的取捨也很明顯，這是面試與實務都常被問的部分：

| 面向 | Reno | CUBIC | BBR（v1 的已知特性） |
|---|---|---|---|
| 壅塞訊號 | 丟包 | 丟包 | 頻寬與最小 RTT 的模型 |
| 長肥管線 | 很差 | 好 | 很好 |
| 有隨機丟包的路徑 | 很差 | 差 | 好（不把丟包當主要訊號） |
| 佇列延遲 | 塞滿 buffer | 塞滿 buffer | 理想上接近零；實務上仍有少量 |
| 與 CUBIC 共存 | 被 CUBIC 壓制 | 基準 | 深 buffer 時可能被壓制，淺 buffer 時可能搶走過多頻寬 |
| 淺 buffer 時的重傳率 | 普通 | 普通 | 可能很高（v1 不理會丟包） |
| RTT 不公平 | 短 RTT 佔優 | 較緩和 | 長 RTT 可能佔優 |

BBRv2 與 BBRv3 的改進方向，正是把丟包與 ECN 重新納入模型，降低在淺 buffer 上的重傳率，並改善與 CUBIC 共存的公平性。對聲聲 Live 的意義是：BBR 很適合「server 送大量資料給遠方或行動網路的使用者」（回放下載、直播分發），但它不是萬靈丹，換之前要量測重傳率與對其他流量的影響。

> [!note] 2026 現況
> 截至 2026 年 10 月（依 2026 年 10 月的知識整理，未逐一查證）：Linux mainline 自 4.9 起內建 BBR（v1 行為）；Google 對外表示其服務已改用 BBRv3，BBRv3 的 Linux patch 公開但是否併入 mainline 依版本而定；IETF 的 CCWG 正在把 BBR 寫成草案，狀態仍是 draft。QUIC 的 RFC 9002 以類似 NewReno 的演算法作為參考，各家 QUIC 實作則常用 CUBIC 或 BBR，這也是 QUIC 能在使用者空間快速換演算法的優勢（第 13 章）。

## 12.9 Head-of-Line Blocking：TCP 與 HTTP 的兩種形式

**head-of-line blocking（HOL blocking，隊頭阻塞）**指的是：隊伍最前面的東西卡住，後面所有東西都動不了，即使後面的東西本身已經準備好。就像超商排隊時第一位客人在找會員條碼，後面拿著一瓶水的人也只能等。網路上有兩種常被混為一談的 HOL，分別發生在不同的層。

第一種在 **HTTP 層**。HTTP/1.1 在一條連線上一次只能進行一個請求／回應（第 20 章）；就算用 **pipelining**（不等回應就連送多個請求），規格也要求回應必須依請求的順序回來。只要前面那支 API 慢，後面已經算好的回應也要等。瀏覽器實際上預設不用 pipelining，而是對同一個 host 開多條連線（常見是 6 條）平行請求。下面這段程式在 localhost 上重現：

```python
# HTTP/1.1 的應用層 HOL：同一條連線上，回應必須照請求順序回來
import socket
import threading
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"          # 讓連線保持 keep-alive

    def do_GET(self):
        if self.path == "/slow":
            time.sleep(0.3)                # 模擬一支要查資料庫的慢 API
        body = self.path.encode()
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):          # 不要讓 access log 干擾輸出
        pass

server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
port = server.server_address[1]
threading.Thread(target=server.serve_forever, daemon=True).start()

def read_responses(sock, count, t0):
    """讀出 count 個回應，記錄每個 body 抵達的時間。"""
    buf, done = b"", []
    while len(done) < count:
        buf += sock.recv(4096)
        while b"\r\n\r\n" in buf:
            head, rest = buf.split(b"\r\n\r\n", 1)
            length = int([l for l in head.split(b"\r\n") if l.lower().startswith(b"content-length")][0].split(b":")[1])
            if len(rest) < length:
                break
            done.append((rest[:length].decode(), round(time.monotonic() - t0, 1)))
            buf = rest[length:]
    return done

req = "GET {} HTTP/1.1\r\nHost: api.shengsheng.example\r\n\r\n"

# 情境 A：pipelining，/slow 與 /fast 排在同一條連線上
t0 = time.monotonic()
with socket.create_connection(("127.0.0.1", port)) as s:
    s.sendall((req.format("/slow") + req.format("/fast")).encode())
    pipelined = read_responses(s, 2, t0)
print("同一條連線（pipelining）：", pipelined)

# 情境 B：兩條連線各送一個請求（瀏覽器對 HTTP/1.1 的實際做法）
results = {}
def fetch(path):
    with socket.create_connection(("127.0.0.1", port)) as s:
        s.sendall(req.format(path).encode())
        results[path] = read_responses(s, 1, t0)[0]
t0 = time.monotonic()
threads = [threading.Thread(target=fetch, args=(p,)) for p in ("/slow", "/fast")]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("兩條連線（各自獨立）：  ", [results["/slow"], results["/fast"]])
server.shutdown()
server.server_close()

assert [p for p, _ in pipelined] == ["/slow", "/fast"]   # 回應順序 = 請求順序
assert pipelined[1][1] >= 0.3                             # /fast 被 /slow 擋住
assert results["/fast"][1] < 0.1                          # 分開連線就不會被擋
```

輸出顯示兩種情境。pipelining 時，`/fast` 雖然 server 一收到就能回答，卻要等 `/slow` 的 0.3 秒結束才輪到，因為 HTTP/1.1 的回應沒有任何編號，client 只能靠順序對應請求，server 不能插隊。分成兩條連線後，`/fast` 立刻回來（0.0 秒）。這就是 HTTP/1.1 時代瀏覽器開多條連線、網站做 domain sharding 的原因；代價是每條連線都要各自交握、各自 slow start，而且 6 條連線會在瓶頸上拿到約 6 倍的公平份額（12.5 的 AIMD 公平是「每條流」公平，不是每個使用者公平）。

第二種在 **TCP 層**。HTTP/2（第 22 章）把請求拆成帶 stream ID 的 frame，在同一條連線上交錯傳送，HTTP 層的 HOL 消失了。但 TCP 對應用程式提供的是一條**有序的位元組流**：kernel 只能把「連續」的資料交給應用程式。只要中間一個 TCP segment 遺失，後面已經抵達的 segment 全部卡在 kernel 的接收 buffer 裡，不管它們屬於哪個 stream。

```text
  HTTP/2 over TCP：三個 stream 的 frame 交錯在同一個位元組流

  送出順序   #0     #1     #2      #3     #4     #5     #6 ...
  stream    api    css    slide   api    css    slide  api
  網路上     ✓      ✓      ✕遺失    ✓      ✓      ✓      ✓
                          │
  TCP 交給     #0 #1 │ ←─ 洞 ─→ │ #3 #4 #5 #6 ... 全部在 kernel buffer 等
  應用程式           └──── 等 #2 重傳（約 1 RTT）────┘

  QUIC：每個 stream 各自排序
  api   : #0 #3 #6 ...   立刻交付
  css   : #1 #4 #7 ...   立刻交付
  slide : ── 等 #2 ── #5 #8 ...  只有這個 stream 等
```

圖中上半部，#2 遺失後，TCP 雖然已經收到 #3 到 #6，卻因為序號不連續而不能交給 HTTP/2 的程式，api 與 css 兩個 stream 和 #2 毫無關係，也被迫等待一個 RTT 以上。下半部是 QUIC 的做法：排序是每個 stream 各自的事，遺失的封包只影響它所屬的 stream。下面的模擬把交付時間算出來：

```python
# 同一條 HTTP/2 連線上三個 stream 交錯傳送，第 3 個封包掉了。
# 比較「TCP 單一位元組流」與「每個 stream 各自排序（QUIC 式）」的交付時間
ONE_WAY = 40          # 單程延遲（ms）
GAP = 2               # 每 2 ms 送出一個封包
LOST = 2              # 第 3 個封包（index 2）在路上遺失
# 後面第 3 個封包（#5）到達時產生第 3 個 duplicate ACK，回到 sender 再重傳一次單程
RETX_ARRIVE = (LOST + 3) * GAP + ONE_WAY + ONE_WAY + ONE_WAY   # = 130 ms

streams = ["api.json", "app.css", "slide.jpg"]
packets = [(i, streams[i % 3]) for i in range(12)]    # round-robin 交錯

arrive = {}
for i, s in packets:
    arrive[i] = RETX_ARRIVE if i == LOST else i * GAP + ONE_WAY

def deliver_tcp():
    # TCP 只能把連續的 byte 交給應用程式：前面有洞，後面全部等
    out, horizon = {}, 0
    for i, _ in packets:
        horizon = max(horizon, arrive[i])
        out[i] = horizon
    return out

def deliver_per_stream():
    # 每個 stream 各自要求順序，別的 stream 掉包不影響自己
    out, horizon = {}, {s: 0 for s in streams}
    for i, s in packets:
        horizon[s] = max(horizon[s], arrive[i])
        out[i] = horizon[s]
    return out

tcp, quic = deliver_tcp(), deliver_per_stream()
print(" 封包 stream       到達   TCP 交付   per-stream 交付")
for i, s in packets:
    flag = "  ← 遺失後重傳" if i == LOST else ""
    print(f"  #{i:<2} {s:<11} {arrive[i]:>4} ms {tcp[i]:>6} ms {quic[i]:>10} ms{flag}")

print("各 stream 最後一個封包交付時間：")
for s in streams:
    last = max(i for i, t in packets if t == s)
    print(f"  {s:<11} TCP {tcp[last]:>4} ms   per-stream {quic[last]:>4} ms")

assert all(tcp[i] == RETX_ARRIVE for i, _ in packets if i > LOST)   # TCP：全部被卡住
assert quic[0] == ONE_WAY and quic[1] == ONE_WAY + GAP and quic[3] == 3 * GAP + ONE_WAY
assert max(quic[i] for i, s in packets if s != "slide.jpg") < 70        # 其他 stream 不受影響
```

逐行看。封包 #2 原本應在 44 ms 到達，遺失後要等後面三個封包觸發 3 個 duplicate ACK（#5 在 50 ms 到達，dupACK 再花 40 ms 回到 sender），重傳又要 40 ms，最後在 130 ms 才到。TCP 欄位顯示 #3 到 #11 全部在 130 ms 才交付，api.json 與 app.css 被拖慢超過一倍；per-stream 欄位中，只有 slide.jpg 的封包等到 130 ms，另外兩個 stream 在 58 ms 與 60 ms 就完成。丟包率越高、RTT 越長，差距越大，這就是手機在捷運上打開課程頁「整頁卡一下」的原因。也因此有人量測到，在高丟包的網路上，HTTP/2 單一連線的表現可能不如 HTTP/1.1 的 6 條連線：後者的一個丟包只卡住六分之一的資源。

| 版本 | HTTP 層 HOL | TCP（傳輸層）HOL | 怎麼解 |
|---|---|---|---|
| HTTP/1.1（單一連線） | 有：回應依序回來 | 有 | 開多條連線、domain sharding |
| HTTP/2 | 沒有：frame 帶 stream ID 交錯 | 有：一條 TCP，所有 stream 共用順序 | 只能靠降低丟包、更快的重傳 |
| HTTP/3（QUIC） | 沒有 | 沒有：每個 stream 獨立排序 | QUIC 在 UDP 上自己做可靠傳輸（第 13 章） |

> [!warning] 常見誤解
> 「HTTP/3 完全沒有 HOL」——QUIC 消除的是跨 stream 的 HOL，同一個 stream 內的資料仍然要依序交付：slide.jpg 本身還是要等它的遺失封包。另外，HTTP/3 的 header 壓縮 QPACK 刻意設計成可以避免 HPACK 那種跨 stream 的依賴，但若設定允許引用尚未確認的動態表項，仍可能出現阻塞（第 22 章）。HOL 也不只存在於 HTTP：TLS record 必須完整收到才能解密，一個大 record 跨多個封包時，掉一個封包整個 record 都得等。

## 12.10 動手做：在一個瓶頸上重現 cwnd 的一生

這一節用四段模擬，依序重現 Reno 的鋸齒、CUBIC 在長肥管線上的優勢、bufferbloat，以及多條流的公平性。模擬是以「每個 RTT 一輪」或固定時間步長計算的簡化模型，不模擬每個 ACK；目的是讓數字和本章的手算對得起來，而不是精確重現 kernel 的行為。

### 步驟 1：Reno 的 slow start、鋸齒與逾時

```python
# 以「每個 RTT 一輪」模擬 TCP Reno 的 cwnd（單位：MSS）
# 這條路一次能容納的封包 = BDP（在線上飛）+ 瓶頸 buffer（在佇列裡排隊）
BDP, BUFFER = 24, 8
CAPACITY = BDP + BUFFER
RTO_ROUND = 30               # 刻意在這一輪製造逾時（例如整段 ACK 都掉了）

def reno(rounds: int):
    cwnd, ssthresh = 10, 10_000   # IW10；初始 ssthresh 視為無限大
    rows = []
    for r in range(rounds):
        phase = "SS" if cwnd < ssthresh else "CA"
        sent = cwnd
        if r == RTO_ROUND:
            ssthresh = max(cwnd // 2, 2)
            cwnd, event = 1, f"RTO → ssthresh={ssthresh}, cwnd=1"
        elif cwnd > CAPACITY:     # 塞爆 buffer → 丟包 → 收到 3 個 duplicate ACK
            ssthresh = max(cwnd // 2, 2)
            cwnd, event = ssthresh, f"3 dupACK → ssthresh={ssthresh}, cwnd={ssthresh}"
        elif cwnd < ssthresh:     # slow start：每個 ACK +1 MSS ≈ 每 RTT 翻倍
            cwnd, event = min(cwnd * 2, ssthresh), ""
        else:                     # congestion avoidance：每 RTT +1 MSS
            cwnd, event = cwnd + 1, ""
        rows.append((r, phase, sent, event))
    return rows

rows = reno(38)
for r, phase, sent, event in rows:
    bar = "#" * min(sent, CAPACITY) + "X" * max(0, sent - CAPACITY)
    print(f"{r:>2} {phase} {sent:>3} {bar:<{CAPACITY + 9}} {event}".rstrip())
print(" " * 10 + "." * (CAPACITY - 1) + "^ 容量 = BDP 24 + buffer 8")

sent = [s for _, _, s, _ in rows]
assert sent[:3] == [10, 20, 40]                 # slow start 每輪翻倍，衝過頭
assert sent[3] == 20                            # 丟包後減半（multiplicative decrease）
assert all(sent[i + 1] - sent[i] == 1 for i in range(3, 15))   # additive increase
assert sent[RTO_ROUND + 1] == 1                 # 逾時最嚴厲：從 1 重新 slow start
```

### 步驟 2：長肥管線上的 Reno 與 CUBIC

```python
# 丟包之後，Reno 與 CUBIC 怎麼把 cwnd 長回來？（單位：MSS）
# 路徑：台北 → 歐洲，RTT 250 ms，BDP 約 2000 MSS，瓶頸 buffer 200 MSS
RTT, BDP, BUFFER, MSS = 0.25, 2000, 200, 1448
C, BETA = 0.4, 0.7                     # CUBIC 常數（RFC 9438 建議值）
ALPHA = 3 * (1 - BETA) / (1 + BETA)    # Reno-friendly 估計的斜率

def simulate(algo: str, seconds: int):
    w_max, cwnd, epoch = 2000.0, 1000.0 if algo == "reno" else 1400.0, 0.0
    trace, losses = [], 0
    for step in range(int(seconds / RTT)):
        t = step * RTT
        trace.append((t, cwnd))
        if cwnd > BDP + BUFFER:                       # buffer 滿 → 丟包
            losses += 1
            w_max, epoch = cwnd, t
            cwnd = cwnd * (0.5 if algo == "reno" else BETA)
            continue
        if algo == "reno":
            cwnd += 1                                 # 每 RTT +1 MSS
        else:
            e = t + RTT - epoch                       # 距離上次丟包的「真實時間」
            k = (w_max * (1 - BETA) / C) ** (1 / 3)
            cubic = C * (e - k) ** 3 + w_max
            est = w_max * BETA + ALPHA * e / RTT
            cwnd = max(cubic, est)
    return trace, losses

def mbps(trace):
    avg = sum(min(w, BDP) for _, w in trace) / len(trace)   # 超過 BDP 的部分只是在排隊
    return avg * MSS * 8 / RTT / 1e6

reno, reno_loss = simulate("reno", 60)
cubic, cubic_loss = simulate("cubic", 60)
print(" 時間   Reno  CUBIC   每格 100 MSS；R=Reno、C=CUBIC、| = BDP")
for i in range(0, len(reno), 12):                     # 每 3 秒取樣一次
    t, r = reno[i]
    c = cubic[i][1]
    line = [" "] * 24
    line[BDP // 100] = "|"
    line[int(r // 100)] = "R"
    line[int(c // 100)] = "C"
    print(f"{t:>4.0f} s {r:>6.0f} {c:>6.0f}   {''.join(line).rstrip()}")
print(f"60 秒平均：Reno {mbps(reno):5.1f} Mbps（丟包 {reno_loss} 次）  "
      f"CUBIC {mbps(cubic):5.1f} Mbps（丟包 {cubic_loss} 次）")

k0 = (2000 * (1 - BETA) / C) ** (1 / 3)
print(f"CUBIC 的 K = {k0:.1f} 秒：不論 RTT 多長，約 {k0:.0f} 秒回到丟包前的大小")
assert reno_loss == 0 and cubic_loss >= 1             # Reno 60 秒內根本長不回去
assert mbps(cubic) > 1.5 * mbps(reno)
```

### 步驟 3：bufferbloat 的延遲

```python
# Bufferbloat：同一條 20 Mbps 上傳線路，buffer 大小不同，延遲差多少？
# 以「每個 RTT 一輪」的流體模型模擬一條 Reno 大檔上傳，同時量測視訊封包要排多久
LINK_PPS = 20e6 / 8 / 1500           # 瓶頸每秒能送出的 1500-byte 封包數 ≈ 1667
BASE_RTT = 0.040                      # 沒有排隊時的 RTT
BDP = LINK_PPS * BASE_RTT             # ≈ 67 個封包

def run(buffer_pkts: float, aqm_target: float | None = None, model_based=False, rounds=4000):
    cwnd, busy, total, delays = BDP, 0.0, 0.0, []
    for _ in range(rounds):
        queue = max(0.0, cwnd - BDP)                  # 超過 BDP 的封包只能在 buffer 排隊
        qdelay = queue / LINK_PPS
        rtt = BASE_RTT + qdelay
        overflow = queue > buffer_pkts
        if aqm_target is not None and qdelay > aqm_target:
            overflow = True                           # AQM：排隊太久就提早丟（或標 ECN）
        busy += min(cwnd, BDP) / BDP * rtt            # 這一輪線路忙碌的比例 × 時間
        total += rtt
        delays.append(qdelay)
        if model_based:
            cwnd = BDP                                # 理想化：送出量剛好等於 BDP
        elif overflow:
            cwnd = max(cwnd / 2, 2)                   # Reno 丟包減半
        else:
            cwnd += 1
    delays.sort()
    return busy / total, sum(delays) / len(delays), delays[int(len(delays) * 0.95)]

cases = [
    ("buffer 16 包（¼ BDP）", run(16)),
    ("buffer 67 包（1 BDP）", run(67)),
    ("buffer 1000 包（家用路由器）", run(1000)),
    ("buffer 1000 包＋AQM 目標 5 ms", run(1000, aqm_target=0.005)),
    ("理想 model-based（cwnd≈BDP）", run(1000, model_based=True)),
]
print(f"BDP ≈ {BDP:.0f} 包；每個排隊的封包增加 {1000 / LINK_PPS:.2f} ms")
print(" 線路利用率  平均排隊   p95 排隊   情境")
for name, (util, avg, p95) in cases:
    print(f"   {util:6.1%}  {avg * 1000:7.1f} ms {p95 * 1000:7.1f} ms   {name}")

util_small, _, _ = cases[0][1]
util_bloat, avg_bloat, _ = cases[2][1]
util_aqm, avg_aqm, _ = cases[3][1]
assert util_small < 0.95 < util_bloat                 # buffer 太小：線路吃不滿
assert avg_bloat > 0.2                                # buffer 太大：排隊上百毫秒
assert avg_aqm < 0.01 and util_aqm > 0.8              # AQM：用少量利用率換到低延遲
```

這是老師家 20 Mbps 上傳線路的模擬，BDP 約 67 個封包，每多排一個封包就多 0.6 ms。逐列看：buffer 只有 ¼ BDP 時，Reno 減半後 cwnd 低於 BDP，線路有 11% 的時間空著，但排隊很短；buffer 1 BDP 時剛好滿載，平均排隊 20 ms；buffer 1000 個封包時吞吐量沒有再增加，平均排隊卻到 400 ms、p95 約 580 ms，和 Joe 看到的 600 ms 同一個數量級。第四列是同樣大的 buffer 加上「排隊超過 5 ms 就提早丟」的簡化 AQM：延遲回到 1 ms 以下，代價是單條流的利用率掉到約 84%。真實的 CoDel 會要求延遲持續超過目標一段時間才動作，多條流時利用率也會更高；這裡呈現的是單條 Reno 流的最壞情況。最後一列是理想化的 model-based sender，在途資料剛好等於 BDP，滿載且零排隊，這正是 BBR 追求的操作點。

### 步驟 4：多條流共享瓶頸的公平性

```python
# 多條流共享同一個瓶頸：AIMD 為什麼會走向公平？RTT 不同時又如何？
CAPACITY = 100        # 瓶頸（BDP + buffer）總共容納的封包數

def jain(xs):
    # Jain's fairness index：1.0 代表完全平均，1/n 代表一條流獨占
    return sum(xs) ** 2 / (len(xs) * sum(x * x for x in xs))

def share(start, increase, rounds=400):
    w = list(start)
    snapshots = []
    for r in range(rounds):
        if sum(w) > CAPACITY:              # 同時丟包（drop-tail 佇列常見的「同步」）
            w = [x / 2 for x in w]
            snapshots.append((r, [round(x, 1) for x in w]))
        else:
            w = [increase(x) for x in w]
    return w, snapshots

aimd, snaps = share([2, 80], lambda x: x + 1)
print("AIMD：兩條流 RTT 相同，起點 2 與 80")
for r, w in snaps[:6]:
    print(f"  第 {r:>3} 輪丟包後 cwnd = {w}  Jain = {jain(w):.3f}")
print(f"  400 輪後 cwnd = {[round(x, 1) for x in aimd]}  Jain = {jain(aimd):.3f}")

mimd, _ = share([2, 80], lambda x: x * 1.05)
print(f"MIMD（每輪 ×1.05）400 輪後 = {[round(x, 1) for x in mimd]}  Jain = {jain(mimd):.3f}")

# RTT 不同：用真實時間模擬，每條流每過一個「自己的 RTT」才 +1
def rtt_unfair(rtts, seconds=120.0, dt=0.001):
    link_pps = 2000.0
    w = [10.0 for _ in rtts]
    sent = [0.0 for _ in rtts]
    t = 0.0
    while t < seconds:
        rates = [wi / r for wi, r in zip(w, rtts)]      # 每條流的送出速率 = cwnd / RTT
        if sum(rates) > link_pps * 1.1:                 # 超過線路＋buffer → 同時丟包
            w = [x / 2 for x in w]
        else:
            w = [x + dt / r for x, r in zip(w, rtts)]   # 每經過一個 RTT 才加 1
        sent = [s + rate * dt for s, rate in zip(sent, rates)]
        t += dt
    return [s / seconds for s in sent]

near, far = rtt_unfair([0.020, 0.080])
print(f"RTT 20 ms 的學生：{near:6.0f} 包/秒；RTT 80 ms 的學生：{far:6.0f} 包/秒；"
      f"比例 {near / far:.1f} 倍")

assert jain(aimd) > 0.99            # AIMD 收斂到公平
assert jain(mimd) < 0.6             # MIMD 保持原本的不公平比例
assert near / far > 4               # 同步丟包下，吞吐量比例接近 RTT 比的平方
```

```text
  第  10 輪丟包後 cwnd = [6.0, 45.0]  Jain = 0.631

  第  62 輪丟包後 cwnd = [20.2, 30.0]  Jain = 0.963

  400 輪後 cwnd = [50.0, 50.0]  Jain = 1.000
```

**Jain's fairness index** 是衡量公平的常用指標：所有流拿到一樣多時為 1，一條流獨占時為 1/n（兩條流時是 0.5）。第一段，兩條 RTT 相同的流從 2 與 80 出發，每次同時丟包後差距減半：45 對 6、35 對 15.5、30 對 20.2……第 140 輪已經是 24.4 對 25.6，Jain 指數 0.999，400 輪後完全平分，正是 12.5 相位圖描述的過程。第二段換成乘法增加，兩條流的比例永遠維持在初始的 1:40，Jain 指數停在約 0.5，等於一條流獨占。第三段讓兩條流的 RTT 分別是 20 ms 與 80 ms：RTT 短的流拿到約 16 倍的吞吐量，接近 RTT 比（4 倍）的平方。原因是 RTT 短的流每秒加速的次數多 4 倍，在同樣的丟包週期內長到 4 倍大的 cwnd，而吞吐量是 cwnd ÷ RTT，又多 4 倍。真實網路的丟包未必同步，比例常介於 RTT 比的一次方與平方之間；但方向很清楚：同一個瓶頸上，離 server 近的使用者佔便宜，這也是 CUBIC 改用真實時間成長的動機之一。

## 12.11 在工作上怎麼用

**情境一：遠端使用者下載慢（後端、SRE）。** 先在 server 端觀察那條連線的擁塞狀態。`ss -ti` 會列出每條 TCP 連線的 cwnd、ssthresh、RTT、重傳數與送達速率：

```bash
# 列出連到 port 443、目的地是某位學生 IP 的連線細節（示意輸出）
ss -tin 'sport = :443 and dst 198.51.100.88'
# ESTAB 0 65160 203.0.113.70:443 198.51.100.88:51544
#   cubic wscale:7,7 rto:452 rtt:251.3/2.1 mss:1448 cwnd:44 ssthresh:31
#   bytes_acked:18233344 delivery_rate:2.0Mbps busy:72000ms sndbuf_limited:69000ms
#   retrans:0/12 notsent:0
```

讀法：`rtt:251.3` 確認是長 RTT 路徑；`cwnd:44` 個封包約 64 KB，乘以 8 除以 0.25 秒剛好約 2 Mbps；最關鍵的是 `sndbuf_limited`，表示大部分時間卡在傳送 buffer，而不是網路。若看到的是 `rwnd_limited`，問題在接收端的視窗；若兩者都很小而 `retrans` 持續增加、cwnd 一直被砍，才是真的網路壅塞。這三種結果的處置完全不同：前兩者改設定，後者才考慮換演算法或走 CDN。

**情境二：檢查與調整擁塞控制演算法。** 下列設定都是 Linux 的 sysctl，修改前先在測試環境量測，並用設定管理工具保存，不要只在 production 主機上手動改：

| 設定 | 用途 | 常見值與注意事項 |
|---|---|---|
| `net.ipv4.tcp_congestion_control` | 預設演算法 | `cubic`；改 `bbr` 前確認 kernel 模組可用 |
| `net.ipv4.tcp_available_congestion_control` | 目前可用的演算法 | 唯讀，列出已載入的模組 |
| `net.core.default_qdisc` | 預設佇列規則 | `fq_codel` 或 `fq`；搭配 BBR 常用 `fq` |
| `net.ipv4.tcp_rmem`、`tcp_wmem` | 自動調整 buffer 的最小、預設、最大值 | 最大值要大於最長路徑的 BDP |
| `net.ipv4.tcp_slow_start_after_idle` | 閒置後是否重新 slow start | 預設 1；長連線、穩定路徑可考慮 0 |
| `net.ipv4.tcp_ecn` | 是否使用 ECN | 預設值依 kernel 而定，常見是「對方要求才用」 |

```bash
sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_available_congestion_control
tc -s qdisc show dev eth0          # 看 qdisc 種類、丟包與排隊統計
ip route show 10.20.0.0/16         # 路由也能針對特定網段設定 congctl、initcwnd
```

應用程式也可以逐條連線指定演算法。Python 在 Linux 上有 `socket.TCP_CONGESTION`；它只影響這條連線的送出方向：

```python
# not-runnable（只在 Linux 上可用，且指定的演算法必須已載入）
import socket
s = socket.create_connection(("api.shengsheng.example", 443))
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_CONGESTION, b"bbr")
print(s.getsockopt(socket.IPPROTO_TCP, socket.TCP_CONGESTION, 16))
```

**情境三：不要手動把 buffer 鎖小。** 故事裡的 `sndbuf=64k` 是典型錯誤。Linux 的 socket buffer 預設會自動調整（autotuning），應用程式一旦用 `SO_SNDBUF` 或 `SO_RCVBUF` 設定固定值，就會關掉這條連線的自動調整。修法是刪除那個設定，讓 kernel 依 `tcp_wmem` 的範圍自行長大，並確認最大值涵蓋最長路徑的 BDP。

**情境四：視訊卡頓但沒丟包（影音）。** 看延遲隨負載的變化：讓使用者在空閒與上傳時各 ping 一次閘道外的位址，或在 WebRTC stats 裡比較 RTT 的趨勢。RTT 隨上傳上升、丟包仍低，就是 bufferbloat。能做的事依序是：請使用者在路由器開啟 SQM／FQ-CoDel、暫停大檔同步；在應用面讓上傳程式限速；長期則靠 WebRTC 自己的延遲型頻寬估計（第 37 章）在佇列變長時主動降碼率。

**情境五：決定要不要上 HTTP/3（前端、平台）。** 用 DevTools 或 RUM 資料把使用者依網路分組。有線與穩定 Wi-Fi 的使用者，HTTP/2 與 HTTP/3 差異通常不大；行動網路、高丟包地區的使用者，才是 TCP 層 HOL 與連線遷移（第 13 章）真正發揮作用的地方。判斷依據是 p75、p95 的延遲，而不是中位數。

## 12.12 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 遠端使用者吞吐量剛好卡在某個整齊的數字（2 Mbps、4 Mbps） | 傳送或接收 buffer 被鎖小，或 window scale 被關掉 | 吞吐量 × RTT 是否約等於 64 KiB 等整數；`ss -ti` 看 `sndbuf_limited`、`rwnd_limited`；抓 SYN 看有沒有 wscale 選項 | 移除固定的 `SO_SNDBUF`／`sndbuf=`；調高 `tcp_wmem`、`tcp_rmem` 最大值；檢查中間設備是否剝掉 TCP 選項 |
| 上傳時視訊與語音延遲飆到數百毫秒，丟包卻很低 | bufferbloat：drop-tail 大佇列被 loss-based 流塞滿 | 比較空閒與負載下的 RTT；`tc -s qdisc` 看佇列長度 | 啟用 FQ-CoDel／SQM；上傳限速；把互動流量與大流量分開 |
| 長 RTT、少量丟包的路徑上速度遠低於頻寬 | loss-based 演算法在長肥管線上恢復太慢（Mathis 公式） | `ss -ti` 看 cwnd 反覆被砍、`retrans` 增加；用 Mathis 公式估算 | 確認是 CUBIC 而不是 Reno；評估 BBR；靠近使用者部署 CDN 或 edge 縮短 RTT |
| 內部服務的突發回應偶爾變慢，量測 RTT 卻很低 | 閒置後 slow start 重新開始，cwnd 回到 IW | 在突發前後讀 `ss -ti` 的 cwnd；比較 `tcp_slow_start_after_idle` | 在穩定的內部路徑關閉 slow start after idle；或改用連線池保持流量 |
| 換成 BBR 之後重傳率大增，或其他服務變慢 | 淺 buffer 路徑上 BBR v1 不理會丟包；與 CUBIC 流共存時搶走頻寬 | 比較切換前後的 `retrans`、同機器其他流量的吞吐量 | 只在特定路徑或特定服務啟用；使用較新版本；持續監控而不是全域切換 |
| HTTP/2 頁面在行動網路上整頁停頓，HTTP/1.1 反而較順 | TCP 層 HOL：單一連線的一個丟包卡住所有 stream | DevTools 看多個資源同時停在 Content Download；server 端看重傳 | 提供 HTTP/3；減少關鍵路徑上的資源數；降低單一連線上的突發 |
| 一個使用者開多條連線下載就搶走大部分頻寬 | AIMD 的公平是「每條流」而不是每個使用者 | 看同一來源 IP 的連線數與各自吞吐量 | 在應用層或 LB 限制每使用者連線數或速率 |

## 12.13 動手練習

1. **擴充 Reno 模擬**：把步驟 1 的 `BUFFER` 改成 0、24、200，觀察鋸齒的高度與「線路沒跑滿的輪數」。再加一個欄位，印出每輪的排隊封包數 max(0, cwnd − BDP)。
   答案要點：buffer 0 時 cwnd 在 12 到 24 之間擺動，一半的時間線路沒跑滿；buffer 24（1 BDP）時減半後仍 ≥ 24，線路一直滿；buffer 200 時線路一直滿，但排隊封包可達 200，換算延遲是 200 個封包的傳輸時間。

2. **手算 BDP 與 Mathis 公式**：聲聲 Live 從台北送直播回放給美西的觀眾，頻寬 200 Mbps、RTT 150 ms、MSS 1448 bytes。算出 BDP（bytes 與 MSS 數），以及丟包率 0.1% 與 0.001% 時 Reno 的理論吞吐量。
   答案要點：BDP = 200e6 ÷ 8 × 0.15 = 3.75 MB，約 2590 個 MSS；Mathis：1448 × 8 ÷ 0.15 × 1.22 ÷ √p，p = 0.001 時約 3.0 Mbps，p = 0.00001 時約 30 Mbps，都遠低於 200 Mbps。

3. **讓 HOL 模擬更真實**：修改 12.9 的 HOL 模擬程式，讓 3 個 stream 改成 2、5、10 個，並讓丟包率變成每 20 個封包隨機丟 1 個（用 `random.Random(42)` 固定種子）。計算 TCP 與 per-stream 兩種交付方式下，所有 stream 完成時間的平均值。
   驗證方法：stream 數越多，per-stream 的優勢越大，因為每次丟包只影響 1/n 的 stream；TCP 的平均完成時間則幾乎不隨 stream 數改善。

4. **用真實工具觀察 cwnd（需要 Linux）**：在一台 Linux 機器上用 `python3 -m http.server` 提供一個 200 MB 的檔案，從另一台機器以 `curl -o /dev/null` 下載，同時在 server 端每 0.5 秒執行一次 `ss -tin 'sport = :8000'`。再用 `tc qdisc add dev eth0 root netem delay 100ms loss 0.5%` 製造延遲與丟包（實驗完以 `tc qdisc del dev eth0 root` 移除），比較 cubic 與 bbr 的 cwnd、`delivery_rate` 與 `retrans`。
   驗證方法：只在自己的實驗機器上操作。加入 0.5% 丟包後，cubic 的 cwnd 會反覆被砍、吞吐量大幅下降；bbr 的 delivery_rate 通常維持得較高，但 retrans 數也較多。

5. **量測家裡的 bufferbloat**：在家裡持續 `ping` 一個穩定的外部位址（例如 ISP 的閘道），同時開始上傳一個大檔到雲端硬碟，記錄 RTT 的變化；再試試路由器的 SQM 或 QoS 選項（若有）。
   驗證方法：上傳開始幾秒內 RTT 若從數十毫秒升到數百毫秒，就是 bufferbloat；啟用 FQ-CoDel 類的 SQM 後，負載下的 RTT 應明顯下降，代價是上傳速度略低於方案上限。

6. **用 DevTools 找 TCP 層 HOL**：在 Chrome DevTools 的 Network 面板開啟 Protocol 欄位，用 Throttling 設定成慢速行動網路，載入一個走 HTTP/2 的網頁，觀察多個資源的 Waterfall。
   答案要點：DevTools 的 throttling 是在瀏覽器層模擬延遲與頻寬，不會製造真正的 TCP 丟包，所以看不到 TCP 層 HOL；要真正觀察，必須像練習 4 一樣在作業系統層用 netem 製造丟包，再比較 HTTP/2 與 HTTP/3 的瀑布圖。能說出這個差異就算完成。

## 本章重點整理

- 流量控制看 rwnd、保護接收端；擁塞控制看 cwnd、保護網路；sender 實際能送的在途資料量是 min(cwnd, rwnd)，cwnd 只存在 sender 的 kernel 裡。
- BDP = 頻寬 × RTT，是填滿一條路所需的在途資料量；吞吐量上限約為視窗 ÷ RTT，長 RTT 路徑需要的視窗遠大於 64 KiB，必須依賴 window scale 與足夠大的 socket buffer。
- slow start 從初始視窗（現今多為 10 個 MSS）開始，每個 RTT 約翻倍，直到 ssthresh 或丟包；短連線大多在 slow start 期間就結束，所以對 RTT 特別敏感。
- congestion avoidance 每個 RTT 加 1 個 MSS；3 個 duplicate ACK 觸發 fast retransmit 與 fast recovery，cwnd 約減半；RTO 逾時則 cwnd 回到 1，代價大得多。
- AIMD 讓多條 RTT 相同的流收斂到平分頻寬，但 RTT 短的流會拿到較多頻寬；公平是「每條流」而不是每個使用者。
- Mathis 公式說明 Reno 的吞吐量與 RTT 和 √丟包率成反比，長肥管線上極小的丟包率就足以讓 Reno 跑不快。
- CUBIC 以距離上次丟包的真實時間決定 cwnd，丟包時乘 0.7，在 W_max 附近形成平台，K 與 RTT 無關；它是 Linux 的預設演算法，但仍然要塞滿 buffer 才會退讓。
- bufferbloat 是大 buffer 加上 loss-based TCP 造成的長佇列，症狀是負載下延遲暴增而丟包很低；排隊延遲等於佇列 bytes 除以線路速度。
- AQM（CoDel、FQ-CoDel）依排隊時間提早丟包或標記，ECN 讓路由器不丟包也能通知壅塞，pacing 讓 sender 不會一次灌爆佇列。
- BBR 用瓶頸頻寬與最小 RTT 建模，目標是停在在途資料約等於 BDP 的點；它在長肥管線與隨機丟包路徑上表現好，但要注意淺 buffer 的重傳率與和 CUBIC 共存的公平性。
- HTTP 層 HOL 來自 HTTP/1.1 回應必須依序；TCP 層 HOL 來自 TCP 只交付連續的位元組流；HTTP/2 解掉前者，HTTP/3 透過 QUIC 每個 stream 獨立排序才解掉後者。
- 除錯時先用 `ss -ti` 分辨是 buffer 受限、接收端受限還是網路壅塞，三種原因的處置完全不同。

## 延伸問答

> [!question]- Q1. cwnd 和 rwnd 都會限制送出量，兩者有什麼本質差異？如果只看 Wireshark 的封包，能看到哪一個？
> rwnd 是接收端在每個 TCP segment 的 Window 欄位裡明確告訴對方的數字（再乘上 window scale），反映的是接收端 buffer 還剩多少空間；cwnd 則是 sender 自己依 ACK、丟包、RTT 推測出來的網路承載量，從頭到尾沒有出現在任何封包上。兩者一個是「對方明說的事實」，一個是「自己猜的估計」。
>
> 所以從封包上只能直接讀到 rwnd。cwnd 只能間接推測：在 sender 附近抓包時，觀察「已送出但尚未被確認的 bytes」（Wireshark 的 bytes in flight）在每個 RTT 的上限；若這個上限明顯小於 rwnd，就代表限制來自 cwnd 或傳送 buffer。最可靠的做法仍是在 sender 端執行 `ss -ti` 直接讀 kernel 的狀態。

> [!question]- Q2. 手算：RTT 80 ms、瓶頸 50 Mbps、MSS 1448 bytes、初始視窗 10。一個 1 MB 的回應大約要幾個 RTT 才能傳完？（忽略丟包與交握）
> 先算 BDP：50e6 ÷ 8 × 0.08 = 500,000 bytes，約 345 個 MSS。1 MB（1,000,000 bytes）約等於 691 個 MSS。slow start 時每個 RTT 依序送出 10、20、40、80、160 個，累計 310 個；第 6 個 RTT 時 cwnd 若翻倍到 320，仍小於 BDP 345，可以全部送出，累計 630 個；第 7 個 RTT 只需要再送 61 個。
>
> 所以大約需要 7 個 RTT，也就是 560 ms，遠多於「1 MB ÷ 50 Mbps = 160 ms」的頻寬估算。這個差距完全來自 slow start：整個傳輸都在試探階段，從未跑滿線路。這說明對中小型回應而言，降低 RTT（CDN、連線重用、提高初始視窗）比增加頻寬有效得多。

> [!question]- Q3. 為什麼 3 個 duplicate ACK 只把 cwnd 砍半，RTO 卻要降到 1？
> 兩者反映的網路狀態不同。duplicate ACK 是 receiver 每收到一個亂序的封包就回一個，連續三個代表「遺失點之後至少有三個封包成功到達」，網路仍在流動，ACK clock 還在運作，只是某個佇列短暫溢出。這種情況下適度退讓（減半）就足以讓佇列消化，而且可以靠持續回來的 dupACK 繼續送新資料。
>
> RTO 則表示 sender 在一整段時間內什麼回音都沒有收到：可能一整個視窗的資料或 ACK 都遺失、路徑斷了、或嚴重壅塞。sender 已經沒有可靠的 ACK clock，也不知道網路還剩多少容量，最保守的做法是回到 1 個封包重新 slow start。這也是為什麼減少 RTO 的機制（SACK、RACK-TLP、tail loss probe）對尾端延遲的影響非常大。

> [!question]- Q4. 你在 production 看到：某條連線 `ss -ti` 顯示 cwnd 很大、retrans 為 0，但吞吐量仍然很低，`rwnd_limited` 的時間佔大半。問題可能在哪裡？
> `rwnd_limited` 表示 sender 是因為接收端的視窗而停下來，跟網路壅塞無關；cwnd 大、沒有重傳也印證網路本身沒有問題。原因在接收端：可能是接收端應用程式讀得太慢（例如單執行緒處理、寫磁碟慢），buffer 滿了，視窗就縮小；也可能是接收端的 socket buffer 被固定設小、`tcp_rmem` 最大值太低，或某個中間設備剝掉了 window scale 選項，讓視窗卡在 64 KiB。
>
> 確認方式是在接收端看該連線的 Recv-Q 是否持續很高（應用程式讀太慢），以及交握時雙方的 wscale 值。前者要修應用程式的讀取效率，後者要修 buffer 設定或中間設備。這時換擁塞控制演算法完全沒有幫助，是常見的誤判。

> [!question]- Q5. 面試題：bufferbloat 是什麼？為什麼「更大的 buffer」會讓延遲變差，而不是讓網路變好？
> bufferbloat 指網路設備的 buffer 過大，loss-based 的 TCP 會一直增加 cwnd 直到丟包，而 buffer 越大，丟包越晚發生，於是佇列被長時間塞滿。所有經過這個瓶頸的封包都要排完整個佇列，延遲等於佇列 bytes ÷ 線路速度，例如 1.5 MB 的佇列在 20 Mbps 線路上就是 600 ms。
>
> buffer 的正當用途是吸收短暫的突發，大約一個 BDP 就能讓單條 Reno 流在減半後維持滿載；超過這個大小，吞吐量不會再增加，多出來的只是排隊時間，而且會讓 TCP 的壅塞訊號延遲，控制迴路反應變慢。解法不是單純縮小 buffer，而是 AQM（依排隊時間提早丟或標記，如 FQ-CoDel）、ECN，以及不以丟包為主要訊號的 sender（如 BBR、pacing）。

> [!question]- Q6. 情境判斷：平台團隊提議把所有 server 的預設擁塞控制從 CUBIC 改成 BBR，你會怎麼評估？
> 先問收益在哪：BBR 最大的好處出現在長 RTT、有隨機丟包的路徑上（例如遠端國家、行動網路的下載），對同機房或短 RTT、乾淨的路徑通常差異不大。聲聲 Live 的回放下載與直播分發可能受益，內部 RPC 不一定。其次是風險：BBR v1 在淺 buffer 路徑上可能造成高重傳率，與同一瓶頸上的 CUBIC 流共存時也可能不公平，影響同台機器或同條線路上的其他服務。
>
> 因此合理的做法是分階段：先在一部分機器或特定服務（可用 route 的 congctl 或 socket 選項逐條連線設定）啟用，量測吞吐量、p95 下載時間、重傳率、以及其他服務的表現；確認 kernel 版本與 qdisc／pacing 設定；有明確收益再擴大範圍。全域一次切換最難判斷因果，也最難回復。

> [!question]- Q7. 看封包找原因：Wireshark 顯示 HTTP/2 連線上，一個 TCP segment 遺失後，後面 120 ms 內陸續收到很多 segment，但瀏覽器的所有資源在這段時間都沒有進度。發生了什麼？
> 這是 TCP 層的 head-of-line blocking。後面的 segment 確實到了接收端的 kernel，但 TCP 必須依序交付位元組流，序號中間有洞，kernel 就只能把它們留在接收 buffer 裡（Wireshark 會把它們標為 out-of-order，並看到 receiver 回 duplicate ACK 或 SACK）。瀏覽器的 HTTP/2 程式在洞被補上之前一個 byte 都讀不到，所以所有 stream 同時停住，即使大部分 frame 和遺失的那個毫無關係。
>
> 120 ms 大約是偵測丟包加上重傳的時間（約 1 到 1.5 個 RTT）。能做的事包括：提供 HTTP/3，讓遺失只影響所屬的 stream；確認 server 支援 SACK 與 RACK，加快恢復；減少關鍵路徑上的資源數。單純開更多 HTTP/2 stream 沒有幫助，因為它們共用同一條 TCP。

> [!question]- Q8. 設計取捨：HTTP/1.1 開 6 條連線和 HTTP/2 用 1 條連線，各有什麼好壞？為什麼不乾脆讓 HTTP/2 也開 6 條？
> HTTP/1.1 的 6 條連線能平行處理 6 個請求，一個丟包只卡住其中一條，對 TCP 層 HOL 比較有韌性；在共享瓶頸上，6 條流也會拿到約 6 倍的 AIMD 份額。但代價是 6 次交握與 TLS 握手、6 條各自從初始視窗開始的 slow start、更多 server 端的連線狀態，而且每條連線上仍有 HTTP 層的 HOL。
>
> HTTP/2 用 1 條連線，只付一次交握，cwnd 能在所有資源間共用並長得更大，header 也能壓縮，對一般網路幾乎都更好；弱點是高丟包時所有 stream 一起被 TCP 層 HOL 卡住。讓 HTTP/2 開多條連線會失去共用 cwnd、優先權與壓縮的好處，並重新引入對其他使用者不公平的問題；真正的解法是把多工搬到傳輸層，也就是 QUIC 與 HTTP/3（第 13 章、第 22 章）。
