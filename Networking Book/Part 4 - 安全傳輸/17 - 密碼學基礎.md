# 第 17 章　給工程師的密碼學基礎

> [!abstract] 本章地圖
> **核心問題**：工程師不需要發明密碼學，但每天都在「使用」密碼學。hash、HMAC、加密、簽章、金鑰交換各自解決什麼問題？怎樣才算用對？
>
> **你會學到**：
> - 用機密性、完整性、真實性三個問題，替任何需求挑出正確的工具，而不是看到「安全」就想到「加密」
> - 分辨 hash 與 HMAC，說清楚 `sha256(secret + body)` 為什麼不是簽章，並用 `hmac.compare_digest` 做 constant-time 比較
> - 用 `secrets` 產生 token 與金鑰，知道 `random` 為什麼不能用在任何安全用途
> - 解釋 nonce 重用為什麼會讓串流加密整個失效，以及 AEAD（AES-GCM、ChaCha20-Poly1305）怎麼同時提供機密性與完整性
> - 用小數字手算 RSA 簽章驗證與 Diffie-Hellman，理解公鑰密碼的直覺，並知道真實參數為什麼要大很多
> - 在程式碼審查中認出常見的密碼學誤用，並寫出一個正確的 webhook 簽章驗證
>
> **前置知識**：第 1 章（聲聲 Live 的系統全貌）、第 2 章（bytes、header 與 checksum 的限制）、第 13 章（QUIC 內建 TLS 1.3 的加密）

## 17.1 故事：Rita 退回了四行程式

聲聲 Live 接上新的金流供應商 `pay.example.net`。學生付款成功後，供應商會從 `198.51.100.64/26` 這段位址，對 `api.shengsheng.example/v1/webhooks/pay` 送一個 **webhook**（對方在事件發生時主動呼叫你的 HTTP 端點，例如「訂單 A1024 付款成功」）。我們收到後把課程點數加進學生帳戶。這個端點對整個網際網路公開，任何人都能對它送 POST，所以供應商在每個請求附上一個簽章 header，讓我們確認「這個請求真的來自供應商，而且內容沒被改過」。

小晴接下這張單，一個下午就寫完了。為了「順便」改善體驗，同一個 PR 還加了兩個小功能：忘記密碼信裡的重設連結，以及付款完成後把訂單資訊「加密」放進導回網址。PR 送出去，資安工程師 Rita 在四個地方留了評論：

```text
 pay.example.net（198.51.100.64/26）
        │  POST /v1/webhooks/pay
        │  Pay-Signature: 3f9a…（供應商附上的簽章）
        ▼
 api.shengsheng.example ── Flask：webhooks.py（小晴的 PR）
        │
        ├─ ① expected = sha256(SECRET + body).hexdigest()    ◄ Rita：這不是 HMAC
        ├─ ② if expected == request.headers["Pay-Signature"] ◄ Rita：不要用 == 比秘密
        ├─ ③ token = "".join(random.choices(ALPHABET, k=22)) ◄ Rita：random 可預測
        └─ ④ blob = xor(order_info, KEY)  # 沿用舊的錄影連結程式 ◄ Rita：固定 keystream、沒有完整性
```

這四行在測試環境全部「能用」：簽章對的請求會通過、錯的會被拒絕，token 看起來亂七八糟，導回網址裡的訂單資訊也看不出原文。小晴不懂為什麼要退回。Rita 的回覆很短：「功能測試只會告訴你『正常情況下對不對』，密碼學的問題全部發生在『有人刻意亂來』的時候。① 讓人可能在不知道 secret 的情況下延伸出有效簽章，② 讓人能一個 byte 一個 byte 猜出簽章，③ 讓人能推算出別人的重設連結，④ 讓人拿自己的連結就解得開別人的連結，還能改內容。」

小晴的 mentor 阿德看了之後說，這四個錯誤幾乎是每個團隊都犯過的經典錯誤，原因是大家把密碼學當成一個「加上去就安全」的黑盒子。這一章就是要打開這個盒子到剛好夠用的深度：我們不推導數學證明，也不自己發明演算法，但要清楚每一種積木保證什麼、不保證什麼、需要什麼前提。章末的動手做會在你的電腦上寫出一個正確的 webhook 驗證端點，並逐一驗證它擋得住竄改、偽造與重放。後面的第 18 章 TLS、第 26 章密碼儲存、第 27 章 JWT、第 30 章 service 之間的簽章，都建立在本章的積木上。

## 17.2 先問對問題：機密性、完整性、真實性

小晴第一個直覺是「webhook 要加密才安全」。阿德反問：webhook 的內容是「訂單 A1024 付款 1200 元」，被別人看到會怎樣？真正可怕的是什麼？想了一下，小晴發現真正可怕的不是被看到，而是有人**偽造**一個「付款成功」的請求，讓沒付錢的帳號拿到點數。這是兩個完全不同的問題，需要的工具也不同。

密碼學在工程上主要回答三個問題。**機密性**（confidentiality）：沒有鑰匙的人看不懂內容，例如學生的聊天訊息走在咖啡廳 Wi-Fi 上不會被旁人讀到。**完整性**（integrity）：內容在路上被改過一個 bit，收方也能發現，例如金額 1200 被改成 12 會被偵測到。**真實性**（authenticity）：收方能確認訊息出自誰，例如這個 webhook 真的來自金流供應商，而不是某個攻擊者自己組的請求。另外還有一個常被一起提到的性質：**不可否認性**（non-repudiation），指第三方也能驗證「這是某人簽的」，簽的人事後賴不掉，只有數位簽章做得到。

| 你要防的事 | 需要的性質 | 對應的工具 | 聲聲 Live 的例子 |
|---|---|---|---|
| 旁人讀到內容 | 機密性 | 對稱加密（AEAD）；金鑰交換建立共享金鑰 | 瀏覽器到 CDN 的 HTTPS（第 18 章） |
| 內容被改而沒人發現 | 完整性 | MAC（例如 HMAC）、AEAD 的 tag、簽章 | 錄影下載連結裡的到期時間 |
| 有人冒充發送者 | 真實性 | 共享秘密的 MAC；或公私鑰的數位簽章 | 金流 webhook、JWT（第 27 章） |
| 發送者事後否認 | 不可否認性 | 數位簽章（只有私鑰持有者簽得出來） | 憑證、程式碼簽章 |
| 檔案在儲存或傳輸中意外損壞 | 錯誤偵測（不防惡意） | checksum、CRC、單純的 hash | 下載安裝檔後比對 SHA-256 |

這張表最重要的是最後一列和第二列的差別。第 2 章提過，IP 與 TCP 的 checksum 只防「意外」：兩個錯誤互相抵銷它就抓不到，更擋不住刻意的修改，因為攻擊者改完內容可以順手重算 checksum。單純的 hash 也一樣：攻擊者改了內容，重新算一次 SHA-256 貼上就好。要防「刻意」的修改，驗證值的計算必須牽涉到攻擊者沒有的東西，也就是**金鑰**（key）。這個觀念直接指出 Rita 第 ① 條評論的方向：小晴確實把 secret 放進了 hash，但放的方式不對，17.4 節會說明。

還有一個每年都有人搞混的觀念：**編碼不是加密**。Base64、URL encoding、hex 都只是換一種表示法，沒有金鑰，任何人都能還原。JWT 的 payload 就只是 base64url，任何拿到 token 的人都看得到內容（第 27 章）。看到「這個欄位 base64 過了所以安全」的說法，就要提出疑問。

> [!warning] 常見誤解
> 「加密了就不能被竄改」是錯的。17.6 節會實際示範：沒有完整性保護的加密，攻擊者看不懂內容，卻能精準地改掉其中幾個字。機密性和完整性要分開思考，現代的做法是用 AEAD 一次滿足兩者。

另一個貫穿全章的原則叫 **Kerckhoffs 原則**：系統的安全只能依賴金鑰保密，不能依賴「演算法沒人知道」。小晴第 ④ 條沿用的舊程式，安全性完全建立在「沒人知道我們用 XOR」上；一旦有人看過原始碼、或從輸出反推出規律，就整個失效。標準演算法反而比較安全，因為全世界的密碼學家已經公開分析了它們幾十年。

## 17.3 Hash：資料的指紋

**密碼學雜湊函數**（cryptographic hash function，常簡稱 hash）把任意長度的輸入變成固定長度的輸出，這個輸出叫**摘要**（digest）。例如 SHA-256 不論輸入是一個字還是一部 4 GB 的影片，都輸出 32 bytes。你可以把它想成資料的指紋：同一份資料永遠得到同一個指紋，資料差一點點，指紋就完全不同。

一個 hash 要能用在安全用途，必須滿足三個性質。**抗原像**（preimage resistance）：給你一個摘要，找不到任何會產生它的輸入。**抗第二原像**（second-preimage resistance）：給你一份資料，找不到另一份摘要相同的資料。**抗碰撞**（collision resistance）：找不到任意兩份摘要相同的資料。最後一個最難達成，也最先被攻破：MD5 在 2004 年、SHA-1 在 2017 年都已經有人公開做出實際的碰撞，所以兩者都不能再用在簽章、憑證這類需要抗碰撞的地方。

下面這段程式示範 hash 的幾個直覺性質：同樣的輸入得到同樣的輸出、輸入差一個字元時大約一半的位元會翻轉（**雪崩效應**，avalanche effect），以及不同演算法的輸出長度。

```python
import hashlib

body = b'{"event":"payment.succeeded","order":"A1024","amount":1200}'
tampered = body.replace(b"1200", b"1209")

d1 = hashlib.sha256(body).hexdigest()
d2 = hashlib.sha256(tampered).hexdigest()
print("原始  ", d1)
print("改一字", d2)

# 雪崩效應：只改一個字元，256 個位元裡大約一半會翻轉
diff_bits = bin(int(d1, 16) ^ int(d2, 16)).count("1")
print(f"不同的位元：{diff_bits} / 256")

# 同樣的輸入永遠得到同樣的輸出；分段 update 與一次餵入結果相同
h = hashlib.sha256()
for chunk in (body[:10], body[10:30], body[30:]):
    h.update(chunk)
assert h.hexdigest() == d1

# 不同演算法的輸出長度（bytes）
for name in ("md5", "sha1", "sha256", "sha512", "sha3_256", "blake2b"):
    print(f"{name:9} {hashlib.new(name, body).digest_size:3} bytes")
```

```text
原始   dc612f6fbc120fc7c4b55bf98c97ee64f1423749388b6986a46ae4d14d5c8455
改一字 1473a8090df7d99abbbcf5500bcd5acf5dd38fcb68c941f40705857dc0988d52
不同的位元：119 / 256
md5        16 bytes
sha1       20 bytes
sha256     32 bytes
sha512     64 bytes
sha3_256   32 bytes
blake2b    64 bytes
```

前兩行是原始 webhook body 與「把 1200 改成 1209」之後的摘要，兩者看不出任何關聯。第三行把兩個摘要做 XOR 再數 1 的個數，256 個位元裡有 119 個不同，接近一半；這就是雪崩效應，它讓你無法從「摘要差多少」推回「資料差多少」。程式中間的 assert 驗證了分段呼叫 `update()` 和一次餵入的結果相同，所以算大檔案的 hash 時可以一塊一塊讀，不必整個載入記憶體（Python 3.11 起也可以直接用 `hashlib.file_digest()`）。最後的長度表裡，MD5 的 16 bytes 與 SHA-1 的 20 bytes 在今天都太短或已被攻破，一般用途選 SHA-256 即可。

SHA-256 的內部結構叫 **Merkle–Damgård 結構**，看懂它就能理解 Rita 的第一條評論：

```text
 訊息（補齊到 64 bytes 的倍數，最後一塊含原始長度）
 ┌──────────┐ ┌──────────┐ ┌──────────┐
 │ block 1  │ │ block 2  │ │ block 3  │
 └────┬─────┘ └────┬─────┘ └────┬─────┘
      ▼            ▼            ▼
 IV ─►[壓縮 f]─►H1─►[壓縮 f]─►H2─►[壓縮 f]─►H3 ══► 摘要（32 bytes）
 （固定常數）                                       ║
                                                   ╚═ 摘要 = 最後的內部狀態
```

訊息先被補齊（padding）並切成 64 bytes 的區塊，從固定的初始值 IV 開始，每個區塊經過壓縮函數 f 更新一次內部狀態，最後的狀態直接當成摘要輸出。問題就在最後這一步：**摘要就是內部狀態本身**。拿到 `sha256(secret + body)` 的人，等於拿到了「處理完 secret 與 body 之後的狀態」，可以從這個狀態繼續餵入更多區塊，算出 `sha256(secret + body + 補齊 + 額外內容)` 的正確摘要，全程不需要知道 secret。這叫 **length extension**（長度延伸）性質，SHA-256、SHA-512、SHA-1、MD5 都有。小晴的寫法因此讓「在原本的內容後面接上東西」成為可能；即使 JSON 解析器剛好擋下這種輸入，安全性也不該寄託在這種巧合上。

SHA-3 與 BLAKE2 的內部結構不同，沒有這個性質；但正確的解法不是換 hash，而是用專門為「帶金鑰的驗證」設計的 HMAC。

| 演算法 | 輸出長度 | 狀態（2026） | 適合的用途 |
|---|---|---|---|
| MD5 | 128 bit | 碰撞已可實際產生 | 只剩非安全用途（例如快取 key）；不要用在任何安全場合 |
| SHA-1 | 160 bit | 碰撞已可實際產生 | 只為了相容舊協定（例如 Git 舊格式、WebSocket 的 Accept 計算） |
| SHA-256、SHA-512 | 256、512 bit | 安全，最廣泛支援 | 一般用途、HMAC、簽章前的摘要、檔案完整性 |
| SHA-3（SHA3-256 等） | 256 bit 等 | 安全，結構不同 | 想要與 SHA-2 不同的設計時 |
| BLAKE2b、BLAKE2s | 最多 512／256 bit | 安全，軟體上很快 | 大量資料的 hash；內建 keyed 模式 |

表中 SHA-1 那一列值得說明：WebSocket 的 `Sec-WebSocket-Accept`（第 32 章）仍然用 SHA-1，但那裡的目的只是確認「server 真的看懂了 WebSocket 握手」，不需要抗碰撞，所以不構成漏洞。判斷一個演算法能不能用，要看它被用來保證什麼。

> [!warning] 常見誤解
> 「密碼用 SHA-256 存起來就安全」是錯的。hash 被設計成很快，一張 GPU 每秒能試數十億個密碼；密碼儲存要用刻意變慢、加 salt 的專用函數（scrypt、Argon2、bcrypt），第 26 章會用 `hashlib.scrypt` 實作。

## 17.4 HMAC：有鑰匙的指紋，與 constant-time 比較

**MAC**（Message Authentication Code，訊息鑑別碼）是一個「需要金鑰才算得出來」的摘要：送方用金鑰對訊息算出一個 **tag**（標籤），收方用同一把金鑰重算，一致就代表訊息沒被改、而且出自持有金鑰的人。它同時提供完整性與真實性，但因為雙方持有同一把金鑰，收方也算得出同樣的 tag，所以沒有不可否認性。**HMAC** 是用 hash 函數建構 MAC 的標準方法，HMAC-SHA256 是 webhook、API 請求簽章、JWT 的 HS256 最常用的選擇。

HMAC 的結構刻意包了兩層：

```text
 key（不足 64 bytes 補 0；超過就先 hash）
   │
   ├─ XOR 0x36…36（ipad）─► K_in ─┐
   │                              ▼
   │                     SHA-256( K_in ‖ message ) ─► inner（32 bytes）
   │                                                    │
   └─ XOR 0x5c…5c（opad）─► K_out ─┐                    │
                                   ▼                    ▼
                          SHA-256( K_out ‖ inner ) ─► tag（32 bytes）
```

由上往下讀。金鑰先調整成 64 bytes（SHA-256 的區塊大小），再分別和兩個常數做 XOR，得到內層金鑰與外層金鑰。內層 hash 處理「金鑰＋訊息」，外層 hash 再把內層結果包起來。外層這一步就是 length extension 的解藥：攻擊者就算能延伸內層的狀態，也得不到外層的輸出，因為外層需要 K_out。HMAC 的安全性已經有完整的證明，而且即使底層 hash 的抗碰撞性受損，HMAC 的安全性也比直接用 hash 好得多。

至於 Rita 的第 ② 條評論：Python 的 `==` 比較兩個字串或 bytes 時，遇到第一個不同的字元就立刻回傳 False。這是很合理的效能最佳化，但用在比較秘密值時，**比較所花的時間洩漏了「前面有幾個 byte 猜對」**。攻擊者送出大量請求、精確量測回應時間並做統計，理論上可以逐 byte 推出正確的 tag。這類透過時間、耗電、快取行為洩漏資訊的問題叫 **side channel**（旁通道）。網路上的雜訊很大，實際利用很困難，但「很困難」不是安全保證，而防禦的成本只有一行程式：`hmac.compare_digest()`，它的比較時間只取決於長度，不取決於在哪裡開始不同。

下面的程式照 HMAC 的定義手算一次並和 `hmac` 模組比對，再用一個模仿 `==` 的函數，數出比較了幾個 byte，讓「工作量洩漏資訊」變得看得見：

```python
import hashlib
import hmac
import secrets

SECRET = bytes.fromhex("6b1f3c9a2d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8")
body = b'{"event":"payment.succeeded","order":"A1024","amount":1200}'


def hmac_by_hand(key: bytes, msg: bytes) -> bytes:
    """照 HMAC 的定義算一次，只為了看懂結構；實務一律用 hmac 模組。"""
    block = 64                                   # SHA-256 的區塊大小
    if len(key) > block:
        key = hashlib.sha256(key).digest()
    key = key.ljust(block, b"\x00")
    ipad = bytes(b ^ 0x36 for b in key)
    opad = bytes(b ^ 0x5C for b in key)
    inner = hashlib.sha256(ipad + msg).digest()
    return hashlib.sha256(opad + inner).digest()


tag = hmac.new(SECRET, body, hashlib.sha256).digest()
assert hmac_by_hand(SECRET, body) == tag
naive = hashlib.sha256(SECRET + body).digest()
print("HMAC-SHA256     ", tag.hex())
print("sha256(key+msg) ", naive.hex())
print("兩者相同？", naive == tag)


def leaky_equal(a: bytes, b: bytes) -> tuple[bool, int]:
    """模仿 == 的行為：遇到第一個不同的 byte 就停。回傳比較了幾個 byte。"""
    steps = 0
    if len(a) != len(b):
        return False, steps
    for x, y in zip(a, b):
        steps += 1
        if x != y:
            return False, steps
    return True, steps


# 猜測的簽章和正確值共用的前綴越長，比較就做得越久：工作量洩漏了「猜對幾個 byte」
for prefix in (0, 1, 8, 31):
    guess = tag[:prefix] + bytes(32 - prefix)
    if prefix < 32 and guess[prefix] == tag[prefix]:
        guess = guess[:prefix] + bytes([guess[prefix] ^ 1]) + guess[prefix + 1:]
    ok, steps = leaky_equal(tag, guess)
    print(f"前 {prefix:2} bytes 正確：比較了 {steps:2} 個 byte，結果 {ok}")

# compare_digest 的執行時間只和長度有關，不和「哪裡開始不同」有關
assert hmac.compare_digest(tag, hmac.new(SECRET, body, hashlib.sha256).digest())
assert not hmac.compare_digest(tag, secrets.token_bytes(32))
print("compare_digest：正確簽章通過、隨機簽章拒絕")
```

```text
HMAC-SHA256      f9579a02136dcdaf0b18d27c58665a3401374e3d97294149437b06f396d2aad9
sha256(key+msg)  ee04bd223a3094bac69b9aba3a9f4fa3adc98be2c400b29300e4db4ccf833ecc
兩者相同？ False
前  0 bytes 正確：比較了  1 個 byte，結果 False
前  1 bytes 正確：比較了  2 個 byte，結果 False
前  8 bytes 正確：比較了  9 個 byte，結果 False
前 31 bytes 正確：比較了 32 個 byte，結果 False
compare_digest：正確簽章通過、隨機簽章拒絕
```

第一行是正確的 HMAC-SHA256 tag，程式的 assert 確認手算結果和 `hmac.new()` 完全一致，代表你已經看懂了它的結構。第二行是小晴原本的 `sha256(key + msg)`，結果完全不同，所以這兩者不能混用，也說明了「把 secret 放進 hash」和 HMAC 不是同一回事。中間四行是重點：猜測值和正確 tag 共用的前綴越長，模仿 `==` 的函數比較的 byte 就越多。真實的 `==` 在 C 裡執行，每個 byte 只差幾奈秒，但這個「差異」本身就是資訊。最後一行改用 `compare_digest`，對正確與錯誤的值都做完整長度的比較。

實務上還有三件事要注意。第一，tag 要整個比，不要截斷到只比前幾個字元。第二，比較前先確認兩邊型別一致（都是 bytes，或都是 ASCII 字串），`compare_digest` 收到含非 ASCII 字元的 str 會拋例外。第三，被簽的內容必須是**收到的原始 bytes**：如果先把 JSON 解析再重新序列化，key 的順序或空白一改，tag 就對不上。Flask 裡要用 `request.get_data()` 取原始 body，而不是 `request.json` 之後再 `json.dumps`。

| 比較項目 | 單純 hash（SHA-256） | HMAC（共享金鑰） | 數位簽章（公私鑰，17.9 節） |
|---|---|---|---|
| 需要金鑰嗎 | 不需要，任何人都能算 | 雙方共享同一把 | 簽用私鑰，驗用公鑰 |
| 防意外損壞 | 可以 | 可以 | 可以 |
| 防刻意竄改 | 不行（改完重算即可） | 可以 | 可以 |
| 誰能驗證 | 任何人 | 只有持有金鑰的人 | 任何拿到公鑰的人 |
| 不可否認性 | 無 | 無（收方也算得出 tag） | 有 |
| 速度 | 最快 | 很快 | 慢很多（但只簽摘要） |
| 典型用途 | 檔案完整性、去重、內容定址 | webhook、API 簽章、HS256 | 憑證、RS256／ES256 JWT、passkeys |

這張表回答了很多設計問題。例如金流 webhook 用 HMAC 是合理的：只有供應商與我們需要驗證，雙方本來就會交換一把 secret。但如果一份公告要讓上萬個 client 驗證，就不能用 HMAC，因為能驗證的人都拿得到金鑰，也就都能偽造；這時要用數位簽章。

## 17.5 隨機數：秘密從哪裡來

幾乎所有密碼學都假設某些值是「攻擊者猜不到的」：金鑰、nonce、session ID、重設密碼 token、OAuth 的 state 與 PKCE verifier。這些值的品質取決於產生它們的亂數來源。電腦是確定性的機器，所謂的亂數分成兩類。**PRNG**（pseudo-random number generator，偽亂數產生器）從一個 seed 開始用公式算出一串「看起來亂」的數字，Python 的 `random` 用的 Mersenne Twister 就是，它統計性質很好，適合模擬與遊戲，但只要觀察到夠多輸出（MT19937 的內部狀態是 624 個 32 bit 整數），就能重建狀態、預測之後所有輸出。**CSPRNG**（cryptographically secure PRNG）則保證即使看過之前所有的輸出，也無法預測下一個；作業系統從硬體事件、時序抖動等來源收集 **entropy**（熵，不可預測性），再用密碼學演算法擴展成源源不絕的亂數。

在 Python 裡，CSPRNG 的入口是 `os.urandom()`，`secrets` 模組則是建在它之上、專門給安全用途的介面。規則很簡單：**跟安全有關的值一律用 `secrets`，`random` 只用在不怕被猜的地方。**

```python
import random
import secrets
import string

ALPHABET = string.ascii_letters + string.digits


def reset_token_wrong(rng: random.Random) -> str:
    # 舊程式的寫法：random 是給模擬與遊戲用的 PRNG，狀態可被重建
    return "".join(rng.choices(ALPHABET, k=22))


# 兩個「獨立」的產生器只要內部狀態相同，就吐出一模一樣的 token
server_rng = random.Random(20261002)
replica_rng = random.Random(20261002)
t1, t2 = reset_token_wrong(server_rng), reset_token_wrong(replica_rng)
print("random  ", t1, t1 == t2)

# secrets 取用作業系統的 CSPRNG（os.urandom），不能設 seed，也不能重現
for name, value in [("token_bytes(16)", secrets.token_bytes(16)),
                    ("token_hex(16)", secrets.token_hex(16)),
                    ("token_urlsafe(32)", secrets.token_urlsafe(32))]:
    print(f"{name:18} 長度 {len(value):2}")

tokens = {secrets.token_urlsafe(32) for _ in range(10_000)}
assert len(tokens) == 10_000          # 256 bit 的空間，一萬個 token 不會撞
print("一萬個 token 全部不同：", len(tokens) == 10_000)
code = f"{secrets.randbelow(10**6):06d}"   # randbelow 沒有取餘數造成的偏差
print("6 位數驗證碼長度：", len(code))
```

```text
random   ji4wR4OEqL13Va2BmxfNan True
token_bytes(16)    長度 16
token_hex(16)      長度 32
token_urlsafe(32)  長度 43
一萬個 token 全部不同： True
6 位數驗證碼長度： 6
```

第一行示範 `random` 的根本問題：兩個不同的產生器只要內部狀態相同，就產生完全相同的「token」。真實的攻擊不需要知道 seed，從公開可見的輸出（例如網站上其他用 `random` 產生的 ID）就有機會重建狀態。接下來三行是 `secrets` 的三個常用函數：`token_bytes(16)` 是 16 個原始 byte，適合當金鑰；`token_hex(16)` 是同樣 16 bytes 的 hex 表示，32 個字元；`token_urlsafe(32)` 是 32 bytes 的 base64url 表示，43 個字元，可以直接放進網址。最後兩行說明 256 bit 的空間大到連產生一萬個 token 都不會撞，以及 `randbelow` 可以安全地產生 6 位數驗證碼。

| 用途 | 正確的做法 | 錯誤的做法 | 為什麼 |
|---|---|---|---|
| 重設密碼、email 驗證連結的 token | `secrets.token_urlsafe(32)` | `random.choices`、時間戳記、遞增 ID | 必須猜不到；至少 128 bit 的熵 |
| session ID、API key | `secrets.token_urlsafe(32)`，儲存時存 hash | `uuid1()`（含時間與 MAC 位址） | `uuid4()` 在 CPython 也來自 `os.urandom`，但只有 122 bit，且語意上是識別碼不是秘密 |
| 對稱金鑰、HMAC secret | `secrets.token_bytes(32)` 或 KMS 產生 | 人想的字串、`"changeme"` | 金鑰的熵決定強度上限 |
| AES-GCM 的 nonce | 12 bytes 隨機或嚴格遞增的計數器 | 固定值、`random.getrandbits(96)` | 重複就整個失效（17.7 節） |
| 6 位數驗證碼 | `secrets.randbelow(10**6)` | `random.randint` | 可預測；也要搭配限速（第 26 章） |
| A／B 測試分組、負載模擬 | `random`（可設 seed 重現） | 不需要 `secrets` | 可重現反而是優點 |

表中「session ID 儲存時存 hash」是個值得養成的習慣：資料庫只存 `sha256(token)`，請求進來時對收到的 token 算 hash 再查表。資料庫外洩時，攻擊者拿到的 hash 無法直接拿來登入。這裡用一般 hash 就夠了，因為 token 本身有 256 bit 的熵，不像密碼那樣能被字典猜中。

> [!tip] 熵要多少才夠
> 安全用途的 token 至少要 128 bit 的熵，常見選擇是 256 bit（32 bytes）。注意「熵」不等於「字串長度」：22 個英數字元約 131 bit（每個字元 log₂62 ≈ 5.95 bit），但如果它們來自可預測的 PRNG，實際的熵只剩 seed 的大小。

## 17.6 對稱加密：同一把鑰匙鎖與開

**對稱加密**（symmetric encryption）是加密與解密用同一把金鑰的加密方式。今天最主要的對稱演算法是 **AES**（Advanced Encryption Standard），金鑰長度 128 或 256 bit，速度極快，現代 CPU 有專用指令（例如 x86 的 AES-NI），每秒能加密數 GB。另一個常見選擇是 **ChaCha20**，在沒有 AES 硬體加速的裝置（例如部分手機晶片）上比 AES 快。

AES 是一個**區塊密碼**（block cipher）：它只會做一件事，把 16 bytes 的明文區塊，用金鑰變成 16 bytes 的密文區塊。要加密任意長度的資料，必須搭配一個**操作模式**（mode of operation），而模式選錯是比演算法選錯更常見的問題。最糟的模式是 **ECB**：每個 16 bytes 區塊各自獨立加密，相同的明文區塊永遠產生相同的密文區塊，資料的「形狀」會原封不動地透出來。

```text
 ECB（不要用）：                         CTR（串流的想法）：
 明文  [ AAAA ][ AAAA ][ BBBB ]          nonce‖0   nonce‖1   nonce‖2
          │       │       │                 │         │         │
       [AES_k] [AES_k] [AES_k]           [AES_k]   [AES_k]   [AES_k]
          │       │       │                 │         │         │
 密文  [ x7Q2 ][ x7Q2 ][ m9Lp ]          keystream keystream keystream
         ▲相同明文→相同密文                  │         │         │
                                    明文 ──►(XOR)────►(XOR)────►(XOR)──► 密文
```

左邊是 ECB：前兩個區塊的明文相同，密文也相同，旁觀者不用解密就知道「這兩段內容一樣」。右邊是 **CTR 模式**（counter mode）：不直接加密明文，而是把「nonce＋計數器」加密，產生一串看起來完全隨機的 **keystream**（金鑰流），再和明文做 XOR。解密時產生同一串 keystream 再 XOR 一次就還原。這把區塊密碼變成了**串流密碼**（stream cipher），ChaCha20 本身也是同樣的形式。

CTR 有一個絕對的前提：**同一把金鑰下，nonce 永遠不能重複**。**nonce** 是「number used once」，一個只用一次的值，不需要保密，但必須唯一。如果兩則訊息用了同一個（金鑰、nonce）組合，它們就用了同一串 keystream，而 XOR 有一個要命的性質：`(P1 ⊕ K) ⊕ (P2 ⊕ K) = P1 ⊕ P2`，keystream 直接抵銷了。這正是 Rita 第 ④ 條評論的核心：舊的錄影連結程式等於每次都用同一串 keystream。

下面用一個教學用的玩具串流加密（用 SHA-256 產生 keystream，模仿 CTR 的結構）重現這個問題。再強調一次：這段程式只為了示範後果，不能用在任何真實系統。

```python
# 教學用玩具串流加密：只為了示範 nonce 重用的後果，絕對不可用於實務
import hashlib
import hmac
import secrets


def keystream(key: bytes, nonce: bytes, length: int) -> bytes:
    # 和 CTR 模式同樣的想法：用 (key, nonce, counter) 產生一串看似隨機的 bytes
    out = b""
    counter = 0
    while len(out) < length:
        out += hashlib.sha256(key + nonce + counter.to_bytes(8, "big")).digest()
        counter += 1
    return out[:length]


def xor(a: bytes, b: bytes) -> bytes:
    return bytes(x ^ y for x, y in zip(a, b))


def toy_encrypt(key: bytes, nonce: bytes, plaintext: bytes) -> bytes:
    return xor(plaintext, keystream(key, nonce, len(plaintext)))


key = secrets.token_bytes(32)
FIXED_NONCE = b"\x00" * 12                     # 舊程式的錯誤：每次都用同一個 nonce

p1 = b"lesson=8812&user=student-0457&exp=1791000000"
p2 = b"lesson=8813&user=teacher-0012&exp=1791003600"
c1 = toy_encrypt(key, FIXED_NONCE, p1)
c2 = toy_encrypt(key, FIXED_NONCE, p2)

# 1. 同一個 keystream 用了兩次：兩份密文 XOR，keystream 完全抵銷
assert xor(c1, c2) == xor(p1, p2)
print("c1 XOR c2 == p1 XOR p2：", xor(c1, c2) == xor(p1, p2))

# 2. 只要知道其中一份明文（例如自己的連結），另一份就整份現形，完全不需要 key
print("還原出的 p2：", xor(xor(c1, c2), p1).decode())

# 3. 每次換新的隨機 nonce，兩份密文的 XOR 就只是雜訊
n1, n2 = secrets.token_bytes(12), secrets.token_bytes(12)
d1, d2 = toy_encrypt(key, n1, p1), toy_encrypt(key, n2, p2)
assert xor(xor(d1, d2), p1) != p2
print("換 nonce 後同樣的手法還原得出 p2？", xor(xor(d1, d2), p1) == p2)

# 4. 串流加密只負責機密性：改密文的位元，明文同一位置跟著翻轉，解密端毫無察覺
flip = xor(b"exp=1791000000", b"exp=1799999999")
pos = p1.index(b"exp=")
forged = c1[:pos] + xor(c1[pos:], flip) + c1[pos + len(flip):]
print("被改過的密文解密：", toy_encrypt(key, FIXED_NONCE, forged).decode())

# 5. 補上完整性：對 nonce＋密文算 HMAC（encrypt-then-MAC）。真實程式請直接用 AEAD
mac_key = secrets.token_bytes(32)              # 加密與 MAC 用不同的 key
tag = hmac.new(mac_key, FIXED_NONCE + c1, "sha256").digest()
for label, ct in (("原始密文", c1), ("被改過的密文", forged)):
    ok = hmac.compare_digest(tag, hmac.new(mac_key, FIXED_NONCE + ct, "sha256").digest())
    print(f"{label}：{'通過，解密' if ok else '標籤不符，拒絕解密'}")
```

```text
c1 XOR c2 == p1 XOR p2： True
還原出的 p2： lesson=8813&user=teacher-0012&exp=1791003600
換 nonce 後同樣的手法還原得出 p2？ False
被改過的密文解密： lesson=8812&user=student-0457&exp=1799999999
原始密文：通過，解密
被改過的密文：標籤不符，拒絕解密
```

逐行看輸出。第一行驗證了 XOR 的抵銷：兩份密文 XOR 起來，恰好等於兩份明文 XOR，keystream 消失了。第二行是後果：攻擊者只要知道其中一份明文，例如自己的下載連結內容（自己是學生，當然知道自己的 lesson、user 與 exp），就能把別人的連結整份解出來，全程不需要金鑰。第三行換成每次隨機產生 nonce，同樣的手法就失效了。

第四行是另一個獨立的問題，也是很多人沒想到的：**串流加密沒有完整性**。攻擊者雖然看不懂密文，但知道 `exp=` 在第幾個 byte（格式是固定的），就能把那幾個 byte 和「舊值 XOR 新值」做 XOR，解密出來的到期時間就從 1791000000 變成 1799999999，解密端完全察覺不到。這種「看不懂但改得動」的性質叫 **malleability**（可塑性）。最後兩行補上 HMAC tag 之後，被改過的密文就被拒絕了，這個組合叫 **encrypt-then-MAC**：先加密，再對 nonce 與密文算 MAC，解密前先驗 tag。

encrypt-then-MAC 的細節很多：加密與 MAC 要用不同的金鑰、tag 要涵蓋 nonce 與所有 header、驗證失敗時不能洩漏任何「解密到哪一步失敗」的資訊。順序也很重要，先 MAC 再加密或兩者各自進行的組合，歷史上都出過問題。這些細節正是不該自己組裝的原因，現代的答案是直接使用把兩者整合好的 AEAD。

## 17.7 AEAD 與 AES-GCM：加密和防竄改一次做好

**AEAD**（Authenticated Encryption with Associated Data，帶附加資料的鑑別加密）是一種把加密與 MAC 合成單一操作的介面。加密時輸入四樣東西：金鑰、nonce、明文、**附加資料**（associated data，AAD，不需要加密但必須防竄改的資料，例如 header、版本號、使用者 ID），輸出密文與 tag。解密時，只要密文、nonce、AAD、tag 任何一個 bit 被改過，就直接回報失敗，**不會吐出任何明文**。你不需要再自己決定先加密還是先 MAC，也不會忘記驗證。

```text
 加密：  key ─┐
       nonce ─┤               ┌──────────────────────┬─────────────┐
     明文 P ──┼──► AEAD 加密 ─►│   密文 C（長度同 P）  │ tag（16 B） │
     AAD ─────┘               └──────────────────────┴─────────────┘
 （AAD 不加密、照原樣傳送，但被 tag 保護）

 實際存或傳的格式（一種常見排列）：
 ┌──────────────┬──────────────────────────┬──────────────────┐
 │ nonce 12 B   │ 密文 C                    │ tag 16 B         │
 └──────────────┴──────────────────────────┴──────────────────┘
 解密：用 key、nonce、AAD 重算 tag ─► 不符：丟出例外，什麼都不回傳
                                  └► 相符：才輸出明文 P
```

上半部是 AEAD 的介面：四個輸入、兩個輸出，AAD 本身不加密也不出現在密文裡，而是和密文一起被 tag 綁住。下半部是一種常見的儲存格式：nonce 不是秘密，直接放在密文前面一起存，解密時讀出來即可；tag 接在最後。解密的流程是「先驗 tag、驗過才解密」，所以應用程式拿不到被竄改的明文。

**AES-GCM**（Galois/Counter Mode）是最普及的 AEAD：加密部分就是 17.6 節的 CTR 模式，tag 部分用一種在有限體上的乘法運算（GHASH）快速計算。它的 nonce 標準長度是 12 bytes（96 bit），tag 16 bytes。另一個主流 AEAD 是 **ChaCha20-Poly1305**，用 ChaCha20 加密、Poly1305 算 tag。TLS 1.3 只允許 AEAD 加密記錄，最常見的就是 `TLS_AES_128_GCM_SHA256`、`TLS_AES_256_GCM_SHA384` 與 `TLS_CHACHA20_POLY1305_SHA256` 三種（第 18 章）。

AES-GCM 對 nonce 重用的反應比玩具例子更嚴重。重用一次，除了洩漏兩份明文的 XOR 之外，攻擊者還有機會推出 GHASH 用的內部鑑別金鑰，之後就能對這把金鑰偽造任意訊息的有效 tag，也就是機密性與完整性同時崩潰。所以 nonce 的產生策略是設計的一部分：

| nonce 策略 | 做法 | 優點 | 限制與風險 |
|---|---|---|---|
| 隨機 | 每次 `os.urandom(12)` | 簡單、不需要保存狀態、多台機器可同時加密 | 生日問題：同一把金鑰的加密次數要遠低於 2³²（NIST 建議的上限），量大就要定期換金鑰 |
| 計數器 | 每則訊息遞增，存在持久的狀態中 | 保證不重複，次數上限接近 2⁹⁶ | 重開機、還原備份、多個 process 共用金鑰時可能重複，要非常小心 |
| 協定推導 | 由協定的序號算出（TLS 1.3：靜態 IV XOR 記錄序號） | 不用在網路上傳 nonce | 只適合由協定完整掌控狀態的場合 |
| 抗誤用的 AEAD | AES-GCM-SIV 等 | nonce 意外重用時只洩漏「兩則訊息相同」 | 函式庫支援較少、稍慢 |

一般的應用程式（加密資料庫欄位、加密要放進網址的資料）選隨機 12 bytes nonce，並規劃金鑰輪替就足夠了。TLS 那一列是協定設計的範例：雙方在交握時各自導出一個 IV，第 N 筆記錄的 nonce 是 IV 與 N 的 XOR，序號只會遞增，所以永遠不會重複，也不必浪費頻寬傳 nonce。

Python 標準函式庫**沒有** AES。真實程式通常用 `cryptography` 套件，介面如下（此段需要安裝第三方套件，checker 不會執行）：

```python
# not-runnable
import os

from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)   # 實務上從 KMS 或 secrets manager 取得，不寫在程式裡
aesgcm = AESGCM(key)

order_info = b'{"order":"A1024","lesson":8812,"exp":1791000000}'
aad = b"redirect-v1|user=student-0457"          # 不加密但要綁定：版本與這份資料屬於誰
nonce = os.urandom(12)                         # 每次加密都產生新的 nonce
ciphertext = aesgcm.encrypt(nonce, order_info, aad)   # 回傳值 = 密文 + 16 bytes tag
blob = nonce + ciphertext                      # nonce 不是秘密，和密文放在一起

try:
    plain = aesgcm.decrypt(blob[:12], blob[12:], aad)
except InvalidTag:
    plain = None                               # 任何竄改、錯誤的 AAD 或金鑰都會走到這裡
```

這段程式對應 Rita 第 ④ 條評論的修正。`encrypt()` 回傳的 bytes 已經把 tag 接在密文後面，所以只要把 nonce 放在最前面就是一個完整的 blob，再用 base64url 編碼放進網址。AAD 綁定了「這份資料屬於 student-0457」，就算有人把自己的 blob 貼到別人的工作階段，tag 也驗不過。解密失敗一律只得到 `InvalidTag`，不要把失敗原因細分回傳給 client。

如果需求只是「加密一段資料、之後自己解開」，`cryptography` 還提供更高階的 **Fernet**（`Fernet.generate_key()`、`Fernet(key).encrypt(data)`、`decrypt(token, ttl=...)`），內部用 AES-128-CBC 加 HMAC-SHA256，自帶時間戳記，連 nonce 都不用管。能選高階介面就選高階介面，這是「不要自己發明密碼學」的第一層含意。更進一步，如果這份資料其實不需要保密，只需要防竄改（例如導回網址裡的訂單號碼），那用 HMAC 簽章就夠了，不必加密。

> [!note] 2026 現況
> 截至 2026 年 10 月，`cryptography` 是 Python 生態系的主流密碼學套件，AEAD 介面（`AESGCM`、`ChaCha20Poly1305`）穩定多年。Python 標準函式庫仍然只提供 hash、HMAC、`secrets` 與 `ssl`，沒有通用的對稱加密 API。實際可用的演算法依安裝的版本與底層 OpenSSL 而定，部署前以 `pip show cryptography` 確認版本。

## 17.8 非對稱密碼：RSA 與 ECC

對稱加密有一個根本難題：雙方要先有同一把金鑰。聲聲 Live 有上百萬個學生，不可能事先寄給每個人一把金鑰；就算可以，n 個人兩兩之間各要一把，就需要 n(n−1)/2 把。**非對稱密碼**（asymmetric cryptography，又稱公鑰密碼）用一對數學上相關的金鑰解決這個問題：**公鑰**（public key）可以公開給全世界，**私鑰**（private key）只有擁有者知道。用私鑰簽的東西，任何人都能用公鑰驗證；用公鑰加密的東西，只有私鑰能解開。它的安全建立在某種「正向容易、反向極難」的數學問題上。

**RSA** 是最經典的公鑰演算法，安全性建立在「兩個大質數相乘很容易，把乘積分解回質數極難」。產生金鑰的步驟可以用小數字手算一次：

```text
 ① 選兩個質數            p = 61, q = 53                         （保密）
 ② 公開模數              n = p × q = 3233                       （公開）
 ③ φ(n) = (p−1)(q−1)     = 60 × 52 = 3120                       （保密）
 ④ 選公開指數 e，和 φ 互質  e = 17                                （公開）
 ⑤ 求私密指數 d：e·d ≡ 1 (mod 3120)
      擴展歐幾里得：3120 = 183·17 + 9
                    17 = 1·9 + 8
                     9 = 1·8 + 1
      倒推：1 = 9 − 8 = 2·9 − 17 = 2·3120 − 367·17
      所以 d ≡ −367 ≡ 2753 (mod 3120)                           （保密）
 公鑰 (n, e) = (3233, 17)       私鑰 d = 2753
```

第 ① 到 ③ 步建立模數：n 公開，但 p、q 與 φ(n) 必須保密，因為知道 φ(n) 就能從 e 算出 d。第 ④ 步選公開指數，真實世界幾乎都用 65537。第 ⑤ 步是唯一需要動腦的地方：用擴展歐幾里得演算法找出 e 在模 φ(n) 下的反元素。倒推那一行的意思是「−367 個 17 加上 2 個 3120 等於 1」，所以 −367 就是 17 的反元素，加上 3120 變成正數 2753。整個安全性的關鍵是：攻擊者只看到 n = 3233，要算出 d 必須先把 3233 分解成 61 × 53。這對 3233 是瞬間的事，但對 2048 bit 的 n，目前已知的方法都做不到。

**簽章**的數學很短：對訊息 m 計算 s = m^d mod n，只有知道 d 的人算得出來；驗證時計算 s^e mod n，等於 m 就通過。以 m = 65 為例，程式會算出 s = 588。驗證 588^17 mod 3233 可以用「反覆平方」手算：588² ≡ 3046、588⁴ ≡ 2639、588⁸ ≡ 439、588¹⁶ ≡ 1974（每一步都 mod 3233），因為 17 = 16 + 1，所以 588^17 ≡ 1974 × 588 = 1,160,712 ≡ 65。結果等於 m，簽章成立。

```python
# 教學用「課本 RSA」：小質數、沒有 padding，只為了看懂數學，絕對不可用於實務
import hashlib

p, q = 61, 53
n = p * q                    # 3233，公開
phi = (p - 1) * (q - 1)      # 3120，必須保密（知道它就能算出 d）
e = 17                       # 公開指數，要和 phi 互質
d = pow(e, -1, phi)          # 私密指數：e*d ≡ 1 (mod phi)
print(f"n={n} phi={phi} e={e} d={d}  檢查 e*d mod phi = {e * d % phi}")

# 手算可驗證的小例子：m = 65
m = 65
s = pow(m, d, n)             # 簽章：只有持有 d 的人算得出來
print(f"簽 m={m}：s = {m}^{d} mod {n} = {s}")
print(f"驗 s：s^{e} mod {n} = {pow(s, e, n)}")
assert pow(s, e, n) == m


def h(msg: bytes) -> int:
    # 先 hash 再簽：訊息多長都只簽固定大小的摘要（這裡為了配合小 n 才取餘數）
    return int.from_bytes(hashlib.sha256(msg).digest(), "big") % n


def sign(msg: bytes) -> int:
    return pow(h(msg), d, n)


def verify(msg: bytes, sig: int) -> bool:
    return pow(sig, e, n) == h(msg)


notice = b"2026-10-02 maintenance 02:00-03:00"
sig = sign(notice)
print("公告的簽章：", sig, "驗證：", verify(notice, sig))
print("改過的公告：", verify(b"2026-10-02 maintenance 02:00-09:00", sig))

# 為什麼真實的 RSA 至少 2048 bit：摘要只剩 n 種可能時，換個訊息很快就撞到同一個值
target = h(notice)
tries = next(i for i in range(1, 100_000) if h(b"fake notice %d" % i) == target)
print(f"第 {tries} 個假訊息就和公告共用同一個簽章")
assert verify(b"fake notice %d" % tries, sig)
```

```text
n=3233 phi=3120 e=17 d=2753  檢查 e*d mod phi = 1
簽 m=65：s = 65^2753 mod 3233 = 588
驗 s：s^17 mod 3233 = 65
公告的簽章： 2853 驗證： True
改過的公告： False
第 764 個假訊息就和公告共用同一個簽章
```

第一行確認了手算的金鑰：d = 2753，e × d mod φ = 1。第二、三行是 m = 65 的簽與驗，和上面手算的 588 與 65 一致。接著程式改成「先 hash 再簽」：真實的簽章從不直接對訊息做運算，而是對訊息的摘要簽章，這樣訊息多長都只要做一次固定大小的運算。改過一個字的公告驗證失敗，代表簽章確實綁定了內容。

最後一行是這個玩具最重要的教訓：因為 n 只有 3233，摘要取餘數後只剩 3233 種可能，隨便產生假訊息，第 764 個就和公告的摘要撞在一起，同一個簽章對它也「有效」。真實的 RSA 至少用 2048 bit 的 n，並且搭配嚴格定義的 padding：簽章用 **RSA-PSS**（或舊有的 PKCS#1 v1.5），加密用 **RSA-OAEP**。沒有 padding 的「課本 RSA」有許多數學弱點，這也是為什麼本節的程式只能當作理解直覺的工具。

**ECC**（elliptic curve cryptography，橢圓曲線密碼）是另一大類公鑰密碼。它的「單向問題」是：在一條特定曲線上，給你一個起點 G 和整數 k，算出 k·G（把 G 自己加 k 次，用類似反覆平方的方法可以很快算完）很容易；但只給你 G 與 k·G，要反推出 k 極難。它最大的優點是金鑰短很多：

| 安全強度（bit） | 對稱金鑰 | RSA／DH 模數 | ECC 曲線大小 | 常見代表 |
|---|---|---|---|---|
| 112 | 3DES（已淘汰） | 2048 bit | 224 bit | RSA-2048：目前仍可接受的下限 |
| 128 | AES-128 | 3072 bit | 256 bit | P-256、X25519、Ed25519 |
| 192 | AES-192 | 7680 bit | 384 bit | P-384 |
| 256 | AES-256 | 15360 bit | 512 bit 以上 | P-521 |

這張表依 NIST 金鑰管理指引的對照整理。讀法是「同一列的東西，被暴力破解的難度大致相同」。128 bit 的安全強度，用 RSA 需要 3072 bit 的模數，用 ECC 只要 256 bit 的曲線。金鑰小就代表簽章小、運算快、封包小：Ed25519 的公鑰 32 bytes、簽章 64 bytes；RSA-2048 的簽章就要 256 bytes。這也是 TLS 憑證、SSH 金鑰、passkeys 逐漸轉向 ECC 的原因。

實務上會遇到的曲線名稱只有幾個：**P-256**（又叫 secp256r1，ECDSA 與 TLS 最廣泛支援）、**Curve25519**（用於金鑰交換時叫 **X25519**，用於簽章時是 **Ed25519**）。你不需要懂曲線的數學，但要知道一個實作上的陷阱：ECDSA 簽章每次需要一個秘密的隨機數，這個隨機數一旦重複或可預測，私鑰就能被算出來，歷史上有遊戲主機的程式碼簽章金鑰因此外洩。防禦方式是使用成熟的函式庫（它們會用確定性的方法導出這個值，或在亂數之外再混入私鑰與訊息，避免依賴單一亂數來源），或直接選 Ed25519，它的設計本身就不依賴每次簽章的亂數品質。

## 17.9 數位簽章：任何人都能驗證的真實性

**數位簽章**（digital signature）讓「一方簽、任何人驗」成為可能：簽的人用私鑰，驗的人只需要公鑰。和 HMAC 最大的差別是驗證者沒有能力偽造，所以一把公鑰可以安心地發給上百萬個 client。

```text
 簽章方（持有私鑰）                         驗證方（只有公鑰）
 ┌────────────────┐                         ┌──────────────────────────┐
 │ 訊息 M          │──── 訊息 M ────────────►│ 訊息 M                    │
 │   │ SHA-256     │                         │   │ SHA-256              │
 │ 摘要 h          │                         │ 摘要 h'                  │
 │   │             │                         │   │                      │
 │ Sign(私鑰, h)   │──── 簽章 S ────────────►│ Verify(公鑰, h', S)       │
 └────────────────┘                         └───┬──────────────────────┘
                                                ├─ 通過：M 未被改，且出自私鑰持有者
                                                └─ 失敗：丟棄 M
```

流程從左上開始：簽章方先算訊息的摘要，再用私鑰對摘要簽章，把訊息與簽章一起送出。驗證方對收到的訊息重算摘要，再用公鑰檢查簽章是否對應這個摘要。整個流程只保證兩件事：訊息沒被改過，以及簽章出自私鑰的持有者。它**不**保證機密性，訊息本身是明文傳送；也**不**保證「私鑰持有者就是你以為的那個人」。

最後一點是公鑰密碼真正的難題：你拿到一把公鑰，怎麼知道它真的屬於 `api.shengsheng.example`，而不是中間某個攻擊者塞給你的？答案是讓一個你已經信任的第三方，對「這把公鑰屬於這個名字」簽章，這份文件就是**憑證**（certificate），簽章的第三方就是 **CA**（Certificate Authority，憑證頒發機構）。瀏覽器內建一份信任的 CA 公鑰清單，沿著憑證鏈一路驗證簽章，這是第 18 章的主題。

數位簽章在本書後面會反覆出現：TLS 伺服器在交握中用私鑰簽章，證明自己持有憑證對應的私鑰（第 18 章）；JWT 的 RS256 與 ES256 讓多個服務只靠公鑰就能驗證登入服務簽發的 token（第 27 章）；passkeys 讓使用者的裝置用私鑰簽伺服器給的 challenge，伺服器只存公鑰，資料庫外洩也不會洩漏可以登入的秘密（第 29 章）。

## 17.10 金鑰交換：Diffie-Hellman

公鑰密碼解決了「驗證身分」，但大量資料的加密還是要靠快得多的對稱加密，而對稱加密需要雙方共享一把金鑰。**Diffie-Hellman 金鑰交換**（DH）讓兩個從未見過面的人，在一條**所有內容都被偷聽**的通道上，算出只有雙方知道的共享秘密。

常見的比喻是調顏料：雙方先公開約定一種共同的底色，各自加入一種只有自己知道的秘密顏色，把混好的顏色公開交換，再各自加入自己的秘密顏色。兩邊最後得到同一種顏色，而偷聽者只看到底色和兩種混合色，在不知道秘密顏色的情況下調不出最終的顏色，因為「把顏料分離」很難。數學上，「混色」就是模指數運算：

```text
 公開參數：質數 p = 23、生成元 g = 5（雙方與偷聽者都知道）

 小晴的瀏覽器                                 伺服器
 私下選 a = 6                                 私下選 b = 15
 A = 5^6 mod 23 = 8                           B = 5^15 mod 23 = 19
   │───────────────── A = 8 ─────────────────────►│
   │◄──────────────── B = 19 ──────────────────────│
 K = B^a = 19^6 mod 23 = 2                    K = A^b = 8^15 mod 23 = 2
   │                                              │
   └──── 雙方得到同一個 K = 2，它從未出現在線路上 ─────┘

 偷聽者看到：p = 23、g = 5、A = 8、B = 19
 要算 K 必須從 A 反推 a（離散對數問題）：小數字很簡單，2048 bit 的 p 做不到
```

逐步驗算。瀏覽器算 5⁶ = 15625，15625 = 679 × 23 + 8，所以 A = 8；伺服器同樣算出 B = 19。交換之後，瀏覽器算 19⁶ mod 23，伺服器算 8¹⁵ mod 23，兩者都等於 (5^(6×15)) mod 23，結果都是 2。關鍵在於指數的交換律：(g^b)^a = (g^a)^b = g^(ab)。偷聽者知道 g^a 與 g^b，但「從 g^a 求 a」叫**離散對數問題**，在夠大的參數下沒有已知的有效解法。

```python
# 教學用 Diffie-Hellman：p=23 這種小數字幾秒就能暴力破解，絕對不可用於實務
import hashlib
import hmac

p, g = 23, 5                      # 公開參數：質數 p 與生成元 g

a = 6                             # 小晴的瀏覽器私下選的數，從不送出
b = 15                            # 伺服器私下選的數，從不送出
A = pow(g, a, p)                  # 公開送出
B = pow(g, b, p)                  # 公開送出
print(f"公開：p={p} g={g} A=g^a mod p={A} B=g^b mod p={B}")

k_client = pow(B, a, p)           # (g^b)^a
k_server = pow(A, b, p)           # (g^a)^b
print(f"client 算 B^a mod p = {k_client}，server 算 A^b mod p = {k_server}")
assert k_client == k_server

# 偷聽者只看到 p、g、A、B。小數字下可以暴力試出 a，這正是真實參數要很大的原因
recovered = next(x for x in range(1, p) if pow(g, x, p) == A)
print(f"p 太小：偷聽者試到 x={recovered} 就滿足 g^x mod p = A")

# g=5 會走遍 1..22 的每一個值，所以共享值有 22 種可能
print("g 產生的子群大小：", len({pow(g, x, p) for x in range(1, p)}))


def hkdf_sha256(ikm: bytes, salt: bytes, info: bytes, length: int) -> bytes:
    """HKDF（RFC 5869）：extract 把不均勻的共享值濃縮成 PRK，expand 依用途展開成金鑰。"""
    prk = hmac.new(salt or bytes(32), ikm, hashlib.sha256).digest()
    okm, block, i = b"", b"", 1
    while len(okm) < length:
        block = hmac.new(prk, block + info + bytes([i]), hashlib.sha256).digest()
        okm += block
        i += 1
    return okm[:length]


# 先用 RFC 5869 的第一組測試向量確認實作正確
okm = hkdf_sha256(bytes([0x0B] * 22), bytes(range(13)), bytes(range(0xF0, 0xFA)), 42)
assert okm.hex().startswith("3cb25f25faacd57a90434f64d0362f2a")
print("HKDF 測試向量：通過")

# 同一個共享秘密，依用途（info）分出互不相關的金鑰
shared = k_client.to_bytes(32, "big")
k_c2s = hkdf_sha256(shared, b"", b"client to server", 16)
k_s2c = hkdf_sha256(shared, b"", b"server to client", 16)
print("c→s key", k_c2s.hex())
print("s→c key", k_s2c.hex())
assert k_c2s != k_s2c
```

```text
公開：p=23 g=5 A=g^a mod p=8 B=g^b mod p=19
client 算 B^a mod p = 2，server 算 A^b mod p = 2
p 太小：偷聽者試到 x=6 就滿足 g^x mod p = A
g 產生的子群大小： 22
HKDF 測試向量：通過
c→s key 36c14a4648de8114fe5572462c4d876f
s→c key 4678ad511de839244c5b040129efd939
```

前兩行重現了手算：A = 8、B = 19，雙方各自算出的共享值都是 2。第三行刻意說明玩具參數的弱點：p 只有 23，偷聽者從 1 試到 22 就能找出 a = 6。第四行顯示 g = 5 會走遍 1 到 22 的每一個值，所以共享值的可能性也只有 22 種；真實系統用 2048 bit 以上的質數或 X25519 這類橢圓曲線，讓搜尋空間大到不可能。

程式後半段處理一個常被忽略的步驟：DH 算出來的共享值**不能直接當金鑰用**。它的分布不夠均勻，而且一次交換通常要產生好幾把用途不同的金鑰（兩個方向各一把加密金鑰、各一個 IV）。標準做法是用 **KDF**（key derivation function，金鑰衍生函數）處理，最常用的是基於 HMAC 的 **HKDF**：extract 步驟把共享值濃縮成一把均勻的偽亂數金鑰，expand 步驟再依「用途標籤」（info）展開成任意多把互不相關的金鑰。程式先用 RFC 5869 的測試向量確認實作正確，再從同一個共享秘密分出兩個方向的金鑰。TLS 1.3 的整個金鑰排程（key schedule）就是一連串的 HKDF。

DH 本身有一個致命的盲點：**它不驗證對方是誰**。如果攻擊者站在中間，對瀏覽器假裝是伺服器、對伺服器假裝是瀏覽器，就能和兩邊各做一次 DH，得到兩把不同的共享金鑰，然後在中間解密、查看、再加密轉送，兩端都毫無察覺。這叫**中間人攻擊**（man-in-the-middle，MITM）。

```text
 瀏覽器               攻擊者（在中間）                  伺服器
   │── A ──────────────►│                                 │
   │                    │── A' ──────────────────────────►│
   │                    │◄─ B ─────────────────────────────│
   │◄─ B' ──────────────│                                 │
 K1 = 和攻擊者共享     K1、K2 都在攻擊者手上            K2 = 和攻擊者共享
 防禦：伺服器對「整個交握內容（含 B）」用憑證的私鑰簽章；瀏覽器驗證簽章與憑證鏈
       攻擊者沒有伺服器的私鑰，簽不出對 B' 有效的簽章 ─► 交握失敗
```

這張圖說明了為什麼 TLS 同時需要金鑰交換與數位簽章。攻擊者把雙方的公開值換成自己的 A' 與 B'，DH 的數學完全正常地運作，只是兩條連線的「另一端」都是攻擊者。防禦方法是讓伺服器對交握內容簽章：瀏覽器收到 B' 時，會檢查伺服器憑證的私鑰有沒有對這份交握內容簽章，攻擊者沒有那把私鑰，偽造不出來。DH 提供「只有雙方知道的金鑰」，簽章提供「另一方確實是對的人」，兩者缺一不可。

現代 TLS 每次連線都用一組**新產生、用完即丟**的 DH 私密值，稱為 **ephemeral DH**（ECDHE 是它的橢圓曲線版本）。好處是**前向保密**（forward secrecy）：就算伺服器的長期私鑰在多年後外洩，攻擊者也解不開過去錄下的流量，因為每次連線的共享秘密只存在於當時的記憶體中，從未用長期私鑰加密傳送。TLS 1.2 及更早版本允許的「client 用伺服器的 RSA 公鑰加密一個隨機秘密再送出」沒有這個性質，TLS 1.3 已經移除它。

> [!note] 2026 現況
> 依 2026 年 10 月查證：量子電腦若成熟，可以有效解開 RSA、DH 與 ECC 所依賴的數學問題；對稱加密與 hash 則只需要加長金鑰與輸出。因此業界優先處理「金鑰交換」，防範「現在先錄下、未來再解密」（harvest now, decrypt later）。NIST 已發布後量子標準 ML-KEM（FIPS 203，金鑰封裝）與 ML-DSA（FIPS 204，簽章）。TLS 1.3 的混合金鑰交換 `X25519MLKEM768`（同時做 X25519 與 ML-KEM-768，兩者都破解才會失守）已由 RFC 10024（2026-08）定義，主流瀏覽器與 OpenSSL 3.5 起已預設支援。它的 key share 比 X25519 大很多（client 約 1.2 KB），可能讓 ClientHello 跨越多個封包。後量子的憑證簽章在 WebPKI 尚未普及。

## 17.11 把積木組起來：不要自己發明密碼學

到這裡，所有積木都上場了。把它們放進一次 HTTPS 連線，就能看出每一種積木負責什麼，以及它們如何彼此依賴：

```text
 TLS 1.3 連線中用到的積木（細節見第 18 章）

 ① 隨機數（CSPRNG） ── client／server random、ephemeral 私密值
        │
 ② 金鑰交換（ECDHE：X25519 或 X25519MLKEM768） ── 雙方算出共享秘密
        │
 ③ hash ＋ HKDF ── 對交握訊息做 transcript hash；從共享秘密導出各方向的金鑰與 IV
        │
 ④ 數位簽章（憑證的私鑰：ECDSA、RSA-PSS、Ed25519） ── 伺服器簽 transcript，擋下 MITM
        │
 ⑤ HMAC（Finished 訊息） ── 雙方確認看到的交握內容完全相同
        │
 ⑥ AEAD（AES-GCM 或 ChaCha20-Poly1305） ── 之後每一筆應用資料的機密性與完整性
          nonce = IV XOR 記錄序號，永不重複
```

從上往下讀，每一步都用到前一步的結果。① 的亂數品質不好，② 的私密值就可被猜中；② 的共享值經過 ③ 的 HKDF 才變成真正的金鑰；④ 的簽章涵蓋交握的 transcript hash，所以中間人換掉任何一個公開值都會被發現；⑤ 再用 HMAC 確認雙方的交握紀錄一致；最後 ⑥ 用 AEAD 保護所有應用資料。這也說明了「安全」是整條鏈的性質，任何一環用錯，例如 nonce 重複或簽章沒驗，整條鏈就斷了。

「**不要自己發明密碼學**」（Don't roll your own crypto）在這個脈絡下有三層意思。第一層，不要自己設計演算法：自創的 XOR、「把字串反轉再 base64」都不是加密。第二層，不要自己實作標準演算法：本章的 HMAC 與 HKDF 手算版是為了理解結構，正式程式用 `hmac` 模組與 `cryptography` 的實作，它們處理了 side channel、邊界條件與各種測試向量。第三層最常被忽略：**不要自己組裝協定**。即使每塊積木都是標準的，自己決定「先加密還是先 MAC」「nonce 怎麼產生」「金鑰怎麼交換」，仍然很容易出錯。能用 TLS 就用 TLS，能用 AEAD 就不要自己組 encrypt-then-MAC，能用 Fernet 或成熟的 JWT 函式庫就不要自己拼。

| 需求 | 建議的選擇（2026） | 避免 |
|---|---|---|
| 傳輸中的資料 | TLS 1.3（或 1.2 搭配 AEAD 套件） | 自己設計的加密通道 |
| 加密一段資料、之後自己解 | AES-256-GCM 或 ChaCha20-Poly1305（隨機 nonce）；或 Fernet | AES-ECB、AES-CBC 沒有 MAC、自製 XOR |
| 只要防竄改、不需保密 | HMAC-SHA256，金鑰 32 bytes | `sha256(secret + data)`、CRC、MD5 |
| 一方簽、多方驗 | Ed25519 或 ECDSA P-256；RSA-PSS 2048 bit 以上 | 課本 RSA、RSA 1024 bit |
| 雙方建立共享金鑰 | X25519（ECDHE），可加上 ML-KEM 混合；搭配 HKDF | 靜態 RSA 金鑰傳輸、直接用 DH 共享值當金鑰 |
| token、金鑰、nonce | `secrets`／`os.urandom` | `random`、時間戳記、遞增 ID |
| 密碼儲存 | Argon2id、scrypt、bcrypt（第 26 章） | SHA-256、MD5，即使加 salt |
| 比較秘密值 | `hmac.compare_digest` | `==` |

這張表可以當成程式碼審查的對照表：看到「避免」欄的東西，就是一條該留的評論。注意每一列的建議都是「現成的、整合好的方案」，而不是「挑一個好演算法自己組」。

最後一個常被低估的部分是**金鑰管理**。演算法再好，金鑰寫死在 Git 裡、所有環境共用同一把、從來沒換過，安全性就只剩「沒人看過我們的 repo」。基本原則是：金鑰放在 secrets manager 或 KMS（Key Management Service，雲端的金鑰管理服務），程式啟動時讀取；每把金鑰有一個 **key ID**，訊息或密文中帶著它，這樣輪替時新舊金鑰可以並存一段時間；production 與 staging 用不同的金鑰。動手做的 webhook 驗證就會示範新舊兩把 secret 並存的輪替方式，第 30 章會再深入 secrets 管理。

## 17.12 動手做：用標準函式庫驗證金流 webhook

現在把 Rita 的四條評論中與 webhook 相關的兩條修好，並補上真實系統需要的另外兩件事：**重放防護**與**金鑰輪替**。供應商的簽章 header 格式如下（這是本書的範例格式，真實供應商各有自己的格式，但結構大同小異）：

```text
 Pay-Signature: t=1791000000,v1=5b0c…（64 個 hex 字元）
                │              │
                │              └─ HMAC-SHA256( secret, "1791000000" ‖ "." ‖ 原始 body ) 的 hex
                └─ 供應商送出時的 Unix 時間（秒）

 驗證流程：
 解析 header ─失敗─► 400
     │
 |現在 − t| ≤ 300 秒？ ─否─► 401（過期：可能是被錄下來的重放）
     │是
 對每一把有效的 secret（k2 目前、k1 輪替中）重算 tag
     │ compare_digest 全部不符 ─► 401
     │有一把相符
 event id 處理過了？ ─是─► 200（冪等：告訴供應商不用再送，但不重複加點數）
     │否
 記錄 event id、加點數 ─► 200
```

把 timestamp 放進被簽的內容，是重放防護的關鍵：攻擊者如果錄下一個合法請求，想在一小時後重送，必須把 t 改成新的時間，但改了 t 就得重算 tag，而攻擊者沒有 secret。時間窗口內的重送則由 event id 去重處理。去重回 200 而不是錯誤碼，是因為供應商在網路逾時時本來就會重送同一個事件，回錯誤會讓它一直重試。

下面的程式在 127.0.0.1 上用 port 0 啟動一個 `http.server`，模擬供應商送出七種請求。時鐘用一個可以撥動的模擬值，所以「一小時後」不需要真的等。

```python
import hashlib
import hmac
import http.client
import json
import secrets
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

TOLERANCE = 300                                   # 允許的時鐘差與傳遞延遲（秒）
NOW = [1_791_000_000]                             # 模擬時鐘，測試時可以撥動
SECRETS = {"k2": secrets.token_bytes(32),         # 目前的 key
           "k1": secrets.token_bytes(32)}         # 輪替期間仍接受的舊 key
seen_events: set[str] = set()


def sign(secret: bytes, ts: int, body: bytes) -> str:
    # timestamp 放進被簽的內容，攻擊者改不了它；"." 分隔避免「1791000000」+「{」拼接歧義
    mac = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return f"t={ts},v1={mac}"


def verify(header: str, body: bytes) -> tuple[int, str]:
    try:
        fields = dict(part.split("=", 1) for part in header.split(","))
        ts, given = int(fields["t"]), fields["v1"]
    except (ValueError, KeyError):
        return 400, "malformed signature header"
    if abs(NOW[0] - ts) > TOLERANCE:              # 先擋過期，避免舊請求被重放
        return 401, "timestamp outside tolerance"
    for kid, secret in SECRETS.items():           # 每把 key 都算，用 constant-time 比較
        expected = sign(secret, ts, body).split("v1=")[1]
        if hmac.compare_digest(expected.encode(), given.encode()):
            event = json.loads(body)["id"]
            if event in seen_events:              # 簽章對但已處理過：冪等地回 200
                return 200, f"duplicate {event}, ignored"
            seen_events.add(event)
            return 200, f"accepted {event} (key {kid})"
    return 401, "signature mismatch"


class Webhook(BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers["Content-Length"]))
        status, reason = verify(self.headers.get("Pay-Signature", ""), body)
        self.send_response(status)
        self.send_header("Content-Type", "text/plain")
        self.end_headers()
        self.wfile.write(reason.encode())

    def log_message(self, *args):                 # 讓輸出保持乾淨
        pass


server = ThreadingHTTPServer(("127.0.0.1", 0), Webhook)
threading.Thread(target=server.serve_forever, daemon=True).start()
port = server.server_address[1]


def deliver(label, body, header):
    conn = http.client.HTTPConnection("127.0.0.1", port, timeout=3)
    conn.request("POST", "/v1/webhooks/pay", body=body,
                 headers={"Pay-Signature": header, "Content-Type": "application/json"})
    resp = conn.getresponse()
    text = resp.read().decode()
    conn.close()
    print(f"{label:14} → {resp.status} {text}")
    return resp.status


body = json.dumps({"id": "evt_8812", "type": "payment.succeeded",
                   "order": "A1024", "amount": 1200}, separators=(",", ":")).encode()
good = sign(SECRETS["k2"], NOW[0], body)
assert deliver("正常送達", body, good) == 200
assert deliver("重送同一事件", body, good) == 200
assert deliver("金額被改", body.replace(b"1200", b"12"), good) == 401
assert deliver("錯的 key", body, sign(secrets.token_bytes(32), NOW[0], body)) == 401
assert deliver("格式錯誤", body, "sha256=abc") == 400
old_key_body = body.replace(b"evt_8812", b"evt_8813")
assert deliver("舊 key 簽的", old_key_body, sign(SECRETS["k1"], NOW[0], old_key_body)) == 200
NOW[0] += 3600                                     # 一小時後，有人重放當初截到的請求
assert deliver("一小時後重放", body, good) == 401

server.shutdown()
server.server_close()
```

```text
正常送達           → 200 accepted evt_8812 (key k2)
重送同一事件         → 200 duplicate evt_8812, ignored
金額被改           → 401 signature mismatch
錯的 key         → 401 signature mismatch
格式錯誤           → 400 malformed signature header
舊 key 簽的       → 200 accepted evt_8813 (key k1)
一小時後重放         → 401 timestamp outside tolerance
```

逐行看這七個結果。「正常送達」通過，並回報是用 k2（目前的 secret）驗過的。「重送同一事件」簽章正確，但 event id 已經處理過，所以回 200 而不重複加點數。「金額被改」是攻擊者攔下合法請求、把 body 的 1200 改成 12 再送出：tag 完全對不上，回 401。「錯的 key」模擬攻擊者用自己的 secret 簽章，同樣被拒。「格式錯誤」在解析階段就被擋下，回 400，不會進到比較。「舊 key 簽的」說明輪替期間的行為：供應商後台換了新 secret，但還有一些請求是用舊的 k1 簽的，伺服器在過渡期同時接受兩把；確認舊 key 不再出現後，就把 k1 從清單移除。最後「一小時後重放」是把一模一樣的合法請求在一小時後重送，簽章本身完全正確，但 timestamp 超出 300 秒的容許範圍，回 401。

程式裡有幾個設計值得再看一次。第一，`verify()` 對每一把 secret 都用 `compare_digest`，而且比較的是 bytes。第二，簽章的計算用的是**收到的原始 body**，不是解析後再序列化的 JSON。第三，event id 只有在簽章通過之後才被記錄，否則攻擊者可以用偽造的請求「預先佔掉」合法事件的 id。第四，容許範圍 300 秒是在時鐘誤差與重放窗口之間的取捨，伺服器的時鐘必須用 NTP 同步，否則合法請求會被誤判過期。

## 17.13 在工作上怎麼用

Rita 的 PR 評論被修完之後，團隊把這次的經驗整理成幾份檢查清單，依角色分工。

**後端工程師：程式碼審查時搜尋這些關鍵字。** 大部分的密碼學誤用都有明顯的特徵，用 grep 就能在幾秒內找出可疑的地方，再逐一判斷：

```bash
# 在 repo 根目錄執行，結果需要人工判斷，不是每一筆都是 bug
grep -rnE "import random|random\.(choice|choices|randint|random|getrandbits)" --include=*.py .
grep -rnE "hashlib\.(md5|sha1)\(" --include=*.py .           # 看用途：安全用途就要換
grep -rnE "sha256\([^)]*(secret|key|SECRET|KEY)" --include=*.py .   # 疑似 hash(secret+msg)
grep -rnE "(signature|digest|token|hmac)[a-z_]* *[!=]= " --include=*.py .   # 疑似用 == 比秘密
grep -rnE "MODE_ECB|modes\.ECB|nonce *= *b?['\"]" --include=*.py .         # ECB 與寫死的 nonce
grep -rnE "(SECRET|API_KEY|PRIVATE_KEY) *= *['\"]" --include=*.py .        # 寫死在程式裡的金鑰
```

第一行找 `random`，安全用途要改成 `secrets`。第二行找 MD5 與 SHA-1，要看它是用在快取 key 這類無害用途，還是簽章或密碼。第三、四行對應 Rita 的 ① 與 ②。第五行找 ECB 與寫死的 nonce，對應 ④。最後一行找寫死的金鑰，這類問題也應該交給 CI 中的 secret scanning 工具自動攔截。

**SRE：用指令驗證設定，不要只相信文件。** 產生金鑰與比對簽章都可以在終端機完成，排查 webhook 驗證失敗時特別好用：

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"     # 產生一把新的 secret
openssl rand -hex 32                                               # 同樣用途，沒有 Python 時
shasum -a 256 recording-8812.mp4                                   # 比對下載檔案的 SHA-256（Linux 用 sha256sum）
printf '%s' '1791000000.{"id":"evt_8812"}' | openssl dgst -sha256 -hmac "$PAY_SECRET"
# 示意輸出（OpenSSL 3 的格式；舊版只印 (stdin)=）：HMAC-SHA2-256(stdin)= 5b0c…（和 header 中的 v1 比對）
```

最後一行在排查「供應商說簽了、我們說驗不過」時最有用：把 log 中記錄的原始 body 與 timestamp 照簽章格式拼起來，用 `openssl dgst -hmac` 算一次。結果和 header 一致，問題就在我們的程式（多半是 body 被框架改過）；不一致，就是 secret 不同（多半是貼錯環境）。注意 `printf '%s'` 不會加換行，用 `echo` 多一個 `\n` 就會算出完全不同的值。另外，HMAC secret 只用環境變數傳入，不要直接寫在指令裡，避免留在 shell history。

**前端工程師：瀏覽器裡的密碼學用 Web Crypto API。** 瀏覽器有 `crypto.getRandomValues()` 與 `crypto.randomUUID()` 可產生安全亂數，`crypto.subtle` 提供 AES-GCM、HMAC、ECDSA 等標準演算法，不要用 `Math.random()` 產生任何安全相關的值，也不要在前端程式裡放任何 secret，因為所有 JavaScript 都會被下載到使用者電腦上。第 28 章的 PKCE verifier 就要用 `getRandomValues` 產生。

**影音工程師：知道媒體加密用的是哪些積木。** Joe 負責的 WebRTC 媒體一律用 DTLS 交換金鑰、SRTP 加密（第 36 章），金鑰交換同樣是 ECDHE，SRTP 常用 AES-GCM 或 AES-CM 搭配 HMAC。SRT 的直播 ingest 可以設定 AES 加密與 passphrase（第 38 章），passphrase 要用 `secrets` 產生並經由 secrets manager 發給講者的編碼器，不要在聊天軟體裡傳。

**資安工程師：建立一份「核准演算法」清單。** Rita 把 17.11 節的表格放進團隊的開發規範，新服務的設計文件要寫明「資料在哪裡、用什麼保護、金鑰在哪裡、怎麼輪替」。判斷流程可以畫成這樣：

```text
 需求：「這個資料要安全」
   │
   ├─ 要防誰？被看到？被改？被冒充？（17.2 節三個問題）
   │
   ├─ 只怕被改／被冒充 ──► 驗證方只有我們？ ─是─► HMAC-SHA256（金鑰 32 bytes、compare_digest）
   │                      └─否（很多方要驗）─────► 數位簽章（Ed25519／ECDSA P-256）
   │
   ├─ 也怕被看到 ──► 在傳輸中？ ─是─► TLS（第 18 章），不要自己加密通道
   │                └─否（存起來的資料）─► AEAD（AES-GCM／ChaCha20-Poly1305）或 Fernet
   │                                         nonce 用 os.urandom(12)；金鑰在 KMS；帶 key ID
   │
   └─ 是密碼？ ──► 不是加密也不是 hash：Argon2id／scrypt／bcrypt（第 26 章）
```

這張流程圖的第一刀永遠是「要防什麼」，而不是「要用哪個演算法」。小晴的導回網址就是一個好例子：訂單號碼本身不是秘密，真正的需求只是「不能被改」，所以最後的修正是改成 HMAC 簽章，比加密更簡單，也少了一把要管理的加密金鑰。

## 17.14 常見錯誤與除錯

下表整理聲聲 Live 與一般團隊最常見的密碼學誤用與排查方式。前幾列多半不會有任何錯誤訊息，只能靠程式碼審查與測試發現。

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| webhook 簽章「偶爾」驗不過，同樣的事件重送又過了 | 用解析後再序列化的 JSON 算 HMAC，key 順序或空白改變 | 在驗證失敗時記錄原始 body 的 SHA-256，與重算用的 bytes 比對 | 一律對 `request.get_data()` 取得的原始 bytes 算 HMAC |
| 所有 webhook 都驗不過，供應商堅稱簽章正確 | secret 貼錯環境、多了換行，或把 hex 字串當 bytes 用 | 用 `openssl dgst -sha256 -hmac` 對 log 中的原始資料重算；檢查 secret 長度 | 從 secrets manager 重新讀取；明確處理 hex／base64 解碼 |
| 驗證程式在測試中都對，資安審查說有漏洞 | 用 `==` 比較 tag、或用 `sha256(secret + body)` 代替 HMAC | 搜尋程式中的 `==` 與 `hashlib.sha256(` 的用法 | 改用 `hmac.new(...).digest()` 與 `hmac.compare_digest` |
| 不同使用者的「加密」連結有相同的前綴或規律 | 固定的 nonce／IV、ECB 模式，或根本只是 XOR | 對兩個相同內容的明文加密，看密文是否相同 | 改用 AEAD 與每次新的隨機 nonce；不需保密就只用 HMAC |
| 解密出來的資料被改過，程式沒有發現 | 只有加密沒有完整性（CTR、CBC 沒有 MAC） | 翻轉密文中的一個 bit 再解密，看是否仍成功 | 改用 AES-GCM／ChaCha20-Poly1305 或 Fernet，解密失敗即拒絕 |
| AES-GCM 解密偶爾出現 `InvalidTag` | AAD 在加密與解密時不一致，或 nonce 沒有和密文一起存好 | 記錄加解密時的 AAD 與 nonce 長度；檢查儲存欄位是否被截斷 | 把 nonce 固定放在密文前 12 bytes；AAD 用固定、有版本的格式 |
| 合法的 webhook 被判定過期 | 伺服器時鐘沒有同步，或容許範圍太小 | 比對主機時間與 NTP；看拒絕時的時間差分布 | 開啟 NTP 同步；容許範圍設在數分鐘並記錄時間差 |
| 安全掃描報告「predictable token」 | 用 `random`、時間或遞增 ID 產生 token | 搜尋 `random.` 的使用處 | 改用 `secrets.token_urlsafe(32)`，並讓舊 token 失效 |
| 換了 secret 後短時間內大量 webhook 失敗 | 一次切換，沒有新舊並存的過渡期 | 失敗時間點與換 key 時間一致 | 支援多把 key（帶 key ID），先加新 key、確認後再移除舊 key |

除錯密碼學問題時，最有效的方法是**把每一步的中間值以 hex 印出來比對**：原始 bytes 的長度與 SHA-256、被簽的完整字串、金鑰的長度（不要印出金鑰本身）、nonce 與 AAD。大部分「驗不過」的問題最後都是 bytes 不一致：多一個換行、不同的編碼、hex 與原始 bytes 搞混。驗證失敗時，回給 client 的訊息要簡短一致，詳細的中間值只寫進內部 log。

## 17.15 動手練習

1. **延伸動手做：加上第二種簽章版本**（延伸本章程式）。供應商宣布將在 header 中同時送出 `v1`（HMAC-SHA256）與 `v2`（HMAC-SHA512），格式改為 `t=…,v1=…,v2=…`。修改 17.12 節的 `verify()`，讓它在過渡期接受任一版本，並寫出測試：只有 v2 正確時要通過、v1 與 v2 都錯時要拒絕。
   答案要點：解析時不能再用 `dict()` 一次收完，要允許多個版本欄位；每個版本都用 `compare_digest` 比較，任何一個相符即通過。也要想清楚「降級」的問題：如果過渡期結束，就應該只接受 v2，避免攻擊者利用較弱的版本。

2. **觀察雪崩效應與 length 不變**（真實工具）。在終端機執行 `printf 'amount=1200' | shasum -a 256` 與 `printf 'amount=1201' | shasum -a 256`（Linux 用 `sha256sum`），再對一個 1 GB 的檔案算一次，比較輸出長度。
   答案要點：輸出永遠是 64 個 hex 字元（32 bytes），和輸入大小無關；只差一個字元的兩個輸入，摘要看不出任何關聯。這也說明了「hash 相同」只能用來比對內容，不能用來推測內容。

3. **用 openssl 驗證 HMAC**（真實工具）。用 17.4 節程式的 `SECRET` 與 `body`，以 `openssl dgst -sha256 -mac HMAC -macopt hexkey:<SECRET 的 hex>` 計算 HMAC，確認結果與程式輸出的第一行相同；再改用 `echo` 取代 `printf '%s'`，觀察結果的差異。
   答案要點：兩者一致代表你掌握了「被簽的 bytes 到底是什麼」。`echo` 會在結尾多一個換行，tag 就完全不同，這是 webhook 驗證失敗最常見的原因之一。注意 `-hmac` 參數接的是字串金鑰，二進位金鑰要用 `-macopt hexkey:`。

4. **手算 Diffie-Hellman 與 RSA**。用 p = 23、g = 5，令 a = 4、b = 9，手算 A、B 與共享值 K；再用 17.8 節的 RSA 金鑰（n = 3233、e = 17、d = 2753），對 m = 42 簽章，用 Python 的 `pow()` 驗證你的結果。
   答案要點：A = 5⁴ mod 23 = 4，B = 5⁹ mod 23 = 11，K = 11⁴ mod 23 = 4⁹ mod 23 = 13。RSA 的部分，計算 s = pow(42, 2753, 3233)，再確認 pow(s, 17, 3233) == 42。重點是理解「私鑰算、公鑰驗」與「指數交換律讓雙方得到同一個值」。

5. **找出 nonce 重用**（延伸本章程式）。修改 17.6 節的玩具程式，寫一個函數檢查一批密文（每筆附上 nonce）中，是否有任何兩筆使用了相同的 nonce，並思考在真實系統中，什麼情況會讓「每次遞增的計數器 nonce」意外重複。
   答案要點：用 set 記錄看過的 nonce 即可偵測。計數器重複的典型情況：服務重啟後計數器從 0 開始、從備份還原舊的計數器值、多個 process 或多台機器共用同一把金鑰各自計數。所以一般應用偏好隨機 nonce，或每台機器用不同的金鑰。

6. **審查一段程式**。下面這段來自某個舊服務：`token = hashlib.md5(str(time.time()).encode()).hexdigest()`，用來產生 email 驗證連結。列出它的所有問題，並寫出修正版。
   答案要點：時間是可預測的輸入，攻擊者知道大致的寄信時間就能逐一嘗試；MD5 在這裡不是主要問題，但也沒有帶來任何安全性，因為 hash 不會增加熵。修正版是 `secrets.token_urlsafe(32)`，資料庫只存它的 SHA-256，並設定到期時間與一次性使用。

## 本章重點整理

- 先問「要防什麼」：機密性（不被看到）、完整性（不被改）、真實性（不被冒充）是三個不同的問題；加密不等於防竄改，編碼也不等於加密。
- Hash 把任意資料變成固定長度的指紋，安全用途選 SHA-256 等級以上；MD5 與 SHA-1 的碰撞都已能實際產生，只能留在不需要抗碰撞的場合。
- 單純的 hash 擋不住刻意竄改，因為攻擊者改完可以重算；`sha256(secret + msg)` 還有 length extension 的問題，帶金鑰的驗證一律用 HMAC。
- 比較 tag、token 等秘密值要用 `hmac.compare_digest`，`==` 會在第一個不同的 byte 停下，讓比較時間洩漏資訊。
- HMAC 驗證的對象必須是收到的原始 bytes；先解析再序列化的 JSON 會讓 tag 對不上。
- 安全相關的值（token、金鑰、nonce、驗證碼）一律用 `secrets` 或 `os.urandom`；`random` 可被預測，只能用在模擬與可重現的場合。
- 串流加密（包括 AES-CTR）在同一把金鑰下重用 nonce，兩份密文 XOR 就等於兩份明文 XOR，知道一份就能解出另一份。
- 只有加密而沒有完整性的密文可以被精準修改；AEAD（AES-GCM、ChaCha20-Poly1305）在一個操作中提供機密性與完整性，tag 不符就不回傳明文。
- AES-GCM 的 nonce 為 12 bytes，同一把金鑰下絕不能重複；隨機 nonce 要控制每把金鑰的加密次數並規劃輪替。
- 公鑰密碼讓「一方簽、多方驗」與「沒見過面也能建立共享金鑰」成為可能；RSA 依賴質因數分解的困難，ECC 用短得多的金鑰達到同等強度。
- 數位簽章提供完整性、真實性與不可否認性，但不提供機密性；公鑰屬於誰要靠憑證與 CA 證明（第 18 章）。
- Diffie-Hellman 讓雙方在被偷聽的通道上算出共享秘密，但本身不驗證身分，必須搭配簽章防中間人；共享值要經過 HKDF 才能當金鑰。
- ephemeral DH 提供前向保密：長期私鑰日後外洩，也解不開過去的流量；後量子的混合金鑰交換是 2026 年 TLS 的主要演進方向。
- 不要自己發明演算法、不要自己實作、也不要自己組裝協定；選用 TLS、AEAD、Fernet、成熟函式庫等整合好的方案，並把金鑰放在 KMS 或 secrets manager、帶 key ID 以便輪替。

## 延伸問答

> [!question]- Q1. 概念辨析：金流 webhook 用 HMAC 簽章，登入服務簽發的 JWT 卻常用 RS256 或 ES256。兩者為什麼選擇不同？
> 判斷的關鍵是「誰需要驗證」。金流 webhook 只有一個驗證者，就是我們自己的 API；供應商與我們本來就要交換一把 secret，用 HMAC 簡單、快速，金鑰也只存在兩個地方。HMAC 的限制是驗證者也算得出 tag，所以能驗證的人都能偽造，但在這個情境下驗證者只有我們，這個限制沒有影響。
>
> 登入服務簽發的 JWT 則會被許多內部服務驗證：課表、聊天、直播、金流各自都要確認 token 有效。如果用 HS256，每個服務都要持有同一把 secret，任何一個服務被入侵，攻擊者就能簽出任意使用者的 token。改用 RS256 或 ES256，只有登入服務持有私鑰，其他服務只拿到公鑰，被入侵也只能驗證不能偽造，而且公鑰可以透過 JWKS 公開發布與輪替（第 27 章）。所以選擇依據是驗證方的數量與信任程度，而不是哪個演算法「比較強」。

> [!question]- Q2. 面試題：為什麼比較 HMAC 不能用 ==？在網路延遲雜訊那麼大的情況下，這真的會被利用嗎？
> `==` 在找到第一個不同的 byte 時就返回，所以比較所花的時間與「猜測值和正確值的共同前綴長度」相關。攻擊者可以固定其他 byte、只改變第一個 byte 的 256 種可能，量測哪一個回應稍微慢一點，就推得第一個 byte，然後依序推下一個。原本要猜 2²⁵⁶ 種可能的問題，變成每個位置猜 256 次，總共只要幾千次。
>
> 網路雜訊確實讓單次量測無法分辨幾奈秒的差異，但統計方法可以靠大量重複量測把雜訊平均掉，攻擊者若和伺服器在同一個雲端區域，雜訊也小得多，研究上已有在網路上實際量測到這類差異的案例。更重要的是防禦的成本極低，只要把 `==` 換成 `hmac.compare_digest`，所以不需要爭論「實際上能不能利用」。面試時能說清楚「洩漏的是什麼資訊、攻擊的複雜度從指數降到線性、修正方法是什麼」，就是完整的答案。

> [!question]- Q3. 手算：用 p = 23、g = 5，小晴選 a = 3，伺服器選 b = 7，雙方的公開值與共享值各是多少？偷聽者要怎麼才能算出共享值？
> 小晴的公開值 A = 5³ mod 23 = 125 mod 23；125 = 5 × 23 + 10，所以 A = 10。伺服器的公開值 B = 5⁷ mod 23：5² = 25 ≡ 2，5⁴ ≡ 4，5⁶ = 5⁴ × 5² ≡ 8，5⁷ ≡ 8 × 5 = 40 ≡ 17，所以 B = 17。共享值由小晴算 17³ mod 23：17² = 289 = 12 × 23 + 13，再乘 17 得 221 = 9 × 23 + 14，所以 K = 14；伺服器算 10⁷ mod 23 也會得到 14，兩者都等於 5²¹ mod 23。
>
> 偷聽者看到 p、g、A = 10、B = 17，要算出 K，必須先從 A 或 B 反推出 a 或 b，這是離散對數問題。在 p = 23 時，只要依序試 5¹、5²、…，試到 5³ = 10 就找到 a，所以這組參數毫無安全性。真實系統使用 2048 bit 以上的質數群或 256 bit 的橢圓曲線，讓這種搜尋在任何可預見的運算資源下都不可行。這題也提醒，DH 的安全完全依賴參數夠大，而不是運算步驟本身有什麼秘密。

> [!question]- Q4. 情境判斷：同事提議「把使用者 ID 用 AES 加密後放進網址，就不怕被改了」。你會怎麼回應？
> 這個提議混淆了機密性與完整性。只有加密的密文，攻擊者雖然看不懂，但如果用的是 CTR 這類串流模式，翻轉密文中的 bit 就會讓明文同一位置跟著翻轉；用 CBC 這類模式，修改密文也會造成可預期的明文變化。如果解密端沒有驗證完整性，攻擊者就可能把 ID 改成別的值。所以「加密了就不怕被改」不成立，除非用的是 AEAD，而 AEAD 的保護來自它的 tag，不是來自「加密」本身。
>
> 更根本的問題是先確認需求：使用者 ID 真的需要保密嗎？如果只是不希望被竄改，用 HMAC 對 ID 與到期時間簽章就夠了，比加密簡單，也不用管 nonce。如果真的需要保密（例如不想洩漏內部 ID 的規律），就用 AES-GCM 或 Fernet，每次產生新的隨機 nonce，並把使用者的工作階段或用途放進 AAD。無論哪一種，伺服器仍然要做授權檢查，不能因為「簽過了」就跳過「這個使用者能不能存取這筆資料」的判斷。

> [!question]- Q5. 看 log 找原因：webhook 驗證在 staging 全部通過，上 production 後約 3% 的請求回 401，失敗的請求都含有中文的課程名稱。可能是什麼？
> 「只有含中文的請求失敗」強烈暗示被簽的 bytes 在某個地方被改變了，最可能的地方是編碼。常見的情況有幾種：production 前面多了一層 proxy 或 API gateway，對 body 做了重新編碼或正規化；程式取 body 時先解碼成 str、再用不同的編碼（或 `ensure_ascii` 不同的 JSON 序列化）轉回 bytes；或者 log 與驗證用的是解析後再序列化的 JSON，中文被轉成 `\uXXXX` 跳脫序列。只要被簽的 bytes 與供應商簽的 bytes 有一個 byte 不同，HMAC 就完全不同。
>
> 確認方式是在驗證失敗時記錄原始 body 的長度與 SHA-256，請供應商提供同一個事件 id 的 body 長度或 hash 比對，並對照 staging 與 production 的請求路徑差異。修正方式是驗證程式一律使用框架提供的原始 bytes（Flask 的 `request.get_data()`），在任何解析之前就完成驗證，並確認前面的 proxy 不會改寫 body。這題也說明了為什麼 staging 的測試資料要包含非 ASCII 字元。

> [!question]- Q6. 設計取捨：要加密資料庫中學生的電話號碼欄位，AES-GCM 的 nonce 用隨機產生還是用遞增計數器比較好？
> 用計數器的好處是保證不重複，而且同一把金鑰可以加密的次數極多；但它要求一個可靠、持久、全域唯一的計數器狀態。資料庫欄位加密通常由多個 API process、多台機器同時執行，還可能從備份還原；任何一種情況都可能讓計數器回到用過的值，而 AES-GCM 的 nonce 重用會同時破壞機密性與完整性。為了一個欄位維護分散式計數器，風險和複雜度都太高。
>
> 隨機 12 bytes nonce 的代價是生日問題：同一把金鑰下加密次數越多，兩個 nonce 碰撞的機率越高，所以 NIST 建議以隨機 nonce 使用時，每把金鑰的加密次數控制在 2³² 以下。聲聲 Live 的學生數遠低於這個量級，就算每次更新電話都重新加密也綽綽有餘，再搭配定期金鑰輪替與 key ID 即可。因此這個情境選隨機 nonce。另一個值得考慮的設計是把學生 ID 放進 AAD，防止有人把 A 學生的密文搬到 B 學生的欄位。

> [!question]- Q7. 概念辨析：TLS 已經加密了整條連線，為什麼 webhook 還需要 HMAC 簽章？
> TLS 保護的是「這條連線」：它保證資料在傳輸中不被看到、不被改，並讓 client 確認 server 的身分。但在 webhook 的情境裡，發起連線的是供應商，接受連線的是我們。一般的 TLS 只驗證 server 的憑證，不驗證 client，所以我們的 server 知道「這條連線沒被竊聽」，卻不知道「連過來的是誰」。任何人都能對 `api.shengsheng.example` 建立一條完全正常的 TLS 連線，再送一個偽造的付款成功事件。
>
> HMAC 簽章補上的就是「請求出自誰」這一環，而且它綁定在訊息本身上，不依賴連線：請求經過 CDN、LB、nginx 時 TLS 會被終結（第 19、25 章），簽章仍跟著 body 走到應用程式。另一種做法是 mTLS，要求 client 也出示憑證（第 18、30 章），但它需要雙方管理憑證，而且 TLS 終結在 LB 時應用程式拿不到原始的驗證結果。來源 IP 範圍（198.51.100.64/26）可以作為額外的一層防護，但不能取代簽章，因為 IP 範圍會變動，也無法證明內容未被改。

> [!question]- Q8. 你在程式碼審查中看到 `key = hashlib.sha256(b"shengsheng-2026").digest()`，接著用它做 AES-GCM 加密。作者說「SHA-256 輸出 256 bit，所以這是 AES-256」。這個說法對嗎？
> 金鑰的長度是 256 bit，但金鑰的**強度**取決於攻擊者猜到它要試幾次，也就是它的熵，而不是長度。這把金鑰完全由一個字串決定，攻擊者只要猜中 `shengsheng-2026` 就能重算出同一把金鑰；這種「公司名＋年份」的字串在任何字典裡都排在很前面。hash 不會增加熵，只會把低熵的輸入換成看起來很亂的輸出。所以這不是 AES-256 的強度，而是「一個好猜的密碼」的強度，而且它還寫死在程式碼裡，任何能讀 repo 的人都拿得到。
>
> 修正方式是用 `secrets.token_bytes(32)` 或 KMS 產生真正隨機的金鑰，存放在 secrets manager，程式啟動時讀取，並帶 key ID 以便輪替。如果真的必須從人類可記憶的密碼導出金鑰（例如使用者自己設定的加密密碼），要用專門設計的 KDF，例如 scrypt 或 Argon2，搭配隨機 salt 與足夠的成本參數（第 26 章），而不是一次 SHA-256。這題的通則是：看到金鑰從字串「算出來」，就要問它的熵從哪裡來。
