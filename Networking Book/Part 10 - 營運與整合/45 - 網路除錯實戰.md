# 第 45 章　網路除錯實戰：從症狀到根因

> [!abstract] 本章地圖
> **核心問題**：使用者只會說「壞了」「好慢」「一直斷」，你要怎麼在幾分鐘內把這句話變成「哪一層、哪一個元件、什麼證據」，再一路推到根因？
>
> **你會學到**：
> - 用「症狀、觀察、假設、驗證」的循環除錯，而不是憑直覺重開服務
> - 依情境選擇由下而上、由上而下或分半法，並用一張判斷流程圖決定第一步
> - 走完八個聲聲 Live 真實事故的完整診斷：DNS、TLS、逾時與被拒、間歇性 reset、慢、CORS、WebSocket 斷線、視訊單向
> - 對每一種症狀說出「先用哪個工具、預期看到什麼、看到之後往哪一章找」
> - 用 Python 寫一個診斷小工具，自動分辨 refused、timeout、RST、沒回應、慢與錯誤的 header
>
> **前置知識**：第 3 章（工具箱）、第 10 章（TCP 狀態與 RST）、第 14–16 章（DNS）、第 18–19 章（TLS 與憑證）、第 20–25 章（HTTP、CORS、proxy）、第 32 章（WebSocket）、第 35、39 章（SDP 與影音除錯）

## 45.1 故事：故障演練日，八張沒有答案的工單

小晴進聲聲 Live 已經半年。這半年裡，CLOSE_WAIT 塞爆連線池（第 10 章）、API 搬家後還有人連到舊 IP（第 14 章）、登入憑證在早上八點過期（第 19 章）、首頁顯示別人的名字（第 21 章）、預約按鈕被 CORS 擋下（第 23 章）、教室 WebSocket 反覆重連（第 32 章），每一次都是阿德先開口說出「這是哪一層的問題」，小晴再跟著查。下個月起小晴要第一次擔任主要值班，阿德決定在那之前辦一場**故障演練**（game day）：在 staging 環境裡刻意重現過去的事故，讓值班的人只拿到使用者的原話，不給任何提示，看能不能自己走到根因。

週六早上十點，第一張工單貼上投影幕：「學生說教室進不去，一直轉圈圈。」小晴的手很快，打開 Flask 的 log 開始搜尋 500。五分鐘過去，什麼也沒找到。阿德把投影幕切回工單：「你還不知道這個請求有沒有到 Flask。轉圈圈可能是名字查不到、連線連不上、TLS 交握失敗、server 不回應，也可能是瀏覽器自己擋掉了。先決定是哪一層，再決定去看誰的 log。」

這句話是本章的主旨。網路問題難，不是因為每個機制都很複雜，而是因為**症狀出現的位置和原因所在的位置往往不同**（第 1 章）：使用者在瀏覽器看到轉圈圈，原因可能在 DNS resolver 的快取、LB 的閒置逾時，或某個 Python 連線池忘了 close。這一天的八張工單，每一張都對應全書發生過的一場事故：

```text
 工單（使用者的原話）          重現的事故                         本章
 ① 教室進不去，一直轉圈        API 搬家後連到舊 IP（第 14 章）       45.4
 ② 登入頁出現紅色警告          auth 憑證過期與鏈不完整（第 19 章）    45.5
 ③ 白板連不上、課表 504        uvicorn 只聽 127.0.0.1／accept queue 滿 45.6
 ④ 偶爾跳出「連線已重設」       閒置逾時不一致、CLOSE_WAIT（第 10 章）  45.7
 ⑤ 課表頁很慢                  五段時間各自的兇手（第 3、12、16 章）   45.8
 ⑥ 預約按鈕沒反應              preflight 失敗、缺 Vary: Origin（第 23 章）45.9
 ⑦ 安靜的教室每分鐘斷一次       心跳停用、proxy_read_timeout（第 32 章） 45.10
 ⑧ 老師看不到我、我聽不到老師   SDP 拒絕視訊、autoplay（第 35、39 章）   45.11
```

這張表是演練結束後小晴整理的對照。左欄是使用者真正會說的話，沒有一句提到 DNS、TCP 或 header；中間是被重現的事故，大部分你在前面的章節已經讀過根因；右欄是本章的小節。本章不再重複每個機制的原理，而是示範**怎麼從左欄走到中間**：每個案例都依序寫出症狀、初步觀察、假設、驗證步驟（工具指令與示意輸出）、根因、修正與預防。最後兩節把八個案例濃縮成一張「症狀到章節」的大表，並用 Python 寫一個診斷小工具，把前半段的判斷自動化。

## 45.2 除錯是一門方法：症狀、證據與假設

在進入案例之前，先把方法講清楚。除錯其實是一個很小的科學實驗循環：**觀察**症狀，提出一個可以被推翻的**假設**，寫下「如果假設成立，我應該看到什麼」的**預測**，用工具**驗證**，再依結果收斂或換一個假設。這個循環最常被跳過的是「預測」那一步。小晴在工單 ① 的反應是「去 Flask 找錯誤」，但沒有先問「如果是 Flask 的錯，Flask 的 log 會有 500，nginx 的 log 會有 5xx」；有了預測，nginx 的 access log 裡根本沒有這些學生的請求，就足以在一分鐘內推翻假設。

```text
        ┌──────────────► ① 觀察：使用者原話、告警、圖表、範圍、時間點
        │                      │
        │                      ▼
        │               ② 假設：「是 X 層的 Y 元件，因為 Z」
        │                      │
        │                      ▼
   ⑤ 換假設             ③ 預測：「如果成立，用工具 T 應該看到 E」
   或縮小範圍                  │
        │                      ▼
        │               ④ 驗證：執行 T，看到的是 E 嗎？
        │                 │是                       │否
        │                 ▼                         │
        │            縮小到元件，找根因             │
        └───────────────────────────────────────────┘
```

這張圖的重點在 ③ 與 ④ 之間的那條「否」：被推翻的假設不是浪費時間，它把搜尋範圍砍掉了一塊。好的假設要**具體到能被推翻**，「網路不穩」不是假設，「學生的 resolver 還快取著 203.0.113.20」才是，因為後者告訴你下一步要對哪一台 resolver 下 `dig`、預期看到什麼數字。

觀察階段有四個問題，阿德要求每一位值班工程師在動手之前先寫下答案。第一，**影響誰**：全部使用者、某個地區、某家 ISP、某所學校、某個瀏覽器版本，還是只有一個人？範圍越窄，原因越靠近使用者那一端。第二，**從什麼時候開始**：精確到分鐘，然後去對部署紀錄、設定變更、憑證到期日與 DNS 修改時間；絕大多數事故都緊跟在一次變更之後。第三，**在哪裡看得到**：同一個請求在瀏覽器、CDN、LB、nginx、應用程式各留下什麼紀錄，哪一站開始「沒有紀錄」。第四，**能不能重現**：每次都壞、偶爾壞，還是只有閒置一段時間後才壞？「偶爾」與「閒置後」本身就是很強的線索，第 45.7 節會用到。

這四個問題中的第三個，決定了你能用哪些證據。下表列出聲聲 Live 一個請求沿途的觀察點，以及每個觀察點看得到與看不到的東西：

| 觀察點 | 看得到 | 看不到 | 常用工具 |
|---|---|---|---|
| 使用者的瀏覽器 | 錯誤分類（`ERR_*`）、CORS 與 CSP 訊息、每個請求的時間分段、WebSocket close code、getStats | 伺服器內部；被瀏覽器擋下的回應內容 | DevTools Network／Console、HAR、webrtc-internals |
| 使用者那一端的命令列 | 該網路的 resolver 答案、到 edge 的路徑、TLS 憑證 | 瀏覽器特有的規則（CORS、HSTS、快取） | dig、curl `-v`／`-w`、openssl s_client、mtr |
| CDN 與 LB | 命中與否、回源狀態、TLS 終結、連線被誰關閉 | 應用程式在想什麼 | CDN log、LB access log 與 metrics |
| nginx | upstream 的連線與回應時間、錯誤類型（refused、timed out、reset） | 應用程式內部的慢查詢 | error log、access log 的 `$upstream_*` 變數 |
| 應用程式主機 | socket 狀態、accept queue、fd、應用程式 log | 路上被丟掉的封包 | ss、lsof、nstat、`x-request-id` |
| 封包 | 真正發生的事：誰送了 SYN、RST、FIN，間隔多久 | 加密之後的內容 | tcpdump、Wireshark |

讀這張表要注意每一列的「看不到」。前端工程師最常犯的錯，是只在瀏覽器看到 CORS 錯誤就去改 CORS 設定，卻不知道 500 錯誤的回應如果沒有 CORS header，也會被瀏覽器報成 CORS 錯誤；後端工程師最常犯的錯，則是用自己筆電上的 `dig` 證明「DNS 沒問題」，卻沒想到使用者的 resolver 和自己的不是同一台。每一個結論都要附上「這是在哪個觀察點看到的」，才能被下一個人驗證。

最後是兩條紀律。**先保留證據，再止血**：重開服務常常是正確的止血手段，但重開之前花三十秒存下 `ss -tanp`、`ss -ltn` 與最近的 log，否則 CLOSE_WAIT 與 accept queue 這類證據會隨 process 一起消失。**一次只改一個變數**：同時改 TTL、重開 nginx、清 CDN 快取，問題好了你也不知道是哪一個修好的，下次還會再犯。

## 45.3 分層排查：由下而上、由上而下與分半法

有了方法，下一個問題是「從哪裡開始驗證」。網路是分層的（第 2 章），排查也可以沿著分層走。常用的策略有三種，它們不是互斥的，而是適合不同的起點。

```text
  層                    由下而上（完全不通時）    由上而下（有明確錯誤時）    分半法（不知道從哪開始時）
  應用（Flask、SFU）          ▲ ⑥                       ① 錯誤訊息、status         ③ 再切一半
  HTTP／WebSocket            │ ⑤                       ② 對應的 header            │
  TLS                        │ ④                       ③ 憑證、ALPN               ① 先從中間切：
  TCP                        │ ③ refused／timeout       ④ 連線狀態                 │  curl 繞過 CDN 直打 LB？
  IP／路由                    │ ② ping、traceroute        ⑤ 路徑                    ② 有問題的那一半再切
  名稱解析                    │ ① dig、getent             ⑥ DNS                     │
  鏈路（Wi-Fi、VPN、MTU）     ① 從最底下開始             ▼                        ▼
```

**由下而上**從最底層開始，一層一層證明「這一層沒問題」，直到找到第一個壞掉的層。它的優點是不會漏，缺點是慢；適合「完全不通」、「新環境第一次部署」、「最近改過網路設定」這類情境。第 8 章辦公室 VPN 的「大東西會消失」就是典型：ping 正常、小請求正常，只有往下追到 MTU 與 ICMP 才找得到原因。

**由上而下**從使用者看到的錯誤訊息開始，順著訊息往下追。它最快，前提是你手上有一個**具體的錯誤**：瀏覽器 Console 的 CORS 訊息、nginx 的 `connect() failed (111: Connection refused)`、WebSocket 的 close code 1009、Python 的 `certificate has expired`。這些訊息往往已經直接點名了層與原因，第 10 章那張「Python 例外對應網路事件」的表就是由上而下的字典。

**分半法**（bisection）在既沒有明確錯誤、又不想從頭排除時最有效：在可疑範圍的「中間」找一個觀察點，判斷問題在它的上游還是下游，每做一次就把範圍砍半。聲聲 Live 的請求路徑是「瀏覽器 → CDN → LB → nginx → gunicorn → Flask」，最好用的中點是 `curl --resolve` 繞過 CDN 直接打 LB：直打 LB 正常，問題在 CDN 或使用者那一側；直打也壞，再往下對 nginx 主機的 127.0.0.1 打一次。分半法也能沿著時間切：問題出現在兩次部署之間，就把中間的設定變更逐一還原，和 `git bisect` 是同一個思路。

| 方法 | 適合的情境 | 第一步 | 常見陷阱 |
|---|---|---|---|
| 由下而上 | 完全不通、新環境、剛改過網路或防火牆 | `dig`／`getent`，接著 `nc -vz` | 每層都測一遍很慢；ping 通不代表 TCP 443 通 |
| 由上而下 | 手上有明確的錯誤訊息或 status code | 把錯誤訊息對應到層（本章 45.12 大表） | 訊息可能是「轉述」：CORS 錯誤背後可能是 502 |
| 分半法 | 路徑很長、元件很多、沒有明確錯誤 | 在路徑中點量一次：繞過 CDN、直打 upstream | 中點的測試條件要和使用者一致（同樣的 Host、SNI、Origin） |

三種方法可以組合。實務上最常見的順序是：先由上而下讀錯誤訊息，訊息不夠明確時用分半法切出元件，再在那個元件上由下而上確認。阿德把這個習慣畫成演練當天投影幕上的判斷流程圖，它是第 3 章那張流程圖的延伸，差別在於每一支都直接指到本章的案例：

```text
                         使用者：「聲聲 Live 壞了」
                                  │
                 先寫下：影響誰？從何時？最近改了什麼？
                                  │
     ┌──────────────┬─────────────┼──────────────┬───────────────┬──────────────┐
   打不開         很慢          會斷線        只有瀏覽器報錯   看不到／聽不到
     │              │              │               │                │
 名字解析對嗎？  curl -w 切五段  斷線時間點      Console 訊息與    ICE 已連線且
 IP 是新的嗎？   哪一段最大？    有規律嗎？      Network 的 status  兩個方向 bytes 都在動？
   │否→45.4        │→45.8        │是→45.7、45.10  │CORS→45.9        │否→網路（第 36、39 章）
   │是             │             │ close code？   │憑證→45.5        │是→45.11
 TLS 錯誤？→45.5                 │→45.10          │混合內容、CSP     │  SDP、SFU、播放端
 connect 結果？                  │否→45.7         │→第 23 章
 refused／timeout／               抓 RST 是誰送的
 連上但沒回應→45.6
```

最上面一行強迫你先回答 45.2 節的三個問題，因為「影響誰」常常直接決定分支：只有一所學校壞，原因幾乎不會在聲聲 Live 的 Flask；所有人都壞，就先查自己的 DNS、憑證與最近的部署。接下來的五個分支對應使用者最常說的五種話。每一支的第一個問題都是一個**是非題**，而且都有一個工具能在一分鐘內回答它，這是流程圖能在壓力下派上用場的關鍵。

## 45.4 案例一：DNS 解析失敗或連到舊 IP

**症狀**。演練重現第 14 章的 API 搬家：21:00 把 `api.shengsheng.example` 的 A 紀錄從舊機房的 203.0.113.20 改成新 LB 的 203.0.113.80，21:10 關掉舊機器。21:15 起工單湧入：「App 一直轉圈」「課表載不出來」，但也有很多人完全正常。

**初步觀察**。小晴這次沒有先開 Flask 的 log，而是寫下範圍：受影響的使用者分散各地，不集中在某家 ISP；新 LB 的流量只有平常的三成；nginx 的 access log 裡完全沒有那些抱怨學生的請求。「請求沒有抵達新 LB」加上「21:00 改過 DNS」，假設幾乎自己浮現。

**假設**。部分 resolver 還快取著舊答案 203.0.113.20，而那台機器已經關機，所以這些學生的連線逾時。預測：從受影響學生的網路查詢，會拿到 203.0.113.20，而且 TTL 是一個還沒倒數完的數字；`curl -w '%{remote_ip}'` 也會顯示舊 IP。

**驗證**。對不同 resolver 問同一個名字，比對答案與剩餘 TTL：

```bash
dig +noall +answer api.shengsheng.example @10.20.0.2      # VPC resolver
dig +noall +answer api.shengsheng.example @198.51.100.53  # 某家 ISP 的 resolver（示意）
dig +noall +answer +norecurse api.shengsheng.example @198.51.100.53   # 只看快取，不幫你去問
curl -s -o /dev/null -w '%{remote_ip} %{time_connect}\n' --max-time 5 https://api.shengsheng.example/v1/me
# ↓ 示意輸出
api.shengsheng.example. 52   IN A 203.0.113.80
api.shengsheng.example. 2710 IN A 203.0.113.20
api.shengsheng.example. 2687 IN A 203.0.113.20
203.0.113.20 0.000000
```

第一行是 VPC resolver，已經拿到新 IP；第二行是 ISP 的 resolver，回答還是 203.0.113.20，而 TTL 2710 代表「這份答案我還會再用 2710 秒」；小晴是在 21:15 左右查的，也就是要到將近 22:00，它才會重新去問權威伺服器。第三行加了 `+norecurse`，證明那是快取裡的舊資料，不是權威伺服器的錯。最後一行從受影響的網路執行 curl，`remote_ip` 是舊 IP、`time_connect` 是 0，代表交握根本沒完成，curl 在 5 秒後放棄。這裡有一個很重要的觀察：**DNS 的問題在使用者那端看起來是「連線逾時」**，如果小晴只看 curl 的錯誤訊息，會被帶去查防火牆。

```text
 21:00 修改 A 紀錄（TTL 3600）                                    22:00 最後一份舊快取過期
   │                                                                │
   │ resolver A：20:59 剛查過 ─────── 舊答案一直用到 21:59 ─────────►│
   │ resolver B：20:15 查過 ───── 舊答案用到 21:15 ──►│              │
   │ resolver C：21:01 才第一次查 ─► 直接拿到新答案                    │
   │                                                                │
   └─ 21:10 關掉舊機器：A 的使用者從這一刻起全部逾時 ─────────────────┘
          （正確做法：舊機器至少撐到 22:00＋長連線的壽命）
```

這條時間軸把根因畫得很清楚：每一台 resolver 在不同時間把答案放進快取，各自倒數 3600 秒，所以「全世界都看到新 IP」的時刻是「修改時刻＋舊 TTL」，不是按下儲存的那一刻。21:10 到 22:00 之間，仍有一部分 resolver 會回答舊 IP，而舊 IP 上已經沒有任何東西在聽。

**根因與修正**。根因不是 DNS 壞了，而是兩個營運決策：搬家前沒有先把 TTL 降低，以及在舊 TTL 過期前就關掉舊機器。止血方式是立刻把舊機器開回來（或讓舊 IP 轉送到新 LB），等到舊 IP 的流量歸零才下線。**預防**：搬家前至少提前一個舊 TTL 的時間把 TTL 降到 60–300 秒（第 15 章）；下線前看舊 IP 的連線數，而不是看時鐘；把「舊端點流量歸零」寫進搬遷檢查清單。

同一類「名字的問題」還有三種常見的變形，它們的症狀很像，證據卻完全不同：

| 變形 | 典型症狀 | 關鍵證據 | 對應章節 |
|---|---|---|---|
| 負面快取 | 新建的名稱「找不到主機」持續一段時間 | `dig` 回 NXDOMAIN，AUTHORITY 段的 SOA 帶著負面快取時間 | 第 15 章 |
| Split-horizon | 只有辦公室或 VPN 使用者連到舊 IP | 內部 resolver 與公共 resolver 答案不同 | 第 15 章 |
| 程式自己的快取與長連線 | DNS 早已改好，某個服務還在打舊版好幾小時 | `getent hosts` 已是新值，但 `ss -tn` 顯示連線仍連向舊 IP | 第 16 章 |
| search domain 與 ndots | 每次解析都慢，或剛好慢 5 秒 | tcpdump 看到一串加了 search 後綴的查詢與重送 | 第 16 章 |

第三列最容易被忽略：`dig` 繞過了程式實際走的路（第 16 章），所以驗證「程式看到什麼」要用 `getent hosts` 或直接在程式裡呼叫 `getaddrinfo`，驗證「程式正在連誰」要用 `ss -tn` 看實際的遠端位址。

## 45.5 案例二：TLS 憑證錯誤

**症狀**。演練重現第 19 章 2026 年 10 月 1 日早上的事故：瀏覽器打開 `auth.shengsheng.example` 出現 `NET::ERR_CERT_DATE_INVALID`，而且沒有「仍要繼續」的按鈕；內部服務的 log 寫著 `certificate verify failed: certificate has expired`。

**初步觀察**。範圍是「所有使用者、只有 auth」：`api.shengsheng.example` 正常，而兩者在同一台 API LB（203.0.113.80）上，依 SNI 選擇不同憑證（第 18、19 章）。時間點是台灣早上 8:00，也就是 UTC 午夜。沒有按鈕可以略過，是因為網域有 HSTS（第 19 章），這反而排除了「使用者自己點錯」的可能。

**假設**。auth 的憑證在 2026-10-01 00:00 UTC 到期。預測：用 SNI `auth` 連到 203.0.113.80，拿到的 leaf 憑證 `notAfter` 正是這個時間。

**驗證**。用 openssl 指定 SNI 連線，再把憑證的日期與名稱印出來：

```bash
openssl s_client -connect 203.0.113.80:443 -servername auth.shengsheng.example </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
openssl s_client -connect 203.0.113.80:443 -servername auth.shengsheng.example </dev/null 2>&1 \
  | grep -E 'verify error|Verify return code'
# ↓ 示意輸出
subject=CN = auth.shengsheng.example
issuer=CN = Example Issuing CA 2
notBefore=Mar 16 00:00:00 2026 GMT
notAfter=Oct  1 00:00:00 2026 GMT
verify error:num=10:certificate has expired
Verify return code: 10 (certificate has expired)
```

`-servername` 是這組指令裡最容易漏掉的參數。少了它，openssl 不送 SNI，LB 會回預設憑證，可能是 `api` 的，於是你看到的是「名稱不符」，被一個測試方法造成的假象帶偏。日期與錯誤碼 10 直接證實假設。

這場事故的價值在於它接連出現了四種 TLS 錯誤，每一種都有不同的觀察點。重新簽發並上傳後，桌面 Chrome 恢復了，但 Android App 與 Python 仍然失敗，錯誤變成 `unable to get local issuer certificate`；同一個 s_client 加上 `-showcerts`，只看到 depth 0 一張憑證，回傳碼是 21（unable to verify the first certificate），代表上傳時漏了中間憑證。桌面瀏覽器沒事，是因為它可能快取過那張中間憑證或自行補抓，這讓「瀏覽器正常」成為最不可靠的證據。接著有學生回報「憑證尚未生效」，截圖裡的電腦日期是 2020 年，這是 client 時鐘的問題，伺服器什麼都不用改。最後，阿德對 rt 的三台 nginx 逐一指定 IP 檢查，發現其中一台沒有 reload：

```bash
for ip in 10.20.2.11 10.20.2.12 10.20.2.13; do
  printf '%s ' "$ip"
  openssl s_client -connect "$ip:443" -servername rt.shengsheng.example </dev/null 2>/dev/null \
    | openssl x509 -noout -enddate
done
# ↓ 示意輸出
10.20.2.11 notAfter=Dec 28 23:59:59 2026 GMT
10.20.2.12 notAfter=Dec 28 23:59:59 2026 GMT
10.20.2.13 notAfter=Oct 10 23:59:59 2026 GMT
```

這段迴圈示範了分半法在多副本上的用法：從外面打 `rt.shengsheng.example` 只會隨機落在其中一台，看起來「有時候正常」；繞過 LB、逐一指定後端 IP，差異立刻浮現。第三台的到期日比其他兩台早，是 7 月簽發、沒有被換下的舊憑證（第 19 章），再過 9 天就會造成「三分之一的連線失敗」這種最難查的間歇性事故。

| 錯誤訊息（Python／openssl） | 瀏覽器常見代碼 | 代表什麼 | 第一個檢查 |
|---|---|---|---|
| `certificate has expired`（10） | `ERR_CERT_DATE_INVALID` | leaf 或中間憑證過期 | `x509 -dates`，逐一檢查每個副本 |
| `certificate is not yet valid`（9） | `ERR_CERT_DATE_INVALID` | 憑證尚未生效，多半是 client 時鐘錯 | 看 client 的系統時間 |
| `unable to get local issuer certificate`（20） | 多數桌面瀏覽器可能仍正常 | 鏈不完整，或 client 不信任這個 CA | `-showcerts` 數憑證張數；內部 CA 則檢查 cafile |
| `Hostname mismatch` | `ERR_CERT_COMMON_NAME_INVALID` | SAN 不涵蓋這個名稱，或 SNI 沒送、拿到預設憑證 | 確認 `-servername`；看 SAN 列表 |
| `self-signed certificate in certificate chain`（19） | `ERR_CERT_AUTHORITY_INVALID` | 鏈上有不被信任的根，常見於公司代理或內部 CA | 比對 issuer；確認是否被中間設備換了憑證 |

**根因與修正**。根因是流程假設過時：手動「一年換一次」碰上 200 天的效期上限（第 19 章），加上沒有任何監控從外面看「每個端點此刻實際送出的憑證」。修正是改用 LB 受管憑證，上傳時一律用 fullchain。**預防**：外部到期監控要逐一連到每一個副本的 IP 並帶正確 SNI（第 19 章的實驗一）；告警門檻依效期比例設定，而不是固定「剩 30 天」。最後還有第 18 章的提醒：遇到內部 CA 造成的 `unable to get local issuer certificate`，正解是把內部 CA 加進該 context 的信任錨，絕不是關掉驗證。

## 45.6 案例三：連線逾時 vs 被拒

**症狀**。演練同時注入兩個故障。教室白板連不上，rt 的 nginx error log 寫著 `connect() failed (111: Connection refused) while connecting to upstream`，upstream 欄位指向即時 gateway gw-41 的 10.20.1.41:8001（`/ws/classroom/8812`）；同一時間，教室入口 API 的 nginx 則是 `upstream timed out (110: Connection timed out) while connecting to upstream`。兩個錯誤都在說「連不上 upstream」，小晴一開始把它們當成同一件事。

**初步觀察**。兩個訊息的關鍵差別在括號裡的 errno：111 是 `ECONNREFUSED`，110 是 `ETIMEDOUT`（Linux 的編號）。第 10 章教過，這兩者幾乎沒有共同的成因：被拒代表**封包到了對方主機，對方核心回了 RST**；逾時代表**封包沒有得到任何回應**。

```text
 (a) refused：一個 RTT 內失敗               (b) timeout：等到放棄                (c) 連上了但沒回應
 nginx            uvicorn 主機              nginx            API 主機             nginx            API 主機
   │── SYN ────────►│ 沒人聽 :8001           │── SYN ────╳     │ 被 SG 丟掉        │── SYN ────────►│ 核心完成交握
   │◄──── RST ──────│                         │── SYN（重傳）╳   │ 或 accept queue 滿 │◄─ SYN+ACK ─────│
   │ ECONNREFUSED                             │── SYN（重傳）╳   │                   │── ACK、請求 ──►│ worker 全卡住
   │ 約 1 ms                                  │ ETIMEDOUT        │                   │   ……沒有回應   │
                                              │ 等到 connect 逾時                    │ read timeout（504）
```

三種情況各有時間特徵。(a) 失敗得很快，大約一個 RTT；(b) 會卡到 connect 逾時才放棄，如果程式沒設 connect timeout，Linux 上可能卡兩分鐘；(c) 是常被混為一談的第三種：連線成功，但應用程式沒回應，nginx 記的會是「while reading response header」而不是「while connecting」，指向的是應用程式的 worker（第 10、42 章），而不是網路。

**假設與驗證**。對 (a) 的假設是「uvicorn 沒有在 10.20.1.41:8001 上 listen」。預測：從 nginx 主機用 nc 測會立刻被拒，在 uvicorn 主機上 `ss -ltn` 看到的 listen 位址不是 VPC IP。

```bash
nc -vz -w 3 10.20.1.41 8001               # 在 rt nginx 主機 10.20.2.11 上
ss -ltnp 'sport = :8001'                  # 在 gateway gw-41（10.20.1.41）上
# ↓ 示意輸出
nc: connect to 10.20.1.41 port 8001 (tcp) failed: Connection refused
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN 0      2048   127.0.0.1:8001      0.0.0.0:*         users:(("uvicorn",pid=4121,fd=3))
```

uvicorn 綁的是 127.0.0.1。這是第 31 章「nginx 與 uvicorn 在同一台主機」時代的設定，第 42 章把 uvicorn 搬到獨立的即時 gateway（gw-41、gw-42）後，演練環境的部署範本沒有跟著改。修正是讓 uvicorn 綁 VPC 位址，並用 security group 只允許 rt nginx 的三台主機連 8001。第 33 章擴充後，每台 gateway 改由本機 nginx（:8080）經 Unix socket 轉給 uvicorn，同一類錯誤會換一種寫法：nginx 記的是 `connect() to unix:/run/rt/uvicorn-1.sock failed (2: No such file or directory)` 或 `(13: Permission denied)`，代表 socket 檔不存在或權限不對，檢查方法從 `ss -ltn` 換成 `ss -lx` 與 `ls -l /run/rt/`。

對 (b) 的假設有兩個方向，必須用封包分開：SYN 根本沒抵達（security group、network ACL、路由，第 7、8、44 章），或 SYN 抵達了但核心不回應（accept queue 滿，第 10 章）。在目標主機上抓 SYN 就能一刀切開：

```bash
sudo tcpdump -ni eth0 -c 4 'tcp[tcpflags] & tcp-syn != 0 and port 8000'   # 在 API 主機 10.20.1.25 上
ss -ltn 'sport = :8000' ; nstat -az TcpExtListenOverflows
# ↓ 示意輸出
20:01:12.401 IP 10.20.3.11.40312 > 10.20.1.25.8000: Flags [S], seq 3011..., length 0
20:01:13.405 IP 10.20.3.11.40312 > 10.20.1.25.8000: Flags [S], seq 3011..., length 0
State   Recv-Q  Send-Q  Local Address:Port
LISTEN  2049    2048    10.20.1.25:8000
TcpExtListenOverflows           184327             0.0
```

同一個來源 port 的 SYN 在 1 秒後重傳，而且中間沒有任何 SYN+ACK，代表 SYN 有抵達、核心卻選擇不回應；`Recv-Q 2049` 大於 `Send-Q 2048`、`ListenOverflows` 持續增加，證實 accept queue 滿了，這正是第 10 章的 CLOSE_WAIT 事故。如果 tcpdump 什麼都抓不到，就往外一層去查 security group 與 network ACL。

| 結果 | 時間特徵 | 封包上看到 | 常見原因 | 對應章節 |
|---|---|---|---|---|
| refused | 約一個 RTT | SYN → RST | 服務沒起來、port 錯、只聽 127.0.0.1、防火牆 REJECT | 第 7、10 章 |
| connect timeout | 卡到逾時（SYN 重傳 1、3、7 秒…） | SYN 沒有回應 | security group、NACL、路由、DROP、accept queue 滿、目標主機已不存在（例如舊 IP） | 第 6、7、10、14 章 |
| 連上但沒回應 | 交握很快，卡在讀取 | 交握完成，請求送出後只有 ACK | worker 卡住、阻塞的 event loop、上游慢 | 第 10、42、43 章 |

**預防**。部署範本把 listen 位址與 port 列為必填，上線後的 smoke test 從**另一台主機**連線，而不是在本機打 127.0.0.1；health check 改成真正會走過應用程式的 HTTP 端點（第 25 章），因為 TCP health check 證明的只是「核心在聽」。

## 45.7 案例四：間歇性 connection reset

**症狀**。演練把 nginx 的 `keepalive_timeout` 從 75 秒改成 30 秒，模擬「有人為了省連線數調低了它」。接下來的兩小時，API 大約有 0.5% 的請求失敗，LB 的 log 記錄 502，部分 App 顯示「連線已重設」。單獨用 curl 怎麼打都正常。

**初步觀察**。間歇性問題最重要的觀察是**它和什麼相關**。小晴把失敗請求的時間點畫出來，發現離峰時段的失敗率反而比尖峰高；失敗的請求都落在「某條 LB 到 nginx 的連線閒置了一段時間之後的第一個請求」。和流量成反比、和閒置相關，這兩個特徵幾乎只指向一種原因：**連線重用與閒置逾時的時序**。

**假設**。LB 會重用到 nginx 的閒置連線，它的閒置上限是 60 秒（第 43 章的設定）；nginx 現在 30 秒就關閉閒置連線。所以在第 30 到 60 秒之間，LB 手上有一批 nginx 已經關掉、自己卻還以為能用的連線。預測：在 nginx 主機上抓 FIN 與 RST，會看到 nginx 在閒置 30 秒時送 FIN，稍後 LB 在同一條連線送出請求，nginx 回 RST。

```bash
sudo tcpdump -ni eth0 'host 10.20.16.5 and port 80 and (tcp[tcpflags] & (tcp-fin|tcp-rst) != 0)'
# ↓ 示意輸出（10.20.16.5 是 API LB 在 VPC 內的位址，10.20.3.11 是 nginx；TLS 已在 LB 終結，這段是 port 80）
21:14:02.118 IP 10.20.3.11.80 > 10.20.16.5.51830: Flags [F.], seq 8812, ack 4410, length 0
21:14:02.119 IP 10.20.16.5.51830 > 10.20.3.11.80: Flags [P.], seq 4410:5021, ack 8812, length 611
21:14:02.119 IP 10.20.3.11.80 > 10.20.16.5.51830: Flags [R], seq 8813, length 0
```

三行封包就是整個事故。第一行 nginx 送出 FIN，關閉一條閒置剛好 30 秒的連線；第二行在不到 1 毫秒後，LB 恰好把一個新請求送進同一條連線，因為 FIN 還在路上，LB 不知道連線已經關了；第三行 nginx 對一條已關閉的連線收到資料，只能回 RST。LB 收到 RST 後回 502 給使用者。這個競態每次只有幾毫秒的窗口，所以頻率不高、用 curl 永遠重現不了。

```text
 重用方（LB，閒置上限 60 秒）                       關閉方（nginx，keepalive_timeout 30 秒）
   │── 請求 A ───────────────────────────────────────────────►│
   │◄─────────────────────────────────────────── 回應 A ──────│
   │                    （閒置 30 秒）                         │ 計時到期
   │                                                ┌── FIN ──│ close()
   │── 請求 B（以為連線還能用）───────────────────►│          │
   │◄─────────────────────────────────── RST ───────┘          │ 「這條連線已經關了」
   │ 回 502 給使用者
 規則：重用方的閒置上限必須「短於」關閉方，讓關閉永遠由重用方發起
```

這張圖說明了為什麼 nginx 的 `keepalive_timeout` 原本設成 75 秒：它比 LB 的閒置上限長，所以閒置連線一定是 LB 先關，LB 永遠不會拿到被 nginx 關掉的連線。同一條規則也適用在第 10 章的 CLOSE_WAIT 事故：教室入口 API 的連線池（重用方）沒有閒置上限，課表服務（關閉方）60 秒就關閉閒置連線，於是池子裡堆滿 CLOSE_WAIT，下一個請求拿到死連線就得到空回應或 reset。

下面這段程式把聲聲 Live 路徑上的重用關係列成清單，自動檢查兩條規則：重用方的閒置上限要短於關閉方；長連線的心跳要明顯短於路徑上最短的閒置逾時。

```python
# 每一條「會被重用的連線」都有兩端：重用它的一方（client 端連線池）與會關掉閒置連線的一方。
# 規則一：重用方的閒置上限必須比關閉方短，否則池子裡遲早會拿到對方剛關掉的連線。
# 規則二：長連線的心跳間隔必須比路徑上最短的閒置逾時短，而且最好留 2 倍以上餘裕。
REUSE_PAIRS = [
    # (重用方, 重用方閒置上限 秒, 關閉方, 關閉方閒置逾時 秒, 出處)
    ("API LB → nginx", 60, "nginx keepalive_timeout", 75, "第 20、25 章"),
    ("教室入口 API 連線池（事故時）", float("inf"), "課表服務閒置關閉", 60, "第 10 章"),
    ("教室入口 API 連線池（修正後）", 50, "課表服務閒置關閉", 60, "第 10 章"),
    ("API LB → nginx（演練注入）", 60, "nginx keepalive_timeout", 30, "本章 45.7"),
]
LONG_LIVED = [
    # (連線, 心跳間隔 秒或 None, 路徑上每一層的閒置逾時)
    ("教室 WebSocket", 25, {"nginx proxy_read_timeout": 75, "rt LB idle": 120}),
    ("教室 WebSocket（演練：心跳停用）", None, {"nginx proxy_read_timeout": 60, "rt LB idle": 120}),
    ("等候室 SSE", 15, {"rt LB idle": 120, "nginx proxy_read_timeout（SSE 路徑）": 3600}),
]

problems = 0
for reuser, r_idle, closer, c_idle, ref in REUSE_PAIRS:
    ok = r_idle < c_idle
    problems += not ok
    limit = "無上限" if r_idle == float("inf") else f"{r_idle}s"
    verdict = "OK" if ok else f"關閉方先關，重用方還會拿來用 → 間歇性 reset／空回應"
    print(f"▸ {reuser}：重用 {limit}／關閉 {c_idle}s → {verdict}（{ref}）")

for conn, beat, layers in LONG_LIVED:
    shortest_name, shortest = min(layers.items(), key=lambda kv: kv[1])
    if beat is None:
        verdict = f"沒有心跳：安靜 {shortest}s 後被 {shortest_name} 切斷"
    elif beat * 2 > shortest:
        verdict = f"心跳 {beat}s 太接近 {shortest_name} {shortest}s，掉一次心跳就斷"
    else:
        verdict = f"OK（心跳 {beat}s，最短逾時 {shortest_name} {shortest}s）"
    problems += not verdict.startswith("OK")
    print(f"▸ {conn}：{verdict}")

assert problems == 3
```

間歇性 reset 不只這一種。第 7 章的白板在 NAT 或防火牆的閒置逾時之後失去回應；第 3 章的高中電腦教室則是內容過濾設備在 ClientHello 之後偽造 RST，證據是那個 RST 的 IP TTL 和 SYN+ACK 的 TTL 不一致，代表它來自路徑上另一台設備，而不是聲聲 Live 的伺服器。所以面對 reset，第一個問題永遠是「**RST 是誰送的**」：在兩端同時抓包，看 RST 是從哪一端出發，再比對 TTL 判斷是否被中間設備插手。**預防**：所有連線池都設定閒置上限並短於上游；把上一段程式的清單放進設定審查；監控 `ss -tan state close-wait` 的數量與 LB 的「後端連線被重設」計數。

## 45.8 案例五：慢──把一次請求切成五段

**症狀**。「課表頁很慢」是最模糊的工單。演練準備了四位使用者的回報，每一位的「慢」都來自不同的地方。

**初步觀察與方法**。「慢」不能直接查，要先切開。第 3 章的 `curl -w` 把一次請求切成五段：DNS、TCP 交握、TLS 交握、等第一個 byte（TTFB）、下載 body。瀏覽器 DevTools 的 Timing 分頁有對應的欄位：DNS Lookup、Initial connection、SSL、Waiting for server response、Content Download，另外還有 Queueing 與 Stalled，代表請求還沒送出就在排隊，常見原因是 HTTP/1.1 每個來源的連線數上限（第 22、31 章）。

```text
 0      DNS        TCP 交握       TLS 交握       等第一個 byte              下載 body       完成
 │──────────│──────────────│──────────────│──────────────────────────│───────────────│
   resolver    約 1 RTT       1–2 RTT        RTT＋伺服器處理＋上游        頻寬、視窗、大小
   search      SYN 重傳       憑證鏈、        nginx $upstream_header_time  BDP、sndbuf、壓縮
   5 秒逾時    accept queue   終結點 CPU      Flask、DB、下游服務          CDN 命中
   第 14–16 章 第 6–8、10 章  第 18、19 章   第 20、24、43 章             第 11、12、21、25 章
```

每一段都有自己的嫌疑名單，所以切開之後，問題就從「網站慢」變成「TTFB 2.3 秒」這種可以行動的句子。讀 `curl -w` 時記得它的時間是累計值，必須相鄰相減（第 3 章）。下面這段程式把四份 `curl -w` 的結果切成五段，指出最大的一段，並加上兩個經驗線索：交握遠大於 RTT 代表 SYN 可能被重傳；下載很慢時用「吞吐 × RTT」反推出等效視窗，看它是否卡在某個 buffer 上限。

```python
# curl -w 的時間都是「從開始累計」，相鄰相減才是每一段的長度（第 3 章）
FIELDS = ["time_namelookup", "time_connect", "time_appconnect", "time_starttransfer", "time_total"]
SEGMENTS = [("DNS", "第 14–16 章：resolver、search domain、5 秒逾時"),
            ("TCP 交握", "第 6–8、10 章：RTT、SYN 重傳、accept queue"),
            ("TLS 交握", "第 18、19 章：憑證鏈、終結點過載、RTT"),
            ("等第一個 byte", "第 20、24、43 章：應用程式、上游、DB"),
            ("下載 body", "第 11、12、21、25 章：頻寬、buffer、壓縮、CDN")]


def split(sample: dict, rtt_ms: float):
    marks = [0.0] + [sample[f] for f in FIELDS]
    lengths = [(b - a) * 1000 for a, b in zip(marks, marks[1:])]
    worst = max(range(5), key=lambda i: lengths[i])
    hints = []
    if lengths[1] > 3 * rtt_ms:                     # 交握應該約 1 個 RTT，多出整秒就是 SYN 重傳
        hints.append("交握遠大於 RTT：SYN 可能被丟後重傳")
    if 4900 <= lengths[0] <= 5200:
        hints.append("DNS 剛好 5 秒：resolver 逾時後重送")
    if "size_download" in sample and lengths[4] > 1000:
        mbps = sample["size_download"] * 8 / (lengths[4] / 1000) / 1e6
        window_kib = mbps * 1e6 / 8 * rtt_ms / 1000 / 1024   # 吞吐 × RTT ＝ 每個 RTT 在路上的資料量
        hints.append(f"吞吐 {mbps:.1f} Mbps，等效視窗約 {window_kib:.0f} KiB：查 buffer 與視窗（BDP）")
    return lengths, worst, hints


CASES = {  # (curl -w 示意值, 這條路徑平常的 RTT ms)
    "課表頁慢（第 3 章）": ({"time_namelookup": 0.004, "time_connect": 0.032, "time_appconnect": 0.094,
                     "time_starttransfer": 2.381, "time_total": 2.402}, 28),
    "金流 webhook 卡 5 秒（第 16 章）": ({"time_namelookup": 5.012, "time_connect": 5.030,
                                "time_appconnect": 5.090, "time_starttransfer": 5.210, "time_total": 5.214}, 18),
    "尖峰時 connect 慢（第 10 章）": ({"time_namelookup": 0.002, "time_connect": 1.004, "time_appconnect": 1.010,
                              "time_starttransfer": 1.046, "time_total": 1.047}, 1),
    "歐洲學生下載回放（第 12 章）": ({"time_namelookup": 0.030, "time_connect": 0.282, "time_appconnect": 0.535,
                             "time_starttransfer": 0.800, "time_total": 400.8,
                             "size_download": 105_000_000}, 250),
}
worsts = []
for title, (sample, rtt) in CASES.items():
    lengths, worst, hints = split(sample, rtt)
    worsts.append(worst)
    bars = " ".join(f"{name}={ms:.0f}" for (name, _), ms in zip(SEGMENTS, lengths))
    print(f"■ {title}\n   {bars}（ms）")
    print(f"   最大段：{SEGMENTS[worst][0]} → {SEGMENTS[worst][1]}")
    for h in hints:
        print(f"   線索：{h}")
assert worsts == [3, 0, 1, 4]
```

```text
■ 課表頁慢（第 3 章）
   DNS=4 TCP 交握=28 TLS 交握=62 等第一個 byte=2287 下載 body=21（ms）
   最大段：等第一個 byte → 第 20、24、43 章：應用程式、上游、DB
■ 金流 webhook 卡 5 秒（第 16 章）
   DNS=5012 TCP 交握=18 TLS 交握=60 等第一個 byte=120 下載 body=4（ms）
   最大段：DNS → 第 14–16 章：resolver、search domain、5 秒逾時
   線索：DNS 剛好 5 秒：resolver 逾時後重送
■ 尖峰時 connect 慢（第 10 章）
   DNS=2 TCP 交握=1002 TLS 交握=6 等第一個 byte=36 下載 body=1（ms）
   最大段：TCP 交握 → 第 6–8、10 章：RTT、SYN 重傳、accept queue
   線索：交握遠大於 RTT：SYN 可能被丟後重傳
■ 歐洲學生下載回放（第 12 章）
   DNS=30 TCP 交握=252 TLS 交握=253 等第一個 byte=265 下載 body=400000（ms）
   最大段：下載 body → 第 11、12、21、25 章：頻寬、buffer、壓縮、CDN
   線索：吞吐 2.1 Mbps，等效視窗約 64 KiB：查 buffer 與視窗（BDP）
```

四份結果對應四種完全不同的修法。第一份是第 3 章的課表頁：網路各段都很小，2.3 秒全在等第一個 byte，下一步拿 `x-request-id` 去 nginx 與 Flask 的 log 找慢查詢，網路工程師可以退場。第二份是第 16 章的 webhook：DNS 剛好 5 秒，正是 glibc resolver 的預設逾時，指向第一台 nameserver 不回應或 A／AAAA 查詢遇到 conntrack 競態。第三份的交握花了 1002 毫秒，而 VPC 內的 RTT 只有 1 毫秒，多出來的整整一秒就是 Linux SYN 重傳的初始逾時，代表第一個 SYN 被丟了，往 accept queue 或防火牆查（45.6 節）。第四份是第 12 章的歐洲學生：其他段都約一個 RTT，下載卻跑了 400 秒；反推出的等效視窗正好 64 KiB，對上 nginx 那行 `sndbuf=64k`。

TTFB 還可以再切。它包含一個 RTT 加上伺服器端的時間，而伺服器端又能用 nginx 的 `$upstream_connect_time`、`$upstream_header_time` 與 `$request_time` 拆成「nginx 連 upstream」「upstream 產生 header」「整個請求」三段；應用程式也可以回 `Server-Timing` header，把 DB、下游呼叫各花多少時間交給瀏覽器的 DevTools 顯示。**預防**：合成監測（第 20 章）每次都記錄五段時間而不是只記總時間；告警依「哪一段變大」分流給不同的團隊。

## 45.9 案例六：CORS 錯誤

**症狀**。演練重現第 23 章預約試聽上線那天的兩個問題：學生在 `www` 的預約頁按下按鈕沒有反應，Console 寫著 `Response to preflight request doesn't pass access control check`；老師後台 `teach` 則偶爾出現 CORS 錯誤，重新整理又好了。第 23 章當時的 preflight 拿到的是沒有任何 `Access-Control-*` 的 200；阿德這次刻意換成另一個常見的變形：讓驗證 middleware 擋下 OPTIONS，看值班的人能不能從 status 分辨出差別。

**初步觀察**。CORS 錯誤有兩個先天的特徵。第一，它是**瀏覽器**執行的規則：同一個 API 用 curl 打完全正常，所以「curl 正常、瀏覽器失敗」本身就是指向 CORS、HSTS、快取或擴充功能這類瀏覽器專屬規則的證據。第二，瀏覽器把被擋下的回應藏起來，Console 只說「被 CORS 擋了」，**不說 server 回了什麼**。所以第一步永遠是打開 Network 面板，看 OPTIONS 與實際請求的 status：一個 502 或 500 只要沒帶 CORS header，也會被報成 CORS 錯誤，這時該修的是 502。

```text
 www 的頁面（瀏覽器）                           api.shengsheng.example
   │── ① OPTIONS /v1/bookings ───────────────────►│ Origin: www
   │     Access-Control-Request-Method: POST       │ Access-Control-Request-Headers:
   │                                               │   authorization, content-type
   │◄── ② 回應：status？Allow-Origin？Allow-Headers？│
   │   ✗ 401（驗證 middleware 擋了 OPTIONS）
   │   ✗ 200 但沒有 Access-Control-Allow-Origin
   │   ✗ Allow-Headers: *（不涵蓋 authorization）
   │   ✓ 204＋允許清單內的 origin＋明列 authorization
   │── ③ 只有 ② 通過，才會送出真正的 POST ─────────►│
```

這張時序圖標出 preflight 最常失敗的三個位置。① 是瀏覽器自動送出的 OPTIONS，帶著「我等一下要用 POST、要帶 authorization 與 content-type」的詢問；② 是 server 的回答，三種失敗分別是驗證 middleware 擋下沒有 token 的 OPTIONS、根本沒有 CORS header，以及用 `*` 以為能涵蓋 `Authorization`（第 23 章）。③ 只有 preflight 通過才會發生，所以後端 log 裡「完全看不到那個 POST」也是 preflight 失敗的證據。

**驗證**。用 curl 模擬瀏覽器的 preflight，把 `Origin` 與兩個 `Access-Control-Request-*` header 帶齊：

```bash
curl -si -X OPTIONS https://api.shengsheng.example/v1/bookings \
  -H 'Origin: https://www.shengsheng.example' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: authorization, content-type' | head -8
curl -si https://api.shengsheng.example/v1/courses -H 'Origin: https://teach.shengsheng.example' \
  | grep -iE '^(access-control|vary|age|cache-control)'
# ↓ 示意輸出
HTTP/2 401
www-authenticate: Bearer
content-type: application/problem+json

access-control-allow-origin: https://www.shengsheng.example
cache-control: public, max-age=60
age: 31
```

第一個請求的 401 與 `www-authenticate` 證明是驗證 middleware 擋下了 OPTIONS：preflight 規定不帶 credentials，當然沒有 token。第二個請求從 `teach` 的 origin 去要公開的課程列表，拿到的 `access-control-allow-origin` 卻是 www 的 origin，`age: 31` 表示這份回應已經在 CDN 快取裡放了 31 秒；再看回應沒有 `Vary: Origin`，就能解釋「偶爾」：CDN 用同一個 cache key 存下第一個請求者的版本，交給下一個不同 origin 的請求。

**根因與修正**。第一個問題：在驗證之前處理 `OPTIONS`，回 204 與允許清單內的 origin，明列 `authorization`、`content-type`、`x-csrf-token`，`Max-Age: 600`（第 23 章的設定）。第二個問題：所有依 origin 回寫的 CORS 回應都加 `Vary: Origin`；真正公開、不帶 credentials 的資源則固定回 `*`，讓快取不必分版本。**預防**：把「用不在允許清單的 Origin 打一次，確認不會被回寫」與「preflight 不帶 token 也回 204」寫進 API 的整合測試；第 45.13 節的診斷工具也會檢查這兩種錯誤的 header 組合。

## 45.10 案例七：WebSocket 斷線

**症狀**。演練把 staging 的 WebSocket 心跳停用，重現第 32 章常見錯誤表裡的那一列。工單寫著：「上課到一半一直跳『重新連線中』，但大家都在講話的時候不會。」

**初步觀察**。WebSocket 斷線的第一個證據是 **close code**，第二個證據是**斷線的時間點**。前端的錯誤回報顯示幾乎都是 1006（沒有收到 close frame 就斷了），這代表不是 server 程式主動關閉，而是路徑上某一層切斷了連線。小晴把每次斷線前「最後一則訊息的時間」與「斷線時間」相減，得到的間隔集中在 60 秒附近；熱鬧的教室從來不斷，安靜的教室每分鐘斷一次。

**假設**。路徑上某一層有 60 秒的閒置逾時，而連線上 60 秒沒有任何資料。預測：nginx 的 `/ws/classroom/` location 沒有設定 `proxy_read_timeout`（預設 60 秒），server 端沒有送 ping；在 nginx 與 uvicorn 之間抓包，會看到 nginx 在最後一個封包後整整 60 秒送出 FIN。

```bash
grep -n -A8 'location /ws/classroom/' /etc/nginx/conf.d/rt.conf | grep -E 'proxy_read_timeout|Upgrade'
sudo tcpdump -ni eth0 'host 10.20.1.41 and port 8001'      # 在 rt nginx 主機 10.20.2.11 上，節錄斷線前後
# ↓ 示意輸出
14:    proxy_set_header Upgrade $http_upgrade;
20:31:05.204 IP 10.20.1.41.8001 > 10.20.2.11.48120: Flags [P.], length 41      ← 最後一則聊天
20:32:05.205 IP 10.20.2.11.48120 > 10.20.1.41.8001: Flags [F.], length 0       ← 剛好 60 秒後 nginx 關閉
20:32:05.206 IP 10.20.1.41.8001 > 10.20.2.11.48120: Flags [F.], length 0
```

grep 只找到 `Upgrade` 那一行，沒有 `proxy_read_timeout`，所以用的是預設 60 秒；封包顯示最後一則訊息在 20:31:05，nginx 在 20:32:05 送出 FIN，間隔正好 60 秒。nginx 關掉的是它到 uvicorn 的那一段，也同時中止了瀏覽器那一段，而沒有人送出 WebSocket 的 close frame，瀏覽器只能回報 1006。

```text
 時間 →  20:31:05 最後一則訊息                                20:32:05
 瀏覽器 ════════════════ 沒有任何 frame ════════════════════════╳ onclose code=1006
 rt LB（idle 120 s）    ………………計時中，還沒到……………………………………………
 nginx（read 60 s）     ………………計時中…………………………………………………………► 到期，關閉兩側連線
 uvicorn（心跳停用）     不送 ping
 正常設定：每 25 s 一個 ping ─┬───────┬───────┬──► 每一層的計時器都被重設，永遠碰不到
```

這張時間軸對應 45.7 節程式的「規則二」：長連線不是靠把每一層的逾時調長來保護，而是靠心跳讓每一層的計時器都碰不到。**根因與修正**：心跳停用加上 nginx 預設逾時。恢復 server 每 25 秒 ping、20 秒沒有 pong 即關閉，並把 `/ws/` 的 `proxy_read_timeout` 設為 75 秒（第 32、33 章的設定）。

1006 只是 WebSocket 斷線的一種。演練的後半段，阿德把第 32、33、42 章的另外三種斷線也放了進來，要小晴只靠 close code 與時間點分類：

| close code | 誰送的 | 時間特徵 | 典型原因 | 對應章節 |
|---|---|---|---|---|
| 1006 | 沒人送（連線被切斷） | 閒置固定秒數後；或換網路時 | 某層 idle timeout 短於心跳、NAT 清表、行動網路切換 | 第 7、32、33 章 |
| 1009 | 收訊方（多半是 server） | 某個大訊息送出後立刻斷，重連後又斷 | 訊息超過上限，前端重連後又重送同一則 | 第 32 章 |
| 1001／1012 | server | 集中在部署時間，所有教室同時 | 例行部署；處理不好會變成重連驚群 | 第 31、33 章 |
| 4001 | server（聲聲 Live 自訂） | 連線剛好滿 15 分鐘 | 連線授權到期，前端應換票重連 | 第 32 章 |
| 1006 大量、伴隨 health check 失敗 | 沒人送 | 尖峰時兩台輪流全斷 | event loop 被阻塞，health check 逾時，節點被移出 LB | 第 42 章 |

這張表的用法和 45.6 節的 errno 一樣：先用 close code 決定是誰關的，再用時間點決定是哪一種原因。**預防**：前端把每次 `onclose` 的 code、reason、`wasClean` 與「距離上一則訊息的秒數」送進錯誤回報；監控 1006 的比例並依時段比對部署紀錄；任何新的 location 或 LB listener 上線時，用 45.7 節的清單檢查心跳與逾時。

## 45.11 案例八：視訊單向（看不到、聽不到）

**症狀**。最後兩張工單一起出現。第一張重現第 35 章：小班課老師 `teacher05` 的畫面上有兩格學生是黑的，「學生看得到老師，老師看不到學生」。第二張重現第 39 章：學生小安說「我看得到美咲老師的嘴巴在動，可是沒有聲音」。兩張都是**單向**的問題，客服的第一反應都是「學生網路不好」。

**初步觀察**。阿德先問了一句：「如果是網路不好，為什麼只壞一個方向？」WebRTC 的媒體在聲聲 Live 是 BUNDLE 在同一組 ICE candidate pair 上（第 35 章），也就是音訊、視訊、兩個方向全部走同一個 UDP 五元組到 SFU 的 203.0.113.60:40000；ICE 的 consent 檢查又是雙向的（第 36 章），路徑只要有一個方向不通，整條連線都會失敗。所以**純網路層造成的單向問題在 WebRTC 中很少見**，單向症狀絕大多數指向上層：SDP 協商、SFU 轉送、送端的 track，或收端的播放。網路的角色是先被快速排除。

```text
 檢查順序（由下而上，每一站都是是非題）                  黑格子（第 35 章）   沒聲音（第 39 章）
 ① ICE／DTLS 狀態是 connected？                            是                   是
 ② candidate-pair 的 bytesSent、bytesReceived 都在增加？   是                   是       ← 到這裡為止，網路沒問題
 ③ 這一路的 SDP：m-line 被接受了嗎？方向對嗎？             m=video 0（被拒）    是
 ④ 送端 outbound-rtp 的 packetsSent 在增加？               沒有 outbound video  是
 ⑤ SFU 有把這一路轉給收端？                                -                    是
 ⑥ 收端 inbound-rtp 的 packetsReceived 與 audioLevel？      -                    都在動
 ⑦ 播放：play() 成功？元素沒被 muted？                      -                    play() 被 autoplay 擋下
```

這張檢查表把第 39 章「沿著媒體管線逐站確認」的方法，加上網路層的兩站放在最前面。① 與 ② 從 `chrome://webrtc-internals` 或 getStats 的 `transport` 與 `candidate-pair` 讀取（第 39 章）。兩張工單在 ② 都是「是」：兩個方向的 bytes 都在增加，網路排除。之後兩張工單分道揚鑣。黑格子在 ③ 就停下：SFU 的 answer 把學生的視訊 m-line 的 port 設成 0，原因是前端 munging 只留下 PT 98，而 98 是 rtx，SFU 以 `no_primary_codec` 拒絕（第 35 章），於是學生端根本沒有 outbound video 這一路。沒聲音則一路走到 ⑦：封包有、音量也有，是收端 `<audio>` 的 `play()` 被 autoplay 政策擋下，而前端沒有處理那個被 reject 的 Promise（第 39 章）。

**驗證**。黑格子的證據在 SFU 的 log 與 SDP：

```bash
grep 'session=8812/student-0457' /var/log/sfu/sfu.log | grep -E 'rejecting|no supported'
# ↓ 示意輸出
2026-10-01T20:14:52+08:00 sfu-60 session=8812/student-0457 mid=1 kind=video
  offer pts=[98] codecs={98: rtx/90000 apt=97} -> no supported primary codec, rejecting m-line (port 0)
```

這一行 log 和第 35 章完全相同，它把「網路不好」的猜測變成一個明確的 SDP 錯誤。沒聲音的證據則在小安的瀏覽器：`inbound-rtp`（audio）的 `packetsReceived` 每秒增加約 50 個，`audioLevel` 在 0.1 上下，Console 有一行 `NotAllowedError: play() failed because the user didn't interact with the document first`。兩者都和網路無關。

為了對比，下表列出 WebRTC 中真正由網路造成的問題。它們幾乎都是**雙向**的：要嘛整條連不上，要嘛兩個方向一起變差。

| 症狀 | 網路層的原因 | 證據 | 對應章節 |
|---|---|---|---|
| 完全連不上、ICE failed | UDP 被企業防火牆擋、TURN 沒設或憑證錯 | candidate-pair 全部 failed；沒有 relay candidate | 第 7、36、37 章 |
| 只在某台新 SFU 上的教室連不上 | TURN 的 `allowed-peer-ip` 沒有包含新節點 | 走 relay 的使用者失敗，直連的正常 | 第 37 章 |
| 雙向都卡、RTT 高、丟包低 | TURN over TLS 走 TCP、bufferbloat | `relayProtocol: tls`、RTT 高而丟包低 | 第 12、39 章 |
| 換網路後整條斷掉再重建 | NAT 映射改變、ICE restart | consent 失敗、ICE 狀態變 disconnected | 第 7、36 章 |

**根因、修正與預防**。黑格子：移除 SDP munging，改用 `setCodecPreferences` 這類標準 API 調整 codec 順序；SFU 拒絕 m-line 時，除了寫 log，也透過 signaling 通知前端顯示錯誤，讓「靜悄悄的黑格子」變成看得見的告警。沒聲音：處理 `play()` 的 rejection，顯示「點一下開啟聲音」。共同的預防是教室頁的「回報問題」按鈕自動附上最近五分鐘的 getStats 摘要，讓第一線一開始就拿得到 ① 到 ⑦ 的答案。

| 單向看不到或聽不到 | SDP 拒絕或方向錯、SFU 沒轉、track 停用、autoplay | candidate-pair 雙向 bytes，再逐站看 RTP 統計 | 第 35、39 章、45.11 |

表格刻意把「看到別人的資料」「被限速 429」這類看起來不像網路問題的症狀也放進來，因為它們的根因都在 HTTP 快取與 proxy 的語意上，值班時同樣會被歸到「網路怪怪的」。另一個刻意的安排是第三欄幾乎都能在一分鐘內執行完，而且執行之後只有兩種結果，這讓表格可以當成分半法的起點。

## 45.13 動手做：寫一個網路診斷小工具

演練結束後，小晴想把 45.3 節流程圖的前半段自動化：給一個 host 與 port，依序做名稱解析、TCP 連線、HTTP 請求，把每一段計時，最後檢查回應 header，輸出一句「是哪一層、往哪一章找」的結論。下面的程式在 127.0.0.1 上同時啟動幾個刻意設計的故障 server：正常的、不回應的、立刻 RST 的、慢回應的、CORS 設錯的，以及一個回應被 CDN 混用的；另外準備一個「確定沒人 listen」的 port，和一個 accept queue 被塞滿、SYN 會被核心丟掉的 listener（第 10 章實驗二的技巧）。

名稱解析用一張假的 DNS 表模擬，讓程式完全離線；真實使用時把它換成 `socket.getaddrinfo` 即可。連線逾時與讀取逾時刻意分開設定，因為它們回答的是兩個不同的問題：前者問「SYN 有沒有回應」，後者問「應用程式有沒有回話」。

```python
import socket
import struct
import threading
import time

ORIGIN = "https://www.shengsheng.example"          # 瀏覽器頁面的 origin（第 23 章的允許清單之一）
CONNECT_TIMEOUT, READ_TIMEOUT = 0.3, 0.5           # 一定要分開設：連線逾時與讀取逾時回答不同問題
STOP = threading.Event()


def respond(conn, headers, body=b"{}", ttfb=0.0, chunks=1):
    """讀掉請求，等 ttfb 秒後送 header，再把 body 分成 chunks 段慢慢送。"""
    conn.recv(4096)
    time.sleep(ttfb)
    head = "HTTP/1.1 200 OK\r\n" + "".join(f"{k}: {v}\r\n" for k, v in headers.items())
    conn.sendall((head + f"Content-Length: {len(body)}\r\nConnection: close\r\n\r\n").encode())
    step = max(1, len(body) // chunks)
    for i in range(0, len(body), step):
        conn.sendall(body[i:i + step])
        time.sleep(0.05 if chunks > 1 else 0)


GOOD = {"Cache-Control": "private, max-age=0", "Access-Control-Allow-Origin": ORIGIN,
        "Access-Control-Allow-Credentials": "true", "Vary": "Origin",
        "Strict-Transport-Security": "max-age=31536000; includeSubDomains; preload"}
BAD_CORS = {"Cache-Control": "public, max-age=60", "Set-Cookie": "__Host-sid=A; Path=/; Secure; HttpOnly",
            "Access-Control-Allow-Origin": "*", "Access-Control-Allow-Credentials": "true"}
CDN_MIXED = {"Cache-Control": "public, max-age=60", "Access-Control-Allow-Origin": ORIGIN,  # 快取裡別人的回應
             "Strict-Transport-Security": "max-age=31536000; includeSubDomains"}


def rst_now(conn):
    conn.setsockopt(socket.SOL_SOCKET, socket.SO_LINGER, struct.pack("ii", 1, 0))  # close 送 RST


HANDLERS = {
    "healthy": lambda c: respond(c, GOOD),
    "slow": lambda c: respond(c, GOOD, body=b"x" * 40_000, ttfb=0.25, chunks=4),
    "reset": rst_now,                               # 一 accept 就 RST，像被中間設備或 crash 中止
    "silent": lambda c: (c.recv(4096), STOP.wait()),  # 收下請求，永遠不回：卡住的 worker
    "bad_cors": lambda c: respond(c, BAD_CORS),
    "cdn_mixed": lambda c: respond(c, CDN_MIXED),
}


def serve(kind):
    lst = socket.socket()
    lst.bind(("127.0.0.1", 0))
    lst.listen(16)

    def loop():
        while True:
            try:
                conn, _ = lst.accept()
            except OSError:
                return
            def run(c=conn):
                with c:
                    HANDLERS[kind](c)
            threading.Thread(target=run, daemon=True).start()
    threading.Thread(target=loop, daemon=True).start()
    return lst


def syn_drop_server():
    """accept queue 塞滿、永不 accept：之後的 SYN 被核心默默丟掉（第 10 章實驗二）。"""
    lst = socket.socket()
    lst.bind(("127.0.0.1", 0))
    lst.listen(1)
    fillers = []
    for _ in range(6):
        c = socket.socket()
        c.settimeout(0.2)
        try:
            c.connect(lst.getsockname())
            fillers.append(c)
        except TimeoutError:
            c.close()                               # 確認佇列已滿就停手
            break
    return lst, fillers


def diagnose(name, port, dns, origin=ORIGIN, path="/v1/me"):
    phases, findings = {}, []
    t0 = time.perf_counter()
    if name not in dns:                             # ① 名稱解析
        return phases, [("DNS", "NXDOMAIN：名稱不存在或負面快取（第 14、15 章）")]
    time.sleep(dns[name][1])                        # 模擬 resolver 的回應時間
    t_dns = time.perf_counter()
    phases["dns"] = t_dns - t0
    sock = socket.socket()
    sock.settimeout(CONNECT_TIMEOUT)
    try:                                            # ② TCP 連線：refused 與 timeout 是兩種世界
        sock.connect((dns[name][0], port))
    except ConnectionRefusedError:
        sock.close()
        return phases, [("TCP", "refused：主機在，但這個 port 沒人 listen（第 10 章）")]
    except TimeoutError:
        sock.close()
        return phases, [("TCP", "connect timeout：SYN 沒有回應，查防火牆或 accept queue（第 7、10 章）")]
    t_conn = time.perf_counter()
    phases["connect"] = t_conn - t_dns
    sock.settimeout(READ_TIMEOUT)
    raw = b""
    try:                                            # ③ HTTP：送出請求、等第一個 byte、下載
        sock.sendall(f"GET {path} HTTP/1.1\r\nHost: {name}\r\nOrigin: {origin}\r\n\r\n".encode())
        first = sock.recv(1)
        if not first:
            return phases, [("HTTP", "連線被正常關閉卻沒有回應（FIN）：worker 中止或 keep-alive 競態（第 10、20 章）")]
        t_first = time.perf_counter()
        phases["ttfb"] = t_first - t_conn
        raw = first
        while chunk := sock.recv(65536):
            raw += chunk
        phases["download"] = time.perf_counter() - t_first
    except (ConnectionResetError, BrokenPipeError):
        return phases, [("TCP", "收到 RST：對方 crash、閒置逾時或中間設備中止（第 10 章）")]
    except TimeoutError:
        return phases, [("APP", f"連線成功但 {READ_TIMEOUT * 1000:.0f} ms 內沒有任何回應：應用程式卡住（第 10、42 章）")]
    finally:
        sock.close()
    head, _, body = raw.partition(b"\r\n\r\n")
    h = {k.strip().lower(): v.strip() for k, _, v in
         (line.partition(":") for line in head.decode().split("\r\n")[1:])}
    cc, acao = h.get("cache-control", ""), h.get("access-control-allow-origin")
    if "public" in cc and "set-cookie" in h:        # ④ header 檢查
        findings.append(("快取", "帶 Set-Cookie 的回應被標成 public：共用快取可能外洩個資（第 21 章）"))
    if acao is None:
        findings.append(("CORS", "沒有 Access-Control-Allow-Origin：瀏覽器會擋下讀取（第 23 章）"))
    elif acao == "*" and h.get("access-control-allow-credentials") == "true":
        findings.append(("CORS", "ACAO 為 * 又允許 credentials：瀏覽器一律拒絕（第 23 章）"))
    elif acao not in ("*", origin):
        findings.append(("CORS", f"ACAO 是別的 origin（{acao}）：多半是快取混用，查 Vary（第 23 章）"))
    if acao not in (None, "*") and "origin" not in h.get("vary", "").lower():
        findings.append(("CORS", "依 origin 回寫 ACAO 卻沒有 Vary: Origin（第 21、23 章）"))
    hsts = h.get("strict-transport-security", "")
    if "max-age=" not in hsts:
        findings.append(("HSTS", "沒有 Strict-Transport-Security（第 19 章）"))
    for seg in sorted(phases, key=phases.get, reverse=True):
        if phases[seg] > 0.15:                      # 超過門檻的每一段都點名，最大的排第一
            findings.append(("效能", f"{seg} 花了 {phases[seg] * 1000:.0f} ms（對照 45.8 節的五段表）"))
    return phases, findings or [("OK", f"HTTP {head.split()[1].decode()}，{len(body)} bytes，header 檢查通過")]


servers = {kind: serve(kind) for kind in HANDLERS}
port = lambda kind: servers[kind].getsockname()[1]
probe = socket.socket()
probe.bind(("127.0.0.1", 0))
dead_port = probe.getsockname()[1]
probe.close()                                       # 一個確定沒人 listen 的 port
drop_lst, fillers = syn_drop_server()
DNS = {"api.shengsheng.example": ("127.0.0.1", 0.004), "rt.shengsheng.example": ("127.0.0.1", 0.004),
       "ops.shengsheng.example": ("127.0.0.1", 0.004), "reco.shengsheng.example": ("127.0.0.1", 0.004),
       "chat.shengsheng.example": ("127.0.0.1", 0.004), "www.shengsheng.example": ("127.0.0.1", 0.004),
       "teach.shengsheng.example": ("127.0.0.1", 0.004)}
TARGETS = [("正常的 API", "api.shengsheng.example", port("healthy")),
           ("還沒建立的名稱", "classroom-v2.shengsheng.example", 443),
           ("沒人 listen", "rt.shengsheng.example", dead_port),
           ("SYN 被丟", "ops.shengsheng.example", drop_lst.getsockname()[1]),
           ("不回應", "reco.shengsheng.example", port("silent")),
           ("立刻 RST", "chat.shengsheng.example", port("reset")),
           ("慢回應", "www.shengsheng.example", port("slow")),
           ("錯誤 CORS", "teach.shengsheng.example", port("bad_cors")),
           ("CDN 混用 CORS", "api.shengsheng.example", port("cdn_mixed"))]
verdicts = {}
for label, name, p in TARGETS:
    origin = "https://teach.shengsheng.example" if label.startswith("CDN") else ORIGIN
    phases, findings = diagnose(name, p, DNS, origin)
    timing = " ".join(f"{k}={v * 1000:.1f}ms" for k, v in phases.items()) or "-"
    print(f"■ {label}  {name}  [{timing}]")
    for layer, msg in findings:
        print(f"   [{layer}] {msg}")
    verdicts[label] = {layer for layer, _ in findings}

STOP.set()
for s in [*servers.values(), drop_lst, *fillers]:
    s.close()
assert verdicts["正常的 API"] == {"OK"} and verdicts["還沒建立的名稱"] == {"DNS"}
assert verdicts["沒人 listen"] == verdicts["SYN 被丟"] == verdicts["立刻 RST"] == {"TCP"}
assert verdicts["不回應"] == {"APP"} and "效能" in verdicts["慢回應"]
assert {"快取", "CORS", "HSTS"} <= verdicts["錯誤 CORS"] and verdicts["CDN 混用 CORS"] == {"CORS"}
```

```text

   [OK] HTTP 200，2 bytes，header 檢查通過
```

毫秒數每次執行都略有不同，但每個目標的結論固定。逐一對照前面的案例。第一個目標是對照組：每一段都很短，header 檢查全部通過，證明工具本身沒有誤判。第二個是名稱查不到，工具在第一步就停下，連 connect 都沒有時間，這和 45.4 節「先看名字再看連線」的順序一致。

第三與第四個是 45.6 節的兩個世界。「沒人 listen」在 connect 階段立刻失敗，被分類為 refused；「SYN 被丟」等滿 300 毫秒的連線逾時，被分類為 timeout。兩者只差在對方核心有沒有回 RST，工具因此能給出完全不同的建議：前者去目標主機看 `ss -ltn`，後者去查防火牆或 accept queue。

第五與第六個都在 connect **之後**出事，是 45.6 節表格的第三列與 45.7 節的 reset。「不回應」的連線很快就建立了，因為交握由核心完成，但 500 毫秒內收不到任何 byte，這就是 nginx 的「while reading response header」；「立刻 RST」則在讀取時得到 `ConnectionResetError`。把讀取逾時和連線逾時分開，正是為了區分這兩種情況和前面的 timeout。

第七個是 45.8 節的分段：TTFB 約 254 毫秒（server 刻意等 250 毫秒）、下載約 215 毫秒（body 分四段、每段間隔 50 毫秒），工具把兩段都點名，最大的排第一。最後兩個是 45.9 節：第一個同時犯了三個錯，帶 `Set-Cookie` 的回應標成 `public`（第 21 章的首頁事故）、`*` 配 credentials、沒有 HSTS；第二個從 `teach` 的 origin 發出請求，卻拿到寫著 www 的 `Access-Control-Allow-Origin`，而且沒有 `Vary: Origin`，正是 CDN 混用的指紋。

這個工具有兩個刻意的限制。第一，它說 HTTP，沒有做 TLS，所以 HSTS 的檢查只看 header 是否存在；真實環境要用 `ssl.create_default_context()` 包住 socket，並把憑證到期日與名稱比對加進檢查。第二，它只從一個觀察點看，看不到使用者那一端的 resolver 與路徑；要回答「某所學校為什麼連不上」，仍然要請對方在當地執行同樣的檢查。

## 45.15 常見錯誤與除錯

本章的「錯誤」不是某個協定設定錯，而是除錯過程本身的錯。下表是聲聲 Live 的事後檢討裡反覆出現的幾種，每一種都讓事故多拖了幾十分鐘。

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 「我這邊正常」，但使用者一直壞 | 用自己的網路、自己的 resolver、已登入的瀏覽器測試 | 比對使用者的公網 IP、resolver、瀏覽器版本 | 從使用者的網路測，或用 `--resolve`、`dig @resolver` 模擬對方條件 |
| 用 `dig` 證明程式的解析沒問題 | `dig` 繞過 `/etc/hosts`、search domain 與 runtime 快取 | 在程式所在的容器裡跑 `getent hosts`，與 `dig` 比對 | 驗證程式行為用程式走的路（第 16 章） |
| 重開服務後問題消失，下週又來 | 重開時一起清掉了 CLOSE_WAIT、accept queue 等證據 | 檢討時找不到任何連線狀態的紀錄 | 止血前先存 `ss`、log；把收集證據寫成一個指令 |
| 改了三個設定，不知道哪個有效 | 一次改多個變數 | 無法回答「是哪一個修好的」 | 一次改一個，每次改完重新驗證預測 |
| 直打 LB 正常就宣布「後端沒事」 | 測試時沒帶使用者的 Host、SNI、Origin 或 cookie | 比對失敗請求與測試請求的 header | 中點測試的條件要和使用者一致 |
| CORS 錯誤改了半天還是錯 | 背後其實是 502／500，沒帶 CORS header | Network 面板看實際 status | 先修 5xx，再確認錯誤回應也帶 CORS header |
| 「網路不穩」結案 | 假設不具體，無法被推翻 | 檢討報告沒有任何工具輸出 | 每個結論附上觀察點與證據 |
| 只在一端抓包，看不出誰送了 RST | RST 可能來自中間設備 | 比對兩端的 pcap 與 TTL | 兩端同時抓，記下各自的時間與 TTL |

這張表的共同主題是「證據的條件」。工具本身很少出錯，出錯的是在錯誤的觀察點、用錯誤的條件執行了正確的工具，然後把結果當成整個系統的答案。

## 45.16 動手練習

1. **延伸診斷工具：加上 TLS**（延伸程式）。把 45.13 節的 `diagnose()` 改成可選擇用 `ssl.create_default_context().wrap_socket(sock, server_hostname=name)` 包住連線，量出 TLS 交握時間，並把 `getpeercert()` 的 `notAfter` 換算成剩餘天數；對你能合法存取的一個測試網站執行。
   答案要點：TLS 交握時間應約為 1 到 2 個 RTT；`server_hostname` 同時決定 SNI 與名稱比對，漏掉它會拿到預設憑證或比對失敗。剩餘天數低於效期的三分之一就該告警（第 19 章），而不是固定 30 天。

2. **延伸診斷工具：分辨 FIN 與 RST**（延伸程式）。新增一個故障 server：讀完請求後直接 `close()`（不設 `SO_LINGER`），確認工具輸出的是「連線被正常關閉卻沒有回應」，再說明它在 nginx 的 log 中會是哪一句。
   答案要點：client 讀到 `b""`，屬於 FIN 而不是 RST；nginx 對應的是「upstream prematurely closed connection while reading response header」，常見於 worker 被殺或 keep-alive 競態（第 10 章 Q5）。

3. **用 curl 切開你自己的網站**（真實工具）。對你負責的任一個網站執行 45.14 節第 2 步的 curl，連續十次，把五段時間的最小值與最大值列成表。
   答案要點：DNS 的第一次通常最慢（快取未命中）；connect 約等於 RTT，若偶爾出現 1 秒或 3 秒的跳躍，代表有 SYN 被重傳；TTFB 的變異最大，代表伺服器端的處理時間不穩定。

4. **比對兩台 resolver**（真實工具）。對同一個名稱分別問公司或家裡的 resolver 與一台公共 resolver，連續查兩次，觀察 TTL 的變化；再對一個不存在的子網域查詢，找出 AUTHORITY 段的 SOA，說明負面快取會保留多久。
   答案要點：同一台 resolver 第二次查詢的 TTL 會變小，代表命中快取；不同 resolver 的 TTL 互不相關。負面快取時間取 SOA 的 minimum 欄位與 SOA 本身 TTL 的較小值（第 15 章）。

5. **在 DevTools 重現 CORS 與 status 的關係**（真實工具）。用第 23 章的 CORS server，故意讓某個路由回 500 而且不帶 CORS header，從另一個 origin 的頁面 fetch 它，比較 Console 與 Network 面板的訊息。
   答案要點：Console 只會說被 CORS 擋下，Network 面板仍看得到 500。修正後讓錯誤回應也帶 CORS header，前端才讀得到錯誤內容。這個練習的結論是：CORS 錯誤先看 status。

6. **設計一場故障演練**（設計）。為你的團隊挑三個過去的事故，各寫出要注入的故障、給值班者的「使用者原話」、預期的診斷路徑與判斷正確的標準。
   答案要點：好的演練題只給症狀不給層；注入的故障要可以安全地復原；評分看的是「第一個正確的是非題用了多久」，而不只是有沒有找到根因。

## 本章重點整理

- 網路除錯最難的地方在於症狀出現的位置和原因所在的位置不同，所以第一步永遠是判斷「哪一層、哪一個元件」，而不是去讀離自己最近的 log。
- 除錯是一個觀察、假設、預測、驗證的循環；假設要具體到能被推翻，每一個結論都要附上它是在哪個觀察點看到的。
- 動手之前先寫下影響範圍、開始時間與最近的變更；止血之前先保留 `ss` 與 log 等證據；一次只改一個變數。
- 由下而上適合完全不通與新環境，由上而下適合手上有明確錯誤訊息，分半法適合路徑長又沒有線索；`curl --resolve` 繞過 CDN 直打 LB 是最常用的中點。
- DNS 的問題在使用者那端常常看起來像連線逾時；用多台 resolver 的答案與剩餘 TTL、`curl -w '%{remote_ip}'` 與 `ss -tn` 確認誰在用舊答案。
- TLS 錯誤要帶正確的 SNI 檢查，並逐一連到每個副本；過期、鏈不完整、client 時鐘錯與名稱不符各有不同的錯誤碼與修法，「瀏覽器正常」是最不可靠的證據。
- refused 是一個 RTT 內收到 RST，timeout 是 SYN 沒有回應，連上卻沒回應則是應用程式的問題；三者的時間特徵、封包證據與成因幾乎不重疊。
- 間歇性 reset 多半來自閒置逾時不一致：重用連線的一方必須比關閉連線的一方更早放棄閒置連線；面對 RST 先問「是誰送的」。
- 「慢」要先切成 DNS、交握、TLS、TTFB、下載五段，各段有各自的嫌疑名單；剛好 5 秒、剛好 1 秒或 3 秒、吞吐乘 RTT 等於某個 buffer，都是很強的線索。
- CORS 是瀏覽器執行的規則，Console 不會顯示被擋下的回應內容；先看 Network 面板的 status，再用 curl 帶齊 `Origin` 與 `Access-Control-Request-*` 模擬 preflight。
- WebSocket 斷線先看 close code 決定是誰關的，再看時間點決定原因；閒置固定秒數後的 1006 幾乎都是心跳與某層 idle timeout 的問題。
- WebRTC 的媒體共用同一組雙向驗證的 candidate pair，純網路造成的單向問題很少見；先用 candidate-pair 的雙向 bytes 排除網路，再沿著 SDP、送端、SFU、收端、播放逐站確認。

## 延伸問答

> [!question]- Q1. 為什麼「我這邊測試正常」幾乎不能當成任何結論？什麼時候它是有用的？
> 因為你的測試和使用者的請求之間，可能有一大串條件不同：公網 IP 與 ISP、使用的 resolver 與它的快取、到 CDN 的哪一個 edge、瀏覽器版本與擴充功能、是否已登入、是否命中快取，甚至 IPv4 或 IPv6。45.4 節的 DNS 搬家事故裡，小晴的筆電剛好問到一台沒有舊快取的 resolver，所以「正常」只代表那一台 resolver 的狀態，對其他七成使用者毫無意義。
>
> 它有用的時候，是你刻意控制了條件並把它當成分半法的一刀。例如「從 VPC 內用 `--resolve` 直打 LB 正常」排除了 LB 之後的元件，「用使用者的 resolver 查到舊 IP」則證明問題在 DNS 快取。關鍵在於說清楚「在哪個觀察點、用什麼條件」測到正常，讓這個結果能被別人重現與推翻。

> [!question]- Q2. 情境判斷：nginx 的 error log 同時出現 `connect() failed (111: Connection refused)` 與 `upstream timed out (110: Connection timed out) while reading response header`。這是同一個問題嗎？你會怎麼分頭查？
> 不是。第一句發生在「連線」階段，111 是 ECONNREFUSED，代表 SYN 抵達了某台主機，對方核心回了 RST：那個 upstream 位址上沒有程式在 listen，可能是服務沒起來、port 錯、只聽 127.0.0.1，或防火牆設成 REJECT。第二句發生在「讀取回應 header」階段，代表連線早就成功，請求也送出了，只是 upstream 在逾時內沒有回 header，指向應用程式的 worker 卡住或上游太慢。
>
> 分頭查的方法是先看兩句 log 各自的 `upstream:` 欄位是不是同一台主機。對 refused 的那台，在 nginx 主機上 `nc -vz` 確認，再到該主機 `ss -ltnp` 看 listen 位址；對讀取逾時的那台，看 worker 狀態、應用程式 log 與 `$upstream_header_time` 的分布。兩者可能同時發生，例如部署時一台還沒起來、另一台被湧入的流量壓垮，但它們的修法完全不同。

> [!question]- Q3. 手算：某條路徑的 RTT 是 180 ms，`curl -w` 顯示 `time_connect` 為 1.183 秒，`time_namelookup` 為 0.003 秒。你能推論什麼？
> 交握的長度是 1.183 − 0.003 ＝ 1.180 秒。正常的 TCP 交握在 client 端只需要等一個 RTT，約 0.18 秒，多出來的正好約 1.0 秒，對上 Linux SYN 初始重傳逾時 1 秒：第一個 SYN（或它換來的 SYN+ACK）遺失了，client 等了 1 秒重傳，第二次才在一個 RTT 內完成。
>
> 下一步是判斷遺失發生在哪裡。偶發一次可能只是路徑丟包；如果大量請求的 connect 時間都集中在「RTT＋1 秒」或「RTT＋3 秒」，那就是系統性的丟 SYN，最常見的是目標主機的 accept queue 滿了，或某個防火牆在尖峰時丟包。到目標主機上看 `ss -ltn` 的 Recv-Q 與 `TcpExtListenOverflows`，同時抓包看 SYN 有沒有抵達，就能一刀切開。

> [!question]- Q4. 面試題：使用者回報「網站很慢」，你會怎麼排查？請說出具體步驟。
> 第一步是釐清範圍與時間：所有人還是部分人、所有頁面還是某一頁、從何時開始、最近有什麼變更。範圍決定方向：所有人都慢，先看自己的服務與最近的部署；只有某地區或某網路慢，先看 CDN 與路徑。第二步是把一次請求切成五段：用 `curl -w` 或 DevTools 的 Timing 量出 DNS、TCP 交握、TLS 交握、等第一個 byte、下載各花多少時間，並且從受影響的使用者那一端量。
>
> 第三步依最大的一段找嫌疑：DNS 大就查 resolver 與 search domain，交握大就比對 RTT 並找 SYN 重傳，TLS 大就看憑證鏈與終結點負載，TTFB 大就用 `x-request-id` 去 nginx 的 `$upstream_header_time` 與應用程式 log 找慢查詢，下載大就算 BDP、看壓縮與 CDN 命中。最後是驗證與預防：修完再量一次五段時間，並讓合成監測持續記錄分段，而不是只記總時間。

> [!question]- Q5. 看封包找原因：在學校電腦教室抓到的封包中，SYN+ACK 的 IP TTL 是 52，緊接在 ClientHello 之後收到的 RST 的 TTL 是 63。這代表什麼？
> IP TTL 每經過一個路由器減 1，同一台伺服器送出的封包，抵達同一個觀察點時的 TTL 應該很接近。SYN+ACK 的 52 代表它從一個初始值（常見 64）出發、經過了十幾跳；RST 的 63 則幾乎沒有減少，代表它是從離學校很近的設備發出的，而不是聲聲 Live 的伺服器。再加上 RST 緊跟在 ClientHello 之後，最合理的解釋是學校的內容過濾設備讀到 SNI 裡的網域，偽造了一個 RST 中止連線，這正是第 3 章那所高中的情況。
>
> 這個結論改變了處理方式：聲聲 Live 的伺服器什麼都不用改，要做的是請學校把網域加進允許清單。它也說明為什麼 45.7 節強調「RST 是誰送的」是 reset 問題的第一個問題，以及為什麼最好在兩端同時抓包：從伺服器那端看，根本看不到這個 RST。

> [!question]- Q6. 設計取捨：為了避免 WebSocket 閒置斷線，同事提議把 LB 的 idle timeout 調到一小時、nginx 的 `proxy_read_timeout` 調到一小時。這樣好嗎？
> 這只解決了自己控制的兩層。學生家的 NAT、行動網路的 CGNAT、企業防火牆都有各自的閒置逾時，而且不受聲聲 Live 控制，安靜的連線仍會在它們那裡被默默清掉；更糟的是，當這些設備清掉連線時不一定送 RST，伺服器這端會以為連線還在，替一條死連線保留記憶體、訂閱與 presence，一小時後才發現。
>
> 正確做法是 45.7 與 45.10 節的規則二：由 server 定期送 ping（聲聲 Live 是 25 秒），讓連線上永遠有流量，路徑上每一層的計時器都被重設；同時用「多久沒收到 pong 就關閉」偵測死連線。各層的逾時只要比心跳間隔長並留下容忍一兩次心跳遺失的餘裕即可，例如 nginx 75 秒、LB 120 秒。調長逾時可以當成補強，但不能取代心跳。

> [!question]- Q7. 情境判斷：老師說「學生看得到我，我看不到其中兩位學生」，客服判斷是學生網路不好。你會怎麼在五分鐘內確認或推翻這個判斷？
> 先打開那兩位學生的 getStats 或 webrtc-internals，看 `candidate-pair` 的 `bytesSent` 與 `bytesReceived` 是否都在增加。在聲聲 Live，音訊、視訊與兩個方向都 BUNDLE 在同一組 candidate pair 上，而 ICE 的 consent 檢查是雙向的；如果學生看得到老師、bytesReceived 在增加，同一條路徑的另一個方向通常也是通的，這時「網路不好」的判斷就站不住了。
>
> 接著沿著學生送出的那一路往下看：answer 裡學生的視訊 m-line 是否被接受（port 是否為 0）、方向是否為 sendrecv 或 sendonly、學生端是否有 outbound-rtp 的 video 統計且 packetsSent 在增加、SFU 是否把這一路轉給老師。第 35 章的事故就在第一步停下：SFU 因為 munging 後的 offer 沒有可用的主要 codec 而拒絕了 m-line。整個過程只需要讀統計與 SFU log，不需要猜測網路。

> [!question]- Q8. 為什麼 45.13 節的診斷工具要把連線逾時與讀取逾時分開設定？如果只設一個 3 秒的總逾時，會失去什麼資訊？
> 因為兩個逾時回答的是不同層的問題。連線逾時只涵蓋三向交握，它觸發代表 SYN 沒有得到回應，原因在網路路徑、防火牆或對方的 accept queue；讀取逾時從請求送出後才開始計，它觸發代表交握早就完成，是應用程式沒有回話，原因在 worker、event loop 或上游服務。工具輸出中「SYN 被丟」與「不回應」兩個目標，正是靠這個區分得到不同的結論。
>
> 如果只有一個總逾時，兩種情況都只會得到「3 秒後逾時」，你分不出該去找網路團隊還是應用程式團隊。它還會掩蓋時間分布的線索：連線逾時之前的 SYN 重傳會讓 connect 時間落在 1 秒、3 秒附近，讀取逾時則與應用程式的處理時間相關。實務上，連線逾時通常設得很短（同機房 1 到 3 秒），讀取逾時依下游的 p99 延遲決定，兩者分開也讓告警能精準分流。
