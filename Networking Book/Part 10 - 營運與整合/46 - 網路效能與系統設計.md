## 46.1 故事：兩個問題，其實是同一個問題

2026 年 10 月的週一早上，產品經理在團隊頻道貼了兩則訊息。第一則是使用者回饋：「在美國東岸讀書的學生說，打開『找老師』頁要將近四秒才看得到完整的清單。」真實使用者監測（RUM，real user monitoring，從使用者瀏覽器回報的效能數字）的 p75 是 3.7 秒。第二則是業務目標：明年春季要正式在美國招生，開學週的尖峰估計會有 60,000 人同時在線，視訊教室數量是今年的兩倍，公開講座要能同時容納 6,000 名觀眾。

小晴是兩件事的負責人之一，第一個反應是把它們拆成兩張單：一張給前端「優化首頁」，一張給 SRE「加機器」。阿德看了說：「這兩件事是同一種功夫。第一件要你把一個請求的時間拆到每一站，第二件要你把一個使用者拆到每一層。你拆不出來，就只能猜：猜升級 HTTP/3 有沒有用，猜要開幾台。」阿德接著宣布，兩週後的年度架構審查改用 system design interview 的形式進行：小晴當候選人，從零講完聲聲 Live 的整個網路架構，Rita 與 Joe 當面試官。

小晴這才發現，前面四十五章學到的東西都是零件：TCP 交握、DNS TTL、TLS 憑證、CDN 的 cache key、WebSocket 的心跳、SFU 的 simulcast、SRT 的 latency。面試官不會問「TIME_WAIT 是什麼」，而是問「美國學生慢，你先改哪裡？為什麼不是別的地方？」「一個 AZ 掛了，學生會看到什麼？」這些問題沒有一章能單獨回答，要把零件組起來，還要拿得出數字。

```text
  DNS │ TCP │ TLS │ TTFB │ 下載 │ 渲染              CDN │ LB │ nginx │ gunicorn │ uvicorn
  每一站幾個 RTT？哪幾站串在一起？                    │ SFU │ TURN │ ingest │ LL-HLS

            └──────────────► 同一張架構圖（46.8）◄────────────────┘
```

這張圖是本章的路線。左半邊是效能：把 3.7 秒拆成每一站，算出每一站要幾個 RTT，找出哪幾站是串在一起、彼此等待的，那條鏈就是要優化的地方。右半邊是容量：從 60,000 人出發，算出每一層有多少連線、多少頻寬、要幾台機器。兩條線最後收斂到同一張架構圖，因為每一個架構決定，都同時影響延遲與成本。本章前半（46.2–46.5）建立方法，後半（46.6–46.13）用面試的形式走完整個設計，46.14 節把兩個問題都寫成可以調參數的 Python 模型。

## 46.2 延遲預算與 critical path

**延遲預算**（latency budget）是把一個總延遲目標，像分配預算一樣分給每一段。例如「找老師」頁的目標是美東學生 p75 在 2.5 秒內看到完整清單，這 2.5 秒要分給 DNS、連線建立、伺服器處理、下載與瀏覽器渲染；任何一段超支，就要從別處省回來。預算的好處是讓討論有共同語言：前端說「渲染只要 100 ms」、後端說「Flask 只要 30 ms」都對，但加起來仍可能超支，因為大部分時間花在兩者都沒看的地方。

光有預算還不夠，因為各段不是全部串在一起。**critical path**（關鍵路徑）是一串彼此依賴、必須依序完成的步驟中最長的那一條：只有縮短它，總時間才會變短；縮短不在路徑上的步驟，總時間一毫秒都不會少。下圖是「找老師」頁的依賴關係：

```text
  t=0 ─► DNS(www) ─► TCP ─► TLS ─► GET /teachers ─► HTML 到齊
                                           │               │
                                           │               ├─► app.css ─────────────┐
                                           │               │                         ├─► 第一次繪製（FCP）
                                           │               ├─► app.js ─► 執行 ─┐     │
                                           │               │                   │     │
                                           │               └─► 80 張大頭照 ────┼─────┼─► 清單完整出現
                                           │                                   │     │
                                           └··(preconnect 可以從這裡開始)··┐   ▼     │
                                                          DNS(api) ─► TCP ─► TLS ─► preflight ─► GET /v1/teachers
                                                                                                     │
  實線：必須等前一步完成　　點線：preconnect 讓後面的步驟提早開始                                     ┘
```

由左往右讀。HTML 一定是第一步，因為瀏覽器要讀到 HTML 才知道還需要哪些資源。HTML 到齊後分成三條支線：CSS 決定第一次繪製（**FCP**，first contentful paint，畫面第一次出現內容），JavaScript 執行後才發出 API 請求，大頭照則在 HTML 裡就能發現。最下面那條 API 支線最長：`api.shengsheng.example` 是另一個網域，要重做 DNS、TCP、TLS，再加一次 CORS preflight（第 23 章），最後才是真正的 GET。如果這條支線最晚完成，它就是 critical path；這時把大頭照壓得再小，清單也不會早一毫秒出現。點線是 46.3 節的主角：`preconnect` 讓 API 那條支線的連線建立提早到「HTML 開始抵達」就動工，把它從 JavaScript 後面拉出來，與其他工作並行。

### 每一站的成本

把每一站的成本用 RTT（第 1 章）表示，就能在量測之前先估出量級：

| 站 | 成本 | 會變大的情況 | 怎麼省 | 詳見 |
|---|---|---|---|---|
| DNS | 本機與 resolver 快取命中時接近 0；未命中時一次到 resolver，再加 resolver 向權威伺服器遞迴 | TTL 太短、名稱太多、resolver 遠 | 減少網域數、合理 TTL、`dns-prefetch` | 第 14–16 章 |
| TCP | 1 RTT | 丟 SYN 時要等重傳（Linux 初始 1 秒） | 連線重用、`preconnect`、CDN 縮短 RTT | 第 10 章 |
| TLS | TLS 1.3 為 1 RTT；TLS 1.2 為 2 RTT | 憑證鏈太長、OCSP 查詢、ClientHello 被拆成多個封包 | TLS 1.3、session resumption、就近終結 | 第 18–19 章 |
| TTFB | 1 RTT＋伺服器時間（＋edge 回源） | 伺服器慢、回源路徑長、排隊 | 快取、暖的回源連線、減少後端扇出 | 第 21、25、43 章 |
| 下載 | slow start 的輪數 × RTT＋大小 ÷ 頻寬 | 回應大、新連線、丟包 | 壓縮、重用暖連線、拆掉關鍵路徑上的大檔 | 第 11–12 章 |
| 渲染 | CSS 與同步 JS 會擋住繪製；字型、LCP 圖片要等 | 阻塞的 JS、晚發現的資源 | 關鍵 CSS 內嵌、`defer`、`preload` | 第 1 章 |

表中有兩欄最值得注意。「成本」欄幾乎都以 RTT 為單位，所以同一個頁面在台北（到東京 edge 約 35 ms）和美東（到 origin 約 180 ms）會有五倍左右的差距，伺服器程式完全一樣。「會變大的情況」欄則說明為什麼平均值常常騙人：一次 SYN 遺失讓 TCP 多等 1 秒，一次 DNS 快取未命中多一次跨洋遞迴，這些事件發生在少數請求上，平均值看不出來，p75、p95 才看得出來。所以延遲預算一律用百分位數訂，不用平均值。

**TTFB**（time to first byte）在第 1 章定義過，這裡要補一個實務上的陷阱：有些工具從「送出請求」算起，有些從「開始導航」算起，後者把 DNS 與交握都算進去。比較兩個團隊的 TTFB 之前，先確認定義。本章的 TTFB 一律從導航開始算，所以它包含 DNS、交握與伺服器時間。

### 下載不只是「大小 ÷ 頻寬」

很多人估下載時間只算「大小 ÷ 頻寬」：120 KB 的 JavaScript 在 50 Mbps 下只要 19 ms。這在新連線上嚴重低估，因為 TCP 的 slow start（第 12 章）讓新連線第一輪 RTT 最多只能送初始壅塞視窗（initial cwnd）那麼多資料，之後每輪加倍。現代 Linux 的初始 cwnd 是 10 個 segment，以 MSS 1448 bytes 計算約 14 KB。下面的程式算出不同大小的回應在新連線上要幾輪：

```python
MSS, INITCWND = 1448, 10            # 初始 cwnd：10 個 segment（第 12 章）


def rounds(nbytes, cwnd=INITCWND * MSS):
    """新連線送完 nbytes 要幾輪 RTT：每輪送一個 cwnd，slow start 每輪加倍。"""
    n = 0
    while nbytes > 0:
        nbytes -= cwnd
        cwnd *= 2
        n += 1
    return n


print(f"第一輪最多 {INITCWND * MSS:,} bytes")
print(f"{'回應大小':<10}{'輪數':>4}{'東京 edge 35 ms':>18}{'美東 180 ms':>14}")
for size in (14_000, 30_000, 120_000, 500_000, 2_000_000):
    r = rounds(size)
    print(f"{size:>10,}{r:>6}{r * 35:>15} ms{r * 180:>11} ms")
assert rounds(14_480) == 1 and rounds(14_481) == 2 and rounds(2_000_000) == 8
```

```text
第一輪最多 14,480 bytes
回應大小        輪數     東京 edge 35 ms     美東 180 ms
    14,000     1             35 ms        180 ms
    30,000     2             70 ms        360 ms
   120,000     4            140 ms        720 ms
   500,000     6            210 ms       1080 ms
 2,000,000     8            280 ms       1440 ms
```

第一行就是業界常說的「14 KB 規則」的由來：第一輪 RTT 最多送 14,480 bytes，所以首頁 HTML 如果能壓在 14 KB 以內，第一次回應就能一次到齊。表格的輪數隨大小以對數成長：30 KB 要 2 輪、120 KB 要 4 輪、2 MB 要 8 輪。真正的差距在最右欄：同樣 120 KB 的 `app.js`，在東京 edge 上要 140 ms，在 180 ms RTT 的路徑上要 720 ms，而頻寬算出來的 19 ms 在兩者之中都只是零頭。

這個結論對設計有三個直接影響。第一，**縮短 RTT 比加大頻寬更有效**，這是 CDN 的第一個價值（46.4 節）。第二，**重用暖的連線**省的不只是交握，還有 slow start：一條已經傳過資料的連線 cwnd 已經長大，大檔可以一輪送完（46.3 節）。第三，**關鍵路徑上的大檔是雙重成本**，既多傳 bytes 又多幾輪 RTT，所以把 `app.js` 拆成「首屏需要的」與「之後才需要的」常常比換 CDN 更有效。程式的模型刻意忽略了丟包與接收視窗；丟包時 cwnd 會減半（第 12 章），行動網路上實際輪數只會更多。

> [!warning] 常見誤解
> 「網站慢就升級使用者的頻寬或伺服器的網卡。」對網頁這種由許多小回應組成的負載，瓶頸幾乎都是往返次數，不是頻寬。頻寬從 50 Mbps 加倍到 100 Mbps，120 KB 的檔案只省 10 ms；把 RTT 從 180 ms 降到 15 ms，省的是幾百毫秒。只有大檔下載（課程錄影、直播 segment）才是頻寬主導。

## 46.3 連線重用與預連線

上一節的表說明了一件事：新連線很貴。對美東學生，一條新的 TCP＋TLS 1.3 連線要 2 個 RTT（360 ms）才能送出第一個請求，之後還要經歷 slow start。降低這個成本有兩種方向：**重用**（不要建新連線）與**預連線**（非建不可的連線，提早在背景建好，不要讓它擋在關鍵路徑上）。

### 重用：每一段都有自己的連線池

連線重用不只發生在瀏覽器。一個請求從學生到資料庫會經過五段連線，每一段都可以、也應該重用：

```text
 瀏覽器 ═①═► CDN edge ═②═► API LB ═③═► nginx 10.20.3.11 ═④═► gunicorn :8000 ═⑤═► PostgreSQL 10.20.17.15:5432
   │            │                         │                     │                    │
   │ HTTP/2：    │ 回源長連線，               │ upstream keepalive   │ gunicorn keep-alive │ 連線池（每個 worker
   │ 每個 origin  │ 讓跨洋的 TCP＋TLS          │ （HTTP/1.1，         │ 75 秒（第 43 章）     │ 一條），重用前檢查
   │ 一條連線     │ 只在 edge 做一次           │ Connection: ""）    │                     │ EOF（第 10 章）
   ▼            ▼                         ▼                     ▼                    ▼
 省：每個請求    省：學生每次都等的跨洋         省：VPC 內的交握（< 1 ms，   規則：nginx 對 upstream 的  省：DB 的 TCP＋
 的 2 RTT       2 RTT 與 slow start          但省下 CPU 與 TIME_WAIT）    閒置上限 60 s 短於 75 s    TLS＋認證往返
```

由左往右看每一段的重點。① 瀏覽器到 edge：HTTP/2 與 HTTP/3 讓同一個 origin 的所有請求共用一條連線（第 22 章），這是最大的一筆節省。② edge 到 origin：CDN 和 origin 之間維持長連線，美東學生只需要和附近的 edge 交握，跨洋那一段的交握由 edge 預先做好、反覆使用，這叫**動態加速**（dynamic acceleration），即使內容不能快取（例如個人化的 HTML）也有效。③ 與 ④ 在 VPC 內，RTT 不到 1 ms，重用省的主要是 CPU、TIME_WAIT 與來源 port（第 10 章），但要注意兩端的閒置上限：nginx 對 upstream 的閒置連線若比 gunicorn 的 keep-alive（預設 2 秒）活得久，就會把請求送進一條 gunicorn 剛關掉的連線（第 10 章延伸問答 Q5），所以第 43 章把 gunicorn 的 keep-alive 拉長到 75 秒，長於 nginx upstream 的 60 秒。⑤ 資料庫連線的建立包含 TCP、TLS 與認證，通常要好幾個往返與可觀的 CPU，所以每個 worker 都持有一條長連線；46.7 節會看到，這也讓「worker 數」直接變成「資料庫連線數」。

TLS 還有一層重用：**session resumption**（第 18 章）。連線斷了以後重建，client 可以出示上次拿到的 ticket，省掉憑證傳送與驗證，但 TLS 1.3 的 resumption 仍是 1 RTT；只有 0-RTT 能讓請求跟著第一個封包出發，而 0-RTT 資料可能被重放，聲聲 Live 只放行 GET 與 HEAD，其他請求回 425 Too Early（第 13、18、22 章）。

### 預連線：resource hints 與 103 Early Hints

有些新連線無法避免：第一次造訪、第三方網域、另一個子網域。這時的目標是讓連線建立與其他工作**並行**。瀏覽器提供幾種 **resource hint**（資源提示，HTML 裡告訴瀏覽器「你等一下會需要這個」的標記）：

```html
<!-- /teachers 的 <head>：越前面越好，瀏覽器解析到才會動作 -->
<link rel="preconnect" href="https://api.shengsheng.example" crossorigin>
<link rel="dns-prefetch" href="https://pay.example.net">
<link rel="preload" href="/static/app.3f9c.js" as="script">
```

`preconnect` 讓瀏覽器提前完成 DNS、TCP 與 TLS，`dns-prefetch` 只做 DNS，`preload` 則直接下載一個稍後才會被發現、但一定會用到的資源。`crossorigin` 屬性很容易被漏掉：瀏覽器會依「是否帶憑證」把連線分到不同的連線池，`fetch()` 跨來源且不帶 cookie 的請求屬於 anonymous 模式，字型也是；preconnect 沒加 `crossorigin` 時，建好的連線可能屬於另一個池，真正的請求用不到，等於白做（各瀏覽器細節依實作而定）。

resource hint 寫在 HTML 裡，要等 HTML 開始抵達才生效。如果 Flask 產生 HTML 需要時間、或 edge 回源要跨洋，這段等待就浪費了。**103 Early Hints** 是一個資訊性的回應狀態碼：server 在最終回應之前，先送一個 `103` 回應，裡面只有 `Link` header，瀏覽器收到就能開始預連線與預載，同時 server 繼續產生真正的 200 回應：

```text
 瀏覽器                         CDN edge（美東）                         origin（Flask）
   │── GET /teachers ─────────────►│── 回源 GET /teachers ──────────────────►│
   │◄── 103 Early Hints ───────────│   （edge 依設定或上次的 103 先回）        │ 產生 HTML 中……
   │    Link: <https://api.shengsheng.example>; rel=preconnect; crossorigin   │
   │    Link: </static/app.3f9c.js>; rel=preload; as=script                   │
   │══ 開始對 api 做 DNS、TCP、TLS ══►（與回源同時進行）                      │
   │                                  │◄──────────────────── 200 OK（HTML）───│
   │◄── 200 OK（HTML）─────────────────│                                        │
```

這張時序圖的重點在中間那條雙線：瀏覽器收到 103 時，HTML 還在 origin 產生、還在跨洋回傳，但對 `api` 的交握與 `app.js` 的下載已經開始。沒有 103 時，這兩件事要等 HTML 的 `<head>` 抵達才會開始，也就是要多等一整段回源時間（對美東學生約 200 ms）。103 的 `Link` 只是提示，不帶任何狀態，所以 edge 可以快取並重複送出同一組 hint；中間任何一層若不認得 1xx 回應，最壞的情況是 hint 被丟掉，最終的 200 不受影響。

| 手法 | 做什麼 | 省掉哪一段 | 適合 | 風險與注意 |
|---|---|---|---|---|
| 連線重用（HTTP/2、keep-alive） | 不建新連線 | 每個請求的 2 RTT 與 slow start | 同一個 origin 的所有請求 | 兩端閒置上限要對齊 |
| `dns-prefetch` | 只解析 DNS | DNS（未命中時數十毫秒） | 稍後可能用到、不一定用到的網域 | 幾乎沒成本 |
| `preconnect` | DNS＋TCP＋TLS | 新網域的 2–3 段 | 2–4 個確定會用到的關鍵網域 | 用不到的連線佔資源；要對 `crossorigin` |
| `preload` | 提前下載 | 「發現資源」前的等待 | 字型、LCP 圖片、晚載入的 JS | 用錯 `as` 會重複下載；搶頻寬 |
| 103 Early Hints | 在最終回應前送出 hint | 伺服器處理與回源的時間 | HTML 產生慢、回源遠 | 中間的 proxy 與 CDN 要支援 |
| TLS session resumption | 重建時省憑證交換 | 部分 TLS 成本（仍 1 RTT） | 回訪使用者、重連 | ticket 金鑰要輪替 |
| 0-RTT | 請求跟著第一個封包出發 | 1 RTT | 回訪的 GET | 可被重放，只放行 GET、HEAD |

讀這張表時，可以把每一列對應回 46.2 節的依賴圖：重用是把整段交握刪掉；`preconnect` 與 103 不刪任何步驟，只是把它們從關鍵路徑上移開，讓它們和其他工作重疊。這也是預連線的上限：如果連線建立比「它被移開之後的那段空檔」還長，剩下的部分仍然在關鍵路徑上。46.14 節的模型會精確算出這個差距，延伸問答 Q1 用它手算一次。

## 46.4 CDN、壓縮與 HTTP/2、HTTP/3

### CDN 的三個價值

第 25 章從快取的角度介紹 CDN；從效能的角度，它提供三種彼此獨立的價值。第一是**縮短 RTT**：TLS 在離使用者最近的 edge 終結，美東學生的交握從 2 × 180 ms 變成 2 × 15 ms。第二是**快取命中**：靜態資源直接由 edge 回應，連回源都不必。第三是**更好的回源路徑**：edge 與 origin 之間的暖連線與 CDN 自己的骨幹，讓不能快取的請求也受益。三者中只有第二項依賴命中率，所以「個人化頁面不能快取，放 CDN 沒用」是錯的。

```text
 沒有 CDN（美東學生 → origin，RTT 180 ms）
 學生 ──TCP 180──TLS 180──GET 180＋Flask 30──► origin               首個 byte：DNS＋570 ms

 有 CDN（學生 → 美東 edge 15 ms；edge → origin 170 ms，連線已暖）
 學生 ─TCP 15─TLS 15─GET 15─► edge ═══ 暖連線 170＋Flask 30 ═══► origin   首個 byte：DNS＋245 ms
                              │
                              └─ 靜態檔命中：edge 直接回應，GET 只要 15 ms；未命中：再加回源 170 ms
```

上半部是沒有 CDN 時，三個往返都跨洋。下半部有 CDN：兩次交握與送出請求只跑到附近的 edge，只有「edge 向 origin 要 HTML」這一趟跨洋，而且用的是早就建好的連線，所以首個 byte 從 570 ms（不含 DNS）降到 245 ms。不能快取的 HTML 照樣省下 325 ms，省的是交握，不是快取。最下面那行是靜態檔：命中時整個請求在 15 ms 內結束；未命中時要多一趟回源。

命中率的影響常被想得太簡單。CDN 儀表板上的 92% 是**請求命中率**的平均值，但一個頁面要等「一批資源全部到齊」才算完成。80 張大頭照、每張 92% 命中，全部命中的機率是 0.92⁸⁰，大約千分之一；也就是說幾乎每一次載入都至少有一張要回源，整批資源的完成時間由最慢的那一張決定。46.14 節的模型會顯示，命中率從 50% 提高到 92% 對「圖片全部到齊」毫無幫助，要到 99.9% 才開始明顯變快。對關鍵路徑上的成批資源，真正有效的做法是讓它們不要有長尾：用 origin shield 縮短 miss 的回源距離（第 25 章）、把 TTL 拉長並用帶 hash 的檔名讓檔案永不過期（第 21 章）、或把小圖合併成一張。

### 壓縮：只壓會變小的東西

HTTP 壓縮由 client 用 `Accept-Encoding` 表明支援哪些演算法，server 選一個並在回應的 `Content-Encoding` 標明；同一個網址可能有壓縮與未壓縮兩種版本，所以快取要加 `Vary: Accept-Encoding`（第 21 章）。常見的演算法有三種：**gzip** 最普及，壓縮快、比例普通；**Brotli**（`br`）在相同速度下通常比 gzip 小一些，高壓縮等級很慢，適合事先壓好的靜態檔；**zstd** 壓縮與解壓都快，適合動態內容（瀏覽器支援度見 2026 現況）。下面用標準函式庫的 gzip 看兩種資料的差別：

```python
import gzip
import json
import random

rng = random.Random(46)                    # 固定種子：每次執行輸出相同
LANGS = ["ja", "ko", "en", "fr", "de", "es", "zh-TW", "vi", "th"]

# 「找老師」API 的回應：欄位名稱一再重複、值各不相同，接近真實的 JSON
teachers = [{"id": f"t_{rng.randrange(10**6):06d}",
             "name": "".join(rng.choice("abcdefghijklmnopqrstuvwxyz") for _ in range(rng.randint(4, 9))),
             "languages": rng.sample(LANGS, 2), "rating": round(rng.uniform(4.0, 5.0), 2),
             "price_ntd": rng.randrange(400, 1500, 50),
             "intro": " ".join(rng.choice(["conversation", "grammar", "JLPT", "business", "travel",
                                           "kids", "pronunciation", "TOPIK"]) for _ in range(8))}
            for _ in range(200)]
body = json.dumps(teachers, ensure_ascii=False).encode()
photo_like = rng.randbytes(60_000)          # 已壓縮過的 JPEG／影片近似隨機資料


def rounds(n, cwnd=14_480):                 # 新連線送完 n bytes 要幾輪 RTT（第 12 章）
    k = 0
    while n > 0:
        n, cwnd, k = n - cwnd, cwnd * 2, k + 1
    return k


for label, data, levels in (("JSON", body, (1, 6, 9)), ("照片", photo_like, (6,))):
    for level in levels:
        z = gzip.compress(data, compresslevel=level, mtime=0)
        print(f"{label} gzip level {level}: {len(data):>6,} → {len(z):>6,} bytes（{len(z) / len(data):>6.1%}）"
              f"，新連線 RTT 輪數 {rounds(len(data))} → {rounds(len(z))}")
assert len(gzip.compress(body)) < len(body) / 3
assert len(gzip.compress(photo_like)) > len(photo_like)   # 壓縮已壓縮的資料只會更大
```

```text
JSON gzip level 1: 35,692 →  7,424 bytes（ 20.8%），新連線 RTT 輪數 2 → 1
JSON gzip level 6: 35,692 →  5,721 bytes（ 16.0%），新連線 RTT 輪數 2 → 1
JSON gzip level 9: 35,692 →  5,435 bytes（ 15.2%），新連線 RTT 輪數 2 → 1
照片 gzip level 6: 60,000 → 60,038 bytes（100.1%），新連線 RTT 輪數 3 → 3
```

前三行是「找老師」API 的 JSON：欄位名稱一再重複，gzip 把 35 KB 壓到 5–7 KB，壓縮等級從 1 提高到 9 只多省了 2 KB，CPU 卻多花不少，所以動態回應通常用中低等級。最右欄的變化才是效能上的重點：壓縮後的回應落進第一輪 RTT 的 14 KB 之內，新連線上從 2 輪變 1 輪，對美東學生就是 180 ms。最後一行是已壓縮的照片：gzip 不但壓不小，還多了 38 bytes 的 header，白白浪費 CPU。所以 nginx 與 CDN 的壓縮設定一律只針對文字類型（HTML、CSS、JS、JSON、SVG），圖片、影片、字型的 WOFF2 都不該再壓。

壓縮還有一個資安上的限制。若同一個回應裡同時有**秘密**（例如 CSRF token）與**攻擊者能控制的內容**（例如反射在頁面上的搜尋字串），攻擊者可以從壓縮後的長度變化推測秘密，這類攻擊稱為 BREACH。防禦是不要把秘密與使用者輸入放在同一個壓縮的回應裡，或替每個回應隨機遮罩 token（第 23 章）。

### HTTP/2 與 HTTP/3 的效益

第 22 章已經詳細比較過，這裡只把它們放回延遲預算。HTTP/2 省的是「排隊」：HTTP/1.1 每條連線一次只能處理一個請求，瀏覽器對每個網域最多開 6 條，80 張大頭照要排 14 輪；HTTP/2 一條連線就能同時送全部。HTTP/3 再省兩件事：交握合併成 1 RTT（第 13 章），以及丟包時不讓其他 stream 一起等待（第 12 章的 head-of-line blocking）。它們的效益都和 RTT 成正比：RTT 越大、資源越多、網路越會掉包，效益越大。反過來，CDN 已經把 RTT 縮到 15 ms 之後，HTTP/2 對圖片只能再省一百多毫秒，46.14 節的模型會算出這個數字。

兩個舊習慣在 HTTP/2 下要拆掉。**domain sharding**（把資源分散到 `img1`、`img2` 等多個網域，讓 HTTP/1.1 多開幾條連線）在 HTTP/2 下只會多出 DNS 與交握，聲聲 Live 已經在第 22 章收回到 `www`。**連線合併**（connection coalescing）則是 HTTP/2 的福利：兩個網域若解析到同一個 IP、憑證又同時涵蓋兩者，瀏覽器可以共用一條連線；但聲聲 Live 的 `www` 在 CDN、`api` 在 API LB，IP 不同，永遠無法合併，這正是 API 那條支線一定要重新交握的原因。

## 46.5 容量估算方法

效能回答「一個請求要多久」，容量回答「一個尖峰要多少東西」。估算的目的不是精確，而是在花錢與壓測之前，先找出**哪一個資源會先用完**、和其他資源差幾個數量級。聲聲 Live 的方法分成七步，每一步都在前面的設計章出現過，這裡把它們整理成一套固定的流程：

```text
 ① 從一個數字出發：尖峰同時在線 60,000 人
        │
 ② 分流：這一刻每個人在做什麼？ ──► 上視訊課 11,600 │ 看直播 6,000 │ 瀏覽、預約、等候 42,400
        │
 ③ 換算成每一層的單位 ──► rps（請求）│ 長連線數 │ Gbps 與 pps │ fd 與來源 port │ DB 連線
        │
 ④ Little's law：同時在忙的數量 = 到達率 × 停留時間
        │
 ⑤ 每台機器的上限：來自壓測，不是規格表（例如單台 SFU 安全上限 3 Gbps 是假設）
        │
 ⑥ 加餘裕：目標使用率 60–80%、N+1、部署時排空用的一台
        │
 ⑦ 交叉驗證：用同一套公式代入今年的數字，看是否吻合前面章節與實際監控
```

① 的關鍵是只用一個起點。各子系統各自估算時（第 33 章的聊天、第 37 章的視訊、第 38 章的直播），用的是不同時間點與不同假設；全站估算必須從同一個「尖峰在線人數」出發，否則加總時會重複計算或漏算。② 分流把人數分給互斥的行為，因為同一個人不會同時在上課又在看直播，但同一個人可能同時開著 WebSocket 與 HTTP 連線。③ 換算時要依每一層的瓶頸挑單位：API 的瓶頸是每秒請求數與 worker，WebSocket 的瓶頸是長連線數與 fd，SFU 的瓶頸是頻寬與每秒封包數（pps，packets per second）。⑦ 是最常被跳過、也最有價值的一步，46.14 節的估算器會代入今年的教室數，驗證它能重現第 37 章的 6 台 SFU。

這裡要先把口徑講清楚，因為三個設計章的數字乍看對不起來。第 33 章的「9,000 間教室」是**所有開著聊天的房間**，除了正在上課的視訊教室，還包含課前等候、課後討論與學習小組，另外再加 40 場講座聊天室；第 37 章的「2,000 間一對一＋300 間小班」只算**同時在開視訊**的教室，是那 9,000 間裡的一小部分。本章則從同一個 60,000 人出發，依「這一刻在做什麼」分流：視訊 11,600 人（4,000 間一對一＋600 間六人小班，是第 37 章今年的兩倍）、看 LL-HLS 直播 6,000 人、其餘 42,400 人在瀏覽、預約、等候或課後聊天。這是同一群人的兩種切法：WebSocket 連線數只取決於總人數與每人 1.15 條連線，所以和第 33 章一樣是 69,000 條、6 台 gateway；SFU 只看在視訊的人，LL-HLS 只看觀眾。所以第 33 章的房間數不能拿來換算 SFU，第 37 章的教室數也不能拿來換算聊天連線。

### Little's law

④ 的 **Little's law** 是排隊理論裡最實用的一條：在穩定狀態下，系統內平均的「在處理中」數量 L 等於到達率 λ 乘以每個工作平均停留的時間 W。它不需要任何分布假設，對 gunicorn 的 worker、資料庫連線池、甚至 WebSocket 連線數都成立（連線數 ＝ 每秒新連線數 × 平均連線長度）。

```python
# Little's law：同時在處理的請求數 L = 到達率 λ × 平均停留時間 W
def workers_needed(rps, service_ms, util):
    busy = rps * service_ms / 1000            # 平均有幾個 worker 正在忙
    return busy, busy / util                  # 依目標使用率留餘裕


rps, service_ms = 1_650, 40
for util in (0.6, 0.8):
    busy, need = workers_needed(rps, service_ms, util)
    print(f"{rps} rps × {service_ms} ms：平均 {busy:.0f} 個 worker 在忙；目標使用率 {util:.0%} → 需要 {need:.0f} 個")

# 為什麼要留餘裕：用最簡單的單一佇列（M/M/1）近似，等待時間隨使用率爆炸
print("\n使用率   平均回應時間（服務時間 40 ms）")
for rho in (0.5, 0.7, 0.8, 0.9, 0.95, 0.99):
    print(f"  {rho:>4.0%}   {service_ms / (1 - rho):>6.0f} ms")

# 現在的 18 個 sync worker 最多撐多少
print(f"\n現況 18 workers × (1000 / {service_ms}) = {18 * 1000 / service_ms:.0f} rps（100% 使用率的理論上限）")
assert round(workers_needed(1_650, 40, 0.6)[1]) == 110
```

```text
1650 rps × 40 ms：平均 66 個 worker 在忙；目標使用率 60% → 需要 110 個
1650 rps × 40 ms：平均 66 個 worker 在忙；目標使用率 80% → 需要 82 個

使用率   平均回應時間（服務時間 40 ms）
   50%       80 ms
   70%      133 ms
   80%      200 ms
   90%      400 ms
   95%      800 ms
   99%     4000 ms

現況 18 workers × (1000 / 40) = 450 rps（100% 使用率的理論上限）
```

第一段把 Little's law 用在 API：每秒 1,650 個請求、每個平均 40 ms，平均有 66 個 worker 正在忙。如果真的只開 66 個，任何波動都會讓請求排隊；以 60% 為目標使用率，要 110 個 worker。第二段說明為什麼要留餘裕：用最簡單的單一佇列模型近似，使用率 50% 時平均回應時間是服務時間的兩倍，90% 時是十倍，99% 時是一百倍。真實系統的數字不同，但「接近滿載時延遲以非線性方式爆炸」這個形狀是普遍的，這也是第 10 章 accept queue 爆掉時的情景。最後一行是第 42 章時的配置：app-a、app-b 共 18 個 sync worker，即使 100% 使用率也只撐得住 450 rps，離開學週的目標差了好幾倍。第 43 章改用 gthread 後，每台有 8 × 7 ＝ 56 個 slot，但 thread 只能覆蓋 I/O 等待：如果這 40 ms 大多花在 CPU 上，GIL 讓一個 process 大約只用滿一個核心，能同時處理的請求數仍取決於 process 數。所以本章的估算保守地以「每台 9 個 process、每個一次處理一個請求」計算；若壓測證實 40 ms 裡大部分是在等資料庫與下游服務（第 43 章的假設是 CPU 只佔 5 ms），每台能撐的 rps 會高得多，主機數可以往下修。

### 常用的換算與經驗值

| 換算或經驗值 | 數字 | 用在哪裡 |
|---|---|---|
| 頻寬與 bytes | 1 Gbps ＝ 125 MB/s；1 Mbps 的串流一小時約 450 MB | 直播、錄影、出口流量費 |
| 一天的秒數 | 86,400；尖峰常是平均的 3–10 倍 | 不要用「每日請求 ÷ 86,400」當尖峰 |
| 封包大小 | 影音約 1,200 bytes；10 Gbps 約 1 Mpps | SFU、TURN 的 CPU 瓶頸常是 pps |
| 來源 port | Linux 預設 28,232 個，同一目的地的連線上限（第 10 章） | nginx 到 uvicorn、LB 到後端 |
| 每條閒置 WebSocket | 應用層約 40 KB，加上核心 buffer（第 33 章的假設） | gateway 記憶體 |
| fd | uvicorn 每條 WebSocket 1 個、nginx 2 個（第 33 章） | `ulimit -n`、`worker_connections` |
| TLS 交握 | 非對稱運算佔 CPU 大宗，重連尖峰時最痛 | 部署、故障後的重連驚群 |
| PostgreSQL 預設 `max_connections` | 100 | worker 數乘以每個 worker 的連線數 |

這張表的數字有兩種性質，要分清楚。前四列是物理或規格事實，任何系統都一樣；後四列是經驗值或聲聲 Live 自己的假設，換成你的系統要用壓測重新取得。估算報告裡把這兩種數字標示出來，審查的人才知道哪些可以質疑。

> [!warning] 常見誤解
> 「平均每秒只有 300 個請求，兩台機器綽綽有餘。」容量要用**尖峰**估，而且要用尖峰時刻的**最壞組合**：晚上八點的開課、講座開場、部署後的重連、某台機器故障，常常同時發生。第 33 章的部署重連驚群、第 25 章的 purge 回源暴增，都是平均值看不到、尖峰才出現的負載。

## 46.7 估算：從尖峰使用者到每一層

小晴用 46.5 節的流程，從 60,000 人出發，把估算器（46.14 節）的結果整理成一張表。這裡先看結論，推導細節與程式在動手做：

| 層 | 尖峰負載 | 頻寬 | 伺服器 | 最先用完的資源 |
|---|---|---|---|---|
| CDN（`www` 靜態） | 約 14,800 rps，回源約 1,200 rps | 約 1.2 Gbps | CDN 供應商 | 命中率與回源連線 |
| API LB → nginx → gunicorn | 約 1,650 rps | 約 105 Mbps | 110 個 worker（保守以 process 計），14 台 | worker 數、DB 連線 |
| 即時服務（WebSocket） | 69,000 條長連線 | 約 0.7 Gbps | 6 台即時 gateway | fd、記憶體、重連 CPU |
| SFU | 11,600 位參與者 | 收約 20.2、送約 20.8 Gbps | 9 台 | 頻寬與 pps（約 2.2 Mpps） |
| TURN | 約 930 位需要中繼 | 中繼約 3.3 Gbps，網卡約 6.6 Gbps | 3 台 | 網卡頻寬 |
| LL-HLS（CDN） | 6,000 位觀眾、約 24,000 rps | 約 13.2 Gbps | CDN；origin 約 80 rps | 每秒請求數 |
| SRT ingest 與轉碼 | 2 路推流 | 約 12 Mbps | 轉碼 3 台（含備援） | 轉碼運算 |

讀這張表要看最右欄：每一層最先用完的東西都不一樣，所以「全站要幾台機器」是個沒有意義的問題。幾個結論特別值得在面試中說出來。第一，**頻寬的大宗是 SFU**：媒體流量是 API 的兩百倍，而且不能快取、不能走 CDN，是雲端出口費的最大來源。第二，**LL-HLS 的負擔在請求數而不是頻寬**：每位觀眾每 0.5 秒的 part 要打兩個請求（playlist 與 part），6,000 人就是每秒 24,000 個請求，CDN 必須支援 blocking playlist reload 與請求合併（第 38 章），origin 才只看到每秒幾十個。第三，**API 的瓶頸會轉移到資料庫**：110 個 worker 各持有一條連線，加上即時服務的連線，超過 PostgreSQL 的預設上限 100，必須加連線池代理（pooler），或限制每台主機的連線池上限；改用 gthread 解決不了這個問題，因為每個 thread 都可能握一條連線（第 43 章）。第四，**即時服務的數字和第 33 章一致**（6 台），因為同一套假設。

小晴也主動說明這張表的不確定性：「SFU 單台 3 Gbps、每個 uvicorn worker 5,000 條連線、TURN 比例 8%，都是聲聲 Live 自己的假設或壓測值；換一台機型或一群企業客戶，數字就會變。我會在上線前用壓測更新這三個數字，其他的公式不變。」面試官要聽的正是這句話：知道哪些數字是事實、哪些是假設，以及假設錯了會影響哪一層。

## 46.9 各元件深入

面試官 Rita 說：「每一個方塊都講兩分鐘，告訴我你做了什麼決定、為什麼。」小晴依請求的方向，從 DNS 一路講到資料層，每一項都指回全書的對應章節。

### DNS 與流量導向（第 14–16 章）

權威 DNS 是全站的第一個依賴，所以至少放在兩家不同的 DNS 供應商，NS 記錄同時列出兩家，避免單一供應商故障讓所有名稱都解析不到。TTL 的取捨是「切換速度」與「快取命中」：300 秒讓故障時最多五分鐘就能把 `www` 從主要 CDN 切到備援、或把 `api` 切到另一組 LB；更短的 TTL 讓 resolver 更常回頭查詢，學生端的 DNS 未命中也變多。搬遷時則照第 14 章的教訓，先把 TTL 降低、等舊 TTL 過期，再換 IP。VPC 內部用 resolver 10.20.0.2、10.20.0.3，Kubernetes 的 Pod 經 kube-dns（10.96.0.10）解析 `cluster.local` 的名稱，記得 `ndots` 造成的額外查詢（第 16 章）。

### 邊緣：CDN 與 www（第 19、21、25 章）

CDN 負責三件事：就近終結 TLS（憑證由 CDN 受管、90 天）、快取靜態檔、以暖連線回源。快取規則沿用第 21 章：匿名首頁 `s-maxage=60, stale-while-revalidate=30`，個人化頁面 `private`，帶 hash 的靜態檔 `immutable`，帶登入 cookie 一律 bypass。cache key 要正規化（排序 query、移除 `utm_*`），避免命中率被追蹤參數打碎。origin shield 讓多個 PoP 的 miss 只回源一次；purge 一律指定路徑，不用 purge everything，第 25 章的回源暴增就是前車之鑑。HSTS 已加入 preload，所有子網域只能走 HTTPS（第 19 章）。

### API 路徑：LB、nginx、gunicorn、Flask（第 20、24、25、41、43 章）

API LB 是 L7：它要讀 SNI 選憑證、讀 Host 與路徑做路由、以 `/readyz` 做 HTTP 健康檢查（interval 5 秒、timeout 2 秒、fall 2、rise 3），不能只檢查 TCP 連得上（第 10、25 章）。nginx 負責覆寫或附加 `X-Forwarded-For`（只信任 VPC 與 CDN 回源網段）、產生 `x-request-id`、對 upstream 維持 keepalive，並以 `default_server` 對未知 Host 回 444。gunicorn 依 46.7 節的保守估算擴到 110 個 worker；第 43 章已改用 gthread，若壓測顯示大部分時間在等資料庫與下游服務，每台能撐的 rps 會比估算高，主機數可以往下修，但資料庫連線要以 thread 數計算並加上連線池上限。timeout 鏈由外往內遞減：client 最長、LB 次之、nginx、gunicorn、Flask 呼叫下游時再用 `x-deadline-ms` 傳遞剩餘時間（第 24、43 章），內層永遠比外層先放棄，才不會讓外層已經放棄的請求還在內層佔資源。付款 `POST /v1/payments` 必帶 `Idempotency-Key`，讓重試與超時重送都安全。

### 登入與授權（第 26–30 章）

`auth.shengsheng.example` 和 API 共用 LB，但它的負載型態不同：平時很低，開學週與撞庫攻擊時暴增。限速依第 26 章的規則分三層：(帳號, IP)、IP、帳號。網頁採 BFF：瀏覽器只拿 `__Host-sid` 這類 HttpOnly cookie，token 留在伺服器端；App 與即時服務用 ES256 的 JWT，有效 5 分鐘，資源伺服器以快取的 JWKS 在本機驗證，不必每次問 auth。refresh token 14 天、每次使用即輪替。企業 SSO 走 OIDC，callback 在 `auth.shengsheng.example/callback`。服務之間：`reco` 以 client credentials 取得 300 秒的 token；金流 webhook 以 HMAC-SHA256 簽章驗證原始 body、容許 300 秒，並以 `webhook_events` 去重（第 30 章）。

### 即時服務：uvicorn 與 WebSocket（第 31–33、42 章）

即時服務不放在 Flask 裡，因為 WSGI 的一個請求佔一個 worker，而一條 WebSocket 會掛幾個小時；ASGI 的 event loop 才能用一個 process 照顧幾千條閒置連線。入口是 L4 LB：WebSocket 不需要 L7 的路由，L4 讓 LB 不必解密、也不必理解 Upgrade；TLS 在 nginx 終結。心跳的時間要和每一層的逾時對齊：server 每 25 秒 ping、nginx `proxy_read_timeout` 75 秒、LB idle 120 秒，由內而外遞增，心跳才能讓每一層都看到流量。房間狀態放 Redis：pub/sub 負責跨 gateway 的 fan-out，每個房間一條有上限的序號日誌負責補發；補不回來時送 `event: reset` 要 client 改打 state API。部署時逐台排空，並讓 client 用指數退避加 jitter 重連，避免第 33 章的重連驚群。

### 視訊：SFU 與 TURN（第 34–37、39 章）

一對一與小班課都走 SFU（第 37 章的理由：錄影、隱藏老師家的 IP、連線成功率、單一媒體管線）。SFU 是有狀態的：DTLS 的金鑰在節點上，所以不能放在 L4 LB 後面隨意分配；教室第一位參與者加入時，signaling 挑一台負載最低的 SFU 寫進 room 註冊表，之後的人都連同一台。每台 SFU 有自己的公網 IP，ICE-lite、UDP 40000，管理介面 7070 只開 VPC 內。小班課開三層 simulcast，SFU 依每位接收者的頻寬估計選層（GCC／TWCC）。TURN 與 SFU 同區，只服務 SFU：`allowed-peer-ip` 只放行 SFU 的 VPC 位址，帳密是 1 小時的 HMAC 短效帳密。擴到 9 台 SFU 時，`allowed-peer-ip` 要同步擴大，否則新節點上的教室對需要 TURN 的學生完全不通，這是 46.16 節的第一個錯誤。

### 直播：SRT ingest 到 LL-HLS（第 38 章）

推流端走 SRT：講者常在飯店或家裡，路徑有丟包，SRT 在 UDP 上用有期限的重傳換取穩定；latency 依講者的 RTT 設定（經驗上 3–4 倍 RTT 起跳，libsrt 的 `SRTO_LATENCY` 單位是毫秒、ffmpeg URL 的 `latency` 單位是微秒），UDP 被擋時退回 RTMPS。每場講座一組新的 passphrase，stream ID 只用來選頻道，不當秘密。觀看端走 LL-HLS：2 秒 segment、0.5 秒 part，延遲約 3–5 秒，靠 CDN 擴展；上台發問的少數人走 WHEP 經 SFU，延遲 1 秒內。CDN 的 cache key 要能區分 `_HLS_msn` 與 `_HLS_part`，blocking 請求要合併，否則 origin 會被每秒數萬個請求打垮。

### 雲端：VPC、security group 與 Kubernetes（第 5、7、16、44 章）

VPC 10.20.0.0/16 依第 5 章切成每個 AZ 一塊 /18，每塊依序是 app /20、public /24、data /24。有狀態且需要固定公網 IP 與大量 UDP 的元件（SFU、TURN、ingest）留在 VM 上；無狀態的 HTTP 服務與內部服務（`reco`、webhook worker、轉碼 job）逐步搬進 Kubernetes 的 namespace `live`，以 Service 名稱互相發現，入口用 Gateway API 的實作（ingress-nginx 已封存）。security group 是 stateful 的允許清單，network ACL 是 stateless 的第二道防線（第 7、44 章）。對外連線（呼叫金流 `pay.example.net`、推播閘道）經 NAT gateway，出口 IP 固定，對方才能設允許清單。

## 46.10 失效模式與降級

Joe 接著問：「每一個方塊都會壞。挑五個，告訴我學生會看到什麼。」小晴的回答從一個原則開始：**每一種失效都要有一個比「全部失敗」更好的降級狀態**，而且降級要自動發生、使用者看得懂。

| 失效 | 學生看到的 | 偵測 | 降級或恢復 | 章節 |
|---|---|---|---|---|
| 一台 gunicorn 主機卡住 | 少數請求變慢 | `/readyz` 連續 2 次失敗（約 10 秒） | LB 移出；其他主機要有 N+1 的餘裕 | 25、43 |
| CDN 某個 PoP 或整家故障 | 靜態檔載入失敗 | 合成監測、RUM 錯誤率 | 切到備援 CDN（DNS TTL 300 秒）；origin 要扛得住未快取的流量 | 15、25 |
| Redis primary 故障 | 聊天暫停、顯示「重新連線中」，WebSocket 不斷 | gateway 的 publish 錯誤 | replica 升格；以序號補發，補不回來送 reset | 33 |
| 一台 SFU 故障 | 該教室畫面凍結數秒 | signaling 收不到 SFU 心跳、client ICE 失敗 | 註冊表改指派新節點，client 重新 offer，10 秒內恢復 | 37 |
| 企業網路封鎖 UDP | 視訊連不上 | ICE 只剩 relay candidate | TURN over TLS 443；延遲較高但能上課 | 36、37 |
| 學生頻寬不足 | 畫質下降 | 頻寬估計下降 | simulcast 降層 → 只送音訊 → 保留聊天與白板 | 37、39 |
| 講者的推流網路中斷 | 直播停格 | ingest 收不到封包 | 播放 slate 畫面；講者端備援推流（第二條 SRT 或 RTMPS） | 38 |
| auth 服務故障 | 已登入的人不受影響；新登入失敗 | 登入錯誤率 | JWT 在本機驗證可撐到過期（5 分鐘）；refresh 失敗才會被登出 | 27 |
| 一個 AZ 故障 | 部分連線中斷後重連 | LB 健康檢查、雲端事件 | 跨 AZ 的 LB 與 N+1；Redis replica 升格 | 5、44 |
| 部署 rt 時 | 聊天短暫重連 | 連線數下降與重連速率 | 逐台排空、jitter 重連、補發 | 33 |
| 憑證到期 | 整個網域打不開 | 從外部逐一檢查每個副本、CT 監控 | 自動續約；受管憑證；依效期比例告警，不用固定的「剩 30 天」 | 19 |

這張表有兩個欄位要一起讀。「學生看到的」決定了降級的優先順序：同樣是故障，「畫質變差」遠比「進不了教室」能接受，所以視訊的降級鏈從畫質開始一路退到聊天。「偵測」決定了恢復速度：`/readyz` 的參數讓 LB 在約 10 秒內移出故障主機，而 DNS 的切換受限於 TTL，最長要五分鐘，所以要依「能接受多久」選擇在哪一層做切換。auth 那一列也說明了短效 JWT 的另一面：它讓資源伺服器不依賴 auth 也能驗證，auth 短暫故障時大家還能繼續上課；但 auth 停太久，所有人會在 refresh 失敗時一起被登出。

教室的降級可以畫成一條階梯，每一步都保留比下一步更多的功能：

```text
 正常：720p 雙向視訊（UDP 直連 SFU）
   │ 頻寬估計下降
   ▼
 降層：SFU 改送 360p／180p（simulcast），老師端不必知道
   │ UDP 不通或持續丟包
   ▼
 中繼：TURN over TLS 443（TCP 的 HOL 讓延遲抖動變大，但能上課）
   │ 頻寬仍不足
   ▼
 只有音訊：關掉影像，Opus 約 40 kbps
   │ 媒體完全不通
   ▼
 文字教室：聊天＋白板（WebSocket 走 TCP 443，最容易穿越企業網路）＋提示換網路
```

由上往下，每往下一階都犧牲一點體驗、換取更高的連線成功率。這條階梯的設計關鍵是「每一階都能自動進入」：simulcast 降層由 SFU 依頻寬估計決定，TURN 由 ICE 依 candidate 優先順序自動退回，只有最後兩階需要前端判斷並提示使用者。第 39 章的除錯流程就是沿著這條階梯反向追查：學生說「只有聲音」，代表影像已經被降掉了，要回頭看頻寬估計與丟包。

## 46.11 安全邊界

Rita 的問題是：「信任邊界在哪裡？每一跳誰驗證誰？」小晴把系統分成四個區域，畫出每一條跨區的連線：

```text
  ┌─ Internet（不可信）────────────────────────────────────────────────────────────┐
  │  學生、老師、講者、攻擊者（例如繞過 CDN 的 198.51.100.99）                       │
  └───────┬────────────────┬───────────────┬──────────────┬──────────────┬─────────┘
          │ TLS（CDN 憑證）  │ TLS（api／auth）│ TLS（rt）      │ DTLS-SRTP    │ SRT AES
  ┌───────▼────────────────▼───────────────▼──────────────▼──────────────▼─────────┐
  │ 邊緣區：CDN edge、API LB、rt LB、SFU、TURN、ingest                              │
  │  WAF 與 DDoS 防護、限速、只開必要 port；TURN 只轉送到 SFU                         │
  └───────┬──────────────────────────┬─────────────────────────────────────────────┘
          │ XFF 只信任 VPC＋CDN 網段  │ 只接受 LB 的 security group
  ┌───────▼──────────────────────────▼─────────────────────────────────────────────┐
  │ 應用區（app 子網、Kubernetes namespace live）：nginx、gunicorn、uvicorn、reco    │
  │  使用者身分：session cookie／JWT（iss、aud、exp）；服務身分：mTLS（SPIFFE）或 HMAC  │
  └───────┬────────────────────────────────────────────────────────────────────────┘
          │ 只接受 app 的 security group；DB 帳號依服務分開
  ┌───────▼───────────────────────┐      ┌─ 管理區 ─────────────────────────────────┐
  │ 資料區：PostgreSQL、Redis       │      │ ops 10.20.3.17：只經 VPN 10.8.0.0/16，    │
  └───────────────────────────────┘      │ mTLS＋SSO；SFU 管理 7070 只開 VPC 內       │
                                         └─────────────────────────────────────────┘
```

由上往下，每穿過一條線都有一次驗證。Internet 到邊緣：每一種流量都加密，HTTP 用 TLS、媒體用 DTLS-SRTP、推流用 SRT 的 AES，而且憑證或金鑰的位置各不相同。邊緣到應用：應用區只接受 LB 的 security group，nginx 只相信來自 VPC 與 CDN 回源網段的 `X-Forwarded-For`，其他來源的 header 一律覆寫，這樣第 25 章那個偽造 XFF 的攻擊者拿不到假的來源 IP。應用區內部：使用者身分由 cookie 或 JWT 承載，每個服務都自己驗證 `aud`，`api` 的 token 不能拿去連 `rt`；服務之間用 mTLS 或 HMAC 簽章，不因為「在 VPC 裡」就互相信任。資料區只接受應用區的連線，而且每個服務用自己的資料庫帳號，一個服務被攻破不等於整個資料庫被攻破。

| 邊界 | 允許 | 拒絕 | 為什麼 |
|---|---|---|---|
| `www` 的回源 | CDN 回源網段 198.51.100.224/27 | 其他來源以 Host `www` 直連 | 防止繞過 CDN 的快取規則與 WAF |
| API LB | 任何來源的 TCP 443 | 其他 port | 公開 API |
| SFU | 任何來源的 UDP 40000 | 管理 7070 只開 VPC | 媒體要讓所有人連；管理面不能外露 |
| TURN | UDP／TCP 3478、TCP 443；只轉送到 SFU 的 VPC 位址 | 轉送到 resolver、metadata、DB 等其他位址 | 避免 TURN 被當成 SSRF 跳板（第 37 章） |
| ingest | UDP 9000；passphrase 正確、stream ID 對應有效的講座 | 錯誤 passphrase、未知頻道 | 講者位置不固定，不能只靠來源 IP |
| 資料區 | app 與 rt 的 security group | 其他一切 | 最小權限 |
| ops | VPN 網段＋client 憑證＋SSO | Internet | 內部後台不暴露在公網 |

這張表的「拒絕」欄和「允許」欄一樣重要。TURN 那一列是最容易被忽略的：TURN 的本質是「替持有帳密的人把封包送到指定位址」，若不限制目的地，它就是攻擊者進入 VPC 的捷徑。ingest 那一列說明了另一個原則：當來源 IP 無法預測時，存取控制就要移到協定層（passphrase 與 stream ID 裡的短效 token），而不是靠 security group。

## 46.12 擴展與取捨

最後十分鐘，阿德問：「如果明年再成長十倍，哪裡先壞？你現在做的決定，哪些到時候要推翻？」小晴沿著 46.7 節的表逐層回答。

**API 先撞到資料庫**。worker 數乘以 10 之後，資料庫連線數到上千條，單一 primary 的寫入與連線管理先成為瓶頸；做法依序是連線池代理、把讀取導向 replica、把熱門的「找老師」清單放進快取，最後才是依學生或地區切分資料。**即時服務先撞到大房間與 broker**：連線數本身可以水平擴展，但單一 Redis 承擔所有 fan-out 有上限，十倍時要依房間切分 broker，並讓大型講座的聊天改成取樣或摘要（第 33 章）。**SFU 的成本與距離同時變成問題**：200 Gbps 的媒體出口費是最大的帳單，而美國學生連台北的 SFU 延遲太高，要在美國加一個 SFU 區域，跨區的教室用 SFU cascading（兩地 SFU 之間轉送一份串流，第 37 章）。**直播觀眾增加十倍反而最輕鬆**：LL-HLS 經 CDN 擴展，origin 只看到每秒幾十個請求，主要成本是 CDN 流量費。

多區域是最大的一個取捨。美東學生的「找老師」頁，即使 46.14 節所有優化都做了，API 仍要跨洋；把 API 部署到美國區域可以把那 180 ms 的 RTT 變成十幾毫秒，但資料要嘛跨區複製（寫入延遲、一致性），要嘛美國區只服務唯讀的查詢。小晴的建議是先做唯讀：老師清單與課程資訊在美國區有唯讀副本，預約與付款仍寫回主區域，因為那兩個操作次數少、可以接受多一個 RTT，而且需要強一致性。

| 決定 | 現在的選擇 | 放棄了什麼 | 何時重新考慮 |
|---|---|---|---|
| 入口 | HTTP 走 CDN＋L7、WebSocket 走 L4、媒體直連 | 單一入口的簡單 | 若改用 WebTransport 等新協定 |
| API 位置 | 單一區域，CDN 動態加速 | 遠地使用者的 API RTT | 海外使用者超過兩成，先做唯讀副本 |
| 即時狀態 | Redis 兼 broker 與房間狀態 | broker 的水平擴展 | 單一 Redis 的 CPU 或頻寬到七成 |
| 一對一視訊 | 也走 SFU | 約 6 Gbps 的頻寬（P2P 可省） | 不錄影、不在意 IP 暴露的產品 |
| 直播觀看 | LL-HLS 為主、WHEP 只給上台的人 | 所有人都 1 秒內的互動 | 觀眾少、互動是核心時改全 WebRTC |
| token | 5 分鐘 JWT＋輪替的 refresh token | 即時撤銷 | 需要秒級撤銷時加 introspection 或撤銷清單 |
| 部署平台 | 無狀態服務進 Kubernetes，SFU、TURN、ingest 留 VM | 統一的部署方式 | Kubernetes 的 UDP 與 host network 方案成熟、團隊熟悉 |

這張表的最右欄是面試官最想聽的：每一個決定都有一個明確的「重新考慮」條件，代表你知道它在什麼規模或需求下會失效，而不是把它當成永遠正確的答案。

## 46.13 面試官追問與回答

架構審查的最後一段是自由追問。以下是 Rita、Joe 與阿德當天實際問的問題，以及小晴的回答（事後整理）。

**追問 1：為什麼 `www` 經 CDN，`api` 卻不經？** `www` 有大量可快取的靜態檔與匿名頁面，CDN 的三種價值都拿得到。`api` 的回應幾乎都是個人化的，快取價值低，而且第 21 章的首頁快取事故說明了「讓個人化內容經過共享快取」的風險。代價是 `api` 對遠地學生要跨洋交握，46.14 節的模型顯示這條支線是美東學生的 critical path；如果要改，第一步是讓 CDN 只做 TLS 終結與動態加速、對 `api` 一律不快取，而不是打開快取。

**追問 2：`rt` 為什麼用 L4 LB，TLS 卻在 nginx 終結？** WebSocket 不需要 L7 的路由判斷，L4 LB 只轉送 TCP，不必理解 Upgrade、也不會因為 L7 的逾時設定把長連線切斷。把 TLS 放在自己管理的 nginx，可以完整控制 `proxy_read_timeout` 與心跳的對齊，也能在 nginx 上做 Origin 檢查。代價是憑證要自己分發到三台 nginx，第 19 章的事故後改成以 DNS-01 集中申請。

**追問 3：WebSocket 為什麼不改走 HTTP/3？** WebSocket over HTTP/3 有規格，但瀏覽器與伺服器的支援都有限，實務上 WebSocket 仍走 HTTP/1.1 的 Upgrade、跑在 TCP 上，所以不受 QUIC connection migration 保護，學生從 Wi-Fi 切到 4G 時要靠應用層重連與補發（第 13、32、33 章）。WebTransport 是更自然的替代，但截至 2026 年 10 月規格仍在 WG Last Call，現在只做評估。

**追問 4：SFU 為什麼不放在 LB 後面？** SFU 的每條連線都有 DTLS 金鑰與 SRTP 狀態，必須一直落在同一台；UDP 的 LB 只能用五元組猜「連線」，學生的 NAT 重新綁定或換網路時，封包可能被送到另一台。所以每台 SFU 有自己的公網 IP，由 signaling 依 room 註冊表告訴 client 要連哪一台，這是有狀態服務的典型做法。

**追問 5：一對一課為什麼不用 P2P 省頻寬？** P2P 能省約 6 Gbps（今年的尖峰），但會失去錄影、暴露老師家的 IP、在雙方都在嚴格 NAT 後時更依賴 TURN（而 P2P 的 TURN 兩段都是 Internet 流量），還要維護兩條媒體管線。對語言家教這個產品，這些代價比頻寬費更貴。

**追問 6：直播為什麼不全部用 WebRTC？** 6,000 位觀眾若都走 WHEP，SFU 的出口要再多十幾 Gbps，而且無法利用 CDN。講座的互動需求是「聊天室跟得上」，3–5 秒的 LL-HLS 已經足夠；真正需要 1 秒內的只有上台發問的幾個人，讓他們走 WHEP 就好。這是「依延遲需求分群」的設計。

**追問 7：一個 AZ 掛了會發生什麼？** API 與 rt 的 LB 都是跨 AZ 的，健康檢查在十秒內把故障 AZ 的後端移出；剩下的機器靠 N+1 撐住。Redis primary 若在故障的 AZ，replica 升格，期間聊天顯示重新連線、恢復後以序號補發。SFU 節點在故障 AZ 上的教室會斷線，client 依註冊表重新指派、10 秒內恢復。要事先驗證的是：剩下一個 AZ 的容量是否真的夠，這要靠演練，不能只看設計圖。

**追問 8：某位老師爆紅、一場講座湧入十倍觀眾，哪裡先壞？** LL-HLS 經 CDN，觀看端通常撐得住；先壞的是互動：講座聊天室的 fan-out 隨人數成長，600 人的房間變成 6,000 人時，每則訊息要送 6,000 份，要改成慢速模式或只顯示取樣。其次是開場前幾分鐘的登入與「進入講座」API，要靠限速、CDN 快取講座資訊與事先擴容。

**追問 9：怎麼防止攻擊者繞過 CDN 直接打 origin？** 回源的 LB 是公開位址，攻擊者只要知道 IP 就能直連，跳過 WAF 與快取。做法有三層：`www` 的 Host 只接受 CDN 回源網段；CDN 回源時帶一個 origin 才知道的 header 或使用 mTLS；nginx 的 XFF 只信任 VPC 與 CDN 網段，直連者偽造的 XFF 會被覆寫（第 25 章）。

**追問 10：做完這些，美東學生還是要 0.9 秒，下一步呢？** 依 46.14 節的模型，剩下的 critical path 是 API 的 preflight 與請求，各要一次跨洋 RTT。最便宜的一步是去掉 preflight：把 `/v1/teachers` 改成不需要 preflight 的請求，或把首屏需要的清單直接嵌在 HTML 裡（伺服器端渲染），讓 API 支線消失。再下一步才是美國區域的唯讀副本。

**追問 11：`rt` 怎麼做到零停機部署？** 新版本先上線並通過健康檢查；舊節點從 LB 移出後不再接新連線，對既有連線送 close code 1012（Service Restart），client 在 jitter 視窗內隨機等待、再以指數退避重連到新節點，並用 Last-Event-ID 式的序號補發（第 31、33 章）。jitter 視窗依第 33 章的「連線數 ÷ 每秒可接受的握手數」計算，讓每秒新增的 TLS 交握不超過 rt nginx 能承受的量。

**追問 12：要監控哪些指標？** 每一層挑一兩個最能代表使用者體驗的指標：RUM 的 FCP、LCP 與 API 延遲（依地區分組）；CDN 的命中率與回源延遲；API 的 p99 與 5xx；WebSocket 的連線成功率、重連速率與 loop lag；WebRTC 的 ICE 成功率、TURN 比例、凍結次數；直播的 rebuffer 比例與延遲。告警依 SLO 的 error budget 燃燒速度設定，而不是每個指標設一條門檻。

**追問 13：成本最大的是哪一塊？怎麼省？** 是 SFU 與 TURN 的媒體出口流量，量級是 API 的兩百倍。省的方式依效果排序：simulcast 讓每位接收者只收需要的層、小格畫面用 180p；TURN 與 SFU 同區，中繼的那一段在 VPC 內；只在需要時錄影；再考慮與雲端或 transit 業者談頻寬的承諾用量。

這十三題有一個共同的答題模式：先講決定，再講理由，最後講代價與何時會改。阿德說，光有決定是 junior 的回答，加上理由是 mid-level，能主動說出代價與重新考慮的條件，才是面試官想聽到的。

## 46.14 動手做：頁面載入模型與全系統容量估算器

這一節把本章的兩個問題寫成兩段程式。第一段是頁面載入時間模型，輸入 RTT、HTTP 版本、每個網域的連線數、是否重用連線與 CDN 命中率，輸出「找老師」頁的各個里程碑；第二段是全系統容量估算器，從尖峰在線人數推出每一層的連線數、頻寬與伺服器數，並用前面章節的數字交叉驗證。兩段都只用標準函式庫、不碰網路，是純粹的模型，數字的意義在於比較不同設定之間的差距，而不是預測真實的毫秒數。

### 實驗一：「找老師」頁的載入時間模型

資源大小沿用第 22 章的「找老師」頁：HTML 30 KB、`app.css` 40 KB、`app.js` 120 KB、80 張各 6 KB 的大頭照，以及一次 8 KB 的 API 回應。模型做了四個簡化：只算往返次數、slow start 與頻寬，不模擬丟包；HTML 一到齊就發現所有子資源；HTTP/2 與 HTTP/3 在無丟包時只差在交握；`api` 預設不經 CDN，第一次呼叫要做 CORS preflight。

```python
import unicodedata

# ---- 固定假設：「找老師」頁 /teachers，資源大小沿用第 22 章 ----
MSS, INITCWND = 1448, 10            # 第 12 章：初始 cwnd 10 個 segment
HTML, CSS, JS, AVATAR, N_AVATAR, API_BODY = 30_000, 40_000, 120_000, 6_000, 80, 8_000
FLASK_MS, STATIC_MS, JS_EXEC_MS, RENDER_MS, DNS_COLD_MS = 30, 2, 40, 30, 40
BW_MBPS = 50                        # 學生家用下載頻寬（假設）


class Conn:
    """一條連線的 cwnd：模擬 slow start，算出送完 n bytes 需要幾輪 RTT。"""
    def __init__(self, warm):
        self.cwnd = 10**9 if warm else INITCWND * MSS     # warm：cwnd 早已長大

    def rounds(self, nbytes):
        n = 0
        while nbytes > 0:
            nbytes -= self.cwnd
            self.cwnd *= 2
            n += 1
        return max(n, 1)


def wire(nbytes):
    return nbytes * 8 / (BW_MBPS * 1000)                  # 頻寬造成的傳輸時間（ms）


def handshake_rtts(version, warm):
    if warm:
        return 0                                          # 連線還在，不必交握
    return 1 if version == "h3" else 2                    # QUIC 1 RTT；TCP＋TLS 1.3 共 2 RTT


def load(rtt, version="h2", conns=6, warm=False, hit=None, preconnect=False,
         api_edge=False, edge_rtt=15, edge_origin_rtt=170):
    """回傳各里程碑（ms）。hit=None 代表沒有 CDN；hit=0.92 代表 CDN 命中率 92%。"""
    cdn = hit is not None
    c_rtt = edge_rtt if cdn else rtt                      # 瀏覽器到 www：有 CDN 就是到 edge
    miss_cost = edge_origin_rtt + STATIC_MS               # 一次 miss：edge 回源一趟
    exp_miss = (1 - hit) * miss_cost if cdn else STATIC_MS
    dns = 0 if warm else DNS_COLD_MS

    # ① HTML：個人化頁面不快取；CDN 就近終結 TLS，再用暖連線回源
    first = Conn(warm)
    sent = dns + handshake_rtts(version, warm) * c_rtt
    ttfb = sent + c_rtt + (edge_origin_rtt if cdn else 0) + FLASK_MS
    html_done = ttfb + (first.rounds(HTML) - 1) * c_rtt + wire(HTML)

    # ② 子資源：HTML 到齊後才發現 CSS、JS 與 80 張大頭照
    if version == "h1":                                   # 每條連線一次一個請求
        lanes = [[html_done, first]] + [
            [html_done + handshake_rtts(version, warm) * c_rtt, Conn(warm)] for _ in range(conns - 1)]
        done = []
        for size in [CSS, JS] + [AVATAR] * N_AVATAR:
            lane = min(lanes, key=lambda x: x[0])
            lane[0] += lane[1].rounds(size) * c_rtt + exp_miss + wire(size)
            done.append(lane[0])
        css_done, js_done, imgs_done = done[0], done[1], max(done)
    else:                                                 # h2／h3：一條連線多工、依優先順序
        start = html_done
        def deliver(nbytes):
            c = Conn(warm)
            c.cwnd = first.cwnd                           # 沿用 HTML 那條連線長大後的 cwnd
            return start + c.rounds(nbytes) * c_rtt + wire(nbytes)
        css_done = deliver(CSS) + exp_miss
        js_done = deliver(CSS + JS) + exp_miss
        p_any = (1 - hit ** N_AVATAR) if cdn else 1.0     # 80 張裡至少一張 miss，整批就要等回源
        imgs_done = deliver(CSS + JS + AVATAR * N_AVATAR) + p_any * (miss_cost if cdn else STATIC_MS)

    # ③ API：api.shengsheng.example 預設不經 CDN，直接連 API LB
    a_rtt = edge_rtt if api_edge else rtt
    behind = edge_origin_rtt if api_edge else 0           # 經 edge 時，請求還要回源一趟
    want = js_done + JS_EXEC_MS                           # JS 執行後才發出 fetch
    setup_start = ttfb if preconnect else want            # preconnect：HTML 一到就先把連線暖好
    t = max(setup_start + dns + handshake_rtts(version, warm) * a_rtt, want)
    if not warm:
        t += a_rtt + behind                               # CORS preflight（Max-Age 內可省）
    api_done = t + a_rtt + behind + FLASK_MS + wire(API_BODY)

    return {"TTFB": ttfb, "FCP": max(html_done, css_done) + RENDER_MS,
            "圖片": imgs_done, "API": api_done, "完成": max(api_done, imgs_done) + RENDER_MS}


def cells(text):                                          # 中文字在終端機佔兩格
    return sum(2 if unicodedata.east_asian_width(ch) in "WF" else 1 for ch in text)


def pad(text, width, right=False):
    space = " " * (width - cells(text))
    return space + text if right else text + space


SCENARIOS = [
    ("① 無 CDN、HTTP/1.1、冷啟動", dict(rtt=180, version="h1")),
    ("② CDN 92%、HTTP/1.1", dict(rtt=180, version="h1", hit=0.92)),
    ("③ CDN 92%、HTTP/2", dict(rtt=180, version="h2", hit=0.92)),
    ("④ ③＋preconnect api", dict(rtt=180, version="h2", hit=0.92, preconnect=True)),
    ("⑤ ④改用 HTTP/3", dict(rtt=180, version="h3", hit=0.92, preconnect=True)),
    ("⑥ ⑤＋api 也經 CDN edge", dict(rtt=180, version="h3", hit=0.92, preconnect=True, api_edge=True)),
    ("⑦ ④的第二頁（連線重用）", dict(rtt=180, version="h2", hit=0.92, warm=True)),
]
COLS = ("TTFB", "FCP", "圖片", "API", "完成")
print(pad("美東學生（RTT 180 ms）", 30) + "".join(pad(c, 7, right=True) for c in COLS))
res = {}
for name, kw in SCENARIOS:
    res[name[0]] = r = load(**kw)
    print(pad(name, 30) + "".join(f"{r[c]:>7.0f}" for c in COLS))

print("\nCDN 命中率與「80 張大頭照到齊」（情境 ④）")
for h in (0.50, 0.92, 0.99, 0.999):
    r = load(rtt=180, version="h2", hit=h, preconnect=True)
    print(f"  命中率 {h:>6.1%}：至少一張 miss 的機率 {1 - h ** N_AVATAR:>6.1%}，圖片到齊 {r['圖片']:>4.0f} ms")

print("\nHTTP/1.1 每個網域的連線數（情境 ②）")
for n in (1, 2, 6):
    print(f"  {n} 條連線：圖片到齊 {load(rtt=180, version='h1', hit=0.92, conns=n)['圖片']:>5.0f} ms")

assert res["①"]["完成"] > 3 * res["④"]["完成"]           # CDN＋HTTP/2＋preconnect：快三倍以上
assert res["⑤"]["完成"] < res["④"]["完成"] and res["⑥"]["完成"] < res["⑤"]["完成"]
assert res["⑦"]["完成"] < 0.6 * res["④"]["完成"]         # 重用連線最省
```

先看主表的第一列：沒有 CDN、HTTP/1.1、全部冷啟動，清單完整出現要 3,746 ms，正好重現故事裡 RUM 的 3.7 秒。拆開來看，TTFB 610 ms 是 DNS 40 加上三個跨洋 RTT 再加 Flask 30；最大的一塊是圖片的 3,716 ms，因為 80 張大頭照在 6 條連線上要排 14 輪，每輪 180 ms。第二列加上 CDN：TTFB 降到 285 ms、FCP 從 1,013 降到 370 ms、圖片從 3.7 秒降到 755 ms，這一步就把總時間砍掉三分之二，證明對遠地使用者最有效的單一手段是縮短 RTT。

接下來幾列要看「哪一欄是最大值」。第二列之後，「完成」都由 API 決定，不再是圖片：`api` 不經 CDN，要跨洋做 DNS、TCP、TLS、preflight 與 GET。所以第三列改用 HTTP/2，圖片從 755 降到 639 ms，「完成」卻只少了 54 ms，因為圖片已經不在 critical path 上。第四列加上 `preconnect`，API 的交握提早開始，省了 129 ms；第五列改用 HTTP/3，API 的交握從 2 個 RTT 變 1 個，再省 195 ms。第六列讓 `api` 也經 CDN edge，只再省 81 ms，因為交握已經被 preconnect 藏起來了，剩下的 preflight 與 GET 仍要回源跨洋。第七列是第二次瀏覽，所有連線、DNS 與 preflight 快取都在，555 ms 中大部分是 HTML 回源與 API 各一次跨洋。

第二段印出命中率的影響。在情境 ④，命中率 50% 與 92% 的「圖片到齊」一模一樣（639 ms），因為 80 張裡至少一張 miss 的機率都接近 100%，整批都要等那一次回源；99% 時機率降到 55%，期望時間才開始下降；99.9% 時降到 480 ms。這就是 46.4 節說的：對成批的資源，儀表板上的平均命中率會誤導你，要看「一批裡有沒有長尾」。

第三段是 HTTP/1.1 的連線數：同樣在 CDN 後面，只開 1 條連線時圖片要 2.8 秒，2 條 1.6 秒，6 條 755 ms。這說明瀏覽器為什麼對每個網域開 6 條連線，也說明 HTTP/2 用一條連線就能做到比 6 條更好的原因：它不需要排隊。最後三個 `assert` 把結論固定下來：CDN＋HTTP/2＋preconnect 至少快三倍、HTTP/3 與經 edge 的 API 依序再快、重用連線最省。

### 實驗二：從 60,000 人到每一層的容量估算器

估算器把 46.5 節的七步寫成程式。所有假設集中在 `DEFAULTS`，每個數字旁邊註明出處；SFU 的頻寬公式沿用第 37 章（一對一不開 simulcast、小班依版面選層），TURN 依第 37 章的 8% 比例與加權平均頻寬，即時服務依第 33 章的每個 worker 5,000 條連線。

```python
import math
import unicodedata

# 每一個數字都是「假設」，要換成你自己的量測；註解標出出處章節
DEFAULTS = dict(
    peak_users=60_000,          # 尖峰同時在線（第 33 章開學週估算）
    rooms_1v1=4_000, rooms_small=600, small_size=6,   # 視訊教室（第 37 章今年的兩倍）
    live_viewers=6_000, lectures=2,                   # LL-HLS 觀眾、同時進行的講座
    pv_per_min=0.5, api_per_page=2, static_per_page=42, cdn_hit=0.92,
    in_class_api_interval_s=30,  # 上課與看直播的人，每 30 秒打一次 API（心跳、狀態）
    flask_ms=40, util=0.6, workers_per_host=9,        # 保守以 process 計：每台 9 個（第 42 章的 sync 配置）
    ws_per_user=1.15, ws_per_worker=5_000, uvicorn_workers=4, ws_fill=0.8, ws_kbps=10,
    sfu_safe_gbps=3.0, turn_ratio=0.08, turn_safe_gbps=4.0,
    abr_mbps=(4.5, 2.5, 1.2, 0.7, 0.128), viewer_avg_mbps=2.2, part_s=0.5, shields=2,
)
MBPS_720P_AV, SIMULCAST = 1.54, 2.19               # 第 37 章：一路 720p 影音、三層 simulcast


def ceil_div(a, b):
    return math.ceil(a / b - 1e-9)


def estimate(**override):
    p = {**DEFAULTS, **override}
    rows = []

    # ---- 人數分流：每個人在尖峰這一刻在做什麼 ----
    in_video = p["rooms_1v1"] * 2 + p["rooms_small"] * p["small_size"]
    browsing = p["peak_users"] - in_video - p["live_viewers"]

    # ---- Web 與 API：Little's law，同時在忙的 worker = 到達率 × 服務時間 ----
    pv = browsing * p["pv_per_min"] / 60
    flask_rps = pv * (1 + p["api_per_page"]) + (in_video + p["live_viewers"]) / p["in_class_api_interval_s"]
    busy = flask_rps * p["flask_ms"] / 1000
    workers = math.ceil(busy / p["util"])
    app_hosts = ceil_div(workers, p["workers_per_host"]) + 1                # N+1
    static_rps = pv * p["static_per_page"]
    rows.append(("CDN（www 靜態）", f"{static_rps:,.0f} rps",
                 f"{static_rps * 10_000 * 8 / 1e9:.2f} Gbps", f"回源 {static_rps * (1 - p['cdn_hit']):,.0f} rps"))
    rows.append(("API LB→nginx→gunicorn", f"{flask_rps:,.0f} rps",
                 f"{flask_rps * 8_000 * 8 / 1e6:.0f} Mbps", f"{workers} workers → {app_hosts} 台"))

    # ---- 即時服務：WebSocket 長連線，瓶頸是連線數 ----
    ws = p["peak_users"] * p["ws_per_user"]
    per_host = p["ws_per_worker"] * p["uvicorn_workers"] * p["ws_fill"]
    rt_hosts = ceil_div(ws, per_host) + 1
    rows.append(("rt：nginx→uvicorn", f"{ws:,.0f} WS",
                 f"{ws * p['ws_kbps'] / 1e6:.2f} Gbps", f"{rt_hosts} 台（nginx fd {2 * ws:,.0f}）"))

    # ---- SFU：一對一不開 simulcast；小班每人上傳三層，下行依版面 ----
    n = p["small_size"]
    small_in = n * SIMULCAST
    small_out = (n - 1) * (1.5 + 0.04 + (n - 2) * (0.15 + 0.04)) + (n - 1) * (0.5 + 0.04)
    sfu_in = (p["rooms_1v1"] * 2 * MBPS_720P_AV + p["rooms_small"] * small_in) / 1000
    sfu_out = (p["rooms_1v1"] * 2 * MBPS_720P_AV + p["rooms_small"] * small_out) / 1000
    sfu_nodes = ceil_div(max(sfu_in, sfu_out), p["sfu_safe_gbps"]) + 2        # N+1＋排空用一台
    pps = sfu_out * 1e9 / 8 / 1_200                                          # 約 1,200 bytes 一個封包
    rows.append(("SFU（UDP 40000）", f"{in_video:,} 人",
                 f"收 {sfu_in:.1f}／送 {sfu_out:.1f} Gbps", f"{sfu_nodes} 台（{pps / 1e6:.1f} Mpps）"))

    # ---- TURN：每個 byte 進一次、出一次 ----
    turn_users = in_video * p["turn_ratio"]
    avg_mbps = (p["rooms_1v1"] * 2 * 2 * MBPS_720P_AV
                + p["rooms_small"] * (small_in + small_out)) / in_video
    relayed = turn_users * avg_mbps / 1000
    turn_nodes = ceil_div(2 * relayed, p["turn_safe_gbps"]) + 1
    rows.append(("TURN（TLS 443）", f"{turn_users:,.0f} 人",
                 f"中繼 {relayed:.2f}／網卡 {2 * relayed:.2f} Gbps", f"{turn_nodes} 台"))

    # ---- 直播：SRT ingest → 轉碼 → LL-HLS 經 CDN ----
    ladder = sum(p["abr_mbps"])
    viewer_rps = p["live_viewers"] * 2 / p["part_s"]                          # 每個 part：playlist＋part
    origin_rps = len(p["abr_mbps"]) * 2 / p["part_s"] * p["shields"] * p["lectures"]
    rows.append(("LL-HLS（CDN）", f"{p['live_viewers']:,} 人／{viewer_rps:,.0f} rps",
                 f"{p['live_viewers'] * p['viewer_avg_mbps'] / 1000:.1f} Gbps",
                 f"origin {origin_rps:.0f} rps、{ladder * p['shields'] * p['lectures']:.0f} Mbps"))
    ingest = p["lectures"] * (p["abr_mbps"][0] + p["abr_mbps"][-1]) * 1.25    # SRT 預留 25% 重傳
    rows.append(("SRT ingest＋轉碼", f"{p['lectures']} 路",
                 f"{ingest:.1f} Mbps", f"轉碼 {p['lectures'] + 1} 台（含備援）"))

    db_conns = workers + rt_hosts * p["uvicorn_workers"]
    return dict(rows=rows, in_video=in_video, browsing=browsing, app_hosts=app_hosts,
                rt_hosts=rt_hosts, sfu_nodes=sfu_nodes, sfu_in=sfu_in, sfu_out=sfu_out,
                turn_nodes=turn_nodes, turn_nic=2 * relayed, db_conns=db_conns, workers=workers)
```

## 46.15 在工作上怎麼用

**前端：把延遲預算放進 CI 與 RUM。** 每個重要頁面訂一份預算（例如「找老師」頁的 JS 首屏不超過 150 KB、關鍵網域不超過 3 個），在 CI 中檢查 bundle 大小；RUM 依地區與網路類型分組看 p75，美東與台灣分開看，才不會被平均值掩蓋。在 DevTools 的 Network 面板開啟 Slow 4G 節流，用 Waterfall 欄找出最長的那條依賴鏈，再決定該用 `preconnect`、`preload` 還是拆檔。

**後端與 SRE：用 curl 把一個請求拆成每一站。** `curl -w` 能印出 DNS、TCP、TLS、TTFB 各段的累計時間，是驗證 46.2 節延遲預算最快的工具（示意輸出，數字為示意）：

```bash
curl -o /dev/null -s -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n' \
     --http2 https://www.shengsheng.example/teachers
# ↓ 示意輸出（從美東的合成監測主機）
dns 0.021  tcp 0.037  tls 0.054  ttfb 0.262  total 0.271

curl -o /dev/null -s -w 'tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}\n' \
     https://api.shengsheng.example/v1/courses
# ↓ 示意輸出：api 不經 CDN，交握各要一次跨洋 RTT
tcp 0.203  tls 0.386  ttfb 0.601
```

這些數字都是從開始算起的累計值：第一個請求的 TCP 只花了 16 ms（0.037 − 0.021），說明連到的是附近的 edge；TTFB 比 TLS 多了 208 ms，是 edge 回源加上 Flask 的時間。第二個請求的 TCP 與 TLS 各約 180 ms，一眼就看出 `api` 沒有經過 edge。把這兩行指令放進合成監測，依地區畫成時間序列，就是延遲預算的儀表板。

**SRE：容量審查的檢查清單。** 每季用 46.14 節的估算器更新一次，並逐項確認：

- 每一層「最先用完的資源」是否有監控與告警（worker 使用率、WebSocket 連線數與 fd、SFU 的 Gbps 與 pps、TURN 網卡、DB 連線數）。
- 壓測取得的單台上限是否過期（換機型、換版本、換 codec 都要重測）。
- N+1 是否以「剩下的機器」驗證過，而不只是算出來的；至少每季做一次單一 AZ 的故障演練。
- 依賴清單（DNS、CDN、IdP、金流）是否都有降級方案與對應的 runbook。
- 擴容時的連帶設定是否同步：TURN 的 `allowed-peer-ip`、security group、XFF 信任清單、資料庫的連線上限。

**影音工程師：每週看三個比例。** Joe 把 TURN 比例、simulcast 低層比例與「只有音訊」的教室比例畫在同一張圖上。TURN 比例上升通常代表新的企業客戶或某個 ISP 的變化，會直接影響 TURN 容量；低層比例上升代表學生端頻寬變差或頻寬估計出問題（第 39 章）；只有音訊的比例是降級階梯的底部，它上升時要立刻查。

**資安工程師：每次架構變更都對照 46.11 節的邊界表。** 新增元件時問三個問題：它屬於哪一個區域？跨區的連線由誰驗證誰？「拒絕」欄寫了什麼？Rita 特別要求任何會「替別人發出連線」的元件（TURN、webhook 轉發、URL 預覽）都要有目的地允許清單。

## 46.16 常見錯誤與除錯

| 症狀 | 原因 | 怎麼確認 | 怎麼修 |
|---|---|---|---|
| 新增 SFU 節點後，部分教室裡用企業網路的學生完全沒畫面 | TURN 的 `allowed-peer-ip` 沒有擴大到新節點的 VPC 位址 | 這些教室都在新節點上；TURN log 顯示 peer 被拒；學生的 ICE 只剩 relay candidate | 擴容流程加入同步 TURN 允許清單；以設定管理產生清單 |
| 升級 HTTP/2 後，遠地使用者的載入時間幾乎沒變 | 瓶頸不在同網域的請求排隊，而在另一個網域的交握或 API | DevTools Waterfall 找最晚完成的那條鏈；看 API 的 Connection ID 是否為新連線 | 對關鍵網域 `preconnect`、去掉 preflight、或把資料嵌進 HTML |
| CDN 命中率 92%，但頁面的圖片仍常常很晚才到齊 | 一批 80 個資源裡幾乎必有一個 miss，整批等最慢的回源 | 依頁面看「至少一個 miss」的比例；看 miss 物件的 `age` 與回源延遲 | 拉長 TTL 並用 hash 檔名、origin shield、合併小圖 |
| `preconnect` 加了，DevTools 卻顯示真正的請求又建了一條新連線 | 少了 `crossorigin`，預先建的連線屬於另一個連線池 | 看 preconnect 的連線與 fetch 的連線 ID 是否不同 | 依請求的憑證模式加上 `crossorigin`（或移除） |
| 擴容 API 後開始出現資料庫 `too many connections` | worker 數（gthread 則是 thread 數）乘以每個的連線數超過 `max_connections` | 數 DB 連線依來源主機分組；對照 worker 與 thread 數 | 連線池代理、限制每台主機的連線池上限 |
| 開學週 rt 的 nginx 記錄 `worker_connections are not enough` | 每條 WebSocket 在 nginx 佔 2 個連線，設定照 HTTP 的經驗值 | nginx error log；`ss -s` 的連線數接近設定值的一半 | `worker_connections` 與 `worker_rlimit_nofile` 設為連線數的兩倍以上並留餘裕 |
| 壓縮開啟後，CPU 上升但頁面沒有變快 | 對圖片、影片、WOFF2 也做了壓縮，或動態回應用了最高等級 | 看 `Content-Type` 與 `Content-Encoding` 的組合；比較壓縮前後大小 | 只壓文字類型；靜態檔事先壓好，動態回應用中低等級 |
| 容量估算說夠，上線當晚卻撐不住 | 用平均值估算、沒有算重連尖峰或故障後的剩餘容量 | 對照當晚的連線建立速率與 TLS 交握數；看故障節點的時間點 | 以尖峰最壞組合估算；N+1 以演練驗證；部署與重連加 jitter |

這張表的前三列都屬於同一個錯誤模式：**優化了不在 critical path 上的東西**。升級 HTTP/2、提高命中率、增加 preconnect 本身都沒錯，但如果沒有先找出最長的那條鏈，就可能把力氣花在不影響總時間的地方。後幾列則是容量估算的錯誤模式：**只算了主要資源，沒算連帶的資源**。worker 帶來資料庫連線，WebSocket 帶來 nginx 的 fd，SFU 節點帶來 TURN 的允許清單；擴容時一起檢查，才不會修好一層、壞掉另一層。

## 46.17 動手練習

1. **延伸實驗一：第三方字型**。在模型中加入一個放在第三方網域的字型（30 KB），它要等 CSS 到齊才會被發現，並且擋住文字的繪製。比較有沒有對該網域 `preconnect`、有沒有 `preload` 字型時的 FCP。
   答案要點：字型要等 CSS，再重做 DNS、TCP、TLS，是典型的「晚發現＋新網域」；`preconnect` 只省交握，`preload` 讓它和 CSS 同時開始，兩者一起用效果最好。若字型改由 `www` 自己提供，連交握都省了。

2. **延伸實驗二：企業客戶與熱門講座**。把 `turn_ratio` 改成 0.2、`live_viewers` 改成 20,000，看哪幾層的伺服器數改變。
   答案要點：TURN 的中繼頻寬變成約 8.2 Gbps、網卡約 16.4 Gbps，要 5 台加 N+1 共 6 台，需要新的公網位址與允許清單；LL-HLS 的請求數變成每秒 80,000 個，CDN 流量約 44 Gbps，但 origin 的負擔幾乎不變。SFU 與即時服務的數字不變；API 因為分流改變而變成約 1,760 rps、15 台（瀏覽中的人變少，但看直播的人每 30 秒也會打一次 API），這正是「從單一起點分流」的好處：改一個數字，所有相關的層一起更新。

3. **用 DevTools 找 critical path**（真實工具）。打開任何一個你常用的網站，在 Network 面板開啟 Disable cache 與 Slow 4G 節流，重新整理，找出最晚完成、且決定畫面出現時間的那條依賴鏈（Initiator 欄能看出誰觸發了誰）。
   答案要點：通常是「HTML → 某個 JS → 某個 API」或「HTML → CSS → 字型」。記下鏈上每一段是否有新的 DNS、Initial connection、SSL，判斷哪一段可以用 `preconnect`、`preload` 或連線重用省掉。

4. **用 curl 拆一個請求**（真實工具）。在本機執行 `python3 -m http.server 8765 --bind 127.0.0.1`，用 46.15 節的 `curl -w` 指令對 `127.0.0.1:8765` 發請求，再對任一個你能存取的 HTTPS 網站做同樣的事，比較各段時間。
   答案要點：本機的 DNS 與 TCP 接近 0、沒有 TLS（`time_appconnect` 為 0）；遠端網站的 `time_connect − time_namelookup` 大約就是一個 RTT，`time_appconnect − time_connect` 是 TLS（TLS 1.3 約一個 RTT）。連續執行兩次，觀察 DNS 時間的變化，那是快取命中的效果。

5. **四十五分鐘模擬面試**。找一位同事，用 46.6 節的時間分配，題目換成「設計一個線上考試系統（監考視訊、即時交卷、成績公布）」。結束後用三個問題自評：需求表的每一列是否都對應到一個設計？估算是否找出了最先用完的資源？是否主動講了至少三種失效模式與降級？
   答案要點：監考視訊多半是「多人上傳、少數人觀看」，和教室不同；交卷是突發的寫入尖峰，要靠佇列與 idempotency key；成績公布是讀取尖峰，適合 CDN 與快取。能說出這些差異，就代表你掌握的是方法，而不是背下聲聲 Live 的答案。

## 46.18 常見網路面試題

最後一節收錄 15 題最常見的網路面試題。每題列出答題要點與對應章節；回答時同樣先講結論，再講機制，最後講實務上的取捨或你遇過的例子。

**1. 在瀏覽器輸入網址按下 Enter 之後，發生了什麼？**
答題要點：依序講 URL 解析與 HSTS、DNS（快取層次）、TCP 交握、TLS 交握與憑證驗證、HTTP 請求經 CDN、LB、reverse proxy 到應用程式、回應與快取、瀏覽器解析與子資源、渲染。加分的是能說出每一站大約幾個 RTT，以及哪幾站能用 CDN、連線重用、HTTP/3 省掉。對應：第 1 章，細節分散在第 14、10、18、20–22、25 章。

**2. TCP 三向交握為什麼是三次？TIME_WAIT 與 CLOSE_WAIT 有什麼不同？**
答題要點：三次是為了讓雙方各自確認對方收到自己的 ISN，並擋掉延遲的舊 SYN。TIME_WAIT 在主動關閉方，持續 2×MSL，確保最後的 ACK 能重送、舊 segment 消失，通常無害；CLOSE_WAIT 在被動關閉方，只有應用程式 close 才會離開，持續增加就是程式沒關連線。對應：第 10 章。

**3. TCP 和 UDP 差在哪？什麼時候選 UDP？**
答題要點：TCP 提供連線、可靠、依序的 byte stream 與擁塞控制；UDP 只是加上 port 的 datagram，保留訊息邊界、不重傳。即時影音、DNS、遊戲選 UDP，因為遲到的資料沒有價值；QUIC 則在 UDP 上重建可靠傳輸，以便在使用者空間演進。對應：第 9、11、13 章。

**4. 什麼是 head-of-line blocking？HTTP/2 和 HTTP/3 各解決了哪一種？**
答題要點：HTTP/1.1 的 HOL 是同一條連線上的請求必須依序回應；HTTP/2 用 stream 多工解決了這一層，但所有 stream 共用一條 TCP，一個封包遺失會讓所有 stream 一起等，這是 TCP 層的 HOL；HTTP/3 在 QUIC 上讓每個 stream 獨立遺失恢復，才解決了這一層。對應：第 12、22 章。

**5. DNS 的解析流程是什麼？為什麼改了 DNS 記錄，有些使用者還是連到舊 IP？**
答題要點：stub resolver 問 recursive resolver，後者從 root、TLD 到權威伺服器迭代查詢，並依 TTL 快取。改記錄後，各層快取（瀏覽器、OS、resolver、應用程式 runtime）要等 TTL 過期，有些還不遵守 TTL；搬遷前要先降低 TTL 並等舊 TTL 過期。對應：第 14–16 章。

**6. HTTPS 的 TLS 交握做了什麼？憑證怎麼驗證？**
答題要點：TLS 1.3 在 1 RTT 內完成金鑰交換（ECDHE）、server 以憑證與簽章證明身分、雙方導出對稱金鑰。client 驗證憑證的名稱（SAN）、效期、到受信任 root 的鏈與簽章，以及撤銷狀態。0-RTT 可被重放，只適合 idempotent 請求；mTLS 讓 client 也出示憑證。對應：第 17–19 章。

**7. HTTP 快取怎麼運作？CDN 怎麼避免把 A 的個人資料給 B？**
答題要點：`Cache-Control`（`max-age`、`s-maxage`、`private`、`no-store`）決定能不能存、存多久，`ETag` 與條件請求用於重新驗證。共享快取只能存可以共享的回應：個人化回應標 `private`、帶登入 cookie 的請求 bypass、`Vary` 與 cache key 要包含所有會改變回應的因素。對應：第 21、25 章。

**8. L4 和 L7 load balancer 差在哪？health check 要怎麼設計？**
答題要點：L4 依 IP 與 port 轉送 TCP／UDP，不看內容、可以不解密；L7 終結 HTTP，能依 Host、路徑、header 路由、改寫 header。health check 要打真正的 HTTP 端點（例如 `/readyz`）並檢查依賴，只檢查 TCP 會被「核心完成交握、應用程式卡死」騙過；fall 與 rise 的參數決定移出與恢復的速度。對應：第 10、25 章。

**9. CORS 是什麼？為什麼有 preflight？它和 CSRF 有什麼關係？**
答題要點：CORS 是瀏覽器在同源政策下，讓 server 以 `Access-Control-Allow-*` header 明確允許跨來源讀取回應的機制；非簡單請求（自訂 header、非簡單 method）要先送 OPTIONS preflight 詢問。CORS 保護的是「讀取回應」，不阻止請求被送出，所以防 CSRF 要靠 SameSite cookie、CSRF token 與 Origin 檢查。對應：第 23 章。

**10. Session 和 JWT 怎麼選？JWT 要怎麼撤銷？**
答題要點：session 由 server 保存狀態，撤銷容易、每次要查儲存；JWT 是自包含的簽章 token，資源伺服器能在本機驗證，但簽出後在過期前難以撤銷。實務上用短效 access token（例如 5 分鐘）加可輪替、可撤銷的 refresh token；驗證時固定 alg、檢查簽章、`exp`、`iss`、`aud`。網頁可採 BFF 讓 token 不進瀏覽器。對應：第 26、27 章。

**11. 說明 OAuth 2.0 的 authorization code＋PKCE 流程。OIDC 多了什麼？**
答題要點：client 把使用者導向 authorization server，帶 `state` 與 PKCE 的 code challenge；使用者同意後拿回一次性的授權碼，client 以 code verifier 換 token，證明自己就是發起者。OAuth 解決的是委派授權；OIDC 在其上加上 ID token、userinfo 與 discovery，用來「登入」。OAuth 2.1 草案要求 PKCE，並移除 implicit 與 password grant。對應：第 28、29 章。

**12. Polling、SSE 和 WebSocket 怎麼選？**
答題要點：short polling 簡單但浪費；long polling 降低延遲但每則訊息一個請求；SSE 是單向的 server 推送，走一般 HTTP、內建重連與 Last-Event-ID；WebSocket 是全雙工、訊息導向的長連線，適合聊天與白板。選擇看方向性、頻率、proxy 與 LB 的支援，以及是否需要二進位資料。對應：第 31、32 章。

**13. 怎麼把 WebSocket 聊天擴展到數萬條連線？**
答題要點：gateway 盡量無狀態、只維持連線；用 pub/sub broker 做跨 gateway 的 fan-out；每個房間一條序號日誌支援去重與補發；心跳與每一層的 idle timeout 對齊；慢 client 的佇列要有上限並依訊息類型丟棄；部署時排空並讓 client 以 jitter 重連。估算時要算連線數、fd、記憶體與 fan-out。對應：第 33 章。

**14. WebRTC 怎麼穿越 NAT？為什麼多人視訊用 SFU？**
答題要點：signaling（應用自訂）交換 SDP 與 ICE candidate；ICE 嘗試 host、srflx（由 STUN 得知的公網位址）與 relay（TURN 中繼）候選，連線檢查成功後以 DTLS 交換金鑰、用 SRTP 加密媒體。mesh 的上行頻寬與編碼負擔隨人數成長；SFU 讓每人只上傳一份，伺服器只轉送不解碼，配合 simulcast 為每位接收者選畫質。對應：第 7、35–37 章。

**15. 直播的延遲從哪裡來？HLS、LL-HLS、WebRTC 怎麼選？**
答題要點：延遲來自編碼、contribution 傳輸、轉碼、封裝（等一個 segment）與播放器 buffer（通常落後三個 segment）；傳統 HLS 的延遲主要是 segment 長度乘了好幾次。HLS 最穩、最便宜、可到百萬人；LL-HLS 用 partial segment 與 blocking reload 降到數秒；WebRTC 在一秒內但每位觀眾都要 SFU 的資源。推流端在丟包網路上用 SRT。對應：第 38 章。

這 15 題可以依角色挑重點：後端面試多半集中在 1、2、5、7、8、10；前端加上 9 與 4；SRE 再加上 3 與 13；影音職缺則是 14、15。不論哪一題，能把答案連回一個真實系統（例如本章的聲聲 Live）並給出數字，都比背定義有說服力得多。

## 本章重點整理

- 延遲預算把總目標分給 DNS、TCP、TLS、TTFB、下載與渲染；只有縮短 critical path，也就是最長的那條依賴鏈，總時間才會變短。
- 網頁的瓶頸多半是往返次數而不是頻寬：新連線要 2 個 RTT 交握，回應還要依 slow start 分好幾輪，第一輪約 14 KB。
- 連線重用發生在每一段：瀏覽器到 edge、edge 到 origin、nginx 到 gunicorn、應用程式到資料庫；兩端的閒置上限要對齊，內層要比外層先關。
- `preconnect` 與 103 Early Hints 不刪掉交握，只把它移出關鍵路徑；交握比騰出的空檔長時，剩下的部分仍在路徑上，`crossorigin` 要與請求的憑證模式一致。
- CDN 的價值有三種：縮短 RTT、快取命中與暖的回源連線；個人化頁面不能快取，仍能從前後兩者受益。
- 平均命中率會誤導成批資源的判斷：80 個資源各 92% 命中，幾乎每次都至少有一個要回源，整批等最慢的那一個。
- 壓縮只用於文字類型，能讓回應落進第一輪 RTT；已壓縮的圖片與影片再壓只會浪費 CPU，秘密與使用者輸入不要放在同一個壓縮回應裡。
- HTTP/2 省的是同網域的排隊，HTTP/3 再省 1 RTT 的交握與 TCP 層的 head-of-line blocking；效益與 RTT 成正比，CDN 縮短 RTT 之後效益變小。
- 容量估算從單一的尖峰在線人數出發，分流、換算成每一層的單位、用 Little's law 算出同時在忙的數量，再加上目標使用率、N+1 與排空的餘裕，最後用已知情境交叉驗證。
- 每一層最先用完的資源不同：API 是 worker 與資料庫連線，WebSocket 是 fd 與記憶體，SFU 是頻寬與 pps，LL-HLS 是 CDN 的請求數。
- 聲聲 Live 依流量性質分開入口：可快取的走 CDN、需要看 header 的走 L7 LB、長連線走 L4 LB、低延遲 UDP 直接連到有狀態的節點。
- 每一種失效都要有比「全部失敗」更好的降級狀態，並且自動進入；教室的降級階梯是降層、TURN、只有音訊、文字教室。
- 安全邊界以區域劃分，每穿過一條邊界都有一次驗證；會替別人發出連線的元件（例如 TURN）一定要有目的地允許清單。
- 面試回答的模式是決定、理由、代價與何時重新考慮；能主動說出失效模式與取捨，並拿出估算數字，才是完整的設計回答。

## 延伸問答

> [!question]- Q1. 手算：46.14 節的模型中，情境 ④ 加了 `preconnect` 只比情境 ③ 快 129 ms，但 API 的交握明明要 2 個 RTT（360 ms）。為什麼沒有省下 360 ms？
> 因為 `preconnect` 不會刪掉交握，只會讓它提早開始。情境 ③ 中，API 的連線要等 JavaScript 執行完才開始建立：`app.js` 約在 374 ms 到齊、執行 40 ms，所以 414 ms 才開始做 DNS（40 ms）與兩個 RTT 的交握，814 ms 才能送出 preflight。情境 ④ 在 HTML 開始抵達的 285 ms 就開始建立連線，到 685 ms（285＋40＋360）完成；這時 JavaScript 早已在 414 ms 想送請求，只好等連線好。
>
> 所以省下的是 814 − 685 ＝ 129 ms，也就是「交握被移出去之後，與其他工作重疊的那一段」。交握本身要 400 ms，而 HTML 抵達到 JavaScript 發出請求之間只有 129 ms 的空檔，剩下的 271 ms 仍在關鍵路徑上。要再省，就要讓交握更早開始（103 Early Hints 讓 edge 在回源的同時就送出 preconnect 提示）、讓交握更短（HTTP/3 只要 1 RTT，這正是情境 ⑤ 再省 195 ms 的原因），或讓這條支線消失（把清單嵌進 HTML）。

> [!question]- Q2. 情境題：CDN 儀表板顯示命中率從 85% 提高到 92%，團隊很高興，但「找老師」頁的 RUM 數字完全沒變。你會怎麼解釋，接下來看什麼？
> 第一個可能是 critical path 根本不在靜態資源上。46.14 節的模型顯示，加上 CDN 之後「完成」時間由 API 決定，圖片早就不是最長的那條鏈，命中率再高也不會讓清單更早出現。這要用 DevTools 或 RUM 的資源時間（Resource Timing）確認最晚完成的是哪個請求。
>
> 第二個可能是成批資源的長尾。即使圖片在 critical path 上，80 張大頭照在 85% 與 92% 命中率下，「至少一張 miss」的機率都接近 100%，整批的完成時間都由一次回源決定，所以平均命中率的進步看不出來。接下來要看的是 miss 物件的分布：是否集中在少數冷門老師的照片、TTL 是否太短、shield 有沒有生效。有效的做法是消除長尾（更長的 TTL 與 hash 檔名、origin shield、合併小圖），或是讓首屏只載入看得到的那幾張圖。

> [!question]- Q3. 設計取捨：有人提議把 API 從 `api.shengsheng.example` 改成 `www.shengsheng.example/api/`，經 CDN 轉送到同一組 LB。這樣能省什麼？要付出什麼代價？
> 能省的很多：同源請求不需要 CORS，也就沒有 preflight；`www` 的連線已經建好（而且是到附近的 edge），API 不必重新做 DNS、TCP、TLS；HTTP/2 讓 API 與靜態檔共用同一條連線。以 46.14 節的模型估計，美東學生的 API 支線會少掉交握與 preflight，大約只剩一次 edge 回源的時間。
>
> 代價也很實際。第一，API 的回應都經過共享快取，CDN 的規則必須保證 `/api/` 一律不快取、帶登入 cookie 時 bypass，第 21 章的快取事故就是規則出錯的後果。第二，同源之後 cookie 會自動附帶，CSRF 的防護（SameSite、CSRF token、Origin 檢查）要更嚴謹，而且 App 與第三方合作夥伴仍需要獨立的 `api` 網域。第三，CDN 成了 API 的必經依賴，CDN 故障時 API 一起受影響，需要備援路徑。所以常見的折衷是網頁前端走同源的 `/api/`，App 與合作夥伴繼續用 `api` 網域。

> [!question]- Q4. 手算：一家大型企業客戶上線後，視訊參與者中需要 TURN 的比例從 8% 變成 20%。以開學週目標（11,600 位參與者、加權平均每人上下行 3.54 Mbps、單台 TURN 安全上限 4 Gbps）計算，TURN 要幾台？還有哪些地方要跟著改？
> 需要中繼的人數是 11,600 × 20% ＝ 2,320 人，中繼頻寬是 2,320 × 3.54 Mbps ≈ 8.2 Gbps。TURN 每個 byte 進來一次、出去一次，網卡要處理約 16.4 Gbps，除以單台 4 Gbps 是 4.1，要 5 台，再加 N+1 共 6 台，是原本 3 台的兩倍。
>
> 連帶要改的地方有幾個。公網位址要從 203.0.113.50–.52 再擴，DNS 的 `turn` 名稱或 `iceServers` 設定要加入新節點；security group 要開放新節點的 3478 與 443；每台的 `allowed-peer-ip` 仍只放行 SFU；短效帳密的金鑰要分發到新節點。另外要注意這群使用者的網路特性：20% 很可能多半只能走 TLS 443，TCP 上的媒體延遲抖動較大，要在 getStats 裡另外追蹤這群人的凍結率，必要時提早讓他們降層。

> [!question]- Q5. 看 log 找原因：開學週第一天晚上八點，rt 的 nginx 開始記錄 `768 worker_connections are not enough`，聊天室大量斷線重連。你怎麼判斷與修正？
> 這個訊息表示 nginx 某個 worker 的連線數到了 `worker_connections` 的上限。關鍵是 nginx 在反向代理 WebSocket 時，每條連線佔兩個 connection（client 端與 upstream 端），所以 768 的設定在每個 worker 上大約只撐得住 380 條 WebSocket。先用 `ss -s` 或 nginx 的狀態頁看目前的連線數，再對照 46.14 節的估算：69,000 條 WebSocket 分給 3 台 nginx，每台約 23,000 條，需要約 46,000 個 connection，遠超過設定。
>
> 修正要一起改三件事：`worker_connections` 依每個 worker 要承擔的連線數乘以 2 再留餘裕；`worker_rlimit_nofile` 與系統的 `ulimit -n` 跟著提高，否則會改成撞到 fd 上限；nginx 到 uvicorn 若用 TCP 的 `127.0.0.1:8001`，還要檢查來源 port 的 28,232 上限，改用 Unix domain socket 可以避開（第 33 章）。斷線重連本身也會放大問題，要確認 client 有指數退避與 jitter，否則每次斷線都是一次重連驚群。

> [!question]- Q6. 情境題：某天晚上資料庫有一條慢查詢，API 的平均服務時間從 40 ms 變成 200 ms。用 Little's law 推演會發生什麼，學生看到的症狀是什麼？
> 以開學週的 1,650 rps 計算，同時在忙的 worker 數從 1,650 × 0.04 ＝ 66 變成 1,650 × 0.2 ＝ 330，而系統總共只有約 126 個 worker（14 台 × 9 個，已經包含 N+1 的那一台）。worker 全部被佔滿後，新請求在 gunicorn 的 listen backlog 裡排隊，backlog 滿了以後新的 SYN 被丟掉（第 10 章），nginx 開始記錄 upstream 逾時並回 504。
>
> 學生看到的是整個網站變慢、部分頁面 504，而且不只是用到那條慢查詢的頁面：因為 worker 是共用的，慢查詢把所有請求的 worker 都佔走了。這說明三件事：每個下游呼叫都要有 timeout，並以 `x-deadline-ms` 讓內層先放棄；資料庫查詢要有 statement timeout；必要時用不同的 worker 池隔離高風險的端點（bulkhead）。監控上，「worker 使用率」與「平均服務時間」比 CPU 更早反映這種問題。

> [!question]- Q7. 情境題：企業客戶北辰物流回報「員工都能進教室、能聊天，但看不到任何視訊」，其他客戶正常。依本章的架構，你會怎麼一層一層排查？
> 能聊天代表 DNS、TLS、`rt` 的 WebSocket（TCP 443）都通，問題集中在媒體平面。第一步看這些教室的 getStats 或伺服器端紀錄：ICE 有沒有成功、選中的 candidate 是 host、srflx 還是 relay（第 36、39 章）。如果所有 candidate pair 都失敗，代表連 SFU 的 UDP 40000 與 TURN 的 UDP、TCP 3478 都被擋了，只能依賴 TURN over TLS 443。
>
> 如果連 TLS 443 的 TURN 也失敗，常見原因是企業的 proxy 會攔截並解密 TLS，或只允許經由明確設定的 HTTP proxy 對外，TURN 的 TLS 連線因此被拒或憑證不被信任。確認方法是請對方 IT 提供防火牆或 proxy 的 log，並在對方網路內用瀏覽器的 WebRTC 測試頁觀察。修正方向依序是：請對方放行 `turn.shengsheng.example` 的 443（不做 TLS 檢查）、確認 TURN 的憑證鏈完整，以及在產品上提供降級階梯最下層的文字教室與明確的提示。

> [!question]- Q8. 設計取捨：access token 只有 5 分鐘，會不會讓 auth 服務負擔太大？auth 故障時又會發生什麼？
> 先算負擔。尖峰 60,000 人在線，若每人每 5 分鐘 refresh 一次，就是 60,000 ÷ 300 ＝ 200 次／秒。每次 refresh 要驗證並輪替 refresh token（一次資料庫寫入）、簽一個 ES256 的 JWT，對一組正常規模的服務並不重；真正要擔心的是同步化：如果大家在同一時刻登入（例如八點開課），refresh 也會集中在同一時刻，所以 client 應在到期前隨機提早一點時間 refresh，把尖峰攤平。
>
> 再看故障。資源伺服器用快取的 JWKS 在本機驗證 JWT，不必呼叫 auth，所以 auth 故障時，已經拿到 token 的人最多還能用 5 分鐘；之後 refresh 失敗，使用者會陸續被要求重新登入，而登入也依賴 auth。這就是短效 token 的取捨：越短，撤銷越及時、外洩的影響越小，但對 auth 可用性的依賴越強。聲聲 Live 的做法是讓 auth 本身多 AZ 部署，並讓教室內的 WebSocket 在連線授權到期時才以 close code 4001 要求換票，避免 auth 短暫故障就把整間教室踢出去。
