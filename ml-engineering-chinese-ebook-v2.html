1.1 AI 軍備競賽：什麼才是決定勝負的關鍵

2024-2026 年的 AI 產業，核心競爭力可以濃縮為三個維度：

維度描述誰做得最好
🔥 算力 (Compute)GPU 叢集規模、互聯頻寬Meta (600K H100), xAI (100K)
📊 數據 (Data)高品質訓練語料的規模與多樣性Google (搜尋+YT), Meta (社群)
🧠 人才 (Talent)頂尖 ML 研究員與工程師OpenAI, DeepMind, Anthropic
💡 實戰觀察：算力是唯一可以用錢直接買到的維度。數據需要時間累積，人才需要文化吸引。所以大公司瘋狂採購 GPU——因為這是最容易「加速」的槓桿。

Scaling Laws 的啟示：

OpenAI 的研究表明，模型性能（loss）與三個因素呈冪律關係：

$$ L(N, D, C) \propto N^{-\alpha} + D^{-\beta} + C^{-\gamma} $$

其中 \(N\) = 參數量、\(D\) = 數據量、\(C\) = 算力。簡單說：越大越好，但報酬遞減。

# 計算 Scaling Law 下的預期 loss 改善
import math

def estimate_loss_improvement(compute_multiplier):
    """
    根據 Chinchilla scaling law 估算 loss 改善
    gamma ≈ 0.05 (compute exponent)
    """
    gamma = 0.05
    improvement = 1 - (1 / compute_multiplier) ** gamma
    return improvement * 100  # 百分比改善

# 如果算力翻倍
print(f"算力 2x → loss 改善約 {estimate_loss_improvement(2):.1f}%")
# 如果算力翻 10 倍
print(f"算力 10x → loss 改善約 {estimate_loss_improvement(10):.1f}%")
# 如果算力翻 100 倍
print(f"算力 100x → loss 改善約 {estimate_loss_improvement(100):.1f}%")

這段程式碼展示了為什麼各大公司要瘋狂堆算力——即使只有幾個百分點的 loss 改善，在最終產品體驗上差異巨大。

1.2 算力需求：訓練一個大模型要多少 GPU？

訓練一個 LLM 的算力需求可以用以下公式估算：

$$ C \approx 6 \times N \times D $$

其中 \(C\) = 總 FLOPS、\(N\) = 參數量、\(D\) = 訓練 token 數。

def estimate_training_compute(
    params_billions: float,
    tokens_trillions: float,
    gpu_tflops: float = 312,
    mfu: float = 0.4,
    num_gpus: int = 1024,
    hours_per_day: float = 24
) -> dict:
    """
    估算訓練大型語言模型所需的時間與成本
    """
    total_flops = 6 * (params_billions * 1e9) * (tokens_trillions * 1e12)
    effective_tflops_per_gpu = gpu_tflops * mfu
    total_flops_per_sec = effective_tflops_per_gpu * 1e12 * num_gpus
    seconds_needed = total_flops / total_flops_per_sec
    days_needed = seconds_needed / (3600 * hours_per_day)
    cost_per_gpu_hour = 2.5
    total_cost = (seconds_needed / 3600) * num_gpus * cost_per_gpu_hour
    
    return {
        "total_pflops": total_flops / 1e15,
        "days": days_needed,
        "gpu_hours": (seconds_needed / 3600) * num_gpus,
        "estimated_cost_usd": total_cost
    }

result = estimate_training_compute(params_billions=70, tokens_trillions=2, num_gpus=2048)
print(f"📊 訓練 70B 模型 (2T tokens, 2048x H100)")
print(f"   總算力需求: {result['total_pflops']:.0f} PetaFLOPS")
print(f"   預估天數: {result['days']:.0f} 天")
print(f"   GPU 時數: {result['gpu_hours']:,.0f} hr")
print(f"   預估成本: ${result['estimated_cost_usd']:,.0f}")
🎯 實戰心得：MFU (Model FLOPS Utilization) 是最關鍵的效率指標。業界頂尖團隊能做到 50-60%，一般團隊約 30-40%。差距 10% 的 MFU 就等於多花幾百萬美金。

def estimate_gpu_memory_for_model(
    params_billions: float,
    precision: str = "bf16",
    optimizer: str = "adam",
    batch_size: int = 1,
    seq_length: int = 4096,
    hidden_dim: int = None
) -> dict:
    """估算模型訓練所需的 GPU 記憶體"""
    bytes_per_param = {"fp32": 4, "bf16": 2, "fp16": 2, "int8": 1}[precision]
    model_memory_gb = (params_billions * 1e9 * bytes_per_param) / (1024**3)
    if optimizer == "adam":
        optimizer_memory_gb = (params_billions * 1e9 * 8) / (1024**3)
    else:
        optimizer_memory_gb = (params_billions * 1e9 * 4) / (1024**3)
    gradient_memory_gb = model_memory_gb
    if hidden_dim is None:
        hidden_dim = int((params_billions * 1e9 / 12) ** 0.5) * 2
    activation_memory_gb = (batch_size * seq_length * hidden_dim * 34 * 2) / (1024**3)
    total_gb = model_memory_gb + optimizer_memory_gb + gradient_memory_gb + activation_memory_gb
    
    return {
        "model_gb": model_memory_gb,
        "optimizer_gb": optimizer_memory_gb,
        "gradient_gb": gradient_memory_gb,
        "activation_gb": activation_memory_gb,
        "total_gb": total_gb,
        "min_gpus_h100": math.ceil(total_gb / 80)
    }

📝 理解確認 Q&A

Q1: 為什麼 Adam 優化器需要額外 8 bytes/parameter？

A: Adam 維護兩個 fp32 的動量估計（first moment 和 second moment），每個 4 bytes，所以 4+4=8 bytes/param。這就是為什麼很多團隊轉向 AdaFactor 或 LION 等低記憶體優化器。

Q2: MFU 40% 代表什麼？剩下 60% 的時間 GPU 在做什麼？

A: GPU 閒置 60% 的時間主要花在：(1) 通訊等待（AllReduce 梯度同步）(2) 記憶體存取延遲 (3) Kernel launch overhead (4) Pipeline bubble。提升 MFU 是 ML 系統工程的核心挑戰。

Q3: 為什麼 Scaling Laws 對 ML 工程師很重要？

A: 因為它讓你在花錢之前就能預測結果。如果你知道 10x 算力只能帶來 ~11% 的 loss 改善，就能理性評估 ROI 而不是盲目堆 GPU。

1.4 FOMO 建議：別慌，冷靜思考

🌱 從零開始理解：AI FOMO 是什麼感覺？

生活比喻

就像 2021 年人人都在買比特幣，你看同事都在訓練大模型、發 paper、拿 offer，內心焦慮「我是不是落後了？」這就是 AI FOMO（Fear Of Missing Out）。

白話解釋

媒體渲染讓每個人覺得不懂 AI 就要被淘汰。但事實是：90% 的公司不需要從頭訓練模型，大部分工作是微調、部署、和 MLOps。

冷靜的現實：

  • 🎯 不是每個問題都需要 LLM（有時候 regex + 規則 > GPT-4）
  • 🎯 大部分公司的瓶頸是數據品質，不是模型大小
  • 🎯 一個好的 7B 微調模型在特定任務上可以打敗通用 70B
  • 🎯 推理成本 >> 訓練成本（長期來看）
# 冷靜的 ROI 計算：自建 vs 調用 API
import math

def compare_build_vs_buy(
    daily_requests: int,
    api_cost_per_1k_tokens: float = 0.01,
    avg_tokens_per_request: int = 500,
    gpu_monthly_cost: float = 2000,
    self_hosted_capacity: int = 50000
):
    """比較自建 vs API 的成本"""
    monthly_api_cost = (daily_requests * 30 * avg_tokens_per_request / 1000) * api_cost_per_1k_tokens
    gpus_needed = math.ceil(daily_requests / self_hosted_capacity)
    monthly_self_cost = gpus_needed * gpu_monthly_cost + 5000
    return {
        "api_monthly": monthly_api_cost,
        "self_monthly": monthly_self_cost,
        "breakeven_requests": int((gpu_monthly_cost + 5000) / 
                                   (avg_tokens_per_request / 1000 * api_cost_per_1k_tokens * 30))
    }

result = compare_build_vs_buy(daily_requests=10000)
print(f"每日 10K 請求:")
print(f"  API 月費: ${result['api_monthly']:,.0f}")
print(f"  自建月費: ${result['self_monthly']:,.0f}")
print(f"  損益兩平點: 每日 {result['breakeven_requests']:,} 請求")

1.7 不請自來的建議

給 ML 新手的 5 條建議：
  1. 先學會用，再學會建 — 先用 API 解決問題，確認問題值得解決後再投資自建

📝 理解確認 Q&A

Q1: 為什麼 Spot Instance 便宜這麼多？風險是什麼？

A: Spot 便宜因為雲端商用閒置容量賣給你，但隨時可以收回（通常 2 分鐘通知）。風險是訓練中斷、checkpoint 可能來不及存。解法：頻繁 checkpoint + 彈性容錯框架。

Q2: 什麼情況下自建叢集比租雲端划算？

A: 通常 GPU 利用率 > 70% 且持續 > 2 年就划算。但要加上：機房電費、冷卻、網管人力、硬體故障替換。很多公司低估了維運成本。

🧪 第一章驗證考題

Q1: 如果你的團隊有 512 張 H100，MFU 從 35% 提升到 45%，等效於「免費」獲得了多少張額外的 H100？

答案：MFU 35%→45% 代表有效算力從 512×0.35=179.2 提升到 512×0.45=230.4，差額 = 51.2 張 H100 的等效算力。換算成雲端成本，以 $3.5/hr/GPU 計，每月省下 51.2 × $3.5 × 24 × 30 ≈ $128,000/月。這就是為什麼系統工程優化的 ROI 極高。

Q2: 一家公司每天有 100K 次 API 呼叫（平均 800 tokens/次），目前用 GPT-4o-mini ($0.15/1M input tokens)。什麼時候應該考慮自建？

答案：月費 = 100K × 30 × 800 / 1M × $0.15 = $360/月。這個量級完全不值得自建（一張 A100 月租就 $2000+）。通常要到 $10K+/月 API 費用且有持續增長趨勢時才考慮自建。自建還要加上工程師人力（$15K+/月）。結論：大多數中小公司應該繼續用 API。

Q3: Chinchilla optimal 建議 70B 模型要用多少 tokens 訓練？如果你只有一半的數據量，會發生什麼？

答案：Chinchilla 規則：最佳 token 數 ≈ 20× 參數量。70B → 1.4T tokens。如果只有 700B tokens（一半），模型會 undertrained（欠訓練）：loss 比 optimal 高，但不會過擬合。實務上的影響是你「浪費了參數」——同樣的 700B tokens 用在 35B 模型上效果可能更好。這就是為什麼 Llama 2 用了 2T tokens 訓練 70B（超過 Chinchilla optimal），因為推論時小模型更便宜。

Q4: 你的老闆說「我們要從頭預訓練一個 13B 模型」。列出 3 個你應該先問的問題來評估是否合理。

答案：(1) 「我們有什麼獨特的數據是公開模型沒見過的？」如果答案是「沒有」，微調就夠了。(2) 「預算多少？訓練 13B + 2T tokens 在 H100 上約需 $500K-1M，團隊準備好了嗎？」(3) 「下游任務的 baseline 是什麼？用 Llama 3 13B 微調能到幾分？」如果微調已經 90+，預訓練的邊際改善可能只有 1-2%，不值得。

Q5: 為什麼 Meta 開源 Llama 系列？這對 AI 算力市場有什麼影響？

答案：Meta 的策略：(1) 降低競爭對手的護城河——如果最好的模型是免費的，OpenAI/Google 的 API 訂閱價值下降；(2) 讓生態系建在 Meta 的模型上——開發者用 Llama 建工具 = Meta 的影響力；(3) 吸引人才——發表論文+開源代碼是最好的招聘廣告。對算力市場的影響：更多公司做微調/推理（需要 GPU）但更少公司做預訓練，推理需求的增長會遠超訓練需求。

2.3 Spot/Preemptible 省錢術

使用 Spot Instance 做 ML 訓練是最有效的省錢策略，但需要工程配套：

"""Spot Instance 容錯訓練的核心模式"""
import signal
from pathlib import Path

class SpotFriendlyTrainer:
    """
    Spot-friendly 訓練器核心設計:
    1. 頻繁 checkpoint（每 N 步）
    2. 捕捉 SIGTERM 信號，被終止前搶救進度
    3. 自動從最近 checkpoint 恢復
    """
    
    def __init__(self, checkpoint_dir: str, save_every_steps: int = 100):
        self.checkpoint_dir = Path(checkpoint_dir)
        self.checkpoint_dir.mkdir(parents=True, exist_ok=True)
        self.save_every_steps = save_every_steps
        self.interrupted = False
        signal.signal(signal.SIGTERM, self._handle_interrupt)
    
    def _handle_interrupt(self, signum, frame):
        print("⚠️ 收到 SIGTERM! 搶存最後 checkpoint...")
        self.interrupted = True
    
    def find_latest_checkpoint(self) -> int:
        checkpoints = list(self.checkpoint_dir.glob("step_*.pt"))
        if not checkpoints:
            return 0
        latest = max(checkpoints, key=lambda p: int(p.stem.split("_")[1]))
        return int(latest.stem.split("_")[1])
    
    def train(self, model, dataloader, optimizer, total_steps: int):
        start_step = self.find_latest_checkpoint()
        if start_step > 0:
            print(f"🔄 從 step {start_step} 恢復訓練")
        
        for step in range(start_step, total_steps):
            if self.interrupted:
                self._save_checkpoint(model, optimizer, step)
                print(f"💾 中斷 checkpoint 已存 @ step {step}")
                return
            # ... 正常訓練邏輯 ...
            if step % self.save_every_steps == 0:
                self._save_checkpoint(model, optimizer, step)
    
    def _save_checkpoint(self, model, optimizer, step):
        path = self.checkpoint_dir / f"step_{step}.pt"
        print(f"  💾 Checkpoint saved: {path}")
🎯 Spot 使用心得：
  • Checkpoint 存到持久化儲存（S3/GCS），不是本機 NVMe
  • 用 save_every_steps=50-100，存一次 < 30 秒，但丟失 100 步可能 10+ 分鐘
  • 配合 auto-scaling group 自動啟動新實例繼續訓練

📝 理解確認 Q&A

Q1: AWS Trainium 跟 NVIDIA H100 的根本差異是什麼？

A: Trainium 是 AWS 自研晶片，用 Neuron SDK 而非 CUDA。優點：性價比好 40-50%、供貨穩定。缺點：生態系不成熟、不能跑所有 PyTorch op。選擇原則：標準 Transformer 架構且不需客製 CUDA kernel，值得試。

Q2: 為什麼「現有基礎設施」的權重這麼高？

A: 跨雲遷移隱性成本：(1) 數據傳輸費 PB 級 = 數萬美金 (2) 重寫 IAM/CI/CD (3) 團隊學習曲線 (4) 服務間延遲增加。省下的 GPU 費用遠不及這些成本。

Q3: Spot 被中斷時，梯度累積到一半怎麼辦？

A: 丟掉就好。中斷在 step 之間就零損失；在 step 中間最多損失一步計算。現代框架自動處理：SIGTERM → 等 step 完成 → 存 checkpoint → 優雅退出。

🧪 第二章驗證考題

Q1: 你的團隊在 GCP 上訓練，老闆說「AWS 的 H100 比較便宜，我們搬過去」。列出 3 個反對的理由和 1 個支持的理由。

答案：
反對：(1) Egress 費用——50TB 訓練數據從 GCS 搬到 S3 = $0.08/GB × 50,000GB = $4,000 傳輸費，加上工程時間；(2) 工具鏈重寫——如果用了 TPU/JAX，換 H100 要重寫訓練腳本為 PyTorch FSDP，可能 2-4 週工程時間；(3) Pipeline 中斷——CI/CD、monitoring、logging 全部要重新接線。
支持：(1) 如果長期(2yr+)算力需求很大，且 AWS 提供了 Reserved 的顯著折扣 or Trainium 適合你的架構，年化省 $100K+ 可能值得遷移一次性成本。

Q2: 你用 Spot Instance 訓練，過去一週被中斷了 12 次。每次恢復需要 15 分鐘載入 checkpoint。如何優化？

答案：(1) 減少 checkpoint 間隔：從每 100 步改為每 50 步，減少中斷後回滾的訓練量；(2) 使用 RAM disk 或本地 NVMe 作為一級快取，再 async 上傳到 S3，避免 checkpoint 載入瓶頸在網路 I/O；(3) 切換到混合策略：用 1-2 台 on-demand 保底（不會中斷），其餘用 Spot，PyTorch Elastic 自動 re-shard；(4) 使用 Nebula/SharedFS checkpoint——把 checkpoint 放在共享檔案系統（FSx Lustre），新節點啟動後不用從 S3 下載，直接 mount 讀取，恢復 < 2 分鐘。

Q3: Google 宣布 TPU v6 性能翻倍。你目前用 H100 訓練。什麼條件下值得遷移到 TPU？什麼條件下不值得？

答案：
值得遷移：(1) 你的模型是純 Transformer（attention + FFN），沒有客製 CUDA kernel；(2) 團隊已經在用 JAX，遷移幾乎零成本；(3) 訓練規模 > 1000 chips 且 Google 提供 committed use discount。
不值得：(1) 你有大量 CUDA-specific 代碼（flash attention custom kernel、CUTLASS gemm）；(2) 團隊只會 PyTorch，學 JAX/XLA 的時間成本 > 3 個月；(3) 你需要最新的 community models（HuggingFace 生態 95% 是 PyTorch first）；(4) 你的 pipeline 依賴 NVIDIA 專有工具（NCCL tuning、Nsight profiling）。

Q4: 比較 FSx Lustre (AWS) vs GCS FUSE (GCP) 作為訓練數據儲存。各自的延遲和吞吐特性如何影響數據載入？

答案：
FSx Lustre：平行檔案系統，設計為 HPC/ML 工作負載。優勢：隨機讀 latency ~1ms、aggregate throughput 可達 TB/s 級、支援 POSIX 語義（直接 open/read/seek）。劣勢：需要 VPC 內部署、容量需預先配置、較貴 ($0.14/GB/月)。
GCS FUSE：把物件儲存 mount 為檔案系統。優勢：無限容量、便宜 ($0.02/GB/月)、與 GCS 原生整合。劣勢：首次讀 latency 50-200ms（物件儲存本質）、小檔案 random read 效能差、不支援完整 POSIX（如 append 效能低）。
影響：如果訓練數據是大量小文件（如 ImageNet 的百萬張圖片），FSx Lustre 勝出 10-50x；如果是少量大文件（如 tokenized text shards），GCS FUSE 配合 prefetch 也能餵飽 GPU。

Q5: 你的公司同時有 AWS 和 GCP 帳號。Research 團隊想用 GCP TPU，Production 團隊在 AWS 上。設計一個最小摩擦的多雲 ML 工作流。

答案：設計原則：訓練在最優硬體上，部署在已有 infra 上。
(1) 模型格式標準化：所有模型存成 SafeTensors/ONNX，不綁定框架；(2) Artifact Registry 用 S3 + 跨雲 sync：研究團隊訓完 push to GCS，有個 Lambda/Cloud Function 自動同步到 S3；(3) 容器化一切：訓練腳本用 Docker，配置用 Hydra/OmegaConf，換環境只改 yaml；(4) Evaluation 跑在兩邊都跑——確保 GCP 訓出的模型在 AWS 推論時精度一致；(5) 統一 experiment tracking：用與雲無關的工具（W&B / MLflow），不用 SageMaker Experiments 或 Vertex ML Metadata 避免鎖定。

🧩 前置知識速覽

  • 浮點數格式：FP32（32 bits, 標準精度）、FP16/BF16（16 bits, 訓練常用）、FP8（8 bits, H100+ 推論加速）。BF16 比 FP16 範圍更大（不易 overflow），是目前訓練首選。
  • 矩陣乘法：深度學習 90%+ 計算都是矩陣乘法（GEMM）。一個 Transformer layer 的 forward pass 包含 QKV projection、Attention、FFN — 全是 GEMM。
  • 記憶體層次：Register → L1 Cache → L2 Cache → HBM → CPU RAM → SSD。越靠近計算單元越快但越小。HBM 是 GPU 的「主記憶體」。
  • 頻寬 vs 延遲：頻寬 = 水管粗細（GB/s），延遲 = 水龍頭打開到水流出的時間（μs）。大資料傳輸看頻寬，小資料傳輸看延遲。

🌱 從零開始理解：什麼是 TFLOP？

生活比喻：想像你在切菜。TFLOP（每秒兆次浮點運算）就像「每秒能切幾刀」。一把普通菜刀每秒切 5 刀（CPU），而一台工業切菜機每秒切 5000 刀（GPU）。GPU 不是刀更鋒利，而是有上千把刀同時切。

白話解釋：TFLOP = Tera Floating-Point Operations Per Second = 每秒 1012 次浮點計算。訓練 LLM 時，模型的每一層都需要大量矩陣乘法，TFLOPS 越高，訓練越快。

為什麼工作上需要：選擇 GPU 時，TFLOPS 決定了你的訓練時間和成本。選錯 GPU 可能讓 3 天的任務變成 3 週。

📝 理解確認 Q&A

Q1：為什麼 H100 的 FP8 TFLOPS 是 FP16 的兩倍？

A：FP8 每個數字只佔 8 bits（FP16 佔 16 bits），同樣的 Tensor Core 每個時鐘週期可以處理兩倍數量的 FP8 運算。代價是精度降低，但 Transformer Engine 會自動在關鍵層保持高精度。

Q2：NVLink 和 PCIe 的頻寬差距為何重要？

A：Tensor Parallelism 需要 GPU 之間每一層都交換 activation。以 70B TP=8 為例，NVLink 4（900 GB/s）比 PCIe（128 GB/s）快 7 倍，80 層累積差距巨大。

Q3：什麼情況下應該選 MI300X 而非 H100？

A：「推論為主 + 模型很大 + 預算有限」。MI300X 有 192 GB HBM 可不切分放下 70B FP16，而 H100 只有 80 GB 必須 TP=2+。但訓練生態（NCCL/DeepSpeed/Megatron）仍以 CUDA 為首選。

🧪 驗證考題 — 舉一反三

Q1：如果你的 70B 模型 MFU 只有 30%（而非業界標準 45%），可能的瓶頸在哪？如何診斷？

A：MFU 低表示 GPU 算力沒被充分利用。可能原因：
(1) Memory-bound：batch size 太小，Tensor Core 空轉等 HBM 讀寫。診斷：用 nsight compute 看 memory throughput 是否接近峰值。
(2) Communication-bound：AllReduce 時間 > 計算時間。診斷：用 NCCL profiler 看通訊佔比。
(3) DataLoader I/O bound：GPU idle 等資料。診斷：nvidia-smi 看 GPU util 是否週期性掉到 0%。
(4) Python GIL / CPU bottleneck：preprocessing 太慢。診斷：htop 看 CPU 是否滿載。
修復順序：先確認 GPU util > 95%（排除 I/O），再用 profiler 看計算 vs 通訊比。

Q2：B200 的 HBM 頻寬是 H100 的 2.4 倍（8.0 vs 3.35 TB/s）。這對推論 latency 的影響比對訓練 throughput 的影響更大，為什麼？

A：推論（尤其是 autoregressive decode）是 memory-bandwidth bound——每生成一個 token 需要讀取整個模型權重一次，但計算量極小（batch=1 時只做 1 次矩陣-向量乘）。所以 HBM 頻寬直接決定 token/s。
訓練是 compute-bound——batch size 大，同一份權重被大量資料重複使用（arithmetic intensity 高），瓶頸在 TFLOPS 而非頻寬。
數字驗證：70B FP16 推論 decode，每 token 讀 140GB 權重。H100: 140/3350 = 42ms/token。B200: 140/8000 = 17.5ms/token。加速 2.4x，幾乎和頻寬比成正比。

Q3：你有預算買 8 張 H100 PCIe 或 4 張 H100 SXM（總成本相近）。訓練 13B 模型該選哪個？

A：選 4 張 H100 SXM。原因：
(1) 13B FP16 = 26GB，4 張 × 80GB = 320GB 綽綽有餘。
(2) SXM 有 NVLink 4（900 GB/s），PCIe 版只有 PCIe Gen5（128 GB/s）互連。Tensor Parallel 或梯度同步快 7x。
(3) 4 GPU TP=4 的通訊開銷遠低於 8 GPU（ring size 小）。
(4) SXM 的 TDP 限制更高（700W vs PCIe 版通常 350W），持續算力更強。
唯一選 8×PCIe 的情況：推論服務需要更多併發（8 卡各跑獨立 request）。

Q4：MI300X 有 192GB HBM 但訓練生態不如 CUDA。如果你的團隊要在 MI300X 上訓練 Llama-70B，最大的工程挑戰是什麼？

A：三大挑戰：
(1) ROCm 軟體成熟度：PyTorch ROCm 版本落後 CUDA 約 1-2 個月，某些 op 缺少 kernel 或效能差。Megatron-LM 官方不支援 ROCm。
(2) 通訊庫：RCCL（ROCm 版 NCCL）在多節點 AllReduce 效能仍落後 NCCL 15-30%，尤其在 Infinity Fabric 跨節點時。
(3) Flash Attention：需要用 AMD 自己的 composable_kernel 或 Triton ROCm backend 重寫，效能驗證和除錯門檻高。
建議：用 AMD 官方的 Megatron-LM fork + ROCm Docker image，先在單節點驗證精度對齊再擴展。

🧩 前置知識速覽

  • 訓練資料流水線：S3/Lustre（持久儲存）→ DataLoader workers（CPU 讀取+預處理）→ GPU（計算）。任何一環慢了，GPU idle 浪費錢。
  • Checkpoint 為什麼重要：大模型訓練可能跑數天到數週。硬體故障率 = 節點數 × 單節點故障率。64 節點跑 2 週，平均會遇到 1-3 次故障。沒 checkpoint = 從頭來過。
  • 頻寬單位：1 GB/s = 8 Gbps。S3 的「100 Gbps」= 12.5 GB/s。別把 bits 和 bytes 搞混。
  • POSIX vs Object Store：Lustre/EFS 是 POSIX（像一般硬碟，有目錄結構），S3 是 Object Store（flat key-value，沒有真正的目錄）。PyTorch 原生支援 POSIX，存 S3 需要額外 library。

🌱 從零開始理解：為什麼儲存速度影響訓練？

生活比喻：GPU 是超高速攪拌機，資料是食材。如果冰箱門（儲存）太小，攪拌機就會空轉等待食材。這叫「I/O bound」——GPU 利用率掉到 30% 以下，你付了 100% 的雲端費用卻只用了 30% 的算力。

白話解釋：大規模訓練的資料流水線：S3/Lustre → DataLoader Workers → GPU。任何一環慢了，GPU 就會 idle。

為什麼工作上需要：ImageNet（144 GB）小問題，但訓練 LLM 的 token 資料集可達 10+ TB。如果 DataLoader 來不及餵 GPU，你的 8×H100 實際上只發揮了 4×H100 的效能。

5.2 Checkpoint 策略

"""
Checkpoint 大小估算公式：

模型參數記憶體 = params × bytes_per_param
Optimizer 狀態 = params × (4+4+4) for Adam FP32 = params × 12 bytes

範例：70B 模型
- 模型 FP16: 70e9 × 2 = 140 GB
- Adam 狀態:  70e9 × 12 = 840 GB (分散在多卡)
- 單個 Checkpoint 總大小: ~140-980 GB (取決於是否存 optimizer)

Checkpoint 寫入時間 = size / write_bandwidth
- NVMe: 980 GB / 5 GB/s = 196 秒 ← 本地暫存
- S3:   980 GB / 10 GB/s = 98 秒 ← 多執行緒上傳
- Lustre: 980 GB / 50 GB/s = 19.6 秒 ← 分散式寫入
"""

import os
import time
import torch
import torch.distributed as dist
from torch.distributed.checkpoint import save, load

def estimate_checkpoint_size(model, include_optimizer=True):
    """估算 checkpoint 大小 (bytes)"""
    param_bytes = sum(p.numel() * p.element_size() for p in model.parameters())
    if include_optimizer:
        optimizer_bytes = sum(p.numel() for p in model.parameters()) * 12
        total = param_bytes + optimizer_bytes
    else:
        total = param_bytes
    return total

def timed_checkpoint_save(model, path, use_distributed=True):
    """帶計時的 checkpoint 儲存"""
    start = time.time()
    if use_distributed and dist.is_initialized():
        save(model.state_dict(), path)
    else:
        torch.save(model.state_dict(), path)
    elapsed = time.time() - start
    size_gb = os.path.getsize(path) / 1e9 if os.path.isfile(path) else 0
    throughput = size_gb / elapsed if elapsed > 0 else 0
    print(f"Checkpoint saved: {size_gb:.1f} GB in {elapsed:.1f}s ({throughput:.1f} GB/s)")

📝 理解確認 Q&A

Q1：為什麼 Lustre 寫入比 S3 快，但大家還是把 Checkpoint 存 S3？

A：Lustre 是暫存層（ephemeral），叢集關閉後資料消失。S3 是持久層（11-9 耐久性）。最佳實踐：每 N 步寫 Lustre（快速恢復），每 M 步非同步上傳 S3（災難恢復）。S3 成本也遠低於 Lustre（~$0.023 vs ~$0.14/GB/月）。

Q2：DataLoader 的 num_workers 應該設多少？

A：經驗法則：num_workers = min(CPU 核心數 / GPU 數, 能填滿 GPU 的最小值)。例如 96 核 8 GPU → 每卡最多 12 workers。觀察 GPU util：< 90% 且 CPU < 50% → 增加 workers；CPU 滿載 → 換 mmap 或 prefetch。

🧪 驗證考題 — 舉一反三

Q1：你的 64-GPU 叢集訓練 70B 模型，每 1000 步存一次 checkpoint（含 optimizer）。如果用 S3 多執行緒上傳（10 GB/s），每次 checkpoint 會讓訓練暫停多久？一天存 10 次的總停機時間？

A：計算：
Checkpoint 大小 = 140 GB (模型) + 840 GB (optimizer) = 980 GB
但用 ZeRO-2/3 或分散式 checkpoint 時，每張卡只存 980/64 = 15.3 GB
情境 A（同步存 S3）：15.3 GB / 10 GB/s = 1.5 秒/卡。但 64 卡同時寫 S3 會競爭帳號級頻寬（100 Gbps = 12.5 GB/s total）！實際 = 980 GB / 12.5 GB/s = 78 秒。一天 10 次 = 13 分鐘。
情境 B（先寫 NVMe + 非同步上傳 S3）：15.3 GB / 5 GB/s = 3 秒暫停，後台上傳不阻塞。一天 10 次 = 30 秒！
結論：永遠用 NVMe 暫存 + async S3 upload。

Q2：你發現 GPU utilization 週期性掉到 0%（每 30 秒掉一次持續 2 秒）。如何判斷是 DataLoader 問題還是 checkpoint 問題？

A：診斷方法：
(1) 頻率判斷：Checkpoint 通常每 N 步一次（如 1000 步，可能 10 分鐘一次）。30 秒一次太頻繁，更可能是 DataLoader。
(2) 確認方法：加 pin_memory=True + 增加 prefetch_factor 看是否消失 → DataLoader。或暫時關閉 checkpoint 看是否消失。
(3) Profiler：torch.profiler 的 timeline 會清楚顯示 CPU→GPU copy 等待（DataLoader）vs disk write 等待（checkpoint）。
(4) 另一個常見原因：epoch 切換時 DistributedSampler shuffle + 重新 seek，也會造成短暫 stall。

Q3：你的訓練資料集 15 TB 在 S3 上。FSx for Lustre（$0.14/GB/月）vs 每次訓練直接從 S3 streaming 讀取。哪個更划算？

A：取決於訓練頻率和持續時間：
FSx 成本：15,000 GB × $0.14 = $2,100/月（固定成本，不管用不用）
S3 streaming 成本：S3 GET requests（$0.0004/1000 requests）+ 出站流量（同 region 免費）。如果每個 epoch 讀完全部資料一次 → 幾乎免費。
但真正的成本是 GPU idle！如果 S3 streaming 讓 GPU util 從 95% 降到 70%，64×H100 的每小時成本 = 64 × $5 = $320/hr。25% idle = $80/hr 浪費。訓練跑 200hr → 浪費 $16,000 >> FSx $2,100。
結論：如果訓練 > 2 週/月，FSx 幾乎必選。S3 streaming 只適合小資料集或極偶爾的訓練。

Q4：Sharded checkpoint（每 GPU 存自己的分片）vs 聚合後單一大檔案。在 64 GPU 場景各有什麼問題？

A：
Sharded（每卡獨立寫）：
✅ 寫入快（並行，無通訊）
✅ 不需要 gather 到 rank 0（省記憶體）
❌ 恢復時 GPU 數量必須相同（64 分片只能用 64 卡讀回）
❌ 產生大量小檔案，S3 list 操作慢
聚合單檔案：
✅ 通用性高（任意 GPU 數恢復）
✅ 方便分享和部署
❌ 需要 gather（rank 0 記憶體可能爆）
❌ 寫入時間 = 全部大小 / 單節點頻寬
最佳實踐：訓練中用 sharded（快速恢復），每天一次聚合存 S3（通用備份）。PyTorch 2.0+ 的 torch.distributed.checkpoint 支援彈性恢復（不同 GPU 數也能讀 sharded ckpt）。

🧩 前置知識速覽

  • 梯度同步：Data Parallel 的每個 step，所有 GPU 的梯度必須取平均。梯度大小 = 模型參數量 × 精度 bytes。70B BF16 = 140 GB 梯度要在所有節點間同步。
  • 頻寬 vs 延遲：大訊息（>100MB）看頻寬，小訊息（<1MB）看延遲。AllReduce 用大訊息，所以主要看頻寬。但 Pipeline Parallel 的 micro-batch 切換是小訊息，看延遲。
  • Gbps vs GB/s：400 Gbps = 50 GB/s（除以 8）。InfiniBand NDR 400 Gbps = 每秒傳 50 GB。
  • TCP vs RDMA：TCP 走 kernel → overhead 大。RDMA 繞過 CPU/kernel 直接存取遠端記憶體 → 延遲低 10 倍以上。分散式訓練必須用 RDMA。

🌱 從零開始理解：為什麼網路是分散式訓練的命脈？

生活比喻：想像 8 間廚房（8 個節點 × 8 GPU = 64 GPU）同時煮一道大菜。每隔 1 秒，所有廚房要「對答案」——把各自的半成品混合再分回去（AllReduce）。如果廚房之間的傳送帶太慢，廚師大部分時間都在等快遞，而不是在煮菜。

白話解釋：Data Parallelism 的每一步都需要同步梯度。梯度大小 = 模型參數量 × 精度。70B FP16 的梯度 = 140 GB。如果網路只有 100 Gbps (12.5 GB/s)，一次 AllReduce 需要 11.2 秒。

為什麼工作上需要：網路頻寬直接決定你能擴展到多少節點。頻寬不足時，加更多 GPU 反而更慢（通訊開銷超過計算加速）。

6.2 AllReduce 時間計算

🌱 AllReduce 是什麼？

AllReduce = 「所有人把自己的梯度加總，然後每個人都拿到加總結果」。Ring AllReduce 是最常用的演算法：N 個 GPU 排成環，每個 GPU 依序傳給下一個，總共 2×(N-1) 步。

"""
AllReduce 通訊時間估算

Ring AllReduce 公式：
  T_allreduce = 2 × (N-1)/N × M / B

  N = GPU 數量（跨節點部分）
  M = 訊息大小（bytes）
  B = 網路頻寬（bytes/sec）
"""

def estimate_allreduce_time(
    model_params_billion: float,
    num_nodes: int,
    gpus_per_node: int = 8,
    bytes_per_param: int = 2,
    network_bandwidth_gbps: float = 400,
    efficiency: float = 0.7,
):
    """估算跨節點 AllReduce 時間"""
    total_gpus = num_nodes * gpus_per_node
    gradient_size_bytes = model_params_billion * 1e9 * bytes_per_param
    gradient_size_gb = gradient_size_bytes / 1e9
    bandwidth_bytes_per_sec = network_bandwidth_gbps * 1e9 / 8
    ring_factor = 2 * (num_nodes - 1) / num_nodes
    theoretical_time = ring_factor * gradient_size_bytes / bandwidth_bytes_per_sec
    actual_time = theoretical_time / efficiency

    print(f"=== AllReduce 時間估算 ===")
    print(f"模型: {model_params_billion}B | 梯度: {gradient_size_gb:.1f} GB")
    print(f"節點: {num_nodes} ({total_gpus} GPUs) | 頻寬: {network_bandwidth_gbps} Gbps")
    print(f"理論: {theoretical_time*1000:.1f} ms | 實際(eff={efficiency}): {actual_time*1000:.1f} ms")
    return actual_time

# 範例
print("【7B, 4 nodes, 400 Gbps】")
estimate_allreduce_time(7, 4)
print("\n【70B, 16 nodes, 400 Gbps】")
estimate_allreduce_time(70, 16)
print("\n【70B, 16 nodes, 100 Gbps (RoCE)】")
estimate_allreduce_time(70, 16, network_bandwidth_gbps=100)

6.3 ZeRO 通訊量分析

"""
ZeRO 通訊量比較

DDP:    2M (AllReduce = ReduceScatter + AllGather)
ZeRO-1: 2M (同 DDP，只省 optimizer 記憶體)
ZeRO-2: 2M (ReduceScatter grad + AllGather param update)
ZeRO-3: 3M (額外 AllGather forward 時取參數)

關鍵洞察：ZeRO-3 通訊量多 50%，但能訓練 N 倍大的模型。
"""

def zero_communication_analysis(model_params_billion, num_gpus, strategy="ddp"):
    M = model_params_billion * 1e9 * 2  # BF16 bytes
    comm = {"ddp": 2*M, "zero1": 2*M, "zero2": 2*M, "zero3": 3*M}
    model_mem = M
    grad_mem = M
    optim_mem = model_params_billion * 1e9 * 12
    mem_per_gpu = {
        "ddp": model_mem + grad_mem + optim_mem,
        "zero1": model_mem + grad_mem + optim_mem / num_gpus,
        "zero2": model_mem + grad_mem / num_gpus + optim_mem / num_gpus,
        "zero3": (model_mem + grad_mem + optim_mem) / num_gpus,
    }
    c = comm[strategy] / 1e9
    m = mem_per_gpu[strategy] / 1e9
    print(f"{strategy.upper()}: 通訊={c:.1f}GB/step | 記憶體={m:.1f}GB/GPU | "
          f"80GB可放: {'✅' if m < 75 else '❌'}")

print("=== 70B, 64 GPUs ===")
for s in ["ddp", "zero1", "zero2", "zero3"]:
    zero_communication_analysis(70, 64, s)

📝 理解確認 Q&A

Q1：為什麼 Tensor Parallel 只在節點內做？

A：TP 每層都需 AllReduce（80 層 = 160+ 次/step）。NVLink 900 GB/s + <1μs 延遲可承受。跨節點 IB 50 GB/s + 1μs+ 延遲會累積成巨大開銷。Data Parallel 每步只需 1 次 AllReduce，可容忍高延遲。

Q2：AllReduce benchmark 只跑出 200 Gbps（理論 400），可能原因？

A：(1) 訊息太小（<10MB），延遲主導；(2) NCCL 未用 GDR，走 PCIe→CPU→NIC；(3) 交換機 oversubscription；(4) PFC/ECN 設定不當導致重傳；(5) rank 映射跨 NUMA。

Q3：ZeRO-3 通訊量比 DDP 多 50%，為什麼有時反而更快？

A：ZeRO-3 可 prefetch（提前 AllGather 下一層）+ overlap（通訊計算重疊）。batch 夠大時計算時間遮蓋 AllGather 延遲。且 ZeRO-3 省記憶體 → 允許更大 batch → 更長計算去遮蓋通訊。

🧪 驗證考題 — 舉一反三

Q1：如果網路頻寬從 400 Gbps 加倍到 800 Gbps，訓練 70B 模型在 16 節點上的 AllReduce 時間會精確減半嗎？為什麼？

A：不會精確減半。原因：
(1) 延遲不變：Ring AllReduce 的 latency term α×2(N-1) 不受頻寬影響。頻寬加倍只降低 bandwidth term。
(2) 軟體開銷恆定：NCCL kernel launch、memory copy、synchronization barrier 有固定開銷（~10-50μs/op），不隨頻寬縮放。
(3) PCIe 瓶頸：如果 NIC 是 PCIe 接入（非 NVLink 直連），PCIe Gen5 128 GB/s 可能成為新瓶頸（800 Gbps = 100 GB/s 已接近 PCIe 極限）。
實際效果：大訊息（>1GB）接近 2x 加速；小訊息（<10MB）可能只有 1.2-1.5x。整體 step time 取決於 overlap 程度。

Q2：你有 32 節點（256 GPU）要訓練 Llama-405B。設計並行策略：TP、PP、DP 各多少？為什麼？

A：分析約束條件：
(1) 記憶體：405B FP16 = 810 GB 純參數。TP=8（一個節點）→ 每卡 ~101 GB > 80 GB ❌。需要 ZeRO-3 或 TP×PP。
(2) 最佳方案：TP=8 (節點內 NVLink) × PP=4 (4 節點串聯) × DP=8 (剩餘 8 組)。
- TP=8：每層 810/80/8 ≈ 12.6 GB/卡 ✅（加 activation/optimizer 後 ~60 GB）
- PP=4：405B 有 126 層，每 PP stage ~31 層
- DP=8：32 / (PP=4) = 8 個 data parallel replicas
(3) 通訊分析：TP 用 NVLink（900 GB/s，無瓶頸）；PP 跨節點傳 activation（幾 MB/micro-batch，延遲敏感）；DP 跨 8 組同步梯度（但 ZeRO-1 已足夠，記憶體由 TP+PP 解決）。
Megatron-LM 預設：TP=8, PP=4-8, DP=remaining，與分析一致。

Q3：Gradient Accumulation 如何減少通訊次數？它有什麼代價？8 步累積和 1 步同步在 16 節點場景下的通訊時間差多少？

A：
機制：Gradient Accumulation = 本地跑 K 個 micro-batch，梯度本地相加，最後只做 1 次 AllReduce。通訊次數從 K 次降到 1 次。
時間差（70B, 16 nodes, 400 Gbps, eff=0.7）：
- 每次 AllReduce ≈ 2×(15/16)×140GB / (50×0.7 GB/s) ≈ 7.5 秒
- 1 步同步：每 step 都等 7.5s
- 8 步累積：每 8 steps 等 7.5s = 平均 0.94s/step
- 節省：7.5 - 0.94 = 6.56s/step × 假設 10,000 steps = 18.2 小時！
代價：
(1) 等效 batch size = K × micro_batch × DP_size。可能太大影響收斂。
(2) 記憶體：需存 activation 給 K 個 micro-batch（或用 activation checkpointing）。
(3) 收斂：大 batch 可能需要 learning rate warmup / LAMB optimizer。

Q4：你的 AllReduce benchmark 在 4 節點跑 350 Gbps，但擴到 32 節點時掉到 220 Gbps。最可能的硬體瓶頸是什麼？怎麼驗證？

A：最可能原因：交換機 oversubscription（非 full-bisection bandwidth）。
解釋：4 節點可能都在同一 leaf switch 下（直接互連，無 spine 瓶頸）。32 節點跨多個 leaf，流量經 spine switch。如果 spine uplink 頻寬 < leaf 下行總和（如 2:1 oversubscription），跨 leaf 通訊就會塞車。
驗證方法：
(1) 測試 intra-leaf pair vs inter-leaf pair 的 iperf3/nccl-tests 差異
(2) 確認交換機 fabric 拓撲（ibnetdiscover 或雲端 placement group 設定）
(3) 如果是 AWS：確認所有節點在同一 placement group（cluster strategy）
修復：用 non-blocking fat-tree spine、或 AWS cluster placement group、或 rail-optimized topology（每 GPU 走獨立 rail 到獨立 spine）。

Q5：為什麼 AWS EFA 的 p5.48xlarge 標稱 3200 Gbps 但實際 AllReduce 達不到？和 InfiniBand 400 Gbps 比哪個實際更快？

A：
3200 Gbps 是多 NIC 聚合：p5.48xlarge 有 32 個 EFA 介面（每個 100 Gbps）。NCCL 需要正確配置 multi-NIC（NCCL_NET_GDR_LEVEL、NCCL_SOCKET_NTHREADS），否則只用到部分介面。
SRD vs IB Verbs：EFA 用 SRD（Scalable Reliable Datagram）不是傳統 RDMA，有輕微 protocol overhead。實測 bus bandwidth 通常到 2400-2800 Gbps（理論的 75-87%）。
vs InfiniBand 400 Gbps：EFA 實際 ~2500 Gbps >> IB 400 Gbps × 效率 80% = 320 Gbps。所以 EFA p5 遠快於單 port IB。
但 HPC 叢集通常每節點有 8× IB port（8×400 = 3200 Gbps），此時和 EFA 相當。
結論：p5 EFA 在大訊息 AllReduce 幾乎和頂級 IB 集群打平，優勢在彈性和免硬體維護。

3.1.1 DDP (Distributed Data Parallel)

概念：最基礎的多 GPU 訓練。每張卡有完整模型副本，各自處理不同 batch，backward 時 AllReduce 同步梯度。

限制：模型必須能完整放進單卡記憶體（含 optimizer states）。

3.1.2 ZeRO / FSDP

核心思想：既然 DDP 每張卡都存完整副本很浪費，不如把 optimizer states / gradients / parameters 切片分散。

ZeRO Stage分散內容記憶體節省（N張卡）通訊量
Stage 1Optimizer States~4x → 分N份同 DDP
Stage 2+ Gradients~6x → 分N份同 DDP
Stage 3+ Parameters~8x → 分N份1.5x DDP
"""
FSDP (Fully Sharded Data Parallel) = PyTorch 原生 ZeRO Stage 3
概念：模型參數、梯度、optimizer 全部切片分散
WHY：不需要 DeepSpeed，原生 PyTorch 就能訓練超大模型
"""
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    ShardingStrategy,
)
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy
from transformers import LlamaDecoderLayer

# 混合精度設定
mixed_precision_policy = MixedPrecision(
    param_dtype=torch.bfloat16,
    reduce_dtype=torch.bfloat16,
    buffer_dtype=torch.bfloat16,
)

# 自動包裝策略：每個 Transformer Layer 獨立 shard
auto_wrap_policy = transformer_auto_wrap_policy(
    transformer_layer_cls={LlamaDecoderLayer}
)

model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # = ZeRO-3
    mixed_precision=mixed_precision_policy,
    auto_wrap_policy=auto_wrap_policy,
    device_id=torch.cuda.current_device(),
    limit_all_gathers=True,
)

# ShardingStrategy 選項：
# FULL_SHARD = ZeRO-3（最省記憶體）
# SHARD_GRAD_OP = ZeRO-2（省記憶體 + 快）
# NO_SHARD = DDP（最快，記憶體最多）
# HYBRID_SHARD = 節點內 FULL_SHARD + 節點間 DDP（推薦多節點）

3.1.3 Tensor Parallelism (TP)

概念：把單一層的矩陣運算切割到多張 GPU。例如一個 [4096, 4096] 的線性層，切成 4 份 [4096, 1024] 分別放在 4 張卡上。

適用場景：同一節點內（NVLink 高頻寬）。跨節點通訊太慢不適合。

通訊模式：Column parallel → AllGather；Row parallel → ReduceScatter。每層需要 2 次集合通訊。

"""
Tensor Parallelism 概念示意（Megatron-LM 風格）
"""
# 概念：一個大矩陣 W [H, 4H] 切成 TP=4 份
# GPU 0: W[:, 0:H]
# GPU 1: W[:, H:2H]
# GPU 2: W[:, 2H:3H]
# GPU 3: W[:, 3H:4H]

# Column Parallel Linear (MLP 第一層)
# 輸入 X 廣播到所有 GPU → 各自算 X @ W_i → 結果 concat

3.1.4 Pipeline Parallelism (PP)

概念：把模型按層切割，前 N 層放 GPU 0，接下來 N 層放 GPU 1...。像工廠流水線。

解法：Micro-batching（GPipe）或 1F1B schedule（PipeDream）減少氣泡。

3.1.5 Sequence Parallelism (SP)

概念：長序列訓練（>8K tokens）時，attention 的記憶體是 O(seq_len²)。SP 把序列切割到多張卡。

搭配：通常和 TP 一起使用。TP 切參數，SP 切 activation（LayerNorm、Dropout）。

3.1.6 Expert Parallelism (EP)

概念：MoE 模型中，每個 expert 放在不同 GPU。Router 決定 token 送到哪個 expert。

通訊：All-to-All。

實例：Mixtral 8x7B 有 8 個 expert，EP=8 時每張卡放一個 expert。

🧪 驗證考題 — 3.1 Model Parallelism

Q1：你有 4 張 A100-80GB（同節點 NVLink），要訓練一個 13B 模型（bf16 params=26GB, AdamW optimizer=156GB）。選哪種並行策略？計算記憶體。

答案：

總記憶體需求：params 26GB + gradients 26GB + optimizer 156GB + activations ~20GB ≈ 228GB

單卡 80GB，4 卡共 320GB。

選 FSDP ZeRO-3 (FULL_SHARD)：參數/梯度/optimizer 各切 4 份。

  • 每卡 params: 26/4 = 6.5GB
  • 每卡 gradients: 26/4 = 6.5GB
  • 每卡 optimizer: 156/4 = 39GB
  • 每卡 activations: ~20GB（不分片）
  • 每卡 total ≈ 72GB ✅ 放得進 80GB

ZeRO-2 不夠（params 26GB 不切，每卡還需 26+26/4+156/4=72.5GB，加 activation 會超）。TP 也可以但 FSDP 更簡單。

Q2：Pipeline Parallelism PP=8，你想把氣泡率降到 10% 以下，至少需要幾個 microbatches？

答案：

公式：bubble = (PP-1) / (PP-1 + M)，要 < 0.1

7 / (7 + M) < 0.1 → 7 < 0.7 + 0.1M → M > 63

至少需要 64 個 microbatches。這也是為什麼 PP 度數越大，需要的 global batch size 越大。

Q3：Tensor Parallelism 為什麼不適合跨節點？給出具體頻寬計算。

答案：

TP 每一層的 forward 需要 2 次 collective（AllGather + ReduceScatter）。以 Llama-3-8B (hidden=4096, TP=4) 為例：

  • 每次通訊量 ≈ 4096 × 4096 × 2 bytes (bf16) = 32MB
  • 32 層 × 2 次/層 = 64 次通訊/forward
  • NVLink (600GB/s): 32MB / 600GB/s = 0.05ms/次 → 可忽略
  • InfiniBand (50GB/s): 32MB / 50GB/s = 0.64ms/次 → 64次 = 41ms overhead

跨節點 41ms overhead 佔 forward 時間 30%+，不划算。PP 只在 stage 邊界通訊一次，跨節點友好。

Q4：HYBRID_SHARD 和 FULL_SHARD 差在哪？什麼時候用？

答案：

  • FULL_SHARD：所有 GPU 間切片。8 節點 × 8 卡 = 64 張卡共同切片。跨節點 AllGather 走 IB 很慢。
  • HYBRID_SHARD：節點內 FULL_SHARD（8 卡切片，NVLink 快），節點間 DDP（只 AllReduce 梯度）。

選擇標準：如果模型切成「一個節點的卡數」份就能放進記憶體 → HYBRID_SHARD。如果連切到一個節點內都放不下 → FULL_SHARD。

例：70B bf16，params=140GB。8 卡切片 = 17.5GB/卡 ✅ → HYBRID_SHARD。405B bf16=810GB，8 卡切片 = 101GB/卡 ❌ → 需要 FULL_SHARD 跨節點切。

Q5：你的團隊要訓練 Mixtral 8x22B (MoE)，共 141B 活躍參數。有 128 張 H100。設計並行策略。

答案：

Mixtral 8x22B：每個 expert 22B，8 個 experts，shared layers ~9B。總量 ≈ 176B，但每 token 只激活 2 experts (44B + 9B = 53B 活躍)。

策略（128 H100 = 16 nodes × 8 GPUs）：

  • EP=8：8 個 experts 放 8 張卡（每卡 1 expert = 22B × 2 bytes = 44GB）
  • TP=2：每個 expert 內部再切 2 份（22GB/卡）— 因為 22B 的 optimizer 要 264GB
  • DP=8：128 / (EP8 × TP2) = 8 份 data parallel

每卡記憶體：expert params 22GB + optimizer 66GB (ZeRO-1 on DP8 → 66/8=8.3GB) + activation ≈ 合理放入 80GB。

3.2 GPU 記憶體解剖學

📚 前置知識速覽

  • VRAM vs RAM：GPU 有獨立記憶體（VRAM），A100=80GB、H100=80GB，不能用主機 RAM 直接補
  • fp32/bf16/fp16 差異：fp32=4 bytes, bf16/fp16=2 bytes per number。精度換空間
  • Adam optimizer 原理：對每個 parameter 追蹤一階動量(m)和二階動量(v)，各需同 shape 的 fp32 tensor
  • Activation：forward pass 中間結果，backward 計算梯度時需要。層數×序列長度×隱藏層大小
  • Gradient Checkpointing 概念：不存 activation，backward 時重算。用 30% 時間換 70% 記憶體

"""
GPU 記憶體解剖 — 以 Llama-3-8B 為例
參數量：8.03B parameters
"""
def calculate_training_memory(
    num_params_B: float,
    precision: str = "bf16",
    optimizer: str = "adamw",
    seq_len: int = 4096,
    batch_size: int = 1,
    num_layers: int = 32,
    hidden_size: int = 4096,
    use_gradient_checkpointing: bool = False,
):
    params_B = num_params_B * 1e9
    bytes_per_param = {"fp32": 4, "bf16": 2, "fp16": 2}[precision]
    model_memory_GB = params_B * bytes_per_param / 1e9
    gradient_memory_GB = model_memory_GB

    if optimizer == "adamw":
        # fp32 master copy + fp32 momentum + fp32 variance = 12 bytes
        optimizer_memory_GB = params_B * 12 / 1e9
    elif optimizer == "sgd":
        optimizer_memory_GB = params_B * 4 / 1e9

    if use_gradient_checkpointing:
        activation_GB = (num_layers ** 0.5) * seq_len * hidden_size * batch_size * 34 * 2 / 1e9
    else:
        activation_GB = num_layers * seq_len * hidden_size * batch_size * 34 * 2 / 1e9

    total_GB = model_memory_GB + gradient_memory_GB + optimizer_memory_GB + activation_GB
    return {
        "model_params_GB": round(model_memory_GB, 1),
        "gradients_GB": round(gradient_memory_GB, 1),
        "optimizer_GB": round(optimizer_memory_GB, 1),
        "activations_GB": round(activation_GB, 1),
        "total_GB": round(total_GB, 1),
    }

3.3 訓練效能優化

📚 前置知識速覽

  • FLOPS：Floating Point Operations Per Second，GPU 每秒能做多少次浮點運算

Q3：effective batch size = 2048 tokens × 512 sequences = 1M tokens。你有 8 GPU，每卡只能放 micro_batch=16。如何設定 gradient accumulation？

答案：

effective_batch = micro_batch × grad_accum × num_gpus

512 = 16 × grad_accum × 8

grad_accum = 512 / 128 = 4 steps

每卡做 4 次 forward+backward 累積梯度，才做一次 optimizer.step()。

注意：gradient accumulation 不增加記憶體（梯度 in-place 累加），但增加時間（4x forward+backward per update）。

Q4：torch.compile 為什麼第一次 forward 很慢？怎麼處理？

答案：

第一次慢是因為 compilation overhead：

  • Dynamo tracing：追蹤 Python 計算圖
  • AOTAutograd：生成 backward graph
  • Inductor：生成優化的 Triton/CUDA kernel
  • Auto-tuning：測試不同 kernel 配置找最快的

典型編譯時間：30s-5min（依模型大小）。

處理方法：前幾個 step 設為 warmup，不計入 throughput 統計。或用 torch.compile(mode="default") 減少編譯時間。production 可以 torch._dynamo.config.cache_size_limit 快取編譯結果。

Q5：bf16 訓練時 loss 突然變 NaN，但 fp32 同樣設定正常。原因和解法？

答案：

bf16 精度只有 7-bit mantissa（fp32 有 23-bit）。可能原因：

  • Gradient explosion：梯度值超出 bf16 範圍（>3.4e38 不會，但精度損失累積）→ 解法：降低 learning rate，加 gradient clipping (max_norm=1.0)
  • Loss scale 問題：某些 op（如 cross_entropy 的 log）在極端值時精度不足 → 解法：確保 loss function 在 fp32 計算
  • LayerNorm 的 variance 太小：在 bf16 下接近 0 → 加 eps=1e-5（而非 1e-8）

Debug 技巧：torch.autograd.detect_anomaly() + 逐層檢查 torch.isnan(param.grad).any()

Q1：你有 2 台機器各 8 張 A100 (16 GPUs total)，要預訓練一個 30B 模型。設計完整並行策略並計算記憶體。

答案：

30B bf16 記憶體需求：

  • Params: 60GB, Gradients: 60GB, Optimizer: 360GB, Activation(GC): ~15GB
  • Total: ~495GB。16 卡 × 80GB = 1,280GB 夠用。

策略：FSDP HYBRID_SHARD

  • 節點內 8 卡 FULL_SHARD：每卡 params 60/8=7.5GB + optimizer 360/8=45GB + grad 60/8=7.5GB + act 15GB = 75GB ✅
  • 節點間 DDP：2 節點只需 AllReduce 梯度（60GB 用 bf16 通訊 = 每次 7.5GB 跨 IB）

不需要 TP 或 PP — HYBRID_SHARD 已足夠且最簡單。

Q2：面試題：「你只有 1 張 A100-80GB，要 inference 一個 70B 模型，怎麼做？」

答案：

70B fp16 = 140GB，放不進 80GB。三種方案：

  1. 4-bit 量化 (GPTQ/AWQ)：70B × 0.5 bytes = 35GB + KV cache ~10GB = 45GB ✅
  2. CPU offload (llama.cpp)：部分層放 CPU RAM，逐層搬到 GPU 計算。慢但能跑。
  3. 8-bit 量化 (bitsandbytes)：70B × 1 byte = 70GB + overhead ≈ 78GB 勉強塞進 80GB

推薦：4-bit AWQ，精度損失 <1% perplexity，速度接近 fp16 的 80%。

Q3：你的 MoE 模型有 16 experts × 7B params each + 3B shared。設計 EP+TP+DP 策略 for 64 H100。

答案：

總參數：16×7B + 3B = 115B（但每 token 只激活 2 experts = 14B + 3B = 17B）

  • EP=16：16 experts → 16 GPUs，每卡 1 expert (7B × 2 bytes = 14GB)
  • TP=1：7B 單卡放得下，不需 TP
  • DP=4：64 / 16 = 4 份 data parallel

每卡記憶體：expert 14GB + shared 6GB + optimizer(ZeRO-1 on DP4) (7B×12/4)=21GB + activation ~10GB = 51GB ✅

通訊：All-to-All for expert routing（每 token 需要送到正確 expert 所在的 GPU）。確保用 NVLink 或高速 IB。

Q4：客戶說「我們只要微調 Llama-3-70B 加入 domain knowledge，預算 4 張 A100」。推薦方案？

答案：

4 張 A100 = 320GB。Full fine-tuning 70B 需要 ~1,266GB → 不可能。

推薦：QLoRA (4-bit + LoRA rank=64)

  • 模型 4-bit: 35GB（分到 4 卡各 ~9GB with device_map="auto"）
  • LoRA params: ~0.14GB
  • Optimizer: ~0.84GB
  • Total per card: ~12GB → 可以用大 batch！

或者 FSDP + LoRA (bf16) 如果精度要求高：模型 140GB/4=35GB/卡 + LoRA optimizer 夠放。

QLoRA 效果通常接近 full fine-tuning 的 95%+，是預算有限的最佳選擇。

Q5：面試終極題：從零設計 GPT-4 級別 (1.8T MoE) 的訓練基礎設施。需要多少 GPU？什麼並行策略？預估訓練時間？

答案：

假設：1.8T params MoE (16 experts × 111B + shared 24B)，每 token 激活 2 experts (222B + 24B = 246B active)

記憶體估算：

  • 每 expert 111B bf16 = 222GB → 單卡放不下 → 需要 TP
  • TP=8 per expert: 222/8 = 27.5GB/卡
  • EP=16: 16 experts 各佔 8 卡 = 128 卡 for experts
  • PP=4: 把 shared layers + routing 分 4 stages
  • DP=8: 數據並行
  • Total: 128(EP×TP) × 4(PP) × 8(DP) ≈ 4,096 H100

訓練時間：

  • 假設 10T tokens，MFU 40%
  • FLOPS needed: 6 × 246B × 10T = 14.8e24 FLOPS
  • 4096 × H100 989 TFLOPS × 40% MFU = 1.62e18 FLOPS/sec
  • Time = 14.8e24 / 1.62e18 = 9.1e6 sec ≈ 105 天

這與已知 GPT-4 訓練規模（數千 A100，3-6 個月）一致。

"""
概念：CUDA OOM 是 ML 最常見的錯誤
當 GPU VRAM 不夠時，PyTorch 會拋出：
RuntimeError: CUDA out of memory. Tried to allocate X GiB
(Y GiB already allocated; Z GiB free; W GiB reserved)

關鍵欄位解讀：
- allocated = 你的 tensor 實際用了多少
- reserved = PyTorch caching allocator 預留的總量
- free = 當前可用
- reserved - allocated = 記憶體碎片（被鎖住但沒用到的）
"""
import torch

def print_gpu_memory(tag=""):
    """即時印出 GPU 記憶體使用狀況"""
    if torch.cuda.is_available():
        allocated = torch.cuda.memory_allocated() / 1024**3
        reserved = torch.cuda.memory_reserved() / 1024**3
        max_allocated = torch.cuda.max_memory_allocated() / 1024**3
        print(f"[{tag}] Allocated: {allocated:.2f} GB | "
              f"Reserved: {reserved:.2f} GB | "
              f"Peak: {max_allocated:.2f} GB | "
              f"Fragmentation: {reserved - allocated:.2f} GB")

# 在 training loop 的關鍵位置插入

loss.backward()

from torch.utils.checkpoint import checkpoint

class CheckpointedTransformerBlock(nn.Module):

📝 理解確認

Q1：PyTorch 報 OOM 時顯示 "74.12 GiB already allocated" 但 nvidia-smi 顯示 76.80 GiB used，差異從哪來？

A1：差異來自 PyTorch 的 caching allocator。"reserved" 是 PyTorch 向 CUDA 要來但還沒分配給 tensor 的記憶體池（為了避免頻繁 malloc）。nvidia-smi 看到的是 reserved 總量，而 allocated 是實際在用的。差值 = 記憶體碎片 + 預留池。

Q2：Gradient checkpointing 為什麼能省記憶體？代價是什麼？

A2：正常 forward 會保留所有 layer 的 activation 給 backward 用。Checkpointing 只保留少數 checkpoint 點的 activation，backward 到某段時重新 forward 計算。省 O(N) → O(√N) 記憶體，代價是約多 33% 計算時間（重算一次 forward）。

Q3：Adam optimizer 為什麼需要 2 倍 model parameter 的額外記憶體？

A3：Adam 對每個 parameter 維護兩個 state：(1) first moment (mean of gradients)，(2) second moment (mean of squared gradients)。每個都跟 parameter 同 shape 同 dtype，所以 7B params × fp32 × 2 states = 56 GB 額外記憶體。

class ForkedPdb(pdb.Pdb):

        finally:

    if dist.get_rank() == 0:

import torch
from torch import nn

class NaNDetector:
    """Hook-based NaN 偵測器：在每個 layer 的 output 檢查 NaN/Inf"""
    def __init__(self, model):
        self.hooks = []
        self.nan_detected = False
        for name, module in model.named_modules():
            hook = module.register_forward_hook(self._make_hook(name))
            self.hooks.append(hook)
    
    def _make_hook(self, name):
        def hook(module, input, output):
            if isinstance(output, torch.Tensor):
                if torch.isnan(output).any():
                    print(f"⚠️ NaN in: {name}, count={torch.isnan(output).sum()}")
                    self.nan_detected = True
                if torch.isinf(output).any():
                    print(f"⚠️ Inf in: {name}, count={torch.isinf(output).sum()}")
        return hook
    
    def remove_hooks(self):
        for h in self.hooks:
            h.remove()

# Gradient Norm 監控
def check_gradients(model, step, threshold=100.0):
    total_norm = 0.0
    for name, p in model.named_parameters():
        if p.grad is not None:
            param_norm = p.grad.data.norm(2).item()
            total_norm += param_norm ** 2
            if param_norm > threshold:
                print(f"  🚨 Step {step}: {name} grad_norm={param_norm:.2f}")
    return total_norm ** 0.5

Q1：Your 70B model gets NaN at step 5000 — describe your systematic debug workflow step by step.

Answer：

  1. 確認可重現性：固定 seed + 同筆 data 重跑。如果不能重現 → 可能是 race condition 或硬體問題
  2. 縮小搜索範圍：加 NaNDetector hook，找到第一個產生 NaN 的 layer name
  3. 檢查 gradient norm history：看 step 4990-5000 的 gradient norm 是否急速上升（gradient explosion 前兆）
  4. 檢查 loss scale：如果用 AMP，查看 loss scaler 是否頻繁 skip steps（grad_scaler._scale 變很小）
  5. 檢查該 batch 的資料：是否有異常 token（全是 padding、超長序列、label 有非法值）
  6. 開啟 detect_anomaly：torch.autograd.set_detect_anomaly(True) 定位 backward 中哪個 op 產生 NaN
  7. 常見 root cause：LayerNorm eps 太小 + fp16 underflow、attention score 沒加 mask 導致 softmax(-inf)、learning rate 過高導致 weight 發散
  8. 修復後驗證：gradient clipping (max_norm=1.0) + 降低 lr + 從 step 4900 checkpoint 恢復繼續訓練
Q2：Training 卡住 30 分鐘沒有任何 output，GPU utilization 顯示 0%。如何診斷？

Answer：

  1. strace -p PID：看 process 卡在什麼 syscall
    • futex(WAIT) → 在等 lock，很可能是 NCCL collective op timeout（某個 rank 掛了或網路斷了）
    • read(fd=N) blocking → DataLoader 在等 IO（NFS 慢、disk full）
    • poll() → 在等網路事件
  2. 檢查所有 node 的 rank process 是否存活：pdsh -w node[0-3] "ps aux | grep train"
  3. NCCL debug：重跑加 NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=ALL 看哪個 collective 卡住
  4. 常見原因：某個 node 的 GPU 掛了（ECC error）、InfiniBand 鏈路斷、某個 rank 的 DataLoader 遇到 corrupted file 卡在 retry
  5. 預防：設定 NCCL_TIMEOUT=1800（30min 後自動報錯而非永久卡住）、加 watchdog timer
Q3：你的 8×A100 訓練 OOM 了，但 nvidia-smi 顯示只用了 45GB/80GB。為什麼？如何解決？

Answer：

原因：PyTorch caching allocator 的記憶體碎片化。雖然「總量」夠，但沒有一塊「連續」的空間能容納新的大 tensor allocation。

診斷：torch.cuda.memory_summary() 看 "Inactive" segments 是否很多 → 碎片化嚴重。

解法（按優先級）：

  1. torch.cuda.empty_cache() — 歸還未使用的 cached blocks 給 CUDA
  2. 設定 PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:128 — 限制 allocator 切分 block 的最大 size，減少碎片
  3. 減少 variable-length sequences（padding to fixed length 避免不同大小的 allocation）
  4. 用 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True（PyTorch 2.1+）讓 allocator 動態擴展 segment
Q4：如何用 Tiny Model 策略在 10 分鐘內驗證一個新的 training pipeline 是否正確？列出步驟和你會檢查的 assertions。

Answer：

  1. 建立 tiny model：保持原始 architecture（attention type, positional encoding），只縮小 hidden_size=64, layers=2, heads=2
  2. 建立 tiny dataset：100 個 samples，sequence length=128，確保有 edge cases（空序列、最大長度）
  3. 跑 50 steps 檢查以下 assertions：
    • ✅ Loss 在前 10 steps 單調下降（確認 gradient flow 正常）
    • ✅ loss.item() < initial_loss after 50 steps
    • ✅ 所有 parameters 的 .grad is not None（沒有 detached graph）
    • ✅ gradient norm > 0 且 < 100（不是 vanishing 也不是 exploding）
    • ✅ 沒有 NaN/Inf in any activation
    • ✅ checkpoint save → load → 同 input 得到同 output（序列化正確）
  4. 如果用 distributed：在 2 GPU 上跑 DDP tiny model，確認 loss 和 single-GPU 一致（gradient sync 正確）
Q5：Mixed precision training 中 loss scale 持續降到 1.0 且 training loss 停滯不動。診斷原因及修復方法。

Answer：

症狀解讀：Loss scaler 反覆偵測到 Inf/NaN gradient → skip step → 降低 scale。當 scale 降到 1.0，fp16 gradient 已經沒有被放大，微小的 gradient 直接 underflow 成 0 → 模型停止學習。

Root Cause 排查：

  1. 某些 layer 的 weight magnitude 差異極大 → 部分 gradient 在 fp16 下 overflow
  2. Learning rate 太高 → gradient 爆炸 → scaler 不斷 skip
  3. 某個 layer（通常是 embedding 或 final projection）不適合 fp16

修復：

  1. 降低 learning rate 2-4x
  2. 對問題 layer 強制使用 fp32：model.lm_head = model.lm_head.float()
  3. 改用 bf16（不需要 loss scaling，因為 exponent range 和 fp32 一樣）
  4. 增加 growth_interval（scaler 嘗試恢復的間隔步數）讓 scale 有時間穩定

# KV Cache 記憶體估算
def estimate_kv_cache_memory(
    batch_size: int, seq_length: int, num_layers: int,
    num_kv_heads: int, head_dim: int, dtype_bytes: int = 2,
) -> float:
    """
    KV Cache size = 2 × layers × kv_heads × head_dim × seq_len × batch × dtype
    '2' 因為要存 K 和 V 兩份
    """
    cache_bytes = (2 * num_layers * num_kv_heads * head_dim 
                   * seq_length * batch_size * dtype_bytes)
    return cache_bytes / (1024 ** 3)

# Llama-2-70B: 32 concurrent 4K requests
print(estimate_kv_cache_memory(
    batch_size=32, seq_length=4096, num_layers=80,
    num_kv_heads=8, head_dim=128, dtype_bytes=2,
))  # → ~10 GB just for KV Cache

Q1：你要 serve 一個 70B 模型給 100 concurrent users（每人 4K context）。計算需要多少 GPU，選擇什麼引擎，解釋 tradeoff。

Answer：

記憶體計算：

  • Model weights (fp16): 70B × 2 bytes = 140 GB
  • KV Cache (100 users × 4K): estimate_kv_cache_memory(100, 4096, 80, 8, 128, 2) ≈ 32 GB
  • Activation + overhead: ~20 GB
  • Total: ~192 GB VRAM minimum

GPU 選擇： 3× A100 80GB (TP=3) 或 2× H100 80GB (TP=2)。4× A100 更寬裕能支撐 burst。

引擎選擇： vLLM — 因為高 concurrent user 場景需要 continuous batching + PagedAttention 最大化 throughput。TensorRT-LLM 如果 latency 更重要（< 100ms TTFT）。

Tradeoff： TP=4 比 TP=2 延遲略高（多一次 AllReduce），但能容納更多 KV Cache。可以用 INT8 量化把 model 降到 70GB，省 1 張卡但 perplexity 升 0.01。

Q2：用戶抱怨 TTFT 太慢（5 秒），但 TPS 正常。分析可能原因及優化方案。

Answer：

TTFT 慢 = Prefill 階段（處理 prompt）太慢。

可能原因：

  1. Prompt 太長：4K+ tokens 的 prefill 在 70B 模型上本身就要幾秒。Prefill 是 compute-bound（O(n²) attention）
  2. 排隊等待：前面有很多 request 正在 decode，新 request 的 prefill 被排在後面
  3. 模型載入/冷啟動：第一個 request 觸發 model loading
  4. KV Cache 分配延遲：需要為 4K context 預分配大塊 memory

優化方案：

  1. Chunked Prefill（vLLM 支援）：把長 prompt 切成小塊，穿插在 decode steps 之間，減少 head-of-line blocking
  2. Prefix Caching：如果多個 request 共享相同 system prompt，cache 其 KV → TTFT 只需算 user-specific 部分
  3. Speculative Decoding 的 prefill 優化：用小模型先做 prefill 得到初始 KV，大模型 verify
  4. Separate prefill / decode pools：用不同的 GPU 群組分別處理 prefill-heavy 和 decode-heavy workload
Q3：INT4 量化後模型在特定 task（code generation）品質明顯下降，但 general QA 正常。如何診斷和修復？

Answer：

診斷：

  1. Perplexity 分析：在 code corpus 上算 perplexity。如果 INT4 比 fp16 高 > 5% → 量化對 code token 有損傷
  2. Layer-wise 分析：量化每一層後分別測品質，找到哪些層對 code 最敏感（通常是前幾層 embedding 和最後幾層 lm_head）
  3. Token-level 比較：fp16 vs INT4 在相同 prompt 下的 top-5 token probability 差異

修復方案：

  1. Mixed-precision quantization：敏感層保持 fp16/INT8，其他層用 INT4（GPTQ 的 act_order=True 有幫助）
  2. AWQ (Activation-Aware Quantization)：根據 calibration data 中每個 weight channel 的 activation magnitude 決定量化精度
  3. Calibration dataset 換成 code：GPTQ/AWQ 的 calibration data 如果全是 prose text，量化可能犧牲 code-relevant 的 weight precision。混入 code 作為 calibration data 可改善
  4. 嘗試 GGUF Q5_K_M：比 Q4 多 1 bit 但品質顯著提升，compromise 方案
Q4：解釋 PagedAttention 如何解決 KV Cache 的記憶體碎片問題。和傳統方法相比省多少？

Answer：

傳統方法的問題：

  • 為每個 request 預分配 max_seq_len 的連續 KV Cache block（如 4096 tokens）
  • 但實際生成可能只用 200 tokens → 剩餘 3896 的空間浪費
  • 不同 request 長度不同，產生大量外部碎片
  • 實際 GPU memory utilization 通常只有 20-40%

PagedAttention 解法：

  • KV Cache 被切成固定大小的「page」（如 16 tokens/page）
  • 每個 request 按需分配 page（用了 200 tokens = 13 pages）
  • Page 不需要物理連續 — 用 page table 映射（和 OS virtual memory 完全相同概念）
  • Request 結束後 page 可以立刻回收給其他 request

節省量：vLLM 論文報告 PagedAttention 讓 throughput 提升 2-4x（相同硬體），因為能同時 serve 更多 concurrent requests（memory waste 從 60-80% 降到 < 4%）。
